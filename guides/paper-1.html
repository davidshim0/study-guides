SOSP 2026 · A Field Guide

Keep the mutable part small, let the rest go stale on purpose

CXL will give you terabytes of shared memory, but hardware only keeps a sliver of it coherent. This is the plain-English story of Prism, an index that wins by borrowing a 1996 disk data structure.

📄 "Disk-Based LSMs: An Unexpectedly Good Index for Partly Coherent CXL Memory" · Hombal et al. 🎓 CXL/tiering background assumed — primers cover the index internals ⏱ ~30 min read
🗂️

Confine in-place updates to a slice small enough to fit in the coherent region — leave the rest immutable so it needs no coherence tracking at all.

Quick glossary, then the concepts behind Prism

The paper's acronyms up front, then collapsible primers — open whichever is unfamiliar.

Acronyms, defined once

CXLCompute Express Link — a cache-coherent interconnect letting multiple hosts load/store into a shared memory device.
scrsmall coherent region — the slice of CXL memory (~128 MB) hardware keeps cache-coherent across hosts.
lnrlarge non-coherent region — the remaining terabytes of CXL memory with no hardware coherence guarantee.
ART / OLCAdaptive Radix Tree; Optimistic Lock Coupling — a fast in-memory index and its lock-free concurrency scheme using per-node version numbers.
LSMLog-Structured Merge tree — a disk-oriented structure: a small mutable memtable plus immutable, sorted SSTables merged by background compaction.
SSTableSorted String Table — an immutable, sorted on-disk/in-memory file produced when a memtable is flushed.
BULBounded Updatable Layer — Prism's addition: a size-capped, in-place-updatable ART sitting between the memtable and SSTables.
Updatable surface areaThe portion of a data structure that can be modified in place — the paper's central diagnostic concept.
scr — hardware-coherent version-number overflow / false invalidation Prism's machinery (memtable, BUL, SSTables) lnr — non-coherent, needs software coherence
1Why CXL memory isn't fully coherent▾

CXL 3.0 defines a hardware coherence protocol, but vendors report that snoop filters and back-invalidation become too expensive once shared memory exceeds a few hundred MB. So real systems keep a small scr coherent and leave the rest (lnr) uncoherent.

Now you're ready: any index spanning more than a few hundred MB must solve the coherence problem for the lnr itself — in software.
2Software coherence, in one sentence▾

Store a small piece of metadata (a version number) for each shared object in the scr, where hardware keeps it coherent. Before trusting a cached copy of data in the lnr, check the version number; if it changed, flush your cache and re-read.

Now you're ready: this works only if the version numbers themselves fit in scr — which is exactly where in-memory indexes break.
3ART and OLC version numbers▾

ART already tags every tree node with a version number for lock-free concurrency (OLC): writers bump it, readers compare it. Porting ART to CXL just moves these version numbers into scr — one per node, since any node can be modified.

Now you're ready: "one version number per node" sounds cheap until you count the nodes in a 100M-key tree.
4LSMs: memtable + immutable SSTables▾

An LSM buffers writes in a small in-memory memtable; once full, it's frozen and written out as an immutable SSTable. SSTables are merged (compacted) in the background and never modified in place — only deleted.

Now you're ready: "immutable" is the property Prism exploits — immutable data needs no per-object coherence tracking.
5False invalidation▾

If one version number covers a whole node of many keys, updating any single key bumps that version number — forcing every host caching any key in that node to flush and re-fetch the entire node, even the keys that didn't change.

Now you're ready: bigger nodes fix the "too many version numbers" problem but create this one instead.
6Updatable surface area▾

The fraction of a data structure that can receive in-place writes. In ART/B-trees, every node from root to leaf qualifies — the whole tree. The paper's core diagnosis: a large updatable surface area forces a lose-lose between version-number overflow and false invalidation.

Now you're ready: the entire design of Prism is an exercise in shrinking this one quantity.
The whole story in one place

Prism in a nutshell

The dilemma, the surprising fix, and the one enhancement that makes it practical.

Building a range index for partly coherent CXL means tracking coherence metadata in a tiny scr for data that mostly lives in a huge lnr. Porting ART or B-trees with per-node version numbers hits a dead end: small nodes mean too many version numbers to fit in scr (forcing flushes on every access); large nodes fit in scr but cause false invalidation on every write. Either way, both in-memory indexes have a large updatable surface area — any node, anywhere, can change — so every node needs a version number.

The paper's surprising fix: use LSMs, designed for disks, because they already confine in-place updates to a small memtable while the bulk of the data sits in immutable SSTables that need zero coherence tracking during their lifetime. Porting this directly (SC-LSM) already beats SC-ART and matches/beats SC-BTree. But plain LSMs have a known weakness: under heavy writes, compactions can't drain level-0 fast enough, so reads must probe many overlapping SSTables.

Prism's second idea exploits something unique to memory (not disk): random in-place writes are cheap in RAM, so a controlled amount of in-place updating can replace repeated SSTable creation. Prism adds a Bounded Updatable Layer (BUL) — an in-place-updatable ART, deliberately size-capped so its fine-grained version numbers still fit in scr — plus an scr-resident memtable repurposed as a cache for hot keys, filtering out one-hit-wonder writes before they ever occupy the memtable's slice of scr (they still land in BUL, which has its own bounded, scr-resident version entries — so they avoid memtable scr pressure, not scr entirely).

The payoff: with a realistic 128 MB scr, Prism beats SC-BTree by up to 9.4× on write-heavy workloads and SC-ART by up to 5.8× on reads, and outperforms existing CXL systems Tigon and Megalon by up to 15.1× — while bounding scr usage regardless of dataset size.

🍯 Key takeaways

  • In-memory indexes (ART, B-tree) have a large updatable surface area — every node can change, so every node needs a version number.
  • That forces a dilemma: small nodes → version numbers overflow scr; large nodes → false invalidation on writes.
  • LSMs confine updates to a small memtable; large immutable SSTables need no coherence tracking — SC-LSM already wins.
  • Prism's BUL adds back a bounded amount of in-place updating to cut compaction pressure, without losing the scr-fit guarantee.
  • Prism's memtable is a cache for hot keys, not a write buffer — one-hit wonders skip it entirely and never consume the memtable's scr capacity (they still pass through BUL's own bounded version entries).
  • Result: up to 9.4× over SC-BTree, 5.8× over SC-ART, 15.1× over prior CXL systems, with bounded scr usage.
Five everyday pictures

How to think about Prism

Each stands alone. Every card ends with where the picture breaks down.

The dilemma · Updatable surface area

Every apartment needs its own mailbox

If any resident in a huge building might receive mail at any time, you need one mailbox per apartment. A small building, that's fine. A skyscraper of 40 million apartments (ART's node count at 100M keys), and the mailboxes themselves don't fit in the lobby (scr) anymore — residents start fetching mail from a remote annex (lnr) every single time, flush required.

Where it breaks: merging apartments into big mailrooms (larger nodes) fits the lobby again, but now everyone in a mailroom gets notified whenever anyone's mail arrives — the false-invalidation problem.
The fix · LSM's small updatable core

A sealed, dated filing cabinet

Instead of letting anyone scribble on any page of a filing system, you write new entries on a small notepad (memtable). When the notepad fills, you photocopy it, seal it in a dated folder (SSTable), and file it away — never to be edited again, only eventually shredded. You only ever need to track "has this folder's seal been broken" (an SSTable ID), not "has any page inside changed."

Where it breaks: if you write to the same name over and over, you create a new sealed folder every time — producing far more folders than necessary. That's the compaction bottleneck BUL fixes.
BUL + memtable · The triage

An ER, not a general clinic

A waiting room (BUL) sees everyone first. Patients who keep coming back for the same recurring issue (repeated writes to the same key) get fast-tracked into a dedicated small clinic (the memtable) with the best equipment (hardware coherence). One-time visitors (one-hit wonders) are treated in the waiting room and discharged straight to long-term records (SSTables) — they never occupy the scarce clinic beds.

Where it breaks: the clinic (memtable) has a strict bed limit (64 MB); when full, the least-recently-seen patients are discharged back to the waiting room, not held indefinitely.
Compaction pressure · L0 pileup

An inbox nobody empties fast enough

If letters (SSTables) arrive at your mail slot (L0) faster than your assistant (compaction) can file them into labeled drawers (L1+), the slot overflows. Now finding any one letter means searching the entire pile at the slot — exactly why reads probe 49 SSTables at 50% writes versus 15 at 5%.

Where it breaks: the real fix isn't hiring a faster assistant — it's writing fewer letters in the first place, which is what BUL does by absorbing repeat writes before they become letters.
The full explanation

How Prism actually works

From the dilemma to the three-tier architecture, with the paper's key diagrams rebuilt.

1 · Why ported in-memory indexes fail

Porting ART/B-tree to the partly-coherent model means storing per-node OLC version numbers in scr while nodes live in lnr. With small nodes (ART's typical Node4, ~40 B), a 100M-key dataset has ~40M nodes — scr coverage falls below 50%, so accessing an overflowed version number costs a mandatory flush. Enlarging nodes (SC-BTree, fan-out 128) fits all version numbers in scr, but now every single-key write invalidates the whole node for every host caching it.

⚠
Measured cost: at 50% writes, SC-BTree (fan-out 128) collapses to 1.8M ops/s (§3.3) — far below the ~12M ops/s SC-ART reaches, but that SC-ART figure is the idealized fits-in-scr / unlimited-scr configuration, not the realistic flush-heavy SC-ART baseline it's normally compared against — purely from false invalidations.

2 · LSMs: confining updates by construction

An LSM's memtable absorbs all in-place writes; once frozen, it becomes an immutable SSTable. Since SSTables never change during their lifetime, no per-SSTable version number is needed — only a strictly-increasing SSTable ID (kept in scr) to detect when a region has been recycled by compaction. Porting this (SC-LSM) already avoids most of the flush traffic that sinks SC-ART and SC-BTree.

3 · BUL — reducing compaction pressure

Without BUL, every memtable flush creates a new SSTable at L0, even if it repeats keys from the last flush. BUL instead absorbs memtable evictions in place: repeated writes to the same key update the same BUL entry, so only unique, cold keys eventually get flushed to L0 — fewer SSTables, less compaction, shorter read paths. BUL is deliberately bounded so its fine-grained per-node version numbers (packed into a 64-bit word: obsolete bit, lock bit, access bit, 42-bit version counter, 16-bit node ID, node-type bits) still fit entirely within scr.

💡
Why does this only work in memory? Disk-based LSMs can't do this — in-place updates mean random disk writes, which erase the sequential-I/O advantage LSMs exist for. In CXL memory, random writes aren't prohibitively expensive, so the trick becomes viable.

4 · The scr-aware memtable — a cache, not a buffer

Naively, every write enters the memtable and the whole thing flushes to BUL once full — expensive (one ART insertion per key) and wasteful (one-hit-wonder keys occupy scr for nothing). Prism inverts this: writes go to the memtable only if the key is already there; otherwise they go straight to BUL. A key is promoted to the memtable only once BUL sees a second write to it — proof it's actually hot. The memtable evicts LRU entries back to BUL incrementally, spreading cost over time instead of bulk-flushing.

5 · The read and write paths

# write(key, value)
if key in memtable: update in place; move to LRU head
elif key in BUL:    update in place; promote to memtable, delete from BUL
else:               insert into BUL   # new / one-hit-wonder keys

# read(key)
for tier in [memtable, BUL, L0 (all SSTables), L1..Ln (≤1 via manifest)]:
    if tier.lookup(key) hits: return value
return not_found

L0 SSTables may overlap in key range (each comes from an independent BUL flush), so a read must check every L0 file. From L1 onward, compaction enforces non-overlapping ranges, so the manifest's key boundaries (all in scr) pick out at most one candidate SSTable per level — no extra lnr access just to narrow the search.

Follow the numbers

Worked examples

The paper's real figures, carried through step by step.

① Why SC-ART's version numbers overflow at 100M keys

The paper reports ~4M ART nodes at 10M keys and ~40M nodes at 100M keys, with a 128 MB scr.

  1. At 10M keys: ~4M nodes. Even at a few bytes of version metadata each, 4M nodes fit comfortably in 128 MB.
  2. At 100M keys: ~40M nodes — 10× more, because YCSB's sparse branching keeps most nodes at the smallest Node4 type (~40 B).
  3. scr coverage: the paper measures scr coverage falling below 50% at this size (Fig. 1b).
  4. Consequence: over half of all version-number lookups must go to lnr, each forcing a cache flush — regardless of whether the underlying node actually changed.
🍯
Insight: the failure isn't about ART being slow — it's that coherence metadata for a fine-grained structure scales with dataset size, and scr doesn't.

② Budgeting Prism's 128 MB scr

Figure 5 breaks the scr into three fixed regions. Add them up.

  1. Manifest: 2 MB — tracks active SSTable IDs, levels, key-range boundaries.
  2. Memtable: 64 MB — an ART-backed cache for hot keys, fully hardware-coherent.
  3. BUL version numbers: 62 MB — one 64-bit version word per BUL ART node.
  4. Total: 2 + 64 + 62 = 128 MB — exactly the realistic scr capacity the paper targets, by construction.
💡
Because this split is fixed, Prism's scr usage never grows with dataset size — unlike SC-ART, whose version numbers scale with the number of tree nodes. (The manifest does grow by one entry per SSTable, so extremely large datasets with many small SSTables would eventually press on that 2 MB slice, but at a far coarser, far slower-growing granularity than per-node version numbers.)

③ Why BUL cuts SSTables probed per read

At 5% writes, SC-LSM (no BUL) probes 15 SSTables per read on average; with BUL, only about 2. At 50% writes without BUL, that number rises to 49.

  1. Without BUL: every memtable flush becomes a new L0 SSTable, even for repeated keys — L0 fills with overlapping files faster than compaction drains it.
  2. With BUL: repeated writes to the same key update the same BUL entry in place, so only genuinely cold, unique keys get flushed to L0 — far fewer SSTables created per unit time.
  3. Measured: at 5% writes, adding BUL drops SSTables probed from 15 to about 2 (Fig. 11). At 50% writes, the paper states that SC-LSM+BUL probes "significantly fewer" SSTables than the 49 of plain SC-LSM, without giving an exact figure.
  4. Prism goes further: because its memtable filters out one-hit wonders before they even reach BUL, fewer unique keys churn through BUL too, reducing L0 writes still more.
🍯
Insight: the fix for "too many SSTables" isn't a faster compactor — it's writing fewer SSTables in the first place, by absorbing repeat writes upstream.

④ Reading the throughput wins

Put the headline numbers in context.

  1. Write-heavy YCSB-A: Prism beats SC-BTree by 9.4× because false invalidation collapses SC-BTree's throughput, while Prism absorbs most writes in its upper two tiers.
  2. Read-heavy (YCSB B, C): Prism beats SC-ART by up to 5.8× (version-number overflow), and SC-BTree by up to 1.4× (ART-OLC's SSTable indexes beat B-tree traversal).
  3. Vs. prior CXL systems: up to 15.1× over Tigon-SWcc, whose per-object metadata doesn't fit scr at 100M keys, forcing constant data migration.
  4. Vs. unlimited scr: Prism matches the idealized "SC-ART with infinite scr" on write-heavy workloads and reaches 83–88% of it on read-heavy ones, despite using 128 MB instead of an unbounded amount.
💡
The consistent theme: Prism's wins grow exactly where the baselines' updatable surface area hurts most — writes and large datasets.
Test yourself

Practice problems

Try each before opening the answer — each checks a specific misconception.

Problem 1 · easy
Why can't you just give SC-ART an unlimited amount of scr and call it solved?
Show answer
You could, in simulation — the paper even measures this as an upper-bound comparison. But scr is a scarce hardware resource (expected to be a few hundred MB, not unlimited), because the coherence mechanisms behind it (snoop filters, back-invalidation) become prohibitively expensive at scale. The whole design problem exists because scr must stay small.Misconception: that this is a software/algorithm limitation. It's fundamentally a hardware cost constraint that software must work around.
Problem 2 · medium
SC-BTree with fan-out 128 fits all its version numbers in scr. Why doesn't that make it strictly better than SC-ART?
Show answer
Fitting in scr solves the overflow problem but introduces false invalidation: one version number now covers 128 keys, so any single-key write invalidates the whole node for every host that cached any of those 128 keys. At 50% writes, this collapses SC-BTree to 1.8M ops/s (§3.3) — far below the idealized fits-in-scr/unlimited-scr SC-ART configuration it's compared against there.Misconception: that coarser coherence tracking is free as long as it fits in scr. Coarseness has its own cost — unnecessary flushes on writes — that grows with the write ratio.
Problem 3 · medium
LSMs were designed for disks. Why does the "immutable SSTable" idea transfer to CXL memory, when LSMs' main original benefit (sequential disk I/O) doesn't apply?
Show answer
The paper's thesis is that LSMs help for a different reason in this setting: immutability means SSTables need no per-object coherence metadata during their lifetime — only a cheap SSTable-ID check for recycling. That benefit is about coherence, not I/O pattern, so it transfers even though the original disk-throughput motivation doesn't.Misconception: that LSMs only matter because of sequential writes. Here, their small-updatable-surface-area property is the valuable part, independent of the storage medium.
Problem 4 · hard
Why doesn't Prism use copy-on-write (CoW) B-trees instead of LSMs, since CoW also avoids in-place updates?
Show answer
CoW B-trees suffer severe write amplification: updating one key copies the entire leaf (Θ(B) for leaf capacity B), plus every ancestor node up to the root must also be copied. LSMs instead batch updates across levels, so an overwritten SSTable typically has far more of its content genuinely changed, giving roughly 4× lower write amplification than B-trees in practice (per RocksDB vs. WiredTiger measurements cited in the paper).Misconception: that any "no in-place update" structure is equally good for CXL. Avoiding in-place writes solves coherence, but CoW's amplification cost would squander memory bandwidth that LSM's batching avoids.
Problem 5 · medium
BUL increases the updatable surface area versus a pure SC-LSM. Why doesn't this reintroduce the original scr-overflow problem?
Show answer
Because BUL's size is deliberately bounded — capped so that even fine-grained, per-node version numbers fit within the remaining scr budget (62 MB in Prism's split). The increase in updatable surface area is controlled and sized to a known scr budget, unlike ART/B-tree where the updatable surface area (and thus version-number count) grows with the whole dataset.Misconception: that any increase in updatable surface area is automatically bad. The problem was unbounded growth with dataset size, not in-place updates per se.
Problem 6 · easy
On range scans with only 5% writes, SC-BTree beats Prism. Why, and when does this flip?
Show answer
B-trees store keys in sorted order within large contiguous nodes, making sequential scans cheap, while Prism must merge streams across the memtable, BUL, and multiple SSTable levels — higher per-scan overhead. This flips once the write ratio reaches about 10%: SC-BTree's false invalidations start dominating (8× drop from 5% to 50% writes), while Prism's throughput holds up, overtaking SC-BTree by 6.0× at 50% writes.Misconception: that Prism is strictly better everywhere. It trades off low-write-ratio range-scan efficiency for resilience as writes increase — a known LSM trade-off, not a flaw unique to Prism.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is "partly coherent" CXL memory?▾
A memory model where a small region (scr, ~128 MB) is kept hardware-coherent across hosts, while the rest (lnr, up to terabytes) has no coherence guarantee. Hosts must manage coherence for lnr data themselves, in software, using metadata stored in scr.
Q2What is "updatable surface area" and why does it matter so much?▾
It's the portion of a data structure that can be modified in place. In ART/B-trees, that's the entire tree, so every node needs coherence tracking, and that metadata scales with dataset size — eventually overflowing scr. LSMs confine it to a small memtable (plus, in Prism, a bounded BUL), so coherence metadata stays capped by a fixed scr budget rather than scaling with the number of keys — though the manifest still adds one entry per SSTable, so very large datasets with many small SSTables add some (still bounded) metadata growth at that much coarser granularity.
Q3Why don't SSTables need version numbers at all?▾
Because they're immutable — once written, an SSTable's contents never change, so a cached copy can never go stale during its lifetime. The only coherence concern is reuse: when compaction deletes an old SSTable and recycles its memory, a strictly-increasing SSTable ID (tracked in scr) tells hosts to flush before trusting a region with a new ID.
Q4What problem does BUL solve that SC-LSM alone doesn't?▾
Pure LSMs suffer when writes outpace compaction: L0 fills with overlapping SSTables, and reads must probe all of them (up to 49 at 50% writes). BUL absorbs repeated writes to the same key in place, so far fewer, more unique SSTables are created, keeping L0 small and reads fast.
Q5Why does the memtable act as a "cache" instead of a write buffer?▾
A plain write buffer accepts every write, including one-time keys that waste scarce scr space and require an expensive bulk flush when full. Prism's memtable only holds keys that have already proven hot (via a second write seen in BUL), so one-hit wonders never consume the memtable's scr capacity — though they still pass through BUL, which has its own bounded, scr-resident version entries — and evictions happen incrementally rather than in an expensive batch.
Q6Does Prism avoid Bloom filters on purpose?▾
Yes. Bloom filters exist to avoid expensive disk I/O on negative lookups. In CXL memory, probing an SSTable's internal ART index is already a memory access comparable in cost to checking a Bloom filter, so the extra memory overhead of Bloom filters isn't justified.
Q7How does Prism compare to Tigon and Megalon, the existing CXL coherence systems?▾
Tigon and Megalon both track per-object coherence metadata in scr that grows with the number of shared objects — Tigon must migrate data in and out of CXL when scr fills, and Megalon must constantly reclaim metadata under writes. Prism bounds scr usage regardless of dataset size and outperforms both: up to 15.1× over Tigon-SWcc and 5.5× over Megalon on write-heavy workloads. Megalon does win on pure reads by serving lookups from a local index replica, at the cost of per-host memory overhead.
Q8Does Prism always win?▾
No. At very low write ratios (~5%), SC-BTree's efficient sequential range scans beat Prism's multi-tier merge. With a very small scr (32 MB) and a read-heavy workload (YCSB-B), SC-BTree can edge out Prism slightly because its version numbers still fit and few writes cause invalidation. Prism also performs worse on workloads that are both very write-heavy and have little key skew, since its memtable/BUL have fewer repeated writes to absorb.
Q9What's left for future work?▾
The paper leaves distributed (multi-host) compaction to future work — currently one designated host runs all background compactions and BUL flushes, though the authors argue existing parallel compaction strategies should apply since the manifest already gives hosts a coherent place to agree on live SSTables. Durability is also explicitly out of scope; Prism assumes a fail-stop model with no recovery.

added for teaching
