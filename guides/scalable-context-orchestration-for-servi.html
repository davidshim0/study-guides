SOSP 2026 · A Field Guide

Giving each turn the context it needs — not the whole transcript

A voice agent has to track what you said, how you said it, and the noisy line it arrived over — then decide, every turn, how much of the past is actually worth paying to re-read. This is the plain-English story of llmovoice, a middleware that makes all three explicit.

📄 "Scalable Context Orchestration for Serving LLMs Over Voice" · Jiang, Fu, Zhu 🎓 Basic voice-pipeline/LLM vocabulary assumed — primers cover it ⏱ ~25 min read
🎙️

Reason over WHAT was said, HOW it was said, and what it arrived THROUGH jointly — then hand the model only the SLICE of history it needs, at the fidelity it deserves.

Quick glossary, then the concepts it assumes

First the acronyms you'll see everywhere; then ten primers you can open in any order.

1The LLM context window▾

An LLM answers using only what's inside its context window — the system prompt, the current input, and whatever prior conversation you paste back in. Nothing outside that window exists to the model. Everything you feed it, you also pay to process, every single call.

Now you're ready: the entire paper is about deciding, each turn, what belongs in that window for a voice conversation — and at what level of detail.
2The streaming turn loop▾

Real-time voice systems run turn by turn: the client streams audio in, a VAD module watches for silence to decide the user is done, the service invokes the model, and the generated audio streams back for playback. One "turn" = one round of this loop.

Now you're ready: llmovoice sits inside this loop as middleware — it doesn't replace the model, it decides what the model sees and how it should behave each turn.
3Cascaded vs. speech-native pipelines▾

Older systems cascade: audio → text (STT) → LLM → text → audio (TTS), losing delivery information at each conversion. Newer speech-native models process audio directly, preserving tone and pacing but still needing something to manage context across turns.

Now you're ready: llmovoice targets speech-native, real-time APIs (its prototype uses OpenAI Realtime) — the gap it fills is context management, not speech modeling.
4Why silence isn't always silence▾

VAD infers "the user stopped talking" from low audio energy. But packet loss on the network can also make received audio go quiet — the microphone never stopped, the bytes just didn't arrive. VAD can't tell the difference from energy alone.

Now you're ready: this is the paper's Figure 2 finding — a lost packet burst can trigger a false end-of-turn and make the system interrupt the user mid-sentence.
5Prompt caching, and why it doesn't fix the real problem▾

Prompt caching reuses computation for an unchanged prefix of the context, cutting cost for repeated content. But it doesn't shrink the context itself — if history keeps growing, per-turn processing still scales with history length, and cache hit rates fall for anything unused in the last 5–10 minutes.

Now you're ready: the paper's Figure 3 shows per-turn cost stays roughly linear in history length even with caching — the true fix has to reduce what's in the window, not just speed up processing it.
6Speaking rate as a signal▾

People naturally match each other's pace in conversation (entrainment). A voice agent that replies far slower or faster than the user is often perceived as mismatched. Speaking rate, in words per minute, is a simple way to quantify "how" someone talks.

Now you're ready: this is the paper's representative paralinguistic signal — and it's the one llmovoice measures and acts on in its evaluation. Note: the paper quantifies this as WPM alignment error, not subjective naturalness ratings.
7RAG and embeddings, briefly▾

RAG retrieves relevant text from a store and adds it to the prompt instead of including everything. Relevance is usually found via embeddings — vectors that place similar meanings close together — searched with an index like HNSW for speed.

Now you're ready: llmovoice's memory-to-context path is RAG-flavored, but over voice-specific units (vpages/vthreads) instead of flat text passages — that distinction is a running theme.
8Function calling / typed tool interfaces▾

Many LLM APIs let you declare a fixed set of callable "functions" with typed arguments; the model can emit a structured call to one instead of free text. The caller then validates and executes it — the model never touches the system directly.

Now you're ready: llmovoice's context orchestrator uses exactly this — the LLM emits function calls like set_response_speed, and a validator turns valid ones into runtime directives.
The whole story in one place

llmovoice in a nutshell

The problem, the fix, and how the pieces connect.

Real-time voice LLM systems treat conversation history as a single, ever-growing sequence appended to every request. This ignores two facts specific to voice: the system must track not just what was said but how it was said (paralinguistic state, e.g. speaking rate) and under what conditions it was captured (environmental state, e.g. packet loss) — and it must do so without visual UI, since voice interfaces are UI-less. Left implicit, this causes responses misaligned with user delivery preferences, false interruptions during network trouble, and, because raw history keeps being reprocessed, cost that grows quadratically with session length.

llmovoice is a middleware layer that runs an orchestration loop with two coupled paths. The state-to-control path extracts semantic, paralinguistic, and environmental states each turn and has the same serving LLM reason over them jointly, emitting typed function calls that become runtime directives (response content, delivery speed, turn-taking). The memory-to-context path replaces the flat transcript with two structured units — a VoicePage per completed interaction and a VoiceThread grouping related pages by topic — and a cost-aware context projector selects, per candidate, one of audio / transcript / summary / omit under a fixed budget, degrading the least-relevant items first.

The payoff, measured against real baselines: speaking-rate alignment error down 52.4%; false-interruption rate under packet loss down from 46.0% to 0.9%; network-induced cost down 79.2%; and on long sessions, per-turn cost bounded by the configured context budget rather than growing with history — up to 24.9× cheaper than the naive full-history API while retaining up to 98.7% of its answer quality.

🎙️ Key takeaways

  • A flat, growing transcript is organized primarily around semantic content, leaving paralinguistic and environmental context implicit in the audio rather than managed as explicit state.
  • The context orchestrator reuses the same serving LLM for reasoning about state, so it reasons over the semantic context already loaded in its window, without needing a separate out-of-band controller to keep in sync.
  • VoicePage / VoiceThread give voice memory two levels of structure — one interaction, and a coherent flow of interactions — so retrieval doesn't break cross-turn locality.
  • The context projector degrades fidelity (audio → transcript → summary → omit) in relevance order under a fixed cost budget, in O(N log N), ~1 ms in practice.
  • Prompt caching lowers cost but not its growth rate; llmovoice's bounded context keeps per-turn cost roughly flat, in the evaluated workloads, as history grows.
  • Result: 52.4% lower rate-alignment error, 98.0% fewer false interruptions, up to 24.9× cheaper on long sessions, 88.7–98.7% of full-history answer quality retained.
Six everyday pictures

How to think about llmovoice

Each stands alone — read in any order. Every card ends with an honest note on where the picture breaks down.

The core idea · Three states, one reasoner

Three witnesses to one moment

What was said, how it was said, and the conditions it arrived under are three different witnesses to the same event — and they can disagree. A user asking to "speak faster" while talking slowly is two witnesses pointing opposite ways. llmovoice puts all three in front of one judge (the serving LLM) each turn, rather than three separate rule-checkers that never talk to each other.

Where it breaks: a human judge reconciles witnesses instantly; llmovoice's "judge" is a full LLM call, costing a measured 790.2 ms mean decision latency whenever it actually needs to rule.
Structured memory · vpage / vthread

A diary, not a stenographer's tape

A stenographer's tape is one unbroken scroll — to find the hotel discussion from twenty minutes ago you scan the whole thing. A diary has entries (vpages) grouped under headings you can flip to directly (vthreads: "Trip Planning," "Dining"). When the same day touches two headings, it's cross-referenced under both — thread membership is many-to-many.

Where it breaks: a real diarist chooses their own headings thoughtfully; llmovoice's threads are assigned automatically by embedding similarity at commit time, so a topic that doesn't cleanly cluster can end up under the wrong heading or spawn a stray singleton thread.
Multi-fidelity projection · Something a tiering researcher will recognize

Demoting a page instead of evicting it

Instead of a binary "keep or discard," the least-relevant history first drops from full audio to a plain transcript, then to a compact summary, and only gets dropped ("omitted") if the budget still won't fit — always processed in increasing order of relevance, so the most useful items retain the highest fidelity for as long as the budget allows. It's the same shape as demoting a cold page from DRAM to a slower tier instead of discarding it outright: graceful degradation under a fixed capacity, not a cliff.

Where it breaks: a demoted memory page can usually be promoted back cheaply; a summarized vpage cannot regenerate the audio it discarded — the paper measures a 14.6% transcript-to-summary failure rate where the needed fact survives in the transcript but not the summary.
Turn control · Deferral under packet loss

Waiting out a bad phone signal

When a call breaks up, you don't hang up at the first silent gap — you wait a beat to see if the other person's still there, and only give up after it's clearly dead. defer_response does the same: a provisional turn boundary gets a 1.5-second soft deadline to see if the network recovers, and only a 5-second hard deadline forces the model to respond anyway.

Where it breaks: a human forgives indefinitely if they sense you're still there; llmovoice's hard deadline is fixed at 5 s regardless of how confident the environmental state is that packets are still dropping.
Prompt caching's limits · The ledger analogy

Photocopying pages you still have to carry

Prompt caching is like photocopying instead of hand-copying a page you'll reuse — cheaper per page, but you still bind every photocopy into the same growing folder and carry the whole thing to every meeting. The folder's weight (and the time to flip through it) keeps climbing with session length even though each individual page got cheaper to produce.

Where it breaks: photocopies never expire; cached prefixes do — typically after 5–10 minutes of inactivity — so in practice you don't even get the photocopying discount on content you haven't touched recently.
Typed function interface · Guardrails, not trust

A remote control, not a live wire

The context orchestrator doesn't let the LLM touch the runtime directly — it hands it a remote control with a fixed set of labeled buttons, each accepting only values in a declared range. The LLM presses buttons (structured function calls); a validator checks the press is legal before anything actually changes.

Where it breaks: a remote's buttons never disagree with each other; here the runtime still has to reconcile multiple directives issued in the same turn (e.g. a content directive and a turn-control directive together), which is exactly the joint-reasoning problem the orchestrator exists to solve upstream.
The full explanation

How it actually works

Section by section, following the paper's own structure (§3), with its formulas rebuilt as diagrams.

1 · Voice context modeling — three states, jointly needed

Each turn, llmovoice extracts three complementary states. The semantic state combines the current input with relevant projected history. The paralinguistic state tracks speaking rate: the ten most recent valid observations (0.5s+ duration, 100–300 WPM for English), combined with a linearly weighted average that favors recent turns — smoothing noise while still following sustained change. The environmental state aggregates WebRTC reception stats over a rolling window (≥1000 ms or the current VAD threshold, whichever is larger), recording concealed-audio duration, how much of it rendered as silence, and time since the last concealment event.

2 · Context orchestration — resolving conflicts with the serving LLM itself

Applying one rule per state independently can produce contradictions: a user asking for a faster reply while a packet-loss burst argues for a longer silence threshold to avoid a false endpoint. llmovoice resolves this by giving the same serving LLM a state snapshot, the current runtime configuration (active speed, VAD threshold), and a typed function interface — then letting it reason jointly and emit zero, one, or several structured function calls. A validator checks types/ranges before converting valid calls into content, style, and turn-control directives.

3 · Structured voice memory — vpage and vthread

A vpage is one completed interaction: user input, model output, and their available audio / transcript / summary representations plus retrieval metadata. A vthread holds an ordered set of references to vpages sharing a topic or goal — membership is many-to-many, since one utterance can constrain several ongoing threads at once (e.g. confirming a hotel while also scheduling a dinner). After committing a page, llmovoice appends it to every matching thread; if none matches, it retrieves at the page level and either spawns a new thread from matched pages or creates a singleton thread. Thread-summary refresh runs asynchronously off the latency-critical path — the new page is retrievable immediately either way.

4 · Directive execution

Four typed functions carry out directives: set_response_instruction (content), set_response_speed (style), and defer_response / set_vad_silence_duration (turn-control). Priority when signals conflict: if the environmental state suggests the input may be incomplete, obtaining a complete input takes precedence over responding; otherwise an explicit semantic request (e.g. "speak faster") overrides an inferred paralinguistic preference. This is a stated instruction to the reasoning LLM, not a hardcoded lookup table.

# style directive: mapping observed/target rate r (wpm) to provider speed s
s(r) = clip( s_min + (r − r_min)/(r_max − r_min) · (s_max − s_min), s_min, s_max )
# OpenAI Realtime profiling: s_min=0.8→r_min=142.4wpm,  s_max=1.5→r_max=267.0wpm
💡
Why the same LLM, not a separate controller? The semantic context is already loaded in that model's window — reusing it avoids serializing state to, and keeping it synchronized with, an out-of-band model. The cost is conditional: no additional function-call decision latency or cost is measured unless a control function is actually invoked — the state itself still has to be represented and processed as context regardless.
Follow the numbers, step by step

Worked examples

Four traces through the paper's actual formulas and results, arithmetic shown.

① Mapping an observed speaking rate to response speed

A user speaks at 200 WPM. Using the prototype's calibrated OpenAI Realtime mapping (s_min=0.8 → r_min=142.4 WPM, s_max=1.5 → r_max=267.0 WPM), what speed setting should the response use?

  1. Compute the fraction of the range covered: (200 − 142.4) / (267.0 − 142.4) = 57.6 / 124.6 ≈ 0.462.
  2. Scale into the speed range: 0.462 × (1.5 − 0.8) = 0.462 × 0.7 ≈ 0.323.
  3. Add the floor: s(200) = 0.8 + 0.323 ≈ 1.12.
  4. Sanity check the clip: 1.12 is within [0.8, 1.5], so no clamping needed.
🍯
Insight: this same linear map, applied across an evaluation set, is what took mean WPM alignment error from 38.26 (default speed) to 18.23 with orchestration on — a 52.4% relative reduction. (This is a WPM alignment measurement, not a subjective naturalness rating.)

② Updating the VAD silence threshold after a false endpoint

Current threshold D_VAD = 500 ms. A continuation is detected, and the gap between the prior speech_stopped and the new speech_started is g = 734 ms. With safety margin δ = 200 ms and granularity q = 100 ms, what's the new threshold?

  1. Sum the raw requirement: D_VAD + g + δ = 500 + 734 + 200 = 1434 ms.
  2. Round up to the nearest 100 ms: ⌈1434/100⌉ = 15, so 15 × 100 = 1500 ms.
  3. Cap at D_max = 5000 ms: min(5000, 1500) = 1500 ms — well under the cap.
  4. Recovery: after five consecutive seconds of healthy reception, the threshold resets to the default 500 ms.
💡
This update needs no LLM call — it fires automatically once a continuation proves the prior boundary was premature, keeping the reactive path cheap.

③ Network-induced cost under packet loss (Table 1)

Fixed-500 (static 500 ms threshold) costs $0.003344/trace from false responses on the ICASSP PLC validation set. llmovoice's turn control reports a $0.000695/trace total, split into $0.000069 residual false-response cost and $0.000626 orchestration cost. Verify the numbers and the relative gain.

  1. Check the split sums correctly: 0.000069 + 0.000626 = 0.000695 ✓ — matches the reported total.
  2. Compute the relative reduction: (0.003344 − 0.000695) / 0.003344 = 0.002649 / 0.003344 ≈ 79.2%, matching the paper.
  3. Check FIR alongside it: false-interruption rate drops from 46.0% to 0.9%: (46.0 − 0.9)/46.0 ≈ 98.0% relative reduction.
  4. Note the trade-off: Static-Max (3200 ms fixed) also drives FIR to 0.0% on these evaluated traces, but at a median endpoint latency of 4021 ms vs. llmovoice's 1830.7 ms — over 2× slower to respond.
⚠
Why llmovoice isn't $0: its cost isn't zero because orchestration itself (the LLM reasoning about the environmental state) has a price — $0.000626 of the $0.000695. The gain comes from spending a little on reasoning to avoid spending a lot on false responses.

④ How large is "up to 24.9×"?

Table 2 gives per-turn cost on RT2 and MSP-PODCAST for OpenAI (at various cache hit rates) and llmovoice. Compute the multipliers.

  1. RT2, uncached OpenAI vs. llmovoice: $0.025468 / $0.005799 ≈ 4.4×.
  2. MSP-PODCAST, uncached OpenAI vs. llmovoice: $0.140198 / $0.005634 ≈ 24.9× — the headline number, on the longer, more diverse workload.
  3. Even against the idealized 100%-cached OpenAI on MSP-PODCAST: $0.009860 / $0.005634 ≈ 1.8× — llmovoice still wins against a cache hit rate that isn't achievable in practice.
  4. Why the gap grows with session length: caching cuts a constant fraction of a linearly growing cost; llmovoice's context stays roughly flat (Fig. 7), so the ratio compounds as history lengthens.
🍯
Insight: the gap is largest exactly where it matters most — long-running sessions — while retaining up to 98.7% (RT2) / 88.7% (MSP-PODCAST) of OpenAI's full-history answer quality.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Prompt caching is enabled and hit rates are strong. Does per-turn voice-serving cost stay flat as the conversation grows?
Show answer
No. Caching reduces the constant factor on repeated content but not the growth rate — cost still rises roughly linearly with history length, because the window itself keeps growing and gets reprocessed each turn (Fig. 3). Reducing what's actually in the window, as llmovoice's projector does, is what keeps the curve roughly flat, bounded by the configured context budget.Misconception: that caching solves the scaling problem. It's a cost multiplier on an already-growing baseline, not a bound on the baseline's growth.
Problem 2 · medium
Using s(r) = clip(s_min + (r−r_min)/(r_max−r_min)·(s_max−s_min), s_min, s_max) with the paper's calibration (s_min=0.8, r_min=142.4, s_max=1.5, r_max=267.0), what speed should a user speaking at 267.0 WPM get, and why does the clip matter here?
Show answer
At r = r_max, the fraction is exactly 1.0, so s = 0.8 + 1.0×0.7 = 1.5 — exactly s_max, no clipping needed at the boundary. The clip matters for rates outside the calibrated 142.4–267.0 WPM range (which the paralinguistic extractor already filters to 100–300 WPM raw): without it, a very fast or slow speaker could push s outside the provider's supported [0.8, 1.5] and produce an invalid API call.Misconception: that the linear map alone is safe. It's only safe because of the explicit clip plus the upstream 100–300 WPM sanity filter on individual observations.
Problem 3 · medium
The environmental state suggests input may be incomplete (packet loss in progress), while the paralinguistic state suggests the user usually prefers a fast reply. Per the orchestration instruction, which wins, and why?
Show answer
Obtaining a complete input takes precedence — the orchestrator would favor deferring the response (or asking the user to repeat/confirm) over immediately generating a fast reply to what might be a truncated utterance. Only once the environmental state doesn't flag reliability concerns does the semantic-over-paralinguistic priority (explicit request beats inferred rate) apply.Misconception: that "user preference" signals always take precedence. Reliability of the input itself is checked first — a fast wrong answer is worse than a slightly slower complete one.
Problem 4 · hard
D_VAD = 1500 ms (already raised from a prior event), a new gap g = 3800 ms is observed, δ = 200 ms, q = 100 ms, D_max = 5000 ms. Compute D_new.
Show answer
Sum: 1500 + 3800 + 200 = 5500 ms. Round up to nearest 100 ms: already a multiple, so 5500 ms. Cap at D_max = 5000: min(5000, 5500) = 5000 ms — the ceiling binds. The threshold cannot rise past the configured maximum even if the observed gap would imply a larger value.Misconception: that the formula always tracks the observed gap exactly. D_max exists precisely to bound how unresponsive the system can become after a single bad gap.
Problem 5 · medium
Page-RAG's multi-page request hit rate on MSP-PODCAST drops from 47.8% (single-page) to 20.4% (multi-page) — a 27.4-point fall. Why does thread-level retrieval avoid most of this drop?
Show answer
Page-level retrieval scores each vpage independently by similarity to the query, so when evidence for one fact is scattered across multiple pages, only the most similar one or two get retrieved — the rest are missed, breaking cross-page locality. A vthread groups those related pages under one retrievable unit, so matching the thread (or one of its pages) pulls in the whole connected set at once, not just the single best-matching fragment.Misconception: that better embeddings alone would fix this. The failure is structural — page-level retrieval has no notion that pages are related — not a similarity-scoring problem.
Problem 6 · easy
What's the core difference between a vpage and a vthread?
Show answer
A vpage is the record of one completed interaction (user input + model output + its audio/transcript/summary representations). A vthread is a group of related vpages, ordered and linked to represent a coherent conversational flow — it stores references, not duplicated content, and one vpage can belong to multiple vthreads.Misconception: that a vthread is just a bigger vpage. It's a different level of structure entirely — pages are the atoms, threads are the topic-level organization over them.
Problem 7 · hard
The context orchestrator's overhead is described as "conditional." Under what circumstance is no additional decision latency measured, and under what circumstance does it cost 790.2 ms on average?
Show answer
If the current semantic, paralinguistic, and environmental states don't warrant any change to runtime behavior, the serving LLM returns no function call and generation proceeds with the existing configuration — no additional function-call decision latency is measured beyond the state already being included in context. If it does decide a directive is warranted, that decision itself (state snapshot in → structured function call out) took a mean of 790.2 ms (median 698.8 ms) across the measured turns that produced a call.Misconception: that orchestration always adds ~800 ms to every turn. It's incurred only on turns that actually need a directive — most turns don't.
Problem 8 · medium
Compaction (summarize older history, keep only the last two turns verbatim) scored a 3.7/10 judge rating on RT2 versus llmovoice's 7.7/10 — far below even Page-RAG's 7.4. What causes such a steep drop for Compaction specifically?
Show answer
Compaction's policy is static and recency-only: it always keeps just the last two turns verbatim and blindly summarizes everything older, regardless of relevance. If the conversation drifts to unrelated chitchat and then returns to an earlier constraint, that constraint has already been compressed into a summary that may omit the exact detail needed — the paper's Case #1 shows this "detail amnesia" concretely (a forgotten "few people" constraint leading to a wrong, crowded recommendation). llmovoice's relevance-ordered degradation, by contrast, keeps relevant older content at higher fidelity even when it isn't recent.Misconception: that recency is a good proxy for relevance in voice conversations. Long sessions branch and return to earlier topics, so "most recent" and "most relevant" frequently diverge.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is llmovoice a new model, or middleware around an existing one?▾
Middleware. It exposes an interface compatible with existing LLM service APIs (the prototype targets OpenAI Realtime, with Gemini Live / GLM-Realtime noted as portable targets) and reuses that same serving LLM for both response generation and context orchestration — it doesn't train or replace the underlying model.
Q2Why not use a separate, smaller model just for orchestration decisions?▾
Because the semantic state (current input + relevant history) is already loaded in the serving LLM's context window. Delegating to a separate controller would require serializing and re-synchronizing that context with another model — extra complexity and staleness risk — for a decision the serving LLM can already make from what it has.
Q3How is this different from standard RAG?▾
Standard RAG (and most baselines evaluated, like Page-RAG) retrieves independent passages by similarity. llmovoice retrieves over two structured, voice-specific levels — vpage (one interaction, multiple fidelities) and vthread (a topic-coherent group of pages) — and additionally chooses a representation fidelity per item under a cost budget, which passage-level RAG doesn't do.
Q4What happens if the LLM emits an invalid function call?▾
The runtime control adapter checks that the requested control is supported and its arguments satisfy the declared types and ranges before applying anything. Invalid calls are rejected outright and the runtime configuration is left unchanged — the typed function interface is a hard guardrail, not a suggestion.
Q5Does llmovoice always beat a full-history baseline on answer quality?▾
No — it retains up to 98.7% (RT2) and 88.7% (MSP-PODCAST) of the unconstrained full-history baseline's judge score, not more. The gap comes mainly from a measured 14.6% transcript-to-summary failure rate, where a needed fact survives at transcript fidelity but is lost once compressed to a summary.
Q6Why measure both retrieval hit rate and judge score separately?▾
Hit rate tells you whether the right vpage was even loaded into context; judge score tells you whether the answer was actually correct. A method can retrieve the right page but still answer wrong if that page's loaded fidelity omitted the needed detail — which is exactly what the summary-fidelity failure mode shows.
Q7Is context orchestration free when nothing needs to change?▾
Not exactly — the state still has to be represented and processed as context every turn. But no additional function-call decision latency or cost is measured unless a control function is actually invoked; that decision cost (mean 790.2 ms) is incurred only on turns that produce a call.
Q8What's the actual measured overhead of the memory-to-context path?▾
78.4 ms (3.8% of end-to-end TTFA) on RT2 and 50.9 ms (2.7%) on MSP-PODCAST — mostly embedding and vector search; context projection itself measures under 1.1 ms. External STT and generation dominate total latency regardless of which context-management method is used.
Q9Why does Static-Max eliminate false interruptions but still lose to llmovoice?▾
Static-Max uses a fixed, conservative 3200 ms silence threshold — long enough that, on these evaluated traces, packet-loss gaps never look like a real endpoint, so FIR hits 0.0%. But that same conservatism makes every genuine turn boundary slower to detect: median endpoint response latency rises to 4021 ms, versus 1830.7 ms for llmovoice's adaptive threshold, which only widens the threshold when the environmental state actually indicates trouble.
Q10What does the real-world deployment (§5.6) add beyond the benchmarks?▾
Three real-world case studies: recovering a constraint after topic drift that a compaction baseline forgot; avoiding a cascade of false-triggered fragmented responses under natural network jitter that a static-VAD baseline produced; and resuming a session after a user-initiated disconnect/reconnect, which the baseline treated as a brand-new conversation.
