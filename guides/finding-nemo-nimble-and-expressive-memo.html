Deep-Dive Explainer

Finding NEMO — A Field Guide to Nimble and Expressive Memory Observability

A memory controller can now run your telemetry program instead of whatever fixed counters the chip designer shipped. NEMO lets the OS define exactly what to count, at what granularity, and when to raise an alarm — all inside the memory controller's datapath, at full line rate, for a fraction of a percent of CPU.

Shihang Li, Matthew Giordano (UW) · Tushar Garg (Meta) · Rohan Kadekodi (UW) · Daniel S. Berger (UW & Microsoft Azure) · Baris Kasikci, Thomas Anderson, Simon Peter (UW)

Motivation

Why memory needs a better speedometer

Server memory used to be one uniform pool of local DRAM. It no longer is. A modern datacenter node can have DRAM behind multiple sockets, memory pooled and tiered across CXL-attached expanders, and compression or internal tiering happening inside those expanders — invisible from the host. Memory is also expensive: the paper cites it as 40–50% of server cost. OS subsystems (page tiering, transparent-huge-page management, per-tenant QoS) all need to know, cheaply and accurately, which memory is hot, how hot, and whose it is — and they need that answer to update as access patterns shift, not thirty seconds later.

The paper frames the tradeoff along five axes, and it's a genuinely useful lens for judging any memory-telemetry mechanism:

DimensionWhat it means
CoverageWhat fraction of memory accesses are actually observed
TimelinessDelay between an access-pattern change and telemetry reflecting it
GranularitySmallest unit telemetry can attribute to (cache line? page? tenant?)
FlexibilityHow much the OS can redefine what's tracked and how it's aggregated
OverheadCPU/resources spent collecting and processing the signal

Existing options each sacrifice something. Software techniques (soft page faults, page-table access-bit scanning) can observe anything but cost a lot of CPU to do it, so in practice they run infrequently, sacrificing timeliness and granularity. Hardware counters — Intel's Memory Bandwidth Monitoring (MBM), per-core PMU counters — are cheap and timely, but the aggregates and granularities were fixed at chip design time; you get socket-level or channel-level numbers whether or not that's the shape your policy needs. Sampling (Intel PEBS) sits in between: it misses whole classes of traffic (prefetches, non-temporal stores), doesn't work for VM guests observed from the host, and — as the paper measures — sampling 10% of cache misses can slow the target application by more than 50%, so production systems sample at much lower rates and eat the resulting imprecision.

The gapNo existing mechanism gives you all five dimensions at once. Software is flexible but slow; hardware counters are fast but rigid. NEMO's pitch is to stop treating that as a law of nature.
The Core Idea

Put a tiny, programmable telemetry engine inside the memory controller

NEMO augments each memory controller (MC) with a small off-datapath pipeline and a modest SRAM budget (kilobytes to low megabytes, not a full cache). The pipeline taps a copy of every memory request's metadata — physical address and read/write type — as it passes through the controller. The actual request still goes straight to DRAM or CXL memory unmodified and undelayed; NEMO only watches. Because it observes every request rather than a sample, and because the OS gets to configure exactly what it counts and how, NEMO doesn't have to trade coverage for flexibility the way software approaches do, and it doesn't have to trade flexibility for cost the way fixed hardware counters do.

The OS installs small telemetry programs called telemetry rules. Each rule says, in effect: "for requests matching this address filter, map the address to a counter using this translation, and update that counter with this operation — and optionally interrupt me if the result crosses this threshold." Multiple OS subsystems can install independent rules concurrently, each with its own address ranges, granularities, and update logic. Read the results back through an ordinary memory-mapped region — no special driver call needed for the hot path, just a load instruction.

In one sentenceNEMO turns "what should the memory controller count" from a question answered once at chip tape-out into a question the OS can answer differently for every workload, every boot, and every few hundred milliseconds if it wants to.
Architecture

The match–update–notify pipeline

Every NEMO telemetry pipeline follows the same three-stage structure — deliberately borrowed from the "match-action" design used in programmable network switches (RMT/P4), where line-rate programmability under a fixed hardware budget is a solved problem. Here's the flow for one memory request:

Match: turning an address into a counter index

NEMO uses a simple mask–shift–add scheme rather than anything content-addressable. A configured bitmask and shift pick out the bits of the physical address that define a primary region (say, a 2 MiB hugepage); those bits index a small SRAM translation table to get a base index. If the OS wants sub-region granularity (e.g., which 4 KiB basepage inside that hugepage), a second mask/shift extracts an offset that's added to the base index to get the final counter slot. This lets the same hardware serve both "one counter per 2 MiB page" and "one counter per 4 KiB basepage within a tracked set of pages," just by changing two small config fields — no logic redesign.

Update: one bounded, safe operation per request

The update stage does a read-modify-write on the matched counter using whatever operator the OS configured — add, subtract, XOR, shift, or a comparison. NEMO restricts these to associative and commutative operations. That restriction is what makes the whole system scale: with multiple memory controllers (one per socket, or one per CXL device) each running its own local pipeline instance, a global telemetry value can be reconstructed by combining the per-controller states in any order — no coordination protocol needed between controllers while requests are in flight.

Notify: line-rate alerting

After an update, the pipeline can evaluate a simple comparison predicate against the new counter value (e.g., "≥ this threshold") and raise a hardware interrupt if it's true. This is what lets NEMO support urgent, push-based signals (a tenant just blew through its bandwidth cap) rather than forcing every policy to poll and hope it's not too late.

Concrete Walkthrough

Tracking access skew inside selected hugepages

The paper builds this up in layers, and it's worth following because it shows how much policy the same three stages can express. Start simple: track one counter per 2 MiB hugepage, incremented on every access, to estimate page hotness. Now extend it to something MEMTIS actually needs — figuring out where inside a hot hugepage the accesses concentrate, so a tiering system knows whether it's worth splitting that hugepage into hot and cold 4 KiB pieces.

nemo_telemetry_t t = nemo_register_telemetry((nemo_spec_t)
{
  .filter      = {.type = R|W},
  .translation = {
    // primary region: every 2 MiB hugepage across all of memory
    .primary = {.mask = NEMO_ALL_MEM, .shift = HP_SHIFT},
    // sub-region: which 4 KiB basepage inside that hugepage
    .sub     = {.mask = HP_BP_MASK,   .shift = BP_SHIFT},
  },
  .update       = {.op = NEMO_OP_ADD, .operand = 1},
  .notify       = {.op = NEMO_OP_NOOP},
  .read_effect  = {.op = NEMO_OP_RESET, .value = 0},
});

// Dynamically retarget which hugepages get tracked
void reprogram(uint64_t hp_paddr[], int npages) {
  for (int i = 0; i < npages; i++)
    nemo_set_translation(t, /*key=*/ hp_paddr[i] >> HP_SHIFT, /*region_idx=*/ i);
}

The static rule (installed once) says: match every read or write, compute a hugepage key from the address, compute a basepage offset within that hugepage, and increment the corresponding counter — resetting it to zero every time the OS reads it, so each poll reports fresh per-interval counts rather than a lifetime total. The dynamic part is reprogram(): the OS calls this whenever it wants to change which hugepages are being watched at basepage granularity, by rewriting translation-table entries. The counters themselves don't move; only the mapping from address to counter slot changes. This separation — static rule shape, dynamic translation targets — is what lets MEMTIS time-multiplex a small, fixed SRAM budget across far more hugepages than it could ever hold counters for simultaneously (§6.1 in the paper works out the math on how much DRAM one SRAM budget can "sweep" per interval).

Why this mattersTranslation can be one-to-many (one hugepage's 512 basepages each get their own counter, as here) or many-to-one (every hugepage belonging to a tenant maps to the same counter, which is exactly how the per-tenant bandwidth-cap use case in §5.3 is built). Same three pipeline stages, opposite aggregation shape — just by changing the translation table's contents.
Evaluation

Three OS policies, evaluated end to end

NEMO is prototyped on an FPGA-based CXL 2.0 Type-3 memory expander (Altera Agilex 7, 913k logic modules, 32 MiB usable SRAM, running the NEMO pipeline at 400 MHz) attached to a host with an Intel Xeon Gold 6430. The CXL-attached memory itself is meaningfully slower than local DRAM — 380.3ns latency and 16.4 GiB/s bandwidth, versus 114.1ns and 114.9 GiB/s for host DRAM (about 3.3× higher latency, 7× lower bandwidth) — which is exactly the kind of tiering gap that makes knowing what's hot so valuable. NEMO's own logic footprint on that FPGA is modest: 4.8% of logic utilization and 4.4% of the SRAM blocks.

Raising the PEBS sampling rate closes the gap on timeliness but blows the CPU budget (up to 2.6% overhead approaching 1% sampling), and prior work shows sampling much beyond 1% visibly slows the target application — so the software approach's tradeoff curve can never fully close the gap.

§5.2 · MEMTIS + Silo

Transparent-huge-page split candidates

Which hugepages are "skewed" enough — mostly cold with a few hot basepages — to be worth splitting out of the fast tier?

10.4×

NEMO finds 2× more genuinely skewed hugepages than PEBS-based sampling and detects 95% of split candidates in ~150s vs. up to ~1000s for PEBS at the tightest (1:8) fast:slow memory ratio. That translates to up to 1.13× application throughput and up to 1.21× Silo speedup, with total CPU overhead actually lower than the PEBS baseline (3% vs. 2.89% — comparable, not worse, despite doing far more).

§5.3 · Linux cgroups + FlexKVS

Noisy-neighbor detection & throttling

Catch a tenant blowing past its memory-bandwidth allocation fast enough to protect a latency-sensitive neighbor.

350×
lower CPU overhead than MBM

NEMO matches Intel MBM's best-case throttling effectiveness (p99 latency increase held to 5.2% vs. MBM's 5.5%, both against 22% unthrottled) while polling MBM that accurately requires a 1000 Hz interval that costs 30%+ CPU. NEMO achieves the same result at just 0.09% CPU, because its interrupt-driven notify stage reacts the instant a tenant crosses its cap rather than needing to be polled fast enough to catch it.

Rolled up across FlexKVS, FASTER KV, and Silo, NEMO-based policies deliver up to 1.7× higher throughput and 23% lower latency than the PEBS/MBM-based state of the art — while, in every case measured, doing it at equal or lower CPU cost.

Discussion

What NEMO can't do (yet)

The paper is upfront about the boundaries of the design, which is worth taking seriously rather than skipping past.

Single bounded update per requestEach pipeline performs exactly one read-modify-write per memory operation. Telemetries needing multiple arithmetic steps or multiple counter locations per single access — e.g., computing a running variance, which needs both a running sum and a running sum-of-squares updated together — don't fit in one pipeline. The workaround is to run two independent pipelines (one per statistic) and combine their results in software afterward, since both are associative/commutative and can be merged in any order.
Exact top-K needs more than a counterPrecisely tracking "the K hottest items" requires history beyond what a single SRAM-resident counter can hold. §6.3 sketches a fix: chain pipelines together the way multi-stage match-action tables do in programmable network switches, implementing something like a count-min sketch across several small counter arrays hashed by a shared key-derivation scheme — future work, not in the current prototype.
Notify stage is prototype-simulatedHardware interrupt delivery from the notify stage isn't implemented in the FPGA build; the §5.3 noisy-neighbor evaluation approximates it by polling counters every 1ms on a spare core until a threshold is crossed. The mechanism is real and designed; the specific interrupt-delivery path just isn't wired up on this dev kit yet.
Only sees what it's attached toThe FPGA prototype is a CXL expander, so it only observes CXL-attached memory — the evaluation's fast-tier (local DRAM) telemetry still comes from PEBS in every use case. The paper argues an in-controller implementation (integrated memory controllers, which recent Xeons already support extending) would give equivalent fast-tier coverage; that's an implementation-completeness argument, not something the prototype demonstrates directly.

On the security side (§6.2), the trusted computing base is just the MC hardware and the NEMO driver in kernel/hypervisor. The driver validates every translation-table entry against the page-ownership rules the kernel already enforces, so a telemetry rule can't be pointed at memory it doesn't own; under virtualization a paravirtual interface lets a guest install telemetries only over its own allocated ranges. Because NEMO runs off the datapath at fixed per-request cost, memory access latency doesn't depend on telemetry state — the paper argues this means no new observable timing side channel is introduced beyond what already exists in caches and DRAM timing.

FAQ

Questions worth asking

How is this actually different from Intel MBM or PEBS?

MBM gives fixed aggregates (per-socket or per-channel bandwidth) baked in at chip design time — you can't ask it for per-page or per-tenant numbers it wasn't built to produce. PEBS is flexible in principle (it samples real memory events) but only sees a sample, misses entire traffic classes like prefetches and non-temporal stores, can't observe from the host into a VM guest, and gets expensive fast if you push the sample rate up for better fidelity. NEMO sees every request and lets the OS define the aggregation, which is the combination neither existing option offers.

Does watching every memory request slow anything down?

No extra latency on the actual memory access — NEMO's pipeline runs off the critical datapath, broadcasting a copy of request metadata to all its pipelines while the real request is routed to DRAM/CXL untouched. The design goal was explicitly to keep an initiation interval of 1 cycle per channel so it never becomes a new bottleneck.

What happens when SRAM runs out — can't track everything at once?

Yes, this is the real constraint. NEMO's SRAM is small (kilobytes to a few MiB), so when the OS wants more telemetry regions than fit, it time-multiplexes by reprogramming translation-table entries between scans (exactly what MEMTIS-NEMO does in §5.2 to cover 112 hugepages with only 8 physical pipelines). §6.1 gives a formula for the resulting "sweep time" — the DRAM-to-SRAM ratio sets an area-vs-timeliness tradeoff, and counter width is a second, roughly orthogonal knob.

Can two different OS subsystems use NEMO for different things at the same time?

Yes — that's the whole point of exposing it as installable rules rather than a single global mode. The paper's three use cases (HeMem tiering, MEMTIS huge-page splitting, cgroup noisy-neighbor throttling) each install their own independent telemetry with its own filter, translation, and update logic, and nothing stops them running concurrently on the same hardware, budget permitting.

Is this only useful for CXL memory?

The prototype happens to be a CXL expander because that's where FPGA memory-controller dev kits are available today, but the design targets memory controllers generally, including integrated memory controllers on the CPU package. The paper notes recent Xeon processors already support delivering memory responses to additional consumers without hurting cache performance, which is the hook an IMC implementation would use.
