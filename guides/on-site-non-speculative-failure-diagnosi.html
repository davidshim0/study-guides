SOSP 2026 · A Field Guide

Stop chasing guesses — chase evidence

Most production-bug time is wasted on wrong hypotheses. CLODS refuses to guess: it adds just enough logging to prove the one true failure path, on the production machine, one careful round at a time.

📄 "On-site, Non-speculative Failure Diagnosis with CLODS" · Devsot et al. 🎓 Some compiler/static-analysis background assumed — primers cover it ⏱ ~30 min read

Before you begin

Ten ideas the paper assumes you know

Collapsed by default — open any that's unfamiliar, skip the rest.

CLODS's evidence-driven approach root cause / symptom static-analysis machinery wild goose chases / speculation
1Non-crashing "partial" failures▾

Not every failure crashes the system. Data corruption, a stalled background thread, or a silently degraded feature can recur for months before anyone diagnoses them — precisely because nothing crashes to force attention.

Now you're ready: CLODS targets exactly these functional failures, where the symptom is a specific bad event (an exception, a wrong metric) rather than a crash.
2Symptom vs. root cause▾

The symptom is what you first notice — a thrown exception, an alarming dashboard metric. The root cause is the earlier event that actually caused it. They're rarely the same instruction, and confusing them is how developers waste time fixing the wrong thing.

Now you're ready: CLODS's whole job is walking backward from the symptom event to the true root-cause event.
3The wild goose chase▾

A developer forms a hypothesis about the cause, spends real effort testing it, and only then discovers it's wrong. In the paper's survey of the ten most-discussed bugs across 5 systems, 62% had at least one of these, consuming 54% of total diagnosis time on average.

Now you're ready: CLODS's design principle is to never speculate — so it structurally cannot go on one.
4Control-flow vs. data-flow dependency▾

An instruction can depend on whether it runs (a branch controls it — control-flow) or on what value it uses (some earlier instruction defined a variable it reads — data-flow). Both kinds of "why did this happen" question recur throughout the paper.

Now you're ready: CLODS's two core analyses — control dependency analysis and data dependency analysis — answer exactly these two questions.
5Program slicing▾

A slice for an instruction is the set of all instructions it could depend on, computed by recursively following dependencies. Slices grow explosively: the slice for one exception in HDFS-10453 was 13,470 instructions.

Now you're ready: CLODS avoids computing a full slice up front — it only expands the slice one step at a time, pruned by real evidence.
6Dominance and control dependency▾

Instruction X dominates Y if every path to Y passes through X. Y post-dominates X if every path from X to the function's exit passes through Y. A "controlling branch" of I is a branch that dominates I without I post-dominating it back — i.e., a branch that genuinely decides whether I runs.

Now you're ready: this is the precise definition behind CLODS's Control Dependency Analysis (CDA).
7LLVM IR and bytecode instrumentation▾

LLVM IR is a common intermediate representation many compilers target. Analysis written against IR works for any source language that compiles to it. Separately, managed-language runtimes (JVM, Android, CPython) let you rewrite the running bytecode on the fly — no restart needed.

Now you're ready: CLODS analyzes LLVM IR (for language-agnostic reasoning) but instruments live bytecode (for zero-downtime logging).
8Executions as ordered events▾

An event is one dynamic instance of an instruction executing. A single-threaded execution is just the program order; for multiple threads, an execution is some total ordering of all events across all threads (Lamport's classic formulation).

Now you're ready: CLODS compares two such event sequences — the failure's and a similar non-failure's — to find where they diverge.
9Off-site vs. on-site diagnosis▾

Off-site means reproducing the bug in a dev environment, where you can freely add logging — but reproduction itself eats 69% of resolution time, and 89% of production failures could only be reproduced after root-cause was already known. On-site means diagnosing right where the failure happened, but any tool used there must be lightweight.

Now you're ready: CLODS is built to run its entire diagnosis loop on-site, unlike prior tools that offload heavy analysis off-site.
10Preview: the inflection point hypothesis▾

A theoretical definition of "root cause": it's the first event in the failure execution that, once it happens, makes the failure inevitable. You find it by comparing the failure's event sequence to the most-similar execution that did not fail — their first difference is the root cause.

Now you're ready: this hypothesis (from prior work, Kairux) is CLODS's theoretical foundation — CLODS's contribution is making it work cheaply, on-site, from partial logs.
The whole story in one place

CLODS in a nutshell

The problem, the loop that fixes it, and how the pieces connect.

Diagnosing a hard production failure means comparing the failure's execution against a similar non-failure execution to find where they diverge — that divergence is the root cause. Prior tools try to do this by computing a huge program slice up front (tens of thousands of instructions) and modifying test executions to synthesize the comparison. That's too heavyweight to run where the failure actually happened, so developers instead guess — and 62% of hard bugs involve at least one wild goose chase, wasting 54% of diagnosis time.

CLODS breaks the same comparison into small, cheap, iterative rounds, run entirely on-site. Each round: the static analyzer looks at the current deviation point, finds the small set of branches or variable definitions that could explain it, and — critically — never forks to try multiple explanations at once. Instead it instruments just those few points and waits for the failure to happen again. When it does, the log analyzer reads the new evidence, narrows the deviation further, and the cycle repeats — typically 2.5 rounds — until the true root cause is nailed down with zero forks and zero guesses.

The payoff: across 23 real production bugs, CLODS correctly diagnosed 83% (19/23), using on average only 24 instrumentation points total, versus roughly 26,894 for the prior slicing-based tool Kairux — with under 4% runtime overhead and under 105 MB of analyzer memory.

🔎 Key takeaways

  • Wild goose chases dominate hard-bug diagnosis time: 62% of top-commented bugs have one; they eat 54% of the time.
  • CLODS's rule: never fork — when evidence is ambiguous, instrument and wait, don't guess.
  • Diagnosis happens in rounds: static analysis proposes a small instrumentation plan, logs resolve it, the loop repeats (avg 2.5 rounds).
  • Root-cause localization follows the inflection point hypothesis, but adapted to work from partial, incremental traces.
  • Analysis is on LLVM IR (language-agnostic) but instrumentation is on live bytecode (zero-downtime, on-site).
  • Result: 83% success, ~24 instrumentation points/bug, <4% overhead — vs. an LLM agent's 62% success on the same bugs.
Seven everyday pictures

How to think about CLODS

Each stands alone — read in any order. Each ends with where the picture stops holding.

The core idea · No forking

A detective who won't guess

Faced with an ambiguous clue, a bad detective interrogates every suspect at once, hoping one confesses. CLODS instead asks the crime scene one more precise question — and waits for the answer — before naming anyone. It follows one trail, not many.

Where it breaks: "waiting for the answer" means waiting for the bug to happen again, which can be slow for rare failures.
CDA/DDA · Backward tracing

Tracing wires from a dead bulb

A light is off. You trace the wire back to the switch (control dependency: does the switch decide if it's on?), or check whether the bulb itself is broken (data dependency: what set its state?). CLODS's static analyzer asks exactly these two questions, one hop backward at a time.

Where it breaks: real circuits are usually simple trees; software dependency graphs branch and merge, so "one wire" can hide several candidate causes needing evidence to disambiguate.
Why not full slicing · Explosive growth

Twenty questions vs. an encyclopedia

You could hand someone an encyclopedia and ask them to find one fact (a full slice — 13,470 instructions for one HDFS bug). Or you could ask twenty sharp, sequential questions that each halve the search space. CLODS plays twenty questions with the execution, using real answers to skip whole branches of "what if."

Where it breaks: twenty questions assumes each answer meaningfully narrows things; if the failure is truly rare, "waiting for an answer" (a reoccurrence) can take a long time.
Inflection point · Point of no return

The rollercoaster's crest

Before the crest, the car could still be stopped; once past it, gravity guarantees the drop. The root cause is the earliest event past which failure is guaranteed — everything before is still "recoverable," everything after inevitably leads to the symptom.

Where it breaks: a rollercoaster has one obvious crest; software may have several near-simultaneous conditions, and picking the "true" first one requires the right non-failure execution for comparison.
On-site vs. off-site · House calls

A house call vs. mailing a specimen

Mailing a blood sample to a distant lab means losing whatever doesn't survive shipping and waiting days for results. A doctor who visits your house diagnoses with everything intact, in real time — but she can't bring a hospital's worth of equipment with her. CLODS is the house call: real-time, faithful, but deliberately lightweight.

Where it breaks: some ailments (kernel bugs, hardware faults) are genuinely beyond what a house-call kit can diagnose — CLODS has the same boundary at code it can't compile to LLVM IR.
Ring buffers · Always-on tracing

A dashcam that erases itself

An always-recording dashcam with a small loop buffer overwrites old footage constantly — fine, unless the crash-causing moment happened more than a buffer-length ago. In HDFS-10453, the gap between cause and symptom was 10 minutes; a 32MB Hubble-style ring buffer would overflow 16× before the crash and erase the exact moment that mattered.

Where it breaks: a bigger buffer helps a dashcam; for software it also raises always-on overhead, so it's not a free fix — which is why targeted, on-demand logging (CLODS) beats always-on tracing here.
Rounds narrowing · Funnel

A funnel, not a fan

Statistical bug-isolation and slicing tools fan out — tracking every branch that could matter, all at once, hoping the real one is in there. CLODS instead funnels: each round narrows to fewer, sharper candidates, using only the one real execution that happened.

Where it breaks: a funnel assumes each round genuinely narrows things down; for a location deviation with no matching non-failure prefix at all (a totally new code path), CLODS must widen its search to the calling function first — a brief, deliberate un-narrowing.
The full explanation

How it actually works

Following the paper's own architecture, with its running HDFS-10453 example.

1 · The problem, concretely

HDFS-10453: a replication thread throws NotEnoughReplicasException whenever a deletion thread races it, temporarily inflating a block's recorded size so every capacity check fails. It took developers a month and three separate wild goose chases (cluster scale, storage heterogeneity, a scheduling parameter) to find — because production logs at INFO level held almost no useful evidence.

2 · The inflection point hypothesis, precisely

Given the failure execution s_fail and the set of all possible non-failure executions, find s_success — the one sharing the longest common prefix with s_fail. The first event where they diverge is the root cause. In HDFS-10453, that divergence is exactly the deletion thread setting the block size to max, right before chooseRandom() reads it.

📐
Prior work (Kairux) computes s_success by running and modifying existing test cases off-site — CLODS instead searches the production workload's own naturally-occurring non-failure executions, on-site.

3 · The three static-analysis building blocks

Control Dependency Analysis (CDA) finds the controlling branch instructions (CBIs) of an instruction — the branches that decide whether it runs. Data Dependency Analysis (DDA) finds every instruction that could have defined a variable's value. Call Site Analysis (CSA) walks up to the callers of a function when the current instruction has no CBI of its own (e.g. it's at a function's very entry).

4 · Branch deviation and round 2

After reoccurrence, the log analyzer finds a branch deviation at line 17: nReplicate was >0 when it shouldn't have been. Branch deviation analysis finds what defines nReplicate (line 14), instruments it, then finds its CBIs — the three branches at lines 9, 11, 13 — bringing round 2's cumulative total to 5 locations.

def BranchDeviationAnalysis(I):
    for var in BranchCondition(I):
        writeSet = DataDependencyAnalysis(var)
        plan.add(writeSet)              # e.g. line 14
        for W in writeSet:
            LocationDeviationAnalysis(W)  # finds CBIs at 9, 11, 13
💡
Only after the failure recurs with these branches logged does the log analyzer learn that line 13 (isGoodTarget) is the true deviation — lines 9 and 11's dependency trees are pruned entirely, unexplored.

5 · Grouping events into executions

Events from different threads are separate executions unless linked by a cross-thread read-after-write. Loop iterations need care too: a map loop's iterations are independent (treat each as its own execution); a reduce loop's iterations accumulate toward one outcome. CLODS classifies a loop as a map loop with respect to instruction I if I is observed at runtime to execute the same number of times every iteration — looser than prior static-only definitions.

6 · Choosing s_success and terminating

CLODS approximates "longest common prefix" using matching stack traces, instructions, and (for branches) matching targets — since its partial logs may not literally contain a full prefix. It picks the non-failure execution with the longest such match that still differs somewhere from the failure run. Analysis terminates successfully when it reaches the program's entry (main/API boundary); it terminates with an error if it hits an unanalyzable dependency (e.g. inside OS/filesystem code) before that.

Follow the numbers

Worked examples

Four passes through the paper's real numbers.

① HDFS-10453, round by round

  1. Symptom: exception at line 18. CDA finds its only CBI, line 17. Instrument it. 1 location.
  2. Reoccurs: line 17 evaluated true when a non-failure run had it false → branch deviation. DDA on nReplicate finds line 14; CDA on line 14 finds CBIs 9, 11, 13. Cumulative: 5.
  3. Reoccurs again: logs show line 13 (isGoodTarget) is the branch that actually flipped — lines 9 and 11 are pruned, unexplored. Analysis continues into isGoodTarget's own dependencies (the capacity check).
  4. Final round: traces the block-size value to a definition in a different thread (the deletion thread) than any non-failure execution used — a location deviation with no shared prefix, which CLODS flags as a likely data race. Total: 59 locations, 4 rounds.
🔎
Insight: every round instruments only what the previous round's real evidence pointed to — never the ~13,470-instruction slice a non-iterative tool would need.

② The cost of full slicing vs. iterative rounds

  1. Kairux's average static slice across its evaluated bugs: 26,894 program points.
  2. CLODS's average total instrumentation per bug: 24 points, across 2.5 rounds.
  3. Ratio: roughly 1,120× fewer points instrumented, on average.
  4. On the specific HDFS-10453 bug: 13,470 (Kairux slice) vs. 59 (CLODS total) — ~228× fewer.
💡
The gap isn't from CLODS being smarter about which instructions matter — it's from never needing to fully resolve dependencies that real evidence later rules out.

③ Why log aggregation off-site is expensive

  1. Say one Android device produces 1 GB of logs per day.
  2. Across 1 million devices: 1M × 1 GB = 1 petabyte per day.
  3. The paper notes retaining/analyzing logs at this scale can cost vendors tens of millions of dollars; large internet services can produce 10–100 PB/day.
  4. CLODS's on-site design means none of this data ever needs to leave the device or be centrally stored.

④ CLODS vs. an LLM agent, head to head

  1. Same 23 bugs, same source code and logs, given to Claude Opus 4.7 as an agent, 5 attempts each.
  2. Agent accuracy: 62% of all attempts succeeded. Per-bug breakdown: 12 bugs "accurate" (>3/5 attempts), 3 "inconsistent" (3/5), 8 "inaccurate" (<3/5).
  3. CLODS accuracy: 83% (19/23), deterministically — no attempt-to-attempt variance.
  4. The agent's failures clustered on bugs with long propagation paths (e.g. HDFS-10453): it correctly spotted the downstream symptom but stopped short of the actual data race. CLODS's strict, evidence-only termination doesn't allow that shortcut.
  5. Conversely, the agent succeeded on 2 bugs CLODS couldn't (kernel/OS-level causes CLODS can't instrument) — the two approaches are complementary, not strictly ordered.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
CLODS's static analyzer finds three possible instructions that could have set variable x to the failing value. What does CLODS do next?
Show answer
Instruments all three as candidate CBIs/VDIs and waits for the failure to reoccur, then uses the new logs to determine which one actually happened — rather than picking one to investigate first (a fork) or guessing.Misconception: that CLODS "picks the most likely" candidate. It never ranks or guesses — it collects evidence for all of them and lets the next failure disambiguate.
Problem 2 · medium
A deviation event occurs in the non-failure execution but never appears anywhere in the failure execution. Is this a location deviation or a branch deviation?
Show answer
Location deviation — specifically a "missing event": the event happened in s but not s′. Branch deviations require the instruction to occur in both executions, just with different outcomes.Misconception: assuming every deviation is a branch. Many real root causes are events that should have happened but didn't.
Problem 3 · medium
An event loop processes a different user request each iteration. Should CLODS treat all iterations as one execution or as separate executions, when diagnosing a request-specific failure?
Show answer
As separate executions — this is a map loop with respect to the failure: each iteration's outcome is independent of the others, so lumping them together would corrupt the comparison against non-failure runs.Misconception: treating all loop iterations as one long execution by default. CLODS decides map-vs-reduce per instruction, using runtime evidence.
Problem 4 · hard
Per the inflection point hypothesis, why is the root cause defined via the most similar non-failure execution, rather than any arbitrary one?
Show answer
Comparing against a dissimilar non-failure execution would flag many irrelevant differences as "the deviation," burying the real cause in noise. The most-similar execution shares the longest prefix, so its single point of divergence is the minimal, most targeted explanation of the failure.Misconception: that any non-failure comparison works. The theoretical guarantee only holds for the execution with the longest common prefix.
Problem 5 · medium
Why does CLODS analyze LLVM IR but instrument live bytecode, rather than doing both on IR or both on bytecode?
Show answer
IR-based analysis is language-agnostic and can be written in efficient C/C++ rather than per-language analysis frameworks. But IR isn't what's actually running — the JVM/Android/Python runtimes execute bytecode, and only bytecode-level instrumentation can be injected live without restarting the process.Misconception: that IR and bytecode are interchangeable. CLODS needs an explicit IR-to-bytecode mapping (via DWARF info it had to add to GraalVM) to bridge the two.
Problem 6 · hard
The static analyzer's plan comes back empty. Under what condition does CLODS report success, and under what condition does it report an error?
Show answer
Success, if the analysis has naturally reached the program's entry point (main/API boundary) — the deviation is then attributed to that API call or its parameters. Error, if the plan is empty for any other reason, e.g. call-site or data-dependency analysis failed before reaching an entry point — typically because the next dependency crosses into unanalyzable code (like OS/filesystem internals).Misconception: that an empty plan always means failure. Reaching the program boundary is itself a valid, successful terminating condition.
Problem 7 · easy
Why can't Hubble or Intel PT-style always-on tracing have caught HDFS-10453's root cause, even though both are lightweight, always running?
Show answer
Both use fixed-size ring buffers. The gap between HDFS-10453's root cause and its symptom was 10 minutes of node traversal — enough to generate ~557MB of Hubble trace data, 16× larger than Hubble's 32MB buffer, so the root-cause moment gets overwritten before the failure is even detected.Misconception: that "always tracing" guarantees you capture everything. Ring buffers only retain the most recent window, which can be shorter than the failure's actual propagation delay.
Problem 8 · medium
CLODS could not diagnose HBase-4078 or HDFS-14135. What do these two failures have in common that explains why?
Show answer
Both require tracking a data dependency through a filesystem read call (f.read()) whose implementation is outside CLODS's instrumentable/analyzable code — the static analyzer can't resolve the return value's origin, so it terminates with an incomplete-analysis error rather than guessing.Misconception: that CLODS can diagnose any bug given enough rounds. Its boundary is exactly the boundary of code it can compile to LLVM IR and instrument — kernel and filesystem internals fall outside it.
Quick answers

Frequently asked questions

Tap to expand.

Q1What exactly is a "wild goose chase"?▾
A developer forms a hypothesis about the root cause without sufficient evidence, spends real effort verifying it, and eventually finds it wrong. The paper measured 62% of hard bugs having at least one, costing 54% of diagnosis time.
Q2Why does CLODS "never fork"?▾
Forking (tracking multiple possible causal paths at once) is how prior tools like Kairux and statistical debuggers handle ambiguity — but only one path actually happened, so every other fork is wasted analysis, and in the worst case forking explodes exponentially. CLODS instead pauses and collects more targeted evidence instead of guessing which fork is real.
Q3How is CLODS different from Kairux?▾
Both follow the inflection point hypothesis. Kairux computes a full program slice up front and synthesizes non-failure executions by modifying test cases, off-site — this doesn't scale on-site (13,470 instructions for one HDFS bug). CLODS builds the slice and the comparison incrementally, using only naturally-occurring production executions, entirely on-site.
Q4How is it different from Log20?▾
Log20 places logging to impartially cover any execution path, not knowing which failure (if any) will occur — "shooting blind." CLODS's logging is target-driven: it only ever logs points relevant to disambiguating the one specific failure path that already happened, which is why its overhead stays under 4% instead of needing thousands of log points to cover everything.
Q5Why use LLVM IR instead of a Java-native analysis framework?▾
LLVM IR analysis is language-agnostic (works for Java, Kotlin, Python alike) and can be written in efficient C/C++ instead of Java, which prior work shows can be substantially slower for this kind of analysis. The tradeoff is engineering cost: GraalVM's Java→LLVM-IR path didn't originally preserve debug info, so the authors patched it upstream.
Q6Does instrumentation ever require restarting the application?▾
No. The instrumenter uses each language runtime's ability to rewrite bytecode dynamically (JVM, Android runtime, CPython), so logging can be added and removed from a running process with low latency.
Q7What's the actual runtime overhead?▾
Averaging across evaluated bugs and workloads: about 3.85% on read-heavy workloads and 2.64% on write-heavy ones (worst case per bug, not average case), with the static analyzer using under 105MB of memory and completing each round in well under 100ms.
Q8How does CLODS do against an LLM agent?▾
On the same 23 bugs, CLODS succeeded deterministically on 83% (19/23); a Claude Opus 4.7 agent succeeded on 62% of attempts, doing worse specifically on bugs with long cause-to-symptom propagation, but better on 2 bugs involving OS/kernel-level causes CLODS can't instrument.
Q9What kinds of bugs can't CLODS diagnose?▾
Three categories: (1) bugs whose root cause lies in code that can't be compiled to LLVM IR or that CLODS lacks access to (filesystem/OS internals); (2) bugs that leave the system in an irrecoverable state, since CLODS needs the program to keep running to reoccur; (3) failures without a well-defined single symptom event (e.g. gradual memory leaks).
Q10Isn't this the same as deterministic replay?▾
No. Deterministic replay records and replays an entire execution to reproduce a bug, but doesn't locate the root cause, and its overhead (20%–3500% in prior work) is generally too high for production. CLODS performs targeted, cheap instrumentation and does the root-cause localization itself.
Q11Why is 2.5 rounds "cheap" if each round requires waiting for a reoccurrence?▾
It's cheap in analysis and instrumentation cost (few log points, low overhead) — the paper is explicit that diagnosis latency can still be long for rarely-occurring bugs, since each round genuinely waits for the failure to happen again. That's listed as one of CLODS's limitations.
Q12What happens if two different root causes can trigger the same symptom?▾
The paper flags this as a known limitation: if different rounds happen to observe different root causes producing the same exception, CLODS's analysis (which discards prior instrumentation each round) could conflate them. The authors suggest keeping all prior rounds' instrumentation active as a fix, ensuring later executions are a superset of earlier ones.

Core terms
CLODSClosed Loop On-Site Diagnosis System — iteratively runs static analysis + targeted logging entirely at the production site to find a failure's root cause without speculation.
Wild goose chaseTime spent verifying a speculative hypothesis about a bug's cause that turns out to be wrong.
Inflection point hypothesisRoot cause = the first event in the failure execution that, once it happens, guarantees the symptom; found via the longest-common-prefix non-failure execution.
Deviation event (e_deviate)The current point of disagreement between the failure and the chosen non-failure execution; the target of each analysis round.
Location deviationAn event occurs in one execution but not the other (includes "missing events").
Branch deviationA conditional branch present in both executions takes different targets.
CDA / DDA / CSAControl Dependency Analysis (controlling branches), Data Dependency Analysis (variable definitions), Call Site Analysis (callers) — the static analyzer's three building blocks.
Program sliceAll instructions an instruction transitively depends on; grows explosively (13,470 for one HDFS exception) if computed all at once.
Supporting terms
Map loop / reduce loopA loop whose iterations are independent w.r.t. an instruction (map) vs. accumulate toward it (reduce); CLODS decides this per-instruction from runtime behavior.
Dominance / post-dominanceX dominates Y if every path to Y passes through X; Y post-dominates X if every path from X to exit passes through Y — defines "controlling branch instruction."
LLVM IRLanguage-independent intermediate representation CLODS's static analyzer operates on, enabling Java/Kotlin/Python analysis in one framework.
Instrumentation planThe small set of program points (CBIs/VDIs) the static analyzer wants logged for the next round.
Per-thread log bufferEach thread writes to its own buffer (default 16MB), flushed when full or on thread exit — avoids synchronization overhead.
Auxiliary/manual cross-component mapA small hand-built hash map linking a value's use to its definition across components (e.g. network boundary); only 4 entries needed in evaluation.
