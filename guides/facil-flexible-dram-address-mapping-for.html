Same bytes, two readings — how FACIL lets PIM and the SoC share one weight matrix

On-device LLM inference needs a near-bank PIM processor to chew through memory-bound GEMV, and a CPU/GPU/NPU to run compute-bound GEMM on the very same weights. Each side wants a different DRAM layout. FACIL stops that from meaning "make a copy" or "translate and wait" — it stamps a tiny mapping ID onto each huge page and lets the memory controller do the rest, for free.

🧩 FACIL: Flexible DRAM Address Mapping · Seo et al., HPCA 2025 🎓 Assumes DRAM address mapping, virtual memory, and basic near-bank PIM ⏱ ~40 min read
🔀

Stamp each huge page with a small MapID in spare page-table bits, and let the memory controller apply PIM's bank-contiguous layout or the SoC's row-major layout to the very same physical bytes — the choice lives in address translation, not in a re-layout pass or a second copy of the weights.

Before you begin

Nine ideas FACIL builds on

You already know DRAM address mapping and virtual memory, so these skip straight to the pieces FACIL actually leans on: why GEMV wants PIM and GEMM doesn't, what a "chunk" and "tile" are, why the interleaving bits fit inside a huge page's offset, and why sharing one weight matrix between PIM and the SoC is genuinely hard. 1Why decode is GEMV and memory-bound, while prefill is GEMM and compute-bound▾

LLM inference has two phases. Prefill processes the whole input prompt at once — matrix×matrix (GEMM), high arithmetic intensity, favors compute throughput. Decode generates one token at a time, auto-regressively — matrix×vector (GEMV), one token's worth of work per weight-matrix pass, so it is starved for bandwidth, not FLOPs.

The paper profiles this directly (Fig. 2) on a Jetson AGX Orin running Llama3-8B: >90% of decode-phase time goes to linear (GEMV) operations, and across the four linear-layer shapes in that model, compute utilization stays below 1% while memory-bandwidth utilization sits around 72–81%.

Now you're ready: decode/GEMV wants a memory-side accelerator; prefill/GEMM wants a compute-side one. FACIL exists because both operate on the same weight matrix.
2Near-bank PIM: bringing the compute to the bank▾

Processing-in-memory (PIM) puts a small compute unit next to (not inside) each DRAM bank, so many banks can do simple arithmetic in parallel using DRAM's own internal bandwidth — far higher than what escapes through the pins. Among PIM flavors (in-memory, near-bank, near-DIMM, buffer-die), the paper focuses on near-bank PIM (e.g. SK Hynix AiM, Samsung HBM-PIM), the class with real taped-out prototypes and commercial products.

The payoff is large: offloading GEMV to an AiM-style PIM on a Jetson AGX Orin running Llama3-8B gives a 3.32× speedup even over a hypothetical, ideal NPU with infinite FLOPS and 100% peak-bandwidth utilization (Fig. 3) — because that ideal NPU is still capped by the external memory bus, and PIM isn't.

Now you're ready: PIM's advantage over even a perfect conventional processor comes from bandwidth internal to DRAM. That's worth protecting — which is exactly why the data layout matters so much (next primer).
3Chunks and tiles: the unit of PIM-friendly placement▾

A chunk is the slice of the matrix one PIM processing unit (PU) works on per step; its shape (output-register size, input-register size) is fixed by the PU's hardware. AiM's input register holds a full DRAM row of the input vector and its output register holds one output element, giving a chunk dimension of (1, 1024) at FP16 (a 2KB LPDDR5/GDDR6 row ÷ 2 bytes). HBM-PIM has 8 input+8 output registers of 32B (HBM2 transfer size) each, but — lacking a reduction unit — each output register only accumulates 16 partial sums for one output element, so its usable chunk dimension is (8, 128), not the naively expected (128,128).

A tile concatenates chunks row-wise across every bank of every channel, because banks in a rank move in lock-step (same command, same location). Placing chunks row-wise keeps every PU reading the same column index, which is what lets the input vector be broadcast cheaply to all of them.

Now you're ready: "PIM-optimized mapping" = keep each chunk contiguous within one bank, keep one matrix row entirely inside one bank, and tile row-wise across banks — three placement rules a conventional DRAM mapping was never designed to satisfy.
4Where the interleaving bits live inside a huge page▾

Conventional DRAM address mapping puts row bits at the most-significant end of the physical address and the channel/bank/rank ("interleaving") bits toward the low end. For an edge device's small memory system (few channels, few ranks), those interleaving bits — plus the column and byte-offset bits — usually all fit inside the 21 least-significant bits of the address, i.e. inside the page offset of a 2MB huge page.

That's the enabling fact behind everything else: software that controls where cache lines land within a huge page can realize any interleaving it wants — including PIM-optimized ones — without the OS ever having to change which physical page backs the huge page.

Now you're ready: a 2MB huge page's page offset is exactly wide enough to hold a full custom DRAM address mapping. That's the "slot" FACIL exploits.
5Why BLAS libraries can't just tolerate a PIM-optimized layout▾

Highly-optimized GEMM kernels (Intel oneMKL, NVIDIA cuBLAS) assume a matrix in virtual address space is a plain 1D array in row-major or column-major order. A PIM-optimized mapping breaks that assumption at the physical level — but if it also changes what a program sees at the virtual-address level, every GEMM call downstream either needs a full re-layout back to row-/column-major, or a hand-written kernel for the PIM layout. Neither is acceptable on a resource-constrained edge SoC.

Now you're ready: the real challenge isn't storing data for PIM (huge pages already solve that) — it's letting the SoC's existing, unmodified GEMM kernels keep working on the same bytes.
6The three candidate fixes — and why two of them are bad▾

(a) Weight duplication — keep one copy in each layout. Simple, but doubles memory footprint, which resource-constrained edge devices can't spare. (b) On-demand re-layout — keep one PIM-optimized copy, and re-layout to conventional form right before each GEMM. Only a small, temporary footprint increase, but the re-layout itself is slow: on a Jetson AGX Orin running Llama3-8B, adding re-layout roughly triples time-to-first-token, from about 100ms to about 300ms, as prefill length grows (Fig. 6). (c) FACIL — one copy, no re-layout, transparent access from both sides.

Now you're ready: this is the design space FACIL is judged against — memory-doubling vs. latency-tripling vs. neither.
7Why time-to-first-token (TTFT) is the metric that matters here▾

TTFT (time until the first output token appears) is set entirely by the prefill phase; TTLT (time to the last token) also includes the whole decode phase. For interactive apps — chatbots, voice assistants, autocomplete — users perceive a system as instantaneous only below roughly 100ms, and a voice assistant is claimed to need TTFT under about 250ms to feel human. Because users read/listen while later tokens stream in, TTFT dominates perceived latency far more than TTLT does.

Now you're ready: re-layout overhead lands squarely on TTFT (it delays prefill), which is exactly the number users notice first. That's why the paper reports TTFT speedup as its headline metric.
8MapID, previewed▾

A MapID is a small integer, recorded once per huge page, that tells the memory controller which physical-address-to-DRAM-address (PA-to-DA) mapping to apply when translating requests to that page. FACIL supports a small, bounded number of mappings — for LPDDR5 with a 2MB huge page, the worst case (single channel, single rank, 8-bank mode) allows at most 13 (i.e. MapID 0–13, 14 total mappings), which fits in just 4 spare bits.

Now you're ready: MapID is the whole trick in miniature — a few bits, stored per page, that turn "which DRAM layout" from a data-movement problem into a lookup.
9pimalloc, previewed▾

pimalloc is FACIL's user-level allocation call. Give it a matrix's dimensions and datatype; a mapping selector (ordinary user-space software) computes the best MapID for that matrix given the memory and PIM configuration; the OS allocator then allocates huge pages and records both the physical addresses and the MapID in the page table; the caller gets back an ordinary virtual address. Every later load or store to that address is completely ordinary from the programmer's point of view — the page table and memory controller carry the MapID silently.

The whole story in one place

FACIL in a nutshell

The conflict, the insight that resolves it, and the numbers that justify the plumbing.

An on-device LLM's weight matrices are used twice, by two different masters. The PIM domain wants them GEMV-ready: each chunk contiguous within a bank, each matrix row entirely inside one bank, chunks tiled row-wise across banks — a layout that has almost nothing in common with conventional DRAM mapping. The SoC domain — the CPU/GPU/NPU running GEMM during prefill, through unmodified oneMKL/cuBLAS-style kernels — wants the exact same matrix to look like an ordinary contiguous row-/column-major array in virtual memory. Naively reconciling the two costs either a full second copy of every weight matrix, or a re-layout pass before every GEMM that roughly triples TTFT on a Jetson AGX Orin (Section II-C, Fig. 6).

FACIL's insight: the fields a PIM-optimized mapping needs to rearrange — column, row, and the channel/bank/rank "PU-changing" bits — all live inside the page offset of a huge page for an edge-scale memory system (Primer 4). So instead of moving data, move the interpretation of its address. FACIL's machinery — a user-level pimalloc plus a mapping selector — picks a small MapID per huge page at allocation time (Section IV-B–C) and stores it in bits of the page-table entry that huge pages leave unused; a lightly-augmented memory controller then reads that MapID alongside the physical address and routes each field (channel/bank/rank/row/column) through the layout the MapID specifies (Section V-B). The SoC still issues ordinary loads/stores to an ordinary virtual address; the PIM processor still gets its bank-contiguous chunks. Nothing moves twice.

The hardware/software cost is deliberately tiny: at most 4 spare page-table-entry bits (the paper bounds the worst case at 14 possible mappings, i.e. MapID 0–13), and on the memory-controller side just five N-to-1 multiplexers — one each for channel, rank, bank, row, and column — added to the frontend that already does PA-to-DA translation. No new memory components, no TLB changes (the MapID rides in bits huge pages already leave idle, so it's safe inside a normal TLB entry).

The payoff: across four real edge platforms (Jetson AGX Orin, MacBook Pro M3 Max, Lenovo IdeaPad, iPhone 15 Pro), FACIL reaches geomean TTFT speedups of 2.37× (Alpaca-style conversation) and 2.63× (code autocompletion) over a SoC-PIM hybrid baseline that still pays the re-layout tax, with only a measured 0.1–2.1% GEMM slowdown from running on the PIM-optimized layout, and a one-time, amortized huge-page allocation overhead of at most 1.90× model-load time under heavy fragmentation.

🍯 Key takeaways

  • The conflict: PIM wants bank-contiguous chunks; SoC/BLAS wants ordinary row-major arrays — over the same weight matrix.
  • The naive fixes cost either 2× memory (duplication) or ~3× TTFT (on-demand re-layout, Fig. 6).
  • FACIL's move: encode the DRAM layout choice as a MapID stored per huge page, not as a copy of the data.
  • MapID lives in page-table bits huge pages already leave unused (≤4 bits suffice; max MapID = 13 in the worst case).
  • The memory controller applies the MapID with five simple multiplexers — no new memory, no TLB change.
  • Result: 2.37×/2.63× geomean TTFT speedup (Alpaca / code-autocompletion) over the SoC-PIM hybrid baseline; GEMM-on-PIM-layout slowdown only 0.1–2.1%.
  • FACIL leaves non-shared memory's mapping untouched — only huge pages holding PIM↔SoC-shared weights are affected.
Five everyday pictures

How to think about FACIL

Each picture stands alone — read in any order. Every card ends with an honest note about where the analogy stops being true.

The conflict · shared weights, two masters

Two readers, one book, no photocopier

Both readers need the exact same book. One reads it front-to-back like a novel (SoC: row-major GEMM). The other needs it re-organized by topic scattered across chapters to work efficiently (PIM: bank-contiguous chunks). Photocopying the book for each reader (duplication) doubles your shelf space; reformatting it before every reading session (re-layout) makes everyone wait.

Where it breaks: a real book's words move when reorganized; FACIL's bytes never move — only the "reading order" (address mapping) does. The analogy is about the conflict, not the fix.
FACIL's machinery · MapID + the MC mux

A universal travel adapter

Your laptop charger's plug (the physical address) never changes. A universal adapter reassigns which pins carry live/neutral/ground depending on a small switch setting (MapID) — US socket or EU socket, same underlying prongs, different wiring at the very last step. FACIL's memory-controller multiplexers are that switch: five of them, one per DRAM field, reading the MapID to decide which physical-address bit goes where.

Where it breaks: a travel adapter is fully general; FACIL's "adapter" only supports as many settings as fit in the spare PTE bits (≤14 mappings in the paper's worst case) — it's a small, fixed menu, not an arbitrary rewiring.
FACIL's machinery · spare PTE bits

Writing in the form's margin

A big form (huge-page PTE) has generous margins because it needs fewer digits to number its bigger "line items" (physical frame numbers) than a small form (4KB-page PTE) does. FACIL writes the MapID in that unused margin — 9 bits of it for 2MB huge pages on a system with 4KB regular pages — instead of stapling on an extra page.

Where it breaks: a form's margin is just blank space; the PTE's spare bits are spare only because huge pages need fewer physical-frame-number bits than regular pages — it's a structural fact about paging, not blank space by convention.
Chunks & tiles · PIM-optimized placement

Packing one shelf per mover, not one book per shelf

A row-major library shelves books by call number, spread wherever they land (conventional mapping). A moving crew instead wants every book of one shelf-load to ride in the same truck (bank) so no truck needs to swap boxes with another mid-route (inter-bank reduction). That's the chunk/tile rule: keep a chunk contiguous in one bank, keep a whole matrix row in one bank.

Where it breaks: a moving crew re-decides truck loading once; FACIL's tiling rule (Section II-C) is fixed by the PU's register geometry (e.g. AiM's (1,1024) chunk) and by which DRAM row size and bank count the platform actually has — it isn't a free choice per shipment.
The tax removed · duplication vs. re-layout vs. FACIL

A live interpreter instead of a photocopy or a break

Weight duplication is photocopying the whole document for the second reader — costly in paper (memory). On-demand re-layout is pausing the meeting to retype the document in the other reader's format — costly in time (TTFT). FACIL is a live interpreter standing between two readers of the same physical page, translating meaning (address bits) on the fly, at essentially no cost.

Where it breaks: a human interpreter's cost scales with sentence length; FACIL's "interpreting" is a handful of hard-wired multiplexers evaluated once per memory access — genuinely near-zero marginal cost, which is a much stronger claim than the analogy suggests.
Section by section

How FACIL actually works

Allocation and access flow (pimalloc) → the mapping formula and its bit rules → the selection algorithm → the OS and memory-controller changes that make it real.

1 · Allocation and access: pimalloc end to end

Everything starts when the LLM runtime calls pimalloc(dim, dtype) for a weight matrix that will be touched by both PIM and the SoC. The mapping selector (user-level software) turns the matrix's shape and datatype, plus the fixed memory and PIM configuration, into a single MapID. That MapID and the matrix's size go to the OS memory allocator, which allocates huge pages and records both the physical addresses and the MapID in the page table, then hands back an ordinary virtual address. From then on, stores and loads look completely normal: the programmer passes only a VA (and data, for stores); the page-table entry supplies the physical address and MapID to the memory controller, which performs PA-to-DA translation according to that MapID before touching DRAM.

2 · The mapping formula: where the bits go

Section IV-B derives the PA-to-DA mapping from three placement rules (Primer 3): keep a chunk's row-major layout inside one DRAM row, keep a whole matrix row inside one bank, and put chunks tiled row-wise. Concretely, assuming LPDDR5 with a 32B transfer size and a 2KB DRAM row: AiM's chunk holds 1024 elements per row at FP16, so log2(1024×2/32) = log2(64) = 6 DRAM column bits are placed directly above the DRAM offset bits. HBM-PIM's chunk holds 128 elements per row (8 partial-sum rows × 16 elements), so log2(128×2/32) = log2(8) = 3 column bits go there instead. Above the column bits come log2(matrix_column / chunk_column) row bits (so one matrix row exactly spans one bank), then the PU-changing bits — the concatenation of bank, rank, and channel bits — so that consecutive matrix rows land on different PUs. Any remaining row bits fill the rest of the page offset's most-significant end.

Because the position of the PU-changing bits is the only thing that changes between mappings, FACIL defines MapID as exactly that position: for AiM-style PIM, the number of bits between the PU-changing bits and the chunk-column bits; for HBM-PIM-style PIM, the number of bits between the chunk-row bits and the chunk-column bits. A bigger MapID means the PU-changing bits sit further from the column bits — i.e. the matrix row is wider, needing more row bits before a bank boundary is reached.

◆
The governing formula. The number of distinct mappings FACIL ever needs to support is bounded: max(MapID) = log2( hugepage_size / (total_bank_count × DRAM_transfer_size) ). Smaller total_bank_count (fewer channels/ranks/banks) and smaller transfer size increase the bound, because there's more room in the page offset for the PU-changing bits to move around in.

3 · The selection algorithm

Figure 9's select_mapping pseudocode is what the mapping selector actually runs, given a matrix's column count and datatype plus the fixed memory/PIM configuration:

int select_mapping(matrix_config, memory_config, pim_config) {
  // matrix: row size in bytes, rounded up to a power of two
  matrix_col = matrix_config->dim[1]
  row_size   = pow2ceil(matrix_col) * sizeof(matrix_config->dtype)

  // memory: how much of a huge page lands in each bank
  total_bank_count = memory_config->n_ch * memory_config->n_rank * memory_config->n_bank
  memory_per_bank  = memory_config->hpage_size / total_bank_count

  // does one matrix row fit in one bank's slice of the huge page?
  need_partition = memory_per_bank < row_size

  map_id = need_partition ? log2(memory_per_bank) : log2(row_size)
  map_id -= log2(pim_config->chunk_col)
  return map_id
}

If a whole matrix row fits inside one bank's share of the huge page, MapID is derived from the row size itself. If it doesn't (need_partition), FACIL instead partitions the row across multiple PUs — potentially in different channels — and derives MapID from how much memory one PU actually gets per huge page. Either way, subtracting log2(chunk_col) expresses everything relative to the chunk's own column width. Tab 5 walks this algorithm through the paper's own worked example (Fig. 10) and reproduces its two MapID values exactly.

When a matrix row must be split across PUs in different channels (the need_partition branch), each channel computes a partial sum for its share of the row; the SoC processor performs the final reduction across channels after the PIM operation completes.

4 · OS paging: where MapID actually lives

FACIL extends mmap() with an optional MapID argument and stores it in the page table entry — using bits that are simply unused, not bits taken from anything else. A 4KB regular page's PTE needs a physical-frame-number (PFN) field wide enough to address 4KB-aligned frames (offset = 12 bits); a 2MB huge page's PTE only needs to address 2MB-aligned frames (offset = 21 bits), so its PFN field is 21 − 12 = 9 bits narrower. Those 9 bits are simply idle in a huge-page PTE — and since the worst-case bound from Section IV-B is 13 (14 total mappings, MapID 0–13), representing any of them needs only ⌈log2(14)⌉ = 4 bits, comfortably inside that margin. Because a TLB entry already supports both page sizes, no TLB change is needed — the MapID simply rides along in bits that were always going to be idle for a huge page.

5 · Memory controller: five multiplexers, no new memory

Inside a typical memory controller, only the frontend — the stage that translates physical addresses into DRAM addresses (channel/rank/bank/row/column) before requests enter the queues — needs to change. FACIL adds an array of N-to-1 multiplexers (N = number of supported mappings), one each for channel, rank, bank, row, and column: each mux takes the physical address plus the page's MapID and outputs the correct bit slice for that field, according to whichever mapping the MapID selects. Figure 12's example supports four mappings total (three PIM layouts plus the conventional one) with this scheme.

6 · Discussion: costs and what's left unsolved

The paper separately measures the one-time cost of allocating huge pages for model weights: on a Jetson AGX Orin loading Llama3-8B (FP16, 16.2GB) from a 1TB NVMe SSD, load time increases by at most 1.90× in the worst tested condition (high fragmentation, low free memory — Table I), a cost the paper considers negligible since it's amortized over many rounds of inference on the same loaded model.

◇
Explicitly named as future work, not solved here. Scheduling PIM and non-PIM (ordinary SoC) memory requests to avoid interfering with normal processes is left open. The paper points to prior CPU-GPU heterogeneous memory-scheduling work, and to NeuPIMs' dual-row-buffer idea (separate row buffers for PIM vs. normal accesses, avoiding row-buffer conflicts) as a plausible direction — but FACIL itself does not implement either.

Worked examples

Every number below is recomputed from the paper's own figures and tables — the arithmetic is shown so you can redo it. The interactive widget reproduces Fig. 9's algorithm exactly against Fig. 10's own example.

Example 1 — the column-bit counts behind Fig. 8

LPDDR5, 32B transfer size, 2KB DRAM row, FP16 weights.

  1. AiM (chunk = 1024 elements/row): bytes per chunk row = 1024 × 2B = 2048B. Column bits = log2(2048 / 32) = log2(64) = 6.
  2. HBM-PIM (chunk = 128 elements/row): bytes per chunk row = 128 × 2B = 256B. Column bits = log2(256 / 32) = log2(8) = 3.
◆
Takeaway: both numbers fall straight out of "how many DRAM transfers does one chunk row span" — the column-bit count is just log2 of that. A narrower chunk (HBM-PIM's 128 vs. AiM's 1024) needs fewer column bits.

Example 2 — the bit budget: max(MapID) and PTE spare bits

Worst case for maximizing MapID count: single channel, single rank, 8-bank mode, 2MB huge page, 32B DRAM transfer size.

  1. total_bank_count = 1 × 1 × 8 = 8.
  2. max(MapID) = log2( 2MB / (8 × 32B) ) = log2( 2,097,152 / 256 ) = log2(8192) = 13. This matches the paper's stated worst-case max of 13 exactly.
  3. MapID ranges 0–13, i.e. 14 distinct mappings. Bits needed: ⌈log2(14)⌉ = 4 (since 2³=8 < 14 ≤ 16=2⁴).
  4. Spare PTE bits from huge pages: 4KB page offset = 12 bits, 2MB page offset = 21 bits, so the PFN field shrinks by 21 − 12 = 9 bits — more than double the 4 bits MapID needs.
◆
Takeaway: the whole "no extra memory, no TLB change" claim rests on 4 ≤ 9 — a small, comfortable margin, not a tight fit.

Example 3 — reproducing Fig. 10's two MapIDs by hand

DRAM spec: 2 channels, 1 rank, 16 banks, 2KB (2048B) chunk column size, 2MB huge page. Two weight matrices, both FP16 (2 bytes/element).

  1. total_bank_count = 2 × 1 × 16 = 32. memory_per_bank = 2MB / 32 = 64KB.
  2. Spec A (2K × 8K matrix): matrix_col = 8192 → row_size = 8192 × 2B = 16KB. Since 16KB < 64KB, no partition needed. MapID = log2(16KB) − log2(2KB) = 14 − 11 = 3 — matches the paper's Fig. 10 exactly.
  3. Spec B (2K × 64K matrix): matrix_col = 65536 → row_size = 65536 × 2B = 128KB. Since 128KB > 64KB, partitioning is needed — the matrix row is split across channels. MapID = log2(memory_per_bank) − log2(2KB) = log2(64KB) − log2(2KB) = 16 − 11 = 5 — also matches Fig. 10 exactly.

Check yourself

Practice

Work the answer before opening it. Each answer ends with the misconception the question is designed to catch.

Warm-up
A near-bank PIM chunk holds 512 elements per row at INT8 precision (1 byte/element), and the DRAM transfer size is 32B. How many DRAM column bits does Section IV-B's rule place in front of the offset bits?
Show answer
Bytes per chunk row = 512 × 1B = 512B. Column bits = log2(512/32) = log2(16) = 4. Catches: treating the "6 column bits" from the AiM/FP16 example as a fixed constant. It's log2(chunk row bytes / transfer size) — it moves with both the chunk geometry and the datatype.
Compute
A platform has 4 channels, 2 ranks, and 8 banks, a 2MB huge page, and a 64B DRAM transfer size. What is max(MapID)?
Show answer
total_bank_count = 4 × 2 × 8 = 64. max(MapID) = log2( 2MB / (64 × 64B) ) = log2( 2,097,152 / 4096 ) = log2(512) = 9. Catches: assuming max(MapID) is always 13. That's specifically the worst case (fewest banks, smallest transfer size) — a platform with more channels/ranks/banks or a larger transfer size supports fewer distinct mappings, not more.
Trace the algorithm
Using the same DRAM spec as Fig. 10 (2 channels, 1 rank, 16 banks, 2KB chunk_col, 2MB huge page), what MapID does select_mapping return for a 2K × 32K FP16 matrix?
Show answer
matrix_col = 32768 → row_size = 32768 × 2B = 64KB. memory_per_bank = 2MB / (2×1×16) = 64KB. Since memory_per_bank (64KB) is not less than row_size (64KB), need_partition is false (the check is strict "<"). MapID = log2(64KB) − log2(2KB) = 16 − 11 = 5 — the same MapID as Spec B, right at the partitioning boundary. Catches: assuming "right at the boundary" always triggers partitioning. The algorithm's `<` is strict, so a row that exactly fills a bank's share still takes the no-partition branch — worth checking boundary cases explicitly rather than eyeballing "close enough."
Design
FACIL leaves the DRAM mapping for ordinary (non-PIM-shared) memory completely untouched, unlike IANUS, which proposes one global mapping for its NPU-PIM accelerator. Why does that difference make sense given FACIL's target platform?
Show answer
IANUS targets a server-scale, discrete NPU-PIM accelerator designed from scratch, where a single global mapping can be co-designed with everything else. FACIL targets edge SoCs that must keep using an existing memory system for all memory traffic, most of which has nothing to do with PIM. Changing the global mapping would risk conventional SoC memory access patterns (for every other app and OS structure) for a benefit that only matters for the specific huge pages shared between PIM and SoC GEMM. Scoping the change to only those pages — via a per-page MapID — is what makes the modification "minimal" and safe to deploy on a general-purpose device. Catches: assuming "more flexible/global" is strictly better than "narrowly scoped." On a resource- and compatibility-constrained edge SoC, the narrower change is the one that's actually deployable.
Diagnose
Across the four platforms, FACIL's real-world-dataset TTFT/TTLT speedup is smallest on the Lenovo IdeaPad, even though the mapping mechanism is identical everywhere. What in the evaluation explains this, and what would you check on a fifth platform before predicting its speedup?
Show answer
The paper measured GEMV-kernel memory-bandwidth utilization per platform: Jetson 76.3%, MacBook 88.3%, iPhone 74.6%, but IdeaPad only 33.3% — all others exceed 70%. Low bandwidth utilization means the IdeaPad's prefill/decode is not dominated by the memory-bound cost that re-layout would otherwise inflate, so eliminating re-layout buys proportionally less. Before predicting speedup on a new platform, you'd want to measure its GEMV kernel's achieved bandwidth utilization (not just its peak bandwidth spec) — a platform that can't reach high utilization won't benefit from FACIL as much, independent of MapID mechanics. Catches: assuming FACIL's benefit is a fixed property of the technique. It's gated by how memory-bound the underlying platform's GEMV execution actually is in practice — a software/hardware efficiency question separate from the mapping mechanism itself.
Loose ends

Frequently asked

The questions that come up once the mechanism clicks.

QIs FACIL a new PIM chip?▾
No. FACIL is a memory-controller and OS augmentation that works with existing near-bank PIM designs (the paper evaluates against AiM-style PIM, simulated). It doesn't propose new PIM compute hardware — it solves the address-mapping-sharing problem that any SoC-integrated near-bank PIM would face.
QDoes FACIL change the DRAM mapping for memory that isn't shared between PIM and the SoC?▾
No — this is deliberate (see Practice, Q4). Only huge pages allocated via pimalloc for PIM↔SoC-shared weight matrices get a non-default MapID. Everything else keeps using the SoC's conventional mapping, unmodified.
QWhere exactly does MapID get stored, and does it need new hardware storage?▾
In bits of the page-table entry that huge pages already leave unused — 9 spare bits for a 2MB huge page vs. a 4KB regular page, of which at most 4 are needed (Example 2). No extra PTE space, and no TLB format change, since a TLB entry already accommodates both page sizes.
QDoes supporting multiple mappings need new DRAM chips or memory-controller memory arrays?▾
No. The change is confined to the memory-controller frontend (the PA-to-DA translation stage) and is implemented as five N-to-1 multiplexers (channel/rank/bank/row/column) — pure combinational logic, no additional storage (Section V-B).
QWhy does the mechanism specifically need huge pages, rather than working at a finer or coarser granularity?▾
For an edge-scale memory system, all the bits a custom DRAM mapping needs to rearrange (row/bank/rank/channel/column) fit inside the ~21-bit page offset of a 2MB huge page (Primer 4) — so one MapID per huge page is exactly the right granularity to describe a full custom mapping. It also matches pimalloc's natural allocation unit, so no extra bookkeeping structure is needed beyond the page table that huge pages already require.
QDoes storing weights in the PIM-optimized layout slow down GEMM on the SoC?▾
A little. The paper measures this directly with GPGPU-Sim (GPU platforms) and ONNXim (NPU platform) across several prefill lengths, finding a worst-case slowdown of 2.1% (Jetson), 0.1% (MacBook), 1.1% (IdeaPad), and 1.6% (iPhone) — and conservatively applies each platform's worst-case number to every FACIL performance result reported (Table III).
QDoes FACIL handle batched/multi-query serving, like NeuPIMs?▾
No — FACIL targets single-query, single-batch on-device inference, where GEMM (prefill) and GEMV (decode) run as discrete, sequential phases. NeuPIMs instead focuses on running GEMM and GEMV in parallel to serve batched requests on server-scale hardware; that's a different problem (throughput under concurrency) from FACIL's (transparent sharing on one resource-constrained device).
QWhat does FACIL explicitly not solve?▾
Scheduling/contention between PIM memory requests and ordinary SoC memory requests. The paper names this as remaining work, pointing to prior CPU-GPU heterogeneous memory-scheduling research and NeuPIMs' dual-row-buffer idea as possible directions, without implementing either itself (Section V-C).

Reference

Glossary, a dated summary card, related work, and honest provenance notes.

Core terms
PIM / near-bank PIMProcessing-in-memory; near-bank PIM places a compute unit adjacent to each DRAM bank to exploit bank-level parallelism and internal DRAM bandwidth.
GEMV / GEMMMatrix-vector (decode, memory-bound) vs. matrix-matrix (prefill, compute-bound) multiplication — the two operations that pull weight matrices toward opposite optimal layouts.
ChunkThe fixed-size slice of a matrix one PIM processing unit handles per step; shape = (output register size, input register size), e.g. AiM (1,1024), HBM-PIM (8,128).
TileA row-wise concatenation of chunks processed by every bank of every channel in lock-step.
PUPIM processing unit — the near-bank compute element that operates on one chunk at a time.
PA-to-DA mappingPhysical-Address-to-DRAM-Address mapping: the function that decides which physical address bits become channel/rank/bank/row/column.
MapIDA small integer, stored per huge page, naming which PA-to-DA mapping the memory controller should apply — specifically, the bit-position of the "PU-changing" field.
pimallocFACIL's user-level allocation call: given a matrix's dimensions and dtype, computes a MapID and allocates huge pages stamped with it.
Supporting terms
Mapping selectorUser-level software that runs Fig. 9's algorithm to pick a MapID from matrix + memory + PIM configuration.
PU-changing bitsThe concatenation of bank, rank, and channel bits — the fields that determine which PU a matrix row lands on.
TTFT / TTLTTime-to-first-token (set by prefill only) vs. time-to-last-token (also includes all of decode); TTFT dominates perceived interactive latency.
Hybrid static / dynamic baselineStatic: all GEMM always on the SoC. Dynamic: FACIL's added optimization that offloads short, tall-and-skinny prefill GEMMs to PIM when that's faster.
Ridge point (roofline)The arithmetic intensity (FLOP/byte) at which a processor transitions from memory-bound to compute-bound; equals Peak FLOPS ÷ Peak Bandwidth.
FMFIFree Memory Fragmentation Index (0–1); higher means free memory is more fragmented, making huge-page allocation slower/harder.
AiM / HBM-PIMSK Hynix's and Samsung's respective commercial/prototype near-bank PIM designs, with chunk dimensions (1,1024) and (8,128) respectively.
need_partitionFig. 9's branch condition: true when one matrix row is too large to fit in a single PU's share of a huge page, forcing the row to split across PUs (possibly across channels).

📌 Summary card · as of 2026-08-30 · FACIL, HPCA 2025

  • What: a memory-controller + OS augmentation letting SoC and near-bank PIM processors access the same weight matrix under different DRAM address mappings, chosen per huge page via a small MapID.
  • Why: GEMV/PIM needs bank-contiguous, chunk-aligned placement; GEMM/SoC (via unmodified BLAS kernels) needs an ordinary contiguous virtual array. Reconciling naively costs 2× memory (duplication) or ~3× TTFT (on-demand re-layout, Fig. 6).
  • Mechanism: pimalloc's mapping selector picks a MapID (Fig. 9) → OS stamps it into 9 spare huge-page PTE bits (only 4 needed) → memory-controller frontend applies it via 5 N-to-1 multiplexers, with no new memory components and no TLB change.
  • Bit budget: max(MapID) = log2(hugepage_size / (total_banks × transfer_size)); worst case for LPDDR5/2MB = 13 (14 mappings, 4 bits).
  • Result: geomean TTFT speedup 2.37× (Alpaca) / 2.63× (code autocompletion) over the SoC-PIM hybrid-static baseline; TTLT speedup 1.20× for both; GEMM-on-PIM-layout slowdown measured at only 0.1–2.1% across platforms.
  • Overhead: huge-page allocation adds at most 1.90× one-time model-load latency under heavy fragmentation (Table I) — amortized over many inference rounds.
  • Not the same as: weight duplication (2× memory, Fig. 5a) or on-demand re-layout (extra per-prefill latency, Fig. 5b) — the two naive alternatives FACIL replaces.
  • Left open: PIM-vs-SoC memory request scheduling/contention (Section V-C, named future work); FACIL is evaluated for single-batch, single-query inference only, not batched serving (contrast NeuPIMs).
  • Best/worst measured platform: Jetson AGX Orin (2.89× single-query TTFT geomean) vs. IdeaPad Slim 5 (1.55×) — explained by IdeaPad's low 33.3% GEMV memory-bandwidth utilization vs. >70% on the other three platforms.
Related work, as the paper positions itself

IANUS — NPU-PIM Unified Memory System contrast

ASPLOS 2024, cited as [74]

Proposes one global DRAM address mapping for a purpose-built NPU-PIM server accelerator. FACIL differs by targeting edge SoCs and leaving the mapping for non-shared memory untouched, changing only the mapping for PIM↔SoC-shared data.

NeuPIMs — NPU-PIM Heterogeneous Acceleration for Batched Inference contrast

ASPLOS 2024, cited as [28]

Targets parallel execution of GEMM and GEMV for batched serving, and proposes dual row buffers to avoid PIM/normal-access conflicts — the idea the FACIL authors point to as a possible fix for the scheduling problem they leave open. FACIL instead targets single-batch, discrete-phase inference.

DReAM — Dynamic Re-arrangement of Address Mapping related mechanism

MEMSYS 2016, cited as [20]

Uses real-time workload analysis to periodically update the memory controller's address mapping table for different access patterns — a related "make the DRAM mapping adjustable" idea, applied to general workload adaptation rather than PIM/SoC sharing specifically.

SDAM — Software-Defined Address Mapping related mechanism

ASPLOS 2022, cited as [86]

Lets user-level software adjust PA-to-DA mapping for 3D memory channel parallelism, offering a wider range of mapping options than FACIL — at the cost of more extensive hardware and OS modification. FACIL trades some of that flexibility for a much smaller footprint.
