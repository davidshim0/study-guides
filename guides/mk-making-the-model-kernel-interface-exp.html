Verify the kernel against what the model can send — not against inputs nobody chose

A CUDA kernel and the model that calls it are written by different people, on different schedules, with no contract between them. This is the plain-English story of M2K, a tool that writes that contract down and checks it.

1The layered inference stack▾

A user's prompt passes through: a Python model file (defines the architecture), an inference framework (vLLM, Transformers — schedules requests, manages memory), host-side wrapper code (prepares tensors, picks a kernel), and finally a CUDA kernel (does the actual matrix math on the GPU).

Now you're ready: M2K's whole premise is that the boundary between the Python layer and the CUDA layer is where nobody is actually checking anything.
2A CUDA kernel, concretely▾

A kernel runs across a grid of blocks, each block a group of threads. Every thread runs the identical code but computes its own array index from built-ins like blockIdx.x and threadIdx.x — typically tid = blockDim.x*blockIdx.x + threadIdx.x. A wrapper function on the CPU computes launch parameters (how many blocks/threads) from tensor sizes and then launches the kernel.

Now you're ready: the same arithmetic that computes tid is exactly where 89% of M2K's detected bugs live — as a 32-bit overflow.
3Why tensor shapes are dynamic▾

A kernel's buffer sizes depend on batch size and sequence length — both chosen by whoever sends the request. A kernel correct at batch=1, seq=128 can silently misbehave at batch=116, seq=18,079, because the index arithmetic was never checked against that combination.

Now you're ready: this is exactly the combinatorial space HFProbe has to characterize without brute-force testing every combination.
4Vectorization and other kernel optimizations▾

To go fast, kernels often process 4 elements per memory access (casting pointers to a float4-like type) and use a grid-stride loop — each thread starts at its own index and jumps forward by the total thread count until it runs out of work. These tricks are exactly where off-by-one and divide-by-4 bugs hide.

Now you're ready: cuKLEE has a dedicated technique (Section 4) for grid-stride loops so it doesn't have to unroll them thread-by-thread.
5Symbolic execution, briefly▾

Instead of running code on one concrete input, symbolic execution runs it on a symbol standing for "any possible value," collecting the logical constraints that describe every path. A solver (like Z3) then asks: "is there a concrete value satisfying these constraints and the condition for a bug?" If yes, it hands back the exact input that triggers it.

Now you're ready: cuKLEE is this technique, specialized so it doesn't choke on GPU tensors and thousands of threads.
6The implicit interface problem▾

A kernel's safety depends on assumptions ("token count fits in 21 bits") that are true only because of how models happen to call it today. Nothing forces the model, the framework, or the kernel to state or enforce that assumption — so it silently breaks as models and context windows grow.

Now you're ready: "making the interface explicit" means writing that assumption down as a checkable constraint — that's HFProbe's whole job.
7Why analyzing a kernel alone fails▾

A kernel analyzed with fully unconstrained inputs reports bugs for shapes that could never actually occur (false positives) — e.g. a scale tensor with zero elements. A kernel analyzed only against inputs a tester happened to try misses bugs that only appear at production scale (false negatives).

Now you're ready: M2K's two components exist precisely to sit between these failure modes — real but comprehensive input constraints.
8State explosion across threads▾

A kernel launch can spawn thousands of threads. Symbolically enumerating each one's execution path is intractable. The fix used elsewhere in systems research — and here — is to treat the thread's identifying numbers themselves as symbolic variables, analyzing the code once for "any thread."

Now you're ready: this is cuKLEE's symbolic thread-ID trick (Section 5.3), the reason one analysis pass covers every thread.
The whole story in one place

M2K in a nutshell

The problem, the two-part fix, and how the pieces connect.

Models and CUDA kernels are developed independently, by different teams, on different release schedules — yet a kernel's correctness silently depends on assumptions about the tensor shapes and input sizes a model will actually produce. When a model grows (bigger hidden size) or serves longer sequences, it can cross a limit the kernel author never wrote down — an implicit 32-bit index cap, a buffer sized for a smaller batch — and the kernel corrupts memory or crashes.

M2K's fix is to make that interface explicit. HFProbe runs a model's forward pass without any GPU — replacing every CUDA kernel call with a logging stub — and classifies each kernel argument as model-fixed (e.g. hidden size), linear in user input (e.g. token count), tied to another argument by equality, or merely bounded. It turns this classification into symbolic constraints: the model-kernel interface, written down for the first time. cuKLEE then symbolically executes the kernel under those constraints, modeling every tensor as a separate memory region (so dynamic shapes stay tractable) and every thread ID as symbolic (so one pass covers every thread), to find inputs — still legal under the interface — that overflow an index or write out of bounds.

The payoff: across 120 models and 173 kernels drawn from vLLM, Hugging Face, and four research papers, M2K finds 181 previously unknown memory bugs — 162 integer overflows, 19 out-of-bounds accesses — with only 9 false positives. Of 26 bugs reported to vLLM, 8 are already fixed and 4 more confirmed.

🍯 Key takeaways

  • Kernels break not because their math is wrong in general, but because their assumptions were never checked against what the model can actually send.
  • HFProbe extracts that interface — GPU-free — as four kinds of constraints: fixed, linear, equal, bounded.
  • cuKLEE models each tensor as a separate memory region and every thread ID as symbolic, so dynamic shapes and thousands of threads stay tractable.
  • M2K validates every finding by re-profiling the concrete input and checking it fits in a target GPU's memory — no un-triggerable "bugs."
  • Result: 181 real bugs, 9 false positives, across three independent sources of models and kernels.
Six everyday pictures

How to think about M2K

Each stands alone. Every card is honest about where the picture stops being true.

The core problem · No contract

Two contractors, no blueprint

A plumber and an electrician each build to their own plan, trusting the other "probably" left enough clearance. It works — until the electrician's team upsizes a panel and clips a pipe nobody told them was there. Models and kernels work the same way: no blueprint states what token counts a kernel must survive, so growth on one side quietly breaks the other.

Where it breaks: real contractors can eventually talk to each other; models and kernels ship on separate release cycles with no shared review, which is precisely why the mismatch persists for years.
cuKLEE · Symbolic execution

Solving with algebra, not plugging in numbers

Instead of testing "does the bridge hold at 40 people, 41, 42…", an engineer writes one equation with a variable and solves for the breaking load directly. cuKLEE does the same to kernel code: it runs it once with a symbol for "any batch size, any sequence length" and asks a solver whether some concrete value makes an index go out of bounds.

Where it breaks: algebra needs the equation to stay solvable — deeply nested loops or huge kernels can make the "equation" too large to solve within cuKLEE's one-hour budget.
cuKLEE · Tensor memory model

Numbered parking spots on separate islands

If every parking lot in a city sat on its own island, no car could ever drift onto another lot's numbering by accident — you'd always know instantly which island a car belongs to. cuKLEE puts every tensor in its own far-apart memory region for exactly this reason: any pointer immediately tells you which tensor it came from, so bounds-checking never has to search.

Where it breaks: real GPU memory doesn't actually work this way — cuKLEE's islands are a deliberate abstraction, not the true layout, so it can't catch cross-tensor aliasing bugs that violate the abstraction itself.
cuKLEE · Symbolic thread IDs

One understudy plays every role

Rather than rehearsing a scene with 10,000 individually cast extras, a director has one understudy read the part symbolically as "whichever extra is speaking," and reasons about the scene once. cuKLEE gives threadIdx.x and friends symbolic values instead of enumerating every thread, so a single analysis pass captures every thread's behavior — including ones the same reasoning shows can misbehave.

Where it breaks: an understudy assumes every "role" behaves by the same script; cuKLEE's data-race check has to re-introduce a second symbolic thread precisely because two threads can genuinely diverge.
HFProbe · Interface constraints

A locksmith's master-key chart

A locksmith doesn't test a lock against infinite keys; they note which pins are fixed and which vary, then cut a master key covering the whole family at once. HFProbe watches a handful of (batch, sequence) runs, notices which kernel arguments never change, which scale linearly with tokens, and which always match another argument — and writes that down as one reusable constraint set instead of testing endlessly.

Where it breaks: a master key chart is only as good as the pins it observed; HFProbe can miss a relationship that never shows up in the small set of runs it profiles, which is one source of its false positives.
Validation · Reachability check

Would it actually fit in the moving truck?

A mover can prove a couch fits through the algebra of doorway dimensions, but still has to check it against the actual truck's cargo size before calling the job done. cuKLEE's solver can prove a batch/sequence combination triggers an overflow, but M2K still estimates the resulting GPU memory footprint (model weights + KV-cache) and only reports the bug once it confirms that combination fits — and is reachable — on a real GPU.

Where it breaks: the estimate ignores intermediate/temporary buffers as negligible — usually fine, but it means the memory check is an approximation, not a guarantee.
The full explanation

How M2K actually works

HFProbe first, then cuKLEE, then how a finding gets confirmed.

1 · HFProbe — tracing a model without a GPU

HFProbe first builds a static, path- and field-sensitive call graph from the model's forward() method to find every CUDA kernel the model can statically reach — standard Python call-graph tools fail here because they don't resolve nn.Module.__call__. It then replaces every registered kernel's Python binding with a logging stub that records the call stack, argument types, tensor shapes/dtypes, and (for integer tensors) observed min/max values, then returns a zero-filled tensor of the right shape. With all GPU computation stripped out, the model runs its full forward pass on a CPU, once per (batch size, sequence length) combination.

🌱
Concretely: for the dynamic_scaled_fp8_quant kernel behind Qwen2's FP8 linear layer, HFProbe learns that out and input always share the same shape, that their last dimension is a model-fixed 896 (the hidden size), that their first dimension scales linearly with token count, and that scale always has exactly one element.

2 · Turning traces into interface constraints

HFProbe reruns the model over several (batch, sequence) combinations and, per kernel-call-site, sorts each argument into one of four buckets:

model-fixed   // constant across every run → pin to that value
user-linear   // scales proportionally with token count → the attacker's lever
equal         // always matches another argument's value → link with "="
bounded       // varies, no clean pattern → cap at the max value observed

3 · Configuration mutation — reaching more kernels

Some kernels are statically reachable but never triggered by a model's default config (e.g. a quantization variant, or a smaller n_routed_experts that switches the MoE padding kernel). HFProbe uses an LLM in agent mode — given the model's repo and a target kernel name — to propose a modified config.json; any mutation that crashes at runtime is simply discarded.

4 · cuKLEE — tensors as separate regions

Ordinary symbolic execution (KLEE) treats the heap as one contiguous space, so a dynamically-sized buffer makes every later buffer's base address symbolic too — bounds-checking becomes intractable. cuKLEE instead gives each tensor its own distinct, far-apart region and a set of symbolic fields describing it.

With these symbolic fields, cuKLEE supports 140 Tensor/TensorIterator methods across four categories: property queries (e.g. t.numel() → N), tensor-producing methods (e.g. t.sum(0) → new symbolic fields tied to the original's), property checks (e.g. contiguity, encoded as a constraint), and analysis-irrelevant methods (skipped).

5 · cuKLEE — threads without enumeration

cuKLEE introduces symbolic variables for blockIdx/threadIdx (bounded by gridDim/blockDim, themselves fixed at the kernel-launch site) and analyzes the kernel body once. For grid-stride loops — a thread starts at its global index and advances by the total thread count — cuKLEE analyzes the loop body a single time and then adds the loop's exit condition (e.g. i ≥ num_vec_elems) as a constraint on the state that follows, rather than unrolling per thread. Data races are checked by introducing a second symbolic thread, asserting the two differ, and checking for a conflicting write to the same address (with block IDs equated for shared memory, which is block-private).

6 · Buggy constraints, input bounds, and validation

cuKLEE injects a bug-condition check at every risky operation, on top of the batch/sequence constraints from HFProbe plus a model's own max_position_embeddings and a practical default (batch ≤ 1,000, sequence ≤ 1,000,000):

// at each pointer dereference
assert pointer outside [base, base+size)   // out-of-bounds
// at each 32-bit add/multiply
assert result exceeds INT32_MAX          // integer overflow
// at each pointer dereference
assert pointer derived from unknown base  // null-pointer deref

A satisfiable result yields concrete (batch, sequence) values. Before reporting, M2K replays them through HFProbe's profiling backend to confirm the framework actually accepts that request and invokes that kernel with matching arguments, and estimates GPU memory as weights + KV-cache, scaled by a fragmentation factor (1.25× vLLM, 1.45× Transformers):

KV-cache size = 2 × L × TC × H × sizeof(dtype)
// L = layers, TC = token count, H = hidden dim
if (weights + KV-cache) × fragmentation > target GPU memory:
    mark bug untriggerable on that GPU
💡
Why bother? A solver can prove a huge batch×sequence combination overflows an index while quietly requiring more VRAM than any GPU has. Without this check, M2K would report bugs no attacker could ever actually reach.
Follow the real numbers

Worked examples

Four bugs from the paper, carried through the arithmetic.

① The 2²¹−1 token cap (dynamic_scaled_fp8_quant)

The kernel behind Qwen2's FP8 linear layer computes tid = blockDim.x·blockIdx.x + threadIdx.x as a 32-bit int, with blockDim.x = 1024 and blockIdx.x ranging over the token count. At what token count does this overflow?

  1. tid caps out once blockIdx.x × 1024 alone exceeds INT32_MAX = 2,147,483,647, i.e. once token count > 2,147,483,647 / 1024 ≈ 2,097,151.999 → cap = 2²¹−1 = 2,097,151 tokens.
  2. A legal request: batch size 116, sequence length 18,079 → token count = 116 × 18,079 = 2,097,164.
  3. Margin past the cap: 2,097,164 − 2,097,151 = 13 tokens over.
  4. Result: tid and step go negative; the read on line 13 lands on an unmapped address → an "illegal memory access" crash, reproduced on an NVIDIA B300.
🍯
Insight: nothing about 116×18,079 is exotic — it's an ordinary large-batch, long-context request, 13 tokens past a limit nobody wrote down anywhere.

② An exact power-of-two overflow (VecQuant8BatchMatMulKernel)

For Qwen-1.8B-Chat (heads=16, height=128), weight_total = batch × width × heads × height is computed as a 32-bit int. Show that batch=128, seq_len(width)=8,192 overflows.

  1. Hidden size = heads × height = 16 × 128 = 2,048.
  2. width × hidden = 8,192 × 2,048 = 16,777,216.
  3. × batch = 128 × 16,777,216 = 2,147,483,648 = exactly 2³¹.
  4. INT32_MAX = 2³¹−1 = 2,147,483,647 — the computation overflows by exactly 1, wrapping weight_total to a large negative number.
  5. Consequence: the bounds check index1 >= weight_total (line 14) never fires, since weight_total is now negative — every dequantized weight silently becomes zero, corrupting the matrix multiply without any crash.
💡
This is why M2K finds far more integer overflows than out-of-bounds crashes: an overflow like this one corrupts results silently — no fault, no log line, just wrong answers.

③ An off-by-shape offset (moe_align_block_size_kernel)

Shared memory is laid out as num_experts+1 header slots followed by a per-thread table. The kernel computes the table's start as shared_mem + blockDim.x + 1 instead of shared_mem + num_experts + 1. When does this matter?

  1. Launch config: num_thread = max(num_experts, 32). For num_experts = 8 (below 32), blockDim.x = 32.
  2. Correct offset should be num_experts + 1 = 9; the kernel instead uses blockDim.x + 1 = 33 — 24 slots too far.
  3. Write on line 8: tokens_cnts[num_experts × (threadIdx.x+1) + i] with threadIdx.x = 31, num_experts = 8 → index = 8×32 + i = 256+i, landing past the shared-memory buffer sized for a 9-expert model.
  4. Result: cuKLEE reports the concrete trigger threadIdx.x = 31, num_experts = 8 — an out-of-bounds shared-memory write.
🌱
The bug only appears when num_experts < 32 — smaller MoE configurations, invisible if you only ever test the large ones.

④ Does the bug actually fit on the GPU?

For example ①, the solver returns batch=116, sequence=18,079. Is that combination physically reachable on a target GPU?

  1. Estimate weights + KV-cache for the model at 2,097,164 tokens; M2K computes a total of ≈211.2 GB (vLLM's 1.25× fragmentation factor included).
  2. Target: NVIDIA B300, 288 GB. 211.2 GB < 288 GB → fits, bug confirmed triggerable.
  3. Contrast: on an H100 (80 GB), the same estimate would exceed capacity — M2K would mark this specific (batch, seq) pair untriggerable there, even though the underlying kernel flaw is identical.
  4. System-wide pattern: across the whole benchmark, out-of-bounds bugs plateau once GPU memory passes ~80 GB, while integer-overflow counts keep climbing with more memory (68 on H100, 119 on H200, 162 on B300) — bigger GPUs simply let batch×sequence reach further into overflow territory.
🍯
Insight: the same kernel bug can be "real but not yet reachable" on one GPU and fully triggerable on the next generation — memory capacity, not just kernel code, decides which overflows become live bugs.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A kernel passes all of vLLM's unit tests (batch ≤ 5, sequence ≤ 17). Why doesn't that rule out the bug in Worked Example ①?
Show answer
Unit tests exercise at most 5×17=85 tokens — nowhere near the 2,097,151-token cap. The bug only exists at production-scale combinations that ordinary testing never reaches, which is exactly why M2K needs symbolic reasoning over the input space rather than a handful of concrete test cases.Misconception: that passing unit tests means a kernel is safe. Passing tests only means it's safe for the inputs those tests happened to pick.
Problem 2 · medium
A kernel has the same 2²¹−1 = 2,097,151-token cap. If batch size is fixed at 200, what is the largest safe sequence length?
Show answer
2,097,151 ÷ 200 = 10,485.755 → the largest safe integer sequence length is 10,485 (10,486 would give 2,097,200 tokens, past the cap).Misconception: rounding up instead of down. Since exceeding the cap is what causes the bug, you must floor the division, not round to the nearest integer.
Problem 3 · medium
Why can't cuKLEE just use KLEE's ordinary single-contiguous-heap memory model for tensors?
Show answer
Tensor sizes are runtime-determined, so in a contiguous heap a symbolically-sized tensor forces every subsequently-allocated tensor's base address to become symbolic too — bounds checks then require reasoning about relationships between many symbolic addresses at once, which explodes. Giving each tensor its own separate, far-apart region keeps every pointer's owning tensor unambiguous regardless of any tensor's size.Misconception: that dynamic shapes are just "bigger" versions of the static-size case KLEE already handles. The problem isn't size, it's that symbolic size makes downstream addresses symbolic.
Problem 4 · hard
Disabling HFProbe (running cuKLEE directly on kernel wrappers) produces 2,349 false positives on the vLLM benchmark. Why so many, rather than just a handful more?
Show answer
Without HFProbe's constraints, every tensor's shape and value range becomes fully symbolic, so the solver is free to pick shapes that are logically possible but never occur in practice — e.g. a scale tensor with zero elements, or a hidden size of 2,147,483,640. Nearly every risky operation then has some unrealistic satisfying assignment, so false positives scale with the number of checked operations, not just a few edge cases. It also makes analysis slower (2.1× per kernel) and causes 18 more kernels to time out.Misconception: that more freedom for the solver only adds a few extra "weird" reports. Unconstrained inputs make nearly every bounds check satisfiable by some unrealistic value, multiplying false positives broadly.
Problem 5 · medium
Why does cuKLEE need a separate GPU-memory usage model instead of just trusting whatever (batch, sequence) the solver returns?
Show answer
The solver only proves that a batch/sequence pair satisfies the memory-safety constraint mathematically — it has no notion of physical GPU capacity. A pair that overflows an index might also require far more VRAM (model weights + KV-cache) than any real GPU has, making the "bug" undeployable. The memory model (weights + 2·L·TC·H·sizeof(dtype), scaled by a fragmentation factor) checks feasibility against a target GPU before the bug is reported.Misconception: that a mathematically valid solver output is automatically an actionable bug report. It's actionable only once it's also shown to be reachable on real hardware.
Problem 6 · easy
Disabling cuKLEE — but keeping HFProbe's config mutation and simply running models on real GPUs at batch ≤ 5, sequence ≤ 17 — finds zero bugs. Why?
Show answer
85 tokens is nowhere near the thresholds that trigger these bugs (e.g. 2,097,151-token caps, or exact power-of-two overflows at millions of elements). Dynamic testing only observes what it happens to run; without symbolic reasoning to search the input space, there is no chance of landing on the rare combinations that actually trigger a fault.Misconception: that running the real model on real hardware is inherently more trustworthy than symbolic execution. It's only as good as the inputs you happen to try — and the bugs here live far outside typical test inputs.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is the "model-kernel interface"?▾
The (currently unwritten) set of assumptions a kernel makes about the tensors and sizes it will be called with — e.g. "token count fits in 21 bits," "this tensor always has exactly one element." M2K's contribution is turning that folklore into explicit, checkable symbolic constraints.
Q2Why not just run the model with huge inputs and see what crashes?▾
Many of these bugs don't crash — they silently corrupt results (Worked Example ②), so dynamic testing wouldn't even notice. And the space of (batch, sequence, model architecture) combinations is too large to brute-force; symbolic execution finds the exact triggering input via constraint solving instead of guessing.
Q3How does HFProbe run a model without a GPU?▾
It replaces every registered CUDA kernel's Python binding with a stub that logs the call and returns a correctly-shaped, zero-filled tensor — so the framework's control flow proceeds normally, just without any real GPU computation. Model-loading is also modified to create correctly-shaped weight tensors without reading the actual weight files.
Q4Why model thread IDs symbolically instead of just picking a few representative threads?▾
A few representative threads (like a specific threadIdx.x=0) can miss the exact thread whose index computation overflows. A symbolic thread ID lets the solver search over every possible thread at once and return the specific one that breaks — e.g. threadIdx.x=31 in Worked Example ③.
Q5Why are 162 of 181 bugs "integer overflow" rather than crashes?▾
The paper suspects overflow bugs are under-reported in the wild because an overflowed value used in a computation (not as an index) corrupts results silently rather than crashing — so they never show up as GPU faults, only as bad outputs someone eventually notices, if ever.
Q6How does M2K know a bug is actually reachable, not just solver-satisfiable?▾
Two checks: (1) replay the concrete (batch, sequence) through HFProbe's profiling backend to confirm the framework accepts it and invokes the kernel with matching arguments; (2) estimate GPU memory (weights + KV-cache × fragmentation factor) and confirm it fits the target GPU's capacity.
Q7Does M2K replace tools like NVIDIA Compute Sanitizer?▾
No — they're complementary. Compute Sanitizer and similar dynamic checkers catch bugs at runtime but only for inputs you actually run, at real runtime overhead. M2K statically searches for inputs — grounded in what a model can actually produce — that would trigger a bug, before it ever ships.
Q8What does M2K not handle yet?▾
Triton kernels, NPU kernels, and TensorFlow models are out of scope; some kernels exceed the one-hour analysis budget without full path coverage; and a handful of missed bugs stem from unsupported C++ constructs (e.g. std::map) or cross-GPU data accesses invisible to static analysis.
