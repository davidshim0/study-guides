Linux Memory Stack · A Field Guide

Bigger pages, no code changes — and the bill that sometimes comes due

Your program allocates memory in 4 KB pages. The hardware would translate addresses far faster in 2 MB chunks. Transparent Huge Pages is the kernel quietly upgrading you to the big chunks behind your back — a real speedup, and occasionally a real tax.

1The TLB, and why it's the whole reason huge pages exist▾

Every virtual→physical translation would be a multi-step memory walk if the CPU redid it each time. So the MMU caches recent translations in the TLB (Translation Lookaside Buffer) — a tiny, very fast associative cache of "virtual page → physical frame" entries. A hit is essentially free; a miss triggers a page-table walk.

Here's the catch that makes huge pages matter: a TLB has a fixed, small number of entries (often tens to a couple thousand across levels), and one entry covers exactly one page. With 4 KB pages, one entry maps 4 KB. With a 2 MB page, that same one entry maps 2 MB — 512× more address space per entry.

Now you're ready: "TLB reach" = entries × page size. THP's entire benefit is multiplying your TLB reach by 512 without touching your code.
2Page-walk depth — and how a 2 MB page shortens it▾

On x86-64 with 4-level paging, a 4 KB translation walks four tables: PML4 → PDPT → PD → PT, then reads the 4 KB frame. Each level is a memory access (though the MMU has its own "page-walk caches" for upper levels).

A 2 MB huge page stops one level early: the Page-Directory (PD/PMD) entry sets a "page size" bit and points straight at a 2 MB frame — no PT level, no fourth access. A 1 GB page stops at the PDPT (PUD) level. Fewer levels = cheaper walk and fewer page-table pages to store.

Now you're ready: huge pages help twice — fewer TLB misses, and each surviving miss is a shorter, cheaper walk. THP handles the 2 MB (PMD) size for ordinary memory.
3The exact numbers: 4 KB, 2 MB, 512, order-9▾

On x86-64: base page = 4 KB, PMD huge page = 2 MB, PUD giant page = 1 GB. Because 2 MB ÷ 4 KB = 512, a single 2 MB page occupies the physical space of exactly 512 contiguous base pages, and it must be 2 MB-aligned in both virtual and physical space.

The kernel's buddy allocator hands out physically-contiguous blocks in power-of-two "orders": order-0 = 1 page, order-9 = 512 pages = 2 MB. So "get me a huge page" literally means "get me a free, aligned order-9 block" — which is exactly the thing that gets hard to find on a fragmented system.

Now you're ready: every THP is one aligned order-9 allocation. Half of THP's difficulty is manufacturing those under fragmentation.
4"Transparent" vs hugetlbfs — the fork in the road▾

Linux has two unrelated huge-page systems. hugetlbfs is the explicit one: an admin pre-reserves a fixed pool (vm.nr_hugepages), and the app deliberately asks for it (mmap(MAP_HUGETLB) or a hugetlbfs mount). Reliable, non-swappable, non-transparent — the app knows.

THP is the automatic one: no reservation, no pool, no app changes. The kernel opportunistically backs your ordinary anonymous memory with 2 MB pages and silently falls back to 4 KB when it can't. "Transparent" means invisible to the application.

Now you're ready: this guide is about THP — the invisible, best-effort one. When people say "we use huge pages for our database," they usually mean the explicit hugetlbfs kind instead, and often disable THP. Primer 9 and the FAQ explain why.
5Anonymous vs file-backed memory▾

Anonymous memory has no file behind it — heap (malloc), stacks, MAP_ANONYMOUS regions. When evicted it goes to swap. File-backed memory mirrors a file on disk (mmap'd files, the page cache, program text).

Classic THP targeted anonymous memory (and tmpfs/shmem). That's still its heartland. Later kernels extended huge/large pages to file-backed memory too (the page cache, via "large folios"), but the canonical THP story — and every knob below — is easiest to understand through anonymous memory.

Now you're ready: when this guide says "a region," picture a big anonymous mapping — a heap arena or an mmap'd scratch buffer. That's where THP does its main work.
6The page-fault path (where a huge page can be born)▾

Freshly allocated anonymous memory isn't physically present yet — mmap just reserves virtual address space. Physical frames are attached lazily, on the first touch: the CPU raises a page fault, the kernel grabs a free frame, wires up the page table, and returns.

THP hooks exactly here. When a fault lands in an eligible, 2 MB-aligned region and a free order-9 block is available, the kernel can install one 2 MB page in a single fault instead of 512 separate 4 KB faults — cheaper up front, and huge from birth.

Now you're ready: one of THP's two creation paths is "at fault time." The other (primer 8) fixes up memory that was already faulted in as 4 KB.
7Memory compaction & fragmentation▾

After a system runs a while, free memory is plentiful but scattered — a page free here, a page free there. Plenty of total free space, yet no contiguous, aligned 2 MB run. That's external fragmentation, and it's THP's natural enemy.

The fix is compaction: the kernel migrates movable pages to pack them together, opening up contiguous 2 MB holes. It runs in the background (kcompactd) and, when desperate, synchronously at allocation time — which is where a fault can stall (primer 9).

Now you're ready: "can I get a huge page?" often becomes "how hard should I compact to make one?" — a knob called defrag that trades latency for hit rate.
8khugepaged — the background collapse daemon▾

Lots of memory is already sitting there as 512 scattered 4 KB pages by the time it'd benefit from being huge. So Linux runs a kernel thread, khugepaged, that slowly scans eligible regions, and where it finds 512 contiguous 4 KB pages covering an aligned 2 MB range, it collapses them: allocates a fresh 2 MB page, copies the data in, and swaps the page-table mapping over to the single huge entry.

It's deliberately lazy (a few thousand pages scanned per pass, with sleeps between) so it doesn't hog CPU — the cost is that promotion is gradual, not instant.

Now you're ready: THP has two makers — the fault path (instant, at first touch) and khugepaged (background, after the fact). A tunable called max_ptes_none decides how empty a range khugepaged will still collapse — the source of THP's infamous memory bloat.
9Why huge pages can hurt — the three taxes▾

THP isn't free money, which is why it's genuinely controversial. Three costs recur: (1) Latency stalls — a fault that triggers synchronous compaction/reclaim to find an order-9 block can block the thread for milliseconds, wrecking tail latency. (2) Memory bloat — promoting a sparsely-used region to 2 MB makes the kernel back all 512 slots, wasting RAM on pages you never touched. (3) Splitting — many operations (a partial munmap, mprotect on a sub-range, swapping, migration) force a huge page back into 512 base pages, undoing the win and costing work.

Now you're ready: this is why databases like MongoDB, Redis, and Oracle often tell you to turn THP off, and why most distros shifted the default from always to madvise. The rest of the guide is really about when the gift outweighs the tax.
The whole story in one place

THP in a nutshell

The problem it solves, the two ways it makes a huge page, and the tax that makes it a judgment call rather than an obvious win.

Big working sets thrash the TLB. A program roaming over gigabytes with 4 KB pages needs one TLB entry per 4 KB, so its translations spill out of the TLB and every few accesses pays a page-table walk. The hardware already supports a fix — 2 MB pages, which cover 512× more per TLB entry and skip a page-walk level — but classically you had to rewrite your program to request them (hugetlbfs), pre-reserve a pool, and give up swapping.

Transparent Huge Pages (THP) removes the rewrite. The kernel backs ordinary anonymous memory with 2 MB pages automatically, by two routes: at page-fault time, when a first-touch in an aligned region can grab a contiguous 2 MB block outright; and in the background via khugepaged, which scans already-faulted memory and collapses runs of 512 base pages into one huge page. If no huge page is available, it silently uses 4 KB — best-effort, never fatal.

The catch is that a 2 MB page is an all-or-nothing unit. To place one the kernel needs a contiguous, aligned, order-9 block, and manufacturing that on a fragmented system means compaction — which can stall the faulting thread. And once placed, the page is backed whole: touch 8 KB of a 2 MB region and you may still pay for all 2 MB (bloat). Many ordinary operations then split it back to 4 KB, erasing the benefit.

The upshot: for dense, long-lived, big allocations — scientific kernels, JVM/allocator arenas, big in-memory analytics — THP is close to free speed (often single-digit to ~20% on TLB-bound codes). For latency-sensitive services with sparse or short-lived allocations, the taxes can dominate, so operators reach for madvise mode or disable it. THP is a default-on heuristic you should know how to steer, not a switch you set once and forget.

🍯 Key takeaways

  • The benefit is TLB reach × 512 plus a shorter page-walk — biggest for large, TLB-bound working sets.
  • "Transparent" = no application changes; contrast hugetlbfs, which needs a reserved pool and explicit calls.
  • Two creation paths: fault-time allocation (instant, on first touch) and khugepaged (background collapse of 512 base pages).
  • Every THP is one aligned order-9 (2 MB) block; getting one under fragmentation means compaction, which can stall.
  • Three taxes: latency stalls, RSS bloat (whole-page backing), and splitting back to 4 KB.
  • Steer it with two knobs: enabled = always|madvise|never and defrag = how hard to work for a page.
  • madvise mode + MADV_HUGEPAGE lets an app opt specific regions in — the modern middle path.
Six everyday pictures

How to think about THP

Each picture stands alone — read in any order. Every card ends with an honest note about where the analogy stops being true.

The core win · TLB reach

Shipping-container labels

Your customs clerk (the TLB) can hold only 64 shipping manifests in memory. Ship your goods in thousands of tiny 4 KB boxes and the clerk forgets old manifests constantly, re-checking paperwork all day. Ship the same goods in a few giant 2 MB containers — one manifest each — and 64 manifests now cover the whole shipment. Same clerk, same desk, 512× the coverage.

Where it breaks: a manifest is free to make; a real 2 MB container needs 512 aligned, contiguous slots in the yard — and if the yard is fragmented, someone has to shuffle boxes first (compaction).
The bottleneck · Compaction

Reserving a whole conference row

You need 512 adjacent seats for one group. The hall has 512 seats free — but scattered as singles all over. To seat the group together, an usher must ask dozens of strangers to shuffle down (migrate pages) until a solid block opens. Do it quietly between sessions (kcompactd) and nobody minds; do it while the group waits at the door (synchronous compaction at fault time) and they stand there for an awkwardly long time.

Where it breaks: some seats are bolted down — kernel allocations that can't be migrated (unmovable pages) — so a hall can be "full of holes" that no amount of ushering will consolidate.
The tax · Memory bloat

The family-size pizza for one slice

You wanted one slice, but the only size on offer is the family pizza. THP is all-or-nothing at 2 MB: back a region and the kernel commits the whole 2 MB even if the program only ever touches 8 KB of it. For a dense array that's perfect; for a sparse, barely-used mapping it's 250× the RAM you needed, silently inflating your RSS.

Where it breaks: you're not charged until khugepaged decides to collapse, and the max_ptes_none knob controls how empty a region it'll still "upsize" — so the waste is tunable, not fixed.
The tax · Splitting

Un-pouring the concrete

Pouring 512 pebbles into one solid slab is fast and strong — until you need to change just one pebble. You can't edit a slab in place; you jackhammer it back into pebbles first. A huge page is a slab: mprotect on a sub-range, a partial munmap, migration, or swapping forces the kernel to split it back into 512 base pages before it can act — real work, and the TLB win evaporates.

Where it breaks: the concrete never re-pours itself, but memory can — after a split, khugepaged may later re-collapse the same range, so a churny workload can thrash between slab and pebbles.
The maker · khugepaged

The night-shift librarian

Readers leave books wherever (4 KB pages land scattered as programs run). A quiet librarian walks the stacks each night, and whenever a full shelf's worth of related books sits together, re-binds them into one big volume (collapses 512 pages into a 2 MB page). Deliberately slow so patrons never notice — the tidying happens in the gaps.

Where it breaks: a real librarian only re-binds full shelves; khugepaged will re-bind a mostly empty shelf too (padding with blanks) if max_ptes_none lets it — which is the bloat analogy meeting this one.
The two systems · THP vs hugetlbfs

Booked seats vs walk-in

hugetlbfs is a reservation: you book a block of huge pages ahead (the pool), guaranteed to be there, but you had to plan and the seats sit empty if unused. THP is a walk-in: no booking, no plan — the kernel seats you at a big table if one happens to be free, and quietly gives you small tables otherwise. Convenience vs guarantee.

Where it breaks: reserved (hugetlbfs) pages are pinned and never swap; THP pages are ordinary memory that can be split, swapped, and reclaimed — so "walk-in" also means "can be re-seated at any time."
Section by section

How THP actually works

First principles → the fault-path birth → khugepaged collapse → the knobs that steer it → how a page dies (split & swap). Numbers are x86-64 unless noted.

1 · First principles: what problem, precisely

Address translation is on the critical path of every memory access. The TLB hides its cost — but only for addresses whose translations it currently holds. Define TLB reach = (number of entries) × (page size). When a program's hot working set exceeds its TLB reach, translations churn and each miss injects a page-table walk into the access latency. For a 4 KB-paged program with, say, 1500 total TLB entries, reach is ~6 MB; a 2 GB analytics scan blows past that by 300×.

Two independent levers shrink the pain: cover more per entry (bigger pages → 512× reach), and make each miss cheaper (bigger pages → one fewer page-walk level, and far fewer page-table pages to cache). Huge pages pull both. THP's job is to pull them without the application asking — for the common case of anonymous memory — and to fail gracefully to 4 KB when it can't.

◆
The governing tradeoff (memorize this). Benefit ≈ (TLB misses avoided × walk cost) + (smaller page tables). Cost ≈ (compaction/reclaim stalls to obtain an order-9 block) + (RAM wasted backing untouched sub-pages) + (split/rebuild churn). THP wins when the region is large, densely touched, long-lived, and alignment-friendly. It loses when it's sparse, short-lived, or latency-critical.

2 · Birth path A — the page fault

New anonymous memory is virtual-only until first touch. On the fault for an address inside an eligible, 2 MB-aligned VMA, the THP fault handler asks the buddy allocator for an aligned order-9 (2 MB) block. If one is available (or the defrag policy says it's worth compacting/reclaiming to make one), the kernel installs a single PMD entry with the page-size bit set — one 2 MB page mapped in one fault. If not, it falls back to a normal 4 KB page and moves on. No error either way; the only observable difference is speed and RSS.

3 · Birth path B — khugepaged collapse

Much memory is already resident as scattered 4 KB pages before it'd benefit from being huge — memory allocated under pressure, or before enough of the region was touched. The khugepaged kernel thread fixes this after the fact. Each pass it scans a bounded number of pages (default pages_to_scan = 4096) across eligible VMAs, sleeping scan_sleep_millisecs (default 10 s) between passes so it stays cheap. When it finds an aligned 2 MB range whose 4 KB pages qualify, it collapses them:

  1. Allocate a fresh, aligned 2 MB page (order-9) — compacting first if needed.
  2. Copy the contents of the (up to) 512 base pages into it; zero-fill any that were never populated.
  3. Take the page-table locks, swap the 512 PTEs for one PMD huge entry, and flush the old TLB entries.
  4. Free the 512 old base pages back to the buddy allocator.

The knob that makes khugepaged famous is max_ptes_none: of the 512 slots, how many may be empty (never faulted) and khugepaged will still collapse the range, zero-filling the rest. The historical default is 511 — meaning even a range with a single touched page can be promoted to a full 2 MB, materializing ~2 MB of RAM for ~4 KB of real data. That's the RSS-bloat mechanism in one number. Lower it (toward 0) and khugepaged only collapses dense ranges. (Related caps: max_ptes_swap, max_ptes_shared.)

▲
The bloat trap, concretely. With enabled=always and max_ptes_none=511, an allocator that mmaps big arenas but sparsely populates them can see RSS balloon 2–10× as khugepaged upsizes half-empty ranges. This is the exact failure mode behind "we turned THP off and memory usage dropped." Try the explorer in Worked Examples to feel it.

4 · The knobs that steer it

Two system-wide policies do most of the work, both under /sys/kernel/mm/transparent_hugepage/:

knobvalueswhat it decides
enabledalways · madvise · neverWho gets THP: everyone eligible (always), only regions marked MADV_HUGEPAGE (madvise), or no one (never).
defragalways · defer · defer+madvise · madvise · neverHow hard to work at fault time to obtain a page: from "stall and compact synchronously" (always) to "never stall — take 4 KB now, let khugepaged upgrade later" (defer).
khugepaged/max_ptes_none0 … 511How empty a range background-collapse will still promote — the bloat dial.
shmem_enabledalways · within_size · advise · never …Whether tmpfs/shared memory gets THP (separate policy from anonymous).

The application-level lever is madvise(): MADV_HUGEPAGE opts a specific range in (honored in both always and madvise modes); MADV_NOHUGEPAGE opts it out. This is how a service enables THP for its one big arena while leaving everything else on 4 KB — the reason distros moved the default to madvise.

●
The modern default recipe. Many distributions ship enabled=madvise and defrag=defer+madvise: no THP unless an app asks, and even then never a synchronous fault-time stall (khugepaged does the upgrade in the background). This keeps the tail-latency and bloat taxes near zero while still letting deliberate, TLB-bound workloads opt in.

5 · How a huge page dies — splitting & swap

A 2 MB page must be split back into 512 base pages whenever an operation needs 4 KB granularity it can't express on a single PMD entry: mprotect/madvise on a sub-range, a partial munmap, page migration (incl. NUMA balancing), or reclaim. Splitting rebuilds the PT level, repopulates 512 PTEs, and flushes TLBs — pure overhead, and the TLB benefit is gone until something re-collapses the range.

Swap is a special case. Historically a THP had to be split before any of it could be written to swap (you swap in 4 KB units). Later kernels added THP swap, which can swap a whole huge page out/in as a unit in favorable cases, avoiding the split. Either way, the lesson holds: huge pages love to stay whole; workloads that constantly re-protect, migrate, or swap sub-ranges fight THP's grain.

◇
Observability, so none of this is guesswork. System-wide: grep -i huge /proc/meminfo (AnonHugePages, ShmemHugePages, FileHugePages). Rates: grep thp_ /proc/vmstat (thp_fault_alloc vs thp_fault_fallback, thp_collapse_alloc, thp_split_page). Per process: the AnonHugePages line in /proc/<pid>/smaps. A high fallback : alloc ratio means fragmentation is starving you of order-9 blocks.
Put real numbers on it

Worked examples

Three calculations you can redo by hand, then an interactive widget for the bloat/collapse tradeoff. All arithmetic is shown; page-size ratios are exact for x86-64, latencies are illustrative.

Example 1 — TLB reach and the miss cliff

A data-TLB with 64 entries; working set 100 MB, touched roughly uniformly.

  1. Reach at 4 KB: 64 × 4 KB = 256 KB. Working set / reach = 100 MB / 256 KB ≈ 400× over. The set can't be held; the TLB miss rate is essentially "constant" for the roaming accesses.
  2. Reach at 2 MB: 64 × 2 MB = 128 MB > 100 MB. The entire working set's translations now fit in the TLB — steady-state TLB misses for translation drop toward zero.
  3. Cost of the misses avoided: suppose 20% of instructions are memory ops and, at 4 KB, ~5% of those miss the TLB at ~100 cycles a walk. Per instruction that's 0.20 × 0.05 × 100 = 1.0 extra cycle/instruction — often a 15–40% slowdown on a memory-bound loop. THP reclaims most of it for free.
◆
Takeaway: the benefit isn't linear — it's a cliff. THP helps enormously exactly when the working set crosses from "fits in TLB reach" to "doesn't," and barely at all when you were already inside reach.

Example 2 — the cost of a synchronous-compaction stall

Fragmented host, enabled=always, defrag=always. A latency-sensitive thread faults into a fresh region.

  1. No aligned order-9 block is free, so the fault triggers direct compaction: migrate movable pages to open a 2 MB hole.
  2. Say compaction migrates a few thousand pages before it succeeds — call it 2 ms of work, all charged to this faulting thread, synchronously.
  3. A request that should have taken 500 µs now takes 2.5 ms — a 5× tail-latency spike, on a request that did nothing wrong except fault at the wrong moment.
  4. The fix: defrag=defer (or defer+madvise). The fault takes a 4 KB page immediately (no stall); khugepaged compacts and upgrades to 2 MB later, off the request path.
▲
Misconception it kills: "THP is a throughput feature, so it can't hurt latency." The allocation of a huge page is exactly where latency is spent. Throughput-oriented batch jobs tolerate it; p99-sensitive services must move that work off the fault path.

Example 3 — RSS bloat from max_ptes_none

A program mmaps a 2 MB-aligned arena and touches only the first 16 KB (4 base pages of 512). enabled=always.

  1. Without collapse: RSS for the region = 4 × 4 KB = 16 KB — you pay for what you touched.
  2. khugepaged with max_ptes_none=511: 512 − 4 = 508 empty slots ≤ 511, so it collapses anyway, zero-filling. RSS jumps to 2 MB — a 128× inflation for this region.
  3. With max_ptes_none=64: 508 empty > 64, so it declines to collapse. RSS stays at 16 KB. Dense regions still get promoted; sparse ones don't.

Check yourself

Practice

Work the answer before opening it. Each answer ends with the misconception the question is designed to catch.

Warm-up
On x86-64, how many 4 KB base pages does one 2 MB THP replace, and what buddy-allocator order is that?
Show answer
2 MB ÷ 4 KB = 512 base pages, which is 2⁹, so it's an order-9 allocation — and it must be 2 MB-aligned. Catches: thinking "huge page" is just "a bigger malloc." It's a specific aligned, contiguous, power-of-two physical block — that constraint is why fragmentation can deny you one.
Diagnose
A service on enabled=always, defrag=always shows fine median latency but a p99 that spikes to milliseconds under memory pressure. What's the likely cause, and which single knob change most directly helps?
Show answer
Faults are triggering synchronous direct compaction to find order-9 blocks, stalling individual requests. Switch defrag to defer (or defer+madvise): faults take 4 KB immediately and khugepaged upgrades later, off the request path. (Or drop enabled to madvise.) Catches: blaming the huge page itself. The page is fine; the cost of obtaining it on the critical path is the problem — move that work to the background.
Diagnose
After enabling THP always, a Redis-like server's RSS grows far beyond the data it stores, even though it isn't leaking. Why, and what are two ways to fix it?
Show answer
khugepaged is collapsing sparsely-touched aligned ranges into full 2 MB pages (default max_ptes_none=511 promotes almost anything), zero-filling the untouched slots — so RSS reflects backed pages, not live data. Fixes: (1) set enabled=madvise (or never) so the allocator's sparse arenas aren't auto-promoted; (2) lower max_ptes_none so only dense ranges collapse. Many such databases simply recommend disabling THP. Catches: assuming RSS growth means a memory leak. Here it's backing amplification — real data is small; the kernel materialized the rest.
Design
You have an HPC kernel that mmaps a 4 GB array, fills it once, and streams over it for minutes. You want THP's benefit with zero tail-latency risk to other threads and no bloat. Sketch a configuration.
Show answer
Keep the system default conservative (enabled=madvise, defrag=defer+madvise) so nothing else is affected. In the code, madvise(arr, 4 GB, MADV_HUGEPAGE) on the array, then pre-fault it densely up front (touch every 2 MB, or use MAP_POPULATE) so promotion happens during init, not during the timed loop. Because the array is dense and long-lived, there's no bloat and no sparse-collapse; because defrag is deferred, no other thread eats a synchronous compaction stall. Catches: reaching for enabled=always system-wide to help one array. Scope the intent with madvise; don't tax every process for one workload's benefit.
Design
Explain why a workload that frequently calls mprotect on 4 KB sub-ranges of a large mapping may see worse performance with THP than without, even though its working set is TLB-bound.
Show answer
Each mprotect on a sub-range of a 2 MB page forces a split back into 512 base pages (rebuild the PT level, repopulate PTEs, flush TLBs). khugepaged may then re-collapse the range, only to be split again on the next mprotect — a split/collapse thrash that burns CPU and keeps the region churning between grains, so the TLB win rarely materializes. Net cost can exceed the 4 KB baseline. Catches: assuming "TLB-bound ⇒ THP always wins." Access pattern to the mapping (fine-grained protection/migration churn) can dominate the reach benefit.
Loose ends

Frequently asked

The questions that come up once the mechanism clicks.

QIs THP the same as the huge pages my DBA reserves?▾
No — different systems. Reserved huge pages are hugetlbfs: a pre-allocated, pinned, non-swappable pool the app explicitly requests (MAP_HUGETLB/vm.nr_hugepages). THP is automatic, best-effort, swappable, and needs no app changes. Many databases use hugetlbfs for their buffer pool and disable THP to avoid its stalls/bloat — the two coexist but solve the problem differently (guarantee vs convenience).
QHow do I check whether THP is even doing anything?▾
Policy: cat /sys/kernel/mm/transparent_hugepage/enabled (the bracketed value is active). Usage: grep AnonHugePages /proc/meminfo for the system, or the AnonHugePages line in /proc/<pid>/smaps for one process. Health: grep thp_ /proc/vmstat — a large thp_fault_fallback relative to thp_fault_alloc means you're asking for huge pages but fragmentation keeps denying them.
QWhy did my distro default to madvise instead of always?▾
Because always applies THP to every process — including latency-sensitive services and sparse allocators that suffer the stall and bloat taxes. madvise flips it to opt-in: only regions the app marks with MADV_HUGEPAGE get promoted, so a deliberate workload gets the benefit while everything else stays on safe 4 KB pages.
QDoes THP work on file-backed memory and shared memory, or only anonymous?▾
Classic THP is anonymous-first. tmpfs/shmem has its own policy (shmem_enabled). File-backed huge/large pages (page cache) arrived later — read-only executable text first, then, in modern kernels, general "large folios" for the page cache. Conceptual / recent: the file-backed and sub-2 MB ("mTHP") story is version-sensitive — verify against your kernel's docs. Everything else in this guide is stated for anonymous memory.
QWhat is "mTHP" / multi-size THP?▾
Recent (2024–2025), conceptual — confirm for your kernel. Newer kernels can back anonymous memory with sizes between 4 KB and 2 MB (e.g. 16 KB, 64 KB), enabled per-size under .../hugepages-<size>kB/enabled. The idea: capture much of the TLB benefit with far less bloat and far easier allocation (smaller contiguous blocks are easy to find), and it maps naturally onto Arm's contiguous-PTE hints. It's an evolution of THP, not a replacement.
QDoes THP change how much memory my page tables use?▾
Yes, downward. A 2 MB region mapped by one PMD entry needs no PT page at all; mapped by 4 KB pages it needs a full 512-entry PT page (4 KB) plus the walk that reaches it. Across a large working set that's a meaningful reduction in page-table footprint — and fewer page-table pages also means the MMU's page-walk caches stay warmer.
QIf THP can hurt, why is it on by default at all?▾
Because for the common case — general-purpose workloads with reasonably dense, longer-lived allocations on a not-too-fragmented system — it's a quiet, free win, and requiring every developer to hand-tune huge pages would leave that performance on the table. The defaults have steadily grown more conservative (madvise, deferred defrag) precisely to keep the benefit while shrinking the worst-case tax.

Core terms
THPTransparent Huge Pages — the kernel automatically backing ordinary (esp. anonymous) memory with 2 MB pages, invisibly to the app.
TLB reachEntries × page size — the total address space the TLB can translate without a walk. THP's benefit is multiplying this by 512.
PMD huge pageA 2 MB page mapped by a single Page-Directory entry with the page-size bit set; the size THP works in on x86-64.
order-9 block2⁹ = 512 contiguous, aligned base pages = 2 MB — exactly what the buddy allocator must hand out for one THP.
khugepagedBackground kernel thread that scans memory and collapses runs of 512 base pages into huge pages after the fact.
collapsekhugepaged's core op: allocate a 2 MB page, copy in (and zero-fill) the 512 base pages, swap 512 PTEs for one PMD entry.
splitThe reverse: break a 2 MB page back into 512 base pages so a 4 KB-granular op (mprotect, partial munmap, migration, swap) can proceed.
compactionMigrating movable pages to create contiguous, aligned free blocks; background (kcompactd) or synchronous (direct) at fault time.
Supporting terms
enabledPolicy knob: always / madvise / never — who is eligible for THP.
defragPolicy knob: how hard to work (compact/reclaim) at fault time to obtain a huge page — the latency dial.
max_ptes_noneHow many of the 512 slots may be empty and khugepaged still collapses (default 511) — the bloat dial.
MADV_HUGEPAGEmadvise() flag opting one range into THP; MADV_NOHUGEPAGE opts out.
hugetlbfsThe other huge-page system: explicit, reserved, pinned, non-swappable pool — not THP.
RSS bloatRSS inflation from backing a whole 2 MB page for a sparsely-touched region.
mTHPMulti-size THP: anonymous pages between 4 KB and 2 MB (recent; version-sensitive).
AnonHugePagesThe /proc/meminfo and smaps field reporting anonymous memory currently backed by THP.

📌 Summary card · as of 2026-08-13 · Linux ~v6.x

  • What: kernel backs anonymous (and, increasingly, file/shmem) memory with 2 MB pages automatically — no app changes.
  • Why: TLB reach ×512 + one fewer page-walk level + smaller page tables → fewer, cheaper translation stalls.
  • Two makers: fault-time allocation (instant, first touch) and khugepaged (background collapse of 512 base pages).
  • The bottleneck: every THP is one aligned order-9 block; under fragmentation you need compaction to make one.
  • Three taxes: synchronous-compaction latency stalls, whole-page-backing RSS bloat, and split churn on 4 KB-granular ops.
  • Steer with: enabled (always/madvise/never), defrag (…/defer/…), max_ptes_none, and madvise(MADV_HUGEPAGE).
  • Modern default: madvise + deferred defrag — opt-in benefit, near-zero worst-case tax.
  • Sweet spot: large, dense, long-lived, alignment-friendly allocations. Anti-pattern: sparse, short-lived, latency-critical, or churny (mprotect/migrate) mappings.
  • Not the same as hugetlbfs (reserved/pinned/explicit) — and databases often use that and disable THP.
  • Diagnose with: /proc/meminfo AnonHugePages, /proc/vmstat thp_* counters, /proc/<pid>/smaps.
