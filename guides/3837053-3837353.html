HotStorage '26 · A Field Guide

Sending compaction to where the data already lives, not wherever is idle

Disaggregated LSM key-value stores re-fetch every compaction's input over the network. This is the plain-English story of LARC, a client-side scheduler that reads a cached placement map and routes each compaction to the node that already holds the most of its input objects.

📄 Shin, Choi, Yoo, Lee · Dankook University · HotStorage '26 🎓 Some LSM/Ceph background assumed — primers cover it ⏱ ~25 min read
🗺️

Route each compaction to the worker that ALREADY HOLDS the most of its input — not whoever is IDLEST or next in a rotation.
Score placement first, then schedule.

Before you begin

Quick glossary, then seven ideas the paper assumes you know

The acronyms first — scan once, then use them as a lookup while you read. The primers below are collapsed; open whatever's unfamiliar.

LSM-treeLog-Structured Merge tree: writes land in memory, flush to sorted files, periodically merged ("compacted") to bound read cost.
SSTSorted String Table — an immutable sorted file holding a range of keys; compaction merges SSTs across levels.
OSDObject Storage Daemon — a Ceph process that owns a disk and serves reads/writes for the objects placed on it.
RADOS objectCeph's fixed-size storage unit (4 MB here); CephFS files are striped across many RADOS objects.
CRUSHCeph's placement algorithm: a deterministic hash-based function mapping an object to its OSDs, computable without a lookup table.
NA (local/global)Network amplification — bytes crossing a boundary ÷ user-write bytes. "Local" = compute node's NIC; "global" = whole-cluster traffic.
WAWrite amplification — total bytes an LSM-tree writes (across all compactions) per byte the user wrote.
ρ (rho)Remote-fetch ratio: the fraction of a compaction's input a worker must pull over the network, = 1 − locality.
L(W)Locality score — the fraction of a compaction's input objects that worker W can read from its own co-located OSDs.
LARCLocality-Aware Remote Compaction — this paper's prototype: score workers client-side, route to the best-scoring one.
locality-aware worker / LARC network cost (NA, WA) CRUSH / control-plane machinery locality-agnostic baseline (Local / round-robin)
1LSM-trees and why compaction exists▾

Writes to an LSM-tree go to an in-memory buffer, then flush as a small, immutable, sorted file (an SST). Over time this produces many overlapping SSTs, which would make reads slow (you'd have to check every file). Compaction periodically merges overlapping SSTs from adjacent levels into fewer, larger, non-overlapping ones.

Merging the same logical data repeatedly means the tree writes far more bytes to storage than the user ever wrote — that ratio is write amplification (WA), measured here at ≈3.8×.

Now you're ready: every byte compaction touches must be read as input and written as output — in a disaggregated system, both legs cross the network.
2Disaggregated storage — compute and storage on separate boxes▾

Instead of attaching disks directly to a database server, a disaggregated architecture puts data on a separate distributed storage cluster (here, Ceph) reached over the network. This lets compute and storage scale independently — but every I/O that used to be a local disk access is now a network round trip.

If you work on CXL memory pooling: this is the same trade as pooled/tiered memory — decoupling a resource from compute buys elasticity at the cost of making "where is the data relative to where I'm computing" suddenly matter again.

Now you're ready: compaction is the single largest consumer of that network path, since every input SST must be fetched remotely.
3Ceph primitives: OSDs, RADOS objects, CephFS▾

Ceph stores data as fixed-size RADOS objects (4 MB in this paper) spread across OSDs — one daemon per disk, several per node (4 OSDs/node here, 32 OSDs total across 8 nodes). CephFS is the POSIX filesystem layer on top: a file (here, an SST) is just a sequence of RADOS objects.

Each object is replicated to R OSDs (R = 3 here) for fault tolerance — so one SST's bytes are physically smeared across multiple nodes, each node holding only some of them.

Now you're ready: whether a compaction worker can read an SST locally depends entirely on whether that worker's node happens to host one of the R replicas of each object inside it.
4CRUSH — placement without a lookup table▾

Most distributed stores need a central metadata service to answer "where is this block?" Ceph instead uses CRUSH: a deterministic function of the object's name and a small, slowly-changing cluster map. Anyone holding a copy of that map can compute an object's OSD set locally, with no network round trip.

This is what makes LARC cheap: a client can score every candidate worker's locality by running CRUSH itself against a cached map, instead of asking a metadata server where 1,000+ objects live.

Now you're ready: LARC's whole trick is legal only because CRUSH makes placement client-computable — a property not every storage system has.
5Network amplification — local vs. global▾

The paper tracks two ratios of network bytes to user-write bytes. NAlocal counts traffic crossing the compute node's own NIC. NAglobal additionally counts the R-fold replication traffic that happens cluster-wide regardless of which node initiated it.

Both are driven by WA (how much the LSM-tree re-writes) and by ρ, the fraction of a compaction's input that must be fetched remotely — which is exactly the quantity worker placement controls.

Now you're ready: lowering ρ by picking a better worker is the only lever in this model that doesn't require changing the LSM-tree or the replication factor.
6Existing remote-compaction systems — and their blind spot▾

Systems like RocksDB-Cloud, CaaS-LSM, Hailstorm, and Disaggregating RocksDB already move compaction off the primary compute node to relieve its CPU. But they pick the destination worker by round-robin or load — never by where the input data physically sits.

Moving the task doesn't reduce network traffic if the new worker has to fetch almost all the input anyway — it just relocates the same bytes to a different node.

Now you're ready: LARC's contribution is orthogonal to all of these — it answers which worker to pick, not whether to offload compaction at all.
7Why uniform placement doesn't mean uniform locality▾

CRUSH spreads data uniformly across the cluster in aggregate, so every node ends up with its fair R/N share of the cluster's objects overall. But any single compaction touches only a small slice of that population — the paper's 100M-key run spans just 1,091 unique RADOS objects across 137 SSTs, a handful per compaction. A small sample of a globally-uniform population still exhibits sampling skew, the same way one exit poll can lean one way even though the full electorate is balanced.

This is the paper's central empirical finding: skew at the per-task scale survives uniformity at the global scale.

Now you're ready: this is exactly why a per-compaction locality score — not a cluster-wide average — is the right thing to optimize.
The whole story in one place

LARC in a nutshell

The problem, the overlooked signal that fixes it, and how the pieces connect.

In a disaggregated LSM-KVS, every compaction's input SSTs must be fetched over the network, and write amplification multiplies that traffic — the authors measure a local network amplification of 8.72× on their testbed. Systems that offload compaction to remote workers already exist, but they pick the worker by round-robin or load, blind to where the input data physically sits. That leaves network traffic close to the baseline, because the chosen worker still has to fetch almost everything remotely.

The paper's finding: although Ceph's CRUSH placement is uniform in aggregate, any single compaction samples only a small slice of the cluster's objects — small enough that sampling skew gives one node a disproportionate share of that task's input, even though no node is favored globally. Measured across 1,674 compactions, the best-locality node holds 51.1% of a task's input on average, versus a worst-locality node at 24.0% — a persistent 27-point gap, well above the R/N = 37.5% a locality-agnostic scheduler would expect on average.

LARC exploits this: a client-side locality score L(W) — computed by running CRUSH against a cached cluster map, no metadata-server round trip — ranks candidate workers, and the task is routed to argmaxW L(W). A three-tier prototype (compute-side plugin → control-plane Agent → storage-node workers) realizes this in RocksDB v9.10.0.

The payoff: LARC lifts mean per-compaction locality to 51.1%, cuts measured network amplification from 8.72× to 5.86× (−32.8%), and raises fillrandom throughput by 16.1% (up to 27.6% under a write-heavy mixgraph workload) — all from a client-side scheduling decision that adds no new hardware and touches no storage data path.

🧭 Key takeaways

  • Existing remote-compaction systems schedule by load, not placement — a locality-agnostic remote worker still averages ρ≈0.63 from replication alone, so network traffic drops only modestly, far short of placement-aware routing.
  • Global uniform placement hides per-task skew: one node typically holds a disproportionate share of any single compaction's input.
  • L(W) = fraction of a compaction's input objects a worker can read from its own OSDs; LARC routes to the argmax.
  • Scoring runs client-side via a cached CRUSH map — no metadata-server query, O(|D|), under 2 ms.
  • Measured locality (51.1%) beats the analytical R/N expectation (37.5%) by a wide margin.
  • Result: NA 8.72× → 5.86× (−32.8%); throughput +16.1% (fillrandom), up to +27.6% (write-heavy mixgraph).
  • Open problem: LARC controls where compaction reads, not where it writes — output placement is still CRUSH's call.
Six everyday pictures

How to think about LARC

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Locality score

Returning a book to the nearest branch

A library patron needs ten titles. One branch happens to shelve seven of them; another, only two. Sending the request to the branch that already holds the most means fewer inter-branch couriers. LARC does exactly this per compaction: score each candidate worker by what fraction of the input it already holds locally, then route there.

Where it breaks: a library's collection is fixed; a compaction's "collection" (its input SSTs) is freshly assembled from scattered objects at write time — so there's no single branch that was deliberately stocked for this request, only one that happens to hold more by chance.
The mechanism · Client-side CRUSH

A hiker with a downloaded map

One hiker calls the ranger station for directions at every fork; another carries a downloaded map and works out the route herself. The second hiker is faster precisely because the map doesn't need a round trip. CRUSH is that downloaded map: any client holding the cached cluster map computes an object's location by formula, instantly, with no query to a metadata server.

Where it breaks: a paper map never changes; CRUSH's map does (nodes join/leave), so clients must refresh their cached copy periodically — a staleness window the paper doesn't quantify.
The surprise · Sampling skew

An exit poll from one precinct

A country's vote is evenly split 50/50 overall — but ask only the 20 voters leaving one polling place and you might get 14-to-6. Small samples of a uniform population are noisy. A compaction touching roughly a handful of objects (≈8 on average per SST in the paper's run) out of the cluster's much larger population is exactly that small sample: CRUSH's placement is uniform in aggregate, but any one task's input still skews toward whichever node got lucky.

Where it breaks: exit-poll skew is pure noise with no exploitable structure; compaction skew is noise LARC can act on, because the "poll" (the input SST set) is known in advance and the "precinct" (best node) can be computed before scheduling.
Why offloading alone isn't enough · Round-robin / load-based

A delivery dispatched to the next driver in line

A dispatcher sends each package to whichever driver is free next, never checking who's already near the pickup address. The package still gets delivered, but the driver may have to cross town. That's round-robin or least-loaded worker selection: it relieves the origin node's workload, but doesn't by itself target the total distance (network bytes) traveled — which is why prior remote-compaction systems still leave measured NA close to the Local baseline, even as they relieve its CPU.

Where it breaks: a delivery driver can freely reroute mid-trip; a compaction worker's locality is fixed the moment it's assigned — there's no partial credit for "getting closer" after the fact.
The open limitation · Output placement

Packing boxes into whichever storage unit the moving company assigns

You unpacked your old apartment efficiently by working from the nearest boxes. But when you re-pack and the movers choose which storage unit gets your new boxes — independent of which unit you were just working out of — your next trip may have to start across town again. LARC controls which worker reads the input (the "unpacking"), but CRUSH still decides where compaction's output SSTs land, independent of the executing worker.

Where it breaks: you could choose your own storage unit if you asked; CRUSH's placement is deterministic and not (yet) steerable toward "wherever I just computed," which is exactly the paper's stated next step.
The tension ahead · Locality vs. load

Everyone's favorite mechanic happens to be the same one

If the mechanic three blocks away is best-positioned for your car, odds are good she's also best-positioned for your neighbor's, since nearby cars share a neighborhood — i.e., overlapping LSM levels tend to share physical placement. Greedily picking "whoever's closest" for every job in parallel can overload that one mechanic. A real scheduler needs to blend locality with how busy each candidate already is.

Where it breaks: a mechanic can finish one job and move to the next; LARC's current prototype has no load term at all (α·L(W) is the whole score for now) — the paper flags blending in load/bandwidth terms as future work, not something already solved.
The full explanation

How it actually works

The cost model, the measured opportunity, the scoring mechanism, and the architecture that enforces it.

1 · The network cost model

The paper models two amplification ratios. Local amplification — bytes crossing the compute node's own interface relative to user writes:

NA_local ≈ WA·(ρ + 1) + 1   # ρ = remote-fetch ratio; +1 = the initial flush of user writes

and global amplification — adding the R-fold replication traffic that happens cluster-wide regardless of which node compacts:

NA_global ≈ WA·(ρ + R) + R

For the standard Local config (compaction on the compute node), the worker fetches everything it doesn't already hold — but since it's the compute node, not a storage node, ρ = 1 by construction, giving NA_local ≈ 2·WA + 1 ≈ 8.72× as measured.

2 · Measuring the opportunity — locality is skewed per task

On an 8-node, 32-OSD Ceph cluster (R = 3), a 100M-key fillrandom run produces 137 SSTs over 1,091 unique RADOS objects. Sorting each SST's per-node locality from best to worst reveals a steep, consistent gradient — not the flat R/N = 37.5% a uniform model alone would suggest.

3 · The locality score and worker selection

Let D be the set of distinct objects in a compaction's input, OSD(d) the OSDs holding object d, and OSD(W) the OSDs on candidate worker W. LARC's locality score:

L(W) = |{d ∈ D : OSD(d) ∩ OSD(W) ≠ ∅}| / |D|

To compute it, the Agent: (1) lists the RADOS object names behind the input SSTs via CephFS inodes, (2) runs CRUSH against its cached cluster map to find each object's OSD set, (3) intersects with each candidate's OSD(W). This runs entirely client-side — O(|D|), under 2 ms even for |D| ≈ 1,000 — so scoring itself adds negligible latency; the plugin still waits up to a bounded timeout for the Agent's response before falling back. The task goes to W* = argmaxW L(W).

4 · Enforcement pseudocode

# on compaction trigger (compute-node plugin)
task = {input_SSTs, output_level}
send(task) to Agent   # gRPC; falls back to local() on timeout

# Agent (control plane)
D = objects_behind(task.input_SSTs)        # via CephFS inodes
for W in candidate_workers:
    L[W] = crush_intersect(D, OSD(W)) / len(D)  # local, cached map, O(|D|)
Wstar = argmax(L)
dispatch(task, Wstar)

# Worker Wstar
for obj in D:
    if obj.local: read_from_disk(obj)   # bypasses network
    else:       read_over_ceph(obj)
write_output_to_CephFS()
return metadata to Agent

5 · Where it doesn't (yet) reach — scaling and output placement

LARC's score only governs where a compaction reads. Output SSTs are still placed by CRUSH, independent of the executing worker. A Monte Carlo simulation in the paper shows this caps the benefit as clusters grow: the best node's absolute locality falls from 43% at N=8 nodes to just 6% at N=256, because a fixed-size input spreads across an ever-larger pool of candidate nodes with no mechanism pulling output back toward the worker that just computed it.

Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's reported figures.

① Sanity-checking the rank-sorted heatmap

The paper reports mean locality by rank (best→worst across 8 nodes, averaged over 137 SSTs): 65.4, 54.1, 46.9, 40.8, 34.5, 26.8, 20.5, 11.0. Does this stay consistent with the global R/N = 37.5% expectation?

  1. Sorting reorders, it doesn't create or destroy locality. For any one SST, ranking its 8 nodes by share just relabels them. Because each object is replicated R=3 times, a node "has" an object if any of its R copies lands there — so the per-node locality shares summed across all 8 nodes come to R×100% = 300%, not 100%.
  2. Sum the 8 rank-means: 65.4 + 54.1 + 46.9 + 40.8 + 34.5 + 26.8 + 20.5 + 11.0 = 300.0.
  3. Divide by 8 nodes: 300.0 / 8 = 37.5% — exactly R/N for R=3, N=8.
  4. Conclusion: the rank-sorted gradient and the flat global average are the same data viewed two ways — sorting reveals the skew that averaging hides.
🧭
Insight: this is exactly the paper's point. "Globally uniform" and "per-task skewed" are not in tension — they're two statistics of the same distribution.

② Reproducing the NA formulas

Given measured NA_local = 8.72× at the Local baseline (ρ=1), back out WA, then predict NA_global and the locality-agnostic ρ.

  1. Solve for WA: NA_local = WA(ρ+1)+1 with ρ=1 → 8.72 = 2·WA + 1 → WA = 3.86 (paper reports "≈3.8×" — consistent within rounding).
  2. Predict NA_global for Local (R=3, ρ=1): NA_global = WA(ρ+R)+R = 3.8·(1+3)+3 = 15.2+3 = 18.2× — matches the paper's stated value exactly.
  3. Locality-agnostic remote worker: on average it holds L = R/N = 3/8 = 0.375 of any input, so ρ = 1 − 0.375 = 0.625 ≈ 0.63 — matches the paper's stated figure.
  4. Takeaway: even a "dumb" remote worker beats the Local baseline's ρ=1 simply by virtue of replication (R copies exist somewhere); LARC's contribution is pushing ρ further down, to 1−0.511 ≈ 0.49.

③ What LARC actually bought

Table 2 reports fillrandom throughput 13,894 → 16,136 ops/s and total cluster traffic 94.2 GB → 63.3 GB over a 100M-key run. Check the paper's headline percentages.

  1. Throughput gain: (16,136 − 13,894) / 13,894 = 2,242 / 13,894 = 16.1% — matches the abstract.
  2. Traffic saved: 94.2 − 63.3 = 30.9 GB over the run.
  3. As a percentage: 30.9 / 94.2 = 32.8% — matches the stated NA reduction, and is consistent with 8.72× → 5.86× directly: (8.72−5.86)/8.72 = 32.8%.
  4. Per key: 30.9 GB ÷ 100,000,000 keys ≈ 309 bytes of network traffic avoided per key written (using decimal GB) — a tangible per-operation saving from a purely client-side scheduling decision.
🧭
Insight: the 32.8% NA cut and the 16.1% throughput gain are two views of the same mechanism — less network traffic competing for bandwidth means fewer write stalls from delayed MemTable flushes.

④ The compaction-level gap and compaction size

Across 1,674 compactions: best-locality average 51.1% (median 50.0%), worst-locality average 24.0%. How big is the exploitable gap, and does it hold for large compactions?

  1. Gap: 51.1 − 24.0 = 27.1 percentage points (the paper states "27.0," consistent within rounding of the two averages).
  2. Median vs. mean: median (50.0%) sits close to the mean (51.1%), so the distribution isn't dominated by a few extreme outlier compactions — most tasks genuinely have a clear best node.
  3. Small vs. large compactions: under 300 MB, best-locality varies widely (40–60%); above that, it converges to a tighter 45–50% band — still well above the 37.5% analytical floor.
  4. Conclusion: the opportunity shrinks slightly but does not disappear as compactions grow — large compactions have lower relative variance but the absolute bytes saved stay significant.
💡
This is why LARC's prototype needs no special-casing for compaction size — the same argmax rule captures most of the benefit across the whole size range measured.
Test yourself

Practice problems

Try each before opening the answer. Every one flags the misconception it's checking for.

Problem 1 · easy
CRUSH places data uniformly across the cluster. Does that mean a locality-aware scheduler has nothing to exploit?
Show answer
No. Uniformity holds in aggregate across the cluster's whole object population — but a single compaction samples only a small slice of it (the paper's 100M-key run spans 1,091 unique objects across 137 SSTs). That small sample size produces statistical skew: one node ends up holding a disproportionate share of that specific task's input, even though no node is favored across the whole dataset.Misconception: that global uniformity implies per-task uniformity. It's the gap between a population average and a small-sample draw from it — the same reason a fair coin can land heads 7 times out of 10 in a short run.
Problem 2 · medium
Why does moving compaction to a "remote worker" chosen by round-robin not meaningfully reduce network amplification, even though it relieves the compute node's CPU?
Show answer
Relocating a task doesn't relocate the data. A round-robin worker holds, on average, only L=R/N of the task's input locally (37.5% here), so it must fetch the remaining ~63% over the network — almost as much as the compute node itself would have. The compute node's load drops, but total network bytes drop only modestly, since that reduction comes from replication alone rather than any placement awareness — the policy never looked at where the input actually sits.Misconception: that "offloading" and "reducing network traffic" are the same lever. Offloading addresses compute contention; locality-aware routing addresses the network — they're orthogonal (per Table 1), and you need the second one to cut NA by more than replication alone provides.
Problem 3 · medium
Compute the remote-fetch ratio ρ for a worker that LARC scores at L(W) = 0.70, and estimate its NA_local using WA ≈ 3.8.
Show answer
ρ = 1 − L(W) = 1 − 0.70 = 0.30. NA_local ≈ WA·(ρ+1)+1 = 3.8·(1.30)+1 = 4.94+1 = ≈5.94× — well below the Local baseline's 8.72× and below even LARC's measured average-case 51.1%-locality result, since this worker was scored higher than average.Misconception: that locality score and remote-fetch ratio are two different quantities to track. They're complements of the same number: ρ = 1 − L(W), always.
Problem 4 · hard
LARC always routes to argmax L(W). Explain the failure mode the paper's Discussion section raises with this greedy, per-task rule when many compactions run concurrently.
Show answer
Compaction inputs at adjacent LSM levels tend to share physical placement, so the node that maximizes L(W) for one task is often also the best for several other, concurrently-scheduled tasks. Greedily sending every task to its individual best node can pile work onto a single "popular" node, creating a load hotspot — trading a network-locality win for a queuing-delay loss. The paper proposes blending in load and bandwidth terms (α·L(W) + β·(1−load(W)) + γ·(1−bw(W))) as future work, not yet implemented.Misconception: that maximizing a per-task metric in isolation is the same as optimizing the whole system. It's a classic local-optimum-vs-global-optimum trap once tasks compete for the same resource.
Problem 5 · medium
A colleague says "Now that input reads are local, LARC must have eliminated almost all network traffic." What's wrong with that claim?
Show answer
LARC controls where a compaction reads its input, not where it writes its output — CRUSH still places new SSTs independently of the executing worker, and R-fold replication of that output still crosses the network regardless. NA fell by 32.8% (8.72×→5.86×, as reported in Table 2), a substantial but partial reduction — output placement and replication traffic remain untouched, which is exactly the paper's stated open challenge.Misconception: that solving the read-side of the problem solves the whole NA equation. Output placement and R-fold replication traffic are untouched by LARC — and the paper's own analytical NA_global formula would in fact predict a floor well above the measured 5.86×, a discrepancy the paper doesn't fully reconcile (see the Reference tab's source notes).
Problem 6 · hard
The Monte Carlo simulation shows best-node locality falling from 43% at N=8 nodes to 6% at N=256. Why does growing the cluster erode locality, given that R and the input size stay fixed?
Show answer
A compaction's input is a fixed-size set of objects, each replicated to R specific nodes out of N. As N grows, those R replicas are spread across a larger and larger pool of candidate nodes, so the chance that any single node happens to hold a large fraction of the whole input set shrinks — the "sampling skew" that LARC exploits at N=8 becomes less pronounced because there are simply more places for the data to be. Without steering output placement toward the executing worker, growing the cluster works directly against the locality opportunity.Misconception: that locality-aware scheduling scales automatically with cluster size, since the underlying mechanism (CRUSH, client-side scoring) is unchanged. The mechanism scales fine computationally; the *opportunity* it exploits shrinks, which is a statistical fact about fixed R and growing N, not an implementation limitation.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What problem is LARC actually solving?▾
Existing remote-compaction systems decouple compaction execution from the compute node but choose the destination worker by round-robin or load, ignoring where the compaction's input data physically sits. LARC answers a narrower, previously unaddressed question: given that a worker must be chosen, which one minimizes the network bytes that compaction actually has to move?
Q2Isn't data placement uniform in a well-configured Ceph cluster?▾
Yes, in aggregate. But a single compaction touches only a small slice of the cluster's objects — the paper's 100M-key run spans just 1,091 unique RADOS objects across 137 SSTs — and small samples of a uniform population still skew, the same statistical effect behind exit polls. The paper measures this directly: best-node locality per compaction averages 51.1%, far above the 37.5% you'd expect if every node held an equal share of every task.
Q3How does LARC compute locality scores without a metadata-server query?▾
It leverages Ceph's CRUSH algorithm, which deterministically computes an object's OSD placement from its name and a small, cacheable cluster map — no lookup table needed. The Agent keeps a cached copy of this map and runs CRUSH itself, client-side, for every object in a compaction's input. The whole computation is O(|D|) and completes in under 2 ms even for ~1,000-object compactions.
Q4What happens if the Agent is slow or unreachable?▾
The compute-node plugin has a timeout; if the Agent doesn't respond in time, the plugin transparently falls back to running compaction locally on the compute node — the same behavior as the unmodified Local baseline. Scoring itself is fast (under 2 ms) and stays off RocksDB's internal path, but the plugin can still wait up to that timeout before falling back if the Agent is slow or unreachable.
Q5What's the difference between NA_local and NA_global?▾
NA_local counts network bytes crossing the compute node's own interface relative to user writes. NA_global additionally counts the R-fold replication traffic that happens cluster-wide, regardless of which node executes compaction. Both scale with write amplification (WA) and the remote-fetch ratio ρ = 1 − locality.
Q6Does LARC change RocksDB's LSM-tree semantics or compaction algorithm?▾
No. LARC only changes which worker executes a compaction task that RocksDB has already decided to run, via RocksDB's existing CompactionService interface. Merge logic, level structure, and write amplification are untouched — the paper calls out that it's orthogonal to work on tuning LSM structure or compaction timing.
Q7Does LARC generalize beyond Ceph?▾
It needs a system where a candidate worker's data placement is determinable without a network round trip on the scheduling path. That includes client-side deterministic systems like Ceph/CRUSH or OpenStack Swift's Ring, and metadata-server-query systems like HDFS, Ozone, or Lustre (with one extra lightweight call). Fully-abstracted object stores like S3-compatible systems expose neither interface and are out of scope.
Q8Why does LARC's benefit shrink as the cluster grows?▾
LARC only controls where compaction reads, not where its output is written — CRUSH places outputs independently of the executing worker. As cluster size N grows with replication factor R fixed, a compaction's fixed-size input spreads across more candidate nodes, so the best single node holds a shrinking share. A Monte Carlo simulation shows best-node locality falling from 43% at N=8 to 6% at N=256.
Q9Is this evaluation production-scale?▾
No — the authors call it preliminary: an 8-node, 32-OSD testbed, a single 100M-key fillrandom trace for the detailed measurements, plus a mixgraph sweep over read/write ratio. The paper is explicit that validating gains on broader, production-representative workloads remains future work.
Q10How is LARC different from accelerator-based compaction offload (D2Comp, DComp) or RDMA-based disaggregation (dLSM, Nova-LSM)?▾
Those systems require specialized hardware (DPUs, FPGAs, or RDMA-capable NICs) and, per Table 1, have no explicit worker-selection policy at all. LARC targets commodity hardware and storage-node execution, and its entire contribution is the worker-selection policy itself — it's a software scheduling layer, not an accelerator.

Remote-fetch ratio ρThe complement of locality: ρ = 1 − L(W), the fraction of input a worker must pull over the network.
NA_local / NA_globalNetwork amplification measured at the compute node's interface vs. cluster-wide including replication traffic.
WA (write amplification)Total LSM-tree bytes written per byte the user wrote; measured ≈3.8× in this testbed.
CRUSHCeph's deterministic, client-computable data-placement algorithm — the mechanism that lets LARC score locality without a metadata-server query.
Agent / Plugin / WorkerLARC's three components: a compute-side RocksDB shim, a control-plane scorer/dispatcher, and storage-node compaction executors.
Supporting terms
LSM-tree / SST / CompactionThe write-optimized storage structure, its sorted-file unit, and the background merge that bounds read amplification.
Disaggregated storageArchitecture decoupling compute from storage over a network, enabling independent scaling at the cost of network-bound I/O.
OSD / RADOS object / CephFSCeph's per-disk daemon, its fixed-size (4 MB here) storage unit, and the POSIX filesystem layered on top.
Replication factor RNumber of copies Ceph keeps per object (R=3 here); sets the analytical locality-agnostic baseline R/N.
fillrandom / mixgraphdb_bench workloads: a pure-write microbenchmark, and a Facebook-trace-derived mixed read/write workload used to vary write pressure.
Results at a glance
Source notes — what's the paper vs. what's framing

From the paper, verbatim or directly computed: all numbers (8.72×, 51.1%, 37.5%, 94.2/63.3 GB, 13,894/16,136 ops/s, 7,838/10,005 ops/s, 1,674 compactions, 137 SSTs, 1,091 objects, 43%→6% at N=8→256, Table 1's system comparison), the locality-score formula, the NA_local/NA_global formulas, and the three-tier architecture description.

Original framing, not in the paper: the library/hiker/exit-poll/mechanic analogies, the CXL/tiered-memory comparisons in the primers, the "schematic" best-vs-worst locality curve shapes in the signature figure (matched to reported means/medians, not the exact per-compaction trace), and the interactive NA-formula explorer's illustrative WA-fixed extrapolation at L=100% and L=70%.

A caveat we flag rather than resolve: the paper's own text calls the Table 2 NA reduction (8.72×→5.86×) a reduction in "NA_global," but 5.86× is far below the NA_global formula's own prediction (≈16–18× range) and much closer to the NA_local formula's prediction at similar locality (~6.7×, Worked Example / interactive). We present both the paper's stated labels and this apparent inconsistency rather than silently reconciling it.

The storage substrate (OSDs, RADOS, CephFS) that LARC's testbed and locality measurements are built on.
