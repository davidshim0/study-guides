HotStorage 2026 · A Field Guide

Giving metadata to neither the CPU nor the GPU

A CPU and a GPU share one file. Whoever's turn it is to own the metadata becomes a bottleneck for the other. DevMeta's fix: put the file system inside the SSD and make both processors equal, stateless clients.

📄 "Bridging CPU and GPU I/O with a Device-Resident File System" · Chen, Chen, Ren, Zhang 🎓 Storage/GPU-I/O specifics explained; OS/arch background assumed ⏱ ~20 min read
🗂️

Keep exactly ONE authoritative copy of file metadata — on the device — so CPU and GPU never need to synchronize with each other.
Move the controller off both endpoints, onto the thing they already share.

Before you begin

Acronyms first, then the concepts

A quick-reference glossary, then eight short primers. Skim the glossary, open only the primers covering something unfamiliar.

1Control path vs. data path▾

Any I/O has two parts: the control path (deciding where the bytes live, and whether the request is even valid) and the data path (actually moving the bytes). GPUDirect Storage made the data path fast — DMA straight from SSD to GPU memory. The paper's whole argument is that the control path, which still has to resolve a file offset into a physical block, is where the cost now hides.

Now you're ready: most of the paper's findings are about the control path's latency — though Finding 2 shows the asymmetry also drags down delivered bandwidth, not just latency.
2GDS vs. BaM — who issues the request▾

Under GDS, a host thread calls cuFile to start the I/O; the SSD then DMAs data into GPU memory. The CPU is on the control path for every request. BaM removes that: GPU threads build NVMe commands in GPU memory and issue them directly. But BaM exposes raw blocks — no naming, no allocation, no offset translation.

Now you're ready: DevMeta wants GPU threads to issue requests without the host, the way BaM does, plus real file semantics — which means somebody still has to own metadata.
3File data vs. file metadata▾

Data is the bytes a program wants. Metadata — inodes, offset→block maps, directory entries, free-space state — is what tells you wherethose bytes physically are, and whether you're even allowed to read them. GPU-direct data access is free to be fast; it's metadata lookup that gates every open, append, or truncate.

Now you're ready: "bypassing the CPU" for data says nothing about who resolves metadata — that's a separate, and harder, problem.
4CPU-resident metadata — GeminiFS▾

GeminiFS keeps the file system on the host and embeds each file's offset→block mapping inside preallocated files so the GPU can cache and use it locally. It assumes predictable access so the mapping stays stable — but anything that evolves at runtime (length, allocation state, namespace) still needs host coordination.

Now you're ready: the paper's Finding 1–2 measure exactly this residual coordination cost: a shared append.
5GPU-resident metadata — GoFS▾

GoFS flips the placement: file-system management runs on the GPU as a persistent kernel, and the CPU is now the guest that must synchronize through it. This removes the CPU from the common GPU I/O path, but CPU operations still stall on the GPU-resident controller when shared state changes.

Now you're ready: Finding 3 shows this is not a fix — it's the same asymmetry, pointed the other way.
6Computational storage / programmable SSDs▾

Modern SSDs and DPUs have embedded cores and on-device DRAM capable of running real logic, not just the FTL. DevFS and CrossFS already showed allocation, mapping, and permission checks can run inside a storage device.

Now you're ready: DevMeta is this lineage applied specifically to CPU–GPU shared files, where neither endpoint wants to be the controller.
7Stateless clients vs. cached mappings▾

A client could cache a file's offset→block map locally to translate offsets itself — but that map is mutable: it changes on append, on truncate, and under a log-structured backend even on in-place overwrite. A cached copy must then be kept in sync with the device, reintroducing the very synchronization being removed.

Now you're ready: DevMeta's clients hold nothing authoritative; they name data by (handle, offset, length) and let the device resolve it.
8Hot metadata caching with device-controlled invalidation▾

Caching normally means a copy can go stale. DevMeta's Profiler caches only read-only, hot, unwritten metadata in GPU memory, tagged with a valid bit the device itself clears via DMA the instant a conflicting write arrives — before that write takes effect.

Now you're ready: this is the one place DevMeta does cache on the GPU — but the cache is non-authoritative and device-managed, not a second source of truth.
The whole story in one place

DevMeta in a nutshell

The problem, the measurement that exposes it, and the fix.

A CPU and a GPU sharing one file inevitably share its metadata too. GPUDirect Storage made the data path direct — SSD to GPU memory, no host bounce buffer — but the control path, resolving an offset to a physical block and keeping length/allocation state current, still runs wherever the file system lives. Put it on the CPU (GeminiFS) and the GPU pays a cross-PCIe hop on every metadata-touching op. Put it on the GPU (GoFS) and the CPU pays instead, and worse, can stall the GPU's own kernel.

The paper's claim: metadata synchronization, not I/O bandwidth, is the bottleneck. Its fix is DevMeta: move the entire metadata controller onto the SSD (or DPU) itself. DevMeta-MDS holds the one authoritative copy of every file's metadata; CPUIOLib/GPUIOLib turn both processors into equal, stateless clients that name data by (handle, offset, length) instead of caching a mutable mapping. Because there's one copy and one arrival order at the device, the two processors stay consistent through that order — not through a protocol between them.

To keep the embedded controller from becoming the new bottleneck under GPU-scale concurrency, two modules help it along: DevMeta-Profiler pushes read-only hot metadata into GPU memory under device-controlled invalidation, and DevMeta-Scheduler coalesces small, scattered I/Os into large sequential ones.

🍯 Key takeaways

  • CPU-resident metadata (GeminiFS): GPU pays a 38% latency tax on a shared append, and the host controller's single lock means throughput halves and queueing latency grows 254× from 1→128 GPU threads.
  • GPU-resident metadata (GoFS): just reverses who pays — CPU I/O slows 34× under heavy GPU load, and GPU I/O stalls 1.58× during CPU metadata updates.
  • Fix: one authoritative metadata copy, on the device. Both processors become stateless clients — no local mapping to keep in sync.
  • DevMeta-Profiler relieves controller pressure by caching hot, read-only metadata in GPU memory with device-initiated invalidation.
  • DevMeta-Scheduler coalesces small I/Os to cut per-request controller work and write amplification.
  • This is a design-and-measurement paper (HotStorage), not a full implementation — numbers come from emulating the device cost on real hardware, not a working DevMeta prototype.
Five everyday pictures

How to think about DevMeta

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Neutral authority

One shared calendar, not two diaries

Two roommates each keeping a private diary of the apartment's chore schedule must constantly cross-check and correct each other. Keep one shared calendar on the fridge instead, and each roommate just reads/writes it — there is nothing to reconcile because there is only one record. DevMeta-MDS is that fridge calendar for file metadata.

Where it breaks: a fridge calendar has no capacity limit; the SSD's embedded controller does — hence the Profiler and Scheduler.
Why placement matters · Asymmetric cost

A seesaw with the fulcrum off-center

Put the pivot on one side and that side barely moves while the other end swings wildly. Putting the file system on the CPU (GeminiFS) makes the GPU do the swinging — 38% extra latency, collapsing concurrency. Putting it on the GPU (GoFS) just moves the pivot and makes the CPU swing instead — 34× slower CPU I/O. Centering the pivot on the SSD, something neither end "owns," balances the seesaw.

Where it breaks: a seesaw has only two riders; real systems have many CPU/GPU processes contending at once, which is why ordering (not just placement) matters.
Consistency · Ordering, not locking

One teller's window, not a race to the counter

If every customer rushes the same counter, you need a lock (or chaos) to decide who goes first. Put one teller at one window and customers just line up — the order they arrive is the resolution, no extra negotiation needed. DevMeta's shared I/O command queue works the same way: operations on the same file are serialized by arrival order at the device, not by a lock either processor holds.

Where it breaks: a teller serves one customer at a time; DevMeta parallelizes across different files, so the single-queue picture only applies within one file.
Profiler · Lease with instant recall

A library's reserve-shelf pass

A library lets regulars keep a photocopy of a popular reference page at their desk — but only while nobody's editing the original, and the librarian can revoke that copy the instant an edit happens, before the edit is visible to anyone else. The Profiler's GPU-side metadata cache is exactly this: read-only, hot, valid-bit tagged, revoked by the device itself the moment a write would make it stale.

Where it breaks: a librarian's recall is a courtesy call; the Profiler's invalidation is designed so the device issues the DMA before applying the update — the paper proposes this ordering, it doesn't formally prove races are impossible.
Scheduler · Batching small requests

Combining errands into one trip

Three small errands to the same store cost three trips if run separately, one if combined. DevMeta-Scheduler sees every client's requests by file and offset — across both CPU and GPU — and merges adjacent small reads/writes into one large sequential operation, cutting the controller's per-request overhead and write amplification.

Where it breaks: errands can wait for a convenient batching moment; latency-sensitive I/O can't wait indefinitely for a batch to fill, so the scheduler must bound how long it holds a request.
The full explanation

How it actually works

Three pieces: one authoritative controller, two stateless clients, two mechanisms to keep the controller from choking.

1 · DevMeta-MDS — the single authoritative copy

DevMeta-MDS runs on the device and holds the one copy of every file's metadata: length, inode, block map, allocation state. Both CPU and GPU post requests to a shared I/O command queue; the MDS serves them in arrival order. Per-process state (open flags, file offset) stays per-process; the file's shared metadata stays single. Operations on different files proceed in parallel; operations on the same file are serialized by queue order, so two processors writing one file are ordered by the device, not by a lock either side holds.

2 · CPUIOLib / GPUIOLib — stateless clients

Both libraries expose open/read/write/lseek and turn each call into a request on the shared queue; GPUIOLib lets GPU threads issue requests themselves, without going through the host. Neither library holds authoritative metadata — a request names data as (handle, offset, length), and the MDS resolves the physical location as it serves the request. A reply is an acknowledgement (plus, for an append, the offset the device chose) — never a mapping for the client to cache.

💡
Why this kills the truncate race: if the CPU truncates a file the GPU is reading, the MDS shrinks the file and frees trailing blocks. A later GPU read of a removed offset still just names (handle, offset) — the device replies "end of file," the normal answer for a read past the end. There's no client-side mapping to invalidate, so a stale read of another file's reused blocks can't happen: the only route to those blocks is the device's mapping, which no longer points there.

3 · DevMeta-Profiler — shedding load to the GPU

The Profiler watches request traffic and tracks per-file hotness. When the device saturates and a hot file is read by many GPU threads but not written, the MDS DMAs a read-only copy of that file's mapping into a small GPU-side cache, tagged valid. The GPU checks the valid bit and, while set, resolves offsets and reads locally — bypassing the MDS entirely. The moment the file is written, the device clears the valid bit by DMA before the write takes effect; the GPU falls back to naming the MDS, and freed blocks are reused only after the GPU acknowledges the change.

4 · DevMeta-Scheduler — raising the granularity

Because every request passes through the device, the scheduler merges contiguous reads or writes sitting in the queue — e.g. a run of adjacent 4 KB reads into one 64 KB read — cutting the per-request name-resolution and mapping-lookup work, and turning many small NAND operations into fewer large ones (lowering write amplification). Because the MDS sees every client's requests by file and offset, it coalesces across both processors, which a scheduler seeing only raw blocks could not.

# request shape, either processor
req = (handle, offset, length, op)     # no mapping attached — ever
MDS.resolve(req)                       # offset → physical block, here
if op == APPEND: reply.offset = MDS.grow(handle, length)
else:            reply.ack
🌱
Together, Profiler and Scheduler are the paper's answer to one worry: an embedded controller is weaker than a host CPU, and under GPU-scale concurrency it could become the new bottleneck. Neither mechanism changes who's authoritative — they just reduce how often the MDS has to do full work.
Follow the numbers

Worked examples

Four traces through the paper's own measurements.

① The 38% append tax

A direct GPU-initiated append has normalized latency 1.00. Routing it through CPU-resident metadata (GeminiFS-style) raises that to 1.38. What is the extra cost, and where does it live?

  1. Overhead = 1.38 − 1.00 = 0.38, i.e. +38% of the direct latency.
  2. The data path is identical in both cases — standard GPU-direct write.
  3. So the entire 0.38 is the cross-PCIe request to the host plus the host's allocation decision, paid before the GPU is allowed to write.
  4. This is a per-operation tax: every shared append, regardless of size, pays it.
🍯
Insight: a "direct" data path says nothing about the control path riding on top of it — the bottleneck lives entirely in metadata resolution, not transfer.

② Concurrency collapses the host controller

Raising concurrent appending GPU threads from 1 to 128: host-mediated bandwidth falls by half; queuing latency at the host grows 254×. GPU-direct data path keeps scaling to the SSD's bandwidth limit. Why the divergence?

  1. Every appending thread must serialize on the single host metadata controller and its lock.
  2. As thread count rises 128×, contention for that one lock rises much faster than linearly — queueing latency grows 254×, far outpacing the 128× increase in demand.
  3. Delivered bandwidth actually drops (to ~50%) because threads spend more time waiting than transferring.
  4. The GPU-direct data path has no such single point — it scales until it hits the SSD's own physical bandwidth ceiling, not a software lock.
💡
This is Finding 2's core point: the asymmetry doesn't just add fixed latency, it actively worsens as you add the GPU parallelism the whole system exists to exploit.

③ GoFS reverses, not removes, the cost

Moving the controller to the GPU (GoFS): CPU-initiated I/O under heavy concurrent GPU I/O pressure is 34× slower than direct CPU-native I/O (Fig. 3a). A CPU core continuously issuing metadata updates causes GPU I/O to run at 1.58× its DevMeta baseline (Fig. 3b) — i.e. fully stalling while the atomic update finishes.

  1. 34×: CPU-initiated requests must wait for in-flight GPU operations to complete before the GPU-resident controller services them.
  2. 1.58× (+58%): when the CPU issues metadata updates (append, allocation, invalidation), all subsequent GPU I/O must fully stall until that atomic update finishes on the GPU.
  3. Both numbers describe the same structural fact as Findings 1–2, just with the roles of CPU and GPU swapped.
⚠
The lesson, stated plainly: whichever processor does not own the file system pays a cross-processor hop on the path of its own I/O. Placement alone — CPU or GPU — never removes that hop; it only decides who pays it.

④ Tracing the Profiler's invalidation

A hot file is read by many GPU threads and not written. Walk through what happens when a CPU write finally arrives.

  1. Profiler detects the file is hot and read-only; MDS DMAs its offset→block mapping into a GPU-side cache, valid bit set.
  2. GPU threads check the valid bit, see it set, resolve offsets locally, and read directly — zero MDS round-trips per read.
  3. A CPU write to that file arrives at the MDS.
  4. Before applying the update, the device DMA-writes the GPU's valid bit to invalid, over the same path it posts completions on.
  5. GPU threads now see the invalid bit, fall back to naming the MDS per request; freed/changed blocks are reused only after the GPU has acknowledged the change.
🍯
Insight: the invalidation is a single device-initiated DMA, not a cross-processor protocol — it costs one message, not a round trip.
Test yourself

Practice problems

Try before opening the answer. Each ends with the misconception it checks.

Problem 1 · easy
GPUDirect Storage DMAs data straight from SSD to GPU memory, "bypassing host memory." Does this mean the CPU is out of the GPU's I/O path?
Show answer
No. GDS bypasses the host memory bounce buffer on the data path, but a host thread still invokes cuFile to issue the request — the control path remains CPU-initiated. "Direct" describes where the bytes go, not who decides where they go.Misconception: that bypassing host memory means bypassing the host. The two are independent — BaM is what actually removes the CPU from issuing the request.
Problem 2 · medium
GeminiFS preallocates fixed-size files so the GPU's cached block mapping stays stable, avoiding most synchronization. What metadata still requires CPU–GPU coordination, and why doesn't preallocation fix it?
Show answer
File length, allocation state, and namespace information (renames, new files) still evolve at runtime and aren't fixed by preallocating block layout. Preallocation only stabilizes the offset→block map for data that's already placed — it says nothing about metadata that inherently changes, like how much of the file is valid right now.Misconception: that caching a mapping is a general synchronization fix. It only works for the subset of metadata that's predictable in advance.
Problem 3 · medium
Why doesn't moving the file system onto the GPU (GoFS) solve the CPU–GPU synchronization problem?
Show answer
Because the problem was never "the CPU is in the way" — it's that whichever processor doesn't own the controller must cross to the one that does. Moving the controller to the GPU just makes the CPU the one crossing: CPU-initiated I/O now waits behind in-flight GPU operations (34× slower under load) and can fully stall GPU I/O when it issues metadata updates (+58%).Misconception: that the asymmetry is caused by a specific processor's design, rather than by splitting authority across two processors at all.
Problem 4 · hard
The CPU truncates a shared file while a GPU thread is mid-read. DevMeta gives clients no local mapping and no invalidation message to the GPU. Why doesn't the GPU read stale, reused blocks?
Show answer
The GPU never held a mapping to begin with — every read names (handle, offset, length) and the device resolves it fresh, at the moment of the request. After truncation, the MDS has already shrunk the file and freed the trailing blocks in its single authoritative map. A read of a now-removed offset simply gets "end of file," the ordinary answer for reading past a file's end — there is no stale mapping to consult because the client never cached one. The freed blocks are only reachable through the device's current mapping, which no longer points there.Misconception: that correctness here requires an explicit invalidation protocol to the GPU. It doesn't — statelessness removes the thing that would need invalidating.
Problem 5 · medium
A skeptic says "DevMeta's Profiler just caches metadata on the GPU — isn't that exactly what GeminiFS does?" What's the structural difference?
Show answer
GeminiFS's GPU-side copy is relied upon as a working mapping the GPU uses to translate offsets on an ongoing basis, with staleness handled by assuming stable, preallocated layout. The Profiler's cache is explicitly non-authoritative, read-only, restricted to hot files with no concurrent writers, and invalidated by a device-initiated DMA before a conflicting update takes effect — the GPU never has to assume stability itself; the device is designed to enforce it via the valid bit, though the paper presents this as a design, not a formally proven guarantee.Misconception: that any GPU-side metadata copy reintroduces the synchronization problem. The difference is who's authoritative and who enforces invalidation — the device, not the GPU client.
Problem 6 · easy
The paper argues the bottleneck is metadata synchronization, not I/O bandwidth. Which measured finding most directly supports this, and why?
Show answer
Finding 2: as GPU thread count rises 128×, the GPU-direct data path keeps scaling right up to the SSD's physical bandwidth limit — bandwidth was never the constraint. Meanwhile the host-mediated metadata path collapses (bandwidth halves, queueing latency grows 254×) under the exact same load, because it serializes on one controller's lock. Same hardware, same SSD — the only difference is whether the operation touches shared metadata.Misconception: that more GPU threads or faster SSDs would fix the slowdown. The ceiling is architectural (one lock, one controller), not physical.
Quick answers

Frequently asked questions

Nine questions newcomers ask most.

Q1What does "device-resident" mean, precisely?▾
The metadata controller — allocation, block mapping, naming — runs inside the SSD or DPU's embedded processor, not just data sitting on the device. It's a different claim than "computational storage runs some offload function"; here the entire file system's authority lives on the device.
Q2Why can't CPU and GPU each just cache the block map locally?▾
Because the map is mutable — it changes on append, truncate, and (under a log-structured backend) even in-place overwrite. A cached copy would need reconciling with the device on every such change, which is exactly the synchronization cost the paper is trying to remove.
Q3Doesn't GPUDirect Storage already solve this by removing the CPU?▾
It removes the host-memory bounce buffer from the data path. The control path — issuing the request, resolving metadata — is unaffected: under GDS a host thread still invokes cuFile for every I/O.
Q4How is BaM different from DevMeta?▾
BaM lets GPU threads issue NVMe commands directly but exposes raw blocks with no file abstraction — no naming, allocation, or offset translation. DevMeta's GPUIOLib similarly lets GPU threads issue requests without going through the host, but adds a real file system, with the controller on the device instead of missing entirely.
Q5What stops the embedded SSD controller, which is weaker than a host CPU, from becoming the new bottleneck?▾
Two mechanisms: DevMeta-Profiler selectively pushes read-only hot metadata into GPU memory when it's useful, letting some hot reads skip the controller, and DevMeta-Scheduler coalesces small requests into large ones to cut per-request controller work. Both are explicitly load-shedding, not changes to authority.
Q6How does the Profiler's GPU-side cache stay correct without a round-trip invalidation protocol?▾
It only ever caches read-only, hot metadata with no concurrent writers. The moment a write to that file arrives, the device itself clears the GPU's valid bit via its own DMA engine before the write takes effect — a single device-initiated message, not a negotiated protocol with the GPU.
Q7Why is crash consistency harder here than for a normal file system?▾
The metadata service must journal or log-structure its updates to flash so a power loss leaves a recoverable state — without a host's memory or mature recovery code. Co-locating the file-system mapping with the flash translation layer may help (both manage block state), but safely unifying the two logs is an open question the paper flags, not a solved one.
Q8Does DevMeta help if there's no GPU-scale concurrency — just one CPU process and one GPU process?▾
The base win (no cross-processor metadata hop) still applies — the 38% append tax and the GoFS reversal happen even at low concurrency. The Profiler and Scheduler specifically matter once you're near the controller's capacity; at low concurrency they have little to do.
Q9How would this scale to multiple SSDs or DPUs?▾
The paper points to borrowing InfiniFS's fine-grained metadata partitioning to distribute metadata objects across devices while preserving locality and load balance, with file data independently striped across SSDs for aggregate bandwidth. This is listed as an open direction, not something evaluated in the paper.

Results at a glance
Source notes — provenance

Paper facts

Testbed: NVIDIA A100 SXM4 GPU + PCIe Gen4 NVMe SSD, dual-socket Xeon, GPU/SSD co-located on one socket; the device-resident path is emulated by throttling memory bandwidth and adding PCIe latency (methodology following DevFS/CrossFS), not run on a real programmable SSD. All five headline numbers (38%, 50% drop, 254×, 34×, 1.58×/+58%) and the architecture (MDS, CPUIOLib/GPUIOLib, Profiler, Scheduler) are stated directly in the paper. This is a HotStorage position/design paper — DevMeta's own mechanisms are a design sketch with open challenges, not an evaluated full implementation.

My framing

The three-panel SVG, all five analogies, the "control path vs. data path" framing, and the grouping of findings into bar-chart vs. "off-chart multiples" are my organization, not the paper's. Worth noting for your own tiering work: putting the single source of truth in a neutral third location to avoid cross-domain coordination is the same structural move memory-tiering systems make when centralizing hot/cold page-state tracking (e.g., in the kernel or a CXL-attached controller) rather than splitting it across NUMA nodes — DevMeta is that idea applied to file metadata instead of page metadata.
