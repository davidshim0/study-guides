eBPF'26 · A Field Guide

A namespace boundary is logical — so why does it cost like a physical one?

Two containers on the same host pay a real throughput tax just for the packet to cross a network namespace. This is the plain-English story of netkit, the eBPF device that makes the crossing (almost) free.

📄 "Netkit: Specializing Linux Packet Delivery for Container Networks" · Borkmann & Chaignon 🎓 Some Linux networking basics assumed — primers cover them ⏱ ~25 min read
📦

Skip the per-CPU backlog queue whenever a packet crosses a namespace and the BPF datapath, not netfilter, is already enforcing policy — redirect straight into the next stack instead of re-queuing it.

Quick glossary, then eight primers

The acronyms first, defined up front, then the concepts they depend on — collapsed, tap to open.

1Network namespaces: isolation without hardware▾

A network namespace gives a process its own private view of interfaces, routes, and ports — the mechanism containers use for network isolation. Crucially, this is a software boundary: no physical wire separates two namespaces on the same host.

Now you're ready: the paper's whole argument is that crossing this logical boundary shouldn't cost what it currently costs.
2veth pairs: the current container-to-host link▾

A veth pair is two interconnected virtual NICs, one per namespace; whatever exits one immediately appears at the other, as if physically wired. Containers get one veth end, the host the other.

Now you're ready: netkit is a drop-in replacement for this pair, designed to let BPF run after the namespace switch instead of just tunneling the packet through.
3The per-CPU backlog queue▾

Incoming packets can be buffered in a per-CPU queue before the upper networking stack processes them, so work can be load-balanced and deferred across cores. Physical NICs usually skip it; veth devices always use it.

Now you're ready: every backlog traversal is a scheduling detour — sometimes handed off to ksoftirqd — and it's exactly what netkit exists to avoid.
4Where BPF hooks into the stack▾

XDP sits in the driver, before the backlog queue and before GRO — fast, but sees raw, unaggregated packets. tc-bpf sits in the "upper stack," after the queue, where most container features (policy, load balancing, NAT) actually live today.

Now you're ready: netkit's redirect helper runs from tc-bpf, not XDP, specifically so it can operate on GRO-aggregated packets.
5GRO: fewer, bigger packets▾

GRO merges a run of same-flow packets into one large "super-packet" before handing it to the upper stack, amortizing per-packet processing cost.

Now you're ready: redirecting after GRO means netkit moves one consolidated packet across a namespace, not many — this is why the redirect helper isn't implemented at XDP.
6Two benchmarks: TCP_RR vs TCP_CRR▾

TCP_RR repeatedly bounces small requests over one already-open connection — a proxy for latency. TCP_CRR opens a fresh connection for every transaction — closer to real microservice traffic (e.g. IAM calls), and stresses connection setup and conntrack much harder.

Now you're ready: the paper reports both, and they respond differently to netkit because they stress different parts of the stack.
7netfilter, conntrack, and why BPF datapaths bypass them▾

netfilter (iptables/nftables) is the traditional place to enforce firewall rules and track connections (conntrack). Modern BPF-based CNIs like Cilium increasingly implement the same features in BPF instead, bypassing netfilter for Pod traffic.

Now you're ready: netkit's redirect is only safe when nothing left in netfilter still needs to see the packet — which is now a realistic assumption for BPF-based datapaths.
8The CNI: Cilium as the control plane▾

Kubernetes delegates pod networking to a CNI plugin. Cilium is an eBPF-based CNI that already implements routing, policy, load balancing, and QoS in BPF rather than netfilter or iptables.

Now you're ready: netkit is a kernel mechanism; Cilium is the real-world control plane that attaches netkit's BPF programs and is used to evaluate it end-to-end.
The whole story in one place

netkit in a nutshell

The problem, the fix, and the one traversal that has to stay.

Containers on the same host communicate through veth pairs, which route every packet through a per-CPU backlog queue — the same mechanism a physical NIC would use, even though no physical wire separates two namespaces on one machine. A packet from container A to container B crosses this queue twice: once leaving A's namespace, once entering B's. Measured directly: two processes sharing one namespace get 31% more throughput than two containers on the same host, and two bare hosts get 26% more than two containers over the wire. The paper's later over-the-wire results trace most of this gap to exactly these redundant queue traversals and the scheduling detour (ksoftirqd) they can trigger.

netkit removes what it can. A new redirect helper, bpf_redirect_peer, lets a tc-bpf program on the host splice a packet straight from the host's upper stack into the container's upper stack, skipping the container-side backlog entirely (ingress from the wire). A new device pair, netkit, replaces veth so that a BPF program can run on the transmit side immediately after the namespace switch — letting it redirect straight to a physical device on egress, again with no backlog. For container-to-container traffic on the same host, both source-side traversals are skipped this way.

One traversal is provably unavoidable: turning a transmit into a receive on the destination container still needs exactly one backlog queue, because that's the mechanism that bridges "sending" code to "receiving" code within one CPU's scheduling model. netkit keeps this single traversal, deliberately, at the destination.

The payoff: up to 37% higher throughput (TCP_RR), connection rates up by 32% same-host / 26% over the wire (TCP_CRR), reaching parity with process-to-process communication — for 78 + 1,048 new kernel lines and 49 + 463 lines of Cilium integration.

🍯 Key takeaways

  • Namespace crossings are logical, but veth makes them pay a physical-device tax: the backlog queue.
  • Container-to-container on one host crosses the backlog twice; over the wire, once per host-container leg.
  • bpf_redirect_peer eliminates the ingress traversal by recirculating a packet directly into the target namespace's upper stack.
  • The netkit device pair (primary in the host netns, peer in the container's) runs BPF right after the namespace switch, before any queue — and containers can't tamper with the peer's programs.
  • One backlog traversal, at the destination on same-host delivery, is structurally required and stays.
  • Requires netfilter to be bypassed in the host (true for modern BPF-based CNIs like Cilium) — all policy/NAT/QoS must already live in BPF.
  • Result: up to 37% throughput, parity with process-to-process, ~1,100 new kernel lines plus ~500 Cilium line changes, upstreamed in Linux v5.10 and v6.7.
Five everyday pictures

How to think about netkit

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Redundant queueing

Two mailrooms, same building

Room A sends a memo to Room B one floor down. Instead of a hand-off, it goes through the building's central mail intake desk — twice: once leaving A, once arriving at B — as if it were being mailed across town. The desk exists for external mail; using it for an internal hand-off is pure overhead. netkit's fix is: if the sender already knows exactly where it's going, skip the desk and hand it straight over.

Where it breaks: one desk visit genuinely can't be skipped — converting "this is being sent" into "this has arrived" still needs one hand-off point, just not two.
The mechanism · bpf_redirect_peer

A guest badge that skips the front desk

Normally every visitor checks in at reception before being allowed upstairs. A pre-verified guest instead gets handed a badge that lets security wave them straight to the right floor — the verification already happened, so the second checkpoint is redundant. bpf_redirect_peer works the same way: the host's BPF program has already applied policy, so it hands the packet straight into the container's upper stack.

Where it breaks: this only works if reception (netfilter) truly has nothing left to check — if any rule still lives there, skipping it means bypassing security, not streamlining it.
The device pair · Primary vs. peer

A landlord-installed intercom

A tenant's intercom is wired by the building, not the tenant — they can use it, but can't rewire or unplug it without locking themselves out. netkit's peer device (in the container) runs BPF logic that only the host-side primary device — managed by the control plane, e.g. Cilium — can install or remove. The application inside the container can't touch it.

Where it breaks: the intercom only talks to the building office; netkit's peer program actually executes with access to host routing state, which has no everyday-object equivalent.
Why not at XDP · GRO ordering

Collating before you staple

You don't staple each loose page as it comes off the printer — you let them collate into one document first, then staple once. GRO collates a run of packets into one aggregate before the upper stack sees it; redirecting there means one "staple," not many. XDP runs before collation, so redirecting there would mean re-doing the hand-off per loose page.

Where it breaks: collation (GRO) doesn't happen for every flow or every workload — small or non-aggregatable traffic gets less benefit from this ordering choice.
Side-effect · Scheduler accounting

A temp worker in the general line

A backlog-queued packet under load can be handed to ksoftirqd, a normal-priority kernel thread that queues up behind everything else runnable — like a temp worker with no dedicated lane, waiting their turn with the general crowd. It also means the work no longer shows up on the sending process's own timesheet (scheduler accounting). Skip the queue, and the packet's cost stays charged to the process that actually sent it.

Where it breaks: ksoftirqd only kicks in under load — at low load, the accounting distortion is smaller, so this benefit of netkit is most visible precisely when the system is busiest.
The full explanation

How it actually works

Three packet paths, fixed one at a time, plus the one that stays fixed forever.

1 · The baseline problem

On the receive side, physical NICs usually skip the per-CPU backlog queue; veth devices always use it, because they behave like any other network device to the kernel. A packet traveling container→container on one host (path 2 in the paper) crosses it twice: once when the source veth "receives" on the host side, once when the destination veth "receives" inside the target container. A packet to/from the wire (paths 1, 3) crosses it once, at the container boundary.

2 · Fixing ingress — bpf_redirect_peer (path 1)

Key observation: the code that runs after a veth's backlog queue inside the container is functionally identical to the code that runs on a physical device's receive path — same upper-stack logic, just a different namespace's tc-bpf programs, routes, and netfilter rules. So instead of enqueuing into the container's backlog, a new helper, bpf_redirect_peer, lets a tc-bpf program on the host switch the packet's namespace and recirculate it directly into the container's upper stack — skipping the container-side veth transmit and its backlog queue.

⚠
Precondition: this only works if netfilter isn't enforcing anything in the host — all security, QoS, and NAT logic must already be in BPF (tc-bpf or XDP), ahead of the redirect. A reasonable assumption for BPF-based CNIs, not for netfilter-based ones.

It's implemented at tc-bpf, not XDP: XDP runs before GRO, so it sees unaggregated packets and would need many redirects instead of one consolidated one.

3 · Fixing egress — the netkit device pair (path 3)

Removing the backlog queue on the way out of a container is harder: it would require a BPF program running inside the container's own namespace, which an application could unload (breaking policy or connectivity) and which has no visibility into host routing state anyway.

netkit solves this with an asymmetric device pair: a primary device in the host namespace and a peer device in the container's. BPF programs on the peer device execute as part of the driver's transmit logic — immediately after the namespace switch, i.e. already running in host context with access to host routes — but only the primary device (managed by the control plane, e.g. Cilium) can attach or detach them. The container can't touch its own peer's programs. With no program attached, the device defaults to a configurable drop policy, so no traffic leaks before setup.

Because that BPF program already runs in host context before any queue, the ordinary bpf_redirect helper (no namespace switch needed) sends the packet straight to the physical device — no new helper required here.

4 · Container-to-container (path 2) and the one required traversal

Same-host delivery combines both fixes: the source container's netkit BPF program redirects straight to the destination container's host-side netkit device, skipping the source-side queue. But entering the destination container still requires one backlog traversal — turning "this was transmitted" into "this was received" needs a hand-off point, and the paper argues eliminating it would require substantial refactoring of the Linux stack. They chose to keep this traversal at the destination (via the container's netkit device) rather than at the source, purely so that the whole path uses one consistent attach point (netkit) instead of mixing netkit and tc-bpf hooks.

💡
The only way past it: bypass the stack entirely via sockmap — but that reintroduces the problem netkit was built to avoid: applications that expect a full network stack (sockets, routing, iptables-equivalents) can't use sockmap.

netkit deliberately does not support XDP (unclear benefit on virtual devices, real code complexity, and it conflicts with operating on GRO-aggregated packets) and defaults to layer-3 mode, skipping the neighbor (ARP/NDP) resolution veth requires — layer-2 mode remains available for containers that need Ethernet semantics.

Follow the numbers

Worked examples

Four calculations straight from the paper's reported numbers.

① Counting eliminated backlog traversals, path by path

Paths 1, 2, and 3 are alternative routes a packet can take, never combined in the same trip. How many backlog traversals does each need, before and after netkit?

  1. Path 1 (wire → container): 1 traversal with veth → 0 with netkit (bpf_redirect_peer) — fully eliminated.
  2. Path 2 (container → container, same host): 2 traversals with veth → 1 with netkit (destination only, per §3.3) — halved, not eliminated.
  3. Path 3 (container → wire): 1 traversal with veth → 0 with netkit (device-pair redirect) — fully eliminated.
🍯
Insight: these are per-path counts, not a single global ratio — the paper never sums the three paths into one "4-to-1" reduction, since any given packet travels exactly one path, not all three. Path 2 is the interesting case: it's the only path with a traversal netkit can't fully remove. The 26–37% throughput gains reported in §4 come from whichever paths a given benchmark exercises, plus side effects like scheduling and conntrack — not from the queue removal alone.

② Closing the process-to-process gap

Section 2 measures process-to-process as 31% faster than container-to-container, same host. Does netkit's reported 34% (TCP_RR) gain close that gap?

  1. Normalize: let container-to-container (veth) throughput = 100.
  2. Process-to-process baseline = 100 × 1.31 = 131 (31% higher, from §2).
  3. netkit's same-host TCP_RR gain = 100 × 1.34 = 134.
  4. 134 > 131 — netkit's containers slightly exceed the loopback baseline, consistent with the paper's claim that Cilium+netkit sometimes outperforms Host networking because it also skips remaining host-side netfilter logic that the loopback path doesn't.
💡
Same check over the wire: baseline gap is 26% (→121... here 126), TCP_CRR gain is 26% (→126) — an exact match, and TCP_RR's 37% gain (→137) exceeds it, both consistent with parity being reached or slightly beaten.

③ Engineering cost vs. payoff

How much new code bought a 26–37% throughput improvement?

  1. Kernel mechanism: bpf_redirect_peer helper = 78 new lines; new netkit device = 1,048 new lines (much of it boilerplate for BPF links/netlink). Total ≈ 1,126 new lines in the kernel.
  2. Cilium integration: the helper alone = 49 line changes (additions plus deletions, including a fallback for old kernels); full device-pair support = 463 line changes. Total ≈ 512 line changes.
  3. Not one number: the paper reports kernel work as new lines of code and Cilium work as line changes (additions + deletions) — two different units. Adding them into a single "total LOC" figure isn't something the paper does or supports.
🍯
Insight: even without a combined total, the shape is informative: the helper alone (78 new kernel lines, 49 Cilium line changes) already removes a whole traversal (path 1) — most of the remaining kernel effort (1,048 lines) goes into the new device abstraction needed for the harder egress case.

④ Why TCP_CRR gains less than TCP_RR over the wire

Over the wire, TCP_RR gains 37% but TCP_CRR only 26%. Why don't the two benchmarks see the same improvement from netkit?

  1. TCP_RR and TCP_CRR stress the stack differently to begin with: TCP_RR bounces requests over one already-open connection, while TCP_CRR opens and tears down a connection per transaction — there's no reason to expect netkit's backlog-queue removal to move both by the same amount.
  2. TCP_CRR's fresh-connection-per-transaction pattern stresses connection-tracking and setup costs far more than TCP_RR's reused connection (per the paper's §4.3 observation that TCP_CRR "strains the connection tracking components in particular").
  3. Those per-connection costs are largely unaffected by the backlog queue netkit removes, so a bigger share of TCP_CRR's per-transaction cost sits outside what netkit changes — diluting its relative improvement compared to the more queue-dominated TCP_RR.
💡
This is echoed in §4.3: CPU consumption drops further for Cilium+netkit than for Host networking specifically because netkit also skips host-side conntrack for Pod connections — a second, independent source of savings layered on top of the backlog-queue fix.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why doesn't XDP need the backlog-queue fix that veth needs?
Show answer
XDP runs in the driver, before the backlog queue is even populated — physical-device receive paths generally skip the queue by default (absent RPS). The queue only exists as an issue for veth devices, which always enqueue.Misconception: that XDP and netkit solve the same problem. XDP avoids the queue on physical devices; netkit avoids it on virtual (veth-like) ones, a different code path entirely.
Problem 2 · medium
A container's application unloads the BPF program it finds attached to its own network device. Under veth-based designs this could break security policy. Why can't this happen with netkit?
Show answer
netkit's peer device (in the container) executes BPF programs that only the primary device — reachable only from the host namespace, managed by the control plane — can attach or detach. The container's application has no access to the primary device, so it cannot remove the peer's programs.Misconception: that "the device is in my namespace" implies "I control what runs on it." netkit intentionally breaks that assumption for its peer device.
Problem 3 · hard
Why is bpf_redirect_peer only needed for path 1 (wire → container), and not for path 3 (container → wire)?
Show answer
For path 3, the netkit device's BPF program already runs in host context immediately after the namespace switch — no further namespace change is needed before redirecting to the physical device, so the ordinary bpf_redirect helper suffices. For path 1, the host's tc-bpf program is running in the host namespace and must switch into the container's namespace before recirculating through its upper stack — that namespace switch is exactly what the new helper adds.Misconception: that any BPF redirect needs the new helper. Only redirects that must also cross a namespace boundary do.
Problem 4 · medium
Why can netkit skip a backlog queue on path 3 (container → wire) but not on path 2 (container → container, same host)?
Show answer
The queue that disappears on path 3 is the host-side veth's receive-side backlog queue: with veth, a packet leaving the container still has to be "received" by the host's veth peer before it can reach the physical device, and that hand-off goes through the backlog queue. netkit's device pair runs its BPF program in host context immediately after the namespace switch and redirects straight to the physical device, so that host-side queue is never entered. On path 2, the destination is another container's netkit device, not a physical device — turning a transmit on one side into a receive on the other still requires one hand-off point (a backlog queue), which is structural and can't be skipped the same way.Misconception: that path 3 has "nothing to skip" because physical NICs don't use backlog queues. The queue removed on path 3 belongs to the host's veth device, not the physical NIC — the physical device was never the one holding the queue.
Problem 5 · medium
A team runs a CNI that still relies on netfilter rules in the host namespace. Should they adopt netkit as described in this paper?
Show answer
Not directly — netkit's redirects assume all security/QoS/NAT logic is already implemented in BPF ahead of the redirect point; any remaining netfilter rule in the host would be silently bypassed. They would need to first migrate that logic into BPF (as Cilium has done) before adopting netkit safely.Misconception: that netkit is a transparent, policy-agnostic performance patch. It has a real precondition on how policy is enforced.
Problem 6 · easy
True or false: netkit turns off the backlog queue mechanism in Linux.
Show answer
False. The backlog queue mechanism still exists and is still used — e.g. the one required traversal on path 2, and by any device or workload that doesn't use netkit. netkit only avoids redundant traversals specific to namespace crossings it can prove are unnecessary.Misconception: netkit as a global optimization to the backlog queue itself, rather than a targeted bypass for specific, provably-redundant crossings.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is netkit a replacement for veth in all cases?▾
It replaces veth wherever the datapath is BPF-based and doesn't rely on host-side netfilter (the precondition for the redirects to be safe). It's not a universal drop-in; container runtimes expecting classic iptables-based policy in the host still need veth or a migration path first.
Q2Does netkit require rewriting the containerized application?▾
No — that's a central design goal. The application still sees a normal NIC (the peer device) and uses regular IPv4/IPv6 sockets and the full Linux stack. This is what distinguishes netkit from AF_XDP or sockmap, which either require new socket interfaces or only cover a subset of traffic.
Q3Why doesn't netkit support XDP?▾
The paper cites three reasons: the performance benefit of XDP on virtual devices is unclear, supporting it adds significant driver complexity (as seen in veth), and it would conflict with netkit's design of operating on GRO-aggregated packets rather than individual ones — plus container apps use sockets, so packets must reach the upper stack regardless.
Q4How is netkit different from ipvlan, which also skips a backlog queue?▾
ipvlan only bypasses the queue on ingress, not egress, causing path asymmetry; its BPF programs can be removed by the container and lack host-namespace visibility; each ipvlan slave is bound to one master device; and it uses an internal FIB instead of the kernel's, which is less BPF-programmable. These limitations led the Cilium project to drop ipvlan support.
Q5Has netkit actually shipped anywhere?▾
Yes. bpf_redirect_peer was upstreamed in Linux v5.10 and netkit devices in v6.7. Per the paper, it's in production at scale at both Meta and ByteDance for container networking.
Q6Why does the paper still call one backlog traversal "required"?▾
Converting a transmit-side code path into a receive-side code path for the destination namespace needs one hand-off structure, and the backlog queue is that structure in Linux today. Removing it entirely would need substantial refactoring of the core networking stack, out of scope for this paper; the only full bypass is sockmap, which sacrifices full-stack compatibility.
Q7Does netkit help with latency, or just throughput?▾
Both — TCP_RR (used as a latency proxy) improves 34–37%, on top of TCP_CRR's 26–32% connection-rate gains. Removing the ksoftirqd hand-off under load also removes a source of latency variance, since packet processing stays charged to, and scheduled with, the sending process.
Q8How does this relate to OS memory-tiering research?▾
It's an instructive contrast, not an analogy that holds structurally: a network namespace boundary is purely logical, so netkit's whole argument is that crossing it should cost nothing — and mostly can be made to. A DRAM/CXL tier boundary is physical: real interconnect latency is unavoidable, so tiering work (TPP, HeMem, Memtis) optimizes placement and migration timing rather than trying to make the crossing free. netkit is a reminder to first check whether an overhead is structural (like PCIe/CXL latency) or accidental (like a redundant backlog queue) before deciding whether "eliminate it" or "hide it" is the right target.
Q9What's left for future work?▾
The paper doesn't list explicit future work beyond describing the one remaining unavoidable traversal and noting sockmap as the only full bypass (at the cost of full-stack compatibility). Related follow-on directions visible from context: deeper stack refactoring to remove the last traversal, and extending BPF-first device designs (like netkit) to other virtual-networking scenarios beyond containers.
