Giving GPUs to whoever's starving, not whoever grabbed them at boot

Split prefill and decoding onto separate GPU pools once, at deployment time, and you've frozen that split forever — even as request patterns shift underneath you. This is the plain-English story of WindServe, a scheduler that keeps re-drawing that line at runtime.

📄 "WindServe" · Feng, Huang, Zhang, Liang, Yan, Wu — ISCA'25 🎓 Some LLM-serving basics assumed — the primers cover them ⏱ ~30 min read
🌬️

Don't nail prefill and decoding to a fixed GPU split decided once — watch queue depth and KV-cache pressure and move work across the boundary before either phase starves.
Measure the bottleneck first, then shift load toward it.

Before you begin

Quick glossary, then nine ideas the paper assumes

Skim the acronym table first — you'll see these letters everywhere. Then the primer cards clear up the concepts behind them; tap any to open.

🔑 Quick glossary

TTFTTime To First Token — queuing + prompt-processing time. The prefill phase's scorecard.
TPOTTime Per Output Token — average time to produce each token after the first. The decoding phase's scorecard.
PDPhase-Disaggregated — prefill and decoding run on separate GPU instances instead of one hybrid batch.
KV cacheCached key/value tensors from earlier tokens, reused every decoding step to avoid recomputation.
SLOService Level Objective — a latency target (e.g. TTFT < 0.25 s) a request must meet.
TP / PPTensor / Pipeline Parallelism — how a model is split across GPUs. "[TP-2, TP-1]" = prefill uses 2-way TP, decode uses 1-way.
SBDStream-based Disaggregation — WindServe's own term for running prefill and decode in separate CUDA streams.
NVLink / PCIeThe two interconnects moving KV cache between GPUs — NVLink is fast (400 GB/s here); PCIe is slower (the paper's KV-transfer example uses ~32 GB/s one-way over PCIe Gen4 ×16, well below the link's 64 GB/s bidirectional rating).
prefill instance / TTFT decoding instance / TPOT WindServe's machinery static baseline (DistServe / vLLM)
1Prefill and decoding — one request, two very different jobs▾

Every LLM request runs through two phases. Prefill processes the entire prompt at once to produce the first output token — every prompt token multiplies against every other, so cost grows roughly quadratically with prompt length and it's compute-bound. Decoding then generates one token at a time, feeding back the last token plus all cached history — mostly moving data around, so it's I/O-bound.

Prefill for a long prompt can take dozens of times longer than a single decode step. Batch the two together and one drowns out the other.

Now you're ready: WindServe's entire design is about giving these two very different jobs the resources each actually needs, and letting that allocation move as the workload does.
2TTFT and TPOT — the two clocks that matter▾

TTFT (time to first token) = queuing delay + prefill time. It's what a user perceives as "how long before anything happens." TPOT (time per output token) = the average gap between subsequent tokens — what a user perceives as "how fast is it typing."

Optimizing one in isolation is easy; the hard part is that fixes for TTFT (e.g. squeezing prefill jobs onto GPUs) often directly interfere with TPOT, and vice versa.

Now you're ready: almost every design choice in this paper is a trade between these two clocks — the paper's whole pitch is getting both without the usual trade-off.
3KV cache — why decoding needs memory, not just compute▾

Self-attention needs the key/value tensors of every prior token on every step. Recomputing them each time would be wasteful, so serving systems cache them — the KV cache — trading GPU memory for compute. The longer the conversation, the bigger the cache.

This cache is large: for OPT-13B at the 2048-token context limit it's about 1.5 GB per request. It has to live somewhere in GPU memory, and in phase-disaggregated systems it must be moved from where it was created (prefill) to where it's used (decoding).

Now you're ready: that move is a real cost — measured in this paper at roughly 65 ms over PCIe — which is exactly the overhead WindServe is built to hide.
4PagedAttention and continuous batching — the ground floor▾

vLLM's PagedAttention allocates KV cache in fixed-size blocks on demand instead of reserving a worst-case slab per request, cutting memory fragmentation. Continuous batching lets requests join or leave a running batch mid-stream instead of waiting for the whole batch to finish.

WindServe builds directly on both — it manages KV cache in blocks and schedules requests continuously — its contribution sits one layer up, in how work is placed across instances.

Now you're ready: when the paper says "KV block manager" or "running pipeline," that's this machinery, inherited and extended.
5Phase-Disaggregation (PD) — split the phases, not just the batch▾

vLLM-style systems batch prefill and decode jobs of different requests together on one GPU pool — simple, but a long prefill can stall decode steps for everyone else in the batch (interference). Phase-disaggregation instead runs prefill and decoding on separate GPU instances, transferring the KV cache between them once prefill finishes.

This removes interference and lets each phase's GPUs be sized and placed independently — but, as this paper shows, it also means each instance's resource allocation is now fixed unless something actively manages it.

Now you're ready: DistServe is the paper's PD baseline; WindServe keeps PD's isolation benefit while removing its fixed-allocation weakness.
6Placement notation: [TP-a, PP-b]▾

A model this large doesn't fit on one GPU, so it's split. Tensor Parallelism (TP) splits each layer's matrices across GPUs, which must talk to each other on every layer. Pipeline Parallelism (PP) splits the model's layers across GPUs, which hand off activations layer-by-layer.

The paper writes placements as [TP-a, PP-b] for a prefill instance and a second pair for decoding — e.g. [TP-2, TP-1] is shorthand meaning prefill uses 2-way TP (no PP), decode uses 1-way TP.

Now you're ready: every placement is a GPU-count decision made once, before serving starts — the "coarse-grained" allocation this paper's whole motivation section is arguing against.
7CUDA streams and Hyper-Q — sharing one GPU without partitioning it▾

A CUDA stream is a queue of GPU commands that execute in order, but different streams can run concurrently, sharing the GPU's SMs and memory bandwidth. Hyper-Q (Kepler-and-later NVIDIA GPUs) provides 32 independent hardware queues so kernels from different streams can genuinely overlap instead of serializing.

This is different from partitioning schemes like MIG (Multi-Instance GPU), which carves the GPU into walled-off, hardware-isolated pieces. MPS (Multi-Process Service) is more flexible — it still allows cross-partition operations via IPC — but its configuration can only be changed at process launch, not adjusted on the fly the way a CUDA stream can.

Now you're ready: Stream-based Disaggregation is exactly this — prefill and decode jobs on the same GPU, in different streams, sharing hardware directly rather than through a rigid partition.
8Chunked-prefill — the other way to reduce interference▾

If a prefill job must share a GPU with decode jobs, one fix is to break the prefill into small chunks and interleave them between decode steps, so no single decode step waits too long behind a giant prefill matrix multiply.

It works — but it stretches out the prefill job itself, since it's now competing for GPU time in small slices rather than running to completion.

Now you're ready: chunked-prefill is WindServe's main point of comparison for handling co-located prefill/decode jobs — Stream-based Disaggregation is offered as a faster alternative.
9Per-GPU request rate and SLO attainment▾

The paper reports load as per-GPU request rate (requests/second divided by GPU count) rather than total throughput, so results stay comparable across differently-sized deployments — this is the paper's "linear scaling rule."

SLO attainment is the percentage of requests that meet both their TTFT and TPOT targets — the paper's single best summary number for "is this system actually usable under load."

Now you're ready: every chart in this paper's evaluation is one of: latency vs. per-GPU rate, or SLO attainment vs. per-GPU rate. That's the whole vocabulary.
The whole story in one place

WindServe in a nutshell

The problem with fixed PD placement, the runtime fix, and how the pieces connect.

Phase-disaggregation solves interference by giving prefill and decoding their own GPU instances — but it introduces a new problem: that split is decided once, at deployment, based on an assumed workload. Under real, shifting traffic, one instance ends up starved while the other sits idle. The paper's Figure 3 makes this concrete: give prefill 2 GPUs and decode 1 ([TP-2,TP-1]) and prefill has near-zero queuing (avg 0.066 s) while decode becomes the bottleneck; give both 2 GPUs ([TP-2,TP-2]) and prefill queuing delay rises to 0.179 s because now decode is over-provisioned and prefill is comparatively squeezed. Whichever fixed split you pick, someone loses. DistServe sizes and places prefill/decode instances well for an assumed workload, but that scheduling becomes inflexible once traffic shifts; the paper discusses replanning placement online as a possible fix, but describes it as a stagnating, disruptive approach rather than a real-time answer.

WindServe's fix is to stop treating the placement as fixed. A Global Scheduler — a Profiler that predicts how long a batch of tokens will take, and a Coordinator that watches both instances' queues and KV-cache pressure — dynamically moves work across the prefill/decode boundary in two directions: Dynamic Prefill Dispatch sends overflow prefill tokens to the decode instance when the prefill instance is queuing up, and Dynamic Rescheduling moves some decode requests to the prefill instance when the decode instance's KV cache is nearly exhausted.

Moving work introduces its own costs, so WindServe adds two mechanisms to keep them cheap: Stall-free Rescheduling lets a request keep decoding while most of its KV cache migrates in the background, pausing only briefly for the final handoff once the remainder is small; and Stream-based Disaggregation runs the borrowed prefill jobs in a separate CUDA stream from the decode instance's own work, so the two barely interfere.

The payoff: against DistServe, the current state-of-the-art PD system, WindServe cuts median TTFT by up to 4.28× and TTFT P99 by 2.1× on OPT-13B, while also cutting TPOT P99 by 1.5× — and it improves SLO attainment by at least 1.5× at high load, across both chatbot and summarization workloads.

🌬️ Key takeaways

  • PD architectures fix interference but freeze resource allocation — one instance idles while the other queues, and the imbalance flips depending on which fixed split you chose.
  • The Profiler predicts batch completion time from token counts (not request counts) using a regressed quadratic/linear model, giving precise overload signals.
  • The Coordinator acts on those signals with two moves: Dynamic Prefill Dispatch (compute→decode instance) and Dynamic Rescheduling (memory pressure→prefill instance).
  • Stall-free Rescheduling migrates most of the KV cache while the request keeps decoding, pausing only briefly for the final handoff once the remaining cache drops below a threshold.
  • Stream-based Disaggregation co-locates borrowed prefill work with decode work in separate CUDA streams — faster for both phases than chunked-prefill.
  • Result: up to 4.28× median TTFT, 2.1× TTFT P99, 1.5× TPOT P99 vs. DistServe; ≥1.5× better SLO attainment at high load.
Six everyday pictures

How to think about WindServe

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Fixed vs. floating staff

Two checkout lines, one till

Staff two registers by their average traffic and you'll still be wrong the moment traffic shifts — one line backs up, the other's cashier waits idle. A store that instead floats a spare cashier to whichever line is backing up stays fast either way. That floating cashier is WindServe's Dynamic Prefill Dispatch and Dynamic Rescheduling — moving jobs to whichever instance is currently starved, not the one decided at open.

Where it breaks: a cashier needs to walk over and learn a new till; a CUDA stream switch is nearly free. The real cost WindServe worries about is GPU hardware contention once the "cashier" arrives, not travel time — that's what Stream-based Disaggregation manages.
Stall-free migration · KV cache handoff

A moving crew that lets you keep cooking

A bad moving crew makes you stop everything while they load the truck. A good one lets you keep using the kitchen until the very last box, then does one quick final handoff. WindServe's Stall-free Rescheduling is the good crew: a request keeps decoding — generating new KV cache — while its existing KV cache streams to the prefill instance in the background, and only pauses for the small remainder at the end.

Where it breaks: a moving crew handles one apartment at a time; WindServe deliberately migrates long-context requests first (the opposite of Llumnix's short-request-first policy), because freeing the most KV-cache space per move matters more here than minimizing per-move cost.
Streams vs. partitions · SBD

Two chefs, one kitchen, no walls

Wall a kitchen into two separate stalls (MIG) and each chef is safe from the other but stuck with whatever's on their side, even when idle. Let two chefs share every burner and counter freely (a CUDA stream) and both can use whatever's free — at the cost of occasionally bumping elbows. WindServe deliberately chooses the shared-kitchen model: it accepts some GPU-resource contention between the streams in exchange for never leaving a burner idle.

Where it breaks: the paper is explicit that this trade only pays off in the decoding instance, where just a few borrowed prefill jobs share space with the main decode work — it deliberately avoids the shared-kitchen model in the prefill instance, where the Profiler's predictions are less reliable.
The Profiler · token-based prediction

Judging the wait by the cart, not the checkout line

Counting people in line tells you little if one cart has 3 items and another has 300. The Profiler ignores request counts and instead predicts completion time from the actual token counts — quadratic in prefill tokens (attention cost grows with the square of prompt length), linear in total context length for decoding — because that's what really drives GPU time.

Where it breaks: the analogy stops at "count the right thing." The Profiler's coefficients are fit offline by profiling and regression before runtime, so it can misjudge if actual hardware behavior drifts from that calibration — the paper doesn't claim it adapts online.
The threshold trade-off · Dynamic Prefill Dispatch

A metering light on the on-ramp

Set a highway on-ramp meter too strict and cars pile up waiting to merge (queuing delay). Set it too loose and the highway itself jams (overload downstream). The thrd threshold that triggers Dynamic Prefill Dispatch is exactly this dial: too low and it dumps too many prefill jobs onto the decode instance, backing it up; too high and prefill jobs queue with nowhere to go. WindServe sets it just under the TTFT SLO.

Where it breaks: a real ramp meter is one fixed rate; WindServe's threshold interacts with a second dial — the decoding instance's budget for how many prefill tokens it will accept per forward pass — so it's really two dials tuned together, not one.
Chunked-prefill vs. SBD

Slicing the cake vs. baking two at once

Chunked-prefill slices one big job into many small pieces so it never blocks anything for long — but slicing a cake doesn't make more oven space; the total baking time still stretches out, sometimes 4× longer than a single decode step in the paper's LLaMA2-70B numbers. Stream-based Disaggregation instead runs the whole prefill job at once, in parallel, in its own oven (stream) — finishing faster overall while still leaving decode's own oven largely undisturbed.

Where it breaks: two ovens sharing one kitchen's power circuit still compete for electricity; the paper reports decode's own per-step time under SBD (≈0.34 s) stays essentially at its uncontended baseline (≈0.35 s) — resource sharing costs decode far less here than the stretched-out prefill costs it under chunking.
The full explanation

How it actually works

Section by section, following the paper's own architecture (Fig. 4).

1 · The problem, quantified — a fixed split can't win

Under a static PD placement, resources for one phase are provisioned once. The paper shows two failure modes directly: with GPU memory, the prefill instance discards its KV cache once transfer completes, so all active KV cache piles onto the decode instance — leading to swapping between GPU and CPU memory once it overflows. With compute, decode jobs are I/O-bound and rarely saturate their GPUs, yet stringent TPOT SLOs push teams to over-provision decode anyway — starving prefill of compute it could have used.

2 · The Profiler — predicting cost from tokens, not requests

Attention and FFN dominate per-layer cost. For a prefill batch of N input tokens and hidden size H, attention FLOPs are 8NH² + 4N²H and FFN FLOPs are 16NH² — dominated by the N² term as prompts grow, which is why the model in Eq. 1 has a quadratic component. For decoding, both modules are I/O-bound: total bytes moved scale with ΣL, the sum of all context lengths in the batch — hence the linear model in Eq. 2.

T̂_prefill = a_p·N + b_p·N² + c_p     # N = prefill tokens in the batch
T̂_decode  = a_d·ΣL + c_d            # ΣL = sum of context lengths

Coefficients (a,b,c) are fit offline via profiling and quadratic regression, then used at runtime to predict how long any candidate batch will take — the signal every scheduling decision below is built on.

3 · Dynamic Prefill Dispatch — Algorithm 1, in plain steps

  1. Predict TTFT. The Profiler estimates completion time for the new request, given everyone already ahead of it in the prefill instance's waiting queue and currently-running batch.
  2. Compare to threshold. If that predicted TTFT exceeds thrd (set just under the TTFT SLO), the prefill instance is considered overloaded for this request.
  3. Check decode-side capacity. The Coordinator computes available slots on the decode instance — a token budget capped so borrowed prefill work won't itself blow the TPOT SLO — using the running pipeline and KV block manager. If KV blocks are inadequate, slots = 0.
  4. Dispatch or queue. If slots cover the new request's length, it's added to assistRequests and slotted into the decode instance's next-ready batch; otherwise it falls back to the prefill instance's normal queue.
  5. Trigger isolation. Any prefill work now running inside the decode instance activates Stream-based Disaggregation for the duration of that batch.
🌬️
Why token-length, not request-count? T̂_prefill depends on total tokens, so the Profiler's flag is a much more precise overload signal than simply counting queued requests — a queue of five tiny requests and a queue of one giant one are treated very differently, as they should be.

4 · Stall-free Rescheduling — migrating memory without pausing compute

When the decode instance's KV blocks near exhaustion, WindServe migrates some long-context requests' KV cache to the prefill instance — chosen specifically because freeing long contexts frees the most space per migration. Crucially, the migrating request keeps decoding and producing new KV cache throughout the transfer; only once the remaining untransferred portion drops below a small threshold does the decode instance briefly pause that one request, hand off the tail, and let the prefill instance resume its decoding. The prefill instance runs any of its own prefill jobs in chunked-prefill form while a rescheduled decode request shares it, to bound the reverse interference.

💡
Why long-context requests, not short ones? Unlike Llumnix — which migrates short requests to minimize per-move overhead and fragmentation — WindServe migrates long ones to maximize the KV cache freed per migration, since the whole point here is relieving memory pressure, not balancing load evenly.
Follow the numbers, step by step

Worked examples

Four traces using the paper's own measurements — KV transfer bandwidth, the FFN FLOPs derivation behind the Profiler, the SBD-vs-chunking comparison, and the headline speedups.

① How expensive is a KV cache migration, really?

OPT-13B, a request at the 2048-token context limit, prefill and decode each on their own single GPU, connected via PCIe Gen4 ×16 (32 GB/s, P2P enabled).

  1. KV cache size at this context length ≈ 1.5 GB (paper, §2.2) — this is what must move between instances.
  2. Naive transfer time = size ÷ bandwidth = 1.5 GB ÷ 32 GB/s ≈ 47 ms.
  3. Measured transfer time ≈ 65 ms — higher than the naive bandwidth calculation because of real transfer/protocol overhead on top of raw throughput.
  4. Compare to one decoding step: the paper states this transfer "could take several times the duration of a single decoding iteration" — meaning a blocking migration would stall many token-generation steps for that request.
🌬️
Insight: 65 ms sounds small in isolation, but against a per-token decode budget it's enormous — which is exactly why WindServe never blocks decoding on a transfer (Stall-free Rescheduling) and instead overlaps the transfer with ongoing prefill or decode computation.

② Where the Profiler's quadratic term comes from

The paper derives FFN cost directly: "the two matrices multiplied at the first layer have shapes B×H and H×4H, and Matrix-Vector multiplication needs one multiply-add (2 FLOPs) per matrix element, so the FLOPs for the first layer are B×H×4H×2."

  1. Layer 1 FLOPs = B·H·4H·2 = 8BH².
  2. Layer 2 (shape 4H×H, projecting back down) is symmetric: 4H·B·H·2 = 8BH².
  3. Total FFN FLOPs = 8BH² + 8BH² = 16BH² — matching Table 1's decode-FFN entry exactly, with B the batch size.
  4. Now compare to prefill attention: Table 1 gives attention prefill FLOPs as 8NH² + 4N²H — that N² term (N = prefill tokens) is why T̂_prefill in Eq. 1 needs a quadratic component, while decode's cost (Eq. 2) stays linear in total context length ΣL, since decoding never re-processes the full prompt at once.
💡
This is the arithmetic reason prefill and decode need different prediction models — it's not an engineering convenience, it falls directly out of how self-attention's cost scales with sequence length.

③ Stream-based Disaggregation vs. chunked-prefill, LLaMA2-70B

A 2048-token prefill job must run alongside ongoing decoding. Chunked-prefill uses chunk size 512; a single decode step here costs ≈0.35 s.

  1. Chunked-prefill total prefill time ≈ 1.4 s. Ratio to one decode step: 1.4 ÷ 0.35 = 4× — matching the paper's own comparison.
  2. Stream-based Disaggregation prefill time ≈ 0.75 s for the same 2048-token job — because it runs as one continuous computation in its own stream rather than being sliced and re-queued.
  3. Speedup in prefill completion: 1.4 ÷ 0.75 ≈ 1.87× faster than chunked-prefill.
  4. Cost to decode: each decode iteration under SBD takes ≈0.34 s — essentially unchanged from the uncontended 0.35 s single-step baseline (the two are within measurement noise of each other, not a real slowdown), versus chunked-prefill's decode steps which stay closer to baseline but at the price of that 4× stretched-out prefill.
🌬️
Insight: chunking trades prefill time for decode smoothness one-for-one; SBD gets both — faster prefill and nearly-undisturbed decode — because the two jobs genuinely run in parallel on shared hardware rather than taking turns.

Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
A team doubles the GPUs on their decoding instance to be safe about TPOT SLOs. Why might this make TTFT worse, not better?
Show answer
Because compute is a shared, zero-sum resource across the deployment. Adding GPUs to decode without adding them to prefill leaves the prefill instance with the same fixed compute budget while decode sits comparatively idle (decode is usually I/O-bound and rarely saturates its GPUs). If traffic grows, prefill queues up — exactly the [TP-2,TP-2] case in Figure 3, where prefill queuing delay rose to 0.179 s because decode was over-provisioned.Misconception: that more GPUs anywhere always helps. In a fixed PD split, resources given to one phase are resources denied to the other — the imbalance doesn't disappear, it just moves.
Problem 2 · medium
A KV cache is 3 GB and must cross a PCIe Gen4 ×16 link at 32 GB/s. Estimate the naive transfer time, and explain why the real measured time (per the paper's OPT-13B example) is typically higher.
Show answer
Naive: 3 GB ÷ 32 GB/s ≈ 94 ms. The paper's own OPT-13B example (1.5 GB) gives a naive estimate of ≈47 ms but a measured transfer of ≈65 ms — about 1.4× the naive figure — due to real transfer/protocol overhead on top of raw bandwidth. Scaling that same overhead factor, 3 GB would realistically take somewhat more than the ≈94 ms naive estimate.Misconception: that bandwidth alone determines transfer time. Real transfers carry fixed and variable overhead beyond the theoretical throughput — always the case in system numbers, not just an LLM-serving quirk.
Problem 3 · medium
Why does the Coordinator set the Dynamic Prefill Dispatch threshold thrd "slightly below the TTFT SLO," rather than exactly at the SLO or well below it?
Show answer
Setting it too low triggers dispatch constantly, dumping excess prefill work onto the decode instance and risking overloading it instead — increasing TTFT via decode-side queuing and hurting TPOT via prefill-decode interference (paper, Fig. 5). Setting it at or above the SLO means requests only get help after they've already begun violating their target, which is too late. Just below the SLO leaves a margin for the dispatch decision and any residual queuing delay to still land inside the SLO.Misconception: that more aggressive load-shedding is always better. The threshold is a genuine two-sided trade-off (Figure 5 shows both directions degrade SLO attainment), not a dial you simply crank down.
Problem 4 · hard
Stall-free Rescheduling lets a request keep decoding while its KV cache migrates. Why not just pause the request immediately and migrate everything in one shot — wouldn't that be simpler and just as fast?
Show answer
Pausing immediately would add the full migration time (tens of ms, "several times" a decode step per the paper) directly to that request's TPOT for every affected step — exactly the stall the design is named to avoid. By letting decoding continue and only pausing for the small remaining delta once most of the cache is already transferred, the visible pause shrinks to a fraction of the full migration cost. It is simpler to implement pause-then-migrate, but at a direct TPOT cost the paper is specifically trying to eliminate.Misconception: that "simpler" and "faster" migration strategies are the same axis. Stall-free Rescheduling trades a bit of engineering complexity (tracking in-flight KV deltas) for a real latency win.
Problem 5 · medium
WindServe deliberately does not apply Stream-based Disaggregation inside the prefill instance, even though the paper shows SBD helps. Why?
Show answer
SBD's scheduling relies on the Profiler predicting when the co-located job is "about to complete" so the other stream can be fetched and synchronized correctly. In the decode instance, only a few borrowed prefill jobs are ever involved, so misprediction risk is limited. Applying SBD inside the prefill instance would make its whole scheduling policy hinge heavily on Profiler accuracy, which the authors judge insufficiently robust there.Misconception: that a technique proven beneficial in one place should be applied everywhere it's structurally possible. WindServe's authors explicitly scope SBD to where its dependency on prediction accuracy is safe.
Problem 6 · easy
MIG (Multi-Instance GPU) offers strong isolation between partitions. Why doesn't WindServe use it instead of CUDA streams for co-locating prefill and decode?
Show answer
MIG partitions are inflexible and fixed at GPU-configuration time — reconfiguring them isn't something you do many times per second in response to a queue filling up. MIG also disables peer-to-peer (P2P) GPU communication, which distributed LLM inference (tensor/pipeline parallelism) depends on. CUDA streams, by contrast, can be created, used, and torn down at runtime with no such restriction.Misconception: that more isolation is always the better engineering choice. Isolation and runtime flexibility are in tension here, and WindServe's whole premise — reacting to load within milliseconds — requires the flexible option even at some cost in isolation.
Problem 7 · medium
Table 4 sets OPT-13B's TPOT SLO to 0.1 s, following the paper's rule "≈4× the execution time of a decoding iteration ... without prefill interference." What does this imply about the uncontended per-step decode latency for OPT-13B, and why build in that 4× margin at all?
Show answer
0.1 s ÷ 4 ≈ 25 ms implied uncontended decode-step latency for OPT-13B under this setup. The 4× margin exists because in practice a decode step is rarely perfectly uncontended — batching effects, occasional prefill interference, and normal variance all inflate the real per-step time above the ideal baseline; setting the SLO at a bare 1× would make it nearly impossible to meet even under healthy conditions.Misconception: that an SLO should equal the best-case measured latency. SLOs need headroom for realistic operating conditions, not laboratory-ideal ones — that's the whole reason for the "≈4×" rule instead of "=1×".
Problem 8 · hard
The paper reports that WindServe's TTFT improvements (up to 4.28×) are consistently larger than its TPOT improvements (up to 1.5×) across every workload tested. Give the mechanistic reason, not just "that's what the graphs show."
Show answer
Dynamic Prefill Dispatch acts directly and aggressively on TTFT — it exists purely to relieve prefill queuing, and the decode instance has a strict token budget for absorbing that work so it never fully saturates. TPOT improvements, by contrast, come indirectly — Dynamic Rescheduling reduces KV-cache swapping and Stream-based Disaggregation limits interference, but both are deliberately conservative (bounded budgets, separate streams, stall-free transfers) specifically so they don't regress TPOT. The mechanisms optimizing TTFT are direct and unbounded-in-intent; the mechanisms protecting TPOT are indirect and intentionally bounded.Misconception: that both metrics are optimized by the "same amount of effort." WindServe's design asymmetrically prioritizes not regressing TPOT over maximizing its improvement, while TTFT is attacked much more directly.

Q1What problem does WindServe actually solve, in one sentence?▾
Phase-disaggregated LLM serving removes prefill/decode interference but freezes the GPU split between them at deployment time; WindServe adds a runtime scheduler that keeps moving individual jobs across that split as load shifts, without giving up disaggregation's isolation benefits.
Q2Isn't phase-disaggregation already the state of the art — why isn't DistServe enough?▾
DistServe plans placement and instance sizing well for an assumed workload, but that scheduling is inflexible once traffic shifts; the paper discusses online replanning as a possible fix but describes it as disruptive and stagnating rather than a real-time answer. WindServe instead reacts within the running system, without replanning placement at all.
Q3What exactly triggers Dynamic Prefill Dispatch?▾
The Profiler predicts a new request's TTFT given everything ahead of it in the prefill instance. If that prediction exceeds a threshold set just under the TTFT SLO, the Coordinator checks whether the decode instance has spare token "slots" (bounded by a budget that protects its own TPOT SLO) and, if so, dispatches the prefill work there.
Q4And what triggers Dynamic Rescheduling?▾
Decode-instance KV cache blocks nearing exhaustion — the memory-pressure signal, not a compute one. WindServe responds by migrating some long-context decode requests to the prefill instance, freeing decode-instance KV blocks for everyone else.
Q5Why migrate long-context requests specifically, not short ones?▾
Migrating a long-context request frees far more KV cache space per migration than a short one — and since the goal here is relieving memory pressure fast, that's the more valuable trade, even though (per Llumnix's logic) short requests would be cheaper to move individually.
Q6What does "stall-free" actually mean?▾
The migrating request keeps decoding — producing new KV cache — while its existing cache streams to the prefill instance in the background. Only once the untransferred remainder is small does decoding briefly pause for the final handoff, so the visible stall is much shorter than the full migration.
Q7How is Stream-based Disaggregation different from chunked-prefill?▾
Chunked-prefill slices a prefill job into small pieces interleaved between decode steps in the same stream — it avoids blocking decode but stretches prefill's own completion time considerably (≈4× a decode step in the paper's LLaMA2-70B example). Stream-based Disaggregation instead runs prefill in a genuinely separate CUDA stream concurrently with decode, finishing faster while leaving decode nearly undisturbed.
Q8Why not use NVIDIA MPS or MIG for this instead of raw CUDA streams?▾
MIG has fixed partitions, disables P2P GPU communication (breaking distributed inference), and can't be reconfigured at runtime. MPS is more flexible but can only be reconfigured at process launch. CUDA streams can be created and adjusted continuously during serving, which is what runtime dynamic scheduling requires.
Q9Does dynamic scheduling ever make things worse?▾
Yes, in bounded ways the paper is upfront about: Stream-based Disaggregation slightly reduces decode efficiency from shared-hardware contention; Dynamic Rescheduling temporarily forces chunked-prefill in the prefill instance, moderately raising TTFT there. Both effects are described as minimal compared to the gains, and ablations (§5.4) quantify them directly.
Q10How does the Profiler know how long a batch will take?▾
It uses a quadratic-in-tokens model for prefill (T̂_prefill = a·N + b·N² + c) and a linear-in-context-length model for decode (T̂_decode = a·ΣL + c), with coefficients fit by profiling and regression before runtime — reflecting that prefill's attention cost grows with the square of prompt length while decode's I/O cost grows linearly with total context.
Q11What are WindServe's own acknowledged limitations?▾
No multi-node evaluation (cross-node NCCL/GDR communication would need additional tuning); Stream-based Disaggregation roughly doubles I/O overhead since independent kernels can't share loads; and GPU sharing via streams is still coarse-grained — the CTA scheduler's opacity limits how finely WindServe can control contention between the two streams.
Q12What's proposed as future work?▾
Extending the PD architecture to heterogeneous GPU clusters (e.g. pairing high-compute/low-bandwidth GPUs for prefill with other GPUs for decode to cut cost), plus load balancing across many instances and fine-grained autoscaling strategies for large-scale deployment.

Core terms
WindServeThe paper's system: a PD-architecture LLM server with a Global Scheduler that dynamically moves work across the prefill/decode boundary at runtime.
Global SchedulerWindServe's cross-instance coordination layer, composed of a Profiler and a Coordinator.
ProfilerPredicts batch completion time from token counts using a regressed quadratic (prefill) / linear (decode) model.
CoordinatorMonitors instance load and KV-cache pressure; triggers Dynamic Prefill Dispatch and Dynamic Rescheduling.
Dynamic Prefill DispatchSends overflow prefill tokens from an overloaded prefill instance to the decode instance when it has spare capacity.
Dynamic ReschedulingMigrates long-context decode requests to the prefill instance when decode-instance KV cache nears exhaustion.
Stall-free ReschedulingMigration method that lets a request keep decoding while its KV cache transfers, pausing only for a small final delta.
Stream-based Disaggregation (SBD)Runs co-located prefill and decode jobs in separate CUDA streams inside the decode instance to reduce interference.
Supporting terms
Prefill / decoding phasePrefill processes the whole prompt (compute-bound); decoding generates tokens one at a time (I/O-bound).
TTFT / TPOTTime To First Token / Time Per Output Token — the two latency metrics the paper optimizes.
KV cacheCached key/value tensors reused every decoding step; ≈1.5 GB per request at OPT-13B's 2048-token context limit.
PD architecturePhase-Disaggregated: prefill and decoding run on separate serving instances with KV cache transferred between them.
Chunked-prefillSplitting a prefill job into small pieces interleaved with decode steps in one stream — avoids blocking but lengthens prefill.
PagedAttentionvLLM's block-based KV cache allocation, avoiding worst-case pre-reservation; the memory-management foundation WindServe builds on.
TP / PP placementTensor / Pipeline Parallelism configuration, written [TP-a, PP-b], deciding how many GPUs an instance uses and how.
CUDA stream / Hyper-QA sequence of GPU commands that can run concurrently with other streams; Hyper-Q provides 32 hardware queues enabling this.
MIG / MPS / Time-Slicing / vGPUAlternative NVIDIA GPU-sharing technologies, all rejected by WindServe for lacking runtime flexibility or P2P support.
Per-GPU request rateLoad reported as requests/second divided by GPU count, per the paper's linear scaling rule, for cross-configuration comparability.
SLO attainmentPercentage of requests meeting both their TTFT and TPOT targets — the paper's summary quality-of-service metric.
