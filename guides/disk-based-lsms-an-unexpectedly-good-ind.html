SOSP 2026 · A Field Guide

Trust almost nothing — except a tiny, honest patch of memory

CXL lets several hosts share memory, but hardware can only keep a sliver of it cache-coherent. This is the plain-English story of Prism, an index that makes peace with that limit by borrowing a trick from disks: log-structured merge trees.

📄 Hombal, Hu, Aguilera, Alagappan, Ganesan · SOSP '26 🎓 Assumes CXL/coherence basics — primers cover them ⏱ ~25 min read
🗂️

Make almost everything IMMUTABLE (so it never needs a coherence check), and squeeze whatever must be MUTABLE into a region small enough to fit in hardware-coherent memory.

Before you begin

Quick glossary, then the primers

Nine acronyms you'll see everywhere, then ten collapsible primers. Skip anything you already know.

CXLCompute Express Link — cache-coherent interconnect letting multiple hosts map and access the same external memory device via load/store.
scrSmall hardware Coherent Region (~100s of MB) — the slice of CXL memory hardware keeps synchronized across hosts.
lnrLarge Non-coherent Region — the TB-scale rest of CXL memory, where host caches can go stale silently.
LSMLog-Structured Merge tree — a disk-oriented structure that buffers writes and flushes them as immutable sorted files.
SSTableSorted String Table — an immutable, sorted on-disk (here: in-lnr) file produced when an LSM's write buffer is flushed.
ARTAdaptive Radix Tree — a fast in-memory index with variable-size nodes (Node4…Node256).
OLCOptimistic Lock Coupling — lock-free reads validated via per-node version numbers; writers lock and bump the version.
BULBounded Updatable Layer — Prism's size-capped, in-place-updatable ART sitting in lnr, the paper's key new idea.
YCSBYahoo! Cloud Serving Benchmark — the standard workload mix (A–F) used to stress key-value stores.
scr / hardware coherence immutable SSTables Prism's machinery (BUL, memtable) the baseline that struggles (SC-ART / SC-BTree)
1CXL shared memory across hosts▾

CXL 3.0/3.2 let several physical machines map the same external memory device into their address spaces and touch it with ordinary loads/stores — no network stack, no RDMA verbs, just pointers.

Now you're ready: the paper's whole problem exists because this sharing is real, but the coherence hardware behind it isn't free.
2Why cache coherence costs anything at all▾

Every host has its own CPU caches. If Host B writes data Host A has cached, A's copy is stale unless hardware snoops/invalidates it. That snooping (and back-invalidation) is exactly what breaks down at scale.

Now you're ready: vendors report snoop filters get "prohibitively expensive" once shared memory passes a few hundred MB — that number becomes scr's size.
3The scr / lnr split (partly coherent memory)▾

Because full hardware coherence doesn't scale, CXL memory splits in two: a small scr (hardware keeps it coherent) and a huge lnr (it doesn't). Everything in lnr is a coherence liability.

Now you're ready: the entire design problem is "how do I build an index across TBs of lnr using only a few hundred MB of scr?"
4Software coherence via version numbers▾

To use lnr safely, systems keep a small piece of coherent metadata (a version number) in scr per object. Before trusting a cached copy of the object in lnr, a host checks: did the version change? If yes, flush and re-read.

Now you're ready: SC-ART, SC-BTree, and Prism's BUL all lean on this per-node version-number mechanism — but not uniformly: Prism's memtable is covered by hardware coherence directly (no version numbers needed), and its SSTables use one coarse ID per SSTable rather than a version number per node.
5ART and optimistic lock coupling▾

ART is a radix tree with adaptively-sized nodes; ART-OLC adds per-node version counters so readers can traverse lock-free and just retry if a writer changed the node mid-read. Conveniently, that counter is exactly what software coherence needs — just move it into scr.

Now you're ready: "SC-ART" = ART-OLC with its version numbers relocated to scr and its actual nodes left in lnr.
6B-trees, fan-out, and false invalidation▾

B-trees pack many keys into each fixed-size node. Fewer, bigger nodes means fewer version numbers — good for fitting scr. But now updating one key bumps the version for the whole node, forcing every host caching that node to flush and refetch, even keys they didn't touch. That's false invalidation.

Now you're ready: SC-BTree trades "too many version numbers" for "too much collateral damage per write" — neither knob alone works.
7LSMs: memtable, SSTables, compaction▾

An LSM buffers writes in a small in-memory memtable. When full, it's frozen and written out as an immutable, sorted SSTable. Levels grow ~10× at a time; a background compaction merges old SSTables into new ones and discards the originals. Reads check the memtable, then levels newest-to-oldest.

Now you're ready: the memtable is the only place mutated in place — everything else is write-once. That fact is the whole paper.
8"Updatable surface area" — the core concept▾

Define this as the portion of a data structure that can be modified in place. In ART/B-trees, that's the entire tree — any node, anywhere. In an LSM, it's just the tiny memtable; SSTables are permanently frozen once written.

Now you're ready: small updatable surface area → few version numbers needed → they fit in scr → no flush penalty. This one idea explains every result in the paper.
9Copy-on-write vs. LSM (why not just CoW?)▾

Copy-on-write B-trees also avoid in-place updates — a write copies the node instead of mutating it. Sounds similar, but CoW must copy an entire node (and the path to the root) per update: write amplification Θ(leaf capacity). LSMs batch many updates before writing, giving much lower amplification.

Now you're ready: immutability alone isn't enough — you also need it to be cheap to produce. That's why the paper reaches for LSMs specifically, not CoW trees.
10Where this differs from tiering work you know▾

Unlike TPP/HeMem/Memtis-style page tiering (hot/cold placement across DRAM/NVM tiers), this paper isn't about where data lives — everything stays on the same CXL device. The axis here is coherence: which bytes hardware keeps synchronized across hosts, not which tier is faster.

Now you're ready: think of scr/lnr as a coherence tier, not a latency tier — the design pressure is "fit the mutable metadata," not "keep hot pages nearby."
The whole story in one place

Prism in a nutshell

The dilemma, the surprising fix, and the one extra trick that makes it fast.

Porting in-memory indexes (ART, B-trees) to partly coherent CXL forces a bad trade. Every node can be updated in place, so every node needs a version number in scr. Small nodes (ART) mean too many version numbers — they overflow scr and force cache flushes on every access. Large nodes (wide B-trees) fit their version numbers in scr, but now one write to a node falsely invalidates every other key sharing it. Both paths mean excessive flushes and collapsed throughput.

The paper's insight: the real culprit is updatable surface area — how much of the structure can be modified in place. SC-ART/SC-BTree have surface area equal to the whole tree. Log-structured merge trees, built decades ago for spinning disks, confine all in-place writes to one tiny memtable and freeze everything else as immutable SSTables. SSTables need no per-write coherence tracking at all — only a per-SSTable ID, checked once when a host first sees it.

Porting this idea gives SC-LSM, which significantly beats SC-ART outright and beats SC-BTree on write-heavy workloads — though the two stay close on read-heavy and read-only workloads. But plain LSMs have a classic problem: under heavy writes, compaction can't keep up, so reads must probe more and more overlapping SSTables. The paper's second idea, unique to the in-memory setting, is to make the LSM's upper layer updatable in place too — random writes are cheaper in memory than on disk. This Bounded Updatable Layer (BUL) absorbs repeated writes without minting new SSTables, as long as its version numbers still fit in scr.

The payoff: with a 128 MB scr and 100M keys, Prism beats SC-BTree by up to 9.4× on writes and SC-ART by up to 5.8× on reads, and beats Tigon-SWcc, an existing CXL system, by up to 15.1×, and CHIME-CXL, a ported RDMA index, by 3.6×–5.7× — though Megalon, which replicates the index into host-local DRAM, actually beats Prism on read-only YCSB-C — all with scr usage that stays flat regardless of dataset size.

🗂️ Key takeaways

  • Updatable surface area — not node size, not tree shape — is the variable that determines flush cost.
  • ART: surface area = whole tree, nodes small → version numbers overflow scr (<50% coverage at 100M keys).
  • B-tree: surface area = whole tree, nodes large → version numbers fit, but writes cause false invalidation.
  • LSM: surface area = the memtable only → fits scr trivially; SSTables need just an ID check, not per-write tracking.
  • BUL extends the updatable region carefully — bounded so its fine-grained version numbers still fit in scr — cutting compaction pressure.
  • The memtable is inverted into a cache for hot keys (not a write buffer), filtering out "one-hit wonders" before they waste scr.
  • Result: up to 9.4× over SC-BTree, 5.8× over SC-ART, and 15.1× over Tigon-SWcc specifically (Megalon still edges out Prism on read-only YCSB-C) — with scr usage independent of dataset size.
Six everyday pictures

How to think about Prism

Read in any order — each ends with where the picture stops being true.

The core idea · Updatable surface area

A whiteboard vs. a printed book

Erase-and-rewrite a whiteboard and everyone in the room has to notice and re-read it. A printed book never changes, so once you've read a page you can trust your memory of it forever. ART/B-trees are whiteboards everywhere; LSMs are books everywhere except one sticky note (the memtable).

Where it breaks: a real whiteboard doesn't scale in size the way a B-tree node does — the trade between "many small notes" and "one big note" is the paper's actual dilemma, not captured by a single whiteboard.
False invalidation · Wide B-tree nodes

One fire alarm evacuates the whole floor

If a whole office floor shares one fire alarm, a small kitchen mishap forces everyone out — even people three offices away who weren't affected. A wide B-tree node is that alarm: change one key, and every host caching any key in that node must flush and re-fetch the entire node.

Where it breaks: a real alarm is rare; writes in a write-heavy workload are constant, so the "evacuation" here happens continuously, not as a one-off event — that's why SC-BTree's throughput collapses, not just dips.
The fix · Memtable + SSTables

A daily mail tray vs. a sealed warehouse

A small in-tray gets checked constantly for changes — cheap because it's small. Once a batch of mail is boxed, sealed, and shipped to the warehouse, nobody re-opens the box; you just note which box number holds what. The memtable is the tray (coherent, tiny); SSTables are the sealed boxes (immutable, tracked only by ID).

Where it breaks: warehouse boxes are permanent until discarded by compaction, but a real warehouse doesn't periodically re-merge boxes to reduce their count — that housekeeping (compaction) is unique to LSMs and costs bandwidth.
The refinement · Bounded Updatable Layer

An overflow parking lane, not the whole street

Letting cars park anywhere solves congestion but you lose track of who's where. Instead, add one bounded overflow lane where you do track every space precisely, while the rest of the street stays exactly as marked (immutable). BUL is that lane — bigger than the memtable, but capped so its per-node version numbers still fit in scr.

Where it breaks: BUL isn't free extra capacity — sizing it too large means its version numbers spill out of scr, reproducing SC-ART's original problem inside the lane itself.
Filtering · scr-aware memtable

A VIP lounge, not a general waiting room

If anyone can sit in the lounge, it fills with one-time visitors and the regulars get pushed out. Prism's memtable only admits keys promoted from BUL after a second write — a one-hit wonder never gets a seat, so scarce scr space is reserved for genuinely hot keys.

Where it breaks: a lounge bouncer decides instantly; Prism only learns a key is "hot" after it's already been written twice, so the first write always pays the BUL-path cost.
The known cost · L0 accumulation

Searching every unsorted inbox pile

If mail gets boxed faster than it's filed away, you accumulate loose piles at your desk — and finding one letter means checking every pile. That's L0 under heavy writes: overlapping SSTables pile up faster than compaction files them into non-overlapping levels, so reads must probe more of them.

Where it breaks: BUL and the memtable-as-cache reduce how fast piles form, but they don't eliminate the pile-up at very high, unskewed write rates — Prism still slows down there, just less than plain SC-LSM.
The full explanation

How Prism actually works

From the failed ports, to SC-LSM, to the BUL refinement, to the read/write paths.

1 · Why SC-ART and SC-BTree fail

Both ports use the standard trick: keep per-node version numbers in scr, nodes and data in lnr. With 100M keys, ART has ~40M nodes (mostly the smallest Node4 type); a 128 MB scr covers well under half of them. The rest force a flush on every access, coherent or not. Widening B-tree nodes (fan-out 128) fixes the fit, but a single-key write now bumps one version number shared by all ~128 keys in that node — every host caching any of them must flush and re-fetch. Small nodes: overflow. Big nodes: false invalidation. Both are excessive flushes.

2 · SC-LSM — confining updates to a memtable

Port an LSM the same way: memtable entirely in scr (hardware coherence, zero software overhead), SSTables in lnr. An SSTable never changes after creation, so it needs only a strictly-increasing ID in scr's manifest — a host flushes an SSTable's region only the first time it sees a new ID, never again during that SSTable's life. This sidesteps per-node version tracking entirely for the bulk of the data.

3 · The remaining LSM problem — compaction can't keep up

Under write pressure, the memtable flushes to L0 faster than compaction drains L0 into L1. L0 SSTables overlap in key range (each came from an independent flush), so a read may have to probe every L0 file. The paper measures this directly: at 5% writes, reads probe 15 SSTables on average; at 50% writes, 49.

4 · BUL — absorbing repeat writes before they become SSTables

Instead of flushing straight to L0, the memtable flushes into BUL, an in-place-updatable ART in lnr. A repeated write to the same key just overwrites its BUL entry — no new SSTable. Only genuinely cold keys, identified by a clock-sweep over each node's access bit, get flushed to L0, one SSTable at a time. Because BUL is bounded, its fine-grained per-node version numbers (the 64-bit word above) still fit in the scr budget.

💡
Why this only works in memory: on disk, in-place updates mean random I/O, which is exactly what LSMs were invented to avoid. In CXL memory, random writes aren't prohibitively expensive, so trading a little more updatable surface for far fewer compactions is a good deal.

5 · The memtable inverted into a cache

Naively, all writes enter the memtable and it bulk-flushes to BUL when full — wasteful, since one-hit-wonder keys occupy scr and then get pushed out. Prism inverts this: new keys go directly to BUL; a key is only promoted into the memtable once it's written a second time (proof it's hot). Eviction from the memtable happens incrementally via LRU, not in an expensive bulk flush.

6 · Coherence across tiers, and the read/write paths

Each tier keeps its own coherence rule: the memtable needs none (hardware covers scr); BUL uses per-node version numbers; SSTables use per-SSTable IDs in the manifest. Transitions between tiers are ordered so a key becomes visible under its new tier's rule before it disappears from the old one — so a reader can never see the key vanish.

# write path
if key in memtable: update in place, promote to LRU head
elif key exists in BUL: update in place, promote to memtable, delete from BUL
else: insert into BUL directly           # one-hit wonders never touch scr

# read path — stop at first hit
check memtable → check BUL → check L0 (all files, newest→oldest)
              → check L1..Ln (≤1 candidate per level, via manifest key-ranges)
🗂️
Every design choice — bound BUL, invert the memtable, order transitions carefully — exists to keep the set of things needing fine-grained coherence tracking small and fixed, no matter how large the dataset grows.
Follow the numbers

Worked examples

Four traces using the paper's own figures.

① Why SC-ART's version numbers overflow at 100M keys

Each version word is 64 bits (8 bytes). scr is 128 MB. ART has ~40M inner nodes at 100M keys, ~4M at 10M keys. Does scr cover them?

  1. Capacity: 128 MB ÷ 8 B/word = 16M version entries fit in scr.
  2. At 10M keys (~4M nodes): 4M ≤ 16M → fits comfortably, near-full coverage.
  3. At 100M keys (~40M nodes): 16M / 40M ≈ 40% coverage — matches the paper's "coverage falls below 50%."
  4. The other 60% of version numbers spill into lnr, where every access — hit or not — requires a flush, since a host can't tell if an lnr-resident version number is stale without reading it.
🗂️
Insight: the overflow isn't a tuning problem — it's structural. Any tree with a node-per-few-keys design will eventually outgrow a fixed-size scr as the dataset scales.

② Prism's fixed 128 MB scr budget

Unlike SC-ART, Prism's scr usage doesn't grow with dataset size. How is 128 MB spent?

  1. Manifest: 2 MB — SSTable IDs, levels, key-range boundaries. Tiny because SSTables are large (few MB each), so there are relatively few of them.
  2. Memtable: 64 MB — an ART holding only promoted, frequently-written keys.
  3. BUL version numbers: the remaining 62 MB — one 8-byte word per BUL node → 62 MB ÷ 8 B ≈ 7.75M nodes of headroom, regardless of how many keys sit in the (much larger, lnr-resident) SSTable layer.
  4. Total: 2 + 64 + 62 = 128 MB, fixed — the dataset can grow into SSTables without touching this budget at all.
💡
This is the structural fix for problem ①: bound the region that needs fine-grained coherence, and let everything else live in coarse-grained, ID-tracked SSTables.

③ How much BUL cuts L0 pressure

Plain SC-LSM probes 15 SSTables per read at 5% writes and 49 at 50% writes (Fig. 4). Adding BUL changes this how much?

  1. SC-LSM at 5% writes: 15 SSTables probed per read — L0 already has meaningful overlap.
  2. SC-LSM + BUL at 5% writes: only 2 SSTables probed — a 7.5× reduction, because repeated writes never reach L0 at all; they're absorbed in place.
  3. At 50% writes: SC-LSM's 49-SSTable probe count still climbs, but SC-LSM+BUL "probes significantly fewer," and full Prism (with the hot-key memtable filtering writes further upstream) reduces read latency again beyond SC-LSM+BUL alone (Fig. 11).
  4. Net effect: two independent levers — BUL (absorb in BUL) and the memtable-as-cache (absorb before BUL) — both shrink the number of SSTables a read must ever look at.

④ Peak throughput gains, end to end

Tying the design back to §7's headline numbers, with a 100M-key dataset and 128 MB scr:

  1. Read-only: Prism reaches up to 6.3× SC-ART's peak throughput (version-number flushes) and modestly beats SC-BTree (faster ART-based SSTable lookups vs. B-tree traversal).
  2. Write-heavy (YCSB-A, 50% writes): Prism beats SC-BTree by 7.4× and beats SC-ART by 5.6× — SC-BTree's false invalidation and SC-ART's flush overhead both compound with more writes.
  3. Against external systems: Prism beats Tigon-SWcc by 8.6× to 15.1× across workloads (Tigon must migrate whole tuples in/out of CXL when scr fills) and beats CHIME-CXL by 3.6×, 5.1×, and 5.7× on the three workloads measured (CHIME flushes twice per leaf access to verify version numbers).
  4. Ceiling check: against an unrealistic SC-ART given unlimited scr, Prism matches it on write-heavy YCSB-A and reaches 83–88% of it on read-heavy workloads — despite using only 128 MB.
Test yourself

Practice problems

Each answer ends with the misconception it checks.

Problem 1 · easy
Why can't you just make scr bigger to fix SC-ART's overflow problem?
Show answer
Hardware coherence mechanisms (snoop filters, back-invalidation) become prohibitively expensive past a few hundred MB — that's why scr is small in the first place. Growing scr isn't a software knob; it's the exact hardware constraint the paper works around.Misconception: that scr size is a tunable parameter of the software design. It's a hardware ceiling the software must live within.
Problem 2 · medium
SC-BTree with fan-out 128 fits all its version numbers in scr. Why does it still lose badly on write-heavy workloads?
Show answer
Fitting version numbers only solves the overflow problem, not the granularity problem. With 128 keys per node, one write bumps a version number that every host caching any of those 128 keys must now treat as stale — false invalidation. At 50% writes, this collapses SC-BTree to 1.9M ops/s, below even SC-ART.Misconception: that "version numbers fit in scr" is sufficient for good performance. Fitting solves one failure mode (overflow) but can trade it for another (false invalidation).
Problem 3 · medium
Why don't SSTables need a version number per key, the way BUL nodes do?
Show answer
SSTables are immutable after creation — once written, their contents never change during their lifetime. The only coherence event that can happen is the entire SSTable being deleted and its memory region reused, which is handled by a single, strictly-increasing ID per SSTable, not per key.Misconception: that "on lnr" automatically means "needs fine-grained coherence tracking." It only does if the data can change; immutable data needs at most a coarse existence/identity check.
Problem 4 · hard
Why is making BUL in-place updatable a "non-starter for disk-based LSMs" but fine for Prism?
Show answer
In-place updates require random writes. On disk, random I/O is the exact overhead LSMs were invented to avoid — accepting it would defeat the purpose. In CXL memory, random writes aren't as expensive as on disk (no seek penalty), so that disk-era objection weakens — but it isn't free: BUL still pays its own cache-flush/coherence costs to keep version numbers valid, and Prism can still slow down under very high, unskewed write rates as BUL and L0 accumulate pressure. The trade is favorable, not costless.Misconception: that LSM design principles (avoid random writes) transfer unchanged to memory, or that removing the disk-seek penalty makes in-place updates free. The reason for the original principle weakens in memory, but a new, smaller cost (coherence flushes) takes its place.
Problem 5 · medium
A one-hit-wonder key is written once and never again. Trace its path through Prism's tiers.
Show answer
It goes directly into BUL (not the memtable, since promotion requires a second write). It sits there until the clock sweep finds its access bit unset (cold), at which point it's flushed to an L0 SSTable. It never occupies scr's precious memtable space.Misconception: that all writes pass through the memtable first. Only repeat-written keys ever reach the memtable; new keys start in BUL.
Problem 6 · hard
On YCSB-E (range scans) at 5% writes, SC-BTree beats Prism, but from 10% writes onward Prism wins — by 6.0× at 50% writes. Explain both halves.
Show answer
At low write ratios, SC-BTree suffers little false invalidation, and its large sorted nodes make sequential range scans cheap — a structural advantage over LSMs, which must merge results across multiple SSTables and tiers. As the write ratio rises, false invalidation dominates SC-BTree's cost (it degrades 8× from 5% to 50% writes), while Prism's scan overhead grows more slowly, so the crossover favors Prism from roughly 10% writes onward, reaching 6.0× higher throughput by 50% writes.Misconception: that one index is "just better" at range queries. The right answer depends on the write ratio — LSMs trade scan efficiency for write robustness.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is this the same problem as DRAM/NVM tiering (TPP, HeMem, Memtis)?▾
No — those systems decide where a page lives across latency tiers. Here, all data lives on the same CXL device; the split is about which bytes hardware keeps coherent across hosts (scr) versus not (lnr). It's a coherence-capacity problem, not a placement/hotness problem.
Q2Why does an LSM, built for spinning disks, help here at all?▾
Because the property that made LSMs good for disks — confining random writes to a small buffer and freezing the rest — happens to be exactly the property partly coherent memory needs: a small mutable region (fits in scr) and a large immutable region (needs no per-write tracking in lnr). The original motivation (avoid disk seeks) is different from the new one (avoid coherence flushes), but the mechanism transfers.
Q3What exactly is "updatable surface area"?▾
The portion of a data structure that can receive in-place modifications. In ART/B-trees it's the entire tree (any node can be written). In an LSM it's just the memtable. Smaller surface area means fewer things need coherence metadata, which is the entire design lever this paper pulls.
Q4Does Prism replace Bloom filters like RocksDB uses?▾
No — Prism skips them entirely. Bloom filters exist to avoid disk I/O on negative lookups; in CXL memory, probing an SSTable's internal ART index is already a cheap memory access comparable in cost to a Bloom filter check, so the extra memory overhead isn't worth it.
Q5Why does BUL need to be "bounded" — what breaks if it's unbounded?▾
BUL's coherence relies on a per-node version number in scr, same mechanism as SC-ART. If BUL grows without limit, its version numbers eventually spill into lnr too — reproducing SC-ART's original overflow problem inside what was supposed to be the fix.
Q6How does Prism guarantee correctness when a key moves between tiers?▾
Every transition (promotion, eviction, compaction) is ordered so the key becomes visible under its new tier's coherence rule before it's removed from the old tier. A reader that catches the key in both places briefly always finds identical values, and the read path checks tiers newest-first, so it never returns stale data. The authors also built and fuzzed a Python model of the protocol to confirm this.
Q7Does Prism always win?▾
No. SC-BTree wins on range scans only at very low write ratios (around 5%) because B-tree nodes scan more cheaply than merging across SSTables; Prism takes over from about 10% writes onward, reaching 6.0× higher throughput at 50% writes. Megalon also wins on pure read-only workloads because it replicates the index into each host's local DRAM, bypassing CXL for lookups entirely — at the cost of per-host memory overhead that grows with host count.
Q8What happens with a host or device failure?▾
Prism assumes fail-stop: any host or CXL device failure halts the entire system, with no recovery, since all state is in memory. Durability is explicitly out of scope — the same assumption made by Tigon.
