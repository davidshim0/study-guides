Zero-cost is a slogan. Instructions are the receipt

A 100 GbE NIC driver, built twice — once in C, once in safe Rust — turns Rust's safety guarantees into a per-packet instruction count, and shows exactly which checks send you the bill.

📄 Bagchi, Nanda, Burtsev · PLOS '26 🎓 Assumes some Rust/systems background — primers cover the rest ⏱ ~25 min read
🦀

Compile-time safety (ownership, lifetimes) is genuinely free. Anything that depends on a runtime value — a bound, a null, an overflow — has to be checked, and checking costs real instructions.

Before you begin

Quick glossary + eight primers

The acronyms first, then the concepts. Skip anything you already know.

1What this driver actually does▾

A user-space, DPDK-style driver polls an RX descriptor ring for completed packets, looks each one up in a shadow slot array, refills the ring with a fresh buffer from a LIFO free-buffer pool, rewrites the L2 header, and hands the original buffer to the TX ring. TX completions return buffers to the pool.

Now you're ready: every "safety check" in this paper lives somewhere in that loop — indexing the slot arrays, popping the free pool, incrementing counters.
2Ownership, borrowing, lifetimes — the free part▾

Rust's compiler tracks who owns a value and how long references to it stay valid, entirely at compile time. No runtime bookkeeping, no reference counting for ordinary references — this really is "zero-cost."

Now you're ready: the paper's whole point is that this free part is not the whole story — a second category of checks depends on runtime values and can't be resolved statically.
3Bounds checks▾

Indexing a slice with a dynamic index (slice[i]) compiles to an implicit assert(i < slice.len()) before the access — a load, a compare, and a branch to a panic path.

Now you're ready: get_unchecked() suppresses this, letting the paper isolate its exact cost.
4Option<T> and niche optimization▾

Option<&T> can represent None using an invalid bit-pattern of the pointer itself (e.g. null) — no extra tag byte needed. Option<usize> can't, since every bit pattern is a valid integer.

Now you're ready: that's why .expect() on a pointer-shaped Option compiles to a cheap null test, not a separate discriminant load.
5Panics vs. Result<T>▾

A panicking .expect() and an explicit .ok_or()? compile to the same comparison and branch — they just jump to different targets (abort vs. an error return).

Now you're ready: so if Result-based code is slower, the check itself isn't the reason — something else changed.
6Inlining▾

The compiler folds small helper functions directly into their caller, avoiding call overhead and enabling further optimization. Anything that blocks inlining — like a changed return type — can ripple into extra loads/stores elsewhere.

Now you're ready: this is the hidden mechanism behind the paper's costliest safety feature.
7Fat pointers▾

A pointer to a dynamically-sized type (a slice, a trait object) carries a second machine word — a length or a vtable pointer — alongside the address.

Now you're ready: widening any reference this way can raise register pressure even before you touch a safety check.
8Regression-based cost attribution▾

Rather than trust raw instruction counts, the authors fit cycles-per-packet to a linear model of instruction count, store count, and a design-specific indicator, then validate it with leave-one-out cross-validation.

Now you're ready: this is how they show a store costs roughly 5× an ordinary instruction — a fact invisible from instruction counts alone.
The whole story in one place

The paper in a nutshell

What "zero-cost" covers, what it doesn't, and how much the gap actually costs.

Rust's marketing pitch is that safety is free: ownership, borrowing, and lifetimes are enforced at compile time with no runtime trace. That part is true. But bounds checks, null checks on Option<T>, integer-overflow checks, and explicit error handling all depend on runtime values the compiler can't fully reason about — so they compile to real, executed instructions.

The authors measure exactly how much by building near-identical C and Rust drivers for an Intel E810 100 GbE NIC and stripping away every confound: no kernel, no allocation or synchronization on the fast path, same data structures, same buffer-management pattern. At batch size 64, their best safe Rust variant hits 93% of unsafe C's throughput while executing ~12% more instructions per packet (129 vs. 115) — and its only extra runtime cost is bounds and null-pointer checks.

Layering on more safety keeps costing: enabling overflow checks costs a further 7.2%; replacing panics with explicit Result<T> propagation costs a further 10.5% — not because the checks themselves are expensive, but because returning Result<T> blocked inlining and added stores. A regression model built from instruction, store, and design-specific counts explains cycles far better than instruction count alone (R²=0.996), assigning a plain instruction ~0.063 cycles but a store an extra ~0.28–0.66 cycle premium on top.

🦀 Key takeaways

  • Compile-time ownership/borrowing/lifetimes are genuinely free; bounds, null, overflow, and error checks are not.
  • Best safe Rust: 93% of C's throughput, 12% more instructions (129 vs. 115 at batch 64).
  • Overflow checks: −7.2%. Panic-free explicit errors: −10.5% — mostly from lost inlining, not the check itself.
  • Instruction count alone under-explains cost: a store costs roughly 5× a plain instruction in the fitted model.
  • A widened (16-byte) buffer reference in a more complex Rust design nearly doubles the modeled per-store cost (0.35 → 0.73 cyc), pointing to store-buffer saturation.
Six everyday pictures

How to think about Rust's safety tax

Each stands alone. Every card ends with where it breaks.

Compile vs. runtime · Zero-cost

Blueprint vs. inspector

An approved blueprint (ownership, lifetimes) is checked once, at design time — free forever after. An inspector who visits the building every single day (a bounds check) is a recurring cost, paid on every access.

Where it breaks: most Rust checks are actually cheap — the visit takes three instructions. The analogy shouldn't imply every runtime check is expensive; just that it's not free.
Option<T> · Niche optimization

Reusing the porch light

Instead of installing a separate "someone's home" indicator, you reuse the porch light itself: off = nobody home. Option<&T> reuses null the same way — no extra tag needed.

Where it breaks: only works if the "light" has a state that's otherwise invalid (a pointer can be null). An integer has no unused bit pattern to spare — Option<usize> needs a real extra tag.
Panics vs. Result<T> · Inlining

Two staircases, same first step

A panic and an explicit Result check both start with the identical comparison and branch — like two staircases sharing the same first step before splitting. The expensive part isn't the branch; it's that the Result-returning function couldn't be folded into its caller.

Where it breaks: the analogy is about the check site only. The real cost (extra stores, −10.5%) happens elsewhere, in code that no longer gets inlined — not on the staircase itself.
Fat pointers · DSTs

Shipping label with the weight printed on

A thin pointer is a box with just an address. A fat pointer (a slice reference) is a box with its weight printed right on the label — convenient, but the label itself takes space, everywhere the box travels.

Where it breaks: C would need to carry that "weight" (a length) separately anyway — the comparison isn't free-vs-costly, it's implicit-and-scattered vs. explicit-and-bundled.
Regression model · Store premium

The moving invoice

A mover doesn't just charge per box — a box that needs climate-controlled storage costs extra. Likewise the cost model charges ~0.063 cyc per instruction, but a store instruction carries an extra ~0.28 cyc premium.

Where it breaks: the "storage surcharge" isn't fixed — it roughly doubles (0.35 → 0.73 cyc/store) once the warehouse (store buffer) is already busier, as it is in the more complex widened-pointer design.
Instruction cascade

A layered tollbooth

Unsafe Rust pays one toll (basic execution). Safe Rust adds a booth for bounds checks. Turning on overflow checks or explicit errors adds another booth further down the same road — each one measured separately by disabling it and re-timing the drive.

Where it breaks: tollbooths cost the same regardless of what's in the car; here the "toll" per booth differs by what kind of instructions it adds (a booth that only checks costs little; one that blocks inlining costs a lot).
The full explanation

How the measurement actually works

From the driver's fast path to the regression model that attributes cost per instruction class.

1 · The fast path being measured

All variants implement the same buffer-management loop used by DPDK/ixy-style drivers: poll RX, look up the buffer in a shadow slot array, refill with a fresh buffer from a LIFO pool, rewrite the L2 header, submit to TX, and reclaim on TX completion. No allocation or synchronization sits on this path — the only differences across variants are how buffer references are represented and which safety checks are enabled.

2 · What a bounds check + null check actually costs

The paper's Figure 2 disassembles one tx_slots update. Restoring the omitted bounds check adds a load, compare, and conditional jump; the subsequent .expect() on the swapped-out Option adds a null test and its own jump.

// Safe Rust source
let old_buf = std::mem::replace(&mut self.tx_slots[idx as usize],
    Some(buf.into_in_flight())).expect("missing tx parked slot");

// Generated assembly (Intel)
mov rsi, [rsp+0xe48]   // bounds: load tx_slots.len()
cmp rsi, rdi           // bounds: idx < len ?
jbe  panic             // bounds: panic
mov rax, [rsp+0xe40]   // reload slots base (register pressure)
mov r13, [rax+rdi*8]   // replace(): read old slot
mov [rax+rdi*8], rbx   // replace(): write new slot
test r13, r13          // .expect(): None test
je   panic             // .expect(): panic if None
🔎
Five instructions total for this one site (3 bounds-check, 2 null-check) — light individually, but they add up: across the affected accesses in Rust|Safe(RefPool), checks like this total +15 instructions (114 → 129) relative to the unsafe variant.

3 · Isolating each feature's cost

The authors build a cascade: strip all checks with get_unchecked_mut(), then add them back one feature at a time, holding everything else fixed.

The puzzle: +19 instructions (overflow) costs 7.2%, but +18 instructions (errors) costs 10.5%. Nearly the same instruction delta, different cost — because errors add mostly stores (lost inlining), while overflow adds ALU/branch instructions. Instruction count alone doesn't explain cycles.

4 · The regression model

Fitting cycles/pkt at batch 256 to instruction count (I), store count (S), and a PtrArith indicator (X):

cyc/pkt = 20.7 + 0.063·I + 0.283·S + 2.33·X
R² = 0.996 · LOOCV typical error 0.19 cyc/pkt (max 0.31)

// a bounds check: 3 non-store instructions (load, cmp, jmp)
cost ≈ 3 × 0.063 = 0.19 cyc   // "relatively lightweight"

// one store: base instruction + store premium
cost ≈ 0.063 + 0.283 = 0.35 cyc

A second model, fit on a more complex Rust design (a per-packet metadata array plus a widened 16-byte buffer reference — a 4-byte index + 8-byte base + 4 bytes padding), finds a much steeper store cost:

cyc/pkt = 16.38 + 0.071·I + 0.66·S
R² = 0.997 · LOOCV typical error 0.57 cyc/pkt (max 0.61)
store cost ≈ 0.071 + 0.66 = 0.73 cyc   // ~2× the RefPool store cost
💡
Why the jump? More stores on the critical path push the store buffer toward saturation; hardware counters point there directly. The simpler RefPool design stays below that limit, so its stores are cheaper.
Follow the numbers

Worked examples

Four calculations, straight from the paper's own figures.

① Recomputing the headline claim

  1. Instructions: Rust|Safe(RefPool) = 129, C|RefPool = 115. Ratio = 129/115 = 1.122 → +12.2% more instructions, matching the abstract's "~12%."
  2. Throughput: 36.87 Gbps / 39.60 Gbps = 0.931 → safe Rust hits 93.1% of C's throughput — matching the abstract's "93%" exactly.
🦀
More instructions, less-than-proportional throughput loss: 12% more work costs only ~7% throughput — because most of the added work (bounds checks) is cheap, non-store work.

② Same instruction delta, different cost — why?

  1. Overflow: +19 instructions, −7.21% throughput. Errors: +18 instructions, −10.5% throughput.
  2. Overflow's added instructions are mostly ALU compares and branches (checked arithmetic) — cheap per the model (~0.063 cyc each).
  3. Errors' added instructions are mostly stores, introduced because losing inlining forces values to memory instead of registers — each carrying the ~0.28–0.66 cyc store premium.
  4. Same count, different instruction class → different cost. This is exactly why the paper needed a regression model, not just an instruction tally.

③ Pricing a bounds check vs. a store

  1. Model: cyc/pkt = 20.7 + 0.063·I + 0.283·S + 2.33·X.
  2. A bounds check = 3 non-store instructions (load, cmp, jmp): cost ≈ 3 × 0.063 = 0.189 cyc.
  3. One store instruction: cost ≈ 0.063 (as an instruction) + 0.283 (store premium) = 0.346 ≈ 0.35 cyc — the paper's own stated figure.
  4. A store costs roughly 1.8× a whole 3-instruction bounds check.

④ The store-buffer jump in the complex design

  1. RefPool-family model store cost: 0.35 cyc. Metadata-array/widened-pointer model: 0.071 + 0.66 = 0.73 cyc.
  2. 0.73 / 0.35 ≈ 2.1× — nearly double, for the same kind of operation (a store), just in a design with more stores already competing for the store buffer.
  3. The 16-byte widened buffer reference (4-byte index + 8-byte base + 4 bytes padding) is exactly the kind of "seemingly simple" representation change the abstract warns about.
💡
The lesson generalizes beyond Rust: store-buffer pressure, not instruction count, is often the real ceiling on a tight packet-processing loop — relevant to any cycle-budgeted systems code, safety checks or not.
Test yourself

Practice problems

Try each before opening the answer.

1 · easy
Is Rust's ownership/borrowing system "zero-cost" in the same sense as its bounds checks?
Show answer
No — ownership, lifetimes, and trait-bound checking are resolved entirely at compile time with no runtime trace, genuinely free. Bounds/null/overflow checks depend on runtime values and compile to executed instructions. "Zero-cost" describes the first category, not the second.Misconception: that "Rust is zero-cost" is a blanket claim covering all safety. It only covers what's decidable statically.
2 · easy
Rust|Unsafe(RefPool) executes fewer instructions than C|RefPool (114 vs 115) yet is 3.67% slower. Why doesn't fewer instructions mean faster?
Show answer
Instruction count is only one term in the cost model — store/load mix, register allocation, and compiler codegen choices (e.g. how each language computes pool offsets) all shift cycles independently of raw count. The paper's own regression model needed store count and a design-specific term precisely because instruction count alone was insufficient.Misconception: instruction count is a reliable proxy for speed. The paper's central empirical finding is that it isn't.
3 · medium
Compute the throughput cost of overflow checks vs. explicit error handling, both relative to Rust|Safe(RefPool) (36.87 Gbps). Which is cheaper, and does its smaller instruction delta explain why?
Show answer
Overflow: (36.87−34.21)/36.87 = 7.2%. Errors: (36.87−33.00)/36.87 = 10.5%. Overflow is cheaper despite adding more instructions (+19 vs +18) — so the instruction delta doesn't explain the ranking. The real driver is instruction class: overflow adds ALU/branch instructions; errors add stores from lost inlining.Misconception: ranking safety features by instruction count added. Rank by what kind of instructions they add instead.
4 · medium
In the Figure 2 disassembly, one instruction just reloads the slot-array base address into a register that was already available moments earlier. What does this reveal about "a bounds check is just one comparison"?
Show answer
It's an understatement. That reload happens because the bounds-check sequence and the subsequent access compete for registers — the base address gets evicted and must be refetched. A bounds check's true cost includes this kind of register-pressure side effect, not just the compare-and-branch at the check site itself.Misconception: a check's cost is fully captured by counting the instructions at its check site. Register pressure can add cost elsewhere in the same function.
5 · hard
Why can Option<&T> encode None for free but Option<usize> cannot?
Show answer
Niche optimization needs an invalid bit-pattern of the payload type to repurpose as the "empty" marker. A reference is never null in valid Rust, so the all-zero pattern is free to mean None. An integer has no invalid bit pattern — every 64-bit value is a legitimate usize — so Option<usize> needs a separate discriminant, costing extra space and a separate tag update.Misconception: all Option<T> wrappers are free. Only pointer-like payload types have a spare bit pattern to exploit.
6 · hard
Using cyc/pkt = 20.7 + 0.063·I + 0.283·S + 2.33·X, a new feature adds 4 extra store instructions. How many extra cycles/pkt does the model predict, and how does that compare to naively counting those as 4 ordinary instructions?
Show answer
Correct: each store is both an instruction and a store, so cost = 4×(0.063+0.283) = 4×0.346 = 1.384 cyc/pkt. Naive (treating them as ordinary, non-store instructions): 4×0.063 = 0.252 cyc/pkt. The naive method undercounts by 1.132 cyc/pkt — more than 5× too low.Misconception: counting instructions is enough to predict cost. Store instructions carry a premium the naive method misses entirely — exactly the paper's justification for the regression model.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Is Rust's zero-cost promise a lie?▾
No — it's accurate for what it actually claims: ownership, borrowing, and lifetimes cost nothing at runtime. It just doesn't cover properties that depend on runtime values (array bounds, null checks, overflow), which necessarily need dynamic checks in any safe language.
Q2Where does the 12% instruction overhead at batch 64 come from?▾
Restoring the bounds and null-pointer checks that get_unchecked_mut() had suppressed — 15 instructions across the affected array accesses, taking Rust|Unsafe(RefPool)'s 114 to Rust|Safe(RefPool)'s 129 (129/115 ≈ 1.12 vs. C's 115).
Q3Why isn't unsafe Rust exactly as fast as C, if it has fewer instructions?▾
Instruction count alone doesn't determine cycles — store/load mix and compiler codegen differences (e.g. how offsets are computed) matter too. Rust|Unsafe(RefPool) is 3.67% slower than C|RefPool despite one fewer instruction.
Q4Why do overflow checks cost more than bounds checks?▾
Overflow checks add more instructions per site (19 vs. 15) and the compiler uses a heavier instruction sequence for them; bounds checks are just load+compare+branch, "relatively lightweight" per the paper.
Q5Why is avoiding panics the single most expensive feature tested?▾
Not because the check changes — a panic and a Result check compile to the same comparison and branch. It's expensive because giving hot-path helpers a Result<T> return type blocked the compiler from inlining them, adding stores elsewhere.
Q6Is this a kernel driver?▾
No — all variants run as user-space processes with direct device passthrough, deliberately factoring out kernel and framework overhead so the measured differences are attributable to language safety mechanisms alone.
Q7What's the difference between RefPool and PtrArith?▾
RefPool tracks buffers with raw pointers (or safe references) into the packet pool. PtrArith tracks them with u32 indices instead, converting to an address only when writing a DMA descriptor — the design closest to the ixy driver study.
Q8Does Rust ever beat C in this study?▾
Yes — Rust|Unsafe(PtrArith) is faster than C|PtrArith at batch 64 (and 2.5–3.6% faster at larger batches) because Rust's noalias guarantee lets the compiler keep base addresses in registers, while C spills and reloads them; adding restrict to the C code didn't help.
Q9How did the authors attribute cost to specific instruction types?▾
They fit a linear regression of cycles/packet against instruction count, store count, and a design-specific indicator, validated with leave-one-out cross-validation (R²=0.996–0.997, typical error under 0.6 cyc/pkt), then cross-checked coefficients with an independent replication.
Q10What would close the remaining gap between safe Rust and C?▾
The authors point to compiler improvements — especially better inlining of functions returning Result<T> — and microarchitectural support such as greater store-buffer or register capacity to make dynamic checks and richer type-level safety state cheaper on the fast path.
