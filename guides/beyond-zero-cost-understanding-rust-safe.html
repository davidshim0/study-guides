Safety that's almost free — until you count the stores

A 100 GbE driver, built twice — once in C, once in safe Rust — shows exactly where "zero-cost" abstractions stop being free: bounds checks, panics-vs-Results, overflow checks, and fat pointers.

📄 Bagchi, Nanda, Burtsev · PLOS'26 🎓 Assumes you've written a driver or a fast-path loop before ⏱ ~25 min read
🦀

Lean, C-idiomatic safe Rust costs ~12% more instructions and hits 93% of C's throughput. Panics-as-Result and overflow checks cost far more — not because the checks are heavy, but because of what they do to inlining and the store buffer.

1What "zero-cost abstraction" actually promises▾

The slogan means: what you don't use, you don't pay for, and what you do use, you couldn't hand-code any cheaper. It does not mean every safety property is free — some (ownership, lifetimes) are enforced entirely at compile time, but others (bounds, nullability) require a runtime check.

Now you're ready: this paper measures exactly the second category — the checks that survive into the compiled binary.
2Ownership, borrowing, lifetimes — compile-time, no GC▾

Rust tracks who owns a value and who may borrow it (shared-immutable or one exclusive-mutable, never both) so the compiler can prove when a value is safe to free — no garbage collector, no reference-counting on ordinary references.

Now you're ready: this part really is free at runtime. The paper's overheads come from what's left over after this static layer.
3Bounds checks on indexing▾

slice[i] compiles to an implicit assert(i < slice.len()) before the access. Unsafe accessors like get_unchecked() skip it — the paper uses these to isolate the check's exact cost.

Now you're ready: a bounds check is a load + compare + branch — three instructions, cheap on its own (Figure 2).
4Option<T>, niches, and None▾

Option<T> models nullable values. For pointer-like T, Rust can reuse an invalid bit pattern (a "niche," e.g. null) to encode None for free — no extra tag byte. Taking a value out (.take()) still needs a store to mark the slot empty.

Now you're ready: .expect() unwrapping an Option costs one test + one branch to the panic path.
5Panics vs. Result<T>▾

A panic aborts on failure — fine in userspace, forbidden in kernels (no unwinding across C/Rust FFI). The safe alternative, returning Result<T> and propagating errors with ?, generates the same comparison/branch as a panic check — the target differs, not the check itself.

Now you're ready: the real cost of Result isn't the check — it's what it does to inlining (Section 4).
6Overflow checks▾

Release builds normally skip integer overflow checks. Enabling -C overflow-checks (or using checked_add/saturating_add) adds a handful of instructions per arithmetic op to detect wraparound before it silently corrupts an index or count.

Now you're ready: few checks, but each touches the hot arithmetic path directly — hence a disproportionate throughput hit.
7Thin vs. fat pointers▾

A pointer to a fixed-size type is one machine word (thin). A pointer to a slice, string, or trait object carries extra metadata (length or vtable) — two words (fat). Fat pointers cost more registers, stack space, and cache footprint per reference.

Now you're ready: even a deliberately widened 16-byte buffer handle (Section 4) measurably changes the generated code.
8The poll-mode driver fast path▾

A DPDK/ixy-style userspace driver polls RX descriptors for a batch of packets, tracks in-flight buffers in shadow rx_slots/tx_slots arrays (since hardware overwrites the descriptor's address field), and recycles freed buffers through a LIFO free-list allocator — no allocation or locking on the hot path.

Now you're ready: every driver variant in the paper implements exactly this loop — only the buffer-reference representation and checks differ (Figure 1).
The whole story in one place

Rust safety in a nutshell

What actually costs cycles, and why the cost isn't uniform.

Rust's headline claim is that safety is free at compile time — ownership, borrowing, and lifetimes leave no trace in the binary. But not every safety property can be proven statically: indexing needs a bounds check, nullable values need a niche test, and panic-avoidance needs explicit error handling. The paper isolates each of these costs using several functionally identical C and Rust implementations of a 100 GbE user-space driver.

The headline result: a carefully written safe Rust driver (Rust|Safe(RefPool)) runs 12% more instructions than unsafe C (129 vs. 115) yet reaches 93% of its throughput — its only overhead is a handful of bounds and null checks. But stacking on overflow checks (-7.2%) and panic-avoiding Result<T> (-10.5%) costs far more than the checks themselves predict, because Result<T> blocks inlining and forces extra stores onto the critical path.

A regression model ties it together: each instruction costs ~0.063 cycles/packet, but each store costs an extra 0.283 (simple design) to 0.66 (store-buffer-saturated design) cycles/packet on top of that — stores, not checks, are where the real money goes.

🦀 Key takeaways

  • Lean, C-idiomatic safe Rust: +12% instructions, 93% of C throughput — bounds + null checks only.
  • Bounds checks are cheap in isolation: 3 instructions, <4% throughput loss in both C and Rust.
  • Overflow checks cost disproportionately more (>7%) because they sit directly on hot arithmetic.
  • Result<T> for panic-avoidance blocks inlining → extra stores → -10.5%, despite identical branch code to panics.
  • Each store costs ~0.28–0.66 cycles/packet beyond its own instruction cost — the store buffer, not the check, is the bottleneck.
  • Fat/widened references increase register pressure and store traffic even with no added logic.
Six everyday pictures

How to think about Rust's safety cost

Each stands alone. Every card names where it stops being accurate.

Bounds checks · light touch

A turnstile, not a checkpoint

A subway turnstile glances at your card and lets you through in under a second — that's a bounds check: load the length, compare, branch. It barely slows the crowd. That's why bounds-checked C and safe Rust both lose under 4% throughput.

Where it breaks: turnstiles don't compound. Stack five of them (bounds + overflow + null + niche + Result) at the same doorway and the crowd does slow down — the paper's stacked variants show exactly this.
Niche optimization

Using the empty seat, not a new sign

You don't need a separate "occupied?" sign if an empty seat is unmistakably empty. Rust's Option<&T> reuses null itself as the "nothing here" marker — no extra tag byte, no extra memory. It's genuinely free.

Where it breaks: not every type has an "obviously empty" state — Option<usize> has no invalid bit pattern to steal, so it needs a real extra tag.
Result<T> and inlining

Toll booths between highway lanes

A highway flows fastest with no exits merging traffic. Give a function's boundary a "you must check my return type" contract (Result<T>), and the compiler often stops inlining it into its caller — like forcing every car through a toll plaza instead of a continuous lane. Extra stores appear at each booth.

Where it breaks: the toll itself (the check) isn't the delay — it's identical machine code to a panic check (Figure 3). The slowdown is purely the lost merge.
Fat pointers

A backpack vs. a backpack with a luggage tag

A thin pointer is just an address — a backpack. A slice reference also carries a length — the same backpack with a tag stapled on. One extra word doesn't sound like much, but multiply it across every argument, register, and cache line and it adds up.

Where it breaks: C pays this cost too whenever it needs a length alongside a pointer — the tag isn't a Rust tax, it's a data-representation tax that C usually just pays less visibly.
Store-buffer pressure

A checkout lane with a tiny conveyor belt

Loads are easy — reading a price tag doesn't block anyone. Stores are like placing items on a short conveyor belt: once it fills, the next customer must wait even if the register itself is fast. Widened references and metadata arrays add stores faster than the store buffer can drain them — costing far more per store (0.66–0.73 cyc) than a plain instruction (0.06).

Where it breaks: the simplest RefPool design never fills the belt, so its measured store cost looks cheap (0.283) — the analogy only bites once you add enough stores to saturate it.
Overflow checks

A tripwire on every step of a tightrope

Walking a tightrope safely means checking your footing at every step, not just at the ends. Overflow checks touch every arithmetic op on the hot loop's counters — a small check, but repeated so often and so close to the critical path that its cost outweighs a one-time bounds check.

Where it breaks: unlike a tightrope, some steps can use saturating_add() to avoid the "fall" (panic) entirely — trading a branch for a clamp, at similar cost.
The full explanation

How it actually works

Section by section, following the paper's own driver internals and measurements.

1 · The fast path (Figure 1)

Every variant implements the same loop: poll RX descriptors for a bounded batch, look up the packet buffer via a shadow slot array (hardware overwrites the descriptor's address field), refill that slot from a LIFO free-buffer pool, rewrite the L2 header, and hand the buffer straight to TX — tracking it in tx_slots until the TX-completion path returns it to the pool.

2 · Bounds checks, up close (Figure 2)

A single tx_slots[idx] update: the paper's assembly shows a load of the slot array length, a compare, and a conditional jump to the panic path (the check) — then a separate load-then-store to swap the value, plus a None test for .expect(). Five extra instructions total for this one access.

mov rsi,[rsp+0xe48]   // bounds: load tx_slots.len()
cmp rsi,rdi           // bounds: idx < len ?
jbe  panic            // bounds: branch to panic
mov rax,[rsp+0xe40]   // reload slots base (register pressure)
mov r13,[rax+rdi*8]   // replace(): read old slot
mov [rax+rdi*8],rbx   // replace(): write new slot
test r13,r13          // .expect(): None test
je   panic            // .expect(): panic if None

3 · Panics vs. explicit errors compile to the same branch (Figure 3)

Swapping .expect() for .ok_or(DriverError::...)? produces the identical comparison and jump — only the jump target changes (panic handler vs. error handler). The static code at each target differs, but neither executes on the hot path. The real cost shows up elsewhere: the Result<T> return type stopped two hot helper functions from being inlined, adding 18 instructions and forcing extra stores.

4 · Overflow checks (Figure 4)

Enabling overflow checks on a simple decrement (self.free -= 1) adds four instructions: load, test for underflow, conditional panic branch, then decrement and store-back only on the safe path. Multiplied across five hot-path counters, this is enough to cost 7.2% throughput in Rust — more than bounds checks, despite touching fewer sites.

5 · The regression models

Instruction count alone doesn't predict cycles — stores do the real damage. Fit at batch size 256:

cyc/pkt = 20.7 + 0.063·I + 0.283·S + 2.33·X    // Eq.1 — RefPool/PtrArith family, R²=0.996
cyc/pkt = 16.38 + 0.071·I + 0.66·S            // Eq.2 — store-buffer-saturated metadata-array design, R²=0.997

I = instructions/packet, S = stores/packet, X = 1 for PtrArith variants (a fixed addressing-mode cost). Loads cost close to an average instruction (~0.1–0.18 cyc); stores cost 3–10× that, and the premium grows once the design pushes enough stores to saturate the store buffer.

💡
Why this matters for tiering work: the same store-buffer-saturation effect shows up in NVM/CXL write paths — a "cheap-looking" extra metadata write (e.g. a hotness counter per page) can cost far more than its instruction count suggests once concurrent stores compete for buffer slots.
Follow the numbers

Worked examples

Four calculations straight from Table 1 and the paper's regression models.

① Cost of one bounds check, C vs. Rust

C|RefPool: 113 instr, 39.60 Gbps. C|Safe(RefPool) adds a manual bounds macro: 123 instr, 38.91 Gbps. Rust|Unsafe(RefPool): 112 instr, 38.14 Gbps. Rust|Safe(RefPool): 127 instr, 36.87 Gbps.

  1. C bounds cost: 123 − 113 = 10 instructions; throughput 39.60 → 38.91 = −1.74%.
  2. Rust bounds cost: 127 − 112 = 15 instructions; throughput 38.14 → 36.87 = −3.3%.
  3. Why Rust pays more per check: Rust adds a comparison and reload of the base pointer (register pressure, Figure 2 L4) at every site; C's manual macro is leaner because the programmer controls it directly.
🦀
Even the "expensive" Rust bounds check is under 4% — the paper's real overheads live elsewhere.

② Safe Rust vs. unsafe C, end to end

Rust|Safe(RefPool): 129 instr (abstract's headline number), 93% of C|RefPool's throughput.

  1. Instruction overhead: (129 − 115) / 115 ≈ 12% more instructions than unsafe C.
  2. Throughput retained: 36.87 / 39.60 ≈ 93.1% — matches the paper's headline exactly.
  3. Sources of that gap: five bounds checks + two null-pointer checks (.expect()) — nothing else. No overflow checks, no blocked inlining yet.

③ Predicting Rust|Safe(RefPool+Errors) with Eq. 1

Table 1 row 7: I=145, S=28, X=0 (RefPool family). Measured cyc/pkt ≈ 37.2.

  1. Instruction term: 0.063 × 145 = 9.14 cyc/pkt.
  2. Store term: 0.283 × 28 = 7.92 cyc/pkt.
  3. Total: 20.7 + 9.14 + 7.92 = 37.76 cyc/pkt — within ~0.6 of the measured 37.2, inside the model's LOOCV error.
  4. Interpretation: the store term (7.92) is almost as large as the instruction term (9.14) despite S being only ~19% of I — stores are disproportionately expensive.

④ Why a store costs 0.35 cyc in one design, 0.73 in another

A store is also an instruction, so its true marginal cost combines both coefficients from whichever model applies.

  1. Simple RefPool design (Eq. 1): 0.063 (as an instruction) + 0.283 (as a store) = 0.346 ≈ 0.35 cyc/pkt per store — matches the abstract's "modeled total cost of approximately 0.35 cycles per packet."
  2. Metadata-array + widened-pointer design (Eq. 2): 0.071 + 0.66 = 0.731 ≈ 0.73 cyc/pkt per store — matches the paper's stated figure exactly.
  3. Why the jump: more stores per packet push the store buffer toward saturation; hardware counters confirm store-buffer pressure as the mechanism, not the instructions themselves.
💡
Same operation, more than double the marginal cost — purely a function of how many other stores are competing for the buffer that cycle.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A colleague says "Rust's zero-cost abstractions mean safety is free." Where exactly does this claim hold, and where does the paper show it breaks down?
Show answer
It holds for statically provable properties — ownership, borrowing, lifetimes — which leave no runtime trace. It breaks down for properties that depend on runtime values: array bounds, nullable pointers, integer overflow, and panic-avoidance all require runtime checks or restructuring, measurable as instructions, stores, and lost inlining.Misconception: that "zero-cost" means "no runtime checks anywhere." It means "no cost beyond what a careful C programmer would also pay for the same guarantee."
Problem 2 · medium
Bounds checks and overflow checks are both small, local checks, yet overflow checks cost more throughput (7.2%) than bounds checks (3.3%) in Rust. Why?
Show answer
Bounds checks are added at a handful of indexing sites. Overflow checks touch every arithmetic increment/decrement on the hot-path counters — more sites, each directly on the critical arithmetic, with four extra instructions per site rather than three.Misconception: that "small check" implies "small aggregate cost." Frequency and placement on the critical path matter more than the size of any one check.
Problem 3 · hard
Figure 3 shows panic-handling and explicit-error-handling (ok_or) compiling to the same comparison and branch. Yet Rust|Safe(RefPool+Errors) is 10.5% slower than Rust|Safe(RefPool). Reconcile this.
Show answer
The check itself isn't the cost — the two variants execute identical comparison/branch instructions. The slowdown comes from a side effect: giving hot-path helper functions a Result<DriverError> return type prevented the compiler from inlining them into their callers, adding 18 instructions (mostly stores) that wouldn't otherwise exist.Misconception: that identical instructions at the check site mean identical performance. Compiler decisions triggered by a type signature can dominate the check's own cost.
Problem 4 · medium
Using Eq. 1 (cyc/pkt = 20.7 + 0.063·I + 0.283·S + 2.33·X), predict cyc/pkt for a RefPool-family variant with I=120, S=20.
Show answer
X=0 (not PtrArith). 20.7 + 0.063×120 + 0.283×20 = 20.7 + 7.56 + 5.66 = 33.92 cyc/pkt.Misconception: forgetting the fixed intercept (20.7) or the X term for PtrArith variants — both are needed for an accurate prediction.
Problem 5 · easy
Rust|Unsafe(PtrArith) is slightly faster than C|PtrArith. What's the mechanism, given both skip bounds checks?
Show answer
The compilers compute pool offsets differently. Rust's noalias annotation lets the compiler keep base addresses in registers; C's restrict qualifier had no equivalent effect, so C spills and reloads base addresses more often.Misconception: that "unsafe Rust" and "C" should always perform identically when checks are removed — aliasing information available to the compiler still differs.
Problem 6 · hard
Why does the metadata-array/widened-pointer design have a different regression model (Eq. 2) with no PtrArith indicator term, and a much larger store coefficient?
Show answer
Eq. 2 comes from synthetic experiments that hold the algorithm fixed and vary instruction mix directly, so there's no separate addressing-scheme family to account for (no X term needed). Its larger store coefficient (0.66 vs 0.283) reflects that this design pushes enough stores per packet to approach store-buffer saturation, where each additional store queues behind others rather than draining freely.Misconception: that a bigger coefficient means a "worse model." It reflects a genuinely different operating regime (store-buffer pressure), not a modeling error — both models fit their own data with R²>0.99.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is Rust "slow" compared to C for systems code?▾
Not inherently. The paper's best safe Rust driver reaches 93% of C's throughput with lean, C-idiomatic code. The gap widens only when additional safety features (overflow checks, explicit error handling) or non-idiomatic representations (widened pointers, metadata arrays) are layered on.
Q2What exactly is left unchecked at compile time?▾
Anything depending on a runtime value: whether an index is in bounds, whether an Option holds a value, whether an arithmetic op overflows, and whether a Result is Ok or Err. Ownership, aliasing, and lifetimes are fully static.
Q3Why do panics and explicit Result checks compile to the same instructions?▾
Both need a comparison and a conditional branch to decide "did this fail?" — the only difference is the branch target (panic handler vs. your error-handling code), and that target's code never executes on the hot path anyway.
Q4So why is explicit error handling slower?▾
Because giving a function a Result<T> return type discouraged the compiler from inlining it, adding real instructions (mostly stores) at the call site — an indirect cost, not the check itself.
Q5Are bounds checks the main source of Rust overhead?▾
No — they're the cheapest safety feature measured (under 4% throughput loss in both C and Rust). Overflow checks and blocked inlining from error handling cost far more.
Q6What's the practical lesson for writing fast safe Rust?▾
Use lean, C-idiomatic data structures and representations that preserve niche optimizations; expect the remaining overhead to be dominated by bounds and null checks, which are small; watch out for Result<T> on hot-path helpers and for widened/fat references, which have compounding effects.
Q7Why do stores cost more than loads or ALU ops?▾
Loads can often be satisfied speculatively or from cache with less serialization; stores must go through the store buffer, which has finite capacity. Once enough stores queue up per packet, the buffer saturates and each additional store queues behind others rather than draining freely.
Q8Does this generalize beyond this one driver?▾
The authors are explicit that this is a single-driver, single-platform study; they call for broader replication. The regression models were validated by an independent nine-variant replication that recovered coefficients within 10%, which is encouraging but not proof of generality.

Core terms
Bounds checkCompiler-inserted assertion (index < length) before an array/slice access; panics if false.
Niche optimizationReusing an invalid bit pattern (e.g. null) of a payload type to encode an enum discriminant (e.g. None) at zero extra size.

Result<T,E> propagationExplicit error handling via the ? operator, used to avoid panics; can inhibit inlining of the function it's added to.
Fat pointerA reference carrying metadata (length or vtable) alongside an address, for dynamically sized types.
Drop glueCompiler-generated destructor code run when an owned value goes out of scope.
Interior mutabilityTypes like RefCell/Cell/Rc/Arc that enforce or bypass borrowing rules at runtime instead of compile time.
Store-buffer pressureContention for the CPU's finite store queue when too many stores per packet are issued in a tight window.
Driver-specific terms
rx_slots / tx_slotsShadow arrays preserving buffer addresses that the NIC's DMA descriptor overwrites with status info.
