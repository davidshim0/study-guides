SOSP 2026 · A Field Guide

Trusting distributed code without proving it, and without slowing engineers down

S3 Express One Zone shipped a brand-new distributed metadata index. Instead of full verification or hope, a small formal-methods team built executable reference models, fuzzed them against the real system, and systematically explored concurrent schedules — then handed the whole thing to engineering.

📄 "Validating a High-Performance Cloud Object Store" · Fernando et al. 🎓 Some distributed-systems/concurrency background assumed ⏱ ~25 min read
🧪

Don't check one global property with one heavyweight tool — decompose correctness, and check each piece with the lightest technique that actually catches its bugs.
Then wire it into the pipeline so it can't rot.

1Why "lightweight" formal methods?▾

Full verification (proving code correct with machine-checked proofs, à la IronFleet or Perennial) gives the strongest guarantee but costs proof maintenance as code evolves. Lightweight formal methods instead write an executable reference model and test the real system against it — less certainty, far less friction, and something an engineering team (not just verification experts) can keep updating.

Now you're ready: this paper is a report on making that trade-off work at production scale, not a proof.
2Reference models and differential testing▾

A reference model implements the same interface as a real component, but simply — sequential, in-memory hash maps, only the non-error behaviors. Run the same operations against both; if the implementation's results ever diverge from the model's, that's a bug. This is "reftesting."

Now you're ready: the data path (§4) and control plane (§6) are validated with different flavors of this same idea.
3Property-based testing (proptest)▾

Instead of writing individual test cases, you define an "alphabet" of possible operations and let a tool generate random sequences of them, biasing toward interesting behavior (small key sets to force conflicts, more mutations, specific failure combinations).

Now you're ready: every test scenario in this paper — data path, control plane, persistent — is proptest-generated over some alphabet.
4Async Rust and cancellation safety▾

An async Rust function compiles to a state machine that only advances when polled, and can yield at any await. Crucially, it can be cancelled by simply being dropped (e.g. by select!) — with no exception and no cleanup except an explicit Drop impl. Multi-step updates can be left half-finished.

Now you're ready: if you've debugged a kernel or mm code path that can be interrupted mid-update, this is the same hazard class — just surfaced by Rust's cooperative scheduler instead of preemption.
5Stateless model checking (Shuttle)▾

Rather than running a test once, a stateless model checker controls the scheduler and re-runs it many times with different interleavings of concurrent tasks, replaying a failure deterministically when found. Since safe Rust has no data races, it's enough to explore interleavings only at await points.

Now you're ready: Shuttle is the tool; "rounds" (§3.2) are how the paper structures what gets interleaved.
6Serializability, the textbook version▾

A concurrent execution of transactions is serializable if it's equivalent to running them one at a time in some order. Concurrency-control theory builds a conflict graph: an edge between two transactions that touch the same data, oriented by which happened first; if the graph has no cycle, a valid serial order exists.

Now you're ready: §5's white-box algorithm is exactly this graph, extended to handle production behaviors (deletes, aborts, backups) that textbook definitions skip.
7Data path vs. control plane▾

The data path serves index reads/writes and has a clean request/response interface — perfect for a reference model. The control plane runs background loops (health checks, partition relocation, scaling) with no such interface, so it's checked differently: safety invariants that must hold always, and stability properties that must hold once things settle.

Now you're ready: this split is why the paper has two separate validation chapters (§4–5 and §6) instead of one model for everything.
8The deployment pipeline as a gate▾

Tests run at increasing cost/fidelity — fast in-memory tests on a laptop, larger Shuttle runs before merge, "longbake" tests at scale overnight, and persistent reftests running for months in pre-production — each an approval step that blocks promotion on failure.

Now you're ready: this staging is what lets shallow bugs get caught cheaply, before expensive stages ever see them.
The whole story in one place

The approach in a nutshell

What broke on the way from a single-node store to a distributed one, and how the team closed each gap.

The team's prior system, ShardStore, validated a single storage node with reference models, property-based testing, and Shuttle. S3 Express's new distributed metadata index broke each of those assumptions: it spans hosts, so it must tolerate crashes and network delays; it uses distributed transactions, so correctness means serializability, not just matching a sequential model; its async Rust runtime introduces cancellation safety as a new bug class Shuttle didn't support; its control plane has no request/response interface to model; and it was expected to keep evolving after launch across software versions.

The fix was not one bigger tool but the same lesson from ShardStore applied harder: decompose correctness and check each piece with the technique suited to it. The data path gets a reference model and reftesting. Transaction correctness gets a new white-box serializability checker built from production instrumentation (partition sequence numbers), because existing black-box checkers (Elle, Cobra) couldn't handle deletes, range queries, or aborted transactions that still leave visible effects. The control plane gets safety invariants and stability properties instead of a reference model. And persistent reftests run reference models for months against real deployments to catch bugs that only appear across software versions.

Shuttle itself needed extending — to support the production Tokio async runtime, and to inject cancellations and timeouts so cancellation-safety bugs could be systematically found rather than discovered in production.

The payoff: 76 bugs caught before production across three test layers, a validation framework that's just 16% of the implementation's code size, and — the paper's central result — sustained engineering ownership: the engineering team's share of validation commits grew from 41% to 84% over 2.5 years, and they've independently shipped conditional writes, object append, and atomic rename.

🍯 Key takeaways

  • Decompose correctness by component (data path / transactions / control plane) — check each with the lightest fitting technique, not one global property.
  • Reference models are executable, written in the same language/API as the implementation — so they can double as mocks before real code exists.
  • Serializability is checked white-box, using PSNs the implementation already emits — polynomial time, and it handles deletes/aborts/backups that black-box tools miss.
  • Rounds impose client-visible ordering, letting concurrent tests bound the search for a valid serial order.
  • Tests run in stages of increasing cost (sequential → Shuttle → longbake → persistent), each a pipeline gate.
  • Reftests-as-pipeline-gates is what kept models and code in sync for 2.5 years without the formal methods team.
  • Result: 76 bugs caught pre-production, 16% code overhead, and engineering ownership grew from 41% to 84%.
Six everyday pictures

How to think about the approach

Read in any order; each ends with where the picture stops being true.

Reference model · Differential testing

The stunt double

A simple, sequential model stands in for the real, concurrent implementation the way a stunt double stands in for the lead actor: not identical, but faithful enough on the moves that matter. Run both through the same script (operations); if they ever land differently, that's the bug.

Where it breaks: the double only mimics scripted moves — error cases like device failures aren't modeled, so the model can't catch bugs there.
Shuttle · Stateless model checking

Replaying a chess game from many openings

Instead of playing one game and hoping it's representative, you replay the same position from many different opening move orders, systematically, and record which lead to trouble. Shuttle does this with task scheduling: same test, many interleavings, deterministic replay of any failure.

Where it breaks: chess openings are finite and enumerable; schedules aren't — Shuttle samples a bounded number of them, so absence of a bug found isn't proof none exists.
Cancellation safety · The dropped call

Hanging up mid-sentence

Cancelling an async future is like the other party hanging up mid-sentence — no chance to say "wait, let me finish this thought." Whatever cleanup you didn't explicitly wire to happen on hangup (a Drop impl) simply doesn't happen, leaving state half-updated — exactly the block-cache bug in §4.2.

Where it breaks: a real hangup is rare and obvious; here it's routine (every losing branch of a select!), which is why it needs systematic injection, not intuition, to find.
Serialization graph · Whodunit ordering

A detective's timeline board

A detective pins events to a corkboard and draws arrows: "X happened before Y because Y's alibi mentions X." The serialization graph does the same with transactions — an edge for every conflict, oriented by hard evidence (partition sequence numbers), not guesswork. No cycle in the timeline means a consistent story exists.

Where it breaks: a detective can be wrong about an arrow's direction; here the PSNs make the direction a fact recorded by the system itself, not an inference.
Pipeline staging · Filters, coarsest first

A coffee filter cascade

Coarse grounds get caught by the first filter; only the finer particles reach the next, finer one. Sequential reftests catch obvious bugs in seconds on a laptop; Shuttle catches subtler interleaving bugs before merge; longbake and persistent reftests catch the rarest bugs that only surface at scale or over months — each stage only has to deal with what got past the one before.

Where it breaks: coffee filters are passive; here each stage is an active pipeline gate — a failure blocks promotion, it doesn't just get logged.
Ownership handoff · Passing the baton

Training wheels coming off

The formal-methods team rode alongside during design and peer-reviewed every model, then gradually let go — not all at once, but as engineers' share of commits climbed from 41% to 84% across successive feature launches. The bike (validation framework) was built sturdy enough to ride without a hand on the seat.

Where it breaks: training wheels come off completely; here the formal-methods team still maintains Shuttle and the serializability checker — the handoff is partial, not total.
The full explanation

How it actually works

From reference models through the serializability checker to persistent canaries.

1 · Reference models and the sequential/concurrent split

Each validated component (namespace, transaction library) gets its own reference model: same Rust API, but a sequential implementation using plain hash maps and arrays, and covering only non-error behaviors. Since the real index guarantees strong consistency, any concurrent execution must be equivalent to some sequential one — so correctness reduces to: does some serial replay of the reference model match the implementation's responses and final state?

2 · Rounds — structuring concurrent tests

Concurrency tests run as a sequence of rounds: each round spawns several clients running jobs (transactions, backups, relocations, crashes) concurrently under Shuttle, and the harness waits for all clients to finish before starting the next round. Background work (like checkpointing) can spill past a round's end, so Shuttle explores interleavings both within and across round boundaries.

3 · The serialization graph — building it white-box

For each transaction, the checker computes read/write sets: KeyAccess(map, keys) for specific keys touched, and MapPresence(map) for conflicts on a map's mere existence (e.g., one transaction creates a map another later deletes). Two transactions conflict if their sets overlap and at least one is a write. For every conflicting pair, an edge is added and oriented using partition sequence numbers (PSNs) — no guessing, since PSNs are ground truth emitted by the implementation.

RuleEdgeCondition
E1 write/writeT1 → T2commit PSN of T1 < commit PSN of T2 on that partition
E2 write/readTw → Tr or Tr → Twcompares writer's commit PSN vs. reader's read PSN
E3 backupT → B or B → Twhether T's writes on every partition are captured by the backup
E4 happens-beforeT1 → T2T1's round precedes T2's, or same client and T1 issued first
💡
Aborted transactions aren't dropped. Two concurrent Deletes of the same key: one succeeds, one aborts because it read the key already gone. The abort must still serialize after the success — drop it from the graph and you could miss a bug where both transactions wrongly abort.

4 · Replay and validation

Any topological order of the graph is replayed against the sequential reference model, comparing each operation's result to what was observed during the real concurrent run, then a full final-state comparison. Aborted transactions replay only to check their reads match. Failures that returned an error to the client but actually committed (e.g., after all 2PC participants durably prepared) are still included — determined by inspecting the durability of prepare-log entries, not the returned status.

🐛
Bug this caught: a coordinator queried about a transaction's status while it hadn't yet finished its own preparation would answer "Unknown" from stale on-disk state, causing one participant to abort while the coordinator later committed — a genuine split-brain outcome the graph replay exposed as a state mismatch (§5.4).

5 · Control plane and persistent reftesting

The control plane has no request/response interface, so it's checked with a partition tracker (a runtime monitor validating the "no double-loading" safety invariant continuously) and stability properties checked once the system quiesces (detected via progress events and an empty task queue). Persistent reftests extend this idea across time: a long-lived reference model runs for months against real pre-production infrastructure, checkpointed to S3 after each segment so it survives host restarts, catching cross-version bugs that short-lived tests structurally cannot.

Follow the numbers

Worked examples

Four traces through the paper's real figures.

① Sizing the validation framework

Implementation is 259K lines. Reference models: 4.8K. Reftest harness + checker: 35.6K. How big is validation, relative to the system it checks?

  1. Models alone: 4.8K / 259K ≈ 1.85% — under 2% of the implementation's size buys the oracle for every reftest.
  2. Harness + checker: 35.6K / 259K ≈ 13.7%.
  3. Total validation framework: (4.8K + 35.6K) / 259K = 40.4K / 259K ≈ 15.6%, matching the paper's reported ~16%.
🍯
Insight: the oracle (the model) is nearly ten times smaller than the machinery (harness, checker, orchestration) needed to run it against reality — sequential simplicity is cheap; systematically exercising concurrency is where the cost lives.

② The two-Deletes abort ordering

T1 and T2 both try to Delete the same key. T1 commits; T2 reads the key as already-absent and aborts. What must the serialization graph do?

  1. T2's read conflicts with T1's write (E2, write/read on the same key) — since T2 observed the deletion, T1's commit PSN must precede T2's read PSN.
  2. Edge direction: T1 → T2. T2 must serialize after T1.
  3. Why this matters: if the checker dropped T2 (a "textbook" abort), a bug where both deletes somehow reported failure (violating per-key linearizability, since one should have succeeded) would go undetected.
💡
This is exactly why the paper calls out that "aborted transactions cannot simply be dropped" (§4.2) — it's not an edge case, it's required for the per-key linearizability guarantee.

③ Reading the ownership handoff chart

Engineering's share of validation commits: 41% pre-launch → 59% (first perf work) → 77–80% (feature work) → 84% (recent perf work). What does the trend tell you?

  1. Pre-launch (41%): the formal-methods team, embedded from the start, still authors the majority of models and harness code.
  2. First post-launch features (59%): crossing 50% — engineers now write more validation code than the formal-methods team, within a year of launch.
  3. Complex new features — conditional writes, append, atomic rename (77–80%): engineers extend the models themselves for features the formal-methods team never touched.
  4. Recent performance work (84%): near-full ownership; formal-methods involvement is now occasional, not structural.
🍯
Insight: the growth isn't a single jump — it tracks each new feature as a fresh opportunity for engineers to practice extending the models, which is what the paper credits for it sticking.

④ The bug funnel, layer by layer

In-memory: 20. Shuttle: 46. Persistent: 10. Total: 76. What does each number actually mean?

  1. 20 in-memory bugs survived existing unit/integration tests — sequential reftesting alone still finds real bugs conventional tests miss.
  2. 46 Shuttle bugs survived all in-memory reftests — more than double the sequential layer, confirming that concurrency interleavings are where most subtle bugs hide (breakdown: 12 transaction-correctness, 15 concurrency, 16 error/edge-case, 3 state-management).
  3. 10 persistent-reftest bugs survived both prior layers entirely — these require real infrastructure, accumulated state, or cross-version interaction that no in-memory test, however long, could trigger (e.g. the ListObject throttling bug, §7.2).
  4. 76 total, all caught before reaching production, none counting bugs developers caught locally before ever committing.
💡
Each layer's count is the marginal value of adding that layer — the paper's argument for running all of them, not just the cheapest one.
Test yourself

Practice problems

Try each before opening the answer; every one names the misconception it checks.

Problem 1 · easy
Why does the reference model stay sequential even though the real implementation is highly concurrent?
Show answer
Because the system is designed to guarantee strong (serializable/linearizable) consistency, any correct concurrent execution must be equivalent to some sequential one. So checking against a sequential model is sufficient — the hard part (finding which sequential order) is handled separately by the serialization graph, not by making the model concurrent.Misconception: that a concurrent system needs a concurrent model to validate it. The model can stay simple precisely because correctness means "equivalent to sequential."
Problem 2 · medium
A transaction returns an error to the client after a partition relocation, but the paper says it must still sometimes be included in the serialization graph as a commit. Why?
Show answer
A transaction can fail after all 2PC participants durably prepared but before the client learns the outcome — the system then drives it to commit in the background regardless of what the client saw. Its writes become visible to later transactions, so excluding it from the graph would make the checker miss real conflicts, and replay would diverge from the implementation's true state.Misconception: that a client-visible error means "no effect." Durability, not the returned status, determines a transaction's true outcome — determined here by inspecting prepare-log durability.
Problem 3 · medium
Why can't the team reuse an off-the-shelf black-box checker like Elle or Cobra?
Show answer
Elle infers write order by tracing the sequence of values a key has held, which requires append-only, unique-valued workloads — but S3 Express overwrites and deletes keys, destroying that value history. Cobra drops aborted transactions and range queries. Neither handles the production behaviors (deletes, range ops, meaningful aborts) this system needs, and lock-order-based approaches fail too, since lock-free transactions acquire no locks.Misconception: that any serializability checker will do. The choice of white-box (PSN-based) checking was forced by specific production behaviors existing tools explicitly exclude.
Problem 4 · hard
Explain, using E1–E4, why the graph having no cycle is enough to guarantee a valid serial schedule exists — and what role the E4 happens-before edges specifically play.
Show answer
E1 and E2 add an edge, correctly oriented by PSNs, for every pair of conflicting transactions — so if acyclic, any topological sort agrees with the concurrent execution on the order of every conflicting pair (conflict-equivalence), which is the definition of a valid serialization. E4 (round/client ordering) adds no new conflict information — it only further restricts which topological orders are allowed, by encoding ordering the test harness already knows is true. A cycle indicates either a genuine serializability violation or (rarely) over-constrained edges from E4.Misconception: that happens-before edges are what make the graph correct. Correctness (conflict-equivalence) comes entirely from E1/E2; E4 only prunes the search space of valid orderings.
Problem 5 · medium
The block-cache cancellation bug (§4.2) was exercised by reftests but not caught for a long time. What was actually wrong, and what fixed the test, not just the code?
Show answer
The bug (a dropped future leaving a stale pending_reads entry, permanently blocking that block) was reached by the tests, but the specification treated all errors as acceptable whenever error injection was enabled — masking the permanent unavailability as "just another injected error." The fix to the test was adding an availability check: after error injection, disable it and continue running; any persistent error in this "error-free" phase now surfaces as a failure.Misconception: that reaching buggy code in a test is the same as catching the bug. A weak specification can let a triggered bug pass silently — the fix here was tightening what counts as a failure, not adding coverage.
Problem 6 · easy
Why does the control plane get safety invariants and stability properties instead of a reference model?
Show answer
Reference-model reftesting needs a request/response boundary to compare against — the control plane instead runs asynchronous background loops (heartbeat monitors, bucket monitors, a task manager) with no such interface. So correctness is specified differently: invariants that must hold at every moment (no double-loading) and properties checked only once the system quiesces (every partition loaded on exactly one healthy worker).Misconception: that reftesting is a one-size-fits-all technique. The paper's core lesson is picking the technique that matches each component's shape — request/response gets reftesting, background loops get invariants.
Problem 7 · hard
Persistent reftests run for months, but the reference model lives in memory. What two mechanisms make this survive host restarts without unbounded replay cost?
Show answer
(1) Checkpointing: after each segment, the model is serialized durably to S3 and the operation log is cleared, so recovery only needs the latest checkpoint plus a bounded log tail, not a full replay from the start. (2) An operation log: each mutating operation is durably logged before being issued, so on restart the harness can replay just the log since the last checkpoint and determine the outcome of the last (possibly interrupted) operation by reading back the affected key.Misconception: that determinism alone (same seed → same segment) is enough to recover state cheaply. It's necessary but not sufficient — without checkpointing, replaying millions of operations per bucket per day would grow unboundedly.
Problem 8 · medium
A colleague argues the growth from 41% to 84% engineering-owned commits proves formal methods "got out of the way." What does the paper actually claim, and what's the more precise reading?
Show answer
The formal-methods team still maintains Shuttle and the serializability checker — the two pieces with genuine subtlety (constraint tuning for the graph, timeout-injection mechanics). What transferred was day-to-day model and test authorship for new features, not the underlying machinery. The precise claim is sustained shared ownership with a shrinking, not zero, formal-methods footprint.Misconception: that 84% means the formal-methods team is uninvolved. It means engineers own most feature-level validation work; core infrastructure maintenance persists.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1Is this full formal verification?▾
No. There are no machine-checked proofs of the production code. It's differential testing against an executable reference model, property-based test generation, and systematic (but bounded) exploration of concurrent schedules — "lightweight" precisely because it trades completeness for something an engineering team can maintain without proof expertise.
Q2Why not just use unit and integration tests?▾
The paper's own numbers answer this: 20 bugs survived existing unit/integration tests and were only caught by in-memory reftests, and another 46 survived those too, requiring Shuttle's systematic interleaving exploration. Hand-written tests don't explore concurrent schedules or generate the volume of randomized scenarios proptest does.
Q3What exactly is cancellation safety, in one sentence?▾
The property that an async operation leaves correct state even if it's dropped (cancelled) mid-execution at any await point — since Rust's cancellation has no exception-based cleanup, only explicit Drop implementations run.
Q4Why is checking serializability hard in general?▾
It's NP-complete in general (Papadimitriou 1979) — naively searching all orderings is intractable. The paper's white-box approach sidesteps this: because the implementation already assigns partition sequence numbers, edge direction is read off directly rather than searched for, making graph construction polynomial-time.
Q5What's the difference between a safety invariant and a stability property here?▾
A safety invariant (like "no double-loading") must hold at every instant, checked continuously by a runtime monitor. A stability property (like "every partition on exactly one healthy worker") only needs to hold once the system has quiesced after reacting to a perturbation — it's still technically a safety property, just checked at a different point in time.
Q6How do they know the system has quiesced?▾
Production code is instrumented to emit progress events when each monitor loop finishes an iteration; the harness waits until the task manager has no outstanding tasks, then runs one more iteration of each monitor to confirm no new tasks appear. Shuttle's depth bound on scheduling decisions catches systems that never quiesce (livelock), at the cost of possible false alarms if the bound is too tight.
Q7Why do persistent reftests matter if Shuttle already explores concurrency thoroughly?▾
Shuttle tests run on an in-memory stack that's fresh each time — they can't catch bugs that depend on real infrastructure, accumulated state over weeks, or the interaction of two different software versions (e.g., version N+1 misreading data written by version N). Persistent reftests trade concurrency-exploration power for that realism.
Q8Does this generalize beyond S3 Express?▾
The paper frames it as a general recipe: decompose a system by interface shape (request/response vs. background loops), write executable reference models in the implementation's own language, and gate deployment on reftests. The same shape of testing is relevant to any concurrent systems code where correctness bugs are subtle and expensive — including kernel or memory-management code with async-like interruption points.
Q9What counts as a "conflict" between two transactions?▾
Their read/write sets overlap (same map and either overlapping key sets, or one references the map's mere existence via MapPresence) and at least one side is a write. Two purely read-only accesses never conflict.
Q10Why is MapPresence its own kind of conflict?▾
Because a map's existence itself can be the contested resource — e.g. one transaction creates a map another later deletes — even though neither transaction touches any key inside it. Without a MapPresence entry, that ordering constraint would be invisible to the checker.
Q11What are the three biggest limitations the authors admit?▾
(1) They check functional correctness, not latency/throughput, and don't model error cases like resource exhaustion. (2) In-memory tests mock storage/networking and miss hardware-dependent bugs; persistent reftests run on real infrastructure but can't systematically explore concurrency. (3) Testing is fundamentally incomplete — randomized exploration gives no guarantee about which states remain unexplored.
Q12What's next for this line of work?▾
Two open threads: building domain-specific coverage metrics (developer-annotated semantic states, not generic line coverage) to measure what testing has and hasn't explored; and exploring AI-assisted theorem proving (the Lean prover) to gain confidence that the reference models themselves are correct, since today that's established only by manual peer review.

Core terms
