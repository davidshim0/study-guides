Why hardware virtualization isn't automatically faster

A field study of two real VMMs — one built from binary translation, one from Intel/AMD's new hardware — measuring where each one bleeds cycles.

⚡ TL;DR

  • VMware built a hardware-assisted VMM alongside its mature binary-translation (BT) software VMM, then measured both head-to-head on the same guest workloads — the paper discusses both Intel VT and AMD SVM architecturally, but the measured hardware is a VT-enabled Intel Pentium 4 672; AMD/SVM isn't benchmarked.
  • On the forkwait process-churn benchmark, the first-gen hardware VMM was ~2.9× slower than the software VMM (106.4s vs 36.9s vs 6.0s native) — hardware traps are stateless and costlier than BT's adaptive callouts.

1Popek & Goldberg's VMM criteria▾

A 1974 paper set three bars for calling something a VMM: Fidelity (guest software behaves as if native), Performance (most instructions run without VMM help), and Safety (VMM controls all real resources).

Crucially, they never said how to meet these — trap-and-emulate was just the obvious 1974 technique. x86 fails at trap-and-emulate but can still meet all three criteria via other means.

Now you're ready: this paper's whole point is that both BT and VT/SVM are legitimate VMMs by this definition — the fight is over which one hits the Performance bar better.
2De-privileging and why x86 resists it▾

Classic trap-and-emulate runs the guest OS at reduced privilege so every sensitive instruction traps. x86 breaks this in two ways: the guest can see it's de-privileged (via %cs's privilege bits), and some privileged instructions (like popf) silently do nothing instead of trapping when run unprivileged.

Now you're ready: these leaks are why x86 needed either a full interpreter/translator (software) or new CPU modes (hardware) — plain trap-and-emulate was never an option.
3Shadow structures and tracing▾

The VMM's privileged state (like page tables) differs from the guest's idea of it. On-CPU state is easy — just intercept the instruction. In-memory state, like page tables, is harder: any ordinary store can modify it with no trap.

The fix is tracing: write-protect the guest's page tables so any edit faults, letting the VMM keep its own shadow copy in sync.

Now you're ready: this trace mechanism is the single biggest source of overhead differences between the two VMMs in this paper.
4Hidden faults vs. true faults▾

When the guest touches unmapped memory, the shadow page table might simply not have an entry yet — a hidden fault, invisible to the guest, fixed by building the shadow entry. A true fault reflects the guest's own permission policy and must be forwarded to the guest.

Now you're ready: both VMMs must tell these apart on every fault — the paper's pgfault nanobenchmark measures exactly this path.
5Binary translation, in one sentence▾

Instead of running guest machine code directly, rewrite it just before executing it: mostly instruction-for-instruction ("IDENT"), except for control flow and privileged instructions, which get replaced with safe equivalents. Translated code is cached (the "TC") so translation cost is paid once, not every time.

Now you're ready: BT trades a one-time translation cost for near-native speed afterward — and lets the VMM choose how to translate each instruction.
6Adaptive translation — "innocent until proven guilty"▾

Most guest instructions are translated identically (fast, but traps on sensitive accesses like page-table writes). If one keeps trapping, the VMM re-translates it into a cheaper non-trapping form (a "callout") and patches old code to jump there — done once, amortized over every future execution.

Now you're ready: this is the software VMM's superpower — it can dynamically move any hot instruction off the expensive trap path. The first-generation hardware VMM can't do this (Paper §6.3).
7The hardware extensions: VMCB, vmrun, VM exit▾

VT/SVM add a "guest mode" that runs privileged guest code directly on real hardware. The VMM fills a VMCB with guest state and exit-trigger bits, executes vmrun, and the guest runs until some configured condition causes a VM exit back to the VMM.

Now you're ready: the VMM can choose which events exit (VMCB control bits), but unlike BT it can't replace one hot exiting instruction with a cheaper non-exiting path; every exit pays a full hardware round trip (its exact cost varies by exit type, see Table 1).
8Nested paging — the fix that wasn't there yet▾

First-gen VT/SVM gave the hardware VMM no help with MMU virtualization, so it still needed the software shadow-page-table machinery — just with costlier traps. Later "nested paging" (EPT/RVI) lets hardware walk guest-physical→host-physical mappings itself, in principle removing traces entirely.

Now you're ready: Section 7 of the paper is a forward-looking pitch for exactly this hardware feature — this guide's How It Works tab covers it.
The whole story in one place

Software vs. hardware virtualization, in a nutshell

The surprising reversal, and the mechanism behind it.

Since x86 can't do classical trap-and-emulate, VMware's software VMM uses binary translation: it rewrites guest kernel code on the fly, translating most instructions identically and only replacing the handful that need special care. Critically, it can adapt — when a translated instruction keeps trapping, the VMM re-translates it into a cheaper form.

Intel's VT and AMD's SVM then added a real hardware VMM mode: guest code runs directly, and only specific configured conditions force a VM exit back to the VMM. This should, intuitively, be strictly faster — no translation, no interpretation.

It usually isn't. Every VM exit is stateless — the hardware VMM must reconstruct what the guest was doing, typically via around ten vmreads and, in some cases, decoding the faulting instruction. The software VMM's adaptive translator instead moves hot, trapping instructions off the slow path (and can move them back if their behavior changes). And first-gen hardware offered no help with MMU virtualization, so the hardware VMM still needed shadow page tables and tracing — just with a costlier trap mechanism underneath.

The payoff of measuring instead of assuming: on the process-churn benchmark forkwait, native takes 6.0s; the software VMM takes 36.9s (6.1×); the hardware VMM takes 106.4s (17.7×) — almost 3× worse than software. Most workloads favor the software VMM; the exceptions with few I/O exits relative to syscalls — Apache-on-Windows and 2D graphics — favor the hardware VMM, with SPECjbb landing close to native for both.

🍯 Key takeaways

  • x86 isn't classically virtualizable — BT and VT/SVM are two different ways to still satisfy Popek & Goldberg.
  • BT can adapt a hot trapping instruction into a cheap callout; the hardware VMM has no such option, so each exit pays a full round trip every time.
  • Hardware VM exits are stateless — reconstructing guest context costs real cycles the software VMM avoids.
  • First-gen VT/SVM added no MMU support, so the hardware VMM inherited software shadow paging's cost — with pricier traps.
  • forkwait: native 6.0s, software VMM 36.9s (6.1×), hardware VMM 106.4s (17.7×).
  • Microarchitecture helps (Core cuts VM-entry cost 61%) but doesn't close the gap — future fix is nested paging (EPT/RVI).
Five everyday pictures

How to think about the two VMMs

Each stands alone. Every card ends with where the picture stops being true.

BT · Adaptive translation

A translator who learns your accent

A simultaneous interpreter starts by translating everything word-for-word. When one particular phrase keeps needing a slow, careful re-explanation, the interpreter learns a shortcut for it and uses that from then on. That's adaptive BT: guest instructions start "innocent" (translated identically); ones that keep trapping get permanently rerouted to a cheaper form.

Where it breaks: the interpreter can only learn shortcuts for patterns they've actually seen misfire — a brand-new phrase (a cold path in guest code) still pays full price the first time.
VT/SVM · Statelessness

Tech support with amnesia

Imagine calling tech support and, every single time, having to re-explain your whole setup from scratch because the rep remembers nothing from the last call. That's a VM exit: the hardware VMM must reconstruct guest context by reading VMCB fields and, in some cases, decoding the faulting instruction on every exit — no memory carried over, unlike BT's cached translations.

Where it breaks: real tech support reps are slow because of habit, not design; VM exits are stateless by architecture — it's a deliberate hardware/software boundary, not an accident.
Shadow paging · Tracing

A photocopy that must match the original

You keep a photocopy of someone's calendar and mirror every edit they make onto your copy. To notice edits, you write-protect their original page — any pen stroke faults, you copy the change, then let them continue. Both VMMs need this "photocopy" (shadow page table); the hardware VMM just pays a costlier fault to notice each edit.

Where it breaks: nested paging removes the photocopy entirely by letting hardware translate through both address spaces directly — no mirroring needed, at the cost of a deeper page-walk per miss.
Nested paging · Two-stage translation

Mail forwarded through two post offices

A letter addressed to a guest's virtual address must be re-addressed first to the guest's idea of physical memory, then re-addressed again to real physical memory — two independent postal systems, chained. Nested paging automates this chaining in hardware: for an M-level guest table and N-level nested table, a worst-case TLB miss costs up to M·N memory accesses.

Where it breaks: real mail forwarding is slow and manual; the paper is betting that large multi-level TLBs will hide most of this cost, the same way they already hide ordinary page-walk costs.
The core reversal

A specialist who forgets vs. a generalist who remembers

Hiring a narrow specialist who's blazing fast at exactly one task, but re-explains context from zero every time you call them, can lose to a generalist assistant who's a little slower per-task but remembers everything and skips the re-explaining. VT/SVM is the fast specialist for "run guest code directly"; BT is the generalist who remembers which instructions misbehave and routes around them.

Where it breaks: for pure system calls (no MMU involvement), the "specialist" (hardware) genuinely wins — it's only exits touching shared, coherency-sensitive state (page tables) where amnesia costs the most.
The full explanation

How it actually works

From x86's obstacles, through both VMM designs, to the future fix.

1 · Why x86 resists trap-and-emulate

Two concrete leaks break classical virtualization: (a) the guest can read its own privilege level out of %cs, revealing that it's been de-privileged; (b) instructions like popf silently no-op instead of trapping when run unprivileged, so the VMM never gets a chance to emulate the intended effect on virtual interrupt state. One such leak is enough to break support for unmodified binary-only guests like Windows.

2 · Software VMM: binary translation

The translator reads guest code in variable-size chunks (translation units, ending at a control-flow terminator or at a cap of 12 instructions), classifies bytes into instructions, and emits a compiled code fragment (CCF) — mostly IDENT (unmodified) except for control flow, PC-relative addressing, and privileged instructions. CCFs are cached in the translation cache (TC) and chained directly to each other, so steady-state execution rarely re-enters the translator. On a real 64-bit Windows XP boot/halt, this produces 229,347 64-bit TUs, 23,909 32-bit TUs, and 6,680 16-bit TUs — translated once, at roughly 2,300 cycles per x86 instruction (vs. 100–200k cycles per bytecode for an optimizing JIT).

💡
Adaptive translation: instructions that trap frequently (e.g., page-table writes) get retranslated to call out to a cheaper handler, and old code is patched with a forwarding jump — a one-time cost amortized over every future execution of that instruction.

3 · Hardware VMM: VMCB, vmrun, VM exit

VT/SVM add a genuine guest mode. The VMM fills a VMCB with guest register state and control bits describing which events should force an exit (page faults, TLB flushes, address-space switches, I/O instructions, accesses to traced page tables and memory-mapped devices), then executes vmrun. Guest code — including privileged instructions — now runs directly on hardware until a configured exit condition fires; the hardware then saves guest state to the VMCB, restores VMM state, and resumes in host mode.

4 · Why exits are so much costlier than traps

Compare the paper's nanobenchmarks (cycles; native / software VMM / hardware VMM): syscall 242 / 2308 / 246 — hardware wins because system calls run without VMM intervention. But ptemod (a page-table write) is 1 / 391 / 12733 — the hardware VMM must exit on every trace hit and pay the full round-trip, while BT's adapted callout runs in-line. pgfault is 1093 / 3927 / 11242 for the same reason: shorter software control-transfer path beats a full guest/host round trip.

5 · The future fix: nested paging

Nested paging (Intel EPT, AMD RVI) lets hardware translate guest-virtual → guest-physical → host-physical addresses itself, without VMM interposition on every page-table write. A TLB miss now costs up to M·N memory accesses for an M-level guest table and N-level nested table — more expensive per miss, but it eliminates tracing and its exits entirely, betting that large associative TLBs will absorb the extra walk depth the same way they already absorb ordinary multi-level page walks.

🍯
The trade being made: swap a per-write trace-fault tax (paid constantly) for a per-miss deeper-walk tax (paid rarely, and hidden by caching) — structurally the same bet OS designers make when they choose a page-table format for any multi-level address translation.

M1 · Classical virtualization: Popek and Goldberg, and trap-and-emulate

The three criteria. Popek and Goldberg (1974) say system software is a VMM if it has three properties. Fidelity: software on the VMM executes identically to its execution on hardware, barring timing effects. Performance: an overwhelming majority of guest instructions are executed by the hardware without VMM intervention. Safety: the VMM manages all hardware resources. The criteria say nothing about how; they define the goal.

Trap-and-emulate. In 1974 one implementation style was so common it was treated as the only practical one. The VMM runs the guest OS directly, but de-privileged (at a reduced privilege level). Any instruction that reads or writes privileged state then traps to the VMM, which emulates the instruction against the virtual machine's state (its saved image of the guest's registers) and resumes the guest. Traps come from two sources: the instruction type itself (the paper's example is out), or the VMM protecting a structure the instruction touches (the address range of a memory-mapped I/O device).

"Classically virtualizable" is the paper's own term for an architecture that can be virtualized purely with trap-and-emulate. The paper stresses that this is narrower than Popek and Goldberg's definition: x86 is not classically virtualizable, but it is virtualizable by their criteria, using binary translation (§3). Much confusion, they say, came from equating "virtualizable" with "trap-and-emulate works".

Invariant. The real privileged state of the CPU always belongs to the VMM; the guest's idea of that state lives in the VMM's image (the virtual CPU, VCPU). Every guest operation that touches privileged state must pass through the VMM. Assumption it rests on: every instruction that is sensitive (reads or changes privileged state, or behaves differently depending on it) traps when run de-privileged. If even one sensitive instruction runs silently without a trap, Fidelity breaks, and the VMM cannot even detect that it broke. (The formal "sensitive instructions must be a subset of privileged instructions" condition is Popek and Goldberg's theorem; this paper does not restate it.)

Where performance goes. Trap-and-emulate meets Performance only if traps are rare relative to ordinary instructions, and cheap. On modern CPUs traps are expensive: the paper measured a trap-and-emulate rdtsc at 2030 cycles on the P4 (§3.3). That number returns in M11. (Paper §2, §2.1)

M2 · Why x86 is not classically virtualizable: the specific instructions

The paper ignores the legacy "real" and "virtual 8086" modes and argues that even 32- and 64-bit protected mode fail, naming two obstacles:

  1. Visibility of privileged state. The current privilege level (CPL) is stored in the low two bits of the code segment selector %cs. Any instruction that reads %cs lets a de-privileged guest kernel see that it is not at CPL 0. Reading a segment register is not a privileged operation, so nothing traps.
  2. Lack of traps for privileged instructions at user level. popf ("pop flags") loads %eflags from the stack. In privileged code it changes both ALU flags (such as ZF) and system flags, including IF, the bit that controls interrupt delivery. A de-privileged guest kernel needs its popf to trap so the VMM can update the virtual IF. But a de-privileged popf, like any user-mode popf, "simply suppresses attempts to modify IF; no trap happens." The guest believes it re-enabled interrupts; the VMM never learns of it.

The paper adds that other obstacles exist, "but one obstacle is enough if it disrupts binary-only OS distributions like Windows." The point: if you cannot change the guest's code, a single non-trapping sensitive instruction that the guest really uses is fatal to pure trap-and-emulate.

Outside this paper (for context). Robin and Irvine (USENIX Security 2000, the paper's reference [21]) catalogued x86's sensitive-but-unprivileged instructions. Examples of the same two kinds: sgdt, sidt, sldt, smsw read privileged descriptor-table or control state at CPL 3 without trapping; pushf exposes IF; push %cs and moves from segment registers expose the CPL.

Three ways out, which frame the whole paper. (1) Do not run guest kernel code directly: interpret or binary-translate it so that virtual state (VCPU) and physical state (CPU) are separate (§3, the software VMM). (2) Change the hardware so the guest kernel can run directly at its expected privilege in a new mode, with sensitive operations either trapping or acting on hardware-kept virtual copies (§4, VT/SVM). (3) Change the guest (paravirtualization, §2.5 and §8), which the paper sets aside because it gives up unmodified and proprietary guests.

M3 · Shadow structures, tracing, true vs hidden faults

Primary vs shadow. The VMM's job is to give the guest an environment that matches its expectations even though the real privileged state differs. It does this by deriving shadow structures (used by the hardware) from guest-level primary structures (what the guest believes is in effect).

On-CPU state is easy. For privileged registers such as the page table pointer or the processor status register, the VMM keeps an image of the guest register and consults it whenever a guest operation traps.

Off-CPU state is hard. Page tables live in memory. Guest PTEs are privileged state because they encode mappings and permissions, yet "dependencies on this privileged state are not accompanied by traps": every guest memory reference depends on some PTE, and any ordinary store in the guest instruction stream can modify a PTE. Even DMA can modify it implicitly. Memory-mapped I/O devices have the same problem: almost any load or store can be an access to device state.

Tracing. To keep shadows coherent, the VMM uses hardware page protection on the primary structures. Guest PTE pages for which shadows have been built are write-protected; memory-mapped device pages are protected for both reads and writes. A trace fault is handled like a privileged-instruction trap: decode the faulting guest instruction, emulate its effect on the primary structure, and propagate the change to the shadow.

x86 page tables. x86 has 2-, 3- or 4-level hardware-walked page tables rooted at %cr3. The VMM runs the guest on shadow page tables, which protect the host from guest memory accesses. VMware's shadow page tables are a cache of the guest page tables: entries are built on demand. When the guest touches a previously untouched region, the hardware faults into the VMM, and the VMM classifies the fault:

  • True page fault: the guest's own PTEs forbid the access. Forward (reflect) it to the guest.
  • Hidden page fault: the guest's PTEs allow the access, but the shadow table has no entry yet. Build the shadow PTE and resume. It is "hidden" because it has no guest-visible effect.
on_hardware_page_fault(gva, access):          # reached directly (SW VMM) or via an exit (HW VMM)
  gpte = walk_guest_page_table(vcpu.cr3, gva)    # the guest's primary structure
  if not permits(gpte, access):
      inject_page_fault_into_guest(gva)          # TRUE fault
  elif access is write and page_of(gva) is traced:
      insn = decode(guest_pc)                    # TRACE fault
      emulate(insn) on the guest page-table page # update the primary
      update_or_invalidate_shadow_for(the PTE written)
  else:
      spte = derive(gpte)                         # HIDDEN fault: gPA → host page, rights ≤ guest rights
      install spte in shadow table
  resume guest

Invariant (this guide's statement of it). Every present shadow PTE grants no more than the guest's current PTE for that address, mapped through the VMM's own guest-physical to host mapping, and the guest cannot observe any difference. Hidden faults fill the cache; traces keep it from going stale when the guest edits its tables.

The three-way trade-off (§2.4). Traces are not free: each traced write is a fault. But avoiding traces entirely means the VMM cannot tell which shadow entries are stale, so on a guest context switch it must either throw shadow state away (paying many hidden faults to rebuild it) or "prevalidate" the shadow tables for the new context (an expensive context switch). So the VMM balances trace costs, hidden page faults and context-switch costs. The authors call striking this balance "surprising both in its difficulty and its criticality to VMM performance", and call tools that make the trade-off more forgiving "rare and precious". Adaptive BT (M11) is such a tool for the software VMM: it makes traced writes cheap. The hardware VMM lacks it (M21).

What would break. If the guest's page-table pages shared a page with ordinary hot data, every ordinary store there would also trace-fault, because protection is per page (inference). DMA writes are not caught by CPU page protection; the paper only lists DMA as a source of implicit modification, and in both of its VMMs devices are emulated models, so device DMA is performed by VMM code anyway (inference). (Paper §2.2 to §2.4)

M5 · The software VMM's translator: six properties and why each is needed

Why translate at all. An interpreter separates virtual state from physical state: it can stop the CPL leaking and can implement popf against the virtual CPL and IF. So interpretation satisfies Fidelity and Safety. It fails Performance: the fetch-decode-execute loop may burn hundreds of physical instructions per guest instruction. Binary translation keeps the interpreter's semantic precision but runs fast, so "a VMM built around a suitable binary translator can virtualize the x86 architecture and it is a VMM according to Popek and Goldberg." The paper notes parallels: JVM JIT compilers, and simulators such as Shade and Embra that combine subject code with analysis code.

M6 · Translation units, CCFs and the IDENT / non-IDENT split

Pipeline. (1) The translator reads guest memory at the guest PC and classifies the bytes as prefixes, opcodes or operands, producing one IR object per guest instruction. (2) It accumulates IR objects into a translation unit (TU), stopping at 12 instructions or at a terminating instruction (usually control flow). The fixed cap lets all translator data structures live on the stack without risk of overflow; in practice the cap is rarely reached, so a TU is usually a basic block. (3) Each translator invocation consumes one TU and produces one compiled code fragment (CCF) in the translation cache (TC). The correspondence from guest address to TC address is kept in a hash table.

Invariant. Translated code computes exactly what the guest code would compute natively on its virtual state, with all guest-visible values (registers, memory, the stack's contents) identical to native. Only the location of the code and the handling of privileged state differ. (Paper §3.2)

M7 · The isPrime example, traced in full

The paper's example is deliberately ordinary code, because "privileged instructions are rare even in OS kernels", so BT performance is decided by how regular instructions translate.

int isPrime(int a) {
    for (int i = 2; i < a; i++) {
        if (a % i == 0) return 0;
    }
    return 1;
}

Compiled to 64-bit x86 (the paper writes the destination operand first, so mov %ecx, %edi means %ecx = %edi; the argument a arrives in %edi):

isPrime:  mov  %ecx, %edi     ; %ecx = a
          mov  %esi, $2       ; i = 2
          cmp  %esi, %ecx     ; is i >= a?
          jge  prime          ; jump if yes
nexti:    mov  %eax, %ecx     ; %eax = a
          cdq                 ; sign-extend into %edx
          idiv %esi           ; a / i, remainder in %edx
          test %edx, %edx     ; remainder zero?
          jz   notPrime       ; jump if yes
          inc  %esi           ; i++
          cmp  %esi, %ecx     ; is i >= a?
          jl   nexti          ; jump if no
prime:    mov  %eax, $1       ; return 1
          ret
notPrime: xor  %eax, %eax     ; return 0
          ret

The input is bytes, not text. The translator sees 89 f9 be 02 00 00 00 39 ce 7d .... Decoding by hand (standard x86 encoding, this guide's check): 89 f9 is mov %ecx, %edi; be 02 00 00 00 is mov %esi, $2 (a 5-byte immediate move); 39 ce is cmp %esi, %ecx; 7d begins jge with an 8-bit displacement. Variable-length decoding is why "on demand" matters (M5).

The final TC holds four CCFs (Figure below). The two that remain are jge [takenAddr] (whose guest target is prime, reached through the entry test) and jmp [fallthrAddr3] (whose guest target is also prime, reached when the loop runs out without finding a divisor). The two that disappeared are the fall-through jumps of TU1 and TU2. Note that the jz continuation was also replaced by a chaining jump, to notPrime'; the paper's sentence counts only five of the six continuations (this guide's count).

The ret translation (verbatim from the paper):

notPrime': *xor   %eax, %eax                 ; IDENT
            pop   %r11                       ; RET: pop the GUEST return address
            mov   %gs:0xff39eb8(%rip), %rcx  ; spill %rcx into VMM memory
            movzx %ecx, %r11b                ; index = low byte of return address
            jmp   %gs:0xfc7dde0(8*%rcx)      ; jump through a VMM-space table

Why ret cannot be IDENT: the value on the guest stack is a guest address (the stack's contents must equal native, per the system-level property), but control must go to the TC address of its translation, which is only known at run time. The translation needs a scratch register, so it borrows %rcx, saving the guest's value through a %gs-relative store into VMM memory; "later, of course, the guest's %rcx value must be reloaded into the hardware %rcx." It then indexes a table in VMM space by the return address's low 8 bits. What the table entry does is not described; presumably it checks the full return address and either jumps to the matching CCF or falls back to a full lookup or the translator, restoring %rcx on the way (inference). This dynamic lookup is the 40-cycle call/ret penalty measured in M19.

What the trace shows. The TC captures an execution trace: the BB at prime is never translated because 49 is not prime. Code that executes first is laid out first and contiguously, so the hot path has good icache locality, and error handling that runs later (if ever) lands away from it. A bigger run behaves the same way: a 64-bit Windows XP Professional boot/halt translates 229,347 64-bit TUs, 23,909 32-bit TUs and 6,680 16-bit TUs.

On the hardware VMM, the paper says isPrime is "uninteresting": it contains only ALU operations and control flow, so "its execution is identical in host and guest mode." No translation, no exits. (Paper §3.2, §4.3)

M8 · Chaining, continuations and the translation cache

Continuation. A translator-invoking stub that stands in for a not-yet-translated successor. When executed it calls out of the TC into the translator with the guest target address.

Chaining. Like earlier translators (the paper cites Shade), the VMM lets "one CCF jump directly to another without calling out of the translation cache." When a continuation runs and its target has been translated (or has just been translated), the continuation jump is overwritten with a direct jump to the target CCF. Continuations are therefore "execute once". Often even the chaining jump can be elided when the target CCF is placed immediately after, as in steps 2 and 3 above.

Steady state. Translation and execution interleave "for as long as the guest runs, with a decreasing proportion of translation as the TC gradually captures the guest's working set." Figure 5 (M20) confirms that translation is a small cost even for boot/halt, which mostly runs cold code.

Code the TC is patching. Note that the TC is itself modified at run time: continuations are rewritten into chaining jumps, and adaptation (M11) writes forwarding jumps into existing CCFs. This patching is local (one jump instruction), which is why it is cheap.

What the paper does not cover. It does not describe the TC's size or replacement policy, or how translations are invalidated when the guest writes to code that has already been translated (self-modifying code, loaded and unloaded modules). A dynamic translator must detect such writes somehow, for example by write-protecting guest pages that have translations (inference; the paper does say BT adapts to "a variety of situations", and Transmeta's hardware has explicit support for self-modifying code, §8). (Paper §3.2)

M9 · Register binding, the %gs escape, and protection by segment truncation

Registers. During TC execution most virtual registers are bound to their physical counterparts, which is what makes IDENT translation possible: the guest's %eax really is in %eax. The exception is %gs, which provides an escape into VMM data structures (the ret translation above uses it to spill %rcx).

Protecting the VMM from IDENT memory accesses. IDENT loads and stores must run at close to native speed and must not be able to reach the VMM. Inserting explicit address checks would be too slow, so the design uses hardware protection. Of x86's two mechanisms, paging and segmentation, "for BT, segmentation works best." The VMM is mapped in the high part of the guest's address space; every guest segment is truncated so that its limit stops below the VMM. With all segment registers except %gs holding truncated segments, any translated instruction that tries to reach the VMM faults. The translator selectively inserts %gs prefixes when TC code needs VMM data, and strips the prefix (translating non-IDENT) from the occasional guest instruction that has its own %gs prefix.

The paper does not say why paging is worse here. A plausible reason: page protection distinguishes only user from supervisor pages, and the translated guest kernel and the VMM both run with privilege above user level, so pages alone cannot keep one away from the other without extra address-space switches (inference).

The 64-bit caveat. Intel CPUs of the time "lack support for segment limits in 64 bit mode", so on the test P4 the software VMM had no such protection and the paper states it "fails Popek and Goldberg's Safety requirement" in the measured configuration. AMD's Opteron supports 64-bit segment limits and the VMM performs similarly there, so the authors are confident the numbers represent the software VMM fairly (§6). For a production hybrid on Intel (M24), they would need "a performant VMM protection scheme that doesn't require segmentation" (§7.3).

Adaptation ties in. One of the adaptation targets listed in §3.3 is "access to the VMM's address range": a guest instruction that keeps faulting on the truncated limit (because the guest really uses those addresses) can be retranslated to emulate the access (the paper names the category; the detail is inference). (Paper §3.2, §3.3, §6, §7.3)

M10 · BT for the guest kernel, direct execution for guest user code

The paper states, without details ("beyond the scope of this paper"), that "BT is not required for safe execution of most user code on most guest operating systems. By switching guest execution between BT mode and direct execution as the guest switches between kernel- and user-mode, we can limit BT overheads to kernel code and permit application code to run at native speed."

Why direct execution of user code is safe and faithful (inference from M2). At guest CPL 3 the virtual CPL and the physical CPL agree, so reading %cs reveals nothing false. A user-mode popf cannot change IF natively either, so its de-privileged behavior is the correct behavior. User code's memory accesses go through the shadow page tables like everything else. Anything that needs the kernel (a system call, a fault, an interrupt) traps to the VMM, which then switches to BT mode to run the guest kernel's handler.

Consequences you should be able to derive. (1) The software VMM's overheads concentrate at guest kernel entry/exit and inside guest kernel code. (2) Every guest system call crosses into the VMM and back: the paper's syscall nanobenchmark shows "a layer of code and an extra privilege transition", about 2000 extra cycles (M19). (3) Compute-bound user-level workloads run at near native speed under BT, the same as under the hardware VMM (M16). (4) The word "most" in the quote: the paper does not list the exceptions.

💡
Exam habit: whenever a question asks how the software VMM handles some piece of code, first decide whether that code runs at guest CPL 0 (translated) or guest CPL 3 (direct execution). The two cases have completely different overhead profiles.

M11 · Adaptive binary translation: "innocent until proven guilty"

Why BT can beat a classical VMM. Traps are expensive on modern CPUs, so avoiding them wins. The paper's rdtsc measurement on the P4:

Way to execute a privileged rdtscCyclesWhat happens
trap-and-emulate2030hardware trap into the VMM, decode, emulate, return
callout-and-emulate1254the translation calls the VMM runtime directly: no trap, but still a call out of the TC
in-TC emulation216a short inline sequence computes the virtual result

The remaining trap source. Simple BT removes traps from privileged instructions, but "an even more frequent trap source remains": non-privileged instructions, ordinary loads and stores, that access sensitive data such as page tables. Those are trace faults (M3), and the translator cannot know ahead of time which store will hit a page table.

The algorithm. Every guest instruction starts "innocent" and is translated IDENT for maximal speed. During execution, the VMM detects instructions that trap frequently and adapts their translation:

on_trace_fault(tc_pc):                      # an IDENT store hit a protected page
  handle the fault normally (decode, emulate, update shadow)
  insn = guest instruction at tc_pc; insn.trap_count += 1
  if insn.trap_count crosses threshold:        # adapt AGGRESSIVELY toward non-trapping
      ccf5 = retranslate(insn, SIMULATE)       # e.g. callout to an interpreter / small program
      patch first instruction of insn's CCF (ccf1) with jmp ccf5   # O(1)

in ccf5 (SIMULATE callout):
  emulate the access in software, keep monitoring it
  if insn behaves innocently for long enough:  # hysteresis: adapt back RELUCTANTLY
      remove forwarding jmp from ccf1; insert opposing jmp in ccf5

The threshold and monitoring details are not given in the paper; the sketch shows the stated structure.

Why the forwarding jump (Figure 1). Many CCFs may jump directly into ccf1 (chaining). Redirecting all of them to ccf5 would require finding every direct predecessor. Patching a jump into ccf1 itself makes adaptation constant time, at the price of one extra jump on every later execution (the "dynamic overhead"). The "static overhead" of adaptation, code patching and the icache contents it destroys, is controlled with hysteresis so adaptation stays infrequent.

More than two states. The VMM adapts "not just in a bimodal form" but to several situations: access to a page table, access to a particular device, access to the VMM's address range. Each gets a translation suited to it.

Invariant (this guide's reading). Correctness never depends on adaptation. The page protection that implements a trace stays armed whatever the translation; an IDENT store that hits a traced page still faults and is handled correctly. Adaptation only changes how often that slow path is taken. So a wrong guess (adapting an instruction that later stops touching page tables, or not yet adapting one that does) costs speed, never fidelity.

Measured payoff. The ptemod nanobenchmark (M19): a guest PTE write costs 1 cycle natively, 391 cycles in the software VMM after adaptation into "a small program that is cheaper than a trap but still quite costly", and 12,733 cycles in the hardware VMM, which has no way to adapt.

What would break. An instruction that alternates between touching a page table and touching ordinary data would make adaptation flip-flop; hysteresis exists to stop that. The nanobenchmarks repeat each operation many times to amortize adaptation, and the authors argue this is representative because "adaptation converges on a small fraction of poorly behaving guest instructions" (§6.3). (Paper §3.3, Figure 1)

M12 · Intel VT and AMD SVM: VMCB, guest mode, vmrun, exits

The paper treats the two vendors' extensions together ("the similarity between the two architectures is obvious from their respective manuals") and uses AMD-style names generically. The primitives:

PrimitiveWhat it is
VMCB (virtual machine control block)an in-memory structure that "combines control state with a subset of the state of a guest virtual CPU"
Guest modea new, less privileged execution mode that supports direct execution of guest code, including privileged code
Host modethe previously architected x86 environment, where the VMM runs
vmruntransfers from host to guest mode: the hardware loads guest state from the VMCB and continues in guest mode

Diagnostic fieldsdescribe why the exit happened; e.g. an I/O exit records the port, width and direction

The cycle. The VMM fills the VMCB with the current guest state and executes vmrun. The guest runs at native speed until an exit condition fires. The VMM reads the VMCB fields describing the exit, vectors to emulation code, applies the emulated effect to the VMCB (for example, advancing the guest PC past an emulated in and writing the result register), and executes vmrun again.

hardware_vmm_loop(vcpu):
  loop:
      vmrun(vcpu.vmcb)                 # load guest state, run in guest mode
      # ... guest runs until a condition chosen by VMCB control bits ...
      # exit: hardware saved guest state into the VMCB, VMM state reloaded
      why = read exit fields of vmcb     # "a typical exit requires ten vmreads" (§7.1)
      switch why:
        I/O:          run device model (port, width, direction from VMCB)
        page fault:   software MMU: true / hidden / trace (M3)
        cr3 write:    switch / build shadow page table; set VMCB cr3
        TLB flush:    resync shadow entries
        ...           # some cases must fetch and decode the guest instruction
      write emulated results into vmcb

Choosing the leash. The control bits let the VMM decide how much to trust the guest. A hypervisor for a general-purpose OS might let the OS drive peripherals, handle interrupts or build its own page tables. For pure virtualization of an unmodified guest, the paper's VMM programs the VMCB to exit on: guest page faults, TLB flushes and address-space switches (to maintain shadow page tables); I/O instructions (to run emulated device models); and accesses to privileged data structures such as page tables and memory-mapped devices (via traces in the shadow tables).

Avoiding exits in hardware (the SIE idea). "Where possible, privileged instructions affect state within the virtual CPU as represented within the VMCB, rather than unconditionally trapping." Two examples the paper gives:

  • popf: a naive design would exit on every guest popf to update the virtual IF, but guests execute popf very frequently. Instead the VMCB holds a hardware-maintained shadow of %eflags, and guest-mode instructions on %eflags operate on that shadow. No exit.
  • %cr8 writes (cr8 sets which pending interrupts may be delivered): only writes that lower %cr8 below the priority of the highest pending virtual interrupt cause an exit (citing Uhlig et al.). The hardware throttles this exit type.

Terminology outside the paper. Intel's real names are VMCS (control structure), VM entry via vmlaunch/vmresume, VM exit, and vmread/vmwrite to access VMCS fields; AMD's are VMCB, vmrun and #VMEXIT. The paper's "ten vmreads" and Table 1's "VMCB read/write" refer to the Intel P4 they measured.

What the hardware does NOT provide (first generation). No MMU virtualization: there is no hardware help for mapping guest-physical to host memory, so the hardware VMM "inherits the software VMM's implementation of the shadowing technique" (M3). That single omission drives most of the paper's results. (Paper §4.1, §4.2, §4.4)

M13 · The hardware VMM implementation and the fork() walk-through

Structure is prescribed. The extensions "provide a complete virtualization solution, essentially prescribing the structure of our hardware VMM (or indeed any VMM using the extensions)." Most emulation code is shared with the software VMM: peripheral device models, guest interrupt delivery, logging, synchronization, interaction with the host OS, and the whole software MMU. Both VMMs ship in one binary (VMware Player 1.0.1).

The fork example (§4.3). A UNIX-like guest on the hardware VMM creates a process:

  1. System call. A user process calls fork(); CPL goes 3 → 0. The guest's trap and system-call vectors are loaded onto the hardware, so this happens without VMM intervention.
  2. Copy-on-write setup. The guest write-protects both parent and child address spaces. The VMM already has shadow tables for the parent, kept coherent with traces, so each guest page-table write causes an exit. The VMM decodes the exiting instruction, emulates it on the traced page, and reflects it into the shadow table, which write-protects the parent in the real MMU.
  3. Context switch. The guest scheduler runs the child and loads the child's page table pointer: exit. The software MMU builds a new shadow page table and points the VMCB's page table register at it.
  4. Hidden faults. The child touches parts of its address space not yet in its shadow tables: hidden page fault exits. The VMM updates the shadow table and resumes.
  5. True faults. Parent and child write to memory and take copy-on-write faults that "reflect protection constraints imposed by the guest." The VMM must still intercept them "to ascertain that they are not an artifact of the shadowing algorithm", then forward them to the guest.

M14 · What decides performance: the exit rate, and the qualitative scorecard

Exit rate. With VT/SVM, "performance depends primarily on the frequency of exits." A guest that never exits runs at native speed, but it would be useless because it can do no I/O. A guest in which every instruction exits would be dominated by mode transitions. "Reducing the frequency of exits is the most important optimization for classical VMMs." The exit rate depends on three things: guest behavior (a guest that only computes never exits), hardware design (means for throttling some exit types, such as the %eflags shadow and the %cr8 rule), and VMM software design (especially its use of traces and hidden page faults, as the fork example shows).

}

Results. Native 6.0 s; software VMM 36.9 s; hardware VMM "a sobering" 106.4 s. Per iteration that is about 150 µs, 920 µs and 2,660 µs (this guide's division by 40,000).

Why it is so bad for both, and worse for hardware. Each iteration exercises "system calls, context switching, creation of address spaces, modification of traced page table entries, and injection of page faults": the whole fork walk-through of M13, plus exit and wait. Every item except the system calls is handled by the software MMU, and in the hardware VMM every one of those is an exit.

The "4.4 times" sentence. The paper says the hardware VMM induces "approximately 4.4 times greater overhead than the software VMM." From the stated times, the overheads are 106.4 − 6.0 = 100.4 s and 36.9 − 6.0 = 30.9 s, a ratio of about 3.2, and the raw time ratio is 2.9. This guide could not reproduce 4.4 from any of the paper's forkwait numbers; treat 2.9× (time) or 3.2× (overhead) as the checkable figures. (Paper §6.2)

M21 · The three-way trade-off revisited, and why few workloads benefit

Recall M3: the software MMU balances trace costs, hidden page faults and context-switch costs. The nanobenchmarks show that "hardware virtualization makes all three dimensions of this design space more treacherous by replacing faults with costlier guest/vmm round-trips." And "in the absence of a hardware basis for supporting BT execution the hardware VMM is unable to adapt to frequently exiting workloads." Without adaptation, the tool that made the trade-off forgiving is gone, so the authors "found few workloads that benefit from current hardware extensions."

The two that do benefit, Apache on Windows and 2D PassMark, share two properties: a single address space (few context switches, so little shadow-table churn), and few I/O exits relative to the number of system calls (thanks to guest buffering for Apache and the SVGA shared-memory FIFO for PassMark). They are "the exception that proves the rule": workloads that enter CPL 0 often but rarely do privileged work are unusual. The paper's quip: the old UNIX benchmark cheat of returning a cached getpid() value; "if the application isn't asking for a privileged service, why enter the kernel at all?" (Paper §6.3)

Two independent levers. Making each exit cheaper (microarchitecture, §7.1) and making exits rarer (algorithms, §7.2; new hardware, §7.4). The paper calls the second "a more potent approach". (Paper §7.1, Table 1)

M23 · §7.2: trading traces for incoherence

The opening. Player 1.0.1 exits on every guest PTE modification because of traces. But "the x86's relaxed TLB coherency rules permit other page table coherency strategies than tracing." The rule being exploited (background, not spelled out in the paper): after the OS changes a PTE, the hardware TLB may keep using the old translation until the OS invalidates it (a TLB flush or a %cr3 reload). So a VMM may let its shadow lag the guest's table until the guest performs such an operation, which the VMM already intercepts.

VMware Workstation 2.0 (released 2000) did exactly that: it "would aggressively drop traces upon guest page table modification, allowing the shadow page tables to become temporarily incoherent with the guest page tables in order to reduce trace costs."

# trace-heavy (Player 1.0.1 software MMU)        # trace-dropping (Workstation 2.0)
on guest PTE write: fault/exit, update shadow      on first write to a PT page: drop its trace,
                                                     note the page as out of sync
                                                   later writes: run at full speed, no fault
on guest cr3 reload: switch shadows (cheap)        on guest cr3 reload / TLB flush: process the
                                                     backlog, resync shadows (expensive)

What it costs. Work moves into the guest page-table reload path, which must process the backlog of writes. And it forfeits an optimization that tracing enables: a PTE write that changes a page from not-present to present usually happens in the guest's page-fault handler during demand paging and is "almost always followed immediately by a user-level access to the freshly mapped page." With tracing, the VMM sees the write and can eagerly install the present shadow entry, saving the hidden fault that would otherwise follow. This matters for process-creation workloads like forkwait and "is hard to apply without tracing."

Why VMware moved to liberal tracing, and why that now hurts. Since Workstation 2.0 the binary translator became good at adapting to trace accesses, so tracing became cheap for the software VMM. That extreme point is "not optimal for the hardware-assisted VMM where trace accesses are costlier." VMware was exploring less trace-intensive MMU algorithms; preliminary result: "the hardware VMM gains on the software VMM, but still does not surpass it." (Paper §7.2)

M24 · §7.3: a hybrid VMM

Both VMMs are in the same binary, and nothing forces one technique per guest. VMware experimented with a hybrid that "dynamically selects the execution technique using simple guest behavior-driven heuristics", aiming to combine the hardware VMM's system-call performance with the software VMM's MMU performance. Results: "encouraging improvements on toy workloads", but the heuristics were immature. And on Intel, production BT would first need VMM protection that does not rely on segmentation (M9). Note the parallel to M11: this is adaptation again, one level up, choosing an execution engine per phase instead of a translation per instruction. (Paper §7.3)

M25 · §7.4: hardware MMU support (nested paging / EPT)

The claim. IBM's s/370 solved the three-way trade-off with hardware; AMD's "nested paging" and Intel's "EPT" proposals are similar to the SIE design. The VMM keeps a hardware-walked nested page table mapping guest-physical to host-physical addresses. The guest keeps full control of its own page tables (guest-virtual to guest-physical), and the hardware composes the two. The TLB caches entries from guest-virtual all the way to host-physical.

A TLB miss on guest virtual address V (the paper's six steps, for a guest with a two-level table):

  1. Use the guest page table pointer (%cr3) to locate the top of the guest's page table.
  2. %cr3 holds a guest-physical address: walk the nested page table to get the host-physical address of the guest's top-level table.
  3. Read the guest page directory entry for V.
  4. That PDE also holds a guest-physical address: translate it through the nested table.
  5. Read the guest PTE for V; it points to guest-physical X, which a third nested walk translates to host-physical Y.
  6. Fill the TLB with (V, Y) and resume the guest, "all without software intervention".

Cost. For an M-level guest table on an N-level nested table, the paper says "a worst-case TLB miss requires MN memory accesses." (Outside the paper: counting the final data-page translation as well, the usual worst-case count is (M+1)(N+1) − 1, which is 24 for four-level tables on both sides. The paper's MN is a simpler bound.) The authors are optimistic: the techniques that make ordinary virtual memory fast (large, highly associative, multi-level TLBs and caching) "should apply at least as well to the nested page table".

What disappears (mechanically): shadow page tables, traces on guest page tables (the guest edits its tables freely), hidden page faults, and VMM intervention on guest context switches (%cr3 loads no longer need to exit). The paper's conclusion: nested paging "should easily repay the costs of (slightly) slower TLB misses". What changes for the trade-off: the cost moves from frequent, software-visible events (each PTE write, each new mapping, each context switch) to TLB-miss latency, which hardware caching can hide. Workloads with poor TLB locality pay the most (inference).

🎓
From the lecture (10/8, ESX session; confirmed by that day's slides, "Today's environments: Hardware support for virtualization"). Explaining ESX's shadow page tables, the professor said they work but are an overhead: an extra copy of every page table, plus the cost of setting them up. AMD and Intel's answer was to "add yet another level of indirection", another hardware-supported page table that maps each guest's pages to machine pages, and he noted that all the techniques ESX used still work with those hardware page tables. That is the §7.4 nested page table, seen from the ESX side.

M26 · Related work and the conclusion

  • RISC vs CISC. The paper's stance comes from that debate: its lasting gifts are "skepticism towards the intuition that hardware always outperforms software" and the consensus that measurement must guide the hardware/software interface. The conclusion calls first-generation VT/SVM "CISC-like in its packaging of a whole solution and difficult to exploit without giving up existing software techniques."
  • picoJava sits at the hardware extreme: it reimplemented the 1.0 JVM in hardware, "not what one would build today to run Java" given multi-stage JITs.
  • Transmeta Crusoe sits at the co-design extreme: a VLIW core plus an optimizing, dynamic, adaptive binary translator from x86, with hardware primitives that support the software (speculation, self-modifying code). This is the model the authors want for virtualization: hardware that supports proven software techniques rather than replacing them.
  • Paravirtualization (Xen, Denali, pre-virtualization) gains performance and a simpler VMM but cannot run legacy or proprietary OSes, and creates a new guest/VMM interface that must be standardized and supported (VMI) alongside the OS/hardware interface.

Conclusions, in the paper's terms. Both VMMs do well on compute-bound workloads. For workloads that perform I/O, create processes, or switch contexts rapidly, software outperforms hardware. In two workloads rich in system calls, the hardware VMM prevails. The new hardware removes the need for BT and simplifies VMM design, but "in our experiments it rarely improves performance." The authors hope coming hardware support "will be designed to blend easily with and complement existing software techniques." (Paper §8, §9)

Connections to the other CS240 papers (mechanical only)

  • ESX (Waldspurger 2002). ESX runs guests on shadow page tables built by the same kind of software MMU described in M3; its pmap (guest physical page to machine page) is the "gPA to host page" step every hidden fault performs here, and the nested page table of M25 is that same mapping moved into hardware. ESX's content-based page sharing write-protects shared pages and breaks sharing on a write fault, the same page-protection trick as tracing (M3), used for copy-on-write instead of coherence. Because traces are implemented with page protection, their granularity is whatever page size the shadow table uses (inference); keep that in mind for any question mixing ESX, shadow tables and large pages.
  • Superpages (Navarro et al. 2002). Two mechanical links. (1) Nested paging makes TLB misses longer (M25), so TLB reach, the motivation of the superpages paper, matters more under it (inference). (2) The Alpha in that paper has no hardware reference or dirty bits and emulates them by protecting pages and taking a trap on first access: the same "protect, fault, record, unprotect" pattern as a trace.
  • Livelock (Mogul and Ramakrishnan). Livelock is about the per-packet and per-interrupt cost of the receive path. In a VM those costs grow: Player's hosted I/O model sends every packet through the host's stack (M17), and each guest access to a device register is an in/out to an emulated device: 216 cycles under BT but 15,826 under the hardware VMM (M19). Interrupt priority writes (%cr8) can also exit when interrupts are pending. Higher per-event cost means the guest saturates at a lower packet rate (inference). Note too that a guest's "disable interrupts" only disables virtual interrupt delivery to that guest (cli becomes vcpu.flags.IF:=0, M6); the VMM and host keep taking real interrupts.
  • Eraser (Savage et al.). Eraser instruments binaries (with ATOM) by inserting analysis code at every load and store, which is why it slows programs 10 to 30×. The BT VMM's translator, by contrast, keeps loads and stores IDENT and relies on hardware protection (segment limits, page protection) instead of inserted checks (M9). The paper's aside about Shade and Embra, which "combine subject code and analysis code", is the Eraser-style use of translation. On interrupts: a guest kernel that uses "disable interrupts" for mutual exclusion still gets it with respect to its own (virtual) interrupt handlers, because the VMM only delivers virtual interrupts when the virtual IF is set (inference from M2/M6).
  • Mesa and the threads/events papers. No direct mechanism in this paper connects to monitors or event loops; do not force one.
Follow the numbers

Worked examples

Four calculations straight from the paper's raw data.

① The headline ratio: how much worse is hardware?

forkwait on the P4: native 6.02s, software VMM 36.95s, hardware VMM 106.4s. How much worse is hardware than software, exactly?

  1. Software slowdown vs. native: 36.95 / 6.02 = 6.14×.
  2. Hardware slowdown vs. native: 106.4 / 6.02 = 17.67× ≈ 17.7×, matching the paper.
  3. Hardware vs. software directly: 106.4 / 36.95 = 2.88× — the hardware VMM takes nearly 3× longer than the software VMM for the exact same 40,000 fork/wait cycles.
🍯
This single ratio is why "hardware assist" doesn't automatically mean "faster" — it depends entirely on what the hardware helps with.

② Why one instruction costs 32× more under hardware

The ptemod nanobenchmark (a page-table write, "unchanged" case): native 1 cycle, software VMM 391 cycles, hardware VMM 12,733 cycles.

  1. Hardware ÷ software: 12733 / 391 = 32.6× costlier under hardware, for the identical operation.
  2. Why: both VMMs trace this write to keep shadow page tables coherent. Software's adapted translation calls a short in-line handler; hardware must exit to host mode, save/restore full guest state, and decode the instruction.
  3. Scale it up: a real XP boot/halt performs over 1,000,000 PTE writes. At the 12,342-cycle-per-op difference (12733−391), that's ≈12.3 billion extra cycles — roughly 3.25 extra seconds at 3.8 GHz, from this one nanobenchmark alone (a back-of-envelope estimate, not the paper's measured total).
💡
This is the mechanism behind Figure 5 in the paper: PTE modification dominates the hardware VMM's overhead during a real boot workload.

③ Does newer silicon close the gap?

Table 1: VM-entry cost drops from 2409 cycles (Pentium 4) to 937 cycles (pre-production "Core") — a 61% cycle reduction. Does forkwait's ratio improve proportionally?

  1. Cycle reduction: (2409 − 937) / 2409 = 61.1%, matching the paper.
  2. Time reduction (accounting for clock speed, 3.8 GHz → 2.66 GHz): 2409/3.8 = 634 ns; 937/2.66 = 352 ns → (634−352)/634 = 44.5%, matching the paper's "44%".
  3. forkwait ratio on Core: native 2.62s, software 18.43s (7.03×), hardware 38.89s (14.84×) — the hardware/native ratio improved from 17.7× to only 14.8×, despite the entry-cost cut being over 60%.
  4. Software actually got relatively worse (6.1× → 7.0×) on the faster chip — a reminder that ratios to a faster native baseline can move in surprising directions.
⚠
Microarchitecture alone narrows but does not close the gap — the paper argues the remaining cost is structural (stateless exits, no MMU support), not just clock-speed catch-up.

④ The two workloads where hardware actually wins

Apache-on-Windows: software 53% of native, hardware 67%. 2D Graphics (PassMark): software 63.4%, hardware 70.0%. What do these share?

  1. Both run in effectively a single address space, so page-table tracing overhead is minimal for both VMMs.
  2. Both perform relatively few I/O exits compared to their system-call rate (buffered I/O for Apache; a shared-memory FIFO for the virtual SVGA device).
  3. Since syscall nanobenchmark cost is near-native under hardware (246 vs. 242 cycles) but costly under software (2308 cycles), a syscall-heavy, exit-light workload flips the usual result. SPECjbb shares some of this character too — both VMMs land close to native, with hardware nudging slightly ahead in the raw numbers, though the paper doesn't treat it as a major "hardware wins" case.
💡
The paper calls this "the exception that proves the rule": workloads that enter the kernel often but rarely touch privileged shared state are unusual — most real kernels aren't built that way.

Guest trap and system-call vectors are loaded directly onto the hardware in guest mode, so a syscall's privilege transition (CPL 3→0) happens without any VMM intervention at all — no exit is even triggered. Problem 4 · hard
ptemod costs 391 cycles under software but 12,733 under hardware (32.6×) — yet both VMMs use the identical shadow-page-table algorithm. What exactly differs?
Show answer
Not the algorithm — the mechanism for noticing the trace. Software's adaptive BT has already retranslated this page-table write into an in-line callout sequence (no trap at all after adaptation). Hardware has no equivalent "adapt away the trap" option: every traced write still forces a full VM exit — save guest state to VMCB, switch to host mode, decode the instruction, emulate, then vmrun back. The 32.6× gap is the cost of that mandatory stateless round-trip vs. an in-line software sequence.Misconception: that removing software's translation layer removes translation's costs. It removes translation's costs but exposes the trace mechanism's true (unmasked) hardware cost instead.
Problem 5 · medium
Apache-on-Windows favors the hardware VMM (67% vs. 53% of native) while Apache-on-Linux favors software (45% vs. 38%). Both run the same benchmark tool. What's different?
Show answer
Configuration, not code: Apache defaults to a single address space on Windows but forks many address spaces (processes) on Linux. Single-address-space workloads minimize page-table tracing/exit costs for both VMMs and let hardware's cheap syscalls dominate; multi-process workloads reintroduce the context-switch and shadow-paging costs where software's adaptive BT wins.Misconception: that a benchmark name alone determines which VMM wins. The guest OS's process/threading model matters at least as much as the workload's identity.
Problem 6 · hard
Nested paging removes tracing but a TLB miss now costs up to M·N memory accesses (M = guest table levels, N = nested table levels). Why does the paper still call this a good trade?
Show answer
Tracing costs are paid on every guest page-table write (measured at 12,733 cycles each under first-gen hardware) — a constant, frequent tax. The M·N walk cost is paid only on a TLB miss, and the paper bets that the same microarchitectural techniques that already make ordinary (non-nested) multi-level page walks fast — large associative TLBs, page-walk caching — will absorb the extra depth just as well. Rare-and-cached beats frequent-and-exiting.Misconception: that "more memory accesses per miss" straightforwardly means "worse performance." Frequency and cacheability of the operation matter more than its raw per-occurrence cost.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Why can't x86 just use classical trap-and-emulate?▾
Two leaks: the guest can read its own de-privileged status from %cs, and some privileged instructions (like popf) silently no-op at user level instead of trapping. Either one is enough to break support for unmodified, binary-only guest OSes.
Q2How does binary translation avoid interpretation's speed penalty?▾
Most guest instructions translate "IDENT" — nearly unchanged — and run at close to native speed once cached in the translation cache. Only control flow, PC-relative addressing, and privileged instructions need special (slower) handling, and privileged instructions are rare in normal execution.
Q3What does "adaptive" mean in adaptive binary translation?▾
Guest instructions start translated as cheaply as possible ("innocent"). If one keeps trapping (e.g., a page-table write), the VMM retranslates it into a non-trapping callout and patches the old code with a forwarding jump — a permanent, one-time fix amortized over every future execution.
Q4Why does the hardware VMM lose on page faults and PTE writes specifically?▾
Both VMMs use the same software shadow-page-table algorithm (first-gen VT/SVM added no MMU virtualization). But every trace hit or true fault forces the hardware VMM into a full, stateless VM exit — costlier than software's shorter, adapted control-transfer path.
Q5Why does the hardware VMM win on system calls?▾
Guest trap and syscall vectors are loaded directly onto hardware in guest mode, so a syscall's privilege transition happens with zero VMM intervention — no exit at all. Software must add an extra privilege transition and code layer around every syscall.
Q6Does newer hardware (Intel "Core" vs. P4) fix the problem?▾
It helps — VM-entry cost dropped 61% in cycles (44% in time) — but forkwait's hardware-vs-native ratio only improved from 17.7× to 14.8×. The paper argues the remaining gap is structural: no MMU support, and exits that are inherently stateless.
Q7What is "stateless" about a VM exit?▾
After a guest resumes in hardware-assisted direct execution, the VMM has no running knowledge of guest state until the next exit. On exit, it must reconstruct context by reading roughly ten VMCB fields and, in some cases, decoding the faulting instruction — every single time, with no cached shortcut.
Q8What is nested paging, and why isn't it in this paper's measurements?▾
Nested paging (Intel EPT, AMD RVI) lets hardware translate guest-virtual→guest-physical→host-physical addresses itself, removing the need for shadow page tables and their trace exits. The measured hardware in this paper predates it — Section 7 is a forward-looking proposal, not a measured result.
Q9Is the software VMM's advantage permanent?▾
The authors don't think so — they expect microarchitecture to keep improving and explicitly call for hardware MMU support that would let the hardware VMM close the gap. Their conclusion is a plea for hardware designers to complement, not replace, proven software techniques.
Q10Why does the paper use a custom test OS ("FrobOS") for nanobenchmarks?▾
To get precise control over exactly which single virtualization-sensitive operation executes, without a real OS's unrelated background work contaminating the measurement — letting each nanobenchmark isolate one cost (e.g., just a page fault, just a PTE write).

This paper predates CXL by 15+ years, but its core lesson — measure before trusting hardware-assist — is exactly the lesson memory-tiering researchers keep relearning.

Nested paging is a preview of CXL's multi-hop translation cost

The M·N worst-case TLB-miss walk for nested paging is this guide's analogy for the multi-hop address translation debates in CXL.mem and tiered-memory systems — not a claim Adams & Agesen make. Both cases add a hardware translation layer (nested page tables, or a CXL switch/fabric hop) that trades a frequent software tax for a rarer, deeper, cache-absorbable one. The bet only pays off if TLBs/caches are big enough to hide the extra hops — the same open question CXL tiering designs (TPP, Memtis) wrestle with today.

"Stateless" hardware exits echo rigid page-placement counters

VT/SVM's inability to adapt its own trap-handling cost mirrors why purely hardware-driven page-placement heuristics (fixed access-bit sampling, fixed migration thresholds) often underperform software policies that can adapt online — exactly the argument for OS-managed tiering (Linux mm, AutoNUMA-style scanning) over rigid hardware-only schemes.

Adaptive BT's "innocent until proven guilty" is an eBPF-style idea a decade early

Retranslating only the guest instructions that misbehave — rather than pessimistically handling everything the same way — is the same design principle behind extensible-kernel mechanisms like eBPF: start with a fast generic path, specialize only where measurement shows it's needed.

The paper's real argument is a monolithic-vs-microkernel-style tradeoff

Software VMM flexibility (many code paths, richly adapted) vs. hardware VMM rigidity (one fixed exit-and-reconstruct path) parallels the monolithic-kernel-flexibility vs. microkernel-fixed-IPC-cost debate: a rigid, "clean" interface isn't automatically cheaper once you count what it costs to cross it.

🍯
Takeaway for tiering research: just as first-gen VT/SVM hardware needed software's shadow-paging flexibility to even function, CXL-tiering hardware primitives will likely need OS-managed software heuristics layered on top — hardware speed alone doesn't guarantee a win until the software/hardware boundary is co-designed, not just measured after the fact.

Given that Core's 61% VM-entry cycle cut only moved forkwait's hardware-vs-native ratio from 17.7× to 14.8×, how much of the residual 14.8× gap is fixable by microarchitecture alone versus requiring an algorithmic fix like nested paging (distinguish "faster exits" from "fewer exits" as two independent levers)?

The paper argues even a hypothetical "free-exit" microarchitecture would still lag software due to the cost of reconstructing guest state on each exit — is this "statelessness tax" fundamentally different from the context-reconstruction cost in a microkernel's IPC path, or the same problem in different clothes (pull on the monolithic-vs-microkernel parallel)?
  3. ptemod costs 12,733 cycles under hardware vs. 391 under software (32.6×) — given nested paging removes tracing entirely, does its own worst-case M·N-memory-access TLB walk reintroduce a similar tax at scale, especially for deep CXL-tiered memory hierarchies (ask whether "rare but expensive" always beats "frequent but cheap")?
  4. Apache-on-Windows and 2D-Graphics were the *only* workloads clearly favoring the hardware VMM, both characterized as "single address space, few I/O exits relative to syscalls" — how would that characterization hold up against today's io_uring or kernel-bypass workloads that also try to minimize syscalls, just from the other direction (is minimizing exits or minimizing syscalls the more general design principle)?
  5. VMware's own history (Workstation 2.0's trace-dropping algorithm, which let shadows go temporarily incoherent and resynced them on page-table reload, vs. its later trace-heavy adaptive-BT MMU) shows the trace/hidden-fault/context-switch trade-off has no fixed answer — what would change your placement in that trade-off space if you were designing page-placement for a DRAM/NVM or CXL-tiered system instead of a shadow page table (map "trace cost" and "hidden fault cost" onto tiering's migration-cost and cold-access-cost analogues)?

Adaptive BTRetranslating a frequently-trapping instruction into a cheaper non-trapping form ("innocent until proven guilty").

Shadow page tableThe VMM's own page table, kept coherent with the guest's, that real hardware actually walks.
