A single search query fans out across dozens of microservices you don't own. QProf treats that whole tangle as one call stack, so it can tell you exactly which service is burning your CPUs — without a single line of manual instrumentation.

1Warehouse-scale services and RPCs▾

A modern cloud program isn't one binary — it's a "web of microservices" talking over the network via RPCs. A single user query (e.g. a search) might touch dozens of independently-owned services, each doing a slice of the work.

This mesh runs across thousands of datacenters — "the data center is the computer." Understanding performance means understanding the whole mesh, not any one service in isolation.

Now you're ready: QProf's whole premise is treating this mesh of RPCs as if it were the call stack of one giant program.
2Traces, spans, and the trace tree▾

A trace represents one distributed computation (like one search query), identified by a 64-bit trace ID. It's built from spans — each a logical unit of work (usually one RPC), with its own 64-bit span ID and a pointer to its parent span. Traces are (usually) trees of spans.

This is the Dapper tracing model, and it's normally used to debug why one particular request was slow.

Now you're ready: QProf repurposes this same tree structure, but sums cost across it instead of just displaying latency for one request.
3Why you sample instead of tracing everything▾

Tracing every single RPC at fleet scale would be prohibitively expensive. So systems sample: trace 1-in-N requests, chosen either uniformly (probability 1/N, good for statistics) or by forced business logic (e.g. "always trace requests from this debug tool").

The sampling decision is usually made at the root of a request and propagated down — but a middleware service partway through can override it, producing a partial trace that's missing everything above it.

Now you're ready: QProf can only build reliable fleetwide statistics from traces that are both uniformly sampled and rooted — Section 3 is entirely about why the other kinds of samples can't be used.
4Cost is summable; latency isn't▾

If service A calls B and C in parallel, the request's latency is roughly max(B, C) — you can't just add wait times. But cost metrics like CPU-seconds, TPU-seconds, or disk ops are additive no matter how the work was scheduled: A's transitive cost is simply its own cost plus B's plus C's.

This is why traces — built for latency debugging — can be repurposed as a cost profiler far more easily than as a general performance profiler.

Now you're ready: QProf deliberately restricts itself to cost metrics (CPU/TPU/disk/$) for exactly this reason — it's the tractable half of the problem.
5Transitive cost: a query's whole bill▾

A service's self cost is what it spends running its own code. Its transitive cost also includes everything it triggers downstream — every backend RPC, and their backends, all the way to the leaves.

Most existing tools only show self cost per-service. Transitive cost answers the more useful question: "if I turn this feature off, how much of the fleet's total spend actually disappears?"

Now you're ready: transitive cost is the entire point of QProf — it's what lets a single frontend feature be blamed for CPU burned four hops away.
6Ambient (background) CPU profilers▾

A sampling CPU profiler periodically interrupts a running process (here, every 10 ms of CPU time) and records what it was doing. Run continuously, "ambient," on every process, it needs no manual setup — it has existed at Google for over a decade.

Normally it just tags samples with the currently-running RPC method name to get self-cost breakdowns per RPC.

Now you're ready: QProf's trick is hooking this profiler's interrupt handler into the trace machinery, so each tick gets credited to a specific query, not just a specific RPC method.
7The observer effect▾

An observer effect is when measuring something changes it. Tracing is supposed to be passive, but if application code checks "am I being traced?" and does extra work only when the answer is yes (e.g. writing debug logs), the trace no longer reflects normal behavior.

Worse, because that extra RPC only ever shows up in traced (and thus statistically over-weighted) requests, naively summing trace data massively over-counts its true cost.

Now you're ready: this is the single biggest reason a "just sum up what's in the traces" cost profiler doesn't work out of the box — Section 3.3 walks through a real 100× overestimate caused by exactly this.
8"Room-at-the-top": doing less work▾

Most performance tools help you do the same work faster — optimize a hot loop, cut a lock, shrink a critical path. "Room-at-the-top" is the other lever: skip work entirely. "The fastest memcpy is the one you don't do; the cheapest search query is the one whose results were cached."

This kind of opportunity (empty results, unnecessary retries, cache misses that shouldn't have missed) is invisible to per-function CPU profiling — you need to see the whole request's fate to spot it.

Now you're ready: this is QProf's stated mission — it's a profiler built specifically to surface "found money" that ordinary profilers can't see, and the case studies tab is full of examples.
The whole story in one place

QProf in a nutshell

The mismatch between what traces are built for and what a cost profiler needs, and the four fixes that close the gap.

Distributed traces exist to debug latency — finding the one slow request out of a haystack. A cost profiler needs the opposite: an unbiased view of the entire haystack's resource spend. Naively summing cost data out of ordinary traces breaks in at least three ways: users can force traces in ways that destroy well-defined sampling probabilities, tracing overhead makes traced requests artificially more expensive, and applications can behave differently when they know they're being watched (the observer effect).

QProf fixes all three by inventing skeletal tracing: an ultra-lightweight, root-only, independently-and-uniformly-sampled trace mode that is completely invisible to application code — is_traced() always returns false, and every public annotation API becomes a no-op. What survives is enough structure (spans + a handful of restricted, cost-only annotations) to compute a reliable statistical population.

To fill in cost without asking any of the fleet's thousands of services to add instrumentation, QProf wires a per-query ambient CPU profiler directly into the trace's TraceContext: every 10 ms interrupt increments a counter on whichever query happens to be running, and that counter is written straight into the trace when the query finishes. New fan-in / batching APIs give batched requests (which merge many logical queries into one RPC) a well-defined sampling probability, so their cost can be split back across the requests inside. Finally, an offline pipeline processes trillions of spans a day, expanding them into per-callstack cost, weighting each sample by its inverse sampling probability (the Horvitz–Thompson "unsampling" estimator), and aggregating down to a queryable dataset.

The payoff: despite being built entirely from sampled data, QProf measures QPS within 10% for 73% of all RPC profiles and CPU within 10% for 47% — both substantially tighter than what ordinary tracing gives you — with zero manual instrumentation, deployed fleetwide for years, credited with saving millions of CPU cores, thousands of TPUs, and large amounts of disk I/O.

🍯 Key takeaways

  • Traces are built for latency (haystack → needle); a cost profiler needs the whole haystack, unbiased.
  • Skeletal tracing = invisible + independently/uniformly sampled + root-only + minimal annotations.
  • An ambient CPU profiler, wired into the TraceContext, gives per-query CPU with zero manual instrumentation.
  • Fan-in / BatchedTraceContext APIs give batched requests well-defined sampling semantics.
  • The offline pipeline expands spans into callstacks, applies Horvitz–Thompson "unsampling" weights, then aggregates 10–20× smaller.
  • Validated against ground-truth self-cost from the background profiler: QPS/CPU accuracy both improve substantially over normal tracing.
  • Deployed fleetwide for years; used to find "room-at-the-top" — caching, batching, wasted work, priority inversion — saving millions of cores.
Seven everyday pictures

How to think about QProf

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks.

The core danger · Observer effect

The security camera that changes the room

Install a visible camera in a break room and people behave differently the moment the red light is on — the footage no longer shows normal behavior. Some services do exactly this: they check "am I being watched?" and log extra data only when traced. Sum that up naively and you conclude everyone always does the extra logging — QProf once overestimated a real RPC's cost by 100× this way.

Where it breaks: the analogy suggests malice; in practice it's a reasonable-looking debug convenience (if (traced) log_extra()) that nobody realized would poison fleetwide statistics.
Turning samples into totals · HT estimator

An exit poll, not a full recount

Pollsters don't survey every voter — they poll a fraction and multiply each response by how many real voters it represents. QProf does the same: a query sampled at 1/10,000 stands in for 10,000 real queries, so each sample's cost gets multiplied by its inverse sampling probability before being summed (the Horvitz–Thompson estimator, "unsampling"). Miscount who was eligible to be polled, and the whole extrapolation is wrong.

Where it breaks: a pollster knows every voter's turnout probability. Force-traced requests have no defined probability at all — there's no honest multiplier, so they simply can't be polled (§3.1).
The fix · Skeletal tracing

A bare mannequin, not a dressed-up one

A shop mannequin shows a garment's silhouette without any of the styling that makes a live model act self-conscious. Skeletal tracing is the mannequin version of a trace: it keeps only the bones (span structure + a few restricted cost annotations) and none of the "clothing" (custom annotations, force-trace hooks) that let application code notice or influence it. is_traced() always returns false, so the app can't even tell it's being measured.

Where it breaks: a mannequin is permanently bare. Skeletal tracing can co-occur with a full "dressed" normal trace on the very same request — they're independent, layered decisions, not mutually exclusive outfits.
Zero-instrumentation cost · Ambient profiler

A strobe light flashing every 10ms

Instead of asking every dancer to self-report what they're doing, a strobe flashes at a fixed interval and a camera notes who's lit up each time. Over enough flashes, whoever dances longest accumulates the most photos. QProf's CPU profiler is that strobe: it fires every 10ms and increments a counter on whichever query's TraceContext happens to be installed on that thread right then — no dancer has to cooperate.

Where it breaks: a strobe catches everyone equally; a 10ms sampling interval is coarse enough that most individual spans get zero flashes and look like they cost nothing — only in aggregate across trillions of spans does the picture resolve.
Amortizing overhead · Batching / fan-in

Carpooling to split the toll

Three commuters driving separately each pay a full toll; carpooled, they split one toll three ways. Batching does the same for RPCs: instead of paying per-request overhead three times, a service merges requests into one bigger RPC. QProf's BatchedTraceContext flips an independent sampling coin for the batch itself, so — unlike the carpool — the cost of the ride can still be honestly measured and attributed back to each rider.

Where it breaks: carpool cost splits evenly by definition. QProf instead assumes even splitting (linear cost in batch size) and validates it empirically — it isn't guaranteed, and the paper flags that very large batches can behave non-linearly.
The mission · Room-at-the-top

The cheapest flight is the one you never book

The paper's own line: the fastest memcpy is the one you don't do; the cheapest search query is the one whose results were cached. Most performance tools help you fly faster; QProf helps you notice trips you didn't need to take at all — a feature that always returns empty, a retry that fires needlessly, a request that a cache should have absorbed.

Where it breaks: some "unnecessary" trips are load-bearing — e.g. MapReduce jobs must read from reliable low-priority-tolerant storage even though it looks wasteful from a pure cost lens (§6.3). Room-at-the-top still needs a human to judge which room is safe to remove.
Wasteful cross-tier demand · Priority inversion

A limo called out for a milk run

A limo is provisioned and priced for urgent, guaranteed-fast trips. Sending it to fetch groceries doesn't slow the groceries down, but it monopolizes an expensive resource that should be idle and ready for the next real emergency. A throughput-oriented batch job issuing high-priority disk requests is the same pattern: it works fine, but it quietly consumes capacity meant for latency-sensitive, high-priority traffic (§6.3.1).

Where it breaks: sometimes calling the limo is intentional and correct — e.g. a MapReduce job legitimately must read from high-reliability storage tiers. Priority inversion is a smell QProf can surface, not automatically a bug.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals.

1 · Why plain traces can't be a cost profiler

Three separate problems corrupt naive "just sum the traces" cost accounting: (1) users can force-trace requests via arbitrary business logic, which have no well-defined sampling probability and are often non-root, producing partial trees; (2) tracing overhead makes traced requests measurably more expensive than untraced ones; (3) applications can behave differently when traced at all (the observer effect). Any one of these can silently invalidate an entire RPC's cost estimate.

2 · Skeletal tracing — invisible, independently sampled

Skeletal tracing samples a request uniformly and independently of every other tracing decision — including whether it's also normally traced. Crucially, it's invisible: is_traced() always returns false and all public annotation APIs become no-ops, so application code cannot detect or react to it. Only a restricted, passkey-guarded API (used by RPC frameworks and the profiler itself) can write critical cost annotations. Sampling always happens at the request root, guaranteeing every skeletal trace represents the entire computation.

3 · Per-query CPU without manual instrumentation

Manually instrumenting every service to report per-query CPU doesn't scale across millions of lines of code owned by different teams. Instead, QProf adds a single atomic counter to the (already per-query) TraceContext. The fleet's existing always-on ambient profiler fires a 10ms interrupt, checks which TraceContext is currently installed on that thread, and increments its counter. When the TraceContext's refcount finally drops to zero — meaning all synchronous and asynchronous work for that query is done — the accumulated tick count is written to the trace as its CPU cost.

💡
Why write CPU straight into the trace instead of tagging profiler samples with trace/span IDs (as other tools do)? At warehouse scale, tagging every CPU sample with a high-cardinality trace_id destroys the profiler's ability to aggregate identical samples together, ballooning storage — and >99.9999% of traces are never individually viewed anyway, so that detail is wasted. Writing the aggregate cost into the trace avoids an enormous join at query time too.

4 · Fan-in: giving batches well-defined sampling semantics

Batching merges several logical requests into one RPC — a fan-in, not a strict tree. Naively, "trace the batch if any request inside is traced" seems reasonable, but it makes the batch's sampling probability depend on the (often unknown or undefined) probabilities of the requests inside — exactly the kind of non-uniform sampling QProf must avoid.

5 · The postprocessing pipeline

Raw data arrives as one row per span. Callstack expansion walks every span up to its root, producing one row per (span, ancestor) pair — an O(N·M) blowup for N spans of average depth M. Unsampling assigns each row a statistical weight = (1/sampling probability) ÷ seconds-per-day, converting counts into a daily rate (Eq. 3), then sums weight × cost across matching callstacks to get total cost or QPS for any operation in the trace (Eq. 4). Finally, aggregation shrinks the now-huge dataset 10–20× by keeping all non-zero-cost spans verbatim, but downsampling the (much more numerous) zero-cost spans at a fixed rate and scaling their weights back up — since summed weight alone is enough to reconstruct QPS even after discarding most of them.

Follow the numbers, step by step

Worked examples

Four traces through the paper's formulas — unsampling a single sample, seeing why forced traces break it, and pricing two real "room-at-the-top" wins. Illustrative example numbers are labeled as such; sampling rates and result percentages are the paper's own.

① Unsampling one skeletal trace (Eq. 3–4)

Skeletal tracing samples at the paper's example rate p = 1/10,000. Suppose one sampled query shows a CPU cost of 5 core-seconds on some RPC. What daily rate of CPU does that single sample represent?

  1. Compute the weight (Eq. 3): weight = (1/p) ÷ (60·60·24) = 10,000 ÷ 86,400 ≈ 0.1157 "queries per second represented" per sample.
  2. Apply it to this sample's cost (Eq. 4, one term of the sum): weight × cost = 0.1157 × 5 ≈ 0.579 cores of estimated fleetwide rate contributed by this one sample.
  3. Scale up: a real RPC profile is estimated by summing this term over every sample that hit it that day — thousands of such terms average out sampling noise.
  4. Sanity check the units: dividing by seconds-per-day converts a raw "cost × how-many-you-represent" number into a steady-state rate (cores, not core-days) — which is what engineers actually want to compare against machine budgets.
🍯
Insight: every sample carries its own multiplier baked into its sampling probability — "unsampling" is just carefully bookkeeping that multiplier through the sum.

② Why a high retry rate can zero out usable data (§3.1, Fig. 4)

Retry code force-traces every retry attempt for debuggability. If retries are common, what fraction of traffic becomes unusable for cost analysis, and why can't we just estimate a probability for it?

  1. Force-traced ⇒ no defined p. A forced trace's probability depends on "what fraction of all requests happen to meet this business logic" — impossible to know at runtime and infeasible to reconstruct afterward.
  2. Every forced trace must be discarded from the statistical population (§3.1) — not down-weighted, excluded, since there's no honest multiplier to apply.
  3. Illustrative scenario: if, say, 90% of an endpoint's traffic ends up going through at least one force-traced retry, only the remaining 10% is usable — the sample population effectively shrinks 10×, and this specific endpoint's true cost becomes far noisier or entirely invisible.
  4. The paper's real example: this exact retry pattern was found in production code, and the intent (trace failures for debugging) was reasonable — the statistical damage was an unintended side effect nobody had reasoned through.
💡
This is why skeletal tracing's sampling decisions are deliberately walled off from any public "force trace" API (§4.1.4) — the bug in example ② simply cannot happen to a skeletal trace.

③ Pricing a response cache with QProf (Eq. 6, §6.1.1)

Illustrative numbers matched to the paper's method: a job sees QPS = 2,000, a cache hit rate of 70%, a cache-hit cost of 0.001 cores/query, and a (transitive) cache-miss cost of 0.05 cores/query. What are the savings from caching for this one job?

  1. Cost saved per hit: miss_cost − hit_cost = 0.05 − 0.001 = 0.049 cores avoided per cache hit.
  2. Hits per second: QPS × hit_rate = 2,000 × 0.70 = 1,400 hits/sec.
  3. Job's savings (Eq. 6, one term): 1,400 × 0.049 ≈ 68.6 cores saved for this job alone.
  4. Scaling up: Eq. 6 sums exactly this term over every job using response caching; summed across the whole fleet, this is the calculation behind the paper's reported "millions of cores + HDD ops and thousands of TPUs" saved by caching.
🍯
Insight: none of these four numbers (QPS, hit rate, hit cost, miss cost) were previously measurable together per-job before QProf — hit rate came from monitoring, but transitive miss cost needed a cost profiler.

④ Pricing request aggregation (Eq. 7, real batch-size stats from Fig. 14)

The paper reports the most common batch size is 1 (44% of batches — no batching happened), and for the rest, the average batch size is 23. Suppose (illustrative) an unbatched baseline query costs 10 CPU-ms, and a real batch of 23 costs 120 CPU-ms total. What are the savings, and what happens for size-1 batches?

  1. Baseline cost if unbatched: batch_size × cost_baseline = 23 × 10 = 230 CPU-ms (what 23 separate requests would have cost).
  2. Actual batch cost: 120 CPU-ms (per-request overhead amortized across the 23).
  3. Savings for this batch (Eq. 7): 230 − 120 = 110 CPU-ms, roughly 48% cheaper than going unbatched.
  4. Now a size-1 "batch": 1 × 10 − 10 = 0. Exactly as the paper states: "no resource savings are achieved here" — with nobody to amortize overhead against, batching a single request buys nothing.
  5. Fleet scale: summing Eq. 7 across every batch (weighted by 1/p as always) is how the paper arrives at request aggregation saving O(100k) cores fleetwide, even though 44% of batches individually contribute zero.
💡
The BatchedTraceContext API is also how the paper measures the unbiased cost_baseline itself: it periodically flushes an already-sampled request in a batch of its own, rather than trusting whatever size-1 batches happen to occur naturally (which would be biased toward slow-to-fill traffic patterns).
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A request is both force-traced (a debug tool set a flag) and, independently, selected by skeletal tracing. Should its cost be counted in QProf's fleetwide statistics?
Show answer
Yes — but only the skeletal half of it matters for statistics. The skeletal sampling decision is independent of the force-trace flag and always has a well-defined probability, so that portion is usable. The normal/forced trace data sitting alongside it is simply extra debugging detail that plays no role in the cost totals.Misconception: that "traced" is one binary status. A single request can carry multiple, independent tracing decisions at once — only skeletal tracing's decision is guaranteed statistically clean.
Problem 2 · medium
Skeletal tracing samples at 1/10,000 while normal tracing's effective fleetwide rate is about 1/4,000. Which one produces more raw trace volume, and does that explain why skeletal tracing's data is more accurate?
Show answer
Normal tracing actually produces more traces (1/4,000 ≫ 1/10,000 — roughly 2.5× the rate), yet skeletal tracing is still the more accurate source. So the improvement isn't from having more samples — it's from each skeletal sample being unbiased (no observer effects, no forced-trace pollution, lower overhead), which the paper explicitly notes.Misconception: that accuracy comes from sample count. Here it comes from sample quality — a smaller, cleaner population beats a larger, contaminated one.
Problem 3 · medium
A batch's sampling probability could in principle be computed as p_batch = 1 − ∏(1−p_i) (Eq. 2) over the requests inside it. Why is this formula useless in practice?
Show answer
Because p_i is unknowable for the vast majority of requests: if a request wasn't traced, nothing recorded its p_i at all, and if it was non-uniformly (forced) sampled, it has no well-defined p_i to begin with. The formula is mathematically correct but requires data that doesn't exist, which is exactly why QProf instead gives the batch its own independent coin flip rather than trying to derive one from its contents.Misconception: that a correct formula is automatically a usable one. Eq. 2 is right in theory and unusable in practice — the paper's real fix sidesteps needing it at all.
Problem 4 · hard
A service logs metadata via an RPC only when a request is traced, and the sampling probability of that trace is 1%. If that RPC shows up in every traced sample, by roughly what factor will naive summation overestimate its true fleetwide cost?
Show answer
About 100×. Each traced sample gets weighted by 1/0.01 = 100 when unsampled, so a span that appears in every traced sample (but in reality only ever fires for that 1% of traced requests) gets counted as if 100× as many real requests trigger it — when the true trigger rate is only the traced fraction itself. This is the paper's actual reported observer-effect incident.Misconception: that any span present in a trace reflects normal behavior. A span caused by the act of tracing itself gets inflated by exactly the inverse of the sampling probability — the rarer the trace, the bigger the distortion.
Problem 5 · medium
The postprocessing pipeline downsamples zero-cost spans at, say, 10% but keeps all non-zero-cost spans. Why doesn't this bias the QPS estimate for a span that's almost always zero-cost?
Show answer
Because QPS is computed purely from summed statistical weights, not from raw row counts. When a zero-cost row survives the 10% downsampling, its weight is scaled up by 10× to compensate — so the total weight (and hence estimated QPS) is preserved even though 90% of the rows were discarded. Only the cost sum needs the actual rows; cost is zero either way, so nothing about the cost total is lost either.Misconception: that dropping 90% of rows must lose 90% of the signal. Downsampling with weight rescaling is designed precisely so that summed statistics survive intact — it's compression, not data loss, for the metrics that matter.
Problem 6 · hard
"Small" services (low, spiky QPS) show much wider CPU-error distributions than medium/large ones, even under skeletal tracing. Why does service size affect sampling accuracy at a fixed sampling probability?
Show answer
A fixed sampling probability applied to a low-traffic, unpredictable service yields very few actual samples per unit time, and those samples are drawn from a bursty, non-smooth traffic pattern. Medium/large services use global load balancers that spread traffic evenly across jobs and regions, producing smooth, predictable patterns that a fixed-rate sample estimates well. Small services get both fewer samples and a lumpier population to estimate from — compounding the error. The paper notes small services are only ~2% of RPC profiles, so this doesn't hurt overall accuracy much.Misconception: that sampling error only depends on the sampling rate. It also depends on traffic smoothness/volume — the same 1/10,000 rate is far noisier for a spiky, low-QPS service than for a load-balanced, high-QPS one.
Problem 7 · medium
A team discovers via QProf that 30% of a service's CPU footprint is spent computing empty ad-candidate sets that return nothing to users. Is fixing this a "make it faster" optimization or a "room-at-the-top" optimization, and why does the distinction matter?
Show answer
It's room-at-the-top: the fix isn't to make the empty-set computation run faster, it's to recognize the work produced no useful output and skip or avoid it. A conventional CPU profiler would show exactly where those cycles go (a hot function), tempting a team to micro-optimize that function — but the actual 30% win comes from not doing the computation at all when it's known to be futile.Misconception: that a profiler pointing at "hot code" always means "optimize that code." Sometimes the honest fix is to stop calling it under conditions where it can't help — a distinction only a whole-request cost view like QProf's makes visible.
Problem 8 · easy
QProf's ground truth for validation is the background CPU profiler's self-cost measurements. Why can't the paper directly validate transitive cost the same way?
Show answer
Because there is no independent, trusted profiler that already measures transitive cost across an entire distributed system — if one existed, QProf itself wouldn't be needed. The paper instead validates the piece it can check (self cost per RPC, against the background profiler) and argues that if self cost is accurate and the trace structure is unbiased, transitive cost (which is just self costs correctly summed up the tree) follows.Misconception: that "validated" means every claim was independently checked end-to-end. Here it means the accurate primitive (self cost) plus an argument about unbiasedness, not a direct ground-truth comparison for the headline metric.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1Is QProf a replacement for normal distributed tracing?▾
No. Skeletal traces are deliberately stripped of everything except structure and cost — they can't be used for interactive latency debugging of one specific request. Normal ("fat") traces still exist for that job; QProf's skeletal traces exist purely to support statistically clean, fleetwide cost aggregation.
Q2Why does making tracing "invisible" matter so much?▾
Because applications can and do change behavior when they know they're traced — most commonly, logging extra debug metadata via an RPC only when traced. If the trace itself reveals whether it's being observed, that observation contaminates the very data being collected. Invisibility (a permanently-false is_traced(), no-op annotation APIs) removes the application's ability to react at all.
Q3How does QProf get CPU cost for every service without asking teams to instrument anything?▾
It piggybacks on an already-existing, always-on ambient CPU profiler that every C++/Java process runs. QProf adds one atomic counter to the per-query TraceContext; the profiler's periodic interrupt increments whichever counter is currently installed on that thread. Since the RPC framework guarantees correct TraceContext propagation fleetwide, coverage is automatic.
Q4Why is a single CPU sample usually reported as zero cost?▾
The profiler only fires every 10ms. Most individual spans live for far less time than that, so the interrupt simply never lands during their lifetime — recording zero. This isn't a bug; over trillions of spans per day, the law of large numbers still produces an accurate aggregate picture for any given RPC.
Q5Why write CPU data directly into the trace instead of tagging CPU samples with trace/span IDs (like other observability tools)?▾
Tagging every CPU sample with a high-cardinality trace_id prevents identical samples from being aggregated together, which balloons storage at warehouse scale — and it requires an expensive join between two huge tables at query time. Writing the already-summed cost straight into the trace avoids both problems, at the cost of losing the ability to inspect individual raw CPU samples later (which the paper argues is rarely needed — most traces are never viewed).
Q6What exactly makes a "forced" trace unusable for cost statistics?▾
Two separate problems: it typically has no well-defined sampling probability (it depends on arbitrary business logic that can't be measured after the fact), and it's frequently non-root (middleware decided to force it), producing a partial trace missing upstream cost. Either problem alone makes the Horvitz–Thompson "unsampling" math invalid.
Q7How does batching get a well-defined sampling probability if the requests inside are unpredictable?▾
By not deriving it from the requests inside at all. BatchedTraceContext flips its own independent, uniform coin when the batch is created. If the batch wasn't already sampled but a request added to it later turns out to be traced, the batch retroactively becomes non-uniformly sampled too — matching the intuitive "trace if anything inside is traced" behavior, while being excluded from clean statistics exactly like any other forced trace.
Q8How accurate is QProf, really?▾
With skeletal tracing, 73% of RPC profiles measure QPS within 10% of ground truth (up from 65% with normal tracing), and 47% measure CPU within 10% (up from 32%). For Java services specifically — hit hardest by tracing overhead — accuracy within 10% jumped from 24% to 61%.
Q9What causes QProf to underestimate cost?▾
Three main causes: throttling (overloaded trace collectors drop data), tracing API misuse (forced traces excluded from the usable population), and huge traces exceeding the in-memory assembly limit on a single machine. All three remove data rather than distort it, so they bias estimates downward.
Q10Does QProf measure latency too?▾
Not as its primary focus. Cost metrics (CPU, TPU, disk) are trivially summable regardless of concurrency, which is what makes trace-based aggregation tractable. Latency requires reasoning about parallelism (e.g. max, not sum, across concurrent branches) and has no single agreed-upon definition for related concepts like lock contention — the paper notes this is ongoing work.
Q11How is QProf different from Transitive Resource Accounting (TRA), the most similar prior system?▾
TRA also attaches cost-per-query to traces and aggregates offline, but it relies on modeling historical tracing overhead and subtracting it after the fact, rather than reducing overhead at the source — and it doesn't address observer effects at all. QProf instead eliminates most overhead and observer effects up front via skeletal tracing, which the paper argues is far more reliable than post-hoc correction across a hugely diverse fleet.

Glossary & further reading

Every term in one place, then a path to go deeper, then exactly which numbers are the paper's own.

Core terms
QProfThe paper's cost profiler: builds on RPC tracing to measure transitive cost across an entire distributed service, treated as one program.
Skeletal tracingAn invisible, independently & uniformly sampled, root-only, minimal-annotation tracing mode built specifically for unbiased cost statistics.
Transitive costA query's total resource spend, including everything it triggers downstream — not just its own self cost.
Observer effectWhen the act of tracing changes application behavior (e.g. logging extra data only when traced), contaminating the trace-derived statistics.
Unsampling (HT estimator)Weighting each sample by 1/sampling_probability and summing — the Horvitz–Thompson estimator — to recover a fleetwide total from sparse samples.
Fan-in / BatchedTraceContextThe API that gives a batched (merged) request its own independent sampling decision, then stitches it to a fairly-chosen sampled parent.
Ambient CPU profilerAn always-on, per-thread sampling profiler (10ms interrupts) wired into the TraceContext to attribute CPU to individual queries with zero manual instrumentation.
Room-at-the-topOptimization by doing less work for the same result (skipping, caching, batching) rather than doing the same work faster.
Supporting terms
Trace / spanA trace is a whole distributed computation (tree of spans); a span is one logical unit of work, usually one RPC.
TraceContextThe reference-counted, per-query runtime object (installed in thread-local storage) representing the currently active span.
Uniform vs. forced samplingUniform = fixed probability 1/N, statistically usable. Forced = arbitrary business logic, no well-defined probability.
Partial traceA trace sampled starting mid-tree (by middleware, not the root) — missing all cost above the sampling point.
Callstack expansionPostprocessing step turning each span into a full ancestor chain, producing O(N·M) rows from N spans of average depth M.
Priority inversionLow-priority work (e.g. a batch job) inducing demand on expensive, high-priority resources it wasn't provisioned to consume.
RPC profileThe unit QProf reports on: the tuple (RPC name, job user) — roughly O(10k) distinct profiles fleetwide.
Symmetric errorQProf's evaluation metric (Eq. 5): reports how far QProf's estimate is from ground truth, in the same relative units whether it over- or under-estimates.
