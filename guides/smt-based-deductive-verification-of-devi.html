PLOS 2026 · A Field Guide

Proving a driver correct by trusting the contract, not the code on the other side

A real, high-performance Ethernet driver for LionsOS, fully verified with an SMT solver — not by modelling the device or the OS in detail, just the promises they make to each other.

📄 "SMT-based Deductive Verification of Device Drivers" · Tyler et al., PLOS '26 🎓 Some OS/verification basics assumed — the primers cover them ⏱ ~25 min read
🧾

Verify the driver only against the interface CONTRACT — never against the concrete device or OS implementation — and the driver's correctness follows from that contract alone, provided the real device and OS actually honour it.
Pre/postconditions in, proof obligations out.

Before you begin

Quick glossary, then eight ideas the paper assumes

First the acronyms, defined once so the rest of the guide can use them freely. Then eight primer cards — collapsed, tap any open, read in order or jump to what's unfamiliar.

Acronyms used throughout

SMTSatisfiability Modulo Theories — the class of automated solver (Z3, cvc5) that checks satisfiability of logical formulas; verification tools use this by checking that the negation of an obligation (a potential counterexample) is unsatisfiable, not by asking "is this formula satisfiable?" directly.
ILIntermediate Language — Viper's own program representation, the transpiler's output target.
IDFImplicit Dynamic Frames — Viper's separation-logic-like permission system for reasoning about shared memory.
NICNetwork Interface Card — here, the 1 Gb/s Ethernet chip the driver controls.
MMIOMemory-Mapped I/O — device registers addressed like memory, mapped uncached.
DMADirect Memory Access — the device reads/writes data buffers in RAM without CPU involvement.
sDDFseL4 Device Driver Framework — LionsOS's driver model: isolated, single-threaded, event-driven.
SPSCSingle-Producer Single-Consumer — the lockless queue discipline used for all four driver↔OS queues.
Rx / TxReceive / Transmit — the two data directions, each with its own active/free queue pair.
ITPInteractive Theorem Proving — expensive, human-guided proof; the paper avoids it in favour of automated deduction.
TCBTrusted Computing Base — code you must trust unconditionally; the transpiler is currently part of it.
AST / LOCAbstract Syntax Tree (parsed program structure) / Lines Of Code — used to size the annotation effort.
Pancake driver code verified / the interface contract OS side device / hardware (unverified, trusted from the datasheet)
1Why device drivers, specifically, need verifying▾

Device drivers are among the most error-prone parts of an OS — they accounted for the majority of Linux CVEs reported 2018–22. The hard part isn't writing one driver correctly; it's that every platform has different device implementations, so new drivers appear constantly. Expensive interactive theorem proving (ITP) can't scale to that churn.

The paper's bet: automated deductive verification, backed by an SMT solver, can be made cheap and modular enough to re-use across drivers of the same class.

Now you're ready: everything that follows is about making that bet work — a language, a translator, and a contract-based proof structure.
2Pancake — a small, verified-compiler systems language▾

Pancake is C-like, built for low-level systems code, with one primitive type — the machine word — and fixed-width wraparound arithmetic. Crucially, its compiler is itself verified and its semantics are simple and precisely defined, which is what makes reasoning about a Pancake program tractable at all.

Now you're ready: the driver you're about to see is written in Pancake, not C — that's what lets the rest of this pipeline exist.
3Viper & permission predicates (IDF)▾

Viper is a verification infrastructure built on Implicit Dynamic Frames (IDF), a separation-logic-like logic. Every piece of memory has an associated permission, a fraction from 0 (no access) to 1 (full read/write access). Passing less than full permission at a call site lets Viper automatically infer the field didn't change — "automatic framing" — for free.

Now you're ready: "ownership" of a buffer or a queue field, throughout this guide, literally means holding permission 1 to it in Viper.
4SMT solvers as the proof engine▾

Viper doesn't prove anything itself — it hands proof obligations to a backend. This paper uses Silicon, Viper's symbolic-execution backend, which in turn calls an SMT solver (Z3 or cvc5) to decide whether each obligation holds. If the solver can't discharge a query, you get a failed proof, not a crash — but also not always a helpful error.

Now you're ready: "verification" in this paper concretely means "Silicon + Z3/cvc5 accepted every generated query."
5The LionsOS/sDDF driver model▾

LionsOS (seL4-based) drivers are deliberately simple: single-threaded, isolated, event-driven handlers — a model that traces back to Dingo's "active driver" idea for Linux. The sDDF (seL4 Device Driver Framework) additionally enforces strict separation of concerns: a driver's only job is translating a device-specific hardware interface into a device-class-generic OS interface.

Now you're ready: because that OS interface is identical for every Ethernet driver, verifying it once pays off across drivers — this is the paper's re-use argument.
6SPSC ring buffers & the ownership split▾

The driver talks to the OS through four lockless SPSC (single-producer single-consumer) queues: rx_active/rx_free and tx_active/tx_free. Each queue is a circular array with a head (where the consumer dequeues) and a tail (where the producer enqueues). The consumer owns entries [head, tail); the producer owns the rest.

Now you're ready: nearly every proof obligation in this paper reduces to "did the driver only ever touch the end of the queue it's allowed to touch?"
7MMIO, DMA, and weak-memory ordering▾

MMIO registers and queue descriptors are mapped uncached (Device-nGnRnE on Arm), so the driver just needs correctly ordered accesses (memory barriers) — no cache-coherence concerns. Data buffers, by contrast, are mapped cached and need explicit software cache management (handled outside the driver). Shared accesses behave like C's volatile: a read may return a value no prior driver write produced, and the compiler must not reorder, fuse, add, or remove these operations.

Now you're ready: this is exactly why shared memory can't be modelled as ordinary Viper memory — Section 2.3 has to invent something else.
8Ghost state — proving properties about history▾

Some properties ("every buffer that left this queue eventually arrived somewhere else") can't be stated using only the current shared state — you need to remember what happened. A ghost set is data that exists only in the proof, not in the running program, recording that history.

Now you're ready: ghost sets are how "correct buffer movement" (Section 3.3.3) gets turned into something an SMT solver can actually check.
The whole story in one place

The Pancake-to-Viper approach, in a nutshell

The problem, the trick that makes it tractable, and what it bought.

Device drivers cause a disproportionate share of OS bugs, but every hardware platform needs its own driver — so per-driver interactive proofs (expensive, human-guided) can't keep up. The paper's answer is automated deductive verification: write the driver in Pancake (a small, verified-compiler systems language), annotate it with Viper-style pre/postconditions, and let a transpiler translate the annotated program into Viper IL, which Viper's Silicon backend checks by calling an SMT solver.

The key design move is where the proof stops: instead of modelling the real device or the rest of the OS, the authors write an interface model — a set of Viper methods whose pre/postconditions are exactly the device's and OS's contract with the driver (Section 3.2.3). Every shared-memory load or store the driver performs becomes a call into this model. The driver is then verified entirely against these contracts, never against anyone else's concrete code — which is what makes the proof modular: the same OS-interface contract applies to every Ethernet driver under sDDF. What this proves is the driver's correctness relative to those contracts — it does not independently verify that the real OS or device implementation actually lives up to them.

Because there's no notion of global time, the model can't assume its view of external state is current — so it treats every precondition as a stable property (one that stays true no matter how far the OS or device run ahead), and every load as returning a non-deterministic but bounded update to that view. A ghost set tracks buffer history so the driver can be proved to move every buffer correctly, not just to avoid crashing.

The payoff: four properties proved (device-protocol adherence, queue integrity, correct buffer movement, no lock-up) on a real, deployed 1 Gb/s Ethernet driver; 1,501 lines of annotations over 11.5 person-weeks, done by an undergraduate with no prior verification background; the process caught one queue-contract violation and two weak-memory bugs; and the verified driver runs within ~20% of the hand-tuned, unverified C original.

🥞 Key takeaways

  • Verify against the interface contract, never the device/OS implementation — this is what makes the proof modular and re-usable, though it assumes the real OS/device honour that contract rather than proving they do.
  • Permissions (0→1, IDF) encode ownership of shared queue fields; passing less than full permission gives "unchanged" for free.
  • No global time: loads return non-deterministic updates; preconditions must be stable under arbitrary further OS/device progress.
  • Ghost sets track buffer history, enabling proofs about movement, not just present-state safety.
  • Four properties proved: device-protocol adherence, queue integrity, correct buffer movement, completion (no lock-up).
  • Cost: 1,501 LOC of annotations, 11.5 person-weeks, by a verification novice. Found 3 real bugs.
  • Performance: verified driver within ~20% CPU of unverified C — most of the gap traces to Pancake's current codegen plus code restructured for verification simplicity, which the authors expect compiler work to shrink.
Five everyday pictures

How to think about the proof

Each stands alone — read in any order. Every card ends with where the picture stops being true.

Ownership · Permission predicates (IDF)

Checking out a library book

A book is either on the shelf (library owns it) or in your bag (you own it, full stop) — you can't both hold it and have the library lend it elsewhere. Viper's permission (0 to 1) works the same way for a queue field: holding full permission means you — and only you — may read or write it, and passing permission away means you've relinquished it.

Where it breaks: a library book is all-or-nothing; Viper permissions are fractional, so two parties can jointly hold read-only access — richer than a simple checkout desk.
No global time · Non-deterministic loads

A whiteboard someone else keeps updating

You glance at a shared whiteboard, then look away. When you look back, someone may have erased and rewritten it any number of times — you can't assume it's still what you last saw, only that whatever it now says obeys the house rules (e.g. "the running total only ever goes up"). A shared-memory load works the same way: its postcondition says the new view is consistent with the old one, not identical to it.

Where it breaks: a whiteboard has no protocol guaranteeing anything about what gets written; the driver's model only works because the OS/device's updates are known to preserve specific stable invariants.
History tracking · Ghost sets

A ship's logbook

A captain's log records every cargo loaded and unloaded, so that months later you can still answer "did container #42 ever leave the ship?" A ghost set plays the same role for buffers: it's data that exists only in the proof, recording every buffer added to or removed from a queue or the device, so "buffer movement" can be proved even after the buffer has left the driver's current view entirely.

Where it breaks: a logbook is optional record-keeping after the fact; a ghost set is essential — without it, "every buffer ends up somewhere" isn't even expressible, let alone provable.
Reasoning under uncertainty · Stable properties

A watermark that never recedes

A tide gauge's high-water mark only ever moves up; once painted, you can trust it no matter how long you've been away — the tide can't un-happen. The paper leans on the same trick: every precondition it assumes must be stable — true now and guaranteed to stay true no matter how far the OS or device run ahead before the driver checks again.

Where it breaks: not every property is a watermark. A transient property (true now, possibly false later) would be unsafe to assume this way — the paper is explicit that this only works because it checked every precondition for stability first.
Scope of the proof · Modularity

A supplier contract, not a factory tour

A manufacturer signs off a component by checking it meets the spec sheet — not by touring the supplier's factory floor. The driver is verified the same way: against the device's and OS's documented contract (pre/postconditions), never against their actual running code. That's what lets one proof of the OS interface apply to every Ethernet driver under sDDF.

Where it breaks: a contract review can't catch a supplier secretly violating the paperwork. If the device silently breaks its modelled protocol (hardware manuals are notoriously imprecise), the driver's correctness proof rests on an assumption nothing here checks.
The full explanation

How it actually works

Section by section, with the paper's contract examples reproduced and its key diagrams rebuilt.

1 · The pipeline

The developer writes Pancake source with Viper-style annotations. The transpiler invokes the Pancake compiler in a diagnostic mode to get the parsed AST (including annotations), then emits Viper IL — one file per Pancake function — plus calls into external Viper model files that encode the device and OS contracts. Silicon, Viper's symbolic-execution backend, discharges the resulting proof obligations to an SMT solver (Z3 or cvc5).

2 · Machine words — Int or bitvector, kept separate per query

Pancake's only primitive type is the machine word, with fixed-width wraparound arithmetic. The transpiler offers two encodings: plain Int, or an SMT-LIB BitVecDomain. Mixing integer and bitvector reasoning in one SMT query is hard for solvers, so the developer keeps each function mostly one style; rare bitwise operations inside an Int-encoded function get locally converted to bitvector and back. Arithmetic is lowered to three-address form, and Int-encoded operations get an automatic bounds check after each step.

3 · Local vs. shared memory

Memory the driver exclusively controls is modelled differently depending on its kind. The driver-local heap is represented as ordinary word-addressed Viper memory guarded by permissions — standard IDF. Stack variables, by contrast, become ordinary Viper variables with no permission predicates at all, and globals are modelled as named global resources. Memory that may be concurrently updated by the device or OS — MMIO registers, DMA descriptors, OS-shared queue metadata — behaves like C's volatile: a read may not reflect the driver's own last write, and the compiler must not reorder, fuse, add, or remove the access. These accesses are transpiled into calls to external Viper methods supplied by a model file, whose contract (pre/postcondition) is checked/assumed at the call site.

4 · The interface model & concurrency

The model has no notion of global time: its fields represent the driver's most recent view of external state, not a live snapshot. Store contracts are deterministic (the driver alone drives the change); load contracts are non-deterministic (the OS/device may have advanced things meanwhile), constrained only by stable invariants that can never be falsified by further execution.

method store_tx_free_tail(gv: Ref, value: Int)
  // preconditions on the nature of the inputs
  requires acc(gv.tx_free.net_tail)
  requires value == (gv.tx_free.net_tail + 1) % (MAX_INT16 + 1)
  // precondition on the state: queue must not be full
  requires gv.tx_free.net_tail - gv.tx_free.net_head != QUEUE_CAPACITY
  // deterministic postcondition: the driver caused this change
  ensures gv.tx_free.net_tail == old(gv.tx_free.net_tail) + 1
method load_tx_free_head(gv: Ref, address: Int) returns (retval: Int)
  // take ALL permission — this is what allows non-determinism
  requires acc(gv.tx_free.net_head)
  ensures  acc(gv.tx_free.net_head)
  // the OS may have advanced head any number of times, but never past tail
  ensures gv.tx_free.net_head >= old(gv.tx_free.net_head)
  ensures gv.tx_free.net_tail >= gv.tx_free.net_head
  // what the driver actually observes, wrapped to 16 bits
  ensures retval == gv.tx_free.net_head % (MAX_INT16 + 1)
💡
Why take all the permission on a load? Viper's automatic framing would otherwise infer the field is unchanged when less than full permission is passed. Taking full permission suppresses that inference, forcing Viper to treat the field as freshly non-deterministic — exactly the behaviour a genuinely external write needs.

5 · Four properties, proved

PropertyWhat it rules out
Device protocol adherenceDriver misuses the NIC's MMIO/descriptor protocol (translated from the hardware manual).
Queue integrityDriver touches the wrong end of a queue, overflows/underflows it, or reads an empty queue.
Correct buffer movementA buffer vanishes or duplicates instead of landing in exactly its next correct queue/device slot (needs ghost sets).
Completion conditionThe driver stalls forever despite having work it could do and an idle device queue (lock-up).

6 · Practical friction with Viper and SMT

Holding permission >1 is an inconsistent assumption in Viper — it silently implies false, after which everything "proves." The authors guard against this with explicit refute false checks. Quantified properties fought back too: Viper's trigger syntax is restrictive, occasionally forcing dummy triggers for manual quantifier instantiation. And SMT solver choice mattered: Z3 (Viper's default) failed on many queries that cvc5 could close — though cvc5 ran slower overall, so timeout tuning was an ongoing, file-by-file balancing act.

Worked examples

Four calculations straight from the paper's own tables and contracts.

① The interface model is bigger than the driver

Table 1 gives: Interface Viper — Device 549 LOC, OS 443 LOC. Program — verified Pancake driver 362 LOC, verified Pancake queues 64 LOC. How do these compare?

  1. Total interface model: 549 + 443 = 992 LOC of Viper contracts.
  2. Total verified driver code: 362 + 64 = 426 LOC of Pancake.
  3. Ratio: 992 / 426 ≈ 2.3× — the contract is more than twice the size of the code it governs.
  4. Why that's not wasteful: the OS-interface half (443 LOC) is shared by every Ethernet driver under sDDF's separation-of-concerns design — write it once, re-use it everywhere.
🍯
Insight: in this style of verification, most of the intellectual cost is describing the contract precisely — the driver code itself is comparatively small.

② Where the 11.5 person-weeks actually went

Table 2: Device Protocol Adherence 2 pw/228 LOC; Queue Integrity 1.5 pw/123 LOC; Buffer Movement 4 pw/350 LOC; Completion Condition 2.5 pw/114 LOC; plus overhead — inlining duplication 250 LOC, weak memory 1.5 pw/280 LOC, other 156 LOC. Total 11.5 pw / 1501 LOC.

  1. Property-specific annotation: 228+123+350+114 = 815 LOC (54.3% of the total 1501).
  2. Not tied to a single property: 250+280+156 = 686 LOC (45.7%) — the paper just doesn't attribute these rows to one specific property. Inlining duplication and "other" are genuine boilerplate, but the 280 LOC of weak-memory annotations are still substantive verification work, not filler.
  3. Most expensive property: Buffer Movement, at 4 of 11.5 person-weeks (35%) and 350 LOC — more than any other single property.
  4. Cheapest: Queue Integrity, 1.5 pw / 123 LOC — the ownership contract of Section 3.2.3 does most of the work already.
💡
Almost half the annotation effort isn't tied to one property. Some of it — duplication from near-identical Rx/Tx paths — is genuine boilerplate ripe for automation; the weak-memory annotations, though also not property-specific, represent real verification work in their own right.

③ Checking a store precondition by hand

Take QUEUE_CAPACITY = 16. The model currently has tx_free.net_tail = 20, net_head = 5 (15 slots occupied). Can the driver call store_tx_free_tail to enqueue one more?

  1. Precondition: net_tail − net_head ≠ QUEUE_CAPACITY.
  2. Compute: 20 − 5 = 15.
  3. Compare: 15 ≠ 16 → precondition holds. The enqueue is allowed.
  4. After the call: postcondition gives net_tail = old(net_tail) + 1 = 21; now 21 − 5 = 16 = capacity — the next enqueue would be rejected.
🌱
One clean inequality is the entire "queue not full" check — no separate near-full special case needed.

④ Overhead: unverified vs. verified Pancake

Unverified Pancake adds 0–10% CPU over C; verified Pancake adds 10–20%. Why the jump, given the code does the same job?

  1. Unverified Pancake hand-caches global variables in locals to avoid repeated load/store sequences — close to C's efficiency.
  2. Verified Pancake reverts to direct global-variable use, because caching in locals made the proof harder to write (Section 4.1).
  3. Result: roughly an extra 10 percentage points of CPU overhead — mostly from Pancake's current global-load/store codegen, plus code restructured for verification simplicity (reverting the local-variable caching), not purely from the proof obligations themselves.
  4. Headline number: the fully verified driver still lands within ~20% of the unverified, hand-tuned C original.
💡
The authors expect ongoing Pancake compiler work on global-variable handling to eliminate most of this gap; the remainder reflects code restructured for verification simplicity rather than the proof obligations themselves.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
Why is a store method's postcondition deterministic (net_tail == old(net_tail)+1) while a load method's postcondition is non-deterministic (net_head ≥ old(net_head))?
Show answer
A store is driven only by the driver's own action — the driver alone decides to increment the tail by exactly one, so the new value is exactly known. A load observes memory the OS also writes; between the driver's last look and now, the OS may have advanced it an unknown number of times, so the postcondition can only bound the new value, not pin it down.Misconception: that determinism is about what Viper "can figure out." It actually reflects who controls the underlying memory — the driver, or someone else.
Problem 2 · medium
A 16-slot queue has net_tail = 30, net_head = 14. Is it safe to enqueue one more buffer? What's the state right after?
Show answer
30 − 14 = 16 = QUEUE_CAPACITY, so the precondition net_tail − net_head ≠ QUEUE_CAPACITY fails — the queue is already full, and the enqueue is disallowed. (Had it been 15, one more enqueue would be allowed, bringing the difference to exactly 16 and blocking the next one.)Misconception: thinking "one more slot" is always safe without checking; the precondition is the only thing standing between the driver and an overflow.
Problem 3 · medium
Why must a load method take the caller's entire permission to a field, rather than a partial fraction?
Show answer
Viper's automatic framing infers a field is unchanged whenever less than full permission is passed at a call. If the load took partial permission, Viper would (wrongly) assume the field kept its old value. Taking full permission suppresses that inference, which is exactly what's needed to let the postcondition assign a fresh, non-deterministic value reflecting the OS's unseen writes.Misconception: treating permission purely as an access-control gate, unrelated to how the proof reasons about value changes.
Problem 4 · hard
Why does Viper treat "permission > 1" as inconsistent (it implies false), and why did the authors add explicit refute false statements?
Show answer
Permission fractions model a resource that must sum to at most 1 (full access) across every holder — it's the core soundness invariant IDF borrows from separation logic. "More than full" access isn't meaningful, so Viper's logic treats it as a contradiction. The danger: once a contradiction (false) sits in the assumption context, every subsequent goal trivially "proves," silently masking real bugs. A refute false statement deliberately checks that no contradiction has crept in, catching that silent failure mode early.Misconception: that a successful-looking proof means the property genuinely holds — an inconsistent context proves everything, including nonsense.
Problem 5 · medium
The paper says preconditions must assume the interface model's state is "arbitrarily outdated." What property of a precondition makes that safe to assume?
Show answer
The precondition must be stable — true now, and guaranteed to remain true no matter how much further the OS or device execute before the driver checks again. "Head ≤ tail" is stable because nothing the OS legitimately does can violate it. A non-stable (transient) property could become false in the gap between "when it was last observed" and "now," so assuming it from a stale view would be unsound.Misconception: assuming "outdated" always means "possibly wrong." Stability is precisely what makes outdated information still trustworthy.
Problem 6 · hard
Verifying against the interface contract (not the concrete device/OS) is called "modular." What does this modularity buy you, and what does it explicitly not prove?
Show answer
It buys re-use: the driver is checked once against a fixed contract, and — because sDDF gives every Ethernet driver the same OS interface — that half of the model (443 LOC) applies unchanged to any other Ethernet driver. What it does not prove: that the real device or OS actually honours the modelled contract. The device-protocol model is hand-translated from a hardware manual, which the paper itself notes "tend to be imprecise and frequently wrong" — so driver correctness here is conditional on that translation being right.Misconception: that "the driver is verified" means the whole system is proven correct end-to-end, rather than correct relative to an assumed (and possibly flawed) interface model.
Quick answers

Frequently asked questions

Nine questions newcomers ask most. Tap any to expand.

Q1Why not just verify the driver in C directly?▾
C's semantics (undefined behaviour, aliasing rules, unspecified evaluation order) make automated reasoning harder and less predictable. Pancake has a verified compiler and deliberately simple, fully-defined semantics — including explicit fixed-width wraparound arithmetic — which removes a whole category of "does the compiler actually preserve my proof" concerns.
Q2Is the transpiler itself trusted?▾
Currently yes — it's written in Rust and sits in the trusted computing base (TCB): a bug in the transpiler could produce Viper IL that doesn't faithfully represent the annotated Pancake source, silently invalidating a "proof." The authors are rewriting it in HOL4 and developing a Viper semantics specifically to prove this correspondence and remove that trust requirement.
Q3What's the difference between Viper, Silicon, and an SMT solver?▾
Viper is the verification language/infrastructure (IDF-based permissions, methods, pre/postconditions). Silicon is one of Viper's backends — a symbolic-execution engine that walks the program and generates proof obligations. Those obligations are then handed to an SMT solver (Z3 or cvc5) to actually decide satisfiability.
Q4Why keep integer and bitvector reasoning separate?▾
SMT solvers find it much harder to reason across mixed integer/bitvector contexts in one query than to stay within one theory. The transpiler lets each function pick predominantly one encoding, converting only the occasional bitwise operation locally, keeping most queries single-theory and fast.
Q5How is shared (volatile-like) memory different from ordinary driver memory in the model?▾
Driver-local memory is modelled differently by kind: the heap is ordinary word-addressed Viper memory guarded by permissions; stack variables become plain Viper variables with no permission predicates at all; and globals are modelled as named global resources. Shared memory (MMIO, DMA descriptors, OS-shared metadata) is never modelled as memory at all; every access becomes a call to an external Viper method whose contract captures exactly what the driver may assume and must establish, mirroring C's volatile semantics.
Q6Did the verification effort actually find real bugs?▾
Yes — one queue-contract violation and two weak-memory bugs, described as "rather subtle errors." These are exactly the class of bug that's hard to catch with testing (timing- or ordering-dependent) and where an SMT-checked contract earns its cost.
Q7How hard was the annotation work, really?▾
1,501 lines of annotations over 11.5 person-weeks, performed by an undergraduate (the first author) with no prior formal-verification expertise. Most functions verify in seconds to a few minutes; four more complex ones take 15–25 minutes; the four most involved take 1–3 hours each.
Q8How much does correctness cost in raw performance?▾
On an i.MX8MQ (4× Arm Cortex-A53, 1 GHz) echoing 1.5 kB Ethernet frames: unverified Pancake adds 0–10% CPU over the original C driver, verified Pancake adds 10–20%. As a share of total system CPU the overhead is described as "in the noise." Most of the gap traces to Pancake's current global-variable codegen and to code restructured for verification simplicity, not to the proof itself.
Q9Does this generalise past this one driver?▾
The OS-side interface (443 LOC of model, plus much proof structure) is identical for every Ethernet driver under sDDF's separation-of-concerns design, so it should be directly re-usable. The device-side model (549 LOC) is specific to this NIC, though the authors expect similar-class devices (other NICs, buses) to share significant structure — and a concurrent project aims to derive such device models automatically from Verilog.

Related work

Dingo: Taming Device Drivers medium

Ryzhyk, Chubb, Kuz, Heiser · EuroSys · 2009

Source of the single-threaded, event-driven "active driver" model this paper's driver follows.

Automatic Device Driver Synthesis with Termite medium

Ryzhyk et al. · SOSP · 2009

Formalised device/OS interfaces (Tingu) and synthesised drivers from them — a generative cousin of this paper's verification approach.

Sound Formal Verification of Linux's USB BP Keyboard Driver hard

Penninckx et al. · NASA Formal Methods · 2012

SMT-based (VeriFast) memory/data-race safety and API-usage verification of a real driver — safety only, no OS-protocol or functional-correctness proof.

Checking the Hardware-Software Interface in Spec# medium

Bierhoff and Hawblitzel · PLOS · 2007

Verified correct device communication for a NIC driver on x86 (no weak memory) — device-side only, no OS interface.

Verus: Verifying Rust Programs using Linear Ghost Types hard

Lattuada et al. · OOPSLA · 2023

The verification framework behind concurrent work (Chen et al. 2024) attempting real-world Rust driver verification.
