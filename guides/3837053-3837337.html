HotStorage 2026 · A Field Guide

Checkpointing that never touches the host, because the host is already busy

Video LLM training keeps the CPU decoding and cropping frames every iteration. Stage a checkpoint in host DRAM at the same time, and you steal the exact bandwidth the pipeline needs. This is the plain-English story of FlashStash, a computational-SSD checkpointing system that removes the host from the datapath entirely.

📄 "The Host Is Not Idle" · Kang, Ko, Lee, Park, Kim, Jung (KAIST CAMEL) 🎓 GPU/storage-systems background assumed — primers cover it ⏱ ~25 min read
💾

Commit checkpoints straight from GPU to SSD — durable the instant they land in the SSD's own DRAM, never waiting on flash or borrowing host bandwidth.
Move the traffic off the contended path, then hide what's left behind compute.

Before you begin

Quick glossary, then the primers

The paper leans on a dozen acronyms before page two. Skim these once, then the primers below build the mental model in order.

Quick glossary — key acronyms

1Video LLM training's extra stage: host preprocessing▾

A video LLM turns each clip into a sequence of patch embeddings (via a ViT) and feeds them alongside text tokens into the LLM backbone. Before that can happen, the host CPU must decode the compressed video and resize/crop frames to the encoder's fixed input size — every single iteration, since decoded frames are ~100× larger than the compressed dataset and can't be cached.

Frameworks hide this by pipelining: while the GPU computes iteration t, the host prepares iteration t+1. This only works if host prep finishes faster than a GPU iteration.

Now you're ready: the host isn't idle during video LLM training — it's on a tight budget, one GPU-iteration wide, every iteration.
2Why checkpoint at all, and why so often▾

Large clusters fail routinely — Llama 3's 16,384-GPU run hit 466 interruptions in 54 days, about one every three hours. A checkpoint lets a job resume from its last save instead of from scratch. The metric that matters is ETTR: useful time ÷ total time, traded off between checkpoint overhead and rollback loss.

The less time between checkpoints, the less work a failure destroys — so the ideal is checkpointing every iteration, provided the per-checkpoint cost is near zero.

Now you're ready: "near-zero-cost, every-iteration checkpointing" is the explicit target this paper — and the ones before it — is chasing.
3The standard trick: stage in host DRAM, persist in the background▾

Existing systems (Gemini, CheckFreq) copy the checkpoint from GPU memory into host DRAM — fast, so the GPU resumes almost immediately — then slowly persist it in the background (to a remote node's memory, or to local SSD) while the GPU keeps computing.

This only works if the host has spare cycles and spare memory bandwidth while the GPU computes — the assumption text-only LLM training usually satisfies.

Now you're ready: this is the assumption video LLM training breaks — the host is busy with decode/resize, not idle.
4Why this breaks: shared, finite host DRAM bandwidth▾

Host-staged checkpointing and resize/crop preprocessing both hammer the same host DRAM bandwidth. When checkpoint traffic saturates it, preprocessing slows down, misses its one-iteration budget, and the GPU stalls waiting for data — a classic bandwidth-contention problem, not a compute problem.

Sparse MoE backbones make it worse: they shrink each GPU iteration (less active compute per token) while the checkpoint size — full weights and optimizer states — stays the same, so the same checkpoint cost eats a larger share of a shorter iteration.

Now you're ready: the fix has to remove checkpoint traffic from host DRAM's bus, not just make it "background."
5GPUDirect RDMA and peer-to-peer DMA▾

Normally, moving GPU data to a device involves the host CPU as a middleman. GPUDirect RDMA instead maps a region of GPU HBM into the PCIe address space (via a resizable BAR), so a third-party device — another GPU, a NIC, or here, an SSD — can DMA it directly, peer-to-peer. The host driver still resolves addresses and hands off a descriptor for each checkpoint, but it's off the data path — none of the checkpoint bytes ever flow through the host.

Now you're ready: this is the mechanism FlashStash uses to get checkpoint data from GPU to SSD without the host CPU or its DRAM in the path.
6Computational SSDs (CSSDs)▾

A CSSD is a drive with onboard compute — here, an FPGA — that can transform data as it streams through the device, instead of just storing bytes. Placing compression logic inside the SSD means the host never even sees the uncompressed checkpoint, and the compute happens right next to where the data will ultimately live.

Now you're ready: FlashStash's pruning, quantization, and reconstruction all run as small accelerator modules inside the SSD.
7Checkpoint compression: prune, then quantize▾

Adjacent checkpoints differ only slightly — most weights barely move between saves. ExCP, the compression scheme FlashStash builds on, exploits this: it magnitude-prunes the weight residual (the change since the last checkpoint) and the optimizer's momentum, keeping only the significant survivors, then applies non-uniform quantization (𝑘-means clustering to a small codebook) to shrink what's left — attaining roughly 70× compression with negligible accuracy loss.

Now you're ready: FlashStash's core contribution is deciding where and when each of these two stages runs — not inventing new compression math.
8Power-loss protection: why volatile DRAM can count as durable▾

Enterprise SSDs carry small capacitors that, on power loss, keep the device alive just long enough to flush its internal DRAM buffer to flash. This is PLP. It means data sitting in the SSD's internal DRAM survives a power failure just as reliably as data already on flash — the flush is guaranteed, just delayed.

Now you're ready: this is why FlashStash can call a checkpoint "committed" the moment it reaches internal DRAM, before it ever touches flash.
The whole story in one place

FlashStash in a nutshell

The problem, the two-phase fix, and how the pieces connect.

Video LLM training keeps the host CPU busy decoding and resizing frames every iteration, leaving no spare memory bandwidth for the checkpoint staging that existing systems (Gemini, CheckFreq) assume is free. Under intensive checkpointing this can slow training by up to 157.5×, because checkpoint traffic saturates host DRAM bandwidth and delays the memory-intensive resize/crop step, which in turn stalls the GPU.

FlashStash removes the host from the datapath: checkpoints move peer-to-peer from GPU HBM directly to the SSD via GPUDirect RDMA, never touching host DRAM. But once host DRAM no longer buffers the write, flash's own low bandwidth would sit directly on the critical path — so FlashStash relocates the durable commit point inside the SSD: a two-phase scheme streams the checkpoint through an inline pruning accelerator and commits it to the SSD's own internal DRAM (Phase 1), made durable by power-loss protection. The GPU resumes immediately. The slower, expensive quantization and the flash write itself are deferred to a background Phase 2, overlapped with the next iterations of GPU compute.

The payoff: on an H100 testbed training seven state-of-the-art video LLMs, FlashStash's full design (AccelSSD) sustains 89.3% of ideal no-checkpoint throughput even under per-iteration checkpointing — versus 65% for Gemini and just 10% for CheckFreq — for under 1 extra watt of in-storage compute.

🍯 Key takeaways

  • Host-staged checkpointing assumes an idle host; video LLM training makes the host busy every iteration decoding/resizing frames.
  • Checkpoint staging and preprocessing compete for the same host DRAM bandwidth — that contention, not compute, is the real bottleneck.
  • P2P GPU→SSD DMA removes the host from the path entirely, but naively exposes flash's slow write on the critical path.
  • FlashStash's fix: commit to the SSD's internal DRAM (durable via PLP) first, defer quantization + the flash write to a background Phase 2.
  • In-storage accelerators keep pruning off the critical path too, at under 1 W of estimated ASIC power.
  • Result: 89.3% of ideal throughput under per-iteration checkpointing — near-zero-cost.
Six pictures, one for the OS/memory-systems reader

How to think about FlashStash

Each stands alone. A few map directly onto DRAM–NVM tiering and CXL ideas — read those with your own systems in mind.

Two-phase commit · vs. write-back tiering

A hot tier that's already durable

DRAM–NVM tiering systems buffer writes in fast DRAM and migrate cold data to NVM later, accepting that a crash before migration can lose the buffered write. FlashStash's Phase 1 looks the same shape — commit fast, drain slow — but because the SSD's internal DRAM is PLP-backed, the "buffer" is already durable the instant data lands, not merely fast.

Where it breaks: your tiering migration is reversible and speculative (you can re-promote a page); FlashStash's Phase 1 commit is final — Phase 2 only changes location, never correctness.
Internal DRAM · vs. CXL persistent memory

A tiny NVDIMM inside the SSD

PLP turns the SSD's internal DRAM into "battery-backed" memory — durable at DRAM latency, the same promise CXL-attached persistent memory and NVDIMMs chase for the host memory bus. FlashStash gets that promise for free, because the durability boundary is already inside the device.

Where it breaks: this durable DRAM is megabytes, not the gigabytes a CXL memory expander offers, and it's reached over NVMe commands, not load/store — no byte-addressable access, no coherence.
P2P DMA · vs. CXL.mem bypassing the host controller

Skipping the shared memory controller

The whole reason this problem exists is that checkpoint DMA and preprocessing compete for the same host memory controller bandwidth — exactly the contention your own tiering work studies when migration traffic collides with application accesses. FlashStash's answer is what CXL.mem promises at a different layer: let the device reach its destination without routing through that shared controller at all.

Where it breaks: DRAM–NVM tiering can't usually take this shortcut — the NVM tier is still behind the same host memory controller, so migration traffic can't be P2P'd away the way checkpoint traffic can here.
Background merge · vs. LSM compaction

Compacting a chain of deltas

Each checkpoint after the first is a residual delta; the chain grows with every save, exactly like an LSM-tree's write-amplifying layer of SSTables. FlashStash periodically merges the chain into a fresh anchor, bounding both recovery latency and the accelerator resources needed to reconstruct — the same reason LSM engines compact and tiering systems batch cold-page scans into epochs.

Where it breaks: the merge trigger here is a fixed hardware resource limit (how many residuals the in-storage dequantizers can chain), not an access-frequency signal — there's no "hot/cold" decision being made, just a depth cap.
Host bandwidth contention · your research problem, restated

The same shared-bandwidth fight, one layer up

This paper's central measurement — checkpoint DMA and image resize/crop both fighting for host DRAM bandwidth, with the loser stalling — is structurally the contention problem tiering systems (TPP, HeMem, Memtis) manage between application access and background migration traffic on a shared memory channel.

Where it breaks: a tiering system typically has to schedule around contention (throttle migration, rate-limit scans) because both traffic streams share the same controller. FlashStash instead eliminates one stream from that controller altogether — a stronger fix than scheduling, but only possible because checkpoint data doesn't need to live in host DRAM at all.
Accelerator modules · vs. near-memory compute

Compute that lives where the data already is

FlashStash's pruning/quantization accelerators run inline as the checkpoint streams through the device — the same pitch behind near-memory or CXL Type-2 "smart" compute expanders: do the transform where the data already sits, instead of paying a round trip to move it to a general-purpose core first.

Where it breaks: these accelerators operate on streamed tiles at NVMe-command granularity, not cache-line-level ops — there's no coherence protocol or fine-grained addressing involved, just a fixed pipeline over a scatter-gather list.
The full explanation

How it actually works

From the contention that motivates it, through the two-phase commit, to how checkpoints are laid out and recovered on the device.

1 · The problem, precisely

Under checkpointing, host operation latency inflates by 9.21× for Gemini and roughly 158× for CheckFreq (normalized to one GPU iteration) — enough to push the host past the GPU's iteration time and stall it. The cause is visible in the breakdown: without checkpointing, memory-intensive resize/crop is 39.8% of host time; with checkpointing, its share jumps to 85.7%, because checkpoint staging is saturating the same host DRAM bandwidth that resize/crop needs.

2 · GPU–SSD direct checkpointing

FlashStash exposes GPU HBM through a PCIe resizable BAR via GPUDirect RDMA, pinning the checkpoint regions so a third-party device can read them peer-to-peer. The host driver resolves the physical addresses of weights and optimizer states into a tensor descriptor — a scatter-gather list tagging each region as weight or optimizer state — and hands it to the SSD via a custom NVMe command. The SSD's internal DMA logic then reads the checkpoint directly; the IOMMU still confines it to only the descriptor-listed regions, so no new trust boundary is opened.

3 · Two-phase checkpointing

# Phase 1 (on the critical path, kept short)
stream checkpoint tile-by-tile through prune accelerator
write pruned result to SSD internal DRAM
commit                                    # durable now, via PLP — GPU resumes

# Phase 2 (background, overlapped with GPU compute)
quantize pruned weights/optimizer state (k-means)
write quantized result to flash
finalize superblock with flash locations

Phase 1 only needs to prune the checkpoint enough to fit in the small internal DRAM — the expensive quantization step is deliberately delayed to Phase 2, where it's matched against flash's much lower write bandwidth instead of competing for critical-path time.

💡
Why is the early commit still durable? The dominant training failures (host or GPU crashes) sit in a failure domain independent of the SSD — the CSSD stays powered and simply finishes draining Phase 2 on its own. For the rarer power failure, PLP only needs to flush the small unwritten tail, not a whole checkpoint. A host-staged snapshot has no such independence, which is why prior systems fall back to replication instead.

4 · Accelerator logic

Three small modules do the work: a vector accelerator (a PE array of adders plus a flag reductor for the pruning bitmap and a max/sum reductor for 𝑘-means), a dequantizer for codebook-lookup reconstruction, and a sparse adder for bitmap-based residual accumulation. Background merging reuses the same datapath, so it adds no extra hardware. Together they draw 9.9 W on the FPGA prototype; given the roughly 12× FPGA-to-ASIC dynamic power gap, an ASIC version would add under 1 W — negligible for an enterprise SSD.

5 · Tolerating rarer failures

To survive the rare loss of the CSSD itself, FlashStash periodically flushes the already-compressed checkpoint to an independent storage server, multi-level-checkpoint style. Because the flush carries only the small compressed state, it adds negligible traffic, and a CSSD loss costs at most the progress since that last flush.

Follow the numbers, step by step

Worked examples

Four traces through the paper's real measurements: the host bottleneck, the E2E time it eats, why MoE sparsity makes it worse, and how FlashStash claws the throughput back.

① How host contention inflates preprocessing latency

Without checkpointing, host operations fit inside one GPU iteration. With CheckFreq's per-iteration checkpointing, the paper reports host latency reaching ~158× a GPU iteration's duration, and resize/crop's share of host time rising from 39.8% to 85.7%. What's happening?

  1. Baseline: host time = decode + resize/crop, and the whole thing fits inside one GPU iteration (normalized latency ≈ 1×).
  2. Add checkpointing: the checkpoint stage now shares host DRAM bandwidth with resize/crop. Decode is compute-bound and barely slows; resize/crop is memory-bound and slows drastically.
  3. Result: total host latency balloons to ~158× a GPU iteration for CheckFreq (vs. 9.21× for Gemini, which persists less aggressively) — and almost all of that inflation lands on resize/crop, whose share of host time jumps from 39.8% to 85.7%.
  4. Consequence: since the GPU can't start iteration t+1 until preprocessing for it finishes, a 158× host latency means the GPU is stalled for nearly the entire time — matching the reported 157.5× training slowdown for CheckFreq.
🍯
Insight: the training slowdown (157.5×) and the host latency inflation (~158×) are almost the same number — direct evidence that host DRAM bandwidth contention, not GPU compute, is the bottleneck.

② How much of end-to-end time checkpointing actually eats

The paper reports that per-iteration checkpointing leaves only 10.5% (Gemini) and 1.1% (CheckFreq) of E2E time as effective training. What overhead does that imply?

  1. Effective time is what's left after storage stalls and CPU stalls: Gemini = 10.5%, CheckFreq = 1.1%.
  2. Overhead = 100% − effective: Gemini's checkpointing overhead = 100 − 10.5 = 89.5%; CheckFreq's = 100 − 1.1 = 98.9%.
  3. That 98.9% figure reappears later as "the normal-SSD path" baseline the paper compares AccelSSD against.
  4. AccelSSD's own share of E2E time spent on checkpointing is reported as 10.7% — a drop from 98.9% to 10.7%, roughly a 9.2× reduction in overhead share.
💡
At the extreme (CheckFreq, per-iteration), a training job spends 99 out of every 100 seconds not training — checkpointing has effectively become the workload.

③ Why MoE sparsity makes checkpointing worse, not better

Table 3 lists Llama-4-Maverick at 400B total / 17B active parameters, routing 1 of 128 experts per token — the sparsest model tested, and the one that retains only ~2% of baseline throughput under per-iteration checkpointing. Why would fewer active parameters hurt more?

  1. Active parameter fraction: 17B ÷ 400B ≈ 4.25% of parameters do any work on a given token — so GPU compute per iteration is small relative to model size.
  2. But the checkpoint saves everything: all 400B parameters' weights and optimizer states must be persisted, active or not — checkpoint size doesn't shrink with sparsity.
  3. Shorter iteration, same checkpoint: lower active-compute means a shorter GPU iteration time, so the same (large) checkpoint cost now occupies a much bigger fraction of each iteration.
  4. Result: the sparsest model in the sweep (Llama-4-Maverick) is also the one whose throughput collapses hardest (~2% retained) — sparsity amplifies exactly the contention this paper targets.
🍯
Insight: as frontier multimodal models trend toward MoE for efficiency, they simultaneously make host-staged checkpointing's relative cost worse — a second, independent reason (beyond video preprocessing) to get the host off the path.

④ Compounding FlashStash's four design steps

Normalized throughput: DirectSSD 0.09 → CompSSD 0.35 → EarlySSD 0.43 → AccelSSD 0.89. What does each step contribute, and does the accuracy cost check out?

  1. CompSSD / DirectSSD = 0.35 ÷ 0.09 ≈ 3.89× — compression alone, by shrinking what flash has to absorb, more than triples throughput over raw P2P writes.
  2. EarlySSD / CompSSD = 0.43 ÷ 0.35 ≈ 1.23× — moving flash persistence and quantization to a background Phase 2 buys a further ~23%.
  3. AccelSSD / EarlySSD = 0.89 ÷ 0.43 ≈ 2.07× — accelerating the remaining critical-path step (streamed pruning) roughly doubles throughput again.
  4. End to end: 0.89 ÷ 0.09 ≈ 9.9× — going from naive P2P to the full design recovers nearly 10× the throughput.
  5. Accuracy check: fine-tuning LLaVA-Video-7B while forcibly recovering from a compressed checkpoint every 100 iterations across a 20,000-step run means roughly 200 forced recoveries — and the final loss differs from uninterrupted training by only 3.8%.
💡
No single step is free — pruning still costs something, quantization still costs something — the design's trick is where each cost is paid: off the critical path, or accelerated on it.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Text-only LLM pretraining checkpoints fine with host-staged systems. Why does the exact same technique fail for video LLM training?
Show answer
Host-staged checkpointing assumes the host has spare DRAM bandwidth while the GPU computes. Text-only training has little host-side work per iteration, so that assumption holds. Video LLM training adds a mandatory per-iteration host stage (decode + resize/crop) that already uses most of the host's budget — checkpoint staging traffic now competes for the same bandwidth and loses (or makes preprocessing lose).Misconception: that checkpointing overhead is purely a GPU/storage-bandwidth question. It's a host memory bandwidth contention problem specific to workloads that keep the CPU busy.
Problem 2 · medium
DirectSSD removes the host entirely via P2P DMA, yet it retains only 0.09× throughput — worse than Gemini's 0.65×. Explain, using what's still on the critical path.
Show answer
Removing the host fixes the contention problem, but DirectSSD still waits for the full flash write to complete before the GPU can resume — and flash bandwidth is far lower than host DRAM bandwidth. So DirectSSD trades "host DRAM contention" for "raw flash latency," and the latter turns out to be worse for training throughput than the contention it replaced.Misconception: that removing the host from the datapath is, by itself, the fix. It's necessary but not sufficient — the slow resource (flash) still has to be hidden, not just relocated.
Problem 3 · medium
FlashStash calls a checkpoint "committed" once it reaches the SSD's internal DRAM — which is volatile. Why is that not a durability gap?
Show answer
Two reasons. First, the dominant training failures (host crash, GPU crash) leave the SSD powered and untouched, so it can simply finish draining Phase 2 on its own — no data is lost. Second, for the rarer case of an actual power failure, the SSD's power-loss protection (PLP) guarantees enough energy to flush whatever's still in internal DRAM to flash before shutting down — so the "volatile" buffer is durable in practice, just not yet relocated.Misconception: that durability requires data to already be on non-volatile media. Durability really requires a guaranteed path to non-volatile media before power is lost — PLP provides exactly that guarantee.
Problem 4 · hard
From Table 3, compute Llama-4-Maverick's active-parameter fraction and explain why it suffers the worst checkpointing slowdown in the sweep, in terms of the ratio of checkpoint size to active compute rather than raw model size.
Show answer
Active fraction = 17B ÷ 400B ≈ 4.25% of parameters do any work per token (this 17B figure includes shared/non-expert components, not just the routed experts — it's a different quantity from "1 of 128 experts routed per token," which is ≈0.78% and not directly comparable to the 4.25% active-parameter share). Checkpoint size scales with total parameters (400B) regardless of sparsity, since all weights and optimizer states must be saved. But GPU iteration time scales with active compute (~17B-worth of FLOPs), which is small. A fixed, large checkpoint cost divided by a small iteration time yields a bigger relative overhead — which is why the sparsest model in the sweep also has the worst throughput retention (~2%) under per-iteration checkpointing.Misconception: that a model's overall size predicts its checkpointing overhead. It's the ratio of checkpoint cost to iteration time that matters, and sparsity shrinks the denominator without shrinking the numerator.
Problem 5 · medium
Why can't FlashStash just serve every checkpoint entirely from the SSD's internal DRAM and skip flash altogether?
Show answer
The internal DRAM is deliberately small — sized to hold one streamed, pruned checkpoint's worth of data, not a growing history of anchors and residual chains for a multi-billion-parameter model. Capacity, not durability, is the reason Phase 2 exists: the checkpoint has to move to flash to make room for the next one, even though it's already "safe" the moment it lands in DRAM.Misconception: that the PLP-backed internal DRAM could just replace flash entirely. It solves the durability-latency problem, not the capacity problem — those are separate constraints.
Problem 6 · hard
Using ETTR and MTBF, explain why "checkpoint less often" is not a free way to reduce FlashStash's already-small overhead.
Show answer
ETTR trades off checkpoint overhead against rollback loss: a longer interval between checkpoints reduces overhead (fewer commits) but increases the average work lost when a failure strikes at a random point between checkpoints, which happens roughly every MTBF (hours, at scale). Since FlashStash's per-iteration overhead is already near zero (89.3% of ideal), the overhead side of that trade is nearly flat — so backing off frequency mostly just adds rollback risk for negligible further overhead reduction. The paper's target of every-iteration checkpointing is specifically what near-zero overhead unlocks.Misconception: that checkpoint frequency and overhead trade off linearly regardless of the system. Once overhead is near-zero, the optimal frequency shifts toward "as often as possible," not toward some balanced middle interval.
Problem 7 · easy
The background merge interval is swept in the paper, and throughput degrades in a sawtooth pattern once the interval exceeds a resource cap (~16 checkpoints), before resetting at the next merge. Why doesn't "merge less often" simply keep improving throughput?
Show answer
Merging less often reduces merge overhead, but it also lets the residual chain grow longer. The device's dequantizer and sparse-adder accelerators can only reconstruct a chain up to a fixed length efficiently; past that cap, both checkpoint creation and recovery slow down until the next merge resets the chain — producing the observed sawtooth. There's a genuine sweet spot, not a monotonic "less is better" relationship.Misconception: that less frequent background work is always better for throughput. Here it trades merge cost against chain-reconstruction cost, and the hardware resource cap sets where the trade-off flips.
Quick answers

Frequently asked questions

Nine questions newcomers ask most.

Q1Is the host literally never involved in a FlashStash checkpoint?▾
Not entirely — the host driver resolves the tensor descriptor (which GPU regions hold weights vs. optimizer state) and issues the custom NVMe command that hands it to the SSD, and it does this on the control path for each checkpoint, not just once at setup. What FlashStash removes is the host from the data path: the checkpoint bytes themselves move peer-to-peer from GPU HBM to the SSD and never buffer in host DRAM, which is what keeps them off the contended bandwidth path.
Q2Why not just make the checkpoint smaller instead of restructuring the datapath?▾
FlashStash does compress (via ExCP-style pruning + quantization, ~70×) — but compression alone (CompSSD) only reaches 0.35× normalized throughput, because the compression compute itself still sits on the critical path, and flash persistence is still synchronous. The datapath restructuring (P2P + two-phase commit) is what removes the remaining stalls; compression and restructuring are complementary, not substitutes.
Q3What exactly happens to the GPU's own weights during compression — is training affected?▾
No. The GPU always continues training from its own uncompressed weights; the compressed checkpoint on the SSD is read back only during an actual recovery. So the failure-free training trajectory is bit-identical to training without FlashStash at all — reconstruction error only enters at a real recovery event.
Q4Why split compression into two phases instead of doing it all at once?▾
Pruning is cheap enough to run inline while streaming, so it stays in Phase 1 and shrinks the data to fit the small internal DRAM. Quantization (k-means clustering) is comparatively expensive; delaying it to Phase 2 matches its cost against flash's own low write bandwidth, where it's already overlapped with GPU compute — so its cost is hidden rather than eliminated.
Q5Does MoE routing make FlashStash's job harder, or does it help?▾
It makes the underlying problem worse (sparsity shrinks GPU iteration time while checkpoint size stays fixed, per Worked Example 3) — but FlashStash's fix (removing host contention, hiding flash latency) is orthogonal to sparsity, so it helps MoE and dense models roughly alike. The paper's throughput retention numbers are averaged across both dense and MoE models.
Q6What happens if the CSSD itself fails mid-checkpoint?▾
This is treated as a separate, rarer failure mode from host/GPU crashes. FlashStash periodically flushes the compressed checkpoint state to an independent storage server (multi-level checkpointing), so a CSSD loss costs at most the progress made since that last flush — not the entire run.
Q7Is this specific to video LLMs, or does it generalize?▾
The paper targets video LLMs as the heaviest current case, but the authors note the same structure — a host kept busy while frequent, large state saves are needed — shows up in audio/image-heavy multimodal training, text pretraining with online data filtering, and RL training with host-side rollouts.
Q8How much extra hardware does this actually require?▾
P2P DMA and PLP are already commodity features of today's GPUs and enterprise SSDs. The new pieces are a vendor-defined NVMe command and three lightweight accelerator modules, estimated at under 1 W on an ASIC. Adoption can be incremental — even the firmware-only stages (CompSSD, EarlySSD) already beat the host-staged SSD baseline severalfold before any accelerator is added.
Q9How does FlashStash compare to just writing checkpoints via GPUDirect Storage (e.g., FastPersist)?▾
GPUDirect-Storage-style approaches also bypass the host for the transfer, but they still leave the full flash write latency on the critical path — essentially what "DirectSSD" measures in this paper's evaluation, which retains only 0.09× throughput. FlashStash's contribution is hiding that flash latency too, via the internal-DRAM early commit and background Phase 2.

Gemini / CheckFreqPrior host-staged checkpointing baselines: Gemini replicates to a remote node's memory over NVLink; CheckFreq persists to local SSD.
Data stallGPU idle time caused by host preprocessing (or, here, checkpoint contention) not finishing before the GPU needs the next batch.
ZeRO-3Shards weights/optimizer states across GPUs; in this paper's evaluation (8-way TP × 16-way ZeRO-3), each node checkpoints its assigned shard to local SSDs.
Resize/cropReshaping native-resolution video frames to a ViT's fixed input size — the memory-bound host step most affected by contention.
