Stop parking checkpoints on a host that's already busy

Video-LLM training keeps the CPU decoding and resizing frames every iteration. The usual checkpointing trick — stage in host DRAM, write back later — assumes the host has spare DRAM bandwidth to spend on it. This is the plain-English story of FlashStash, which gets the host out of the way entirely.

📄 "The Host Is Not Idle" · Kang, Ko, Lee, Park, Kim, Jung (KAIST CAMEL) 🎓 OS memory-tiering / CXL background assumed — primers fill paper-specific gaps ⏱ ~25 min read
💾

Commit the checkpoint to where streaming it in makes it durable against host, GPU, and power failures (the SSD's PLP-backed DRAM) — not where it contends with the thing the host is busy doing.
Move the durable point off-host, then hide the slow flash write behind compute.

1Why video LLM training keeps the CPU busy▾

Video datasets are stored codec-compressed (decoded form would be ~100× bigger) and resampled with fresh random crops every epoch, so each clip must be decoded and resized on the fly by the host CPU, every iteration, for the next batch.

This is pipelined against GPU compute (host preps batch t+1 while GPU runs batch t), but only works if host prep is shorter than one GPU iteration.

Now you're ready: any extra host-side traffic — like checkpoint staging — eats into that margin and risks stalling the GPU.
2Why checkpointing exists and how it's normally hidden▾

At cluster scale, hardware failures are routine (Llama 3: 466 interruptions over 54 days on 16,384 GPUs — about one every 3 hours). Checkpointing saves weights/optimizer state so a failure only costs progress since the last save.

The standard trick (Gemini, CheckFreq): copy the checkpoint into host DRAM fast, then persist it to its real destination (another node's memory, or local SSD) in the background, overlapped with GPU compute.

Now you're ready: that trick assumes the host has spare DRAM bandwidth to spend on the staging copy — exactly what video preprocessing is already using.
3Memory bandwidth contention, not CPU-cycle contention▾

The paper's bottleneck isn't the CPU running out of compute cycles — it's host DRAM bandwidth. Resize/crop is memory-intensive (lots of pixel data moved, little compute per byte); checkpoint staging is also a big memcpy. Both compete for the same DRAM channels.

Now you're ready: this is the same resource-contention shape as DRAM/NVM tiering work — two consumers (preprocessing, checkpoint I/O) fighting over one scarce bandwidth pool, except here the fix is to remove one consumer from host DRAM entirely rather than schedule around it.
4What P2P GPU↔SSD actually means▾

GPUDirect RDMA exposes a region of GPU HBM to other PCIe devices via a resizable BAR. A third-party device — here, the SSD's internal DMA engine — can then read that memory directly, with no host-DRAM hop and no CPU involvement in the data path (the CPU only sets up the transfer descriptor once).

Now you're ready: "host-free" in the title means the checkpoint bytes never touch host DRAM, not that the host is uninvolved in setup.
5Why flash write latency can't just be exposed directly▾

Once you remove the host-DRAM staging buffer, the natural next step — write straight to flash — reintroduces a different stall: flash is slow (far lower bandwidth and higher latency than DRAM), and now that latency sits directly on the GPU's critical path at every checkpoint.

Now you're ready: FlashStash's whole design is finding a different place to put the "durable" moment that isn't flash — see Tab 4.
6PLP as a trick for treating DRAM as durable▾

Enterprise SSDs carry onboard capacitors (power-loss protection) that, on a power cut, keep the chip alive just long enough to flush internal DRAM to flash. That converts the SSD's internal DRAM — otherwise purely volatile — into something that survives the failures that matter.

Now you're ready: this is conceptually close to using a fast-but-volatile tier as if it were a persistent tier, under an explicit guarantee — the same move CXL-attached battery-backed memory makes, just inside an SSD instead of on the memory bus.
The whole story in one place

FlashStash in a nutshell

The contention problem, the fix, and the number it buys.

Host-staged checkpointing (Gemini, CheckFreq) copies the checkpoint into host DRAM so the slow secondary write can happen in the background. That design silently assumes the host has spare DRAM bandwidth. Video LLM training breaks the assumption: the host CPU is already decoding and resizing every incoming batch, a memory-intensive job. Checkpoint staging then contends for the same DRAM bandwidth, inflating preprocessing latency past one GPU iteration and stalling the GPU — up to 157.5× slower at per-iteration checkpointing for CheckFreq.

FlashStash removes the host from the datapath by committing checkpoints peer-to-peer from GPU HBM straight to a computational SSD. But a naive P2P write just relocates the stall: flash is slow, so writing straight to flash still blocks the GPU. FlashStash's fix is a two-phase commit: Phase 1 streams the checkpoint through in-storage accelerators that prune it to fit the SSD's internal DRAM, and declares the commit done once the pruned data lands there — durable against host/GPU crashes and, thanks to PLP, against power loss too, though a separate SSD failure still waits on periodic independent-server flushes. Phase 2 then quantizes and drains the pruned checkpoint to flash in the background, fully overlapped with GPU compute.

The payoff: on an H100 cluster training seven state-of-the-art video LLMs, FlashStash's full design (AccelSSD) sustains 89.3% of ideal no-checkpoint throughput, versus 65% for Gemini and 10% for CheckFreq — shrinking checkpointing's share of end-to-end training time from 98.9% to 10.7%.

🍯 Key takeaways

  • The bottleneck is host DRAM bandwidth contention between checkpoint staging and video preprocessing — not CPU compute, not GPU compute.
  • P2P DMA (GPU↔SSD) removes the host-DRAM hop, but naively exposes flash's slow write latency instead.
  • Two-phase commit relocates the durable point to the SSD's PLP-backed internal DRAM — commit is fast once pruning lands it there, flash write happens later, off the critical path.
  • Compression is split: cheap pruning runs inline (must fit internal DRAM); expensive quantization is deferred to the background flash write.
  • In-storage accelerators (vector unit, dequantizer, sparse adder) remove the remaining compression stall for <1 W (ASIC-projected).
  • Result: 89.3% of ideal throughput under per-iteration checkpointing, vs 65% (Gemini) / 10% (CheckFreq).
Five everyday pictures

How to think about FlashStash

Each stands alone. Every card ends with where it stops being literally true.

The core problem · Shared pipe

One faucet, two buckets

Host DRAM bandwidth is one faucet. Video preprocessing already keeps it nearly fully open. Pour a checkpoint through the same faucet and preprocessing's stream thins — it falls behind, and the GPU (which was waiting on the next preprocessed batch) stalls.

Where it breaks: a faucet is passive; DRAM bandwidth contention also adds queuing/scheduling effects that make the slowdown worse than a simple linear split (CheckFreq hits 157.5×, not 2×).
P2P DMA · Skipping a stop

Shipping straight to the warehouse

Normally a package (checkpoint) is driven to your office (host DRAM), re-boxed, then driven again to the warehouse (SSD). GPUDirect RDMA + the SSD's P2P DMA let the courier skip your office entirely and deliver straight from the factory (GPU HBM) to the warehouse — one hop, no detour through a building that's already crowded.

Where it breaks: the office isn't cut out of all decisions — the host driver still resolves addresses into a descriptor once per checkpoint; it's the repeated, bulky data transfer that's eliminated, not every host touch.
PLP · Relocating "durable"

A safe inside the armored truck

Flash is the bank vault — secure but a long drive away. FlashStash instead drops the checkpoint into a safe bolted inside the armored truck itself (the SSD's PLP-backed DRAM): once it's in the safe, it's protected against the truck losing power, so you can call the delivery "done" before it ever reaches the vault. The vault trip (flash write) still happens, just later, unhurried.

Where it breaks: PLP protects against power loss, not against the SSD itself dying — which is why FlashStash still periodically flushes a compressed copy to an independent server, the armored truck's own insurance policy.
Residual chain · Compounding debt

Sticky-note corrections on a ledger

Instead of rewriting the whole ledger (anchor weight) every checkpoint, FlashStash sticks a small note of just what changed (a residual) on top. Cheap to write, but reading the current balance means reading the ledger and every note since — the more notes pile up, the slower recovery and the slower the next compression pass. Periodically, FlashStash rewrites a clean ledger (background merge) and clears the notes.

Where it breaks: the merge itself competes for the same in-storage accelerators as live checkpointing, so merging too often defeats its own purpose — the paper leaves the scheduling of when to merge as future work.
The full explanation

How it actually works

The two-phase commit, the datapath, and the accelerators that keep both off the critical path.

1 · The datapath — cutting the host out

FlashStash exposes GPU HBM via a PCIe resizable BAR through NVIDIA GPUDirect RDMA. The host driver resolves the physical addresses of the weights and optimizer states once, into a tensor descriptor (a scatter-gather list tagging each region as weight or optimizer state), and ships that descriptor to the SSD via a custom NVMe command. From there, the CSSD's own DMA engine pulls the checkpoint directly from GPU memory — no host-DRAM copy, no host CPU cycles spent moving bytes.

2 · The naive fix fails — and why

Simply doing P2P writes straight to flash (DirectSSD) does remove host contention, but now the GPU must wait for the entire checkpoint to reach flash before the commit completes. Flash bandwidth is far below DRAM's, so this exposes the full flash-write latency on the critical path — DirectSSD measures 0.09× of ideal throughput, actually worse than host-staged Gemini (0.65×).

3 · Two-phase checkpointing — moving the "done" point

FlashStash's fix: don't wait for flash. Phase 1 streams the checkpoint tile-by-tile through in-storage accelerators that apply lightweight magnitude-pruning (dropping near-zero weight residuals and low-momentum optimizer entries), small enough to fit the SSD's internal DRAM. The commit is declared complete the moment the pruned checkpoint lands in that DRAM — and because PLP makes this DRAM power-loss-safe, that commit is already durable against the training job's dominant failure modes (host and GPU crashes), which live in a different failure domain than the SSD.

Phase 2 then moves the pruned checkpoint from internal DRAM to flash in the background, applying the expensive non-uniform quantization (k-means clustering + codebook) during this slow write — matching the extra compute to the already-low flash bandwidth, so it costs nothing extra in wall-clock time.

4 · Checkpoint management — append-only, like a log-structured FS

FlashStash stores weights as an anchor (full snapshot) plus a growing residual chain of diffs, and optimizer state as just its latest version — tracked in a superblock that advances at every Phase 1 commit and is finalized with flash locations at Phase 2 or a merge. On a host/GPU failure, the CSSD autonomously drains any in-flight Phase 2 so recovery always finds the latest committed checkpoint; on a power failure, PLP flushes only the unwritten tail. A periodic background merge collapses the residual chain once it exceeds roughly 16 checkpoints (the accelerators' reconstructible chain-length cap), bounding both compression and recovery time — visible as a sawtooth in sustained throughput.

5 · Accelerators — the 9.9 W that buys 89.3%

Three small FPGA modules remove the remaining compression stall: a vector accelerator (a PE array of floating-point adders with a flag reductor for the pruning bitmap and a value reductor for k-means max/sum), a dequantization accelerator (codebook lookup for residual reconstruction), and a sparse adder (bitmap-driven accumulation). The background merge reuses the same datapath, so it needs no extra hardware. Together they draw 9.9 W on the FPGA prototype; given a ~12× typical FPGA-to-ASIC dynamic-power gap, an ASIC version would add under 1 W — negligible for an enterprise SSD.

Follow the numbers

Worked examples

Three traces using the paper's own figures.

① From 98.9% stall to 10.7%

At per-iteration checkpointing, the normal-SSD path (CheckFreq) spends 98.9% of end-to-end time on checkpointing (Fig. 4), leaving 1.1% useful. AccelSSD sustains 89.3% of ideal throughput. What's AccelSSD's checkpointing share of E2E time?

  1. Useful fraction of wall-clock time ≈ throughput ratio when checkpointing only adds stall time (no extra useful work): useful share ≈ 89.3%.
  2. Checkpointing's share of E2E time = 100% − 89.3% = 10.7%.
  3. Compare to CheckFreq's 98.9%: FlashStash shrinks checkpointing's bite into end-to-end time by roughly 9.2×.
🍯
Insight: Under the simplified model used above — checkpointing only adds stall time, with no other overheads — "89.3% of ideal throughput" and "10.7% of E2E time spent on checkpointing" are the same number read two ways. The paper reports the 10.7% figure directly; this derivation just shows it's consistent with the throughput number, not a general identity between the two framings.

② Stacking the throughput multipliers

The paper reports each design's gain over the previous one: CompSSD is 3.89× DirectSSD; EarlySSD is 1.23× CompSSD; AccelSSD is 2.07× EarlySSD. Starting from DirectSSD = 0.09× ideal, does chaining these multipliers land near AccelSSD's reported 0.89×?

  1. CompSSD = 0.09 × 3.89 ≈ 0.35 — matches the reported 0.35×.
  2. EarlySSD = 0.35 × 1.23 ≈ 0.43 — matches the reported 0.43×.
  3. AccelSSD = 0.43 × 2.07 ≈ 0.89 — matches the reported 0.89×.
💡
Each stage targets a distinct stall: CompSSD removes the flash-bandwidth problem via compression; EarlySSD removes the flash-latency problem via early return; AccelSSD removes the remaining compression-compute stall. The multipliers compose because each attacks a different, now-dominant bottleneck.

③ Why MoE models suffer most under naive checkpointing

Llama-4-Maverick (1/128 experts active) retains only ~2% of baseline throughput under Gemini at per-iteration checkpointing, far below dense models. Why does sparsity make it worse, given the checkpoint size is roughly the same either way?

  1. MoE activates few experts per token, so each GPU iteration finishes faster than a dense model's iteration at similar total parameter count.
  2. Checkpoint size depends on total parameters (all experts must be saved), not active parameters — so the checkpoint-write cost stays roughly fixed.
  3. Fixed checkpoint cost ÷ shorter iteration = a larger fraction of each iteration spent stalled on checkpointing.
  4. Conclusion: as frontier models trend toward sparser MoE backbones, the host-contention problem FlashStash targets gets worse, not better, over time.
⚠
This is a structural trend, not a one-model quirk — the paper explicitly flags MoE adoption in frontier multimodal models as compounding the problem (§1).
Test yourself

Practice problems

Each ends with the misconception it checks.

Problem 1 · easy
Why does checkpointing slow down video LLM training far more than text-only LLM training, for the same checkpoint size and frequency?
Show answer
Because the host is already busy. Text-only training's host is largely idle during a GPU iteration, so staging a checkpoint in host DRAM has spare bandwidth to use. Video LLM training keeps the host continuously decoding/resizing frames, so checkpoint staging must compete for the same DRAM bandwidth that preprocessing needs — inflating preprocessing latency and stalling the GPU.Misconception: that checkpointing cost is purely a function of checkpoint size and frequency. It's equally a function of what else the host is doing at the time.
Problem 2 · medium
DirectSSD writes the checkpoint P2P straight to flash and removes all host contention, yet performs worse than host-staged Gemini (0.09× vs 0.65× ideal throughput). Explain.
Show answer
Removing host contention only fixes one bottleneck. DirectSSD's commit doesn't complete until the entire checkpoint reaches flash, and flash bandwidth/latency is far worse than DRAM's — so now the GPU stalls on the full flash-write duration every checkpoint, which is worse than the host-DRAM-bandwidth stall it replaced.Misconception: that bypassing the host is sufficient. The checkpoint still needs somewhere to land quickly; P2P alone just relocates the slow part to flash.
Problem 3 · medium
Why can FlashStash call a checkpoint "durable" the moment it reaches the SSD's internal DRAM, when that DRAM is normally volatile?
Show answer
Two things combine: (1) power-loss protection (PLP) lets the SSD flush that DRAM to flash even during a power cut, so it survives the failure mode PLP covers; (2) the dominant failures in large training clusters strike the host or GPU, a separate failure domain from the SSD — so for those (the common case), the CSSD simply stays powered and autonomously finishes draining to flash later. Durability against the common failures doesn't require flash to be reached yet.Misconception: that "volatile memory" always means "not durable." Durability is about surviving the failures that actually occur, and here a backup power guarantee plus a separate failure domain cover the realistic cases.
Problem 4 · hard
Why does FlashStash run cheap pruning inline (Phase 1) but defer expensive quantization to the background flash write (Phase 2), rather than doing both inline or both deferred?
Show answer
The constraint is the internal DRAM's small size: the pruned checkpoint must fit there before Phase 1 can complete, so pruning has to happen inline, on the critical path, where it must be cheap. Quantization instead doesn't gate the commit — it only needs to finish before the flash write does — and flash bandwidth is already the slowest stage, so quantization's extra compute is "free," hidden behind an already-slow background operation. Doing both inline would unnecessarily lengthen the critical path; doing both deferred would mean the internal DRAM has to hold an unpruned (larger) checkpoint, which may not fit.Misconception: that "more compression, sooner, is always better." Where compression happens should match what resource is scarce at that point — DRAM capacity inline, compute time in the background.
Problem 5 · medium
What causes the sawtooth pattern in FlashStash's sustained throughput over time (Fig. 16b), and what two things must the background-merge interval balance?
Show answer
The residual chain grows by one link each checkpoint; the limited number of dequantizers/sparse adders can only reconstruct a chain up to ~16 checkpoints long before compression/recovery performance degrades. Once the interval exceeds that cap, throughput falls — until the next merge collapses the chain back to an anchor, resetting it (the sawtooth). The interval must balance: merging too rarely lets the chain exceed the cap (slow operation); merging too often means the merge itself — which reuses the same accelerators — contends with live checkpointing.Misconception: that more frequent merging is strictly safer. It trades one cost (long-chain slowdown) for another (merge/checkpoint contention); the paper leaves finding the right interval automatically as future work.
Problem 6 · easy
FlashStash injects a reconstruction error only "upon an actual recovery," not during normal training. Why does this matter for the accuracy experiment (Fig. 14, forced recovery every 100 iterations)?
Show answer
Because the GPU always continues training from its own uncompressed weights — the compressed checkpoint is read back only if a failure actually triggers a recovery. So the failure-free trajectory is bit-identical to uncompressed training, and accuracy exposure scales with the number of failures, not with training length or checkpoint frequency. Forcing a recovery every 100 iterations is therefore a stress test (many more "failures" than realistic), and the paper reports that the resulting 3.8% final-loss gap stays negligible even under this much heavier failure load — not a formally proven upper bound, but strong evidence that accumulated error doesn't compound across repeated recoveries.Misconception: that compressing every checkpoint accumulates error continuously, like lossy video re-encoding. Here, error is injected per-recovery-event, not per-checkpoint-written.
Quick answers

Frequently asked questions

Q1Is this just "write checkpoints to SSD instead of host memory"?▾
No — that's DirectSSD, which the paper shows is worse than host-staged checkpointing (0.09× vs 0.65× ideal throughput) because it exposes flash's slow write latency directly. FlashStash's contribution is the two-phase commit that hides that latency behind GPU compute, plus the in-storage compression/acceleration that makes the inline pruning step itself cheap.
Q2Does FlashStash change what the GPU trains on?▾
No. The GPU always continues from its own uncompressed, in-HBM weights. Compression only affects the checkpoint copy used for recovery; the failure-free training trajectory is bit-identical to training without any of this.
Q3Why not just speed up the host preprocessing instead?▾
That's a complementary, orthogonal fix (the paper cites DALI, FusionFlow, DIP as preprocessing-side optimizations) — it composes with FlashStash rather than replacing it. Speeding up preprocessing shrinks one contender for host DRAM bandwidth; FlashStash removes the other contender (checkpoint staging) entirely.
Q4What exactly does "host-free" not cover?▾
The host driver still resolves tensor addresses into a descriptor and issues the custom NVMe command once per checkpoint — a small, infrequent, non-bandwidth-intensive operation. "Host-free" refers to the bulk checkpoint data path, not all host involvement.
Q5How is this different from FastPersist (GPUDirect Storage)?▾
FastPersist also writes GPU-to-NVMe via GPUDirect, removing host staging — but it still leaves flash write latency on the critical path. FlashStash's two-phase commit and in-storage compression are what additionally hide that latency, which is the gap the paper explicitly targets (§6, Related work).
Q6What happens if the SSD itself fails, not the host or GPU?▾
That's the one failure mode PLP + two-phase commit don't cover, since it's in the SSD's own failure domain. FlashStash handles it the same way multi-level checkpointing schemes (like Gemini) do: periodically flush the already-compressed checkpoint to an independent storage server. Because it's compressed and infrequent, this adds negligible traffic, and a CSSD loss costs at most the progress since that last flush.
Q7Does FlashStash need custom GPU or SSD hardware?▾
No new mechanisms at the GPU/PCIe level — resizable BAR, GPUDirect RDMA, and PLP are already commodity features of today's GPUs and enterprise SSDs. The SSD side needs firmware support for the custom NVMe command and (optionally) the accelerator modules; the paper notes CompSSD/EarlySSD already beat CheckFreq severalfold with firmware changes alone, before adding any accelerator hardware.
Q8Is video LLM training the only workload this applies to?▾
No — the paper frames video as today's heaviest case of a general pattern: any workload with a busy host plus frequent large state saves. It explicitly names audio/image-heavy multimodal training, text pretraining with online data filtering, and RL training with host-side rollouts as sharing the same structure (§6).
