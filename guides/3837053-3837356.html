HotStorage '26 · A Field Guide

Reach CXL memory by PCIe, not by CXL

GPUs can't speak CXL.mem yet. This paper's fix: let an on-device DMA controller drive ordinary PCIe peer-to-peer transfers straight into GPU HBM, and keep CXL strictly on the host's side of the link — so today's GPUs get CXL-expander capacity with zero GPU changes.

📄 Burru, Burla, Nalla, Prasad (Marvell) · HotStorage '26 🎓 Assumes CXL/tiering fundamentals — primers cover GDS/NIXL specifics ⏱ ~22 min read
🔌

Keep the GPU on plain PCIe P2P it already speaks via GDS; put CXL only on the host–expander link for capacity and management.
The GPU never issues a single CXL.mem transaction.

Before you begin

Quick glossary, then seven paper-specific primers

You already know CXL and memory tiering — these primers are just the paper's specific plumbing: GDS, NIXL, the queue model, and why the GPU-CXL gap exists at all.

CXLCompute Express Link — coherent load/store fabric. Here used only on the host↔expander link.
GDSGPUDirect Storage — NVIDIA's P2P DMA path between GPU HBM and NVMe, bypassing the host. The paper's comparison baseline.
P2P DMAPeer-to-peer DMA — one PCIe device moves data to/from another without routing through host DRAM.
NIXLNVIDIA Inference Xfer Library — abstracts data movement across GPU/host/storage tiers for inference frameworks like Dynamo.
KV cachePer-token key/value tensors cached across autoregressive decode steps — grows incrementally, accessed in small (4KB–128KB) chunks.
HBMHigh-Bandwidth Memory — the GPU's local memory, the thing being staged out of under pressure.
Device-DAX (/dev/dax)A Linux interface exposing a memory device as byte-addressable, mmap'able space — the paper's "CXL.DAX" comparison mode.
IOMMUI/O Memory Management Unit — translates device-side addresses; adds per-transaction latency, disabled in the paper's baseline.
1GDS: the incumbent the expander must beat▾

GDS already lets a GPU P2P-DMA straight to/from NVMe, skipping the host. It's the production mechanism frameworks use to offload KV caches and tensors when HBM is full. But it's tuned for large sequential block I/O; NVMe's bandwidth and latency floor becomes the bottleneck for small, frequent accesses.

Now you're ready: every number in this paper is a head-to-head against GDS-to-NVMe on the same host — same GPU, same PCIe switch, just a different device on the other end.
2The actual gap: no CXL.mem on today's GPUs▾

A CXL memory expander is normally reached by issuing CXL.mem loads/stores. GPUs don't implement that protocol, so a GPU can't natively treat expander memory as addressable memory the way a CXL-aware CPU can.

Now you're ready: the whole design exists to route around this one missing piece of silicon, not to replace CXL.
3Two links, two jobs▾

The expander has two interfaces: a CXL link to the host CPU (for capacity expansion, discovery, management) and a PCIe surface reachable from the GPU via the shared switch. The GPU's bytes travel only the second path, as plain PCIe P2P — the same mechanism GDS already uses.

Now you're ready: "CXL memory, PCIe-delivered" is the one-sentence summary of the whole architecture.
4Structera: an active device, not passive memory▾

Marvell's Structera A packs DMA + compute + DDR5 on one device. Crucially, its on-device DMA controller is the master of GPU-facing transfers — it issues the PCIe reads/writes against GPU HBM. Neither the GPU's own DMA engines nor the host CPU drive the data path.

Now you're ready: when you read "the controller moves data," that's the expander acting on the GPU, not the GPU acting on the expander.
5NIXL as the integration surface▾

The authors wrote a custom NIXL backend plugin (DMA transfers) and a DAX plugin (/dev/dax access), using NIXL's existing buffer-registration/transfer APIs. Any framework already speaking NIXL (e.g. via Dynamo) can target the expander without redesign.

Now you're ready: this is why the paper claims "production pipelines can adopt it" — it's a new backend, not a new API.
6Submission queues, doorbells, polling▾

The kernel driver sprays DMA descriptors across 16 submission queues ("instruction queues") in the device's MMIO/BAR space and rings a doorbell. Each queue has a paired completion queue; this implementation detects completion by polling a counter continuously rather than waiting on an interrupt — lower latency, but it burns a host thread.

Now you're ready: the 16-queue, one-worker-core-each design is what lets descriptor building scale across CPU cores instead of becoming the bottleneck.
7Why 4 KB–128 KB is the yardstick▾

KV-cache reads/writes during autoregressive decode are small and frequent — concentrated in the 4 KB–128 KB range — not the large sequential transfers GDS/NVMe were optimized for. The paper sweeps the full 4 KB–8 MB range and reports where NVMe aggregation catches up and eventually overtakes the expander on writes beyond ~2 MB, but frames 4 KB–128 KB as the range most relevant to KV-cache and tensor staging in production workloads.

Now you're ready: the paper tracks the write crossover explicitly — NVMe aggregation overtaking the expander beyond ~2 MB, including at 8 MB — rather than hiding it; 4 KB–128 KB is just the range it argues matters most for KV-cache staging.
The whole story in one place

CXL capacity, PCIe delivery

The problem, the workaround, and what it buys over GDS.

LLM inference stages KV caches and tensors out of GPU HBM under memory pressure, today via GDS to NVMe. NVMe's bandwidth and latency are a poor match for the fine-grained, high-frequency 4 KB–128 KB accesses this generates. A CXL memory expander would be a faster tier — except current GPUs can't speak CXL.mem at all.

The paper's move: split the expander's two interfaces by role. CXL stays on the host↔expander link, purely for capacity, discovery, and management. The GPU-facing path stays plain PCIe P2P — the same mechanism GDS already relies on — but now driven by the expander's own on-device DMA controller (Marvell Structera A) rather than by NVMe. Custom NIXL plugins expose this to inference frameworks with no redesign.

The payoff, measured head-to-head against GDS on 4× Gen5 ×4 NVMe on the same host: the expander hits 51 GB/s reads (~80% of the Gen5×16 peak) and 29.7 GB/s writes (~46% of peak); it beats GDS on reads across the full 4 KB–8 MB sweep (6–7× at 64–128 KB, narrowing to ~1.6× by 8 MB) and on writes through roughly 1 MB (~5× at 128 KB, ~1.3× at 1 MB) before aggregated NVMe edges back ahead at 8 MB. At KV-relevant sizes, end-to-end latency is more than an order of magnitude lower than GDS (single-digit µs vs. tens of µs).

🍯 Key takeaways

  • The workaround: CXL for capacity (host-side), plain PCIe P2P for data (GPU-side) — no GPU changes needed.
  • The on-device DMA controller, not the GPU or host, is the active party moving every byte.
  • 51 GB/s read / 29.7 GB/s write, ~80%/~46% of the Gen5×16 link — the interconnect, not the 409.6 GB/s DDR5 behind it, is the bottleneck.
  • Expander wins decisively at KV-relevant 4 KB–128 KB (bandwidth and >10× lower latency); NVMe aggregation closes the gap and wins on bulk multi-MB writes.
  • A clear read/write bandwidth asymmetry (~1.7–1.8×) remains unexplained — flagged as future work.
🔭
For the tiering reader: this is explicit, application-directed staging of GPU-resident data via NIXL — not transparent DRAM/CXL page migration on the CPU's hot/cold path like TPP, HeMem, or Memtis. It's closer in spirit to Pond's CXL pooling than to OS-level tiering, since the memory consumer issuing requests is the GPU/NIXL layer, not the kernel's page-fault or NUMA-balancing machinery.
Five everyday pictures

How to think about the design

Each stands alone; every one ends with where it breaks down.

Two links · Role split

A loading dock and a hotline

The PCIe dock between GPU and expander moves actual boxes (data) directly. The CXL line to the host is a hotline used only to negotiate how much warehouse space you get — it never carries a single box.

Where it breaks: on a CXL-native host the hotline could carry boxes too (CXL.DAX does) — the GPU just isn't wired to dial it.
Who drives · Active vs passive

A chauffeured car, not a rental

Neither the GPU nor the host "drives" these transfers — the expander's own DMA controller does, fetching and delivering data on its own initiative while GPU and host just hand it addresses.

Where it breaks: a chauffeur takes verbal instructions; here the "instructions" are pre-built descriptors queued ahead of time, so there's no back-and-forth mid-trip.
Scaling out · 16 queues

16 checkout lanes, 16 cashiers

One queue building descriptors would bottleneck on a single CPU core. Spraying across 16 submission queues, each drained by its own worker core, parallelizes the one job (keeping the PCIe link fed) that would otherwise stall on software overhead.

Where it breaks: more lanes don't help once the store itself (the PCIe link) is the limit — the paper found deeper queues past a point gave no further gain.
Completion · Polling vs interrupts

Watching the pot vs. the timer beeping

Polling a completion counter continuously is like staring at the pot — fastest to notice it's done, but it occupies you (a host thread) the whole time. An interrupt is the timer beep — frees you up, but with a little reaction delay.

Where it breaks: the paper only measured the "staring" version; it doesn't yet report the CPU cost of staring, or how much latency an interrupt-driven version would add.
CXL.DAX · The host detour

Direct flight vs. connecting through a hub

CXL.DAX routes every byte GPU→host DRAM (bounce buffer)→CXL expander — a layover. CXL.DMA-P2P flies direct across the PCIe switch. The layover amortizes away on big suitcases (large blocks), which is why DAX writes can win past ~256 KB — but it taxes every small, frequent trip.

Where it breaks: the layover also shares the host's root-complex bandwidth with other devices — a cost the direct flight never pays, that this analogy doesn't capture.
The full explanation

How it actually works

Topology, data path mechanics, the two access modes, and the measured trends.

1 · Topology — one switch, two roles

GPU, CXL expander, and four NVMe SSDs all sit under a shared PCIe Gen5 ×16 switch on the host (an AMD EPYC 9555/768 GB system in these measurements). The expander additionally carries a CXL link back to the host CPU — used only for capacity/management, never for GPU-facing data.

2 · Data path — submit, execute, complete, pipeline

The NIXL backend submits DMA descriptors (source, destination, length) via io_uring; the driver sprays them across 16 submission queues in the expander's BAR space and rings a doorbell. The controller then issues PCIe reads/writes directly against GPU HBM through the switch — GPU HBM is only ever a source or destination, never an orchestrator. Completions post to paired completion queues and are detected by polling (an interrupt path is planned). To avoid stalling on software overhead before the link saturates, the host posts several descriptors back-to-back and collects completions later, with each queue drained by its own CPU core.

3 · Two access modes — direct vs. host-mediated

CXL.DMA-P2P is the mode above: direct, switch-local, host-bypassing. CXL.DAX is the alternative measured for comparison: host CPU load/stores on an mmap'd /dev/dax region, which means every GPU byte detours GPU↔host DRAM (bounce buffer)↔expander, consuming root-complex bandwidth shared with other devices.

4 · The read/write asymmetry

Reads run ~1.7× faster than writes at peak (51 vs. 29.7 GB/s), widening to ~1.8× at the largest blocks. The paper does not yet explain the cause — it's named explicitly as future work alongside an interrupt-driven completion path and IOMMU-enabled measurements.

Follow the numbers

Worked examples

Four calculations straight from the paper's reported figures.

① Checking the "~80% / ~46% of peak" claims

  1. Gen5×16 theoretical peak = 64 GB/s per direction (Table 1).
  2. Measured peak read = 51 GB/s → 51 ÷ 64 = 79.7% ≈ 80%, matching the paper's stated figure.
  3. Measured peak write = 29.7 GB/s → 29.7 ÷ 64 = 46.4% ≈ 46%, also matching.
💡
The expander's 409.6 GB/s internal DDR5 bandwidth is never the limiter here — 6.4× the link's own peak — confirming the PCIe link, not the device, bounds throughput.

② Recovering the implied GDS read bandwidth at 128 KB

  1. Paper states DMA-P2P is ~7× GDS reads at 128 KB, and gives the absolute DMA-P2P figure elsewhere: 35.9 GB/s (vs. CXL.DAX's 28.0 GB/s).
  2. Implied GDS: 35.9 ÷ 7 ≈ 5.1 GB/s (not stated directly — derived from the paper's own ratio).
📌
Marked with an asterisk wherever used in this guide, since it's a derived, not directly reported, figure.

③ The write crossover, three points

  1. 128 KB: 29.7 vs. 5.8 GB/s → ratio 29.7/5.8 ≈ 5.1× lead for the expander.
  2. 1 MB: 28.4 vs. 21.6 GB/s → ratio 28.4/21.6 ≈ 1.3× — NVMe aggregation is catching up.
  3. 8 MB: 28.3 vs. 31.1 GB/s → GDS now ahead by 31.1/28.3 ≈ 1.10× (about 10%).
🍯
Insight: the expander's write bandwidth barely moves (29.7→28.4→28.3) across almost two orders of magnitude in block size (128 KB→8 MB is a 64× range), while four aggregated NVMe drives keep climbing — exactly the opposite shape from the read story, where the expander keeps climbing toward its own ceiling.

④ Order-of-magnitude latency check (4 KB–128 KB)

  1. Read latency: DMA-P2P 2.9–3.7 µs vs. GDS 52.3–72.5 µs → ratio ≈ 14–25×.
  2. Write latency: DMA-P2P 3.1–4.4 µs vs. GDS 53.6–75.9 µs → ratio ≈ 12–24×.
  3. Both confirm the paper's claim of "more than an order of magnitude" lower latency across the 4 KB–128 KB KV-relevant range.
💡
At 8 MB the absolute gap narrows in ratio (167 µs vs. 311 µs read, ≈1.9×) because fixed per-transaction overhead — the thing P2P DMA eliminates — stops dominating once transfer time itself is large.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why can't the GPU just issue CXL.mem loads/stores to the expander directly?
Show answer
Current GPUs don't implement the CXL.mem protocol at all — it's a hardware/firmware gap, not a driver limitation. The paper's entire design exists to route around this by keeping the GPU-facing path on plain PCIe P2P, which GPUs already support via GDS.Misconception: that this is a software compatibility issue solvable with drivers. It's missing protocol support in silicon.
Problem 2 · medium
At 128 KB, is the expander's write advantage over GDS driven by the device being 5× faster in absolute terms, or by GDS being unusually slow at that size?
Show answer
Both contribute, but GDS's 5.8 GB/s at 128 KB is low because fine-grained NVMe transactions carry overhead that dominates at small block sizes, and aggregating four drives doesn't help until the block size grows enough to amortize that overhead — not because the drives are intrinsically slow (they later reach 31.1 GB/s at 8 MB). The expander's 29.7 GB/s is already close to its own near-flat ceiling at this size.Misconception: that GDS's low number reflects NVMe's raw bandwidth ceiling. It reflects overhead amortization, which block size fixes on its own.
Problem 3 · medium
Why does aggregated NVMe eventually beat the expander on writes at 8 MB, when the expander wins decisively at 128 KB?
Show answer
The expander's write bandwidth is nearly flat across sizes (29.7 → 28.4 → 28.3 GB/s) — it saturates early. Four NVMe drives' aggregate bandwidth keeps climbing as block size grows and per-transfer overhead amortizes, eventually passing the expander's flat ceiling (31.1 vs. 28.3 GB/s at 8 MB).Misconception: that a "faster" tier wins at every size. Winning depends on where each path's bottleneck (link saturation vs. overhead amortization) kicks in.
Problem 4 · hard
CXL.DAX writes can exceed CXL.DMA-P2P beyond ~256 KB on a favorable host, yet CXL.DAX loses badly at 4–128 KB. Explain the mechanism behind both halves of that statement.
Show answer
CXL.DAX routes every byte through a host-DRAM bounce buffer (GPU↔host DRAM↔expander) via CPU load/store, paying a fixed per-transfer detour cost each time. At small blocks that detour dominates, so DMA-P2P's single-hop switch-local path wins easily. At large blocks the detour's fixed cost amortizes over more bytes, and a CXL-native host's load/store path can sustain enough bandwidth to edge past the DMA controller's own ceiling.Misconception: that one access mode is strictly "better." Each wins in a different regime defined by block size and overhead amortization.
Problem 5 · medium
The baseline measurements disable IOMMU. What does that choice isolate, and what does it NOT tell you?
Show answer
It isolates block-size effects from IOMMU translation overhead, letting the paper cleanly attribute latency/bandwidth trends to transfer size alone. It does not tell you what a production deployment with IOMMU enabled (needed for isolation/security in most real systems) would see — the paper explicitly lists IOMMU-enabled characterization as future work.Misconception: that these are production-realistic numbers. They're a controlled baseline; IOMMU-on numbers may differ, especially for fine-grained transfers.
Problem 6 · hard
Why would a CXL-Flash-backed version of this expander (DRAM cache in front of NAND) likely perform worse specifically for KV-cache staging, even though flash offers much more capacity per dollar?
Show answer
KV-cache staging is frequent, fine-grained, and not read-heavy-with-high-locality — so a modest DRAM cache in front of flash would see frequent misses. Misses expose NAND read latency, and the workload's write-heavy nature would hit limited sustained NAND write bandwidth, write amplification, and endurance wear. The paper's DRAM-backed numbers are explicitly called an "optimistic bound" for any CXL-Flash variant.Misconception: that more capacity at lower cost is a free upgrade. For read/write-intensive staging, DRAM-backed capacity is the better fit; flash suits colder, capacity-oriented tiers instead.
Quick answers

Frequently asked questions

Q1Does this require a new GPU?▾
No. The whole point is that the GPU only needs existing PCIe P2P DMA support (the same thing GDS already uses) — no CXL support, no architectural changes.
Q2Is CXL even necessary, then?▾
Yes, but only on the host side — CXL gives the host pooled, manageable capacity and discovery for the expander. Without it you'd need some other host-attached memory-expansion mechanism; the GPU's experience doesn't depend on it either way.
Q3What exactly is NIXL's role here?▾
NIXL is the integration surface inference frameworks already use to move data across tiers. The authors wrote a DMA backend plugin and a DAX plugin so the expander looks like just another NIXL-reachable tier — no framework redesign needed.
Q4Why compare against four NVMe drives instead of one?▾
The expander attaches over a full Gen5×16 link; there's no single Gen5×16 NVMe drive to match that link budget, so four Gen5×4 drives approximate a comparable aggregate on commodity hardware.
Q5Why does polling beat interrupts here?▾
Polling eliminates interrupt dispatch latency, which matters when individual transfers complete in single-digit microseconds. The cost is a host thread kept continuously busy — the paper flags an interrupt-driven variant as future work, partly to quantify this trade-off.
Q6Does adding more DMA queue depth help?▾
Not materially, per the paper's testing — once descriptor submission already drains queues aggressively, the PCIe interconnect itself becomes the limit, not queueing. A fuller queue-depth sweep is left for future work.
Q7What causes the read/write asymmetry?▾
Unknown — the paper reports it (~1.7–1.8×) but explicitly does not explain it, naming it a direction for future optimization work.
Q8Could this backing memory be flash instead of DRAM?▾
Architecturally yes — the P2P DMA path is agnostic to backing media. But the paper argues a flash-backed tier would expose NAND read latency and write limitations under KV-cache's frequent, fine-grained access pattern, making DRAM-backed the better fit here and flash better suited to colder, capacity-oriented tiers.
Q9How is this different from LMB or TraCT, which also use CXL with GPUs/SSDs?▾
LMB redirects PCIe-device accesses through the host rather than an on-device DMA engine; TraCT treats a shared CXL Type-3 device via Device-DAX as a rack-scale KV-transfer substrate with GPUs using CXL load/store and DMA. This paper's point is deployability on today's GPUs: all GPU-facing traffic stays plain PCIe P2P, with CXL confined to the host–expander link.
Q10Is CXL.DMA-P2P ever worse than Host DRAM staging?▾
No — Host DRAM (GPU-to-host-DRAM via PCIe with CPU involvement) is shown as a weaker baseline throughout: it plateaus early (~14.5 GB/s read, ~26 GB/s write) and its latency grows sharply with block size (145 µs at 128 KB read), so CXL.DMA-P2P exceeds it, not merely approaches it.
Q11What's left for future work?▾
Closing the read/write bandwidth asymmetry, an interrupt-driven completion path with quantified per-transfer CPU cost, IOMMU-enabled measurements, GPU-HBM data-layout effects, host-DRAM contention quantification, and exploring FlexiCache-style hierarchical KV offload onto the expander's on-device compute.
