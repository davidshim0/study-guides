PLOS 2026 · A Field Guide

Deriving the isolation boundary you need, instead of guessing between process, container, and VM

Processes, containers, and VMs are three familiar points in a vast design space of isolation mechanisms — and picking between them by hand is guesswork dressed up as engineering. This is the plain-English story of IsoSearch, a beam search over a formal graph model that derives the mechanism your goals actually require.

📄 "Exploring the Design Space of Isolation Mechanisms" · Agrawal et al., PLOS '26 🎓 Graph and search basics assumed — the primers cover them ⏱ ~25 min read
🕸️

Give each protection domain only what your constraints require — then search the graph for whichever design shares the least, not whichever came pre-built.

Before you begin

Quick glossary, then the fundamentals

The paper leans on a compact set of acronyms. Skim these once, then work through the primers below — collapsed by default, tap any to open.

Quick glossary

PDProtection Domain — a process, container, VM, or any unit that holds resources and can be isolated from others.
RSIResource Similarity Index — the Jaccard overlap between two PDs' resource sets; lower means stronger isolation.
MCMemory Consumption — total footprint: every resource's memory counted once, plus each PD's private overhead.
TCBTrusted Computing Base — the set of PDs a given PD must trust to function correctly.
IBImpact Boundary — a companion isolation metric from prior OSmosis work, queryable on the same graph.
BFSBreadth-First Search — explores all successors level by level; IsoSearch's beam search is a pruned form of it.
KV-cacheKey/Value cache — per-client attention state an LLM server caches to speed up token generation.
TLS key / HBAThe case-study "crown jewels": a TLS private key and pg_hba.conf, PostgreSQL's host-based auth config.
isolated / private resource optimization goal (RSI · MC · TCB) IsoSearch machinery shared resource / trust risk
1Isolation mechanisms: process, container, VM, and everything between▾

A process is cheap but shares the kernel with everyone. A container also shares the host kernel — so a kernel bug affects every co-tenant — but adds namespacing. A VM runs its own kernel, so the blast radius of a compromise stops at the hypervisor, at the cost of a heavier, slower boundary.

These three are just three points on a spectrum defined by how much is shared and how much is trusted — not the only three points possible.

Now you're ready: IsoSearch treats "process vs container vs VM" as an outcome of search, not a menu you pick from up front.
2Graphs as system models — nodes and edges▾

A graph is just dots (nodes) connected by lines (edges). Represent a running system this way and you can ask precise, checkable questions about it: who can reach what, who shares what, who must be trusted.

The paper's whole method rests on one such graph: nodes for protection domains and resources, edges for the relationships between them.

Now you're ready: "exploring the design space" literally means editing this graph — adding a node here, moving an edge there — and asking whether the result is still legal and better.
3The OSmosis model — PDs, Resources, Resource Spaces▾

OSmosis, the authors' prior model, has three node types: Protection Domains (processes, containers, VMs), Resources (a file, a key, a cache entry), and Resource Spaces (allocation pools grouping resources of one type — think "the set of all open file descriptors").

Four edge types connect them: Hold (a PD owns something), Request (a PD may ask another PD for resources), Subset (a resource belongs to its space), Map (a correspondence between like nodes).

Now you're ready: every mechanism in this guide — mediators, tenant isolation, privilege separation — is just a particular arrangement of these five node/edge kinds.
4Well-formedness — what makes a graph legal▾

Not every arrangement of nodes and edges is a sensible system. A resource floating with no owner, or a Request edge pointing at a resource instead of a PD, describes nothing real. Well-formedness is a set of six structural rules (Sec. 2) that rule these out.

IsoSearch is built so that every single edit it tries preserves well-formedness by construction — it never has to check for garbage afterward.

Now you're ready: when the paper says a "transition" takes a well-formed graph to another well-formed graph, that's an engineering guarantee, not a hope.
5Constraints vs. goals — "must" vs. "should"▾

A functional constraint is a hard requirement the final design must satisfy — e.g. "PD A must be able to reach resource R." A goal is something to optimize, not merely satisfy — e.g. "minimize how much A and B share."

Constraints are pass/fail; goals are a dial you turn as far as possible. IsoSearch needs both: constraints alone don't tell you which of many legal designs is best.

Now you're ready: every case study in this guide is defined by exactly this pair — a short list of constraints, plus one or more goals to minimize or maximize.
6The Jaccard index — measuring overlap▾

Given two sets, the Jaccard index is |intersection| / |union| — 1 if the sets are identical, 0 if they share nothing. It's a standard, simple way to quantify "how much do these two things overlap."

The paper's RSI metric is exactly this, applied to the resource sets two PDs hold.

Now you're ready: when you see "RSI = 1/3," read it as "these two PDs' resource sets overlap by one part in three" — nothing more exotic than that.
7Why exhaustive search doesn't scale▾

Every added PD, edge, or resource multiplies the number of legal next graphs. Trying every possible graph reachable from a starting point — full breadth-first search — grows combinatorially (far worse than polynomially) with the number of nodes, edges, and available transitions, and quickly becomes computationally infeasible.

You need a way to throw away unpromising branches early — accepting the risk of losing the best one — just to keep the search tractable.

Now you're ready: that's the exact problem beam search is built to solve — the next primer.
8Beam search — bounded breadth-first search▾

Beam search expands every candidate at the current frontier (like full BFS), scores them all, then keeps only the top-k ("the beam") to expand next — discarding the rest. It trades a guarantee of finding the global optimum for a search that stays tractable.

It sits between two extremes: single-path greedy (keeps only the single best candidate — brittle) and full BFS (keeps everything — explodes).

Now you're ready: IsoSearch's beam width is 12 throughout the paper's case studies — enough parallel paths to recover from a locally bad-looking move.
9Trusted Computing Base — who you're betting on▾

Your TCB is everyone who could break your component even though you did nothing wrong: anyone you send Requests to, and anyone who co-holds a resource you also hold (since either of you could corrupt it). It's a statement about exposure, not about code quality.

Shrinking a PD's TCB means shrinking the list of other components a compromise of them could hurt you through.

Now you're ready: when a case study reports "TCB(PD) = 2," that's a count of trust relationships, directly computable from the graph — not a vibe.
The whole story in one place

IsoSearch in a nutshell

The problem, the graph model that makes it tractable, and the search that finds an answer.

Developers routinely need custom isolation mechanisms — not off-the-shelf processes, containers, or VMs — but designing one today means stating security requirements informally ("the key server must not be reachable from the network") and hand-enforcing them, a process industry reports flag as a leading source of misconfiguration.

IsoSearch makes this systematic. It represents a deployment as an OSmosis graph — protection domains, resources, and the Hold/Request/Subset/Map edges between them — and treats finding a better isolation mechanism as searching that graph for a well-formed variant that satisfies a developer's functional constraints (things that must hold) while optimizing one or more goals (things to minimize, like shared resources, memory footprint, or trust exposure).

The search itself is a beam search: at each step, apply all twelve valid graph transitions (adding/deleting PDs, resources, resource spaces, and three of the four edge types — Hold, Request, Map; Subset is maintained automatically alongside its resource) to every graph currently in the beam, score every result, and keep only the top 12 for the next round. A candidate becomes a solution once it satisfies every constraint and clears every goal's threshold.

The payoff: across five case studies, IsoSearch automatically rediscovers hand-designed isolation patterns — a log mediator, per-tenant KV-cache isolation that closes a real side channel, a dedicated TLS-key PD — in seconds, while also surfacing valid alternatives (up to 109 in one case study) a manual approach would never enumerate.

🍯 Key takeaways

  • An isolation mechanism is a point in a graph design space, not a fixed menu of process/container/VM.
  • RSI (Jaccard overlap of resource sets), MC (memory footprint), and TCB (trust set size) turn "isolation" into numbers you can optimize.
  • Twelve graph transitions (create/delete on PDs, Resources, Resource Spaces; add/delete on Hold, Request, Map edges) generate every reachable design.
  • Beam search (width 12) tolerates an imperfect scoring function better than greedy, and stays tractable where full BFS explodes.
  • A candidate's score W = α·S + β·P is tuned (α/β = 50) so any fully constraint-satisfying graph always beats any violating one.
  • Search never deletes a PD, resource, or resource space present in the starting graph G₀ — it may still delete or restructure G₀'s edges (essential to case studies like the mediator pattern), closing a loophole where deleting an object trivially "satisfies" a constraint about it.
  • Five case studies: 2–8 steps (Privatization and Sharing take just 2) and 1.1–20.5 seconds to a first solution, each rediscovering a known-good isolation pattern from constraints and goals alone.
Six everyday pictures

How to think about IsoSearch

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Off-the-shelf vs. derived

Buying a house plan vs. building to code

Process, container, and VM are like three floor plans a developer knows by heart — good defaults, but nobody checked whether the plumbing actually satisfies your building code. IsoSearch instead starts from your code (constraints) and your budget (goals) and derives a plan — sometimes one of the three familiar ones, sometimes a custom room nobody had drawn before, like a dedicated mediator PD.

Where it breaks: a house plan is judged once, at move-in. IsoSearch's graph is judged continuously against constraints that can themselves be wrong or incomplete — a bad blueprint problem, not a search problem.
RSI · Jaccard overlap

Two roommates and one filing cabinet

Two roommates keep separate folders but both stuff bills into one shared drawer. Ask "how much do they share?" and the honest answer is a ratio: shared items over all items either owns — exactly the Jaccard index. RSI applies this to a PD's resources: fewer shared drawers, lower RSI, stronger isolation.

Where it breaks: Jaccard only counts what is shared, not how sensitive it is or who reads it first. A roommate could dilute the ratio by labeling a junk drawer "private," just as a candidate graph can lower RSI by adding a resource nobody actually shares — see Problem 4.
TCB · Trust exposure

Who's on your co-signer list

Your TCB is everyone whose failure can hurt you even though you did nothing wrong — like everyone who co-signed a loan with you, or anyone you delegated a task to. It doesn't matter whether they've ever misbehaved; the exposure exists the moment the relationship does. IsoSearch's TCB(PD) counts exactly this: everyone reachable via Request, plus everyone who co-holds a resource.

Where it breaks: a co-signer list has a natural stopping point (the bank). TCB can chain transitively through Request edges across many PDs; the paper's metric only reports the direct set, so a full transitive trust picture takes a further graph walk.
Beam search · Multiple live paths

Scouting three trailheads at once

You're not sure which trailhead leads to the summit, so instead of committing to the one that looks steepest-uphill-fastest (greedy, and easily wrong), you send small scouting parties up several at once and keep only the ones making real progress. Beam search keeps the top-12 candidate graphs alive each round — enough parallel attempts to recover if the best-looking single move turns out to be a dead end (as it is for candidate G1_c in the paper's own walk-through).

Where it breaks: real trail scouts share intel; IsoSearch's beam states are scored and pruned independently, with no cross-pollination between surviving candidates.
Metric-gaming · Where the score misleads

Adding a garnish to dilute the soup

If "average saltiness per ingredient" is your metric, you can lower it just by adding a spoonful of plain water — nothing about the soup's actual flavor improved. IsoSearch's tenant-isolation case study finds exactly this move: adding a 1 KB resource nobody shares dilutes the RSI average (from 1/3 to 5/18) without isolating anything real, and it scores better under the stated goal.

Where it breaks: a chef would never confuse "diluted" with "better" — but an optimizer that only sees the number will, unless the goal or its cost model is tightened to rule the move out.
Mediation pattern · Structural fix

A receptionist instead of a shared front desk

Two departments both used to walk straight into the records room; now a receptionist mediates every request, fetching what's needed without either department directly touching what the other left there. That's exactly the mediator PD IsoSearch derives for the shared-log case study: access is preserved (both can still eventually reach the log) but direct co-holding — and the ability to corrupt what the other left behind — disappears.

Where it breaks: a receptionist can also become a bottleneck or a single point of failure; the paper doesn't model mediator throughput or availability, only sharing and trust.
The full explanation

How it actually works

The model, the moves, the score, and how a search actually runs — grounded in the paper's own walk-through.

1 · The OSmosis graph

Three node types — Protection Domain, Resource, and Resource Space — connected by four edge types: Hold (a PD owns a resource or another PD), Request (a PD may ask another PD for resources), Subset (a resource belongs to its resource space), and Map (a correspondence between like nodes of the same type).

2 · Constraints, goals, and the twelve transitions

Two constraint forms capture the paper's common isolation requirements: reachable(src, dst, nEdges) — can src reach dst within nEdges hops? — and exists(PD) — is this PD still present? The paper leaves more complex constraint forms to future work. Goals are metrics to optimize: RSI, MC, and TCB.

Twelve transitions generate every reachable graph — create/delete for each of the three node types, add/delete for each of the three non-Subset edge types (Subset edges are added/removed automatically alongside their resource):

ElementTransitionPrecondition
PDCreate / DeleteDelete needs no outgoing edges
ResourceCreate / DeleteCreate needs a PD + resource space; delete needs exactly one Hold edge
Resource SpaceCreate / DeleteDelete needs no outgoing Subset edges
Hold edgeAdd / DeleteDelete can't remove a resource's last Hold edge
Request edgeAdd / DeleteNeeds two existing PDs
Map edgeAdd / DeleteDelete needs no Map edges left between the two resource spaces
💡
Why never delete anything from G0? A constraint like "PD_W must reach Res_log" is trivially "satisfied" if PD_W is deleted — the predicate is vacuous. IsoSearch forbids deleting any node present in the starting graph, so it can only add or restructure, closing this loophole by construction.

3 · Scoring a candidate

Each candidate graph gets a score W = α·S + β·P. Constraint satisfaction S ∈ [0,5] scales with the fraction of constraints met (5 = all, 0 = none) — violators are still explored, not discarded, so the search can pass through temporarily-invalid graphs on the way to a solution. Goal progress P gives each goal up to 10 points, scaled by how far it's moved toward its target: for RSI, full marks means reaching 0; for MC, points scale with the fraction of the budget still remaining, not merely whether the budget is met (staying under budget is constraint validation, not automatically full goal progress); for TCB, full marks means trust fully shrunk.

# with |G| goals, any constraint-satisfying graph must always outscore any violator:
α > 10 · β · |G|        # each of the |G| goals contributes ≤10 to P; each violation costs α
# the paper uses up to 3 goals, and sets:
α / β = 50
🍯
Robustness check: the authors reran three scenarios with α/β ∈ {5, 10, 20, 50} — twelve runs total. The iteration at which the first solution appeared, and its core structure, were identical every time: the weight ratio changes score magnitude, not which designs win.

4 · The beam search loop

beam = { G0 }
while not all(beam solved) and score still improving:
    candidates = {}
    for G in beam:
        for T in the 12 transitions:
            for each eligible node/edge satisfying PreCond_T(G):
                # skip: well-formedness violations; deleting anything in G0
                candidates.add(T(G))
    score each candidate: W = α·S + β·P
    beam = top-12 candidates by W
    solutions += { G in beam : all constraints hold, all goals reach threshold }
return solutions

Search stops when every beam state has found a solution, or the mean beam score plateaus for three iterations, or a depth bound is hit. Because the search continues past the first solution (up to the depth bound), it typically surfaces several valid designs, not just one.

5 · Scaling, and where scoring can mislead

Table 2 (reproduced under Reference) shows search cost varying widely across case studies — from 2 steps / 1,246 candidates for Privatization up to 6 steps / 10,916 candidates for the three-constraint privilege-separation case study at 20.5 seconds — broadly tracking constraint count and depth, though the table alone doesn't establish that as a general scaling law. In every case the beam prunes 94–97% of evaluated candidates. But the score is only as good as the metric: minimizing RSI alone, with no cost attached to creating resources, lets the search "win" by adding a trivial private resource that dilutes the average without isolating anything real (the RSI = 5/18 alternative in Sec. 4.2) — a reminder that the optimizer will find the shortest path to the number you asked for, not necessarily the one you meant.

Follow the numbers, step by step

Worked examples

Four traces straight from the paper's case studies — RSI arithmetic, a memory budget, and the scoring function itself.

① Computing RSI for per-tenant KV-cache isolation

Three LLM clients; IsoSearch settles on 3 PDs, each holding the shared 100 MB model plus its own 20 MB KV-cache. What's the global RSI?

  1. Resources per PD: each PD_i holds {model, kv_i} — 2 resources.
  2. Any pair (PD_i, PD_j): intersection = {model}, size 1. Union = {model, kv_i, kv_j}, size 3.
  3. Jaccard for the pair = 1/3. This holds for every one of the 3 pairs.
  4. Global RSI = mean over all pairs = 1/3 — exactly the paper's reported value for the intended design (Fig. 3).
  5. Check the alternative: give PD_1 an extra private 1 KB resource nobody shares. Now PD_1–PD_2 and PD_1–PD_3 each score 1/4 (intersection still {model}=1, union grows to 4), while PD_2–PD_3 stays 1/3. Mean = (1/4+1/4+1/3)/3 = 5/18 — lower, and matching the paper's "gamed" solution exactly.
⚠
The catch: 5/18 < 1/3, so it scores better under "minimize RSI" — but the extra resource isolates nothing real. It's cheap padding that dilutes the average (see analogy "Adding a garnish to dilute the soup").

② The memory budget that blocks a fourth tenant PD

G0 costs 210 MB (100 MB model + 3×20 MB KV-caches + 50 MB single-process overhead) against a 320 MB GPU budget. Why does the three-PD solution fit but a fourth PD doesn't?

  1. MC counts each resource once, plus per-PD overhead. With 3 tenant PDs: 100 MB model (once, shared) + 3×20 MB KV (60 MB) + 3×50 MB overhead (150 MB) = 310 MB.
  2. 310 MB ≤ 320 MB — fits, with 10 MB to spare.
  3. Add a 4th (empty) PD: no new resources needed, just another 50 MB of PD overhead. 310 + 50 = 360 MB — exceeds the 320 MB budget, exactly as the paper states.
  4. So the budget itself, not just the RSI goal, pins the design at exactly 3 tenant PDs — a hard constraint and a soft goal jointly determined the shape of the solution.

③ RSI and the memory ceiling in privilege separation

The PostgreSQL-like case study reports RSI(G0) ≈ 0.095 and a 530 MB budget that caps the design at 5 PDs. Confirm both.

  1. Frontend holds 5 resources (3 connection resources + tls_key + auth_hba); backend holds 3 (data, wal, tls_key). Overlap = {tls_key}, size 1. Union = 5+3−1 = 7. RSI = 1/7 for this pair, and the same 1/7 for frontend–admin (sharing auth_hba).
  2. Backend–admin share nothing: RSI = 0.
  3. Mean over the 3 pairs = (1/7 + 1/7 + 0)/3 = ≈ 0.095 — matches the paper exactly.
  4. Memory: G0 = 350.02 MB of resources (350 MB bulk + 16 KB of keys/logs) + 3×30 MB PD overhead = 440.02 MB. The 4-PD solution (adding a dedicated tls_key PD) costs 350.02 + 4×30 = 470.02 MB.
  5. A 6th PD would need 350.02 + 6×30 = 530.02 MB — 0.02 MB over the 530 MB budget, so at most 5 PDs are ever reachable.

④ Why α/β = 50 guarantees constraints dominate

With up to 3 goals in play, show that a fully constraint-satisfying candidate always outscores one that violates even a single constraint.

  1. Best possible goal contribution: each of up to |G|=3 goals gives at most 10 points, so P ≤ 30, contributing at most β·30 to the score.
  2. Cost of one constraint violation: S drops by a fraction of its 5-point range; the dominance requirement is α > 10·β·|G| = 10·β·3 = 30β.
  3. With α/β = 50: 50β > 30β holds comfortably — even a candidate that perfectly maximizes all 3 goals (P=30) cannot outscore one that satisfies every constraint, regardless of that graph's goal progress.
  4. Why this matters: without this margin, the beam could evict a required Hold edge purely to improve RSI — trading correctness for a better-looking number, exactly the failure mode the weight ratio is chosen to prevent.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Two PDs each hold 4 resources and share exactly 2 of them. What is their RSI?
Show answer
Intersection = 2. Union = 4 + 4 − 2 = 6. RSI = 2/6 = 1/3.Misconception: dividing shared count by one PD's total (2/4 = 1/2) instead of the union of both. RSI is a Jaccard index over the union, not either PD's own set.
Problem 2 · easy
Why can't IsoSearch ever delete a PD that was present in the starting graph G0, even if doing so would satisfy a constraint about that PD?
Show answer
Because deleting the PD makes any constraint naming it vacuously true — e.g. "PD_W must reach Res_log" is trivially satisfied if PD_W no longer exists. That's satisfying the letter of the constraint while destroying the functionality it was meant to protect. IsoSearch forbids deleting anything present in G0, so the constraint can only be met by real reachability, not by erasing the subject.Misconception: that any transition sequence reaching a "satisfied" state is a valid solution. Validity requires preserving G0's required components, not just passing the predicate check.
Problem 3 · medium
In the tenant-isolation case study, the "gamed" solution (RSI = 5/18) scores higher than the intended one (RSI = 1/3) under "minimize RSI." Was IsoSearch wrong to prefer it?
Show answer
No — IsoSearch did exactly what it was told: minimize the stated metric. The mismatch is between the metric and the developer's actual intent ("isolate the KV-caches meaningfully"), which the RSI number alone doesn't capture, and which the constraint set didn't rule out (a low-cost decoy resource wasn't priced realistically under MC). The fix is a better goal or constraint, not a better search.Misconception: that a lower score always means a better design. A score is only as trustworthy as the metric and cost model behind it.
Problem 4 · medium
Why does IsoSearch use beam search instead of a single-path greedy search, given that greedy is simpler and the scoring function already ranks candidates?
Show answer
Because the scoring function is an approximation of progress, not a perfect ranking — the paper's own example shows the highest-scoring candidate at one iteration isn't necessarily on the path to the eventual solution. A single greedy path has no way to recover from a misstep; discarding all but the top-1 candidate can permanently exclude the winning path. Beam search keeps 12 candidates alive, tolerating an imperfect score at the cost of more computation.Misconception: that a good scoring function makes greedy safe. Greedy is only safe if the score is a perfect, monotonic guide — beam search exists precisely because it usually isn't.
Problem 5 · hard
Why doesn't full breadth-first search (exploring every legal successor, with no pruning) scale, given that IsoSearch's graphs start small (a handful of PDs and resources)?
Show answer
Because the number of legal next-graphs at each step grows with the product of (nodes eligible for a transition) × (12 transition types), and this branching compounds multiplicatively across iterations — reaching a solution 2–8 steps deep, as in the paper's case studies, means the unpruned tree has already produced tens of thousands of candidates by the deeper case studies alone (the beam search itself evaluates up to 10,916 while keeping only 12 alive per round). Full BFS keeps all of them, not just the top 12, so its candidate count compounds without bound.Misconception: that a small starting graph implies a small search space. The space is small at depth 0 and grows combinatorially with depth, transitions, and node count — not with the starting graph's size alone.
Problem 6 · medium
A candidate graph violates one functional constraint but has excellent goal progress (say P = 30, the max for 3 goals). With α/β = 50, can it ever outscore a fully constraint-satisfying candidate with poor goal progress (P = 0)?
Show answer
No. The violating candidate's constraint satisfaction S drops below the maximum of 5; losing even one constraint (of, say, 2–3 total) typically costs at least 5/3 to 5/2 points of S. Its score is at most α·(S<5) + β·30. The fully-satisfying candidate scores at least α·5 + β·0 = 5α. Since α = 50β, 5α = 250β, while the violator's ceiling is under 5α + 30β − (its S deficit)·α, and the dominance inequality α > 10β|G| = 30β is specifically chosen to guarantee 5α always exceeds any violator's maximum possible score.Misconception: that a high goal score can compensate for a broken constraint. The weight ratio is deliberately chosen so it never can — constraints are lexicographically prior to goals.
Problem 7 · easy
IsoSearch's mediation case study discards candidate G1_c despite it satisfying the same fraction of constraints as the winning G1_a. Does this mean G1_c was invalid?
Show answer
No — G1_c wasn't invalid, it just scored lowest among the 8 candidates generated at that step (it made the least goal progress). With only 8 candidates here, it wouldn't have been cut by the beam-width cap of 12 alone — the walk-through simply follows the most promising surviving path forward, and G1_c's low score means it's not worth continuing to expand, not that it's illegal. Being left behind means "not among the most promising to continue exploring," not "constraint-violating."Misconception: conflating "discarded from the beam" with "constraint-violating," and assuming every discard is caused by hitting the width-12 cap rather than simply being outscored.
Problem 8 · hard
CellulOS instantiation found that a shared-mediator design and a two-private-PD design both score RSI = 0, yet differ by +9.7% in cycles. What does this reveal about relying on RSI alone to choose between designs?
Show answer
RSI measures resource-set overlap, not topology or runtime cost — two structurally different graphs (one mediator serving both clients vs. two fully private PDs) can be RSI-identical while imposing very different real performance costs (extra PD creation, extra indirection through Request edges, etc.). RSI alone can't distinguish designs that are equally "isolated" by its own definition but not equally good deployments.Misconception: that a single metric at RSI = 0 means "job done, pick either." Real deployment decisions need the metrics the search optimized for, plus whatever it didn't (here, instantiation cost) — exactly the paper's stated limitation that no single metric captures every notion of isolation.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What problem is IsoSearch actually solving?▾
Choosing or designing an isolation mechanism (which resources a protection domain should hold, share, or reach only indirectly) currently means hand-translating informal security requirements into an implementation — a process prone to the misconfigurations that industry reports cite as a leading source of security exposure. IsoSearch turns this into search over a formal graph: give it a starting deployment, hard constraints, and optimization goals, and it finds (multiple) graphs that satisfy both.
Q2What is OSmosis, and how is it different from IsoSearch?▾
OSmosis is the authors' prior graph model of protection domains, resources, resource spaces, and their relationships — the "language" the whole approach is written in. IsoSearch is this paper's new contribution: the beam-search procedure that navigates that graph model to find good designs. LinTool (also prior work) extracts an OSmosis graph from a live system to feed IsoSearch's starting point.
Q3Why beam search specifically, and why width 12?▾
The design space is too large for exhaustive (full BFS) search, but the scoring function is only an approximate guide, so single-path greedy is brittle — one wrong step can permanently exclude a solution. Beam search keeps a bounded set of the most promising candidates (12, in every case study) alive per round, balancing tractability against robustness to an imperfect score.
Q4What exactly does RSI measure, and what does it miss?▾
RSI is the Jaccard index of two PDs' resource sets, averaged over all resource-holding pairs — a pure measure of sharing. It ignores PD count, PD size, and graph structure, so two topologically different designs (e.g. a shared mediator vs. two fully private PDs) can score identically. It can also be gamed: adding an unshared filler resource lowers the average without isolating anything meaningful.
Q5How does IsoSearch guarantee it never produces an invalid system design?▾
Every one of the twelve transitions is constructed so that applying it to a well-formed graph yields another well-formed graph, proven by induction from the starting graph G0. Preconditions (e.g. "a resource needs exactly one Hold edge before it can be deleted") are checked before a transition is even attempted, so illegal graphs are never generated in the first place.
Q6Does IsoSearch find the mathematically optimal design?▾
No — it's explicitly a best-effort search. Beam search bounds the explored space to stay tractable, so it can miss a global optimum that full exhaustive search would find (which is itself often infeasible). What the paper demonstrates instead is that IsoSearch reliably rediscovers known-good, hand-designed patterns — mediators, per-tenant isolation, dedicated key PDs — from constraints and goals alone, and surfaces multiple valid alternatives when the goals don't pin down a single answer.
Q7How does this connect to isolation in CXL-pooled or disaggregated memory?▾
Not directly addressed in the paper, but the framing transfers: a CXL memory pool shared across tenants is structurally similar to the LLM KV-cache case study — a shared resource (pooled memory / model weights) plus per-tenant private state (a client's pages / KV-cache) that must not cross-leak. The same RSI-style question — "how much do two tenants' memory footprints overlap, and does that overlap ever include something private?" — is a natural lens for reasoning about isolation boundaries in a tiered or pooled-memory system, even though OSmosis doesn't model page-granularity sharing today.
Q8How is IsoSearch different from FlexOS's exploration approach?▾
FlexOS, the closest prior work, semi-automatically explores a system's protection profile using a partial order to compare configurations, but its exhaustive search doesn't scale to large spaces. IsoSearch builds on a more expressive formal model (OSmosis), enabling arbitrary scoring functions and pruning strategies, and replaces exhaustive search with beam search to handle larger design spaces.
Q9What happens after IsoSearch finds a graph — does it produce a running system?▾
IsoSearch is the middle stage of a three-stage pipeline: LinTool extracts the starting graph from a live system, IsoSearch searches for a better one, and a target OS instantiates it. The authors built the instantiation stage for CellulOS, an seL4-based OS, and validated it by comparing CellulOS's own extracted graph back against IsoSearch's output. Full automation across other backends (Genode, FlexOS, CubicleOS, Tyche) is future work.
Q10What did the authors explicitly leave out or flag as future work?▾
Automating instantiation across more OS backends and encoding each platform's structural restrictions as constraints; combining or choosing between metrics that capture complementary isolation notions (no single metric captures every notion of isolation); using an LLM to translate natural-language security policies directly into reachable/exists constraints; extending OSmosis with information-flow (taint) tracking; and generating the executable content of newly derived PDs (currently IsoSearch specifies structure and resource footprint, not code).

Glossary, results, and provenance

Every term in one place, the case-study numbers at a glance, and where each claim in this guide comes from.

Core terms
IsoSearchThe paper's beam-search procedure for deriving isolation mechanisms from a starting OSmosis graph, functional constraints, and optimization goals.
OSmosisThe prior graph model representing a system as Protection Domains, Resources, and Resource Spaces, connected by Hold/Request/Subset/Map edges.
Protection Domain (PD)A process, container, VM, or any unit of isolation that holds resources.
RSI (Resource Similarity Index)Mean Jaccard overlap of resource sets across all resource-holding PD pairs; lower means stronger isolation.
Memory Consumption (MC)Total footprint: each resource's memory counted once, plus each PD's private overhead (stack, heap, runtime state).
TCB (Trusted Computing Base)For a PD: every PD reachable via Request edges, plus every PD that co-holds a resource with it directly.
TransitionA well-formedness-preserving graph edit — one of twelve (create/delete on 3 node types; add/delete on 3 edge types).
Beam / beam widthThe bounded set of highest-scoring candidate graphs retained between search iterations; width 12 in every case study.
Supporting terms
Hold / Request / Subset / MapThe four OSmosis edge types: ownership, permission-to-ask, resource-space membership, and cross-structure correspondence.
Well-formednessSix structural invariants (Sec. 2) a graph must satisfy to represent a valid system.
Functional constraintA hard requirement (reachable / exists predicate) the final design must satisfy.
GoalAn optimization target (RSI, MC, or TCB) the search minimizes or maximizes, scored on a progress scale.
Scoring functionW = α·S + β·P, combining constraint satisfaction and goal progress; α/β = 50 in the paper.
Jaccard index|A∩B| / |A∪B| — the set-overlap ratio underlying RSI.
LinToolPrior tool that extracts an OSmosis graph from a running Linux system — stage one of the pipeline.
CellulOSAn seL4-based OS that natively tracks OSmosis graph state — the instantiation target used to validate IsoSearch's output.
Impact Boundary (IB)A companion isolation metric from prior OSmosis work, queryable on the same graph but not a primary IsoSearch goal in this paper.
Mediator patternA dedicated PD introduced to hold a resource on behalf of others, replacing direct co-holding with indirect Request-based access.
