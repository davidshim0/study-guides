SOSP 2026 · A Field Guide

Picking the exact next event, instead of nudging the clock and hoping

Distributed-system fuzzers usually can't say "deliver this message before that timer fires" — they can only sprinkle in delays and hope the OS scheduler cooperates. This is the plain-English story of Tamias, a fuzzer that controls the exact schedule and still mutates it like ordinary fuzzing input.

📄 "Tamias: Feedback-Guided Systematic Concurrency Exploration..." · Liu, Song, Fonseca, Zhang 🎓 Assumes greybox-fuzzing basics — the primers cover them ⏱ ~30 min read
🧭

Let a real scheduling algorithm CONTROL exactly which event runs next — don't just NUDGE timing with delays and hope the right order falls out.
Then make that control replayable enough for feedback-guided fuzzing to reuse it.

1Greybox fuzzing, in one paragraph▾

A greybox fuzzer keeps a corpus of test cases. It picks one (a "seed"), mutates it slightly, runs the mutant, and checks lightweight feedback — usually which code branches executed. If the mutant hit a branch nobody's hit before, it's added to the corpus as a new seed. Repeat for hours.

The corpus only helps if feedback is reproducible: a seed is kept because it reaches some branch, so mutating it should still reach that branch, plus something new.

Now you're ready: Tamias's central worry is exactly this — making a distributed-system test case's feedback reproducible enough to mutate reliably.
2Why distributed-system bugs are a different beast▾

A single-node fuzzer mutates one input string. A distributed system's behavior depends on both user inputs and the order in which messages, timers, and thread wakeups happen to interleave across nodes. Many severe bugs need a very specific combination of both — a "needle in a haystack" across two search spaces at once.

Now you're ready: Tamias represents a test case as two programs — an input program and a schedule-control program — precisely because one space alone isn't enough.
3Concurrency exploration algorithms: random walk vs. PCT/PCTCP▾

Random walk just picks a random enabled event at each step. PCT (and its distributed form PCTCP) is smarter: it groups causally-related events into chains, gives each chain a random priority, and forces a handful of random priority-drops during the run. This gives a mathematical guarantee: any bug that needs at most d ordering decisions is found with bounded probability per run, instead of hoping randomness stumbles onto it.

Now you're ready: Tamias doesn't invent a new scheduling algorithm — it makes existing ones (random walk, PCTCP) pluggable and mutable inside a fuzzing loop.
4Branch coverage as feedback▾

Compilers can instrument every conditional branch in a program (LLVM's trace-pc-guard, or Go's built-in libFuzzer mode). At runtime this yields a bitmap of "which branches executed." Fuzzers compare bitmaps across runs — a new bit set means new behavior was reached.

Now you're ready: "feedback determinism," Tamias's central goal, means this bitmap — not the full execution — must reproduce.
5Record-replay and the determinism spectrum▾

Tools like rr provide full execution determinism: re-run and every instruction, every scheduling decision, is bit-identical. That's powerful for debugging but expensive to build and to port to new systems — you must intercept nearly everything the OS itself leaves nondeterministic.

Output determinism (used in some multicore debugging) relaxes this to "same externally visible output." Tamias defines a third point on this spectrum, tailored to fuzzing.

Now you're ready: Tamias's feedback determinism sits between these — reproduce only what the fuzzer's feedback signal (branch coverage) can see, nothing more.
6Transparent testing — no source changes▾

Some model checkers require rewriting the target to call into a testing framework instead of the OS directly. That's a large porting cost for a 5–7 million-LOC system like MongoDB or MySQL. "Transparent" means the tool controls an unmodified binary from outside — via proxies, kernel hooks, and library interposition — rather than by editing its source.

Now you're ready: Tamias tests Redis, etcd, MySQL, MongoDB, Nuraft, and Braft with zero source-code changes (only two compile-time flags disabled).
7Timing-based perturbation (the baseline approach)▾

Instead of precisely choosing the next event, many distributed fuzzers just inject delays before certain messages or faults and let the OS scheduler sort out what actually happens first. This can bias outcomes statistically, but it never guarantees a specific fine-grained ordering — two runs with "the same" injected delay can still interleave differently.

Now you're ready: this coarse, nondeterministic control is exactly what Tamias replaces with explicit, feedback-deterministic event selection.
8sched_ext and eBPF, briefly▾

sched_ext is a Linux mechanism that lets a user-space program implement a custom CPU scheduling policy without patching the kernel. eBPF is the sandboxed bytecode layer that runs the small, verified in-kernel hooks (e.g., "notify me when a thread becomes runnable") that sched_ext and network tracing rely on.

Now you're ready: Tamias's thread-scheduling control is a thin user-space policy sitting on top of sched_ext — one generic hook instead of wrapping every pthread/futex call.
9LD_PRELOAD, seccomp, and syscall interception▾

LD_PRELOAD injects a shared library that overrides libc functions (like poll or clock_gettime) before the real ones load — a classic transparent-interception trick. seccomp is a kernel filter that traps selected raw syscalls to a signal handler, catching calls that bypass libc. Neither alone catches calls issued via the vDSO fast path, which is why Tamias also patches that.

Now you're ready: these three mechanisms together are how Tamias rewrites every timeout and clock read a target program makes, without touching its source.
10Test-case mutation, corpus seeds, and "replay"▾

Standard fuzzing mutation edits a stored input and reruns from scratch. But concurrency-exploration algorithms like PCTCP are normally designed to generate a whole schedule from scratch each run — there's no obvious way to "mutate" a schedule the way you'd flip a byte in a string.

Now you're ready: this mismatch — mutation wants to reuse partial progress, scheduling algorithms want to start fresh — is the second problem Tamias's replay-explore strategy solves.
The whole story in one place

Tamias in a nutshell

Two limitations in prior fuzzers, two insights that fix them, and how the pieces connect.

State-of-the-art distributed-system fuzzers have two blind spots. First, they treat fine-grained, deterministic event control as impractical, so they only bias the OS scheduler with injected delays — nondeterministic, coarse, and unable to guarantee a specific message/timer/thread ordering. Second, they generate schedules through ad hoc timing perturbation rather than integrating a principled concurrency-exploration algorithm (like PCTCP) with feedback-guided mutation, so exploration has no coverage guarantees and can't build on prior discoveries.

Tamias fixes both with two insights. Insight 1: fuzzing doesn't need full execution determinism — only feedback determinism (same branch-coverage bitmap on rerun). That's a much cheaper bar, so Tamias can use a lightweight transparent TCP proxy, sched_ext-based thread control, and a virtual clock instead of emulating the whole OS. Insight 2: a scheduling algorithm can be mutated without regenerating it from scratch, via a replay-explore strategy: replay a corpus test case's proven prefix exactly, then reconfigure the scheduler (new PRNG seed, new enabled inputs, new virtual-clock policy) so the remaining suffix diverges into new, systematically-explored territory.

The payoff: across Redis, etcd, MySQL, MongoDB, Nuraft, and Braft — with zero source modifications — Tamias found 12 new bugs in mature releases, achieved feedback determinism for branch coverage on every target, beat DistFuzz's coverage by up to 47%, and its own replay-explore mutation improved final coverage by up to 22% over scheduling from scratch.

🌰 Key takeaways

  • Coarse timing perturbation biases the OS scheduler; it never guarantees a specific fine-grained event order.
  • Feedback determinism (same coverage bitmap) is enough for stable fuzzing — full execution determinism is overkill and costly to achieve transparently.
  • A test case = input program + schedule-control program (step-indexed policy changes) — two mutable programs, not one.
  • Replay-explore reuses a proven prefix exactly, then reconfigures the scheduler so only the suffix diverges — preserving the algorithm's exploration guarantees (the "suffix-exploration property").
  • Three lightweight, transparent mechanisms do the controlling: a TCP proxy (messages), sched_ext+eBPF (threads), a virtual clock (timers) — no OS-scale reimplementation.
  • Result: 12 new bugs, feedback determinism on all 6 targets, up to 47% more coverage than DistFuzz, up to 22% more from mutation alone.
Seven everyday pictures

How to think about Tamias

Each stands alone — read in any order. Every card ends with where the picture stops being true.

Feedback determinism · vs full determinism

A play, not a rehearsal transcript

A director doesn't need every actor's exact footstep reproduced night after night — only that each actor hits their line on cue. Tamias only needs the same branches to fire on rerun; a client's TCP port number can differ every time and nobody cares. Chasing bit-identical replay would mean scripting every footstep — expensive, and beside the point.

Where it breaks: if a line is dropped entirely (a branch fails to reproduce), the scene breaks — feedback determinism still requires the things the fuzzer measures to be solid, just not everything else.
Replay-explore

Retracing a hike to a fork, then trying a new trail

You don't restart from the trailhead every time you want to explore past a fork — you retrace the known path to the fork (replay), then branch onto an unexplored trail from there (explore). Tamias replays a corpus test's schedule exactly through step s, then reconfigures the scheduler so only the path after s diverges.

Where it breaks: retracing assumes the trail hasn't washed out — if the replayed prefix doesn't reach quite the same state (feedback-deterministic, not execution-deterministic), you fork from a slightly different spot each time.
PCTCP · Priority change points

Musical chairs with a forced reshuffle

Everyone gets a random turn order (chain priority), but at a few pre-picked moments the referee deliberately demotes whoever's currently "it" — forcing a different chain to go next. Do this d−1 times and you guarantee that any bug needing at most d ordering decisions gets a real chance of appearing, instead of hoping pure randomness lines them up.

Where it breaks: the guarantee weakens fast as event count n and depth d grow (§5.2 notes PCTCP "may struggle" on deep bugs) — reshuffling helps, but the search space still grows combinatorially.
sched_ext + eBPF

One doorman for every exit, not a lock on every door

Wrapping every synchronization primitive (locks, futexes, condition variables) individually is like installing a lock on every door in a building. sched_ext instead puts one doorman at the single hallway everyone must pass through to become runnable — it sees every reason a thread might wake, through one hook.

Where it breaks: the doorman only watches whole-thread runnability, not instruction-level interleaving — Tamias explicitly does not explore finer-grained thread interleavings within a "run one thread to completion" step.
The virtual clock

A film's speed ramp, not a broken watch

A director can speed up or slow down a scene's felt passage of time without changing what the actors say or the order they say it in. Tamias's virtual clock works the same way: it controls how fast virtual time advances and fires the earliest-due timer — but timer order still follows deadlines, never scrambled arbitrarily.

Where it breaks: a film can ramp different characters at different speeds; Tamias currently runs one global virtual clock — per-node clock skew isn't supported yet.
The transparent TCP proxy

A phone operator, not a bugged phone line

Rather than tapping every wire inside the phone system (emulating the full socket API), Tamias sits as an old-style operator who physically holds every call: it merges chatter that arrives as one logical message, preserves who's calling whom, and puts calls through in order — using ~420 lines of code instead of reimplementing TCP.

Where it breaks: an operator can't un-say something a caller already said — the proxy preserves FIFO delivery per connection but doesn't reorder within a single stream, by design (that would violate TCP's own guarantees and create false bugs).
The full explanation

How it actually works

Section by section, with the paper's algorithms rebuilt as pseudocode and diagrams.

1 · The test case: two mutable programs

A Tamias test case is ⟨I, P⟩: an input program I (client requests, partition faults) and a schedule-control program P — a sequence of pairs ⟨s, p⟩ meaning "apply policy change p at scheduling step s." At runtime, the chosen scheduling algorithm A and the virtual clock consume P together with enabled events to produce a realized schedule σ of message deliveries, timer firings, thread decisions, and external events.

🌰
Both parts are separately mutable: mutating I adds new client requests (delayed until the divergence step, so they don't disturb the replayed prefix); mutating P reconfigures the scheduler (new PRNG seed, new enabled events, new clock policy).

2 · The fuzzing loop (Algorithm 1)

Standard greybox structure — select, mutate, run, collect feedback — but the "run" step is itself replay-then-explore:

loop:
    ⟨I, σ⟩ ← SelectSeed(corpus)          // pick a seed test case
    s ← ChooseStep(σ)                    // pick divergence point
    I' ← MutateInput(I, grammar, s)      // new commands added after s

    REPLAY
    P ← GetPolicies(σ[0, s))             // reuse the original policies
    Run(A, I, P, 0, s)                   // replay the exact prefix

    EXPLORE
    P̃ ← NewSchedulerPolicy(A) + NewClockPolicy() + NewInputPolicy(I')
    σ̃[s,∞) ← Run(A, I', P̃, s, ∞)         // diverge into a new suffix

    COLLECT
    if HasNewFeedback(): corpus += ⟨I', σ[0,s) ∥ σ̃[s,∞)⟩

3 · The scheduler's own state machine

Each scheduling step runs one enabled event to completion, then decides when to schedule the next. Tamias needs to know when the system has gone quiescent (no runnable threads, no in-flight proxy messages) — including the tricky case where delivering a message wakes nobody.

4 · Replay-explore and the suffix-exploration property

The core risk of "mutating" a schedule is that arbitrary tweaks (e.g., editing a few entries in a recorded random-choice log) can silently change the scheduler's exploration guarantees for everything downstream. Tamias avoids this by giving each algorithm a principled Reconfig that resamples only future randomness, preserving the distribution over possible suffixes:

// PCTCP reconfiguration (Algorithm 3)
rng ← InitPRNG(new_seed)
C_past ← { c ∈ C | c < s }                    // keep change points before s
C_future ← SampleDistinct([s, n), d − 1 − |C_past|)   // resample only the rest
C ← C_past ∪ C_future
💡
Why this matters: because Reconfig touches only unused randomness, replay-explore and running the algorithm fresh from the replayed state induce the same probability distribution over suffixes (the paper's suffix-exploration property, proved by induction over steps). Prefix nondeterminism can change where exploration starts, but not the guarantee once it starts.

5 · Feedback-deterministic event interception

Three mechanisms, each chosen to minimize what must be intercepted:

  • Messages: an L4 transparent TCP proxy (iptables TPROXY for remote traffic, DNAT/SNAT for local traffic) — 420 LOC, no socket-API emulation.
  • Threads: sched_ext + eBPF — a kernel data-plane hook reports runnability; a user-space control-plane scheduler decides what runs next, with an effectively infinite timeslice to enforce run-to-completion.
  • Timers: a virtual clock (time-dilation style) plus timeout rewriting via LD_PRELOAD, seccomp, and vDSO patching — timeouts become "infinite," and Tamias fires them itself by advancing virtual time and signalling the thread.

Remaining nondeterminism is mitigated directly: merging TCP-coalesced messages into one logical event, disabling Nagle's algorithm, reordering multi-connection sends using an eBPF send trace, classifying known transient kernel sleeps (e.g. page writeback during fsync) so they aren't mistaken for modeled blocking, masking RDSEED/RDRAND via trapped CPUID, fixing /dev/urandom output, and assigning deterministic PIDs via a PID namespace.

Follow the numbers, step by step

Worked examples

Four traces through the paper's own tables — verifying the percentages, sizing the probability gap replay closes, tracing a real bug lineage, and tallying the implementation.

① Verifying the ablation percentages (Table 3)

The paper claims joint mutation (R‑ISM) improves random-walk coverage on MongoDB by 22.2% over the no-mutation baseline (R). Check it.

  1. Baseline (R), MongoDB, random walk: 90,812 branches (Table 3).
  2. Full Tamias (R‑ISM): 110,997 branches.
  3. Absolute gain: 110,997 − 90,812 = 20,185 branches — exactly the number the paper calls out.
  4. Relative gain: 20,185 ÷ 90,812 = 0.2222 = 22.2%. Matches the paper's headline "up to 22%" figure.
  5. Cross-check under PCTCP: 112,277 − 99,654 = 12,623 branches, ÷ 99,654 = 12.7% — also matches.
🌰
Insight: the gain isn't just a percentage on paper — MongoDB alone picks up over twenty thousand additional covered branches from mutation, more than the entire branch count of some of the smaller targets.

② Why "from scratch" gets expensive fast

Apply PCTCP's guarantee p ≥ 1/(w²n^(d−1)) with illustrative w=4, n=200 events, d=4 ordering decisions needed.

  1. From scratch: p ≥ 1/(4² · 200³) = 1/(16 × 8,000,000) = 1/128,000,000. Expect roughly 128 million executions in the worst case to guarantee hitting this exact ordering by chance alone.
  2. Now suppose replay reaches a useful state at step s=150 (i.e., 150 of the 200 events, and some change points, are already fixed by a proven prefix). Algorithm 3 only resamples the remaining [150,200) — 50 events — for whatever change points aren't already placed.
  3. If 2 of the 3 needed change points already occurred before s=150, only 1 remains to resample: p ≥ 1/(4² · 50¹) = 1/800.
  4. Shrinkage: 128,000,000 ÷ 800 = 160,000× fewer expected trials needed once the useful state is reached and replayed, instead of re-searching the full 200-event, depth-4 space every run.
💡
This is framing, not a number the paper states directly — but it's exactly the mechanism the paper is exploiting: reaching state S_s once via a retained corpus seed, then replaying it, converts an astronomically rare event into an ordinary one.

③ Tracing the real Nuraft-1 mutation lineage

§5.2's case study: the mutation trace 62 → 64 → 70 → 80 → 82 → 83 → bug. What did each generation actually add?

  1. 62 → 64: input mutation grows the Raft log enough that node N1 falls behind the leader — establishing step ① of the bug in Figure 2.
  2. 70, 80: preserve that prefix (replay) but explore other, unrelated behaviors — dead ends for this bug, but they don't erase the useful prefix.
  3. 82: the first to place N1 into a long-lived snapshot-installation state — reaching step ② on top of ①.
  4. 83: drives the leadership change and delivers the overlapping second InstallSnapshot message — reaching ③ and ④.
  5. Final mutant: releases additional late requests only after this deep state is reconstructed, triggering the crash at step ⑤.
🌰
Why it matters: the ablation confirms this wasn't luck — P‑IM (PCTCP restarted from scratch each run, input mutation only) found Nuraft-1 in 0 of 10 24-hour trials; P‑ISM (adding schedule mutation via replay-explore) found it in 2 of 10 (Table 4). The bug needed the accumulated prefix, not just a lucky single run.

④ Tallying the implementation cost (Table 5)

Is "transparent, feedback-deterministic control" actually lightweight to build? Add up the 13,496 LOC.

  1. Fuzzer (Go): 3,152 LOC — the mutation/corpus/feedback loop itself.
  2. Scheduler misc. (Go): 2,678 LOC — Run/ApplyPolicy, algorithm interface glue.
  3. Network proxy (Go): just 420 LOC — the entire message-interception layer, because it never emulates the socket API.
  4. Monitor, user space (Go) + eBPF (C): 2,365 + 1,343 = 3,708 LOC — the runnability/network tracepoint plumbing.
  5. In-process runtime (C): 3,538 LOC — LD_PRELOAD/seccomp/vDSO interception for timers, clocks, and entropy.
  6. Total: 3,152+2,678+420+2,365+1,343+3,538 = 13,496 LOC — matching the paper's stated total exactly.
💡
The network proxy — arguably the hardest transparency problem (intercepting arbitrary distributed messages) — is only 3% of the codebase, because Insight 1 let it stay a coarse logical-message relay instead of a full protocol emulator.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
A rerun of the same Redis test case produces a different TCP port number in a CLIENT INFO response, but the same set of branches executes both times. Does this violate Tamias's determinism guarantee?
Show answer
No. Tamias only guarantees feedback determinism — that branch coverage reproduces. The port number is a concrete-execution detail invisible to the branch-coverage abstraction, so it's allowed to vary; the fuzzer treats both runs as the same behavior.Misconception: that "deterministic testing" always means bit-identical replay. Tamias deliberately targets a weaker, cheaper, fuzzing-sufficient notion.
Problem 2 · medium
Suppose Tamias's PCTCP Reconfig resampled change points from the full range [0,n) instead of [s,n) when reconfiguring after step s. What breaks?
Show answer
It would silently discard the priority changes already applied during the replayed prefix, meaning the "replayed" prefix might not even match the original schedule that was already executed — undermining the whole point of replay (reconstructing a proven state cheaply). Algorithm 3 explicitly partitions into C_past (kept, <s) and C_future (resampled, [s,n)) to avoid exactly this.Misconception: that "reconfiguring the scheduler" means restarting its randomness entirely. It must only touch future randomness to preserve the suffix-exploration property.
Problem 3 · medium
Using Table 3: for etcd under PCTCP, baseline (P) = 13,783 and full Tamias (P‑ISM) = 13,952. Compute the relative coverage gain.
Show answer
(13,952 − 13,783) ÷ 13,783 = 169 ÷ 13,783 ≈ 1.2% — matching the paper's reported etcd/PCTCP ablation gain. Small in relative terms because etcd already has a small grammar (#GR=44) and less room for input-driven divergence, consistent with the paper's observation that gains track grammar size.Misconception: that a small percentage gain means the technique "doesn't matter" for that target — the paper explicitly frames this as expected given etcd's narrower input space, not as a failure of the method.
Problem 4 · hard
Fest (a concurrent work cited in §6) mutates a schedule by editing a few entries in a recorded random-choice sequence, leaving the rest fixed. Why does the paper say this does not preserve the scheduler's suffix distribution, while Tamias's Reconfig does?
Show answer
Editing a few entries in an already-recorded sequence while leaving the rest fixed produces an arbitrary, ad hoc perturbation — there's no guarantee the resulting sequence still follows the algorithm's intended probability distribution over outcomes from that point. Tamias's Reconfig instead installs a *fresh* source of randomness (new PRNG seed, or resampled distinct change points) for *all* remaining choices, so by construction the algorithm's own distribution over suffixes is preserved exactly, as proved by induction over steps.Misconception: that any way of "changing some choices in a recorded run" counts as valid schedule mutation. Only mutations that resample using the algorithm's own sampling procedure preserve its coverage guarantees.
Problem 5 · easy
What's the difference between "transparent" and "systematic" as Tamias uses the terms?
Show answer
Transparent = tests unmodified target systems (no source changes, no porting). Systematic = explicitly selects each next event via a scheduling algorithm with defined exploration properties, rather than merely biasing the OS scheduler with delays. Tamias is the first tool the paper credits with being both at once.Misconception: conflating "doesn't require code changes" with "systematically explores schedules" — DistFuzz, for instance, is transparent (black-box) but not systematic in this sense.
Problem 6 · medium
Why does the network proxy merge all messages on one connection within a scheduling step into a single logical event, and separately disable Nagle's algorithm (TCP_NODELAY)?
Show answer
TCP is a byte stream: the kernel can coalesce or split application-level messages across packets nondeterministically, and Nagle's algorithm can nondeterministically delay small packets. Both would inject nondeterminism into "how many events happened" and "when," undermining feedback determinism. Merging same-step, same-connection traffic into one logical event and disabling Nagle removes both sources at their root, rather than trying to detect and compensate for them after the fact.Misconception: that network nondeterminism only comes from message *reordering*. Coalescing/splitting and delivery-timing quirks below the message abstraction are just as disruptive.
Problem 7 · hard
Tamias currently supports one global virtual clock, not per-node clock skew. Why does this follow from how timer interposition is implemented, and what would adding skew require?
Show answer
Virtual time is computed as "start time + scheduler-advanced time," read from a single shared-memory value the scheduler controls; every node's clock_gettime/RDTSCP calls are rewritten against that one value. Introducing per-node skew would require maintaining and consistently advancing a separate virtual-time state per node, and ensuring every timer/timestamp interception path reads the *correct* node's clock — a real increase in bookkeeping the paper explicitly defers to future work.Misconception: that clock virtualization is inherently per-node just because the target system is distributed. Tamias's current design deliberately keeps one global virtual clock for simplicity.
Problem 8 · medium
The ablation shows joint mutation helping Redis (#GR=104) and MongoDB (#GR=56) much more than Nuraft (#GR=5) or Braft (#GR=3). Why would grammar size affect how much replay-explore mutation helps?
Show answer
Joint mutation's benefit comes from combining many different input variants with systematic schedule exploration — the bigger the input space, the more distinct input×schedule combinations there are to discover, so there's more room for mutation to find something new. With only 3–5 grammar rules, the input space is nearly exhausted quickly, so most of the remaining coverage gain has to come from schedule exploration alone, which mutation helps less dramatically.Misconception: that a fuzzing technique's percentage improvement is an intrinsic property of the technique. Here it's explicitly conditioned on the target's input-space size — the same technique, different ceilings.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1What exactly does "feedback determinism" guarantee?▾
That rerunning the same test case produces the same feedback signal — for Tamias, the same branch-coverage bitmap. The concrete execution (exact interleavings, port numbers, timings) can still differ run to run; only the abstraction the fuzzer measures needs to be stable.
Q2Why not just achieve full execution determinism like rr?▾
Full determinism requires intercepting essentially everything the OS leaves nondeterministic, which enlarges the interposition surface and makes transparent support for large, feature-rich systems (5–7M LOC targets like MySQL/MongoDB) much harder. The paper argues — and shows empirically — that fuzzing doesn't need this stronger, costlier guarantee.
Q3What is a "schedule-control program," concretely?▾
A sequence of ⟨step, policy⟩ pairs. At each recorded step during execution, Tamias applies that policy: reconfigure the scheduling algorithm (e.g., new PRNG seed), enable newly-added input events, or adjust the virtual clock's timer-selection behavior.
Q4How is PCTCP different from plain PCT?▾
PCT was designed for single-machine multithreaded programs. PCTCP generalizes it to distributed systems by organizing events into causally-related chains (a message and everything it triggers) rather than treating every event independently, since distributed events have causal structure PCT doesn't model.
Q5Does replay-explore work with any scheduling algorithm?▾
Only ones that expose a Reconfig implementation satisfying the suffix-exploration property — the paper provides this for random walk (fresh PRNG) and PCTCP (partitioned resampling of change points). A new algorithm would need its own principled Reconfig to plug in safely.
Q6Why intercept threads via sched_ext instead of wrapping pthread/futex calls?▾
Wrapping synchronization APIs means enumerating and correctly emulating every primitive a target might use — a large, error-prone compatibility surface across 6 different codebases. sched_ext's kernel hook captures every source of thread runnability generically, at the cost of only controlling whole-thread scheduling, not sub-instruction interleaving.
Q7How big is Tamias, and where does the complexity actually live?▾
13,496 LOC total. Roughly 40% is Go for the fuzzer/scheduler glue, another ~45% is the monitor (userspace + eBPF) and in-process runtime that do the actual interception, and the network proxy — often the hardest part conceptually — is only 420 LOC (3%) because it stays at the logical-message level.
Q8How does Tamias find bugs beyond crashes?▾
Crashes are caught by process-exit monitoring; memory errors via AddressSanitizer for C/C++ targets; and target-specific semantic checkers (e.g., etcd's ported Porcupine-based linearizability checker and watch-response checker, ~1 person-day to integrate) catch silent correctness violations that don't crash anything.
Q9Does Tamias always beat DistFuzz?▾
On all four shared targets it achieves higher branch coverage — up to 47% (etcd), 19% (Nuraft), 11% (Braft), 4% (Redis/Raft) — attributed to fine-grained event control and systematic schedule exploration rather than timing perturbation. The paper doesn't claim universal dominance beyond these four comparison targets.
Q10Is Tamias's approach the same as record-and-replay debugging?▾
No. Record-replay tools (rr, Shadow) aim to reproduce a specific past execution exactly for debugging. Tamias's replay step is a means to an end inside a fuzzing loop — reconstructing a useful state cheaply so exploration can continue from it, not preserving an execution for its own sake.
Q11What are the known limitations?▾
No per-node clock skew; no sub-thread instruction-level interleaving exploration; feedback-determinism is verified specifically for branch coverage (finer-grained feedback might expose nondeterminism Tamias doesn't currently control); and native timerfd isn't yet supported (mitigated by disabling it at compile time on the two targets that needed it, without touching application logic).
Q12What did the evaluation actually run on, and for how long?▾
Bare-metal CloudLab machines (two Intel Silver 4114 CPUs, 192 GiB RAM, Ubuntu 22.04). Ablation and DistFuzz comparisons each used 10 independent 24-hour trials per configuration; peak fuzzing throughput ranged from 4 executions/sec (MySQL, etcd) to 33/sec (Redis) using 36 single-vCPU VMs.

Glossary & further reading

Every term in one place, results at a glance, then a path to go deeper.

Core terms
TamiasThe paper's fuzzer: transparent, feedback-guided input exploration integrated with systematic concurrency exploration via replay-explore.
Feedback determinismSame test case → same feedback (branch coverage) on rerun, even if the concrete execution differs. Weaker than, and sufficient in place of, full execution determinism.
Replay-exploreReplay a corpus test's schedule exactly through step s, then reconfigure the scheduler so only the suffix after s diverges into new territory.
Suffix-exploration propertyA guarantee that replay-explore, once a state S_s is reached, induces the same probability distribution over schedule suffixes as running the algorithm fresh from S_s.
Schedule-control programA step-indexed sequence of policy-change commands ⟨s,p⟩ that reconfigure the scheduling algorithm, virtual clock, or enabled inputs during a run.
PCTCPProbabilistic Concurrency Testing with Chain Partitioning — random chain priorities plus d−1 forced priority-drop points, with a probabilistic bug-finding guarantee.
Scheduling poset width (w)A structural parameter of PCTCP's causal-chain partial order that appears in its probability guarantee.
Quiescence detectionHow Tamias decides a scheduling step is over: no runnable threads and no in-flight proxy messages.
Supporting terms
Input program / schedule-control programThe two halves of a Tamias test case, each independently mutable.
Transparent testingControlling and testing an unmodified target from outside — no source-code changes required.
Branch coverage feedbackThe bitmap of executed code branches, collected via LLVM trace-pc-guard (C/C++) or libFuzzer mode (Go); Tamias's chosen feedback signal.
Virtual clock / time dilationControlling a target's entire perception of elapsed time so timeout behavior follows a scheduler-advanced virtual clock, inspired by time dilation in system emulation.
Transient sleepA short, unintended kernel-internal block (e.g., fsync waiting on writeback) that could be mistaken for an intended, event-driven blocking point.
R / R-IM / R-ISM, P / P-IM / P-ISMAblation configurations: random-walk or PCTCP, with no mutation, input-only mutation, or joint input+schedule mutation (full Tamias).
DistFuzzThe prior state-of-the-art black-box distributed fuzzer used as the coverage-comparison baseline; relies on symmetry-pruned message-sequence feedback and timing-based perturbation.
