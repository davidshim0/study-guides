Why event-driven is not the opposite of threaded

Two camps keep arguing over one axis when the real design space has two. This is the plain-English story of how "task management" and "stack management" got conflated into a single fake choice — and the sweet spot you get once you split them apart.

Before you begin

The vocabulary this paper needs

Not CS-101 review — just the paper's own distinctions, sharpened. Read in order, or jump to whatever's unfamiliar.

⚡ TL;DR

  • "Event-driven" and "threaded" each secretly bundle two independent decisions — task management (when tasks interleave) and stack management (how a paused task's local state survives). The paper unbundles them and shows a third, unnamed point: cooperative task management + automatic stack management, the "sweet spot."
  • The headline finding is a cost, not a benchmark number: under manual stack management, one function learning to block on I/O forces "stack ripping" that can propagate arbitrarily far up the call graph, and breaks four specific language features — scoping, automatic variables, control structures, and the debugger's call stack.
  • Why it matters: you can keep cooperative scheduling's easy concurrency reasoning without paying the stack-ripping tax — a tradeoff every callback-vs-coroutine, kernel-vs-userspace async design (io_uring, kernel workqueues, green threads) still re-litigates today.

1Task management: preemptive, serial, cooperative▾

A program's work splits into tasks, each a control flow touching some shared state. Preemptive task management lets tasks interleave or run in parallel at any point — powerful, but every access to shared state is a potential race. Serial runs one task to completion before starting the next — no races, but no overlap while a task waits on slow I/O. Cooperative is the compromise: a task only yields to others at points it chooses, usually when it must wait on I/O.

A yield point is exactly that chosen point — the specific place in a task's code where it voluntarily gives up the CPU and lets another task run. Under cooperative scheduling, a yield point is the only place another task's actions can possibly interleave with yours; everywhere else in your code, you have the shared state entirely to yourself, uninterrupted, with no lock needed to guarantee it.

Now you're ready: this paper argues for cooperative task management specifically because it keeps serial's easy reasoning (invariants only need to hold at yield points) while still overlapping slow I/O.
2Stack management: automatic vs. manual▾

When a task pauses (say, to wait on disk I/O), its local state has to live somewhere until it resumes. Automatic stack management lets the language's ordinary call stack hold it — you write one procedure, and a blocking call inside it just... blocks, transparently. Manual stack management means the programmer rips that procedure into separate event-handler functions and hand-carries the local state between them in an explicit data structure, because there's no call stack keeping it alive across the pause.

The push/pop mechanics of a call stack are always automatic, in the trivial CPU sense — that part is never the question. What "automatic vs. manual" actually asks is whether your task gets to keep using one particular stack continuously, uninterrupted, across a blocking wait. In a real OS thread (or a fiber/coroutine with its own separate stack), yes: something underneath is willing to let that stack sit idle, fully intact, while the task waits, and resume it later exactly where it left off — automatic. In a plain callback invoked directly by a shared event loop, no: once your handler function returns control to the loop (which it must do to let the loop keep dispatching other events), the loop's own stack unwinds back past your handler's frame, and that frame — and everything in it — is gone. There is no stack left to resume, so if you need to pick the work back up later, you must manually build a heap object holding whatever you needed to remember, and manually write a second function to pick it up. That is the case where it's manual: any style built as callbacks on a single shared event-loop stack, with no per-task stack of its own to fall back on.

Now you're ready: this is the second, independent axis. "Event-driven" typically means cooperative + manual; "threaded" typically means preemptive + automatic — but nothing stops you from mixing task management and stack management choices.
3What a continuation actually is▾

Under manual stack management, when a function initiates I/O and returns instead of blocking, it needs some way to remember "what to do when the result arrives" and "what local variables mattered." A continuation is exactly that: a small object bundling a function pointer (where to resume) plus the saved arguments/locals. The event scheduler calls the function pointer, passing the bundle, once the I/O completes.

Now you're ready: a continuation is manual stack management's hand-rolled substitute for what the call stack normally does for free.
4Synchronous vs. asynchronous I/O — a third, separate axis▾

A synchronous I/O call appears to block the caller until the result is ready. An asynchronous call returns immediately, letting the caller issue several overlapping operations and collect results later, in any order. This is orthogonal to task management: any task-management style can call either kind of I/O interface, and (with the right primitives) you can build one out of the other.

Now you're ready: don't conflate "my I/O call didn't block" with "my task management is cooperative" — they're different questions the paper keeps carefully separate.
5Conflict management: how much atomicity do you get for free?▾

Whatever runs between two yield points is effectively one atomic operation on shared state. Serial and cooperative task management hand you large, free atomic regions; preemptive hands you none, so you build atomicity yourself with locks/semaphores/monitors. Those primitives come in two flavors: pessimistic (lock the resource before touching it) and optimistic (compute speculatively, then retry if a conflict is detected).

Now you're ready: cooperative task management is valuable specifically because its atomic regions are big and free — as big as "everything between two yields" — with no locks required.
6Data partitioning: reducing conflicts by reducing sharing▾

Rather than manage conflicts over shared state, you can simply have less shared state. Data partitioning separates task-specific state (no concurrency concerns at all) from truly shared state (where task/conflict management still matters). Data crosses partitions by value, with care taken around anything that's really an implicit reference (like an array index).

Now you're ready: partitioning is orthogonal to, and can be combined with, any task-management/stack-management choice — it just shrinks the problem the other choices have to solve.
7Stack ripping, previewed▾

Under manual stack management, a single conceptual function that starts out compute-only (never blocks) and later evolves to need I/O must be torn — "ripped" — into two or more event-handler functions. Worse, every caller up the call chain that relied on it returning immediately may need ripping too. The paper treats this propagation, triggered purely by software evolution, as manual stack management's central cost.

Now you're ready: the GetCAInfo example you'll see later is exactly this scenario — an in-memory lookup that evolves into a disk-backed one.
8Hidden concurrency assumptions, previewed▾

Automatic stack management's cost is the mirror image: a blocking call is syntactically invisible. Nothing in a call site marks whether the callee might yield, so local state computed from shared state before the call may be silently stale after it returns. The paper's fix is to declare the assumptions explicitly: statically, by tagging yielding functions and marking atomic blocks so a compiler or tool can check them (proposed, not built); or dynamically, by bracketing atomic blocks with startAtomic()/endAtomic() so that yield() dumps core if the counter is non-zero (built).

Now you're ready: automatic stack management isn't free of risk — it trades a visible cost (ripping) for an invisible one (silently broken invariants) unless you add a check.

The whole story in one place

Two axes, mistakenly sold as one choice

The conflation, why it happened, and the point in the design space nobody had a name for.

The community's advice to programmers usually comes as a binary: pick "threaded" programming or pick "event-driven" programming. The paper's core move is to show this is a false binary because each label secretly bundles two separate decisions. Task management asks when tasks are allowed to interleave — preemptively, cooperatively, or serially. Stack management asks how a paused task's local state survives until it resumes — automatically, on the language call stack, or manually, hand-carried in continuation objects.

"Threaded programming" is really shorthand for one corner of a two-axis grid: preemptive task management paired with automatic stack management. "Event-driven programming" is shorthand for the diagonally opposite corner: cooperative task management paired with manual stack management. Because the two corners are always discussed as a package, it looks like task management and stack management must move together — but they don't. There is an unoccupied, unnamed third corner: cooperative task management with automatic stack management. The paper calls this the sweet spot.

First, what each label actually names, before the pairing. Threaded means: you write ordinary sequential procedures, and an OS or language runtime is free to interrupt any thread at essentially any instruction and run a different one — you never choose the interleaving points, the scheduler does, at arbitrary granularity. Event-driven means: a single loop dispatches short handler functions one at a time, and a handler runs uninterrupted, start to finish, until it itself decides to hand control back to the loop — normally by simply returning, right at the point it needs to start some I/O; nothing preempts it mid-handler.

Why do these two labels each bundle in a stack-management style, rather than the pairing being pure coincidence? Because of how each was actually built, not because of any logical necessity. A preemptible OS thread needs its own dedicated stack anyway, simply to survive being interrupted at an arbitrary instruction and resumed later — and once that persistent per-thread stack exists, ordinary blocking calls can just use it too, so automatic stack management comes along for free. A single-threaded event loop, conversely, was adopted specifically to avoid the cost and the races of OS threads — but without a real thread backing each task, there is no persistent stack sitting idle across a wait; the only option left is to hand-carry state in a heap object, which is manual stack management. The paper's point in flagging this as a false binary is that the coupling is an artifact of these two dominant historical implementations, not a rule: you could build cooperative task management on top of a persistent stack too (a fiber or coroutine, scheduled by you rather than preempted by the OS, but still a real stack that survives a wait) — which is exactly the unoccupied "sweet spot" corner.

Section 3 then spends its effort showing why each stack-management choice has a real cost. Manual stack management pays for its explicit yield points with stack ripping — tearing procedures apart, and having that tearing propagate up the call graph whenever a previously compute-only function evolves to need I/O. Automatic stack management avoids ripping but hides the yield points, risking invariant violations that are invisible in the source and only surface as software evolves. The paper's partial fix for that second risk is a runtime startAtomic()/endAtomic() counter that turns a silent violation into an immediate crash.

🍯 Key takeaways

  • Task management (when tasks interleave) and stack management (how paused state survives) are orthogonal axes, not one dial.
  • "Threaded" ≈ preemptive + automatic; "event-driven" ≈ cooperative + manual — two corners of a grid, not opposite ends of a line.
  • The unoccupied corner — cooperative + automatic — is the paper's "sweet spot": easy concurrency reasoning, ordinary readable procedures.
  • Manual stack management's tax is stack ripping: one blocking call can force many functions, up the whole call graph, to be torn apart.
  • Automatic stack management's tax is hidden concurrency assumptions: yield points are invisible at every call site.
  • A dynamic startAtomic()/endAtomic() counter converts that second, invisible risk into a loud runtime crash instead of silent corruption.
Five everyday pictures

How to think about the two axes

Each stands alone. Every card is honest about where the picture stops being true.

The core idea · Two independent axes

Two light switches on one wall

Two switches sit side by side, and it's tempting to assume they're wired together — flip one, the other follows. But one switch controls when tasks interleave (task management); the other controls how a paused task's state survives (stack management). They just happen to usually be flipped together by convention — "threaded" flips both one way, "event-driven" flips both the other.

Where it breaks: a real light switch has no in-between, and the task-management axis has a genuine third setting (serial) that a binary switch undersells. The stack-management axis really is two-valued in the paper (manual or automatic).
Stack ripping · Continuations

A recipe torn into index cards

One recipe, written as a single page, lets you glance up at earlier steps any time. Manual stack management tears that page into separate index cards — one per step that might have to wait (for the oven, say) — and each card must explicitly say which card to flip to next, plus jot down any ingredient amounts you'd otherwise just remember from reading the whole page. That jotted note is the continuation.

Where it breaks: index cards are static once written; the paper's real problem is that a page you already trusted as "one step, no waiting" gets retroactively torn into cards after the fact, when a later step turns out to need to wait.
Hidden concurrency · Automatic stack mgmt's risk

An invisible trapdoor in the floor

You walk confidently across a familiar room, certain nothing changes underfoot mid-stride. With automatic stack management, any function call is a plank that might silently become a trapdoor: it can start blocking for I/O tomorrow even though it never did today, and nothing marks the plank differently. Local state you computed just before stepping on it may not be there when you land.

Where it breaks: a trapdoor is binary (safe or not); the paper's actual danger is subtler — the call itself still "succeeds," it's the shared state around it that may have shifted while you were suspended.
Conflict management · Pessimistic vs. optimistic

Reserving a room vs. just walking in

A pessimistic lock is booking the conference room in advance — guaranteed exclusive access, but you paid the booking overhead even if no one else wanted it. An optimistic scheme is walking straight in, and backing out (retrying) only if someone's already there. Cooperative task management gives you something better than either: the whole room for as long as you like, for free, because nobody else can walk in until you yield.

Where it breaks: cooperative "free" exclusivity only lasts until the next yield point — if your task needs the room across an I/O wait, the analogy's "for free" part quietly ends there.
Enforcement · startAtomic() / endAtomic()

A sign that's only checked when someone tries the door

You could hang a permanent "do not enter" sign (a static compile-time check) that everyone reads before ever reaching for the handle. The paper instead uses a cheaper trick: the sign is invisible, but a private counter ticks up when you enter a no-interruption zone and ticks down when you leave; if anything tries to yield while the counter is nonzero, it slams the door and dumps core. You only find out a violation happened at the moment someone actually tries it.

Where it breaks: a runtime crash on violation is useful but reactive — a code path that's never exercised in testing can carry a live violation nobody notices, unlike a static check the compiler would have caught up front.

2 · The running example: GetCAInfo (§3.1)

A function looks up a certificate authority record by id. It starts life compute-only — pure in-memory hash lookup, no I/O, no stack-management decision needed at all:

CAInfo GetCAInfo(CAID caId) {
    CAInfo caInfo = LookupHashTable(caId);
    return caInfo;
}

Now the CA population grows too large to fit in memory, so lookups may need a disk read on a miss. The function must now sometimes block on I/O. With automatic stack management, this is a small, local edit — the compiler's call stack keeps caId/caInfo alive across the blocking DiskRead call:

CAInfo GetCAInfoBlocking(CAID caId) {
    CAInfo caInfo = LookupHashTable(caId);
    if (caInfo != NULL) return caInfo;
    caInfo = new CAInfo();
    DiskRead(caId, caInfo);       // blocks; state just sits on the stack
    InsertHashTable(caId, caInfo);
    return caInfo;
}

With manual stack management, the same edit rips the function into two event handlers connected by a hand-built continuation:

class Continuation {
    void (*function)(Continuation cont);   // where to resume
    void *returnValue;
    void *arg1, *arg2, ...;                // hand-carried locals
};

void GetCAInfoHandler1(CAID caId, Continuation *callerCont) {
    CAInfo *caInfo = LookupHashTable(caId);
    if (caInfo != NULL) { (*callerCont->function)(caInfo); return; }
    caInfo = new CAInfo();
    Continuation *cont = new Continuation(&GetCAInfoHandler2, caId, caInfo, callerCont);
    EventHandle eh = InitAsyncDiskRead(caId, caInfo);
    RegisterContinuation(eh, cont);         // returns immediately — no blocking
}

void GetCAInfoHandler2(Continuation *cont) {
    // recover caId, caInfo, callerCont from cont->arg1..3
    InsertHashTable(caId, caInfo);
    (*callerCont->function)(callerCont);    // "return" via a call, not a return
}
💡
Notice the signature change: GetCAInfoHandler1 no longer returns a CAInfo at all — the value only exists once Handler2 runs, later. Every caller must now pass a continuation instead of receiving a return value.

Handler1 has two genuinely different endings, and it's worth tracing both explicitly. Cache hit (caInfo != NULL): the answer is already known, so Handler1 calls callerCont's function right now — (*callerCont->function)(caInfo) — handing the result to whoever is waiting for this whole lookup, then hits return; only to exit its own function body; there's nothing left for it to do. Cache miss (caInfo == NULL): Handler1 does not call callerCont at all yet — that would be wrong, since the real answer isn't ready. Instead it builds a brand-new, different continuation (cont, not callerCont) that bundles up everything Handler2 will need, kicks off the async disk read, registers cont against that pending I/O, and then hits the same return; — but this time the return means "Handler1 has nothing more to do right now," not "here is the answer." The rest of the original lookup's logic — InsertHashTable, and finally handing the result to callerCont — doesn't run inside Handler1 at all; it's relocated entirely into Handler2, a separate function invocation that the scheduler triggers later, once the disk read's event fires.

The continuation itself is the Continuation object built by new Continuation(&GetCAInfoHandler2, caId, caInfo, callerCont). Its function field is the resume point — a pointer to GetCAInfoHandler2, the code that should run next. Its arg1/arg2/... fields are where the actual values live — here, caId, the freshly allocated caInfo, and callerCont itself all get packed in, because none of them would otherwise survive past Handler1's return. When the disk read completes, the event system calls GetCAInfoHandler2(cont), passing back that exact same heap object; the comment // recover caId, caInfo, callerCont from cont->arg1..3 is where those values get unpacked back out, and only then does Handler2 finish the job — inserting into the hash table and finally calling callerCont's function, which is the "real" return for the whole lookup, three function-call boundaries later than where it started.

3 · Stack ripping: four things the compiler used to do for free (§3.2)

Once ripped, the programmer must manually reconstruct four language features that automatic stack management gets for free:

Feature lostWhat breaks
Function scopingOne conceptual function is now two-or-more source-language functions.
Automatic variablesLocals that lived on the stack must move into a heap-allocated continuation to survive the yield.
Control structuresEvery basic block containing a potentially-blocking call — including each loop iteration — must be reachable as its own continuation target, so loops get ripped repeatedly, not just once.
Debugging stackA debugger stopped inside Handler2 shows only that handler's frame — the earlier call history must be manually reconstructed from continuation objects, and hand-optimized tail calls can make even that impossible.
⚠
The propagation problem: when a previously compute-only function's concurrency semantics change, every function on every call-graph path from it up to the root may need ripping too — unless that ancestor already calls in continuation-passing form. Different teams often own different points along that path, which is exactly what makes the change hard to land.

4 · Hidden concurrency assumptions, and the dynamic check (§3.3)

Manual stack management's advantage is the mirror of its cost: every yield point is visible in the source, at every level of the call graph, because the function signature itself changes when a function starts yielding. Automatic stack management hides this — a call that "did not yield yesterday" can yield tomorrow with no syntactic trace, silently invalidating local state a caller computed from shared state beforehand.

The paper's fix pairs an ideal (but unimplemented in their systems) static check — tag yielding functions, mark non-yielding blocks atomic, and have the compiler reject any call to a yielding function from inside an atomic block — with a dynamic check they actually built:

startAtomic() { counter++; }
endAtomic()   { counter--; }

yield() {
    assert(counter == 0);   // dump core if we're inside an atomic block
    ... actually yield to another task ...
}
🍯
The tradeoff, honestly stated: the dynamic check turns a silent invariant violation into a loud crash — strictly better than corruption, but only if the violating path is actually exercised. A static check would catch it at compile time regardless of test coverage; the paper chose dynamic because it was "quick and easy to implement."

M1 · Task management and the atomicity contract (§2.1)

A task is one conceptual control flow; all tasks access some common shared state. Task management decides when one task's execution may interleave with another's. The paper defines three points on this axis.

Task managementWhere another task can runWhen global invariants must holdPaper's stated limitation
SerialOnly between whole tasksAt task boundariesNo multiprocessor parallelism; a slow task defers later tasks for a long time
CooperativeOnly at explicit yield points, "usually only when the task must wait for long-running I/O"Only at each yield; may be assumed valid on resumeLocal state derived from global state before a yield may be invalid after it; no multiprocessor parallelism
PreemptiveAnywhere (interleave on a uniprocessor, overlap on a multiprocessor)All the time, so synchronization primitives are neededRaces and deadlocks; the classic thread pitfalls

The contract cooperative task management offers. The paper states it as: "invariants on the global state only need be restored when a task explicitly yields, and they can be assumed to be valid when the task resumes." That is serial task management's guarantee, shrunk from "the whole task" to "the code between two yields." The price is the other half of the same sentence pair: if a task copied something out of shared state into a local variable before a yield, that local copy may be stale after the yield. The paper notes the identical problem appears under preemptive task management whenever code releases a lock for the duration of a slow I/O operation [Bir89].

The wrapping requirement. Cooperative task management only works if no task can block the whole program. So "every I/O library function called must be wrapped so that instead of blocking, the function initiates the I/O and yields control to another task. The wrapper must also arrange for its task to become schedulable when the I/O completes." A sketch of what such a wrapper does (names are this guide's, the steps are the paper's):

// cooperative wrapper around a blocking read (§2.1, sketch)
Result CoopRead(Args a) {
    Handle h = StartAsyncRead(a);        // 1. initiate, do not block the thread
    WakeTaskOnCompletion(h, currentTask);// 2. arrange to become schedulable again
    yield();                             // 3. the ONLY place other tasks may run
    return ResultOf(h);                 // 4. resumes after the I/O completed
}

Assumptions the contract depends on, and what breaks. (i) Exactly one task executes at a time. Put cooperative tasks on two processors and code between yields is no longer atomic; the paper's own analogy is interrupt masking in a uniprocessor kernel (§2.4), which likewise stops giving atomicity once a second CPU exists (inference for the multiprocessor half). (ii) Every blocking operation is wrapped. An unwrapped blocking call stalls the whole thread: atomicity survives (no one else runs) but all I/O overlap is lost (inference). (iii) Nothing preempts a task between yields; a task that computes for a long time delays every other task, the same weakness the paper names for serial task management. (Paper §2.1, §2.4)

M3 · Figure 1, cell by cell (§2.6)

Figure 1 puts task management on the x axis (serial, cooperative, preemptive, left to right) and stack management on the y axis (manual at the bottom, automatic at the top). It plots three named points. "Multithreaded" is preemptive plus automatic: conventional concurrent programming "exploits the automatic stack management of a standard language." "Event-driven" is cooperative plus manual: tasks are organized as event handlers that "yield control by returning control to the event scheduler, manually unrolling their stacks." The sweet spot is cooperative plus automatic. The paper draws two arrows: one from "multithreaded" diagonally down to "event-driven," and one from "event-driven" straight up to the sweet spot. It does not caption them. This guide's reading: the diagonal is the move the community recommended (and the authors first made, §1 and §5), which changes both axes at once; the vertical arrow is the paper's proposal, which keeps the task-management choice and changes only stack management.

The grid has six cells, not four. The "2x2" people usually mean is cooperative/preemptive by manual/automatic. The serial column matters as the anchor for cooperative's guarantee (M1).

Why the axes are orthogonal (the mechanical argument). Task management is about when the scheduler may switch. Stack management is about what is saved at a switch: a whole stack (automatic) or a hand-built continuation (manual). A cooperative scheduler can switch between full stacks (fibers) as easily as between continuations; the paper says "the scheduler is given precisely the same opportunities to schedule as in event-driven code; the only difference is whether stack state is kept on stacks or in chains of continuations on the heap" (§6). Conversely, a preemptive system could dispatch continuations from many threads (inference). Nothing ties one axis to the other except history.

M4 · The continuation object and the calling convention (§3.1)

Under manual stack management a task is a sequence of event handlers: procedures the scheduler invokes in response to events and that run to completion without blocking. To start an I/O, handler E1 schedules the request, does not wait, and registers a task-specific continuation with the scheduler. The continuation "bundles state indicating where E1 left off working on the task, plus a reference to a different event-handler procedure E2." E1 then returns to the scheduler. On the completion event, the scheduler calls E2 and passes E1's bundled state.

The protocol, step by step. (1) E1 calls an asynchronous initiator, e.g. InitAsyncDiskRead, which returns an EventHandle. (2) E1 allocates a continuation naming E2 and holding every value E2 will need, including E1's own callerCont. (3) RegisterContinuation(eh, cont) tells the scheduler which continuation to run when that event fires. (4) E1 returns; the whole language stack unwinds back to the scheduler. (5) On completion, the scheduler runs cont->function(cont). (6) E2 casts the arg fields back to their types, finishes, stores its result in callerCont->returnValue and "returns" by calling callerCont->function. The chain of callerCont pointers on the heap is the task's ripped call stack.

M6 · Control structures and the debugging stack (§3.2)

The paper lists four language features the programmer must now manage by hand for every ripped routine: function scoping (two or more language functions for one conceptual function), automatic variables (moved into a heap state structure), control structures, and the debugging stack. The first two are M5. The last two need a closer look.

Control structures. "The entry point to every basic block containing a function that might block must be reachable from a continuation, and hence must be a separate language-level function. That is, conceptual functions with loops must be ripped into more than two pieces." The reason is that a continuation's function field can only point at the start of a procedure, not into the middle of a loop. Every place execution must be able to resume becomes a procedure, and every jump into such a place (including a loop's back edge) becomes a call. An example built for this guide:

// automatic: one function
int SumBlocks(Id ids[], int n) {
    int sum = 0;
    for (int i = 0; i < n; i++)
        sum += ReadBlock(ids[i]);          // may block
    return sum;
}
// ripped: i and sum leave the stack; the loop head is its own function
void Sum1(Id *ids, int n, Cont *k) { State *s = new State{ids, n, 0, 0, k}; SumLoop(s); }
void SumLoop(State *s) {
    if (s->i == s->n) { s->k->returnValue = s->sum; (*s->k->function)(s->k); return; }
    StartReadBlock(s->ids[s->i], new Cont(SumBody, s));
}
void SumBody(Cont *c) {
    State *s = (State*) c->arg1;
    s->sum += (int) c->returnValue;  s->i++;

Debugging stack. Stopped in GetCAInfoHandler2, a debugger shows the scheduler and that one handler, "no information about the sequence of events that the ripped task performed before arriving" there. In theory the history can be recovered by following continuation objects; "in practice we have observed that programmers hand-optimize away tail calls, so that much of the stack goes missing." A hand tail-call here means a handler that passes its own callerCont straight through to the next operation instead of building a new continuation for itself, so no record of that level remains (this guide's reading of the phrase).

M7 · Software evolution under manual stack management (§3.2)

The trigger is a function changing from compute-only (never pauses for I/O) to potentially yielding, as when GetCAInfo's in-memory table becomes an on-disk structure with an in-memory cache. The paper's rule: "all functions, along every path from the function whose concurrency semantics have changed to the root of the call graph may potentially have to be ripped in two. (More precisely, all functions up a branch of the call graph will have to be ripped until a function is encountered that already makes its call in continuation-passing form.)" This propagation is what the paper names stack ripping and calls "the primary drawback to manual stack management."

Why the propagation is forced, step by step. (1) The evolved function's signature changed (M4), so every direct caller stops compiling. (2) To call it, a caller must pass a continuation, which means the caller must have a "rest of me" function to name: it must itself be cut at that call (RIP, M5). (3) Once cut, the caller no longer has the result before it returns, so it cannot return a value to its caller: its signature changes too. (4) Repeat. The recursion stops on a path only at a caller that already passes a continuation at that call site, because that caller is already split there and already expects a deferred answer.

RipUpward(f):                         // f just became potentially yielding
    for each caller g of f:
        if g already calls f in continuation-passing form: continue   // this path stops
        RIP(g) at its call to f       // M5 steps 1-7; loops in g add more pieces (M6)
        RipUpward(g)                  // g's signature changed as well

Two features make this expensive in practice. It follows every path, so a widely used helper drags many callers with it. And "as with all global evolutions, functions on the call graph may be maintained by different parties, making the change difficult." The compensating virtue is that the compiler finds every affected caller for you, because each one breaks.

M8 · Hidden yields under automatic stack management (§3.3)

"The huge advantage of manual stack management is that every yield point is explicitly visible in the code at every level of the call graph." With automatic stack management, the call to DiskRead inside GetCAInfo "hides potential concurrency": "local state extracted from shared state before the DiskRead call may need to be reevaluated after the call. Absent a comment, the programmer cannot tell which function calls may yield and which local state to revalidate as a consequence thereof."

The evolution asymmetry. When a manual-stack function evolves to yield, "its signature changes to reflect the new structure, and the compiler will call attention to any callers." When an automatic-stack function evolves to yield, "such a change is syntactically invisible and yet it affects the semantics of every function that calls the evolved function, either directly or transitively." The paper names the danger precisely: "a semantic property (yielding) of a called procedure dramatically affects how the calling procedure should be written, but there is no check that the calling procedure is honoring the property."

// example built for this guide: helper was compute-only, now logs to disk and yields

M9 · Making atomicity assumptions explicit: the static and dynamic checks (§3.3)

"Happily, concurrency assumptions can be declared explicitly and checked statically or dynamically." Both checks need the same two annotations: functions that may yield, and blocks that assume they do not.

Static check (proposed, "would be ideal"). Tag yielding functions with a yielding property; mark each block of a caller that assumes no yield as atomic. A compiler or static tool checks two rules: (R1) a function that calls a yielding function must itself be marked yielding; (R2) no call to a yielding function appears inside an atomic block. "In fact, one could reasonably abuse an exception declaration mechanism to achieve this end." This guide's reading of that remark: declare yielding functions as throws Yield in a language with checked exceptions; the compiler then forces every caller to declare throws Yield too (R1), and code written in a function that does not declare it cannot call a yielding function at all (R2, with "atomic" meaning "declared not to throw Yield").

Dynamic check (built). The paper chose it "because it was quick and easy to implement":

void startAtomic() { counter++; }        // "increments a private counter"
void endAtomic()   { counter--; }
void yield() {                            // reached whenever any function tries to block on I/O
    assert(counter == 0);                 // otherwise: dump core
    ... switch to the scheduler ...
}

Why a counter and not a flag: atomic blocks nest (an atomic helper called from an atomic region), and a flag would be cleared by the inner endAtomic. Why one counter is enough (inference): the paper calls it "a private counter" without saying whose. Since only one task runs at a time and a task can never yield while its count is non-zero (it would crash), the counter is always zero at every task switch, so a single per-thread counter correctly belongs to whichever task is running.

M10 · The fiber runtime and MainFiber (§4 intro, §5)

"In the Windows operating system, 'threads' are scheduled preemptively and 'fibers' are scheduled cooperatively." The implementation schedules many fibers on a single thread, so "at any given time, only one fiber is active." A fiber is a user-level thread: "each task's state is represented with a stack, and control is transferred by simply swapping one stack pointer for another, as with setjmp and longjmp" (§5). The measured cost of a switch in their fiber package is "less than ten times the cost of a procedure call" (§6).

Placement rules (the invariants the hybrid rests on).

  1. The scheduler runs on a special fiber, MainFiber, and schedules both manual-stack code (event handlers, i.e. continuations) and automatic-stack code.
  2. Event handlers run on MainFiber. The adaptor code is annotated "Executed on MainFiber" wherever it plays the role of a continuation.
  3. Automatic code that expects to block always runs on a fiber other than MainFiber, and when it blocks "it always yields control back to MainFiber, where the scheduler selects the next task." It never switches directly to another worker fiber.
  4. Compute-only functions may run on any fiber, "since they may be freely called from either context."

Why one combined scheduler. Two reasons, both stated. The Windows fiber package "only supports the notion of explicitly switching from one fiber to another specified fiber; there is no notion of a generalized yield operation that invokes a default fiber scheduler," so the authors had to supply the scheduler anyway. And a single scheduler avoids "two, potentially conflicting, schedulers running in parallel: one for event handlers and one for fibers." The scheduler's only abstraction is "run a continuation": resuming a blocked fiber is itself packaged as a continuation (FiberContinue, M13).

// MainFiber, assembled from §4 (inference: the paper never prints the loop)
for (;;) {
    Continuation *c = NextReady();   // I/O completions + entries from scheduler->schedule(...)
    (*c->function)(c);               // a handler, an adaptor half, or FiberContinue;
}                                    // it may SwitchTo a fiber, and control comes back here

What breaks if rule 3 is violated (inference). Automatic code that blocked while running on MainFiber would try to "switch back to MainFiber" from MainFiber itself. The scheduler's frames would sit underneath the blocked task's frames, so the scheduler could not run another task until this one finished: the whole program would stall. That is exactly why manual code may not call automatic code directly (M11). Limits of fibers (inference). The kernel sees one thread. A page fault or an unwrapped blocking system call stops every fiber, and fibers cannot use a second processor; the paper concedes the multiprocessor point in §2.1 and §6.

M12 · CFA: manual code calling automatic code (§4.1, Figure 2)

CFA stands for Continuation-to-Fiber Adaptor: it accepts a continuation (the manual convention) and runs the callee on a fiber (the automatic convention). Idea in one sentence: "we create a new fiber and execute the callee code on that fiber. The caller resumes (to manually unroll its stack) as soon as the first burst of execution on the fiber completes." The adaptor is itself ripped into a call part and a return part.

void VerifyCertCFA(CertData certData, Continuation *callerCont) {
    // Executed on MainFiber
    Continuation *vcaCont = new Continuation(VerifyCertCFA2, callerCont);
    Fiber *verifyFiber = new VerifyCertFiber(certData, vcaCont);
    SwitchToFiber(verifyFiber);   // starts VerifyCertFiber::FiberStart
    // Control returns here when verifyFiber blocks on I/O
}
VerifyCertFiber::FiberStart() {
    // Executed on a fiber other than MainFiber; the call below could block on I/O
    this->vcaCont->returnValue = VerifyCert(this->certData);
    scheduler->schedule(this->vcaCont);  // schedule VerifyCertCFA2
    SwitchTo(MainFiber);
}
void VerifyCertCFA2(Continuation *vcaCont) {
    // Executed on MainFiber, scheduled after verifyFiber is done
    Continuation *callerCont = (Continuation*) vcaCont->arg1;
    callerCont->returnValue = vcaCont->returnValue;
    (*callerCont->function)(callerCont);    // "return" to FetchCert (FetchCert3)
}
  1. Call. Event handler FetchCert2, on MainFiber, calls VerifyCertCFA(certData, callerCont) where callerCont names FetchCert3. The CFA takes "the arguments of the adapted function and a continuation ('stack frame') for the calling task."
  2. Own continuation. It builds vcaCont = {VerifyCertCFA2, arg1 = callerCont}.
  3. Fiber. It creates verifyFiber, an object of VerifyCertFiber (a subclass of Fiber) that remembers the function arguments and vcaCont.
  4. Switch in. SwitchToFiber(verifyFiber). The new fiber runs the glue routine FiberStart, which unpacks the parameters and calls VerifyCert.
  5. First block. When VerifyCert yields for I/O, the switch to MainFiber happens "in the I/O function (not the call site shown in the FiberStart() routine above)." Control lands just after SwitchToFiber in VerifyCertCFA.
  6. Unroll. VerifyCertCFA returns, then FetchCert2 and GetCertData2 return to the scheduler. "Thus, the hybrid task has blocked for the I/O initiated by the code with automatic stack management while ensuring that event handler FetchCert2 does not block."
  7. Further bursts. When the I/O completes, verifyFiber is resumed (the mechanism is the FCA, M13). The fiber "may run and block for I/O several times."
  8. Finish. VerifyCert returns into FiberStart, which "stuffs the return value into VerifyCertCFA2's continuation, schedules it to execute, and switches back to the MainFiber a final time. At this point, verifyFiber is destroyed."
  9. Return. The scheduler later runs VerifyCertCFA2 on MainFiber; it copies the return value into callerCont and calls FetchCert3, "as code with manual stack management normally does."

Why FiberStart schedules VerifyCertCFA2 rather than calling it (inference). A direct call would run manual code (FetchCert3 and everything it calls) on verifyFiber, breaking the rule that handlers run on MainFiber; any further continuation-passing calls in FetchCert3 would unwind into FiberStart instead of the scheduler; and the fiber could not be destroyed while code is still executing on its stack. Handing the result over through the scheduler lets the fiber end cleanly first.

No short circuit in this direction (inference). If VerifyCert never blocks, the first burst runs to the end: the result still goes through scheduler->schedule, and other tasks may run before FetchCert3. That is harmless, because manual code already treats every continuation-passing call as a possible yield. Cost per CFA call (counted from the code): one new fiber (a stack), two continuations, at least two fiber switches, plus two more switches for every I/O block inside the callee. The paper does not measure fiber creation.

M13 · FCA: automatic code calling manual code (§4.2, Figure 3)

FCA stands for Fiber-to-Continuation Adaptor: called by code running on a fiber, it invokes manual code with "a special continuation and relinquishes control to the MainFiber, thereby causing the adaptor's caller to remain blocked. When the I/O completes, the special continuation runs on the MainFiber and resumes the fiber of the blocked adaptor."

Boolean GetCAInfoFCA(CAID caid) {
    // Executed on verifyFiber. Get a continuation that switches control
    // to this fiber when called on MainFiber
    FiberContinuation *cont = new FiberContinuation(FiberContinue, this);
    GetCAInfo(caid, cont);
    if (!cont->shortCircuit) {
        SwitchTo(MainFiber);          // GetCAInfo did block
    }
    return cont->returnValue;
}
void FiberContinue(Continuation *cont) {
    if (!Fiber::OnMainFiber()) {
        // Manual stack mgmt code did not perform I/O: just mark it as short-circuited
        FiberContinuation *fcont = (FiberContinuation) *cont;
        fcont->shortCircuit = true;
    } else {
        // Resumed after I/O: simply switch control to the original fiber
        Fiber *f = (Fiber *) cont->arg1;
        f->Resume();
    }
}

The FiberContinuation. A continuation whose function is FiberContinue, whose arg1 is the fiber to resume, plus a shortCircuit flag (false at creation). To GetCAInfo it is an ordinary callerCont.

  1. Call. On verifyFiber, VerifyCert calls GetCAInfoFCA(caid), an ordinary blocking-style call.
  2. Special continuation. The FCA allocates the FiberContinuation naming the current fiber.
  3. Run the manual code on the fiber. GetCAInfo(caid, cont). On a miss it starts the disk read, registers its own continuation (GetCAInfo2, holding cont as its caller continuation) and returns "to what it believes to be the event-handling scheduler; of course, in this case, the control returns to GetCAInfoFCA."
  4. Block. shortCircuit is still false, so the FCA "must ensure that control does not yet return to VerifyCert" and calls SwitchTo(MainFiber). The frames FiberStart, VerifyCert, GetCAInfoFCA stay parked on the fiber's stack.
  5. Unwind on MainFiber. MainFiber resumes in "the continuation code that started this burst of fiber execution," here VerifyCertCFA, which "returns several times to unroll its stack," and the scheduler runs other tasks.
  6. Completion. The scheduler runs GetCAInfo2 on MainFiber. It fills the hash table and "returns" by calling its caller's continuation, which is FiberContinue.
  7. Resume. FiberContinue sees it is on MainFiber, so it calls Resume() on the fiber in arg1. Control continues in the FCA just after its SwitchTo; the "bottom half" returns cont->returnValue to VerifyCert.
  8. Back to MainFiber, later. When the fiber next blocks or finishes, MainFiber resumes inside FiberContinue (where it switched away), which returns, then GetCAInfo2 returns to the scheduler. Figure 3 draws this as "verifyFiber Done" arriving at FiberContinue.

Invariant. A parked fiber is resumed only by a continuation that the scheduler runs on MainFiber, and FiberContinue is that continuation. Whichever MainFiber code switched into a fiber is the code that resumes when the fiber switches out (first burst: VerifyCertCFA; later bursts: FiberContinue), and in every case it simply returns, so the scheduler only ever sees ordinary continuations returning.

M14 · The short circuit (§4.2, Figure 4)

The branch "not followed in the example handles the case where GetCAInfo returns a result immediately without waiting for I/O. When it can do so, it must not allow control to pass to the scheduler." On a hit, GetCAInfo calls its caller continuation right away, before returning. That runs FiberContinue on verifyFiber; OnMainFiber() is false, so it only sets shortCircuit = true. GetCAInfo returns, the FCA sees the flag, skips the switch, and returns the value. No other task ran.

Why "am I on MainFiber?" is the right test. The scheduler only runs on MainFiber (M10 rule 1), and an FCA's caller is never on MainFiber (rule 3). So FiberContinue runs on MainFiber exactly when the scheduler invoked it after the task gave up the CPU, i.e. exactly when the I/O path was taken. Running anywhere else means it was called synchronously from inside GetCAInfo.

Why the paper needs it. "This is necessary so that a caller can optionally determine whether or not a routine has yielded control and hence whether or not local state must be revalidated. Without a short circuit path, this important optimization and an associated design pattern that we describe in Section 5 cannot be achieved." The pattern is the Pinning Pattern (M17).

What would break without some flag (inference). Suppose the FCA always called SwitchTo(MainFiber). On a hit the continuation has already run, so nothing is left registered that will ever resume the fiber: the task would be parked forever, a lost wakeup. The only safe alternative would be to have FiberContinue schedule a resume through the scheduler even on a hit, which makes every call a yield: cached lookups would cost a scheduler round trip, and a caller could never get through a sequence of cache hits atomically.

No race between "check flag" and "switch" (inference). Could the disk read complete and FiberContinue run between GetCAInfo returning and the FCA testing the flag? No: completions are processed by the scheduler, the scheduler runs only on MainFiber, and MainFiber does not run until this fiber switches to it. Cooperative scheduling makes check-then-switch atomic. In a preemptive setting this is the classic lost-wakeup window between deciding to sleep and sleeping.

M15 · Why the hybrid stays cooperative, and what each side sees (§4.3)

"With adaptors in place, each style of code is unaware of the other. A function written with automatic stack management sees what it expects: deep in its stack, control may transfer away, and return later with the stack intact. Likewise, the event-handler scheduler cannot tell that it is calling anything other than just a series of ordinary manual-stack-management continuations." In short: "fiber execution looks like a continuation to the event-driven code, and the continuation scheduler looks like any other fiber to the procedure-oriented code."

The invariants, collected. (I1) One fiber executes at a time (fibers share one thread; in UCoM, at most one condition variable is signalled, M16). (I2) Control leaves automatic code only at a SwitchTo(MainFiber) inside an I/O function or an FCA's blocked path, or when the fiber finishes. (I3) Control leaves manual code only by returning to the scheduler. (I4) Nothing on MainFiber blocks. Consequence (this guide's reading): other tasks can run only at the points where the same code, written in a single style, would also have yielded, so the atomic regions are the same as in a pure cooperative program. The one addition is the CFA's final pass through the scheduler (M12), which occurs inside a continuation-passing call that manual code already treats as a yield.

What would break each invariant (inference). Run fibers on several preemptive threads and I1 fails: code between yields is no longer atomic, the scheduler's queues need locks, and the FCA's check-then-switch acquires a race. Deliver I/O completions by calling continuations directly from an I/O thread instead of queueing them to the scheduler and FiberContinue could run off MainFiber, misread the case, and set shortCircuit on a fiber that is about to park forever. Call an automatic function from a handler without the CFA and I4 fails (M10).

The OS still preempts these threads, but every task thread except one is blocked on its condition variable, so preemption cannot interleave two tasks' accesses to shared state: the cooperative semantics come from the baton discipline, not from the OS. The go flags matter (inference): with Mesa-style condition variables a signal is only a hint and is lost if no one is waiting yet, so each waiter must loop on a predicate, the same rule as in the Mesa paper.

The adaptor macros. Both directions of adaptor were "implemented ... with a series of mechanically-generated macros." There are two groups, one per direction. Within a group, variants cover the number of arguments, void versus non-void return type, and static function versus object method, because each needs different syntax. Each macro takes the signature of the function being adapted and declares and creates the appropriate Fiber and Continuation objects. In other words, the CFA and FCA code of M12 and M13 is boilerplate a programmer never writes by hand.

I/O threads and partitioning. "Both systems use extra threads for converting blocking I/O operations to non-blocking operations and for scheduling I/O operations, as is done in many other systems, such as Flash. Data partitioning prevents synchronization problems between the I/O threads and the state shared by cooperatively-managed tasks." These helper threads are preemptive, but they never touch the cooperative tasks' shared state, so the atomicity contract (M1) is untouched. The I/O-wrapping work of §2.1 "can be tedious," but "it can be automated, and we found that paying an up-front cost to reduce subtle race conditions was a good investment."

The evidence offered. "Our experience with both systems has been positive and our subjective impression is that we have been able to preempt many subtle concurrency problems by using cooperative task management." No bug counts, lines of code, or performance numbers are given.

M17 · The Pinning Pattern (§5)

The problem. "Cooperative task management avoids the concurrency problems of locks only if tasks can complete without having to yield control to any other task." A task that needs I/O must yield partway through, and the yield splits its atomic region. The authors found they "could often avoid the need for a lock" with a design pattern.

The idea. "I/O operations are used to pin resources in memory where they can be manipulated without yielding." Pinning "does not connote exclusivity": a pinned resource is held in memory so accessing it needs no I/O, "but when other tasks run, they are free to manipulate the data structures it contains." Functions have two phases: "a loop that repeatedly tries to execute all potentially-yielding operations until they can all be completed without yielding, and an atomic block that computes results and writes them into the shared state."

Dependent pins. "A function may need to compute on the results of a previously-pinned resource in order to decide which resource to pin next; for example, in Farsite this occurs when traversing a path in a directory tree. Thus, in the fully general version of the design pattern, a check after each potentially-yielding operation ascertains whether the operation did indeed yield, and if so, restarts the loop from the top. Once the entire loop has executed without interruption, we know that the set of resources we have pinned in memory are related in the way we expect, because the final pass through the loop executed atomically."

// sketch for a path lookup; PinEntry reports whether it yielded (via the FCA short circuit)
Result Lookup(Path p) {
  restart:
    Dir *d = root;
    for each component c in p {
        bool yielded;
        Entry *e = PinEntry(d, c, &yielded);  // may do I/O to bring the entry into memory
        if (yielded) goto restart;              // others ran: d -> c may no longer hold
        d = e->dir;                           // next pin depends on this one
    }
    startAtomic();                            // phase 2: no yields allowed
        compute on the pinned entries; write results into shared state;
    endAtomic();
}

Assumptions and what breaks (inference unless quoted). (1) The loop terminates only if a later pass can find everything already in memory. Pinning is what makes that likely: resources pinned on an earlier pass stay resident, so the next pass hits. If other tasks keep changing the structure (say, renaming directories on the path), new components keep requiring I/O and the loop can repeat; the paper gives no progress guarantee. Its §2.4 description of optimistic mechanisms mentions "falling back on a pessimistic mechanism if no forward progress is being made," and the Pinning Pattern is an optimistic scheme in which "a yield happened" stands in, conservatively, for "a conflict may have happened." (2) Without the short circuit every pin would yield, every pass would be interrupted, and the loop would never finish. (3) Phase 2 must not yield; wrapping it in startAtomic/endAtomic turns any mistake there into an immediate crash (M9). (4) Unpinning is not described in the paper.

⇄
Connection: Mesa monitors. The restart-on-yield loop is the cooperative version of Mesa's rule that a process woken by NOTIFY re-tests its condition in a WHILE loop before proceeding: in both, a wait released exclusive access, so the state observed before the wait is rechecked rather than trusted.

M19 · Limits, and what the paper does not show (§2.1, §5, §6, §7)

  • No evaluation. One measured number (fiber switch under ten procedure calls). No adaptor overhead, fiber-creation cost, memory per blocked task, or comparison of bug rates; the experience claim is a "subjective impression."
  • No multiprocessor parallelism. Stated in §2.1 and repeated in §6.
  • No preemption. A long compute burst delays every task (the serial-task weakness of §2.1 applies between yields).
  • Every I/O function must be wrapped (§2.1); an unwrapped blocking call stalls all tasks on the thread (inference).
  • Hidden yields remain in automatic code; the static check is proposed but not built, and the dynamic check only fires on executed paths and only in marked blocks (M9).
  • Language scope. The analysis targets systems languages without closures (§2.2); with closures or call/cc, manual stack management largely disappears.

The conclusions (§7), in the paper's terms. The debate is clarified by separating task management from stack management. "Whereas the choice of task management strategy is fundamental, the choice of stack management can be left to individual taste." The term "event-driven" bundles cooperative task management with manual stack management, which stops people from considering automatic stack management with cooperative tasks. Evolving manual code imposes stack ripping; evolving either style means revisiting invariant logic and sometimes making local changes to revalidate state. The hybrid adaptors let programmers of both camps, and code bases in both styles, work together.

Follow the paper's own example, step by step

Worked examples

Four traces through GetCAInfo, the call-graph propagation, and the atomicity counter.

① Tracing GetCAInfoBlocking (automatic stack management)

Walk through a cache miss for caId = 42.

  1. LookupHashTable(42) returns NULL — not cached.
  2. caInfo = new CAInfo() — allocated on the heap, but its pointer lives in a local variable on the stack frame.
  3. DiskRead(42, caInfo) blocks. The entire stack frame — caId, the caInfo pointer, the return address — sits untouched on the call stack for the duration.
  4. Disk I/O completes; execution resumes exactly where it left off, because the stack was never disturbed.
  5. InsertHashTable and return caInfo run as ordinary next lines — no restructuring was needed anywhere in this function.
🍯
Insight: nothing about this function's source changed shape when it grew an I/O path — only its behavior did. That's exactly the property manual stack management gives up.

② The same miss, manually stack-managed

  1. GetCAInfoHandler1(42, callerCont) runs. LookupHashTable(42) returns NULL.
  2. caInfo = new CAInfo(), then a Continuation is built: function = &GetCAInfoHandler2, arg1 = 42, arg2 = caInfo, arg3 = callerCont.
  3. InitAsyncDiskRead(42, caInfo) issues the request and returns an EventHandle immediately — no blocking.
  4. RegisterContinuation(eh, cont) hands the continuation to the scheduler, and Handler1 itself returns — control goes back to whatever called it, which is not the original caller's continuation yet.
  5. Later, the scheduler sees the I/O event and invokes GetCAInfoHandler2(cont), which recovers 42/caInfo/callerCont from the bundle, inserts into the hash table, then calls (*callerCont->function)(callerCont) — a function call standing in for what would have been a plain return.
💡
Compare step 4 here to step 3 in example ①: automatic stack management just waits; manual stack management must explicitly hand off to a scheduler and trust it to call back later. The continuation is doing the stack's job by hand.

③ Stack ripping propagating up the call graph

Suppose (hypothetically, following the paper's general claim in §3.2) a function F calls G, which calls H — and H is GetCAInfo, which just evolved to sometimes block.

  1. H (GetCAInfo) ripped: becomes Handler1/Handler2 as in example ②. It no longer returns a value to its caller directly.
  2. G must be ripped too — unless G already called H in continuation-passing form. If G expected a return value from H to keep computing, G now has to be split at the point it called H, becoming G_before (initiates the call, passes a continuation) and G_after (resumes once H's continuation fires).
  3. F must be ripped by the same logic, if F's continuation past its call to G depended on G returning promptly.
  4. The propagation stops only when it reaches a function that was already written in continuation-passing form — i.e., one that never assumed its callee returned promptly in the first place.
⚠
Why this is the paper's central complaint: the trigger (H's evolution) and the damage (ripping F and G) can be owned by entirely different programmers, at arbitrary distance up the call graph — a purely local-looking change (H starts blocking) becomes a non-local refactor.

④ Tracing the startAtomic()/endAtomic() counter

A nested atomic region, followed by an accidental yield attempt.

  1. Enter an outer atomic block: startAtomic() → counter = 1.
  2. Call a helper that itself starts an inner atomic block: startAtomic() → counter = 2.
  3. The inner block ends: endAtomic() → counter = 1.
  4. Inside the (still-active) outer block, code calls a library function that — unbeknownst to the caller, perhaps recently changed — now calls yield().
  5. yield() asserts counter == 0. It's 1, so the assertion fails and the process dumps core, pinpointing the exact call that violated atomicity — before any shared-state corruption could occur.
🍯
Insight: the counter can't tell you the violation is possible ahead of time — only that it happened, on whatever execution path was actually taken. That's the dynamic-check tradeoff named explicitly back in §3.3.

Practice problems

Problem 1 · easy
A system uses preemptive task management but automatic stack management — is this "threaded programming," "event-driven programming," neither, or the sweet spot?
Show answer
This is exactly the "multithreaded" corner as the paper defines it — preemptive task management is standard practice paired with automatic stack management (an ordinary language procedure that can block). It is not the sweet spot, which requires cooperative, not preemptive, task management.Misconception: that "automatic stack management" alone signals the sweet spot. The sweet spot needs both axes set correctly — cooperative AND automatic — not just one.
Problem 2 · easy
True or false: switching an I/O call from synchronous to asynchronous automatically makes a program's task management cooperative.
Show answer
False. I/O management (sync/async) is an orthogonal axis from task management. You can issue asynchronous I/O calls inside preemptive, serial, or cooperative code equally; the paper explicitly separates this concern (§2.3) precisely to prevent this conflation.Misconception: treating "non-blocking call" and "cooperative scheduling" as the same fact. A call not blocking the caller says nothing about how/whether other tasks get to run.
Problem 3 · medium
GetCAInfo evolves from a pure in-memory lookup to one that may hit disk. Under manual stack management, exactly which call sites are forced to be ripped, and which aren't?
Show answer
Only call sites (and their ancestors up the call graph) that assumed GetCAInfo returned a value immediately need ripping — and the ripping propagates only as far up as the nearest ancestor that was already written in continuation-passing form (i.e., already didn't assume an immediate return). A caller that was itself already an event handler taking a continuation doesn't need further changes.Misconception: that ripping is "all or nothing" across the whole program. It propagates along specific call-graph paths and can stop early if it hits code already structured the right way.
Problem 4 · medium
Why does the paper call cooperative task management's atomic regions "free," when conflict management under preemptive task management needs explicit locks?
Show answer
Because under cooperative task management, everything executed between two yield points is automatically atomic with respect to other tasks — no other task can run and touch shared state until a yield happens. No lock acquisition, no lock data structure, no contention — the atomicity is a structural consequence of the scheduling discipline itself, not a mechanism you had to build.Misconception: that "free" means infinite — the atomic region ends the moment the task yields (e.g., for I/O), so anything spanning a yield still needs its invariants re-checked on resume.
Problem 5 · hard
Construct a scenario where automatic stack management's hidden-yield risk causes a real bug, and explain exactly what the dynamic startAtomic()/endAtomic() check would and would not catch.
Show answer
Suppose function A reads shared counter x, calls helper B (previously compute-only, now silently modified to block on I/O internally), then uses the earlier value of x assuming it's still current — but another task ran during B's block and changed x. If A had wrapped the region in startAtomic()/endAtomic(), B's internal yield() call would assert counter != 0 and crash immediately, pointing straight at the violation. But if A never wrapped the region (because the programmer didn't know to), the check catches nothing — the stale read proceeds silently, and the bug still happens.Misconception: that adding the dynamic check anywhere in the codebase protects the whole program. It only protects the specific atomic blocks a programmer remembered to mark.
Problem 6 · medium
Lauer and Needham's "message-oriented" system passes task state around in messages with no shared-state conflicts. Is this the paper's "event-driven" corner?
Show answer
No. Section 6 answers this directly: the message-oriented model has manual stack management (task state travels in messages) and avoids conflicts by partitioning state so it is effectively never shared, but the paper says neither Lauer and Needham model uses cooperative task management "as we regard it," because both require identically detailed reasoning about conflict management. So their duality result is "decidedly not" a comparison between multithreaded and event-driven programming. See How It Works, Part II, M18.Misconception: assuming any message-passing, no-shared-state design must be "event-driven" in this paper's sense. The paper's terms are precise axis labels: event-driven means cooperative task management plus manual stack management, and manual stack management alone is not enough.
Problem 7 · easy
A function's local variables need to survive a blocking call. Under automatic stack management, where do they live? Under manual?
Show answer
Automatic: on the ordinary language call stack, untouched, exactly as for any other function call. Manual: hand-copied into a heap-allocated Continuation object's fields (arg1, arg2, ...), because there is no call stack frame spanning the yield.Misconception: thinking manual stack management avoids using memory for this state — it just moves the same state from the (free, compiler-managed) stack to a (programmer-managed) heap object.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Isn't "event-driven" just another word for "asynchronous"?▾
No — that's exactly the conflation the paper is trying to dissolve. Asynchronous vs. synchronous is about whether an I/O call appears to block its caller (§2.3), which is orthogonal to task management. "Event-driven" as commonly used bundles cooperative task management (§2.1) with manual stack management (§2.2) specifically — two separate decisions, neither of which is simply "asynchronous."
Q2So is cooperative task management always the "right" choice?▾
The paper is explicit that it's a compromise, not a universal winner: cooperative task management is inappropriate when you need real multiprocessor parallelism, or when a slow task genuinely must not be allowed to defer others for a long stretch — those cases call for preemptive task management despite its harder conflict-management story.
Q3What exactly makes manual stack management hard, in one sentence?▾
It forces the programmer to hand-reimplement four things a structured language normally gives for free — function scoping, automatic variables, control-structure entry points, and the debugger's call stack — and re-do that reimplementation every time a previously non-blocking function evolves to block.
Q4What exactly makes automatic stack management risky, in one sentence?▾
A function's decision to yield is a semantic property that silently affects every caller's correctness, but nothing in ordinary procedure syntax marks which calls yield — so the compiler can't warn you when a previously safe assumption becomes false.
Q5Why doesn't the paper just use a static check instead of the runtime counter?▾
It says the static approach — tagging yielding functions and having the compiler reject yielding calls inside atomic blocks — would be ideal, catching violations at compile time regardless of test coverage. They built the dynamic startAtomic()/endAtomic() counter instead because, in their own words, it was "quick and easy to implement."
Q6Does a "compute-only" function ever need to worry about any of this?▾
Not initially — the whole point of the GetCAInfo example is that a compute-only function needs neither stack-management style, since it never yields. The danger is purely about what happens when such a function evolves to potentially block, at which point the choice suddenly matters retroactively.
Q7Can stack ripping ever be bounded, or does it always propagate to the program's root?▾
It's bounded by the nearest ancestor in the call graph that was already written in continuation-passing form — i.e., one that never assumed its callee returned immediately. Ripping stops there rather than necessarily reaching the top-level entry point, but that ancestor could still be arbitrarily far away.
Q8Is data partitioning a substitute for choosing a task-management or stack-management style?▾
No — it's a fifth, separate concept (§2.5) that reduces how much state is even subject to conflict management, but it doesn't answer when tasks interleave or how paused state survives. You still need a task-management and stack-management choice for whatever state remains genuinely shared.
Q9Why does the paper bother naming "serial" task management at all if nobody wants it?▾
Serial task management is the conceptual anchor that makes cooperative's advantage legible: it has zero conflict-management burden because a task is a complete atomic unit, and cooperative is explicitly framed as preserving most of that property while still overlapping I/O — you can't state that comparison without naming serial first.

Where a 2002 paper about I/O callbacks rhymes with today's kernel and memory-tiering work.

🧭
Heads up: this tab is speculative, not source text. Everything in the tabs before this one is grounded in the paper. Everything below is this guide's own extrapolation to modern systems the paper never discusses; treat it as "interesting analogy," not as a claim the paper makes.

🔁 io_uring and async/await, as an analogy — not an identity

Raw io_uring's submission/completion-queue model resembles manual stack management: you register a request, get a completion event later, and must hand-carry whatever state the "continuation" needs. Async/await layers built on top of it (Rust's tokio, C#, JS) are a useful picture of the paper's "sweet spot" — cooperative scheduling with a call site that reads like one ordinary procedure — but not an exact match: under the hood, the compiler/runtime lowers an async function into a generated state machine, not the paper's literal automatic call-stack management. It gets close to the sweet-spot experience without being the same mechanism.

🛡️ eBPF's verifier: closer to banning yield points than to "manual stack management"

An eBPF program's verifier forbids arbitrary blocking kernel calls and unbounded loops. That's closer to eliminating yield points altogether — forcing compute-only execution — than to the paper's manual stack management, which is specifically about continuation/state-passing across a wait. When an eBPF program needs something that can block, it doesn't rip its own stack the way the paper describes; it hands off to a separate program triggered by a new event, sidestepping the ripping problem rather than exemplifying it.

🧹 Kernel reclaim paths: mostly ordinary sleeping stacks, not continuations

Kernel threads like kswapd, and most workqueue-based reclaim/migration code, actually run on ordinary kernel stacks and are free to sleep — they don't fit the paper's "manual stack management" model of hand-carried continuation objects. The closer kernel analogues to that model are contexts that truly can't sleep (hardware interrupt handlers, softirqs/tasklets), which must hand state off via a callback-style structure precisely because they have no call stack to spare across a wait.

⏸️ Interrupt handlers: serial-like on one core, not conflict-free system-wide

An interrupt handler running with interrupts masked resembles the paper's serial task management only within a single CPU's timeline: nothing else on that core interleaves during the handler. But on a multiprocessor, other cores keep running concurrently, so the handler still needs locks or memory barriers to synchronize with them — "zero conflict-management overhead" doesn't hold system-wide. That partial atomicity is still part of why long-running migration/tiering work gets pushed out to a sleepable workqueue context instead of staying in the handler.

🍯
Speculative extension, not a claim from the paper: whatever mechanism decides page placement in a memory-tiering system (kernel thread, eBPF hook, or async userspace daemon) faces a structurally similar tension — a callback-driven state machine avoids blocking the reclaim path but pays some "ripping"-like tax whenever a fast path gains a slow one. This is offered here as a suggestive parallel for further thought, not something the paper itself argues.

Discussion questions

Each ties to a specific claim or design decision from Sections 1–3.

  1. Is the "orthogonality" of task management and stack management (Fig. 1) actually clean, or does cooperative task management make automatic stack management strictly safer to get away with? (the paper claims two independent axes, but every atomic-block violation example it gives involves cooperative scheduling specifically — push on whether the axes really are independent in practice.)
  2. The dynamic startAtomic()/endAtomic() check only fires on paths actually executed — how far does that undermine its usefulness compared to the "ideal" static check the paper describes but didn't build? (ask what fraction of real ripping-adjacent bugs would hide in untested code paths.)
  3. Section 3.2 says stack-ripping propagation stops at "a function already in continuation-passing form" — under what call-graph shapes (diamond dependencies, cross-team library boundaries) could that propagation still become effectively unbounded? (probe whether the stopping condition is as reassuring as it sounds once ownership crosses team lines.)
  4. Compare the paper's "a call that didn't yield yesterday might yield tomorrow, invisibly" risk to modern async/await, where a function's async-ness is part of its type signature — does that fully solve the §3.3 problem, or just relocate it? (consider whether type-level async tagging is the "static check" the paper wished it had.)
  5. The GetCAInfo example triggers ripping the moment the hash table becomes disk-backed — does the paper's cost analysis change at all if most lookups still hit the in-memory cache and rarely actually block? (the paper's own cost accounting in §3.2 doesn't condition on hit rate — is that a gap, or does ripping's cost genuinely not depend on how often the slow path fires?)

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
Task managementThe axis governing when tasks may interleave: preemptive, cooperative, or serial.
Stack managementThe axis governing how a paused task's local state survives: automatic (call stack) or manual (continuations).
Cooperative task managementTasks yield to each other only at chosen points, typically before blocking I/O — the paper's preferred axis-1 choice.
The sweet spotCooperative task management + automatic stack management — the paper's unoccupied, unnamed third corner of the design grid.
Manual stack managementHand-splitting a task into event handlers, carrying state in continuation objects since the call stack can't span the pause.
ContinuationA bundled function pointer + saved state, standing in for a stack frame under manual stack management.
Stack rippingTearing a procedure into event handlers, and that tearing propagating up the call graph as a callee's concurrency semantics evolve.
Hidden concurrency assumptionLocal state computed before a call that silently becomes stale if that call starts yielding, invisibly, under automatic stack management.
startAtomic() / endAtomic()A runtime counter marking "must not yield" regions; yield() asserts the counter is zero and crashes if not.
Supporting terms
Preemptive task managementTasks can be interrupted/interleaved at any point — the conventional multithreaded model.
Serial task managementOne task runs to full completion before the next begins; no interleaving, no conflict management needed.
I/O management (sync/async)Whether an I/O call appears to block its caller — an axis orthogonal to task management.
Conflict managementHow atomicity guaranteed by the task-management style is turned into a mechanism (locks, or optimistic retry) for avoiding races.
Pessimistic / optimistic synchronizationLock-before-touching vs. compute-speculatively-and-retry-on-conflict.
Data partitioningSeparating task-local state from truly shared state to shrink how much needs conflict management at all.
Compute-only functionA function that never yields — needs no stack-management decision until/unless it evolves to block.
call-with-current-continuation (call/cc)Scheme's built-in facility for first-class continuations, which sidesteps manual stack management entirely — noted by the paper as out of scope for languages without it.
