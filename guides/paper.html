SOSP 2026 · A Field Guide

The index that wins by forgetting almost everything it just wrote

CXL lets several hosts share memory — but hardware only keeps a sliver of it (~128MB) truly coherent. Every mutable byte outside that sliver needs a version check before a host can trust its cache, and a real flush when that check comes back stale. This is the story of Prism: an index built on the disk-era LSM tree, because LSMs happen to confine mutation to almost nothing.

📄 Hombal, Hu, Aguilera, Alagappan, Ganesan · SOSP'26 🎓 CXL/coherence basics assumed — this guide focuses on the LSM/index mechanics ⏱ ~25 min read
🗄️

Keep the part of the index you can modify SMALL enough to fit the coherent island — not whichever layout is easiest to build.
Everything else should be write-once, so nobody has to ask if it's stale.

Before you begin

Quick glossary, then six primers

You already know CXL, tiering, and the mm stack — the glossary is just for this paper's vocabulary, and the primers focus on the LSM/database-index side, which is the less familiar half.

scrSmall hardware-coherent region of CXL memory (~128MB) — behaves like ordinary coherent DRAM.
lnrLarge non-coherent region (TBs) — CPU caches for it are not kept in sync across hosts by hardware.
LSMLog-structured merge tree — memtable + immutable sorted files, built for disks, repurposed here.
SSTableAn immutable, sorted, on-disk-style file an LSM writes once a memtable fills.
ARTAdaptive Radix Tree — the fast in-memory index Prism competes against and also uses internally.
OLCOptimistic Lock Coupling — per-node version numbers for lock-free concurrent reads.
BULBounded Updatable Layer — Prism's new idea: a size-capped, in-place-updatable ART sitting in lnr.
YCSBYahoo Cloud Serving Benchmark — the standard key-value workload suite used for evaluation.
scr — hardware coherent lnr — needs software coherence Prism / BUL machinery the core insight
1Software coherence, in one sentence▾

Hardware only guarantees coherence inside scr. For data in lnr, a host keeps a version number for that data in scr; before trusting its own CPU cache, it checks whether the version changed, and if so clflushopts the stale lines and re-reads from CXL. If it has changed, that's a real flush — expensive. If not, the cache still serves the data, but that version check itself is another memory access every single node access pays, even when nothing changed.

Now you're ready: every design decision in this paper is really a decision about where version numbers live and how coarsely they cover the data — because that's what determines flush frequency.
2Optimistic Lock Coupling (OLC), briefly▾

ART-OLC and B-tree-OLC already keep a version counter per tree node so lock-free readers can detect a concurrent writer mid-traversal and retry. Prism's trick is piggybacking coherence tracking on this exact mechanism — the same counter that says "did a writer touch this node" can also say "did a *remote host* touch this node," so no new metadata scheme is needed, just a new place to put it (scr) and a new reason to consult it (flush).

Now you're ready: "SC-ART" and "SC-BTree" (SC = software-coherent) are just ART-OLC/B-tree-OLC with their version numbers relocated to scr.
3LSM basics: memtable, SSTable, compaction▾

An LSM buffers writes in a small in-memory memtable. When full, it's frozen and serialized as an immutable, sorted SSTable at level L0. Levels grow ~10× per step; a background compaction merge-sorts SSTables from one level into the next, discarding the old ones. L0 files can overlap in key range (each came from an independent memtable flush); L1+ files within a level don't.

Now you're ready: the memtable is the only place an LSM writes in place — everything below it is created once and only ever deleted, never edited.
4Updatable surface area — the paper's central concept▾

Defined as the portion of a data structure that can receive in-place modification. In ART/B-trees, that's the *whole tree* — any node from root to leaf can change, so every node needs a version number. Shrinking this surface is the entire design problem: small nodes track coherence precisely but need too many version numbers; large nodes need few version numbers but invalidate too coarsely.

Now you're ready: LSMs win not because they're clever about coherence, but because their native updatable surface (just the memtable) is already tiny — the paper exploits a property LSMs already had for an unrelated reason (avoiding random disk writes).
5False invalidation▾

If one version number covers many keys (a large B-tree node), updating any key in that node bumps the shared version — forcing every host that cached any key from that node to flush and re-read the whole thing, even keys nobody touched. It's the coarse-granularity tax you pay to make version numbers fit scr.

Now you're ready: this is the mechanism behind SC-BTree's collapse under writes in §3.3 — the exact opposite failure mode from SC-ART's scr overflow.
6Write amplification, quickly▾

How many bytes get physically rewritten per logical byte written. Copy-on-write B-trees pay Θ(leaf size) per update (copy the whole leaf, plus every ancestor to the root). Leveled LSMs pay roughly Θ(size-ratio · log(data/SSTable-size)) — batching many logical updates into one physical rewrite. RocksDB measures ~4× lower write amplification than the CoW-style WiredTiger B-tree.

Now you're ready: this is why the paper dismisses copy-on-write B-trees as a rival small-updatable-surface design — they'd solve the coherence problem but at prohibitive memory-bandwidth cost.
The whole story in one place

Prism in a nutshell

Why in-memory indexes fail this model, why an ancient disk trick fixes it, and what Prism adds on top.

Porting ART or a B-tree to partly coherent CXL with software coherence forces a version number onto every tree node, since any node can be modified in place. With 100M keys, ART grows to ~40M nodes and less than half their version numbers fit in a realistic 128MB scr — the rest spill to lnr, requiring a flush on every access regardless of whether data changed. Widening B-tree nodes shrinks the node count so version numbers fit, but now one key's update falsely invalidates every other key sharing that node — at fan-out 128, write-heavy throughput collapses to 1.8M ops/s, versus 12M ops/s for the scr-fitting configuration.

The paper's insight: this is one dilemma — a large updatable surface area — and LSM trees, designed decades ago for spinning disks, already solve it for an unrelated reason. An LSM confines all in-place writes to a small memtable (fits entirely in scr, no coherence tracking needed) and makes everything else — SSTables — immutable, tracked with one coarse ID per multi-MB file rather than one version per key. Porting this (SC-LSM) already beats both ART and B-tree variants.

But disk-era LSMs have a canonical flaw: under heavy writes, compaction can't drain L0 fast enough, so reads must probe more and more overlapping SSTables (15 at 5% writes → 49 at 50%). Disk-based LSMs can't fix this with in-place updates — that requires random writes, which kill the sequential-I/O benefit LSMs exist for. In memory, random writes aren't expensive, so Prism adds a Bounded Updatable Layer (BUL) — a size-capped, in-place-updatable ART in lnr, with fine-grained per-node version numbers, deliberately bounded so those version numbers still fit scr.

The payoff: Prism reaches up to 9.4× higher throughput than SC-BTree on write-heavy workloads and up to 15.1× over existing CXL systems, while matching an unlimited-scr SC-ART on write-heavy workloads using only 128MB.

🍯 Key takeaways

  • The real bottleneck isn't coherence itself — it's the updatable surface area of the index.
  • LSMs fit partly coherent CXL by accident: their disk-era design already keeps mutation tiny.
  • SC-LSM decisively beats SC-ART and, on write-heavy workloads, beats SC-BTree by up to 2.2× — though the two run close on read-heavy/read-only loads. SC-LSM still inherits LSMs' own weakness: compaction can't keep up with writes.
  • BUL makes the LSM's upper layer in-place updatable — feasible in memory, impossible on disk.
  • The memtable is inverted into a cache for hot keys — one-hit wonders skip scr entirely.
  • Result: up to 9.4× over SC-BTree, 15.1× over prior CXL systems, ~0.2%–1% scr footprint discipline.
Six everyday pictures

How to think about Prism

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Updatable surface area

A whiteboard vs. sealed boxes

One small whiteboard you erase and rewrite constantly — cheap, and only one person needs to glance at it to know if it changed. Next to it, sealed shipping boxes: nobody opens one to edit a label, they just get replaced wholesale. LSMs are the boxes-and-whiteboard warehouse; ART/B-trees are a warehouse where every box has a hinged lid anyone might open, so you need a sensor on each one.

Where it breaks: the whiteboard (memtable) isn't infinite — Prism still needs a second, bigger "scratch area" (BUL) with lighter-weight sensors, since one whiteboard can't hold all the hot data.
SC-ART's failure · Version overflow

A sticky note per book

A librarian tries to track every book's "last touched by" status with a sticky note on a corkboard. With a small library, all notes fit on the board — free, instant lookups. Grow the library 10× and the notes themselves overflow off the board; now checking "is my copy of this note current?" requires walking to a second corkboard across the building — for every single lookup, even unchanged ones.

Where it breaks: the real problem isn't the sticky notes overflowing per se — it's that reading an overflowed note itself requires a flush, so the overflow tax applies uniformly, not just to actually-stale entries.
SC-BTree's failure · False invalidation

One fire alarm for the whole floor

Widen the B-tree's nodes and version numbers now fit scr — great. But one alarm now covers the entire floor: change one desk's papers and the whole floor evacuates and re-checks everything, including desks nobody touched. At fan-out 128 under writes, SC-BTree drops to 1.8M ops/s — worse than SC-ART, which at least tracks precisely (when it fits).

Where it breaks: the alarm analogy suggests random false positives; false invalidation is deterministic — every write in a node triggers it, so it scales directly with write rate, not with bad luck.
Why an "old" idea works · Shape over medium

An umbrella that also stops sand

LSMs were built to dodge one constraint: disks hate random writes. Nobody designed them to solve coherence — that constraint didn't exist yet. But "confine writes to a small region, make the rest immutable" turns out to be exactly the *shape* partly coherent CXL needs too. Same umbrella, different storm.

Where it breaks: the shapes only rhyme, they don't match perfectly — disk-era LSMs still stall writes when compaction lags, which the paper shows is unacceptable in-memory, motivating BUL as a genuinely new addition, not just a port.
The memtable inversion · One-hit-wonder filtering

A club bouncer, not a waiting room

Old design: everyone who shows up waits in the lobby (memtable) before being let downstairs (BUL). New design: the lobby is a VIP room — you only get in once you've been recognized as a regular (written twice). First-timers go straight downstairs. This means the precious lobby never fills with people who were never coming back, freeing it for keys that actually benefit from hardware coherence.

Where it breaks: a bouncer's judgment is subjective; Prism's promotion rule is mechanical — literally "has BUL seen a second write for this key" — with no notion of importance beyond write frequency.
Compaction / recycling · SSTable IDs

A new edition, a new barcode

When a library replaces a worn-out book with a new printing, it doesn't reuse the old barcode — it stamps a new one, so any scanner instantly knows "I haven't seen this edition, better re-check the shelf" rather than trusting a stale memory of the old copy. SSTable IDs are strictly increasing for exactly this reason: recycled memory gets a fresh ID, forcing a flush on first encounter.

Where it breaks: a real barcode swap is instantaneous; Prism's manifest update must be ordered so the new ID is published in scr only after the new SSTable's bytes are actually flushed to lnr — otherwise a host could see the ID before the data is safely there.
The full explanation

How it actually works

From the failure of in-memory indexes, through SC-LSM, to Prism's two additions.

1 · Why ported in-memory indexes fail

Porting ART/B-tree via software coherence means assigning a version number (in scr) to every node, since any node can be updated. Two knobs, one dilemma:

Node sizeVersion numbersResult
Small (ART Node4)Many — don't fit scr at scale (40M nodes / 100M keys, <50% coverage)Flush on every spilled version-number access
Large (B-tree fan-out 128)Few — fit scr easilyFalse invalidation: 1.8M ops/s under writes vs 12M scr-fitting
⚠
Both failure modes stem from one root cause: updatable surface area spans the entire tree in both designs. There's no node-size knob that escapes the trade-off.

2 · SC-LSM — confining mutation to the memtable

An LSM's memtable absorbs writes in place; once full it's frozen as an immutable SSTable. Since the memtable is small (a few MB), it fits entirely in scr — no version numbers needed. SSTables, holding the bulk of the data, live in lnr and are tracked by one strictly-increasing ID per file (not per key) in the scr manifest: unseen ID → flush the whole region once; seen it before → trust the cache. Because SSTables are large (MBs), there are few of them, so this metadata is tiny regardless of dataset size.

💡
This is the whole trick: coherence granularity scales with file count, not key count. SC-LSM already beats SC-ART and SC-BTree on this basis alone (Fig. 3).

3 · SC-LSM's inherited flaw — compaction can't keep up

L0 SSTables can overlap in key range (each comes from an independent memtable flush), so a read may have to probe every one of them. Under write pressure, the memtable fills and flushes faster than background compaction can drain L0 into L1.

4 · BUL — a bounded, in-place-updatable upper layer

Instead of flushing the memtable straight to a new L0 SSTable, it flushes into BUL, a bounded ART living in lnr. Repeated writes to the same key update BUL's entry in place — no new SSTable. BUL is explicitly size-capped so its per-node 64-bit version words (obsolete flag · lock bit · access bit · 42-bit version counter · node ID · node type) all fit within the scr budget left over after the manifest and memtable. When BUL fills, a clock-sweep policy flushes cold entries — one to two SSTables at a time — to L0, while hot entries stay resident.

# BUL version word packing (64 bits total, kept in scr)
bit 0      obsolete flag        // node logically deleted, awaiting reclamation
bit 1      lock bit             // serializes concurrent writers
bit 2      access bit           // clock sweep reads this for hotness
bits 3-44  version counter      // bumped on every lock/unlock; readers detect via this
bits 45-61 node ID               // strictly increasing, detects recycled nodes
bits 62-63 node type

5 · The scr-aware memtable inversion

Rather than a write buffer that every key passes through, the memtable becomes a cache for hot keys. Writes check the memtable first; a hit updates in place. A miss goes straight to BUL. A key only enters the memtable via promotion — the second time BUL sees a write to it. One-hit wonders never touch scr, and evictions from a full memtable happen incrementally (LRU, in small batches) rather than as one expensive bulk flush.

6 · Coherence protocol summary

TierWhere data livesCoherence mechanism
MemtablescrHardware — no software coherence needed
BULlnr, per-node version # in scrCheck version; unseen node ID → flush; changed version → flush + restart traversal
SSTableslnr, ID + manifest in scrOne ID per file; unseen ID → flush entire region once
🔁
Transitions are ordered, not atomic: a key becomes readable under its new tier's mechanism before it's removed from the old one (e.g., BUL→memtable promotion inserts into the memtable, then deletes from BUL). A brief window of visibility in both places is safe because the read path checks tiers newest-first.
Follow the numbers

Worked examples

Four calculations straight from the paper's reported figures.

① How many nodes can BUL's scr budget actually track?

Prism gives BUL 62MB of scr for version numbers, each a 64-bit (8-byte) word.

  1. 62MB in bytes: 62 × 1024 × 1024 = 65,011,712 bytes.
  2. Divide by 8 bytes/entry: 65,011,712 / 8 = 8,126,464 nodes — about 8.1M.
  3. Compare to the whole index: a 100M-key ART has ~40M nodes total. BUL's budget covers ~20% of that — by design, it only needs to hold the currently-hot, actively-rewritten fraction, not everything.
🍯
Insight: "bounded" isn't a vague safety margin — it's a hard arithmetic constraint: BUL's node capacity is fixed the moment scr is sized, independent of total dataset size.

② Why SC-ART's scr coverage collapses as the dataset grows

The paper reports 10M keys → ~4M nodes fitting "comfortably," but 100M keys → ~40M nodes with <50% coverage in the same 128MB scr.

  1. 10× more keys ⇒ roughly 10× more nodes (4M → 40M), since YCSB's sparse key distribution keeps most nodes at the smallest ART type.
  2. scr capacity is fixed at 128MB regardless of dataset size — call it C nodes' worth of version numbers.
  3. Coverage = C / node count. At 10M keys, C/4M ≈ 100% ("comfortably fits"). At 100M keys, C/40M < 50% ⇒ C < 20M.
  4. So version-number size is roughly bounded between 128MB/40M ≈ 3.2 bytes and 128MB/20M ≈ 6.4 bytes per node — consistent with a small fixed-width counter.
💡
Coverage falls roughly in proportion to dataset size for ART, because node count scales with dataset size but scr doesn't. That's structurally different from SSTable IDs, whose count barely grows with dataset size.

③ The false-invalidation collapse, by the numbers

§3.3 reports SC-BTree (fan-out 128) at 1.8M ops/s under write-heavy YCSB-A, versus 12M ops/s for a scr-fitting SC-ART configuration.

  1. Compute the gap: 12 / 1.8 ≈ 6.7× — purely from coherence granularity, with no change to the underlying data or access pattern.
  2. Why: at fan-out 128, one key update bumps the version for all ~128 keys in that node, forcing every host that cached any of them to flush and re-fetch — even though only one key actually changed.
  3. The lesson: widening nodes solves the scr-fit problem but reintroduces a cost that's directly proportional to write rate — exactly the regime BUL is designed to avoid, since it tracks coherence per-node at a size small enough that few keys share a version.

④ BUL's effect on read latency, end to end

Ablation (§7.7, Fig. 11): SC-LSM alone probes 15 SSTables at 5% writes, 49 at 50% writes. Adding BUL drops 5%-write probes to 2.

  1. Reduction at 5% writes: 15 → 2 SSTables, a 7.5× cut, because repeated writes to the same keys now update BUL in place instead of minting new SSTables.
  2. Growth rate flattens too: without BUL, probes grow ~3.3× (15→49) from 5% to 50% writes; with BUL, growth is far shallower since fewer, more consolidated flushes reach L0.
  3. Prism's memtable inversion works alongside BUL by keeping one-hit wonders out of the memtable/scr cache — they still land in BUL on their first write like any other key, and later get evicted straight to L0 once cold, so scr stays reserved for keys that are genuinely rewritten often.
🍯
Fewer SSTables probed is a direct, mechanical consequence of absorbing repeat writes in place — the same logic that makes any cache effective, just applied to the boundary between mutable and immutable data.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Disk-based LSMs use Bloom filters to avoid disk I/O on negative lookups. Does Prism use them?
Show answer
No. Bloom filters exist to avoid an expensive disk seek; in CXL memory, probing an SSTable's internal ART index is already just a memory access, comparable in cost to checking a Bloom filter. Adding one would cost memory for no latency win.Misconception: that LSM design choices are universal. Several exist specifically to hide disk latency and don't carry over once the medium is memory.
Problem 2 · medium
If Prism instead gave BUL only 8MB of scr for version numbers (same 8-byte word), how many nodes could BUL track?
Show answer
8MB = 8,388,608 bytes ÷ 8 bytes/entry = 1,048,576 nodes (~1M) — an 8× smaller budget than the paper's 62MB, tracking roughly 8× fewer nodes. BUL would fill (and flush to L0) much sooner, increasing compaction pressure and pushing Prism's behavior back toward plain SC-LSM.Misconception: that BUL's size doesn't matter much. Its capacity is a hard linear function of scr allotted — shrink the budget, shrink exactly how much write-absorption you get.
Problem 3 · medium
Widening B-tree fan-out fixes the scr-overflow problem. Why isn't that simply "solved"?
Show answer
It trades one failure mode for another: fewer, bigger nodes mean fewer version numbers (fits scr), but each version number now covers many keys, so any single-key write falsely invalidates all of them for every host with a cached copy — collapsing write-heavy throughput to 1.8M ops/s (§3.3).Misconception: that "fits in scr" is the finish line. Fitting in scr is necessary but not sufficient — granularity still determines flush frequency under writes.
Problem 4 · hard
Traditional LSMs handle compaction backlog by stalling writes. Why doesn't Prism just do that, and why does BUL's alternative (in-place updates) work in memory but not on disk?
Show answer
Stalling writes trades write throughput for read latency — an acceptable trade on disk where I/O is already the bottleneck, but wasteful in memory where the system could otherwise sustain much higher write rates. In-place updates would fix backlog directly by reducing the number of SSTables created in the first place, but on disk that requires random writes, which squander the sequential-I/O benefit LSMs exist for. In memory, random writes cost little more than sequential ones, so BUL can update in place with no such penalty — an option disk-based LSM designers never had.Misconception: that BUL is just "an LSM optimization." It's specifically an in-memory-only move, infeasible in the disk setting the LSM was designed for.
Problem 5 · medium
Why must a key be written to BUL twice before it's promoted into the memtable, rather than entering on the first write?
Show answer
The memtable's scr space is scarce (64MB) and its only advantage is zero-overhead hardware coherence for keys that get rewritten often. A key written exactly once (a "one-hit wonder") gains nothing from that advantage — it will just get flushed out again. Requiring a second write before promotion filters these out mechanically, so scr space is reserved for keys that have demonstrated repeat-write behavior.Misconception: that caching should happen on first access, as with typical read caches. Here the goal is filtering by write-repetition specifically, not by recency of any access.
Problem 6 · hard
During BUL→SSTable eviction, why must the new SSTable be written and the manifest updated in scr before the flush thread removes entries from BUL — rather than removing first (since the data has logically "moved")?
Show answer
If entries were removed from BUL first, there would be a window where the key exists in neither BUL nor any published SSTable — a concurrent reader would report "not found" even though the value is safely written, just not yet visible under its new coherence mechanism. Writing and publishing first, then deleting, guarantees a key is always readable under some valid mechanism; a brief window of visibility in both places is harmless since both copies hold the same value and the read path checks tiers in a fixed order.Misconception: that a value "moving" between tiers is instantaneous. Every tier transition in Prism is an ordered two-step operation precisely to avoid a gap where the key is unreadable anywhere.
Quick answers

Frequently asked questions

Nine questions readers ask most.

Q1What exactly is scr vs. lnr, in one line?▾
scr (~128MB) is the slice of CXL memory hardware keeps coherent across hosts, like ordinary shared DRAM. lnr is everything else (terabytes) — CPU caches for it aren't automatically synchronized, so software must track staleness itself.
Q2Why does an index built for disks fit this model better than one built for memory?▾
Because the fit is about shape, not speed. LSMs confine all in-place mutation to a small memtable, purely to avoid random disk writes. That same small mutable region happens to be exactly what's needed to keep coherence metadata inside scr. ART/B-trees have no such confinement — any node anywhere can change — so every node needs tracking.
Q3Is "updatable surface area" a new formal metric, or informal framing?▾
The paper defines it precisely as "the portion of the data structure that can receive in-place modification," and uses it as the paper's unifying diagnostic — both SC-ART's overflow and SC-BTree's false invalidation are explained as two symptoms of the same large-surface-area problem.
Q4Is BUL just SC-ART with a size cap?▾
Mechanically, yes — same ART-OLC-style structure and version-word format. The difference is entirely in how it's used: bounded so its version numbers always fit scr, receiving every write that misses the memtable (with a repeat write to the same key promoting it up into the memtable), and periodically drained by a clock sweep to SSTables rather than growing unboundedly like SC-ART's full tree.
Q5Why not just make B-tree nodes even bigger to fix false invalidation for good?▾
Bigger nodes make false invalidation worse, not better — more keys share one version number, so more unrelated keys get invalidated per write. There's no node size that solves both problems simultaneously; that's precisely the dilemma the paper identifies.
Q6Does Prism need lnr to support atomic operations, unlike SC-ART?▾
No. SC-ART's version numbers spill into lnr at scale, requiring the paper to assume hardware atomics there for safe concurrent increments. Prism's design keeps all version numbers in scr by construction (bounding BUL), so it never needs that assumption.
Q7Does Prism always beat SC-BTree on range scans?▾
No — at very low write ratios (~5%), SC-BTree's contiguous sorted nodes make scans cheaper than merging across Prism's three tiers. Prism overtakes it starting around 10% writes, reaching 6.0× at 50% writes, since SC-BTree's false invalidation dominates at that point.
Q8How is this different from Tigon/Megalon, which also put coherence metadata in scr?▾
Both store per-object metadata proportional to the number of shared objects, so scr usage grows with dataset size — Tigon must migrate tuples in and out of CXL when it overflows, Megalon must reclaim metadata. Prism bounds scr usage independent of dataset size (fixed manifest + memtable + bounded BUL), which is why it outperforms both under write-heavy loads by 5.5× and 15.1× respectively.
Q9How does this relate to memory-tiering systems like TPP, HeMem, or Pond?▾
(Framing, not a paper claim.) Those systems solve a different problem — migrating hot/cold pages between DRAM and slower tiers within one coherence domain. Prism instead assumes CXL memory is already multi-host-shared and asks how to index it given a hardware coherence boundary, not a speed boundary. The two are complementary: a tiering system could place Prism's SSTables on a colder tier while BUL/memtable stay on the fastest one.
