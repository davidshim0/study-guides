Skip the mailman — let producers and consumers meet inside CXL memory

Every message broker you've used relays bytes through a process, over a socket. Shadix deletes that step: producers and consumers exchange messages with plain loads and stores into shared, disaggregated CXL memory. No broker process. Single-digit µs round trips.

📄 "Shadix" · Hackenberg, Hagen, Weisgut, Schmeller, Rabl · DIMES '26 🎓 CXL/tiering basics assumed — primers focus on the broker-specific mechanics ⏱ ~25 min read
📬

Meet directly in shared CXL memory via plain load/store — not by relaying bytes through a broker process over RDMA or TCP.
Manage coherence yourself in software; the hardware doesn't do it for you below CXL 3.0.

Before you begin

Quick glossary, then ten ideas the paper leans on

You know CXL's host/device model and coherence basics already — these primers skip that and focus on what's specific to building a message broker on top of it. Acronyms first, then primers; open any that look unfamiliar.

Quick glossary

CXLCompute Express Link — the PCIe-based interconnect Shadix rides on for cache-coherent load/store access to memory outside a host's own DIMMs.
RDMARemote Direct Memory Access — lets a NIC read/write another host's memory without its CPU. It bypasses the kernel's socket/TCP stack, but still goes through NIC hardware and InfiniBand verbs (queue pairs, completion queues). What Valkey uses here, over InfiniBand — unlike NATS/Pulsar, which use plain TCP/IP sockets.
SPSCSingle-Producer Single-Consumer queue — the simplest lock-free ring buffer: one writer, one reader.
MPMCMulti-Producer Multi-Consumer queue — what a broker really is. Shadix builds one out of many SPSC queues.

1Why CXL < 3.0 forces "manual" coherence▾

You already know CXL distinguishes a coherence-managing host from a device. What's specific here: without CXL 3.0's cross-host coherence hardware, each host that touches the shared CXL memory keeps its own coherence domain. One host's write doesn't automatically invalidate the other host's cached copy of that line.

The device Shadix runs on is a real hardware prototype — a Seagate Composable Memory Appliance Blade, FPGA-based, speaking CXL 1.1 — not a hypothetical constraint. It's a research appliance rather than a shipping product, but it's the actual hardware this paper's numbers were measured on.

Now you're ready: Shadix's whole queue design — explicit flushes, ordered writes, atomic 64B stores — exists to substitute in software for the coherence hardware CXL 3.0 would eventually provide.
2Publish/subscribe roles▾

Producers send messages, consumers receive them, and a broker sits between them and does the actual exchanging. In conventional brokers the broker is a separate running process — Kafka, Valkey, NATS, Pulsar all work this way.

Now you're ready: Shadix's core move is eliminating the broker-as-process. The "broker" becomes a data structure living in shared memory that producers and consumers both touch directly.
3SPSC vs. MPMC, and composing one from many▾

An SPSC queue is the easy case: exactly one writer, one reader, so it needs no arbitration between multiple producers or multiple consumers. An MPMC queue — what an actual broker needs — has many of both, which is harder to make lock-free.

A well-known trick: build an MPMC queue out of a grid of SPSC queues, one per (producer, consumer) pair, and let each side pick which SPSC queue to use.

Now you're ready: Shadix uses exactly this trick — P producers × C consumers = P×C independent SPSC ring buffers in CXL memory, each simple enough to reason about.
4The ring buffer + index-guard pattern▾

A ring buffer reuses memory slots, so a reader needs to know "is this slot's content new, or stale from an earlier lap?" The fix: tag every message with a monotonically increasing index (sequence number), store it alongside the message, and let the reader compare the stored index to the index it expects.

If they match, the message is ready. If not, the reader isn't there yet — it backs off and retries.

Now you're ready: this index doubles as both a "new data" flag and an ordering guarantee — no separate lock or flag bit needed.
5Writing across multiple cache lines safely▾

Small messages fit in one 64-byte cache line (index + payload together). Larger ones spill into several lines. If a reader could see the index before the rest of the message finishes writing, it would read a torn, half-written message.

The fix is ordering: write every line except the index-bearing one first, wait for those writes to complete (a fence), then write the index-bearing line last — the one atomic write that "unlocks" the whole message for the reader.

Now you're ready: "index line written last" is the whole correctness argument for multi-cache-line messages — watch for it in the worked examples.
6RFO and why movdir64b matters▾

A normal cached CPU write to a line it doesn't already own triggers a Read-For-Ownership (RFO): the CPU first fetches the current contents, then modifies them. Over CXL, that's an extra round trip on an already-precious link.

movdir64b is an x86 instruction that writes a full 64-byte line atomically without that read step — it just overwrites, no RFO.

Now you're ready: every producer write in Shadix uses movdir64b specifically to keep CXL traffic to one direction per write, not two.
7Backoff and cooperative scheduling▾

When a producer's chosen queue is full, or a consumer's chosen queue is empty, spinning and immediately retrying would hammer the CXL link — and CXL throughput/latency both degrade under concurrent contention.

Instead, Shadix uses exponential backoff (capped at 512 ns) and, during the wait, suspends the current task and hands control to an in-application scheduler that does other useful work rather than burning CPU cycles waiting.

Now you're ready: this backoff is the single biggest source of latency variance in the results — you'll compute its contribution directly in Worked Example ②.
8RDMA vs. CXL: two different "remote memory" paths▾

RDMA (what Valkey uses here, over InfiniBand) skips the kernel's socket/TCP network stack — but it still goes through a NIC: RDMA verbs involve queue pairs, completion queues, and a PCIe hop to that NIC. CXL load/store bypasses the NIC entirely — the CPU issues an ordinary memory instruction, and CXL routes it to the device.

Now you're ready: this is the structural reason CXL RTTs land in single-digit µs while RDMA-based Valkey lands in tens of µs, even before any application-level overhead.
9Synchronous vs. asynchronous sending▾

In synchronous mode, a client thread sends one message and waits for the broker's acknowledgment before sending the next — throughput is capped at one RTT per message per thread. In asynchronous mode, the client library can coalesce several messages before they hit the network, trading added latency for much higher throughput.

Shadix only has a synchronous mode: a message is committed — meaning visible in CXL memory — before the next one is sent, so there's nothing to batch. (This is an in-memory visibility guarantee, not durability: the evaluation is entirely in-memory, and Shadix makes no claim about surviving a crash.)

Now you're ready: the throughput graphs' sync/async split for Valkey/NATS/Pulsar is really "with vs. without" this batching trick — Shadix competes against both columns using only its one mode.
10Why RTT, and what the CDF plots show▾

One-way latency needs synchronized clocks on both hosts, which is its own hard problem. The paper sidesteps it: a sender and receiver run on the same host (so they share a clock), and a message bounces sender → remote server → receiver. The receiver just subtracts two local timestamps.

The latency figure plots a CDF (cumulative distribution function): x-axis is RTT, y-axis is the fraction of messages at or below that RTT — so the curve's height at "100 µs" tells you what fraction finished within 100 µs.

Now you're ready: "median RTT" = where the CDF crosses 0.5; "p99" = where it crosses 0.99 — the numbers used throughout the worked examples.
The whole story in one place

Shadix in a nutshell

The problem with broker-as-process, the CXL-native fix, and why it works despite lacking hardware coherence.

Every widely-used message broker — Valkey, NATS, Apache Pulsar — is architecturally the same shape: a producer sends bytes to a separate broker process — over RDMA/InfiniBand for Valkey, over a TCP socket for NATS/Pulsar — and the broker relays them the same way to a consumer. Even RDMA, which skips the kernel's socket/TCP stack, still crosses a NIC and its own verbs protocol, and still involves a distinct broker process doing the relaying. That shape imposes a latency floor of tens to hundreds of µs, no matter how fast the interconnect gets.

Shadix removes the broker process entirely. Producers and consumers on two separate hosts share a region of disaggregated CXL memory and exchange messages by writing and reading it directly with ordinary load/store instructions — the same instructions a CPU uses to touch its own DRAM. The "broker" is just a grid of SPSC ring buffers in that memory, one per producer–consumer pair, arbitrated by uniform-random queue selection with retry-on-failure.

The catch: the CXL hardware available today (CXL 1.1, in this paper's testbed) does not provide hardware cache coherence across the two hosts. Shadix manages it manually — index-guarded slots so a stale read is detectable, an ordered two-step write so a reader never sees a torn multi-cache-line message, atomic movdir64b writes to avoid extra coherence traffic, and explicit cache-line flushes before every read.

The payoff: Shadix reaches single-digit-µs round-trip latency — as low as 1.8 µs, matching the CXL device's own theoretical floor — and saturates the CXL link's bandwidth at large message sizes (13.60 GB/s of a ~14 GB/s bound at 8 KiB messages). It outperforms all three baselines' synchronous mode by roughly one to two orders of magnitude in latency (23–57× lower), and even against their fastest asynchronous (batched) throughput modes it still comes out ahead — though by a much narrower ~2.8–3× at small messages, since Shadix has no batching of its own to lean on.

🍯 Key takeaways

  • Conventional brokers relay every message through a process over a socket; Shadix replaces the broker with a data structure in shared CXL memory.
  • An MPMC broker = a grid of P×C SPSC ring buffers, one per producer–consumer pair, selected uniformly at random.
  • Below CXL 3.0 there's no hardware cross-host coherence — Shadix manages it manually: index guards, ordered multi-line writes, movdir64b, explicit flushes.
  • Backoff (capped at 512 ns) plus cooperative scheduling avoids hammering the CXL link under contention — at the cost of added, explainable latency variance.
  • Shadix reaches 1.8 µs best-case RTT and saturates CXL bandwidth (13.60 GB/s of ~14 GB/s) at 8 KiB messages.
  • It beats Valkey/NATS/Pulsar synchronous mode by roughly 20–60× in latency, and still wins on throughput against their asynchronous (batched) modes — though by a much narrower ~2.8–3× at small messages — with the hardware setups differing, so treat this as suggestive, not a controlled comparison.
Six everyday pictures

How to think about Shadix

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · No broker process

Skip the post office

Sending a letter across town normally means dropping it at a post office, which sorts and relays it to another office, which delivers it. Shadix is two people who happen to share a mailbox in the hallway between their apartments — drop it in, the other picks it up, no sorting office involved. The mailbox is CXL memory; the sorting office is what Valkey/NATS/Pulsar still are.

Where it breaks: a real shared mailbox needs no coordination protocol. The hallway mailbox here still needs an index guard and ordered writes to avoid two people fumbling the same slot at once — that machinery is the whole engineering contribution.
Detecting stale data · Index guard

A claim ticket, not a padlock

A dry cleaner doesn't lock your clothes away — they pin a numbered ticket to them. You know your items are ready when the ticket number on the rack matches the one on your stub. Shadix's ring buffer slots work the same way: a slot holds a message plus its index, and a reader only trusts the slot once the stored index matches the one it expects. No lock, just a number to check.

Where it breaks: a paper ticket doesn't need a memory fence. Here, the index and the message live in different cache lines that can be written out of order — which is exactly why the index line must be written last, deliberately, not just "eventually."
Multi-line messages · Write ordering

Seal the envelope last

You write the letter, fold it in, then seal the envelope — never the reverse. If the seal (the visible "this is ready" signal) went on before the letter was finished, a reader could open it too early and see a half-written mess. Shadix writes every non-index cache line of a message first, waits for those writes to finish, then writes the index-bearing line — the "seal" — last.

Where it breaks: an envelope's contents don't change after sealing. Here the danger is a genuinely concurrent reader that could poll the index line mid-write — the ordering exists specifically to defeat that race, not just tidiness.
Arbitration · Uniform random pick

Randomized bank-teller lines

Instead of checking which of several teller lines is shortest, you just pick one uniformly at random — and if it's closed, you pick again. It's not the smartest possible policy, but it's simple, needs no shared "which line is shortest" signal, and spreads load reasonably well. That's exactly how Shadix's producers and consumers pick which SPSC queue to use.

Where it breaks: a real customer can see the lines and pick the shortest. Shadix's random pick has no visibility into other queues' state at all — the paper is explicit that this policy is a simplicity choice, swappable for something smarter.
Contention control · Backoff + scheduler

Step out of line instead of pushing

If the ATM line isn't moving, pushing harder doesn't help — everyone just gets in each other's way. The better move is to step aside for a bit, do something else, then check back. Shadix's exponential backoff (capped at 512 ns) plus handing control to a scheduler is exactly this: don't hammer a full or empty queue, do other work, and retry after a growing delay.

Where it breaks: a person who steps out of line is gone for a while. Shadix's "step out" is a few hundred nanoseconds of scheduled other work — brief, but the paper shows it's still the dominant source of latency variance in the results, not free.
Write mechanics · Avoiding RFO

A rubber stamp, not "read it back first"

Overwriting a form the normal way means reading its current contents first, then writing your update — two trips. A rubber stamp just overwrites in one motion, no reading required. movdir64b is the rubber stamp: an atomic 64-byte write that skips the Read-For-Ownership step a normal cached write would trigger, halving the CXL traffic per write.

Where it breaks: a rubber stamp can't do partial updates — and neither can movdir64b, which is exactly why it only applies to whole-cache-line writes, and why multi-line messages need the ordered two-step write from the analogy above.
The full explanation

How Shadix actually works

Section by section, with the paper's key figures rebuilt as diagrams you can read at a glance.

1 · The problem shape — every broker relays through a process

Valkey, NATS, and Apache Pulsar are all, structurally, the same: a producer talks to a broker process — over RDMA/InfiniBand for Valkey, over a TCP socket for NATS/Pulsar — and the broker relays the message to a consumer the same way. Even RDMA, which lets a NIC touch remote memory without the remote CPU's involvement and skips the kernel's socket/TCP stack, still routes through a NIC and InfiniBand's own verbs protocol. Measured synchronous RTTs bear this out: Valkey 76–182 µs, NATS 131–306 µs, Pulsar 200–349 µs (min–p99, across message sizes).

2 · MPMC as a grid of SPSC queues, with random arbitration

Shadix instantiates one SPSC ring buffer per (producer, consumer) pair. To send, a producer picks a consumer uniformly at random and tries to enqueue; if that queue is full, it tries a different random consumer. To receive, a consumer does the symmetric thing over producers.

  1. Pick a queue at random from the P×C grid, on whichever side (producer or consumer) is acting.
  2. Try the operation. Enqueue (producer) or dequeue (consumer) against that one SPSC queue only.
  3. On failure (queue full for a producer, empty for a consumer), apply exponential backoff, suspend the task, let the internal scheduler do other work.
  4. Retry with a newly-random queue once the backoff elapses.
🌱
Because each SPSC queue only ever has one writer and one reader, none of the hard multi-writer/multi-reader races exist within a queue — all the interesting correctness work is inside a single SPSC queue's ring buffer, covered next.

3 · Multi-cache-line items and flow control

// producer, enqueueing a message that spans k cache lines
if (last_index_written - last_index_read >= ring_buffer_size):
    return FULL                      // consumer is lagging; try another queue
slot = (last_index_written + 1) % ring_buffer_size
if k > 1:
    write_non_index_lines(slot, message)   // movdir64b, unordered among themselves
    fence()                                // wait for those writes to be visible
write_index_line(slot, index, first_part)  // movdir64b — this line "unlocks" the item
last_index_written += 1

// consumer, dequeuing
slot = (last_index_read + 1) % ring_buffer_size
flush_cache_line(slot.index_line)          // force a fresh read from CXL memory
if stored_index != last_index_read + 1:
    return EMPTY                     // not written yet; back off, try another queue
if k > 1: flush_remaining_lines(slot)
last_index_read += 1
store_to_cxl(last_index_read)              // tells the producer it can reclaim this slot
💡
Why compare with subtraction, not equality? The 32-bit index wraps around eventually. Using last_written − last_read < ring_buffer_size with unsigned arithmetic stays correct across that wraparound, without needing a special case.

4 · Coherence, without hardware help

Every piece above exists because CXL 1.1/2.0 gives each host its own coherence domain. Three concrete mechanisms fill the gap: the producer writes with movdir64b (atomic 64 B, no RFO, so the CXL link only sees the write traffic it needs); the index-bearing line is written last with a fence in front of it (so a reader can never observe a torn multi-line item); and the consumer explicitly flushes the relevant cache line before every read (so it never trusts a stale local copy). None of this needs OS or driver support — it's all inline in the producer/consumer code.

Follow the numbers, step by step

Worked examples

Four calculations, carried through with the paper's own measured numbers.

① Is Shadix actually saturating the CXL link?

At 8 KiB messages, Shadix sustains 1.66 M msgs/s. At 2 KiB, 5.49 M msgs/s. The background-load bandwidth bound is 14 GB/s. Is Shadix bandwidth-bound at these sizes?

  1. 8 KiB data rate: 1.66×10⁶ msgs/s × 8192 B = 13,598,720,000 B/s ≈ 13.60 GB/s.
  2. As a fraction of the bound: 13.60 / 14 ≈ 97% — essentially saturated.
  3. 2 KiB data rate: 5.49×10⁶ msgs/s × 2048 B = 11,243,520,000 B/s ≈ 11.24 GB/s → 11.24 / 14 ≈ 80%.
  4. Both figures match the paper's own reported data rates exactly (13.60 GB/s and 11.24 GB/s), confirming: past ~2 KiB, Shadix's message rate decline isn't a software inefficiency — it's the CXL device's raw bandwidth running out.
🍯
Insight: below ~1 KiB, Shadix is limited by per-message overhead (backoff, index checks); above ~2 KiB, it's limited by the hardware's bytes/second — a clean, explainable crossover.

② The RTT floor vs. the measured median at 8 B

Theoretical minimum RTT is ~1.8 µs. Measured median at 8 B is 3.21 µs. Where does the extra 1.41 µs come from?

  1. Theoretical floor: one-way delay ≈ write (~400 ns) + read (~500 ns) ≈ 900 ns; RTT crosses two such hops (Send→Server, Server→Receive) → 2 × 900 ns = 1.8 µs.
  2. Measured median: 3.21 µs. Gap = 3.21 − 1.8 = 1.41 µs.
  3. Why: at this message rate the consumer is always waiting at maximum backoff (512 ns cap). The message becomes visible in CXL memory at some uniformly random point inside the ~1 µs window between a failed read attempt (~500 ns) and the next retry — so the consumer's extra wait averages ~0.5 µs one-way, ~1 µs round-trip.
  4. 1.8 µs + ~1 µs backoff ≈ 2.8 µs, close to the measured 3.21 µs — the residual is normal measurement noise from the isolated-core setup.
💡
At p99 (7.29 µs), the same backoff effect contributes ≥2 µs, and the CXL device's own tail latency (reads up to 1.2 µs under background load, vs. ~500 ns typical) stacks on top — explaining the rest of the 5.49 µs p99 gap.

③ Why 64 B costs ~1 µs more than 8 B

Median RTT jumps from 3.21 µs (8 B) to 4.42–4.51 µs (64–256 B) — a message size increase of 8× but a shift the paper attributes to something else entirely.

  1. 8 B fits in one cache line — index and message share the single line the consumer must read.
  2. 64 B (with its index) needs two cache lines — one line, plus one more. The consumer must flush and read both.
  3. Each read costs ~500 ns, so two consecutive reads instead of one adds roughly 500 ns – 1 µs.
  4. That single extra read accounts for essentially the entire shift — not the extra 56 bytes of payload, which is tiny by comparison.
🍯
Insight: the 8→64 B jump is a cache-line effect: 64 B needs a second cache-line read (index line + data line) that 8 B doesn't. 128 B and 256 B actually span more than two lines, but their RTT stays close to the 64 B number anyway — a small number of extra reads/writes can execute in parallel rather than serially, so they don't add up one-for-one. Latency only visibly climbs again at 512 B, once write time itself becomes significant.

④ Flow control: can the producer write the next message?

Shadix is configured with a ring buffer of 4,000,000 slots per SPSC queue. The producer has written up to index 4,000,010. Can it write index 4,000,011 if the consumer's last-index-read is (a) 8, or (b) 20?

  1. Rule: allowed only if last_index_written − last_index_read < ring_buffer_size.
  2. Case (a): 4,000,010 − 8 = 4,000,002. Is 4,000,002 < 4,000,000? No — the producer must wait. The consumer is lagging by more than a full lap of the buffer.
  3. Case (b): 4,000,010 − 20 = 3,999,990. Is 3,999,990 < 4,000,000? Yes — the write is allowed.
  4. Takeaway: the producer never checks the consumer's identity or state directly — only this one arithmetic comparison, read from a value the consumer itself stores back into CXL memory.
💡
This is why the design doesn't need a lock: both flow control (this check) and freshness (the index guard from Worked Example ①'s companion primer) reduce to comparing plain integers.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A consumer process crashes mid-processing, without being restarted or healed. What happens to messages already enqueued for it in Shadix, and why?
Show answer
They sit in the ring buffer forever, undelivered — Shadix's design explicitly does not address consumer failures. If the consumer is later healed, correctness of redelivery is left to the application (e.g., persisting the in-progress index to CXL memory before starting work on it).Misconception: that a "distributed" system like this has some baseline fault tolerance for free. It doesn't — that's stated as a known limitation, not an oversight to work around.
Problem 2 · medium
A ring buffer has 1,000 slots. The producer has written up to index 2,450. The consumer's last-index-read is 1,470. Can the producer write index 2,451?
Show answer
2,450 − 1,470 = 980. Is 980 < 1,000? Yes — the write is allowed, with 20 slots of headroom before the producer would have to stop.Misconception: comparing against the raw index values (2,450 vs 1,470) instead of their difference against the buffer size — it's the gap that matters, not the absolute position.
Problem 3 · medium
Why does the producer write the index-bearing cache line last, behind a fence, rather than writing it first for simplicity?
Show answer
The index line is the reader-visible "this item is ready" signal. If it were written first, a consumer could read a fresh index but stale (or unwritten) message-body lines — a torn read. Writing it last, after a fence guarantees the other lines are complete, means the moment the index becomes visible, the whole item is guaranteed complete too.Misconception: that write order doesn't matter as long as all the writes eventually happen. Order matters specifically because a concurrent reader can observe any intermediate state without it.
Problem 4 · hard
Why does Shadix pick a queue uniformly at random instead of always routing to the least-loaded queue?
Show answer
Tracking "which queue is least loaded" would itself require a shared, contended piece of state that every producer/consumer reads and updates — adding more CXL traffic and coordination overhead to solve a problem uniform-random selection sidesteps almost for free. The paper is explicit that the random policy is a simplicity choice, not a claimed-optimal one, and can be swapped for something smarter.Misconception: that the paper claims random selection is the best possible policy. It doesn't — it's a deliberately simple baseline, with the swap left as future work.
Problem 5 · medium
Valkey's latency barely changes between synchronous and asynchronous sending, while NATS's median RTT rises from ~226 µs (sync) to 1.4–1.8 ms (async). Why do "async" modes behave so differently across brokers?
Show answer
Valkey's async mode sends immediately and only defers reading the acknowledgment — so per-message latency is essentially unaffected. NATS and Pulsar's async modes actively buffer/batch several messages before transmitting, which increases throughput but means an individual message often waits for the batch to fill (or a timeout), directly inflating its RTT.Misconception: that "asynchronous" means one specific, universal behavior. Here it means two different things — deferred acknowledgment (Valkey) vs. batching (NATS/Pulsar) — with very different latency consequences.
Problem 6 · hard
CXL 3.0 adds hardware-managed cross-host cache coherence. If Shadix's testbed had CXL 3.0 hardware instead of CXL 1.1, which specific pieces of its design would likely become unnecessary?
Show answer
The explicit cache-line flush before every consumer read (hardware coherence would keep the local cache consistent automatically) and, potentially, some of the manual write ordering — though the index-guard pattern itself would likely remain useful for detecting "is this slot new" regardless of coherence hardware, since that's an application-level freshness question, not a caching one. The paper notes CXL 3.0 deployment is still a "long, gradual adoption journey," which is why it designed for 1.x/2.0 instead.Misconception: that hardware coherence would make the whole manual-coherence design obsolete. Some of it (flushes, RFO avoidance) is coherence-specific and would shrink; the index/sequence-number logic solves a different problem (message freshness) that persists regardless.
Problem 7 · easy
Shadix ran on two Intel-based hosts connected via a CXL device; Valkey/NATS/Pulsar ran on three AMD-based hosts connected via InfiniBand. What's the right way to interpret a claim like "Shadix is 57× lower latency than Pulsar"?
Show answer
As suggestive evidence that CXL shared memory has a fundamentally lower latency floor than RDMA/TCP for this kind of workload — not as a controlled, apples-to-apples benchmark. Different CPUs, different interconnects, and different clusters mean some of the gap could reflect hardware differences unrelated to the broker architecture itself. The paper says exactly this: comparisons are difficult given the different hardware setups.Misconception: treating cross-cluster benchmark numbers as precise, controlled measurements. The authors themselves flag this caveat rather than overselling the comparison.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What is Shadix, in one sentence?▾
A message broker with no broker process — producers and consumers exchange messages directly through a grid of SPSC ring buffers living in shared, disaggregated CXL memory.
Q2How is this different from just using RDMA, like Valkey does?▾
RDMA (what Valkey uses, over InfiniBand) skips the kernel's socket/TCP network stack, but still routes through a NIC and IB's own verbs/queue-pair protocol — and Valkey still has a separate broker process relaying messages. CXL load/store bypasses the NIC entirely — the CPU treats remote memory almost like local memory — and Shadix has no broker process at all, just a shared data structure.
Q3What does "manually manage cache coherence" mean in practice?▾
Three things: writing with an atomic instruction (movdir64b) that skips Read-For-Ownership, writing multi-cache-line items in a specific order (data lines, then the index line, behind a fence), and explicitly flushing a cache line before every read so the consumer never trusts a stale local copy.
Q4Why does Shadix only support synchronous sending?▾
A message is fully committed to CXL memory (its index line written) before the API call returns — there's no notion of a pending, unacknowledged send to batch, unlike TCP/RDMA-based clients that can queue several messages before flushing them to the network.
Q5What happens if a consumer crashes?▾
Messages already enqueued for it are never processed — this is an explicitly stated limitation, not handled by the current design. The paper suggests a consumer could persist its in-progress index to CXL memory to support recovery, but that's left as future work.
Q6Does Shadix support topics or message routing?▾
No — there's no built-in way to control which subset of consumers receives a message. The paper suggests running one Shadix instance per topic as a workaround, but notes this doesn't scale to many topics.
Q7Why does throughput peak at 8 B instead of climbing further with even smaller messages?▾
8 B is the smallest size tested and the only one where the whole item (index + message) fits in a single cache line — every larger size needs at least one more cache line touched per operation, which is the dominant cost once messages exceed one line.
Q8Why is Shadix's throughput edge over Pulsar (~2.9×) so much smaller than its latency edge (dozens of ×)?▾
Pulsar's asynchronous mode batches many messages per network round trip, which is specifically a throughput optimization — it trades away latency (messages wait to fill a batch) to get there. Shadix has no batching at all, so it competes on throughput using only the raw speed of individual CXL operations, which narrows the gap even though its latency stays far lower.
Q9Is the comparison to Valkey/NATS/Pulsar fair?▾
Not a controlled one — the paper measured the baselines on a separate three-host AMD/InfiniBand cluster because the CXL testbed's hosts lack high-speed networking. The authors flag this explicitly: treat the comparison as evidence Shadix is competitive, not as a precise apples-to-apples benchmark.
Q10What's still missing before Shadix could be a production broker?▾
Consumer failure handling, topic/routing support beyond one-instance-per-topic, and — more fundamentally — it currently targets CXL 1.x/2.0-style manual coherence; a future CXL 3.0 deployment with hardware cross-host coherence could simplify parts of the design, but that hasn't been evaluated here.

Glossary, results, and provenance

Every term in one place, the headline numbers, and a clear line between the paper's claims and this guide's framing.

Core terms
ShadixThe paper's prototype: an MPMC message broker implemented as a grid of SPSC ring buffers in shared, disaggregated CXL memory, with manually managed coherence.
Index (sequence number)A 32-bit counter assigned to each message and stored alongside it; a consumer compares the stored index to its expected value to detect whether a slot holds a new message.
Last index written / readPer-queue counters the producer and consumer maintain in CXL memory, used for flow control (don't overwrite unconsumed messages) and freshness checks.
ItemAn index-message pair stored together in a ring buffer slot; may span multiple cache lines for larger messages.
BackoffExponential delay (capped at 512 ns) applied after a failed enqueue/dequeue attempt, paired with yielding to an internal scheduler instead of busy-waiting.
movdir64bThe x86 instruction Shadix uses for all producer writes — atomic 64-byte stores that avoid Read-For-Ownership traffic.
Manual coherence managementSoftware techniques (flushes, ordered writes, atomic stores) substituting for hardware cross-host coherence on CXL 1.x/2.0.
Supporting terms
Publish/subscribeThe distributed-systems pattern with producers, consumers, and a broker exchanging messages between them.
RFORead-For-Ownership — the coherence transaction a normal cached write triggers before modifying a line it doesn't own.
CDFCumulative distribution function — how the paper's latency figures are read (x = RTT, y = fraction of messages at or below it).
RTTRound-trip time, used instead of one-way latency to avoid needing synchronized clocks across hosts.
Sync / async sendingClient library modes: one message per round trip (sync) vs. batching several before transmission (async, for the baseline brokers only).
CXL 1.x / 2.0 vs. 3.0Backward-compatible CXL generations; 3.0 adds hardware-based cross-host coherence, absent in the 1.1 device this paper evaluates on.

Related work (from the paper's own comparisons)

Valkey easy

open-source Redis fork · used as a baseline in this paper

Supports RDMA (experimentally) via its list data structure as a queue. Only its main thread could be used for asynchronous RDMA measurements — I/O threads with async sending and RDMA failed to work together.

RocketBufs medium

Hoang, Cassell, Brecht, Al-Kiswany · DEBS 2020

An RDMA-based message-oriented middleware framework. Source code unavailable, so the comparison used the authors' own reported numbers; Shadix outperforms it by at least an order of magnitude in both latency and throughput.

Ghostwriter medium

Makait, Del Monte, Rabl · ADMS 2024

A distributed message broker using RDMA one-sided verbs over non-volatile memory. Evaluated on the same IB hosts as Valkey/NATS/Pulsar here — yielded lower throughput than all three.

CXL-Bench medium

Weisgut, Ritter, Schmeller, Tözün, Rabl · ADMS 2025

The benchmarking tool used to establish this paper's CXL device's raw bandwidth/latency bounds — the numbers behind every "theoretical limit" figure in this guide.
