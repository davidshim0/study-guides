Making the broker disappear into shared memory, instead of a network hop

Every message broker you've used — Kafka, Valkey, NATS — is a separate process you talk to over a network. Shadix asks: what if the queue just lived in memory both machines already share, and a producer's store became a consumer's load?

📄 "Shadix" · Hackenberg, Hagen, Weisgut, Schmeller, Rabl · DIMES '26 🎓 CXL fundamentals assumed — primers focus on the broker-specific mechanics ⏱ ~25 min read
📬

Put the queue inside the CXL memory both hosts share, and hand-manage the cache-line visibility that CXL 1.x/2.0 doesn't give you for free.
No broker process, no RFO, no NIC round trip.

Before you begin

Quick glossary, then the broker-specific ideas

You already know CXL's host/device split and coherence domains. What follows leans into the parts that are specific to building a message queue on top of that — skip anything you already know.

📖 Quick glossary — acronyms used throughout

CXLCompute Express Link — PCIe-based interconnect for cache-coherent CPU access to remote memory via ordinary load/store.
MPMCMulti-producer multi-consumer (queue) — many senders, many receivers, one logical channel.
SPSCSingle-producer single-consumer (queue) — the simplest, lock-free building block; Shadix composes many of these.
RDMARemote direct memory access — lets a NIC read/write remote memory without the remote CPU, used by Valkey over InfiniBand.
RTTRound-trip time — send a message out and get a reply back; used here since one-way latency needs synchronized clocks.
RFORead-for-ownership — the hidden read a CPU does before a normal write, to gain exclusive ownership of a cache line.
movdir64bAn x86 instruction that atomically writes a full 64-byte cache line, bypassing RFO.
IBInfiniBand — the high-speed network fabric used for the RDMA/TCP baseline brokers in this paper.
1What a message broker actually does▾

Producers send messages; consumers receive them; a broker sits between them and does the routing. It's the standard publish/subscribe pattern behind systems like Kafka. Brokers need low latency (for interactive/streaming use) and high throughput (for bulk pipelines) simultaneously — a broker that's fast at one and slow at the other isn't good enough.

Now you're ready: Shadix's whole pitch is replacing the broker process — and the network hop to reach it — with a queue that lives directly in memory both endpoints already share.
2SPSC and MPMC queues — and why MPMC is built from SPSC▾

A single-producer single-consumer (SPSC) ring buffer is the easy case: exactly one writer, one reader, no coordination needed between them beyond a head/tail pointer. A multi-producer multi-consumer (MPMC) queue is harder — many writers and readers contend for the same slots.

A common trick: don't build one hard MPMC structure — build a grid of easy SPSC queues, one per producer-consumer pair, and let senders/receivers pick which pair to use.

Now you're ready: Shadix is exactly this — one SPSC ring buffer per (producer, consumer) pair, so P producers and C consumers need P × C queues.
3CXL 1.x/2.0 vs 3.0 — who manages coherence▾

You know CXL lets a CPU access remote memory with plain loads and stores. What matters for this paper specifically: CXL 3.0 adds hardware-managed coherence between hosts sharing a device. Below 3.0 (1.x, 2.0 — what's actually deployable today), each host has its own coherence domain: writing on host A does not automatically invalidate host B's cached copy.

Now you're ready: because real CXL 1.1 hardware (like the device this paper uses) has no cross-host coherence, Shadix cannot use an off-the-shelf lock-free MPMC library — those all assume the hardware keeps caches coherent. Shadix manages coherence itself, in software.
4Cache lines, flushes, and why "reading memory" isn't free of staleness▾

A CPU's private cache can silently hold a stale copy of a CXL memory location that another host just changed — there's no snooping across hosts below CXL 3.0. To see a fresh value, software must explicitly flush/invalidate the relevant cache line before reading it, then re-fetch from the underlying memory.

Now you're ready: Shadix's consumer explicitly flushes the cache line holding a message's guard index before every read attempt — that's the software substitute for hardware coherence.
5Sequence numbers as freshness guards▾

A ring buffer reuses slots. So how does a reader know "is what's in this slot the message I want, or leftover data from three laps ago?" The standard fix: tag each write with a monotonically increasing sequence number (an "index"), and have the reader check that the stored index matches what it expects before trusting the payload.

Now you're ready: Shadix's items are (32-bit index, message) pairs. A consumer only accepts a slot once its stored index equals the index it is currently expecting.
6RFO and why avoiding it matters on shared memory▾

A normal CPU store to a cache line it doesn't already own triggers a hidden read first (read-for-ownership, RFO) to fetch the line and claim exclusive access — extra traffic you don't need if you're just going to overwrite the whole line anyway. On a CXL link, that's extra round trips over an already latency-sensitive path.

Now you're ready: Shadix writes with movdir64b, an x86 instruction that atomically stores a full 64-byte cache line without an RFO — cutting the CXL traffic per write roughly in half.
7Backoff and cooperative scheduling▾

When a queue is full or empty, spinning in a tight retry loop wastes CPU and can hammer a shared resource (worse, CXL memory itself degrades under concurrent load). A common fix is exponential backoff: wait a little longer after each failed attempt, up to a cap, so contention eases instead of compounding.

Now you're ready: Shadix backs off (capped at 512 ns) after a failed enqueue/dequeue, and — instead of burning CPU on that wait — hands control to an in-application scheduler that does other useful work.
8Synchronous vs asynchronous client sending▾

Synchronous sending: send one message, wait for the broker's acknowledgment, then send the next — one round trip per message. Asynchronous sending: the client library batches/coalesces several messages before flushing them over the network, trading per-message latency for much higher throughput.

Now you're ready: the baseline brokers in this paper are measured both ways. Shadix only has a synchronous mode — a message is fully written to CXL memory before the next one is sent (the system runs entirely in-memory, with no persistence/durability guarantee) — which is worth remembering when comparing throughput numbers.
9Throughput (msgs/s, GB/s) vs latency (RTT)▾

Two different scorecards, and a system can be great at one and mediocre at the other. Throughput is how much data moves per second under sustained load (messages/second, or bytes/second). Latency is how long one message takes — measured here as round-trip time (RTT) rather than one-way delay, because one-way timing needs clocks synchronized across hosts, which the authors avoid.

Now you're ready: the two evaluation sections of this paper (throughput, then RTT) are testing exactly these two, separately, at multiple message sizes.
The whole story in one place

Shadix in a nutshell

Why CXL changes the broker calculus, what Shadix actually builds, and what it costs in latency and throughput.

Every conventional message broker — Valkey, NATS, Apache Pulsar — is a separate process that producers and consumers reach over a network (TCP, or RDMA for the fastest ones). Even RDMA's best case is a network operation with single-digit-µs latency per word. CXL offers something categorically different: a CPU can touch memory on a shared CXL device (not another host's own memory) using an ordinary load or store instruction, at latencies the paper measures around 500 ns read / 400 ns write — no NIC, no broker process in between.

The catch: the CXL hardware available today (CXL 1.1) does not give hosts a shared, hardware-managed coherence domain. If host A writes and host B has a stale cached copy, B won't automatically see the update — that arrives only in CXL 3.0, whose real deployment is still a gradual journey. So Shadix, the paper's contribution, is an MPMC message queue built directly in CXL memory that manages this coherence itself: it composes one SPSC ring buffer per producer–consumer pair, guards each slot with a sequence-number index, writes messages so the guard becomes visible only after the payload is durable, and uses movdir64b atomic writes to sidestep read-for-ownership traffic.

The payoff, measured on a real FPGA-based CXL 1.1 device: Shadix reaches single-digit-µs round-trip latency (median 3.21 µs at 8 B, right down to the theoretical 1.8 µs floor in the best case) and saturates the CXL device's throughput at large message sizes (13.60 GB/s at 8 KiB, against a measured ~14 GB/s ceiling under concurrent read/write load) — while the RDMA- and TCP-based baselines it's compared against (on separate InfiniBand hardware) run one to three orders of magnitude slower in synchronous mode — though the authors caution that the differing hardware setups make this a hard comparison to draw cleanly, not a controlled apples-to-apples benchmark.

🍯 Key takeaways

  • CXL turns "send a message" into "do a load/store" — but only within a coherence domain, which CXL 1.x/2.0 doesn't span across hosts.
  • Shadix = a grid of P × C SPSC ring buffers, one per producer–consumer pair, guarded by 32-bit sequence-number indices.
  • The index-bearing cache line is written last, after a fence, so a torn write never looks complete.
  • movdir64b atomic 64 B writes avoid read-for-ownership (RFO) traffic on the CXL link.
  • Exponential backoff (capped at 512 ns) plus cooperative scheduling avoids wasting CPU / hammering the CXL device under contention.
  • Result: median RTT of 3.21–4.66 µs across message sizes (best case dips to 1.8 µs at 8 B; the 99th percentile reaches 9.14 µs at 512 B), and throughput up to 13.60 GB/s — near the ~14 GB/s device ceiling under concurrent load.
  • Vs. Valkey/NATS/Pulsar (measured on separate IB hardware — the authors caution this comparison is difficult given the differing hardware): 1–3 orders of magnitude faster in synchronous mode.
Six everyday pictures

How to think about Shadix

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core design · MPMC from SPSC

A grid of private mailboxes

Instead of one shared mail bin everyone reaches into (hard to manage without collisions), give every sender-receiver pair their own private mailbox. Sender 1 has a separate slot for Receiver A and Receiver B; sender 2 too. Nobody's mail gets mixed up, because nobody shares a slot. Shadix is exactly this: one SPSC ring buffer per (producer, consumer) pair.

Where it breaks: the grid grows as P × C — with many producers and consumers, that's a lot of mailboxes to check. Selection is uniformly random with retry, which is simple but not necessarily the smartest routing.
The guard · Sequence-number index

Numbered parking tickets

A parking garage reuses spot #12 over and over for different cars. To know whether the car in spot 12 right now is your car or someone else's from an hour ago, you check the ticket number, not just "is a car there." Shadix's ring buffer reuses slots the same way — each item is stamped with an ever-increasing index, and a consumer only trusts a slot when its stamped index matches the one it's currently expecting.

Where it breaks: 32-bit indices eventually wrap around. Shadix's fullness check (last-written minus last-read) is written with unsigned arithmetic specifically so the wraparound doesn't break the comparison.
Write ordering · The two-step write

Sealing a package, label last

If you seal the label reading "contents complete" before the box is actually full, anyone reading the label is misled. Pack the box first, then apply the label. Shadix's producer does the same: it writes the non-index cache lines of an item first, issues a memory fence, and only then writes the cache line holding the index — the line the consumer treats as "message ready."

Where it breaks: this only guarantees the appearance of atomicity for a reader checking the label; it doesn't protect against a producer crashing mid-write. Shadix doesn't handle producer/consumer failure recovery (see Reference tab).
Efficient writes · Avoiding RFO

Skipping the checkout desk

Normally, to replace a page in a shared binder you first check the binder out (so nobody else edits it at the same time), then write your page. If you're replacing the entire page anyway, that checkout step is pure overhead. movdir64b is the "just hand over the finished page" move — an atomic 64-byte write that skips the CPU's usual read-for-ownership step.

Where it breaks: it only works because the write is exactly one full 64-byte cache line. Once an item spans more than one line, Shadix still writes each line with movdir64b, but now needs an extra sequential CXL write (and the consumer an extra sequential read) — that added round trip, not RFO, is what the paper attributes its throughput cliff to.
Contention control · Backoff & scheduling

Running errands between check-ins

Waiting for a table at a busy restaurant, you don't stand frozen at the host stand — you run a quick errand and check back a bit later, waiting longer each time it's still full, up to a point. Shadix's producers/consumers do this after a failed enqueue/dequeue: back off (capped at 512 ns) and hand control to the application's own scheduler to do other useful work, rather than spinning.

Where it breaks: this variance in wait time is exactly what shows up as Shadix's RTT tail — the paper attributes much of its high-percentile latency to a consumer landing at a random point inside that backoff window.
Baseline comparison · Sync vs async clients

One letter at a time, or a mailbag

Hand-delivering one letter and waiting for a signed receipt before writing the next is safe but slow. Dropping a whole mailbag in one trip is much faster per letter, but no single letter arrives any sooner — in fact the ones at the bottom of the bag arrive later. That's synchronous vs. asynchronous/batched sending: NATS and Pulsar's async mode buys throughput by batching, at the cost of median RTT rising into the millisecond range.

Where it breaks: Shadix has no "mailbag" mode — every message is fully written and visible in CXL memory before the next is sent (there's no persistence to disk either) — so its throughput gains come from CXL's raw speed, not from batching tricks the baselines use.
The full explanation

How Shadix actually works

Section by section, with the paper's key mechanics rebuilt as diagrams you can read at a glance.

1 · The MPMC layer — a grid of SPSC queues

Shadix connects P producer processes and C consumer processes using one SPSC ring buffer per (producer, consumer) pair — P × C queues total. To enqueue, a producer picks a consumer uniformly at random and tries that pair's queue; if it's full, it tries another consumer. Dequeuing is symmetric: a consumer picks a producer at random, and retries on another if that queue is empty.

# producer enqueue (simplified)
loop:
    c = random_consumer()
    if Q[me][c].try_enqueue(msg): return
    backoff()                      # capped at 512 ns

# consumer dequeue (symmetric)
loop:
    p = random_producer()
    if msg = Q[p][me].try_dequeue(): return msg
    backoff()

2 · The SPSC ring buffer — items, indices, and the write order

Each SPSC queue is a ring buffer of user-configurable size (4 million messages per queue in the experiments). A message and its 32-bit sequence-number index together form an item; the slot for index i is i mod ring_size. A consumer trusts a slot's message only once the stored index equals the index it expects — otherwise it applies backoff and retries elsewhere.

3 · Making the write "atomic-looking" without hardware coherence

If a message spans multiple cache lines, only the first cache line carries the index. The producer must guarantee the whole message is visible before the index becomes visible — otherwise a consumer could read a half-written message. Shadix enforces this ordering explicitly, in software:

# producer write, for a multi-cache-line item
write_non_index_cache_lines(message)
memory_fence()                 # wait until those writes are visible
movdir64b(index_cache_line)     # atomic 64B write, no RFO — this "publishes" the item

On the read side, the consumer flushes the cache line containing the index before every check (so it isn't fooled by a stale cached copy), and flushes any additional message cache lines before reading them, once the index confirms the item is ready.

4 · Reading the paper's own throughput numbers by message size

Try the sizes the paper actually measured and see how throughput, data rate, and cache-line span move together.

5 · Evaluation harness — how the numbers were actually collected

To get trustworthy single-digit-µs measurements, the authors isolated CPU cores for Shadix (kernel parameters nohz_full and isolcpus) and timed with clock_gettime(CLOCK_MONOTONIC_RAW), whose own back-to-back call overhead they measured at ~20 ns — small enough not to distort µs-scale RTTs. Because one-way latency needs synchronized clocks across hosts, RTT was measured instead: a Send and Receive process share one host (no clock-sync needed between them), while a Server role on the other host echoes the timestamp back, using two separate Shadix queue instances for the forward and return paths (Shadix has no built-in topic routing).

Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own numbers — cache-line spanning, the bandwidth ceiling, the theoretical RTT floor, and the backoff-latency budget.

① Why 8 B is fastest and 64 B isn't

An item is a 32-bit (4 B) index followed by the message. A cache line is 64 B. How many cache lines does an 8 B message need vs. a 64 B message?

  1. 8 B message: item size = 4 + 8 = 12 B. ⌈12 ÷ 64⌉ = 1 cache line — a single atomic movdir64b write, no fence needed.
  2. 64 B message: item size = 4 + 64 = 68 B. ⌈68 ÷ 64⌉ = 2 cache lines — the producer must write the payload line, fence, then write the index line.
  3. Consequence: that extra sequential step is exactly what the paper reports: message rate falls from 25.62 M msgs/s (8 B) to ~11 M msgs/s (64 B) — the additional write/read pair dominates.
🍯
Insight: the throughput cliff isn't about message size per se — it's about crossing a 64-byte cache-line boundary, which forces a second sequential CXL operation.

② Confirming the bandwidth-ceiling numbers

The paper reports 5.49 M msgs/s at 2 KiB and 1.66 M msgs/s at 8 KiB. Do these reproduce the stated data rates of 11.24 GB/s and 13.60 GB/s?

  1. 2 KiB: 5.49 × 10⁶ msgs/s × 2048 B = 1.124 × 10¹⁰ B/s = 11.24 GB/s. ✓ matches the paper exactly.
  2. 8 KiB: 1.66 × 10⁶ msgs/s × 8192 B = 1.3599 × 10¹⁰ B/s = 13.60 GB/s. ✓ matches exactly.
  3. Against the measured device ceiling under concurrent read/write load (~14 GB/s from CXL-Bench), Shadix reaches 80% of it at 2 KiB and 97% at 8 KiB — it's genuinely bandwidth-bound at large sizes, not overhead-bound.
💡
This is why the paper's own framing of the 8 KiB result is "saturates the throughput of the CXL hardware" — the arithmetic confirms it, not just the claim.

③ Deriving the theoretical minimum RTT — and matching it

CXL-Bench measures ~500 ns best-case read latency and ~400 ns best-case write latency on this device. What's the theoretical floor for a Shadix round trip, and does the measurement hit it?

  1. One-way delay: a message must be written to CXL memory (400 ns) and then read from it (500 ns) ≈ 900 ns.
  2. Round trip: the same happens on the way back ⇒ theoretical minimum RTT ≈ 2 × 900 ns = 1.8 µs.
  3. Measured: at 8 B, Shadix's best-case RTT is exactly 1.8 µs — the implementation adds essentially zero overhead over the raw device physics in the best case.
  4. But the median is 3.21 µs — almost 2× the floor — because under the low offered load used for latency testing, the consumer is nearly always waiting at maximum backoff (see next example).
🍯
Insight: the gap between "matches theory exactly" (min) and "2× theory" (median) is not implementation slack — it's the backoff protocol doing its job of not busy-spinning.

④ The backoff window's contribution to median latency

Backoff is capped at 512 ns; a failed read costs ~500 ns. The paper argues these combine into roughly a 1 µs uniformly-random wait before a successful read. What does that predict for RTT?

  1. The window: 512 ns (max backoff) + ~500 ns (failed read) ≈ 1 µs interval during which the message became visible but the consumer hadn't checked yet.
  2. Median contribution: a uniformly random arrival inside a 1 µs window averages 0.5 µs extra one-way delay, i.e. about 1 µs extra RTT.
  3. Check against measurement: theoretical floor 1.8 µs + ~1 µs backoff effect ≈ 2.8 µs — close to the measured 8 B median of 3.21 µs (the remainder is the device's own latency variance, not just its best case).
  4. Tail: the paper notes the device's high-percentile latencies (p99 read ≈ 0.8–1.2 µs vs. best-case 500–700 ns) amplify this effect for both failed and successful reads, contributing at least 2 µs to the 99th-percentile RTT.
💡
This is the paper's own explanation of its variance, reconstructed from its stated constants — a nice example of how a single design choice (a capped backoff) becomes a visible, quantifiable term in the latency budget.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why can't Shadix just use an existing lock-free MPMC queue library designed for shared-memory multicore systems?
Show answer
Those libraries assume the hardware keeps all cores' caches coherent automatically — a store on one core is visible to every other core "for free." Shadix's target hardware is CXL 1.x/2.0, where each host has its own coherence domain; a write on one host isn't automatically visible on another. Shadix has to manage that visibility itself (flush-before-read, ordered writes), which off-the-shelf libraries don't do.Misconception: that "shared memory" automatically means "coherent memory." CXL gives you the former without the latter below version 3.0.
Problem 2 · medium
A message is 500 bytes. Using a 4-byte index and 64-byte cache lines, how many cache lines does the item span?
Show answer
Item size = 4 + 500 = 504 bytes. ⌈504 ÷ 64⌉ = ⌈7.875⌉ = 8 cache lines.Misconception: forgetting the index. The guard itself takes space, so even a message that's an exact multiple of 64 bytes will spill into an extra cache line once you add the 4-byte index.
Problem 3 · medium
Why must the producer write the non-index cache lines of an item before writing the cache line containing the index, with a fence in between?
Show answer
The index is the guard the consumer checks to decide whether a slot's contents are trustworthy. If the index-bearing line were written first (or concurrently), a consumer could see a "ready" index while the rest of the message is still being written — a torn read. Writing payload first, fencing, then writing the index last guarantees that by the time the index is visible, the whole message already is.Misconception: that a memory fence makes the write atomic across all the item's cache lines. It doesn't — it only orders the writes; the two-line write is still two separate operations, just correctly sequenced.
Problem 4 · hard
The producer decides whether it can write a new message by checking last_index_written − last_index_read < ring_size, using unsigned 32-bit arithmetic. Why does this work correctly even after the index counter wraps around past 2³²−1?
Show answer
Unsigned subtraction naturally "wraps" the same way the indices do: if last_index_written has wrapped past zero while last_index_read hasn't yet, the subtraction still yields the correct small positive difference (modulo 2³²), rather than a huge negative number a signed comparison would produce. The check stays meaningful as long as the two indices are never more than one full range apart — true here since the ring size is far smaller than 2³².Misconception: that wraparound needs special-case handling (like an explicit "did it wrap?" branch). Unsigned modular arithmetic handles it automatically as long as you never let the gap exceed the counter's range.
Problem 5 · medium
Why is round-trip time (RTT) measured instead of one-way latency, and why do Send and Receive run on the same host?
Show answer
One-way latency requires the sender's and receiver's clocks to be synchronized to sub-microsecond precision across hosts — hard to guarantee. RTT avoids this: it only needs one clock. Running Send and Receive on the same host means the timestamp is written and later read by processes sharing that host's clock, so no cross-host synchronization is needed at all — only the middle "Server" hop (over CXL or the broker) needs to forward the timestamp faithfully.Misconception: that RTT is "twice the one-way latency," so you can just halve it. The paper explicitly avoids that inference — RTT includes the return path's own queuing/backoff, which need not equal the forward path's.
Problem 6 · easy
NATS and Pulsar's asynchronous mode dramatically increases throughput but also increases median RTT into the millisecond range. Why does batching help one metric and hurt the other?
Show answer
Batching coalesces many messages before flushing them to the network, amortizing per-flush overhead across all of them — great for aggregate throughput. But an individual message now has to wait for the batch to fill (or a timeout) before it's even sent, which directly adds to that message's own latency. It's a throughput/latency trade, not a free win.Misconception: that higher throughput always implies lower latency, or vice versa. They're independent axes — a system can dominate on one while regressing on the other, exactly as seen here.
Problem 7 · hard
Shadix's minimum RTT at 8 B (1.8 µs) exactly matches the theoretical floor computed from CXL-Bench's read/write latencies, but the median (3.21 µs) doesn't. What does this gap — and not the minimum — actually tell you about Shadix's design?
Show answer
The minimum matching theory tells you Shadix adds essentially zero fixed software overhead over the raw hardware in the best case. The gap at the median tells you where the variable cost lives: the backoff-and-retry protocol, which by design makes a consumer wait a random amount before re-checking a queue, rather than spin continuously. That's a deliberate trade — less CPU burn and less contention on the CXL device — paid for in typical-case (not best-case) latency.Misconception: that a good minimum-latency result means the "typical" latency is close to it. Backoff-based designs specifically decouple these — the median reflects the backoff policy, not the hardware floor.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What exactly is Shadix's novelty?▾
It's presented as the first message broker that uses shared, disaggregated CXL memory as its communication medium, rather than a network protocol (TCP or RDMA) reaching a separate broker process. The queue data structures live directly in the CXL device; producers and consumers interact with them via ordinary loads/stores.
Q2Why can't Shadix rely on hardware cache coherence to keep things simple?▾
Because the CXL memory available today (CXL 1.1 in this paper's hardware) doesn't provide hardware-managed coherence across hosts — that's a CXL 3.0 feature whose real deployment is still gradual. Below 3.0, each host has its own coherence domain, so Shadix has to flush/invalidate cache lines and order writes manually in software.
Q3How many queues does Shadix actually create?▾
One SPSC ring buffer per (producer, consumer) pair — so P producers and C consumers need P × C queues. In the paper's throughput experiment that's 2 producers × 2 consumers = 4 queues; in the latency experiment, two separate Shadix instances handle the forward and return paths.
Q4What is the "index" and why does it need to be 32 bits?▾
It's a monotonically increasing sequence number stamped on each message, letting a consumer tell a fresh item in a reused ring-buffer slot from a stale leftover. 32 bits is simply the chosen counter width; the producer's fullness check is written with unsigned arithmetic specifically so wraparound past 2³²−1 doesn't break the comparison.
Q5Why does the producer write the index-bearing cache line last?▾
The index is what tells the consumer "this message is ready to read." If it were written first (or concurrently with the payload), a consumer could observe a valid-looking index while the rest of the message was still being written — a torn read. Writing the payload first, fencing, then the index last makes the index's visibility a reliable "everything is here" signal.
Q6What does movdir64b buy you, concretely?▾
A normal store to a cache line the CPU doesn't already own first triggers a hidden read-for-ownership (RFO) — an extra round trip. movdir64b atomically writes a full 64-byte cache line without that RFO, which matters a lot on a CXL link where every extra round trip costs real latency and bandwidth.
Q7Why does throughput peak at the smallest message size instead of scaling smoothly?▾
Because an item (index + message) either fits in one 64-byte cache line or it doesn't. At 8 bytes it fits (fastest path, one atomic write). At 64 bytes and above it doesn't (index + 64 B message = 68 B), forcing a second sequential write/read pair — hence the sharp drop from ~25.6 M to ~11 M msgs/s between 8 B and 64 B, not a smooth decline.
Q8Is the comparison to Valkey, NATS, and Pulsar fair, given they ran on different hardware?▾
No, and the authors say so explicitly: Shadix ran on two hosts with CXL 1.1, while the baselines ran on three hosts connected via HDR200 InfiniBand, because the CXL hosts lack high-speed networking. The authors frame the comparison as showing Shadix is "competitive" rather than claiming a strictly controlled apples-to-apples benchmark.
Q9What can't Shadix do yet?▾
Two notable gaps: it doesn't handle consumer failures (a message sent to a dead consumer is simply never processed), and it provides no message routing/topics — you'd have to run one Shadix instance per topic, which doesn't scale to many topics.
Q10How does this connect to other CXL memory-pooling and database work I might know?▾
The paper explicitly situates itself alongside CXL-for-databases work like Tigon (a distributed database for a "CXL pod") and Lerner & Alonso's argument that CXL turns network-API applications into many-core shared-memory applications — Shadix is offered as evidence for exactly that transition, applied to message brokers rather than databases. It also cites Pond and DirectCXL as prior CXL pooling/disaggregation studies and CXL-Bench (by an overlapping author group) as the source of the raw device numbers used throughout.
Q11What future work do the authors flag?▾
Implementing consumer-failure recovery and topic-based routing directly in Shadix, or alternatively extending a conventional message broker with CXL-based communication instead of building a new one from scratch.

SPSC ring bufferA fixed-size circular buffer for exactly one writer and one reader; the basic building block of each producer–consumer pair's queue.
ItemAn (index, message) pair stored together in the ring buffer; the index acts as a freshness guard against reused slots.
Last index read / writtenCounters, stored in CXL memory, that let the producer know how far the consumer has progressed, used to avoid overwriting unconsumed messages.
movdir64bx86 instruction for an atomic 64-byte cache-line write that avoids read-for-ownership (RFO) traffic.
Exponential backoffProgressively longer waits after a failed enqueue/dequeue attempt, capped at 512 ns in Shadix, to reduce contention.
CXL host / deviceA host manages cache coherence; a device (here, the Seagate CMA blade) does not. Multiple hosts can share one device.
Hardware-managed coherence (CXL 3.0)Cross-host cache coherence enforced by the CXL fabric itself — absent in the CXL 1.1 hardware this paper evaluates on.
Supporting terms
RTTRound-trip time; used here instead of one-way latency to avoid needing synchronized clocks across hosts.
Sync / async client sendingWait for each acknowledgment before sending the next message, vs. batching several messages before flushing — a throughput/latency trade.
RFO (read-for-ownership)The implicit read a CPU performs before a normal write, to gain exclusive ownership of a cache line — adds CXL traffic Shadix avoids.
Delivery / ordering / routing semanticsBroker design choices: at-least/at-most-once delivery, FIFO ordering per producer, and topic-based routing — Shadix provides ordering per producer–consumer pair but no topics.
CXL-BenchThe benchmarking tool (by an overlapping author group) used to measure the raw CXL device's bandwidth and latency ceilings referenced throughout.
Valkey / NATS / Apache PulsarThe three baseline brokers: Valkey (RDMA-capable Redis fork), NATS and Pulsar (TCP-based general-purpose brokers), measured on separate InfiniBand hardware.

Related work cited by the paper

CXL-Bench: Benchmarking Shared CXL Memory Access medium

Weisgut, Ritter, Schmeller, Tözün, Rabl · ADMS 2025

Source of the raw device bandwidth/latency numbers (40/35 GB/s, 20/14 GB/s under background load, ~500/400 ns latencies) this paper builds its theoretical limits from.

RocketBufs medium

Hoang, Cassell, Brecht, Al-Kiswany · DEBS 2020

An RDMA-based message-broker framework; Shadix reports outperforming its published numbers by at least an order of magnitude in latency and throughput (no shared source code for a direct run).

Ghostwriter: a Distributed Message Broker on RDMA and NVM medium

Makait, Del Monte, Rabl · ADMS 2024

An NVM/RDMA message broker evaluated on the same baseline hardware as Valkey/NATS/Pulsar in this paper; reported to yield lower throughput than all of them.

CXL and the Return of Scale-Up Database Engines hard

Lerner, Alonso · PVLDB 2024

The argument this paper explicitly invokes: CXL can turn a networking-API-based application into a many-core shared-memory application — Shadix as a concrete instance for brokers.

Pond: CXL-Based Memory Pooling Systems for Cloud Platforms hard

Li, Berger, Hsu, et al. · ASPLOS 2023

Cited as prior work on CXL memory pooling/disaggregation — the broader systems context this paper's "shared disaggregated CXL memory" setup sits within.

Tigon: A Distributed Database for a CXL Pod hard

Huang, Chen, Ni, et al. · OSDI 2025

Cited alongside other CXL-for-databases work as the sibling research direction — distributed data systems built directly atop shared CXL memory.
