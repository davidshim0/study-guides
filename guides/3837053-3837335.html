Let the page table be the index, not just the map

Three PMEM sticks, one bandwidth ceiling. The fast fix (BIOS interleaving) can't be reconfigured without a reboot; the flexible fix (software RAID-0) throws away PMEM's whole point. Vessel gets close to both by turning a Linux page table into persistent, interleaved storage — though reshuffling data onto a newly added device still costs a lock-and-copy, not an instant switch.

Quick glossary

PMEMPersistent Memory — byte-addressable, non-volatile, accessed via load/store on the memory bus (here: Intel Optane).
NVPTTNon-Volatile Page Table Tree — Vessel's core structure: a page table persisted in PMEM, whose leaf entries map to interleaved data blocks.
PGD / PUD / PMD / PTEThe four levels of an x86-64 radix page table (Global/Upper/Middle Directory, Table Entry), each with 512-way fan-out.
MMU / TLBMemory Management Unit (walks page tables in hardware) / Translation Lookaside Buffer (caches recent walks).
VMAvm_area_struct — the kernel's descriptor for a contiguous region of a process's virtual address space.
RAID-0Striping data across devices for bandwidth, with no redundancy — here via Linux mdadm + EXT4.
devdax / DAXDevice-DAX: a raw PMEM device node you can mmap directly, bypassing the page cache and block layer.
CXLCompute Express Link — the interconnect expected to carry future PMEM, with hot-plug (runtime add) support for new devices.
1Byte-addressable vs. block I/O▾

Disks and SSDs are accessed in blocks through the kernel's I/O stack. PMEM sits on the memory bus: the CPU can load/store individual bytes directly, no syscall, no block layer, no interrupt.

Now you're ready: any PMEM design that forces data through a block layer (like RAID-0) throws away this advantage before the data even moves.
2Why one PMEM stick isn't enough▾

A single PMEM module has limited bandwidth that saturates under concurrent access. Scaling throughput means spreading accesses across several devices in parallel — the same reason DRAM is interleaved across channels.

Now you're ready: Vessel exists purely to aggregate this per-device bandwidth ceiling across 2–3+ sticks.
3Hardware interleaving (the fast, rigid option)▾

BIOS can stripe physical addresses across PMEM DIMMs (like DRAM interleaving), giving near-linear bandwidth scaling. But the interleave set is fixed at boot — adding a device means backup, reboot, BIOS reconfig, restore.

Now you're ready: this rigidity is exactly what breaks under CXL hot-plug, where devices can appear while the server is running.
4Software RAID-0 (the flexible, slow option)▾

mdadm can stripe any block devices, PMEM included, and lets you add/remove members without reboot. But every access now pays kernel trap, block-layer, and indexing overhead — and loses direct mmap access.

Now you're ready: this is Vessel's baseline to beat — the paper measures it losing by up to 14.9× on append throughput.
5Radix page tables, fan-out 512▾

x86-64 translates a virtual address through four fixed-fan-out levels (PGD→PUD→PMD→PTE), each a 512-entry table, bottoming out at a 4KB page. It's structurally just a radix tree.

Now you're ready: NVPTT reuses this exact tree shape as a persistent index — a 2-level tree reaches 1GB, a 3-level tree reaches 512GB.
6MMU/TLB acceleration — built into the CPU▾

Because page tables are a first-class hardware structure, walking one (and caching recent walks in the TLB) is accelerated by silicon that already exists on every CPU — no custom software indexing code required. Translation isn't literally free, though: a TLB miss still costs a real hardware page walk, just one the CPU already knows how to do fast.

Now you're ready: install NVPTT as a process's real page table, and every data lookup becomes a normal, MMU/TLB-accelerated address translation.
7VMAs and mmap▾

To give a process access to a memory region, the kernel allocates a VMA describing its virtual range and fault handler, then wires up page tables as pages are touched.

Now you're ready: mapping an NVPTT into a process is literally installing a VMA plus a (persistent) page table — the standard mmap path, repurposed.
8devdax mmap as the "ideal" baseline▾

When three PMEM devices are hardware-interleaved and exposed as one devdax node, mmap'ing it and copying directly is as fast as this hardware gets — no filesystem, no page cache, pure physical-address striping.

Now you're ready: this is the paper's performance ceiling. Vessel's whole claim is landing within 1.5% of it, in software.
The whole story in one place

Vessel in a nutshell

The trade-off, the structural trick that dissolves it, and the payoff.

Aggregating PMEM bandwidth has forced a choice: hardware interleaving is fast but can't be reconfigured without a reboot, while software RAID-0 is reconfigurable but routes every access through the block layer, erasing PMEM's byte-addressable advantage.

Vessel dissolves this by noticing that a radix page table and an interleaved-block index have the same shape. It persists a page table in PMEM — the Non-Volatile Page Table Tree (NVPTT) — and installs it directly into a process's address space. Translation then rides hardware already on every CPU: the MMU walks the tree and the TLB caches recent walks, so no custom software indexing code runs on the lookup path (a TLB miss still costs a hardware page walk — it's accelerated, not literally free). The tree's leaves are data blocks interleaved across the PMEM devices Vessel manages via its Interleaved Block Allocator, so bandwidth aggregates just like hardware interleaving — but the device set is a software decision, changeable at runtime via vessel_add_pmem and ptt_rebalance (though rebalancing itself locks the NVPTT and copies data, so it isn't instantaneous).

The payoff: on three Intel Optane modules, Vessel beats EXT4(mdadm RAID-0) by up to 14.9× on append throughput, and trails hardware-interleaved devdax mmap by under 1.5%.

🧩 Key takeaways

  • HW interleaving: fast, boot-time-fixed. RAID-0: flexible, block-layer-slow. Vessel wants both.
  • NVPTT = a real page table, installed into the process, whose leaf entries map to interleaved PMEM data blocks.
  • Translation rides existing MMU/TLB hardware — no custom indexing code on the data path, though a TLB miss still triggers a real hardware page walk.
  • New devices are added live (vessel_add_pmem); existing data stays valid without forced migration.
  • ptt_rebalance redistributes an NVPTT's blocks onto a newly added device, per-file; it locks that NVPTT and copies data, can be deferred, and a crash mid-rebalance just leaves it partially redistributed — fixed by rerunning it.
  • Result: ≤1.5% behind hardware interleaving, up to 14.9× ahead of RAID-0 on append.
🔭
For your tiering work: Vessel sits one layer below a hot/cold migration policy. It answers "how do I turn N PMEM/CXL-memory devices into one fast, flexible pool," not "which pages should live where." A TPP/Memtis/HeMem-style tiering engine could run on top of a Vessel-managed pool exactly as it would on a NUMA node today — Vessel just widens the bandwidth available underneath it.
Six everyday pictures

How to think about Vessel

Read in any order. Each ends with where the picture stops being true.

The core move · NVPTT

The map points straight at the warehouse

Normally a floor-plan tells you where the boxes are; the boxes live elsewhere, a separate lookup away. NVPTT makes the floor-plan's lowest-level pins point directly at the boxes — the page table's leaf entries map straight to the data blocks, interleaved across three warehouses (PMEM devices). Walk the map, and its last step lands you right at the goods — no separate warehouse-locator structure in between.

Where it breaks: page table entries still obey the hardware's fixed bit layout, so there's no free space to smuggle in arbitrary extra metadata beyond what that format already allows.
The trade-off · HW vs. software

A fixed train vs. a different taxi each stop

Hardware interleaving is a train on a published schedule: fast, but the route can't change mid-journey. Software RAID-0 is calling a fresh taxi for every block: flexible, but you pay a dispatch fee each time. Vessel is more like a subway with switchable platforms — one fast system, reroutable without stopping service.

Where it breaks: the "switch" still costs something — ptt_rebalance genuinely copies data; it's deferred and per-file, not free, just far cheaper than a full reboot-and-restore.
MMU/TLB · free acceleration

A GPS that remembers your commute

The first drive to a new address needs full directions (a page-table walk); the hundredth time, your GPS just recalls the route instantly (TLB hit). NVPTT gets this caching for nothing, because it's a real page table the CPU already knows how to walk fast.

Where it breaks: the TLB only caches so many "routes." A working set that roams far beyond TLB reach still pays the full walk cost on many accesses — caching helps, it doesn't erase translation.
Append · PTE-granularity faults

Pre-ordering a whole case, not one bottle

Faulting in a single 4KB page at a time means paying a fault's overhead for every bottle. Vessel allocates a full PTE range (2MB) on the first fault, so the next 511 pages in that range are already provisioned — one order placed, 512 bottles delivered.

Where it breaks: if the write is small and scattered rather than a long append, you've pre-ordered a case you'll barely touch — the trick pays off specifically for sequential append workloads.
Rebalance · crash safety

Reshuffling a deck mid-game, safely

Adding a device and rebalancing is like reshuffling a card deck while the game continues: cards not yet reshuffled are still playable from their old spot. If you're interrupted mid-shuffle, nothing is lost — the deck is just split between "old-only" and "fully shuffled," and you simply resume shuffling.

Where it breaks: "resume" here means re-running ptt_rebalance from scratch on that file, not resuming from a checkpoint — the paper doesn't describe partial-rebalance resumption.
Symmetric layout

Identical filing cabinets in every branch office

Every PMEM device gets the same layout — superblock, bitmap, data region — even though branches (devices) can hold different total sizes. Predictable layout everywhere means Vessel can always find the right drawer, regardless of which branch it's in.

Where it breaks: identical layout doesn't mean identical capacity — allocation logic still has to account for devices of different sizes when striping.
The full explanation

How it actually works

The structure, the allocator, lazy append, and online rebalancing — with the paper's real numbers.

1 · The measured gap (why a new approach is needed)

The paper's motivating experiment (Fig. 1) runs EXT4 sequential read/write across three configurations: a single PMEM, three PMEM hardware-interleaved, and three PMEM under mdadm RAID-0. Across 1–8 threads, RAID-0 trails hardware interleaving by roughly an order of magnitude — confirming that block-layer overhead, not device bandwidth, is the bottleneck software striping must solve.

2 · Two allocators for two kinds of data

Vessel's space-management module gives each PMEM device the same layout (superblock + free-block bitmap + data region) and runs two allocation policies: an Interleaved Block Allocator for NVPTT data blocks (assigns device by logical block index, so sequential blocks land on different devices) and a Round-Robin Block Allocator for NVPTT tree nodes and metadata (where interleaving by index doesn't matter, just even spread).

3 · Page-fault based append

A new NVPTT allocates nothing upfront. The first touch to a page triggers a fault; Vessel then provisions the entire PTE range it falls in — 2MB under 4KB pages — rather than one 4KB page, amortizing fault overhead across 512 pages. Page tables are wired up bottom-up: a lower-level table is linked into its parent only once it's fully configured, so a crash never exposes a half-built, dangling entry.

4 · Adding a device and rebalancing

vessel_add_pmem registers a new device's superblock immediately, growing total pooled capacity — new NVPTTs can span it right away. Existing NVPTTs are untouched and remain fully accessible; ptt_rebalance optionally re-traverses one NVPTT's blocks and redistributes them across all devices, locking only that NVPTT, deferrable until the file is idle. A crash mid-rebalance just leaves some blocks pre-addition (old devices only) and some post-addition (all devices) — valid either way; re-running the rebalance finishes the job.

5 · The programming model

APIDoes
vessel_add_pmemRegister a new device (start addr + size); inspects its superblock to decide if init is needed.
vessel_new_pttCreate a new NVPTT at a given level; returns its id.
vessel_ptt_map / unmapInstall/remove an NVPTT in the calling process's address space; returns the mapped virtual address.
vessel_del_pttDelete an NVPTT and free its space.
ptt_rebalanceRedistribute one NVPTT's blocks across all currently managed devices (locks that NVPTT only).
ptt_level_upGrow an NVPTT to a larger addressing range, keeping its existing data.
Follow the numbers

Worked examples

Four traces through the paper's actual measurements.

① Scaling from 1 to 3 PMEM devices (Fig. 4, 4KB I/O, 8 threads)

  1. Sequential write: 1.3 GB/s → 3.7 GB/s (2 dev) → 6.0 GB/s (3 dev).
  2. Ratio, 1→3: 6.0 / 1.3 ≈ 4.6× — on 3× the devices.
  3. Random write: 1.2 → 3.2 → 4.9 GB/s, ratio ≈ 4.1×.
  4. Why super-linear: a single device under 8 concurrent threads is contention-bound; spreading those threads over 3 devices relieves per-device contention, not just adding raw bandwidth.
🧩
This is the paper's own claim (§4.2): "throughput...even exceeds 3× that of a single device...in some cases" — confirmed exactly by the write numbers above.

② Rebalance time vs. data size (Table 1)

  1. 16GB NVPTT, 1→2 devices: 14.95s to rebalance ⇒ 16GB/14.95s ≈ 1.07 GB/s effective rate.
  2. 16GB NVPTT, 1→3 devices: 10.23s ⇒ 16/10.23 ≈ 1.56 GB/s — faster, because more destination devices add bandwidth to the rebalance itself.
  3. 256MB vs. 16GB (1→3): 0.18s vs. 10.23s — roughly linear in data size, as expected for a full traversal-and-redistribute.
💡
Takeaway: rebalancing cost is predictable and bounded by the same bandwidth Vessel is trying to aggregate in the first place — it's not a separate, slow path.

③ Append: 14.9× over RAID-0, ~1% behind mmap

  1. Across I/O sizes 1KB–2MB, Vessel's append throughput is "up to 14.9×" that of MDRAID-0 EXT4 (Fig. 6) — the gap is largest at small I/O sizes, where RAID-0's block-layer overhead dominates per-operation cost.
  2. Against interleaved mmap (the hardware ceiling), Vessel's append throughput is on average only about 1% lower — meaning the lazy page-fault + 2MB-granularity design adds negligible cost versus pre-populated hardware striping.
⚠
Note the asymmetry: Vessel beats RAID-0 by over an order of magnitude but only matches mmap within ~1%. The real engineering win is closing the software gap, not beating hardware.

④ NVPTT addressing range from fan-out arithmetic

  1. PTE level: 512 entries × 4KB pages = 2MB (Level-1 root).
  2. PMD level: 512 × 2MB = 1GB (Level-2 root) — this is the largest a 2-level NVPTT reaches.
  3. PUD/PGD level: 512 × 1GB = 512GB (Level-3 root) — matches the paper's stated "3-level NVPTT can address 512GB" exactly.
  4. Check: 512³ × 4KB = 134,217,728 × 4096B = 549,755,813,888B = 512 GiB. ✓
🧩
The addressing range is a property of tree depth alone, independent of how much physical PMEM capacity actually exists — ptt_level_up grows the tree without touching existing data.
Test yourself

Practice problems

Try each before opening the answer.

1 · easy
CXL supports hot-plugging a PMEM module physically. Does that mean hardware interleaving can now add it without a reboot?
Show answer
No. Hot-plug makes the device physically available at runtime, but joining it to an existing interleave set still requires reprogramming the memory decoders and, per the paper, a full data migration that interrupts service — it's not the same as the old NVDIMM "backup/reboot/restore" cycle, but it's still disruptive.Misconception: physical hot-plug capability implies logical reconfiguration is free. The paper explicitly separates these.
2 · medium
From Fig. 4 (4KB I/O, 8 threads): sequential read goes 5.8 → 12.6 → 18.2 GB/s for 1→2→3 devices. Is this scaling linear, sub-linear, or super-linear, and does it matter which operation you look at?
Show answer
1→3 ratio = 18.2/5.8 ≈ 3.14×, slightly super-linear for reads. But sequential write scales to ≈4.6× (1.3→6.0 GB/s) — more super-linear, because writes are more contention-bound on a single device, so adding devices relieves more contention per write than per read.Misconception: that "3 devices = 3× bandwidth" is the ceiling. Contention relief can push real workloads past the naive linear estimate.
3 · medium
RAID-0 is marketed as "flexible." Why is it also slow for small I/O specifically, rather than slow overall?
Show answer
Block-layer overhead (kernel trap, request queue, indexing) is roughly constant per operation, so it dominates when the I/O itself is small (4KB) and becomes proportionally smaller as I/O size grows (2MB). The paper's Fig. 5/6 data shows the Vessel/RAID-0 gap shrinking as I/O size increases.Misconception: flexibility and performance cost are unrelated axes. Here RAID-0's flexibility mechanism (the block layer) is literally the source of its small-I/O penalty.
4 · hard
At high thread counts, the paper notes MDRAID-0 EXT4 sometimes surpasses Vessel on writes. What's the proposed explanation, and why is it not simply "Vessel has a bug"?
Show answer
The authors speculate that RAID-0's extra software overhead inadvertently throttles concurrent access, partially relieving PMEM write contention under very high concurrency — the "overhead" accidentally acts like a rate limiter. Vessel, being closer to raw hardware, exposes the devices' actual write contention directly.Misconception: more overhead is strictly worse. Under specific high-contention conditions it can coincidentally help — a cautionary, paper-acknowledged exception, not the general rule.
5 · medium
Why is a crash halfway through ptt_rebalance not a correctness problem?
Show answer
Rebalancing only moves existing, valid data between devices. A crash mid-rebalance just leaves some blocks still only on the original device(s) and others already spread across all devices; both states are individually valid and readable, so nothing is corrupted — re-running ptt_rebalance finishes the redistribution. (The bottom-up, crash-safe linking argument is a separate guarantee that applies to page-fault append/allocation, not to rebalance itself.)Misconception: partial migration implies corruption. Here it implies "not yet fully redistributed," which is a performance state, not a correctness one.
6 · medium
Why is NVPTT's stripe size fixed at 4KB (or multiples), rather than something finer?
Show answer
Two independent constraints converge on 4KB: the Linux memory-management subsystem only supports page-table-based mappings at page granularity (4KB or multiples), and Intel Optane's own hardware interleaving granularity is also fixed at 4KB — a design choice balancing performance against PMEM's persistence characteristics. NVPTT inherits both limits.Misconception: that software striping could trivially go finer than hardware. Here the OS page-table mechanism, not just the device, caps the granularity.
7 · hard
The discussion section suggests putting NVPTT copies in DRAM to cut CXL latency. What does this trade away, and does the paper fully resolve it?
Show answer
A DRAM copy of the tree is faster to walk but is, by definition, volatile — so the paper is proposing to accelerate lookups using a structure that isn't the authoritative persistent index anymore. The paper raises this as future mitigation for CXL's higher latency but does not specify a recovery/consistency protocol for rebuilding or trusting a DRAM copy after a crash.Misconception: that this is a solved part of the design. It's explicitly framed as discussion/future work, not a built mechanism — worth flagging rather than assuming it exists.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What problem is Vessel actually solving?▾
Aggregating bandwidth across multiple PMEM devices without choosing between hardware interleaving's rigidity (boot-time fixed) and software RAID-0's overhead (block-layer, loses byte-addressability).
Q2Why use a page table specifically, instead of a custom hash/B-tree index?▾
Because a page table installed into a process's address space is translated by the CPU's own MMU, cached by the TLB, and reached via ordinary load/store — no custom software indexing code runs on the data path. (A TLB miss still triggers a hardware page walk; the win is skipping software indexing, not eliminating translation cost.) A custom index would need to re-implement all of that in software.
Q3If page tables map virtual→physical addresses, how can their leaves be "data blocks"?▾
They still map to physical addresses — those physical addresses just happen to be the interleaved PMEM data blocks themselves, not "ordinary" RAM pages. Structurally it's a normal page table; semantically, the pages it maps are the payload.
Q4Can you really add a PMEM device without rebooting?▾
Yes — vessel_add_pmem registers the device's superblock and grows the pooled capacity immediately; no reboot, BIOS change, or backup/restore cycle is needed, unlike hardware interleaving.
Q5Does adding a device automatically speed up my existing files?▾
No. Existing NVPTTs keep their current data placement until you explicitly call ptt_rebalance on them; only newly created NVPTTs can span the new device from the start.
Q6Why is the stripe size fixed at 4KB?▾
Linux's page-table-based mapping only works at page granularity (4KB or multiples), and that happens to match Optane PMEM's own fixed hardware interleaving granularity — a constraint that may carry over to future CXL-PMEM too.
Q7Does Vessel replace a filesystem like EXT4?▾
Not yet. Vessel is presented as the substrate for a future PMEM filesystem; this paper covers pooling, mapping, and throughput aggregation, not namespaces, POSIX semantics, or crash-consistency guarantees for file metadata.
Q8How close is Vessel to raw hardware interleaving?▾
Within 1.5% on general throughput, and about 1% on average for append throughput specifically — measured against interleaved devdax mmap, the paper's performance ceiling.
Q9Is this Optane-specific, or does it generalize to CXL-PMEM?▾
The design only assumes byte-addressability and persistence, not the DIMM attachment interface, so the authors argue it applies to CXL-attached PMEM — with the caveat that CXL's higher latency and the page-table walk's added latency may need mitigation (TLB caching, or DRAM-resident tree copies).
Q10What's left for future work?▾
Building the full PMEM filesystem on top of Vessel (namespaces, POSIX, crash consistency), exploring cross-NUMA PMEM management, and validating benefits on real-world applications rather than microbenchmarks alone.
