HotStorage 2026 · A Field Guide

Letting the page table do the interleaving, not the BIOS or the block layer

One PMEM device isn't enough bandwidth. Hardware interleaving is fast but frozen at boot; software RAID-0 is flexible but shreds byte-addressability. Vessel turns a page table into a persistent, reconfigurable stripe map.

📄 "PMEM Throughput Aggregation with Non-volatile Page Table Tree" · Guo, Zhang, Yin 🎓 OS/mm background assumed — primers cover the rest ⏱ ~22 min read
🌲

Persist the page table itself so its structure carries the striping, with the MMU/TLB accelerating every lookup — instead of a fixed BIOS map or a block-layer RAID doing it in software.

Before you begin

Quick glossary, then the primers

Acronyms first — skim, don't study. Then eight short primers on the OS mechanisms Vessel repurposes.

NVPTTNon-Volatile Page Table Tree — this paper's persisted radix tree used for striping.
devdaxDevice-DAX — mmaps a raw PMEM region directly, bypassing any filesystem.
RAID-0Striping across devices for bandwidth, no redundancy; mdadm is Linux's software RAID tool.
VMAvm_area_struct — the kernel's record of one contiguous region of a process's virtual address space.
PGD/PUD/PMD/PTEThe four levels of an x86-64 radix page table, top to bottom.
MMU/TLBHardware that walks/caches page-table translations — the acceleration NVPTT piggybacks on.
CXLCompute Express Link — the successor interconnect expected to host next-gen PMEM, with hot-plug.
1Byte-addressable PMEM vs block storage▾

SSDs/HDDs are accessed in blocks through a driver and I/O stack. PMEM sits on the memory bus and is accessed with ordinary load/store instructions — no syscall, no block layer, sub-microsecond latency. Any design that routes PMEM through a block interface (like RAID-0 + a filesystem) throws that advantage away.

Now you're ready: Vessel's whole motivation is keeping accesses on the load/store path while still spanning multiple devices.
2DIMM/BIOS interleaving▾

Like DRAM interleaving, the memory controller round-robins physical addresses across PMEM DIMMs at a fixed granularity (here, 4KB), set once in BIOS at boot. It's transparent and fast, but the device set is frozen — adding a DIMM means backup, reboot, BIOS reconfig, restore.

Now you're ready: this rigidity is exactly what CXL hot-plug makes untenable, and what NVPTT is designed to replace.
3Software RAID-0 (mdadm) and the block layer▾

mdadm stripes a block device across several underlying devices at a chosen chunk size. Every access still goes through the kernel's generic block layer — request queues, interrupts, indexing — even for PMEM, where that overhead dwarfs the actual memory access.

Now you're ready: Fig. 1's order-of-magnitude gap between RAID-0 and hardware interleaving reflects this software overhead — though the paper is also clear that individual PMEM devices' limited bandwidth, and contention among them under high concurrency, remain real hardware limits Vessel still has to work within.
4Radix page tables, PGD→PTE▾

x86-64 translates a virtual address through up to four levels of 512-entry tables: PGD → PUD → PMD → PTE, each entry pointing to the next table (or, at PTE, a 4KB page). It's a fixed-fanout tree, walked in hardware by the MMU and cached in the TLB.

Now you're ready: NVPTT reuses this exact structure — same entry format, same fanout — as a general-purpose persistent radix tree, not just for its usual job of translation.
5VMAs and page faults▾

A VMA (vm_area_struct) records one contiguous virtual range in a process and the handler to call when it's touched. On first access to an unmapped page, a page fault traps into the kernel, which can allocate a physical page and install the mapping on demand.

Now you're ready: Vessel installs a VMA with a custom fault handler so NVPTT physical space is allocated lazily, only as data is actually appended.
6devdax mmap▾

Device-DAX exposes a raw PMEM range as /dev/daxN.M; mmap-ing it maps physical PMEM pages directly into a process's address space with no filesystem, no page cache, no copy. This is the paper's hardware-interleaving baseline — about as direct a software path to PMEM as exists, though not a proven ceiling over every possible access pattern.

Now you're ready: "interleaved devdax mmap" in the results = hardware interleaving accessed via that direct path — the bar Vessel is chasing.
7Crash consistency, briefly▾

Because PMEM survives power loss, a crash mid-update can leave a persistent structure in a torn, half-written state. Correct PMEM systems must ensure any crash point leaves the structure recoverable — often via ordered writes, logging, or, as here, operations that can simply be reexecuted from scratch after a crash.

Now you're ready: this is why Vessel's rebalance can leave data partially rebalanced after a crash — not corrupted — and the paper's fix is just to reexecute ptt_rebalance.
8CXL hot-plug▾

CXL-attached memory devices can be added to a running system without a reboot, unlike DIMM-attached PMEM. But hardware interleaving still needs the memory controller's address decoders reprogrammed — which typically forces a full data migration to keep addresses consistent.

Now you're ready: Vessel's argument is that software-level (NVPTT) reconfiguration can sidestep that forced migration — directly relevant if your CXL tiering work ever needs to grow a pool online.
The whole story in one place

Vessel in a nutshell

The trade-off, the fix, and why a page table is the right data structure for it.

A single PMEM module's bandwidth is a bottleneck, so servers aggregate several. Hardware interleaving stripes physical addresses across DIMMs at boot — fast, but the device set is fixed until the next reboot and BIOS reconfig. Software RAID-0 (mdadm + a filesystem) can add or remove devices, but routes every access through the kernel block layer, erasing PMEM's load/store advantage — up to an order of magnitude slower.

Vessel breaks this trade-off by persisting the mapping structure itself. Its core data structure, the Non-Volatile Page Table Tree (NVPTT), is a radix tree with exactly the on-disk layout of a normal x86-64 page table (PGD/PUD/PMD/PTE), but stored in PMEM and installable directly into a process's virtual address space. Once installed, the MMU and TLB do the translation work for free — applications read and write via ordinary load/store, with no user-kernel transition. NVPTT's leaf entries are data blocks that a separate space-management layer allocates interleaved across all managed PMEM devices, so the tree's structure doubles as a stripe map.

Because it's software, the stripe map can change: vessel_add_pmem adds a device online, and ptt_rebalance redistributes an existing tree's blocks across the new device set — no reboot, no BIOS. The payoff: up to 14.9× higher append throughput than mdadm RAID-0 EXT4, while staying within 1.5% of hardware-interleaved devdax mmap.

🍯 Key takeaways

  • Hardware interleaving = fast, frozen at boot. RAID-0 = flexible, block-layer overhead kills byte-addressability.
  • NVPTT reuses the literal page-table layout as a persistent radix tree — MMU/TLB accelerate it for free.
  • Leaf blocks are allocated interleaved across devices; metadata/tree nodes use plain round-robin.
  • Append allocates a whole PTE range (2MB) per fault, not one 4KB page, to amortize fault overhead.
  • ptt_rebalance redistributes data after adding a device; a crash mid-rebalance is safely re-runnable.
  • Result: ≤1.5% behind hardware interleaving, up to 14.9× faster append than RAID-0 EXT4.
Five everyday pictures

How to think about Vessel

Each stands alone. Every card ends with where the picture breaks down.

The core idea · NVPTT

A building directory that's also the mail slots

Normally a lobby directory just tells you which floor a tenant is on — a separate index. NVPTT makes the directory be the mail slots: the same radix structure the MMU already walks for translation holds the actual data pointers, striped across three mail rooms (PMEM devices) round the corner.

Where it breaks: a real directory doesn't need crash consistency; NVPTT's bottom-up construction order exists specifically so a half-built branch is never linked in and read.
Why RAID-0 is slow · Block layer

A courier who repacks every parcel at a depot

You hand a parcel straight to a neighbor (load/store) — fast. Route it through a courier depot instead (the block layer) and every parcel gets queued, re-labeled, and dispatched, even for a next-door delivery. mdadm RAID-0 forces exactly this detour onto every PMEM access.

Where it breaks: a real depot adds latency but not necessarily throughput loss at scale; the paper shows RAID-0's gap does narrow at high concurrency and large I/O, where the "depot" overhead better amortizes.
Why HW interleave is rigid · Boot-time map

A seating chart printed before the guests arrive

BIOS-configured interleaving is a seating chart fixed and printed at boot. It works great for the guests it was made for, but a latecomer (a new PMEM device) can't be seated without reprinting the chart — backing up, rebooting, reconfiguring BIOS, restoring.

Where it breaks: CXL hot-plug can reprogram decoders live, but the paper notes this still typically forces a full data migration — closer to "reseat everyone" than "add a chair."
Rebalance semantics · Deferred, re-runnable

Reshelving a library while it stays open

Add a new bookcase (PMEM device) and you don't need to freeze the whole library to use it — existing books stay findable on their old shelves. Reshelving (ptt_rebalance) can happen whenever convenient, and if a crash interrupts it partway, the librarian doesn't have to untangle what moved — just start the reshelving over and it finishes correctly.

Where it breaks: a real library reader tolerates a book being in transit; Vessel must lock the NVPTT during its own rebalance to keep concurrent readers consistent — the "library" isn't open to that one shelf mid-move.
Two allocators · RR vs interleaved

Dealing cards two different ways

Dealing a deck round-robin, one card per player, is simple and fair — that's how Vessel places tree nodes and metadata (Round-Robin Block Allocator). But for data blocks, Vessel deals by a fixed formula keyed to logical index instead (Interleaved Block Allocator), so writes land evenly across every managed device rather than clustering. Either way, a block is later found the same way — by walking the installed NVPTT itself, not by re-deriving its device from the allocator.

Where it breaks: round-robin dealing has no notion of "which card is this" — fine for metadata nobody stripes deliberately, wrong for data blocks, which need balanced placement across devices for aggregate bandwidth.
The full explanation

How it actually works

Section by section, with the paper's structural figures rebuilt as diagrams.

1 · The trade-off, measured

Fig. 1 of the paper compares EXT4 sequential read/write on a single PMEM, three PMEM with hardware interleaving, and three PMEM with mdadm RAID-0. Interleaving scales throughput roughly linearly with device count; RAID-0 trails it by close to an order of magnitude across thread counts — strong evidence that RAID-0's block-layer overhead is a major bottleneck. The paper doesn't treat this as the only one, though: it also emphasizes a single PMEM device's limited raw bandwidth, and contention among devices at high concurrency, as real hardware limits Vessel still has to contend with.

2 · Multi-level addressing, page-fault-based append

Each NVPTT level adds one radix table, extending the addressable range 512× (a table has 512 entries): level-1 (PTE only) covers 2MB; level-2 (+PMD) covers 1GB; level-3 (+PUD) covers 512GB. ptt_level_up grows an existing tree without disturbing its current data.

A new NVPTT allocates no physical space upfront. The first touch to a page triggers a fault, and Vessel allocates the entire PTE range it belongs to — 2MB, not 4KB — so a burst of sequential appends amortizes the fault cost across 512 pages instead of paying it per page.

3 · Two allocators, one purpose

Data blocks use the Interleaved Block Allocator: device = f(logical block index), so blocks are spread evenly across every managed device for balanced striping bandwidth. This governs where a block is placed, not how it's later found — lookup for both data blocks and tree nodes works the same way, by walking the installed NVPTT and following its page-table entries via the MMU. NVPTT nodes and metadata use the simpler Round-Robin Block Allocator, since their placement doesn't need to follow any striping pattern.

4 · API and rebalance semantics

vessel_add_pmem(addr, size)         # online; init'd via superblock check
vessel_new_ptt(level) → id
vessel_ptt_map(id) → vaddr           # installs NVPTT as the process's page table
ptt_rebalance(id)                     # locks id; redistributes blocks over ALL devices
ptt_level_up(id)                      # grow addressable range, data untouched
💡
Why is rebalance optional, not automatic? Existing data stays fully accessible on the original devices without it — Vessel doesn't require migrating everything the instant a device is added. Rebalance can be deferred per file until it's idle, so adding capacity never has to stall live workloads.
⚠
Crash mid-rebalance leaves some blocks on the old device set and some redistributed. The paper notes this doesn't corrupt the NVPTT — it's still fully valid, just partially rebalanced — and simply re-running ptt_rebalance finishes the job.
Follow the numbers

Worked examples

Three traces through the paper's real figures and tables.

① Why level-2 caps at 1GB and level-3 at 512GB

Each radix table has 512 entries (standard x86-64 fanout), and a page is 4KB. Verify the paper's stated ranges.

  1. Level-1 (PTE only): 512 entries × 4KB/page = 2MB — matches Fig. 2's "Level 1 Root, 2MB."
  2. Level-2 (adds PMD): one PMD entry points to a full PTE table, so 512 × 2MB = 1GB — matches "Level 2 Root, 1GB," and the paper's statement that a level-2 tree can't hold more than 1GB.
  3. Level-3 (adds PUD): 512 × 1GB = 512GB — matches "Level 3 Root, 512GB," which is why the rebalance experiment (Table 1, up to 16GB) uses a level-3 tree.
🍯
Insight: the addressing range is purely a property of tree depth, independent of how much physical PMEM is actually attached — choose the level for your data size, not your device count.

② Super-linear scaling with device count (Fig. 4, 4KB I/O, 8 threads)

Sequential read: 5.8 GB/s (1 device) → 12.6 GB/s (2) → 18.2 GB/s (3). Is this linear?

  1. 2 devices: 12.6 / 5.8 = 2.17× — already above the "expected" 2×.
  2. 3 devices: 18.2 / 5.8 = 3.14× — above 3× linear scaling.
  3. Write shows the same pattern, more sharply: 1.3 → 3.7 → 6.0 GB/s is 2.85× then 4.6× the single-device number.
  4. Why super-linear: the paper attributes this to reduced per-device contention — spreading concurrent accesses across more devices means each device individually serves fewer competing requests.
💡
For tiering work: this is a reminder that per-device PMEM bandwidth figures from isolated microbenchmarks can understate real aggregate throughput once contention is spread across a pool.

③ What rebalance actually costs (Table 1)

Rebalancing a 16GB level-3 NVPTT takes 14.95s (1→2 devices) or 10.23s (1→3 devices). How fast is that, really?

  1. 1→2 devices: 16GB / 14.95s ≈ 1.07 GB/s effective migration bandwidth.
  2. 1→3 devices: 16GB / 10.23s ≈ 1.56 GB/s — faster, because more destination devices absorb the writes in parallel.
  3. Compare to peak: 3-device sequential read alone hits 18.2 GB/s (Fig. 4) — rebalance runs at roughly 1/12th of peak bulk throughput.
  4. Why the gap: rebalance isn't pure sequential copy — it walks the tree, reads each block, recomputes its new interleaved location, and writes it back with metadata updates per block, which is inherently more overhead than a streaming copy.
🍯
Insight: rebalance cost scales with data size, not device size — this is why the paper recommends deferring it until a file is idle rather than treating device-add as a synchronous operation.
Test yourself

Practice problems

Try each before opening the answer — every one names the misconception it checks.

Problem 1 · easy
A colleague says "just use RAID-0, it's more flexible than hardware interleaving anyway." What's missing from that recommendation?
Show answer
Flexibility isn't the only axis — RAID-0 routes every access through the block layer, costing up to an order of magnitude of throughput (Fig. 1) and destroying byte-addressable mmap access. Vessel's whole point is that you shouldn't have to trade one for the other.Misconception: treating flexibility and performance as independent, when the paper's core observation is that existing approaches force a choice between them.
Problem 2 · medium
You need to address 3GB of data. What's the minimum NVPTT level, and why not the smaller one?
Show answer
Level-3 (512GB range). Level-2 tops out at 1GB (512 PTE-table entries × 2MB each), so 3GB exceeds it — you'd need to add a PUD level (level-3) even though 3GB is far below 512GB, because addressing range depends on tree depth, not how much data you actually plan to store.Misconception: assuming level should be sized to exactly fit the data. It's sized to the next power-of-512 addressing boundary; there's no "level 2.5."
Problem 3 · medium
Why does Vessel allocate a full 2MB (one PTE range) on the first page fault of an append, instead of just the 4KB page that was touched?
Show answer
Sequential appends are the common case, and page faults trap into the kernel — expensive relative to a memory access. Allocating the whole PTE range up front means the next 511 pages in that range are already mapped, so only 1-in-512 accesses pays the fault cost instead of every access.Misconception: assuming lazy allocation always means "as small as possible." Here laziness (deferred until first touch) is combined with batching (2MB per fault) — two separate design choices.
Problem 4 · hard
A crash happens exactly halfway through ptt_rebalance. What state is the NVPTT in, and why doesn't this corrupt it?
Show answer
Some data blocks have been moved to the new interleaved layout spanning all devices; the rest are still on the original device(s). The paper treats this as valid, not corrupt — just partially rebalanced — and its fix is simply to re-run ptt_rebalance, which redistributes the tree to completion.Misconception: assuming a partially-completed migration is automatically corrupted. The paper doesn't claim every block's location is separately tracked mid-move; it claims re-executing the operation resolves the partial state safely.
Problem 5 · medium
Why do NVPTT tree nodes use the Round-Robin allocator while data blocks use the Interleaved allocator?
Show answer
Data blocks are addressed by logical block index, and the Interleaved allocator places each one across devices as a function of that index — necessary for balanced striping bandwidth, not for lookup: a block is still found by walking the installed NVPTT and its page-table entries, same as any tree node. Tree nodes (PGD/PUD/PMD/PTE entries) don't need to follow any striping pattern, so plain round-robin balancing is sufficient and simpler.Misconception: assuming one allocator would be simpler and should be used everywhere, or that the Interleaved allocator is what makes a block "findable." The two allocators only decide placement; addressing/lookup work is the tree's job, done identically for both.
Problem 6 · hard
At high thread counts, some write workloads show MDRAID-0 EXT4 catching up to or beating Vessel. What's the paper's speculated explanation, and what does it imply about Vessel's design?
Show answer
The paper speculates that RAID-0/EXT4's extra software overhead — the very thing that hurts it at low concurrency — incidentally throttles concurrent access enough to partially relieve PMEM contention at high thread counts, where Vessel's more direct path lets more concurrent writers contend on the device itself. It implies Vessel's advantage is largest precisely where PMEM isn't yet contention-bound — i.e., low-to-moderate concurrency.Misconception: assuming a faster path is strictly better at every concurrency level. Removing overhead can also remove incidental throttling, which matters once the underlying device becomes the real bottleneck.
Quick answers

Frequently asked questions

Q1Is NVPTT literally the process's real page table?▾
Yes — it's installed into the process's virtual address space with the same entry format as a normal page table, so the MMU walks it and the TLB caches its translations exactly as it would for any other mapping. That's the source of the "hardware acceleration" claim.
Q2Does Vessel replace the filesystem?▾
Not yet — the paper positions Vessel as a substrate. Future work is a full PMEM filesystem built on top, adding namespace management, POSIX interfaces, and crash-consistency guarantees beyond what NVPTT alone provides.
Q3Why is stripe granularity fixed at 4KB (page-size multiples)?▾
Linux memory management operates at page granularity, so NVPTT's stripe unit is bound to 4KB or multiples of it — finer striping isn't representable in this page-table-based scheme. The paper notes this is a practical, not severe, limitation since Optane's own hardware interleaving is also fixed at 4KB.
Q4Can devices of different sizes be mixed?▾
Yes. The symmetric layout (superblock + bitmap + data region) is per-device, so heterogeneous sizes are supported natively — each device just has a differently sized data region.
Q5What happens to existing NVPTTs when a device is added but not rebalanced?▾
They keep working exactly as before, fully accessible on their original device set. Only newly created NVPTTs (or ones explicitly rebalanced) span the new device — adding capacity never forces an interruption to existing data.
Q6Does Vessel work over CXL, or only DIMM-attached PMEM?▾
The paper only evaluates DIMM-attached Optane, but argues the design depends only on byte-addressability and persistence, not the attachment interface — so it should extend to CXL-attached PMEM, with TLB caching and optionally DRAM-resident page-table copies mitigating CXL's extra latency.
Q7How does this compare to CXL hardware cross-NUMA interleaving?▾
Hardware NUMA interleaving over CXL can aggregate more devices for bandwidth but adds latency to every access. The paper suggests NVPTT could let this be a per-file choice — striping bandwidth-hungry files across NUMA nodes while keeping latency-sensitive files node-local — rather than an all-or-nothing system setting.
Q8Why not just use mdadm with a PMEM-aware block driver instead?▾
The paper notes no PMEM-specific software RAID-0 implementation exists, and used generic mdadm as the closest available baseline. The deeper issue is architectural: any block-layer-based RAID, PMEM-aware or not, still forces accesses through request queues and indexing rather than direct load/store — the mechanism NVPTT avoids by construction.
