SOSP 2026 · A Field Guide

Sharing the weights that are already the same, not throwing every model into one blender

A GPU can only hold so many fine-tuned models. Merge them all into one and accuracy collapses; keep them all separate and you run out of memory. This is the plain-English story of SANDHI, a system that finds the pieces safe to share.

📄 "SANDHI" · Gupta, Duran, Meda, An, Ananthanarayanan, Iyer 🎓 LoRA/serving basics assumed — the primers cover them ⏱ ~30 min read
🧩

Share a component across models only when it TOLERATES being replaced — not because every model HAS one at that layer.
Measure tolerance per component, then merge incrementally, checking as you go.

1Fine-tuning and why deployments need many models▾

A base model is generic. Fine-tuning continues training it on a specific task (medicine, legal advice, code) so it performs better on that task than the base model does. Because different tasks need different fine-tunes, and applications increasingly chain several specialized models together (a "compound AI system"), a single deployment often needs to host many fine-tuned variants at once — not just one.

Now you're ready: SANDHI's whole premise is that hosting five, ten, or twelve fine-tuned models concurrently is now normal, not exotic — and that's what strains GPU memory.
2Why GPU memory is the bottleneck▾

Every hosted model consumes two kinds of GPU memory: a fixed amount for its weights (the checkpoint), and a variable, growing amount for its KV cache — the keys/values cached per in-flight request, which scales with batch size and sequence length. Once weights + KV cache saturate the GPU, you can't add more concurrent requests (throughput stalls) or more models (coverage stalls) without buying more GPUs.

Now you're ready: any memory freed by merging weights doesn't just sit idle — it converts directly into more KV cache headroom, i.e. bigger batches.
3LoRA: the popular fix, and its fine print▾

LoRA stores one shared base model plus a small low-rank "adapter" per fine-tuned variant, cutting per-model memory dramatically. But it has three requirements: (1) all served models must share the exact same base architecture/version/size; (2) building a good adapter needs the original fine-tuning data and rank tuning; (3) efficient batched adapter math needs uniform adapter configs across models. Cross-family deployments (Llama + Qwen + DeepSeek) violate requirement 1 outright.

Now you're ready: SANDHI is designed for exactly the deployments LoRA can't serve — different families, different sizes, no training data — and also stacks on top of LoRA where it does apply.
4What a decoder layer is made of▾

A transformer decoder is a stack of identical-looking layers. Each layer has two blocks: attention (computes how tokens relate to each other) and an MLP (a feed-forward network that encodes task-specific knowledge). Fine-tuning changes these two blocks differently — a task might reshape the MLP's knowledge heavily while barely touching attention, or vice versa.

Now you're ready: this is why SANDHI decides mergeability per component (attention vs. MLP), not per whole layer — treating them the same wastes savings or accuracy.
5Model merging, the traditional ML sense▾

Outside of serving, "merging" combines multiple fine-tuned models' parameters (e.g. by weighted averaging, or via SLERP/task-vector composition) into one model that inherits several models' skills — useful when you want a single generalist checkpoint. It assumes you're happy losing each model's separate identity.

Now you're ready: serving needs the opposite guarantee — every model must keep behaving like itself. SANDHI repurposes merging machinery but only applies it where it won't change any model's outputs enough to matter.
6GQA vs MHA and why it matters for batch size▾

Multi-Head Attention (MHA) stores a full set of keys/values per attention head. Grouped-Query Attention (GQA) shares keys/values across groups of heads, shrinking the KV cache per token substantially. That means for GQA models, freeing the same amount of weight memory buys proportionally more KV cache room — and therefore a bigger batch-size gain — than for MHA models.

Now you're ready: this is why the paper's Figure 1 shows Qwen (GQA) gaining far more batch size from merging than DeepSeek-7B (MHA) for the same fraction of layers shared.
7Combinatorial explosion, briefly▾

If you must decide, independently, whether to merge each of many components, the number of possible configurations grows as 2 raised to the number of components — exponentially. Across many model pairs, that exponential multiplies again. Trying every configuration exhaustively becomes impossible almost immediately.

Now you're ready: SANDHI's whole design (profiler → clustering → incremental merge) exists specifically to avoid ever searching this space exhaustively.
8Accuracy evaluation harnesses▾

To know whether a merge is "safe," you need to score the resulting model on a task-appropriate benchmark (e.g. GSM8K for math, HumanEval for code, MedQA for medical) and compare against a threshold. SANDHI uses a standard evaluation harness to score models automatically after each candidate merge step.

Now you're ready: "accuracy bound ρ" in the paper is exactly this — a user-set threshold on this per-task score that no merged variant may cross.
9CUDA Virtual Memory Management (a Linux mm-flavored idea)▾

Normally, each GPU process (each vLLM instance) owns its own private copy of every tensor. CUDA's VMM APIs let you allocate physical GPU memory once and map that same physical memory into multiple virtual address spaces — conceptually the same trick as memory-mapped shared libraries, or page sharing across processes on the CPU side.

Now you're ready: SANDHI uses VMM to keep exactly one physical copy of a shared merged component while multiple vLLM engines each see it in their own address space — without modifying vLLM's scheduler, kernels, or execution logic (though the implementation still required roughly 500 lines of changes to vLLM for the weight-manipulation plumbing itself).
The whole story in one place

SANDHI in a nutshell

The problem, the cheap per-model signal that fixes it, and how the pieces connect.

Serving several fine-tuned models on one GPU is bounded by memory: every model's weights plus its KV cache must fit. LoRA helps when all models share one base — but cross-family, cross-version, or data-unavailable deployments can't use it. The obvious alternative, full model merging, collapses accuracy by 20–80% on specialized tasks because fine-tuning-induced incompatibilities compound across every merged layer.

SANDHI's fix is selective, component-level merging: identify exactly which attention or MLP blocks tolerate being shared, and merge only those — one at a time, checking accuracy after each step. To find candidates cheaply, SANDHI's Gaussian noise profiler replaces one component with distribution-matched random noise and measures the resulting accuracy drop, entirely per-model — no pairwise comparison across the whole pool required. Candidates are then clustered by parameter-magnitude similarity and merged incrementally by MICR (Merge-Incrementally-Check-Rollback), which accepts a merge only if accuracy stays within a user-set bound, rolling back otherwise. The result isn't one merged model but a family of variants along an accuracy–memory frontier.

At runtime, a workload-aware selector picks which variant to run, spending freed memory on bigger KV cache (throughput), fewer GPUs (cost), or better accuracy — and swaps between variants using CUDA VMM weight-sharing: fetching happens off the request path, old requests drain on their current instances, and the final pointer rebind is a short atomic step, so P99 TTFT/TPOT stays within 2% of baseline rather than requests being blocked outright.

The payoff: across 12 models spanning 3 families and 9 benchmarks, SANDHI reduces GPU memory footprint by 26.7%–49.8%, improving throughput by up to 2.93× (1.28× average), cutting P95 TTFT by up to 1050× (138× average), and halving infrastructure cost — while accuracy often improves (up to +1.9% on Qwen-32B), unlike LoRA (up to 7.4% drop on Llama, up to 59% drop on Qwen-32B) or full-merge (20–80% drops) — and note LoRA and full-merge are only usable within a shared-base/common-family pool to begin with, unlike SANDHI.

🍯 Key takeaways

  • LoRA needs a shared base model, training data, and uniform adapter ranks — SANDHI needs none of these.
  • Full-merge (all layers, one model) collapses accuracy 20–80% on specialized tasks; the fix is selective, per-component merging.
  • A Gaussian noise profiler scores each component's mergeability per model, in isolation — no pairwise search.
  • MICR clusters compatible components and merges incrementally, validating and rolling back as needed.
  • The output is a frontier of variants, not one model — a workload-aware runtime picks the operating point.
  • Freed memory is fungible: bigger KV cache (throughput), fewer GPUs (cost), or accuracy — depending on load.
  • Result: 26.7%–49.8% memory saved, up to 2.93× throughput, up to 1050× lower TTFT, up to 2× cheaper.
Six everyday pictures

How to think about SANDHI

Each stands alone — read in any order. Every card ends with where the picture stops being true.

Full-merge vs selective · The crux

Blending two smoothies into one

Pour a medical-expert model and a legal-expert model into one blender (full-merge) and you get a single, muddled drink that's mediocre at both. SANDHI instead pours out only the identical ingredients both smoothies already share — leaving each recipe's distinctive parts untouched — so both models keep tasting like themselves while the shared ingredients are bought once.

Where it breaks: smoothies have no notion of "this ingredient happens to be safe to share but that one isn't" — SANDHI's whole engineering effort is exactly measuring that distinction per ingredient (component).
The profiler · Testing with a dummy

The crash-test dummy

To learn how badly a car door failure would hurt a driver, you don't crash real people — you swap in a dummy matched to human weight and size, then measure the damage. SANDHI's profiler does the same to a model component: swap it for random Gaussian noise matched to its own weight magnitude distribution, then measure the accuracy drop. A component that "survives" the dummy swap is a strong candidate to share.

Where it breaks: a crash-test dummy can't stand in for every possible passenger; likewise, the noise profiler is a proxy, not a guarantee — which is exactly why MICR still validates real accuracy after every actual merge, ready to roll back.
Component granularity · Two different jobs

The receptionist and the specialist

In an office, the receptionist (attention) routes and relates incoming requests to the right place — that role looks similar wherever you go. The specialist (MLP) holds the task-specific expertise. Swap receptionists between two offices and little changes; swap specialists and you swap the actual expertise. Treating both roles identically — either always swappable or never — either misses free savings or breaks something important.

Where it breaks: the split isn't always this clean in practice — some tasks reshape attention heavily too — which is why SANDHI measures each component per model rather than assuming the analogy always holds.
MICR · Incremental, reversible steps

Renovating one wall at a time

A contractor removing walls to open up a house doesn't tear out everything and then check if the roof still stands — they remove one wall, verify structural integrity, and only then move to the next. If a wall turns out structural, they put it back and try a different one. MICR merges one component cluster, evaluates the model, and either keeps the merge or reverts it — building up a house (model) that's more open (memory-efficient) without ever collapsing.

Where it breaks: a contractor's checks are usually visual; MICR's "structural check" is a full accuracy evaluation on real benchmarks, which is why it's run sparingly (only when adding a model), not per request.
CUDA VMM · One copy, many mappings

A shared library, GPU edition

On a CPU, multiple processes running the same program don't each get a private copy of libc in physical RAM — the OS maps one physical copy into each process's virtual address space. SANDHI's CUDA VMM weight-sharing does the GPU equivalent: a merged component lives once in physical GPU memory, mapped into every vLLM engine's own address space, so the engines never even notice they're sharing.

Where it breaks: shared libraries are usually read-only and version-locked forever; SANDHI's shared components can be atomically re-pointed to a different merged variant at runtime — closer to remapping a page than to a static shared object.
Runtime navigation · Two speeds, two jobs

A thermostat with a long memory

A responsive thermostat reacts to every door opening (a fast autoscaler handling request-rate spikes). But a separate, slower-moving policy decides whether the whole building's usage pattern has genuinely shifted — say, from a daytime office to an evening event space — and only then reconfigures the HVAC zoning. SANDHI's variant selector is the slow policy: it tracks per-model request-rate mix over a 10-minute window and only swaps merged configurations when the mix drifts by more than a set threshold, leaving spike-handling to the ordinary autoscaler.

Where it breaks: a thermostat's reconfiguration is usually instantaneous; SANDHI's swap involves fetching weights off the critical path and an atomic pointer rebind — closer to a phased HVAC changeover than an instant switch.
The full explanation

How it actually works

Section by section, following the paper's three techniques.

1 · The problem — full-merge collapses, LoRA doesn't always apply

Naively averaging or SLERP-merging every layer of two fine-tuned models produces a single checkpoint, but fine-tuning-induced incompatibilities compound layer after layer: the paper reports 20–80% accuracy drops on specialized benchmarks from full-merge. LoRA avoids this by keeping models mostly separate, but only works when every served model shares one exact base architecture, version, and size — ruling out cross-family and cross-version pools.

🌱
The gap SANDHI fills: deployments that mix Llama, Qwen, and DeepSeek variants of different sizes, with no access to original fine-tuning data — a large and growing class LoRA structurally cannot serve.

2 · The Gaussian noise profiler (Challenge 1)

Existing importance signals — cosine similarity to the base model, Fisher information — show too little variation across layers to reliably guide merging (Fig. 2), and they require comparing model pairs directly, which doesn't scale. SANDHI's fix: for each weight matrix in a component, generate Gaussian noise matched to that matrix's own mean and standard deviation, average it in with the real weights, then measure the accuracy drop on that model alone.

# per component, per model — no pairwise comparison needed
noise = Gaussian(mean=W.mean(), std=W.std(), shape=W.shape)
W_shadow = (W + noise) / 2
accuracy_drop = eval(model_with(W_shadow)) − eval(model)   ← the mergeability signal

This is run separately for attention and MLP because their magnitude distributions can differ substantially within the same layer — a single layer-level signal would hide that difference, causing missed savings or unnecessary accuracy loss.

💡
Why noise, not a real second model? A signal computed against noise is a property of the model alone — it doesn't change if you add a 13th model to the pool. That's what lets SANDHI add models incrementally without recomputing pairwise comparisons across everyone already hosted.

3 · Clustering, scheduling, and the scaler (Challenge 2)

For a pair of 32-layer models with 2 components per layer, independently deciding merge-or-keep for every component yields 264 configurations per pair; across 10 models that's 45 pairs × 264 — intractable to search. SANDHI avoids search entirely: it groups components into parameter-sharing clusters using hierarchical (Ward-linkage) clustering on magnitude distributions, separately for attention sub-components (q/k/v/o) and MLP projections of matching dimension.

Three ordering rules then decide the merge schedule:

  1. Space out merges. Never merge adjacent layers (or components in the same block) back-to-back — residual connections would let perturbations compound before the network can absorb them.
  2. MLP before attention. MLP blocks hold far more parameters (Table 1: up to ~6.9× an attention block's size), so merging them first captures the bulk of the memory savings early.
  3. Middle layers before boundary layers. Input- and output-adjacent layers are known to matter disproportionately for accuracy, so their merges are deferred until late.

For cross-family pairs especially, large magnitude mismatches cause hidden-state scale shifts that take ~10 layers to dissipate — by which point accuracy is often already hurt. SANDHI inserts a lightweight scaler at each merged component's output to keep hidden-state scales consistent. The paper's scaler ablation actually uses DeepSeek-Coder + DeepSeek-Math — two fine-tunes of the same DeepSeek-7B base, so a same-family pair — and shows the scaler still helps there, demonstrating its value for both homogeneous and heterogeneous pools; without it, cross-family pairs in particular can end up with no valid merged variant at all.

4 · Runtime navigation (Challenge 3)

Freed memory is fungible — spend it on more KV cache (throughput), more hosted models (coverage), or claw it back for accuracy. SANDHI tracks each model's request rate with an exponential moving average and only reconsiders its operating point when the traffic mix drifts: if the total-variation distance between old and new per-model rate distributions exceeds 0.2 over a 10-minute window, it triggers a variant swap. This multi-minute window deliberately filters out short spikes, which a conventional autoscaler already handles.

# every 10-minute window
if total_variation_distance(rate_now, rate_baseline) > 0.2:
    new_variant = select_from_frontier(kv_capacity, rate_now)  # stays within ρ
    launch_new_instances(reuse_current_weights=True)
    fetch(new_variant.changed_components)   # off critical path, ~31ms
    drain(old_instances)
    atomically_rebind(new_variant)          # ~0.61ms pointer swap
🍯
Never violates the accuracy bound: because the runtime only ever selects among MICR-pre-validated variants, every operating point it can move to has already passed the accuracy check — swapping only trades among already-safe options.
Follow the numbers, step by step

Worked examples

Four traces using the paper's real figures — the search-space explosion, memory-to-batch conversion, GPU-count savings, and a throughput divergence curve.

① Just how big is the merge search space?

10 models, 32 layers each, 2 components per layer (attention, MLP). How many possible pairwise merge configurations exist in total?

  1. Components per pair: c·L = 2 × 32 = 64 independent merge-or-keep decisions.
  2. Configurations per pair: 264 ≈ 1.8 × 1019 — each of the 64 decisions doubles the space.
  3. Number of pairs among 10 models: C(10,2) = (10×9)/2 = 45.
  4. Total: 45 × 264 ≈ 8.3 × 1020 possible configurations — as the paper states, "rendering exhaustive search intractable."
  5. Sanity-check the paper's other framing: restricting to whole-layer decisions only (1 decision per layer, not 2) for a single pair of 32-layer models gives 232 ≈ 4.3 billion — matching the paper's separately-stated "up to four billion possible configurations" for that coarser granularity.
🍯
Insight: whichever granularity you count at, the space is far too large to search — which is exactly why SANDHI never searches it, relying instead on the noise profiler plus clustering to propose a short, ordered schedule.

② From freed weight memory to extra KV cache capacity

Using Table 1: Llama-3.1-8B's MLP block is 336 MiB, and its KV cache costs 128 KiB per token. If SANDHI merges one Llama-3.1-8B MLP block across two co-located Llama models, how much extra token capacity does that free?

  1. Memory freed: merging means one model's 336 MiB MLP is now shared, not duplicated — freeing 336 MiB that was previously a second private copy.
  2. Convert to tokens of KV cache: 336 MiB ÷ 128 KiB/token = 336×1024 KiB ÷ 128 KiB ≈ 2,688 tokens worth of extra KV cache capacity.
  3. Convert to requests: at ~1,000 tokens/request (the paper's evaluation workload mean), that's roughly 2.7 more concurrent requests' worth of KV cache headroom — from a single MLP block.
  4. Scale up: this is why merging even "a small fraction of layers" (the paper's own framing) is enough to noticeably raise achievable batch size in Fig. 1.
💡
This is the mechanical link between §2.2's claim and Fig. 1's chart: weight memory and KV-cache memory are fungible, and the exchange rate is set by each model's per-token KV cache footprint (Table 1).

③ Halving GPU count for three Qwen3-32B models

Each Qwen3-32B checkpoint is 65.5 GB in bf16 (Table 2). An H200 GPU has 141 GB of HBM. Does independent serving of three copies fit on one GPU? Does SANDHI's 49.8% saving change that?

  1. Independent footprint: 3 × 65.5 GB = 196.5 GB of weights alone.
  2. Fits on 1×H200 (141 GB)? No — 196.5 GB > 141 GB, so independent serving needs 2×H200 (282 GB capacity) just to hold the weights, before any KV cache.
  3. Apply SANDHI's 49.8% reduction: 196.5 GB × (1 − 0.498) ≈ 98.6 GB.
  4. Fits on 1×H200 now? Yes — 98.6 GB < 141 GB, leaving ~42 GB free for KV cache on a single GPU.
  5. Result: the deployment drops from 2 GPUs to 1 — exactly the paper's claim that this configuration "halves the infrastructure cost while maintaining serving capacity."
🍯
Insight: memory savings don't need to be spent on KV cache to matter — crossing a GPU-count threshold is often the single biggest cost lever available.

④ Where baseline throughput saturates and SANDHI doesn't

In the 9-model deployment (Fig. 6e), DeepSeek-7B's baseline throughput plateaus at ~1000 tok/s even at 2 RPS, while SANDHI reaches ~3000 tok/s at the same request rate. Confirm the reported 2.93× figure and explain the mechanism.

  1. Ratio: 3000 ÷ 1024 ≈ 2.93× — matches the paper's reported improvement exactly.
  2. Why baseline plateaus so early: DeepSeek-7B's MHA architecture has the largest per-token KV cache in the study (480 KiB/token, Table 1) — its available KV cache memory saturates at very low request rates, so extra requests simply queue.
  3. Why SANDHI keeps scaling: the memory SANDHI frees by merging shared components is added directly to KV cache capacity, pushing the saturation point to a higher request rate.
  4. Compounding effect on latency: once baseline saturates, every additional request waits in queue, so P95 TTFT degrades far faster than throughput does — which is why the paper reports the TTFT improvement (~1052×) as even larger than the throughput improvement (2.93×) for this exact model.
💡
Models with the largest per-token KV cache (highest "demand" for cache) benefit most from SANDHI's freed memory — mirroring how memory-tiering systems prioritize relief for whichever workload is most cache-starved.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
A team wants to co-serve a Llama-3.1-8B fine-tune and a Qwen2.5-7B fine-tune using LoRA to save memory. Will this work?
Show answer
No. LoRA adapters are trained as residuals on a specific base model's weights — applying a Llama-trained adapter to a Qwen base (or vice versa) produces undefined behavior, because the two models don't even share an architecture or base checkpoint. This is exactly the cross-family case SANDHI targets instead.Misconception: that LoRA is a general memory-saving technique for "any fine-tuned models." It specifically requires all served models to share one identical base.
Problem 2 · medium
Why doesn't SANDHI just use "Multi-SLERP" (full-merge across all layers) and skip the profiler and MICR entirely?
Show answer
Full-merge treats every layer as equally safe to share, but fine-tuning concentrates task-specific knowledge unevenly across layers and components. Merging layers that actually matter compounds errors through the residual stream, causing the 20–80% accuracy drops the paper reports for full-merge. Selective merging is needed precisely because "mergeable" and "exists at that layer" are different properties.Misconception: that more merging is strictly better for memory with only a graceful accuracy cost. In practice it's a cliff, not a gradient, once you cross into task-critical layers.
Problem 3 · medium
The profiler perturbs a component with noise matched to that component's own magnitude distribution, rather than comparing it directly to the corresponding component in another model. Why is that the better design?
Show answer
A noise-based signal is a property of one model, computed once, independent of who else is in the pool. Pairwise comparison would need recomputing for every new model added — an O(N²) cost that grows with the deployment. The noise signal lets SANDHI profile a new model once and slot it into an existing pool without touching prior work.Misconception: that mergeability is inherently a property of a *pair* of models. The paper's key insight is that a model-intrinsic signal (tolerance to noise) predicts pairwise mergeability well enough to avoid pairwise computation.
Problem 4 · hard
For 6 models with 24 layers and 2 components per layer, how many pairwise merge configurations exist in total (using the c·L formula)?
Show answer
c·L = 2×24 = 48 decisions per pair → 248 ≈ 2.8×1014 configurations per pair. Pairs: C(6,2) = 15. Total ≈ 15 × 2.8×1014 ≈ 4.2×1015 configurations — still far beyond exhaustive search, even for a smaller pool than the paper's 10-model example.Misconception: that the search space only becomes intractable at the paper's specific scale (10 models, 32 layers). The exponential blows up the search space at nearly any realistic pool size.
Problem 5 · medium
The ablation shows layer-level merging achieves 24.9% savings with −1.9% accuracy, while SANDHI's component-level merging achieves 35.2% savings while improving accuracy. Why does finer granularity help both dimensions?
Show answer
Layer-level merging must treat a layer's attention and MLP as a single unit: if either sub-block is sensitive, the whole layer is excluded, forfeiting savings from the safe sub-block — or if forced through, it drags an accuracy-critical sub-block along, hurting accuracy. Component-level merging decides independently, capturing savings from every tolerant sub-block while never touching a sensitive one — hence more memory saved *and* better accuracy.Misconception: that finer granularity is just a memory/accuracy trade-off knob. Here it's a Pareto improvement — finer granularity strictly dominates the coarser one because it removes a false coupling, not because it trades one metric for another.
Problem 6 · hard
Omitting the "residual-spacing" ordering rule (never merge adjacent layers back-to-back) increases rollback rate from 7.7% to 23.1% and costs 15% in memory savings. Explain the mechanism.
Show answer
Each layer's residual connection feeds directly into the next layer's input. If two adjacent layers are merged back-to-back, a perturbation introduced by the first merge has no intervening unmerged layer to help the network re-normalize before the second merge compounds on top of it. The combined perturbation is more likely to exceed the accuracy bound, so MICR rolls back more often — and each rollback is a merge that doesn't happen, directly costing memory savings.Misconception: that ordering merges is a minor implementation detail. The ablation shows it materially changes both the rollback rate and the final memory savings achieved.
Problem 7 · medium
SANDHI's runtime only swaps merge variants when per-model request-rate mix drifts by more than a total-variation-distance threshold over a 10-minute window. Why not just re-evaluate on every request?
Show answer
Variant swaps involve fetching changed weight components and atomically rebinding pointers — not free, and not meant to happen constantly. Reacting to every request's fluctuation would cause thrashing between variants with no net benefit, since short-term spikes are already handled by a conventional autoscaler operating at a faster timescale. The 10-minute window and TVD threshold specifically filter for *sustained* shifts in the workload mix, which is the timescale SANDHI's frontier navigation is designed for.Misconception: that faster reaction is always better. SANDHI deliberately separates fast autoscaling (someone else's job) from slow operating-point selection (its job) to avoid wasted swap overhead.
Problem 8 · easy
Two saturating-utility, well-fitting models are co-located and both already run comfortably within GPU memory at low request rate. How much will SANDHI likely help here?
Show answer
Relatively little in the short term — if neither model is memory-constrained, there's no queuing to relieve and no GPU-count threshold to cross. SANDHI's savings become valuable once memory pressure actually binds: high request rates, tight GPU budgets, or growing model pools. The paper's own framework treats memory savings as fungible only when there's pressure to relieve.Misconception: that merging always helps regardless of whether memory is actually the bottleneck. Like any capacity optimization, it pays off only where the constraint it targets is binding.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1Is SANDHI a replacement for LoRA?▾
No — it's complementary. Where LoRA's prerequisites hold (same base model, available training data, uniform adapter configs), operators can use LoRA and layer SANDHI on top to merge shared full-rank components across the adapter-augmented models, compounding savings (the paper reports +44.7% additional memory saved atop LoRA). Where LoRA's prerequisites don't hold — cross-family, cross-version, no training data — SANDHI operates on its own.
Q2Does merging components change what a model outputs?▾
It can, slightly — that's exactly what MICR's accuracy check is guarding against. Every accepted merge stays within a user-set accuracy bound ρ measured on task-relevant benchmarks. Surprisingly, the paper often finds small accuracy *improvements* rather than degradation, likely because sharing well-tolerated components acts similarly to a mild regularizer.
Q3How is the Gaussian noise profiler different from just measuring cosine similarity to the base model?▾
Cosine similarity and Fisher information showed too little variation across layers in the paper's own tests (Fig. 2) to reliably rank mergeability. The noise profiler instead directly simulates the effect of merging — replacing a component with a distribution-matched random substitute — and measures the actual accuracy consequence, which the paper found tracks true merge impact far more closely.
Q4Can components from different layers, or different model families, be merged with each other?▾
Yes, as long as the component type and tensor dimensions match — SANDHI doesn't require strict layer-index alignment. This is one reason it's called "cross-component": layer 3's attention in one model can potentially be merged with layer 8's attention in another, if their magnitude distributions cluster together.
Q5What exactly gets checkpointed as a "variant"?▾
After each accepted MICR step, the entire current merge state (which clusters are shared, which remain private) is saved as one point on the accuracy–memory frontier (Fig. 7). The runtime later picks among these pre-validated checkpoints rather than computing a new merge on the fly.
Q6Does SANDHI ever run in a way that could violate the user's accuracy bound?▾
No — by design. MICR only accepts merges into the frontier if they pass validation, and the runtime only ever selects among already-validated variants. Runtime adaptation changes which safe operating point is active; it never introduces a new, unvalidated merge on the fly.
Q7Why does merging sometimes *improve* accuracy instead of just costing a little?▾
The paper reports gains up to +1.5% (Llama) and +1.9% (Qwen-32B) on individual tasks. This echoes a broader pattern in model merging where sharing well-aligned parameters across related fine-tunes can act like implicit regularization or knowledge transfer between tasks — though the paper doesn't claim this is guaranteed, only observed empirically and validated per-step.
Q8How expensive is running SANDHI's profiling and merging pipeline?▾
Evaluation/profiling costs at most 2×num_layers×eval_time (eval_time is typically 1–5 minutes per benchmark run). It's triggered infrequently — mainly when a new model joins the pool — and the paper's Llama-pool example took 20 minutes across 2 H200 GPUs in parallel, a cost the paper argues is easily recouped by the GPU-hours or throughput gained afterward.
Q9Does SANDHI work with quantized models or Mixture-of-Experts architectures?▾
Yes to both, and the paper evaluates each. On 8-bit quantized Llama-3.1-8B models, SANDHI adds further savings atop quantization with a small accuracy gain. On MoE models (Qwen3-30B-A3B), it applies noise at expert-layer granularity and clusters at per-expert granularity, achieving 14.1% additional memory reduction.
Q10What's left for future work?▾
The paper doesn't lay out an explicit future-work agenda beyond its evaluated scope (12 models, 3 families, 9 benchmarks); what it does make explicit is that SANDHI offers no theoretical guarantee on accuracy — only the empirical bound ρ enforced per-step by MICR's validation and rollback.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
SANDHIThe paper's system: identifies which model components tolerate sharing, merges them incrementally, and navigates the resulting accuracy–memory frontier at runtime.
Gaussian noise profilerPer-model, per-component signal: replace a component with distribution-matched noise and measure the accuracy drop, without comparing to any other model.
MICRMerge-Incrementally-Check-Rollback — SANDHI's merge algorithm: merge one cluster, validate accuracy, accept or revert.
Accuracy–memory frontierThe family of merged variants MICR produces, each within the user's accuracy bound ρ at a different memory footprint.
Workload-aware variant selectorSANDHI's runtime component that picks which frontier variant to run based on per-model request-rate mix and available KV capacity.
Cluster Acceptance Rate (CAR)The fraction of profiler-proposed merge clusters MICR accepts; higher CAR means the profiler is steering toward genuinely mergeable candidates.
ScalerA lightweight per-component output correction that keeps hidden-state scales consistent across merged components — useful for same-family pairs and essential for cross-family ones.
CUDA VMM weight-sharingMapping one physical copy of a merged component's weights into multiple vLLM engines' virtual address spaces.
Supporting terms
LoRA / adapterLow-Rank Adaptation — a compact residual applied to a shared base model to represent a fine-tune without a full weight copy.
GQA / MHAGrouped-Query vs Multi-Head Attention — GQA's smaller per-token KV cache amplifies the batch-size benefit of freed weight memory.
KV cachePer-request cached keys/values; the resource that reclaimed weight memory is most often converted into.
TTFTTime To First Token — degrades sharply once a memory-bound baseline starts queuing requests.
Task vector / SLERPWays of composing fine-tuned models' parameter differences from a base model; the machinery behind "full-merge," which SANDHI applies only selectively.
Total variation distance (TVD)The metric SANDHI uses to detect meaningful drift in per-model request-rate mix, triggering a variant swap above 0.2 over 10 minutes.
Fisher information / cosine similarityPrior importance signals for layer sensitivity that the paper finds too undifferentiated to guide merging reliably (Fig. 2).

Related work (from the paper's §6 and citations)

S-LoRA: Scalable Serving of Thousands of LoRA Adapters medium

Sheng et al. · MLSys 2024

The main LoRA-serving baseline SANDHI compares against and can be layered on top of; decouples base model from adapters with unified memory pooling.

Chen et al. · 2024

Introduces cross-tenant batched adapter kernels — the batching-homogeneity constraint SANDHI's Prerequisite #3 discussion references.

dLoRA: Dynamically Orchestrating Requests and Adapters hard

Wu et al. · OSDI 2024

Dynamically switches between merged/unmerged adapter paths — a runtime-adaptation idea in the same spirit as SANDHI's variant navigation, for a different mechanism (LoRA, not component merging).

GEMEL: Model Merging for Memory-Efficient Video Analytics medium

Padmanabhan et al. · NSDI 2022

Applies layer sharing to co-located CNNs, exploiting heterogeneous layer types; the paper's starting point and point of contrast — transformer decoders lack CNN's structural heterogeneity, motivating SANDHI's noise-profiler approach.

TIES-Merging hard

Yadav et al. · NeurIPS

An advanced full-model merging technique requiring a shared backbone — the kind of traditional merging SANDHI applies only selectively, at component granularity.

Evolutionary Optimization of Model Merging Recipes hard

Akiba et al. · Nature Machine Intelligence, 2025

Searches merge configurations via evolutionary methods rather than SANDHI's profiler-guided clustering — an alternative answer to Challenge #2's combinatorial search problem.

PagedAttention / vLLM medium

Kwon et al. · SOSP 2023

The serving engine SANDHI is implemented atop; its KV-cache memory management is what SANDHI's freed weight memory ultimately feeds.
