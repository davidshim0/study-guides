Letting the task graph change shape with the hardware

A DAG says "this task runs here." It never says "and if it runs on a GPU instead, it becomes eleven tasks with a setup and a cleanup step." hDAGs add that missing sentence.

📄 Lütke Dreimann, Friesel, Lenze, Spinczyk · Universität Osnabrück 🎓 Written for readers who already know DAGs, tasks, NUMA ⏱ ~20 min read
🔀

Attach each task to a placement-dependent SUB-DAG, not one fixed micro-structure that's wrong for every device but one.
The graph should be shaped by where it runs, not the other way around.

Before you begin

Quick glossary, then seven primers

The acronyms first, then the concepts hDAGs are built on top of.

Quick glossary

DAGDirected acyclic graph — nodes are tasks, edges are data dependencies.
hDAGHeterogeneous DAG — this paper's extension: each task can carry a placement-dependent sub-DAG.
HPCHigh-performance computing — the domain where DAG-based task scheduling originates.
GPUGraphics processing unit — an accelerator with internal SPMD parallelism, dedicated memory.
PIMProcessing-in-memory — compute embedded in memory (here: UPMEM); dedicated, limited memory per rank.
CXLCompute Express Link — an interconnect enabling memory/accelerator expansion; motivates this work even though the eval uses UPMEM PIM.
HBMHigh-bandwidth memory — another disruptive memory type mentioned as context for heterogeneity.
NUMANon-uniform memory access — CPU cores can reach remote memory directly, just slower.
SPMDSingle program, multiple data — the internal parallelism style of GPU/PIM devices, as opposed to spawning many CPU tasks.
HEFTHeterogeneous Earliest Finish Time — a classic DAG scheduling algorithm; hDAGs' coarse-grained stage borrows its ranking idea.
1What a DAG is, and why HPC uses it▾

A DAG (𝑉, 𝐸, 𝐷, 𝑊) has tasks 𝑉, dependency edges 𝐸, exchanged-data sizes 𝐷, and per-unit runtimes 𝑊. A scheduler walks it, deciding when and where each task runs, respecting dependencies.

Now you're ready: hDAGs keep this exact tuple for the "coarse" view — the innovation is what can hide inside a single node.
2Tasks, compute units, and 𝐶ᵢ▾

Each task 𝑣ᵢ is annotated with the set 𝐶ᵢ⊆𝐶 of compute units it may run on (CPU core, GPU, PIM rank). A task runs on exactly one compute unit — CPU parallelism needs several concurrent tasks instead.

Now you're ready: "one task per kernel" is fine for a GPU, but wrong for the CPU version of the same kernel.
3SPMD vs. multi-threading (why granularity differs)▾

GPUs and PIM devices already parallelize inside one task (SPMD). CPUs don't — they need the programmer/scheduler to split work across several concurrent tasks to use multiple cores.

Now you're ready: the "right" number of tasks for a kernel is device-specific — this is the core problem hDAGs solve.
4Shared vs. dedicated memory, and data objects▾

CPU cores can usually reach any memory (even a remote NUMA node) directly. GPUs and PIM ranks can only see their own dedicated memory — everything else must be explicitly transferred. HetSim models each task's inputs as a set of data objects 𝑂ᵢ, each with a size.

Now you're ready: offloading to GPU/PIM needs partitioning and transfer logic that CPU execution never needs (Fig. 3).
5Setup and follow-up tasks▾

Before a GPU/PIM kernel can run, someone (a CPU) must allocate device resources, upload the program, and reshape data. After it finishes, someone must tear that down and reshape results back. These setup/follow-up steps take real, often non-constant, time.

Now you're ready: a conventional DAG has nowhere to put these steps except "hide them inside the kernel's number" — hDAGs give them their own tasks.
6HEFT and critical-path runtime estimates▾

HEFT ranks tasks by an estimated runtime (often averaged over possible placements) plus the critical path to the end of the graph, then places the highest-ranked task first. It's still considered state of the art for DAG scheduling.

Now you're ready: hDAGs reuse this exact idea to collapse a whole sub-DAG into one number a HEFT-style scheduler can consume.
7Backwards-compatibility, the goal▾

Decades of DAG scheduling research exists. A new format that can't use any of it is a hard sell. So the paper insists any hDAG must be translatable — even if lossily — back into a plain DAG that old algorithms already understand.

Now you're ready: hDAGs are meant as a strict superset, not a replacement, of the DAG format.
The whole story in one place

hDAGs in a nutshell

The problem, the fix, and how the pieces connect.

A conventional DAG assumes each task has one implementation and runs on one compute unit — fine when every device is a CPU. But once a task can also run on a GPU or a PIM rank, the honest structure of "the SELECT kernel" is different for each device: CPU wants several parallel tasks, GPU wants one SPMD task plus a setup/follow-up pair, PIM wants a different setup/follow-up pair and possibly its own task count. A single DAG cannot represent all three without lying about at least two of them.

hDAGs fix this by extending the DAG with a partial function g: V×C ⇀ G that maps a (task, compute unit) pair to a compute-unit-specific sub-DAG. Each sub-DAG is itself a legal (flat) DAG, constrained so it can't nest further, must use one compute-unit type throughout, and must expose a single initial and final pseudo-task that carry the same data objects as the parent task — so the rest of the graph doesn't need to know or care what's inside.

Scheduling then happens in two stages: a coarse-grained stage treats the hDAG as an ordinary DAG (each sub-DAG collapsed to a single HEFT-style runtime estimate via its critical path) to decide which compute unit each task gets; a fine-grained stage then expands the chosen sub-DAG and places its internal tasks and data. Because stage one is just DAG scheduling, any existing DAG algorithm works — hDAGs are backwards-compatible by construction.

The payoff, on real hardware (SELECT and SpMV, CPU/GPU/UPMEM-PIM): up to 38% lower latency from picking the right task granularity per device, up to 1.20× real speedup from locality-aware setup/follow-up placement, and simulation latency error cut from 61% (plain DAG) to 7% (hDAG) — an 89% reduction in prediction error — at the cost of 17–28% more lines of code.

🍯 Key takeaways

  • A DAG assumes one fixed implementation per task; heterogeneous accelerators break that assumption.
  • hDAGs attach a sub-DAG per (task, compute unit) pair — CPU parallelism, GPU/PIM setup+kernel+follow-up.
  • Sub-DAGs are constrained (no nesting, one compute-unit type, single in/out pseudo-task) so they collapse cleanly.
  • Two-stage scheduling: coarse (HEFT-style, on the collapsed DAG) then fine (inside the chosen sub-DAG).
  • Translating an hDAG down to a DAG makes it backwards-compatible with existing schedulers — lossily.
  • Real gains: −38% latency (granularity), 1.20× speedup (setup locality), −89% prediction error — for +17–28% LOC.
Five everyday pictures

How to think about hDAGs

Each stands alone; every one ends with where it breaks down.

The core idea · placement-dependent structure

A recipe that adapts to the kitchen

"Make dinner for eight" means one thing with a home stove (batch it, four pans, sequential) and another with a restaurant line (parallel stations, someone dedicated to plating). The dish is the same task; the steps depend on the kitchen. hDAGs let "SELECT" keep one name while its internal steps differ by device.

Where it breaks: a chef improvises; an hDAG's sub-DAG for a given device is fixed once the workload is defined, not decided live mid-execution.
Data objects · Fig. 3's partitioning

Packing a move — box, van, or ship container

The same apartment gets packed differently depending on the vehicle: small boxes for a car, one big load for a van, many small crates for container shipping. Same belongings (data object 𝑑), different fragmentation per destination — exactly how hDAGs let CPU, GPU, and PIM each fragment a data object into a different number of pieces.

Where it breaks: the mover decides packing on the day; hDAG partitioning is baked into the sub-DAG's setup/follow-up tasks ahead of time.
Setup / follow-up tasks · locality

Renting the venue before the event

Booking a hall, wiring the sound system, and tearing it down afterward is real work with real cost — it doesn't just vanish because it's "not the concert." hDAGs make GPU/PIM setup and follow-up their own tasks; scheduling the setup crew right next to where the show happens (same node as the predecessor task) avoids extra travel — this locality trick is worth the paper's 1.20× speedup.

Where it breaks: venue setup is a one-off; some accelerator setup costs vary per kernel invocation, not just per venue type.
Backwards-compatibility · lossy translation

Translating a poem

A poem translated to another language keeps the meaning but loses rhyme, rhythm, some nuance — still readable, still useful, just not the full original. Collapsing an hDAG's sub-DAGs into one runtime number per node (for stage-one scheduling) is the same trade: any existing DAG scheduler can read it, but the fine device-specific detail is gone until stage two expands it back.

Where it breaks: a bad translation can mislead a reader permanently; hDAG's lossy view is temporary and deliberately reversible — the full sub-DAG is expanded right after.
Coarse-stage estimate · HEFT ranking

A test kitchen's dry run

Before service, a restaurant times a dry run of each dish's slowest step (the "critical path" through prep) to decide the menu order — not every micro-detail, just the number that matters for scheduling the night. hDAGs' coarse stage does the same: average each sub-DAG's task/transfer times, take the critical path, and use that single estimate to rank placements HEFT-style.

Where it breaks: a dry run is a rough guess before the real thing; hDAGs' estimate is later validated by simulation, which is what the 7%-vs-61% error comparison actually measures.
The full explanation

How it actually works

From the formal model to the two-stage scheduler.

1 · The baseline model — DAGs and HetSim

A platform is a set 𝐶 of compute units with memory pools, linked in a mesh annotated with latency and bandwidth. A DAG is (𝑉, 𝐸, 𝐷, 𝑊): tasks, dependency edges, data sizes, and placement-dependent runtimes. HetSim (the simulator this work builds on) refines 𝐷 into explicit data objects 𝑂ᵢ per task, restricts each task to a compute-unit set 𝐶ᵢ, and adds a constant per-accelerator setup cost, scheduled on a CPU. Outside of shared-memory nuances and that constant setup cost, HetSim DAGs are ordinary DAGs.

2 · The gap — structure that depends on placement

A constant setup cost can't capture task-dependent setup/upload time, and a single task per kernel can't capture that CPU execution wants many parallel tasks while GPU wants one SPMD task. Prior "hierarchical DAG" work handles the CPU side but not accelerators; HetSim handles accelerators' cost but only as a constant. Nobody lets the DAG's shape — not just its annotations — depend on where a task lands.

3 · The extension — g: V×C ⇀ G

hDAGs add a partial function g(vᵢ, cⱼ) = Gᵢ,ⱼ mapping a task and a compute unit to a sub-DAG, drawn from the set G of legal HetSim DAGs subject to three constraints:

  1. No nesting. A sub-DAG cannot itself contain further sub-DAGs — this keeps collapsing well-defined.
  2. One compute-unit type. Every task inside a given sub-DAG runs on "CPU" or on the specific accelerator in question, never mixed.
  3. Single in/out pseudo-tasks. Exactly one zero-latency initial and one final pseudo-task, each carrying the same data objects as the parent task 𝑣ᵢ — so the rest of the graph is unaffected by what happens inside.
🧩
Inserting a sub-DAG is mechanical: replace 𝑣ᵢ with 𝐺ᵢ,ⱼ, reroute 𝑣ᵢ's inbound edges to the initial pseudo-task, and its outbound edges to the final pseudo-task. Both pseudo-tasks have zero latency — they exist purely to give the sub-DAG clean boundaries.

4 · Two-stage scheduling

Stage 1 (coarse): translate the hDAG into a plain DAG by collapsing each 𝑔(𝑣ᵢ,𝑐ⱼ) into one runtime estimate 𝑊(𝑣ᵢ,𝑐ⱼ) — the critical path through the sub-DAG's tasks/transfers, averaged over legal internal placements. Any DAG scheduler (e.g. HEFT) then assigns each coarse task to a specific compute unit.

Stage 2 (fine): for every task whose chosen unit has a sub-DAG, expand it and schedule its internal tasks and data — either with a constrained DAG scheduler (forcing same-sub-DAG tasks onto the same physical device, not just the same device type) or with heuristics informed by stage 1's already-concrete choice (e.g. "this specific GPU 2").

# stage 1 — coarse, per sub-DAG
for each (v_i, c_j) with g(v_i, c_j) != ⊥:
    W(v_i, c_j) = critical_path(avg_runtimes(g(v_i, c_j)))
run any DAG scheduler on the collapsed graph   → compute-unit per task

# stage 2 — fine, per chosen sub-DAG
for each task v_i placed on c_j with g(v_i, c_j) != ⊥:
    expand g(v_i, c_j)
    pin all its non-CPU tasks to the SAME physical device
    place setup task near its predecessor for locality

5 · Backwards-compatibility

Because stage 1 is ordinary DAG scheduling on a collapsed graph, every existing DAG-based placement algorithm works unmodified on an hDAG — it just sees fewer details than an hDAG-aware one would. The translation is intentionally lossy (device-specific granularity is invisible until stage 2), but it means hDAGs don't require throwing away decades of scheduling research.

Follow the numbers

Worked examples

Four calculations, using the paper's real figures.

① Why "one task per kernel" costs 38%

SELECT's optimal granularity (Fig. 5): CPU 16 tasks (32 loses to cross-socket overhead), GPU 1 task, PIM 16 tasks. A conventional DAG must pick one number for all three.

  1. Pick 1 task (optimal for GPU): CPU now runs single-threaded — leaves 15 of 16 cores idle for that kernel.
  2. Pick 16 tasks (optimal for CPU/PIM): with only 2 GPUs available, those 16 tasks queue as 8 sequential batches per GPU — "abysmal GPU performance."
  3. Either choice is wrong for at least one device — there is no single number that is simultaneously optimal for CPU, GPU, and PIM.
  4. hDAG's fix: give each device its own sub-DAG with its own optimal task count. Result (Fig. 6): CPU placement latency drops 38% versus the single-task DAG; PIM improves slightly; GPU latency is unchanged (it was already using its optimum, 1 task).
🍯
Insight: the 38% isn't from a smarter algorithm — it's from the format finally being able to express the right answer for CPU at all.

② Locality-aware setup placement → 1.20×

Baseline: a hierarchical DAG with setup/follow-up as ordinary tasks, placed round-robin onto the next free compute unit — so a GPU's setup task might land far from the GPU's predecessor task, adding transfer overhead.

  1. hDAG's adjustment: because setup/follow-up tasks are explicit in the sub-DAG, the scheduler can special-case them — pin each setup task to the same node as its predecessor.
  2. Effect: input data for the GPU kernel doesn't take an extra hop before setup even begins.
  3. Measured on real hardware, across SELECT and SpMV with GPU execution and round-robin scheduling: average speedup 1.20× (Fig. 7).
💡
This came from a "simple scheduler adjustment," not a new placement algorithm — exactly the paper's point that hDAGs let even naive schedulers do better, because they can finally see the setup/follow-up tasks to special-case them.

③ Latency prediction: 61% error → 7% error

GPU-accelerated SpMV, 10⁶ non-zero elements. A conventional DAG simulation ignores (or under-models) setup/follow-up cost.

  1. DAG-based simulation underestimates real latency by more than 50% — the paper reports 61% error, meaning setup/follow-up account for over half of total latency here.
  2. hDAG-based simulation, which models setup and follow-up as real tasks with real (measured) durations, comes within 7% of real hardware.
  3. Relative improvement: (61 − 7) ÷ 61 = 54 ÷ 61 ≈ 0.885 → 89% lower prediction error — matching the paper's own figure caption exactly.
🍯
Insight: if setup/follow-up genuinely dominate half the runtime, any scheduler reasoning about a plain DAG is optimizing against a fantasy — the accuracy gain here is arguably hDAGs' most important number for tiering/CXL-style research, since offload setup costs are exactly the kind of overhead that's easy to hand-wave away.

④ The price: 17–28% more code

Implementing SELECT and SpMV with hDAGs (constant granularity, no runtime auto-tuning) versus with conventional DAGs.

  1. SELECT: lines of code increase by 28% — mostly the explicit setup/follow-up tasks and per-device sub-DAG wiring.
  2. SpMV: lines of code increase by 17% — smaller increase, since SpMV's data transformation logic was already substantial under the DAG model.
  3. The trade-off, stated plainly by the authors: for HPC workloads where a 20–40% latency win is valuable and code is written once but run many times, the extra 17–28% development cost is expected to pay for itself.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A kernel runs fastest on GPU with exactly 1 task, and on CPU with 16 tasks. Why can't a conventional DAG just annotate the task with both numbers?
Show answer
Because a conventional DAG's task count is part of the graph's fixed structure (how many nodes exist), not a per-placement annotation like runtime. Annotating "runtime if on GPU" vs "runtime if on CPU" for one node is fine (𝑊: 𝑉×𝐶→ℝ already does this) — but you can't annotate "this one node is secretly sixteen nodes if placed on CPU." That requires changing which nodes exist, which is exactly what hDAGs' sub-DAG mapping g enables.Misconception: that granularity is just another runtime annotation. It's a structural property — the number of tasks — which plain DAGs can't vary by placement.
Problem 2 · medium
Why must a sub-DAG's initial and final pseudo-tasks carry the exact same data objects as the parent task 𝑣ᵢ?
Show answer
So that inserting the sub-DAG is transparent to the rest of the graph: any edge that pointed into 𝑣ᵢ (expecting a certain set of data objects) can be rerouted to the initial pseudo-task without the sender needing to know anything changed, and likewise for outbound edges and the final pseudo-task. If the pseudo-tasks used different data objects, every neighboring task would need custom logic per sub-DAG.Misconception: that the sub-DAG can freely change what data flows in/out at the boundary. It can transform data internally, but the interface contract with the rest of the graph must stay fixed.
Problem 3 · medium
Why does hDAG scheduling need two stages instead of just always expanding every sub-DAG up front?
Show answer
Which sub-DAG applies depends on which compute unit a task is placed on — but you don't know that until a scheduler has made a placement decision. Expanding every possible sub-DAG up front would mean building CPU, GPU, and PIM versions simultaneously and somehow deciding among them without a coherent single graph to schedule. The two-stage approach breaks the circular dependency: decide placement first (stage 1, on a collapsed view), then expand only the sub-DAG that was actually chosen (stage 2).Misconception: that more detail up front is always better for a scheduler. Premature detail here creates an unresolvable chicken-and-egg problem between structure and placement.
Problem 4 · hard
The paper says hierarchical DAGs (Wu et al.) support CPU sub-DAGs but not accelerator sub-DAGs, and assume "similar execution time" within a sub-DAG. Why would that second assumption break for a GPU sub-DAG with setup, kernel, and follow-up tasks?
Show answer
A GPU sub-DAG's setup task (device allocation, upload) and follow-up task (de-allocation, data mangling) are CPU-bound housekeeping — typically much shorter or structurally different in duration than the SPMD kernel task itself, which does the actual compute. "Similar execution time" assumptions, tuned for linear-algebra CPU sub-tasks that split work evenly, don't hold for a three-stage setup→kernel→follow-up chain where each stage has a fundamentally different job.Misconception: that any sub-graph of "similar" tasks generalizes to setup/compute/follow-up chains. Those stages differ in kind, not just in size, so uniform-time assumptions fail.
Problem 5 · medium
A colleague argues: "Just always use hDAGs — a hierarchical or conventional DAG is strictly worse." What's the honest counterargument from the paper's own numbers?
Show answer
hDAGs cost 17–28% more lines of code to implement, and the paper doesn't design or evaluate a novel placement algorithm for the fine-grained stage — it only sketches options. For a simple, CPU-only, single-device workload with no accelerator variability, that extra development cost buys nothing, since there's no placement-dependent structure to express in the first place.Misconception: that a strictly more expressive format is a free upgrade. Expressiveness has a development cost, and the benefit only materializes when the workload actually spans heterogeneous compute units.
Problem 6 · easy
Why does the paper use UPMEM PIM rather than CXL-based PIM for its evaluation, even though CXL is a stated motivation?
Show answer
The paper states plainly: "due to unavailability of CXL-based PIM modules, we use UPMEM PIM instead." It's a practical hardware-availability substitution, not a claim that UPMEM and CXL-PIM behave identically — CXL is the broader motivating trend, UPMEM is what could actually be benchmarked.Misconception: that the evaluation targets validate hDAGs specifically for CXL memory. The mechanism generalizes, but the numbers come from UPMEM hardware.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is a sub-DAG, in one sentence?▾
A small, ordinary DAG — with one compute-unit type throughout and a single entry/exit pseudo-task — that a task can expand into when placed on a specific compute unit.
Q2Do all tasks need a sub-DAG?▾
No — 𝑔 is a partial function. In the SELECT example, INIT and PRINT have no sub-DAG (𝑔(𝑣,∗)=⊥) since they're always CPU-bound and simple; only SELECT, which can be offloaded, has one per compute unit.
Q3How is this different from just writing three separate DAGs (one per device)?▾
Three separate DAGs would need a scheduler to be told in advance which whole DAG to use — placement and structure would no longer interact. hDAGs keep one graph where placement decisions (which task goes where) and structure (which sub-DAG unfolds) are resolved together, task by task, by the two-stage scheduler.
Q4Is the 38% latency reduction from a smarter scheduling algorithm?▾
No — the paper is explicit that designing a novel placement algorithm is out of scope. The 38% comes purely from the hDAG format finally being able to express
Q5Why does GPU latency stay unchanged in Fig. 6?▾
Because the conventional DAG baseline already used a single task for SELECT — which happens to be the GPU-optimal granularity. The comparison only helps CPU (and slightly PIM), since those needed a granularity the baseline DAG couldn't express.
Q6What does "backwards-compatible" actually guarantee?▾
That any existing DAG-based scheduling algorithm can run on an hDAG's collapsed (translated) form without modification. It does not guarantee that algorithm will find the hDAG-optimal schedule — the translation is lossy, so fine-grained, device-specific benefits require an hDAG-aware second stage.
Q7How is 𝑊(𝑣ᵢ,𝑐ⱼ) computed for a sub-DAG?▾
Average each internal task's and transfer's latency over its legal placements, then take the critical path (longest path from the sub-DAG's initial to final pseudo-task) through those averages — mirroring the ranking function HEFT uses for ordinary DAG tasks.
Q8Does hDAG scheduling have to run offline?▾
No. The coarse stage typically runs offline (before execution), but the fine-grained stage can run either offline or online (at runtime), depending on how much the implementation wants to react to current device utilization.
Q9What's left for future work?▾
The authors flag: designing and evaluating novel task/data placement algorithms specifically for hDAGs (this paper only sketches options), and determining optimal sub-DAG granularity dynamically at runtime rather than encoding it statically per workload.
