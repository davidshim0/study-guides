DIMES 2026 · A Field Guide

Letting the task graph change shape depending on where it runs

A DAG assumes one fixed structure. But the CPU, GPU, and PIM versions of the same kernel need different task counts and different setup work. This is the plain-English story of hDAGs, a small extension that lets the graph's own shape depend on placement.

📄 "hDAGs: A DAG Representation for Scheduling Tasks on Heterogeneous Hardware" · Lütke Dreimann, Friesel, Lenze, Spinczyk · DIMES'26 🎓 Task-graph / DAG-scheduling basics assumed — the primers cover them ⏱ ~25 min read
🧩

Let each task carry placement-dependent sub-DAGs instead of forcing one fixed structure onto every compute unit.

Before you begin

Quick glossary, then nine ideas the paper assumes you know

You already know CXL and PIM from the memory-tiering side; these primers focus on the task-scheduling / DAG side, which is the less familiar half of this paper.

Quick glossary — acronyms used throughout

1What a task DAG actually is▾

A workload is written as a tuple (V, E, D, W): nodes V are tasks (atomic units of work), edges E are data dependencies, D annotates each edge with the size of exchanged data, and W annotates each task with its execution time per compute unit. A scheduler's job is to map each node to a compute unit and each edge's data to a location.

This has been the HPC standard for decades precisely because it separates "what depends on what" from "who runs where" — the same separation your mm-stack work relies on between data dependencies and physical placement.

Now you're ready: hDAGs keep this exact tuple for the "coarse" view of a workload — the extension is entirely about what a single node can secretly expand into.
2Compute units, memory pools, and HetSim's platform model▾

HetSim (the simulator/framework this paper builds on) models a platform as a set C of compute units, each with an associated memory pool, connected in a mesh where every compute-memory and memory-memory link carries its own latency and bandwidth. CPU cores can access data on a reachable memory pool (e.g., a remote NUMA node) directly; GPUs and PIM devices generally cannot — their data must be transferred first.

Now you're ready: this is the same distinction you already reason about with CXL-attached memory — "reachable directly" vs "needs an explicit transfer" — just expressed as a scheduling-framework primitive instead of a page-table one.
3Task granularity: why one task count doesn't fit every device▾

A CPU core runs exactly one task at a time, so parallel CPU execution of a kernel requires multiple concurrent tasks. GPUs and PIM devices instead provide internal SPMD-style parallelism inside a single task — you only need multiple tasks if you want to use multiple GPUs or multiple PIM ranks concurrently. So the "right" number of tasks for a kernel is a function of which device runs it, not a property of the kernel alone.

Now you're ready: this granularity mismatch is the central problem hDAGs solve — a conventional DAG has to commit to one task count for a kernel, no matter which device eventually executes it.
4Setup and follow-up tasks▾

Offloading a kernel to a GPU or PIM device usually needs extra CPU-bound work first (allocating device resources, uploading the application/kernel, transforming data layouts) and afterward (de-allocation, further data mangling). Non-CPU execution often requires these CPU-bound setup/follow-up operations, and their cost can be substantial and device-specific — not a fixed constant.

Now you're ready: conventional DAGs and even HetSim's own baseline model these as a single, task-independent constant latency. hDAGs instead model them as real tasks with their own dependencies and placement.
5Data objects vs. data-size annotations▾

Conventional DAGs annotate each edge with just a data size D(e). HetSim instead gives each task v_i an explicit set of data objects O_i, and derives the transferred size between dependent tasks as the size of the objects they share: D(v_i,v_j) = Σ over d in O_i ∩ O_j of size(d). This makes data movement explicit and object-level rather than a single opaque number per edge.

Now you're ready: hDAG sub-DAGs reuse this object model — a sub-DAG's start and end pseudo-tasks must reference exactly the same data objects as the coarse-grained task they replace, so the substitution is transparent to the rest of the graph.
6HEFT and critical-path runtime estimates▾

HEFT (Heterogeneous Earliest Finish Time) is a classic, still-competitive DAG scheduling algorithm. Part of its trick is ranking tasks by an estimated runtime: average their execution and data-transfer latency over all legal placements, then use the DAG's critical path (the longest chain of dependent latencies) as a single scalar estimate.

Now you're ready: hDAGs' runtime estimate closely resembles this idea, collapsing an entire sub-DAG into one number — the estimated execution time W(v_i,c_j) that a coarse-grained, hDAG-unaware scheduler can consume.
7Prior art: hierarchical DAGs (Wu et al.)▾

Hierarchical DAGs already let a node expand into a CPU-specific sub-DAG (useful for linear-algebra libraries where CPU work is split across cores). But they provide no sub-DAG for accelerators — GPU/PIM execution is always a single opaque task — and no setup/follow-up modeling. They also assume all tasks within a sub-DAG have similar execution time, which doesn't hold in general.

Now you're ready: hDAGs are a strict superset: sub-DAGs can be attached for any compute unit type where one is needed (the mapping is partial — plenty of tasks have none), plus first-class setup/follow-up tasks, plus no assumption about uniform task cost.
8The chicken-and-egg problem▾

Optimal placement depends on the DAG's structure (how many tasks, how much data each moves) — but with hDAGs, the structure itself depends on the placement decision you haven't made yet. You can't fully expand every possible sub-DAG for every task up front — this guide's intuition is that doing so would blow up combinatorially, though the paper doesn't spell that reasoning out — and you can't decide placement without knowing what each choice would cost.

Now you're ready: this loop is exactly why hDAG scheduling is split into two stages — coarse placement first, using estimates; then fine-grained placement second, using the sub-DAG the coarse stage actually selected.
9Backwards compatibility, and why it's lossy▾

An hDAG can always be translated into a conventional DAG by collapsing each sub-DAG into one node with an estimated runtime. This lets any existing DAG-based scheduling algorithm — decades of published research — run on hDAG workloads unmodified for the coarse stage. The translation necessarily loses detail (it's a single number standing in for a whole sub-graph), but that's not a flaw specific to hDAGs: conventional DAGs never had the detail to lose in the first place.

Now you're ready: you're set up for the full mechanism in "How It Works."
The whole story in one place

hDAGs in a nutshell

The problem, the fix, and how the pieces connect.

Directed acyclic graphs are the de facto standard for describing HPC workloads, but they assume a fixed structure: one set of tasks, each pinned to a single compute unit's execution-time slot. That assumption breaks the moment an application supports both CPU and accelerator execution. A kernel that runs as 16 parallel tasks on a CPU may need to run as a single SPMD task on a GPU, plus CPU-bound setup and follow-up tasks that a conventional DAG has no place to put — except as an unrepresentative constant.

The paper's fix, heterogeneous DAGs (hDAGs), extends the DAG definition with a partial function g: V×C ⇀ G that maps a (task, compute unit) pair to an accelerator-specific sub-DAG. Each sub-DAG has its own internal tasks, its own single initial and final pseudo-task, and is forbidden from containing further sub-DAGs — keeping the extension one level deep and tractable. Scheduling is then split into two stages: a coarse stage that treats each sub-DAG as one estimated-runtime node (using a HEFT-style critical-path estimate) to decide placement, and a fine-grained stage that unfolds the chosen sub-DAG and schedules its internal tasks and data.

The payoff, measured on real hardware (2× Intel Xeon Gold 5218, 2× NVIDIA A30 GPUs, 40× UPMEM-PIM ranks): hDAG-based placement reduces SELECT application latency by up to 38% versus a single-task conventional DAG; simple scheduler adjustments that exploit hDAG's setup/follow-up modeling yield an average 1.20× real-world speedup; and hDAG-based latency prediction is within 7% of measured execution time, versus a conventional DAG's estimate that is off by 61%. hDAGs remain backwards-compatible with existing DAG-based scheduling algorithms via lossy translation.

🍯 Key takeaways

  • A conventional DAG's structure is fixed; the real, optimal structure of an accelerator-capable kernel is placement-dependent.
  • hDAGs attach an optional, per-compute-unit sub-DAG to any task — a strict superset of hierarchical DAGs and HetSim's constant-cost setup model.
  • Sub-DAGs can't nest, must use a single compute-unit type internally, and must expose exactly one initial/final pseudo-task referencing the parent's data objects.
  • Two-stage scheduling resolves the placement↔structure chicken-and-egg loop: coarse (HEFT-style estimate) first, fine-grained (real sub-DAG) second.
  • hDAGs stay backwards-compatible: translate to a conventional DAG and any existing scheduler still works for the coarse stage.
  • Results: up to 38% lower latency, 1.20× average real-world speedup, 89% lower prediction error (61%→7%) — at a 17–28% lines-of-code cost.
Six everyday pictures

How to think about hDAGs

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Granularity

A recipe that reads differently per station

The same dish is plated by a single line cook (GPU: one SPMD task), assembled by a crew of four working in parallel (CPU: many tasks), or portioned across sixteen small prep stations (PIM: many rank-parallel tasks). One recipe card, three very different workflows depending on which kitchen station gets it.

Where it breaks: a real recipe adapts live as the cook improvises; hDAGs decide the sub-DAG shape statically, ahead of time, per workload configuration — not dynamically per run.
Modeling cost · Setup & follow-up

Renting a truck vs. using your own bike

Riding your own bike (CPU) needs no paperwork. Renting a moving truck (GPU/PIM) needs a reservation, a walkaround inspection, and a return process — real time that has nothing to do with the actual move. hDAGs model that paperwork as explicit CPU-bound setup/follow-up tasks, instead of pretending it's free or folding it into one constant.

Where it breaks: rental paperwork is roughly fixed; for SpMV on real hardware, setup and follow-up account for over 50% of total latency — far more dominant than any truck-rental analogy suggests.
The unfold · Pseudo-tasks, no nesting

A choose-your-own-adventure insert page

Land on "go to the accelerator," and a whole new page unfolds with its own beginning and end. hDAG sub-DAGs work the same way: a single initial and final pseudo-task with zero latency, existing only so inbound/outbound edges have somewhere to reroute to. But the rulebook is explicit: an inserted page can't contain another insert page — sub-DAGs may not nest.

Where it breaks: real choose-your-own-adventure books nest freely, chapter within chapter. hDAGs forbid that on purpose, to keep the unfold one level deep and the two-stage scheduler tractable.
Scheduling · Two stages

Planning a road trip in two passes

First you pick the highway route (coarse: which compute unit gets each task, using a rough time estimate for the whole detour). Only once you know which town you'll pass through do you plan the actual side-street turns (fine-grained: place the sub-DAG's real tasks and data). Trying to plan every possible detour before choosing a highway would be hopeless.

Where it breaks: in a real trip, the highway choice rarely depends on local turns. Here, the two are more entangled than the analogy admits — the fine-grained sub-DAG's true cost is exactly what the coarse stage was trying to estimate, so the "estimate first, refine later" split is a deliberate heuristic, not a clean separation.
Compatibility · Lossy translation

Translating a poem for a foreign edition

Translating a poem preserves the gist but loses rhyme, rhythm, and nuance — yet it's still worth doing, since it lets a new audience read it at all. Collapsing an hDAG into a conventional DAG works the same way: each rich sub-DAG becomes one number (an estimated runtime), losing internal detail, but making the workload legible to decades of existing DAG schedulers.

Where it breaks: a translated poem is usually the final, standalone artifact. The hDAG→DAG translation is only used to make the coarse-stage decision — the full, untranslated hDAG is still what actually gets scheduled and executed afterward.
Prediction · Missing setup cost

A moving quote that forgets the packing crew

Quote a move by driving distance alone and you'll badly underestimate — the packing, wrapping, and unpacking crew's hours dwarf the drive. A conventional DAG-based simulator does the same thing: without setup/follow-up tasks, it underestimates SpMV's GPU latency by more than half.

Where it breaks: a bad moving quote is usually just sloppy estimation. Here it's structural — the conventional DAG has no node to put the packing crew's hours on, no matter how carefully you estimate.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The formal extension

A conventional (HetSim) DAG is the tuple (V, E, D, W) plus a compute-unit set C_i ⊆ C per task. hDAGs add one thing: a partial function

g: V × C ⇀ G   # maps (task, compute unit) to an optional sub-DAG

Every G_i,j ∈ G — every legal sub-DAG — must satisfy three constraints: (1) it may not itself contain further sub-DAGs (no nesting), (2) every task inside it is pinned to a single compute-unit type (all-CPU, or the one accelerator in question — no mixing inside one sub-DAG), and (3) it has exactly one initial pseudo-task (no predecessors) and one final pseudo-task (no successors), both referencing the same data objects as the coarse-grained task v_i they will replace.

2 · Inserting a sub-DAG — the rerouting algorithm

Once a scheduler decides task v_i runs on compute unit c_j with g(v_i,c_j) ≠ ⊥, the coarse DAG G is updated mechanically:

insert sub-DAG G_i,j in place of v_i
reroute every inbound edge of v_i  → G_i,j's initial pseudo-task
reroute every outbound edge of v_i → G_i,j's final pseudo-task
# pseudo-tasks have zero execution latency — pure rerouting points

Because pseudo-tasks reference the same data objects as v_i, nothing else in the surrounding DAG needs to change — the substitution is transparent from the outside.

3 · Two-stage scheduling

Coarse stage: translate the hDAG into a conventional DAG by estimating, for every (v_i,c_j) with a sub-DAG, a single execution time W(v_i,c_j). This is computed HEFT-style: average each internal task's execution/transfer latency over all its legal placements, then take the sub-DAG's critical path as the estimate. Any existing DAG scheduling algorithm can then place each coarse task on a compute unit.

Fine-grained stage: for every task actually scheduled onto a compute unit with a sub-DAG, unfold that sub-DAG and place its internal tasks and data. The paper sketches two options: reuse a DAG scheduler with an added constraint (all of one sub-DAG's non-CPU tasks must land on the same physical device, not just the same device type), or use heuristics/current-utilization information — optionally reusing the coarse stage's already-specific placement (e.g. "GPU 1", not just "a GPU") as a hint.

💡
Why keep it two-stage instead of one big search? Expanding every task's every possible sub-DAG before deciding anything would plausibly blow up combinatorially — a reasonable intuition, though the paper itself doesn't spell out this argument. Estimating first and refining second breaks the loop at the cost of a (deliberately bounded) loss of precision in the coarse decision.

4 · Backwards compatibility

Because the coarse stage's translation produces an ordinary (V,E,D,W) DAG, any DAG-based scheduling algorithm — HEFT, round-robin, evolutionary schedulers, anything published in the last two decades — can consume it without modification for that coarse-grained decision. hDAGs add capability without demanding that placement research start over, though fine-grained placement may still need an added constraint, as noted above, to keep a sub-DAG's non-CPU tasks together on one physical device.

🌱
A connection to tiered-memory scheduling: the same failure mode shows up in naive page-placement policies that ignore migration cost — treating a promotion as instantaneous the way a plain DAG treats accelerator setup as free. Just as TPP- or HeMem-style policies must explicitly account for migration overhead to avoid thrashing, hDAGs must explicitly account for setup/follow-up cost to avoid mis-scheduling accelerator work.
Follow the numbers, step by step

Worked examples

Four results from the paper's SELECT and SpMV benchmarks, carried through the reasoning behind each number.

① Why one task count can't serve all three devices

On real hardware, SELECT's optimal granularity is 16 tasks for CPU, 1 task for GPU, and 16 tasks (ranks) for PIM. What happens if a conventional DAG is forced to pick just one?

  1. Pick 16 tasks (CPU-optimal) and place SELECT on GPU anyway. The system has only 2 GPUs, so 16 tasks must run as 16 ÷ 2 = 8 sequential rounds per GPU — serialized, when 1 task would have used the GPU's own internal SPMD parallelism directly.
  2. Pick 1 task (GPU-optimal) and place SELECT on CPU instead. Now only one CPU core does the work — the other 15 sit idle, since a single task can't be split across cores after the fact.
  3. An hDAG needs neither compromise: it encodes all three optimal shapes at once via g(v_SELECT, c), and the scheduler picks the sub-DAG matching wherever it actually lands.
  4. Measured result: hDAG-based CPU placement latency is 38% lower than the single-task DAG baseline; PIM improves slightly; GPU latency is identical (both use 1 task there anyway).
🍯
Insight: the 38% gap isn't from a smarter algorithm — it's purely from being able to express the CPU-optimal shape instead of being stuck with whatever single shape the DAG format allows.

② Locality-aware setup placement — the 1.20× speedup

A round-robin scheduler places each task on the next available compute unit. How does modeling setup tasks explicitly turn into a real speedup?

  1. Baseline (hierarchical DAG): setup and follow-up are ordinary tasks with no special treatment; round-robin may place a setup task on a different node than the data it needs to prepare, forcing an extra transfer.
  2. hDAG adjustment: because setup/follow-up are explicit, first-class tasks in the sub-DAG, the scheduler can be told a simple rule: always place a setup task on the same node as its predecessor.
  3. Effect: the GPU's input data doesn't need a second hop — it's already local when the setup task runs.
  4. Measured result: averaged over SELECT and SpMV with GPU execution, this one adjustment yields a 1.20× real-world speedup — without replacing round-robin with a custom algorithm.
💡
The scheduling algorithm didn't change — round-robin is still round-robin. What changed is that hDAGs gave it something concrete (an explicit setup task with a real predecessor) to make a locality-aware decision about.

③ Latency prediction: 61% error → 7% error

For GPU-accelerated SpMV on 10⁶ non-zero elements, how far off is a conventional DAG's simulated latency from the real thing, and why?

  1. Conventional DAG estimate: is off by 61% — it has no task to represent setup/follow-up, so that time simply doesn't appear in the model.
  2. hDAG estimate: within 7% of measured latency, because setup and follow-up are modeled as real tasks with their own (measured) execution times.
  3. Relative improvement: (61 − 7) ÷ 61 ≈ 89% lower error — matching the paper's own framing of the result.
  4. Why the gap is so large: the paper reports that for this workload, setup and follow-up account for more than 50% of total SpMV latency — so a model that omits them isn't missing a rounding error, it's missing the majority of the runtime.
🍯
Insight: this isn't a tuning problem solvable by better constants — a conventional DAG has no node to attach that time to. The fix has to be structural, which is exactly what hDAGs provide.

④ The engineering cost: +28% / +17% lines of code

hDAGs aren't free to write. How large is the cost, and is it worth it?

  1. SELECT: implementing it with hDAGs (constant granularity for CPU, GPU, and UPMEM PIM) increases lines of code by 28% versus the conventional-DAG version.
  2. SpMV: the same comparison shows a 17% increase.
  3. What the extra code buys: per-device task counts and explicit setup/follow-up modeling — the source of the 38% latency reduction and 89% prediction-error reduction shown above.
  4. The paper's own framing: since it targets the HPC field — where workloads are long-running and heavily re-executed — the authors judge the benefits likely to outweigh the added development cost, though they don't quantify a break-even point.
⚠
Honest caveat: this is a real, measured cost, not hand-waved away — worth weighing explicitly for workloads that are short-lived, run rarely, or aren't performance-critical.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks for.

Problem 1 · easy
A conventional DAG models SELECT as a single task, and that DAG is scheduled onto a GPU. Latency is great. The same DAG is then scheduled onto the CPU instead. What happens, and why?
Show answer
Latency is poor: a single task can only run on one CPU core, so the other 15 cores sit idle. The DAG that was optimal for GPU (1 task) is exactly wrong for CPU (which wants ~16 parallel tasks in this benchmark).Misconception: that a task count optimized for one device is a safe default for others. Granularity is placement-dependent, not a fixed property of the kernel.
Problem 2 · medium
A scheduler instead picks 16 tasks (CPU-optimal) and places SELECT on a system with 2 GPUs. What happens to those 16 tasks, and why does latency suffer?
Show answer
With only 2 GPUs available, the 16 tasks must be spread across them, giving each GPU 16 ÷ 2 = 8 sequential tasks to execute one after another — serializing work that a single SPMD task could have handled at once, and adding scheduling/launch overhead per task on top.Misconception: that more parallelism is always better regardless of the compute unit's own internal parallelism model. GPUs already parallelize inside one task; splitting further just adds sequential rounds.
Problem 3 · medium
Why are accelerator setup tasks CPU-bound rather than running on the accelerator itself?
Show answer
Setup covers resource allocation, application/kernel upload, and (for some workloads) data transformation. The paper treats non-CPU execution as generally requiring this kind of CPU-bound setup/follow-up work, and hDAGs model it as explicit CPU-bound tasks rather than an opaque constant.Misconception: that setup/follow-up cost is negligible or safely folded into a fixed constant. hDAGs model it explicitly because, for workloads like SpMV, it can dominate total latency.
Problem 4 · hard
Explain the "chicken-and-egg" problem hDAG scheduling solves with two stages: why can't you decide final structure before placement, and why can't you decide placement without knowing structure?
Show answer
The optimal placement of a task depends on the cost of the sub-DAG it would unfold into (which differs per compute unit) — so you need the structure to judge placement. But which sub-DAG applies depends on which compute unit gets chosen — so you need the placement to know the structure. Fully expanding every sub-DAG for every possible placement ahead of time would plausibly be combinatorially expensive — a reasonable intuition rather than something the paper states outright. The two-stage approach breaks the loop with an estimate: collapse each sub-DAG to one HEFT-style number for the coarse decision, then unfold only the sub-DAG that was actually chosen.Misconception: that one-pass scheduling should be sufficient just because it works for conventional DAGs. Conventional DAGs never had this loop because their structure never depended on placement.
Problem 5 · medium
Why does the paper forbid sub-DAGs from containing further sub-DAGs?
Show answer
Unlimited nesting would reintroduce the same placement-depends-on-structure loop recursively, at every level, making the two-stage estimate-then-unfold strategy far harder to bound and reason about. Restricting to one level keeps the coarse-stage translation (collapse sub-DAG → one estimated number) and the fine-grained unfold both simple, single-pass operations.Misconception: that more expressiveness (arbitrary nesting) is free. It would keep the format "more general" but destroy the tractability that makes the two-stage scheduler practical.
Problem 6 · easy
A DAG-based simulator predicts GPU-accelerated SpMV will finish much faster than it actually does. What's structurally missing from the model, and roughly how large is the resulting error?
Show answer
The model has no task representing GPU setup and follow-up (resource allocation, data transformation, de-allocation) — for SpMV, these account for over 50% of total latency, so omitting them causes the DAG's estimate to be off by 61%. The hDAG version, which does model them as real tasks, comes within 7%.Misconception: that simulation error like this is numerical noise fixable by better constants. It's a structural gap — there's no node to attach the missing time to.
Problem 7 · hard
A round-robin scheduler gains a 1.20× average speedup once it's told to place setup tasks on the same node as their predecessor. Why doesn't this require replacing round-robin with a custom algorithm, and what would be lost if setup tasks weren't modeled explicitly?
Show answer
Round-robin itself is unchanged — it still cycles through compute units in order. The only addition is a placement constraint applied specifically to setup tasks, which is only possible because hDAGs expose them as first-class tasks with real predecessors and data objects. If setup were still a single opaque constant (as in HetSim's baseline or a hierarchical DAG), there would be no task to apply a locality rule to — the scheduler couldn't even express "put this near its input data."Misconception: that getting hDAG's scheduling benefits always requires designing a new placement algorithm from scratch. Often a small, targeted rule layered on an existing algorithm is enough — that's the point of hDAGs staying backwards-compatible.
Problem 8 · medium
hDAGs increase lines of code by 28% (SELECT) and 17% (SpMV) versus conventional-DAG implementations. Does this mean hDAGs are a net loss for these workloads?
Show answer
Not according to the paper's own numbers: for the same workloads, hDAGs deliver up to 38% lower latency, an 89% reduction in prediction error, and a 1.20× real-world speedup from simple scheduler adjustments. The LoC increase is a real, one-time development cost; the latency and accuracy gains recur every execution — which is why the authors judge it likely worthwhile for HPC workloads specifically, without claiming it's free.Misconception: that any added development cost is disqualifying on its own, without weighing it against a workload's execution frequency and performance sensitivity.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most.

Q1What is an hDAG in one sentence?▾
A conventional task DAG, extended with an optional, per-compute-unit sub-DAG for any task — so the same coarse node can expand into different internal structures depending on where it's scheduled.
Q2How does this differ from a hierarchical DAG (Wu et al., 2015)?▾
Hierarchical DAGs provide a sub-DAG only for CPU execution, assume uniform task cost within it, and treat GPU/accelerator execution as a single opaque task with no setup/follow-up modeling. hDAGs can attach a sub-DAG for any compute-unit type where one is needed — the mapping is partial, so plenty of tasks (like CPU-bound INIT/PRINT) have none — and make setup/follow-up tasks explicit and placement-aware.
Q3What exactly triggers a sub-DAG, and when does a task not get one?▾
Whenever g(v_i,c_j) ≠ ⊥ for the compute unit a task is scheduled on. In the SELECT example, INIT and PRINT are always CPU-bound with no sub-DAG (g = ⊥ for all compute units), while SELECT has one sub-DAG per supported compute unit (CPU, GPU, PIM).
Q4Why do pseudo-tasks have zero execution latency?▾
Their only job is to give the surrounding DAG's inbound/outbound edges somewhere concrete to reroute to once a sub-DAG is inserted. They don't represent real work — assigning them any latency would double-count time already accounted for by the sub-DAG's actual tasks.
Q5Why can't sub-DAGs be nested?▾
Nesting would reproduce the placement-depends-on-structure loop recursively at every level, making the two-stage scheduling strategy much harder to reason about and bound. Restricting to one level keeps both the coarse translation and the fine-grained unfold simple, single-pass operations.
Q6How does the two-stage scheduler avoid the chicken-and-egg loop?▾
By estimating first: the coarse stage collapses every sub-DAG into one HEFT-style critical-path runtime estimate and schedules the resulting conventional DAG. Only afterward, in the fine-grained stage, does it unfold the specific sub-DAG that was actually chosen and place its real tasks and data.
Q7Is hDAG backwards-compatible with existing DAG-based scheduling algorithms?▾
Yes — by construction, for the coarse-grained placement stage. Translating an hDAG into a conventional DAG (collapsing sub-DAGs into estimated-runtime nodes) produces a normal (V,E,D,W) DAG that any existing scheduler can consume unmodified there; fine-grained placement may still need an added constraint, such as keeping a sub-DAG's non-CPU tasks on one physical device.
Q8Why are setup/follow-up tasks CPU-bound?▾
Non-CPU execution often requires CPU-bound setup/follow-up operations — resource allocation, kernel upload, and data transformation before execution, plus de-allocation and further data mangling afterward. hDAGs model these as explicit CPU-bound tasks in the sub-DAG rather than an opaque constant.
Q9How is a sub-DAG's execution-time estimate computed for the coarse stage?▾
Average each internal task's execution and data-transfer latency over all its legal placements, then take the resulting critical path (the longest chain of dependent latencies) as the single estimate W(v_i,c_j) — an approach that closely resembles the ranking scheme HEFT uses for ordinary DAG tasks.
Q10What's the practical cost of adopting hDAGs?▾
Measured as lines-of-code increase versus a conventional-DAG implementation: 28% for SELECT, 17% for SpMV, when both use constant (non-adaptive) task granularity per device. The paper argues this is likely worthwhile in HPC settings but doesn't quantify a formal break-even point.
Q11What's left for future work?▾
The paper is explicitly about the hDAG data format, not a new placement algorithm — future work includes designing and evaluating dedicated hDAG-aware scheduling strategies, and deciding sub-DAG granularity (task counts) dynamically at runtime rather than fixing it statically per workload configuration.

Glossary & further reading

Core terms
hDAG (heterogeneous DAG)A DAG extended with a partial function g: V×C ⇀ G mapping (task, compute unit) pairs to accelerator-specific sub-DAGs.
Sub-DAGA legal HetSim DAG attached to a task for one specific compute unit; may not nest, must use one compute-unit type internally, has one initial and one final pseudo-task.
Pseudo-taskA zero-latency placeholder task (initial or final) inside a sub-DAG, used purely to reroute the surrounding DAG's edges.
Setup / follow-up taskCPU-bound tasks bracketing accelerator execution — resource allocation/upload (setup) and de-allocation/data mangling (follow-up) — modeled explicitly in hDAGs.
Two-stage schedulingCoarse stage (estimate sub-DAG runtimes, schedule as a conventional DAG) followed by a fine-grained stage (unfold and place the chosen sub-DAG).
Backwards compatibilityhDAGs can be losslessly-in-structure-but-lossy-in-detail translated into conventional DAGs, letting existing schedulers run unmodified for coarse placement.
Supporting terms
DAGDirected Acyclic Graph — tuple (V,E,D,W): tasks, data dependencies, data sizes, placement-dependent runtimes.
Data object (HetSim)An explicit, sized unit of data a task uses; edge data size is the sum of objects two dependent tasks share.
HEFTHeterogeneous Earliest Finish Time — classic DAG scheduler whose critical-path ranking scheme hDAGs' sub-DAG runtime estimate closely resembles.
SPMDSingle Program, Multiple Data — the internal parallelism GPUs/PIM provide within one task.
NUMANon-Uniform Memory Access — remote memory nodes CPU tasks may access directly, unlike accelerator-dedicated memories.
UPMEM PIMThe real processing-in-memory hardware used as a stand-in for CXL-based PIM in the paper's evaluation.
HetSimThe simulator/framework this paper builds on, providing the underlying platform and DAG model that hDAGs extend.
Round-robin schedulingA simple baseline that places each task on the next available compute unit in sequence; used to show hDAGs help even without a custom algorithm.
SELECT / SpMVThe paper's two benchmark workloads: a database SELECT kernel and sparse matrix-vector multiplication, each with CPU/GPU/PIM variants.
