Sizing DRAM by asking "what if?" instead of guessing

A tiered-memory system needs to know how much DRAM each app actually needs. TierSizer answers that by predicting a workload's slowdown at a DRAM size it isn't running on — without ever running it there — and shrinking toward the smallest safe size.

📄 "TierSizer" · Yadalam, Deshpande, Saxena, Arun, Yadwadkar, Akella 🎓 CXL/tiering background assumed known — primers focus on the counterfactual machinery ⏱ ~25 min read
🧮

Predict the slowdown at a DRAM size you're NOT running on, using only what you can measure at the size you ARE running on — then take a small, reversible step toward the minimum.

Before you begin

Quick glossary, then ten ideas the paper leans on

Acronyms first — skim once, then use the primers below for anything unfamiliar.

Quick glossary

CXLCompute Express Link — coherent fabric used to attach a second, slower memory tier.
DRAMThe fast, local memory tier being sized — the scarce, expensive resource.
LLCLast-Level Cache. A miss here means the CPU must fetch from DRAM or CXL and stalls.
MLPMemory-Level Parallelism — outstanding concurrent memory requests; hides latency as stalls.
PEBSPrecise Event-Based Sampling — Intel hardware feature tiering engines use to estimate page hotness.
ARMSAdaptive and Robust Memory tiering System — the state-of-the-art engine TierSizer is built on top of.
RSSResident Set Size — a workload's total memory footprint (Table 1).
SLOService-Level Objective — the performance target TierSizer must not violate.
CHACache/Home Agent queues — their occupancy is used as a proxy for MLP.
NBFNumber of Blocking Faults — page faults that stall a thread mid-migration.
DRAM — the fast tier CXL — the slow tier TierSizer's models/controller the performance target
1Tiered memory and CXL, in one paragraph▾

A tiered system gives the OS two pools of main memory: fast local DRAM and a larger, cheaper, slower pool attached over CXL (here ≈90ns unloaded vs ≈180ns — roughly 2× the latency). A tiering engine (e.g. ARMS, TPP, HeMem, Memtis) decides which pages sit in which tier.

Now you're ready: TierSizer doesn't decide which pages go where — that's the tiering engine's job. It decides how big the DRAM pool should be in the first place.
2LLC misses and CPU stalls▾

When data isn't in cache, the CPU fetches it from memory and waits — that wait is a stall. A DRAM access stalls less than a CXL access, simply because CXL is farther and slower. More stall cycles per instruction means a slower program.

Now you're ready: shrinking DRAM moves some accesses to CXL. The paper's whole stall model exists to predict how many extra stall cycles that causes.
3Memory-level parallelism (MLP) — why latency ≠ stalls▾

If a CPU can have many memory requests in flight at once, their latencies overlap — the second request's wait is mostly "free" if it started while the first was still outstanding. That's MLP. A high-MLP workload hides most of a CXL access's extra latency; a low-MLP one exposes almost all of it as stalls.

Now you're ready: this is why the stall model can't just multiply access count by latency — it divides by MLP, and even then splits DRAM and CXL contributions separately (αD, αC).
4Page hotness and PEBS sampling▾

Tiering engines don't know a page's true access count — they estimate it by sampling a subset of memory accesses (via PEBS or page-table scans). Pages estimated "hot" stay in DRAM; pages estimated "cold" get demoted to CXL. Sampling means the estimate has noise, especially for pages accessed rarely.

Now you're ready: this noise is exactly what makes real tiering engines imperfect — and it's what TierSizer's misplacement model (§4.1) corrects for.
5Page migration and blocking faults▾

Moving a page between tiers takes time. If an application thread touches that exact page while it's mid-move, the thread faults and must wait for the migration to finish — a blocking fault. Smaller DRAM triggers more migrations (more thrashing), hence more chances to block.

Now you're ready: this is the paper's second source of slowdown — separate from, and additive to, LLC stalls.
6Bandwidth-latency curves▾

Memory latency isn't a fixed number — it rises as offered bandwidth approaches the channel's limit (queuing delay). A "bandwidth-latency curve," measured once per platform by sweeping load, lets you look up the latency a tier will deliver at a given traffic level, rather than assuming it's constant.

Now you're ready: TierSizer indexes these curves by predicted per-tier bandwidth at the counterfactual size to estimate L′D, L′C.
7Counterfactual reasoning▾

A counterfactual is a "what would have happened" question: what would this workload's slowdown be at a DRAM size it is not currently running on? You can't just try it — a bad guess could tank performance before you can react. So you must infer the answer from what's measurable at the current size.

Now you're ready: this is the paper's central move — two analytical models let TierSizer answer that question cheaply, every control period.
8Fitting a model online with linear programming▾

The stall model (Eq. 2) has a few unknown scaling parameters (αD, αC, β). Rather than guess them, TierSizer solves a small linear program every 30 seconds that finds the parameter values best matching recently measured stalls — so the model tracks the workload's current behavior instead of a stale offline profile.

Now you're ready: this refit is what lets the same simple equation follow a workload across phases, without per-workload hand-tuning.
9Why conservative bias matters here▾

Two kinds of error are not symmetric: predicting too much slowdown just costs a little extra DRAM; predicting too little risks violating the performance target. The paper repeatedly chooses model variants that lean toward over-predicting slowdown.

Now you're ready: whenever you see a modeling choice in this paper, ask "which direction does this err?" — the answer is almost always "safely toward more DRAM."
10Why small steps, not big jumps▾

Performance-vs-DRAM curves have a knee: flat, then a cliff (Fig. 1). A model fit at one operating point is only trustworthy near that point — MLP and bandwidth shift as size changes. Stepping 10% at a time keeps every prediction inside the region where the model's assumptions still roughly hold, and keeps any mistake small and recoverable.

Now you're ready: this is why TierSizer is a controller, not a one-shot optimizer — it re-evaluates and re-steps every period.
The whole story in one place

TierSizer in a nutshell

The unsolved problem, the two-model fix, and why it's a controller rather than a one-time calculation.

Placement-focused tiering systems — AutoNUMA, TPP, HeMem, Memtis, ARMS, Colloid, Pond — all answer "which pages go where," given a fixed DRAM capacity. None of them answer the prior question: how much DRAM should that capacity even be? Operators default to fixed ratios (Google/Meta/Microsoft report 3:1 or 2:1) that either waste DRAM or silently violate performance on the wrong workload.

TierSizer's fix is a counterfactual predictor: estimate a workload's slowdown at a DRAM size it isn't running on, using only metrics measurable at the size it is running on. It decomposes slowdown into exactly two additive terms — Δstalls (extra LLC-miss stalls from accesses pushed to CXL) and ΔOmig (extra migration blocking) — each captured by a small analytical model rather than a learned black box, so it needs little data and adapts fast.

Crucially, both models explicitly account for a real, imperfect tiering engine: pages near the hot/cold boundary get misplaced due to sampling noise, and that misplacement is modeled directly (not folded into a generic error term). A controller then steps DRAM by ±10% each period, checking the counterfactual at neighboring sizes and moving toward the minimum that still meets a target — watching for phase changes that invalidate its fit.

The payoff: across 9 diverse workloads on ARMS, TierSizer saves 35% DRAM on average (up to 90%) versus a static 2:1 configuration, while staying within 5% of baseline performance on every workload.

🧮 Key takeaways

  • Fixed DRAM:CXL ratios (2:1, 3:1) are a one-size-fits-none heuristic; the right size is workload-specific and drifts.
  • Slowdown from resizing splits cleanly into Δstalls (LLC misses moved to CXL) and ΔOmig (migration blocking).
  • The stall model divides latency by MLP and keeps DRAM/CXL scaling factors (αD, αC) separate.
  • A real tiering engine misplaces pages near the hot/cold boundary — modeled via a PEBS-noise probability, not ignored.
  • Blocking faults scale roughly linearly with CXL access count (η=1) — no per-workload calibration needed.
  • Every modeling choice is deliberately biased to over-predict slowdown — safe errors cost DRAM, not SLOs.
  • The controller takes small (10%) steps and re-fits every 30s, staying inside the region its own model trusts.
  • Result: 35% avg DRAM savings, up to 90%, within 5% of baseline performance, layered on top of ARMS using its existing per-page counts, blocking-fault counts, and migration timings.
Six everyday pictures

How to think about TierSizer

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Sizing, not placement

Renting the smallest apartment that fits

Renting a bigger apartment than you need wastes money every month; renting one too small means constant clutter and trips to a storage unit. TierSizer is the tool that tells you the smallest apartment (DRAM size) where your stuff (working set) still fits comfortably — not which drawer each item goes in (that's the tiering engine's job).

Where it breaks: a landlord's price scales smoothly with square footage; DRAM's "cost" is a cliff — comfortable right up to the knee, then miserable. TierSizer is built specifically to find that cliff, not just minimize average size.
The controller · Small steps, conservative bias

Titrating a medication dose

A doctor lowering a dose doesn't jump straight to a guess — they step down gradually, watching for side effects, and are quicker to raise the dose back than to risk under-treating. TierSizer steps DRAM down 10% at a time, checks its predicted "side effect" (slowdown), and is deliberately biased to over-estimate the risk of shrinking further.

Where it breaks: a doctor gets a live read from the patient's body; TierSizer must predict the effect of a dose it hasn't given yet, from a model — that's the harder counterfactual step a doctor doesn't face.
Counterfactual reasoning · Predict, don't try

Guessing your commute without leaving early

You want to know if leaving 15 minutes later still gets you to work on time — but you can't test it without actually leaving late and risking being stuck. So you reason from what you already know: current traffic patterns, typical light timing, how sensitive your route is to delay. TierSizer reasons about a DRAM size it isn't running on the same way — from current access patterns and latency curves, never by "just trying it."

Where it breaks: your commute model uses other drivers' history; TierSizer's model is fit purely from the same workload's own recent behavior, which is why it must keep re-fitting as that workload's "traffic" shifts.
Insight 1 · PEBS misplacement

An eye chart's blurry line

On an eye exam, letters far above the threshold line you read easily, and letters far below you clearly can't — only the letters right at the blurry threshold get called wrong sometimes. Page hotness works the same way under sampling noise: pages far hotter or colder than the demotion cutoff are placed correctly; only pages near the boundary get misplaced, with the odds set by a normal-CDF, Φ(z), just like guessing at a blurry line.

Where it breaks: an eye chart's blur is fixed; a page's "blur" (its estimate's noise) shrinks with more samples (∝ 1/√h), so hotter pages near the boundary are actually less blurry than cold ones — the analogy simplifies away that asymmetry.
Migration overhead · Blocking faults

A moving crew mid-lift

If you reach for a box just as the movers are carrying it out the door, you have to wait for them to set it down before you can use it — even though you didn't ask for it to be moved right then. A blocking fault is exactly that: your thread touches a page at the exact moment it's being migrated, and must wait out the move.

Where it breaks: movers move on a fixed schedule; page migrations are triggered by access patterns, so more CXL traffic means more moves in flight — which is why blocking faults scale with CXL accesses, not with a clock.
Model simplicity · Robust extrapolation

A ruler, not a fitted spline

Given six dots roughly on a line, you can draw a straight ruler-line through them and confidently extrapolate one step beyond the data. A wiggly curve fit through the exact same six dots might match them better but flies off wildly one step outside — it memorized noise instead of the trend. TierSizer deliberately picks straight-line, few-parameter models for exactly this reason: refit is cheap and extrapolation to a nearby, untested size stays trustworthy.

Where it breaks: a ruler assumes the trend keeps going forever; TierSizer's models are trusted only near the current size — which is exactly why the controller takes small steps instead of extrapolating far.
The full explanation

How it actually works

From the slowdown decomposition to the controller's step-by-step loop, with the paper's key ideas rebuilt as diagrams.

1 · Splitting slowdown into two additive terms

Moving from DRAM size D to D′, the paper defines total slowdown as one equation (Eq. 1):

ΔP(D→D′) = (Δstalls + ΔO_mig) / cycles

Δstalls is the change in cycles the CPU spends waiting on LLC misses; ΔO_mig is the change in cycles threads lose to blocking faults during migration. These are additive and modeled separately because they come from different mechanisms — one is exposed memory latency, the other is a scheduling collision with the migration engine.

2 · The LLC-stall model

stalls = α_D·(A_D·L_D / MLP) + α_C·(A_C·L_C / MLP) + β  ± ε

AD, AC are accesses served by each tier (from hardware counters); LD, LC come from the bandwidth-latency curves; MLP comes from CHA queue occupancy. αD, αC — fit separately, not shared — absorb how much of each tier's latency actually surfaces as stalls, since MLP is a single aggregate number that doesn't say how DRAM and CXL accesses overlap among themselves. β captures stalls from pages the tiering engine doesn't manage (code, stack) — constant regardless of DRAM size.

🔎
Errors come from three places: averaging LD, LC, MLP over a 1-second window (acceptable since total stalls sum over every access, so only the average cost matters); offline-measured latency curves that ignore read:write mix and access size; and residual workload variation, all absorbed into ε.

3 · Insight 1 — modeling a real engine's misplacement

Shrinking by ΔD ideally demotes exactly the coldest ΔD resident pages. A real engine, using noisy PEBS samples, instead demotes each resident page i with probability set by how far its estimated access count sits from the new boundary, in units of its own sampling noise:

P_dem(i) = Φ(z_i),    z_i = (h★ − h_i) / √(h_i / p)

hi = page i's true access count, h★ = the count of the new boundary page, p = PEBS sampling rate, Φ = standard normal CDF. Expected demoted traffic ΔA = Σ hi·Φ(zi), summed so the total number of demotions still equals ΔD.

4 · Insight 2 — migration overhead scales with CXL traffic

Every migration is triggered by a slow-tier access becoming hot enough to promote (demotions rarely block, since cold pages aren't being touched). So blocking faults should track CXL access volume:

O_mig = N_BF · t_block,     t_block = t_mig / 2
N_BF(D′) = N_BF(D) · (A′_C / A_C)^η,     η = 1 (fixed, not fit per-workload)

tblock = tmig/2 because a fault arrives at a uniformly random point during an in-flight migration, so the expected wait is half the migration's duration. Fixing η=1 rather than fitting it per workload slightly overestimates NBF where the true growth is sublinear — again, the conservative default.

5 · The controller loop

  1. Monitor — every second, read AD, AC, bandwidth, LLC-stall cycles, MLP (from CHA occupancy), and pull per-page counts, NBF, and tmig from the tiering engine (ARMS).
  2. Fit — every 30 seconds, solve a small linear program (PuLP + CBC) for αD, αC, β against measured stalls.
  3. Predict — evaluate the counterfactual at D−ΔD and D+ΔD using the current fit, holding MLP fixed and only re-estimating the access split and blocking faults.
  4. Step — shrink by 10% if the predicted slowdown at D−ΔD stays within target; hold if not; grow immediately if the measured slowdown already exceeds budget.
  5. Watch — if tier-access ratio, bandwidth, or stalls shift abruptly (phase change, drift, co-tenant interference), refit immediately and revert to the last known-safe size if the target was crossed.
💡
Why this order matters: the model is trusted only near its fitting point, so every step re-grounds the model in fresh measurements before trusting its next prediction — never extrapolating far, never skipping the check.
Follow the numbers, step by step

Worked examples

Four traces through the paper's own equations and numbers — the stall model, the misplacement probability, blocking-fault scaling, and the reported DRAM savings.

① Estimating stalls with real latency numbers

The paper's hardware setup reports unloaded latencies of ≈90ns for local DRAM and ≈180ns for the emulated CXL tier. Suppose (illustrative counts) a 1-second period sees AD=8×10⁸ DRAM accesses and AC=2×10⁸ CXL accesses, with MLP≈8, αD=αC=0.6, and β negligible.

  1. DRAM term: αD·AD·LD/MLP = 0.6 × 8×10⁸ × 90×10⁻⁹s / 8 ≈ 5.4 s of stalls.
  2. CXL term: αC·AC·LC/MLP = 0.6 × 2×10⁸ × 180×10⁻⁹s / 8 ≈ 2.7 s of stalls.
  3. Total predicted stalls ≈ 8.1 s — larger than the 1 s period itself, a sign these illustrative access counts run far hotter than any real core could sustain; the per-term arithmetic, not the absolute total, is the point here.
  4. Now shrink DRAM: if ΔA=1×10⁸ accesses move from DRAM to CXL, the DRAM term drops by ≈0.675 s to ≈4.725 s, while the CXL term rises by ≈1.35 s to ≈4.05 s (2× the latency, same MLP) — net Δstalls ≈ +0.675 s, even though total access count didn't change.
🧮
Insight: each access that moves tier costs roughly α·(LC−LD)/MLP in extra stalls — here ≈0.6×(180−90)ns/8 ≈ 6.75ns per access, times however many accesses move. That per-access cost, not the raw latency gap, is what the model tracks.

② A page near the misplacement boundary

Using Eq. 4 (Insight 1): PEBS sampling rate p=0.01, boundary page's true count h★=1000. Consider a resident page i with true count hi=900.

  1. Noise term: √(hi/p) = √(900/0.01) = √90000 = 300.
  2. Distance from boundary: zi = (h★ − hi) / 300 = (1000−900)/300 ≈ 0.33.
  3. Demotion probability: Φ(0.33) ≈ 0.63 — this page is actually slightly colder than the cutoff, so a 63% chance of demotion here is a plausible, likely-correct call, not a misplacement.
  4. Compare a page far away: hi=100 → noise=√(100/0.01)=100, z=(1000−100)/100=9 → Φ(9)≈1.0 — correctly demoted with near-certainty.
💡
This is the arithmetic behind "only pages near the boundary get confused." A page 900 vs. boundary 1000 is genuinely ambiguous under sampling noise; a page at 100 is not — exactly the eye-chart analogy, quantified.

③ Scaling blocking faults to a smaller DRAM size

Suppose at the current size D, TierSizer measures NBF(D)=500 blocking faults and AC=1×10⁹ CXL accesses in the period. The counterfactual size D′ is predicted to raise CXL accesses to A′C=1.4×10⁹.

  1. Apply Eq. 6 with η=1: NBF(D′) = 500 × (1.4×10⁹ / 1×10⁹)¹ = 500 × 1.4 = 700 blocking faults.
  2. Convert to overhead (Eq. 3): if the average migration time tmig=20μs, then tblock=10μs, so Omig(D′) = 700 × 10μs = 7 ms.
  3. Compare to stalls: if Δstalls at D′ is predicted at ~8 s (Example ①'s scale), migration overhead (7 ms) is a small fraction of that total — matching the paper's own finding that migration overhead contributes only modestly to overall slowdown. The paper still models it as a separate additive term rather than folding it into ε, since that fraction isn't always negligible for every workload or size.
🧮
Insight: fixing η=1 means this estimate is exactly proportional — it costs nothing to compute and, per the paper, tends to overestimate at smaller sizes, which is precisely the direction that keeps the controller from over-shrinking.

④ Reading the paper's headline DRAM savings

Table 1 lists RSS for XSBench at 64.97 GiB. The paper reports TierSizer achieves up to 90% DRAM savings on XSBench versus the static 2:1 baseline, while every workload stays within the 5% slowdown target.

  1. Approximate the 2:1 baseline DRAM for a workload whose footprint ≈ RSS: DRAM:CXL=2:1 over a footprint of ~65 GiB gives DRAM ≈ (2/3)×65 ≈ 43 GiB (illustrative — the paper doesn't give this exact split, but the ratio's definition implies it).
  2. A 90% reduction from that baseline leaves DRAM ≈ 43 × (1−0.90) ≈ 4.3 GiB — TierSizer found that XSBench's actual hot set is a small fraction of its 65 GiB footprint.
  3. Average across all 9 workloads: the paper reports 34.6% average savings — consistent with GapBS-CC seeing ~0% (its stall model's residual error stayed too high to trust, so TierSizer safely made no change) pulling the average down from workloads like XSBench and Liblinear that save far more.
💡
The "0% for CC" case is the safety mechanism working as intended: an untrustworthy fit produces no resize, not a bad one — exactly the fail-safe direction the paper designs for throughout.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A workload has extremely high MLP (many outstanding requests at once). Its DRAM:CXL access ratio shifts sharply when DRAM shrinks. Does its stalls necessarily rise sharply too?
Show answer
Not necessarily. In Eq. 2, both the DRAM and CXL terms are divided by MLP — a high MLP workload overlaps and hides much of the added CXL latency, so Δstalls can stay small even when the access split shifts a lot. This is exactly why treating Δstalls/cycles as "the slowdown" is known to overestimate true slowdown for high-MLP workloads (§3), which the paper accepts deliberately since it errs conservative.Misconception: that access-count shift alone determines slowdown. Latency only becomes stall to the extent MLP fails to hide it.
Problem 2 · medium
Why does the model use two separate coefficients αD and αC instead of one shared α applied to both tiers' latency terms?
Show answer
MLP is a single aggregate count of concurrent outstanding requests — it says how much overlap exists overall, but not how DRAM and CXL accesses overlap among themselves, nor what fraction of each tier's specific latency is hidden. Rather than model that split explicitly, the paper lets αD and αC absorb it separately, fit online to match measured stalls.Misconception: that MLP alone fully determines exposed latency per access. It's an aggregate signal; the per-tier α's are what let the model stay accurate despite that aggregation.
Problem 3 · medium
Using Eq. 4, a page has true count hi=4h★ (four times hotter than the boundary). Without computing exactly, is it more or less likely to be misplaced than a page with hi=1.1h★? Why?
Show answer
Far less likely. zi = (h★−hi)/√(hi/p) grows both because the numerator (distance from boundary) is large and negative, and because a hotter page has proportionally more samples, shrinking its own noise term. Large |zi| pushes Φ(zi) toward 0 or 1 — correct placement. The 1.1h★ page sits close to the boundary in both count and (relative) noise, so its Φ(z) sits nearer 0.5 — genuinely ambiguous.Misconception: that misplacement risk is uniform across all resident pages. It's concentrated entirely near the boundary; pages far from it are placed correctly almost always.
Problem 4 · hard
The paper fixes η=1 in Eq. 6 rather than fitting it per workload from data. What does this cost, and why is it an acceptable trade given the paper's stated design principle?
Show answer
It costs some accuracy: if a workload's true blocking-fault growth is sublinear in CXL accesses (η<1), fixing η=1 overestimates NBF at smaller DRAM sizes. But the paper's stated principle is to bias every uncertain choice toward over-predicting slowdown, since that only costs a little extra DRAM rather than risking a target violation — and per-workload fitting would need more data and more time to converge, working against the goal of fast online adaptation.Misconception: that a fixed exponent is just a shortcut for lack of a better idea. It's a deliberate application of the paper's conservatism principle, traded against sample-efficiency.
Problem 5 · medium
GapBS-CC is the one workload where TierSizer achieves ~0% DRAM savings. Is this a failure of the approach? What does the paper attribute it to, and what protects the workload from a bad outcome?
Show answer
It's a safe non-result, not a harmful failure. CC's stalls vary continuously, faster than TierSizer's 30-second refit period can track, so the residual error ε stays high (~20%) and the model is untrustworthy. TierSizer's controller only shrinks when it trusts its prediction — an unreliable fit yields no resize rather than a wrong one, so CC simply keeps its baseline allocation and stays within target, at the cost of forgone savings.Misconception: that TierSizer always finds savings. It finds savings only where its (simple, fast) model can track the workload — that boundary is itself informative, not a bug.
Problem 6 · hard
Silo-TPC-C shows the model under-predicting stalls over time, even though most of the run stays within the ±ε error band. What is happening, and why doesn't a single point-in-time model catch it?
Show answer
Silo-TPC-C is write-heavy with a growing resident set and a recency-skewed ("latest") access distribution — newly inserted rows are hot, so the hot set keeps shifting forward continuously rather than settling into a stable pattern. A model fit on a recent window describes the recent past well, but by construction can't anticipate a hot set that keeps moving into never-before-seen territory. The ε band absorbs the error for a while, but widens over time as the mismatch compounds — a sign the fit itself, not just its noise, is going stale.Misconception: that staying inside the ±ε band always means the model is fine. A widening band over time signals the model no longer fits, even if no single point has crossed it yet.
Problem 7 · easy
Why does TierSizer step DRAM size by only ~10% per period instead of jumping directly to its best current estimate of the optimal size?
Show answer
Two reasons. First, safety: a large jump risks overshooting a performance cliff (Fig. 1's knees can be sharp) before the controller can react, while a misjudged small step is easily recoverable next period. Second, accuracy: the model's inputs (access counts, latencies, MLP, fitted α/β) are only valid near the current operating point — small steps keep every prediction inside that trusted region.Misconception: that the model directly computes "the" optimal size and the controller just applies it. The model is only locally valid; stepping is what keeps its predictions honest.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1How is TierSizer different from a tiering system like TPP, HeMem, or Memtis?▾
Those systems solve placement: given a fixed DRAM capacity, which pages go in DRAM vs. CXL. TierSizer sits above them and solves sizing: how big should that DRAM capacity be in the first place. TierSizer is evaluated on top of ARMS, an existing placement engine, and doesn't change how pages are chosen — only how much room they have to work with.
Q2Why not just profile each workload offline and pick a size once?▾
Production workloads are too diverse and evolve too fast for offline profiles to stay accurate — a profile taken today can go stale as access patterns drift (as Silo-TPC-C illustrates). TierSizer instead fits its (cheap) model online from live metrics, so it tracks the workload as it actually runs.
Q3Why not just try a smaller size and measure what happens?▾
Blind exploration is dangerous: Figure 1 shows some workloads (Embedding-Reduction) degrade sharply right past a modest shrink. If you tried it and it was bad, you'd have already violated the performance target before you could react. The counterfactual model predicts the outcome before committing to the resize.
Q4What exactly does "counterfactual" mean in this paper?▾
Predicting what a workload's slowdown would be at a DRAM size it is not currently running on — using only metrics measurable at the size it is running on now. It's the same logical move as "what if I left 15 minutes later," answered from current conditions rather than by actually leaving late.
Q5Why does the migration model matter if LLC stalls dominate slowdown?▾
Stalls are the dominant source on average, but migration blocking is not negligible for every workload or size — the paper models it explicitly rather than lumping it into the stall model's error term, because it comes from a genuinely different mechanism (a fault racing a migration, not memory latency).
Q6Is TierSizer biased in a specific, useful direction?▾
Yes, deliberately. Nearly every uncertain modeling choice — using Δstalls/cycles as slowdown, assuming ideal promotion when growing, fixing η=1 for blocking faults — is chosen to over-predict slowdown rather than under-predict it. Over-prediction just costs a bit of extra DRAM; under-prediction risks violating the target.
Q7How expensive is TierSizer to run?▾
Cheap: metrics are read once per second from existing hardware counters and the tiering engine's own bookkeeping; the linear-program refit runs every 30 seconds and is lightweight, off the application's critical path. No new hardware is needed — this is a software controller layered on an existing tiering system.
Q8Does TierSizer always find DRAM to save?▾
No — on GapBS-CC it saves ~0%, because CC's stalls change faster than the model's fitting window can track, keeping residual error too high to trust a resize. This is treated as a safe outcome (no change) rather than a failure, consistent with the paper's conservative design.
Q9Why measure bandwidth-latency curves offline instead of modeling latency as a constant?▾
Memory latency rises with load due to queuing — it isn't fixed. A one-time-per-platform sweep of offered bandwidth vs. resulting latency lets TierSizer look up the right latency for the predicted bandwidth at a counterfactual size, rather than assuming today's latency holds regardless of traffic.
Q10What's left unresolved or for future work?▾
The paper's own limitation, seen in Silo-TPC-C, is workloads with continuously shifting, growing hot sets — no recent window predicts what comes next for those. More generally, the approach assumes a bandwidth-aware tiering engine (like ARMS or Colloid) that keeps DRAM out of its bandwidth-saturated region; a poorly-behaved engine would need the model's assumptions revisited.

Core terms
TierSizerThe paper's online predictor + controller: sizes DRAM on a tiered system by predicting slowdown counterfactually and stepping toward the minimum that meets a target.
Counterfactual slowdownPredicted performance loss at a DRAM size the workload is not currently running on, computed from metrics at the size it is running on.
ΔstallsChange in LLC-miss stall cycles caused by resizing DRAM — the dominant slowdown term (Eq. 2).
ΔO_migChange in migration-blocking overhead caused by resizing DRAM — the secondary, additive slowdown term (Eq. 3, 6).
Blocking faultA page fault that occurs when a thread touches a page mid-migration and must wait for the move to finish.
Misplacement probability Φ(z)Insight 1's model of how often a real (PEBS-driven) tiering engine demotes the wrong page near the hot/cold boundary.
Marginal exponent ηFixed at 1 in Eq. 6 — sets how blocking faults scale with CXL access count; deliberately not fit per workload.
2:1 / 3:1 ratioIndustry-standard fixed DRAM:CXL capacity ratios (reported by Google, Meta, Microsoft) that TierSizer is compared against.
Supporting terms
MLPMemory-level parallelism — outstanding concurrent memory accesses; hides latency as stalls when high.
PEBSPrecise Event-Based Sampling — the hardware mechanism used to estimate per-page hotness.
Bandwidth-latency curveOffline-measured mapping from offered memory bandwidth to resulting loaded latency, per tier.
ARMSAdaptive and Robust Memory tiering System — the placement engine TierSizer is implemented on top of.
CHA queue occupancyOn-chip Cache/Home Agent queue depth, used as a proxy signal for measuring MLP.
PuLP / CBCThe Python linear-programming toolkit and solver backend used to online-fit αD, αC, β every 30 seconds.
RSSResident Set Size — total memory footprint of a workload, listed per-benchmark in Table 1.
ε (residual error)The bounded slack absorbing everything the simple model doesn't explicitly capture — window averaging, curve indexing, workload noise.
Results at a glance
Source notes

From the paper (facts): the slowdown decomposition (Eq. 1–3), the stall model and its calibration via linear programming, the misplacement probability model (Eq. 4–5) and blocking-fault scaling (Eq. 6, η=1), the 10%-step controller with 30s refit, the ARMS-based implementation, the 9-workload evaluation (Table 1), the headline results (34.6% avg / 90% peak DRAM savings, ≤5% slowdown target met on all workloads, 2.27% median stall-model error), and the GapBS-CC and Silo-TPC-C limitation cases.

My framing (not in the paper verbatim): the eye-chart, apartment-rental, medication-titration, commute-guessing, moving-crew, and ruler-vs-spline analogies; the illustrative worked-example numbers in tabs 5–6 (access counts, page-hotness values, blocking-fault counts) explicitly flagged as illustrative; the interactive slider's XSBench/Embedding-Reduction curve shapes, shaped to match the knee locations described in the paper's Fig. 1 discussion but not read off exact pixel values; and all SVG diagrams, which are original renderings of the paper's equations and Fig. 1/2 concepts, not reproductions of the paper's actual figures.

Related systems mentioned in the paper

TPP, AutoNUMA, HeMem, Memtis, Pond, Colloid medium

tiering placement systems, cited §2

All solve data placement given a fixed DRAM capacity — the layer beneath TierSizer, and the systems the reader's own tiering work sits alongside.

ARMS easy

Yadalam, Kanellis, Swift, Venkataraman · arXiv 2025

The specific state-of-the-art tiering engine TierSizer is built and evaluated on top of in this paper.

AOL — tiered memory beyond hotness medium

Liu, Hadian, Xu, Li · OSDI 2025

Predicts slowdown for a fixed placement (all-CXL), and is the source of the CHA-based MLP estimation TierSizer reuses. Doesn't size DRAM at intermediate points.

PROFET hard

Radulovic et al. · SIGMETRICS 2019

Offline analytical model relating latency/bandwidth to performance for a uniform memory system — TierSizer's stall model shares its intuition but must handle tiering's non-uniform latency shift instead.

Vulcan & Tuna medium

Tang et al. 2025 · Chen et al. 2024

The two closest prior attempts at the sizing problem: Vulcan allocates a fixed DRAM pool across co-runners (not per-workload sizing to a target); Tuna sizes from offline microbenchmark matching (static, generalizes poorly).
