Give the fair scheduler's weight to whoever is about to unlock the GPU

A short CPU "feeder" task preps the next GPU launch, but Linux fair scheduling only sees CPU service and sleep/wake events — it can't tell that feeder apart from the middleware timer that just happens to look the same. This is the plain-English story of AGX, a weight-only extension that fixes it.

📄 "Linux AGX" · Shirvani & Liu, UC Riverside 🎓 Assumes CFS/EEVDF familiarity roughly at kernel-doc level ⏱ ~30 min read
🤖

Bias the scheduler's weight toward whoever is gating GPU progress, not whoever merely requests short slices and sleeps often.
Measure it in user space, apply it as one number, change nothing else.

Before you begin

Quick glossary, then the primers

Acronyms first, so nothing below is opaque. Then eight short primers — open whichever concept is fuzzy.

AGXAdaptive GPU eXtension — the paper's mechanism: a weight-only extension to Linux fair scheduling.
EEVDFEarliest Eligible Virtual Deadline First — the fair-scheduling algorithm in Linux ≥6.6.
CFSCompletely Fair Scheduler — the older min-vruntime fair scheduler, still common on vendor/embedded kernels.
DAGDirected acyclic graph — the task-dependency graph of a robotic pipeline.
CPSCritical-Path Stretch — makespan ÷ measured critical-path sum; 1.0 is perfectly efficient.
L4TLinux for Tegra — NVIDIA's embedded Linux distribution for Jetson boards.
MPSMulti-Process Service — NVIDIA's mechanism for sharing one GPU context across processes.
Jain's indexA fairness statistic on dominant resource shares; 1.0 = perfectly balanced.

1Proportional-share weight, in one line▾

Linux fair scheduling gives each runnable task a weight (from its nice value). Over any interval, a backlogged task's CPU share should track weighti ÷ Σweights — that's the whole fairness contract. AGX's entire intervention is replacing this one weight with a computed effective weight; nothing else about the scheduler changes.

Now you're ready: everything AGX does is describable as "same scheduler, different weight number."
2CFS's min-vruntime vs EEVDF's eligible-deadline pick▾

CFS tracks each task's virtual runtime (CPU time ÷ weight) and always runs whoever has the smallest value. EEVDF refines this: each request gets a virtual eligible time and virtual deadline; among tasks eligible right now, it runs the earliest deadline. Crucially, a task requesting a shorter slice earns an earlier deadline and gets to run sooner — this is EEVDF's built-in "interactivity" trick.

Now you're ready: EEVDF already helps short tasks — but it can't tell a short task that matters (a GPU feeder) from a short task that doesn't (a log flush). That blind spot is AGX's target.
3Lag: how "fair so far" is measured▾

Lag is the gap between the CPU service a task should have gotten under an ideal fluid proportional-share model and what it actually got. EEVDF (and CFS) guarantee this gap stays bounded by roughly one request size — no task drifts arbitrarily far behind or ahead.

Now you're ready: AGX's fairness proof (Thm 5.2) is exactly this bounded-lag guarantee, just measured against AGX's effective weights instead of the base ones.
4Feeder, gate, and gating slice▾

The feeder is the CPU thread that prepares and submits a GPU kernel. Its pre-launch CPU work is the gating slice; the gate is reached once that CPU work is done and the kernel can launch. Gate delay is the wall-clock wait to reach the gate.

Now you're ready: AGX's whole job is shrinking gate delay without touching anything else about the scheduler.
5Micro-preemption — the paper's specific failure mode▾

Streams of short, frequently-waking CPU tasks (middleware timers, driver callbacks) repeatedly become eligible with earlier deadlines than the feeder's current request, fragmenting the feeder across many dispatch rounds even though its total work is small. CPU-level fairness holds; the GPU still idles.

Now you're ready: this is the paper's Fig. 14 adversarial pattern — the concrete thing AGX's bounded boost is built to neutralize.
6Critical path and makespan▾

In a dependency graph, the critical path is the longest chain of dependent stages that determines the earliest possible finish time. Makespan is the actual end-to-end completion time. If CPU scheduling delays a critical-path GPU node's upstream feeder, the whole graph slips even if every other task is on time.

Now you're ready: AGX's payoff metric (CPS, Sec 6.6) is literally makespan ÷ critical-path sum — how close the system runs to the ideal 1.0.
7Why this reads like your tiering work▾

AGX's user-space profiler samples per-task signals every 250 ms, computes a bounded importance score, and pushes one batched update to the kernel — a windowed, sampled, decay-free control loop applying a numeric bias to an existing mechanism. That shape (periodic epoch, bounded score, cheap kernel-side application) is structurally the same move that epoch-based hotness trackers in tiered-memory systems (à la TPP, HeMem, Memtis) make for page promotion/demotion, just for CPU weight instead of page placement.

Now you're ready: read AGX's c_i importance score the way you'd read a hotness counter, and its κ knob the way you'd read a promotion aggressiveness knob.
8Jain's dominant-share fairness▾

With both CPU and GPU in play, a task's dominant share is the larger of its CPU-share and GPU-share (fraction of capacity used). Jain's index over these dominant shares summarizes overall balance in [0,1], with 1 meaning perfectly even sharing.

Now you're ready: the evaluation reports this alongside makespan to show AGX isn't buying speed by silently starving everyone else.
The whole story in one place

AGX in a nutshell

The blind spot, the two tightly-scoped fixes, and why the guarantees still hold.

Linux fair scheduling (EEVDF on modern kernels, CFS on older ones) sees only CPU service and sleep/wake events. It rewards a specific behavioral signature — request short slices, sleep often — with earlier dispatch, because on desktops that signature happens to correlate with "interactive." In ML-driven robotic pipelines it doesn't: the CPU feeder that gates the next GPU launch and an unrelated middleware timer both look short and sleepy, so the scheduler can't tell them apart or track which one currently sits on the critical path.

AGX fixes this through the narrowest possible interface: the weight used in virtual-deadline computation and virtual-time accounting. A user-space profiler computes a bounded importance score c_i ∈ [0,1] per task every window (default M = 250 ms) from its GPU share, CPU→GPU handoff frequency, and optional dependency criticality. The kernel turns this into an effective weight w_eff = w0·(1+κc_i) — a long-term bias. Separately, while a gate is pending, a bounded temporary boost λ (capped at 1+κ) gives the feeder just enough share to clear one base request within a short gating-response horizon τ = 5 ms. Everything else — EEVDF's eligibility test, deadline ordering, pick logic — is untouched.

The payoff: across three NVIDIA platforms, AGX-EEVDF cuts makespan by 6.0–20.0% and lifts GPU utilization by 7.6–22.1% versus vanilla EEVDF. Under background CPU pressure it cuts p99 perception-to-control latency by 38.5% and deadline misses by 33.8 percentage points, while keeping CPU-only Jain's fairness ≥0.94 and total scheduler+profiler overhead under 2% of one core (8.7–17.7 CPU-ms/s at default settings).

🍯 Key takeaways

  • EEVDF rewards a behavioral signature (short slice + frequent sleep), not actual GPU-gating criticality.
  • AGX changes exactly one interface: the weight used in virtual-deadline computation and accounting.
  • Effective weight (long-term, windowed) and bounded boost (short-term, event-driven) operate at complementary timescales.
  • κ=0 or daemon-off ⇒ AGX is algebraically vanilla EEVDF — fail-safe by construction.
  • Proven: bounded proportional fairness w.r.t. effective weights (Thm 5.2); K-independent gate-delay bound when the boost isn't clipped, bounded coalescing when it is (Thm 5.5).
  • Result: 6.0–20.0% shorter makespan, 7.6–22.1% higher GPU utilization, <2% of one CPU core overhead.
Five everyday pictures

How to think about AGX

Read in any order. Each ends with where the picture stops being true.

Critical path · Feeder/gate

Relay race baton handoff

Your team's fastest sprinter (the GPU) can't leave the blocks until the baton (the feeder's CPU prep) arrives. If the runner carrying the baton keeps getting shoved aside at the exchange zone by kids racing for snacks, the fast sprinter stands idle — the team's overall time is set by the handoff, not by the sprint.

Where it breaks: a real handoff is a single event; a gating slice can itself be split across many CPU dispatches, which is exactly the fragmentation AGX targets.
Bounded boost λ

An ambulance's temporary siren

An ambulance doesn't own the road permanently — it gets a temporary right-of-way exactly while carrying an active call, capped by traffic law, and yields the moment the call ends. AGX's boost λ is the same: active only while the gate flag is set, capped at 1+κ, released the instant the launch is submitted, cancelled, or times out.

Where it breaks: a real ambulance's priority is nearly unbounded in an emergency; AGX's boost is deliberately capped, so under extreme contention it degrades to bounded coalescing rather than an unbounded override.
The core blind spot

The loud kid vs. the quiet expert

A teacher who calls on whoever's hand shoots up fastest and most often ends up favoring the loud kid, not the one who actually knows the answer. EEVDF's "shorter request ⇒ earlier deadline" rule is the loud-kid heuristic: it favors a behavioral signature, not demonstrated importance — and a GPU feeder and an irrelevant middleware timer can raise their hands equally fast.

Where it breaks: the loud kid isn't malicious; EEVDF's heuristic is genuinely useful for desktop interactivity. It only misfires when many equally "loud" tasks compete and none of them is labeled.
Effective weight

A toll discount card

A frequent, high-priority commuter gets a discounted toll rate — they still pay for road use, just less per mile, so they can make more trips for the same budget. AGX's effective weight is a virtual-time discount: w_eff = w0(1+κc_i) means a critical task is charged less virtual time per real CPU cycle, so it becomes eligible again sooner.

Where it breaks: a toll discount is usually permanent per commuter class; AGX's discount is recomputed every 250 ms from fresh measurements, so it can rise, fall, or vanish as the task's actual GPU-gating role changes.
Profiling window M

A weather forecast, refreshed hourly

An hourly forecast is accurate enough for most planning, but if a storm forms in the last ten minutes of the hour you're still working off stale data until the next refresh. AGX's profiler recomputes importance every M = 250 ms — plenty for most pipeline phases, but a critical-path shift inside that window is invisible until the next tick.

Where it breaks: this is exactly the failure the paper reports on twolf-vpr/gzip-twolf-style fast-phasing workloads, where vanilla EEVDF's continuous, per-access adaptation occasionally beats AGX's coarser, windowed one.
The full explanation

How it actually works

Mechanism by mechanism, with the two equations and their guarantees.

1 · The problem — a behavioral signature, not a criticality signal

EEVDF improves latency over CFS through two channels: shorter requests earn earlier virtual deadlines, and sleeping tasks retain lag that decays rather than resets. Neither channel knows which task matters — both just favor "requests short slices, sleeps often." In a robotic pipeline, the GPU feeder and a dozen unrelated middleware/logging/timer threads present that same signature, so vanilla EEVDF can't prioritize the one that's actually gating the GPU, nor notice when the critical path shifts to a different task.

2 · Effective weight — a long-term, windowed bias

w_eff_i ≜ w0_i · (1 + κ·c_i)     // κ≥0 sensitivity knob, c_i∈[0,1] windowed importance

c_i is computed in user space every window M (default 250 ms) as the equal-weight average of three normalized signals (Eq. 2):

ρ_i = ΔtGPU_i / (ΔtCPU_i + ΔtGPU_i + ε_t)    // GPU-share
g_i = NCPU→GPU_i / (NCPU_i + ε_n)          // handoff frequency
d_i = d_idx_i / D_max                        // optional dependency criticality
c_i = (ρ_i + g_i + d_i) / 3
🌱
A task with no GPU activity gets c_i≈0, so w_eff≈w0 — identical to vanilla behavior. Because w_eff is fixed within each weight epoch, AGX is algebraically vanilla EEVDF run on different static weights during that epoch (Lemma 5.1) — this is what makes the fairness proof possible.

3 · Bounded boost — a short-term, event-driven override

Define the coverage threshold θ ≜ Δ/(Cτ): the proportional share that supplies one base request Δ within one gating-response horizon τ, on C cores. While the gate is active, AGX raises the feeder's weight to the smallest bounded factor that restores this coverage:

λ ≜ min( 1+κ,  max( 1,  θ/(1−θ) · S_B/w0_B ) )
w_eff_B ← max( w_eff_B, λ·w0_B )     // S_B = total competing effective weight

Heavy contention (large S_B) needs a bigger boost; light contention needs none (λ=1). Once the launch is submitted, cancelled, or times out, the boost is cleared — CPU-only tasks see no interference while no gate is pending.

4 · Enforcement — EEVDF's pick logic is untouched

// every window M: refresh effective weights
for i in R: w_eff_i ← w0_i·(1+κ·c_i)

// on gate flag set for feeder B
if gate_active(B): w_eff_B ← max(w_eff_B, λ·w0_B)

// unchanged EEVDF dispatch
i* ← EEVDFPick(R, {w_eff})
run(i* under its EEVDF request); account(i*, δ, w_eff_i*)
💡
Why keep two mechanisms? Effective weight answers "who has been gating GPU progress over recent windows"; the boost answers "who needs to clear a specific pending gate right now." Collapsing them into one signal would either react too slowly (window-only) or overreact to noise (boost-only).

5 · Specializing to CFS and beyond

AGX depends only on (i) a virtual-time charge rule keyed to a weight, and (ii) a bounded service quantum. Swap EEVDF's eligible-deadline pick for CFS's min-vruntime pick and the same effective-weight substitution and boost logic apply, with an analogous "bounded virtual-runtime spread" lemma standing in for bounded lag (App. D). More broadly, any proportional-share scheduler with a monotone least-served-progress notion and a bounded quantum can host AGX.

Follow the numbers

Worked examples

Four traces: computing the two AGX numbers by hand, then checking them against the paper's measured results.

① Effective weight from the importance score (Eq. 1–2)

A feeder has base weight w0=1024 (nice 0). Over one window: ΔtGPU=15 ms, ΔtCPU=5 ms; it issued 8 of its 20 CPU dispatches with a GPU launch; no dependency tag. With κ=1, find w_eff.

  1. GPU share: ρ = 15/(5+15+ε_t) ≈ 15/20.001 ≈ 0.75.
  2. Handoff frequency: g = 8/(20+1) ≈ 0.38.
  3. Dependency tag absent ⇒ d = 0.
  4. c_i = (0.75+0.38+0)/3 ≈ 0.38.
  5. w_eff = 1024·(1+1·0.38) ≈ 1413 — a ~38% virtual-time discount versus a task with c_i≈0.
🍯
Insight: a task with no dependency metadata still gets a meaningful boost purely from GPU share and handoff frequency (Sec. 4.4's fallback iii) — c_i=0 only for genuinely GPU-irrelevant tasks.

② Is the boost clipped? (Eq. 3)

C=2 cores, τ=5 ms, Δ=3 ms (a typical base slice), κ=1 (cap 1+κ=2). Twelve equal-weight competitors, so S_B/w0_B=12.

  1. θ = Δ/(Cτ) = 3/(2·5) = 0.3.
  2. Requested factor = θ/(1−θ) · S_B/w0_B = (0.3/0.7)·12 ≈ 5.14.
  3. Compare to cap 1+κ = 2: 5.14 > 2, so the cap binds: λ = 2.
  4. This matches the paper's measured cap-hit rate of 55% of gate episodes at K=12 (Sec. 6.7, App. B.1) — heavy contention routinely saturates λ.
💡
Even capped, AGX still improves feeder share from 1/13 (≈0.077) to 2/(2+11)≈0.154 — double — which is why the paper still measures a ~2× delay reduction (34.5→13.8 ms) even when the bound isn't strictly K-independent.

③ Gate delay: vanilla EEVDF vs AGX (Appendix B.1, real numbers)

Short-vs-short contention, K=12 competing tasks, mean per-run p99 feeder-ready-to-submit delay over 10 runs.

  1. CFS: 34.5 ms p99 delay.
  2. Vanilla EEVDF: 33.3 ms — within 4% of CFS, since request-length alone can't distinguish similarly-short tasks.
  3. AGX-EEVDF: 13.8 ms — a 58.6% reduction versus EEVDF, by identifying which short task is actually gating GPU progress.
  4. At this K, the boost is capped in 55% of gate episodes, so this is the "bounded coalescing" regime (Remark 5.6), not the strict K-independent bound — yet the reduction is still large.
🍯
Insight: the explicit short-vs-long experiment (Fig. 15a) shows EEVDF alone gets most of the way there (44.6→27.1 ms, 39.2% over CFS) when request size differs; AGX's extra 21.0% comes specifically from resolving the short-vs-short case EEVDF's own mechanism can't see.

④ Overhead tally on Jetson Orin AGX (Sec. 6.5, N=100)

  1. Baseline scheduling cost (shared with vanilla EEVDF): 1.72 ms/window.
  2. Total with AGX: 3.33 ms/window — AGX adds 1.61 ms/window.
  3. Breakdown of the add: user daemon ≈0.93 ms + mark_gpu() ≈0.40 ms + update_weight ≈0.28 ms ≈ 1.61 ms. ✓ matches.
  4. As a rate: 1.61 ms per 250 ms window = 6.44 CPU-ms/s, i.e. ≈0.64% of one core — inside the paper's reported 8.7–17.7 CPU-ms/s range across platforms.
💡
The components scale sublinearly with runnable-task count (Sec. 6.5), so this overhead stays small even as pipeline complexity grows — important for long-running robotic deployments.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A task requests very short slices and sleeps frequently, but never submits GPU work. Under AGX, what is its w_eff, and why?
Show answer
w_eff ≈ w0, its base weight. With no GPU share, no CPU→GPU handoffs, and (absent metadata) d=0, c_i≈0, so w_eff = w0(1+κ·0) = w0. It keeps EEVDF's normal short-slice advantage but gets no extra AGX bias.Misconception: that AGX boosts every short/sleepy task. It boosts only tasks whose measured signals show GPU-gating or dependency criticality — "short and sleepy" alone earns nothing extra.
Problem 2 · medium
Compute w_eff for w0=512, ρ=0.4, g=0.5, d=0.3, κ=2.
Show answer
c_i = (0.4+0.5+0.3)/3 = 0.4. w_eff = 512·(1+2·0.4) = 512·1.8 = 921.6.Misconception: forgetting κ multiplies c_i, not adds to it directly — doubling κ roughly doubles the discount's strength, not the score itself.
Problem 3 · medium
Why is the boost capped at 1+κ instead of always granting whatever λ Eq. 3 computes?
Show answer
An unbounded λ under heavy contention (large S_B) would let the feeder starve every competitor arbitrarily, breaking AGX's fairness guarantee entirely and risking priority inversion on background work. Capping means that under extreme contention AGX falls back to "bounded coalescing" (Remark 5.6) — a weaker but still bounded guarantee — rather than an unbounded override.Misconception: that hitting the cap means AGX "fails." It still substantially improves the feeder's share relative to vanilla; it just no longer guarantees full K-independence.
Problem 4 · hard
Does increasing κ from 0 to 2 violate EEVDF's fairness guarantee? What does Theorem 5.2 actually promise?
Show answer
No. Theorem 5.2 promises bounded proportional service with respect to the effective weights currently in force — the same structural form as vanilla EEVDF's guarantee, just restated in effective-weight space. It does not promise tasks keep their original base-weight share once κ>0. Setting κ=0 recovers the vanilla guarantee exactly.Misconception: that "preserves fairness" means "preserves the original shares." It means the new shares (however biased) are themselves delivered fairly and predictably, with a bound that doesn't grow with interval length.
Problem 5 · medium
On CPU-bound stress-ng (no GPU work at all), what should AGX-EEVDF's makespan and GPU utilization look like relative to vanilla EEVDF, and why?
Show answer
Essentially identical — the paper reports AGX-EEVDF within ~3% of vanilla EEVDF on stress-ng. With no GPU activity, every task's ρ, g ≈0, so c_i≈0 and w_eff≈w0 for everyone; no gate is ever pending, so λ=1 always. AGX degrades cleanly to vanilla behavior.Misconception: that AGX always biases toward "the busiest" task. It only biases toward measured GPU-gating/dependency signals — absent those signals, there's nothing to bias.
Problem 6 · hard
Table 1's ablation shows removing effective weights (keep only the boost) hurts makespan more (+9.3%) than removing the boost (keep only effective weights, +5.6%). Why might the longer-timescale mechanism matter more here?
Show answer
The boost only fires reactively once a gate is already pending, fixing a symptom moment-to-moment; effective weights proactively keep the feeder eligible and well-positioned across the whole window, reducing how often the feeder falls behind enough to need rescue in the first place. Removing effective weights means every gate has to be recovered from a worse starting position, inflating both makespan and dependency delay (24→38 ms).Misconception: that the boost is the "main" AGX mechanism because it's the more dramatic, event-driven one. The windowed reweighting is what prevents most gate crises from becoming severe in the first place.
Problem 7 · easy
Why does AGX target CFS as well as EEVDF, given modern kernels default to EEVDF?
Show answer
Many production robotic and embedded stacks (Jetson-class L4T builds, Yocto-based systems) still run older or vendor kernels where CFS remains the effective fair-class policy. Since AGX only needs a virtual-time charge keyed to a weight and a bounded service quantum — both present in CFS — the same mechanism transfers by swapping EEVDF's eligible-deadline pick for CFS's min-vruntime pick.Misconception: that AGX is an EEVDF-only patch. Its guarantees are stated generally enough (proportional-share weights + bounded quantum) to specialize to CFS and generalize to future fair schedulers.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does AGX change in the kernel?▾
One thing: the weight used in virtual-deadline computation and virtual-time accounting. It replaces the base weight with a computed effective weight and, while a gate is pending, applies a bounded temporary boost to that weight. EEVDF's eligibility test, deadline ordering, and pick logic are all unchanged.
Q2Why not just redesign the scheduler for GPU awareness?▾
The authors' measurements suggest EEVDF's core pick/eligibility logic isn't the root cause — it's already deeply integrated with cgroups, load balancing, and RT/Deadline classes, so replacing it would sacrifice compatibility. Targeting the weight interface gets the fix with minimal blast radius.
Q3Does AGX require changing the application or ROS graph?▾
No. Dependency metadata is optional — if a ROS executor or launch graph exposes stage structure, AGX uses it; if not, AGX still works from inferred GPU-share and handoff-frequency signals alone (d_i=0 fallback), staying within 3% of the best tested configuration across the evaluated workloads.
Q4How is this different from tuning nice or latency_nice?▾
Static tuning (EEVDF+Tune) helps briefly right after retuning but decays mid-stage as the critical path shifts, since it isn't updated continuously. AGX recomputes its signal every profiling window and reacts immediately to gate events, tracking phase changes without manual intervention.
Q5What's the actual overhead?▾
8.7–17.7 CPU-ms/s total (scheduler hooks + user daemon) at the default 250 ms window — under 2% of one CPU core across all three test platforms.
Q6Does AGX ever make things worse than vanilla EEVDF?▾
Occasionally, on workloads with phase changes faster than the 250 ms profiling window (e.g. twolf-vpr, gzip-twolf style mixes), where vanilla EEVDF's continuous per-access adaptation can outrun AGX's coarser windowed one. This is an explicit, acknowledged trade for low overhead.
Q7What happens if the user-space daemon crashes or is disabled?▾
AGX degrades cleanly to vanilla fair scheduling — c_i is never refreshed, so effective weights stay at their last (or base) values and no new boosts are triggered. Setting κ=0 has the same effect algebraically.
Q8Does AGX generalize beyond a single GPU?▾
Yes — Sec. 5.3 sketches per-device queues for multi-GPU/heterogeneous accelerators (same coverage/coalescing argument per device) and an effective-capacity term for heterogeneous CPUs. The core requirement is just proportional-share weights plus a bounded service quantum.
Q9How does AGX relate to application-level schedulers like DREAM?▾
Complementary, not competing. DREAM decides the logical DAG order at the framework level; Linux still has to dispatch the resulting runnable threads amid callbacks and middleware, which is where AGX's gap-filling applies. DREAM+AGX further reduces makespan by 1.8–3.9% over AGX-EEVDF alone.
Q10Is AGX's importance score like a hotness counter in tiered memory systems?▾
Structurally, yes — both are periodic, bounded, sampled scores computed cheaply and applied as a coarse-grained bias to an existing mechanism (CPU weight here, page placement in tiering). The key difference: AGX has no promotion/demotion state machine or migration cost to amortize — it just rewrites one number every window.
Q11Why 250 ms for the profiling window and 5 ms for the gating-response horizon?▾
Sec. 6.7's sweep shows a sweet spot near M≈250 ms balancing responsiveness against daemon overhead and noisy estimates; τ=5 ms is a separate, much finer-grained target for how quickly one base request should clear once a gate is pending. The two knobs are set independently because they answer different questions.
