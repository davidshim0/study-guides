Paying the WAL tax once, not once per record

A ZNS SSD will only let you append — never overwrite. Except in one small window. ZWAN uses that window to glue tiny log records together into full blocks, in place, without ever delaying a commit.

📄 "ZWAN: Leveraging ZRWA for Avoiding WAL Tax" · Kim, Cho, Kim · HotStorage'26 🎓 Zoned-storage basics assumed — primers cover them ⏱ ~25 min read
📼

Commit every record INDIVIDUALLY for low tail latency, but PACK them into one block via in-place overwrites inside the ZRWA window — never trade one problem for the other.

Before you begin

Quick glossary, then six primers

The acronyms first — skim once, come back when one trips you up. Then six short primers build the zoned-storage background the paper assumes.

ZNSZoned Namespace — SSD address space split into fixed-size, append-only zones.
WPWrite Pointer — the one position a zone may currently be written at.
ZRWAZone Random Write Area — a small overwrite-capable window just ahead of the WP.
ZRWAFGZRWA Flush Granularity — the unit size by which the WP advances on a flush.

LSM-treeLog-Structured Merge tree — buffers writes, flushes sorted batches (SSTables).

SST(able)Sorted String Table — an immutable on-disk sorted batch an LSM-tree flushes.

1Zones and the write pointer▾

A ZNS SSD divides its address space into zones — large contiguous LBA ranges (96 MiB here). Each zone tracks a single write pointer (WP): the only LBA currently writable. A write lands at the WP, and the WP then advances by that write's length.

Now you're ready: every WAL design in this paper is really a design for "how do multiple threads share one WP."
2Sequential-only writes and zone reset▾

Within a zone, writes must land in increasing LBA order — no overwrites, no gaps. To reclaim space you reset the whole zone at once. This is what lets the device skip internal garbage collection, but it also means a block, once written, is normally frozen until reset.

Now you're ready: "packing" a WAL record into an already-written block should be impossible on ZNS — unless you're inside the ZRWA window, next primer.
3Zone Append — let the device pick the LBA▾

Instead of the host tracking the WP and serializing writes behind it, Zone Append lets the host fire off writes concurrently; the device assigns each one the next free LBA and reports it back. This removes host-side WP contention but each append still consumes a full block.

Now you're ready: WALTZ (the baseline) commits one WAL record per Zone Append — fixing the serialization problem, but not the padding problem.
4ZRWA — a window that allows overwrites▾

Just ahead of the WP, a ZRWA window (64 KB here) temporarily lifts the sequential rule: you can issue random writes inside it, and overwrite the same LBA repeatedly. It doesn't persist to NAND immediately — it's buffered in device DRAM. The WP only advances past it via an Explicit Flush (host command, in ZRWAFG-sized steps) or an Implicit Flush (triggered automatically when the host writes past the window, which can race and fail concurrent in-window writes).

Now you're ready: ZWAN's entire trick is to keep a WAL block sitting in this window and overwrite it in place as new records arrive, instead of allocating a fresh block each time.
5The WAL and group commit▾

An LSM-tree buffers writes in memory (a MemTable) but must first durably log each write to a WAL, so a crash doesn't lose unflushed data. Writing one small record at a time wastes most of a 4 KB block. Group commit fixes that by having one thread batch several writers' records into a single I/O — but every follower now waits on the leader's batching delay, which grows tail latency with batch size.

Now you're ready: ZWAN wants group commit's packing efficiency without its batching delay — that tension is the whole paper.
6Write amplification and tail latency▾

WAF = device bytes written ÷ logical (user) bytes. A 100-byte record forced into a 4 KB block has a WAF contribution of ~41×. P50/P99 latency describe the typical vs. near-worst-case wait per request — P99 is what a user actually feels during a bad moment, even if the average looks fine.

Now you're ready: ZWAN's headline numbers are exactly these two: it cuts WAF (less wasted padding) and cuts P99 (less queuing behind slow commits) at the same time — usually a tradeoff, here not.
The whole story in one place

ZWAN in a nutshell

The tradeoff, the fix, and why it only works inside ZRWA.

On a ZNS SSD, every WAL record must become a full-block write — no in-place updates are allowed in a normal zone. RocksDB's group commit batches several records per block to cut this waste, but every follower now pays the leader's batching delay, inflating tail latency. WALTZ instead commits each record individually via Zone Append, fixing the tail-latency problem — but reintroduces the padding waste: up to 2.5× higher WAL-level WAF than group commit.

ZWAN's fix: commit each record individually, as WALTZ does, but target the ZRWA window instead of a normal zone. Because ZRWA permits in-place overwrites, ZWAN keeps a partially-filled block staged and re-writes it — now holding one more record — every time a new record arrives. Many small writes, one evolving block; no padding, no batching delay.

To make this hold up under concurrent writers, ZWAN adds a dedicated I/O engine: each writer claims a buffer page it owns exclusively (no scanning, off the allocation critical path), and a WP-aware priority queue steers writers toward blocks closest to the WP so the window keeps advancing instead of stalling behind one slow straggler.

The payoff: vs. WALTZ, up to 3.4× throughput, 3.0× lower P50, 9.8× lower P99 — while cutting WAL-level WAF by 98.6%.

🗜️ Key takeaways

  • Group commit trades WAF for latency; per-record commit (WALTZ) trades latency for WAF. ZWAN needs neither tradeoff.
  • ZRWA in-place overwrites let many sub-block records share one physical block — packing without batching.
  • Ownership-based buffer allocation keeps allocation off the critical path and minimizes contention between writers.
  • A WP-aware priority queue biases allocation toward blocks near the WP so the window keeps flushing forward.
  • Device DRAM absorbs the overwrites — ZRWA writes are 3.8× faster than Zone Append yet just as durable.
  • Result: up to 3.4× throughput, 9.8× lower P99, 98.6% less WAL-level WAF, 6.7× faster crash recovery.
Five everyday pictures

How to think about ZWAN

Each stands alone. Every card ends with where the picture stops being true.

The problem · WP serialization

One-lane toll booth

Every car (writer) must pass the same booth (WP) in order — no merging, no skipping. Zone Append is like letting the booth wave cars through and tell each one its lane after the fact: concurrency without a fight over a single slot.

Where it breaks: Zone Append removes the queueing fight but each car still needs a whole lane (a full block) — ZRWA is what lets several small cars share one lane.
Packing · ZRWA overwrite

A sticky note you keep adding to

Instead of mailing a new envelope (full block) for every short memo, you keep adding lines to the same sticky note until it's full, then move on. ZRWA's in-place overwrite is exactly this: one physical block, re-written each time a new record arrives, until it's packed.

Where it breaks: a sticky note is mailed once it's full, by choice. A ZWAN block is only flushed once it's completely full and the window's turn comes — a slow neighbor can hold up the mail run (see "the slow lane" below).
Allocation · Ownership-based pages

Your own numbered locker

You're handed a locker number, not left to scan a wall of lockers for a free one. Each ZWAN writer "pops" an exclusive buffer page off a queue — no scanning, no two writers fighting over the same page.

Where it breaks: a locker is yours until you choose to leave it. A buffer page is reclaimed automatically once it's marked full and flushed — ownership is temporary, tied to the record's lifetime.
Scheduling · WP-aware priority

Metered highway on-ramp

A metering light favors cars merging near the front of a slow-moving jam, not ones already cruising further back, because clearing the front is what lets the whole line move. ZWAN's priority queue does the same: writers are steered toward near-WP blocks first, because those are what the WP is waiting on.

Where it breaks: a highway meter can leave a car waiting indefinitely. ZWAN's fallback to the Normal Queue lets writers drain it once the Priority Queue runs empty — the paper describes this ordering but doesn't prove every writer is guaranteed a page under sustained priority pressure, just that priority traffic is served first.
The constraint · WP advances over runs

A single slow checkout lane

A conveyor belt only moves forward once every item up to a point has been scanned — one slow item stalls everyone behind it, even if later items are already done. The ZRWA window's WP only advances over a consecutive run of fully-packed blocks starting right at the WP — one straggling block blocks every block behind it from being exposed as free space.

Where it breaks: a checkout line is first-come-first-served; ZWAN actively fights this by biasing allocation toward the stalling block (the on-ramp analogy above), not just waiting it out.
The full explanation

How it actually works

From the WAL tax to the I/O engine that exploits ZRWA, to crash recovery.

1 · The WAL tax

Every committed Put must hit stable storage before the MemTable update, for crash durability. On ZNS, a normal zone forces each record to consume a full block (padding waste) or forces a leader to batch several writers' records (latency waste). RocksDB's group commit picks the second; WALTZ's per-record Zone Append picks the first.

2 · Packing records inside a ZRWA block

ZWAN keeps one buffer page in host memory per in-progress ZRWA block, staging its contents. A new record is appended at the next free offset in the page; the page's dirty flag is set and a ZRWA Write overwrites the block in place on the device. Because the device buffers ZRWA writes in DRAM (not NAND) — confirmed by throughput scaling with overwrite count in §4.1 of the paper — each overwrite is cheap, and only the final, fully packed version of the block is what eventually reaches NAND.

3 · The I/O engine: ownership + WP-aware priority

Three structures coordinate this: a Staging Buffer (per-block state + in-progress contents), a Ready Queue (indices of pages that can accept a new record), and a Full Bitmap (which pages are full). A WAL Writer per DB thread pops a page, writes its record, and either re-queues the page (if space remains) or marks it full and pops another. A single WAL Thread runs three roles: the Submitter issues ZRWA writes for dirty pages; the WP Advancer scans the Full Bitmap from the current WP and issues an Explicit Flush once a consecutive run of full pages reaches ZRWAFG; the Committer signals completions and returns pages to the queue.

💡
Why bias toward the WP? The window only advances over a consecutive run of full blocks starting right at the WP — one slow straggler there stalls every block behind it. Routing writers toward near-WP pages first (the Priority Queue, ~4 blocks wide in practice) clears that chokepoint fastest.

4 · Crash recovery

Both WALTZ and ZWAN write out of submission order, so recovery can't just trust the WP. WALTZ's existing out-of-order recovery is reused: scan the WAL region, apply records by embedded sequence number. ZWAN's one difference — valid blocks can exist past the WP (still buffered in the ZRWA window) — so recovery scans to the end of the window, finds written blocks via per-block checksum, and parses each block's packed records sequentially using the length field in each record's header.

Worked examples

Four traces using the paper's reported numbers.

① Back out ZenFS's WAF from the ratios

At 100 B values, the paper states ZWAN's WAF is 1.15, "30× and 12× lower than WALTZ and ZenFS." What's each baseline's WAF?

  1. WALTZ: 1.15 × 30 = 34.5 ≈ the paper's stated "35" for WALTZ at 100 B.
  2. ZenFS: 1.15 × 12 = 13.8.
  3. Cross-check with §2.2: "WALTZ incurs up to 2.5× higher WAL-level WAF than ZenFS" → 13.8 × 2.5 = 34.5. Consistent.
🍯
Insight: at tiny records, group commit's batching (ZenFS) still beats per-record Zone Append (WALTZ) on WAF — but ZWAN's packing beats both by an order of magnitude, with none of group commit's delay.

② Device-level ZRWA throughput scaling

Fig. 3(a): Zone Append = 42.3 MB/s; ZRWA-1 (no overwrite) = 42.1; ZRWA-2 = 84.1; ZRWA-4 = 148; ZRWA-inf = 162 MB/s.

  1. ZRWA-1 ≈ Zone Append (42.1 vs 42.3) — a single write to the window gains nothing by itself.
  2. ZRWA-2 ≈ 2× ZRWA-1 (84.1 ≈ 42.1×2) — each overwrite up to this point is nearly free, confirming the device buffers in DRAM rather than re-writing NAND.
  3. Diminishing returns set in by ZRWA-4 (148, not 4×42.1=168) as fixed per-command overhead starts to dominate.
  4. Ceiling: ZRWA-inf / Zone Append = 162 / 42.3 ≈ 3.8× — the paper's reported max.
💡
This is why packing more records per block doesn't just save space — each additional overwrite also lands faster than a fresh append, compounding the win on both WAF and latency.

③ Table 2's WAF breakdown (PreDist, MixGraph)

ZenFS: WAL 93.15 + Meta 100.36 + SST 4.47 = 197.99. WALTZ: 95.63 + 0 + 4.48 = 100.11. ZWAN: 1.35 + 0 + 4.48 = 5.83.

  1. ZenFS→WALTZ: dropping per-record metadata sync removes 100.36, roughly halving total WAF (198 → 100.1).
  2. WALTZ→ZWAN total WAF reduction: 100.11 / 5.83 ≈ 17.2× — matches the paper's "17×."
  3. WAL-level only: 95.63 / 1.35 ≈ 70.8×; the paper separately reports 98.6% reduction, i.e. (95.63−1.35)/95.63 = 0.986. Both describe the same drop, different units (factor vs. percent).
  4. Packing density: with average record size 42.8 B, a 4 KB block holds at most 4096/42.8 ≈ 95.7 records; ZWAN packs ~71 — about 74% of theoretical max. The paper doesn't break down what accounts for the remaining gap, so treat the exact source of that loss as an open question rather than a settled explanation.
🍯
Insight: at MixGraph's low (14%) write ratio, WAL writes still consume over 20× the bandwidth of SSTable writes in both baselines — the WAL tax dominates total WAF even when writes are rare.

④ Recovery cost: replay time from bytes read

Mean replay: WALTZ 10.3 s vs. ZWAN 1.54 s. Mean WAL bytes read: WALTZ 1038 MB vs. ZWAN 35 MB. Logical WAL volume ≈ 30 MB.

  1. Replay speedup: 10.3 / 1.54 ≈ 6.7×, matching the paper.
  2. Read amplification, WALTZ: 1038 / 30 ≈ 34.6× — unpacked records force one 4 KB read per record.
  3. Read amplification, ZWAN: 35 / 30 ≈ 1.17× — close to the logical volume, since packing means most of each block read is useful data.
  4. Ratio of bytes read: 1038 / 35 ≈ 29.7× ≈ the paper's "30×."
  5. Where the time goes: WAL read is 89.4% of WALTZ's recovery time but only 22.6% of ZWAN's — the same packing that cuts write-time WAF also cuts read-time amplification during recovery.
Test yourself

Practice problems

Try each before opening the answer; every one names the misconception it checks.

Problem 1 · easy
Why can't WALTZ simply overwrite a partially-filled block the way ZWAN does?
Show answer
WALTZ writes via Zone Append into a normal zone, which forbids overwrites and out-of-order rewrites of the same LBA by the sequential-write constraint. ZRWA is a special window where that constraint is explicitly lifted — without it, every record must claim a fresh block.Misconception: that ZRWA is just "a faster Zone Append." It's a different write-semantics region, not merely a speed boost.
Problem 2 · medium
A 4 KB block holds six 600 B records so far (3600 B used, 496 B free). A 700 B record arrives. What does ZWAN's WAL Writer do?
Show answer
700 B exceeds the 496 B of remaining space, so the Writer marks the current page full in the Full Bitmap and pops a new page from the Ready Queue (Priority Queue first) to place the 700 B record there — it does not split the record across two blocks.Misconception: that packing means records can span block boundaries. Each record stays whole within one block; a page is marked full and abandoned once it can't fit the next record.
Problem 3 · medium
The WP has 6 consecutive full blocks ahead of it, then one half-full block, then 4 more full blocks. ZRWAFG = 4 blocks. How far does the WP Advancer move it?
Show answer
The WP only advances over a consecutive run of full blocks starting exactly at its current position. With 6 full blocks available and ZRWAFG = 4, it flushes in one ZRWAFG-sized step (4 blocks), leaving 2 full blocks still waiting for the next flush. It cannot reach the 4 full blocks past the half-full one — that block (not yet full) blocks the run entirely, regardless of how much is full further ahead.Misconception: that the WP advances over any full blocks in the window. It only advances over an unbroken run starting at the current WP — one gap stops everything behind it, no matter how full the rest is.
Problem 4 · hard
Why does ZWAN bias allocation toward low-LBA (near-WP) pages instead of, say, the emptiest pages?
Show answer
The bottleneck isn't "how full is any given page" — it's "is there an unbroken full run starting at the WP." A page far from the WP can sit half-full for a long time without hurting anything, since it isn't on the critical path yet. A page near the WP that fills slowly, by contrast, personally blocks every block behind it from ever being exposed as free space. Biasing toward near-WP pages targets exactly that chokepoint.Misconception: that "most empty" and "most urgent" are the same thing. Urgency here is about position relative to the WP, not fill level.
Problem 5 · easy
At 4 KB value sizes, all three systems (ZenFS, WALTZ, ZWAN) write one WAL block per record and WAF is nearly identical. Why does ZWAN still outperform?
Show answer
Packing's WAF advantage vanishes once a record already fills a block — there's nothing left to pack. But ZWAN's underlying ZRWA write is still intrinsically lower-latency than a Zone Append or group-commit I/O (§4.1: ZRWA-1 cuts average latency 71% vs. Zone Append). Every synchronous Put rides this per-write latency advantage directly, independent of packing.Misconception: that ZWAN's benefit is entirely about reducing WAF. A second, independent benefit is ZRWA's lower per-write latency, which shows up even when there's no packing opportunity.
Problem 6 · medium
On a conventional (non-ZNS) SSD with a normal write buffer, why would a WAL-packing scheme similar to ZWAN deliver a smaller device-level benefit?
Show answer
A conventional SSD's write buffer is managed by the device, not isolated per workload — WAL and SSTable data inevitably co-locate in the same garbage-collection units. Since WAL records expire far sooner than SSTable data, this inflates device-internal GC WAF regardless of host-side packing. ZNS zones architecturally separate WAL from SSTable data, and ZRWA extends that separation into the device's DRAM buffer per open zone — a guarantee a conventional SSD's buffer doesn't offer.Misconception: that packing's benefit is purely a host-side WAF trick portable to any SSD. Its full benefit relies on ZNS's zone-level data isolation, which conventional SSDs don't provide.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is ZRWA data as durable as a normal zone write?▾
Yes — the paper is explicit that ZRWA writes carry the same durability guarantees as Zone Writes, including persistence across power failures and atomic block-write semantics, even while buffered in device DRAM rather than immediately in NAND.
Q2Does packing WAL records risk losing data if a block is never fully packed?▾
No — the Committer and WP Advancer only expose/advance past fully packed and flushed blocks; a partially-filled page's data remains buffered and durable (per Q1) until flushed. Recovery handles partial blocks explicitly by scanning to the window's end and checksumming each block (§3.3).
Q3Why not just increase group commit's batch size to cut WAF further?▾
Bigger batches pack more tightly but every follower's latency now includes the full batch's leader-election, batching, and I/O time — tail latency grows with batch size. ZWAN sidesteps the tradeoff entirely by never batching; each record commits (and is durable) the moment it's written, regardless of how the block eventually fills.
Q4How many writers can use the ZRWA window concurrently?▾
Each buffer page allows only one in-flight write at a time (to prevent a stale version overwriting a newer one), but a ZRWA window spans many pages, so the effective zone-level queue depth stays high even though per-page depth is 1.
Q5What happens if the ZRWA window itself fills up before the WP advances?▾
The paper doesn't detail an explicit backpressure mechanism beyond the WP-aware priority bias, which exists precisely to keep the window advancing and new LBAs becoming available before this happens; the parameter sweep in §5 shows the mechanism holds up even with the smallest tested window (32 KB).
Q6Is ZWAN sensitive to the device's specific ZRWA window size or flush granularity?▾
Barely. Sweeping window size 32–64 KB and flush granularity 32/64 KB changes throughput by ≤2.2%, P50 by ≤0.5%, and P99 by ≤6.1% — even the minimal 32 KB window/granularity sustains full throughput.
Q7Why does WALTZ beat ZenFS in some write-intensive small-value workloads, but lose in others?▾
WALTZ's per-record commit avoids ZenFS's batching delay but inflates WAL-level WAF (up to 2.5×) from padding. At very small values and high write intensity, that WAF cost can outweigh the latency benefit, so WALTZ underperforms ZenFS by up to 54% in those specific configurations — motivating ZWAN's "both at once" fix.
Q8Why does ZWAN's throughput advantage shrink on MixGraph vs. the microbenchmarks?▾
MixGraph's four workloads average only a 14% write ratio, so the WAL path (what ZWAN optimizes) contributes less to overall throughput than in the write-heavy microbenchmarks. ZWAN still wins on latency throughout, since every Put — rare or not — traverses the WAL synchronously.
Q9Is ZWAN's idea specific to LSM-tree key-value stores?▾
The paper designs and evaluates ZRWA-packing specifically for the LSM-tree WAL — that's the only write stream it measures. The underlying mechanism (committing sub-block records via in-place ZRWA overwrites) isn't conceptually tied to RocksDB beyond the integration point, but the paper itself makes no claim about how it would perform on other small, frequent write streams on ZNS; treat broader generalization as a reasonable guess, not a result.
Q10What's left for future work?▾
The paper's Discussion section focuses on explaining why the ZNS architecture (zone-level isolation + per-zone DRAM buffering) makes packing more effective than on conventional SSDs, and confirms robustness to ZRWA parameter choices — it doesn't list further open problems explicitly.

Core terms
ZWANThe paper's LSM-tree KV store design: packs WAL records into ZRWA blocks via in-place overwrites, plus a dedicated I/O engine.
ZRWAZone Random Write Area — a small (here 64 KB) overwrite-capable window adjacent to the WP, buffered in device DRAM.
WAL taxThe paper's umbrella term for WAL persistence overhead on ZNS: inflated WAF from sub-block padding, plus WP-serialization contention.
Ownership-based allocationEach writer exclusively claims a buffer page via a queue pop — no scanning, keeping allocation off the critical path and minimizing contention.
WP-aware prioritizationA Priority Ready Queue that biases page acquisition toward low-LBA (near-WP) blocks, to keep the window advancing.
Implicit / Explicit FlushTwo ways the WP advances past the ZRWA window: automatically on an out-of-window write (implicit, can race) or via a dedicated command (explicit, ZRWAFG-sized steps).
Supporting terms
Zone AppendA write mode where the device assigns the LBA, letting hosts issue concurrent writes to a zone without tracking the WP themselves.
Group commitRocksDB's leader-batches-followers WAL-commit strategy; cuts WAF but grows tail latency with batch size.
Lazy metadata managementWALTZ's technique of deferring filesystem metadata updates until zone replacement, instead of per-record fsync.
Staging Buffer / Ready Queue / Full BitmapZWAN's three core data structures tracking per-block state, allocatable pages, and completed pages respectively.
MixGraphFacebook's realistic KV workload generator with Pareto-distributed value sizes and four access-pattern variants (AllRand, AllDist, PreRand, PreDist).
