ASPLOS 2025 · A Field Guide

Stop scheduling memory for the worst case that almost never happens

A secure memory controller must never let two VMs' requests collide — so every prior defense assumed each turn might need to handle a write followed by a read, the slowest possible pairing. FlexProf shows that committing to the likely case first, and patching the rare case opportunistically, buys back real performance without opening a single side-channel.

📄 "FlexProf" · Minton & Balasubramonian · Univ. of Utah 🎓 Assumes the LLC side-channel is already closed ⏱ ~30 min read
🕐

Design the schedule for what's LIKELY next — a read, or a write — not what's merely POSSIBLE. Patch the rare case with one extra cycle, not a permanently wider gap.

1What a memory controller does, and why sharing it is risky▾

The memory controller issues commands — activate, column-read/write, precharge — to DRAM, obeying a set of fixed timing constraints. On a cloud server, several VMs share one controller, one set of channels, ranks, and banks. Contention is unavoidable: when two VMs' requests would touch the same resource too close together, one must wait.

That wait time is externally observable, and it depends on what the other VM is doing — which is exactly the leak an attacker wants.

Now you're ready: FlexProf's whole job is to schedule this shared resource so that the wait time never depends on a co-tenant's secret behavior, while wasting as little bandwidth as possible doing so.
2Channels, ranks, and banks — the DRAM hierarchy▾

A channel is an independent path from the CPU to memory, with a unidirectional command bus and a bidirectional data bus. A DIMM on that channel holds several ranks (chip groups accessed together); each rank holds several banks, which can be accessed in parallel.

Two requests to the same bank need a long recovery gap; different banks need less; different ranks need the least of all.

Now you're ready: FlexProf's isolation rule is defined in terms of ranks — consecutive turns are assigned to different rank groups (Quad Rank Alternation) so cross-VM contention never lands at the wrong moment.
3DRAM timing parameters — the vocabulary of every equation▾

Every command is separated from the next by a named delay: tRCD (row→column), tRP (precharge), tCAS (column read strobe), tCWD (column write delay), tRAS (row active time), tRRD (row-to-row), tWR/tWTR (write recovery/write-to-read), tRTRS (rank switch), tBURST (data transfer length).

This paper's simulator (Table 2) fixes concrete cycle values: tRCD=tRP=tCAS=11, tCWD=5, tRAS=28, tRRD=5, tWR=6, tRTRS=2, tBURST=4.

Now you're ready: Section 3.1's whole derivation is just plugging these numbers into a handful of inequalities to find the smallest safe gap between any two commands.
4Command bus vs. data bus▾

The command bus carries the activate/read/write instructions, one at a time. The data bus carries the actual burst of data — occupied for tBURST = 4 cycles per transfer. Two transactions conflict if their command-bus or data-bus occupancy windows overlap in time, even for different physical banks.

Now you're ready: the paper's eight inequalities (Eq. 1–8) are literally an exhaustive list of every way two transactions' command-bus timings could collide.
5Timing side-channels and covert channels▾

If an attacker's own memory access takes longer than usual, it can infer that a co-scheduled victim recently touched the same resource. Wang et al. exploited exactly this to infer the Hamming weight of an RSA key. A malicious Trojan inside a victim VM can deliberately access memory to signal a "1" bit and stay idle to signal a "0" — a covert channel.

Now you're ready: FlexProf must guarantee this timing difference simply never exists — every VM's access takes exactly the same number of cycles no matter what its neighbors do.
6The threat model — even the OS may be malicious▾

The attacker has no physical bus access — only a timing channel through contention. Because the OS itself may be untrusted, you can't rely on page placement to keep VMs on separate channels/ranks/banks. Isolation must come entirely from hardware in the memory controller.

Now you're ready: this is why the defense lives entirely below the OS, in the controller's scheduling logic, and assumes no software cooperation.
7Temporal Partitioning — turns and dummy requests▾

The baseline defense (Wang et al.): give each VM a fixed-length turn with consistent spacing to the next VM's turn. If a VM has nothing queued, the controller inserts a dummy request — so external behavior looks identical whether or not real work happened.

Now you're ready: RQA and FlexProf are both refinements of this one idea. The whole research question is: how short can a turn safely be made?
8RTA/RQA — today's state-of-the-art baseline▾

RTA splits ranks into 3 groups and gives each VM a 14-cycle turn (2 requests, 7-cycle gap), with a 1-cycle bubble every 3rd turn. A flaw was found — the write-recovery gap between two turns could shrink to 37 cycles instead of the required 43 — fixed by moving from 3 groups to 4: Rank Quad Alternation (RQA).

Now you're ready: every "vs. baseline" number in this paper — the 8%, the 33% — means "vs. RQA."
9The spacing "l" — why one number governs the whole schedule▾

Assume a data block hits the memory bus every l cycles, periodically. Solving DRAM's timing inequalities for the minimum safe l gives a different answer depending on what request types are allowed: l=7 if either a read or a write could come next; l=6 if you already know it'll be one type or a read-then-write; l=7 if it could be write-then-read.

Now you're ready: this is the mathematical core of FlexProf — restricting what a turn allows lets l drop from 7 to 6 most of the time.
10The alternative: shaping traffic to a profile (DAGguise)▾

Instead of guaranteeing a fixed turn, some schemes profile a program's average memory behavior beforehand and shape its live traffic to match that average — inserting dummies or delaying bursts as needed. This can look efficient on paper, but bursts above the average simply queue up.

Now you're ready: this is why DAGguise underperforms turn-based FS-BTA once you require every program to be secure — explained fully in Section 4.2.
The whole story in one place

FlexProf in a nutshell

The problem, the restriction that fixes it, the flexibility that saves it from being too restrictive.

Secure memory scheduling gives every VM a deterministic turn so its neighbor can never infer anything from contention. But prior schedules had to assume the worst case: any request in a turn might be a write immediately followed by a read — the slowest transition DRAM allows — so every gap between commands was sized for that possibility. This is a big reason side-channel defenses have historically cost about a 2× slowdown.

FlexProf's insight: if a turn commits in advance to being Read Mode or Write Mode, the worst-case write-then-read pairing never occurs inside that turn, and the safe gap between commands shrinks from 7 cycles to 6. A 14-cycle worst-case 2-slot turn shrinks to a 12-cycle 2-slot turn in Read/Write Mode — peak data-bus utilization rises from RQA's 56% to FlexProf's 66%.

Restricting turns this way risks wasting slots when the wrong mode is active, so FlexProf adds two opportunistic escape hatches: a Read-Mode turn can silently issue two writes to the same rank instead, and a (slightly longer, 13-cycle) Write-Mode turn can silently issue two opportunistic reads. Neither escape hatch changes the timing of the next turn, so neither leaks anything. An offline profiling step picks each VM's ideal Read/Write-Mode ratio — though the opportunistic tricks make profiling optional for most programs. A three-tier hardware algorithm then assigns turns to rank groups (security), VMs (fairness), and modes (performance).

The payoff: compared to RQA, FlexProf improves mixed-workload performance by a geometric mean of 8% (up to 35% for lbm), and single-program-workload performance by 5% (up to 33%). Over half the benchmarks gain more than 10%.

🕐 Key takeaways

  • Prior defenses size every gap for the worst case (write→read); FlexProf sizes most gaps for the likely case (Read Mode or Write Mode).
  • Committing to a mode drops the safe inter-command gap from 7 cycles to 6, and turn length from 14 to 12 (Read) or 13 (Write) cycles.
  • Opportunistic writes in Read Mode, and opportunistic reads in Write Mode, recover utilization without changing neighboring turns' timing — so they leak nothing.
  • Profiling picks each VM's Read/Write-Mode ratio, but is now optional — opportunistic draining gets most of the benefit for most programs.
  • A three-tier algorithm assigns turns to rank group (security), VM (fairness), then mode (performance) — with profiling able to override the mode preference.
  • Result: +8% geomean on mixed workloads (up to +35%), +5% geomean on single-program workloads (up to +33%), formally proven leakage-free with Z3.
🧊
For your tiering/CXL lens: FlexProf's mechanism — deterministic, mode-committed "turns" per tenant on a shared controller — is a close cousin of the isolation problem CXL memory pooling will eventually face: once several tenants share a CXL.mem-attached pool, contention on the shared fabric/controller becomes an observable side channel again, and heterogeneous DRAM/NVM tiers (with very different tRAS/tRP-equivalents) would make a single fixed l even harder to pick than in this single-technology DDR study. This connection is our framing, not a claim in the paper.
Seven everyday pictures

How to think about FlexProf

Each picture stands alone. Every card ends with an honest note about where the picture stops being true.

The core idea · Restrict, don't hedge

Packing for a coin flip

If you don't know whether it'll be a heat wave or a blizzard, you pack for both — heavy coat and sunscreen — and your bag is twice as big. If the forecast says "sunny," you pack light and carry one small umbrella just in case. FlexProf's turn is the bag: committing to Read Mode or Write Mode is packing for the forecast, and the opportunistic escape hatch is the umbrella.

Where it breaks: a real forecast can be wrong; FlexProf's "forecast" (the mode) is never wrong about safety — worst case it just wastes a slot, it never causes a collision.
Baseline · Temporal Partitioning & dummies

The doctor's fixed appointment slot

Every patient gets a 15-minute slot, whether or not they show up — the receptionist's schedule looks identical either way, so nobody in the waiting room can tell who actually came in. That's Temporal Partitioning's dummy request: every VM gets its turn, real request or not, so the schedule reveals nothing.

Where it breaks: real appointment slots don't get shorter based on what's likely; FlexProf's slot length does adapt (12 vs. 13 cycles) based on which mode is committed — the analogy only covers the "slot exists regardless" part.
Read Mode / Write Mode · Two lanes

An express lane with one rule

A highway lane restricted to "buses only" moves faster per-vehicle than a mixed lane, precisely because drivers behind you don't need to brake for a car merging in. A Read-Mode turn works the same way: because nothing behind it can be a write, the gap to the next request can be tight (6 cycles) instead of defensive (7).

Where it breaks: a real highway lane's rule is fixed for hours; FlexProf re-designates the "lane rule" every single turn, at essentially zero cost.
Opportunistic writes · The carpool exception

Letting a carpool through the express lane

The bus-only lane normally excludes cars — but a car carrying enough passengers to count as a "carpool" can slip in without slowing anyone behind it, because it behaves close enough to a bus for that stretch of road. A Read-Mode turn similarly allows two writes to the same rank — because same-rank writes only need a short 1-cycle tRRD gap, not the full 2-cycle rank switch, they slot in without disturbing the next turn.

Where it breaks: the carpool rule is about vehicle occupancy; the real constraint here is specifically "same rank" — writes to different ranks don't qualify for this trick.
Rank Quad Alternation · The relay baton

A four-runner relay with a rest lap

A relay team with four runners guarantees each one gets three full legs of rest before running again — plenty of recovery time, by construction. Quad Rank Alternation cycles turns through four rank groups the same way, so a bank that was just accessed always gets several turns' worth of rest before anyone touches it again.

Where it breaks: relay runners are interchangeable; rank groups are fixed physical partitions of memory — you can't reorder which "runner" (rank) is up next to fit the story.
Profiling · The pre-planned menu

A weekly menu vs. improvising dinner

A chef can trial a few different fixed meat/vegetable ratios across sample weeks and commit to whichever ratio the diners responded best to — that's profiling: not measuring the "natural" order mix, but testing candidate ratios and keeping the best-performing one. Or the cook can just default to vegetables and swap in meat opportunistically whenever a customer's order calls for it — no planning needed, and it adapts instantly if tastes shift mid-week. FlexProf's opportunistic accesses are the improvising cook: they get most of the benefit of the pre-planned ratio without needing the plan.

Where it breaks: the planned menu can occasionally still beat improvising — profiling still adds up to 15% for write-heavy programs like lbm/ft, which the "always improvise" default doesn't fully capture.
Turn assignment · Three independent decisions

A building's three-tier security rotation

A building assigns guards to a door (security rotation), then to a shift (fair scheduling among guards), then to a duty for that shift (deciding whether to check IDs or patrol). Each layer is decided independently by a different rule. FlexProf's three tiers work the same way: rank group first (security), then VM (fairness), then Read/Write Mode (performance) — with the profiling result allowed to override the mode layer only.

Where it breaks: the building's three tiers rarely override each other; FlexProf's mode tier is explicitly overridable by profiling, which the security and fairness tiers are not.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams you can read at a glance.

1 · Why the baseline needs 7 cycles

The controller must guarantee no two consecutive transactions ever collide on the command or data bus. Assuming a fixed period l between data transfers, the paper writes eight inequalities (Eq. 1–8) covering every pairing of read/write commands at every stage (Activate, Column-Rd/Wr). Because most of these equations mix tCAS (for reads) and tCWD (for writes), allowing either type forces the largest solution: l = 7 cycles.

🧮
The key derivation: restrict to reads-only (ignore all but Eq. 6) and the minimum shrinks to l = 6, bound only by tBURST + tRTRS = 4 + 2 = 6. Writes-only (Eq. 3 only) also gives l = 6. Read-then-write (Eqs. 1, 5, 7) gives l = 6. Only write-then-read (Eqs. 2, 4, 8) still needs l = 7.

2 · RQA's utilization ceiling

RTA's original attempt gave each VM a 14-cycle turn (2 requests, 7-cycle gap) and tried to guarantee the mandated 43-cycle bank-recovery interval with a 1-cycle bubble every 3rd turn: over 3 turns (3×14+1 = 43 cycles), 6 data transfers × 4 cycles = 24 busy cycles, ≈56% peak utilization. That bubble protects the data-bus transfers' spacing but not the earlier Activate commands, which is the timing flaw RQA fixes by rotating through 4 rank groups instead of 3. RQA keeps the same 14-cycle, 2-request turn structure, so it lands at the same ≈56% peak data-bus utilization the paper reports — even in the best case, over 40% of the data bus sits idle by design.

3 · Read Mode and Write Mode

FlexProf designates every turn as Read Mode or Write Mode in advance. Because a Read-Mode turn's two requests are guaranteed reads, and a Write-Mode turn's are guaranteed writes, the internal spacing shrinks to 6 cycles and the turn itself shrinks to 12 cycles. Quad Rank Alternation still applies across turns for bank-recovery security. Whenever the schedule transitions from a Write-Mode turn to a Read-Mode turn, a 1-cycle bubble is inserted (that write→read case still needs 7 cycles). Peak data-bus utilization: 8/12 ≈ 66%.

4 · Why Write Mode can't mirror the trick — and the 13-cycle fix

The natural mirror — two opportunistic reads to the same rank, 5 cycles apart, in Write Mode — turns out to violate the command bus (both the write→opportunistic-read and opportunistic-read→opportunistic-read transitions conflict). Two options remain: (a) issue only one opportunistic read and waste the second slot, or (b) lengthen every Write-Mode turn to 13 cycles, which safely fits two opportunistic reads to any allowed rank. The paper's experiments favor option (b) — the small extra cycle is worth the doubled opportunistic capacity. Peak utilization for a Write-Mode turn: 8/13 ≈ 62%, still well above RQA's 56%.

5 · Turn assignment — the three-tier algorithm

# tier 1 — security: rank group, strict round-robin
groups = [R0, R1, R2, R3]; turn.rank_group = groups[turn_index % 4]

# tier 2 — fairness: VM, strict round-robin (staggered per round if needed)
turn.vm = vms[(turn_index + round_offset) % num_vms]

# tier 3 — performance: mode, alternating preference, overridable by profiling
if vm.profiled_ratio is fixed:
    turn.mode = vm.profiled_ratio.next_mode()   # overrides round preference
else:
    turn.mode = round.preferred_mode            # batches Read turns, then Write turns
💡
Why batch Read turns, then Write turns? FlexProf batches mode preferences the same way conventional (non-secure) memory schedulers batch reads and writes — grouping same-type requests together reduces the wait time for critical reads. This is the default tier-3 policy whenever no profiled ratio overrides it.

6 · Proving it's still leakage-free

Every timing case — normal Read/Write Mode, plus both opportunistic variants — is re-expressed as a system of inequalities and checked with the Z3 theorem prover for resource conflicts. Separately, the USIMM simulator itself asserts that no issued command is ever stalled by a resource conflict, giving an empirical cross-check of the formal proof.

Follow the numbers, step by step

Worked examples

Four traces, carried through with the paper's own cycle counts and percentages.

① Why RTA's bubble patch failed, and how RQA still lands at 56%

RTA gives 14-cycle turns and tried to guarantee the mandated 43-cycle bank-recovery interval with a 1-cycle bubble every 3rd turn. What utilization does this target, and why doesn't the bubble actually fix RTA?

  1. RTA's intended "super-cycle" = 3 turns + 1 bubble = 3 × 14 + 1 = 43 cycles — exactly the mandated bank-recovery interval.
  2. Data transfers per super-cycle: 2 requests/turn × 3 turns = 6 transfers, each occupying the data bus for tBURST = 4 cycles.
  3. Busy cycles: 6 × 4 = 24 cycles out of 43 → ≈55.8%, rounded to 56%.
  4. The flaw: the bubble only protects the data-bus transfers' spacing. The earlier Activate commands for a write-then-read pair still end up only 37 cycles apart, short of the required 43 — so the bubble doesn't close the gap it was meant to guarantee. RQA fixes this by rotating turns through 4 rank groups instead of 3, with no ad hoc bubble needed. Since RQA keeps the same 14-cycle, 2-request turn structure, it lands at the same order of peak utilization — the paper reports ≈56% for RQA.
🕐
Insight: nearly half the data bus's capacity is spent idle purely to guarantee the worst-case write→read gap — that idle capacity, not the bubble mechanics themselves, is exactly what FlexProf recovers.

② FlexProf's 66% peak, and why Write Mode costs a cycle

A Read-Mode turn is 12 cycles; a Write-Mode turn is 13. What's the peak utilization of each, and why the difference?

  1. Read-Mode: 2 transfers × 4 cycles = 8 busy cycles / 12-cycle turn = 66.7% ≈ the paper's stated 66%.
  2. Write-Mode: same 8 busy cycles / a 13-cycle turn = 61.5% — lower, because the 13th cycle is deliberately reserved as a hand-off bubble.
  3. Why the bubble exists here but not in Read-Mode: a Write-Mode turn might be followed by a Read-Mode turn next round — the classic write→read case that needs the full 7 cycles, not 6 — so Write-Mode reserves its 13th cycle for that hand-off. A Read-Mode turn only needs 12 cycles because even when it opportunistically ends in two same-rank writes instead of two reads, the second write is scheduled a cycle earlier (cycle 5, not 6), which frees up exactly the extra cycle needed to still hand off safely to a following read — without stretching the turn.
  4. Net effect: even Write-Mode's 61.5% still beats RQA's 56% — restricting the type of request pays off even in the "expensive" mode.
💡
This is why the paper calls 12-cycle turns (2 issue slots) optimal (Fig. 11): a 3rd slot would need to protect against more possible transitions, eating back the gains from restricting the mode in the first place.

③ Why the second opportunistic write moves to cycle 5, not 6

In an opportunistic Read-Mode turn, two writes to the same rank are issued at cycles 0 and 5 instead of 0 and 6. Why is this both faster and still safe?

  1. Same-rank writes skip the rank-switch delay. A normal Read-Mode turn's second request needs the 2-cycle rank-to-rank switch (tRTRS) built into its 6-cycle spacing; two writes to the same rank don't switch ranks at all.
  2. Instead they need only tRRD = 1 cycle beyond the 4-cycle transfer: 4 + 1 = 5 cycles between the two writes.
  3. Check the gap to the next turn: the next turn still starts at cycle 12 (unchanged). From the second write at cycle 5, that's 12 − 5 = 7 cycles — exactly the minimum required for a write immediately followed by a read.
  4. Result: the freed cycle isn't wasted — it's spent guaranteeing the one case (write→read) that still needs the full 7-cycle gap, without moving the turn boundary at all.
🕐
Insight: the opportunistic trick works because it repurposes slack that was already built into the schedule for a different reason (rank-switch delay), rather than creating new slack from nothing.

④ Reading the headline results

FlexProf reports 8% geomean (mixed) and 5% geomean (individual) improvement over RQA, up to 33%/35% for lbm. What do these numbers mean concretely?

  1. Individual-program workloads (7 VMs all running the same program) show a geometric mean improvement of 5% across 23 SPEC/NAS benchmarks; the single best case, lbm, improves 33%.
  2. Mixed workloads (7 VMs each running a different program, 10 random mixes) show an even larger geometric mean improvement of 8%; lbm's best-case gain rises to 35% here.
  3. Why mixed does better: when 7 instances of a write-heavy program like lbm run together, every VM wants long Write-Mode turns, which lowers overall utilization. Mixed alongside programs that mostly need short Read-Mode turns, the schedule's average turn length shrinks and total throughput rises.
  4. 12 of 23 benchmarks — over half — beat RQA by more than 10%; only 3 programs regress slightly, because they were unusually good at using RQA's native "read-then-write in the same turn" flexibility.
💡
The paper's own framing (§7): FlexProf closes part, but not all, of the security-vs-performance gap noted in the abstract — more innovation is needed to fully bridge the remaining distance to a non-secure baseline.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
Why does allowing "either a read or a write" in a turn force a 7-cycle gap, when restricting to reads-only allows 6?
Show answer
Because most of the timing inequalities mix tCAS (for reads) and tCWD (for writes); allowing both request types means the schedule must satisfy the union of every constraint, and the tightest one — the write-then-read case — needs 7 cycles. Restricting to one type eliminates the constraints that pair the two different delays.Misconception: that "flexible" scheduling is always faster. Here, flexibility about what kind of request comes next is exactly what forces the wider, slower gap.
Problem 2 · medium
RQA already lets a VM send a read and a write in the same turn. Why doesn't FlexProf just copy that flexibility instead of introducing Read/Write Mode?
Show answer
The paper measured it directly (Fig. 3): under RQA, very few turns actually issue one read and one write — most turns are either two reads or two writes. The flexibility exists but isn't used, so it buys nothing while still forcing the worst-case 7-cycle spacing on every turn, whether or not that turn ever needs it.Misconception: that flexibility that exists is flexibility that helps. If a capability is rarely exercised, restricting it (as FlexProf does) can be pure upside.
Problem 3 · hard
Why can Read-Mode drain two opportunistic writes to the same rank, but Write-Mode can't drain two opportunistic reads the same way?
Show answer
Same-rank writes only need the short tRRD gap (1 cycle beyond the transfer) because they don't switch ranks — so the second write can slide a cycle early and still leave 7 clean cycles to the next turn. The mirror-image attempt for reads runs into a command bus conflict (both write→opportunistic-read and opportunistic-read→opportunistic-read transitions collide), which has nothing to do with rank-switch timing — it's a different physical constraint that the writes case doesn't hit.Misconception: that reads and writes are symmetric in DRAM timing. tCAS and tCWD differ, and so do the constraints each triggers — the asymmetry is real, not an oversight.
Problem 4 · easy
If profiling is skipped entirely and every VM defaults to 100% Read-Mode, does security still hold?
Show answer
Yes. Security comes from the fixed, secret-independent turn structure and rank-group rotation (tiers 1 and 2), not from the profiled ratio. The ratio only affects performance (tier 3) — a wrong or missing ratio wastes some slots (more opportunistic accesses, more dummy requests) but never creates a timing dependency on secret data.Misconception: that profiling is a security mechanism. It's a performance optimization; the leakage-free guarantee comes entirely from the deterministic turn/rank assignment.
Problem 5 · medium
Given 7 VMs and 4 rank groups, does the fairness tier need to "stagger" which VM starts each round to make sure every VM eventually visits every rank group equally?
Show answer
No staggering is needed here. Staggering is only required when the VM count and rank-group count share a common factor greater than 1 (which would otherwise trap some VMs on a fixed subset of rank groups). Since gcd(7, 4) = 1, plain round-robin already guarantees every VM visits every rank group evenly once the schedule completes a full cycle of 28 turns (7 VMs × 4 groups).Misconception: that staggering is always required for fairness. It's only required when VM count and rank-group count aren't coprime — check the gcd before assuming you need it.
Problem 6 · hard
RTA (3 rank groups) has a timing flaw that RQA (4 groups) fixes. What exactly goes wrong in RTA, and why does adding a 4th group fix it?
Show answer
In RTA, the gap between the data-bus transactions of two VMs separated by 3 turns is a full 43 cycles — but the corresponding Activate commands (which precede the data transaction by a fixed offset) end up only 37 cycles apart when one VM writes and the next reads, violating the true bank-recovery requirement. RTA sized only the data-bus gap correctly, not the earlier Activate-to-Activate gap. Adding a 4th rank group (RQA) simply gives one more turn's worth of spacing before a rank recurs, which is enough slack to cover the Activate-timing shortfall as well.Misconception: that "the data transfers are correctly spaced" implies the whole schedule is safe. Earlier pipeline stages (like Activate) can have tighter effective spacing than the final data transfer suggests — you have to check every stage, not just the visible one.
Problem 7 · medium
The paper says DAGguise underperforms FS-BTA once every VM must be secure, even though DAGguise reports better overall performance in its own paper. Reconcile these two facts.
Show answer
DAGguise's own results come from mixed secure + non-secure workloads: its secure VMs perform worse than under FS-BTA, but its non-secure VMs (unconstrained by any turn structure) perform much better, lifting the overall average. This paper only evaluates the all-secure case (every VM needs protection), which strips away the non-secure VMs' advantage and exposes that DAGguise's secure-VM performance alone is the weaker number.Misconception: that a paper's headline "outperforms X" result applies under any evaluation setting. Always check what workload mix produced the number — DAGguise's advantage lives entirely in the non-secure portion of its mixed workloads.
Problem 8 · easy
Why does the paper test with exactly 7 VMs, rather than 8 or a nicer round number?
Show answer
RQA (and FlexProf's Quad Rank Alternation) round-robins turns among 4 rank groups; if the VM count were a multiple of the alternation factor, some prior schemes required a dummy VM or restructuring to avoid degenerate scheduling. Using 7 — a number that shares no common factor with the standard alternation schemes used by prior work (3-way RTA or 4-way RQA) — lets every baseline be evaluated on equal footing without artificially padding or shrinking the VM count for any one method.Misconception: that benchmark configuration choices (like VM count) are arbitrary. Here it's a deliberate choice to avoid giving any single baseline scheme an unfair structural advantage.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What's the single-sentence version of FlexProf's idea?▾
Instead of scheduling every memory turn defensively for the worst-case read/write pairing, commit each turn to a likely pattern (all-reads or all-writes) to shrink the safe gap from 7 to 6 cycles, then recover any lost utilization with two leakage-free "opportunistic" escape hatches.
Q2Why does read/write flexibility within a turn (as RQA already allows) not actually help?▾
The paper measured it: under RQA, the vast majority of turns issue either two reads or two writes, almost never one of each. The flexibility exists in the hardware but isn't exercised by real programs, so it buys nothing while forcing every turn to pay the worst-case 7-cycle spacing regardless.
Q3What exactly is a "turn"?▾
A fixed-length window during which one VM may issue a bounded number of requests (2, in FlexProf's chosen design) to one rank group. If it has nothing to send, a dummy request fills the slot so the schedule looks identical either way.
Q4Why can't Write Mode mirror Read Mode's opportunistic trick exactly?▾
The natural mirror (two opportunistic reads to the same rank, 5 cycles apart) violates a command-bus constraint that the writes-case doesn't hit. FlexProf instead lengthens every Write-Mode turn to 13 cycles, trading one extra cycle for the ability to issue two opportunistic reads to any allowed rank.
Q5How do we know FlexProf is actually as secure as RQA?▾
Every scheduling case — normal and opportunistic — is formalized as a system of DRAM timing inequalities and checked for satisfiability with the Z3 theorem prover. The USIMM simulator additionally asserts no issued command is ever stalled by a resource conflict during evaluation, cross-checking the formal proof empirically.
Q6What happens if a VM has no request ready when its turn comes?▾
The controller inserts a dummy request in the missing slot(s), exactly as in prior temporal-partitioning schemes, so the external schedule is indistinguishable whether or not real work happened.
Q7Why exactly 7 VMs in the evaluation?▾
To avoid needing a dummy VM or unequal alternation for any of the compared schemes — 7 shares no common factor with the 3-way (RTA) or 4-way (RQA/FlexProf) rank alternation used by different baselines, so every method is evaluated fairly.
Q8Does the offline profiling step leak anything?▾
No — profiling runs the workload under a range of candidate Read/Write-Mode ratios and keeps whichever ratio performs best, treating the resulting choice as a secret-independent, coarse-grain property of the program, not a moment-to-moment secret-dependent signal.
Q9How does FlexProf compare to DAGguise?▾
DAGguise shapes a program's traffic to match a pre-declared average pattern (an rDAG), which queues requests whenever real behavior exceeds that average. When every VM must be secure, this underperforms turn-based FS-BTA — so the paper doesn't use DAGguise as a baseline and instead compares against RQA and FS-BTA directly.
Q10Why was RTA replaced by RQA as the state-of-the-art baseline?▾
RTA's 3-way rank alternation leaves the Activate-to-Activate gap between certain write→read pairs at only 37 cycles when the true DRAM requirement is 43 — a genuine timing bug. Moving to 4-way alternation (RQA) provides enough extra spacing to close that gap.
Q11Where does the threat model draw the line on what attacks are in scope?▾
The attacker has no physical access to buses or signals — only a co-scheduled VM (possibly aided by a Trojan inside the victim) inferring timing from its own memory latency. Attacks needing physical probing, or exploiting non-timing side effects like differing energy use between reads and writes, are explicitly out of scope (though the paper flags energy differences as a place additional safeguards might be needed).
Q12Does FlexProf fully close the security-performance gap?▾
No — the paper's own conclusion states the best design point still runs well below a non-secure baseline, and explicitly calls for more innovation to further close that remaining gap. FlexProf meaningfully narrows it (from RQA) but doesn't eliminate it.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
FlexProfThis paper's memory controller: mode-committed turns (Read/Write) plus opportunistic accesses and offline profiling.
TurnA fixed window in which one VM may issue a bounded number of requests to one rank group; unused slots get dummy requests.
Read Mode / Write ModeFlexProf's two turn types, each pre-committed to a fixed request-type pattern, enabling a tighter 6-cycle inter-request gap.
Opportunistic accessIssuing a request of the "wrong" type for the current mode (e.g. a write during Read Mode) without disturbing neighboring turns' timing — leakage-free by construction.
ProfilingAn offline, secret-independent search across candidate Read/Write-Mode turn ratios, keeping whichever ratio performs best for a VM's workload, used to override the default mode-assignment preference.
Three-tier turn assignmentRank group (security) → VM (fairness) → mode (performance) — three independently decided layers per turn.
l (spacing)The minimum safe number of cycles between consecutive data-bus transfers; 7 in the unrestricted worst case, 6 when the request type is known in advance.
Supporting terms
TPTemporal Partitioning (Wang et al. 2014) — the original turn-based defense with 43-cycle turns.
RTA / RQARank Triple / Quad Alternation — the prior state-of-the-art and its flaw-fixed successor; FlexProf's main comparison baseline.
FS-BTAFixed Service: Bank Triple Alternation (Shafiee et al. 2015) — alternates bank groups instead of ranks.
DAGguiseA shaping-based defense (rDAG) for mixed secure/non-secure workloads; underperforms FS-BTA in all-secure settings.
USIMMUtah SImulated Memory Module — cycle-accurate, trace-driven DRAM simulator used for evaluation.
Z3An SMT theorem prover used to formally verify that FlexProf's scheduling rules never produce a resource conflict.
Rank / bank / channelDRAM's physical hierarchy: channels are independent CPU–memory paths; ranks are chip groups; banks within a rank can be accessed in parallel.
tRAS, tRP, tRCD, tCAS, tCWD, tRTRS, tBURST, tRRD, tWR/tWTRDRAM timing parameters governing row activation, precharge, column access/write, rank switching, data burst length, row-to-row delay, and write recovery — the vocabulary of every scheduling equation.
Covert channelA side-channel deliberately exploited by a Trojan inside a victim VM to exfiltrate secrets to a co-scheduled attacker.
