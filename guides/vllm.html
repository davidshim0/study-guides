SOSP 2023 · A Field Guide

Give GPU memory to a request as it grows, not for the worst case it might reach

Existing LLM serving systems reserve a giant contiguous slab of GPU memory per request, sized for a length it may never reach. This is the plain-English story of PagedAttention and vLLM, which borrow a fifty-year-old OS trick — paging — to fix it.

📄 "PagedAttention" · Kwon, Li, Zhuang, Sheng, Zheng et al. (UC Berkeley) 🎓 OS virtual memory / paging basics assumed — primers cover them ⏱ ~30 min read
🧩

Store the KV cache as fixed-size, non-contiguous blocks allocated on demand — like OS pages — instead of one oversized contiguous reservation per request.
Same GPU. 2–4× the throughput.

Before you begin

What this paper is doing, in 30 seconds

A TL;DR, a glossary of the paper's own jargon, then the concepts it assumes you know. Read primers in order the first time, or jump to whatever's unfamiliar.

⚡ TL;DR

  • Core contribution: PagedAttention, an attention algorithm that reads the KV cache from small, non-contiguous, fixed-size blocks — plus vLLM, a serving engine built around it with a page-table-like block manager, copy-on-write sharing, and preemptive scheduling.
  • Headline result: 2–4× higher serving throughput than FasterTransformer and Orca at the same latency, by pushing KV cache memory utilization from 20.4%–38.2% up to 96.3%.
  • Why it matters: LLM serving throughput is bottlenecked by GPU memory, not compute — treating the KV cache like OS-managed virtual memory (paging, COW, swap) unlocks batching and sharing that contiguous allocation structurally cannot.

Quick glossary — the paper's own terms

KV cacheCached key/value vectors for every previous token in a sequence; must stay resident to generate the next token, and grows one token at a time.
PagedAttentionThe attention algorithm this paper introduces: computes attention over KV cache stored in small, non-contiguous blocks instead of one contiguous tensor.
vLLMThe serving system built on PagedAttention — scheduler + KV cache manager + custom GPU kernels.
Block / block tableA fixed-size chunk of KV cache (a "page"); a per-sequence block table maps its logical blocks to physical blocks, like an OS page table.
Copy-on-write (COW)Blocks shared by multiple sequences are only duplicated at the moment one of them needs to write a different value into it.
Iteration-level schedulingBatching decisions are remade every decoding step (not once per whole request), so finished/new requests join or leave immediately.
Orca / FasterTransformerThe two state-of-the-art serving-system baselines vLLM is compared against throughout the paper.
SPMD tensor parallelismMegatron-LM-style strategy for splitting one model across several GPUs, each processing the same tokens but a slice of the attention heads/weights.
1Autoregressive generation and why the KV cache exists▾

An LLM generates tokens one at a time; each new token's probability depends on all previous tokens via self-attention. Recomputing every previous token's key/value vectors at every step would be wasteful, so they're cached — the KV cache — and reused across steps.

The KV cache for one token depends on its position, so it must grow by one slot every time a new token is generated — its final size isn't known until generation stops.

Now you're ready: the KV cache is the paper's whole subject — a memory region that grows unpredictably, one token at a time, for the entire life of a request.
2Why batching requests is necessary — and hard▾

GPUs are fast at parallel matrix math but the autoregressive decode phase is memory-bound (one token at a time, matrix-vector multiplies). Batching many requests together amortizes the cost of moving model weights and keeps the GPU busy.

But requests arrive at different times, have wildly different lengths, and their KV cache footprints keep changing — so batching requires actively managing per-request memory, not just queuing compute.

Now you're ready: the batch size — and hence throughput — is limited by how much KV cache memory you can fit on the GPU at once. That's the whole game.
3Contiguous memory allocation and why it's the default▾

Most deep learning frameworks require tensors to live in one contiguous block of memory, since that's fast and simple for the GPU to address. So existing LLM servers pre-allocate one contiguous chunk per request, sized for its maximum possible sequence length.

This is the root of the paper's problem: reserving space you don't yet need, and might never fully use, in a block nobody else can touch.

Now you're ready: PagedAttention exists specifically to break this contiguous-tensor requirement for the KV cache.
4Internal vs. external fragmentation▾

Internal fragmentation: space reserved for a request but never used — e.g. reserving 2048 slots for a sequence that only ever reaches 300 tokens. External fragmentation: space that's free but too oddly-shaped/scattered to give to anyone, from allocating different-sized chunks per request.

Both are pure waste — memory that sits idle while other requests could have used it.

Now you're ready: the paper measures existing systems using only 20.4%–38.2% of KV cache memory for actual token data — the rest is exactly this waste.
5Virtual memory and paging, the OS original▾

An OS gives each process the illusion of a large, contiguous address space, while physically scattering its data across fixed-size pages anywhere in RAM. A page table maps each virtual (logical) page to wherever its physical page actually lives — allocated only when first touched, never all upfront.

This is literally the mechanism vLLM borrows: think blocks as pages, tokens as bytes, requests as processes.

Now you're ready: everything in "How It Works" — block tables, on-demand allocation, copy-on-write — is this OS idea, re-applied to KV cache instead of RAM.
6Decoding algorithms that share context: parallel sampling & beam search▾

Parallel sampling: one prompt, several independent sampled completions — they all start from the identical prompt KV cache. Beam search: keeps the top-k partial sequences at every step, pruning and branching, so different candidates can share long stretches of KV cache that only diverge partway through.

In a contiguous-memory system, sharing is impossible — each sequence's cache is a private, separate blob.

Now you're ready: memory sharing across sequences is one of the two headline wins vLLM claims (the other is near-zero waste) — and it needs the block/page abstraction to even be possible.
7Copy-on-write, the OS original▾

When an OS forks a process, both processes initially point at the same physical pages (cheap — no copy). Only when one of them writes to a shared page does the OS clone it at that instant, giving the writer a private copy.

vLLM uses the identical trick for KV cache blocks shared between sequences (e.g. two parallel samples of the same prompt): share until a write forces a copy, tracked via a per-block reference count.

Now you're ready: "sharing" in this paper mostly means deferring a copy for as long as possible, not literally always keeping one copy forever.
The whole story in one place

PagedAttention & vLLM in a nutshell

The problem, the OS-inspired fix, and how the pieces connect.

Serving LLMs at scale means batching many requests on one GPU, and the limiting resource is the KV cache — memory that grows one token at a time and whose final size is unknown up front. Existing systems handle this the same way naive memory allocators always have: reserve one big contiguous chunk per request, sized for its worst-case length. The paper shows this wastes the majority of the memory — only 20.4%–38.2% of allocated KV cache actually holds real token data in existing systems, the rest lost to internal and external fragmentation and to reservations for tokens not yet generated.

The fix, PagedAttention, is a direct transplant of OS virtual memory: split each sequence's KV cache into fixed-size blocks (pages), let them live anywhere in physical GPU memory, and track the mapping with a per-sequence block table. Blocks are allocated only when the previous one fills up, so waste is bounded to less than one block per sequence, no matter how long it runs. Because blocks are addressable independently, sequences that share a prompt (parallel sampling) or a partial history (beam search) can literally share the same physical blocks, cloning only on write via copy-on-write.

On top of this, vLLM adds a centralized scheduler with first-come-first-served fairness, an all-or-nothing eviction policy when memory runs out, and a choice of swapping evicted blocks to CPU RAM or simply recomputing them later — plus support for multi-GPU tensor-parallel serving.

The payoff: vLLM sustains 2–4× the throughput of FasterTransformer and Orca at matched latency (up to 22× over FasterTransformer, 1.7–2.7× over an oracle-informed Orca), by pushing effective KV cache utilization to 96.3% in the paper's basic-sampling experiment (§6.2, Fig. 2) and unlocking up to 55% extra memory savings from sharing in beam search on Alpaca (up to 66% on ShareGPT).

🍯 Key takeaways

  • Existing servers reserve KV cache contiguously for a request's max possible length; PagedAttention instead pages it in fixed-size blocks, allocated on demand.
  • Waste is bounded to less than one block per sequence, versus 62%–80% of memory wasted by reservation + fragmentation in existing systems.
  • A per-sequence block table (like a page table) maps logical blocks to scattered physical blocks — this indirection is what makes non-contiguous storage transparent to the attention kernel.
  • Copy-on-write + reference counts let parallel-sampling and beam-search sequences share physical blocks, up to 55% memory savings in beam search on Alpaca (up to 66% on ShareGPT).
  • Preemption uses all-or-nothing eviction (whole sequences, never partial) and recovers via swap to CPU RAM or recomputation.
  • Result: 2–4× throughput over FasterTransformer/Orca, ~96.3% effective KV cache utilization (§6.2 basic-sampling avg.), 20–26% higher attention-kernel latency that's swamped by the batching win.
Six everyday pictures

How to think about PagedAttention

Each stands alone — read in any order. Every card ends with an honest note about where it stops being true.

The core idea · Contiguous reservation vs paging

Renting the whole hotel floor for one guest

A hotel that doesn't know how long a guest will stay books them the entire floor "just in case," leaving most rooms locked and empty for someone who only needed one room. PagedAttention instead checks guests into single rooms one at a time, anywhere on the property, and hands out a new room only when they actually need it.

Where it misleads: a hotel wants guests in nearby rooms for convenience; vLLM's blocks are scattered on purpose — proximity doesn't matter once a block table can find any block instantly.
The manager · Block table

A library's card catalog

A book's call number tells you which shelf and slot holds it — the book itself can sit anywhere in the stacks. vLLM's block table is that catalog card for each sequence: logical block 0, 1, 2… each points to wherever its 16-token slice actually lives in GPU memory, so the attention kernel just "looks it up" instead of assuming everything sits side by side.

Where it breaks: a librarian re-shelves books for browsing convenience; vLLM doesn't need to for correctness — but the indirection isn't free, either: the paper measures the PagedAttention kernel at 20–26% higher latency than a contiguous-memory kernel in its tested context lengths, a cost worth watching as context windows grow much longer.
Sharing · Copy-on-write

Splitting a shared document

Two coworkers open the same shared doc read-only — no need for two copies while neither edits it. The instant one of them starts typing, they fork off their own private copy from that point forward. vLLM does exactly this for two parallel samples of one prompt: they share the prompt's physical blocks (reference count 2) until one needs to write a different token, at which point only that one block gets copied.

Where it breaks: shared docs track edits at arbitrary granularity; vLLM's copy-on-write only operates at whole-block granularity, so any divergence inside a shared block forces copying the entire block, not just the changed token.
Dynamic sharing · Beam search

A family tree that prunes itself

A family tree shares a common ancestor at the root, then branches — and if a whole side-branch dies out, its private twigs are simply removed while the shared trunk remains. Beam search candidates share a common prompt "trunk," diverge into separate "branches" as decoding proceeds, and when a losing candidate is dropped, only its unshared blocks (reference count reaching 0) are freed — the shared ancestry stays.

Where it breaks: a family tree only grows; beam search's tree can re-converge in the sense that surviving candidates keep sharing ever more of their recent history too, since top-k candidates often descend from the same one or two parents.
Recovery · Swap vs. recompute

Moving boxes to a storage unit — or just repacking

When your apartment (GPU memory) is full, you either haul boxes to an off-site storage unit (CPU RAM, "swapping") to fetch back later, or you simply repack from scratch when you need the stuff again ("recomputation"). Which is cheaper depends on how big the boxes are and how far the truck has to drive — exactly why vLLM's choice between swap and recompute depends on block size and PCIe bandwidth.

Where it breaks: repacking from scratch usually costs more than a short drive to storage; for vLLM, recomputation is often cheaper than swapping, because the "repack" (recompute) can be done in one parallel prompt-phase pass instead of token-by-token.
Scheduling · Iteration-level batching

A relay race, not a marathon start-gun

A marathon makes every runner wait for the starting gun together and finish before the next group begins. A relay handoff zone instead lets a runner join or leave the moment they're ready, without freezing the whole race. Iteration-level scheduling batches requests per decoding step, so a finished request exits and a new one joins on the very next iteration — not after the whole batch completes.

Where it breaks: a relay still has fixed legs of equal length; LLM requests have wildly different remaining lengths, so vLLM must additionally handle preemption when memory (not just scheduling slots) runs out mid-race.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as visuals you can read at a glance.

1 · The problem, quantified

For a 13B-parameter OPT model, one token's KV cache costs 2 (K,V) × 5120 (hidden size) × 40 (layers) × 2 (bytes, FP16) = 800 KB. At a 2048-token max length, that's up to 1.6 GB per request — and a contiguous allocator must reserve the full 1.6 GB up front, even for a request that stops after 30 tokens. Measured across real traces, this leaves existing systems using only 20.4%–38.2% of allocated KV cache for actual token data (Fig. 2) — the rest is reserved-but-unused space, internal fragmentation, and external fragmentation from variable-sized chunks.

2 · PagedAttention — attention over non-contiguous blocks

Split each sequence's keys/values into fixed-size blocks of B tokens. For query position i, instead of one attention computation over the whole contiguous history, PagedAttention sums over each block j separately: compute the attention score against block j's keys, weight block j's values, and accumulate — then fetch the next block, wherever it physically sits. The math is identical to standard attention; only the memory-access pattern changes, from "one big contiguous read" to "fetch scattered blocks and combine."

3 · Decoding walkthrough — allocate only when full

During the prompt phase, vLLM computes KV cache for the whole prompt in parallel and fills logical blocks left to right; the last block's unused slots are simply left empty (not reserved elsewhere). During autoregressive decoding, each new token's KV cache is appended to the current last block; only when that block fills up does vLLM allocate a fresh physical block and extend the table. Because the wasted space is always confined to "less than one block" per sequence, waste no longer scales with the max possible sequence length.

4 · Memory sharing across sequences

Parallel sampling: multiple outputs from one prompt map their prompt logical blocks to the same physical blocks, with a reference count (e.g. 2). A copy-on-write triggers only when a sample writes a new token into a still-shared block — allocate a fresh physical block, copy, decrement the old count. Beam search: extends this to a dynamically evolving tree — candidates share a prompt trunk and any common branches; when a candidate is pruned, its now-unshared blocks (ref count → 0) are freed immediately. Shared prefix: a service provider can pre-compute and pin the KV cache for a common system prompt once, and every new request just maps onto those cached physical blocks — computing only its own unique suffix.

5 · Scheduling and preemption

vLLM schedules strictly first-come-first-served to prevent starvation. When GPU memory runs out, it uses an all-or-nothing eviction policy — either every block of a sequence is evicted, or none — because a sequence's blocks are always accessed together, and multiple sequences within a request (e.g. beam candidates) are gang-scheduled as one unit due to their potential block sharing. To recover an evicted sequence, vLLM either swaps its blocks to CPU RAM (classic OS swap) or recomputes its KV cache from scratch in one parallel prompt-phase pass — recomputation latency is at most 20% of swapping's, but swapping wins with large block sizes when PCIe transfers are efficient.

6 · Distributed execution

For models spanning multiple GPUs (Megatron-LM-style SPMD tensor parallelism), every GPU worker processes the same input tokens but only its own slice of attention heads — so they all need the same block table. vLLM keeps a single centralized scheduler + KV cache manager that broadcasts one shared block table to all workers each step; workers synchronize intermediate results via all-reduce without needing to coordinate memory management themselves.

Follow the numbers, step by step

Worked examples

Four traces carried through with the paper's own numbers — footprint math, fragmentation bound, batching gains, and sharing savings.

① Computing a request's KV cache footprint (OPT-13B)

  1. Per-token cost: 2 (key & value) × 5120 (hidden size) × 40 (layers) × 2 (bytes, FP16) = 819,200 bytes = 800 KB/token.
  2. At max length 2048 tokens: 800 KB × 2048 = 1,638,400 KB ≈ 1.6 GB per request — reserved up front in existing systems.
  3. GPU budget: A100 has 40 GB; parameters take 26 GB (65%), leaving ~14 GB, of which the paper allocates ~12 GB to KV cache (Table 1).
  4. Max concurrent requests if each reserves the full 1.6 GB: 12 GB ÷ 1.6 GB ≈ 7–8 requests — regardless of how short most of them actually turn out to be.
🍯
Insight: the 1.6 GB figure is a worst case, not a typical case — ShareGPT's average output is only 338 tokens (Fig. 11), meaning a typical request needs ~270 MB, not 1.6 GB. Reserving the max wastes the difference for every single request.

② Why waste is bounded to less than one block, regardless of length

  1. Block size B = 16 (vLLM's default). A sequence that generates 25 tokens needs ⌈25/16⌉ = 2 blocks = 32 slots.
  2. Internal fragmentation = 32 − 25 = 7 slots — less than one full block (16), no matter how long the sequence runs.
  3. Contrast with contiguous reservation: the same 25-token sequence in a max-2048 system wastes 2048 − 25 = 2023 slots — over 280× worse.
  4. General bound: internal fragmentation per sequence ≤ B − 1 tokens' worth of KV cache, i.e. a small, fixed cost independent of sequence length.
💡
This is the direct payoff of allocating in fixed-size blocks on demand instead of one variable-size upfront reservation — the paging trick, restated as an inequality.

③ Reading the batching improvement (Fig. 13a, OPT-13B, ShareGPT @ 2 req/s)

  1. Average requests batched concurrently: Orca (Max) = 7.00, Orca (Pow2) = 9.81, Orca (Oracle) = 13.62, vLLM = 30.42.
  2. vLLM vs. Orca (Oracle): 30.42 ÷ 13.62 ≈ 2.2× more requests fit at once — even though Oracle already knows each request's exact future length.
  3. vLLM vs. Orca (Max): 30.42 ÷ 7.00 ≈ 4.3× more requests — Max reserves the full 2048-token slab regardless of actual need.
  4. Why more batched requests → more throughput: each decoding step processes one token per active sequence in parallel; more concurrent sequences means more useful GPU work per step, better amortizing the fixed cost of moving model weights.
🍯
Insight: even Oracle — the theoretical best case for a contiguous allocator — loses to vLLM by 2.2×, because knowing the final length doesn't remove external fragmentation from variable-sized chunks; only block-uniform paging does.

④ Quantifying memory-sharing savings (Alpaca dataset, OPT-13B)

  1. Parallel sampling: 2 samples save 6.09%, 4 samples save 8.53%, 6 samples save 9.79% of KV cache memory (Fig. 15a) — only the shared prompt blocks are deduplicated.
  2. Beam search: width 2 saves 37.56%, width 4 saves 53.13%, width 6 saves 55.16% (Fig. 15b) — far more, because candidates keep sharing new blocks as they decode, not just the original prompt.
  3. Why the gap: parallel samples only ever share the fixed prompt; beam candidates continuously re-share their evolving common history until they diverge, so the shareable fraction stays high even deep into generation.
  4. Translating to throughput: on OPT-13B/Alpaca, vLLM's advantage over Orca (Oracle) grows from 1.3× (basic sampling) to 2.3× at beam width 6 — memory saved directly becomes room for more concurrent requests.
💡
Sharing isn't a bonus feature bolted on — it falls straight out of the block/page abstraction: anything addressable by reference can be shared by reference.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A request's true output turns out to be only 40 tokens, but the system pre-allocated for a 2048-token maximum. In a contiguous allocator, how much memory was wasted, and would vLLM waste the same amount?
Show answer
The contiguous allocator wastes 2048 − 40 = 2008 tokens' worth of KV cache — reserved for the entire request's lifetime. vLLM, with block size 16, needs ⌈40/16⌉ = 3 blocks = 48 slots, wasting only 48 − 40 = 8 slots — 251× less.Misconception: that "the system didn't know the length in advance" excuses the waste. vLLM doesn't need to know the length in advance either — it just never reserves further ahead than one block at a time.
Problem 2 · medium
Orca (Oracle) is told the exact final output length of every request in advance — arguably an unfair advantage over vLLM. Yet vLLM still batches 2.2× more requests. What kind of waste does Oracle's knowledge fail to eliminate?
Show answer
External fragmentation. Even knowing the exact length, Oracle still allocates one contiguous, variable-sized chunk per request via a buddy allocator — differently-sized chunks from finished requests leave gaps too irregular to reuse for a new, differently-sized request. vLLM's fixed-size blocks never have this problem: any freed block fits any request.Misconception: that internal fragmentation (over-reservation) is the only kind of waste. Oracle eliminates internal fragmentation almost entirely but is still hurt by external fragmentation, which only uniform block sizes fix.
Problem 3 · medium
In parallel sampling, two output sequences A and B initially share the same physical blocks for their common prompt, with reference count 2. Sequence A now needs to write its first newly-generated token into the shared last block. Walk through what vLLM does.
Show answer
vLLM sees the block's reference count (2) is greater than 1, so it: (1) allocates a new physical block, (2) copies the shared block's contents into it, (3) writes A's new token into the copy, (4) updates A's block table entry to point at the new block, and (5) decrements the original block's reference count to 1. B's table entry is untouched — it still points at the original block, which it can now write to directly next time without copying, since the count is back to 1.Misconception: that copy-on-write duplicates data upfront "just in case." It only copies at the exact moment of a conflicting write — until then, sharing is completely free.
Problem 4 · hard
Beam search with width 4: candidates 0–2 share the first 3 blocks and diverge at block 4; candidate 3 diverges earlier, at block 2. At the next step, only candidates from parents 1 and 2 survive the top-4 cut. What happens to candidate 0's and candidate 3's blocks?
Show answer
Every physical block that was uniquely owned by candidate 0 or candidate 3 (i.e. reference count would drop to 0 once they're pruned) is freed immediately and can be reused for the new candidates spawned from 1 and 2. Blocks that candidates 0/3 shared with surviving candidates (e.g. the common prompt blocks, or block 1–2 shared with candidate 3's siblings) simply have their reference count decremented, but stay resident since other candidates still need them.Misconception: that pruning a candidate frees "its" blocks wholesale. Only the blocks it doesn't share with anyone still alive are freed — shared ancestry blocks live on as long as any survivor needs them.
Problem 5 · medium
Fig. 18b shows block size 256 performs terribly on the Alpaca dataset but is fine on ShareGPT. Alpaca's average output length is 58 tokens (Fig. 11b); explain the gap using the internal-fragmentation bound from Problem 1.
Show answer
Internal fragmentation is bounded by (block size − 1) tokens per sequence. With B=256 and a typical Alpaca output of ~58 tokens, a sequence needs just 1 block (256 slots) but only fills 58 — wasting up to 198 slots, more than 3× the tokens actually used. ShareGPT's much longer sequences (mean 338 output tokens) amortize that same fixed per-sequence waste over far more useful tokens, so the relative cost of a large block shrinks.Misconception: that a bigger block size is always safer because "more headroom." Bigger blocks trade away exactly the fragmentation guarantee that PagedAttention was built to provide, especially for short-sequence workloads.
Problem 6 · hard
The paper finds recomputation latency is never more than 20% of swapping's latency, yet vLLM still supports swapping as an option. Under what circumstances (per §7.3) would swapping actually be the better choice?
Show answer
Swapping's overhead comes from small, numerous CPU↔GPU data transfers, which is worst at small block sizes because each transfer's fixed cost isn't amortized. At medium-to-large block sizes (roughly 16–64 and up), transfers are big enough to approach effective PCIe bandwidth, closing the gap with recomputation — the paper reports comparable end-to-end performance for block sizes 16–64, and swapping can pull ahead when CPU-GPU bandwidth is high and recomputation would otherwise burn scarce GPU compute that could serve other requests.Misconception: that recomputation is unconditionally better since it's usually faster in the microbenchmark. The end-to-end tradeoff also depends on PCIe bandwidth and how much GPU compute recomputation competes for.
Problem 7 · easy
Two workloads both have very predictable, short output lengths that never vary. Would vLLM's memory-management advantage over Orca (Oracle) shrink or stay the same?
Show answer
It would shrink. Orca (Oracle)'s main weakness is not knowing lengths in advance (which it does here) plus external fragmentation from variable chunk sizes (which shrinks when all requests are similarly short). The paper observes exactly this pattern on OPT-175B/Alpaca (Fig. 12f), where large available memory + short, uniform sequences make the workload compute-bound rather than memory-bound, narrowing vLLM's edge.Misconception: that vLLM's gains are constant across all workloads. The gains scale with how badly the baseline's memory management performs, which depends on sequence-length variance and how memory-constrained the setup is.
Problem 8 · medium
vLLM's PagedAttention GPU kernel is measured to be 20–26% slower than FasterTransformer's highly optimized attention kernel (Fig. 18a). Why doesn't this show up as vLLM losing in end-to-end throughput?
Show answer
The 20–26% overhead applies only to the attention operator — one part of one layer's computation — while linear layers and everything else are untouched. This small, localized cost is dwarfed by the much larger gain from fitting far more requests into the batch at once, since batch size (not per-kernel speed) is what's bottlenecked by memory in LLM serving.Misconception: that a slower kernel must mean a slower system. When the system is memory-bound rather than compute-bound, a modest compute overhead is a trivial price for a large increase in effective batch size.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly does PagedAttention change about the math of attention?▾
Nothing about the math — the attention scores and outputs are numerically identical to standard attention. What changes is only how the key/value vectors are fetched: block by block, from wherever the block table says they live physically, instead of assuming one contiguous span.
Q2Why does the block table need to exist at all — why not just track free memory directly?▾
Because a sequence's data must appear logically contiguous and in order to the attention computation, even though it's physically scattered. The block table is the indirection layer that reconciles these two views — exactly the job a page table does for a process's virtual address space.
Q3Does non-contiguous storage make the GPU kernels slower?▾
Slightly — the PagedAttention kernel measures 20–26% higher latency than FasterTransformer's tuned contiguous-memory kernel (Fig. 18a), due to block-table lookups and handling variable sequence lengths. But this only affects the attention operator, and the batching gains from better memory use far outweigh it end-to-end.
Q4How is copy-on-write different from just always copying shared data upfront?▾
Copying upfront defeats the purpose — you'd pay the memory cost of duplication immediately, gaining nothing. Copy-on-write defers the copy until (and unless) a write actually happens, so sequences that never diverge from a shared prompt never pay any copying cost at all.
Q5Why "all-or-nothing" eviction instead of evicting individual blocks?▾
Because every block of a sequence is needed together to continue its generation — evicting half a sequence's cache wouldn't free it to make useful progress elsewhere, it would just break both the evicted and remaining halves. Evicting whole sequences (and gang-scheduling sequence groups that share blocks) keeps eviction decisions meaningful.
Q6Swapping or recomputation — which does vLLM actually use?▾
Both are supported and the tradeoff depends on block size and hardware: recomputation overhead is never more than 20% of swapping's, but the two have comparable end-to-end performance at block sizes 16–64, and swapping becomes more efficient than recomputation as block size grows larger with good PCIe bandwidth. vLLM lets the deployer choose.
Q7Does using vLLM change a model's outputs or accuracy?▾
No. PagedAttention computes the exact same attention values as standard attention; it only changes memory layout and scheduling. The paper reports the throughput gains come "without affecting the model accuracy at all."
Q8How does vLLM handle a model that doesn't fit on one GPU?▾
It uses Megatron-LM-style tensor parallelism: the model is sharded across GPUs (e.g. attention heads split across workers), but a single centralized scheduler and KV cache manager maintains one shared block table used by every worker, since all workers process the same tokens at the same positions.
Q9Is Orca's iteration-level scheduling a competing idea to PagedAttention?▾
No — the paper describes them as complementary. Orca increases GPU utilization by interleaving more requests' compute; vLLM increases it by fitting more requests' memory footprints at once. In fact, fine-grained scheduling like Orca's makes efficient memory management even more necessary, not less.
Q10Would PagedAttention help a GPU workload that isn't LLM serving?▾
Only if that workload shares LLM serving's two properties: memory footprints that grow unpredictably at runtime, and performance actually bottlenecked by memory capacity rather than compute. The paper notes DNN training (static tensor shapes) and non-LLM DNN serving (often compute-bound) wouldn't benefit and might even be slowed by the added indirection.
Beyond this paper

Connections to OS & memory-systems design

Short links from this paper's specific choices to the broader memory-tiering and OS-design landscape.

🗂️ Block tables are page-placement machinery in miniature

vLLM's block table is a minimal page table: an indirection layer decoupling logical position from physical location. That's the exact mechanism DRAM/CXL/NVM tiering systems like TPP and HeMem exploit to migrate "hot" pages between tiers transparently — the OS (or vLLM's KV manager) can move data without the application noticing, because nothing above the indirection layer assumes a fixed physical address.

💾 Swap-to-CPU-RAM is literally cross-tier demand paging

vLLM's "swap evicted blocks to CPU RAM" is the same demand-paging move that memory tiering systems make when spilling cold pages from DRAM to a slower NVM or CXL-attached tier. The twist here is vLLM's recomputation alternative — trading a fetch-from-slow-tier for pure recompute — which parallels the recompute-vs-fetch cost models explored for cheap-to-regenerate data in tiered-memory and persistent-memory research.

🌳 Copy-on-write sharing needs coarser granularity than general OS COW

Standard OS copy-on-write operates at page (4KB) granularity per process; vLLM's beam-search "gang scheduling" of whole sequence groups is a reminder that COW's efficiency depends on choosing the right sharing unit for the workload — too fine-grained and you pay bookkeeping overhead, too coarse and unrelated writers block each other, a tension familiar from choosing page sizes (4KB vs. huge pages) in CXL-tiered memory.

⚙️ Memory-bound, not compute-bound — the same lever tiering research pulls

The paper's central claim — that LLM serving throughput is capped by effective memory capacity, not raw FLOPs — is structurally identical to the argument for OS-managed memory tiering: when the bottleneck is fitting more useful data in fast memory, better placement/allocation (not more compute) is the highest-leverage fix, exactly the premise behind Memtis-style access-pattern-driven tiering.

🍯
PagedAttention is a case study in a broader OS-memory-tiering thesis: fifty-year-old virtual-memory abstractions (paging, page tables, copy-on-write, swap) generalize past CPU RAM to any workload with unpredictable, capacity-bound memory growth — including GPU accelerator memory.

Class prep — sharp questions to raise

Each references a specific claim, number, or design decision from the paper.

  1. The paper reports PagedAttention's kernel is 20–26% slower than FasterTransformer's due to block-table indirection (Fig. 18a) — as context windows grow into the tens of thousands of tokens, does this per-access indirection cost start to resemble the page-table-walk / TLB-miss overhead problem in OS memory, and would a "TLB for KV blocks" help? (the paper treats this cost as fixed and small — is that assumption safe at much longer contexts?)
  2. vLLM ships one fixed default block size of 16, yet Fig. 18b shows the optimal size clearly differs by workload (16–128 best for ShareGPT, only 16–32 for Alpaca) — why not select block size dynamically per request or per deployment, the way OS memory management offers multiple page sizes (huge pages) for different access patterns? (what would the added bookkeeping cost of mixed block sizes look like?)
  3. The all-or-nothing eviction policy evicts a sequence's blocks wholesale, but copy-on-write can leave a physical block shared between a sequence being evicted and one that isn't — how does the reference-counting scheme behave when one sharer is swapped out while another remains resident on the GPU? (the paper doesn't spell this interaction out explicitly)
  4. Orca (Oracle) — which is told the exact future output length of every request — still trails vLLM by 1.7–2.7× (Fig. 12/13); the paper attributes some of Oracle's residual loss to external fragmentation from its buddy allocator and dismisses compaction as "impractical due to the massive KV cache" (§3.1) — is that dismissal fully justified, or just unexplored for this specific workload? (compaction works fine for other large memory-bound systems)
  5. vLLM schedules strictly FCFS "to ensure fairness and prevent starvation," but ShareGPT-style long conversations and Alpaca-style short instructions have very different service times (mean output 338 vs. 58 tokens, Fig. 11) — could short requests get stuck queued behind long ones under FCFS, and would a scheduling policy borrowed from general-purpose OS schedulers (e.g. multi-level feedback queues) do better without sacrificing fairness? (the paper doesn't evaluate mixed-length-distribution fairness directly)

Glossary, results & further reading

Every term in one place, then a path to go deeper.

Core terms
KV cacheCached key/value vectors for every generated token; grows one token at a time and dominates dynamic GPU memory use during serving.
PagedAttentionAttention algorithm that reads KV cache from fixed-size, non-contiguous blocks rather than one contiguous tensor.
vLLMThe end-to-end serving system built on PagedAttention: scheduler, KV cache manager, and custom CUDA kernels.
Logical / physical blockA logical block is a sequence's own ordered view of its KV cache; each maps to a physical block anywhere in GPU memory.
Block tablePer-sequence mapping from logical to physical blocks, plus fill-count bookkeeping — vLLM's analogue of an OS page table.
Copy-on-write (COW)A shared block is duplicated only at the moment a sharer needs to write different data into it; tracked via reference counts.
Internal / external fragmentationInternal: space reserved but unused within a chunk. External: free space too scattered/oddly-sized to reuse. Existing systems suffer both; vLLM nearly eliminates them.
Iteration-level schedulingRebatching decisions every decoding step instead of per whole request, so requests join/leave without waiting on the rest of the batch.
Supporting terms
Prompt phase / decoding phasePrompt phase processes the whole input in parallel; decoding phase generates output tokens one at a time, sequentially.
Parallel samplingMultiple independent output samples generated from one shared prompt — shares only the prompt's KV cache.
Beam searchKeeps top-k partial sequences at each step; candidates share KV cache blocks up to their point of divergence, and the sharing pattern evolves as decoding proceeds.
Shared prefixA common system prompt whose KV cache is pre-computed once and reused across many requests' logical block tables.
All-or-nothing evictionvLLM's preemption policy: evict every block of a sequence, or none — never a partial sequence.
Swapping / recomputationTwo recovery strategies for evicted sequences: copy blocks to CPU RAM, or regenerate the KV cache from scratch later.
SPMD tensor parallelismMegatron-LM-style model sharding across GPUs; all workers process identical tokens but distinct attention heads/weight slices.
FCFS schedulingFirst-come-first-served request ordering, chosen by vLLM to guarantee fairness and prevent starvation.
Normalized latencyMean per-request end-to-end latency divided by output length — the paper's primary evaluation metric.
Orca / FasterTransformerState-of-the-art serving-system baselines: Orca for throughput-optimized iteration-level scheduling; FasterTransformer for latency-optimized inference.

Related papers

One-Level Storage System medium

Kilburn, Edwards, Lanigan, Sumner · IRE Trans. Electronic Computers · 1962

The origin of paging and virtual memory — the fifty-year-old idea this paper re-applies to GPU KV cache.

Yu, Jeong, Kim, Kim, Chun · OSDI · 2022

The most closely related system — iteration-level scheduling, which the authors describe as complementary to (not competing with) PagedAttention.

Dao, Fu, Ermon, Rudra, Ré · NeurIPS · 2022

Kernel fusion and I/O-aware tiling to reduce attention's peak memory — a complementary, kernel-level optimization vLLM's implementation adapts.

Steiner, Elhoushi, Kahn, Hegarty · 2022

Reduces fragmentation via tensor lifetime/placement optimization, but at the tensor level, not fine-grained block-level runtime management.
