Give the KV cache pages, and the batch grows

An LLM server's throughput is set by how many requests fit in GPU memory at once, and most of that memory is the per-token key and value cache. Existing systems reserved it in one contiguous chunk per request and used only 20 to 38% of it for real tokens. vLLM stores it in small fixed-size blocks reached through a block table, the way an OS stores a process in pages, and fits two to four times as many requests.

Before you begin

Store each request's key and value cache in pages, not in one reserved chunk

A 2023 SOSP paper from UC Berkeley (with Stanford and UC San Diego co-authors): why serving a large language model is limited by GPU memory, how much of that memory the existing servers wasted, and how borrowing paging, page tables, copy-on-write and swapping from operating systems recovers it. The system is vLLM; the new attention kernel is PagedAttention.

⚡ TL;DR

  • Problem: generating text one token at a time is memory-bound, so a server only uses its GPU well with a large batch of requests, and the batch is capped by GPU memory. Most of the free memory goes to the KV cache, the saved key and value vectors of every earlier token: 800 KB per token for OPT-13B, up to 1.6 GB for one 2048-token request. Existing servers (FasterTransformer, Orca) reserve one contiguous chunk per request sized for the maximum length, and only 20.4% to 38.2% of KV cache memory ends up holding real token states (Fig. 2).
  • PagedAttention: split each sequence's KV cache into fixed-size KV blocks (16 tokens by default) that can sit anywhere in GPU memory; the attention kernel finds them through a per-sequence block table. Blocks are pages, tokens are bytes, requests are processes (the paper's analogy).
  • KV cache manager: logical blocks are mapped to physical blocks only when a token needs a slot, so waste is at most one partly filled block per sequence: 96.3% of KV memory holds token states in vLLM's run of the same experiment.
  • Sharing: one physical block can back logical blocks of several sequences, with a reference count and block-level copy-on-write. Parallel samples share the prompt; beam-search candidates share most of their history; requests can share a cached system prompt. Measured savings on OPT-13B: 6.1 to 9.8% (parallel sampling) and 37.6 to 55.2% (beam search) on Alpaca, 16.2 to 30.5% and 44.3 to 66.3% on ShareGPT.
  • When memory runs out: first-come-first-serve, preempt the latest arrivals, evict all blocks of a sequence group at once, then bring them back by swapping to CPU memory or by recomputing them in one prefill pass.
  • Result: 2 to 4× the throughput of Orca and FasterTransformer at the same latency; OPT-13B on ShareGPT batches 30.42 requests on average versus 13.62 for an Orca that knows every output length in advance. Cost: the paged attention kernel is 20 to 26% slower than FasterTransformer's.

Quick glossary
TokenThe unit of text a language model reads and writes: an integer index into a fixed vocabulary of word pieces (tens of thousands of entries). "Four score and seven" is about four tokens.
Large language model (LLM)A neural network, here a Transformer with billions of parameters, that takes a sequence of tokens and outputs a probability for every possible next token.
Transformer layerOne of the identical stages a token's vector passes through in order (40 in OPT-13B): an attention step that mixes in information from earlier tokens, then a per-token feed-forward network.
Hidden stateThe vector of numbers that represents one token inside a layer; its length is the hidden size (5120 for OPT-13B).
Query, key and value vectorsThree vectors computed from each token's hidden state in each layer by multiplying it with three learned weight matrices. A token's query is compared with earlier tokens' keys to decide how much of each earlier token's value to take.
AttentionThe computation that, for one token, scores its query against every earlier key, turns the scores into weights that sum to 1 (softmax), and outputs the weighted sum of the earlier values.
KV cacheThe stored key and value vectors of every token already processed, for every layer, kept in GPU memory so that each new token's attention can read them instead of recomputing them. It grows by one entry per layer for every token.
Prompt phase (prefill)The first step of serving a request: all prompt tokens are processed together in one pass, producing their KV cache and the first output token.
Generation phase (decode)The rest of serving a request: one pass per output token, each taking the newest token as input and adding its keys and values to the KV cache.
SequenceThe paper's term for a prompt plus the output tokens generated after it. A request produces one sequence, or several (parallel sampling, beam search).
Iteration-level schedulingA batching discipline (from Orca) in which the server re-forms the batch after every decoding step: finished requests leave and waiting ones join, rather than the whole batch finishing together.
HBM (GPU memory)The high-bandwidth DRAM stacked next to the GPU chip: 40 or 80 GB on an A100, about 1.5 to 2 TB/s (general knowledge). Weights, KV cache and activations all live here.
KernelA function launched from the CPU that runs on the GPU across thousands of threads at once. Every launch has a fixed overhead of a few microseconds (general knowledge).
WarpA group of 32 GPU threads that execute the same instruction together; its memory accesses are fastest when the 32 threads read consecutive addresses (a coalesced access).
KV blockvLLM's unit of KV cache storage: a fixed-size slot holding the keys and values of B consecutive tokens of one sequence (B = 16 by default).
Logical KV blockA block-sized position range in one sequence (tokens 0 to 15 are logical block 0, 16 to 31 logical block 1), the analogue of a virtual page.
Physical KV blockA block-sized slot carved out of a pre-allocated region of GPU (or CPU) memory, identified by a number, the analogue of a physical page frame.
Block tableA per-sequence array whose entry i holds the physical block number backing logical block i and how many of its slots are filled: the analogue of a page table.
Reference countA counter kept for each physical block equal to the number of logical blocks (across all sequences) mapped to it; the block is freed when it reaches 0.
Copy-on-write (CoW)A sharing rule: a block mapped by several sequences stays shared until one of them must write into it; that writer first gets its own copy.
Parallel samplingA decoding mode that draws several independent random outputs for one prompt, so one request has several sequences with the same prompt.
Beam searchA decoding mode that keeps the k most probable partial outputs (the beam width) and, at every step, extends each by every possible token and keeps the best k of the results.
PreemptionStopping a running sequence so its memory can be used by others, with its state either moved elsewhere or discarded and rebuilt later.
Swapping (in vLLM)Copying a preempted sequence's KV blocks from GPU memory to CPU memory over PCIe, and back when it is rescheduled.
RecomputationDiscarding a preempted sequence's KV cache and rebuilding it later by running prefill over the prompt plus the tokens already generated.
Tensor model parallelismSplitting each layer's weight matrices across several GPUs (Megatron-LM style), so each GPU computes a slice of every layer and the slices are combined with an all-reduce after each layer.
Buddy allocatorA memory allocator that hands out power-of-two-sized chunks by splitting larger free chunks in halves and merging free halves back; the paper assumes Orca uses one.
Normalized latencyThe paper's metric: each request's end-to-end latency divided by its number of output tokens, averaged over requests (seconds per token).
Short primers (tap to open)
1A Transformer at inference time, and why it keeps a KV cache▾

A language model turns text into tokens and predicts the next token from all the earlier ones. The probability of a whole sequence is written as a product of next-token probabilities, P(x1) · P(x2 | x1) · ... (the paper's Eq. 1), so text is produced one token at a time: predict, pick a token, append it, predict again.

Inside the model, each token is a vector of d numbers (d = 5120 for OPT-13B) that passes through L layers (L = 40). In every layer, three weight matrices turn the token's vector into a query q, a key k and a value v (Eq. 2). Attention then lets token i look back: score qi against each earlier key kj (a dot product scaled by 1/√d), turn the scores into weights with a softmax, and output the weighted sum of the earlier values (Eq. 3). Every other part of the layer (the feed-forward network, normalization, the residual connection) works on each token separately; attention is the only place tokens interact.

When token 501 is generated, its attention needs the keys and values of tokens 1 to 500 in every layer. Those do not change once computed (a token's key depends only on it and the tokens before it), so the server keeps them: the KV cache. Each new token adds one key and one value vector of d numbers per layer. In 16-bit floating point (FP16, 2 bytes per number) that is 2 × L × d × 2 bytes per token: 2 × 40 × 5120 × 2 = 819,200 bytes = 800 KB for OPT-13B, exactly the paper's number (where KB means 1024 bytes).

One subtlety the paper points out: the cached key of a word depends on everything before it, so "the" at position 3 and "the" at position 40 have different KV cache entries. Two sequences can share cache entries only for a common prefix, not for any common word.

Now you're ready: the KV cache grows by a fixed number of bytes per token, for as long as the request runs, and nobody knows in advance how long that is.
2Prefill, decode, batching, and why serving is memory-bound▾

A request is served in two phases. Prefill processes the whole prompt in one pass: all prompt tokens are known, so each weight matrix multiplies a matrix of many token vectors at once (matrix-matrix multiplication), which keeps the GPU's arithmetic units busy. Decode then produces one token per pass, because each token depends on the previous one. A decode pass for one request multiplies each weight matrix by a single vector (matrix-vector multiplication).

Matrix-vector work is limited by memory bandwidth, not arithmetic. Each weight (2 bytes) is read from GPU memory and used for 2 floating-point operations (a multiply and an add) per token. An A100 can do about 312 trillion FP16 operations per second but read only about 1.5 trillion bytes per second (general knowledge), so it needs roughly 200 operations per byte to keep its arithmetic units busy. One request gives 1 operation per byte. A decode step for OPT-13B with one request reads all 26 GB of weights, about 17 ms at 1.5 TB/s, to produce a single token (this guide's arithmetic).

Batching fixes this: if 30 requests decode together, the weights are read once and used 30 times. The paper: "the overhead of moving weights is amortized across the requests in a batch". But each request in the batch needs its own KV cache resident in GPU memory, and the attention step reads each request's whole cache every step. So the batch size, and with it the throughput, is set by how many KV caches fit. The paper calls this being memory-bound, in both senses: bandwidth limits each step, and capacity limits the batch.

Now you're ready: any byte of GPU memory wasted on a reservation is a smaller batch, and a smaller batch is lower throughput at the same per-step cost.
3GPU memory, kernels, warps and the PCIe link▾

A GPU is many simple processors (108 streaming multiprocessors on an A100) sharing one large DRAM, the HBM. Code runs as kernels: the CPU launches a kernel, and the GPU runs it with thousands of threads. Threads are grouped into warps of 32 that execute in lockstep. When the 32 threads of a warp read 32 consecutive words, the hardware merges the reads into a few wide memory transactions (coalescing); scattered reads waste bandwidth. Each kernel launch costs a few microseconds of fixed overhead, so many tiny kernels are slow (general knowledge throughout this primer).

GPUs do have virtual memory hardware, but at a coarse granularity (allocations are managed in 2 MB pages on recent NVIDIA GPUs) and under the driver's control, not the serving system's. A framework like PyTorch hands a kernel a pointer to a contiguous tensor and the kernel computes element addresses by arithmetic (general knowledge). The paper's starting observation is exactly this: "most operators in current deep learning frameworks [33, 39] require tensors to be stored in contiguous memory". So a request's KV cache had to be one contiguous array, and an array cannot grow in place if something else sits right after it.

The GPU talks to the CPU's memory over PCIe, about 32 GB/s per direction for PCIe 4.0 x16, roughly 50 times slower than HBM. Copies are issued with calls such as cudaMemcpyAsync; each call has a fixed setup cost, so many small copies achieve much less than the link's bandwidth. This is why the paper's swapping is slow with small blocks (M14).

Now you're ready: PagedAttention is a kernel change first. Without a kernel that can follow a block table, the KV cache has to stay contiguous.
4What an LLM serving system does: requests, decoding modes, and Orca's batching▾

A serving system accepts requests (prompt plus parameters such as maximum length or number of samples), runs the model, and streams back tokens. A request ends when the model emits an end-of-sequence token (<eos>) or hits its maximum length (2048 tokens for OPT). Output lengths are therefore unknown when a request arrives and vary widely (the paper's Fig. 11: ShareGPT outputs average 338 tokens, Alpaca 58).

Decoding modes differ in how the next token is picked. Greedy decoding takes the most probable token. Sampling draws one at random. Parallel sampling draws several independent outputs from one prompt (code assistants show several suggestions). Beam search keeps the k best partial outputs at each step; the survivors are usually extensions of the same few earlier candidates, so their histories overlap.

Old servers batched at the request level: a batch started together and ended when its longest member ended, with shorter requests padded. Orca (OSDI 2022) introduced iteration-level scheduling: re-form the batch after every decoding step. That removed queueing behind long requests and padding, but it made memory harder: requests now join and leave the batch at arbitrary times, each needing KV cache space of unknown final size. vLLM keeps Orca's scheduling and fixes the memory side.

FasterTransformer is NVIDIA's latency-optimized inference library; it has no scheduler, so the authors gave it a simple one that batches up to B earliest arrivals.

Now you're ready: the baselines differ only in how much KV cache space they reserve per request, so the comparison isolates memory management.
5The OS ideas the paper borrows: pages, fragmentation, copy-on-write, swapping▾

Paging: the OS divides memory into fixed-size pages (4 KB on x86). A process sees contiguous virtual addresses; a page table maps each virtual page to any free physical frame. Frames are allocated only when a page is first touched (demand paging).

Fragmentation comes in two kinds. Internal: space allocated to someone but unused, such as the unused part of the last page, or a chunk sized for a maximum that was never reached. External: free space broken into pieces too small or misaligned for a request, as happens when variable-size chunks are allocated and freed. Fixed-size pages eliminate external fragmentation (any free frame fits any page) and bound internal fragmentation to less than one page per region.

Copy-on-write: after fork, parent and child share all pages read-only; the first write to a shared page traps and the writer gets a private copy. A reference count per frame tells when sharing ends and when the frame is free. Shared libraries map the same frames into many processes.

Swapping: when memory is full, the OS writes some pages to disk and reads them back on demand. Which pages go is a policy (often an approximation of least recently used). A buddy allocator manages power-of-two-sized chunks; it rounds every request up to a power of two (internal waste) and can still leave free pieces that cannot be merged (external waste).

Now you're ready: vLLM's mapping is "blocks as pages, tokens as bytes, and requests as processes", and nearly every mechanism in the paper has an OS counterpart, with two the OS cannot do (M13, M15).
6Splitting one model across GPUs: Megatron-style tensor parallelism▾

OPT-66B has 132 GB of FP16 weights and OPT-175B 346 GB; neither fits in one 40 or 80 GB GPU. Tensor model parallelism (Megatron-LM) splits each layer's weight matrices across N GPUs. For attention, the split is by head: a layer's 5120-wide (for 13B) query, key and value vectors are really 40 heads of 128 numbers each, and each GPU computes a subset of heads. For the feed-forward network, each GPU holds a slice of the columns or rows. After each layer the partial results are summed across GPUs with an all-reduce, a collective operation that leaves every GPU with the total.

All GPUs run the same program on the same tokens at the same time (SPMD, single program multiple data). So every GPU needs KV cache for the same token positions, but only for its own heads: with 4 GPUs, each holds a quarter of each token's keys and values (general knowledge for the head counts).

Now you're ready: because every GPU caches the same positions, one block table can serve all of them (M16).
The whole story in one place

Throughput is batch size, and batch size is memory

The model and its math stay exactly the same. Only where each request's keys and values are stored, and who decides, changes.

A language model generates one token per forward pass, and each pass for one request reads every weight of the model to do very little arithmetic. The only way to use a GPU's arithmetic is to run many requests in the same pass, so serving throughput is set by the batch size. Every request in the batch needs its KV cache resident in GPU memory: the key and value vectors of all its earlier tokens, 800 KB per token for OPT-13B. On a 40 GB A100 holding the 26 GB of OPT-13B weights, about 12 GB remains for KV cache, room for about 15,700 tokens in total across all requests.

The servers before vLLM stored each request's KV cache as one contiguous tensor, because deep learning kernels expect contiguous tensors, and since the final length is unknown they reserved space for the maximum: 2048 tokens. The paper names three kinds of waste in such a chunk: reserved slots that will hold later tokens but block everyone else until then, internal fragmentation past the point where the request actually ends, and external fragmentation between chunks. Measured on its re-implementation of Orca, only 20.4% to 38.2% of KV cache memory holds actual token states (Fig. 2). Separate chunks also make it impossible to share the identical prompt cache of several samples of one request.

vLLM applies the operating system's answer to the same problem. PagedAttention is an attention kernel that reads keys and values from fixed-size blocks (16 tokens each by default) found through a per-sequence block table, so a sequence's blocks can be anywhere. The KV cache manager maps logical blocks to physical blocks only when a token needs a slot, so a sequence wastes at most one partly filled block. A physical block can be mapped by several sequences, with a reference count and copy-on-write, which gives prompt sharing for parallel samples, history sharing for beam search, and a cached system prompt shared across requests.

Paging also brings the operating system's other problem: memory can run out mid-request, because sequences grow. vLLM's scheduler serves requests first-come-first-serve, preempts the most recent ones when blocks run out, evicts all of a sequence group's blocks at once (a sequence cannot run with part of its cache), and restores them either by swapping to CPU memory or by recomputing the cache from the tokens in one prefill pass, an option an OS does not have. For models split across GPUs, one central scheduler owns the block tables and sends them to every GPU with each step's inputs.

The result, on OPT-13B, 66B and 175B with the ShareGPT and Alpaca traces: 96.3% of KV memory holds token states, the average batch on OPT-13B grows from 13.62 (an Orca that knows output lengths in advance, impossible in practice) to 30.42, and vLLM sustains 1.7 to 2.7 times the request rate of that idealized Orca on ShareGPT at similar latency. The gain shrinks when memory is not the bottleneck (short Alpaca requests on the 8-GPU OPT-175B setup) and grows with longer sequences and beam search. The price is a 20 to 26% slower attention kernel and new choices with no free answer: the block size, and swap versus recompute.

🍯 Key takeaways

  • Decoding is memory-bound, so throughput comes from batching, and the batch is limited by how many KV caches fit in GPU memory.
  • Contiguous per-request reservation wastes most of that memory: 20.4 to 38.2% holds tokens in the paper's measurements, against 96.3% in vLLM.
  • PagedAttention makes non-contiguous storage possible by changing the attention kernel to follow a block table; everything else in vLLM is built on that.
  • Logical-to-physical block mapping with on-demand allocation bounds waste to one block per sequence and removes external fragmentation, because all blocks are the same size.
  • Reference counts and block-level copy-on-write let samples, beams and requests share KV cache, saving up to 55% (Alpaca) or 66% (ShareGPT) of blocks in beam search.
  • Growing caches mean memory can run out mid-request: FCFS scheduling, all-or-nothing eviction of sequence groups, and recovery by swapping or recomputation handle it.
  • Costs: 20 to 26% slower attention kernels, and a block size that trades GPU efficiency against fragmentation (16 by default).
Six everyday pictures

How to think about paged KV cache

Each stands alone. Every card ends with where the picture stops being true, tied to a mechanism in How It Works.

Contiguous reservation · internal and external fragmentation

A restaurant that seats every party at a table for twelve

Nobody knows how many friends will join later, so the host gives each arriving party a table for the largest possible group. A couple sits at a table for twelve all evening; the room holds seven parties and turns away the rest, and the strips of floor between big tables fit no table at all. That is Orca (Max): 2048 slots per request, 20.4% of them ever used.

Where it breaks: a restaurant could move a party to a smaller table; a server cannot cheaply move a gigabyte-scale KV tensor, and the paper calls compaction "impractical" (M4).
PagedAttention · block table

A long novel shelved one volume wherever a slot is free, with a card listing where each volume is

The library no longer keeps an empty stretch of shelf for every series that might grow. Each new volume goes in any free slot, and the series' catalog card records "vol. 1: shelf 7, vol. 2: shelf 1, vol. 3: shelf 3". A reader follows the card. vLLM's block table is that card, and the attention kernel is the reader who follows it for every block of every sequence.

Where it breaks: a person reading a card is free compared with reading a book; for the GPU kernel the extra lookup and branches cost 20 to 26% of attention time (M5, M18).
Reference counts · copy-on-write · parallel sampling

Two students sharing one set of lecture notes until each wants to write on the last page

Both read the same pages, so only one copy exists. When the first student wants to add a line to the half-written last page, he photocopies that page and writes on his copy; the second student then writes on the original, since nobody else holds it anymore. Every other page stays shared. That is parallel sampling: the prompt blocks are shared, and only the partly filled last block is copied, once.

Where it breaks: students would copy before every edit to be safe; vLLM counts references, so with n sharers there are exactly n − 1 copies and the last writer copies nothing (M9).
Beam search · dynamic sharing · freeing at count zero

Drafts of a speech that share their opening paragraphs

A speechwriter keeps the four most promising drafts. Most begin with the same paragraphs and branch near the end. When two drafts are thrown out and the two best are each split into two new variants, the paragraphs only the discarded drafts used go in the bin, and the new variants start from the shared pages without retyping them. In Fig. 9, blocks 2, 4, 5 and 8 are freed and blocks 9 to 12 are new; blocks 0, 1 and 3 stay shared by all four.

Where it breaks: a writer can rewrite a shared paragraph for one draft; a cached key or value never changes once written, so sharing only covers identical prefixes, and the tree only grows at the leaves (M10).
Shared prefix · system prompt

Letterhead printed once in bulk, with only the personal line typed per letter

An office that sends thousands of letters with the same three paragraphs of instructions has them preprinted, and types only the recipient's line. vLLM's service provider reserves physical blocks holding the KV cache of a fixed system prompt, and every request with that prefix maps its first logical blocks to them and runs prefill only on its own input.

Where it breaks: the paper only covers prefixes the provider predefines; it does not detect common prefixes between arbitrary requests, and a prefix that ends mid-block costs every request one block copy (M11).
All-or-nothing eviction · swapping · recomputation

A kitchen that moves a whole party out when it needs their table

A party cannot eat with half its members seated, so when the room is full and an earlier party needs more space, the most recently seated party is moved out together: either to the waiting room with their plates (swapping blocks to CPU memory) or sent home with their order slip, to be cooked again later (recomputation from the tokens). New guests wait at the door until every moved party has finished.

Where it breaks: re-cooking a meal costs as much as the first time, but recomputing a KV cache is cheaper than generating it was, because the already generated tokens are fed back as one parallel prefill pass instead of one pass per token (M15).

What one step costs, and why the batch matters
  • Weights: every decoding step reads all 26 GB of weights once, whatever the batch size. At about 1.5 TB/s (A100-40GB, general knowledge) that is roughly 17 ms per step (this guide's arithmetic).
  • KV cache: every step reads each running sequence's whole KV cache in every layer. 30 sequences of 500 tokens is 30 × 500 × 800 KB ≈ 12 GB, about 8 ms more per step at the same bandwidth (illustrative).
  • Arithmetic: about 2 operations per weight per token, so a batch of 30 does 30 times the useful work for the same weight traffic. The GPU's arithmetic would only be saturated at roughly 200 tokens per step (general knowledge ratio of peak FLOPS to bandwidth).
  • So: tokens per second ≈ batch size ÷ step time, and step time grows slowly with batch size. Every extra sequence that fits is nearly free throughput, which is why the paper treats KV cache memory as the bottleneck ("the serving system's throughput is memory-bound").

1 · The problem: contiguous KV cache wastes most of the memory that sets the batch size

Decode steps are memory-bound, so throughput comes from batching, and the batch is capped by how many KV caches fit (M1, M2). One OPT-13B token's cache is 800 KB and one request can need 1.6 GB (M3). Existing servers store each request's cache as one contiguous tensor reserved for the maximum length, which wastes memory three ways (reserved slots, internal fragmentation, external fragmentation) and prevents sharing: only 20.4 to 38.2% of KV memory holds token states (M4).

2 · PagedAttention and the KV cache manager

The attention kernel is rewritten to compute block by block over fixed-size KV blocks found through a block table (M5). A central KV cache manager keeps, for every sequence, a table from logical blocks to physical blocks and the number of filled slots, and allocates a physical block only when the previous one is full (M6, M7). The block size, 16 tokens by default, trades kernel efficiency against fragmentation and sharing (M8).

3 · Sharing: one physical block, many sequences

A reference count per physical block and copy-on-write at block granularity let parallel samples share their prompt (M9), beam-search candidates share their common history as it changes every step (M10), and requests share a provider-defined system prompt (M11). Decoding algorithms are expressed with three operations, fork, append and free, and the kernel only ever sees lists of physical block numbers, so requests with different decoding methods batch together (M12).

4 · Running out: scheduling, eviction, swapping and recomputation

Requests are served first-come-first-serve; when no free block remains, the most recently arrived sequence group is preempted and all its blocks are evicted together (M13). They come back either by swapping, copying blocks to a CPU-memory pool and back over PCIe (M14), or by recomputation, re-running prefill over the prompt plus the generated tokens (M15). For models split across GPUs, one scheduler holds the only KV cache manager and sends each step's block tables with the token IDs to every GPU (M16).

5 · Kernels, and what the evaluation shows

Three custom kernels make the indirection cheap enough: a fused reshape-and-block-write (M17), a fused block-read-and-attention kernel with one warp per block (M18), and a batched block copy for copy-on-write (M19). Against FasterTransformer and three versions of Orca (M20), vLLM batches 2.2 to 4.3 times as many requests on OPT-13B with ShareGPT, sustains 1.7 to 2.7 times Orca (Oracle)'s request rate there, and up to 2.3 times with beam search; the attention kernel itself is 20 to 26% slower (F).

P · Paper map

Background and context
  • Kwon, Li (equal contribution), Zhuang, Sheng, Zheng, Yu, Gonzalez, Zhang, Stoica. UC Berkeley, with Stanford, UC San Diego and an independent researcher. SOSP 2023, Koblenz. The version read here is arXiv:2309.06180v1 (12 September 2023), 16 pages.
  • Setting: hosted LLM services (chatbots, programming assistants). "processing an LLM request can be 10× more expensive than a traditional keyword query", so throughput, which sets cost per request, is what matters.
  • Prior systems it measures against: FasterTransformer (NVIDIA, latency-optimized, no scheduler) and Orca (OSDI 2022, iteration-level scheduling; not public, so re-implemented by the authors in three variants).
  • Hardware: NVIDIA A100 GPUs on Google Cloud A2 instances (40 GB, and 80 GB for OPT-175B). Models: OPT-13B, 66B, 175B and LLaMA-13B.
  • Implementation: 8.5K lines of Python (scheduler, block manager) and 2K lines of C++/CUDA (kernels), FastAPI frontend with an OpenAI-compatible API. Open source as vLLM.
The problem

Serving throughput is "memory-bound": decode steps underuse the GPU unless many requests are batched, and the batch is limited by KV cache memory. Existing servers keep each request's KV cache in one contiguous, maximum-length chunk, so "only 20.4% - 38.2% of the KV cache memory is used to store the actual token states", and sequences of one request cannot share their identical prompt cache.

The result

"vLLM improves the throughput of popular LLMs by 2-4× with the same level of latency compared to the state-of-the-art systems, such as FasterTransformer and Orca. The improvement is more pronounced with longer sequences, larger models, and more complex decoding algorithms." Near-zero waste: 96.3% of KV memory holds token states (Fig. 2).

Mechanisms in dependency order
  1. Diagnose (M1 to M4): why decode is memory-bound, how big the cache is, how contiguous reservation wastes it.
  2. Make non-contiguous storage possible (M5): an attention kernel that computes over blocks found through a table.
  3. Manage blocks like pages (M6 to M8): logical and physical blocks, block tables, on-demand allocation, a block size.
  4. Share blocks (M9 to M12): reference counts, copy-on-write, beam search, prefixes, and the fork/append/free interface.
  5. Handle running out (M13 to M15): FCFS, all-or-nothing preemption of sequence groups, swap or recompute.
  6. Scale out and make it fast (M16 to M19): one manager for all GPUs; three fused kernels.
  7. Measure (M20, F): baselines, traces, normalized latency, ablations.
The central trade-offs
  • Flexibility versus kernel speed: indirection through a block table makes the attention kernel "20–26% higher attention kernel latency" than FasterTransformer's, which the paper argues is small because "it only affects the attention operator but not the other operators in the model, such as Linear."
  • Block size: "If the block size is too small, vLLM may not fully utilize the GPU's parallelism for reading and processing KV cache. If the block size is too large, internal fragmentation increases and the probability of sharing decreases." Default 16.
  • Swap versus recompute: swapping depends on PCIe bandwidth and suffers with small blocks; recomputation depends on GPU compute and is independent of block size.
  • Aggressive admission versus preemption: allocating on demand lets more requests in, but memory can then run out mid-request, which reservation-based servers never face.
Effect of changes (whole design)
  • If the workload is compute-bound (short sequences on a large-memory setup), better memory use buys little: Fig. 12(f), OPT-175B on Alpaca, shows vLLM barely ahead of Orca (Oracle). The paper's Discussion says the technique may even "degrade the performance" for non-LLM DNN serving.
  • If output lengths were known in advance, Orca (Oracle) shows reservation still loses: 38.2% token states, because reserved-but-not-yet-used slots and allocator waste remain.
  • If GPU memory grew faster than compute, the bottleneck would move toward compute; the paper argues the opposite trend ("from NVIDIA A100 to H100, The FLOPS increases by more than 2x, but the GPU memory stays at 80GB maximum").
  • If attention used a fixed window or compressed cache (later model designs, general knowledge), the cache per sequence would be bounded, which reduces the internal-fragmentation problem but keeps the variable-length, sharing and preemption problems (inference).

M1 · Prefill, decode and the KV cache

TL;DR
ProblemEach new token's attention needs the keys and values of every earlier token in every layer; recomputing them every step would redo all earlier work.
MechanismCompute the prompt's keys and values in one parallel prefill pass, then cache them and add one token's keys and values per decode step.
Trade-offEach step only computes one token's work, in exchange for memory that grows by 800 KB per token (OPT-13B) for the life of the request.
Breaks whenThe caches of all running requests do not fit in GPU memory, or their final size must be known in advance.
Key points
  • Prompt phase: "takes the whole user prompt (x1, ..., xn) as input and computes the probability of the first new token P(xn+1 | x1, ..., xn). During this process, also generates the key vectors k1, ..., kn and value vectors v1, ..., vn." It "can be parallelized using matrix-matrix multiplication operations".
  • Generation phase: "the key and value vectors at positions 1 to n + t − 1 are cached at previous iterations, only the new key and value vector kn+t and vn+t are computed at this iteration."
  • "The computation at different iterations cannot be parallelized due to the data dependency and often uses matrix-vector multiplication, which is less efficient. As a result, this phase severely underutilizes GPU computation and becomes memory-bound, being responsible for most portion of the latency of a single request."
  • End condition: "This phase completes either when the sequence reaches a maximum length (specified by users or limited by LLMs) or when an end-of-sequence (<eos>) token is emitted." So the cache's final size is unknown when the request starts.
  • "Note that the KV cache of one token depends on all its previous tokens. This means that the KV cache of the same token appearing at different positions in a sequence will be different." Sharing is therefore only possible for identical prefixes.
  • Only attention mixes positions: all other components "are all applied independently position-wise in a form of yi = f(xi)."
How it works, step by step: Fig. 6's request
  1. Prefill. Prompt "Four score and seven years ago our", 7 tokens. One forward pass computes, in each of the 40 layers, k1...k7 and v1...v7 (a 7 × 5120 matrix times each weight matrix) and the distribution of token 8, from which "fathers" is picked. Cache: 7 tokens × 800 KB = 5.6 MB.
  2. Decode step 1. Input: "fathers" only. Each layer computes q8, k8, v8, appends k8, v8 to that layer's cache, scores q8 against k1...k8, and outputs a weighted sum of v1...v8. Out comes "brought". Cache: 8 tokens, 6.4 MB.
  3. A detail that matters for M7: a generated token's own keys and values are computed in the step that takes it as input, one step after it was produced. That is why Fig. 6's first decode step stores the KV cache of "fathers", the token prefill already produced.
  4. Decode step t. Reads (7 + t) cached tokens in every layer and adds one. The read traffic per step grows linearly with the sequence, and the cache grows by 800 KB per step until <eos>.
  5. Done. A ShareGPT request averages 161 input and 338 output tokens (Fig. 11), so about 500 tokens × 800 KB ≈ 0.4 GB at its end (this guide's arithmetic).
Assumptions it relies on
  • A1. A cached key or value never changes once computed (implicit: it depends only on its own and earlier tokens).
  • A2. Attention at position i uses all positions 1 to i (stated, Eq. 3).
  • A3. The final length is unknown until <eos> or the maximum (stated).
  • A4. The caches of all running requests stay resident in GPU memory (implicit; the kernel reads them every step).
If an assumption changes
  • A1 changes (cached entries could be updated): sharing by reference (M9 to M11) would need invalidation, and copy-on-write would trigger on old blocks, not only the last one (inference).
  • A2 changes (sliding-window attention, general knowledge): blocks older than the window could be freed from the front of the block table, which paging makes easy and a contiguous tensor does not (inference).
  • A3 changes (lengths known): this is Orca (Oracle). Fig. 2 shows it still wastes 61.8% of KV memory, so knowing lengths does not remove the need for paging.
  • A4 changes (cache could live elsewhere and be streamed in): each decode step would pay PCIe transfers, about 50 times slower than HBM; FlexGen does this for offline, throughput-only inference, which the paper says "does not target the online serving settings".
Design notes and rejected alternatives

Caching keys and values is standard practice (the paper cites it as the "KV cache [41]"); the paper does not consider dropping it. Its one form of recomputation (M15) is used only after preemption, where all lost tokens can be recomputed in one parallel prefill pass rather than one pass per token.

Connections

Hints: the KV cache is Lampson's "cache answers to expensive computations", with the unusual property that its entries never go stale (inference). Salus: Salus divides deep learning memory into model (persistent), ephemeral (freed at the end of each iteration) and framework-internal; the KV cache fits none of them: it outlives iterations like model memory but is per request and grows like nothing in a training job (inference).

M2 · Batching, iteration-level scheduling, and why memory sets throughput

TL;DR
ProblemA decode step for one request reads all the weights to produce one token; the GPU's arithmetic sits idle.
MechanismRun many requests in the same step (batching), and re-form the batch after every step so requests join and leave independently (iteration-level scheduling, from Orca).
Trade-offWeight traffic is amortized across the batch, but every request in the batch needs its KV cache resident, so the batch is capped by memory.
Breaks whenKV cache memory is wasted, so fewer requests fit than the GPU could compute for.
Key points
  • "Because the requests share the same model weights, the overhead of moving weights is amortized across the requests in a batch, and can be overwhelmed by the computational overhead when the batch size is sufficiently large."
  • Two obstacles to naive batching: requests "may arrive at different times", and they "may have vastly different input and output lengths", so padding to equal length wastes compute and memory.
  • Fine-grained batching (cellular batching, Orca's iteration-level scheduling): "After each iteration, completed requests are removed from the batch, and new ones are added. Therefore, a new request can be processed after waiting for a single iteration".
  • What remains: "the number of requests that can be batched together is still constrained by GPU memory capacity, particularly the space allocated to store the KV cache. In other words, the serving system's throughput is memory-bound."
  • Fig. 1 (right): with existing systems memory hits 40 GB at about 8 requests and throughput is about 0.27K tokens/s; vLLM reaches about 38 requests and about 0.9K tokens/s on the same throughput curve (approximate read-offs).
  • vLLM's step input: it "concatenates all the input tokens of the current iteration (i.e., all tokens for prompt phase requests and the latest tokens for generation phase requests) as one sequence and feeds it into the LLM."
How it works, step by step: one iteration with three requests
  1. Batch at iteration t: request R1 (decoding, 300 tokens cached), R2 (decoding, 40 cached), R3 (just arrived, 120-token prompt). Illustrative numbers.
  2. Input: 1 + 1 + 120 = 122 tokens concatenated into one sequence. The linear layers (q, k, v projections, feed-forward) process all 122 positions with one matrix multiply each, because they act position by position.
  3. Attention: each position attends only within its own request: R1's new token reads 301 cached positions, R2's reads 41, R3's 120 prompt tokens attend among themselves. This needs a kernel that handles variable lengths in one batch (M18).
  4. Weight reads: 26 GB once for all 122 positions instead of three times.
  5. Iteration t + 1: if R2 emitted <eos>, it leaves; its KV memory is freed; a waiting request may join. The batch size the next step can have is whatever the free KV memory allows.
Assumptions it relies on
  • A1. All requests use the same model weights (stated).
  • A2. Step time grows slowly with batch size while memory-bound (implicit; true until the batch is large enough to saturate arithmetic).
  • A3. Requests are independent, so any subset can be batched (implicit).
If an assumption changes
  • A1 changes (many different models on one GPU): batching across models amortizes nothing; this is the multi-model setting of earlier serving systems (Clipper, Nexus) and of Salus, not this paper's (inference).
  • A2 changes (compute-bound): extra batch slots no longer raise throughput. Fig. 12(f) is this case, and the paper says so: "the performance of the systems becomes compute-bound rather than memory-bound."
  • A3 changes (sequences that share state, such as beams): they must be scheduled together, which is why vLLM gang-schedules a request's sequences as a group (M13).
Design notes and rejected alternatives

vLLM keeps iteration-level scheduling; the paper calls Orca's scheduling and PagedAttention "complementary techniques": Orca raises utilization "by scheduling and interleaving the requests", vLLM "by increasing memory utilization so that the working sets of more requests fit into memory." It also notes that fine-grained interleaving "makes memory management more challenging", because a request's memory needs are now spread over arbitrary iterations.

Connections

Livelock: the normalized-latency curves (Fig. 12) rise slowly and then explode once arrivals exceed capacity, the queueing collapse the Livelock paper studies for packets; the paper's explanation is the same: "the queue length continues to grow infinitely" (connection is inference). Salus: Salus also switches GPU work at iteration boundaries, between whole training or inference jobs rather than between requests of one model.

M3 · How big the KV cache is, from first principles

TL;DR
ProblemTo see whether memory is the bottleneck, one must know how many bytes each token's cache takes and how many tokens fit.
MechanismBytes per token = 2 (key and value) × layers × hidden size × bytes per number. Tokens that fit = KV memory ÷ bytes per token.
Trade-offBigger models need more bytes per token and also more memory for weights; the number of token slots does not grow with the model (Table 1: 15.7K, 9.7K, 60.1K).
Breaks whenModels use fewer key/value heads than query heads, or quantized caches (later techniques, general knowledge), which change the formula's factors.
Key points
  • "for the 13B parameter OPT model [62], the KV cache of a single token demands 800 KB of space, calculated as 2 (key and value vectors) × 5120 (hidden state size) × 40 (number of layers) × 2 (bytes per FP16). Since OPT can generate sequences up to 2048 tokens, the memory required to store the KV cache of one request can be as much as 1.6 GB."
  • "Concurrent GPUs have memory capacities in the tens of GBs. Even if all available memory was allocated to KV cache, only a few tens of requests could be accommodated."
  • Table 1: memory for KV cache 12 GB / 21 GB / 264 GB and maximum KV cache slots 15.7K / 9.7K / 60.1K for 13B / 66B / 175B.
  • Fig. 1 (left): for 13B on a 40 GB A100, parameters 26 GB (65%), KV cache labeled ">30%", and "Others" for activations. The text says "Close to 30%", and Table 1's 12 of 40 GB is exactly 30%.

Design notes and rejected alternatives

The paper uses the 13B arithmetic only to argue the problem's scale. The trend argument ("the GPU's computation speed grows faster than the memory capacity", A100 to H100 more than 2× FLOPS, 80 GB maximum) is the claim that the problem will get worse, not better.

M4 · Contiguous pre-allocation in existing systems, and its three wastes

TL;DR
ProblemDeep learning kernels need a request's KV cache in one contiguous tensor, and the final length is unknown.
MechanismAt admission, reserve a contiguous chunk sized for the request's maximum possible length (Orca (Max): 2048 tokens), from a buddy allocator.
Trade-offSimple, and a request never runs out mid-way, but memory is lost to reserved slots, internal fragmentation and external fragmentation, and sequences cannot share.
Breaks whenActual lengths are far below the maximum (ShareGPT averages about 500 of 2048), so only 20.4 to 38.2% of memory holds tokens.
Key points
  • "Since most operators in current deep learning frameworks [33, 39] require tensors to be stored in contiguous memory, previous LLM serving systems [31, 60] also store the KV cache of one request as a contiguous tensor across the different positions. Due to the unpredictable output lengths from the LLM, they statically allocate a chunk of memory for a request based on the request's maximum possible sequence length".
  • Three wastes: "reserved slots for future tokens, internal fragmentation due to over-provisioning for potential maximum sequence lengths, and external fragmentation from the memory allocator like the buddy allocator."
  • "The external fragmentation will never be used for generated tokens, which is known before serving a request. Internal fragmentation also remains unused, but this is only realized after a request has finished sampling. They are both pure memory waste. Although the reserved memory is eventually used, reserving this space for the entire request's duration, especially when the reserved space is large, occupies the space that could otherwise be used to process other requests."
  • "even if the actual length is known a priori, the pre-allocation is still inefficient: As the entire chunk is reserved during the request's lifetime, other shorter requests cannot utilize any part of the chunk that is currently unused."
  • On compaction: "performing compaction in a performance-sensitive LLM serving system is impractical due to the massive KV cache. Even with compaction, the pre-allocated chunk space for each request prevents memory sharing".
  • Fig. 2 (token states, reserved, internal, external and other): Orca (Max) 20.4 / 13.3 / 57.3 / 8.9; Orca (Pow2) 26.8 / 17.9 / 13.6 / 41.6; Orca (Oracle) 38.2 / 25.2 / none / 36.6; vLLM 96.3 with a thin remainder.
How it works, step by step: Orca (Max) on OPT-13B
  1. Admission: a request arrives; the server asks the buddy allocator for 2048 slots × 800 KB = 1.6 GB of contiguous memory. 15,728 slots hold floor(15,728 ÷ 2048) = 7 such chunks, and 15,728 − 14,336 = 1,392 slots (8.85%) can never hold an eighth. Fig. 2 reports 8.9% external fragmentation and other; Fig. 13 reports exactly 7.00 batched requests on both traces (this guide's arithmetic, assuming the Fig. 2 run is OPT-13B).
  2. Prefill: the prompt's tokens fill the start of the chunk. The rest of the chunk is now two different things that look the same: slots that will be used by tokens not yet generated (reserved), and slots past where the request will end (internal fragmentation). Nobody can tell which is which until <eos>.
  3. Decode: each step fills one more slot. On average over the run, a chunk holds 20.4% × 15,728 ÷ 7 ≈ 458 tokens, 299 reserved slots and 1,288 slots that will never be used (this guide's arithmetic from Fig. 2).
  4. Why 458 + 299 ≈ 757 is above ShareGPT's 499-token mean: long requests stay in the batch longer, so at a random moment the running requests are longer than the average request (length-biased sampling, inference).
  5. Pow2 and Oracle: reserving less (at most 2× the true output, or exactly the true output) shrinks internal fragmentation but not the reserved share, and the buddy allocator's power-of-two rounding and leftovers show up as external waste: 41.6% and 36.6%.
Assumptions it relies on
  • A1. Kernels need contiguous tensors (stated).
  • A2. A request must never run out of KV space once admitted (implicit; pre-allocation exists to guarantee it).
  • A3. Each sequence has its own chunk (implicit in "separate contiguous spaces").
  • A4. The allocator is a buddy allocator (stated as an assumption about Orca: "We assume Orca uses the buddy allocation algorithm").
If an assumption changes
  • A1 changes (kernel follows a table): this is PagedAttention (M5); everything else in vLLM follows.
  • A2 changes (allow running out): the server needs preemption and a way to recover state (M13 to M15). Paging buys memory efficiency at the price of this new failure mode.
  • A3 changes (sequences may share): requires that a sequence's cache can be partly someone else's memory, which a single contiguous tensor cannot express.
  • A4 changes (a better variable-size allocator): reduces external waste only; the 57.3% internal fragmentation of Orca (Max) comes from the reservation rule, not the allocator.
Design notes and rejected alternatives

The paper rejects compaction (moving chunks to merge free space) as impractical for gigabyte tensors and useless for sharing. The three Orca variants are the paper's construction to separate the effects: Max isolates over-reservation, Oracle removes it entirely and still shows the reserved and allocator waste.

Connections

Superpages: Navarro et al.'s reservation-based allocation also reserves a contiguous aligned region up front for a mapping that may or may not grow into it, but it fills that region with base pages on demand and can preempt the unused part of a reservation under memory pressure; Orca's chunks cannot give back their unused tail (inference). FFS: fragments within a block versus whole blocks is the same internal-fragmentation trade-off, and the free space reserve is the same idea as keeping memory headroom.

M5 · PagedAttention: attention computed block by block

TL;DR
ProblemAttention kernels read a sequence's keys and values from one contiguous tensor, which forces contiguous reservation (M4).
MechanismSplit each sequence's keys and values into blocks of B tokens stored anywhere; the kernel fetches block by block through the sequence's block table and combines the per-block scores into one softmax.
Trade-offAny memory layout works and blocks can be shared, in exchange for table lookups, extra branches and less regular memory access: 20 to 26% slower attention than FasterTransformer's kernel (Fig. 18a).
Breaks whenBlocks are so small that each fetch moves too little data to use the GPU well, or attention dominates the step so its slowdown dominates too.
Key points
  • "Unlike the traditional attention algorithms, PagedAttention allows storing continuous keys and values in non-contiguous memory space. Specifically, PagedAttention partitions the KV cache of each sequence into KV blocks. Each block contains the key and value vectors for a fixed number of tokens".
  • Key block Kj = (k(j−1)B+1, ..., kjB), value block Vj likewise. Eq. 4: Aij = exp(qi⊤Kj/√d) ÷ Σt=1⌈i/B⌉ exp(qi⊤Kt1/√d), and oi = Σj=1⌈i/B⌉ VjAij⊤, where Aij is "the row vector of attention score on j-th KV block."
  • "During the attention computation, the PagedAttention kernel identifies and fetches different KV blocks separately." Fig. 5: the query is "forth"; its keys and values are in three blocks that "are not contiguous on the physical memory".
  • Footnote 1: a token's key and value vectors span layers and heads; they can all be managed in one block, "or the key and value vectors at different heads and layers can each have a separate block and be managed in separate block tables. The two designs have no performance difference and we choose the second one for easy implementation."
  • Prefill does not use it: "In the prefill step, vLLM generates the KV cache of the prompts and the first output token with a conventional self-attention algorithm (e.g., [13])", where [13] is FlashAttention.
  • The abstract and introduction claim the method works "without affecting the model accuracy at all": it is the same attention, regrouped.
How it works, step by step: the query of "forth" (i = 10, B = 4)
  1. Which blocks: ⌈10 / 4⌉ = 3 logical blocks. The block table says logical 0, 1, 2 are physical 0, 1, 2 in Fig. 5's numbering (in Fig. 6's numbering the same sequence uses 7, 1, 3; the kernel does not care).
  2. Block 0: fetch the 4 keys of "Four score and seven", compute 4 scores q · k / √d (d is the head dimension per head in practice; the paper writes √d).
  3. Block 1: 4 more scores against "years ago our fathers".
  4. Block 2: only 2 of its 4 slots hold tokens ("brought", "forth"), so only 2 scores count. Eq. 4 as printed sums the full block (qi⊤Kt1) up to ⌈i/B⌉, which would include slots 11 and 12; the implementation must mask positions beyond i, using the filled count or the sequence length it is given (inference; the kernel's "support for variable sequence lengths" in §5.1 is where this lives).
  5. Combine: exponentiate all 10 scores, divide by their single sum (the shared denominator), multiply each block's values by its weights and add: o10. Same number as Eq. 3; only the grouping differs.
  6. Per head and per layer: this happens for each of 40 heads in each of 40 layers per decode step, for every sequence in the batch, which is why the kernel's efficiency matters (M18).
Assumptions it relies on
  • A1. A block holds consecutive positions of one sequence, so position p is slot p mod B of logical block ⌊p/B⌋ (stated by the definition of Kj).
  • A2. Regrouping the sum by blocks does not change the result (stated implicitly: "without affecting the model accuracy").
  • A3. The extra cost is confined to the attention operator (stated: "it only affects the attention operator but not the other operators in the model, such as Linear").
  • A4. The kernel receives each sequence's block table and length each step (stated in §4.6 and §5.1).
If an assumption changes
  • A1 changes (a block could hold scattered positions): each slot would need its own position record, the table would grow B-fold, and sharing a prefix by block would no longer be meaningful (inference).
  • A2 changes (bit-exact output required): floating-point sums in a different order can differ in the last bits (general knowledge), so the paper's "without affecting the model accuracy at all" means mathematically equivalent, not bitwise identical to FasterTransformer (inference).
  • A3 changes (long contexts): attention's share of step time grows with context length, so a 20 to 26% attention slowdown becomes a larger share of the step; Fig. 18a only measures contexts of 64 to 256 tokens.
  • A4 changes (tables not shipped each step): workers would need their own copy of memory management state and a protocol to keep it consistent; §4.6 avoids that by broadcasting tables with the inputs.
Design notes and rejected alternatives

The kernel is adapted from FasterTransformer's attention kernel, not written from scratch. The paper chose one block table per head and layer for "easy implementation" (footnote 1), yet §4.6 describes the scheduler sending "the block table for each request" and every GPU worker using "the same physical block IDs"; both readings are consistent if the same logical-to-physical numbering is reused for every layer and head, each with its own storage (the released vLLM code keeps one table per sequence and a separate key and value cache array per layer, general knowledge). Prefill keeps a conventional kernel because all prompt keys are computed in that same pass anyway.

Connections

x86 VMM (hwsw): the VMware paper contrasts software techniques (binary translation, shadow page tables) with hardware support for the same translation; PagedAttention is translation done entirely in software, inside the one consumer that needs it, with no hardware TLB, and pays for it in kernel time (inference). Exokernel: the serving engine implements its own virtual memory on raw device memory because it knows its access pattern (whole sequences, every step), the library-OS argument applied to a GPU (inference).

M6 · Logical blocks, physical blocks and block tables

TL;DR
ProblemThe model wants each sequence's cache as one ordered list of positions; memory efficiency wants any free space usable by anyone.
MechanismEach sequence's cache is a list of logical blocks; a per-sequence block table maps each to a physical block in a pre-allocated pool and records how many slots are filled. The KV cache manager in the scheduler owns the tables and the free pools (GPU and CPU).
Trade-offNo external fragmentation (all blocks are interchangeable) and growth without reservation, in exchange for a table per sequence and a central manager that must be consulted every iteration.
Breaks whenThe pool's size, fixed at startup, is wrong for the workload, or blocks of different sizes are needed.
Key points
  • "OS partitions memory into fixed-sized pages and maps user programs' logical pages to physical pages. Contiguous logical pages can correspond to non-contiguous physical memory pages, allowing user programs to access memory as though it were contiguous. Moreover, physical memory space needs not to be fully reserved in advance".
  • "A request's KV cache is represented as a series of logical KV blocks, filled from left to right as new tokens and their KV cache are generated. The last KV block's unfilled positions are reserved for future generations."
  • "On GPU workers, a block engine allocates a contiguous chunk of GPU DRAM and divides it into physical KV blocks (this is also done on CPU RAM for swapping; see §4.5)."
  • "The KV block manager also maintains block tables", "the mapping between logical and physical KV blocks of each request. Each block table entry records the corresponding physical blocks of a logical block and the number of filled positions."
  • "Separating logical and physical KV blocks allows vLLM to dynamically grow the KV cache memory without reserving it for all positions in advance, which eliminates most memory waste in existing systems".
  • Architecture (Fig. 4): a scheduler containing the KV cache manager (block tables) with a CPU block allocator and a GPU block allocator; N workers, each with a cache engine and a model shard. "the KV cache manager manages the physical KV cache memory on the GPU workers through the instructions sent by the centralized scheduler."
  • From the introduction: fixed-size blocks mean the design "eliminates external fragmentation as all blocks have the same size."
How it works, step by step: setting up OPT-13B
  1. Startup: the cache engine on the GPU allocates one contiguous region for the KV cache: 12 GB (Table 1). With B = 16, one physical block holds 16 tokens × 800 KB = 12.5 MB across all layers, so the pool has 12 GiB ÷ 12.5 MiB = 983 blocks (this guide's arithmetic).
  2. Layout inside a block: per the footnote, each layer (and head) has its own storage; physical block number b means "slot b" in every layer's key array and value array, 160 KB per layer per K or V for B = 16 (this guide's arithmetic; the exact layout is "optimized for block read", §5.1).
  3. Free pool: the GPU block allocator tracks which of the 983 numbers are free. Since every block is the same size and nothing on a GPU depends on where a block is, any free number is as good as any other (inference; HBM has no seek or locality cost at this granularity).
  4. A sequence arrives: its block table starts empty; entries are appended as the sequence grows (M7). A 2048-token sequence needs 128 entries, a few hundred bytes of table for 1.6 GB of cache (this guide's arithmetic).
  5. A sequence finishes: "its KV blocks can be freed to store the KV cache of other requests": its block numbers go back to the free pool (after reference counts reach zero, M9).
  6. CPU side: the same structure exists in CPU RAM, managed by the CPU block allocator, used only for swapped-out blocks (M14).
Assumptions it relies on
  • A1. All blocks have the same size (stated).
  • A2. The pool is allocated once at startup and does not grow or shrink (implicit; "allocates a contiguous chunk of GPU DRAM").
  • A3. One manager, in the scheduler, owns all tables (stated, Fig. 4 and §4.6).
  • A4. Physical placement does not affect performance (implicit).
If an assumption changes
  • A1 changes (several block sizes, for example big blocks for long sequences): free memory could again be broken into pieces of the wrong size, the external fragmentation the design removed; this is the Superpages problem of keeping contiguous free runs (inference).
  • A2 changes (memory needed by activations varies): the pool size must be chosen conservatively in advance; the paper does not describe how 12 GB is chosen (released vLLM profiles peak activation memory at startup and gives the rest to the pool, general knowledge).
  • A3 changes (managers per GPU): each GPU would need the same decisions for the same positions anyway (M16), so separate managers would only add agreement traffic.
  • A4 changes (non-uniform memory, for example blocks split across GPU and CPU or across HBM stacks): which physical block a sequence gets would start to matter, and the allocator would need placement policy, as FFS's did (inference).
Design notes and rejected alternatives

The paper presents the manager as the direct analogue of OS virtual memory and does not discuss alternatives such as allocating each block with the GPU driver's allocator. One pool allocated up front avoids per-block driver calls, which are slow and can synchronize the device (general knowledge). Keeping the tables in the scheduler, in Python, rather than on the GPU means the GPU never makes allocation decisions; it only receives tables.

Connections

FFS: FFS replaced a free list with per-group bitmaps because on a disk where a free block is matters; on GPU memory it does not, so vLLM can hand out any free block number (inference). LFS and F2FS: the inode map and node address table are also logical-to-physical maps that let data move without changing its name; vLLM's tables likewise let a swapped-in block land at a different physical number than it left (inference). Superpages: page tables with a single page size, which Superpages extends to several sizes at the cost of contiguity management.

M7 · Decoding with on-demand allocation: Fig. 6 and Fig. 7 step by step

TL;DR
ProblemThe server must give a growing sequence space for each new token without knowing how many there will be.
MechanismAt prefill, allocate only the blocks the prompt needs; at each decode step, write the new token's keys and values into the last block's next free slot, and allocate a new physical block only when the last one is full.
Trade-offWaste is at most one partly filled block per sequence, in exchange for a check (and possibly an allocation) every iteration and the possibility that no block is free.
Breaks whenThe free pool is empty when a sequence needs a new block; then a sequence must be preempted (M13).
Key points
  • ① "As in OS's virtual memory, vLLM does not require reserving the memory for the maximum possible generated sequence length initially. Instead, it reserves only the necessary KV blocks to accommodate the KV cache generated during prompt computation. In this case, The prompt has 7 tokens, so vLLM maps the first 2 logical KV blocks (0 and 1) to 2 physical KV blocks (7 and 1, respectively)."
  • ② "In the first autoregressive decoding step, vLLM generates the new token with the PagedAttention algorithm on physical blocks 7 and 1. Since one slot remains available in the last logical block, the newly generated KV cache is stored there, and the block table's #filled record is updated."
  • ③ "At the second decoding step, as the last logical block is full, vLLM stores the newly generated KV cache in a new logical block; vLLM allocates a new physical block (physical block 3) for it and stores this mapping in the block table."
  • "As all the blocks are filled from left to right and a new physical block is only allocated when all previous blocks are full, vLLM limits all the memory wastes for a request within one block".
  • Per iteration: "vLLM first selects a set of candidate sequences for batching (more in §4.5), and allocates the physical blocks for the newly required logical blocks."
  • Fig. 7: two requests share the pool; A's logical blocks 0, 1, 2 are physical 7, 1, 3, and B's logical blocks 0, 1 ("It was the best", "of times") are physical 5, 2. "The neighboring logical blocks of both sequences do not need to be contiguous in physical GPU memory".
How it works, step by step: one iteration of the whole engine
  1. Select: the scheduler picks the sequences that will run this iteration (FCFS, M13).
  2. Reserve slots: for each selected sequence in decode, if its last block is full (filled = B), take a block number from the free pool and append it to the table. For a new request in prefill, take ⌈prompt length ÷ B⌉ blocks. If the pool cannot supply them, preempt (M13) before running.
  3. Run: concatenate the inputs (whole prompts for new requests, one token for decoding ones), send token IDs and block tables to the workers, run the model. Each layer writes the new keys and values into slot (filled mod B) of the last block (M17) and reads all earlier blocks through the table (M18).
  4. Update: increment each sequence's filled count, sample the next tokens, and free every block of sequences that ended (reference counts permitting, M9).
  5. Waste at any moment: at most B − 1 = 15 empty slots per running sequence. With 30 sequences that is at most 450 of 15,728 slots, 2.9% (this guide's arithmetic), consistent with Fig. 2's 96.3% token states.
Assumptions it relies on
  • A1. Sequences only grow at the end, one token per decode step (stated: "filled from left to right").
  • A2. The per-iteration bookkeeping is cheap compared with a model step (implicit; the scheduler and block manager are Python).
  • A3. If no block is free, some sequence can be preempted (stated, §4.5).
If an assumption changes
  • A1 changes (several tokens appended per step, or tokens rolled back, as in speculative decoding, general knowledge): a step may need several new blocks at once, and rollback means decrementing filled and freeing trailing blocks; the table supports both, but the "one block of waste" bound still holds only at step boundaries (inference).
  • A2 changes (very fast steps, small models): Python bookkeeping per iteration could become a visible share of step time; the paper does not measure scheduler overhead (inference).
  • A3 changes (preemption not allowed, for example a strict latency service): the server would have to keep enough free blocks to finish every admitted request, which is reservation again in another form (inference).
Design notes and rejected alternatives

vLLM does not pre-allocate even one block ahead: the new block is allocated in the iteration that needs it. Prefill allocates exactly the prompt's blocks; the remaining slot in Fig. 6's logical block 1 is "reserved for the subsequent autoregressive generation phase", the only reservation in the design.

Connections

OS demand paging: the paper's own analogy; the difference is that the "fault" is predictable: the manager knows exactly when a block fills, so allocation happens before the kernel runs, not on a trap (inference). Hints: "Handle normal and worst cases separately": most iterations allocate nothing, since a block fills only every 16 steps (inference).

M8 · Choosing the block size

TL;DR
ProblemBlocks that are too small make the kernel and swaps inefficient; blocks that are too large waste slots and share less.
MechanismOne block size for the whole system, chosen by measurement: 16 tokens by default.
Trade-offKernel parallelism and large transfers (big B) versus internal fragmentation and sharing granularity (small B).
Breaks whenSequences are shorter than a block (Alpaca with B ≥ 64), or blocks are so small that each warp's fetch is tiny (B ≤ 4).
Key points
  • "Storing multiple tokens within a KV block (block size > 1) enables the PagedAttention kernel to process the KV cache across more positions in parallel, thus increasing the hardware utilization and reducing latency. However, a larger block size also increases memory fragmentation."
  • "If the block size is too small, vLLM may not fully utilize the GPU's parallelism for reading and processing KV cache. If the block size is too large, internal fragmentation increases and the probability of sharing decreases."
  • Fig. 18b: "In the ShareGPT trace, block sizes from 16 to 128 lead to the best performance. In the Alpaca trace, while the block size 16 and 32 work well, larger block sizes significantly degrade the performance since the sequences become shorter than the block sizes."
  • "In practice, we find that the block size 16 is large enough to efficiently utilize the GPU and small enough to avoid significant internal fragmentation in most workloads. Accordingly, vLLM sets its default block size as 16."
  • Swapping also depends on it (Fig. 19): small blocks mean "numerous small data transfers between CPU and GPU, which limits the effective PCIe bandwidth."

At B = 1 each block holds a single token, so the per-block costs (a table lookup, a branch, a separate small fetch) are paid for every token instead of once per 16.   • A2. Sequence lengths are mostly well above 16 tokens (implicit in "most workloads").
  • A3. One block size for all sequences and all layers (implicit).
If an assumption changes
  • A1 changes (a kernel that processes several small blocks per warp): the lower bound on B would fall and the internal-fragmentation side would win (inference).
  • A2 changes (very short requests, such as classification prompts): even B = 16 could waste a large share; Alpaca already shows the effect at 64.
  • A3 changes (variable block sizes): brings back external fragmentation and a promotion/demotion policy, the Superpages problem (inference).
Design notes and rejected alternatives

The paper picks 16 from Fig. 18b and leaves B fixed. It does not explore separate sizes for prefill and decode, per-layer sizes, or adapting B to the trace. The swap results (M14) add a reason not to go below 16.

Connections

Superpages: the same trade-off as page size: big units for translation reach and efficient transfers, small units to limit internal fragmentation; Superpages answers with several sizes and promotion, vLLM with one tuned size (inference). FFS: FFS answers the same tension with two sizes at once, blocks plus fragments for the tail of a file; the analogue for vLLM would be a small "fragment" block for each sequence's last tokens (inference, not in the paper).

M9 · Parallel sampling: shared prompt blocks, reference counts and copy-on-write

TL;DR
ProblemSeveral samples of one request have an identical prompt, but separate contiguous chunks store its KV cache once per sample.
MechanismMap every sample's prompt logical blocks to the same physical blocks, keep a reference count per physical block, and before a sample writes into a block whose count is above 1, give it a private copy of that block.
Trade-offThe prompt is stored and computed once, in exchange for one block copy per extra sample when the prompt ends mid-block, and reference-count bookkeeping.
Breaks whenPrompts are short relative to outputs, so there is little to share (Alpaca: 6.1 to 9.8% saved).
Key points
  • "In parallel sampling, one request includes multiple samples sharing the same input prompt, allowing the KV cache of the prompt to be shared as well." From here on the paper assumes "the more general case in which a request generates multiple sequences."
  • Fig. 8: "the logical block 0 and 1 of both sequences are mapped to physical blocks 7 and 1, respectively. Since a single physical block can be mapped to multiple logical blocks, we introduce a reference count for each physical block. In this case, the reference counts for physical blocks 7 and 1 are both 2."
  • "vLLM implements a copy-on-write mechanism at the block granularity for the physical blocks that need modification by multiple sequences, similar to the copy-on-write technique in OS virtual memory (e.g., when forking a process)."
  • "when sample A1 needs to write to its last logical block (logical block 1), vLLM recognizes that the reference count of the corresponding physical block (physical block 1) is greater than 1; it allocates a new physical block (physical block 3), instructs the block engine to copy the information from physical block 1, and decreases the reference count to 1. Next, when sample A2 writes to physical block 1, the reference count is already reduced to 1; thus A2 directly writes its newly generated KV cache to physical block 1."
  • "vLLM enables the sharing of most of the space used to store the prompts' KV cache across multiple output samples, with the exception of the final logical block, which is managed by a copy-on-write mechanism."
  • Measured (Fig. 15a, OPT-13B, Alpaca): 6.09%, 8.53%, 9.79% of blocks saved for 2, 4, 6 samples; on ShareGPT "16.2% - 30.5%". §3 also says the prompt "accounts for 12% of the total KV cache memory in our experiment (§6.3)", a number §6.3 does not contain.
How it works, step by step: n samples, one prompt
  1. Prefill once: compute the prompt's KV cache for one sequence, P tokens in ⌈P/B⌉ blocks.
  2. Fork n − 1 times (M12): each new sample gets a copy of the block table (a few integers), and every prompt block's count rises to n. No KV data moves.
  3. First decode step: each sample's new token goes into slot (P mod B) of its last logical block. If P is a multiple of B, that block is full, so each sample simply allocates a fresh block: no copies at all. Otherwise the last block is shared: the first n − 1 samples to write each get a copy (count drops by one each time) and the last writes in place. Total: n − 1 block copies, each of the (P mod B) filled slots.
  4. Afterwards: outputs differ, so every later block is private. The full prompt blocks stay shared until all samples finish (count reaches 0).
  5. Worked numbers: n = 4, P = 161 (ShareGPT's mean prompt), B = 16: 10 full blocks + 1 block with 1 token. Without sharing 4 × 11 = 44 prompt blocks; with sharing 10 + 4 = 14 (the shared partial block plus 3 copies). Saving on the prompt: 30 blocks, 375 MB on OPT-13B (this guide's arithmetic).
Assumptions it relies on
  • A1. The samples have byte-identical prompts, so identical prompt KV caches (stated).
  • A2. After the prompt, samples diverge; their generated KV "should remain unshared due to the different sample results and their dependence on context and position" (stated).
  • A3. The manager knows which sequences came from one request, because it created them by forking (stated, §5.2).
  • A4. Writes only ever go to a sequence's last block, so only that block can need a copy (implicit in "filled from left to right").
If an assumption changes
  • A1 changes (prompts nearly identical, differing in one early token): nothing after that token can be shared, because every later key depends on it (M1).
  • A2 changes (two samples happen to generate the same tokens): vLLM still keeps two private copies; it shares by provenance (fork), not by content, unlike ESX's content-based page sharing (inference).
  • A3 changes (unrelated requests with the same prompt): no fork relationship exists, so this mechanism does not share them; that needs the prefix mechanism (M11) or content matching (inference).
  • A4 changes (writes into older blocks): any shared block could need a copy, and copy volume would no longer be bounded by one block per sample (inference).
Design notes and rejected alternatives

The OS analogy is exact in effect but not in trigger: an OS discovers a write to a shared page through a protection fault, whereas vLLM knows before the step which block each sequence will write (its last one) and checks the reference count then (inference). Copies are issued to the block engine and batched into one kernel launch (M19). The paper does not discuss the alternative of copying the whole prompt per sample, which is what contiguous systems must do.

Connections

ESX: ESX shares identical pages across virtual machines by hashing contents and marks them copy-on-write; vLLM shares by construction and never scans contents, so it finds only sharing it created (inference). Hints: copy-on-write is "use lazy evaluation": defer the copy until a write proves it necessary, and here only n − 1 single-block copies ever happen (inference).

M10 · Beam search: sharing that changes every step

TL;DR
ProblemBeam candidates share long common histories that change every step as candidates are pruned and extended; contiguous systems copy whole caches between candidate slots.
MechanismCandidates' block tables point to shared physical blocks; pruning a candidate decrements counts and frees blocks that reach 0; extending one forks its table; copy-on-write handles a shared partly filled block.
Trade-offCopies shrink to at most one block per fork, in exchange for reference-count updates every iteration.
Breaks whenCandidates diverge early and never re-converge, leaving little shared history.
Key points
  • Beam search keeps "the top-k most probable sequences out of k · |V| candidates, where |V| is the vocabulary size."
  • "beam search facilities sharing not only the initial prompt blocks but also other blocks across different candidates, and the sharing patterns dynamically change as the decoding process advances, similar to the process tree in the OS created by compound forks."
  • Fig. 9, k = 4: "All beam candidates share the first block 0 (i.e., prompt). Candidate 3 digresses from others from the second block. Candidates 0-2 share the first 3 blocks and diverge at the fourth block. At subsequent iterations, the top-4 probable candidates all originate from candidates 1 and 2."
  • "vLLM frees all physical blocks whose reference counts reach 0 (blocks 2, 4, 5, 8). Then, vLLM allocates new physical blocks (blocks 9-12) to store the new KV cache from the new candidates. Now, all candidates share blocks 0, 1, 3; candidates 0 and 1 share block 6, and candidates 2 and 3 further share block 7."
  • "Previous LLM serving systems require frequent memory copies of the KV cache across the beam candidates. For example, in the case shown in Fig. 9, after the dotted line, candidate 3 would need to copy a large portion of candidate 2's KV cache to continue generation."
  • "The copy-on-write mechanism is applied only when the newly generated tokens are within an old shared block, as in parallel decoding. This involves only copying one block of data."
  • Measured (Fig. 15b, Alpaca): 37.56%, 53.13%, 55.16% saved for widths 2, 4, 6; ShareGPT "44.3% - 66.3%". Throughput gain over Orca (Oracle) "goes from 1.3× in basic sampling to 2.3× in beam search with a width of 6."
How it works, step by step: the iteration at the dotted line
  1. Score: each of the 4 candidates is extended by every vocabulary token; the top 4 of the 4 × |V| results are kept. All 4 survivors extend old candidates 1 and 2 (two children each).
  2. Free the losers: old candidates 0 and 3 are freed. Candidate 0 alone held block 5; candidate 3 alone held 2, 4, 8. Their counts drop to 0: blocks 2, 4, 5, 8 go back to the pool. Blocks 0, 1, 3 lose one or two references but stay in use.
  3. Fork the winners: new candidates 0 and 1 get copies of old candidate 1's table (0, 1, 3, 6); new 2 and 3 get old candidate 2's (0, 1, 3, 7). Counts: 0, 1, 3 → 4; 6, 7 → 2.
  4. Append: every candidate had 4 full blocks, so each new token needs a new block: 9, 10, 11, 12 are allocated. No copy-on-write is needed because no shared block is partly filled.
  5. Accounting: 9 physical blocks serve 20 logical blocks (55% saved at this instant); before the step, 9 served 16 (44%). A contiguous system would at this point copy two whole candidate caches (old 1 into old 0's slot, old 2 into old 3's slot), 8 blocks of data (this guide's arithmetic).
  6. When a copy does happen: if a candidate with two surviving children ends mid-block, the block is shared with count 2; the first child to write copies it, the second writes in place, exactly as in M9.
Assumptions it relies on
  • A1. Surviving candidates usually descend from a few earlier candidates, so histories overlap (stated through the process-tree analogy and the example).
  • A2. Freed candidates' blocks can be released at once (stated).
  • A3. Re-pointing a candidate is cheap: tables are small and live on the CPU (implicit).
  • A4. All candidates of one request are scheduled and preempted together (stated in §4.5: "gang-scheduled as a sequence group").
If an assumption changes
  • A1 changes (diverse beams that are pushed apart, general knowledge): the shared part shrinks toward the prompt, and the saving approaches parallel sampling's.
  • A2 changes (freed blocks kept for possible reuse): memory would hold dead candidates; nothing in beam search revives a pruned candidate, so there is no reason to (inference).
  • A3 changes (tables on the GPU, updated by kernels): every fork would be a device operation; the paper keeps them in the scheduler and ships them each step (M16).
  • A4 changes (one candidate preempted alone): its blocks are shared with the others, so evicting "its" blocks would either evict blocks still in use or free nothing; hence group-level eviction (M13).
Design notes and rejected alternatives

The paper frames the advantage against copying in existing systems, not against a different sharing scheme. Block-level sharing means the tree can only share at block boundaries: two candidates that diverge in the middle of a block share the earlier full blocks and the copy of the divergent block, never part of a block.

Connections

OS fork: the paper's own analogy, "the process tree in the OS created by compound forks". LFS: blocks that lose their last reference are freed immediately here, whereas LFS lets dead blocks accumulate in segments until a cleaner copies live data out; uniform-size blocks with exact counts need no cleaner (inference).

M11 · Shared prefixes: a system prompt cached once

TL;DR
ProblemMany requests start with the same long instructions and examples, whose KV cache is computed and stored once per request.
MechanismThe provider reserves physical blocks holding the KV cache of predefined prefixes; a request with that prefix maps its first logical blocks to them, with the last block marked copy-on-write, and runs prefill only on its own input.
Trade-offPrefix compute and memory are paid once, in exchange for memory held permanently by the prefix and the need to know prefixes in advance.
Breaks whenPrefixes are not known ahead of time, or differ in any token.
Key points
  • "Commonly, the LLM user provides a (long) description of the task including instructions and example inputs and outputs, also known as system prompt [36]. The description is concatenated with the actual task input to form the prompt of the request."
  • "the LLM service provider can store the KV cache of the prefix in advance to reduce the redundant computation spent on the prefix. In vLLM, this can be conveniently achieved by reserving a set of physical blocks for a set of predefined shared prefixes by the LLM service provider, as how OS handles shared library across processes."
  • "A user input prompt with the shared prefix can simply map its logical blocks to the cached physical blocks (with the last block marked copy-on-write). The prompt phase computation only needs to execute on the user's task input."
  • Fig. 10: an English-to-French few-shot prompt ("sea otter", "peppermint", "plush girafe") shared by sequence A ("cheese" → "fromage") and sequence B ("I love you" → the figure prints "Je t'amie").
  • Evaluation (§6.4, LLaMA-13B, WMT16 English-to-German): one-shot prefix "1 example with 80 tokens", five-shot "5 examples with 341 tokens"; vLLM "achieves 1.67× higher throughput than Orca (Oracle)" and "3.58× higher throughput" respectively.
How it works, step by step: a 5-shot request
  1. Setup (once): the provider runs prefill on the 341-token prefix and keeps its 22 blocks reserved: 21 full, the last holding 5 tokens.
  2. Request arrives with prefix + "cheese =>" (say 6 own tokens, illustrative). Its table starts with the 22 prefix block IDs; counts rise by one.
  3. Prefill on own tokens only: the first own token must go into slot 6 of the shared last block, so the request first gets a copy of that block (5 filled slots), then the 6 own tokens fill slots 6 to 11 of the copy. The attention for these tokens reads the 21 shared blocks plus the copy.
  4. Saved per request: prefill over 341 tokens of compute, and 21 blocks (21 × 12.5 MB = 262 MB on a 13B model) of memory. Cost: one 16-slot block copy (this guide's arithmetic).
  5. One-shot case: 80 tokens fill exactly 5 blocks, so there is no partly filled block and no copy at all; the own tokens start a fresh block.
Assumptions it relies on
  • A1. Prefixes are predefined by the provider (stated).
  • A2. The shared part is a token-for-token identical prefix (implicit, from M1: keys depend on everything before them).
  • A3. Prefix blocks stay resident (implicit in "reserving").
  • A4. Requests never write into a full prefix block (stated through the copy-on-write marking of only the last one).
If an assumption changes
  • A1 changes (discover common prefixes automatically): the manager must recognize, at admission, that a request's first blocks equal blocks already cached, for example by hashing each block together with everything before it (later vLLM versions do this, general knowledge); sharing becomes content-based, like ESX, but keyed by the whole prefix (inference).
  • A2 changes (prefix varies in one early token, such as a date or user name): nothing after that token can be shared; putting variable fields at the end of the prompt preserves sharing (inference).
  • A3 changes (prefix blocks evicted under pressure): the next request must redo the 341-token prefill; the paper does not say whether reserved prefix blocks can be preempted (inference).
  • A4 changes: cannot happen under left-to-right filling (inference).
Design notes and rejected alternatives

The paper presents this as a capability ("can be conveniently achieved") and measures it with two fixed prefixes; it does not describe a policy for which prefixes to cache or how many blocks to set aside. §5.2 says prefix sharing is implemented with the same fork, append and free methods.

Connections

OS shared libraries: the paper's analogy: read-only pages mapped into many address spaces, with copy-on-write for the writable part. ESX: content-based page sharing discovers identical pages after the fact; vLLM's prefix sharing is declared in advance, so it needs no scanning but finds nothing it was not told about (inference).

M12 · Fork, append and free, and batching mixed decoding methods

TL;DR
ProblemEach decoding algorithm has its own sharing pattern; a server that special-cases each cannot batch requests that use different ones.
MechanismThree operations on sequences (fork, append, free) build every algorithm; the block tables hide all sharing, so the kernel only sees, per sequence, a list of physical block IDs.
Trade-offOne mechanism for all decoding modes and freely mixed batches, in exchange for limiting what an algorithm can do to the cache to these three operations.
Breaks whenAn algorithm needs to edit or remove tokens other than at the end of a sequence.
Key points
  • "vLLM implements various decoding algorithms using three key methods: fork, append, and free. The fork method creates a new sequence from an existing one. The append method appends a new token to the sequence. Finally, the free method deletes the sequence."
  • "in parallel sampling, vLLM creates multiple output sequences from the single input sequence using the fork method. It then adds new tokens to these sequences in every iteration with append, and deletes sequences that meet a stopping condition using free. The same strategy is also applied in beam search and prefix sharing by vLLM. We believe future decoding algorithms can also be supported by combining these methods."
  • "vLLM conceals the complex memory sharing between different sequences via a common mapping layer that translates logical blocks to physical blocks. The LLM and its execution kernel only see a list of physical block IDs for each sequence and do not need to handle sharing patterns across sequences."
  • "Compared to existing systems, this approach broadens the batching opportunities for requests with different sampling requirements, ultimately increasing the system's overall throughput." The paper gives no separate measurement of mixed batches.
How it works, step by step: what each operation does to blocks
  1. fork(s) → s′: copy s's block table to s′ and add 1 to the count of every block in it. No KV data is copied (this guide's reading of how fork must work given M9).
  2. append(s, token): if the last block is full, allocate a block; else if the last block's count is above 1, copy it to a new block (copy-on-write) and decrement the old count; then the step writes the token's keys and values into the next slot and increments filled.
  3. free(s): decrement every block in s's table; return blocks that reach 0 to the free pool; drop the table.
  4. Beam search, one step: for each surviving new candidate, fork its parent, append its token; free the old candidates that have no children. Fig. 9's step is 4 forks, 4 appends (new blocks 9 to 12) and 4 frees, which releases blocks 2, 4, 5, 8 (this guide's decomposition).
  5. A mixed batch: a greedy request (one table), a 4-sample request (four tables sharing prompt blocks) and a beam request (four tables sharing a tree) all hand the kernel "a list of physical block IDs" per sequence. Some IDs appear in several lists; the kernel reads them the same way.
Assumptions it relies on
  • A1. Every decoding algorithm can be written with fork, append and free (stated as a belief, not shown).
  • A2. Reading a shared block is no different from reading a private one (implicit; blocks are read-only once full).
  • A3. A sequence's sharing never matters to the kernel (stated).
If an assumption changes
  • A1 changes (an algorithm that rolls back tokens, such as speculative decoding, or edits the middle): needs a truncate operation (decrement filled, free trailing blocks), which fits the table easily; editing the middle invalidates every later key and cannot be expressed as block sharing (inference).
  • A2 changes (concurrent writes into a shared block in one step): two sequences writing different tokens into the same slot would corrupt each other; copy-on-write before the step is what prevents this (inference).
  • A3 changes (a kernel that exploits sharing, for example computing a shared prefix's attention once for many queries): would need sharing information in the kernel, breaking this layering for speed (later work does this, general knowledge).
Design notes and rejected alternatives

The interface is the separation of policy from mechanism: the decoding algorithm (policy) decides which sequences exist; the block manager (mechanism) keeps their memory consistent. The paper argues existing systems "cannot efficiently" batch different decoding preferences, without measuring it.

Connections

Unix: fork, exit and copy-on-write pages, the paper's own analogy. Exokernel: a small set of mechanism-level operations on which applications build their own policies (inference). Hints: "keep interfaces simple", and an interface that does one thing, here three (inference).

M13 · FCFS scheduling and all-or-nothing preemption of sequence groups

TL;DR
ProblemBecause nothing is reserved, running sequences can grow until no free block is left for the next token.
MechanismServe requests first-come-first-serve; when blocks run out, preempt the most recently arrived sequence group and evict all of its blocks at once; admit no new requests until every preempted group has finished.
Trade-offOldest requests always make progress and no group runs with part of its cache, in exchange for wasted work on the preempted group (a swap or a recomputation) and a pause in admissions.
Breaks whenPreemptions become frequent (memory oversubscribed by long outputs), so groups are evicted and restored repeatedly.
Key points
  • "In vLLM, we adopt the first-come-first-serve (FCFS) scheduling policy for all requests, ensuring fairness and preventing starvation. When vLLM needs to preempt requests, it ensures that the earliest arrived requests are served first and the latest requests are preempted first."
  • "As the number of requests and their outputs grow, vLLM can run out of the GPU's physical blocks to store the newly generated KV cache. There are two classic questions that vLLM needs to answer in this context: (1) Which blocks should it evict? (2) How to recover evicted blocks if needed again?"
  • "Typically, eviction policies use heuristics to predict which block will be accessed furthest in the future and evict that block. Since in our case we know that all blocks of a sequence are accessed together, we implement an all-or-nothing eviction policy, i.e., either evict all or none of the blocks of a sequence."
  • "multiple sequences within one request (e.g., beam candidates in one beam search request) are gang-scheduled as a sequence group. The sequences within one sequence group are always preempted or rescheduled together due to potential memory sharing across those sequences."
  • "Once it preempts a sequence and evicts its blocks, vLLM stops accepting new requests until all preempted sequences are completed." (Stated in the swapping paragraph; the paper does not say whether the same rule applies with recomputation.)
  • Discussion: this is one of the "LLM-specific optimizations", an "all-or-nothing swap-out policy, which exploits the fact that processing a request requires all of its corresponding token states to be stored in GPU memory."
How it works, step by step: the trace above
  1. t1, t2: three groups run; S1 grows into the last free block. The pool is full.
  2. t3: S2's last block filled at t2, so it needs one new block. None is free. The latest arrival is S3, so S3 is preempted: all 3 of its blocks leave the GPU together (all-or-nothing). Evicting only one of S3's blocks would free enough memory for S2, but S3 could then not run at all, since every step reads its whole cache.
  3. t3 to t5: S1 and S2 continue. New request R4 arrives but is not admitted while S3 is preempted, so admissions cannot keep pushing S3 back.
  4. t6: S2 finished; its 6 blocks are free; S3 comes back (swap in, or recompute) and continues where it stopped.
  5. t7: nothing is preempted any more, so R4 is admitted.
  6. Victim choice is by arrival, not size: the latest group is chosen even if it frees less than needed; then the next latest goes too (inference: the rule as stated implies repeated preemption until the oldest groups fit).
Assumptions it relies on
  • A1. Every step reads all blocks of every running sequence, so partial residency is useless (stated).
  • A2. Sequences of a request may share blocks, so they must move together (stated).
  • A3. Arrival order is the right priority: fair and starvation-free (stated).
  • A4. Preemption is occasional, not the steady state (implicit).
If an assumption changes
  • A1 changes (attention that reads only some blocks, for example sparse or windowed attention): a per-block policy like LRU would become meaningful, and partial eviction could keep a sequence running (inference).
  • A2 changes (sequences of a request did not share): they could be preempted one at a time, a finer-grained choice (inference).
  • A3 changes (requests have priorities or deadlines): FCFS ignores them; shortest-first is not available because output lengths are unknown (inference).
  • A4 changes (memory strongly oversubscribed): groups are evicted and restored repeatedly, the GPU analogue of thrashing; the admission freeze limits it by not adding new load until preempted groups finish (inference).
Design notes and rejected alternatives

The paper explicitly sets aside the classic per-page heuristic ("predict which block will be accessed furthest in the future") because all blocks of a sequence have the same next-use time: now. It does not discuss reserving headroom to avoid preemption, or preempting the longest or largest group.

Connections

Livelock: stopping new admissions until preempted work completes is the Livelock paper's principle of not accepting new input that the system cannot finish, so that admitted work completes (inference). ESX: ESX reclaims memory from running virtual machines (ballooning, swapping) under overcommitment; vLLM reclaims from whole sequence groups, chosen by arrival rather than by ESX's shares and idle-memory tax (inference).

M14 · Recovery by swapping to CPU memory

TL;DR
ProblemA preempted group's KV cache must be kept somewhere if it is not to be recomputed.
MechanismCopy its blocks over PCIe into a CPU-memory block pool managed by a CPU block allocator; copy them back into free GPU blocks when it is rescheduled, updating the tables.
Trade-offNo recomputation, in exchange for PCIe traffic both ways and CPU memory.
Breaks whenBlocks are small, so the transfer is many small copies: at block size 1, swap out plus in takes about 137 ms versus about 34 ms at 64 and above (Fig. 19a, read-off).
Key points
  • "This is the classic technique used by most virtual memory implementations which copy the evicted pages to a swap space on the disk. In our case, we copy evicted blocks to the CPU memory. As shown in Fig. 4, besides the GPU block allocator, vLLM includes a CPU block allocator to manage the physical blocks swapped to CPU RAM."
  • "When vLLM exhausts free physical blocks for new tokens, it selects a set of sequences to evict and transfer their KV cache to the CPU. Once it preempts a sequence and evicts its blocks, vLLM stops accepting new requests until all preempted sequences are completed. Once a request completes, its blocks are freed from memory, and the blocks of a preempted sequence are brought back in to continue the processing of that sequence."
  • "Note that with this design, the number of blocks swapped to the CPU RAM never exceeds the number of total physical blocks in the GPU RAM, so the swap space on the CPU RAM is bounded by the GPU memory allocated for the KV cache." (See Class Prep C1: under the stated rules this bound can be exceeded.)
  • §7.3: "swapping incurs excessive overhead with small block sizes. This is because small block sizes often result in numerous small data transfers between CPU and GPU, which limits the effective PCIe bandwidth."
  • Fig. 19a (read-off, ms): swap in ≈ 82 / 54 / 35 / 26 / 22 / 19.5 / 18.5 / 17.5 / 17.5 and swap out ≈ 55 / 36 / 26 / 21 / 18.5 / 17.5 / 17 / 16.5 / 16.5 for block sizes 1 to 256; the paper does not state how much KV cache each measurement moves.
How it works, step by step: swapping one 512-token OPT-13B sequence
  1. Data: 512 × 800 KB = 400 MB, in 32 blocks of 16 tokens.
  2. Copies: each block exists separately in each layer's key and value storage (footnote 1), so one block is 2 × 40 = 80 copies of 160 KB, and the sequence is 2,560 copies. At block size 1 it would be 40,960 copies of 10 KB (this guide's arithmetic, assuming one copy per block per layer per K or V).
  3. Time: at a practical 20 to 25 GB/s over PCIe 4.0 (general knowledge), 400 MB takes about 16 to 20 ms each way if transfers are large. Each copy call also has a fixed cost of a few microseconds (general knowledge, illustrative 5 µs), negligible for 2,560 copies but about 200 ms for 40,960.
  4. Out: allocate 32 CPU blocks, copy, free the 32 GPU blocks, point the table entries at CPU block numbers.
  5. In: when blocks free up, allocate 32 GPU blocks (any numbers), copy back, rewrite the table, free the CPU blocks. The sequence resumes with its next token.
Assumptions it relies on
  • A1. CPU memory can hold everything swapped out, bounded by the GPU's KV memory (stated).
  • A2. PCIe bandwidth is high enough when transfers are large (stated dependency: "depend on the bandwidth between CPU RAM and GPU memory").
  • A3. A swapped-in block may land at a different physical number; only the table changes (implicit).
  • A4. No new requests are admitted while anything is swapped out (stated).
If an assumption changes
  • A1 changes (the bound fails): if running sequences grow after one preemption and force another, the swapped total can exceed the GPU pool (Class Prep C1); the released vLLM uses a fixed-size CPU swap space and aborts when it is exhausted (general knowledge).
  • A2 changes (a faster CPU-GPU link, such as the coherent links on newer CPU-GPU packages, general knowledge): swap gets cheaper relative to recompute, shifting Fig. 19's crossover to smaller blocks (inference).
  • A3 changes (blocks pinned to physical locations): a swapped-in sequence would wait for its exact blocks; the indirection is what lets it take any free ones (inference).
  • A4 changes (keep admitting): new arrivals could take every freed block, and a swapped-out group could wait indefinitely (inference).
Design notes and rejected alternatives

Disk is not used; CPU RAM is the swap device. The paper keeps both swap and recompute because their costs depend on different resources and on block size (§7.3).

Connections

Salus: Salus's Observation 1 is that "Transferring GPU memory back and forth is not practical to achieve low latency given current GPU communication bandwidth", so Salus keeps every job's persistent memory resident; vLLM accepts PCIe swaps but only as a rare recovery path (inference). ESX: hypervisor-level swapping as the last resort after ballooning and sharing; here swap is likewise a fallback after on-demand allocation and sharing (inference).

M15 · Recovery by recomputation

TL;DR
ProblemSwapping costs PCIe transfers and CPU memory, and is slow with small blocks.
MechanismDiscard the preempted sequence's KV cache; when it is rescheduled, run one prefill pass over its prompt plus every token it had already generated.
Trade-offNo transfers and no swap space, in exchange for GPU compute; the cost does not depend on block size.
Breaks whenThe GPU is compute-bound, or the group's sequences share blocks that separate re-prefills would duplicate.
Key points
  • "In this case, we simply recompute the KV cache when the preempted sequences are rescheduled. Note that recomputation latency can be significantly lower than the original latency, as the tokens generated at decoding can be concatenated with the original user prompt as a new prompt", and "their KV cache at all positions can be generated in one prompt phase iteration."
  • "The performances of swapping and recomputation depend on the bandwidth between CPU RAM and GPU memory and the computation power of the GPU."
  • Discussion: recomputation "to recover the evicted blocks, which is not feasible in OS."
  • §7.3: "the overhead of recomputation remains constant across different block sizes, as recomputation does not utilize the KV blocks. Thus, recomputation is more efficient when the block size is small, while swapping is more efficient when the block size is large, though recomputation overhead is never higher than 20% of swapping's latency. For medium block sizes from 16 to 64, the two methods exhibit comparable end-to-end performance."
  • Fig. 19a: recompute ≈ 36 to 39 ms at every block size (read-off). Fig. 19b (OPT-13B, ShareGPT, one fixed rate): recompute and swap are nearly equal from 8 to 128, but at 256 recompute is ≈ 1.12 s/token versus swap ≈ 0.67 (read-off), a gap the text does not discuss.
How it works, step by step: one preempted sequence
  1. Preempt: free all its blocks immediately; keep only its token IDs (prompt plus generated so far) and sampling state.
  2. Example: 120-token prompt, 80 tokens generated (illustrative). Originally that took one prefill plus 80 decode steps.
  3. Reschedule: treat the 200 tokens as a new prompt. One prefill pass computes all 200 positions' keys and values in every layer, using matrix-matrix multiplication (M1), then decoding resumes at token 201.
  4. Why cheaper than the original: 80 sequential memory-bound decode steps (each reading all weights) become one compute-efficient pass. Rough scale for OPT-13B: 2 × 13 × 109 × 200 ≈ 5 × 1012 operations, tens of milliseconds on an A100, versus 80 decode steps of about 20 ms each (general-knowledge hardware numbers, this guide's arithmetic).
  5. Same result: the recomputed keys and values are a function of the same tokens and weights, so the sequence continues as if never interrupted; previously sampled tokens are kept, not resampled (inference).
  6. Groups: for a beam or parallel-sampling group, separate re-prefills would recompute shared prefixes once per sequence and lose the sharing unless the group is re-forked; the released vLLM recomputes only single-sequence groups and swaps multi-sequence groups (general knowledge, not in the paper).
Assumptions it relies on
  • A1. The KV cache is a deterministic function of the token sequence and the weights (implicit).
  • A2. The GPU has compute to spare for an extra prefill (implicit; the workload is memory-bound).
  • A3. The tokens themselves are kept (implicit).
  • A4. Its cost does not depend on block size (stated).
If an assumption changes
  • A1 changes (weights change between preemption and resume, for example a different adapter): recomputed keys would differ from the originals; the sequence would continue under a different model (inference).
  • A2 changes (compute-bound): the extra prefill directly delays everyone else; swapping uses the otherwise idle PCIe link instead (inference).
  • A3 changes: without the tokens there is nothing to recompute from; an OS page has no such compact "recipe", which is why the paper says recomputation is "not feasible in OS".
  • A4 changes (very long sequences): recompute cost grows with the sequence (prefill attention grows faster than linearly in length, general knowledge), so for long contexts swap may win at any block size (inference).
Design notes and rejected alternatives

The sentence "recomputation overhead is never higher than 20% of swapping's latency" cannot be read literally: at block size 1, recompute (≈36 ms) is about 27% of swap (≈137 ms), and at 256 it is about 16% higher than swap (≈39 versus ≈33.5 ms). The data support "never more than about 20% higher than swapping", which is probably what is meant (this guide's reading of Fig. 19a).

Connections

OS paging: a clean page backed by a file can be dropped and re-read rather than written to swap; recomputation is the analogue, with "re-read" replaced by "re-derive from the tokens" (inference). LFS: roll-forward recovery rebuilds state by replaying a log; recomputation rebuilds the cache by replaying the token log through the model (inference).

M16 · Distributed execution: one scheduler, one set of block tables, many GPUs

TL;DR
ProblemOPT-66B and 175B do not fit on one GPU, so the model is split across GPUs, and each GPU holds part of every token's KV cache.
MechanismMegatron-LM tensor parallelism, split by attention head; a single KV cache manager in the central scheduler; every GPU uses the same physical block IDs for its own heads; each step the scheduler broadcasts token IDs and block tables, workers compute and all-reduce on their own, and return sampled tokens.
Trade-offWorkers never coordinate on memory, in exchange for a central scheduler on every step's critical path.
Breaks whenShards need different positions (not true for tensor parallelism), or the scheduler cannot keep up with step rate.
Key points
  • "vLLM is effective in distributed settings by supporting the widely used Megatron-LM style tensor model parallelism strategy on Transformers [47]. This strategy adheres to an SPMD (Single Program Multiple Data) execution schedule, wherein the linear layers are partitioned to perform block-wise matrix multiplication, and the the GPUs constantly synchronize intermediate results via an all-reduce operation. Specifically, the attention operator is split on the attention head dimension".
  • "We observe that even with model parallel execution, each model shard still processes the same set of input tokens, thus requiring the KV Cache for the same positions. Therefore, vLLM features a single KV cache manager within the centralized scheduler".
  • "Although each GPU worker has the same physical block IDs, a worker only stores a portion of the KV cache for its corresponding attention heads."
  • "In each step, the scheduler first prepares the message with input token IDs for each request in the batch, as well as the block table for each request. Next, the scheduler broadcasts this control message to the GPU workers." Workers read KV "according to the block table in the control message", synchronize "with the all-reduce communication primitive without the coordination of the scheduler", and "send the sampled tokens of this iteration back to the scheduler."
  • "GPU workers do not need to synchronize on memory management as they only need to receive all the memory management information at the beginning of each decoding iteration along with the step inputs." NCCL is used for tensor communication.
How it works, step by step: one step of OPT-66B on 4 GPUs
  1. Sizes per GPU: a token's KV cache is 2.25 MB in total and 576 KB per GPU (18 of 72 heads × 128 numbers × 2 bytes × 2 × 64 layers). Each GPU's pool is a quarter of Table 1's 21 GB, 5.25 GB, or about 597 blocks of 16 tokens (9 MB per block per GPU), and block 7 on GPU 2 holds heads 36 to 53 of the same 16 tokens that block 7 holds on GPU 0 (this guide's arithmetic).
  2. Scheduler: picks the batch, allocates blocks, and builds one message: token IDs plus each sequence's block table. For 30 sequences of about 500 tokens that is roughly 30 × 32 table entries, a few kilobytes (illustrative).
  3. Broadcast to all 4 workers. Each runs every layer for its 18 heads: reads blocks through the table, writes the new token's keys and values for its heads into the same slot numbers.
  4. All-reduce after the attention and feed-forward partial products, worker to worker (NCCL), with no scheduler involvement.
  5. Return sampled token IDs to the scheduler, which updates tables, frees and allocates for the next step.
Assumptions it relies on
  • A1. Every shard processes the same tokens at the same time, so needs the same positions (stated).
  • A2. Tensor parallelism split by head (stated: Megatron-LM style).
  • A3. All workers have identical pools, so one ID means the same slot everywhere (implicit).
  • A4. The scheduler and broadcast are fast relative to a step (implicit).
If an assumption changes
  • A1, A2 change (pipeline parallelism, general knowledge: GPUs hold different layers and work on different micro-batches at once): positions per sequence are still the same at every stage, so one table still describes the cache, but tables must be versioned per micro-batch because stages are at different steps (inference).
  • A3 changes (GPUs with different memory sizes): the common ID space is limited by the smallest pool (inference).
  • A4 changes (very short steps or very many GPUs): the Python scheduler and broadcast become a larger share of each step; the paper does not measure their cost (inference).
Design notes and rejected alternatives

The single manager follows from A1: per-GPU managers would make identical decisions and need to agree. The paper does not consider replicating the manager for fault tolerance.

Connections

NFS: a central authority hands out the metadata (here, block tables) and the workers act on data they hold, with all state needed for the step carried in the message, like NFS requests carrying their file handles and offsets (inference). Salus: Salus shares one GPU among many jobs; vLLM spreads one model over many GPUs and keeps memory decisions in one place (inference).

M17 · Kernel 1: fused reshape and block write

TL;DR
ProblemEach layer produces new keys and values as one dense tensor; storing them into scattered blocks in a read-friendly layout would take several small kernels per layer.
MechanismOne kernel per layer splits the new keys and values by block, reshapes them into the block-read layout, and writes each token's vectors to the slot the block table names.
Trade-offOne launch and one pass over the data instead of several, in exchange for a custom kernel tied to the cache layout.
Breaks whenLaunch overhead no longer matters (very large batches), so the fusion buys little.
Key points
  • "Since PagedAttention introduces memory access patterns that are not efficiently supported by existing systems, we develop several GPU kernels for optimizing it."
  • "(1) Fused reshape and block write. In every Transformer layer, the new KV cache are split into blocks, reshaped to a memory layout optimized for block read, then saved at positions specified by the block table. To minimize kernel launch overheads, we fuse them into a single kernel."
  • The layout itself is not specified beyond "optimized for block read".
How it works, step by step: one layer, one iteration
  1. Input: the layer's key and value projections for every token in this iteration's input: 1 row per decoding sequence plus all prompt rows of new requests (M2), each row 5120 numbers for OPT-13B.
  2. Slot lookup: for token at position p of sequence s, the destination is physical block tables[⌊p/16⌋], slot p mod 16 (the scheduler can precompute this slot number per token, inference).
  3. Write: each thread group copies its token's vectors into the block, arranged per head in the layout the read kernel expects.
  4. Without fusion: a split, a reshape (transpose) and a scatter would each be a kernel launch with an intermediate tensor written to and read from HBM; with 40 layers, that is 80 or more extra launches per step (illustrative count).
Assumptions it relies on
  • A1. Destination slots are known before the kernel runs (stated: positions "specified by the block table").
  • A2. Kernel launch overhead is significant relative to per-layer work in decode (stated as the reason).
  • A3. No two tokens in one step write the same slot (implicit; copy-on-write runs first, M9).
If an assumption changes
  • A1 changes (allocation decided on the GPU): the kernel would need an allocator of its own, with atomic operations on a free list (inference).
  • A2 changes (launch overhead hidden, for example by capturing a step as a CUDA graph, general knowledge): fusion matters less for launches but still saves the intermediate HBM traffic (inference).
  • A3 changes: two sequences writing different tokens into one shared slot would corrupt the cache for both (inference).
Design notes and rejected alternatives

The paper reports no separate measurement of this kernel. It is part of what Fig. 18a's attention microbenchmark and the end-to-end results include.

Connections

Hints: batching to amortize a fixed per-operation cost (inference). LFS: LFS gathers many small writes into one large segment write to amortize per-I/O cost; here many small scattered writes are gathered into one kernel launch (inference).

M18 · Kernel 2: fused block read and attention

TL;DR
ProblemAttention must now follow a block table, handle sequences of different lengths in one batch, and still read memory efficiently.
MechanismAdapt FasterTransformer's attention kernel to read keys and values block by block from the table and compute attention on the fly; assign one warp per block so its reads are coalesced; support variable sequence lengths in a batch.
Trade-offPaging works at all, in exchange for 20 to 26% higher attention kernel latency than FasterTransformer's contiguous kernel.
Breaks whenAttention dominates the step (long contexts), so its slowdown becomes a large share of total time.
Key points
  • "(2) Fusing block read and attention. We adapt the attention kernel in FasterTransformer [31] to read KV cache according to the block table and perform attention operations on the fly. To ensure coalesced memory access, we assign a GPU warp to read each block. Moreover, we add support for variable sequence lengths within a request batch."
  • §7.1: "our GPU kernels (§5) involve extra overheads of accessing the block table, executing extra branches, and handling variable sequence lengths. As shown in Fig. 18a, this leads to 20–26% higher attention kernel latency, compared to the highly-optimized FasterTransformer implementation. We believe the overhead is small as it only affects the attention operator but not the other operators in the model, such as Linear."
  • Fig. 18a (read-off, µs; vLLM vs FT): batch 32 at context 64 / 128 / 256 ≈ 77 vs 61, 127 vs 107, 235 vs 195 (about 19 to 26% higher); batch 8 ≈ 31 vs 22, 43 vs 35, 84 vs 62, which reads as about 23 to 40% higher, above the stated range, though at these small values a few microseconds of reading error matter.
  • Discussion: vLLM "mitigates the overhead of memory indirection in paging by fusing the GPU kernels for memory access operations with those for other operations such as attention."
How it works, step by step: one head, one sequence
  1. Inputs: the query, the sequence's block table and its length (41).
  2. Assign: ⌈41/16⌉ = 3 blocks, one warp each. Warp j reads table[j] to find its physical block; this extra load and the branch for the last, partial block are the "extra overheads" of §7.1.
  3. Read: the warp's 32 threads fetch adjacent addresses of the block's keys, so the hardware merges them into wide transactions. A block of 16 tokens is one contiguous run per head in the block layout (M17), which is what makes this possible.
  4. Score and combine: each warp computes its block's scores; the warps then combine maxima and sums to form one softmax across all 41 positions, weight their values, and add.
  5. Batch: every sequence in the batch has its own length and table; the kernel handles them in one launch ("variable sequence lengths within a request batch") instead of padding them to equal length.
Assumptions it relies on
  • A1. Attention is a minority of step time, so its slowdown matters little end to end (stated).
  • A2. A block is large enough for a warp to read efficiently (stated through the block-size discussion).
  • A3. The kernel can be derived from an existing optimized kernel (stated: adapted from FasterTransformer).
If an assumption changes
  • A1 changes (long contexts, small models): attention's share of step time grows with context length while the linear layers do not, so a 20 to 26% attention penalty approaches a 20 to 26% step penalty (inference; Fig. 18a stops at 256 tokens).
  • A2 changes (B = 1 to 4): each warp does little work per table lookup; Fig. 18b's poor results at small block sizes are consistent with this.
  • A3 changes (starting from a faster kernel, such as FlashAttention-style tiling, general knowledge): the paged version of a faster kernel could close the gap; later work did this (general knowledge).
Design notes and rejected alternatives

The paper accepts a slower kernel because the larger batch it enables dominates: "Despite the overhead, PagedAttention makes vLLM significantly outperform FasterTransformer in end-to-end performance". It does not try to remove the overhead, for example by prefetching table entries.

Connections

x86 VMM (hwsw): the VMware paper found that software techniques could beat early hardware virtualization because the hardware made each trap expensive; here software translation costs 20 to 26% of one operator but enables a 2 to 4× system gain, a similar "measure the whole system" lesson (inference). Superpages: translation overhead per access falls as the unit grows, the TLB-reach argument applied to a block table (inference).

M19 · Kernel 3: fused block copy for copy-on-write

TL;DR
ProblemCopy-on-write produces several block copies per step, each to and from discontinuous places, and one cudaMemcpyAsync per piece is many small transfers.
MechanismA kernel takes the list of (source, destination) block pairs for the step and performs all the copies in a single launch.
Trade-offOne launch instead of many small API calls, in exchange for another custom kernel.
Breaks whenCopies are rare (basic sampling), so there is nothing to batch.
Key points
  • "(3) Fused block copy. Block copy operations, issued by the copy-on-write mechanism, may operate on discontinuous blocks. This can lead to numerous invocations of small data movements if we use the cudaMemcpyAsync API. To mitigate the overhead, we implement a kernel that batches the copy operations for different blocks into a single kernel launch."
  • The paper gives no measurement of this kernel by itself.
How it works, step by step: a beam step with four copies
  1. Copies needed: suppose two beam parents each end mid-block and each has two surviving children: copy-on-write gives 2 block copies (the second child of each writes in place, M10). With parallel sampling of 6 samples on a mid-block prompt, 5 copies (illustrative).
  2. Pieces per copy: a block exists separately in every layer's key and value storage (footnote 1), so one block copy on OPT-13B is 2 × 40 = 80 pieces of 160 KB (this guide's arithmetic).
  3. With cudaMemcpyAsync: 5 copies × 80 = 400 calls per step, each with fixed API and launch cost.
  4. Fused: one launch receives the 5 (source, destination) pairs; its threads copy all layers' pieces in parallel (the single launch across layers is how the released code does it, general knowledge).
Assumptions it relies on
  • A1. All copies for a step are known before the step runs (implicit; copy-on-write is resolved by the scheduler first).
  • A2. Copies are GPU to GPU (stated by context: CoW within GPU memory; swaps are separate).
If an assumption changes
  • A1 changes (copies discovered during the kernel): the copy would need to be on the critical path inside the attention kernel (inference).
  • A2 changes (CPU to GPU, as in swapping): a GPU kernel cannot pull from pageable CPU memory efficiently; swaps use transfer calls, which is why Fig. 19a's swap cost depends so strongly on block size (inference).
Design notes and rejected alternatives

Rejected: the plain cudaMemcpyAsync path, for its per-call overhead.

Connections

ESX: copy-on-write breaking in ESX copies one 4 KB page per fault; here the scheduler collects every break for the step and does them together (inference). Livelock: batching work to cut per-item overhead under load (inference).

M20 · The evaluation setup: traces, baselines and the metric

TL;DR
ProblemTo show a throughput gain from memory management alone, the baselines must differ only in how they manage memory.
MechanismSynthesized request streams from real length distributions (ShareGPT, Alpaca) with Poisson arrivals; FasterTransformer with a simple batching scheduler; Orca re-implemented three ways (Oracle, Pow2, Max); metric is normalized latency versus request rate.
Trade-offControlled comparisons, in exchange for depending on the authors' re-implementation of Orca and on synthetic arrival times.
Breaks whenReal arrivals are burstier than Poisson, or the original Orca manages memory differently from the assumed buddy allocator.
Key points
  • Models and hardware: OPT 13B, 66B, 175B and LLaMA 13B on "A2 instances with NVIDIA A100 GPUs on Google Cloud Platform" (Table 1: 1 × A100-40GB, 4 × A100-40GB, 8 × A100-80GB).
  • Workloads: ShareGPT ("user-shared conversations with ChatGPT") and Alpaca (instructions "generated by GPT-3.5 with self-instruct"). "the ShareGPT dataset has 8.4× longer input prompts and 5.8× longer outputs on average than the Alpaca dataset, with higher variance." "we generate request arrival times using Poisson distribution with different request rates."
  • Metric: "normalized latency of the systems, the mean of every request's end-to-end latency divided by its output length, as in Orca [60]. A high-throughput serving system should retain low normalized latency against high request rates." Traces are 1 hour, except "15-minute traces for the OPT-175B model due to the cost limit."
  • FasterTransformer: "As FasterTransformer does not have its own scheduler, we implement a custom scheduler with a dynamic batching mechanism similar to the existing serving systems such as Triton [30]." It takes "up to B number of earliest arrived requests" with B "as large as possible" for the GPU memory.
  • Orca: "Since Orca is not publicly available for use, we implement our own version of Orca. We assume Orca uses the buddy allocation algorithm". Oracle knows true output lengths ("infeasible to achieve in practice"); Pow2 "over-reserves the space for outputs by at most 2×. For example, if the true output length is 25, it reserves 32 positions"; Max reserves "up to the maximum sequence length of the model, i.e., 2048 tokens."
How it works, step by step: reading one point on a Fig. 12 curve
  1. Pick a rate, say 1.5 requests/s, and draw Poisson arrivals for an hour (about 5,400 requests); each gets an input and output length from the dataset.
  2. Run the system; record each request's end-to-end time (queueing plus prefill plus every decode step).
  3. Normalize: divide each request's latency by its output tokens and average. A request that waited 10 s in the queue and produced 50 tokens in 5 s contributes 15 ÷ 50 = 0.3 s/token (illustrative).
  4. Sweep the rate: below capacity, normalized latency is flat (each step's cost); past capacity the queue grows without bound for the whole trace and the curve shoots up. "Sustainable rate" is where the curve turns upward; the paper does not define a precise threshold.
  5. Why it measures throughput: the rate a system sustains at low latency is its throughput in requests per second, and that rate is set by how many requests it can batch (M2).
Assumptions it relies on
  • A1. The Orca re-implementation reflects Orca's memory behavior (stated as an assumption).
  • A2. Poisson arrivals with dataset lengths stand in for real traffic (stated as the method; representativeness implicit).
  • A3. Normalized latency is a fair throughput proxy (stated, following Orca).
  • A4. Model outputs are the same across systems, so only speed differs (stated: no effect on accuracy; output lengths come from the dataset).
If an assumption changes
  • A1 changes (real Orca uses a smarter allocator): external fragmentation would shrink, but Orca (Oracle) already has no over-reservation and still holds only 38.2% token states, so the gap would narrow, not close (inference).
  • A2 changes (bursty arrivals): bursts would hit memory limits more often, exercising preemption, which the evaluation never isolates (inference).
  • A3 changes (latency-critical service measured by time to first token or tail latency): normalized latency averages away tails and divides by output length, so short outputs weigh heavily; the paper reports no percentiles (inference).
  • A4 changes: not an issue; outputs are not generated text with quality metrics but lengths taken from the dataset (inference from "use their input and output lengths to synthesize client requests").
Design notes and rejected alternatives

The three Orca variants bracket what any reservation-based system could do. FasterTransformer differs in both scheduling and memory, so its gap (up to 22×) mixes the two effects; the Orca comparisons isolate memory management.

Connections

FFS: FFS measured file systems after a month of production use because performance on a fresh system misleads; here the analogue is measuring at steady state under sustained load, which the hour-long traces aim at (inference). Livelock: the throughput-versus-offered-load methodology, with collapse past saturation (inference).

L · Stated limitations and future work

What the paper itself says
  • Not for every GPU workload: "in DNN training, the tensor shapes are typically static, and thus memory allocation can be optimized ahead of time", and for non-LLM serving that is compute-bound, "introducing the vLLM's techniques may rather degrade the performance due to the extra overhead of memory indirection and non-contiguous block memory."
  • Kernel cost: "20–26% higher attention kernel latency" than FasterTransformer, argued to be small because it "only affects the attention operator".
  • Compute-bound configurations gain little: Fig. 12(f), OPT-175B on Alpaca.
  • Block size is a compromise: 16 is chosen as good "in most workloads"; Alpaca degrades badly with large blocks.
  • Swap versus recompute is left as an empirical choice depending on block size and hardware (§7.3).
  • Baselines: Orca "is not publicly available", so the authors "implement our own version" and "assume Orca uses the buddy allocation algorithm"; FasterTransformer runs under a scheduler the authors wrote.
  • Cost limits: "we use 15-minute traces for the OPT-175B model due to the cost limit."
  • Chatbot: "We do not store the KV cache between different conversation rounds as doing this would occupy the space for other requests between the conversation rounds."
  • Future work: "we would be excited to see vLLM's techniques being applied to other workloads with similar properties to LLM serving."
What the evaluation does not cover (this guide's list)
  • How often preemption happens in any experiment, and what it costs end to end; §7.3's comparison is the only measurement, at one rate.
  • Tail latency or time to first token: normalized latency is a mean over requests, divided by output length.
  • Mixed decoding methods in one batch, which §4.4 says vLLM enables; no experiment mixes them.
  • Fairness of FCFS with latest-first preemption and the admission freeze under sustained overload.
  • The swap-space bound (shown false in a corner case, Class Prep C1) and CPU memory use.
  • Scheduler and block-manager overhead in Python per iteration, and the size and latency of the per-step control message to workers.
  • Real arrival processes: arrivals are Poisson because the datasets have no timestamps.
  • Which experiment Fig. 2 measures (model, trace, rate).
  • Other GPUs (H100 is mentioned only in the trend argument) and models whose key/value size differs from multi-head attention.

S · vLLM next to Salus (11/17)

Salus (Yu and Chowdhury, MLSys 2020), the paper before this one, also manages GPU memory for deep learning, with the opposite sharing pattern: many jobs on one GPU rather than many requests of one model. Salus facts below are from the Salus paper; the comparison is this guide's.

The key difference is which memory outlives an iteration. C · Connections to the other CS240 papers (mechanical only)

  • Superpages (10/13): the block size trade-off is the page size trade-off (translation work per byte versus internal fragmentation). Navarro et al. use reservations that are filled on demand and can be broken up under pressure; Orca's chunks are reservations that can never be shrunk, and vLLM drops reservation entirely in favor of small pages (inference).
  • ESX memory management: content-based page sharing with copy-on-write versus vLLM's sharing by construction (forking a sequence) with reference counts; ESX must hash pages to discover sharing, vLLM knows it from the decoding algorithm. Both overcommit memory and need a reclaim path (ballooning and swapping, preemption and swapping) (inference).
  • x86 VMM (hardware versus software virtualization): vLLM's block table is walked by software inside the attention kernel, like a software-maintained translation, and its 20 to 26% kernel overhead is the price of not having hardware translation at this granularity. Unlike shadow page tables, nothing needs tracing: the block manager is the only writer of the tables (inference).
  • Exokernel (11/10): vLLM manages GPU memory with application knowledge a generic pager lacks: all-or-nothing eviction, gang-scheduled sequence groups, and recomputation (inference).
  • Dune (11/12): Dune gives a process direct use of page-table hardware for its own policies; vLLM builds its own page table in software because the GPU's translation hardware is not exposed at block granularity (inference).
  • Salus (11/17): see S above.
  • LFS (10/27) and F2FS (11/5): both keep a logical-to-physical map (inode map; node address table) so data can move without rewriting references; vLLM's block table plays the same role when a swapped-in block lands at a new physical number. Unlike LFS, vLLM needs no cleaner, because equal-size blocks never need compaction (inference).
  • FFS: blocks plus fragments versus fixed blocks with a partly filled last block: both bound tail waste per file or sequence; FFS's free space reserve is the analogue of the headroom vLLM does not keep, which is why it needs preemption (inference).
  • Livelock (10/6): Fig. 12's latency explodes once offered load passes capacity; vLLM's admission freeze while preempted work is pending is the same principle as not accepting input that cannot be finished (inference).
  • NFS (10/22): each step's control message carries all state a worker needs (token IDs and block tables), so workers keep no memory-management state of their own, the way NFS requests carry file handles and offsets to a stateless server (inference).
  • Hints (12/1): the KV cache is "Cache answers to expensive computations"; the fused kernels and batched block copies are "Use batch processing if possible"; the admission freeze is "Shed load to control demand". Contiguous reservation follows "Split resources in a fixed way if in doubt, rather than sharing them" and "Safety first" (a request never runs out), and vLLM deliberately gives both up for utilization, paying with preemption (inference).

④ Why block size 256 wrecks Alpaca but barely hurts ShareGPT

⑦ What one decoding step reads, and why the batch pays for itself

OPT-13B on an A100-40GB. Weights 26 GB (Table 1). HBM bandwidth ≈1.5 TB/s (general knowledge). Batch of 30.42 requests holding ≈517 tokens each (Example ②). Illustrative: assumes the step is limited by memory traffic alone.

  1. One request alone: read 26 GB of weights to produce one token: 26 ÷ 1,500 GB/s ≈ 17 ms per token.
  2. The batch's KV reads: 30.42 × 517 × 819,200 bytes ≈ 12.9 GB per step: every request's whole cache is read once per step.
  3. Batched step: (26 + 12.9) GB ÷ 1.5 TB/s ≈ 26 ms, producing 30 tokens: ≈ 0.86 ms per token, about 20 times the single-request rate.
  4. Where the time goes: a third of the step's bytes are KV cache, read by the attention kernel; this is why the kernel's 20 to 26% overhead (Fig. 18a) is not negligible, though the paper argues it touches only "the attention operator" (inference).
🍯
Weights are read once per step regardless of batch size; KV cache is read per request. Batching amortizes the first, and memory capacity limits how much of the second can be resident.

Connecting outward

What vLLM teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

Capacity, not bandwidth, sets throughput when work can be batched

Each decode step is bandwidth-bound, yet the paper's gains come entirely from capacity: more resident KV cache means a bigger batch, and a bigger batch amortizes the weight reads. Wasting capacity therefore costs throughput even when no bandwidth is wasted. The same reasoning applies to any tier where requests share a large read-mostly structure (weights here, an index or a model elsewhere) and each request also needs private state: the private state's footprint decides how many requests share each pass over the common data.

Indirection is affordable when the consumer does the translation

vLLM has no MMU at block granularity, so the attention kernel itself reads the block table and fetches each block, at 20 to 26% kernel cost (Fig. 18a) but far less end to end. The lesson is about where translation lives: putting the lookup inside the kernel that already streams the data, with one warp per block, hides most of it. Software-managed translation layers in flash and memory controllers make the same bet, and their cost likewise depends on how much useful work each lookup covers (here, the block size).

Allocation unit and transfer unit are the same knob

The block is both the unit of allocation (small is better: less internal waste, more sharing) and the unit of transfer (large is better: coalesced reads, efficient PCIe copies). Fig. 18b and Fig. 19 show both sides on the same axis, with 16 as the compromise. Any tiered memory system that pages between devices faces this coupling; decoupling them, for example allocating small and transferring in batches of contiguous blocks, is what the fused copy kernel starts to do (M19).

On-demand allocation needs a plan for running out

Reservation is wasteful but safe; on-demand allocation is efficient but can fail mid-request. vLLM pays for its 96.3% utilization with a preemption path: victim choice, all-or-nothing eviction, swap or recompute, and an admission freeze. Overcommitted hypervisors, thin-provisioned storage and memory overcommit in operating systems make the same trade. The design question is never only how to pack better but also what to do on the rare step when packing fails.

Know what the data is, and eviction gets simpler and cheaper

Two of vLLM's departures from OS paging come from knowing the data. All blocks of a sequence are needed together, so per-block replacement policies are pointless and eviction is all-or-nothing. And the KV cache is a deterministic function of tokens the server keeps, so evicted state can be recomputed rather than written out, like dropping a clean page that can be re-read. Knowing that cached data is derived, immutable or accessed as a unit is what lets a memory manager skip write-back, tracking and partial residency.

Immutability makes sharing cheap

A cached key or value never changes once written, so sharing by reference is safe without invalidation, and copy-on-write triggers only at the single partly filled block where a sequence appends. Compare content-based page sharing in ESX, which has to hash pages to find duplicates and break sharing on any write. When the structure of the computation tells you what is shared (a fork, a common prefix), and shared data is append-only, deduplication is close to free.

C1 · Is the CPU swap space really bounded by the GPU's KV memory?

Section 4.5 says that with its design "the number of blocks swapped to the CPU RAM never exceeds the number of total physical blocks in the GPU RAM." The stated rules are: preempt the latest group first, evict all of a group's blocks, accept no new requests while anything is preempted, and bring a group back when a request completes. But the groups that keep running still grow. With a 12-block GPU pool, can I build a case where more than 12 blocks end up in CPU memory?

AnswerWork it out first, then open▾

Yes. Start with S1 (oldest, 2 blocks), S2 (4) and S3 (6): the pool is full. S2 needs a block, so S3, the latest, is swapped out: 6 blocks in CPU memory. No request completes for a while, so S3 stays out, and S1 and S2 keep decoding into the 6 freed blocks: S1 grows to 3, S2 to 9, and the pool is full again. S2 needs another block; the latest running group is now S2, so its 9 blocks are swapped out too. CPU memory holds 6 + 9 = 15 blocks, more than the 12-block pool.

The admission freeze stops new requests from adding load, but not admitted sequences from growing. The bound holds only if freed blocks were held back for the preempted group's return, which the paper does not describe. The released vLLM sets a fixed CPU swap space and aborts a request when it runs out (general knowledge, not in the paper).

Where the answer comes from: The four rules quoted from Section 4.5, applied to a constructed trace (this guide's counterexample).

C2 · Why does parallel sampling save only 6 to 10% on Alpaca?

Alpaca prompts average 19.31 tokens and outputs 58.45 (Fig. 11), so a prompt is about a quarter of a sequence's tokens. Section 3 says the prompt part of the KV cache "accounts for 12% of the total KV cache memory in our experiment", and Fig. 15a shows savings of only 6.09%, 8.53% and 9.79% for 2, 4 and 6 samples. If the whole prompt were shared, what would the savings be, and what accounts for the gap?

AnswerWork it out first, then open▾

Token-level sharing of the whole prompt saves P(n − 1) / (n(P + O)) of a finished request's memory: 12.4%, 18.6% and 20.7% for n = 2, 4, 6. The measured values are about half that.

Sharing is per block, not per token. Only full prompt blocks are shared; the last, partly filled prompt block is copied for each extra sample. With block size 16, a prompt under 16 tokens shares nothing and a 19-token prompt shares one block. If a fraction s of each sequence's blocks is shareable, the saving is s(n − 1) / n. Taking s = 12.2% from n = 2 predicts 9.1% and 10.2% for n = 4 and 6, close to the measured 8.53% and 9.79%. So the paper's "12%" is the shareable fraction at block granularity, and it is consistent with Fig. 15a.

ShareGPT's 161-token prompts span about 10 full blocks, so rounding costs little there: the token-level ideal for n = 2 is 16.2%, the bottom of the paper's "16.2% - 30.5%".

Where the answer comes from: Arithmetic on Fig. 11's means, Fig. 15a and the 12% sentence in Section 3; the s(n − 1)/n model is this guide's.

C3 · How many block copies does beam search cost per step?

The paper says copy-on-write in beam search "is applied only when the newly generated tokens are within an old shared block" and "involves only copying one block of data." In Fig. 9's step (width 4), how many block copies does vLLM make, and how many would a contiguous-buffer system make? At a step where the new tokens land mid-block and the 4 new candidates descend from 2 parents, how many copies?

AnswerWork it out first, then open▾

Fig. 9's step: zero. Every candidate "has used 4 full logical blocks", so new tokens go into new blocks 9 to 12 and the old blocks are only referenced again. A system with one contiguous buffer per candidate must overwrite candidate 0's buffer with candidate 1's history and candidate 3's with candidate 2's: two whole histories, 8 blocks of data.

Mid-block: each parent's last block is partly filled and now has 2 children (reference count 2). The first child to write copies it; the second writes in place. Two copies of one block each. In general a step costs (number of new candidates − number of distinct parents) one-block copies, and none when the step starts a new block. "One block" is per copy, not per step.

Where the answer comes from: Section 4.4's copy-on-write rule and Fig. 9, worked through.

C4 · Which of §6.4's prefixes forces a copy for every request?

Section 6.4 shares an 80-token 1-shot prefix and a 341-token 5-shot prefix. A request maps its logical blocks to the cached prefix blocks "with the last block marked copy-on-write." With block size 16, does either prefix cost every request a block copy? How much KV memory does each request avoid storing in each case?

AnswerWork it out first, then open▾

80 = 5 × 16: the prefix fills its last block exactly, so the task input starts a new private block and no copy is ever needed. 341 = 21 × 16 + 5: the 22nd block holds 5 prefix tokens, so each request's first task-input token lands in a shared block and triggers a copy of one block.

LLaMA-13B has the same 40 layers and hidden size 5120 as OPT-13B (general knowledge), so 800 KiB per token and 12.5 MiB per block. Per request, the 1-shot case shares 80 × 800 KiB = 62.5 MiB; the 5-shot case shares 21 blocks = 262.5 MiB and pays one 12.5 MiB copied block holding 5 useful slots. Both also skip computing the prefix's keys and values entirely ("The prompt phase computation only needs to execute on the user's task input").

Where the answer comes from: Arithmetic on Section 6.4's prefix lengths with Section 4.4's copy-on-write rule; model dimensions are general knowledge.

C5 · Why do all three Orca variants behave the same in the chatbot test?

In Section 6.5 the three Orca baselines nearly coincide, and the paper says "Due to the buddy allocation algorithm, the Orca baselines reserve the space for 1024 tokens for the request outputs, regardless of how they predict the output lengths." Even Orca (Oracle), which knows a reply will be 50 tokens? Work out why, and how many requests each can run at once on OPT-13B.

AnswerWork it out first, then open▾

Most prompts are cut to exactly 1024 tokens. A chunk holds prompt plus output space: Oracle asks for 1024 + 50 = 1074 slots, Pow2 for 1024 + 64 = 1088, Max for 2048. A buddy allocator only hands out power-of-two chunks, so anything above 1024 rounds up to 2048, leaving 1024 slots for output whatever the prediction.

So every variant holds 2048 slots per request: ⌊15,728 ÷ 2048⌋ = 7 requests at once. vLLM holds 1024 tokens plus what has actually been generated, in 16-token blocks, so roughly twice as many requests fit early in their replies (this guide's arithmetic). The paper reports 2× higher sustainable rate; Fig. 17 read at 0.5 s/token looks closer to 1.5×.

Where the answer comes from: Section 6.5's sentence, Table 1's slot count, and how buddy allocators round (general knowledge).

C6 · With one block table for all GPUs, which GPU sets the pool size?

Section 4.6: every GPU worker uses the same physical block IDs and stores only its attention heads' share. For OPT-66B on 4 GPUs, suppose one GPU has 1 GiB less free memory than the other three (for example, it also holds the embedding table). Starting from Table 1's 21 GB of KV memory split evenly, how many KV blocks does vLLM get?

AnswerWork it out first, then open▾

OPT-66B (64 layers, hidden 9216, general knowledge) caches 2.25 MiB per token, 576 KiB per GPU, so one 16-token block is 9 MiB on each GPU. Evenly split, 5.25 GiB per GPU gives 597 blocks (9,557 slots).

Block number b must exist on every GPU, so the pool is the minimum over GPUs: ⌊4.25 GiB ÷ 9 MiB⌋ = 483 blocks = 7,728 slots. Total KV memory fell by 1 GiB of 21 (4.8%) but the pool fell by 19%, and about 1 GiB on each of the other three GPUs is unusable for KV cache.

Where the answer comes from: Section 4.6's shared block IDs, Table 1, and this guide's arithmetic; model dimensions are general knowledge.

C7 · What is vLLM's missing 3.7% in Fig. 2?

vLLM "limits all the memory wastes for a request within one block", and Fig. 2 shows 96.3% token states for vLLM. If Fig. 2 is OPT-13B on ShareGPT, where Fig. 13a shows about 30 requests running in a 983-block pool, how much of the remaining 3.7% can partly filled last blocks account for? What must the rest be?

AnswerWork it out first, then open▾

At most 15 empty slots per sequence: 30.42 × 15 = 456 slots = 2.9% of 15,728. With lengths spread evenly over a block, the average is about 7.5 empty slots: 228 slots = 1.45%. So partly filled blocks explain at most 2.9 points and probably about 1.5; at least 0.8 points, likely about 2, are something else.

In the paper's terms the empty tail of a last block is "reserved for future generations", so it belongs in the orange slice. The rest must be memory holding no running sequence's tokens: free blocks the scheduler leaves unused in an iteration, for example when the next waiting prompt needs more blocks than are free and FCFS admits nothing behind it (inference), plus whatever "Others" includes. The figure does not label the slivers.

Where the answer comes from: Fig. 2, Fig. 13a, Table 1 and the one-block bound in Section 4.3. The assumption that Fig. 2 is OPT-13B on ShareGPT is this guide's; the paper says only "the experiment in §6.2".

Glossary, results, and provenance

Every term in one place, then where the numbers came from and what this guide found inconsistent in the paper.

Core terms
PagedAttentionAn attention algorithm, implemented as a GPU kernel, that computes exact attention for a query by reading the keys and values of earlier tokens one fixed-size block at a time from wherever a block table says each block is, instead of from one contiguous tensor.
vLLMThe paper's LLM serving system: a FastAPI front end plus an engine (8.5K lines of Python, 2K of C++/CUDA) whose scheduler and KV cache manager manage KV cache memory in blocks and drive GPU workers that run PagedAttention.
KV cacheGPU-resident storage holding the key and value vectors of every token a sequence has processed, in every layer, kept so each decoding step reads them instead of recomputing them; 800 KiB per token for OPT-13B.
KV blockA fixed-size unit of KV cache storage holding the keys and values of B consecutive tokens of one sequence (B = 16 by default); in the paper's implementation each layer and head has its own storage for the block.
Block size (B)The number of token positions in one KV block; a global constant chosen at startup, trading kernel efficiency and transfer size against internal waste and sharing.
Logical KV blockThe i-th block-sized range of positions in one sequence (positions iB to iB + B − 1), the analogue of a virtual page; it has no storage of its own.
Physical KV blockA numbered block-sized slot in a contiguous region of GPU memory (or CPU memory, for swapping) that the block engine divides up at startup, the analogue of a physical page frame.
Block tableA per-sequence array whose i-th entry holds the physical block number backing logical block i and the number of filled positions in it; the analogue of a page table, walked by the attention kernel.
KV cache manager (block manager)The component inside the centralized scheduler that owns all block tables and reference counts and decides allocation, sharing, copying and eviction; it sends its decisions to GPU workers.
GPU and CPU block allocatorsTwo free-block pools in the KV cache manager, one for physical blocks in GPU memory and one for blocks in CPU memory used as swap space.
Cache engine (block engine)The part of each GPU worker that allocates the KV memory region and carries out block writes, copies and swaps the scheduler orders.
Reference countA per-physical-block counter equal to the number of logical blocks, across all sequences, mapped to it; a write needs a copy if it is above 1, and the block is freed when it reaches 0.
Block-level copy-on-writeThe rule that a sequence about to write into a physical block with reference count above 1 first gets a private copy of that one block, decrementing the original's count.
SequenceThe paper's term for a prompt followed by the output tokens generated after it; one request yields one or more sequences.
Sequence groupAll sequences belonging to one request (for example a request's beam candidates), which are scheduled, preempted and resumed together because they may share blocks.
Fork, append, freeThe three sequence operations from which vLLM builds decoding algorithms: create a sequence sharing another's blocks, add one token to a sequence, and delete a sequence, releasing its references.
All-or-nothing evictionvLLM's eviction rule: when blocks run out, a victim sequence group loses all of its GPU blocks at once, never some of them.
Swapping (vLLM)Recovery by copying a preempted group's KV blocks to CPU memory over PCIe and back into any free GPU blocks when it is rescheduled.
RecomputationRecovery by discarding a preempted group's KV blocks and rebuilding them with one prefill pass over its prompt plus all tokens generated so far.
Shared prefix (system prompt)A provider-defined instruction and example text that many requests' prompts begin with, whose KV cache vLLM keeps in reserved physical blocks that requests map into, with the last block copy-on-write.
Reservation (paper's waste category)KV slots held by a request for tokens it will generate later; eventually used, but unavailable to others meanwhile.
Internal fragmentation (paper's sense)KV slots inside a request's allocation that it will never use, known only when the request finishes; under maximum-length reservation, everything past the final length.
External fragmentation (paper's sense)Free KV memory between requests' chunks that the allocator cannot give to any request, caused by variable-size contiguous chunks.
Supporting terms
TokenAn integer index into a model's fixed vocabulary of word pieces; the unit a language model reads and emits.
Prefill (prompt phase)The first model pass for a request, processing all prompt tokens at once with matrix-matrix multiplication and producing their KV cache and the first output token.
Decode (generation phase)The rest of a request: one model pass per output token, each with one new input token per sequence, memory-bound because each weight is read for little arithmetic.
Attention headOne of several independent attention computations in a layer, each over its own slice of the query, key and value vectors (OPT-13B: 40 heads of 128 numbers, general knowledge).
FP16The 16-bit floating-point number format, 2 bytes per value, used for weights and KV cache in the paper.
HBMHigh-bandwidth DRAM stacked beside the GPU die; on the A100, 40 or 80 GB at roughly 1.5 to 2 TB/s (general knowledge).
GPU kernelA function launched by the CPU and executed by thousands of GPU threads; each launch has a fixed overhead of a few microseconds (general knowledge).
Warp and coalesced accessA warp is a group of 32 GPU threads executing in lockstep; an access is coalesced when the warp's threads touch consecutive addresses, which the hardware merges into a few wide transactions.
cudaMemcpyAsyncThe CUDA runtime call that queues one memory copy (within the GPU or between CPU and GPU); each call carries fixed setup cost.
PCIeThe serial expansion bus linking GPU and CPU memory, about 32 GB/s per direction for PCIe 4.0 x16 (general knowledge), the path swapping uses.
Tensor model parallelismMegatron-LM's method of splitting each layer's weight matrices across GPUs (attention by head), with an all-reduce combining partial results after each layer.
SPMDSingle program, multiple data: every GPU runs the same program on its own slice of the data in lockstep.
All-reduceA collective operation after which every participant holds the combination (here the sum) of all participants' inputs; done with NVIDIA's NCCL library in vLLM.
Buddy allocatorAn allocator that serves power-of-two-sized chunks by splitting free chunks in halves and merging free buddies; the paper assumes Orca uses one.
CompactionMoving allocated chunks together to merge free space; the paper rejects it as impractical for gigabyte-sized KV tensors.
Iteration-level schedulingOrca's batching discipline: the batch is re-formed after every model iteration, so requests join and leave individually.
Orca (Max), (Pow2), (Oracle)The authors' three re-implementations of Orca, reserving output space of the maximum length (2048), the next power of two above the true output length, or exactly the true output length.
FasterTransformerNVIDIA's latency-optimized inference library; in the evaluation it runs under a simple scheduler batching up to B earliest arrivals.
Normalized latencyThe paper's metric: the mean over requests of end-to-end latency divided by output length, in seconds per token.
ShareGPT, AlpacaTwo datasets whose input and output lengths drive the synthetic traces: user-shared ChatGPT conversations (means 161 and 338 tokens) and GPT-3.5-generated instructions (19 and 58).
Parallel samplingA decoding mode producing several independent random outputs for one prompt.
Beam search and beam widthA decoding mode that keeps the k most probable partial outputs (k is the beam width) and, each step, keeps the top k of their k · |V| one-token extensions.
OPT, LLaMAFamilies of open Transformer language models (Meta); the paper uses OPT-13B, 66B, 175B and LLaMA-13B.

Inconsistencies found in the paper

(1) Fig. 3 labels 2038 never-used slots for request A, but its own labels give 7 + 2 + 2 = 11 used or reserved slots of 2048, so 2037; the "1 slot for generated token" bracket spans two tokens. (2) Fig. 1 labels the KV cache ">30%"; the text says "Close to 30%". (3) Table 1: 21 GB at 2.25 MiB per token is 9,557 slots, not 9.7K; 346 GB of FP16 parameters implies about 173B parameters, not 175B. (4) The claim that swapped blocks "never" exceed the GPU's block count fails when running groups grow after a preemption (Class Prep C1). (5) "Recomputation overhead is never higher than 20% of swapping's latency" is false as written at small block sizes (≈36 versus ≈137 ms); Fig. 19a supports "never more than about 20% above swapping". (6) Fig. 18a's batch-8 lines read as ≈23 to 40% overhead, above the stated 20 to 26%, which matches the batch-32 lines. (7) Fig. 12 read at 0.5 s/token gives ≈1.45× over Orca (Oracle) in panel (c) and at most ≈4.9× over Orca (Max), against the stated 1.7 to 2.7× and 2.7 to 8×; with no defined threshold this may be a reading difference. (8) Fig. 17 reads as ≈1.5× over the Orca baselines, not "2×". (9) Footnote 1 says each head and layer has a separate block table, while §4.6 sends "the block table for each request"; both hold only if every per-layer table carries the same mapping (M5).
