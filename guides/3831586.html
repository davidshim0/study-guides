The heap says it's free. The kernel begs to differ

Your allocator frees a block, RSS doesn't move, and DRAM keeps getting pricier. This is the story of why — and a classification scheme that measures exactly how many bytes are stuck at the user/kernel boundary.

📄 "Lost Bytes At The Crossroads..." · Fistanto, Tempel, Dietrich (TU Braunschweig) 🎓 Assumes OS/mm background — primers focus on paper-specific vocabulary ⏱ ~20 min read
🗄️

A byte only becomes ELIGIBLE FOR RECLAIM once its WHOLE page (P — 4KiB in the paper's setup) is empty, and even then the kernel may not reclaim it right away (e.g. lazy MADV_FREE) — a hole that merely touches a page boundary is lost, not reclaimable.

Vocabulary before content

Quick glossary + six primers

You know VMAs and page tables — these primers only cover the paper-specific pieces: the tools it uses to measure loss, and the allocator behavior it's measuring.

VMAVirtual memory area — the kernel's coarse unit for mmap()/munmap(); the boundary allocators must request memory across.
RSSResident set size — physical frames actually mapped for a process, regardless of what the allocator thinks is "free."
madvise(DONTNEED/FREE)Sub-VMA hints that release physical frames within an existing VMA without unmapping it.
mincore()Syscall that reports, per page, whether it is currently backed by physical memory — the paper's measurement instrument.
Halloc / HminThe paper's notation: the allocator's real hole list vs. the same holes merged wherever adjacent — an upper bound on returnability.
mallocngmusl libc's slab-style allocator, the paper's case study; supports optional madvise(FREE) release.
1Two granularities of kernel control▾

mmap()/munmap() operate on whole VMAs — expensive, and require extensive locking [15,13]. madvise(WILLNEED/DONTNEED) operates on page-aligned sub-ranges of an existing VMA, changing physical backing without touching the VMA structure.

Now you're ready: allocators use the fine-grained madvise() path to return memory — but only if the range they want to release happens to be page-aligned.
2DONTNEED vs. FREE — eager vs. lazy▾

DONTNEED removes pages immediately, forcing a TLB shootdown. Linux 4.16 added MADV_FREE: pages are marked reclaimable but stay mapped until real memory pressure hits, avoiding the shootdown cost.

Now you're ready: mallocng optionally uses FREE for cheaper releases — but "reclaimable" is not the same as "already reclaimed," which matters for the paper's RSS measurements.
3Size classes misalign with pages on purpose▾

Allocators like TCMalloc [27] round requests to fixed, deliberately "uneven" size classes (e.g. class 22 covers 1153–1408B) to cut internal fragmentation — a standard technique [27,4,6].

Now you're ready: uneven sizes are good for fragmentation, bad for page alignment — every third 1408B block in that class crosses a 4KiB boundary.
4How the paper actually measures loss▾

An LD_PRELOAD'd sampling thread reads mallocng's internal hole list directly, and calls mincore() on the heap region to see which of those hole-bytes are still physically resident.

Now you're ready: "lost" in this paper is a precise, measured quantity — bytes in an unallocated hole that mincore() reports as still backed.
5Halloc vs. Hmin: real vs. best-case▾

mallocng's own hole list (Halloc) does some adjacent-slot merging, but it isn't page-aware — it doesn't target producing page-sized, page-aligned holes. The paper also builds Hmin — the same holes merged wherever they touch, with no such limitation — via a red-black tree, O(log N) per merge, purely for evaluation.

Now you're ready: the gap between Halloc and Hmin results is the headroom a smarter allocator could capture.
6Same mismatch, bigger granularity▾

Framing, not from the paper: the page-alignment mismatch described here recurs at 2MB huge-page granularity — cited related work on adaptive huge-page subrelease [18] tackles exactly that scaled-up version of this problem.

Now you're ready: this paper's classification vocabulary (sub/head/body/tail) is a clean lens for reasoning about any "can the OS reclaim this range" question, at any granularity.
The whole paper in one place

Lost bytes, in a nutshell

Why memory efficiency (not just speed) matters now, and what exactly gets stuck.

Since late 2025, DRAM prices have risen sharply due to AI-datacenter demand [10], reviving interest in memory-efficient allocators — after a decade where allocator research optimized almost exclusively for speed [12,20,16,27].

The paper's core observation: a memory allocator manages blocks at arbitrary byte granularity, but the kernel can only reclaim physical memory at page granularity via madvise(). When an allocator frees a block, the resulting hole — an unallocated region still requested from the OS — usually doesn't align to page boundaries. The paper classifies every byte of every hole into one of four categories relative to the page grid: sub (whole hole inside one page), head/tail (partial pages at the hole's edges), and body (full pages in the middle — the only class directly returnable via madvise()).

The headline result: in mallocng (musl libc's allocator), merging holes wherever they're adjacent (Hmin) unlocks up to 75 percent more returnable ("body") bytes than the allocator's real hole list ever finds on its own — most dramatically in LuaJIT. For a 300-second Redis benchmark, integrated over time the allocator returned 195.58 MiB·seconds of memory but wasted 1 070.45 MiB·seconds — over 5× more lost than reclaimed.

🍯 Key takeaways

  • The kernel reclaims at page granularity; allocators track free space at block granularity — the mismatch is the whole story.
  • Only the body class — full pages entirely inside a hole — is directly returnable via madvise().
  • Halloc (what mallocng actually tracks) vs. Hmin (merged upper bound) exposes real, measurable headroom.
  • For LuaJIT, merging holes into Hmin raises the returnable "body" share by up to 75% of accumulated hole bytes — the potential savings from smarter merging.
  • Existing mitigations exist (madvise(FREE), decay timers, malloc_trim()) but are opt-in, lazy, or barely used (only 120 of ~42,000 Debian packages call malloc_trim()).
Four everyday pictures

How to think about lost bytes

Each stands alone. Every card ends with where the picture breaks.

🏬
The core mismatch

Kerbside recycling picks up whole bins

You can sort a single glass bottle out of a mixed-waste bin, but the truck only ever lifts whole bins. If your bin still has one non-recyclable item in it, the whole bin goes to landfill — no matter how much of it is technically sortable. The kernel's madvise() is the truck: it only ever picks up whole pages.

Where it breaks: real bins don't have "size classes" chosen to reduce waste — TCMalloc's uneven size classes are a deliberate trade that worsens this specific problem to improve a different one (fragmentation).
🏨
head / body / tail

A hotel only certifies whole vacant floors

Guests check out of individual rooms whenever they like, but housekeeping can only tell the landlord "floor 4 is fully empty" once every room on it is vacant. A floor that's empty except for one lingering guest at the very top stays fully staffed — that's your head/tail. A floor that's entirely empty (body) can be shut down completely.

Where it breaks: real floors don't get created mid-hole the way a hole can straddle a page it never asked to touch — the analogy needs a floor plan that's decided by the guest, not the building.
💺
Halloc vs. Hmin

Empty airline seats vs. a shuffled-full row

Ten scattered empty seats across a plane are useless to close off. The same ten seats consolidated into one full empty row could be roped off entirely. mallocng usually leaves free slots where they land (Halloc); the paper additionally computes what happens if the airline aggressively reseated everyone into contiguous blocks (Hmin) — showing how much is recoverable in principle.

Where it breaks: reseating live passengers (live allocated objects) isn't possible without compaction — Hmin only merges already-free slots, it never moves allocated ones.
🕰️
MADV_FREE laziness

A "for sale" sign, not a moving truck

DONTNEED is calling the movers immediately: expensive, disruptive, but the apartment is empty tonight. FREE is putting up a "for sale" sign: cheap, no disruption, but the previous tenant's furniture stays until a buyer (memory pressure) actually shows up. jemalloc waits a 10-second decay timer before even putting up the sign.

Where it breaks: the sign only ever gets posted on body-class apartments — a head/tail apartment can never be listed, sign or no sign, until the neighboring live tenant moves out too.
The mechanics

How it actually works

The formal classification, the measurement pipeline, and why Halloc undercounts.

1 · The formal classification (§3)

For page size P and a hole h = [v_s, v_e), define page-aligned floor/ceiling helpers ⌈v⌉P and ⌊v⌋P. A hole entirely within one page is a sub-page hole. Otherwise it splits into three parts:

head(h) = [v_s, ⌈v_s⌉_P)     // partial page at the start
body(h) = [⌈v_s⌉_P, ⌊v_e⌋_P)  // whole pages in the middle — only these are returnable
tail(h) = [⌊v_e⌋_P, v_e)     // partial page at the end

Intersecting this classification with the set of pages mincore() reports as physically mapped gives, per category, exactly how many bytes are stuck vs. genuinely reclaimable.

2 · Measurement pipeline

1 · LD_PRELOAD
Load a shim over mallocng; spawn a periodic sampling thread
→
2 · Read Halloc
Extract mallocng's real hole list from its internal slot bitfields
→
3 · Merge to Hmin
Sort into a red-black tree, merge adjacent holes, O(log N) per op
↓
4 · mincore()
Query which heap pages are still physically resident
→
5 · Classify & intersect
Apply sub/head/body/tail formulas, intersect with resident pages

3 · Why Halloc already undercounts

mallocng is a slab-style allocator that groups up to 32 adjacent slots into one area, and it does merge some adjacent free slots — but not in a page-aware way, so the merged holes it produces aren't targeted at page-sized, page-aligned regions. The paper observed this directly in LuaJIT: mallocng's own merging produced a suspicious spike of holes sized exactly 2032 bytes (size class 23), even though the benchmark and JIT never requested that size — a sign of partial, non-page-aware merging happening under the hood.

⚠
This is exactly the TCMalloc-style problem from the primers: uneven size classes (chosen to reduce internal fragmentation) actively work against page alignment, and are baked into how the allocator merges free slots long before madvise() ever gets a chance.
Real numbers from the paper

Worked examples

Three calculations, following the paper's definitions and reported measurements.

① Classifying a hole with the §3 formulas

Page size P = 4096 B. A hole spans offsets [3000, 13000) — illustrative numbers, using the paper's own floor/ceiling definitions.

  1. Check sub-page: ⌊3000⌋4096 = 0, ⌊13000⌋4096 = 12288 ≠ 0 → not a sub-page hole.
  2. head = [3000, ⌈3000⌉4096) = [3000, 4096) = 1096 B, stuck on the first page.
  3. body = [⌈3000⌉4096, ⌊13000⌋4096) = [4096, 12288) = 8192 B = 2 whole pages — returnable via madvise().
  4. tail = [⌊13000⌋4096, 13000) = [12288, 13000) = 712 B, stuck on the last page.
🍯
Of a 10000B hole, only 8192B (82%) is returnable — and only if the allocator actually calls madvise() on those pages; with lazy MADV_FREE, they can stay resident until real memory pressure forces the reclaim.

② Why TCMalloc's class 22 crosses pages

TCMalloc's size class 22 handles objects sized 1153–1408 B; the paper notes "every third 1408-byte block crosses a 4KiB page boundary."

  1. Pack 1408B blocks back-to-back: block 1 ends at 1408, block 2 ends at 2816, block 3 ends at 4224.
  2. 4224 mod 4096 = 128 — block 3 starts at offset 2816 (inside page 0) and ends at 4224 (128 B into page 1).
  3. 4096 / 1408 ≈ 2.91 — confirming a page holds just under three blocks, so the pattern of crossings repeats every 3 blocks (≈ 4224 B ≈ ~1.03 pages).
💡
The allocator picked 1408B to minimize internal fragmentation for a class covering up to 1408B objects — a completely sound choice by classic fragmentation metrics [24,4], but it guarantees a fraction of freed blocks will always straddle a page.

③ Redis: 5× more wasted than returned

Over a 300s run, mallocng returns 195.58 MiB·seconds of memory to the OS while 1070.45 MiB·seconds sit wasted (Fig. 2). About 20% of RSS is holes, and 82% of those holes stay physically backed.

  1. Waste-to-return ratio: 1070.45 / 195.58 ≈ 5.47× more wasted than actually reclaimed.
  2. Instantaneous "held hostage" fraction: 20% holes × 82% still-backed ≈ 16.4% of RSS at any moment is a free-but-resident hole.
  3. Hmin headroom: merging Redis's holes grows the body class 2.85× (0.83 → 2.38 MiB average, Table 1) — to 63% of accumulated Hmin hole size.
🍯
For LuaJIT the gap is starker still: body goes from 0 MiB under Halloc to 181.04 MiB under Hmin — 75% of accumulated hole size becomes theoretically returnable once you allow merging.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it checks.

Problem 1 · easy
Your glibc program calls free() heavily and RSS never drops. Will calling madvise() manually fix it?
Show answer
Only partially, and only via malloc_trim() — glibc doesn't return holes surrounded by allocated blocks unless explicitly told to. Even then, only body-class pages within those holes actually shrink RSS; head/tail/sub bytes stay resident regardless.Misconception: that free() automatically informs the kernel. It only updates the allocator's internal bookkeeping.
Problem 2 · medium
Page size 4096 B. A hole spans [3000, 13000). Compute head, body, and tail sizes.
Show answer
head = [3000, 4096) = 1096 B. body = [4096, 12288) = 8192 B (2 pages). tail = [12288, 13000) = 712 B. Total = 1096+8192+712 = 10000B, matching the hole size. Only the 8192B body is a madvise() candidate.Misconception: rounding the hole size down/up to the nearest page gives the returnable amount. It doesn't — you must align to the boundaries the hole actually crosses, not its own start/end.
Problem 3 · medium
mallocng merges small free slots into 2032B blobs (observed in LuaJIT). Does merging alone make those bytes returnable?
Show answer
Not necessarily. 2032B is well under a 4096B page, so a merged hole of that size is almost always still a sub-page hole — entirely stuck if it shares its page with any live allocation. Merging only helps once the combined hole spans a full page's worth of contiguous, page-aligned free space.Misconception: any merging = progress toward returnability. Merging that stays within one page changes nothing about what the OS can reclaim.
Problem 4 · hard
A sub-page hole sits on a page that also holds one live, still-allocated object. Can any amount of adjacent-hole merging (Hmin-style) ever make that page returnable?
Show answer
No — not without moving the live object (compaction), which Hmin explicitly does not do; it only merges already-free slots. As long as one live allocation remains on that physical page, the whole page stays resident, no matter how the free bytes around it are grouped.Misconception: Hmin represents "what a smarter allocator could achieve." It's an upper bound on merging free space only — real returnability additionally requires the page to have zero live occupants.
Problem 5 · easy
For Redis, 20% of RSS is holes and 82% of those holes are still physically backed. What fraction of total RSS is "free but resident" right now?
Show answer
0.20 × 0.82 = 0.164 → 16.4% of RSS is memory the allocator considers free but the kernel is still holding physical frames for.Misconception: "20% holes" already tells you how much is wasted. You must also account for how much of that hole space is still physically backed — some hole bytes may already have been reclaimed.
Quick answers

Frequently asked questions

Six questions readers ask first.

Q1Why doesn't the allocator just madvise() on every free()?▾
Cost. madvise() is a syscall, and calling it on every free() would be catastrophic on the hot path — this is exactly why jemalloc waits a default 10-second decay timeout and mallocng's madvise(FREE) support is optional rather than eager.
Q2What's the difference between Halloc and Hmin, concretely?▾
Halloc is mallocng's actual, currently-in-use hole list — what the allocator really "knows" right now. Hmin is the paper's own construction: the same holes, virtually merged wherever adjacent, computed purely for evaluation to show the headroom a more aggressive allocator could capture.
Q3Does this only matter for tiny objects?▾
No — the paper shows it across the mimalloc-bench suite, including a Redis key-value store, LuaJIT's garbage collector, and even a Clang/SQLite3 compilation job (which lost 74.3% of its Hmin hole bytes to the sub class alone).
Q4Doesn't MADV_FREE already solve this?▾
No — MADV_FREE changes when and how cheaply a body-class page gets reclaimed (lazily, without a TLB shootdown), but it does nothing about head/tail/sub-page bytes, which were never eligible for madvise() in the first place.
Q5Is this the same thing as classic internal/external fragmentation?▾
Related but distinct. Classic fragmentation [24,1] describes virtual-memory waste inside the allocator. This paper adds an orthogonal axis: given already-fragmented free space, how much of it is even visible to the kernel as reclaimable? The two compound — bad fragmentation plus bad alignment is worse than either alone.
Q6Why would a CXL/huge-page researcher care about a userspace allocator paper?▾
Framing, not the paper's claim: the exact same "granularity mismatch" reasoning applies wherever a fine-grained bookkeeping structure meets a coarse-grained reclaim/migrate mechanism — the paper's own related work cites adaptive huge-page subrelease [18] and learning-based placement [17] as the 2MB-scale analogue of this same problem.
