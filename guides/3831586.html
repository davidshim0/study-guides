The memory your allocator hoards but never gives back

malloc() frees bytes to the heap, not pages to the kernel. This is the plain-English story of why a quarter of your RSS can be empty — and why the OS has no idea.

📄 "Lost Bytes At The Crossroads..." · Fistanto, Tempel, Dietrich (TU Braunschweig) 🎓 Some allocator/VM basics assumed — primers cover them ⏱ ~20 min read
🧱

Only whole, page-aligned holes can be returned to the kernel — everything that straddles a page edge, however small, stays stuck sharing that page with live bytes, often for the rest of the process's life.

Quick glossary

Acronyms you'll see everywhere

VMAVirtual Memory Area — the kernel's record of one contiguous mapped region of a process's address space (e.g. the heap).
RSSResident Set Size — physical RAM frames currently backing a process, as tracked by the kernel.
madvise()Syscall that advises the kernel about a page-aligned sub-range of a VMA, e.g. "free this" (DONTNEED) or "may free this" (FREE).
mincore()Syscall/interface that reports, per page, whether it is currently backed by a physical frame.
holeA span of heap bytes the allocator has freed but not yet handed back out — tracked in its internal free-list/metadata.
Halloc / HminThis paper's two hole lists: the allocator's actual (unmerged) holes vs. the theoretical minimum after merging every hole adjacent in virtual address space.
mallocngmusl libc's slab-style allocator, the paper's instrumentation target.
TTLTime-to-live — used in the Redis benchmark to guarantee objects actually expire and free memory during the run.
Before you begin

Seven ideas the paper assumes you know

1free() doesn't mean "give back to the OS"▾

free() returns a block to the allocator's own free-list cache, so a future malloc() can reuse it without a syscall. The kernel is not told and the physical frame stays mapped.

Now you're ready: everything the allocator is "holding free" is, to the OS, indistinguishable from memory still in use.
2Pages, VMAs, and why the kernel only sees 4 KiB units▾

The kernel manages physical memory in fixed-size pages (commonly 4 KiB) inside VMAs. It can map/unmap/advise a whole page, never a handful of bytes inside one.

Now you're ready: any reclaim operation is necessarily page-granular — the paper's whole argument hinges on this mismatch with byte-granular allocator holes.
3madvise(DONTNEED/FREE) — the only way back▾

DONTNEED immediately drops the physical frame (and zeroes it on next touch); the lazier MADV_FREE (Linux ≥4.16) marks a page reclaimable under memory pressure without the immediate TLB-shootdown cost. Both require page-aligned, page-sized ranges.

Now you're ready: the allocator must find a run of bytes that is itself a whole page before it can call either.
4Slab/size-class allocators▾

mallocng, jemalloc, and TCMalloc round allocations into fixed "size classes" (e.g. 2032 B) packed back-to-back in slabs/areas, trading a little internal fragmentation for fast, lock-light allocation.

Now you're ready: size classes are rarely chosen as divisors of the page size — that's precisely what creates misaligned holes.
5RSS vs. "logically free" bytes▾

RSS counts resident pages, not live objects. A process can have high RSS while most of those bytes are dead allocator holes the application no longer needs.

Now you're ready: the paper doesn't simply compute "RSS minus live bytes" — it extracts the allocator's actual hole list, classifies each hole against the page grid, and only then intersects with residency data (via mincore()/pagemap) to see what's truly lost.
6mincore() / pagemap: asking "is this page really resident?"▾

mincore() (or reading /proc/pid/pagemap) lets a process ask, per page, whether a physical frame currently backs it — the ground truth the paper uses to measure "lost" bytes.

Now you're ready: this is how the paper distinguishes "returnable in theory" from "actually still costing you RAM."
7Why this matters for memory tiering▾

Hotness trackers used by tiering systems (page-fault sampling, PTE access bits, PEBS) operate purely at page granularity on OS-visible residency — they cannot see whether a resident page's bytes are allocator garbage or live data.

Note: the paper itself does not evaluate or discuss tiering systems — this connection is this guide's own extrapolation from its measurements, included because it's a natural reader question.

Now you're ready: by this guide's extrapolation, a "free" application heap could look identical to a "hot" one from the tiering layer's point of view. See the Analogies and FAQ tabs.
The whole story in one place

Lost bytes in a nutshell

A userspace allocator and the kernel disagree about granularity. The allocator thinks in bytes — it frees a 2032 B object and keeps it in a free-list "hole," ready to satisfy the next malloc() without a syscall. The kernel thinks in pages — it can only unmap or advise away a whole, page-aligned span via madvise(). Whenever a hole straddles, starts inside, or ends inside a page shared with still-allocated bytes, that page can never be returned, no matter how "free" the allocator considers it.

The paper formalizes this by splitting every allocator hole against the page grid into four classes. Only one, body (the pages a hole covers entirely), is ever returnable. head, tail, and tiny sub-page holes are stuck sharing a page with live data — physically resident, invisible to the OS, and lost.

Measuring real workloads with an instrumented mallocng (musl's allocator), the authors find mallocng keeps 20–25% of RSS as holes, most of it physically backed — yet if the allocator eagerly merged adjacent holes before deciding what to return, the returnable body share can jump dramatically: up to 75% of accumulated hole bytes in LuaJIT.

🍯 Key takeaways

  • free() ≠ returned to OS. The allocator caches the hole; the kernel never finds out.
  • Reclaim is page-granular; allocator holes are byte-granular. Only fully page-covering (body) holes qualify.
  • mallocng's own merging is incomplete — it treats adjacent free slots as separate holes, hiding returnable body regions.
  • Virtually merging all holes adjacent in virtual address space (Hmin) can recover up to 75% of a workload's hole bytes as returnable.
  • Fix directions: page-aware size classes, page-level occupancy tracking, and cheaper OS hints than today's madvise() syscall.
Five everyday pictures

How to think about lost bytes

Each stands alone. Every card ends with where the picture breaks.

Core idea · Scattered rooms

Empty rooms across two apartments

Your free bedroom is in apartment A, your free office is in apartment B next door — you can't sublet "one combined room" to anyone; you'd have to empty a whole apartment first. A byte-sized hole spanning a page boundary is the same: unusable as a unit until an entire page is clear.

Where it breaks: apartments don't move; pages are fixed-size and contiguous, so with the right layout a hole can be made to land cleanly inside one — that's the paper's "block alignment" fix.
Reclaim mechanism · madvise()

Donating only sealed boxes

A charity bin accepts full, sealed boxes of donations — not "half a box plus some loose items sitting on top of other stuff." madvise() is that bin: it will take a whole page (the body), never a partial one, no matter how much of it is logically garbage.

Where it breaks: MADV_FREE is lazier than a strict donation — the page stays around until real pressure hits, more like a bin that only empties when the truck is full.
Tiering connection · Blind landlord

The landlord who never inspects the rooms

A building super checks which apartments have had the lights on recently (page access bits) but never peeks inside to see whether a lit apartment's rooms are actually full of furniture or sitting half-empty. Page-level hotness trackers — the same kind used by DRAM/CXL tiering daemons — are exactly this super: they see residency and access, never allocator-level occupancy.

Where it breaks: this framing is ours, extending the paper's measurement problem to the tiering use case it doesn't directly discuss — see FAQ for the full argument.
Scale · Loose change vs. notes

Coins you can't bring to the bank

A jar of loose change isn't "worthless," but most banks won't deposit it unless you first roll it into fixed-denomination tubes. Sub-page, head, and tail bytes are that loose change: real, freed memory that no OS call will accept until it's rolled up into page-sized units.

Where it breaks: coins can always eventually be rolled; a head sliver stuck beside a long-lived object may never become rollable while that neighbor stays allocated.
Cost · Slow mail carrier

Waiting for the mail carrier before you declutter

Calling madvise() on every tiny free costs a trip to the kernel — locking, TLB shootdowns — so jemalloc waits ~10 s before sending anything, betting the bytes will be reused before the carrier even arrives.

Where it breaks: under genuine memory pressure, that delay is exactly the wrong bet — this tension motivates the paper's call for a "cheap OS hint" interface.
The full explanation

How it actually works

1 · The classification, formally

For each hole h = [v_s, v_e) and page size P, let ⌈v⌉_P/⌊v⌋_P round up/down to the page grid:

head(h) = [v_s, ⌈v_s⌉_P)
body(h) = [⌈v_s⌉_P, ⌊v_e⌋_P)   // page-aligned → returnable
tail(h) = [⌊v_e⌋_P, v_e)

If the whole hole fits inside one page (⌊v_s⌋_P = ⌊v_e⌋_P), it's classified as a single sub-page hole instead. Only body bytes, intersected with the pages actually still backed by physical frames (checked via mincore()), count as genuinely returnable.

2 · Halloc vs. Hmin: does the allocator actually merge?

mallocng tracks each freed slot somewhat independently (Halloc) rather than always coalescing neighbors. The authors also compute Hmin: what the classification yields if every hole adjacent in the heap's virtual address space is first virtually merged into one. Because body bytes only appear when a hole fully covers a page, merging small neighboring holes can conjure body regions that didn't exist in Halloc at all.

3 · Measuring it: LD_PRELOAD + a sampling thread

  1. Hijack mallocng by compiling it as a separate shared library and LD_PRELOAD-ing it under unmodified Redis / LuaJIT.
  2. Spawn a sampling thread that periodically extracts mallocng's internal hole list (Halloc) and calls mincore() on the heap VMAs to learn which pages are still physically backed.
  3. Build Hmin by inserting every hole into a sorted red-black tree and merging adjacent entries in O(log N) per insert.
  4. Classify & intersect each hole (in both lists) against the page grid and against the mincore() results, accumulating bytes per class.

4 · Benchmarks

Redis: memtier_benchmark, 800 connections / 16 threads, SET:GET = 1:5, 2–8 KiB objects, 30–60 s TTL (guarantees real expirations). LuaJIT: a GCBench-style short-lived binary-tree workload, depth 21.

Worked examples

① Merging grows Redis's returnable body 2.85×

Illustrative single-run figures from Table 1: Redis body size is 0.83 MiB under Halloc, 2.38 MiB under Hmin.

  1. Ratio = 2.38 / 0.83 ≈ 2.87× for this run — close to the paper's 5-run average of 2.85×.
  2. mallocng was already calling madvise(FREE) in this config, so this is a missed opportunity on top of an already-reclaiming allocator.

② How much RAM could LuaJIT actually give back?

From Table 2: LuaJIT average RSS = 932.90 MiB, Σ Hmin = 235.941 MiB, body = 75% of Σ Hmin.

  1. Returnable bytes ≈ 0.75 × 235.941 MiB ≈ 176.96 MiB.
  2. As a share of RSS: 176.96 / 932.90 ≈ 19% of this process's entire physical footprint — reclaimable purely by eagerly merging holes and calling madvise().
ℹ
This 19% figure is a derived calculation from the paper's reported percentages, not a number stated verbatim in the text.

③ TCMalloc: why ~every 3rd block crosses a page

TCMalloc's size class 22 packs 1153–1408 B objects back-to-back. Page size = 4096 B.

  1. Block k occupies bytes [k·1408, (k+1)·1408).
  2. k=0: 0–1408 (in page 0). k=1: 1408–2816 (in page 0). k=2: 2816–4224 — crosses the 4096 boundary.
  3. 4096/1408 ≈ 2.91, so straddling happens roughly every 3 blocks — but it's not a clean, forever-repeating k=2,5,8,… sequence. Since lcm(1408,4096) = 45056 bytes = 32 blocks, the block start offsets only cycle back to 0 at k=32 — which therefore lands exactly on a page boundary and does not straddle. Over one full 32-block period, 10 of 32 blocks straddle, close to but not exactly "1 in 3."
💡
Matches the spirit of the paper's claim that "every third 1408-byte block crosses a 4 KiB page boundary" — a useful approximation, not an exact modular law — and shows how uneven size classes are a direct source of head/tail waste.

④ Reading Table 2's LuaJIT row

LuaJIT, Hmin: sub = 1.2%, head = 9.5%, body = 75%, tail = 14.3% of Σ Hmin.

  1. 1.2 + 9.5 + 75 + 14.3 = 100.0% for this row — but the paper is explicit that Table 2's percentages need not sum to 100% in general, since some physical memory may already have been returned to the OS before sampling. LuaJIT summing exactly to 100% here is a property of this particular run, not a guaranteed partition rule.
  2. Interpretation: for this run, 25% of accumulated holes (sub+head+tail) were structurally unreturnable even after perfect merging — the floor imposed by object sizes vs. page alignment.
Test yourself

Practice problems

Problem 1 · easy
Page size 4096 B. A hole spans [3800, 4300). Classify it into head/body/tail and state which bytes are returnable.
Show answer
⌈3800⌉4096=4096, ⌊4300⌋4096=4096. head=[3800,4096)=296 B. body=[4096,4096)=empty. tail=[4096,4300)=204 B. All 500 bytes are unreturnable — the hole crosses one boundary but is too short to ever cover a full page.Misconception: assuming any hole that "crosses a page boundary" automatically has a returnable body — it needs to fully contain at least one page.
Problem 2 · medium
Page size 4096 B. A hole spans [100, 12338). It "looks like" roughly 3 pages (12238/4096≈3). Compute head, body, tail exactly.
Show answer
⌈100⌉4096=4096, ⌊12338⌋4096=⌊3.012⌋·4096=12288. head=[100,4096)=3996 B. body=[4096,12288)=8192 B (exactly 2 pages). tail=[12288,12338)=50 B. Only 2 of the "≈3" pages are returnable — 4046 B sits in head+tail and isn't returnable as this hole currently stands.Misconception: dividing hole_size by page_size to estimate returnable pages. Alignment of the endpoints, not raw size, determines how many full pages are covered.
Problem 3 · medium
The paper reports LuaJIT's sub-page class is ~53% of Halloc but shrinks to 1.2% of Hmin. Why does merging change this so drastically?
Show answer
mallocng doesn't always coalesce physically adjacent free slots into one tracked hole — many small, separately-recorded holes sit right next to each other. Halloc sees each as individually too small to span a page (sub-page). Once merged (Hmin), their combined span frequently does fully cover pages, converting most of that mass into body.Misconception: thinking sub-page holes are inherently tiny and unmergeable. They're only artificially small because of how the allocator's data structure tracks them, not because the underlying freed bytes are physically scattered.
Problem 4 · hard
A page-level memory tiering daemon (à la TPP/HeMem/Memtis) samples PTE access bits to decide which pages to demote to slower tiers. Why can't it directly use "this page looks idle" as a signal that the application doesn't need the memory? (This scenario is this guide's extrapolation — the paper doesn't itself study tiering systems.)
Show answer
A resident page can be idle (no recent access bit) for two very different reasons: (a) it holds live, cold data the app still needs — a legitimate demotion candidate — or (b) it holds allocator holes the app already freed, which the allocator just hasn't bothered to touch or return. The tiering daemon sees only residency and access recency; it has no visibility into allocator-level occupancy, so it cannot distinguish "cold but needed" from "free but never released." A page full of holes is a false positive for "working set," not a true demotion target — demoting it instead of returning it wastes a tier transition on bytes that should simply be freed.Misconception: assuming OS-visible access signals alone are a sufficient proxy for an application's true memory needs. Allocator-level logical occupancy is an orthogonal, invisible-to-the-OS axis that this paper's classification makes explicit.
Problem 5 · easy
Why does jemalloc wait ~10 s (its "decay timeout") before calling madvise() on a reclaimable page, instead of calling it immediately on every free()?
Show answer
madvise() is a syscall with real cost (locking, possible TLB shootdown on DONTNEED). Calling it on every free would thrash performance if the memory is reused moments later — you'd pay the syscall cost twice (return, then re-fault/re-map) for no benefit. The decay timer bets that short-lived frees will be reused before the timer fires, deferring the OS call until the memory has proven it's actually idle.Misconception: assuming "return memory as fast as possible" is unconditionally the right policy. There's a genuine latency-vs-memory-efficiency tradeoff, which is exactly why the paper calls for a cheaper OS-hint interface as future work.
Quick answers

Frequently asked questions

Q1Isn't this just "memory fragmentation"? How is it different?▾
Classic fragmentation is about wasted space within the allocator (internal) or unusable gaps between live objects (external). This paper is specifically about the subset of fragmented/freed bytes that additionally fail to align with OS page boundaries — a narrower, measurable category that determines returnability to the kernel, not just allocator efficiency.
Q2Why can't the kernel just scan the heap and figure out what's unused?▾
The kernel has no notion of "allocated object" — it only sees mapped pages. Only the allocator's internal metadata (free-lists, size-class bitmaps) knows which bytes are logically free. The kernel must be told explicitly, via madvise(), which page-aligned ranges to reclaim.
Q3What's the actual difference between Halloc and Hmin, and why report both?▾
Halloc is mallocng's real, current hole list — what the allocator could act on today. Hmin virtually merges every hole adjacent in the heap's virtual address range first, showing the theoretical upper bound on returnability if the allocator merged aggressively. The gap between them quantifies how much mallocng's own data structures leave on the table.
Q4Is this a mallocng-specific bug, or do other allocators share it?▾
It's structural, not a mallocng bug. TCMalloc's uneven size classes (e.g. 1153–1408 B) cause the same boundary-crossing pattern; jemalloc delays reclaim via a decay timer; glibc's malloc only aggressively returns memory when the application explicitly calls malloc_trim() — which the paper found only ~120 of ~42,000 Debian source packages actually do.
Q5Why trust mincore() over the allocator's own bookkeeping?▾
The allocator's bookkeeping tells you which bytes are logically free, not which pages are physically backed right now (the kernel may already have reclaimed some, or the page may never have been touched). mincore() is ground truth for actual RAM usage, letting the paper measure genuinely wasted physical memory rather than a theoretical upper bound.
Q6If body bytes are "returnable," are they guaranteed to be freed as soon as madvise() is called?▾
Not necessarily. MADV_DONTNEED frees immediately; MADV_FREE (used by mallocng in these experiments) only marks pages reclaimable under memory pressure — they may stay resident, and hence still count toward RSS, until the kernel actually needs them.
Q7How does this relate to huge pages?▾
Huge pages (2 MiB+) make the alignment problem worse by raising the granularity requirement by ~500×. Prior work (Maas et al., cited by the paper) tackles this by "breaking up" huge pages adaptively so partially-used ones can still be subreleased — directly related future work the paper points to.
Q8What does the paper actually propose to fix this?▾
Four directions: (1) size classes designed with page alignment in mind; (2) page-level occupancy tracking inside slab allocators, not just slot bitfields; (3) a cheaper OS-hint interface than today's syscall-based madvise(); (4) auditing other sources of "memory bloat" like caches that aren't strictly allocator-related. All are future work, not implemented in this paper.
Q9Why should a DRAM/NVM/CXL tiering researcher care about this specific paper?▾
Note: the paper doesn't evaluate tiering systems directly — this is this guide's extrapolation. Tiering systems act on page-level hotness signals derived from OS/hardware mechanisms (access bits, PEBS, fault sampling) that are blind to allocator-level occupancy. This paper gives a concrete, measured vocabulary — sub/head/body/tail — for exactly the invisible-to-the-OS waste that could, in principle, masquerade as "resident, maybe-hot" memory to a tiering daemon, inflating the working set it believes it must place or migrate.
