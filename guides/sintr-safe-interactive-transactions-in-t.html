SOSP 2026 · A Field Guide

A transaction can be perfectly legal and still be a lie

Modern Byzantine-fault-tolerant databases let clients run application code themselves — fast, flexible, and completely unable to tell whether that code was followed honestly. This is the plain-English story of Sintr, which makes Byzantine clients redundantly prove their transactions were honest before a single write commits.

📄 "Sintr: Safe Interactive Transactions in the Presence of Byzantine Clients" · Li, Lee, Alvisi, Crooks, Suri-Payer 🎓 Some BFT / distributed-systems basics assumed — the primers cover them ⏱ ~25 min read
🔏

Accept a write only once enough independent clients have RE-EXECUTED it and reached the same outcome — not merely because it passed isolation checks.
Serializable ≠ correct. Endorsement is the difference.

Before you begin

Acronyms first, then the assumed background

Skim the glossary, then work through the primers — each clears up one concept Sintr builds on. Collapsed by default; open whatever's unfamiliar.

Quick glossary
BFTByzantine Fault Tolerant — a system that keeps working correctly even if some participants behave arbitrarily (crash, lie, collude).
SMRState Machine Replication — the classical model where replicas execute the same commands, in the same order, on their own state.

IFCInformation-Flow Control — techniques that track and restrict how data of one sensitivity level may influence data of another.

TPC-C / SEATS / Smallbank / YCSBStandard transactional benchmarks used in the evaluation — TPC-C (high contention), SEATS (lower contention), Smallbank (skewed KVS), YCSB (configurable microbenchmark).

1SMR, and why replicas executing code is the "safe" default▾

In classical state machine replication, a set of replicas all run the same application code, in the same order, over the same state. Because each replica computes updates itself, it can directly check that a proposed transition is a valid execution of an approved command — nobody can sneak in a bogus update.

In Byzantine settings, replicas additionally vote, so only updates endorsed by enough correct replicas are applied.

Now you're ready: Sintr's whole argument is that a newer, faster architecture quietly drops this guarantee — and Sintr exists to bring it back.
2Serializability — a guarantee about order, not meaning▾

Serializability says a set of concurrent transactions' reads and writes could have happened in some one-at-a-time order. It's the standard database correctness guarantee — but it says nothing about whether any individual transaction's writes are the right writes for what it claims to be doing.

A transaction that debits Alice $50 but credits a warehouse $100 out of thin air can still be perfectly serializable.

Now you're ready: this gap — serializable-but-wrong — is exactly the vulnerability Sintr closes. "Isolation" and "integrity" are different guarantees.
3Client-centric BFT databases (the architecture Sintr hardens)▾

To avoid forcing developers into replica-side stored procedures, recent BFT databases (e.g., Basil, Pesto) let clients — typically front-end servers — execute application logic locally, interleaving ordinary reads/writes with business logic, and submit only the resulting operations to the replicated backend.

Replicas enforce ordering and isolation over those operations, but they never see — and can't check — the application code that produced them.

Now you're ready: this is the exact boundary in Figure 1 of the paper — app execution happens entirely outside the trusted replicated core.
4Interactive transactions▾

An interactive transaction interleaves database requests with client-side computation — read a value, compute on it, decide the next read, write a result — rather than being submitted as one opaque, precompiled stored procedure.

This is what makes client-side execution developer-friendly (ordinary code, ordinary languages) but also what makes validating it hard: you can't just replay a static SQL string, you have to re-run real logic.

Now you're ready: Sintr's validators literally re-execute this interleaved logic, step for step, alongside the initiating client.
5Byzantine clients and per-object fault bounds▾

A Byzantine participant may deviate from the protocol arbitrarily — lie, omit, collude — subject only to being unable to break cryptography. A coarse-grained way to handle this would be a single, system-wide bound on how many clients may be simultaneously Byzantine and colluding — but Sintr deliberately avoids that. Instead it adopts a transaction-centric fault model: each object carries its own bound on how much collusion it can tolerate, so different objects can be protected to different degrees.

This is reasonable because, unlike anonymous end users, Sintr's clients are typically front-end servers run by the participating organizations themselves, and are individually authenticated.

Now you're ready: "tolerating up to x Byzantine clients" (a policy of P-x) means: even if x clients collude against one object, they can't corrupt it — a per-object bound, not a system-wide one.
6Signatures, quorums, and proofs of correctness▾

BFT systems authenticate messages with digital signatures and often require a quorum of matching, signed replica replies before a client trusts a result — that quorum itself is a portable "proof" the result is correct.

HMACs (keyed hashes) offer similar authenticity more cheaply between parties who share a secret.

Now you're ready: Sintr forwards database results between clients bundled with exactly this kind of proof, so a validator never has to blindly trust the initiating client.
7Optimistic concurrency control (OCC), briefly▾

Under OCC, a transaction reads and computes freely, then at commit time the system checks whether anything it read was concurrently overwritten. If so, it aborts and (usually) retries; otherwise it commits.

This "execute now, validate at the end" pattern is a natural fit for interactive transactions, since the full read/write set often isn't known until execution finishes.

Now you're ready: Sintr's governance transactions (policy changes) are illustrated using OCC-style conflict checks against regular transactions' implicit policy reads.
8Information-flow control and noninterference, in one sentence▾

Information-flow control tags data with a sensitivity/integrity label and restricts how labels may mix. Noninterference is the property that low-integrity data must not be able to influence high-integrity outputs, undetected.

Classic IFC systems (Biba, JFlow, Fabric) enforce this in programming languages or storage layers to stop untrusted input from silently corrupting trusted state.

Now you're ready: Sintr repurposes this idea at the object level — a low-policy object can't quietly influence a write to a high-policy object unless explicitly "lifted."
9Why "just add stronger DB constraints" doesn't work▾

Databases already support integrity constraints (non-negative balances, foreign keys). It's tempting to think these could catch invalid transactions. But checking that a transaction's execution was correct — e.g., that a payment's debit equals its credit — generally requires knowing the transaction's inputs and re-deriving its outputs, which is equivalent to re-executing the transaction.

Now you're ready: this is precisely why Sintr chose redundant re-execution instead of trying to encode correctness as a database constraint.
The whole story in one place

Sintr in a nutshell

The problem, the fix, and how the pieces connect.

Client-centric BFT databases let clients execute application logic locally, then submit only the resulting reads/writes to a replicated backend that enforces ordering and isolation (e.g., serializability). This is fast and developer-friendly — but it moves application execution outside the trusted replicated core. The backend can verify that a transaction's operations are consistent with some valid ordering; it has no way to verify those operations came from a faithful execution of the application's actual logic. A Byzantine client can therefore submit a serializable transaction that is nonetheless semantically wrong — the paper's running example: a Payment transaction that debits Alice $50 but silently credits a warehouse $100.

Sintr restores this lost guarantee — application execution validity — without giving up client-side execution. Its mechanism: before a transaction's writes are accepted, other validation clients must independently re-execute the same transaction, over the same forwarded (and proof-backed) database reads, and produce a matching cryptographic hash of the outcome. These matching endorsements are the transaction's proof of honesty. To avoid paying this cost uniformly, Sintr lets applications assign each database object an integrity policy — a required endorsement count — so cheap, low-stakes data can stay fast while sensitive data (e.g., account balances) demands more corroboration.

Because objects with different policies can interact within one transaction, Sintr borrows noninterference from information-flow control: a transaction may not let a weakly-protected read silently influence a strongly-protected write, unless the application explicitly lifts that read's effective policy after validating it. Policies themselves are versioned, first-class data, updated through ordinary governance transactions that participate in the same concurrency control as everything else.

The payoff: retrofit onto Basil, Pesto, and SMR systems atop HotStuff/BFT-SMaRt, across TPC-C, SEATS, and Smallbank, Sintr costs just 3%–16% throughput and 3%–21% latency — for a guarantee those systems previously had none of.

🔏 Key takeaways

  • Client-centric BFT databases enforce isolation over client operations, but never validate the application logic that produced them.
  • A serializable transaction can still be an invalid one — the gap Sintr calls application execution validity.
  • Sintr's fix: other clients re-execute the same transaction and must produce a matching hash, or the transaction can't commit.
  • Integrity policies (P-x) let each object demand a different number of endorsements — pay for safety where it matters.
  • Noninterference (with optional, explicit lifting) stops low-policy data from silently laundering into high-policy writes.
  • Governance transactions update policies at runtime, atomically and without halting the system.
  • Result: 3–16% throughput / 3–21% latency overhead, retrofit onto four existing BFT systems.
Six everyday pictures

How to think about Sintr

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · Endorsement

A notarized signature

A single signature says "I signed this." A notarized one says "an independent party watched me sign this, and confirms it." Sintr treats a client's writes the same way: not just self-attested, but re-derived and confirmed by other clients who watched (re-executed) the same transaction. A write without enough independent confirmations never becomes official.

Where it breaks: a notary just watches; a Sintr validator actually redoes the entire computation from scratch — closer to a second accountant recomputing your taxes than a witness watching you sign.
Mechanism · Redundant execution

Two students re-solving the same problem

Give the same equation to two students separately; if both are honest and the problem is deterministic, they land on the same final number. If one "solver" cheated or made an error, their answer won't match — and you don't need to know how they got it wrong, just that it disagrees. Sintr's validators are exactly this: fed identical inputs, they either converge on the same transaction hash, or they don't.

Where it breaks: two students can debate an ambiguous problem; Sintr's transactions are defined to be deterministic precisely so there's never a legitimate reason for correct answers to differ.
Heterogeneous policy · Object-level trust

Insurance deductibles

Insurers don't apply one deductible to every claim — a scratched bumper and a totaled car warrant different scrutiny. Sintr's per-object policy works the same way: a low-value, easily-reconciled record (inventory counts) needs few endorsements; a customer's financial balance needs several. You pay for validation in proportion to what's actually at stake.

Where it breaks: deductibles are chosen once, per policy type; Sintr's policies are versioned data an application can change at runtime via governance transactions, mid-flight.
Noninterference · Lifting

Chain of custody, with a validated exception

Evidence from an uncontrolled source normally can't enter a trusted record untouched. But if a trusted process explicitly verifies it against something already trusted — matching a delivery log against a signed invoice — it can be "admitted" and treated as trusted from then on. Sintr's lift function is this admission step: a deterministic, application-defined check that promotes a low-policy read so it can safely influence a high-policy write.

Where it breaks: real chain-of-custody exceptions are often judged case-by-case; Sintr's lift functions must be fully deterministic and are evaluated identically by every validator, with no discretion.
Avoiding extra DB load · Forwarded proofs

Lecture notes with citations

You don't need to sit through the same lecture twice to trust a classmate's notes — if they cite chapter and page for each claim, you can verify those citations quickly without redoing their research. Validation clients never query the database themselves; the initiating client forwards each result plus a cryptographic proof, so validators can trust it without adding load to the backend or risking a second, possibly-different answer.

Where it breaks: a citation can be fabricated by a dishonest note-taker; Sintr's "citations" are BFT quorum proofs, cryptographically unforgeable, so this failure mode doesn't apply.
Governance · Versioned policy

Changing your insurance mid-term

When you raise your coverage mid-year, the new terms apply going forward — claims already filed under the old policy aren't retroactively judged by the new one. Sintr's governance transactions work identically: they atomically install a new policy version, and every transaction (before or after) is checked against whichever version was in force when it executed, tracked via ordinary concurrency control.

Where it breaks: insurers process a change over days; Sintr's policy change is a single serializable transaction, so the "old" and "new" worlds never overlap ambiguously — there's a precise commit point.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams you can read at a glance.

1 · The pitfall — isolation without execution validity

Classical SMR replicas execute application logic themselves, so they can enforce that committed state transitions are valid executions of approved commands. Client-centric BFT databases break this coupling: replicas store state and vote on operations, but clients execute the logic that produces those operations. The backend can enforce serializability over whatever reads/writes it's handed — it has no visibility into whether those reads/writes came from faithfully executing Payment(...), or from a Byzantine client inventing numbers.

🗂
The paper is careful to frame this as architectural, not implementation-specific: any BFT system that decouples client-driven computation from replicated agreement — quorum stores, client-driven storage, not just SMR — inherits the same blind spot.

2 · Defining the target — application execution validity

The paper formalizes an application as a fixed set of deterministic, interactive transactions T = {T₁,…,Tₙ}. A transaction is valid if it corresponds to a faithful execution of some Tᵢ ∈ T; an execution is valid if every non-read-only committed transaction in it is valid. This is the exact guarantee lost by client-centric architectures, and the one Sintr restores — deliberately leaving ordering, isolation, and input-validity as orthogonal, already-solved problems.

3 · The fault model — integrity policies

Rather than one system-wide Byzantine bound, Sintr adopts a transaction-centric fault model: every object carries an integrity policy p, meaning it's protected against up to p colluding Byzantine clients. To modify an object with policy p, the writer must collect p independent endorsements beyond its own. This is deliberately heterogeneous — a TPC-C-style application can set customer balances to P-5 while leaving inventory counts at P-1, paying validation cost only where the application semantics demand it.

4 · Endorsement collection — the client-side protocol

Sintr organizes endorsement collection around the natural phases of transaction execution.

💡
Why forward results instead of letting validators query the DB? Two reasons: it keeps backend load flat regardless of how many endorsements a policy requires, and it guarantees all clients compute over identical data — independent reads could otherwise return different (but individually valid) results and cause correct clients to diverge for no real reason.

5 · Commit-time checks — endorsement validation and information flow

At commit, replicas run two checks before voting, both derived purely from the commit message's declared read/write sets and endorsements — no replica ever re-executes application logic.

// Endorsement validation
E = { e in Endorsements : e.sig valid and e.hash == H_T }
for key in WriteSet:
    if |E| < GetPolicy(key): vote ABORT

// Policy information flow
P_T = max( GetPolicy(key) for key in WriteSet )
for key in ReadSet excluding lifted keys:
    if GetPolicy(key) < P_T: vote ABORT
⚠
Why the read-set check matters: without it, a transaction could satisfy endorsement counts on its writes while quietly basing those writes on a weakly-protected read — laundering low integrity into a high-integrity object even though the write itself looks properly endorsed.

6 · Try it — dialing endorsement strength (real TPC-C/Pesto numbers)

Every extra required endorsement means more clients must re-execute and more signatures must be checked at commit. Use the dial below — it plays back the paper's actual Pesto/TPC-C measurements (20 warehouses).

7 · Governance — policies as versioned, first-class data

Policy values live in a versioned policy store, itself ordinary replicated database state. Regular transactions implicitly "read" the policy id/version tied to each key they write; governance transactions write new policy versions. Standard OCC then detects conflicts bidirectionally: a regular transaction aborts if a governance transaction committed a newer policy version between its read and commit timestamps, and a governance transaction aborts if it collides with a regular transaction that implicitly depended on the version it's replacing — guaranteeing policy changes take effect atomically in the serialization order, with no window where a stale policy could be exploited.

🔏
Measured result: in a microbenchmark upgrading 10–90% of keys from P-1 to P-5 and back, governance transactions commit in under 5 ms, each client aborts at most one in-flight transaction per change, and throughput shifts immediately to the new policy's level without ever pausing execution.
Follow the numbers, step by step

Worked examples

Four traces carried all the way through, using the paper's own figures.

① Why a serializable Payment can still be invalid

Alice starts with $200, warehouse W1 with $10. A correct Payment transaction debits Alice $50 and credits W1 $50.

  1. Both clients read the same state: Alice = 200, W1 = 10 (forwarded with proofs, so no disagreement is possible here).
  2. Correct write to Alice: 200 − 50 = 150. Both the Byzantine initiator and the correct validator agree — this half of the transaction is trivially right.
  3. Correct write to W1 should be 10 + 50 = 60. The validator computes exactly this.
  4. The Byzantine initiator instead computes 10 + 100 = 110 — internally consistent, still serializable, still wrong.
  5. Hash comparison: H_T is computed over (tx-id, read-set excluding any lifted keys, write-set). Since the write sets differ (60 vs. 110), the hashes differ, the endorsement can never match, and the replica aborts at commit.
🔏
Insight: no replica ever needed to understand "Payment" semantics. The mismatch alone — produced purely by re-execution — is sufficient proof something was wrong.

② Reading the TPC-C overhead numbers (Pesto, P-1)

Base Pesto peaks at 1681 tx/s on TPC-C (20 warehouses); Pesto with P-1 peaks at 1471 tx/s.

  1. Absolute drop: 1681 − 1471 = 210 tx/s lost to one endorsement's worth of signature-verification and validation overhead.
  2. Relative drop: 210 ÷ 1681 = 0.1249 → ≈12.5%, matching the paper's reported figure exactly.
  3. Latency moves further: the paper reports +16.8% at the inflection point — latency is more sensitive than throughput here because Pesto is CPU-bound, and each added endorsement adds cryptographic work directly on the request's critical path.
  4. Contrast with P-2: throughput falls only a little further (1431 tx/s, ≈14.9% off baseline) while latency rises to +21.7% — confirming that most of the marginal cost per additional endorsement shows up as latency, not lost throughput.

③ Why the SMR baselines barely notice Sintr

Under TPC-C, Peloton-HS drops only 6.4% in throughput at P-1, and Peloton-Smart just 3.0% — versus Pesto's 12.5%.

  1. Identify the bottleneck: Pesto is CPU-bound — its baseline latency is already low, so added cryptographic work (endorsement checks) is a large fraction of total time per transaction.
  2. Peloton-SMR systems are dominated by consensus latency (ordering through HotStuff or BFT-SMaRt), which is already the largest cost per transaction.
  3. Adding Sintr's checks is a roughly fixed increment of work; as a fraction of a already-larger baseline latency, that increment shrinks proportionally.
  4. Takeaway: Sintr's absolute overhead is fairly stable across systems, but its relative overhead depends entirely on what the underlying system was already bottlenecked on — CPU-bound systems feel it more than consensus-bound ones.

④ What lifting actually buys you

In the TPC-C lifting experiment, financial tables are P-5, record-keeping tables are P-1, and Delivery uses a lift function. Lifting improves throughput by 11.6% over a uniform-P-5 deployment, and the paper states this recovers 43% of the throughput gained by an (unsafe) uniform-P-1 deployment.

  1. Set up the relationship: let G = uniform-P-1's throughput advantage over uniform-P-5, expressed as a percentage of uniform-P-5's throughput (the paper doesn't state G directly — this is a guide-derived estimate).
  2. Lifting's 11.6% gain is stated as 43% of that gap: 0.43 × G = 11.6%.
  3. Solve for G: G = 11.6% ÷ 0.43 ≈ 27% — under this reading, uniform-P-1 throughput is roughly 27% higher than uniform-P-5's in this workload. That's a relative percentage, not 27 additional percentage points.
  4. Interpretation: heterogeneous policy plus lifting recovers well under half of the unsafe configuration's speed advantage — but for zero loss of safety on the financial tables, which is the entire point: pay full price only where the application says it matters.
💡
The 11.6% and 43% figures are the paper's own; the ~27% gap is this guide's derived estimate assuming both percentages share the same P-5-relative denominator, not a number the paper states outright.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A transaction is serializable and every replica votes to commit it under standard BFT SMaRt-style consensus. Does that guarantee the transaction is valid in Sintr's sense?
Show answer
No. Serializability and consensus agreement only guarantee that the operations, as submitted, could have occurred in some valid ordering with no conflicting concurrent access. They say nothing about whether those operations are the outputs of a faithful execution of the intended application logic. That's exactly the gap Sintr closes with endorsements.Misconception: conflating "the database agreed on this" with "this is correct." Agreement is about ordering; validity is about application semantics — two different guarantees.
Problem 2 · medium
Object balance has policy P-3. An initiating client collects endorsements from exactly 3 other clients, but one of them is itself Byzantine and colludes with the initiator to sign a matching (wrong) hash. Does the transaction commit?
Show answer
Only if the remaining 2 correct endorsers also happen to compute the same wrong hash — which they won't, since they re-execute honestly from the same forwarded inputs. P-3 means the object is protected against up to 3 colluding Byzantine clients; a single colluding validator among several correct ones isn't enough by itself. The real risk model is: if 3 or fewer clients collude on a P-3 object, they still cannot forge a majority of matching honest-looking endorsements against correct validators' independently-computed hashes.Misconception: thinking "policy P-x" just counts endorsements without regard to who's honest. It's a bound on tolerated collusion; a scheme only fails if enough of the endorsers overall are colluding Byzantine clients (i.e., f_O ≤ p_O is violated).
Problem 3 · medium
Why can't a validation client just issue its own database reads instead of waiting for the initiating client to forward results?
Show answer
Two reasons. First, it would multiply backend load by the endorsement count for every transaction, undermining the whole point of keeping validation cheap. Second — and more subtly — without additional server-side support, two independent reads issued at different times could return different (but individually valid) results, causing correct clients' local execution to diverge for reasons that have nothing to do with Byzantine behavior. Forwarding guarantees everyone computes over identical inputs.Misconception: assuming "reading the database yourself" is always safer than trusting a forwarded value. Here, forwarding + a cryptographic correctness proof is strictly safer, because it also guarantees consistency across validators.
Problem 4 · hard
A Delivery-style transaction reads a P-1 "order" object and writes a P-5 "balance" object, with no lift function invoked. What happens at commit, and why?
Show answer
The replica's information-flow check computes P_T = max(policy of all written keys) = 5, then checks every non-lifted read has policy ≥ 5. The order object's policy is 1 < 5, so the check fails and the replica votes to abort — regardless of whether endorsement counts were satisfied. This is noninterference in action: a strongly-protected write cannot be silently influenced by weakly-protected data, even if the write itself gathered enough signatures.Misconception: assuming enough endorsements on the write alone are sufficient. Endorsement validation and information-flow validation are two independent checks — both must pass.
Problem 5 · medium
An initiating client underestimates its validation set |V| and, deep into an interactive transaction, writes a key requiring more endorsements than it anticipated. What's the cost, and when is it cheapest?
Show answer
The client must contact additional validators and wait for them to re-execute the transaction from the start. If this correction happens early in execution, the extra validators' work overlaps with the ongoing transaction and adds little end-to-end latency. The worst case is when the triggering write is the transaction's last operation — then the added cost is a full message round-trip plus the new validators' entire re-execution time, since there's no remaining work to overlap it with.Misconception: assuming underestimating |V| always costs "one extra round trip." The real cost scales with how late in execution the discovery happens — late surprises are expensive, early ones are nearly free.
Problem 6 · hard
A governance transaction G updates the policy for key balance from P-1 to P-5 at the same time a regular transaction T is in flight writing to balance under the old policy. Using OCC, which one aborts, and why is the conflict bidirectional?
Show answer
It depends on commit order, but the mechanism is symmetric: T implicitly "reads" the policy id/version of every key in its write set. If G commits between T's read and commit timestamps, T aborts (it was validated against a now-stale policy). Conversely, if T's implicit read is detected as concurrent with G's write to that same policy id, G itself aborts to avoid retroactively invalidating T's already-serialized dependency. The conflict must be checked in both directions — otherwise one side could silently commit against an inconsistent policy view.Misconception: assuming policy updates are somehow "outside" normal concurrency control. Sintr deliberately treats policies as ordinary versioned data so existing CC machinery (here, OCC) handles the conflict without any bespoke locking protocol.
Problem 7 · easy
Which of the paper's two Byzantine-client attacks — ignore-val (ignoring validation requests) or ddos (requesting endorsements from every client) — gets worse as per-transaction validation cost rises, and why?
Show answer
ddos. Under ignore-val, correct clients simply time out and contact 1–2 more validators — a small, roughly constant cost regardless of how expensive each validation is. Under ddos, Byzantine clients force correct clients to perform many extra (expensive) re-executions on their behalf; as the per-validation compute cost rises, this excess work increasingly delays the victim's own transaction processing — the paper measures up to a 25% throughput reduction at its highest simulated validation cost.Misconception: assuming all Byzantine misbehavior degrades performance equally. The two attacks scale completely differently with validation cost — one is nearly free to defend against, the other compounds.
Problem 8 · medium
Under a Zipfian (contended) YCSB workload, adding P-1 costs more throughput (−20.6%) than under a uniform (uncontended) workload (−15%), even though the raw cryptographic work per transaction is identical. Why?
Show answer
Endorsement checks add latency to each transaction's commit path. Under contention, that extra latency widens each transaction's window of exposure to conflicts, increasing abort rates — a knock-on cost that doesn't exist under the uncontended workload, where servers are simply CPU-bound and the added crypto work is the whole story. Contention amplifies any added latency into lost throughput, on top of the raw compute cost.Misconception: assuming overhead is a fixed property of "how much crypto work was added." The same fixed overhead can cost more or less throughput depending on whether the system is CPU-bound or contention-bound.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does an "endorsement" prove?▾
That an independent client, given the same transaction inputs and the same (proof-backed) database reads, deterministically computed the same read set, write set, and outcome as the initiating client. It's a signed hash over (tx-id, read-set, write-set), with any lifted keys excluded from the read set before hashing — matching hashes across enough validators is the proof.
Q2Doesn't re-executing every transaction multiple times destroy performance?▾
It would, uniformly. Sintr avoids this several ways: read-only transactions need no endorsements at all, since the paper's validity definition covers only non-read-only committed transactions; heterogeneous policies mean most low-stakes write objects need few or zero extra endorsements; and validators never touch the backend database, so redundant execution scales at the (independently scalable) client tier, not the replicated storage tier. Measured overhead across three benchmarks is 3–16% throughput, 3–21% latency.
Q3What stops a Byzantine initiating client from just forging endorsements?▾
Endorsements are individually signed by the validating client's private key. A Byzantine initiator can't fabricate another client's signature, and it can't reuse an old endorsement because each hash is bound to a unique transaction id and the specific read/write set — any tampering changes the hash and breaks the signature match.
Q4Why do validators need forwarded database results at all — can't they just trust the initiator's claimed reads?▾
No — trusting claimed reads would let a Byzantine initiator simply lie about what it read, then "correctly" compute a write from a fabricated input. Forwarded results are accompanied by BFT correctness proofs (e.g., a quorum of matching signed replica replies), so validators can verify a read is genuine without querying the database themselves.
Q5What is "lifting," in one sentence?▾
An explicit, deterministic, application-defined function that promotes a low-policy read's effective policy (for that transaction only) after validating it against trusted data — e.g., checking a low-policy order against a high-policy payment before letting the order influence a balance update.
Q6Can Byzantine clients ever break correctness, not just performance, under Sintr?▾
Not if the object's policy is set correctly: Theorem 1 guarantees that as long as the number of colluding Byzantine clients targeting an object doesn't exceed its policy, that object is only ever updated by validly-executed transactions. Byzantine clients can still degrade throughput/latency (Q7), but they can't corrupt data protected by a sufficient policy.
Q7So what CAN Byzantine clients still do under Sintr?▾
Degrade performance, not correctness. They may ignore validation requests (correct clients simply contact a few more validators, small cost) or request excessive endorsements from many peers at once (a mild denial-of-service, whose severity scales with how expensive validation is). Neither lets them commit an invalid transaction against a well-chosen policy.
Q8How does Sintr decide how many validators to contact if the write set isn't known yet?▾
The initiating client makes a best-effort estimate up front (optionally guided by application hints, e.g., "this transaction touches these tables"). If a later write turns out to need a stronger policy than anticipated, the client contacts additional validators mid-transaction — cheap if it happens early, costing up to one extra round trip if it happens at the very end.
Q9Are governance transactions themselves vulnerable to Byzantine clients?▾
By default, no more than any other transaction — they're subject to the endorsement requirements of the policies they modify, and applications can require even stronger rules (e.g., majority-of-all-clients) for governance specifically. They skip information-flow checks only because their effects are confined to policy metadata, not application data.
Q10Does Sintr require rewriting the underlying BFT database?▾
No — it's designed as a retrofit. The paper hardens four different existing systems (Basil, Pesto, and SMR over HotStuff and BFT-SMaRt) by layering endorsement collection at the client and adding commit-time checks at replicas, without changing the underlying concurrency control or consensus protocol.
Q11What's outside Sintr's scope?▾
The paper doesn't lay out an explicit future-work list — this is the guide's own reading of the system model. Sintr's guarantees are formalized over a fixed application transaction set with fixed policy-id-to-key mappings, and it deliberately treats input-validity (whether a transaction's parameters are themselves legitimate) as a separate, already-solved problem it doesn't attempt to address. Treat this as an inference about scope, not a paper-stated roadmap.
Q12Is Sintr a blockchain / smart-contract system?▾
No. Blockchains typically re-embed application logic inside replica-side execution (smart contracts), which is exactly the stored-procedure-style coupling Sintr's target architectures were designed to escape. Sintr keeps execution client-side and restores validity through redundant client-side re-execution instead.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
SintrThe paper's framework: validate interactive transactions via redundant client re-execution, enforced through per-object integrity policies.
Application execution validityThe formalized safety guarantee: every committed, non-read-only transaction is a faithful execution of a predefined application transaction.
Integrity policy (P-x)Per-object requirement that a write gather x independent endorsements; tolerates up to x colluding Byzantine clients on that object.
EndorsementA validator's signed hash over a transaction's (id, read-set, write-set) — lifted keys excluded from the read set before hashing — proving it independently re-executed and agreed with the outcome.
NoninterferenceThe requirement that objects only influence writes to objects of equal-or-lower policy — prevents laundering low integrity into high-integrity state.
LiftingAn explicit, deterministic, application-defined promotion of a read's effective policy after validating it, excluding it from noninterference for that transaction.
Governance transactionA transaction that updates policy values, itself versioned data subject to normal concurrency control.
Interactive transactionA transaction whose logic interleaves database requests with client-side computation, rather than one precompiled stored procedure.
Supporting terms
SMRState Machine Replication — replicas execute identical commands in identical order over their own state.
Client-centric BFT databaseArchitecture where clients execute application logic and submit only resulting reads/writes to a BFT-replicated backend.
Validation clientA client that re-executes a transaction on another client's behalf to produce an endorsement, without querying the database.
Fwd-ResThe message forwarding a database result plus its correctness proof from initiator to validators.
OCCOptimistic Concurrency Control — validate for conflicts at commit rather than locking up front; used to illustrate governance-transaction conflicts.
Policy information flow checkReplica-side check that every read's policy is ≥ the maximum policy among the transaction's writes (excluding lifted keys).
Write-set discoveryThe process of determining, possibly mid-execution, how many validators a transaction ultimately needs.
P-x notationShorthand throughout the evaluation for "policy requiring x endorsements besides the initiator."
