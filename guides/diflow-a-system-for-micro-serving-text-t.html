Scheduling the model, not the whole workflow

A text-to-image request runs a pipeline — text encoder, diffusion backbone, ControlNet, decoder. Existing servers bundle all of it into one opaque blob and scale, place, and schedule that blob as a unit. This is the plain-English story of DiFlow, a system that cuts the blob into independently schedulable model nodes.

📄 Yang, Li et al., "DiFlow: A System for Micro-Serving Text-to-Image Diffusion Workflows" · SOSP 2026 🖥️ GPU serving basics assumed — the primers cover them ⏱ ~25 min read
🧩

Make the MODEL the schedulable unit — not the WORKFLOW. Scale, share, and parallelize each one on its own merits.

1What a diffusion workflow actually is▾

A basic text-to-image request runs three models in sequence: a text encoder turns the prompt into embeddings; a diffusion model starts from random noise and iteratively "denoises" a latent tensor over many steps, conditioned on those embeddings; a VAE decoder turns the final latent into a pixel image.

Production workflows add adapters on top of this base pipeline to steer composition or style.

Now you're ready: DiFlow's whole argument is about how these several models — not one monolithic model — should be scheduled.
2Two kinds of adapters: ControlNet vs LoRA▾

ControlNet is a parallel-execution adapter: it runs alongside the base diffusion model at every denoising step, feeding intermediate feature maps into specific layers. It's roughly as large as the base model and needs GPU-to-GPU synchronization.

LoRA is a weight-patching adapter: it's fetched once and merged into the base model's weights before inference, adding no extra runtime compute — but it specializes that model replica to one request's style until the patch is removed.

Now you're ready: these two adapter types demand two different scheduling tricks — deferred data-fetch for ControlNet, patch-swap-aware sharing for LoRA (§4.3.2, §5.1).
3Monolithic serving — the default, and its four cracks▾

Systems like HuggingFace Diffusers treat an entire workflow — base model plus every adapter — as one opaque instance: provisioned, placed, and scaled together on a fixed set of GPUs.

This causes four problems: L1 coarse scaling (replicate everything to fix one bottleneck), L2 no model sharing across workflows, L3 no runtime visibility to tune per-model resources, L4 a workflow-wide failure domain.

Now you're ready: DiFlow is named after its fix — micro-serving instead of monolithic serving — and each design piece maps to one of L1–L4.
4Microservices, generally▾

A microservice architecture decomposes a large application into small, independently deployable components that communicate over well-defined interfaces, instead of one large program. Each component can be scaled, updated, and debugged on its own.

DiFlow applies this idea to diffusion inference: each model (not each workflow) becomes a microservice-like unit.

Now you're ready: the paper's central design choice — "workflow node" as the schedulable unit — is this microservices idea applied to GPU model inference.
5DAGs and graph compilation▾

A directed acyclic graph (DAG) represents a computation as nodes (units of work) and directed edges (data dependencies), with no cycles. Topologically sorting a DAG gives a valid execution order; nodes with no dependency between them can run in parallel.

A compiler here means: turn a high-level program (the workflow definition) into this executable graph, optionally rewriting it to apply optimizations.

Now you're ready: DiFlow's graph compiler turns a Python-composed workflow into a DAG of model nodes, then runs optimization passes (like approximate caching) as graph rewrites.
6GPU-direct data movement (NVSHMEM/RDMA)▾

Normally, moving data between two GPUs on different machines means: GPU → host CPU memory (PCIe) → network → remote host memory → remote GPU. Each hop adds latency and burns CPU/PCIe bandwidth.

GPU-direct / RDMA techniques let one GPU write directly into another GPU's memory over NVLink or the network, skipping host-memory staging entirely — "zero-copy." NVSHMEM is a library providing this as one-sided put/get operations.

Now you're ready: DiFlow's data engine is built on NVSHMEM specifically because diffusion tensors are large (gigabytes per workflow) and CPU staging would be too slow.
7Model parallelism: splitting one model across GPUs▾

When one model's inference is too slow on a single GPU, you can split the computation across several GPUs so they work on it concurrently. Two forms appear here: latent parallelism splits the two classifier-free-guidance passes across GPUs, requiring a "scatter-gather" sync every denoising step; ControlNet parallelism runs the ControlNet and base model on separate GPUs concurrently, exchanging feature maps mid-inference.

Now you're ready: DiFlow calls the first kind "intra-node" parallelism (splitting work inside one model's node) and the second "inter-node" parallelism (overlapping two different models' nodes).
8Scheduling basics: queues, batching, admission, SLOs▾

FCFS (first-come-first-served) processes requests in arrival order — simple, and easy to reason about. Batching groups several inference calls to the same model into one GPU pass for efficiency. Admission control rejects a request up front if the system predicts it can't be served in time, rather than letting it queue uselessly. SLO attainment is the fraction of all submitted requests (including rejected ones) that finish within their latency deadline.

Now you're ready: DiFlow's scheduler makes exactly these three kinds of decisions every cycle — batch/place, size parallelism, admit/reject (§5).
The whole story in one place

DiFlow in a nutshell

The problem, the fix, and how the pieces connect.

Text-to-image workflows are pipelines of several distinct models — a text encoder, a diffusion backbone, and adapters like ControlNet and LoRA. But existing servers, from HuggingFace Diffusers to ComfyUI, treat the entire pipeline as one opaque, monolithic instance: provisioned, placed, and scaled as a single black box. Since diffusion backbones are usually the sole bottleneck, and the full workflow is often 1.7×–4× larger than the base model alone, scaling the whole monolith to fix one hot model wastes enormous GPU memory and loading time — and precludes sharing a common backbone across the many workflows that reuse it.

DiFlow's fix is micro-serving: make the individual model, not the workflow, the unit of scheduling. A DSL and graph compiler turn a workflow into a DAG of independently schedulable workflow nodes, each wrapping one model's load/execute logic. A GPU-native distributed data engine built on NVSHMEM moves tensors directly between GPUs, with eager fetch (wait for the input) or deferred fetch (start now, fetch at the point of use) matched to each dependency's timing. A scheduler then exploits this decomposition three ways: it scales only the bottleneck model, it dispatches same-model requests from different workflows onto shared warm GPU replicas, and it adapts each model's parallelism degree to current cluster availability.

The payoff: across 12 workflows built from SD3, SD3.5-Large, Flux-Dev, and Flux-Schnell, DiFlow sustains up to 3× higher request rates, meets 6× more stringent SLOs, tolerates 8× burstier traffic, and needs up to 3× fewer GPUs for the same 90% SLO-attainment target — for under 150 ms of added overhead per request, on requests that themselves take 2–20 seconds.

🍯 Key takeaways

  • Monolithic serving scales, places, and shares at workflow granularity; DiFlow does all three at model granularity.
  • A Model base class standardizes load/execute logic; a Workflow DSL composes models with ordinary Python; a compiler lowers this to a DAG.
  • The data engine's eager/deferred fetch modes let dependent models start before their input is ready, when the paper's dataflow allows it.
  • The scheduler batches same-model nodes across workflows (sharing), right-sizes parallelism per batch, and admits/rejects by predicted SLO.
  • Result: up to 3× request rate, 8× burst tolerance, 3× fewer GPUs, <150 ms overhead, full compatibility with existing diffusion-specific optimizations.
Six everyday pictures

How to think about DiFlow

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Micro vs monolithic serving

Two food trucks vs one shared kitchen

Monolithic serving is like giving every customer their own fully-equipped food truck — grill, fryer, oven, cashier — even if they only want fries. Micro-serving is a shared kitchen: each station is staffed independently, and any order routes to whichever free grill or fryer can take it. DiFlow makes the model the station, not the whole truck.

Where it breaks: kitchen stations don't need "reloading" between orders. GPU model weights do — a station that doesn't already have the right model loaded pays real loading latency before it can help.
Model sharing · Cross-workflow reuse

Carpooling to overlapping destinations

Two commuters heading roughly the same way share one car instead of each driving separately. DiFlow's scheduler does this for models: when workflows A and B both invoke the same diffusion backbone, their requests are batched onto the same warm GPU replica, regardless of which workflow they came from.

Where it breaks: not every "car" fits every "rider." A LoRA-patched model replica is specialized to one style until the patch is removed — two riders wanting different styles can't share that particular ride without a patch swap first (§7.3).
Deferred data fetch · Timing

Starting the meal before dessert exists

A good waiter seats you and starts the appetizer immediately, ordering dessert only when you actually reach that course — you're not stuck waiting at the door until the whole meal is plated. This is deferred fetch: the Flux node starts inference right away and only fetches ControlNet's output at the exact layer that consumes it, instead of blocking on it up front.

Where it breaks: a real diner can chat while dessert is prepared. DiFlow's node can't improvise — if the ControlNet output isn't ready by the moment it's actually needed, that specific fetch call blocks until it arrives.
Adaptive parallelism · Right-sizing

Hiring temps for today's crowd, not every day

A restaurant that calls in extra cooks only when it's actually busy — and only as many as its kitchen can usefully use — beats one that always staffs for peak or always staffs for a slow Tuesday. DiFlow's scheduler sets each batch's GPU count to min(available GPUs, max useful degree), fresh every scheduling cycle.

Where it breaks: a temp cook can start mid-shift instantly; adding a GPU mid-request cannot — parallelism is chosen once, when the batch is dispatched, not adjusted while it's already running.
Admission control · Early rejection

A bouncer who does the math before you wait in line

Instead of letting everyone queue and disappointing them at the door, a good bouncer estimates whether you'll get in before doors close and turns you away immediately if not — saving you a wasted evening and keeping the line moving for those who'll actually make it. DiFlow's admission control estimates a new request's completion time from its remaining critical path and rejects it up front if it can't meet its SLO.

Where it breaks: the bouncer's estimate is only as good as the profiled latencies it's built from; under-profiled models could get requests wrongly admitted or wrongly turned away.
Fault isolation · Node granularity

A modular desk, not a welded frame

If one drawer of a modular desk breaks, you replace that drawer — the rest of the desk keeps working. DiFlow's node-level execution and immutable intermediate tensors give the same property: a failed node's downstream re-executes, but sibling nodes and unrelated workflows are untouched.

Where it breaks: the isolation is per-node, not per-GPU. If the executor (the "desk leg") holding several nodes goes down, everything it was hosting is lost together, and its coordinator must reassign all of it.
The full explanation

How it actually works

Component by component, from the programming model down to the scheduling loop.

1 · The problem, quantified

A full diffusion workflow's memory footprint is often 1.7×–4× larger than its base model alone. Under monolithic serving, scaling to relieve a bottleneck means replicating that entire footprint — Diffusers-based replication adds up to 80% extra loading latency and wastes up to 75% of GPU memory versus scaling only the bottlenecked model; vLLM-Omni and SGLang-Diffusion show similar 70–75% overheads. The other two costs — no cross-workflow sharing, and no runtime visibility for per-model tuning — compound this on production traces where a handful of backbones and ControlNets are reused across tens of thousands of distinct workflows.

2 · Programming model — Model class + Workflow DSL

Model developers subclass a Model base class and implement three methods: setup_io() (typed inputs/outputs), load(), and execute() — nothing about how the model plugs into a larger workflow. Workflow developers write ordinary Python: create model instances, call them, and let intermediate tensors flow between calls. Every call to a model automatically records a workflow node; the framework infers the DAG edges from the typed I/O each node declared.

🧩
This split is the whole trick: a model developer never has to reason about workflow composition, and a workflow developer never has to manually wire up nodes or transfers — both are derived by the framework.

3 · Graph compiler — DAG + optimization passes

The compiler resolves recorded model invocations into a topologically sorted DAG, recording for every edge its producer, consumer, and fetch mode (eager/deferred). It then applies graph-rewriting passes that pattern-match on node properties and insert, remove, or replace nodes — for example, swapping a random-noise-init node for a cache-lookup node (approximate caching), or inserting async-load-and-patch nodes around a LoRA-attached model (async LoRA loading). Adding a new optimization means writing a new pass, not touching the core compiler.

4 · Runtime & distributed data engine

At request time, the compiled DAG is instantiated once; root nodes are enqueued, and completed nodes unlock their downstream dependents until the workflow's output is returned. Because CUDA tensors dominate inter-node traffic (over 99% of transferred data; a single SDXL+ControlNet workflow moves 5.3 GiB), DiFlow avoids host-memory staging entirely: a per-executor local data store built on NVSHMEM provides GPU-direct, zero-copy transfers over NVLink/RDMA.

5 · Scheduler — three decisions every cycle

Given a ready queue ordered by FCFS (ties broken by shallower DAG depth), the scheduler pops the earliest node, then makes three decisions:

# 1. batch same-model nodes across workflows — this IS model sharing (§5.1)
Batch = {n_head} ∪ {n' in ready_queue | n'.model == n_head.model}[:B_max]

# 2. score each candidate executor and pick the top-k (§5.1, §5.2)
for e in available_executors:
    L_data  = CalcDataFetchLatency(Batch, e)
    L_load  = 0 if e already hosts n_head.model else CalcLoadTime(n_head.model)
    L_infer = CalcInferenceTime(Batch, e, k)
    e.score = L_data + L_load + L_infer
k = min(len(available_executors), k_max_for_model)   # adaptive parallelism
dispatch Batch to top-k lowest-scoring executors

# 3. admission control runs asynchronously, independent of the loop above (§5.3)
on new request arrival:
    est = sum(profiled latency of remaining DAG nodes) + queueing delay
    if est > request.SLO: reject immediately
    else: admit
💡
Why L_load = 0 matters: a model state table tracks which models are already resident on which executor, updated for free via node-completion piggybacking. Zeroing the load cost for warm executors is what naturally routes batches toward sharing — no separate "sharing policy" is needed.

6 · Compatibility with existing optimizations

Because optimizations are expressed as compiler passes or logic inside a node's execute(), DiFlow reproduces prior techniques without new machinery: approximate caching (Nirvana) becomes a cache-lookup node replacing random-noise init, recovering matching 1.13×/1.17× and 1.43×/1.42× speedups; asynchronous LoRA loading (Katz) becomes an async-load node plus a check node, cutting patch latency from 0.5 s to 0.05 s, matching the original implementation.

🔗
For the tiering-minded reader: the data engine's design — GPU-resident, one-sided, zero-copy transfers with an explicit eager/deferred consumption contract — parallels how CXL-attached or pooled memory systems separate "when is data placed" from "when is it consumed," letting a consumer start work before every input has physically arrived. DiFlow just applies that separation to inter-model tensor dependencies instead of inter-tier page placement.
Follow the numbers, step by step

Worked examples

Four calculations using the paper's own reported figures.

① Why full-workflow scaling wastes up to 75% of GPU memory

The paper states a workflow footprint can be up to 4× the base model's size alone, and that scaling the whole workflow "wastes up to 75% of GPU memory" versus scaling just the bottleneck. Let's derive that 75%.

  1. Take a base diffusion model at, say, 8 GiB (within the paper's reported 2–24 GiB range for these backbones).
  2. At the high end (4×), the full workflow — text encoder, diffusion model, decoder, adapters — weighs 8 × 4 = 32 GiB.
  3. Scaling only the bottleneck (the diffusion model) to add capacity costs 8 GiB. Scaling the whole workflow costs 32 GiB for the same added capacity.
  4. Wasted memory = 32 − 8 = 24 GiB, spent on components that weren't the bottleneck.
  5. As a fraction of the monolithic replica: 24 / 32 = 75% — exactly the paper's reported worst case (§2.2, L1).
🍯
Insight: the "up to 75%" isn't a rounded estimate — it falls directly out of "workflow can be 4× the base model" and "only the base model needed to scale." Model-granular scaling (§3.1) is what recovers this.

② What LoRA patch-swap sharing actually saves

The paper reports: a LoRA occupies 886 MiB and takes 100 ms to swap onto an already-loaded base model, versus 3.9 GiB and 430 ms to load a fresh SD3 model copy instead.

  1. Memory saved = 3.9 GiB − 886 MiB. Converting: 3.9 GiB = 3993.6 MiB, so savings = 3993.6 − 886 = 3107.6 MiB ≈ 3.03 GiB.
  2. As a percentage: 3107.6 / 3993.6 ≈ 77.8% less memory than loading a whole fresh SD3 replica.
  3. Latency saved = 430 ms − 100 ms = 330 ms.
  4. As a percentage: 330 / 430 ≈ 76.7% faster than a cold model load.
💡
This is why DiFlow shares base-model replicas across requests needing different LoRAs, rather than treating each patched model as its own unsharable instance: the patch itself is cheap; a whole new backbone copy is not.

③ Turning "1.3× faster" into a latency reduction

The paper reports adaptive parallelism accelerates average request serving by 1.3× versus a fixed Parallelism=1 policy, and 1.2× versus a fixed Parallelism=2 policy. What does that mean for actual latency?

  1. Let L₁ be the average latency under fixed Parallelism=1. "1.3× faster" means L₁ / L_adaptive = 1.3, so L_adaptive = L₁ / 1.3 ≈ 0.77 · L₁ — a 23% latency cut.
  2. Let L₂ be the average latency under fixed Parallelism=2. "1.2× faster" gives L_adaptive = L₂ / 1.2 ≈ 0.83 · L₂ — a 17% latency cut.
  3. Why isn't Parallelism=2 always best? Fixing 2 GPUs per request means later requests queue for an available GPU pair when the cluster is busy — visible as the "stepped" CDF in the paper's Figure 4-right.
  4. Adaptive avoids both failure modes: it uses 1 GPU when that's all that's free (beating fixed=2's queueing) and 2 when available (beating fixed=1's lack of speedup).
🍯
Insight: "1.3× faster" and "23% lower latency" describe the same result — the multiplier compares full latencies (L₁ vs L_adaptive), while the percentage describes the drop.

④ Admission control's 110× swing in setting S1

At the highest tested rate scale (RS=8) in setting S1, SLO attainment is 0.4% without admission control and 44% with it enabled.

  1. Improvement ratio = 44 / 0.4 = 110×.
  2. Why so large? Without admission control, an overloaded system keeps admitting requests it cannot possibly serve in time — they queue, consume resources, and still miss their SLO, dragging down every other request's chances too.
  3. The denominator still includes rejects — SLO attainment is computed over all submitted requests, so 44% isn't achieved by only counting the requests that were let in; rejected requests count as misses.
  4. This is feasible only under micro-serving: the estimate needs per-node progress visibility (which nodes of an inflight request have finished) that a monolithic black-box workflow simply doesn't expose.
💡
Compare this to the system's overall overhead: the maximum end-to-end micro-serving overhead measured is 150 ms, against workflows that take 2–20 s — between 0.75% and 7.5% of total runtime, negligible next to a 110× admission-control gain.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
DiFlow scales only the bottleneck diffusion model under load. Does that mean the text encoder and VAE decoder stop running, or get removed from GPU memory?
Show answer
No. Their existing loaded replicas keep serving requests — via model sharing, in fact — DiFlow simply doesn't create additional redundant copies of them the way monolithic replication would. "Scale only the bottleneck" means don't over-provision the non-bottleneck components, not that they disappear.Misconception: that per-model scaling means starving non-bottleneck models. It means not wastefully duplicating them.
Problem 2 · medium
Using the paper's low-end multiplier (workflow footprint = 1.7× the base model), and a base model of 8 GiB, compute the memory wasted by full-workflow scaling versus base-model-only scaling, and its percentage.
Show answer
Workflow footprint = 8 × 1.7 = 13.6 GiB. Wasted memory = 13.6 − 8 = 5.6 GiB. As a fraction: 5.6 / 13.6 ≈ 41.2% — notably less than the 75% high-end case, since a lighter adapter set means less non-bottleneck weight to needlessly duplicate.Misconception: that the "up to 75%" figure applies uniformly to every workflow. It's the ceiling, reached only at the heaviest adapter compositions (4×); lighter workflows waste proportionally less.
Problem 3 · medium
A model developer marks ControlNet's output as an eager input to Flux instead of deferred. What happens to inter-node parallelism between them?
Show answer
It disappears. Flux can no longer start until ControlNet's output is fully available, forcing the two nodes to run sequentially even though they were placed on separate executors. Marking the input deferred is exactly what lets Flux begin its early layers while ControlNet is still computing, recovering the overlap.Misconception: that placing two nodes on separate GPUs automatically parallelizes them. Placement enables concurrency; the fetch mode on the data dependency determines whether it's actually exploited.
Problem 4 · hard
Why does DiFlow run admission control asynchronously, outside the main scheduling loop, instead of checking every request's SLO feasibility inside the loop before dispatching?
Show answer
The scheduling loop's job is to dispatch already-admitted ready nodes as fast as possible every cycle; blocking it on a fresh admission estimate for every newly arriving request would add latency to the hot path for all in-flight work, not just the new arrival. Running admission control asynchronously lets it reject doomed requests early without slowing down the dispatch of nodes that are already progressing toward their deadlines.Misconception: that admission control and node dispatch are the same kind of decision. Admission control is a one-time, coarse-grained gate at arrival; dispatch is a per-cycle, fine-grained placement decision — coupling them would serialize unrelated work.
Problem 5 · medium
The scheduler uses FCFS with shallow-depth tie-breaking rather than a sophisticated priority policy. What does the paper trade away by doing this, and why is it a deliberate choice?
Show answer
It trades away the extra gains a priority-aware or SLO-aware scheduling policy (like those in prior multi-model serving work) could add on top. It's deliberate because using the simplest possible ordering isolates the performance gains attributable to micro-serving itself (model-granular scaling, sharing, adaptive parallelism) from gains a smarter policy might separately contribute — and because the scheduler is explicitly pluggable, so such policies remain compatible, just orthogonal to the paper's contribution.Misconception: that FCFS is used because it's necessarily optimal. It's used because it's a clean, low-overhead baseline that doesn't need global optimization or future-arrival knowledge — not because more sophisticated policies wouldn't help further.
Problem 6 · easy
Model sharing's SLO-attainment benefit grows from a modest gap at low request rates to a huge one at high rates (e.g. 86%→100% at RS=0.25 vs 22%→92% at RS=1.0 in the paper's Figure 10). Why does sharing help more as load increases?
Show answer
At low request rates there's little contention — even without sharing, models mostly aren't fighting over the same GPUs or paying repeated load costs, so attainment is already high either way. As the rate rises, workflows increasingly compete for GPUs; without sharing, each must separately re-load or wait for its own dedicated model copy, and that redundant loading cost compounds under contention. Sharing removes exactly that redundant cost, so its benefit is largest precisely when the system is most stressed.Misconception: that a mechanism's benefit is a fixed percentage independent of load. Model sharing's payoff scales with contention — it's most valuable exactly when you need it most.
Problem 7 · hard
DiFlow's node-level fault isolation limits a failure to "affected nodes and their lost inputs." Construct a scenario where a single executor failure still disrupts more than one workflow, despite this isolation.
Show answer
Because model sharing deliberately places nodes from different workflows onto the same warm executor, one executor can be hosting, say, the shared diffusion-model node for both Workflow A and Workflow B at once. If that executor fails, both workflows lose their in-flight diffusion-model node simultaneously — the failure domain is per-node, but a node that's serving multiple workflows' requests (via batching/sharing) means the executor failure's blast radius spans those workflows too. Recovery still only re-executes the affected nodes (not entire workflows), but "affected" can span multiple workflows when sharing is active.Misconception: that node-level isolation means "one workflow" isolation. The isolation boundary is the node/executor, and because sharing intentionally colocates different workflows' nodes, a shared node's failure can touch several workflows at once — narrower than monolithic (whole-workflow) failure, but not single-workflow-narrow.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What's the actual unit DiFlow schedules — a GPU, a workflow, or something else?▾
A workflow node: one model invocation (e.g., "run this diffusion model on this batch") produced by the graph compiler. It's smaller than a whole workflow and larger than a raw kernel — the granularity chosen specifically because it's what can be independently scaled, placed, and shared.
Q2Why can't existing microservice or LLM-agent frameworks (Ray, Parrot) just be reused for this?▾
They target CPU-centric dataflow or autoregressive token generation, neither of which expresses diffusion-specific semantics: ControlNet feature maps consumed at specific layers mid-denoising, LoRA weight-patching that mutates model state, GPU-native tensor communication instead of host-memory dataflow, and diffusion-specific parallelism strategies. DiFlow's programming model, compiler, and data engine are built to carry these semantics end to end.
Q3How is "eager" fetch different from just a normal function call?▾
It isn't conceptually different — it's the default: a node can't begin executing until its eager inputs are physically present in its local data store. The distinction only matters because DiFlow also offers deferred fetch, where a node begins executing and fetches an input only when execution reaches the point that actually consumes it.
Q4Does model sharing mean two requests literally run inside the same GPU kernel call?▾
Often yes, in the common case: the scheduler batches same-model nodes from different workflows together (up to a profiled max batch size) and runs them as one inference call on a shared executor. This is standard request batching, just applied across workflow identities rather than within one.
Q5What happens to a LoRA-patched model when it needs to serve a request with a different LoRA?▾
The scheduler triggers a patch swap: remove the current LoRA's weights, apply the new one. This is far cheaper than loading a whole fresh base model (§7.3) — reported at 886 MiB / 100 ms versus 3.9 GiB / 430 ms for SD3 — so patched replicas remain shareable across requests wanting different styles, just with a small swap cost.
Q6Is intra-node and inter-node parallelism the same mechanism?▾
No. Intra-node parallelism splits one model's computation (e.g., the two CFG passes) across several GPUs — it's a scheduler decision about how many executors to assign one batch. Inter-node parallelism overlaps two different models' nodes (e.g., ControlNet and Flux) that have no eager dependency between them, letting them run concurrently on separate executors.
Q7Does DiFlow change what image comes out, compared to running the same workflow monolithically?▾
No — the paper explicitly verifies computational equivalence: DiFlow and Diffusers produce identical images for identical inputs. DiFlow only changes how model executions are scheduled and where tensors move, not the underlying diffusion computation.
Q8How does the system scale beyond one coordinator as the cluster grows?▾
Executors are sharded across multiple coordinators, each managing a disjoint subset of workflows chosen to preserve model-sharing opportunities within a shard. A cluster management service handles coordinator discovery and failure detection; an executor failure triggers reassignment of just its affected nodes, not a full workflow restart.
Q9Is the micro-serving overhead (extra communication, coordination) actually negligible?▾
Measured end-to-end overhead tops out at 150 ms against workflows that take 2–20 s to complete (0.75–7.5% of runtime). At 256-GPU simulated scale with 500 in-flight requests, the coordinator itself accounts for only 2.7–3.4% of execution time for the two largest-DAG workflow families tested.
Q10What's explicitly left for future work?▾
The paper does not target long-horizon global replica placement — it makes online decisions from current executor state and per-model profiles. A complementary global planner forecasting demand over longer horizons (as explored for LLM serving and omni-modal workflow serving) is noted as an open problem for shared, adapter-rich diffusion workflows specifically.

Workflow nodeThe unit of scheduling: one model invocation, with typed inputs/outputs, produced by compiling a workflow.

Graph compilerLowers a composed workflow into a topologically sorted DAG of nodes and applies optimization-rewrite passes.
Distributed data enginePer-executor local data stores over NVSHMEM providing GPU-direct, zero-copy tensor transfers between nodes.
Eager / deferred fetchEager: input must be ready before a node starts. Deferred: node starts immediately, fetches the input at first use.
Model sharingDispatching same-model nodes from different workflows onto the same warm-loaded GPU replica, avoiding redundant loads.
Adaptive parallelismChoosing a batch's GPU parallelism degree at dispatch time as min(available executors, max useful degree).
SLO-aware admission controlEstimating a new request's completion time from remaining DAG latency and rejecting it early if it can't meet its deadline.
Model state tablePer-executor record of which models are currently resident in GPU memory, kept current via node-completion piggybacking.
Supporting terms
ControlNetA parallel-execution adapter, roughly base-model-sized, that feeds feature maps into specific layers during denoising.
LoRAA weight-patching adapter merged into base-model weights before inference; specializes a replica until unpatched.
Latent parallelismSplitting classifier-free guidance's two denoising passes across GPUs, with scatter-gather sync each step.
ControlNet parallelismRunning a ControlNet and the base model concurrently on separate GPUs, exchanging feature maps mid-inference.
NVSHMEMNVIDIA's GPU-side one-sided-communication library, used here for zero-copy tensor transfer over NVLink/RDMA.
FCFSFirst-come-first-served — the scheduler's base ordering, tie-broken by DAG depth.
SLO attainmentFraction of all submitted requests (including rejected ones) completed within their latency deadline.
Approximate cachingNirvana's optimization: initialize denoising from a cached similar image instead of random noise, cutting steps.
Async LoRA loadingKatz's optimization: overlap LoRA fetch with early base-model inference, then hot-patch when ready.
CV (coefficient of variation)Parameter controlling simulated traffic burstiness while holding the mean arrival rate fixed.
