SOSP 2026 · A Field Guide

One writer per word, one pair published at a time

Two hosts share a CXL memory device but not a coherent cache. Borges turns that constraint into a fast, fault-tolerant shared log — by never letting two writers touch the same word, and never showing a reader a commit that's half-published.

📄 "Borges" · Chen, Xiang, Jia, Sun, Kim, Witchel · SOSP '26 🎓 Assumes OS/mm background — the primers focus on shared-log & CXL specifics ⏱ ~30 min read
🔑

Give every shared metadata word exactly ONE writer, and publish a committed prefix only as a matching (global cut, index) PAIR — never one without the other.

Before you begin

Quick glossary — the acronyms you'll see everywhere

Defined once, up front, so the rest of the guide can move fast.

CXLCompute Express Link — a PCIe-based interconnect exposing byte-addressable, load/store-accessible memory across a small pod of hosts, at sub-microsecond latency but (in current prototypes) without inter-host cache coherence.
CMM-HSamsung's CXL Memory Module–Hybrid: a Type-3 CXL device with a 48GB DRAM cache (8-way, LRU) backed by NAND, presented to software as persistent memory on a CPU-less NUMA node. Measured at 583ns access latency.
mCASMemory-based compare-and-swap — the only demonstrated cross-host atomic on non-coherent CXL, implemented as a device-side operation (or, here, modeled as a cacheline flush + CPU CAS). Costs a device round trip per attempt: 2.3–2.7𝜇s at low contention, tens of 𝜇s under contention.
RCURead-Copy-Update — a synchronization style where readers see either the old or new version of a data structure, never a partial update, and a writer waits for old readers to finish before reclaiming. Borges reuses this pattern, without coherent hardware, to publish its index.
Global cutThe paper's name for the committed frontier: how many records from each shard are safely durable and ordered, as of one sequencing round.
Stream / shard / segmentA stream is one logical object's history; a shard is an independently replicated partition of the log a stream may span; a segment is a shard's fixed-size (2KB default) storage unit.
eADRPlatform-level "enhanced Asynchronous DRAM Refresh" — flushes dirty CPU cache lines to a persistent device on power loss, the first stage of CMM-H's two-stage durability.
YCSB / RetwisYCSB is a standard key-value workload generator (A–D: mixed/read-heavy/read-only/read-insert). Retwis is a Twitter-clone benchmark used here as a fault-tolerant, exactly-once workflow application.

Eight ideas the paper assumes you know

Not cache/coherence 101 — these are the shared-log and CXL-pod specifics the design hinges on.

Borges / CXL-native design CMM-H hardware dual-index / sequencer machinery network baselines (Scalog/Boki) & mCAS cost
1Shared logs: order-first vs. replication-first▾

A shared log gives distributed apps one abstraction — a fault-tolerant, totally ordered, append-only history — that unifies replication, coordination, and recovery. Order-first designs (CORFU, Delos) fix a record's global position before replicating it. Replication-first designs (Scalog, Boki) make a record durable first, then assign it a position by merging per-shard progress summaries ("local cuts") into a global order.

Now you're ready: Borges is replication-first, for the same reason Scalog is — ordering only already-durable records avoids holes from mid-flight client failures.
2CXL pods and the coherence gap▾

CXL lets several hosts load/store into one shared device — but current pod prototypes provide no inter-host hardware cache coherence. One host can hold a stale cached line until software explicitly flushes or bypasses it. This is unlike the single-host shared memory a tiering system like TPP or HeMem manages: there, coherence is free background hardware; here, across hosts, it's simply absent.

Now you're ready: every synchronization primitive that assumes coherent caches (POSIX locks, futexes, ordinary CAS) is unusable across hosts. Borges is built to route around this, not paper over it.
3mCAS: the one cross-host atomic, and its price▾

Absent coherence, an atomic read-modify-write must execute at the device. The only demonstrated primitive, mCAS, costs a device round trip per attempt — microseconds, not nanoseconds — and gets worse under contention (2.3𝜇s at 1 writer, 38.5𝜇s at 16, in the FPGA prototype Borges cites).

Now you're ready: Borges's central engineering bet is to avoid needing mCAS anywhere on the fast path, by giving every shared word a single writer instead.
4CMM-H's flat latency curve▾

CMM-H is a DRAM-cached, NAND-backed CXL device. Its latency stays under 590ns for working sets up to 32GB and rises only modestly (621–638ns) up to 512GB — i.e. it doesn't fall off a cliff once you exceed the DRAM cache, unlike a naive tiered-memory system might.

Now you're ready: this flat profile, plus built-in durability, is precisely what lets Borges put both hot metadata and durable log data on the same device.
5Streams, shards, and the placement tradeoff▾

A stream (one object's history) can be pinned to one shard — replay is local, but a hot stream creates a hotspot under skew — or spread across shards — load balances, but replay needs a remote read on a networked system.

Now you're ready: this is the exact tradeoff CXL lets Borges dissolve, because a "remote read" on CXL is just a local load.
6The publication problem: cut and index must match▾

The global cut says how much is committed; the index says which records are visible for replay. If the index advances ahead of the cut, readers see uncommitted data. If the cut is visible before the index is complete, readers can miss records or see them out of order.

Now you're ready: this pairing problem — invisible in networked designs because other hosts can't peek at a shard's storage — is the second core challenge Borges must solve for direct CXL visibility.
7RCU-style reader announcement▾

A reader announces which version of a data structure it's using in a shared slot; a writer builds the new version privately, swaps a single pointer, then waits until no reader still advertises the old version before reclaiming it. No locks, no per-access atomics — just an announce/wait discipline.

Now you're ready: Borges's dual-index publication is exactly this pattern, applied to a shared cut/index pair on non-coherent CXL memory using only ordinary loads/stores.
8Leases, for liveness without coherence▾

A lease is a time-bounded grant: "you may hold this role/resource until time T unless renewed." It lets a system detect failure and reclaim state without a live heartbeat channel, at the cost of waiting out the timeout.

Now you're ready: Borges uses leases to detect shard/sequencer failure and to bound how long a writer waits for a possibly-dead reader before retiring an old index — the liveness escape hatch for the RCU-style protocol.
The whole story in one place

Borges in a nutshell

The problem, the fix, and why it doesn't reduce to "just use a faster network."

Existing shared logs (Scalog, Boki) coordinate shard servers, sequencers, and replicas over the network. Even at >1M appends/s, that coordination — not storage — dominates latency: server-side communication is 51.0% of Scalog's and 40.1% of Boki's end-to-end append latency. CXL offers an alternative: byte-addressable shared memory at sub-microsecond access (583ns on the Samsung CMM-H device Borges targets), so a sequencer could read progress instead of waiting for a message, and any host could read another shard's committed data instead of fetching it remotely.

But porting a networked design onto CXL naively doesn't work, because current CXL pods have no inter-host cache coherence. The only cross-host atomic, mCAS, costs a device round trip (microseconds) per attempt and gets worse under contention — in Borges's Scalog-CXL baseline, lock acquisition alone eats 24.1% of end-to-end p99 latency. And making every shard's storage directly readable creates a new correctness problem: readers must see the global cut (what's committed) and the index (what's visible) as a consistent pair, or replay can omit, reorder, or over-expose records.

Borges's answer is two coupled mechanisms. Single-writer metadata: every shared word has exactly one writer, so all coordination uses plain loads/stores — no mCAS on the fast path. Dual-index publication: the sequencer builds a new index privately, then atomically publishes it with its matching global cut using an RCU-style reader-announcement protocol — so a reader never observes a mismatched pair. A third piece, byte-offset stream indexing, keeps the published index compact (one offset per stream per shard, not one entry per record) so cross-shard replay stays cheap even though streams can span shards freely.

The payoff: 2.87× lower append p99 latency and 2.16× higher throughput than Scalog-CXL; a linearizable lock 3.1×/13.7× faster (p50) than vScalog-CXL/Boki-CXL; under high skew, throughput drops only 2.1% (vs. ~30% for a single-shard-per-stream design); and Retwis, a fault-tolerant workflow app, sees 5.7×/22.5× lower p50 latency.

🔑 Key takeaways

  • Coordination cost, not storage cost, dominates existing shared-log latency — CXL only helps if the software is redesigned around it.
  • Single-writer metadata removes multi-host lock contention (and mCAS) from the fast path entirely.
  • Dual-index publication (front/back index + RCU-style pointer swap) guarantees every visible cut names a fully-built, matching index.
  • Byte-offset indexing lets a stream span shards for load balance, without per-record shared metadata.
  • The sequencer is effectively stateless — all its inputs/outputs already live in durable CXL memory — so recovery means "reinstate the role," not "replay a private log."
  • Result: 2.87× append p99, 2.16× throughput, 3.1–22.5× application-level latency gains, skew resilience within 2.1% of ideal.
Six everyday pictures

How to think about Borges

Each stands alone. Every card ends with where the picture stops being accurate.

Core mechanism · Single-writer metadata

Assigned mailboxes, not a shared whiteboard

A shared whiteboard needs a marker-passing protocol so two people don't scribble over each other — that's what mCAS/locks buy on non-coherent CXL, at a device round trip each time. Borges instead gives each fact its own mailbox with exactly one person allowed to write into it. Nobody ever needs to ask "can I write now?" — they just write.

Where it breaks: mailboxes only work if the fact genuinely has one natural owner. Two things that must change together atomically (the cut and its index) can't each get their own mailbox — that's why publication needs a second trick.
Publication · Dual-index / RCU

Printing the newspaper edition

A newspaper doesn't distribute page 3 the moment it's typeset — every page is bound into one edition, and only the finished, bound copy goes out. Borges's back index is the paste-up table: assembled privately. Only once it fully matches a global cut does the front-index pointer swap — readers only ever see a complete, bound "edition," never loose pages.

Where it breaks: a newspaper's readers don't hold up the print run. Here, a slow reader still advertising the old edition does make the writer wait (bounded by a lease) before recycling the old paste-up table.
The cost model · mCAS

Calling a courier for every high-five

On one coherent machine, two threads coordinating is like two people in the same room high-fiving — instant. Across non-coherent CXL hosts, an atomic update means calling a courier who drives to a central office, checks and updates a ledger, and drives back — every single time, and the line gets longer the more people call at once (2.3𝜇s → 38.5𝜇s from 1 to 16 concurrent writers).

Where it breaks: a courier is at least reliable. mCAS here is a performance model (flush + CPU CAS), not a real hardware primitive on CMM-H — Borges validates the model against a real FPGA implementation rather than deploying it.
Indexing · Byte offsets vs per-record

Chapter bookmarks, not a page-by-page index

Tracking every record globally is like publishing a page-level index for a whole library — accurate but huge, and expensive to keep current. Borges instead publishes one bookmark per stream per shard: "this stream's committed history in this shard reaches byte 192." Readers scan each shard-local stream from its segment-chain head up to that bookmark — often using cached object views to skip full replay — rather than needing per-record lookups.

Where it breaks: a bookmark only tells you how far, not in what order across shards — that's why replay still needs the sequence of global cuts to interleave streams correctly (see the "recipe cards" analogy below).
Replay across shards · Global cuts

Merging recipe cards from two cooks

Two cooks each keep their own numbered stack of recipe steps for a shared dish. A supervisor's checklist ("cook A's step 2 and cook B's step 1 are both done") tells you which combined step sequence is safe to serve. Global cuts are that checklist: each names how many steps from each shard are committed, so any host can deterministically reconstruct the same interleaved order.

Where it breaks: real cooks might reorder on a whim; shards can't. Borges relies on a fixed, deterministic tie-break (lexicographic shard order within a round) — without it, two hosts could reconstruct different "valid" orders from the same cuts.
Recovery · A stateless sequencer

A clock, not a diary keeper

A diary keeper who dies mid-entry leaves you guessing what they knew. A clock, if it stops, just needs to be re-read from the wall — the current time was never "inside" it. Borges's sequencer only ever consumes and produces metadata that's already durable in CXL memory, so a replacement doesn't reconstruct hidden state; it just re-reads the last published cut/index and resumes.

Where it breaks: a wall clock is trivially globally consistent; the sequencer's "current time" is a global cut that must itself have been fully, atomically published — the dual-index protocol is what makes the clock analogy hold.
The full explanation

How Borges actually works

The append path, the replay path, and the fault model, with the paper's own diagrams rebuilt for reading at a glance.

1 · Architecture — replication-first, CXL-resident

Borges follows Scalog/Boki's replication-first decomposition: shard servers in the data plane, one sequencer in the control plane. The difference is the substrate — servers communicate only through replicated CXL storage, not the network. Metadata is split into local (written by one shard, read by the sequencer: local cuts, stream deltas) and global (written only by the sequencer, read by all shards: the global cut, the global index). Every object is cache-line aligned and padded, so independently-updated objects never share a line — eliminating false sharing without needing coherence to do it.

2 · Why "take the minimum" matters

Each replication thread reports its own local cut. A higher value on one device might describe records present there but not yet on the other replica. Using those to advance the committed index would expose data that could be lost on failure — so the sequencer commits only the minimum across a shard's replicas, and reads stream deltas only up to that point (in Fig. 4's example, record r3 reached the primary but not the backup, so its delta waits).

3 · Dual-index publication

The sequencer maintains a front index (the only one readers may consult) and a back index (updated privately). After identifying a new safe prefix, it applies deltas to the back index, builds a global cut naming that back index, persists and checksums the cut on both devices, then swaps the front-index pointer, then advances the cut ring. This ordering is the whole invariant: a visible cut always names a fully-built, matching index.

# reader i, before consulting the index
def beforeRead():
    while True:
        index1 = load(index_ptr)
        store index1 INTO active[i]
        index2 = load(index_ptr)
        if index1 == index2: return index1
        store 0 INTO active[i]; backoff

# writer, installing a new index
def switchIndex(new_ptr, old_ptr):
    store new_ptr INTO index_ptr
    for each reader i:
        while load(active[i]) == old_ptr: backoff   # bounded by a lease
💡
Why not just update one shared index in place? A reader could observe it half-updated (unsafe), and the sequencer and readers would repeatedly contend on the same cache lines (expensive on non-coherent CXL). The RCU-style swap uses only non-temporal loads/stores on single-writer slots — no mCAS anywhere in this path.

4 · Replay — merging local order with global cuts

Replay needs only two inputs: each shard's committed byte boundary for a stream, and the sequence of global cuts. Everything else is reconstructed by scanning log data. A shard server reads the stream's byte-offset vector from the front index, then scans its local segment chain from head to committed tail — mostly sequential, a good fit for CXL-attached storage.

5 · Fault tolerance

The global cut is the sole source of truth. On sequencer failure, a replacement restarts from the last fully-replicated cut and reinstalls its named index — no private log to replay, because the sequencer never held private state. On shard-server failure, the replacement recovers its sequence number, delta cursor, and byte boundaries from the most recent cut; anything beyond it was never published, so it's safely discarded. On CXL device failure (with 𝑓+1 replicas), recovery scans the surviving global-cut log backward, skips torn tails via checksum, and treats the newest complete cut as authoritative.

Follow the numbers

Worked examples

Four calculations carried through with the paper's own measurements.

① Where do Borges's mean-path savings come from?

Table 3 gives mean-latency breakdowns for Borges (175μs) vs Scalog-CXL (442μs) — this is a different measurement from the 2.87× append p99 headline, which comes from Table 4. Isolate the coordination stages in the mean-path numbers to see where the architectural savings live.

  1. Replication: Borges 26μs vs Scalog-CXL 81μs → 81/26 ≈ 3.1× — matches the paper's reported figure.
  2. Sequencing (report local cut, no batch wait needed in Borges): Borges 13μs vs Scalog-CXL's batch-wait-for-entries (60μs) + report-local-cut (56μs) = 116μs → 116/13 ≈ 8.9×.
  3. Committing (update index 6 + write cut 13 + switch index 6 + receive cut 2 = 27μs) vs Scalog-CXL (batch-wait 51 + write cut 14 + receive cut 67 = 132μs) → 132/27 ≈ 4.9× — exactly the three multipliers the paper states.
  4. But Client I/O barely changes (105μs vs 102μs) — both go through the same Linux TCP/IP stack. It's 60% of Borges's own budget, meaning the server-side redesign, not the network, explains almost the entire gap.
🔑
Insight: these 3–9× component ratios explain where Borges's mean-path architectural savings come from (Table 3). They are not a decomposition of the 2.87× headline — that's a separate p99 end-to-end measurement (Table 4). Both tell the same architectural story (coordination stages, not client I/O, drive the gap), but don't expect the mean-path ratios to multiply out to exactly 2.87×.

② Is the mCAS performance model trustworthy?

Borges models mCAS as flush+CAS since CMM-H has no real hardware primitive. Check it against Cxlalloc's real FPGA implementation.

  1. At 1 writer: modeled p50/p99 = 2.7/3.2μs; FPGA hardware = 2.3/2.8μs. Difference = 0.4μs both times → 0.4/2.3 = 17% at p50, 0.4/2.8 ≈ 14% at p99, matching the paper's stated percentages.
  2. At 4 writers (the paper's max contention level): modeled 7.58/34.25μs vs FPGA 6.80/32.34μs → (7.58−6.80)/6.80 ≈ 11.5%, (34.25−32.34)/32.34 ≈ 5.9% — again matching.
  3. Why this matters: CMM-H's base access latency (583ns) is 63% higher than the FPGA's own memory (357ns), yet the modeled mCAS tracks the real hardware within ~6–17%. The model is conservative but not distorting the comparison.
💡
This validates using Scalog-CXL/Boki-CXL (which rely on mCAS-guarded locks) as fair baselines — their overhead isn't an artifact of an unrealistic mCAS model.

③ Quantifying skew resilience

Table 6: a Zipf counter workload, uniform → θ=0.99, 96 clients fixed.

  1. Borges throughput: 147.3K → 144.2K req/s. Drop = (147.3−144.2)/147.3 ≈ 2.1%.
  2. vScalog-CXL throughput: 60.4K → 42.0K req/s. Drop = (60.4−42.0)/60.4 ≈ 30.5% — matches the paper's "nearly 30%."
  3. Why: vScalog-CXL binds each stream to one shard, so the hot counter under skew all lands on one shard server — measured at 2.25× the CPU utilization of the other shard. Borges lets either shard append to and replay any counter, since committed records are directly readable from shared CXL memory, so load spreads naturally.
  4. Latency confirms it: at fixed 96 clients, going uniform → θ=0.99 raises vScalog-CXL's p50/p99 by 48.6%/30.0%, while Borges barely moves.
🔑
Insight: this is the direct payoff of dissolving the placement tradeoff from Primer 5 — flexible placement only pays off if cross-shard replay is cheap, and CXL is what makes it cheap.

④ Segment size: the fragmentation tradeoff

Segments are Borges's replay-sequential storage unit. What does the 256B→4KB range actually cost?

  1. Throughput: +45.1% going from 256B to 4KB segments (fewer allocations, fewer segment links on the fast path).
  2. Fragmentation at 4KB: 25.03MB wasted across 8.8K allocations → 25.03MB/8.8K ≈ 2.85KB wasted per allocation (≈19.58% of allocated space).
  3. Fragmentation at 256B: 18.30MB wasted across 382K allocations → 18.30MB/382K ≈ 48 bytes wasted per allocation (≈11.53% of allocated space) — far less waste per-op, but 43× more allocation operations.
  4. The chosen default, 2KB: yields 16.7% fragmentation — between the two extremes, favoring throughput over minimal waste.
💡
Larger segments trade a small, bounded amount of wasted space for a large reduction in allocation-path overhead — a classic space/time knob, tuned once and left alone rather than adapted dynamically.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it checks.

Problem 1 · easy
Two hosts both want to increment a shared "next sequence number" word on CXL. Why doesn't Borges use mCAS for this?
Show answer
Because Borges never lets two hosts share write-ownership of the same word in the first place. The word is restructured so exactly one writer (e.g., one shard server, or the sequencer) owns it, and everyone else only reads it. No contention means no need for an atomic RMW at all.Misconception: that "shared memory" implies "shared writers." Borges's core trick is to make the memory shared for reading while keeping writes exclusive.
Problem 2 · medium
Scalog-CXL — Scalog with server messages replaced by a CXL queue — is faster than Scalog-NET, but still far slower than Borges. Why doesn't swapping the transport close most of the gap?
Show answer
Scalog-CXL still uses Scalog's original metadata protocol, which assumes cheap shared-memory atomics: its enqueue/dequeue operations acquire locks via mCAS. Lock acquisition alone accounts for 15–16% of replication/sequencing/publication latency and 24.1% of end-to-end p99. Moving the same lock-based protocol onto a faster wire doesn't remove the lock's cost — it just makes the trip to acquire it slightly shorter.Misconception: that CXL's speed advantage is purely about bandwidth/latency of data movement. Here the dominant cost is synchronization semantics, which the transport alone can't fix.
Problem 3 · medium
Why does Borges maintain two copies of the index (front/back) instead of updating one index in place?
Show answer
Updating one shared index in place is unsafe (a reader could observe a partially-updated index mid-write) and expensive (the sequencer and readers would repeatedly contend for the same cache lines). Building the new state privately in a back index, then atomically swapping a single pointer only once it's complete, guarantees readers see either the fully-old or fully-new index — never a mix.Misconception: that "atomic" means "instant," so a single shared index updated carefully would be fine. The problem isn't speed, it's that a multi-field index update isn't a single atomic operation, and non-coherent CXL gives you no hardware help making it one.
Problem 4 · hard
Why does Borges deliberately allow a stream to span multiple shards, even though that makes replay logic more complex than pinning each stream to one shard?
Show answer
Pinning simplifies replay (it's always local) but recreates hotspots: a popular stream concentrates all its load on one shard server, exactly what vScalog-CXL suffers under skew (throughput drops ~30%). Because Borges makes cross-shard replay a direct CXL read rather than a remote RPC, the usual "replay locality vs. load balance" tradeoff mostly disappears — Borges gets the load-balancing benefit of spanning shards while keeping replay nearly as cheap as if it were local.Misconception: that replay complexity is a fixed cost you should always minimize. On CXL, the "expensive" cross-shard case (remote read) is cheap enough that the flexibility is worth the extra bookkeeping.
Problem 5 · medium
The paper calls the sequencer "effectively stateless." Does that mean it holds no data structures at runtime?
Show answer
No — at any moment it holds an in-progress back index, ring-buffer cursors, etc. "Stateless" means none of that state is the sole copy of anything durable: every input (local cuts, stream deltas) and output (published cut/index) already lives in durable CXL memory. So on failure, a replacement doesn't need to recover hidden private state — it just re-derives its working state from the last published cut.Misconception: equating "stateless" with "has no variables." It means "has no unique, unrecoverable state" — a subtler and more useful property for recovery.
Problem 6 · hard
Suppose the sequencer persisted and checksummed a global cut on both devices, then crashed before swapping the front-index pointer. What does a replacement sequencer do, and why is this safe?
Show answer
The replacement restarts from the last fully-replicated global cut in the persisted cut ring, and may retain a legally-ordered suffix of pending operations that were already durably replicated but never folded into a published cut. Because the pointer swap never happened, no reader could have observed the crashed cut as the current front index, and clients waiting on it were never acknowledged — but the replicated records it named aren't simply thrown away: they're still durable on both devices and get picked up again (and re-ordered if needed) by the next sequencing round.Misconception: that a persisted-but-unpublished cut is erased, as if it never happened. Only its role as the visible front-index boundary is redone; the underlying durable data survives and is folded into the next published cut.
Problem 7 · medium
Borges's default segment size is 2KB, even though 4KB segments give 45% higher throughput. Why not always use the largest segment size?
Show answer
Larger segments waste more space per allocation before a stream fills them (25.03MB / 19.58% fragmentation at 4KB, vs 18.30MB / 11.53% at 256B). The 2KB default is a deliberate middle point (16.7% fragmentation) trading some throughput for materially less wasted capacity — a fixed configuration knob, not something the paper claims is universally optimal.Misconception: that "faster" settings are strictly better. Every configuration choice in §4.8 (segment size, record size, shard count, replica count) is a tradeoff the authors characterize rather than a free win.
Problem 8 · easy
Borges uses one sequencer for a pod, while some networked shared logs scale sequencers across many nodes. Why doesn't a single sequencer bottleneck Borges?
Show answer
Prior systems scaled the sequencer mainly to amortize network communication cost, making sequencing itself a distributed problem. Borges's sequencer only ever does metadata work over shared CXL memory — a fixed-size summary per shard per round — so bursty request rates don't inflate its per-round CPU work. Measured up to 16 emulated shards, one five-core sequencer uses only ~40% CPU at 612K req/s.Misconception: that centralizing a control-plane role always creates a scaling bottleneck. It only does if that role's cost grows with request volume or requires network round-trips — neither is true here at pod scale.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is a "shared log," and why would a distributed system want one?▾
A fault-tolerant, totally-ordered, append-only history that every participant can read as a consistent prefix. It's a single abstraction that unifies replication, coordination, and recovery — instead of building each separately, apps just append and replay records.
Q2Why replication-first instead of order-first?▾
Order-first (CORFU-style) fixes a record's global position before it's durable, which can leave "holes" if a client fails mid-write. Replication-first (Scalog/Boki/Borges) only orders records that are already known to be durable everywhere, and removes per-record sequencer interaction from the append path.
Q3What breaks if you just run an existing shared log's client/server code with CXL swapped in for the network?▾
Two things: (1) synchronization primitives that assume coherent caches (POSIX locks, futexes, plain CAS) simply don't work across hosts without hardware coherence, so any lock-based coordination must fall back to an expensive mCAS device round trip; (2) making all storage directly host-visible creates a new correctness hazard — readers can see a shard's data mid-commit, before global order and durability are settled.
Q4What is single-writer metadata, concretely?▾
Every shared CXL-resident word is assigned exactly one writer (e.g., one specific replication thread, or the sequencer). Because no other party ever writes that word, reads and writes can use ordinary loads/stores — no locking, no atomic RMW, no mCAS.
Q5How does dual-index publication actually prevent inconsistent reads?▾
The sequencer builds a new index privately (the back index), persists a matching global cut on both devices with a checksum, and only then swaps the reader-visible front-index pointer using an RCU-style protocol where readers announce which index they're using. A reader therefore always sees a complete index that exactly matches the cut it's replaying against.
Q6Does allowing a stream to span shards make replay slow?▾
Not on CXL: a cross-shard read is a direct load from shared memory (measured at 10.1μs p99 in Borges), versus a remote RPC fetch on a networked system (673μs p50, >2.5ms p99 in the paper's Boki-CXL measurement). This is what lets Borges get load-balancing without the usual remote-replay penalty.
Q7Is Borges linearizable?▾
Yes. A write's linearization point is exactly when the sequencer publishes its matching cut/index pair; clients are acknowledged only after that. A read replays exactly the committed prefix named by the current published state, so it includes every prior completed write and excludes every unpublished one.
Q8What happens if a CXL device itself fails?▾
With 𝑓+1 device replicas, Borges tolerates up to 𝑓 failures. On a backup-only failure, service continues in degraded mode while a replacement rebuilds. On a primary failure, commits pause. Recovery scans the surviving global-cut log backward, skips any torn tail via checksum, and treats the newest complete cut as authoritative — every record named by that recovered cut had already reached both devices before the cut was published/selected; any records replicated beyond that cut are discarded.
Q9Is Borges forward-compatible with future CXL coherence (CXL 3.2)?▾
Yes, by design. Single-writer ownership and dual-index publication remain correct even with hardware coherence — an implementation could then use ordinary coherent loads/stores and drop the explicit cache management (clflushopt/sfence), but wouldn't need to change the protocol.
Q10How is this different from the CXL memory-tiering work (TPP, HeMem, Memtis, Pond) on transparently placing hot/cold pages?▾
Those systems manage where a single host's pages physically live across DRAM/CXL tiers, transparently to applications, using access-frequency signals. Borges instead treats a CXL pod's shared memory as a multi-host coordination and durability substrate for an explicit distributed-systems abstraction (a shared log) — the challenge isn't hot/cold classification, it's correctness under no inter-host coherence. They're complementary layers: a tiering system could sit underneath a CXL device Borges uses, invisible to Borges's protocol.
Q11What's left for future work?▾
The paper doesn't enumerate a separate future-work list, but positions Borges within a pod-scale (8–16 host), single-sequencer-per-pod design; scaling beyond that would follow Boki's logBook-style decomposition, with independent per-pod sequencers avoiding cross-pod coordination.

Glossary, results, and provenance

Every term in one place, the headline numbers, then what's paper fact vs. this guide's framing.

Core terms
Single-writer metadataEvery shared CXL word has exactly one designated writer, enabling coordination via plain loads/stores instead of cross-host atomics.
Dual-index publicationMaintaining a private back index and a reader-visible front index; the sequencer builds the new state privately and atomically swaps the front pointer only once it fully matches a persisted global cut.
Global cutThe authoritative record of the committed prefix: how many records from each shard are durable and ordered as of a sequencing round.
Local cutA shard-local, single-writer word reporting one replication thread's progress; the sequencer takes the minimum across a shard's replicas before trusting it.
Byte-offset indexingPublishing one committed byte boundary per stream per shard, instead of a per-record entry, keeping the shared index compact.
mCASMemory-based compare-and-swap; the only demonstrated cross-host atomic on non-coherent CXL, costing a device round trip per attempt.
Stream / shard / segmentA stream is one object's ordered history; a shard is an independently-replicated log partition a stream may span; a segment (2KB default) is a shard's fixed-size storage unit.
CMM-HSamsung's CXL Type-3 DRAM/SSD hybrid device: 48GB DRAM cache (8-way LRU) backed by NAND, 583ns measured latency.
Supporting terms
Order-first vs replication-firstOrder-first fixes global position before durability (CORFU/Delos); replication-first orders only already-durable records (Scalog/Boki/Borges).
LeaseA time-bounded ownership grant used to detect shard/sequencer failure and bound how long a writer waits for a possibly-dead reader.
eADRPlatform mechanism flushing dirty CPU cache lines to a persistent device on power loss — CMM-H's first durability stage.
vScalogA stream-aware Scalog variant that binds each stream to a single shard — the paper's baseline for the "replay-local but hotspot-prone" design point.
-CXL / -NET suffixPaper's naming for baseline variants: "-NET" keeps original network messaging; "-CXL" replaces server-side messages with a CXL-resident queue, isolating transport from software-design effects.
Reconfiguration epochA monotonically increasing tag on cluster configuration changes, embedded in the next published global cut so membership changes reuse the same atomic publication boundary as ordinary data.
