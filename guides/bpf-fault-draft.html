Handling a page fault where it happens, not by relaying it to userspace

userfaultfd hands every fault to a separate thread across four extra kernel crossings, plus scheduling and IPI overhead. bpf_fault runs the handler as an eBPF program, right where the fault fired, in the faulting thread itself.

📄 Zussman, Dey, Zengin, Fang, Hildenbrand, Cidon · SOSP '26 🎓 Some eBPF/mm basics assumed — the primers cover them ⏱ ~25 min read
🧩

RESOLVE the fault in-kernel, in the faulting thread — don't RELAY it to a separate userspace thread and pay for the round trip.
Same fault types uffd handles, minus the four extra kernel crossings and the scheduling/IPI overhead.

Quick glossary

1What a page fault actually is▾

A page fault traps into the kernel whenever the processor hits a PTE that's non-present or whose permissions don't allow the access. The kernel looks up the faulting address in the process's VMA tree, then decides which of three things happened: a major fault (page isn't in memory — allocate or read it), a minor fault (page is in memory but not mapped into this process), or a protection fault (page is present but the access violates its permissions, most commonly a write to a COW page).

Now you're ready: both uffd and bpf_fault are just different ways of letting an application customize what happens once the kernel has decided which of these three cases applies.
2VMAs and page tables▾

A process's address space is a tree of VMAs, each a contiguous range with uniform permissions, backing store, and — relevantly — the same uffd or bpf_fault handler. Registering a handler on part of a range can split a VMA; unregistering can merge them back. Underneath, page tables translate virtual to physical addresses; unused hardware bits in each PTE are repurposed by Linux for bookkeeping, such as marking a page "uffd write-protected."

Now you're ready: bpf_fault reuses the exact same VMA and PTE-bit infrastructure as uffd (it adds a new VM_BPF_FAULT flag but no new per-VMA fields), which is why it can share so much existing kernel machinery.
3userfaultfd, the old way▾

uffd lets an application register an address range and spin up a dedicated handler thread that polls a file descriptor. When another thread faults in that range, the kernel blocks it, enqueues a message, and wakes the handler thread — which resolves the fault via an ioctl (e.g. UFFDIO_COPY) and the kernel installs the PTE. This works, but every fault pays for a message enqueue, a thread wakeup, and (at least) four extra syscall crossings on the critical path.

Now you're ready: that "wake a separate thread and round-trip through syscalls" pattern is exactly what bpf_fault eliminates by running the handler in the faulting thread itself.
4eBPF and the verifier▾

eBPF lets userspace-supplied programs run inside the kernel, but only after a static verifier proves they're memory-safe and terminate in bounded time (no unbounded loops, no out-of-bounds accesses). This is what makes it safe to run a verifier-checked handler on the kernel's most sensitive path — the page fault handler — without risking a kernel crash or hang; the tradeoff is that the handler can't run arbitrary logic — it's constrained by the verifier and by which kfuncs are exposed, and currently can't issue arbitrary syscalls or I/O the way a uffd userspace handler can.

Now you're ready: bpf_fault's safety story rests heavily on this bounded-execution guarantee. Separately, fault handlers are also non-sleepable by default — a deliberate policy choice, not itself a verifier check — which closes off the kind of unbounded blocking uffd handlers are prone to.
5struct_ops — eBPF as a kernel callback table▾

struct_ops lets userspace attach a whole set of eBPF programs as a struct of function pointers that the kernel calls directly — no message queue, no polling thread. sched_ext uses it for CPU schedulers, cache_ext for page-cache eviction policies, and bpf_fault uses it for page-fault callbacks (handle_missing_fault, handle_wp_fault, etc.).

Now you're ready: this is the concrete mechanism behind "run the handler in-kernel" — it's a callback, not a message.
6Context switches and IPIs — why they're expensive▾

Waking a sleeping thread on another core costs an inter-processor interrupt (IPI) plus a full context switch and scheduler decision — thousands of cycles, dwarfing the ~15-cycle cost of an ordinary cache hit. uffd's protocol requires exactly this: the faulting thread sleeps, an IPI wakes the handler thread, and later another IPI/context-switch wakes the faulting thread back up.

Now you're ready: the paper's instrumented breakdown (Fig. 2, revisited on the How It Works tab) attributes 43% of a single uffd fault's latency to exactly this scheduling/IPI cost.
7TOCTOU and why blocking kernel execution is dangerous▾

If a userspace handler can indefinitely delay a fault that originated inside the kernel (e.g. a kernel-mode read() that touches an unfaulted page), an attacker gets a wide timing window to race a security check against its use — a Time-Of-Check-To-Time-Of-Use exploit. uffd has had several CVEs built on exactly this pattern.

Now you're ready: this is why bpf_fault handlers are non-sleepable by default, and why unprivileged uffd is now disabled in modern distros and blocked by Docker/Podman.
8Relative relocations and dynamic linking cost▾

A dynamically linked binary's compile-time addresses must be patched ("relocated") to its actual load address. A relative relocation (R_RELATIVE) is the simple case — store load-address-plus-addend — but large position-independent binaries can have over a million of them, and Linux's linker applies every single one eagerly at startup, dirtying every page it touches.

Now you're ready: this is the cost bpf_fault's lazy dynamic linking use case (§5.2) attacks — deferring each relocation until the page is actually touched.
9Write barriers, compaction, and electric fences▾

Three more mm techniques the paper accelerates: generational GC needs a write barrier on every pointer store to find new cross-generation references; a compacting GC must intercept accesses to objects it's still moving; an electric fence memory debugger surrounds every allocation with an inaccessible guard page so an out-of-bounds access faults immediately instead of corrupting silently.

Now you're ready: all three can be recast as "do this expensive thing lazily, only on the page that's actually touched" — which is precisely what a cheap in-kernel fault handler enables.
10Why a memory-tiering researcher should care▾

Tiered-memory and far-memory systems (HeMem, ExtMem, Mira — all cited in this paper's related work) have long used uffd's missing-fault mode to intercept accesses and drive page placement across DRAM/NVM/CXL tiers, paying its per-fault overhead as a tax on every migration decision. bpf_fault's authors explicitly note that tiered-memory systems "could benefit from inspecting PTE bits [in-kernel] to support informed page placement" — something uffd's userspace-only handlers cannot do at all.

Now you're ready: read this less as "a faster userfaultfd" and more as "a fault-handling substrate a CXL/tiering hot-page tracker could be built on without uffd's latency floor."
The whole story in one place

bpf_fault in a nutshell

The problem, the mechanism, and what it unlocks.

uffd made custom page-fault handling possible in Linux, but its design offloads every fault to a dedicated userspace thread. Even a trivial decision — "should this page be zeroed?" — pays for a context switch, an IPI, and multiple syscall crossings. Under load, that single handler thread becomes a serializing bottleneck; the design also can't intercept general file-backed missing or minor faults — the kind needed for executable mappings — and it doesn't compose well with libraries that don't control when their host process forks.

bpf_fault fixes this by moving the handler into the kernel as an eBPF struct_ops program, invoked directly, in the faulting thread's own context, on the fault path. There is no handler thread, no message queue, no extra kernel-user crossing. The eBPF verifier's bounded-execution guarantee is what makes this safe: a buggy scheduler or cache policy degrades performance, but a buggy fault handler runs on the critical path of every memory access, so bpf_fault leans on the same safety net that makes sched_ext and cache_ext viable.

The result, measured directly against uffd: 2.8–6.7× lower fault latency, only 1.4× overhead versus the kernel's own default fault path, and linear scaling with faulting threads instead of uffd's single-handler bottleneck. bpf_fault also reaches use cases uffd structurally cannot: file-backed missing faults (needed for a dynamic linker) and safe kernel-originating fault handling (needed for a correct memory debugger).

🥇 Key takeaways

  • uffd's overhead is structural: a separate thread, a message queue, and extra kernel-user crossings — not something you can tune away.
  • bpf_fault replaces the handler thread with a handler callback, invoked in the faulting thread via eBPF struct_ops.
  • The eBPF verifier's bounded-execution guarantee is what makes an in-kernel, per-fault handler safe to ship.
  • bpf_fault extends fault handling to file-backed memory, which uffd's missing mode cannot touch.
  • Non-sleepable-by-default handlers close off uffd's classic TOCTOU attack pattern.
  • Four integrations — VM snapshots, lazy dynamic linking, GC compaction, memory debugging — show the same pattern winning in different domains.
  • Kernel changes: ~2,500 LoC total (1,750 mm, 750 eBPF/libbpf) — a targeted extension, not a rewrite.
Six everyday pictures

How to think about bpf_fault

Each stands alone. Every card ends with where the picture breaks down.

The core idea · Relay vs. one runner

A relay race vs. running it yourself

uffd is a relay race: the faulting thread hands off a baton (the fault message) to a second runner (the handler thread) who must be woken up, run the leg, and hand the baton back. bpf_fault is just running the leg yourself — no handoff, no second runner, no waiting for them to wake up.

Where it breaks: a relay lets the second runner do genuinely different things (read a network socket, run arbitrary syscalls) — bpf_fault's "runner" is verifier-constrained and currently can't do I/O, so some legs still need a real relay (§4.8).
Safety · The eBPF verifier

An airport security checkpoint

Before your bag reaches the plane, security proves it doesn't contain anything that could bring the flight down — bounded, checked, in advance. The eBPF verifier does the same to a fault handler before it's allowed onto the kernel's most sensitive path: no unbounded loops, no unsafe memory access, proven at load time, not discovered at runtime.

Where it breaks: security checks the bag once; the verifier's guarantees are static too — a sleepable handler that's technically bounded can still be slow in practice, which is why bpf_fault treats sleepable handlers as an explicit, rarer opt-in.
Overhead · No round-trip for trivial decisions

Calling a manager to approve a form

Imagine every routine decision — even "should this be zero-filled?" — required paging a manager and waiting for a reply. That's uffd: even trivial fault resolutions round-trip to userspace. bpf_fault is the front-desk clerk who's simply allowed to make the routine call on the spot.

Where it breaks: some decisions genuinely need the "manager" — e.g. reading data from a network socket during post-copy migration — and eBPF currently can't do that in-kernel (§4.8), so those cases still need a real round-trip.
Lazy dynamic linking · Defer the work

Translating a book page by page as you read it

Translating an entire novel before handing it over wastes effort on chapters the reader may never open. bpf_fault's lazy relocation instead translates (relocates) each page only the first time you actually turn to it — the rest of the "book" never gets touched, and never gets dirtied.

Where it breaks: per-page "translation" isn't free — the fault-time lookup (rbtree search + relocation table binary search) has its own cost, which is why Docker, whose startup touches almost every relocated page anyway, ends up slightly slower under this scheme.
Security · Non-sleepable by default

Leaving the front door open while you fetch help

If a fault handler can block indefinitely, it's like leaving your front door wide open while you run for help — an attacker gets an arbitrarily wide window to slip in and swap something while your defenses are down (a TOCTOU race). Non-sleepable handlers slam the door shut immediately: the handler runs, finishes, and the door closes, all in one uninterruptible instant.

Where it breaks: some legitimate use cases need to hold the door open briefly (e.g. allocating memory) — bpf_fault's opt-in sleepable mode allows this, but only for verifier-bounded, non-attacker-controlled waits, not an arbitrary blocking wait like uffd's.
GC compaction · Fault-driven renovation

Renovating rooms only as tenants walk in

Instead of renovating an entire building before anyone's allowed back in (stop-the-world compaction) or renovating every room in the background regardless of who's using it (uffd-driven concurrent compaction, paying a round-trip per room), bpf_fault's approach renovates — copies, compacts, relocates — a room exactly when, and only when, a tenant walks toward its door.

Where it breaks: on heaps where almost no rooms need renovating (xalan, lusearch: ~10 ms GC pauses already), the fixed per-collection setup cost of "being ready to renovate on demand" can outweigh the savings — bpf_fault loses slightly to stop-the-world there.
The full explanation

How it actually works

From the fault trap to the eBPF callback, with the paper's own overhead breakdown rebuilt as a diagram.

1 · The fault path, and where uffd spends its time

A fault traps into the kernel, which walks the VMA tree and the page tables to classify it (missing, minor, or protection). For a uffd-registered VMA, the kernel instead blocks the faulting thread and enqueues a message. The paper instruments this end-to-end for a single anonymous MISSING fault (Figure 2):

2 · bpf_fault's two-phase protocol

bpf_fault hooks the same fault sites as uffd, but replaces the message/thread protocol with a direct in-kernel callback, invoked synchronously in the faulting thread.

Phase 1 · Release & invoke
Release the per-VMA fault lock, allocate a page if needed, call the eBPF program directly — no other thread involved
→
Phase 2 · Re-lock & install
Re-acquire the VMA lock, validate it's still current, install the PTE — or deliver SIGBUS on a non-zero return

This mirrors uffd's basic protocol but strips out the event queue and the separate thread entirely. A missing-fault callback receives a freshly zeroed page it can write into directly (zero-copy); a WP callback receives a read-only mapping of the existing page; a minor-fault callback receives the existing page-cache folio. A zero return installs the page; non-zero delivers SIGBUS — a failure signal uffd has no equivalent for (a stuck uffd handler simply blocks the faulting thread forever).

bpf_fault also extends this path to file-backed mappings — populating the page cache first, then invoking the handler — which uffd's missing mode cannot do at all. This single extension is what makes the dynamic-linker use case possible, since executables are mapped file-backed.

3 · Fitting into existing mm machinery

bpf_fault deliberately reuses uffd's plumbing rather than duplicating it: it stores its fault context in the same per-VMA union field uffd uses (so a VMA can be registered with one or the other, never both), reuses uffd's existing WP PTE bit rather than consuming one of the scarce remaining software PTE bits, and reuses uffd's page-table routines for COPY/ZERO/WRITEPROTECT operations. The result is zero new per-VMA memory overhead. Like uffd, it disables a few incompatible optimizations on registered VMAs only — transparent huge pages, batched shmem allocation, and fault-around — because every page installation must pass through the handler.

4 · Security: bounded by construction

Because handlers are eBPF programs, the verifier guarantees bounded loops and memory-safe accesses at load time. By default, handlers are also non-sleepable — they run atomically and cannot be delayed — which closes off uffd's dominant vulnerability pattern: an attacker triggering a kernel-originating fault (e.g. via read()) while a userspace handler blocks indefinitely, freezing kernel state and widening a TOCTOU race window. bpf_fault supports opt-in sleepable handlers for use cases that genuinely need to block, but even then the verifier's bounded-loop guarantee and eBPF's bounded blocking primitives make mounting a uffd-style attack strictly harder, and a slow handler only delays the process that installed it — not other processes or the kernel.

Follow the numbers, step by step

Worked examples

Four traces through the paper's real measurements.

① Verifying the "2.8–6.7×" latency claim

Table 3 gives average fault latency (µs) for uffd and bpf_fault across three fault types. Does the abstract's range actually hold?

  1. Missing (anon): uffd 11.6 µs, bpf_fault 2.7 µs → 11.6 / 2.7 = 4.30×.
  2. Write-Protect: uffd 10.8 µs, bpf_fault 1.6 µs → 10.8 / 1.6 = 6.75× — the paper's upper bound (≈6.7×).
  3. Minor (shmem): uffd 10.3 µs, bpf_fault 3.7 µs → 10.3 / 3.7 = 2.78× — the paper's lower bound (≈2.8×).
  4. Why WP wins biggest: uffd's WP resolution needs an extra UFFDIO_WRITEPROTECT-lifting round-trip; bpf_fault clears the marker in-kernel with no extra crossing.
  5. Overhead vs. baseline: missing-write fault, bpf_fault 2.7 µs vs. kernel baseline 2.0 µs → 2.7/2.0 = 1.35× ≈ the abstract's "1.4×."
🥇
Insight: every number in the abstract's headline range is independently reproducible from Table 3 — none of it is a single cherry-picked case.

② Why uffd's scalability collapses under load

§3.2/§6.1 report thread-pool run times at 512 threads. What do the ratios actually say about where the bottleneck lives?

  1. Baseline kernel path: 0.3 ms (1 thread) → 17 ms (512 threads) = 57× longer. This is the unavoidable cost of more faults happening.
  2. uffd, single handler thread: 1.4 ms → 863 ms = 616× longer — roughly 616/57 ≈ 10.8× worse scaling than the baseline, because every fault still funnels through one serializing thread.
  3. Throwing 16 handler threads at it: only drops to 557 ms (a 35% reduction from 863 ms — the paper's "36%"), while burning 5× more CPU. More threads barely dents a fundamentally serial design.
  4. bpf_fault (Fig. 7), 512 threads: 25 ms — compare to uffd's 859 ms at the same point: 859/25 = 34.4× faster, matching the paper's "34× slower" for uffd.
  5. bpf_fault vs. baseline at 512 threads: 25/17 = 1.47× ≈ 1.5× — a small, constant eBPF-invocation tax, not a scalability problem.
💡
The gap between uffd and baseline grows with thread count (a bottleneck); the gap between bpf_fault and baseline stays roughly constant (an overhead). That distinction is the whole scalability story.

③ QEMU snapshot tail latency, end to end

Table 4 compares four QEMU snapshot modes on an 8 GB Redis VM. Trace the tradeoff.

  1. Synchronous: total 2.31 s, but the VM is fully paused for the whole snapshot — downtime = worst-case latency = 2.3–4.4 s. Unusable for latency-sensitive services.
  2. Background (uffd): downtime drops to 3–4 ms (huge win), but total time balloons to 3.33 s (1.5× longer than synchronous) because QEMU's single migration thread must both resolve faults and stream pages — uffd's overhead directly delays the snapshot itself.
  3. Background (bpf_fault): total time returns to 2.33 s — essentially matching synchronous — while keeping downtime at 3–4 ms.
  4. Worst-case request latency: uffd 124–142 ms vs. bpf_fault 6–7 ms → 142/7 = 20.3× lower, matching the paper's "20× lower worst-case latency."
  5. Conclusion: bpf_fault is the only mode here that gets uffd's low downtime and synchronous's fast total time, simultaneously.

④ Lazy relocation: why Chrome wins big and Docker loses a little

Table 2 and §6.3 give relocation counts and startup deltas per application. Work out why the same mechanism helps some apps and hurts another.

  1. Chrome has 1,075,978 relative relocations (99.1% of all its relocations, 78.8% of linker time) — the largest of the five apps studied. Deferring nearly all of them is where the biggest win lives.
  2. Startup: Chrome's --version completes in 20 ms with bpf_fault vs. 36 ms baseline → (36−20)/36 = 44% faster.
  3. Dirty memory: Chrome drops from roughly 200 MB to 100 MB of dirty pages on real workloads — the paper's headline "50%, or 95 MB" savings (measured across its actual workload mix, not the isolated startup case above).
  4. Beating the zygote: Chrome's own zygote optimization amortizes relocation cost across forked children but still shares 135 MB of proportional dirty memory (PSS_Dirty); bpf_fault needs no zygote at all and reaches 104 MB → (135−104)/135 = 23% lower, using a fully generic mechanism.
  5. Docker (120,231 relocations, 99.8% relative) is the one exception: Docker's Go-runtime startup touches nearly every relocated page immediately anyway, so deferring gains nothing — while every deferred relocation now pays a per-fault rbtree/binary-search lookup cost instead of being free at eager load time. Net effect: slightly slower startup.
🥇
Insight: the mechanism's win is proportional to how much of a binary's relocated pages are never touched at runtime — high for Chrome/Clang, near-zero for Docker.

Practice problems

Problem 1 · easy
A VMA is never registered with bpf_fault. How much extra latency does bpf_fault add to faults on that memory, and why?
Show answer
Effectively none. bpf_fault only diverts the fault path for VMAs explicitly marked with the VM_BPF_FAULT flag; it adds no new per-VMA fields for unregistered memory and no measurable overhead on the default fault path for everyone else.Misconception: that adding a kernel extensibility framework taxes all memory management. bpf_fault is designed to add no measurable overhead or new memory footprint to non-bpf_fault workloads.
Problem 2 · medium
Why can't uffd's missing mode be used to implement the lazy dynamic linker, even though missing faults are its most common mode?
Show answer
The dynamic linker maps shared libraries and executables as file-backed VMAs, and uffd's missing mode only supports anonymous and shmem memory — not general file-backed mappings. bpf_fault extends missing-fault handling to file-backed VMAs (populating the page cache, then invoking the handler), which is the specific extension that made this use case possible at all.Misconception: that this is purely a performance story. The paper is explicit that lazy relocation via uffd is "impossible," not just slower — it's an applicability gap, not an overhead one.
Problem 3 · medium
Using Table 3, compute the 99th-percentile latency improvement for write-protect faults, and say which single design choice explains most of it.
Show answer
p99 for WP: uffd 13.9 µs, bpf_fault 1.8 µs → 13.9/1.8 ≈ 7.7× — the paper's largest reported tail-latency improvement. The dominant cause is that lifting write-protection with uffd requires an additional ioctl round-trip beyond the basic fault-message protocol every other fault type also pays; bpf_fault clears the WP marker directly in the in-kernel handler with no extra crossing.Misconception: assuming all fault types improve by roughly the same factor. WP improves the most precisely because it has the most uffd-specific extra work to eliminate.
Problem 4 · hard
bpf_fault handlers are non-sleepable by default. Explain precisely what attack this closes off, and why an opt-in sleepable mode doesn't reopen it.
Show answer
The classic uffd exploit pattern: trigger a fault that originates inside the kernel (e.g. via a read() syscall touching an unfaulted page) while a userspace handler blocks indefinitely — freezing kernel execution in a known state and widening the timing window for a TOCTOU race elsewhere. A non-sleepable bpf_fault handler runs atomically to completion, so there is no window to freeze. Sleepable handlers reopen the ability to block, but the verifier still forbids unbounded loops, and the blocking primitives available to eBPF (like memory allocation) are themselves bounded and cannot wait on an attacker-controlled event — unlike uffd, where literally any handler logic, including waiting on attacker input, is possible.Misconception: that "sleepable" and "vulnerable to uffd-style TOCTOU" are the same thing. The vulnerability specifically requires an unbounded, attacker-controlled wait, which sleepable eBPF handlers structurally cannot express.
Problem 5 · medium
On the h2 GC benchmark, concurrent compaction with bpf_fault beats stop-the-world on both pause time and total runtime, but on lusearch and xalan it loses on runtime. What's different about those two benchmarks?
Show answer
xalan and lusearch already pause for only about 10 ms under stop-the-world compaction — there's very little pause time to save. But every collection, regardless of size, pays bpf_fault's fixed per-collection setup cost (mremap-based aliasing, metadata setup in the eBPF arena). At hundreds of collections, that fixed cost accumulates and outweighs the negligible pause savings, making bpf_fault worse on total runtime even though the underlying mechanism is sound. h2, by contrast, has large pauses (526 ms under STW) where the fixed setup cost is small relative to the compaction work it eliminates.Misconception: that a technique which wins on its best-case benchmark (h2) must win everywhere. The paper explicitly reports it does not beat stop-the-world on every workload — fixed per-invocation costs matter when the thing being amortized is small.
Problem 6 · hard
In the efency memory-debugger microbenchmarks, SIGBUS mode slightly beats bpf_fault on seq_malloc_free (every allocation touched) but loses by 4.7× on no_touch (nothing touched). Explain the mechanism behind both results.
Show answer
SIGBUS mode eagerly populates every allocated page at malloc() time via UFFDIO_COPY, so a valid access never faults at all — when every page really is touched (seq_malloc_free), that eager work is never wasted, and it avoids paying for any fault at runtime, edging out bpf_fault's per-fault cost. But on no_touch, where pages are allocated and freed without ever being dereferenced, all of that eager population is pure waste — SIGBUS pays the population cost regardless. bpf_fault instead populates lazily, on the first real access, so untouched allocations cost nothing.Misconception: that one efency mode is simply "better." The paper shows the two mechanisms trade off eager-vs-lazy cost, and bpf_fault dominates specifically because lazy population, unlike SIGBUS's, doesn't sacrifice correct interception of kernel-originating faults to achieve it.
Problem 7 · easy
A tiered-memory system wants to inspect PTE bits directly when deciding whether to migrate a page between DRAM and a slower tier. Why is this impossible with uffd but possible with bpf_fault?
Show answer
uffd handlers run entirely in userspace and have no access to kernel state such as raw PTE bits — they only see what the fault message protocol exposes. A bpf_fault handler is an eBPF program running inside the kernel's fault path, so it can (subject to the verifier and available kfuncs) inspect kernel-side state directly, which is exactly the gap the paper calls out for tiered-memory systems in §3.3.Misconception: that uffd's limitation here is just "slower" access to the same information. It's a hard visibility boundary — userspace handlers structurally cannot see kernel-internal PTE state at all.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is bpf_fault a replacement for userfaultfd?▾
Functionally it overlaps a lot — same fault types, similar registration model — but it trades uffd's generality (any userspace code, any syscall) for performance and safety (verifier-bounded eBPF, no I/O yet). The paper positions it as a better fit for the majority of uffd's existing use cases, while acknowledging it can't yet cover cases needing network I/O in the handler, like post-copy live migration.
Q2Why is running in the "faulting thread's context" the key idea?▾
Because it eliminates the need for a separate handler thread entirely. With uffd, resolving a fault always means waking a different thread, which costs a context switch and an IPI. With bpf_fault, the same thread that faulted runs the resolution logic itself, in-line, with no handoff.
Q3What stops a buggy or malicious eBPF fault handler from crashing the kernel?▾
The eBPF verifier, at load time: it proves the program has bounded execution (no unbounded loops) and only performs provably safe memory accesses (e.g. bounded writes to the page argument). Loading any eBPF program also requires CAP_BPF.
Q4Does bpf_fault support all the fault types uffd does?▾
Yes — missing and write-protect faults for anonymous memory, and missing, write-protect, and minor faults for shmem memory, matching what uffd already supports — and it goes further, adding missing and minor fault support for general file-backed mappings (e.g. executables), which uffd cannot handle at all.
Q5What happens on fork()?▾
With the BPF_FAULT_INHERIT flag, a forked child gets a lightweight inherited link (just a reference to the parent's struct_ops) rather than full link setup in the fork fast path; it can later promote this to a full link via BPF_FAULT_CLAIM if it needs to register its own region. A deduplication list ensures a fault context spanning multiple VMAs isn't duplicated per-VMA during fork.
Q6Can an eBPF fault handler read a file or the network to supply page content?▾
Not currently — this is the framework's most significant limitation (§4.8). The VM snapshot integration works around the file-write side by streaming pre-images to userspace via a ring buffer; the network-read side (needed for post-copy migration) is still blocked on eBPF socket-read support, which is under active development.
Q7Why does bpf_fault reuse so much of uffd's existing kernel infrastructure?▾
To keep the code and memory footprint small: it shares uffd's per-VMA context field, its WP PTE bit (a scarce resource on x86-64), and its page-table manipulation routines for COPY/ZERO/WRITEPROTECT, rather than duplicating complex PTE and TLB logic. The tradeoff is that a VMA can be registered with uffd or bpf_fault, but never both.
Q8Does bpf_fault help every application that currently uses uffd?▾
It helps the common case strongly, but not universally: applications whose I/O needs (network reads) or existing architecture depend on uffd's full userspace generality can't move over yet. And even within a supported use case, gains scale with how much work is actually being deferred or eliminated — Docker's dynamic linking startup, which touches almost every relocated page immediately, sees essentially no benefit.
Q9How big is the kernel-side change required?▾
About 2,500 lines of code: 1,750 in memory management, 750 in eBPF/libbpf — a targeted extension of the existing fault path and struct_ops infrastructure, not a new subsystem.
Q10Why does the paper implement a dynamic linker feature that seems unrelated to page faults at first glance?▾
Because relocation is fundamentally a "do this on first touch" problem: a relative relocation only needs to happen before a page's content is read, which is exactly what a page fault signals. Deferring the work to fault time — impossible with uffd due to its file-backed-memory and applicability limits (§3.3) — is a natural fit for bpf_fault's extended fault-handling reach.
Q11What did the paper leave for future work?▾
The main gaps are I/O from eBPF handlers (file writes, network reads/sends — UDP sending is already proposed, TCP is under discussion), which would unlock use cases like post-copy live migration entirely in-kernel. More broadly, the authors frame bpf_fault as an experimentation platform, expecting new fault-handling strategies (e.g. per-fault page-size selection, application-specific prefaulting) as eBPF's capabilities grow.

Glossary, results, and further reading

Every term in one place, then a path to go deeper.

Core terms
bpf_faultThe paper's mechanism: run page-fault handlers as eBPF struct_ops programs invoked directly in-kernel, in the faulting thread's context.
userfaultfd (uffd)Linux's 2015 syscall for offloading page-fault handling to a dedicated userspace thread via a message-queue protocol.
struct_opseBPF's mechanism for attaching a set of programs as a kernel-invoked callback table; also used by sched_ext and cache_ext.
Fault contextA refcounted kernel object tying a bpf_fault link's struct_ops to the (possibly multiple, non-contiguous) memory regions it manages.
Two-phase fault protocolbpf_fault's handling sequence: (1) release lock, allocate, invoke eBPF; (2) re-lock, validate, install PTE or deliver SIGBUS.
Lazy dynamic linkingDeferring ELF relative relocations from load time to first-touch page-fault time, enabled by bpf_fault's file-backed fault support.
Fault-based compactionA GC compaction design where pages are copied, compacted, and pointer-relocated on demand, inside the fault handler, rather than eagerly during a pause.
Electric fenceA memory debugger design that surrounds each allocation with an inaccessible guard page so out-of-bounds accesses fault immediately.
Supporting terms
Major / minor / protection faultThe three fault classes: page not in memory / page in memory but unmapped / access violates present-page permissions.
Write-protect (WP) faultA write to a page whose PTE is marked read-only — used for COW and, deliberately, for live-snapshot and GC dirty tracking.
Non-cooperative modeuffd mode where a separate monitor process handles faults on behalf of a target process — essential for checkpoint/restore (CRIU).
Sleepable / non-sleepable handlerWhether a bpf_fault handler may block. Non-sleepable is the default and closes off uffd's classic TOCTOU attack pattern.
Dynamic Set Sampling–style tradeoffsNot used in this paper — bpf_fault's cost model is per-fault latency and CPU, not a sampled statistical estimate.
Zygote processChrome's fork-based optimization that amortizes eager relocation cost across child processes by sharing already-relocated pages.
Concurrent compactionGC compaction that runs while mutator threads continue executing, intercepting accesses to not-yet-moved objects via faults.
PSS_DirtyProportional dirty-page memory accounting for sharing — used to compare bpf_fault's lazy relocation against Chrome's zygote fairly.

Extensible kernels: SPIN, Mach, Exokernel medium

Bershad et al. SOSP'95 · Rashid et al. 1987 · Engler et al. SOSP'95

SPIN's in-kernel, Modula-3 fault handlers are the closest historical precursor to bpf_fault's design; Mach's IPC-based pagers share uffd's round-trip overhead.

Virtual memory primitives for user programs easy

Appel & Li, ASPLOS'91

Catalogs the GC, object-store, and distributed-shared-memory use cases that motivate custom fault handling in the first place.

cache_ext: Customizing the page cache with eBPF medium

Zussman et al., SOSP'25

Same authors, same struct_ops pattern applied to page-cache eviction rather than fault handling — the closest sibling system.

HeMem / ExtMem / Mira medium

Raybuck et al. SOSP'21 · Jalalian et al. ATC'24 · Guo et al. SOSP'23

Tiered- and far-memory systems that already lean on uffd for page-placement decisions — the paper's own pointer to where bpf_fault's lower fault latency and PTE-bit visibility could matter for tiering.

Native relocations / page-in linking hard

Chromium docs · Kledzik, WWDC'22

How Windows (fixed load addresses, in-kernel lazy relocation) and Apple (Mach-O page-in linking) solved the same relocation-cost problem with OS/format changes bpf_fault avoids on Linux.
