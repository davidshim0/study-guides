Giving pages to the right tier, not just the nearest socket

Linux's page placement was built for DRAM-only NUMA, where "closer" always means "faster." Add a second, slower tier of memory and that assumption quietly breaks. This is the plain-English story of AutoTiering, the Linux page-management redesign that fixes it.

📄 Kim, Choe, Ahn · Ajou University · USENIX ATC'21 🎓 Assumes NUMA/Linux-mm background — primers focus on AutoTiering's own machinery ⏱ ~25 min read
🧭

When a page can't go where it "belongs," ask which TIER is faster before asking which SOCKET is closer.
Remote DRAM beats local DCPMM. Stock Linux's allocation fallback gets this backwards — and its dynamic promotion path often just gives up instead.

Before you begin

Quick glossary, then the paper's own machinery

This assumes you already know NUMA, DRAM, and Linux's mm basics. The glossary below is just the paper's acronyms; the primers cover only what's specific to AutoTiering — the fallback-path bug, the LAP scheme, and the latency-hiding trick.

Quick glossary
DCPMMIntel Optane DC Persistent Memory — the paper's lower-tier SCM, denser but slower than DRAM, byte-addressable, DIMM-installable.
SCMStorage-Class Memory — the general category DCPMM belongs to; bridges the DRAM–SSD performance/density gap.
Upper-/lower-tierThis paper's terms for "fast" (DRAM) and "slow" (DCPMM) memory, cutting across the usual local/remote NUMA axis.
AutoNUMAStock Linux facility that periodically unmaps pages, catches the resulting faults, and migrates hot pages toward the accessing thread.
NUMA hinting faultThe page fault AutoNUMA deliberately induces to detect "this page was just touched" — repurposed here as a promotion/migration demand signal (demotion is a follow-on action to make room, not a direct response to the fault itself).
CPM / CPMXAutoTiering's Conservative scheme: promote/migrate to the next-best alternative node when the ideal one is full (X = adds page exchange between same-tier nodes when a migration would otherwise fail, e.g. remote↔local DRAM).
OPM / OPMX / OPM(BD)AutoTiering's Opportunistic scheme: demote a cold upper-tier page to make room for a hotter one (X = exchange fusion; BD = background demotion).
LAPLeast Accessed Page — AutoTiering's per-page access-history classification used to pick demotion victims.
kdemotedNew kernel thread that demotes cold pages to the lower tier in the background, replenishing a small reserved free-page pool.
kswapdStock Linux's existing reclaim daemon, which frees pages to storage — not tier-aware, and the paper finds it often never fires.
DRAM · upper-tier (fast) DCPMM · lower-tier (slow) AutoTiering's machinery
1The bug: fallback path ignores the tier▾

Stock Linux's memory allocator has a fallback path per NUMA node, ordered purely by physical distance. On the paper's 2-socket, 4-node system, when local DRAM (node-0) is full, the fallback path sends the request to local DCPMM (node-2) — not remote DRAM (node-1) — because "local" always wins in a distance-only model.

Measured latency/bandwidth show local DCPMM is actually slower than remote DRAM. The distance-only fallback order is simply wrong once a second tier exists.

Now you're ready: every AutoTiering mechanism is, at bottom, a fix to this one ordering mistake — insert the access tier as a first-class factor, ahead of locality.
2Promotion vs migration vs demotion▾

Three distinct page moves recur throughout: promotion (lower-tier → upper-tier), migration (movement within the same tier, e.g. remote DRAM → local DRAM), and demotion (upper-tier → lower-tier, which stock Linux doesn't support at all).

AutoNUMA already does migration for DRAM-only NUMA. AutoTiering adds promotion logic that survives a full upper tier, and demotion, which is entirely new.

Now you're ready: CPM is about smarter promotion/migration targets; OPM is about creating room via demotion so promotion doesn't have to wait.
3Why AutoNUMA's binary active/inactive isn't enough▾

Linux's page reclaim already sorts pages into active and inactive LRU lists. That's a coarse, binary signal — fine for deciding "keep or evict," but too blunt for deciding which one page, among many resident in fast memory, is the single best demotion victim right now.

AutoTiering needs a finer ranking, which motivates its own per-page access-history structure (LAP, primer 5).

Now you're ready: the paper reuses active/inactive for file-backed pages, but layers a new N-bit-vector scheme on top for anonymous pages.
4File-backed vs anonymous regions▾

File-backed pages mirror file contents (so page cache serves I/O from memory); anonymous pages hold arbitrary data like heap/stack (malloc'd memory). Linux already tracks recency for file-backed pages via the active/inactive lists tied to reads/writes.

AutoTiering's demotion search checks file-backed pages first (cheap, existing signal), falling back to the anonymous region (needs the new LAP machinery) only if no free space turns up there.

Now you're ready: this ordering is why GraphMat's win comes almost entirely from demoting file-backed pages — its working data structures are anonymous and stayed put.
5LAP: an 8-bit access history, not a threshold▾

For anonymous pages, AutoTiering reuses AutoNUMA's periodic page-scan facility to record, per page, an N-bit vector (N=8): one bit per scan window, set if the page was touched. The page is bucketed into LAP[k], where k = number of bits set — so LAP[0] holds pages untouched in all 8 recent windows, LAP[8] holds pages touched in every one.

A demotion victim is pulled from the lowest non-empty LAP bucket. This is a relative ranking across many recency levels, not a single hot/cold cutoff.

Now you're ready: Worked Example ① below walks through classifying a page into a LAP bucket by hand.
6Hiding demotion latency: a reserved pool + kdemoted▾

Naively, a promotion into a full upper tier must wait for a demotion to finish first — demotion and promotion serialize on the fault-handling critical path. AutoTiering instead keeps a small pool of pre-freed pages (16 for 4KB pages, 4 for 2MB huge pages) so a promotion can proceed immediately.

A new background thread, kdemoted, wakes once the pool drops below a threshold (4) and refills it by demoting LAP-selected victims — off the critical path.

Now you're ready: this is the OPM(BD) variant in the results — same demotion logic as OPMX, but with the wait moved out of the fault handler.
The whole story in one place

AutoTiering in a nutshell

The problem, the fix, and how the pieces connect.

Linux's page-placement machinery — the allocation fallback path, AutoNUMA's migration, kswapd's reclaim — was designed when "memory" meant DRAM-only NUMA, where the only performance-relevant question is how far a node is. Add a second, genuinely slower tier (DCPMM beside DRAM) and a second question appears: which tier is the page in. The paper shows that on their real Optane DCPMM system, this second question dominates — local DCPMM is measurably slower than remote DRAM, which existing NUMA logic never even considers as an option.

AutoTiering's fix arrives in two layers. First, CPM (Conservative Promotion/Migration) simply widens the set of alternatives the fault handler will consider when the ideal (local DRAM) node is full — trying remote DRAM before giving up to local DCPMM, and allowing migration between the CPU-less DCPMM nodes that AutoNUMA previously ignored entirely. Second, OPM (Opportunistic Promotion/Migration) goes further: it actively demotes a judiciously-chosen cold page from the upper tier to make room, using a new per-page access-history ranking called LAP. A background thread (kdemoted) and a small reserved-page pool keep that demotion off the critical path.

The payoff: across graph500, GraphMat, Liblinear, and five SPECaccel workloads, AutoTiering's full scheme improves performance by roughly 2× on most workloads and up to ~6.9× (graph500) and ~2.3× (GraphMat) over stock Linux 5.3 — and by up to 3.5× over Intel's own contemporaneous tiering patch (Tiering v0.6).

🍯 Key takeaways

  • Stock Linux's fallback path is distance-first; multi-tiered systems need tier-first — local DCPMM can be slower than remote DRAM.
  • CPM/CPMX: widen the promotion/migration alternatives (remote DRAM, cross-DCPMM migration, page exchange) without demoting anything.
  • OPM/OPMX/OPM(BD): actively demote the least-accessed upper-tier page (via LAP, a 9-level access-history ranking) to free room for hotter pages.
  • Demotion latency is hidden with a small reserved free-page pool (16 pages @4KB / 4 @2MB) drained by a background kdemoted thread.
  • Metadata cost: ~32 bytes/page, ≈0.91% less usable DRAM on a 32GB+256GB system — for up to 2–7× speedups.
  • AutoTiering beats CPM-only, beats stock Linux, and mostly beats Intel's Tiering v0.6 — but not universally (graph500's BFS phase, Liblinear).
Five everyday pictures

How to think about AutoTiering

Each stands alone — read in any order. Every card ends with where the picture breaks.

The core rule · Tier before locality

Borrowing across town vs. your own damp closet

Need a book right now. A friend across town has a pristine copy (remote DRAM); your own basement copy is water-damaged and slow to read (local DCPMM). Distance says "your own copy is closer." Quality says "call your friend." AutoTiering's CPM makes the OS call the friend.

Where it breaks: if both alternatives are the same tier (two DRAM nodes), distance really is the only thing that matters — the rule only overrides locality across tiers, not within one.
Ranking victims · LAP

An 8-week attendance sheet

Instead of a single "present/absent" flag, LAP keeps eight weeks of check marks per page. Count the checks and you get a graded ranking — never-showed (0 checks) is the obvious pick to drop first, always-showed (8 checks) is the last. Demotion pulls from the emptiest bucket, not an arbitrary cutoff.

Where it breaks: eight weeks is a fixed, shallow memory — a page that was hammered nine windows ago and idle since looks identical to one that's always been idle. The window length (N=8) is a tuned constant, not a law.
Reserved pool + kdemoted · Latency hiding

The restaurant's always-open table

A busy restaurant keeps one or two tables free at all times, so a walk-in never waits for busboys to clear a table before being seated. A busser (kdemoted) works quietly in the back, clearing tables to keep the buffer stocked — never in the customer's critical path. AutoTiering's reserved-page pool plays exactly this role for promotion.

Where it breaks: the busser and the diners still share the same kitchen resources — Liblinear's case shows the background thread can contend for memory bandwidth with foreground work even while hiding latency, so end-to-end time doesn't always improve.
Page exchange · One swap, not two moves

Trading seats instead of both standing up

Two people want each other's seats. Standing both up and re-seating them is two operations with an awkward gap where nobody's seated. Swapping directly is one atomic move. AutoTiering fuses two moves into one atomic exchange whenever destination and source line up: OPMX pairs a demotion with a promotion, while CPMX pairs two same-tier migrations (e.g. remote DRAM ↔ local DRAM) when a plain move would otherwise fail — no demotion involved — skipping a wasted allocate-then-free round trip.

Where it breaks: the swap only helps when the two moves' source/destination actually line up; when they don't, you're back to two ordinary, separate operations.
Two personalities · Conservative vs progressive

The cautious agent vs the assertive one

A cautious real-estate agent only shows you units that are already vacant (CPM: just try better alternatives, never evict anyone). An assertive agent will politely ask a current, low-engagement tenant to relocate to free up the unit you actually want (OPM: demote a cold page). The assertive agent gets you a better outcome, but only works if she can reliably tell who's "low engagement" — that's what LAP is for.

Where it breaks: being assertive isn't free — the agent's own time (the demotion + LAP bookkeeping) is overhead, which is why CPM alone still wins for workloads whose data is already well balanced (555.pseismic).
The full explanation

How it actually works

Section by section, following the paper's own progression: diagnose, patch conservatively, patch opportunistically, hide the latency.

1 · Three problems, one root cause

Every mechanism in the paper answers one of three concrete, diagnosed problems — all traceable to the same root cause: the OS was built assuming one uniform memory tier.

ProblemAutoTiering's answer
Allocation fallback ignores the access tier; promotion stalls when the upper tier is fullCPM / CPMX — promote/migrate to the next-best alternative
Pages are never demoted upper→lower tier; CPU-less DCPMM nodes get skewed usageOPM / OPMX — LAP-ranked opportunistic demotion
Demotion sits on the fault-handling critical pathReserved pool + kdemoted — OPM(BD), background demotion

2 · Conservative design (CPM / CPMX)

On a NUMA hinting fault, if the ideal target (local DRAM) is full, CPM tries the next-best location instead of giving up:

Fault in local DCPMM
→ promote to remote DRAM (2nd best)
→
Fault in remote DCPMM
→ try remote DRAM, else migrate to local DCPMM
→
Fault in remote DRAM
→ already 2nd-best; use page exchange (CPMX) with a same-tier neighbor
💡
Why this needs a code change, not just a distance-table edit: stock AutoNUMA can migrate CPU-having nodes toward each other, but it never moves pages onto CPU-less DCPMM nodes at all — CPM adds that path so locality can be restored within the lower tier once the upper tier is unavailable.

3 · Opportunistic design (OPM / OPMX) and LAP

CPM never evicts anyone, so if the upper tier stays full, hot lower-tier pages simply can't get promoted — CPM's own results show this stalling GraphMat and Liblinear, whose file-backed pages fill DRAM and never get reclaimed by kswapd. OPM instead actively finds the least-accessed upper-tier page and demotes it to free room.

For anonymous pages, "least accessed" is decided by LAP: an 8-bit access-history vector per page (reusing AutoNUMA's periodic scan), bucketed by popcount into levels LAP[0]…LAP[8].

When a promotion or migration request needs room, AutoTiering compares the faulting page against the current least-accessed upper-tier page; only if the faulting page is relatively more accessed does the demotion proceed — otherwise the request is simply denied, keeping already-hot data in place.

4 · Hiding demotion latency (OPM-BD)

Serializing "demote, then promote" on the fault path makes fault latency the sum of both operations. AutoTiering decouples them with a small pool of pre-freed pages (16 @4KB / 4 @2MB) that immediately satisfies promotion requests, plus a background thread kdemoted that wakes when the pool drops below threshold 4 and refills it by demoting LAP-selected victims in a batch.

# foreground (fault handler, on the critical path)
on promotion_request:
    if reserved_pool.not_empty():
        page = reserved_pool.take()      # no wait — pool absorbs the request
    else:
        page = demote_now(lap_victim())  # OPMX fallback: pay the cost inline
    install(faulted_page, page)

# background (kdemoted)
while True:
    if reserved_pool.size() < 4:
        victim = lap_victim()            # scan LAP[0] upward, file-backed first
        demote(victim) into reserved_pool
⚠
Not a free lunch: kdemoted still consumes real memory bandwidth. For Liblinear, the paper measures shorter per-fault latency under OPM(BD) but no end-to-end speedup — contention between the background thread and foreground application threads eats the gain. The authors flag "rigorous scheduling of kdemoted" as future work.
Follow the numbers, step by step

Worked examples

Four calculations, using the paper's own reported values, followed through completely.

① Classifying a page into a LAP bucket

A page's 8-bit access history (oldest → newest scan window) reads: 0 0 1 1 1 1 0 0. Which LAP bucket does it join, and would it be chosen for demotion before a page in LAP[1]?

  1. Count the set bits. 0,0,1,1,1,1,0,0 → four 1-bits.
  2. Bucket = popcount → LAP[4]. This page was touched in exactly 4 of the last 8 scan windows.
  3. Compare to LAP[1]: demotion always scans from LAP[0] upward, so a non-empty LAP[1] is exhausted before LAP[4] is ever consulted.
  4. Answer: this page (LAP[4]) is not chosen while any LAP[0]–LAP[3] page remains — it's mid-tier, not the coldest available victim.
🍯
Insight: LAP gives a full ranking, not a hot/cold cutoff — which is exactly the granularity problem the paper identifies with plain active/inactive lists.

② Metadata overhead, recomputed

The paper states LAP metadata costs 32 bytes/page (a 1-byte/8-bit history vector + 16B two list pointers + 8B page-frame number + 1-byte last-faulted-CPU, rounded/aligned to 32 bytes), adding "an extra 288MB for the system memory of 32GB DRAM with 256GB DCPMM," a 0.91% cut to usable DRAM.

  1. Check the percentage directly: 288 MB ÷ 32 GB of DRAM. Using binary units, 32 GB = 32,768 MiB, so 288 / 32768 ≈ 0.88%.
  2. Compare to the paper's 0.91%: close — the small gap is consistent with GB/GiB rounding or the paper measuring against slightly-less-than-nominal usable capacity, not an error in the mechanism.
  3. Put it in context: under 1% of DRAM bought back roughly 2–7× speedups across the workload suite — a favorable trade by any measure.
🌱
For your CXL/tiering work: this is the same order of magnitude as per-page hotness metadata in later systems (e.g. histogram-based counters) — a useful sanity check when budgeting metadata for your own tiering mechanism.

③ Sizing the reserved page pool

The reserved pool holds 16 pages for 4KB base pages and 4 pages for 2MB huge pages. How big is each pool in bytes, and as a fraction of the 32GB upper tier?

  1. 4KB pool: 16 × 4KB = 64 KB reserved at all times.
  2. 2MB pool: 4 × 2MB = 8 MB reserved at all times.
  3. As a fraction of 32GB DRAM: 64KB/32GB ≈ 0.0002%; 8MB/32GB ≈ 0.024%. Both are negligible next to the 32-byte-per-page LAP metadata (~0.9%).
  4. Why the huge-page pool is proportionally smaller in page count: demoting one 2MB page is a much bigger, slower operation than one 4KB page, so keeping only 4 in reserve (vs 16) still absorbs a comparable amount of promotion demand before kdemoted must catch up.
💡
This is the concrete answer to "how do you decouple demotion from the critical path without keeping half the cache empty" — the pool only needs to be big enough to cover the gap until kdemoted wakes, not to buffer indefinitely.

④ Reading the speedup numbers honestly

Abstract: GraphMat ≈2.3×, graph500 ≈6.9×, most SPECaccel ≈2×, up to 3.5× over Intel's Tiering v0.6. But Fig. 15 shows Tiering v0.6 actually beating OPM(BD) on graph500. Are these consistent?

  1. The 6.9× figure is graph500 vs. stock Linux 5.3 (no tiering support at all) — a very low bar.
  2. The Fig. 15 comparison is against Tiering v0.6, Intel's own tiering-aware patch — a much higher bar, and a different phase of graph500 matters: OPM(BD) wins the graph-building phase but Tiering v0.6's simpler two-scan hot/cold heuristic happens to do better once graph500 starts traversing (BFS), which touches more lower-tier pages than OPM(BD) has promoted.
  3. Both statements are true simultaneously: "6.9× over nothing" and "occasionally slower than a competing tiering patch" describe different comparisons, not a contradiction.
  4. Takeaway: always check which baseline a tiering speedup is measured against — a lesson that generalizes directly to comparing your own tiering results against TPP, HeMem, Memtis, or Pond.
🍯
Framing (mine, not the paper's): this baseline-sensitivity is exactly why later systems standardized on reporting against both "no tiering" and "best prior tiering" — worth keeping in mind when you read AutoTiering's numbers next to more recent work.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A process page-faults for a brand-new page and local DRAM is full. Stock Linux's allocation fallback path sends the request to local DCPMM. Why is this the wrong choice on this hardware, specifically?
Show answer
Because the fallback path is ordered purely by physical distance, and on this system local DCPMM is measurably slower than remote DRAM — a fact that doesn't exist in DRAM-only NUMA, where "local" and "fast" always coincide. The right target is remote DRAM, one hop further away but a full memory tier faster.Misconception: that "local" is always the safe default. It's safe only within one tier; across tiers, tier speed can dominate distance. (This is the initial-allocation fallback path specifically — when AutoNUMA later tries to promote a resident page and finds local DRAM full, stock Linux doesn't redirect it to DCPMM at all; it simply drops the request and leaves the page where it is.)
Problem 2 · easy
A page's 8-bit access-history vector is 1 1 1 1 1 1 1 1. Should AutoTiering's OPM ever pick it as a demotion victim?
Show answer
Essentially never, by design — it belongs to LAP[8], the highest bucket, and demotion always drains the lowest non-empty bucket first (LAP[0] upward). As long as any lower bucket has a candidate, this page is skipped.Misconception: that LAP scans pages individually by "recent access." It scans by bucket, and a bucket-8 page is the last resort, not a candidate under normal conditions.
Problem 3 · medium
CPM alone gives GraphMat only modest gains, and the paper explains this by noting kswapd is never invoked. Why does that specifically block CPM from helping?
Show answer
CPM only redirects promotion/migration to better alternatives when the ideal target is full — it never frees space itself. If DRAM stays full and nothing (like kswapd) ever reclaims the file-backed pages sitting there, there's never an opening for CPM to redirect a hot lower-tier page into DRAM at all. The bottleneck isn't "wrong destination," it's "no destination has room" — which is exactly the gap OPM's active demotion closes.Misconception: that a smarter fallback path is sufficient on its own. It only helps when free space appears somewhere; it can't manufacture free space.
Problem 4 · medium
For a few SPEC workloads (e.g. 553.pclvrleaf), OPMX performs slightly worse than the simpler CPMX. What kind of access pattern would explain this?
Show answer
A relatively uniform access pattern, where pages are touched with similar frequency across the working set. When accesses are already evenly spread, LAP can't find a clearly "cold" victim, so the extra demotion/promotion bookkeeping (and the reduced opportunity for a clean page exchange, since demotion source and promotion destination line up less often) becomes pure overhead rather than a targeted win.Misconception: that a more aggressive, "smarter" mechanism (OPM over CPM) can never lose. It loses exactly when its core assumption — a meaningfully cold page to sacrifice — doesn't hold.
Problem 5 · hard
OPM(BD) reduces per-fault latency for Liblinear but does not improve its end-to-end runtime. What's the mechanism, and what's the general lesson for any background-reclaim design?
Show answer
Removing demotion from the fault-handling critical path helps the foreground thread's individual fault latency, but kdemoted still runs concurrently and competes for memory bandwidth and cache/TLB resources with the application's own threads. If that contention offsets the latency win, kernel time doesn't improve even though fault latency measurably does. The general lesson: hiding latency by moving work to the background only pays off if the background work doesn't itself become the new bottleneck — which is why the paper flags kdemoted scheduling as future work.Misconception: that "off the critical path" is synonymous with "free." It's cheaper for the faulting thread, not costless for the system.
Problem 6 · hard
555.pseismic shows essentially no improvement under any AutoTiering scheme. What does that imply about when tiering-aware page management helps at all?
Show answer
It implies the stock kernel's default placement for 555.pseismic already balances hot and cold data reasonably well across the tiers — there's no meaningful misplacement to correct. AutoTiering (like any tiering optimization) can only help when the baseline is misplacing data; if the workload's natural access pattern already lines up with where the data landed, smarter promotion/demotion logic has nothing to fix.Misconception: that a tiering mechanism should always show a gain. It only shows a gain proportional to how badly the untiered baseline was misallocating memory for that specific workload.
Quick answers

Frequently asked questions

Ten questions, tap any to expand.

Q1Why not just edit the NUMA distance table to make remote DRAM look "closer" than local DCPMM?▾
The paper considers and rejects this: reweighting distances is a one-dimensional hack that still can't express "consider several alternatives in this specific order" or "allow migration onto CPU-less nodes," both of which the existing NUMA fallback machinery structurally can't do. A real fix needs new code paths (CPM/OPM), not just new numbers in an existing table.
Q2What exactly triggers a promotion attempt?▾
A NUMA hinting fault — AutoNUMA's existing mechanism of periodically unmapping pages so the next access faults, revealing "this page was just touched by this thread." AutoTiering repurposes that fault as its demand signal for promotion (from DCPMM) or migration (between DRAM nodes), rather than inventing a new monitoring facility.
Q3What's the actual difference between CPM and CPMX, or OPM and OPMX?▾
Both X variants add page exchange, but for different failure modes. OPMX fuses a demotion with a promotion into one atomic swap when their destination/source line up, instead of two separate allocate/free operations. CPMX is narrower: it swaps two pages between same-tier nodes (especially remote DRAM ↔ local DRAM) when an ordinary same-tier migration would otherwise fail — no demotion is involved. CPM/OPM are the base mechanisms (finding better alternatives / opportunistic demotion); CPMX/OPMX add these respective exchange optimizations.
Q4Does AutoTiering ever slow things down?▾
Yes, in specific cases: OPMX is 7–8% slower than CPMX on 503.postencil, 553.pclvrleaf, and 560.pilbdc (overhead not amortized by a clear victim to demote); OPM(BD)'s background thread doesn't help Liblinear's end-to-end time despite lower fault latency; and large 2MB pages under OPM(BD) hurt 559.pmniGhost and 560.pilbdc because per-page demotion cost scales with page size.
Q5How is LAP different from just using the existing active/inactive LRU lists?▾
Active/inactive is binary — fine for reclaim decisions, too coarse for "of everything currently resident, which single page is the best demotion victim." LAP adds a graded, 9-level ranking (via an 8-bit history vector's popcount) specifically for anonymous pages; file-backed pages still use the existing inactive-list ordering, since that already gives adequate granularity there.
Q6Why keep a reserved page pool instead of just always demoting synchronously?▾
Synchronous demote-then-promote makes fault latency the sum of both operations, and DCPMM's write latency in particular is worse than its read latency, making synchronous demotion especially costly. The reserved pool (16 @4KB / 4 @2MB) absorbs the immediate request; kdemoted refills it asynchronously, so the common-case fault only pays promotion cost.
Q7Does AutoTiering help multi-programmed (multiple co-running apps) workloads?▾
Yes, particularly when applications run across sockets rather than isolated per-socket: CPM alone gives no benefit when each app is confined to its own socket (nothing to redirect across), but OPM(BD) still helps by rebalancing within that socket's tiers. When apps run across sockets, both CPM and OPM(BD) help, with OPM(BD) consistently ahead.
Q8How does this compare to newer systems like Meta's TPP, HeMem, Memtis, or Pond?▾
Framing, not paper content (all four postdate this 2021 paper): AutoTiering's fault-driven demand signal and reserved-pool latency hiding anticipate ideas TPP later formalizes as async promotion; its LAP bucket ranking is a coarser cousin of Memtis's histogram-based hotness tracking; HeMem instead uses hardware PEBS sampling rather than fault-based sampling for hotness, trading overhead for precision; Pond targets CXL-pooled, disaggregated memory rather than a locally-attached second tier, so its placement problem is shaped more by network/pooling constraints than by a DRAM/DCPMM speed gap. None of this is asserted by the paper itself.
Q9Does large-page (2MB) support just work by flipping a flag?▾
No — the paper finds mixed results. GraphMat and 553.pclvrleaf benefit from large pages under OPM(BD), but 559.pmniGhost and 560.pilbdc get worse, because demoting a 2MB page costs proportionally more, and that fixed cost doesn't amortize for those access patterns. A multithreaded page-copy helps 559.pmniGhost but not the others — this remained an open tuning problem.
Q10What did the authors leave for future work?▾
Two things explicitly: (1) more rigorous scheduling of kdemoted to avoid contending with foreground threads (the Liblinear problem), and (2) generalizing the design with a measured, dynamically-updated table of placement alternatives and their actual performance, rather than the current design's built-in assumptions about which tier/node ordering is best.

AutoNUMAStock Linux's page-scan/fault-based facility for migrating pages toward the accessing thread on DRAM-only NUMA.
NUMA hinting faultThe deliberately-induced fault AutoNUMA uses as an access signal; repurposed by AutoTiering as its promotion/migration trigger. Demotion follows as a room-making step, not a direct response to the fault.
kswapdStock reclaim daemon that frees pages to storage-backed swap; the paper finds it's often never invoked, blocking CPM's opportunities.
Active / inactive listsLinux's existing binary LRU classification for file-backed pages, checked before falling back to LAP for anonymous pages.
Page exchangeAtomic swap of two pages' locations, avoiding a separate free+allocate round trip; originally proposed in Nimble Page Management.
HMATACPI 6.2's Heterogeneous Memory Attribute Table, exposing per-node performance data — related infrastructure, not itself a placement policy.
