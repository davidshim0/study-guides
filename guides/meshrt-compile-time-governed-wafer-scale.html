SOSP 2026 · A Field Guide

Compiling the decisions, not just the math, so a wafer never phones home

900,000 tiny cores share one wafer and no shared memory. The obvious way to handle a changing batch or a token's expert choice is to ask a central coordinator — but on this hardware that round trip costs thousands of cycles. This is the plain-English story of MeshRT, which bakes those decisions into every core's own schedule before the chip ever runs a token.

📄 He, Xu, Lu et al. · SOSP 2026 🎓 Some LLM-serving basics assumed — primers cover them ⏱ ~30 min read
🧩

Compile the STRUCTURE of every runtime decision into each core's schedule ahead of time — only the VALUES get resolved live, locally, with no host in the loop.

Before you begin

Quick glossary, then eight ideas the paper assumes

Acronyms first, so nothing below reads as alphabet soup. Then eight collapsed primers — read in order, or jump to whatever's unfamiliar.

PEProcessing Element — one of ~900,000 tiny compute+router cores tiled across the wafer. This paper calls a PE a "core."
NoCNetwork-on-Chip — the point-to-point mesh linking neighboring cores. There is no shared memory or bus.
GALSGlobally Asynchronous, Locally Synchronous — each core runs its own clock; coordination happens only through data arrival.
MoEMixture-of-Experts — a layer where a gating network sends each token to a small subset of "expert" sub-networks.
CF (payload)Control-Flow payload — a few bytes of metainfo (e.g. which batch slot just finished) piggybacked on ordinary activation data.
RDTRequest Descriptor Table — a core-local table of which requests currently occupy which batch slots.
TPOTTime Per Output Token — the decode-side latency metric; lower TPOT means faster per-token generation.
WSE-3 / CS-3Cerebras Wafer-Scale Engine 3, the chip; CS-3 is the system that houses it. MeshRT's testbed.
1What a wafer-scale accelerator actually is▾

Instead of cutting a silicon wafer into many small GPU-sized dies, a wafer-scale chip keeps the entire wafer as one accelerator. The WSE-3 packs ~900,000 simple cores into a 762×1172 grid, with 44 GB of on-chip SRAM total and 21 PB/s of aggregate memory bandwidth — but each individual core only has about 48 KB of local SRAM and talks only to its four mesh neighbors.

Now you're ready: MeshRT's entire design is a response to "lots of tiny, tightly-budgeted cores with no shared memory," not "a few big cores with a shared cache."
2Why a core here can't just run a scheduler▾

A GPU Streaming Multiprocessor can run general-purpose control code — branch on arbitrary state, call into a runtime, etc. A WSE-3 core exposes only three primitives: Compute (local arithmetic + simple conditionals), Receive, Send. There's no room, literally, for an open-ended scheduler loop.

Now you're ready: if runtime logic can't live in a scheduler, it has to live in the schedule itself — the paper's whole premise.
3Why "runtime dynamism" is unavoidable in LLM serving▾

Modern serving keeps throughput high with tricks whose exact effect isn't known until execution: continuous batching (requests finish and arrive at different steps, so the active batch composition shifts every step) and MoE routing (a gating network decides, per token, which expert group handles it). Neither can be nailed down at compile time as a fixed value — only its shape can.

Now you're ready: MeshRT's bet is that the shape (which cores, what type of decision) is fully known ahead of time even though the value isn't.
4The host-mediated pattern GPU systems already use▾

On GPU serving stacks (vLLM, SGLang, TensorRT-LLM), the device runs kernels but a host CPU keeps the request queue, decides batch composition, and issues the next kernel launch. This works because host↔GPU coordination is cheap and the host can hold arbitrarily large runtime state.

Now you're ready: this is exactly the pattern that breaks on a wafer — the "host" analog is impossibly far, in cycle terms, from most of the 900,000 cores.
5Why coordination is expensive on a mesh (the cost table)▾

Cores only reach neighbors directly. A broadcast to reach all cores costs O(N) hops (~100–1,000 cycles); an all-to-all exchange costs O(N²) messages (~10⁵–10⁶ cycles); a round trip to the host costs ~7,000 cycles regardless of N. A single decode step can involve hundreds of small decisions — so any of these paid per-decision adds up fast.

Now you're ready: every design choice in the paper is measured against this cost table — it's the reason "just synchronize" is never the answer.
6The existing alternative: precompiled, branching dataflow▾

Systems like Groq's TSP, Graphcore's IPU stack, and WaferLLM (the paper's baseline) precompile a static execution schedule, sometimes with simple per-core if/else branches among a few pre-baked paths. This keeps everything on-chip and fast — but it can't gracefully absorb an evolving batch or expert routing; it either restricts those features or pads around them.

Now you're ready: MeshRT doesn't replace static compilation — it extends it to also compile the dynamism-handling logic, not just the math.
7GALS and why a "safe moment to reconfigure" is subtle▾

Each core runs on its own clock; there's no chip-wide tick. A core whose queues look empty may still have data in flight from an upstream neighbor. Changing that core's routing table (a reconfiguration) while old data is still arriving can corrupt it or deadlock the mesh.

Now you're ready: this is why MeshRT needs a principled notion of a "safe boundary," not just "whenever a core looks idle."
8Consistent cuts and all-or-nothing collectives▾

A collective like AllReduce has a property: a core can only finish its part after it has both contributed and received the final result — which in turn required every other participant to contribute. So the moment a collective completes is guaranteed to be a point where every participating core has reached a mutually consistent state, even without a global clock. (This idea is a distributed-systems classic — Chandy & Lamport's "distributed snapshots.")

Now you're ready: MeshRT's safe reconfiguration mostly rides on this "free" consistent cut that collectives already provide.
The whole story in one place

MeshRT in a nutshell

The problem, the compile-time trick that fixes it, and how the pieces connect.

Wafer-scale chips are attractive for low-latency LLM inference because on-chip SRAM and a dense NoC eliminate the two biggest sources of per-token latency on GPUs: off-chip HBM reads and off-chip interconnect hops. But modern serving relies on runtime dynamism — continuous batching, MoE routing — whose exact values aren't known until execution. Existing wafer-scale systems handle this by either forcing everything to be static (padding, no expert parallelism — throughput suffers) or falling back to host-mediated control (a ~7,000-cycle round trip per decision — latency suffers).

MeshRT's fix — compile-time governance of runtime dynamism: observe that LLM inference uses a closed, known set of kernel types. So although a specific runtime value (which slot just finished, which expert a token routes to) is unknown until execution, the structure of the decision — which cores produce it, which cores consume it, what type it is — is fully determined at compile time. MeshRT's compiler weaves metainfo-handling sub-schedules directly into each core's compiled event table, alongside the ordinary data-processing steps, in a single synthesis pass.

Because the synthesized schedule can exceed a core's tight routing/queue/buffer budget, MeshRT also performs safe incremental materialization: it slices each core's schedule into segments that fit the hardware, and reconfigures between segments only at boundaries that are provably safe — mostly by reusing the "free" consistent cut a completed collective already provides.

The payoff: on a Cerebras CS-3, MeshRT improves decode throughput by up to 56× over WaferLLM while adding only 25–40 μs (7.6–9.5%) per decode token. Against measured single-instance SGLang on H200, MeshRT is 4.5–7.0× lower latency and, projected to an area-equivalent GPU cluster, 1.6–12.1× more decode-energy-efficient.

🍯 Key takeaways

  • The structure of a runtime decision is compile-time knowable, even when its value isn't — that's the key observation.
  • ReceivesDynamism / ProducesDynamism predicates tell the compiler exactly which cores need metainfo sub-schedules woven in.
  • Control metainfo (CF) piggybacks on activation data — a few bytes vs ~4 KB, <0.2% overhead, no extra network trip.
  • Safe incremental materialization partitions each core's schedule into hardware-budget-sized segments and reconfigures only at consistent cuts, mostly for free at collective boundaries.
  • Result: up to 56× throughput over WaferLLM, only 7.6–9.5% added TPOT, nothing chip-wide-synchronous on the critical path.
  • GPUs still win on compute-bound prefill; MeshRT's edge is decode latency and energy, where SRAM bandwidth and on-chip control dominate.
Six everyday pictures

How to think about MeshRT

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Compile-time governance

A choose-your-own-adventure book

Every branch is printed in advance — "if the reader picks the sword, turn to page 40." The author resolves the structure at print time; the reader only resolves which page number at read time. MeshRT does the same for a decode step: the compiler bakes in every branch a runtime decision could take; the actual choice (which slot finished, which expert) is filled in at execution, locally, per core.

Where it breaks: a novel-length book has a manageable branch count. MeshRT's completeness argument depends on LLM inference using a closed set of kernel types — a genuinely new operator (e.g. a state-space model) may need new "pages" the compiler doesn't have yet.
The rejected default · Host round trip

Radioing the control tower every turn

Imagine a pilot who can't taxi, turn, or brake without radioing a distant tower and waiting for a reply — even for decisions the pilot could make locally. That's host-mediated dynamism on a mesh: a ~7,000-cycle round trip for something a neighboring core group could resolve itself, hundreds of times per token.

Where it breaks: some decisions genuinely need central coordination (e.g. a truly global load-balance policy) — MeshRT still routes those through a compiled collective, it just avoids paying tower-radio cost for local decisions that don't need it.
The metainfo channel · CF payload

A sticky note on the parcel, not a phone call

You don't call ahead to tell the delivery hub what's inside a box — you tape a small label to the box itself, and the hub reads it as the box arrives. MeshRT's control-flow metainfo (which slot finished, which expert a token wants) rides as a few extra bytes prepended to the ordinary activation transfer — no separate Send/Receive, no separate network trip.

Where it breaks: a label only works if the recipient already knows how to read it. This only works because the compiler pre-installed the exact parsing logic (ReceivesDynamism) on the receiving core — an unlabeled or unexpected box would go unhandled.
Safe reconfiguration · The consistent cut

A relay baton handoff mid-stride

A relay team doesn't stop running to swap runners — they hand off the baton within a marked zone where both runners are moving together, guaranteeing the baton is never dropped or duplicated. MeshRT's segment transitions work the same way: rather than a global stop-the-world barrier, it waits for a moment — usually a collective's completion — where every affected core is provably in a consistent state, then swaps schedule segments.

Where it breaks: the handoff zone has to be pre-marked. Boundaries that don't naturally align with a collective need the compiler to insert its own bounded marker exchange first — the "free" cut isn't available everywhere.
The hazard · GALS asynchrony

Two clocks in one household

Two people on independent schedules can each think it's "safe" to act — one thinks the kitchen is free because they don't see anyone in it right now, not realizing food is still en route from the next room. Each WSE-3 core runs its own clock; a core with empty-looking queues may still have data in flight from an upstream neighbor whose clock is slightly out of phase.

Where it breaks: counterintuitively, the analogy's "busy household" (heavy traffic) is actually the safer case — backpressure naturally aligns clocks. It's the quiet, low-latency, small-data regime MeshRT targets that widens this exact race window.
The completeness bet · Closed kernel set

A fixed menu with pre-planned daily specials

A restaurant with a fixed menu can pre-print every ticket format its kitchen will ever need, including blanks for the "special of the day" — because the categories of dish (appetizer, entrée, dessert) never change, only which specific special fills the blank. MeshRT leans on the same trick: transformer inference decomposes into a small, known set of kernel types (attention, FFN, gating, AllReduce, sampling…), so the compiler can pre-print a slot for every kind of runtime value each kernel might produce or need.

Where it breaks: a genuinely new dish category (a new operator family, like linear attention or state-space models) has no pre-printed ticket — the paper flags this explicitly as a limitation, not a solved case.
🧠
For the tiering reader: compile-time governance is the mirror image of what OS-managed tiering systems (TPP, HeMem, Memtis-style hot/cold classifiers) do — they push a decision (migrate this page or not) into the kernel precisely because a fixed, cheap policy can be evaluated locally without a slow round trip to userspace. MeshRT pushes the analogous decision (route this token, refill this slot) into the compiled schedule for the same reason: the round trip (host, or here even chip-wide broadcast) is the expensive thing to avoid. This is a framing connection, not a claim in the paper itself.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams.

1 · Two challenges, one shared substrate

Compile-time governance introduces two problems. Schedule synthesis: turn a logical computation graph (with global dependencies) plus a spatial mapping into per-core event tables that also absorb runtime dynamism. Safe materialization: those synthesized schedules can exceed a core's tight routing/queue/buffer budget, so they must be split and reconfigured without host help. Both rely on a shared on-chip control substrate: small local control state (active slots, pending routing results) plus bounded control messages riding the same NoC as data.

2 · Dynamism-aware schedule synthesis (§4.2)

The compiler's key move is two predicates evaluated per kernel instance k and core c: ReceivesDynamism(k,c) and ProducesDynamism(k,c). Whenever either is true, the compiler injects a metainfo sub-schedule — a resolver before the kernel (if c consumes a runtime value) or a producer after it (if c generates one) — scoped strictly to the region R_k that kernel is mapped to. Algorithm 1 walks kernels in topological order, so dependencies are respected, and specializes per core within each kernel's region.

3 · Use case: continuous batching

The sampling kernel at the last transformer layer ProducesDynamism: after producing output tokens, each core detects end-of-sequence events and generates batch-state metainfo (which slots just finished), prepended to the outgoing activation. The first-layer kernel of the next decode step ReceivesDynamism: each core parses that metainfo, updates its local Request Descriptor Table, admits a waiting request into the freed slot, and selects which data to compute over — all before ordinary computation begins.

4 · Use case: MoE expert routing

Each layer's experts occupy disjoint spatial regions ("expert regions") so activated experts compute concurrently. The gating kernel in the attention stage ProducesDynamism: after top-k selection, each core prepends routing metainfo (which expert region) to the token. Relay cores along the path and the destination expert-FFN kernel both ReceivesDynamism: relay cores parse it to pick a forwarding direction; expert cores parse it to know which tokens to actually compute.

The same synthesis algorithm handles both use cases — and, per the paper, generalizes to speculative decoding (verification kernel produces an accept/reject decision) and sparse attention (selection kernel produces an active-KV-entry set) without any change to Algorithm 1.

5 · Safe incremental materialization (§4.3)

Walk each core's synthesized sub-schedules in order, accumulating them into a segment as long as they fit the core's resource budget (routing channels, queue bindings, buffers). When the next sub-schedule would overflow, close the segment — for free if the most recent kernel was a collective (its completion is already a consistent cut across participants), otherwise by inserting a bounded local marker exchange first. Then reconfigure, reset the budget, and start the next segment.

⚠
Why this matters more at low latency, not less: the GALS race window (Primer 7 / analogy 5) is widest exactly in MeshRT's target regime — fine-grained parallelism means small per-core data volumes that drain queues before upstream cores finish, and no backpressure to implicitly align clocks. The paper notes these races "manifest only at full hardware scale," not in simulation.
Follow the numbers, step by step

Worked examples

Four calculations, recomputed from the paper's own reported figures.

① The governance tax, computed from throughput alone

The paper reports MeshRT adds "25–40 μs (7.6–9.5%) per decode token" versus WaferLLM. Let's derive that from the raw per-user throughput numbers it also reports.

  1. Qwen3.5-9B, matched micro-bs=1: WaferLLM = 2,368 tok/s/user, MeshRT = 2,163 tok/s/user.
  2. Convert to TPOT (time per output token) = 1 ÷ throughput. WaferLLM: 1/2368 s ≈ 422.3 μs. MeshRT: 1/2163 s ≈ 462.3 μs.
  3. Overhead = 462.3 − 422.3 = 40.0 μs — matches the paper's "40 μs" exactly.
  4. As a fraction: 40.0 / 422.3 ≈ 9.47% ≈ the paper's "9.5%."
  5. Repeat for GPT-OSS-20B (2,980 → 2,770 tok/s/user): TPOT 335.6 μs → 360.9 μs, overhead 25.3 μs ≈ 7.6%. Both match.
🍯
Insight: the larger model (20B) doesn't pay a larger absolute tax than the smaller one (9B) — 25 μs vs 40 μs — confirming the paper's claim that the overhead is dominated by fixed metainfo handling, not model size.

② Why 56 H200 dies per WSE-3

The GPU comparisons scale to an "area-equivalent" GPU cluster. Where does 56× come from?

  1. WSE-3 die area ≈ 46,225 mm² (the whole wafer).
  2. H200's GH100 die area ≈ 814 mm².
  3. Ratio: 46,225 ÷ 814 ≈ 56.8, which the paper reports (conservatively) as 56 H200 dies per WSE-3.
  4. Why it matters: every "system throughput" GPU number in Table 2 is one measured GPU instance scaled by this factor under ideal linear scaling — an optimistic upper bound the paper is explicit about, not a physically measured cluster.
💡
This is why the paper frames GPU-cluster throughput comparisons as favoring GPUs (an upper bound for the baseline) even while MeshRT still wins decisively on decode latency and energy.

③ Padding waste vs. the measured continuous-batching factor

Figure 2 reports up to ~48–52% of ShareGPT decode compute wasted on padding at batch size 8. Table 4 separately reports continuous batching contributing a 1.6–1.7× throughput factor. Are these consistent?

  1. If p = 48% of compute is padding, the useful fraction is 1 − 0.48 = 0.52.
  2. Ideal uplift from eliminating all padding = 1 ÷ 0.52 ≈ 1.92×.
  3. Compare to Table 4's measured factor: 1.6–1.7× — same ballpark as 1.92×, but noticeably lower.
  4. Why lower: continuous batching's real-world factor also has to share credit with, and interact with, pipeline scheduling and expert parallelism (Table 4's other two columns) — it isn't a clean, isolated A/B on padding alone.
📎
Both numbers are the paper's own; the 1.92× is my derived sanity check, not a paper claim — it shows the two reported figures are compatible in direction and rough magnitude, not that they should match exactly.

④ Decomposing GPT-OSS-120B's 71.3× decode factor

Table 4 attributes decode gains for GPT-OSS-120B (micro-bs=4) to three policies: expert parallelism ×1.4, pipeline scheduling ×30.1, continuous batching ×1.7.

  1. Multiply them: 1.4 × 30.1 × 1.7 = 42.14 × 1.7 = 71.6, matching the paper's reported total of 71.3× (small rounding from using unrounded intermediates, as the paper notes).
  2. Pipeline scheduling dominates — 30.1× of the 71.3× — because overlapping micro-batches across compiled pipeline stages is where most of the raw parallelism comes from.
  3. This is a different number from Figure 9's 55.8× peak-to-peak decode ratio for the same model — that figure compares each system's best point across all evaluated micro-batches, not a fixed matched configuration. The paper is explicit these are separate measurements.
💡
Lesson for reading any systems paper's numbers: a "56×" and a "71×" for the same model aren't a contradiction once you check what's held fixed — matched-configuration ablation vs. peak-over-a-sweep are different questions.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
A request finishes at decode step t. Why doesn't MeshRT just broadcast "slot 2 is free" to all ~900,000 cores?
Show answer
A broadcast to reach every core costs O(N) hops — on the order of 100–1,000 cycles per Table 1 — repeated for every completion event, of which there can be hundreds per token. MeshRT instead scopes the notification to only the cores the compiler already knows are affected (the next pipeline stage's cores), piggybacked on the activation data those cores were receiving anyway.Misconception: that "notify everyone" is the safe default. Compile-time knowledge of which cores actually need the information is what makes narrow, piggybacked notification possible and cheap.
Problem 2 · medium
Redo Worked Example ① yourself for Qwen3.5-9B at throughput-oriented settings (micro-bs=8): WaferLLM has some TPOT; MeshRT's system throughput is 29,686 tok/s aggregate over the batch. Why can't you directly compute a governance-overhead percentage from this pair the way Example ① did?
Show answer
Example ①'s calculation used per-user throughput at micro-bs=1, isolating the TPOT of a single decode stream. At micro-bs=8, "system throughput" is an aggregate across 8 concurrent requests sharing pipeline stages — it conflates per-token latency with batch concurrency. To isolate governance overhead you need matched per-user TPOT at the same micro-batch size on both systems, which is exactly why Table 3 reports both single-user and system columns separately.Misconception: that any two throughput numbers can be subtracted to get an "overhead." The comparison is only meaningful when batch configuration is held constant on both sides.
Problem 3 · medium
Padding compute ratio rises from ~0% at batch size 1 to 45–68% at batch size 8 (Figure 2). Why does padding get worse with a larger batch, rather than better?
Show answer
Under static batching, every slot must be padded to the length of the longest-running request currently in the batch. With more concurrent requests (larger batch), there's a higher chance that at least one request runs much longer than the others — and every shorter request in that batch pays padding for the full duration. More slots means more opportunities for one straggler to inflate the padding bill for everyone.Misconception: that batching is "free" scaling. Static batching's padding cost scales with output-length variance across the batch, which is why continuous batching (refilling slots as requests finish) matters more, not less, at higher concurrency.
Problem 4 · hard
Why is a segment boundary right after an AllReduce "free," but a boundary at an arbitrary point in a core's schedule is not?
Show answer
AllReduce has all-or-nothing completion semantics: a core only finishes its part after contributing its data and receiving the final reduced result, which itself required every other participant to have already contributed. So the instant all participating cores reach "AllReduce done," they are guaranteed to be in a mutually consistent state — a "consistent cut" — with no message still in flight that could be corrupted by reconfiguration. An arbitrary point in the schedule offers no such guarantee: a core might look locally idle while a neighbor still has in-flight data addressed to it (the GALS race), so the compiler must insert its own bounded marker exchange to manufacture an equivalent guarantee.Misconception: that "the core finished its last instruction" means it's safe to reconfigure. Safety requires that *no other core* still expects the old configuration — which only a consistent cut (natural or manufactured) can guarantee.
Problem 5 · medium
MeshRT loses to GPUs on prefill (compute-bound, GPU 1.3–2.3× faster per-user, 25–61× higher projected system throughput) but wins decisively on decode. What structural fact explains the split?
Show answer
Prefill is GEMM-heavy and compute-bound — it rewards dense, high-FLOPS tensor cores, which is exactly what H200's GPU architecture is purpose-built for; WSE-3 trades compute density for many simple cores and aggregate SRAM bandwidth. Decode, by contrast, is memory-bandwidth-bound (each token requires reading the full KV cache and weights), which is precisely where WSE-3's 21 PB/s on-chip SRAM bandwidth — versus GPUs' much slower off-chip HBM bus — pays off, on top of MeshRT's on-chip dynamism handling avoiding host round trips.Misconception: that a "better" accelerator wins everywhere. The paper is explicit this is a structural mismatch for prefill, not a bug MeshRT is trying to hide — pipeline parallelism only partially compensates.
Problem 6 · easy
MeshRT's mapping choices (which kernel goes on which spatial region) are taken as an input, not solved by MeshRT itself. What would change if a user assumed MeshRT also finds the optimal mapping?
Show answer
They'd be crediting MeshRT with a separate research problem the paper explicitly scopes out: "mapping choices are important; prior work has explored mapping strategies for spatial accelerators... such choices are outside our scope; we select them empirically." MeshRT's contribution is what happens after a mapping is fixed — synthesizing dynamism-aware schedules and making them fit hardware budgets — not choosing the mapping itself.Misconception: that a "wafer-scale runtime" paper owns the whole stack end to end. MeshRT composes with, rather than replaces, mapping/placement research.
Problem 7 · hard
A brand-new attention variant (say, a linear-attention kernel) is added to a model MeshRT hasn't seen. What has to happen before MeshRT can serve it with compile-time governance, per the paper's own stated limitations?
Show answer
MeshRT's completeness argument rests on the "closed operator space assumption" — that transformer inference decomposes into a finite, known set of mesh kernel primitives, each with a known kernel function that GetCoreSche can lower and that ReceivesDynamism/ProducesDynamism can be evaluated against. A genuinely new operator type may require implementing new kernel primitives and potentially new dynamism-handling logic before the existing synthesis algorithm (Algorithm 1) can be pointed at it — the paper lists this explicitly as a limitation, not something handled automatically.Misconception: that "compile-time governance" is a fully general technique that adapts to any new kernel automatically. It generalizes across *dynamism patterns* (Section 4.2's use-case list) given known kernel types — not across unknown kernel types themselves.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What is "compile-time governance of runtime dynamism," in one sentence?▾
Instead of resolving dynamic decisions (evolving batch composition, MoE routing) with a runtime scheduler or host round trip, the compiler pre-determines where each decision arises and which cores it affects, and weaves the handling logic directly into each affected core's fixed schedule — leaving only the actual value to be resolved at execution time, locally.
Q2How is this different from what vLLM/SGLang already do on GPUs?▾
Those systems keep dynamic scheduling logic (request queues, batch composition, dispatch decisions) on the host CPU, which works because host↔GPU coordination is cheap and the host can hold large runtime state. On a wafer-scale mesh, neither is true: host round trips cost ~7,000 cycles and there's no shared memory for a centralized queue. MeshRT moves the equivalent logic on-chip and into the compiled schedule instead.
Q3Why can't a core just run a little scheduler itself at runtime?▾
A WSE-3 core exposes only Compute (local arithmetic + simple branching), Receive, and Send — not a general-purpose instruction stream that could host an open-ended scheduler. Runtime logic has to be small, bounded, and baked into the schedule ahead of time, which is exactly what dynamism-aware synthesis does.
Q4What exactly is the CF (control-flow) payload?▾
A few bytes per batch slot — e.g. (request_id, status) — prepended to an ordinary activation transfer. It's typically <0.2% of the ~4 KB of activation data it rides alongside, so continuous batching adds no standalone network trip.
Q5How does MeshRT differ from WaferLLM, the baseline?▾
Both share the same static execution foundation (2D-tiled GEMM/GEMV, neighbor-based AllReduce). WaferLLM uses PE-level if-else branching among a few pre-compiled paths but has no per-request metainfo propagation (fixed, padded batches), no distributed expert routing (MoE experts tiled in one block, no expert parallelism), and no decentralized reconfiguration. MeshRT adds all three via compiled dynamism handling.
Q6Why is incremental materialization needed — why not just compile the whole schedule and install it once?▾
A core's full synthesized schedule across an entire forward pass can exceed its local routing, queue, and buffer capacity. There's no HBM to spill to and no runtime to reschedule on. So the compiler partitions each core's schedule into segments sized to fit the hardware budget, and reconfigures between segments as execution proceeds.
Q7Does MeshRT beat GPUs on every metric?▾
No — prefill (compute-bound) still favors GPUs: 1.3–2.3× lower per-user latency and, under ideal linear scaling, 25–61× higher projected system throughput. MeshRT's advantage is concentrated in decode: 4.5–7.0× lower latency and 1.6–12.1× better energy efficiency, where SRAM bandwidth and on-chip dynamism handling dominate.
Q8Does MeshRT decide which cores get which kernels (the spatial mapping)?▾
No. Mapping choices are a required input to MeshRT, selected empirically in the paper's evaluation. MeshRT's contribution starts once a computation graph and mapping are fixed — synthesizing schedules and making them fit hardware budgets.
Q9What happens with a model that uses an operator type outside the paper's evaluated set?▾
The paper flags this as an open limitation: MeshRT's synthesis depends on a closed, known set of kernel types. A genuinely novel operator (state-space models, new linear-attention variants) may need new kernel implementations, and potentially new dynamism-handling mechanisms, before the existing compiler pass applies.
Q10Does MeshRT handle multiple models or tenants on one wafer, or PE hardware failures?▾
No to both, by explicit scope. MeshRT assumes exclusive single-model access to the mesh (multi-tenancy would need PE-region partitioning/migration it doesn't address) and relies entirely on the vendor's manufacturing-defect masking for fault tolerance — it does not detect or recover from runtime PE failures itself.

Core terms
Compile-time governanceMeshRT's architecture: compiling the structure of runtime dynamism into per-core schedules ahead of execution, rather than deferring it to a host or a runtime scheduler.
Runtime dynamismAspects of execution unknown until inference proceeds — evolving batch composition, token-dependent MoE routing, speculative-decode accept/reject decisions.
ReceivesDynamism / ProducesDynamismCompile-time predicates over (kernel, core) pairs that tell the synthesizer where to inject metainfo-resolver / metainfo-producer sub-schedules.
Dynamism-aware schedule synthesisAlgorithm 1: a single topological pass over the computation graph that lowers each kernel to per-core event tables and weaves in dynamism handling.
Safe incremental materializationPartitioning each core's schedule into hardware-budget-sized segments and reconfiguring between them only at provably safe (consistent-cut) boundaries.
Consistent cutA point at which every affected core has reached a mutually agreed-upon state, so no in-flight message can straddle old and new configurations. Naturally provided by collective completion.
Supporting terms
PE / coreA processing element on the WSE-3 mesh: compute + local SRAM + router, no shared memory.
GALSGlobally Asynchronous, Locally Synchronous — no chip-wide clock; coordination only via data arrival.
CF payloadBounded control-flow metainfo piggybacked on activation data (a few bytes vs ~4 KB), avoiding a separate network trip.
RDTRequest Descriptor Table — per-core record of current batch composition (request IDs, KV pointers, sequence lengths).
Expert regionA spatial core region on the mesh dedicated to one expert or fixed expert group in an MoE layer.
TPOTTime Per Output Token — the decode latency metric MeshRT's governance overhead is measured against.
Area-equivalent GPU clusterA projected GPU baseline: one measured GPU instance, scaled by silicon-area ratio (56 H200 dies ≈ 1 WSE-3) under ideal linear scaling.
WaferLLMThe paper's baseline — state-of-the-art wafer-scale inference via PE-level branching among precompiled paths, no continuous batching or expert parallelism.
