FAST 2015 · A Field Guide

Writing where the flash wants it, not where the app asked

Random writes are hard on flash storage — they cause internal fragmentation and degrade sustained performance, especially on mobile and other resource-constrained flash devices — and they're exactly what mobile apps and databases produce constantly. F2FS is Samsung's from-scratch Linux file system that reshapes writes to match how NAND flash and its controller actually work.

📄 "F2FS: A New File System for Flash Storage" · Lee, Sim, Hwang, Cho · Samsung, FAST'15 🎓 Basic SSD/FTL and Linux VFS concepts assumed ⏱ ~30 min read
💾

Lay data out to match the FTL's erase units, log everything append-only and sequential, and separate hot from cold — instead of writing wherever the file happens to land and letting random writes and update-in-place fragment the flash.

Before you begin

What you need before reading F2FS

A TL;DR, a quick glossary of the paper's key nouns, then ten primers you can skip once they feel obvious.

⚡ TL;DR

  • F2FS is a Linux file system built from scratch around flash's real constraints: it lays out on-disk structures to align with the FTL's erase units, logs writes append-only in six hot/warm/cold streams, and replaces LFS's recursive "wandering tree" index with a flat Node Address Table.
  • On mobile it beats EXT4 by up to 3.1× (random write throughput) and 2× (SQLite transactions), cutting real-app elapsed time by up to 40% (Twitter-app trace); on servers it beats EXT4 by up to 2.5× (SATA SSD, varmail) and 1.8× (PCIe SSD, varmail).
  • It matters because it's a working proof that a file system co-designed with its storage device's internal geometry (erase units, associativity, random-write tolerance) beats one designed for generic block devices — the same argument OS-managed memory tiering makes about CXL/NVM.

Quick glossary

FTLFlash Translation Layer — the controller firmware inside an SSD/eMMC/UFS that hides flash's erase-before-write quirks behind a normal block interface.

CheckpointA consistent, recoverable snapshot of file system state written periodically and on sync/unmount.

1Why NAND flash hates random writes▾

NAND flash can only be erased in large blocks, and once erased it can only be written sequentially within that block before it must be erased again ("erase-before-write"). It also wears out after a bounded number of erase cycles.

An update-in-place file system (like EXT4) asks the device to rewrite scattered small regions constantly — this pattern of small in-place writes causes internal fragmentation and can trigger internal garbage collection inside the device, which is slow and shortens its life, especially on mobile and other resource-constrained flash.

Now you're ready: F2FS's entire design point is turning application-level random writes into flash-level sequential writes, before they ever reach the FTL.
2The FTL — a block device pretending to be simple▾

Bare NAND chips expose ugly constraints directly. Modern flash storage (eMMC, UFS, SSD) instead bundles chips behind a controller running an FTL, which remaps logical block addresses to physical flash pages, handles wear-leveling, and exposes a familiar "just a block device" interface.

The FTL itself is log-structured internally — it keeps "log flash blocks" to absorb updates to a data flash block before finally consolidating during garbage collection (GC).

Now you're ready: F2FS doesn't just avoid random writes for its own sake — it tries to write in a way that lines up with how the FTL underneath is already organized, so the two logs don't fight each other.
3Log-structured file systems (LFS), in one line▾

Classic LFS (Rosenblum & Ousterhout, 1992) never overwrites data in place. Every write — new or updated — goes to the next free slot in an append-only log. This turns all writes sequential, at the cost of needing periodic "cleaning" (garbage collection) to reclaim space occupied by now-obsolete old copies.

Now you're ready: F2FS is an LFS at heart, but the paper argues that BTRFS and NILFS2 — despite log-structured/copy-on-write designs — weren't built with flash's specific geometry in mind, which is the gap F2FS fills.
4Inodes, indirect blocks, and the "wandering tree"▾

A file's data is located through a chain of index blocks: the inode points to direct blocks (or indirect blocks, which point to more blocks). In classic LFS, updating one leaf data block means its direct index block must also be rewritten to a new log location — and now its parent indirect block must be rewritten too, and so on up to the inode. One small write cascades upward.

Now you're ready: this cascade is the "wandering tree problem," and F2FS's Node Address Table is built specifically to stop it after just one extra write.
5Hot vs. cold data▾

Some blocks get overwritten constantly (metadata, actively-edited files); others are written once and rarely touched again (photos, videos, archival data). Mixing hot and cold data in the same log segment is wasteful: by the time you want to reclaim that segment, the cold blocks are still valid and have to be copied elsewhere first.

Now you're ready: F2FS's "multi-head logging" writes hot and cold data to separate segments from the start, so cleaning later is cheap and targeted.
6Cleaning / garbage collection, LFS-style▾

As the log fills up, obsolete (invalidated) blocks accumulate. "Cleaning" picks a victim region, copies its still-valid blocks elsewhere, and reclaims the region as free space. Cleaning cost depends heavily on how many valid blocks a victim region holds — fewer is cheaper.

Now you're ready: good hot/cold separation makes cleaning nearly free (victims end up either empty or fully valid); bad separation makes every victim half-full and expensive to clean.
7fsync and why mobile apps care so much▾

fsync forces previously-buffered writes to be durably on disk before returning. Databases like SQLite call it constantly to guarantee no data loss on crash. On mobile, apps like Facebook and Twitter route almost all their storage through SQLite, so fsync latency directly becomes app latency.

Now you're ready: a huge fraction of F2FS's design (roll-forward recovery) exists purely to make fsync cheap without sacrificing crash safety.
8Checkpoints and crash consistency▾

A checkpoint is a snapshot of file-system metadata guaranteed to be internally consistent — a safe point to roll back to after a crash. Writing a full checkpoint on every small sync would be far too expensive, since it touches nearly all dirty metadata.

Now you're ready: F2FS keeps checkpoints infrequent and cheap, then patches the gap between checkpoints with roll-forward recovery for fsync-heavy workloads.
9Write amplification factor (WAF)▾

WAF = (physical bytes actually written to flash) ÷ (logical bytes the application asked to write). A WAF of 1.0 is ideal — no wasted writes. Cleaning/GC and small discard commands both tend to push WAF above 1.0, and a high WAF both slows the system and burns through flash's limited erase cycles faster.

Now you're ready: WAF is the paper's yardstick for how well F2FS's cleaning and discard strategy avoids wasted work at high storage utilization.
10Threaded logging vs. normal logging▾

Normal (append-only) logging always writes to clean, free space — perfectly sequential, but it runs out of free space and needs cleaning. Threaded logging instead writes into holes (invalidated space) inside already-dirty segments — no cleaning needed, but the writes become somewhat random.

Now you're ready: F2FS switches between the two based on how much clean space remains — this is "adaptive logging," and it's the difference between graceful and catastrophic behavior when storage is nearly full.
The whole story in one place

F2FS in a nutshell

The problem, the flash-aware fix, and how the pieces connect.

Modern storage is increasingly flash — eMMC, UFS, SSD — hidden behind an FTL that turns sustained random writes into internal garbage collection headaches. Prior Linux file systems, even log-structured ones like NILFS2 or copy-on-write ones like BTRFS, were not designed with flash's geometry in mind, so they leave performance and device lifetime on the table.

F2FS is built from scratch around three flash-specific ideas. First, its on-disk layout uses configurable segment/section/zone units intended to align with the FTL's own erase and log-block units — especially for set-associative FTL designs — so file-system-level cleaning and FTL-level GC don't fight each other as often. Second, its Node Address Table (NAT) replaces classic LFS's recursive index-block chain with one flat table, killing the "wandering tree" problem — one small update stays one small update. Third, multi-head logging writes hot and cold node/data blocks to six separate log streams from the moment they're created, so cleaning later is cheap.

On top of that, F2FS adapts: it switches between purely sequential ("normal") and hole-filling ("threaded") logging as free space shrinks, and it optimizes fsync-heavy workloads with a lightweight roll-forward recovery that avoids full checkpointing on every sync.

The payoff: on a mobile platform, F2FS beats EXT4 by up to 3.1× (iozone random write) and 2× (SQLite), cutting real workload elapsed time by up to 40%. On servers, it beats EXT4 by up to 2.5× (SATA SSD) and 1.8× (PCIe SSD).

🍯 Key takeaways

  • Random writes are hard on flash and degrade sustained performance; F2FS's entire design turns them into sequential ones, aligned with the FTL's own units where possible.
  • The NAT makes index updates flat (one write) instead of recursive (the "wandering tree").
  • Multi-head logging statically classifies hot/warm/cold node and data blocks into six separate logs — no runtime monitoring needed.
  • Adaptive logging switches from sequential to threaded (hole-filling) writes once free space drops below a 5% threshold, trading write pattern for guaranteed forward progress.
  • Roll-forward recovery makes fsync cheap by writing only data + direct node blocks with a special flag, replaying just those after a crash.
  • Result: up to 3.1× (mobile random write), 2× (SQLite), 2.5× (server SATA), all for a file system already shipping in the Linux kernel since 3.8.
Seven everyday pictures

How to think about F2FS

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Append-only logging

Never erase mid-page

A notebook where you never scratch out a line — you just write the correction on the next blank line and move on. That's LFS: every write goes to the next free slot in the log, turning scattered edits into one steady stream of sequential writes flash handles well.

Where it breaks: the notebook eventually fills up. Old, scratched-through lines still take space, so you periodically have to "clean" — copy what's still valid to a fresh notebook and recycle the old pages.
The fix · Node Address Table

One change-of-address card

Move house and you don't track down every relative to fix their address book — you file one change-of-address card, and everyone's mail is forwarded automatically. F2FS's NAT is that card: update one leaf data block, rewrite one direct node block, update its one NAT entry — done. No cascading rewrite up through indirect blocks and the inode.

Where it breaks: this only works because there's exactly one central forwarding table. If a system had many independent trees pointing at the same block with no shared indirection layer, one card wouldn't be enough.
Hot/cold separation · Multi-head logging

Sorting the mail into bins

Sort incoming mail by how soon you'll deal with it again — bills in one bin, catalogs in another — instead of piling everything together. F2FS does this at write time: direct node blocks and directory data are "hot," regular file data is "warm," and cleaned or user-marked or multimedia data is "cold," each going to its own log segment.

Where it breaks: F2FS guesses the bin from static clues (file type, operation, extension) rather than watching actual access behavior — a misclassified file sits in the wrong bin until the next cleaning cycle sorts it out.
Alignment · Segment/section/zone

Boxes sized to the truck's shelves

Pack moving boxes to fit the truck's shelving, and the movers are less likely to have to unpack a half-filled shelf to make room. F2FS's segments/sections/zones are configurable, and the paper intends them to line up with the FTL's own erase and "log flash block" units, so file-system cleaning and device-level garbage collection don't collide as often.

Where it breaks: this only pays off if you know the shelf size (FTL associativity) in advance. F2FS's zone mapping strategy is tuned for set-associative FTLs — a different FTL design could reduce the benefit.
Cleaning policy · Greedy vs. cost-benefit

Two ways to declutter a drawer

In a hurry, you grab the emptiest drawer to declutter — fast, low effort (greedy). With time to spare, you instead weigh emptiness and how long something's sat untouched, since an old, slowly-filling drawer might be worth clearing even if it's not the emptiest right now (cost-benefit). F2FS uses greedy for latency-sensitive foreground cleaning and cost-benefit for background cleaning.

Where it breaks: cost-benefit's age-aware patience only helps when there's idle time to run it in the background — under sustained load, F2FS falls back to plain greedy, old-and-nearly-full sections and all.
Adaptive logging · Normal vs. threaded

Detour when the highway jams

The highway (clean, sequential space) is fastest — until it's jammed (free sections nearly exhausted). Then you take side streets (write into holes in dirty segments) to guarantee forward progress, even though it's a bit less direct. F2FS switches to threaded logging once clean sections drop below a 5% threshold.

Where it breaks: side streets (random writes) are "not that bad" specifically because flash tolerates random writes far better than spinning disks — the same detour would be a real disaster on an HDD.
fsync path · Roll-forward recovery

A sticky note, not a re-copied ledger

Instead of re-copying an entire ledger every time you jot a note, you keep a sticky note of just today's edits and reconcile it later. F2FS's roll-forward recovery writes only the data block and its one flagged direct node block on fsync, then after a crash replays just those flagged blocks to catch the ledger (the last checkpoint) up to date.

Where it breaks: it only recovers what was actually flagged and written before the crash — anything still purely buffered in the page cache with no on-disk trace is lost, the same fundamental limit any journaling scheme has.
The full explanation

How it actually works

Section by section, following the paper's own structure, with diagrams and one interactive.

1 · Flash-friendly layout, and a file lookup walked through

F2FS divides the whole volume into six areas — Superblock, Checkpoint, SIT, NAT, SSA, and Main (see the layout figure on the Big Idea tab). Segments, sections, and zones are the allocation units layered on top of this — their sizes are configurable and intended to align with the FTL's own erase and log-block units, especially for set-associative FTL designs, so file-system cleaning doesn't have to fight FTL-level GC as often.

Concretely, looking up /dir/file takes these steps:

  1. Read the root inode's block location from NAT.
  2. Search the root inode's data blocks for a directory entry named dir, get its inode number.
  3. Translate that inode number to a physical location via NAT again.
  4. Read the dir inode block.
  5. Inside it, find file's directory entry, and repeat steps 3–4 to get file's inode — then read the actual data from Main using the indices in that inode.
🌱
NAT resolves each node ID (the root inode, the dir inode, the file inode) to a physical location — steps 1, 3, and 5 all depend on it. But the directory-entry search itself happens by scanning the directory's own data blocks, and once file's inode is found, its actual data is retrieved via the indices inside that inode, not through NAT — NAT locates node/inode blocks, it isn't the path to every byte.

2 · File structure — killing the wandering tree

An inode block holds direct pointers, two single-indirect, two double-indirect, and one triple-indirect pointer — plus optional inline data (files under 3,692 bytes) and inline extended attributes (200 bytes reserved), avoiding a separate block entirely for small files/attributes.

3 · Multi-head logging — six streams, statically classified

F2FS runs up to six active log segments simultaneously, one per temperature level:

TypeTemp.Objects
NodeHotDirect node blocks for directories
NodeWarmDirect node blocks for regular files
NodeColdIndirect node blocks
DataHotDirectory entry blocks
DataWarmData blocks made by users
DataColdCleaning-migrated blocks; user-marked cold blocks; multimedia file data (by extension)
💡
Why static classification works well enough: temperature is inferred from cheap, always-available signals — file operation (append vs. overwrite), file type (directory vs. regular), and extension — rather than runtime access monitoring. With six logs, a controlled experiment shows a clearly bimodal distribution of valid blocks per dirty segment (many near-empty, many near-full) — exactly what good hot/cold separation should look like, versus a much flatter distribution with only two logs.

4 · Cleaning — pick a victim, migrate, then free

1 · Victim selection
Greedy (fewest valid blocks) in the foreground; cost-benefit (valid blocks + age) in the background

2 · Migration

🌱
The "pre-free" delay matters: reusing a section before its checkpoint lands could lose data still referenced by the previous, still-current checkpoint.

5 · Adaptive logging — try it yourself

F2FS defaults to normal (sequential) logging while more than 5% of sections are clean, then switches to threaded (hole-filling) logging once free space drops below that. The interactive below uses the paper's own utilization-vs-cost measurements (§3.2.4, Fig. 7) for the performance-loss and WAF trend: as file-system utilization climbs from 80% toward 97.5%, both grow — but only the 97.5% point is the paper's own reported number for those two figures.

6 · Checkpointing and recovery

A full checkpoint flushes dirty node/dentry blocks, suspends ordinary file-system calls, writes NAT/SIT/SSA, then writes a checkpoint pack (header/footer with a version number, NAT/SIT bitmaps and journals, active-segment summaries, and orphan-inode info) into one of two alternating segments (#0/#1) — so one stable pack always survives a crash.

For fsync-heavy workloads, a full checkpoint every sync would be far too costly. Roll-forward recovery instead:

  1. Collects direct node blocks with a special flag, written since the last stable checkpoint at log position N (call the range N+n).
  2. Loads the most recently checkpointed versions of those same node blocks (N-n) into the page cache.
  3. Compares the data indices between N-n and N+n.
  4. Refreshes and marks dirty any node blocks whose indices differ, then performs one checkpoint to make the recovered state permanent.
Follow the numbers, step by step

Worked examples

Four traces through the paper's own numbers — index-update savings, fsync efficiency, the utilization cliff, and adaptive logging's payoff.

① Counting index-block writes saved by NAT

Suppose an app appends 1,000 times to a 2GB file (in the 8MB–4GB range), 4KB at a time, ignoring cache effects. How many index-propagation block writes (data + pointer/node blocks, excluding NAT-entry updates) does classic LFS need vs. F2FS?

  1. Both write the leaf data block each time: 1,000 leaf writes for each system.
  2. LFS (8MB–4GB range): per the paper, each append also recursively rewrites 2 pointer blocks (direct + indirect). Total = 1,000 + 1,000×2 = 3,000 block writes.
  3. F2FS: each append rewrites 1 direct node block and updates its NAT entry. Counting only index-propagation writes (data + pointer/node blocks, as the paper's comparison does): Total = 1,000 + 1,000×1 = 2,000 writes. (F2FS's true total also includes 1,000 NAT-entry updates — the paper's point isn't that NAT updates are free, but that they stay flat at one per append instead of cascading.)
  4. Savings (index-propagation writes only): (3,000 − 2,000) / 3,000 = 33% fewer index-propagation writes.
  5. Now redo it for a >4GB file: LFS adds a third pointer block (double-indirect) — 1,000 + 1,000×3 = 4,000; F2FS is still 2,000 (plus 1,000 NAT-entry updates). Savings = (4,000−2,000)/4,000 = 50% fewer index-propagation writes.
🍯
Insight: the wandering-tree fix gets more valuable as files (and their indirect-pointer depth) grow — exactly why the paper calls out both size ranges explicitly.

② Why roll-forward recovery roughly doubles SQLite TPS

F2FS cuts SQLite's data writes by ~46% versus EXT4 and reports up to 2× the transactions per second (TPS). How do these connect?

  1. Naive fsync via full checkpointing would flush all dirty node and dentry blocks system-wide — vastly more than the one data block and one direct node block that actually changed.
  2. Roll-forward recovery writes only the changed data block + its flagged direct node block per fsync, deferring everything else to an infrequent checkpoint.
  3. Measured result: across insert/update/delete, F2FS writes ~46% less data than EXT4 for the same SQLite workload.
  4. Since these transactions are fsync/write-latency bound (not CPU bound), writing roughly half the data per transaction plausibly lets roughly twice as many transactions complete per second — consistent with, though not a strict derivation of, the reported up to 2× TPS.
💡
Contrast with BTRFS, which writes 3× more data than EXT4 here (heavy indexing overhead) and loses ~80% performance — the same fsync-bound logic, running in reverse.

③ The utilization cliff: small WAF, big slowdown

At 97.5% file-system utilization, the paper reports ~30% performance loss but WAF of only ~1.02. Isn't a 2% write overhead too small to explain a 30% slowdown?

  1. WAF 1.02 means only about 2% more physical bytes are written than logically requested — a small bandwidth overhead.
  2. Foreground cleaning is triggered once free sections run low, and the paper reports that GC/cleaning activity increases as utilization rises, blocking the application while it identifies and migrates valid blocks.
  3. A plausible explanation, not a measured one: the 30% loss could come mostly from stall latency rather than bandwidth — the application waiting on cleaning operations even though those operations don't move many extra bytes. The paper doesn't decompose latency vs. bandwidth cost directly, so this is the guide's own inference.
  4. Consistency check: with the default 5% overprovisioning and 512-block sections, a near-full (97.5% utilized) file system leaves very little slack, so foreground cleaning has to run often and each victim section still holds many valid blocks to migrate first.
🍯
Insight: the paper shows performance loss and WAF both grow with utilization, but it doesn't establish that stall latency (rather than bytes written) is the dominant cost — that's this guide's best guess, and it's consistent with why adaptive (threaded) logging, not just "write less," is the paper's real fix.

④ What adaptive logging buys at 94% fill

In the fileserver aging test (device filled to 94%, workload repeated four times), F2FS_normal's performance dropped 48% between round 1 and round 2, while F2FS_adaptive dropped only 22%, and F2FS_normal wrote 27% more data overall than F2FS_adaptive. Quantify the benefit.

  1. Relative drop reduction: 22% / 48% ≈ 0.46 — adaptive logging's round-2 performance drop is less than half of normal logging's drop.
  2. Extra data written by normal logging: 27% more than adaptive — that's the direct cost of foreground cleaning it triggers to keep finding clean sequential space.
  3. Where that 27% comes from: normal logging insists on clean segments, so when free space runs low it must clean (copy valid blocks) before it can keep writing sequentially — extra migration writes that adaptive logging mostly avoids by switching to threaded logging instead.
  4. Net effect: F2FS_adaptive keeps pace comparable to BTRFS's 22% drop and stays within reach of EXT4's mild 17% drop, while F2FS overall still maintains a 2×-or-better improvement ratio over EXT4 across all four rounds.
💡
This is the paper's clearest demonstration that "always stay sequential" is not always the right rule — sometimes guaranteeing forward progress (threaded logging) beats insisting on purity.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why does F2FS size its segments, sections, and zones to align with the FTL's erase and log-block units, instead of just picking a convenient fixed block size?
Show answer
Because cleaning happens at both levels — F2FS cleans at the file-system level (sections), and the FTL garbage-collects at the flash level (erase blocks / log flash blocks). If the units don't align, an F2FS-level clean operation can straddle multiple FTL erase units (or vice versa), triggering extra, uncoordinated device-level GC. Aligning them means a clean operation is more likely to map cleanly onto a device-level operation.Misconception: that a file system's allocation unit size is an arbitrary implementation choice. Here it's a configurable, deliberate co-design decision with the specific FTL association strategy (set-associative) F2FS targets, not a guarantee of an exact match with every FTL.
Problem 2 · medium
A 10GB file (well over 4GB) receives 500 sequential 4KB appends. Using the paper's stated update counts and ignoring cache effects, how many total index-propagation block writes (leaf data + pointer/node blocks, excluding F2FS's NAT-entry updates) does classic LFS need, and how many does F2FS need?
Show answer
For files >4GB, LFS rewrites 3 pointer blocks recursively per append: 500 leaf + 500×3 pointer = 2,000 total. F2FS rewrites only 1 direct node block per append: 500 leaf + 500×1 = 1,000 total — exactly half. (F2FS also updates 500 NAT entries, one per append, which the paper's comparison counts separately from this index-propagation total.)Misconception: that the wandering-tree savings are the same regardless of file size. They get proportionally larger for bigger files, since larger files need deeper (triple-indirect) index trees in classic LFS.
Problem 3 · medium
A cleaning-migrated block, a user-tagged "cold" block, and a JPEG photo all end up in the same F2FS log. What do they have in common that put them there, and what's the misconception this challenges?
Show answer
All three are classified "cold data" — not because they're all old files, but because F2FS expects each to remain valid and unmodified for a long time: cleaning-migrated blocks have already survived one cleaning pass, user-tagged blocks are explicitly marked, and multimedia files are typically write-once/read-only by extension match. "Cold" means "expected not to change soon," determined at write time from static signals — not measured recency of access.Misconception: that "cold" means "old" or "rarely accessed so far." It's a forward-looking prediction about future write behavior, made from cheap static heuristics, not a backward-looking access-frequency measurement.
Problem 4 · hard
Why does F2FS use the greedy victim-selection policy for foreground cleaning but cost-benefit for background cleaning, rather than always using whichever policy cleans the fewest total bytes over time?
Show answer
Foreground cleaning happens synchronously, blocking the application until enough free sections exist — so latency, not long-run efficiency, is what matters, and greedy (pick the section needing the least migration work right now) minimizes that latency. Background cleaning runs during idle time with no latency pressure, so it can afford cost-benefit's extra consideration of section age, which better separates hot and cold data over time and reduces future cleaning cost — a benefit only realizable when you're not in a hurry.Misconception: that one policy is simply "better" than the other in isolation. The right policy depends on whether the cleaning is on or off the application's critical path.
Problem 5 · medium
F2FS switches from normal to threaded logging once free sections drop below its default 5% threshold. What would go wrong if that threshold were set to 0% instead (i.e., only switch when completely out of clean sections)?
Show answer
Waiting until sections are literally exhausted means every write right up to that point still demands a clean sequential run, forcing foreground cleaning to scramble constantly right at the threshold — exactly the harsh, high-latency behavior the paper measures for "F2FS_normal" under heavy fragmentation (performance dropping to under 5% of EXT4 in the iozone aging test). A nonzero threshold gives the switch some slack to happen before things get desperate.Misconception: that delaying the switch as long as possible maximizes sequential-write benefit. In practice it just delays the cliff, making the eventual transition more abrupt and costly.
Problem 6 · hard
Explain, using the roll-forward algorithm's four steps, why F2FS can safely skip writing indirect node blocks and most metadata on every fsync.
Show answer
Roll-forward only needs to reconstruct which data indices changed since the last checkpoint, and it can find that out by comparing the last-checkpointed direct node blocks (N-n) against the newer, specially-flagged direct node blocks written since (N+n) — direct node blocks are exactly where those data-block addresses live. Indirect node blocks only change when whole node blocks are added/removed (not on ordinary data writes), so they're irrelevant to catching up individual data writes and can be safely deferred to the next full checkpoint.Misconception: that skipping metadata writes on fsync risks losing consistency. Consistency is preserved because the skipped metadata (indirect blocks, most of NAT/SIT) didn't actually change — only the roll-forward-relevant direct node blocks did.
Problem 7 · easy
On the videoserver Filebench workload (mostly sequential reads/writes), F2FS, EXT4, BTRFS, and NILFS2 all perform about the same. Why doesn't F2FS's design advantage show up here?
Show answer
F2FS's advantages (turning random writes sequential, cheap fsync via roll-forward, hot/cold separation) all target problems that arise from randomMisconception: that a better-designed file system should win on every workload. F2FS's gains are concentrated precisely where its target problem (random writes, fsync) actually occurs.
Problem 8 · medium
On the fileserver workload, EXT4 issues far more small discard ("trim") commands than F2FS (trimming two-thirds of its block address space with mostly sub-256KB discards, versus F2FS's 38% with no small discards), yet F2FS is 2.4× faster. What's the misconception this challenges?
Show answer
More discard/trim activity is not automatically helpful — small, frequent discard commands carry real command-processing overhead, especially on SATA. F2FS avoids this by discarding obsolete space only in whole segments, only at checkpoint time, so it issues far fewer, larger discards. Trimming less total space but doing it coarsely and infrequently outperforms trimming more space in many small, frequent commands.Misconception: that discard/trim hints are a pure win the more you issue them. Discard commands have processing costs of their own, and granularity/frequency matter as much as total coverage.

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1Is F2FS just another log-structured file system?▾
It builds on LFS's append-only core idea, but deviates significantly: flash-aligned layout units, a flat NAT instead of recursive index chains, multi-head hot/cold logging, adaptive normal/threaded logging, and roll-forward recovery are all F2FS-specific additions the original LFS proposal didn't have.
Q2Why not just use NILFS2 or BTRFS, which are already log-structured / copy-on-write?▾
The paper argues neither was designed with flash's specific geometry in mind. NILFS2's periodic synchronous flushes hurt sequential write performance (~50% degradation) and it issues up to 30% more write requests than others; BTRFS's heavy indexing overhead makes it write 3× more data than EXT4 under SQLite, costing ~80% of performance.
Q3What exactly is the "wandering tree problem"?▾
In classic LFS, updating one leaf data block forces its direct index block to be rewritten (since it moved), which forces its parent indirect block to be rewritten, and so on up to the inode — one small update cascades into a chain of writes.
Q4How does the Node Address Table (NAT) actually fix that?▾
NAT is a flat table mapping every node ID directly to its physical location. When a direct node block moves, only its one NAT entry needs updating — the inode and any indirect blocks above it don't need to change at all, since they never stored a physical address, only a node ID that NAT resolves.
Q5What are segments, sections, and zones, concretely?▾
A segment is F2FS's basic allocation unit; a section is a group of consecutive segments (the unit of cleaning); a zone is a group of sections. Their sizes are configurable and intended to align with the underlying FTL's own management units, especially for set-associative FTLs, so file-system cleaning and device garbage collection are less likely to fight each other.
Q6How does F2FS decide whether data is "hot" or "cold"?▾
Statically, from cheap signals available at write time: node type (direct vs. indirect), whether data belongs to a directory or regular file, whether a block was just migrated by cleaning, an explicit user extended-attribute tag, or a matching "multimedia" file extension — no runtime access monitoring required.
Q7What's the difference between normal and threaded logging?▾
Normal logging always writes to clean, free segments — perfectly sequential, but requires cleaning once free space runs low. Threaded logging writes into holes (invalidated space) within already-dirty segments — no cleaning needed, but the resulting writes are less sequential. F2FS switches to threaded logging once fewer than 5% of sections remain clean (configurable).
Q8Why does roll-forward recovery only need direct node blocks?▾
Direct node blocks are where data-block addresses actually live. By flagging them specially and comparing the newest flagged versions against the last checkpoint's versions, F2FS can tell exactly which data indices changed since the last checkpoint — without needing to touch indirect blocks or most file-system metadata at all.
Q9Does F2FS always beat EXT4?▾
No — on mostly-sequential workloads like videoserver, all tested file systems perform about the same, since there's no random-write or fsync problem for F2FS's mechanisms to fix. Gains are largest specifically on random-write and fsync-heavy workloads (mobile SQLite/app traces, server varmail/oltp).
Q10What is write amplification factor (WAF) and why does the paper track it?▾
WAF = physical bytes written ÷ logical bytes requested. It's the paper's yardstick for how much "extra" work cleaning imposes at high storage utilization. F2FS's adaptive logging is shown to keep WAF low (~1.02 even at 97.5% utilization) largely by avoiding unnecessary foreground cleaning.
Q11Would F2FS help on a traditional hard disk drive?▾
Not by the paper's own logic — threaded logging's random writes are tolerable specifically because flash handles random writes far better than HDDs. On an HDD, that same detour would reintroduce the seek-heavy random I/O that log-structured designs exist to avoid in the first place.
Q12Is F2FS still relevant / where is it used?▾
F2FS has been in the mainline Linux kernel since version 3.8 (2012) and is used in commercial products, particularly Android devices and embedded/mobile flash storage, per the paper's own footnote.
Zooming out

What this means for OS-managed memory systems

Four short connections between F2FS's choices and the broader problem of software that must know about its underlying medium's real geometry. These are this guide's own extrapolations, not claims the paper makes.

🧱 Erase-unit alignment ↔ tiering's placement granularity

F2FS's segment/section/zone sizes are configurable and intended to align with the FTL's erase and log-block units — especially for set-associative FTL designs — so file-system-level and device-level cleaning are less likely to collide. OS-managed DRAM/NVM or CXL tiering faces an analogous problem in a different guise: migration/promotion granularity (a 4KB page, a 2MB huge page, or a CXL device's own internal interleave/wear unit) arguably needs to be chosen with the device's real physical geometry in mind, not just what's convenient for the page table.

🌡️ Static hot/cold classification ↔ page-placement heuristics

F2FS classifies data temperature from cheap static signals (file type, operation, extension) rather than runtime access monitoring — and it works well enough that the paper never needed a Memtis/TPP-style PEBS-driven hotness tracker. That's a suggestive analogy for tiering research, not a claim the paper makes about memory systems: before reaching for expensive runtime access-tracking, it's worth asking how far a cheap structural heuristic (allocation site, object type, access pattern class) gets you, and reserving dynamic monitoring for what static signals can't capture.

🔀 Adaptive logging ↔ threshold-based tier-pressure policies

F2FS's switch from normal to threaded logging at a 5%-free-sections watermark is structurally analogous to a tiering system switching promotion/demotion aggressiveness (or falling back to remote/slow-tier allocation) once a fast-tier occupancy watermark is crossed — both trade a "purer" policy for guaranteed forward progress once headroom runs low, and both accept a policy discontinuity right at the threshold as the price. This is an analogy this guide draws, not a comparison the paper itself makes.

🧾 Roll-forward recovery ↔ persistent-memory consistency

F2FS's roll-forward recovery — flag only what actually changed since the last checkpoint, replay just that — resembles the crash-consistency strategies persistent-memory file systems (e.g., NOVA-style per-inode logs) use to avoid full-volume journaling on every durable write. A CXL-attached persistent memory tier would plausibly benefit from an analogous "cheap incremental recovery" primitive rather than treating every write as requiring full-checkpoint-grade durability — though this extends well beyond anything either paper claims directly.

🍯
The throughline for LtRAM-style tiering work: F2FS's 2–3× wins came from refusing to treat the storage device as an opaque flat block range and instead exposing its real internal structure (erase units, associativity, wear) up through the software stack — an analogy for why OS memory tiering may similarly benefit from being CXL/NVM-geometry-aware rather than device-agnostic.

Sharp questions for seminar

Each references a specific claim, number, or design decision — enough context to raise it confidently.

  1. Given that F2FS's hot/cold classification is entirely static (file type, operation, extension, §2.4) while SFS (built on NILFS2, cited in §4.1) uses runtime "update likelihood" monitoring, is the 20% (Facebook-app) vs. 40% (Twitter-app) gap in real-world gains evidence that static heuristics are leaving performance on the table for some access patterns (the paper never runs SFS head-to-head on these same traces)?
  2. Foreground cleaning uses greedy victim selection purely to bound latency (§2.5) — would borrowing cost-benefit's age-awareness into foreground cleaning, accepting slightly higher tail latency, actually reduce total cleaning work enough to be worth it (the paper only justifies greedy foreground by latency, never quantifies the total-work tradeoff)?
  3. The 5%-free-sections threshold for switching to threaded logging (§2.6) is a fixed default — should it instead be set per-device, given that the paper's own oltp results show SATA and PCIe SSDs hit different bottleneck points (§3.2.2) (threaded logging's "not too costly" argument rests on flash tolerating random writes well, which varies by device)?
  4. F2FS's zone-to-log mapping is explicitly tuned for set-associative FTLs (§2.4) — how much of the reported 3.1×/2.5× gains would survive on a fully-associative or a multi-streaming-capable FTL, where the multi-streaming interface (cited in §2.4) might make F2FS's own zone alignment partially redundant (the paper mentions multi-streaming as a "natural match" but never measures it directly)?
  5. At 97.5% utilization the paper reports ~30% performance loss but only WAF ~1.02 (§3.2.4) — if the loss is indeed dominated by foreground-cleaning stall latency rather than bytes written, would a purely asynchronous (non-blocking) cleaning design close most of that 30% gap, or does something else force cleaning onto the critical path (the paper attributes the loss to GC overhead but doesn't decompose latency vs. bandwidth cost directly)?

Glossary & further reading

Every term in one place, results at a glance, then a path to go deeper.

Core terms
F2FSThe paper's file system — a Linux LFS-derived design built around flash storage's specific erase, alignment, and random-write characteristics.
LFSLog-structured File System — never overwrite in place, always append; the classical basis F2FS builds on and modifies.
FTLFlash Translation Layer — controller firmware that hides NAND's erase-before-write quirks behind a generic block interface (eMMC, UFS, SSD).
Wandering tree problemLFS's flaw where updating a leaf block cascades rewrites up through every indirect index block above it to the inode.
NAT (Node Address Table)F2FS's flat node-ID-to-location table; the mechanism that reduces the wandering-tree cascade to one extra write.
SIT (Segment Information Table)Per-segment metadata (valid block count, validity bitmap) used to pick cleaning victims.
SSA (Segment Summary Area)Owner information for every block in Main, used to find a block's parent node quickly during cleaning.
CheckpointA periodically-written, internally consistent snapshot of file-system state — the recovery point after a crash.
Roll-forward recoveryCheap fsync-time recovery mechanism: write only flagged direct node blocks, replay just those after a crash instead of full checkpointing.
Threaded loggingWriting into holes (invalidated space) within dirty segments instead of clean free space — avoids cleaning at the cost of write sequentiality.
WAF (write amplification factor)Physical bytes written ÷ logical bytes requested; the paper's measure of cleaning/discard overhead at high utilization.
Supporting terms
Segment / section / zoneF2FS's nested allocation units — their sizes are configurable and intended to align with the FTL's own erase/management units, especially for set-associative FTL designs.
Hot / warm / cold dataF2FS's three temperature levels for node and data blocks, statically inferred and written to separate logs.
Greedy / cost-benefit victim selectionForeground cleaning picks the section with fewest valid blocks (fast); background cleaning also weighs section age.
Inline data / inline xattrSmall files (<3,692 bytes) or extended attributes (≤200 bytes) stored directly in the inode block, avoiding an extra block.
Multi-streamingA device interface letting software tag writes by stream, so an FTL can keep them physically separate — a natural match for F2FS's multi-head logging.
eMMC / UFS / SSDFlash storage packaging types the paper targets — chips plus a dedicated FTL controller, exposed as a generic block device.
fsyncA system call forcing buffered writes durably to disk before returning — heavily used by SQLite and the mobile apps built on it.
DentryDirectory entry — a slot recording a file name, inode number, and type inside a directory data block.
Direct / indirect node blockDirect blocks hold data-block addresses; indirect blocks hold other node IDs, forming the index chain above data.
Lazy background migrationBackground cleaning loads valid blocks into the page cache and marks them dirty rather than issuing immediate I/O, letting the kernel batch the actual flush.
