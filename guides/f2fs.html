Write sequentially, sort by lifetime, and find every node through one table

A 2015 paper from Samsung's memory business: a Linux file system that keeps the log-structured idea from LFS but rebuilds it around the flash translation layer inside phones and SSDs. Six logs sorted by expected update rate, a node address table that stops index updates from cascading, cleaning tuned for latency, a switch to filling holes in place when free space runs out, and an fsync path that writes only data and direct node blocks.

Before you begin

A log-structured file system rebuilt around the flash translation layer

A 2015 paper from Samsung's memory business describing F2FS, which had been in mainline Linux since 3.8 (late 2012). It keeps LFS's append-only log and cleaner, and changes almost everything else for eMMC, UFS and SSD devices that hide raw NAND behind firmware.

⚡ TL;DR

  • Problem: phone apps issue mostly small random writes followed by fsync (the paper cites studies: over 80% of I/Os random, over 70% of random writes triggered by fsync, mostly from SQLite). On flash behind a flash translation layer (FTL), random writes are slow (the test eMMC writes 72 MB/s sequentially but 12 MB/s randomly) and wear the device through internal garbage collection.
  • Layout: fixed metadata areas up front (checkpoint, segment information table SIT, node address table NAT, segment summary area SSA) and a Main area written as logs, in 2 MB segments (512 blocks of 4 KB) grouped into sections (the cleaning unit) and zones, sized to match the FTL.
  • Index: indirect node blocks store node IDs, not addresses, and the NAT maps each node ID to its current location. A data update rewrites one direct node block plus one NAT entry, instead of LFS's chain of pointer blocks (the "wandering tree").
  • Six logs: hot, warm and cold logs for node blocks and for data blocks, assigned by static rules (directory blocks hot, user data warm, cleaned or multimedia data cold), so segments tend to end up nearly empty or nearly full and cleaning copies little.
  • When space runs out: cleaning is greedy in the foreground and cost-benefit in the background, with 5% of space reserved; when clean sections drop to 5% of all sections, F2FS switches from appending to threaded logging (writing into holes of dirty segments) to avoid foreground cleaning. fsync writes only the data and its direct node blocks; a crash is repaired by rolling back to the last checkpoint and rolling forward over flagged node blocks.
  • Results versus EXT4: on a Galaxy S4, up to 3.1× iozone random-write bandwidth and 2× SQLite transactions per second, 20% and 40% less elapsed time on Facebook and Twitter traces; on servers up to 2.5× (SATA SSD, varmail) and 1.8× (PCIe SSD), with no loss on sequential I/O.

Quick glossary
NAND pageThe unit a NAND flash chip reads and programs (writes): a row of cells, typically 4 to 16 KB plus a spare area. A programmed page cannot be reprogrammed until its whole block is erased.
Erase blockThe unit a NAND chip erases: a group of typically 64 to several hundred pages (hundreds of KB to several MB). Erasing resets every cell in it; pages inside must then be programmed in order.
FTL (flash translation layer)Firmware running on the flash device's controller that presents a normal block device: it keeps a table from logical block addresses to physical flash pages, writes every update to a fresh page, and garbage-collects old pages.
Garbage collection (GC), inside the deviceThe FTL's process of picking an erase block, copying its still-valid pages elsewhere, and erasing it so it can be written again. The copies are extra writes the host never asked for.
Write amplification factor (WAF)A ratio: bytes actually written divided by bytes the layer above asked to write. 1.0 means no extra writes; GC and cleaning raise it.
eMMC, UFS, SSDPackaged flash storage: several NAND chips plus a controller running an FTL. eMMC and UFS are the soldered-down kinds used in phones; SSD is the drive form used in PCs and servers.
Log-structured file system (LFS)A file system that never overwrites in place: every changed block, including metadata, is appended at the head of a log, and a cleaner later compacts partly dead regions to make free space.
Segment (F2FS)A fixed-size, aligned run of 512 blocks of 4 KB (2 MB) in the Main area; the unit in which logs are allocated and the SIT keeps statistics.
Section and zoneA section is a configurable number of consecutive segments, the unit of cleaning; a zone is a configurable number of consecutive sections, used to keep different logs in different FTL regions.
Node blockA 4 KB block in the Main area that holds index information rather than file contents: an inode, a direct node (data block addresses) or an indirect node (node IDs). Each has a fixed node ID.
NAT (node address table)A table in a fixed area, indexed by node ID, whose entry holds the current physical block address of that node block. It extends LFS's inode map to every node block.
SIT (segment information table)A table in a fixed area with one entry per segment: the count of valid blocks, a bitmap with one validity bit per block, and the last modification time.
SSA (segment summary area)A fixed area with one summary entry per Main-area block, recording which node owns that block and at which offset, so the cleaner can find and update the block's parent.
Checkpoint packA self-describing record written to one of two slots in the checkpoint area: header and footer with matching version numbers, NAT and SIT set bitmaps, small NAT and SIT journals, active-segment summaries and orphan inodes.
Hot, warm, coldF2FS's three temperature labels: predictions of how soon a block will be overwritten (hot soon, cold rarely), fixed by block type and simple hints rather than measured.
CleaningThe file system's own garbage collection: choose a victim section, move its valid blocks to a log, and free the section. It is a second GC on top of the FTL's.
Normal logging and threaded loggingTwo ways to place new blocks: normal logging appends to a clean segment (strictly sequential); threaded logging writes into invalid slots (holes) of a dirty segment, needing no cleaning but producing scattered writes.
Roll-back and roll-forward recoveryRoll-back restores the state recorded by the last valid checkpoint; roll-forward then replays specific later writes found in the log (in F2FS, only flagged direct node blocks written by fsync).
fsyncA system call that returns only after a file's modified data and the metadata needed to read it back are on stable storage.
Discard (trim)A command telling the device that a logical address range holds no valid data, so the FTL can skip copying it during GC (paper footnote 3).
Short primers (tap to open)
1NAND flash: pages, erase blocks, and no overwrite▾

A NAND chip stores bits as charge in cells arranged in pages (rows read and written together, typically 4 to 16 KB) and erase blocks (groups of typically 64 to 512 pages). Three rules shape everything above it (general knowledge; the paper names the same three limits): a page can only be programmed after its block has been erased, so there is no overwrite in place; pages in a block must be programmed in order; and each block survives only a limited number of program/erase cycles (thousands for the multi-level cells of 2015, fewer for later denser cells).

The operations are also unequal in time (illustrative figures for 2015-era parts): reading a page takes tens of microseconds, programming hundreds of microseconds, erasing a block milliseconds. So "update 4 KB" cannot mean "rewrite those cells". The new version must go to an already-erased page somewhere else, and the old page becomes garbage that occupies space until its whole block is erased.

For a reader who works on NVM: this is the strongest form of write asymmetry. Phase-change memory and RRAM allow overwrite at small granularity with slow, wearing writes; NAND forbids overwrite entirely and makes the reclaim unit (the block) hundreds of times larger than the write unit (the page).

Now you're ready: any layer that writes to NAND is log-structured underneath, whether the file system knows it or not.
2The FTL: mapping granularity and garbage collection inside the device▾

eMMC, UFS and SSDs hide NAND behind a controller running an FTL, which exposes ordinary numbered 512-byte or 4 KB logical blocks (general knowledge unless cited). Every write goes to a fresh physical page, and a mapping table records where each logical block currently lives. The granularity of that table is the main design choice:

  • Page mapping: one entry per page, any logical page anywhere. Most flexible, but the table is large (about 1 GB of entries per 1 TB of flash at 4 bytes per 4 KB page), too big for the small RAM of a phone controller.
  • Block mapping: one entry per erase block; a logical page always sits at the same offset inside its block. Tiny table, but updating one page means copying the rest of the block.
  • Hybrid (log-block) mapping: data blocks are block-mapped, and a few page-mapped "log blocks" absorb updates. The paper classifies these by which data blocks may share a log block: one (block-associative), all (fully-associative), or a group of contiguous ones (set-associative). When log blocks fill, the FTL must merge them back into data blocks by copying.

Garbage collection: when free blocks run low, the FTL picks a victim erase block, copies its still-valid pages, and erases it. If the victim holds 192 valid pages out of 256, the device writes 192 pages of copies to gain 64 free pages: a write amplification of 256 / 64 = 4 for that reclaim (illustrative). The paper's footnote 2: GC "involves copying valid flash pages and erasing flash blocks for further data writes. GC overheads depend partly on how well file system operations align to the given FTL mapping algorithm."

Now you're ready: the FTL is a second log-structured system with its own cleaner, and F2FS's job is to make that cleaner's victims easy (mostly empty), not to replace it.
3Why random writes hurt, and what parallelism changes▾

Sequential writes fill erase blocks with data that tends to be invalidated together (the file is later overwritten or deleted as a unit), so GC finds blocks that are entirely invalid and erases them with no copying. Small random writes spread each block's contents over many unrelated files and times; later overwrites leave every block partly valid, and GC must copy. Min et al., cited in the paper, call the result "internal fragmentation of the underlying media" that degrades "sustained SSD performance". On hybrid-mapped FTLs it is worse: random writes touching many data blocks force expensive merges (general knowledge).

Parallelism. A device contains several channels, each with several NAND dies, each with planes that can program at once (general knowledge). A large sequential write is striped across all of them; one 4 KB write at a time keeps one die busy. The paper's own measurements (Table 2, single thread, 512 KB sequential and 4 KB random I/O with O_DIRECT) show the gap: the phone's eMMC writes 72 MB/s sequentially and 12 MB/s randomly (6×); the SATA SSD 471 versus 140 (3.4×); the PCIe SSD 922 versus 254 (3.6×).

Note one oddity worth knowing before the results: on both SSDs, 4 KB random writes are faster than random reads (140 versus 40 MB/s; 254 versus 41). A single-threaded read must wait for NAND every time (41 MB/s ≈ 10,000 reads per second ≈ 100 µs each, this guide's arithmetic), while a write can be acknowledged from the device's DRAM buffer and programmed later in parallel (general knowledge).

Now you're ready: turning many small random writes into a few large sequential ones helps twice: higher bandwidth now, and cheaper GC later.
4LFS in one page: the design F2FS starts from▾

Rosenblum and Ousterhout's log-structured file system (the 10/27 paper) buffers changes in memory and writes them all, data and metadata, in large sequential chunks at the head of a log. Inodes therefore move every time they are written, so an inode map (itself written to the log, located through fixed checkpoint regions) translates inode numbers to locations. The disk is divided into segments (512 KB or 1 MB in Sprite LFS); a cleaner reads partly dead segments and rewrites their live blocks compactly, guided by a segment usage table (live bytes and youngest modification time per segment) and per-segment summary blocks (which file and offset each block belongs to). Victims are chosen by a cost-benefit formula, (1 − u) × age / (1 + u), that prefers old, cold segments over a simple greedy choice of the emptiest.

Crash recovery uses two alternating checkpoint regions plus roll-forward through the log written after the last checkpoint. LFS also discusses threading the log through free holes as the alternative to copying, and uses threading only at whole-segment granularity.

Now you're ready: F2FS keeps the log, the segments, the two policies and the checkpoints, and changes where the metadata lives, how pointers work, how many logs there are, and when to stop appending.
5fsync, SQLite, and the page cache▾

Linux file systems buffer writes in the page cache and write them back later. fsync(fd) forces the file's dirty data, plus whatever metadata is needed to find it again (its inode, allocation maps, directory entry for a new file), to stable storage and then usually issues a cache-flush command to the device (general knowledge).

SQLite, the embedded database behind most Android apps, calls fsync at every transaction commit. In write-ahead logging (WAL) mode, which the paper uses and calls the fastest SQLite journal mode, a commit appends the changed database pages to a separate -wal file and fsyncs it; pages are copied back to the main database file later in a checkpoint (general knowledge for the mechanics). The result is exactly the paper's motivating pattern: a few KB written to a small file, then fsync, many times per second.

Now you're ready: on such workloads the cost is set by how many blocks each fsync must write, which is what roll-forward recovery (M19) attacks.
6The comparison file systems: EXT4, BTRFS, NILFS2▾

EXT4 (the paper: "a widely used update-in-place file system") descends from the FFS design: block groups with bitmaps and inode tables at fixed places, file data overwritten where it lies, and a journal that first writes changed metadata blocks to a log area and then commits (general knowledge). Random file overwrites stay random writes to the device.

BTRFS ("a copy-on-write file system") keeps all metadata in B-trees and never overwrites a block; an update writes new copies of the changed leaf and every node up to the root (general knowledge). NILFS2 ("an LFS") is a Linux log-structured file system that writes everything sequentially in segments and keeps continuous snapshots (general knowledge). The paper's point about both: they produce sequential writes but "do not consider the characteristics of flash storage devices".

Now you're ready: EXT4 is the baseline (normalized to 1), BTRFS shows the cost of copy-on-write indexing, and NILFS2 shows that being an LFS is not enough by itself.
The whole story in one place

Make the FTL's job easy, and keep the log from cascading

F2FS cannot see the NAND chips. It can only choose which logical addresses it writes, in what order, and how often. Every design decision is about that choice.

A phone's eMMC or a server's SSD is NAND flash behind a controller running a flash translation layer. The FTL never overwrites: each write lands on a fresh page and the old copy becomes garbage that its own garbage collector must later reclaim by copying whatever is still valid out of an erase block. How expensive that is depends on the write pattern the file system produces. Sequential, related writes leave erase blocks that die together; small random writes leave every erase block partly valid. On the paper's eMMC, 4 KB random writes run at 12 MB/s against 72 MB/s sequential, and the paper cites studies finding that Android apps issue mostly random writes, most of them forced by fsync from SQLite.

The classic answer is the log-structured file system: append every change at the head of a log and clean later. F2FS starts there, but the original LFS has three problems on this hardware. Moving a data block changes the pointer in its parent, which moves the parent, which changes its parent: the wandering tree. One log mixes short-lived and long-lived blocks, so segments end up half valid and the cleaner copies a lot. And when the disk is nearly full the cleaner runs constantly, which the paper measures as a collapse of more than 90%.

F2FS answers the first problem with a node address table. Index blocks ("nodes") have fixed IDs; indirect nodes store IDs, not addresses; and the NAT, in a fixed area, maps each ID to the node's current location. Updating a data block rewrites only its direct node and one NAT entry, which is buffered in memory until a checkpoint. The second problem gets six logs: hot, warm and cold for node blocks and for data blocks, chosen at write time by static rules (directory blocks hot, user data warm, data moved by cleaning or multimedia files cold), each log in its own zone so an associative FTL does not mix them back together. Segments (2 MB), sections (the cleaning unit) and zones are sized to match the FTL's own units.

For the third problem, cleaning is split by urgency: a greedy victim (fewest valid blocks) when an application is waiting for space, a cost-benefit victim (fewest valid blocks weighted by age) by a background thread that migrates blocks lazily through the page cache. And when clean sections fall to 5% of the total, F2FS stops appending altogether and switches to threaded logging, filling holes in dirty segments. That is a random write, which LFS was built to avoid, but on flash it is far cheaper than cleaning a nearly full volume.

Durability follows the same economy. A checkpoint writes a consistent image (NAT, SIT, SSA and a checkpoint pack with matching header and footer version numbers, alternating between two slots). But a checkpoint per fsync would write every dirty node in the system, so fsync instead writes just the file's data and its direct node blocks, marked with a flag; after a crash, F2FS rolls back to the last checkpoint and rolls forward over the flagged nodes. On SQLite this cuts data written by about 46% against EXT4 and raises transactions per second by up to 2×.

What the evaluation shows: large wins where the motivating pattern dominates (random writes plus fsync on slow mobile flash), parity on sequential workloads, smaller wins on a fast PCIe SSD, and graceful rather than catastrophic behavior on a nearly full device. What it does not show: device lifetime or erase counts, which the paper names as a goal, are never measured.

🍯 Key takeaways

  • On FTL-based flash, the file system's write pattern sets the device's garbage-collection cost; F2FS's goal is sequential, lifetime-sorted writes aligned to the FTL's units.
  • The NAT stops the wandering tree: indirect nodes hold node IDs, so moving a direct node changes one table entry, not a chain of pointer blocks.
  • Six logs (hot, warm, cold, for node and for data) separate blocks by expected lifetime at write time, which pushes segments toward all-valid or all-invalid and makes cleaning cheap.
  • Cleaning is greedy when an application waits, cost-benefit in the background with lazy migration, and a cleaned section is reused only after a checkpoint.
  • Near full, append-only logging collapses; F2FS switches to threaded logging (fill holes in dirty segments) when clean sections fall to 5%, trading sequentiality for no foreground cleaning.
  • fsync writes only data plus flagged direct nodes; recovery rolls back to the last checkpoint and rolls forward over those nodes. This is where most of the SQLite and varmail gains come from.
Six everyday pictures

How to think about F2FS

Each stands alone. Every card ends with where the picture stops being true, tied to a mechanism in How It Works.

NAND erase blocks · FTL garbage collection

A notebook in ink, where you can only tear out whole booklets

You cannot erase a line; a correction must be written on the next blank line, and the old line is crossed out. Blank pages come back only by tearing out an entire booklet, so before you tear one out you must recopy every line in it that is still current. Booklets full of crossed-out lines are cheap to recycle; booklets that are mostly current are expensive. That recopying is the FTL's garbage collection, and its cost is set by how mixed the booklets are.

Where it breaks: you choose where you write; F2FS does not. It only picks logical addresses and order, and hopes the FTL puts them in the same booklet, which is why zones and sections are sized to match the FTL (M2, M10).
Node IDs · the node address table · the wandering tree

Citing a book by its catalog number, not its shelf

If every reading list cited books by shelf position, moving one book would force rewriting every list that cites it, and every index of reading lists that cites those lists. Citing by catalog number means a move changes one catalog card. F2FS's indirect nodes cite direct nodes by node ID, and the NAT is the catalog: moving a direct node changes one NAT entry, and nothing above it.

Where it breaks: the last hop is still by shelf: a direct node stores data blocks' physical addresses, so moving a data block during cleaning still rewrites its direct node, and the catalog itself must be saved durably at each checkpoint (M5, M13, M17).
Multi-head logging · hot, warm and cold logs

Packing moving boxes by when you will throw things away

Put this week's groceries in one box, clothes in another, and the photo albums you will keep for decades in a third. Groceries get used up together and their box empties completely; the album box stays full and you never need to repack it. Mix them, and every box ends up half empty, so you are constantly consolidating. F2FS packs blocks into six logs by expected lifetime so that segments end up nearly empty (cheap to clean) or nearly full (never worth cleaning).

Where it breaks: F2FS decides by what the item is (directory block, user data, a .jpg), never by watching how it is actually used, so a regular file that is rewritten constantly still goes in the "warm" box (M9).
Greedy versus cost-benefit victim selection

Which storage unit to empty when you need one

If the truck is outside right now, empty the unit with the fewest boxes in it: least lifting while someone waits. With a free weekend, it can pay to consolidate a fuller unit whose boxes nobody has touched in years, because once moved they stay put, while the nearly empty unit full of this week's items may empty itself if you wait. F2FS is greedy in foreground cleaning and cost-benefit (utilization weighted by age) in background cleaning.

Where it breaks: the background "weekend" only comes when the system is idle; the paper could show its benefit (over 10%) only by inserting ten minutes or more of idle time between runs (M11, M12).
Adaptive logging · threaded logging

Parking in the gaps when the empty rows are gone

A lot that normally fills empty rows front to back (fast, orderly) will, when nearly full, either make each new driver wait while a valet compacts a row, or let drivers take any gap in partly filled rows. F2FS takes the gaps once clean sections fall to 5% of the total, and fills every gap in one row before moving to the next, which keeps the scattered writes somewhat local.

Where it breaks: gap parking is only cheap because flash has no seek; the paper says the strategy "may not do so on HDDs", and even on flash F2FS loses about 30% of throughput at 97.5% utilization, where it relies on threaded logging (M15).
Checkpoint packs · roll-back · roll-forward

A ledger page signed with the same serial number at top and bottom

Two ledger pages are used in turn. A page counts only if the serial number at the top matches the one at the bottom, so a page interrupted halfway is visibly incomplete and the reader falls back to the other page. Receipts stapled after the last good page (the flagged direct nodes written by fsync) are re-entered on recovery, then a fresh page is signed.

Where it breaks: only receipts that carry the fsync flag are re-entered; ordinary writes after the last checkpoint are simply lost, and freed space cannot be reused until a new page is signed, or the old page would point at overwritten data (M14, M18, M19).

What F2FS keeps on the device
  • Superblock (two copies at the start, per Figure 1): the format-time parameters, never changed.
  • Checkpoint area: two checkpoint packs, used alternately, each a complete consistent description of the file system status (M16, M17).
  • SIT, NAT, SSA: fixed-location tables, each kept in two copies (SIT and NAT) or one (SSA), updated at checkpoint time (M3).
  • Main area: 4 KB node blocks (inodes, direct nodes, indirect nodes) and data blocks (file contents, directory entry blocks), written as six logs (M3, M4, M9).

Compared with the earlier CS240 file systems: FFS overwrites data and metadata in place at fixed locations computed from block and inode numbers; LFS writes everything, including its inode map and segment usage table, into the log and finds the map through a fixed checkpoint region. F2FS sits between them: data and nodes are logged, while the tables that locate and describe them stay at fixed addresses.

1 · The problem: small random writes plus fsync, on flash behind an FTL

Mobile apps write small amounts of data at random offsets and force them out with fsync, mostly through SQLite. On an eMMC that writes 12 MB/s randomly against 72 MB/s sequentially, that pattern is slow now, and by spreading every erase block's contents across unrelated writes it makes later device garbage collection expensive and wears the flash. Existing log-structured or copy-on-write file systems (NILFS2, BTRFS) produce sequential writes but, the paper argues, ignore how the FTL works (M1).

2 · The layout: fixed tables up front, six logs in the Main area

The volume is cut into 2 MB segments, grouped into sections (the cleaning unit) and zones, sized to line up with the FTL's own units (M2). Six areas follow: superblock, checkpoint, SIT (valid-block counts and bitmaps per segment), NAT (node locations), SSA (owner of every block) and the Main area of 4 KB node and data blocks. Node and data blocks never share a section (M3).

3 · The index: node blocks and the NAT

A file is an inode block with direct pointers (or inline data), plus direct node blocks holding data addresses and indirect node blocks holding node IDs (M4, M6). The NAT maps every node ID to its current address, so a moved direct node changes one NAT entry and no pointer above it: the wandering tree is cut after one level (M5). Lookups translate inode numbers through the NAT (M7); directories are multi-level hash tables of 4 KB dentry blocks (M8).

4 · Keeping cleaning cheap: six logs, two victim policies, and a fallback

Blocks are routed at write time to hot, warm or cold node and data logs by static rules (M9), and each log is placed in its own zone so an associative FTL does not mix them (M10). Cleaning works a section at a time: greedy when free sections run short and an application waits, cost-benefit in a periodic background thread that migrates blocks lazily through the page cache, with 5% of space reserved (M11 to M13). A cleaned section becomes free only after the next checkpoint (M14). When clean sections fall to 5% of the total, F2FS stops appending and fills holes in dirty segments instead (threaded logging, M15).

5 · Crash consistency: checkpoints, roll-back and roll-forward

On sync, unmount or foreground cleaning, F2FS flushes dirty node and dentry blocks, pauses namespace operations, writes NAT, SIT and SSA to their areas, and writes a checkpoint pack whose header and footer carry the same new version number (M16). Two packs and two NAT and SIT sets mean the last consistent image is never overwritten (M17). At mount, F2FS picks the newest valid pack, cleans up orphan inodes (M18), and replays the direct node blocks that fsync wrote with a special flag since then (M19). Freed segments are discarded to the device at checkpoint time, in whole segments (M20).

  • F2FS was merged into Linux 3.8 ("late 2012", footnote 1 and Section 5) and "has been adopted in commercial products". The evaluated version was back-ported from the 3.15-rc1 kernel.
  • Targets: devices with an FTL and a block interface (eMMC, UFS, SSD), not raw NAND. Test platforms: a Galaxy S4 phone (Exynos 5410, 2 GB RAM, 16 GB eMMC, 2 GB partition) and an Intel i7-3770 server with a 250 GB SATA SSD and a 960 GB PCIe (NVMe) SSD.
  • Prior work it builds on: the original LFS (Rosenblum and Ousterhout) for the log, inode map, cleaning policies and logging modes; Oh et al. for threaded logging at high utilization; hot/cold separation work (WOLF, Hylog, SFS); raw-flash file systems (JFFS, YAFFS, UBIFS, LogFS); FTL designs (block-, set- and fully-associative hybrid mappings; DFTL; DAC).
The problem

Mobile workloads are dominated by small random writes forced out by fsync (SQLite). On FTL-based flash, random writes are several times slower than sequential ones and fragment the device internally, which raises garbage-collection cost and wear. HDD-era designs, including log-structured and copy-on-write ones, "fall short of fully leveraging and optimizing the usage of the NAND flash media" (Section 1).

The result

From the abstract: on the phone, F2FS "outperforms EXT4 under synthetic workloads by up to 3.1× (iozone) and 2× (SQLite). It reduces elapsed time of several realistic workloads by up to 40%. On a server system, F2FS is shown to perform better than EXT4 by up to 2.5× (SATA SSD) and 1.8× (PCIe SSD)." Under aging, adaptive logging keeps F2FS from collapsing: in the fileserver test F2FS stays at two or more times EXT4, and in the full-device iozone test it matches EXT4 after the first rounds instead of falling below 5% of it.

Mechanisms in dependency order
  1. Name the device problem (M1): random writes and fsync on FTL flash.
  2. Lay out the volume for the FTL (M2, M3): FTL-aligned segments, sections and zones; fixed metadata tables up front and a logged Main area.
  3. Index without cascades (M4 to M8): node blocks, the NAT, inline data, lookups through the NAT, hashed directories.
  4. Separate lifetimes at write time (M9, M10): six logs with static temperature rules, placed in different zones.
  5. Reclaim space cheaply and safely (M11 to M15): foreground and background cleaning, two victim policies, SIT and SSA lookups, pre-free sections, and the switch to threaded logging.
  6. Make crashes and fsync cheap (M16 to M20): checkpoint packs, shadow table sets and journals, roll-back with orphan cleanup, roll-forward for fsync, and segment-sized discards.
The central trade-offs
  • Sequential writes versus cleaning cost: appending turns random writes into sequential ones only "as long as there exists enough free logging space"; as free space "shrinks to nil", cleaning costs explode (over 90% performance drop "under harsh conditions"), so F2FS gives up sequentiality (threaded logging) to avoid cleaning.
  • Static versus measured temperature: classifying by block type and file extension costs nothing at run time but misclassifies files whose behavior does not match their type; the paper leaves run-time monitoring as possible future refinement.
  • Durability cost versus recovery work: a checkpoint per fsync is simple and slow; writing only data and direct nodes is fast but needs roll-forward logic at mount.
  • Working with the FTL versus around it: F2FS keeps the generic block interface and tunes its units to the FTL, rather than requiring special device support (as DFS does) or managing raw NAND (as UBIFS does).
Effect of changes (whole design)
  • If random writes cost the same as sequential ones on the device (a page-mapped FTL with ample spare area and DRAM), the log's bandwidth benefit shrinks to its fsync and metadata savings; the PCIe SSD results (fileserver about equal to EXT4) point that way (inference).
  • If the device exposes placement (multi-stream SSDs, which the paper mentions; zoned devices, general knowledge), zones and six logs map directly to device streams or zones and the FTL no longer has to guess (inference).
  • If the storage is an HDD, threaded logging becomes a seek per hole; the paper says adaptive logging "may not do so on HDDs" (Section 1).
  • If the volume runs nearly full for long periods, F2FS lives mostly in threaded logging and behaves like an update-in-place file system with extra node cleaning (Figure 7 at 97.5%, Figure 8(b)).

M1 · The problem: small random writes and fsync, on flash behind an FTL

TL;DR
ProblemMobile apps issue mostly small random writes forced by fsync; on FTL flash these are slow (12 versus 72 MB/s on the test eMMC) and fragment the device internally, raising GC cost and wear.
MechanismA log-structured file system designed around the FTL: sequential multi-stream writes in FTL-aligned units, a cheap index, and a minimal fsync path.
Trade-offThe usual LFS cost (cleaning, and the code to manage it) in exchange for turning the device's worst access pattern into its best one.
Breaks whenThe device handles random writes as well as sequential ones, or the workload is already sequential (videoserver shows no gain).
Key points
  • Flash has "several limitations, like erase-before-write requirement, the need to write on erased blocks sequentially and limited write cycles per erase block." Devices hide them behind an FTL that "addresses the NAND flash memory's limitations and provides a generic block device abstraction".
  • "Min et al. [21] observe that frequent random writes to an SSD would incur internal fragmentation of the underlying media and degrade the sustained SSD performance."
  • Cited workload studies: "the Facebook mobile application issues 150% and WebBench register 70% more random writes than sequential writes"; "over 80% of total I/Os are random and more than 70% of the random writes are triggered with fsync by applications such as Facebook and Twitter [8]. This specific I/O pattern comes from the dominant use of SQLite [2] in those applications."
  • "Unless handled carefully, frequent random writes and flush operations in modern workloads can seriously increase a flash device's I/O latency and reduce the device lifetime."
  • On BTRFS and NILFS2: "they do not consider the characteristics of flash storage devices and are inevitably suboptimal in terms of performance and device lifetime."
  • Claim of novelty: "the first publicly and widely available file system that is designed from scratch to optimize performance and lifetime of flash devices with a generic block interface." And: "F2FS builds on the concept of LFS but deviates significantly from the original LFS proposal with new design considerations."
  • Device numbers (Table 2, MB/s, sequential read, sequential write, random read, random write): eMMC 114, 72, 12, 12; SATA SSD 486, 471, 40, 140; PCIe SSD 1,295, 922, 41, 254.
How it works, step by step: one SQLite commit on EXT4 and on the eMMC (illustrative)
  1. The app updates a row. SQLite in WAL mode appends the changed 4 KB page (and a frame header) to the -wal file in the page cache, then calls fsync (general knowledge of SQLite).
  2. EXT4 makes it durable: it writes the WAL file's data block where the file's blocks live, then commits the changed inode (size, times) and any allocation metadata through its journal: a descriptor block, the metadata blocks, a commit block, with cache flushes in between (general knowledge of EXT4 ordered journaling).
  3. The device sees a handful of 4 KB writes at unrelated addresses, separated by flushes: the random-write regime. At the eMMC's 12 MB/s, 4 KB writes run at about 12,000,000 / 4,096 ≈ 2,900 per second (this guide's arithmetic, taking MB as 106 bytes).
  4. Inside the FTL, erase blocks fill with an interleaving of short-lived WAL pages, journal blocks and long-lived metadata. When the WAL is checkpointed and truncated and the journal wraps, those pages die at different times, so each erase block is left partly valid and GC must copy (general knowledge; this is the "internal fragmentation" Min et al. describe).
  5. F2FS's target for the same commit: one data block appended to a data log and one node block appended to a node log, no journal, no fixed-location metadata until the next checkpoint (M9, M19).
Assumptions it relies on
  • A1. Random writes are much slower than sequential writes on the target devices (stated; Table 2).
  • A2. The device has an FTL behind a generic block interface; the file system controls only logical addresses and order (stated).
  • A3. Target workloads are dominated by small synchronous writes (stated for mobile, citing [8] and [12]).
  • A4. Sequential, same-lifetime logical writes lead to cheaper device GC (implicit; the paper's argument for logging and zones depends on it but never measures device GC directly).
If an assumption changes
  • A1 changes (random as fast as sequential): the bandwidth gain from logging disappears, leaving only reduced metadata and fsync writes; fileserver on the PCIe SSD, where the paper says "all file systems perform rather similarly", is close to this case.
  • A2 changes (raw NAND): F2FS has no wear leveling or bad-block handling; the paper's related work assigns that case to JFFS, YAFFS, UBIFS and LogFS.
  • A3 changes (sequential, large-file workloads): nothing to fix: videoserver shows no difference among the four file systems.
  • A4 changes (an FTL that remaps aggressively or mixes streams): sequential logical writes can still be scattered physically; this is why F2FS adds zones (M10), and why the multi-stream interface it mentions matters.
Design notes and rejected alternatives

The paper rejects reusing an existing LFS or copy-on-write file system (NILFS2, BTRFS) as flash-unaware, a raw-flash file system because devices with a dedicated controller and FTL are, in its words, "more commonplace", and DFS because it relies on host FTL support and is "limited to specific flash devices and system configurations and is not open source". It keeps the generic block interface and tunes to it.

Connections

LFS: the same move (turn small random writes into large sequential ones) for a different reason: LFS avoided disk seeks; F2FS avoids FTL fragmentation and the random-write penalty. FFS: FFS tuned placement to disk geometry it could see; F2FS tunes to FTL units it can only configure. Rethink the Sync: the same fsync-heavy applications, attacked from the durability-semantics side instead of the layout side (inference).

M2 · Segments, sections and zones: units that line up with the FTL

TL;DR
ProblemIf the file system's allocation and cleaning units straddle the FTL's units, freeing space at the file system level still leaves partly valid flash blocks, and the FTL must copy.
MechanismThree configurable units: segments (2 MB, allocation and statistics), sections (consecutive segments, the cleaning unit), zones (consecutive sections, used to keep logs apart), sized at format time to match the FTL.
Trade-offLess duplicated copying by the FTL, in exchange for needing to know the FTL's units, which the block interface does not report.
Breaks whenThe FTL's units are unknown or the FTL scatters logical ranges physically anyway (page mapping with its own placement).
Key points
  • "F2FS employs three configurable units: segment, section and zone. It allocates storage blocks in the unit of segments from a number of individual zones. It performs “cleaning” in the unit of section. These units are introduced to align with the underlying FTL's operational units to avoid unnecessary (yet costly) data copying."
  • "F2FS divides the whole volume into fixed-size segments. The segment is a basic unit of management in F2FS and is used to determine the initial file system metadata layout. A section is comprised of consecutive segments, and a zone consists of a series of sections."
  • A segment holds at most 512 valid blocks "under the default configuration" (Section 3.2.3), so a segment is 512 × 4 KB = 2 MB (this guide's arithmetic).
  • Zones exist "to be compatible with an FTL, with a view to mitigating the garbage collection (GC) overheads" (Section 2.4, M10).
  • Defaults (general knowledge from the F2FS tools, not in the paper): 1 segment per section and 1 section per zone. The paper's Figure 1 draws 2 segments per section and 2 sections per zone. The paper never states which values its experiments used.
How it works, step by step: sizing sections for an FTL that reclaims 8 MB at a time (illustrative)
  1. The device: suppose the FTL stripes each logical 8 MB range across four planes and reclaims all four 2 MB erase blocks together (illustrative numbers).
  2. Default F2FS (1 segment per section): the cleaner frees one 2 MB section. In the FTL's 8 MB unit, the other 6 MB belong to three other sections that may still hold valid data, so the FTL cannot erase the unit without copying them. The file system copied blocks once to clean its section; the device may copy them again.
  3. Aligned F2FS (4 segments per section): the cleaner frees an entire 8 MB section and, at the next checkpoint, discards it (M20). The FTL now finds the whole unit invalid and erases it with no copying.
  4. Zones on top: with each active log in its own zone (M10), the hot log's segments and the cold log's segments never share an FTL unit, so a unit full of hot data dies all at once.
  5. Cost: bigger sections mean each foreground cleaning moves more data before it frees anything; the paper does not measure this trade-off.
Assumptions it relies on
  • A1. The FTL's operational units can be known at format time (implicit; the paper gives no method to discover them).
  • A2. The FTL keeps a contiguous, aligned logical range together in the same flash units (implicit; true of block- and set-associative mappings, which the paper says this design targets).
  • A3. The FTL's units do not change after formatting (implicit; the superblock parameters are "not changeable").
If an assumption changes
  • A1 changes (units unknown): the defaults (2 MB, 1, 1) may straddle FTL units, and the double copying in step 2 can happen silently (inference).
  • A2 changes (a page-mapped FTL with its own placement): logical alignment says little about physical placement; what still helps is writing data of one lifetime together in time and discarding whole freed ranges (inference).
  • A3 changes (the device is replaced or reconfigured): the units are fixed at format time; only reformatting changes them (inference from "given at the format time and not changeable").
Design notes and rejected alternatives

One unit for everything (as in LFS, where a segment is both the write and the cleaning unit) would force a choice between small segments (fine-grained statistics, cheap cleaning steps) and big ones (FTL-sized). F2FS separates statistics (segment), cleaning (section) and placement (zone). The default of one segment per section suggests the authors expected many devices not to need larger sections (inference).

Connections

FFS: cylinder groups and rotational parameters are FFS's version of matching allocation units to device geometry; both designs depend on parameters the device may hide. Superpages, ESX: allocation units sized to a hardware unit (a TLB superpage, a large page) for the same reason: freeing a whole unit is cheap, freeing part of one is not (inference). Exokernel: the configurable units are a mild form of exposing device structure to the layer above (inference).

M3 · The six areas: fixed tables up front, a logged Main area

TL;DR
ProblemA log-structured file system needs tables to find moved blocks and to know which blocks are still valid; putting those tables in the log (as LFS does) makes them move too.
MechanismSuperblock, checkpoint (CP), segment information table (SIT), node address table (NAT) and segment summary area (SSA) at fixed addresses, then the Main area of 4 KB node and data blocks written as logs.
Trade-offThe tables are rewritten in place (random writes, per Figure 1), but only at checkpoint time and in small amounts; in exchange they never need locating and never cascade.
Breaks whenCheckpoints are so frequent that table writes dominate, or the tables are too large to cache.
Key points
  • Superblock: "has the basic partition information and default parameters of F2FS, which are given at the format time and not changeable." Figure 1 shows two copies, Superblock #0 and #1, before segment 0.
  • Checkpoint: "keeps the file system status, bitmaps for valid NAT/SIT sets (see below), orphan inode lists and summary entries of currently active segments." It "stores two checkpoint packs across the two segments (#0 and #1): one for the last stable version and the other for the intermediate (obsolete) version, alternatively."
  • SIT: "contains per-segment information such as the number of valid blocks and the bitmap for the validity of all blocks in the “Main” area". It "is retrieved to select victim segments and identify valid blocks in them during the cleaning process". Section 2.5 adds that segment ages come from "their last modification time recorded in SIT".
  • NAT: "a block address table to locate all the “node blocks” stored in the Main area."
  • SSA: "stores summary entries representing the owner information of all blocks in the Main area, such as parent inode number and its node/data offsets. The SSA entries identify parent node blocks before migrating valid blocks during cleaning."
  • Main area: "filled with 4KB blocks. Each block is allocated and typed to be node or data. A node block contains inode or indices of data blocks, while a data block contains either directory or user file data. Note that a section does not store data and node blocks simultaneously."
  • Figure 1 labels the span from CP to SSA "Random Writes" and the Main area "Multi-stream Sequential Writes", with hot/warm/cold node segments and hot/warm/cold data segments.
How it works, step by step: the areas on a 120 GB volume (this guide's arithmetic, using general-knowledge entry sizes)
  1. Segments: 120 GB / 2 MB = 61,440 segments (taking GB and MB as powers of two).
  2. SIT: one entry per segment, carrying a 512-bit (64-byte) validity bitmap plus a count and a modification time. The bitmaps alone are 61,440 × 64 bytes = 3.75 MB for the whole volume, small enough to keep in memory, which is what makes valid-block identification fast (M13).
  3. SSA: one 4 KB summary block per segment (general knowledge: 512 entries of 7 bytes each), so 61,440 × 4 KB = 240 MB, 0.2% of the volume.
  4. NAT: one entry (general knowledge: 9 bytes, 455 per 4 KB block) per node ID; its size is set by the maximum number of node blocks chosen at format time.
  5. During normal operation new node and data blocks go only to the Main area's active segments; changes to NAT and SIT entries accumulate in memory (general knowledge), and SSA entries for the active segments are kept in memory as "summary blocks of active segments".
  6. At a checkpoint the changed NAT, SIT and SSA blocks are written to their fixed areas, in the alternate set for NAT and SIT, and a new checkpoint pack is written (M16, M17). These are the "Random Writes" of Figure 1.
Assumptions it relies on
  • A1. The fixed areas' random writes are small and infrequent enough that the FTL absorbs them (implicit in Figure 1's labeling; never measured separately).
  • A2. The SIT and the active part of the NAT can be cached in memory (implicit; general knowledge confirms F2FS caches both).
  • A3. Consistency comes from checkpoints and two table sets, not from updating each table atomically in place (stated, Section 2.7).
If an assumption changes
  • A1 changes (checkpoints every few milliseconds, or a weak hybrid FTL): table writes become a stream of random writes to a small region; the NAT and SIT journals in the checkpoint pack exist to blunt exactly this (M17).
  • A2 changes (very large volumes on small memory): NAT misses add a block read per node access, and the cleaner's bitmap scan needs SIT reads (inference).
  • A3 changes (tables updated without a second set): a crash mid-update could leave a NAT block half new, half old, with no consistent image to fall back to (inference).
Design notes and rejected alternatives

LFS writes its inode map and segment usage table into the log and records their addresses in a fixed checkpoint region; F2FS fixes the tables themselves. Moving them into the log would make every table update another block that moves and must be found (a second, smaller wandering tree), and on an FTL a fixed logical address is not a fixed physical one, so "in place" costs no wear concentration (inference). Keeping node and data blocks in separate sections separates two populations with different update rates before the six logs refine them further (M9).

Connections

LFS: SIT ↔ segment usage table (LFS keeps live bytes and the youngest modification time; F2FS adds a per-block validity bitmap), SSA ↔ the segment summary blocks LFS writes inside each segment, NAT ↔ inode map, CP ↔ checkpoint regions. FFS: FFS also keeps fixed per-region bitmaps (in each cylinder group), but updates data in place too.

M4 · Node blocks: inodes, direct nodes and indirect nodes

TL;DR
ProblemA file needs an index from file offsets to block addresses that can grow from a few bytes to terabytes.
MechanismThree node types, each a 4 KB block with a fixed node ID: an inode (metadata plus direct pointers or inline data, plus five node-ID pointers), direct nodes (data addresses) and indirect nodes (node IDs).
Trade-offA familiar pointer tree, but every node-to-node hop goes through the NAT, so a lookup costs one table translation per level.
Breaks whenNAT entries are not cached, so each hop adds a table read.
Key points
  • "Each node block has a unique identification number, “node ID”. By using node ID as an index, NAT serves the physical locations of all node blocks. A node block represents one of three types: inode, direct and indirect node."
  • "An inode block contains a file's metadata, such as file name, inode number, file size, atime and dtime. A direct node block contains block addresses of data and an indirect node block has node IDs locating another node blocks."
  • "An inode block contains direct pointers to the file's data blocks, two single-indirect pointers, two double-indirect pointers and one triple-indirect pointer."
  • In the paper's naming, a "single-indirect pointer" in the inode points to a direct node, a "double-indirect pointer" to an indirect node of direct nodes, and the "triple-indirect pointer" to an indirect node of indirect nodes (Figure 2 draws exactly these chains).
  • Counts from the Linux source (general knowledge, not in the paper): 923 direct pointers in an inode, 1,018 data addresses per direct node, 1,018 node IDs per indirect node, all 4-byte values.
How it works, step by step: reading byte 100 MB of a file
  1. Block index: 100 MB / 4 KB = 25,600.
  2. Skip the inode's direct pointers: 25,600 − 923 = 24,677. Skip the two direct nodes: 24,677 − 2,036 = 22,641. So the block is in the first double-indirect chain (each covers 1,018 × 1,018 = 1,036,324 blocks).
  3. Inside that chain: 22,641 / 1,018 = 22 remainder 245. Slot 22 of the indirect node holds a direct node's ID; slot 245 of that direct node holds the data address.
  4. Walk: NAT[inode's ID] → read inode; take its first double-indirect node ID → NAT → read the indirect node; slot 22 → node ID → NAT → read the direct node; slot 245 → read the data block. Four block reads and three NAT translations on a cold cache (this guide's arithmetic with general-knowledge counts).
  5. Compare FFS (12 direct pointers, 1,024 addresses per 4 KB indirect block, general knowledge): the same offset is 25,588 blocks past the direct ones, inside the double-indirect range; also four block reads, but no table translation, because every pointer is an address.
Assumptions it relies on
  • A1. A node keeps its node ID for its whole life, wherever it is written (implicit; it is what makes the NAT work).
  • A2. NAT translations are usually cache hits (implicit; general knowledge: F2FS caches NAT entries in memory).
  • A3. Most files are small enough to need few or no node blocks beyond the inode (stated for inline data: "many systems have small files").
If an assumption changes
  • A1 changes (node IDs reassigned when a node moves): the parent would have to be rewritten, which is the wandering tree again (M5).
  • A2 changes (cold NAT): each hop costs an extra 4 KB NAT block read, roughly doubling random-read latency for large files (inference).
  • A3 changes (mostly huge files): more lookups pass through two or three NAT translations, and appends regularly add direct nodes, which dirties an indirect node too (inference).
Design notes and rejected alternatives

The paper keeps "pointer-based file indexing" rather than extents or B-trees. Pointers make one data block's update touch exactly one direct node, which keeps update cost flat; an extent tree would be smaller for sequential files but would split and rebalance under random overwrites (inference). Only the last hop (direct node to data) stores physical addresses; making data pointers indirect too would need a table entry per 4 KB data block, the size of a page-mapped FTL's map (inference, M5).

Connections

FFS and LFS: both use the FFS inode format (direct, single, double, triple indirect blocks of addresses); F2FS keeps the shape but replaces addresses with node IDs above the bottom level. Superpages: a radix tree of fixed-size nodes with a fixed fan-out, like a page table (1,018-way here, 512-way on x86-64) (inference).

M5 · The node address table and the wandering tree

TL;DR
ProblemIn a log-structured file system, writing a data block to a new place changes the pointer in its parent, which must then move, and so on to the root: "a chain of writes, creating the “wandering tree” problem".
MechanismParents above the bottom level hold node IDs, and the NAT maps IDs to addresses. A moved direct node changes its NAT entry (in memory until a checkpoint); no parent changes.
Trade-offOne more lookup per node access and a table to persist at checkpoints, in exchange for a constant one node block per data update.
Breaks whenNAT updates have to be made durable as often as data (they are not: fsync defers them via roll-forward, M19).
Key points
  • Section 1: "LFS writes data and index blocks to newly allocated free space. If a leaf data block is updated (and written to somewhere), its direct index block should be updated, too. Once the direct index block is written, again its indirect index block should be updated. Such recursive updates result in a chain of writes, creating the “wandering tree” problem [4]."
  • "The original LFS introduced inode map to translate an inode number to an on-disk location. In comparison, F2FS utilizes the “node” structure that extends the inode map to locate more indexing blocks."
  • "F2FS, however, only updates one direct node block and its NAT entry, effectively addressing the wandering tree problem. For example, when a 4KB data is appended to a file of 8MB to 4GB, the LFS updates two pointer blocks recursively while F2FS updates only one direct node block (not considering cache effects). For files larger than 4GB, the LFS updates one more pointer block (three total) while F2FS still updates only one."
  • The comparison counts pointer blocks only. Both systems also rewrite the inode when an append changes the file size (general knowledge; see Class Prep C1).
How it works, step by step: appending 4 KB to a 100 MB file, then a checkpoint
  1. Data: the new 4 KB block is allocated at the head of the warm data log (user data, Table 1) and written there.
  2. Direct node: the direct node covering that offset (node ID 7731 in the figure) gets the new data address in slot 245 and is written to the head of the warm node log, at a new address. Its node ID is unchanged.
  3. NAT: the in-memory NAT entry for 7731 is set to the new address. The old copy's block becomes invalid in the SIT's bitmap (in memory).
  4. Indirect node: it stores 7731, which did not change, so it is not touched. The chain stops here.
  5. Inode: the file size and modification time changed, so the inode block is dirty too (general knowledge; the paper's count ignores it).
  6. At the next checkpoint: the NAT change is written either into the NAT journal in the checkpoint pack or into the NAT block in the alternate NAT set (M17). Thousands of node moves between two checkpoints cost one table write each, or less if they share NAT blocks.
Assumptions it relies on
  • A1. NAT changes can wait until the next checkpoint, because a crash rolls back to the last checkpoint anyway (implicit in Section 2.7).
  • A2. Changes that must survive a crash before the next checkpoint can be rediscovered without the NAT (stated mechanism: flagged direct nodes and roll-forward, M19).
  • A3. The NAT entries of active nodes are cached in memory (implicit).
  • A4. The cost that matters is pointer blocks per update (implicit in the paper's count, which leaves out the inode and caching).
If an assumption changes
  • A1 changes (every node move made durable at once): each update would write a data block, a node block and a NAT block at a fixed address: three writes, one random, worse than the chain it replaces for small files (inference).
  • A2 changes (no roll-forward): fsync would need a checkpoint, which writes all dirty nodes and tables; the paper calls that approach "poor performance" (M19).
  • A3 changes (NAT not cached): every node access adds a NAT block read; with 455 entries per NAT block (general knowledge) locality among node IDs decides how bad this is (inference).
  • A4 changes (count everything): for appends the inode is rewritten in both systems, so the real ratio for a file in the 4 MB to 4 GB range is about 2 node blocks (F2FS) to 4 index blocks (LFS, with inode and inode map), not 1 to 2 (this guide's arithmetic).
Design notes and rejected alternatives

The indirection stops at direct nodes on purpose: data addresses stay physical. A NAT entry per data block would be a page-mapped FTL inside the file system, one entry per 4 KB, about 31 million entries for the 120 GB volume (this guide's arithmetic), duplicating the device's own map. The paper cites the wandering tree to both [4] (Bityutskiy's JFFS3 design notes) in Section 1 and [27] (the LFS paper) in Section 2.2; the term comes from the flash file system literature (general knowledge).

Connections

LFS: the inode map already stops the chain at the inode for inode moves; the NAT extends that to direct and indirect nodes. FTL designs (DFTL, page mapping): the NAT is a page-mapped translation table for node blocks only, kept by the host (inference). Virtual memory and ESX: the same trick as a level of indirection that lets an object move while its name stays fixed (guest physical pages behind ESX's pmap, inference). Hints: deferring NAT writes to the checkpoint is Lampson's "batch processing" applied to metadata: many in-memory updates, one durable write (inference).

M6 · Inline data and inline extended attributes

TL;DR
ProblemA small file would cost a 4 KB inode block plus a 4 KB data block, two allocations and two writes, for a few hundred bytes of content.
MechanismFiles under 3,692 bytes keep their data inside the inode block, in the space otherwise used for direct pointers; 200 bytes of every inode are reserved for extended attributes.
Trade-offHalf the space and half the writes for small files, in exchange for a conversion step when an inline file grows past the limit.
Breaks whenSmall files grow soon after creation (each pays a conversion), or files carry more extended attributes than 200 bytes hold.
Key points
  • "F2FS supports inline data and inline extended attributes, which embed small-sized data or extended attributes in the inode block itself. Inlining reduces space requirements and improve I/O performance."
  • "Note that many systems have small files and a small number of extended attributes. By default, F2FS activates inlining of data if a file size is smaller than 3,692 bytes. F2FS reserves 200 bytes in an inode block for storing extended attributes."
  • Figure 2 labels the inode region "direct pointers or inline data", so inline data occupies the direct-pointer area. 3,692 = 923 × 4, exactly the size of 923 four-byte pointers, and 200 = 50 × 4 (this guide's arithmetic; 923 is general knowledge).
  • The paper gives no measurement of inlining by itself.
How it works, step by step: 1,000 configuration files of 1,000 bytes each
  1. Create and write one file: the inode block holds the metadata and the 1,000 bytes in its pointer area; no data block is allocated.
  2. Where it goes: the inode is a node block, so it is written to a node log (for a regular file, the warm node log, Table 1), not to a data log (inference from Table 1's categories).
  3. Space: 1,000 × 4 KB = about 4 MB with inlining, against 1,000 × 8 KB = about 8 MB without (this guide's arithmetic).
  4. Reading: opening and reading the file needs only the inode block; one block read instead of two.
  5. fsync: one node block to write (M19) instead of a data block plus a node block.
  6. Growth: if the file passes the limit, its data must move to a normal data block and the pointer area becomes pointers again (general knowledge of the implementation; the paper does not describe conversion).
Assumptions it relies on
  • A1. Many files are small (stated).
  • A2. Files have few extended attributes (stated: "a small number of extended attributes").
  • A3. Small files usually stay small (implicit).
If an assumption changes
  • A1 changes (mostly large files): no gain and no real cost; the pointer area is used for pointers as usual.
  • A2 changes (security labels, many attributes): attributes beyond the 200 inline bytes need separate storage, losing the one-block benefit for those files (general knowledge: F2FS keeps them in an extra node block).
  • A3 changes (append logs that start small): every such file is written once inline, then converted, rewriting its contents into a data block: extra writes for exactly the files inlining was meant to help (inference).
Design notes and rejected alternatives

Inline data puts small-file contents in the node logs, so their temperature follows the node classification rather than the data classification; a frequently rewritten small file makes its inode hot either way (inference). The FFS alternative to the same problem is fragments (a fraction of a block for the tail); with 4 KB blocks and an inode that is itself a 4 KB block, using the inode's spare space is the cheaper equivalent (inference).

Connections

FFS: fragments solve small-file waste by splitting blocks; F2FS solves it by not allocating a data block at all. LFS: LFS implementations pack several inodes into one log block (general knowledge), so they do not pay a whole block per inode; F2FS pays 4 KB per inode and puts the spare space to use with inlining (inference).

M7 · Path lookup: every inode is found through the NAT

TL;DR
ProblemInodes move every time they are written, so an inode number cannot be turned into a location by arithmetic as in FFS.
MechanismAn inode number is the inode block's node ID; each path component costs a NAT translation, an inode read, and a directory hash lookup.
Trade-offFreedom to move inodes, for one table translation per component (a memory lookup when cached).
Breaks whenThe NAT working set does not fit in memory, adding a NAT block read per component.
Key points
  • The paper's walk-through for "/dir/file": "(1) It obtains the root inode by reading a block whose location is obtained from NAT; (2) In the root inode block, it searches for a directory entry named dir from its data blocks and obtains its inode number; (3) It translates the retrieved inode number to a physical location through NAT; (4) It obtains the inode named dir by reading the corresponding block; and (5) In the dir inode, it identifies the directory entry named file, and finally, obtains the file inode by repeating steps (3) and (4) for file."
  • "The actual data can be retrieved from the Main area, with indices obtained via the corresponding file structure."
  • Step (3) implies inode numbers index the NAT directly; in the implementation an inode's number is its node ID (general knowledge).
How it works, step by step: opening /dir/file with a cold cache
  1. Root: the root inode number is fixed (general knowledge: stored in the superblock). NAT[root] → read the root inode (1 block, plus 1 NAT block if not cached).
  2. Find "dir": hash "dir", read one bucket (2 or 4 dentry blocks) per hash level until a match (M8). Suppose level 0 hits: 2 blocks.
  3. dir's inode: NAT[dir's inode number] → read dir's inode (1 block, plus possibly 1 NAT block).
  4. Find "file": 2 or more dentry blocks.
  5. file's inode: NAT → 1 block. If the file is small, its data may be inline (M6) and the open-and-read is done.
  6. Total: about 7 block reads plus up to 3 NAT block reads on a completely cold cache (this guide's count). FFS needs the same inode and directory reads but computes inode locations from the number, so it has no NAT reads (general knowledge of FFS).
Assumptions it relies on
  • A1. NAT entries for active inodes are cached (implicit).
  • A2. Directory buckets are found by hashing, not by scanning (stated, M8).
If an assumption changes
  • A1 changes: each component costs an extra random 4 KB read; on flash this is about 100 µs on the SATA SSD's queue-depth-one random read rate (40 MB/s ≈ 10,000 reads/s), against roughly 10 ms for a random read on a disk (this guide's arithmetic from Table 2).
  • A2 changes (a linear directory): lookups in large directories would read every dentry block; M8 is what keeps lookups logarithmic.
Design notes and rejected alternatives

The paper chooses one translation table for all nodes rather than separate maps for inodes and index blocks. A single NAT keyed by node ID means inodes, direct nodes and indirect nodes are all found the same way, and one roll-forward mechanism (M19) covers all node types (inference).

Connections

LFS: identical in shape to LFS lookups through the inode map; "inode map lookups rarely require disk accesses" in Sprite LFS because the active map is cached. NFS: an NFS file handle carries an inode number; on F2FS, a server decoding a handle goes through the NAT instead of FFS's arithmetic (inference).

M8 · Directories as multi-level hash tables of dentry blocks

TL;DR
ProblemA directory with many entries must be searched without reading every block.
Mechanism4 KB dentry blocks (a validity bitmap plus paired slot and name arrays) organized as hash tables by level; a lookup hashes the name and reads one bucket of 2 or 4 blocks per level, from level 0 to the maximum allocated level.
Trade-offO(log(number of entries)) bucket reads per lookup, in exchange for a fixed structure that grows by adding levels.
Breaks whenA name is absent (every level must be checked), or names hash unevenly so some buckets fill early.
Key points
  • "In F2FS, a 4KB directory entry (“dentry”) block is composed of a bitmap and two arrays of slots and names in pairs. The bitmap tells whether each slot is valid or not. A slot carries a hash value, inode number, length of a file name and file type (e.g., normal file, directory and symbolic link)."
  • "A directory file constructs multi-level hash tables to manage a large number of dentries efficiently."
  • "When F2FS looks up a given file name in a directory, it first calculates the hash value of the file name. Then, it traverses the constructed hash tables incrementally from level 0 to the maximum allocated level recorded in the inode. In each level, it scans one bucket of two or four dentry blocks, resulting in an O(log(# of dentries)) complexity. To find a dentry more quickly, it compares the bitmap, the hash value and the file name in order."
  • "When large directories are preferred (e.g., in a server environment), users can configure F2FS to initially allocate space for many dentries. With a larger hash table at low levels, F2FS reaches to a target dentry more quickly."
  • Implementation details (general knowledge, not in the paper): 214 slots per dentry block, names stored in 8-byte pieces, level n has 2n buckets, the bucket index is the hash modulo the number of buckets, and buckets have 2 blocks at lower levels and 4 at higher ones.
How it works, step by step: looking up "report.txt" (hash 13) in a directory with levels 0 to 3
  1. Hash the name once: h = 13 (illustrative).
  2. Level 0 has one bucket; read its 2 dentry blocks; for each valid slot (bitmap) compare the stored hash with 13, and only on a hash match compare names. No match.
  3. Level 1: bucket 13 mod 2 = 1; 2 blocks; no match. Level 2: bucket 1 of 4; no match. Level 3: bucket 5 of 8; match: the slot gives the inode number and type.
  4. Cost: 4 buckets = 8 dentry block reads in the worst case for this directory, against reading every block of a linear directory (this guide's arithmetic).
  5. Why logarithmic: each level doubles the buckets, so the number of levels grows with log2 of the entries, and a lookup reads one bucket per level.
  6. Writes: a new entry dirties one dentry block, which goes to the hot data log; the directory's direct node goes to the hot node log (Table 1).
Assumptions it relies on
  • A1. The name hash spreads entries evenly over buckets (implicit).
  • A2. The maximum allocated level is recorded in the inode, so a lookup knows when to stop (stated).
  • A3. Directory blocks are rewritten often and with patterns unlike file data (stated as the reason they are "hot").
If an assumption changes
  • A1 changes (adversarial or clustered names): one bucket fills, new entries spill to deeper levels, and lookups for those names read more levels (inference).
  • A2 changes: without the recorded maximum, a negative lookup could not stop early (inference).
  • A3 changes (directories that never change): their blocks would sit in hot segments without dying, which raises the cleaning cost of hot segments; static rules cannot detect this (inference).
Design notes and rejected alternatives

Pre-allocating a larger table at low levels for server directories trades space for fewer levels per lookup. The order of comparison (bitmap, then hash, then name) means most slots are rejected by an integer compare. The paper gives the complexity but no directory benchmark; varmail and fileserver create and delete files, so directory cost is inside those numbers but not isolated.

Connections

FFS: 4.2BSD directories are searched linearly in 512-byte chunks (FFS guide, M15). LFS: unchanged UNIX directories; F2FS's hash directories are independent of the log design.

M9 · Multi-head logging: six logs and the temperature rules

TL;DR
ProblemOne log mixes blocks that will be overwritten soon with blocks that will live for months, so most segments end up partly valid and cleaning copies a lot.
MechanismSix active logs, hot, warm and cold for node blocks and for data blocks; each new block goes to a log chosen at allocation time by static rules about its type, its file's extension, a user hint, or whether the cleaner moved it.
Trade-offCheaper cleaning (segments trend toward all-valid or all-invalid), for six open segments instead of one, and no adaptation when a file behaves unlike its type.
Breaks whenBlock type is a poor predictor of lifetime for the workload, or the device cannot sustain several concurrent write streams.
Key points
  • "Unlike the LFS that has one large log area, F2FS maintains six major log areas to maximize the effect of hot and cold data separation. F2FS statically defines three levels of temperature (hot, warm and cold) for node and data blocks, as summarized in Table 1." (The paper's dashes around "hot, warm and cold" are replaced by parentheses here.)
  • Table 1: Node hot = "Direct node blocks for directories"; Node warm = "Direct node blocks for regular files"; Node cold = "Indirect node blocks"; Data hot = "Directory entry blocks"; Data warm = "Data blocks made by users"; Data cold = "Data blocks moved by cleaning; Cold data blocks specified by users; Multimedia file data".
  • "Direct node blocks are considered hotter than indirect node blocks since they are updated much more frequently. Indirect node blocks contain node IDs and are written only when a dedicated node block is added or removed. Direct node blocks and data blocks for directories are considered hot, since they have obviously different write patterns compared to blocks for regular files."
  • Cold data reasons: moved by cleaning ("Since they have remained valid for an extended period of time, we expect they will remain so in the near future"); labeled cold by the user ("F2FS supports an extended attribute operation to this end"); multimedia ("They likely show write-once and read-only patterns. F2FS identifies them by matching a file's extension against registered file extensions").
  • "Since the flash storage devices exploit media parallelism, multiple active segments can run simultaneously without frequent management operations, making performance degradation due to multiple logging (vs. single-segment logging) insignificant."
  • Section 4.1 says F2FS "estimates update likelihood using information readily available, such as file operation (append or overwrite), file type (directory or regular file) and file extensions." Table 1 has no append-versus-overwrite rule; this guide could not find one in the paper's design section (see Source notes).
How it works, step by step: a mail server delivers one message while a user copies photos (illustrative)
  1. Create inbox/msg123: a new entry in the inbox's dentry block (hot data log) and an update to the directory's direct node, here its inode (hot node log).
  2. Write the 16 KB message: 4 data blocks (warm data log) and the new file's inode with their addresses (warm node log).
  3. Copy IMG_0042.jpg: the extension matches a registered multimedia extension, so its data blocks go to the cold data log; its inode and direct nodes still go to the warm node log, since nodes are classified by node type (inference from Table 1).
  4. A large file grows enough to need a new direct node: the indirect node holding the new node's ID is rewritten to the cold node log.
  5. Later, the cleaner moves the still-valid blocks of an old warm data segment: they are written to the cold data log, joining other long-lived data.
  6. Result: the hot logs fill with blocks that die quickly (dentries and directory nodes churn with every create and delete), the cold data log with blocks that rarely die, so segments in each log tend toward empty or full (measured in Figure 6, M12).
Assumptions it relies on
  • A1. Block type predicts update frequency: directory blocks and direct nodes change often, indirect nodes rarely (stated).
  • A2. Data that survived until cleaning will keep surviving (stated).
  • A3. Multimedia files, identified by extension, are written once (stated: "likely").
  • A4. The device absorbs several concurrent sequential streams at no cost (stated: media parallelism).
If an assumption changes
  • A1 changes (a database file rewritten constantly): its data is "warm" like everything else users write and shares segments with cold-ish user data; only cleaning eventually separates them (inference).
  • A2 changes (cleaned data that is soon overwritten): those blocks pollute the cold log with dying blocks, and cold segments become partly valid, the expensive kind to clean (inference).
  • A3 changes (a photo editor rewriting .jpg files): rewritten photos land in the cold log, again mixing short and long lifetimes (inference).
  • A4 changes (a single-channel eMMC that serializes streams): six interleaved streams look like random writes to the device; this is one reason the log count can be reduced to two or four at mount (the paper: "if doing so is believed to yield better results on a given storage device and platform").
Design notes and rejected alternatives

Related work separates hot and cold data by monitoring at run time: WOLF reorders in the buffer cache, SFS tracks "write counts and age per block" and groups segments by "iterative quantization", DAC clusters in the FTL. F2FS uses only "information readily available", which costs no tracking memory or CPU; the paper says run-time monitoring "can be incorporated in F2FS to fine-track data temperature." LFS separates by age only at cleaning time (it sorts live blocks by age when rewriting them); F2FS separates at write time and again at cleaning time (moved blocks go cold, and background cleaning uses age, M12).

Connections

LFS: one log plus age-sorting in the cleaner versus six logs at write time. Hints: classifying by type is a hint in Lampson's sense: cheap, usually right, and wrong only in cost, never in correctness (inference). Memory tiering: the same choice as placing pages in fast or slow memory by static type (stack, heap, file cache) versus measured access counts (inference).

M10 · How many logs, and zones that keep an associative FTL from remixing them

TL;DR
ProblemHybrid FTLs absorb updates in shared "log flash blocks"; if F2FS's separated streams fall into the same FTL group, the FTL puts them back into the same flash block.
MechanismEach active log takes its segments from a different zone, so its addresses fall into a different FTL set; the number of logs (2, 4 or 6) is a mount option.
Trade-offSeparation that survives into the device, for free space that is partitioned by zone and a dependency on the FTL being set-associative.
Breaks whenThe FTL is fully associative (any log block takes any address) or page-mapped, where address ranges do not determine flash placement.
Key points
  • "By default, F2FS activates six logs open for writing. The user may adjust the number of write streams to two or four at mount time if doing so is believed to yield better results on a given storage device and platform. If six logs are used, each logging segment corresponds directly to a temperature level listed in Table 1. In the case of four logs, F2FS combines the cold and warm logs in each of node and data types. With only two logs, F2FS allocates one for node and the other for data types."
  • "FTL algorithms are largely classified into three groups (block-associative, set-associative and fully-associative) according to the associativity between data and “log flash blocks” [24]. Once a data flash block is assigned to store initial data, log flash blocks assimilate data updates as much as possible, like the journal in EXT4 [18]."
  • "The log flash block can be used exclusively for a single data flash block (block-associative) [13], for all data flash blocks (fully-associative) [17], or for a set of contiguous data flash blocks (set-associative) [24]. Modern FTLs adopt a fully-associative or set-associative method, to be able to properly handle random writes."
  • "Note that F2FS writes node and data blocks in parallel using multi-head logging and an associative FTL would mix the separated blocks (in the file system level) into the same flash block. In order to avoid such misalignment, F2FS maps active logs to different zones to separate them in the FTL. This strategy is expected to be effective for set-associative FTLs."
  • "Multi-head logging is also a natural match with the recently proposed “multi-streaming” interface [10]." Reference [10], the multi-streamed SSD paper, shares an author (Sangyeun Cho) with this one.
How it works, step by step: configuring logs and zones (illustrative)
  1. Format: choose segments per section and sections per zone to match the FTL (M2). Suppose an FTL set covers 16 MB of logical space: make a zone 16 MB.
  2. Mount: choose 6, 4 or 2 logs. Each active log is given a current segment.
  3. Allocating a new segment for a log picks a free segment in a zone not currently used by another active log (the paper: "maps active logs to different zones"), so concurrent streams fall into different FTL sets.
  4. Inside the device, each set's log flash blocks receive one stream, so each such block holds blocks of one temperature and tends to die as a unit.
  5. With a multi-stream SSD (the interface the paper mentions), each log could tag its writes with a stream ID instead, and the device would separate them directly (inference).
Assumptions it relies on
  • A1. The FTL is set-associative, so logical address ranges decide which log flash blocks absorb writes (stated: "expected to be effective for set-associative FTLs").
  • A2. The zone size matches the FTL's set size (implicit).
  • A3. The device has enough parallel resources for several open streams (stated).
If an assumption changes
  • A1 changes (fully associative or page-mapped FTL): streams are mixed by arrival time in whatever block is open; the remaining separation comes from writing each log's data in large sequential runs (inference).
  • A2 changes (zones smaller than a set): two zones can share a set, recreating the left panel (inference).
  • A3 changes: reduce to four or two logs at mount; Figure 6 shows how much separation that gives up (M12, F).
Design notes and rejected alternatives

The paper's own experiment (Figure 6) found four logs barely better than two, and says that merging differently ("If we separate cold data from hot and warm data ... rather than hot data from warm and cold data (default), the result would look different"). The four-log merge rule is therefore a choice whose alternative, by the authors' own account, could give a different result. The paper does not report any measurement of zones' effect on FTL GC.

Connections

Exokernel: zones are a workaround for an interface that hides placement; multi-stream SSDs (and later zoned devices, general knowledge) expose it, in the Exokernel spirit of letting the layer with the knowledge decide (inference). Superpages: like a page colored to avoid cache-set conflicts, a log is "colored" to avoid FTL-set conflicts (inference).

M11 · Cleaning: when it runs, in what unit, and with how much reserve

TL;DR
ProblemOnce the volume has filled, every new log segment must come from cleaning, so cleaning cost sets sustained performance.
MechanismClean one section at a time: in the foreground only when free sections run short, otherwise in a periodically woken background thread that stays out of the way of normal I/O; keep 5% of space unused so cleaning always has room.
Trade-offApplications pay cleaning latency only in emergencies, in exchange for depending on idle time for the cheaper background work, and 5% of capacity.
Breaks whenThe system is never idle (background cleaning never runs) and the volume is nearly full (foreground cleaning on every allocation).
Key points
  • "Cleaning is a process to reclaim scattered and invalidated blocks, and secures free segments for further logging. Because cleaning occurs constantly once the underlying storage capacity has been filled up, limiting the costs related with cleaning is extremely important for the sustained performance of F2FS (and any LFS in general). In F2FS, cleaning is done in the unit of a section."
  • "F2FS performs cleaning in two distinct manners, foreground and background. Foreground cleaning is triggered only when there are not enough free sections, while a kernel thread wakes up periodically to conduct cleaning in background."
  • "Background cleaning does not kick in when normal I/O or foreground cleaning is in progress."
  • "F2FS reserves a small unused capacity (5% of the storage space by default) so that the cleaning process has room for adequate operation at high storage utilization levels."
  • Foreground cleaning is one of the events that trigger a checkpoint (Section 2.7: "events like sync, umount and foreground cleaning").
  • Evaluation: background cleaning is hard to show because it "is suppressed during busy periods"; the authors "measured over 10% performance improvement at a 90% utilization level when we insert an idle time of ten minutes or more between runs."
How it works, step by step: a write arrives when free sections are short
  1. The writer needs a new segment for its log and the free-section count is below the foreground threshold (the implementation compares free sections with what the dirty node and dentry blocks will need plus a reserve; general knowledge, the paper says only "not enough free sections").
  2. Foreground cleaning: pick a victim section greedily (M12), move its valid blocks immediately (M13), and write a checkpoint so the section becomes free (M14, M16). The writing thread waits for all of it.
  3. Background cleaning, in contrast, runs from a kernel thread that wakes periodically (general knowledge: by default every 30 to 60 seconds, backing off when nothing is worth cleaning), skips its turn if the system is busy, picks a victim by cost-benefit, and only marks the victim's valid blocks dirty in the page cache.
  4. The 5% reserve on the 120 GB test partition is 6 GB (this guide's arithmetic). Section 3.2.4's utilization levels (80% to 97.5%) are measured on the capacity left after this reserve.
  5. Below 5% clean sections, F2FS stops appending altogether and switches to threaded logging, which avoids cleaning on the write path (M15).
Assumptions it relies on
  • A1. Workloads have idle periods in which background cleaning can work (implicit; the evaluation needed inserted idle time to show any effect).
  • A2. A 5% reserve leaves the cleaner enough room to make progress (stated).
  • A3. Cleaning a whole section at once matches the FTL's reclaim unit (stated intent of sections, M2).
If an assumption changes
  • A1 changes (a server busy around the clock): background cleaning rarely runs, so free sections come only from foreground cleaning or from threaded logging avoiding the need; the cheaper cost-benefit choices are never made (inference).
  • A2 changes (a smaller reserve): at high utilization, victims carry more valid blocks and each cleaning frees less; the paper does not test reserves other than 5%.
  • A3 changes (sections smaller than the FTL unit): F2FS frees space the device cannot reclaim without its own copying (M2).
Design notes and rejected alternatives

Sprite LFS starts cleaning when clean segments drop below a threshold ("typically a few tens of segments", LFS paper) and cleans until a second threshold is passed. F2FS splits by urgency instead: latency-critical cleaning is greedy and immediate, opportunistic cleaning is smarter and lazy. The 5% reserve is the file system's version of an SSD's over-provisioned spare area; Section 3.2.4 calls it "overprovisioning".

Connections

FFS: the 10% free reserve that keeps FFS's allocator effective is the same idea as F2FS's 5% reserve. LFS: same goal (sustained write performance) and same dependence on idle time; the LFS paper hoped "to perform much of the cleaning at night or during other idle periods". Livelock: background work suppressed while foreground work exists, with a foreground fallback when it falls behind (inference).

M12 · Victim selection: greedy in the foreground, cost-benefit in the background

TL;DR
ProblemWhich section to clean: the cheapest one now, or the one whose cleaning pays off longest?
MechanismGreedy (fewest valid blocks) when an application is waiting; cost-benefit (few valid blocks and old age, the age averaged from the SIT's per-segment modification times) in background cleaning.
Trade-offMinimum copying per cleaning when latency matters, versus better long-run separation of hot and cold data when it does not.
Breaks whenGreedy runs constantly on mixed data (it keeps cleaning hot segments that would have emptied on their own), or modification times are a poor proxy for future stability.
Key points
  • "The cleaning process starts first to identify a victim section among non-empty sections." The two policies are "greedy and cost-benefit [11, 27]", citing Kawaguchi et al. and the LFS paper.
  • "The greedy policy selects a section with the smallest number of valid blocks. Intuitively, this policy controls overheads of migrating valid blocks. F2FS adopts the greedy policy for its foreground cleaning to minimize the latency visible to applications."
  • "On the other hand, the cost-benefit policy is practiced in the background cleaning process of F2FS. This policy selects a victim section not only based on its utilization but also its “age”. F2FS infers the age of a section by averaging the age of segments in the section, which, in turn, can be obtained from their last modification time recorded in SIT. With the cost-benefit policy, F2FS gets another chance to separate hot and cold data."
  • The paper gives no formula. The LFS paper's is benefit / cost = (1 − u) × age / (1 + u). The Linux F2FS code uses the same shape with u and age scaled to 0..100, age measured relative to the oldest and newest segment times (general knowledge).
  • Figure 6 measures the result of separation at write time: with six logs, dirty segments split into a nearly empty group and a nearly full group (redrawn below).
How it works, step by step: two candidate sections (illustrative numbers, 512 blocks each)
  1. Section A: 100 valid blocks (u ≈ 0.20), last modified 5 minutes ago. Section B: 300 valid blocks (u ≈ 0.59), last modified 2 days (2,880 minutes) ago.
  2. Greedy picks A: copy 100 blocks to free 412, 0.24 copies per freed block. B would cost 300 copies for 212 blocks, 1.42 per freed block.
  3. Cost-benefit with the LFS formula: A: (1 − 0.20) × 5 / (1 + 0.20) ≈ 3.3; B: (1 − 0.59) × 2,880 / (1 + 0.59) ≈ 743. B wins by a factor of over 200.
  4. Why B is the better long-run choice: A's 100 valid blocks were written minutes ago and are likely to be overwritten soon, so A may empty itself for free. B's blocks have survived two days; moved to the cold data log they will stay put, and the 212 free blocks B yields stay free (the LFS paper's argument, applied here).
  5. With F2FS's scaled version (general knowledge), if A is the newest and B the oldest segment, A's age scores 0 and its value is 0, while B scores 100 × (100 − 59) × 100 / (100 + 59) ≈ 2,580; B is chosen.
  6. In the foreground none of this matters: the application is waiting, and A frees space with the least copying now.
Assumptions it relies on
  • A1. Copying cost is proportional to valid blocks (implicit; true when reading is cheap, as on flash; LFS charged for reading the whole segment too).
  • A2. Older data is more stable (the cost-benefit premise, inherited from LFS).
  • A3. A section's age can be summarized by the average of its segments' last modification times (stated).
If an assumption changes
  • A1 changes (reads are expensive, as on a disk): each victim costs a full section read plus the copies, and a nearly empty victim is still not free; LFS's cost term 1 + u reflects this, and F2FS keeps the term even though flash reads are cheap (inference).
  • A2 changes (old data suddenly rewritten, e.g., a photo library edited): cost-benefit has just paid to move blocks that die soon after; it guessed wrong at a higher cost than greedy would have (inference).
  • A3 changes (a section with one very old and one brand-new segment): the average hides both; with the default of one segment per section, the issue does not arise (inference).
Design notes and rejected alternatives

LFS uses cost-benefit everywhere, since its simulations showed greedy performs worse under locality. F2FS uses greedy where latency matters because the application is blocked, and, plausibly, because write-time separation (six logs) already provides much of the bimodal distribution LFS needed cost-benefit to create (inference; the paper gives only the latency reason). Figure 6 shows that with six logs about half the dirty segments hold 100 or fewer valid blocks, so even greedy victims are cheap (this guide's reading of the figure).

Connections

LFS: the policies and formula come from it; LFS's Figure 6 shows the same bimodal shape produced by cost-benefit cleaning with age sorting. FTLs: device GC chooses victims the same two ways (general knowledge). Memory allocators and compacting GCs: evacuate the regions with the least live data first (greedy) unless generational information says otherwise (inference).

M13 · Finding valid blocks (SIT), finding their owners (SSA), and moving them lazily

TL;DR
ProblemTo move a valid block, the cleaner must know which blocks in the victim are valid and which node points at each one, without reading every inode.
MechanismA per-segment validity bitmap in the SIT identifies valid blocks; the SSA entry for each gives its parent node and offset; foreground cleaning writes the moved blocks now, background cleaning just marks them dirty in the page cache.
Trade-offFast identification (a bitmap scan) for 64 bytes of bitmap per segment; lazy migration avoids competing with foreground I/O, at the cost of a delay before the section can be freed.
Breaks whenMemory pressure flushes or drops the lazily migrated pages at bad moments, or the parent node must be read from flash for every block.
Key points
  • "After selecting a victim section, F2FS must identify valid blocks in the section quickly. To this end, F2FS maintains a validity bitmap per segment in SIT. Once having identified all valid blocks by scanning the bitmaps, F2FS retrieves parent node blocks containing their indices from the SSA information. If the blocks are valid, F2FS migrates them to other free logs."
  • "For background cleaning, F2FS does not issue actual I/Os to migrate valid blocks. Instead, F2FS loads the blocks into page cache and marks them as dirty. Then, F2FS just leaves them in the page cache for the kernel worker thread to flush them to the storage later. This lazy migration not only alleviates the performance impact on foreground I/O activities, but also allows small writes to be combined."
  • Table 1: data blocks moved by cleaning go to the cold data log.
  • The SSA records "parent inode number and its node/data offsets" (Section 2.1).
How it works, step by step: background cleaning of the section above
  1. Scan the bitmap: 512 bits (64 bytes) per segment; the four 1s mark blocks 0, 7, 10 and 15.
  2. For each, read its SSA entry: block 0 belongs to node 7731 at slot 245 (data block), and so on. For a node block in a node section, the SSA gives the node ID itself (general knowledge).
  3. Check the parent: look up 7731 in the NAT, read that direct node, and confirm slot 245 still holds block 0's address. If it does not, the block is stale and is skipped.
  4. Migrate lazily: read the block into the page cache and mark it dirty, tagged for the cold data log. No write is issued now.
  5. Later, writeback writes the four blocks (perhaps together with other dirty pages) to the cold data log and updates slots in nodes 7731, 902 and 5120, which are then written to their node log. The SIT clears the victim's bits and sets the new ones.
  6. With zero valid blocks left, the section becomes pre-free (M14).
Assumptions it relies on
  • A1. The SIT bitmaps are accurate (implicit; they are updated on every block invalidation).
  • A2. The SSA entry names the block's current owner (stated purpose: "identify parent node blocks before migrating").
  • A3. Dirty pages in the page cache will be written back within a reasonable time (implicit in lazy migration).
If an assumption changes
  • A1 changes (no per-block bitmap, as in LFS): the cleaner must check every block's owner to decide liveness; LFS does this with the summary block plus a version number per file (LFS paper), which costs reading inodes for live candidates (inference).
  • A2 changes (no SSA): finding the parent of a data block would require searching the file system's index; the SSA is a reverse map, the same thing FTLs keep in each page's spare area (general knowledge).
  • A3 changes (writeback delayed under memory pressure or held back): the victim cannot become pre-free until the moved blocks are actually written; lazy cleaning frees space later than the decision to clean (inference).
Design notes and rejected alternatives

Lazy migration reuses the normal write path: moved blocks go through the page cache, get merged with other writes, and are allocated by the same log logic as user writes. The cost is that background cleaning's benefit arrives only after writeback and a checkpoint. Foreground cleaning cannot afford that and writes immediately.

Connections

LFS: the segment summary block plays the SSA's role; LFS avoids a bitmap by checking version numbers and inode pointers, which F2FS replaces with the SIT bitmap. FTLs: page-level valid bitmaps and reverse maps in the spare area are standard FTL equipment (general knowledge); F2FS keeps the same two structures at the file system level. Rethink the Sync: deferring the moved blocks' writes to normal writeback is the same choice of doing work later unless someone needs it now (inference).

M14 · Pre-free sections: freed space waits for a checkpoint

TL;DR
ProblemThe last checkpoint may still reference blocks in a section the cleaner just emptied; reusing it before a new checkpoint could overwrite data that recovery would need.
MechanismA cleaned section becomes "pre-free"; only after the next checkpoint is it free for allocation.
Trade-offCrash safety for roll-back recovery, in exchange for delaying reuse until a checkpoint (and forcing a checkpoint when space is urgently needed).
Breaks whenCheckpoints are rare and space is tight, so many pre-free sections sit unusable.
Key points
  • "After all valid blocks are migrated, a victim section is registered as a candidate to become a new free section (called a “pre-free” section in F2FS). After a checkpoint is made, the section finally becomes a free section, to be reallocated."
  • "We do this because if a pre-free section is reused before checkpointing, the file system may lose the data referenced by a previous checkpoint when unexpected power outage occurs."
  • Foreground cleaning triggers a checkpoint (Section 2.7), which is what turns its freshly cleaned sections into usable ones (inference connecting the two rules).
How it works, step by step: what goes wrong without the rule
  1. Checkpoint v41 is written. In it, the NAT says direct node 7731 is at address X, whose slot 245 points to data block 0 of section S.
  2. The cleaner moves block 0 to the cold log at address Y and writes node 7731 at a new address Z with slot 245 = Y. The in-memory NAT says 7731 → Z. Section S now has no valid blocks.
  3. Suppose S were reused at once: the hot data log writes new dentry blocks over S, including the place where block 0 was.
  4. Power fails before checkpoint v42. At mount, F2FS rolls back to v41: the NAT says 7731 → X, X's slot 245 points into S, and S now holds a dentry block. The file silently returns wrong data.
  5. With the rule: S is pre-free and untouched until v42 is durable. After a crash before v42, v41's references into S are still intact. After v42, nothing durable points into S, and it becomes free.
Assumptions it relies on
  • A1. Recovery returns to the last checkpoint (stated: roll-back model, M18).
  • A2. Checkpoints happen often enough that pre-free sections do not pile up (implicit).
If an assumption changes
  • A1 changes (recovery replayed a full log instead of rolling back): the rule could be relaxed, but then every metadata change would need to be logged (inference).
  • A2 changes (long checkpoint intervals under heavy cleaning): cleaned space is unusable for long periods; foreground cleaning's built-in checkpoint is what keeps the emergency path working (inference).
Design notes and rejected alternatives

The same rule must also apply to individual blocks reused by threaded logging, since a block invalidated after the last checkpoint is still referenced by it. The paper does not discuss this; the implementation keeps a second bitmap of validity as of the last checkpoint and skips such blocks (general knowledge; Class Prep C4).

Connections

LFS: LFS has the same constraint: a segment may be reused only after a checkpoint no longer refers to it (general knowledge of LFS implementations). Shadow paging and copy-on-write file systems (BTRFS): old blocks are released only after the new root is durable (general knowledge). Salus: state may be discarded only after the replacement is durably committed (inference).

M15 · Adaptive logging: append while clean sections last, then fill holes

TL;DR
ProblemNear full, normal (append-only) logging spends its time cleaning; the paper reports performance drops of over 90% "under harsh conditions".
MechanismIf there are more than k clean sections (k = 5% of all sections by default), use normal logging; otherwise use threaded logging, writing new blocks into invalid slots of dirty segments, filling one segment's holes before moving to the next.
Trade-offNo cleaning on the write path, in exchange for random (but locally clustered) writes.
Breaks whenThe device is slow at random writes (an HDD, or weak flash), or holes are scattered so thinly that writes become truly random.
Key points
  • "The original LFS introduced two logging policies, normal logging and threaded logging. In the normal logging, blocks are written to clean segments, yielding strictly sequential writes. Even if users submit many random write requests, this process transforms them to sequential writes as long as there exists enough free logging space."
  • "As the free space shrinks to nil, however, this policy starts to suffer high cleaning overheads, resulting in a serious performance drop (quantified to be over 90% under harsh conditions, see Section 3.2.5). On the other hand, threaded logging writes blocks to holes (invalidated, obsolete space) in existing dirty segments. This policy requires no cleaning operations, but triggers random writes and may degrade performance as a result."
  • "Specifically, if there are more than k clean sections, where k is a pre-defined threshold, normal logging is initiated. Otherwise, threaded logging is activated. k is set to 5% of total sections by default and can be configured."
  • "Such random writes typically show better spatial locality than those in update-in-place file systems, since all holes in a dirty segment are filled first before F2FS searches for more in other dirty segments. Lee et al. [16] demonstrate that flash storage devices show better random write performance with strong spatial locality."
  • Section 1: "This strategy works well on modern flash devices but may not do so on HDDs."
  • Evaluation: in the fileserver aging test, F2FS adaptive "serves 51% of total writes with threaded logging"; F2FS normal "writes 27% more data than F2FS adaptive due to foreground cleaning"; in the full-device iozone test F2FS normal falls to "less than 5% of EXT4 from round 3" while F2FS adaptive tracks EXT4 (M15 numbers detailed in F).
How it works, step by step: the 120 GB partition crossing the threshold
  1. Threshold: 61,440 sections (one segment each, by default) × 5% = 3,072 clean sections, about 6 GB (this guide's arithmetic).
  2. With 4,000 clean sections, writes go to the head of their log in a clean segment: normal logging.
  3. At 3,072 or fewer, the next segment a log needs is a dirty one: the log fills that segment's invalid slots in order, then picks another dirty segment. No cleaning runs on the write path.
  4. Back above 3,072 (cleaning in the background, or deletes that leave whole sections invalid), new segments are clean again and writes return to appending.
  5. The measured effect (Figure 7, 80% utilization): on the third run "the file system ran out of free segments and there was a performance dip. During this run, it switched to threaded logging from normal logging, and as the result, performance stabilized." After that, "nearly all data were written via threaded logging, in place. In this case, cleaning is needed not for data, but for recording nodes."
  6. The cost at the top end: at 97.5% utilization "the performance loss was about 30% and WAF 1.02".
Assumptions it relies on
  • A1. On flash, random writes with locality inside a segment are much cheaper than cleaning a nearly full volume (stated, citing Lee et al. and Section 3.2.4's argument: "cleaning could render very costly due to a high WAF when the file system is fragmented, and SSDs have high random write performance").
  • A2. The free-section count is a good indicator of how expensive cleaning is about to become (implicit).
  • A3. Reusing holes does not endanger the last checkpoint (implicit; requires the safeguard in M14's design note).
If an assumption changes
  • A1 changes (an HDD): each hole fill is a seek and rotation, roughly 10 ms per 4 KB (general knowledge), against sequential bandwidth; the paper says the strategy "may not do so on HDDs". On such a device, cleaning in idle time would be preferable (inference).
  • A2 changes (plenty of clean sections but each dirty segment nearly full): the count says "normal logging" while cleaning would be expensive; the switch only looks at clean sections, not at the valid-block distribution (inference).
  • A3 changes (no checkpoint-validity check): a hole freed since the last checkpoint could be overwritten, and a crash would roll back to a checkpoint that points at it, the M14 failure at block granularity (inference).
Design notes and rejected alternatives

Two alternatives bracket the design. Always appending ("F2FS normal") is the paper's control: 48% drop in the fileserver aging test and under 5% of EXT4 in the full-device iozone test. Always threading would give up the sequential writes that make F2FS fast when space is plentiful (inference). Related work: Wilkes et al.'s hole plugging (move a victim's valid blocks into other segments' holes), Matthews et al.'s cost-benefit choice between normal logging and hole plugging, and Oh et al.'s threaded logging at high utilization. F2FS's switch is a fixed threshold rather than a cost model.

On the paper's history claim: the LFS paper describes "threading" (leaving live data in place and writing through the free extents) as the alternative to copying, and Sprite LFS threads only at whole-segment granularity; block-level threading in dirty segments is closer to Oh et al.'s work, which the paper cites for it in Section 1 (this guide's reading of both papers).

Connections

LFS: threading versus copying is LFS's Section 3.2 choice; F2FS makes it dynamically. FFS and EXT4: threaded logging at 100% utilization behaves much like an update-in-place file system, which is why F2FS adaptive converges to EXT4 in Figure 8(b) (inference). Livelock: a mode switch under overload that trades peak efficiency for guaranteed progress, like switching from interrupts to polling (inference).

M16 · The checkpoint procedure and what a checkpoint pack contains

TL;DR
ProblemThe Main area is a set of logs and the tables that describe it live in memory between checkpoints; after a power failure there must be one consistent, complete description to return to.
MechanismOn sync, unmount or foreground cleaning: flush dirty node and dentry blocks, pause namespace operations, write NAT, SIT and SSA, then write a checkpoint pack (header, table-set bitmaps, journals, active-segment summaries, orphan list, footer).
Trade-offA consistent recovery point and no full-volume scan at mount, for a brief stop of create, unlink and mkdir, and a burst of metadata writes.
Breaks whenCheckpoints are needed very often (for example, if every fsync required one); M19 exists to prevent that.
Key points
  • "Whenever it needs to remain a consistent state across events like sync, umount and foreground cleaning, F2FS triggers a checkpoint procedure as follows: (1) All dirty node and dentry blocks in the page cache are flushed; (2) It suspends ordinary writing activities including system calls such as create, unlink and mkdir; (3) The file system metadata, NAT, SIT and SSA, are written to their dedicated areas on the disk; and (4) Finally, F2FS writes a checkpoint pack, consisting of the following information, to the CP area".
  • Header and footer: "written at the beginning and the end of the pack, respectively. F2FS maintains in the header and footer a version number that is incremented on creating a checkpoint. The version number discriminates the latest stable pack between two recorded packs during the mount time".
  • NAT and SIT bitmaps: "indicate the set of NAT and SIT blocks comprising the current pack". NAT and SIT journals: "contain a small number of recently modified entries of NAT and SIT to avoid frequent NAT and SIT updates".
  • Summary blocks of active segments: "consist of in-memory SSA blocks that will be flushed to the SSA area in the future". Orphan blocks: "keep “orphan inode” information".
  • Dirty data blocks of regular files are not in the list: a checkpoint makes the namespace and the index consistent, and user data reaches the device by writeback or fsync (inference from the list; general knowledge confirms).
How it works, step by step: a sync arrives; the newest pack is v41
  1. Flush all dirty dentry blocks and node blocks to their logs (hot data, hot, warm and cold node logs). Each written node gets a new address, so more NAT entries change in memory.
  2. Suspend create, unlink, mkdir and other writers so nothing new becomes dirty. In the implementation steps 1 and 2 form a loop: block operations, and if anything is still dirty, unblock, flush and retry (general knowledge).
  3. Write tables: each NAT and SIT block with changed entries is written into the set that v41's bitmaps do not point to, unless its few changes fit in the journals (M17); the active segments' in-memory summaries go into the pack; other SSA blocks to the SSA area.
  4. Write the pack into the slot v41 is not in: header with version 42, bitmaps with the flipped bits, journals, summaries, orphan list, and the footer with version 42 last.
  5. After it is durable, pre-free sections become free (M14) and freed segments are discarded (M20). Operations resume.
Assumptions it relies on
  • A1. The device writes the pack's blocks durably in order, or at least makes the footer durable only after the rest (implicit; requires cache flushes or forced-unit-access writes, general knowledge).
  • A2. Pausing namespace operations for the duration of a checkpoint is acceptable (implicit; the paper does not measure checkpoint latency).
  • A3. Checkpoints are infrequent relative to writes (implicit; sync, umount and foreground cleaning only, with fsync handled separately).
If an assumption changes
  • A1 changes (a device that reorders writes in its cache and loses them on power failure): a footer could become durable before the body, making a torn pack look valid; matching versions alone cannot detect that (inference; the implementation also stores a CRC in the header and footer blocks, which protects those two blocks but not the ones between them, general knowledge).
  • A2 changes (latency-sensitive metadata workloads): every sync or foreground cleaning stalls all creates and unlinks for the checkpoint's duration (inference).
  • A3 changes (a checkpoint per fsync): the "naïve approach" the paper rejects in Section 2.7.2, because "checkpointing involves writing all node and dentry blocks unrelated to the database file".
Design notes and rejected alternatives

F2FS uses no journal for metadata, unlike EXT4: consistency comes from never overwriting the last consistent image. Logged blocks are new by construction; fixed-location tables get two sets; the pack gets two slots. The header-footer pair is a cheap torn-write detector.

Connections

LFS: two checkpoint regions used alternately, with "the checkpoint time ... in the last block of the checkpoint region, so if the checkpoint fails the time will not be updated"; F2FS's footer version plays the same role. Sprite LFS checkpoints every 30 seconds; F2FS checkpoints on events. Salus, Hints: atomic commit by writing a new version beside the old one and switching with a single small write (inference).

M17 · Two packs, two table sets, and the NAT and SIT journals

TL;DR
ProblemWriting NAT and SIT blocks in place would destroy the last consistent version mid-write; and a few changed entries would each cost a whole 4 KB block write.
MechanismTwo checkpoint packs used alternately; two sets of NAT and SIT blocks, selected per block by bitmaps in the pack; a small journal of recently changed NAT and SIT entries inside the pack.
Trade-offAtomic switching and fewer table writes, for doubled table space and an extra lookup (journal, then table).
Breaks whenMany scattered entries change between checkpoints, overflowing the journals into full block writes.
Key points
  • "In order to keep at least one stable checkpoint pack while creating a new pack, F2FS maintains two checkpoint packs. If a checkpoint pack has identical contents in the header and footer, F2FS considers it valid. Otherwise, it is dropped."
  • "Likewise, F2FS also manages two sets of NAT and SIT blocks, distinguished by the NAT and SIT bitmaps in each checkpoint pack. When it writes updated NAT or SIT blocks during checkpointing, F2FS writes them to one of the two sets alternatively, and then mark the bitmap to point to its new set."
  • "If a small number of NAT or SIT entries are updated frequently, F2FS would write many 4KB-sized NAT or SIT blocks. To mitigate this overhead, F2FS implements a NAT and SIT journal within the checkpoint pack. This technique reduces the number of I/Os, and accordingly, the checkpointing latency as well."
  • Sizes (general knowledge): a NAT entry is 9 bytes (version, inode number, block address), so 455 per block; a SIT entry is 74 bytes, 55 per block; the journals hold about 38 NAT entries and 6 SIT entries.
How it works, step by step: a checkpoint after a burst of fsync calls (illustrative)
  1. Since v41, 20 direct nodes in 20 different files moved, so 20 NAT entries changed; their node IDs fall in 20 different NAT blocks. 6 segments had blocks invalidated or added, so 6 SIT entries changed.
  2. Without journals: 20 NAT blocks + up to 6 SIT blocks, each 4 KB, written to the alternate sets: 26 random 4 KB writes, about 104 KB, to record about 20 × 9 + 6 × 74 = 624 bytes of changes (this guide's arithmetic).
  3. With journals: all 20 NAT entries fit in the NAT journal (about 38) and the 6 SIT entries in the SIT journal (about 6), so no table block is written at all; the changes ride in the pack, which is written anyway.
  4. When a journal overflows, its entries are flushed into the corresponding table blocks (alternate set), and the bitmaps flip for those blocks (general knowledge of the implementation).
  5. On lookup, the in-memory NAT cache is consulted first; at mount, journal entries override the table blocks they belong to (general knowledge).
Assumptions it relies on
  • A1. Between checkpoints, only "a small number" of NAT and SIT entries change (stated as the case the journal targets).
  • A2. Doubling the NAT and SIT areas costs little space (implicit; they are a small fraction of the volume).
If an assumption changes
  • A1 changes (checkpoints after heavy random writes across many files): the journals overflow, and the checkpoint writes one NAT block per touched 455-entry range and one SIT block per touched 55-segment range: the "Random Writes" region of Figure 1 at its busiest (inference).
  • A2 changes: negligible in practice; on the 120 GB example, two SIT sets are about 2 × 1,118 blocks ≈ 8.7 MB (this guide's arithmetic with 55 entries per block).
Design notes and rejected alternatives

Two sets per table block (rather than two copies of the whole table) mean only changed blocks are written, and a single bit per block in the pack selects the current copy: shadow paging at 4 KB granularity, committed by the pack. Putting the journals inside the pack makes the cheapest case free.

Connections

LFS: LFS writes inode map and segment usage table blocks into the log at each checkpoint, so it never needs two sets; F2FS pays the double area for fixed addresses (M3). FTLs: map updates in many FTLs are batched and journaled in a similar way (general knowledge). Hints: "log updates to record the truth about the state" and "make actions atomic or restartable" (Lampson's slogans; the mapping is inference).

M18 · Roll-back recovery at mount, and orphan inodes

TL;DR
ProblemAfter a power failure, find a consistent state quickly, without scanning the volume, and reclaim the space of files that were deleted while still open.
MechanismRead both packs, drop invalid ones, take the newer valid one; truncate and free the inodes on its orphan list; run roll-forward (M19); then start with the NAT and SIT sets its bitmaps select.
Trade-offMount-time work proportional to the orphan list and the post-checkpoint log, for losing everything after the last checkpoint that was not fsynced.
Breaks whenApplications rely on ordering or durability without fsync; anything since the last checkpoint not covered by roll-forward is gone.
Key points
  • "After a sudden power-off, F2FS rolls back to the latest consistent checkpoint."
  • "During the recovery procedure at mount time, F2FS searches valid checkpoint packs by inspecting headers and footers. If both checkpoint packs are valid, F2FS picks the latest one by comparing their version numbers."
  • "Once selecting the latest valid checkpoint pack, it checks whether orphan inode blocks exist or not. If so, it truncates all the data blocks referenced by them and lastly frees the orphan inodes, too. Then, F2FS starts file system services with a consistent set of NAT and SIT blocks referenced by their bitmaps, after the roll-forward recovery procedure is done successfully".
  • Orphans: "If an inode is deleted before it is closed (e.g., this can happen when two processes open a common file and one process deletes it), it should be registered as an orphan inode, so that F2FS can recover it after a sudden power-off." "Recover" here means reclaiming its space, since the file has no name left (inference from the truncate-and-free step).
How it works, step by step: power fails while a video player holds a deleted temporary file open
  1. Before the crash: process A has /tmp/cache.bin (40 MB) open; process B unlinks it. The name is gone, but the inode and its 10,240 blocks must live until A closes it, so the inode is put on the orphan list; checkpoint v42 records it in its orphan blocks.
  2. Power fails before A closes the file.
  3. Mount: slot 0 holds v43 with header 43 and footer 41 (torn); slot 1 holds v42, header and footer both 42. v43 is dropped; v42 is used.
  4. Orphans: v42 lists the inode; F2FS truncates its 10,240 data blocks (marking them invalid in the SIT) and frees the inode. Without this, 40 MB would leak until a full check.
  5. Roll-forward replays fsynced direct nodes written after v42 (M19), then a new checkpoint is written, and the file system goes live.
Assumptions it relies on
  • A1. At least one pack is always valid (stated: two packs so that one stable pack survives).
  • A2. Everything durable that recovery needs is reachable from the pack: tables via bitmaps, active segments via summaries, orphans via orphan blocks (stated).
  • A3. Applications that need durability call fsync (implicit).
If an assumption changes
  • A1 changes (both packs damaged by a media error): the paper describes no fallback; only an offline checker could rebuild (inference).
  • A2 changes (an orphan list too large for the pack's orphan blocks): recovery would leak the overflow; the implementation bounds the number of orphans (general knowledge).
  • A3 changes (an app relying on write ordering without fsync): after a crash it sees the state of the last checkpoint, possibly seconds old, with no newer unsynced writes at all (inference).
Design notes and rejected alternatives

The rejected alternative is the FFS approach: scan all metadata after a crash (fsck). Roll-back makes mount time independent of volume size; the price is the loss of unsynced work since the checkpoint, which is the usual contract of UNIX file systems anyway.

Connections

FFS: fsck scans everything; F2FS reads two packs. LFS: "reads both checkpoint regions and uses the one with the most recent time"; orphan handling is an addition (LFS's directory operation log covers a related consistency problem). Rethink the Sync: what a crash may lose is exactly what was not made durable; F2FS's answer is fsync plus checkpoints, Rethink the Sync's is external synchrony (inference).

M19 · fsync acceleration and roll-forward recovery

TL;DR
ProblemSQLite-style workloads call fsync after every few KB; implementing fsync as a checkpoint writes every dirty node and dentry block in the system.
Mechanismfsync writes only the file's data blocks and their direct node blocks, with a special flag in the node blocks; after a crash, roll back to the checkpoint, find the flagged nodes in the log, merge their new data indices into the checkpointed nodes, and checkpoint.
Trade-offfsync cost proportional to the file's changes, for extra mount-time work and NAT, SIT and SSA updates that are deferred and reconstructed.
Breaks whenThe fsynced change needs metadata beyond direct nodes to be found (a new name in a directory, a rename); then the implementation falls back to a checkpoint (general knowledge, Class Prep C6).
Key points
  • "Applications like database (e.g., SQLite) frequently write small data to a file and conduct fsync to guarantee durability. A naïve approach to supporting fsync would be to trigger checkpointing and recover data with the roll-back model. However, this approach leads to poor performance, as checkpointing involves writing all node and dentry blocks unrelated to the database file."
  • "The key idea is to write data blocks and their direct node blocks only, excluding other node or F2FS metadata blocks. In order to find the data blocks selectively after rolling back to the stable checkpoint, F2FS remains a special flag inside direct node blocks."
  • "If we denote the log position of the last stable checkpoint as N, (1) F2FS collects the direct node blocks having the special flag located in N+n, while constructing a list of their node information. n refers to the number of blocks updated since the last checkpoint. (2) By using the node information in the list, it loads the most recently written node blocks, named N-n, into the page cache. (3) Then, it compares the data indices in between N-n and N+n. (4) If it detects different data indices, then it refreshes the cached node blocks with the new indices stored in N+n, and finally marks them as dirty. Once completing the roll-forward recovery, F2FS performs checkpointing to store the whole in-memory changes to the disk."
  • Reading of the notation (this guide's interpretation; the paper does not define it further): "N+n" are the flagged node blocks found in the log after position N; "N-n" are the versions of the same nodes that the checkpoint's NAT points to, the latest as of the checkpoint.
  • Measured effect: on SQLite, "F2FS reduces the amount of data writes by about 46% over EXT4 in all examined cases", and "the roll-forward recovery policy of F2FS produces huge benefits".
How it works, step by step: what one SQLite commit costs (illustrative)
  1. Commit: SQLite appends one 4 KB page to its WAL file and calls fsync. While the WAL file is under 3.6 MB, its data pointers live in its inode, which therefore is the "direct node" for this file (inference from M4's counts; Table 3 lists 3.3 MB files for the SQLite benchmark).
  2. F2FS roll-forward path: write the data block (warm data log), wait, write the inode block with the flag (warm node log), flush: 2 blocks, 8 KB, each appended sequentially to its log.
  3. Checkpoint path (rejected): flush every dirty node and dentry block in the system, write changed NAT, SIT and SSA blocks (or journals), write a pack of several blocks: at least the pack plus whatever else is dirty, typically many more than 2 blocks (illustrative).
  4. EXT4 path (general knowledge, ordered journaling): the data block in place, plus a journal transaction with a descriptor, the inode table block, and a commit block, about 4 blocks, with one of them at a random address.
  5. Compare with the measurement: 2 blocks against about 4 is a reduction of about half, consistent in size with the paper's "about 46%" fewer data writes on SQLite (this guide's illustration, not the paper's accounting).
Assumptions it relies on
  • A1. A direct node contains everything needed to make the file's new data reachable (stated: data blocks "and their direct node blocks only").
  • A2. Recovery can find all flagged nodes written since the checkpoint without the NAT (implicit; the paper says only that it "collects the direct node blocks having the special flag located in N+n").
  • A3. The data blocks are durable before the flagged node that points to them (implicit; general knowledge confirms the ordering).
  • A4. The change being synced does not involve the namespace (implicit; the paper's examples are database files).
If an assumption changes
  • A1 changes (the fsync also grew the file into a new indirect range): the new direct node must be linked from an indirect node that roll-forward does not replay; F2FS handles this by writing the inode with its node pointers too or by checkpointing (general knowledge; the paper is silent).
  • A2 changes (the node log wrapped into reused segments): stale nodes from before the checkpoint could look like new ones; the implementation stamps each node with the checkpoint version to reject them (general knowledge, Class Prep C3).
  • A3 changes (a device that reorders writes): a flagged node could point to garbage; the cache flush after the node write is what makes the fsync durable at all (general knowledge).
  • A4 changes (fsync of a newly created file): the directory entry is not written by this path; see Class Prep C6.
Design notes and rejected alternatives

The paper's rejected alternative is fsync-as-checkpoint ("poor performance"). Unlike LFS's roll-forward, which replays everything found in the log after the checkpoint (new inodes, data, and a directory operation log), F2FS replays only what fsync flagged; ordinary writeback after the checkpoint is discarded by the roll-back even if it reached the device. That keeps recovery simple and bounded, and makes the flag the only commit record.

Connections

LFS: roll-forward over segment summaries, with a directory operation log for namespace consistency; Sprite LFS had not installed roll-forward in production when the paper was written. Rethink the Sync: both reduce the cost of synchronous durability: Rethink the Sync by deferring when the caller must block, F2FS by shrinking what each fsync writes (inference). NFS: an NFS server must make data and metadata durable before replying; the F2FS path would turn that into a data block plus a flagged node per request (inference).

M20 · Discards in whole segments, at checkpoint time

TL;DR
ProblemThe FTL keeps copying logical blocks it believes are valid until told otherwise; telling it with many small discard commands costs command processing time, especially on SATA.
MechanismF2FS issues discards only for whole obsolete segments, and only when a checkpoint is made.
Trade-offFew, large discards and no risk of discarding data the last checkpoint references, for discarding less address space and later than an eager scheme.
Breaks whenInvalid space stays scattered inside partly valid segments (it is never discarded until cleaned), or checkpoints are rare.
Key points
  • Footnote 3: "A discard command gives a hint to the underlying flash storage device that a specified address range has no valid data. This command is sometimes called “trim” or “unmap”."
  • Fileserver on the SATA SSD: EXT4 "issues many small discard commands and causes visible command processing overheads, especially on the SATA drive; it trims two thirds of all block addresses covered by data writes and nearly 60% of all discard commands were for an address space smaller than 256KB in size."
  • "In contrast, F2FS discards obsolete spaces in the unit of segments only when checkpointing is triggered; it trims 38% of block address space with no small discard commands. These differences lead to a 2.4× performance gain (Figure 4(a))."
  • BTRFS "trims 47% of block address space with small discard commands (corresponding to 75% of all discard commands) during the read service time"; its fileserver performance is 8% below EXT4. In the aging test, "The large performance hit on BTRFS is due partly to the heavy usage of small discard commands."
  • The paper describes this behavior only in the evaluation; Section 2 does not present it as a mechanism.
How it works, step by step: one cleaned segment
  1. Cleaning empties segment 4,812 (512 blocks); it becomes pre-free (M14).
  2. At the next checkpoint, it becomes free, and F2FS sends one discard for its 2 MB range.
  3. The FTL marks those pages invalid; when GC later picks their flash blocks, it does not copy them.
  4. EXT4 by comparison (fileserver trace): nearly 60% of its discards cover less than 256 KB; if all of them did, freeing the same 2 MB would take more than eight commands (this guide's arithmetic).
  5. Why that is expensive on SATA: on SATA devices of this era, TRIM is a non-queued command, so each one drains the device's command queue before it runs (general knowledge, which explains the paper's "especially on the SATA drive").
Assumptions it relies on
  • A1. Discard commands have a fixed per-command cost large enough to matter (stated as observed: "visible command processing overheads").
  • A2. Space freed by cleaning comes in whole segments (implicit: sections are emptied entirely).
  • A3. Discarding before the checkpoint would be unsafe (inference: a discarded range may read back as zeros, so it must not be referenced by the last checkpoint, the same reason as M14).
If an assumption changes
  • A1 changes (queued TRIM, as on NVMe, general knowledge): small discards cost little, and the advantage of batching shrinks; consistent with the PCIe SSD's fileserver results where all file systems are close (inference).
  • A2 changes (threaded logging at high utilization): holes inside dirty segments are reused, not discarded, so the device keeps copying invalid data in them until F2FS overwrites them (inference).
  • A3 changes: eager discards would be faster to inform the FTL but would need the same checkpoint guard to be safe (inference).
Design notes and rejected alternatives

Discards are the channel through which file system cleaning becomes device GC savings: freeing a section in F2FS saves the FTL nothing until the FTL is told. Batching them per segment at checkpoint time matches the segment and section alignment of M2. The paper attributes the fileserver gain jointly to larger writes (6.9% of F2FS write requests are 512 KB versus 0.9% for EXT4) and to discard behavior, without separating the two effects.

Connections

FFS and EXT4: an update-in-place file system frees space block by block as files are deleted, so its discards are naturally small. Hints: discard is literally a hint to a lower layer that it is free to ignore (inference). Exokernel: one of the few channels by which the device learns file system semantics (inference).

L · Stated limitations and future work

What the paper itself says is unfinished or conditional
  • Threaded logging "works well on modern flash devices but may not do so on HDDs", and "incurs undesirable random writes when there are scattered holes" (Sections 1, 2.6).
  • Zones are "expected to be effective for set-associative FTLs"; no other FTL type is claimed (Section 2.4).
  • Multi-head logging: "Rather than presenting extensive evaluation results that span many different workloads, we focus on an experiment that captures the intuitions of our design." Separating cold from hot and warm instead of the default "would look different"; aging should make the benefit "more visible"; "Fully studying these observations is beyond the scope of this paper."
  • Temperature is static; "more sophisticated runtime monitoring approaches can be incorporated in F2FS to fine-track data temperature" (Section 4.1).
  • Background cleaning's benefit is hard to show "because background cleaning is suppressed during busy periods"; one number is given (over 10% at 90% with ten minutes of idle time).
  • "F2FS is fairly young ... We expect new optimizations and features will be continuously added to the file system."
What the evaluation does not cover (this guide's list)
  • Device lifetime, erase counts or device-level write amplification, although lifetime is a stated design goal; the only WAF reported is the file system's, in one experiment with device GC deliberately avoided.
  • Zones and sections larger than the defaults, and any FTL whose type is known: the paper never says what FTL its test devices use or what unit sizes the experiments used.
  • Crash recovery: no test of correctness after power loss, mount time, or roll-forward cost.
  • Checkpoint latency and frequency, and the stall of create, unlink and mkdir during checkpoints.
  • Read performance of aged, fragmented files (threaded logging scatters a file's blocks into holes); only write-heavy aging tests are shown.
  • Separate contributions of each mechanism: the fileserver gain is attributed to request sizes and discards together, the SQLite gain to roll-forward, with no ablation (no F2FS without NAT, without six logs, with checkpoint-per-fsync).
  • Memory use of NAT and SIT caching on large volumes, and CPU cost, which the paper says matters on the server.

C · Connections to the other CS240 papers (mechanical only)

  • LFS (10/27): the base design: log, segments, cleaner, greedy and cost-benefit, checkpoints, roll-forward. F2FS changes the index (NAT), the number of logs, the near-full policy and the scope of roll-forward (S).
  • FFS: the inode shape (direct, single, double, triple) survives in F2FS's node blocks; FFS's 10% reserve is F2FS's 5%; FFS tuned units to disk geometry it could see, F2FS to FTL units it can only configure (M2, M4, M11).
  • Rethink the Sync (10/29): both attack the cost of fsync-heavy applications; Rethink the Sync defers when the caller blocks, F2FS shrinks what each fsync writes to a data block plus a flagged node (M19) (inference).
  • NFS (10/22): an NFS server must commit data and metadata before replying; on F2FS that commit is a data block and a flagged direct node, and file handles carry inode numbers that F2FS translates through the NAT (M7, M19) (inference).
  • Superpages and ESX: allocation units sized to a hardware unit so that freeing a whole unit is cheap (sections and zones, M2); the NAT is a level of indirection that lets an object move while its name stays fixed, like a pmap (M5) (inference).
  • Exokernel (11/10): zones and the multi-stream interface are about the layer above learning or controlling placement that the device hides (M10) (inference).
  • Livelock (10/6): a mode switch under overload, threaded logging instead of cleaning, that trades peak efficiency for bounded cost (M15) (inference).
  • Salus: commit by writing a new version beside the old and switching with one small write (checkpoint packs, M16) (inference).
  • Hints (12/1): static temperature classification is a hint (cheap, wrong only in cost); "log updates", "make actions atomic", "use batch processing" map onto roll-forward, checkpoint packs and NAT journals (M9, M17) (inference).

Worked examples

Seven calculations from the paper's own numbers. Read-offs from plots are approximate; general-knowledge inputs and illustrative assumptions are labeled where they enter.

① How much room did each device leave for a log-structured file system?

Paper, Table 2 (MB/s, single thread, 512 KB sequential and 4 KB random, O_DIRECT): eMMC 114, 72, 12, 12; SATA SSD 486, 471, 40, 140; PCIe SSD 1,295, 922, 41, 254. Figure 3(a): F2FS random write is 3.1× EXT4 on the eMMC.

  1. Sequential-to-random write gap: eMMC 72 / 12 = 6.0×; SATA 471 / 140 = 3.4×; PCIe 922 / 254 = 3.6×. This is the most a file system can gain by turning random writes into sequential ones on that device.
  2. Per-request time at 4 KB (taking MB as 106 bytes): eMMC random write 12,000,000 / 4,096 ≈ 2,930 per second, about 341 µs each. SATA random write ≈ 34,200 per second (29 µs); SATA random read 40 MB/s ≈ 9,770 per second (102 µs).
  3. iozone on the eMMC: if EXT4's random writes ran at the device's random rate, 12 MB/s (an assumption; Figure 3 is normalized and gives no absolute numbers), F2FS's 3.1× is about 37 MB/s, 52% of the 72 MB/s sequential rate.
  4. A mix model of the paper's sentence "turns over 90% of 4KB random writes into 512KB sequential writes": if 90% of the bytes go at 72 MB/s and 10% at 12 MB/s, one MB takes 0.9 / 72 + 0.1 / 12 = 0.0125 + 0.0083 = 0.0208 s, so 48 MB/s, 4.0× EXT4. The measured 3.1× is below that; node writes, checkpoints and CPU time take the rest (inference).
🍯
F2FS's gains track each device's random-write gap: largest on the eMMC (6× room), smaller on SSDs whose controllers already absorb random writes well (3.4 to 3.6× room, and parity on fileserver for the PCIe drive).

② Where do "8MB to 4GB" and "two pointer blocks" come from?

Paper, Section 2.2: appending 4 KB to "a file of 8MB to 4GB", LFS "updates two pointer blocks recursively while F2FS updates only one direct node block"; above 4 GB, LFS updates three. FFS-style geometry (12 direct pointers, 4-byte addresses, 4 KB blocks) and F2FS's 923 and 1,018 are general knowledge.

  1. FFS-style inode (as in Sprite LFS): direct pointers reach 12 × 4 KB = 48 KB. The single indirect block holds 4,096 / 4 = 1,024 addresses: 4 MB more, so up to about 4.05 MB. The double indirect block reaches 1,024 × 1,024 × 4 KB = 4 GB more.
  2. So in LFS an append between about 4.05 MB and 4 GB rewrites the single indirect block and the double indirect block: two pointer blocks. Past 4 GB it adds the triple indirect: three. The paper's counts check; its lower bound of 8 MB is safe but not tight (files from 4.05 MB up also need two).
  3. The same file in F2FS: the inode's 923 direct pointers reach 3.6 MB; its two direct nodes add 2 × 1,018 × 4 KB ≈ 8.0 MB, up to 11.6 MB; the double-indirect chains then reach 2 × 1,018² × 4 KB ≈ 7.9 GB. An append at 100 MB rewrites one direct node; the indirect node above it stores the direct node's ID and does not change.
  4. Everything else that moves (general knowledge, not in the paper's count): the append changes the file size, so the inode is rewritten in both systems, and in LFS the inode map block holding that inode's address too. Totals for one append at 100 MB: LFS 4 index blocks (single, double, inode, inode map); F2FS 2 node blocks (direct node, inode) plus one NAT entry deferred to the checkpoint.
💡
The paper's 1-versus-2 ratio is really 2-versus-4 once the inode is counted, and both shrink with caching. The structural point holds: in F2FS the count stays fixed as the file grows; in LFS it grows with tree depth. F2FS's two direct nodes happen to cover exactly 8 MB (2 × 1,018 × 4 KB), which may be where the paper's "8MB" comes from (inference; the paper does not say).

③ What six logs save the cleaner, from Figure 6

Figure 6 read-offs (approximate, M12 redraw): 2 logs about 7% of dirty segments at 0 valid blocks, 20% by 100, 24% by 140, 40% at about 287; 6 logs about 16% at 0, 30% by 50, 38% by 75, 47% by 100. Scenario (illustrative): greedy cleaning has to reclaim the emptiest 40% of dirty segments, 512 blocks each.

  1. Average valid blocks in those victims (integrating the read-off curves, this guide's arithmetic): 2 logs about 137 of 512, u ≈ 0.27; 6 logs about 25 of 512, u ≈ 0.05.
  2. Copies per block freed = u / (1 − u): 2 logs 0.27 / 0.73 ≈ 0.36; 6 logs 0.05 / 0.95 ≈ 0.05, about 7 times fewer.
  3. Writes per new block on flash, where the SIT bitmap means only valid blocks are read: 1 / (1 − u) = 1.36 versus 1.05. Counting the reads of valid blocks as well: (1 + u) / (1 − u) = 1.74 versus 1.11.
  4. The LFS paper's write cost 2 / (1 − u), which charges for reading the whole victim segment, would give 2.73 versus 2.10. On flash the "2" mostly disappears because dead blocks are never read (LFS guide, write cost).
🍯
Separation at write time moves victims toward u = 0, where any cost formula is near its minimum. The gain from 2 to 6 logs here is in copies (7×), not in total writes (1.36 to 1.05), because even the 2-log victims were fairly empty in this unaged experiment.

④ Figure 7 at 97.5%: what would normal logging have cost?

Paper: 120 GB partition, 5% reserved, then cold 60% and hot 37.5% of the rest; each run writes 20 GB of random 4 KB writes to the hot region; measured WAF about 1.02, performance loss about 30%. Units: GB as in the paper.

  1. Space: usable 120 × 0.95 = 114 GB. Hot data 0.375 × 114 = 42.75 GB; cold 0.60 × 114 = 68.4 GB (never overwritten, so its segments stay full); free 0.025 × 114 = 2.85 GB, plus the 6 GB reserve: 8.85 GB not holding live data.
  2. Average utilization of the space the hot data churns in: 42.75 / (42.75 + 8.85) = 0.83. A cleaner forced to take average victims would write 1 / (1 − 0.83) ≈ 5.8 blocks per new block.
  3. Greedy does better: a standard approximation for greedy cleaning under uniform random overwrites (general knowledge, from the SSD literature) is WAF ≈ (1 + ρ) / (2ρ), with ρ = spare / live = 8.85 / 42.75 = 0.21: (1.21) / (0.41) ≈ 2.9.
  4. Measured: 1.02. The difference is threaded logging: once clean sections run out, data goes into holes and is never copied; the remaining 2% is cleaning for node blocks ("cleaning is needed not for data, but for recording nodes").
  5. Where the 30% went: the paper attributes the degradation to "the amount of GC" increasing. The copies alone are 2% extra writes and cannot cost 30%; the rest presumably comes from what cleaning does besides writing (reading victims, the checkpoints foreground cleaning triggers) and from the random writes of threaded logging. Note that even run 1 at 97.5% is already at about 0.71 (inference; the paper gives no breakdown).
💡
Normal logging at this utilization would plausibly write 3 to 6 times the user data (this guide's estimate); threaded logging writes 1.02 times. That is the paper's case for giving up sequential writes near full, stated in numbers it does not compute.

⑥ Discards: how many commands to free 1 GB?

Paper: F2FS discards "in the unit of segments only when checkpointing is triggered"; for EXT4 "nearly 60% of all discard commands were for an address space smaller than 256KB". Segment = 2 MB. The EXT4 size mix below is illustrative.

  1. F2FS: 1 GB / 2 MB = 512 commands at most (fewer if adjacent free segments are merged into one range, which the paper does not say).
  2. A command stream like EXT4's (illustrative): 60% of commands at 128 KB and 40% at 1 MB average (0.6 × 128 + 0.4 × 1,024) ≈ 486 KB per command, so 1,048,576 / 486 ≈ 2,160 commands, 4.2× as many.
  3. If every command were under 256 KB: at least 1,048,576 / 256 = 4,096 commands, 8× as many.

A 4 KB block at offset 50 MB of a 1 GB file is overwritten and later written back. Which Main-area blocks are written, and which tables change? Does the indirect node above the block's direct node change?

At mount, checkpoint slot 0 holds header 88 and footer 88; slot 1 holds header 89 and footer 87. Which pack is used? What if slot 1 held 89 and 89?

Problem 6 · medium

Connecting outward

What F2FS teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

Two garbage collectors stacked on each other

F2FS is a log with a cleaner, running on an FTL that is also a log with a cleaner. Each layer's write amplification multiplies the other's, and the upper layer can only influence the lower one indirectly: by aligning its units (sections, zones), by keeping lifetimes apart in time and address, and by telling it what died (whole-segment discards). The paper measures the upper collector's WAF and deliberately avoids the lower one's. Any tiered memory or storage design with remapping at two levels (a host-managed log on a device-managed translation layer, or OS page placement over a memory controller that remaps) faces the same question of which layer should own placement and how much the other must be told.

Indirect by name everywhere except the last hop

The NAT turns every node pointer into a name, so moving a node changes one table entry instead of a chain of parents. It stops at direct nodes: data addresses stay physical, because a table entry per 4 KB data block would duplicate the device's own page map. That is the general rule for indirection tables in memory systems too: add a level of naming where objects move often and are few (nodes, pages of a guest), keep physical pointers where objects are many and the extra table would cost as much as what it saves.

Static classification at allocation time is cheap, and wrong in predictable ways

Six logs sorted by block type, file extension and whether the cleaner moved the block cost no tracking state at all, and Figure 6 shows they are enough to make segments bimodal. They fail exactly when type does not predict lifetime: a database file is "warm" however hot it is, an edited photo is "cold" however often it changes. Memory tiering faces the identical choice between placing by allocation site or type (free, sometimes wrong) and by measured access counts (accurate, costs sampling and metadata), and the usual answer is the same as F2FS's: start static, correct with a second pass (here, the cost-benefit cleaner moving survivors to the cold log).

Design the near-full case as a separate mode

Append-only logging is excellent while free space lasts and collapses as it runs out (F2FS normal falls below 5% of EXT4 on a full device). F2FS does not try to make the log cheaper near full; it switches policy, filling holes in place and accepting random writes, and keeps write amplification near 1.02 at 97.5% utilization. Utilization cliffs appear in every out-of-place system: SSD over-provisioning, copying garbage collectors, compaction in log-structured stores. A threshold-triggered fallback with bounded cost is often better than a cleverer version of the primary policy.

The price of durability is the size of the commit record

An fsync in F2FS writes the data and one flagged direct node; that flag is the entire commit record, and recovery reconstructs everything else (NAT, SIT, SSA) from it. The 46% reduction in SQLite writes and the 2× transaction rate come from shrinking that record, not from faster media. For persistent-memory and NVM work the lesson transfers directly: decide what minimal state makes an update findable after a crash, write only that synchronously, and rebuild derived indexes lazily or at recovery.

A stated goal that was never measured

The paper names device lifetime as a design goal from the first page, yet reports no erase counts, no device-level write amplification, and no wear figures; the one WAF it shows is the file system's, with device GC deliberately prevented. The performance results are solid; the lifetime claim rests on the argument that sequential, sorted writes make device GC cheaper. When an evaluation omits the metric a design is named for, the reader should treat that benefit as a hypothesis, which is how a memory-device researcher would treat an endurance claim without cycling data.

Questions with real answers

Each one is a tricky case the paper does not spell out, but it has a definite answer you can work through from the paper's numbers, its mechanisms, or labeled general knowledge of the Linux implementation. C1 · Is an append really "only one direct node block"?

The paper says that appending 4KB to a file of 8MB to 4GB makes LFS update two pointer blocks while F2FS "updates only one direct node block". But an append changes the file size, the size lives in the inode, and the inode is itself a node block found through the NAT. Counting every index block that must eventually be written, what is the real comparison for one 4 KB append to a 100 MB file? And when does F2FS have to write a third node block?

AnswerWork it out first, then open▾

F2FS writes the data block, the direct node (new address in one slot) and the inode (new size and modification time): two node blocks, each at a new address, so two NAT entries change in memory. LFS with an FFS-style inode writes the data, the single and double indirect blocks, the inode, and the inode map block that records the inode's new address: four index blocks. The real ratio is 2 to 4, not 1 to 2; the paper's count leaves out the inode in both systems and LFS's inode map.

A third F2FS node is written every time the append crosses into a new direct node, once per 1,018 blocks (about 4 MB, general knowledge count): the new direct node's ID must be stored in its parent, an indirect node (cold node log) or, for the first two, the inode. With caching, many appends share one write of each dirty block per writeback, which is what the paper's "not considering cache effects" sets aside.

Where the answer comes from: Section 2.2's count and its list of inode contents (file size); the inode map moving in LFS is from the LFS paper; 1,018 entries per node is general knowledge from the Linux source.

C2 · Can 3,691 bytes of inline data and 200 bytes of inline xattrs share one inode?

Section 2.2 says F2FS inlines data "if a file size is smaller than 3,692 bytes" and "reserves 200 bytes in an inode block for storing extended attributes", and Figure 2 puts inline data in the region labeled "direct pointers or inline data". If the inode has 923 four-byte direct pointers, can a file have both a 3,691-byte inline body and 200 bytes of inline attributes? If not, what is the real inline limit when inline attributes are in use?

AnswerWork it out first, then open▾

No. 923 × 4 = 3,692 bytes is exactly the whole pointer area. The rest of the 4 KB inode is already spoken for: about 360 bytes of header (including the 255-byte name), 20 bytes for the five node IDs and a 24-byte footer, which with 3,692 sums to 4,096 (general knowledge layout). There is no separate 200-byte region, so the attributes must come out of the pointer area: 50 slots.

With inline attributes on, inline data is at most 3,692 − 200 = 3,492 bytes, and the implementation reserves one more slot, giving 3,488 (general knowledge). The same file has 873 usable direct pointers, not 923, if it is not inline. The paper's two numbers are each a maximum on its own, not simultaneous limits.

Where the answer comes from: Arithmetic on the paper's 3,692 and 200; the 923-pointer count and the inode layout are general knowledge from the Linux F2FS source.

C3 · How does roll-forward find its nodes, and where does the chain end?

After an fsync, the on-disk NAT still points to the old copy of the file's direct node; the new copy is somewhere after the checkpoint's log position N. Recovery "collects the direct node blocks having the special flag located in N+n". How does it find those blocks without the NAT and without scanning the whole Main area? And if the log head wrapped into a segment that was freed and reused, an old flagged node from before the checkpoint may sit right after the last new one. How does recovery know where the post-checkpoint part ends?

AnswerWork it out first, then open▾

The checkpoint pack records the active segments ("summary entries of currently active segments"; in the implementation also each log's current segment and block offset). Direct nodes of regular files go to the warm node log, so recovery starts at that log's position as of the checkpoint. Each node block's footer holds the address of the next block that log will write (allocated in advance), so recovery follows a chain from block to block, across segment boundaries, reading only blocks written since the checkpoint.

Each node footer also holds the checkpoint version it was written under. Recovery stops at the first block whose version is not the current pack's, which rejects stale flagged nodes and garbage alike. For the chain to exist, the warm node log must append rather than fill holes, and in the implementation of that era it always does (general knowledge).

Where the answer comes from: Section 2.7.2 for the flag and N+n; the next-block pointer, the checkpoint version in each node footer and the append-only warm node log are general knowledge of the Linux implementation.

C4 · Can threaded logging reuse a hole created a second ago?

Cleaned sections stay pre-free until a checkpoint, "because if a pre-free section is reused before checkpointing, the file system may lose the data referenced by a previous checkpoint". Threaded logging reuses individual holes in dirty segments. Suppose a data block was valid at checkpoint v20 and was overwritten (so invalidated) a second ago. May threaded logging put a new block into that hole before v21? What must the SIT record for threaded logging to be safe?

AnswerWork it out first, then open▾

No. v20's NAT and direct nodes still point at that block. If a new block of another file is written there and power fails before v21, roll-back returns to v20 and the first file reads the second file's data: the pre-free failure at block granularity.

A hole is reusable only if it is invalid both now and as of the last checkpoint. The implementation keeps two bitmaps per segment, current validity and validity at the last checkpoint, and threaded logging skips any block set in either (general knowledge). So holes created since the last checkpoint become usable only after the next one; threaded logging, like cleaning, depends on checkpoints to recycle space. The paper does not mention this.

Where the answer comes from: The rule from Section 2.5 applied to single blocks; the second bitmap is general knowledge of the implementation.

C5 · If data is written "in place", what is the cleaner still cleaning?

In the Figure 7 experiment, after the third run at 80% utilization "nearly all data were written via threaded logging, in place. In this case, cleaning is needed not for data, but for recording nodes." At 97.5% the WAF is still about 1.02. If data is written in place, why does any node block need cleaning, and what are the extra 2% of writes?

AnswerWork it out first, then open▾

"In place" means into holes of already-used segments, not at the block's old address: the new version of a block is written before the old one is invalid, and a just-invalidated block cannot be reused before a checkpoint anyway. So every overwrite gives the data block a new address, the slot in its direct node changes, and the direct node is rewritten.

Node blocks are appended to node logs (the warm node log always appends in the implementation, general knowledge), and each rewrite leaves an invalid old copy in a node segment. Node segments therefore fill with holes and must be cleaned to give the node logs clean segments. The roughly 2% of extra writes are mostly the valid node blocks copied by that cleaning (inference; the paper does not break the WAF down).

Where the answer comes from: Section 3.2.4's statement plus the mechanism of M5 (direct nodes store physical data addresses); the append-only node log is general knowledge.

C6 · Does fsync on a newly created file survive a crash?

The roll-forward path writes "data blocks and their direct node blocks only, excluding other node or F2FS metadata blocks." An app creates /data/new.db, writes it and calls fsync, which returns; power fails before the next checkpoint. The new name lives in a dentry block of /data, which this path does not write. After recovery, can the app open /data/new.db? What must F2FS do for that fsync to be honest?

AnswerWork it out first, then open▾

With the paper's path alone, no. Roll-back returns to a checkpoint in which /data has no such entry. Roll-forward replays the file's flagged inode, but no directory names it, so the file is unreachable and its blocks are lost to the namespace.

The paper's list of inode contents includes the "file name". The implementation stores the name and the parent's inode number in the inode and, for a file whose entry is not yet in a checkpoint, marks the fsynced inode so that roll-forward re-inserts the directory entry (general knowledge). Where that is not enough (the parent itself is new, the file has several links, or was renamed), fsync falls back to a full checkpoint (general knowledge; the exact conditions vary by kernel version). Strict POSIX also expects an fsync of the directory to make a new name durable (general knowledge).

Where the answer comes from: Section 2.7.2 defines the path; Section 2.2 lists the file name among the inode's contents; the dentry mark and the checkpoint fallback are general knowledge of the implementation.

C7 · Do Figure 8(a)'s numbers support the text?

Section 3.2.5 says that between the first and second fileserver rounds EXT4 dropped 17%, "BTRFS and F2FS (especially F2FS normal) saw a severe performance drop of 22% and 48% each", and F2FS adaptive limited its drop to 22%, "comparable to BTRFS". Reading Figure 8(a), do the percentages hold? Is adaptive's advantage over normal what the text implies, and does F2FS keep "two or more" over EXT4?

AnswerWork it out first, then open▾

Read-offs (approximate), runs 1 → 2: EXT4 1.00 → 0.83 (17%), adaptive 2.17 → 1.72 (21%), normal 2.19 → 1.27 (42%), BTRFS 1.00 → 0.53 (47%). EXT4 and adaptive match the text; BTRFS has the largest drop, about 47%, not 22%, and normal's is about 42%, not 48%. The two numbers look misassigned, and "comparable to BTRFS" does not hold.

Adaptive halves normal's loss. Adaptive over EXT4 is 2.17, 2.07, 2.02 and 2.12 across the runs, so "two or more" holds; normal is only 1.53 in run 2. Normal writes 27% more data, and 1 / 1.27 = 0.79 is close to normal's 1.27 / 1.72 = 0.74 of adaptive's throughput, so the extra cleaning writes explain most of the gap (inference).

Where the answer comes from: Figure 8(a) read-offs and the Section 3.2.5 text; the ratios are this guide's arithmetic.

Glossary, results, and provenance

Every term in one place, then where the numbers came from, what this guide found inconsistent in the paper, and corrections to the companion outline.

Core terms
F2FS (Flash-Friendly File System)A Linux log-structured file system for flash devices that have an FTL: fixed metadata tables at the front of the volume and six append logs in the Main area, merged into Linux 3.8.
Main areaThe part of the volume after the metadata areas, made of 4 KB blocks each typed as a node block or a data block, and written as logs.
SegmentA fixed-size, aligned group of 512 consecutive 4 KB blocks (2 MB) in the Main area: the unit in which a log takes new space and the SIT keeps statistics.
SectionA configurable number of consecutive segments that the cleaner treats as one victim and frees as a whole; the free-section count drives cleaning and the logging switch.
ZoneA configurable number of consecutive sections; F2FS gives concurrently active logs segments from different zones so their addresses fall into different FTL groups.
Node blockA 4 KB Main-area block holding index information rather than file contents (an inode, a direct node or an indirect node), identified by a node ID that does not change when the block moves.
Node IDThe fixed number naming one node block, used as the index into the NAT; an inode's node ID is its inode number.
Inode blockThe node block for one file: its metadata (including the file name and size), 923 direct pointers or inline data, inline extended attributes, and five node IDs (two single-, two double-, one triple-indirect).
Direct nodeA node block whose entries are physical addresses of data blocks (1,018 per block in the implementation).
Indirect nodeA node block whose entries are node IDs of other node blocks, so it does not change when those nodes move.
NAT (node address table)A fixed-location table indexed by node ID whose entries hold each node block's current physical address; kept in two sets and cached in memory.
SIT (segment information table)A fixed-location table with one entry per segment: number of valid blocks, a 512-bit validity bitmap, and last modification time; kept in two sets.
SSA (segment summary area)A fixed-location area with one summary entry per Main-area block naming its owner (parent node and offset), the reverse map the cleaner uses to update parents.
Checkpoint (CP) areaTwo segments at the start of the volume holding two checkpoint packs, written alternately.
Checkpoint packA record of one consistent file system state: header and footer with the same version number, NAT and SIT set bitmaps, NAT and SIT journals, active-segment summaries and orphan inode blocks.
NAT and SIT sets, set bitmapsTwo copies of every NAT and SIT block; a bit per block in the checkpoint pack says which copy is current, so new versions are written into the copy the stable pack does not use.
NAT and SIT journalsSmall arrays of recently changed NAT and SIT entries stored inside the checkpoint pack, so a few changes need no table-block writes.
Active log (logging head)One of the segments currently being appended to; F2FS keeps six by default, one per node or data temperature.
Hot, warm, coldF2FS's three temperature labels, static predictions of how soon a block will be overwritten, fixed by block type, file extension, a user attribute, or whether the cleaner moved the block.
Multi-head loggingWriting to several active logs at once (6, 4 or 2, chosen at mount), each receiving one class of blocks.
Normal loggingThe allocation mode that appends new blocks to clean segments, producing strictly sequential writes.
Threaded logging (SSR)The allocation mode that writes new blocks into invalid slots of dirty segments, filling one segment's holes before the next; called slack space recycling in the implementation.
Adaptive loggingF2FS's rule for choosing between the two: normal logging while there are more than k clean sections (k = 5% of sections by default), threaded logging otherwise.
Cleaning (foreground, background)The file system's garbage collection of sections: foreground cleaning runs in the writer's context when free sections run short; background cleaning runs in a periodically woken kernel thread when the system is otherwise idle.
Victim sectionThe section chosen for cleaning, whose valid blocks are moved so the whole section can be freed.
Greedy policyA victim rule that picks the section with the fewest valid blocks; F2FS uses it in the foreground.
Cost-benefit policyA victim rule that weighs free space gained against copying cost and age (LFS's (1 − u) × age / (1 + u)); F2FS uses it in the background, with age from SIT modification times.
Lazy migrationBackground cleaning's way of moving a block: read it into the page cache and mark it dirty, leaving the write to normal writeback.
Pre-free sectionA cleaned section with no valid blocks that cannot be reused until the next checkpoint, because the last checkpoint may still point into it.
Orphan inodeAn inode whose last name was removed while a process still had it open; listed in the checkpoint pack so its blocks can be freed after a crash.
Roll-back recoveryMounting from the newest valid checkpoint pack, discarding all changes made after it.
Roll-forward recoveryAfter roll-back, finding direct node blocks written with the fsync flag since the checkpoint and merging their data addresses into the checkpointed nodes, then writing a new checkpoint.
fsync flagA mark inside a direct node block written by fsync that lets roll-forward recognize it; the only commit record of an fsync.
Inline data, inline xattrsSmall file contents (under 3,692 bytes) or extended attributes (up to 200 bytes) stored inside the inode block itself instead of separate blocks.
Dentry blockA 4 KB directory data block: a validity bitmap, an array of slots (hash, inode number, name length, type) and an array of names.
Multi-level hash directoryF2FS's directory organization: hash tables at increasing levels with more buckets per level, each bucket 2 or 4 dentry blocks; a lookup reads one bucket per level.
Wandering treeThe cascade in a log-structured file system where moving a block changes its parent's pointer, which moves the parent, and so on up to the root.
Supporting terms
NAND pageThe unit a NAND chip reads and programs, typically 4 to 16 KB; it cannot be reprogrammed until its block is erased.
Erase blockThe unit a NAND chip erases, typically 64 to 512 pages, whose pages must then be programmed in order.
Program/erase (P/E) cycleOne erase of a block and the programming that follows; each block survives a limited number, which sets the device's lifetime.
FTL (flash translation layer)Firmware on the device's controller that maps logical block addresses to flash pages, writes every update out of place, and garbage-collects, presenting a normal block device.
Page mapping, block mappingFTL map granularities: one entry per page (any page anywhere, large table) or one per erase block (fixed page offsets, tiny table, copying on update).
Hybrid (log-block) mappingAn FTL design with block-mapped data flash blocks plus a few page-mapped log flash blocks that absorb updates and are later merged back by copying.
Block-, set-, fully-associative FTLThe paper's classes of hybrid FTL by which data flash blocks may share a log flash block: one, a contiguous group, or all.
Device garbage collectionThe FTL's reclamation: copy a victim erase block's valid pages elsewhere and erase it.
Write amplification factor (WAF)The ratio of bytes actually written by a layer to bytes asked of it; 1.0 means no extra writes.
Over-provisioningCapacity held back from the user so the cleaner or GC always has room; F2FS reserves 5%.
Discard (TRIM, UNMAP)A command telling the device that a logical range holds no valid data, so its GC need not copy it.
Multi-stream SSDA device interface where each write carries a stream ID and the device keeps streams in separate flash blocks.
Channels, dies, planesThe levels of parallel hardware inside a flash device; a large write is striped across them, a single small write occupies one.
eMMC, UFSSoldered flash packages with an on-board controller and FTL, used in phones; the paper's phone uses a 16 GB eMMC.
SATA SSD, PCIe (NVMe) SSDFlash drives attached through the older SATA disk interface or directly over PCI Express with the NVMe command set, which queues commands much more deeply.
LBA (logical block address)The number of a sector on the block interface; Figure 5 plots LBAs of each request over time.
O_DIRECTA Linux open flag that sends reads and writes straight to the device, bypassing the page cache; used for the Table 2 measurements.
Page cache, writebackKernel memory caching file pages; dirty pages are written to the device later by a worker thread unless fsync forces them.
SQLite WAL modeA SQLite journal mode in which each commit appends changed pages to a separate write-ahead log file and fsyncs it.
iozone, mobibench, FilebenchBenchmarks: a file I/O microbenchmark, a mobile benchmark that drives SQLite, and a configurable workload generator with predefined personalities (videoserver, fileserver, varmail, oltp).
EXT4The default Linux file system: update in place, block groups with bitmaps, and a journal for metadata.
BTRFSA Linux copy-on-write file system keeping all metadata in B-trees, rewriting the path to the root on every update.
NILFS2A Linux log-structured file system that writes all changes sequentially in segments and keeps continuous snapshots.
Hole pluggingMoving a victim segment's valid blocks into invalid slots of other segments instead of to the log head (Wilkes et al.).
