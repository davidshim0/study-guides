SOSP 2026 · A Field Guide

Same code path, different guts — teaching a fuzzer to notice

Two runs of a JS engine can trace the exact same control-flow edges and still differ in the one internal condition that turns a benign access into a type-confusion bug. This is the plain-English story of StateLens, which uses an LLM to find those conditions and wire them into the fuzzer's feedback.

📄 "State-Aware Fuzzing of JS Engines with LLM-Guided Instrumentation" · Wong, Xiao, Lai, Ke, Wang 🎓 Fuzzing/compilers basics assumed — primers cover the rest ⏱ ~30 min read
🔍

When edges stop telling you anything new, watch the internal states instead of the edges — and let an LLM read the developers' own comments to find which states matter.

Before you begin

Quick glossary, then six ideas the paper assumes

Acronyms first — you'll see all of these within the first page of the paper. Then six collapsible primers on the background concepts. Skip anything you already know.

Quick glossary — acronyms up front
JSJavaScript — the scripting language; the engines (V8, SpiderMonkey, etc.) execute it.
JITJust-In-Time compiler — compiles hot JS functions to native code at runtime, in multiple optimization "tiers."
ICInline Cache — a per-callsite cache that remembers how to access a property quickly next time, so the engine skips a full lookup.
GCGarbage Collector — reclaims and sometimes relocates heap objects the engine no longer needs.
ASTAbstract Syntax Tree — the parsed, tree-shaped representation of source code that analysis tools traverse.
KBKnowledge Base — StateLens's vector-indexed store of bug reports, comments, and design docs.
LLMLarge Language Model — here, the offline reasoner (GPT-5.1) that mines developer artifacts for candidate states.
PoC / CVEProof of Concept (a minimal triggering input) / Common Vulnerabilities and Exposures (a public bug identifier).
RCERemote Code Execution — the worst-case outcome of some memory-safety bugs.
ASanAddressSanitizer — a compile-time instrumentation that turns memory-safety violations into immediate, precise crashes.
v8CTFGoogle's public bug bounty tracker for V8, used here as a corpus of 35 real vulnerabilities to study.
CTFCapture-The-Flag — a security competition format; several StateLens-found bugs were later reused as CTF challenges.
1Coverage-guided fuzzing, in one paragraph▾

A fuzzer generates or mutates inputs, runs them against an instrumented target, and checks a feedback signal — classically, edge coverage: a bitmap of which control-flow edges (branches taken) were exercised. If an input hits an edge never seen before, it's kept and mutated further; if not, it's usually discarded. This loop is how tools like AFL and, for JS specifically, Fuzzilli explore huge input spaces without any model of "correct" behavior.

Now you're ready: StateLens keeps this exact loop — it just adds a second bitmap alongside the edge one.
2JIT tiers and why the same function runs different code▾

JS engines don't compile everything eagerly. A function starts in an interpreter; if it runs often, a baseline JIT compiles it; if it's still hot, an optimizing JIT (V8's TurboFan, e.g.) recompiles it with aggressive, type-specialized assumptions. If those assumptions are later violated, the engine deoptimizes back to a slower tier. Which tier is active is invisible to line/edge coverage — the same source line executes under interpreter, baseline, or optimized code.

Now you're ready: "JIT optimization tier" is one of the running examples of a state edge coverage can't see (Abstract, §1).
3Hidden classes, Maps, and Inline Caches▾

Because JS objects can gain/lose properties dynamically, engines like V8 group objects with the same property layout under a shared descriptor — V8 calls it a Map (also "hidden class" or "shape" elsewhere). A property access at some callsite installs an Inline Cache (IC): "last time, objects with Map X used this fast handler." Next time, the engine just checks the object's current Map against X — if it matches, it reuses the cached handler instead of a full lookup.

Now you're ready: the paper's central case study, CVE-2022-1134, is exactly an IC handler built under one Map and executed against a different, incompatible object.
4What "internal state" means here — precisely▾

The paper defines a state formally: a side-effect-free expression over runtime values (a variable, or a pure query function). A state transition is the pair of that expression's value just before and just after some operation. "State coverage" means: has this fuzzer ever seen this particular (pre, post) value pair at this site before? Two executions can share every control-flow edge yet still differ in state, because state coverage looks at values, not just which code ran.

Now you're ready: the entire framework exists to find good expressions to instrument as states, and wire their transitions into a second coverage bitmap.
5LLM agents with tools and retrieval, briefly▾

An "LLM agent" here is a loop: the model issues a natural-language query against a retrieval index (the KB), inspects what comes back, decides whether it's actually relevant (self-reflection), and can also call structured code-analysis tools (call-graph lookup, def-use tracking, AST pattern matching) rather than reason over raw source text alone. This keeps the model grounded in the actual codebase instead of hallucinating function names or call relationships.

Now you're ready: StateLens's Phase 1–2 pipeline is exactly this loop, repeated until it has traced a bug-relevant condition across function boundaries.
6Shared-memory bitmaps as fuzzer feedback▾

Classic AFL-style fuzzers instrument the target so that each executed edge flips a bit in a memory region shared (via mmap/POSIX shared memory) between the target process and the fuzzer process. After each run, the fuzzer just reads that region — no serialization, no IPC round-trip per bit. It's cheap, and it's the reason coverage-guided fuzzing can run millions of executions per hour.

Now you're ready: StateLens adds a second such bitmap (plus a small array of "best value seen" slots for integer states) written by the new state probes, read by the same fuzzer loop.
The whole story in one place

StateLens in a nutshell

The plateau, the fix, and why an LLM is the right tool for finding what to instrument.

State-of-the-art JS engine fuzzers guide input generation with edge coverage: keep an input if it exercises a control-flow edge never seen before. This works well early on, but production engines like V8 have millions of lines of code, and the same edges get re-executed under wildly different internal conditions — different JIT tiers, different object layouts, different heap pressure. Once the edge bitmap saturates, the fuzzer is blind to everything that still varies.

StateLens adds a second feedback signal, state coverage, that tracks the actual runtime values behind those conditions rather than which code ran. The hard part is deciding what to track: the internal state space is far too large to instrument exhaustively, and instrumenting the wrong variables just adds overhead with no signal. StateLens's answer is to mine the knowledge developers already left behind — 33,000+ debug assertions and 772 enum classes in V8 alone — using an LLM agent that iteratively queries a knowledge base of bug reports, comments, and design docs, traces the flagged condition across function boundaries with call-graph and data-flow tools, and synthesizes a small, targeted probe once it has isolated a genuine cross-component state transition.

Those probes write into a shared-memory bitmap alongside the existing edge-coverage bitmap. A dual-feedback fuzzer runs two engine instances — a cheap edge-only one for early exploration, and a state-augmented one it switches to once edge coverage plateaus for 100 consecutive iterations — so the extra instrumentation cost is only paid once it's actually useful.

The payoff: across six production engines (V8, SpiderMonkey, JavaScriptCore, QuickJS, Hermes, Escargot), StateLens found 68 new bugs in a three-month campaign (≥35 with security impact), and in a controlled 72-hour comparison found 39 unique bugs versus the best baseline's 23 — a 70% improvement — while adding only 5.5% runtime overhead and 23% memory overhead.

🍯 Key takeaways

  • Edge coverage answers "which code ran"; state coverage answers "under what runtime values." The paper's bug study found bug-relevant conditions cross function boundaries in 31/35 cases (88.6%) and involve a side-effect/transition invalidating an assumption in 12/35 (34.3%).
  • StateLens mines semantic beacons — developer artifacts hinting at fragile states — instead of requiring manual annotation (as IJON does) or settling for call-stack shape alone (as SDFuzz does).
  • The pipeline is three offline LLM-guided phases (beacon extraction → iterative state discovery → transition prioritization/probe synthesis) feeding one online mechanism (dual-feedback fuzzing).
  • Probes are read-only with respect to engine state — they only write to a separate shared-memory bitmap, so they can't introduce new bugs of their own.
  • Result: 68 bugs / 6 engines, 70% more bugs than the best baseline in a controlled 72h run, at 5.5% runtime and 23% memory overhead.
Six everyday pictures

How to think about StateLens

Each card stands alone — read in any order. Every one ends with where the picture stops being true.

The core idea · Structural vs. semantic

Two identical doorways, different rooms

Two doorways look exactly alike from outside — same frame, same hinge. But one leads to an empty room and the other to a room with a live wire. Walking through either doorway is the same "edge" to a coverage counter; only stepping inside (the internal state) reveals the danger. Edge coverage records that you used the doorway; state coverage records what you found in the room.

Where it breaks: a real room's danger doesn't depend on a specific side-effect-free predicate the way engine states do — StateLens needs the predicate to be pure (no side effects) to safely probe it.
Semantic beacons · O3

Margin notes in an old textbook

A well-annotated used textbook has margin notes — "watch out, this step is easy to get wrong" — written by someone who already struggled through it. Developers leave the same kind of notes in code: assertions, enum names, bug-report post-mortems. StateLens's LLM agent reads those margin notes (V8 alone has 33,000+ assertions and 772 enum classes) to find which "steps" are fragile, instead of re-deriving fragility from scratch by reading every line.

Where it breaks: margin notes can be stale or wrong for the current version of the code — that's exactly why self-reflection filtering exists, to reject a beacon whose retrieved snippet uses the right words for the wrong entity.
Interprocedural tracing · O1

Chasing a rumor through a company

A rumor starts in HR, gets slightly distorted in Engineering, and causes a bad decision in Sales — nobody in Sales knows it originated in HR. In 88.6% of the real V8 bugs studied, the dangerous condition was established in one function and consumed, unchecked, in another. StateLens's call-graph and data-flow tools chase the rumor across department (function) boundaries, the way an investigator would interview each link in the chain rather than stopping at the first office.

Where it breaks: a real rumor chase has no step limit; StateLens caps traversal at 25 tool-using steps per beacon to bound analysis cost, so very long or obscure chains may be missed.
The bug pattern · Two guards, one gap

Two different bouncers checking two different IDs

A club has two doors run by two bouncers who never compare notes. The front-door bouncer checks the ID of whoever's expected; the side-door bouncer lets in whoever's actually there, no ID check, trusting the front door already vetted them. CVE-2022-1134 is exactly this: handler construction checks the lookup-start object's Map; handler execution runs on the real receiver without re-checking its Map. When those two people differ, the gap opens.

Where it breaks: a bouncer's mistake is usually a single missed check; here the "mistake" is an architectural split (construction phase vs. execution phase) that's reasonable in isolation — the danger only appears in the interaction, which is why it needed a cross-phase probe to expose.
Probe density · Quality over quantity

Fewer, sharper trip-wires beat a thousand loose ones

A security patrol with 1,000 low-quality motion sensors scattered randomly triggers constantly on nothing and gets ignored; 20 sensors placed exactly at the two windows a burglar actually uses catch the real event. StateLens's ablation shows this directly: cutting probes to 10% of the full set drops bugs found by 42% overall, even though edge coverage barely moves — the probes that go missing are disproportionately the ones sitting exactly at a real transition.

Where it breaks: unlike a security patrol, StateLens doesn't yet rank probes by expected value before pruning — the ablation removes them at random, so the "sharper" framing describes the aggregate effect, not a per-probe guarantee.
Dual feedback · Switching lenses

A cheap lens for scanning, a sharp lens once you've spotted something

A birdwatcher scans a whole field with cheap binoculars — fast, wide, good enough while everything is new. Once the same three trees stop producing new birds, they switch to an expensive spotting scope trained on those trees specifically. StateLens runs a cheap edge-only engine instance while coverage is still growing, and switches to the pricier state-augmented instance only after 100 consecutive iterations add no new edge — paying for the sharp lens exactly when the cheap one has stopped helping.

Where it breaks: the birdwatcher can un-switch back to the wide view at will; StateLens's 100-iteration threshold is a fixed global policy in the paper's implementation, not a continuously re-evaluated one.
The full explanation

How it actually works

Phase by phase, following the paper's own running example, CVE-2024-5830.

1 · Defining the target — states and transitions

StateLens defines a state as a side-effect-free expression over runtime values — a variable or a pure observation function. For an operation with a pre- and post-program point, the pair of state values at those two points is a state transition. State coverage is simply the set of previously unseen states or transitions recorded in a semantic bitmap. This framing is deliberately narrow: it must be cheap to evaluate and safe to insert anywhere, which rules out anything with side effects.

2 · Phase 1 — semantic beacon extraction

Running example, CVE-2024-5830: Map::PrepareForDataProperty calls Map::Update and then asserts the result is still fast-mode (DCHECK(!map->is_dictionary_map())). A historical, already-fixed bug report shows Update can in fact return a dictionary map when a hidden-class transition table is exhausted — that's the beacon. The agent queries the KB for "Map::Update map storage mode transition," gets back three candidates, and self-reflects: only the snippet describing how an outdated map migrates is kept; one about transition-tree context and one about an unrelated ECMAScript collection type are rejected, because keyword overlap alone can't tell V8's internal Map from a JS-visible Map collection.

3 · Phase 2 — iterative state discovery across functions

Seeded from Map::PrepareForDataProperty and Map::Update, the agent expands the call graph in two directions: a migration branch through JSObject::MigrateInstance, and a caller chain FastAssign → CreateDataProperty → TryFastAddDataProperty → PrepareForDataProperty. The two branches meet at Map::Update.

4 · Phase 3 — transition prioritization and probe synthesis

Not every observable expression is worth instrumenting. Guided by observation O2 (side effects and transitions invalidate assumptions), StateLens prioritizes state changes triggered by side effects — here, an accessor inside FastAssign that can deprecate the transition map before CreateDataProperty reuses it, a divergence invisible to edge coverage since both outcomes take the same code path. Of three candidate expressions (stable, is_deprecated(), is_dictionary_map()), the source-map-local stable flag is rejected as not reflecting the target map's property; the other two are kept and packed into one probe:

// before Map::Update
bool deprecated_before = map->is_deprecated();
bool dictionary_before = map->is_dictionary_map();
map = Update(isolate, map);
// pack pre-state into 2 bits, pair with post-state
uint32_t pre_state = (deprecated_before << 1) | dictionary_before;
SEMANTIC_CONTEXT_ENUM(id, pre_state, map->is_dictionary_map());
💡
Why pack pre- and post-state together? The bug isn't "the map is a dictionary map" (that's sometimes fine) — it's specifically the transition from deprecated-fast to dictionary via this call. Hashing pre and post state jointly is what lets the bitmap distinguish that one transition from every other outcome of Map::Update.

5 · Instrumentation and dual-feedback fuzzing

Probes are compiled in, the engine's own test suite is run to catch unintended side effects (e.g., broken reference counting), and an LLM repairs whatever compile or test failures show up. At startup, the engine opens a POSIX shared-memory region keyed to its process ID, containing the bitmap plus a "maximization slot" array for integer-valued states; the fuzzer maps the same region for zero-copy reads after each execution.

Fuzzilli then runs two instrumented instances sharing one seed corpus: an edge-only instance for cheap early exploration, and a state-augmented instance. The fuzzer counts consecutive iterations with no new edge; after 100 such iterations it switches to the state-augmented instance, so the ~5.5% runtime overhead of state probing is paid only once structural exploration has run dry.

Follow the numbers

Worked examples

Four calculations straight from the paper's tables — instrumentation cost, the headline bug-finding gain, the state-coverage multiplier, and the ablation's probe-density arithmetic.

① Pricing one engine's instrumentation

The paper reports an average synthesis cost of $6.45 per engine, broken into four line items. What does that add up from, and why does V8 cost so much more than QuickJS?

  1. Four cost components (average, per engine): LLM calls $3.20 + retrieval $1.50 + re-instrumentation $1.00 + validation-driven repair $0.75 = $6.45.
  2. Token budget behind the LLM-call cost: ~1.02M input + ~0.51M output tokens per engine, averaged across six engines — this is what the $3.20 mostly pays for.
  3. Range across engines: QuickJS is cheapest at $0.28; V8 is most expensive at $13.75 — roughly 49× more, tracking codebase size (V8 is far larger, with the most call-graph edges and assertions to traverse).
  4. Wall-clock: 19–80 minutes end-to-end, average 48 minutes; QuickJS is fastest, V8 slowest, for the same reason.
🍯
Insight: this is a one-time offline cost per engine (and per revision, since the campaign re-instruments on each engine update) — it's not paid per fuzzing run, which is why it doesn't appear in the 5.5% runtime overhead figure.

② The headline number: 70% more bugs

In the controlled 72-hour, 5-run comparison, StateLens found 39 unique bugs versus Fuzzilli's 23 (the best baseline). Where does "70%" come from, and what does "14 exclusive bugs" add?

  1. Relative gain: (39 − 23) / 23 = 16/23 ≈ 0.696 → "70% more", matching the paper's headline exactly.
  2. Not just faster — different: of StateLens's 39 bugs, 14 were found by no baseline at all, meaning they weren't just discovered sooner — several likely require the state-coverage signal to be found at all within 72 hours.
  3. Consistency check against the long campaign: the 3-month, six-engine run found 68 total bugs (25+14+9+7+7+6 = 68 ✓), a larger number than the 72h/single-comparison run because it covers more engines and far more wall-clock time.
💡
These are two different experiments in the paper: the 68-bug figure is an unconstrained, three-month, six-engine campaign (Q1); the 39-vs-23 figure is a tightly controlled, equal-resource, 72-hour, 5-repetition comparison against baselines (Q2). Keep them separate when citing StateLens's numbers.

③ Where "1.72×" state coverage comes from

Table 2 reports per-engine state-coverage multipliers, normalized so Fuzzilli = 1.00×. Verify the paper's claimed 1.72× average by hand.

  1. Per-engine multipliers (StateLens vs. Fuzzilli): V8 2.04×, JSC 2.19×, SpiderMonkey 1.33×, QuickJS 1.30×, Hermes 1.75×, Escargot 1.68×.
  2. Sum: 2.04 + 2.19 + 1.33 + 1.30 + 1.75 + 1.68 = 10.29.
  3. Average over 6 engines: 10.29 / 6 = 1.715 ≈ 1.72× — matches the paper's reported average exactly.
  4. Compare to the weaker baselines' averages: DIE 1.01×, OptFuzz 1.23×, HLPFuzz 1.18× — all clearly below StateLens's 1.72×, while edge coverage stays within about one percentage point across all fuzzers on every engine (Table 2). The separation is entirely in the new signal, not the old one.
🍯
Insight: this is the paper's clearest evidence that state coverage measures something edge coverage doesn't — if it were just "better mutation," edge coverage should have separated the fuzzers too, and it didn't.

④ The ablation's "42% overall reduction"

At 10% probe retention, the paper reports bug counts of 9 (V8, down from 14) and 2 (QuickJS, down from 5), and calls this "a 42% overall reduction." Reconstruct that number.

  1. Full-probe baseline, combined: 14 (V8) + 5 (QuickJS) = 19 bugs.
  2. 10%-probe combined: 9 (V8) + 2 (QuickJS) = 11 bugs.
  3. Overall reduction: (19 − 11) / 19 = 8/19 ≈ 0.421 → 42% — matches the paper's stated figure.
  4. Per-engine checks, at 50% retention: V8 goes 14→10, a (14−10)/14 ≈ 29% drop; QuickJS goes 5→3, a (5−3)/5 = 40% drop — both match the paper's individually stated percentages.
  5. What stays flat: edge coverage on V8 moves by less than 5% across every retention level (15.85% → 15.74%) even as bug count drops by a third — probe removal is invisible to the old signal and visible only in bugs found.
💡
This is the strongest single piece of evidence for why more, better-targeted probes matter: the harm from removing them shows up only in ground-truth bug counts, never in the coverage metric a fuzzer actually watches during the run.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A fuzzer reports 0% new edge coverage for the last hour but StateLens's state bitmap keeps gaining entries. Is the fuzzer stuck?
Show answer
No. Edge coverage saturating just means no new control-flow edges are being reached — it says nothing about whether the values flowing through the already-reached edges are new. New state-bitmap entries mean the fuzzer is still exploring meaningfully different internal configurations along the same code paths, which is precisely the signal edge coverage is blind to.Misconception: that edge-coverage plateau equals "nothing left to find." It equals "structural exploration has plateaued" — a distinct claim from "no more bugs are reachable."
Problem 2 · medium
Why must a state expression be side-effect-free before StateLens will instrument it?
Show answer
The probe's whole safety argument rests on being read-only with respect to engine state — it only writes into a separate shared-memory bitmap. If the expression being observed had a side effect (e.g., allocated memory, mutated a counter, or triggered a callback), inserting the probe would itself change the engine's behavior, potentially masking the very bug it's trying to expose, or introducing a new one. Restricting to pure expressions keeps probes purely observational.Misconception: that any variable read is automatically safe to instrument. A getter or accessor call can have side effects even though it looks like a "read" — the paper explicitly restricts states to variables or side-effect-free observation functions.
Problem 3 · medium
During Phase 1, the agent retrieves three KB snippets for a query about "Map::Update map storage mode transition," but keeps only one. What is self-reflection filtering actually protecting against?
Show answer
Keyword overlap without semantic relevance. A vector-retrieval query can surface snippets that mention the same words ("map," "transition") while describing an unrelated concept (native-context membership, or a JS-visible ECMAScript collection type also called "Map"). Self-reflection prompts the LLM to justify, against the specific target transition, why a candidate should be kept — catching cases where lexical similarity masks semantic irrelevance.Misconception: that retrieval quality alone (a better embedding model) would solve this. Even a perfect retriever returns semantically related-but-wrong results when a term is overloaded; filtering requires reasoning about the specific target, not just similarity scores.
Problem 4 · hard
The ablation shows GPT-5.1 generates fewer probes than GLM 4.7 (1,194 vs. 1,232 on V8) but finds more bugs (14 vs. 12). What does this tell you about what makes a probe set effective?
Show answer
Probe count is a poor proxy for probe quality. The paper's manual inspection found GPT-5.1's probes target specific engine-internal semantics — exact type assumptions at JIT guards, object status at GC safepoints — while GLM 4.7's probes skew toward coarse-grained signals like function entry points, which correlate weakly with actual state transitions. More probes with lower average relevance can underperform fewer, better-targeted ones.Misconception: that instrumentation density is the main lever. The knowledge-base and language-model ablations both show it's the semantic precision of where probes are placed, not how many exist, that drives bug discovery.
Problem 5 · medium
Why does StateLens run two separate engine instances (edge-only and state-augmented) instead of always fuzzing with full state instrumentation on?
Show answer
State probes add real overhead (5.5% runtime, 23% memory in the paper's measurements) for a signal that's only useful once edge coverage has stopped providing dense, cheap feedback. Running the state-augmented instance from the start would pay that cost during early exploration, when edge coverage alone is already finding plenty of new territory. Switching only after 100 stagnant iterations concentrates the expensive signal where it actually helps.Misconception: that "more feedback is always better, so turn it all on." Feedback signals have different costs and different marginal value at different stages of the search — cheap-then-expensive beats expensive-always here.
Problem 6 · hard
StateLens found the QuickJS Worker use-after-free (Listing 9) by probing (a) the property-type transition in JS_DefineProperty and (b) the GC-phase × handler-type pair at finalization. Why are two probes needed instead of one?
Show answer
The bug requires both an unusual setup and an unusual cleanup condition to coincide: (a) redefining onmessage from a data property into a destructive accessor (captured by the property-type-transition probe), and (b) the Worker's finalizer running while its message-handler reference is still live and desynchronized from the runtime's port list (captured by the GC-phase/handler-type probe). Neither condition alone triggers the use-after-free; a single probe on just one of them wouldn't distinguish the buggy combination from countless benign single-condition hits.Misconception: that a single well-placed probe is usually enough. Many of the paper's case studies — including the V8 JIT bug — require the fuzzer to find a novel combination across two separate probes/subsystems before mutation can zero in on the trigger.
Problem 7 · easy
A team wants to apply StateLens to a brand-new, in-house scripting engine with almost no bug-tracker history and few code comments. What should they expect?
Show answer
Reduced effectiveness, by the paper's own ablation logic. The knowledge-base ablation (disabling KB access) already shows probe counts drop 22–34.5% and bugs found drop from 14→10 (V8) and 5→3 (QuickJS) even on mature, well-documented engines. An engine with little bug-tracker history or few comments gives the LLM agent much thinner semantic beacons to work from, so probe quality — and likely bug yield — would degrade further, though the mechanism itself (KB, traversal, probes, dual feedback) still applies.Misconception: that StateLens's gains come purely from "using an LLM," independent of what artifacts are available to mine. The paper's own ablation shows the knowledge base specifically, not just LLM reasoning over source code, is a major contributor.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Is StateLens replacing edge coverage, or adding to it?▾
Adding to it. StateLens keeps the standard edge-coverage bitmap and fuzzing loop (built on Fuzzilli) entirely intact; state coverage is a second, parallel bitmap that becomes the dominant feedback only after edge coverage plateaus (100 consecutive iterations with no new edge). Both signals guide input retention throughout a run.
Q2Why can't a static analyzer find these semantic beacons instead of an LLM?▾
The paper argues the critical context is often in natural-language comments and cross-file bug-report narratives, not machine-readable code structure — e.g., "an outdated map may cache the map objects should migrate to" is a comment, not a type annotation. Traditional static analysis struggles with this mix of informal developer intent and cross-file dependencies; LLMs are used specifically because they can interpret that natural language and connect it to code symbols.
Q3Does the LLM run during fuzzing, slowing down each execution?▾
No. The LLM is used entirely offline, once per engine (and re-run when the engine is updated), to synthesize instrumentation before fuzzing starts. During fuzzing, the LLM is not in the loop at all — the fuzzer just executes the already-instrumented binary and reads a shared-memory bitmap, which is why runtime overhead is only 5.5%, not LLM-inference-scale.
Q4How is this different from IJON or SDFuzz, which also do "state coverage"?▾
IJON requires developers to manually identify and annotate which states to track — it doesn't scale to a codebase the size of a JS engine. SDFuzz represents state using call-stack configurations, which capture calling context but not the actual variable values or object configurations that distinguish, say, a fast-mode object from a dictionary-mode one with the identical call stack. StateLens automates state selection at the semantic level instead of the annotation or call-stack level.
Q5Can a probe itself introduce a bug into the engine?▾
By design, probes are read-only with respect to engine state: they read existing values and write only to a separate shared-memory bitmap that the engine's own logic never consults. Combined with compiling the instrumented engine through its existing test suite (to catch, e.g., incorrect reference-count updates) and LLM-driven repair of anything that fails, this is meant to keep probes from perturbing the behavior they're observing.
Q6Does StateLens generalize beyond the six JS engines it was evaluated on?▾
The authors argue yes — the pipeline operates over generic C++ source and ASTs, not engine-specific structure, and it's already evaluated across engines with quite different codebase sizes and use cases (browser engines V8/SpiderMonkey/JSC, embedded QuickJS/Hermes/Escargot). They also suggest extending the approach to other language virtual machines (WebAssembly runtimes, BPF verifiers, Ethereum VMs) as future work, though that extension isn't evaluated in this paper.
Q7What's the actual overhead cost of running StateLens versus plain Fuzzilli?▾
Measured on V8 over 24 hours: Fuzzilli executed 9.35M test cases versus StateLens's 8.83M — a 5.5% runtime overhead. On QuickJS, mean resident-set-size memory was 23% higher with probes than without, sampled across ten instances after 24 hours of fuzzing.
Q8Are these 68 bugs all independent, or could some be duplicates?▾
The paper reports they represent independent root causes — upstream maintainers tracked and patched each in a separate ticket with a distinct fix, spanning graph construction, IR lowering, register allocation, deoptimization dispatch, and JIT-constant/GC interactions. For the 72-hour baseline comparison specifically, the authors additionally deduplicated crashes via manual root-cause analysis before counting "unique bugs."
Q9Why does OptFuzz have "N/A" for QuickJS, Hermes, and Escargot in the coverage table?▾
OptFuzz is specifically a JIT-optimization-path-guided fuzzer, so it's only meaningful (and only evaluated) on the three engines with JIT compilers in this comparison — V8, JavaScriptCore, and SpiderMonkey. QuickJS, Hermes, and Escargot are interpreter-focused or have different compilation strategies that OptFuzz's approach doesn't target.
Q10What do the authors flag as future work?▾
Two directions stand out in the paper: extending state-sensitive feedback to other language virtual machines beyond JS engines (WebAssembly runtimes, BPF verifiers, Ethereum VMs), and combining StateLens's offline instrumentation approach with fully autonomous LLM-agent vulnerability-discovery systems (like Big Sleep or Mythos) that keep the LLM in the loop as an online reasoner rather than an offline instrumentation author — the authors note a small experiment suggesting the two approaches are complementary.

Glossary, results, and provenance

Every term in one place, then where the paper's numbers came from versus this guide's own framing.

Core terms
StateA side-effect-free expression over runtime values (a variable or pure observation function) chosen as an instrumentation target.
State transitionThe ordered pair of a state's value immediately before and after some operation.
State coverageThe set of previously unseen states or transitions recorded in the semantic bitmap — the paper's new feedback signal.
Semantic beaconDeveloper-authored evidence (assertion, comment, bug report, enum) suggesting a candidate state or transition — not itself a state.
Knowledge Base (KB)A vector-indexed store of bug-tracker reports, in-source comments, and design docs that the agent queries on demand.
Self-reflection filteringPrompting the LLM to justify keep/reject on each retrieved snippet against the specific target, to catch keyword-only false matches.
SEMANTIC_CONTEXT_ENUMThe probe primitive that hashes a site ID plus pre/post state values into the shared-memory bitmap.
Dual-feedback fuzzingRunning an edge-only and a state-augmented engine instance, switching to the latter after 100 stale iterations.
Supporting terms
Edge coverageThe classic fuzzing feedback signal: has this control-flow edge ever been exercised before.
Coverage plateauThe point at which new inputs stop adding new edges, even though internal behavior may still vary.
Inline Cache (IC)A per-callsite cached property-access handler, keyed to an expected object layout (Map).
Map / hidden classV8's internal descriptor for an object's property layout; other engines call this a "shape."
CallGraph / DataFlow / ASTMatchThe three structured code-analysis tools the agent can invoke, for interprocedural calls, def-use tracking, and structural pattern search respectively.
Fuzzilli / FuzzILThe IR-based JS fuzzer and its custom intermediate representation that StateLens is built on top of.
ASanAddressSanitizer, the memory-safety instrumentation compiled into every evaluated engine build.
v8CTFGoogle's public v8 bug-bounty tracker, source of the 35-vulnerability study behind observations O1–O3.
