The big idea

State machine replication (SMR) is the standard way to make a service fault-tolerant: a set of replicas agree on a single total order of client commands and execute them in that order. The traditional correctness specification only cares that all correct replicas agree on some order that contains every correct client's commands; which order they pick is, by design, immaterial. Byzantine fault tolerant (BFT) SMR inherits this same specification, just hardened against replicas that behave arbitrarily rather than merely crashing.

That indifference to order breaks down in permissioned blockchains such as Libra, CCF, or Hyperledger Fabric, where nodes belong to different organizations with a real financial stake in the specific sequence recorded on the ledger. Reordering, delaying, or injecting transactions ahead of others (front-running) is not a safety violation under the standard SMR specification, yet it has let bots extract documented profits in the millions of dollars on networks like Ethereum. The existing fixes, rotating leaders, holding leaders accountable after the fact, or removing leaders entirely, all attack the symptom (a leader's unchecked discretion) without ever stating what a "correct" order should guarantee, so none of them can be checked against a precise specification.

The paper's key idea is to extend the SMR specification itself with Byzantine ordered consensus: nodes attach an ordering indicator (for example a timestamp) to each command they propose, and the protocol's correctness conditions constrain which total orders are admissible given those indicators. This gives the paper a vocabulary, borrowed from classical social choice theory, to ask precise questions: can a protocol be built so that Byzantine nodes never fully dictate the order (ruling out a Byzantine oligarchy)? And can Byzantine influence be eliminated altogether? The paper proves the second goal is unreachable the moment correct nodes are given a genuine voice in ordering, a result it calls Byzantine democracy. It then identifies ordering linearizability, a timestamp-based property analogous to Herlihy and Wing's linearizability, as a correctness condition that is both meaningful and achievable.

The paper instantiates these ideas in Pompē, a BFT protocol built around a new architecture that factors ordering out of consensus: a short ordering phase locks each command's relative position using a quorum-median timestamp that Byzantine nodes cannot manipulate past the bounds set by correct nodes, and a separate, unmodified leader-based consensus phase only finalizes a prefix of that order onto the ledger. Because the order is already locked before consensus runs, a Byzantine leader retains the efficiency benefits of being in charge of consensus but loses all power to pick which commands go where. Built atop SBFT/Concord and HotStuff and run on up to 100 Azure VMs across three datacenters, Pompē-HS achieves 40% higher throughput at only 6% higher latency than HotStuff with batching (about 360,000 commands/s at 53 ms with n = 4 nodes in one datacenter), and sustains high throughput at 100 nodes across three geo-distributed datacenters when each node's compute scales up with n.

Key takeaways

  • Standard (BFT) SMR correctness says nothing about which total order is produced, but in blockchains the specific order has real financial consequences (front-running), a gap the paper names and formalizes.
  • Byzantine ordered consensus lets nodes attach ordering indicators to commands and states correctness conditions on the resulting total order, borrowing structure from social choice theory.
  • Theorem: any protocol that respects "free will" (every correct node's preferences can determine an outcome) is subject to Byzantine democracy, a weaker but unavoidable form of Byzantine influence; full elimination of Byzantine influence is impossible without silencing correct nodes.
  • Ordering unanimity (always honor a unanimous correct-node preference) is provably impossible, via a Condorcet cycle; ordering linearizability (based on the acyclic happened-before relation on timestamps) is achievable.
  • Pompē separates a timestamp-locking ordering phase from an unmodified leader-based consensus phase, enforcing ordering linearizability; it beats HotStuff on throughput at competitive latency and scales to 100 nodes with proportional resources.
Mechanism, step by step

From a formal gap to a two-phase protocol

Why order matters, what can and cannot be guaranteed about it, and how Pompē's ordering and consensus phases enforce the achievable guarantee.

1 · Background: SMR, BFT, and why order was never specified

SMR replicates a deterministic service across n nodes so that, as long as enough replicas are correct, clients see the behavior of a single correct server. It does this by running one instance of consensus per position in a request sequence; the only requirement is that every correct client's command eventually appears somewhere. BFT SMR (the n = 3f + 1, up to f Byzantine nodes model used throughout this paper) adds resilience to arbitrary, not just crash, faults, but keeps the same order-agnostic specification. In a leader-based BFT protocol such as PBFT, SBFT, or HotStuff, a single leader node decides, for each consensus instance, which command fills that ledger position, so a Byzantine leader can single-handedly choose the order without ever violating SMR's safety or liveness guarantees.

2 · Why rotating or policing the leader is not enough

Prior defenses, periodic leader rotation, performance-based leader accountability (Aardvark), partial-order pre-ordering (Prime), or leaderless consensus (Lamport's leaderless Byzantine Paxos, DBFT, HoneyBadgerBFT), all reduce a leader's power in some way, but none of them state a correctness property that the resulting order must satisfy. Concurrent work on order-fairness (Kelkar et al.) is the closest prior attempt to specify order correctness directly, but its achievable property (Block-Order-Fairness) only constrains ordering within blocks, its compiler-generated protocols need at least 4f + 1 nodes versus Pompē's 3f + 1, and the paper notes they appear to have been neither implemented nor evaluated.

3 · Formalizing the problem: ordering indicators and profiles

Byzantine ordered consensus generalizes BFT SMR's inputs: each proposal is a pair ⟨o, c⟩ of an ordering indicator o (a timestamp, sequence number, or dependency set) and a command c, together with an order-before relation ≺o on indicators. A profile is a set of such proposals; PC denotes the proposals from correct nodes only. A single profile can yield different traces (concrete runs) because Byzantine nodes and the network can behave differently each time, and different traces of the same PC can produce different final ledger orders.

4 · Byzantine oligarchy, free will, and Byzantine democracy

The paper defines three notions to pin down how much power Byzantine nodes can have over the order, independent of any specific mechanism:

NotionInformal meaningStatus
Byzantine oligarchyFor every profile of correct nodes, Byzantine nodes can force either relative order of any two commandsWhat a protocol should rule out
Free will(i) every correct profile has a trace where all its commands appear in the ledger, and (ii) correct nodes' indicators can actually determine an order for at least two profilesA minimal fairness property any reasonable protocol should have
Byzantine democracyThere exists at least one profile of correct nodes where Byzantine nodes can still force either orderProved unavoidable if free will holds (Theorem 3.1)

Theorem 3.1's proof constructs a chain of n + 1 profiles that interpolate, node by node, between two profiles PA and PB that free will requires to produce opposite orders for the same pair of commands. Somewhere along the chain, flipping a single node's proposals from PA's version to PB's version must flip the final order; if that pivotal node happens to be Byzantine, Byzantine democracy holds for the profile built around it. The conclusion: giving every correct node real influence (free will) necessarily leaves a backdoor for Byzantine nodes in some profiles.

Why this matters for protocol design. It rules out chasing an impossible goal (zero Byzantine influence with real correct-node influence) and redirects effort toward achievable properties that respect correct nodes' collective preferences whenever those preferences are strong, which is the role of ordering linearizability below.

5 · Two candidate ordering properties, one of which is impossible

Ordering unanimity says that if every correct node agrees c1 should precede c2, the ledger must respect that. The paper shows no protocol can combine free will with ordering unanimity, using a four-node Condorcet cycle: nodes propose timestamps for four commands c1..c4 such that, for every consecutive pair (modulo 4), three of the four nodes prefer the first before the second, but the preferences form a cycle (c1 before c2 before c3 before c4 before c1), so no single total order can honor all of them, and because any node might be the dissenting Byzantine one, the unanimity requirement applies to a set of preferences that cannot simultaneously hold.

Ordering linearizability escapes the cycle because it is phrased over timestamps' natural real-time ordering rather than majority voting: if the highest timestamp any correct node assigns to c1 is lower than the lowest timestamp any correct node assigns to c2, then c1 must precede c2. Because real-time happened-before is acyclic, this property cannot be trapped in a Condorcet cycle, and the paper proves it is achievable and efficiently implementable. 6 · Pompē's architecture: factor ordering out of consensus

Pompē assumes n = 3f + 1 nodes, up to f Byzantine, standard cryptographic primitives (signatures, collision-resistant hashes), an adversarial but partially synchronous network, and per-node timers that produce monotonically increasing timestamps. Its two phases are:

  1. Ordering phase. Locks a position for a command in the eventual total order, using timestamps as ordering indicators, before consensus ever runs.
  2. Consensus phase. Runs any standard leader-based BFT consensus protocol (the paper uses SBFT/Concord and HotStuff unmodified) to agree on which already-ordered commands become a stable, immutable prefix of the ledger.

Because the relative order is locked before the leader ever proposes a consensus value, the leader has no discretion left over ordering, only over when to finalize it, so a single leader can still run the fast consensus step without reintroducing a Byzantine oligarchy.

7 · The ordering phase: locking a timestamp with two round trips

  1. A node Ni with command c broadcasts a signed ⟨RequestTS, c⟩ and collects signed ⟨ResponseTS, c, ts⟩ replies from a quorum of 2f + 1 nodes.
  2. Ni takes the median of those 2f + 1 timestamps as c's assigned timestamp. Since at most f of the 2f + 1 responders are Byzantine, the median is both upper- and lower-bounded by a timestamp from a correct node; this is the fact that makes ordering linearizability provable.
  3. Ni broadcasts ⟨Sequence, c, T⟩ (T being the 2f + 1 timestamp responses) and collects ⟨SequenceResponse, ack/nack, h⟩ from 2f + 1 nodes.
  4. A node Nj acks only if c's assigned timestamp exceeds its own localAcceptThresholdTS (the latest timestamp it believes any stable command could still have). If c is accepted by a quorum, it is sequenced: guaranteed to eventually appear in correct nodes' ledgers at a position fixed by its assigned timestamp.

Under sufficient synchrony this takes two round trips, fewer than many prior BFT protocols' four. Nodes may execute sequenced commands speculatively while waiting for consensus to confirm their position, re-executing if speculation turns out wrong.

8 · The consensus phase: turning ordered commands into a stable ledger

Consensus slots are mapped to fixed, non-overlapping time intervals (for example 50 ms windows), known to all nodes in advance. Nodes also run a lightweight clock-synchronization sub-protocol: each periodically broadcasts a Sync message carrying the (f+1)th-highest timestamp it has seen (itself bounded by a correct node's timestamp), and resets its own timer upward to match. A leader proposing for slot k with interval [ts, ts′) proceeds as follows:

  1. Broadcast ⟨Collect, k⟩ and wait for 2f + 1 responses.
  2. A responding node Nj waits until (a) it has seen a Sync proving some node's timer reached T ≥ ts′, and (b) an additional delay Δ has passed on its own timer, giving all correct nodes time to finish ordering any command with a lower timestamp before this threshold advances. Nj then raises its localAcceptThresholdTS to ts′ and replies with the commands in its own sequenced set that fall in [ts, ts′).
  3. The leader runs the underlying consensus protocol (SBFT or HotStuff, unmodified) to agree on the union of 2f + 1 such replies as the value for slot k.

Once a prefix of slots is agreed, nodes build the total order by sorting each slot's commands by assigned timestamp (ties broken by hash) and append it to the ledger. Mechanism details stop here; measured performance is in the Evaluation tab.

9 · What the protocol guarantees, and what it cannot

The paper proves standard SMR consistency and validity, plus two properties specific to Pompē: ordering linearizability (Theorem 4.3, following from the median-timestamp bound of Lemma 4.1) and strong liveness (Theorem 4.4: during sufficient synchrony, a correct node's command is guaranteed to land at the position its assigned timestamp dictates). Residual Byzantine power is narrow but real: within the short window before enough correct nodes synchronize timers, a Byzantine node's reported timestamp can still tip a close call between two commands, and a Byzantine node can request a timestamp for a command and then simply withhold it from the Sequence step, deciding only later (indistinguishably from a network fault) whether to let it into the ledger. The paper proposes, but does not implement or evaluate, two mitigations: append-only hash chains over assigned timestamps for after-the-fact auditing, and hiding command contents with threshold encryption until sequencing completes.

10 · Implementation: extending two existing BFT protocols

Pompē-C extends VMware's Concord (an SBFT implementation); Pompē-HS extends the authors' libhotstuff. Both reuse the base protocol's consensus machinery unmodified and add the ordering phase plus leader-side proposal assembly on top:

CodebaseBase lines of C++Added lines
Concord (Pompē-C)22,1411,122

The added code implements four new message types (RequestTS, Sequence, Collect, and their responses), the handlers that sign and verify timestamps, and the localSequencedSet / localAcceptThresholdTS data structures; the leader logic changes only in how it assembles a proposal (by collecting 2f + 1 CollectResponses per time window) before handing it to the unmodified underlying consensus protocol. One optimization reduces message size: when the network is synchronous, CollectResponse messages carry only a hash of the sender's sequenced set; the leader proceeds directly to consensus if 2f + 1 hashes match its own, falling back to full command lists only on mismatch. This optimization is enabled by default in the evaluated system.

Evaluation

What the paper measures on Azure VM deployments, the headline throughput/latency tradeoffs, and how Pompē scales.

Setup

Experiments run on 100 Standard D16s_v3 Azure VMs (16 vCPUs, 64 GB RAM) across three datacenters (West US, Southeast Asia, North Europe), Ubuntu 18.04. Single-datacenter experiments use only the West US VMs. Clients run on separate VMs in a closed loop (one outstanding command at a time), and all reported results are from failure-free executions, since the paper states failures do not change Pompē's performance relative to its baselines.

Result 1

Without batching, Pompē-HS has lower ordering latency but higher peak throughput than HotStuff

What it shows. With batch size 1 and n = 4 in a single datacenter, HotStuff reaches 474 commands/s at 8.2 ms median latency. Pompē-HS reaches 1,642 commands/s, with median ordering latency 2.3 ms and consensus latency 47.7 ms. Ordering latency is 28% of HotStuff's latency because the ordering phase needs only two round trips versus HotStuff's four. The higher throughput is not from explicit batching (βo = 1 means no batching within the ordering phase) but from Pompē-HS implicitly collecting commands from many clients during its fixed consensus window; the paper observed an effective batch size of 82 commands in a 50 ms window.

What to take from it. The tradeoff is explicit: Pompē-HS's consensus latency (47.7 ms) is dominated by waiting out the fixed proposal interval (every 50 ms, with Δ = 10 ms), not by extra communication rounds. Pompē-C shows the same qualitative pattern against Concord (1,415 vs 40 commands/s at βo/βc = 1), so the paper reports results mainly for Pompē-HS.

Result 2

With matched batch sizes, Pompē-HS beats HotStuff's peak throughput at competitive latency

What it shows. Setting HotStuff's batch to βc = 800 and Pompē-HS's per-node ordering batch to βo = 200 (so the n = 4 nodes collectively match 800), HotStuff reaches 253,360 commands/s at 49.9 ms; Pompē-HS reaches 361,687 commands/s, with 5.7 ms ordering latency and 53.1 ms consensus latency. That is the paper's headline: 1.4x HotStuff's throughput (about 40% higher, matching the abstract) at about 6% higher latency. Batching lifts both systems' throughput by two to three orders of magnitude over the unbatched case (220x for Pompē-HS, 535x for HotStuff) because both are CPU-bound on cryptographic operations that batching amortizes.

What to take from it. Pompē's extra throughput over HotStuff at matched batch size comes from an additional, free batching effect: the fixed interval between consensus proposals naturally groups more commands together. The paper is explicit that, absent this effect, Pompē's extra signature verification work in the ordering phase makes its nodes saturate earlier than the baseline's.

Result 3

Geo-distribution hurts a rotating-leader baseline far more than it hurts Pompē

What it shows. With the same batch sizes as above but n = 4 nodes spread across three datacenters, HotStuff's throughput collapses to 6,160 commands/s (2.4% of its single-datacenter value) at 915.8 ms latency. Pompē-HS instead retains 315,753 commands/s, 87.3% of its single-datacenter throughput, with 259.7 ms ordering latency and 1,518.1 ms consensus latency. Concord and Pompē-C show the analogous pattern (1,461 vs 172,774 commands/s).

What to take from it. The paper attributes HotStuff's collapse to its rotating-leader design: a new leader cannot propose its own batch until it has collected enough votes confirming the previous leader's batch, and in a geo-distributed deployment that confirmation round trip is slow. Pompē avoids this because its effective batching does not depend on handing off leadership between proposals.

Result 4

Pompē trades higher consensus latency for higher throughput, with stable latency up to saturation

What it shows. The paper plots, for the geo-distributed n = 4 setup, the maximum ordering and consensus latency experienced by the fastest 50%, 90%, and 99% of commands as throughput increases. Both of Pompē-HS's latencies (ordering and consensus) stay stable until the system saturates. HotStuff's latency drops at low throughput because more clients let it fill batches faster while also raising throughput. Pompē-HS's ordering latency is consistently lower than its own consensus latency, since the latter adds the extra communication round of the consensus phase on top.

What to take from it. The gap between ordering and consensus latency is a feature, not just an artifact: because a command is sequenced (and therefore guaranteed a fixed position) as soon as the ordering phase accepts it, a client can learn its command's eventual relative order well before the ledger entry is finalized by consensus.

Result 5

Pompē's throughput degrades with a fixed-size ordering batch per node as n grows, but scales back up if each node gets more VMs

What it shows. Scaling n from 4 to 100 with HotStuff's batch fixed at βc = 800, HotStuff's throughput scales well. Three Pompē-HS configurations are compared: "Light" (βo = 800/n, one VM per node regardless of n) degrades quickly, because each node's ordering batch shrinks as n grows. "Fixed batch" (βo = 200 regardless of n) avoids this degradation. "Scale-up" (βo = 800/n, but VMs per node grow proportionally to n, as ⌊n/4⌋) is measured for n ∈ {4, 10, 16} (limited by the 100-VM testbed) and matches the "fixed batch" configuration's throughput; for n = 31, 61, 100 the paper reports predicted throughput (not measured), extrapolated from benchmarks showing the ordering phase scales near-linearly with VMs assigned per node. For both Pompē-HS and HotStuff, latency stays relatively stable as n grows in this geo-distributed deployment, since it is dominated by network communication rather than node count. Pompē-C shows qualitatively similar scaling against Concord.

What to take from it. Pompē's extra batching opportunity (each node batching its own clients' commands before the ordering phase) is what lets it sustain throughput at large n, but doing so costs proportionally more compute per node; the n = 31/61/100 numbers are projections, not measurements, and the paper is explicit about that distinction.

Result 6

The ordering phase's network cost is modest

What it shows. Comparing total bytes sent per node over an experiment with n = 4, Pompē-HS (βo = 1) sends about 18% more network traffic than HotStuff (βc = 1).

What to take from it. The paper characterizes this as a tolerable price for enforcing ordering linearizability and eliminating Byzantine oligarchy, though it reports this single comparison point rather than a sweep across batch sizes or deployment topologies.

What the evaluation does not cover. No experiments with actual Byzantine or crash failures (the paper asserts, without measurement, that failures would not change relative performance); no measurement of the early-stopping / selective-inclusion attack described in Section 4.3, nor of the proposed hash-chain or threshold-encryption mitigations; no evaluation of the client-facing deployment model discussed in Section 8 (clients talking directly to nodes rather than through a trusted organizational node); and no measurement under network conditions that violate partial synchrony.
Common questions

FAQ

Q·What problem is this paper actually solving, in plain terms?▾

In a fault-tolerant replicated service, all that usually matters is that every honest replica agrees on the same sequence of operations; which particular sequence is chosen is normally irrelevant. In a blockchain shared across competing organizations, the particular sequence can determine who profits from a trade or an auction, so "any agreed-upon order" is no longer good enough. The paper gives a way to state and enforce specific guarantees about which orders are acceptable, and a protocol, Pompē, that meets a useful one of those guarantees.

Q·What is state machine replication, and why does BFT make it harder?▾

State machine replication (SMR) runs the same deterministic program on multiple replicas and feeds them the same sequence of commands, so they stay in the same state and clients can trust the collective output as if it came from one correct server. Byzantine fault tolerant (BFT) SMR extends this to tolerate replicas that behave arbitrarily, not just crash, which is harder because a faulty replica might actively lie, which standard fault models like crash-stop do not need to anticipate.

Q·If order doesn't matter for correctness, why does it matter here?▾

Because "correctness" here is being measured by two different yardsticks. The classic SMR yardstick only asks whether replicas agree and include every valid command. The blockchain yardstick also asks about fairness between competing parties, and the specific order can hand one party a financial edge over another (for example, seeing a large trade and inserting your own ahead of it). The paper's contribution is to add that second yardstick to the formal specification.

Q·What is a "Byzantine oligarchy" and why is it bad?▾

It is the paper's name for the worst case: a protocol where, no matter what correct nodes prefer, the faulty nodes can always force either relative order between any two commands. Standard leader-based BFT protocols are subject to this whenever the leader is faulty, since the leader alone decides what fills each ledger slot.

Q·Why can't the paper just eliminate Byzantine influence entirely?▾

It proves that it can't, as long as the protocol also respects "free will," meaning that correct nodes' preferences can genuinely determine the outcome in at least some cases. The argument (Theorem 3.1) constructs a sequence of scenarios that gradually swaps one node's proposals at a time between two scenarios with opposite preferred orders; somewhere in that sequence, a single node's choice must flip the final order, and since any node could be the Byzantine one, there's always some scenario where a Byzantine node holds that pivotal power. The paper calls the resulting, more limited form of influence "Byzantine democracy."

Q·What is "ordering linearizability," and how is it related to the linearizability I already know?▾

Linearizability (for concurrent objects) says an operation that finishes before another one starts must appear to happen first. Ordering linearizability applies the same intuition to a set of timestamps collected from correct nodes for two commands: if every correct node's timestamp for c1 is lower than every correct node's timestamp for c2, then c1 must precede c2 in the ledger. It is a generalization because, instead of one operation's start/end, it reasons about the spread of many nodes' individually reported times.

Q·Why is unanimous agreement among correct nodes not enough to guarantee an order ("ordering unanimity")?▾

The paper constructs a four-node, four-command example (a Condorcet cycle, a classic social-choice-theory construction) where, for every pair of consecutive commands in a cycle, three out of four nodes prefer one order, but the preferred orders chain back on themselves (c1 before c2 before c3 before c4 before c1). Since any one node might be the Byzantine outlier, the requirement effectively applies to overlapping three-node majorities that can't all be satisfied simultaneously, so no protocol can promise to always honor them.

Q·How does Pompē stop a Byzantine leader from controlling the order, if a leader still runs consensus?▾

Pompē splits the work into an ordering phase and a consensus phase. The ordering phase locks each command's position (using a quorum-median timestamp that a Byzantine minority cannot push past bounds set by correct nodes) before consensus ever runs. By the time the leader proposes a value for a consensus slot, the relative order within that slot is already decided; the leader only decides when to finalize that already-fixed content, not what it contains or how it's ordered.

Q·Why use the median of 2f+1 timestamps instead of, say, the average or the leader's own timestamp?▾

With up to f Byzantine nodes out of a 2f+1 quorum, the median discards exactly f of the highest and f of the lowest reported timestamps, guaranteeing that at least one correct node's timestamp is at or below the median and at least one correct node's timestamp is at or above it. That sandwiching is the fact (Lemma 4.1) the entire ordering linearizability proof rests on; an average or a single node's value would not give the same guaranteed bound.

Q·Can a Byzantine node still cheat at all?▾

Yes, in two narrow ways the paper acknowledges rather than fully solves. First, during the brief window before all correct nodes' clocks have synchronized (bounded by a parameter Δ), a Byzantine node's reported timestamp can still tip the order of two commands whose correct-node timestamps are very close. Second, a Byzantine node can request a timestamp for a command and then simply not broadcast it further, later deciding, during the consensus phase, whether to let it surface at all; this is indistinguishable from an honest network delay, so it cannot be prevented, only discouraged after the fact (for example with append-only hash chains for auditing, which the paper proposes but does not implement).

Q·Is this the same as the "order-fairness" idea from other recent work?▾

They are motivated by the same gap but take different approaches. Order-fairness (Kelkar et al.) tries to define a property tied to what fraction of all nodes actually received commands in a given order, finds the strict version impossible (also via a Condorcet-style argument), and relaxes it to blocks of commands via an automatic compiler that needs at least 4f+1 nodes. Pompē instead defines properties over correct nodes' preferences specifically, proves the sharper Byzantine-oligarchy/democracy distinction, and needs only the standard 3f+1 nodes; it is also implemented and benchmarked, while the paper notes the order-fairness compiler's output had not been.

Q·Does Pompē need application changes, or work with any consensus protocol?▾

Pompē's consensus phase can use any standard leader-based BFT consensus protocol unchanged; the paper demonstrates this by extending both SBFT (via Concord) and HotStuff with the same small set of added message types and data structures (about 900 to 1,100 added lines of code on top of each base implementation). Clients interact with it the same way they would with the underlying protocol, except they receive two acknowledgements (one for sequencing, one for final commitment) instead of one.

Background terms
State machine replication (SMR)Running the same deterministic program on multiple replicas, fed the same sequence of commands, so that correct replicas stay in the same state and clients can trust the collective output.
Byzantine fault tolerance (BFT)Tolerance to replicas that may behave arbitrarily (lie, collude, send conflicting messages), not just crash. Typically assumes at most f faulty nodes out of n = 3f+1.
Byzantine nodeA replica that may deviate arbitrarily from its prescribed protocol, as opposed to a correct node, which always follows it.
QuorumA subset of nodes, here of size 2f+1 out of 3f+1, large enough to guarantee overlap with any other quorum by at least one correct node.
Leader-based consensusA consensus design where one designated node per round proposes a value (here, a batch of commands) for the other nodes to vote on and agree upon.
PBFTPractical Byzantine Fault Tolerance, the seminal leader-based BFT SMR protocol that most later BFT protocols, including SBFT and HotStuff, build on or compare against.
HotStuffA leader-based BFT consensus protocol with linear communication complexity and a rotating-leader design, used as Pompē's consensus engine in its HS variant and as the basis for the Libra blockchain.
SBFT / ConcordSBFT is a scalable BFT protocol building on PBFT; Concord is VMware's implementation of it, used as Pompē's consensus engine in its C variant.
LinearizabilityA correctness condition for concurrent objects: an operation that completes before another begins must appear to happen before it in any observed execution.
Permissioned blockchainA blockchain where only a known, authenticated set of organizations run nodes, as opposed to a permissionless blockchain open to anyone.
Ordering indicatorMetadata a node attaches to a proposed command expressing how it would like that command ordered relative to others, for example a timestamp or sequence number.
Front-runningObserving a pending transaction and inserting one's own transaction ahead of it to profit from the resulting price or outcome change.
Condorcet cycleA set of pairwise preferences among three or more options where majorities cyclically prefer A over B, B over C, and C over A, making no single consistent ranking possible.
Social choice theoryThe study of how individual preferences (as in voting) can or cannot be aggregated into a single collective decision; the paper draws its oligarchy/unanimity/manipulation vocabulary from this field.
BatchingGrouping multiple commands together to amortize the fixed per-round cost of consensus (e.g., signature verification) across all of them, raising throughput at the cost of added latency.
Round-trip time (RTT)The time for a message to travel from a sender to a recipient and back; a standard way to measure how many communication rounds a protocol step needs.
Threshold encryptionAn encryption scheme where decryption requires cooperation from a quorum of parties, usable here to hide a command's contents until it has been totally ordered.
