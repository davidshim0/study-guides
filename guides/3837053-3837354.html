HotStorage 2026 · A Field Guide

Repairing lost data with copies you already have, assigned to finish fastest overall

When a node dies, erasure-coded storage rebuilds it by downloading chunks from survivors — expensive, every time. This is the plain-English story of Asclepius, a scheduler that checks for duplicate data first and picks the repair node that can finish fastest overall, not by habit.

📄 "Asclepius" · Rizk, Ibrahim, Lambert · HotStorage '26 🎓 Erasure coding & scheduling basics covered in Start Here ⏱ ~25 min read
🩹

Assign repairs across nodes to minimize the time the SLOWEST one takes — weighing both the duplicate chunks each node already holds and its real download bandwidth — not the node that's closest by hash or next in line.

Quick glossary, then eight primers

The acronyms first, so nothing stalls you later; then one card per background concept. Skim in order or jump to what's unfamiliar.

Quick glossary

ECErasure Coding — split data into N chunks + K parity chunks; any N of N+K rebuild it.
RS(N,K)Reed-Solomon code with N data chunks, K parity chunks. Paper's default: RS(10,4).
CIDContent Identifier — a hash of a chunk's bytes; identical content ⇒ identical CID.
IPFSInterPlanetary File System — P2P storage using CIDs and node-local dedup.
CRDTConflict-free Replicated Data Type — lets Altocumulus keep cluster-wide metadata without a central lock.
L / D / MLocal / Direct / Missing chunk counts for a repair task at a candidate peer (§3.2).
RijTotal repair traffic if task i is assigned to node j: Dij + N×Mij.
R||Cmax"Unrelated machines, minimize makespan" — the scheduling problem Asclepius maps repair onto.
ASC / XOR / BAL / DEDUPThe four schedulers compared: Asclepius, IPFS's XOR-distance default, Altocumulus's round-robin default, and a greedy similarity-only baseline.
1Erasure coding and why repair is expensive▾

A block is split into N data chunks plus K parity chunks (a stripe); any N of the N+K survive-and-rebuild. It's cheaper on storage than full replication, but reconstructing one lost chunk means downloading N surviving chunks from other nodes ("helpers") — not just one.

Now you're ready: every "missing chunk" in this paper costs N chunks of download, which is why avoiding reconstruction entirely (via duplicates) is such a big win.
2Repair bandwidth is the bottleneck▾

Repair time is dominated by how long it takes to download the helper chunks over the network — not by CPU-side encoding/decoding, which is fast. So anything that cuts the bytes a repair node must pull, or routes the pull over a faster link, directly cuts download time. That's not quite the same as cutting total repair time, though — §4.4 shows the later send phase (storing the repaired shard somewhere) can dominate and erase those download-side gains if it's left unmanaged.

Now you're ready: Asclepius's base cost model (Section 3) is built around download time only — that's a deliberate simplification, and it's exactly why the paper needs a separate fix (ASC-Fast) for the send-phase blind spot.
3Content identifiers and deduplication▾

Hash a chunk's bytes and you get a CID. Two chunks with identical content get the identical CID. Storage systems use this to avoid storing the same bytes twice — deduplication. Note: dedup here is about identical data appearing in different places, unrelated to erasure coding's redundancy.

Now you're ready: if a lost chunk's CID matches something another node already stores, that node can hand it over directly — no reconstruction needed.
4IPFS: node-local dedup, no global view▾

IPFS chunks files into 256 KB pieces, each named by CID, and won't store the same chunk twice on a single node. But IPFS is decentralized — no node knows what every other node holds — so the same chunk can (and does) exist on many different nodes. That's inter-node duplication, and plain IPFS can't see it.

Now you're ready: Asclepius's first job is literally building the global-duplication view IPFS lacks, just for the chunks of a lost shard.
5Altocumulus: shards, CRDTs, heartbeats▾

Altocumulus layers erasure coding onto IPFS, grouping chunks into 100 MB shards and tracking every shard's CID cluster-wide via a CRDT — giving shard-level global dedup. But it still only dedups chunks within a node, so duplicate chunks across different shards go undetected by default. A 15-second missed heartbeat marks a peer dead and triggers repair.

Now you're ready: this is the real system Asclepius is bolted onto, and the gap it closes is exactly that cross-shard, cross-node chunk duplication.
6Scheduling on unrelated machines▾

Classic problem: assign n tasks to m machines where pij (processing time of task i on machine j) can differ arbitrarily per pair — not just by a machine-speed constant. The goal is usually makespan: the finish time of the last task. "Unrelated" is the key word — it's not that one machine is uniformly 2× slower, it's that a task might be fast on machine A and slow on machine B for its own reasons.

Now you're ready: repair fits this exactly — a shard's repair time at a node depends on duplication overlap and bandwidth, both of which vary per (shard, node) pair independently.
7NP-completeness and the Max-Min heuristic▾

Minimizing makespan on unrelated machines is strongly NP-complete — no efficient exact algorithm is expected to exist. The Max-Min heuristic sidesteps this cheaply: repeatedly find each unscheduled task's best (minimum) completion time across machines, then schedule the task whose best option is worst (largest) first — so the hardest-to-place task never gets stuck behind easier ones.

Now you're ready: Asclepius doesn't try to solve repair assignment exactly — it runs Max-Min once per failure and accepts a good, fast answer.
8Network heterogeneity▾

Real clusters (and especially WAN-spanning P2P deployments) don't have uniform bandwidth — the paper tests download bandwidths from 80 to 1384 Mbit/s across peers. A scheduler that ignores this can route a repair task to a node that's a great duplication match but sits behind a slow link.

Now you're ready: this is why Asclepius's cost model multiplies data volume by that peer's bandwidth, not a cluster average.
The whole story in one place

Asclepius in a nutshell

The problem, the cost model that fixes it, and how the pieces connect.

When a storage node dies, erasure-coded systems repair it by downloading surviving chunks — but which node does the downloading, and from whom, is usually decided carelessly: by hash distance (XOR, IPFS's default) or round-robin (BAL, Altocumulus's default). Neither looks at whether the repair node already holds some of the missing data, nor at how fast its network link actually is.

Asclepius fixes this by classifying every chunk of a lost shard, at every candidate peer, into three buckets: already local (free), retrievable directly from one other node (1 chunk transferred), or genuinely missing and needing full reconstruction (N chunks transferred). That gives a repair-traffic estimate Rij = Dij + N×Mij for every (shard, peer) pair. Divide by that peer's real download bandwidth and you get a processing time pij — turning "which node repairs which shard" into a textbook scheduling-on-unrelated-machines problem, solved cheaply with the Max-Min heuristic.

The payoff: up to 80% less repair bandwidth and up to 10× faster repair than the baselines, implemented as a real coordinator inside Altocumulus, an IPFS-based erasure-coded store.

🩺 Key takeaways

  • Repair cost isn't just "how much data" — it's duplication-adjusted data ÷ that peer's bandwidth.
  • Classifying chunks as Local / Direct / Missing turns duplication into a number: Rij = Dij + N×Mij.
  • Picking repair nodes is a scheduling-on-unrelated-machines problem (strongly NP-complete) — Asclepius solves it approximately with Max-Min.
  • Pure duplication-greedy (DEDUP) transfers the least data but can still be slow — it piles tasks on a few "best match" peers.
  • Fixing where the repaired shard is sent afterward (ASC-Fast) matters almost as much as fixing who repairs it.
  • Result: up to 80% less repair bandwidth, up to 10× faster repair, over three baselines.
🧭
For the tiering-minded reader: swap "repair node" for "destination tier" and Rij/bj is the same shape of question bandwidth-aware page placement asks across heterogeneous DRAM/CXL/NVM tiers — pick the target that minimizes transfer cost given both a data-affinity term (duplication here, locality/hotness there) and a heterogeneous-bandwidth term. Asclepius just applies that logic to node selection instead of page placement.
Five everyday pictures

How to think about Asclepius

Read in any order; each ends with where the picture stops being literally true.

The core idea · L/D/M chunks

Checking the pantry before the store

Before driving to the supermarket for a recipe, you check what's already in the pantry (local — free), what a neighbor can hand you right now (direct — one trip), and what genuinely has no substitute and must be cooked from scratch (missing — the expensive path, costing N ingredients here instead of 1). Asclepius does this per chunk, per candidate repairer, before assigning anyone a repair task.

Where it breaks: a real pantry check is free; Asclepius's version costs an RPC round-trip to every peer, which is why that step (not the scheduling) dominates coordinator overhead.
The model · Unrelated machines

Two movers, two jobs, no fixed rates

Mover 1 is fast at piano-moving but slow with pianos-in-walk-ups; Mover 2 is the reverse. Neither is simply "faster" — it depends on the job. That's "unrelated machines": the time for task i on machine j (pij) can't be reduced to a single per-machine speed. Repair is the same: a peer's repair time for shard X depends on that shard's duplication overlap with that peer, not a fixed peer rank.

Where it breaks: real movers also get tired or learn; pij in the paper is treated as a known constant, measured fresh for each failure.
The heuristic · Max-Min

Booking the trickiest guest first

A small venue is scheduling events: one group needs a huge, rare hall (few good slots — "hard to place"), others are flexible. Book the hard group first, while its few good slots are still open; the flexible groups can always be slotted in around whatever's left. Max-Min does exactly this with repair tasks: schedule whichever task's best available option is worst, before that option gets taken by someone else's assignment.

Where it breaks: Max-Min is a heuristic, not a proof of optimality — for small instances an exact solver could do better; the paper picks it purely for speed.
The contrast · Three baseline dispatchers

A hash lottery, a round-robin clipboard, and a one-track scout

XOR deals out repair jobs by hash distance — a lottery blind to both load and duplication. BAL is a clipboard going strictly in order — fair in count, blind to task size or speed. DEDUP is a scout who always picks whoever's data looks most similar — great instinct, but he'll send every job to the same few similar people even if they're slow, overloading them. Asclepius is the dispatcher who actually asks "similar and how fast can you go?"

Where it breaks: at zero duplication there's no "similarity" signal left to exploit — ASC then behaves just like a bandwidth-aware BAL, not like DEDUP.
The hidden tail · Destination placement

Renting the roomiest storage unit across town

You pick a storage unit purely by how much free space it has — and end up on the far side of town down a slow road, because the roomy units near you filled up fast (busy = popular = full). Default Altocumulus does this: it sends a freshly repaired shard to whichever peer has the most free space, which tends to be the slower peers (fast peers fill their disks sooner). ASC-Fast instead picks the fastest peer that doesn't already hold a copy.

Where it breaks: always picking the fastest unit creates its own traffic jam if many trucks converge on the same unit at once — the paper flags this hotspot risk as future work.
The full explanation

How it actually works

From chunk classification to the Max-Min decision to the hidden tail that almost undoes it.

1 · Classifying chunks: Local, Direct, Missing

For a repair task i (a lost shard) and a candidate repair node j, every chunk of that shard falls into one of three buckets at peer j: Lij chunks peer j already has locally (zero transfer), Dij chunks it can pull from one other node directly (one chunk transferred each), and Mij chunks with no surviving copy anywhere — truly missing, requiring full erasure-coded reconstruction (N chunks transferred, per the RS(N,K) rule).

2 · Turning assignment into scheduling

Multiply Rij by chunk size q to get bytes, divide by peer j's download bandwidth bj, and you get a processing time: pij = q × Rij / bj. Tasks = lost shards, machines = candidate peers, and the goal is to minimize makespan — the finish time of the last repair. This is the R||Cmax scheduling problem: strongly NP-complete, so Asclepius uses the Max-Min heuristic instead of an exact solver.

# Max-Min heuristic, one round
while unscheduled tasks remain:
    for each unscheduled task i:
        best[i] = min over candidate machines j of (load[j] + p_ij)
    pick task i* with the largest best[i]   # hardest task, schedule it first
    assign i* to its best machine j*
    load[j*] += p_(i*)j*

3 · Implementation: an RPC-gathering coordinator

Asclepius runs as a coordinator on the peer closest to the failure. It broadcasts the CIDs of every chunk in the lost shards to all available peers; each peer compares against its local CIDs and reports matches back. That builds the L/D/M counts — and thus the whole pij matrix — which feeds Max-Min to produce the final assignment.

4 · The hidden tail: where does the repaired shard go?

Repair isn't done once a shard is reconstructed — it must be stored somewhere. Altocumulus's default sends it to the peer with the most free space. But fast peers finish their own repairs (and fill their disks) sooner, so "most free space" systematically points at slow peers, who then also carry someone else's incoming write on top of their own repair queue. ASC-Fast — an evaluation variant built on top of Asclepius specifically to study this — instead sends the repaired shard to the fastest peer that doesn't already hold a copy from that stripe, at the cost of a possible hotspot if several repairs converge on the same fast peer at once (left as future work).

Follow the numbers

Worked examples

Four passes through the real model and real results, step by step.

① Computing Rij and pij for one peer

A toy example (numbers chosen for clarity, not from the paper). RS(10,4), so N=10. A candidate peer j has, for a lost shard: Lij=12 local chunks, Dij=5 direct chunks, Mij=3 chunks with no surviving copy anywhere. Chunk size q=256 KB, bandwidth bj=2 Gbit/s (decimal units throughout: 1 KB = 1,000 bytes, 1 Gbit/s = 10⁹ bit/s).

  1. Local chunks cost nothing: the 12 L chunks drop out of the formula entirely.
  2. Rij = Dij + N×Mij = 5 + 10×3 = 35 chunks worth of transfer.
  3. Convert to bytes: 35 × 256 KB = 8.96 MB.
  4. Convert bandwidth: 2 Gbit/s = 250 MB/s.
  5. pij = 8.96 MB ÷ 250 MB/s ≈ 0.036 s ≈ 36 ms.
💡
Notice the 3 missing chunks (not the 5 direct ones) dominate the cost: 30 of the 35 "chunk-equivalents" come from reconstruction. A peer with even one fewer missing chunk and much lower duplication elsewhere could easily win.

② Max-Min, by hand

Two repair tasks, two peers. pA,peer1=10s, pA,peer2=4s; pB,peer1=6s, pB,peer2=8s.

  1. Best option per task: task A's best is peer2 (4s); task B's best is peer1 (6s).
  2. Pick the worse of the two bests: 6s (task B) > 4s (task A) — schedule B first, onto peer1. load[peer1] = 6.
  3. Re-evaluate task A: peer1 now costs 6+10=16s; peer2 still costs 4s. Assign A to peer2. load[peer2] = 4.
  4. Makespan = max(6, 4) = 6 seconds.
  5. Why task order mattered: B had no good option elsewhere (peer2 cost it 8s) — scheduling it first, before peer1 got loaded, is exactly what avoided a worse makespan.
🩺
This is the full Max-Min logic from §3.1 — scaled down from dozens of shards and peers to two of each.

③ Duplication ratio 0 → 0.7, homogeneous network

50 GB dataset (DS1→DS3). What changes as duplication rises?

ApproachData transferred (dup 0 → 0.7)Repair time change
ASC50 GB → ~10 GB (−80%)−18%
DEDUP50 GB → ~10 GB (−80%)−74%
XOR50 GB → ~42 GB (−16%)−12.5%
BAL50 GB → ~45 GB (−10%)−8%
  1. At dup=0, BAL ≈ ASC — no duplication signal to use, so ASC just load-balances by bandwidth, same as BAL.
  2. At dup=0, XOR and DEDUP are ~3× slower than ASC — both concentrate repairs on a handful of peers (hash-close, or single "most similar"), causing contention.
  3. As dup rises, DEDUP improves fastest (−74%) — it both exploits duplication and is forced to spread tasks across more peers as more peers become viable similarity matches.
  4. At dup=0.7, ASC and DEDUP end up close (consistent with "almost the same performance... when the shards and network are homogeneous," §4.2) — because in a homogeneous network, bandwidth-awareness adds little once duplication-awareness is already present.

④ Heterogeneous network: when less data ≠ faster repair

DockerHub dataset (dup=0.76), bandwidths 80–1384 Mbit/s across peers.

  1. DEDUP transfers 22–33% less data than ASC/BAL/XOR — the best duplication matching of all four.
  2. Yet ASC repairs ~3× faster than DEDUP (and 2× vs BAL, 1.96× vs XOR) — DEDUP concentrates repairs on only 10 peers, some with low bandwidth.
  3. ASC's download phase alone is 25×/12×/12× faster than DEDUP/BAL/XOR's — bandwidth-awareness pays off hardest exactly where the network is uneven.
  4. But the "most free space" destination policy erodes that gain — slow peers accumulate free space fastest and get chosen to receive repaired shards, adding hundreds of seconds of send time.
  5. ASC-Fast (send to fastest free peer instead) recovers ~10× over the other "-Fast" variants, confirming the destination choice — not just the repair-source choice — was the missing piece.
⚠
Coordinator overhead: repairing 50 shards (5.2 GB) costs 4.45s of coordinator time — 4.2s gathering CID matches via RPC, only 0.25s running Max-Min. Having peers answer in parallel instead of serially cuts that 4.2s to ~300ms.
Test yourself

Practice problems

Try before opening the answer. Each ends with the misconception it checks.

Problem 1 · easy
RS(10,4). A peer has Dij=2 direct chunks and Mij=1 missing chunk for a lost shard. What is Rij?
Show answer
Rij = Dij + N×Mij = 2 + 10×1 = 12 chunk-equivalents.Misconception: treating a "missing" chunk like a "direct" one (cost 1). Reconstructing it needs a full stripe of N helper chunks — here, 10× the cost of a direct chunk.
Problem 2 · medium
On DS4 (variable shard sizes, homogeneous network), BAL gives every peer the same number of repair tasks, yet ASC still beats it by up to 26%. Why?
Show answer
Shards vary in size (20–100 MB → different chunk counts). BAL balances task count, not task size — one peer can get two huge repair tasks while another gets two tiny ones, both "balanced" by count. ASC balances by actual pij (size-aware), so it splits large and small tasks more evenly across peers.Misconception: that "same number of tasks per peer" means "same load per peer." It only does if tasks are uniform in size — which real shards aren't.
Problem 3 · medium
On the heterogeneous DockerHub test, DEDUP transfers 22–33% less data than every other approach but is still 2–3× slower than ASC. What's the lesson?
Show answer
DEDUP optimizes one variable (duplication match) and ignores the other (bandwidth). It concentrates tasks on the ~10 peers with the best content match, some of which have low bandwidth — so overall time suffers even though bytes transferred are minimized.Misconception: that minimizing bytes transferred always minimizes repair time. It only does when bandwidth is uniform; under heterogeneity, routing matters as much as volume.
Problem 4 · hard
Why is repair node selection modeled as "unrelated machines" (R||Cmax) rather than simpler "identical machines" scheduling?
Show answer
"Identical machines" would mean every peer processes any task at a rate scaled only by one per-machine speed constant — i.e., if peer X is 2× faster than peer Y, it's 2× faster on every task. But here pij depends on duplication overlap (which varies per shard-peer pair, not just per peer) and bandwidth — a peer can be the best match for one shard and a poor match for another, independent of its raw speed. That per-pair independence is exactly what "unrelated machines" captures.Misconception: assuming heterogeneity only means "some peers are generally faster." Here, duplication overlap breaks that symmetry — speed depends on the specific (task, peer) pairing.
Problem 5 · medium
ASC's download phase is up to 25× faster than DEDUP's, yet total repair-time improvement is "only" ~3×. Where did the rest of the gain go?
Show answer
Into the send phase. After reconstruction, the repaired shard must be stored somewhere; the default "most free space" destination policy tends to pick slow peers (fast peers fill up sooner), adding hundreds of seconds regardless of how fast the download was. ASC-Fast (routing to the fastest free-of-duplicate peer) is needed to recover that gap.Misconception: that fixing the "repair source" selection fixes the whole pipeline. The "repair destination" selection is a separate decision with its own, large impact.
Problem 6 · easy
At duplication ratio 0 (DS1), why do BAL and ASC perform similarly, while XOR and DEDUP perform poorly?
Show answer
With zero duplication, there is no similarity signal for ASC to exploit beyond bandwidth-aware load balancing — which is essentially what BAL already does in a homogeneous network. XOR (hash-distance) and DEDUP (always-best-match, here meaningless since nothing matches well) both concentrate tasks on a few peers regardless of duplication, causing contention and ~3× slower repair than ASC/BAL.Misconception: that a duplication-aware scheduler always outperforms a simple one. It only has an edge when duplication actually exists to exploit.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What does Asclepius actually decide?▾
Which surviving peer repairs each lost shard — based on how much of that shard's data the peer already has (local/direct duplicates) and how fast that peer's download link is. (Deciding where the repaired shard gets sent afterward is a separate question the paper studies with an evaluation variant, ASC-Fast — not part of base Asclepius.)
Q2What's the difference between Local, Direct, and Missing chunks?▾
Local chunks are already stored at the candidate peer (free). Direct chunks exist whole on some other single peer and can be fetched in one transfer. Missing chunks have no surviving whole copy anywhere and must be reconstructed from N helper chunks via erasure coding — far more expensive.
Q3Why model repair assignment as a scheduling problem instead of a simpler rule?▾
Because the real cost (Rij adjusted by bandwidth bj) varies per shard-peer pair in a way no fixed ranking of peers captures. Scheduling theory already has a name and known heuristics for exactly this shape of problem — "unrelated machines, minimize makespan" — so the paper reuses that machinery instead of inventing new rules from scratch.
Q4Why Max-Min instead of an exact optimal solver?▾
The underlying problem (R||Cmax) is strongly NP-complete — no efficient exact algorithm is expected. Max-Min is a cheap heuristic instead: each round it recomputes the best option for every remaining task across every machine, so its cost grows more like tasks² × machines than linearly — but that's still fast enough in absolute terms to rerun on every node failure.
Q5Does Asclepius change the erasure code itself?▾
No. It doesn't touch RS(N,K) encoding/decoding or invent a new code (unlike LRCs or regenerating codes). It only decides who does the repairing, complementing — not replacing — coding-level repair-bandwidth reductions.
Q6Why can less data transferred (DEDUP) still mean slower repair?▾
DEDUP greedily sends each task to whoever matches best on content, ignoring bandwidth and load. That concentrates many repairs on a handful of peers — some slow — so real elapsed time suffers even though total bytes moved is lower. Time, not bytes, is the metric that matters for users waiting on durability to be restored.
Q7What is the "destination placement problem" and ASC-Fast?▾
After reconstruction, a repaired shard needs a home if the repairing peer already holds a sibling shard. The default policy sends it to whoever has the most free disk space — which tends to be slow peers, since fast peers fill their disks sooner. ASC-Fast instead sends it to the fastest eligible peer, recovering most of the gain the default policy was quietly erasing.
Q8How expensive is gathering duplication information?▾
For 50 shards (5.2 GB), about 4.2 of the coordinator's 4.45 total seconds — almost all of it RPC round-trips asking peers which CIDs they hold. Letting peers answer in parallel (as DEDUP already does) cuts this to roughly 300 ms.
Q9Is Asclepius tied specifically to IPFS or Altocumulus?▾
The prototype is built into Altocumulus (an IPFS-based erasure-coded store), reusing its CID-based content addressing and CRDT metadata to detect duplication. The underlying idea — cost-model duplication plus bandwidth as a scheduling problem — doesn't require IPFS specifically, but the implementation leans on IPFS's content-addressing to get duplication detection "for free."
Q10How does this relate to prior repair-bandwidth research?▾
Prior work either changes the code (LRCs, regenerating codes — fewer chunks needed per repair) or changes the repair algorithm's mechanics (PPR, PivotRepair, ROR — pipelining, bandwidth-aware routing, read-based lazy repair) without looking at data duplication. Asclepius is explicitly positioned as complementary: it decides who repairs, orthogonal to how the code or pipeline works.
