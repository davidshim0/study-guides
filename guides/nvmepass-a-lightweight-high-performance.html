HPCA 2025 · A Field Guide

Letting a VM dial the SSD directly — without handing it the whole card

Software NVMe virtualization is either slow (virtio) or CPU-hungry (polling). Hardware-assisted passthrough (VFIO, SR-IOV) is fast, but VFIO can't be shared across VMs and SR-IOV/SIOV need specialized controller hardware to share one device. NVMePass gets near-native speed and zero CPU tax with almost no new hardware — by passing through just the I/O queues, and checking every request inside the drive's firmware.

Before you begin

The NVMe-specific pieces the paper leans on

You already know IOMMU/EPT-style address translation and DMA from the mm-stack side. These primers skip that and focus on what's specific to NVMe queues and virtualization. Read in order, or jump to what's unfamiliar.

NVMePass (the hero — no CPU tax) VFIO (hardware-assisted gold standard) NVMePass machinery (NRD / NP components) virtio / SPDK-Vhost (the baseline being fixed)
1The NVMe queue model: SQ, CQ, and doorbells▾

An NVMe device is driven through Queue Pairs: a Submission Queue (SQ) where the driver writes commands, and a Completion Queue (CQ) where the device writes results. Both are circular buffers in host memory, filled/drained via DMA. A small Doorbell Register (DB) per queue tells the device "I just added an entry" (SQ tail) or tells the host "I just consumed one" (CQ head).

One Admin Queue Pair manages the whole controller (create queues, manage namespaces); up to 65,535 I/O Queue Pairs can exist per device, each dedicated to moving read/write commands.

Now you're ready: "I/O queue passthrough" means a VM gets its own SQ/CQ/doorbells mapped directly into its address space — no software driver in the host ever touches the data path.
2Trap-and-emulate and the cost of a VM Exit▾

When a VM touches virtualized hardware the hypervisor doesn't let it access directly, the CPU traps into the hypervisor (a VM Exit), the hypervisor emulates the effect in software, then resumes the VM. This is flexible but costly — hundreds to thousands of cycles per exit, worse than any real I/O operation should cost.

Virtio pays this tax on every I/O request. NVMePass's whole architecture is designed so I/O requests never trigger a VM Exit at all.

Now you're ready: the paper's "control resources vs. data resources" split exists specifically to keep VM Exits confined to rare admin operations, off the hot I/O path.
3CMB — Controller Memory Buffer▾

The NVMe spec defines an optional Controller Memory Buffer: general-purpose read/write memory exposed by the controller, usable for things like storing SQ entries so the driver writes directly into the device's internal memory instead of host RAM.

NVMePass repurposes the name but not the hardware feature: its "CMB" is host memory carved out by the hypervisor's NP device manager, used purely as the shared region where guest I/O queue pages get mapped. No real device CMB support is required.

Now you're ready: when you see "CMB" in this paper, think "the hypervisor's staging memory for queue pages," not "on-device SRAM."
4The passthrough spectrum: virtio → polling → SR-IOV/VFIO▾

Virtio emulates a device via a paravirtual driver — every I/O crosses the hypervisor, cheap to deploy, slow. Polling solutions (SPDK vhost-NVMe, Mdev-NVMe) dedicate a host CPU core to continuously check shared-memory queues, trading a whole core for near-native speed. VFIO hands an entire physical device to one VM via IOMMU-based DMA/interrupt remapping — fast and free of CPU cost, but not shareable. SR-IOV shares one device across VMs by replicating PCIe functions (PF/VFs) in silicon.

Now you're ready: NVMePass sits at a new point on this spectrum — VFIO-like passthrough, but of just the I/O queues (a software-defined slice) instead of the whole PCIe function.
5Posted interrupts & IRQ bypass▾

Normally a device interrupt goes to the host, which then has to inject a virtual interrupt into the guest — another VM Exit. Posted interrupts are a CPU/IOMMU feature that lets a physical interrupt be delivered straight into the correct VM's virtual CPU, bypassing the host entirely.

Now you're ready: NVMePass pairs I/O queue passthrough with posted interrupts so that neither the request nor its completion ever needs the hypervisor.
6LBA, PRP/SGL — the addresses a malicious guest could forge▾

A Logical Block Address (LBA) names a location on the virtual disk. A PRP (Physical Region Page) or SGL (Scatter-Gather List) names the host-memory buffer the device should DMA into/out of for that request.

Once a VM can submit raw NVMe commands directly to hardware, both fields are guest-controlled — and a compromised or malicious guest driver could write LBAs or PRPs belonging to another tenant. This is exactly the gap passthrough opens and software-only checks can't close once the request leaves the CPU.

Now you're ready: this is the problem the paper's NRD mechanism exists to solve — verifying LBA and PRP legitimacy at the one place a forged command can't avoid: the drive's own firmware.

The whole story in one place

NVMePass in a nutshell

The problem, the split that fixes it, and how the pieces connect.

NVMe virtualization has always forced a choice. Virtio routes every I/O through the hypervisor and loses over half its throughput. Polling solutions like SPDK-Vhost recover the performance by burning a dedicated CPU core per device to spin on shared-memory queues — a tax that gets worse, not better, as VM density rises. VFIO and SR-IOV skip both problems by giving VMs direct hardware access, but VFIO can't be shared and SR-IOV needs bespoke silicon (extra PCIe functions) baked into every controller.

NVMePass's move is to notice that an NVMe device's resources aren't uniform: some (PCIe config space, BARs, the admin queue) are only touched for rare management operations — call these control resources. Others (I/O queues, doorbells, interrupts, LBAs) are touched on every single I/O — call these data resources. Emulate the control resources in software (they're off the hot path anyway, so trap-and-emulate costs nothing that matters); pass the data resources straight through to the VM via CMB-backed memory mapping, EPT, IOMMU DMA remapping, and posted interrupts.

That leaves one problem passthrough always creates: a VM with direct queue access could forge an NVMe command's LBA or PRP to read or corrupt another tenant's data. NVMePass closes this with NRD (NVMe Resource Domain) — binding each VM's queues, LBA range, and PRPs into one domain, checked by a few added lines in the drive's own firmware, so a forged command is rejected at the one place it can't be bypassed.

The payoff: 100.1%–100.5% of VFIO's IOPS, 203.2% of virtio's IOPS, zero extra CPU cores (vs. 1+ dedicated core for SPDK-Vhost), 40.0% lower latency and 68.0% higher IOPS than SPDK-Vhost in synthetic fio scaling at 150 VMs — for about 300 lines of firmware C code, no new PCIe hardware.

🍯 Key takeaways

  • Split by resource type, not by trust level: control resources stay emulated (slow path, no I/O impact); data resources pass through (fast path).
  • Passthrough is accomplished with a hypervisor-owned CMB + a custom page-fault handler that installs GPA→HPA mappings in the EPT — once per page, not per request.
  • DMA isolation comes from giving each VM a non-overlapping GPA range, so PRPs from different VMs can never collide even though the IOMMU translates them the same way.
  • NRD binds {I/O queues, LBA range, PRPs} per VM and checks every command in the NVMe controller's firmware — a few hundred lines of C, negligible cycles.
  • No dedicated hardware beyond that firmware check — unlike SR-IOV, which needs real silicon for every additional Virtual Function.
  • Result: near-VFIO performance, near-zero CPU overhead, and scaling verified up to 700 VMs in the paper's evaluation — well short of NVMe's 65,535-queue architectural ceiling, since real controllers (e.g., 64 queues on the Dongting-N2, 128 on the Intel P4510) and other host resources are the actual limits.
Six everyday pictures

How to think about NVMePass

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks.

The core split · Control vs. data

An express lane and a toll plaza

Most cars (I/O requests) should never stop — give them a dedicated lane straight through. Only rare admin traffic (registering a new account, changing a plan) needs the toll booth's paperwork. NVMePass builds exactly this: an express lane for I/O queues/doorbells/interrupts/LBAs, and a slow booth (trap-and-emulate) for PCIe config and the admin queue, which barely gets used.

Where it breaks: a real toll booth still spot-checks express-lane cars occasionally. NVMePass's express lane is never checked by the booth — the checking happens somewhere else entirely (see the next card).
Enforcement · NRD in firmware

A locksmith who re-cuts the key, not a guard at the door

A guard at the building entrance can be walked around if you get in another way. NVMePass instead makes the vault itself (the SSD controller) refuse any key (LBA/PRP) that wasn't cut for this exact tenant — checked at the one point every request must pass through no matter how it got there: the drive's own firmware.

Where it breaks: a locksmith re-cuts keys occasionally; NRD checks every single command, at line rate, in a hardware compare — the analogy undersells how cheap and constant the check is (the paper calls it "a few cycles").
Isolation · non-overlapping LBA/GPA

Fenced-off garden plots, not a shared lawn

Give two neighbors overlapping garden plots and eventually one plants where the other already dug. Give them non-overlapping plots — LBA range 0–999 to VM0, 1000–1999 to VM1; GPA 0–4G to VM0, 4–8G to VM1 for DMA — and there's structurally nothing to trip over, no matter what either does inside their own plot.

Where it breaks: garden fences are advisory; here the "fence" is enforced twice — once by EPT/IOMMU translation, once by NRD's firmware check — because a compromised guest driver could still try to write outside its plot.
Why the split is safe · slow vs. fast path

Back-office paperwork vs. the shop floor

A company can be slow at onboarding paperwork (done once, rarely) and still ship product fast every minute (the shop floor never waits on HR). NVMePass's control resources are the paperwork — PCIe config, admin queue, BARs — touched only at setup/management time; the data resources are the shop floor, touched on every I/O and never routed through the slow office.

Where it breaks: a real org chart's roles shift over time; here the classification is fixed by the NVMe spec itself — a resource is either always "control" or always "data," which is exactly what makes the split simple to implement.
Polling's cost · SPDK-Vhost

A doorman who never stops walking to the door

Hiring a doorman guarantees instant response — but only if he does nothing else, ever, spinning between the door and the desk even when no one's coming. That's a polling thread: it owns a whole CPU core, continuously checking shared-memory queues, whether or not I/O is happening. More SSDs means more full-time doormen.

Where it breaks: a real doorman can glance at other tasks between visitors; a busy-polling thread by design cannot — it's constant, unconditional CPU consumption, which is precisely why the paper measures it in whole cores per device, not a percentage.
Scalability · 65,535 queues

Private phone lines, not a switchboard operator

An old telephone switchboard needs an operator to manually connect every call — that operator is the bottleneck (virtio's hypervisor mediation). Give everyone their own direct line instead (a dedicated I/O queue pair per VM) and the "operator" is only needed to install the line once, never again per call.

Where it breaks: private lines don't share a trunk; NVMePass's VMs still share the same underlying SSD bandwidth and its finite queue count (65,535 per device), so density is bounded — just by a much bigger number than "how many PCIe VFs fit in silicon."

3 · DMA remapping and posted interrupts

PRP/SGL addresses in a guest's I/O command are GPAs; the IOMMU translates them to HPAs for the device's DMA engine automatically. NVMePass's only job is making sure that translation can never let two VMs collide: the hypervisor hands out non-overlapping GPA ranges at VM boot (e.g. VM0 gets 0–4G, VM1 gets 4G–8G), so their PRPs are isolated by construction before the IOMMU even runs. Interrupts use the posted-interrupt mechanism via the IRQ bypass manager, so a completion is delivered straight to the right VM's vCPU.

4 · Isolation and security: the NRD mechanism

Passthrough queues mean a VM's NVMe driver — or a malicious replacement for it — submits raw commands straight to hardware. Two protections apply:

  1. Queue and doorbell isolation via EPT. A submission command is 64 B; a 1024-entry SQ spans 16 pages. A completion is 16 B; a 1024-entry CQ spans 4 pages. Each VM's queues sit on their own pages, so EPT alone keeps VMs off each other's queues. Doorbell registers (8 B per queue pair) are packed 512-to-a-page by default — dense enough that EPT can't isolate them page-by-page, so NVMePass widens the spacing via CAP.DSTRD until each VM's doorbell lands on its own page too.
  2. LBA/PRP validation via NRD, in firmware. Each VM's I/O queues, LBA range, and PRPs are bound into one NVMe Resource Domain. On every command, the controller's existing command-validation module — normally just a legality check — gets one added comparison: does this LBA/PRP belong to the NRD this queue is bound to?
// NP Guarder, inside NVMe controller firmware
for each I/O command in Preprocessed_List:
    lba, prp = GET_LBA_PRP(command)
    if COMPARE(lba, pre_allocated_range) == FAIL:
        return IO_ERROR_LBA
    if COMPARE(prp, pre_allocated_range) == FAIL:
        return IO_ERROR_PRP
return verified_command   // only then does the device execute it
💡
Why firmware, not the hypervisor? Once a command leaves the guest and reaches the device, the hypervisor never sees it — that's the entire point of passthrough. The only place a check can catch every command, forged driver or not, is where the command is finally executed: the controller itself.

Worked examples

Four calculations, recomputed from the paper's own figures — checking the headline percentages hold up.

① Is "near-native" real? Recomputing VFIO parity

Fig. 6a gives randread-4k-4-128 IOPS: VFIO 514.1K, NVMePass 514.3K. Randwrite-4k-4-128: VFIO 20.4K, NVMePass 20.6K.

  1. Randread ratio: 514.3 ÷ 514.1 = 1.00039 → 100.04% of VFIO.
  2. Randwrite ratio: 20.6 ÷ 20.4 = 1.0098 → 100.98% of VFIO.
  3. Compare to the paper's claim: "100.1% and 100.5% IOPS of VFIO" for the same two cases. Our recompute lands close but not identical (100.04% vs. 100.1%, 100.98% vs. 100.5%) — the gap is rounding: the figure's labels are truncated to one decimal, so the true underlying IOPS differ slightly from what's plotted.
  4. Either way, the conclusion survives: the passthrough data path adds no measurable throughput cost over full hardware assignment.
🍯
Insight: when a paper's headline percentage and your recompute from its own chart don't match to the decimal, check for rounding before assuming an error — the direction and magnitude of the claim (≈100%) is what matters.

② Virtio's tax, quantified: the 203.2% figure

Same Fig. 6a group: NVMePass 514.3K IOPS, virtio 253.0K IOPS.

  1. Ratio: 514.3 ÷ 253.0 = 2.0328 → NVMePass delivers 203.3% of virtio's IOPS.
  2. Matches the paper's stated 203.2% to within rounding — this is the exact pairing the text is citing ("In randread-4k-4-128, NVMePass can achieve 203.2% IOPS of virtio").
  3. Where did virtio lose the other ~half? Every request crosses a VM Exit into the hypervisor and back — the paper attributes this to VM Exit cost, context-switch overhead, and cache pollution from the emulation path.

③ Scaling to 150 VMs: three claims, one figure

Fig. 8a/8b (2 SSDs, 4k-randread-1-1) at 150 VMs: latency — NVMePass 196.9µs, SPDK-Vhost 328.2µs, virtio 425.7µs. IOPS — NVMePass 757.6K, SPDK-Vhost 450.9K, virtio 348.7K.

  1. Latency reduction vs. SPDK-Vhost: (328.2 − 196.9) ÷ 328.2 = 0.4001 → 40.0% lower. Matches the paper's headline exactly.
  2. IOPS gain vs. SPDK-Vhost: (757.6 − 450.9) ÷ 450.9 = 0.6803 → 68.0% higher. Also an exact match.
  3. IOPS gain vs. virtio: (757.6 − 348.7) ÷ 348.7 = 1.1726 → 117.2% higher. Also exact.
  4. Why SPDK-Vhost degrades with density but NVMePass doesn't: SPDK-Vhost's fixed pool of polling cores gets divided across more queues as VM count rises, so per-VM service quality drops. NVMePass's path never touches a CPU core, so density doesn't compete for the same resource.
💡
This is the paper's clearest evidence that removing CPU from the I/O path isn't just a cost saving — it's what makes performance density-independent.

④ The CPU tax, per IOPS

Table III (test case 4k-randread-4-128, varying I/O pressure): virtio needs 1.94 cores at 200K IOPS and can't sustain 400K IOPS at all ("x"). SPDK-Vhost needs a flat 1 core regardless of pressure, up to 400K IOPS. VFIO and NVMePass need 0 cores at every pressure level.

  2. SPDK-Vhost's efficiency at 400K IOPS: 400,000 ÷ 1 = 400,000 IOPS per core — roughly 4× better than virtio's best ratio, because its cost is fixed rather than scaling with request volume.
  3. Context from the motivation section: virtualizing 16 SSDs on a 128-core server this way costs 16 cores → 16 ÷ 128 = 12.5% of the whole machine's compute, just for storage I/O.
  4. NVMePass and VFIO: 0 cores at any pressure — the ratio is undefined because there's no CPU cost to divide by. That 12.5% simply disappears.

Practice problems

Problem 1 · easy
Classify each as a "control resource" or "data resource" in NVMePass's terms: (a) PCIe BAR, (b) I/O submission queue, (c) NVMe admin queue, (d) doorbell register.
Show answer
Control: (a) PCIe BAR, (c) admin queue — touched only for setup/management, safely emulated. Data: (b) I/O SQ, (d) doorbell register — touched on every I/O, passed through directly.Misconception: assuming "control" means "important" and "data" means "bulk traffic only." The split is about access frequency and whether hypervisor mediation is affordable, not importance.
Problem 2 · medium
A VM issues 10,000 I/O requests to its passthrough queue. How many EPT page faults does this generate, assuming the queue pages were already established?
Show answer
Zero. The page fault handler installs the GPA→HPA mapping once, the first time a queue page is touched. Every subsequent access — no matter how many requests — is a normal EPT walk with no fault, no hypervisor involvement.Misconception: assuming passthrough still costs "a little overhead per request." The whole design goal is that after the one-time mapping, the marginal cost of an extra request is negligibly different from bare metal, per the paper's measurements.
Problem 3 · medium
A completion queue has 1024 entries at 16 bytes each. How many 4K pages does it span, and why does this number matter for isolation?
Show answer
1024 × 16 B = 16,384 B = 4 pages (4096 B each). It matters because EPT isolates at page granularity — as long as one VM's CQ pages never share a page with another VM's CQ, EPT alone (no NRD check needed) keeps them from reading each other's completions.Misconception: thinking isolation always needs the firmware-level NRD check. Queue/doorbell isolation is handled by EPT; NRD is specifically for LBA/PRP, which EPT cannot see inside a raw NVMe command.
Problem 4 · hard
Doorbell registers are 8 bytes per queue pair, and a 4K page fits 512 of them. Why is this a security problem for passthrough, and what's the fix?
Show answer
If 512 VMs' doorbells share one 4K page, EPT can't separate them — granting a VM access to its own doorbell also grants it access to the other 511 on that page. The fix is increasing register spacing via CAP.DSTRD (per the NVMe spec) so each queue pair's doorbell lands on its own page, restoring EPT's page-granularity isolation.Misconception: assuming "smaller resource = automatically safe to passthrough." Isolation granularity (EPT = whole pages) has to match resource size (doorbells = 8 bytes) or resources end up co-located and exposed.
Problem 5 · medium
Why can't the NP guarder's LBA/PRP check live in the hypervisor instead of the SSD firmware, given that passthrough already avoids the hypervisor for performance?
Show answer
Because passthrough means the command never touches the hypervisor at all — it goes straight from the guest's queue to the device. A hypervisor-side check would either require re-introducing a trap on every I/O (destroying the performance benefit) or would simply never see the command in time to block it. The firmware is the only point every command must pass through regardless of path.Misconception: treating "isolation" and "performance" as requiring the same enforcement point. NVMePass deliberately splits them — EPT/IOMMU (host-side, pre-flight, page-granularity) for queues and DMA, NRD (device-side, per-command) for LBA/PRP.
Problem 6 · easy
Table III shows virtio's CPU consumption rising with I/O pressure (0.17 → 1.07 → 1.94 cores) while SPDK-Vhost stays flat at 1 core. What does this say about the source of virtio's CPU cost?
Show answer
Virtio's cost scales with the number of requests because each one triggers a VM Exit and hypervisor emulation — more I/O literally means more trap-and-emulate cycles. SPDK-Vhost's cost is fixed because a polling thread spins continuously regardless of load — its cost comes from occupying a core at all, not from processing volume.Misconception: assuming all "software overhead" behaves the same way. Per-request overhead (virtio) and fixed-occupancy overhead (polling) are different failure modes with different scaling behavior.
Problem 7 · hard
SR-IOV achieves high performance and no CPU overhead too — so what does NVMePass actually add over it?
Show answer
Scalability and lightness. SR-IOV shares a device by replicating PCIe Virtual Functions in hardware, so the number of shareable "slots" is bounded by silicon design and adds real cost/complexity/power to the controller. SR-IOV is also optional in the NVMe spec, so only a few devices support it — vendor lock-in risk. NVMePass shares the device in software (I/O queues, up to 65,535 per device) and needs only a few hundred lines of firmware to enforce isolation, so it scales further and deploys on any NVMe controller whose firmware can be modified.Misconception: treating "hardware-assisted" as a single category. SR-IOV's hardware assistance (replicated PCIe functions) is a fundamentally heavier mechanism than NVMePass's (one firmware compare), even though both avoid CPU overhead.
Problem 8 · medium
Fig. 10 shows 8 VMs sharing 2 SSDs, each getting close to an even 1/4 share of one disk's IOPS, with tightly clustered tail latencies. What would it look like if NVMePass's partitioning were unfair instead — and why doesn't that happen here?
Show answer
Unfairness would show up as a few VMs' IOPS/latency curves diverging sharply from the rest — e.g., one VM dominating a disk's queue while others starve. It doesn't happen because NVMePass gives each VM its own hardware I/O queue (not a shared one arbitrated by software), so the SSD's own per-queue scheduling — not a contended software layer — determines how bandwidth splits; the paper reports this in fact produced roughly even service in its 8-VM/2-SSD experiment (Fig. 10), though that's an empirical observation at that scale, not an architectural fairness guarantee.Misconception: assuming fairness must be actively enforced by the virtualization layer, or that it's guaranteed at any VM count. Here it's mostly a byproduct of giving each tenant a structurally separate queue rather than a shared one — the paper demonstrates it, but doesn't prove it scales to arbitrary densities.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What's the fundamental problem NVMePass solves?▾
Every existing way to virtualize an NVMe SSD forces a trade-off among performance, CPU cost, and hardware complexity/scalability. Virtio is slow, polling burns CPU cores that get scarcer as VM density rises, and hardware-assisted schemes (SR-IOV, FVM, BM-Store) need bespoke silicon. NVMePass targets all three simultaneously by passing through only the data resources and checking legality in existing firmware.
Q2How is this different from just using VFIO for the whole device?▾
VFIO passes through the entire physical function to one VM — great performance, but the device can't be shared. NVMePass passes through only the I/O queues (a much smaller, software-definable slice), so many VMs can each get their own queues from the same physical device while control resources stay emulated and shared in the hypervisor.
Q3What actually establishes the direct memory path?▾
Three pieces working together: the hypervisor's CMB (a region of host memory holding the queue pages), a custom page-fault handler that installs the GPA→HPA mapping in the EPT the first time a queue page is touched, and the IOMMU, which separately translates PRP/SGL addresses for the device's own DMA engine.
Q4Does the NVMe device need to actually support a CMB?▾
No. NVMePass's "CMB" is a naming choice for hypervisor-managed host memory used to stage I/O queue pages — it requires no on-device memory or spec-level CMB feature from the physical SSD.
Q5How does NRD stop a malicious or buggy guest driver?▾
Every VM's queues, LBA range, and PRPs are bound into one NVMe Resource Domain. The controller firmware compares each incoming command's LBA and PRP against the domain bound to the queue it arrived on; a mismatch returns an I/O error and the command never executes — regardless of what software (legitimate or forged) submitted it.
Q6Why can't SR-IOV do the same thing more cheaply?▾
SR-IOV shares a device by replicating PCIe functions in hardware — each Virtual Function needs real silicon, capping how many VMs can share one device and adding controller design cost. It's also optional in the NVMe spec, so few SSDs support it. NVMePass shares queues in software (up to 65,535 per device) and needs only ~300 lines of added firmware logic, with no new PCIe hardware.
Q7What exactly does the NP guarder need from the SSD vendor?▾
Access to the firmware's existing command-validation module, plus a few hundred lines of C to add the LBA/PRP comparison against the pre-allocated NRD. The paper implemented this on a Yingren Dongting-N2 controller; it notes the same hook exists in NVMeVirt's __nvmev_proc_io and in Xilinx's NVMe target controller's Command Validation module.
Q8Does the guest OS or application need to change?▾
No application changes needed. The NP frontend driver does replace the guest's NVMe driver (about 300 lines of guest-kernel code) with one that speaks the passthrough protocol, but it still presents a standard NVMe interface upward — so unmodified guest applications, and the rest of the guest OS, require no changes.
Q9How are interrupts delivered without hypervisor involvement?▾
Via posted interrupts: the NP backend driver configures posted-interrupt I/O queues through the IRQ bypass manager, so a completion interrupt is delivered by hardware straight into the correct VM's virtual CPU, without a VM Exit to the host.
Q10What's the actual minimum hardware requirement?▾
Just the NP guarder / NRD check in the NVMe controller firmware — a few hundred lines of C with negligible per-command cost. No CMB hardware, no SR-IOV, no ADI/PASID support, no dedicated accelerator. Everything else (frontend, backend, device manager) is ordinary host/guest software.
Q11Where does NVMePass fall short of VFIO, if anywhere?▾
The paper doesn't report a performance gap in its benchmarks (IOPS ratios are ≈100%). The trade NVMePass makes relative to VFIO is architectural, not a performance cost: it requires implementing and trusting the NRD firmware check, whereas VFIO needs no device-side trust at all because the whole device belongs to one VM.
Q12How does this connect to CXL / memory-tiering work?▾
The shape of the problem is familiar from CXL device sharing: give an untrusted VM/tenant a direct, low-latency path to a shared device (here NVMe queues; there CXL.mem or CXL.io regions) while enforcing isolation somewhere the fast path can't route around — IOMMU/EPT for addressing, and a device-side check (NRD here; a CXL device's own access-control logic there) for what software addressing alone can't catch. This connection is this guide's framing, not a claim from the paper.

Core terms
NVMePassThe paper's software-hardware co-design: pass NVMe I/O queues through to VMs directly, verify legality in device firmware.
I/O queues passthroughMapping a VM's SQ/CQ/doorbells directly into its address space via CMB + EPT, so I/O never crosses the hypervisor.
NRD (NVMe Resource Domain)A bound set of {I/O queues, LBA range, PRPs} for one VM, checked by the NP guarder on every command.
NP guarderFirmware module in the NVMe controller that verifies each command's LBA/PRP against its NRD, rejecting illegal requests.
Control resourcesPCIe config space, BARs, admin queue — touched rarely, safely emulated by the hypervisor.
Data resourcesI/O queues, doorbells, interrupts, LBAs — touched on every request, passed through to the VM.
NP frontend / backend / device managerNVMePass's guest-kernel, host-kernel, and hypervisor components respectively (see How It Works, section 5).
Supporting terms
SQ / CQ / DBSubmission Queue, Completion Queue, Doorbell register — the NVMe queue-pair primitives.
CMBController Memory Buffer — here, hypervisor-owned staging memory for guest queue pages, not on-device SRAM.
EPT / IOMMUExtended Page Table (CPU memory virtualization) and I/O MMU (DMA/interrupt remapping) — the two translation layers NVMePass relies on.
GPA / HPAGuest / Host Physical Address — the two ends of EPT and IOMMU translation.
PRP / SGLPhysical Region Page / Scatter-Gather List — how an NVMe command specifies its DMA buffer.
VFIOFramework for handing a full physical device directly to one VM via IOMMU.
SR-IOV / SIOVPCIe hardware-sharing standards requiring replicated Virtual Functions / Assignable Device Interfaces.
VM Exit / trap-and-emulateThe costly context switch into the hypervisor that passthrough is designed to avoid on the I/O path.
Posted interrupt / IRQ bypassHardware mechanism delivering a physical interrupt straight to the correct VM's vCPU.
FirecrackerThe lightweight microVM hypervisor NVMePass was implemented and evaluated on.
