eBPF '26 · A Field Guide

Policies that get verified, not native crashes

NCCL plugins run as unsandboxed native code inside a training job. One null pointer and thousands of GPUs stall. This is the plain-English story of NCCLbpf, a verified eBPF layer for NCCL's tuner, profiler, and net plugins.

1What an NCCL collective is▾

Distributed training splits work across many GPUs, and periodically they must exchange data — sum gradients (AllReduce), gather shards (AllGather). NCCL is the library that implements these collectives efficiently over NVLink/InfiniBand.

Now you're ready: everything in this paper is about how NCCL decides how to run a collective — which algorithm, protocol, and channel count.
2NCCL's plugin architecture▾

NCCL exposes extension points loaded via dlopen: a tuner picks algorithm/protocol/channels per call, a profiler receives timestamped events, a net plugin controls transport, and an env plugin sets parameters. Cloud providers ship custom tuners in production.

Now you're ready: NCCLbpf doesn't replace this architecture — it becomes one very safe implementation of it.
3Why native plugins are risky▾

Plugins run as ordinary native code with full process privileges, no sandbox. NCCL's own inspector plugin has caused production crashes from use-after-free and deadlock; profiler plugins have segfaulted multi-GPU nodes. Llama 3 pre-training saw 466 job interruptions in 54 days.

Now you're ready: this is the concrete cost NCCLbpf is trying to eliminate.
4What the eBPF verifier checks▾

Before an eBPF program runs, a verifier statically proves memory safety (no out-of-bounds access, no null-deref), bounded execution (no infinite loops), stack safety, and that only whitelisted helper functions are called — all before a single instruction executes.

Now you're ready: this is what turns "plugin crashes the job" into "plugin fails to load, with an error message."
5Userspace eBPF (bpftime), not kernel eBPF▾

Classic eBPF runs in the Linux kernel. bpftime is a userspace runtime that verifies and JIT-compiles the same bytecode model inside an ordinary process — no kernel privileges, no kernel modules, so it can be embedded directly in NCCL's address space.

Now you're ready: "verified extensibility" moves from the kernel into a training job's own process.
6Algorithm, protocol, channels — and the cost-table trick▾

A tuner doesn't return "use Ring" directly — it fills a 2D cost table with a value per (algorithm, protocol) pair: 0 for preferred, a sentinel 1e9 for disallowed, so NCCL can fall back gracefully if a choice is unavailable.

Now you're ready: a policy's "decision" is really an edit to this cost table, translated by NCCLbpf's host code.
7Maps — typed, shared, concurrent state▾

eBPF maps are fixed-size key/value stores with atomic access, usable from multiple programs at once. NCCL's native plugins have no equivalent — profiler and tuner have no shared state today, so cross-plugin coordination is ad hoc or absent.

Now you're ready: maps are how a profiler's latency readings reach a tuner's next decision, safely.
8Why one verifier isn't enough for a distributed system▾

A verifier proves properties of one program, one execution. But NCCL needs all ranks to agree — if one rank's tuner picks Ring and another picks Tree, the collective hangs. No single-execution verifier can see across ranks to check that.

Now you're ready: this is the paper's central new problem, solved with static taint analysis over shared vs. rank-local inputs — the topic of "How It Works" §3.
The whole story in one place

NCCLbpf in a nutshell

The safety gap, the verified fix, and the one problem kernel eBPF never had to solve.

NCCL plugins run as native code with no sandbox: a null pointer crashes the job, and updating a policy requires restarting it. NCCLbpf embeds a userspace eBPF runtime (bpftime) inside NCCL's existing tuner/profiler/net plugin ABI — no NCCL source changes. Policies compile to verified eBPF bytecode, are load-time checked for memory safety and bounded execution, then JIT-compiled to near-native speed.

The twist beyond kernel eBPF: a verifier only sees one program, one execution — but NCCL needs every rank to pick the same algorithm, or the collective hangs. NCCLbpf's machinery adds static taint analysis at load time, rejecting policies that read rank-local state and letting through only policies whose decisions depend on inputs shared across replicas (message size, collective type).

Typed maps let a profiler and tuner cooperate — closed-loop adaptation NCCL's native plugins never had. Atomic hot-reload swaps policies via compare-and-swap with zero dropped calls.

The payoff: 80–130 ns per decision (<0.03% of collective latency), all 7 tested unsafe policies rejected at load time, and a message-size-aware policy that improves 8-GPU AllReduce throughput by up to 27% over NCCL's default.

🍯 Key takeaways

  • Verification catches memory-safety and termination bugs, not bad policy decisions — a memory-safe policy can still tank throughput.
  • The paper's novel problem: a verifier sees one execution, but NCCL needs cross-rank agreement — solved with static taint analysis on shared vs. rank-local inputs.
  • Typed maps give profiler and tuner shared, atomic state — a closed loop NCCL's native plugins lack.
  • Hot-reload swaps policies via CAS: old calls finish under the old policy, next calls use the new one, zero drops.
  • Overhead follows 80 + 30·nlookup + 10·nupdate ns — <0.03% of collective latency.
  • Message-size-aware policy: up to 27% AllReduce throughput gain, selecting Ring/LL128 for 4–32 MiB and Ring/Simple for 64–192 MiB.
Six everyday pictures

How to think about NCCLbpf

Read in any order. Each ends with where the picture stops being true.

The core idea · Verify before running

A security checkpoint, not a post-flight inquiry

Screening bags before boarding catches a problem before it's airborne; investigating a crash afterward is too late. The eBPF verifier checks a policy's memory-safety and null-checks before it ever executes; a native plugin's bug is only found via a segfault mid-flight — SIGSEGV at address 0x0, job dead.

Where it breaks: screening only catches known bag-shaped threats. The verifier catches memory/termination bugs, not a policy that's memory-safe but makes a terrible decision (the one-channel case, §5.3).
The distributed twist · Taint analysis

Three kitchens, one recipe card

Give identical recipe cards to three kitchens and they'll plate the same dish — if every ingredient listed is the same across kitchens. If one recipe secretly says "use whatever's in this kitchen's fridge," the dishes diverge. NCCL ranks are the kitchens: if a policy reads only shared inputs (message size), every rank picks Ring together; if it reads rank-local state, ranks can disagree (R, R, T above) and the collective hangs.

Where it breaks: real kitchens can taste and adjust; NCCLbpf's taint check is static and conservative — it rejects rank-local reads outright rather than reasoning about whether they'd happen to agree.
Composability · Shared typed maps

A walkie-talkie, not a note left on a desk

Leaving a sticky note for a coworker is ad hoc — it might get lost, overwritten, or read out of order. A shared walkie-talkie channel is structured and reliable. The profiler eBPF program writes latency into a typed map; the tuner reads it with atomic, verifier-enforced null checks — no locking bugs, no ad hoc shared memory.

Where it breaks: a walkie-talkie carries any message; eBPF maps only carry fixed-size keys/values — NCCL's simple per-communicator scalars fit fine, richer state wouldn't.
Zero-downtime updates · Atomic hot-reload

Changing runners mid-relay, without dropping the baton

A relay team can swap in a fresh runner at the handoff line without the baton ever touching the ground. NCCLbpf verifies and JIT-compiles a replacement policy, then does one atomic compare-and-swap on the active function pointer: any in-flight call finishes under the old policy, the very next call uses the new one. Total reload is ~9.4 ms, but only the 1.07 µs swap touches the hot path.

Where it breaks: a relay team agrees on one baton at a time; here, different threads can briefly run different policies mid-swap. That's fine only because each collective's decision is independent — there's no shared "baton" being fumbled.
The mechanism · Cost-table sentinel

Graying out a disabled menu item

A restaurant app doesn't delete a sold-out dish from the menu — it grays it out, so the kitchen can still serve it if something changes. NCCL's tuner does the same: it marks a preferred (algorithm, protocol) pair cost 0 and disfavored ones 1e9, letting NCCL fall back gracefully if a combination turns out to be unavailable at runtime.

Where it breaks: a greyed-out dish is still visibly listed; NCCL's cost table has no such transparency for the policy author — the sentinel value is a convention the host code must translate correctly.
Verifier boundary · Safe but wrong

A spellchecker, not a fact-checker

A spellchecker will happily pass a grammatically perfect sentence that's completely false. The verifier is the same: it proves a policy is memory-safe and terminates, saying nothing about whether pinning every collective to one channel is a good idea. The one-channel policy passes verification cleanly and then tanks throughput 87–95%.

Where it breaks: a fact-checker exists as a separate role; NCCLbpf has no semantic-correctness layer at all — that responsibility stays fully with the operator writing the policy.
The full explanation

How it actually works

From the safety gap to the distributed-consistency fix, with the paper's mechanisms rebuilt as diagrams.

1 · The safety gap — native plugins, no sandbox

NCCL's tuner, profiler, net, and env plugins load via dlopen and run with full process privileges. A null-pointer dereference, race, or memory corruption in any of them can crash the whole job or silently corrupt state — production incidents the paper cites include a use-after-free deadlock in NCCL's inspector plugin and segfaults from profiler plugins on multi-GPU nodes.

2 · Load-time verification — catching bugs before execution

NCCLbpf embeds bpftime, whose PREVAIL-based verifier statically checks every policy: memory safety, bounded execution, stack safety, and a helper-function whitelist. Map lookups must be null-checked before dereference — omit one, and the program is rejected at load time with an actionable error, not a runtime crash.

// same bug, two outcomes
Native plugin:  Signal: SIGSEGV (address 0x0) in getCollInfo()
eBPF policy:    VERIFIER REJECT: R0 is map_value_or_null;
                must check != NULL before dereference at insn 7

3 · The distributed-consistency problem — the paper's central novelty

A verifier proves properties of one program on one execution. But NCCL requires every rank to select the same algorithm — a mismatch hangs the collective. Since identical bytecode fed identical (replica-shared) inputs always produces identical outputs, NCCLbpf runs static taint analysis at load time, tracking which inputs flow into the output decision and rejecting any policy whose decision depends on rank-local state.

4 · Composable state — the profiler/tuner closed loop

Typed maps let independently-loaded policies share state with atomic access — capability NCCL's native plugin APIs simply don't expose.

SEC("profiler")
int record_latency(ctx) {
  st = bpf_map_lookup_elem(&latency_map, &key);
  if (!st) return 0;           // verifier-enforced null check
  st->avg_latency_ns = ctx->latency_ns;
}
SEC("tuner")
int size_aware_adaptive(ctx) {
  st = bpf_map_lookup_elem(&latency_map, &key);
  if (!st) { ctx->n_channels = 4; return 0; }
  ctx->algorithm = (ctx->msg_size <= 32*1024) ? TREE : RING;
  ctx->n_channels = (st->avg_latency_ns > 1000000)
      ? min(st->channels + 1, 16) : st->channels;
}

5 · Enforcing and hot-reloading

The active policy is stored as an atomic function pointer. Reload has three phases: verify the replacement, JIT-compile it, then compare-and-swap the pointer. If verification fails, the old policy keeps running uninterrupted — the system never enters an unverified state.

Follow the numbers

Worked examples

Four traces using the paper's own measurements.

① What the overhead model can (and can't) tell you

The paper's model is 80 + 30·nlookup + 10·nupdate ns. slo_enforcer measures ΔP50 = 130 ns. What combinations of lookups/updates are consistent with that?

  1. Subtract the fixed base: 130 − 80 = 50 ns left to explain with map ops.
  2. Try 1 lookup: 50 − 30 = 20 ns remaining — that's exactly 2 updates (2 × 10 ns), so (1 lookup, 2 updates) is one combination that fits.
  3. Check against the table: lookup_update (1 lookup, 1 update) predicts 80+30+10=120 ns — close to, but distinct from, slo_enforcer's 130 ns.
  4. Caveat: the paper reports timings and the model's coefficients (Table 1), not each policy's exact op count — (1 lookup, 2 updates) fits the arithmetic but isn't confirmed as slo_enforcer's actual access pattern.
🍯
The model is precise enough to narrow down plausible map-access patterns — but going from "a combination that fits" to "the combination that's actually used" requires reading the policy's source, not just its latency.

② The 27% AllReduce gain, from raw bandwidth

Table 2 gives 8 MiB AllReduce bandwidth: 196.3 GB/s (default NVLS) vs. 249.7 GB/s (Ring).

  1. Improvement = (249.7 − 196.3) / 196.3 = 53.4 / 196.3 = 27.2% — the paper's headline number.
  2. Compare at 128 MiB: (628.9 − 596.9)/596.9 = 5.4% — the gain shrinks as NVLS's hardware multicast becomes more effective at scale.
  3. Compare at 256 MiB: (632.5 − 656.5)/656.5 = −3.7% — Ring is now worse; NVLS has crossed over.
  4. Why the policy still wins overall: it selects Ring/LL128 for 4–32 MiB and Ring/Simple for 64–192 MiB, deferring to NCCL's default outside those ranges, capturing the gain without the crossover's loss.

③ Why a static env var can't do what the policy does

Could an operator just set NCCL_ALGO=Ring globally?

  1. Below 256 MiB, Ring wins by 5.4–27.2% (Table 2) — a global Ring setting looks great here.
  2. At 8 GiB, default is 836.3 GB/s vs. Ring's 697.6 GB/s — a −16.6% regression under a global Ring setting.
  3. A per-call policy avoids this by reading msg_size (a shared input, so every rank agrees) and switching algorithms per collective — impossible with a single process-wide environment variable.

④ How little of hot-reload is actually on the hot path

Total reload cost is ~9.4 ms; the atomic swap itself is 1.07 µs.

  1. Fraction on the hot path: 1.07 µs / 9,400 µs ≈ 0.011% — verification and JIT-compilation happen off to the side, only the pointer swap is instantaneous and visible to callers.
  2. Across 400,000 invocations spanning a reload, zero calls are dropped — each in-flight call simply finishes under whichever policy pointer it read at call time.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A policy omits a null check after a map lookup. What happens under NCCLbpf, vs. under a native plugin doing the same thing?
Show answer
Under NCCLbpf, the verifier rejects the program at load time with an error like "R0 is map_value_or_null; must check != NULL before dereference." Under a native plugin, the same bug runs until it actually dereferences a null pointer, crashing the job with SIGSEGV.Misconception: that eBPF just runs "safer" versions of the same crashes. It doesn't run the buggy path at all — it's caught before execution, not recovered from after.
Problem 2 · medium
Using 80 + 30·n_lookup + 10·n_update ns, predict ΔP50 for a policy with 2 lookups and 0 updates. What's the nearest measured ΔP50 in Table 1?
Show answer
80 + 30(2) + 10(0) = 140 ns predicted ΔP50. Table 1 reports total P50 latencies alongside ΔP50 — they're not the same column: lookup_update and adaptive_channels both show a total P50 of 140 ns, but their ΔP50 (the added overhead over baseline) is +120 ns each, not +140 ns. The nearest measured ΔP50 to this prediction is slo_enforcer at +130 ns.Misconception: that overhead is a single fixed eBPF "tax," or that a table's total-P50 and ΔP50 columns are interchangeable. Overhead scales with map operations, and it's ΔP50 — not total P50 — that the model predicts.
Problem 3 · hard
The one-channel (bad_channels) policy passes the verifier cleanly but causes 87–95% throughput degradation. Does this mean the verifier failed?
Show answer
No — the verifier's job is memory safety and bounded execution, both of which this policy satisfies; it never crashes or hangs. It's simply a bad decision, which NCCLbpf's threat model explicitly excludes ("the system does not protect against... semantically incorrect decisions"), alongside TCB bugs, resource exhaustion, and side channels. Semantic validation remains the operator's responsibility.Misconception: that "verified" means "correct," "good," or exhaustively safe. The verifier rules out crashes, memory corruption, and non-termination for verified policy bytecode under the runtime's trusted assumptions — nothing about whether the decision is wise, and nothing about bugs in the trusted runtime itself.
Problem 4 · medium
Why can't a verifier alone (checking one program, one execution) guarantee that all NCCL ranks select the same algorithm?
Show answer
A verifier's proof is scoped to a single program's single run — it never sees the other ranks or their inputs. Distributed agreement is a cross-execution property (all ranks' outputs must match), which is outside what any single-execution verifier can observe. NCCLbpf instead adds static taint analysis: it doesn't check agreement directly, but guarantees agreement indirectly by rejecting any policy whose output could depend on an input that differs across ranks.Misconception: that a stronger verifier would eventually catch this. It's a category mismatch — no amount of single-execution analysis observes multi-execution behavior; a structurally different check (taint tracking of input provenance) is required.
Problem 5 · easy
Why is hot-reload's user-visible downtime 1.07 µs and not the full ~9.4 ms reload time?
Show answer
Verification and JIT-compilation (the bulk of the 9.4 ms) happen off to the side on the replacement program, while the old policy keeps serving every call normally. Only the final atomic compare-and-swap of the function pointer — 1.07 µs — is on the path any caller could observe.Misconception: that reloading a policy means pausing the system for the whole reload. Only the instant of the pointer swap is shared with live traffic.
Problem 6 · medium
Why do eBPF maps require fixed-size keys/values, and why is that an acceptable trade-off for NCCL specifically?
Show answer
Fixed-size maps let the verifier bound memory access statically at load time — a variable-size structure couldn't be proven safe without runtime checks the verifier can't perform (T2 in the paper). It's an acceptable trade-off here because NCCL policy state is inherently simple: per-communicator scalars like latency and channel count, which fit fixed-size entries naturally.Misconception: that this constraint is a missing feature to be added later. It's structural to how the verifier proves safety — relaxing it would mean giving up static verification, not just an engineering gap.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Does the verifier guarantee my policy makes good decisions?▾
No. For verified policy bytecode, it rules out memory-safety violations and non-termination under the runtime's trusted assumptions — it says nothing about whether the decision itself is good, and it doesn't cover bugs in the trusted runtime, resource exhaustion, or side channels. A policy can pass verification and still be a bad idea, like the one-channel policy that degrades throughput 87–95% while remaining perfectly memory-safe.
Q2Why can't a kernel-style eBPF verifier ensure distributed consistency?▾
A verifier proves properties of one program on one execution. NCCL needs agreement across ranks (multiple executions), which is a different kind of property — NCCLbpf adds static taint analysis specifically to bridge this gap.
Q3What is bpftime, and why userspace instead of kernel eBPF?▾
bpftime is a userspace eBPF runtime with an LLVM-based JIT, a PREVAIL-based verifier, and a map subsystem. It runs inside NCCL's own process, with no kernel privileges or kernel modules required — essential since NCCL is an ordinary user process.
Q4What happens if a hot-reloaded policy fails verification?▾
The compare-and-swap never happens; the old policy continues uninterrupted. The system never enters an unverified state.
Q5Why does the tuner fill a cost table instead of returning an algorithm ID?▾
NCCL's tuner API evolved from simple integer outputs in early plugin versions (v2) to a 2D cost table in later versions (v5): the tuner edits a cost per (algorithm, protocol) pair — 0 = preferred, 1e9 (sentinel) = disallowed — letting NCCL gracefully fall back if a combination turns out unavailable at runtime.
Q6Does NCCLbpf modify NCCL's source code?▾
No. It operates entirely within NCCL's existing plugin ABI (ncclTunerPlugin_v3/v5, ncclProfilerPlugin_v1/v6) — no source changes, no custom builds, no kernel modules.
Q7Is 80–130 ns of overhead significant?▾
Against a ~394 µs 128 MiB 8-GPU AllReduce, 130 ns is about 0.03% — well below measurement noise for messages ≥4 MiB. It's only visible in dedicated microbenchmarks.
Q8Can this approach work on AMD GPUs?▾
The paper notes RCCL (AMD's NCCL equivalent) exposes a structurally similar plugin architecture, suggesting a cross-vendor port is feasible — this is discussed as future direction, not implemented.
