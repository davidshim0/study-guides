SOSP 2026 · A Field Guide

Nobody should wait for whoever's link is slowest — let every GPU stream

Mixture-of-Experts inference splits experts across GPUs and syncs every one of them, every layer, at a hard collective barrier. This is the plain-English story of StreamEP, which deletes that barrier and lets tokens flow like water instead of marching in lockstep.

📄 "StreamEP" · Liang, Wang, Song, Zhou, Kim, He, Park 🎓 Some distributed-GPU-serving basics assumed — the primers cover them ⏱ ~30 min read
🌊

Let each GPU START on tokens that have ARRIVED — not WAIT for the ones still in flight.
Queue what's late; compute on what's ready; forward the result immediately.

Quick glossary — the acronyms you'll see everywhere

1What Mixture-of-Experts actually computes▾

A dense transformer layer runs every token through the same feed-forward network. An MoE layer instead has many parallel "expert" networks and a small router that picks the top-k experts for each token (GPT-OSS-120B: 128 experts, top-4; GLM-4.5-Air: 128 experts + 1 shared, top-8). This lets total parameters grow into the hundreds of billions while each token only touches a small slice of them.

Now you're ready: because different tokens want different experts, and experts live on different GPUs, every MoE layer needs to shuffle tokens to the right device and back — that shuffle is the whole story of this paper.
2Why decoding is memory-bandwidth-bound, not compute-bound▾

Generating one token at a time (autoregressive decoding) means each step reads the full expert weights from GPU memory to process a comparatively small batch. Throughput hinges on arithmetic intensity: compute-per-byte-moved. Sparse MoE routing already makes each expert's per-step batch small; anything that shrinks it further (like splitting it across pipeline stages) tanks efficiency.

Now you're ready: this is exactly why Pipeline Parallelism (PP) — which divides the batch by N stages — is "counterproductive" for MoE decode (§2.1), while Expert Parallelism (EP) keeps full-size batches per expert.
3Expert Parallelism (EP) — the standard fix▾

EP places a subset of experts on each GPU. Each device processes all tokens routed to its experts using full-size weight matrices — arithmetic intensity stays high no matter how many GPUs you add. Attention is usually replicated (data-parallel), so collectives are confined to two exchanges per MoE layer: dispatch (send tokens to their expert's GPU) and combine (send results back).

Now you're ready: dispatch and combine are implemented as blocking collectives (all-to-all, or all-gather+all-reduce) — and blocking is the problem this paper attacks.
4A collective barrier, and what a straggler does to it▾

A collective (all-to-all, all-gather, all-reduce) is a hard synchronization point: every participating GPU must send and receive its full share before any of them can proceed. If one link is slow or one GPU is late, the whole collective — and therefore every GPU in it — waits. This paper calls that slow contributor a straggler, and the wait it imposes on everyone else barrier EP.

Now you're ready: on the paper's 16-GPU cluster, an instrumented all-to-all shows the first, median, and last peer arriving at visibly different times (Fig. 2) — that spread is pure wasted GPU-idle time under a barrier.
5Commodity clusters vs. hyperscaler fabrics▾

Hyperscalers hide the barrier's cost with huge NVLink domains (900 GB/s per GPU) or 400–800 Gbps NICs, plus MoE-optimized stacks that need Hopper-or-newer GPU features (TMA, WGMMA). Most academic and enterprise clusters have neither: pre-Hopper GPUs (A100, L40S), 100–200 Gbps shared NICs, and a mix of PCIe/NVLink intra-node links.

Now you're ready: Table 2's survey found only 21% of academic GPUs are Hopper-or-later and just 5.1% sit in 8-GPU HGX nodes — the hardware the fast stacks need is genuinely scarce.
6Two-batch overlap (TBO) — the leading existing mitigation▾

TBO splits each step's batch into two micro-batches and interleaves them: while micro-batch A does its all-to-all, micro-batch B runs expert compute on a separate stream, and vice versa. This hides communication behind computation — but each micro-batch still hits its own collective barrier, so the slower of the two (compute or comm) still sets the pace, and the maximum speedup is bounded by 1 + C/M (compute time over comm time).

Now you're ready: TBO overlaps the barrier's cost; it never removes the barrier itself. That distinction is exactly what separates it from StreamEP.
7NCCL's point-to-point straitjacket▾

NCCL is the one communication library available on essentially every GPU cluster — but its point-to-point send/recv requires the receiver to already know the sender's rank and exact tensor size before the call, so it can allocate a correctly-sized buffer, and both sides must then launch matched NCCLSend/NCCLRecv kernels for the transfer to complete. Fine for a scheduled collective; awkward when any GPU might send a variable-size batch to any other GPU at an unpredictable moment.

Now you're ready: this mismatch is exactly why StreamInfer needs a dedicated protocol (the two-phase communicator, §4.6) instead of calling NCCL P2P naively.
8Prefill vs. decode, and why they're usually split▾

Serving an LLM request has two phases: prefill (processing the whole input prompt in one compute-bound pass — PP works great here) and decode (generating output tokens one at a time — memory-bandwidth-bound, where EP wins). Because their optimal parallelism strategies differ, production systems often run them on separate GPU pools (prefill–decode disaggregation).

Now you're ready: StreamInfer is a decode-only engine — it's meant to slot into the decode pool of such a disaggregated deployment (§6.7).
The whole story in one place

StreamEP in a nutshell

The problem, the fix, and the numbers it buys.

Serving MoE models across GPUs with Expert Parallelism means every layer runs two collectives — dispatch and combine — and a collective is a hard barrier: all GPUs must finish before any can continue. On commodity clusters with shared, nonuniform PCIe/NIC links, that barrier can consume up to 75% of a layer's execution time, because it always waits for whichever GPU or link happens to be slowest that round.

StreamEP removes the barrier entirely. Instead of collecting the whole batch before computing, each GPU independently receives tokens as they arrive, executes the layer on whatever has arrived, and forwards the results immediately via point-to-point transfers — no waiting for stragglers, no global synchronization point. The paper's system, StreamInfer, realizes this on nothing more exotic than vanilla NCCL, using four mechanisms: per-layer μ-queues that buffer asynchronously arriving tokens; a defragmenting scheduler that decides what to execute next without fragmenting batches or starving requests; batch-reformation optimizations that hide the new per-layer reconstruction cost; and a two-phase communicator that lets any GPU send a variable-size batch to any other GPU at any time over plain NCCL.

The payoff: on a 16×L40S cluster with 200 Gbps inter-node networking, StreamInfer reaches 36 K tokens/s on ShareGPT versus barrier EP's 21 K — a 1.7× improvement — and stays essentially flat under injected network interference that degrades barrier EP by up to 24%, even though that interference consumes only ~7.5% of average bandwidth.

🌊 Key takeaways

  • Barrier EP's dispatch/combine collectives force every GPU to wait for the slowest link or peer, every layer.
  • StreamEP swaps collectives for point-to-point transfers: compute on what's arrived, queue what hasn't, forward what's done.
  • Removing the barrier turns straggler impact from global (everyone stalls) to local (only that token's path is delayed).
  • The idle time barrier EP wastes waiting for late tokens becomes StreamEP's natural batching mechanism — no explicit load balancing needed.
  • Four mechanisms make this real on vanilla NCCL: μ-queues, a defragmenting scheduler, batch-reformation overlap, and a two-phase communicator.
  • Result: up to 1.7× decoding throughput vs. EP, near-constant throughput under interference that costs EP up to 24%, and no Hopper-class hardware required — unlike the specialized EP stacks in Table 1, which only 21% of surveyed academic GPUs (and just 5.1% of HGX-class nodes, 6% of NSF ACCESS GPUs) can even run.
Six everyday pictures

How to think about StreamEP

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks down.

The core idea · Barrier vs. stream

The whole table must be served at once

A rigid kitchen won't send out any dish until every dish for the table is plated — so if one dish is slow, the whole table waits, food cooling. A better kitchen sends each dish the moment it's ready. Barrier EP is the rigid kitchen: dispatch/combine waits for every GPU's data before any device proceeds. StreamEP sends each token group the moment it's cooked.

Where it breaks: a table's dishes are independent; MoE layers aren't — a token's layer-2 attention still needs its layer-1 expert output first. StreamEP pipelines this dependency instead of ignoring it.
Removing the barrier · Local vs. global straggling

Independent streets, not one clogged highway

A jam on one lane of a single-lane highway stops everyone behind it. A grid of independent streets means one clogged block delays only the traffic on that block — everyone else routes around it. Barrier EP is the highway (one straggling link stalls all 16 GPUs); StreamEP is the grid (a straggling link delays only the tokens riding it).

Where it breaks: real street grids let you reroute around a jam entirely; a straggling token still has to eventually arrive at its assigned expert — StreamEP tolerates the delay, it doesn't eliminate it.
Natural batching · μ-queues

Mail piling up in your cubbyhole while you're on a call

While you're busy with one task, mail keeps arriving and stacks neatly in your cubbyhole. When you're free, you process a batch of it at once — no one had to wait for you, and you didn't have to interrupt yourself for each letter. That's a μ-queue: tokens accumulate per layer while the GPU computes something else, forming a natural batch with zero explicit coordination.

Where it breaks: a cubbyhole has no notion of priority — mail sits until you look. μ-queues need an active scheduler (next analogy) deciding which pile to open, or some piles never get touched.
Scheduling · Defragmenting vs. strawmen

Serve the fullest table, or the nearest one?

"Always serve whoever's queue is longest right now" (most-tokens-first) sounds efficient but leaves scraps behind at every other table, scattering your effort thin. "Always serve table 1 first, no matter what" avoids scattering but lets new walk-ins cut the whole line forever. StreamInfer's defragmenting scheduler does neither: it scores each queue by current depth plus a decayed look-ahead down the execution chain, concentrating effort into one advancing wave without starving anyone.

Where it breaks: a host can glance at every table instantly; the scheduler's look-ahead only estimates a few steps ahead (window W) — it's a heuristic, not a crystal ball.
Enforcement · Two-phase communicator

Call ahead before you drive over

You don't show up at a friend's door with an unannounced truckload of furniture — you call first: "I have 3 boxes, here's how big." They clear the space, then you drive over and unload. NCCL P2P needs the same courtesy: the sender's metadata phase tells the receiver how many tensors and what size are coming (via a lightweight CPU message queue), so the receiver can allocate the right buffer before the tensor phase's actual NCCLSend/NCCLRecv fires — all without either side blocking on the other's schedule.

Where it breaks: a phone call is instant; the metadata phase still costs real (if tiny) CPU-side latency, and the sender must throttle how many "trucks" it has in flight to bound memory.
Fragility · Interference amplification

A splash in the bucket everyone drinks from

If sixteen people share one water bucket in strict turn order, spilling just 7.5% of it on one person's turn can still stall the whole line while they wait for a refill — everyone downstream pays for one small spill. If instead everyone has their own cup, that same spill only shorts the person it fell on. Barrier EP's 24% throughput loss from interference that removes only ~7.5% of average bandwidth is exactly this amplification; StreamEP's per-GPU independence contains the damage to the affected link.

Where it breaks: a bucket has one shared resource; the real cluster has many links, so the "spill" in the analogy is really "whichever link is worst that instant" — which link that is keeps changing.
The full explanation

How StreamInfer actually works

Section by section, matching the paper's own structure (§3–§4.6).

1 · Why EP, and why its collectives are the bottleneck

Table 1 in the paper lists nearly every specialized EP communication stack (DeepEP, pplx-kernels, fabric-lib, UEP, NCCL EP, FlashMoE, Comet) — and their hardware requirements vary widely: FlashMoE needs only SM70+ and NVLink, Comet needs SM90+ and NVLink, several TBO-oriented stacks need SM90+ and GPUDirect RDMA, while vanilla NCCL runs on any GPU over any interconnect. None of the specialized stacks remove the barrier; they only overlap or fuse around it. On commodity hardware, dispatch and combine still serialize on whichever GPU or link is slowest — measured at up to 75% of a layer's execution time.

3 · μ-queues and token metadata

An L-layer model keeps 2 × L μ-queues per GPU: one attention queue and one expert queue per layer. Each token carries a compact LayerID triple — <layer#> | <attn. DP rank> | <expert#> — plus a RequestID (needed because async arrival destroys position-based ordering), a reference to its GPU-resident tensor, and its top-k gating weight. The attn. DP rank field never changes for a request's lifetime, guaranteeing it always finds its way back to the GPU holding its KV cache.

4 · The defragmenting scheduler

Two naïve strawmen fail in opposite ways. Most-tokens-first-serve (MTFS) always executes whichever queue is currently fullest — this scatters execution across many layers with small, inefficient batches, because the "last slice" of every layer keeps getting deprioritized by whatever queue just grew bigger. First-layer-first-serve (FLFS) strictly prioritizes the earliest layer — this defragments beautifully but lets a flood of brand-new requests (which always enter at layer 0) permanently starve tokens already deep in the pipeline: livelock.

// score(layer, type) = current depth + decayed lookahead down the chain
score = Q[l][t]
for k in 1..W:
    (l, t) = next(l, t)                 // attn → expert → next layer's attn
    occ = Q[l][t] + sum(drained_last_B_steps[l][t])
    score += occ * δ^k                // exponential decay, δ < 1
pick (l*, t*) = argmax score
💡
Why blend current depth with drained history? A queue that was just drained looks momentarily empty, but its co-runners are likely still feeding it — counting recently drained tokens keeps the scheduler from abandoning an active wave the instant it dips.

5 · The two-phase communicator

Because scheduling is asynchronous, any GPU may need to send a variable-size batch to any other GPU at an unpredictable moment — the opposite of NCCL's expectations. StreamInfer splits each transfer into two phases.

6 · Hiding batch reformation behind computation

Because tokens land at scattered GPU memory locations, every layer needs a reformation kernel to gather them into a contiguous batch before computing — a cost barrier EP never paid, since its collectives delivered contiguous batches for free. StreamInfer hides most of this: while the GPU computes μ-batch i−1, the CPU concurrently schedules and prepares μ-batch i's metadata via GDRCopy, so the GPU can launch reformation + compute for batch i the instant batch i−1 finishes.

Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own reported figures.

① The TBO speedup bound, and why it's optimistic

The paper bounds ideal two-batch-overlap speedup as T_ideal_TBO ≤ T · (C+M)/max(C,M). On Sphere's communication-bound setup, the paper reports C/M ≈ 0.33.

  1. Communication-bound means M > C, so max(C,M) = M.
  2. Simplify the bound: (C+M)/M = 1 + C/M = 1 + 0.33 = 1.33×. This ceiling is TBO's speedup over its own non-overlapped, single-micro-batch throughput — not a comparison against StreamInfer.
  3. That's the absolute ceiling for TBO on its own terms — even with zero interference between the overlapped communication and compute kernels.
  4. StreamInfer separately measures 1.4× throughput over the projected EP-TBO baseline itself on ShareGPT (36 K vs. 25 K tok/s). This is a different ratio with a different denominator than the 1.33× above — the 25 K figure is EP-TBO's projected throughput after applying its own overlap benefit, so "36 K/25 K = 1.4×" isn't "StreamInfer beating TBO's 1.33× ceiling" in any direct sense. What it does show is that StreamInfer still comfortably outperforms the already-optimistic EP-TBO projection.
  5. Why: TBO still pays a full collective barrier per micro-batch; StreamEP never pays one at all. A real TBO implementation would fall further short of both its own 1.33× ceiling and the 25 K projection, making StreamInfer's true advantage larger still.

② Reading Sphere's headline throughput numbers

StreamInfer: 36 K tok/s (ShareGPT) and 40 K tok/s (GSM8k). Barrier EP: 21 K and 28 K tok/s.

  1. ShareGPT ratio: 36,000 ÷ 21,000 = 1.71× — matches the paper's headline "up to 1.7×."
  2. GSM8k ratio: 40,000 ÷ 28,000 = 1.43× — smaller gain.
  3. Why the gap between datasets? GSM8k has shorter, more uniform sequences than ShareGPT's high length variance — shorter, uniform sequences produce less skewed dispatch/combine volume, so barrier EP's straggler penalty is naturally smaller to begin with, leaving less room for StreamEP to reclaim.
  4. Sanity check on Delta: 25 K ÷ ~19K(EP, backed out from 1.3× ratio) ≈ 1.3×, and 31 K ÷ ~20.7K ≈ 1.5× — smaller than Sphere because Delta's 4×4 NVLink topology hides more inter-node hops behind fast intra-node links.

③ Compounding the ablation gains

Ablation baseline: MTFS scheduling, no batch-reformation optimizations, no CPU–GPU overlap.

  1. MTFS → +Defrag: the paper reports a 3.2× throughput jump — the single largest contributor, because MTFS's fragmented tiny batches waste arithmetic intensity.
  2. +Defrag → +Defrag+Opt (full StreamInfer): batch-reformation optimizations and CPU–GPU overlap add a further 4.5%.
  3. Total multiplier over the MTFS baseline: 3.2 × 1.045 = 3.34×.
  4. Interpretation: getting the scheduling policy right matters an order of magnitude more than shaving overhead — but the overhead-shaving still compounds on top of it, not instead of it.

④ End-to-end makespan sanity check

Table 5: serving 5,000 ShareGPT requests. Prefill (profiled separately): 12.4 s. Total makespan: SGLang EP 171 s, StreamInfer 96 s.

  1. Decode-only time for EP: 171 − 12.4 = 158.6 s.
  2. Decode-only time for StreamInfer: 96 − 12.4 = 83.6 s.
  3. Decode-only ratio: 158.6 ÷ 83.6 = 1.90× — even higher than the 1.7× headline decoding-throughput number, since removing the fixed 12.4 s prefill isolates decoding more precisely.
  4. Total makespan ratio (what a user actually experiences, prefill included): 171 ÷ 96 = 1.78×, close to the paper's reported "about 1.7× faster."
  5. Takeaway: because prefill is a small, fixed, compute-bound cost, StreamInfer's decode-side speedup survives almost intact into end-to-end serving time — but only for decode-heavy workloads (§6.7's explicit caveat).
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Removing the collective barrier means batches are no longer delivered whole — shouldn't that make every execution smaller and less efficient, hurting throughput?
Show answer
No — the paper argues the opposite happens. Under barrier EP, a GPU idles after early tokens arrive, waiting for the rest. Under StreamEP, that same idle interval becomes productive: the GPU computes on early arrivals while later tokens queue in μ-queues, forming the next batch with zero explicit synchronization. The spread in arrival times that used to be wasted idle time becomes the batching mechanism itself.Misconception: that asynchronous arrival necessarily means smaller, less-efficient batches. It only does that if nothing buffers the early arrivals — μ-queues are precisely what prevents that.
Problem 2 · medium
Suppose a redesigned TBO pipeline has per-micro-batch compute time C = 80 μs and communication time M = 240 μs. What's the ideal TBO speedup ceiling, and is it achievable in practice?
Show answer
M > C, so the bound is (C+M)/M = 1 + C/M = 1 + 80/240 = 1 + 0.33 = 1.33×. This is a ceiling assuming perfect, zero-interference overlap between the concurrent micro-batches' kernels. In practice, pipeline fill/drain, kernel interference on shared SMs, and lower per-micro-batch kernel efficiency (half the batch size) all pull real TBO implementations below this ceiling — which is exactly why the paper compares against the optimistic projection rather than a real TBO run, and still shows StreamInfer ahead.Misconception: that the bound itself is achievable. It's a theoretical maximum; real systems fall short of it, making the true StreamEP-vs-TBO gap even larger than the paper's conservative comparison shows.
Problem 3 · hard
Interference consuming only ~7.5% of average bandwidth degrades barrier EP's throughput by up to 24%. Explain the mechanism behind this disproportion.
Show answer
A collective's completion time is set by its worst instantaneous link, not its average bandwidth. Even a brief interference spike on a single link — which barely dents the cluster-wide average — forces every other GPU in the barrier to wait for that one link to recover before the whole collective (and hence every GPU's next layer) can proceed. Average bandwidth loss and worst-case delay are different quantities; the barrier is exposed to the latter, not the former. Separating TCP control traffic onto a different NIC from NCCL's RoCE datapath doesn't fix it either, confirming the bottleneck is structural (the collective itself), not a NIC contention artifact.Misconception: that throughput impact should scale roughly with the fraction of bandwidth lost. Under a hard barrier, a small, localized spike can have an outsized, cluster-wide effect because everyone waits for the single worst link.
Problem 4 · medium
Construct a short scenario where first-layer-first-serve (FLFS) scheduling causes livelock, and explain why the defragmenting scheduler avoids it.
Show answer
Under FLFS, layer 0 (where every new request's tokens first enter) always outranks every other layer, no matter how full those other layers' queues are. If requests arrive continuously at a high rate, layer 0's queue is perpetually replenished by new arrivals, so the scheduler never "runs dry" there and never moves on to drain layers 1, 2, 3… — tokens already deep in the pipeline wait forever. The defragmenting scheduler avoids this because its score for each (layer, type) blends current occupancy with a decayed look-ahead down the execution chain, so a heavily-loaded downstream layer with recently drained tokens can out-score layer 0, so the wave keeps advancing instead of getting pinned at the entry point.Misconception: that "always prioritize the earliest stage" is a safe way to defragment. It defragments well under moderate load but is vulnerable to starvation whenever new arrivals can outpace draining — precisely the high-request-rate regime that matters for throughput-optimized serving.
Problem 5 · easy
Why can't a GPU just call NCCLSend the moment its output tokens are ready for some other GPU, at any time?
Show answer
NCCL's point-to-point API requires the receiver to already know the sender's rank and the exact tensor size before it can post a matching NCCLRecv — otherwise it can't allocate a correctly-sized receive buffer — and both sides must then launch matched send/recv kernels for the transfer to complete. Under StreamEP, any GPU may need to send a variable-size batch to any other GPU at an unscheduled moment, which violates NCCL's buffer-size-agreement expectations. The two-phase communicator solves this by having the sender announce size and rank via a lightweight CPU message queue first (Phase 1), so the receiver can prepare its buffer before the actual NCCL transfer (Phase 2) launches.Misconception: that NCCL's collective-oriented P2P calls are naturally suited to ad-hoc, unscheduled transfers. They're built for scheduled, size-known exchanges — asynchronous serving needs an extra negotiation layer on top.
Problem 6 · easy
For what kind of workload would StreamInfer's decoding speedup translate into essentially no end-to-end benefit?
Show answer
An extremely prefill-heavy or prefill-only workload (e.g., a single-pass LLM binary decision on a long input, with little or no generated output). §6.7 shows that prefill is already fast and compute-bound (12.4 s / 8.8 s for 5,000-request batches, versus 96–171 s of decoding) — StreamInfer only accelerates the decode phase, so if a workload spends almost all its time in prefill, there's little decode time left to speed up.Misconception: that a 1.7× decoding speedup always means a 1.7× end-to-end speedup. It only approaches that when decoding dominates total serving time — the paper is explicit that decode-heavy and moderately-prefill-heavy workloads benefit; prefill-dominated ones won't.
Problem 7 · medium
GLM-4.5-Air's speedup over EP widens from ~1.2× (full 46-layer model, low concurrency) to 1.3–1.4× (halved 23-layer model, roughly double concurrency). Why does StreamInfer's advantage grow with concurrency while EP's shrinks?
Show answer
StreamInfer pays a fixed per-layer overhead (scheduling, batch reformation, metadata transfer) each step; larger concurrency means larger batches, which amortize that fixed cost better — so its efficiency improves with scale. Barrier EP does the opposite: larger concurrency means more tokens must cross the same collective every layer, which amplifies per-layer collective volume and, combined with the barrier waiting on the slowest transfer, actually degrades EP's throughput at higher concurrency. The two systems' overheads move in opposite directions as concurrency rises, which is why the gap between them widens.Misconception: that both systems should scale similarly with more concurrent requests. EP's collective-based design makes more concurrency actively harmful past a point; StreamInfer's queue-based design makes more concurrency actively helpful.
Problem 8 · hard
On Delta (4×4 A100, NVLink intra-node) StreamInfer's advantage over EP (1.3–1.5×) is smaller than on Sphere (1.4–1.7×), even though both clusters have 200 Gbps inter-node networking. Why?
Show answer
Two structural differences. First, A100's smaller memory (40 GB vs. L40S's 48 GB) caps batch concurrency lower, which reduces cross-node traffic and shrinks the communication bottleneck StreamEP is designed to route around. Second, Delta's 4-GPUs-per-node NVLink topology means only the 4 inter-node NIC hops (one per node) can gate a step, with intra-node traffic riding fast NVLink; on Sphere, all 8 PCIe links and 8 shared NICs run at comparable, more uniform speeds, so any of many hops can become the bottleneck — precisely the "nonuniform and shared interconnect" scenario StreamEP targets. Fewer, faster-hidden bottleneck links means less barrier-serialization for StreamEP to eliminate.Misconception: that identical inter-node bandwidth numbers (200 Gbps on both clusters) predict identical gains. The gain depends on how uniform the whole interconnect is and how much of the path is masked by fast intra-node links, not just the inter-node NIC spec.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1Is StreamEP removing the network, or just the software barrier?▾
Just the software barrier. The physical network — the same 200 Gbps RoCE/Slingshot links, the same shared PCIe/NICs — is untouched. StreamEP changes how software uses that network: instead of a synchronous all-to-all/all-gather that forces every participant to wait, it uses asynchronous point-to-point sends so each GPU proceeds as soon as its own data is ready.
Q2Doesn't asynchronous, out-of-order token arrival risk mixing up which token belongs to which request?▾
No — every token carries a persistent RequestID plus a LayerID that encodes exactly which layer, attention DP rank, and (if applicable) expert it's headed for. Since position-based ordering is meaningless once tokens can arrive in any order, this explicit metadata is what makes reassembly correct regardless of arrival order.
Q3Why can't most people just buy Hopper GPUs and NVLink fabric to sidestep this whole problem?▾
Because that hardware is genuinely scarce outside hyperscalers. The paper's survey of major U.S. academic HPC clusters (Table 2) found only 21% of available GPUs are Hopper-or-later, and just 5.1% sit in 8-GPU HGX-class nodes; only 6% of NSF ACCESS GPUs meet DeepEP's requirements. Commercial clouds are similarly uneven — AWS EFA supports some optimized stacks only on P5 instances, and GCP's GPU networking support varies sharply by instance type.
Q4What stops the defragmenting scheduler's newest requests from starving the tokens already in flight?▾
That's specifically the failure mode of the FLFS strawman, which the real scheduler avoids by not strictly prioritizing the earliest layer. Its score blends each queue's current depth with a decayed look-ahead down the execution chain, so a heavily-loaded, actively-advancing wave downstream can out-score layer 0's queue — new arrivals accumulate there without permanently blocking older tokens' progress.
Q5Does StreamEP change the model's outputs or numerical results?▾
No. StreamEP changes the scheduling and communication of MoE decoding, not the math each layer computes. Tokens still go to exactly the experts the router assigns them to (top-k routing is preserved via one copy dispatched per assigned expert, §4.3), and top-k merge weighting is applied identically — the paper is a systems contribution, not a model-architecture change.
Q6Why is StreamInfer's advantage smaller on Delta (A100/NVLink) than on Sphere (L40S/PCIe)?▾
Delta's smaller per-GPU memory caps concurrency (and thus cross-node traffic), and its 4-GPUs-per-node NVLink topology means fewer, faster-hidden inter-node hops can bottleneck a step. Sphere's 8 uniform PCIe/NIC hops all run at comparable speed, so any one of many links can straggle — the exact scenario StreamEP is built to tolerate — giving it more room to help there.
Q7How is StreamEP fundamentally different from two-batch overlap (TBO)?▾
TBO overlaps one micro-batch's communication with another's computation, hiding the barrier's cost behind concurrent work — but each micro-batch still fully waits at its own collective barrier before proceeding, and the achievable speedup is capped at 1 + C/M. StreamEP removes the barrier itself: there is no point at which a GPU waits for the whole batch to arrive before computing.
Q8Why does StreamInfer use GDRCopy instead of ordinary CUDA memcpy for CPU–GPU metadata transfers?▾
Per-layer scheduling requires many small, frequent host–device transfers (KV-slot allocation, per-token metadata for paged attention, gating weights and expert indices copied back to the CPU). GDRCopy offers lower per-transfer latency than standard CUDA memcpy for exactly this pattern of small, frequent copies, which matters because these transfers happen every layer, not once per request.
Q9Is StreamInfer a complete serving stack, including prompt processing?▾
No — StreamInfer is a decode-only engine. It's meant to be deployed as the decoding worker in a prefill–decode disaggregated architecture, with a separate system (e.g., SGLang for prefill, Mooncake-style KV-cache transfer) handling prompt processing and handing off the resulting KV cache.
Q10How much new engineering did removing the barrier actually require?▾
The performance-critical components — communicator, receptor, scheduler, and dispatcher — are about 9,000 lines of C++, exposed to a Python model executor via pybind11. The scheduler and executor run in the main Python thread; the receptor and dispatcher run on dedicated POSIX threads with their own CUDA streams, which is also how they sidestep Python's GIL to overlap communication and computation.
Q11What happens to "shared experts" that every token must pass through?▾
Some MoE architectures (e.g., DeepSeek-style models) add shared experts that process every token in addition to its top-k routed experts. StreamInfer executes shared experts under data parallelism immediately after attention, on the same GPU, before dispatching token copies onward to the routed experts — no cross-GPU communication needed for that part.
Q12Does StreamEP have anything to say about the prefill phase or training?▾
Not directly. The paper's case for EP specifically concerns decoding, where sparse per-token compute makes arithmetic intensity fragile; prefill is compute-bound and already served well by pipeline parallelism, so prefill–decode disaggregation (not StreamEP) is the paper's answer there. Training is out of scope entirely — StreamInfer targets throughput-optimized inference serving.

Glossary & further reading

Core terms
StreamEPThe paper's paradigm: remove the EP collective barrier, letting each GPU independently receive, compute, and forward tokens as they arrive.
Barrier EPStandard expert parallelism using blocking dispatch/combine collectives — every GPU must finish before any can proceed.
StreamInferThe serving system that realizes StreamEP on vanilla NCCL, using μ-queues, a defragmenting scheduler, batch-reformation overlap, and a two-phase communicator.
μ-queueA per-layer, per-type (attention or expert) queue that buffers tokens arriving asynchronously from any peer.
LayerIDCompact routing metadata per token: <layer#> | <attn. DP rank> | <expert#>, used to select the right μ-queue and destination GPU.
Defragmenting schedulerSelects which (layer, type) queue to execute next by combining current depth with a decayed look-ahead, avoiding both fragmentation (MTFS) and livelock (FLFS).
Two-phase communicatorA protocol layered on NCCL P2P: a CPU-side metadata exchange (Phase 1) followed by an async GPU tensor transfer (Phase 2), enabling variable-size, unscheduled transfers.
Batch reformationGathering scattered, individually-arrived token tensors into one contiguous buffer before launching a layer's kernels.
Supporting terms
MoE / EP / TP / PPMixture-of-Experts; Expert / Tensor / Pipeline Parallelism — the three strategies for sharding a model across GPUs.
Dispatch / CombineThe pair of collectives per MoE layer: sending tokens to their expert's GPU, and returning expert outputs.
StragglerA slow GPU or link that, under a collective barrier, delays every other participant.
TBO (Two-Batch Overlap)Splits a batch into two micro-batches, overlapping one's collective with the other's compute; still barrier-bound per micro-batch.
Attn. DP rankThe data-parallel rank holding a request's replicated attention weights and KV cache; a token's LayerID always routes it back here for attention.
GDRCopyA low-latency host–device copy library used for the frequent, small CPU–GPU metadata transfers StreamInfer's per-layer scheduling requires.
ITLInter-Token Latency — the metric used alongside throughput to characterize decoding responsiveness.
Prefill–decode disaggregationRunning prompt processing and token generation on separate GPU pools, each using its best-fit parallelism strategy.
