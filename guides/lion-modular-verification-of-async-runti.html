Proving a scheduler never forgets a task — not just that it doesn't crash

Async runtimes promise that a yielded task will eventually wake up. That promise is a temporal property no deductive verifier speaks natively. Lion proves it anyway, by turning "eventually" into a fact about positions in a log.

📄 Zhou, Zhang, Chowdhury, Mu · SOSP '26 · Stony Brook 🦀 Tokio-compatible runtime, verified in Verus/Rust ⏱ ~30 min read
📜

Don't ask the verifier to reason about □always / ♢eventually. Ask it about ∃j>i. L[j]=B — a later index in an append-only log.

Before you begin

Quick glossary, then eight primers

This paper sits at the intersection of async runtimes and deductive program verification — neither is your home turf, so we ground both before the real argument. Acronyms first, then the concepts they name.

1Tasks, futures, and polling▾

An async task is compiled from an async fn into a state machine (a Future) whose states are its .await points. The runtime drives it by calling poll(): if the awaited resource is ready, execution advances toward Ready; if not, poll() returns Pending and the task must be re-polled later.

A task may return Pending many times before finishing — nothing forces it to make progress on any one call. That's exactly the gap the liveness proof has to close.

Now you're ready: Lion's central claim is a fact about repeated poll() calls — but it's conditional, not unconditional: provided the awaited event fires within a bound, the task keeps its resource registered until woken, and task IDs stay unique, every task that returns Pending gets polled again within a bounded number of further calls.
2Executor, reactor, and wakers▾

The executor owns task queues and calls poll(). The reactor watches OS-level events (timers, sockets) and, when one fires, invokes a waker — a callback that re-enqueues the waiting task. Utility modules (channels, semaphores) implement the same wake pattern for purely in-process conditions.

Every one of these is a hand-off: a task's fate is passed from executor to reactor (or to another task) and back. A lost hand-off is a silently stalled task.

Now you're ready: the paper's proof structure — one contract per module, chained together — exists to cover every one of these hand-offs.
3epoll/io_uring — OS readiness, briefly▾

You already know these from the kernel side: epoll and io_uring let a thread block on "tell me when any of these descriptors is ready" instead of polling each one. The reactor is a thin userspace layer on top — it registers interest, blocks in park(), and turns each readiness notification into a waker call.

Now you're ready: Lion's reactor liveness contract — "a registered event eventually fires a wakeup" — is machine-checked for the runtime logic built on top of epoll/mio, but the OS/mio/epoll/timer syscalls themselves stay in the trusted base: Lion assumes the kernel actually delivers readiness notifications, it doesn't verify epoll's own semantics.
4Safety vs. liveness — two different promises▾

Safety: nothing bad ever happens (no crash, no data race, no use-after-free). Liveness: something good eventually happens (the task resumes). Safety violations are witnessed by a finite bad prefix — a crash trace. Liveness violations have no finite witness: a stalled task looks identical to a slow one, forever.

Now you're ready: this is why the bugs in §2.2 are so nasty — Issue 5020 stayed open over a year precisely because nothing crashed.
5Hoare contracts vs. temporal properties▾

Verus checks Hoare-style contracts: given a precondition requires before a function call, prove a postcondition ensures after it returns. That's inherently local — one function, one call. Liveness properties like "T is eventually polled" span an unbounded sequence of separate function calls, with no single call whose postcondition can state it.

Now you're ready: the whole methodology exists to translate that unbounded, cross-call obligation back into something a single postcondition can state — an assertion about log positions.
6Deductive verification & SMT, in one paragraph▾

Verus is a deductive verifier for Rust: you annotate functions with pre/postconditions and loop invariants, and it translates the resulting proof obligations into formulas an SMT solver (satisfiability modulo theories — quantifiers, arithmetic, arrays) can automatically discharge. It has no built-in notion of "eventually" — only first-order implications and quantifiers.

Now you're ready: Lion doesn't extend Verus. It re-expresses temporal claims as ordinary ∃/∀ statements over log indices, so the existing SMT machinery just works.
7Ghost state — proof-only bookkeeping▾

A ghost variable exists only for the proof: it's updated alongside real code, reasoned about in specifications, and erased entirely at compile time — it costs zero at runtime. Verus enforces this separation so ghost bookkeeping can never influence real control flow.

Now you're ready: Lion's event log is a ghost variable. It never runs in the compiled binary; it exists purely so the proof has something to quantify over.
8Thread-per-core vs. work-stealing▾

Two scheduling philosophies you've likely seen on the OS-scheduler side too. Work-stealing (Tokio's default): idle worker threads pull tasks off busier threads' queues, sharing a reactor and timer wheel — good load balance, costs synchronization. Thread-per-core (Lion, Monoio, Glommio, Seastar): one executor, one reactor, no shared state per core — cheap and easy to reason about, but a heavy task pins its core with nowhere to steal from.

Now you're ready: Lion's verified core is single-threaded by design — that's what makes per-module isolation (and the whole proof) tractable — with multi-core support via independent per-core instances, not shared-state work-stealing.
The whole story in one place

Lion in a nutshell

The temporal-logic obstacle, the log-based fix, and how modules compose into one end-to-end guarantee.

Every async runtime makes an implicit liveness promise: if a task yields waiting for an event, the runtime eventually resumes it once that event fires. Formally that's □∀t. event_fired(t) → ♢is_completed(t) — a temporal statement spanning the entire, unbounded execution. Verus, like most deductive verifiers, reasons in Hoare logic: pre/postconditions attached to individual function calls. There is no □ or ♢ to write down.

Lion's fix is to stop trying to state "eventually" directly. Instead, each module maintains a ghost, append-only event log recording the abstract actions it performs. Because the log only grows, its indices are timestamps: "event A is eventually followed by event B" becomes ∃j>i. L[j]=B — an ordinary first-order statement Verus already knows how to check. This is a Kamp-style translation of LTL into FOL, exploiting the fact that a single-threaded runtime's execution is a deterministic, linearly ordered sequence.

Each module's obligation is packaged as an async contract: an acceptance event (a task enters this module's care), a fulfillment event (the module discharges its duty), and an assumption (environmental preconditions, e.g. the clock keeps advancing). Contract chaining — one module's fulfillment triggers the next module's acceptance — composes bounded local guarantees into one bounded end-to-end guarantee, with no need to reason about concurrent interleavings, since a single-threaded runtime has none.

The payoff: Lion, a Tokio-compatible Rust runtime verified this way in Verus, is proved to never forget a task under its stated environment and calling-convention assumptions, catches 3/3 confirmed liveness bugs that hang Tokio/libevent/libuv under stress, and reaches 99–119% of Tokio's throughput on the nine real-app workloads it measures (the paper's abstract cites at least 95% as its broader headline figure) — for roughly 11.7× as much proof text as verified executable code.

🍯 Key takeaways

  • Hoare contracts describe one call; liveness spans unbounded calls — that mismatch is the whole problem.
  • An append-only ghost log + Kamp's theorem turns "eventually" into ∃j>i. L[j]=event — plain FOL.
  • Async contracts (acceptance, fulfillment, assumption) package one module's bounded leads-to guarantee.
  • Contract chaining composes modules without any interleaving search — single-threaded execution is deterministic.
  • The guarantee is conditional: environment behaves, user tasks behave, and the log is honestly append-only (trusted, not proven).
  • Lion instantiates this for a Tokio-compatible executor + reactor + utilities, with 30 module invariants and 21 cross-module predicates.
  • Result: never forgets a task under its stated assumptions, 3/3 on a bug-derived stress test, 99–119% of Tokio's throughput on nine workloads, <1 exec LOC per proof-effort ratio-inverse (11.7× spec/proof to verified code).
Seven everyday pictures

How to think about Lion's proof machinery

Each stands alone; every card ends with an honest note on where it stops being true.

The core idea · Event log

A logbook with numbered pages

Instead of arguing "the ship will eventually reach port," a captain's log lets you point at page 47 and say "there it is." Ordering is free: page 12 happened before page 47 just because 12 < 47. Lion's event log is the same trick applied to a scheduler — indices replace time.

Where it breaks: a real logbook can be torn out or forged. The append-only property that makes indices trustworthy is assumed, not proven — it's enforced by a small trusted wrapper, not checked by the verifier (§5.2).
One module's promise · Async contract

An IOU

You accept a loan (acceptance): the lender's condition is that you keep your job (assumption). In return you promise to repay within, say, 12 installments (fulfillment, bounded). Every module in Lion signs one of these for every task it takes in — a timer registration, a queued task, a stored waker.

Where it breaks: a real IOU can be broken with no formal consequence beyond reputation. An async contract is a proof obligation — Verus's build simply fails if a module can't discharge it, so it can't ship broken.
End-to-end · Contract chaining

Relay-race baton passes

Each runner (module) only has to guarantee finishing their own leg within a bounded distance. Handing off the baton — one module's fulfillment triggering the next module's acceptance — lets you bound the whole race by simply adding the legs: n₁ + n₂.

Where it breaks: relay racers can drop the baton with no one noticing until it's too late. Lion's 21 cross-module predicates exist precisely to prove the baton (the task) really did land in the next runner's hand — that's the extra proof work composition costs.
The theoretical engine · Kamp's theorem

Translating a promise into a dated contract clause

"You'll eventually get your delivery" is unenforceable in court. "Delivery will occur on a date recorded in the shipping log after today" is a clause a judge (verifier) can check mechanically. Kamp's 1968 theorem says this translation is always possible for temporal logic over a discrete, linear timeline — exactly what a single-threaded execution log is.

Where it breaks: Kamp's theorem needs a linear, discrete order. It wouldn't translate cleanly for branching time or genuinely concurrent (non-deterministic) execution — which is exactly why Lion's verified core stays single-threaded.
Compile-time erasure · Ghost state

A referee's private notebook

The referee tracks fouls in a notebook the players never see and that has no effect on the game itself — it exists purely so the match can be reviewed afterward. Lion's event log is exactly this: a ghost variable, updated in lockstep with real code, erased entirely at compile time, invisible to the running binary.

Where it breaks: if the referee's notebook can be secretly edited, review is worthless. That's why the log's append-only guarantee is deliberately placed in the small trusted base (§5.2) rather than left to the referee's word.
Well-founded induction · Ranking function

Counting down a fuse

A task waiting on a wakeup needs at most cap more polls before reaching Ready; each trip around Pending→Runnable→Polled burns one unit off that count, like a fuse that only ever shortens. It can't relight, so it must hit zero — that's the well-founded induction behind §4.4's cross-module argument.

Where it breaks: the fuse only bounds tasks that behave — one whose poll() genuinely loops forever has no fuse to count down, and the framework explicitly excludes it as a user-task assumption, not a proof (§5.2).
Deployment model · Thread-per-core

One cashier per checkout lane

Thread-per-core assigns each customer (connection) to one register for their entire visit — no coordination cost, but a slow customer blocks that whole lane. Work-stealing lets any idle cashier grab a waiting customer from a busy lane, at the cost of coordinating who's idle.

Where it breaks: the analogy suggests stealing is instant. In practice Tokio parks idle workers, so "grabbing" a queued customer first requires waking a napping cashier — up to tens of milliseconds at low load (§7.3), which is exactly the gap Lion's always-resident reactor avoids.
The full explanation

How the proof actually works

Section by section, from the log encoding to the composed end-to-end theorem.

1 · Why Hoare contracts alone can't state the property

Verus checks requires/ensures pairs attached to a single function call. The runtime's promise — every task that yields is eventually resumed — ranges over an unbounded sequence of poll()/wake calls, none of which has a postcondition that can name "eventually." The paper's fix does not add temporal operators to Verus; it removes the need for them.

2 · The event log and the progress invariant

Each module keeps a ghost, append-only log L of abstract events. A step is one unit of driving (one tick for the executor, one park cycle for the reactor). A progress_inv(L) is an inductive invariant — true before a step implies true after — asserting local liveness facts like cached ⇒ poll: if the cache is non-empty after popping, a Poll event appears before the tick ends.

fn tick(&mut self)
    requires progress_inv(old(self).log@), queue_matches_log(old(self).cache@, old(self).log@)
    ensures  progress_inv(self.log@),        queue_matches_log(self.cache@, self.log@)
{
    self.log = Ghost(self.log@.push(Tick(Begin)));
    // ... pop from input queue into cache ...
    if !self.cache.is_empty() {
        // helper invariant: non-empty cache means the obligation is now live
        poll_task(self.cache.pop_front());
        self.log = Ghost(self.log@.push(Poll(task)));  // discharged before Tick(End)
    }
    self.log = Ghost(self.log@.push(Tick(End)));
}
💡
Two things a fake proof can't fake. The tick can't be a no-op that logs progress it never made — progress_inv forces exactly one Tick(Begin)…Tick(End) pair per step, and cached⇒poll forces a real Poll inside it. And tick can't simply never return — its inner loops carry decreasing measures, so it's forced to terminate and actually hand control back.

3 · Async contracts, formalized

Each module packages its progress invariant into a reusable, parametric shape:

struct AsyncContract<L, T> {
    acceptance:  spec fn(L, T) -> bool,   // e.g. task popped into cache
    fulfillment: spec fn(L, T) -> bool,   // e.g. task polled
    assumption:  spec fn(L, T) -> bool,   // e.g. task IDs unique
}
// liveness: acceptance ⋀ assumption ⟹ ∃n. fulfillment holds within n steps

4 · Assumptions and scope — what's actually proved

🌍
Environment (not the runtime's to control): the clock strictly advances; every wake source a task registers fires within a bound (timer deadline, bounded I/O polls, invoked waker); submitted tasks arrive in fixed finite order.
👤
User tasks (a calling convention, not proved): a task returns Ready within a bounded number of polls; it keeps an awaited resource registered until woken; it doesn't cancel another task's pending wait; task IDs are unique.
📜
Trusted log (in the code, not the proof): append-only-ness is enforced by a small family of external_body wrapper functions — audited by hand once, not mechanically checked. Everything else (FIFO scheduling, timer/I/O wakeup timeliness, resource ownership) is discharged by the verifier.

Scope: the guarantee is that the runtime never drops a task — not that the application (or user code) makes progress. Whether a task ever reaches Ready is up to its own logic; that's explicitly out of scope.

Follow the numbers, step by step

Worked examples

Four traces carried through with the paper's own numbers — from a single tick, to the composed proof, to what verification actually cost and bought.

① Checking cached ⇒ poll on a real trace

The paper gives this exact log for tick 2: Tick(B), Pop(T2), Pop(T3), Poll(T2), Poll(T3), Tick(E). Does the progress invariant hold?

  1. Identify acceptance events. Pop(T2) at index i₂ and Pop(T3) at index i₃ both put a task into the cache — each triggers cached⇒poll.
  2. Identify fulfillment events. Poll(T2) appears at some index j₂ > i₂; Poll(T3) at j₃ > i₃.
  3. Check the deadline. Both Poll events occur before Tick(End) — the obligation window for this tick.
  4. Conclusion: ∃j₂>i₂. L[j₂]=Poll(T2) and ∃j₃>i₃. L[j₃]=Poll(T3) both hold within the tick — cached⇒poll is satisfied, and the invariant carries into tick 3.
🍯
Insight: this is the shape of what the verifier checks — but Verus isn't literally scanning a concrete slice of this log; it discharges a quantified first-order proof obligation (∃j>i. L[j]=Poll(T2)) over the abstract log and step invariants, so it holds for every execution consistent with those invariants, not just this one trace.

② Bounding a timer-wakeup chain

A task registers a timer and returns Pending. Chain the contracts to get an overall poll bound.

  1. input_queue_poll (executor): acceptance = task enters the injection queue; fulfillment = task polled within n₁ steps.
  2. First poll returns Pending, registers a timer: this satisfies the acceptance of timer_wakeup (reactor).
  3. timer_wakeup: fulfillment = wakeup fires within n₂ steps (bounded by the environment assumption that the clock advances and deadlines are reached).
  4. Cross-module predicate routes the fired wakeup into the executor's reactor-wake queue — this is reactor_wake_poll's acceptance.
  5. reactor_wake_poll: fulfillment = task polled again within n₃ steps (a separate executor contract from the injection-queue one, re-triggered on the reactor-wake queue).
  6. Total bound for one Pending round-trip: n₁ + n₂ + n₃ steps. If the second poll is Ready, done; if Pending again, repeat — bounded by cap, the task's own remaining-polls count from its user-task assumption.
💡
This is exactly why no interleaving search is needed: a single-threaded log has one, deterministic next event, so "trace-splitting" at the fulfillment point is just an ordinary lemma, not a model-checking problem.

③ Where the 11.7× proof ratio actually comes from

Per-module spec+proof ÷ verified-LOC ratios, from the LOC table: Executor 2,844/451, Reactor 9,860/1,651, Utilities 2,006/595, Collections 3,906/696.

  1. Executor: 2,844 ÷ 451 ≈ 6.3×.
  2. Reactor: 9,860 ÷ 1,651 ≈ 6.0× — the largest absolute proof burden (19 local invariants for timer/I/O correctness).
  3. Utilities: 2,006 ÷ 595 ≈ 3.4× — smallest ratio; per-task obligations are simpler than scheduling logic.
  4. Collections: 3,906 ÷ 696 ≈ 5.6×.
  5. Contracts + composition: 21,014 spec+proof lines, 0 verified executable lines — undefined ratio, because this layer is the cross-module reasoning, not runtime code.
  6. Whole system: 39,630 ÷ 3,393 ≈ 11.7×, dragged up almost entirely by that composition layer.
🍯
Insight: per-module proof cost (3–6×) is comparable to other verified-systems work; what's distinctive here is that relating modules to each other costs more than verifying any one of them.

④ What verification bought: the IronFleet Paxos swap

Same verified Dafny/C# Paxos core; only the I/O layer changes (7+ OS threads/replica vs. Lion's async tasks on one background thread).

  1. Unpinned throughput: Lion 3,330 req/s vs. C# IO 1,635 req/s → 3330/1635 ≈ 2.0×.
  2. Unpinned CPU: Lion 138% vs. C# IO 505% peak → 138/505 ≈ 27% of the CPU for more than 2× the throughput.
  3. Pinned to one core: Lion 2,005 req/s vs. C# IO 329 req/s → 2005/329 ≈ 6.1×; latency 0.85 ms vs. 5.28 ms ≈ 6.2× lower.
  4. Why the gap widens under a tight CPU budget: the C# backend's 7+ kernel threads per replica must be preemptively interleaved by the OS scheduler with a busy-spinning Paxos loop; Lion's cooperative async tasks yield voluntarily, so I/O isn't starved by the spin.
💡
The mechanism — avoiding synchronous, thread-per-connection blocking in favor of event-driven, cooperative scheduling — is the same efficiency argument behind moving hot/cold decisions off a synchronous fault path in tiered-memory systems: overlap waiting with useful work instead of parking a whole execution context on it.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
Why can't a single Hoare-style postcondition state "task T is eventually polled," even though Verus can easily state "after this call, T is in the cache"?
Show answer
A postcondition describes state immediately after one function call returns. "Eventually polled" ranges over an unbounded number of future calls to possibly different functions (pop, poll, park, wake) — there's no single call boundary at which that postcondition could be checked.Misconception: that liveness is just a "weaker" version of a postcondition. It's a different kind of claim — about an unbounded future — not a weaker one about the present.
Problem 2 · medium
For the log Tick(B), Pop(T2), Pop(T3), Poll(T2), Poll(T3), Tick(E), does cached⇒poll require Poll(T2) to occur immediately after Pop(T2)?
Show answer
No. It only requires Poll(T2) to occur at some later index before Tick(End) — here it's fine that Pop(T3) intervenes. The obligation window is the whole tick, not the very next event.Misconception: reading "eventually" as "immediately next." The FOL translation is ∃ a later index, with no adjacency requirement.
Problem 3 · medium
Write the Kamp-style FOL translation of "after event A at index i, event B eventually occurs."
Show answer
∃j > i. L[j] = B. This is a statement about one specific log — an existence claim over indices, expressible with a single quantifier, not a modal operator ranging over all possible execution futures.Misconception: conflating this with the LTL formula □(A → ♢B) meaning "globally." The FOL version checks one particular instance (one specific i), which is exactly what's needed per-task, per-acceptance.
Problem 4 · hard
Why does composing contracts (n₁ + n₂ steps) not require reasoning about all possible thread interleavings, the way concurrent liveness proofs usually do?
Show answer
Lion's verified core is single-threaded, so execution is a deterministic sequence — there is exactly one "next event," not a set of possible next events from different threads racing. Chaining two bounded leads-to facts is then just an ordinary trace-splitting lemma: if a run has n₁+n₂ steps from A, split it at the point where the first contract's fulfillment lands, and the second contract's clock starts there.Misconception: assuming any liveness proof needs interleaving/model-checking machinery. That's needed for concurrent systems; Lion sidesteps it entirely by construction, at the cost of not covering cross-thread work-stealing.
Problem 5 · hard
The induction bounding a Pending→Runnable→Polled loop uses "polls remaining, bounded by cap" as its ranking function. Why not use wall-clock time instead?
Show answer
Wall-clock time isn't under the runtime's control and the proof doesn't know real-time bounds on external events in general — it only assumes each wake source fires eventually, within some (module-specific) bounded number of steps, not within a specific duration. Counting polls-to-Ready keeps the induction purely about the runtime's own driving cycles, which the environment assumption (clock advances, wake sources eventually fire) is enough to bound.Misconception: that a liveness proof needs real-time deadlines. It only needs a discrete measure that strictly decreases — steps/polls, not milliseconds.
Problem 6 · medium
In the mutation study, mutants M01–M04 (timer-link bugs) are rejected by the verifier but the stress test still passes on all of them. What does that tell you — that the proof missed something?
Show answer
No — it's the opposite: the proof caught real bugs the test suite couldn't. M04, for example, makes the reactor scan only the timer wheel's lowest level, missing nearer upper-level deadlines; the stress test's 100 ms park-timeout cap happens to mask the resulting lateness as bounded extra latency rather than a hang. The verifier has no such luck-dependent blind spot — it rejects the mutant statically, before any workload runs.Misconception: treating "passes the stress test" as the gold standard. The whole point of the mutation study is that tests sample behavior; proofs constrain it.
Problem 7 · medium
Mutant C1 (an empty thread-local wakeup batch) verifies green — Verus raises no objection — yet hangs the stress test in all 3 runs. Doesn't a "verified" system rule this out?
Show answer
C1 mutates a trusted shim (thread-local storage plumbing), which sits outside the ~3,393 verified LOC by design (§5.2) — its correctness is assumed, hand-audited once, never mechanically checked. The proof's guarantee is conditional on the trusted base being honest; C1 demonstrates exactly what breaks if it isn't.Misconception: that "formally verified" means every line of the system is checked. Lion's trusted base is small (~500 LOC) and explicitly inventoried — but it's not zero, and bugs there are unprotected by the proof.
Quick answers

Frequently asked questions

Ten questions newcomers to this paper ask most.

Q1What exactly does Lion guarantee — and what does it explicitly not?▾
It guarantees the runtime never forgets a task: every task that yields is eventually polled again, within a bounded number of steps, provided the environment and user-code assumptions hold. It does not guarantee whole-application liveness — whether a task itself ever finishes is up to its own logic, which is out of scope (§5.2).
Q2Why not just add temporal operators (□, ♢) to Verus directly?▾
That would mean rearchitecting the verifier's proof model and SMT encoding to support modal/temporal logic natively — a much larger undertaking. Lion instead reduces the problem to logic Verus already checks (first-order, via Kamp's theorem over the log), requiring no changes to the verifier.
Q3What mathematical fact actually licenses the log-index trick?▾
Kamp's theorem (1968): over a discrete, linearly ordered structure (like the naturals, or an append-only log's indices), Linear Temporal Logic is exactly as expressive as First-Order Logic with a "less than" relation. Lion applies this Kamp-style reduction specifically to the leads-to obligations (□(A → ♢B)-style claims) that its async contracts need over append-only, linearly ordered logs — that's the scope of the translation, not a claim that every possible temporal formula reduces this cleanly in general.
Q4How is this different from IronFleet's or Anvil's liveness proofs?▾
IronFleet and Anvil prove liveness of application-level state machines (a replicated log, a cluster controller) using a TLA-style temporal encoding atop Dafny/Verus, but they assume the underlying I/O/callback layer reliably delivers events. Lion proves liveness of that I/O/scheduling layer itself, and does so without a state-machine/TLA encoding — using the log-to-FOL reduction instead.
Q5Does Lion support Tokio-style multi-threaded work-stealing?▾
No. The verified core is single-threaded (one executor, one reactor per core); multi-core deployment runs independent per-core instances with no shared state. Cross-thread work-stealing, where tasks migrate and shared queues need concurrent reasoning, is named explicit future work (§6).
Q6What's in the trusted base, and why isn't it verified?▾
OS/mio syscall shims (timers, epoll), a thread-local-storage shim, and the append-only ghost-log wrapper make up Lion's ~507 trusted LOC (Fig. 6) — these interface with primitives (the OS, Rust's runtime) that Verus cannot model, so their contracts are asserted and hand-audited rather than proven. Adapter glue exposing Tokio-compatible Future/Arc<Mutex> APIs is a separate, larger 1,537-LOC category in Fig. 6, sitting outside both the verified and the trusted-base counts.
Q7Why does Lion lose to Tokio on some raw microbenchmarks, like timer-cancel at 10K concurrency?▾
Tokio's timer wheel is heavily hand-optimized with pointer-based shared mutable state and a locking-bypass fast path. Lion's verification-friendly design deliberately avoids shared mutable state (each module owns its state exclusively, §3) — that ownership discipline is what makes independent module proofs possible, and it costs about 8% throughput only at the highest timer churn (2.86M vs. 2.64M ops/s at 10K).
Q8How much of the proof was AI-assisted, and does that undercut the result?▾
The 39,630 spec+proof lines (≈11.7× the verified executable code) were produced with heavy Claude assistance for mechanical boilerplate and quantifier instantiation, but the authors designed the specifications, invariants, and proof decomposition by hand — fully autonomous proof repair did not work at this scale. The mutation study (Appendix B) is a separate check on whether the resulting proofs actually constrain the implementation, independent of who wrote them.
Q9If the stress test already caught real hangs in Tokio, libevent, and libuv, what does the mutation study add?▾
The stress test shows Lion doesn't hang on one particular adversarial workload — but a vacuous or over-permissive spec could pass that same test by luck. The mutation study directly attacks the proof: it injects scheduling-breaking faults and checks the verifier rejects them. All 10 verified-region mutants were rejected; only 6 of 10 would have been caught by the stress test alone, showing the proof constrains more than the test observes.
Q10Could this log-to-FOL methodology apply beyond async runtimes?▾
In principle, yes — the authors present it as a general parametric framework, not Lion-specific. Any single-threaded, event-driven system with a deterministic execution order (an append-only log is a natural model for many such systems) could reduce its leads-to obligations to first-order log-index statements the same way.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
Async contractA module's packaged liveness obligation: (acceptance, fulfillment, assumption) over its event log — the reusable unit the whole proof is built from.
Event logA ghost, append-only, per-module list of abstract runtime actions. Its indices serve as logical timestamps for "before"/"after."
Progress invariantAn inductive predicate over the log (preserved by every step) asserting a module's local liveness facts, e.g. cached⇒poll.
Contract chainingComposing modules by having one contract's fulfillment trigger the next's acceptance; bounded leads-to facts add (n₁+n₂ steps).
Kamp-style translationReducing an LTL formula to an equivalent FOL formula over a linear order, following Kamp's 1968 expressiveness theorem.
Ghost stateSpecification-only variables (e.g. the log) that are reasoned about in proofs but erased entirely at compile time.
Ranking functionA measure (polls remaining, bounded by cap) that strictly decreases each loop iteration, making a bounded-induction argument well-founded.
Cross-module predicateA fact relating two modules' separate logs (e.g. a reactor wakeup routes into the executor's correct queue) needed to compose independent proofs.
Supporting terms
Executor / Reactor / Utility moduleLion's three kinds of components: task scheduler, OS-event monitor, and inter-task condition (channels, semaphores) respectively.
WakerA callback stored by a Pending task and invoked when its awaited condition is met, re-enqueuing it for polling.
VerusAn SMT-based deductive verifier for Rust, providing Hoare-style contracts but no native temporal-logic support.
Trusted baseThe ~507 executable lines (OS/mio shims, thread-local shim, log append-only wrapper) whose correctness is assumed, not proven — separate from the 1,537 LOC of Tokio-compatibility adapter glue, which sits outside both the verified and trusted-base counts (Fig. 6).
Thread-per-core / work-stealingTwo multi-core scheduling models; Lion adopts the former (independent per-core instances, no shared state).
CapThe bound on how many more polls a well-behaved task needs before reaching Ready — the user-task assumption that makes induction well-founded.
