Finding a candidate isn't the same as having a safe commit

Two caches that look alike: a replicated catalog that just needs to agree eventually, and a decoder that must never reuse the wrong bytes. This is the plain-English story of how a disaggregated LLM KV-cache can have one without sacrificing the other.

📄 "Disaggregated LLM KV-Cache Storage Requires Coordination-Free Consistency Abstractions" · Pullela & Acharya 🎓 Some distributed-systems basics assumed — primers cover them ⏱ ~30 min read
🗂️

Let metadata that only adds facts converge for free; anything that retracts, picks a unique winner, or thresholds mutable state still needs coordination — decoder-commit checks make reuse safe, but unique-source choice, admission thresholds, scheduling, and reclamation may still need coordination of their own.

1Why an LLM KV-cache exists at all▾

Each decoded token's attention computation produces key/value tensors. If a later request shares a prefix (same system prompt, same conversation so far), those tensors can be reused instead of recomputed — a huge savings for long contexts.

Disaggregated serving splits prefill (building the cache) and decode (consuming it) onto different workers, so that reuse now has to cross machines.

Now you're ready: this paper is about the metadata that tells one worker where another worker's cached blocks live — and what can go wrong trusting that metadata.
2Prefill/decode disaggregation▾

Prefill (processing the prompt) and decode (generating tokens one at a time) have very different resource profiles — prefill is compute-heavy, decode is memory-bandwidth-heavy. Splitting them onto separate workers (as in DistServe, Splitwise) lets each be provisioned and scheduled independently.

The cost: KV state produced by a prefill worker must be transferred to, or made discoverable by, decode workers — across a network, through a shared storage tier, or both.

Now you're ready: LMCache and Mooncake exist to manage exactly this cross-worker KV placement, which is what the paper's 47-operation audit is drawn from.
3Monotonicity and the CALM theorem▾

A computation is monotone if adding more input facts can never invalidate a conclusion you already drew — "that record exists" stays true forever once it's true. CALM says: if your program is monotone, replicas can derive correct results from whatever facts they've seen, in any order, with no coordination.

The moment a program needs to retract a fact, decide something is absent, pick a unique winner, or compare against a changing threshold, monotonicity breaks — and some coordination becomes unavoidable.

Now you're ready: the whole paper is CALM applied as a diagnostic — not "add more CRDTs everywhere," but "find exactly which metadata effects are monotone, and design around that boundary."
4CRDTs and the observed-remove set▾

A CRDT is a data type whose replicas, merged by a simple rule (usually set union), always converge to the same state regardless of message order. A grow-only set is the simplest CRDT: you can only add, never remove, so union always converges.

An observed-remove (OR) set adds removal: every add gets a unique tag, and a remove deletes exactly the tags it has personally observed — never a tag it hasn't seen yet. That lets a later, concurrent re-add survive a removal aimed at an earlier instance of "the same" logical item.

Now you're ready: the paper's catalog re-encodes cache-block retirement this way, so admission and observed retirement both become pure additions that converge by union.
5Positional encoding and RoPE▾

Transformers need to know a token's position in the sequence. Rotary Position Embedding (RoPE) bakes position into the key (and query) vectors via a rotation that depends on position — values are left untouched. Two consequences matter here: a cached key is tied to the position it was encoded at, and a scheme that reinterprets a block at a different position is implicitly asking the model to read keys it never produced for that position.

Now you're ready: this is why a "positional rewrite" (changing which positions a cached block represents) is a semantic hazard, not just a bookkeeping detail — it's the premise behind §5's fault injection.
6Three kinds of identity▾

A catalog record in this paper carries three distinct identities, deliberately kept separate: logical identity (which semantic derivation this is — model, tokenizer, token content, position map), catalog identity (which admission tag, instance, location this metadata record is), and physical-object identity (which sealed storage generation and payload digest actually hold the bytes).

A catalog can be stale about location without being wrong about logical identity, and a location can be "the same place" while holding different bytes (a new generation).

Now you're ready: almost every subtlety in the valid-hit contract (§4) comes from checking these three identities independently instead of collapsing them into one "is it cached?" bit.
7Root-down traversal and fail-closed reads▾

A requested prefix is a chain of blocks, each depending on its parent. "Fail closed" means: walk from the root, validate each block and its parent link, and stop at the first missing or invalid one — returning a shorter hit or a miss, never an orphan block from deeper in the chain.

This is unrelated to how metadata is replicated; it's a property of how the reader walks the chain, and it holds regardless of which catalog design sits underneath.

Now you're ready: this is the paper's Lemma 1 — a separate, simpler safety net that catches ordinary eviction races, independent of the catalog's consistency model.
8Causal stability and safe garbage collection▾

Once a tagged fact (like a retirement) has done its job, you'd like to delete it to reclaim space — but if a delayed message carrying the original admission that tag describes is still in flight, deleting the tag too early lets that delayed message "resurrect" something that should stay retired.

Causal stability is the condition that no such delayed message can still arrive — e.g., because every relevant replica has acknowledged having seen the tag. A fixed timer (TTL) does not establish this; acknowledgment (or an equivalent causal test) does.

Now you're ready: this is exactly what the paper's GC experiment tests — TTL-based collection resurrects a delayed admission; acknowledgment-based collection doesn't.
9Bounded model checking with TLA+▾

TLA+ lets you specify a system as states and allowed transitions; the TLC model checker then exhaustively explores every possible interleaving of a bounded instance (small numbers of replicas, blocks, messages) looking for a state that violates a stated property.

Finding zero violations in, say, 1,733 generated states is a strong local guarantee for that bounded configuration — it is not a proof that no larger or differently-configured system can violate the property.

Now you're ready: §6's model checking is one of three complementary validation artifacts (alongside fault injection and a four-replica prototype) — each checks a different layer, and none alone is a full confluence proof.
10Reading "M" and "NM" labels correctly▾

An "M" (monotone) label applies to one projected metadata effect of an operation — not to the operation's full implementation, and not to every consumer of that fact downstream. A monotone placement-admission fact can still feed a non-monotone decision (ranking candidates, picking a unique source, admitting against mutable capacity).

So "11 of 47 are monotone" is a descriptive count under one audit representation, not a claim that 11 operations are "safe" and 36 are "unsafe."

Now you're ready: you can now read Table 1 and the 47-row appendix audit without over- or under-reading what each label promises.
The whole story in one place

Coordination-free metadata, coordinated commit

The problem, the CALM-guided diagnostic, and how the pieces fit together.

A disaggregated KV-cache needs a catalog: metadata telling one worker where another worker placed reusable KV state. That catalog looks like a distributed storage namespace, and the easy move is to make it a CRDT and call it done. But KV blocks are model-semantic state — a catalog entry can locate a block, but safe reuse also depends on the model's positional interpretation of that block, the physical generation containing it, and that generation staying valid while a decoder uses it. An available hit is not necessarily a safe hit.

The paper uses the CALM monotonicity criterion as a diagnostic, auditing the metadata effects of 47 operations drawn from LMCache, Mooncake, vLLM-style paging, and token-selective caching. 11 are monotone in isolation — pure additions, like admitting a sealed placement. 36 are non-monotone — retractions (eviction), absence/uniqueness decisions (lookup miss, unique-source routing), or thresholds over mutable state (SLO/overload checks).

Guided by that boundary, the design re-encodes the one effect that matters most for replication — observed retirement — as the addition of concrete tags to a tagged observed-remove (OR) set. Admission and retirement now both grow by union, so the catalog converges under delayed, duplicated, and reordered messages without a global order. That re-encoding does not make physical reclamation, unique-source choice, or decoder commit coordination-free — those obligations move to a separate valid-hit contract checked once, locally, at commit time.

The payoff: a bounded TLA+ model finds zero committed-hit violations across 1,733 generated states in the safe, copy-on-write configuration, while six unsafe/ablated configurations reproduce the expected fault — and a constructed positional-rewrite schedule reliably perturbs decoder output when the contract's protections are removed.

🍯 Key takeaways

  • An "available" catalog candidate and a "safe" decoder hit are two different properties — conflating them is the paper's central hazard.
  • CALM is used as a design diagnostic: 11/47 audited metadata effects are monotone, 36 require coordination somewhere.
  • Retirement is re-encoded as a tagged OR-Set addition, so catalog convergence needs no global order — but this doesn't remove reclamation/commit coordination.
  • Root-down traversal (fail-closed prefix walk) and the valid-hit contract (identity + sealed generation + digest + reader protection) are separate safety nets layered on top.
  • A positional rewrite under a stable identity is a concrete, constructed hazard — not a reported bug in LMCache/Mooncake as shipped.
  • Validated with three complementary, bounded artifacts: fault injection, a four-replica catalog prototype, and TLA+ model checking — not a production benchmark.
🧩
For tiered-memory / CXL readers (our framing, not the paper's): the "observed retirement" problem rhymes with the hot/cold page-migration races that systems like TPP, HeMem, and Memtis navigate when deciding whether a page is still at its advertised tier — a stale "present at DRAM" bit has a similar flavor of ambiguity to this paper's stale "present in cache" bit. The analogy is loose: page migration usually has coherence directories, page-table updates, and TLB shootdowns to fall back on, while this paper's hazard is model-semantic — identity, generation, digest, and reader protection for bytes a decoder will feed straight into attention. The paper itself does not discuss CXL or these systems.
Six everyday pictures

How to think about the design

Each stands alone — read in any order. Every card ends with an honest note on where the picture breaks.

The audit · Monotone vs retraction

A logbook you can add to, not erase

Two ship's logs: one where every crew member can only add a line ("cargo loaded at noon"), and one where a line can be struck out ("cargo removed"). Anyone reading the add-only log can trust any entry forever, in any order they receive pages. The strike-out log needs everyone to agree on which entries are still live before trusting a summary. The paper's audit sorts all 47 operations into these two kinds.

Where it breaks: a monotone add can still feed a non-monotone decision downstream (picking a "unique" best entry from the log). The log being safe to add to doesn't make every use of the log coordination-free.
The catalog · OR-Set tags

A tracking number, not just "delivered"

"Delivered: yes/no" can't tell a courier whether today's "yes" refers to this morning's package or last week's. A tracking number fixes it: each shipment gets a unique code, and "returned" cancels the exact code it saw. A later, different shipment gets its own code and is untouched. The catalog does this for cache placements — admission tags, retirement removes only the tags it observed.

Where it breaks: tracking numbers accumulate forever unless old ones are safely archived. That's garbage collection — and archiving one too early (before confirming no delayed packages reference it) can "resurrect" a cancelled shipment. See the shredding analogy below.
Reading the chain · Fail-closed walk

A rope with knots, checked from one end

Checking a knotted rope for weak points by grabbing a spot in the middle tells you nothing about whether the earlier knots held. Starting from one end and stopping at the first weak knot tells you exactly how much rope is trustworthy. A decoder walks the requested prefix the same way — root-down, stopping at the first invalid or missing block — so it never hands back a "hit" built on a broken earlier link.

Where it breaks: this only protects against missing or clearly invalid links. A link that's present, looks valid, but secretly holds the wrong bytes (the rewrite hazard) slips through — that needs the separate valid-hit checks, not just the walk.
The commit · Valid-hit contract

A boarding gate, not a departures board

The departures board (the catalog) tells you a flight exists and roughly where to go — it's often slightly stale and that's fine, you just re-check at the gate. Boarding (the commit) is where your ticket, ID, and the plane's tail number are all checked together, right before you step on. A stale board costs you a walk to the wrong gate; a skipped gate check costs you boarding the wrong plane.

Where it breaks: airports re-check per passenger; the paper's contract re-checks per block, and only once per commit — it doesn't re-verify continuously while you're "in flight" (mid-use), which is exactly why reader protection has to span the whole use, not just the check.
The hazard · Positional rewrite

Renovating a room while a guest is still inside

If a crew repaints and renumbers a hotel room while a guest, still holding the old room's key and floor plan, is walking in — the guest ends up "in the right door" but in a room that no longer matches what they expected. That's the positional rewrite: the catalog still advertises the old position map while the physical bytes have been rewritten for a new one, and an unfenced reader can walk in mid-change.

Where it breaks: a real hotel has a "do not disturb" sign (reader protection / leases). The hazard only exists in designs that skip that sign — the paper constructs it as a conditional witness, not a reported incident in LMCache or Mooncake as shipped.
Reclamation · Causal stability

Shredding paperwork, but only after every branch confirms

Head office wants to shred an old policy memo once it's been superseded — but only after every branch office has confirmed receipt of the update. Shred on a timer instead, and a branch that was offline might still be acting on a memo that's now been destroyed, with no record it ever existed. Timer-based (TTL) garbage collection of retired catalog tags makes the same mistake; acknowledgment-based collection doesn't.

Where it breaks: waiting for every branch to confirm can stall collection indefinitely if one branch goes dark. The paper's experiment shows exactly this: a stalled replica member means safe GC reclaims nothing until that member is explicitly retired.
The full explanation

How it actually works

Section by section, following the paper's own structure (§2–§6).

1 · Two problems that look alike but aren't

Ordinary prefix-boundary eviction already has a safe answer: walk the chain root-down, stop at the first missing/invalid block (Lemma 1). Replicated catalog updates are a different problem. Suppose a placement is admitted, retired, and later re-admitted while messages are delayed or reordered — a Boolean "present" bit on its own cannot distinguish a delayed copy of the old placement from the new one. The paper treats these as genuinely separate concerns, solved separately.

2 · The CALM audit

47 operations from LMCache, Mooncake, vLLM-style paging, and token-selective caching were each reduced to a normalized metadata projection — additions, retractions, absence/uniqueness decisions, or thresholds over mutable state — and classified monotone (M) or non-monotone (NM) under that abstraction.

ComponentAudited effectDesign consequence
Placement admissionPure add — monotonePublish only after the generation is sealed; disseminate without a global order.
Observed retirementRetracts a live binding — non-monotone as auditedRe-encode as addition of observed tags; converges by union; reclamation still coordinated.
Candidate lookupPositive facts OK; unique-source/miss commit is NMA catalog result is a candidate, never authorization to consume a bare location.
Unique source, miss, reclaimAbsence/uniqueness/reuse can change mid-read — NMAcquire a named generation; reject acquisition after retirement; protect through use.
Positional rewriteSame identity, different interpretation — NMPublish under a new identity/generation; exclude unprotected readers.
📊
Under this representation, 11 of 47 projected metadata effects are monotone; 36 are non-monotone. The count is descriptive — the design-relevant result is which effects land where, not the ratio itself.

3 · The tagged OR-Set catalog

Each record carries three identities together: a = (σ, h, p, π, t, inst, loc, g, δ) — semantic namespace σ, logical key h, expected parent p, position map π, unique admission tag t, catalog instance/location, physical generation g, and sealed-payload digest δ. The logical key chains to its parent: h_i = H(σ ‖ h_{i-1} ‖ tokens_i ‖ π_i).

Catalog state is S = (A, R): a grow-only set of admitted records and a grow-only set of retired tags. admit(a) happens only after g is sealed; retire(T) adds the concrete tags T its issuer observed. Replicas merge by plain set union — merge(S1,S2) = (A1∪A2, R1∪R2) — which is associative, commutative, and idempotent, so any delivery order converges.

4 · Root-down safety and the valid-hit contract

Lemma 1: if a reader validates each block's key and parent edge before advancing, induction from the root guarantees every returned depth is a valid path — no orphan descendant is ever returned as part of a hit.

That alone doesn't establish physical-object validity. For each block, the decoder must check: namespace/key/parent/position match the request; the named generation can be acquired; the fetched payload matches the sealed digest; and the acquired generation stays protected through use:

ValidBlock(q,i,a_i)  ⇐⇒  σ_i=σ_q ∧ h_i=h_i(q) ∧ π_i=π_i(q) ∧ p_i=h_{i-1}(q)
                 ∧ Acquire(loc_i,g_i,δ_i)=r_i ∧ H(Fetch(r_i))=δ_i ∧ Protected(r_i,use_i)

Proposition 1 (committed-hit safety): under five premises — publish-after-seal, atomic check-and-pin acquisition, immutability until release, versioned rewrites, and root-down validation — every commit satisfies CommitHit(q,k) ⇒ ValidHit(q,k), despite staleness, reordering, duplication, retirement, re-admission, and address reuse. The critical premises are the validate-to-use ones: checking the right identity is useless if the generation can be reclaimed or changed before use completes.

5 · The positional-rewrite hazard

If a position-changing rewrite keeps the same published identity/generation while the catalog still advertises the old position map, and no fence (generation check, copy-on-write, lease) protects an overlapping read, a reader can obtain a valid-looking candidate whose bytes no longer match what was requested — CommitHit holds while ValidHit does not (Proposition 2). This is a constructed conditional witness, not a reported fault in the LMCache/Mooncake versions studied.

6 · Three validation artifacts, three different questions

  1. Fault injection: can an unfenced rewrite actually change decoder state? A two-thread CPU schedule and real KV tensors on two models say yes, under the constructed conditions (worked out numerically in Tab 5).
  2. Four-replica catalog prototype: does the OR-Set converge under reordering, duplication, and partition/rejoin — and does safe GC avoid resurrecting retired facts where TTL-based GC does not?
  3. Bounded TLA+ model: does the composed lifecycle (admit → retire → acquire → validate → rewrite → reclaim → commit) ever let CommitHit hold without ValidHit in the safe configuration — and do ablated/unsafe configurations reproduce the expected counterexample?
Follow the numbers, step by step

Worked examples

The audit split, a concrete OR-Set trace, the rewrite fault-injection numbers, and the model-checking + benchmark results — all from the paper.

① Reading the 11/47 audit split correctly

What does "11 of 47 metadata effects are monotone" actually tell you?

  1. 11 ÷ 47 ≈ 23.4% of audited effects are monotone (add-only, under the stated abstraction); 36 ÷ 47 ≈ 76.6% are non-monotone.
  2. Row 1 (batched_admit): adds a placement fact — M. No downstream retraction is implied by this label alone.
  3. Row 6 (batched_evict): retracts a hash-to-location binding — NM. This is exactly the effect the catalog design re-encodes (§3), turning it into an addition of observed-retirement tags.
  4. Row 30 (KVCache load at decode): labeled M for adding a completed-load fact — but the paper flags this as an edge case: object validity is a separate, still-coordinated question.
  5. Conclusion: the ratio is descriptive, not a safety score. The design value is knowing which rows (admission, candidate facts) can leave the global order, and which (eviction, unique-source choice, thresholds) cannot.
💡
This is why the paper insists the audit is "a design diagnostic, not a confluence proof" — it tells you where to re-architect, not that the system is now safe.

② A concrete OR-Set trace (illustrative, following §3's mechanism)

Block admitted as tag t7, retired, re-admitted as tag t9 — messages arrive out of order at a second replica. Does it converge?

  1. True order of events: admit(t7) at time 1, retire({t7}) at time 2, admit(t9) at time 3.
  2. Replica B receives them reordered: admit(t9), admit(t7), retire({t7}).
  3. Apply as grow-only unions regardless of order: A = {t7, t9}, R = {t7}.
  4. Lookup rule: visible records = A minus tags in R = {t9}. Same for both replicas, any arrival order.
  5. Why a Boolean bit fails here: if "present" were one shared flag, replica B applying retire after admit(t9) could clear the flag and hide the still-live t9 placement — exactly the ambiguity the paper is solving.
🍯
Insight: the fix isn't "use a CRDT" in the abstract — it's specifically giving retirement something concrete (observed tags) to point at, so union stays correct under any delivery order.

③ The positional-rewrite fault-injection numbers

Across randomized schedules, forced schedules, and real KV tensors on two models — how often does the unfenced rewrite actually perturb the read?

  1. Randomized 500-trial schedules: the reader observed the rewrite in 329 and 346 trials → 65.8% and 69.2% of runs, varying with thread-timing luck.
  2. Forced schedules (timing pinned to the hazard window): 10 of 10 trials → 100%, confirming the hazard is real whenever the window is actually hit, not just a rare fluke.
  3. Qwen2.5-1.5B, 8 fixed tasks, unsafe in-place rewrite: 8 of 8 outputs differ from the fresh-prefill reference; mean first-token KL divergence 8.24 — a large distributional shift.
  4. SmolLM3-3B, same 8 tasks: all final answers matched the reference, but 1 of 8 top-1 tokens changed; mean KL divergence only 0.73 — a much smaller effect.
  5. Takeaway: the same injected hazard has model- and task-dependent severity. The paper does not claim a universal quality drop — only that an unfenced rewrite can perturb output, sometimes severely.
⚠
The safe controls — prefix-boundary eviction and protected copy-on-write — matched the fresh-prefill baseline's first-token behavior in both runs. The hazard only appears when the fences are deliberately removed.

④ Model checking, catalog traffic, and the latency caveat

What did TLA+ actually find, and what do the prototype's numbers support (or not)?

  1. TLA+, safe copy-on-write config: zero counterexamples to CommitHit ⇒ ValidHit within 1,733 generated states (634 distinct, depth 16) — a strong result, bounded to this small instance (2 replicas, 2 blocks, 2 locations).
  2. Six unsafe/ablated configs reproduced the expected lifecycle or hit-soundness counterexample — e.g. omitting reader protection lets reclamation slip in between validation and commit, exposing exactly the P2–P3 gap in Prop. 1.
  3. Four-replica prototype, 2,000 faulted steps: 33.8 MB of encoded updates + 19.2 MB full-sync traffic; 8,023 retired-tag references emitted; 27,152 retired-tag pairs reclaimed across replicas and GC passes (a cross-replica sum, so it can exceed the first count).
  4. Latency microbenchmark: at 500 logical ops/s with batch size 64, replicated p50 was 4.00–4.18 ms vs. 5.00–5.10 ms centralized — replicated faster in this one regime — but other operating points favored the centralized design, and the original 54-row CSV is lost, so no aggregate win/loss tally is auditable.
  5. Rerun completion check: only 15 of 27 matched configuration pairs completed ≥99% of offered operations in both designs (centralized completed all 27; replicated completed 15 ≈ 55.6%) — a caveat on how far the latency numbers generalize.
📎
The paper is explicit that this is prototype/bounded-scale evidence, not a production serving benchmark — reproduce the honest uncertainty, don't round it off.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
A catalog replica returns a placement record for the requested block. Is it now safe for the decoder to fetch and reuse that block?
Show answer
No. The record is only a candidate. The decoder still must run the valid-hit contract: confirm namespace/key/parent/position match, acquire the named sealed generation, verify the payload digest, and hold reader protection through use. Catalog convergence establishes discovery, not physical-object validity.Misconception: that "the catalog found it" is equivalent to "it's safe to use." The paper separates these into two layers on purpose.
Problem 2 · medium
Why can't a plain grow-only set (no removal at all) represent cache-block retirement?
Show answer
A grow-only set can only ever add facts, so it can represent "this was admitted" but has no way to represent "this is no longer live." Lookups would keep returning retired placements forever. The paper needs retirement to actually remove visibility for specific admissions — which is why it uses an observed-remove set (tagged adds + tagged removes), not a bare grow-only set.Misconception: that any CRDT will do. The specific shape of the CRDT (OR-Set vs. two-phase-set vs. grow-only set) matters for whether re-admission after retirement is even possible.
Problem 3 · medium
A two-phase set (once removed, an item can never be re-added) also prevents the stale-bit ambiguity. Why doesn't the paper use one?
Show answer
A two-phase set solves the ambiguity by making retirement permanent for that logical identity — but the paper's workload re-admits the same logical block at a new physical generation after eviction, which is a normal, expected event, not an error. A two-phase set would permanently blacklist that logical key, breaking reuse. The OR-Set's fresh tag per admission lets a later legitimate re-admission survive a retirement aimed at an earlier one.Misconception: that "prevents ambiguity" is the only requirement. The catalog also has to preserve legitimate re-admission, which rules out some otherwise-valid CRDTs.
Problem 4 · hard
Root-down prefix validation (Lemma 1) is described as "independent of the observed-remove catalog." Construct a scenario where root-down validation alone is not enough.
Show answer
Root-down validation only catches missing or clearly invalid blocks — it walks the chain and stops at the first bad link. It says nothing about a block that is present, has a matching key and parent, but has had its underlying bytes rewritten under the same identity (the positional-rewrite hazard). The chain looks perfectly intact; only a payload-digest mismatch or generation check would catch it. That's exactly why the valid-hit contract adds digest verification and reader protection on top of root-down walking.Misconception: that "no missing links" means "no corruption." Fail-closed traversal is a different safety property than payload integrity.
Problem 5 · medium
TLA+ model checking found zero counterexamples in 1,733 generated states for the safe configuration. What exactly does that establish, and what doesn't it establish?
Show answer
It establishes that, within the bounded model — 2 replicas, 2 blocks, 2 locations, old/new generations, depth 16 — every reachable state satisfies CommitHit ⇒ ValidHit under the stated premises. It does not prove the property holds for larger configurations, different numbers of replicas/blocks, or an unbounded search depth, and it is not a proof about the real LMCache/Mooncake systems, only about the abstracted lifecycle model.Misconception: that "model checker found no bugs" means "proven correct in general." Bounded model checking is exhaustive only within its stated bounds.
Problem 6 · easy
Fixed-TTL garbage collection resurrected a delayed admission in the paper's experiment. What should replace the TTL, and why does it fix the problem?
Show answer
Acknowledgment-based (causal-stability) collection: only collect a retired tag once every relevant replica has confirmed it has seen that tag. A TTL just guesses "enough time has probably passed," but a stalled or slow replica can still have an in-flight message referencing the collected tag — reviving something that should stay retired. Acknowledgment waits for proof, not a guess.Misconception: that a longer TTL is "safer." No fixed timer can guarantee no message is still in flight; only an explicit confirmation (or equivalent causal test) can.
Problem 7 · hard
The fault-injection results showed very different severity on Qwen2.5-1.5B (mean KL 8.24, all outputs differ) versus SmolLM3-3B (mean KL 0.73, final answers mostly unchanged) under the identical injected hazard. What should and shouldn't you conclude from this difference?
Show answer
You should conclude that the decoder-level consequence of a stale-state hazard is model- and task-dependent — the hazard is real and reproducible in both cases (the mechanism doesn't care which model you're running), but how much it visibly perturbs output varies. You should not conclude that the hazard is "mostly harmless" because one model tolerated it better, nor that it's universally catastrophic because the other model didn't. The paper explicitly declines to isolate which model/task property explains the gap.Misconception: that a single model's robustness generalizes. A hazard that's forgivable on one model/task pair is not a guarantee it's forgivable everywhere.
Problem 8 · medium
The replicated catalog beat the centralized design on latency at one operating point (500 ops/s, batch 64) but the raw 54-row benchmark is lost. What's the correct way to report this result?
Show answer
Report the single surviving data point honestly (replicated p50 4.00–4.18ms vs. centralized 5.00–5.10ms at that one rate/batch combination) while being explicit that other operating points favored the centralized design and that no auditable aggregate win/loss tally exists because the full CSV wasn't preserved. It would be incorrect to present this as "the replicated design is faster," since that generalizes a single favorable point into a universal claim the lost data can no longer support.Misconception: that one good number is representative. Frequently asked questions

Tap any to expand.

Q1What's the one-sentence problem this paper solves?▾
How to let a disaggregated LLM KV-cache's placement metadata converge without a global order, while still enforcing — and, within a bounded TLA+ model, verifying — that a decoder never silently reuses an invalid or stale object. "The catalog found something" and "it's safe to reuse" are different guarantees.
Q2Isn't "just use a CRDT" the whole answer?▾
No — that's exactly the oversimplification the paper argues against. CRDTs solve the metadata-convergence problem for the subset of effects that are monotone (mainly admission and, after re-encoding, retirement). They say nothing about whether a physical generation is still valid, whether it's been reclaimed, or whether it still represents the position map the decoder expects. Those need the separate commit-time contract.
Q3Why is cache eviction non-monotone but placement admission monotone?▾
Admission only ever adds a new fact ("this placement exists") — adding more facts later can't make that one false. Eviction retracts a live binding ("this placement no longer holds") — it's a negative statement that depends on the current state, which is exactly the case CALM says needs coordination (or, as here, a redesign that re-encodes it as an addition instead).
Q4How does an OR-Set stop a stale admission from "winning" over a real retirement?▾
Every admission gets a fresh, unique tag. A retirement message carries the concrete set of tags its issuer has actually observed and removes exactly those. A delayed copy of an old admission message doesn't create a new tag — it's the same tag, already covered by the retirement that already removed it — so it stays retired regardless of delivery order.
Q5What does root-down traversal protect against that the catalog design doesn't?▾
Ordinary prefix-chain gaps — a block that's missing or fails validation somewhere in the middle of the chain. It's a property of how the reader walks a request, completely independent of whether the underlying catalog is centralized or a replicated OR-Set. It does not, by itself, detect a block that's present and chain-consistent but has had its bytes secretly rewritten — that's the job of the digest check in the valid-hit contract.
Q6What exactly is checked at "commit," and why so many checks?▾
Four things, each catching a different failure mode: (1) semantic/positional identity — is this the block I actually requested; (2) a sealed, acquirable physical generation — does the location still denote a valid object; (3) payload-digest match — do the fetched bytes match what was sealed; (4) reader protection through use — can the generation be reclaimed or changed while I'm still using it. Dropping any one reopens a specific hazard (the paper's ablations demonstrate this directly).
Q7Is the positional-rewrite hazard a bug in LMCache or Mooncake?▾
No — the paper is explicit that this is a constructed conditional witness for an implementation that permits in-place rewrites without fencing, not a reported fault in the specific LMCache/Mooncake versions they analyzed (both use prefix-granular management today). It's a warning for future designs — e.g. token-selective or cross-position KV reuse — that might introduce such rewrites.
Q8Why does a fixed TTL fail for garbage collection here, when TTLs work fine elsewhere?▾
A TTL is a guess about how long messages take to arrive, not a guarantee. If any relevant replica is slow, partitioned, or just unlucky, a delayed admission message referencing an already-collected tag can still arrive and "resurrect" something that should stay retired. Acknowledgment-based (causal-stability) collection replaces the guess with a confirmation that no such message can still be in flight.
Q9Does the replicated design actually perform better than a centralized one?▾
The evidence is intentionally partial: at one measured operating point (500 ops/s, batch 64) the replicated p50 latency was lower, but other operating points favored the centralized design, and the original full benchmark (54 rows) is unavailable, so no aggregate win/loss tally can be audited. The paper does not claim a general performance advantage.
Q10How does this connect to OS-managed memory tiering (DRAM/NVM, CXL)?▾
The core tension — a location-tracking directory that can go stale, versus the object/page it points to actually changing tier or meaning underneath it — rhymes with remote-page tracking in CXL-pooled or tiered memory: a "this page is hot/at DRAM" record can race with an in-progress migration in a way loosely similar to how this paper's catalog record can race with a retirement or rewrite. The paper itself never discusses CXL or named tiering systems, and the analogy is imperfect — page migration typically has coherence directories, page-table, and TLB mechanisms to lean on, while this paper's hazard is specifically model-semantic (identity, generation, digest, reader protection). With that caveat, the paper's split (coordination-free metadata vs. coordination-required lifecycle, bridged by a one-time commit check) is still a pattern worth comparing against how systems like TPP, HeMem, and Memtis handle promotion-record staleness versus actual page-copy completion.
Q11What's actually novel here versus prior CALM/CRDT work?▾
The paper builds directly on established CALM and CRDT results (Hellerstein & Alvaro; Laddad et al.; Shapiro et al.) — it doesn't claim new theory. Its contribution is applying CALM as a diagnostic to a specific, under-examined domain (disaggregated LLM KV-cache metadata), producing a coordination-boundary map for real systems' operations, and composing that with a model-semantic commit contract that CRDT theory alone doesn't address.
Q12What are the paper's own stated limits on its claims?▾
Explicitly: the CALM audit is a design diagnostic, not a confluence proof for the whole serving stack; catalog convergence establishes candidate discovery, not physical-object validity; the positional-rewrite hazard is a constructed witness, not a bug report; and the prototype/model-checking artifacts validate interfaces at bounded scale, not a production serving benchmark.

Core terms
CALMConsistency As Logical Monotonicity — monotone programs can be computed correctly by replicas without coordination.
Monotone / non-monotone metadata effectWhether a projected conclusion can be invalidated as more facts arrive. M = add-only; NM = retraction, absence/uniqueness, or mutable threshold.
Tagged observed-remove (OR) catalogThe paper's CRDT: admission and retirement both become grow-only facts (unique tags + observed-tag removal sets) merged by union.
Logical / catalog / physical identityThree separately-tracked identities of a KV block: its semantic derivation (σ,h,p,π), its catalog record (t, inst, loc), and its physical bytes (generation g, digest δ).
Root-down prefix validationReading a requested chain from the root, stopping at the first missing/invalid block — fail-closed, independent of catalog design (Lemma 1).
Valid-hit contractThe local check a decoder runs before reuse: identity match, acquirable sealed generation, payload-digest match, reader protection through use (Prop. 1).
Positional-rewrite hazardA constructed witness where a rewrite changes a published generation's position-map interpretation while an unfenced reader overlaps it (Prop. 2).
Causal stabilityThe condition required before garbage-collecting a retired tag: no delayed message referencing it can still arrive (e.g. all replicas have acknowledged it).
Supporting terms
Prefill / decode disaggregationSplitting prompt processing from token generation onto separate workers, so KV state must move or be discovered across machines.
RoPERotary Position Embedding — bakes sequence position into cached keys (not values) via a position-dependent rotation, making a cached block's keys position-dependent.
Generation / digestA physical allocation version (generation) and an integrity hash of its sealed payload (digest) — together they verify "this is still the object advertised."
Marginal utility of the audit (11/47)11 of 47 audited metadata effects are monotone in isolation — a descriptive count, not a safety certificate.
TLA+ / TLCLamport's specification language and its model checker; used here to exhaustively search a bounded lifecycle model for safety-property counterexamples.
LMCache / MooncakeOpen-source and research systems for KV-cache management in disaggregated LLM serving; sources of the audited 47 operations.
SLO / TTFT / TBTService-level objective; time-to-first-token; time-between-tokens — Mooncake's latency-facing scheduling signals, several of which are threshold-based and non-monotone.
Copy-on-write (CoW) rewritePublishing a changed object as a new generation/identity rather than mutating the old one in place — the fix that defeats the positional-rewrite hazard.
