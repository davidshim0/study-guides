Not every cache hit is safe to commit

A disaggregated LLM's KV-cache catalog can tell you where a block was placed without ever agreeing on a single global order. But knowing "where" isn't the same as knowing it's safe to feed straight to the decoder. This is the plain-English tour of why — and of the coordination-free catalog, and the separate commit contract, that the paper builds to handle it.

📄 "Disaggregated LLM KV-Cache Storage Requires Coordination-Free Consistency Abstractions" · Pullela & Acharya 🎓 Some CRDT / distributed-systems basics assumed — primers cover them ⏱ ~30 min read
🗂️

Disseminate metadata that only GROWS — admissions, observed retirements-as-tags — without any global order. Coordinate for real whenever something must RETRACT, PICK A UNIQUE WINNER, OR CROSS A THRESHOLD before a decoder commits.

Before you begin

Quick glossary, then eight primers

The acronyms first, one line each. Then the primers — collapsed, tap any open, read in order or jump to what's unfamiliar.

Quick glossary

1KV caches, and why LLM serving disaggregates them▾

Generating text with a transformer means attending over every prior token's key/value vectors. Recomputing them from scratch for a reused prompt prefix is wasted work, so servers cache them. Modern serving further splits prefill (processing the prompt) from decode (generating tokens one at a time) across different workers and storage tiers, so KV state routinely moves between machines.

Systems like LMCache and Mooncake maintain a catalog: metadata telling one worker where another worker placed a reusable KV block — structurally, a distributed storage namespace.

Now you're ready: this paper is about keeping that catalog useful under concurrent updates, without forcing every placement change through one global choke point.
2A cache hit vs. a safe decoder hit▾

KV blocks aren't inert bytes — they're model-semantic state. A catalog entry can tell you a block exists at some location, but safe reuse also depends on the model/positional interpretation of that block, the physical allocation that holds it, and whether that allocation stays valid while the decoder actually reads it.

A miss just loses reuse (recompute and move on). An invalid commit silently perturbs the decoder's output — a much worse failure, because nothing crashes or errors.

Now you're ready: the paper's central move is treating "catalog says it's here" and "safe to hand to the decoder" as two separate questions, answered by two separate mechanisms.
3CALM: which conclusions need coordination▾

CALM (Consistency As Logical Monotonicity) says: if adding more input facts can never invalidate a conclusion, replicas can compute that conclusion without first agreeing on one current view. Pure additions typically qualify. Retraction (taking something back), negation over changing state (asserting absence), and thresholds over mutable values typically don't — a later fact can flip the answer.

The paper treats this as a per-operation diagnostic: extract each operation's externally-relevant metadata effect, and ask whether that projected effect is monotone under a declared representation.

Now you're ready: the audit in §2 runs exactly this test across 47 real KV-cache operations.
4Grow-only sets and OR-Sets▾

A grow-only set (G-Set) only ever adds elements; replicas merge by union and always converge, order-independent — a textbook monotone structure. But it can't express deletion.

An Observed-Remove Set (OR-Set) fixes that: every add is tagged with a fresh, unique identifier, and a remove message carries the specific tags it has observed rather than a bare "delete X." A concurrent add with a different tag survives (add-wins), and a delayed duplicate of an old add is still correctly excluded once its tag is retired — regardless of message order.

Now you're ready: the paper's catalog is exactly an OR-Set over placement admissions and observed retirements.
5RoPE and why position is part of a block's identity▾

Rotary Position Embedding encodes a token's position directly into its key/value vectors at computation time. So a cached KV block isn't just "the tokens" — it's "the tokens, at this position, under this positional convention." Reinterpreting the same bytes under a different position map changes what they mean to the model.

Now you're ready: this is exactly the mechanism behind the paper's positional-rewrite hazard in §5 — a rewrite that changes a block's position map without changing its published identity.
6A bridge from hardware: directory-based coherence▾

If you work on CXL or NUMA memory tiering, this catalog will feel familiar: a hardware coherence directory also tracks "which node currently holds this line" so requests don't have to broadcast. The difference is enforcement. A hardware directory is wired into a fixed protocol state machine with bounded invalidation latency; this software catalog deliberately lets "where" converge lazily, with no such bound, and pushes correctness onto a separate, explicit commit-time check instead.

Now you're ready: read the catalog as "directory without the hardware invalidation guarantee" — which is precisely why the paper needs sealed generations and reader protection to stand in for what a coherence protocol would otherwise enforce.
7Root-down prefix walking▾

A prefix cache is a chain: block 0, block 1 (whose key depends on block 0), block 2, and so on. The standard safe read pattern walks from the root, validating each block and its parent edge before advancing, and stops at the first missing or invalid block — returning whatever valid prefix it reached as a shorter hit, or a miss.

Now you're ready: this ordinary mechanism (Lemma 1) is intentionally kept separate from the harder problem of validating a single block's physical safety (§4).
8Bounded model checking with TLA+▾

TLA+ specifications describe a system as states and transitions; the TLC model checker exhaustively explores every reachable state up to some bound, checking an invariant at each one. Finding zero counterexamples within N states is strong evidence, not a proof for an unbounded system — but it's very good at surfacing subtle races that testing alone would miss.

Now you're ready: §6 uses this to check one composed KV-cache lifecycle (admission → retirement → acquisition → rewrite → reclamation → commit) at bounded scale.
The whole story in one place

The paper in a nutshell

Where coordination can be removed, where it can't, and how the design keeps those two zones from getting confused.

Disaggregated LLM serving needs a catalog that tells one worker where another worker placed reusable KV state — structurally a distributed storage namespace. The paper asks a CALM-guided question of every metadata effect in that namespace: does this conclusion stay true as more facts arrive, or can a later fact invalidate it? A source-guided audit of 47 operations drawn from LMCache, Mooncake, vLLM-style paged KV management, and token-selective cache management finds 11 monotone metadata effects and 36 non-monotone ones — retractions, absence/uniqueness decisions, and thresholds over mutable state.

Guided by that boundary, the paper redesigns exactly the coordination-free part: placement admission and observed retirement become a tagged, grow-only OR-Set catalog that merges by union and converges regardless of message delay, duplication, or reordering. Ordinary prefix incompleteness is handled separately by a root-down walk that fails closed at the first missing or invalid block (Lemma 1).

Catalog convergence only answers "where might this be?" A separate valid-hit / committed-hit contract (Proposition 1) governs whether the decoder may actually consume a candidate: checking semantic and positional identity, acquiring a sealed physical generation, verifying the payload digest, and holding reader protection through use. A positional-rewrite witness (Proposition 2) shows concretely what breaks if that contract is skipped: a rewriter can change a block's position map under its old identity while a reader overlaps, producing a committed hit that is not actually a valid hit.

The design is validated with a constructed fault-injection experiment, a four-replica catalog prototype under 2,000 faulted steps, and bounded TLA+ model checking (1,733 generated states, 634 distinct, depth 16) that finds no committed-hit violation under the contract — while an unfenced rewrite does perturb real decoder output.

🗂️ Key takeaways

  • Under the audit's source representation, 11 of 47 metadata effects are monotone; 36 of 47 still require coordination.
  • Placement admission and observed retirement are re-encoded as tagged facts in an OR-Set catalog, merging by union under any delivery order.
  • Root-down prefix walking (Lemma 1) handles ordinary incompleteness independently of the catalog's convergence.
  • A separate valid-hit contract (Proposition 1, premises P1–P5) is what actually authorizes a decoder commit — catalog freshness is not that authorization.
  • A positional-rewrite hazard (Proposition 2, premises H1–H6) is a constructed witness, not a bug report against LMCache/Mooncake as shipped.
  • Re-encoding retirement as tags does not remove the lifecycle coordination needed for physical reclamation, unique-source choice, or decoder commit.
  • TLA+ finds zero committed-hit counterexamples under the safe copy-on-write configuration; omitting reader protection produces one immediately.
Six everyday pictures

How to think about coordination-free metadata

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The catalog · OR-Set tags

A sign-in sheet with claim tickets

Each check-in gets a unique numbered stub, not just a checkmark. A check-out message names the specific stub numbers it saw, not "the guest." So a late-arriving duplicate check-in for a stub that's already been checked out is correctly ignored, while a genuinely new check-in (fresh stub) is never mistaken for the old one — no matter which message arrives first.

Where it breaks: shredding old stubs too early can let a delayed duplicate check-in "come back to life," since nothing remembers it was already handled — which is exactly why the paper's garbage collection needs causal stability, not a fixed clock.
Candidate vs. commit

A card catalog and the actual book

The card catalog tells you a book is somewhere on the shelf. You still walk over and check it's the right edition, the pages aren't damaged, and nobody's re-binding it under the same call number while you're reading. The catalog answers "where" cheaply; the physical check answers "safe to read," and they're genuinely different questions.

Where it breaks: real libraries rarely rebind a book invisibly while a patron is mid-chapter. This paper's setting assumes a rewrite can happen mid-read, which is exactly why it needs an explicit lock (reader protection), not just good manners.
A bridge from hardware

A coherence directory, minus the hardware guarantee

A CXL/NUMA coherence directory tracks which node holds a cache line so requests don't have to broadcast — this KV catalog does the same job for KV blocks. Where they differ: a hardware directory is wired into a fixed protocol with bounded invalidation latency, so a stale pointer is transient by construction. This software catalog has no such bound.

Where it breaks: because there's no protocol-guaranteed invalidation latency, the paper can't lean on "it'll settle in a few cycles" — it has to substitute an explicit sealed-generation-plus-protection mechanism for what hardware coherence would otherwise enforce for free.
Prefix walk · fail closed

A hallway of numbered doors

You walk a hallway door by door, only ever opening the next one after confirming the previous room led here correctly. The first locked or wrong door, you stop — you keep whatever valid hallway you already walked, you don't skip past the bad door hoping the rest holds up.

Where it breaks: a real hallway's rooms don't quietly get swapped for a different room behind a door you already validated — but a cache generation can be rewritten in place after your walk passed it, which is exactly the failure mode the prefix walk alone doesn't catch.
Positional rewrite

The same coordinates, repainted

A cached key is like a note filed under a GPS coordinate. If someone repaints that exact coordinate to mean a different address, but keeps the same listing, anyone still trusting the old listing walks into the wrong building — the listing wasn't wrong when they read it, but the ground shifted underneath it while they were walking there.

Where it breaks: real coordinates are fixed by geography; a cache generation is mutable by design, which is the actual hole. The fix mirrors the real-world fix for changed addresses: give the new meaning a new listing (new identity/generation) instead of overwriting the old one.
Safe garbage collection

A coat check that never shreds early

A coat check with a stub log can safely shred old stubs only once it's sure every coat with that stub has actually been claimed — not just after a fixed amount of time. Shredding on a timer risks handing your coat to whoever still has a copy of a delayed stub.

Where it breaks: a real coat check has a closing time to fall back on; a distributed catalog doesn't, so it substitutes acknowledgment or causal-stability proof for "everyone's definitely picked up their coat by now."
The full explanation

How it actually works

From the audit method through the catalog, the two safety proofs, and the constructed hazard they guard against.

1 · The audit — classify, don't just diagnose the whole system

For each of 47 operations (drawn from LMCache, Mooncake, vLLM-style paged KV management, and token-selective cache management, plus the pinned LMCache controller source at commit 9cbae8af), the audit extracts a normalized metadata projection: additions of placement/replica/pin/derived-key facts, retractions of live bindings, decisions that commit absence or uniqueness, and predicates over mutable counters or load. An M label means that projected conclusion stays true as source-level state grows — it does not certify the whole surrounding operation as coordination-free.

OperationSystemClassWhy
batched_admitLMCacheMAdds a placement fact; no negative premise.
Chained prefix-hashbothMDeterministic derivation from immutable tokens + parent key.
Prefill token accumulationtoken-selectiveMPure append to the token set.
batched_evictLMCacheNMRetracts a hash-to-location binding.
LRU eviction policyLMCacheNMRecency comparison over mutable timestamps.
allocate_blocksvLLMNMfree_count > 0 — a threshold over a decreasing counter.
📋
Full result: 11 of 47 projected effects monotone in isolation, 36 of 47 non-monotone (Table 2, Appendix A). Six rows carry explicit classification caveats — e.g. positive candidate facts are monotone, but ranking or uniquely selecting a destination from them is a separate, non-monotone step.

2 · Identity — three kinds, one record

A catalog record carries logical, catalog, and physical identity together: a = (σ, h, p, π, t, inst, loc, g, δ), where σ is the semantic namespace (model revision, tokenizer, adapter, KV layout, positional convention, tenant isolation domain), h is the block's logical key, p its expected parent key, π its position map, t a unique admission tag, and (g, δ) the physical generation and payload digest.

h_i = H(σ ‖ h_(i-1) ‖ tokens_i ‖ π_i)   // logical key: names the derivation
// generation g and digest δ name and verify the physical object actually fetched

3 · The catalog — an OR-Set that merges by union

State is S = (A, R): a grow-only set of admitted records and a grow-only set of retired tags. admit(a) may fire only after generation g is fully written and sealed; retire(T) adds the concrete tag set T that its issuer observed. A lookup returns records in A whose tags are absent from R.

merge(S1, S2) = (A1 ∪ A2, R1 ∪ R2)   // associative, commutative, idempotent → converges under any delivery order
💡
Because retire(T) carries the concrete tags it saw, a receiver never reconstructs a deletion from its own stale view — a delayed duplicate admission is excluded correctly even if it physically arrives after the retirement that logically preceded it. Deleting a retirement fact for garbage collection is a separate, non-monotone action; Appendix B states the causal-stability condition that makes it safe.

4 · Root-down prefix safety (Lemma 1)

If a reader begins at the requested root and returns a block at depth i only after validating its expected key and parent edge, then returning depth k means every depth 0…k was validated — no orphan descendant can be part of that hit. A concurrent retirement may cause the first absent/invalid candidate and hence a shorter hit or miss, but the reader never reaches below that point.

5 · The valid-hit condition and committed-hit safety (Proposition 1)

A candidate block is valid only if all of these hold: matching namespace/key/position/parent; an acquired, checked generation; a payload digest match; and reader protection through use.

ValidBlock(q,i,a_i) ⇔
    σ_i = σ_q ∧ h_i = h_i(q) ∧ π_i = π_i(q) ∧ p_i = h_(i-1)(q)
    ∧ Acquire(loc_i, g_i, δ_i) = r_i
    ∧ H(Fetch(r_i)) = δ_i
    ∧ Protected(r_i, use_i)
PremiseRequires
P1Publication follows sealing (generation is complete before it's advertised).
P2Acquisition atomically checks and pins the advertised generation.
P3An acquired generation stays immutable and unreclaimed until release.
P4A semantic/positional rewrite gets a new identity; a byte replacement gets a new generation.
P5The consumer validates every root-down block before commit.
🗂️
Proposition 1: under P1–P5, every commit event satisfies CommitHit(q,k) ⇒ ValidHit(q,k) — despite staleness, reordering, duplication, retirement, re-admission, and address reuse. The critical validate-to-use gap is P2–P3: checking the right identity once is not enough if the generation can be reclaimed or changed before use completes.

6 · The positional-rewrite hazard (Proposition 2)

This is a constructed witness for designs that permit in-place, unfenced rewrites — not a bug report against the LMCache/Mooncake versions analyzed, which use prefix-granular management.

PremiseWhat it assumes
H1Cached keys are position-dependent (true under RoPE).
H2A transformation changes the logical position map from π to π′.
H3The rewritten bytes stay reachable through the same identity/generation while the record still advertises π.
H4A reader overlaps the rewrite.
H5No generation check, copy-on-write, refcount, or lease fences the read.
H6No independent payload-identity check rejects the rewritten bytes before commit.
⚠
Under H1–H6, an execution exists where CommitHit(q,k) holds while ValidHit(q,k) does not — the record's positional fields still match the request, but the fetched bytes no longer match the sealed digest δ, so H(Fetch(r_i)) = δ_i is false and (under H6) that mismatch goes undetected. Falsifying any one of H1–H6 — e.g. publishing the rewrite under a new generation (defeats H3), or checking the digest independently (defeats H6) — blocks the witness.
Follow the numbers, step by step

Worked examples

Four traces carried through with the paper's real numbers: the audit ratio, an OR-Set walkthrough, the rewrite hazard's measured severity, and the catalog's cost and convergence.

① Reading the audit ratio

47 operations, 11 monotone. What fraction is coordination-sensitive, and what does a representative pair of each look like?

  1. Monotone share: 11 ÷ 47 = 23.4%. These persist as facts accumulate — e.g. batched_admit (adds a placement fact, no negative premise) and prefill token accumulation (pure append).
  2. Non-monotone share: 36 ÷ 47 = 76.6%. These retract, decide absence/uniqueness, or threshold mutable state — e.g. batched_evict (retracts a hash-to-location binding) and allocate_blocks (free_count > 0, a threshold over a shrinking counter).
  3. The catalog redesign re-encodes two operations, not two of the 36 rows: batched_admit-style placement admission (row 1, already M in the audit) becomes a plain OR-Set addition, and batched_evict-style observed retirement (row 6, the one NM row this redesign targets) is re-encoded as an addition of observed tags. So at most one audited non-monotone row is re-encoded here. The remaining non-monotone effects — unique-source choice, reclaim, thresholds — are untouched by that redesign.
🗂️
Insight: re-encoding one operation's representation doesn't shrink the audit's 36 — it just moves that one operation's dissemination onto a different, monotone representation. The audit ratio and the design's actual coordination-free surface are two different numbers.

② Tracing an admit → retire → re-admit sequence

A block is admitted, retired, and re-admitted at a new generation, with messages reordered. Does the OR-Set get it right?

  1. Admission 1 publishes tag t1. A = {a(t1)}.
  2. Retirement arrives observing {t1}: R = {t1}. Lookup now excludes t1.
  3. Re-admission at a new generation publishes a fresh tag t2. A = {a(t1), a(t2)}, still R = {t1}.
  4. A delayed duplicate of admission 1 (still tag t1) finally arrives, out of order, after the retirement. Union with an already-present a(t1) changes nothing; t1 is still in R, so it's still excluded.
  5. Result: lookup correctly returns only a(t2), regardless of the arrival order of steps 1–4. A plain G-Set couldn't express step 2; a two-phase set would have permanently blocked step 3.
💡
This is exactly why the paper needed tagged (not Boolean) admission/retirement facts — a bare "present" bit cannot distinguish a delayed copy of the old placement from the new one.

③ How bad is an unfenced rewrite, really?

Fault injection and real-model runs both probe Proposition 2's hazard. Do the numbers agree on "how often" and "how bad"?

  1. Natural race, two 500-trial runs: the reader observed the rewrite in 329 and 346 trials — 65.8% and 69.2%.
  2. Forced schedule: 10 of 10 trials (100%) — confirming this is a genuine race, not a rare fluke the natural runs happened to under-sample.
  3. Real KV tensors, Qwen2.5-1.5B: 8 of 8 unsafe outputs differed from the fresh-prefill baseline; mean first-token KL divergence 8.24.
  4. Real KV tensors, SmolLM3-3B: all final answers matched the baseline, but 1 of 8 top-1 tokens changed; mean KL divergence 0.73 — roughly 11× smaller than Qwen's.
  5. Controls: the safe prefix-boundary-eviction and copy-on-write controls matched the fresh baseline in both models.
🗂️
Insight: the same structural hazard has a model- and task-dependent decoder-level blast radius — SmolLM3 barely wobbled while Qwen diverged sharply. The safety contract deliberately doesn't assume a universal severity; it closes the hazard structurally instead of hoping the blast radius stays small.

④ Catalog cost, convergence, and model-checked safety

Does decentralizing the catalog actually converge cheaply, and does the formal model back up Proposition 1?

  1. Traffic: 2,000 faulted steps delivered 33.8 MB encoded updates ≈ 16.9 KB/step, plus 19.2 MB of full-sync traffic — with delayed/duplicate delivery, partitions, and repeated admit/retire.
  2. Tag accounting: 8,023 retired-tag references (event-side) vs. 27,152 reclaimed tag pairs — the latter sums removals across 4 replicas and multiple GC passes, so it can exceed the former.
  3. GC safety: a fixed-TTL control resurrected a delayed admission; acknowledgment/causal-stability collection did not, across a 90-case matrix.
  4. TLA+: 2 replicas, 2 blocks, 2 locations, old/new generations — 1,733 generated states, 634 distinct, depth 16, zero committed-hit counterexamples in the safe copy-on-write configuration; 6 ablated configurations (e.g. omitting reader protection) each produced the expected counterexample.
  5. Latency, one operating point (500 ops/s, batch 64): replicated p50 4.00–4.18 ms vs. centralized p50 5.00–5.10 ms — roughly ~19% lower at that point (midpoints 4.09 vs. 5.05 ms). The paper explicitly does not generalize this: the original 54-row benchmark's raw data is lost, and other operating points reportedly favored the centralized design.
💡
The honest scope here matters: convergence and the commit-safety proof are demonstrated at bounded scale; the one favorable latency number is explicitly not claimed as a general performance win.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
Under the audit's representation, is "a placement fact is added" monotone? Is "an eviction retracts a placement" monotone?
Show answer
Addition is monotone (M) — more facts can't invalidate an earlier placement fact. Eviction is non-monotone (NM) — it retracts a live hash-to-location binding, which is exactly the kind of conclusion that can be invalidated by a later event.Misconception: conflating "the operation is safe to run" with "its projected metadata effect is monotone." Eviction can be a perfectly correct operation while still being coordination-sensitive as metadata.
Problem 2 · medium
Why can't a plain grow-only set (G-Set) represent catalog retirement, and why can't a two-phase set (add-then-remove, no re-add) either?
Show answer
A G-Set has no remove operation at all, so it can't express "this placement is retired." A two-phase set adds a remove, but once removed, an element can never be re-added — which permanently blocks the same logical block from ever being admitted again after its first retirement. The paper needs repeated admit/retire/re-admit under reordering, which requires tagging each admission uniquely (an OR-Set) so a retirement can target the specific instance it observed.Misconception: assuming "any CRDT" solves the problem. The specific requirement — safe re-admission after retirement, under reordering — rules out both simpler options.
Problem 3 · medium
A retire({t1}) message arrives at a replica before the admit(a1) message carrying tag t1 (reordering). What happens once admit(a1) finally arrives, and why is this safe?
Show answer
retire({t1}) simply adds t1 to R — a plain set addition, independent of whether a1 has been seen yet. When admit(a1) later arrives, a1 enters A. Lookup filters A minus R; since t1 is already in R, a1 is correctly excluded the moment it appears, even though its "physical" admit message arrived after its retirement. Union of monotone additions is commutative and idempotent, so the outcome doesn't depend on delivery order.Misconception: assuming retire must arrive after admit to work correctly. The whole point of the OR-Set design is that arbitrary delivery order still converges to the right answer.
Problem 4 · hard
Proposition 1 needs both P2 (acquisition atomically checks and pins) and P3 (an acquired generation stays immutable and unreclaimed until release). Omitting reader protection in the TLA+ model produces a counterexample. What specific attack does each premise block?
Show answer
P2 blocks a check-then-use race at acquisition time: without atomicity, a reader could validate a generation that is reclaimed or rewritten in the gap before the handle is actually pinned. P3 blocks a race after acquisition: without it, the generation could be reclaimed or changed between validation and the moment the decoder actually consumes the bytes — exactly what the TLA+ ablation (omit reader protection) demonstrates, allowing reclamation between validation and commit.Misconception: thinking a one-time identity check at read time is sufficient. P2–P3 close the "validate-to-use" gap — the object must stay pinned for the whole window, not just at the instant it's checked.
Problem 5 · medium
Root-down walking finds block 3 of a 5-block prefix chain missing or invalid. What happens to blocks 4 and 5, and why can't the decoder just fetch a substitute for block 3 out of order and continue?
Show answer
The walk stops there: it returns a shorter hit through depth 2 (or a miss). Blocks 4 and 5 are never returned as part of the hit. The decoder can't substitute a fetched block 3 out of order because Lemma 1's guarantee is inductive — depth k is only validated if every depth before it, including its parent edge, was validated in sequence. Skipping ahead breaks that induction and could return an orphan descendant.Misconception: believing any set of individually-valid-looking blocks forms a safe hit. Only a root-anchored, sequentially-validated prefix does.
Problem 6 · hard
Name two of H1–H6 and a concrete mechanism that falsifies each, blocking the positional-rewrite witness.
Show answer
H3 (rewritten bytes stay reachable under the same identity/generation while the record still advertises the old π) is falsified by publishing the rewrite under a new generation via copy-on-write — the catalog then advertises the new identity, not the stale one. H6 (no independent payload-identity check before commit) is falsified by verifying H(Fetch(r_i)) = δ_i independently — this rejects the rewritten bytes even if a stale catalog resolves them.Misconception: assuming one fix (e.g. "just add a lock") covers the whole hazard. The contract layers independent defenses — versioning, atomic acquisition, and digest verification — any one of which alone blocks the witness.
Problem 7 · easy
Natural-race fault injection reproduced the rewrite hazard in 65.8–69.2% of trials, not 100%. Forced scheduling reproduced it in 100% of trials. What does this gap tell you about trusting "we tested it and mostly didn't see the bug" as evidence of safety?
Show answer
It tells you natural timing under-samples a deterministic race — the bug is present every time the schedule is actually forced, but ordinary scheduling only hits the bad interleaving roughly two-thirds of the time. A sub-100% natural reproduction rate is not evidence the bug is rare or low-impact; it's evidence you need forced scheduling or model checking to see the hazard's true likelihood.Misconception: treating "the bug didn't show up in most runs" as reassurance. For a genuine race, that just means your test schedule was lucky most of the time.
Problem 8 · medium
The paper reports a favorable p50 latency point (4.00–4.18 ms replicated vs. 5.00–5.10 ms centralized) but concludes "we infer neither a general performance advantage nor a demonstrated reduction in controller load." Why the caution?
Show answer
The original 54-row benchmark (two designs × three rates × three batch sizes × three repeats) had its raw CSV lost; only this one favorable point survived, and the surviving manuscript notes other operating points favored the centralized design. One preserved favorable number can't stand in for an aggregate win/loss tally across the full matrix that no longer exists.Misconception: cherry-picking the one surviving favorable number as the paper's overall performance conclusion, when the authors themselves flag the missing data and decline to generalize.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What's the difference between a "catalog hit" and a "committed hit"?▾
A catalog hit means a lookup found a candidate record — it might be stale. A committed hit means the decoder has passed the full valid-hit check (identity, sealed generation, digest, reader protection) and is authorized to consume those bytes. Catalog convergence only ever produces candidates; the commit contract is the separate gate that turns a candidate into safe reuse.
Q2What does CALM actually prove, and what does the audit borrow from it?▾
CALM (Hellerstein & Alvaro) relates monotonicity to coordination-free, confluent distributed computation: if a program's conclusions are monotone in its inputs, replicas don't need to agree on a current view to compute them correctly. The audit borrows just the monotonicity test, applied operation-by-operation to KV-cache metadata effects, as a design diagnostic — not as a confluence proof for the entire serving stack.
Q3Why can't the catalog just use a simple present/absent boolean flag?▾
A Boolean can't distinguish a delayed copy of an old placement from a legitimate new admission of the same logical block after a retirement — both look like "present" once the delayed message arrives. Unique per-admission tags, removed only by name in a retirement's observed set, resolve that ambiguity without a global order.
Q4Does "monotone" mean "safe" or "correct"?▾
No — it means "doesn't need cross-replica coordination to compute correctly." A monotone fact (like a placement addition) can still feed a non-monotone consumer, like choosing a unique best source or deciding a committed miss. Monotonicity is about the dissemination of a fact, not about whether everything downstream of it is automatically safe.
Q5What exactly is a "generation," and why is it separate from the logical key?▾
The logical key h names what was requested (the derivation from tokens, namespace, and position). The generation g names which physical allocation currently backs that key, and the digest δ verifies the bytes in it. Separating them lets the system detect when the same logical name has come to point at different — or altered — physical bytes.
Q6Is the positional-rewrite hazard a bug found in LMCache or Mooncake?▾
No. The paper is explicit that this is a constructed hazard for a hypothetical design that permits in-place rewrites under the same identity — a conditional witness (Prop. 2, premises H1–H6), not a reported bug in the prefix-granular LMCache or Mooncake versions the audit examined.
Q7Why does garbage collection need causal stability instead of a TTL?▾
Deleting a retirement fact too early can "resurrect" a delayed admission that arrives afterward, since nothing remembers the tag was already retired. A fixed TTL has no relationship to whether every relevant replica has actually seen and acknowledged the retirement; the paper's 90-case matrix shows TTL collection does exactly this resurrection, while acknowledgment/causal-stability collection doesn't.
Q8What's the actual overhead of the catalog — did they measure it?▾
Yes, at bounded scale: a four-replica prototype over 2,000 faulted steps produced 33.8 MB of encoded metadata updates and 19.2 MB of full-sync traffic (excluding KV payloads and network framing). This is prototype metadata cost, not a rack-scale gossip benchmark.
Q9Does bounded TLA+ model checking prove the design correct?▾
Not for an unbounded system — it proves no counterexample exists within the explored bound (here, 1,733 generated states, 634 distinct, depth 16, two replicas/blocks/locations). It's strong bug-finding evidence, and the six ablated configurations that do produce counterexamples show the checker is actually sensitive to the premises it's supposed to be testing.
Q10Why do Qwen2.5-1.5B and SmolLM3-3B respond so differently to the same injected staleness?▾
The paper reports the contrast (8/8 diverged outputs, mean KL 8.24 for Qwen vs. all-final-answers-matched, 1/8 top-1 changes, mean KL 0.73 for SmolLM3) but doesn't isolate which model or task property explains it. The takeaway they draw is that decoder-level severity is model- and task-dependent, so the safety contract shouldn't assume a fixed blast radius.
Q11Does "coordination-free" mean no locking or coordination anywhere in the system?▾
No — only placement admission and observed-retirement metadata dissemination are made coordination-free, and not for the same reason: admission was already monotone under the audit's representation, while observed retirement was audited as non-monotone (it retracts a live binding) and only becomes coordination-free after being redesigned as grow-only, tagged retired facts. Acquisition, reader protection, reclamation, unique-source choice, and rewrite versioning all still require real coordination at commit time.

Glossary, results, and further reading

Every term in one place, the headline numbers, and a source-notes block separating paper facts from framing.

Core terms
CALMConsistency As Logical Monotonicity — the criterion used to test whether a metadata effect can be disseminated without coordination.
Monotone / non-monotone effectA projected metadata conclusion that does (M) or doesn't (NM) remain true as source-level facts accumulate, under a declared representation.
CatalogThe replicated metadata namespace recording where a KV block was placed — distinct from the physical KV object it points to.
OR-Set (Observed-Remove Set)A CRDT where each add gets a unique tag and a remove targets only the tags it has observed, enabling safe re-admission after retirement.
Logical / catalog / physical identityThree identity layers a record carries together: (σ,h,p,π) names the request; (t,inst,loc) names the catalog entry; (g,δ) names and verifies the physical object.
Root-down prefix walkValidating a prefix chain from the root, stopping at the first missing/invalid block (Lemma 1) — handles ordinary incompleteness.
Valid-hit / committed-hit contractThe separate check (Proposition 1) that authorizes a decoder to consume a catalog candidate — identity, sealed generation, digest, reader protection.
Positional-rewrite hazardA constructed witness (Proposition 2) showing that an unfenced in-place rewrite of a block's position map can defeat catalog convergence.
Supporting terms
Generation (g) / digest (δ)The physical allocation currently backing a logical key, and a hash verifying its sealed payload bytes.
Semantic namespace (σ)Model revision, tokenizer, adapter, KV layout, positional convention, and tenant isolation domain — must match for reuse to be valid.
RoPERotary Position Embedding — the mechanism that ties a KV block's meaning to its encoded position.
Causal-stability GCGarbage collection that waits for acknowledgment that a retired tag can no longer be reconstructed by a delayed admission, rather than a fixed TTL.
TLA+ / TLCFormal specification language and bounded model checker used to search for committed-hit counterexamples.
Copy-on-write (CoW)Publishing a change under a new generation/identity instead of mutating the existing one in place — the paper's fix for the rewrite hazard.
Claim scopeThe paper's own caveat: the audit is a design diagnostic, not a confluence proof; the prototype and model are bounded, not a production benchmark.
