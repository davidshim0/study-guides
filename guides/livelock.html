USENIX 1996 · A Field Guide

Answering every interrupt is how a kernel livelocks instead of making progress

A flood of network packets can drive a system to spend 100% of its CPU handling interrupts — and deliver 0% of those packets anywhere. This is the plain-English story of how a small set of scheduling fixes — polling, quotas, and feedback — cures it for good.

📄 "Eliminating Receive Livelock in an Interrupt-driven Kernel" · Mogul & Ramakrishnan 🎓 Basic interrupts/scheduling assumed — primers cover the rest ⏱ ~25 min read
🚦

Schedule packet processing like any other task — poll it, quota it, feed back its queue state — instead of letting fixed interrupt priority claim the CPU unconditionally forever.

Quick glossary
Receive livelockthe system burns 100% of its CPU on packet processing yet delivers nothing — not deadlocked, just making zero forward progress.
MLFRRMaximum Loss-Free Receive Rate — the input rate up to which a well-behaved system's throughput tracks the offered load exactly.
IPL (Interrupt Priority Level)a fixed priority tier a piece of code runs at; higher-IPL code can't be preempted by lower-IPL code, only by still-higher interrupts.
ipintrq4.2BSD's fixed-length queue between the device driver and the IP protocol layer — the queue that overflows first when livelock begins.
screenda user-mode packet-filtering program (an early firewall) used in the experiments to add a realistic extra processing stage per packet.
Polling quotaa cap on how many packets one device callback may handle before yielding, so no single interface can monopolize the CPU.
Queue-state feedbackdisabling input processing when a downstream queue nears full (high water mark) and re-enabling it once it drains (low water mark).
CPU cycle-limit mechanisma timer-based budget that caps the fraction of CPU cycles packet processing may consume per period, guaranteeing time for user-level work.
1Interrupts vs. polling — the basic trade▾

An interrupt lets hardware yank the CPU's attention immediately when an event occurs — fast response, but the CPU pays a fixed dispatch cost every time. Polling means periodically checking "did anything happen?" — cheap per check if nothing happened, but adds latency (you only notice an event on your next check) and wastes cycles checking when nothing's there.

Now you're ready: this paper's whole fix is a hybrid — use an interrupt only to kick off a burst of polling, then poll until there's nothing left to do.
2Interrupt Priority Levels and preemption▾

Code that handles a device interrupt normally runs at a fixed, elevated IPL. While it runs, nothing at a lower IPL — including the rest of the kernel's protocol stack, and all user processes — gets to run at all. A second interrupt at the same IPL also has to wait; only a higher-IPL interrupt can preempt it.

Now you're ready: livelock is a direct consequence of this rule — if events at a fixed high IPL arrive fast enough, nothing below that IPL ever runs again.
3Kernel queues have fixed limits▾

Data handed between stages of kernel processing (e.g. from a device driver to the IP layer) sits in a queue with a fixed maximum length. When a queue is full, the kernel has no choice but to drop the next arrival — there's nowhere to put it.

Now you're ready: where a system chooses to drop packets — early, before spending CPU on them, or late, after wasting work — is one of this paper's central design decisions.
4Livelock is not deadlock▾

Deadlock: the system is stuck and will never recover, even if the load causing it disappears. Livelock: the system is technically still "running" — cycling through work — but makes zero useful progress, and it recovers automatically the moment the overload subsides.

Now you're ready: because livelock is self-correcting once load drops, the paper's fixes are about reshaping behavior under sustained overload, not about breaking a permanent stall.
5Interrupt batching — the existing partial fix▾

Instead of taking one interrupt per packet, a driver can take one interrupt and then drain as many packets as have arrived before returning — amortizing the fixed per-interrupt dispatch cost over a whole burst.

Now you're ready: batching raises the input rate at which livelock begins (the MLFRR), but the paper shows it cannot prevent livelock outright — it only postpones the cliff.
6Fair scheduling across competing tasks▾

A scheduler is "fair" if no one task can starve the others of CPU time indefinitely — usually enforced by giving each task a bounded time slice or work quota before it must yield.

Now you're ready: the paper explicitly imports this idea from process scheduling into interrupt handling — round-robin polling with a per-device quota, so no interface (and no phase of processing) can hog the CPU forever.
The whole story in one place

Receive livelock, in a nutshell

The pathology, the fix, and how the pieces fit together.

Most operating systems schedule network processing entirely through interrupts, which by design have absolute priority over everything else the CPU could be doing. That's fine when packets are rare (a few hundred per second, like a disk). But modern network loads — RPC-heavy client/server traffic, multicast, unsolicited broadcast — can arrive far faster, and unlike a disk, a network interface generates interrupts whether or not the CPU asked for them. There's no natural flow control.

Once the input rate exceeds the reciprocal of the time it takes to process one packet, the fixed-IPL interrupt handler never stops running. Every lower-priority task — including the code that would deliver a packet to an application, or transmit an already-processed one — starves completely. The system is fully busy and fully unproductive: receive livelock.

The paper's fix has four cooperating pieces: (1) move nearly all packet processing out of the interrupt handler into a polling thread that runs at IPL 0 — below all interrupts — and processes each accepted packet to completion, using its own internal round-robin scheduling among devices (the paper notes it's probably impractical to invoke the real process scheduler per packet); (2) give each device callback a quota so no single interface monopolizes the polling loop; (3) use queue-state feedback — high/low water marks on downstream queues — to disable input before a queue overflows, not after; and (4) enforce a CPU cycle-limit so user-level and housekeeping tasks keep making progress even under sustained overload.

The payoff: on a real router (DECstation 3000/300 Alpha), the unmodified kernel peaked at 4,700 pkts/sec and fully livelocked near 6,000 pkts/sec; adding a user-mode firewall filter (screend) to the path made overload behavior turn poor above just 2,000 pkts/sec, though complete livelock still set in around 6,000. The modified kernel showed no livelock at any input rate tested — and separately, even completely idle, a compute-bound user process only received about 94% of the CPU, a fixed baseline overhead unrelated to this fix.

🍯 Key takeaways

  • Fixed interrupt priority gives network events absolute, unconditional priority — with no negative feedback to the source, this is inherently unstable under overload.
  • Interrupt batching raises the livelock threshold (MLFRR) but cannot prevent livelock by itself.
  • The fix: process packets in a polling thread at IPL 0, using its own internal round-robin scheduling, triggered by (not competing with) interrupts.
  • A per-callback quota gives round-robin fairness between interfaces, and between input and output on the same interface.
  • Queue-state feedback disables input before a full queue forces a drop, rather than after wasting CPU on a doomed packet.
  • A CPU cycle-limit mechanism guarantees a slice of CPU to user-level work even under sustained flood.
  • Result: livelock eliminated at every rate tested, peak throughput preserved, no new instability introduced elsewhere.
Five everyday pictures

How to think about receive livelock

Each stands alone; every card ends with where the picture stops being true.

The core failure · Absolute priority

Answering every doorbell ring

If house rules say you must instantly answer the door no matter what, a prankster ringing the bell nonstop means you never eat, sleep, or do anything else — you're always mid-answer. Fixed-IPL interrupts are that rule: a flood of packets means the "answer the door" code runs forever, and everything else — including delivering the last ten visitors' messages — never happens.

Where it breaks: at low ring rates, answering immediately really is the right call — the pathology only appears once rings arrive faster than you can finish one answer.
Queue-state feedback · Water marks

A bathtub with a shutoff valve

Instead of letting a bathtub overflow and only then turning off the tap, you install a float valve: at 75% full, the tap shuts; once it drains to 25%, the tap reopens. That's exactly the screend queue's high/low water marks — the kernel disables input before the downstream queue forces a drop, and reopens it once there's real headroom again, avoiding both overflow and needless thrashing.

Where it breaks: the paper picked the 75%/25% marks "arbitrarily" for one queue feeding one consumer — a bathtub with several drains feeding different rooms would need a more careful, per-queue policy.
Wasted work · Drop early, not late

An inspection line with the reject bin at the very end

Imagine a factory where every part is fully machined, painted, and boxed — and only then quality control checks it and throws out the defective ones. Every rejected part wasted the entire line's effort. That's the unmodified kernel: it does expensive link-level processing on a packet at the highest priority, only to discard it later when a downstream queue is already full — full CPU cost, zero benefit.

Where it breaks: some inspection genuinely can't happen until the part is finished (some packet fields aren't known until parsed) — you can't move every check to the front of the line, only the ones based on information already available (like "is there room downstream at all?").
Fairness · Round-robin quota

A kitchen timer at the buffet table

At a buffet with a line behind you, house rules give each guest a fixed 90 seconds at the serving table before stepping aside for the next person — even if you'd happily fill your plate for ten minutes straight. The polling thread's per-callback quota does the same for network interfaces: each device gets to process a fixed number of packets, then must yield, so a torrent on one interface can't starve every other interface (or output processing) forever.

Where it breaks: a good quota size is context-dependent — too small and you pay overhead switching tables too often; too large (or "infinity") and one queue can still monopolize things downstream, which is exactly what happened with the paper's unbounded-quota experiment.
Guaranteed progress · Cycle limit

A reserved lane for emergency vehicles

A city can reserve one lane exclusively for ambulances and fire trucks, guaranteeing they get through even during total gridlock — regardless of how much other traffic wants the road. The CPU cycle-limit mechanism does this for user-level and housekeeping code: it measures how many cycles packet processing has consumed in a period, and once it crosses a threshold, it disables further input handling until the next period, guaranteeing the "emergency lane" of user CPU time.

Where it breaks: reserving the lane doesn't guarantee anything about the destination — the paper found the user process still got noticeably less CPU than the threshold implied, due to baseline system overhead and the fact that output processing wasn't similarly capped.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The unmodified structure — and why it livelocks

In the 4.2BSD model, a device interrupt runs at a fixed IPL (SPLIMP), does minimal link-layer work, then queues the packet on ipintrq and posts a software interrupt to run the IP layer at a lower IPL (SPLNET) — which can be preempted by another device interrupt. Every queue between stages has a fixed length limit; when full, packets are dropped.

2 · Why batching alone can't fix it

Batching lets a driver process a whole burst of packets per interrupt instead of one, amortizing dispatch overhead — this raises the input rate at which the system saturates (the MLFRR). But it changes nothing about priority: the batched work still all happens at the top of the IPL stack. Push the input rate high enough and the same collapse occurs, just later.

⚠
Also worth noting: giving transmission a lower priority than reception — reasonable-looking, since it reduces packet loss on bursts — causes transmit starvation under sustained overload: packets sit ready to send while the interface idles, because the CPU never gets around to the lower-priority transmit code.

3 · The fix — move work out of high IPL, quota it

The paper considers two general strategies: do (almost) everything at high IPL (so nothing can preempt it mid-packet), or do (almost) nothing at high IPL (so the interrupt handler barely runs at all). They implement the second: the interrupt handler just sets a flag and schedules a polling thread, then returns — it doesn't even re-enable the device's interrupt yet. The polling thread runs at IPL 0 — below every interrupt, but above ordinary process scheduling — and cycles through all registered devices with its own internal round-robin logic, calling each one's callback to process packets to completion (no intermediate queueing and dropping). The paper notes it's probably not feasible to hand each packet off to the real process scheduler individually, hence the thread's own simulated round-robin.

// interrupt handler — does almost nothing
on device_interrupt():
    schedule_polling_thread_if_needed()
    // interrupt stays disabled until polling thread re-enables it
    return

// polling thread — round-robin with quota
for each registered device:
    n = 0
    while device.has_pending_packet() and n < QUOTA:
        process_to_completion(device.next_packet())   // no ipintrq
        n += 1
    if device.queue_empty():
        device.enable_interrupt()   // only now do we re-arm
💡
Why a quota? Without one, one interface's burst can occupy the whole polling loop, so the callback for transmission (which frees buffers for further sends) never runs — reproducing transmit starvation inside the fix itself. The paper found QUOTA = 10–20 packets gave stable, near-optimal behavior on their hardware; QUOTA = ∞ performed worse than doing nothing, because packets were now dropped later (at the output queue) after more CPU had already been spent on them.

4 · Queue-state feedback — disable before you'd have to drop

Even with quotas, a downstream queue (e.g. the queue feeding the user-mode screend filter) can still fill under sustained overload. The fix: watch that queue's occupancy. At a high water mark, disable further input processing; at a low water mark, re-enable it. In the tested configuration the screening queue held 32 packets, with input disabled at 75% full and re-enabled at 25% full — plus a 1-tick timeout in case the consumer is simply stuck.

5 · CPU cycle-limit — guaranteeing user-level progress

Queue feedback protects the kernel's own queues, but says nothing about user processes. The last mechanism directly measures CPU time: over each period (several clock ticks, ~10 msec in the implementation), a running total tracks cycles spent in packet-processing code (read via a cheap hardware cycle counter). If the total exceeds a configured threshold fraction of the period, input handling is disabled until the next period — reserving the remainder for everything else.

🌱
Even with no input load at all, a compute-bound user process only got about 94% of the CPU — the other ~6% is baseline system overhead. So no threshold setting, however generous, can promise a user process 100% of the machine.

6 · Summary of techniques

  1. Use interrupts only to initiate polling — the handler itself does almost no work.
  2. Round-robin poll with a per-callback quota — fair allocation across interfaces and between input/output.
  3. Queue-state feedback — disable input at a high water mark, re-enable at a low one, before a queue is forced to drop.
  4. CPU cycle-limit — cap the fraction of cycles/period spent on packets, guaranteeing time for user and housekeeping code.
  5. Drop early, not late — once a packet is accepted, try to process it to completion rather than discarding it after investing CPU time.
Follow the numbers

Worked examples

Four calculations grounded in the paper's own reported figures.

① Why "14,880 packets/second" is the Ethernet ceiling

The paper notes the router "would probably livelock somewhat below the maximum Ethernet packet rate of about 14,880 packets/second." Where does that number come from?

  1. 10 Mbps Ethernet, minimum-size frame: 64 bytes of frame (header+payload+CRC).
  2. Add fixed overhead: an 8-byte preamble plus a 96-bit (12-byte) mandatory gap between frames = 64 + 8 + 12 = 84 bytes per minimum transmission cycle.
  3. Convert to bits: 84 × 8 = 672 bits per smallest possible packet, including overhead.
  4. Divide into link rate: 10,000,000 bps ÷ 672 bits ≈ 14,880.95 packets/sec — the physical hard ceiling on this link, no matter how fast the CPU is.
🍯
Insight: livelock is a CPU scheduling pathology, not a link-bandwidth one — the router's 4,700 pkts/sec peak throughput is under a third of what the wire itself can even carry, so the CPU, not the network, is the bottleneck being mismanaged (and that peak is not itself a guarantee against livelock — the same unmodified system still collapsed to zero throughput once load rose further).

② The screening queue's hysteresis, in packets

The screening queue held 32 packets; input was disabled at 75% full and re-enabled at 25% full. What does that mean in absolute packet counts?

  1. Queue capacity = 32 packets.
  2. High water mark = 75% × 32 = 24 packets — cross this, and input processing is inhibited.
  3. Low water mark = 25% × 32 = 8 packets — the queue must drain all the way back down to this before input resumes.
  4. The gap: 24 − 8 = 16 packets of hysteresis — deliberately wide, so the system doesn't rapidly flip on/off right at one threshold.
💡
A single threshold (say, "disable and re-enable both at 75%") would thrash every time the queue level bounced across that one line. Two thresholds with real separation is what makes the feedback loop stable.

③ Why the source host could overload the router at all

The router-under-test was a DECstation 3000/300 (SPECint92 = 66.2); the packet source was a DECstation 3000/400 (SPECint92 = 74.7). How much of an edge did the source have?

  1. Ratio: 74.7 ÷ 66.2 ≈ 1.128 — the source was about 12.8% faster on integer workloads.
  2. Why it matters: generating a UDP packet is cheap relative to forwarding one (which requires route lookup, header rewriting, and driver-level work), so even a modest single ordinary host — not a specialized traffic generator — was enough to drive the router past its MLFRR.
  3. The lesson: livelock isn't an exotic attack scenario; it's reachable by unremarkable, everyday hardware imbalances, which is exactly why the paper frames it as a general OS scheduling problem, not a networking edge case.

④ Reading the cycle-limit mechanism's accounting

The paper reports a period of ~10 msec, a polling quota of 5 packets per callback in these experiments, and a forwarding rate around 5,000 pkts/sec at saturation. How much of one period does a single quota-burst consume?

  1. Time per packet at 5,000 pkts/sec ≈ 1 ÷ 5000 = 0.2 msec/packet.
  2. Time to process one quota-burst of 5 packets ≈ 5 × 0.2 msec = 1 msec.
  3. As a fraction of the 10 msec period: 1 ÷ 10 = 10%.
  4. Why this matters: the threshold is only checked after a burst, not continuously — so up to ~10% of a period's worth of "unmetered" processing can slip through per check, which the paper offers as one reason the delivered CPU share for user processes tracked, but consistently undershot, the configured threshold (e.g. under a 100% threshold, the process still didn't get 100% — see baseline 94% overhead above).
🍯
Insight: a budget you only check between bursts is only as tight as the burst size — smaller quotas mean finer-grained enforcement, at the cost of more frequent bookkeeping.
Test yourself

Practice problems

Try each before opening the answer — every one names the misconception it's checking.

Problem 1 · easy
Increasing a driver's interrupt-batching factor raises the MLFRR. Does this eliminate livelock for a sufficiently fast packet source?
Show answer
No. Batching amortizes per-interrupt dispatch cost, raising the input rate at which the system saturates — but the batched work still runs at absolute interrupt priority. Push the source fast enough and the same collapse to zero throughput occurs, just at a higher input rate.Misconception: that livelock is a "how efficient is the interrupt handler" problem. It's a priority-and-feedback problem; efficiency only moves the cliff, it doesn't remove it.
Problem 2 · hard
The paper's own "quota = infinity" modified kernel performed worse than the completely unmodified kernel. Explain why removing the quota backfired.
Show answer
With no quota, one interface's input callback can run to exhaustion, so the polling thread never reaches the output callback that would free transmit buffers and drain the output queue — packets now pile up and get dropped at the output queue instead of the ipintrq input queue. The unmodified kernel does less work per discarded packet (it drops earlier, at ipintrq), so it occasionally catches up with input bursts; the no-quota kernel invests more CPU per packet before discarding it, wasting more work overall.Misconception: that removing a scheduling constraint (the quota) is always at least as good as having one. Here it moved the drop point later, which is strictly worse.
Problem 3 · medium
A queue holds 40 packets. Design high/low water marks following the paper's 75%/25% convention, in absolute packet counts.
Show answer
High water mark = 75% × 40 = 30 packets (disable input here). Low water mark = 25% × 40 = 10 packets (re-enable input here). The 20-packet gap between them is the hysteresis band that prevents rapid on/off flapping.Misconception: that a single threshold (e.g. "toggle at 50%") is simpler and just as good. A single threshold thrashes every time occupancy oscillates near that line; two well-separated marks avoid that.
Problem 4 · hard
The CPU cycle-limit mechanism throttles input processing when its budget is exceeded, but does not similarly cap output processing. What failure mode does this asymmetry risk, and how does the paper's data hint at it?
Show answer
Because only input is capped, the output queue can keep absorbing CPU cycles even after input handling has been inhibited for the period — Figure 7-1's data shows the user process getting less CPU than the configured threshold implies, and the paper explicitly attributes part of that gap to output processing continuing unchecked at high input rates. In principle, sustained heavy output-side work could itself starve user code the same way input once did, just via a different queue.Misconception: that "fixing input" fixes the whole starvation problem. Any unbounded, high-priority phase of processing — input or output — can reproduce the same starvation pattern.
Problem 5 · easy
Why does the paper insist on "drop packets early, rather than late" as a design principle, rather than just dropping wherever convenient?
Show answer
Every stage of processing a packet consumes CPU cycles that are wasted if the packet is eventually dropped anyway. Dropping at the earliest possible point — ideally in the receiving interface's own buffer, before the host even takes an interrupt for it — means zero host CPU is spent on packets that won't survive. Dropping "late," after link-level and protocol processing, means the system pays real cost for work it then throws away, which is precisely what fuels livelock.Misconception: that a dropped packet has the same cost regardless of when it's dropped. Under overload, when it's dropped is the entire difference between "graceful degradation" and "livelock."
Problem 6 · medium
The paper found that even with zero input load, a compute-bound process only received ~94% of the CPU. A colleague argues this is a bug the paper should have fixed. Is it?
Show answer
Not necessarily a bug — it's baseline system overhead (scheduler bookkeeping, clock interrupts, other housekeeping) that exists independent of the packet-processing changes described in the paper. It's an important number to report, though, because it sets a ceiling: no cycle-limit threshold, however generous, can promise a user process more CPU than the system's own fixed overhead allows.Misconception: that the mechanisms in this paper should deliver exactly the configured threshold to user code. They deliver a bound relative to packet processing specifically, not a guarantee against all other system overhead.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is receive livelock the same as being "network-bound"?▾
No. Being network- or CPU-bound just means throughput has plateaued at some maximum — the system is still doing useful work. Livelock is throughput collapsing toward zero as load keeps rising past that point: the system is fully busy but delivering nothing.
Q2Why not just make interrupt handlers faster?▾
Faster handlers raise the MLFRR (the point where livelock begins) but don't remove the underlying cause — unconditional, unbounded interrupt priority with no feedback to the packet source. Given enough input rate, even an infinitely fast handler still eventually loses all its time to dispatch overhead per event; the fix has to change the scheduling model, not just the constant factor.
Q3Why poll instead of just disabling interrupts under load?▾
Simply disabling interrupts (section 5.1's rate-limiting idea) prevents saturation but doesn't by itself guarantee fair progress across multiple event sources or between input and output. Polling, combined with a quota, gives round-robin fairness explicitly; interrupts are used only to wake the polling thread when the system is otherwise idle, keeping low latency at low load.
Q4Does eliminating livelock cost peak throughput?▾
In the paper's measurements, no — the modified kernel's peak throughput (without screend) was comparable to or slightly better than the unmodified kernel's peak; the difference is what happens past that peak: throughput plateaus instead of collapsing.
Q5What's the right quota size?▾
The paper found 10–20 packets per callback near-optimal on their specific Alpha-based router; too small wastes cycles on scheduling overhead per switch, too large risks starving other work (as quota = ∞ demonstrated). The authors explicitly note this should be a tunable parameter, since the right value depends on the CPU and interface hardware.
Q6Does this approach change which packets get dropped under overload?▾
No — the paper is explicit that it keeps the existing "drop-tail" policy (drop whichever packet arrives when a queue is full). Their contribution is entirely about when packets get dropped (as early as possible) and how CPU time is scheduled around that, not about smarter packet-selection policies like RED, which they cite as complementary future work.
Q7Why measure CPU cycles instead of just counting packets processed?▾
Packet counts don't capture cost — some packets take longer to process than others (e.g. through screend vs. direct forwarding). A cycle counter measures actual CPU time consumed directly, using a cheap, high-resolution hardware register, which is a more accurate basis for enforcing a genuine CPU-time budget.
Q8Is this specific to BSD-derived kernels?▾
The specific implementation targets Digital UNIX's (4.2BSD-derived) driver model, but the paper explicitly notes that other systems of the era — VMS, DOS, Windows NT, and even individual Ethernet chips — exhibit the same fixed-priority interrupt structure and are subject to the same pathology. The fix is a general scheduling pattern, not a BSD-specific patch.
Q9What did the paper leave unresolved?▾
They hadn't yet applied the modifications to a high-speed interface driver (e.g. FDDI) to measure end-to-end TCP/NFS throughput effects, hadn't built a tuning interface for the cycle-limit threshold (they patched a kernel variable directly for testing), and note that smarter drop policies (like RED) and symmetric feedback for other queues (e.g. output queues) are natural extensions they didn't implement.
Connecting to your world

Why this still matters for OS & memory-systems design

Four short connections to modern kernel and memory-tiering work.

🧩 A clear conceptual ancestor of Linux NAPI

Linux's NAPI (New API) networking model — interrupt to trigger, poll with a per-device budget (default 64), re-arm the interrupt only when the queue is drained — follows essentially the same pattern as this paper's fix. The "budget" in NAPI plays the same role as this paper's quota, arrived at independently decades later on very different hardware but for exactly the same reason.

🧩 Kernel-bypass I/O takes the "do almost nothing at high IPL" idea to its extreme

DPDK and similar kernel-bypass frameworks eliminate the interrupt-priority problem entirely by mostly disabling interrupts and dedicating a CPU core to pure polling. It's the same insight pushed to an extreme: if you can afford a whole core, skip the hybrid and poll continuously — trading power and core count for the latency this paper's polling thread otherwise has to manage carefully.

🧩 CXL/NVMe interrupt coalescing faces the identical trade-off

Modern NVMe and CXL completion queues let you choose interrupt-per-completion, coalesced-interrupt batching, or pure polling — the same three points on this paper's spectrum, with the same failure mode: an unthrottled completion-interrupt storm under high queue depth can starve other work exactly like receive livelock, which is why NVMe drivers implement their own completion-queue polling budgets.

🧩 Memory-reclaim storms are receive livelock with pages instead of packets

Under severe memory pressure, direct reclaim and page-fault handling can dominate CPU the way unbounded receive interrupts once did — kswapd's background, budgeted, "poll under pressure" design mirrors this paper's polling thread, and cgroup memory pressure feedback (analogous to the paper's queue-state feedback) exists precisely to avoid the reclaim equivalent of livelock.

🍯
The general lesson — any resource governed by unconditional interrupt priority needs a bounded budget plus feedback to its source — is exactly the discipline that page-placement and migration heuristics in DRAM/CXL/NVM tiering systems need under memory pressure: unthrottled migration or reclaim triggered by hot-page interrupts can just as easily livelock a tiering system as an unthrottled NIC can livelock a router.

Sharp questions for seminar

  1. The paper reports quota = ∞ performed worse than the completely unmodified kernel — is that finding hardware-specific, or a structural property of any quota-less polling design? (consider whether the same reversal would occur on today's much deeper hardware queues and higher core counts)
  2. (the paper explicitly flags the value as hardware-dependent and un-tuned by any feedback mechanism)
  3. The screening queue's 75%/25% water marks were chosen "arbitrarily" — what would an ECN/RED-style probabilistic feedback signal (cited as related work) change about the on/off behavior this paper measured? (think about whether hard on/off thresholds versus gradual, probabilistic throttling matters more at higher core counts)
  4. The CPU cycle-limit mechanism throttles input but not output — under what workload would you expect this asymmetry to actually cause an output-side starvation event the paper never tested? (the paper's own data shows unthrottled output eating into the user-process CPU share it promised)
  5. Core terms
Receive livelockThe system is fully busy processing packets yet delivers none — throughput at zero, but recoverable the moment load drops.
MLFRRMaximum Loss-Free Receive Rate — the input rate up to which throughput exactly tracks offered load in a well-behaved system.
IPL (Interrupt Priority Level)A fixed execution priority; code at a higher IPL can't be preempted by code at an equal or lower IPL.
Polling thread + quotaThe paper's core fix: a thread running at IPL 0 that services devices via its own internal round-robin scheduling, each capped at a fixed packet count per turn.
Queue-state feedbackDisabling input at a high water mark on a downstream queue, re-enabling at a low water mark, to drop early rather than late.
CPU cycle-limit mechanismA timer/period-based budget capping the fraction of CPU cycles packet processing may consume, to guarantee user-level progress.
Supporting terms
ipintrq4.2BSD's fixed-length queue between the driver and IP layer — the first queue to overflow as livelock begins.
screendA user-mode packet filter (early firewall) used to add a realistic extra per-packet processing stage in the experiments.
Interrupt batchingDraining a whole burst of arrived packets per interrupt instead of one, amortizing dispatch cost; raises but doesn't remove the livelock ceiling.
Transmit starvationPackets sit ready to send while the CPU never reaches the lower-priority transmit code, because receive processing consumes it all.
Drop-tailThe queueing policy of simply dropping whatever arrives once a queue is full; unchanged by this paper's fix.
SPECint92A standardized integer-performance benchmark score used here to compare the router's and source host's raw CPU speed.
Results at a glance
Source notes

From the paper directly: the definitions of receive livelock and MLFRR; the 4.2BSD IPL/ipintrq structure; the DECstation 3000/300 (SPECint92 66.2) and 3000/400 (SPECint92 74.7) test hardware; peak throughput 4,700 pkts/sec and livelock near 6,000 pkts/sec without screend, degradation above 2,000 pkts/sec with screend; the screening queue's 32-packet limit with 75%/25% water marks; the near-optimal quota range of 10–20 packets; the ~94% baseline CPU availability at zero load; and the cited related work (Jacobson's protocol implementation notes, Traw & Smith's clocked interrupts, RED).

Our framing, not stated verbatim in the paper: the 14,880 pkts/sec Ethernet-ceiling derivation from frame/preamble/gap arithmetic; the SPECint92 ratio (1.128×) computed from the two reported scores; the 1 msec/10 msec (10%) quota-burst accounting in Worked Example ④; the water-mark-in-packets arithmetic; and all Insights/Class Prep connections to NAPI, DPDK, NVMe/CXL completion queues, and memory-tiering reclaim, which are this guide's extrapolations, not the authors'.

Related work (as cited by the paper)

Efficient Protocol Implementation medium

Van Jacobson · SIGCOMM '90 tutorial notes

Source of the "process a received packet directly to completion" technique this paper adopts to improve TCP performance and avoid queueing overhead.

Random Early Detection gateways for Congestion Avoidance hard

Floyd & Jacobson · ACM Trans. Networking · 1993

The smarter, probabilistic drop-policy the paper explicitly leaves as future work, in contrast to the drop-tail policy it keeps unchanged.

Hardware/Software Organization of a High-Performance ATM Host Interface medium

Traw & Smith · IEEE JSAC · 1993

Proposes "clocked interrupts" (periodic polling) as an alternative to per-packet interrupts — the paper contrasts this with its own hybrid interrupt-plus-polling design.
