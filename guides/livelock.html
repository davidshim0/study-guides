Answering every interrupt is how a kernel livelocks instead of making progress

A flood of network packets can drive a system to spend 100% of its CPU handling interrupts — and deliver 0% of those packets anywhere. This is the plain-English story of how a small set of scheduling fixes — polling, quotas, and feedback — cures it for good.

1Interrupts vs. polling — the basic trade▾

An interrupt lets hardware yank the CPU's attention immediately when an event occurs — fast response, but the CPU pays a fixed dispatch cost every time. Polling means periodically checking "did anything happen?" — cheap per check if nothing happened, but adds latency (you only notice an event on your next check) and wastes cycles checking when nothing's there.

Now you're ready: this paper's whole fix is a hybrid — use an interrupt only to kick off a burst of polling, then poll until there's nothing left to do.
2Interrupt Priority Levels and preemption▾

Code that handles a device interrupt normally runs at a fixed, elevated IPL. While it runs, nothing at a lower IPL — including the rest of the kernel's protocol stack, and all user processes — gets to run at all. A second interrupt at the same IPL also has to wait; only a higher-IPL interrupt can preempt it.

Now you're ready: livelock is a direct consequence of this rule — if events at a fixed high IPL arrive fast enough, nothing below that IPL ever runs again.
3Kernel queues have fixed limits▾

Data handed between stages of kernel processing (e.g. from a device driver to the IP layer) sits in a queue with a fixed maximum length. When a queue is full, the kernel has no choice but to drop the next arrival — there's nowhere to put it.

Now you're ready: where a system chooses to drop packets — early, before spending CPU on them, or late, after wasting work — is one of this paper's central design decisions.
4Livelock is not deadlock▾

Deadlock: the system is stuck and will never recover, even if the load causing it disappears. Livelock: the system is technically still "running" — cycling through work — but makes zero useful progress, and it recovers automatically the moment the overload subsides.

Now you're ready: because livelock is self-correcting once load drops, the paper's fixes are about reshaping behavior under sustained overload, not about breaking a permanent stall.
5Interrupt batching — the existing partial fix▾

Instead of taking one interrupt per packet, a driver can take one interrupt and then drain as many packets as have arrived before returning — amortizing the fixed per-interrupt dispatch cost over a whole burst.

Now you're ready: batching raises the input rate at which livelock begins (the MLFRR), but the paper shows it cannot prevent livelock outright — it only postpones the cliff.
6Fair scheduling across competing tasks▾

A scheduler is "fair" if no one task can starve the others of CPU time indefinitely — usually enforced by giving each task a bounded time slice or work quota before it must yield.

Now you're ready: the paper explicitly imports this idea from process scheduling into interrupt handling — round-robin polling with a per-device quota, so no interface (and no phase of processing) can hog the CPU forever.
The whole story in one place

Receive livelock, in a nutshell

The pathology, the fix, and how the pieces fit together.

Most operating systems schedule network processing entirely through interrupts, which by design have absolute priority over everything else the CPU could be doing. That's fine when packets are rare (a few hundred per second, like a disk). But modern network loads — RPC-heavy client/server traffic, multicast, unsolicited broadcast — can arrive far faster, and unlike a disk, a network interface generates interrupts whether or not the CPU asked for them. There's no natural flow control.

Once the input rate exceeds the reciprocal of the time it takes to process one packet, the fixed-IPL interrupt handler never stops running. Every lower-priority task — including the code that would deliver a packet to an application, or transmit an already-processed one — starves completely. The system is fully busy and fully unproductive: receive livelock.

The paper's fix has four cooperating pieces: (1) move nearly all packet processing out of the interrupt handler into a polling thread that runs at IPL 0 — below all interrupts — and processes each accepted packet to completion, using its own internal round-robin scheduling among devices (the paper notes it's probably impractical to invoke the real process scheduler per packet); (2) give each device callback a quota so no single interface monopolizes the polling loop; (3) use queue-state feedback — high/low water marks on downstream queues — to disable input before a queue overflows, not after; and (4) enforce a CPU cycle-limit so user-level and housekeeping tasks keep making progress even under sustained overload.

The payoff: on a real router (DECstation 3000/300 Alpha), the unmodified kernel peaked at 4,700 pkts/sec and then lost throughput steadily as load kept rising; adding a user-mode firewall filter (screend) to the path made overload behavior turn poor above just 2,000 pkts/sec, with complete livelock around 6,000 pkts/sec. The modified kernel (quota 5 without screend, queue feedback with it) showed no livelock at any input rate tested — and separately, even completely idle, a compute-bound user process only received about 94% of the CPU, a fixed baseline overhead unrelated to this fix.

🍯 Key takeaways

  • Fixed interrupt priority gives network events absolute, unconditional priority — with no negative feedback to the source, this is inherently unstable under overload.
  • Interrupt batching raises the livelock threshold (MLFRR) but cannot prevent livelock by itself.
  • The fix: process packets in a polling thread at IPL 0, using its own internal round-robin scheduling, triggered by (not competing with) interrupts.
  • A per-callback quota gives round-robin fairness between interfaces, and between input and output on the same interface.
  • Queue-state feedback disables input before a full queue forces a drop, rather than after wasting CPU on a doomed packet.
  • A CPU cycle-limit mechanism guarantees a slice of CPU to user-level work even under sustained flood.
  • Result: with a small quota (and queue feedback when screend is used), livelock was eliminated at every rate tested and peak forwarding rate rose slightly. Without the quota, the polling kernel livelocked worse than the original.
Five everyday pictures

How to think about receive livelock

Each stands alone; every card ends with where the picture stops being true.

The core failure · Absolute priority

Answering every doorbell ring

If house rules say you must instantly answer the door no matter what, a prankster ringing the bell nonstop means you never eat, sleep, or do anything else — you're always mid-answer. Fixed-IPL interrupts are that rule: a flood of packets means the "answer the door" code runs forever, and everything else — including delivering the last ten visitors' messages — never happens.

Where it breaks: at low ring rates, answering immediately really is the right call — the pathology only appears once rings arrive faster than you can finish one answer.
Queue-state feedback · Water marks

A bathtub with a shutoff valve

Instead of letting a bathtub overflow and only then turning off the tap, you install a float valve: at 75% full, the tap shuts; once it drains to 25%, the tap reopens. That's exactly the screend queue's high/low water marks — the kernel disables input before the downstream queue forces a drop, and reopens it once there's real headroom again, avoiding both overflow and needless thrashing.

Where it breaks: the paper picked the 75%/25% marks "arbitrarily" for one queue feeding one consumer — a bathtub with several drains feeding different rooms would need a more careful, per-queue policy.
Wasted work · Drop early, not late

An inspection line with the reject bin at the very end

Imagine a factory where every part is fully machined, painted, and boxed — and only then quality control checks it and throws out the defective ones. Every rejected part wasted the entire line's effort. That's the unmodified kernel: it does expensive link-level processing on a packet at the highest priority, only to discard it later when a downstream queue is already full — full CPU cost, zero benefit.

Where it breaks: some inspection genuinely can't happen until the part is finished (some packet fields aren't known until parsed) — you can't move every check to the front of the line, only the ones based on information already available (like "is there room downstream at all?").
Fairness · Round-robin quota

A kitchen timer at the buffet table

At a buffet with a line behind you, house rules give each guest a fixed 90 seconds at the serving table before stepping aside for the next person — even if you'd happily fill your plate for ten minutes straight. The polling thread's per-callback quota does the same for network interfaces: each device gets to process a fixed number of packets, then must yield, so a torrent on one interface can't starve every other interface (or output processing) forever.

Where it breaks: a good quota size is context-dependent — too small and you pay overhead switching tables too often; too large (or "infinity") and one queue can still monopolize things downstream, which is exactly what happened with the paper's unbounded-quota experiment.
Guaranteed progress · Cycle limit

A reserved lane for emergency vehicles

A city can reserve one lane exclusively for ambulances and fire trucks, guaranteeing they get through even during total gridlock — regardless of how much other traffic wants the road. The CPU cycle-limit mechanism does this for user-level and housekeeping code: it measures how many cycles packet processing has consumed in a period, and once it crosses a threshold, it disables further input handling until the next period, guaranteeing the "emergency lane" of user CPU time.

Where it breaks: reserving the lane doesn't guarantee anything about the destination — the paper found the user process still got noticeably less CPU than the threshold implied, due to baseline system overhead and the fact that output processing wasn't similarly capped.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The unmodified structure — and why it livelocks

In the 4.2BSD model, a device interrupt runs at a fixed IPL (SPLIMP), does minimal link-layer work, then queues the packet on ipintrq and posts a software interrupt to run the IP layer at a lower IPL (SPLNET) — which can be preempted by another device interrupt. Every queue between stages has a fixed length limit; when full, packets are dropped.

2 · Why batching alone can't fix it

Batching lets a driver process a whole burst of packets per interrupt instead of one, amortizing dispatch overhead — this raises the input rate at which the system saturates (the MLFRR). But it changes nothing about priority: the batched work still all happens at the top of the IPL stack. Push the input rate high enough and the same collapse occurs, just later.

⚠
Also worth noting: giving transmission a lower priority than reception — reasonable-looking, since it reduces packet loss on bursts — causes transmit starvation under sustained overload: packets sit ready to send while the interface idles, because the CPU never gets around to the lower-priority transmit code.

3 · The fix — move work out of high IPL, quota it

The paper considers two general strategies: do (almost) everything at high IPL (so nothing can preempt it mid-packet), or do (almost) nothing at high IPL (so the interrupt handler barely runs at all). They implement the second: the interrupt handler just sets a flag and schedules a polling thread, then returns — it doesn't even re-enable the device's interrupt yet. The polling thread is a kernel thread running at IPL 0, below every interrupt (the paper does not state its scheduling priority relative to user processes), and it cycles through all registered devices with its own internal round-robin logic, calling each one's callback to process packets to completion (no intermediate queueing and dropping). The paper notes it's probably not feasible to hand each packet off to the real process scheduler individually, hence the thread's own simulated round-robin.

// interrupt handler — does almost nothing
on device_interrupt():
    schedule_polling_thread_if_needed()
    // interrupt stays disabled until polling thread re-enables it
    return

// polling thread — round-robin with quota
for each registered device:
    n = 0
    while device.has_pending_packet() and n < QUOTA:
        process_to_completion(device.next_packet())   // no ipintrq
        n += 1
    if device.queue_empty():
        device.enable_interrupt()   // only now do we re-arm
💡
Why a quota? Without one, one interface's burst can occupy the whole polling loop, so the callback for transmission (which frees buffers for further sends) never runs — reproducing transmit starvation inside the fix itself. The paper found QUOTA = 10–20 packets gave stable, near-optimal behavior on their hardware; QUOTA = ∞ performed worse than doing nothing, because packets were now dropped later (at the output queue) after more CPU had already been spent on them.

4 · Queue-state feedback — disable before you'd have to drop

Even with quotas, a downstream queue (e.g. the queue feeding the user-mode screend filter) can still fill under sustained overload. The fix: watch that queue's occupancy. At a high water mark, disable further input processing; at a low water mark, re-enable it. In the tested configuration the screening queue held 32 packets, with input disabled at 75% full and re-enabled at 25% full — plus a 1-tick timeout in case the consumer is simply stuck.

5 · CPU cycle-limit — guaranteeing user-level progress

Queue feedback protects the kernel's own queues, but says nothing about user processes. The last mechanism directly measures CPU time: over each period (several clock ticks, ~10 msec in the implementation), a running total tracks cycles spent in packet-processing code (read via a cheap hardware cycle counter). If the total exceeds a configured threshold fraction of the period, input handling is disabled until the next period — reserving the remainder for everything else.

🌱
Even with no input load at all, a compute-bound user process only got about 94% of the CPU — the other ~6% is baseline system overhead. So no threshold setting, however generous, can promise a user process 100% of the machine.

6 · Summary of techniques

  1. Use interrupts only to initiate polling — the handler itself does almost no work.
  2. Round-robin poll with a per-callback quota — fair allocation across interfaces and between input/output.
  3. Queue-state feedback — disable input at a high water mark, re-enable at a low one, before a queue is forced to drop.
  4. CPU cycle-limit — cap the fraction of cycles/period spent on packets, guaranteeing time for user and housekeeping code.
  5. Drop early, not late — once a packet is accepted, try to process it to completion rather than discarding it after investing CPU time.

M1 · Why kernels were interrupt-driven, and what changed

The original trade. An interrupt lets the CPU do useful work and still respond to an event within a few tens of microseconds. Getting that latency by polling would mean polling tens of thousands of times per second, which is pure overhead when events are rare. In the 1980s they were rare: disks seldom interrupted more than a few hundred times per second, and first-generation LANs gave any one host a few hundred packets per second. So for a general-purpose system the paper agrees that "an interrupt-driven design works best", as long as interrupt handling is a small fraction of CPU time. (Paper §1)

What broke that assumption. Two things, and both matter for every later mechanism.

  • Solicited versus unsolicited events. A disk interrupts only to answer a request the OS issued, so the OS bounds the event rate simply by bounding outstanding requests: the device is "inherently flow-controlled". A network interface interrupts whenever a packet arrives, whether or not the host asked for it.
  • Protocols without flow control. Telnet, FTP and mail ride on flow-controlled transports. Multimedia streams want constant-rate service, RPC systems such as NFS often use datagram transports, and multicast and broadcast deliver load to "innocent-bystander hosts" that never asked for it. None of these slow down when the receiver falls behind.

Why that is dangerous. Once the event rate saturates the host, there is no negative feedback loop to the sources, so the host cannot shed load gracefully. If it keeps running at full throughput and serves sources fairly, it "at least preserves the possibility of stability". If its throughput falls as load rises, the whole system is unstable. That one sentence is the design target for the rest of the paper: not "never drop", but "never let delivered throughput fall as offered load grows". (Paper §1)

The applications that hit it. Host-based routing (almost all firewalls of the time were UNIX or Windows NT boxes, and routing research ran on UNIX), passive network monitoring with the interface in promiscuous mode, and network file service (NFS). Web servers are named as another example. The authors had seen livelock in all three, had shipped fixes, and chose IP forwarding for the experiments because forwarding rate is easy to measure. Section 6 adds that routers and firewalls must be livelock-proof to resist denial-of-service attacks. (Paper §2, §6)

M2 · Requirements, MLFRR, and the three possible overload curves

Throughput is defined as the rate at which the system delivers packets to their ultimate consumers: an application on the host, or, for a router, the next hop on another network. Receiving a packet and then dropping it does not count. (Paper §3)

MLFRR (Maximum Loss Free Receive Rate) is the highest input rate at which the system still delivers everything. A well-designed system tracks the offered load up to the MLFRR and "at higher loads throughput should not drop below this rate". It is a property of the whole system (CPU speed, code path length, interface), not of the NIC alone. The paper notes in passing that inefficient code lowers the MLFRR and so makes livelock more likely, while fast paths and removing unneeded steps postpone it. (Paper §3, §5.4)

The full requirement list (§3): acceptable throughput, reasonable latency and jitter (so avoid long queues, which add latency, and bursty scheduling, which adds jitter), fair allocation of CPU among packet reception, packet transmission, protocol processing, other I/O, system housekeeping and applications, overall stability, and low overhead, especially when overloaded. Transmission is listed explicitly: under input overload the scheduler "must ensure that packet transmission continues at an adequate rate". The host must also stay responsive to management and control requests.

Why a misbehaving host hurts others. A livelocked router loses or delays routing control messages. Neighboring routers may then wrongly conclude a link has failed and propagate bad routes across the wide area, and lost control messages can cause positive feedback in control traffic. So livelock is a network stability problem, not only a local performance problem. (Paper §3, citing Perlman)

The paper's definition: receive livelock is "a state of the system where no useful progress is being made, because some necessary resource is entirely consumed with processing receiver interrupts." It is not deadlock: when the input rate drops, the system leaves the state on its own. A livelocked system "wastes all of the effort it puts into partially processing received packets, since they are all discarded." (Paper §4.2)

M3 · The original packet path: 4.2BSD and Digital UNIX, step by step

Interrupt priority levels (IPL). A device interrupt has a fixed IPL. It preempts every task running at a lower IPL and does not preempt tasks at the same IPL. Kernel code can also raise its own IPL to block interrupts at or below a level (in BSD, the spl calls such as splimp(); standard BSD practice, not described in the paper). The OS process scheduler sits underneath all of this: it schedules processes, and interrupt-level work simply steals time from whatever process is running. In the paper's words, the scheduler "does not participate in any of this activity, and in fact is entirely ignorant of it." (Paper §4.1)

The forwarding path (Figure 6-2 of the paper, and §4.1, §6.3), for one packet entering on interface A and leaving on interface B:

  1. Arrival. Interface A receives the frame into its own buffer (on the DECstation's LANCE-style controller, by DMA into a host buffer named by a receive descriptor ring) and raises a receive interrupt at device IPL.
  2. Receive interrupt handler, at device IPL (SPLIMP). The driver does only buffer management and data-link processing. It then appends the packet to ipintrq, the IP input queue. If ipintrq is at its length limit, the packet is dropped here. With interrupt batching, the handler loops, pulling every packet the interface holds before it returns, so at high input rates "very few interrupts are actually taken".
  3. Software interrupt. The driver posts a software interrupt for the IP layer. In 4.2BSD that runs at SPLNET, which is lower than SPLIMP, so IP processing can be preempted by any later device interrupt. In Digital UNIX the IP layer instead runs as a separately scheduled kernel thread at IPL 0; the priority ordering relative to the driver is the same.
  4. IP input and forwarding. The IP code dequeues packets from ipintrq, decides where each goes, and appends a forwarded packet to the output interface's queue (ifqueue), which also has a length limit; overflow is dropped here. A packet for a local consumer goes to that consumer's socket queue instead.
  5. Transmission. The driver for interface B takes packets from its ifqueue, hands them to the interface, waits until the interface has sent each one, and releases the buffer. Completion is signaled by a transmit interrupt at device IPL, whose handler frees the buffer and starts the next packet.
  6. With screend. The packet instead goes to a socket queue for the user-mode screend process, which reads it with one system call per packet, checks its policy, and writes accepted packets back into the kernel for output. screend runs as an ordinary user process, below everything above.

Why the queues exist. They decouple steps that run at different IPLs, they absorb transient bursts, and they keep the time spent at high IPL short, which the paper wants "to reduce latency for handling certain other events". Every queue has a fixed limit; how to size them "is critical to good performance, but beyond the scope of this paper." (Paper §4.1)

Why the first step got absolute priority. In the early 1980s, adapters had little buffer memory; if the host did not copy a received packet into main memory promptly, the next arrival could overwrite or lose it. So 4.2BSD did the minimum at device IPL and gave that minimum priority over all other network work. Modern adapters receive many back-to-back packets without host help (big buffers or autonomous DMA), which "eliminates much of the rationale" for that absolute priority. The paper notes the problem remains for low-cost interfaces. (Paper §4.1)

// 4.2BSD-style receive path (paper §4.1, §6.3), one input interface
on rx_interrupt():                     // runs at SPLIMP, preempts everything below
    while nic.has_packet():             // interrupt batching: drain what is there
        m = nic.take()                    // buffer mgmt + link-layer work (cost d)
        if ipintrq.full(): drop(m)       // drop point D2: d already spent
        else: ipintrq.append(m)
    post_softint(SPLNET)                  // or wake the IP thread (Digital UNIX)

on softnet():                           // runs at SPLNET, preemptable by rx_interrupt
    while m = ipintrq.remove():
        out = ip_forward(m)              // IP work (cost p, part of it)
        if out.ifqueue.full(): drop(m)  // drop point D3: d + IP work spent
        else: out.ifqueue.append(m); out.start_if_idle()

on tx_interrupt():                     // device IPL: free sent buffer, start next
    free(sent_buffer); start_next_from(ifqueue)

The structural property that matters. Priority falls at every step as a packet moves deeper into the system. The paper's conclusion names this directly: such systems "progressively reduce the priority of processing a packet as it goes further into the system", so under overload the CPU goes to the earliest steps and packets die at later ones, after work has been spent on them. (Paper §9)

From the lecture: why the code looked like this. The professor's first workstation NIC, the 3Com 3C501 EtherLink, had one receive and one transmit buffer on the card and no DMA: the CPU copied packets with programmed I/O, and a second arriving packet corrupted the receive buffer if the first had not been copied out. M4 · How receive livelock arises, and Figure 6-1

The general statement (§1): "Once the input rate exceeds the reciprocal of the CPU cost of processing one input event, any task scheduled at a lower priority will not get a chance to run." Any purely interrupt-driven system with fixed interrupt priorities has this property.

The concrete chain in 4.2BSD (§6.3):

  1. The input rate rises past the rate at which the driver can pull packets off the interface and append them to ipintrq using all of the CPU.
  2. The driver's work at SPLIMP then occupies the CPU continuously, so the IP code (SPLNET, or the IPL 0 thread) never runs.
  3. Nothing removes packets from ipintrq, so it fills, and every later packet is dropped at ipintrq, after the driver has already spent its cycles on it.
  4. Output, screend and every user process get nothing. The CPU is saturated "because it discards each packet after a lot of CPU time has been invested in it at elevated IPL."

The partial-livelock region. Between the MLFRR and full livelock, lower levels get whatever the top level leaves. A simple cost model makes the shape exact (this guide's model, not the paper's). Let each packet cost d seconds at device IPL and p seconds at lower priority. At input rate R the driver consumes a fraction R·d of the CPU, and the rest can forward at most (1 − R·d)/p packets per second. So:

  • output = R while R ≤ 1/(d+p), which is the MLFRR;
  • output = (1 − R·d)/p above it, a straight line falling with slope −d/p;
  • output = 0 at R = 1/d: full receive livelock.

Fitting the two parameters to points read off Figure 6-1 (no screend) gives roughly d ≈ 75 µs and p ≈ 140 µs (inference: a fit, not numbers the paper reports). M5 · Increased latency under overload

Interrupts are supposed to reduce latency, but under bursts they can increase it (§4.3). Because link-level processing runs at a higher IPL than everything after it, a burst that arrives quickly gets link-level processing for every packet in the burst before any higher-layer processing starts on the first one. The first packet's delivery is delayed by almost the time it takes to receive the whole burst.

The paper's example: if the burst is several independent NFS requests, the server's disk "sits idle when it could be doing useful work", because the first request does not reach the NFS code until the whole burst has been taken off the wire. Total work is the same; what changes is the order, and with it when the first useful result appears. Processing each packet to completion (M7, M9) fixes the ordering. The 1996 paper states this problem but reports no latency measurements of its own; it refers to earlier work by Ramakrishnan for experiments.

What breaks if the assumption changes (inference): with a quota (M10), the polling thread processes at most a quota of packets before moving on, so worst-case per-packet delay grows with the quota. The paper says so when discussing quota size: a larger quota amortizes polling better "but increasing the quota could also increase worst-case per-packet latency." (§6.6.2)

M6 · Transmit starvation

The transmit process (§4.4): select packets from an output queue, hand them to the interface, wait until the interface has sent each one, then release the buffer. If the host never gets back to the last two steps, the interface runs out of buffers or descriptors to send with, and stops.

Why transmit gets low priority. Running transmission below reception is "superficially sound": it minimizes the chance that an arriving burst overflows receive buffers. But under long overload a fixed lower priority for transmission leads to reduced throughput or "complete cessation of packet transmission. Packets may be awaiting transmission, but the transmitting interface is idle." That is transmit starvation.

Three ways it happens (§4.4):

  1. The transmitter interrupts at a lower priority than the receiver.
  2. They interrupt at the same priority, but the driver handles the receiver's events first (so a driver that loops on receive work never gets to transmit completions).
  3. Transmit completions are detected by polling, and that polling runs at a lower priority than receive processing.

Why it matters for a router. A forwarded packet counts as throughput only when it leaves on the output interface, so transmit starvation is livelock by another route: input may be accepted at full speed and still produce zero output. The same pathology reappears inside the paper's own first fix: without a quota, the polling thread's input callback never returns, so the transmit callback that frees transmit buffer descriptors never runs (M10). The paper explicitly calls that "similar to the transmit starvation condition identified in section 4.4."

Invariant needed. The step that releases transmit resources must run at least as often as packets are queued for output. Any scheme in which receive work can run unboundedly ahead of transmit-completion work violates it.

M7 · The design space: what the authors considered (§5)

5.1 Limit the interrupt arrival rate. The system checks whether interrupt processing is taking more than its share and, if so, temporarily disables interrupts. Signals that livelock is near: packets being discarded because a queue overflowed; higher-layer protocol processing or user code making no progress; or a measured fraction of CPU cycles spent on packets. The key argument for the queue-overflow signal: once a packet has been processed up to the point of being queued, "it makes more sense to process that packet to completion than to drop it and rescue a subsequently-arriving packet from being dropped at the receiving interface, a cycle that could repeat ad infinitum." So when the host is about to drop a received packet because an internal queue is full, it should disable input interrupts instead, let the already-queued packets finish (which frees buffers), and let new arrivals pile up in the interface's own buffer. Interrupts then need a re-enable trigger: internal buffer space becoming available, or a timer.

For user-level progress, §5.1 sketches the cycle accounting later built in §7: record a fine-grained clock on entry to packet-input code and on exit, sum the deltas, and disable input interrupts if the sum or a running average exceeds a set fraction of elapsed time. On a machine without a fine-grained clock, sample the CPU state on every clock interrupt (clock interrupts usually preempt device interrupt processing); if several consecutive samples land in interrupt processing, disable input interrupts for a few clock ticks. Digital's GIGAswitch uses a similar mechanism.

5.2 Use polling. Rate limiting stops saturation but does not by itself guarantee fair progress between input and output, or among interfaces. Round-robin polling of all event sources does. Pure polling at fixed intervals, however, adds "unacceptable latency" at low load. The paper frames the choice as where policy lives: when task behavior is unpredictable, let the scheduler and interrupts allocate the CPU; when tasks are predictable, the tasks themselves schedule better, and polling relies on voluntary cooperation among them. At low load packet arrivals are unpredictable; at high load the system knows packets arrive at or near saturation. Hence the hybrid rule: "the system polls only when triggered by an interrupt, and interrupts happen only while polling is suspended."

5.3 Avoid preemption. Livelock happens because interrupt processing preempts all other packet processing. Make higher-level packet processing non-preemptable, in one of two ways:

(Almost) everything at high IPL(Almost) nothing at high IPL (the paper's choice)

The thread runs at IPL 0, checks flags, services devices, and re-enables a device's interrupt only when done with it.
What it guaranteesPacket processing cannot be preempted by another arrival, so livelock cannot occur inside the kernel's protocol stack."The polling thread can be interrupted at most once by each device, and so it progresses at full speed without interference."

Either way, the queue between the driver and the protocol code disappears. A packet must still be queued where the protocol stack has to wait for something: data ready for delivery to a user process, or an IP fragment whose companion fragments have not arrived. (§5.3)

5.4 Summary of techniques, verbatim in substance. To avoid livelock: use interrupts only to initiate polling; use round-robin polling to allocate resources fairly among event sources; temporarily disable input when feedback from a full queue or a CPU-usage limit shows other important tasks are pending; drop packets early rather than late, and once a packet is accepted, try to process it to completion. To keep performance high: re-enable interrupts when no work is pending (to avoid polling overhead and keep latency low); let the receiving interface buffer bursts; and eliminate the IP input queue and its overhead.

M9 · The polling thread and the modified driver (§6.4, §6.5)

The fix is the "nothing at high IPL" approach from M7, implemented in Digital UNIX. Two principles drive it: do as much work as possible in a kernel thread rather than in the interrupt handler, and eliminate the IP input queue with its queue manipulations and software interrupt (or thread dispatch). A footnote credits Van Jacobson with already using direct processing to speed up end-system TCP.

Registration. At boot, each modified interface driver registers with the polling system and provides three callbacks: one to handle received packets, one to handle transmitted packets (completions), and one to enable the device's interrupts.

The interrupt handler does almost nothing. It schedules the polling thread if it is not already scheduled, records that this device needs service, and returns. It does not set the device's interrupt-enable flag, "so the system will not be distracted with additional interrupts until the polling thread has processed all of the pending packets."

The polling thread checks every registered device for requested service and calls the appropriate callbacks to do what the interrupt handler used to do. The receive callback calls IP input processing directly instead of queuing the packet, so an accepted packet is processed "as far as possible": to the output interface queue if forwarded, or to a queue for delivery to a process. If the system falls behind, the interface's own input buffer soaks up packets for a while, and excess packets are dropped by the interface "before the system has wasted any resources on it." The thread passes each callback a quota (M10); when the quota is used up the callback must return, which lets the thread round-robin among interfaces and between input and output on one interface. Once all packets pending at an interface are handled, the thread calls that driver's interrupt-enable callback, so the next packet event raises an interrupt again.

Why its own round robin. "It is probably not possible to use the system's real scheduler to control the handling of each packet", so the thread simulates round-robin scheduling of packet processing itself by polling. The paper does not say what scheduling priority the thread has relative to user processes; Section 7 shows that, under flood, it can take all of the CPU from a compute-bound process, so it must at least never yield to one while it has work (inference).

// modified driver + polling thread (paper §6.4, §6.6, §7); names are this guide's
on device_interrupt(dev):              // device IPL, a few instructions
    dev.service_needed = true

    // do NOT re-enable dev's interrupts here

                                                //   straight to ifqueue / socket queue

Invariants the design maintains. (1) While a device has unprocessed events, its interrupts stay off, so a device costs at most one interrupt per polling episode no matter how fast packets arrive. (2) Once the host takes a packet from the interface, it is not dropped at a host queue whose only reason for being full is that a lower-priority stage was starved: the IP input queue is gone, and the remaining queues are the unavoidable ones (output ifqueue, delivery queues). (3) Under overload, excess input is dropped by the interface, where it costs no host CPU. Invariant (2) is only as good as the policy in the thread: without a quota or feedback the output and screend queues still overflow (M10, M11).

Results (Figure 6-3, no screend). The modified kernel with polling and quota 5 (open squares) "slightly improves the MLFRR, and avoids livelock at higher input rates": it tracks input to about 5,000 pkts/s and then stays flat near 5,100 out to about 10,700 offered (approx.). The modified kernel can be configured to behave like the unmodified one ("No polling", open circles); it performs slightly worse than the real unmodified kernel (filled circles), for reasons the authors could not pin down: "slightly longer code paths, different compilers, or unfortunate changes in instruction cache conflicts."

A gap the paper does not discuss (inference). Re-enabling interrupts after finding a device idle has a race: a packet that arrives after the last "anything pending?" check but before interrupts are re-enabled must still produce an interrupt, otherwise it sits in the ring until some later event. Hardware that raises an interrupt whenever an enabled condition is already pending, or a re-check after enabling, closes the window. This is the same lost-wakeup shape that Mesa's wakeup-waiting switch exists to fix for naked NOTIFYs.

M10 · The packet-count quota (§6.6, §6.6.2; Figures 6-3, 6-5, 6-6)

What happens with no quota (gray diamonds in Figure 6-3). Output tracks input to about 5,000 pkts/s, then above the MLFRR "the total throughput drops almost to zero" (approx. 200 to 600 pkts/s from about 6,200 offered). The paper's explanation, step by step:

  1. Packets arrive faster than the input callback can process them, so the receive ring is never empty and the input callback "never finishes its job".
  2. So the polling thread never calls the output-handling callback for the transmitting interface.
  3. So transmit buffer descriptors are never released, and no further packets can be handed to the output interface.
  4. Packets are no longer dropped at the IP input queue (it is gone), but they pile up and are dropped at the output interface queue. That queue "is unavoidable, since there is no guarantee that the output interface runs as fast as the input interface."

Why it is worse than the unmodified kernel. In the no-quota kernel every dropped packet has had both driver work and IP forwarding spent on it before it dies at the output queue. The unmodified kernel drops at ipintrq after only the driver's work, so it "does less work per discarded packet, and therefore occasionally discards them fast enough to catch up with a burst of input packets." When it catches up, the lower layers run and some packets get out.

Why a cliff rather than a slope (this guide's reading). In the unmodified kernel the CPU is split by priority, and the share left for forwarding shrinks continuously as the rate grows (M4), giving a gradual decline. In the no-quota kernel the split is all-or-nothing: either the input callback empties the ring and returns, in which case transmit runs, or it does not, in which case transmit gets nothing at all. Once the rate exceeds what one callback can consume with the whole CPU, the second case holds almost always, so output drops at once. The small residual output plausibly comes from moments when the unpaced source leaves gaps long enough for the callback to return.

With the quota. The thread passes each callback a limit on packets; the callback must return when it is used up. Each round therefore serves input and output on every interface, the transmit callback runs at least once per round, and transmit descriptors keep flowing. Packets the thread cannot get to stay in the interface ring, and overflow is dropped there for free.

Figure 6-5 (no screend, quotas 5, 10, 20, 100, infinity). All five configurations are identical up to the peak near 5,000 pkts/s. Above it they separate into flat plateaus ordered by quota: about 5,100 for quota 5, about 4,400 for 10, about 2,300 for 20, about 600 for 100, and about 200 for infinity (approx.). The paper's summary: "smaller quotas work better. As the quota increases, livelock becomes more of a problem." Why larger quotas lose (inference): between two calls of the transmit callback, the input callback can push up to a quota's worth of fully processed packets toward the output interface. Whatever the output queue and the free transmit descriptors cannot absorb in that interval is dropped at the output queue after full processing, so the wasted fraction of CPU grows with the quota, and the plateau falls.

Figure 6-6 (screend, same quotas). Every quota now rises to a plateau of roughly 2,600 to 2,900 pkts/s from about 3,000 offered (approx.). The queue-state feedback of M11 prevents livelock regardless of quota; small quotas cost about 5% of maximum throughput, which the authors attribute to amortizing polling cost over fewer packets. "Once the quota is large enough to fill the screening queue with a burst of packets, the feedback mechanism probably hides any potential for improvement." This guide's reading of why even quota = infinity is safe here: the feedback inhibits input once the screening queue reaches 24 packets, which ends the input callback's run, so the feedback acts as an implicit quota of a couple of dozen packets.

The recommendation. "A quota of between 10 and 20 packets yields stable and near-optimum behavior, for the hardware configuration tested." For other CPUs and interfaces the value may differ, so it should be tunable. Trade-off: a larger quota amortizes polling overhead and does better with screend; a smaller quota keeps the output path served and limits worst-case per-packet latency. (§6.6.2)

Invariant. Every callback returns within a quota of packets, so the length of one round-robin round is bounded by (quota × per-packet cost × number of callbacks), and every phase of packet processing, on every interface, runs at least once per round. Assumptions: per-packet cost is bounded; callbacks honor the quota; the quota counts packets, so fairness is in packets, not cycles (a callback whose packets are expensive gets more CPU per round; inference). If the quota is too large relative to output queue and descriptor capacity, the drop point drifts back to the output queue.

M11 · Queue-state feedback for screend (§6.6.1, Figure 6-4)

The problem. Polling with a quota fixes in-kernel forwarding, but with screend in the path the modified kernel "performs about as badly as the unmodified kernel" (open squares in Figure 6-4). Because screend runs in user mode, the kernel must queue packets for delivery to it. Under overload this queue fills and packets are dropped, and "screend never gets a chance to run to drain this queue, because the system devotes its cycles to handling input packets." The polling thread is kernel work; screend is a user process; nothing in polling or quotas gives screend CPU.

The paper's explanation: "Feedback from the queue state means that the system properly allocates CPU resources to move packets all the way through the system, instead of dropping them at an intermediate point."

What it protects, precisely. (1) The work already invested in packets that reached the screening queue: those packets are not dropped there. (2) CPU time for screend: in this system the only way kernel-level input processing gives a user process cycles is to stop running, and the inhibit makes it stop. (3) The drop point: while input is inhibited, arrivals collect in the interface buffer and overflow is dropped by the interface, where it costs the host nothing. Output processing is not inhibited, so packets screend writes back still leave.

Why two thresholds (inference, the paper only says the values were arbitrary). A single threshold would toggle input on and off around one occupancy value, paying the cost of disabling and re-enabling interrupts for nearly every packet. The 16-packet gap makes each on and off period last many packets. The high mark below 100% leaves 8 slots of headroom for packets already being processed when the inhibit takes effect (for example the rest of a quota burst). The low mark above 0 keeps screend supplied with work while input restarts, so it does not sit idle waiting for the next packet to get through the whole input path.

Why the signal is trustworthy here, and why it generalizes poorly. The paper suggests the same feedback for interface output queues and packet-filter queues used in network monitoring, but warns those policies "would be more complex, since it might be difficult to determine if input processing load was actually preventing progress at these queues." For screend it is easy: screend is typically the only application, so "a full screening queue is an unequivocal signal that too many packets are arriving." The feedback is correct only if "queue full" really means "the consumer is being starved by input processing". If the consumer is slow for another reason (blocked, waiting, or simply hung), inhibiting input does not help it and stalls everyone else's input; the 1 msec timeout bounds that damage.

Invariant. New input is admitted only while the screening queue has room for what is already in flight, so no packet that has paid for driver and IP work is dropped at the screening queue. Assumptions: one consumer that matters; its lack of progress is caused by CPU starvation; the interface can buffer arrivals during an inhibit (and if not, it drops them cheaply); the inhibit is global to input, so it is fair only when one consumer exists.

M12 · Cycle limits: guaranteeing progress for user-level processes (§7, Figure 7-1)

The problem. Polling and queue feedback make every phase of packet processing progress, but they "are indifferent to the needs of other activities", so user processes can still starve: the user interface becomes unresponsive and housekeeping such as routing-table maintenance stalls. The authors verified it: with a compute-bound process running on the modified router and a flood of minimum-sized packets to forward, the router forwarded at full rate, "as if no user-mode process were consuming resources", and the user process "made no measurable progress".

The hardware it relies on. The Alpha has a high-resolution, low-overhead cycle counter that counts every instruction cycle and can be read in one instruction without data cache misses. Other RISC architectures have similar counters; the paper notes Intel's Pentium has one "as an unsupported feature".

The mechanism, step by step (§7):

  1. Period. CPU usage is measured over a period of several clock ticks: 10 msec in this implementation, "chosen arbitrarily to match the scheduler's quantum". Once per period a timer function clears the running total of cycles spent in packet processing.
  2. Measure each polling loop. When the polling loop starts, read the cycle counter; read it again at the end; the difference is the cycles spent handling input and output packets during that loop. The quota keeps each loop short.
  3. Check. Add the difference to the running total. If the total is above the threshold, input handling is inhibited immediately.
  4. Re-enable. At the end of the current period a timer re-enables input handling. Execution of the system's idle thread also re-enables input interrupts and clears the running total (inference about why: if the CPU is idle, no other task is being starved).
  5. Threshold. A fraction of the cycles in a period. There was no programming interface yet: the authors patched a kernel global holding the percentage allocated to network processing, which the kernel converts to a cycle count.
// cycle limit (paper §7); threshold_pct is the patched kernel global
threshold = threshold_pct/100 * cycles_per_period      // period = 10 ms
every period:  total = 0; enable_input()             // timer
in poll loop:  t0 = rpcc(); service devices (rx + tx); total += rpcc() - t0
               if total > threshold: inhibit_input()    // output keeps running
in idle thread: total = 0; enable_input_interrupts()

  • All four curves share one falling line at low rates: about 77% at 500 pkts/s, 64% at 1,000, 41% at 1,700, 26% at 2,000, 10% at 2,500.
  • 100% threshold: keeps falling, to 0 by about 3,100 pkts/s and stays there. This is the unprotected case: the user process starves, exactly the problem the section opens with.
  • 75%: dips to about 4% near 3,000 pkts/s, then recovers to a plateau near 15 to 16%.
  • 50%: dips to about 29% at 2,000 pkts/s, then recovers to about 44%.
  • 25%: leaves the shared line early (about 70% at 1,200 pkts/s) and holds about 65% from 1,700 on, with no dip.

Why the plateaus sit below 100% minus the threshold. The paper says the curves are "fairly stable" but the user process "does not get as much CPU time as the threshold setting would imply", and gives three reasons. (1) System overhead: even with no input load, the user process gets only about 94% of the CPU. (2) The cycle limit inhibits input processing but not output processing; at higher input rates, before input is inhibited, the output queue fills enough to "soak up additional CPU cycles". (3) Measurement error: the threshold is checked only after a burst of input packets (quota 5 in these runs); at about 5,000 pkts/s such a burst takes about 1 msec, about 10% of the checking period, so the total can overshoot the threshold by up to a burst.

Why the 50% and 75% curves dip. The paper: the dips "probably reflect the cost of handling the actual interrupts; these cycles are not counted against the threshold, and at input rates below saturation, each incoming packet may be handled fast enough that no interrupt batching occurs." Unpacked (inference): the counter brackets only the polling loop, so interrupt dispatch and the thread wake-up it causes are invisible to the limit. At moderate rates every packet costs an interrupt and a thread dispatch, so the true packet cost is much higher than the counted cost, the limit has not yet tripped, and the uncounted overhead eats the user's share. The shared falling line implies roughly 300 µs of user CPU lost per packet per second at low rates, more than the roughly 200 µs per packet implied by a ~5,000 pkts/s forwarding ceiling. As the rate rises, packets start to accumulate between polls, interrupts stay disabled for longer, fewer are taken per packet, the counted share becomes an accurate measure, the limit trips, and the user's share recovers to the plateau. The 25% curve does not dip because its smaller budget is exhausted at a low rate, before uncounted interrupt cost grows large.

What it buys and what it does not. With a cycle limit "the system is subjectively far more responsive, even during heavy input overload", but mostly for local users: network-based interaction such as Telnet "still suffers because many packets are being dropped." The limit trades forwarding throughput for user CPU, since input is cut off for the rest of each period once the budget is spent (inference; Figure 7-1 does not plot the forwarding rate).

Invariant. In every 10 msec period, counted packet-processing cycles exceed the threshold by at most one polling loop. Assumptions and what breaks: a cheap, accurate cycle counter (without one, fall back to §5.1's clock-tick sampling, which is coarser); short loops (a large quota loosens the bound); interrupt cost negligible (false at low rates, hence the dips); output processing bounded (not enforced, hence part of the shortfall); the timer still fires during overload (clock interrupts outrank device work).

M14 · What the paper leaves open, transport effects, and related work (§7.1, §8)

End-system transport protocols (§7.1). The changes could affect TCP and the UDP/RPC/XDR/NFS stack, but the authors had not yet applied them to a high-speed interface driver such as FDDI, so they could not measure that; the test machine easily saturates an Ethernet, so TCP over Ethernet showed no effect. Expected effects: processing a packet directly from the driver into TCP without an IP-level queue (Van Jacobson's technique) should cut receive cost by avoiding queue operations and their locking, and should improve latency of kernel-to-kernel interactions such as TCP acknowledgements and NFS RPCs. Polling should not hurt end-system performance because it happens mainly during input overload; some implementations already poll to avoid transmit interrupts altogether.

Which packets get dropped. Unchanged. "Our modifications do not affect which packets are dropped; we only change when they are dropped." The policy "was and remains 'drop-tail'"; other policies such as RED might do better.

Related work (§8). Earlier uses of polling in UNIX aimed to reduce interrupt overhead, which lowers the chance of overload for a given input rate "but does not prevent livelock". Traw and Smith's "clocked interrupts" poll periodically; they note the polling-frequency dilemma (too high and the system spends all its time polling, too low and latency soars), their analysis seems to ignore interrupt batching, and they allude to an interrupt-prompts-polling scheme. 4.3BSD polled an eight-port terminal interface periodically when the recent input rate exceeded a threshold, to avoid losing characters on a device with little buffering; the authors note one could view that as livelock avoidance. Several router implementations use polling as their primary scheduling method.

Explicitly open or arbitrary in the paper: queue length limits (out of scope), the 75%/25% water marks, the 1-tick timeout, the 10 msec period, the quota value (should be tunable), no API for the cycle threshold, feedback for queues other than screend's, and network-facing responsiveness under overload.

Follow the numbers

Worked examples

Four calculations grounded in the paper's own reported figures.

① Why "14,880 packets/second" is the Ethernet ceiling

The paper notes the router "would probably livelock somewhat below the maximum Ethernet packet rate of about 14,880 packets/second." Where does that number come from?

  1. 10 Mbps Ethernet, minimum-size frame: 64 bytes of frame (header+payload+CRC).
  2. Add fixed overhead: an 8-byte preamble plus a 96-bit (12-byte) mandatory gap between frames = 64 + 8 + 12 = 84 bytes per minimum transmission cycle.
  3. Convert to bits: 84 × 8 = 672 bits per smallest possible packet, including overhead.
  4. Divide into link rate: 10,000,000 bps ÷ 672 bits ≈ 14,880.95 packets/sec — the physical hard ceiling on this link, no matter how fast the CPU is.
🍯
Insight: livelock is a CPU scheduling pathology, not a link-bandwidth one — the router's 4,700 pkts/sec peak throughput is under a third of what the wire itself can even carry, so the CPU, not the network, is the bottleneck being mismanaged (and that peak is not itself a guarantee against livelock: past it, the same unmodified system lost throughput steadily as load rose, and with screend in the path it collapsed to zero at about 6,000 pkts/sec).

② The screening queue's hysteresis, in packets

The screening queue held 32 packets; input was disabled at 75% full and re-enabled at 25% full. What does that mean in absolute packet counts?

  1. Queue capacity = 32 packets.
  2. High water mark = 75% × 32 = 24 packets — cross this, and input processing is inhibited.
  3. Low water mark = 25% × 32 = 8 packets — the queue must drain all the way back down to this before input resumes.
  4. The gap: 24 − 8 = 16 packets of hysteresis — deliberately wide, so the system doesn't rapidly flip on/off right at one threshold.
💡
A single threshold (say, "disable and re-enable both at 75%") would thrash every time the queue level bounced across that one line. Two thresholds with real separation is what makes the feedback loop stable.

③ Why the source host could overload the router at all

The router-under-test was a DECstation 3000/300 (SPECint92 = 66.2); the packet source was a DECstation 3000/400 (SPECint92 = 74.7). How much of an edge did the source have?

  1. Ratio: 74.7 ÷ 66.2 ≈ 1.128 — the source was about 12.8% faster on integer workloads.
  2. Why it matters: the setup was tilted on purpose. The authors chose the router as "the slowest available Alpha host, to make the livelock problem more evident", and slightly modified the source's kernel "to allow more efficient generation of output packets". Generating a packet is also plausibly cheaper than receiving and forwarding one (this guide's reasoning), so one ordinary host was enough to push the router past its MLFRR.
  3. The lesson: livelock needs no exotic attacker: any source that can send faster than the receiver's per-packet cost allows will do, which is why the paper frames it as a general OS scheduling problem and mentions denial-of-service resistance for firewalls.

④ Reading the cycle-limit mechanism's accounting

The paper reports a period of ~10 msec, a polling quota of 5 packets per callback in these experiments, and a forwarding rate around 5,000 pkts/sec at saturation. How much of one period does a single quota-burst consume?

  1. Time per packet at 5,000 pkts/sec ≈ 1 ÷ 5000 = 0.2 msec/packet.
  2. Time to process one quota-burst of 5 packets ≈ 5 × 0.2 msec = 1 msec.
  3. As a fraction of the 10 msec period: 1 ÷ 10 = 10%.
  4. Why this matters: the threshold is only checked after a burst, not continuously — so up to ~10% of a period's worth of "unmetered" processing can slip through per check, which the paper offers as one reason the CPU share left for user processes came out below what the threshold implies (100% minus the threshold). The other two reasons it gives are baseline system overhead (about 94% available even with no input) and output processing, which the limit does not inhibit.
🍯
Insight: a budget you only check between bursts is only as tight as the burst size — smaller quotas mean finer-grained enforcement, at the cost of more frequent bookkeeping.
Test yourself

Practice problems

Try each before opening the answer — every one names the misconception it's checking.

Problem 1 · easy
Increasing a driver's interrupt-batching factor raises the MLFRR. Does this eliminate livelock for a sufficiently fast packet source?
Show answer
No. Batching amortizes per-interrupt dispatch cost, raising the input rate at which the system saturates — but the batched work still runs at absolute interrupt priority. Push the source fast enough and the same collapse to zero throughput occurs, just at a higher input rate.Misconception: that livelock is a "how efficient is the interrupt handler" problem. It's a priority-and-feedback problem; efficiency only moves the cliff, it doesn't remove it.
Problem 2 · hard
The paper's own "quota = infinity" modified kernel performed worse than the completely unmodified kernel. Explain why removing the quota backfired.
Show answer
With no quota, one interface's input callback can run to exhaustion, so the polling thread never reaches the output callback that would free transmit buffers and drain the output queue — packets now pile up and get dropped at the output queue instead of the ipintrq input queue. The unmodified kernel does less work per discarded packet (it drops earlier, at ipintrq), so it occasionally catches up with input bursts; the no-quota kernel invests more CPU per packet before discarding it, wasting more work overall.Misconception: that removing a scheduling constraint (the quota) is always at least as good as having one. Here it moved the drop point later, which is strictly worse.
Problem 3 · medium
A queue holds 40 packets. Design high/low water marks following the paper's 75%/25% convention, in absolute packet counts.
Show answer
High water mark = 75% × 40 = 30 packets (disable input here). Low water mark = 25% × 40 = 10 packets (re-enable input here). The 20-packet gap between them is the hysteresis band that prevents rapid on/off flapping.Misconception: that a single threshold (e.g. "toggle at 50%") is simpler and just as good. A single threshold thrashes every time occupancy oscillates near that line; two well-separated marks avoid that.
Problem 4 · hard
The CPU cycle-limit mechanism throttles input processing when its budget is exceeded, but does not similarly cap output processing. What failure mode does this asymmetry risk, and how does the paper's data hint at it?
Show answer
Because only input is capped, the output queue can keep absorbing CPU cycles even after input handling has been inhibited for the period — Figure 7-1's data shows the user process getting less CPU than the configured threshold implies, and the paper explicitly attributes part of that gap to output processing continuing unchecked at high input rates. In principle, sustained heavy output-side work could itself starve user code the same way input once did, just via a different queue.Misconception: that "fixing input" fixes the whole starvation problem. Any unbounded, high-priority phase of processing — input or output — can reproduce the same starvation pattern.
Problem 5 · easy
Why does the paper insist on "drop packets early, rather than late" as a design principle, rather than just dropping wherever convenient?
Show answer
Every stage of processing a packet consumes CPU cycles that are wasted if the packet is eventually dropped anyway. Dropping at the earliest possible point — ideally in the receiving interface's own buffer, before the host even takes an interrupt for it — means zero host CPU is spent on packets that won't survive. Dropping "late," after link-level and protocol processing, means the system pays real cost for work it then throws away, which is precisely what fuels livelock.Misconception: that a dropped packet has the same cost regardless of when it's dropped. Under overload, when it's dropped is the entire difference between "graceful degradation" and "livelock."
Problem 6 · medium
The paper found that even with zero input load, a compute-bound process only received ~94% of the CPU. A colleague argues this is a bug the paper should have fixed. Is it?
Show answer
Not necessarily a bug — it's baseline system overhead (scheduler bookkeeping, clock interrupts, other housekeeping) that exists independent of the packet-processing changes described in the paper. It's an important number to report, though, because it sets a ceiling: no cycle-limit threshold, however generous, can promise a user process more CPU than the system's own fixed overhead allows.Misconception: that the mechanisms in this paper should deliver exactly the configured threshold to user code. They deliver a bound relative to packet processing specifically, not a guarantee against all other system overhead.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is receive livelock the same as being "network-bound"?▾
No. Being network- or CPU-bound just means throughput has plateaued at some maximum — the system is still doing useful work. Livelock is throughput collapsing toward zero as load keeps rising past that point: the system is fully busy but delivering nothing.
Q2Why not just make interrupt handlers faster?▾
Faster handlers raise the MLFRR (the point where livelock begins) but don't remove the underlying cause — unconditional, unbounded interrupt priority with no feedback to the packet source. As long as each packet costs the handler some nonzero time, a high enough input rate still consumes the whole CPU at interrupt level; the fix has to change the scheduling model, not just the constant factor.
Q3Why poll instead of just disabling interrupts under load?▾
Simply disabling interrupts (section 5.1's rate-limiting idea) prevents saturation but doesn't by itself guarantee fair progress across multiple event sources or between input and output. Polling, combined with a quota, gives round-robin fairness explicitly; interrupts are used only to wake the polling thread when the system is otherwise idle, keeping low latency at low load.
Q4Does eliminating livelock cost peak throughput?▾
In the paper's measurements, no — the modified kernel's peak throughput (without screend) was comparable to or slightly better than the unmodified kernel's peak; the difference is what happens past that peak: throughput plateaus instead of collapsing.
Q5What's the right quota size?▾
The paper found 10–20 packets per callback near-optimal on their specific Alpha-based router; too small wastes cycles on scheduling overhead per switch, too large risks starving other work (as quota = ∞ demonstrated). The authors explicitly note this should be a tunable parameter, since the right value depends on the CPU and interface hardware.
Q6Does this approach change which packets get dropped under overload?▾
No — the paper is explicit that it keeps the existing "drop-tail" policy (drop whichever packet arrives when a queue is full). Their contribution is entirely about when packets get dropped (as early as possible) and how CPU time is scheduled around that, not about smarter packet-selection policies like RED, which they cite as complementary future work.
Q7Why measure CPU cycles instead of just counting packets processed?▾
Packet counts don't capture cost — some packets take longer to process than others (e.g. through screend vs. direct forwarding). A cycle counter measures actual CPU time consumed directly, using a cheap, high-resolution hardware register, which is a more accurate basis for enforcing a genuine CPU-time budget.
Q8Is this specific to BSD-derived kernels?▾
The specific implementation targets Digital UNIX's (4.2BSD-derived) driver model, but the paper explicitly notes that other systems of the era — VMS, DOS, Windows NT, and even individual Ethernet chips — exhibit the same fixed-priority interrupt structure and are subject to the same pathology. The fix is a general scheduling pattern, not a BSD-specific patch.
Q9What did the paper leave unresolved?▾
They hadn't yet applied the modifications to a high-speed interface driver (e.g. FDDI) to measure end-to-end TCP/NFS throughput effects, hadn't built a tuning interface for the cycle-limit threshold (they patched a kernel variable directly for testing), and note that smarter drop policies (like RED) and symmetric feedback for other queues (e.g. output queues) are natural extensions they didn't implement.
Connecting to your world

Why this still matters for OS & memory-systems design

Four short connections to modern kernel and memory-tiering work.

🧩 A clear conceptual ancestor of Linux NAPI

Linux's NAPI (New API) networking model — interrupt to trigger, poll with a per-device budget (default 64), re-arm the interrupt only when the queue is drained — follows essentially the same pattern as this paper's fix. The "budget" in NAPI plays the same role as this paper's quota, arrived at independently decades later on very different hardware but for exactly the same reason.

🧩 Kernel-bypass I/O takes the "do almost nothing at high IPL" idea to its extreme

DPDK and similar kernel-bypass frameworks eliminate the interrupt-priority problem entirely by mostly disabling interrupts and dedicating a CPU core to pure polling. It's the same insight pushed to an extreme: if you can afford a whole core, skip the hybrid and poll continuously — trading power and core count for the latency this paper's polling thread otherwise has to manage carefully.

🧩 CXL/NVMe interrupt coalescing faces the identical trade-off

Modern NVMe and CXL completion queues let you choose interrupt-per-completion, coalesced-interrupt batching, or pure polling — the same three points on this paper's spectrum, with the same failure mode: an unthrottled completion-interrupt storm under high queue depth can starve other work exactly like receive livelock, which is why NVMe drivers implement their own completion-queue polling budgets.

🧩 Memory-reclaim storms are receive livelock with pages instead of packets

Under severe memory pressure, direct reclaim and page-fault handling can dominate CPU the way unbounded receive interrupts once did — kswapd's background, budgeted, "poll under pressure" design mirrors this paper's polling thread, and cgroup memory pressure feedback (analogous to the paper's queue-state feedback) exists precisely to avoid the reclaim equivalent of livelock.

🍯
The general lesson — any resource governed by unconditional interrupt priority needs a bounded budget plus feedback to its source — is exactly the discipline that page-placement and migration heuristics in DRAM/CXL/NVM tiering systems need under memory pressure: unthrottled migration or reclaim triggered by hot-page interrupts can just as easily livelock a tiering system as an unthrottled NIC can livelock a router.
