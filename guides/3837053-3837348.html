HotStorage 2026 · A Field Guide

Let every cache hit stay in user space — but let the whole system decide who gets evicted

NVMe SSDs are fast enough that the kernel's own bookkeeping — syscalls, VFS, page-cache locks — is now the bottleneck for small I/O. Nexus moves the hot path out of the kernel without losing the one thing a kernel is good at: seeing every process at once.

Quick glossary, then eight primers

Acronyms first, then the concepts Nexus assumes. Primers are collapsed — open what's unfamiliar.

Quick glossary

NVMeModern SSD interface; sub-10 μs latency, millions of IOPS — fast enough that software is now the bottleneck.
IOPSI/O operations per second — throughput measured in requests, not bytes.
VFSVirtual File System — the kernel's abstraction layer that every file-system call passes through.
POSIXThe standard read/write/pread API; "buffered I/O" means these calls go through the page cache.
DMADirect Memory Access — the device writes/reads memory without CPU copying; needed for zero-copy I/O.
IPCInter-process communication — e.g. messages between a client and a coordinating server process. Costly per call.
SPDK / io_uring / eBPFKernel-bypass building blocks: a user-space NVMe driver, an async syscall batching API, and in-kernel sandboxed programs.
U2K / K2U queueNexus's shared-memory queues that operate without system calls: user→kernel (report new pages) and kernel→user (request evictions).
data plane (user space, fast) control plane (kernel, coordinating) kernel page cache / ext4 baseline
1Why NVMe flipped the bottleneck▾

Spinning disks were slow enough that software overhead was noise. NVMe SSDs now answer in single-digit microseconds — comparable to a single syscall's own cost (~160 ns of ring transition, register save, page-table switch, per call, before the device is even touched).

Now you're ready: the paper's whole premise is that for small I/O, the kernel's fixed per-call tax, not the device, is what you're paying for.
2Buffered I/O vs. direct I/O▾

Buffered I/O goes through the OS page cache: writes land in memory and return immediately (writeback happens later); reads may already be cached. Direct I/O bypasses the cache and talks straight to the device — used for huge sequential transfers where caching adds no value.

Now you're ready: almost all kernel-bypass work (SPDK, XRP, BypassD) only accelerates direct I/O. Buffered I/O — the default for nearly everything — was left untouched.
3What the kernel page cache actually does▾

It keeps recently-used file pages (4 KB units) in memory, indexed by a radix tree per file, so reads can be served without touching disk. It also does readahead (prefetch sequential pages), async writeback, and LRU-style reclamation when memory is tight.

Now you're ready: Nexus's design goal is to keep all of this — "file-level caching" — but move the fast-path parts to user space.
4Where the kernel's per-I/O cost comes from▾

Three stacked costs: (i) the syscall itself (~160 ns), (ii) traversal through VFS and the filesystem (indirect calls, locks), (iii) page-cache bookkeeping (radix-tree lookup, refcounts, LRU list maintenance). Cost (iii) is unavoidable for any cache; (i) and (ii) are pure kernel-path tax.

Now you're ready: a user-space cache eliminates (i) entirely and shrinks (ii) to one short code path — which is exactly where Nexus's speedups come from.
5Kernel-bypass frameworks — and their blind spot▾

SPDK put the whole NVMe driver in user space. io_uring, XRP, BypassD, UnICom each shave layers off the direct-I/O path. None of them touch buffered I/O: BypassD and UnICom, for instance, fall back to the ordinary POSIX path whenever a request doesn't meet their direct-I/O preconditions (e.g., isn't page-aligned and block-sized).

Now you're ready: this is the gap Nexus targets — the paper's claim is that no existing approach meets all four properties (file-level caching, low overhead, memory efficiency, hardware agnosticism) for buffered I/O at once, not that nobody has looked at user-space caching before.
6Process address-space isolation▾

Each process has its own private virtual memory. A user-space cache library linked into process A cannot see or reclaim memory held by process B's copy of the same library — there's no shared view, unlike the kernel which maps all physical pages in one global structure.

Now you're ready: this single fact is why naive "port the page cache to user space" designs (Aeolia, uFS) end up with static, per-process memory pools instead of one shared, dynamically-sized cache.
7CLOCK and "recently accessed" bits▾

CLOCK is a cheap approximation of LRU: pages are arranged in a ring with a reference bit each; a sweeping hand clears bits and evicts the first page it finds already clear. The kernel normally gets reference bits for free from the MMU's hardware Accessed bit.

Now you're ready: Nexus has no MMU hook in user space, so it fakes the reference bit with a plain memory store into a shared bitmap on every hit.
8DMA and zero-copy I/O▾

Normally the device DMAs data into a kernel buffer, then the CPU copies it into the user buffer — one extra copy. "Zero-copy" means the device DMAs straight into memory the application will read, with no intermediate copy.

Now you're ready: Nexus's cache memory is pre-mapped for DMA once at allocation time, so the same segment serves as both the cache backing store and the I/O target — no per-I/O mapping, no extra copy.
The whole story in one place

Nexus in a nutshell

Four requirements, why a naive port fails one of them, and the split that fixes it.

A user-space page cache needs four properties to be a real substitute for the kernel one: file-level caching (not just raw blocks), low access overhead (no syscalls on the hot path), efficient memory usage across all processes (not a fixed pool per process), and hardware agnosticism (no exotic CPU features). Existing systems each sacrifice one: block-level caches (TriCache, ScalaCache) drop file semantics; uFS pays IPC on every operation; Aeolia needs a specific CPU instruction (user interrupts) and still uses static per-process pools.

The obvious move — port the kernel's page cache straight into user space — gets three of the four for free (file-level, low-cost, hardware-agnostic), because cache hits never need to leave one process. It fails the fourth: memory efficiency. Isolated address spaces mean one process can't see another's idle pages, so each process ends up hoarding a static pool, exactly like Aeolia.

Nexus's fix: split the design into a user-space data plane that does every cache hit and I/O submission as a plain function call (zero syscalls), and a lightweight kernel control plane that — because the kernel already sees every process — handles global memory allocation and cross-process cold-page reclamation. The two sides talk through shared-memory segments and two shared-memory queues (U2K, K2U) that operate without system calls, never blocking the hot path.

The payoff: up to 3.4× throughput for small sequential reads and 1.5–1.8× for random reads over ext4, with the memory pool growing and shrinking dynamically across processes — something no prior user-space cache achieved.

🗝️ Key takeaways

  • Small buffered I/O (32 B–4 KB) costs 2–15× more than an "ideal" in-memory user-space cache — and dominates real server/mobile workloads.
  • No prior system hits all four properties at once: file-level caching, low overhead, cross-process memory efficiency, hardware agnosticism.
  • A straight port of the kernel page cache gets 3 of 4 — it fails only on cross-process memory efficiency, because address spaces are isolated.
  • Nexus's fix: data plane (user space, 0 syscalls) for hits + I/O submit; control plane (kernel module) for global allocation + reclamation.
  • Two-level allocation: coarse 4 MB segments from the kernel, fine 4 KB pages managed entirely in user space.
  • Reclamation is fully async: a shared access bitmap + CLOCK + U2K/K2U queues, off the critical path.
  • Result: up to 3.4× sequential, 1.5–1.8× random read throughput over ext4.
Six everyday pictures

How to think about Nexus

Each stands alone; every card ends with where it breaks down.

The core move · Data vs. control plane

A tollbooth you don't stop at

Imagine a highway where every car used to stop and show ID at a booth (a syscall) even for a 30-second trip. Nexus installs an E-ZPass lane: cars with cached credentials (cache hits) cruise straight through, in-lane. The booth still exists — for the rare car that needs a new permit (a new memory segment) — but almost nobody waits at it.

Where it breaks: E-ZPass still needs a central authority issuing passes. Nexus's "pass issuer" is the kernel control plane — it just operates rarely enough to stay invisible.
The problem a naive port doesn't fix

Two apartments, no shared hallway

Each tenant (process) has their own locked apartment (address space) and stocks their own fridge (memory pool). Tenant A's fridge sits half-empty while Tenant B is out of milk — but A can't see into B's apartment, so nobody reallocates. Just porting the page cache into each apartment recreates this: fast, but wasteful.

Where it breaks: real apartments don't want a shared fridge for privacy reasons; memory pages have no such constraint — which is exactly why routing coordination through the kernel (the one party who can see every apartment) is the natural fix, not a compromise.
Two-level allocation

Buying by the pallet, selling by the can

A warehouse buys soda by the pallet (a 4 MB segment, via a rare syscall) but a cashier rings up individual cans (4 KB pages) all day without calling the warehouse each time. Most of the work happens at can-granularity, entirely on the shop floor (user space); only restocking crosses to the warehouse (kernel).

Where it breaks: a real warehouse call is slow regardless of size; here the point is specifically that pallet-sized calls are rare — not that they're individually fast.
Global reclamation · CLOCK + async queues

A night janitor, not a bouncer

A bouncer checking every guest at the door (synchronous eviction on every allocation) would create a line. Instead, Nexus posts a janitor who sweeps overnight: guests just raise a hand when they use a seat (a store into the shared access bitmap), and the janitor later walks the room with a clipboard (CLOCK), politely asking stragglers to move (K2U eviction request) — never interrupting the party.

Where it breaks: a janitor sweeps on a fixed schedule; Nexus's kernel module polls queues continuously, so "overnight" here really means "whenever cycles are free, off the critical path."
Zero-copy I/O

Delivering straight to the shelf

A normal delivery drops boxes at the loading dock (kernel buffer), and a worker re-carries them to the shelf (CPU copy to user buffer). Nexus pre-wires the shelf itself as the delivery address (DMA mapping set up once, at segment allocation), so the truck (NVMe device) unloads directly where the data will be read.

Where it breaks: the "pre-wiring" has to happen once per segment, not per delivery — which is exactly why Nexus does the DMA mapping at allocation time and reuses it, rather than per I/O.
The full explanation

How it actually works

Three challenges, three solutions, then how disk I/O rides the same architecture.

1 · Why a straight port isn't enough

Porting the kernel page cache to user space gets file-level caching, low-cost access, and hardware agnosticism for free — a hit never needs to leave the process. It fails memory efficiency: private memory is invisible across isolated address spaces, so without extra machinery each process is stuck with a static pool (exactly uFS's and Aeolia's failure mode).

2 · Challenge 1 — system-wide dynamic allocation

Nexus uses two-level allocation. The control plane maps coarse 4 MB segments into user space, backing the cache in 4 KB pages; segment metadata is shared between kernel and user. On the fast path, the data plane carves pages out of already-mapped segments with zero kernel involvement. Only when the local segment pool runs dry does it make a (rare, and pre-fetchable) syscall for a new one.

3 · Challenge 2 — global cold-page reclamation

Eviction is inherently off the critical path: no cache hit needs to wait for it. Nexus exploits this. Each segment carries a shared access bitmap; a hit sets its bit with one plain store. New pages are announced to the kernel via the shared-memory U2K queue (no syscalls). The kernel module polls all processes' U2K queues, reads the access bitmaps directly from shared memory, and runs CLOCK globally across every process's pages to find cold ones — then requests their release via the K2U queue. Segment-level reclamation works the same way one level up: the control plane periodically retires the least-utilized segments (e.g. greedy: fewest active pages).

4 · Challenge 3 — a unified kernel-bypass data plane

Readahead, writeback and fsync must run without blocking the caller, but user space has no interrupt handler to learn when NVMe I/O finishes. Nexus's answer is lazy polling: submit the I/O straight to the NVMe submission queue and return immediately; check the completion queue later, at a convenient point (before the next readahead, during eviction, or at an explicit fsync). Synchronous reads just do submit→poll→return directly. The same segment memory serves as both cache storage and the DMA target, mapped once at allocation — so prefetch and writeback ride one zero-copy DMA path straight into the cache; a cache hit still copies the cached bytes into the caller's buffer, it just never has to pass through a separate kernel buffer first.

💡
Why this works: async operations don't need an answer now — only before their result is actually used. Lazy polling isn't free, but it avoids blocking the caller and sidesteps the complexity of interrupt-driven control-plane involvement — the cost of checking completion just gets folded into work the caller was already going to do (the next readahead, an eviction sweep, an explicit fsync).
Follow the numbers

Worked examples

Four calculations straight from the paper's reported figures.

① Why 32 B sees a bigger speedup than 128 KB

The kernel pays a roughly fixed per-call cost regardless of I/O size. At 32 B sequential reads, the ideal user-space cache is 15× faster; at 4 KB, only 2.6×; at 128 KB, ~2×. Why does the ratio shrink?

  1. Model the kernel's cost as fixed_tax + transfer_cost(size). The fixed_tax (syscall + VFS + indexing) barely changes with I/O size.
  2. At 32 B, transfer_cost ≈ 0, so total time ≈ fixed_tax almost entirely. Removing that tax (user space) removes almost the whole latency → ~15×.
  3. At 128 KB, transfer_cost (the memcpy / DMA of 128 KB) is now large relative to fixed_tax, so even eliminating fixed_tax only shaves a smaller fraction off the total → ~2×.
  4. Conclusion: the fixed tax is "the dominant source of overhead for small I/O" exactly because it doesn't scale — which is why the paper frames Nexus around small buffered I/O specifically.

② Segment/page math

A segment is 4 MB; a page is 4 KB. How many pages does one control-plane allocation buy the data plane, and why does that matter?

  1. Pages per segment = 4 MB ÷ 4 KB = 1024 pages.
  2. One syscall (segment request) therefore supplies 1024 subsequent page allocations that need zero kernel involvement.
  3. Amortized cost: even at the (worst-case) ~160 ns syscall cost, that's under 0.16 ns of kernel tax per page amortized — negligible next to a ~400 ns–μs-scale cache operation.
  4. Insight: this 1024:1 ratio is what makes "rare syscalls, hidden by async pre-allocation" a credible claim rather than hand-waving.

③ Reading Table 2: two real speedup rows

From the paper's throughput table (ext4 / Nexus, GiB/s), single-threaded: 32 B sequential read is 0.09 / 0.23; 4 KB random read is 5.0 / 7.6.

  1. 32 B sequential: 0.23 ÷ 0.09 = 2.56× — matches the paper's reported "2.6×," within rounding.
  2. 4 KB random: 7.6 ÷ 5.0 = 1.52× — matches the paper's "1.5×" for 4 KB random reads at 1 thread.
  3. Why random < sequential at the same size: sequential access is CPU-cache-friendly (hardware prefetchers keep lines warm along the short path); random access pays the full cost of radix-tree-style indexing on every lookup, a cost no software layer removes.
  4. At 32 threads, this isn't a uniform shrink toward 1.0×: small, cache-friendly sequential cases hold onto much of their advantage (32 B sequential is still around 2.9× at 32 threads in Table 2), while larger or random-access cases drop toward 1.0× as the platform's ~56 GiB/s memory bandwidth ceiling and 8-core contention come to dominate the software path.

④ Why Aeolia's 32 KB cache unit backfires

Aeolia uses a 32 KB cache/I/O unit for high sequential throughput, but a 4 KB request still consumes a full 32 KB slot and incurs up to ~13.5 μs of disk I/O (vs. ~4 μs for a 4 KB I/O).

  1. Space amplification: one 4 KB request occupies 32 KB ÷ 4 KB = 8× the cache space it needs.
  2. Latency amplification: 13.5 μs ÷ 4 μs ≈ 3.4× the disk latency a right-sized 4 KB I/O would cost.
  3. Why it happens: a fixed large unit optimizes one access pattern (long sequential) at the expense of the other (small, scattered) — exactly the small-I/O-dominant pattern the paper shows is most common.
  4. Nexus's choice: a 4 KB page unit (matching the kernel's own page size) avoids this trade entirely — no amplification either way.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
An engineer says "Nexus is fast because it bypasses the page cache, like direct I/O." Is that right?
Show answer
No — it's the opposite. Nexus keeps the page cache (file-level caching, readahead, writeback) but relocates it to user space so cache hits need no syscall. Direct I/O skips caching altogether; Nexus's whole point is to make buffered I/O (the cached path) fast, not to avoid caching.Misconception: conflating "faster than ext4" with "bypasses caching." Nexus bypasses the kernel, not the cache.
Problem 2 · medium
Why can't a pure user-space library (no kernel component at all) achieve both low overhead and efficient cross-process memory usage simultaneously?
Show answer
Low overhead wants zero IPC/syscalls on the hot path. Cross-process efficiency wants one party to see every process's memory usage and reallocate it — but address-space isolation means no single user-space process has that view without IPC to the others (uFS's approach), which reintroduces overhead. The kernel is the only entity that already spans every process for free, which is why Nexus routes only the *coordination* (not the hot path) through it.Misconception: that "more user space is always better." The isolation that makes user space fast is the same isolation that makes cross-process coordination expensive there.
Problem 3 · medium
The paper says eviction is "inherently asynchronous." What property of eviction justifies moving it entirely off the critical path?
Show answer
No cache hit needs an eviction to have already happened — hits either find the page present or they don't, and misses just trigger a fresh fetch. Nothing about serving the *next* request depends on *this* request's page being reclaimed *now*. That slack is what lets Nexus defer eviction to whenever the kernel module gets around to polling.Misconception: that eviction must keep pace with allocation in real time. It only needs to keep pace on average, over the segment pool's lifetime — not per-request.
Problem 4 · hard
Nexus fakes a hardware Accessed bit with a shared bitmap written on every hit. What would go wrong if, instead, every hit sent a message through the U2K queue?
Show answer
The U2K queue is for infrequent events (new page allocations); routing every single cache hit through it would turn the hot path into a producer against a shared queue — adding synchronization/contention cost to literally every access, defeating the "plain function call" goal. A plain memory store to a bitmap bit, by contrast, is as cheap as a cache hit itself and needs no queue machinery.Misconception: that "communicate with the kernel" always means "send a message." A shared-memory bit the kernel reads later is communication without a queue, and it's far cheaper when the event (a hit) is this frequent.
Problem 5 · medium
Why does the speedup from Nexus shrink as thread count rises from 1 to 32 in Table 2, even though Nexus is still "faster" by the paper's own account?
Show answer
Two separate ceilings take over: the platform's memory bandwidth (~56 GiB/s) is shared by both ext4 and Nexus, so once a workload is bandwidth-bound, no software-path improvement can add more throughput; and beyond 8 threads (the available P-cores), CPU contention degrades both systems similarly. Nexus's advantage is in the *software path*, which matters less once hardware limits dominate.Misconception: that a diminishing speedup means the optimization "stopped working." It means a different resource (bandwidth, cores) became the bottleneck — Nexus still wins, just by a smaller margin.
Problem 6 · easy
A colleague argues ScalaCache is strictly better than Nexus because it also achieves low-cost cache access. What's missing from that comparison?
Show answer
ScalaCache is a block-level cache (no file-level semantics — no readahead/writeback at file granularity), needs custom hardware support, and uses a static per-process pool (not memory-efficient across processes). Low access cost is only one of the four properties; ScalaCache trades away three of the other four to get it.Misconception: judging a system on a single axis. The paper's whole framing is that all four properties must hold simultaneously — a win on one doesn't make a system "better" overall.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is Nexus a filesystem?▾
Not primarily — it's an I/O stack layered to provide file-level caching and I/O submission; the paper doesn't describe it as replacing ext4's on-disk format, just the hot-path access to cached data and the I/O path to disk.
Q2Does the "zero system calls" claim apply to every operation?▾
It applies to cache hits, page lookups, and I/O submission on the data plane. Rare events — requesting a new 4 MB segment when the local pool is exhausted — still need one syscall, but these are infrequent and can be hidden with async pre-allocation.
Q3How is Nexus different from mmap-based caching?▾
mmap-style designs rely on page faults to trigger kernel involvement, which is synchronous and adds latency on the critical path. Nexus avoids page-fault-driven synchronization entirely: hits are served directly from pre-mapped segments, and eviction is communicated via async queues instead of faults.
Q4What exactly does the kernel control plane do that a daemon process couldn't?▾
A user-space daemon (like uFS's server process) requires IPC for every coordinated operation. The kernel module instead lives at a privilege level that already maps every process's relevant shared memory, so it can read access bitmaps and queues directly — the "coordination" is just reads/writes to shared memory, not message-passing to a separate process.
Q5Why 4 MB segments specifically?▾
The paper gives 4 MB as the example coarse-grained unit; the design principle is that segments should be large enough that kernel-crossing calls are rare relative to the much more frequent 4 KB page-level operations, not that 4 MB is uniquely optimal.
Q6Does Nexus help write-heavy workloads too?▾
The preliminary evaluation in this paper focuses on reads; the motivation section notes RocksDB's small WAL writes and SQLite's 24 B frame headers as evidence of small buffered *writes* being common, but write throughput numbers aren't yet reported — it's listed under future work (realistic workload evaluation).
Q7What happens if the U2K or K2U queue fills up?▾
The paper flags this explicitly as open future work — "how to handle queue overflow" is listed as a practical aspect still to be studied, alongside when to harvest messages to minimize combined overhead.
Q8Is crash consistency handled?▾
Not yet — the paper lists protecting dirty user-space pages against application crashes, without reintroducing kernel overhead, as a key open problem for future work.
Q9Does Nexus need special CPU features like Aeolia's user interrupts?▾
No — hardware agnosticism is one of its four required properties. It uses ordinary shared memory, lock-free queues, and standard NVMe submission/completion queues, no exotic instructions.
Q10What's the single biggest open question before this could ship?▾
Crash consistency for dirty user-space pages, arguably — losing acknowledged writes on a crash is a correctness issue, not just a performance one, and the paper is explicit that it's unresolved.
