Answering the verifier's objections before it raises them — not one phone call at a time

The Linux eBPF verifier rejects safe programs it can't prove with simple math. One fix phones userspace for help, mid-verification, every single time it gets stuck. This is the plain-English story of PCB, which does all that phoning in advance.

Ten-minute primers

Eight ideas the paper assumes you know

Collapsed by default — open what's unfamiliar, skip what isn't.

1What eBPF is, and why a verifier exists at all▾

eBPF lets you load small programs into the Linux kernel at runtime — for networking, observability, security — without writing a kernel module or rebooting. Because this code runs with kernel privilege, something has to guarantee it can't crash the kernel or read memory it shouldn't.

That something is the verifier: a static analyzer that walks every possible path through the bytecode before the kernel JIT-compiles and attaches it, rejecting anything it can't prove safe.

Now you're ready: both BCF and PCB exist because that same verifier is, by design, cautious — and cautious analyzers reject things that are actually fine.
2Non-relational domains — why the verifier loses the plot▾

The verifier tracks each register's possible range independently (an interval, or a bit-pattern called a tnum). That's cheap and fast, but it throws away relationships between registers — it can't remember "R2 always equals 15 minus R0," even if that's exactly why an access is safe.

This is the single root cause of most verifier rejections of genuinely safe code.

Now you're ready: every example in this guide (R1's bound at P9/P12) is the verifier losing exactly this kind of relationship.
3"Fighting the verifier"▾

Developers write BPF logic in C or Rust and compile it. Because the verifier's precision is brittle, a harmless change — a different optimization level, a different compiler version — can restructure the generated bytecode just enough to trip a rejection that didn't happen before. Nothing about program behavior changed; only how it's expressed did.

Now you're ready: PCB's promise is that anything its own backend emits is guaranteed to load — the backend and the kernel are kept in lockstep, so this frustration disappears for code compiled through it.
4Backward slicing and refinement conditions▾

When a check fails, you can trace backward from the offending access to every instruction that could have influenced it — a chain of registers and the branches that gated them. Turn that chain into a logical formula (a fresh symbolic name for each unknown input, plus the branch conditions taken) and you get a refinement condition: a precise statement of exactly when the access would be unsafe.

Now you're ready: both BCF and PCB build the same kind of refinement condition — PCB just decides when to solve it.
5SMT solving, UNSAT, and proof objects▾

Feed the refinement condition to an SMT solver and ask it to prove the condition is UNSAT — never true for any input. If it succeeds, the access is safe for every possible value the interval analysis couldn't rule out. Modern solvers can also emit a proof object: a sequence of small logical steps that a much simpler program can re-check without re-solving anything.

Now you're ready: the solver is untrusted and can be wrong or malicious — safety comes entirely from re-checking its proof, not from trusting its verdict.
6Proof-carrying code, the classic idea▾

Necula & Lee's 1996 insight: an untrusted code producer can ship native code together with a formal proof that it obeys a safety policy. The consumer (here, the kernel) doesn't need to derive anything — it just checks the attached proof with a small, trusted checker, which is far simpler than doing the original analysis.

Now you're ready: PCB is this idea applied narrowly — only the program points the verifier's own analysis can't already handle get a carried proof.
7BCF's interactive refinement loop▾

BCF wires an SMT solver into the load path itself. When the kernel verifier hits an unprovable check, it suspends, pins its entire verification state to a file descriptor, returns an error with the refinement condition attached, waits for userspace to solve it and call back in with a proof, checks that proof, and resumes exactly where it stopped. This repeats for every rejected check in the program.

Now you're ready: a program with n rejection points costs BCF n+1 separate bpf() syscalls, each one a round trip to userspace and a live, paused verifier state sitting in the kernel in between.
8Path exploration and pruning▾

The verifier explores the program's control-flow graph depth-first, one path at a time. To avoid exploring exponentially many paths, at designated points it compares the current abstract state to states it has already fully explored — if an earlier state subsumes the current one, it prunes and stops early, trusting the earlier result covers this path too.

Now you're ready: a userspace program that wants to predict exactly which checks the kernel will reject must reproduce this exploration order and pruning logic precisely — get it wrong and your proofs won't line up with what the kernel actually needs.
The whole story in one place

PCB in a nutshell

The problem, the reordering that fixes it, and how the pieces connect.

The eBPF verifier's non-relational domains reject some programs that are actually safe. BCF fixes this by inserting an untrusted SMT solver into the load path: whenever the kernel verifier gets stuck, it suspends, ships the problem to userspace, and waits for a proof before resuming — once per rejected check, in the same syscall sequence that loads the program.

Proof-Carrying-BPF (PCB) asks a simple question: why solve these proofs during the load at all? PCB attaches a userspace mirror of the kernel verifier to the BPF backend. While compiling, the mirror runs the exact same analysis the kernel will run, finds every point where the kernel's default domains will fail, and proves each one with an SMT solver offline. All the resulting proofs are bundled together, indexed by a hash of their refinement condition, and shipped alongside the bytecode. At load time, the kernel verifier runs exactly as before — and the moment it would fail a check, it hashes its own refinement condition, looks up the matching proof in the bundle, and validates it with the same small in-kernel checker BCF uses. No suspension, no saved state, no trip to userspace — ever, at load time.

The payoff: PCB accepts all 360 previously-rejected production objects (Calico, Cilium, BCC, Inspektor Gadget) — matching BCF's coverage exactly — while eliminating BCF's 40,672 kernel-to-userspace round trips entirely, and loading every single object faster: 1.28×–49.5×, median 1.66×, average 3.4×.

🍯 Key takeaways

  • The verifier's non-relational domains lose relationships between registers, causing false rejections of safe programs.
  • BCF fixes rejections on demand, during the load — suspend, round-trip to userspace, resume — once per rejected check.
  • PCB moves that same fix offline, into the compiler backend, via a userspace mirror of the kernel verifier.
  • Proofs are bundled and indexed by a hash of the refinement condition, so the kernel can find the right proof in one pass.
  • Soundness is untouched: the kernel still independently re-checks every proof with the same small in-kernel checker.
  • Result: identical acceptance coverage (360/360), zero load-time round trips (down from 40,672), 1.28×–49.5× faster loads.
Seven everyday pictures

How to think about PCB

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core problem · Non-relational domains

Two clipboards, no stapler

A customs officer tracks the contents of box A on one clipboard and box B on another. He can tell you what's in each box individually — but if the safety rule is "A's weight plus B's weight must be under 20kg," he can't check it, because the fact linking the two clipboards was never written down anywhere. The eBPF verifier's interval/tnum domains are exactly these two clipboards: each register tracked alone, no memory of R2 = 15 − R0.

Where it breaks: the officer could in principle staple the clipboards together (a relational domain like Zones). The paper's point is that doing so in the kernel raises complexity; PCB stays with the two clipboards and instead answers the occasional cross-check by hand, offline.
The mechanism · Proof-carrying code

Show your work, don't redo it

A teacher grading a hard algebra problem doesn't want to re-derive the factoring from scratch — she wants to see each step and confirm it follows validly from the last. If a student writes "(x−2)(x−3)=0, therefore x=2 or x=3," checking that is trivial even if finding it wasn't. PCB's SMT solver is the (untrusted) student working out the factoring; the kernel's in-kernel proof checker is the teacher, who only ever checks steps, never solves.

Where it breaks: a dishonest student can't fool a careful teacher, but a buggy checker could be fooled by a malformed "proof." That's why the in-kernel checker is small and its rule set (AND_ELIM, BIT_BLAST, POLY_NORM, CONTRA) is narrow enough to scrutinize closely.
Why PCB is faster · Precompute, don't interrupt

A take-home exam with footnotes already written

Imagine turning in an exam where, instead of waiting for the grader to call you with clarifying questions one at a time (and you calling back with each answer), you anticipated every possible question and attached a footnote answering it up front. The grader reads straight through, consulting a footnote only when needed — no phone calls, no waiting. That's BCF's per-check round trip versus PCB's precomputed bundle.

Where it breaks: writing all those footnotes takes real effort — PCB's backend still has to run the full analysis and SMT solving, it just does so once, offline, rather than per-load. For a program run only once (e.g. patched at deploy time), that footnote-writing cost isn't amortized.
Matching · Hash-indexed bundle

A coat-check ticket

You hand over your coat and get a numbered ticket. Come back later, hand over the same ticket, and the attendant hands back your exact coat — no searching through the whole rack. The kernel does the same thing: it builds its own refinement condition when it hits a stuck check, hashes it, and uses that hash as a ticket to look up the matching proof in PCB's bundle — an exact match, confirmed before the proof is trusted.

Where it breaks: if you hand the attendant a ticket from a different coat check (a stale bundle from a different kernel version or program build), there's no coat waiting — the lookup simply fails and the kernel falls back to rejecting, safely.
Robustness · Fail-closed staleness

A permit for a lot that just got repainted

Your parking permit specifies space B-12 — valid until the lot is repainted and the spaces renumbered, at which point it's simply void and you park nowhere until you get a new one. A PCB proof bundle is tied to the exact program and kernel-verifier version it was built for; if either changes, its refinement conditions no longer match what the kernel computes, the hash lookups miss, and the program is rejected — safely, not unsoundly.

Where it breaks: a stale permit just means "go park somewhere else" (rebuild, ~a minute for the median object); it never means "park illegally and hope no one checks" — the kernel re-derives and re-verifies its own condition regardless.
Trust boundary · Independent re-checking

A notary who always checks your ID anyway

You can tell a notary your name is whatever you like; a good one doesn't take your word for it — she checks your ID herself, every time, regardless of what you claim. The kernel treats both the userspace mirror and the SMT solver this way: it never trusts their say-so that a program is safe. It independently reconstructs the refinement condition and re-validates the proof with its own small checker before accepting anything.

Where it breaks: the notary can't detect a forged ID that's convincingly made; the in-kernel checker's guarantee is only as strong as its own logic (AND_ELIM, BIT_BLAST, etc.) being correctly implemented — a bug there, not in the solver, would be the real soundness risk.
Why it's hard to build · Exact pruning

Cloning a stunt double's exact moves

A stunt double doesn't just perform a similar-looking fall — the choreography must match the lead actor's blocking exactly, frame for frame, or the edit won't cut together. PCB's userspace mirror has to reproduce the kernel verifier's depth-first exploration order and its state-subsumption pruning precisely, or it will predict rejections at the wrong points, generate proofs for conditions the kernel never actually asks about, and the hash lookups will miss.

Where it breaks: a stunt double only needs to look right on camera; the mirror's fidelity is checked mechanically against 3,267 kernel selftests, and any divergence (false accept or false reject) is treated as a bug to fix, not an acceptable approximation.
The full explanation

How it actually works

Section by section, following the paper's own P9/P12 example through to the kernel's final check.

1 · The problem, concretely

A 16-byte stack buffer holds valid offsets [0,15]. A program computes R0 ∈ [0,15] from a helper call, then R2 = 15 − R0, also ∈[0,15]. A branch on R2 < 4 splits execution. On the fall-through path (R2 ≥ 4, i.e. R0 ≤ 11), the program reads at offset R0 + 4 — always within bounds, since R0 ≤ 11 ⇒ R0+4 ≤ 15. But the kernel verifier tracks R0 and R2 as independent intervals and forgets their relationship, so it computes R1's interval as base+[4,19] — apparently out of bounds — and rejects.

2 · Building the refinement condition

The kernel traces backward from the failing read at P9: R1 is set at P8, gated by the branch at P7, which reads R2, which is computed from R0 at P5–P6, which traces back to the helper call at P0. Every one of P0–P8 joins the slice. The only leaf — R0 — gets a fresh symbolic name, sym. Substituting forward, R1 at P9 is (sym & 15) + 4, and the path condition from the branch is 15 − (sym & 15) ≥ 4. The access is unsafe exactly when:

(15 − (sym & 15) ≥ 4) ∧ ((sym & 15) + 4 > 15)   # refinement condition for P9

If an SMT solver proves this UNSAT, the access is safe for every value of sym.

3 · The proof, checked step by step

CVC5 derives a contradiction. The in-kernel checker replays exactly these steps, trusting only the small rule set below:

StepRuleEstablishes
0ASSUME(15 − (sym&15) ≥ 4) ∧ ((sym&15) + 4 > 15)
1AND_ELIM15 − (sym&15) ≥ 4
2AND_ELIM(sym&15) + 4 > 15
3BIT_BLAST(sym&15) ≤ 15
4POLY_NORMfrom 2 & 3 ⇒ (sym&15) ≥ 12 ⇒ 15−(sym&15) ≤ 3
5CONTRAstep 4 (≤3) contradicts step 1 (≥4) ⇒ False
💡
Deriving False from the assumption proves the assumption itself is UNSAT — so the unsafe case can never occur, and the read at P9 is safe. The checker only needs to confirm each step follows the stated rule; it never has to find this derivation itself.

4 · From BCF's loop to PCB's single pass

BCF runs this same construction inside the load: suspend at P9, round-trip for the proof, resume, hit P12, suspend again, round-trip again, resume, accept. PCB's userspace mirror — attached to the compiler backend — runs the identical kernel-faithful analysis while compiling, discovers that P9 and P12 will both fail, builds and proves both refinement conditions with CVC5, and stores {condition, proof} pairs in a hash table keyed by the condition's hash.

5 · Staying faithful — and failing safely

Because the mirror must predict exactly where the kernel will reject, it needs the kernel's own exploration order, subsumption checks, liveness-gated comparisons, and loop bookkeeping — not an approximation of them. The authors built this test-driven against the kernel's 3,267-test selftest suite, porting the kernel's exact logic wherever a divergence appeared: false accepts (soundness bugs) fixed first, false rejects (lost coverage) fixed after.

🛡
Soundness never depends on the mirror being right. The kernel independently reconstructs its own refinement condition and re-validates the proof itself. If the mirror is stale relative to a kernel update, or a proof bundle is stale relative to a recompiled program, the hash lookup simply misses — the program is rejected, not unsoundly accepted.

6 · Bundle reuse and its limits

Production programs sharing a library (e.g. Cilium's datapath) often trigger refinement in the same library functions, so several of Cilium's 17 objects built with the same compiler produce byte-identical bundles — these can be cached and reused rather than rebuilt per load. This caching amortizes the one-time build cost across many loads of the same, or equivalent, bundle. It doesn't help a program generated fresh and loaded exactly once (e.g. per-node constant patching at deploy time); such cases pay the full build cost for a single load, where BCF's on-demand proving remains competitive on total end-to-end latency even though PCB still loads the object itself faster.

Worked examples

Four calculations straight from the paper's own figures and evaluation numbers.

① Why the kernel rejects a provably-safe read

R0 ∈ [0,15]; R2 = 15 − R0; branch keeps only R2 ≥ 4 on the fall-through path; read at offset R0 + 4. Show the access is always safe, and why the kernel can't see it.

  1. R2 ≥ 4 on this path ⇒ 15 − R0 ≥ 4 ⇒ R0 ≤ 11.
  2. Offset accessed = R0 + 4 ≤ 11 + 4 = 15 — exactly the buffer's last valid byte.
  3. So the true range of the offset is [4, 15], entirely inside the 16-byte buffer.
  4. The kernel, tracking R0 and R2 separately, only knows R0 ∈ [0,15] (from the earlier mask) — it never re-derives R0 ≤ 11 from R2's branch, so it computes the offset as [4, 19].
  5. [4,19] spills 4 bytes past the buffer's end ⇒ rejected, despite the true range being safe.
🍯
Insight: the gap between [4,15] (true) and [4,19] (tracked) is exactly the relationship — R2 = 15 − R0 — that a non-relational domain cannot express.

② Deriving False from the refinement condition

Confirm the proof in the table above actually closes — plug in the arithmetic by hand.

  1. Assume the unsafe case: 15 − (sym&15) ≥ 4 and (sym&15) + 4 > 15.
  2. From the second clause: (sym&15) > 11, i.e. (sym&15) ≥ 12 (integers).
  3. Since sym&15 masks to 4 bits, (sym&15) ≤ 15 always (BIT_BLAST) — consistent so far, ≥12 and ≤15 both hold.
  4. Substitute (sym&15) ≥ 12 into the first clause's form: 15 − (sym&15) ≤ 15 − 12 = 3.
  5. But the first clause assumed 15 − (sym&15) ≥ 4. 3 ≥ 4 is false — contradiction, so the original assumption (the unsafe case) can never hold. The read is safe.
💡
This is precisely what steps 1–5 of Figure 3 do in the solver's formal proof language — the arithmetic above is the human-readable version of AND_ELIM → BIT_BLAST → POLY_NORM → CONTRA.

③ How many round trips does PCB actually remove?

BCF performs 40,672 kernel-to-userspace round trips across the 360-object corpus; PCB performs zero. What does that mean per object, and for total time?

  1. Average round trips per object = 40,672 ÷ 360 ≈ 113 — most objects need over a hundred individual suspend/resume cycles under BCF.
  2. Total corpus load time: BCF = 6,886 s; PCB = 2,181 s.
  3. Time removed: 6,886 − 2,181 = 4,705 s, about 68% of BCF's total load time for the whole corpus.
  4. Aggregate speedup = 6,886 / 2,181 ≈ 3.16× — close to, but distinct from, the paper's reported per-object average of 3.4× (an average of ratios, not a ratio of totals; a few objects with huge speedups pull the per-object average above the aggregate figure).
🍯
Insight: the benefit scales with how many refinement points a program has — programs that fought the verifier hardest under BCF see the biggest PCB speedups.

④ Why BCC sees the largest speedups

BCC's median speedup is 24×, the highest of any project, and its proof bundles are the corpus's largest (up to 59 MB). Connect the two.

  1. BCC's ksnoop objects perform variable-length copies, each one needing its own range-refinement obligation — many more than a typical Calico or Cilium object.
  2. More refinement points under BCF means more suspend/round-trip/resume cycles per object — and BCC has the most.
  3. PCB pays that cost once, offline, producing a correspondingly large bundle (up to 59 MB) — but the kernel load itself still requires just one syscall, regardless of bundle size.
  4. So BCC's objects, which suffered the most under BCF's per-refinement overhead, benefit the most from removing it — a 24× median speedup versus Calico's 1.6× median.
💡
The pattern across the whole corpus (Cilium 10×, IG 8×, Calico 1.6×, BCC 24×) tracks exactly how refinement-heavy each project's programs are — not their raw size.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A program is compiled with clang-15 -O2 and loads fine. The same source recompiled with clang-19 -O3 gets rejected. Did the program's behavior change?
Show answer
No. The program's semantics are identical; only the generated bytecode's shape changed, which happened to restructure register usage in a way the verifier's non-relational domains can no longer follow. This is "fighting the verifier" — a codegen artifact, not a real safety difference.Misconception: that a verifier rejection always signals a real bug. It signals the analysis's imprecision at least as often as it signals unsafety.
Problem 2 · medium
Why does PCB still need the kernel's in-kernel proof checker, if the userspace mirror already confirmed the program is safe during compilation?
Show answer
Because the mirror and its SMT solver are both untrusted. The mirror could be stale relative to the kernel it's targeting, and the solver could have a bug or be malicious. The kernel's proof checker is the only trusted judge — it independently reconstructs the refinement condition from the bytecode it is actually verifying and re-checks the attached proof step-by-step before accepting anything.Misconception: that precomputing the proof means trusting the precomputation. PCB's soundness comes entirely from the kernel re-validating, not from anything the backend claims.
Problem 3 · medium
A Cilium object built for kernel 6.1 is loaded, unmodified, on a host running kernel 6.8 whose verifier logic has since changed. What happens to its proof bundle, and is this a safety problem?
Show answer
The kernel's refinement conditions at each check may now differ from what the bundle was built for, so the hash lookups for those checks will very likely miss. The kernel falls back to rejecting those checks — the program fails to load, but nothing unsafe is ever accepted. Fixing it requires rebuilding the bundle against the new kernel, a one-time cost of about a minute for the median object.Misconception: that a stale proof bundle is a security hole. It's a coverage loss (fail-closed), not a soundness loss — the kernel never accepts on a mismatched or invalid proof.
Problem 4 · hard
Classic proof-carrying code (Necula & Lee) proves that an entire program satisfies a safety policy. How does PCB's use of proofs differ, and why does that difference shrink the kernel's changes relative to BCF?
Show answer
PCB does not prove whole-program safety with one monolithic proof. It leaves the kernel's existing default analysis to handle everything it already can, and attaches small, local proofs only at the specific program points where that default analysis would reject a genuinely safe access. Because the kernel verifier's core logic is untouched — it just gains a proof-checking step at its existing failure points — the required kernel modifications are far smaller than either classic PCC (which would replace verification with proof-checking entirely) or BCF (which adds state suspension/resumption machinery).Misconception: that "proof-carrying" implies replacing the verifier. PCB augments the verifier's existing analysis at its weak points; it doesn't replace it.
Problem 5 · medium
Why must PCB's userspace mirror reproduce the kernel's exact path-pruning logic (state subsumption at prune points), rather than just exploring every path itself more thoroughly?
Show answer
The proofs are only useful if they're attached to the exact same rejection points the kernel actually reaches. If the mirror prunes differently — exploring more or fewer paths than the kernel, or comparing states at different points — it will predict rejections that don't correspond to what the kernel computes, generate proofs for the wrong (or no) refinement conditions, and the kernel's hash lookups will fail to find a match even though a relevant proof exists somewhere in the bundle.Misconception: that more thorough analysis in the mirror is strictly better. What matters is matching the kernel's behavior exactly, not being more precise or exhaustive than it.
Problem 6 · easy
A program passes the kernel's default verification with no rejected checks at all. Does PCB do anything extra for it?
Show answer
No. If the userspace mirror's analysis (which matches the kernel's) never hits a rejection, there's nothing to prove — no refinement conditions, no proof objects, an empty or absent bundle. The program loads exactly as it would without PCB in the picture at all.Misconception: that PCB adds overhead to every program. It only does work — and only ships proofs — for the specific points a program would otherwise be rejected.
Problem 7 · hard
Why is BCF's on-demand approach still preferable for a program generated fresh and loaded exactly once (e.g., a runtime-patched template), even though PCB loads any given object faster?
Show answer
PCB's speed advantage is in the load step alone, but that advantage is bought by a build step (running the mirror and the SMT solver) that happens beforehand. For a program reused across many loads, that build cost is amortized (or eliminated via bundle caching) across all those loads. For a program built and loaded exactly once, the full build cost is paid for a single benefit, and BCF's total end-to-end latency (which has no separate offline phase) can come out ahead, since it only proves the checks it actually hits, not a build that also covers checks an unused path may never reach.Misconception: that PCB is strictly faster in every scenario. It shifts cost from load time to build time — a win only when the build is reused or the load-time savings alone outweigh the one-time build cost.
Problem 8 · medium
Across 3,267 kernel selftests, PCB's userspace mirror produced zero false accepts and zero false rejects. Why are these two kinds of divergence treated with different urgency by the authors?
Show answer
A false accept — the mirror thinks a program is safe when the kernel would reject it — is a soundness bug in the mirror's logic that, if it led to a mismatched proof being accepted, could threaten kernel safety; these are fixed first. A false reject — the mirror predicts a rejection the kernel wouldn't actually make — only costs coverage (PCB simply doesn't help on that program), since the kernel independently re-verifies everything regardless. Neither kind of mirror bug can cause an actually-unsafe program to be accepted, because the kernel's own checker has the final word either way.Misconception: that any mirror bug is a safety risk. The kernel's independent re-verification means mirror bugs can only ever cost performance/coverage, never soundness.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the one-sentence difference between BCF and PCB?▾
BCF proves refinement conditions during the load, suspending and round-tripping to userspace for each one; PCB proves all of them before the load, offline in the compiler backend, and ships a bundle the kernel checks in a single pass.
Q2Does PCB make the kernel trust anything new?▾
No more than BCF already does. The kernel still only trusts its own small in-kernel proof checker. The userspace mirror and the SMT solver are both untrusted — their output is only ever useful if the kernel's own re-verification accepts it.
Q3What happens if a proof in the bundle is wrong or doesn't match?▾
The kernel independently reconstructs its own refinement condition and its own hash; if the hash doesn't match an entry, or the matched proof doesn't check out against the in-kernel checker's rules, the check fails and the program is rejected — exactly as if no proof had been offered.
Q4Is the SMT solver running inside the kernel?▾
No — in both BCF and PCB, CVC5 runs entirely in userspace (for PCB, inside the compiler backend at build time). The kernel only ever runs the small, fixed proof-checking rule set (AND_ELIM, BIT_BLAST, POLY_NORM, CONTRA, etc.), never the solver itself.
Q5Does PCB accept any programs that BCF rejects, or vice versa?▾
No — on the 360-object evaluation corpus, PCB accepts exactly the same programs BCF does. The contribution isn't a larger class of accepted programs than BCF; it's removing BCF's load-time userspace round trips while keeping the same coverage.
Q6How is a proof matched to the right check at load time?▾
When the kernel's default analysis fails a check, it reconstructs the same kind of refinement condition BCF would build, computes a canonical hash of it, and looks that hash up in the proof bundle. If an entry exists and its stored condition exactly matches the one just computed, its proof is validated.
Q7What is CO-RE/BTF's role here?▾
177 of the 360 evaluation objects are CO-RE (Compile Once – Run Everywhere) builds, meaning field offsets are relocated per target kernel using BTF type info before verification. PCB parses the .BTF.ext section and applies these relocations first, so the bytecode it analyzes and proves matches exactly what the kernel will verify.
Q8Why not just add a more precise (relational) abstract domain to the kernel instead?▾
Domains like Zones or Octagons would accept more programs outright, but implementing and maintaining them inside the kernel verifier substantially increases its complexity and attack surface. PCB's goal is explicitly to widen acceptance without growing the in-kernel analysis — it adds a small, fixed proof checker instead of a bigger analyzer.
Q9How does PCB compare to ExoBPF?▾
ExoBPF (Nelson et al., LPC'21) goes further: it replaces the kernel's own analysis with checking a userspace-supplied proof against a Lean-specified policy, minimizing the kernel's role to proof-checking alone. PCB keeps the kernel's existing verifier doing everything it already can, adding proofs only at its specific failure points — a smaller change, and (unlike ExoBPF's early-stage prototype) validated on production programs.
Q10How does PCB compare to PREVAIL (eBPF for Windows)?▾
PREVAIL is a full replacement verifier using a relational (zone) domain and whole-CFG fixpoint analysis, accepting more programs by being inherently more precise. Adopting it in Linux would mean swapping in a much larger analyzer or trusting an external tool's verdict outright. PCB instead keeps the existing Linux verifier as the trusted core and supplies proofs only where needed.
Q11What's an open question the authors flag?▾
Whether refinement conditions stay stable when Cilium-style per-node templates are patched with different constants (addresses, endpoint IDs) at deployment. If so, one bundle could serve every per-node variant instead of rebuilding per instance — the authors note they haven't explored this yet.
Q12Is PCB's prototype available to try?▾
Yes — the paper states the prototype ("Alivio") is open source and publicly released alongside the paper.

Glossary & further reading

Every term in one place, then provenance and a path to go deeper.

Core terms
PCB (Proof-Carrying-BPF)This paper's framework: a userspace mirror of the kernel verifier precomputes proofs for every point the default analysis would reject, bundled with the bytecode.
BCFSun & Su's prior framework (SOSP'25): proves refinement conditions on demand, mid-load, via kernel-to-userspace round trips.
Refinement conditionA logical formula, built from a backward slice and path condition, that is true exactly when an access the default analysis can't prove safe would actually be unsafe.
Userspace mirrorPCB's instruction-by-instruction reimplementation of the kernel verifier, kept faithful via the kernel's own selftest suite.
Proof bundleThe collection of {refinement condition, proof} pairs for one program, indexed by condition hash, shipped alongside the BPF bytecode.
In-kernel proof checkerThe small, trusted kernel component (reused from BCF) that validates a proof's individual steps without solving anything itself.
Supporting terms
Non-relational domainIntervals / tnums tracked per-register; can't express relationships between registers, the root cause of most false rejections.
DAG sliceThe backward-traced set of instructions that influence an unsafe-looking access; its leaves become symbolic values.
AND_ELIM / BIT_BLAST / POLY_NORM / CONTRAThe proof rules the in-kernel checker trusts: splitting conjunctions, reasoning over bits, normalizing polynomials, and deriving False.
CO-RE / BTF relocationPatching field offsets in a compiled BPF object against the target kernel's type info before verification.
State subsumption / pruningThe kernel's technique for cutting off path exploration early when an earlier explored state already covers the current one.
Build time vs. load timePCB's one-time offline cost (backend + solver) vs. the single, fast kernel syscall that actually loads the program.
TCBTrusted computing base — for PCB, the kernel verifier and its proof checker; the mirror and solver are explicitly untrusted.
