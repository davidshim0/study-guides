SOSP 2026 · A Field Guide

Handing out a pointer to the weights, not a copy of them

Every RL training step floods thousands of GPUs with terabytes of fresh model weights. This is the plain-English story of TensorHub — a storage system that never actually stores anything.

📄 "TensorHub: Scalable and Elastic Weight Transfer for LLM RL Training" · Ye et al., ByteDance Seed / UW–Madison 🎓 Distributed-systems basics assumed; RDMA/DMA mechanics can be skimmed ⏱ ~25 min read
🔗

TRACK who already holds a weight version on GPU and read straight from them — never OWN a copy just to hand it out.
The redundancy already exists; stop paying to duplicate it.

Before you begin

Quick glossary, then seven primers

Acronyms first, so nothing below is opaque. Then seven collapsible primers — open whatever's unfamiliar, skip what you already know from your own DMA/RDMA-adjacent work.

Acronyms used throughout

RLReinforcement learning — the training loop this whole paper supports.
LLMLarge language model — the thing being trained; its weights are the payload.
ROSReference-Oriented Storage — the paper's core abstraction (§3).
RDMARemote Direct Memory Access — NIC-driven reads/writes of remote memory, no CPU copy.

SPMDSingle-program, multiple-data — how a sharded model-parallel group executes.

DCDatacenter — cross-DC training spans two or more, linked by slow TCP/VPC.
PCIe / VPC NICPCIe: the bus between GPU and host CPU memory. VPC NIC: the (slower, non-RDMA) cross-datacenter network interface.
1The RL training loop: rollout, score, train▾

RL post-training runs a continuous loop: rollout workers use the current weights to generate responses to prompts; a reward module scores those responses; trainer workers turn the scores into gradients and produce updated weights. Those new weights must reach rollout workers before the next round — that hand-off is weight transfer.

Now you're ready: everything in this paper exists to make that one hand-off — trainer's new weights → rollout's GPUs — fast, cheap, and robust to failures.
2Why weight transfer is the bottleneck▾

Rollout (inference) can take 90%+ of total RL step time, so production systems scale it out onto dedicated GPUs separate from trainers. But then weights must physically move — often terabytes of them — after every training step, typically every few to tens of minutes. Until the transfer completes, rollout GPUs sit idle: they cannot do inference with half-updated weights.

Now you're ready: "GPU stall time" (idle GPU-seconds waiting on weights) is the paper's central cost metric — nearly every number in the evaluation is a stall-time reduction.
3Model parallelism and shards▾

A model too big for one GPU is split (sharded) across a group of GPUs; that group runs in SPMD lockstep — every worker in the group must execute the same control-flow decisions, or the group hangs or corrupts state. A full model copy = one replica = a set of shards, one per worker.

Now you're ready: "consistency" in this paper means all shards of one replica must agree on what version is available — not a global, cluster-wide agreement.
4RDMA and one-sided reads▾

If you already work with DMA engines or CXL.mem-style memory access, you know this: RDMA lets a NIC read memory on a remote host directly into local memory, without interrupting the remote CPU. A "one-sided read" means the requester alone drives the transfer — the source just needs its memory pre-registered with the NIC.

Now you're ready: TensorHub's entire performance story rests on turning every weight fetch into a one-sided RDMA read between two GPUs' memory — no third copy, no remote CPU involvement.
5Three existing ways to move weights▾

Collective communication (NCCL): fast broadcast, but requires a fixed group of participants and a global barrier. Point-to-point (UCX): flexible sender/receiver pairs, but no global view, so senders get overloaded under fan-out. Distributed storage (parameter servers, Ray object store): clean push/pull decoupling, but the storage system must physically own a copy of the data.

Now you're ready: the paper's whole argument is that you can get storage's decoupling without storage's copying — that's ROS.
6Elastic / spot GPUs and cluster churn▾

Spot GPU instances are cheap but can be preempted (killed) at any moment, with no warning. A cluster that uses them must tolerate workers appearing and disappearing constantly ("churn") without the whole job crashing.

Now you're ready: a weight-transfer system that assumes a fixed set of participants (like NCCL) is fundamentally incompatible with spot instances.
7Cross-datacenter deployments▾

Sometimes the GPUs you want (e.g., inference-optimized ones) live in a different datacenter than your trainers. The link between datacenters is orders of magnitude slower than intra-datacenter RDMA (TCP over a shared VPC NIC, not dedicated RDMA fabric), so naively repeating the intra-DC transfer pattern across DCs is disastrous.

Now you're ready: the paper's cross-DC design is really about crossing that slow link exactly once per version, then fanning out locally over RDMA.
The whole story in one place

TensorHub in a nutshell

The problem, the observation that dissolves it, and how the pieces fit together.

Rollout workers need trainers' latest weights; trainers want to hand them off with minimal fuss. Storage interfaces (push, then pull) give you that decoupling cleanly — but they force every write to be physically copied into storage-owned space, which is ruinous at TB scale: extra network hops, extra GPU↔CPU copies, extra (de)serialization, and extra memory that can simply run out.

The paper's move is to notice that RL weights already have three properties for free: they're highly replicated (data-parallel inference runs many copies), immutable while in use, and short-lived (only the newest few versions matter). Given that, storage doesn't need to own anything — it just needs to know who currently holds a copy and broker a direct read between two GPUs. That's Reference-Oriented Storage (ROS): a server that manages only lightweight references, while the bulk data moves peer-to-peer over RDMA.

TensorHub turns this idea into a production system: topology-aware scheduling picks the least-loaded, closest-replica source; pipeline replication lets partially-updated workers immediately re-serve others, turning fan-out into a bandwidth-amplifying relay; a mutability contract and retention protocol keep the illusion safe even when weights must be overwritten or every holder disappears; and failure handling reroutes transfers and swaps reference servers transparently.

The payoff: up to 6.7× less GPU stall for standalone rollouts, 4.8× faster weight updates under spot-instance churn, and 19× less cross-datacenter stall — all while requiring roughly 40 lines of integration code, versus hundreds for NCCL/UCX. TensorHub is in ByteDance production today.

🔑 Key takeaways

  • Storage's win is decoupling (push/pull, no framework coordination); its cost is ownership (copies). ROS keeps the first, discards the second.
  • ROS is enabled by three facts about RL weights: replicated, immutable, short-lived. Break any one and the abstraction stops being safe.
  • Integrity needs a mutability contract (publish/unpublish); availability needs a retention protocol (offload-to-CPU as a rare safety net, not the common path).
  • Pipeline replication makes every newly-updated worker a new source — throughput scales with demand instead of collapsing under it.
  • TensorHub enforces consistency only within a model-parallel replica (per-replica transactions), not cluster-wide — a deliberate, cheap relaxation that off-policy RL already tolerates.
  • If you work on DRAM/NVM tiering: ROS's "retain the newest, offload the last copy of anything older" is structurally the same trade-off as demoting cold pages to a slower tier — except here the "hot tier" is GPU HBM already committed to a live task, not a spare capacity pool.
Seven everyday pictures

How to think about ROS and TensorHub

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · ROS

The coat-check ticket

Checking a coat, you get a numbered ticket, not the coat. The attendant never duplicates your coat — they just remember which hook it's on. When you (or anyone with the ticket number) come back, they fetch the real coat directly. ROS's reference server is the attendant: it hands out pointers ("Worker-0, shard 3, version 12 lives here"), never copies of the weights themselves.

Where it breaks: a coat-check has one coat per ticket. ROS's "coat" can vanish (the worker unpublishes or fails) — which is exactly the availability problem the retention protocol exists to patch.
Integrity · Mutability contract

A borrowed library book

While a book is checked out to readers, you don't scribble in it — that's the deal that makes lending safe. If the author needs to revise it, they must first recall every copy. In ROS, holding a published replica means promising not to mutate it; to change the underlying buffer, a worker must call unpublish() first, and the server waits for any in-flight reads to finish draining before confirming.

Where it breaks: a real library can't force a instant recall — readers keep books for weeks. ROS's "recall" is fast specifically because RL weight buffers have clean, short-lived usage windows between training stages.
Scaling throughput · Pipeline replication

A gossip chain, not a megaphone

A megaphone (single-source broadcast) can only shout so loud — everyone hears it at the same, limited rate. Gossip spreads differently: as soon as you've heard a rumor, you can repeat it to someone else, and they to someone else. TensorHub does the same with weight shards — a worker that's only 40% replicated can already re-serve that 40% to a third worker, turning one source into an expanding relay.

Where it breaks: gossip can distort a rumor in transit. TensorHub's relay never distorts data — it reads exact byte ranges via a progress counter, so partial replication is exact, not approximate.
Scheduling · Topology & load awareness

Picking the shortest, least-busy checkout line

You don't queue at the first register you see — you scan for the line that's both closest and shortest. TensorHub's reference server does this for every replication request: prefer a same-datacenter replica, and among those, pick the one currently serving the fewest other readers.

Where it breaks: store checkout lines don't get faster as more shoppers join them. TensorHub's replicas do, via pipelining — so the "line" analogy undersells how well it scales.
Cross-datacenter · Seeding & smart-skip

The first scout crosses the slow bridge

Two camps separated by a rickety, one-lane bridge (the inter-DC link). Rather than everyone crossing it, one scout crosses first (the seeding replica); everyone else in the second camp waits for the scout, then travels the fast local roads (RDMA) to reach them. "Smart-skipping" is the rest of camp politely not crowding the scout mid-crossing.

Where it breaks: a real scout can't be duplicated. TensorHub optionally splits work further with offload seeding — a background CPU-memory relay that starts the crossing without even stalling the scout's own GPU.
Availability · Retention protocol

A spare key, only when everyone's out

You don't keep a spare key hidden outside your house when a family member is always home to let you in — that's pointless duplication. Only when the last person is about to leave do you stash one spare. TensorHub's retention protocol works the same way: it offloads a CPU-memory copy of a version only when its last GPU holder is about to unpublish and no one else has fetched it yet.

Where it breaks: a hidden house key sits there indefinitely. The offload copy is deliberately transient — released the moment another worker replicates it or a newer version supersedes it.
Correctness · Model-parallel consistency

Synchronized swimmers, one scoreboard

Synchronized swimmers must move in lockstep, so they all watch the same scoreboard clock rather than each guessing the time independently — otherwise their routine falls apart. Shards of one model-parallel replica are the same: TensorHub serializes each replica's requests into a transaction so every shard reads an identical answer to "what's the latest version?", preventing SPMD divergence.

Where it breaks: different swim teams in the pool don't need to share a clock. Likewise, TensorHub deliberately does not synchronize across different replicas — only within one.
The full explanation

How it actually works

From the trade-off table that motivates ROS, through TensorHub's scheduling, cross-DC, and consistency mechanisms.

1 · Why nothing existing satisfies every goal

The paper sets five goals: topology awareness, elasticity, minimal coordination, minimum data movement, and no extra storage/memory. Each existing approach satisfies some but not all:

ApproachTopology-awareElasticMin. coordinationMin. data movementNo extra space
Collective (NCCL)✓——✓✓
Point-to-point (UCX)—✓—✓✓
Distributed storage (PS/Ray)✓✓✓——
TensorHub✓✓✓✓✓
📌
Collective comm needs a fixed group (breaks under churn) and a global barrier (amplifies stragglers). Point-to-point has no global view (senders overload). Storage owns a copy (extra movement + space). TensorHub is the only approach in this table without a structural gap — that's the whole thesis of §3–4.

2 · Integrity: the mutability contract

Holding a published reference is a promise: I will not mutate this data while others may be reading it. To break that promise safely, a worker must revoke it first:

# reading side — safe by construction
handle.replicate("latest")      # RDMA-reads someone else's published buffer

# writing side — must revoke the promise first
handle.unpublish()             → server waits for in-flight reads to drain
mutate_weights_in_place()      # now safe: no other reader can be mid-transfer
handle.publish(new_version)
💡
Why this is cheap in practice: RL worker code already has clean stage boundaries (rollout → train → rollout), so "don't mutate while published" maps naturally onto existing phases — no new discipline is imposed on the RL framework.

3 · Availability: the retention protocol

Because ROS owns nothing, a version disappears the moment its last holder unpublishes it. That's fine for stale versions — but catastrophic if it's the only copy of the newest one and no rollout has fetched it yet.

on unpublish(version, worker):
    if worker.is_last_replica_of(version) and version.is_retained():
        client.offload_to_cpu_memory(version)   # ~48 GB/s over PCIe, <2s even for a full GPU's weights
        server.mark_as(offload_replica)
    else:
        server.drop_reference(worker, version)
🔑
Offloading is the rare-path safety net, not the common case: rollouts usually replicate promptly, so trainers unpublish without ever triggering it. When it does trigger, only one extra CPU-memory copy exists cluster-wide — a bounded, worst-case cost rather than a per-write tax.
🧠
For the tiering-minded reader: this is structurally a demotion policy — spill the last copy of "hot" data to a slower tier (GPU HBM → host DRAM) only at the moment of eviction pressure, exactly like a page migrated to NVM/CXL memory when DRAM capacity is reclaimed. The difference: TensorHub's "hot tier" isn't idle capacity waiting to be filled — it's another task's live working memory, borrowed opportunistically.

4 · Topology-aware scheduling and pipeline replication

The reference server always prefers a same-datacenter source, then picks whichever replica is currently serving the fewest requests. Because most RDMA NICs are full-duplex, a worker mid-receive can simultaneously serve others from the portion it already has — turning single-rooted fan-out into an expanding pipeline.

5 · Cross-datacenter replication

The first replica in a new datacenter (the seeding replica) must cross the slow link over TCP; every subsequent replica in that DC then fetches over local RDMA from the seed, never re-crossing the slow link. Smart-skipping stops other workers from prematurely reading a still-filling seed; optional offload seeding moves the slow TCP leg to a background CPU-memory buffer so the seeding GPU itself barely stalls.

6 · Consistency and fault tolerance

Requests from shards of one model-parallel replica can arrive at the server interleaved with another replica's publish, risking different shards seeing different "latest" versions. TensorHub serializes each replica's requests into a per-replica transaction, so every shard in that replica reads an identical answer — but replicas are not synchronized with each other, which is fine for the off-policy, slightly-stale-tolerant RL workloads this targets.

Failures are handled at replica granularity: a missed heartbeat evicts the replica and releases its resources; a failed source mid-transfer causes the receiver to time out (~4s) and the server to reroute to another source; a failed reference server itself carries no hard state to recover — a backup server simply starts empty and is repopulated by the next publish.

Follow the numbers

Worked examples

Four traces, each recomputed from the paper's own reported figures.

① Saturating RDMA bandwidth

TensorHub transfers a 50 GB shard in 2.2 s. The theoretical roofline is 25 GB/s per shard. How close does it get, and how does that compare to NCCL/UCX?

  1. Achieved throughput = 50 GB ÷ 2.2 s ≈ 22.7 GB/s (paper reports "22 GB/s").
  2. Fraction of roofline = 22.7 ÷ 25 ≈ 91% (paper reports 88%, using its own precise timing — consistent within rounding).
  3. NCCL achieves 18.8 GB/s (75% of roofline); UCX achieves 18.1 GB/s (72%) — both leave real bandwidth on the table that TensorHub captures.
🔑
The gap isn't about RDMA hardware — all three use the same NICs. It's implementation: hardware-affinity-aware NIC selection and zero-copy registration let TensorHub squeeze closer to the physical limit.

② Deriving the 6.7× standalone-rollout stall reduction

For the mocked 1T-parameter model (1024 GPUs: 768 trainers + 256 standalone rollouts), the paper reports NCCL stalls all 1024 GPUs for 5.3 s each, while TensorHub stalls only the 256 standalone GPUs for a mean of 3.1 s.

  1. NCCL total GPU-stall = 1024 GPUs × 5.3 s = 5,427 GPU-seconds (its global barrier stalls trainers too).
  2. TensorHub total GPU-stall = 256 GPUs × 3.1 s = 794 GPU-seconds (publish is non-blocking, so trainers never stall).
  3. Reduction = 5,427 ÷ 794 ≈ 6.8× — matching the paper's reported "up to 6.7×."
💡
Notice the reduction comes from two separate effects stacked together: 768 fewer GPUs stalling at all (decoupled control flow), and a lower per-GPU stall time (3.1 s vs 5.3 s, from avoiding the straggler-amplifying global barrier).

③ The 4.8× elastic-rollout speedup, from a stall-time cap

Under UCX, the paper reports the last batch of elastic GPUs waits up to 7.2 s at step 10. Under TensorHub, per-GPU stall stays near-constant at ~1.5 s regardless of elastic GPU count.

  1. UCX's worst-case tail grows with elastic GPU count because new elastic workers must wait behind standalone rollouts (trainer → standalone → elastic), and contend for bandwidth once outnumbering standalones.
  2. TensorHub's tail is flat because the server load-balances across trainers, standalones, and peer elastic rollouts simultaneously via pipeline replication.
  3. Speedup = 7.2 s ÷ 1.5 s = 4.8× — exactly the paper's headline number, and it's really a statement about variance: TensorHub turns a growing tail into a flat one.

④ The 19× cross-datacenter reduction, via offload seeding

Setup: 4 rollout replicas × 2 shards = 8 GPUs in the remote datacenter. UCX: every GPU waits 7.8 s over TCP. TensorHub (skip+offload): the seeding replica (2 GPUs) stalls only 0.21 s (PCIe offload time); the other 3 replicas (6 GPUs) fetch over local RDMA at 0.45 s.

  1. UCX total stall = 8 GPUs × 7.8 s = 62.4 GPU-seconds.
  2. TensorHub total stall = (2 GPUs × 0.21 s) + (6 GPUs × 0.45 s) = 0.42 + 2.70 = 3.12 GPU-seconds.
  3. Reduction = 62.4 ÷ 3.12 ≈ 20× — matching the paper's reported "up to 19×" reduction, within rounding of the measured constants.
🔑
Offload seeding is what turns the seeding replica's stall from 2.5 s (waiting on the TCP transfer itself) down to 0.21 s (waiting only on the local PCIe hand-off) — the single biggest lever in this calculation.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
A rollout worker calls replicate("latest"). Where does the actual weight data come from — the reference server, or somewhere else?
Show answer
Somewhere else: another worker's GPU memory. The server only looks up which replica currently holds the requested version and returns a pointer; the requesting worker then issues RDMA directly against that source. The server never stores or transfers the weight bytes themselves.Misconception: that ROS is "just a faster parameter server." A parameter server's defining trait — the server owns a copy — is exactly what ROS eliminates.
Problem 2 · medium
A trainer wants to reuse its weight buffers in place for the next version. Walk through the exact sequence of calls it must make, and why order matters.
Show answer
unpublish() first — this asks the server to hide the current reference and blocks until any in-flight reads from this worker finish draining. Only after that returns is it safe to mutate the buffer in place. Then publish(new_version) makes the new contents visible. Reversing the order (mutating before unpublish completes) risks a concurrent reader RDMA-reading a half-written buffer — silent data corruption, not a crash.Misconception: that unpublish is just bookkeeping. It's a real synchronization barrier — it's what makes in-place mutation safe at all.
Problem 3 · medium
Under the retention protocol, does TensorHub offload a CPU copy every time any worker unpublishes a retained version? If not, when exactly does it trigger?
Show answer
No — only when the unpublishing worker is the last replica holding that retained version. If other replicas (including offload replicas) still hold it, the server simply drops the reference with no data movement. Offload is a rare corner-case safeguard, not a routine cost of every unpublish.Misconception: that retention implies a standing extra copy at all times. In the common case (a rollout has already replicated the new version before the trainer unpublishes), no offload ever happens.
Problem 4 · hard
Using the linear/quadratic model from the "How It Works" interactive (per-group time t₀ = 2.2 s), compute total GPU stall for 6 requesting groups, with and without pipeline replication, and the ratio between them.
Show answer
With pipeline: total = n·t₀ = 6 × 2.2 = 13.2 s. Without pipeline: total = t₀·n(n+1)/2 = 2.2 × 21 = 46.2 s. Ratio = 46.2 ÷ 13.2 = 3.5× — matching the general formula (n+1)/2 = 3.5. The gap widens as n grows, because single-source contention makes each successive group wait behind all the ones before it.Misconception: that "more replicas requesting data" is symmetric under both schemes. It's linear cost under pipelining but quadratic under single-source fan-out — the whole reason pipelining exists.
Problem 5 · medium
Two shards of the same model-parallel replica issue replicate("latest") at nearly the same instant a third replica publishes a new version. Can the two shards observe different "latest" versions?
Show answer
No. TensorHub's server groups requests from the same replica into a single transaction: the first request from that replica starts the transaction, evaluates "latest" once, and every subsequent request in that transaction reuses the same answer. This prevents the SPMD divergence that would occur if the two shards' requests were resolved independently against a version counter that changed in between.Misconception: that consistency here means cluster-wide agreement. TensorHub deliberately does not synchronize across different replicas — only within one.
Problem 6 · hard
A source replica fails midway through serving an RDMA read to a receiver. What happens to (a) the receiver, and (b) the reference server's bookkeeping?
Show answer
(a) The receiver's RDMA layer detects the failure via timeout (~4 s in the paper's measurements) and reports it to the server rather than hanging indefinitely. (b) The server marks that source as failed, prevents future replication from it, and reschedules the receiver to an alternate healthy source — the transfer resumes rather than aborting. This is handled entirely by TensorHub; the RL framework and other, unrelated workers are unaffected.Misconception: that a source failure mid-transfer requires the whole job (or even the whole replica group) to restart, as collective-communication failures typically do.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is ROS a cache?▾
No. A cache stores a copy to speed up future access to data that lives authoritatively elsewhere. ROS stores nothing at all — the GPU memory it references is the only copy, already committed to another live task (inference). There's no "cache miss" fallback to a slower authoritative store; if no worker holds a version, it's simply gone (barring a retained/offloaded copy).
Q2What exactly does the reference server store?▾
Only metadata: which workers (replicas/shards) hold which versions, their network locations, current load (in-flight request counts), and retention policy. It never allocates space for tensor data and never appears on the data-transfer path.
Q3How is this different from a parameter server or the Ray object store?▾
Both PS and Ray require the storage layer to physically own a copy — PS on dedicated server nodes, Ray typically via a GPU→CPU copy and serialization. That ownership is precisely what causes their overhead (extra network hops, extra copies, crashes at TB scale). ROS's server owns nothing; the "storage" is just the same GPU memory already in use for inference.
Q4Does TensorHub replace checkpointing systems?▾
No — they solve different problems. Checkpointing (e.g., ByteCheckpoint, Gemini) persists model state durably for long-term recovery and is not latency-critical. TensorHub/ROS is ephemeral and latency-critical: it exists purely to move the newest few versions between live workers as fast as possible, with no durability guarantee beyond what's currently held on GPUs.
Q5What happens if every worker unpublishes the latest version before any rollout replicates it?▾
This is exactly the corner case the retention protocol targets: the server detects that the departing worker is the last holder of a retained version and instructs it to offload a copy to CPU memory first, keeping the version available until a real GPU replica picks it up.
Q6How does TensorHub avoid the deadlocks that plagued earlier NCCL/UCX integrations?▾
By keeping every API call's blocking behavior fixed and small: publish never blocks, update blocks only for its own transfer, unpublish blocks only for draining its own in-flight readers. No framework-specific orchestration logic (like a driver issuing a global stop-the-world) ever enters this critical section, so the circular waits the authors observed in earlier systems can't form.
Q7Why does pipeline replication scale bandwidth instead of just latency?▾
Because most RDMA NICs are full-duplex: receiving data doesn't consume a worker's outbound bandwidth. So a partially-replicated worker can serve others "for free" while still receiving. As more workers join, more independent sources exist simultaneously — total available bandwidth grows with demand rather than being fixed at one source's uplink.
Q8What's a "seeding replica" and why not let every remote worker fetch over TCP directly?▾
If every remote-datacenter worker fetched independently over TCP, they'd all contend for the same slow, shared inter-DC link — and re-pay that slow cost per worker. Instead, exactly one worker (the seed) pays it once; everyone else in that datacenter fetches from the seed over fast local RDMA.
Q9Does a single reference server become a bottleneck at scale?▾
In the paper's measurements, one server sustains 8.5–9.7K control-plane ops/sec with 8,192 clients across 64 machines — far more than an RL cluster's actual publish/update/unpublish rate (a handful of calls per worker every few minutes). If it ever did bottleneck at extreme scale, the authors propose partitioning workers across multiple lazily-synchronized servers as future work.
Q10What did the paper NOT solve?▾
Cross-replica (cluster-wide) consistency is explicitly out of scope — replicas can observe new versions at different times, which off-policy RL tolerates but which would need an explicit broadcast if a framework required strict synchrony. It's also specific to RL's replicated/immutable/short-lived weight pattern; it isn't a general-purpose distributed storage system.
Q11How does this connect to memory tiering / CXL work?▾
The mechanism is structurally close to hot/cold tiering: RDMA-direct reads are a zero-copy access to remote-but-fast memory, much like CXL.mem load/store to pooled memory, and the retention protocol's offload-to-CPU-on-last-eviction mirrors demoting a cold page to a slower NVM/CXL tier. The key structural difference is ownership of capacity: a tiering system (TPP, HeMem, Memtis) manages dedicated pool capacity it's free to place pages into, whereas ROS's "source tier" is another task's live, uninterruptible working set — it can only be read, never reclaimed or repurposed, which is why the whole design centers on references and consent (the mutability contract) rather than a placement policy.
