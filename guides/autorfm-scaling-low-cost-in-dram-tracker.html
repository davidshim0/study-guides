Stalling one room, not the whole motel

DDR5's fix for Rowhammer at low thresholds — the RFM command — stalls an entire memory bank to buy mitigation time. AutoRFM shows you only need to lock the one subarray doing the work.

Before you begin

Quick glossary, then eight primers

The domain is DRAM Rowhammer mitigation, not cache/mm policy — so start with the acronym list, then skim any primer that's unfamiliar. Terse on purpose; you already know OoO cores and the mm stack.

Quick glossary — acronyms you'll see everywhere

TRH(-S/-D)Rowhammer Threshold — activations to flip a bit; single- vs double-sided pattern. TRH-D is the paper's default metric.
RFMRefresh Management — DDR5 command that stalls a bank so the DRAM chip can perform mitigation. Blocking.
ACT / PREActivate (open a row) / Precharge (close it) — the two DRAM commands the MC issues per access.
ALERTA DRAM→MC signal. DDR5 uses it to ask for more time; AutoRFM repurposes it to say "that ACT failed, retry."
SAUMSubarray Under Mitigation — the one subarray per bank that AutoRFM temporarily locks.
MINT / PrIDE / PARFMSecure low-cost in-DRAM trackers that probabilistically flag an aggressor row (this paper's tracker of choice: MINT).
RM / FMRecursive Mitigation (victim rows can themselves trigger mitigation) vs Fractal Mitigation, this paper's fix.
PRAC / ABOPer-Row Activation Counting / Alert Back-Off — the DDR5 in-array counter alternative this paper compares against.
SMDSelf-Managed DRAM — the broader prior region-based maintenance framework; AutoRFM is architecturally similar but specialized for ultra-low-threshold Rowhammer, adding Rubix and Fractal Mitigation.
tRC / tRFC / tRFM / tREFIDRAM timings: time between ACTs (48ns), refresh duration (410ns), RFM duration (205ns), refresh interval (3900ns).
RAARefresh-management Activation-count — the MC's per-bank counter that triggers RFM.
1Rowhammer and the threshold (TRH)▾

Rapidly activating one DRAM row (the aggressor) can flip bits in physically adjacent rows (the victims) via charge leakage. TRH is the activation count needed to cause a flip. It has fallen hard across generations: 139K (2014, DDR3) → 22.4K → 10–17.5K (DDR4) → 4.8–9K (LPDDR4), and the paper's whole point is to keep mitigation viable as TRH heads toward triple, then double, digits.

Now you're ready: everything in this paper is in service of tolerating an ever-lower TRH without the mitigation mechanism itself becoming the bottleneck.
2Banks, subarrays, and row buffers▾

A DRAM chip has several banks (32 for DDR5), each with one architecturally-visible row buffer. But internally, a bank is built from many independent subarrays (here, 256 per bank, 512 rows each), each with its own row buffer and sensing circuitry — so a mitigation confined to one subarray leaves every other subarray's sensing circuitry free to keep servicing accesses in parallel.

Now you're ready: AutoRFM's entire trick is that "stall the bank" and "stall one subarray" are very different costs — 256 rooms exist, but RFM locks the whole floor.
3DRAM timing is deterministic — ACT, PRE, and the refresh budget▾

DRAM is a scheduled device: tRC (48ns) between ACTs, tRAS/tRCD/tRP govern opening/closing a row. Ordinary refresh (REF) already borrows time every tREFI (3900ns) for a duration of tRFC (410ns) — leaving room for at most (3900−410)/48 ≈ 73 activations per interval before the next refresh. That's the natural "slack budget" mitigation competes for.

Now you're ready: when thresholds were higher, REF-time slack could carry most of the mitigation burden — though the paper is careful that relying on REF alone severely limits both mitigation time and the tolerable threshold. AutoRFM exists because sub-100 thresholds blow through even a generous slack budget.
4Secure low-cost in-DRAM trackers (PARFM, PrIDE, MINT)▾

Deterministic per-row counters (the PRAC approach) need real DRAM-array area. Cheaper alternative: probabilistically sample activations into a tiny structure (a few bytes) and mitigate whichever row got sampled. MINT is the leanest of these — a single-entry tracker that, over a window of W activations, pre-decides which of the W slots will be mitigated. Smaller W ⇒ higher selection probability ⇒ lower tolerated threshold (W=4 → TRH-D 96; W=32 → TRH-D 702).

Now you're ready: MINT is the tracker this paper builds on. Its job is choosing which row to mitigate; AutoRFM's job is finding the time to do it without stalling everything.
5Refresh Management (RFM) — DDR5's answer to "when"▾

The MC counts activations per bank (the RAA counter); once it hits a threshold (RFMTH), the MC issues RFM, and the whole bank is blocked for tRFM (205–410ns) while the DRAM chip mitigates. RFM-N shorthand means RFMTH = N.

Now you're ready: RFM works, but it's blocking — the villain of this paper. At RFMTH=4 (needed for TRH-D≈96) it costs 33% average slowdown.
6ALERT — a signal DDR5 already has▾

DDR5 already lets a DRAM chip assert ALERT back to the MC to request more time. AutoRFM reuses the exact same wire for a new purpose: signal that an incoming ACT collided with the one subarray currently under mitigation, so the MC should retry later.

Now you're ready: no new pin, no new command — AutoRFM's interface change is "ALERT can now also mean 'that request failed, retry.'"
7Half-Double and transitive attacks▾

Mitigation performs victim refresh — but at low thresholds, that refresh is itself enough activation-equivalent stress to hammer a more distant row. This indirect chain is a transitive attack (Half-Double being the canonical example). Naively, defenders respond with recursive mitigation: victim rows can themselves trigger another mitigation round.

Now you're ready: recursive mitigation defends against transitivity but can tie up the same subarray for many consecutive rounds — exactly the non-determinism AutoRFM needs to avoid. That tension motivates Fractal Mitigation (How It Works, §5).
8Randomized memory mapping (Rubix)▾

Standard mappings (e.g. AMD Zen's) place spatially-nearby lines in the same row/bank to exploit locality. Rubix instead encrypts the line address with a low-latency block cipher before mapping it to a bank/row, destroying spatial correlation between consecutive accesses at the cost of some row-buffer locality.

Now you're ready: AutoRFM only works well if back-to-back requests rarely land on the same subarray — Rubix is what makes that true.
The whole story in one place

AutoRFM in a nutshell

The bottleneck, the fix, and the two extra pieces needed to make the fix actually safe and fast.

Secure low-cost in-DRAM trackers like MINT can identify aggressor rows cheaply even at ultra-low thresholds — but identifying isn't enough; DRAM also needs scheduled time to perform the victim refresh. DDR5's RFM command provides that time by stalling the entire bank. That's fine at today's thresholds (RFM-32, TRH-D 702, costs 0.2%) but catastrophic once thresholds drop below 100 — RFM-4 (needed for TRH-D≈96) costs an average 33% slowdown.

AutoRFM's fix: exploit the fact that a bank is really built from 256 independent subarrays. Mitigate on only one subarray (the SAUM) at a time; every other subarray keeps serving requests uninterrupted. If an ACT happens to target the SAUM, the chip sends ALERT and the MC retries after a fixed ~200ns — no bank-wide stall.

Two extra pieces make this practical. Randomized memory mapping (Rubix) keeps consecutive accesses from clustering on the same subarray, cutting the observed ALERT rate from 3.7% to 0.22% and slowdown from 16.5% to 3.1%. Fractal Mitigation replaces recursive (open-ended) transitive-attack defenses with a single deterministic round — refresh both immediate neighbors always, and distant neighbor d with probability 2(1−d) — so the SAUM is guaranteed free again after exactly 200ns, and MINT can select more aggressively (dropping TRH-D from 96 to 74).

The payoff: AutoRFM tolerates a threshold as low as 74 at an average slowdown of only 3.1% — versus RFM's 33% at a comparable threshold, and cheaper than PRAC+ABO's flat ≥4% slowdown tax that applies at every threshold.

🧱 Key takeaways

  • RFM buys mitigation time by stalling the whole bank; AutoRFM buys it by stalling one subarray (of 256).
  • A blocked ACT gets ALERT, not an error — the MC just retries after a deterministic ~200ns.
  • Randomized mapping (Rubix) is what keeps subarray conflicts rare (1/256-ish) — without it, slowdown is 16.5%, not 3.1%.
  • Fractal Mitigation replaces open-ended recursive mitigation with one deterministic round, defending Half-Double-style transitive attacks.
  • Combined result: TRH-D as low as 74, average slowdown 3.1% — cheaper than RFM at any comparable threshold and cheaper than PRAC+ABO's flat overhead.
  • Storage cost is tiny: ~5 bytes/bank in the DRAM chip, 2 bytes/bank (128B total) in the MC.
Six everyday pictures

How to think about AutoRFM

Each stands alone. Every card ends with an honest note on where the picture stops being true.

The core idea · AutoRFM vs RFM

Locking one room, not the motel

RFM is the manager taping off the entire motel to fix a leaky pipe in room 4 — every guest is stuck outside. AutoRFM tapes off just room 4; everyone else checks in and out normally, and if a guest happens to want room 4, the front desk just says "come back in a couple minutes."

Where it breaks: a motel has one front desk queueing everyone; a DRAM bank has independent subarrays that genuinely run in parallel — so the "everyone else is fine" part is more literally true in silicon than in the motel.
Reducing conflicts · Rubix mapping

Shuffling the seating chart

If three friends always sit next to each other, one conversation at their table blocks all three. Shuffle everyone to random seats each time and the odds any two friends land at the same table (subarray) drop sharply. Rubix encrypts the line address before mapping it to a row, so consecutive requests almost never re-hit the SAUM — cutting the observed conflict rate 16×.

Where it breaks: shuffling seats is free; shuffling addresses isn't — Rubix sacrifices row-buffer locality and adds ~18% more activations, costing about 1.5% of the total 3.1% slowdown even with zero conflicts.
Enforcement · ALERT and retry

A "come back in 200ns" note on the door

A blocking RFM is like a doctor's office that locks the whole waiting room while one patient is treated. AutoRFM is a note taped to one exam-room door: "occupied — try again in exactly 200ns." Every other exam room in the building stays open, and the note's timer is exact, not vague.

Where it breaks: a paper note doesn't guarantee the room is free the instant the timer expires; AutoRFM's determinism (no recursive mitigation) is precisely engineered so the retry is guaranteed to succeed after tM — that guarantee is the hard part, not the note itself.
The threat · transitive attacks

A row of dominoes that tips its own neighbors

Hammer the middle domino directly and it tips its two immediate neighbors on purpose (that's the mitigation). But if you hammer it hard and often enough, the "controlled tip" of those neighbors starts to nudge the next row over too — an unintended chain. Half-Double is exactly this: victim refresh, done often enough, becomes its own attack on more distant rows.

Where it breaks: real dominoes always fall the same way every time; Fractal Mitigation deliberately makes distant "nudges" probabilistic (halving with distance) rather than deterministic, which is what keeps the chain from running away.
The defense · Fractal Mitigation

A lighthouse beam that dims by half per row

The two nearest ships (d=1) always get the full beam — guaranteed refresh. Ships further out (d=2, 3, 4…) get a beam that's half as likely to reach them as the one before it: probability 2(1−d). On average, distant rows get refreshed just enough to stay safe without needing a guaranteed, ever-recursing sweep.

Where it breaks: a real lighthouse beam dims continuously with distance (inverse-square); Fractal Mitigation dims in discrete halving steps per row and is implemented with something even simpler — counting leading zeros in a 16-bit random number.
Why conflicts are rare · 256 subarrays

A 256-room motel where only one door is locked

With 256 independent rooms and only one locked at a time, a randomly-arriving guest has roughly a 1-in-256 (~0.4%) chance of wanting the locked one. Measured conflict rate under Rubix comes out even lower (0.22%) because not every activation slot in a window is actually used — half the time there's no locked room to conflict with at all.

Where it breaks: guests arrive independently; memory accesses don't — without randomized mapping, spatial locality means "the next guest" is disproportionately likely to want the room right next to the one just occupied, which is exactly the SAUM. That's why the naive mapping saw 3.7% conflicts, not 0.4%.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals you can read at a glance.

1 · The bottleneck — RFM is blocking

The MC tracks activations per bank in a counter (RAA); on hitting RFMTH, it issues RFM, and the entire bank is inaccessible for tRFM (205–410ns) while the DRAM chip mitigates. This is fine when mitigation is rare — but MINT's tolerated threshold is set purely by its window size W, and small W (needed for low TRH-D) means the MC's RAA counter — decremented by RFMTH on each RFM and also reduced by REF — reaches its trigger roughly every W activations, so RFM fires almost that often.

⚠
Concretely: W=4 gives TRH-D=96 but needs RFM every 4 ACTs — average 33% slowdown. W=32 gives TRH-D=702 at negligible (0.2%) cost. RFM's cost curve and MINT's security curve pull in opposite directions.

2 · AutoRFM — mitigate a subarray, not a bank

A bank is built from 256 subarrays, each with its own row buffer. AutoRFM lets MINT (or any tracker) select an aggressor row as before, but instead of asking the MC to stall the bank, the DRAM chip marks the aggressor's subarray as the Subarray Under Mitigation (SAUM) and performs the victim refresh internally. Requests to any other subarray proceed exactly as before. Only an ACT that maps into the SAUM fails — the chip asserts ALERT, the MC marks that bank busy with a timestamp, and retries after tM (~200ns).

3 · Memory-controller changes — a busy bit and a timestamp

The only new MC state is, per bank, a busy bit and a 15-bit timestamp for when the bank becomes free again. On ALERT, the bank is marked busy with timestamp = now + tM; once current time exceeds it, the bit clears and demand requests resume. 64 banks × 2 bytes = 128 bytes total.

💡
Why not track conflicts per request-queue entry? That would let the MC keep servicing non-SAUM requests from a "busy" bank immediately. The paper skips this complexity — with a large subarray count, conflicts are rare enough that the simpler per-bank design performs comparably.

4 · Mapping matters — Randomized Memory Mapping (Rubix)

AutoRFM's low overhead assumes consecutive accesses rarely target the SAUM. Standard mappings (e.g. AMD Zen's, which places two lines of a page in the same row to boost bank-level parallelism) violate this: two nearby accesses from the same page can both ACT into the same row/subarray, and the second one collides with a mitigation triggered by the first. Measured effect: 3.7% ALERT rate, 16.5% average slowdown.

Rubix encrypts the line address (a 3-cycle block cipher) before mapping it to bank/row/subarray, breaking the spatial correlation. Result: ALERT rate drops to 0.22%, slowdown to 3.1% — a ~5× reduction, for a modest cost in lost row-buffer locality that's offset by increased bank-level parallelism.

5 · Transitive attacks — Recursive vs Fractal Mitigation

Victim refresh at low thresholds can itself hammer distant rows (transitive attacks; Half-Double). The naive fix — recursive mitigation, letting victim rows also trigger further mitigation — can tie up the same SAUM for many consecutive rounds, making the mitigation duration non-deterministic (200ns–2000ns) and reopening denial-of-service concerns.

Fractal Mitigation avoids recursion entirely: always refresh the two immediate (d=1) neighbors, and refresh each more distant neighbor d with probability 2(1−d) (d=2 at 1/2, d=3 at 1/4, …). Exactly 4 victim refreshes happen, always, in one deterministic round.

🧱
Payoff of avoiding recursion: because FM never re-triggers, MINT no longer needs to reserve a slot for "recursive mitigation" — it selects from N slots instead of N+1, raising its selection probability and lowering the tolerated threshold from 96 (recursive) to 74 (fractal) at AutoRFMTH=4.
Follow the numbers, step by step

Worked examples

Four traces from the paper's own numbers, carried through the arithmetic.

① The refresh-time budget: why 73 activations?

The paper states a bank can perform "a maximum of 73 activations within tREFI." Verify it from Table I's DDR5 timings.

  1. tREFI (time between refresh commands) = 3900 ns.
  2. tRFC (time refresh occupies the bank) = 410 ns. That leaves 3900 − 410 = 3490 ns of "free" bank time per interval.
  3. tRC (time between successive ACTs) = 48 ns — the fastest rate the bank can accept activations.
  4. Max activations = 3490 / 48 ≈ 72.7 → 73 activations, matching the paper exactly.
💡
This is the natural slack that ordinary refresh already provides. Once a tracker needs mitigation more often than roughly once per 73 activations, borrowing REF time alone stops being enough — which is exactly the sub-100-threshold regime this paper targets.

② Fractal Mitigation's security bound: why TRH-D ≥ 53?

Appendix B models an attacker trying to use FM's probabilistic refreshes to hammer a row R via its neighbors. Reproduce the threshold.

  1. Damage on R after N episodes = p·N (from R⁻, probability p) + 0.25·p·N (from R⁺, probability p/4) = 1.25pN.
  2. Escape probability (R itself never refreshed) ≈ e−Damage/2.5 (from (1 − p/2)N ≈ e−pN/2, and Damage/1.25p·(p/2) simplifies to Damage/2.5).
  3. Target MTTF of 10K years ⇒ escape probability of 10−18. Solve: e−Damage/2.5 = 10−18 ⇒ Damage = 2.5·ln(1018) = 2.5 × 41.4 ≈ 103.6.
  4. TRH-D = Damage / 2 ≈ 103.6 / 2 ≈ 52, matching the paper's "≥53."
🧱
Since AutoRFM+FM's achieved TRH-D is 74 — comfortably above this 52–53 floor — direct hammering of a row remains the attacker's most effective strategy even in the presence of FM's own probabilistic refreshes.

③ Storage overhead: the whole tab, added up

Tally AutoRFM's hardware cost exactly as the paper does.

  1. Memory controller, per bank: 1 busy bit + a 15-bit timestamp ≈ 2 bytes. × 64 banks = 128 bytes total.
  2. DRAM chip, per bank — SAUM identifier: 1 valid bit + 8 bits (to address 256 subarrays) = 9 bits.
  3. DRAM chip, per bank — MINT tracker: a single-entry tracker, 4 bytes = 32 bits.
  4. Per-bank DRAM total: 9 + 32 = 41 bits ≈ 5 bytes/bank, matching the paper.
  5. Plus a PRNG for the random numbers Fractal Mitigation and MINT need — no separate storage tally given, but implementable with a lightweight LFSR.
🧱
A mechanism that turns 33% slowdown into 3.1% costs on the order of a few hundred bytes chip-wide — for comparison, PRAC's per-row activation counters require redesigning the DRAM array itself and increase tRC by ~10%.

④ Connecting to memory-tiering/CXL intuition: subarray-level parallelism as a controller-design lever

Why should a tiering/CXL researcher care about the specific mechanism here, beyond Rowhammer itself?

  1. The core lever is bank-level → subarray-level granularity. Just as bank-level parallelism (SALP) lets independent operations proceed concurrently within a bank, AutoRFM shows a maintenance operation (mitigation) can be pinned to one subarray while the rest of the bank stays live — the same granularity argument that motivates fine-grained refresh/scrub scheduling in disaggregated or CXL-attached memory controllers.
  2. Randomized mapping trades locality for parallelism — a familiar tension. Rubix's ~1.5% standalone cost (extra activations, lost row-buffer hits) for a 5× conflict reduction is the same trade a page-placement/interleaving policy makes when spreading hot pages across channels for bandwidth instead of packing them for locality.
  3. Pooled memory raises the stakes on hardware-level defenses generally (a guess, not a paper claim). If DRAM capacity is ever pooled and shared across tenants — as in disaggregated/CXL-attached memory — an in-DRAM, transparent mitigation like AutoRFM would matter regardless of which tenant's traffic triggers it, since no OS-level placement policy can see inside a shared physical bank. The paper itself says nothing about CXL or multi-tenancy; this is this guide's extrapolation.
💡
AutoRFM is a reminder that "transparent to software" mechanisms like this one are complementary to — not a substitute for — OS/mm-level placement decisions: the memory controller still needs to reason about per-bank busy state, which is exactly the kind of low-level timing detail that page-migration and tiering policies usually get to ignore, until it becomes the tail latency they can't explain.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
RFM-32 costs only 0.2% slowdown, but RFM-4 costs 33%. Both stall the bank for roughly the same tRFM (~205–410ns) per invocation. Why such a huge gap?
Show answer
It's not the per-stall cost that differs, it's the frequency. RFM-N fires roughly once every N activations (the MC's RAA counter is decremented by RFMTH on each RFM, and also reduced by REF, so the exact spacing depends on refresh timing too). RFM-4 fires far more often than RFM-32, so the fixed ~205ns stall is amortized over far fewer useful activations — a much larger fraction of total time is spent stalled rather than serving requests.Misconception: that the stall duration itself is the bottleneck. It's the rate of stalls (set by the mitigation window, which is set by the desired threshold) that drives slowdown.
Problem 2 · medium
With 256 subarrays per bank and one SAUM at a time, why did the paper measure a 3.7% ALERT rate under the baseline (AMD Zen) mapping instead of the naively-expected ~0.4% (1/256)?
Show answer
1/256 assumes each ACT independently and uniformly lands on a random subarray. The baseline mapping places two lines of the same 4KB page in the same row, so two back-to-back requests from a hot page are disproportionately likely to target the very subarray whose mitigation the first request just triggered — spatial correlation, not randomness, drives up the observed rate 9×.Misconception: that "256 subarrays" alone guarantees rare conflicts. Rarity depends on the memory mapping's independence properties, which is exactly why Rubix is a load-bearing part of AutoRFM, not an optional add-on.
Problem 3 · medium
Recursive mitigation defends against transitive attacks by letting victim rows themselves trigger mitigation. Why does AutoRFM specifically dislike this, when RFM-based designs (MINT, PrIDE) use it without issue?
Show answer
Under RFM, a stall is already bank-wide and its exact duration doesn't change the fundamental cost model much — a longer stall is just a longer stall on an already-blocked bank. Under AutoRFM, the whole benefit rests on the SAUM being free again after a fixed, short, known time (~200ns) so a retried ACT is guaranteed to succeed. Recursive mitigation can chain the same subarray busy for several consecutive rounds (200ns–2000ns), turning that guarantee into a gamble and reopening denial-of-service concerns AutoRFM was designed to avoid.Misconception: that any working transitive-attack defense is interchangeable. Determinism of mitigation duration is a hard requirement specific to AutoRFM's non-blocking design, not a general property all defenses need.
Problem 4 · hard
Fractal Mitigation refreshes distance-d neighbors with probability 2(1−d). Compute the expected number of victim refreshes an attacker who continuously hammers a single aggressor row would inflict on its distance-2 neighbor over 1000 mitigation rounds — and explain why that's not itself dangerous.
Show answer
Distance-2 probability = 2(1−2) = 1/2. Over 1000 rounds, expected refreshes ≈ 500 — half of what a deterministic "always refresh d=1 and d=2" scheme would give. That's intentional: the paper notes (from prior characterization) that a d=2 neighbor suffers under 10% of the charge loss a d=1 neighbor does, so refreshing it every single round (as older schemes do) is wasteful; giving it a refresh half the time is calibrated to its actual, smaller vulnerability, freeing up the "2nd refresh slot" to occasionally reach farther (d=3, d=4, ...) where Half-Double-style attacks actually live.Misconception: that probabilistic refresh means "sometimes unsafe." The design deliberately spends refresh budget where the physical charge-loss risk is highest, not uniformly — 500 refreshes to a low-risk neighbor over 1000 rounds is a feature, not a shortfall.
Problem 5 · medium
PRAC+ABO incurs a flat ≥4% slowdown "regardless of threshold." AutoRFM's slowdown is also roughly flat (2–3.1%) across near-term to ultra-low thresholds. Are these flatness properties caused by the same thing?
Show answer
No. PRAC's flat cost comes from a structural change to the DRAM array itself (per-row counters that must be read/updated on every access), which lengthens tRC by ~10% independent of how often mitigation actually happens — it's a tax on every access. AutoRFM's near-flatness comes from mitigation being cheap in the first place (one subarray, ~200ns, non-blocking) — the residual cost is dominated by Rubix's fixed ~1.5% mapping overhead plus a small, roughly constant rate of SAUM conflicts, not by a redesigned critical path.Misconception: that "flat overhead across thresholds" implies the same underlying mechanism. One is a fixed tax on every access (PRAC); the other is a fixed-but-small tax on the rare occasions mitigation is actually needed (AutoRFM).
Problem 6 · easy
Row-Press, a different DRAM disturbance attack, is explicitly out of scope for this paper. Why doesn't AutoRFM need to handle it?
Show answer
The paper states Row-Press's effects can be mitigated using alternative techniques (referencing prior work, IMPRESS). AutoRFM is scoped specifically to solving the time problem for activation-count-based Rowhammer trackers (MINT et al.) — it assumes some tracker has already identified an aggressor row via activation counting, which is not how Row-Press disturbance is characterized.Misconception: that a complete Rowhammer defense must handle every disturbance mechanism at once. This paper deliberately narrows scope to the RFM-latency bottleneck for activation-based trackers, leaving other disturbance classes to other, complementary defenses.
Quick answers

Frequently asked questions

Ten questions newcomers to this paper ask most.

Q1Is AutoRFM a new Rowhammer tracker?▾
No — it's tracker-agnostic. AutoRFM solves the "how do we find time to mitigate" problem; MINT (or PrIDE, or Mithril) still does the "which row is the aggressor" job. Appendix D shows AutoRFM working with all three, with MINT as the paper's chosen default because it's the cheapest (single-entry) and lowest-threshold.
Q2What exactly gets "locked" during mitigation?▾
Just one subarray per bank — the Subarray Under Mitigation (SAUM). A bank has 256 of them; the other 255 keep servicing ACT/PRE/read/write normally. Only a request whose row maps into the SAUM's address range fails and gets ALERT.
Q3Does a failed (ALERTed) request ever fail twice?▾
No, by design. AutoRFM guarantees the SAUM becomes free again after exactly tM (~200ns) by avoiding recursive mitigation (that's what Fractal Mitigation is for). So a retried ACT after tM is guaranteed to succeed — the mechanism has a deterministic worst case, not a probabilistic one, which also rules out denial-of-service via repeated conflicts.
Q4Why does mitigation take ~200ns specifically?▾
With a blast radius of 2 (refresh two rows on either side of the aggressor), mitigation performs 4 victim refreshes, each roughly one tRC (48ns) — about 4×48 ≈ 200ns. That sets the minimum practical AutoRFMTH at 4, since the subarray needs at least that many activations' worth of time to complete one mitigation round.
Q5Why do we need Randomized Memory Mapping (Rubix) at all — isn't 256 subarrays enough on its own?▾
256 subarrays only helps if requests are spread roughly independently across them. Standard mappings correlate nearby line addresses with nearby rows/subarrays to boost locality — which is exactly the property that makes consecutive accesses likely to hit the same (currently mitigating) subarray. Rubix's address encryption breaks that correlation, cutting ALERT rate from 3.7% to 0.22% and slowdown from 16.5% to 3.1%.
Q6What's the difference between Recursive Mitigation and Fractal Mitigation?▾
Recursive Mitigation lets any victim row that gets refreshed also probabilistically trigger another full mitigation round — potentially chaining for several consecutive rounds, making mitigation duration non-deterministic. Fractal Mitigation instead does exactly one round: always refresh the two immediate neighbors, and refresh farther neighbors with exponentially decaying probability (2^(1−d)) — no recursion, always 4 refreshes, always ~200ns.
Q7How does AutoRFM compare to PRAC+ABO, DDR5's own newer answer to Rowhammer?▾
PRAC solves the space problem (per-row activation counters, deterministic tracking) by redesigning the DRAM array — at the cost of significant area and a ~10% increase in tRC, incurred at every threshold, even high ones. AutoRFM keeps a cheap probabilistic tracker (MINT) and solves only the time problem, at a much smaller and more threshold-proportional cost (2–3.1%). The paper frames AutoRFM as a lower-cost alternative for scaling to low thresholds, not a full replacement for PRAC's deterministic guarantees.
Q8How is this different from Self-Managed DRAM (SMD)?▾
SMD is the general framework: split memory into regions, do maintenance on at most one, decline conflicting requests with ACT_NACK. AutoRFM is architecturally similar but purpose-built for ultra-low-threshold Rowhammer: it adds the two pieces SMD didn't have — randomized mapping to break spatial correlation (SMD's own PARA evaluation hit 11.3% slowdown without it) and Fractal Mitigation to handle transitive attacks deterministically (SMD doesn't address them at all).
Q9Does AutoRFM require new DDR5 pins or protocol changes?▾
No new pins. It reuses the existing ALERT signal (already defined in DDR5 for the DRAM chip to request more time) to also mean "this ACT failed, retry later." The MC gains a small busy-bit/timestamp table; the DRAM chip gains subarray-conflict detection logic and Fractal Mitigation's refresh logic — both minor relative to PRAC's array redesign.
Q10What threshold can AutoRFM actually tolerate, and at what cost?▾
TRH-D as low as 74 (AutoRFMTH=4, with Fractal Mitigation), at an average slowdown of 3.1% across SPEC, GAP, and Stream workloads — versus 33% for RFM at a comparable threshold (RFM-4, TRH-D=96 with recursive mitigation).

Core terms
AutoRFMThis paper's non-blocking refresh-management mechanism: mitigate one subarray (SAUM) instead of stalling the whole bank.
SAUMSubarray Under Mitigation — the single subarray per bank temporarily unavailable while its aggressor row's victims get refreshed.
RFMRefresh Management — DDR5's blocking command that stalls a whole bank for tRFM to give the DRAM chip mitigation time.
ALERTDRAM→MC signal, repurposed by AutoRFM to mean "this ACT conflicted with the SAUM, retry after tM."
Rubix / Randomized Memory MappingEncrypting the line address before mapping to bank/row/subarray, breaking spatial correlation to keep SAUM conflicts rare.
Fractal Mitigation (FM)A single deterministic mitigation round that refreshes near neighbors always and far neighbors with exponentially decaying probability — defends transitive attacks without recursion.
Recursive Mitigation (RM)The alternative transitive-attack defense: victim rows can themselves trigger further mitigation rounds, at the cost of non-deterministic duration.
MINTThe single-entry secure low-cost in-DRAM tracker used as AutoRFM's default; tolerated threshold is set purely by its window size.
Supporting terms
TRH-S / TRH-DRowhammer threshold for single-sided vs double-sided hammering patterns; TRH-D is the paper's default reporting metric.
RFMTH / AutoRFMTHThe activation count that triggers RFM / AutoRFM's internal mitigation, respectively — the key knob trading threshold for overhead.
RAARefresh-management Activation-count — the MC's per-bank counter that accumulates until it triggers RFM.
tRC / tRAS / tRCD / tRPDDR5 timings governing ACT/PRE cadence — the deterministic "clock" mitigation has to fit inside.
tREFI / tRFC / tRFMRefresh interval (3900ns), refresh duration (410ns), RFM duration (205ns) — the time budget mitigation competes for.
PRAC / ABOPer-Row Activation Counting / Alert Back-Off — DDR5's deterministic, array-redesign alternative; costlier but tracker-independent.
SMDSelf-Managed DRAM — the general region-based maintenance framework AutoRFM specializes for Rowhammer at ultra-low thresholds.
Half-Double / transitive attackA hammering pattern that uses victim refresh itself to inflict Rowhammer on rows beyond the direct blast radius.
