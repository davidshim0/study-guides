Filling idle compute by borrowing data, not adding silicon

Sixteen HBM channels stream a sparse matrix into 128 processing elements — yet the state-of-the-art scheduler wastes roughly 69% of PE-cycles on zero placeholders in the typical case. This is the plain-English story of Chasoň, which reaches across to a neighboring HBM channel to hand an idle PE real work instead of a zero.

📄 "Chasoň" · Bakhtiar, Namjoo, Asgari · MICRO'25 🎓 Some FPGA/HBM basics assumed — the primers cover them ⏱ ~30 min read
🔀

When a PE stalls, hand it a real non-zero BORROWED from the next HBM channel — not a zero placeholder from its own, mostly-empty rows.

Before you begin

Quick glossary, then the fundamentals

The paper's acronyms up front, then nine primers on the ideas they build on. Skip anything you already know.

Quick glossary

1What SpMV is, and why sparsity makes it hard▾

SpMV multiplies a sparse matrix A (mostly zeros) by a dense vector x to get y = Ax. Because the non-zeros are scattered unpredictably, you can't just stream through memory sequentially and expect good reuse — each row may have a wildly different number of non-zeros, at unpredictable positions.

This makes SpMV memory-bound: it spends more time waiting on data movement and irregular access patterns than actually computing. That's exactly the bottleneck HBM-based accelerators target.

Now you're ready: Chasoň is an SpMV accelerator; its whole fight is against the irregularity sparsity creates in scheduling non-zeros onto compute units.
2HBM: channels, bandwidth, and why FPGAs use it▾

High-Bandwidth Memory stacks DRAM dies vertically and exposes many independent channels (32 on the Alveo U55C) that can be read/written concurrently. That parallelism is what makes HBM so much faster than conventional DRAM for memory-bound kernels.

AMD's Alveo U55C card offers 460 GB/s peak HBM bandwidth; Chasoň uses 19 of its 32 channels and reaches 273 GB/s in practice.

Now you're ready: the paper's whole scheduling problem is about how to fill each of these independent channels' compute units without stalling.
3FPGA resources: LUT, FF, DSP, BRAM, URAM▾

An FPGA is built from generic building blocks: LUTs (lookup tables, for logic), FFs (flip-flops, for registers/pipeline stages), DSPs (hardened multiply-accumulate units), and two flavors of on-chip memory — BRAM (smaller, dual-port, used here for the dense vector x) and URAM (bigger blocks, 36 KB each on this chip, used here for partial-sum storage).

Every one of these is a limited, fixed budget on a given chip — you can't just "add more" without hitting the ceiling.

Now you're ready: Chasoň's biggest design constraint — why it migrates from only one neighboring channel — comes down to running out of URAM (Table 1).
4Streaming accelerators▾

A streaming accelerator doesn't fetch data on demand the way a CPU cache does — it continuously pushes data from memory into a pipeline of compute units, in a pre-decided order, and the units process whatever arrives. There's no cache miss to wait on; the challenge instead is making sure the pre-decided order keeps every unit busy.

Now you're ready: Chasoň and its baseline Serpens are both streaming accelerators — all the "scheduling" happens ahead of time (offline), deciding what order data streams in.
5RAW dependency and pipeline stalls▾

A PE's accumulation (adding a new partial product into a running sum) takes multiple cycles on this hardware — 10 cycles, specifically. If the very next value to process needs to add into that same running sum, it must wait for the first accumulation to finish: a Read-After-Write (RAW) dependency.

HLS-generated pipelines can't forward partial, in-progress results — the dependent operation must wait for the full 10-cycle result. That wait is a stall: the PE sits idle.

Now you're ready: the entire paper is about filling these stalls with something useful instead of letting the PE sit idle.
6Row-based and PE-aware non-zero scheduling (the baseline)▾

Row-based scheduling assigns all of one matrix row's non-zeros to one PE. Since consecutive non-zeros in the same row hit the same RAW dependency, this stalls badly.

PE-aware OoO scheduling (the prior state of the art) interleaves multiple rows round-robin onto the same PE, so the next instruction usually comes from a different row and doesn't have to wait. But it only pulls from rows already assigned to that PE's own channel — if those rows run dry of non-zeros, it inserts zero placeholders, which show up as stalls.

Now you're ready: Chasoň's whole contribution is extending this scheme's reach from "the same channel" to "the neighboring channel" — that's CrHCS.
7HLS and the initiation interval (II)▾

High-Level Synthesis (HLS) compiles C++ into hardware. A key metric is the initiation interval (II) — how many cycles must pass before the pipeline can accept a new input. II = 1 means a new value every cycle (ideal).

Without explicit zero placeholders in the data list, HLS tools conservatively assume every value might cause a RAW stall and inflate II to 10 cycles — tanking throughput. Explicitly inserting zeros keeps II = 1, at the cost of wasting those cycles on non-work.

Now you're ready: that's precisely why "idle PE" and "explicit zero in the data list" mean the same thing in this paper — and why CrHCS replaces zeros with real values instead of removing them.
8Reading the metrics: underutilization, GFLOPS, energy efficiency▾

PE underutilization % = stalls ÷ (real work + stalls) — the fraction of PE-cycles wasted on zero placeholders. Throughput (GFLOPS) = 2×(NNZ+K) ÷ latency, where K is the vector length (each non-zero does one multiply + one add). Energy efficiency (GFLOPS/W) = throughput ÷ power.

Now you're ready: every result in this paper reduces to one causal chain — lower PE underutilization → higher throughput → higher GFLOPS/W, for roughly the same power budget.
The whole story in one place

Chasoň in a nutshell

The problem, the fix, and how the pieces connect.

HBM-based SpMV accelerators stream sparse matrix data from many parallel channels into per-channel groups of PEs. The state-of-the-art scheduler, PE-aware OoO scheduling (used by Serpens and others), interleaves several matrix rows onto each PE round-robin to dodge RAW-dependency stalls. It works — until those interleaved rows simply run out of non-zeros, at which point the scheduler pads the data stream with zeros, and the PE sits idle. Across 800 real SuiteSparse/SNAP matrices, that leaves the most likely PE underutilization at 69% — meaning on a typical matrix, roughly seven in ten PE-cycles do nothing.

The paper's fix, Cross-HBM Channel OoO Scheduling (CrHCS), extends the same round-robin idea one step further: when a channel's own rows run dry, borrow a non-zero value from the next HBM channel instead of inserting a zero — as long as doing so doesn't violate the borrowed value's own RAW-dependency distance. To make this correct, the accompanying architecture, Chasoň, tags every migrated value with a 1-bit pvt flag and a 3-bit PE_src flag, routes its partial sum into a dedicated shared-channel URAM (ScUG) instead of mixing it with the channel's own private sums, reduces all eight shared copies back together in a Reduction Unit, and finally reorders the resulting streams in a Rearrange Unit so output still lines up channel-by-channel.

The payoff: PE underutilization on 800 matrices drops from a most-likely rate of 69% to roughly 30%, translating into up to 8× speedup and 2.03× better energy efficiency over Serpens — plus up to 20.33×/11.65×/2.67× over an RTX 4090 / RTX 6000 Ada / Intel Core i9 — for about 10 percentage points more LUTs and 12 more percentage points of URAM. The extra URAM storage itself doesn't touch the critical computation path, though the Reduction, Reorder, and Router units add some latency of their own.

🔀 Key takeaways

  • PE-aware OoO scheduling only refills stalls with rows from the same HBM channel — if those run dry, the PE idles.
  • CrHCS extends refilling to the neighboring channel, respecting the same RAW-dependency distance the original scheduler uses.
  • Migrated (shared) values need extra bookkeeping — a pvt bit and 3-bit PE_src — so their partial sums land in the right accumulator, not the wrong channel's.
  • A Reduction Unit (adder tree over 8 ScUGs) and a Rearrange Unit (re-order + arbiter + merge) restore correct, channel-aligned output.
  • On-chip URAM is the hard constraint: the full design needs 1024 URAMs but only 960 exist, so migration is limited to a single next channel.
  • Result: PE underutilization most-likely rate 69%→30% (800 matrices); up to 8× over Serpens, 2.03× better energy efficiency, for roughly +10pp LUTs, +6.4pp FFs, +3.4pp DSPs, and +12pp URAM (Table 1).
Six everyday pictures

How to think about CrHCS

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Cross-channel migration

Checkout lanes at the supermarket

One cashier's line stalls waiting on a slow customer; the lane beside it is backed up with quick sales. A store manager doesn't clone a cashier — they walk a customer over to the idle register. CrHCS does exactly this: an idle PE, instead of processing a zero, gets handed a real non-zero physically migrated from the neighboring HBM channel's data stream.

Where it breaks: a customer can walk to any open register; CrHCS only reaches the immediate next channel — going further costs on-chip memory it doesn't have (see the "extra shelf space" analogy).
RAW dependency · Accumulation latency

You can't slice bread mid-bake

The oven needs its full 10 minutes before the loaf is ready to slice — checking at minute 3 just gets you dough. A PE's accumulation instruction is the same: it needs its full 10-cycle pipeline before the running sum is valid, so the next add into that same sum must wait the whole way through, no partial peeking allowed.

Where it breaks: ovens don't have neighbors to borrow a finished loaf from mid-bake — but a PE does: CrHCS's whole trick is finding a different loaf (a value from another row) to slice while this one keeps baking.
The limit of round-robin · PE-aware baseline

A relay team with a fixed roster

A relay coach interleaves several runners on one track to keep it always occupied — smart, as long as the roster has enough runners. But if that team's whole roster (its assigned rows) runs out of legs to run, the track sits empty no matter how cleverly you interleaved them. That's PE-aware OoO scheduling: it fixes most stalls but is stuck once its own rows are exhausted.

Where it breaks: a real coach could recruit a spare runner from another team on the spot; PE-aware scheduling — by design — never looks past its own channel. That's the exact gap CrHCS closes.
pvt / PE_src flags · Reduction Unit

Luggage tags at the airport

A bag loaded onto a different flight's cart still has its own destination tag, so it ends up on the correct carousel at baggage claim — not mixed into a stranger's pile. A migrated non-zero keeps its origin channel and PE encoded in a pvt bit and 3-bit PE_src field, so the Router sends its partial sum to the right ScUG slot, and the Reduction Unit — the carousel — gathers every bag tagged for a given PE back together correctly.

Where it breaks: airport carousels don't need to reorder themselves afterward; Chasoň's Rearrange Unit does extra work the airport analogy skips, resequencing the shared and private streams to line up before final merging.
The hard limit · URAM budget

Extra sorting bins cost shelf space

Sorting mail by 8 destination bins keeps everything organized, but every bin needs its own shelf — and the warehouse only has so much shelving. Chasoň's full design needed 1024 URAM blocks for private- and shared-channel sorting bins, but the FPGA only has 960. So the design shrinks each ScUG from 8 bins to 4, bringing the total to 512 — the largest sorting scheme that actually fits.

Where it breaks: shrinking the shelf doesn't just save space for free — it also caps how big a single matrix pass can be, forcing bigger matrices to be split into partitions and processed in multiple passes.
Why only one hop · Scope of migration

Ask the next desk, not across the office

Borrowing a stapler from the desk right next to you costs a few seconds; walking across the office and back to a desk three rows over costs a lot more, and now two more people are involved in the errand. CrHCS restricts migration to the immediate next channel for the same reason — reaching further would need routing and bookkeeping (more pvt/PE_src combinations, more ScUG slots) for benefit that keeps shrinking the farther you reach.

Where it breaks: the paper notes that with a larger FPGA (more URAM budget), reaching two or three channels over is a real, described extension — the "one desk over" limit is a resource constraint of this specific chip, not a limit of the idea itself.
The full explanation

How it actually works

Section by section, with the paper's own examples rebuilt as diagrams you can read at a glance.

1 · The problem, quantified

PE-aware OoO scheduling maps at least 10 rows per PE and interleaves them round-robin. Whether that eliminates stalls depends entirely on whether those 10 rows contain enough non-zeros. Running the scheme on 800 real SuiteSparse/SNAP matrices (density 10⁻⁵–10¹%), the paper plots PE underutilization as a probability density: the most likely rate is 69%, and utilization ranges from 19%–96% across the whole set. The scheduler is structurally blind to one thing — non-zeros sitting one channel over that could have filled the gap.

2 · CrHCS — migrating across the RAW-dependency boundary

CrHCS is built directly on top of PE-aware scheduling. When a channel's own data list would need a zero, CrHCS instead looks at the next channel's data list for a real non-zero to insert — but it must still respect that value's own RAW-dependency distance in its original position.

3 · Encoding the migrated data

Each 64-bit element in the (offline-scheduled) data stream packs a 32-bit float value with 32 bits of metadata. Without CrHCS, that metadata is just row/column indices. With CrHCS, two extra fields make correctness possible:

// one 64-bit element in Chasoň's data stream
32-bit value  |  15-bit row  |  1-bit pvt  |  3-bit PE_src  |  13-bit col
// pvt=1: belongs to this (private) channel → use URAM_pvt
// pvt=0: migrated (shared) → use PE_src to pick the right ScUG slot
💡
Why not skip the flags? Without pvt/PE_src, a migrated partial sum would silently accumulate into the wrong channel's running total — corrupting the result. The flags cost 4 bits per element so the Router can send each value's product to the correct accumulator.

4 · Architectural support — the Router, ScUG, and Reduction Unit

Inside each PE, a small Router reads the pvt/PE_src bits and picks where the partial sum lives: URAM_pvt for private-channel values, or the matching slot in the Shared-Channel URAM Group (ScUG) for migrated ones. Since a PEG has 8 PEs, each PE's ScUG is defined with 8 slots — one per possible source PE in the neighboring channel. But that full 8-slot design needs 1024 URAMs, which exceeds the U55C's 960-URAM budget, so the implemented ScUG is trimmed to 4 slots per PE (512 URAMs total — see §6 below).

Periodically, the Reduction Unit sweeps across all 8 PEs' ScUGs, gathers the k-th slot from each (all belonging to the neighboring channel's PE k), and reduces them with an adder tree into a single running sum for that PE — recovering exactly what that PE's true total would have been had none of its values ever left its home channel.

5 · A full worked schedule (paper's own example, §3.4)

Three channels, four PEs each. Click through the paper's own numbers below to see the effect of migrating in two steps.

6 · Why underutilization never reaches 0%

CrHCS can only pull from the immediate next channel, and only if that channel has a dependency-free value on hand. When it doesn't, the stall remains. The paper's own tally: URAM demand for the full design is 1024 blocks, but the Alveo U55C has only 960 — so ScUG size is cut from 8 to 4, landing on 512 URAMs (52% utilization). Extending the reach to two or three channels would need even more URAM than the chip has, which is exactly why peak PE underutilization in Chasoň still reaches 60–65% on the hardest matrices, even though the typical case improved from ~69% to ~30%.

Follow the numbers, step by step

Worked examples

Five calculations straight from the paper's own figures and tables.

① The toy pipeline: 10% → 60% → 100%

A PE's accumulation takes 10 cycles. Over a 10-cycle window, how utilized is each scheduler?

  1. Row-based: instruction I2 needs I1's result, which isn't ready for 10 cycles. Only I1 does useful work in the window: 1/10 = 10% utilized.
  2. PE-aware OoO: interleaving 4 rows lets I1–I6 execute back-to-back before those rows run dry; cycles 7–10 fall back to zero placeholders. 6/10 = 60% utilized — i.e. the paper's stated "40% PE underutilization" for this example.
  3. CrHCS: the 4 gaps at cycles 7–10 are filled with values migrated from the neighboring channel. 10/10 = 100% utilized, "PE underutilization goes to 0%" for this toy case.
🔀
Insight: every improvement in the paper is this same arithmetic — count the wasted cycles, then find a legal value to put in their place.

② Skipping a too-close value during migration

Channel 1 offers A (row 1), B (row 1), C (row 5) to fill channel 0's gaps. Dependency distance = 2 cycles. A is scheduled at cycle 1. What happens at cycle 2?

  1. Check B: B is also row 1. Scheduling it just 1 cycle after A would violate the 2-cycle RAW distance for row 1's running sum.
  2. CrHCS skips B and checks the next candidate, C (row 5) — no dependency conflict.
  3. C is scheduled at cycle 2 in channel 0's PE1. B remains available for a later cycle, once enough distance has passed.
💡
CrHCS never breaks the correctness guarantee that made PE-aware scheduling safe in the first place — it only extends where it looks for a legal value, not whether the value is legal.

③ Figure 5's full example: 52.8% → 29%

3 channels × 4 PEs, 17 real non-zeros total.

  1. PE-aware alone needs 3 cycles × 4 PEs × 3 channels = 36 PE-cycle slots to place 17 values → 19 zero stalls. Underutilization = 19/36 ≈ 52.8% (paper rounds to 52%).
  2. Step 1: CrHCS migrates channel 1's values into channel 0's gaps (assuming no RAW conflicts, per the paper's simplifying assumption for this example).
  3. Step 2: CrHCS migrates channel 2's values into channel 1's now-emptier gaps; channel 2 in turn borrows some of channel 0's values back, to keep the three channels' workloads balanced.
  4. Result: all 17 values now fit in 2 cycles × 4 PEs × 3 channels = 24 slots → 7 stalls remain. Underutilization = 7/24 ≈ 29.2% (paper: 29%).
  5. Bonus: fewer cycles needed (3→2) means fewer HBM transfers for the same computation — the direct mechanism behind Chasoň's measured ~7× reduction in data transferred, on average, across real matrices.

④ URAM budget arithmetic

Why does Chasoň use exactly 512 URAM blocks, and how does that map to 18 MB of on-chip memory?

  1. Full design needs 1024 URAMs (private + shared storage for 16 channels × 8 PEs each) — but the Alveo U55C has only 960 available.
  2. Shrink ScUG from 8 to 4 slots per PE: this roughly halves the shared-storage term, bringing the total down to 512 URAMs (52% utilization — Table 1).
  3. Each URAM block stores 36 KB (a Xilinx URAM288 primitive). 512 × 36 KB = 18,432 KB ≈ 18 MB — matching the paper's reported on-chip memory for Chasoň.
  4. Check against Serpens: Serpens uses 384 URAMs (no shared storage needed) → 384 × 36 KB = 13,824 KB ≈ 13.5 MB — exactly the number the paper reports.
  5. The dense vector x adds 1024 BRAM18K blocks (32 per PEG) ≈ 2.5 MB, identical in both designs.
💡
The extra 4.5 MB Chasoň spends (18 MB vs 13.5 MB) buys the segregation that makes cross-channel migration correct — and it's pure on-chip storage, off the critical path, so it costs no cycles.

⑤ Real hardware: the reorientation_4 matrix, and the 2.03× average

The paper's peak reported speedup over Serpens (8.4×) comes from one specific matrix.

  1. reorientation_4 (RE): Serpens latency 0.144 ms → Chasoň latency 0.017 ms. Speedup = 0.144/0.017 ≈ 8.47×, matching the paper's stated peak of 8.4×.
  2. Throughput: Serpens 0.505 GFLOPS → Chasoň 4.289 GFLOPS, the same ≈8.5× gain, since throughput and 1/latency scale together at fixed NNZ.
  3. Energy efficiency for RE: Serpens 0.03 GFLOPS/W → Chasoň 0.11 GFLOPS/W ≈ 3.67× — a smaller gain than the throughput gain, because Chasoň's extra Router/Reduction/Rearrange logic and URAM draw a bit more power (~39 W actual vs ~36 W for Serpens).
  4. Averaged over all 20 detailed matrices (Table 3): Serpens ≈ 0.16 GFLOPS/W, Chasoň ≈ 0.33 GFLOPS/W → 2.03× average energy-efficiency improvement, the paper's headline number.
  5. Caveat (C5 vs MY, §6.2.2): data-transfer reduction doesn't map 1:1 to speedup — matrix C5 gets 6.7× less data transferred but only ~4.2× speedup, because its 23K columns need deeper ScUG accumulation in the Reduction Unit; matrix MY, with only 3K columns, gets more speedup (≈4.3×) from a smaller 4.4× data-transfer reduction.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A PEG has 12 PE-cycle slots across 3 cycles, and the matrix has 9 real non-zeros. What is the PE underutilization %, using Equation 4?
Show answer
Stalls = 12 − 9 = 3. Underutilization = stalls / (NNZ + stalls) = 3 / (9 + 3) = 3/12 = 25%.Misconception: dividing stalls by total NNZ instead of (NNZ+stalls). The denominator is the total number of PE-cycle slots actually used, not just the useful ones.
Problem 2 · medium
PE-aware OoO scheduling interleaves rows round-robin specifically to avoid RAW-dependency stalls. Why does it still leave a most-likely 69% of PEs idle on real matrices?
Show answer
Interleaving avoids stalls only when the interleaved rows collectively contain enough non-zeros to fill every cycle. It maps at least 10 rows per PE, but if those particular 10 rows (all confined to one HBM channel) are themselves sparse, there simply isn't enough real work to schedule — and the scheme has no mechanism to look beyond its own channel for more.Misconception: that round-robin interleaving "solves" RAW dependencies in general. It only solves them when there's enough same-channel data to interleave — it can't manufacture non-zeros that don't exist locally.
Problem 3 · medium
Why does a migrated non-zero need both a pvt bit and a 3-bit PE_src field — wouldn't the pvt bit alone be enough to mark it as "borrowed"?
Show answer
pvt alone tells the Router that a value came from elsewhere, but not which of the 8 PEs in the neighboring channel it originally belonged to. Without PE_src, all migrated values landing at one destination PE would get lumped into a single running sum — merging partial sums that actually belong to 8 different output rows. PE_src is what lets the Reduction Unit later separate and correctly re-sum each source PE's contributions.Misconception: that "shared" is a single bucket. It's actually 8 buckets (one per source PE) — that's exactly why ScUG needs 8 URAM slots per PE, not 1.
Problem 4 · hard
Chasoň could theoretically migrate from 2 or 3 channels ahead instead of just 1. Using the URAM arithmetic from Worked Example ④, explain concretely why it doesn't.
Show answer
Migrating from one extra channel already pushed the design from 384 URAMs (Serpens, no ScUG) to a theoretical 1024 (full 8-slot ScUG per PE) — already over the chip's 960-URAM budget, forcing a cut to 512 (4-slot ScUG). Reaching a second or third neighboring channel would require additional ScUG copies (one set per extra hop) plus wider PE_src fields to disambiguate more source channels — multiplying an already-over-budget URAM requirement. The paper explicitly frames this as a resource ceiling on this specific FPGA, not a limitation of the scheduling idea.Misconception: that migration depth is a purely algorithmic choice. It's constrained by a hard, countable hardware resource (URAM blocks), and the paper shows its arithmetic for exactly why 1 hop is the ceiling here.
Problem 5 · medium
Chasoň achieves higher throughput than an Nvidia RTX 6000 Ada in geomean (≈1.28×) but far higher throughput than an Intel Core i9 in peak (2.67×) yet less than 1× in geomean against the CPU. What does this tell you about GPUs and CPUs on SpMV?
Show answer
Both GPUs underuse their massive peak compute on SpMV because of irregular memory access patterns and underutilized ALU pipelines in streaming multiprocessors — sparsity breaks the dense, regular parallelism GPUs are built for. Interestingly, the CPU (via Intel MKL) handles SpMV better than the GPUs on average because of advanced threading and large on-chip cache (24 MB) tuned for irregular access — but at much higher power (132 W vs ~65–70 W for the GPUs), which is exactly why Chasoň still wins decisively on energy efficiency against the CPU (up to 14.61×) even where its raw throughput doesn't always win.Misconception: that more raw FLOPS (GPU) or a faster clock (CPU) automatically wins at sparse kernels. Irregular data access, not compute throughput, is usually the real bottleneck for SpMV.
Problem 6 · hard
Matrix C5 gets a 6.7× reduction in HBM data transferred by CrHCS but only a ~4.2× speedup, while matrix MY gets a smaller 4.4× data-transfer reduction but a similar or better speedup. What single structural fact about the matrices explains this?
Show answer
C5 has about 23K columns vs MY's 3K. More columns means each PE's Reduction Unit and ScUG must accumulate over a deeper set of partial sums before the final value is ready, adding latency that isn't reduced just because fewer HBM transfers were needed. So C5's extra Reduction Unit work partially offsets its data-transfer savings, while MY — with a shallower accumulation depth — converts its (smaller) data-transfer savings into speedup more directly.Misconception: that reducing data movement in isolation guarantees proportional speedup. Chasoň's added on-chip reduction logic has its own latency cost that scales with matrix shape (column count), independent of how much HBM traffic was saved.
Problem 7 · easy
Why doesn't Chasoň need to add an owner-bit-style enforcement mechanism the way a cache partitioning scheme would?
Show answer
Chasoň isn't dividing a shared resource between competing programs at runtime — its schedule (which value goes to which PE, which cycle) is decided entirely offline, before execution, by the CrHCS algorithm. There's no runtime contention to arbitrate; the pvt/PE_src tags are just labels carried along so the hardware can route an already-decided assignment correctly, not a mechanism for resolving a live conflict.Misconception: that any "shared resource" scheme needs a runtime enforcement mechanism. Chasoň's sharing is scheduled statically, so runtime bookkeeping (Router + Reduction Unit) is about correctness of a known plan, not fairness between live competitors.
Problem 8 · medium
Chasoň's average PE underutilization on 800 matrices drops to ~30%, but the paper also reports a per-PEG average that only drops to 60–65% (Figure 13, 20-matrix subset) from Serpens' ~95%. Are these two facts contradictory?
Show answer
No — they measure different things. The ~30% figure is the most-likely (mode) underutilization across a probability density over 800 diverse matrices, many of which are easy cases. The 60–65% figure is specifically the average per-PEG underutilization on a randomly selected 20-matrix subset (Table 2), where imbalanced sparsity patterns happen to stress the scheme more. Both are consistent with the paper's claim that Chasoň substantially reduces — but does not eliminate — underutilization, with the residual amount depending heavily on which matrices and which statistic you look at.Misconception: that a single "underutilization number" describes the whole system. The paper reports multiple views (PDF over 800 matrices, per-PEG averages over 20) precisely because a single number would hide real variation across workloads.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly is Chasoň accelerating?▾
Sparse matrix-vector multiplication (SpMV): y = Ax, where A is a sparse matrix and x, y are dense vectors. It's implemented on an AMD Alveo U55C FPGA using 19 of its 32 HBM channels.
Q2What's the actual difference between CrHCS and the prior "PE-aware OoO scheduling"?▾
PE-aware scheduling interleaves rows round-robin, but only among rows already mapped to the same HBM channel's PEs. CrHCS extends that lookup to the next HBM channel too, so a PE that would otherwise idle can instead process a real, dependency-free non-zero borrowed from its neighbor.
Q3How does the hardware know a value came from another channel?▾
Every 64-bit data element carries a 1-bit pvt flag (private vs. shared/migrated) and a 3-bit PE_src field identifying which of the 8 PEs in the source channel it truly belongs to. A small Router inside each PE reads these bits to route the resulting partial sum to the correct on-chip memory.
Q4Is CrHCS decided at runtime or ahead of time?▾
Entirely offline. The non-zero schedule — including which values get migrated from which channel — is computed once during preprocessing and streamed into the accelerator; Chasoň's hardware just executes and correctly reassembles that pre-decided plan.
Q5Why does Chasoň use more FPGA resources than Serpens?▾
Correctly handling migrated data requires new hardware Serpens doesn't have: a Router per PE, a Shared-Channel URAM Group (ScUG) per PE, a Reduction Unit (adder tree), and a more complex Rearrange Unit. Table 1 shows this costs roughly 10 extra percentage points of LUTs, 6.4 of FFs, 3.4 of DSPs, and 12 of URAM. The extra URAM storage itself doesn't touch the critical computation path, though the Router, Reduction, and Rearrange units add some latency of their own.
Q6Why is PE underutilization never fully eliminated?▾
Two reasons: (1) CrHCS only reaches one channel ahead, so if that specific neighbor also lacks a dependency-free value, the stall remains; (2) going further would need more URAM than the Alveo U55C has (1024 needed vs. 960 available), so the reach is capped at one hop by hardware, not by the algorithm's ambition.
Q7Does Chasoň only work for SpMV?▾
The implemented and evaluated design targets SpMV, but Section 7.1 sketches an SpMM (sparse × dense matrix) extension using 29 HBM channels total, with a larger ScUG to buffer the dense matrix's partial sums — the same Router/Reduction/Rearrange machinery generalizes.
Q8Why does an Intel CPU sometimes beat Nvidia GPUs on this workload?▾
GPUs are built for dense, regular parallelism; SpMV's irregular access patterns underuse their streaming multiprocessors' ALU pipelines. Intel's MKL, by contrast, uses advanced CPU threading and a large 24 MB on-chip cache well-suited to irregular sparse access — at the cost of much higher power draw (132 W).
Q9How is "energy efficiency" measured, and why doesn't it track throughput exactly?▾
Energy efficiency = throughput (GFLOPS) ÷ power (W). Chasoň's extra logic and URAM draw slightly more power than Serpens (~39 W vs ~36 W measured), so its energy-efficiency gain (2.03× average) is somewhat smaller than its raw throughput gain on the same matrices — the added correctness machinery isn't free.
Q10What did the authors flag as future work?▾
Extending migration beyond one neighboring channel (given more on-chip memory), and generalizing CrHCS-style cross-channel scheduling to other sparse kernels like SpMM, building on the sketch in Section 7.1.

Core terms
CrHCSCross-HBM Channel OoO Scheduling — migrates non-zeros from a neighboring HBM channel to fill PE stalls, extending intra-channel PE-aware scheduling.
ChasoňThe streaming SpMV accelerator (built on Serpens) that provides the architectural support (Router, ScUG, Reduction Unit, Rearrange Unit) CrHCS needs to be correct.
PE-aware OoO schedulingThe prior state of the art: round-robin interleaving of several rows onto one PE, limited to rows on the same HBM channel.
pvt / PE_src1-bit "private vs. shared" flag and 3-bit source-PE index carried by each migrated value, used to route its partial sum correctly.
ScUGShared-Channel URAM Group — 4–8 URAM slots per PE storing migrated (shared) partial sums separately from private ones.
Reduction UnitAn adder tree that sums each source PE's scattered ScUG contributions back into one correct running total.
Rearrange UnitRe-order + Arbiter + Merge logic that realigns private and shared output streams into correct channel order before final output.
PE underutilizationStalls ÷ (real non-zeros + stalls) — the fraction of PE-cycles spent on zero placeholders instead of real work (Eq. 4).
Supporting terms
HBM channelOne of many independent memory ports on a High-Bandwidth Memory stack; Chasoň uses 19 of 32 on the Alveo U55C.
RAW dependency distanceThe minimum number of cycles that must separate two operations touching the same accumulator (here, 10 cycles for a full accumulation).
URAM / BRAMTwo flavors of Xilinx on-chip memory; URAM (36 KB/block) stores partial sums, BRAM stores the dense vector x.
Initiation Interval (II)Cycles between successive pipeline inputs in HLS-generated hardware; explicit zero-padding keeps II = 1.
NNZNumber of non-zero elements — the only entries that do real computational work in a sparse matrix.
GFLOPS / GFLOPS-per-WattThroughput and energy-efficiency metrics: 2×(NNZ+K)/latency, and throughput÷power respectively.
TAPA / AutobridgeThe HLS task-parallel dataflow framework and floorplanning/place-and-route tool used to build and lay out Chasoň on the FPGA.
SerpensThe prior HBM-based SpMV accelerator (PE-aware OoO scheduling, no cross-channel migration) that Chasoň is built on top of and compared against throughout.
