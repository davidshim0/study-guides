Threads that must run together, not just pinned apart

A litmus test only reveals a weak memory behavior if its threads race on different cores within a few cycles. Pinning them helps one test — it can't coordinate a whole campaign. Here's how sched_ext turns "run together" into a scheduler policy.

📄 Siddiqui & Wang · eBPF '26 🎓 Some OS/concurrency basics assumed — primers cover them ⏱ ~20 min read
🧵

Don't just pin WHERE threads run — tell the scheduler they must run TOGETHER, or the cycle-scale window for the weak behavior never opens.

Before you begin

Quick glossary, then the primers

Acronyms first, since the paper leans on them hard; then ten short primers you can open in any order.

Quick glossary

1What a litmus test is▾

A tiny concurrent program designed to expose one specific hardware reordering. Example SB: thread 0 stores x, reads y; thread 1 stores y, reads x. If both reads return the old value, that's the "weak" outcome — proof each core buffered its store past its own read.

Now you're ready: the whole paper is about making that weak outcome show up reliably, at scale, across a test campaign.
2Why the timing window is so tight▾

Weak behaviors like SB's often require both threads' relevant accesses to overlap within a window just a few cycles wide. For SB's weak outcome, both threads' reads must land inside that window — meaning both threads must actually be executing, on different cores, at nearly the same instant.

Now you're ready: this is the "cycle-scale window" the paper keeps referencing — it's a scheduling requirement, not just a code requirement.
3Sockets, NUMA nodes, and "same-socket"▾

A 2-socket server has two NUMA nodes; cores on the same node share faster interconnects and (often) a more predictable timing relationship than cores split across nodes. Cross-socket communication adds latency — enough to blow the cycle-scale window.

Now you're ready: "same-socket placement" is the paper's single biggest lever — Table 1's whole story is what happens when you get this right vs. wrong.
4Why static affinity (taskset) isn't enough▾

taskset sets a thread's CPU affinity mask — it can bind a thread (or process) to one or more CPUs, but it says nothing about a group of threads needing to run simultaneously. Once a campaign runs more test instances than the machine can fit at once, pinned threads still get time-sliced independently — a gang can be individually "placed" yet never actually co-scheduled. The missing piece is coordination, not placement.

Now you're ready: this gap — coordination, not just placement — is exactly what scx_gang/scx_tgang add.
5eBPF and the verifier▾

eBPF lets you load custom code into the kernel, but only after a verifier proves it's safe: bounded loops, no unchecked memory access, bounded state. This is a real constraint, not a formality — it shapes what algorithms you can even write (Section 3.3's rewrite is a direct consequence).

Now you're ready: when scx_tgang's first design gets rejected with -E2BIG, that's the verifier's state budget, not a bug.
6sched_ext callbacks and the DSQ▾

sched_ext gives the eBPF program a few hooks: select_cpu (pick a CPU on wakeup), enqueue (route a runnable task to a queue), dispatch (move work onto a core when it needs more). Tasks sit in DSQs (dispatch queues) before landing in a per-CPU local DSQ that actually feeds the core.

Now you're ready: both schedulers in this paper reuse the same three callbacks — they differ only in what they do inside them.
7Gang scheduling, in one sentence▾

Schedule a group of threads (a "gang") as a single unit: either give them dedicated resources so they can all run at once (spatial), or run the whole group together for a burst of time before switching to the next group (temporal). Traditionally used in HPC to stop threads spin-waiting on descheduled peers.

Now you're ready: this paper inverts the usual motivation — not avoiding wasted spinning, but exploiting precise co-execution to widen a measurement window.
8Reading the rate numbers▾

Results are reported as "weak behaviors per 10⁶ iterations," as a median with a [min, max] range, because the rate is often heavy-tailed or bimodal (it depends on where the scheduler happened to place threads on a given run). A high median with a near-zero minimum is a warning sign, not a success.

Now you're ready: several of the paper's punchlines are about the minimum, not the average — watch for that in the worked examples.
9Oversubscription▾

A machine is oversubscribed when more runnable threads exist than there are cores to run them at once — e.g. 96 gang threads on 48 cores is 2× subscription. Spatial reservation (giving each gang permanent dedicated cores) simply runs out of room here; something has to share.

Now you're ready: this is exactly the regime where scx_gang degrades and scx_tgang's time-slicing becomes necessary.
10tgid / tid and process structure▾

A thread group ID (tgid) identifies a process; each of its threads has its own thread ID (tid). The paper's gang map is keyed first by tgid, then by tid, so the scheduler can look up "which gang does this thread belong to" cheaply.

Now you're ready: that's the entire enrollment mechanism — a thread writes itself into this nested map, and the scheduler reads it back.
The whole story in one place

Gang-scheduling litmus tests, in a nutshell

The problem, the fix, and why it matters for anyone who runs concurrent microbenchmarks on real hardware.

A litmus test's sensitivity depends on a condition it cannot enforce itself: its threads must race on different cores within a cycle-scale window. The default Linux scheduler treats those threads like any other work — it may scatter them across NUMA sockets, and on a 2-socket 48-core Xeon, that scattering alone collapses SB's weak-behavior rate from 10,906 (same-socket) to 62 per 10⁶ iterations, a roughly 176× drop, with the unpinned default landing in between at a wildly inconsistent 1,429 (ranging from 7 to 12,284 across runs).

Manual taskset pinning fixes this for one hand-tuned test. It does not scale: once a campaign runs more gang threads than the machine has cores, statically pinned threads are still time-sliced independently, and gangs fall apart even though every thread is "placed" correctly.

The paper's fix is to make co-scheduling an explicit scheduler policy using sched_ext, Linux's eBPF-based extensible scheduling class. Threads opt into a gang by writing their ID into a pinned eBPF map. Two policies then enforce the gang invariant differently: scx_gang reserves dedicated, NUMA-local cores per gang (spatial), matching hand-tuned pinning (11,835 median) without manual topology tuning. scx_tgang instead time-slices whole gangs as units (temporal), sustaining a high floor — the worst per-gang rate stays above 11,000 — even at 2× oversubscription, where scx_gang and static affinity both collapse.

🧭 Key takeaways

  • Placement, not just synchronization primitive, dominates weak-behavior rate — cross-socket vs same-socket is a ~176× swing with identical code.
  • The default scheduler is not just lower on average — it's bimodal, silently losing 1–2 orders of magnitude of sensitivity on some runs.
  • scx_gang (spatial) automatically matches hand-tuned same-socket pinning: 11,835 vs 10,906 median.
  • scx_tgang (temporal) is what survives oversubscription — static affinity effectively livelocks at 2×.
  • Overhead is real but secondary: scx_gang costs ~39% raw throughput on a single socket, dwarfed by NUMA placement gains on a real server.
  • The eBPF verifier's state budget directly shaped the algorithm — a natural two-phase design was rejected; a single-pass, greedy design shipped instead.
Five everyday pictures

How to think about gang scheduling

Each stands alone. Every card ends with where the picture stops being accurate.

The core idea · Relay team

A relay team, not solo runners

Pinning one runner to lane 3 says nothing about whether her teammates are even on the track at the same moment. A litmus gang is a relay team: its members must all be racing, at once, on adjacent lanes (NUMA-local cores) — not one on this field, one on a field across town (another socket).

Where it breaks: a relay team only needs sequential handoffs; litmus threads need simultaneous overlap — the synchronization is tighter than the metaphor suggests.
Safety gate · eBPF verifier

Airport security for kernel code

Before eBPF code runs inside the kernel, it must pass a checkpoint: bounded loops, provably-terminating scans, no unchecked memory access. Most designs pass fine; some — like the first scx_tgang attempt, which scanned the whole machine and then the gang queue — get turned away for carrying too much "luggage" (state) through the gate.

Where it breaks: airport security doesn't reshape your itinerary; the verifier's rejection directly forced a redesign (single-pass activation) — it's a design constraint, not just a filter.
Spatial policy · scx_gang

Reserved adjacent parking

Instead of hoping your carpool parks nearby, the lot assigns your whole group a reserved block of adjacent spots, on the side of the lot near your building (NUMA node) — and tows other cars that try to park there. That's scx_gang: dedicated, NUMA-local cores per gang, with interlopers preempted off.

Where it breaks: a parking lot has plenty of blocks; a machine has a fixed number of cores. Once more gangs arrive than there are blocks, reservation-based parking simply runs out — this is exactly where scx_gang degrades under oversubscription.
Temporal policy · scx_tgang

A shared conference room's booking calendar

When there isn't a room for every team, you don't let each person wander in independently — you book the whole room for team A's slot, then team B's, so each team always meets as a complete group during its turn. scx_tgang does this for cores: it moves an entire gang onto idle cores for a fixed slice, then rotates to the next gang, rather than letting individual threads drift in and out.

Where it breaks: a calendar booking is all-or-nothing; scx_tgang's actual activation is greedy — it seats as many of the front gang's members as there are idle chairs, occasionally leaving a few standing until the next round.
Why not pure affinity · Sticky notes vs a contract

A sticky note vs. a standing agreement

taskset is a sticky note on one desk: "sit here." It says nothing about the other sticky notes on other desks needing to be occupied at the same time. sched_ext is a standing agreement the building manager enforces: these specific desks are reserved together, or these people meet as a group during this hour — coordinated, not just individually labeled.

Where it breaks: a standing agreement in a building is administrative; in the kernel it comes with real runtime cost (extra map lookups, dispatch logic) — about a 39% raw-throughput hit on an otherwise idle single socket.
The full explanation

How it actually works

From the gang abstraction to the two eBPF policies that enforce it, and the verifier constraint that reshaped the algorithm.

1 · The gang abstraction

A litmus gang is the set of threads belonging to one test instance that must be co-scheduled. Each thread enrolls by writing its thread ID into a pinned eBPF hash-of-maps, keyed first by thread-group ID (tgid), then by thread ID (tid). The resulting gang identity is visible to the scheduler through the map. Threads that don't enroll run as ordinary background work on a shared weighted-vtime queue.

2 · scx_gang — spatial partitioning

When a gang's first member appears, the scheduler reads its NUMA node (scx_bpf_cpu_node) and treats it as the gang's home node. Each member then claims one CPU from a global per-CPU ownership table via atomic compare-and-swap. On enqueue, a gang thread goes straight into its reserved core's local DSQ and the core is preemptively kicked; background tasks run only on CPUs no gang owns. Reservations release when a gang thread exits — dynamic, not a fixed offline partition.

3 · scx_tgang — temporal multiplexing

Spatial reservation needs enough free cores for every gang at once — it breaks down once a campaign oversubscribes the machine. scx_tgang instead keeps runnable gang members in a shared FIFO (GANG_DSQ) and activates one gang at a time for a fixed slice.

void dispatch(s32 cpu) {
  if (nr_queued(GANG_DSQ) == 0) { move_to_local(SHARED_DSQ); return; }
  if (cas(&actlock, 0, 1) != 0) { move_to_local(SHARED_DSQ); return; } // another CPU activating
  u64 G = 0;
  for_each (p, GANG_DSQ) {              // single verifier-friendly pass
    u64 k = gang_of(p);
    if (G == 0) G = k;              // first member fixes the gang
    if (k != G) continue;
    s32 c = scx_bpf_pick_idle_cpu();
    if (c < 0) break;              // no more idle cores right now
    move(p, LOCAL_ON|c, PREEMPT);       // place + preempt onto c
  }
  cas(&actlock, 1, 0);
  move_to_local(SHARED_DSQ);
}
💡
Why a try-lock, not a full mutex? It prevents two CPUs from activating two different gangs at once, while staying cheap and verifier-friendly. The activation is greedy — it places as many of the front gang's members as there are idle cores, leaving any remainder queued for the next slice.

4 · The verifier constraint that reshaped the algorithm

The natural design — scan the machine to check the front gang fits, then scan the FIFO to place it — was rejected by the eBPF verifier (reported as -E2BIG): bounded loops, repeated map lookups, and per-CPU scans together exceeded its state budget. The single-pass procedure above was the fix: it finds idle cores and places members greedily in one verifier-friendly pass, trading strict all-or-nothing admission for something that compiles and works well in practice.

⚠
Consequence: partial activations (some but not all gang members placed) are possible. They're negligible while gangs fit the machine (≤0.01% of activations at K≤16) and rise only under oversubscription (1.6%→29% from 1.25× to 2×) — round-robin rotation typically reforms the gang within one or two slices.
Follow the numbers

Worked examples

Four calculations straight from the paper's tables.

① The 190× swing, recomputed

Table 1: D-crossnode median = 62; scx_gang median = 11,835. What's the multiplier, and does it match the paper's headline number?

  1. 11,835 ÷ 62 = 190.9×.
  2. The paper states "a 190× swing caused only by CPU placement" — this matches exactly, confirming the number comes from comparing cross-socket against scx_gang (not against same-socket pinning).
  3. Same-socket pinning vs. cross-socket gives a slightly smaller 10,906 ÷ 62 ≈ 176× — still enormous, but scx_gang's slight edge over manual pinning pushes the figure to the rounder "190×."
🍯
Insight: every bit of this swing comes from CPU placement alone — code and synchronization are held fixed across all four configurations.

② The "8×" default-scheduler gap

D-1socket median = 10,906; D-unpinned median = 1,429. Check the paper's "about 8× below same-socket pinning" claim.

  1. 10,906 ÷ 1,429 ≈ 7.63× — the paper rounds this to "roughly 8×."
  2. But the unpinned range is [7, 12,284] — its best runs nearly match same-socket pinning, its worst runs are catastrophic.
  3. The median understates the real problem: it's not a uniform 8× slowdown, it's a coin flip between "fine" and "nearly zero."
💡
This is why the paper reports min/max alongside the median — a single average would hide the bimodality that motivates gang scheduling in the first place.

③ Why the median lies at high load (Table 2, K=32)

At K=32 gangs (2× oversubscription): default median = 15,590 — higher than scx_tgang's 14,628. Does the default scheduler win here?

  1. Taken at face value, yes — default's median is higher.
  2. But taskset-pin (static affinity) at the same load is 0 (livelocked) and scx_gang drops to 5,105 — the machine is under real contention, and per-gang outcomes vary enormously.
  3. The paper's claim is about the floor, not the median: scx_tgang maintains its worst per-gang rate above 11,000 across all loads, while default and scx_gang both have runs that collapse into the hundreds.
  4. A high median built on some gangs winning the scheduling lottery and others losing badly is exactly the unpredictability the paper is arguing against — the same trap as example ②.
⚠
Takeaway: for a testing tool, a guaranteed floor beats an occasionally-higher average — a single unlucky gang can silently undercount weak behaviors by orders of magnitude.

④ ARM: placement still matters on weakly-ordered hardware

Table 3, 2+2W on the Jetson Orin Nano: ARM (default) = 3,500; ARM (best pin) = 25,000.

  1. 25,000 ÷ 3,500 ≈ 7.1× — same-cluster vs. cross-cluster placement, matching the paper's "roughly 7×" claim.
  2. This is a different ISA and a different microarchitecture than the x86 Xeon/i7 machines in Table 1, yet the same placement sensitivity reappears.
  3. Also note: x86-TSO forbids MP, 2+2W, and IRIW outright (0 weak behaviors observed), while ARM permits all three — confirming the test suite is correctly distinguishing memory models, not just measuring noise.
🍯
Insight: the scheduling effect this paper targets isn't an x86-NUMA quirk — it reappears on ARM too. That said, the evaluation covers only two x86 machines and one ARM board; the paper itself flags broader tests across more microarchitectures, and an ARM NUMA machine in particular, as needed to strengthen the generality claim.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
You pin SB's two threads to two specific cores with taskset and get a great weak-behavior rate. Why might this same command fail to help once you launch 20 more SB instances concurrently?
Show answer
Taskset only fixes which CPU each individual thread may run on — it says nothing about when it runs relative to its partner thread. Once the machine is busy with 20 other pinned gangs, each pinned thread is still time-sliced independently by the default scheduler, so a gang can be "correctly placed" yet never actually co-scheduled at the cycle scale the test needs.Misconception: that correct placement implies correct timing. Affinity is necessary but not sufficient — coordination requires the scheduler to treat the gang as a unit.
Problem 2 · medium
D-unpinned's weak-behavior rate ranges from 7 to 12,284 across 30 runs, median 1,429. A colleague argues "the median (1,429) is a reasonable summary of default-scheduler performance." What's wrong with that framing for a testing tool?
Show answer
The distribution is bimodal, not centered around 1,429 — runs tend to land near the same-socket rate (~11,000, when the scheduler happens to keep threads together) or near the cross-socket rate (~7–100, when it scatters them), with the median as an artifact of the mix. A campaign that silently lands in the low mode has lost one to two orders of magnitude of sensitivity without any error message.Misconception: that a median summarizes a unimodal-ish spread. For heavy-tailed, bimodal measurements, the floor (minimum) matters more than the center for a tool whose job is not to miss real behaviors.
Problem 3 · medium
scx_gang collapses to a median of 370 weak/10⁶ at K=8 gangs, even though the machine (48 cores, 3 threads/gang) has plenty of free cores for 24 threads. Why?
Show answer
scx_gang assigns a gang's home node from its first member's current NUMA node. With several gangs launching around the same time, first-member assignment can pile multiple gangs onto one socket while leaving the other underused — an imbalance, not a lack of total capacity. A load-balancing node assignment would fix this; the paper names it as a known limitation.Misconception: that "enough total free cores" is the same as "enough free cores on the node the gang happened to land on." Spatial reservation is sensitive to per-node balance, not just aggregate occupancy.
Problem 4 · hard
The first scx_tgang design (scan-then-place, two phases) was rejected by the eBPF verifier with -E2BIG. Explain what kind of program property the verifier is bounding, and why a single-pass redesign fixes it.
Show answer
The verifier bounds the total reachable program state it must exhaustively check for safety — combining bounded loops, repeated map lookups, and per-CPU scans across two separate phases multiplies that state past its budget. A single pass that both checks idle-core availability and places members inline (Listing 1) keeps the loop-and-lookup combination small enough to verify, at the cost of being "greedy" (no strict all-or-nothing admission check) rather than fully atomic.Misconception: that verifier rejections are just a formality to route around with equivalent code. Here the rejection forced a genuinely different algorithm (greedy single-pass vs. two-phase check-then-commit), with a measurable side effect (partial activations under oversubscription).
Problem 5 · medium
On the single-socket i7-9700, D-unpinned and scx_gang produce statistically similar weak-behavior rates (87,322 vs 90,972), yet scx_gang's raw throughput is lower (88k vs 144k weak/s). What does this pair of results establish?
Show answer
It isolates scx_gang's mechanism from its overhead. Same rate when there's only one socket (no harmful placement to correct) shows scx_gang doesn't fabricate weak behaviors — it just removes bad placements. The throughput gap shows the scheduler's extra dispatch logic and map lookups have a real cost. The paper's argument is that this cost is worth it only on NUMA/contended machines, where it's dwarfed by the placement gains in Table 1 — not universally.Misconception: that scx_gang "speeds up" litmus testing in general. It trades some raw throughput for reliability specifically where placement is a risk (multi-socket, contended); on a single idle socket it's a net cost with no benefit.
Problem 6 · easy
SB is allowed under x86-TSO, but MP, LB, and IRIW are forbidden. On the x86 machines in this paper, what weak-behavior rate should MP show, regardless of scheduling policy?
Show answer
Zero. TSO forbids the outcome MP is designed to detect, so no amount of better placement or gang scheduling will produce it on x86 hardware — Table 3 confirms 0 weak behaviors for MP, LB, and IRIW under x86-TSO. Scheduling only affects how reliably you observe behaviors the hardware actually permits; it can't create behaviors the memory model forbids.Misconception: that gang scheduling makes "more" weak behaviors appear. It only raises the rate of observing a behavior that's already possible on that hardware — it changes sensitivity, not the memory model.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Isn't this just a fancier taskset?▾
No — taskset binds individual threads to CPUs but expresses nothing about a group needing to run simultaneously. Once a campaign runs more gangs than fit on the machine, statically pinned threads are still scheduled independently. sched_ext lets the policy treat a gang as one unit: reserve cores for it (scx_gang) or move the whole group together (scx_tgang).
Q2Does gang scheduling create weak behaviors that wouldn't otherwise be possible?▾
No. It only improves how often an already-hardware-permitted behavior is observed. Behaviors forbidden by the memory model (e.g. MP, LB, IRIW under x86-TSO) stay at zero regardless of scheduling.
Q3When does scx_gang beat scx_tgang, and vice versa?▾
scx_gang wins when gangs comfortably fit on the machine and map cleanly onto NUMA nodes — it matches hand-tuned pinning with zero manual topology work. scx_tgang wins once the campaign oversubscribes the machine (more gang threads than cores) or gangs pile unevenly onto one node — its time-slicing sustains a high floor where spatial reservation runs out of room.
Q4What exactly forced the eBPF verifier rejection?▾
The original scx_tgang design scanned the machine to check whether the front gang fit, then separately scanned the FIFO to place it. Combining bounded loops, repeated map lookups, and per-CPU scans across those two phases exceeded the verifier's state budget (reported as -E2BIG). The fix was a single verifier-friendly pass that checks and places in one step.
Q5Is scx_tgang's activation strictly all-or-nothing?▾
No — it's greedy. It places as many of the front gang's members as there are idle cores in one pass, leaving any remainder queued. This is negligible while gangs fit the machine and rises under oversubscription (up to 29% of activations at 2×), though round-robin rotation typically reforms a partial gang within one or two slices.
Q6How much does gang scheduling cost in raw overhead?▾
On a single, otherwise-idle socket where placement isn't an issue, scx_gang drops raw throughput from ~144k to ~88k weak behaviors/second (~39%) due to extra dispatch logic and map lookups. On a real NUMA machine this cost is outweighed by avoiding catastrophic cross-socket placements.
Q7Does this replace litmus7 / diy?▾
No — it's complementary. litmus7 already provides test generation, barriers, and static affinity; on a single test with careful pinning it matches or beats this paper's schedulers. The gap appears when many tests share a machine, where litmus7's static affinity reproduces the same collapse seen in taskset-pin. The authors propose litmus7 could enroll its threads in the gang map and inherit the co-scheduling guarantee.
Q8Why does the reliability framing matter more than average speedup?▾
A litmus campaign reports an empirical bound on hardware behavior. If the scheduler silently collapses sensitivity by 1–2 orders of magnitude on some runs (as the default does), the campaign can falsely conclude a weak behavior doesn't occur, when it simply wasn't given the chance to appear. A guaranteed high floor is worth more than an occasionally-higher average for this use case.
Q9Does this generalize beyond x86?▾
The paper's evaluation is mostly x86 (a NUMA server and a single-socket desktop), with one ARM board (Jetson Orin Nano) confirming the same placement sensitivity (~7× for 2+2W across clusters). The authors note a sched_ext-capable ARM NUMA machine would strengthen this further — it's flagged as a limitation, not yet fully validated.
Q10What's still missing / left for future work?▾
Gangs only span a single process (no cross-process gangs); the map-based opt-in is unguarded; scx_tgang's greedy activation could be made strictly all-or-nothing at a throughput cost; scx_gang's node assignment could be load-balanced; and dispatch overhead is reported only in aggregate, not as a full fairness/starvation study against real background work.

Core terms
GangThe set of threads belonging to one litmus-test instance that must be co-scheduled; identified by (tgid, group) in a pinned eBPF map.
