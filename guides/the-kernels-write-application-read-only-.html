Let the kernel hold the pen; the app only reads

Optane tried to make cheap, slow-to-write memory look exactly like DRAM — and paid for the disguise in latency. This paper strips the disguise off: LtRAM stays read-only to applications, and only the OS is allowed to write it.

📄 "The Kernel's Write: AROM" · Shim, Mohr, Levis 🎓 Assumes CXL/tiering background — primers focus on what's new here ⏱ ~25 min read

Before you begin

Seven things the paper assumes or builds on

Tuned for a tiering/CXL background — these skip cache/tiering basics and go straight to what's specific to LtRAM and AROM.

1LtRAM's three drawbacks, precisely▾

Not "slow like SSD" — LtRAM reads compete with DRAM. The costs are: (a) read/write latency asymmetry (writes are μs-scale, not ns), (b) coarse write granularity (a block, not a cache line), and (c) bounded endurance (10⁵–10⁸ writes/cell). All three are write-side; reads are the whole reason LtRAM is attractive.

Now you're ready: every design choice in this paper is about isolating writes from the fast, unconstrained read path.
2Why Optane copied the SSD playbook▾

SSDs hide flash's write quirks behind a Flash Translation Layer (FTL): wear-leveling, remapping, buffering. Optane put the same three mechanisms on a DIMM controller (XPController) so software could treat it like DRAM.

Now you're ready: the paper's argument is that this pattern works for SSDs (async, block-granular, off the CPU's critical path) but backfires on a memory bus (sync, load/store, on the critical path).
3CoW, but flipped▾

Classic CoW shares one physical page across processes until either writes; the fault duplicates the page so writers don't disturb readers. AROM repurposes the same fault mechanism for a different goal: any write to an LtRAM-resident page is illegal, so the fault always migrates the page to DRAM, not just a private copy for one writer.

Now you're ready: "CoW" here means "copy-on-write-to-LtRAM," a placement decision, not a sharing optimization.
4Three granularities in tension▾

A CPU cache line (64B), a DRAM/Linux page (4KB), and a flash-style erase block (also 4KB here, but 256B on Optane's XPLine) don't naturally align. Mismatches force read-modify-write. AROM's fix is to pick one write unit — the 4KB page — and make every layer (device write granularity, OS page size, migration unit) use exactly that.

Now you're ready: watch for "4KB" throughout — it's the load-bearing number that makes the whole interface line up.
5LtRAM zone as a Linux mm concept▾

Linux already partitions physical memory into zones (DMA, Normal, Movable) with per-zone free lists. AROM adds an LtRAM zone at the top of the allocator's fallback order, so LtRAM is never used unless explicitly requested or migrated into — reusing existing mm plumbing rather than a bolt-on tiering daemon.

Now you're ready: this is a much lighter mechanism than TPP/Memtis-style promotion/demotion daemons — no separate hotness tracker, just a write-protect + fault path.
6Token-bucket rate limiting, applied to endurance▾

A token bucket normally paces network packets. Here it paces migrations into LtRAM: tokens regenerate at a fixed rate tied to the device's rated endurance and target lifetime; a migration consumes one; none available means the migration waits. This is the software replacement for hardware wear-leveling.

Now you're ready: the rate is derived once from device specs (§5.2.2) — no per-block erase-count bookkeeping needed.
7Why this isn't just another CXL-tiering paper▾

TPP, Memtis, HeMem, and Colloid all manage a slower tier that both reads and writes pay a penalty for — misplacement only costs you a slower access. AROM's LtRAM is a main-memory replacement for read-mostly data: reads are DRAM-competitive by design, and the entire penalty is concentrated in one CoW migration paid only when a write actually happens.

Now you're ready: this reframes "misplacement cost" from a read-side problem (classic tiering) to a write-side, critical-path problem — which is why phase changes are more dangerous here (see Practice, Q8).
The whole story in one place

AROM in a nutshell

Why Optane's hardware translation layer backfires, and what replacing it with an OS invariant buys you.

DRAM now costs over half of server budgets, and its cost-per-bit scaling has slowed for a decade — a structural problem the 2025–26 AI demand spike only made more visible. LtRAM technologies (RRAM, PCM, FeFET, MRAM) offer a denser, cheaper complement with DRAM-competitive read latency, at the cost of slow/coarse writes and limited endurance.

Intel Optane, the one commercial LtRAM DIMM, tried to hide those write quirks by copying the SSD translation-layer pattern into an on-DIMM controller (XPController): wear-leveling, an Address Indirection Table (AIT), and read/write buffers. The paper's measurements show each mechanism taxing latency directly — RMW on sub-256B writes, an AIT lookup on every read, 160× tail spikes from opaque migrations, and bandwidth collapse under mixed workloads.

The proposed fix is Application Read-Only Memory (AROM): applications may only read LtRAM; only the kernel writes it, and only while migrating a page back to DRAM. AROM is enforced with copy-on-write — a store to an LtRAM page faults, the kernel copies it to DRAM, then the store applies. Because the invariant guarantees the device only ever sees whole-page writes from one trusted writer, the on-DIMM controller can drop wear-leveling and the AIT entirely, and the OS instead uses machinery it already has: dirty bits for read-mostly classification, and a token bucket for endurance.

The payoff: a prototype on Enzian with NOR flash validates the interface, and latency projections put candidate LtRAM technologies within 9% faster to 220% slower than DRAM per access — a 26–79% improvement over Optane — while retaining LtRAM's density and cost advantage.

🔑 Key takeaways

  • Optane's overhead comes from the DRAM-compatible interface, not the underlying memory technology.
  • AROM: apps read LtRAM only; the kernel writes it only during page migration, enforced via CoW.
  • Aligning writes to 4KB pages (not 256B XPLines or 64B cache lines) structurally removes the read-modify-write path.
  • Removing the AIT and hardware wear-leveling removes their latency taxes (~76–200ns/read, 160× tail spikes) at the cost of new OS responsibilities.
  • Read-mostly classification reuses dirty-bit scanning; endurance is paced by a token bucket, not per-block erase counters.
  • Misplacement cost is asymmetric: a cold-but-wrong page just reads slower (like CXL tiering); a page that turns write-heavy pays a CoW migration on the critical path.
  • Projected per-access read latency: 9% faster to 220% slower than DRAM; 26–79% faster than Optane, for the three non-prototype candidates.
Six pictures

How to think about AROM

Each stands alone; every card names where the picture stops being literally true.

The invariant · AROM

A reference-only library book

Patrons may read the reference volume at the desk but never write in it. If a page truly needs updating, the librarian pulls it, copies it to a working notebook, edits there, and reshelves later. LtRAM is the reference book; the kernel is the only librarian allowed to touch the original.

Where it breaks: a real librarian edits in place occasionally; the kernel never does — it always relocates the page to DRAM first, never patches LtRAM directly.
The villain · Optane's mistake

Bringing an SSD's paperwork to a DIMM's meeting

An SSD's controller can shuffle papers (wear-level, remap) while the requester waits asynchronously off to the side — the delay is tolerable. Optane brought the same paperwork habit to a DIMM, where the CPU is standing at the counter waiting synchronously for every load/store. The habit that worked in one room stalls the other.

Where it breaks: SSDs also suffer FTL overhead; it's just amortized over a slower baseline (μs-scale NAND access) where a few hundred extra ns barely registers.
Enforcement · CoW fault

A one-way turnstile

Anyone may walk through the turnstile toward the reading room (reads pass freely). Try to push back the other way (a write) and it locks, redirects you through a side door to a fresh copy in the "editing room" (DRAM), and only there do you actually make your mark.

Where it breaks: a turnstile is a hard mechanical gate; AROM's redirect is a soft page-fault — cheap when writes are rare, expensive if they suddenly aren't (see Practice, Q8).
Endurance · Token allocator

A water-rationing meter, not a punishment

A household is allotted a fixed flow rate of water per day, computed once from the reservoir's known capacity and the community's planned lifespan. Use less today, bank the difference for a heavier day later. Migrations into LtRAM draw from the same kind of meter — sized from rated endurance ÷ deployment lifetime — so the OS never needs to track each individual pipe's wear.

Where it breaks: the meter caps total flow, not where it goes — it doesn't by itself guarantee even wear across physical blocks (an open problem the paper flags in §7).
Huge pages · The open problem

One messy roommate spoils the whole dorm room

A 2MB huge page is like a shared dorm room: if even one 4KB "bunk" inside it is a hot write-heavy resident, the entire room becomes ineligible for the quiet LtRAM wing — or worse, the whole 2MB gets copied out on that one resident's single write.

Where it breaks: real roommates don't get duplicated; a CoW migration really does copy the full huge page's data, so this isn't just a metaphor for inconvenience — it's a literal 2MB copy the paper flags as unresolved (§7).
Contrast · vs. CXL tiering

A slow lane vs. a locked lane

Classic tiering (TPP, Memtis, HeMem) treats the far tier like a slow lane on the highway — misjudge it and you just drive a bit slower on your next trip through, for both directions. AROM's lane is lockedfor writes — misjudge a page as read-mostly and the very next write forces an immediate, on-the-spot detour (a page copy) before you can proceed at all.

Where it breaks: the locked lane always eventually opens (the copy succeeds and completes the store); it's not a dead end, just a forced, synchronous detour.
The full explanation

How it actually works

From Optane's four overheads to the OS mechanisms that replace them, to the Enzian prototype.

1 · What Optane's controller cost, mechanism by mechanism

MechanismOverheadAROM's fix
Cache-line/XPLine mismatch75% write throughput drop (2.3→0.56GB/s); ~2× random read4KB page writes only — OS coalesces naturally
Hardware wear-levelingMigration ≈ every 3.4MB written; ~60μs tail (>160×)OS-scheduled erases; no hidden migration
Address Indirection Table+76–200ns/read; 94% of reads miss the 16MB AIT cache on a 128GB DIMMNo on-module map at all
Workload-agnostic design~67–70% read-bandwidth loss under 50/50 R/W mixRead-mostly by construction; writes paced by token allocator

2 · The AROM invariant and four OS guarantees

Controller responsibilities shrink to three: accept cache-line reads, accept 4KB page writes, and report per-block health. In exchange, the OS guarantees: (1) only the kernel migration path issues 4KB page writes to LtRAM; (2) an application store to an LtRAM page CoW-faults and migrates the page to DRAM before the store applies; (3) pages placed into LtRAM are read-mostly; (4) write traffic is wear-leveled in software via the token allocator.

💡
Why 4KB specifically? It's a multiple of every candidate LtRAM technology's native write/erase granularity (Table 1) and the OS base page size — one alignment removes the read-modify-write path structurally, not just heuristically.

3 · OS mechanisms — placement, migration, wear-leveling

Allocation: LtRAM is a Linux zone with its own free list, at the top of the fallback order — used only when requested or migrated into. Migration to DRAM is the CoW fault path: allocate a DRAM page, copy, retarget the PTE, apply the store, free the LtRAM page, schedule its block for erase when idle. Migration to LtRAM reuses the existing dirty-bit scan: each interval, pages with a clear dirty bit are candidates, subject to the token budget; deferral when tokens run out is treated as benign (a page that survives another interval unwritten is an even safer bet).

4 · Wear-leveling by token allocation

# rate derived once from device specs and deployment target
r = N * E / T   # tokens/sec: N pages, E rated erases/page, T-sec lifetime

on migration_to_ltram(page):
    if tokens_available >= 1:
        consume 1 token; migrate page
    else:
        defer to next scan interval   # banked idle tokens absorb bursts later
🔑
Because the OS is the only writer and the allocator paces those writes, the device meets its rated lifetime by construction — no per-block erase-count bookkeeping needed, only a running token balance. Uniformity across physical sections is explicitly left open (§7).

5 · The Enzian prototype

48-core ARM v8 host + coherent FPGA fabric running Linux 6.8 with page-migration extensions; the FPGA implements the LtRAM controller against a 256MB Micron NOR flash device. NOR isn't a canonical LtRAM technology, but shares the shape: byte-addressable reads, 256B writes, 4KB erases, 10⁵ erase cycles/block — enough to validate the interface end-to-end. The controller adds two optimizations beyond the bare spec: an SRAM buffer acknowledges writes before the slow NOR program completes (so unrelated reads aren't stalled), and erase is exposed to the OS to schedule during read-quiet periods rather than firing opportunistically inside the device.

6 · Projected read latency

Per-access latency = interconnect + controller + media. NOR's prototype controller runs at 200MHz (36 cycles ≈ 180ns); reclocked to a DDR5-class 2.8GHz, the same 36-cycle budget becomes 13ns — the controller estimate used for the three production candidates.

Follow the numbers

Worked examples

Four traces through the paper's real measurements.

① The AIT's coverage gap

  1. 16MB AIT cache, 4KB granularity entries → covers ≈8GB of address space.
  2. On a 128GB DIMM: 8GB / 128GB = 6.25% coverage.
  3. So 93.75% (~94%) of random accesses miss the AIT cache, paying the media-resident AIT lookup.
  4. Measured: AIT-hit reads = 351ns; AIT-miss reads = 427ns → gap = 76ns added by the extra media access alone.
🔑
On a modern multi-hundred-GB DIMM, this ratio only worsens — the AIT cache doesn't scale with capacity, but the address space it must map does.

② Granularity mismatch → write amplification

  1. Cache line = 64B; XPLine = 256B → any misaligned write touches 4× more media than requested.
  2. Sequential (coalescible) writes: ~2.3GB/s. Random 64B writes: ~0.56GB/s.
  3. Drop = (2.3 − 0.56)/2.3 = 75.7% ≈ 75% throughput loss — matching the paper's reported figure.
  4. Random reads pay the same 4× tax: ~169ns sequential vs. ~305–374ns random, i.e. 1.8–2.2× latency.
💡
AROM's fix isn't a smarter buffer — it removes the mismatch structurally by making 4KB (a multiple of every candidate's native unit) the only write granularity that ever reaches the device.

③ Sizing a token bucket

Illustrative sizing (not paper-stated numbers): a 4GB LtRAM region (N = 1,048,576 4KB pages), NOR-class endurance E = 10⁵ erases/page, target lifetime T = 3 years ≈ 9.46×10⁷ s.

  1. r = N·E/T = (1.048×10⁶ × 10⁵) / 9.46×10⁷ ≈ 1,108 tokens/sec.
  2. Each token = one 4KB migration, so the sustained migration-in bandwidth budget ≈ 1,108 × 4KB ≈ 4.3MB/s.
  3. Any burst above that rate must either drain a banked surplus from a quiet period or defer — by design, deferral doesn't hurt correctness, only migration promptness.
📎
The formula (r = NE/T) is the paper's (§5.2.2); the N/E/T values above are a plausible worked example, not figures the paper reports.

④ Projected latency multiples (Fig. 4)

  1. NOR prototype: 40ns interconnect + 180ns controller (200MHz, unreclocked) + 320ns media = 540ns → 540/80 ≈ 6.8× DRAM.
  2. 3D FeFET: 40 + 13 + 200 = 253ns → 253/80 ≈ 3.2× DRAM, or +216% ≈ 220% slower.
  3. 3D V-RRAM: 40 + 13 + 100 = 153ns → 153/80 ≈ 1.9× DRAM.
  4. STT-MRAM: 40 + 13 + 20 = 73ns → 73/80 ≈ 0.91×, i.e. 9% faster than DRAM.
  5. Vs. Optane's 305–374ns band (avg ≈340ns): FeFET saves (340−253)/340 ≈ 26%; STT-MRAM saves (340−73)/340 ≈ 79% — exactly the paper's headline 26–79% range.
🔑
The 26–79%-over-Optane and 9%-faster-to-220%-slower-than-DRAM ranges both refer to the three projected production candidates — the NOR prototype (6.8×) is excluded because 16 of its 36 controller cycles are off-the-shelf wait states a purpose-built controller wouldn't incur.
Test yourself

Practice problems

Try before opening — each answer ends with the misconception it checks.

Problem 1 · easy
Why can't Optane fix its overhead just by making the AIT cache bigger or the wear-leveling smarter?
Show answer
Because the cost isn't a tuning problem — it's structural to hiding LtRAM behind a DRAM-compatible interface. Any hardware that must transparently absorb granularity mismatch, wear-leveling, and address indirection pays a tax on every access, regardless of how well-engineered the structures are. AROM's move is to remove the need for those structures altogether by changing what software promises the device.Misconception: that this is an engineering/tuning problem solvable with better hardware. The paper's claim is it's an interface-design problem.
Problem 2 · medium
A 128GB Optane DIMM's 16MB AIT cache maps entries at 4KB granularity. What fraction of the device does it cover, and what does that imply as DIMM capacity grows?
Show answer
16MB covers ≈8GB, or 8/128 = 6.25% of the device — so ≈94% of random accesses miss and pay the full media-resident AIT lookup (+76ns). Since the AIT cache size is fixed by DIMM design while capacity scales, coverage percentage only shrinks on bigger modules — the AIT overhead gets structurally worse with density, not better.Misconception: that a fixed-size hardware cache scales with capacity. It doesn't — that mismatch is exactly why removing the AIT matters more as densities grow.
Problem 3 · medium
A shared library .so page mapped read-only into 5 processes lives in LtRAM. One process writes to a global (triggering a relocation fix-up). How many physical-page migrations happen?
Show answer
One. AROM's CoW migrates the underlying physical LtRAM page to a fresh DRAM page and retargets page tables — it isn't per-mapping. All 5 processes' page-table entries for that page get updated to point at the new DRAM copy; there's exactly one physical copy operation regardless of how many processes shared the original.Misconception: that CoW migration count scales with the number of sharers. It scales with the number of physical pages written, not the number of virtual mappings onto them.
Problem 4 · hard
Why does the token allocator not need to persist per-block erase counts, when hardware wear-leveling on Optane does?
Show answer
Because the OS is the sole writer to LtRAM (AROM's invariant), the token allocator can pace the aggregate migration rate against the device's rated total endurance budget (r = NE/T) without knowing which specific block absorbed which write. Hardware wear-leveling, by contrast, must track individual block wear because it has no visibility into or control over the software's write pattern — it reacts after the fact. AROM shifts from reactive per-block tracking to proactive rate-limiting of the only write path that exists.Misconception: that any wear-leveling scheme needs per-block bookkeeping. It's only needed when the mechanism doesn't control the write source; controlling the source lets you budget in aggregate instead.
Problem 5 · hard
A 2MB transparent huge page holding mostly read-only weights has one 4KB sub-region that's briefly write-heavy. What are the two options AROM/khugepaged face, and the cost of each?
Show answer
(1) Treat the huge page as the migration unit: keeps the TLB benefit, but a single write anywhere triggers a 2MB CoW copy back to DRAM — inflating exactly the write traffic AROM tries to minimize. (2) Split into 4KB sub-pages: restores fine-grained CoW so only the hot 4KB moves, but costs extra page-table entries and TLB pressure, undoing the huge-page win for the rest of the region. The paper leaves the split/coalesce policy as future work.Misconception: that huge pages are a free win everywhere. Under AROM, huge-page granularity and CoW migration granularity actively conflict.
Problem 6 · medium
Contrast where CXL tiering (TPP/Memtis/HeMem) pays its misplacement cost versus where AROM pays its misplacement cost.
Show answer
CXL tiering misplacement costs a slower read (and write) on every future access to a cold page stuck in the far tier — a steady-state tax, symmetric across reads and writes. AROM misplacement costs a one-time, synchronous CoW write migration the moment a "read-mostly" page is actually written — asymmetric, concentrated, and specifically on the write path.Misconception: that "misplacement cost" means the same thing across all tiering schemes. Where the cost lands (steady-state read tax vs. one-shot write fault) changes what kind of workload hurts each design.
Problem 7 · hard
Why is a sudden phase change (many LtRAM pages simultaneously turning write-heavy) more dangerous for AROM than for classic memory tiering, and what defends against it?
Show answer
In classic tiering, a wrong hotness classification just means slower access to cold pages — no synchronous, unavoidable cost spike. In AROM, every write to a still-LtRAM-resident page triggers an immediate CoW fault + 4KB copy on the critical path; if a large region flips write-heavy at once, this can flood the DRAM free list with migration traffic all at once. The paper's defense is standard back-pressure: admission control on migration and DRAM-occupancy watermarks that throttle new LtRAM placement before DRAM fills.Misconception: that this is a rare edge case ignorable at design time. The paper treats it as a first-class failure mode requiring explicit back-pressure, not a marginal risk.
Problem 8 · easy
Is AROM visible to application code — does a program need to be rewritten to benefit?
Show answer
No. AROM is transparent: a process only sees its normal virtual address space and never learns whether a page is DRAM- or LtRAM-backed. The kernel handles placement and CoW migration automatically. An application may optionally hint read-mostly regions via madvise for faster initial placement, but this is advisory, not required.Misconception: that exploiting a new memory tier always requires application-level API changes. AROM's default path needs none; richer hints are a future optimization, not a prerequisite.
Quick answers

Frequently asked questions

Tap to expand.

Q1How is AROM different from TPP/Memtis/HeMem-style CXL tiering?▾
Those systems manage a slower tier — misplacement costs a slower access, symmetric across reads and writes, and the far tier sits below DRAM in the hierarchy. AROM treats LtRAM as a main-memory replacement for read-mostly data with reads competitive with DRAM by design; the entire misplacement cost is a one-shot CoW write migration, not a steady-state read tax.
Q2How does AROM relate to Pond or Managed Retention Memory?▾
Pond pools CXL memory across VMs/hosts — a different axis (sharing/allocation) than AROM's read/write invariant. Managed Retention Memory (Legtchenko et al.) and Li et al.'s long-term/short-term RAM split argue emerging memory deserves its own category and interface rather than forcing DRAM- or storage-class-memory framing — AROM is a concrete instantiation of that argument, specifically via a read-only-to-apps invariant.
Q3Why copy-on-write specifically, instead of a write-back cache in DRAM?▾
CoW reuses a fault mechanism the kernel already implements for page-sharing, redirected to a new purpose: any write anywhere on an LtRAM page is illegal, so the fault always relocates the whole page. A write-back cache would need its own dirty tracking and eviction logic layered on top — CoW gets the same effect from existing plumbing.
Q4Doesn't removing hardware wear-leveling risk uneven wear?▾
The token allocator bounds total wear to the rated budget by construction, since the OS is the only writer. It does not by itself guarantee uniform wear across physical blocks — pinned read-only pages (code, ML weights) can sit on the same blocks indefinitely while others absorb more churn. The paper flags achieving uniformity as open future work (§7).
Q5Why NOR flash for the prototype instead of real RRAM/MRAM?▾
Availability and cost — NOR is an off-the-shelf part that drops onto the Enzian FPGA board, while MRAM/RRAM would require a research-specific tape-out. NOR shares the target shape (byte-addressable reads, coarse writes, bounded endurance) closely enough to validate the interface end-to-end, even though it isn't a canonical LtRAM candidate itself.
Q6What happens to a page if the workload suddenly becomes write-heavy?▾
Fewer pages qualify as read-mostly under the dirty-bit scan, so migration into LtRAM slows and the system behaves increasingly like a conventional DRAM-only machine — swapping colder pages to storage to free DRAM when it's exhausted. Admission control and DRAM-occupancy watermarks provide back-pressure so a burst doesn't overwhelm the DRAM free list.
Q7How exactly does 4KB write granularity remove Optane's RMW penalty?▾
Optane's RMW happened because sub-256B (XPLine) writes forced a read-modify-write of the whole line. AROM's controller only ever accepts 4KB writes — a multiple of every candidate technology's native write/erase unit — so every write already spans a full underlying block; there's nothing to read-modify.
Q8Are the latency numbers from real workload benchmarks?▾
No — Figure 4 is a per-access latency projection (interconnect + controller + media) in isolation, not an application-level benchmark. The paper notes cache, prefetching, and memory-level parallelism could let real workloads on read-mostly data approach DRAM more closely than the raw per-access numbers suggest; full benchmark evaluation is future work.
Q9Does an application need to change to use LtRAM?▾
No — placement is transparent. An optional madvise-style hint can speed up initial classification, and the paper flags a richer, AIFM-style hint interface (letting e.g. database engines share access-pattern knowledge) as a possible future extension, not a requirement.
Q10What's left unresolved by the paper itself?▾
Three things, explicitly (§7): wear-leveling for pinned/unmovable read-only pages, the huge-page vs. 4KB-CoW granularity conflict, and how much benefit a richer application hint interface would add beyond the transparent default.

The closest prior pattern: OS manages a slower tier with cost deferred to access time. AROM extends this to a HW/SW co-design where the deferred cost is a write-only CoW migration.

Managed-Retention Memory hard

Legtchenko et al. · HotOS 2025

Argues emerging memory needs its own category/interface rather than SCM- or DRAM-replacement framing — the conceptual predecessor AROM instantiates concretely.

Long-Term and Short-Term RAM hard

Li et al. · DIMES 2025

Introduces the LtRAM/short-term RAM split this paper builds directly on, by the same broader research group.
