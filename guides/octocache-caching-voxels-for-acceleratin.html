ASPLOS 2025 · A Field Guide

Answering most queries from a fast cache, not routing everyone through the slow tree

OctoMap's octree can eat up to 72% of a UAV's onboard compute. OctoCache slips a small hash-table cache in front of it, so duplicate voxel writes hit fast and most queries skip the root-to-leaf tree walk — though a cache miss still means a trip to the tree.

📄 "OctoCache" · Chen, Li, Wan, Hsiao, Yu, Reddi, Liu — ASPLOS'25 🎓 Some caching/OS background assumed — the primers cover it ⏱ ~30 min read
🧊

Serve most queries straight from a CACHE so they skip the tree — then feed the evicted voxels (and cache misses) back in MORTON-CODE order so even the slow octree update moves as fast as it can.

Nine ideas the paper assumes you know

Each card clears up one concept OctoCache builds on. Collapsed by default — tap any to open. You already know several of these from the systems side; they're here mostly to fix vocabulary (voxel, octree, Morton code) rather than teach caching from scratch.

the cache (fast path) Morton Code ordering OctoCache system / threads the octree (slow baseline)
1Voxels and occupancy maps▾

A voxel is a 3D cube — the volumetric equivalent of a pixel. An occupancy map divides all of space into a grid of voxels and, for each one, tracks a probability that it's occupied by an obstacle (stored as a log-odds value, so updates are just additions/subtractions instead of multiplying probabilities).

Now you're ready: OctoCache is a caching layer for exactly one operation — reading and writing a voxel's occupancy value, over and over, as a robot scans its surroundings.
2Octrees — a tree that mirrors 3D space▾

An octree recursively splits a cube of space into 8 smaller cubes, each split again, down to a target resolution. Every node stores one voxel's occupancy value; a node's value is the max of its 8 children, so identical children can be pruned to save memory. Finding a voxel means walking from the root down to its leaf — up to 32 memory accesses for a 16-level tree.

Now you're ready: that root-to-leaf walk, repeated for every incoming voxel, is the entire performance problem this paper solves. The octree is memory-efficient but access-expensive — sound familiar from any tiered-storage structure that trades access latency for compactness.
3Ray tracing (in this context)▾

When a LiDAR/depth sensor returns a point cloud, the mapping system draws a straight line ("ray") from the sensor to each point. Every voxel the ray passes through is marked free; the voxel at the point itself is marked occupied. This is the step before anything touches the octree or cache.

Now you're ready: because many rays converge near the sensor and many points fall in the same voxel, ray tracing itself manufactures a flood of duplicate voxel writes — 2.78× to 31.32× duplication in one batch. That flood is what the cache is built to absorb.
4Hash tables, buckets, and collisions▾

A hash table maps a key to a fixed-size array slot ("bucket") via a hash function. Different keys can land in the same bucket (a collision); most implementations let a bucket hold several entries (here, a small vector of "cells") rather than just one.

Now you're ready: OctoCache's cache is a hash table of voxels — w buckets, each capped at τ cells. Get the bucket count and cap wrong and you either evict too eagerly or search too long per insert.
5Morton Code (Z-order curve)▾

Morton Code turns a multi-dimensional coordinate (x, y, z) into a single integer by interleaving the bits of each axis. Two points close together in 3D space usually get Morton codes that are close together as integers — so sorting by Morton code approximately sorts by spatial (and thus octree-ancestor) locality.

Now you're ready: OctoCache uses Morton Code twice — once to pick a voxel's bucket, and once (implicitly, via sequential eviction from Morton-hashed buckets) to decide the order in which evicted voxels get written to the octree.
6Data locality and tree traversal cost▾

Visiting two tree nodes that share a close common ancestor is cheaper (more cache-hit-friendly, fewer redundant pointer chases) than visiting two unrelated nodes, because the shared path segment is likely still warm from the previous visit. This is the same intuition behind sequential vs. random access to any backing store.

Now you're ready: the paper formalizes "good ordering" as minimizing total tree-distance between consecutively inserted leaves — and proves Morton order is optimal for that.
7Producer–consumer queues and mutexes▾

A single-producer/single-consumer queue lets one thread push work items and another thread pop them, safely, without a full lock on every operation. A mutex is a lock that lets only one thread touch a shared resource at a time — necessary whenever two threads might read and write the same memory.

Now you're ready: OctoCache's parallel design uses exactly this pair — a lock-free queue to hand evicted voxels from thread 1 to thread 2, and a mutex to keep octree reads and octree writes from racing.
8The perception → planning → control pipeline▾

Autonomous robots run a loop: perception (turn sensor data into a map update), planning (query the map to find a safe path), control (drive the motors along that path). Planning cannot safely proceed until the current perception update has landed in the map — otherwise it might plan through an obstacle nobody told it about yet.

Now you're ready: "map update latency" isn't an abstract metric — it directly gates how fast planning can run, which directly gates how fast (and how safely) the robot can fly.
9Write-back vs. write-through consistency▾

A write-through cache pushes every write straight to the backing store immediately. A write-back cache accumulates writes and flushes them later, in a batch — faster, but it must guarantee that any read (even one that misses the cache) still sees the latest accumulated value.

Now you're ready: OctoCache's cache is write-back: it holds the running total occupancy value like a mini-octree, and only flushes it to the real octree on eviction — which is exactly why query results stay correct on both a cache hit and a cache miss.
The whole story in one place

OctoCache in a nutshell

The bottleneck, the fix, and why it generalizes past robotics.

OctoMap represents 3D occupancy with an octree: memory-efficient, but every voxel update or query demands a root-to-leaf round trip — up to 32 memory accesses per voxel. Profiling shows this octree update dominates runtime, up to 96% at high resolution and 99% once ray tracing is hardware-accelerated. Meanwhile the incoming voxel stream is massively redundant: 2.78×–31.32× duplication inside one sensor scan, and 40–90%+ overlap between consecutive scans as a UAV flies its trajectory.

OctoCache exploits that redundancy directly: a small flattened hash-table cache sits in front of the octree and absorbs most of the repeated writes — hit rates that can exceed 93% on favorable datasets like New College, at well under 1% of the octree's memory footprint. On a hit, the cache updates an accumulated occupancy value in place — no tree walk at all. Queries are served from the cache first, falling back to the octree only on a miss, so query results are always consistent with the "true" accumulated value, whether or not the answer has reached the octree yet.

Two more moves squeeze out the rest. First, evictions are indexed and drained by Morton Code, which the paper proves is an optimal ordering for octree-insertion locality — up to 1.34×–1.38× faster inserts than OctoMap's native order, and up to 3.32× faster than a random order. Second, the octree update is moved to a second CPU thread, running concurrently with ray tracing and cache eviction, guarded by a single mutex so octree reads and writes never race.

The payoff: OctoCache speeds up 3D map construction by 45.63%–88.01% over OctoMap, and in closed-loop UAV navigation delivers up to 3.02× end-to-end speedup and 28% shorter mission time — for a cache that costs roughly 14MB and one extra CPU core.

🍯 Key takeaways

  • The octree is memory-efficient but access-expensive — it dominates OctoMap's runtime (up to 96%, or 99% once ray tracing is fast).
  • Voxel updates are highly redundant, both within one scan (2.78×–31.32×) and across consecutive scans (often >80% overlap).
  • A small hash-table cache in front of the octree turns most of that redundancy into cheap in-place updates instead of tree walks.
  • The cache stores an accumulated occupancy value (a mini-octree), so cache hits and cache misses both return consistent results.
  • Morton Code ordering of evictions is a provably-optimal way to feed voxels back into the octree with maximum locality.
  • Moving octree updates to a second thread overlaps the slow tree write with the fast cache path, guarded by one mutex.
  • Result: 45.63%–88.01% faster map construction; up to 3.02× UAV speedup; 28% shorter missions; ~14MB cache, one extra core.
💡
For the tiering reader: this is structurally close to a DRAM write-buffer in front of a CXL/NVM-backed structure — absorb hot, duplicate writes cheaply; batch and reorder the cold remainder for sequential-friendly access on the slow tier; move that flush off the critical path onto another core. The "accumulated value, flushed on eviction" trick is exactly write-back semantics with a correctness guarantee on miss.
Six everyday pictures

How to think about OctoCache

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Absorb before you traverse

A doorman with a clipboard

Instead of walking every visitor all the way up to the penthouse to log them, a doorman keeps a clipboard by the entrance. Repeat visitors just get a checkmark added — no elevator ride. Only when the clipboard fills up does someone walk the accumulated tally upstairs, once, for everyone at once. The cache is the clipboard; the octree is the long elevator ride.

Where it breaks: a doorman only checks people in once; OctoCache's clipboard also has to answer "is this person currently inside?" correctly at any moment — which is why it stores a running total, not just a tally mark.
Query consistency · Accumulated value

A running bar tab, not a receipt pile

A bartender who keeps a running tab (current total owed) can answer "how much do I owe?" instantly at any time. One who just piles up individual receipts has to add them all up first. OctoCache's cache keeps the running accumulated occupancy, like the tab — so a query hitting the cache gets the right answer immediately, no summation, no tree walk.

Where it breaks: a bar tab is settled once at checkout; OctoCache's "tab" is settled (flushed to the octree) repeatedly, every time that voxel's bucket overflows — it's a rolling settlement, not a one-time one.
Reordering evictions · Morton Code

Running errands by neighborhood, not by list order

If your to-do list says "bakery, dry cleaner across town, bakery's neighbor, then back near the bakery," you'll waste half your trip backtracking. A smarter route visits everything near the bakery together, then everything near the dry cleaner. Morton Code does this for voxel evictions: it groups voxels that share tree ancestors so the octree walk barely has to backtrack.

Where it breaks: a real errand-run can adapt live to traffic; Morton order is fixed in advance from coordinates alone — it's provably good on average, not adaptive to which ancestor nodes happen to be warm right now.
Parallelization · Two threads, one lock

A relay handoff, not a shared pen

Two relay runners never touch the baton at the same instant — there's one clean handoff moment. OctoCache's two threads work the same way: thread 1 hands off evicted voxels through a queue, and a single mutex ensures thread 2's octree write and any octree read never happen at the exact same moment. Everything else — ray tracing, cache eviction — runs untouched by that lock.

Where it breaks: a relay handoff is instantaneous; the mutex handoff can make thread 1 wait if thread 2's octree write is still running when the next batch arrives — the paper calls this the "gap," and it shrinks as the cache absorbs more writes.
Sensor overlap · Why the cache stays full

Retracing your own footprints in snow

Walk a familiar loop through fresh snow and much of your new path overlaps yesterday's tracks. A UAV scanning as it flies does the same thing — consecutive scans see 40–90%+ of the same voxels again. That overlap is exactly why a cache sized for just a few batches keeps producing a high hit rate, batch after batch, without needing to grow.

Where it breaks: footprints in snow never change; voxel occupancy can — a UAV revisiting a spot after an obstacle moved needs the update to actually land, which the cache guarantees (it never silently drops writes), it just delays when they reach the octree.
Sizing the cache · The τ knob

A mail slot, not a mailroom

A mail slot too small forces you to check it constantly (frequent, wasteful evictions); a mailroom so big you dig through piles to find anything (slow per-insert search). There's a sweet spot: big enough to hold a batch's worth of repeats, small enough to search quickly. OctoCache's τ (max cells per bucket) is exactly this knob, and the paper finds τ=2–4 is that sweet spot for its workloads.

Where it breaks: a mail slot's "right size" doesn't depend on how mail arrives; τ's optimum does — it's tuned to this workload's collision rate and duplication pattern, and would need re-tuning for a very different sensor or scene.
The full explanation

How it actually works

Section by section, following the paper's own build-up: strawman cache → Morton ordering → parallel design.

1 · The bottleneck — why the octree is slow

Every voxel update or query in OctoMap requires a root-to-leaf traversal: locate the leaf, update it, then walk back up updating every ancestor's max-of-children value. For a 16-level tree this is up to 32 memory accesses per voxel. Profiling on three public datasets shows octree update is 86%+ of total runtime, rising to 93–96% at higher resolution, and 99% once ray tracing itself is hardware-accelerated (so the octree becomes the only bottleneck left).

🌱
Concretely: the same tree structure that makes OctoMap memory-efficient for sparse 3D space is precisely what makes it access-expensive — there's no free lunch inside the tree itself. The fix has to come from outside it.

2 · Strawman cache — insertion, query, eviction

OctoCache's cache is an array of w buckets, each holding a small vector of cells; each cell stores a voxel's coordinates plus its accumulated occupancy value. On insertion, hash the incoming voxel to a bucket, scan its cells: a hit just updates the accumulated value in place (cheap); a miss pulls the current value from the octree (or initializes it fresh) and writes a new cell. On eviction, any bucket over its cap τ drops its oldest records, and those records — with their final accumulated values — get written into the octree as a batch.

3 · Morton Code ordering — proving the eviction order matters

Given the same set of voxels to insert, different orderings produce very different total insertion time — because consecutive insertions that share tree ancestors reuse warm traversal paths, while consecutive insertions to unrelated branches waste the walk. The paper defines a locality cost F(S) = Σ D(aᵢ, aᵢ₊₁) — the sum of tree-distances between consecutive leaves in ordering S — and proves that ordering leaves by their Morton Code minimizes F: nodes with small Morton-code differences always share more ancestors, and the proof (via a chain of lemmas on common ancestors) shows Morton order is one of the sequences that keeps every subtree's leaves contiguous — the best you can do.

Measured on a Jetson TX2 across three datasets, Morton order beats OctoMap's native (ray-tracing) order by 1.34×–1.38×, and beats a random shuffle by 1.97×–3.32×.

4 · Parallel OctoCache — moving the tree off the critical path

Even with a high hit rate, the octree update remains the single largest remaining chunk of work. OctoCache moves it to a second thread, running concurrently with ray tracing and cache eviction on thread 1. A single mutex partitions operations: cache insertion/query need to read the octree (on a cache miss); octree update writes it. Ray tracing and cache eviction never touch the octree at all, so they run freely alongside it.

// thread 1 (critical path)
ray_trace(batch);
cache.insert(voxels);          // serves query immediately after
serve(query);
evicted = cache.evict();       enqueue(evicted, shared_buffer);  // Morton order preserved

// thread 2 (off critical path)
while (buffer.dequeue(v)):
    mutex.lock();
    octree.update(v);          // writes; reads from thread 1 must wait
    mutex.unlock();
💡
Why this doesn't fully double throughput: thread 1's next batch still must wait if the octree update from the previous batch hasn't finished (a query might need to read the octree on a miss). The achievable gain is bounded by min(T_raytracing + T_eviction, T_octree_update) — classic overlap-limited speedup, not free parallelism. A cache with a higher hit rate shrinks T_octree_update, which shrinks this wait.
Follow the numbers, step by step

Worked examples

Four traces using the paper's real numbers: computing a Morton bucket index, sizing the cache, connecting duplication to hit rate, and reading the UAV payoff.

① Computing a voxel's Morton-Code bucket

The paper's own example: locate voxel v = (1, 5, 3) in the cache.

  1. Binary-encode each axis: vₓ=1 → 001₂, v_y=5 → 101₂, v_z=3 → 011₂.
  2. Interleave bit-planes from highest to lowest, in x, y, z order at each level, concatenating across all three levels.
  3. Convert the resulting bit string to decimal: the paper reports M(v) = 167.
  4. Locate the bucket: insert v into bucket M(v) mod w — bucket 167 mod w for whatever bucket count w is configured.
🍯
Insight: because Morton Code tends to preserve spatial locality, voxels that are physically close usually end up hashed to numerically close buckets — so evicting buckets in increasing order also drains voxels in roughly spatial (and therefore tree-ancestor) order.

② Sizing the cache to a memory budget

The UAV evaluation uses w = 512K buckets and τ = 4 cells/bucket, each cell 7 bytes (3 bytes coordinates + 4 bytes occupancy). What's the total cache footprint?

  1. Buckets: w = 512K = 524,288.
  2. Max cells after eviction: τ = 4 per bucket.
  3. Bytes per cell: 7 (3B coords + 4B float occupancy).
  4. Total: 524,288 × 4 × 7 = 14,680,064 bytes ≈ 14.0 MB — matching the paper's stated cache size exactly.
💡
General formula: M = 7 × w × τ. Given a memory budget, this is a single division to pick w once you've settled on τ — no search needed.

③ Why duplication becomes a high hit rate

Two sources of redundancy feed the cache: intra-batch duplication (2.78×–31.32×, from overlapping sensor rays) and inter-batch overlap (often >80% of a batch already seen in the last 3 updates).

  1. Intra-batch: if a batch has 31.32× duplication, roughly 97% of raw voxel writes in that single batch are repeats of others already in the batch — the cache absorbs these on the very first pass.
  2. Inter-batch: with >80% overlap between consecutive batches, most of what's "new" in this batch was already cached from the last one or two batches — another near-certain hit.
  3. Combined effect, New College dataset: the paper reports a cache sized at just 0.23% of the octree's footprint (out of a 0.99GB octree) still achieves >93% hit rate. (Other datasets like Freiburg report lower hit rates for comparable cache sizes — e.g. ~91.8% at 14MB — so this figure is dataset-dependent, not a universal number.)
  4. What that buys: on New College, only ~7% of voxel writes ever reach the octree at all — the other 93%+ are settled by a bucket lookup and a float addition.
🍯
Insight: the hit rate isn't a tuning miracle — it's a direct consequence of how physically redundant LiDAR/depth sensing is. The cache is exploiting a property of the workload, not fighting against it, though the exact hit rate varies by dataset.

④ Reading the UAV runtime and mission-time payoff

MavBench profiling shows OctoMap can consume up to 72% of end-to-end UAV compute. What happens when OctoCache removes most of that?

  1. End-to-end runtime: the OctoCache-based system is 1.78×–3.02× faster than OctoMap across the four MavBench scenarios (Openland, Farm, Room, Factory), with the Room scenario (hardest, indoor) hitting the top end.
  2. Why Room benefits most: Room uses the finest resolution (0.15m) and shortest range — exactly the high-resolution regime where octree update dominates most (up to 92–96% of OctoMap's own runtime).
  3. Flight speed → mission time: a faster perception stage raises the UAV's max safe flight velocity (per the roofline-style model in [30]), which the paper translates into 13%–28% shorter mission completion time on the AscTec Pelican.
  4. The DJI Spark exception: in Openland and Factory, the lighter, lower-power DJI Spark sees no mission-time improvement — its bottleneck there is rotor pull power, not compute, so a faster mapping system has nothing left to unlock.
💡
This is the same "fix the actual bottleneck" logic as the octree-vs-cache story, one level up the stack: speeding up compute only helps mission time when compute — not the airframe — is what's actually gating the UAV.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
A colleague says "a 14MB cache in front of a gigabyte-scale octree can't possibly matter — it's less than 2% of the data." Where's the flaw?
Show answer
The cache isn't sized to hold the whole map — it's sized to hold the currently repeating voxels from the last few sensor batches, which is a tiny, highly-reused working set. Because 40–90%+ of each new batch overlaps recent ones, a small cache absorbing that overlap prevents most octree accesses entirely, even though it stores a negligible fraction of total map data.Misconception: that cache effectiveness scales with the fraction of total data it holds. It scales with the fraction of accesses it can serve — and access patterns here are extremely skewed toward recent, repeated voxels.
Problem 2 · medium
With w=512K buckets and τ=4, what's the total cache size if τ is doubled to 8 (keeping w fixed)? Is doubling τ generally a good idea?
Show answer
Using M = 7×w×τ: 7 × 524,288 × 8 = 29,360,128 bytes ≈ 29.3 MB — exactly double, as expected. But the paper finds this is not a good idea past τ≈4: hit rate has already plateaued (all the real duplication is captured), while doubling τ doubles the number of cells to scan on every insertion, since each lookup must check every cell in the target bucket for a match.Misconception: that a bigger cache (bigger τ) is always at least as good. Past the point where hit rate saturates, a bigger bucket only adds per-insertion search cost with no compensating benefit.
Problem 3 · medium
Why can't OctoCache just remove the mutex and let both threads touch the octree freely, now that most writes are absorbed by the cache?
Show answer
Even with a high hit rate, cache misses still require reading the octree (thread 1), and evicted voxels still require writing it (thread 2). If those overlap in time on the same node, you get a data race — reading a node mid-update, or two writes stepping on each other. The mutex cost is paid only when both operations actually happen concurrently, which becomes rare (not impossible) as hit rate rises — but "rare" isn't "safe."Misconception: that a high hit rate makes synchronization unnecessary. It reduces how often the lock is contended, not whether it's needed for correctness on the misses/evictions that remain.
Problem 4 · hard
The paper shows random voxel order is 1.97×–3.32× slower into the octree than Morton order. Sketch, in your own words, why a sorted-by-X-coordinate order (sort purely by the x-axis) is worse than Morton order even though it's also "sorted."
Show answer
Sorting purely by x-coordinate groups voxels that agree on x but ignores y and z entirely — two voxels with the same x but wildly different y/z can be adjacent in the sequence, yet sit in completely different octree subtrees (since octree splits divide all three axes together at each level). Morton Code interleaves bits from all three axes, so numeric closeness in Morton Code implies closeness in all three dimensions simultaneously — which is what determines shared tree ancestors. X-only sorting captures locality in one axis; Morton captures it in all three at once.Misconception: that any "sorted" order captures spatial locality. Only orderings that respect all the dimensions the tree actually splits on do — single-axis sorts are locality in one dimension, not three.
Problem 5 · medium
A cache miss retrieves the voxel's current value from the octree, applies the update, and writes a new cell — it does not immediately write that update back to the octree. Why is this safe for query consistency?
Show answer
Because the cache always holds the running accumulated occupancy value (not just "the last delta"), a query hitting the cache after a miss-then-update sees the fully correct total — the octree's stale copy is simply superseded in the cache until eviction flushes the newer value back. The octree is only ever consulted directly when the cache itself has no record — at which point the octree's value is, by construction, still current (nothing newer exists yet).Misconception: that "not writing straight to the octree" risks returning stale data. It only would if the cache stored deltas instead of accumulated totals — the accumulated-value design is precisely what closes that gap.
Problem 6 · hard
Parallel OctoCache gives "an extra 0.16×–0.33× gain over serial" at resolutions 0.1–0.3m, but much less at very coarse resolutions. Using the min(ray_tracing+eviction, octree_update) bound, explain why.
Show answer
At coarse resolution, the octree is shallow and updates are already cheap — T_octree_update is small, possibly smaller than T_raytracing+T_eviction. The bound min(a, b) is then capped by the raytracing+eviction side, which parallelization doesn't touch, so there's little to overlap and little to gain. At fine resolution, T_octree_update grows large (deeper tree, more accesses) and becomes the dominant term — exactly the regime where moving it to a second thread, off the critical path, pays off most.Misconception: that parallelizing a component always helps proportionally to how slow that component is in isolation. It only helps to the extent that component is the *bottleneck* relative to what continues running alongside it.
Problem 7 · medium
Why does the paper report OctoCache-RT's speedup over OctoMap-RT (up to 37× at 0.01m resolution) as so much larger than plain OctoCache's speedup over OctoMap (up to 3.02× end-to-end)?
Show answer
OctoMap-RT already eliminates ray-tracing-side duplicates, so its octree update becomes an even larger share of total runtime (up to 99% in some accelerated settings) — there's less "other work" left to dilute the improvement. OctoCache-RT then removes almost all of what's left (the octree bottleneck itself), so the *relative* end-to-end speedup looks enormous, especially at the finest resolution where the untouched OctoMap-RT octree update was slowest to begin with.Misconception: that a bigger reported multiplier means a "better" optimization in absolute terms. It partly reflects how dominant the fixed bottleneck already was in the baseline being compared against — always check what fraction of runtime that baseline's bottleneck represented.
Problem 8 · easy
The DJI Spark sees no mission-time improvement from OctoCache in the Openland and Factory scenarios. Does this mean OctoCache "doesn't work" for lightweight UAVs?
Show answer
No — OctoCache still speeds up the mapping computation itself on the DJI Spark exactly as it does elsewhere. What changes is whether that speedup translates into a faster mission: in those two scenarios the Spark's low rotor pull power, not compute, is the binding constraint on flight speed, so a faster mapping system has no bottleneck left to relieve on the mission-time metric specifically. The Room and (implicitly) other constrained scenarios do show gains.Misconception: that "no end-to-end metric improvement" means the optimization failed. It can mean the optimization succeeded at its target (compute) but a different, unrelated bottleneck (rotor power) now dominates the metric you're watching.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1Is OctoCache a new data structure replacing the octree?▾
No — the octree stays exactly as-is underneath. OctoCache is a caching layer in front of it that absorbs duplicate writes and reorders what actually reaches the tree. This is deliberate: it preserves OctoMap's existing query API and memory-efficiency properties, unlike prior work that replaced the octree with a different (often larger) structure.
Q2How does the cache guarantee the same query results as vanilla OctoMap?▾
It stores the accumulated occupancy value (like a mini-octree) rather than just the most recent delta, and every eviction overwrites the octree with that accumulated value before dropping it from the cache. So a query is always answered with the latest true value, whether served by the cache (hit) or the octree (miss) — the two are kept consistent by construction, not by chance.
Q3Why cache voxels instead of just making the octree traversal itself faster?▾
The traversal cost is fundamental to the octree's design — it's exactly what makes it memory-efficient (only 32 accesses worst-case for 65,536³ resolution). Rather than fight that trade-off, OctoCache reduces how often the traversal has to happen at all, by intercepting the enormous fraction of writes that are duplicates before they ever reach the tree.
Q4What exactly does Morton Code buy that a plain hash function wouldn't?▾
A plain hash function scatters voxels randomly across buckets — fine for lookup speed, but it destroys any relationship between a voxel's spatial position and where it lands. Morton Code tends to preserve that relationship: nearby voxels usually get nearby codes (though not perfectly — points straddling a Z-curve discontinuity can land far apart despite being spatially close), so bucket assignment and eviction order end up mostly spatially coherent, which is what speeds up the subsequent octree insert.
Q5Is the Morton-order proof specific to octrees, or does it generalize?▾
The paper proves this specifically for octree leaf ordering — a proof sketch for uniform tree depth, extended in the supplementary material to non-uniform depth, but both still within octrees. The underlying intuition (keeping every subtree's leaves contiguous minimizes total consecutive-pair tree-distance) plausibly carries over to other trees built by partitioning space along all dimensions at once, like quadtrees — but the paper doesn't prove this for quadtrees or k-d trees, so treat that broader generalization as our speculation, not an established result.
Q6Why only one extra CPU core, and not more?▾
The paper specifically targets resource-constrained edge devices (e.g. Jetson TX2's 6 cores), where "requires a dedicated hardware accelerator" or "needs many extra cores" solutions aren't deployable. Splitting into exactly two threads — one for the fast path, one for the octree — captures the main overlap opportunity (ray tracing + eviction vs. tree update) without demanding hardware most robots don't have.
Q7Does OctoCache help ray tracing, or only the octree update?▾
Ray tracing itself is unmodified. OctoCache's gains come from absorbing writes in the cache (so most voxels skip the octree read/write entirely), reordering the evictions and cache misses that do reach the octree so inserts have better locality, and overlapping the octree update with ray tracing and eviction via the second thread — which also cuts the synchronization/critical-path overhead of the pipeline, not just the octree-update kernel in isolation. The paper evaluates against both OctoMap (unmodified ray tracing) and OctoMap-RT (a ray-tracing method that already removes intra-batch duplicates), showing OctoCache still helps substantially on top of OctoMap-RT because the octree bottleneck is largely independent of how ray tracing produces its voxels.
Q8What happens if the cache is undersized relative to the workload?▾
Buckets overflow more often, forcing more frequent evictions before duplicates within the current or next batch get a chance to hit — hit rate drops, and more voxels take the slow octree path. The paper's Fig. 23 shows hit rate rising steeply with cache size before plateauing — undersizing costs you real hit rate, not just a theoretical inefficiency.
Q9Why does the parallel design sometimes barely beat the serial one?▾
The achievable gain from moving octree updates to a second thread is bounded by min(T_raytracing + T_eviction, T_octree_update). If the octree update was already fast relative to the rest of the pipeline (e.g. coarse resolution, small batches), there's little slow work to hide behind the fast work, so parallelizing adds synchronization overhead for a small win.
Q10What did the authors leave for future work?▾
The paper is scoped to single-robot, CPU-based OctoMap acceleration on edge devices like the Jetson TX2, and doesn't itself lay out a future-work agenda beyond that scope. Given the related-work landscape in Table 1, plausible next steps we'd speculate about — GPU-resident caching, multi-robot shared maps, dynamic (moving-obstacle) re-caching beyond what write-back consistency already provides, or hardware co-design (e.g. pairing OctoCache with an octree accelerator like OMU) — are our extrapolations, not claims the authors make.

Glossary & further reading

Core terms
OctoCacheThe paper's caching layer in front of OctoMap's octree: absorbs duplicate voxel writes, reorders evictions by Morton Code, and overlaps octree updates with ray tracing on a second thread.
VoxelA 3D cube representing one unit of occupancy in the map, storing an accumulated log-odds occupancy value.
OctreeA tree that recursively splits a cubic volume into 8 children, storing occupancy at leaves and the max-of-children at every ancestor. Root-to-leaf traversal is required for both reads and writes.
Morton Code (Z-order)A function mapping 3D integer coordinates to a single integer by interleaving axis bits; numeric closeness approximates spatial (and tree-ancestor) closeness. Proven optimal for minimizing consecutive-insertion tree-distance.
Cache bucket / τThe cache is w hash buckets, each capped at τ cells after eviction. τ trades off hit rate (bigger helps, up to a point) against per-insertion search cost (bigger always hurts).
Accumulated occupancy valueThe running total occupancy the cache keeps per voxel (a "mini-octree"), which is what lets both cache hits and cache misses return consistent query results.
Parallel OctoCacheThe 2-thread design: octree updates run on a second thread, overlapping with ray tracing and cache eviction on the first, synchronized by one mutex over octree reads/writes.
Duplication rate / overlap ratioIntra-batch duplication (2.78×–31.32×, from ray-tracing geometry) and inter-batch overlap (often >80%, from overlapping sensor scans) — the two sources of redundancy the cache exploits.
Supporting terms
Log-odds occupancyOctoMap's representation of P(occupied) as a bounded additive value, so repeated sensor evidence just adds/subtracts instead of multiplying probabilities.
Ray tracingConverting a point cloud into a batch of free/occupied voxels by tracing a line from the sensor to each detected point.
MavBenchThe closed-loop UAV simulation benchmark (built on the Unreal engine) used to evaluate end-to-end navigation performance.
Jetson TX2The edge compute platform (quad ARM CPU, embedded GPU, 8GB RAM) used for all on-device evaluation, fixed at 15W.
Weighted speedup analogue — end-to-end runtimeThe paper's primary performance metric for 3D construction: total wall-clock time to build the map from a full dataset.
Safe flight velocityThe maximum speed at which a UAV can still react to obstacles in time, computed from sensing range, sensor FPS, and system compute latency (via the roofline-style model of Krishnan et al.).
Mission completion timeNavigation path distance divided by safe flight velocity — the paper's end-user-facing metric, since it also proxies energy use (rotors dominate UAV power draw).
OctoMap-RTA ray-tracing variant that removes intra-batch voxel duplicates before they reach the octree; used as a stronger baseline to isolate the octree's remaining bottleneck.
Shared buffer (SPSC queue)The lock-free single-producer/single-consumer queue moving evicted voxels from thread 1 (producer) to thread 2 (consumer, octree writer).
