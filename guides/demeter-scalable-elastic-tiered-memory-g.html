Stop asking the hypervisor to guess what the guest already knows

A VM sits between two things that both know its memory access pattern intimately — the guest kernel, and the hardware sampler watching it. The hypervisor, stuck outside both, has been doing tiered-memory management the hard way. Demeter just hands the job to the guest.

📄 "Demeter" · Hu, Hu, Wu, Yang · SOSP '25 🎓 Some virtualization/mm basics assumed — primers cover them ⏱ ~30 min read
🌾

Quick glossary, then ten minutes of primers

The acronyms first, since the paper leans on them heavily; then the concepts they sit on, collapsed — open whichever is unfamiliar.

1Tiered memory: FMEM + SMEM▾

Server DRAM capacity per core has been shrinking for a decade, so clouds pair a small fast tier (DRAM) with a large slow tier — PMEM or CXL.mem — that costs roughly half as much per GB. The system's job is to keep hot pages in FMEM and cold ones in SMEM.

Now you're ready: the whole paper is about who decides which pages go where, inside a virtualized cloud.
22D address translation in a VM▾

A guest thinks in guest virtual addresses (gVA). Its own page tables (GPT) turn that into a guest physical address (gPA) — an illusion of physical memory the hypervisor maintains. A second hardware structure, EPT (Intel) or NPT (AMD), turns gPA into the real host physical address (hPA). Every memory access, in the worst case, walks both tables: up to 25 memory accesses for one translation on modern 5-level page tables.

Now you're ready: anything that has to modify either table (GPT or EPT) pays this translation tax — which is exactly what access tracking does.
3TLBs and why flushing them hurts▾

The TLB caches translation results so most accesses skip the expensive page-table walk. But whenever a page table entry changes, cached TLB entries referencing it become stale and must be flushed — single-address flushes remove one mapping; full flushes (invept) wipe every mapping for a guest, forcing every subsequent access to re-walk both dimensions.

Now you're ready: §2.3.1's entire argument is that hypervisor-based tracking is forced into expensive full flushes, while guest-side tracking can use cheap single-address ones.
4PTE.A/D bits — the traditional access signal▾

Hardware automatically sets an Access bit (and Dirty bit, on writes) in a page table entry whenever it's used. A scanner periodically reads these bits to infer "was this page touched recently?", then clears them to detect future accesses — and clearing requires a TLB flush so the hardware doesn't serve a stale cached translation instead of re-setting the bit.

Now you're ready: that clear-then-flush cycle, repeated every scan round across gigabytes of VM memory, is the mechanism Demeter tries to avoid entirely.
5PEBS — hardware sampling instead of bit-scanning▾

Processor Event-Based Sampling has the CPU itself record a sample (with the accessed address) every N memory events, writing it to a buffer in memory — no page-table bit clearing, no TLB flush. Kernel-based systems (HeMem, Memtis) already showed PEBS beats PTE.A/D scanning on bare metal. It was long assumed unusable for guest VMs.

Now you're ready: Demeter's second core insight is that this assumption was wrong — modern hardware (PEBS v5) makes guest PEBS safe and fast. See §2.3.2 and the analogies tab.
6Memory ballooning & overcommitment▾

Clouds rent out more memory than physically exists, betting most VMs won't use their full allocation simultaneously. A balloon driver inside the guest lets the host reclaim (inflate) or return (deflate) memory pages, giving elasticity without hard-resizing the VM.

Now you're ready: conventional balloons have no idea which tier a page belongs to — that's the gap Demeter's double balloon closes.
7NUMA nodes as a tier-exposure trick▾

Multi-socket machines already expose "NUMA nodes" to the OS — regions of memory with different latency from each CPU. Guest kernels already know how to handle multiple NUMA nodes with different characteristics, so exposing FMEM and SMEM as two virtual NUMA nodes needs no new OS abstraction at all.

Now you're ready: this is how Demeter tells the guest kernel "here are your two tiers" using nothing but standard ACPI tables.
8Segment-tree-style range classification▾

Rather than tracking hotness per 4 KiB page (millions of entries), you can track hotness per contiguous range of virtual address space, splitting a range in two only when one half looks hotter than its neighbors, and merging ranges back together once they've gone cold.

Now you're ready: this range tree, operating in guest virtual address space, is the core data structure behind Demeter's hotness classifier (§3.2.1).
9Three flavors of TMM: kernel, hypervisor, guest-delegated▾

Kernel-based systems (TPP, Memtis, HeMem) run on bare metal with full access to hardware and the true virtual address space. Hypervisor-based systems (RAMinate, vTMM, HeteroOS) run TMM in the host for a VM, but only ever see gPA/hPA — never the guest's virtual addresses. Guest-delegated (Demeter) runs the full TMM pipeline inside the guest kernel itself, keeping only elastic provisioning at the host.

Now you're ready: Demeter's argument is that hypervisor-based is the wrong layer entirely — not just an implementation detail to optimize.
The whole story in one place

Demeter in a nutshell

The problem with tracking from outside the guest, the two insights that fix it, and how the pieces fit together.

Existing virtualized tiered-memory systems put the hypervisor in charge of tracking, classifying, and migrating guest pages. To track accesses, they scan PTE.A/D bits in EPT or GPT — but the hypervisor only ever sees guest physical addresses (gPA), never the guest's own virtual addresses (gVA). Without gVA, it can't target single-address TLB invalidation, so it's forced into destructive full EPT flushes on every scan round. Demeter's authors measured this directly: a hypervisor-based TPP variant (TPP-H) issues 4.7× more TLB flush instructions than the same logic run inside the guest, and runs 2.5× slower.

Demeter's fix is architectural, not incremental: delegate the entire three-step TMM pipeline — tracking, classification, migration — to the guest kernel, and leave the hypervisor with only tiered memory provisioning (TMP): making elastic capacity available. Two insights make this workable. Insight 1: inside the guest, access tracking sees real gVAs, so it can use cheap single-address TLB invalidation and read undisturbed locality. Insight 2: PEBS, long assumed off-limits to guests due to an old architectural bug, is now safe and fast under PEBS v5 — and is fundamentally unusable from the host side, since PEBS only ever records guest virtual addresses, meaningless to a hypervisor.

On top, Demeter designs a range-based hotness classifier that operates in guest virtual address space (not physical — where the kernel's lazy allocator has already scrambled locality), a scalable PEBS pipeline that drains samples at context-switch time instead of running dedicated polling threads, and a double balloon mechanism giving the host page-granular, tier-aware elastic control without touching TMM decisions.

The payoff: up to 2× over hypervisor-based approaches, and 28% on average (geomean) over the next-best guest-based alternative (TPP), across seven real workloads on DRAM+PMEM and DRAM+CXL.mem, all while keeping system-wide monitoring overhead under 0.2 CPU cores as VM count scales on a 36-core host.

🌾 Key takeaways

  • Hypervisor-based TMM can only see gPA/hPA, forcing destructive full TLB flushes — 4.7× more flush instructions, 2.5× slower than the same logic in-guest.
  • PEBS was wrongly believed unusable in guests; an architectural EPT-fault bug was the culprit, fixed by PEBS v5 — and it's structurally unusable from the host anyway (host can't act on gVAs).
  • Guest virtual address space, not physical, preserves true locality — the kernel's lazy page allocator scrambles physical layout.
  • Range-based classification (segment-tree-like splits/merges) scales to TiB address spaces with <50 tracked ranges.
  • Context-switch-time PEBS draining eliminates dedicated polling threads — 16× less CPU than Memtis's design.
  • Double balloon gives page-granular, tier-aware elasticity — unlike block-granular (128 MiB/1 GiB) conventional hot-plug.
  • Result: up to 2× vs hypervisor-based, 28% avg vs best guest-based alternative, system-wide monitoring overhead <0.2 core as VM count scales.
Seven everyday pictures

How to think about Demeter

Read in any order. Each ends with where the picture stops being literally true.

The core split · Guest vs. host

Asking a neighbor to guess your grocery list

Your neighbor (the hypervisor) can watch you come and go, but can only guess what you bought by peeking at your trash — indirect, laggy, and it requires disturbing your bins every time (a TLB flush). You (the guest) simply know your own list. Demeter's move: stop guessing from outside, let each guest report its own needs directly.

Where it breaks: the guest is untrusted in a real cloud — Demeter still needs the host to enforce resource bounds and per-tier limits (§7.3), it just doesn't need the host to track.
Full vs. single TLB flush

Repainting the whole hallway to update one room number

Update one door's number and you only need to repaint that door — that's a single-address TLB flush. But if you don't know which door changed (no gVA), the only safe option is repainting the entire hallway (a full EPT flush) so nobody follows a stale sign. That's the 4.7× flush-count gap between TPP-H and TPP-G in Table 1.

Where it breaks: even single-address flushes aren't free — Demeter's further 47% reduction comes from avoiding TLB-flush-triggering PTE.A/D bits altogether via PEBS, not just aiming them better.
Isolation · EPT-friendly PEBS

Each guest keeps a diary in their own locked drawer

The long-standing fear was that enabling PEBS in guests would spill every VM's samples into one shared notebook the host could read. In fact each VM's PEBS buffer address is a guest-private VMCS field (vmcs.debugctl) — hardware switches to a fresh, private drawer on every VM entry. No cross-tenant leakage, no shared buffer.

Where it breaks: isolation solved the leakage fear, but a separate, older bug (PEBS writes couldn't survive an EPT page fault) was the real reason PEBS looked broken — fixed only recently by PEBS v5 (§2.3.2).
Classification · Range splitting

Zooming a map, not surveying every house

A country-level map (one big range) is cheap to draw but useless for finding a hotspot. Zoom in only on the busy region, splitting it in half repeatedly until you've isolated a city block (2 MiB granularity) — while the quiet countryside stays one big, coarse range. Demeter's segment tree does exactly this: split hot ranges, decay and merge cold ones, reaching TiB-scale spaces with under 50 tracked ranges.

Where it breaks: a map's regions are static; Demeter's ranges continuously decay (halved access counts each epoch) and can re-merge, so the "map" is constantly being redrawn every 500 ms.
Elastic capacity · Double ballooning

Two separate air-pressure dials, not one

A conventional balloon is one dial for "how much memory total" — it can't tell FMEM from SMEM, so squeezing it can accidentally deflate the fast tier a workload desperately needs. Demeter gives each guest NUMA node (FMEM, SMEM) its own dial, adjustable page-by-page rather than in 128 MiB/1 GiB blocks, so the host can shrink SMEM without ever touching FMEM.

Where it breaks: two independent dials still need policy — Demeter deliberately leaves the actual QoS rebalancing policy unspecified (§3.3), providing only the plumbing.
Migration · Balanced relocation

Swapping seats directly, no spare chair needed

Older migration schemes free a temporary "spare chair" in FMEM, seat the new arrival, then move the displaced person to the vacated slow-tier seat — extra shuffling that can trigger a fire-drill (kernel reclamation) if seats run short. Demeter instead pairs one promotion with one demotion and swaps their contents directly, no spare seat ever allocated.

Where it breaks: the one-to-one pairing assumes promotion and demotion lists are equal length by construction — it works because Demeter deliberately truncates both lists to length 𝑚, not because swaps are always naturally balanced.
Why virtual, not physical address space

Your bookshelf vs. the moving truck

On your bookshelf (virtual address space), related books sit together — you organized them that way. Pack them into a moving truck (physical address space) loaded in whatever order boxes arrived, and that spatial order is gone; box #40 might be next to box #3 purely by coincidence of arrival time. Figure 4's heat maps show exactly this: gVA hotspots are tight and contiguous, gPA hotspots are scattered.

Where it breaks: file-backed page cache has no guest virtual address at all (it's kernel-managed), so this trick doesn't extend to it — an explicit limitation the paper flags (§3.4.2).
The full explanation

How it actually works

Section by section, following the guest TMM pipeline and the host's elastic provisioning.

1 · The problem — tracking from the wrong side of the boundary

Hypervisor-based systems (RAMinate, HeteroOS, vTMM) scan PTE.A/D bits in EPT or GPT from the host. Because the host only sees gPA/hPA, it cannot target single-address TLB invalidation and must fall back to destructive full flushes. Measured on a GUPS workload (126 GiB footprint, 36 threads): a hypervisor variant of TPP (TPP-H) issues 4.7× more TLB flush instructions than the same code run in-guest (TPP-G), and runs 2.5× slower.

🔬
Concretely: TPP-H = 62.3M single + 20.2M full flushes, 896.35s. TPP-G = 17.7M single + 0 full, 353.91s. Same tracking logic, different vantage point — that gap is the cost of the virtualization boundary.

2 · EPT-friendly PEBS — removing the last excuse

PEBS was believed structurally incompatible with guest VMs. The real cause was an architectural bug: a PEBS write to memory couldn't tolerate being interrupted by an EPT page fault (which happens under memory overcommitment, where guest pages are lazily mapped) without risking machine malfunction. PEBS version 5 removes this defect. Separately, isolation was never actually broken — the sample buffer lives in a guest-private VMCS field (vmcs.debugctl), switched per-VM by hardware automatically.

💡
Why this matters structurally: even if the host could intercept guest PEBS, the samples only contain gVAs — meaningless to a hypervisor without expensive, continuous GPT snooping (§7.5). PEBS is not just hard for the host to use; it's the wrong side of the boundary entirely.

3 · Range-based hotness classification (§3.2.1)

Demeter tracks hotness over contiguous virtual-address ranges rather than individual pages, using a segment-tree-like structure seeded with two ranges: the heap (growing up from start_brk) and the mmap region (growing down from mmap_base). Code, data, and stack are excluded — small and inherently hot.

// every epoch (t_split), for each leaf range vs. its neighbors:
α = Δaccess / (τ_split · vcpu)
if α exceeds threshold and range ≥ 2×split_granularity(2MiB):
    split range in half, divide access count evenly
// every epoch: halve every range's access count (decay)
// after τ_merge idle epochs at zero: merge back with neighbor

After splitting, ranges are ranked by hotness frequency (accesses ÷ size), ties broken by creation age (younger favored — temporal locality). Chosen defaults: epoch 500 ms, α threshold 2, split threshold τsplit=15, minimum granularity 2 MiB.

🌾
Scale check: reaching a 2 MiB hotspot inside a 64 TiB address space takes ~24 splits — about 12 seconds at 500 ms/epoch — creating fewer than 50 ranges total, since the guest's sparse address space keeps most of the tree large and cold.

4 · Scalable EPT-friendly PEBS sampling (§3.2.2)

Unlike HeMem/Memtis, which record physical addresses and must walk the page table to translate every PEBS sample, Demeter feeds gVA samples directly to the range classifier — no translation per sample. Two design choices avoid wasting CPU: a fixed (not dynamically adjusted) sample frequency of 1-in-4093 events, and draining the PEBS buffer at process context-switch time rather than via a dedicated polling thread — eliminating both idle-polling overhead and PMI storms from buffer overshoot.

The PEBS trigger event is MEM_TRANS_RETIRED.LOAD_LATENCY — media-agnostic (works for PMEM and CXL alike, unlike cache-miss events that need per-media variants) — filtered via MSR_PEBS_LD_LAT_THRESHOLD set to 64 ns, comfortably between the measured 53.6 ns cache-hit latency and 68.7 ns best-case DRAM read latency (Table 2), so cache hits are effectively filtered out rather than masquerading as memory accesses.

5 · Balanced page relocation (§3.2.3)

// f = largest index such that ranges [0, f) fit in FMEM
promotion_list = pages in hot ranges [0, f) currently in SMEM   // length m
demotion_list  = coldest m pages currently in FMEM (reverse scan)
for (p, d) in zip(promotion_list, demotion_list):
    unmap(p); unmap(d)
    swap contents directly (no temporary buffer)
    remap(p → FMEM); remap(d → SMEM)
💡
Why no temp buffer matters: sequential demote-then-promote schemes can trigger kernel page reclamation (kswapd or direct reclaim) under memory pressure, causing unwanted cascading demotions of other hot pages. One-to-one direct swapping sidesteps this entirely.

6 · Elastic provisioning — NUMA exposure + Demeter balloon (§3.3)

The host exposes FMEM and SMEM as two virtual NUMA nodes via ACPI (with NUMA distance conveying relative latency), so the guest OS needs zero new abstractions. Capacity control comes from the Demeter balloon: one dedicated, page-granular balloon per NUMA node (vs. 128 MiB/1 GiB block granularity in conventional hot-plug), each sized up to 100% of total memory, letting the FMEM:SMEM ratio slide smoothly from all-fast to all-slow. The whole thing is asynchronous — requests flow over VirtIO queues, guest-side work runs on the kernel workqueue, and completion is signaled back via epoll() on event-fd descriptors — so provisioning never blocks the critical path.

Follow the numbers, step by step

Worked examples

Four calculations, traced from the paper's own tables, connecting straight to the metrics you'd use to judge any tiering system.

① The TLB-flush chain: hypervisor → guest → guest+PEBS (Table 1)

Verify the paper's headline ratios from the raw flush counts and elapsed times.

  1. Total flushes, TPP-H: 62,289,626 single + 20,214,840 full = 82,504,466.
  2. Total flushes, TPP-G: 17,707,154 single + 0 full = 17,707,154.
  3. Ratio TPP-H / TPP-G = 82,504,466 ÷ 17,707,154 ≈ 4.66× — matches the paper's "4.7× TLB flush instructions."
  4. Elapsed-time ratio: 896.35 ÷ 353.91 ≈ 2.53× — matches "2.5× total execution time."
  5. Demeter vs. TPP-G, single flushes: (17,707,154 − 9,305,363) ÷ 17,707,154 ≈ 47.5% fewer — matches "47% reduction."
  6. Demeter vs. TPP-G, elapsed time: (353.91 − 299.57) ÷ 353.91 ≈ 15.4% faster — matches "15% improvement."
🌾
Insight: two separate architectural moves stack multiplicatively — crossing the virtualization boundary (host→guest) buys 4.7×/2.5×; then swapping bit-scanning for PEBS buys a further 1.9×/1.18× on top.

② Access-tracking primitive overhead (Table 3, pure DRAM)

Compare three raw tracking primitives, isolated from the rest of the TMM pipeline.

  1. EPT-friendly PEBS (Demeter): 5.937s, 0.64% CPU.
  2. PTE.A/D bits (TPP-H style): 27.814s, 3.08% CPU.
  3. PML-based (vTMM style): 135.410s, 14.61% CPU.
  4. PML vs. PTE.A/D: 14.61 ÷ 3.08 ≈ 4.74× more overhead — matches the paper's "4.7× higher overhead than PTE.A/D bit scanning."
  5. PEBS vs. PTE.A/D: 27.814 ÷ 5.937 ≈ 4.7× faster; PEBS vs. PML: 135.410 ÷ 5.937 ≈ 22.8× faster.
💡
PML's fixed 512-entry buffer forces frequent VM-exits regardless of workload — a rigid, fixed-frequency cost that PEBS's flexible, tunable sampling avoids.

③ CPU cost of scaling to nine VMs (Fig. 2)

Turn "cores wasted" into a fraction of a 36-core host — the number a cloud operator actually bills against.

  1. TPP wastes >4.5 of 36 cores ⇒ >12.5% of the whole host spent just tracking accesses.
  2. Memtis wastes ≈1.25 of 36 cores ⇒ ≈3.5% of the host.
  3. Demeter stays under 0.2 of 36 cores ⇒ under 0.56% of the host.
  4. Headroom reclaimed vs. TPP: roughly 12.5 − 0.56 ≈ 12 percentage points of host CPU returned to paying tenants — pure TCO, not performance.
💡
This is the number that matters for anyone designing a multi-tenant tiering monitor: overhead must scale with number of guests, not just look cheap in a single-VM microbenchmark — the same scalability concern behind sampling-based monitors like UMON/DSS in cache partitioning work.

④ From memory latency to real workload speedup

Ground the "why bother tiering at all" question in Table 2's raw numbers, then connect to the paper's end-to-end results.

  1. DRAM read (best case): 68.7 ns, 88,156.5 MB/s. PMEM read: 176.6 ns, 21,414.5 MB/s.
  2. Latency penalty of a cold page: 176.6 ÷ 68.7 ≈ 2.57× slower per access than a hot one.
  3. Bandwidth penalty: 88,156.5 ÷ 21,414.5 ≈ 4.12× — worse than the latency gap, since PMEM bandwidth degrades faster under contention.
  4. End-to-end payoff of getting placement right: Demeter reaches up to 2× over hypervisor-based approaches and 28% average (geomean) over the next-best guest-based alternative (TPP) across seven real workloads — consistent with the intended mechanism of keeping more of that 2.57–4.12× gap on the DRAM side of the line, though the paper doesn't isolate placement quality precisely enough to attribute the full end-to-end speedup directly to that gap alone.
🌾
Insight: every tiering paper's speedup number is ultimately bounded by this latency/bandwidth ratio between tiers — CXL.mem narrows this gap versus PMEM (§5.5), which is exactly why the paper calls CXL.mem "a more challenging environment" for a tiering system to show gains in.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
Why can't a hypervisor-based access tracker use single-address TLB invalidation, even in principle?
Show answer
Because the hypervisor only ever observes guest physical addresses (gPA) and host physical addresses (hPA) through EPT/GPT — it never sees the guest virtual address (gVA) that originated the access. Single-address invalidation needs a gVA to target; without one, the only safe option is a full invalidation of the entire EPT mapping.Misconception: that this is an implementation oversight fixable with better host-side code. It's structural — the information (gVA) simply doesn't cross the virtualization boundary in PTE.A/D-based designs.
Problem 2 · medium
Table 1 gives TPP-H: 62,289,626 single + 20,214,840 full flushes, 896.35s elapsed. TPP-G: 17,707,154 single + 0 full, 353.91s elapsed. Compute the total-flush ratio and the elapsed-time ratio, and note which grows faster.
Show answer
Total flushes: TPP-H = 82,504,466; TPP-G = 17,707,154; ratio ≈ 4.66×. Elapsed time ratio: 896.35/353.91 ≈ 2.53×. The flush-count gap (4.66×) is nearly double the time gap (2.53×) — flushes don't translate 1:1 into wall-clock time, since some of that extra flushing overlaps with other work or hits caches that were already partially cold.Misconception: assuming flush-count ratio and slowdown ratio must match. They're correlated but not equal — flush cost also depends on how much useful work was already in flight.
Problem 3 · easy
True or false: Demeter turns off PEBS on the host and only enables it in guests.
Show answer
Misleading framing — PEBS was never usable by the host for guest memory in the first place, due to the architectural bug and the fact that host-side PEBS samples wouldn't even correspond to guest addresses. Demeter doesn't disable anything on the host; it enables PEBS inside guests, made safe by PEBS v5, and isolated per-VM via vmcs.debugctl.Misconception: thinking of this as a toggle moved from one place to another. It's closer to "a capability was unlocked where it was always meant to run."
Problem 4 · medium
A range covering 8 MiB has accumulated far more accesses than its neighbors. Walk through what happens to it over the next few epochs under Demeter's range-splitting scheme (τ_split=15, split granularity=2 MiB).
Show answer
If its significance factor α = Δaccess/(τ_split·vcpu) exceeds the threshold, the range is split in half (4 MiB + 4 MiB), each inheriting half the access count. If one half remains hot, it keeps splitting in subsequent epochs — 4→2→2 MiB — until it hits the 2 MiB minimum granularity, at which point splitting stops even if it's still hot. Meanwhile every epoch, all ranges' access counts are halved (decay), so a half that stops being accessed will cool toward zero and eventually merge back with a cold neighbor after τ_merge idle epochs.Misconception: assuming splitting continues indefinitely toward per-page granularity. It's capped at 2 MiB specifically to avoid destroying the TLB-coverage benefit of hugepages (§3.4.1).
Problem 5 · hard
Why does Demeter's balanced page relocation avoid a temporary buffer, and what failure mode does that specifically prevent?
Show answer
By pairing exactly one promotion candidate with one demotion candidate (both lists truncated to the same length m) and swapping their contents directly, Demeter never needs to allocate a free page mid-migration. Sequential approaches that first demote into a scratch free page, then promote into the vacated slot, can trigger the kernel's page reclamation machinery (kswapd or direct reclaim) if free pages run short — and that reclamation can cascade into evicting other, unrelated hot pages that had nothing to do with the current migration.Misconception: thinking "no temp buffer" is just an optimization for fewer memcpy operations. Its real purpose is avoiding memory-pressure side effects that corrupt unrelated hot data.
Problem 6 · medium
A cloud operator points a conventional VirtIO balloon at a VM and asks it to shrink SMEM by 20%. What goes wrong, per §5.2.1's finding?
Show answer
A conventional balloon has no tier awareness — it's a single dial for "total memory," not two dials for FMEM and SMEM. Its inflation mechanism conflicts with the Linux allocator's own preferences and ends up prioritizing FMEM reservation regardless of which tier was actually targeted, resulting in severe FMEM under-provisioning rather than the intended SMEM shrink. Demeter balloon's dedicated per-NUMA-node balloons avoid this by construction.Misconception: that "the balloon just reclaims free pages" is tier-neutral. Free-page selection is governed by the guest allocator's own tier preferences, which a tier-blind balloon can't override.
Problem 7 · hard
§5.4 reports Demeter underperforms hypervisor-based TPP-H on PageRank by 60%, its only loss out of seven workloads. What property of PageRank's access pattern plausibly explains this, based on how Demeter classifies hotness?
Show answer
The paper describes graph workloads (graph500, PageRank) as having power-law, scattered access patterns — a small subset of vertices/edges is hot, but their addresses are interleaved fine-grained across the whole memory space rather than sitting in contiguous ranges. Demeter's classifier gets its efficiency from range-based (contiguous) grouping; a workload whose hot data is scattered single-word-scale across a huge span defeats that assumption, forcing many small ranges and reducing classification accuracy relative to a scheme not relying on spatial contiguity.Misconception: assuming Demeter is strictly better on every access pattern. Its core efficiency trick (range contiguity) is also its Achilles' heel on genuinely scattered, fine-grained-hot workloads.
Problem 8 · easy
Does Demeter manage file page cache the same way it manages heap/mmap memory?
Show answer
No — file page cache is managed by the kernel in physical address space and has no corresponding guest virtual address, so Demeter's gVA-based range classification doesn't apply to it (§3.4.2). The paper argues this limitation is softened because even naive (non-hotness-aware) placement of file-backed data in SMEM still beats frequent disk I/O.Misconception: assuming a gVA-space-based system is a universal solution for all guest memory. It explicitly excludes anything without a guest virtual address.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What exactly does "guest delegation" mean?▾
Running the entire tiered-memory-management pipeline — access tracking, hotness classification, and page migration — inside the guest kernel, instead of in the hypervisor. The host is left with only tiered memory provisioning: making elastic FMEM/SMEM capacity available, without deciding which pages go where.
Q2Isn't delegating management to an untrusted guest a security risk?▾
Demeter treats all guest code as untrusted by design (§7.3). PEBS state is hardware-isolated per VM and cleared on VM-exit; each balloon has a VM-private VirtIO channel; the host enforces hard per-tier resource bounds regardless of what the guest requests; and the host retains authority to terminate anomalous VMs. The guest decides placement, never total resource limits.
Q3Why was guest PEBS thought to be unusable for years?▾
An architectural bug meant a PEBS buffer write couldn't survive being interrupted by an EPT page fault without risking a machine hang — and EPT faults are common under memory overcommitment, where guest pages are lazily mapped on first touch. This created a real blind spot until PEBS version 5 fixed the underlying defect.
Q4Could the hypervisor just read the guest's PEBS samples itself?▾
Structurally, no — even setting isolation aside, PEBS samples contain guest virtual addresses, which carry no meaning to the hypervisor's page-migration logic without continuously snooping or trapping guest page table updates, which would defeat the entire point of hardware-assisted virtualization (§7.5).
Q5Why classify hotness in virtual address space instead of physical?▾
The kernel's physical page allocator optimizes for reduced fragmentation and lazily maps pages in the order they're first touched — not their spatial relationship. This scrambles locality: Figure 4's heat maps show gVA hotspots concentrated in small contiguous regions, while the same accesses in gPA space appear scattered across the entire usable memory.
Q6How does the range classifier avoid becoming a huge data structure?▾
It only refines (splits) ranges that are actually hot, down to a 2 MiB floor, and merges cold ranges back together after they've decayed to zero access count for τ_merge epochs. Because most of a real application's address space is sparse and cold, the tree stays small — under 50 ranges even for a 64 TiB space.
Q7What's the double balloon, and how is it different from a normal memory balloon?▾
A normal balloon has one dial for total VM memory and no tier awareness. Demeter gives each guest NUMA node (FMEM, SMEM) its own dedicated balloon, with page-level (not 128 MiB/1 GiB block-level) granularity, so the host can resize either tier independently without accidentally starving the other.
Q8Does Demeter work with CXL.mem, or only PMEM?▾
Both — the paper evaluates DRAM+real-PMEM and DRAM+emulated-CXL.mem configurations. The PEBS trigger event chosen (memory load latency, not a media-specific cache-miss event) is deliberately media-agnostic, so it works unchanged as new tiers like CXL.mem appear.
Q9How much CPU overhead does Demeter's monitoring actually cost?▾
Under 0.2 CPU cores system-wide even at nine concurrent VMs on a 36-core host (Fig. 2) — versus over 4.5 cores for a naive PTE.A/D approach (TPP) and about 1.25 cores for an optimized PEBS design run the conventional way (Memtis). The saving comes from context-switch-time sample draining instead of dedicated polling threads.
Q10Does Demeter beat hypervisor-based approaches on every workload?▾
No — it wins on 6 of 7 real workloads (up to 2× on dynamic hotspot patterns, 20% on static hotspots, 10% on uniform access), but underperforms on PageRank by 60%, likely due to that workload's fine-grained scattered (power-law) access pattern working against range-based contiguous classification.
Q11Does this work for bare-metal cloud instances too?▾
Yes, and arguably more naturally — bare-metal VMs expose physical memory directly to tenants with a stripped-down or offloaded hypervisor, which makes hypervisor-based tiering impossible in the first place. Since Demeter's TMM lives entirely in the guest kernel, it does not require hypervisor-side TMM to function — though the full system still depends on host-side provisioning and tier-exposure mechanisms (§7.4).
Q12What did the paper leave for future work?▾
Concrete QoS/fairness policies on top of the exposed telemetry (the architecture is deliberately policy-agnostic), finer intra-hugepage hotness detection below 2 MiB, and extending range-based classification to file-backed page cache, which currently falls outside gVA-space management.
