Don't ask the LLM for the whole proof — ask it to block one bad state at a time

Inductive invariants must be exactly right, everywhere, all at once — which is exactly what LLMs are bad at producing in one shot. I3DP wraps an LLM inside IC3's frame machinery so it only ever has to answer a small, checkable question.

📄 "I3DP: Neuro-Symbolic Inductive Invariant Inference for Distributed Protocols" · Cao et al. 🎓 No formal-methods background assumed — primers cover TLA+ and IC3 from scratch ⏱ ~30 min read
🧩

1What "proving a protocol safe" actually requires▾

A distributed protocol is a transition system: it starts in some initial state and moves via allowed steps. "Safety" means a bad state (two leaders, two committed-and-aborted decisions, etc.) is never reached. Testing can't prove this — there are infinitely many reachable states.

The standard proof technique is an inductive invariant: a predicate that (1) holds in every initial state, (2) is preserved by every transition, and (3) implies the safety property. If you can find one, you've proven safety without enumerating states.

Now you're ready: the entire paper is about how to automatically find such a predicate for a given TLA+ protocol.
2TLA+ in one paragraph▾

A TLA+ spec declares state variables (vars), an Init predicate describing legal starting states, and a Next relation describing legal transitions (often a disjunction of named actions like "vote", "commit", "fail"). Distributed protocols are typically written with sets, functions, and quantifiers over nodes/messages/terms — e.g. ∀ s,t ∈ Server : ....

A run is written Init /\ [][Next]_vars: start in Init, then every step either follows Next or leaves everything unchanged.

Now you're ready: "the safety property" and "the invariant" are both just TLA+ state predicates over these same variables.
3Why the safety property alone usually isn't inductive▾

It's tempting to think "safety holds everywhere reachable, so safety = the invariant." It's almost never that simple. There are typically unreachable-but-safety-satisfying states from which one transition violates safety — so Safety fails condition (2), preservation.

The paper's two-phase-commit example: the state go_abort={n1}, abort_flag=FALSE (everything else at its initial value) satisfies Safety, yet node n1 can fire the Abort action from it and land in a state that violates Safety. An inductive invariant needs extra clauses that exclude such "safe but dangerous" states.

Now you're ready: synthesis means strengthening Safety with extra clauses until the whole conjunction is preserved by every transition.
4IC3/PDR — frames as over-approximations▾

IC3 builds a sequence of frames F₀ ⊆ F₁ ⊆ F₂ ⊆ ..., where F₀ = Init and each Fᵢ over-approximates "every state reachable within i steps" (it may include some extra, unreachable-but-safe states too — that's fine, as long as it never excludes a truly reachable one).

Every frame beyond F₀ starts out containing Safety, and gets strengthened over time by adding learned clauses that exclude specific bad states without excluding anything truly reachable.

Now you're ready: when two adjacent frames become identical, that shared formula is closed under Next and implies Safety — i.e. it is an inductive invariant. That's IC3's termination condition.
5The four IC3 operations▾

(1) Frontier query: does the deepest frame F_k have a state that can step to a Safety violation? If so, that's a "bad state." (2) Backward predecessor search: does the shallower frame F_{k-1} have a predecessor of that bad state? If yes, recurse deeper; if no, the state is predecessor-free. (3) Clause learning: derive a clause that excludes a predecessor-free bad state (and ideally others like it) from its frame. (4) Frontier extension & push: add a new frame, and propagate each clause as deep as it still holds.

Now you're ready: I3DP keeps this exact four-stage skeleton — it just changes who proposes the clause in step (3).
6Why standard IC3's clause learning doesn't transfer to TLA+▾

In hardware IC3 (SAT-based), a bad state is a Boolean assignment, and clause learning is a mechanical, always-succeeding step: generalize a cube via SAT-solver-driven literal dropping. TLA+ protocol states involve sets, functions, and quantifiers with no natural Boolean-cube form — there's no mechanical generalization procedure.

This is precisely the gap I3DP fills with an LLM: instead of a SAT-derived cube, the LLM proposes a protocol-level predicate (e.g. "every node in the quorum has voted") that excludes the bad state.

Now you're ready: the LLM's job is narrow — propose a clause for a batch of concrete counterexample states — not "understand the whole protocol and write a full invariant."
7Explicit-state (TLC) vs. symbolic (Apalache) model checking▾

TLC exhaustively enumerates the reachable states of a finite TLA+ instance — fast and simple for checking many concrete candidate clauses against known reachable states in one batch. Apalache encodes the transition system into SMT constraints and asks a solver for a satisfying assignment (a witness state) — well-suited to "does a state matching this pattern exist?" queries where explicit enumeration would be too large.

Now you're ready: I3DP uses Apalache for the IC3 witness queries (frontier, predecessor, admission, push) and TLC for batch-screening LLM-proposed clauses against concrete reachable states.
8LLMs as hypothesis generators, not oracles▾

An LLM asked to write a whole invariant in one shot must get every clause right simultaneously — one bad clause invalidates the entire conjunction, and a failed induction check on the full formula doesn't say which clause is wrong. Treat the LLM instead as a source of candidate clauses for a narrow, concrete sub-problem, and have a separate mechanical process check and filter every candidate.

Now you're ready: this "propose, then verify" split is the paper's central design principle — the LLM conjectures, IC3's admission checks decide.
9Finite-instance checking vs. the unbounded proof▾

TLC and Apalache both reason about a finite instance of the protocol (a fixed, small number of nodes/terms). An invariant that's inductive on that finite instance doesn't automatically generalize to arbitrary protocol sizes. Closing that gap requires a separate, unbounded proof — here, TLAPS, the mechanized TLA+ proof checker.

Now you're ready: "I3DP discovers 29/29 invariants" and "TLAPS proves all 29 inductive for unbounded instances" are two separate, sequential results — both are needed to call the protocols verified.
The whole story in one place

I3DP in a nutshell

The problem with asking an LLM directly, the fix, and how the pieces fit together.

Proving a distributed protocol safe usually means finding an inductive invariant — a state predicate that holds initially, is preserved by every transition, and implies the target safety property. Finding one is hard: existing tools either restrict the protocol to a decidable logic fragment (excluding common TLA+ patterns) or demand manually curated predicate pools from an expert.

LLMs can reason about protocol semantics, but asked to produce a complete invariant directly, they fail: on the paper's two-phase-commit example, 44 attempts time out, each plausible but containing a few overly strong clauses, and a failed induction check on the full conjunction never says which clause is at fault.

I3DP's fix is architectural, not a bigger model: wrap the LLM inside IC3's frame-based decomposition. IC3 maintains a sequence of frames that over-approximate reachable states; each frontier query exposes one concrete bad state; backward predecessor search walks it back through earlier frames until it's predecessor-free; only then does the LLM get asked — for a clause that blocks that one concrete state (or a small batch of related ones), never for the whole invariant. Every candidate is checked against two conditions (holds in Init; inductive relative to the current frame) before admission, and a checked, exact fallback blocker guarantees the loop still terminates even if the LLM never proposes anything useful.

The payoff: across 29 distributed protocols — consensus, reconfiguration, transaction commit, client–server — I3DP discovers candidate invariants for all 29, including MongoLoglessDynamicRaft (MLDR), an industrial-scale Raft reconfiguration protocol that none of five compared tools (Endive, IC3PO, SWISS, DuoAI, P-FOL-IC3) solves. Every discovered invariant is then confirmed inductive for the unbounded protocol by TLAPS.

🧩 Key takeaways

  • A complete-invariant-in-one-shot LLM prompt fails because a global induction failure gives no per-clause signal.
  • IC3's frames decompose that global problem into a stream of local "block this concrete bad state" tasks.
  • The LLM only proposes clauses; the IC3 controller's admission checks (Init ⇒ c; F ∧ c ∧ Next ⇒ c′) decide what survives.
  • A checked, exact aggregate-blocker fallback preserves finite-instance completeness even when the LLM fails.
  • Apalache handles symbolic witness queries; TLC batch-screens candidate clauses against concrete reachable states.
  • 29/29 protocols solved, including MLDR, which no compared tool solves; all 29 confirmed inductive by TLAPS for unbounded instances.
Six everyday pictures

How to think about I3DP

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core mechanism · Frames

A row of watchtowers, each seeing one step further

F₀ is the guardhouse right at the gate (Init). Each next tower stands one step further out, and from it you can see everything reachable that far — plus a little unreachable margin you haven't ruled out yet. A "bad state" spotted from the farthest tower gets walked back tower by tower; if it turns out no earlier tower could have produced it, you post a new sign (a clause) there forbidding it.

Where it breaks: real watchtowers see a fixed area; IC3 frames are logical over-approximations that shrink as clauses are added — the picture works for intuition, not for the exact logic of implication.
Backward search · Predecessor-free states

A detective retracing a getaway route

Start at the crime (the safety violation) and ask: where was the car one step before? Keep tracing backward. Eventually either you reach the very start of the trip (a real counterexample — the protocol really is unsafe) or you reach a spot with no earlier trace at all: a dead end. That dead end is the concrete fact worth writing down — "no route leads here" — which is exactly the state I3DP asks the LLM to explain away with a clause.

Where it breaks: a detective's dead end is one specific location; a predecessor-free state in IC3 is usually one representative of a whole family, which is why I3DP batches several before asking the LLM to generalize.
The propose/decide split · Admission checks

An eager intern and a strict editor

The intern (LLM) drafts plausible sentences quickly — some brilliant, some overreaching. The editor (IC3's admission check: does it hold in Init? is it inductive relative to the current frame?) never trusts a draft on the intern's word; every sentence is checked against the source material before it's allowed into the final document. The prompt asks the intern for 10–15 candidate clauses per round — one motivating round in the paper yields 15 — and only whichever pass the editor's checks make it into the final document.

Where it breaks: a human editor can be persuaded by argument; the IC3 admission check is a hard, mechanical logical test — nothing gets in on the strength of a good explanation alone.
Why decomposition works · Feedback granularity

One giant essay vs. a stack of short quizzes

Grade a 20-paragraph essay pass/fail and a "no" tells the writer almost nothing about which paragraph is wrong — they'll rewrite the whole thing, guessing. Break the same content into 20 short quiz questions, each independently gradable, and every wrong answer points straight at the misunderstanding. I3DP's frontier query is the quiz-question generator: each round asks about one concrete bad state, not the whole protocol at once.

Where it breaks: the paper found that giving the essay-grading loop finer clause-level feedback didn't fix it — it just caused local patching without global reconsideration, and even hurt one benchmark. The fix isn't "more feedback," it's asking a genuinely smaller question.
Reuse across bad states · clauseMemory

A locksmith's ring of master keys

A key cut for one stubborn lock sometimes opens a different lock down the hall too. I3DP keeps every filtered clause in a shared clauseMemory; before ever calling the LLM again for a new bad state, the controller first tries every key already on the ring. In the two-phase-commit walkthrough, 5 of 7 frontier rounds are resolved this way — no new LLM call needed.

Where it breaks: unlike a real key ring, the "fit" here is re-verified by an exact admission check every single time — nothing is assumed to still work just because it worked once before.
The completeness guarantee · Aggregate blocker

A safety net under a trapeze act

The LLM's creative swings (protocol-level clauses) are the interesting part of the act — but there's a plain net strung underneath regardless. If the LLM keeps missing and no new bad states appear, I3DP negates and conjoins all the accumulated bad states into one exact, checked "aggregate blocker" clause and moves on. It's ugly and unstructured, but it's guaranteed to work on the finite instance — the loop always terminates.

Where it breaks: the net only catches you on the checked finite instance — it says nothing about the unbounded protocol, which is why TLAPS is still needed afterward.
The full explanation

How it actually works

Stage by stage, with the controller's architecture and the backward-blocking mechanics rebuilt as diagrams.

1 · Why direct LLM synthesis fails

Asked to produce a complete inductive invariant for the two-phase-commit protocol directly (generate → check induction → feed back counterexample → retry), the LLM (Claude Opus 4.6) makes 44 attempts and times out. Each candidate has 13–26 clauses, mostly individually correct, but a few are too strong — e.g. asserting go_abort ≠ {} ⇒ vote_yes ≠ Node, which is false because a node can vote yes and then crash, letting the coordinator broadcast abort while every node actually voted yes. The induction counterexample refutes only the full conjunction, never identifying the offending clause, so the LLM oscillates without converging. Adding clause-level feedback doesn't fix this — it steers toward local patching and even causes one additional benchmark (tla-simpleregular) to newly fail.

2 · The IC3 controller's four stages

I3DP keeps IC3's frame sequence Frames = [{Init}, {Safety}] and a global clauseMemory retaining every filtered clause across the run.

  • Frontier query. Ask Apalache: does F_k ∧ Next ⇒ Safety′ hold? If not, it returns a bad state at the frontier.
  • Predecessor query. For each bad state, check F_{i-1} ∧ Next ⇒ ¬badState′ one level shallower at a time. A predecessor descends the search; reaching level 0 means a real counterexample — the protocol is unsafe. No predecessor at a level above 0 means the state is predecessor-free.
  • Blocking-clause query. First check clauseMemory for an already-admissible clause; only if none exists is the LLM invoked with the current batch of bad states.
  • Clause push. Once the frontier is fully blocked, append a fresh frame and propagate each clause as deep as F_k ∧ Next ⇒ c′ still holds.

3 · Key deviations from standard IC3

Three changes adapt IC3 to LLM-generated, protocol-level clauses instead of SAT-derived Boolean cubes:

①
Deferred, batched blocking. A single bad state may not give the LLM enough context to infer a protocol-level condition, so I3DP lets blocking be deferred: unresolved bad states accumulate in a shared worklist, and the LLM sees a batch — richer context for spotting a common pattern across several related failures.
②
A cross-round clause pool (clauseMemory). Standard IC3 needs no such pool because SAT-based clause derivation is deterministic. Because LLM clauses can generalize unpredictably, a clause learned for one bad state may later block a different one at a different frame level — worth checking before paying for another LLM call.
③
Opportunistic blocking during push. When a clause fails to propagate to the next frame, standard IC3 just leaves it behind. I3DP instead treats the push-failure counterexample as one more bad state: check clauseMemory first, then allow at most one extra LLM query, before giving up and moving on.

4 · Soundness and completeness, on the checked finite instance

Every LLM clause is screened by TLC against concrete reachable states before it can be admitted — nothing falsified by a reachable state ever enters a frame — and admission itself enforces the two IC3 conditions (Init ⇒ c and F_{i-1} ∧ c ∧ Next ⇒ c′). Because a finite instance has only finitely many bad states, and I3DP keeps accumulating them, the process is guaranteed to terminate: either the LLM eventually supplies enough clauses, or the exact aggregate blocker closes the gap. This is the completeness guarantee flat CTI-elimination approaches (like Endive) don't provide.

💡
A note for readers coming from OS/memory-systems verification: the frame-based "prove safety by incremental over-approximation, discharge exactly what's left with a mechanical fallback" recipe generalizes beyond consensus protocols — it's the same shape of argument you'd want for proving invariants on concurrent page-migration or CXL-coherence protocols (e.g. "no two nodes simultaneously believe they own a hot page during a tier-migration race"), where the "bad states" are races between migration and access rather than races between voters. This connection is the author's framing, not a claim from the paper.
Follow the numbers, step by step

Worked examples

Four traces carried through with the paper's real numbers: the motivating walkthrough, the hardest case study, and the two comparisons that isolate what IC3 actually buys.

① Two-phase commit: direct synthesis vs. IC3 decomposition

Same protocol, same LLM, two architectures. What does the arithmetic say about efficiency?

  1. Direct synthesis: 44 attempts inside a 600-second timeout, no success. That's roughly 600 ÷ 44 ≈ 13.6 seconds per attempt, all wasted — the budget is exhausted before convergence.
  2. IC3 decomposition, round 1: the frontier query finds bad state go_abort={n1}, alive={n1}. Backward search confirms it's predecessor-free. The LLM proposes 15 candidates; the controller admits go_abort={} ∨ go_abort=Node.
  3. Round 2: the next frontier bad state is already covered by an existing clause (go_commit={} ∨ go_commit=Node) — zero new LLM calls.
  4. Total: 7 frontier rounds, only 2 require a new LLM call — 5 ⁄ 7 ≈ 71% of rounds reuse clauseMemory for free.
  5. Result: 11 strengthening clauses at fixpoint, minimized to 8 (a 3⁄11 ≈ 27% reduction), found in 171 seconds with 2 total LLM calls — versus 600 seconds and 44 calls for zero success.
🧩
Insight: the win isn't a smarter LLM — it's the same model asked a smaller question repeatedly, with most of the "work" done by reusing a previously validated answer.

② MLDR: the hardest benchmark, clause by clause

MongoLoglessDynamicRaft — 5 state variables per server, 4 actions, safety property OnePrimaryPerTerm. I3DP takes 4,525 seconds (the longest of any benchmark).

  1. 15 strengthening conjuncts discovered (16 total including the safety clause itself), split into three categories: 8 single-server constraints (found early, e.g. configVersion[s] ≥ 1), 4 cross-server relationships (configuration uniqueness, quorum overlap), and 3 nested-quantifier quorum properties — 8 + 4 + 3 = 15, matching the reported count.
  2. Post-hoc minimization: iterating from older clauses to newer ones, dropping each and re-checking inductiveness with Apalache eliminates 8 redundant clauses, leaving a minimal 7-conjunct strengthening (15 − 8 = 7) — fully automatic once the invariant exists.
  3. Verification cost: a single inductiveness check on MLDR can exceed 5 minutes (300s). Against the 4,525-second total, that's ≥ 300 ⁄ 4525 ≈ 6.6% of the run spent on just one check — motivating the extended 2-hour timeout used for this benchmark.
  4. Budget used: 4,525 ⁄ 7,200 ≈ 62.8% of the 2-hour allowance — I3DP finishes with headroom to spare, unlike every compared tool, which times out entirely.
  5. Downstream proof: TLAPS confirms the 7-conjunct invariant inductive for unbounded instances in a proof exceeding 3,000 lines, completed by LLM agents with minimal human intervention.
💡
The genuinely hard clauses are the 3 nested ∀∃ quorum properties — each requires inferring a cross-variable relationship from counterexample states that expose only a handful of concrete node configurations at a time.

③ Ablation: what does the IC3 structure actually buy?

Same 29 protocols, three configurations: full I3DP (Claude Opus 4.6 + IC3), LLM-alone (Claude Opus 4.6, no IC3), LLM-var (Gemini 3 Flash + IC3).

  1. I3DP (strong model + IC3): 29 ⁄ 29 solved = 100%.
  2. LLM-var (weak model + IC3): 27 ⁄ 29 = 93.1%, timing out only on the two hardest (mldr, pyv-paxos-epr).
  3. LLM-alone (strong model, no IC3): 24 ⁄ 29 = 82.8%, timing out on 5, including tla-twophase — a benchmark the weaker Gemini model solves once wrapped in IC3.
  4. The gap that matters: 93.1% (weak model + structure) > 82.8% (strong model, no structure) — a ≈ 10.3 percentage-point swing from architecture alone, holding the hardest task (MLDR) constant as a failure for both non-full configurations.
  5. On MLDR specifically: LLM-alone makes 62 attempts within 10 minutes (≈ 9.7 s/attempt) and even an extended run past 24 hours (> 86,400s) never escapes the loop — versus I3DP's success in 4,525 seconds (75 minutes).
🧩
Insight: the frame structure, clause admission, and backward search supply enough guidance that a weaker model outperforms a stronger model missing that structure — on this benchmark suite, IC3 structure can compensate for a weaker underlying model, though the ablation doesn't establish architecture as the dominant factor for LLM-guided invariant synthesis in general.

④ Cross-tool comparison: solve-rate arithmetic

Across the 29-protocol suite (28 shared with Endive), how does I3DP's headline "29/29" actually compare?

  1. I3DP: 29 ⁄ 29 = 100%.
  2. IC3PO: 26 ⁄ 29 ≈ 89.7% — times out on the 3 hardest (pyv-learning-switch, mldr, pyv-paxos-epr); often faster than I3DP on protocols it does cover.
  3. Endive: 24 ⁄ 28 shared protocols ≈ 85.7% — and only with a manually curated predicate pool (I3DP needs none).
  4. P-FOL-IC3: 24 ⁄ 29 ≈ 82.8% — restricted to mypyvy's decidable fragment.
  5. DuoAI: 21 ⁄ 29 ≈ 72.4%; SWISS: 17 ⁄ 29 ≈ 58.6% (8 timeouts, 4 terminate without an invariant).
💡
Every one of the five baselines fails on MLDR, though not identically: Endive's TLA+-based CTI-elimination search doesn't converge on it, while the Ivy/mypyvy-based tools (IC3PO, SWISS, DuoAI, P-FOL-IC3) cannot propose a candidate that passes their own inductiveness check under the same finite-instance size, and cannot verify I3DP's discovered invariant for unbounded instances at all, since MLDR sits outside their decidable fragment.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
In the two-phase-commit example, the state go_abort={n1}, abort_flag=FALSE (all else initial) satisfies the safety property. Why isn't Safety itself an inductive invariant here?
Show answer
Because preservation fails: from that state, node n1 can execute the Abort action (n1 ∈ go_abort), producing decide_abort={n1} while abort_flag is still FALSE — violating the third safety conjunct ("every abort decision carries the abort flag"). The state is safe but not "safety-preserving," so an inductive invariant needs extra clauses that exclude it.Misconception: that a state satisfying the target property today is automatically fine to remain in a candidate invariant. Inductiveness requires the property to survive every transition, not just hold at a snapshot.
Problem 2 · medium
Suppose I3DP's LLM fails to propose an admissible clause for the remaining bad states, and no new frontier bad states can be found either. What does the controller do, and why does this preserve termination?
Show answer
It negates and conjoins all the currently accumulated bad states into one exact, checked "aggregate blocker" clause and adds it to the frame as a last resort. This works because on a finite instance there are only finitely many bad states; the complement of the full accumulated bad-state set is guaranteed to be an inductive invariant in that finite state space, so the loop is guaranteed to eventually terminate even without any useful LLM output.Misconception: that I3DP's correctness depends on the LLM eventually succeeding. The LLM only affects efficiency — the checked aggregate-blocker fallback is what guarantees the finite-instance completeness result.
Problem 3 · medium
On the 28 TLA+ protocols shared with Endive, I3DP solves 28 and Endive solves 24 — a gap of 4 protocols. What's the primary structural reason (not just "the LLM is better"), and what does it cost I3DP to avoid?
Show answer
Endive's flat CTI-elimination loop draws candidate predicates from a manually curated, protocol-specific predicate pool — it needs expert insight about which predicates and quantifier patterns matter for each protocol, and lacks IC3's completeness backstop. I3DP replaces that curated pool with LLM-generated clauses driven by concrete counterexample states, requiring no manual template design, while retaining IC3's frame structure and its exact fallback blocker for finite-instance completeness.Misconception: that the gap is purely "bigger model, better clauses." Much of it is architectural — a completeness guarantee and zero manual predicate engineering that Endive's design doesn't provide.
Problem 4 · hard
The paper reports that adding clause-level feedback (pointing out which specific clause a counterexample violates) to the direct full-invariant LLM loop doesn't help — it even causes one additional benchmark to fail. But TLC's per-clause screening inside I3DP's IC3 loop clearly does help. What's the structural difference?
Show answer
In the direct loop, the LLM is still being asked to produce a whole 13–26 clause conjunction; clause-level feedback just tells it which one piece of an already-huge draft to locally patch, without prompting it to reconsider the invariant as a whole — this can trap it oscillating between similarly flawed variants. In I3DP, the task itself is already scoped to a handful of concrete bad states before the LLM is ever called; TLC's screening filters candidates for that narrow, already-decomposed task rather than trying to locally repair a sprawling conjunction.Misconception: that "more granular feedback" is always the fix for a struggling LLM loop. The real fix here is granular task scope — feedback quality can't compensate for asking a task that's still too large.
Problem 5 · medium
MLDR's discovered invariant has 15 strengthening conjuncts, later minimized to 7 for the TLAPS proof. Why does IC3 produce redundant clauses in the first place, if it's checking admissibility rigorously at every step?
Show answer
Each admitted clause is checked for validity (it must hold in Init and be inductive relative to its frame) at the moment it's introduced, to strengthen a specific frame and block a specific bad state or batch — but IC3 never checks whether an earlier clause has since become logically implied by clauses admitted later. Once stronger clauses are in place, some earlier weaker ones become unnecessary; a separate minimization pass (drop-and-recheck with Apalache) is needed to find and remove them.Misconception: that "admissible" and "necessary" mean the same thing. Every admitted clause is individually valid; that doesn't mean every admitted clause is still needed once the full set is in place.
Problem 6 · easy
The frontier query checks F_k ∧ Next ⇒ Safety′. What does it mean if this implication holds, versus if it fails?
Show answer
If it holds, every state in the current frontier frame is one step away from safety only — no bad state exists there, so the controller can move straight to extending the frontier (appending a new frame and pushing clauses). If it fails, Apalache returns a concrete witness: a state in F_k with a successor that violates Safety — that's the new frontier bad state, which then enters backward predecessor search.Misconception: that a failing frontier query means the protocol is unsafe. It only means there's more blocking work to do at this frame; unsafety is only confirmed if backward search reaches F₀ = Init.
Problem 7 · hard
IC3PO, SWISS, DuoAI, and P-FOL-IC3 all build on Ivy or mypyvy and require reasoning within a decidable first-order fragment (mypyvy's decidable fragment, of which EPR is a well-known example). Why does this specifically doom them on MLDR, beyond "it's just a hard protocol"?
Show answer
MLDR's core safety argument needs nested ∀∃ quorum properties with cross-variable term/version comparisons (e.g. "every quorum has a witness node whose term is at least as high, or whose config is newer") — reasoning that involves ordering and non-symmetric relational structure outside the decidable fragments these tools support. The paper notes these tools can't even verify I3DP's already-discovered invariant for unbounded instances on MLDR, and under the same finite-instance size, none proposes a candidate that passes its own inductiveness check — the protocol is structurally outside their scope, not merely unsolved by search.Misconception: that these are strictly weaker search algorithms. On protocols within their decidable fragment they are often faster than I3DP (e.g. IC3PO); the failure on MLDR is a scope limitation, not a search-quality one.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most.

Q1What is an inductive invariant, in one sentence?▾
A state predicate that holds in every initial state, is preserved by every protocol transition, and implies the target safety property — proving all three at once establishes safety without enumerating states.
Q2Why can't you just ask an LLM to write the whole invariant?▾
Because every clause must be simultaneously correct — one overly strong clause invalidates the entire conjunction — and a failed induction check on the full formula gives no signal about which clause is wrong. On the paper's two-phase-commit example, this direct approach makes 44 attempts and times out.
Q3What does IC3 contribute that a flat CTI-elimination loop (like Endive) doesn't?▾
Two things: a principled decomposition (predecessor-free bad states accumulate into batches that give the LLM a tractable, concrete sub-problem instead of the whole protocol), and a completeness backstop (the exact aggregate blocker), which guarantees the loop terminates on the finite instance even when LLM-guided clause search fails entirely.
Q4Why use both TLC and Apalache instead of just one?▾
They answer different kinds of questions well. Apalache's SMT encoding handles "does a state exist matching this pattern?" queries (frontier, predecessor, admission, push) over quantified TLA+ state spaces without enumeration — essential since these query spaces can exceed explicit-state limits. TLC's explicit enumeration is efficient for batch-checking many candidate clauses against a known, finite set of reachable states.
Q5Does I3DP actually prove protocols correct, or just find candidates?▾
Both, in sequence. I3DP's IC3 loop finds a candidate invariant that's inductive on a checked finite instance. Separately, for all 29 solved benchmarks, TLAPS mechanically proves the same invariant is inductive for the unbounded protocol — that combination is what establishes safety.
Q6What exactly is a "predecessor-free" bad state?▾
A bad state at frame level i for which the shallower frame F_{i-1} has no predecessor (i.e. F_{i-1} ∧ Next ⇒ ¬badState′ holds). It means nothing reachable within i-1 steps can step into this bad state, so it's a legitimate target for a new blocking clause rather than something needing further backward tracing.
Q7Why does I3DP defer blocking and batch bad states, instead of blocking each one immediately like standard IC3?▾
Standard IC3's SAT-based clause learning is a mechanical, always-succeeding step on Boolean cubes. A TLA+ bad state has no such natural generalization, and a single state may not give the LLM enough context to infer the right protocol-level condition. Batching several related bad states gives the LLM more signal to spot a common structural pattern.
Q8What is "opportunistic blocking" during the push phase?▾
When a clause fails to propagate to the next frame, standard IC3 just leaves it in its current frame. I3DP instead treats the resulting push-failure counterexample as one more bad state to try to block — first against clauseMemory, then with at most one extra LLM query — before giving up and moving on as usual.
Q9Why does MLDR take so much longer than everything else?▾
Its safety argument needs nested ∀∃ quorum properties inferred from counterexample states that typically expose only a few concrete node configurations at a time — hard for the LLM to generalize correctly on the first few tries. It's also the most expensive to verify: a single inductiveness check can exceed 5 minutes, so verification cost alone consumes a large share of the 4,525-second run.
Q10Could this same "LLM proposes, symbolic controller decides" recipe apply outside distributed consensus — say, to memory-tiering or CXL-coherence protocols?▾
The paper doesn't claim this, but the shape of the argument transfers: IC3's frame-based over-approximation plus a checked completeness backstop is domain-agnostic, and a concurrent tier-migration or CXL directory-coherence protocol is itself a transition system with the same "prove no two roles collide" structure as leader election or quorum overlap. This is the author's framing for this specific reader, not a result from the paper.
Q11Is I3DP's result vulnerable to LLM memorization of public benchmark solutions?▾
The paper checks this directly for MLDR: I3DP's discovered invariant is a 7-clause version, while the publicly available reference invariant has 5 clauses, and the key four-quantifier clauses differ substantially between the two — neither implies the other. This suggests the LLM is synthesizing from IC3-gathered counterexample information rather than recalling a memorized solution, though the paper is careful to note this only partially alleviates the concern.

Glossary & further reading

Every term in one place, then provenance and a path to go deeper.

Core terms
I3DPThe paper's neuro-symbolic tool: an IC3 controller with LLM-generated blocking clauses, synthesizing inductive invariants for TLA+ protocols.
Inductive invariantA predicate holding in Init, preserved by every Next transition, and implying Safety — the target artifact of the whole synthesis process.
IC3 / PDRProperty-Directed Reachability — proves safety by building a sequence of frames F₀⊆F₁⊆... that over-approximate bounded-step reachability.
Frame (Fᵢ)An over-approximation of states reachable within i transitions; strengthened over time by admitted blocking clauses.
Frontier / frontier queryThe deepest current frame; querying it for a state that can step to a Safety violation.
Backward predecessor searchWalking a bad state back through shallower frames until it either reaches Init (real counterexample) or a level with no predecessor.
Predecessor-free stateA bad state with no predecessor in the shallower frame — the trigger for clause learning.
Blocking clauseA learned predicate excluding a bad state from a frame, admitted only if it holds in Init and is inductive relative to that frame.
clauseMemoryThe global pool of all filtered blocking clauses, retained across the run so later bad states can reuse previously validated clauses without a new LLM call.
FixpointThe point where two adjacent frames become equal; their shared formula is the candidate inductive invariant.
Completeness backstop / aggregate blockerThe exact fallback clause (negation of all known bad states) admitted when no LLM-guided clause suffices — guarantees termination on the finite instance.
Supporting terms
TLA+ / Init / Next / SafetyLamport's specification language; the initial-state predicate, transition relation, and target safety property of a protocol spec.
CTICounterexample to Induction — a state showing a candidate invariant is not yet preserved by some transition.
TLCExplicit-state TLA+ model checker; used here to batch-screen candidate clauses against concrete reachable states.
ApalacheSymbolic, SMT-based TLA+ model checker; used here for all IC3 witness queries (frontier, predecessor, admission, push).
SANYThe TLA+ syntax checker/parser used to validate LLM-generated clauses are syntactically well-formed before filtering.
TLAPSThe TLA+ Proof System — mechanically proves a discovered invariant inductive for the unbounded protocol.
EPREffectively Propositional Reasoning — a decidable first-order fragment; Ivy/mypyvy-based baseline tools (IC3PO, SWISS, DuoAI, P-FOL-IC3) each require some decidable fragment, of which EPR is the best-known example.
MLDRMongoLoglessDynamicRaft — the industrial-scale Raft reconfiguration benchmark; I3DP's hardest case and the only one no baseline solves.
Marginal quorum propertyThe paper's nested ∀∃ clause type in MLDR: for any two servers, every quorum has a witness node that is at least as current or runs a newer config.
