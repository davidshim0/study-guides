Prefetching the address you'll need two loop levels from now

Graph and sparse-matrix code chases pointers through pointers. Existing software prefetchers only look as far as the current loop's boundary — Magellan reads the whole nested-loop skeleton instead, and prefetches across it.

📄 "Magellan: A High-Performance Loop-Guided Prefetcher for IMA" · Fu, Xia, Yin, Nair, Lis, Ren 🎓 Assumes caches, LRU, and prefetching basics — primers cover only what's IMA-specific ⏱ ~30 min read
🧭

Before you begin

What's actually new here

You already know caches, prefetching, and LRU. This paper's novelty is entirely about indirect memory access and how to read its shape out of nested loops at compile time. Eight primers, collapsed — open what's unfamiliar.

Quick glossary — the acronyms you'll see everywhere

IMAIndirect Memory Access — a load whose address comes from another array's value: x[a[i]].
LDGLoop Dependence Graph — Magellan's directed graph of load/induction-variable dependencies across nested loop levels.
SFISoftware Fault Isolation — the classic bounds-check-every-access safety technique Magellan deliberately avoids.
GEPGetElementPtr — the LLVM IR instruction that computes an array-element address from a base pointer and offset.
ROBReorder Buffer — bounds how far a mispredicted-path load can speculatively execute; sizes Magellan's safety margin.
DMP / IMPDifferential-Matching / Indirect Memory Prefetcher — the strongest hardware IMA prefetchers Magellan is benchmarked against.
Magellan (the prefetcher) SW Prefetch (the closest rival) LDG / detection machinery naive baselines (SFI, hardware prefetchers)
1Local vs. global indirection — the paper's core vocabulary▾

An IMA involves an index array a[] and a target array x[]. Local indirection fetches one element per index: x[a[i]]. Global indirection uses the index as a base address and fetches several consecutive elements offset by an inner-loop variable: x[a[i]+j].

Real code combines both: outer loop picks a node, offset=a[i] is a global IMA giving that node's edge range, and each x[offset+j] load inside is local.

Now you're ready: BFS's Edgelist[Worklist[...]] access is global (depends on an outer-loop value as base); its Visited[Neighbor] access is local. Magellan needs to tell these apart to prefetch correctly.
2Why SW Prefetch (the 2019 baseline) falls short▾

SW Prefetch [Ainsworth & Jones] walks backward from a load through its source operands to find loop induction variables, then prefetches index + ahead_distance — but only within the current inner loop. It stops the moment the dependency chain crosses into an outer-loop variable.

On sparse graphs, inner loops are short (few neighbors per vertex), so j+32 routinely overshoots the loop bound and gets clamped to the boundary — the same address, prefetched redundantly, over and over.

Now you're ready: the paper measures this precisely — 85.3% of SW Prefetch's BFS prefetch indices are clamped. Magellan's entire design is a response to this one failure mode.
3The Loop Dependence Graph (LDG)▾

A directed graph where each node is a load instruction or a loop induction variable, and an edge a→b means b is data-dependent on a. Unlike a plain use-def chain confined to one loop, the LDG explicitly links induction variables across loop levels — so it can see that an inner-loop bound depends on an outer-loop load.

Now you're ready: traversing the LDG is how Magellan classifies a load as local (depends only on same-level things) or global (depends on an outer-loop load/induction variable) — mechanically, not heuristically.
4Three nested-loop patterns: stream-in, stream-out, irregular▾

Once an IMA is inside a nested loop, Magellan asks: how does the outer loop's direction relate to the inner loop's? Stream-in — same direction, inner index moves continuously across outer iterations (row-by-row matrix traversal). Stream-out — opposite direction (a reverse triangular solve). Irregular — the outer loop's direction isn't fixed at all (worklist-driven graph traversal, e.g. BFS).

Now you're ready: this classification is the whole reason Magellan needs four different prefetch strategies rather than one — each pattern makes a different kind of future address predictable.
5Four prefetch strategies, one core trade-off▾

Inner-bound (stay inside the current loop, bounds-checked — high instruction cost), inner-free (prefetch unconditionally past the bound, catching the next loop too — medium cost), outer (insert the prefetch in the outer loop body, for the whole next inner loop at once — low cost), and opposite inner-free (inner-free run in reverse, for stream-out).

Every strategy trades prefetch coverage against extra executed instructions — there is no free strategy, only a best fit per pattern.

Now you're ready: Magellan's compiler pass is essentially "classify the pattern, then look up the strategy" — see the mapping table in How It Works.
6Why this needs a compiler pass, not a runtime detector▾

Magellan is an LLVM IR pass: it statically analyzes the source (backward dependency search, loop bound comparison) and inserts new prefetch instructions into the binary — no new hardware, no runtime pattern learner. The trade-off is the mirror image of hardware IMA prefetchers (IMP, DMP): those adapt at runtime with custom logic and area cost; Magellan commits to a strategy at compile time for zero hardware cost.

Now you're ready: this is why the headline comparison in the paper is "matches the best hardware prefetcher, with none of its area."
7The safety problem: prefetching can crash the program▾

A prefetch instruction is architecturally a no-fault hint. But computing its address (x[a[j+32]]) requires first loading a[j+32] — a real, faulting load. If j+32 runs past the end of array a, that's an out-of-bounds access.

The standard fix, Software Fault Isolation, bounds-checks every such load — and the paper measures this costing 31% more instructions and a 28% slowdown on SpMV. Magellan avoids this entirely (primer 8).

Now you're ready: "ensuring safe prefetches without sacrificing performance" is listed as a first-class contribution, not an afterthought — this is a real correctness constraint, not a hardware-safe hint.
8Magellan's fix: pad the allocation instead of checking the address▾

Instead of checking every prefetch address at runtime, Magellan statically finds the malloc/calloc call that allocated the prefetched array (by walking backward through the GEP's base-address operand) and enlarges that one allocation by prefetch_distance + ROB_size. Now every possible prefetch index — including ones down a mispredicted branch — lands in valid, allocated memory.

Now you're ready: this only works when the allocation site is staticaly traceable; externally-allocated or heavily-aliased arrays fall back to no optimization, trading some coverage for a guarantee of correctness.
The whole story in one place

Magellan in a nutshell

The failure mode it fixes, the two mechanisms that fix it, and how they connect.

Sparse and graph workloads live on indirect memory access: x[a[i]]-style loads whose addresses are only known once a[i] itself has been read. These addresses are effectively random with respect to the target array, so they miss the cache constantly, and neither next-line/stride hardware prefetchers nor prior software prefetchers cover them well.

The prior software approach, SW Prefetch, only looks as far as the boundary of the loop it's currently in. That's fatal for sparse graphs: inner loops (a vertex's neighbor list) are often just a few iterations long, so the prefetch's look-ahead distance routinely overshoots the loop and gets clamped — wasting the prefetch on a redundant address, 85.3% of the time on BFS.

Magellan's fix has two parts. First, it builds a Loop Dependence Graph (LDG) that tracks load/induction-variable dependencies across loop levels, so it can classify each IMA as local or global and each nested loop as stream-in, stream-out, or irregular — the actual shape of the access pattern. Second, it maps each shape to a tailored prefetch strategy that reaches past the current loop's boundary into the next one (or the current one's later iterations), instead of stopping at the fence SW Prefetch stops at.

A separate mechanism keeps this safe without runtime bounds checks: Magellan statically extends the allocation of any array a prefetch load might overrun, so every possible prefetch address — even down a mispredicted branch — stays in valid memory, at a measured cost of 0.0036% extra storage.

The payoff: across 14 memory-intensive benchmarks, Magellan cuts cache misses by 25% and dynamic instructions by 14% versus the best existing software prefetcher, for a 1.14× average speedup (up to 1.41×) — matching the best hardware IMA prefetcher's benefit with zero added silicon.

🍯 Key takeaways

  • SW Prefetch's failure is structural: it can't see past the loop it's in, and sparse inner loops are short.
  • Magellan's LDG traces dependencies across loop levels — this is what lets it detect global IMAs at all.
  • Nested-loop shape (stream-in / stream-out / irregular) determines which of four prefetch strategies applies.
  • Safety comes from extending allocations, not bounds-checking every access — near-zero overhead vs. SFI's 28% slowdown.
  • Result: 25% fewer misses, 14% fewer instructions, 1.14× avg speedup vs. the best software rival; on par with the best hardware prefetcher, at zero hardware cost.
Six everyday pictures

How to think about Magellan

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core failure · Loop-bound myopia

Reading a map that stops at the page edge

SW Prefetch is a driver reading a paper map: perfectly accurate for the road on this page, but the map simply ends at the page border — there's no hint of what's on the next sheet. When the "page" (inner loop) is short, the driver is constantly told "off the map" and just re-reads the last visible point. Magellan tapes the pages together first (the LDG), so the route continues seamlessly onto the next one.

Where it breaks: a real map's next page is fixed in advance; which "page" (loop iteration) comes next in an irregular pattern like BFS is only known at runtime — Magellan predicts the shape of the next page, not its exact contents.
Detection · Local vs global IMA

A store clerk vs. a delivery dispatcher

A local IMA is a store clerk fetching one item you named. A global IMA is a dispatcher: you give an address, and dispatcher hands you a whole range of items starting there, indexed by a separate running counter. The dispatcher's job (global IMA) can't be understood by watching one clerk transaction (a single-loop backward search) — you need to see where the "starting address" instruction actually came from, possibly a level up.

Where it breaks: real dispatchers know their range in advance; Magellan must derive the range (the inner loop's trip count) separately from the base address itself — they come from different LDG edges.
Classification · Stream-in vs stream-out

An escalator going the same way as the crowd — or against it

Stream-in is an escalator moving the same direction as the foot traffic beside it: momentum carries forward smoothly, so predicting the next step is easy in the forward direction. Stream-out is the same escalator running the opposite way to a crowd walking past it: still perfectly predictable, but the prefetch logic has to flip its arithmetic to match the reversed direction, or it points the wrong way entirely.

Where it breaks: escalators never change direction mid-ride; some workloads (SYMGS) genuinely reverse direction between algorithm phases, which is why Magellan re-detects the pattern rather than assuming it's fixed for the whole program.
Irregular pattern · Worklist-driven traversal

A tour guide with no fixed itinerary

Most tour guides (stream-in/out) follow a route you could predict from the map. A worklist-driven guide instead visits whichever site got added to today's list last — determined dynamically by which sites earlier visitors flagged as interesting. You can't predict the next stop from direction alone, so the best you can do is prefetch for "wherever the very next stop turns out to be," which means moving the prefetch to the outer loop, right where that decision gets made.

Where it breaks: a real irregular tour has no exploitable structure at all; BFS's irregularity is bounded — it's still one hop away in the worklist, which is exactly what outer prefetching exploits.
Safety · Extending allocations vs. SFI

A guardrail along the whole road vs. a toll booth every mile

SFI is a toll booth at every mile marker, stopping traffic to check each car's papers — safe, but the delay adds up (measured: 31% more instructions, 28% slower). Magellan instead builds the guardrail a little farther out along the whole road before anyone drives it, so no car can ever leave the pavement — a one-time cost paid once, at compile/allocation time, not on every trip.

Where it breaks: guardrails work because the road's shoulder is knowable in advance; Magellan's version only works when it can statically trace the array back to its malloc — externally allocated or heavily aliased arrays don't get a guardrail and fall back to no optimization.
Design point · Software vs hardware prefetching

A tailor's alterations vs. a custom-built suit

A hardware IMA prefetcher (DMP, IMP) is a custom-built suit: fits its target patterns exactly, but takes real fabric (chip area) that's wasted on every program that isn't wearing it. Magellan is a skilled tailor altering an off-the-rack suit (an ordinary CPU) at compile time — no extra fabric bought, ready for whichever program shows up next, and the paper measures it fitting nearly as well as the custom suit (1.7× vs 1.8× average speedup).

Where it breaks: a tailor can only alter what the source code exposes; a truly runtime-discovered pattern with no loop structure in the IR (e.g. through an opaque library call) has no seam for Magellan to alter at all.
The full explanation

How it actually works

Four phases, in the order Magellan's compiler pass runs them.

1 · IMA detection via the Loop Dependence Graph

For each load inside a loop, Magellan recursively walks its source operands backward (skipping calls, stores, terminators) until it hits either another load or an induction variable — building a dependency chain. It separately walks the loop's induction variable back to its phi-incoming value, which surfaces any loop-carried dependency on an outer loop. All these chains are unified into the LDG.

Classifying a load is then a graph query: if it depends only on same-level loads/variables, it's local; if its chain reaches an outer-loop load or induction variable, it's global.

2 · Nested-loop pattern detection (3 steps)

  1. Locate the inner loop's induction variable and read its preheader (initial value) and latch (bound value) expressions.
  2. Unroll the inner loop twice and compare the first iteration's preheader to the second iteration's latch. If they don't match, the inner bounds shift unpredictably between outer iterations — classify as irregular.
  3. If they match, check the outer loop's iteration condition: incrementing → stream-in; decrementing → stream-out.
💡
Why this works: stream-in/out both have an inner loop whose bounds are a clean function of the outer index (ptr[i]…ptr[i+1]) — so the preheader/latch pair repeats predictably. BFS's Offset loop matches this cleanly even though the outer traversal order (which vertex is visited next) is irregular — that irregularity lives one level higher, in which the outer-loop pattern is classified separately.

3 · Prefetch strategy selection

Each pattern gets the strategy that best balances prefetch coverage against instruction overhead:

PatternStrategyPrefetch scopeOverhead
stream-ininner-freecurrent + future inner loopmedium
stream-outopposite inner-freecurrent + future (reverse direction)medium
irregular (small trip count)outerfuture loop only, issued in outer looplow
irregular (large trip count)inner-boundcurrent loop only, bounds-checkedhigh
 
// stream-in: inner-free — prefetch j+32 unconditionally, no bound check
for (i=0;i<size;i++){
  start,end = ptr[i], ptr[i+1];
  for (j=start;j<end;j++){
    load(x[a[j]]);
    pref_j = j+32;                    // deliberately unchecked
    prefetch(x[a[pref_j]]);           // safe: allocation was pre-extended
  }
}
🌱
Removing the bound check (vs. SW Prefetch's min(j+32,end)) is exactly what fixes the 85.3%-clamped problem — but it's only safe because of the allocation-extension mechanism in step 4.

4 · Fault avoidance — extend the allocation, not the runtime check

Magellan locates the memory-allocation call behind any array a prefetch might overrun, by tracing a GEP's base-address operand backward through bitcasts and call arguments to a malloc/calloc site (using LLVM's AliasSetTracker and DominatorTreeAnalysis for harder aliasing cases), then rewrites that call's size parameter:

alloc_size += prefetch_distance + rob_size
// prefetch_distance = 32 (look-ahead), rob_size = 224 (Kabylake) / 168 (Sandy Bridge)
// covers both correctly-predicted and mispredicted-path speculative loads
⚠
Falls back safely when it can't be sure. If the allocation site is external, or the pointer is ambiguously aliased across multiple malloc calls, Magellan skips the optimization for that array rather than guess — correctness over coverage.
Follow the numbers, step by step

Worked examples

Four traces using the paper's real measurements.

① Why 85.3% of SW Prefetch's BFS prefetches are wasted

BFS's inner loop runs from j=start to end, where range=end-start is a vertex's degree. SW Prefetch computes pref_j = min(j+32, range). Real web/social graphs have many low-degree vertices — say range=6.

  1. At j=0: j+32=32, but range=6, so pref_j = min(32,6) = 6 — clamped to the boundary.
  2. At j=1,2,3,4,5: same clamp — every iteration of this inner loop computes the identical pref_j=6.
  3. Result: instead of 6 distinct useful prefetches, SW Prefetch issues 6 identical prefetches for Visited[Edgelist[start+6]] — one address, six times.
  4. Measured across the whole benchmark: this clamping happens in 85.3% of cases — the paper's headline number for why SW Prefetch underperforms on sparse graphs.
🍯
Insight: the bug isn't in the prefetch distance choice — it's structural. Any fixed look-ahead distance will overshoot short loops; the fix has to reach into the next loop, which requires seeing across the loop boundary (the LDG).

② Classifying SpMV's loop with the 3-step detector

SpMV's kernel: for(i=0;i<row;i++) for(j=ptr[i]; j<ptr[i+1]; j++) y[j]+=x[a[j]].

  1. Step 1: inner induction variable j; preheader = ptr[i], latch = ptr[i+1].
  2. Step 2: unroll twice — iteration i's preheader is ptr[i]; iteration i+1's latch is ptr[i+2]. Compare iteration i+1's preheader (ptr[i+1]) to iteration i's latch (ptr[i+1]) — they match (both ptr[i+1]).
  3. Step 3: outer loop condition i<row; i++ is incremental → classified stream-in.
  4. Strategy chosen: inner-free — prefetch x[a[j+32]] unconditionally, catching both later iterations of this row and the start of the next row.
💡
This is exactly why SpMV, PageRank, CC, and DC (all row-by-row / stream-in) see the largest gains — an average 1.2× geomean, up to 1.4× — over the baseline: the pattern is the easiest case to exploit fully.

③ Sizing the safety net — the 0.0036% storage claim

The paper reports an average extended-allocation cost of 1486 bytes per application, equal to 0.0036% of that application's total memory footprint. How large is the typical dataset implied by that ratio?

  1. Set up the ratio: 1486 B ÷ (total memory) = 0.0036% = 0.000036.
  2. Solve for total memory: total memory = 1486 ÷ 0.000036 ≈ 41.3 million bytes ≈ 41 MB.
  3. Sanity check against Table 1: Kabylake's L3 is 6 MB, Sandy Bridge's is 40 MB — a ~41 MB average dataset is comfortably larger than even the bigger LLC, confirming these are genuinely LLC-busting sparse workloads, not something that would fit in cache anyway.
  4. Why the padding itself stays small: the extension is prefetch_distance (32) + ROB_size (≤224) elements, times at most 13 distinct IMAs (bc's worst case) — a few hundred extra elements against a multi-million-element array.
🍯
Insight: the safety mechanism's cost scales with ROB size and prefetch distance, not with dataset size — so it stays negligible precisely because sparse datasets are large, which is also why they miss the cache in the first place.

④ Stacking the wins: from naive prefetch to full Magellan

The paper's ablation (§5.10) isolates two optimizations on top of a naive prefetch insertion: removing bound checks, then adding global-IMA prefetching.

  1. Naive prefetch insertion (bound-checked, local IMA only): limited speedup, and for spmv actually a slowdown — the added instructions cost more than the misses they save.
  2. Remove bound checks: +11% performance, by cutting the compare-and-clamp instructions and letting more prefetches actually reach ahead.
  3. Add global-IMA prefetching on top: a further +15% for graph applications, by covering the Edgelist-style accesses local-only detection misses entirely.
  4. Compounding: 1.11 × 1.15 ≈ 1.28× from these two optimizations alone — most of the way to Magellan's full reported 1.14–1.2× (the remainder comes from strategy selection and the LDG's pattern-specific tuning).
🌱
Every one of Magellan's mechanisms earns its keep individually — none of them alone gets you to the full result, which is why the paper reports this as a staged ablation rather than a single "it works" number.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
A vertex has degree 40 (its neighbor list has 40 entries). Would SW Prefetch's j+32 look-ahead get clamped for this vertex?
Show answer
Rarely — only for j > 8 (since j+32>40 requires j>8), so most of the loop's 40 iterations prefetch a genuinely distinct, useful address. The clamping problem is specific to low-degree vertices, which dominate real social/web graphs (most vertices have few neighbors) — not high-degree ones.Misconception: that SW Prefetch is broken everywhere. It's broken specifically where sparse graphs concentrate most of their vertices — short inner loops — which is why the 85.3% figure is so damaging in aggregate.
Problem 2 · medium
A load's dependency chain, walked backward, terminates at another load from the same loop level. Is this a local or global IMA? What if it terminates at an induction variable of the outer loop instead?
Show answer
Terminating at a same-level load → local IMA (e.g. Visited[Neighbor], where Neighbor comes from the same inner loop). Terminating at an outer-loop induction variable or load → global IMA (e.g. Edgelist[Worklist[start_pointer]]). The LDG's cross-level edges are exactly what let this distinction be made mechanically.Misconception: that "global" means "accesses a global variable." It means the address chain crosses a loop-level boundary — nothing to do with variable scope.
Problem 3 · medium
Using the 3-step detector: an inner loop's preheader/latch match across unrolled iterations, and the outer loop's condition is for(i=size; i>0; i--). What pattern, and what strategy follows?
Show answer
Matching preheader/latch rules out irregular. The outer condition is decremental → stream-out. Strategy: opposite inner-free — prefetch is issued in the reverse direction so that overshooting the current inner loop's bound correctly lands in the previous (not next) row, matching the outer loop's backward traversal.Misconception: that "stream-in" and "stream-out" only differ in which way you count — they require different prefetch-index arithmetic, because a forward-looking prefetch computed the normal way would point at already-visited data.
Problem 4 · hard
Could increasing SW Prefetch's look-ahead distance from 32 to, say, 128 fix its problem on BFS's Edgelist access specifically?
Show answer
No. Edgelist's address doesn't depend on the inner-loop variable j at all in the way SW Prefetch assumes — it's a global IMA, whose base address depends on the outer-loop's Worklist[start_pointer]. SW Prefetch's backward search never reaches that dependency because it halts at the current loop's boundary, regardless of look-ahead distance. This isn't a tuning problem, it's a detection-scope problem — only an LDG that spans loop levels fixes it.Misconception: that SW Prefetch's limitation is a tunable parameter (distance). It's structural: the search itself never looks at the right instruction.
Problem 5 · medium
Why does Magellan extend the allocation size rather than just skip the prefetch when j+pref_d would exceed the array bound?
Show answer
Skipping would require a runtime check on every prefetch — exactly the SFI-style overhead (measured at 31% more instructions, 28% slower on SpMV) Magellan is trying to avoid. Extending the allocation once, at allocation time, makes every possible index — including on mispredicted branches — land in valid memory, so the prefetch instruction never needs a guard at all.Misconception: that "avoiding a crash" and "avoiding a bounds check" are the same choice. Magellan achieves the first without paying for the second by moving the fix from access-time to allocation-time.
Problem 6 · hard
Magellan's allocation-extension trick only applies "when the memory allocation site... can be precisely identified and safely extended." Name two concrete situations where it can't, and what happens then.
Show answer
(1) The array is allocated in a different translation unit or passed in externally (linkage marks the function as externally callable, or the variable as external) — Magellan can't see or rewrite the allocation call. (2) The pointer is aliased through multiple potential malloc sites that AliasSetTracker/dominator analysis can't disambiguate statically — e.g. conditional aliasing on a runtime branch. In both cases Magellan skips the optimization for that array, preserving correctness at the cost of losing prefetch coverage for it.Misconception: that Magellan's safety guarantee is unconditional. It is conditional on static traceability — this is a deliberate "no-opt on doubt" policy, not a gap in the design.
Problem 7 · medium
Magellan is described as "on par with" the best hardware IMA prefetcher (DMP) rather than beating it (1.7× vs. 1.8× average). Why is this framed as a win for Magellan?
Show answer
Because the comparison isn't apples-to-apples in cost: DMP requires dedicated custom logic and chip area on every core, permanently, whether or not the workload ever uses IMA. Magellan gets essentially the same benefit purely through a compiler pass — zero hardware cost, deployable on existing commercial CPUs today. "On par in performance, free in hardware" is the actual claim, not "faster than."Misconception: that a software prefetcher not beating the best hardware prefetcher outright is a weakness. Given the near-zero marginal cost of software prefetching, matching hardware performance is itself the headline result.
Problem 8 · easy
Triangle Counting (TC) gets only a 1.06× speedup from Magellan, far below SpMV's 1.2–1.4×. Given VTune shows only 15% of TC's pipeline slots are memory-latency-bound, is this a failure of Magellan's detection or strategy selection?
Show answer
Neither — it's a ceiling problem, not a detection problem. If only 15% of TC's execution time is even attributable to memory latency, no prefetcher (however perfect) can improve more than that 15% ceiling. TC has good data locality and reuse, making it compute-bound rather than memory-bound; Magellan's IMA detection may work fine, there's just little latency left to hide.Misconception: that a memory-intensive-looking application (lots of indirect array accesses in the source) is automatically memory-latency-bound in practice. Locality and reuse can make the same code pattern compute-bound instead.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly makes an access "indirect"?▾
The address used to load from array x is itself the valuea: x[a[i]]. Because a[i]'s value can be almost anything (a vertex ID, a matrix column index), the resulting address into x has little spatial or temporal locality — the defining pain point IMA prefetchers target.
Q2Why can't a generic hardware prefetcher (stride, next-line) handle this?▾
Those prefetchers predict the next address from a simple arithmetic pattern in the address stream itself (constant stride, sequential lines). IMA addresses are essentially random with respect to the target array — there's no arithmetic regularity in the stream of x[a[i]] addresses to extrapolate from, only in the index computation that produced them, which lives in the source code, not the memory trace.
Q3How is the LDG different from a normal compiler dependence graph?▾
A standard use-def or data-dependence graph is typically scoped to a single loop or basic block. The LDG's specific job is unifying dependency chains across nested loop levels — connecting an inner-loop load's operand back through the outer loop's induction variable — which is exactly the piece SW Prefetch's single-loop backward search is missing.
Q4Why does Magellan need three separate nested-loop categories instead of one universal strategy?▾
Because each category makes a different kind of future address predictable in a different way. Stream-in and stream-out need arithmetic that runs in opposite directions; irregular loops have no exploitable arithmetic at all across outer iterations, so the only lever left is issuing the prefetch earlier (in the outer loop) rather than computing it differently. One-size-fits-all would either waste instructions or miss opportunities.
Q5Isn't inserting a prefetch in the outer loop for an irregular pattern risky, since you don't know the next iteration's target yet?▾
Not as risky as it sounds: BFS-style irregular loops are still driven by a worklist that's already been populated one step ahead (e.g. Worklist[end_pointer] was just written). Outer prefetching exploits the fact that the next node to process is already knowable from that structure, even though the overall visitation order isn't predictable arithmetically.
Q6Does extending allocations waste much memory?▾
Measured average: 1486 bytes per application, about 0.0036% of that application's total memory footprint — negligible because sparse datasets are themselves large (tens of MB or more), while the padding only needs to cover prefetch_distance + ROB_size, a few hundred elements at most.
Q7Why does BC (Betweenness Centrality) sometimes see Magellan underperform?▾
BC has 13 distinct indirection loads per traversal — the most of any benchmark tested — so inserted prefetches for different loads can interfere with each other's memory requests, and Magellan's static, compile-time scheduling can't adapt to which of those 13 turns out to matter most at runtime. The paper flags this as a case for future dynamic, feedback-based tuning.
Q8Does Magellan replace hardware prefetchers, or work alongside them?▾
Alongside. Hardware prefetchers (next-line, stride) are left running and catch the regular/streaming accesses Magellan doesn't target; Magellan handles the irregular indirect ones. Enabling both together improves performance a further 1.13× on average over Magellan alone, because the two cover complementary access patterns.
Q9Why is the outer-prefetching degree fixed at 1 instead of tuned per application?▾
The paper measured up to a 40% performance gap across degree settings, and found most workloads peak at degree 1 (one node's worth of look-ahead); a few (e.g. sssp on com-LiveJournal) peak at degree 4, but the average trade-off across all tested graphs and machines favors degree 1 as the single, non-tuned default — simplicity over squeezing out the last few percent on select cases.
Q10How does Magellan compare to profile-guided software prefetchers like APT-GET?▾
APT-GET profiles the program first (minutes of profiling, then recompiles with tuned prefetch parameters) and beats plain SW Prefetch by 1.13× on average. Magellan, using purely static loop-structure analysis with no profiling step, still outperforms APT-GET by a further 1.14× — the paper notes APT-GET's profile-guided tuning could in principle be layered on top of Magellan for additional gains.
Q11Does Magellan keep helping as core count increases?▾
Up to a point. SpMV shows nearly 7.2× speedup at 8 cores vs. 1 core, but scaling degrades by 16 cores because DRAM bandwidth contention starts dominating — more cores competing for the same memory channels means each core's prefetches face longer latencies and more interference. The authors note adaptively throttling prefetch aggressiveness at high core counts as future work.
Q12What's the biggest limitation the paper acknowledges?▾
Everything is decided statically at compile time — there's no runtime feedback loop. This shows up concretely in BC (static scheduling can't adapt to which of 13 IMAs matters most at runtime) and in scalability (no adaptive throttling under bandwidth pressure at high core counts). The paper positions a dynamic, feedback-based extension as the natural next step.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
IMA (Indirect Memory Access)A load whose address is itself the value read from another array: x[a[i]]. The paper's central object of study.
Local IMAAn IMA that fetches one element per index value, entirely within one loop level, e.g. x[a[i]].
Global IMAAn IMA that uses an outer-loop-derived value as a base address, offset by an inner-loop variable: x[a[i]+j].
Loop Dependence Graph (LDG)Magellan's directed graph of load/induction-variable dependencies spanning multiple nested loop levels — what lets it detect global IMAs.
Nested-loop patternStream-in, stream-out, or irregular — classifies how an outer loop's direction relates to its inner loop's, determining the prefetch strategy.
Inner-bound / inner-free / outer / opposite inner-freeMagellan's four prefetch strategies, each matched to one nested-loop pattern, trading prefetch coverage against instruction overhead.
Fault avoidance (allocation extension)Statically enlarging an array's allocation by prefetch_distance + ROB_size so every possible prefetch address stays valid, without runtime bounds checks.
Supporting terms
SFI (Software Fault Isolation)Bounds-checking every memory access explicitly. Measured cost: 31% more instructions, 28% slowdown on SpMV — the baseline Magellan's allocation trick avoids.
GEP (GetElementPtr)The LLVM IR instruction computing an element address from a base pointer + offset; Magellan traces its base-address operand back to a malloc/calloc site.
ROB (Reorder Buffer)Bounds how far speculative execution down a mispredicted branch can go; sizes the extra safety margin Magellan adds to an allocation (224 on Kabylake, 168 on Sandy Bridge).
Preheader / latchA loop's entry value and exit-condition value for its induction variable — compared across unrolled iterations to detect the nested-loop pattern.
AliasSetTracker / Dominator Tree AnalysisLLVM analyses Magellan uses to track pointer aliasing and find the last store before a prefetched load, when the allocation site isn't immediately obvious.
SW PrefetchAinsworth & Jones's 2019 compiler prefetcher for IMA — the closest prior software approach, limited to the current inner loop (inner-bound prefetching).
APT-GETA profile-guided software prefetcher using outer prefetching, tuned via runtime profiling; beats SW Prefetch by 1.13× but is itself outperformed by Magellan.
DMP / IMP / Berti / IPCP / Event-triggerHardware (and one software-hardware co-designed) IMA/spatial prefetchers Magellan is benchmarked against on gem5; DMP is the strongest.
