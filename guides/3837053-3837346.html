HotStorage '26 · A Field Guide

Every time you read DNA, you spend it

DNA storage promises exabyte density and centuries of durability — but the read operation itself degrades the medium. This is the plain-English tour of the first system model that takes that seriously.

📄 "Towards A System Model for DNA-based Storage" · Schustermann et al. 🎓 No biology background assumed — primers cover it ⏱ ~20 min read
🧬

Reading a DNA pool hydrates it (durability starts decaying) and spends a slice of its fixed read budget — so a storage system must treat reads as a scarce, decaying resource, not a free operation.

Before you begin

Quick glossary + eight ideas the paper assumes

Skim the glossary first, then open whichever primer cards are unfamiliar.

Quick glossary
PoolA small dry container holding many DNA strands from many objects — the unit of DNA storage.
PrimerA short address sequence appended to an object's strands; PCR uses it to selectively pull one object out of a pool.
PCRPolymerase Chain Reaction — replicates strands so a sample can be read; each cycle adds errors.
Hydrated / DryDry = stable powder form. Hydrated = dissolved in solution after a read; decays in years, not centuries.
ExpendedA pool that has hit its read limit — its objects can no longer be retrieved.
Endangered objectAn object whose every replica's pool is expended — unrecoverable without prior replenishment.
ReplenishRe-synthesizing a pool's objects (via bulk-read or reserved read budget) before it's lost.
Zipf / Zipf-poolSkewed-popularity workloads: Zipf skews objects; Zipf-pool skews which pool is hit, plus skew inside it.
r-pool / r-hash / CopysetsThree replication schemes compared in §4 — replicate whole pools, replicate objects across independent hash-picked pools, or group pools into fixed copysets.
1The DNA storage pipeline▾

Binary data is encoded into DNA bases, synthesized into physical strands, stored dry, later sequenced (read) and decoded back to bits. Synthesis and sequencing are both error-prone, so encoding schemes build in heavy redundancy.

Now you're ready: the paper's model sits above this pipeline — it doesn't touch the biology, only the system-level consequences of reading.
2Pools and primers set the read granularity▾

Many objects' strands live together in one pool; a primer lets PCR selectively amplify just one object's strands. The number of usable primers caps how many distinct objects a pool can hold — currently limiting pools to roughly 1 TB logical capacity, far below DNA's theoretical exabyte density.

Now you're ready: "max objects per pool" and "max logical pool capacity" are two of the model's three core parameters.
3Reads are destructive▾

Reading hydrates the dry pool, extracts a sample, and discards the processed portion. What remains is hydrated DNA — vulnerable, with durability dropping to just a few years even refrigerated. PCR can replicate the remainder, but each cycle adds errors, so eventually a pool becomes unreadable.

Now you're ready: this is why every pool has an effective read limit — the third core model parameter.
4Pool lifecycle: dry → hydrated → expended▾

A pool starts dry. Its first read makes it hydrated (decay clock starts). Repeated reads eventually expend its read limit; its objects become endangered unless replenished first, either by a bulk-read of the whole pool or by reserving part of its budget.

Now you're ready: the whole paper tracks three counts over time — hydrated pools, expended pools, and endangered objects.
5Why "load factor" and bucket overflow matter▾

Under uniform random access, reads landing on pools behave like inserting items into hash buckets: the ratio of requests to total read-limit budget is a load factor, and bucket-overflow statistics (Poisson) predict when pools get expended — small pools overflow (expend) sooner.

Now you're ready: this explains why pool size 100 shows much sharper expenditure than pool size 10,000 in the results.
6Skewed workloads: Zipf and Zipf-pool▾

Real archival access is rarely uniform. Zipf skews which objects get read; Zipf-pool additionally skews which pool is hit (modeling popularity-aware placement) and skews objects within that pool too.

Now you're ready: a surprise in the results is that "ideal" popularity-aware placement (Zipf-pool) does not reduce endangered objects versus plain Zipf.
7Replication as a design lever▾

r-pool replicates an entire pool r times (like buying more copies of the same book). r-hash replicates each object across r independently hash-chosen pools (classic datacenter load balancing). Copysets groups pools into fixed-size sets and only replicates within a group, bounding "blast radius."

Now you're ready: the paper shows these trade immediate object endangerment against long-term hydration/replenishment cost.
8Why this connects to your tiering work▾

Swap "hydrated" for "promoted/migrated hot page" and "expended" for "worn-out device" and the shape is familiar: a scarce, state-changing resource (reads) governs data placement, much like DRAM/NVM tiering trades access latency against migration cost and NVM endurance.

Now you're ready: keep this analogy loose — it's a framing device, not a claim from the paper (see Reference tab's Source notes).
The whole story in one place

A system model that treats reads as scarce

Three parameters, three tracked metrics, and the punchline for storage-system design.

DNA storage research is dominated by biologists and coding theorists pushing three knobs: how many objects a pool can address (primer count), how much logical capacity a pool holds (density), and how many times a pool can be read before it's unusable. The systems community has barely engaged with how a storage system built from many such pools should be managed.

This paper builds the first system model abstracted above the fast-changing biology: each pool is characterized by exactly those three parameters, and the model tracks three consequences of user reads — hydrated pools (durability now degrading), expended pools (read limit exhausted), and endangered objects (unrecoverable without prior replenishment). An event-based C simulator, run over Uniform/Zipf/Zipf-pool workloads with trivial LRU caching and random placement, turns these definitions into concrete numbers.

The punchline: current efforts to shrink strand length and grow primer libraries (raising density and object count) will not be enough on their own. Without a proportionate increase in read limit, efficient bulk retrieval for replenishment, and DNA-aware management policies, systems built from denser pools will simply expend and endanger data faster.

🍯 Key takeaways

  • Reads are destructive: they hydrate (degrade durability) and spend a finite read limit.
  • Larger pools resist expenditure but hydrate almost instantly and cost more to replenish.
  • Raising the read limit delays endangerment more effectively than raising pool capacity.
  • r-hash replication balances load well but spreads "blast radius" across more pools; copysets is a middle ground.
  • LRU caching, unaware of pool state, protects skewed (Zipf) workloads well but barely helps Uniform or "ideal" Zipf-pool placement.
  • Overall: DNA storage needs management policies aware of hydration and read-limit state — conventional digital-storage policies are blind to both.
Five everyday pictures

How to think about DNA pools

Each stands alone. Every card ends with where the picture stops being true.

Load factor · Bucket overflow

Hash buckets that fill up

Uniform reads landing on pools behave exactly like inserting keys into hash buckets. When requests ≈ total read budget (load factor 1), Poisson math says roughly half the buckets overflow — matching the paper's finding that ~50% of pools expend at that point.

Where it breaks: real archival access is rarely uniform. Under Zipf, a handful of buckets fill instantly from popularity alone, and the bucket-overflow math no longer applies cleanly.
Hydration · A one-way door

Opening a sealed jar

A dry pool is a sealed jar of preserves. Opening it (a read) lets air in — you can reseal it, but it's never as durable again. Every subsequent read draws from an already-opened jar whose contents spoil faster.

Where it breaks: a jar spoils passively over time; DNA also loses information actively on each PCR cycle used to re-read it, so "opening" and "reading again" both cost something, not just time.
Read limit · Wear-out

A rare book's photocopy limit

A fragile rare book can only be photocopied so many times before the pages degrade past legibility. Each copy is a PCR cycle; the "read limit" is how many copies the archive lets you make before the original is retired.

Where it breaks: a book degrades gradually and predictably; DNA's error accumulation is probabilistic and interacts with sequencing technology choice (cheap-but-noisy nanopore vs. accurate-but-costly Illumina), so the "limit" is really a reliability threshold, not a hard count.
Replication · Blast radius

One fire vs. many small fires

r-pool is one bigger fire station (more copies of the same building); r-hash is scattering your valuables across many neighbors' houses. r-hash balances load beautifully, but if a house burns (a pool expends), the "blast radius" — how many distinct pools now need attention — is much larger.

Where it breaks: in a datacenter, node failure is a probabilistic risk you might avoid entirely. In DNA, hydration begins decaying the moment a neighbor pool is touched — it's not probabilistic, it's immediate.
Caching · Blind to danger

A firefighter who only tracks call volume

An LRU cache keeps whatever's been requested most recently — like a firefighter who responds based purely on how often a street calls in, with no idea which specific houses are about to catch fire (about to be expended). It happens to protect popular objects well, but offers no protection to a cold object whose entire pool is close to its read limit.

Where it breaks: real firefighters do triage by risk; the paper's takeaway is precisely that a DNA-aware cache should do the same — but the baseline LRU studied here doesn't.
The full explanation

How the model and simulator work

From the three parameters, through the simulator's default policies, to what the experiments reveal.

1 · Three parameters capture the whole medium

Instead of modeling synthesis cost, sequencing throughput, or latency (all rapidly changing and hard to predict), the model abstracts each pool by exactly three numbers: max objects per pool (primer capacity), max logical pool capacity (density, from encoding/error-correction/strand length), and read limit (molecule stability and error-correction quality). Everything else — mapping objects to pools, object sizes — is simplified away for this first version.

2 · Default (deliberately naive) policies

PolicyDefault behavior
Object → pool placementrandom hash of object ID
Cachedurable digital media, managed by plain LRU
Uncached readread from a hydrated replica pool, else hydrate one
All replicas expendedobject marked endangered; future requests fail
🌱
These are intentionally trivial so the experiments isolate the medium's fundamental behavior, not the cleverness of any particular policy — a baseline for future DNA-aware policies to beat.

3 · Three tracked metrics ⇒ overall system cost

The simulator (C, event-based, 100M objects, 15M requests) logs three quantities over time as requests are served: hydrated pools (§ objects at risk, refrigeration cost rising), expended pools (read limit exhausted), and endangered objects (every replica's pool expended). Together with initial pool creation, these determine overall lifetime synthesis + sequencing cost.

4 · Pool size: a genuine trade-off, not a free win

Bigger pools resist expenditure under Uniform access (fewer, larger "buckets" overflow less often) — but they hydrate almost immediately, since any single read on a huge pool still hydrates the whole thing. And because read limit doesn't automatically scale with pool size (it's bounded by biology, currently a few hundred reads/pool), bigger pools mean proportionally more replenishment work per hydration event.

5 · Read limit: the more effective lever

Raising the read limit delays endangerment roughly proportionally — a 10× larger limit lets the system absorb about 10× more requests before reaching the same endangerment level. Unlike pool size, it doesn't trade off against hydration risk, making it, per the paper, a higher-leverage target for future DNA technology improvements.

6 · Replication: load-balancing vs. blast radius

r-pool (replicate whole pools) mainly helps skewed workloads modestly, since reads still concentrate. r-hash (replicate each object across independently hashed pools) balances load far better — each extra replica cuts endangered objects by roughly an order of magnitude under Uniform — but scatters each expended pool's fallout across many more pools, so more pools get hydrated. Copysets (group pools, replicate only within a group) sits between the two extremes.

7 · Caching helps skew, not uniformity — and it's blind

Because LRU has no notion of "this pool is close to its read limit," a small cache dramatically protects heavily skewed (Zipf) workloads — a handful of hot objects, once cached, each "shield" an entire pool from ever being expended — but does almost nothing for Uniform access, and only modestly helps the "ideal" Zipf-pool placement, since protecting a whole pool from expenditure requires caching nearly all of it.

Follow the numbers

Worked examples

Four traces through the paper's actual figures.

① Small pools expend fast under load factor 1

Pool size 100, read limit 10% (= 10 reads/pool), Uniform workload, 15M total requests over 100M objects.

  1. Load factor = requests served ÷ total read budget of all pools. At reqs = 10% of n, load factor ≈ 1.
  2. Like hash-bucket overflow at load factor 1: Figure 3 shows ≈50% of pools already expended at this point.
  3. At load factor 1.5 (reqs = 15%), expenditure climbs toward ≈100% of pools.
  4. Even earlier — reqs = 7% — more than 10% of objects are already endangered for pool size 100.
🍯
Insight: small pools behave exactly like small hash buckets — they overflow (expend) well before the "average" load factor would suggest.

② Most expended data was never even read

Compare "total endangered" objects to "read & endangered" objects (Figure 3).

  1. The paper reports the fraction of expended objects that were actually read before expenditure: <10% (Uniform), <8% (Zipf), <5% (Zipf-pool).
  2. So even in the best case (Uniform), >90% of an expended pool's content must still be sequenced from scratch for replenishment — it was never touched, just collaterally exhausted by reads to its pool-mates.
  3. This holds even if every object ever read were kept in cache forever — the gap is structural, not a caching shortfall.
💡
This is why the paper singles out efficient bulk retrieval as a first-class system need: replenishment isn't about re-fetching hot data, it's about recovering mostly-untouched data before it's gone.

③ Read limit trades off almost 1:1 against requests served

Pool size fixed at 1,000; compare read limits 1% and 10% (Figure 5).

  1. System state at limit = 1%, reqs = 0.1% ≈ system state at limit = 10%, reqs = 1%.
  2. Both the limit and the request count that produces the same endangerment level scaled by the same 10×.
  3. Pool hydration is unaffected by read limit — a pool hydrates on its first access regardless of how many reads it can tolerate.
🍯
Insight: raising the read limit buys proportional headroom on endangerment without changing hydration exposure — the cleanest lever in the model.

④ Replication: r-hash crushes endangerment, grows blast radius

Pool size 1,000, read limit 10%, comparing r-pool vs. r-hash (Figures 6–7).

  1. Under Uniform, going from r=1 to r=2 with r-hash almost eliminates object endangerment for the simulation's duration.
  2. Each additional r-hash replica reduces endangered objects by roughly an order of magnitude.
  3. But r-hash scatters an expended pool's objects across many other pools, so hydrating one of its replicas can trigger hydration of a much wider set of pools ("blast radius").
  4. Copysets (r=4, group size 16) lands between r-pool and r-hash on both endangerment and hydrated-pool percentage — a tunable compromise.
💡
Unlike a datacenter node failure (a probabilistic risk), DNA hydration is immediate and certain once triggered — so a wide blast radius in DNA storage is a bigger deal than the same pattern in conventional systems.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A team doubles pool size to reduce object endangerment under Uniform access, keeping the read limit unchanged. What's the hidden cost?
Show answer
Larger pools do resist expenditure — but they hydrate almost instantly (100% hydrated even at reqs=0.1% for the largest sizes tested), and since the read limit didn't scale with pool size, each hydration event now risks a proportionally larger amount of unread data needing replenishment.Misconception: that bigger pools are strictly better. Pool size is a trade-off between expenditure resistance and hydration/replenishment cost, not a free win.
Problem 2 · medium
A team implements "ideal" popularity-aware placement (Zipf-pool: hot objects grouped into hot pools) expecting fewer endangered objects than plain Zipf. What does the paper actually find?
Show answer
Surprisingly, Zipf-pool does not reduce the percentage of endangered objects compared to plain Zipf. Applying a Zipf distribution to a small set (pools) produces a heavier tail — pools holding unpopular objects still get hit disproportionately.Misconception: that concentrating popularity always helps. Skew applied at the pool level can concentrate risk instead of isolating it.
Problem 3 · easy
Why can't a system simply cache every object it ever reads to avoid replenishment costs?
Show answer
Even in that idealized case, the paper shows >90% (Uniform) of an expended pool's content was never read at all before expenditure — it's collateral damage from reads to other objects sharing the same pool. Caching only protects what's actually requested.Misconception: that caching solves replenishment. The gap is structural (shared pools, not shared objects), not a caching miss.
Problem 4 · medium
A system doubles its read limit per pool. Roughly how much does this delay reaching a given endangerment level, and does it change hydration behavior?
Show answer
Roughly proportionally — doubling the limit lets the system absorb about twice as many requests before hitting the same endangerment level (paper shows a 10× limit increase ≈ 10× more requests tolerated). Hydration is unaffected, since a pool hydrates on its first access regardless of its read limit.Misconception: that read limit affects hydration. Hydration is triggered by the first read; the read limit only governs how many subsequent reads a hydrated pool can survive.
Problem 5 · hard
r-hash replication reduces endangered objects by an order of magnitude per added replica. Why doesn't the paper simply recommend maximizing r-hash replication?
Show answer
r-hash scatters each object's replicas across independently-chosen pools, so when one pool is expended, its objects' surviving replicas are spread across many other pools — hydrating a much wider "blast radius" than r-pool or copysets would. More replication reduces one risk (endangerment) while amplifying another (widespread hydration/decay exposure).Misconception: that more replicas are strictly safer. In DNA storage, replication spreads durability risk (hydration) even as it shrinks recoverability risk (endangerment) — the two must be balanced.
Problem 6 · medium
Under Zipf access with a 1%-sized cache, hit rate is only ~4.5% yet zero objects become endangered. Under Uniform access with the same cache, hit rate is ~0.1% and the cache has almost no effect. Explain the gap.
Show answer
Under Zipf, the handful of objects that dominate access frequency stay resident in the small cache, and each cached hot object "shields" its entire pool from ever needing another physical read — so a low hit rate still fully protects the pools that matter. Under Uniform, no object is accessed often enough to stay cached, so essentially every read still goes to a physical pool.Misconception: that hit rate alone predicts protection. What matters is whether caching a few objects can shield whole pools from ever being touched — which depends on access skew, not raw hit-rate magnitude.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Why can't a pool just be read normally, like a hard drive sector?▾
Because reading requires hydrating the dry DNA and running PCR, which introduces cumulative errors each cycle. Unlike a magnetic sector, a DNA pool physically degrades from the act of reading — hydration alone drops durability from centuries to a few years, and repeated PCR eventually makes decoding impossible.
Q2What's the difference between "hydrated" and "expended"?▾
Hydrated means the pool has been opened at least once and its durability clock has started ticking down (years, not centuries). Expended means it has additionally exhausted its read limit — it can no longer be read at all, regardless of durability.
Q3Why do the authors ignore dollar cost, latency, and throughput?▾
Because synthesis/sequencing technology is changing so fast that concrete cost and speed numbers would be stale within a year or two. Instead they model the more stable, fundamental side effects of reads (hydration, read-limit consumption) that will remain relevant regardless of which specific technology wins.
Q4Is bigger pool size always better for reducing lost data?▾
No. Bigger pools resist read-limit expenditure under uniform access, but they hydrate almost immediately on first touch and cost more to replenish per hydration event, since read limit doesn't scale with pool size in current technology.
Q5What is "blast radius" in this context?▾
How many pools get affected when one pool is expended or hydrated. With r-hash replication, an object's replicas are scattered across many pools, so the fallout of one pool's expenditure spreads widely. Unlike a datacenter node failure (probabilistic risk), DNA hydration is an immediate, certain consequence once triggered.
Q6Does the LRU cache used in the model know which pools are at risk?▾
No — it's a plain, DNA-unaware LRU. It happens to help a lot under skewed (Zipf) access because a few hot objects protect whole pools, but it provides essentially no protection against read-limit exhaustion by design, since it never considers a pool's remaining read budget.
Q7What's the single biggest lever the paper identifies for reducing system cost?▾
Increasing the per-pool read limit, since it delays endangerment roughly proportionally without the hydration downside that comes with growing pool size.
Q8How was the model actually evaluated?▾
Via a custom event-based C simulator with 100 million objects, three pool sizes (100/1,000/10,000), three read limits (1%/10%/100% of pool size), replication factors 1–4, and two cache sizes, over Uniform, Zipf, and Zipf-pool synthetic workloads — 15 million total requests per run.
Q9Does this paper propose a DNA-aware management policy?▾
Not yet — this is explicitly a first step establishing the model and baseline (naive) policies. The authors state that designing actual DNA-aware placement, caching, and replication policies is future work informed by these findings.
Q10How does this differ from prior systems-focused DNA storage work?▾
Li et al. analyzed single-pool capacity limits; Agliamzanov & Tuck studied caching effects on 10–100 pools for one high-rate workload and omitted hydration entirely. This paper is the first to model multiple pools with varied workloads, placement strategies, and — crucially — hydration alongside read-limit expenditure.
