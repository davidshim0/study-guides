HotStorage 2026 · A Field Guide

A write that costs eight tokens for every token it actually stores

LLM-based memory agents now run a model on every write to turn raw context into durable "state." That write-path LLM call is a new, byte-invisible storage cost — and over half of it, on average, pays to re-digest things the store already knew.

📄 "Token Write Amplification in LLM-Mediated State Stores" · Yang et al. 🎓 Storage-systems background assumed — LLM-specific terms covered in the primers ⏱ ~25 min read
🪙

Charge a write by the LLM TOKENS it burns, not the bytes it stores — then ask how many of those tokens paid for semantics already known.
That's Token Write Amplification, and the redundant half of it.

Before you begin

Quick glossary, then eight ideas the paper assumes you know

The acronyms first — you'll see them everywhere. Then collapsible primers on the LLM-specific machinery; skip anything that's already familiar from storage systems.

Quick glossary

TWAToken Write Amplification — write-path LLM tokens ÷ raw context tokens written.
TSAToken Space Amplification — stored state tokens ÷ minimum tokens needed to express that semantic content.
SORSemantic Overlap Ratio — fraction of an incoming write's content already covered by the existing state.
SCBSemantic Coalescing Buffer — groups related raw writes and flushes them as one backend write.
Semantic unitAn atomic piece of application semantics (entity, fact, note) a store preserves — backend-agnostic.
Extraction / ConsolidationThe two write-path LLM stages: derive semantic units from raw context, then merge them into existing state.
NativeA store's default write path, run with no SCB in front of it.
Overlap-attributed TWAThe portion of TWA the accounting rule assigns to semantics already covered by the state.
new / non-overlap tokens (useful work) overlap-attributed tokens (re-processing cost) measurement machinery (TWA / SOR / SCB)
1What makes these "LLM-mediated" state stores different▾

A traditional write path mostly tokenizes, chunks, and embeds raw context (cheap, linear preprocessing) — think vector-RAG ingestion. An LLM-mediated state store (SimpleMem, LightRAG, A-Mem, MemoryOS) instead runs a full LLM on the write path: it reads the raw context, extracts semantic content, and merges it into durable state.

The write is no longer "parse and index" — it's "interpret and consolidate," and interpretation is expensive.

Now you're ready: this is a new storage workload where write cost scales with LLM reasoning, not with bytes moved.
2Tokens as the new unit of write cost▾

In a normal storage system you cost a write in bytes and I/Os. Here, the dominant cost is LLM tokens consumed on the write path — every token of model input and output. A tiny raw write (a few hundred tokens) can trigger thousands of tokens of extraction and consolidation.

Now you're ready: TWA is simply write-path tokens divided by raw context tokens — a unit conversion from "bytes written" to "tokens burned."
3Semantic units — a backend-agnostic yardstick▾

Each store materializes state differently: SimpleMem keeps compact memory entries, LightRAG keeps graph entities/relations, A-Mem keeps structured notes, MemoryOS keeps hierarchical pages/segments/traits. To compare them fairly, the paper defines a semantic unit — the smallest self-contained piece of application semantics a store preserves — independent of internal format.

Now you're ready: SOR and overlap accounting are computed over semantic units, not over each backend's native representation, so the metrics transfer across very different stores.
4Extraction vs. consolidation — the two LLM stages▾

Extraction turns raw context into candidate semantic units. Consolidation merges those units into the existing state — which means feeding some of the existing state back into the LLM so it can update, link, or supersede prior entries. Both stages cost tokens; consolidation often costs more, because it reprocesses state that was already paid for once.

Now you're ready: TWA = (extraction tokens + consolidation tokens) ÷ raw context tokens — exactly these two stages in the numerator.
5The classic write-amplification analogy▾

You already know write amplification from SSDs and LSM-trees: a logical write triggers extra physical writes (erase-before-write, compaction). TWA is the explicit token-level analog the paper names: a logical write (raw context) triggers extra LLM work (tokens) to maintain the higher-level "semantic" structure, the same way compaction maintains sorted runs.

Now you're ready: everything you know about amplification factors — average-case vs. worst-case, workload-dependence, the case for buffering/batching — transfers directly, with tokens standing in for physical bytes.
6Semantic overlap — writes that revisit what's already known▾

A write can introduce genuinely new semantics, or it can repeat, revise, or extend something already in the state (e.g., two web searches confirming the same fact). The residual of a semantic unit is the part not recoverable from the current state; SOR is the fraction of the unit's content that is already recoverable.

Now you're ready: high SOR means the write path is spending tokens on content the store didn't need to be told again.
7Temporal/semantic locality in agent write streams▾

Agent workloads aren't random: a deep-research agent fetching several pages about one topic, or a conversation revisiting the same user fact, produces writes that are close in time and close in meaning. This is the same locality intuition behind caching and group-commit — nearby writes are likely to be related.

Now you're ready: if nearby writes overlap, batching them before they hit the expensive write path should cut redundant LLM work — that's the whole motivation for the paper's buffer.
8The Semantic Coalescing Buffer, in one sentence▾

Instead of calling the expensive write path on every raw context, buffer related ones and flush a single concatenated write when semantic continuity breaks (topic drift) or a size limit is hit — conceptually a write-combining buffer or group-commit log, but keyed on embedding similarity instead of physical address or time.

Now you're ready: SCB changes only write grouping; it never touches a backend's extraction/consolidation logic, which is why it's "backend-agnostic."
The whole story in one place

TWA in a nutshell

The problem, the metric that exposes it, and the fix that exploits it.

LLM-based agents increasingly keep persistent state stores that survive across long sessions. To keep that state useful rather than a raw transcript dump, modern stores put an LLM on the write path: every write triggers extraction (pull semantic units out of raw context) and consolidation (merge them into existing state). This shifts write cost from bytes to tokens — a cost that's invisible if you only measure storage size.

The paper names this Token Write Amplification (TWA): write-path LLM tokens ÷ raw context tokens. Across five store configurations (SimpleMem, two LightRAG settings, A-Mem, MemoryOS) and seven agent workloads, native TWA averages 8.00× — writing a token of context can burn eight tokens of LLM work.

Crucially, not all of that cost buys new information. Using a semantic-unit abstraction and an LLM-estimated residual per unit, the paper defines the Semantic Overlap Ratio (SOR) — how much of a write's content the state already covers — and an overlap-attributed TWA that traces token cost back to that redundancy. The result: 54.9% of native TWA is spent on semantics the store already had.

That redundancy is exploitable because related writes cluster in time. A lightweight, backend-agnostic Semantic Coalescing Buffer (SCB) batches semantically continuous writes and flushes once, cutting average TWA from 8.00× to 3.02× and reducing TSA (stored-state bloat) by 33% — with no backend changes.

🪙 Key takeaways

  • LLM-mediated writes shift cost from bytes stored to tokens processed — TWA makes that cost measurable.
  • Native average TWA = 8.00× across 5 store configs × 7 workloads (184 streams, 16.6K writes, 12.2M raw tokens).
  • 54.9% of native TWA is overlap-attributed — tokens spent re-processing semantics already in the state.
  • Average per-write SOR is 36.8% — but that content-level overlap inflates to a 54.9% token share, because consolidation re-feeds whole existing-state entries, not just the overlapping fraction.
  • SCB batches semantically continuous writes before they hit the backend — no backend modification needed.
  • SCB cuts average TWA 8.00× → 3.02× and TSA by 33%, at the cost of a small, bounded read-side context increase.
  • Workload structure matters as much as the backend: Game workload TWA (45.51×) is ~18× Openworld-QA's (2.55×).
Six storage-systems pictures

How to think about TWA

Each analogy leans on ideas you already know from systems/storage. Every card ends with where it stops matching the paper.

The core idea · Token-level analog

Write amplification, denominated in tokens

You already measure how one logical write triggers extra physical writes on an SSD or LSM-tree. TWA is the same ratio with a different unit: one logical (raw-context) write triggers extraction + consolidation LLM calls, and TWA = total tokens ÷ raw tokens is exactly a write-amplification factor, just priced in tokens instead of bytes.

Where it breaks: classic WA is driven by physical layout (page size, compaction policy); TWA is driven by semantic redundancy and prompt overhead, which don't shrink with better data structures alone — hence the need for SOR-style accounting.
The fix · Semantic Coalescing Buffer

Group commit, keyed on meaning

A database batches several transactions into one log flush (group commit) to amortize fsync cost. SCB does the same for LLM writes: hold several raw contexts, flush them as one concatenated write once continuity breaks or a limit is hit — amortizing fixed prompt overhead across the group, the same way group commit amortizes fixed I/O overhead.

Where it breaks: group commit batches by arrival order under a latency bound; SCB batches by semantic continuity (embedding similarity), so its boundary is content-defined, not time-defined — a very different trigger condition.
Attribution · Residual / SOR

Deduplication, but semantic not byte-identical

Content-defined dedup finds byte-identical chunks already on disk and stores only a reference. SOR does the conceptual equivalent for meaning: given an incoming semantic unit and the current state, estimate the residual — the part that isn't recoverable from what's already stored — even when the new write paraphrases rather than repeats the old one verbatim.

Where it breaks: byte-level dedup is exact and cheap (hashing); semantic residual estimation is approximate and itself costs an LLM call — the paper validates it's stable across judge models (Fig. 3a / Appendix C), but it's a fuzzy measurement, not a hash comparison.
Cost of buffering · Two-tier reads

A write-back cache with dirty data still visible

A write-back cache holds dirty lines that haven't reached the backing store, but reads still see them. SCB is analogous: while writes sit in the buffer unflushed, queries must read a two-tier view — the consolidated (clean) state plus the active raw buffer (dirty) — to avoid losing recent information.

Where it breaks: a cache's dirty data is in the same representation as clean data; SCB's buffered reads mix raw, unprocessed context with consolidated semantic state, so the read path must tolerate two different formats, not just two freshness tiers.
The space side · TSA

Space amplification, LSM-style

In an LSM-tree, space amplification is stored bytes ÷ logical bytes — stale versions and fragmentation inflate it, and compaction is supposed to shrink it. TSA plays the same role for semantic state: stored tokens ÷ minimum tokens needed to express the same content. Richer, more structured stores (A-Mem, MemoryOS) have higher TSA, the same way more metadata-heavy layouts cost more space per logical byte.

Where it breaks: LSM compaction (merging sorted runs) reliably reduces space amplification; the paper's counterexample shows more frequent LLM-driven "merging" (LightRAG's aggressive summarization) does not always reduce TSA — LLM consolidation isn't equivalent to traditional compaction.
The tradeoff · No free lunch

The classic three-way knob, re-drawn

Storage engineers know you can't minimize write amplification, space amplification, and read amplification simultaneously (RUM conjecture territory). The paper's Figure 7 shows the same shape here: SimpleMem has low TWA but high TSA (it only ever appends); LightRAG trades higher write-path cost for lower TSA; richer stores raise both costs but read back more accurately.

Where it breaks: the classic RUM tradeoff is about data structure choices with well-understood knobs; here the "read amplification" axis is read tokens vs. task accuracy, a much fuzzier quality metric than a count of I/Os.
The full explanation

How it actually works

The system model, the metrics, the validation, and the buffer — in the order the paper builds them.

1 · System model — a write interface with two LLM stages

The store is modeled abstractly: for write w, the application submits raw context C_w with T_raw(w) tokens, and the store updates state: S_{w+1} = Write(S_w, C_w). Internally, this decomposes into extraction — U(w) = Extract(C_w) = {u1, …, un}, deriving semantic units from the context — and consolidation, which incorporates those units into S_w. Both stages' token costs are internal write-path cost, separate from the raw context itself.

2 · Semantic Overlap Ratio and the residual

For each extracted unit u ∈ U(w), an LLM estimates residual(u, S_w) — the part of u not recoverable from the current state S_w. Then:

SOR(w) = 1 − Σ tokens(residual(u, S_w)) / Σ tokens(u)   # token-weighted over u ∈ U(w), not a per-unit average

SOR(w) = 0 means every unit in the write is entirely new; SOR(w) = 1 means the write is a pure duplicate of existing state.

3 · Overlap-attributed TWA — tracing token cost to redundancy

SOR says how much content overlaps; overlap-attributed TWA estimates how many tokens that overlap costs. The attribution rule treats extraction and consolidation differently:

# Extraction processes the whole raw context, so attribute proportionally to SOR
TWA_overlap_ext(w) = SOR(w) * T_ext(w) / T_raw(w)

# Consolidation input = selected existing-state tokens (ALL overlap) + new unit tokens (SOR share)
A_in(w) = T_sel_cons(w) + SOR(w) * T_new_cons(w)

# Output tokens attributed in proportion to the overlap share of the input
T_overlap_cons(w) = A_in(w) + (A_in(w) / (T_sel_cons(w) + T_new_cons(w))) * T_out_cons(w)
💡
Why selected existing-state tokens count fully as overlap: those tokens were already processed by an earlier LLM call — feeding them back in is pure re-processing, regardless of the current write's SOR. That's the mechanical reason the token share of overlap (54.9%) runs well above the average content overlap (SOR, 36.8%).

4 · Validating SOR on controlled cases

Because SOR depends on both extraction and residual estimation, the paper validates the pipeline on 45 controlled cases built from 15 unrelated seed facts: for each pair (A, B), it constructs a duplicate chunk (restates A), a partial overlap chunk (A plus unrelated B), and a new chunk (only B) — each wrapped in noise and run through the same SOR pipeline, scored by three independent judge models.

5 · The Semantic Coalescing Buffer

SCB tracks an active buffer B of unflushed raw contexts. For an incoming context C, it computes a continuity score against the buffer's recent tail (window k):

cont(C, B) = max over C_j in tail_k(B) of cos( Embed(C), Embed(C_j) )

A running history H of recent continuity scores (window W) sets an adaptive boundary: if the current score drops below recent history by more than a drift threshold τ, or adding C would exceed a write-count limit N_max or raw-token limit T_max, the buffer is flushed as one concatenated write before C is appended. The evaluation fixes k=3, W=12, τ=2.0, N_max=10, T_max=8192 tokens, with Qwen3-Embedding-0.6B for similarity — the same settings across every workload and backend.

6 · Try it — how much of TWA is overlap?

The accounting rule in §3 means overlap-attributed TWA isn't just "SOR × TWA" — consolidation's full re-read of selected state tokens pushes the token-level overlap share above the content-level SOR. The slider below is calibrated so that the paper's measured average (SOR 36.8% → overlap share 54.9%) sits exactly on the curve; drag it to see how the relationship plays out at other overlap levels, holding total TWA fixed at the measured average of 8.00×.

7 · Evaluation scope

Five store configurations — SimpleMem, LightRAG with FORCE_LLM_SUMMARY_ON_MERGE set to 3 (LR-3) or 8 (LR-8), A-Mem, MemoryOS — each run natively and behind SCB, across seven workloads (Game, Text2SQL, Openworld-QA, Embodied AI, Software, Web, LongMemEval). In total: 184 streams, 16.6K writes, 12.2M raw context tokens, using Qwen3-8B on vLLM/A40 GPUs for write-path LLM calls.

Follow the numbers, step by step

Worked examples

Four traces through the paper's own reported numbers — computing TWA, decomposing it by overlap, contrasting workloads, and tallying SCB's net benefit.

① From token counts to the reported 8.00× average

Illustrative per-write token counts chosen to land on the paper's reported average: T_raw = 500, T_ext = 1,200, T_cons = 2,800.

  1. Numerator (write-path tokens): T_ext + T_cons = 1,200 + 2,800 = 4,000.
  2. Denominator (raw context tokens): T_raw = 500.
  3. TWA = 4,000 / 500 = 8.00× — matching the paper's measured average native TWA across all five store configs and seven workloads.
  4. Reading it: for every token of context the agent actually produced, the store's write path consumed eight tokens of LLM input/output to turn it into durable state.
🌱
These specific per-write counts are illustrative, chosen only to reproduce the real reported ratio — the paper reports the aggregate 8.00× directly (§4.2), not a single-write trace.

② Decomposing 8.00× by semantic overlap

Using the paper's reported overlap share directly: 54.9% of native TWA is overlap-attributed.

  1. Overlap-attributed TWA = 54.9% × 8.00 = 4.39×.
  2. Non-overlap TWA = 8.00 − 4.39 = 3.61× (the share spent on genuinely new semantics).
  3. Compare to content-level SOR: average SOR is only 36.8% — meaning the token share of overlap (54.9%) is noticeably higher than the content share (36.8%).
  4. Why the gap: per the attribution rule, consolidation counts all selected existing-state tokens as overlap regardless of the current write's SOR — so writes that merge against a lot of prior state inflate the token-level share beyond what content overlap alone would predict.
💡
Takeaway: if you only tracked SOR, you'd underestimate how much write-path cost is redundant — the token-level accounting is the more honest cost signal.

③ Why Game has 18× the TWA of Openworld-QA

Reported native TWA: Game = 45.51×, Openworld-QA = 2.55×.

  1. Ratio: 45.51 / 2.55 ≈ 17.85× — nearly an order of magnitude difference between workloads, using the same kind of store.
  2. Game: short, dense writes (avg. 103 raw tokens/update per Table 7) — each small write still triggers a near-fixed-cost extraction + consolidation call, so the fixed overhead dominates the ratio.
  3. Openworld-QA: long, noisy writes (avg. 5.91K raw tokens/update) — the same fixed LLM overhead is amortized over far more raw context, even though much of that context is irrelevant to the eventual semantic units.
  4. Lesson: TWA is not purely a backend property — workload write-size distribution changes it by an order of magnitude on its own.

④ SCB's net benefit for LightRAG (LR-3)

From Table 1, SCB's cost relative to Native for the LR-3 backend: Δwrite tokens = −8.3k and Δwrite latency = −31.0s (both per update), Δread tokens = +1.0k and Δread latency = +0.1s (both per query).

  1. Write side: SCB saves 8,300 write-path tokens and 31.0 seconds of write latency per update, by batching writes before extraction/consolidation.
  2. Read side cost: exposing the still-unflushed buffer costs only +1,000 read tokens and +0.1s of read latency per query.
  3. Net: per-update write-token savings (8.3k) outweigh the per-query read-token cost (1.0k) by more than 8×, and the read latency change is negligible (+0.1s) against a 31.0s write-latency reduction — note these are different per-event units (per update vs. per query), not directly summable totals.
  4. General pattern (Table 1): every backend shows the same shape — thousands of write tokens saved per update against roughly one thousand extra read tokens per query, which is why SCB's accuracy impact stays small (Fig. 7b).
Test yourself

Practice problems

Try each before opening the answer. Every one flags the misconception it's checking for.

Problem 1 · easy
A write has T_raw = 300, T_ext = 900, T_cons = 1,500. What is its TWA?
Show answer
TWA = (T_ext + T_cons) / T_raw = (900 + 1500) / 300 = 2400/300 = 8.0×.Misconception: including T_raw in the numerator. TWA only counts the write-path LLM tokens (extraction + consolidation) over the raw context tokens — the raw context itself isn't LLM-generated cost.
Problem 2 · medium
If a write's SOR = 60% and its total TWA is 10×, is its overlap-attributed TWA necessarily 6×? Why or why not?
Show answer
No, not necessarily. SOR is a content-level ratio over semantic units; overlap-attributed TWA is computed with a different rule that treats consolidation's selected existing-state tokens as 100% overlap regardless of SOR, and only scales newly extracted unit tokens and extraction tokens by SOR. Depending on how much of consolidation's input is "selected existing state" vs. "new units," the overlap-attributed share can be higher or lower than SOR×TWA — in the paper's aggregate data it runs higher (54.9% token share vs. 36.8% average SOR).Misconception: treating SOR as a direct multiplier on TWA. The accounting rule in §3.3 is deliberately asymmetric between extraction and consolidation.
Problem 3 · medium
Why does the paper wrap controlled SOR test chunks in noise (tool-log headers, numeric strings) before running them through the SOR pipeline?
Show answer
To test robustness: real agent writes are never clean isolated facts, they're embedded in logs, tool output, and formatting artifacts. Wrapping the controlled new/partial/duplicate chunks in fixed noise checks whether the residual-estimation pipeline still correctly separates the three cases (Figure 3a shows it does) when irrelevant surrounding text is present — the same validation goal as testing a parser against malformed real-world input, not clean unit-test strings.Misconception: that the noise is meant to fool the pipeline into failing. It's a sanity check for realistic conditions, not an adversarial test.
Problem 4 · easy
True or false: SCB reduces TWA by making each backend's extraction and consolidation logic cheaper.
Show answer
False. SCB never modifies the backend's extraction or consolidation logic — it changes only write grouping, batching semantically continuous raw contexts and calling the unmodified backend write path once per group instead of once per individual write. The savings come from amortizing fixed per-call overhead and avoiding intermediate consolidations against partially-updated state, not from making any single LLM call cheaper.Misconception: conflating "backend-agnostic" optimization with "modifying the backend." SCB sits entirely in front of the store.
Problem 5 · hard
SCB increases read tokens per query (Table 1 shows +0.7k to +1.0k across backends) because it must expose the unflushed buffer. Why doesn't this noticeably hurt downstream task accuracy (Fig. 7b)?
Show answer
Two reasons. First, the added context is additive, not a replacement — the persisted, consolidated state is still fully exposed, and only the small active raw buffer is appended on top, so no previously-available information is lost. Second, the buffer's size is tightly bounded by the flush policy (N_max = 10 writes, T_max = 8192 raw tokens, plus the semantic-drift boundary), so the extra context can't grow unboundedly between flushes — it stays a small, recent slice.Misconception: assuming any staleness/format mixing in a read path must degrade accuracy. Bounding the window size and keeping persisted state intact limits the downside.
Problem 6 · medium
The paper reports a TSA counterexample: LightRAG with more frequent LLM summarization (LR-3 vs. LR-8) does not always have lower TSA. What does this tell you about LLM-mediated consolidation vs. traditional storage compaction?
Show answer
In traditional compaction (e.g., LSM-tree merges), doing it more often reliably removes stale/duplicate entries and shrinks space amplification — more compaction work predictably buys less space overhead. The LightRAG counterexample shows LLM-driven "merging" doesn't have that guarantee: more frequent LLM summarization can leave TSA unchanged or worse, because an LLM's merge behavior isn't a deterministic dedup/compaction rule — it may rewrite, expand, or restructure content rather than strictly shrinking it.Misconception: assuming "more consolidation" is monotonically good, the way "more compaction" is in classical storage engines. LLM-mediated consolidation needs its own space-efficiency evaluation, not an inherited assumption from LSM-trees.
Problem 7 · medium
Why can't SCB reduce TWA to near-1× just by making the buffer window larger (bigger N_max and T_max)?
Show answer
Two limits remain even with a larger buffer. First, SCB only removes inter-write redundancy (overlap across nearby writes) — it does nothing about intra-write redundancy, i.e. a single long, noisy write (like an Openworld-QA search result) that is internally repetitive; the paper's Discussion flags this as a limitation. Second, larger buffers increase the read-side cost (more unflushed raw context to expose per query) and risk mixing semantically unrelated content into one flush if the drift detector doesn't trigger soon enough, trading write savings for read-side and consolidation-quality cost.Misconception: that batching is a free knob — bigger buffers trade one cost (write-path tokens) for another (read-path context size, consolidation precision).
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly does TWA measure?▾
The ratio of write-path LLM tokens — all model input after prompt construction plus all generated output, across both extraction and consolidation (T_ext + T_cons) — to the raw context tokens the application actually submitted on that write. It's a direct token-level analog of storage write amplification: how much extra "work" one logical write triggers.
Q2Why measure in tokens instead of bytes or wall-clock time?▾
Because tokens are the unit the write path actually spends — LLM API cost and most serving-time compute scale with tokens processed, not with the byte size of the underlying text. Wall-clock time is also affected by batching, hardware, and model choice; tokens isolate the amplification effect from those confounders (and Table 3 shows TWA stays close across four different write-path models).
Q3What is a "semantic unit" and why not just compare raw backend formats?▾
Different stores keep state in very different shapes — graph entities (LightRAG), structured notes (A-Mem), hierarchical pages (MemoryOS). A semantic unit is an abstraction over all of them: the smallest self-contained piece of application semantics a store preserves. Defining SOR and overlap accounting over semantic units, rather than each backend's native format, is what makes cross-store comparison possible at all.
Q4Is SOR an exact measurement?▾
No — it's an LLM-estimated diagnostic, not an exact overlap count. The paper validates it on 45 controlled cases with known overlap (new/partial/duplicate) across three judge models and finds the ordering holds consistently (Fig. 3a, Appendix C), which supports using it as a comparative diagnostic, but it remains an approximation.
Q5Why is overlap-attributed TWA (54.9%) higher than average SOR (36.8%)?▾
Because the attribution rule treats consolidation's "selected existing-state tokens" as fully overlap-related regardless of a write's own SOR — those tokens were already processed by an earlier LLM call, so re-feeding them in is counted as redundant work. Only the newly-extracted unit tokens get scaled by SOR. This asymmetry pushes the token-level overlap share above the content-level overlap ratio.
Q6How does SCB reduce TWA without touching any backend?▾
SCB sits entirely in front of the store. It buffers raw contexts that are semantically continuous (via embedding similarity) and flushes them as one concatenated write when continuity breaks or a size limit is hit. This reduces the number of expensive write-path LLM calls and avoids intermediate consolidations against partially-updated state — all without changing what the backend's extraction/consolidation logic does.
Q7Does SCB hurt accuracy or add meaningful latency?▾
The measured impact is small: SCB adds 0.7k–1.0k read tokens per query (Table 1) because it must expose the unflushed buffer alongside persisted state, but Fig. 7b shows this doesn't noticeably move downstream task accuracy, and end-to-end read latency changes by at most 2.2%.
Q8Why do richer stores like A-Mem and MemoryOS have higher TSA?▾
They materialize more structure per semantic unit — linked notes with metadata, or hierarchical pages/segments/traits — which costs more stored tokens per unit of underlying content, the same way a richly-indexed record format costs more space per logical byte than a flat append-only log (which is why SimpleMem, which only appends, keeps lower TWA but higher TSA from redundant entries).
Q9Does more frequent LLM-driven merging always lower space overhead?▾
No — LightRAG's LR-3 (more frequent summarization) vs. LR-8 (less frequent) shows TSA doesn't simply decrease with merge frequency. Unlike deterministic storage compaction, LLM-mediated consolidation isn't guaranteed to shrink stored size; it can restructure or expand content instead.
Q10What is Token Read Amplification (TRA), and why isn't it fully defined in this paper?▾
TRA would be the read-side analog: state tokens exposed per query relative to the minimum evidence needed to answer it. The paper raises it in the Discussion as future work, noting that unlike TWA, TRA depends heavily on retriever design (what gets fetched and reranked), making a backend-independent definition harder to pin down.
