SOSP 2026 · A Field Guide

Give every agent its own fork of the log, not a seat at the shared table

AI agents reading and writing streaming data are exploratory, high-volume, and occasionally wrong. AgileLog gives each one a cheap, isolated fork of the shared log — including a new kind that keeps drinking live data. This is the plain-English tour of the abstraction, and of Bolt, the system that makes forks nearly free.

📄 "AgileLog: A Forkable Shared Log for Agents on Data Streams" · Bhat, Hong, Noguera, Ganesan, Alagappan 🎓 Assumes distributed-systems background — primers cover the streaming-specific parts ⏱ ~30 min read
🍴

1What a shared log actually offers▾

A shared log is a durable, linearizably ordered sequence of records with two calls: append(record) returns a position, read(position) returns what's there. Producers append; consumers read from wherever they last stopped. It's the storage primitive underneath Kafka, Pulsar, CORFU, and most streaming systems.

Everything in this paper is about deciding who gets to append to and read from which log — and how to give an agent its own log-like view without paying to copy data.

Now you're ready: a "fork" in AgileLog is just another AgileLog instance — same append/read API — created cheaply from an existing one.
2The diskless shared-log architecture▾

Traditional logs (Kafka included) replicate data across a set of stateful brokers that write to local disks. Diskless designs instead make brokers stateless: they batch records and write them as objects to a shared, scalable object store (S3, Azure Blobs). A separate fault-tolerant metadata layer then assigns each record a log position and remembers which object/byte-range holds it — an index from position → storage location.

This matters because it separates "who serves the read/write path" (brokers, cheap to add) from "who owns the bytes" (the object store, already elastic).

Now you're ready: Bolt is diskless-first. A fork can be served by a different broker while still pointing at the same objects — that's the whole trick behind zero-copy forks.
3SMR, Raft, and why the metadata layer is a bottleneck to protect▾

The metadata layer sequences appends and updates each log's index/tail. To survive failures it runs as a replicated state machine (SMR) over a consensus protocol — Bolt uses Raft. Every metadata operation (an append's index update, a fork's creation, a tail bump) is logged and executed identically on every replica.

Because every log's metadata funnels through one small consensus group, anything that makes metadata operations bigger or slower (e.g., copying index entries) throttles every log the instance hosts — not just the one being copied.

Now you're ready: most of Bolt's cleverness (HLI, tail-only updates, lazy propagation) exists specifically to keep metadata operations small and cheap, because the metadata layer is the shared bottleneck.
4Why AI agents stress a streaming system differently▾

A traditional stream consumer follows fixed, programmer-written logic: read, transform, write, repeat. An LLM-driven agent instead reasons step-by-step about a natural-language goal, issuing tool calls it decides on the fly — often several in parallel, to explore multiple hypotheses before picking one.

Two consequences: (1) agentic read/write load is bursty and much higher-volume than a hand-coded consumer's, and (2) an agent's writes can simply be wrong, because they're LLM-generated.

Now you're ready: this is precisely the pair of problems AgileLog targets — performance isolation for the load, and write isolation (via cFork + promote) for correctness.
5Fork as a systems primitive, before this paper▾

"Fork" already means something precise in OS design (a process's copy-on-write child) and in databases (Neon, Dolt, Supabase branches). The shared thread: create an isolated child that shares history with the parent up to some point, cheaply, usually via copy-on-write or shared immutable storage rather than a real copy.

What's new here is applying it to a shared log's ordered, ever-growing stream — where "the child keeps seeing new parent data" is a requirement, not an edge case.

Now you're ready: hold this OS/DB intuition loosely — AgileLog's cFork deliberately breaks the "disconnected at fork point" assumption these prior forks all share.
6MCP: how agents actually touch streams today▾

The Model Context Protocol is the de facto interface agents use to call external tools. Practical streaming systems (Confluent, Redpanda, Lenses, StreamNative) already expose MCP servers so an agent can read records, run analysis, and write outputs — all as ordinary tool calls the LLM decides to invoke.

This is the paper's grounding: agents interacting with streams isn't hypothetical, it's already shipping, and it's shipping without the isolation the paper argues is needed.

Now you're ready: imagine an MCP tool that says "create a fork" instead of "read the live topic" — that single substitution is most of what AgileLog changes for an agent's code.
7Log indexes: position → storage location▾

A log's index maps each position (0, 1, 2, …) to where its record physically lives — here, an object identifier plus a byte range within that object. The tail is just the next free position. Appending = pick the tail, write the data, record an index entry, advance the tail.

Note what the index does not contain: the data itself. It's pure metadata, small and cheap to reason about compared to the (potentially huge) objects it points into.

Now you're ready: because forks share the same objects, "creating a fork" can become "creating index entries that point at existing objects" — no data movement required, only metadata.
8Subtree updates in logarithmic time (Euler tours)▾

If many descendants need the "same" update whenever their common ancestor changes, updating each one individually is O(descendants) — too slow at scale. A classic trick: flatten the tree into an array via a depth-first Euler tour, so every subtree becomes one contiguous range in that array. A range update on a balanced BST with lazy propagation then touches any subtree in O(log n), regardless of how many nodes it contains.

This is a general data-structure trick — you may already know it from segment trees or interval scheduling.

Now you're ready: Bolt's Lazy Tail Tree is exactly this: an inheritance tree of cFork "tails," stored as an Euler tour, so bumping every descendant's tail after a parent append costs O(log n), not O(n).
The whole story in one place

AgileLog & Bolt in a nutshell

The problem, the abstraction, and the architectural bet that makes it cheap.

AI agents now read and write streaming data through the same shared log that production consumers depend on. That's a problem on two fronts: agents are exploratory — they issue bursts of parallel, speculative tool calls — so they load the system unpredictably; and agents' writes can simply be wrong, because they're LLM-generated, so they need to be isolated and validated before they count. Today's shared logs (Kafka included) offer neither performance isolation nor write isolation for a second class of client sharing the same log.

The paper's answer is AgileLog: give forking first-class status in the shared-log abstraction itself. Traditional apps keep using the root log; each agent gets its own fork — a cheap, logically separate, performance-isolated child that can itself be read, appended to, and forked further. The genuinely new idea is the continuous fork (cFork): unlike every prior notion of "fork" (OS processes, database branches), a cFork doesn't disconnect from its parent — it keeps inheriting the parent's new appends forever, while its own appends stay unidirectionally private (parent → child visible; child → parent not, unless promoted). AgileLog also offers the more familiar severed fork (sFork) for point-in-time snapshots and what-if exploration.

Bolt is the implementation. Its architectural bet: build on the emerging diskless shared-log design (stateless brokers, data durable on a shared object store, a small metadata layer that sequences positions). That lets Bolt create a fork by pointing the child's metadata at the same storage objects as the parent — zero data copy — and serve the fork from a separate broker for performance isolation. The remaining engineering is entirely about keeping the metadata cheap too: a Hierarchical Log Index (HLI) avoids copying even metadata at fork time, and a Lazy Tail Tree (LTT) propagates a parent's new appends to hundreds of cForks in logarithmic time instead of touching every descendant eagerly.

The payoff: forks that cost ~50 µs regardless of parent log length (vs. up to 100 ms and rising with a naive metadata copy), a root log whose throughput and latency are unaffected by 100s of cForks, and — in Bolt's Kafka comparison — elimination of the 14× mean / 130× p99 latency spikes a production workload suffers when an exploratory agent shares its broker.

🍯 Key takeaways

  • Agents need two things prior shared logs don't give them: performance isolation (they're exploratory and bursty) and write isolation (their writes can be wrong).
  • AgileLog's headline primitive is the continuous fork (cFork): shares history to the fork point, then keeps inheriting parent appends forever, with unidirectional write isolation.
  • promote turns a validated cFork into the new parent — the mechanism for safely landing agentic writes, linearizably interleaved with everything else.
  • Bolt makes forks cheap by riding a diskless architecture: same storage objects, separate broker, zero data copy.
  • HLI avoids even metadata copy at fork time; tail-only updates + the Lazy Tail Tree propagate parent appends to many cForks in O(log n), not O(n).
  • Result: ~50 µs forks independent of log size, no measurable root-log slowdown with 100s of cForks, and elimination of Kafka's 14×/130× interference spikes.
Seven everyday pictures

How to think about forks in Bolt

Each stands alone — jump around. Every card names honestly where the picture stops matching the mechanism.

The starting point · OS fork()

Forking a process, copy-on-write

fork() gives a child process its own page table entries pointing at the same physical pages as the parent — no copy until a write happens. AgileLog's sFork is exactly this: a snapshot that shares history via pointers (index entries), diverging privately after the fork point.

Where it breaks: fork()'s child is frozen relative to the parent the instant it's created — the parent's later writes are invisible to it. That covers sFork, but not cFork, which deliberately keeps seeing the parent's new writes. There's no POSIX primitive for that.
The novelty · Continuous forks

A one-way mirror you can write behind

A one-way mirror: the observation room (cFork) sees everything happening in the main room (parent) in real time, but nothing in the observation room is visible back through the glass. The agent can also write on its own whiteboard behind the glass — the main room never sees it unless someone carries it through the door (promote).

Where it breaks: a mirror is passive; a cFork is linearizably interleaved — its own writes get a definite, provable position relative to every inherited parent write, not just "sometime after." That ordering guarantee is doing real work.
Zero-copy forks · HLI

A child page table that borrows the parent's

This one should feel native: a child's page table doesn't duplicate every PTE — for shared, unmodified pages, it just walks up to the parent's table. HLI does the same for log positions: the child's index starts empty, and a lookup for any position below the fork point transparently walks to the parent's index instead.

Where it breaks: page-table lookups are hardware-walked in nanoseconds; HLI's recursive lookup adds a real (if tiny — ~2 µs at depth 7) software hop per level of fork nesting, since it's metadata-layer software, not a TLB.
Scaling to many cForks · Lazy propagation

Not calling every relative — leaving a forwarding note

When new mail arrives for someone who's moved, the post office doesn't chase down every relative who might ask — it leaves a forwarding note at the old address, resolved only when someone actually comes looking. Bolt's tail update is that note: a parent append leaves a single lazy marker on the whole subtree, and a descendant's tail is only actually resolved and updated when an operation on that descendant needs its current value — never immediately.

Where it breaks: a forwarding note is per-address; Bolt needs to leave the "note" for potentially hundreds of descendants at once per parent append. That's why it needs the Euler-tour trick below, not just a simple pointer.
The data structure · Euler tour + LTT

Flattening a family tree into one line

Genealogists sometimes flatten a family tree into a single timeline of "enter this person / leave this person" events (a depth-first traversal). Do that, and every branch of the tree — no matter how big — becomes one contiguous slice of that timeline. The Lazy Tail Tree stores Bolt's cFork inheritance tree this way, so "update every descendant of this fork" becomes one range update on that slice — logarithmic, not linear in descendant count.

Where it breaks: family trees are static; Bolt's inheritance forest grows and shrinks as forks are created and squashed. The Euler tour has to support that dynamically, which is the harder (but standard) part of the data structure the paper doesn't dwell on.
Landing writes · Promote

A restricted merge, not a free relabel

Git users know two ways to land a branch: merge (combine divergent histories, resolve conflicts) and fast-forward (repoint a label because the branch already contains everything the target needs — no data moves). Promote looks fast-forward-like in spirit — no conflict resolution needed, since the cFork already linearizably contains the parent's interleaved history — but the paper calls it a restricted merge: Bolt actually copies the cFork's post-fork-point metadata entries into the parent, replacing whatever was there. It's cheap because only that (typically small) suffix moves, not because nothing moves.

Where it breaks: a true git fast-forward touches nothing but a pointer; promote does real (if small) metadata work. And unlike git, which can fast-forward many independent branches over time, AgileLog allows many promotable cForks to explore in parallel but only the first promote wins — the rest are squashed automatically, not merged or replayed.
The substrate · Compute/storage disaggregation

A shared pantry, many separate kitchens

Diskless brokers are stateless "kitchens" that all pull ingredients from one shared, elastic "pantry" (the object store). Giving an agent its own broker is like giving it its own kitchen off the same pantry — no groceries move, but nobody's dish burns because someone else is hogging a stove. This is the same disaggregation instinct behind CXL memory pools: separate the resource that's contended (compute/broker cycles, or DRAM capacity) from the resource that scales cheaply and passively (bulk storage, or pooled memory).

Where it breaks: CXL disaggregation is fighting nanosecond-to-microsecond byte-addressable latency; Bolt's shared storage is comfortably in the millisecond object-fetch regime, hidden behind batching, an index, and broker-local caches. The isolation goal rhymes; the latency budget doesn't.
The full explanation

How Bolt actually works

From the diskless read/append path up through zero-copy forks, continuous inheritance, and promotion.

1 · The tension Bolt has to resolve

Two obvious designs both fail. Copy the data to a separate cluster for each fork — you get real performance isolation, but fork creation is slow and expensive, a non-starter for agents that fork often. Share the same broker/disk as the parent — fork creation is instant, but the fork's load now contends for the same disks and CPU as production traffic, defeating the whole point.

💡
Bolt's resolution: adopt the diskless architecture as the substrate. Data durability already lives on a shared, elastic object store — so a fork can point at the same objects as its parent (zero copy) while being served from a different, dedicated broker (performance isolation). The tension dissolves because "share the bytes" and "separate the serving path" are no longer the same decision.

2 · The diskless read/append path (a primer)

An append can land on any broker. The broker batches records from many clients into one object, writes it to the object store, then tells the metadata layer "object O contains these records for these logs." The metadata layer — a small Raft-replicated group — assigns each record the log's current tail as its position, updates the index and tail, and returns. A read does the reverse: ask the metadata layer for the object/byte-range at a position, fetch it from the object store (often via a broker-local cache).

3 · From naive to lazy: three versions of continuous inheritance

Getting a cFork to "see" new parent appends could be done three ways, in increasing order of cleverness:

# v1 — BoltNaiveCF: copy the index entry into every descendant, eagerly
on append(r) to P:
    insert r.meta into P.index
    for D in descendants(P): insert r.meta into D.index   # O(descendants), duplicates metadata

# v2 — Bolt-ET (eager tail): update only tails, but still touch every descendant
on append(r) to P:
    insert r.meta into P.index
    for D in descendants(P): D.tail += 1                    # no duplication, but still O(descendants)

# v3 — Bolt: update tails lazily, via one range update on the Lazy Tail Tree
on append(r) to P:
    insert r.meta into P.index
    LTT.range_update(subtree(P), +1)                          O(log n)          # resolved per-descendant only on demand
⚠
Why not stop at v2? Bolt-ET avoids metadata duplication, so memory is fine — but it still iterates every descendant on every parent append, in the critical path. With 1000 cForks that's 1000 tail bumps per append, and it becomes the throughput bottleneck (§6.4). v3's Euler-tour range update is what actually decouples parent throughput from cFork count.

4 · Promote and squash

Promoting a cFork copies only its post-fork-point metadata entries over the parent's — a metadata-only operation, no data copy, fast because only the (typically small) suffix after the fork point moves. Because promotion can change the parent's positions beyond the fork point, Bolt blocks parent reads (and appends' returned indexes) past earliest-fp — the fork point of the oldest still-open promotable cFork — until that cFork is promoted or squashed. Squash simply deletes a fork's metadata-layer state (and, for a promotable cFork, unblocks the parent if it was the last one pending).

💡
Guarding against rogue agents. An agent that opens a promotable cFork and never resolves it would permanently block reads on the parent. Bolt's optional lease bounds this: any promotable cFork whose lifetime exceeds a configured duration (the paper demonstrates 500 ms) is internally squashed, and parent throughput heals automatically.
Follow the numbers, step by step

Worked examples

Four traces through the paper's own measurements — index arithmetic, fork latency, metadata memory, and Kafka interference.

① Walking the recursive lookup by hand

G is forked into R at G.tail = 1 (so G already has g0). Afterward: r0 is appended to R, then g1 to G, then r1 to R, then g2 to G. R never stores g1 or g2's metadata. What does lookup(R, 2) return?

  1. Reconstruct R's positions: r0 lands at R-position 1 (R.tail was 1, inherited from G). g1's append only bumps R's tail (to 3) — no R.index entry. r1 then lands at R-position 3. g2 bumps R's tail again (to 5) — again no entry.
  2. Position 2 isn't in R's index (only 1 and 3 are — R's own appends). So it must be an inherited parent position.
  3. Find R's local count below position 2: the largest R-index entry below 2 is r0 at position 1, with local count 1 (one locally-appended record so far).
  4. Subtract and recurse into G: requested position 2 − local count 1 = 1. Look up position 1 in G's index.
  5. G.index[1] = g1.meta. So lookup(R, 2) correctly returns g1's metadata — one recursive hop, no duplicated entry anywhere.
🍯
Insight: the "local count" field is the whole trick — it's what lets a position expressed in the child's coordinate system be translated back into the parent's, without ever copying the parent's entries into the child.

② When does copying metadata stop being viable?

The paper reports Bolt at ~50 µs regardless of log length, and BoltMetaCpy at 100 ms with a 25M-entry parent. Model BoltMetaCpy as roughly linear in log length (a metadata copy is proportional to the number of entries copied) and find where it stops being competitive with Bolt.

  1. Derive the per-entry rate: 100 ms ÷ 25,000,000 entries = 0.000004 ms/entry = 4 ns/entry.
  2. Solve for the crossover where BoltMetaCpy's latency equals Bolt's flat 50 µs: 50 µs ÷ 4 ns/entry = 12,500 entries.
  3. Below ~12.5K entries, a metadata copy is actually roughly comparable to Bolt's fixed cost — copying a short index isn't yet expensive.
  4. At the paper's measured 25M entries, BoltMetaCpy is 100 ms ÷ 50 µs = 2000× slower — "three orders of magnitude," matching the paper's own framing.
  5. The takeaway isn't the specific ratio — it's that BoltMetaCpy's cost is a function of parent history, while Bolt's is not. Any sufficiently long-lived production log (and streaming logs are long-lived by design) eventually makes metadata copying untenable.
💡
This is exactly the computation behind the interactive slider on the "How It Works" tab — move it past ~12.5K entries and watch BoltMetaCpy fall off a cliff while Bolt stays flat.

③ Why tail-only updates save gigabytes, not just milliseconds

The paper measures memory to support 1000 cForks of a root log with 1M appended records: 4.4 GB for BoltNaiveCF vs. 8 MB for Bolt. Quantify the difference.

  1. Compute the reduction factor: 4.4 GB ÷ 8 MB = 4400 MB ÷ 8 MB = 550× less memory for Bolt.
  2. Why BoltNaiveCF is this big: every one of the 1M root records gets its metadata copied into all 1000 cForks' indexes — roughly 1000 × 1M = 1 billion duplicated index entries.
  3. Per-entry cost implied: 4.4 GB ÷ 1×10⁹ duplicated entries ≈ 4.4 bytes/duplicated entry — consistent with a compact index-entry encoding, just paid a thousand times over.
  4. Why Bolt avoids nearly all of it: each record's metadata is stored exactly once (in whichever log it was actually appended to). The 8 MB that remains is essentially the Lazy Tail Tree's O(number of forks) bookkeeping, not O(forks × records).
  5. Consequence beyond memory: this is also why Bolt-ET (tail-only, but eager) avoids the memory blowup yet still hits a throughput wall at 1000 forks (§6.4) — memory and throughput are separate costs, and Bolt needed to fix both.

④ What 14× mean / 130× p99 actually costs an agent

In the ad-hoc analytics case study, a latency-critical workload runs alongside an agent that alternates between "thinking" (LLM calls) and "query execution" (parallel reads of up to 9 concurrent investigations, annotated 8Q/3Q/9Q/5Q in the paper's trace). On Kafka, query-execution phases are 14× the mean and 130.8× the p99 latency of thinking phases.

  1. Read the ratios as "what changes, not what's absolute": the paper reports relative degradation between the agent's two phases on the same system, isolating the effect of the agent's own read bursts rather than absolute hardware speed.
  2. Tail latency degrades far more than mean (130.8× vs 14×): this is the signature of resource contention, not uniform slowdown — most requests are fine, but a growing fraction queue behind the agent's parallel query burst (8Q, 9Q) at the shared broker.
  3. Bolt reports both ratios as ≈1.0× — the paper describes this as no interference: the lc-workload's latency during query-execution phases matches its latency during thinking phases, because the agent's sFork is served by its own broker. (The paper doesn't report a statistical test here — "≈1.0×" is a measured ratio, not a claim of statistical indistinguishability.)
  4. Why this helps at scale: object stores handle reads at very high aggregate throughput (the paper cites ~220 GB/s with 4 MB objects and 10 object-name prefixes on S3), which motivates why object storage can absorb far more concurrent agent read load than a single shared broker before becoming a bottleneck itself — though the paper doesn't claim this eliminates contention at every scale; a sufficiently large agent fleet could still stress the object store or brokers.
🍯
Insight: the number that matters to a production on-call engineer isn't "the agent is slower" — it's "the agent made my workload's p99 130× worse." Bolt's isolation claim is specifically about not moving that number at all.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
Why can't Bolt just copy the parent's metadata (not the data) to create a fork instantly — isn't metadata supposed to be small?
Show answer
Metadata is small per entry, but a long-lived production log can have millions of entries, so copying its whole index is still a real, growing cost — the paper measures 100 ms at 25M entries, three orders of magnitude slower than Bolt's zero-copy ~50 µs. "Metadata, not data" only helps if you avoid copying the metadata too.Misconception: that "just metadata" implies "basically free." Cost scales with count, and shared-log metadata volumes aren't small at production scale.
Problem 2 · medium
cFork R is created from G at G.tail = 3. R locally appends r0 and r1 (R.tail becomes 5). G then appends g3. What changes in R's index, and what changes in R's tail?
Show answer
R's index doesn't change at all — g3's metadata is never copied into R. Only R's tail is bumped, from 5 to 6, reflecting that one more (inherited) record now precedes any future local append to R.Misconception: assuming every parent append must touch every descendant's index. Bolt deliberately separates "the child knows this record exists" (a tail bump) from "the child stores this record's metadata" (an index entry) — only the latter is expensive, and Bolt avoids it entirely for inherited records.
Problem 3 · medium
Bolt-ET (eager tail updates, no duplication) still bottlenecks at 1000 cForks even though it uses almost as little memory as full Bolt. What's the resource it's spending too much of?
Show answer
Metadata-layer throughput (CPU/consensus-op time in the critical path), not memory. Bolt-ET still iterates every descendant on every parent append to bump its tail — with 1000 cForks that's 1000 tail-bump operations per append, all before the append can be acknowledged. Full Bolt replaces that per-descendant loop with a single O(log n) range update on the Lazy Tail Tree.Misconception: that avoiding memory duplication automatically avoids the scaling problem. Bolt-ET proves memory and throughput are separate bottlenecks that both had to be solved.
Problem 4 · hard
Why must Bolt block reads on the parent log beyond a promotable cFork's fork point, rather than just letting them proceed and sorting it out at promote time?
Show answer
Because promotion can change the positions of records beyond the fork point — records inserted into the cFork get spliced into the parent's timeline. A consumer that already read (and, say, checkpointed) "position 42" on the parent before promotion might find that position now holds different data after promotion. Blocking those reads until the cFork is resolved (promoted or squashed) prevents ever exposing a position whose meaning could still change.Misconception: that positions are permanent identifiers, like a database primary key. In AgileLog, positions beyond an open promotable cFork's fork point are provisional — which is precisely why the paper stops returning append indexes there too.
Problem 5 · medium
A misbehaving agent opens a promotable cFork and then hangs forever — never promoting or squashing it. What breaks, and what bounds the damage?
Show answer
Every consumer of the parent log is blocked from reading past that cFork's fork point indefinitely — a single stuck agent can stall production consumers forever. Bolt's optional lease mechanism bounds this: if leasing is enabled, the metadata layer internally squashes any promotable cFork whose lifetime exceeds a configured duration (the paper demonstrates 500 ms), after which the parent's blocked reads resume automatically.Misconception: that promotable cForks are inherently safe because they're "just isolated forks." The isolation is one-directional in the other sense too — an unresolved promotable cFork imposes a real liability on its parent until it's leased away.
Problem 6 · easy
A testing agent needs to inject synthetic fraud transactions interleaved with real production data, but those synthetic records must never leak into the real stream. Which fork type, and why?
Show answer
A non-promotable cFork. It inherits the real transaction stream live (so injected fraud events sit in realistic temporal context) while its own writes remain private to it forever, via unidirectional write isolation — and since it was never created with the promotable flag, there's no path for those synthetic writes to ever land on the parent.Misconception: that any cFork risks polluting the parent. Only promotable cForks can ever affect the parent, and only via an explicit promote call — a plain cFork's writes are structurally incapable of leaking upstream.
Problem 7 · hard
Severed forks (sForks) don't impose the "block parent reads beyond the fork point" restriction that promotable cForks do. Why is sFork exempt?
Show answer
The restriction exists only because a promotable cFork's future promotion could retroactively change positions on the parent. An sFork provides bidirectional write isolation — by definition, it can never be folded back into the parent (it's not promotable), so nothing it does can ever change what a parent position means. There's no future event to protect readers from.Misconception: that "isolation" is a single property that implies the same restrictions everywhere. sFork and cFork are isolated in different directions (bidirectional vs. unidirectional), and the read-blocking cost is specifically the price of cFork's promotability, not of forking in general.
Problem 8 · medium
Two agents each create a promotable cFork off the same parent to explore different content-moderation strategies, and both eventually call promote. What happens?
Show answer
Only the first promote call succeeds and becomes the new parent; AgileLog internally squashes the other promotable cFork(s) automatically. There is no merge of the two explored paths — this is a "first past the post," fast-forward-only mechanism, not a general merge.Misconception: that promote resolves conflicts like a database merge. The paper is explicit that a general multi-fork merge would break linearizable ordering of appends, so it deliberately isn't offered — exploration picks a winner, it doesn't combine winners.

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What's the actual difference between a "fork" and a "branch"?▾
The paper is softer here than a hard rule: it notes that forking is sometimes called branching, and that branching is desirable when divergent paths are meant to eventually be merged. AgileLog's promote is itself a restricted merge — a single-child, fast-forward-style operation, not a general merge of conflicting histories — which is why the paper favors "fork" for its primitive rather than claiming full branch/merge semantics.
Q2Why can't an agent just read the main log directly with some kind of filter, instead of forking?▾
Reading the live log directly means the agent's read load lands on the same broker serving production traffic — exactly the contention the paper measures (14×/130.8× latency degradation on Kafka). A fork moves that load to a separate broker while still exposing the same data, via the shared object store underneath.
Q3How is linearizable interleaving on a cFork actually guaranteed, mechanically?▾
Both the parent's appends and the cFork's own appends are sequenced by the same metadata layer, which assigns positions from the cFork's current tail. Since the tail is updated (even if lazily resolved) whenever the parent gets a new record, any append to the cFork issued after that update is guaranteed to be ordered after it — the same consensus-backed sequencing that orders a single log's appends extends naturally across the inheritance relationship.
Q4Do writes on a non-promotable cFork ever reach the parent?▾
No — that's the point of not setting the promotable flag. They remain private to that cFork (and its descendants) forever, by construction, useful for testing and what-if exploration where the writes are synthetic and should never contaminate production data.
Q5Why not build this on top of Kafka's existing mirroring tools (MirrorMaker, etc.)?▾
Mirroring tools continuously copy data to a separate cluster — that gives isolation, but fork creation and maintenance require ongoing, expensive data movement. Bolt's zero-data-copy approach (shared objects, separate metadata pointer) is fundamentally cheaper because it never duplicates the underlying records at all.
Q6Doesn't the metadata layer (Raft) become the new bottleneck once you add fork bookkeeping?▾
That's exactly the risk Bolt's techniques target. Naive approaches (BoltNaiveCF, Bolt-ET) do overwhelm the metadata layer at scale (§6.4). The Lazy Tail Tree keeps each fork-related operation at O(log n) regardless of fork count or nesting depth, which the paper shows keeps root-log throughput essentially flat with 0, 10, and 100 cForks, and even with 1000 in isolated metadata-layer benchmarks.
Q7How is this different from database branching systems like Dolt or Neon?▾
Those systems branch a point-in-time database snapshot — closer to AgileLog's sFork. AgileLog's distinguishing contribution is the continuous fork, which keeps inheriting a live, ever-growing stream after the fork point — a requirement specific to streaming data that snapshot-style database branches don't need to solve.
Q8Does creating a fork cost anything at the object-storage layer?▾
No new objects are written at fork time — the fork's metadata simply references existing objects. Ongoing reads from a cFork do add read load to the object store, but cloud object stores are built to scale reads to very high aggregate throughput (the paper cites ~220 GB/s achievable with S3 using 4 MB objects and multiple object-name prefixes), so this isn't the bottleneck fork isolation needs to solve.
Q9Is there a limit to how deep or wide fork hierarchies can get?▾
The paper tests star (wide, shallow), balanced (fan-out 4), chain (deep, narrow), and irregular hierarchies up to 1M total logs, and finds parent insert latency differs by less than 0.5 µs across shapes, growing only logarithmically with total log count — so hierarchy shape isn't a practical limiting factor.
Q10What happens to a rogue agent's cFork if it's never promoted or squashed?▾
Without leasing, it can block the parent's reads beyond its fork point indefinitely. With leasing enabled, Bolt's metadata layer squashes it automatically once its configured lifetime expires, healing parent consumer throughput without any external intervention.
Q11What's left for future work?▾
The paper focuses on single-agent, multi-tool architectures; it doesn't deeply explore multi-agent coordination on shared forks, richer merge semantics across multiple promotable cForks, or dynamic broker scaling policies for fork placement — the current design co-locates many forks of a parent on one broker as a simple heuristic, which the paper notes applications can override.

Glossary & further reading

Every term in one place, key numbers with their provenance, then a path to go deeper.

Core terms
AgileLogThe abstraction: a shared log offering forking (cFork, sFork), promote, and squash as core primitives.
BoltThe system implementing AgileLog atop a diskless architecture; ~21K LOC C++, uses eRPC, MinIO/S3, and Raft.
cFork (continuous fork)Shares history to the fork point, then continuously inherits all further parent appends; own appends stay private unless promoted.
sFork (severed fork)Regular fork semantics: disconnected from the parent at (or before) the fork point; bidirectional write isolation.
Unidirectional write isolationcFork's isolation property: parent writes visible to the child, child writes never visible to the parent (unless promoted).
promoteFolds a validated (promotable) cFork's post-fork records into the parent as a metadata-only operation.
squashDeletes a fork's metadata-layer state; used to discard sandboxes or resolve an unwanted promotable cFork.
HLI (Hierarchical Log Index)Lets a fork's index recursively defer to its parent's for positions before the fork point — zero metadata copy.
LTT (Lazy Tail Tree)An Euler-tour-over-BST structure that propagates a parent's new appends to all descendants' tails in O(log n).
Supporting terms
Diskless architectureStateless brokers + a shared object store for durability + a metadata layer that sequences positions.
Metadata layerThe Raft-replicated group maintaining each log's index (position → object/byte-range) and tail.
SMRState-machine replication — the consensus-backed technique making the metadata layer fault-tolerant.
Local countPer-entry field in HLI recording the cumulative count of locally-appended records up to and including that position — enables recursive position translation.
earliest-fpFork point of the oldest open promotable cFork of a log; parent reads beyond it are blocked.
Lease-based internal squashOptional timeout after which Bolt auto-squashes a stalled promotable cFork to bound rogue-agent impact.
BoltNaiveCF / Bolt-ETAblation variants: eager full-index copy to descendants / eager tail-only updates (no LTT), used to isolate each technique's contribution.
MCPModel Context Protocol — the tool-invocation interface practical systems already use to expose streams to agents.
lc-workloadThe paper's label for the latency-critical, production-style workload whose isolation from agents is being measured.

Scalog: Seamless Reconfiguration and Total Order in a Scalable Shared Log medium

Ding et al. · NSDI 2020

Separates data and metadata like Bolt, but with stateful (disk-based) storage servers — prone to the same contention as Kafka.

Jia & Witchel · SOSP 2021

Another data/metadata-separated shared log; cited alongside Scalog as lacking forking as a primitive.

Luo, Bhat, Hu, Alagappan, Ganesan · SOSP 2024

Prior work from the same group on shared-log design; establishes context for AgileLog's lineage.

The FuzzyLog: A Partially Ordered Shared Log hard

Lockerman et al. · OSDI 2018

The paper notes FuzzyLog implicitly allows forked histories during network partitions, but not as a deliberate first-class primitive.

Tardis: A Branch-and-Merge Approach to Weak Consistency hard

Crooks, Pu, Estrada, Gupta, Alvisi, Clement · SIGMOD 2016

Prior branch-on-conflict system with real merge capability — the paper contrasts promote's restricted, single-child fast-forward against this more general merge.
