Baking the decision into the machine code, not interpreting it

A placement decision that takes longer than the time it saves is worthless. This is the plain-English story of turning a trained regression tree into a handful of cmp instructions — fast enough to call from inside a scheduler or allocator.

📄 "Code Generation from Regression Trees for µs-Scale Decisions in OSes" · Friesel, Lütke Dreimann, Spinczyk 🎓 Some C++/x86 assembly reading assumed — primers cover it ⏱ ~25 min read
🌳

If the tree's shape is known at compile time, don't walk it at runtime — let the compiler unroll it into branches with the thresholds baked in as immediates.

Before you begin · Quick glossary

The paper's acronyms, up front

RT = conventional regression tree (CART). RMT = regression model tree (boolean/categorical splits, linear-regression leaves). RF = regression forest (ensemble of RTs, here boosted via XGBoost). plainC / plainC++ / templateC++ = the three code-generation strategies compared. NMC = near-memory computing. HBM = high-bandwidth memory. CXL = the memory-expansion interconnect this all feeds into.

1Why a placement decision needs a latency budget▾

The paper's opening example: spending 5 ms to decide on a placement that reduces latency by 2 ms is a net loss. So the decision itself must cost far less than the benefit it buys — the paper targets nanosecond-to-microsecond decisions.

Now you're ready: every latency number in this guide is being judged against that same yardstick — is it cheap enough to be worth calling on the hot path of a scheduler or allocator?
2What a regression tree is▾

A function 𝑓: ℝⁿ→ℝ. Each internal node asks "is feature xi ≤ threshold z?"; each leaf holds a predicted value. Walking from root to leaf along the answers gives the prediction — no more than d comparisons for a tree of depth d.

Now you're ready: the paper's Fig. 1 tree — depth 2, 7 nodes — is the running example used throughout this guide.
3Three flavors: RT, RMT, RF▾

RT — CART-style, numeric thresholds. RMT — splits only on boolean/categorical features (multi-way), leaves hold linear formulas over numeric features. RF — an ensemble of trees (here, XGBoost-boosted); the prediction sums each tree's output.

Now you're ready: all three share the same core per-node array idea, but it isn't identical across the board — forests add a list of trees plus a summing traversal on top, and RMTs need more involved changes to the node structure and traversal function. The differences show up in code complexity as well as in latency and size.
4Depth 𝑑, node count 𝑚, and why they're separate▾

Trees aren't necessarily balanced, so depth and node count must be tracked independently: 2𝑑+1 ≤ 𝑚 ≤ 2𝑑+1−1. Inference cost scales with the number of comparisons actually made — bounded by 𝑑, not 𝑚.

Now you're ready: every latency model in Table 1 is stated per unit of depth (𝑑) or depth×tree-count (𝐾𝑑), not per node.
5Encoding a tree as a flat array▾

Instead of a pointer-chasing object per node (16 bytes per decision node just for the two 8-byte pointers to its subtrees on 64-bit), every node is packed into a pre-order array: {rightChild, feat, threshold}. Pre-order traversal means the left child is always at index j+1, so it never needs to be stored.

Now you're ready: this single encoding (Listing 1/2) underlies plainC, plainC++, and templateC++ — only the traversal code differs.
6Three ways to walk the same array▾

plainC: a branch-free loop using arithmetic to pick the next index. plainC++: a recursive method the compiler turns into tail-recursive loop code. templateC++: a C++ template parameterized by node index, expanded at compile time into nested if/else — no loop, no recursion, no runtime array lookups.

Now you're ready: "How It Works" walks through the generated assembly for all three, for the same tree.
7Executable data structures▾

Instead of separating "data" (the tree) from "code" (the traversal function), templateC++ compiles the tree's structure directly into the instruction stream — thresholds become immediate operands in cmp instructions. The tree is the code.

Now you're ready: this is why templateC++ trees can't be retrained at runtime — the structure must be a C++ constexpr known to the compiler.
8Quantization: int8/16/32 vs float▾

Thresholds and inputs can be stored as 8-, 16-, or 32-bit signed integers, or as 32-bit floats. Smaller integer types mean smaller nodes and — crucially for templateC++ — thresholds that fit directly as machine-code immediates. Floats can't be embedded that way and must live in a data segment.

Now you're ready: nearly every speed and size result in this paper splits by data type first — int8 is where templateC++ shines brightest.
9How the numbers were measured▾

An Intel Xeon E5-2650 v2 @ 2.6 GHz (2013-era, Linux 6.12) — chosen as a conservative baseline since newer CPUs should do better. Trees were built with scikit-learn (RT), XGBoost (RF), and custom code (RMT), swept across 6 configuration dimensions, with each configuration measured several hundred times and the median taken.

Now you're ready: every latency figure that follows is a median over hundreds of runs on that specific (deliberately modest) CPU.
The whole story in one place

Compile the tree, don't interpret it

Why regression trees fit an OS's latency budget, and what compile-time template expansion buys you.

Modern servers need placement decisions — which core, which memory tier, which NMC device — not just scheduling decisions. Hand-crafted heuristics for this are hard to reason about and rarely tuned per-system. The paper's proposal: replace them with small machine-learning models, provided inference is cheap enough to not eat the savings it's meant to produce.

Neural networks are ruled out immediately — a single neuron can cost dozens to thousands of operations, and networks have hundreds to millions of neurons. Regression trees, by contrast, cost at most d comparisons for depth d. The paper examines three flavors (RT, RMT, RF) and three ways to compile them to C/C++: plainC (branch-free loop), plainC++ (tail-recursive method), and templateC++ — compile-time template expansion that inlines the entire tree into nested branches, turning the tree into an executable data structure.

Every tree is stored with the same core flat, pre-order array of {rightChild, feat, threshold} nodes — so the main variable is how the traversal is generated. Measured on a 2013-era Xeon, plain compiled C/C++ is already 2–3 orders of magnitude faster than Python inference. templateC++ goes further: up to an order of magnitude faster still for 8-bit integer data, while also halving code size — because thresholds become immediate operands baked directly into cmp instructions, with no tree array left in memory at all.

🍯 Key takeaways

  • Median inference latency ranges 23 ns to 79 µs depending on tree type, depth, and data type.
  • Every tree — RT, RMT, or RF — builds on the same flat pre-order array idea; only the traversal code (and, for forests/RMTs, some extra structure) differs.
  • Compiled C/C++ beats Python inference by 2–3 orders of magnitude on the same hardware.
  • templateC++ inlines the whole tree into branches at compile time — up to 10× (int8 RF: up to 14×) faster than plainC, and (for int8) about half the code size.
  • Trade-off: templateC++ requires the tree to be a compile-time constant — no runtime retraining without recompilation.
  • At a 1 µs decision budget, templateC++ supports depth up to ~128 (int8 RT) or a tree-count×depth product up to ~650 (int8 RF).
Five everyday pictures

How to think about tree code generation

Each stands alone. Every card ends with where it stops being literally true.

The core idea

A recipe card vs a pre-set oven

plainC/plainC++ hand the CPU a recipe card (the tree array) and a general-purpose reader (the traversal loop) that looks up each step at runtime. templateC++ instead pre-configures the oven itself — the dial settings (thresholds) are welded into the machine as immediate operands. No card to read; the machine is the recipe.

Where it breaks: a welded-in oven can't be reset to bake something else — exactly why templateC++ trees can't be retrained without recompiling.
The encoding

A choose-your-own-adventure book

"Turn to page 1 if the answer is yes; turn to page 47 if no." Pre-order layout means the "yes" page is always the very next page — free, no printed reference needed — while the "no" page number (rightChild) has to be printed explicitly. That's the entire node struct: a feature, a threshold, and one page number.

Where it breaks: a real book can't have thousands of nested "turn to page X" branches printed as literal text efficiently — but a compiler can, which is templateC++'s whole trick.
Quantization

Rounding to the nearest inch vs a laser ruler

An 8-bit integer threshold is a coarse ruler — imprecise, but its "reading" is a single small whole number, which a compiler can stamp straight into an instruction. A float is a laser ruler: precise, but the reading needs its own storage slot elsewhere, so the instruction has to go fetch it.

Where it breaks: the analogy suggests precision is purely a downside; in practice float thresholds can represent real-valued cutoffs int8 simply cannot, which is exactly why the paper still measures both.
Compile-time vs runtime

A thermostat you can adjust vs one set in the factory

plainC/plainC++ trees are loaded at runtime, so the paper notes they support retraining without a recompile — like turning a thermostat dial. templateC++ trees are set once, in the factory (at compile time) — changing the target temperature means building a new unit.

Where it breaks: a factory-set thermostat is usually a downgrade; here it's the opposite — giving up the dial is exactly what buys the 10× speedup.
The framing

A toll booth that costs more than the toll

A shortcut that saves 2 minutes of driving is pointless if the toll booth for it takes 5 minutes to process your payment. The paper's whole motivation is making the "toll booth" (the placement decision) fast enough that the shortcut (the better placement) is a net win.

Where it breaks: a toll booth's cost is fixed; a tree's decision cost is tunable via depth and quantization — the paper's real contribution is showing how far that dial can be pushed.
The full explanation

How it actually works

From node encoding to the generated assembly, section by section.

1 · Encoding a tree as a flat, pointer-free array

Each node is {rightChild: uint16, feat: uint8, threshold: inout_t}. Pre-order layout means the left child is always at index+1 — never stored. A leaf sets feat = 255 (UINT8_MAX) and rightChild = 0, with its predicted value stored in threshold.

2 · Three traversal strategies over the same array

MethodControl flowWhere thresholds liveRetrainable at runtime?
plainCsingle loop, branch-free index arithmeticplain array in memoryyes
plainC++tail-recursive method, compiled to a loopplain array in memoryyes
templateC++compile-time-expanded nested if/else, no loop or callimmediate operands (int); rodata (float only)no — compile-time constant

For plainC, the compiler emits ≤12 instructions per loop iteration with just one (unlikely) conditional jump for the loop-exit test. plainC++'s tail recursion compiles to an 11-instruction loop with two conditional and two unconditional jumps. Both fit the traversal function in 44–62 B of text, with the tree array (4–8 B/node) separate in rodata for the paper's benchmark builds.

3 · Template expansion: the tree becomes the code

templateC++ makes the node index a template parameter. The compiler instantiates one traverse<i> per node, and because applications only ever call traverse<0>, it inlines every instantiation into one function — a series of nested if/else statements shaped exactly like the tree. For Fig. 1: if (x3≤7) return (x1≤3)?1:2; else return (x3≤121)?7:5;.

For integer types, thresholds become immediate operands directly in cmp/cmpb instructions — data and rodata segments end up empty; everything lives in text, improving locality. Only float thresholds must still be stored separately. For the Fig. 1 tree at int8, this compiles to 31 bytes total (code + data combined) — under half of plainC/plainC++'s space for the same tree.

4 · The trade-off, and the 1 µs budget it implies

⚠
The catch: a templateC++ tree's array must be a C++ constexpr — it cannot be swapped at runtime. plainC/plainC++ trees remain ordinary runtime data, and the paper notes they support retraining at runtime, unlike templateC++, which needs a recompile.

Given the int8 RT coefficient of 7.8 ns/level, a 1 µs budget supports depth up to 1000/7.8 ≈ 128 — matching the paper's own stated figure. For int8 regression forests (1.5 ns per 𝐾·𝑑 unit), the same budget supports a tree-count×depth product up to ~650.

Follow the numbers

Worked examples

Four calculations, straight from the paper's own figures.

① Tracing an inference through the array

Using Listing 2's array for Fig. 1, evaluate 𝑓(10, 20, 30).

  1. Start at index 0: feat=3, threshold=7. Compare x3=30 to 7 → 30 > 7, so take the right child: index = rightChild = 4.
  2. Index 4: feat=3, threshold=121. Compare x3=30 to 121 → 30 ≤ 121, so take the left child: index = 4+1 = 5.
  3. Index 5: feat=255 → leaf. Return threshold = 7.
  4. Result: 𝑓(10,20,30) = 7, matching the paper's stated value exactly, in just 2 comparisons (= tree depth).
🍯
Note x2 never appears in any comparison — the tree simply doesn't need it for this prediction, exactly as the paper observes.

② Sizing the node struct

What does the 7-node Fig. 1 tree cost in plainC/plainC++ at int8, vs templateC++?

  1. Per-node cost (int8): 2 B rightChild + 1 B feat + 1 B threshold = 4 bytes.
  2. Array for 7 nodes: 7 × 4 B = 28 bytes in rodata, plus 44–62 B of traversal code in text.
  3. templateC++ for the same tree: thresholds become immediates inside cmp instructions — rodata is empty, everything is text. Paper states this totals 31 bytes combined.
  4. Comparison: 28 B (data) + ~50 B (code) ≈ 78 B for plainC, vs 31 B for templateC++ — less than half, matching the abstract's "halving the code size" claim for 8-bit data.

③ How deep can a templateC++ tree be at 1 µs?

Using Table 1's int8-RT coefficient for templateC++ (7.8 ns per level).

  1. Budget: 1 µs = 1000 ns.
  2. Max depth: 1000 ⁄ 7.8 ≈ 128 levels.
  3. Compare to plainC (13.9 ns/level): 1000 ⁄ 13.9 ≈ 72 levels — templateC++ affords nearly double the tree depth for the same time budget.
💡
This is exactly the Discussion section's headline: "templateC++ allows us to use trees with a maximum depth of up to 128" for a 1 µs decision.

④ The order-of-magnitude forest speedup

Using Table 1's int8-RF coefficients (ns per unit of 𝐾·𝑑): plainC = 15.4, templateC++ = 1.5.

  1. At 𝐾·𝑑 = 650 (e.g. 𝐾=65 trees, depth 10): templateC++ = 1.5 × 650 = 975 ns — just inside the 1 µs budget.
  2. Same forest under plainC: 15.4 × 650 = 10,010 ns ≈ 10 µs — an order of magnitude over budget.
  3. Speedup ratio: 15.4 ⁄ 1.5 ≈ 10.3×, matching the abstract's "reduce inference latency by up to an order of magnitude."
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why doesn't the node struct store a "left child" index?
Show answer
Nodes are stored in pre-order, so the left child of the node at index 𝑗 is always at index 𝑗+1 — storing it would be redundant. Only the right child's index has to be recorded explicitly, since it isn't at a fixed offset.Misconception: that every child pointer must be stored explicitly, as in an object-per-node design. The flat pre-order layout makes half of them implicit.
Problem 2 · medium
Compute plainC and templateC++ latency for an int32 RT of depth 𝑑=10, using Table 1 (14.2 ns/level and 7.9 ns/level).
Show answer
plainC: 14.2 × 10 = 142 ns. templateC++: 7.9 × 10 = 79 ns. Speedup ≈ 1.8× — smaller than the int8 case, because int32 thresholds still fit as immediates but the narrower win margin reflects less aggressive quantization.Misconception: that templateC++'s speedup is always ~10×. The order-of-magnitude figure is specific to int8 (especially for forests); int32 gains are far more modest.
Problem 3 · medium
Why is templateC++'s speedup over plainC smaller — or even a regression — for float thresholds?
Show answer
A 32-bit float cannot be encoded as an x86_64 immediate operand the way small integers can, so float thresholds must still be stored in a data segment and loaded at runtime — losing the "bake it into the instruction" advantage that drives templateC++'s int8 wins. The paper notes floating-point forests are "the only exception" to templateC++'s general speedup, and float trees can even be up to ~6× larger in code size.Misconception: that template expansion is a universal win. Its biggest payoff is specifically tied to small-integer thresholds fitting as immediates.
Problem 4 · hard
Why is templateC++'s speedup over plainC larger for regression forests (up to 14×) than for single regression trees (up to ~2× for int8)?
Show answer
A forest inference sums many trees' predictions, so templateC++ eliminates per-tree loop/function overhead 𝐾 times over — each tree's comparisons collapse into flat inlined branches with zero looping machinery, and there's no array indexing or loop-exit test repeated per tree. A single tree has less traversal overhead to eliminate in the first place, so the relative gain is smaller.Misconception: that speedup scales the same way for trees and forests. Forests amplify templateC++'s advantage because there's more traversal overhead (per tree, K times) to remove.
Problem 5 · medium
A team wants to retrain their placement model online, every few minutes, without recompiling. Which codegen method should they pick, and what do they give up?
Show answer
plainC or plainC++ — both keep the tree as ordinary runtime data, so the paper notes they support retraining without recompiling. They give up templateC++'s latency and size advantages (up to 10× slower, up to 2× larger for int8), unless they add a dynamic-recompilation step to regenerate templateC++ code after each retrain.Misconception: that templateC++ is strictly "the better" method. It's only better when the tree structure is fixed at compile time — runtime-updatable models need the other two.
Problem 6 · easy
Why were neural networks ruled out for this use case before any measurement was even done?
Show answer
A single neuron already costs dozens to thousands of math operations depending on layer type, and typical networks contain hundreds to millions of neurons — far exceeding the nanosecond-to-microsecond budget the paper targets, regardless of implementation cleverness. Regression trees, by contrast, cost at most 𝑑 comparisons.Misconception: that any ML model can be made fast enough with the right code generation. Some model classes are asymptotically too expensive for this latency regime before optimization even begins.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does this paper contribute?▾
Three C/C++ code-generation methods (plainC, plainC++, templateC++) for regression trees/forests, a shared pointer-free array encoding, and a systematic latency/size analysis across data types and tree complexity — showing templateC++ (compile-time template expansion) is up to an order of magnitude faster and, for 8-bit data, roughly half the size of conventional approaches.
Q2Is this paper about the machine-learning training side?▾
No — training (which algorithm, which hyperparameters, how to build the input feature vector from system state) is explicitly out of scope. The paper only addresses whether trained models can be executed fast enough at inference time.
Q3Why regression trees instead of classification trees?▾
Because computers must encode categorical outputs as numbers anyway, the paper builds on the more general regression formulation (ℝⁿ→ℝ or ℤⁿ→ℤ); everything examined applies equally to generic decision trees.
Q4What is a regression model tree (RMT), concretely?▾
A tree whose internal nodes split only on boolean/categorical features (with multi-way splits for categories), and whose leaves hold linear regression formulas over the numeric features. It combines tree-friendly boolean handling with regression-friendly numeric handling.
Q5Why does templateC++ need constexpr?▾
Template expansion happens entirely at compile time — the node index is a template parameter, so the compiler must know the tree's full structure while compiling. Marking the array constexpr tells it that's safe.
Q6Does templateC++ ever lose to plainC/plainC++?▾
Rarely — under 1.7% of all configuration pairs show a slowdown, and those are concentrated among float-threshold forests, where immediates aren't available and floats must still be fetched from a data segment.
Q7How is this relevant to memory tiering / CXL work?▾
The paper frames this explicitly as infrastructure for placement decisions on heterogeneous memory (DDR, HBM, NMC, CXL): a tiering policy that decides "which tier" per allocation is itself a placement function, and this work is about making that function's inference cheap enough to sit on a fast path — the same concern that motivates avoiding expensive migration-decision logic in DRAM/NVM tiering.
Q8What CPU were these numbers measured on, and does that matter?▾
An Intel Xeon E5-2650 v2 @ 2.6 GHz (2013), chosen deliberately as a conservative, decade-old baseline. The authors call the resulting measurements "rather conservative" and expect newer CPUs to do better; they also note that Linux-based latency measurements are inherently noisy. So treat these figures as conservative estimates on old hardware, not as strict upper bounds.
Q9What's left for future work?▾
The paper only covers code generation for regression trees in detail (forests and model trees extend the same ideas but aren't shown due to space); actual learning algorithms, runtime placement policies, and end-to-end OS integration are left open. Related work also notes a broader gap: no prior publication provides this kind of fine-grained latency/size trade-off analysis for tree-based runtime decisions.

Glossary & further reading

Core terms
RTConventional regression tree (CART): binary numeric splits, constant leaf values.
RMTRegression model tree: boolean/categorical multi-way splits, linear-regression leaves over numeric features.
RFRegression forest: an ensemble of trees (here, XGBoost-boosted) whose predictions are summed.
plainCBranch-free loop traversal using index arithmetic; no function calls or recursion.
plainC++Recursive traversal method embedded in the node struct; compiler converts it to a tail-recursive loop.
templateC++C++ template expansion that inlines the entire tree into nested if/else at compile time — an executable data structure.
inout_tThe generic type used for feature/threshold values: int8, int16, int32, or float in this paper's experiments.
Supporting terms
Pre-order traversalNode storage order where a node's left child is always at the very next array index — never needs to be stored.
rightChild / feat / thresholdThe three fields of a node struct (Listing 1); feat=255 marks a leaf.
Immediate operandA constant value embedded directly in a machine instruction (e.g. in cmpb) rather than loaded from memory — what makes templateC++ int thresholds free to read.
Tail recursionA recursive call that is the last operation in a function; compilers convert it into a loop with no call overhead.
Executable data structureA structure whose logic is expressed as code rather than as separately-interpreted data — the template-expanded tree.
QuantizationRepresenting thresholds/features as fixed-width integers (8/16/32-bit) instead of floats, to shrink nodes and enable immediates.
NMC / HBM / CXLNear-memory computing / high-bandwidth memory / the memory-expansion interconnect — the heterogeneous placement targets motivating this work.
ROM usageCode + read-only data footprint of the generated inference function and its tree.
