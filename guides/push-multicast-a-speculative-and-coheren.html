HPCA 2025 · A Field Guide

Making the cache guess who needs data next, instead of just answering who asked

Four cores read the same shared line. A conventional LLC replies to each request one at a time — same data, four separate trips. This is the plain-English story of Push Multicast, a scheme that turns one reply into a proactive broadcast.

📄 "Push Multicast" · Huang, Chen, Wang, Hughes, Ding, Xie 🎓 Coherence/NoC basics assumed lightly — primers fill the rest ⏱ ~30 min read
📡

When the LLC answers one reader of a shared line, PUSH a copy to every other known sharer too — don't just reply to whoever asked.
Prune duplicate requests in the network on the way there.

Before you begin

Eight ideas the paper leans on

You already know caches and coherence from the memory-tiering side. These cards fill in the NoC-specific machinery this paper actually modifies — mesh routing, virtual channels, in-network state — skip whatever you already know.

Push Multicast (the solution) L1Bingo-L2Stride (eval baseline) in-network filter machinery reactive LLC (the problem)
1Tiled manycore + mesh NoC — the fabric this paper targets▾

Each tile on the chip holds a core, private L1/L2, and a slice of a globally shared LLC. A given physical address hashes to exactly one "home" slice. Tiles talk over a mesh network-on-chip (NoC): a grid of routers, one per tile, each with 5 ports (North/East/South/West + Local).

Packets move as flits (flow-control units); the head flit carries address and source/destination. A request is a 1-flit packet; a data response is larger (5 flits here).

Now you're ready: Push Multicast lives entirely in the LLC controller and the routers of this mesh — no changes to cores, ISA, or software.
2Dimension-order routing: XY vs YX▾

XY routing moves a packet fully along X (horizontal) first, then Y (vertical). YX does the reverse. Deterministic routing like this guarantees a fixed, predictable path for any source-destination pair.

The paper deliberately sends read requests via XY and responses/pushes via YX — the reverse path. That's not arbitrary: it maximizes the chance that an in-flight push physically crosses paths with a later request for the same line, at some router in between.

Now you're ready: the in-network filter (primer 6) only works because pushes and requests are routed to actually meet.
3Virtual channels and virtual networks▾

A physical link can be shared by multiple logically independent flows called virtual channels (VCs) — this avoids one blocked packet stalling everything behind it. A virtual network (vnet) is a further separation used to break protocol-level dependency cycles (e.g. requests can't block behind responses). This system uses 3 vnets, 4 VCs each.

Virtual cut-through flow control lets a router start forwarding a packet's flits before the whole packet has arrived, but only if the full packet's buffer space is reserved at the next hop — unlike wormhole, which doesn't need that guarantee but can't be dropped mid-flight as easily.

Now you're ready: pushes are placed on their own data-VC to avoid deadlocking against ordinary responses, and virtual cut-through is what lets a router safely drop a whole pushed packet if needed (primer 5).
4Directories, snoop filters, and the sharer list▾

To keep caches coherent, the LLC (or a separate structure) tracks, per line, which private caches currently hold a copy — the sharer list. This is the same bookkeeping a CXL Type-3 device's bias/coherence directory does for host-side caching, just scoped to on-chip cores instead of hosts.

Push Multicast adds nothing new here — it just reads the existing sharer list to decide who else should get a copy when one sharer's request is serviced.

Now you're ready: the "cost" of knowing who to push to is already paid by ordinary coherence tracking; Push Multicast just repurposes that list.
5Capacity misses vs coherence misses▾

A coherence miss happens because another core invalidated your copy (e.g. after a write). A capacity miss happens because your own private cache is too small to hold everything you're actively reusing, so a line you'll want again gets evicted before you return to it.

This distinction is the paper's whole target: it's about read-shared lines that are re-fetched repeatedly because they got evicted from small private caches (large working sets), not because someone wrote to them.

Now you're ready: this is why the paper explicitly separates itself from prior coherence-prediction work, which targets producer-consumer/migratory (write-driven) sharing, not capacity-driven re-reads.
6In-network filtering — deduplicating in the router, not at the endpoint▾

Normally, deduplication (e.g. request coalescing) happens at an endpoint — the LLC or memory controller sees two identical requests and merges them. An in-network filter instead does this inside a router, mid-flight, before a request even reaches the LLC.

This requires the router to briefly remember "a response for address X, destined for these IDs, is already passing through" — a tiny piece of state, cleared once the response has moved on.

Now you're ready: this filter state is what lets a push double as an answer to a request that hasn't arrived at the LLC yet — killing that request in the network instead of letting it generate a redundant round trip.
7MPKI, injection, and ejection bandwidth▾

MPKI (misses per kilo-instruction) is the usual cache scorecard. On the network side, injection bandwidth is traffic a node puts into the NoC; ejection bandwidth is traffic a node pulls out. A push adds injection traffic at the LLC (fan-out) but can reduce injection traffic at private caches (fewer requests need to be sent at all).

Now you're ready: when you see "LLC injection savings" vs "private-cache injection," they're measuring different points in the same pipe — both matter for whether a technique actually helps.
8MSI/MESI coherence states and transient states▾

In MSI, a cached line is Modified (dirty, exclusive), Shared (clean, possibly multiple copies), or Invalid. Real protocols add transient states between these — e.g. "waiting for acknowledgments" — to correctly handle races between concurrent requests without violating coherence.

Two invariants govern any protocol: Single-Writer/Multiple-Readers (SWMR) and the Data-Value Invariant (a read must return the most recently written value).

Now you're ready: Push Multicast adds one new transient state (Shared-Push, "P") to the directory side precisely to keep pushes from racing incorrectly against writes (How It Works, §5).
The whole story in one place

Push Multicast in a nutshell

The problem, the proactive fix, and how the pieces connect.

In a manycore CPU with a shared LLC, the cache hierarchy is reactive: it only ever answers the request in front of it. When several cores read the same shared line — common in multi-threaded workloads where threads do similar work on different data — each core's private-cache eviction (due to a large working set) forces it to send its own request to the LLC, and the LLC replies to each one separately, even though the data is identical every time. The paper measures this directly: read-shared data makes up 10%–80% of LLC traffic across their workloads, and it's genuinely redundant.

Push Multicast turns the LLC into a proactive agent. When it answers a read from a sharer it already recognizes (not a brand-new one), instead of a plain unicast reply it fires a multicast push to every known sharer of that line at once. The pushed packet acts as a traveling representative of the cache line: a coherent in-network filter in each router along the way can recognize a same-line read request arriving from a destined sharer and drop it on the spot — the push becomes that request's answer. If the push beats the core's own request entirely, a miss silently becomes a hit.

Because blind pushing can backfire — flooding the network when it's already congested, or polluting caches with lines nobody uses — a dynamic pause/resume knob tracks, per private cache, what fraction of received pushes were actually useful, and turns pushing off for cores where it isn't paying off, resuming periodically to recheck.

The payoff: vs a system with L1 Bingo + L2 Stride prefetching, Push Multicast saves an average of 33% NoC bandwidth with a 1.02× geomean (up to 1.56×) speedup on 16 cores, and 43% bandwidth savings with a 1.11× geomean (up to 2.08×) speedup on 64 cores — for about 16.3% extra area on the router alone, which is itself only ~3% of a tile's area.

🧭
For the tiering crowd: the core move here — stop waiting for a request and act on a prediction instead — is philosophically the same shift as proactive hotness-driven page promotion (à la TPP/HeMem) replacing purely fault-reactive demotion/promotion. Push Multicast just does it at cache-line granularity, in the NoC, using the coherence directory as its (free) predictor instead of a PTE access-bit scan.

🍯 Key takeaways

  • Reactive LLCs answer who asked; Push Multicast answers who else will ask, using the existing sharer list — no new predictor structure per line.
  • A coherent in-network filter lets a push prune matching requests mid-flight, turning would-be misses into hits and killing redundant traffic before it reaches the LLC.
  • Blind pushing can hurt (congestion, pollution) — a TPC/UPC feedback knob pauses pushing per-core and resumes it periodically.
  • Two coherence extensions — PushAck (block writes until acked) and OrdPush (order pushes ahead of invalidations in the network) — both preserve the data-value invariant.
  • 16-core: 33% NoC bandwidth saved, 1.02× geomean / 1.56× max speedup. 64-core: 43% saved, 1.11× geomean / 2.08× max speedup.
  • Cost: ~16.3% extra router area (router ≈ 3% of tile area) — nothing on the critical read-hit path.
Six everyday pictures

How to think about Push Multicast

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · Push vs pull

CC'ing the whole team, not replying to one email

A reactive inbox answers each "did you see the report?" message one at a time — same attachment, three separate replies. Push Multicast is hitting Reply-All the first time: the LLC already knows (from the sharer list) who else has been asking about this line, so it broadcasts once instead of waiting for each person to ask.

Where it breaks: Reply-All is free; a hardware multicast still costs real bandwidth to fan out. The whole design is about making sure that fan-out cost is smaller than the redundant unicasts it replaces — which is why it only pushes to known sharers, not everyone.

Sharer establishing phase · Regulars vs strangers

The barista learns your usual before starting it early

A good barista doesn't start making a drink for someone they've never seen order it — that risks a wasted cup. Only once you've become a regular do they start it as you walk in. The LLC does the same: the first read from a new sharer just gets a normal unicast reply (establishing phase); only once a line has a settled group of repeat sharers does the LLC start pushing to all of them speculatively (push activated phase).

Where it breaks: a barista learns preferences over weeks; the LLC's "steady state" check is much cruder — literally just "is this requester already on the sharer list?" It has no memory of how reliable that sharer has historically been.
The pause/resume knob · A tipping habit you re-evaluate

Un-subscribing from a newsletter that stopped being useful

You keep a mental tally: of the last several emails from this newsletter, how many did you actually read? Once the "useful" fraction drops below half, you unsubscribe. Weeks later, out of curiosity, you might resubscribe to check if it's improved. That's the TPC/UPC knob exactly: each private cache tallies total-pushes-received vs useful-pushes-used, opts out (sets `need_push=false`) below 50%, and the LLC periodically re-includes opted-out cores to recheck.

Where it breaks: your unsubscribe decision is permanent until you act; the hardware's resume is on a fixed clock (a Time Window counter) regardless of whether conditions actually changed — so it can flip back on into a still-bad situation and have to re-learn.
Coherence extension · A shared whiteboard rule

Everyone must read the memo before anyone edits it

If a memo is being handed around a room and someone wants to scribble a correction on it, the polite (and correct) rule is: let it finish its current round of readers first, or make it very clear the new edit supersedes the copy in transit, before anyone acts on stale info. Push Multicast's PushAck/OrdPush extensions are this rule made precise — a write racing against an in-flight push either waits for acknowledgments (PushAck) or is guaranteed, by routing order, to arrive strictly after the push (OrdPush).

Where it breaks: the memo analogy has one document; here the same line can be "in transit" toward several different sharers simultaneously, each needing its own acknowledgment or ordering guarantee — which is why the directory needs a dedicated transient state (P) to track it.
Sharing degree · A group discount

The more people splitting one pizza order, the bigger the saving

Ordering one large pizza for 16 people instead of 16 individual slices delivered separately saves the most when all 16 actually show up to share it. The paper measures this directly: on cachebw, a push's average number of real destinations is 15.4 out of a theoretical max of 16 — almost everyone shows up — which is exactly why its bandwidth savings are so large.

Where it breaks: unlike a pizza order, the "discount" here doesn't automatically convert 1:1 into speedup — cachebw's 60% traffic cut only becomes a 25% speedup, because saving bandwidth only helps as much as bandwidth was actually the bottleneck (see Worked Example ①).
The full explanation

How it actually works

Section by section, following the paper's own structure.

1 · Why the LLC is stuck being reactive

Under conventional coherence, the LLC only acts when a request arrives; it has no notion of "who else will want this." The paper's own profiling shows why this matters: private L2 MPKI exceeds 100 on several data-intensive workloads, meaning enormous request volume to the LLC, and read-shared data — lines multiple cores read repeatedly — accounts for 10–80% of that LLC-triggered NoC traffic depending on workload. Worse, consecutive accesses to the same shared line from different cores are typically ~1000 cycles apart, far longer than an LLC lookup — so simple request-coalescing at the LLC (waiting for near-simultaneous requests to merge) rarely finds anything to coalesce.

2 · Push triggering — two phases

The LLC's rule is simple: on a read to a line, check if the requester is new to that line's sharer list. If new → ordinary unicast reply, and add it to the list (sharer establishing phase). If it's already on the list → the access is a re-reference, meaning the workload has settled into a steady pattern, so the LLC triggers a push to the entire sharer list instead of a plain reply (push activated phase).

🔧
Why this is cheap: the sharer list already exists for coherence — this reuses it as a free predictor. No new per-line tracking structure is required, unlike prior coherence-predictor schemes that need a dedicated predictor per line.

3 · Handling a push at the private cache — avoiding deadlock

A private cache normally only expects data in response to its own request. An unrequested push arriving while all ways in the target set are blocked (mid-transaction, awaiting acks) could deadlock if it must be accepted. The fix: pushes travel on their own data virtual channel, and if a pushed line would have to evict a currently-blocked line, the router/cache simply drops the push instead of blocking. No livelock results, because any push or response that answers an actual outstanding miss is always guaranteed to be accepted — dropping only ever affects speculative, unrequested copies.

4 · The coherent in-network filter

Three stages, all running in an augmented 2-stage router pipeline alongside normal route computation and switch allocation:

  1. Filter registration. When a push head flit arrives and its output port is computed, its address and destination bit vector are registered in that output port's filter (plus checked against requests already sitting in the router's queues — "stationary filtering" — and any arriving in the very same cycle — "filtering at port").
  2. Read request filtering (lookup). An arriving read request checks the filter at its input port. If its address and requester ID hit, the request is silently dropped — the in-flight push will serve it.
  3. Filter de-registration. Once the push's tail flit wins switch arbitration and is sent onward, the filter entry is cleared (with a short lazy delay to still catch a request that arrives during the final hop's link traversal).

Per port, the router keeps a filter for each of the other ports (a 5-port router needs 20 filters total), each with one entry per input data virtual channel. See Worked Example ③ for the exact tally and its area cost.

5 · Dynamic pause & resume

Each private cache keeps two counters per its pushed lines: TPC (Total Push Counter — pushes received) and UPC (Useful Push Counter — pushes that served a real miss or got used before eviction). Checking "is more than 50% of pushes useful?" needs no divider — just compare TPC>>1 (half of TPC) against UPC. If (TPC>>1) > UPC, fewer than half were useful, so the cache clears its need_push bit, signaling the LLC (via its next request) to exclude it from future pushes.

At the LLC, a per-slice Push Disabled Requester Bit Map (PDRMap) records who has opted out, and pushes exclude those cores. A periodic Time Window alternates between a "Disable Accepting" phase (opt-outs are recorded) and a "Resume" phase (opted-out cores are re-included and their counters reset, so they get a fresh trial).

# push pause check at private cache, on eviction of a pushed line
if (TPC >> 1) > UPC:      # fewer than 50% of pushes were useful
    clear need_push bit    # tell LLC to stop pushing to me
if TPC ~ overflow:
    TPC, UPC >>= 1          # halve both to keep headroom

6 · Staying coherent — PushAck vs OrdPush

A push is treated as an implicit read, so it never violates the Single-Writer/Multiple-Readers invariant. The danger is a push racing a write: if a write's invalidation reaches a sharer before a stale, already-in-flight push, that sharer could end up with old data. The paper offers two fixes, both serializing pushes and writes:

ApproachMechanismTrade-off
PushAckDirectory adds a transient Shared-Push (P) state; writes are blocked until acks arrive from all pushed sharersExtra ack messages add LLC ejection / private-cache injection traffic
OrdPushRelies on deterministic routing: an invalidation to the same line is stalled in a router if a same-address push is still registered in that port's filterNo ack traffic, but depends on the ordered network property; generally the better performer
💡
Consistency is unaffected. A push behaves exactly like a prefetch — it installs data early, it doesn't change when a write becomes visible. Only the data-value invariant (a read must return the latest write) needs protecting, and both schemes do that.
Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own reported figures.

① cachebw: 60% traffic cut → only 25% speedup — why the gap?

OrdPush cuts cachebw's shared-data traffic by 60% (Fig. 13), yet its speedup over L1Bingo-L2Stride is only ~1.23× (25% faster, Fig. 11). Traffic and speedup should move together — so what eats the difference?

  1. cachebw's sharing is near-ideal: the paper measures an average of 15.4 real destinations per push, out of a theoretical max of 16 (all 16 cores sharing the same array) — 96% of the best case.
  2. So most of the theoretical 16× LLC-side reduction is captured — this is where the reported 60% shared-data traffic cut comes from (traffic, not overall runtime).
  3. But total network traffic isn't the only bottleneck. The paper's link-load analysis (Fig. 14) shows the baseline already concentrates traffic on bisection links; multicasts replicate as they fan out in the X dimension, so traffic shifts toward — and can pile up on — edge routers instead of disappearing.
  4. Net effect: bandwidth pressure drops a lot, but a new (smaller) hotspot forms elsewhere in the mesh, so end-to-end latency — and hence speedup — improves by much less than the raw traffic number suggests.
🍯
Insight: "bandwidth saved" and "time saved" are not the same currency. A multicast's benefit is capped by wherever the new bottleneck ends up, not by how much redundant traffic it eliminated.

② The 50%-useful pause check, worked in binary

A 16-core PushAck configuration uses a TPC Threshold of 64 (Table I). Suppose a private cache has received TPC = 64 pushes, of which UPC = 28 were useful (served a miss or got accessed before eviction). Does it pause pushing?

  1. Compute the useful fraction: 28 / 64 = 43.75% — below the 50% target.
  2. Hardware doesn't divide — it shifts. TPC >> 1 = 64 >> 1 = 32.
  3. Compare: is 32 > 28 (UPC)? Yes.
  4. Decision: pause. The cache clears its need_push bit; the LLC adds it to the PDRMap and stops pushing to it until the next Resume phase.
  5. Check the boundary: if UPC had been exactly 32 (50% usefulness), 32 > 32 is false — pushing stays enabled. The shift-compare correctly implements a ≥50% threshold with only an adder/shifter, no divider.
💡
This is why the paper notes other power-of-two ratio thresholds (25%, 12.5%) are equally cheap — each is just a different shift amount.

③ Router filter cost: from 20 filters to 16.3% area

The paper states: "a 5-port router with 4 input data VCs per port needs 20 filters and each filter has 4 entries." What does that add up to, and what does it cost in area?

  1. Filters per router: 5 ports × 4 filters each (one per other port a push could be forwarded toward) = 20 filters.
  2. Entries per filter: the paper states 4 entries per filter (one per input data VC) → 20 × 4 = 80 filter entries total per router, each holding an address tag plus a destination bit vector — structurally similar to a small snoop-filter entry.
  3. Synthesized cost (ASAP 7nm PDK, RTL vs an open-source baseline router): 16.3% extra router area — 8.8% combinational logic, 1.5% buffers, 6% other non-combinational logic.
  4. Scale to the tile: the paper notes the router itself is only about 3% of total tile area (per the OpenPiton ASIC study). So the filter's contribution to tile area is roughly 16.3% × 3% ≈ 0.5%.
🍯
Insight: even though 16.3% sounds significant, it's 16.3% of a component that's a small slice of the tile — the same "cheap because the base is small" logic that makes UCP's cache-side monitor (a different paper's trick) look inexpensive too.

④ Scaling from 16 to 64 cores

The paper reports both a 16-core and 64-core evaluation. Line up the headline numbers.

SystemNoC bandwidth savedGeomean speedupMax speedup
16-core (4×4 mesh)33%1.02×1.56×
64-core (8×8 mesh)43%1.11×2.08×

Both bandwidth savings and speedup improve going from 16 to 64 cores, rather than degrade — the opposite of what you might expect if multicast overhead scaled worse than the traffic it removes.

💡
Why bigger is better here: more cores means a larger mesh (more hops per unicast reply) and typically higher sharing degree per line, both of which make eliminating redundant round trips more valuable — the same reason the paper widens its TPC Threshold and Time Window settings at 64 cores (Table I) to let pushing run longer before re-evaluating.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A brand-new core reads a line for the first time. Does the LLC push to anyone?
Show answer
No — a request from a requester not yet on the sharer list is answered with a plain unicast, and the requester is simply added to the sharer list (the "sharer establishing phase"). Pushing only triggers once a known sharer re-references the line.Misconception: that Push Multicast pushes on every read. It only activates for re-references from already-known sharers — the first touch is always ordinary.
Problem 2 · medium
A push and a same-line read request enter the same router in the same cycle, both destined for the same output port. Does the filter still work?
Show answer
Yes — this exact case is called out separately as "Filtering at Port": the push's metadata is forwarded to the input port of the computed output direction concurrently with Filter Registration, specifically to catch a same-line request arriving in the very same cycle, not just later ones.Misconception: that the filter can only catch requests that arrive strictly after registration. Same-cycle arrivals and even earlier ("stationary") requests already queued are both explicitly handled.
Problem 3 · hard
Why does a write racing an in-flight push threaten correctness, when a read racing a push does not?
Show answer
A push is treated as an implicit read, so two reads (or a read and a push) never conflict — the SWMR invariant only restricts writers, not readers. But a write changes the line's value; if its invalidation reaches a sharer before a stale push that was already traveling, that sharer would install outdated data, violating the data-value invariant (a read must return the most recently written value). That's exactly the race PushAck and OrdPush are built to prevent.Misconception: that any concurrent push and other transaction is automatically unsafe. Only push-vs-write races are dangerous; push-vs-read races are not races at all under SWMR.
Problem 4 · medium
bfs (irregular graph traversal) does worse under Push Multicast than under L1Bingo-L2Stride. Why, and what mechanism limits the damage?
Show answer
bfs's access pattern is irregular — most lines are touched by only one thread, so there's little genuine read-sharing for pushes to exploit, while L1Bingo-L2Stride can still prefetch long adjacent node lists effectively. Blindly pushing here would waste bandwidth on low-value speculation. The dynamic pause/resume knob limits this: cores quickly see a low useful-push ratio and opt out via the TPC/UPC check, so Push Multicast's effect on bfs stays close to neutral rather than actively harmful.Misconception: that Push Multicast always helps sharing-heavy code and always hurts irregular code equally hard. The pause knob is specifically there to make the irregular case merely neutral, not to prevent the technique from ever being tried.
Problem 5 · medium
MSP (a push-only baseline with no multicast and no filtering) causes large performance losses in most workloads. Why does adding multicast and filtering fix this rather than just adding more overhead?
Show answer
Without multicast, MSP's "push" degenerates into re-predicting and re-sending a separate unicast-like message per sharer, generating redundant traffic on top of the original requests rather than replacing them. Without in-network filtering, none of the later, redundant read requests get pruned, so they still hit the LLC and generate their own responses. Multicast collapses N sends into one; filtering removes the now-redundant requests before they cost anything further. Neither piece alone is enough — MSP has neither, so its speculative traffic is pure addition, not substitution.Misconception: that "pushing data early" is inherently good. It's only good if it *replaces* traffic rather than adding to it — which requires both multicast and filtering together.
Problem 6 · hard
Why does the paper route read requests via XY and pushes/responses via YX, instead of using the same routing algorithm for both?
Show answer
The in-network filter can only prune a request if it physically meets the matching push in some router's input/output ports. If both requests and pushes used the same deterministic route, a later request to the LLC and an earlier push traveling from the LLC back to sharers would tend to travel the *same* path in *opposite* directions only by coincidence. Using the reverse routing order (YX for the return trip) maximizes the geometric overlap between a request's path toward the LLC and a push's path away from it, increasing the odds they cross at some shared router — which is what filtering strictly requires.Misconception: that request/response routing direction is a performance-only detail. Here it's foundational to whether filtering can happen at all, not just how balanced the network load is.
Problem 7 · easy
On PARSEC workloads with low network load, Push Multicast is reported as roughly "neutral." Why would a bandwidth-saving technique have no effect when bandwidth isn't scarce?
Show answer
Push Multicast's benefit comes from removing redundant traffic from a congested resource. If the NoC and LLC aren't under pressure (low injection load, low L2 MPKI, as measured for most PARSEC benchmarks), removing redundant traffic doesn't unblock anything — there was no queueing delay to relieve in the first place. The dynamic knob also keeps any inaccurate pushes from actively hurting these workloads, so the net effect settles near zero rather than negative.Misconception: that any traffic reduction must translate into a speedup. Speedup requires that traffic was the bottleneck; under low load, it typically wasn't.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is this the same thing as prefetching?▾
No, though it behaves similarly at the receiving cache — installing data before it's requested. The difference is who decides and why: a prefetcher on core C predicts C's own future accesses from C's own history. Push Multicast is triggered by the LLC, based on the coherence sharer list of a line another core already asked for — it's cross-core, and it exploits actual observed sharing, not a per-core access-pattern guess.
Q2Does pushing to a core that didn't ask violate coherence?▾
No. A push is treated as an implicit read — it can only move a line to Shared state at the receiver, never grant exclusive/write permission. Since it never lets anyone write, it can't violate the Single-Writer/Multiple-Readers invariant. The only invariant at risk is the data-value invariant, handled by PushAck/OrdPush.
Q3What happens to a push if the destination's cache set is full and blocked?▾
It's dropped. Pushes travel on a separate data virtual channel specifically so an unrequested, speculative line never has to wait behind — or force out — a line involved in an in-progress, blocking transaction. Dropping a push only loses a speculative opportunity; it never loses correctness, since genuine misses are always guaranteed service.
Q4Why not just always push to every possible sharer, all the time?▾
Because inaccurate pushes cost real bandwidth and can pollute caches with lines that get evicted unused — exactly what the ablation study shows: adding pushes alone (before multicast+filtering) actively hurts moderate-to-high-load workloads by flooding the network. The dynamic pause/resume knob exists precisely to stop pushing where it isn't paying off.
Q5How is this different from the NYU Ultracomputer's request combining, or GPU packet coalescing?▾
Those combine requests that arrive at a switch or LLC nearly simultaneously and are not coherent — they don't fit into a hardware cache-coherence protocol and struggle with the all-to-all sharing patterns of manycore CPUs. The paper also measures that consecutive same-line accesses are typically ~1000 cycles apart — far too spread out for simultaneous-arrival coalescing to find much to combine. Push Multicast instead speculates ahead of time using the sharer list, so it doesn't need requests to arrive together at all.
Q6What's the difference between PushAck and OrdPush, and which is better?▾
Both prevent a stale push from racing a write. PushAck adds a transient directory state and blocks writes until every pushed sharer acknowledges — simple, but the acks add extra injection/ejection traffic. OrdPush instead relies on deterministic routing to guarantee invalidations always arrive after a same-line push, with no ack messages. The paper generally finds OrdPush performs better.
Q7Does Push Multicast need any software or ISA changes?▾
No — that's a deliberate design goal, contrasted with prior stream-offload approaches (like Stream Floating) that need changes throughout software, the ISA, the core pipeline, and the cache hierarchy. Push Multicast is confined to the LLC controller and the NoC routers.
Q8Why does mlp benefit less from Push Multicast than cachebw?▾
mlp has high sharing but low network load — it has a low compute-to-memory-access ratio without aggressive SIMD, so it's latency-sensitive rather than bandwidth-bound. Under low load, L1Bingo-L2Stride's latency-hiding prefetching is simply more effective than bandwidth-saving, since bandwidth isn't the constraint (see Practice Problem 7).
Q9Could this apply to GPUs, or to CXL-attached memory?▾
The authors explicitly flag GPUs as a good future fit, since GPU compute engines often execute very similar code at the same time, making sharing easy to predict. The paper doesn't discuss CXL directly, but the underlying idea — treat the shared home/directory as a proactive agent rather than a passive responder — maps naturally onto a CXL Type-3 device's coherence engine, especially for read-mostly, multi-host-shared regions in a pooled-memory setup.
Q10What's left for future work?▾
The paper lists: extending pushes beyond capacity-miss read-sharing to producer-consumer/migratory patterns; enabling pushes on LLC misses (not just hits) via a directory-decoupled sharer predictor; propagating pushes across multiple levels of shared cache; smarter, load-aware multicast routing to avoid shifting (not just reducing) network hotspots; and studying the interplay between pushing and conventional prefetching, which the authors found is not simply additive.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
Push MulticastThe paper's mechanism: the LLC speculatively multicasts a shared line to all known sharers when replying to a repeat sharer, instead of a plain unicast.
Sharer establishing / push activated phaseTwo phases per line: first-time requesters get a unicast and are added to the sharer list; once a requester is already known, later reads there trigger a push.
Coherent in-network filterRouter-level state that recognizes a read request matching an in-flight push's address/destination and drops the request, since the push already answers it.
Filter registration / lookup / de-registrationThe three-stage lifecycle of a router's filter entry: created when a push arrives, checked against incoming requests, cleared once the push departs.
TPC / UPCTotal Push Counter / Useful Push Counter — per-private-cache tallies used to decide whether pushing is paying off (target: ≥50% useful).
Push Disabled Requester Bit Map (PDRMap)Per-LLC-slice bitmap of cores that have opted out of receiving pushes; periodically reset by the Resume phase.
PushAckCoherence extension adding a transient Shared-Push (P) directory state; writes block until all pushed sharers acknowledge.
OrdPushCoherence extension using deterministic (reverse-path) routing to guarantee invalidations always arrive after a same-line push — no acks needed.
Supporting terms
Read-shared dataCache lines multiple cores read (not write) repeatedly — the paper's traffic target, 10–80% of LLC traffic depending on workload.
Capacity miss (vs coherence miss)A miss from a private cache being too small to retain a reused line, as opposed to a miss from another core's write invalidating it.
Virtual cut-throughFlow control letting a router forward flits before the full packet arrives, requiring the next hop's buffer to already be reserved — enables safely dropping a whole pushed packet.
Dimension-order (XY/YX) routingDeterministic mesh routing; requests go XY, pushes/responses go YX, maximizing the chance their paths cross for filtering.
Coalesce (baseline)Prior GPU-style scheme that groups near-simultaneous requests at the LLC and replies via a single multicast — the paper's strongest non-speculative rival.
MSP (baseline)A push-only scheme with no multicast and no in-network filtering, mimicking prior coherence-prediction work; causes large slowdowns from redundant traffic.
Data-Value / SWMR InvariantThe two coherence invariants: reads return the latest write, and only one writer may hold a line at a time while others hold none.
MPKIMisses per kilo-instruction — the private-cache scorecard the paper uses to show which workloads stress the LLC/NoC.

Related work

Combining requests: the NYU Ultracomputer medium

Gottlieb et al. · ACM SIGARCH · 1982

Combines near-simultaneous requests to the same address in network switches; not coherent and not designed for manycore CPU sharer patterns — the historical ancestor of request coalescing.

GPU packet coalescing easy

Kim et al. · ICS · 2017

The "Coalesce" baseline in this paper's evaluation — combines requests at the shared LLC and replies with a single multicast, but only for requests already arriving together.

Memory Sharing Predictor hard

Lai & Falsafi · ISCA · 1999

Coherence prediction for speculative DSM; the conceptual basis for the "MSP" baseline, which lacks multicast and filtering and so generates heavy redundant traffic when applied here.

Stream Floating hard

Wang, Weng, Lowe-Power, Gaur, Nowatzki · HPCA · 2021

Software-described access streams proactively pushed by the cache subsystem — a general but intrusive alternative this paper positions itself against on deployment cost.

In-Network Cache Coherence hard

Eisley, Peh, Shang · MICRO · 2006

Maintains sharer trees inside routers for lower-latency snooping; contrasted with this paper's filter, which needs no persistent per-line router state.

Intel Data Direct I/O (DDIO) easy

Intel documentation

Pushes I/O data directly into the LLC rather than memory — a single-destination "push," unlike this paper's speculative multi-sharer multicast.
