Systems Paper · Submission #906 · A Field Guide

Letting a CXL pod feel like one machine without paying CXL's full latency tax

Eight racked machines share a pool of CXL memory. The question is how much of the OS and app actually needs to live there. StarfishOS's answer: almost none of it — and that's exactly what makes it both fast and crash-resilient.

📄 "StarfishOS: Revisiting Single System Image on CXL with State-Partitioned Microkernel" 🎓 Assumes you already know CXL load/store, coherence, and basic mm — primers skip that ⏱ ~30 min read
🪸

Only state needed for cross-machine coordination pays CXL latency. Everything locality-sensitive stays in private DRAM — and because the CXL slice is small, it can be made crash-recoverable.

Before you begin

Quick glossary, then eight ideas the paper builds on

You already know CXL mechanics and the Linux mm stack, so the primers below skip that and focus on what's new: SSI, microkernel capability state, and crash-safe shared data structures.

Quick glossary — acronyms used throughout
SSISingle System Image — a pod of machines presented as one logical machine: one address space, PID space, file namespace, device namespace.
IPCInter-Process Communication — the microkernel's call path into user-space system services.
PMOPhysical Memory Object — ChCore's capability object representing a set of physical pages.
CapGroup / VMSpaceCapability objects holding, respectively, a process's access rights and its virtual-address-space metadata.
DSMDistributed Shared Memory — user-level libraries that emulate shared memory over message passing; the "user-level SSI" alternative StarfishOS rejects.
LLFreeA lock-free, crash-consistent page-frame allocator StarfishOS adopts for its CXL buddy system.
MPSCMulti-Producer Single-Consumer — the queue pattern shared by StarfishOS's IPC, scheduler, and notification mechanisms.
CASCompare-And-Swap — the atomic primitive that makes StarfishOS's shared queues lock-free.
p-logPersistent operation log — records completed filesystem mutations so a replacement instance can replay them after a crash.
2PCTwo-Phase Commit — the message-passing commit protocol Tigon redesigns its database to bypass using CXL shared memory. StarfishOS instead runs DB×1000 unmodified (2PC intact) and still outperforms Tigon in the paper's comparison.
private DRAM (fast, local) StarfishOS machinery shared CXL (slow, blast-radius risk)
1The CXL pod's partial-failure model▾

You know CXL gives load/store across hosts. The new wrinkle here: in a CXL pod, each host's CPU+DRAM and the CXL memory modules have separate power domains. A host can die while the CXL memory it was touching stays live and electrically fine — unlike a single machine, where losing power kills CPU and memory together.

That means a crashed host can leave shared state (a lock, a half-updated queue) sitting in CXL, visible to every surviving machine.

Now you're ready: the paper's whole resilience story is about making sure that half-updated shared state can never block or crash a survivor.
2Single System Image (SSI)▾

SSI is an old OS idea (Locus, Hive, V, Sprite): make a cluster of machines look like one machine to unmodified software — one PID namespace, one file namespace, one address space, one device namespace. Threads get scheduled pod-wide; cross-machine calls become ordinary load/store instead of sockets or RPC.

StarfishOS's bet: CXL finally makes the "ordinary load/store" part cheap enough for SSI to be worth reviving.

Now you're ready: everything else in the paper is "how do we build SSI's single-image illusion on top of CXL without putting everything in CXL."
3Microkernel vs. monolithic kernel▾

A monolithic kernel (Linux) runs filesystems, drivers, and network stacks inside the kernel, with state cross-linked through pointers across subsystems. A microkernel keeps the kernel to a handful of mechanisms — IPC, scheduling, memory mapping — and pushes everything else (filesystems, process managers) into ordinary user-space processes.

Result: the kernel's own state is small and enumerable, and services can be restarted independently because they don't share kernel-internal state with each other.

Now you're ready: this is the structural reason the paper picks a microkernel (ChCore/seL4-family) as its base rather than Linux.
4Capability-based state: objects, not pointers▾

In a capability microkernel, every kernel resource — a thread, an address space, a page of memory — is a typed object with an explicit identity, and a process holds capabilities (unforgeable references) naming which objects it may touch. ChCore's objects: CapGroup, Thread, VMSpace, PMO, IPC, Notification (Table 2).

Because every piece of state is one of these named, typed objects, you can ask "where should this object live, DRAM or CXL?" as a concrete per-object decision — not a vague architectural question.

Now you're ready: this object model is literally the mechanism StarfishOS uses to decide placement in §7.1 (Figure 9).
5L4-style local IPC vs. remote IPC▾

In seL4/L4-family microkernels, local IPC is a direct, synchronous context switch from client thread to server thread — no scheduler round-trip, almost free. But a context switch only changes which code runs on this core; it can't magically move execution to a server living on a different physical machine.

So cross-machine IPC can't reuse that trick — it needs an actual message to cross to where the server really lives.

Now you're ready: this is exactly why StarfishOS keeps L4-style IPC for local calls but builds a separate CXL-queue-based path for remote calls (§5.1).
6Lock-free & detectably-recoverable data structures▾

"Lock-free" means no thread can block forever waiting on another thread that might never come back (e.g. because it crashed holding a lock). "Detectably recoverable" (Friedman et al.) is a stronger property for persistent/shared memory: after a crash, an observer can tell how far an in-flight operation got from the data structure's own state — no separate crash log needed. In StarfishOS this mostly applies at the queue level: a dequeuer that crashes after flipping a node's status to DOING can leave the request's real-world effects ambiguous, which is why recovery there is component-specific rather than fully automatic.

The trick that makes this work where it applies: design an operation so it linearizes at a single CAS (compare-and-swap) — before that CAS nothing happened, after it the step is done. Not everything in the paper gets this property, though — the appendix is explicit that LLFree's base-page operations are not globally atomic.

Now you're ready: every CXL-resident structure in StarfishOS (IPC queues, scheduler queues, notification lists, the CXL allocator) is built this way.
7Micro-reboot▾

Candea et al.'s micro-reboot: when a software component misbehaves or its host dies, restart just that component — not the whole system. It works well when the component's persistent state lives outside the component itself, so a fresh instance can reload it.

Now you're ready: StarfishOS recovers a failed filesystem instance by booting a fresh one elsewhere and replaying a log — never rebooting the pod (§6.2).
8Page-fault-driven migration▾

Instead of deciding up front where every heap page lives, let the first touch decide: a page is born in the DRAM of whichever machine first allocates it, and only gets promoted to shared CXL memory the moment a page fault proves a different machine actually needs it.

Now you're ready: this is how StarfishOS keeps CXL usage down to a few hundred MiB even for multi-GiB applications (§7.2, Table 4).
The whole story in one place

StarfishOS in a nutshell

The tension, the fix, and how the pieces fit together.

CXL lets multiple hosts share memory through ordinary load/store. Prior work (Tigon, CXL-SHM) shows this can replace expensive message-passing coordination — but only after redesigning the application from scratch (Tigon: 5,000 LoC of changes to an 18,000-LoC database). StarfishOS asks whether an unmodified shared-memory application can get the same benefit, by moving the redesign down a layer, into the OS, via Single System Image (SSI): make the pod look like one big shared-memory machine.

The naive way to build that illusion — put all OS and app state on CXL — breaks two ways at once: CXL is 2–5× slower and 20–80% as much bandwidth as local DRAM, so everything gets slower (up to 3.4× in the paper's measurements); and because hosts and CXL memory fail independently, a crashed host can leave CXL-resident locks or data structures half-updated, threatening to block or crash every surviving machine.

StarfishOS's insight: both problems have the same root cause — too much state on CXL — and one fix: a state-partitioned microkernel. Keep only cross-machine coordination state (IPC queues, scheduler queues, ownership metadata, a handful of capability objects) in CXL; keep everything locality-sensitive (thread stacks, page tables, service internals, most of the heap) in private DRAM. Because the CXL slice is now small, it's affordable to make it lock-free and detectably recoverable, so a host crash degrades gracefully instead of propagating.

The payoff: unmodified Phoenix, DB×1000, and GeminiGraph scale to 8 machines with 2.0–6.0× speedup and zero code changes, beating their hand-redesigned distributed/CXL-optimized versions by up to 4.2× and 2.0× respectively — and applications can soak up CPU cores stranded on other machines, recovering most of the throughput (83–93%) that naive bin-packing (17–77%) would otherwise lose.

🍯 Key takeaways

  • CXL's efficiency problem and its partial-failure problem both come from the same cause: too much state on CXL. One fix handles both.
  • Microkernels make this fix tractable: small, enumerable kernel state + capability objects give per-object placement decisions, which monolithic kernels' implicit cross-linked state doesn't allow.
  • Rule applied uniformly at every layer: kernel modules, user-space services, and applications each keep only coordination state in CXL.
  • The small CXL slice is made partial-failure-safe with lock-free, detectably recoverable data structures (DurableQueue, LLFree) plus micro-reboot + replay for services.
  • Result: unmodified apps auto-scale to a full pod, beating app-specific CXL redesigns, at roughly 1–2% CXL memory overhead for memory-heavy workloads (higher — around 11% — for small, compute-bound jobs like Matrix Mult.).
Six everyday pictures

How to think about state-partitioning

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · State partitioning

Paying a customs duty

Goods that stay within one country move freely; only goods that cross the border pay a duty. StarfishOS treats CXL latency the same way: a thread's own stack, its page table, a service's private bookkeeping never cross a border, so they're duty-free. Only the sliver of state that genuinely needs to be seen by another machine — a queue, a mount-point map — pays the CXL tax.

Where it breaks: customs duties are static policy; StarfishOS's "border" moves dynamically, per page, via page faults — more like a toll that only appears the moment goods actually try to cross.
Why microkernel · Structured state

An itemized packing list vs. a duffel bag

A packing list names every item and its category — you can decide, item by item, "ship this, carry that." A duffel bag just has stuff mixed together — you can't selectively route pieces of it. Capability objects (CapGroup, VMSpace, PMO, …) give StarfishOS the packing list; a monolithic kernel's cross-linked internal state is the duffel bag.

Where it breaks: a packing list is static; capability objects also encode access rights between items, which the list analogy drops entirely.
Partial-failure safety · DurableQueue

A relay baton pass that can't drop the race

In a careless relay, a runner who collapses mid-handoff can take the baton down with them, stalling the whole team. StarfishOS's queues are built so the "handoff" is a single atomic CAS — before it, nothing happened; after it, the baton is fully transferred. A runner (machine) that collapses mid-stride never leaves the baton in limbo for the others.

Where it breaks: a real relay has one baton; StarfishOS's queues let many producers enqueue concurrently (MPSC), more like several runners feeding one anchor leg at once.
Service recovery · Micro-reboot

Replacing a blown fuse, not rewiring the house

One fuse trips, you replace that fuse — you don't rewire the whole house. A filesystem instance crashing with its host is the blown fuse; StarfishOS pops in a fresh instance on a surviving machine and lets it replay the p-log, rather than rebooting the pod.

Where it breaks: a fuse replacement restores the exact same wiring; the new filesystem instance must actively replay 446 logged operations to reconstruct state — more like rebuilding the fuse's function from a wiring diagram than swapping an identical part.
Allocator recovery · LLFree

A full ledger vs. a running tally

A bank keeps a full transaction ledger (ground truth) and also a quick running balance for fast glances. If the teller is interrupted mid-update, the quick balance might drift off in either direction — but the ledger is never wrong. LLFree's per-bit bitfield is the ledger (always correct); its free counter is the quick tally (can drift stale after a crash, but because allocation always checks the ledger, it never causes a double-allocation).

Where it breaks: a bank reconciles the tally against the ledger occasionally; LLFree only needs to reconcile after a crash is detected, by rescanning the bitfield of the affected region.
Heap placement · Page-fault migration

A shared hallway locker, filled on request

You don't move every box from your apartment into the shared hallway locker "just in case" a neighbor wants one — you move a box only the moment a neighbor actually asks for it. A heap page starts in the DRAM of whoever first touches it, and migrates to CXL only when a remote page fault proves another machine genuinely needs it.

Where it breaks: moving a box is a one-time act; migrating a page also requires atomically swapping in a special "in-flight" PTE and flushing stale TLB entries on the old owner, so concurrent accesses don't race the move.
The full explanation

How it actually works

Section by section, following the paper's own structure (§3–§7).

1 · The tension, quantified

The paper's own hardware numbers (Table 3) make the efficiency side concrete: local DRAM is 107 ns / 52 GB/s per channel; local CXL is 241 ns / 2 GB/s; remote CXL climbs to 383 ns / 0.3 GB/s. That's roughly 2–4× the latency and 1/17 to 1/170 the bandwidth of local DRAM — enough to cause up to 3.4× slowdown if everything lived there. On the failure side: hosts and CXL modules fail independently, so a host crash can leave a CXL-resident lock unreleased or a structure half-written, and a survivor that touches it can block or crash — turning one host's death into a pod-wide outage.

2 · Why a microkernel, concretely

Two structural properties, not just philosophy. First, decoupled, typed state: ChCore keeps kernel-space state to IPC, scheduling, and memory-management objects; filesystems and process managers run as ordinary user processes with their own state. Second, easier recovery: because a failed service doesn't share kernel-internal state with the rest of the system, it can be micro-rebooted alone. Both properties are what make "decide per-object where state lives" a tractable engineering question instead of an open-ended kernel rewrite.

3 · Three layers, one rule

LayerShared (CXL) statePrivate (DRAM) stateFailure handling
Kernel modulesIPC/sched/notif queues, CXL allocator metadatathread stacks, local scheduling queues, per-CPU slabslock-free, detectably recoverable
System servicesmount-point / PID ownership metadatafull service instance statemicro-reboot + p-log replay
ApplicationsCapGroup/VMSpace/PMO + on-demand heap pagesstacks, per-machine page tables, rest of heapapp's own recovery mechanism

4 · Partial-failure handling at the kernel level

Every CXL-resident queue (IPC, scheduler, notification) is a DurableQueue: enqueue and dequeue each linearize at one CAS. The two crash cases are handled asymmetrically:

# Enqueuer crash — never blocks anyone
if enqueuer dies mid-link:
    other machines help finish the link (lock-free design)
    queue stays usable; at worst this one request is lost

# Dequeuer crash — bounded, component-specific recovery
if dequeuer dies mid-handle:
    node.status tells you exactly how far it got:
    INIT  → never started   → safe to retry
    DOING → interrupted     → component-specific: retry / abort / redo
    DONE  → fully handled   → nothing to do
💡
Why this matters: the queue's own status field is the recovery log — no separate crash journal needed. That's what "detectably recoverable" buys you.

5 · The CXL memory allocator — LLFree

StarfishOS's kernel-space buddy allocator for CXL memory is LLFree: a two-field metadata scheme where a per-page bitfield (free/allocated) is always ground truth, and a free counter is a fast-path cache of "how many free pages in this 2 MiB region." A crash between the bit-set and the counter update can leave the counter stale in either direction — the appendix lists both an overestimate case (bit set before the counter is decremented) and an underestimate case (counter incremented before the bit is cleared). Safety doesn't come from the counter being biased one way; it comes from allocation always checking the ground-truth bitfield, so a stale counter can at worst mislead the fast-path hint, never cause a double-allocation. Recovery just rescans the bitfield of the affected region and fixes the counter with one CAS. The per-CPU slab allocator on top adds a lightweight in-memory undo-log so a half-finished allocate/free leaves the slab consistent.

6 · Collaborative system services + micro-reboot

Each system service (e.g. the filesystem) runs as several instances, each owning a disjoint slice of the namespace (one mount point each), with only a small ownership map (which instance owns which mount point) kept in CXL. On a crash, StarfishOS starts a fresh instance elsewhere and rebuilds its state by replaying a p-log — a persistent record of every mutating operation written before the service replied to its client, so anything already acknowledged survives even if it never reached the SSD.

7 · Scaling to remote CPUs, not just remote memory

Prior disaggregated systems (e.g. LegoOS) split memory/storage pools but still bin-pack each process onto one CPU node. StarfishOS extends disaggregation to CPUs: the scheduler can hand a thread to any core in the pod via a per-core shared queue in CXL, checked along that core's normal scheduling path — so cross-machine scheduling costs no explicit round-trip message, just a queue check that was already happening.

Follow the numbers

Worked examples

Four traces through the paper's own measurements.

① Where does remote IPC's extra latency actually go?

P50 latency for a 4 KiB file read via IPC: local 2.8 μs, remote (one sender) 5.5 μs, remote (four concurrent senders) 24.3 μs. The paper also reports: local breakdown = 1.8 μs filesystem read + 706 ns context switch + 200 ns IPC logic + 130 ns kernel trap; remote = ~1.4 μs enqueue/dequeue + ~2.0 μs handling.

  1. Check the local number: 1.8 μs + 706 ns + 200 ns + 130 ns = 1.8 + 0.706 + 0.2 + 0.13 ≈ 2.84 μs — matches the reported 2.8 μs.
  2. Check remote (single sender): 1.4 μs (queue ops) + 2.0 μs (handling, which already includes the 1.8 μs fs read) ≈ 3.4 μs of itemized cost — below the reported 5.5 μs. The paper doesn't itemize that ~2 μs residual; our inference is that it's additional per-request overhead not broken out in the remote breakdown, not a figure the paper states directly.
  3. Concurrent senders add queuing delay, not per-request cost: 24.3 − 5.5 ≈ 18.8 μs extra — consistent with the paper's own framing ("the extra ~19 μs overhead is caused by queuing delay").
🍯
Insight: remote IPC's single-sender cost is dominated by the same work local IPC already does (handling the request), plus a modest queue-traversal tax — contention, not the queue mechanism itself, is what hurts under load.

② How much does fine-grained partitioning actually buy?

Figure 13 compares four placements: Share (all CXL), K-mix/U-share (kernel partitioned, app all-CXL), K-mix/U-mix (both partitioned — StarfishOS), Private (all-DRAM, the ideal ceiling).

  1. K-mix/U-mix vs. Share: the paper reports 1.2–2.2× improvement — partitioning both kernel and app state beats partitioning neither.
  2. K-mix/U-mix vs. K-mix/U-share: 1.0–1.7× improvement — even after the kernel is already partitioned, partitioning the application's state on top adds more.
  3. The exception: CPU-intensive workloads (PCA, Matrix Mult.) show little gap between Share and K-mix/U-mix, because most of their data fits in CPU cache regardless of where it nominally lives in memory.
💡
Partitioning helps in proportion to how memory-bound the workload is — a useful lens for predicting which of your own tiering workloads will benefit most from keeping hot state off a slow tier.

③ Is "a few hundred MiB on CXL" really small?

Table 4 gives total memory and CXL memory for four auto-scaled apps.

  1. DB×1000: 500 MiB / 30 GiB = 1.6% on CXL.
  2. Tigon (hand-redesigned baseline, fixed at the same CXL budget): 500 MiB / 30 GiB = 1.6%.
  3. GeminiGraph: 600 MiB / 50 GiB = 1.2% on CXL.
  4. Matrix Multiplication: 109 MiB / 1 GiB = 10.9% — notably higher, because the problem is small enough that a fixed-size shuffle buffer is a bigger fraction of total memory.
  5. Takeaway: CXL overhead lands around 1.2–1.6% for memory-heavy workloads (DB×1000, GeminiGraph) — not quite the "<1%" a casual read might suggest — while a small, compute-bound job like Matrix Mult. is an honest outlier at nearly 11%, worth flagging rather than hidden by the average.

④ Recovering a crashed LevelDB instance (Figure 16)

Machine-A running LevelDB is killed. Reported milestones: crash detect 19.0 ms; FS restart + p-log apply 533.5 ms (p-log replay alone: 528 ms for 446 entries); LevelDB restart 73.5 ms; full warm-up to steady throughput by the 3.060 s mark.

  1. Microreboot overhead vs. replay: 533.5 − 528 = 5.5 ms to spin up the empty filesystem instance; the remaining 528 ms is actual log replay.
  2. Replay rate: 528 ms ÷ 446 entries ≈ 1.18 ms/entry — the cost of reconstructing filesystem state operation-by-operation.
  3. Fixed recovery cost before the app is even usable: 19.0 + 533.5 + 73.5 = 626 ms, well under a second, before LevelDB itself starts reconstructing its in-memory state.
  4. Most of the 3.06 s is LevelDB's own warm-up (cache refill, compaction state), not StarfishOS's recovery machinery — the OS-level piece is done in under 0.7 s.
🍯
Insight: the expensive part of recovery is proportional to how much happened since the last persisted checkpoint (446 entries), not to data size — a lesson that generalizes to any log-replay-based recovery scheme.
Test yourself

Practice problems

Try each before opening the answer; every one names the misconception it checks.

Problem 1 · easy
A thread's stack and a thread's scheduling queue entry are both "kernel state." Why does StarfishOS place one in private DRAM and the other (partly) in CXL?
Show answer
The stack is accessed only by the thread's own execution, on whichever core it's currently running on — nothing else needs to see it, so there's no coordination to pay for. A remote-scheduled thread's shared queue entry, by contrast, must be visible to the target core so it can admit the thread — that visibility is the coordination StarfishOS is willing to pay CXL latency for.Misconception: that "kernel state" is one uniform category. The partitioning rule is about who needs to see it, not which subsystem owns it.
Problem 2 · medium
LLFree's free counter can drift stale after a crash, but the paper insists this never causes a double allocation. Why not?
Show answer
Because the bitfield, not the counter, is what actually gets checked to find and claim a free page — the counter only decides whether to even start looking, as a cheap fast-path hint. If a crash leaves the counter undercounting, the allocator might wrongly report out-of-memory even though free bits exist; if it leaves the counter overcounting, the allocator might look for a free page that isn't there and fail to find one. Either way is wasteful but safe, because allocation can never set a bit that's already set — it always goes through an atomic bit-set on the bitfield itself, and a post-crash rescan reconciles the counter.Misconception: that any "stale" metadata after a crash is dangerous, or that the counter is biased to fail safe in one direction. Staleness is only dangerous if it's on the path that actually grants access; LLFree keeps that path on the always-correct bitfield regardless of which way the counter drifted.
Problem 3 · medium
If an enqueuer crashes mid-operation on a DurableQueue, the paper says the queue "stays usable" for everyone else. If a dequeuer crashes mid-operation, recovery is "component-specific." Why the asymmetry?
Show answer
Enqueue only adds a node via a lock-free CAS that any other producer can help complete if abandoned — the queue's structure is never at risk, and at worst one request is simply never published. Dequeue, by contrast, hands a node to a specific consumer who then goes off and does real work with it (replying to a client, scheduling a thread) — if that consumer dies partway, the queue structure is still fine, but whether the work happened is ambiguous, and resolving that ambiguity depends on what the work was (hence "component-specific": IPC retries, scheduler reconstructs, notification times out).Misconception: that lock-freedom alone guarantees recoverable semantics. Lock-freedom protects the data structure; recovering the meaning of an interrupted operation is a separate, per-use-case problem.
Problem 4 · hard
StarfishOS gives applications zero transparent crash recovery — a failed machine's processes just die, like ordinary process crashes. Why not add transparent rollback, given the OS already tracks so much state explicitly?
Show answer
Transparent system-wide rollback requires logging or checkpointing every state change on the common (non-crashing) path, all the time — exactly the "pay CXL/logging tax for things that usually don't fail" cost the whole design is trying to avoid. Since many real applications already have their own recovery mechanisms (WAL, restart-from-checkpoint, replay), StarfishOS instead preserves the environment those mechanisms need (surviving machines stay usable, files and flushed CXL state stay accessible) and lets the application decide how to recover, rather than paying a tax on every operation to support a generic mechanism most apps don't need.Misconception: that "the OS tracks state explicitly" implies "the OS should recover everything automatically." Explicit tracking is what makes selective, cheap partitioning possible — it's not free license for comprehensive rollback.
Problem 5 · medium
Why does StarfishOS keep per-machine private page tables instead of one shared page table in CXL, even though a single shared table would seem to simplify the "single address space" illusion?
Show answer
A page table is read on every memory access (via the TLB, but refilled from the table on a miss) — it's about as "hot" and locality-sensitive as state gets. Putting it in CXL would put CXL latency on the critical path of nearly every instruction. StarfishOS instead keeps a private "sub page table" per machine (so a virtual page may be mapped on one machine and simply absent on others) and only synchronizes the small amount of information needed to find a page's true owner when a fault proves cross-machine sharing is actually needed.Misconception: that a single logical address space requires a single physical page-table structure. The illusion is maintained at the VMSpace/fault-handling level, not by literally sharing the table.
Problem 6 · easy
DB×1000 running unmodified on StarfishOS outperforms Tigon, a database hand-redesigned specifically for CXL, by 2×. Does this mean OS-level SSI is strictly better than application-specific CXL redesign?
Show answer
No — the paper is explicit that this isn't an apples-to-apples comparison: Tigon is specialized to a particular concurrency-control design (2PL, next-key locking) and pays other costs unrelated to CXL placement, while StarfishOS runs the unmodified original. The result shows transparent OS-level support can be competitive with or better than a specific hand-engineered redesign in this case — not that redesign is never worthwhile.Misconception: that one benchmark comparison settles a general "OS-level vs. app-specific" question. The paper itself flags this caveat rather than overclaiming.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does "state-partitioned microkernel" mean?▾
An architecture that explicitly splits every layer of the OS — kernel modules, user-space services, applications — into a small piece of state that must be visible across machines (placed in CXL) and the rest, which stays in each machine's private DRAM. The same rule is applied uniformly at every layer rather than per-case.
Q2Why can't a monolithic kernel (like Linux) do the same partitioning?▾
Monolithic kernels spread state across tightly-coupled subsystems connected by implicit pointers rather than explicit, typed objects. Deciding "should this live in DRAM or CXL" per piece of state requires first being able to name and isolate that piece — which capability-based microkernels give you for free and monolithic kernels generally don't.
Q3Does StarfishOS require application code changes?▾
No — that's the whole point. Phoenix, DB×1000, and GeminiGraph run with zero code changes and still auto-scale across the pod; the OS, not the application, decides state placement and schedules threads across machines.
Q4How is this different from a DSM (distributed shared memory) library?▾
DSM libraries also let programmers write single-machine-style code, but they're user-level and still generally need application-specific tuning of what data goes where to be efficient on CXL. They also can't provide OS-level resource pooling (devices, pod-wide scheduling) or transparent POSIX execution the way an OS-level SSI can.
Q5What happens to an application running on a machine that crashes?▾
It terminates abruptly — the same as an ordinary process crash on a single machine. StarfishOS doesn't hide this from the application; it only guarantees that the OS and shared CXL state remain usable for applications on surviving machines, and relies on the application's own recovery mechanism (if any) to resume.
Q6Why does cross-machine IPC need a different design from local IPC?▾
Local IPC in the base microkernel is an L4-style synchronous context switch — it changes which thread runs on the current core, but can't move execution to a different physical machine where the server's address space actually lives. Cross-machine IPC therefore uses an explicit message (a CXL-resident FIFO queue) instead.
Q7How small is the CXL memory footprint, really?▾
For memory-heavy applications, roughly 1.2–1.6% of total memory (DB×1000, GeminiGraph). For a small compute-bound job like Matrix Multiplication, it's a larger fraction (~11%) simply because the fixed coordination buffer is a bigger slice of a small total — but still a few hundred MiB in absolute terms.
Q8Is coherent CXL memory used for everything, or just a small region?▾
StarfishOS is designed to keep coherent CXL usage as small as possible, and in the paper's evaluated applications (Table 4) that works out to several hundred MiB even for multi-GiB apps — the operating point the system targets and measures, not a hard architectural ceiling. The paper argues broader hardware coherence is technically feasible if an application needed it.
Q9What failure types does StarfishOS NOT handle?▾
It assumes fail-stop failures of entire physical machines (CPU + DRAM together) with a reliable global failure detector — not fail-slow failures (a machine that's alive but degraded) and not Byzantine failures (a machine that behaves maliciously or arbitrarily incorrectly).
Q10How does StarfishOS help with stranded CPU resources?▾
On a traditional OS, a multithreaded app is bin-packed onto one machine, so idle cores on other machines can't help it. StarfishOS's pod-wide scheduler lets an app's threads run on any core in the pod, recovering 83–93% of exclusive-machine throughput for apps that would otherwise be stuck co-located and running at only 17–77%.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
State-partitioned microkernelStarfishOS's architecture: explicitly divide each OS layer's state into a small CXL-resident coordination slice and a large private-DRAM remainder.
CXL podRack-scale machines with private DRAM and a shared, cache-coherent CXL memory pool reachable from every host via load/store.
SSI (Single System Image)Presenting a pod as one logical machine — unified address space, PID/file/device namespaces — so unmodified apps auto-scale.
DurableQueueA lock-free, detectably-recoverable FIFO queue (Friedman et al.) that StarfishOS specializes for IPC, scheduler, and notification traffic.
LLFreeLock-free, crash-consistent page allocator; its bitfield is always ground truth, its free counter is a fast-path hint that can drift stale in either direction after a crash and is reconciled by rescanning the bitfield.
Micro-rebootRestarting only a failed user-space service instance, not the whole OS — practical because microkernel services don't share kernel-internal state.
p-logPersistent operation log, written before a service replies, that lets a replacement instance replay and reconstruct state after a crash (Ananke-style).
Page-fault-driven migrationLazily moving a heap page from private DRAM to CXL only when a remote access actually faults on it.
Supporting terms
Capability objectA typed OS resource (CapGroup, Thread, VMSpace, PMO, IPC, Notification) referenced via unforgeable capabilities — the unit of placement decisions.
Collaborative system serviceA service split into per-machine instances, each owning a disjoint resource slice, coordinated via small CXL-resident ownership metadata.
Fail-stop failureA machine's CPU and DRAM both die together, cleanly, detected by a reliable global failure detector — the only failure mode StarfishOS targets.
Owner machine / MRU-style lookupClients cache which instance owns a given mount point / resource after first lookup, routing subsequent requests directly.
Bootloader coordinationPer-machine bootloaders that agree on a unified kernel-space virtual address layout so CXL is mapped identically on every host.
K-mix/U-mixThe paper's evaluation label for "kernel state partitioned AND application state partitioned" — StarfishOS's actual configuration.
