eBPF '26 Workshop · A Field Guide

One Sail model, three artifacts you can trust are in sync

The Linux kernel's eBPF interpreter has no single formal reference. This paper writes one — in Sail — and generates Rocq definitions and a human-readable spec document from the same source, with a handwritten Rocq driver and CompCert-backed runtime layered on top to make it executable.

📄 Tang, Yuan, Talpin, Chen · eBPF '26 🎓 Some Rocq/type-theory familiarity assumed — primers cover the rest ⏱ ~25 min read
🧾

Write the semantics ONCE in Sail, not separately as code, proof, and prose — then generate the other two.
Generation keeps artifacts synchronized; it does not itself prove they agree with Linux.

Before you begin

Quick glossary, then eight primers

The acronyms first, cold, so nothing below stalls on vocabulary. Then ten collapsed primers — open whichever looks unfamiliar.

Quick glossary

eBPFextended Berkeley Packet Filter — a sandboxed bytecode VM inside the Linux kernel, used for networking, tracing, security.
ISAInstruction Set Architecture — the set of instructions, their encodings, and their meanings.
RFC 9669The 2024 IETF document that is the first official, natural-language eBPF ISA standard.
SailA domain-specific language (REMS project) for writing ISA semantics once and generating definitions for proof assistants, executable code, and docs from it.
RocqThe proof assistant formerly called Coq; used here both for generated definitions and a handwritten execution layer.
CompCertA formally verified C compiler; its memory model is reused here to give eBPF loads/stores precise semantics.
SOSStructural Operational Semantics — the standard style of defining "one execution step" from a program state.
AV / ASAccess Variety / Access Strength — metadata Sail attaches to a memory effect (plain vs atomic-RMW; normal vs acquire/release).
RMEM / IslaTwo Sail-compatible backends for exploring relaxed-memory (operational / axiomatic) concurrency — future work here.
LKMMLinux Kernel Memory Model — the axiomatic concurrency model that would need to interpret this paper's AV/AS events.
BTF / kfuncBPF Type Format / kernel function — the mechanism for calling kernel functions beyond the 211 fixed BPF helpers.
JITJust-In-Time compiler — translates eBPF bytecode to native machine code before execution.
1What "formal ISA semantics" buys you▾

Natural-language specs (like RFC 9669) can be read two ways by two implementers. A formal semantics pins the meaning down in math/code so a machine can check it, execute it, and — eventually — prove things about it.

Now you're ready: this paper's whole motivation is that eBPF has an RFC but no executable, checkable reference — this Sail model is meant to be that reference.
2Sail: one language, many outputs▾

Sail lets you write an instruction's syntax, its binary encoding, and its execution semantics once. Its toolchain then emits Rocq/Isabelle/Lean definitions, executable C/OCaml, and semantics-aware documentation from that single source. The Sail RISC-V specification was adopted as the official basis for the RISC-V Foundation's ISA spec; Sail has also been used successfully to model ARMv8-A, though that isn't its official spec basis.

Now you're ready: "generated from the same Sail source" is the paper's central design choice — it's what keeps the spec doc and the Rocq semantics from silently drifting apart.
3Structural Operational Semantics (SOS)▾

SOS defines a program's behavior as a sequence of small steps: given a state (here: registers + memory + auxiliary bookkeeping) and the next instruction, a step function produces the next state. It's the standard mathematical skeleton for "what does running this instruction do."

Now you're ready: the paper's step_program/execute functions are exactly this — fetch, decode, one SOS step, repeat.
4Registers, memory, and "auxiliary state"▾

eBPF has ten general-purpose registers R0–R9, a stack pointer R10, a hidden R AX, and a program counter. Memory is where R10 and pointers passed in R1 point. Beyond that, the interpreter also needs bookkeeping state that isn't "memory" in the usual sense: a call stack for internal calls, and counters for tail calls.

Now you're ready: when the paper says "program configuration," it means exactly these three buckets together.
5The CompCert memory model▾

CompCert (a verified C compiler) models memory as a set of disjoint blocks, each an array of bytes; a pointer is a (block, offset) pair. It provides Mem.alloc, Mem.free, Mem.load, Mem.store with proven properties.

Now you're ready: this paper's Rocq runtime doesn't invent a new memory model — it maps each eBPF memory region onto a CompCert block and reuses CompCert's memory-model operations (Mem.load, Mem.store) — though the paper doesn't itself claim these eBPF-specific accesses are verified against real Linux behavior.
6Union clauses, mapping clauses, execute clauses▾

Sail's three-step instruction recipe: a union clause declares the instruction's abstract shape (its operands); a mapping clause relates that shape bidirectionally (<->) to its bit-pattern encoding; an execute clause defines what happens when it runs.

Now you're ready: when you see BPF_SDIV32 defined three separate times in the paper, that's this recipe, not redundancy.
7Weak memory, and why atomics are different▾

On real multi-core hardware, concurrent memory accesses can appear reordered unless special atomic or acquire/release instructions constrain them. Fully specifying this ("weak memory semantics") is a separate, hard problem from sequential per-instruction semantics — it requires relating events across threads, not just within one instruction stream.

Now you're ready: this is exactly why the paper fully formalizes atomic instructions' encodings, decoding, value computation, and register writeback, but explicitly stops short of a concurrent memory model for their memory effects.
8Tail calls and the call stack▾

An eBPF tail call jumps to another eBPF program (looked up via a program-array map) without growing the call stack — it replaces the current program rather than nesting. The kernel still bounds how many tail calls can chain, to guarantee termination.

Now you're ready: the paper's tail_call_count and the constant 33 are exactly this kernel-imposed bound, carried into the formal model.
9Instruction encoding, bit by bit▾

Each 64-bit eBPF instruction packs several fields into fixed bit ranges: an 8-bit opcode, two 4-bit register fields, a 16-bit offset, and a 32-bit immediate. Which fields mean what depends on the instruction class (ALU, jump, load/store, etc.) encoded inside the opcode itself.

Now you're ready: the "How It Works" tab walks the BPF_SDIV32 opcode byte 0x3c apart, field by field.
10Verified vs. validated — a crucial distinction▾

"Type-checks" and "runs on test programs" are validation — evidence the model is plausible. A refinement proof against the real interpreter (or against another trusted Rocq model) would be verification — a mathematical guarantee of agreement. The paper is explicit that it has only the former so far.

Now you're ready: read every "we generate / we execute" claim in this paper as validation, not proof — the FAQ and Reference tabs return to this distinction.
The whole story in one place

Sail as the single source of truth

The gap this fills, the mechanism, and the honest scope of what's actually covered.

eBPF has an RFC (9669) but no executable formal reference, and prior Rocq formalizations of eBPF are hand-written independently from any documentation — so the proof, the runnable model, and the human-readable spec can silently drift apart as the kernel evolves. This paper instead writes one Sail model covering all 153 sequential instructions in the Linux 7.1 eBPF interpreter (out of 181 total), and from that single source generates both Rocq definitions and a human-readable ISA-style specification document.

For the remaining 28 atomic instructions (RMW ops like add/xchg/cmpxchg, plus acquire-loads and release-stores), the model defines their encodings, register effects, and tags each memory access with AV/AS metadata (plain vs. atomic-RMW; normal vs. acquire/release) — the interface a future concurrency backend would need — but does not yet define what those accesses mean under concurrent execution.

To actually run programs, a handwritten Rocq execution layer (a driver plus a CompCert-backed runtime) combines with the generated Rocq semantics, mapping eBPF memory regions onto CompCert's verified memory blocks.

🍯 Key takeaways

  • One Sail model → generated Rocq defs + generated ISA-style PDF spec, kept in sync by construction.
  • 153/181 instructions have full executable semantics; 28 atomic instructions have encodings, decoded forms, value computation, register writeback, and memory-effect annotations, but no concurrent memory semantics.
  • Execution needs a handwritten Rocq driver + CompCert-backed runtime — generation alone isn't enough to run programs.
  • Generation guarantees the artifacts are synchronized, not that they're correct relative to Linux — that's future validation work.
  • A known spec/implementation divergence exists already: register-based shifts (masked in the spec, not always masked by JIT backends).
  • 211 predefined BPF helper functions and BTF-based kfuncs are out of scope — no effect handler is implemented for them yet.
Six everyday pictures

How to think about this workflow

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Single source

One master blueprint, three deliverables

An architect draws one master blueprint, then generates the framing plan, the materials list, and the inspector's checklist from it — instead of three people drawing three documents by hand that can quietly disagree. The Sail model is the blueprint; Rocq semantics and the spec PDF are generated deliverables.

Where it breaks: a generator can still faithfully reproduce a wrong blueprint. Synchronization isn't correctness — the blueprint itself still needs checking against the real building (Linux).
Encoding · Mapping clause

A shipping label with fixed boxes

A shipping label has fixed fields — sender, tracking number, weight — always in the same place on the form, so both a human and a scanner read it identically. A Sail mapping clause is that label template for an instruction: bit ranges assigned to opcode, registers, offset, immediate, defined once and read in both directions (decode a byte string, or encode an AST node).

Where it breaks: a shipping label means the same thing on every truck. eBPF's register fields actually swap position between little- and big-endian hosts — the "template" itself depends on context.
Atomic instructions · Declared, not settled

An IOU, not a completed transaction

An IOU note states what's owed — an amount, who owes whom — without specifying which bank, on what day, or in what order among several IOUs it clears. The Sail model's atomic instructions are exactly this: the shape of the obligation (encoding, register effect, AV/AS tag) is written down, but the settlement rules across concurrent threads aren't.

Where it breaks: an IOU resolves eventually by one bank's rules. Concurrent memory has no single "bank" — the ordering rules themselves (LKMM-style) are the hard, unwritten part.
Validation vs verification · The paper's honesty

A compass vs. a surveyed boundary

A compass reading, cross-checked against a landmark, gives you good confidence you're pointed the right way. A legally surveyed property boundary is a proof — measured and certified. Type-checking, running test programs, and manual comparison with the interpreter are the compass: strong evidence, not a certificate.

Where it breaks: a compass can be consistently, systematically off in one direction (magnetic declination) and still "agree with itself" every time — the paper flags exactly this risk for semantic review.
Shift semantics · A known divergence

The posted speed limit vs. how people actually drive

The sign says 55; on that particular stretch, everyone actually drives 62 and the highway patrol doesn't ticket it — a documented, tolerated gap between rule and practice. RFC 9669 says "mask the shift amount"; several JIT backends emit a native shift with no mask, relying on the target CPU to happen to behave the same way.

Where it breaks: a speed gap is usually harmless; here it's architecture-dependent — ARM32 and PowerPC's native out-of-range shift behavior differs from the masked spec, so the "gap" can actually change program behavior.
Memory model · Layered delegation

A hotel's room directory, not the rooms themselves

The front desk keeps a directory mapping room numbers to physical rooms, but doesn't reinvent plumbing or electricity per room — it defers to the building's existing systems. Sail's memory effects carry an address and size; the Rocq runtime's region map looks up which CompCert block that address belongs to, and defers the actual load/store to CompCert's own memory operations.

Where it breaks: a hotel directory covers every room. The region map only covers modeled region types (context, stack, packet, map values) — helper-created objects like sockets aren't in the directory yet.
The full explanation

How it actually works

State, execution loop, the three-step instruction recipe, atomics, and the generation pipeline.

1 · Program state

A configuration bundles three pieces. Registers: R0–R9, R10 (stack pointer), RAX, all 64-bit bit-vectors, plus PC as a mathematical integer. Memory: Sail-level registers hold only 64-bit addresses; actual access happens through abstract memory effects (address, size, AV/AS metadata) — concretely realized by a Rocq driver + CompCert runtime that maps disjoint address ranges to CompCert memory blocks. Auxiliary state: call_stack (internal calls), tail_call_count and current_code_id (tail calls).

2 · Execution environment: init, then step

Initialization sets PC=0, R1 → eBPF context, R10 → top of local stack, all other registers to 0; memory regions (context, local stack, packet data, map values) are populated with their initial bytes; auxiliary state starts empty/zero. Static inputs — program code (as byte lists plus a tail-call jump table), host endianness, and the tail-call limit (33, matching the kernel's bound) — are supplied alongside. run_program then repeatedly calls step_program, which fetches the instruction at PC, decodes it, and dispatches to execute, producing Success (continue), a terminal result (e.g. Exit), or a request for runtime handling (internal/tail calls).

3 · One instruction, three Sail clauses

Take BPF_SDIV32 (32-bit signed division). A union clause declares its shape: source kind (register or immediate), destination register, source register, 32-bit immediate. A mapping clause relates that shape bidirectionally to its bit encoding. An execute clause defines the semantics: read operands, compute (with x÷0→0 and MIN÷-1→MIN special-cased to avoid overflow/trap), write back, advance PC.

4 · Atomic instructions: declared, not yet concurrent

All 28 atomic instructions get encodings, decoded forms, value computation, and register writeback — but their memory effects are only tagged with metadata for a future concurrency backend to interpret, following the same interface the Sail RISC-V model uses for RMEM/Isla.

Access kindAV (variety)AS (strength)Examples
Plain load/storeAV_plainAS_normalordinary LDX/STX
Atomic RMWAV_atomic_rmwAS_normaladd, or, and, xor, xchg, cmpxchg (+ fetch variants)

⚠
What's still missing: ordering guarantees from acquire/release, and how the read+write of one atomic RMW group into a single indivisible update — i.e. the actual concurrent memory semantics, likely via an LKMM-style axiomatic model or RMEM/Isla.

5 · The generation pipeline

Each instruction becomes a spec entry ⟨Id, Desc, Enc, Ope⟩: Id from the union-clause name; Desc from a handwritten doc comment; Enc (encoding diagrams) extracted from the mapping clauses; Ope (operation section) generated from the execute clause, with helper functions inlined. Mechanically: sail --doc emits JSON; an AsciiDoc file with Sail macros assembles it; the Asciidoctor toolchain + Sail's plugin renders the final PDF. Separately, the Sail-to-Rocq backend emits the Rocq definitions consumed by the handwritten execution layer.

💡
Why this matters for correctness: the encoding diagrams and operation sections in the spec PDF are generated from the same clauses used for execution — so they can't silently diverge from the executable semantics. The handwritten description text is the one part generation can't protect.
Follow the numbers

Worked examples

Real figures from the paper, traced through by hand.

① Rebuilding the opcode byte from its three parts

The paper states BPF_SDIV32's register-source opcode is 0x3c, built from ALU32=0x04, SRC_X=0x08, DIV=0x30. Verify it, then find the immediate-source opcode.

  1. Add the three contributions: 0x04 + 0x08 + 0x30 = 0x3c. ✓ matches the paper.
  2. Swap SRC_X → SRC_K for the immediate-source form: SRC_K contributes 0x00 in place of SRC_X's 0x08 — the paper independently states this opcode is 0x34.
  3. Check: 0x3c − 0x08 = 0x34. ✓ consistent — the source-kind field really is exactly 8 (bit 3) of the opcode.
🍯
Insight: the opcode byte is literally a small bitfield struct (class | src-kind | op), which is why one mapping clause per source-kind, sharing the same DIV/ALU32 pieces, suffices.

② The two overflow guards in signed division

The execute clause special-cases two situations before dividing. Walk through why each is needed, with concrete 32-bit values.

  1. Divide by zero: e.g. dst = 10, src = 0. Ordinary integer division is undefined here; the semantics defines the result as 0 rather than trapping or being left unspecified.
  2. Signed overflow: 32-bit signed min is −2147483648. Compute −2147483648 ÷ −1 mathematically: the true result is 2147483648, which does not fit in a 32-bit signed register (max is 2147483647) — one past the top.
  3. The guard: when src = −1 and dst = signed-min, the semantics returns signed-min itself (−2147483648) instead of overflowing, matching two's-complement wraparound behavior rather than undefined behavior.
  4. Otherwise: ordinary truncating signed division, tdiv_int(d_s, s_s), applies.
💡
Both guards exist because a 32-bit two's-complement signed range is asymmetric (−2147483648 to 2147483647) — the one value with no positive counterpart is exactly the one that needs special-casing.

③ How much of the ISA is actually done

Linux 7.1's interpreter has 181 total instructions. What fraction has full executable semantics vs. partial (encoding-only) treatment?

  1. Sequential, fully formalized: 153 instructions.
  2. Atomic, partially formalized: 181 − 153 = 28 instructions (matches the paper's count exactly).
  3. Coverage fraction: 153 / 181 ≈ 84.5% with complete executable semantics; the remaining 15.5% has encodings, decoded forms, value computation, and register writeback, but not a concurrent memory model.
🍯
Insight: "covers all 153 sequential instructions" and "181 total" are both exact figures from the paper — the 28-instruction gap is precisely the concurrency-relevant slice, not a random leftover.

④ Where the tail-call limit of 33 comes from

The model sets tail_call_count's ceiling to 33. Trace why.

  1. Source of truth: the paper follows the Linux kernel's own constant, MAX_TAIL_CALL_CNT, defined in bpf.h — not an independently chosen number.
  2. Effect: each tail-call instruction increments tail_call_count; once it would exceed 33, the runtime must refuse the jump (guaranteeing termination of tail-call chains).
  3. Why it matters for formalization: this is a case where the Sail model's auxiliary state directly mirrors an undocumented-in-the-RFC, kernel-source-only constant — faithfulness here required reading the kernel, not just RFC 9669.
💡
A reminder that "formal spec derived from Sail" still rests on manual transcription choices like this one — generation can't verify that 33 is the right number, only that it's used consistently everywhere downstream.
Test yourself

Practice problems

Try each before opening the answer; every one flags the misconception it checks.

Problem 1 · easy
Does generating Rocq definitions and a spec PDF from the same Sail model prove the model matches Linux's actual interpreter?
Show answer
No. Generation only guarantees the three artifacts stay synchronized with each other — it says nothing about whether the Sail source itself correctly reflects Linux 7.1's behavior. The paper's own evidence for that is limited to type-checking, running on concrete programs, and manual comparison during construction.Misconception: conflating internal consistency (generation) with external correctness (agreement with Linux) — the paper is explicit these are separate concerns.
Problem 2 · medium
153 sequential + 28 atomic = 181. Does "atomic instructions are formalized" mean they're fully executable in this model?
Show answer
No. Atomic instructions have encodings, register effects, and AV/AS memory-effect tags defined, but not a concurrent memory semantics — so their behavior under actual concurrent execution (ordering, indivisibility of RMW) is not yet specified.Misconception: treating "instruction count covered" as a single binary — the paper distinguishes full sequential semantics from partial (encoding + effect-tag-only) treatment.
Problem 3 · medium
Register-based shifts in the Sail model mask the shift amount, matching RFC 9669. Why might a real eBPF program still behave differently on some hardware?
Show answer
Because some JIT backends lower shifts directly to native instructions without inserting an explicit mask, for performance reasons. On architectures where an out-of-range native shift behaves differently than "mask then shift" (e.g. ARM32, PowerPC), the running program's actual behavior can diverge from both RFC 9669 and this Sail model.Misconception: assuming the formal spec and the deployed JIT-compiled behavior are automatically identical — they can diverge precisely because JIT backends optimize around the spec's letter.
Problem 4 · hard
What specifically is missing for a "full concurrent semantics" of eBPF atomics, beyond what this paper already provides?
Show answer
Two things: (1) the ordering constraints imposed by acquire/release instructions across threads, and (2) how the read and write halves of a single atomic RMW instruction are grouped into one indivisible update relative to other threads' accesses. Both require relating the AV/AS-tagged events to an actual concurrency model — e.g. an LKMM-style axiomatic treatment or an operational model connected via RMEM/Isla — which the paper leaves as future work.Misconception: assuming "tagging memory effects with metadata" is equivalent to "defining concurrent semantics" — the tags are the interface, not the model.
Problem 5 · medium
The paper mentions 211 predefined BPF helper functions and BTF-based kfuncs. Are these covered by the current Sail/Rocq model?
Show answer
No effect handler for helper calls is implemented. The Rocq side has partial infrastructure — a generic BPF map record (instantiated for array, hash, and program-array maps) and the BPF context modeled as a region-map entry — which could support helpers like bpf_map_lookup_elem in the future, but packet state, socket state, and time/randomness oracles are all still missing.Misconception: assuming "formalizes eBPF" implies helper functions are modeled too — helpers touch external kernel objects and are explicitly out of scope here.
Problem 6 · easy
Why does the Sail model represent PC as a mathematical integer but R0–R10/RAX as 64-bit bit-vectors?
Show answer
R0–R10 and RAX hold actual machine words that participate in bitwise arithmetic (shifts, masks, two's-complement overflow), so they need fixed-width bit-vector semantics to match hardware exactly. PC is only ever used as an index into the instruction sequence/jump targets, never as data subject to wraparound arithmetic in the model — so representing it as an unbounded integer simplifies the semantics without losing fidelity.Misconception: assuming every "register-like" quantity needs identical representation — the choice tracks how the value is actually used, not just its name.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Is this the first formal semantics of Linux eBPF?▾
No — the paper explicitly disclaims this. Prior Rocq work (the RIOT-OS eBPF VM, Solana eBPF, CompCert-BPF, and a closest-in-coverage prior Rocq semantics of the Linux sequential ISA) already exists. This paper's contribution is using Sail as a single source for an executable model, generated Rocq definitions, and a generated ISA-style spec document together.
Q2Why Sail instead of writing Rocq semantics directly?▾
Writing directly in Rocq gives you a proof assistant model but no generated documentation, and no automatic synchronization if you also want a human-readable spec. Sail is purpose-built to emit multiple downstream artifacts (Rocq/Isabelle/Lean, executable C/OCaml, docs) from one specification, and has prior success on ARMv8-A and RISC-V.
Q3Does "generated from Sail" mean no manual work was needed?▾
No. The Sail model itself is entirely handwritten (from the interpreter and RFC 9669), as is the AsciiDoc scaffolding for the spec document and the entire Rocq execution layer (driver + CompCert-backed runtime). Generation only automates turning the Sail source into Rocq definitions and JSON model info.
Q4What does "153 sequential instructions" actually mean?▾
It's the count of non-atomic instructions in Linux 7.1's eBPF interpreter (181 total minus 28 atomic ones) for which the Sail model provides complete union/mapping/execute clauses — i.e. full executable semantics, not just encodings.
Q5Why leave concurrency out entirely rather than approximate it?▾
A correct concurrent memory semantics requires relating events across threads via an established model (LKMM-style axiomatic, or an operational model via RMEM/Isla) — getting this wrong would be worse than not claiming it. The paper instead defines the AV/AS metadata interface so a future concurrency backend can consume these events without re-deriving them.
Q6How is this related to RFC 9669?▾
RFC 9669 is the natural-language standard this formal model is checked against during construction. The paper treats natural-language ambiguity as the underlying problem it's solving, and found at least one concrete spec/implementation divergence (register-based shift masking) while doing so.
Q7What's the difference between the Sail model and the handwritten Rocq execution layer?▾
The Sail model (and its generated Rocq definitions) describes what an instruction means abstractly — including abstract memory effects. The handwritten execution layer (Rocq driver + CompCert-backed runtime) is what actually runs that meaning: it resolves addresses to CompCert memory blocks and performs real loads/stores.
Q8Can this model check real eBPF programs today?▾
Yes, for the 153 sequential instructions — the paper reports executability on concrete programs as part of its validation evidence. Programs relying on atomic concurrency semantics, helper calls, or kfuncs are not fully supported yet.
Q9What would it take to trust this model more?▾
Three concrete next steps the paper names: running the BPF Conformance test suite against the executable model; reusing a trace-based workflow (from prior Rocq eBPF work) to compare model states against real interpreter traces; and, longer-term, a refinement/equivalence proof relating the Sail-derived Rocq semantics to the prior independently-written Rocq semantics.
Q10Does the model stay in sync automatically as Linux updates?▾
No — it's versioned against Linux 7.1 and requires manual comparison against a new kernel release plus manual revision of affected Sail clauses, followed by regenerating and reviewing the downstream Rocq/doc artifacts. The authors note future tooling to suggest candidate updates from kernel diffs, but that doesn't exist yet, and maintenance effort hasn't been measured.

Core terms
Sail modelThe handwritten specification of eBPF instruction syntax, encoding, and execution — the single source for all generated artifacts.
Union clauseDeclares an instruction's abstract AST shape (its operand fields) inside Sail's global instruction datatype.
Mapping clauseBidirectionally relates an instruction's AST constructor to its concrete bit-pattern encoding, via <->.
Execute clauseDefines what a step of execution does for one instruction: read operands, compute, write back, advance PC.
ExecutionResultSail datatype for one step's outcome: normal continuation, termination (e.g. Exit), or a request for runtime handling (calls).
AV / AS metadataAccess Variety (plain / atomic-RMW) and Access Strength (normal / acquire-release) tags attached to memory effects.
Region mapThe Rocq runtime's mapping from disjoint concrete address ranges to CompCert memory blocks.
Spec entry ⟨Id,Desc,Enc,Ope⟩The generated document's per-instruction tuple: name, handwritten description, encoding diagrams, generated operation section.
