PLOS '26 · A Field Guide

Teaching Rust's own tools to read the assembly they were told to ignore

Inline assembly is a blind spot for Kani, Miri, and every fuzzer in the Rust ecosystem. This paper doesn't build a new verifier or model checker — it introduces a macro, a compiler backend, and a machine model that rewrite the assembly into plain Rust, so the old verification tools can finally see it.

📄 Castes, Debaussart, Bourgeat · PLOS '26 (EPFL) 🎓 Some Rust-unsafe & RISC-V basics assumed — primers cover them ⏱ ~25 min read
🦀

For an asm! block to be well-defined, a pure Rust program with the same effect on the Rust Abstract Machine must exist. soft_asm! builds that program automatically from the official Sail spec — no hand-written axioms required.

Before you begin

Quick glossary, then eight ideas the paper assumes

Acronyms first, so nothing downstream is opaque. Then eight collapsed primers — open any that look unfamiliar.

Quick glossary — the paper's key acronyms
UBUndefined Behavior — a program state the language spec places no guarantees on. The compiler may assume it never happens.
ISAInstruction Set Architecture — the contract between hardware and software: which instructions exist and what each one does.
Rust AMRust Abstract Machine — the formal model Rust's semantics (and its UB) are defined against, independent of any real CPU.
SailA language for writing executable ISA specifications. The official RISC-V spec is written in Sail and compiles to C/OCaml/Lean/Rust.
KaniA Rust bounded model checker — proves properties (or finds counterexamples) over symbolic inputs.
MiriA Rust interpreter that detects Undefined Behavior — invalid pointers, data races, alignment violations — during concrete execution.
CSRControl and Status Register — RISC-V's system registers (trap vectors, privilege state, PMP config, hart ID, ...).
PMPPhysical Memory Protection — RISC-V's hardware mechanism for restricting which physical addresses a privilege level may access.
ABIApplication Binary Interface — the calling convention (which registers hold arguments/return values) a function call must respect.
CFGControl-Flow Graph — the graph of basic blocks and branches a decompiler reconstructs from a flat instruction stream.

1Why systems code needs inline assembly at all▾

High-level languages can't express everything a kernel, hypervisor, or firmware needs: configuring memory protections, installing trap handlers, reading a hardware ID, switching privilege levels. Crypto code and numerical kernels use it too, for constant-time branchless logic or vector instructions.

Every one of these falls into one of four buckets the paper studies: pure register arithmetic, memory accesses, unusual control flow, and system instructions.

Now you're ready: the paper's whole structure (§3) is organized around exactly these four categories — see Table 1.
2Rust's asm! contract, and how it causes UB▾

Rust's asm! macro is a declared contract: you list which Rust variables map to inputs, outputs, and clobbered registers. The compiler trusts your declaration completely and interleaves compiled Rust with your raw assembly, without checking it.

Any mismatch between what you declared and what the assembly actually does — an undeclared clobber, a missing side effect — is Undefined Behavior, silently.

Now you're ready: soft_asm! is a syntax-compatible replacement for asm! — same declared contract, different expansion — though matching a real-world asm! block exactly can still need a few manual tweaks, as the Miralis retrofit shows.
3The Rust Abstract Machine — what UB is defined against▾

Rust's semantics — and therefore its notion of UB — aren't defined relative to any physical CPU. They're defined relative to an abstract model of state and steps: the Rust Abstract Machine (Rust AM). Tools like Miri and Kani reason about programs entirely in terms of this abstract machine.

An asm! block is, from the Rust AM's point of view, a single opaque step — nothing inside it is visible to Rust-level reasoning.

Now you're ready: the paper's central figure is literally this: Rust AM states before/after an opaque asm! step, and a "witness" that fills in the gap — see the Big Idea tab.
4The witness-program principle▾

The Rust community's own criterion (credited to Ralf Jung) for when inline assembly is well-defined: there must exist a pure Rust program that performs the identical state transformation on the Rust AM. If no such program exists, the assembly is UB by definition — full stop.

This criterion isn't new to this paper. What's new is automating the construction of that witness program instead of leaving it as a proof obligation in someone's head.

Now you're ready: soft_asm!'s entire output is the witness program, made concrete and runnable.
5Sail and executable ISA specifications▾

Sail is a language for describing instruction semantics precisely enough to compile into a runnable simulator. The RISC-V community's official specification is written in Sail; ARM's is written in the analogous language ASL, with community translations to Sail.

Because Sail specs are executable, you can compile them to C, OCaml, Lean — or, as this paper does, to a Rust library exposing decode and execute functions.

Now you're ready: the paper builds a new Sail-to-Rust backend; base RISC-V instruction semantics come straight from the official Sail model, not hand-modeled by the authors — though custom, non-standard instructions (like Flashpoint's two new ones) still need a manual Sail definition before the backend can compile them.
6RISC-V system state: CSRs, privilege, traps, PMP▾

Beyond general-purpose registers, RISC-V has Control and Status Registers (CSRs) holding trap vectors, the current privilege mode, and Physical Memory Protection (PMP) configuration — the hardware mechanism that restricts which physical addresses a privilege level may touch.

Reading/writing these is exactly what "system instructions" (the paper's fourth category) do — and it's where side effects can leak outside what any model captures.

Now you're ready: the evaluation's headline property — "PMP is always configured correctly" — is a direct assertion about this CSR state, checked symbolically with Kani.
7The Rust verification & testing toolbox▾

cargo test runs concrete unit tests. Kani does bounded model checking over symbolic inputs. Miri interprets code step-by-step and flags UB. Fuzzers (cargo-fuzz) hammer code with pseudo-random inputs. Verus/Creusot do full deductive verification against pre/post-conditions.

Every one of these tools operates on pure Rust source. None of them — as of this paper — understands what's inside an asm! block.

Now you're ready: this is the entire gap the paper closes — not by building a ninth tool, but by making the other eight applicable.
8Two places translation must make a choice▾

Register allocation: asm!'s contract names a Rust variable, not a physical register — the compiler picks the mapping. To emit concrete code, the macro must commit to one allocation, even though real hardware would accept any valid one.

Control-flow recovery: assembly is a flat instruction stream with jumps; Rust requires structured if/loop bodies. The macro runs a lightweight decompilation pass to recover structure, and simply refuses to translate patterns it doesn't recognize.

Now you're ready: both choices are deliberate, narrow blind spots, not bugs — see §3.2, §3.4, and Practice Q2.
The whole story in one place

soft_asm! in a nutshell

The problem, the fix, and why it doesn't need a new proof system.

Verification and bug-finding tools for Rust — Kani, Miri, fuzzers, Verus, Creusot — all reason about pure Rust source. An inline asm! block is, to every one of them, an opaque box: a single unanalyzed step on the Rust Abstract Machine. The standard fixes either hand-write an axiomatized model of each instruction in a program logic (trusted but untestable), or drop to the assembly level entirely and lose access to high-level Rust semantics and tooling.

This paper takes a third path, grounded in a principle the Rust community already accepts: for an asm! block to be well-defined, a pure Rust program with the same effect on the Rust Abstract Machine must exist. The paper's soft_asm! macro builds that witness program automatically, by replacing each instruction with a call into a Rust CPU model compiled from the official RISC-V Sail specification — 7.4k lines of generated code exposing decode/execute/register-access functions. Base RISC-V instruction semantics aren't hand-modeled: they come straight from the official Sail spec, so any discrepancy from real hardware there is a specification bug or a compiler bug, not a modeling error — though the authors did write two new manual Sail definitions to extend the model with Flashpoint's non-standard instructions.

The result is ordinary, compilable Rust with no asm! left in it — so every existing Rust tool applies immediately. Applied to Miralis (a RISC-V hypervisor) and Flashpoint (a new dynamic root-of-trust firmware), this surfaced two previously invisible bugs and enabled exhaustive model checking of firmware state transitions — for a one-time cost of 6 manually-edited lines out of 208 lines of assembly.

🦀 Key takeaways

  • An asm! block is opaque to Rust tooling; Rust's own rule says a pure-Rust witness must exist for it to be well-defined.
  • soft_asm! builds that witness automatically, using a CPU model compiled from the official Sail ISA spec — not hand-axiomatized.
  • Four categories, four challenges: register ops (allocation), memory (unsafe deref), control flow (decompilation), system instructions (side effects).
  • Output is plain Rust — no new verifier or model checker is needed; Kani, Miri, and fuzzers apply unmodified once the soft_asm! macro and Sail-derived model have done the lifting.
  • Miralis retrofit: 208 lines of assembly, only 6 needed manual edits, 2 new bugs found.
  • Flashpoint (new firmware): 600 LOC, six state transitions proven correct via exhaustive Kani model checking.
  • Blind spots are explicit: fixed register allocation per translation, and effects outside the CPU struct (MMU, FP control) aren't modeled.
Six everyday pictures

How to think about lifting assembly

Each stands alone. Every card ends with an honest note about where the picture stops being true.

Core idea · Witness program

A stunt double, doing the exact scene

The opaque asm! block is like a stunt performed off-camera — you only see the actor go in and come out unharmed. The witness is a stunt double who performs the exact same moves, in full view, so the safety inspector (Kani/Miri) can watch every step.

Where it breaks: the double is only as faithful as the script they were handed — the Sail specification. A bug in the official spec ships straight into the "verified" double.
Translation vs. axiomatization

Subtitles, not a dub

Axiomatizing instructions in a program logic is like re-dubbing a film in a new voice — you're trusting the dubber's paraphrase of what was said. Lifting is more like subtitles: the original meaning, made legible in a language the audience (your Rust tools) already reads, with the exact semantics coming from the official spec.

Where it breaks: some scenes don't get subtitled at all — the macro's decompilation pass refuses unstructured control-flow patterns rather than guessing.
Trust model

The notarized original, not a paraphrase

A hand-written axiomatic model is like trusting someone's summary of a contract. This approach instead consults the notarized original — the official RISC-V Sail spec — and mechanically compiles it. Any gap between model and hardware is a spec bug, not a "did the verifier understand the instruction correctly" bug.

Where it breaks: you still trust the notary's translator — the Sail-to-Rust compiler backend itself is new, untested machinery, not formally verified.
Memory accesses

Keyhole surgery, not open surgery

A load/store instruction becomes an ordinary unsafe Rust pointer dereference — a small, precise incision Miri and Kani already know how to inspect (alias rules, live-allocation checks), instead of needing an entirely new memory model built from scratch.

Where it breaks: the "keyhole" only reaches normal memory. Memory-mapped device registers and the MMU sit outside the incision entirely — accesses to them are bypassed, not modeled.
Exhaustive model checking

Freezing every player mid-play

Symbolic model checking with Kani is like a referee who freezes the entire field, mid-play, to check every player's position against the rulebook simultaneously — not sampling a few plays, but ruling out any starting configuration that could break the rule.

Where it breaks: freezing the whole field — the entire ISA model, not just the reachable subset — is expensive: 3 hours and ~50 GB per checked transition in Flashpoint, due to insufficient dead-code pruning.
Register allocation blind spot

A passport valid in one country only

The asm! contract says "this variable goes in some register" — any valid allocation is legal. The translator must commit to one specific mapping to emit concrete code, like issuing a passport that only clears border control at a single checkpoint.

Where it breaks: a bug that only surfaces under a different register allocation — say, reading an undeclared register that happens to be idle in this mapping — stays invisible unless the test harness randomizes every register, declared or not.
The full explanation

How it actually works

Section by section, following the paper's own four-way split.

1 · The Rust CPU model

A custom Sail-to-Rust backend compiles the official RISC-V Sail specification into a Rust library: 7.4k lines of generated code, exposing a core struct holding all architectural registers, CSRs, privilege mode, and a configuration field for which RISC-V extensions are enabled. Two methods matter most: core.get(reg)/core.set(reg, val) read and write the emulated register file, and core.execute(instr) runs one decoded instruction and returns whether it trapped.

2 · Pure register operations

The simplest case: arithmetic/logic over declared registers, no memory, no branches. The macro picks one concrete register allocation, emits core.set for each input, a core.execute call per instruction (using the decoded AST node from the Sail model), and core.get for each output.

3 · Memory accesses

Memory isn't part of the core struct — it's whatever Rust object the address happens to point at. A load like ld rd, 0(rs1) translates to: read the base address via core.get(rs1), dereference it as a raw pointer (unsafe), write the result back via core.set(rd, ...). This is exactly the shape of unsafe code Miri and Kani already know how to check — live-allocation, alignment, and aliasing rules apply unchanged.

⚠
Limit: the memory model is just "the pointer that's there." Vector loads/stores with masks and strides, and memory-mapped I/O, aren't captured — both are flagged as future work.

4 · Control flow

Assembly's flat jump-based control flow doesn't map directly onto Rust's structured if/loop syntax. The macro runs a lightweight decompilation pass — building a CFG, finding branch targets, matching known patterns — and errors out rather than guessing on anything unrecognized.

Exceptional control flow (traps) is handled by letting the user supply a list of expected trap handlers; each core.execute call returns Trap::Some(addr) or Trap::None, matched against that list, panicking if nothing matches:

match core.execute(instr) {
  Trap::Some(addr) => handle_trap(addr, &[handler1, ...]),
  Trap::None       => (),
};

Function calls (the call pseudo-instruction) need an ABI the macro can't infer from a declarative macro alone, so the user annotates it explicitly; a wrong annotation fails to type-check rather than silently misbehaving:

// #[abi("C", 2, u64)]  — user-supplied, checked at compile time
core.set(X10, 100); core.set(X11, 42);
let _: extern "C" fn(_, _) -> u64 = add_two; // typecheck the annotation
let ret = add_two(core.get(X10), core.get(X11));
core.set(X10, ret);

5 · System instructions

Because CSRs, privilege mode, and other architectural state already live inside the Sail-derived model, system instructions need no new translation logic — they just read/write fields of the core struct. This is what makes assertions like "is PMP configured correctly after this block?" directly expressible: query core.pmp_check(addr).

⚠
Honest limit: effects outside the modeled state aren't captured. Disabling floating-point via a CSR write will correctly trap subsequent assembly float instructions — but not plain Rust float operations. Likewise, the MMU is bypassed entirely by the direct-pointer translation of loads/stores, both in lifted assembly and in ordinary Rust code around it.

Worked examples

Four traces using the paper's own figures and evaluation numbers.

① Verifying the abs() witness with Kani

The 3-instruction srai/xor/sub block (Fig. 3) claims to compute abs(x) for a 64-bit signed x. How would Kani check this?

  1. Lift it. soft_asm! expands the block into three core.execute calls plus register set/get glue (Fig. 4) — ordinary Rust, no asm! left.
  2. Write the spec. The intended behavior is if x < 0 { x.wrapping_neg() } else { x }.
  3. Symbolic input. Give Kani a fully symbolic 64-bit x (kani::any()) instead of a fixed test value.
  4. Assert equivalence. Run the lifted block and the spec on the same x; assert their outputs match.
  5. Result: Kani exhaustively checks all 2⁶⁴ inputs symbolically — not by enumeration, but by proving the assertion can't fail — something no unit test or fuzzer could claim.
🦀
Insight: this equivalence check is now a completely ordinary Kani harness. Nothing about it is asm-specific once the lifting is done.

② Retrofitting Miralis: 208 lines, 6 edits, 2 new bugs

Miralis had 208 lines of inline assembly, previously verified only via a hand-written mock Rust module standing in for it. What happened when asm! was swapped for soft_asm! directly?

  1. Remove the mock. Delete the hand-written pure-Rust stand-in used for prior verification.
  2. Swap the macro. Replace every asm! with soft_asm! across the 208 lines.
  3. Fix the 6 lines that needed it: 1 explicit call annotation, 2 explicit type casts, 1 explicit global-symbol mention, 2 disambiguations between add and addi.
  4. Re-run Kani. Two bugs surface that the old mock-based verification never caught.
  5. The bugs: a register that should have been declared clobber but wasn't, and one bit silently lost during a CSR manipulation due to a hardwired-zero field.
💡
Why this matters: 6 of 208 lines (2.9%) needed a human — the rest translated automatically, and the two bugs were invisible to Rust-only tooling precisely because the old mock stood in for the real assembly's actual behavior.

③ The CPU model's size and what it buys

Is compiling the whole Sail spec to Rust a lightweight dependency, or a heavyweight one?

  1. Generated library: 7.4k lines of Rust, covering most of the base RISC-V ISA, configurable per-project by extension.
  2. Extending it is possible: Flashpoint needed two new, non-standard RISC-V instructions — these were added directly to the Sail model and recompiled, not bolted on as a Rust-side special case.
  3. The library is the single source of truth for both "what does this instruction do" (used by the witness) and "is this memory access legal" (used by core.pmp_check in assertions).
💡
Insight: because the model is generated, not hand-maintained, extending coverage to new instructions is a spec change, not a new proof obligation.

④ Flashpoint: exhaustive verification, at a real cost

Flashpoint is a new ~600-line dynamic root-of-trust firmware. The goal: prove it always leaves the system in a correctly-isolated state, from any starting CPU state.

  1. Symbolic everything: every general-purpose register and CSR starts as a symbolic (kani::any()) value in the harness — modeling an arbitrary prior system state.
  2. Run the entry point (an assembly snippet that sets up the stack and calls into Rust) through the lifted model.
  3. Assert two kinds of properties: Rust-level asserts on internal firmware state, and CPU-model asserts like core.pmp_check(addr) returning true only for explicitly allowed regions.
  4. Cost: ~3 hours and ~50 GB of memory per transition, on an AMD EPYC 9224, for each of six state transitions verified.
  5. Root cause of the cost: insufficiently aggressive dead-code pruning — SMT queries encode the behavior of the entire RISC-V spec, not just the reachable subset for this firmware.
⚠
Honest trade-off: that's roughly 18 transition-hours of compute at ~50 GB peak memory each across six proofs — expensive, but the paper notes Miri/fuzzing/unit tests on the same lifted code were "very helpful" during development, well before paying the full model-checking cost.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
A colleague says: "We already verify this assembly — we wrote an axiomatic model of each instruction in our program logic." Why might the paper's authors consider the lifted approach more trustworthy?
Show answer
The hand-written axioms must themselves be trusted — they can't be tested or cross-checked against a reference, so a modeling mistake in the axiom is indistinguishable from a correct proof. The lifted witness, by contrast, is generated from the official Sail specification and is itself an executable program: any discrepancy from real hardware is a spec bug or translator bug, not an unfalsifiable modeling error, and the witness can be run and tested like any other code.Misconception: that any formal model is equally trustworthy once it's written down. Whether the model can itself be executed and tested matters as much as whether it's formal.
Problem 2 · medium
The abs() example maps x→X1, sign→X2, result→X3. Suppose the assembly also contains an instruction that reads X5 — a register that's not declared as an input, output, or clobber — silently assuming it still holds a caller-saved value from before the block started. Under the allocation the macro picked (X1/X2/X3), X5 sits idle, so the read looks harmless. Would Kani, run against this lifted soft_asm! translation, catch that the block depends on an undeclared register?
Show answer
Not by default. The translation commits to one fixed allocation, and in that allocation X5 is never written by soft_asm!'s setup code, so its value in the model is whatever it happened to start at — Kani has no reason to flag reading it. The dependency on an undeclared register only becomes visible if the harness also initializes undeclared registers like X5 to nondeterministic values: a read of X5 then propagates that nondeterminism into a failing property, exposing the hidden dependency. (Under a different legal allocation, the compiler could instead place a live, declared variable in X5 — turning the same undeclared read into real corruption.)Misconception: that a declared variable living in a register (like x in X1) is the same kind of risk as an undeclared register being read. The bug here isn't about x going stale — it's about the block touching a register the contract never mentioned at all.
Problem 3 · easy
True or false: after translation, running the lifted memory-access code under Miri will catch a bug where an assembly load reads from an address one byte past the end of a buffer.
Show answer
True. The load becomes an ordinary unsafe raw-pointer dereference in Rust; Miri already checks that dereferenced pointers point inside a live allocation, so an out-of-bounds address triggers exactly the same UB report it would for handwritten unsafe Rust.Misconception: that memory safety bugs in assembly need special-purpose assembly tooling to find. Once lifted to a raw pointer, they're caught by machinery that already exists and wasn't built for this paper.
Problem 4 · hard
An assembly snippet writes a CSR that disables floating-point instructions, then some ordinary (non-asm) Rust code performs a floating-point addition. Does the lifted model catch a violation if that Rust addition "shouldn't" have been allowed to execute?
Show answer
No. The CPU model faithfully makes subsequent assembly floating-point instructions trap, because that's encoded in the Sail-derived execute() semantics. But plain Rust floating-point operations compiled by rustc aren't routed through the model at all — the model only governs code inside soft_asm! blocks. The effect on Rust-level float ops would have to be checked by a separate, explicitly-written assertion in the test harness, not inferred automatically.Misconception: that the CPU model enforces system-wide invariants everywhere in the program. It only governs the state and instructions it directly models — anything happening in plain Rust around it is invisible to it unless asserted by hand.
Problem 5 · medium
Why does the macro's decompilation pass raise a compile error on unrecognized control-flow patterns instead of translating them "best effort"?
Show answer
A best-effort translation that guesses wrong would silently produce a witness program with different effects than the real assembly — defeating the entire purpose, since the whole approach rests on the witness performing the identical state transformation. Refusing to translate unsupported patterns keeps every accepted translation actually faithful, at the cost of not yet supporting general state machines (left as future work via techniques like the relooper algorithm).Misconception: that more automatic coverage is always better. A translator that's honestly incomplete is safer than one that's silently wrong.
Problem 6 · medium
Flashpoint's model checking takes 3 hours and ~50 GB per transition. Is this an inherent cost of the lifting approach, or an engineering gap?
Show answer
The paper attributes it to insufficiently aggressive dead-code pruning: the SMT queries currently encode the behavior of the whole RISC-V specification, rather than just the subset of instructions/registers actually reachable in this firmware's six transitions. That's explicitly called out as future work, not a fundamental limit of lifting assembly to Rust — a smarter prune step could shrink the queries substantially.Misconception: that exhaustive model checking on a lifted ISA model must always be this expensive. The cost here is tied to a specific, fixable pruning gap in this implementation, not to the underlying idea.
Problem 7 · hard
Someone proposes applying this exact approach, unmodified, to assembly that switches the active page table (changes the address-translation root) mid-block. What goes wrong?
Show answer
The paper explicitly scopes out assembly that modifies the current execution environment — changing privilege levels or the active page tables — from automatic translation. The memory-access lifting assumes ordinary Rust pointer semantics (a fixed, live allocation); switching page tables mid-block changes what a given virtual address even refers to, which the raw-pointer-dereference translation has no way to represent. This falls outside the categories the paper automates.Misconception: that "system instructions" as a category covers everything privileged. Instructions that change the execution environment itself (not just read/write state within it) are called out as a boundary the automatic translation doesn't cross.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What exactly does soft_asm! output?▾
Ordinary, compilable Rust with no asm! macro left in it: a sequence of calls into a per-project core struct (register get/set, execute) compiled from the official RISC-V Sail spec, plus whatever structured Rust control flow was recovered from the original branches. It's a syntax-compatible replacement for asm! — not a strict drop-in, since real-world blocks can still need a few manual tweaks, as Miralis's 6 edited lines show: targeting the real architecture forwards to asm!, verification mode expands to pure Rust.
Q2Does this replace QEMU-based full-system testing?▾
No — the paper is explicit about this. It's a lightweight, cross-platform execution path for programs with a modest amount of inline assembly, complementary to (not a replacement for) full-system emulator testing. It shines where you want to run standard Rust tooling (Kani, Miri, fuzzers) without a target emulator at all.
Q3Why can't tools like Miri or Kani just handle asm! directly?▾
They reason at the level of Rust source and the Rust Abstract Machine. An asm! block's internals simply aren't expressed in that vocabulary — from the tool's point of view it's an unanalyzed foreign step. Teaching each tool to natively understand RISC-V (or every ISA) would duplicate enormous effort across every tool; lifting instead solves it once, upstream of all of them.
Q4Where does the instruction semantics actually come from?▾
The official RISC-V Sail ISA specification, compiled by a custom Sail-to-Rust backend into a 7.4k-line Rust library. Base RISC-V instruction behavior is never hand-encoded by the paper's authors — which is also why any mismatch with real hardware there is attributable to the spec or the compiler, not to a modeling choice made for this paper. The one exception: Flashpoint's two non-standard instructions needed manual Sail definitions written by the authors before the backend could compile them.
Q5What's the register-allocation blind spot, concretely?▾
asm!'s contract names Rust variables, not physical registers — the real compiler is free to pick any valid mapping. soft_asm! must commit to one specific mapping to emit code, so verification only exercises that one allocation. Test harnesses can partially compensate by initializing all registers (declared and undeclared) to nondeterministic values: a read of an undeclared register then propagates that nondeterminism into a failing property, and asserting that non-output registers keep their initial values catches undeclared clobbers.
Q6What system effects fall outside what's modeled?▾
Anything not represented in the core struct's state. Two named examples: disabling floating point via a CSR correctly traps subsequent asm float instructions but doesn't affect plain Rust float code; and the MMU is entirely bypassed since loads/stores translate to direct Rust pointer dereferences, in both lifted assembly and surrounding Rust code.
Q7What did applying this to Miralis and Flashpoint actually find?▾
In Miralis (208 lines of inline assembly, 6 lines needing manual edits after the macro swap): two new bugs — an undeclared clobbered register and a bit silently lost in a CSR write due to a hardwired-zero field — neither caught by the prior mock-based verification. In Flashpoint (a new ~600-line firmware), six state transitions were proven correct via exhaustive Kani model checking, including that PMP is always configured to enforce the intended isolation.
Q8Why does Flashpoint's verification take hours and tens of gigabytes?▾
The SMT queries currently encode behavior for the entire RISC-V specification rather than just the reachable subset for this firmware, due to insufficiently aggressive dead-code pruning. The paper flags fixing this as future work — it's a known engineering gap, not claimed to be inherent to lifting.
Q9Can this be applied to other ISAs, or other languages?▾
The paper argues yes to both, as future work. Arm's official ASL spec has a community translation to Sail, and there's a Sail formalization of user-space x86, so the same pipeline could target them. The core idea — emulate via an official executable spec rather than axiomatize by hand — isn't Rust-specific either; it could be adapted to C/C++ via a custom preprocessor instead of Rust's macro system.
Q10Is this sound — does it prove the assembly has no bugs?▾
It extends the reach of whatever tool you run on the output — Kani's guarantees are as strong as Kani's guarantees normally are, now covering assembly too. But the translation itself has explicit, named boundaries (fixed register allocation, no environment-switching instructions, no modeled MMU/device effects) — bugs strictly inside those boundaries can hide. It's a large expansion of coverage, not a universal soundness proof over all possible assembly.

Core terms
soft_asm!A Rust macro, syntax-compatible with asm!, that either forwards to real assembly or expands to a pure-Rust emulation using the Sail-derived core model.
Witness programA pure Rust program that performs the same Rust-AM state transformation as an asm! block — the thing that must exist for the block to be well-defined.
Sail-to-Rust backendA new Sail compiler target that turns the official RISC-V ISA spec into a runnable Rust library (decode/execute/register access).
core structThe generated Rust model of CPU state (registers, CSRs, privilege, extension config); the (s, pm) cross-product state in Fig. 1.
Simulation relationThe requirement that the witness and the original program agree on Rust-visible state at the entry and exit of the asm! block.
LiftingTranslating low-level (assembly) code into the host high-level language, as opposed to lowering high-level code down to the assembly level to verify it there.

Source notes — what's the paper's, what's framing

Straight from the paper: the witness-program criterion (§2.1, credited to Ralf Jung); the Sail/Sail-to-Rust pipeline and 7.4k-LOC model (§3.1); all four instruction categories and their translations (§3.2–3.5, Figs. 3–8); the Miralis numbers — 208 lines, 6 manual edits, 2 bugs (§4.1); the Flashpoint numbers — ~600 LOC, 6 transitions, ~3h/~50GB on an AMD EPYC 9224 (§4.2); every named limitation (register allocation, decompilation refusal, MMU/FP bypass, page-table-switching exclusion).

This guide's own framing (not in the paper): all six analogies (stunt double, subtitles, notarized original, keyhole surgery, freezing the field, one-country passport); the redrawn Fig. 1 diagram's circle/arrow layout; the "Blocked → Unlocked" tool-applicability framing of the results bars; and any explicit connection to memory-tiering/CXL-style systems work, which the paper itself does not discuss.

Related work cited in the paper

TickTock: Verified Isolation in a Production Embedded OS hard

Rindisbacher et al. · SOSP · 2025

Uses refinement types with hand-trusted axioms for assembly contracts — the axiomatization baseline this paper contrasts against.

Scaling Symbolic Evaluation with Serval hard

Nelson et al. · SOSP · 2019

Verifies compiled binaries directly at the assembly level — the "reason at the assembly level" alternative this paper avoids.

Vale: Verifying High-Performance Cryptographic Assembly Code hard

Bond et al. · USENIX Security · 2017

Direct assembly-level verification with a custom machine model — another point on the axiomatization-vs-lifting spectrum.

Get Rid of Inline Assembly through Verification-Oriented Lifting (TINA) hard

Recoules et al. · 2019

The closest prior work: decompiles inline assembly to C for equivalence checking, but only for user-mode code — this paper extends the idea to system state.

Jung et al. (POPL'20) · Villani et al. (PLDI'25)
