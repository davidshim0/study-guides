MICRO 2025 · A Field Guide

Send the ray to the tree, not the tree to the ray

BVH traversal is a pointer-chasing scavenger hunt through a tree that can be gigabytes wide, and it misses cache often enough that a hop routinely leaves the GPU, crosses the cache and interconnect, and comes home slower than the ray itself. This is the plain-English story of RayN, which parks a tiny ray-tracing unit right inside the memory stack.

📄 "RayN: Ray Tracing Acceleration with Near-memory Computing" · Saed, Nair & Aamodt 🎓 GPU and memory-systems basics assumed — the primers cover them ⏱ ~30 min read
📡

Put the hardware that walks the tree NEXT TO the tree, and only ship it the 32-byte ray — not the gigabyte-scale tree.
Latency is the bottleneck; move compute, not data.

Before you begin

Quick glossary, then eight primers

Acronyms first, so nothing below is opaque. Then eight collapsible primers — read in order the first time, or jump to whatever's unfamiliar.

1Ray tracing, in one paragraph▾

A ray is shot from the camera through each pixel. To shade that pixel, the renderer must find the closest geometry the ray hits. Extra "secondary" rays (reflections, shadows, global illumination) get traced from that hit point too — this is what makes ray tracing look realistic, and what makes it expensive: finding "closest-hit geometry" is the bottleneck.

Now you're ready: RayN accelerates exactly this closest-hit search, not the shading math around it.
2The BVH tree and why you need one▾

Looping over every triangle in a scene per ray is hopeless at millions of triangles. A BVH tree groups geometry into nested boxes (AABBs): internal nodes bound their children, leaf nodes hold actual geometry. A ray tests the root box first — if it misses, the whole subtree is skipped for free.

Now you're ready: "BVH traversal" = walking this tree, testing boxes, until you reach the geometry a ray actually hits.
3Why traversal is memory-intensive: pointer chasing▾

Different rays take different paths down the tree — they diverge. Each step follows a pointer to a child node whose address you don't know until you've read the parent, so accesses can't be prefetched far in advance. In the paper's workloads, average L1 and L2 cache miss rates are 39% and 45% — the tree mostly doesn't fit in cache once games hit millions of geometries.

Now you're ready: this is the "villain" of the whole paper — a chain of dependent, unpredictable, high-latency loads.
4TLAS vs BLAS — the industry's two-level split▾

Vulkan/DirectX already split a scene's BVH into a TLAS (Top-Level AS, one per scene, whose leaves point to objects) and multiple BLASes (Bottom-Level AS, one per object, whose leaves hold real geometry). This lets an unchanged object's BLAS be reused frame-to-frame without rebuilding.

Now you're ready: RayN reuses this split as its unit of work-placement, then refines it further — TLAS plus the top levels of each BLAS ("BLAS Breaking") stay GPU-side, and only the bottom BLAS partitions go near memory.
5GPU RT units, warps, and the ray pipeline▾

A GPU groups 32 threads into a warp executed together (SIMT). Each Streaming Multiprocessor (SM) has a dedicated RT unit that a warp's threads offload BVH traversal to: it holds a ray buffer, schedules memory fetches, and runs box/triangle intersection tests as node data arrives.

Now you're ready: because rays diverge, most of a warp's 32 lanes sit idle inside the RT unit — measured SIMT efficiency there is just 13%. That underuse is exactly what RayN exploits by consolidating RT units near memory instead.
63D-stacked memory and the logic layer▾

HBM stacks several DRAM dies on top of a logic layer, connected vertically by TSVs. That logic layer is silicon too — it can hold more than plumbing. Since it sits right beneath the memory, anything placed there reaches data without crossing the GPU's cache, interconnect, or memory channel.

Now you're ready: RayN's whole architecture is "put an RT unit in that logic layer."
7Near-memory computing / PIM, the general idea▾

Near-memory computing (PIM) places compute logic close to or inside memory to cut the cost of moving data. It has been explored for graph processing (partition a big graph evenly across near-memory cores) and, commercially, for ML (Samsung/SK Hynix accelerator-in-memory parts, UPMEM's near-bank RISC cores).

Now you're ready: RayN argues graph-style PIM designs don't transfer directly to ray tracing — they lack intersection-test hardware and a way to load-balance an unpredictable, camera-dependent workload.
8JEDEC, memory controllers, and structural hazards▾

JEDEC's HBM standard places the memory controller in the host GPU, not in the stack. Add a second controller in the logic layer and both could try to drive the same physical memory at once — a structural hazard. Simple fixes (like UPMEM's) lock whole banks/channels for near-memory use, blocking the host — unworkable here because the GPU shader and the near-memory RT unit both need to read the same BVH tree concurrently.

Now you're ready: resolving this hazard, cleanly, is the subject of RayN's three memory-controller designs.
The whole story in one place

RayN in a nutshell

The problem, the fix, and the numbers that back it up.

Ray tracing is latency-bound, not bandwidth-bound: halving BVH memory latency yields a 1.9× speedup, while doubling bandwidth yields only 1.2× (Fig. 1). BVH traversal misses L1/L2 cache often enough (average 39%/45% miss rates) that a large share of node fetches pay the full round trip through the GPU's cache hierarchy, interconnect, and memory channel — even though the payload it's chasing (a 64–128 B node) is small and the round trip itself, not the data volume, is what hurts.

RayN's fix: place a dedicated near-memory RT unit inside the logic layer of each HBM stack, right next to the BVH data. The TLAS — traversed by every ray, coherent, and cache-friendly — stays on the GPU RT unit. The BLASes — where rays diverge and cache hit rates collapse — are offloaded to the near-memory unit, which reaches memory 49.2% faster because it skips the cache/interconnect/channel hierarchy entirely.

Making this concurrent-safe requires new memory-controller machinery: HBM's JEDEC standard puts the controller in the host GPU, so a second controller in the logic layer risks colliding with it. RayN studies three designs — JEDEC-compatible (partition channels, duplicate the tree), Unified (remove the GPU controller entirely), and Hybrid (keep both, coordinated) — and a load-aware way to split the BVH tree ("BLAS Breaking") across memory modules so no single near-memory RT unit is overwhelmed.

The payoff: 3.0× average speedup over a GPU without near-memory support, 70% lower energy, for just 0.78% logic-layer area — with the GPU's own RT-unit memory transactions cut by 78%.

🍯 Key takeaways

  • Ray tracing is latency-bound (1.9× from 2× latency) far more than bandwidth-bound (1.2× from 2× bandwidth) — Fig. 1.
  • RayN reuses the industry's existing TLAS/GPU · BLAS/near-memory split, refined by "BLAS Breaking" to also keep top BLAS levels on the GPU.
  • HBM's JEDEC controller lives in the GPU, so a second near-memory controller can collide with it — three designs (JEDEC-compatible, Unified, Hybrid) trade standard-compliance for performance.
  • BVH partitions are placed to balance estimated load (root-node volume × partition depth), since true load depends on the not-yet-known camera view.
  • GPU RT units are barely used (13% SIMT efficiency) — RayN can shrink 30 GPU RT units down to 4 near-memory ones and still win.
  • Result: 3.0× speedup (up to higher on high-geometry scenes), 70% energy reduction, 0.78–1.10% logic-layer area.
💡
For the tiering-minded reader: RayN is an offload-to-data answer to a latency problem, where OS-managed tiering (TPP, HeMem, Memtis, Pond) is a migrate-data-to-compute answer to a related tension. Both exploit the same physical fact — compute placed closer to memory sees lower latency — but RayN fixes it with fixed-function hardware inside the device, while CXL-style tiering fixes it by moving hot pages toward the compute, under OS/hypervisor control. This is a parallel we're drawing for intuition, not a comparison the paper itself makes: RayN's controller-placement debate (JEDEC-compatible vs. Unified vs. Hybrid) is really about avoiding a structural hazard between two controllers sharing one physical memory, which only loosely echoes CXL.mem's host-managed vs. device-managed split — treat it as a suggestive analogy, not an equivalence.
Six everyday pictures

How to think about RayN

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks.

The core idea · Compute-to-data

A cook stationed in the pantry

Instead of a runner sprinting to the pantry for each ingredient and back to the far-off kitchen, station a small cook inside the pantry. Send only the order slip (the 32-byte ray); the cook prepares the dish there and passes back the result. The pantry (HBM stack) never has to travel — the near-memory RT unit does the fetching where the ingredients (BVH nodes) already live.

Where it breaks: a pantry cook still needs proper equipment (intersection-test hardware) — a general-purpose near-memory core without that gear is like a cook with no stove, which is exactly why prior PIM-for-graphs designs don't transfer directly.
Splitting the work · TLAS / BLAS

A library's front desk and its back stacks

Every visitor passes the busy front desk (TLAS) — it's small, shared, and stays warm in the librarian's memory (GPU cache). But once a visitor needs a specific collection's shelf (a BLAS), the search fans out unpredictably into the sprawling stacks. RayN keeps the front desk staffed by the librarian (GPU RT unit) and hires a dedicated shelver inside each stack room (near-memory RT unit) for the divergent part.

Where it breaks: real library shelves don't get physically rebuilt each visit; a BLAS does, when its object moves or deforms — new "shelves" have to be re-partitioned and placed.
The controller trilemma

Two chefs sharing one stove

JEDEC-compatible (J): each chef gets their own stove, on a fixed rota — safe, but each only ever gets half the burners. Hybrid (H): the head chef keeps their stove but a sous-chef in back interleaves both orders on the fly — nearly full use of the stove, no protocol torn up. Unified (U): hire one new chef to run the whole kitchen from scratch — most flexible, but now the original chef's specialized technique (the GPU's own request reordering) is gone.

Where it breaks: real kitchens don't need a written industry standard (JEDEC) to keep two chefs from colliding — hardware does, which is why "J" needs address-space partitioning and BVH duplication that a kitchen analogy can't capture.
Load estimation · Equation 1

Routing trucks before you know traffic

A dispatcher sizes each delivery route by the package's size and destination depth, without knowing the day's actual traffic — a reasonable proxy, not a guarantee. RayN estimates a BVH partition's load as root-node volume × partition depth, a stand-in for "how many rays will reach here and how far will they dig," because the camera position isn't known until render time.

Where it breaks: the correlation with real intersection counts is weak (Fig. 10) — like a forecast that's directionally useful but often wrong for a specific day; the paper reports a residual load imbalance (max/min intersection ratio averaging 3.14, not the ideal 1.0).
Consolidation · Fewer, busier units

Retiring idle security guards

Thirty guards stand watch, but because visitors trickle in unevenly (divergent rays), each guard is actively checking someone only 13% of the time. Replace them with four guards who are kept genuinely busy by routing all the traffic through them. RayN removes one GPU RT unit per SM (30 total) and adds just one per memory module (4 total) — fewer units, each doing real work instead of waiting.

Where it breaks: real guards can be reassigned instantly; here the "reassignment" (routing BVH traffic to the near-memory unit) still costs a ray-store-and-fetch round trip, so consolidation only pays off because that round trip is now cheap.
Feasibility · Area & heat

A single space heater in a data hall

A 3D memory stack already has to shed heat through a narrow footprint, so adding compute there is a real worry. But RayN's near-memory RT unit only adds about 0.35 W — closer to one small space heater in a data hall than a new furnace. Prior work has shown a stack with 17 W in its logic layer stays coolable with an ordinary fan, so 0.35 W is comfortably within budget.

Where it breaks: a space heater's heat is uniform; silicon hotspots are localized, so the real engineering check is thermal density at the RT unit's exact footprint, not just total watts — the paper cites feasibility rather than re-deriving it.
The full explanation

How RayN actually works

Section by section, with the paper's key structures redrawn as diagrams you can read at a glance.

1 · The pipeline, before RayN touches it

A ray tracing kernel starts on the GPU's execution units, which compute each thread's ray origin/direction, then calls a single TraceRay instruction that offloads BVH traversal to the GPU RT unit. The RT unit holds many rays' state at once (Ray Buffer), fetches the next node each ray needs (Memory Scheduler), and runs three kinds of intersection tests as nodes arrive: ray-box (internal nodes), ray-triangle (leaf nodes), and transform (nodes pointing into another AS). A fetch that misses cache pays the full latency of L1/L2, interconnect, and memory channel — and in these workloads that happens often, with average L1/L2 miss rates of 39%/45%.

2 · The near-memory RT unit itself

Structurally it mirrors the GPU RT unit: a Ray Buffer (register file) holds in-flight traversals; a Memory Scheduler reads each traversal's stack, fetches the next node, and coalesces requests to the logic-layer controller; an Operation Unit Scheduler hands arriving nodes to one of the ray-box / ray-triangle / transform units; a Completed Rays Queue tracks which traversals have finished (read either by polling, by a dedicated "done" pin, or implicitly via a blocking read, depending on which memory-controller design is used).

3 · Three memory-controller designs

HBM's JEDEC standard puts the controller on the GPU. Adding a second one on the logic layer risks both controllers driving the same memory at once, so RayN studies three ways to avoid that structural hazard.

📎
Measured speedups: JEDEC-compatible ≈ 2.0× over treelet prefetching (channel-splitting halves available bandwidth); Unified and Hybrid ≈ 2.2× and perform almost identically — Hybrid gets there without discarding the GPU's own request-reordering logic. Even so, the paper uses Unified architecture and BLAS Breaking as its main configuration for the rest of the evaluation.

4 · BVH partitioning: FULL BLAS vs. BLAS Breaking

Each BLAS could simply be one partition (FULL BLAS): TLAS on the GPU, whole BLASes near memory. But BLAS top levels are less divergent than their leaves — there's real value in keeping them on the GPU too. BLAS Breaking peels the top N levels off every BLAS into the top partition (still GPU-side), leaving smaller, more numerous bottom partitions for near-memory RT units.

5 · Estimating and placing load

The true load of a partition (its intersection-test count) is unknowable at BVH-build time — it depends on a camera position that doesn't exist yet. RayN approximates it as:

load ≈ Volume(root_node) × depth(partition)   # rays reaching it × nodes each ray must cross

Every new partition is placed into whichever memory module currently holds the least total estimated load — a simple greedy bin-packing, re-run only for partitions that actually changed in a dynamic scene (unchanged BLASes keep their memory location to avoid needless data movement).

⚠
Known weakness: the estimate correlates only weakly with real intersection counts (Fig. 10) because camera information is genuinely unavailable ahead of time. BLAS Breaking still improves the max/min-load ratio across modules on average, but degrades it on a few scenes (PARTY, SPRNG, LANDS) where the heuristic guesses wrong.

6 · API and driver changes — the whole integration cost

Vulkan currently separates CreateAccelerationStructure (allocate) from BuildAccelerationStructure (build), but partition sizes aren't known until geometry is in hand. RayN's only API change is merging these into one call. The partitioning logic itself slots into existing top-down or bottom-up BVH-construction algorithms as an extra bookkeeping pass, adding a measured 1.1% construction-time overhead.

Follow the numbers, step by step

Worked examples

Four calculations taken all the way through, using the paper's own measurements.

① Why "latency-bound" isn't just a slogan

Figure 1 reports: doubling memory latency's improvement gives 1.9× speedup; doubling bandwidth gives 1.2×. What does that gap actually tell us?

  1. If ray tracing were bandwidth-bound, doubling bandwidth should buy close to a 2× speedup (data arrives twice as fast, work finishes near-proportionally sooner).
  2. It buys only 1.2× — most of the wall-clock time isn't spent waiting on data volume, it's spent waiting on data round trips.
  3. Halving latency instead buys 1.9× — almost matching the theoretical best case for a purely latency-bound program.
  4. Conclusion: a system that only widened HBM's channels would leave most of the performance on the table; a system that shortens the round trip (RayN's approach) attacks the real bottleneck.
🍯
Insight: this single figure is the paper's entire justification for choosing near-memory compute over, say, simply buying faster/wider HBM.

② The area cost of the near-memory RT unit, exactly

Table 5 gives per-unit areas (scaled to 12 nm) for 32 operation units of each type. Does the claimed 0.78% area overhead actually add up?

  1. Ray-box intersection: 0.0043 mm² × 32 = 0.1372 mm².
  2. Ray-triangle intersection: 0.0119 mm² × 32 = 0.3804 mm².
  3. Control logic: 0.0065 mm² × 32 = 0.208 mm². Register file (4 KB): 0.0009 mm².
  4. Sum (Near-Memory BLAS config, no Transform units): 0.1372 + 0.3804 + 0.208 + 0.0009 ≈ 0.7265 mm².
  5. As a fraction of a 91.99 mm² HBM2 die: 0.7265 / 91.99 ≈ 0.79% — matching the paper's stated 0.78%.
  6. Add Transform units (0.0090 mm² × 32 = 0.2912 mm², needed once GPU RT units are removed entirely): total ≈ 1.0177 mm² → 1.0177 / 91.99 ≈ 1.11%, matching the paper's 1.10% for BLAS Breaking + TLAS.
💡
The arithmetic checks out — and shows exactly what the extra 0.3 percentage points buys: the ability to remove every GPU RT unit and traverse the whole tree near memory, not just the BLASes.

③ Why moving the ray beats moving the tree

A ray is 32 B; a BVH node is 64–128 B; but a single traversal touches a BVH depth nodes deep (depth up to 25 in these scenes). Why does offloading still win?

  1. Baseline: the GPU RT unit fetches every node on the path to the memory — potentially dozens of round trips per ray, each 64–128 B, across the full cache/interconnect/channel hierarchy.
  2. RayN: the GPU sends one 32 B ray to the near-memory unit and waits for one result — every intermediate node fetch during that BLAS traversal happens entirely inside the stack, off the GPU's memory channel.
  3. Measured effect: GPU RT unit memory transactions drop 78% on average (Fig. 13) — the two transaction types that dominate what remains are the ray store and the final result load (some TLAS-related traffic can still occur, since the TLAS can also be served out of the GPU's caches rather than being entirely absent from its memory activity).
  4. Scenes with the deepest, largest trees (PARK, ROBOT, FOX) save the most bandwidth this way, and correspondingly show the largest speedups.
🍯
Insight: the win isn't "smaller messages," it's fewer round trips across the expensive hierarchy — consistent with example ① above.

④ Finding the sweet spot in BLAS Breaking's depth

Breaking by 0,1,2,3,4,5 levels changes speedup by −14.3%, −0.3%, (best), −10.9%, −28.8%, −45.3% relative to the 2-level optimum. What's the trade-off?

  1. 0 levels (FULL BLAS): whole BLASes offloaded — no top-level GPU-side reuse, so performance is 14.3% below optimal.
  2. 1 level: almost matches 2 levels (−0.3%) — a little top-level coherence captured cheaply.
  3. 2 levels: the measured optimum — enough top-level coherence, without excessive fragmentation.
  4. 3–5 levels: performance drops sharply (−10.9%, −28.8%, −45.3%) as partitions get smaller and more numerous, driving up the number of ray-store-and-fetch round trips between GPU and near-memory RT units.
💡
This is a direct trade-off between data reuse (favors more levels on the GPU) and offload overhead (favors fewer, bigger near-memory partitions) — more partitioning is not free, exactly the shape of a diminishing-then-negative returns curve.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Doubling HBM bandwidth only buys 1.2× speedup on this workload. Would doubling bandwidth again (4× total) get you close to 4× speedup?
Show answer
No. Because ray tracing is latency-bound, not bandwidth-bound, adding bandwidth runs into fast diminishing returns — the bottleneck is round-trip latency per pointer-chase, which more bandwidth doesn't shorten.Misconception: that "more bandwidth" and "more speed" scale together. They only do so when bandwidth, not latency, is the binding constraint — Fig. 1 shows it isn't here.
Problem 2 · medium
Why can't RayN just reuse an existing near-memory graph-processing design (e.g., partitioning a graph evenly across near-memory cores) for BVH traversal?
Show answer
Two reasons given in the paper: (1) graph-PIM cores lack the specialized ray-box/ray-triangle intersection hardware, which would otherwise take hundreds of cycles on general compute; (2) graph partitioning assumes node count is a good proxy for load, but BVH partition load depends on an unknown, camera-dependent ray distribution — a harder, more dynamic load-balancing problem.Misconception: that "near-memory computing" is a single interchangeable technique. The near-memory *placement* idea transfers; the *operation units* and the *load model* do not.
Problem 3 · medium
Traversing both TLAS and BLAS on the near-memory RT unit (BB+T) degrades performance by 8% versus keeping TLAS on the GPU. Why doesn't "offload everything" win?
Show answer
Every ray touches the TLAS, so it stays warm in the GPU's own cache — traversing it there is nearly free and highly coherent across a warp. Moving the TLAS to a single memory module forces every ray through that one module's near-memory RT unit, creating a bottleneck, and also increases total nodes processed near-memory by 74%, without gaining anything since the GPU cache was already handling it well.Misconception: that near-memory compute is strictly better wherever it's used. It only wins where the baseline was already latency-bound and cache-unfriendly — the TLAS is neither.
Problem 4 · hard
Increasing BLAS Breaking beyond 2 levels makes performance worse, even though it improves load balance further. Explain the trade-off.
Show answer
More levels create more, smaller bottom partitions, which does spread load more evenly — but each partition boundary is a place where a ray must be written to the near-memory RT unit and its result fetched back, i.e., a round trip. Past 2 levels, the added round-trip overhead (and the shrinking pool of top-level, reusable coherence on the GPU) outweighs the load-balance gains, producing net slowdowns of 10.9% to 45.3%.Misconception: that finer partitioning always improves a partitioned system. Here it trades one cost (load imbalance) for a bigger one (offload round trips) past a fairly shallow optimum.
Problem 5 · medium
JEDEC-compatible RayN gets only 2.0× speedup over treelet prefetching, while Unified/Hybrid get 2.2×, despite JEDEC-compatible following the official HBM standard. What's the cost of compliance here?
Show answer
To avoid a structural hazard without changing the HBM protocol, JEDEC-compatible statically splits memory channels between the GPU and the near-memory RT unit — so each side only ever gets access to half the channels' bandwidth and parallelism, regardless of how the load actually splits at runtime. Unified and Hybrid instead let both streams share full channel access (via a unified or coordinated controller), recovering that lost memory-level parallelism.Misconception: that following a hardware standard is free. Here, standards-compliance costs real memory-level parallelism, which the paper quantifies directly.
Problem 6 · hard
In the worst-case load-imbalance test — all partitions forced into one memory module — RayN's average speedup drops by 1.3× (worst case 1.7× in ROBOT), yet ROBOT still beats the baseline by 3.2×. Why does RayN still win even when load balancing completely fails?
Show answer
Load imbalance only affects how work is *distributed* across near-memory RT units, not whether near-memory access is *individually* faster than a GPU round trip. Even a single overloaded near-memory RT unit still fetches each BVH node with 49.2% less latency than the GPU RT unit would — it's simply doing all of that fast work serially instead of in parallel across four units. The core latency advantage survives; only the additional benefit of parallelism is lost.Misconception: that load balancing is the source of RayN's speedup. It's a multiplier on top of the real source — per-access latency reduction — not the mechanism itself.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly does RayN move near memory?▾
Not the whole ray tracing pipeline — just BVH traversal for the divergent, cache-unfriendly bottom levels of the tree (BLAS partitions past the BLAS-Breaking boundary). Ray generation and shading stay on the GPU; TLAS traversal and the top of each BLAS also stay on the GPU RT unit.
Q2Why is ray tracing latency-bound rather than bandwidth-bound?▾
BVH traversal is pointer chasing: each node read depends on the previous one, so accesses can't be issued far ahead of time or overlapped freely. That makes the number and length of round trips the bottleneck, not the total bytes moved — measured directly in Fig. 1 (1.9× from 2× latency vs. 1.2× from 2× bandwidth).
Q3Why can't the near-memory controller just be added alongside HBM's existing one?▾
HBM's JEDEC standard already places a controller on the host GPU. A second, independent controller in the logic layer could issue conflicting commands to the same physical memory — a structural hazard. RayN's three designs (JEDEC-compatible, Unified, Hybrid) are three different ways to prevent that collision.
Q4Why does JEDEC-compatible need to duplicate the BVH tree?▾
Because it partitions physical channels between the GPU and the logic-layer controller, the GPU and the near-memory RT unit can no longer both reach the same physical memory — so each needs its own copy of the tree in its own set of channels. This costs 127 MB to 1721 MB extra memory depending on scene size.
Q5How does RayN decide where to place each BVH partition?▾
It estimates each partition's future load as root-node volume × partition depth (a proxy for "rays reaching it" × "nodes each ray crosses"), then places every partition into whichever memory module currently holds the least total estimated load — a simple greedy heuristic, since the true, camera-dependent load is unknowable ahead of time.
Q6Can the GPU RT units be removed entirely?▾
Yes, in the BLAS Breaking + TLAS configuration, where near-memory RT units also handle TLAS traversal — at the cost of needing Transform units near memory too (raising area from 0.78% to 1.10%) and a measured 8% performance hit versus keeping TLAS on the GPU, since the TLAS was already cache-friendly there.
Q7Does RayN handle scenes where the camera or objects move?▾
Yes — the partitioning and placement algorithm supports dynamic scenes. Unchanged objects' partitions are reused in place (no data movement); only newly built or deformed partitions are (re)placed by the load-balancing heuristic. Measured across four frames of a moving-camera scene, speedup ranged from 1.8× to 2.9× depending on how much BVH traversal that frame actually required.
Q8Is the area/power overhead actually negligible?▾
The near-memory RT unit adds about 0.78–1.10% of a comparable HBM2 die's area and roughly 0.35 W of power — well within the ~17 W logic-layer budget shown elsewhere to be coolable with an ordinary fan. Memory controller overhead is negligible for the JEDEC-compatible and Hybrid designs, whose logic-layer controllers stay simple and in-order; the Unified design instead needs a full, complex controller in the logic layer, which the paper notes has a higher thermal impact.
Q9How does RayN compare to treelet prefetching, the closest prior work?▾
Treelet prefetching predicts which BVH subtree a ray will need next and prefetches it — but 44% of its prefetches go unused because prediction is hard on divergent rays. RayN sidesteps prediction altogether by moving the traversal compute to where the data already sits, and outperforms treelet prefetching by roughly 2.0–2.2× depending on the controller design.
Q10What did the authors leave for future work?▾
The paper itself doesn't spell out an explicit future-work list. Two plausible extrapolations, not claims the paper makes: better (camera-aware or adaptive) load estimation, given that the current heuristic correlates only weakly with real intersection counts (Fig. 10); and applying similar partitioning ideas to non-dedicated near-memory GPU cores instead of fixed-function RT units.

HBM / TSVHigh Bandwidth Memory (3D-stacked DRAM) and the Through-Silicon Vias connecting its layers to the logic layer.
Near-memory computing / PIMPlacing compute inside or beside memory to cut data-movement cost; the general technique RayN specializes for ray tracing.
SM / warp / SIMTGPU Streaming Multiprocessor; a group of 32 threads executed together; the execution model behind them.
Cache miss ratesAverage L1/L2 miss rates of 39%/45% observed for BVH traversal in these workloads (plain miss rates, not MPKI).
Structural hazardTwo memory controllers contending for the same physical memory address — the core problem the three controller designs solve.
Weighted speedup metricRayN reports average and per-scene speedup normalized to a GPU without near-memory support, on the LumiBench suite.
