Reserving and freeing blocks, without wasting the room you have

A pool of memory, carved into "reserved" and "free" chunks that keep splitting and merging. Knuth's classic chapter lays out and compares first-fit, best-fit, boundary tags, and the buddy system — ideas whose echoes you'll recognize in allocators and page-frame managers you've used since, even though the text itself doesn't trace that lineage.

Ten ideas this chapter assumes you know

Tap any card to expand. Read in order the first time, or jump to whatever's unfamiliar.

1Why fixed-size nodes aren't enough▾

Earlier linked-list techniques assume every node is the same size. That's fine for lists of uniform records, but often we need blocks of many different sizes sharing one pool — for example, an interpreter allocating strings of arbitrary length. That's dynamic storage allocation: reserving and freeing variable-size, contiguous blocks from a shared area.

Now you're ready: the whole chapter is about two operations — reserve n consecutive words, and later free them again — done efficiently, thousands of times, without wasting space.
2The memory map — reserved vs. free▾

At any moment the pool looks like a checkerboard: some stretches reserved (in use), interleaved with stretches free (available). Knuth's Fig. 42 shows a real snapshot: 53 reserved blocks mixed with 21 free ones.

Now you're ready: every algorithm in this chapter is really just answering "how do I track this checkerboard, and update it fast?"
3The AVAIL list lives inside the free space itself▾

You need a list of where the free blocks are. The clever trick: don't allocate separate bookkeeping memory for it — store the list inside the free blocks themselves. The first word of each free block holds its SIZE and a LINK to the next free block. Free space bookkeeps itself, for free.

Now you're ready: reserved blocks cost nothing extra to track; only free blocks need a SIZE/LINK header — and they already have the room.
4First-fit vs. best-fit — the core policy choice▾

To satisfy a request for n words, walk the AVAIL list until you find a block big enough. First-fit: take the very first one that qualifies. Best-fit: search the whole list and take the smallest one that still qualifies (hoping to save big blocks for later).

Now you're ready: best-fit sounds smarter, but Knuth shows — with real numbers — that it can strand you where first-fit wouldn't. That's the paper's first big surprise.
5Fragmentation — the recurring villain▾

Every time you carve n words out of a bigger block, a smaller leftover remains. Repeat this enough times and the pool fills with tiny, useless slivers — plenty of total free space, but no single piece big enough for the next request.

Now you're ready: nearly every technique in this chapter — the constant c, boundary tags, the buddy system — exists to fight fragmentation in a different way.
6Coalescing — merging neighbors back together▾

When a block is freed, check whether its immediate left and right neighbors in memory are also free. If so, merge all three into one larger free block. Skip this step and boundaries between free/reserved areas tend to perpetuate themselves, leaving memory more broken up than it needs to be.

Now you're ready: "liberation" (freeing) is mostly the problem of coalescing cheaply — that's what boundary tags are built to solve.
7Boundary tags — checking neighbors in O(1)▾

Put a TAG (reserved/free) and SIZE field at both ends of every block — first word and last word. To free a block, jump directly to the tag just before it and just after it: two memory reads tell you instantly whether either neighbor is free, with zero list-searching.

Now you're ready: this is the mechanism that makes freeing (Algorithm C) run in constant time, no matter how long the AVAIL list is.
8The buddy system — powers of two only▾

Restrict every block to a size that's a power of two (2, 4, 8, 16, …), and keep a separate free-list per size class. Splitting a block of size 2k+1 yields two buddies of size 2k. The trick: given a block's address and size, you can compute its buddy's address instantly with an XOR — no list search needed. You still have to check the buddy's own TAG and KVAL to confirm it's actually free and the same size before merging, but that's one direct read, not a search.

Now you're ready: the buddy system trades some wasted space (rounding up to a power of two) for near-instant, guaranteed-correct merging.
9The fifty-percent rule — an equilibrium heuristic▾

Run first-fit/best-fit allocation long enough and the system settles into a rough steady state where the number of free blocks is about half the number of reserved blocks (when leftover slivers below a small threshold are simply absorbed rather than kept). It's a statistical regularity, not a guarantee — but it predicts AVAIL-list length surprisingly well.

Now you're ready: when you see "N reserved, M free" numbers later, check them against M ≈ ½N — that's the fifty-percent rule at work.
10Overflow and relocation▾

Sometimes there's enough total free space for a request but no single free block big enough — fragmentation, not scarcity. Fixing this means either compacting (physically sliding reserved blocks together) or evicting something to secondary storage. Compacting requires being able to relocate every reference to a block — which many programs can't guarantee.

Now you're ready: the chapter ends by asking which blocks to evict when overflow strikes — using a "recently-used" bit and a circular scan, the direct ancestor of the clock/LRU page-replacement algorithms.
The whole story in one place

Dynamic storage allocation in a nutshell

The problem, the policy choice that matters more than it looks, and the two structural fixes that dominate practice.

A pool of memory is shared by many differently-sized blocks that come and go unpredictably. Two questions recur forever: reservation — given a request for n words, which free block do we carve it from? — and liberation — when a block is freed, how do we get it back into circulation without leaving the pool more fragmented than before?

The reservation policy matters more than intuition suggests. Best-fit sounds prudent — save the big blocks for later — but Knuth's own worked example shows it can get stuck on a request that first-fit satisfies easily, using the exact same total free space. Best-fit also tends to leave behind more tiny, useless slivers, because it deliberately hunts for tight fits.

Liberation's core danger is fragmentation: unless adjacent free blocks are merged back together immediately, boundaries between reserved and free areas tend to calcify, and memory gets permanently more broken up. Two structural answers dominate: boundary tags (a TAG+SIZE field at both ends of every block, plus doubly linked pointers on free blocks) let you check either neighbor and splice a merge into the AVAIL list in constant time, with no list search needed to find that neighbor; and the buddy system restricts sizes to powers of two so a block's merge partner can be computed with a single XOR, at the cost of rounding every request up and wasting roughly a third of the space on average.

A statistical regularity — the fifty-percent rule — predicts that in equilibrium, the number of free blocks settles near half the number of reserved ones. And a deeper theorem, due to J. M. Robson, proves something sobering: no allocator that never relocates already-reserved blocks can guarantee good memory utilization in the worst case — some amount of copying/compaction is unavoidable if you want a utilization guarantee.

🧩 Key takeaways

  • The AVAIL list of free blocks is stored inside the free blocks themselves — no separate bookkeeping memory needed.
  • First-fit beats best-fit in practice: best-fit searches more, leaves smaller slivers, and can get stuck where first-fit succeeds.
  • Boundary tags make neighbor-checking O(1) — no AVAIL-list search to find who's next door — though splicing a freed neighbor out of the AVAIL list still relies on the doubly linked LINKF/LINKB fields, not the tags alone.
  • The buddy system makes coalescing an O(1) address computation (XOR), at the cost of rounding to powers of two.
  • The fifty-percent rule: at equilibrium, free blocks ≈ half of reserved blocks.
  • Immediate coalescing beats the simple, non-compacting garbage collection Knuth critiques, because it lets boundary scars perpetuate between sweeps — though he notes GC with compaction, under the right pointer-discipline assumptions, can do just as well.
  • Robson's theorem: without relocation, no allocator can guarantee good worst-case utilization — some copying is unavoidable.
Seven everyday pictures

How to think about allocation

Read in any order. Every card ends with an honest note on where the picture breaks.

Reservation policy · First-fit vs. best-fit

A parking lot with no assigned spots

First-fit: pull into the very first open spot you see. Best-fit: keep circling, looking for the space that fits your car most snugly. Circling costs time and gas — and if you're too picky, you can end up stuck outside while two "too-small-for-you" spots sit open that together would have room, if only they were one spot. That's best-fit's exact failure on the 1300/1200 example.

Where it breaks: real parking spots don't fragment into slivers over time the way memory blocks do — a car leaves a whole spot; a memory request frees a whole block that then gets split unevenly by later requests.
Boundary tags · O(1) coalescing

Page numbers printed top and bottom

Some books print the chapter title at both the top-left and bottom-right of every spread, so you can tell instantly, from any page, where you stand — without flipping back to the table of contents. A boundary tag does the same for a memory block: a TAG+SIZE stamped at the first word and the last word. To check whether your neighbor is free, jump straight to its tag — one read, no searching.

Where it breaks: books don't merge pages together. Boundary tags exist specifically to enable merging (coalescing) two neighboring blocks into one — the analogy only captures the "instant lookup" half of the trick.
Buddy system · Instant merge partners

Halving a pizza, again and again

Cut a pizza exactly in half, then cut one half in half again. Each piece has exactly one "buddy" — the specific other piece it was split from — and it will only ever reunite with that one buddy, never with any other slice of the same size lying around. Because every cut is a clean halving, you always know, just from a slice's position, exactly where its buddy is: no need to inspect it first.

Where it breaks: if your party needs 3 slices' worth of pizza, you still have to buy (and pay for) 4 slices — you round up to the next power of two. That's the buddy system's real cost: on average about a third more space than you actually asked for.
Fifty-percent rule · Equilibrium

A subway platform at rush hour

Riders (reserved blocks) fill most of the platform; gaps (free blocks) appear as people board trains. In steady, random traffic, the platform settles into a predictable rhythm — roughly half as many gaps as riders, on average, even though any single snapshot looks noisy. That's exactly the shape of Knuth's fifty-percent rule: not a hard guarantee, but a statistical equilibrium.

Where it breaks: the rule assumes each freed block is equally likely to be any reserved block ("random lifetime"). If departures are more first-in-first-out — like a real rush-hour crowd boarding in arrival order — the platform empties more cleanly than the rule predicts.
Immediate coalescing vs. sweep GC

Washing dishes as you go, vs. Sunday's big pile

Wash each dish right after the meal and your sink stays clear and organized. Let dishes pile up for one big Sunday wash and, in the meantime, you improvise — stacking mismatched pots wherever there's room, wedging things in oddly. By the time you finally clean up, the kitchen has settled into an awkward arrangement that a single big wash doesn't fully undo. Knuth makes the same point about garbage collection: waiting until memory is exhausted, then sweeping, lets boundary scars between free and reserved areas calcify in ways that immediate coalescing on every free never allows.

Where it breaks: modern garbage collectors add compaction — physically sliding live objects together during the sweep — which does fix the scarring problem Knuth describes for his simpler, non-compacting sweep.
Overflow eviction · Recently-used bit

A night guard walking a circular hallway

Rooms line a circular hallway, each with a light that turns on when someone's inside working. A guard walks the loop repeatedly: at each room, if the light is on, they turn it off and move on; if the light is already off, that room is evicted. Anyone still actively using a room gets one more lap of grace before their light is checked again. This is precisely the "recently-used bit + circular scan" scheme Knuth proposes for choosing what to evict on overflow — and it's the direct ancestor of the clock algorithm used in real page-replacement systems.

Where it breaks: a real guard's walk takes real time proportional to the hallway's length; in fast paths, hardware or approximate/segmented scans (as in modern OS page reclaim) are needed to keep the "walk" itself cheap.
Distributed fit · Sized slots + overflow

Assigned seating, with a few extra chairs in the back

A banquet hall assigns each guest a seat sized (roughly) for them, based on the expected distribution of party sizes — mostly right, occasionally a mismatch that spills into a small block of flexible overflow seating near the back. Coffman and Leighton's distributed fit method works the same way: pre-size N slots to match the known size distribution, then add a small overflow area of about √N · lg N slots — the same math that governs how far a linear-probing hash table's insertions wander from their ideal slot.

Where it breaks: fixed-size seats never need "coalescing" — they're just occupied or empty. Distributed fit works only because it assumes a known, stable size distribution; an unexpected mix of party sizes defeats the pre-sizing entirely.
The full explanation

How it actually works

Section by section, following the paper's own algorithm labels (A, B, C, R, S).

1 · Reservation — Algorithm A (first-fit)

Walk the AVAIL list from a pointer Q; let P = LINK(Q). If SIZE(P) ≥ N, that block qualifies — subtract N from it (or remove it entirely if the remainder K = SIZE(P) − N is zero) and reserve the tail-end N words. Otherwise advance Q and keep walking. This is plain first-fit.

💡
The refinement (A4′): if the leftover K is smaller than a small constant c (Knuth suggests 8–10), don't bother keeping that sliver as a separate free block — just give the whole thing away. A block of size 1 is "so small it is virtually useless" and just clogs the AVAIL list.

2 · Liberation — Algorithm B (sorted AVAIL list)

To free a block at address P0, keep the AVAIL list sorted by memory address so you can find its immediate left neighbor Q and right neighbor P by walking forward until you pass P0. Check both: if P0 + N = P, merge with the right neighbor; if Q + SIZE(Q) = P0, merge with the left. This correctly collapses up to three adjacent free areas into one — but costs a search through, on average, about half the AVAIL list.

3 · Liberation without searching — boundary tags (Algorithm C)

Give every block, reserved or free, a TAG and SIZE field in both its first and last word. Now freeing a block at P0 needs no list search at all: read TAG(P0 − 1) to check the left neighbor and TAG(P0 + SIZE(P0)) to check the right one — both are direct memory reads, not searches.

4 · The buddy system — Algorithms R and S

Restrict all sizes to powers of two, and keep a separate doubly-linked free-list AVAIL[k] for each size 2k. To reserve 2k words (Algorithm R): find the smallest non-empty list at size ≥ 2k, and if it's larger than needed, repeatedly split in half, shelving the unused half at the next size down, until you reach exactly 2k.

To free a block at address L of size 2k (Algorithm S): compute its buddy's address directly — buddyk(x) = x XOR 2k — and check whether that buddy is currently free and the same size. If so, remove it from its free-list, merge the pair into one 2k+1-word block, and repeat the check one level up. If not, simply add the freed block to AVAIL[k].

# buddy address — no search, just bit arithmetic
buddy_k(x) = x + 2^k   if x mod 2^(k+1) == 0
buddy_k(x) = x − 2^k   if x mod 2^(k+1) == 2^k

5 · Comparing costs — the fifty-percent rule and the limits of any allocator

At equilibrium, if p is the probability that a reservation's leftover exceeds the small constant c (i.e., a genuine new free block is created rather than being absorbed), the expected number of free blocks M relates to the number of reserved blocks N by M ≈ ½pN — the fifty-percent rule. Knuth derives it by tracking how freeing a block changes M by −1, 0, or +1 depending on whether zero, one, or two of its neighbors are already free.

⚠
The hard limit. J. M. Robson proved that no allocation strategy that never relocates already-reserved blocks can guarantee good worst-case memory utilization — even restricting block sizes to just 1 and 2, overflow can occur with memory only about ⅔ full, regardless of which algorithm you use. Guaranteed utilization requires the ability to move things — i.e., compaction.

Overflow itself — needing more room than any single free block offers — is handled by either compacting memory (sliding reserved blocks together) or evicting something. For eviction, Knuth proposes a circular list of reserved blocks, each carrying a "recently used" bit set on every access; a pointer sweeps the circle, clearing bits, and evicts the first block it finds whose bit was already clear. This is the direct ancestor of the clock algorithm used for page replacement in real operating systems.

Follow the numbers, step by step

Worked examples

Four traces using the paper's own numbers.

① Tracing first-fit vs. best-fit through the same three requests

Free blocks: 1300, 1200. Requests, in order: 1000, then 1100, then 250.

  1. First-fit, request 1000: the first block encountered ≥ 1000 is the 1300-word one. Reserve 1000, leaving 300. State: {300, 1200}.
  2. First-fit, request 1100: 300 is too small; 1200 qualifies. Reserve 1100, leaving 100. State: {300, 100}.
  3. First-fit, request 250: 300 qualifies (first in address order). Reserve 250, leaving 50. State: {50, 100}. Success.
  4. Best-fit, request 1000: both blocks qualify; choose the smallest that fits — 1200. Reserve 1000, leaving 200. State: {1300, 200}.
  5. Best-fit, request 1100: only 1300 qualifies (200 too small). Reserve 1100, leaving 200. State: {200, 200}.
  6. Best-fit, request 250: neither 200-word block qualifies. Stuck — despite 400 total free words.
🧩
Insight: best-fit's "save the big block" instinct backfires: it used up all the large free space early, leaving two mid-size slivers that individually can't satisfy a mid-size request. First-fit's indifference kept one block flexible enough.

② Computing a buddy address with XOR

The paper states: the buddy of the size-16 block at binary address 101110010110000 is 101110010100000. Verify it.

  1. Size 16 = 24, so k = 4. A block of size 2k always has its address a multiple of 2k — the low k bits are zero, which they are here: ...10110000 ends in four zeros.
  2. buddyk(x) = x XOR 2k — flip exactly bit position 4 (counting from 0). 24 = 10000 in binary.
  3. x = ...10110000. Bit 4 of x (the "1" just left of the trailing zeros) is currently 1.
  4. Flip it: ...10110000 XOR ...00010000 = ...10100000.
  5. Result: 101110010100000 — exactly matches the paper's stated buddy address.
💡
This is the whole trick: because every split is a clean binary halving, "where is my buddy" is answered by one XOR — never a search, never even a memory read of the buddy itself.

③ Checking the fifty-percent rule against real simulation numbers

Knuth's Fig. 42 simulation, first-fit, size distribution (S1): 53 reserved blocks, 21 free blocks. He also reports 49 reserved, 25 free at TIME = 4600. Does the rule (M ≈ ½N, since p ≈ 1 here) hold?

  1. Fig. 42 snapshot: predicted M ≈ ½ × 53 = 26.5. Actual: 21. Off by about 5.5 blocks.
  2. TIME = 4600 snapshot: predicted M ≈ ½ × 49 = 24.5. Actual: 25. Off by only 0.5 — essentially exact.
  3. Interpretation: the rule is an equilibrium average, not a per-snapshot guarantee — Knuth explicitly notes the number of available blocks "generally ranged between 20 and 30" while reserved ranged "45 to 55," which brackets both readings.
  4. Sanity range check: ½ × 45 = 22.5 and ½ × 55 = 27.5 — both real snapshots (21 and 25) fall within a few blocks of this band.
🧩
Insight: the fifty-percent rule is a statistical center of gravity, not a fixed ratio at every instant — exactly what you'd expect from an equilibrium argument built on averages, and Knuth says so explicitly.

④ Why the buddy system wastes about a third of its space

The paper says rounding to powers of two "on the average means about four thirds as much memory was requested." Derive that ratio for sizes uniformly distributed between 2k−1+1 and 2k.

  1. Every such request rounds up to 2k words (the next power of two).
  2. The mean requested size over that uniform range is roughly the midpoint: (2k−1 + 2k) / 2 = 3·2k−1/2 = 3·2k−2.
  3. The ratio of allocated to requested: 2k / (3·2k−2) = 4/3 ≈ 1.33.
  4. That's the "four thirds" the paper cites — a 33% average overhead from power-of-two rounding, assuming sizes are uniform within a range. Knuth separately gives a looser estimate for sizes that aren't powers of two at all: about 44% more space than requested — a different assumption about the input distribution, not a simulated worst case.
  5. Contrast with boundary tags: per the paper's own timing estimates, boundary-tag reservation costs about 33 + 7A time units (A ≈ 2.8 on average ⇒ ≈ 52.6); the buddy system's own formulas are 19 + 25R for reservation and 27 + 26S for liberation, where R and S are the fraction of operations that trigger a split or merge — often faster in practice, but that speed is bought with the 33%+ space tax just computed.
💡
Space vs. time, in one comparison: buddy system ≈ faster operations, more wasted bytes; boundary tags ≈ zero rounding waste, a bit more per-operation work. Neither dominates — which is why real allocators (and real tiered-memory managers) often layer both ideas at different granularities.

Practice problems

Problem 1 · easy
Free blocks {1300, 1200}, but now the requests arrive in the opposite order: 1100 first, then 1000, then 250. Does best-fit still get stuck?
Show answer
Best-fit, req 1100: smallest block ≥ 1100 is 1200 → leaves 100. State {1300,100}. Req 1000: only 1300 qualifies → leaves 300. State {300,100}. Req 250: 300 qualifies → leaves 50. Succeeds this time! Misconception: that best-fit is "always" worse. It's worse on this specific request order/sizes — order matters, which is exactly why Knuth calls the counter-example illustrative, not universal (and notes a contrary example exists too).
Problem 2 · medium
A buddy-system block of size 2⁶ = 64 sits at address 192 (binary 11000000). What is its buddy's address?
Show answer
k=6, so check bit 6 (value 64) of x=192=11000000₂. 192 mod 128 = 64, which equals 2^6, so we're in the "x − 2^k" case: buddy = 192 − 64 = 128. Check: 128 XOR 64 = 192 ✓.Misconception: that you need to know the buddy's contents to find it. You only need the block's own address and size — buddy address is pure arithmetic.
Problem 3 · medium
A steady-state system has 80 reserved blocks and the constant c is set very small (so p ≈ 1). Roughly how many free blocks does the fifty-percent rule predict?
Show answer
M ≈ ½pN = ½ × 1 × 80 = 40 free blocks, though any given snapshot might read anywhere from roughly 35–45 due to statistical variation, as the paper's own simulations show.Misconception: that the rule gives an exact count. It's an equilibrium average with real variance around it — treat it as a sanity check, not a formula to plug in and trust exactly.
Problem 4 · hard
Algorithm B (sorted AVAIL list) searches about half the list on average to free a block. Boundary tags (Algorithm C) need zero search. What did we give up to get that speedup?
Show answer
Extra bookkeeping bits in every block, reserved or free — a TAG and SIZE field at both the first and last word (versus Algorithm B, which only needs SIZE/LINK in the free blocks it's currently tracking). This overhead is negligible for large blocks but can be a real cost when average block size is small.Misconception: that boundary tags are "strictly better." They trade a fixed per-block space overhead for eliminating a search — a good trade when blocks are large, a worse one when they're tiny (a few words each).
Problem 5 · medium
Two adjacent free areas exist, but a naive garbage collector doesn't merge them because one was never removed from a "currently free" bookkeeping structure the way immediate coalescing would. What specifically goes wrong if you then reserve part of the visible free area and later garbage-collect?
Show answer
You get two separate free areas where, had you coalesced immediately, you'd have had one larger one (or a cleanly re-mergeable pair). The paper's own diagram shows this exactly: reserving inside a known-available region and then garbage-collecting leaves the boundary split in a worse position than immediate liberation-and-coalescing would have — the "boundary perpetuates itself" effect.Misconception: that garbage collection is strictly simpler and therefore safe to prefer. Without compaction, sweep-based GC can leave memory measurably more fragmented than eager coalescing, which is why Knuth recommends coalescing-on-free for the algorithms in this section.
Problem 6 · hard
Robson proved no non-relocating allocator guarantees good worst-case utilization, even restricting block sizes to just 1 and 2. Why can't a "smarter policy" simply be designed around this?
Show answer
Robson's result is adversarial: for any fixed algorithm that never moves already-placed blocks, there exists some sequence of requests and frees that drives it into a bad fragmentation state — regardless of how the policy chooses among candidates. It's a limit on the whole class of non-relocating strategies, not a flaw in any one of them. The only way around it is to allow relocation (compaction/copying), which changes the problem entirely.Misconception: that this is just an unlucky edge case for weak algorithms. It's a fundamental impossibility result — no clever heuristic escapes it without relocation.
Problem 7 · easy
Where does the AVAIL list's bookkeeping data (SIZE, LINK) physically live?
Show answer
Inside the free blocks themselves — the first word (and, for boundary tags, the last word too) of each currently-free block. No separate directory is needed except for special cases like disk-based storage with nonuniform access time.Misconception: that a separate index structure tracks free space. For ordinary memory, the free list is self-hosting — the free space is its own directory.
Problem 8 · medium
In the "night guard" eviction scheme, four rooms in circular order have recently-used bits [1,0,1,1] and the guard's pointer currently sits at room 1 (the second room, bit=0). Walk through eviction.
Show answer
Room 1's bit is already 0 → evict room 1 immediately, no clearing needed. (Had it been 1, the guard would clear it to 0 and advance, giving that room "one more lap" of grace before being reconsidered — exactly the second-chance behavior of the clock algorithm.)Misconception: that the guard always makes a full lap before evicting anything. Eviction happens at the very first room found with an already-clear bit — which could be the very next room checked.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the actual difference between "block," "node," and "area" in this chapter?▾
Knuth deliberately switches from "node" (used elsewhere in the book for fixed-size linked structures) to "block" or "area" here, precisely because this section is about variable-size, contiguous regions of memory — not uniform linked-list cells.
Q2Why not just always use best-fit — isn't a tighter fit obviously better?▾
A tighter fit locally looks efficient, but best-fit systematically hunts down the smallest usable block, which tends to (a) create more tiny unusable slivers and (b) require a full list search rather than stopping at the first match. Knuth's worked example also shows it can get outright stuck where first-fit succeeds, using identical total free space.
Q3How can freeing a block be "instant" — don't you have to at least check both neighbors?▾
Yes — but "checking" with boundary tags means reading one word at a fixed, precomputed address (right before the block, and right after it), not searching a list. That's O(1): a couple of direct memory reads, regardless of how many other free blocks exist elsewhere in the pool.
Q4Why does the buddy system need power-of-two sizes specifically?▾
Because the buddy-address trick (XOR with 2^k) only works if every split is an exact halving all the way down from one power-of-two total pool size. Any other split ratio would make "where is my buddy" ambiguous without extra bookkeeping.
Q5How much space does the buddy system actually waste?▾
On average about 33% ("four thirds as much memory") for sizes uniformly spread within a power-of-two range. Knuth gives a separate, looser estimate of about 44% more space when sizes aren't powers of two at all — a different assumption about the input distribution, not a simulated worst case.
Q6Is the fifty-percent rule a proof or a heuristic?▾
It's a derived equilibrium result (Knuth gives the derivation), but it rests on a simplifying assumption — that each freed block is equally likely to be any currently-reserved block. Real freeing patterns (e.g., closer to first-in-first-out) can do noticeably better than the rule predicts.
Q7Why is immediate coalescing better than garbage collection for fragmentation?▾
Garbage collection (in the simple, non-compacting form Knuth describes) only reclaims blocks — it doesn't merge them with neighbors that were already available but sitting outside the "in-use" tracking. Boundaries between reserved and free regions can then calcify between collections, leaving memory more broken up than eager, every-free coalescing would.
Q8What does Robson's theorem actually rule out?▾
It rules out any guarantee of good worst-case utilization for allocators that never relocate already-placed blocks — even in the simplest case of block sizes restricted to 1 and 2. It doesn't say typical/average-case behavior is bad (simulations show it's often quite good); it says no worst-case guarantee is possible without relocation.
Q9What's "distributed fit," in one sentence?▾
Pre-allocate slots matching the known distribution of request sizes, plus a small overflow area sized like the expected maximum displacement in a linear-probing hash table — trading a small, provably-bounded amount of overflow space for near-zero search cost, if the size distribution is known in advance.
Q10How does the "recently-used bit" eviction scheme relate to real operating systems?▾
Directly — it's essentially the clock (second-chance) page-replacement algorithm: a circular scan over resident items, clearing a "used" bit on each visit and evicting the first item whose bit is already clear. Many production page-reclaim algorithms (and their tiered-memory descendants) are refinements of exactly this idea.
Q11Do first-fit and best-fit ever perform identically?▾
Yes — Knuth notes this happens with the "distributed fit" method, because pre-sorting slots by size makes searching from the front (first-fit) and searching for the smallest fit (best-fit) find the same slot. In general, though, the two policies diverge, sometimes sharply, as the 1300/1200 example shows.
Q12What did the simulations conclude about the modified Algorithm A (with constant c)?▾
A striking result: unmodified Algorithm A needed about 125 list-inspections on average to find a fit (with ~250 available blocks present), while the version that absorbs tiny leftover slivers (exercise 6's refinement) needed only about 2.8 — over half the time finding a fit on the very first try.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
Dynamic storage allocationAlgorithms for reserving and freeing variable-size, contiguous blocks from a shared memory pool.
AVAIL listThe linked list of free blocks, typically stored inside the free space itself via SIZE and LINK fields.
First-fitReservation policy: take the first free block in the list large enough for the request (Algorithm A).
Best-fitReservation policy: search the whole list, take the smallest free block that still fits.
FragmentationThe state where free space exists but is split into pieces too small individually to satisfy a request.
CoalescingMerging adjacent free blocks back into one, done on every liberation to prevent fragmentation from compounding.
Boundary tagsTAG + SIZE fields stored at both the first and last word of every block, enabling O(1) neighbor checks and merges (Algorithm C).
Buddy systemAllocation restricted to power-of-two sizes; a block's merge partner ("buddy") is computed via XOR, not search (Algorithms R, S).
Fifty-percent ruleEquilibrium heuristic: at steady state, the number of free blocks is roughly half the number of reserved blocks.
Robson's theoremNo non-relocating allocation strategy can guarantee good worst-case memory utilization; relocation (compaction) is required for that guarantee.
Supporting terms
TAG fieldA bit or field marking a block as reserved ("+") or free ("−"); read directly to check neighbors without searching.
Buddy address, buddyk(x)The address of the sibling block a given block of size 2k was split from; computed as x XOR 2k.
Distributed fitCoffman & Leighton's method: pre-size slots to match the known request-size distribution, plus a small overflow area of about √N · lg N slots.
CompactionPhysically sliding reserved blocks together to eliminate fragmentation entirely — requires the ability to relocate references.
Recently-used bit / circular scanOverflow-eviction scheme: a bit set on access, cleared by a sweeping pointer, with eviction at the first already-clear bit — ancestor of the clock page-replacement algorithm.
Constant c (Algorithm A′)A small threshold below which a reservation's leftover sliver is absorbed rather than kept as a new free block, to avoid clogging the AVAIL list.
