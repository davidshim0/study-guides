SOSP '97 · ACM TOCS 1997 · A Field Guide

Catching races by checking a promise, not by getting lucky with timing

Two threads touch the same variable. The old way waits for the one unlucky schedule that lets you see them collide. Eraser instead asks, on every single access: has some lock consistently protected this? — so scheduler luck stops mattering.

📄 Savage, Burrows, Nelson, Sobalvarro, Anderson · "Eraser" 🎓 Threads, locks, and OS basics assumed — primers cover the rest ⏱ ~30 min read
🔒

If no single lock was held by every thread on every access to a shared variable, the locking discipline was broken — no matter what actually happened to occur during this run.
Refine a candidate set of locks; if it ever empties out, sound the alarm.

1Threads and shared memory▾

A thread is an independent stream of execution inside one process, sharing that process's memory with every other thread in it. That sharing is the whole point of multithreading (fast communication, no copying) — and the whole source of the danger this paper is about.

Now you're ready: "shared variable" means any memory word more than one thread can reach — globals and heap data, which is exactly what Eraser watches.
2What a data race actually is▾

Two threads race on a variable when both access it concurrently, at least one access is a write, and nothing in the program stops the two accesses from overlapping in time. The outcome then depends on scheduling luck — a bug that may vanish for months and reappear under load.

Now you're ready: Eraser's whole job is finding these three conditions without ever needing them to actually collide during a test run.
3Locks and mutual exclusion▾

A lock is a mutual-exclusion object: available, or owned by exactly one thread. lock(mu) / unlock(mu) around a piece of code (a "critical section") guarantees only one thread executes it at a time. Locks are the standard tool for preventing races.

Now you're ready: a "locking discipline" is a policy about which lock(s) must be held around accesses to which variable — Eraser checks that the discipline was actually followed.
4The happens-before relation▾

Lamport's happens-before is a partial order over all events in a concurrent run: events in one thread are ordered by program order, and a lock's release happens-before the next thread's acquire of it. Two accesses that are not ordered by happens-before could, in principle, have occurred simultaneously — a potential race.

Prior race detectors watched for exactly this: conflicting accesses unrelated by happens-before in the one interleaving that actually ran.

Now you're ready: happens-before tools need the unlucky interleaving to show up during testing. Eraser's contribution is a check that doesn't.
5Binary rewriting / instrumentation▾

Rather than requiring source changes, a binary rewriter (here, DEC's ATOM tool) takes a compiled program and inserts extra instructions — e.g. a call before every load and store — producing a new, functionally identical binary that also reports to a monitoring runtime.

Now you're ready: Eraser instruments every load, every store, and every lock/unlock call in an unmodified Alpha/Digital Unix binary — no source annotations required to get started.
6Shadow memory▾

A shadow word is a small piece of metadata that a monitoring tool keeps alongside each real memory word — found at a fixed address offset from the data it describes. It's a general technique used by many dynamic-analysis tools, not just Eraser.

Now you're ready: Eraser gives each monitored 32-bit word its own shadow word holding a candidate-lockset ID and a 2-bit state.
7Sets and set intersection▾

The set intersection A ∩ B keeps only elements common to both sets. If A shrinks every time you intersect it with something new, it can only ever get smaller (or stay the same) — it never grows back on its own.

Now you're ready: the candidate lock set C(v) only ever shrinks via intersection as more accesses are observed — once a lock leaves C(v), it's gone until you reset the algorithm's state for v.
8Reader-writer locks▾

A plain lock allows one owner at a time, for anything. A read-write lock is more permissive: any number of threads may hold it in read mode simultaneously, but write mode requires sole ownership. This is safe because concurrent reads never conflict — only a write can conflict with anything.

Now you're ready: Eraser has a relaxed version of its rule for these locks — read accesses only need some mode of the lock; writes need it in write mode specifically.
9False positives and program annotations▾

A dynamic checker built on a heuristic (here, "one consistent lock") will sometimes flag code that is actually correct for reasons the checker can't see — private allocators, hand-rolled locks, or deliberately unsynchronized "benign" races. An annotation is a small marker programmers add to tell the tool "trust me, this is fine" for a specific case.

Now you're ready: a handful of annotations (EraserIgnoreOn/Off, EraserReuse, EraserReadLock/WriteLock) is what turns Eraser's raw output — often over a hundred warnings — into zero.
The whole story in one place

The Lockset algorithm in a nutshell

The problem with waiting for luck, the fix that doesn't need it, and how the pieces connect.

Prior dynamic race detectors relied on happens-before: watch one execution, and flag any two conflicting accesses that weren't ordered by synchronization in that particular run. The catch is that whether a race gets flagged depends entirely on which interleaving the scheduler happened to produce — a genuine race can hide for months if the unlucky ordering never shows up during testing.

Eraser instead enforces a locking discipline directly: for every shared variable v, it maintains a candidate lock set C(v) — the locks that have protected every access to v seen so far. Each access intersects C(v) with the locks the accessing thread currently holds. If C(v) ever becomes empty, no single lock protected every access — a violation is reported regardless of the order those accesses actually occurred in.

Naively this would misfire constantly on ordinary, correct code — unlocked initialization, read-only sharing, reader-writer locks — so the paper layers in a small state machine (Virgin → Exclusive → Shared → Shared-Modified) that suppresses warnings until a variable is genuinely write-shared, plus a relaxed rule for reader-writer locks. The result, implemented via ATOM binary rewriting on Digital Unix/Alpha, found real bugs in production AltaVista, Vesta, and Petal server code — at a 10–30× runtime cost, with false alarms suppressed by a handful of hand-placed annotations.

🔍 Key takeaways

  • Happens-before tools need the right interleaving to occur; Eraser's discipline check doesn't depend on which interleaving ran.
  • C(v) only shrinks — once it's empty, a race has been proven, independent of timing.
  • A four-state machine (Virgin/Exclusive/Shared/Shared-Modified) tames false alarms from initialization and read-sharing.
  • Reader-writer locks get a relaxed rule: reads need any mode held, writes need write mode specifically.
  • Implemented via ATOM binary rewriting — no source changes needed to get a first run.
  • Cost: 10–30× slowdown, but found real bugs in three of four production servers tested.
  • Annotations (EraserIgnoreOn/Off, EraserReuse, EraserRead/WriteLock) reduce hundreds of false alarms to zero.
💡
Why this rhymes with kernel memory-tiering work: Section 3.4 of the paper describes porting this idea into the SPIN OS kernel, treating each raised interrupt level as an implicit lock. The same shape of problem shows up in Linux's mm — per-node LRU lists, hot/cold page counters, and migration bookkeeping in tiering paths are full of intentionally racy counters, the kernel's own dynamic checker (KCSAN) is a direct descendant of this exact idea: watch every access, infer a discipline, flag violations without needing a specific bad interleaving to occur.
Six everyday pictures

How to think about Eraser

Each picture stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Process of elimination

A detective narrowing suspects

Start with every possible suspect (every lock). Each new clue (access) rules some out — keep only who's consistent with all clues so far. If the list of suspects ever hits zero, you've proven nobody fits the story: something's wrong. Eraser's C(v) is exactly this — a shrinking suspect list, and an empty list is a solved case, not a hunch.

Where it breaks: a detective can be wrong about which clues matter; C(v) can't — but it also can't tell you why the discipline broke, only that it did. You still read the backtrace to find the actual bug.
Why happens-before misses things · Timing luck

A guard filmed only sometimes

Imagine a hallway camera that only films when two people are in it at the exact same moment — if they walk through seconds apart, no footage, no evidence, even if the corridor never had a proper guard posted at all. That's happens-before: it can only see a race in the one interleaving that ran. Eraser instead checks the guard's actual duty roster (which lock protected which visit) — a gap shows up whether or not two people happened to overlap.

Where it breaks: the roster check only works if "protection" means "a lock was consistently held." Post/wait signaling (semaphores) has no owner and no roster — Eraser can't reason about it the same way.
Suppressing false alarms · Initialization

A diary before it's shared

You can scribble freely in your own diary with nobody watching — no need to lock the drawer. Only once you start passing it around to others does the "everyone must ask permission first" rule need to kick in. Eraser's Virgin → Exclusive states are exactly this grace period: a variable touched by only one thread so far is assumed to be mid-initialization, and its accesses don't refine C(v) at all.

Where it breaks: if you hand the diary to a friend before you've finished writing in it, there's no warning — the paper admits this makes initialization-checking dependent on the scheduler again, in exactly the narrow case Eraser otherwise avoids.
Cheap representation · Lockset canonicalization

A library call-number instead of a shelf list

A library doesn't reprint a book's full location description on every card — it assigns a call number once, and every reference afterward is just that number. Eraser observed under 10,000 distinct lock sets in any run, so instead of storing a per-variable list of lock addresses, each shadow word stores a tiny 30-bit lockset index into one shared table — set intersection becomes a cached table lookup.

Where it breaks: the trick only pays off because real programs reuse a small number of distinct locksets. A program that constructed a wildly different lock combination on every access would blow up the table just as fast as storing lists directly.
Living with heuristics · Annotations

Telling the smoke detector "that's just toast"

A smoke detector can't tell burnt toast from a real fire — it just alarms on smoke. Rather than remove the detector, you learn to silence it for the one known-harmless case. EraserIgnoreOn/Off, EraserReuse, and the read/write-lock annotations are exactly this: a targeted, permanent "this specific smoke is fine" note, so the alarm stays sharp everywhere else.

Where it breaks: annotate too broadly (silence the whole kitchen, not just the toaster) and you can genuinely mask a later fire — the paper is explicit that sloppy annotations risk losing real warnings, not just false ones.
Legitimate races · Double-checked idioms

Peeking through the window before knocking

You glance through the window to see if anyone's home before ringing the bell — no lock needed for a glance, but you still knock (take the lock) and check again before walking in, in case someone arrived while you were crossing the yard. Ni2's "check the field unlocked, then lock and check again" pattern is this exact idiom: a deliberate, correct race used purely to skip locking overhead in the common case.

Where it breaks: it only stays correct if the field never "unpeeks" (transitions from set back to unset) once other threads can see it, and if the hardware's memory model doesn't reorder the two writes — a subtlety that made the Ni2 authors rewrite the code even after confirming it was technically correct.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals you can read at a glance.

1 · The basic Lockset algorithm

For every shared variable v, Eraser keeps a candidate lock set C(v), initialized to all locks in the program. On every access by thread t:

C(v) := C(v) ∩ locks_held(t)
if C(v) = { }: issue a warning

A lock that genuinely protects v every time stays in C(v) forever, since intersecting with a set that contains it changes nothing. A lock that doesn't consistently protect v eventually gets intersected away. If C(v) empties, no single lock survived every access — proof, not suspicion, that the discipline was violated.

2 · Taming false alarms — the state machine

Applied naively, this simple rule fires constantly on correct code: unlocked initialization, and read-only data shared freely between threads. Eraser fixes both with a four-state machine per variable.

3 · Reader-writer locks

Multiple-reader/single-writer locks need a relaxed rule: a lock held only in read mode by a writer doesn't protect against a race with a genuine reader, so it must be dropped from C(v) whenever a write occurs.

# locks_held(t)       = locks t holds in ANY mode
# write_locks_held(t) = locks t holds in WRITE mode

on read of v by t:   C(v) := C(v) ∩ locks_held(t);        warn if empty
on write of v by t:  C(v) := C(v) ∩ write_locks_held(t);  warn if empty
🌱
Reads intersect against the generous set (read or write mode both count); writes intersect against the strict set. A lock a writer holds only for reading is invisible to the write-side check — exactly the case that would otherwise let a real race slip through.

4 · Implementation — ATOM, shadow memory, lockset indices

Eraser instruments every load/store (to maintain C(v)), every lock/unlock call and thread init/exit (to maintain locks_held(t)), and every allocator call (to reset C(v) for new memory) — all via ATOM binary rewriting, with no source changes required. It treats each 32-bit word as the smallest shared-memory unit and skips stack-pointer-relative addressing, assuming shared data lives in globals or the heap.

Storage is kept small by canonicalizing lock sets: since the paper never observed more than 10,000 distinct lock sets in any run, each is assigned a small integer lockset index into a shared table of sorted lock-address vectors, with intersections cached — so the common case of set intersection becomes a table lookup, not a list-merge. A shadow word alongside each monitored word holds a 30-bit lockset index plus a 2-bit state (Virgin/Exclusive/Shared/Shared-Modified) — 32 bits total, matching the word it describes.

5 · From detection to explanation

When C(v) empties, Eraser reports the file and line, a full stack backtrace, the thread ID, the memory address, the access type, and key registers. Users can also ask Eraser to log every access that changed C(v) for a specific variable — usually enough, combined with source, to locate the actual synchronization mistake.

⚠
Known blind spot: Eraser reasons about lock ownership, so post/wait-style synchronization (semaphores signaling across threads with no owner) confuses it — it can't infer which data a semaphore protects, producing false alarms in interrupt/device-driver-style code, a limitation the authors hit directly when porting toward the SPIN kernel.
Follow the numbers, step by step

Worked examples

Four traces from the paper, carried through completely — refinement by hand, a real benign race, the production-server scale, and the performance cost.

① Refining C(v) by hand (Figure 3)

A program has exactly two locks, mu1 and mu2. Variable v is accessed twice: once by a thread holding mu1, once by a thread holding only mu2. Trace C(v).

  1. Initialize: C(v) = {mu1, mu2} — every lock in the program is a candidate.
  2. Access 1 (thread holds {mu1}): C(v) := {mu1, mu2} ∩ {mu1} = {mu1}.
  3. Access 2 (thread holds {mu2}): C(v) := {mu1} ∩ {mu2} = { }.
  4. C(v) is empty → no single lock protected both accesses. Report a race — correctly, regardless of which access actually happened first in wall-clock time.
🍯
Insight: this is proof by elimination, not observation of a collision — the two accesses never needed to overlap for Eraser to catch the bug.

② A real benign race: Ni2's double-checked field

Ni2's code checks p3ip_fp unlocked; if unset, takes p3ip_lock, re-checks, and sets it. Why did Eraser flag this, and why was the flag technically correct even though the program worked?

  1. Unlocked read: the first if (p3ip_fp == 0) reads the field holding no lock. C(v) := C(v) ∩ { } = { } — Eraser reports a race here.
  2. Why it's still correct in practice: p3ip_fp only ever transitions 0 → non-zero, never back, and the re-check inside the lock prevents double-initialization — so the unlocked read can't observe a "torn" or nonsensical value under the intended semantics.
  3. The subtlety that worried the authors anyway: the Alpha's memory-consistency model permits reordering of memory operations without an intervening synchronization point — so a thread could observe p3ip_fp set before the data it points to is fully initialized.
  4. Resolution: annotated with EraserIgnoreOn/Off() to silence the report, but the programmer simplified the code afterward specifically because Eraser had exposed how fragile the correctness argument actually was.
💡
A "benign" race isn't a false alarm about the discipline — the discipline genuinely was broken. It's a judgment call that breaking it, here, doesn't cause observable harm under the platform's actual memory model.

  2. Vesta: 10 annotations plus one real bug fix (the unlocked fingerprint-validity flag) reduced "several hundred" reports to zero.

④ What the 10–30× slowdown is made of

Applications ran 10 to 30 times slower under Eraser. The paper attributes roughly half of that to one specific cause — what does the arithmetic suggest about fixing it?

  1. The stated cause: "we estimate that half of the slowdown... is due to the overhead of making a procedure call at every load and store instruction."
  2. Take the midpoint, ≈20×, as illustrative: if half of that overhead (≈10× worth) is pure call overhead and the other half (≈10× worth) is the actual lockset bookkeeping, removing the per-access call — e.g. by inlining, as ATOM later supported — leaves roughly the bookkeeping-only cost.
  3. That implies an achievable slowdown closer to the bottom of the range, not the top, without changing the algorithm at all — pure instrumentation-technique improvement.
  4. The paper's own framing: performance wasn't a major design goal, and "many opportunities for optimization" (inlining, static analysis to skip provably-safe accesses) were explicitly left unexplored.
💡
This is a useful lesson independent of race detection: dynamic-analysis overhead is often dominated by how you inject the check (a call per site) rather than what the check computes — the same reason modern kernel sanitizers (KCSAN, KASAN) lean hard on compiler-level inlining rather than runtime calls.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
A program has three locks: mu1, mu2, mu3. Variable v is accessed four times, by threads holding: {mu1,mu2}, {mu2,mu3}, {mu2}, {mu1}. What is C(v) after each access, and is a race reported?
Show answer
Start {mu1,mu2,mu3}. After access 1: ∩{mu1,mu2} = {mu1,mu2}. After access 2: ∩{mu2,mu3} = {mu2}. After access 3: ∩{mu2} = {mu2}. After access 4: ∩{mu1} = { }. A race is reported — mu2 protected the first three accesses, but the fourth held only mu1.Misconception: that "mostly consistent" locking is good enough. One inconsistent access is enough to empty C(v), by design — there is no partial credit.
Problem 2 · medium
Why did Eraser flag Ni2's double-checked p3ip_fp pattern as a race even though the program worked correctly in every observed test run?
Show answer
Eraser checks the locking discipline, not observed behavior: the first read of p3ip_fp genuinely happens with no lock held, so C(v) genuinely empties — that's a true discipline violation, not a bug in Eraser. The code is correct anyway because of program-specific invariants (the field only transitions one way, and the check is repeated under the lock) that Eraser has no way to know about.Misconception: that a flagged race must be a real bug, or that a "benign" race means Eraser made a mistake. Eraser is right about the discipline; benign-ness is a judgment only a human (or deeper memory-model reasoning) can make.
Problem 3 · medium
Explain, using the Virgin/Exclusive/Shared/Shared-Modified state machine, why Eraser can still miss a genuine initialization race.
Show answer
A variable stays in Exclusive (no refinement, no reporting) until a second thread actually accesses it — Eraser has no other way to know initialization is "done." If a thread publishes a pointer to unfinished data before finishing initialization, and the second thread's access happens to occur after the first thread's remaining unlocked writes complete, no violation is ever observed, purely due to scheduling luck.Misconception: that Eraser is entirely immune to scheduler luck. It removes that dependency for the general locking-discipline check, but the initialization heuristic reintroduces a narrow amount of it.
Problem 4 · hard
Construct a two-thread example (à la the paper's Figure 2) where a happens-before-based race detector misses a real, unprotected race — and explain why Eraser catches it regardless.
Show answer
Thread 1: lock(mu); write y; unlock(mu). Thread 2: write y (no lock at all). If, in the observed run, Thread 1's critical section always completes before Thread 2 ever runs, happens-before sees Thread 1's unlock ordered before... nothing conflicting, since Thread 2 never overlaps it in that trace — no violation of any synchronization ordering is observed, so no race is flagged. Eraser instead tracks C(y): Thread 1's write intersects to {mu}; Thread 2's write intersects {mu} with { } (holds nothing) → empty. Eraser reports the race on the very first test run that exercises both code paths, regardless of their relative timing.Misconception: that if two racy accesses never actually overlapped, there's nothing to detect. The bug is in the code paths existing without a consistent lock — not in any particular execution's timing.
Problem 5 · medium
A variable is meant to be protected by a reader-writer lock m. Thread A reads it holding m in read mode. Thread B writes it holding m in write mode. Thread C writes it holding no lock at all. Walk through C(v) and say whether a race is reported.
Show answer
Start C(v) = {m}. Read by A: C(v) := {m} ∩ locks_held(A) = {m} ∩ {m} = {m} (read mode still counts for the read-side check). Write by B: C(v) := {m} ∩ write_locks_held(B) = {m} ∩ {m} = {m}. Write by C: C(v) := {m} ∩ write_locks_held(C) = {m} ∩ { } = { }. Race reported, correctly — C's unprotected write is the actual bug.Misconception: that any access under "some form" of the right lock is always safe. Writes specifically require write-mode ownership; a write under only read-mode access to the correct lock would also empty C(v), and rightly so.
Problem 6 · easy
Why does Eraser treat each 32-bit word as the smallest unit of shared memory, rather than each byte?
Show answer
On the target platform (Alpha), a 32-bit word is the smallest memory-coherent unit the hardware and compiler reason about for ordinary loads/stores — matching granularity to it keeps one shadow word cleanly describing one monitored word, with no sub-word bookkeeping needed.Misconception: that finer granularity is always more precise and therefore better. Finer than the hardware's own coherence unit buys no additional correctness, only extra shadow-memory overhead.
Problem 7 · hard
The paper never observed more than 10,000 distinct lock sets in any run, so it canonicalizes them into a shared table with 30-bit indices. Why not just size the index field to fit 10,000 (14 bits) exactly?
Show answer
30 bits plus a 2-bit state exactly fills one 32-bit shadow word — matching the natural word size of the machine, which is cheap to load/store/align. Tightening the index to 14 bits would save bits in principle but leave an awkward, non-word-aligned shadow layout, complicating (and likely slowing down) every shadow-memory access for a saving that doesn't change the dominant cost (the per-access procedure call).Misconception: that minimizing bit-width is always the right optimization. Matching natural hardware word/alignment boundaries usually matters more than shaving a few unused bits.
Problem 8 · easy
Rerunning the Ni2 and Vesta tests with 2 threads instead of 10 produced the same race reports (in different order). What does this demonstrate about Eraser, and what would happen to a happens-before-based tool under the same experiment?
Show answer
It demonstrates Eraser's central claim: its findings depend on which code paths were exercised, not on the specific thread interleaving or count. A happens-before tool could plausibly report a different set of races with fewer threads, since fewer threads changes which orderings are even possible to observe.Misconception: that more concurrent threads always finds more bugs in dynamic race detection. For a discipline-checking tool, thread count matters far less than which lines of code actually ran.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly counts as a data race, per this paper?▾
Two concurrent threads access a shared variable, at least one access is a write, and nothing in the program prevents the accesses from happening simultaneously. The outcome then depends on unpredictable scheduling — usually a serious bug, occasionally a deliberate, harmless "benign" race.
Q2What is the locking discipline Eraser actually enforces?▾
In its full form: every shared variable v must have some lock m such that m is held in write mode for every write of v, and held in some mode (read or write) for every read of v. Eraser infers m (or proves none exists) from execution history rather than requiring the programmer to declare it.
Q3How can Eraser catch races that never actually occurred during the test run?▾
It doesn't wait to observe two accesses colliding. It checks whether a consistent lock protected every access seen so far. If two code paths independently reach the same variable holding disjoint locks, that's a provable discipline violation — regardless of whether those two paths happened to run at overlapping times in this particular execution.
Q4How does Eraser avoid flagging normal unlocked initialization?▾
Every new variable starts in the Virgin state; its first accesses (by one thread) move it to Exclusive, where reads/writes don't refine C(v) at all. Only once a second thread accesses the variable does refinement (and potential reporting) begin — treating "still exclusive to one thread" as "probably still being initialized."
Q5How does it avoid flagging read-only shared data?▾
A second thread's read moves the variable to the Shared state, where C(v) keeps being refined but violations are not yet reported. Only when some thread performs a write does the variable become Shared-Modified, where an empty C(v) finally triggers a warning — so purely concurrent readers never trip the checker.
Q6How does Eraser handle reader-writer locks?▾
Reads intersect C(v) against every lock the thread holds in any mode; writes intersect against only the locks held in write mode. This correctly drops a lock from C(v) the moment it's shown to be held merely for reading by some writer, since that doesn't protect against a race with an actual reader.
Q7How is Eraser actually implemented?▾
It uses DEC's ATOM binary-rewriting tool to instrument an unmodified Digital Unix/Alpha binary: a call is inserted before every load, store, lock/unlock, and allocator call. A shadow word per monitored 32-bit word stores a 30-bit lockset index (into a shared, canonicalized table of lock vectors) plus a 2-bit state.
Q8Why is it 10–30× slower, and can that be fixed?▾
Roughly half the overhead is attributed to making a separate procedure call at every single load and store; the rest is the actual lockset bookkeeping. The authors explicitly note that inlining the checks (rather than calling out to them) and static analysis to skip provably-safe accesses were unexplored optimizations that could shrink this considerably.
Q9What causes most of Eraser's false alarms, and how are they suppressed?▾
Three categories dominate in practice: memory reuse (private free lists Eraser doesn't know about — fixed with EraserReuse()), private lock implementations Eraser never sees (fixed with EraserRead/WriteLock()), and deliberate benign races (silenced with EraserIgnoreOn/Off()). A handful of each was enough to bring every tested program's report count to zero.
Q10Did Eraser find real bugs, or just theoretical violations?▾
Real bugs in production code: an unprotected boolean guarding a cached fingerprint in Vesta, an unlocked reference count and a missing subroutine lock in AltaVista's Ni2 (both later reintroduced from history and re-found in minutes), an unprotected status read in Petal's server-monitoring thread, and races in roughly 10% of tested undergraduate coursework assignments.

ATOMDigital's binary-code-modification toolkit (Srivastava & Eustace, 1994) used to instrument unmodified program binaries.
Shadow memory / shadow wordPer-word metadata (here: a 30-bit lockset index + 2-bit state) kept at a fixed offset from the real data it describes.
Supporting terms
Lockset indexA small canonical integer identifying one specific set of locks in a shared table — avoids storing full lock lists per variable.
Benign raceA true locking-discipline violation that the programmer has judged harmless for platform- and program-specific reasons.
Read-write lock disciplineReads need any mode of the protecting lock; writes need write mode specifically, since read-mode holders don't guard against readers.
Multiple protecting locksA variant discipline where several locks jointly protect a variable (all needed for writes, any one sufficient for reads) — supported experimentally, at some risk of false negatives.
EraserIgnoreOn / EraserIgnoreOffAnnotation bracketing code where known benign races should not be reported.
EraserReuse(addr, size)Annotation resetting shadow state for privately-recycled memory Eraser's allocator hooks can't see.
EraserRead/WriteLock, EraserRead/WriteUnlockAnnotations informing Eraser about custom lock implementations outside the standard pthreads interface it instruments by default.
Interrupt level as lockThe paper's approach for kernel code: treat raising the interrupt level to n as implicitly acquiring the first n "interrupt locks," to reason about interrupt-based mutual exclusion.
