Shrinking the set of suspect locks until only the guilty one is left

Two threads touch the same variable. Did a lock protect both accesses? Instead of replaying every possible schedule, Eraser just watches which locks were held every single time — and waits for that set to hit empty.

1Threads and shared memory▾

Imagine one program running several "mini-programs" at once inside it, called threads — like several cooks working in the same kitchen at the same time. All the threads in a program can see and use the exact same variables, the same way all the cooks share the same countertop and ingredients. That sharing is what makes this style of programming fast and powerful — and also where bugs sneak in, the same way two cooks grabbing the same bowl at once can cause a mess.

Now you're ready: Eraser exists because two threads touching the same piece of memory, with nothing coordinating them, is exactly where bugs live.
2Locks and mutual exclusion▾

A lock is like a single bathroom key hanging on a hook: at any moment it's either free, or one thread is holding it and everyone else has to wait. Calling lock(mu) means "wait for the key, then take it"; unlock(mu) means "hang the key back up." Only whoever is currently holding the key is allowed to hang it back up — that's the one detail that makes a lock different from some other coordination tools.

Now you're ready: the paper's whole argument is about which key — if any — was consistently required before touching each shared variable.
3What a data race actually is▾

The paper's definition of a data race: two threads touch the same shared variable at around the same time, at least one of those touches is a write, and nothing (no lock) is stopping them from happening at literally the same instant. When that's true, what actually happens is down to luck in the timing — which is a serious bug, even if it doesn't visibly break anything today.

Now you're ready: Eraser's whole job is spotting exactly this pattern in the code's habits — without needing the unlucky timing to actually happen during the one test run you watched.
4The happens-before relation▾

Happens-before is a way of proving a definite before/after order between two threads' actions, using events like locking and unlocking as evidence (e.g., "thread A's unlock happened before thread B's lock of that same key, so A definitely finished first"). Older race-detecting tools only raise an alarm if they can't find any such proof of ordering between two touches of a variable.

Now you're ready: this only catches a race if the one schedule that actually ran during your test happens to expose it — that's Eraser's central complaint about it.
5Hoare's monitor▾

A monitor is an older idea: bundle a group of shared variables together with the only functions allowed to touch them, and automatically lock them as a set whenever any of those functions runs. Because this is set up when the program is written (not while it's running), it breaks down for data that gets created fresh, on the fly, while the program is already running — a monitor can't automatically know to protect something that didn't exist yet.

Now you're ready: Eraser's goal is to get that same kind of safety back, but by watching the running program instead of requiring it to be structured a certain way in advance.
6Binary rewriting (ATOM)▾

Normally, adding monitoring code means editing and recompiling the source code. A binary rewriter skips that: it takes the already-compiled program (the file the computer actually runs) and inserts new tracking instructions directly into it, producing a new version that behaves identically but is now being watched. ATOM is the specific tool, from Digital Equipment Corp., that Eraser is built on.

Now you're ready: this is how Eraser was able to watch every memory access and every lock/unlock inside real production programs, without needing their original source code.
7Shadow memory▾

Shadow memory is a second, hidden region of memory that mirrors the real one — for every real piece of data, there's a matching hidden slot right alongside it, used to store extra bookkeeping (like "which lock(s) have guarded this?") without touching the program's real data at all.

Now you're ready: Eraser gives every shared variable its own small hidden slot, used to store which locks have been seen protecting it.
8Narrowing down a list of suspects▾

Think of it like narrowing down a list of suspects: you start by assuming every lock in the whole program could be the one protecting this variable, and every time the variable gets touched, you cross off any lock that wasn't being held at that moment. The list of remaining "suspects" can only ever get smaller or stay the same — it never grows back.

Now you're ready: this crossing-off process is the entire Lockset algorithm; once the suspect list hits zero, you've proven no single lock protected every touch.
9Reader/writer locks▾

A read-write lock is a smarter kind of key: any number of threads can hold it at once as long as they only want to read the data, but only one thread at a time may hold it to write — and no reader is allowed in while a writer holds it. This lets safe, harmless reading happen in parallel while still preventing writes from colliding with anything.

Now you're ready: Eraser has to tell the difference between "holding the key just to read" and "holding the key to write" — a distinction the simplest version of the algorithm ignores.
10False alarms and testing tools▾

Any tool that only watches a program while it runs (rather than mathematically proving something about the code) can only judge what it actually saw happen. That means it can miss real bugs it never happened to observe, and it can also wrongly flag perfectly fine, just-unusual-looking code as suspicious (a false alarm). A good tool needs some way for the programmer to say "yes, I know, this one's fine on purpose."

Now you're ready: Eraser is upfront that it's a testing tool, not a mathematical guarantee — which is why it comes with a small set of annotations programmers can use to tell it "this pattern is intentional, stop complaining."
The whole story in one place

Eraser in a nutshell

Why happens-before wasn't enough, what Lockset checks instead, and how the pieces fit together.

First, some quick vocabulary. A program can run several threads at once — think of them as several workers inside the same program, all able to read and write the same pieces of memory. Whenever the program runs, the operating system decides, moment to moment, whose turn it is to execute next; that specific ordering of "who ran when" is called the schedule (or interleaving) for that run. Run the exact same program twice and you can get two different schedules, because the OS is juggling lots of other things too. A tool that watches the program while it actually runs (rather than just reading the source code) is called a dynamic tool.

Older dynamic race-detection tools used an idea called happens-before: while the program runs, watch which events (like locking and unlocking) tie two threads' actions into a definite before/after order. If two threads touch the same variable and the tool can't find anything tying those two touches into an order — they look like they could have happened at the same moment — it calls that a race. The catch: this only works for the one schedule that actually happened during that run. If, purely by luck, the OS happened to run things in an order where the two threads' visits looked "in order" this time (even though nothing in the program actually guarantees that order), the tool sees nothing wrong — even though the bug is real and could still hit someone the next time the schedule comes out differently. The paper's Figure 2 shows exactly this: an unguarded variable y is touched by two threads with zero real coordination between them, but because of a coincidence in this particular run, happens-before-based tools miss it entirely.

Eraser's big idea, called the Lockset algorithm, is to stop caring about any one schedule and instead check a rule: has this variable been protected by a lock every single time, consistently? Here's how: for every shared variable v, Eraser keeps a running list, C(v), of "locks that might be the one consistently guarding v." Every time any thread touches v, Eraser looks at which locks that thread is currently holding, and throws out of C(v) any lock that isn't one of them. Over time this list can only shrink. If it ever shrinks all the way down to nothing, that proves no single lock was present at every single touch — meaning the variable was never actually being protected consistently, whether or not the threads happened to collide badly during this particular run.

The plain "shrink the list to nothing" rule is too trigger-happy for real programs — it would wrongly complain about perfectly normal things, like one thread quietly setting up a new variable before anyone else even knows it exists. So the paper adds a small set of exceptions: a per-variable status that starts as "brand new, being set up by one thread" and only starts being checked strictly once a second thread gets involved and someone writes to it (four stages: Virgin → Exclusive → Shared → Shared-Modified) — plus a special case for locks that let many threads read at once but only one thread write. Eraser builds all of this by editing an already-compiled program directly (a technique called binary rewriting, via a tool named ATOM) and by attaching a small hidden tracking record to every shared variable (a shadow word). The cost: the instrumented program runs 10 to 30 times slower — noticeable, but fine for a one-time testing run, not something you'd ship to users.

Did it work? The authors ran Eraser on four multithreaded server programs written at Digital Equipment Corporation's Systems Research Center, without modifying the programs beforehand, then iterated: fix or annotate what was reported, rerun. The paper says Eraser found undesirable race conditions in 3 of the 4; it does not name them, but reading §4 they are mhttpd, the Vesta cache server and Petal (Ni2's reports were false alarms and intentional races). It also found several places where a race was intentional and harmless (a benign race). On about 100 runnable undergraduate operating-systems assignments, 10% of the working ones had data races found by Eraser.

🍯 Key takeaways

  • Lockset checks whether the code has a consistent habit of locking a variable — it doesn't need the bad timing to actually happen during the test to catch the problem.
  • C(v) (the candidate-lock list for variable v) only ever gets smaller; empty means "no single lock was present at every visit to v."
  • Three exceptions had to be built in so it wouldn't cry wolf: unlocked setup by one thread, unlocked read-only sharing, and read/write locks (a lock held only for reading doesn't count as protecting a write).
  • A four-stage status per variable (new → single-owner → shared-for-reading → shared-and-being-written) implements those exceptions and decides when a warning actually fires.
  • Built by editing the already-compiled program directly (binary rewriting, via a tool called ATOM) plus a small hidden tracking record per shared variable — no source-code changes needed.
  • Found real races in 3 of 4 production servers and 10% of student assignments, at the cost of running 10 to 30 times slower during testing.
  • It's a testing tool, not a mathematical proof: it can still raise false alarms (handled with manual annotations), and one specific corner case around initial setup can still depend on lucky timing.
Six everyday pictures

How to think about Eraser

Read in any order. Each one names honestly where the picture stops matching the paper.

The core idea · Lockset refinement

Narrowing a suspect list

A detective starts with every employee as a suspect and, after each new witness account, keeps only names consistent with all testimony. C(v) works the same way: every lock is a suspect protector until an access rules some out. When the list empties, nobody is consistent — meaning no single lock ever guarded every visit.

Where it breaks: a detective can reopen the case with new information; C(v) can only shrink, never grow back — even if the "true" protecting lock briefly got crossed off by pure coincidence (see Problem 5).
Why not happens-before · Schedule dependence

A traffic camera vs. a rule book

Happens-before is a traffic camera: it only "sees" a collision if it happens to be pointed the right way when two cars actually cross. Eraser is a rule book: it checks whether every driver followed the same right-of-way convention every time, and flags the violation whether or not two cars actually met at the intersection this time.

Where it breaks: the rule book can misjudge an intersection with a genuinely unusual (but safe) convention, like a roundabout — that's exactly what "benign races" and reader/writer patterns look like to Lockset.
The exceptions · Four-state machine

A house that's still being furnished

A new house (Virgin) is fine to arrange alone before anyone else has a key (Exclusive). Once you hand out spare keys, guests browsing is fine too (Shared) — no alarm until someone starts rearranging the furniture while others are also using the house (Shared-Modified), which is the only state where Eraser actually raises the alarm.

Where it breaks: a house only "counts" as furnished once, but the paper's proxy for "initialization is done" is just "a second thread touched it" — if that second thread arrives too early, the analogy (and Eraser) can miss the problem entirely.
The implementation · Shadow memory

A hotel key card's magnetic stripe

The physical key doesn't carry your reservation details — a paired database entry does, looked up by the key's ID. Eraser's shadow word is that paired record: every 32-bit shared word gets a same-size shadow word, found by a fixed offset, holding a compact lockset index instead of the full guest history.

Where it breaks: a hotel's database is centralized and easy to reset for a new guest; Eraser's shadow memory has no automatic "new guest" signal for privately recycled memory (custom free lists), which is exactly its top cause of false alarms.
Read vs write locks · Asymmetric protection

A library reading room vs. the archive vault

Any number of patrons may sit and read in the reading room at once — no conflict. But only one archivist at a time may go into the vault to re-shelve, and while they're in there, nobody reads from that shelf. Eraser's read/write refinement mirrors this: a lock held only in read mode never counts toward protecting a write, only toward protecting other reads.

Where it breaks: a library has one vault; real programs sometimes protect one variable with several locks (writers hold all, readers hold one), a pattern the current Eraser does not handle: it reports false alarms, and the experimental fix the paper tried risks letting some real races slip through instead.
Deliberate exceptions · Benign races

A fire alarm everyone can trip

Some warning systems are designed so any of several people can pull the same lever without coordinating — the outcome (alarm sounds) doesn't depend on which person pulled it first. A flag like kill_queries, read and written by many threads with no lock, is exactly this: the race is real, but harmless by design.

Where it breaks: a fire alarm is obviously safe to everyone; whether a race is truly benign is often subtle — the paper's own Ni2 ip_fp case was a deliberately programmed race that the authors confirm is correct as shown, yet they flag that a tempting further unlocked use of the same value later in the same procedure would not be safe — which is why "benign" needs an explicit annotation, not a guess.
The full explanation

How it actually works

From the naive rule to the working system, in the order the paper builds it.

1 · The problem with tools that depend on lucky timing

Tools based on happens-before watch every touch of a variable and only raise an alarm if they can't prove a before/after order between two threads' touches in this one run. The paper's Figure 2 shows exactly how this fails: an unguarded variable y is touched by two threads with no real coordination between them, but purely because Thread 1's lock/unlock of some unrelated shared key happens to finish before Thread 2 even starts, happens-before can "prove" an order existed — even though nothing in the program actually guarantees that order. So the real, timing-independent bug goes unreported. Catching it this way would need a lucky (or exhaustively repeated) test run where the timing came out differently.

⚠
This dependence on lucky timing is the whole reason Lockset exists: check a habit in the code's locking behavior, not a property of one particular run's timing.

2 · The basic Lockset algorithm

The simplest possible rule: every shared variable should be protected by some lock, meaning that same lock is held by whichever thread touches it, every single time. Nobody tells Eraser in advance which lock is supposed to protect which variable — it has to figure that out purely by watching what actually happens as the program runs, narrowing down the "suspect" locks step by step (the "narrowing suspects" idea from the primers).

let locks_held(t) = set of locks held by thread t
for each v: initialize C(v) = ALL LOCKS
on each access to v by thread t:
    C(v) := C(v) ∩ locks_held(t)      # lockset refinement
    if C(v) == {}: issue a warning

If some lock l truly protects v throughout, l survives every intersection and stays in C(v) forever. If no such lock exists, C(v) is guaranteed to hit empty as soon as enough conflicting accesses have been observed.

3 · Handling initial setup and read-sharing

The raw rule above is too strict: it would wrongly flag ordinary unlocked initial setup by one thread, and safe unlocked read-only sharing, as if they were bugs. The fix is to give each variable a status — one of four stages — and only start actually checking and reporting problems once that status shows the variable has moved past simple setup and read-sharing into a state where it actually matters.

4 · Read-write locks

Real programs also use the "many readers, one writer" locks from the primers. The final version of the rule: some lock m must be held in write mode for every write to the variable, and in either mode (read or write) for every read. So a read gets checked against every lock the thread is holding, but a write only gets checked against locks held specifically in write mode — a lock held just for reading doesn't count toward protecting a write:

on each read of v by thread t:
    C(v) := C(v) ∩ locks_held(t)
    if C(v) == {}: warn
on each write of v by thread t:
    C(v) := C(v) ∩ write_locks_held(t)   # read-mode locks don't protect writes
    if C(v) == {}: warn

5 · Implementation — binary rewriting and shadow memory

Eraser is built on ATOM (the already-compiled-program editor from the primers), which inserts a call to Eraser's runtime at every memory read and write (except loads and stores addressed off the stack pointer, which are assumed to be private stack accesses) and at every lock, unlock, thread initialization/finalization stub, and memory-allocation call in the already-compiled program; no source code needed. Every chunk of shared memory gets a paired hidden shadow word sitting at a fixed, predictable distance away from it, storing a number that identifies its current lockset (the lockset index) plus a small code for which of the four stages (Virgin/Exclusive/Shared/Shared-Modified) it's in; while a variable is still in the single-owner Exclusive stage, that same space instead just stores the ID of the one thread that owns it.

How that index actually gets set, step by step, on one access (thread t touching v): Eraser already has locks_held(t): it keeps this per thread, updating it at every instrumented acquire and release (the paper says acquisitions and releases, like intersections, create lockset indexes). Thread IDs enter in two places only: choosing whose locks_held to use, and the owner ID stored in the shadow word while the location is Exclusive. Next it reads v's shadow word, takes the index stored there, and follows it into the global table to get the actual lock combination that index currently names — that's C(v). It intersects: new_set = C(v) ∩ locks_held(t). The fast case is a lookup in a cache of earlier intersection results; only on a miss does Eraser compare the two sorted lock vectors. Then it looks new_set up in that same global table — keyed by the lock combination's actual contents (e.g. "does an entry for exactly {mu1} already exist?"), never by thread ID and never by which variable is asking. If a matching entry already exists, Eraser reuses its index; if not, it allocates the next free slot, stores the new combination there, and uses that new index. Either way, the resulting index gets written back into v's shadow word, replacing the old one.

The table itself is one single table, shared by the entire program — not one per variable and not one per shadow word. Because it's keyed by lock-set contents rather than by variable, two completely unrelated variables that both happen to always be touched under just {mu1} end up pointing at the exact same table entry. That sharing is the point: it's what keeps the table small (the paper never saw more than 10,000 entries in any run) no matter how many variables, threads, or locks the program has — the table only grows with the number of distinct combinations of locks anyone was ever holding, which stays small in practice even when the thread and variable counts are large. The 30 bits are just headroom on how many such entries could ever exist (over a billion slots) — they're not a hash of the locks and they don't grow with the lock count.

6 · Performance

Checking every single memory read and write isn't free: programs typically run 10 to 30 times slower under Eraser. About half of that slowdown, the authors estimate, comes from the overhead of jumping out to a separate piece of tracking code every single time — pasting that tracking code directly inline instead (rather than jumping to it each time) was identified as the main way to speed this up, but the authors left actually building that for future work.

💡
10–30× sounds large, but it's a testing-time cost paid once per debugging run, not a production cost — and the paper found it didn't materially change which races got reported (see the 2-thread vs. 10-thread sensitivity experiment in Worked Examples).

7 · Annotations for false alarms

Three recurring patterns caused false alarms: privately recycled memory (custom free lists Eraser can't see), private lock implementations Eraser wasn't told about, and genuinely intentional benign races. Each got a matching annotation:

EraserIgnoreOn()  / EraserIgnoreOff()        # suppress reports in this bracketed region — benign races
EraserReuse(address, size)                    # reset shadow memory to Virgin — private free lists
EraserReadLock(lock)  / EraserReadUnlock(lock)  # declare a private lock's acquire/release
EraserWriteLock(lock) / EraserWriteUnlock(lock) # in read or write mode (custom rwlocks)

A handful of these annotations per program was consistently enough to take race reports from the hundreds down to zero in three of the four production servers — Petal had one false alarm, caused by stack-frame reuse, that the authors could not annotate away (see Worked Examples).

8 · Beyond user-level locks — the SPIN kernel

Trying to use Eraser inside the SPIN operating-system kernel surfaced two coordination tricks that don't look like ordinary locks at all. Kernels often protect data simply by temporarily blocking certain interrupts (signals from hardware) rather than using a lock — this is called an interrupt level, and raising it to a higher level automatically also blocks everything a lower level would have blocked, working much like holding several nested locks at once. Eraser was extended to treat each interrupt level as if it were its own lock, so raising to level n counts as grabbing the first n of these implicit locks together. (The SPIN port did not yet work, because SPIN's runtime code generation and late binding complicated instrumentation, so the paper reports no races found there.) Trickier still are post/wait semaphores — a signal a driver sends to wake up a thread that's waiting for something. Unlike a lock, nobody "owns" a semaphore the way a thread owns a lock, so Eraser has no way to figure out which piece of data the signal is actually meant to protect, and it produces false alarms around this pattern.

M1 · What a data race is, and what Eraser actually checks

The paper's definitions. A lock is either available or owned by one thread; the operations are lock(mu) and unlock(mu), and only the owner may release it. That ownership rule is what separates a lock from a binary semaphore, and it matters later: Eraser can attribute a held lock to a thread, but it cannot attribute a semaphore to anyone (M15). A data race occurs when two concurrent threads access a shared variable, at least one access is a write, and the threads use no explicit mechanism to prevent the accesses from being simultaneous. (Paper §1.1)

What Eraser checks instead of races. Eraser never looks for two accesses that actually overlapped. It checks a locking discipline, "a programming policy that ensures the absence of data races". The first version is: every shared variable is protected by some lock, meaning that lock is held by any thread whenever it accesses the variable. The final version (M7) is: for each variable v some lock m is held in write mode for every write of v and in some mode for every read of v.

The logical relationship. Obeying the discipline implies no data race on v: if every access holds m, no two accesses can be simultaneous. The converse is false: a program can be race-free through some other mechanism (a thread handing an object to another, a semaphore, a join) while violating the discipline. So a discipline violation means "a race is possible unless something Eraser cannot see orders these accesses", and that gap is the source of every false alarm in the paper. The paper's own phrasing for the case studies is that experienced programmers "tend to obey the simple locking discipline" (§4), which is the empirical bet the tool rests on.

Scope. Eraser targets lock-based programs. It handles mutexes and reader-writer locks; it does not model semaphores, condition-variable signalling, message passing or thread creation/join as synchronization. It also only reasons about individual memory words, so a bug where every access holds the right lock but two critical sections should have been one (an atomicity bug) is not a data race by this definition and is out of scope. (The name is unrelated to Mellor-Crummey's earlier Eraser tool for parallel Fortran; the paper says so in §1.)

🎓
From the lecture. The professor started from "what is a race condition?" and separated the broad notion (the result depends on timing, for example a check-then-use window in a package manager that let AI agents escape a sandbox) from the paper's narrow data-race definition. He then asked whether int foo; ... foo++; run on many threads is a race: foo++ is a read and a write, so yes if foo is shared; on x86 it can compile to one memory-increment instruction, but that instruction is not atomic without the lock prefix, so the source alone does not tell you. His VMware example: an unlocked foo++ used as an approximate event counter, because a lock would make it far more expensive and an occasional lost increment did not matter. Eraser would report it, because it is a real discipline violation even if the programmer considers it harmless; the paper's annotation for this case is EraserIgnoreOn/Off (M13).

M2 · Happens-before, and why the paper rejects it

The relation. Lamport's happens-before is a partial order on all events of all threads in one execution. Events in one thread are ordered in program order. Across threads, an access to a synchronization object is ordered before the next access to the same object by a different thread if the object's semantics forbid swapping them; for a lock, an unlock(mu) happens before the next lock(mu) by another thread, because the lock cannot be acquired until its owner releases it. The relation is transitive. Figure 1 of the paper shows this for two threads each running lock(mu); v := v+1; unlock(mu): all six statements end up in one chain. (Paper §1.2, Fig. 1)

How a happens-before detector decides. It monitors every data reference and every synchronization operation, and reports two conflicting accesses (same location, different threads, at least one write) that are not ordered by happens-before in the execution it watched. The logic is that if they are unordered, a different execution with different thread speeds could have run them simultaneously.

The two drawbacks the paper names. (1) Cost: such tools need per-thread information about concurrent accesses to each shared location. (2) More importantly, effectiveness depends on the interleaving the scheduler happened to produce. Synchronization that is unrelated to a variable can still create happens-before edges that order its accesses in one run.

Lock covers. Dinning and Schonberg's "lock covers" improved happens-before for lock-heavy programs. The paper describes its own approach as extending that improvement and discarding the happens-before machinery underneath it. (§1.2)

What Eraser gives up by dropping happens-before (this guide's reading). Happens-before understands every synchronization primitive whose ordering semantics it models, including fork, join, semaphores and message hand-offs. Lockset understands only locks, so correct code that is ordered by those other primitives looks unprotected. That is the trade: Eraser is less dependent on the schedule but more dependent on the program using locks. The paper argues the trade is right "for many programs" written in the lock-based style.

Static alternatives the paper sets aside. Hoare's monitors give a compile-time guarantee but, the paper says, do not cover dynamically allocated shared data (see M19 for what Mesa actually provided). Purely static race checkers (Sun's lock_lint, the Extended Static Checker for Modula-3) "seem problematical, since they require statically reasoning about the program's semantics". Eraser's stated goal is to allow dynamically allocated shared data "while retaining as much of the safety of monitors as possible". (§1.2)

M3 · The basic Lockset algorithm and the C(v) invariant

Eraser does not know which lock is meant to protect which variable, so it infers the protection relation from the execution. For each shared variable v it keeps C(v), the set of candidate locks. The paper's definition: "a lock l is in C(v) if, in the computation up to that point, every thread that has accessed v was holding l at the moment of the access."

# Paper §2, first version
let locks_held(t) = set of locks held by thread t
for each v: C(v) := set of all locks
on each access to v by thread t:
    C(v) := C(v) ∩ locks_held(t)          # lockset refinement
    if C(v) = { }: issue a warning

Invariant. After any sequence of accesses, C(v) is exactly the intersection of the lock sets held at those accesses. A lock that consistently protects v therefore never leaves C(v), and C(v) becomes empty exactly when no single lock was held at all of them. C(v) only shrinks; nothing in the algorithm adds a lock back, which is why a reset has to come from outside (allocation, or the EraserReuse annotation).

Why this is schedule-insensitive. Intersection is commutative and associative, so the final C(v) depends only on which accesses happened and which locks were held at each, not on their order. Any test that executes two code paths that touch v under disjoint lock sets drives C(v) to empty, whatever the interleaving. This is the precise sense in which Lockset beats happens-before in Figure 2. Note that this property belongs to the basic algorithm: the state machine in M4 makes some accesses count or not count depending on order, and that is where schedule dependence comes back (M6).

Reading Figure 3. The figure has three columns: the program (one thread's statements, top to bottom), locks_held after each statement, and C(v) after each access. With two locks in the program, C(v) starts as {mu1, mu2}. lock(mu1); v := v+1 refines it to {mu1}. After unlock(mu1); lock(mu2); v := v+1 the refinement is {mu1} ∩ {mu2} = { }, and the empty set is the warning. Note that the figure is a single statement sequence; the paper's point is that v is "sometimes protected by mu1 and sometimes by lock mu2", which the plain algorithm flags regardless of how many threads executed those statements. (Paper §2, Fig. 3)

What the warning does and does not say. An empty C(v) says that the observed accesses share no common lock. It does not say two accesses overlapped, and it does not identify the other access involved: the report points at the access where the set became empty (M11).

M4 · The state machine, transition by transition

Why plain Lockset is too strict. The paper names three race-free practices that violate the simple discipline (§2.1): initialization (shared variables are often initialized without a lock, because no other thread can see them yet), read-shared data (written during initialization only, read-only afterward, safe without locks), and read-write locks (multiple readers, single writer). The first two are handled by a per-location state machine; the third by changing the refinement rule (M7).

The two design decisions. First, "delay the refinement of a location's candidate set until after it has been initialized". There is no easy way to know when initialization is complete, so Eraser uses a proxy: a variable is considered initialized "when it is first accessed by a second thread". Second, "report races only after an initialized variable has become write-shared by more than one thread", so read-only sharing never produces a report.

M6 · What the two relaxations cost

The initialization window. The paper states the cost directly: "Our support for initialization makes Eraser's checking more dependent on the scheduler than we would like." Suppose a thread allocates and initializes a shared object without a lock and "erroneously makes the variable accessible to a second thread before it has completed the initialization". Eraser detects the error "if any of the second thread's accesses occur before the first thread's final initialization actions, but otherwise Eraser will miss the error." The authors add: "We do not think this has been a problem, but we have no way of knowing for sure." (§2.2)

General rule for what the Exclusive window hides (this guide's reading). Every access by the owner before the first access by any other thread is dropped. That is harmless exactly when those accesses really are private, which is the programmer convention the heuristic assumes. It is harmful whenever the object becomes reachable by another thread earlier than the owner's last unlocked access. The same rule also means that the owner's lock behaviour during that window never shows up in C(v): C(v) starts from whatever the first other thread holds.

What the Shared state hides. Read-sharing never reports, so a location that is written only while Exclusive and afterwards only read by many threads without locks is never reported, which is the intended behaviour. The cost is only that a report waits for the next write; because Shared keeps refining C(v), an unlocked read in Shared is not lost.

M7 · Read-write locks

The final discipline. "For each variable v, some lock m protects v, meaning m is held in write mode for every write of v, and m is held in some mode (read or write) for every read of v." Eraser keeps two per-thread sets: locks_held(t), locks held in any mode, and write_locks_held(t), locks held in write mode. The state transitions of Figure 4 are unchanged; once the location is in Shared-Modified the refinement depends on the access type. (§2.3)

# Paper §2.3 (read-branch typo ":=" corrected to "=")
on each read of v by thread t:
    C(v) := C(v) ∩ locks_held(t)           # read or write mode both count
    if C(v) = { }: issue a warning
on each write of v by thread t:
    C(v) := C(v) ∩ write_locks_held(t)     # read-mode locks are dropped
    if C(v) = { }: issue a warning

Why a write drops read-mode locks. In the paper's words, locks held purely in read mode by a writer "do not protect against a data race between the writer and some other reader thread". A read-mode hold admits other read-mode holders simultaneously, so a writer holding m only in read mode can run alongside a reader holding m in read mode. Removing m from C(v) at that write is what makes the empty set appear.

Invariant after this change (inference). For the accesses Eraser counts, m ∈ C(v) exactly when every counted write held m in write mode and every counted read held m in any mode. That is the discipline above, restricted to the accesses made after the location left Exclusive.

Private reader-writer locks. Eraser instruments the standard pthreads interface. Several servers had home-grown multiple-reader/single-writer locks, which Eraser could not see; that was the "Private Locks" false-alarm category, fixed with the EraserReadLock, EraserReadUnlock, EraserWriteLock, EraserWriteUnlock annotations (M13).

M9 · ATOM, word granularity, and the stack exemption

Binary rewriting. Eraser is implemented for Digital Unix on the Alpha using ATOM (Srivastava and Eustace, 1994). It "takes an unmodified program binary as input and adds instrumentation to produce a new binary that is functionally identical, but includes calls to the Eraser runtime". No source changes or recompilation are needed. The flip side (inference, consistent with §3.4): only code present in the binary at rewrite time is instrumented, which is why SPIN's runtime code generation and late code binding complicated the port.

Granularity. "Eraser treats each 32-bit word in the heap or global data as a possible shared variable, since on our platform a 32-bit word is the smallest memory-coherent unit." Consequences (inference): two distinct variables packed into one 32-bit word share one shadow word, so if they are protected by different locks their accesses intersect to the empty set and look like a race; a variable wider than 32 bits is checked as independent words.

The stack exemption. "Eraser does not instrument loads and stores whose address mode is indirect off the stack pointer, since these are assumed to be stack references, and shared variables are assumed to be in global locations or in the heap." Two details matter. (1) The decision is made per instruction at rewrite time from the addressing mode, not per address at run time. (2) Stack locations accessed through any other register do get candidate sets, "an artifact of the implementation rather than a deliberate plan to support programs that share stack locations between threads". So a stack variable whose address is passed to another thread is unchecked when the owner touches it via SP and checked when anyone touches it via a pointer.

Shadow state on the stack is never reset per frame. Petal's GmapCh_Write2() forked threads, passed each a pointer into its own stack frame, and used a join-like construct to keep the frame alive. That was correct. But "Eraser does not reinitialize the shadow memory for each new stack frame; consequently the reuse of the stack memory for different instances of the stack frame resulted in a false alarm", the one false alarm the authors could not annotate away. In other words, stack memory reused by a later frame keeps whatever state an earlier frame's non-SP accesses left in its shadow words. (§4.3)

🎓
From the lecture. "Why did they special case index off register R30?" R30 is the Alpha stack pointer; each thread has its own stack, so they assumed no thread touches another's stack. The professor explained the payoff: in a typical program most memory references are to local variables, so instrumenting them would have made the 10 to 30 times slowdown far worse. The price: nothing in the architecture stops a procedure from allocating memory in its frame and handing it to child threads, which is legal as long as the procedure does not return first. He said he has written code like that himself, because stack allocation is a single instruction and frees itself on return, and that such code breaks the scheme; the authors were fortunate their test programs did not do it.
🔗
Connection: Adams and Agesen (hardware vs software virtualization). ATOM rewrites a binary once, before it runs. VMware's software VMM translates guest code dynamically, as it is about to execute, and caches the translations. The professor drew this contrast in class: a tool that rewrites object files cannot see code produced at run time (JIT-compiled Java or JavaScript, interpreters), so modern instrumentation tools rewrite code dynamically, a basic block at a time, which handles arbitrary programs. Eraser's own §3.4 hits the static limitation on SPIN's runtime-generated code.

M10 · Shadow memory, the lockset table, and cached intersections

The problem. A naive implementation would store a list of candidate locks for each memory word, "potentially consuming many times the allocated memory of the program". Eraser avoids this by exploiting "the fortunate fact that the number of distinct sets of locks observed in practice is quite small": the authors never observed more than 10,000 distinct lock sets in any execution. (§3.1)

The data structures, field by field.

  • Shadow word. For every 32-bit word in the data segment and heap there is one 32-bit shadow word holding a 2-bit state (four states, exactly two bits) and 30 more bits. In Exclusive those 30 bits store "the ID of the thread with exclusive access"; otherwise they store a lockset index. Eraser finds the shadow word "by adding a fixed displacement to the location's address". The standard allocation routines are instrumented "to allocate and initialize a shadow word for each word allocated by the program".
  • Lockset index table. Each distinct set of locks is represented by a small integer that indexes a table "whose entries canonically represent the set of locks as sorted vectors of lock addresses". Entries "are never deallocated or modified, so each lockset index remains valid for the lifetime of the program".
  • Hash table of complete lock vectors. Searched before a new index is created, so that each index represents a unique set. New indexes arise from three operations only: lock acquisitions, lock releases, and intersections.
  • Intersection cache. "Eraser also caches the result of each intersection, so that the fast case for set intersection is simply a table lookup." On a miss, the slow case compares the two sorted vectors.
  • Per-thread lock sets. locks_held(t) and write_locks_held(t). Because acquisitions and releases create lockset indexes, these are naturally held as indexes too (inference), which is what makes the intersection cache keyable by a pair of integers.

Invariants these choices buy. (1) Canonical form: one set, one index, so set equality is integer equality and a cache keyed by (index, index) is sound. (2) Immutability: since table entries never change or disappear, an index stored in any shadow word never dangles and a cached intersection never goes stale, so neither needs invalidation. (3) Sorted vectors make the slow intersection a linear merge of two vectors and give every set one byte-exact representation to hash.

The per-access handler, assembled. The paper describes the pieces separately; the sketch below puts them in one place. The structure is this guide's reading; lines marked inference are not stated in the paper.

"Set of all locks" is never stored (inference). C(v) is conceptually initialized to all locks, but a location only gets a lockset index when it leaves Exclusive, and all-locks ∩ held = held, so the first index is just the accessing thread's own lock-set index. No table entry for "all locks" is needed.

How big can the table get? The measured counts are small: about 250 lock sets for mhttpd, about 3,600 for Ni2, 70 for Vesta, never more than 10,000. The theoretical bound is not small: with L locks there are 2L possible sets, and the closure of the observed sets under intersection is what fills the table. The design bets on programs holding locks in a few recurring combinations. With 30 bits the index space holds about a billion entries, so the bound that matters in practice is the memory for the table, its hash table and the cache, not the index width.

Memory cost. The shadow region is the same size as the data segment plus heap, so checked data costs twice its normal footprint, plus the lockset structures. The stack is not shadowed (inference: the paper says SP-relative accesses are skipped and shadow words exist for the data segment and heap; it does not describe how the non-SP stack accesses of M9 find their shadow words).

M11 · What a race report contains

When a race is reported, Eraser gives the file and line number where it was discovered, a backtrace of all active stack frames, the thread ID, the memory address, the type of access, and register values such as the program counter and stack pointer. The authors found this "usually sufficient to locate the origin of the race" when read with the source. If not, the user can direct Eraser to log every access to a particular variable that changes its candidate lock set. (§3)

Why the log option exists (this guide's reading). The report describes the access at which C(v) became empty, not the earlier access that removed the protecting lock. The log of C(v)-changing accesses recovers that history: it shows which access first dropped each lock.

M12 · Performance

"Performance was not a major goal." Applications typically slow down by a factor of 10 to 30. The authors estimate that half of the slowdown is the overhead of making a procedure call at every load and store, which "could be eliminated by using a version of ATOM that can inline monitoring code" (citing Scales et al., Shasta, 1996). Static analysis could also remove monitoring code, but they did not explore it. Their criterion: Eraser is "fast enough to debug most programs". (§3.2)

Time dilation. The slowdown "can change the order in which threads are scheduled and can affect the behavior of time-sensitive applications". The authors' experience was that scheduling differences had little effect on results, and they admit less experience with very time-sensitive programs. Connect this to M6 (inference): the only part of Eraser whose verdict depends on order is the state machine's Exclusive window and the Shared/Shared-Modified boundary, so dilation can matter exactly there.

🎓
From the lecture. Asked whether the overhead comes from doubling memory, the professor said the first-order cost is instructions: every non-stack load and store gets a procedure call that runs tens to hundreds of instructions, which easily produces a 10 to 30 times slowdown. The extra memory probably slowed things somewhat, assuming it all fit in physical memory. He noted that modern checkers are much cheaper partly because they are smarter about what to instrument, for example only the parts that are actually shared.

M15 · The kernel: interrupt levels and semaphores

The authors began porting Eraser to the SPIN kernel. Runtime code generation and late code binding complicated instrumentation and "Eraser does not yet work in this environment", so there are no results, only lessons about how kernel synchronization differs. (§3.4)

Interrupt levels. Kernels raise the processor interrupt level to protect data shared with device drivers and interrupt-level code: level := SetInterruptLevel(n); ... RestoreInterruptLevel(level). Raising the level to n means only interrupts of priority greater than n are serviced until it is lowered. Unlike a lock, "a particular interrupt level inclusively protects all data protected by lower interrupt levels". Eraser's model: one lock per interrupt level, and setting the level to n is treated "as if the first n interrupt locks had all been acquired". The authors expected this to catch races between code using locks and code using interrupt levels.

The invariant any interrupt-as-lock mapping has to satisfy (this guide's reading). Lockset reasoning is right only if, for every pair of code regions that touch v, the regions share a "held" lock exactly when they cannot run at the same time. So to check any proposed mapping, list the code regions that touch shared data (thread code at various levels, handlers at various levels), write down which locks each is treated as holding, and check pairwise that a common lock appears exactly when the hardware really prevents overlap.

Post/wait semaphores. Kernels use semaphores to synchronize a thread with a device driver: the driver does minimal processing and does a V to wake a thread waiting in P, for example on I/O completion. If the driver and thread share data, Eraser raises false alarms, "Because semaphores are not 'owned'" and Eraser cannot infer what data they protect. The paper suggests systems that integrate thread and interrupt processing (Kleiman and Eykholt, "Interrupts as threads") may have less trouble.

🔗
Connection: Livelock (Mogul and Ramakrishnan). The livelock paper's kernel synchronizes interrupt handlers and kernel code by enabling and disabling device interrupts, and its fix moves packet processing out of interrupt handlers into a polling kernel thread with quotas. In Eraser's terms (inference), work done in a thread that takes ordinary locks is the case Eraser models directly, while interrupt-level exclusion needs the extra interrupt-lock mapping above; the paper's own pointer to "interrupts as threads" makes the same observation for semaphores.

M16 · The case studies, bug by bug

Method. The authors first calibrated Eraser on small programs with deliberate errors (forgot to lock, used the wrong lock) and their corrected versions; while writing these they accidentally introduced a race, which Eraser caught. They then ran it on servers written by experienced researchers at DEC SRC (the AltaVista HTTP server and indexing engine, the Vesta cache server, the Petal distributed disk) and on University of Washington undergraduate homework. Ni2: the deliberate race on ip_fp

if (p->ip_fp == (NI2_XFILE *) 0) {        // has file pointer been set?  (no lock)

The unlocked first test races with threads that set the field under ip_lock. It was "deliberately programmed as an optimization to avoid locking overhead in the common case". The paper's correctness argument has two parts: the field never goes from nonzero back to zero while multiple threads can see it, and the test is repeated under the lock so two threads that both see zero cannot both initialize it. The trap the paper points out: using p->ip_fp in the rest of the procedure (the ellipsis) "would be a mistake, because the Alpha's memory consistency model permits processors to see memory operations out of order if there is no intervening synchronization". A thread that saw a nonzero pointer without taking the lock has no guarantee of seeing the writes that initialized what it points to. After Eraser flagged it, the programmer rewrote the code so its correctness argument was simpler.

Eraser's view (inference). The field is written under ip_lock and read once without any lock, so after sharing, C(ip_fp) = {ip_lock} ∩ { } = { } at the first unlocked read in Shared-Modified. Lockset cannot tell a carefully argued benign race from a bug; that judgment is the programmer's, recorded with EraserIgnoreOn/Off.

These were bracketed with EraserIgnoreOn/Off. mhttpd omitted locks when periodically updating configuration data and statistics; the paper calls these real synchronization errors whose effect is minor, "which is perhaps why they were undetected for so long". Vesta: the validFP race

Combine::XorFPTag::FPVal() {

Computing a fingerprint is expensive, so each cache entry keeps a boolean validFP and computes fp lazily. The boolean was accessed without a protecting lock. This was the one bug fix among Vesta's changes. (§4.2)

🎓
From the lecture. The professor put this code on a slide ("What does this mean?"). The Alpha was designed at DEC by Dick Sites as a new 64-bit RISC architecture after the VAX, and it deliberately promised very little about memory ordering so that multiprocessors would be easy to build: reading one variable tells you nothing about another. His point: code like this may well have run correctly on every Alpha implementation that existed, and still be wrong, because it violates what the architecture specification allows. Connection: Mesa. Vesta: the CacheS log and the Flush routines

CacheS keeps a free list of log entries. The authors first put EraserReuse where entries were allocated off the free list, but calls that flush the log still produced reports. The head of each log was protected by a lock, the individual entries were not. Each Flush routine locks the head, copies it into a stack variable, sets the head to 0, releases the lock, and then walks the entries with no lock held, eventually putting them on the free list. This is correct because other threads touch entries only with the head lock held and keep no pointers into the log, so detaching the list "effectively makes the data private to the thread in which Flush was called". Moving the EraserReuse annotations into the three Flush routines removed the reports. (§4.2)

Petal

Petal is a distributed storage system that presents clients with a huge virtual disk built from a cluster of servers and disks, with distributed consensus and failure detection and recovery. Eraser found: false alarms from a private reader-writer lock implementation, suppressed with annotations; a real race in GMapCh_CheckServerThread(), run by a single thread to check periodically that neighbouring servers are up, which reads gmap->state without holding the gmapState lock that all other threads hold before writing it; two intentional races on global statistics, based on the premises that locking is expensive and statistics need only be approximately right; and the unannotatable stack false alarm in GmapCh_Write2() described in M9. (§4.3)

Why a single-threaded reader still races (inference). One thread does the reading, but other threads write the field. The discipline is per variable, not per thread: the unlocked read and a locked write by another thread share no lock, so C(v) empties once the location is Shared-Modified.

Undergraduate coursework

Two University of Washington colleagues (S. E. Choi and E. C. M17 · Effectiveness and sensitivity experiments

Reintroduced bugs. From Ni2's history the authors reintroduced two races that had existed for several months before the program's author found and fixed them by hand: an unlocked access to a reference count used to garbage-collect file data structures, and a missing additional lock needed to protect a subroutine's data structures, called in the middle of a large procedure. Using Eraser, one author located both in several minutes without being told where they were or how they were caused, and it took 30 minutes to correct both and verify there were no further reports.

Sensitivity to interleaving. They reran the Ni2 and Vesta experiments with 2 concurrent threads instead of 10, reasoning that if Eraser were sensitive to thread interleaving the set of reports should change. They found "the same race reports (albeit sometimes in different order) across multiple runs using either two threads or 10." (§4.5)

What these experiments do and do not show (this guide's reading). The first shows Eraser finds known races faster than manual debugging did, on two races chosen from history. The second shows the report set was stable across thread counts for these two programs and tests; it does not measure false negatives, and it cannot, since a missed race produces no report to compare. There is no head-to-head comparison against a happens-before detector and no count of how many reports were false alarms versus bugs; the paper gives only before and after totals.

🎓
From the lecture. "How good a job did they do convincing you?" Students praised testing on mature code by expert engineers and the iterate-annotate-rerun loop, and criticized: no ratio of false positives to real bugs, no comparison to happens-before tools, unquantified annotation effort, and a 10 to 30 times slowdown that is hard to accept for long-running programs. M18 · §5: multiple protecting locks, and deadlock

Multiple protecting locks. Some programs protect a variable with several locks: every writer must hold all of them, every reader at least one. That still forbids every simultaneous pair except two reads, so it is race-free. Its purpose is less concurrency than avoiding deadlock in programs with upcalls. Under Lockset, two readers holding different protecting locks intersect to the empty set, so an earlier Modula-3 version of Eraser gave false alarms on Trestle programs that used this technique. As an experiment the authors refined C(v) only on writes and only checked it on reads:

# Paper §5, experimental variant (as printed)
on each read of v by thread t:
    if C(v) = { }: issue a warning             # no refinement on reads
on each write of v by thread t:
    C(v) := C(v) ∩ locks_held(t)
    if C(v) = { }: issue a warning

This removed the false alarms but can cause false negatives. The paper's example: thread t1 reads v holding m1, thread t2 writes v holding m2; "the violation of the locking discipline will be reported only if the write precedes the read". In general the variant works well only if tests make enough reads follow the corresponding writes.

A detail worth checking (this guide's reading). With the pseudo-code exactly as printed, a read only tests whether C(v) is already empty, so in the example the write leaves C(v) = {m2} and a later read by t1 holding m1 tests a non-empty set and does not warn either. The paper's example works only if the read check is "does the reader hold at least one lock in C(v)", that is, warn if C(v) ∩ locks_held(t) = { } without storing the result, which matches the stated rule that a reader must hold at least one protecting lock. Under that reading: write first gives C(v) = {m2}, and the later read with {m1} warns; read first refines nothing and tests all-locks ∩ {m1}, which is non-empty, and the later write leaves {m2}, so nothing is reported.

Why the current Eraser does not do this. Handling multiple protecting locks with no false negatives would need sets of sets of locks, whose complexity seemed out of proportion to the gain. Since the authors are "uncomfortable with false negatives" and the technique is uncommon, the current version ignores it and produces false alarms for programs that use it. Note the stated preference: given a choice, they accept false alarms over missed races.

Deadlock. "If the data race is Scylla, the deadlock is Charybdis." A simple discipline avoids deadlock: choose a partial order on locks and have every thread that holds more than one lock acquire them in ascending order. Like the locking discipline, it suits dynamic monitoring, and a test that breaches the discipline is easier to produce than one that actually deadlocks. In a stand-alone experiment on formsedit, a Trestle double-view user interface editor known for complicated synchronization, they logged all lock acquisitions and checked whether some order was respected by every thread. A few seconds into startup the monitor found a cycle, so no partial order existed, and examining the cycle revealed a potential deadlock. This was not built into Eraser. (§5)

Conclusion of the paper. Hardware designers learned to design for testability and thread programmers must too; correctness should be demonstrable, "ideally by static checking, realistically by a combination of partial static checking followed by disciplined dynamic testing". The authors argue dynamic race detection should be standard in testing multithreaded programs. (§6)

Follow the numbers, step by step

Worked examples

Four traces using the paper's own figures — from a hand-computed lockset to the actual server-testing statistics.

① Tracing C(v) by hand across three accesses

The paper's own scenario: locks mu1, mu2 exist. Thread A accesses v holding {mu1}. Later, Thread B accesses v holding only {mu2}. What happens to C(v)?

  1. v is allocated: C(v) starts as the universal set, {mu1, mu2, …} — every lock is still a suspect protector.
  2. Thread A accesses v holding {mu1}: C(v) := C(v) ∩ {mu1} = {mu1}. So far, mu1 is consistent with everything observed.
  3. Thread B accesses v holding {mu2}: C(v) := {mu1} ∩ {mu2} = { }.
  4. C(v) is now empty → Eraser issues a warning: no lock has protected every access to v.
🍯
Insight: this is the entire algorithm. No replaying the run, no dependence on lucky timing — just two accesses under different locks are enough to prove the habit was broken. (Paper §2, Fig. 3)

Same trace, but through the actual table (matching the indices in the shadow-memory figure above; this illustrates the plain algorithm of §2, and the paper does not say how "all locks" is represented, so treat index 0 as illustrative. With the state machine, a location gets its first index only when it leaves Exclusive, and that index is simply the accessing thread's lock set): step 1, v starts with every lock as a candidate; say the table already has 0 → {mu1, mu2}, so v's index is set to 0. Step 2, Thread A accesses holding {mu1}: Eraser computes {mu1,mu2} ∩ {mu1} = {mu1}, looks up {mu1} by content in the table, finds it's already there as 1 → {mu1} (maybe some earlier variable put it there), and just rewrites v's index from 0 to 1 — no new table entry needed. Step 3, Thread B accesses holding {mu2}: Eraser computes {mu1} ∩ {mu2} = {}, looks up the empty set by content, finds 2 → {} already exists (it's a common one — lots of unprotected variables end up there), and rewrites v's index to 2. Only now does Eraser check the state and see the index points at an empty set → warning. Notice a thread ID never once appears inside the table: threads only feed in through locks_held(t) (and, separately, through the owner ID a shadow word holds while Exclusive).

② Sizing the shadow-word overhead

Every shared variable gets a paired hidden shadow word (a mostly-numeric tracking record). What's the memory cost of that, and why doesn't the number identifying its lockset need to be huge?

  1. The hidden shadow word is the same size as the real word: for every 32 bits of real shared data, there's another 32 bits of hidden tracking data → a flat 100% extra memory cost on anything being watched.
  2. Most of that 32 bits is spent as an index number that can identify up to about 1.07 billion different lock combinations.
  3. The paper never actually saw more than 10,000 different lock combinations show up in any one run — so that huge number space is way more room than it ever needed.
  4. The real savings: it's not really about how big the number is — it's that Eraser never has to store a full written-out list of locks per variable, only a small number that points into one shared, deduplicated table.
💡
A naive design (writing out the full list of locks for every single shared variable) would grow with how many locks touch each variable; Eraser's index design instead only grows with the number of distinct lock combinations ever seen at all — which stays small in practice.

③ Scale of testing across the four production servers

How much lock activity did Eraser actually have to track in each system, and how many annotations did it take to reach zero false alarms?

  1. mhttpd (AltaVista HTTP server, ~5,000 lines C): ~100 distinct locks, ~250 distinct locksets. 10 annotations; together with Ni2's 14, these took reported races from more than a hundred down to zero (the paper gives one combined count).
  2. Ni2 (AltaVista indexing engine, ~20,000 lines C, tested with 10 threads via the ft harness): ~900 locks, ~3,600 locksets. 9 library annotations + 5 harness annotations = 14. Eraser reported a large number of races, mostly false alarms: memory reuse first, then private locks, then benign races. The best-known benign one, on ip_fp, was a deliberately programmed and correct racy optimization rather than a bug.
  3. Vesta cache server (~30,000 lines C++, 10 threads, 26 locks, 70 locksets): 10 annotations + 1 real bug fix (the unprotected validFP fingerprint flag) reduced reports from several hundred to zero.
  4. Petal (~25,000 lines C, 64 worker threads): found one genuine unprotected read (gmap_state) and two intentional statistics races; one false alarm (stack-frame reuse in a fork/join pattern) could not be annotated away.
🍯
Insight: how many locks and lock-combinations show up scales with how big the codebase is (900 locks for 20k lines vs. 26 for 30k lines of a design that just uses fewer locks), but the number of manual annotations needed to quiet the tool stayed small — around a dozen lines per program — in nearly every case. Petal's one false alarm that couldn't be annotated away (caused by memory being reused for a different purpose) was the one exception.

④ Checking the results aren't just luck

Two experiments test whether Eraser's results depend on lucky timing or on how many threads happen to be running.

  1. Putting old bugs back in: two real, historical Ni2 bugs (an unlocked counter, and a missing lock around a subroutine) — both of which had sat undiscovered in the code for months before someone found them by hand — were deliberately reintroduced.
  2. Result: one of the authors found both bugs using Eraser within a few minutes, with no hints about where to look, and fixed and double-checked them in 30 minutes total.
  3. Does thread count matter? Ni2 and Vesta were rerun with only 2 threads running at once instead of 10.
  4. Result: the exact same set of race reports showed up either way (just possibly in a different order) — evidence that what Eraser reports doesn't just depend on how many threads happened to be running or how the timing happened to fall.
💡
This is the paper's direct answer to "doesn't running 10-30× slower change the timing enough to throw off your own results?" — the signal Eraser reports comes from the code's locking habits, not from which particular timing happened to occur.

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
Thread A touches v while holding locks {mu1, mu2}. Thread B later touches v while holding {mu2, mu3}. What is C(v) after both touches, and does Eraser report a race?
Show answer
C(v) = {mu1, mu2} ∩ {mu2, mu3} = {mu2} (keep only the locks common to both). No race is reported — the list still has something in it, meaning mu2 has been present at every touch so far.Misconception: assuming that using "different locks" automatically means a race. Only an empty list is a real violation — partial overlap is completely normal and expected as the list narrows down over time.
Problem 2 · easy
A brand-new variable has only ever been touched by the one thread that created it (status: Exclusive), always without holding any lock. Does Eraser report a race?
Show answer
No. While a variable is in the Exclusive stage, C(v) isn't being narrowed down at all — the paper deliberately holds off so a single thread can freely set up newly created data without needing a lock.Misconception: forgetting that the four-stage status, not the raw narrowing rule alone, decides when C(v) actually gets updated. The plain version of the algorithm (Tab 4, §2) would wrongly flag this as a problem.
Problem 3 · medium
A thread holds lock mu1 only in read mode, then writes to variable v, whose list C(v) currently only contains {mu1}. Does this trigger a warning?
Show answer
Yes. Writes only get checked against locks held in write mode, not against every lock the thread happens to be holding. Since mu1 is only held in read mode here, there are zero write-mode locks to check against, so C(v) := {mu1} ∩ {} = { } (empty) → warning.Misconception: assuming "holding a lock at all" is enough, regardless of mode. A lock held just for reading only protects against other reads racing — never against a write. That's the whole point of the read/write split.
Problem 4 · medium
In the paper's Figure 2 example, an unguarded variable y is touched by two threads, but happens-before doesn't catch the race in that one run. Would Lockset catch it in that same run? Why?
Show answer
Yes. Lockset only cares whether the two touches of y both happened without any lock in common — which is true no matter what order they happened to run in. Happens-before instead asks whether the specific timing that occurred that run happened to prove an order between the two touches, and in this case it did (through an unrelated lock/unlock pair), so it stayed quiet.Misconception: assuming happens-before is strictly more sensitive because it "sees more relationships." It's actually dependent on lucky timing in a way that can hide exactly this kind of bug.
Problem 5 · hard
C(v) can only ever shrink, never grow back. What does that imply if one weird, one-off touch accidentally knocks the "true" protecting lock out of the list — and what tool does the paper give programmers for this situation?
Show answer
Because the list can only shrink, once a lock is knocked out of C(v) it can never come back — even if every other touch was perfectly consistent with it. So a single unusual touch (say, memory that got quietly reused for a new purpose under a different lock) can permanently wreck C(v) and cause a false alarm forever after. The paper's fix isn't a change to the algorithm — it's the EraserReuse(address, size) annotation, which manually resets that piece of memory's status back to brand-new so the narrowing-down process starts fresh.Misconception: expecting the algorithm to "heal itself." The one-way, never-grows-back behavior is deliberate — it's exactly what makes an empty list a trustworthy signal — so recovering from a bad case has to be done by hand.
Problem 6 · medium
Eraser treats a variable as "done being set up" the moment a second thread first touches it. Describe a situation where this shortcut brings back the same lucky-timing problem Eraser was built to avoid.
Show answer
Suppose a thread creates a shared variable and starts setting it up without a lock, then by mistake shares a reference to it (say, by adding it to a shared list) before it's actually finished setting up. Eraser only catches this bug if the second thread happens to touch the variable before the first thread's last setup step finishes. If the timing happens to let setup finish first, Eraser misses it — exactly the same kind of luck-dependence Lockset was built to get away from.Misconception: thinking Eraser is completely immune to timing luck. The paper is upfront that this one specific case — sharing something too early, during setup — brings back the same weakness happens-before has.
Problem 7 · easy
Why does Eraser represent each variable's candidate-lock list as a small number pointing into one shared table, instead of just storing the actual list of locks for each variable?
Show answer
Because the number of genuinely different lock combinations that ever show up across a whole run is small (the paper never saw more than 10,000), most shared variables end up pointing at the same handful of table entries. Storing one small number per variable (small enough to fit in the hidden shadow word) is far cheaper than storing a full, variable-length list of locks for every single variable — and it turns "narrow down the list" into a quick table lookup instead of comparing full lists every time.Misconception: thinking this is just "compression" for its own sake. The real payoff is turning an expensive comparison into a fast lookup, which is what keeps the 10-30× slowdown from being far worse.
Problem 8 · hard
Eraser slows programs down 10 to 30 times, which changes exactly how threads get scheduled. The paper argues this doesn't undermine its results — using which specific experiment, and what would you expect to see if it did undermine them?
Show answer
The 2-threads-vs-10-threads experiment on Ni2 and Vesta: if Eraser's own slowdown were quietly changing which bugs get found, then running with a very different number of threads (and therefore very different timing) should turn up a different set of reported races. Instead, the exact same reports showed up both times (just possibly in a different order) — evidence the reports reflect the code's actual locking habits, not a lucky run. If the two thread counts had produced substantially different sets of reported races, that would be a red flag that Lockset's own results depended on lucky timing too, undercutting its whole argument.Misconception: assuming that any overhead which changes program behavior automatically invalidates a race detector's findings. What actually matters is whether the reports themselves change with timing, which this experiment directly tests.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1What exactly counts as a "data race" in this paper?▾
Two threads touching the same shared variable at close to the same time, where at least one of those touches is a write, and nothing (no lock) is stopping them from happening at literally the same instant. It's about whether this could happen, not about whether the program visibly broke this particular time.
Q2Why not just use happens-before, like earlier tools?▾
Happens-before only raises a flag if it can't prove an order between two touches in that one specific run's timing. A program can have a real, live bug that a given test just never happens to expose this way, so happens-before tools need lots of test runs, with lots of different timings, to be trustworthy. Lockset instead checks a habit in the code, so a single good test run is often enough.
Q3What is the "locking rule" Eraser actually checks?▾
In its full form: every shared variable needs some lock m such that m is held in write mode for every write to it, and held in either mode (read or write) for every read. If no such lock exists — nothing was ever consistently present — that's what triggers a warning.
Q4Doesn't checking every unlocked touch spam warnings for normal setup code?▾
It would, without the fix: Eraser holds off on narrowing down C(v) until a variable gets touched by a second thread (the Exclusive stage), so one thread can freely set up new data without needing a lock.
Q5How does Eraser avoid flagging read-only sharing?▾
Once a second thread has only read a variable (the Shared stage), C(v) keeps getting narrowed down in the background, but warnings stay switched off. Only once some thread actually writes to it while it's shared (Shared-Modified) does Eraser start reporting races.
Q6How does Eraser watch a program without its source code?▾
It uses ATOM, a tool that edits an already-compiled program directly, to insert tracking code at every memory read and write (except those addressed off the stack pointer), every lock/unlock, the thread start/exit stubs, and every memory-allocation call, right in the compiled program itself.
Q7How expensive is running Eraser?▾
Typically 10 to 30 times slower than the un-watched program. About half of that is estimated to come from jumping out to separate tracking code at every single memory read and write; the paper notes pasting that code inline instead would likely help, but they didn't build that.
Q8Doesn't a 10-30× slowdown change the very timing you're testing?▾
It can, but the paper's 2-threads-vs-10-threads experiment on Ni2 and Vesta found the same races reported either way, suggesting what Eraser reports doesn't actually depend much on exactly how the timing shifts.
Q9What causes Eraser's false alarms, and how are they silenced?▾
Three main causes: memory quietly being reused for a new purpose (Eraser can't see a program's own private "reuse this memory" bookkeeping), private lock implementations it was never told about, and genuinely intentional, harmless races. Programmers silence these with EraserReuse(), EraserReadLock/ReadUnlock/WriteLock/WriteUnlock(), and EraserIgnoreOn/Off() respectively.
Q10Did Eraser find real bugs, or mostly false alarms?▾
Both, but real bugs stood out: an unprotected "is this cached value still valid" flag in Vesta (genuinely unsafe on that hardware's memory behavior), an unprotected status read in Petal's server-health check, and real races in 10% of ~100 runnable undergraduate assignments — plus several intentional, harmless races the authors hadn't previously written down as such.
Q11What can't Eraser handle well?▾
Variables protected by more than one lock held at once (a pattern used to avoid a different problem, deadlock) cause false alarms under the basic algorithm; a proposed fix trades those false alarms for a risk of missing real bugs instead. It also doesn't catch deadlocks at all, and moving it into the SPIN kernel exposed trouble with signal-based coordination between drivers and threads (see How It Works, §8).
Q12Can Eraser prove a program is race-free?▾
No — it's explicitly a testing tool, not a mathematical proof. It can only report on the code paths that actually ran during your test; it skips stack-pointer-relative accesses; annotations can hide races; and the initialization heuristic (something being shared too early, during setup) can miss a bug depending on timing. No warnings means "no discipline violation among the accesses Eraser counted in this run," not "guaranteed race-free." See Part II, M14.
Beyond the paper

Connections to modern OS & memory-systems design

Where Eraser's ideas resurface in today's kernels, memory tiers, and concurrent data structures.

🧬 The "hidden tracking memory" trick lives on in modern bug-finding tools

Eraser's core trick (a hidden extra word of memory paired with every real word, sitting at a fixed distance away) is the same basic idea behind two widely-used modern tools: AddressSanitizer and the Linux kernel's KASAN (both catch memory-corruption bugs, not races, but reuse this same "shadow memory" idea). It's not a perfect family tree, though. Google's ThreadSanitizer (a modern race detector) also keeps shadow memory, but fills it with happens-before information (per-thread logical timestamps) rather than locksets, and the Linux kernel's own current race detector, KCSAN, doesn't use hidden tracking memory at all: it randomly spot-checks a few memory accesses per run instead (more on that below). Still, if you were instrumenting a concurrent page-hotness tracker or a memory-migration path for correctness testing today, some descendant of Eraser's 1997 idea is probably underneath the tool you'd reach for.

🔀 Lockset-style checking struggles exactly where lock-free code lives

Eraser's own admission — that a variable protected by more than one lock at once causes false alarms — points at a bigger problem: some modern data structures (heavily used inside Linux's memory manager) are deliberately designed to avoid needing a lock at all for reading, using a technique called RCU. A Lockset-style checker has nothing to narrow down here, because there's no consistent lock to find in the first place. This is one reason the Linux kernel's actual race detector, KCSAN, takes a completely different approach: instead of tracking locks, it randomly watches a small number of memory locations per run and waits to see if two threads collide on one of them — sampling for evidence of a race, rather than checking a locking habit.

⏱ Treating "interrupt level" as a stack of locks is a similar idea to modern device-driver code

Eraser's SPIN extension, treating "we've currently blocked interrupts up to level n" as if it meant "we're holding n different locks at once", resembles the kind of reasoning needed for modern device drivers on newer, pluggable memory hardware, where correctness depends on exactly which interrupts are currently blocked, not just which explicit locks are held. Adapting this same idea could be a reasonable starting point for instrumenting kernel-level memory-tiering code that mixes "interrupts temporarily blocked" sections with ordinary locks, though the paper reports no results for it: the SPIN port did not yet work, so the trick was never shown working even on SPIN.

🏷 The four-stage variable life cycle echoes per-page tracking in memory systems

Virgin → Exclusive → Shared → Shared-Modified is a small four-stage status designed to avoid false alarms on normal setup and read-sharing. Systems that automatically move data between fast and slow memory (tracking which pages of memory are "hot" or "cold" to decide what to promote or demote) use very similar per-page status tracking — and whenever more than one thread might update that per-page status at the same time, that's exactly the kind of new shared-variable race a Lockset-style checker would need to be pointed at.

🍯
Any time you build or instrument new tracking data that more than one thread can touch at once — a promotion queue, a hotness counter, a migration flag, in a system that moves data between memory tiers — you've created exactly the kind of shared-variable race Eraser targets. A Lockset-style checker is a reasonable tool to point at that new tracking data, alongside the sampling-based approaches (like KCSAN) that modern kernels increasingly lean on instead, precisely because so much of today's code avoids locks altogether.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
EraserThe paper's tool: a program that watches a running, lock-based multithreaded program and looks for data races, by editing the already-compiled program to add tracking code.
Lockset algorithmEraser's core check: keep a running, shrinking list of locks that could be consistently protecting each shared variable; raise a warning once that list is empty.
Candidate set C(v)The current list of locks that could still be the one consistently protecting variable v — narrowed down by keeping only what's common at every touch, and only ever shrinking.
Locking disciplineA programming habit (e.g. "every shared variable always has one specific lock guarding it") that, if followed consistently, rules out races.
Happens-before relationA way of proving a definite before/after order between two threads' actions using synchronization events as evidence; the basis of earlier race detectors, whose big weakness is that it only sees the one timing that actually happened during a given test.
Virgin / Exclusive / Shared / Shared-ModifiedThe four stages Eraser tracks per variable (new / single-owner setup / shared for reading / shared and being written) to tolerate unlocked setup and read-sharing, only reporting races in the last stage.
Shadow memory / shadow wordA hidden extra word of memory (holding a lockset index + stage) kept right alongside each real shared word, found at a fixed distance away.
Lockset indexA small number standing in for a full list of locks, pointing into one shared, deduplicated table — never more than about 10,000 distinct entries were ever observed.
Supporting terms
ATOMDigital Equipment Corporation's tool for editing an already-compiled program (for the Alpha processor) that Eraser is built on top of.
Benign raceA real, uncoordinated access to shared memory that the programmer intentionally allows because it happens to be harmless (e.g. a simple flag).
Read-write lock (rwlock)A lock that allows many threads to hold it at once for reading, but only one at a time for writing (and never together with a reader).
Monitor (Hoare)An older idea: bundle shared data with the only functions allowed to touch it, all guarded by one automatic lock — decided when the program is written, not while it runs.
Lock coversDinning & Schonberg's earlier improvement to happens-before for lock-heavy programs; Eraser is framed as extending and simplifying this idea.
EraserIgnoreOn/Off, EraserReuse, EraserRead/WriteLockManual annotations programmers add to their code to tell Eraser "this specific pattern is fine, stop warning about it" — for benign races, memory reuse, and private lock implementations respectively.
Interrupt levelA kernel mechanism that keeps code safe from interruption by temporarily blocking lower-priority hardware signals, instead of using a lock; Eraser treats each level as if it were a set of nested locks.
DeadlockA different hazard from a data race — two threads stuck forever, each waiting on a lock the other one holds. The paper sketches a way to check for this too, as related future work.
