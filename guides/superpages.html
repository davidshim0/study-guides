Reserving contiguity before you need it, instead of copying for it later

A TLB miss is a trip back to the page table. Superpages shrink that trip's frequency dramatically — if the OS can find contiguous physical memory when it matters. This is the plain-English story of how FreeBSD's reservation-based superpage system does that, transparently.

📄 "Practical, Transparent OS Support for Superpages" · Navarro, Iyer, Druschel, Cox 🎓 Assumes basic TLB/page-table knowledge — primers cover the rest ⏱ ~30 min read
🧩

Reserve contiguous physical memory speculatively, before you know you'll need it — because fixing up contiguity after the fact means copying pages, and that cost is hard to recover.

⚡ TL;DR

  • The paper builds a reservation-based, transparent superpage manager for FreeBSD/Alpha: speculatively reserve a large contiguous physical region on first touch, and incrementally promote it as more of it gets populated — no relocation copying, no per-app tuning.

Quick glossary
TLBTranslation lookaside buffer — a tiny, fully-associative cache of virtual→physical page mappings that sits on the critical path of every memory access.
SuperpageA single large page (e.g. 4MB) that occupies one TLB entry but covers what would otherwise be hundreds of base-page mappings.
TLB coverageTotal memory reachable via cached TLB entries without a miss; it hasn't scaled with main memory size, so it's shrunk to a tiny fraction of RAM.
Reservation-based allocationSpeculatively grabbing an aligned, contiguous chunk of physical frames at first touch, so later pages in the region can be promoted without copying.
FFTW"Fastest Fourier Transform in the West," a widely used C library (Frigo and Johnson, MIT) for computing discrete Fourier transforms, which convert a signal or grid of values into its frequency components. Mathematically a DFT is a multiplication by a dense matrix of complex roots of unity, but the FFT never builds that matrix: it splits the problem recursively into smaller transforms (Cooley-Tukey), reaching O(N log N) work instead of the O(N²) of a direct matrix-vector product, and far less arithmetic reuse per data element than matrix multiplication. A multidimensional transform, like the paper's 200×200×200 input, is computed as many one-dimensional transforms along each axis in turn. FFTW picks its algorithm at run time by timing candidate strategies on the actual machine.
Daemon / page daemonA daemon is a long-running background process or kernel thread that does housekeeping on its own schedule rather than in response to a direct request (sshd, cron). FreeBSD's page daemon is the kernel thread that wakes under memory pressure, ages pages through its active, inactive, and cache lists, writes dirty pages out, and frees clean ones; Linux's equivalent is kswapd. It's one long-lived thread that spends most of its time asleep: allocation code wakes it when free memory runs low, it scans and reclaims until it reaches its free-memory target, then goes back to sleep. It isn't created or destroyed with the pressure; it just sleeps and wakes. This paper adds a second wake-up trigger (a failed contiguous allocation, even with plenty of free memory) and makes it pick victims that restore contiguity, sleeping again once it has freed that contiguity or run out of candidates. Linux's kswapd follows the same pattern, waking below a low watermark and sleeping once free memory is back above a high one.
Relocation-based allocationThe alternative: physically copy already-scattered pages into a contiguous region when you decide a superpage would help — expensive and hard to amortize.
Promotion / demotionMerging base pages into a bigger superpage TLB entry (promotion), or splitting one back down (demotion) when only part of it is still in active use.
Buddy allocatorA classic physical-memory allocator that splits/merges power-of-two-sized blocks, used here to hand out contiguous frame extents.
Fragmentation (external)Free memory existing only in small scattered pieces, preventing large contiguous allocations even when total free memory is plentiful.
Population mapA per-object radix tree tracking which base pages within a reservation have actually been allocated, used to decide when to promote.
1Why TLB coverage matters▾

Every memory access needs a virtual→physical translation. The TLB caches recent translations so the CPU doesn't walk the page table each time. But the TLB is small (often ≤128 entries) and fully-associative, so it must stay fast — its size hasn't grown with RAM.

Over 1986–2001, TLB coverage as a fraction of main memory shrank by roughly 100×. Applications with working sets bigger than TLB coverage now pay 30–60% performance penalties from TLB misses, up from ~5% in the 1980s.

Now you're ready: superpages are the software answer — one TLB entry maps megabytes instead of kilobytes, restoring coverage without enlarging the TLB.
2Superpages: what they cost the OS▾

A superpage must be contiguous and aligned in physical memory, and the hardware gives it only one reference bit, one dirty bit, and one set of protection bits for the whole thing — the OS can't distinguish behavior of individual base pages inside it.

That coarseness is the source of almost every design headache in this paper: you can't tell which part of a superpage is still used, or which part is actually dirty.

Now you're ready: most of the paper's mechanisms (speculative demotion, dirty-superpage handling) exist specifically to work around this one-bit-per-superpage limitation.
3Reservation vs. relocation▾

Two ways to get contiguous physical memory for a superpage. Relocation: let pages land wherever, then copy them into a contiguous region once you decide superpages would help. Reservation: grab the contiguous region up front, before you know how much of it will be used, so later pages just land in the right spot with no copying.

Reservation trades a possible wasted reservation (if the app never touches those pages) for zero copying cost.

Now you're ready: this paper's whole design is reservation-based, extending Talluri & Hill's original scheme to multiple sizes.
4Physical memory objects and page faults▾

A process's address space is made of memory objects (code, stack, heap, mmap'd files). Physical pages are normally allocated lazily — only when first touched, via a page fault. The fault handler picks any free frame and maps it in.

This lazy, one-frame-at-a-time allocation is exactly what plain systems do, and exactly what has to change to make superpages possible without copying.

Now you're ready: the paper's page-fault handler instead grabs a whole aligned superpage-sized extent on the first touch, reserving the rest for later touches.
5Buddy allocators▾

A classic technique for managing physical memory in power-of-two-sized, aligned blocks. Splitting a free block gives two half-size "buddies"; when both buddies are free again, they coalesce back into the larger block.

This structure naturally matches superpage size/alignment constraints — asking a buddy allocator for a 4MB-aligned chunk is a native operation.

Now you're ready: the paper's allocator is a buddy system, extended with per-size reservation lists layered on top.
6External fragmentation▾

Even with plenty of total free memory, it can be scattered in pieces too small to satisfy a large contiguous request. Running ordinary desktop workloads for 15 minutes was enough to exhaust all >64KB-contiguous regions in the paper's test, despite 360MB of 512MB being free.

Fragmentation is the enemy of sustained superpage use — a system that looks great in a fresh boot can degrade fast.

Now you're ready: a large chunk of the paper (Sections 4.4, 5.1) is about actively fighting fragmentation, not just exploiting contiguity when it's free.
7LRU-based page replacement (A-LRU)▾

FreeBSD's page daemon keeps active/inactive/cache lists in approximate LRU order, evicting pages under memory pressure roughly in least-recently-used order. This maximizes hit rate but has no notion of physical contiguity — it can happily scatter pages that happen to be adjacent in physical memory.

Now you're ready: the paper modifies this daemon to also care about contiguity, trading a little A-LRU fidelity for a lot more usable superpage material.
8Dirty/reference bits and write-back▾

The OS tracks whether a page has been accessed (reference bit) or modified (dirty bit) to decide what's safe to evict and what needs to be written to disk first. Normally this is per-base-page.

With superpages, hardware often gives only one dirty bit for the whole superpage — so writing back a superpage with even one dirty base page means writing back all of it.

Now you're ready: this is why the paper demotes a superpage the moment any part of it is written — to avoid a potential 512× I/O blowup.
9The Alpha's PTE-replication superpage implementation▾

Unlike some architectures with a genuinely separate superpage TLB entry format, the Alpha's firmware implements superpages by replicating the same page-size field across every constituent base-page PTE. Promoting a 4MB region means touching all 512 of its 8KB page table entries.

Now you're ready: this hardware quirk is the direct cause of the paper's "linear-in-superpage-size" cost for promotion, demotion, and dirty-bit emulation.
The whole story in one place

Superpage management in a nutshell

The problem, the reservation trick, and how the pieces fit together.

TLB coverage has fallen roughly 100× relative to main memory over ten years, so many applications' working sets no longer fit in the TLB's reach, costing 30–60% in performance. Hardware offers superpages — single TLB entries covering megabytes — but using them well is an OS problem: allocate the right size, keep the physical memory contiguous enough to make more, and don't let coarse hardware bits (one dirty bit, one reference bit per superpage) cause silent I/O blowups.

The paper's answer is reservation-based allocation, generalized to multiple superpage sizes: on first touch of a memory object, speculatively reserve the largest aligned contiguous extent that seems appropriate for that kind of object. As more base pages in that extent get touched, incremental promotion upgrades it to bigger and bigger superpages — no copying, ever. When memory gets tight or fragmented, the system preempts under-used reservations and runs a contiguity-aware page daemon that biases eviction toward pages that would restore large contiguous regions, rather than blindly following LRU order.

Two hardware limitations get careful treatment: a superpage's single reference bit can't reveal which parts are still used, so the system periodically and speculatively demotes active superpages to check; and its single dirty bit would force writing back a whole superpage even if one base page is dirty, so the system demotes on first write to keep write-back granular.

The payoff: best-case speedups of 30–60% (up to 7.5× for a pathological matrix transpose) when memory is uncongested, sustained performance under realistic fragmentation (recovering up to 42.4% of the system's contiguity between FFTW runs vs. 8.8% for a naive scheme), and under ~1–2% average overhead when superpages don't pay off — rising only to 8.9% under a deliberately adversarial promote-then-discard workload — with no special hardware beyond what most CPUs already provide.

🍯 Key takeaways

  • Reservation, not relocation: grab contiguous physical memory speculatively at first touch — avoids ever copying pages to build a superpage.
  • Incremental promotion: a superpage forms the instant a fully-aligned sub-extent is fully populated; larger sizes follow as more fills in.
  • Preemption reclaims under-used reservations (LRU by "least recently allocated") rather than refusing new large allocations outright.
  • Contiguity-aware page daemon deviates from strict LRU just enough to actively restore fragmented contiguity: 0.8% overhead for the restoration work, plus about 3% extra slowdown for a web server running concurrently (§6.5).
  • Demote-on-write avoids the "one dirty bit means write back everything" blowup — measured at a 512× larger I/O volume and over 20× runtime penalty if skipped.
  • Speculative demotion compensates for the single reference bit, letting the OS discover which parts of a superpage are stale.
  • Result: 30–60% speedups sustained over time, <2% average overhead, no new hardware required.
Six everyday pictures

How to think about superpage management

Each stands alone. Every card ends with where the picture breaks.

The core idea · Reservation

Booking the whole row at the theater

You want one seat now, but you might bring friends later. Book the whole row up front — nobody else can take those seats, and when friends show up they just sit down, no shuffling. That's reservation-based allocation: grab a big contiguous extent on first touch so later pages land in place, with zero physical copying.

Where it breaks: if your friends never show, you've held seats nobody used — this is exactly the "wasted reservation" the preemption policy has to reclaim.
The alternative · Relocation

Moving apartments to be near friends

You could physically pack up and move to be next to someone you want to be near — that's relocation: copy pages into a contiguous region once you decide it's worth it. It works, but the moving cost is real and paid every time, even when a nearby empty apartment (free contiguous memory) was available all along.

Where it breaks: relocation is more robust to a fully-booked building (fragmented memory) than reservation — it can still find a spot elsewhere, just at moving-cost.
The mechanism · Incremental promotion

Merging four small envelopes into one package

Postage is cheaper per item if you consolidate into one box, but you only tape it shut once all four items are actually inside — sending an empty slot wastes the box's capacity. That's incremental promotion: only when an aligned extent is fully populated does it merge into a bigger superpage, avoiding wasted memory footprint.

Where it breaks: real packages don't grow bigger later; superpages can be promoted again to a still-larger size as more envelopes (base pages) arrive.
The problem · Fragmentation

A parking lot with cars scattered one-per-row

Plenty of empty spaces exist, but they're scattered so no bus (a large contiguous region) can park anywhere. The lot needs active management — moving a few cars — to open up a bus-sized gap, even though total free space never changed.

Where it breaks: the paper's fix doesn't physically move cars (no relocation) — it changes which cars leave next (contiguity-aware eviction) to naturally clear useful gaps.
The limitation · One reference/dirty bit

One smoke detector for the whole floor

A single detector tells you something on the floor triggered it, but not which room. If only one room actually has a fire, you still have to evacuate (or inspect) the whole floor. That's a superpage's single reference/dirty bit: the OS knows the superpage was touched or dirtied somewhere, but not which base page.

Where it breaks: you can't "split the floor" to isolate the fire, but the OS can demote a superpage into smaller pieces to regain per-base-page visibility.
Enforcement cost · Demote-on-write

Reprinting a whole book for one typo

If your printer can only mark "this book has an edit somewhere" (not which page), fixing one typo means reprinting the entire book. The system avoids this: the instant any page inside a clean superpage is written, it demotes to base pages first — so only the truly dirty pages get written back to disk later.

Where it breaks: real reprinting is cheap to avoid by tracking page numbers; the hardware genuinely can't, which is why the paper measured a 512× larger I/O volume and over 20× runtime penalty for skipping this step.

How it actually works

Section by section, with the paper's key mechanisms visualized.

1 · Allocation — reserve first, populate later

On a page fault with no existing reservation, the system asks the buddy allocator for a contiguous, aligned extent sized according to a policy (Section 4.2): the largest superpage that fits within a fixed-size object (code, mmap'd files) without overlapping other allocations, or — for growable objects like heaps/stacks — the largest superpage that fits the object's current size, to avoid wasting contiguity on objects that may never grow. Only the faulting page is mapped immediately; the rest of the extent is added to a reservation list, unmapped, waiting.

So a 4KB touch can trigger a 4MB reservation, with only that page mapped? Yes, with two refinements. First, nothing "asks" for a page: the application touches an address in a region it already mapped (heap, stack, code, an mmap'd file), the touch faults, and the decision happens inside the fault handler. Second, the page that gets mapped isn't necessarily the first one in the extent. A superpage must be aligned identically in virtual and physical space, so each virtual page's future frame is fixed by its offset: if the faulting page is the 37th page of its aligned 4MB virtual region, it gets the 37th frame of the reserved physical extent ("the frame with the same address alignment as the faulted page"). That's what lets the region later become one superpage without moving anything.

How does the OS know how much an application will need? It doesn't, and it doesn't try to predict: no compiler or static analysis, no profiling, no application hints. The paper says the decision is "usually made early in a process's execution, when it is hard to predict its future behaviour," so the policy "looks only at attributes of the memory object to which the faulting page belongs," meaning its type (fixed-size versus growable) and its current size. That's a deliberate contrast with IRIX and HP-UX, which pick sizes from user-supplied per-segment page-size hints, an approach the paper rejects as not transparent. The policy errs toward large because the two kinds of mistake aren't symmetric: a reservation that's too big is cheap to undo (unused frames get preempted back), while one that's too small can't be grown later without relocating pages. The real "learning" happens after the fact, in promotion, which waits for actual population, and preemption, which reclaims whatever the guess got wrong. This is consistent throughout the paper. (Paper §3, §4.1, §4.2, §4.3)

Why does §4.2 keep saying "does not overlap with existing reservations or allocations"? Isn't that obviously true? For physical frames it is: the buddy allocator never hands out a frame that's already in use. But that isn't what the condition is about. It's a limit on the size of the new reservation, measured in the object's virtual range. The candidate superpage is the aligned virtual chunk around the faulting page, and some pages inside that chunk may already have frames: faulted in earlier under a smaller reservation, or (for an mmap'd file) already sitting in the file cache from someone else's read. Those pages live in frames somewhere else. If the OS reserved a fresh 512KB physical extent for the chunk anyway, those already-placed pages wouldn't be in it, so the chunk could never become one superpage without copying them, which is exactly the relocation cost reservations exist to avoid. Likewise, a chunk that includes part of an earlier reservation would leave some virtual pages with two possible frames. So the rule shrinks the reservation to the largest aligned size whose virtual range is still entirely untouched. Example with 8KB base pages: a fault lands on page 100 of a heap whose pages 64 to 99 were already faulted in one at a time. The 512KB chunk around it (pages 64 to 127) and the 64KB chunk (pages 96 to 103) both include already-allocated pages, so this fault gets only a base page. A fault on page 120 instead, whose 64KB chunk (pages 120 to 127) is untouched, can still get a 64KB reservation. That's how a single growing heap ends up with a patchwork of sizes. (Paper §4.1, §4.2)

Fixed versus dynamic objects, worked through. Both kinds start from the same rule: the largest aligned superpage that contains the faulting page and doesn't overlap pages that already have frames or reservations. They differ only in the final limit. A fixed-size object (code, an mmap'd file) adds "and doesn't reach beyond the end of the object." A growable object (heap, stack) drops that limit and instead caps the size at the object's current size. Examples below use the Alpha's 8KB base pages (64KB = 8 pages, 512KB = 64 pages, 4MB = 512 pages) and assume each object starts at a 4MB-aligned virtual address.

Fixed: a 296KB mmap'd file (pages 0 to 36). A fault on page 0: the 4MB chunk (pages 0 to 511) and the 512KB chunk (0 to 63) both run past page 36, past the end of the file. Those extra virtual pages aren't part of this object and it can never grow into them, so they could never be populated, the chunk could never be promoted, and the extra reserved frames would just sit wasted until preempted. The 64KB chunk (0 to 7) lies entirely inside the file, so that's the reservation. A later fault on page 34: its 64KB chunk (32 to 39) runs past page 36, so it gets only a base page. That's "reaching beyond the end of the object": an aligned chunk sticking out past the object's last page.

Dynamic: a heap that grows over time. (1) The heap is 24KB (pages 0 to 2). Faults on pages 0 to 2 are capped at 24KB, which is smaller than any superpage, so each gets a base page. (2) The heap has grown to 104KB (pages 0 to 12) and page 8 faults. The cap now allows 64KB, the chunk 8 to 15 is untouched, and it sticks out past the current end (13 to 15), which is allowed for a heap because brk will likely grow into it. Reserve 64KB. (3) The heap is 704KB (pages 0 to 87) and page 16 faults. The 512KB chunk (0 to 63) would overlap pages 0 to 2, which already have scattered frames, and the 64KB reservation on 8 to 15, whose frames are already earmarked for those pages; including them would mean copying the old pages in or giving pages 8 to 15 two candidate frames. So it falls back to the 64KB chunk 16 to 23. (4) Page 64 faults. The 512KB chunk (64 to 127) is untouched, sticks out past the current end (88 to 127), which is fine for a heap, and 512KB is under the 704KB cap. Reserve 512KB. The 4MB chunk would both overlap earlier pages and exceed the cap.

Overlap only arises because each fault decides independently, using the object's size at that moment: early faults, made while the heap was small, leave small reservations and loose pages behind, and later, bigger decisions have to route around them. For files, pages already in the file cache from an earlier read() count as allocated too. (Paper §4.2)

Does a heap always reserve its current size? No. The current size is a ceiling, not the amount reserved. The reservation is still one aligned chunk around the faulting page, its size must be one of the hardware's superpage sizes, and it's the largest such size that is no bigger than the object's current size and doesn't overlap anything. A 704KB heap can't get a 704KB reservation, because 704KB isn't a page size; the largest size under the cap is 512KB, and that 512KB covers only the chunk around the faulting page, not the whole heap. Other parts of the heap get their own reservations at their own faults.

The ceiling exists because of the dropped end-of-object rule. A growing heap is usually touched right at its current end, so "don't reach past the end" would leave room for nothing more than a base page every time; that's why the rule is dropped for growable objects. But with no limit at all, a 24KB heap that may never grow could grab a 4MB chunk. Current size is the paper's evidence of how big the object is likely to get: a heap that has already reached 704KB has shown it's large, so betting 512KB on it is reasonable, while a 24KB heap gets nothing bigger than a base page. In the paper's words, the policy "uses large reservations only for objects that have already reached a sufficiently large size." A consequence worth noticing (this guide's reading, not the paper's statement): since the reserved chunk can't exceed the current size, the part reserved past the current end is always smaller than what the heap already holds, so a heap can at most roughly double its reserved footprint in one step, and even that excess can be reclaimed later by preemption. (Paper §4.2, §4.3)

Zooming in on step (2): the heap is 104KB (pages 0 to 12), only pages 0 to 2 have ever been touched, and page 8 faults first. Is the 64KB reservation for 8 to 15, or for 0 to 7? It's for 8 to 15, the aligned chunk that contains the faulting page; a reservation is always the chunk around the page that faulted. Chunk 0 to 7 doesn't contain page 8, and it's ruled out anyway because pages 0 to 2 already sit in scattered frames. Growing the heap with brk doesn't fault anything in; it only extends the object's virtual range, so pages 3 to 12 exist but have no frames until touched. The policy doesn't size the reservation to what's "needed" (pages 8 to 12, 40KB); it only checks that the chunk is a supported size (64KB), no bigger than the heap (104KB), and untouched. So all eight frames for pages 8 to 15 are set aside, only page 8's frame is mapped, and pages 13 to 15, beyond the current end, are a bet on growth. If the heap grows past page 15 and all of 8 to 15 get touched, the chunk becomes a 64KB superpage. If it never grows, the chunk never fills, is never promoted, and its unused frames sit reserved until preemption takes them back. Meanwhile pages 3 to 7 will only ever get base pages: any fault there finds its chunk (0 to 7) already overlapping pages 0 to 2, so that chunk can never become a superpage without copying, which this design never does.

The resulting shape of a heap. One precision on "64KB is the largest aligned superpage containing page 8": the 512KB chunk (pages 0 to 63) also contains page 8, but it fails two checks, it's bigger than the 104KB heap and it overlaps pages 0 to 2. So 64KB is the largest size that passes every check, not the largest that contains the page. Put together, a heap ends up small-paged at its start and progressively larger toward its growing end: early faults happen while the cap is small, so they get base pages or small reservations, and since nothing is ever relocated, that start of the heap stays small-paged for good. Later faults, made once the heap is large, can earn 512KB and then 4MB chunks. It's a tendency rather than a guarantee: a later large chunk can still be blocked by overlap with earlier leftovers, or fall back to a smaller size when contiguous physical memory is short. (A stack shows the same pattern mirrored, since it grows toward lower addresses.) Fixed-size objects look different: their size is known from the start, so they get large chunks throughout, and only their tail is trimmed to small pages by the end-of-object rule. (Paper §4.2)

2 · Incremental promotion — merge only when full

As more pages in a reservation get touched, the population map (a radix tree, one level per page size) tracks how full each aligned sub-extent is. The instant an aligned sub-extent becomes fully populated with uniform protection and dirty-bit status, it's promoted to the next superpage size. This repeats upward — 8KB → 64KB → 512KB → 4MB on the Alpha — so a densely-populated region climbs to the largest useful size without ever pre-populating pages the application hasn't touched.

Does it grab the full 4MB up front, and does it have to fill all 4MB before anything gets promoted? No on both counts, and the distinction between reserving and allocating is the key. On the first fault in a region, the system picks a preferred size and takes a contiguous, aligned extent of that size from the buddy allocator, but it maps (and zero-fills) only the one base page that faulted. Every other frame in the extent is just set aside: not mapped, not zeroed, not charged to the process as resident memory, and preemptible later if it turns out to be a bad bet. The reserved size also isn't always 4MB. For fixed-size objects (code, mmap'd files) it's the largest aligned superpage that contains the faulting page, fits inside the object, and doesn't overlap existing reservations; for heaps and stacks it's capped at the object's current size, so a tiny heap gets a small reservation and only earns a large one after it has actually grown.

Nor is it a 4KB-or-4MB world. The authors built this on the Alpha, which offers 8KB base pages plus 64KB, 512KB, and 4MB superpages (the paper notes Itanium offers ten sizes from 4KB to 256MB; it's the i386 of the time that offered only 4KB and 4MB). Promotion happens the moment any aligned, superpage-sized extent inside the reservation is fully populated: 8 touched 8KB pages in an aligned 64KB block become a 64KB superpage right away, eight of those become 512KB, eight of those become 4MB. So a 4MB reservation starts paying off in TLB reach after just 64KB of real use, long before it's full.

Your instinct is correct for a machine with only two sizes, though. On i386, going from 4KB straight to 4MB really would require all 1024 base pages in the aligned 4MB region to be touched first, because the system refuses to populate pages the application hasn't touched just to make promotion possible (doing so would inflate the footprint and, as the paper notes, quietly stop catching some invalid accesses). That's exactly why the paper argues for multiple sizes: in Table 2 the best single size differs by application (64KB for SP, 512KB for vpr, 4MB for FFTW), because smaller programs never fully populate large superpages, and letting the system pick among all sizes per region beats any single size, more than doubling the speedup for mcf. (Paper §2.2, §4.1, §4.2, §4.5, §6.4)

3 · Preemption — reclaiming under-used reservations

When a new allocation needs a contiguous extent that isn't available from the buddy allocator, the system preempts an existing, partially-used reservation rather than refusing the request outright. Among candidates, it picks the reservation whose most recent page allocation happened least recently — a proxy for "least likely to fill up soon." Preemption doesn't shatter the reservation into base pages; it breaks it into the next-smaller size, freeing fully-unpopulated chunks and reinserting partially-populated ones into the appropriate size-specific reservation list (the multi-list reservation scheme, §4.8).

What does "broken to smaller extents" mean? Down to the largest chunks possible? It means one size step down, not all the way to base pages. The paper's example: a 512KB reservation (64 base pages) is preempted and cut into its eight aligned 64KB pieces, and each piece is then handled by how full it is. Say pieces 1, 2, 4, 5, 6 and 7 have no pages in use, piece 0 has a few, and piece 3 is completely in use. The six empty pieces go back to the buddy allocator as free 64KB extents, one of which satisfies the request that triggered the preemption. Piece 0 stays a reservation, now a 64KB one, keeping its unused frames set aside so it can still grow into a 64KB superpage; it's reinserted into the 8KB list, since 8KB extents are the most it could yield if preempted later, and at the head of that list, which makes it the first candidate next time. Piece 3 is complete, so it isn't a reservation anymore and isn't reinserted. Smashing everything to base pages wouldn't free more contiguous memory, since the buddy allocator would merge the freed frames back into 64KB blocks anyway; what it would destroy is piece 0's reservation, scattering its spare frames so that piece could never become a superpage. The paper's example shows a single step; for a reservation whose largest free extent is two sizes down (say a 4MB reservation where every 512KB piece has some page in use, which the scheme files under the 64KB list), splitting presumably continues only as far as needed to expose those extents, but the paper doesn't spell that case out. (Paper §4.8)

4 · Fragmentation control — the contiguity-aware page daemon

Standard FreeBSD evicts pages in approximate LRU order, oblivious to physical contiguity. This paper's page daemon adds three changes: (1) clean cache pages are treated as available for reservations and kept coalesced by the buddy allocator; (2) the daemon wakes not just on memory pressure but also when a contiguous-allocation attempt fails, and then scans the inactive list specifically for pages that would restore the missing contiguity; (3) file-backed pages are moved to the inactive list as soon as their file closes, growing the pool of reclaimable candidates.

Why deviate from strict LRU at all? Because contiguity is itself a scarce, contended resource — restoring it purely reactively (only on hard memory pressure) is too late; the daemon needs a second trigger tied to failed contiguous allocations specifically.

5 · Speculative demotion & dirty-superpage handling

Because a superpage carries only one reference bit, the OS can't tell if all its base pages are still actively used or just a few. Under memory pressure, whenever the page daemon resets a superpage's reference bit, it also demotes that superpage (with probability p=1 in the implementation) — splitting it back down so individual base pages can be independently evaluated and, if truly cold, evicted. If they're all still hot, the pieces simply re-promote later.

How can the daemon reset "a base page's" reference bit if a superpage has only one bit? It can't tell the base pages apart, and that's exactly the problem this mechanism exists to solve. Two things make the sentence make sense. First, nothing has to detect the reset: resetting is the daemon's own action. Like a clock or second-chance algorithm, the daemon walks its page lists one base page at a time (the OS keeps a bookkeeping structure for every base page, even ones inside a superpage), clears that page's reference bit, and later checks whether it got set again; a page that stayed clear is cold. The paper hooks into that moment. Second, for a base page inside a superpage, "its reference bit" is really the superpage's one shared bit (on the Alpha, an emulated bit: the OS removes access, and the first touch anywhere in the superpage traps and marks it referenced). So every base page in the superpage gives the same answer, and the daemon can't learn which ones are actually in use.

Rather than guess, under memory pressure it demotes. The demotion is recursive along the path to the chosen page: a 4MB superpage splits into eight 512KB superpages, the 512KB one containing the chosen page splits into eight 64KB ones, and the 64KB one containing it splits into eight base pages, while the other pieces stay as smaller superpages. Each piece now has its own mapping and its own reference bit, so one shared bit has become many. The daemon clears them and watches: pieces that get referenced again are in use, pieces that stay unreferenced are cold and can be evicted. If every base page of a demoted region turns out to be referenced, it's promoted back ("incremental repromotion"). The probability p is a knob for how often to pay that price, since each speculative demotion loses TLB reach until repromotion; with p = 1, the implementation demotes every time the conditions hold. (Paper §4.6, §6.8)

Does the daemon keep its own per-base-page reference bit? No; it keeps per-base-page bookkeeping, which is different. The reference bit itself is set by the hardware (or, on the Alpha, by the OS's trap-based emulation) in the page mapping whenever the page is touched; the daemon only reads and clears it. Separately, the OS keeps a software record for every physical base frame (which object and offset it belongs to, which list it's on: active, inactive, or cache), and that record exists all the time, before and after promotion, because merging pages into a superpage changes only how they're mapped, not the per-frame bookkeeping. What promotion loses is per-page reference information. While the pages are mapped individually, each mapping has its own bit and the daemon gets a real answer per page. Once they're mapped as one superpage there's one mapping and one bit, so asking about any base page inside it returns the superpage's shared answer, and the per-page record holds no new information. Demotion is what restores separate mappings, and with them separate bits. (Paper §4.6)

Why demote a superpage that looks active? To find the hot pages, move them, and free the superpage? Close in goal, opposite in mechanics: nothing is moved. "Active" only means the shared reference bit got set, which happens if even one base page inside was touched. Picture a 4MB superpage where the program actively uses only 64KB. As long as it stays merged it always looks active, so the daemon can never evict any of it, and the cold 3.9MB is held hostage by the hot 64KB. Demotion splits the mapping in place (every page keeps its physical frame), so after the next scan the cold pieces show up as unreferenced and can be evicted one by one, while the hot 64KB stays exactly where it is and can even be repromoted to a 64KB superpage. Moving pages would be relocation, the copying cost this design avoids. That's also why it's done only under memory pressure, since there's nothing to gain from finding cold pages when memory isn't needed, and why it's called speculative: the OS doesn't know whether the superpage is fully hot or mostly cold, so it splits it and lets the reference bits answer. If every piece turns out hot, the pieces are repromoted and the only cost was some temporary TLB reach plus the demote and repromote work. (Paper §4.6)

Reading the sentence literally: "recursively demotes the superpage that contains the chosen base page." It means exactly that: the superpage containing the chosen page is split, chosen page included. Nothing is being excluded. The "chosen base page" isn't special, hot or cold; it's simply whichever base page the daemon happened to be scanning when it cleared the reference bit. Because the daemon walks through pages one at a time, any superpage it runs into while memory is tight gets split. "Recursively" says how far: split one level, then split again the piece that still contains the chosen page, down to base pages, leaving every sibling piece as a smaller superpage. The paper describes eviction-triggered demotion in the same terms ("first demoted to the next smaller superpage size, then the process is applied recursively for the smaller superpage that encompasses the victim page").

What is p? A coin flip made each time the trigger occurs (memory pressure plus the daemon clearing the bit of a base page inside a superpage): with probability p the superpage is demoted, otherwise it's left intact. It isn't choosing among pages; it only decides whether this encounter causes a split. The paper's only statement is "in our current implementation, p is 1," meaning always demote, and it reports no experiments with other values. The knob exists because demotion has a price: lost TLB reach until repromotion, plus demotion and repromotion work, which the paper notes can repeat several times in a process's life under memory pressure and gets expensive for large superpages on the Alpha, where every base-page PTE must be rewritten. A smaller p would demote less often and churn less, at the cost of discovering cold pages more slowly. (Paper §4.6, §6.8)

The whole cycle, step by step. The paper gives the shape (three lists in approximate LRU order, speculative demotion, repromotion when every piece is referenced); the activity-count detail in step 1 is how FreeBSD's page daemon worked generally, not something the paper spells out.

  1. The daemon sweeps. FreeBSD keeps every physical page on one of three lists: active, inactive, and cache. Under memory pressure the daemon walks them. For each page it checks the reference bit and clears it. Referenced pages stay (or go back to) active; pages found unreferenced lose standing (FreeBSD keeps a small activity count per page that rises when referenced and falls when not) and, once it runs out, move to inactive.
  2. It hits a page inside a superpage. The bit it just cleared is the superpage's single shared bit, so the answer says nothing about that particular page. With memory tight, the superpage is split along the path to that page into smaller superpages and, at the bottom, separate base pages.
  3. The new pieces start out "unreferenced." Each piece now has its own mapping and its own bit, starting cleared. From here on, the hardware (on the Alpha, a trap on first access) sets the bit of whichever piece actually gets touched.
  4. The "wait" is just the sweep coming back around. The daemon doesn't sleep on these pages or set a timer. It keeps working through the rest of memory, and the waiting period is however long it takes to get back to these pages, which is shorter the harder memory is pressed, since the daemon scans faster.
  5. On the next visit, the bits give the answer. A piece whose bit is set was used since the split: it's active, so its bit is cleared and it stays. A piece whose bit is still clear wasn't touched for a full sweep: it drifts toward inactive, and from there clean pages move to the cache (reclaimable at once) while dirty ones are written out first.
  6. Hot pieces merge back. If every base page of a demoted piece turns out to be referenced, the piece is promoted again, so a superpage that was fully hot all along only paid for a temporary split.

Nothing about "active" is decided at the moment of the split. Splitting just makes the next sweep able to ask the question page by page instead of once for the whole superpage. (Paper §4.6, §5.1)

Which superpages get split, and which go straight toward eviction? The trigger is the daemon resetting a superpage's bit, which means it found the bit set: the superpage looked used, but the OS can't tell how much of it. That's the case that gets speculatively split. A superpage whose bit is already clear when the daemon returns wasn't touched at all for a full sweep, so every page in it is cold and it heads toward inactive and eviction like any other page. Eviction still works page by page, and evicting a page inside a superpage demotes it as a side effect, one size step at a time along the path to that page.

What if half of a demoted superpage is hot and half is cold? Each piece is judged separately; nothing forces them to share a fate. Repromotion is incremental: any aligned piece whose base pages are all referenced can be promoted to that piece's size, regardless of its neighbors. Take a 4MB superpage where the hot half is four of its eight 512KB pieces. After the split, the sibling 512KB pieces were never broken below 512KB, so the hot ones simply remain 512KB superpages, and hot pieces along the split path can climb back to 64KB or 512KB. The cold pieces show up unreferenced on the next sweep and drift toward eviction. The region can't return to 4MB while any of it is evicted, because promotion requires every base page to be present; it would need those pages to fault back in and be touched first.

Is this all only under memory pressure, and does the daemon keep evicting once pressure is gone? Speculative demotion and eviction both happen only under pressure; without it, superpages are typically promoted early in a process's life and only demoted at exit. Repromotion has no such condition and happens whenever a piece qualifies. The daemon doesn't evict everything it can in a pass: it works toward a goal and stops when the goal is met. In the paper's contiguity mode, the goal is restoring exactly the contiguity that recent failed allocations needed, moving only pages that contribute to it, and going back to sleep if it reaches the end of the list first. For ordinary memory pressure, FreeBSD's daemon similarly works toward a free-page target rather than a full sweep (general FreeBSD behavior, not stated in the paper). Pieces already split stay split and are judged by future sweeps. Pages moved to the cache list keep their contents and are reactivated, not re-read, if touched before their frames get reused. (Paper §4.6, §5.1, §6.8)

Mid-pass: the daemon splits the superpage at page 0, keeps going, and pressure ends before it gets back. Does it finish evicting there, or repromote because the memory is no longer needed? Neither, according to the rules the paper states; it doesn't describe this exact case, so this follows from them. Nothing undoes a demotion because pressure ended, and nothing evicts once pressure is gone. Each piece's fate falls out of two separate conditions. Eviction (and further speculative demotion) only happens under memory pressure, so with pressure gone the cold pieces are not evicted; they simply stay resident as base pages. Repromotion is driven by references, not by pressure: "incremental repromotions occur when all the base pages of a demoted superpage are being referenced." So pieces whose pages are all in use get promoted back whether or not pressure is still on, and pieces with cold pages stay split until those pages are touched again (then they can be repromoted) or pressure returns (then they can be evicted). The split at page 0 is simply a sunk cost, the kind of churn the paper acknowledges when it notes that under memory pressure "demotions and repromotions may happen several times in a process's life." One detail the paper leaves open is exactly when the repromotion check runs; the only promotion check it describes runs after a page fault is serviced. (Paper §4.6, §4.9, §6.8)

Separately, because there's only one dirty bit, writing back a superpage with even a single dirty base page would otherwise force writing back all of it. The system instead demotes a clean superpage the moment any process writes to it, keeping dirty tracking at base-page granularity, and only re-promotes once the whole thing is dirtied.

Walking through it with only 4KB and 4MB pages: does one write demote all 1024 entries, just the written page, or break something? It replaces the single 4MB mapping with all 1024 base-page entries, and nothing moves. A superpage is all-or-nothing in hardware: one TLB entry covers the whole aligned 4MB region with one dirty bit and one set of permissions, so there's no way to express "a 4MB superpage with one 4KB hole in it." Keeping 1023 pages in the superpage and splitting off only the written one isn't an option. With only two sizes there's no middle step either; on the Alpha, eviction-driven demotion steps down one size at a time (4MB to eight 512KB, and so on), but here the next size down is the base page. Nothing crashes, because demotion never changes where any address points: each of the 1024 new PTEs maps to the exact physical frame it already occupied inside the 4MB region. The translation is identical, just written as 1024 small entries instead of one big one. The real hazard is a stale 4MB TLB entry lingering alongside the new 4KB ones, so the OS invalidates the superpage's TLB entry (on a multiprocessor, on every CPU) before the faulting write is allowed to proceed.

The sequence: a clean superpage is mapped without write permission, so the first write traps into the OS. The OS demotes it to 1024 base PTEs, grants write permission to the one page being written and marks only that page dirty, and leaves the other 1023 clean and still write-protected. Each later write to one of them traps once and marks just that page dirty. When the page daemon later needs to evict, it writes back only the dirty 4KB pages, not 4MB. If all 1024 eventually become dirty, the region is promoted back to a 4MB superpage, since at that point the single dirty bit is no longer lying about anything. (Paper §4.6, §4.7)

Does this apply to anonymous pages or file pages? Both use the same mechanism, but the payoff is clearest for file-backed pages, and the paper's own evaluation (§6.7) is file-backed: it maps a 100MB file, reads every page so the region gets promoted, writes every 512th page, then flushes the file. Without demote-on-write that flush writes 512 times more data and runs over 20 times slower. Clean versus dirty only matters for a page that already has a copy on disk. A clean file page matches the file, so evicting it costs no I/O at all; only dirty ones must be written back. Fresh anonymous memory has no backing copy, so its first eviction has to go to swap whether or not the dirty bit is set; the clean/dirty distinction only starts saving I/O for anonymous pages that were swapped out and read back in, which are then clean relative to their swap copy until written again. (The paper doesn't separate the two cases explicitly; this is the general paging rule it relies on.)

6 · Scalability — where the design stays cheap, and where it doesn't

Most operations (lookup, overlap avoidance, counter updates) are O(1) or O(S) in the number S of distinct superpage sizes, and preemption is O(S·R), where R is the ratio between consecutive sizes. The exceptions are the page daemon's background scan and three routines on the critical path, promotion, demotion, and dirty/reference-bit emulation, which are O(size) because the Alpha's PTE-replication hardware requires touching every constituent base-page PTE individually. This is a hardware artifact, not a fundamental limit of the design — the paper notes that superpage-friendlier page table structures (e.g. clustered page tables) would remove it.

M1 · The hardware substrate: what a superpage physically is

The test machine is a Compaq XP-1000 with a 500MHz Alpha 21264: a fully associative TLB with 128 data entries and 128 instruction entries, page tables kept in memory and loaded into the TLB by firmware on a miss, 512MB of RAM, 64KB L1 caches and a 4MB direct-mapped L2. With 128 entries of 8KB, the TLB reaches just 1MB; with 4MB superpages the same 128 entries reach 512MB, all of memory.

Four hardware rules govern every decision that follows. A superpage must be one of the supported sizes. It must be contiguous in both virtual and physical memory. It must start at a multiple of its own size in both address spaces, which means a page's virtual offset and physical offset must agree modulo the superpage size. And its TLB entry carries only one reference bit, one dirty bit and one set of protections, so every base page inside must share the same protection and the OS can tell only whether some part was touched or written, not which part.

The Alpha implements superpages by PTE replication. The page table always keeps one entry per base page, even inside a superpage; each entry holds its own translation plus a page-size field. To make a 64KB superpage, the OS writes "64KB" into the size field of all eight PTEs of the aligned region; on a TLB miss the firmware loader reads that field and installs one entry covering the whole region. Promotion and demotion are therefore literally loops over PTEs: 8 writes for 64KB, 64 for 512KB, 512 for 4MB.

The Alpha also has no hardware reference or dirty bits; the OS emulates them by protecting a page so its first access or first write traps, recording the fact in its own structures, and lifting the protection. For a superpage that protection change has to be applied to every replicated PTE, which makes reference/dirty tracking another cost that grows with superpage size.

M2 · Free memory: the buddy allocator

Free physical memory is kept by a buddy allocator: free space is held as size-aligned blocks, a large block is split when a smaller one is requested, and when a block's buddies become free again they are merged back. (The paper cites Peterson and Norman's buddy systems [14] but does not say whether its blocks are powers of two or only the four page sizes; either way every block of a page size starts at a multiple of that size.) That merging is what lets freed pages turn back into a 64KB, 512KB or 4MB extent without any copying, and it is why breaking things into the next size down (rather than into base pages) loses nothing on the free side.

Two twists in this system. First, clean cache pages (unmapped, contents still valid) count as available and are coalesced together with truly free pages, but blocks containing them go to the tail of the allocator's lists, so free memory is handed out first and cached data survives as long as possible. If a cache page is referenced while it sits in a buddy list or inside a reservation, it is pulled out and reactivated; if it was inside a reservation, that reservation is preempted. Second, the authors' allocator ignores FreeBSD's hint to prefer pages that are already zeroed. That omission, not the superpage logic, explains the one benchmark that slowed down (mesa, 1.5%); measured on its own it costs 0.9% on average, 1.7% at worst. (Paper §4, §5.1, §6.3)

M3 · The population map, in full

The population map answers, for any memory object, "which of its pages already have frames, and how are they grouped?" It serves four purposes: on a fault, find the frame already reserved for this address; when reserving, avoid overlapping pages that already have frames or reservations; decide when a region is full enough to promote; and during preemption, tell which pieces of a reservation are empty, partial or full. Because it is consulted on every page fault, lookups have to be cheap.

Shape. One radix tree per aligned 4MB window of a memory object, with one level per page size. The root stands for the 4MB window; each of its R = 8 children stands for one 512KB slice; each of theirs for a 64KB slice; and the leaves are the 8KB base pages. So a full tree has 1 + 8 + 64 nodes above 512 page leaves. If the pages a node covers have a reserved extent of frames, the node points to that reservation and the reservation points back to the node.

Counters. Every non-leaf node keeps two numbers about its R children. somepop counts children whose region holds at least one populated page. fullpop counts children whose region is completely populated. Both run from 0 to R. At the lowest level, the children are single base pages, and a page is either empty or populated, so there somepop and fullpop are always equal. Higher up they diverge: somepop says "how many children have started," fullpop says "how many children are done."

Finding the tree. A hash table maps the pair (memory object, index of the window's first page within the object) to the root. On a fault the virtual address is rounded down to a multiple of 4MB, converted to that pair, hashed, and the walk starts at the root.

Laziness. Nodes are created only when a page under them is first populated, and a missing child is treated exactly like a child with both counters at zero. A sparse object therefore costs a few nodes, not a full tree.

Why updates stop unless a counter crosses 0↔1 or R−1↔R

This is the rule in §4.9 that's easy to read past: "upward propagation of the counters occurs only when somepop transitions between 0 and 1, or when fullpop transitions between R−1 and R." The reason is what a parent actually stores. A parent doesn't record its child's counts; it records two yes/no facts about the child, folded into its own counters: "this child has pages" (one unit of the parent's somepop) and "this child is full" (one unit of the parent's fullpop).

For a child node, "has pages" is true exactly when its own somepop ≥ 1, and "is full" is true exactly when its own fullpop = R (all R of its own children are full). So the only events that change what the parent knows are the moments those two facts flip: somepop going 0→1 (child just became non-empty) or 1→0 (just became empty), and fullpop going R−1→R (just became full) or R→R−1 (just stopped being full). Every other change, such as somepop going from 3 to 4, leaves both facts as they were, so the parent's counters are already correct and the update ends at that level.

When a flip does happen, the parent's counter moves by one, and the same test runs on the parent: did that ±1 make it cross 0↔1 or R−1↔R? If so, continue up; if not, stop. A page fault therefore walks up at most S levels and usually stops after one. Concretely on the Alpha: the very first page touched in a 4MB window flips somepop at the 64KB node, the 512KB node and the root; the second page in the same 64KB slice changes only the 64KB node; the eighth page of a 64KB slice flips that node's fullpop (7→8), which bumps the 512KB node's fullpop by one, which only propagates further if that was the 512KB node's eighth full child.

The four uses, step by step

Reserved-frame lookup (every fault). Hash to the root, walk down toward the faulting page. If a node on the path owns a reservation, the frame for this page is already decided: the reservation's first frame plus the page's offset inside the region that node covers. That fixed offset is what keeps virtual and physical alignment in step, so the region can later be promoted without moving anything.

Overlap avoidance (fault with no reserved frame). Walk down from the root and stop at the first node whose somepop is zero, or that doesn't exist. That node's region is the largest aligned region around the faulting page with no populated pages, and it can't contain a reservation either, because every reservation always holds at least one allocated frame (it was created by a fault, and preemption frees any piece left with none). Its size is the upper limit for the new reservation; the size policy from §4.2 can only lower it. If even the 64KB node has somepop above zero, the limit is a single base page.

Promotion decisions (after each fault is serviced). Walk down from the root and stop at the first node that is fully populated and backed by a reservation. Starting from the root means the largest qualifying size is found first. Only this one path is checked, and that is enough: the fault just populated page v, so the only regions whose status could have changed are the ones containing v, which are exactly the nodes from the root down to v (four on the Alpha: 4MB, 512KB, 64KB, and the page). Every other region is as full or as empty as it was before. At each node the test is cheap, because the counters already updated by this fault say whether its region is complete (its fullpop equals R). The attempt succeeds only if the faulting process maps every page in that region with the same protection and the same dirty state; otherwise nothing happens and a later fault may retry.

Preemption assistance. A preempted reservation follows its back pointer to its node, and that node's children answer the sorting question directly: a child with somepop = 0 (or absent) is an empty piece to free, a child that is full is complete and leaves the lists, and anything in between is a partial piece to reinsert.

M4 · The page-fault path, end to end

Every mechanism above is invoked from one place: the page-fault handler. The sketch below is the order of operations assembled from §4.1, §4.2, §4.5, §4.8, §4.9 and §5.1; the paper describes each step but never lists them in one place.

Two consequences fall out of this layout. First, the expensive decision (how big, from where) is made once per region, at its first touch; every later fault inside the reservation takes the short path. Second, promotion is attempted only right after a fault, so a region becomes a superpage the moment its last page is faulted in, never earlier and never by background work.

M5 · Reservation lists and preemption, precisely

Which list a reservation is on. There is one list per page size except the largest: on the Alpha, an 8KB list, a 64KB list and a 512KB list. A reservation sits on the list for the largest free extent it could hand back if preempted. Since every reservation holds at least one allocated frame, that is at most one size below its own: a 512KB reservation can yield at most 64KB pieces, a 4MB reservation at most 512KB pieces. It can be lower: a 4MB reservation in which every 512KB slice already holds a page cannot yield any free 512KB extent, so it belongs on the 64KB list. That's why the paper says the 64KB list "may contain reservations of size 512KB and 4MB." As pages fill in, a reservation's best possible yield can only shrink, so by this definition it would move to a smaller list over time; the paper states the membership rule but not the bookkeeping that keeps it true, so that movement is an inference.

Order within a list. Each list is sorted by the time of each reservation's most recent page allocation, so the head is the reservation that has gone longest without gaining a page. Preempting the head implements the policy from §4.3: reservations that are going to be used tend to fill quickly, so one that has been idle is the best guess for one that never will.

The fallback chain (the paper's own example). A fault wants a 64KB reservation. Ask the buddy allocator for 64KB. If that fails, preempt the head of the 64KB list, which by construction yields at least one free 64KB extent. If that list is empty, preempt from the 512KB list. If that is empty too, give up on a superpage and fall back to a single base page: the buddy allocator first, the 8KB list as the last resort.

Breaking a reservation. The preempted reservation is cut one size step down, not into base pages; empty pieces go to the buddy allocator, partially populated pieces become smaller reservations and go back on the appropriate list (at its head), and full pieces leave the lists. The worked example and diagram in §3 above walk through a 512KB case. Cost: a preemption touches up to R pieces per level across up to S levels, O(S·R), the most expensive bookkeeping operation in the design.

Measured. With only 4MB of contiguous memory available and a process touching memory at a 4MB stride, the system settles into one preemption every seven allocations. Each preemption cuts a reservation into 8 pieces: one stays reserved around the page that made the original reservation, one is taken for the page now faulting, and six return to the free lists. The process slowed by 1.1%. (Paper §4.3, §4.8, §6.6, §6.8)

M6 · Promotion: exact conditions and cost

A region is promoted to size X when all of these hold: it is an aligned X-sized region; every base page in it is populated (its population-map node is full); its frames come from one reservation, so they are contiguous and aligned; and the faulting process maps all of its pages with the same protection and the same dirty state. The check runs after each fault, starting from the largest size, so a region that just completed a 512KB slice is promoted to 512KB directly even if some of its 64KB pieces were promoted earlier. Mechanically, promotion is the PTE loop from M1.

Why "every page populated" and not a lower threshold. Promoting earlier would require the OS to populate the region's untouched pages itself, since a superpage maps all of them. That inflates the application's memory footprint, and it changes OS semantics slightly: accesses to pages the program never allocated would no longer fault, so some invalid accesses would go uncaught. The authors accept the cost visible in Table 2 (small programs can't fill the larger sizes) because most applications populate their address space densely and early.

Cost. With no memory pressure, a region is typically promoted step by step early in the program's life and demoted only at exit, which works out to O(S) per page, negligible in every benchmark. The worst case is a synthetic adversary that allocates memory, touches one byte per page and frees it, so the TLB never pays back: an 8.9% slowdown, of which 7.2% is the Alpha's PTE replication (each PTE is rewritten six times: three incremental promotions, 8KB→64KB→512KB→4MB, and three demotions on the way back) and 1.7% is population-map maintenance. With the same allocation and promotion work but the benefit factored out (writing the new size into unused PTE bits instead of the real field), realistic workloads lose at most 2%, about 1% on average. (Paper §4.5, §4.9, §6.4, §6.6, §6.8)

M8 · Dirty superpages and the hash-digest alternative

The problem: one dirty bit per superpage means a superpage with one modified page must be written out whole. The adopted fix is demote-on-write (M7). Measured on a program that maps a 100MB file, reads every page (so the region is promoted), writes every 512th page and flushes: without demote-on-write the I/O volume is 512 times larger and the run is more than 20 times slower. The price is that a process that never writes to every page of a region keeps that region in base pages once it writes at all; the authors chose that to keep the pathological case cheap.

The alternative they built and rejected: when a clean page is read from disk, record a 160-bit SHA-1 hash of its contents. Partially dirty regions may then be promoted (treating every page as dirty), and at write-back time each page's hash is recomputed and only pages whose hash changed are written. A collision has probability about one in 280, far below the odds of a hardware fault, so it is safe; but hashing cost up to 15% on disk-intensive programs and 60% in the worst case (a large sequential read on a saturated CPU). Two optimizations were left as future work: hash only once a superpage is actually partially dirty (fully clean, fully dirty and unpromoted pages need no hashes), and move hashing off the critical path into the idle loop. (Paper §4.7, §6.7)

M9 · The contiguity-aware page daemon

Reservations only help if aligned free extents exist, and ordinary workloads destroy them fast: running grep, emacs, netscape and a kernel build on a freshly booted machine, the authors found every free region larger than 64KB gone within about 15 minutes, even with 360MB of the 512MB free. Preemption reclaims contiguity sitting inside reservations; the modified page daemon reclaims contiguity held by other processes' idle pages.

Its three changes, in mechanism terms. (1) Cache pages become part of free memory for the buddy allocator, merged into larger blocks but kept at the tail of the free lists. This is what makes the daemon's choices matter: moving a particular inactive page to the cache can complete an aligned free extent. (2) The daemon wakes not only on memory pressure but whenever an allocation of the preferred contiguous size fails. Its goal is then specific: restore the contiguity the requests that failed since its last wake-up would have needed. It walks the inactive list and moves to the cache only pages that contribute to that goal, and goes back to sleep if it reaches the end of the list first. (3) When every process has closed a file, the file's clean pages move to the inactive list immediately, rather than staying active indefinitely when there's no pressure, giving the daemon more candidates.

The trade-off is deviation from approximate LRU: the more aggressively contiguity is restored, the more often a page is evicted that LRU would have kept. The design tries to restore the most contiguity while disturbing the fewest pages.

How well it works

The authors fragment memory by replaying a web-server trace (238MB working set, file pages left scattered among active, inactive and cache pages), then run FFTW four times, comparing a naive "cache" scheme (just treat cache pages as free and coalesce them) against the full "daemon" scheme (contiguity-aware replacement plus wired-page clustering). The naive scheme never produces a single 4MB superpage, even with 47MB free on the first run and 290MB on the rest, because the free memory is interleaved with active, inactive and wired pages. The daemon scheme recovers 20 of the 60 requested 4MB regions on the first run, then 35, 38 and 40, reaching near-optimal performance (a 55% speedup) within two runs; rerunning the web server afterwards costs it only 1.6%.

To measure contiguity over time they score every base page 1, 2 or 3 points if it lies in a free, aligned 64KB, 512KB or 4MB region, normalized to an empty machine. The naive scheme recovers only 8.8%, the daemon scheme 42.4%; FFTW finishes at 8.5 minutes versus 9.8. Afterwards the naive scheme has permanently lost 54% of contiguity, mostly to scattered wired pages, and the daemon scheme 13%, because the remaining active and inactive pages ended up spread over 54 4MB chunks instead of the 22 they started in. In a concurrent test, a helper that maps, touches and unmaps 1MB five times a second needs about 3000 512KB extents while the web server runs: stock FreeBSD satisfies 3.3% of them, the contiguity-aware daemon 29.9%, at 0.8% daemon overhead and 3% web-server slowdown. (Paper §6.5)

M10 · Wired page clustering

Wired pages hold kernel data structures and can never be paged out, so each one permanently disqualifies the 4MB chunk it sits in. At boot they are clustered, but as the kernel allocates while other programs run they scatter, and on the 512MB machine most 4MB chunks soon held at least one, at which point large-superpage contiguity is unrecoverable. The fix is to recognize pages that are about to be wired for the kernel's internal use and allocate them from pools of contiguous memory, so they fragment no more chunks than necessary. (Paper §5.2)

M11 · Multiple mappings of the same file

A file's pages sit in fixed frames, so their physical alignment is decided once. If two processes map the file at virtual addresses that differ by, say, one base page, at most one of them can match that alignment, and only that one can build superpages for the file. Most programs don't ask for a specific address when they map a file, which leaves the choice to the kernel; the system picks a virtual address aligned to the largest superpage smaller than the mapping, keeping every mapping superpage-compatible. (Paper §5.3)

M12 · Implementation and cost model

The design was built into FreeBSD 4.3 as a loadable kernel module of about 3,500 lines of C, plus hooks that call into the module at four places: page faults, page allocation and deallocation, the page daemon, and the physical-mapping layer (to demote when protections change and to track dirty/modified bits of superpages).

Most operations cost O(1), or O(S) in the number of distinct superpage sizes, except preemption at O(S·R), where R is the size ratio (8 on the Alpha, never more than 8 on modern processors). Only four routines take time proportional to a superpage's size in base pages: the page daemon's scan (in the background, off the critical path), and promotion, demotion and reference/dirty-bit emulation, all three because of the Alpha's PTE replication. The authors expect superpages far beyond 4MB to need page-table structures friendlier to superpages, such as clustered page tables.

Why misses got more expensive, not just more frequent. Two trends the paper names. Reach arithmetic. Reach = entries × page size. With the Alpha's 128 data-TLB entries: 8KB pages reach 1MB, 64KB pages 8MB, 512KB pages 64MB, 4MB pages 512MB, which on the test machine is all of RAM (§6.1). The rejected fix: bigger base pages. Using, say, 64KB or 4MB as the only page size raises reach but causes internal fragmentation (partly used pages), which brings on memory pressure early, and raises paging I/O because every transfer is page-sized (§2.1). Does reserving or promoting change how much memory a process uses?

The paper does not report a side-by-side measurement of resident memory with and without superpages. What it does give is enough to state precisely how each part of the design touches memory use. Separate three quantities: frames that hold the program's data (resident), frames set aside but not mapped (reserved), and the granularity at which memory is mapped and paged.

  • Resident pages. A page becomes resident only when the program faults on it; the reservation maps "this page only" (§4.1). Promotion requires every base page of the region to be populated by the application (§4.5), so promotion itself never makes a page resident. The two designs the paper contrasts do add resident pages: eager promotion populates the surrounding pages at the first fault (§3.1), and a lowered promotion threshold would have to "populate the entire region, which could artificially inflate the memory footprint" (§4.5).
  • Reserved frames. They hold no data and are not mapped, but while reserved the buddy allocator cannot hand them to anyone else. They return only by preemption, which happens when an allocation of the desired size fails (§4.3), or when the reserved region fills. The paper does not say whether reserved frames are counted as free when the page daemon measures memory pressure.
  • Mapping and paging granularity. Superpages change how memory is mapped, not which frames hold data. Paging stays at base-page granularity because eviction demotes along the path to the victim page (§4.6) and a clean superpage is demoted on its first write (§4.7); under pressure, speculative demotion lets the cold parts of a superpage be found and evicted (§4.6).
  • What the evaluation reports instead. Superpage counts at peak memory use (Table 1, from which a footprint can be computed but not compared with the base kernel), runtime, TLB-miss reduction, the contiguity metric of Figure 5, and the overhead experiments of §6.6.

What a single-size system changes mechanically. Reservations and promotions can only be of that one size, so a program gains only where it fully populates aligned regions of exactly that size, and its reach is 128 × that size. Combining the reach figure below with Table 1's footprints explains most rows; working sets are smaller than footprints, so treat footprint as an upper bound on what must be covered.

M17 · Figures 4 and 5: does the benefit survive fragmentation?

How memory is fragmented first. A web server replays the Rice CS department trace. Its file-backed pages stay in memory and leave little contiguity, and its access pattern interleaves active, inactive and cache pages across physical memory (§6.5). Two schemes are then compared. Cache: cache pages are treated as available and coalesced into the buddy allocator, and nothing else. Daemon: the full contiguity-aware page replacement of §5.1 plus wired-page clustering (§5.2).

Figure 4 plots FFTW's speedup over the unmodified kernel for four back-to-back runs after the fragmenting web-server run, with a horizontal line at the best case (Table 1's 1.549). Under the cache scheme FFTW never gets a single 4MB superpage, so every run is near 1.0, even though 47MB is free in the first run and 290MB in the later ones: the free memory is fragmented by active, inactive and wired pages. Under the daemon scheme the first run wakes the page daemon on contiguity failures, and it recovers 20 of the 60 4MB regions FFTW requests; later runs get 35, 38 and 40, and performance is "near-optimum within two runs, i.e., a speedup of 55%" (§6.5). Run to run improvement comes from the daemon's goal-directed passes plus the web server's closed files, whose pages the modified daemon treats as inactive (§5.1, §6.5). Afterwards the web server is rerun and is only 1.6% slower than on the base system.

Figure 5's metric. Each base page scores 1, 2 or 3 points if it lies in a free, contiguous, aligned 64KB, 512KB or 4MB region, and the sum is normalized to the score of a machine with every page free (§6.5). So a machine whose free memory consists only of isolated 64KB chunks can score at most about a third (inference from the definition, assuming each page scores only for the largest such region). The metric counts only free and cache memory as available, so it is "unfavorable to the daemon scheme": inactive pages that the daemon could move to the cache do not count.

Reading the curves (the corrected redraw is in §4 above). Neither scheme starts at 100%: some memory is in use at boot, and the cache scheme starts 5% lower because its wired pages are not clustered. For about five minutes the web server drives contiguity to zero. Then the four FFTW runs: contiguity appears only in the short gaps between runs, when one FFTW exits and the next has not yet consumed it. The cache scheme's bursts recover only 8.8% of the system's contiguity; the daemon scheme's reach as much as 42.4%. FFTW finishes at 8.5 minutes under the daemon scheme and 9.8 minutes under the cache scheme, and the daemon curve stays high once FFTW is done.

Afterwards: how much is gone for good? A synthetic program then uses enough anonymous memory to free as many pages as possible when it exits. The cache scheme has lost 54% of contiguity, "mostly due to scattered wired pages". The daemon scheme cannot recover 13%, because the few active and inactive pages left are spread over 54 4MB chunks, against 22 chunks on the freshly booted machine; part of that 13% is inactive pages the daemon could still reclaim, so the long-term loss is "bounded only by the number of active pages" (§6.5).

The concurrent experiment tests the replacement policy alone, with superpage promotion disabled. The web server is warmed with 100,000 requests and timed over the next 100,000, while a dummy program maps, touches and unmaps 1MB five times a second, about 3000 requests for 512KB contiguous chunks in all (it replaces FFTW so that CPU competition does not distort the timing). Because the web server keeps its active files open, the daemon cannot treat their pages as inactive, and without compaction only limited contiguity can be restored. Stock FreeBSD satisfies 3.3% of the chunk requests, the contiguity-aware daemon 29.9%; the restoration work costs 0.8%, and the web server runs an additional 3% slower because replacement deviates from approximate LRU (§6.5).

What these experiments do not show (this guide's reading). Only one fragmenting workload is used; there is no comparison against relocation or compaction; and the sequential experiment favors recovery because the fragmenting process closes its files and exits before FFTW needs memory, which is exactly the case where change (3) of §5.1 applies.

M18 · The adversary experiments, step by step

§6.6 builds three synthetic worst cases, each maximizing one cost of the design while giving it no benefit, then measures overhead on the real benchmarks.

1. Incremental promotion overhead. The program allocates memory, touches one byte in each page, and frees it. Each translation is used once, so the TLB never pays back, but every region still climbs 8KB→64KB→512KB→4MB as its pages are touched, and is torn down again when it is freed. Slowdown: 8.9%. Of that, 7.2% is PTE replication: each PTE is traversed six times, once for each of the three incremental promotions and once for each of the three incremental demotions. Per 4MB region that is 64 promotions of 8 PTEs, 8 of 64 and 1 of 512, i.e. 512 PTE writes per level and 3 per PTE, plus the same on the way down (this guide's arithmetic). The other 1.7% is mainly population-map maintenance (§6.6). With a page table that stores one entry per superpage, the replication part would not exist (§6.8, M12).

2. Sequential access overhead. Touching pages in order is common, but real programs use every byte of a page, which spreads the same per-page costs over far more work. cmp comparing two identical 100MB files through memory mappings slows by less than 0.1%.

3. Preemption overhead. Only 4MB of memory is free and contiguous, and a process touches memory with a 4MB stride, so every touch wants a new 4MB reservation that cannot be had. The paper reports one preemption every seven allocations; each preemption splits a reservation into 8 pieces, of which one stays reserved with the page that made the original reservation, one is taken for the page being allocated, and 6 go back to the free list. Slowdown: 1.1%. The trace below reconstructs how that steady state arises from the rules of §4.3 and §4.8; the paper states only the outcome.

4. Overhead in practice. All the benchmarks are rerun with every allocation and fragmentation-management step active, but the benefit removed: regions are not really promoted; instead the new size is written into an unused part of each PTE so the promotion cost is still paid. Result: at most 2% slower, about 1% on average (§6.6).

Which costs have no adversary (this guide's reading). None of the four experiments drives repeated speculative demotion and repromotion under sustained memory pressure, the cost §6.8 says "may become significant for very large superpages" because of linear PTE replication. The dirty-superpage experiment of §6.7 (M8) is the closest relative: it shows the cost avoided by demote-on-write, not the cost of the mechanism.

M19 · From the lecture: modern hardware, modern OSes, ASLR and guard pages

Everything in this section comes from the 10/13 slides, which go beyond the paper; explanations marked as this guide's reasoning connect the slide items back to the paper's rules.

"Except for a few embedded CPUs, hardware reloaded TLBs are used; page table format dictated by hardware." The Alpha's software-reloaded TLB let firmware define the page-table format, and the paper's superpages ride on that format (PTE replication, M1). With a hardware page walker, the OS cannot invent a format, and it never sees a TLB miss (this guide's reasoning): that removes both PTE replication and any Romer-style design that counts misses in a software handler (M14).

"Multiple page sizes supported by truncating page table walk." The slide's examples: x86-64 with 4KB, 2MB and 1GB pages; ARM64 with a 4KB, 16KB or 64KB base page and 3 levels of page table (example on the slide: Apple 16KB, 512KB, 32MB); RISC-V the same as x86-64. Mechanism, as standard architecture background: an upper-level entry can be marked as a leaf, so the walk stops early and the remaining address bits become the page offset. On x86-64 each level has 512 entries, so the sizes are 512× apart, versus 8× on the Alpha; there is no intermediate size between 4KB and 2MB, so incremental promotion through several sizes (§4.5) has fewer steps available (this guide's reasoning).

"CPUs can count TLB misses but not point OS at the pages." Performance counters give how many misses occurred, not which pages caused them. The paper's own evaluation had a coarse version of this limit, a counter that ticks once per 512K misses (§6.4, M15). It is also why a reservation design, which decides from page-fault events and population counts alone, fits modern hardware better than a design that needs per-region miss counts (this guide's reasoning).

OSes on the slide. Linux: transparent and explicit large pages (4KB, 2MB, 1GB). Windows: explicit only (4KB, 2MB typical, 1GB optional). macOS: no explicit interface, some internal use of large pages. "Explicit" is the non-transparent model of the transparency slide: the application asks for the large page.

"Random issues: Address Space Layout Randomization (ASLR); Guard pages." The slide lists only the two terms. How each collides with the paper's rules (this guide's reasoning): ASLR randomizes where regions start, but a superpage needs the virtual and physical offsets to agree modulo its size (§2.2), and the multiple-mappings fix relies on the kernel choosing an aligned address (§5.3); randomizing at base-page granularity removes that choice, while randomizing at superpage granularity keeps it with fewer random bits. A guard page is a page left unmapped or inaccessible next to a stack or allocation so that overruns fault; because all base pages in a superpage must share one protection (§2.2), an aligned region containing a guard page can never be fully populated with uniform protection, so it cannot be promoted, and changing protection on part of an existing superpage forces a demotion (§4.6).

M20 · Connections to other CS240 papers

ESX Server (Waldspurger, OSDI 2002, the same conference). Three mechanical links. (1) Pinned pages. The balloon driver inflates by allocating pinned guest pages through get_free_page() or MmProbeAndLockPages() (ESX §3.2). Pinned pages, like the wired pages of §5.2, cannot be evicted or moved, so wherever they land they block contiguity recovery. (2) An extra translation layer. ESX's pmap maps each guest "physical" page (PPN) to a machine page (MPN), and it can remap one PPN by changing its entry "in a manner that is completely transparent to the VM" (ESX §2). The hardware TLB caches guest-virtual to machine translations from the shadow page table. The superpage rules (contiguous, aligned, one protection and one dirty/reference set per entry; §2.2) apply to whatever range the hardware entry maps, which under virtualization is a machine range; whether a guest's contiguous PPN range is contiguous in machine memory depends on how the pmap assigned MPNs. (3) Coloring. ESX preserves guest page coloring when it allocates machine pages ("distinct PPN colors are mapped to distinct MPN colors", ESX footnote 2); this paper notes that physically contiguous superpages make coloring automatic (§6.3). ESX's per-page mechanisms (content-based sharing with copy-on-write, ballooning, swapping) all act on single 4KB pages, which is the granularity a superpage mapping cannot express; M7's demotion triggers are the paper's version of that same conflict.

Adams & Agesen, software versus hardware virtualization (lecture 10/15). Their paper describes shadow page tables kept coherent by tracing guest page-table writes, and the nested-paging hardware (AMD NPT, Intel EPT) that replaces them, where "For an M-level guest page table on an N-level nested page table, a worst-case TLB miss requires MN memory accesses to satisfy" (§7.4 of that paper). The connection here is the cost model of M13: the more a TLB miss costs, the more TLB reach is worth, so superpages in either dimension of a nested walk reduce the number of these expensive walks (this guide's reasoning; that paper argues the microarchitectural techniques used for ordinary paging, such as large TLBs and caching, will contain the cost).

Worked examples

Four traces using the paper's actual measurements.

① Best-case speedup: why Matrix hits 7.5×

Table 1 reports a 7.546 speedup for the 1000×1000 non-blocked matrix transpose. Why so extreme compared to, say, gzip's 1.007?

  1. Matrix transpose has terrible locality: its access pattern produces roughly one TLB miss for every two memory accesses under base pages — nearly worst-case TLB pressure.
  2. Superpages eliminate almost all of those misses: the paper reports a 99.47% data-TLB miss reduction for Matrix — virtually every miss it used to take, it no longer takes.
  3. Contrast with gzip: only 80.00% miss reduction and a 1.007 (0.7%) speedup — gzip's working set was already mostly within reach of the base-page TLB, so there was little to gain.
  4. Takeaway: speedup tracks how TLB-miss-bound the original workload was, not how big the app is. FFTW (99.59% reduction) gets 1.549×; Web (only 16.67% reduction, due to many small files) gets a modest 1.019×.
🍯
Insight: superpages are a targeted fix for TLB-miss-bound workloads specifically — pointer-chasing, streaming, and strided-access codes benefit most; already cache/TLB-friendly codes see little.

② Picking the right superpage size — why "all sizes" beats any single size

Table 2 shows mcf: 1.24× with 64KB-only, 1.31× with 512KB-only, 1.22× with 4MB-only, but 1.68× when the system picks per-region.

  1. Single-size systems force a compromise: forcing 4MB everywhere can waste memory on small regions (internal fragmentation) or fail to find contiguous 4MB extents; forcing 64KB everywhere caps TLB coverage gains for regions that could use bigger pages.
  2. mcf's different regions have different natural sizes: parts of its address space end up best served by different sizes, so no single size is right everywhere. (The paper says the system "selects the best size for every region of memory" but doesn't break down which parts of mcf got which size; the 64KB/512KB/4MB split is the guide's reading, not a reported measurement.)
  3. Letting the allocator choose per-region (the "All" column) lets each part of the address space get its best size independently, so the combined speedup (1.68×) exceeds any single-size result.
  4. Corroboration: Table 3 shows mcf's TLB miss reduction jumps from 84.18% (best single size, 512KB) to 99.97% when all sizes are available — the remaining single-size misses come from regions poorly matched to that one size.

Is "region" here the VMA? Close, but finer. The paper's unit is the memory object: a contiguous range of virtual address space holding one thing, such as a process's code, data, heap, or stack segment, or an mmap'd file. In Linux terms that's roughly a VMA (in FreeBSD, a map entry plus the vm_object behind it). The object sets the outer boundary: a superpage never spans two objects, which is exactly why the Web benchmark gains little, since it touches many small files and no superpage can straddle them. But the size decision isn't made once per object. It's made at each fault, for the aligned extent containing the faulting page, so one object routinely ends up with a mix of sizes: its tail can't fit a full aligned 4MB extent, a heap's early faults get small reservations because the cap is the heap's size at that moment, a partly populated reservation sits as some 64KB or 512KB superpages until it fills, and if contiguous memory is short the allocator falls back to a smaller extent. So "region" in this example means an aligned chunk inside an object, and "per-region" means per fault, not per VMA. (Paper §2.3, §4.2, §4.5, §6.2, §6.4)

The odd one out: FFTW. Its row looks nothing like mcf's. Speedup is 1.01 with 64KB pages only, 1.00 with 512KB only, then 1.55 with 4MB only, the same as with all sizes; TLB miss reduction is 7.41%, 7.41%, 99.59%. Making pages 8 times bigger (64KB to 512KB) buys nothing, and 4MB buys almost everything. The paper only notes that "there is almost no speedup if 4MB pages are not supported"; the explanation below is this guide's reading, assuming FFTW's default 16-byte double-precision complex numbers.

The input is a 200×200×200 grid: 8M elements, about 128MB. A 3D transform runs 1D transforms of 200 elements along each axis in turn. Along the fastest axis consecutive elements are 16B apart, along the middle axis 200×16B = 3.2KB apart, and along the slowest axis 200×200×16B = 640KB apart. So a single transform along the slowest axis reads 200 elements of 16 bytes each, spread 640KB apart across the whole 128MB array, and the pass repeats that for all 40,000 such columns.

  • 64KB or 512KB pages: both are smaller than the 640KB stride, so every element of a transform sits on a different page. One transform touches 200 distinct pages, more than the TLB's 128 data entries, so it misses constantly no matter which of the two sizes is used; that's why both give the identical 7.41% (what's saved is presumably the misses from the other two axes and the rest of the program, small next to this axis).
  • 4MB pages: now about 6 elements share each page, and the entire 128MB array is only 32 pages, which fits easily in 128 TLB entries. Every page a transform needs is already mapped, so the misses nearly vanish.

Two conditions have to hold together: the page must be larger than the stride, so neighbors in a transform share pages, and the number of pages the access sweeps must fit in the TLB. Only 4MB meets both, which is why FFTW is all-or-nothing and why it shows up in Table 1 with 60 superpages of 4MB. It's a large-stride pattern: few bytes used per page touched, many far-apart pages per short burst of work.

💡
This is the direct argument for supporting multiple superpage sizes rather than picking one "good enough" size system-wide — heterogeneous access patterns need heterogeneous page sizes.

③ Sustained performance: FFTW after web-server fragmentation

After a fragmenting web-server run, FFTW is executed four times in sequence. How does the contiguity-aware daemon recover performance run over run?

  1. Run 1: only 20 of the 60 requested 4MB regions are obtained — the daemon has just started restoring contiguity reactively.
  2. Run 2: 35 of 60 4MB regions obtained — each exit of FFTW releases contiguity the daemon can now supply to the next run.
  3. Runs 3–4: 38, then 40 of 60 — approaching (but not fully reaching) the best-case count. In this scheme wired pages are clustered; what stays scattered are the remaining active and inactive pages, which at the end of the experiment are spread over 54 4MB chunks instead of the 22 they occupied after boot (§6.5).
  4. Net effect: FFTW converges to near-optimal performance (55% speedup) within two runs, rather than needing a full reboot to see any benefit.
🍯
Insight: the system doesn't need pristine memory to deliver superpage benefits — it needs a policy that actively and repeatedly claws back contiguity as workloads come and go.

④ The cost of demote-on-write, quantified

A test program maps a 100MB file, reads every page (triggering promotion), then writes to just 1 in every 512 pages. What's the I/O cost with and without demote-on-write?

  1. Without demote-on-write: the single dirty bit forces the OS to treat the entire superpage as dirty, so write-back flushes all 512 base pages for each superpage even though only 1 was actually modified.
  2. 512× more data written than necessary — exactly matching the 1-in-512 write ratio in the test.
  3. Measured penalty: the paper reports over a 20× slowdown in running time from this superfluous I/O. The paper does not explain why the slowdown is smaller than the 512× I/O ratio; a plausible reading (this guide's, not the paper's) is that the run also includes reading the 100MB file and other work that demote-on-write does not change.
  4. With demote-on-write: the superpage splits back to base pages the instant the first write occurs, so only the genuinely dirty base page needs to be written back.
💡
This is the clearest illustration in the paper of how a single coarse hardware bit can turn a performance win (superpages) into a severe loss if the OS doesn't compensate for it.

Problem 1 · easy
An application streams through a 100MB array once, touching each page exactly once, then exits. Should the OS aggressively promote superpages for it?
Show answer
Not particularly beneficial. Superpages mainly pay off by amortizing the fixed cost of a TLB miss over more subsequent accesses to that same mapping — but a one-shot linear scan already touches every byte of each page before moving on, so the one-time TLB fill for that page is already spread over a full page's worth of useful work, and by the time an aligned extent is fully populated (and eligible for promotion) the scan has typically already swept past it, leaving no future accesses left to benefit from the bigger TLB entry. Aggressively reserving large contiguous extents for this pattern also ties up contiguity other processes could use, for little payoff.Misconception: that the lack of benefit is simply because "each page is only touched once," implying reuse of the identical page is what superpages need. It isn't quite that — a superpage TLB entry can still cover other, not-yet-touched base pages within the same scan. The sharper contrast the paper draws is between touching one byte per page (its adversarial workload, where promotion/demotion overhead dominates) versus touching every byte of each page (ordinary sequential access, where that same fixed overhead is diluted across far more useful work).
Problem 2 · medium
Why does the preemption policy choose the reservation whose most recent allocation happened least recently, rather than, say, the one with the fewest pages populated?
Show answer
Recency of last allocation is a better predictor of future use than current population count. A reservation with few pages populated but a very recent allocation is likely mid-fill and will probably need the rest soon; a reservation untouched for a while — even if partially full — is less likely to ever complete. The paper explicitly frames this as: "useful reservations are often populated quickly."Misconception: that "least populated" is the natural signal to preempt. Population level alone can't distinguish "just started, about to fill up" from "abandoned."
Problem 3 · medium
Why does the system promote only fully-populated aligned extents, rather than promoting as soon as, say, 50% of the pages are touched?
Show answer
Promoting a partially-populated extent would require the OS to also populate (e.g., zero-fill) the untouched pages to satisfy the superpage's contiguity/validity requirements — artificially inflating the application's memory footprint and increasing paging traffic for pages the app never actually asked for. The paper observes that most applications populate their address space densely and early, so waiting for full population rarely delays promotion much in practice.Misconception: that earlier promotion is strictly better. Earlier promotion at a population threshold trades memory footprint inflation for slightly faster TLB benefit — the paper judges that trade not worth it.
Problem 4 · hard
Two processes map the same file at virtual addresses differing by exactly one base page. Can both use superpages for that mapping? Why or why not, and how does the system usually avoid this?
Show answer
No — at most one of them can, because a superpage requires its virtual address to have the same alignment as its physical address, and the two processes' virtual addresses can't both be superpage-aligned to the same physical pages if they differ by less than a superpage size. The paper's fix: since applications usually don't specify an address when mapping a file (letting the kernel choose), the kernel deliberately picks virtual addresses aligned to the largest usable superpage size, so all processes mapping that file get compatible alignment.Misconception: that this is purely an application bug. It's a fundamental consequence of the hardware's alignment requirement for superpages, best avoided at the kernel's address-assignment policy level.
Problem 5 · medium
The "adversary" experiment allocates, touches one byte per page, then deallocates — rendering every TLB translation useless. It shows an 8.9% slowdown, of which 7.2 points come from one specific hardware quirk. What is it, and why does it dominate?
Show answer
PTE replication on the Alpha: each promotion or demotion requires updating the page-size field of every constituent base-page PTE. Because this adversary triggers three incremental promotions followed immediately by three incremental demotions (since the memory gains no reuse benefit before being freed), each page table entry gets touched six times — all pure overhead with zero payoff, since the TLB is never actually reused. The remaining 1.7% comes from population-map bookkeeping.Misconception: that the population-map machinery is the main cost. The dominant cost is a hardware artifact (PTE replication), not the OS's own bookkeeping structures.
Problem 6 · hard
The paper reports mesa slows down by ~1.5%, the only benchmark to regress. Is this due to the superpage mechanism itself? Explain what the actual cause was.
Show answer
No — it's an implementation gap unrelated to superpage logic. FreeBSD's normal allocator can preferentially hand out already-zeroed pages when a page needs zero-filling (avoiding a zero-fill at fault time), but the paper's buddy allocator implementation ignores this hint. The authors measured this omission alone costs an average 0.9% (max 1.7%) penalty across benchmarks — enough to explain mesa's small regression, not any inherent cost of superpage management.Misconception: that any regression in the results indicts the core design. Here it's flagged and attributed to a specific, fixable implementation shortcut, not a fundamental tradeoff.
Problem 7 · easy
Why does the paper's page daemon move a file's cached pages to the inactive list as soon as the file is closed by all processes, rather than waiting for real memory pressure?
Show answer
Because inactive pages are the daemon's raw material for restoring contiguity — the more candidates on the inactive list, the more likely a useful contiguous region can be recovered without touching genuinely active pages. Under default FreeBSD behavior, a page from a closed file could remain "active" indefinitely if there's no memory pressure, denying the daemon a cheap, low-cost source of reclaimable contiguity.Misconception: that this is purely a caching-policy decision unrelated to superpages. It's specifically motivated by the goal of keeping the contiguity-restoration pool well-stocked.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the single biggest design choice in this paper?▾
Reservation-based allocation — grabbing a large, contiguous, aligned physical extent speculatively at first touch, so superpages can form later with zero page-copying. Everything else (preemption, incremental promotion, the daemon) exists to make that initial choice sustainable over time.
Q2Why not just always use large base pages instead of variable superpages?▾
Large fixed base pages cause internal fragmentation for small objects (wasted space inside partly-used pages) and increase paging I/O granularity, since every page fault now moves a much bigger chunk to/from disk. Superpages let the OS use large pages selectively — only where a region is dense enough to benefit — while small objects keep small base pages.
Q3How does the OS decide what superpage size to try for first?▾
For fixed-size objects (code, mmap'd files), it's the largest aligned superpage that fits inside the object without overlapping existing allocations. For growable objects (heap, stack), it's the largest aligned superpage that fits the object's current size — deliberately conservative, so small, never-grown objects don't waste large reservations.
Q4What happens if the system guesses too large a superpage size?▾
The reservation can later be preempted (broken down and reclaimed) if memory pressure or fragmentation requires it — no harm done beyond the reservation being wasted until preempted. Guessing too small is worse: it can't be corrected without relocating (copying) pages, which the whole design tries to avoid.
Q5Does this design need special hardware support?▾
No — that's a stated advantage over approaches like partial-subblock TLBs or address-remapping memory controllers, which require specific, not-yet-commercial hardware. This design works with the reference bit, dirty bit, and multiple page sizes that most general-purpose processors already provide.
Q6How expensive is the mechanism when superpages don't even help?▾
Overhead in realistic scenarios averages about 1%, with a worst observed case of 2%, measured by preserving all the bookkeeping and promotion costs but disabling the actual TLB benefit. Even the deliberately adversarial "promote-then-immediately-discard" workload costs only 8.9%, most of which is a specific hardware artifact (PTE replication), not the core algorithm.
Q7Why demote a superpage speculatively even when it seems to still be in use?▾
Because the hardware gives only one reference bit for the whole superpage, the OS can't tell whether all base pages are actively used or just a few. Periodically demoting under memory pressure exposes each base page's own reference bit again, letting truly unused pages be identified and reclaimed — with cheap re-promotion if it turns out they were all still needed.
Q8Why did the SHA-1 hash-digest alternative for dirty tracking get rejected?▾
While it would have preserved superpage benefits even for partially-dirty pages, preliminary microbenchmarks showed up to 15% overhead on disk-intensive applications, and a worst case of 60% degradation when a large sequential read saturates the CPU while hashing. The simpler demote-on-write approach avoids this cost, so the authors chose it despite its coarser granularity.
Q9Is more superpage promotion always better?▾
No. The adversary experiment shows a workload that touches each page exactly once still pays real promotion/demotion overhead (8.9% slowdown) for zero TLB benefit. And promoting too eagerly consumes scarce contiguity that other processes or later, more beneficial superpages could have used.
Q10What's left as future work?▾
The authors mention that superpage-friendlier page table structures (like clustered page tables) would remove the linear-in-size cost that comes from the Alpha's PTE-replication hardware; further optimizing the rejected hash-digest approach (postponing hashing, moving it to idle time) is also flagged as future work.

Insights

Where this 2002 paper's ideas resurface in modern OS-memory-systems work.

⚠
Extrapolation, not the paper's claim: this tab is the guide author's own connections to later systems. The 2002 paper says nothing about CXL, tiered memory, TPP, HeMem, or Linux's multi-generational LRU — treat everything below as food for thought layered on top of the source text, not a conclusion drawn from it.

Reservation-based allocation ≈ page-placement heuristics for tiered memory

(Extrapolation — beyond the paper.) Speculatively reserving contiguous DRAM for a growing region is structurally the same bet a CXL/tiered-memory page-placement policy makes when it hot-promotes a page range to fast tiers before confirming reuse. Both trade a possibly-wasted resource commitment for avoiding a later, more expensive fixup (copying pages here; a slow tier access there).

Coarse hardware bits force OS-side approximation — a recurring theme

(Extrapolation — beyond the paper.) The single reference/dirty bit per superpage is the same class of problem as coarse-grained hot/cold tracking in DRAM/NVM tiering systems (e.g. sampled access bits, PEBS-based approximations in systems like TPP or HeMem). Both need to periodically "demote" or resample at finer granularity to recover information the hardware won't give directly.

Contiguity-aware page replacement anticipates page-placement-aware reclaim in modern LRU variants

(Extrapolation — beyond the paper.) Biasing eviction to serve a secondary goal (contiguity) rather than pure recency is the same move made by contiguity- or tier-aware page reclaim in Linux's multi-generational LRU or migration-aware reclaim in tiered-memory systems — deviating from strict LRU slightly to serve a structural goal, while bounding the fidelity loss.

Demote-on-write mirrors copy-on-write and dirty-tracking granularity tradeoffs

(Extrapolation — beyond the paper.) Splitting a superpage the instant it's written to avoid a large I/O blowup is the same granularity-vs-overhead tradeoff seen in copy-on-write fork() (page vs. huge-page COW) and in persistent-memory dirty-tracking schemes that must choose between coarse, cheap tracking and fine, expensive tracking.

(Current hardware, not the paper.) The 2002 landscape (Alpha with four sizes, i386 with only 4KB and 4MB) has shifted in two different directions.

x86-64 stayed close to the i386 model: a 4KB base and big jumps (2MB, 1GB), with nothing in between, so the paper's "you'd need all 512 base pages touched before a 2MB promotion" problem applies directly. AMD's hardware PTE coalescing is the one quiet exception, and it only fires if the OS happened to place the pages contiguously and aligned, which is exactly what a reservation allocator produces: a 2023 measurement study found FreeBSD's reservation system, the direct descendant of this paper, produces far more coalesced entries than Linux's buddy allocator.

Arm64 looks much more like the Alpha. The OS picks a translation granule (4KB, 16KB, or 64KB; which ones a chip supports is implementation-defined, and Apple silicon runs macOS on 16KB), and each granule gets real block mappings plus a contiguous bit: a hint that a run of adjacent, aligned entries (16 entries for the 4KB granule) maps contiguous memory, so the TLB can cache them as one entry. On a 4KB-granule Linux system that yields four usable sizes, 64KB, 2MB, 32MB, and 1GB, which is the paper's multi-size ladder almost exactly.

Linux has caught up to the paper's idea in software, too. Multi-size THP (mTHP, Linux 6.8) lets anonymous memory be allocated in intermediate sizes like 16KB to 1MB instead of only 4KB or 2MB. On Arm64 those sizes map onto the contiguous bit, giving the in-between TLB wins this paper argued for; on x86 they mostly save page faults and allocator work, since there's no matching hardware size (beyond AMD's coalescing).

Reading question: primum non nocere ("first, do no harm")

An implicit but overriding principle of the paper is to never be worse than the base system. Give two choices that satisfy it and one that does not.

Satisfies: demote clean superpages on the first write. With one dirty bit per superpage, a single modified page would force the whole superpage to disk. Demoting on write keeps dirty tracking per base page, at the price of denying superpages to regions that are never fully written. The paper states the principle almost word for word: "we choose to pay that price in order to keep the degradation in pathological cases low." Without it, writing one page in 512 of a mapped file costs 512 times the I/O and runs more than 20 times slower (§4.7, §6.7). The same reasoning rejected the SHA-1 alternative, which cost up to 15%, and 60% in the worst case.

Satisfies: promote only fully populated regions. Promoting earlier would force the OS to fill in pages the program never touched, inflating its memory footprint, and would quietly change OS semantics, since accesses to those pages would no longer fault and some invalid accesses would go uncaught. The system gives up superpage benefits for small programs rather than risk either (§4.5, §6.4). Reservations with preemption are an equally good example: a reservation is a bet that can be called off, since unused reserved frames are preempted and returned when memory is needed, and no page is ever copied, unlike the relocation approach of §3.2.

Does not: the contiguity-aware page daemon, in particular moving a closed file's clean pages to the inactive list. The base system keeps those pages around in case the file is reopened; this system deliberately gives that up and deviates from approximate LRU to recover contiguity, and says so: it "finds it worthwhile to favor the likelihood of recovering the contiguity from these file-backed pages, than to keep them for a longer time for the chance that the file is accessed again." The cost is measured against the unmodified system: the web server runs 1.6% slower when replayed after FFTW and 3% slower in the concurrent experiment (§5.1, §6.5). Smaller departures from the principle also exist, such as the incremental-promotion overhead (8.9% slower on an adversary workload, §6.6) and the allocator ignoring the zeroed-page hint (mesa 1.5% slower, §6.3), but those are accepted costs or omissions rather than a stated trade.

Core terms
SuperpageA large memory page (up to several MB) occupying a single TLB entry, covering what would be many base pages.
TLB coverageTotal memory reachable through cached TLB translations without a miss; has shrunk ~100× relative to RAM over ten years (Figure 1, 1986 to 2001).
Reservation-based allocationSpeculatively claiming a large, aligned, contiguous physical extent on first touch so a superpage can form later without copying.
Relocation-based allocationBuilding a superpage by physically copying already-allocated pages into a contiguous region.
Incremental promotionUpgrading a fully-populated aligned sub-extent to the next superpage size, repeating as more of the reservation fills in.
Speculative demotionProactively splitting an active superpage under memory pressure to regain per-base-page reference-bit visibility.
Demote-on-writeSplitting a clean superpage back to base pages the instant it's written, to avoid write-back of the entire superpage for one dirty page.
Contiguity-aware page daemonA modified page-replacement daemon that also evicts pages to restore fragmented physical contiguity, not just under raw memory pressure.
Multi-list reservation schemeSeparate reservation lists per superpage size, used to track and preempt partially-used reservations efficiently.
Population mapA radix tree (one level per page size) tracking which base pages of a memory object are allocated, used to trigger promotion decisions.
Supporting terms
Buddy allocatorA physical memory allocator managing power-of-two aligned blocks via splitting/coalescing — the base allocator here.
Preemption (of a reservation)Reclaiming an under-used reservation's unallocated frames when a new, more urgent contiguous request arrives.
PTE replicationThe Alpha's method of implementing superpages by writing the same page-size field into every constituent base-page's page table entry.
A-LRU (approximate LRU)FreeBSD's active/inactive/cache page-list scheme approximating true LRU ordering without per-access bookkeeping.
Partial-subblock TLBA hardware-based alternative (Talluri & Hill) allowing superpage TLB entries with "holes" for missing base pages.
Page coloringChoosing physical frames so virtually-contiguous pages map to distinct locations in a physically-indexed cache; automatically achieved by superpages.
