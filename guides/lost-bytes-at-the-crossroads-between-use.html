Freeing memory doesn't mean the kernel gets it back

Redis and LuaJIT call free() constantly. But the kernel only understands whole 4 KiB pages, while allocators think in odd-sized blocks. This is the plain-English tour of why, for a workload like LuaJIT's GC benchmark, up to 75% of its held-but-freed memory could become directly returnable "body" pages if the allocator merged holes aggressively — and a classification for talking about exactly where the rest gets stuck.

📄 Fistanto, Tempel & Dietrich · "Lost Bytes At The Crossroads…" · PLOS'26 🎓 Linux mm / allocator background assumed — primers cover the paper-specific bits ⏱ ~20 min read
🧱

A byte can only leave the process once its entire 4 KiB page is empty — so a hole's BODY (whole free pages) is returnable, while its HEAD, TAIL, and SUB-PAGE remnants stay stuck unless the allocator later merges them with a neighboring hole into a full page.

Before you begin

Quick glossary, then six primers

You already know Linux mm and cache/tiering territory — this paper's specific vocabulary is what's worth front-loading.

Quick glossary

RSSResident Set Size — physical memory frames actually backing a process, as opposed to virtual address space it merely reserved.
VMAVirtual Memory Area — the kernel's record of one contiguous region of a process's address space (e.g. one mmap() call). Page-aligned by construction.
TLB shootdownCross-core invalidation triggered when a mapping is torn down (e.g. madvise(DONTNEED)) — expensive enough that allocators avoid it on the hot path.
Halloc / HminThe paper's notation: Halloc is the allocator's actual hole list; Hmin is that list after virtually merging every adjacent hole — an upper bound on returnability.
TTL / GC / JITTime-to-live (Redis key expiry), garbage collection, just-in-time compilation (LuaJIT) — properties of the two benchmark workloads.
LD_PRELOADLinux mechanism to inject a shared library ahead of libc, used here to swap in an instrumented mallocng without recompiling Redis/LuaJIT.
body — fully free pages, returnable now head / tail — partial pages, stuck allocator / kernel machinery sub-page hole — stuck until merged with a neighbor
1The allocator sits between two granularities▾

The kernel only deals in whole pages (mmap()/munmap() for VMAs, madvise() for sub-ranges). The allocator subdivides those pages into arbitrarily-sized blocks to satisfy malloc(). Whenever the application free()s a block, the allocator usually keeps it in a free list rather than syscalling the kernel — that free-but-held block is a hole.

Now you're ready: the whole paper is about what happens to a hole once you ask "does this actually align with a page boundary the kernel could reclaim?"
2Why allocators hoard memory on purpose▾

Returning memory costs a syscall, and on anonymous mappings madvise(DONTNEED) forces an immediate, synchronous TLB shootdown. Linux 4.16 added MADV_FREE to relax this — mark pages reclaimable and let the kernel take them lazily, batched, under actual memory pressure. Allocators differ in how they act on this: glibc holds holes until the app explicitly calls malloc_trim() (a glibc-specific API, not something jemalloc or TCMalloc expose the same way), while jemalloc instead runs a background decay timer — 10 s idle by default — that eventually calls madvise() on its own without any app opt-in. Either way, holes routinely sit around far longer than the data they once held was needed.

Now you're ready: "not returning memory" isn't a bug — it's a deliberate performance trade the paper argues needs rebalancing now that DRAM is expensive again.
3mincore() and the pagemap — asking "is this byte physically here?"▾

mincore() (or reading /proc/<pid>/pagemap) lets a process query, per page, whether a physical frame is actually mapped behind a virtual address — independent of whether the allocator considers that address "free" or "allocated." That's the tool that turns a purely virtual hole classification into a measurement of real, wasted DRAM.

Now you're ready: the paper's core measurement is literally M ∩ (holes) — physically-backed addresses intersected with the allocator's free list.
4mallocng: slab allocation with small, fixed slots▾

mallocng (musl libc's allocator, embedded-Linux focused) groups same-size allocations into slabs of up to 32 independent slots. Slots freed inside a slab don't automatically merge with their neighbors — mallocng treats them as separate, un-spanning holes unless it explicitly coalesces them. It optionally supports madvise(MADV_FREE) to release whole freed pages.

Now you're ready: this slot-not-region design is exactly why the paper needs to distinguish Halloc (what mallocng actually sees) from Hmin (what it could see if it merged aggressively).
5Why this matters again in late 2025▾

DRAM prices spiked in late 2025 on surging AI-datacenter demand. For a decade the field optimized allocators for allocation/free latency because memory itself was cheap; that calculus has flipped, and this paper is a first attempt to quantify, systematically, how much DRAM is sitting idle purely because of the allocator/kernel granularity mismatch — not because of cold or unused data.

Now you're ready: keep this distinct from a tiering problem — this memory isn't cold, it's invisible: the OS's access-bit scanners can't reclaim or demote a hole they don't know exists as free.
6This paper's scope: measurement, not a new allocator▾

This is an 8-page workshop work-in-progress. It contributes a classification scheme for lost bytes and an empirical measurement (via mallocng + LD_PRELOAD instrumentation) of how much is currently lost and how much could be recovered with better merging. It does not yet build or evaluate a new page-aware allocator — that's explicitly future work.

Now you're ready: read every number below as "measured today" (Halloc) vs. "theoretical upper bound if holes were eagerly merged" (Hmin) — not as "achieved by a new design."
The whole story in one place

Lost bytes, in a nutshell

The mismatch, the classification that names it, and what it costs in practice.

When an application frees memory, the language runtime's allocator usually keeps it as a hole rather than returning it to the kernel — partly because it can't (other live data shares the same page), partly as a deliberate performance optimization. The kernel, however, can only reclaim memory at page granularity via madvise()/munmap(). Whenever a hole doesn't line up with that page grid, part of it becomes unreturnable no matter how empty it is.

The paper's contribution is a simple geometric classification: intersect each hole with the page grid. A hole entirely inside one page is a sub-page hole — stuck for now, unless it later merges with an adjacent hole into something page-sized. A hole spanning multiple pages splits into a head and tail (the partial pages at each end, stuck today because that page still has something else on it — sometimes a live allocation, sometimes just another hole mallocng hasn't merged yet) and a body (the whole pages in the middle) — the only part the OS can actually get back right now.

Applying this to mallocng running Redis and LuaJIT, and checking which of those bytes are physically resident via mincore(), the authors find mallocng currently holds roughly 20–25% of its RSS as holes, most of it physically backed. Critically, most allocators (including mallocng) don't try to merge adjacent holes into page-sized bodies — so when the authors virtually merge them (Hmin), the reclaimable body share of LuaJIT's holes jumps from 0% to 75%, and Redis's from ~22% to ~63%.

🍯 Key takeaways

  • Kernel reclamation is page-granular; allocator holes are block-granular — the gap between the two is where bytes get lost.
  • Only the body of a large hole (whole pages, nothing else sharing them) is directly returnable today; head, tail, and sub-page holes are stuck under Halloc — but can turn into body once adjacent holes get merged (Hmin).
  • Halloc = what the allocator's own hole list looks like today; Hmin = the same holes after eagerly merging adjacent ones — an upper bound, not a shipped fix.
  • For mallocng running LuaJIT's GC benchmark, up to 75% of the holes' total size could be a reclaimable body — today it's 0%, because mallocng never merges across its 32-slot slabs.
  • This is a visibility problem, distinct from a coldness problem: the kernel can't reclaim or demote memory it doesn't even see as free.
Five everyday pictures

How to think about lost bytes

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core rule · Page-granular return

A shared moving truck

Three families share one rented truck; the rental company only takes the whole truck back, not "the middle third." If your boxes are in the middle and the other two families haven't unloaded yet, your empty space is worthless to the rental company — it can't repossess just your section. Only when an entire truck is empty does it go back to the lot. That's a body page.

Where it breaks: a real truck has one owner per trip; a page can be shared by many small, unrelated allocations from the same process, so "whose fault" the stuck bytes are is less clear-cut than three tidy families.
Sub-page holes · Permanently stuck

A gap between two glued-together shelves

Two bookshelves are bolted together into one unit, and there's a slim gap between the shelves where a book used to sit. You can't unbolt just that gap and give it back to the store — the shelves come as a package. A sub-page hole is like this: it lives entirely within one page that also has live neighbors on it, so no amount of tidying can free it without moving those neighbors first.

Where it breaks: shelves are physically bolted; a page is only "bolted" by the allocator's placement choices — a smarter allocator could avoid ever putting unrelated live objects on the same page, unlike the bookshelf's fixed hardware.
Head & tail · The edges you can't touch

A parking garage's end floors

A garage has floors 1–5. Floors 2–4 are completely empty and could be shut off to save electricity. But floor 1 shares its ramp structure with the lobby (still in use), and floor 5's top deck overlaps the neighboring building's rooftop garden (still occupied). You can power down floors 2–4 (the body) but floors 1 and 5 (head and tail) stay lit no matter how few cars are parked there, because something else still needs that same structure.

Where it breaks: in a real garage the "something else" is a fixed structural constraint; in memory it's just whatever other allocation happened to land on that page — a placement choice, not physics.
Halloc vs Hmin · Merging is an upper bound

Adjacent empty parking spots, unmarked as one

Three consecutive parking spots are empty, but the garage's map still lists them as three separate stalls rather than one long empty lane — so the system that decides "can I fit a truck here" never sees the full length. mallocng's slab design does exactly this to holes inside a slab: adjacent free slots stay logically separate (Halloc) unless something walks the map and merges them into one long, page-spannable region (Hmin).

Where it breaks: repainting the parking lines is basically free; the paper only ever merges the map offline, in a sampling thread that periodically snapshots the hole list and runs it through a red-black tree — it doesn't instrument every single free(). Making that merging cheap enough to run continuously, on the hot path, is exactly the overhead the paper flags as future work.
Why eager return is rare · TLB shootdown cost

Recalling a library book the instant it's returned

Instead of letting returned books sit on the reshelving cart for routine pickup, imagine dispatching a courier the second any single book comes back. It'd be prompt, but the courier trip costs more than the book is worth if it happens constantly. madvise(DONTNEED) on an anonymous page is that courier — it forces an immediate, synchronous TLB shootdown across cores. MADV_FREE is the reshelving cart: mark it reclaimable, let the kernel take it in a lazy, batched sweep only when it actually needs the shelf space.

Where it breaks: a courier trip is a fixed cost; a TLB shootdown's cost scales with how many cores hold the stale mapping — so the "how much is too eager" line moves with core count in a way the library metaphor doesn't capture.
The full explanation

How it actually works

The formal classification, the measurement pipeline, and the mallocng integration, section by section.

1 · The formal classification (§3)

Let P be the page size and a hole be h = [v_s, v_e) — a half-open byte range. Define page-aligned floor/ceiling helpers:

⌈v⌉_P = ⌈v/P⌉ · P      # round up to next page boundary
⌊v⌋_P = ⌊v/P⌋ · P      # round down to previous page boundary

If the hole fits inside a single page (⌊v_s⌋_P = ⌊v_e⌋_P) and doesn't start page-aligned, it's a sub-page hole — the entire thing, unclassified further. Otherwise it's a large hole, split three ways:

head(h) = [v_s,        ⌈v_s⌉_P)     # partial page at the start — empty if v_s already aligned
body(h) = [⌈v_s⌉_P,    ⌊v_e⌋_P)     # whole pages in the middle — empty if the hole spans only 2 pages
tail(h) = [⌊v_e⌋_P,    v_e)         # partial page at the end — empty if v_e already aligned
📎
Only body is actionable. head/tail sit on pages that, by definition, also contain other bytes (live allocations or the hole's own partial extent) — the allocator generally cannot madvise them away without also touching neighboring, still-used data on that same page.

2 · Turning it into a physical-memory measurement (§3, §3.1)

Classification alone is virtual-memory bookkeeping. To find out how many of those bytes are actually costing DRAM, the authors intersect the classified holes with the set of physically-mapped addresses M, obtained via mincore() or the /proc/pid/pagemap pseudo-file:

lost_physical_bytes = M ∩ (⋃ sub(h_i) ∪ head(h_i) ∪ body(h_i) ∪ tail(h_i))   # for h_i in H

Many allocators — mallocng included — don't eagerly merge adjacent holes: mallocng treats slots inside a slab (up to 32 per area) as independent, non-spanning holes. So the paper runs the classification twice: once on the allocator's actual hole list H_alloc (today's behavior), and once on a virtually-merged list H_min where v_e^i = v_s^j holes are coalesced — the theoretical upper bound if the allocator merged perfectly.

3 · Building H_min efficiently — a red-black tree (§3.1)

Computing H_min isn't done on every free() — that would mean instrumenting the allocator's hot path, which the paper explicitly avoids. Instead, a background sampling thread wakes up periodically, takes a snapshot of the allocator's current H_alloc, and inserts each hole from that snapshot into a sorted red-black tree; each insertion checks its immediate left/right neighbors and merges if they're adjacent. That turns an O(N²) pairwise merge into an O(N log N) tree build per snapshot — a technique used purely to make the paper's evaluation tractable, not a proposed production policy.

4 · Two benchmarks, deliberately different shapes

Redis, driven by memtier_benchmark (800 connections over 16 threads, 300 s, SET:GET = 1:5, TTL 30–60 s, object sizes 2048–8192 B), represents a long-running server with steady, uneven-sized churn. LuaJIT runs a simplified GCBench — repeatedly building complete binary trees of depth 21 — representing a GC'd language allocating and freeing enormous numbers of small, short-lived objects.

💡
These two were picked precisely because they land in different corners of the classification: Redis's larger objects can form real page-sized bodies; LuaJIT's tiny tree-node allocations mostly produce sub-page and tail fragments unless merged.
Follow the numbers

Worked examples

All figures below are recomputed directly from the paper's Table 1 and Table 2 — including reproducing the abstract's headline "75%" from raw MiB values.

① Classifying the paper's own example hole

Hole h = [6144, 22528), page size P = 4096 B. Apply the floor/ceil definitions from §3.

  1. Is it sub-page? ⌊6144⌋P = 4096, ⌊22528⌋P = 20480 — different, so it's a large hole (spans multiple pages).
  2. head = [6144, ⌈6144⌉P) = [6144, 8192) → 2048 B, sitting in page 1 (4096–8192).
  3. body = [⌈6144⌉P, ⌊22528⌋P) = [8192, 20480) → 12288 B = 3 whole pages (8192–12288, 12288–16384, 16384–20480).
  4. tail = [⌊22528⌋P, 22528) = [20480, 22528) → 2048 B, sitting in page 5 (20480–24576).
  5. Check: 2048 + 12288 + 2048 = 16384 = 22528 − 6144. ✓ And the hole indeed crosses exactly 4 boundaries (8192, 12288, 16384, 20480) touching 5 pages — matching the paper's own description.
🍯
Then add residency: the paper notes only the middle body page (p3) is still physically backed; the other two body pages were already unmapped. So of this 16 KiB hole, only 4096 B (p3) is currently reclaimable DRAM — head, tail, and the two already-freed body pages don't count toward "lost."

② Reproducing the "75 percent" headline for LuaJIT (Table 1)

Table 1 gives average Head/Body/Tail/Subhole sizes for LuaJIT under Halloc and Hmin.

  1. Halloc total = 13.32 + 0 + 99.38 + 127.81 = 240.51 MiB of holes.
  2. Hmin total = 22.8 + 181.04 + 33.9 + 2.82 = 240.56 MiB — essentially the same total, as expected: merging only reclassifies bytes, it doesn't create or destroy them.
  3. Body share under Hmin = 181.04 / 240.56 = 75.3% — this is exactly the paper's headline "potential savings of up to 75 percent," specifically the body share of LuaJIT's own classified holes, not a claim about all freed memory everywhere.
  4. Sub-page share under Halloc = 127.81 / 240.51 = 53.1%, matching the paper's "53 percent of the holes are subpage holes" for LuaJIT before merging.
  5. As a fraction of RSS: 240.51 / 925.82 (avg RSS) = 26.0%, close to the paper's stated "≈25%."
💡
The story in one line: mallocng's per-slab slot tracking currently sees zero mergeable body in LuaJIT's holes (0 MiB). Once you merge adjacent slots, 181 of 240 MiB of held memory turns out to sit in whole, giveaway-ready pages.

③ The same computation for Redis — a smaller, subtler effect

  1. Halloc total = 0.97 + 0.83 + 1.41 + 0.59 = 3.80 MiB.
  2. Hmin total = 0.55 + 2.38 + 0.79 + 0.09 = 3.81 MiB — conserved, as expected.
  3. Body share, Halloc = 0.83/3.80 = 21.8% ≈ the paper's stated "20 percent of its holes are body pages."
  4. Body share, Hmin = 2.38/3.81 = 62.5% ≈ the paper's "63 percent" after merging.
  5. Relative to RSS: 3.80/20.77 = 18.3%, close to the paper's "≈20%."
📎
Redis already forms some body pages (its 2048–8192 B objects are big enough to occasionally span a full page on their own) — that's why its Halloc body share (22%) starts much higher than LuaJIT's (0%). Merging still roughly triples it.

④ A mimalloc-bench case: how much of xmalloc-testN's RSS is stuck?

Table 2 (Hmin): xmalloc-testN has RSS = 29.56 MiB, ΣHmin = 8.070 MiB, body share = 61.8%.

  1. Reclaimable body bytes = 8.070 MiB × 0.618 ≈ 4.99 MiB.
  2. As a fraction of total RSS = 4.99 / 29.56 ≈ 16.9% of this process's entire physical footprint sits in immediately-returnable body pages — today, unreturned.
  3. Compare to sh8benchN in the same table: RSS 119.12 MiB, ΣHmin only 9.978 MiB, body share just 5.9% → reclaimable ≈ 0.59 MiB, roughly 0.5% of RSS. Same suite, wildly different opportunity — the allocation pattern (sizes, lifetimes) drives everything.
🍯
Insight: "lost bytes" isn't a fixed tax — the mimalloc-bench table swings from 100% sub-page (barnes, effectively unreclaimable) to 61.8% reclaimable body (xmalloc-testN) depending purely on how an application's object sizes interact with the page grid.
Test yourself

Practice problems

Try each before opening the answer — every one names the misconception it's checking.

Problem 1 · easy
A hole spans [1000, 3000) and the page size is 4096. Is this a sub-page hole or a large hole? Why?
Show answer
Sub-page: ⌊1000⌋P = 0 and ⌊3000⌋P = 0 — both ends round down to the same page (page 0), so the entire 2000-byte hole sits inside one page.Misconception: judging by absolute size. A hole can be large in bytes yet still be "sub-page" if it never crosses a page boundary — the classification is purely about boundary crossing, not size.
Problem 2 · medium
A hole spans exactly [8192, 16384) with P = 4096. Compute head, body, and tail.
Show answer
head = [8192, ⌈8192⌉P) = [8192,8192) = empty (already page-aligned). tail = [⌊16384⌋P,16384) = [16384,16384) = empty (already page-aligned). body = [8192,16384) = the entire 8192 B hole — 2 full pages.Misconception: assuming every large hole has a nonzero head and tail. If both endpoints already land on page boundaries, the hole is pure body — the ideal, fully-returnable case.
Problem 3 · medium
Redis's H_alloc and H_min totals are both ≈3.80 MiB (Worked Example ③), yet the body share jumps from 22% to 63%. If merging doesn't create new free bytes, where does the extra "body" come from?
Show answer
From reclassifying existing head/tail/sub bytes, not from new memory. When two adjacent holes — say one hole's tail and its neighbor's head — merge into a single hole, that combined region may now itself contain a whole page in its middle that neither original hole, viewed alone, could form. The total lost bytes stay ≈3.80 MiB; merging only changes which class each byte falls into.Misconception: that H_min represents "additional savings" on top of H_alloc's losses. It's the same pool of bytes, reclassified into a more favorable (and more reclaimable) shape.
Problem 4 · hard
Why does LuaJIT show 0% body under H_alloc but 75% under H_min, while Redis only moves from 22% to 63%? Both use the same mallocng allocator.
Show answer
It's about object size relative to slab structure, not the allocator's code path. mallocng groups same-size allocations into slabs of up to 32 slots and doesn't merge across slots. LuaJIT's GCBench allocates many small, uniform tree-node objects — individually far smaller than a page, so no single freed slot can ever be a body page on its own; only after merging many adjacent freed slots does a full page emerge. Redis's 2048–8192 B objects are large enough that some freed blocks already span or nearly span a whole page by themselves, so H_alloc already shows some body even before merging.Misconception: that the allocator "treats LuaJIT worse." Same allocator, same policy — the gap is purely a function of each workload's object-size distribution against the fixed 4 KiB grid.
Problem 5 · medium
Only 120 of ≈42,000 Debian source packages call malloc_trim(). The paper argues this is a design flaw, not developer laziness. Why?
Show answer
malloc_trim() forces the application itself to decide when and how aggressively to give memory back — a decision that requires knowing about system-wide memory pressure, something an individual application generally can't see. The paper argues this responsibility belongs to the OS/allocator layer by design, not bolted on as an opt-in the vast majority of developers will never reach for.Misconception: that low adoption of malloc_trim() is a documentation or awareness problem. The paper frames it as evidence the API puts the decision at the wrong layer.
Problem 6 · hard
The mimalloc-bench "barnes" row shows 100% sub-page holes with RSS 40.21 MiB but ΣH_min of only 0.002 MiB. Is barnes actually wasting 40 MiB?
Show answer
No. ΣH_min (0.002 MiB) is the total size of unallocated holes the instrumentation could find — a tiny fraction of the 40.21 MiB RSS, meaning barnes's allocator is holding almost no free-but-unreturned memory at all; nearly all of its RSS is genuinely live, in-use data. The "100% sub-page" figure describes the composition of that small 0.002 MiB of holes, not a statement about the 40 MiB of RSS.Misconception: reading percentage-of-holes figures as percentage-of-RSS. Table 2's Sub/Head/Body/Tail columns are always percentages of that row's own ΣH_min, which can be a vanishingly small slice of total RSS.
Problem 7 · easy
Why can't the allocator simply madvise() away a head or tail segment the moment it notices the segment is unused?
Show answer
Because madvise() operates at page granularity — telling the kernel to drop a page drops the whole page, including whatever live, in-use data shares that same page with the head or tail segment. Returning a head/tail would corrupt or discard a neighbor's still-needed bytes.Misconception: that madvise() can operate on arbitrary byte ranges within a page. It fundamentally can't — that's the entire reason head/tail exist as an unreturnable category.
Quick answers

Frequently asked questions

Ten common questions, tap to expand.

Q1What's the single most important distinction in this paper?▾
Between Halloc (the holes an allocator actually maintains today) and Hmin (the same holes after virtually merging every adjacent pair). Hmin is a theoretical ceiling on returnability, not something mallocng currently achieves — the gap between the two is the paper's central empirical finding.
Q2Why can't the kernel just scan for free bytes itself?▾
The kernel doesn't know which bytes inside a page are "free" from the application's point of view — that's allocator-internal bookkeeping (free lists, slab metadata) that never crosses the syscall boundary unless the allocator explicitly calls madvise()/munmap(). To the kernel, a page with any live byte on it looks fully resident and in-use.
Q3Is a sub-page hole ever reclaimable?▾
Not directly, and not by the allocator returning memory alone. The only way to eliminate it is to change the allocation strategy so that the objects sharing that page eventually all become free together (or get moved/compacted) — that's the "Block Alignment" direction the authors flag for future work, not something the current classification fixes.
Q4Why does mallocng specifically get used for the experiments?▾
mallocng is musl libc's allocator, designed for memory efficiency on embedded Linux, and it already has an (optional, currently disabled by default) madvise(MADV_FREE) path — making it a natural, memory-conscious baseline to instrument rather than a purely performance-oriented allocator like TCMalloc or jemalloc.
Q5Why do Redis/LuaJIT appear in both Table 1 and Table 2?▾
Table 1 is the paper's own detailed, custom-instrumented benchmark setup for Redis (memtier_benchmark) and LuaJIT (a hand-adapted GCBench), giving the full Head/Body/Tail/Subhole breakdown. Table 2 is built around the mimalloc-bench suite — but the authors explicitly excluded mimalloc-bench's own built-in Redis, Lua, and Lean workloads as redundant (some spawn multiple processes, which the paper's per-process instrumentation isn't set up for), and instead list their own Redis/LuaJIT results under a separate "Custom Real-World Application Benchmarks" category inside Table 2 for comparison against the mimalloc-bench-suite programs. So the two tables aren't rerunning the same workload with different tooling — Table 2 simply reuses the paper's own Redis/LuaJIT numbers alongside a different, broader set of benchmarks.
Q6Does this paper propose a new allocator?▾
No — it's explicitly a work-in-progress measurement paper. It contributes the classification scheme and the empirical quantification of lost bytes in mallocng; designing and evaluating a page-aware allocator that actually captures the H_min upper bound is listed as future work.
Q7How is this different from the huge-page fragmentation work by Maas et al.?▾
Maas et al. (ASPLOS'20, ISMM'21) tackle a related but coarser problem: reducing fragmentation at 2 MiB huge-page granularity by placing objects according to predicted lifetime, then adaptively "breaking up" and returning huge pages. This paper works at ordinary 4 KiB page granularity and focuses on classifying exactly where returnability is lost, rather than proposing a placement policy — the authors call the huge-page line of work reciprocal to their own.
Q8How does this relate to OS memory-tiering / CXL work?▾
It's a different failure mode of the same broader problem — DRAM that's technically "there" but not doing useful work. Tiering systems (e.g. access-bit or PEBS-driven hot/cold classifiers) target pages that are live but cold, and try to migrate or demote them. This paper's lost bytes are pages the allocator never releases in the first place — invisible to a tiering scanner because the kernel still sees them as resident, application-owned memory. Fixing allocator-side returnability (this paper) and fixing access-driven demotion (tiering) are complementary, not competing, levers on the same DRAM budget.
Q9Is 75% a realistic, achievable number, or a best case?▾
It's an upper bound from H_min — assuming perfect, eager merging of every adjacent hole, with no consideration of the runtime cost of doing that merging continuously. The paper is explicit that a real paging-aware return policy still needs to account for that bookkeeping overhead, which is left to future work.
Q10What's the paper's most concrete near-term recommendation?▾
Two, paired: (1) allocators should size/place blocks with page alignment in mind rather than purely minimizing internal fragmentation with "uneven" size classes, and (2) slab-style allocators should track enough per-page occupancy information (not just per-slot) to know when an entire page — not just a slot — has gone empty and is safe to madvise().

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
HoleA block of memory the allocator has obtained from the OS and freed back to its own internal cache, but not yet returned to the kernel or reused.
Sub-page holeA hole entirely contained within one physical page. Stuck under Halloc, but not necessarily forever — if it later merges with an adjacent hole into a full page (Hmin), it becomes body.
head(h) / body(h) / tail(h)The three-way split of a hole that crosses page boundaries: partial start page, whole middle pages, partial end page. Only body is directly madvise()-able.
HallocThe allocator's actual, unmerged hole list — what the paper measures as "today's" behavior.
HminHalloc after virtually coalescing every pair of adjacent holes — the paper's upper bound on achievable returnability.
mincore()A syscall returning, per page, whether a physical frame is currently resident behind a virtual address — used to find how many classified hole-bytes are actually costing DRAM.
Supporting terms
VMAVirtual memory area — the kernel's page-aligned unit for structuring a process's address space, created/destroyed via mmap()/munmap().
madvise(WILLNEED / DONTNEED / MADV_FREE)Sub-VMA hints to the kernel. DONTNEED forces immediate reclaim (and a TLB shootdown on anonymous memory); MADV_FREE (Linux 4.16+) allows lazy, batched reclaim instead.
Slab / size classAllocators group same-size objects into slabs (e.g. mallocng's up to 32-slot areas) to cut per-object bookkeeping — at the cost of making cross-slot merging non-trivial.
RSSResident Set Size — the physical memory footprint of a process, as opposed to its (typically larger) virtual address space.
LD_PRELOAD instrumentationLoading a custom mallocng build ahead of libc to intercept and inspect allocator internals in unmodified Redis/LuaJIT binaries.
Red-black tree mergeThe structure the paper's sampling thread uses to coalesce a periodic snapshot of Halloc into Hmin for evaluation — rebuilt each sampling interval, not maintained on every individual alloc/free.

Foundational study of allocator fragmentation that this paper's lost-bytes classification extends specifically to the allocator/kernel boundary.

The 2 MiB-granularity analogue of this paper's problem — breaking up huge pages to return unused parts to the OS at warehouse scale.
