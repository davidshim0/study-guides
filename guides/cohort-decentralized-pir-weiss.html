SOSP 2026 · A Field Guide

One server you must trust, or a thousand you don't have to

Private database queries usually mean one provider holding all the cryptographic weight — and all the power to censor, crash, or be coerced. This is the plain-English story of Cohort, which spreads that trust (and that cost) across many weak, unreliable, possibly-lying servers.

📄 "Cohort: Decentralized PIR" · Weiss & Gilad 🎓 Some FHE/coding basics assumed — the primers cover them ⏱ ~30 min read
🧩

Split the database and every query into REDUNDANT shares across many servers, so the client still reconstructs the truth even if up to 25% of servers lie.

1What PIR promises, and why it's expensive▾

A PIR client wants entry i from a database without the server learning i — not even statistically. The naive private way is to have the server send you the entire database; PIR's whole point is doing much better than that while keeping the same privacy.

CPIR schemes buy this privacy with Fully Homomorphic Encryption: the server computes over an encrypted query, so it never sees a plaintext index — but FHE computation over a large database is costly, which is why most CPIR deployments have one or a few providers.

Now you're ready: Cohort keeps CPIR's privacy guarantee but spreads that expensive computation across many independent servers instead of one.
2PIR as matrix-vector multiplication▾

Arrange the database as an m×m matrix M. To fetch row r, column c, the client builds a one-hot vector (all zeros, a single 1 at position c), encrypts every entry, and sends it as the query Qc. The server computes M·Qc — this homomorphically "selects" column c without ever learning c — and a second one-hot vector Qr compresses the result down to the single entry M[r,c].

Now you're ready: Cohort's whole distributed protocol is this same matrix-vector product, just split into slices that different servers each compute a piece of.
3BGV ciphertexts as polynomials, and the NTT▾

A BGV ciphertext is a tuple of polynomials over a ring Rq. Multiplying ciphertexts grows the tuple (2 polynomials → 3 → …); adding them doesn't. To multiply polynomials fast, BGV implementations switch to the NTT domain — evaluating a polynomial at many fixed points turns multiplication into simple point-wise multiplication, then an inverse transform brings you back.

Now you're ready: Cohort's central trick reuses exactly this evaluation-at-many-points idea — but keeps the evaluations themselves, scattered across servers, instead of transforming back.
4The single-point-of-control problem▾

Even a cryptographically perfect single-provider PIR service has an operational weakness: one entity runs it. That entity can be coerced, DoS'd, taken down, or simply go out of business — and every client relying on it loses service at once. Replicating servers under the same operator doesn't fix this; it just moves the single point of control up a level.

Now you're ready: Cohort's decentralization goal is specifically about removing this single point of control — many independent operators, no one of whom can unilaterally break the system.
5Reed-Solomon codes: errors vs. erasures▾

An (n,k) RS code evaluates a degree-<k message polynomial at n points, giving n "codeword" values. Lose some values (erasures, you know which ones are missing) or corrupt some (errors, you don't know which ones are wrong), and you can often still recover the message — corruptions just cost twice as much of the redundancy budget as erasures, because you first have to find them.

Now you're ready: Cohort treats each server as one evaluation point. A dropped/censored server is an erasure; a lying server is an error — and the paper's "25% tolerance" headline is exactly this RS budget.
6Polynomial commitments: binding without hiding▾

A PCS lets you commit to a polynomial once (a short digest) and later prove its value at any point, without revealing the whole thing. The property that matters for accountability is binding: once committed, you can't later claim two different values at the same point.

Now you're ready: Cohort doesn't need the commitment to hide anything (the query is already encrypted) — it just needs binding, so a client can't send different servers conflicting queries and later frame an honest one.
7Partial synchrony and Byzantine tolerance▾

In the partial synchrony model, message delays can be unbounded for a while, but after some unknown Global Stabilization Time (GST), delays become bounded. A system built for this model can't promise instant answers, but it can promise eventual termination — and separately, it must tolerate some fraction of servers behaving arbitrarily badly (Byzantine faults), not just crashing.

Now you're ready: Cohort's availability guarantee is phrased exactly this way — "eventually, by some bounded time after GST" — and its Byzantine budget is the same 25% corruption threshold from the RS code.
8Sharding vs. replication vs. erasure coding▾

Three ways to spread data across many machines: sharding (each server holds a disjoint slice — cheap, but any one server's loss loses that slice); replication (every server holds everything — robust, but n× the storage and compute); erasure coding (each server holds a redundant-but-partial slice — a middle ground that tolerates losing some servers at a fraction of replication's cost).

Now you're ready: Cohort is erasure coding applied to an encrypted database and its queries simultaneously — that's the "not black-box" part the paper emphasizes.
The whole story in one place

Cohort in a nutshell

The problem, the encoding trick that fixes it, and how the pieces fit together.

Standard CPIR emulates a single, cryptographically perfect server — which means it also inherits a single point of control. Whoever runs that server can be coerced, censored, or simply disappear, taking every client's privacy-preserving access down with it. Running more servers under the same operator doesn't remove the operator; it just spends more money for the same fragility.

Cohort's fix is to fold Reed-Solomon error correction directly into BGV ciphertext arithmetic. The database and every client query are evaluated at n points (via the NTT machinery BGV already uses), producing n RS slices — one per evaluation point. A deployment can run exactly n servers, one slice each, but doesn't have to: the paper's own prototype uses n=65,536 slices spread across just 128 servers, each holding 512 slices. Because the client is really sending an RS codeword, it can reconstruct the correct BGV ciphertext even if up to 25% of the slices it gets back are wrong — or, with no corruption at all, even if up to roughly 50% of servers simply never answer (corruptions cost twice what erasures do: 2f+s < n−k+1).

When a server does lie, the client doesn't just discard the bad slice — it builds a publicly verifiable accusation from the signed responses, without revealing anything about its query. Servers store these proofs, and other clients periodically ask around and verify them before routing around a bad server — a gradual, checkable eviction, not an instant global change triggered by one client's broadcast.

The payoff: a working Go prototype retrieves 16 KB from a 2 GB database in under 170 ms, per-server storage shrinks as more servers join (e.g. 128 MB per server for a 4 GB database across 256 servers), and the system keeps returning correct answers even with 32 out of 128 servers actively lying.

🍯 Key takeaways

  • Centralized CPIR trades a cryptographic single point of failure for an operational one; Cohort removes the operational one.
  • The core novelty: RS-encode BGV ciphertexts/plaintexts by evaluating each polynomial limb at n roots of unity — no black-box composition.
  • n counts RS slices, not necessarily servers — a deployment can spread those n slices across fewer than n servers (the prototype: 65,536 slices across 128 servers, 512 each); the client's total bandwidth stays fixed regardless of server count.
  • Tolerates up to 25% adversarial servers by design (2f < n−k+1), with no runtime monitoring needed.
  • A signature- and commitment-based accusation mechanism publicly proves misbehavior without leaking the client's query.
  • Headline numbers: <170 ms for 16 KB from a 2 GB database (no-corruption response latency); per-server storage shrinks as more servers share a fixed-size encoded database.
Six everyday pictures

How to think about Cohort

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core move · No single point of control

A city with four power plants

Knock out one plant and the lights stay on, because no single plant was ever "the grid." A regulator can seize one plant's operator, but not the electricity itself. Cohort's n independent server operators play the same role: no coercion order, takedown notice, or bankruptcy can touch more than the one operator it's aimed at.

Where it breaks: a real grid still needs enough plants online to meet demand. Cohort's limit is asymmetric, though: the math tolerates up to 25% of servers actively lying, or up to roughly 50% simply vanishing — not both budgets in full at the same time (2f+s < n−k+1).
FHE · Computing without opening

A locked ballot box on a scale

You can weigh a sealed ballot box, sort several by weight, even combine two boxes into a bigger one — all without ever opening it and reading a single ballot. BGV lets a server do arithmetic on an encrypted query the same way: add and multiply the locked boxes, and the answer that pops out (still locked) is exactly the arithmetic result on what's inside.

Where it breaks: "multiplying boxes" isn't free — each multiplication makes the box bulkier (BGV's ciphertext tuple grows), which is exactly why Cohort's parameters must budget for the query's multiplicative depth in advance.
Reed-Solomon · Redundancy by design

A moving crew with spare boxes

Pack a shipment into more boxes than strictly needed, so if one box is crushed or lost in transit, the recipient can still reconstruct everything from the rest. RS coding does the same to a BGV element: instead of storing it once, evaluate it at n points — any k correct ones (out of n) are enough to rebuild the original.

Where it breaks: spare boxes only protect against loss. A box that arrives looking fine but has swapped contents (corruption, not erasure) costs twice the "spare budget" to catch and fix — which is exactly why Cohort's malicious-server tolerance (25%) is half its dropped-server tolerance (50%).
Query commitment · Binding without hiding

A notarized single copy

A notary doesn't need to know what's written on a document to stamp it — the stamp just proves that this exact document was the one you submitted, and you can't later swap in a different version and claim it's the same. Cohort's KZG commitment does this to a query: every server checks its slice against the same stamp, so the client is locked into one query everywhere.

Where it breaks: a notary stamp says nothing about whether the document's contents are true — the commitment doesn't verify the query is well-formed or privacy-preserving, only that it's the same query everyone answered.
Catching corruption · Re-encode & compare

Redoing the receipt yourself

You don't trust a cashier's handwritten total — you re-add the items yourself and compare. If your total disagrees with theirs, you know exactly which line item to dispute, and you have the original receipt as evidence. Once a Cohort client decodes the true answer, it re-encodes that answer into slices and compares each one against what each server actually sent — any mismatch is provable, signed evidence.

Where it breaks: re-adding the receipt only works because you know the correct total first — Cohort's client can only run this check after a successful decode, so it can't catch corruption in a query that fails to decode at all.
Availability · Partial synchrony

Waiting out a storm, not forever

A courier company can't promise "delivered in 10 minutes" during a hurricane, but it can promise "once the storm passes, every package moves normally, and yours will arrive." Cohort's availability guarantee is the same shape: no bound on delay before some unknown Global Stabilization Time, but a hard bound afterward — so a client's query is guaranteed to finish, just not on a fixed clock.

Where it breaks: the courier's promise says nothing about deliveries arriving correctly, only that they arrive — Cohort still needs the separate RS correctness argument to guarantee the package (the decoded answer) is the right one.
The full explanation

How it actually works

From a single BGV element to a full accusation, with the paper's parameter constraints made concrete.

1 · RS-encoding a BGV element

A BGV plaintext or ciphertext is one or more polynomials in the ring Rq, where q = p1·p2···pl is a product of primes. Cohort defines RS-Encode for such a polynomial by evaluating it at n roots of unity — the same NTT machinery BGV already uses for multiplication — producing n scalar values per polynomial. Because Zq is composite, encoding works limb-wise via the CRT: each polynomial is viewed modulo each prime factor pi separately, and RS is applied to each limb independently.

2 · Distributing the database and the query

The logical database M ∈ Rqm×m becomes a tensor in Zqn×m×m once RS-encoded, giving n slices M1,…,Mn ∈ Zqm×m. With exactly n servers, server ℓ stores just Mℓ; in the more typical deployment with P<n servers, each server stores and computes over n/P such slices (the prototype: 512 apiece, for 128 servers and n=65,536). A client's two-dimensional query (Qr,Qc) is sliced the same way, so each slice ℓ a server holds needs just (Qrℓ,Qcℓ) — a handful of scalars, not a full ciphertext. For each slice, the server computes locally: resultℓ := (Mℓ·Qcℓ)T·Qrℓ, signs it, and returns it.

3 · Robust reconstruction

The client starts trying to decode once it holds k+f responses, treating any that never arrive as erasures. Because RS can uniquely decode whenever 2f+s < n−k+1, the client recovers the exact BGV result — the same 3-polynomial tuple a single honest centralized server would have produced — despite up to f corrupt and s missing slices.

// client-side reconstruction loop
received = {}
while len(received) < n:
    received[ℓ] = wait_for_next_signed_answer()
    if len(received) >= k + f:
        result = RS_decode(received, n, k)   // Gao's algorithm
        if result != ⊥:
            return decrypt(result)          // success, stop waiting
// too many corruptions to decode → ⊥, client can only wait for more slices

4 · Removing corrupt servers

After decoding, the client re-encodes the true result and compares it slice-by-slice against every signed answer it received. A mismatch at slice ℓ, combined with server ℓ's own signature, is unforgeable proof of misbehavior. The client bundles k+f correct signed answers, the bad one, and the query commitment into an accusation — verifiable by anyone, without the database or the query itself.

💡
Why the commitment matters here: without it, a malicious client could send servers different queries and then "accuse" an honest server whose correct answer to its own query just looks wrong against a different query's expected result. The commitment locks every server to the same query, so this framing attack is provably impossible (Theorem 5).

Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own parameters and measurements.

① Do the prototype's parameters actually satisfy k ≥ 3N?

  1. N = 2¹³ = 8192. The BGV ring degree.
  2. Minimum required k = 3N = 3 × 8192 = 24,576 (so the degree-3N−3 product from a two-dimensional query fits without wraparound).
  3. Chosen k = 2¹⁵ = 32,768. Check: 32,768 ≥ 24,576 ✓ — with room to spare.
  4. Notice the exact relationship: 32,768 ÷ 8,192 = 4. The prototype sets k = 4N exactly, one full multiple above the bare 3N minimum.
  5. And n = 2¹⁶ = 65,536 = 2k — so n−k = k, a clean rate-1/2 code: half the slices are "real," half are redundancy.
🍯
Insight: the same tripling that makes ciphertext multiplication expensive (a degree-2 ciphertext times a query reaches degree 3N−3) is exactly what sets the RS message-length floor — the crypto and the coding theory aren't independent choices.

② Where does 128 MB per server actually come from?

A 4 GB logical database, RS-encoded and split across 256 servers.

  1. Start: 4 GB of plaintext.
  2. Pad to 12 GB (3×) so the ciphertext's multiplicative depth has room, mirroring the k ≥ 3N logic above.
  3. Round up to 16 GB to keep the polynomial degree NTT-friendly.
  4. RS-encode at rate 1/2 (n = 2k) → 32 GB total encoded volume across all servers.
  5. Split across 256 servers: 32 GB ÷ 256 = 128 MB per server.
  6. Compare: plain sharding (no redundancy) would be 4 GB ÷ 256 = 16 MB — Cohort is 8× that. Full replication would need the whole 4 GB (4096 MB) per server — Cohort is 32× smaller than that.
💡
128 MB sits exactly between the two extremes: 8× more than naive sharding buys 25% Byzantine fault tolerance; 32× less than full replication buys most of that same resilience.

③ Checking the 25% corruption-tolerance claim

  1. n = 2¹⁶ = 65,536 total slices, k = 2¹⁵ = 32,768.
  2. Decode condition (no erasures, s=0): 2f < n−k+1 = 32,769 → f ≤ 16,384 corrupt slices.
  3. With 128 servers, slices per server = 65,536 ÷ 128 = 512.
  4. Max corrupt servers = 16,384 ÷ 512 = 32.
  5. As a fraction: 32 ÷ 128 = 25% — exactly the paper's headline number.
🍯
Insight: "25% tolerance" isn't a separately-tuned parameter — it falls straight out of the rate-1/2 RS code (n=2k) once you divide by 2 for the error/erasure asymmetry.

④ How much does parallelism actually buy?

From Table 2 (query encoding/commitment) and §8.6 (decoding).

  1. Query encoding, 4 → 64 cores: 1.16 s → 0.12 s, a 9.67× speedup (1.16 ÷ 0.12) from 16× more cores — about 60% parallel efficiency.
  2. Query commitment, 4 → 64 cores: 31.7 s → 3.4 s, a 9.32× speedup — similarly efficient.
  3. Decoding, 4 → 9 cores: 5.31 s → 2.61 s, a 2.03× speedup. The 9 comes from a degree-2 ciphertext's 3 polynomial components × 3 CRT limbs of q = 9 independent units of work.
  4. Because queries are cached and reused (§2.2, §8.7), that ~3.4–31.7 s commitment cost is a one-time charge amortized over every future retrieval with that query — not paid per-query.
💡
The one-off, parallelizable setup costs (encoding, commitment) are separate from the paper's per-query response-latency headline — but decoding, especially under corruption, is not free at query time (see FAQ Q9).
Test yourself

Practice problems

Try each before opening the answer. Every one flags the misconception it's checking for.

Problem 1 · easy
With n=65,536 and k=32,768, and no erasures (s=0), what is the maximum number of corrupted slices f the client can tolerate and still decode?
Show answer
2f < n−k+1 = 32,769, so f < 16,384.5, meaning f ≤ 16,384 slices exactly.Misconception: rounding up to 16,385, or using the weaker "detection" bound (f < n−k+1 ⇒ f ≤ 32,768) which only guarantees the client notices too much corruption — not that it can actually decode.
Problem 2 · medium
Why does a corrupt (wrong) response cost the RS budget twice as much as a missing (erased) response?
Show answer
An erasure tells the decoder exactly which position is unreliable — it just needs enough other points to interpolate around the gap. A corruption gives no such hint: the decoder must first locate which points are wrong before it can ignore them, which consumes extra redundancy. That's why the decode condition is 2f + s < n−k+1 — each error "f" counts double, each erasure "s" counts single.Misconception: assuming a corrupt answer is "no worse" than a missing one since both are just "bad data" — the extra cost of locating a lie is the whole reason Byzantine tolerance (25%) is half of crash tolerance (50%).
Problem 3 · medium
Why does per-server storage shrink as more servers join, even though the total RS-encoded database size (32 GB for a 4 GB DB) stays fixed?
Show answer
The 32 GB total is fixed by the padding and redundancy rate (independent of server count), but that fixed volume is divided across however many servers hold slices. More servers means each one holds a thinner slice of the same total — 256 servers → 128 MB each; 512 servers would mean 64 MB each.Misconception: thinking more servers means more total redundancy (and thus more total storage) — the RS code's rate is fixed by (n,k), which are cryptographic/coding parameters, not the deployment's server count.
Problem 4 · hard
Why must the RS message length satisfy k ≥ 3N, rather than just k ≥ N?
Show answer
Cohort's two-dimensional query computes (M·Qc)T·Qr, a product of ciphertext polynomials. Because Cohort avoids modular reduction (padding instead, to prevent RS-scrambling wraparound), multiplying degree-(N−1) polynomials without reducing can reach degree 3N−3. The message space (of length k, before RS lifting) must be large enough to hold that unreduced degree, so k must be at least 3N.Misconception: assuming the BGV ring degree N alone bounds every intermediate polynomial — that's only true after modular reduction, which Cohort deliberately postpones to keep RS decoding clean.
Problem 5 · medium
Can a malicious client fabricate a valid accusation against a server that behaved honestly?
Show answer
No (Theorem 5). Every server's signed answer is bound to the same query commitment C, and KZG's binding property means the client cannot produce a valid opening showing two different values at the same evaluation point. Since the honest server's answer is the unique correct evaluation of the committed query at its point, no accusation claiming otherwise can pass verification.Misconception: thinking this relies on the commitment hiding the query — soundness here comes purely from binding, not hiding; hiding is unnecessary because the query is already encrypted.
Problem 6 · hard
Why not just shard the database with off-the-shelf erasure coding, then run ordinary single-server PIR against each shard independently?
Show answer
That black-box approach is conceptually simpler but bandwidth-inefficient: each of the n servers must return a full FHE ciphertext response, and the client's total download grows with n. Cohort's RS-inside-BGV integration makes each server's response a handful of scalars instead — the paper notes that sharding SPIRAL this way into n=2¹⁶ slices would produce responses 375× larger than Cohort's.Misconception: assuming any combination of "erasure code + PIR" gives similar efficiency — the specific algebraic embedding (evaluating ciphertext coefficients, not wrapping whole ciphertexts) is what keeps per-server responses small.
Problem 7 · hard
Why does RS decoding run in O(n log n) time with zero errors but O(n log²n) with errors present?
Show answer
With zero errors, the client only needs to interpolate the received points into a polynomial (an inverse NTT, O(n log n)) and check its degree is below k — every slice already lies on the correct polynomial. With errors present, Gao's decoder must additionally locate which points are wrong, requiring polynomial division with remainder (via Newton iteration) and a Half-GCD computation — algorithms that cost an extra O(log n) factor on top of the transform.Misconception: assuming decoding cost is the same regardless of corruption — the paper's own benchmark shows a visible step increase in latency the moment even one server lies, precisely because of this extra algorithmic machinery.
Problem 8 · easy
Why does the radio-streaming application rely on query caching rather than issuing a fresh query every epoch?
Show answer
A listener's query index (which station) stays fixed across many epochs even though the station's content changes every epoch. Query encoding and commitment are the expensive, one-time costs (up to ~31.7 s for commitment); by reusing the same cached, committed query against each new database version, the client pays that cost once and gets many cheap retrievals afterward.Misconception: thinking freshness requires a new query — in Cohort, freshness comes from the database updating (new database version, same query), not from re-querying.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What's the difference between CPIR, IT-PIR, and where does Cohort sit?▾
CPIR uses FHE for cryptographic privacy that holds even if every server colludes, but is computationally expensive. IT-PIR uses cheap secret-sharing across servers, but privacy fails entirely if those servers collude. Cohort keeps CPIR's collusion-resistant privacy guarantee while borrowing IT-PIR's multi-server distribution and fault tolerance — it's the first system to combine both.
Q2Why not just replicate the whole database across many trusted servers for availability?▾
Full replication needs every server to run the expensive FHE computation over the entire database (no cost sharing) and each server needs 32× the storage Cohort's slicing requires (Worked Example ②). It also doesn't remove a single point of control if one operator runs all the mirrors.
Q3How exactly does RS coding get combined with BGV, rather than just wrapping around it?▾
Every BGV polynomial coefficient (viewed limb-wise via CRT) is evaluated at n roots of unity using the same NTT machinery BGV already relies on for fast multiplication. Polynomials are padded to a higher degree first so ciphertext multiplication (which can reach degree 3N−3) doesn't wrap around and scramble the RS encoding.
Q4What happens if a server just goes offline, versus sending garbage?▾
Offline/unresponsive is treated as an erasure — cheap for RS to tolerate (up to n−k of them). Sending a signed wrong answer is a corruption — twice as expensive for RS, because the decoder first has to locate it before it can ignore it.
Q5How are malicious servers actually punished and removed?▾
A client that detects a mismatch after decoding packages the signed responses plus the query commitment into a publicly verifiable accusation. The accused server's proof is stored, not instantly broadcast to a global blocklist: other clients periodically ask servers for known accusations, verify them independently (no database or query access needed), and then choose to avoid the bad server — a gradual, checkable eviction rather than an automatic state change triggered by one client.
Q6Can a malicious client frame an honest server?▾
No — the query commitment (KZG) binds the client to one query value at every server's evaluation point, and KZG's binding property means the client can't produce a conflicting opening later. An honest server's genuine response can never be shown inconsistent with the unique committed query (Theorem 5).
Q7Why use KZG despite its trusted setup requirement?▾
KZG was chosen for succinctness — constant-size commitments and openings, cheap verification. The paper explicitly flags transparent alternatives (Orion, Dory, FRI-based PCS) that avoid trusted setup as future work if that assumption is unacceptable for a deployment.
Q8How does Cohort's performance compare to centralized CPIR systems?▾
Cohort processes each query independently, so throughput scales linearly with the number of servers, similar to SPIRAL. It does strictly more work per query than the prior distributed-PIR system SlicedPIR (the RS redundancy overhead), but unlike SlicedPIR/DPIR it needs no central validating server — removing their bottleneck and single point of failure.
Q9What does the "16 KB from 2 GB in under 170 ms" headline actually cover?▾
That's the paper's response-latency headline for the no-corruption case — the time from sending the query out to receiving back the servers' answers, not counting the separate, one-off query encoding/commitment cost (up to ~31.7 s, amortized over many future retrievals of the same query, §8.7). It also doesn't reflect what happens when servers are actively corrupt: the paper's §8.6 measurements show RS decoding under corruption can take seconds, not milliseconds. The 170 ms figure describes the common honest-servers path — fast enough to sustain the paper's private news-radio demo, where each retrieved 9 KB transcript yields about 8.5 minutes of synthesized speech per query.
Q10What did the authors leave as limitations or future work?▾
Reducing the RS/BGV padding overhead by exploiting BGV's negacyclic convolutions directly; adopting transparent polynomial commitment schemes (Orion, Dory, FRI-based) instead of KZG's trusted setup; and an alternative deployment that keeps seed servers around to simplify write dissemination and drop query commitments entirely.

A cross-domain note aside

If your own work is OS-managed memory tiering or CXL-attached memory, the closest conceptual cousin here isn't PIR itself but the erasure-coding trade-off (Primer 8): Cohort spends 2× storage for 25% Byzantine tolerance the same way erasure-coded distributed storage trades capacity for availability — just applied to encrypted ciphertext coefficients instead of raw data blocks.

Related work cited by the paper

SlicedPIR medium

Weiss & Gilad · CCS 2025

The prior distributed-PIR system Cohort builds its prototype on; offloads FHE work to clients but keeps a central validating server that Cohort removes.

Distributed PIR (DPIR) medium

Tovey, Weiss & Gilad · CCS 2024

Introduced client-assisted PIR computation verified by the server; shares SlicedPIR's central-server bottleneck.

SPIRAL hard

Menon & Wu · IEEE S&P 2022

Fast single-server CPIR via FHE composition; the paper's naive-sharding bandwidth comparison (375× larger) uses SPIRAL as the baseline.

BGV: Leveled FHE without Bootstrapping hard

Brakerski, Gentry & Vaikuntanathan · ITCS 2012

The original FHE scheme Cohort's entire construction is built on top of.

KZG Polynomial Commitments hard

Kate, Zaverucha & Goldberg · ASIACRYPT 2010

The constant-size commitment scheme Cohort uses to bind clients to a single query across all servers.

A New Algorithm for Decoding Reed-Solomon Codes medium

Shuhong Gao · 2003

The RS decoder Cohort implements, chosen for composing well with the NTT/roots-of-unity structure BGV already uses.
