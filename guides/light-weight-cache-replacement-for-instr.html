ISCA 2025 · A Field Guide

Beating a learned predictor with five hand-picked numbers

Mockingjay predicts cache reuse with a sampled cache, a reuse-distance predictor, and ETA counters — tens of kilobytes of extra silicon per core. PACIPV gets nearly the same speedup with two 5-element lookup tables and 20 bits of extra state, by asking a coarser, better-targeted question.

📄 "Light-weight Cache Replacement for Instruction Heavy Workloads" · Mostofi, Gupta, Hassani, Tibrewala, Teran, Gratz & Jiménez 🎓 RRIP / LLC replacement basics assumed — primers cover them ⏱ ~25 min read
🎯

Sort every access into one of 4 coarse buckets, treat demand and prefetch accesses differently instead of building a per-block predictor, and pick the tiny 5-number rule by brute-force search, not machine learning.

Before you begin

Quick glossary, then the assumed background

Acronyms first — you'll see them everywhere. Then eight short primers on the concepts PACIPV builds on. Tap any to expand.

Quick glossary

IPVInsertion/Promotion Vector — a small lookup table that says where a cache block's recency value goes next, on insertion or on a hit.
RRIPRe-Reference Interval Prediction — the coarse-grained (4-state) alternative to LRU that PACIPV builds on.
RRPVRe-Reference Prediction Value — a block's 2-bit "how soon will I be reused" label (0 = imminent, 3 = distant).
SRRIP / DRRIPStatic / Dynamic RRIP — the standard RRIP implementations PACIPV is compared against.
PACIPVPrefetch Aware Coarse-grained IPVs — this paper's policy: separate IPVs for demand and prefetch accesses.
EIPEntangling Instruction Prefetcher — the aggressive instruction prefetcher used alongside PACIPV.
LLCLast-Level Cache — the shared cache PACIPV manages (3 MB, 12-way, in this study).
MPKI / IPCMisses Per 1000 Instructions / Instructions Per Cycle — the miss-rate and speed scorecards. This paper's central surprise: they can move in opposite directions.
1Why LRU struggles at the last-level cache▾

LRU assumes recent access predicts near-future reuse. At the LLC this assumption is often wrong: thrashing (a working set bigger than the cache) and scanning (long one-pass sequences) both make LRU evict exactly the blocks that would soon be reused, and keep exactly the ones that won't.

Now you're ready: both RRIP and PACIPV exist because plain LRU's precise recency ordering is the wrong tool for the LLC.
2RRIP: four buckets instead of a precise stack▾

Instead of a full N-way ordering (LRU), RRIP gives every block a 2-bit RRPV: 0 (near-immediate reuse), 1–2 (long), 3 (distant). New blocks insert at "long" by default. On a hit, a block is promoted toward 0. To evict, RRIP looks for a block at RRPV 3; if none exists, it ages every block (increments all RRPVs) until one appears.

Now you're ready: that four-bucket scheme is exactly the state PACIPV reuses — it changes only the promotion/insertion rules, not the bucket count.
3Insertion and promotion — the two decisions every policy makes▾

Any recency-based replacement policy answers two questions: (1) Insertion — where does a brand-new block start? (2) Promotion — where does a block move when it's hit again? LRU's answers are fixed (MRU, MRU). SRRIP's answers are fixed too (RRPV 2, RRPV 0). PACIPV's whole trick is making these two answers configurable and searchable.

Now you're ready: an IPV is just a table of answers to those two questions, one entry per starting RRPV.
4An IPV, concretely▾

For an n-way (or n-state) cache, an IPV is a vector V[0..n]. A block sitting at recency value p that gets accessed jumps to V[p]. A newly inserted block starts at V[n]. For RRIP with 4 RRPVs, that's a 5-element vector, each entry a 2-bit RRPV — e.g. SRRIP is the vector [0,0,0,0,2]: any hit jumps straight to 0, and new blocks insert at 2.

Now you're ready: PACIPV replaces that one fixed SRRIP vector with two searched vectors — one for demand, one for prefetch.
5Demand vs. prefetch — a property of the access, not the block▾

A demand access is one the core actually issued because it needs the data or instruction now. A prefetch access is a speculative fetch issued ahead of need, hoping to hide latency. Critically, PACIPV classifies the access, not the block: the same cache line can be touched once by a prefetch and later by a demand hit, and each event uses its own IPV.

Now you're ready: "two IPVs" doesn't mean two kinds of cache lines — it means two rulebooks applied depending on how each individual access arrived.
6Why instruction caches break PC-based predictors▾

Policies like SHiP index a table by the program counter (PC) of the memory instruction, learning "this load's PC tends to reuse its data." That works for data because one load PC touches many different addresses over a run, giving the table many samples to learn from. An instruction fetch's PC essentially identifies one specific code block — there's no cross-address pattern for the table to generalize.

Now you're ready: PACIPV deliberately avoids PC entirely — it's a structural fix, not a workaround for missing data.
7MPKI and IPC can disagree▾

MPKI (misses per 1000 instructions) counts how often you miss. IPC (instructions per cycle) measures how fast the program actually runs. Usually fewer misses means higher IPC — but not always: a miss that overlaps with other in-flight misses (memory-level parallelism, MLP) costs far less than an isolated one. A policy can raise MPKI while still raising IPC, if it trades away "cheap," overlappable misses to protect blocks whose loss would cause expensive, isolated ones.

Now you're ready: this is PACIPV's most counterintuitive result — worth watching for directly in the "How It Works" tab.
8Design/verification cost as a real metric, not an afterthought▾

Extra SRAM is only part of a replacement policy's cost. Routing the PC from the front-end to the LLC, or implementing online learning (perceptrons, temporal-difference updates), demands cross-team design and verification effort — and may be outright impossible if the LLC sits behind third-party IP (e.g. a licensed Arm core) that never exposes the PC downstream.

Now you're ready: PACIPV's central pitch is that it needs none of that — just physical addresses and a demand/prefetch bit, both of which any LLC controller already sees.
The whole story in one place

PACIPV in a nutshell

The problem with one shared vector, the search that fixes it, and why it competes with far more complex machinery.

SRRIP uses one fixed insertion/promotion rule for every access — demand or prefetch alike: [0,0,0,0,2]. But a prefetch is a guess and a demand is a fact, and treating them identically either lets bad guesses squat on cache space or under-trusts real reuse. Recent work fixes this by building learned predictors — Mockingjay emulates Bélády's optimal MIN policy using a sampled cache, a reuse-distance predictor, and per-block ETA counters. It works, but it costs 24 KB/core + 32 KB of metadata, plus real design and verification effort across multiple hardware teams.

PACIPV takes the opposite bet: generalize RRIP's implicit rule into an explicit, searchable IPV — a 5-element vector defining insertion and promotion for demand accesses, plus a second IPV for prefetch accesses — and find the best pair by trying all of them. The trick that makes exhaustive search feasible is shrinking the RRPV granularity from LRU's 16 positions to RRIP's 4: the original IPV work searched a 17-element, 16-valued space (1617 ≈ 2.95 × 1020 vectors) with a genetic algorithm and no optimality guarantee. RRIP-based IPVs live in a space of just 210 = 1,024 single vectors; after filtering out IPVs that can't reach every RRPV or that demote a block on a hit, only 4,032 reasonable pairs remain — small enough to simulate every single one on a training set and simply keep the best.

The winning pair — demand [0,1,1,0,3], prefetch [0,1,0,0,3] — inserts new blocks as presumed-dead (RRPV 3), but promotes a block straight to MRU (RRPV 0) on its very first reuse. That single design choice recovers most of what a learned predictor buys, at essentially SRRIP's hardware cost: 12 KB/core, plus 20 bits of static IPV state.

The payoff: with the EIP instruction prefetcher enabled, PACIPV reaches a 3.3% speedup over LRU — matching Mockingjay's 3.2% and beating SRRIP's 2.2%. Without EIP, PACIPV still leads at 3.0% vs. Mockingjay's 2.8% and SRRIP's 2.0%. And it does this with roughly 2,700× less extra state than Mockingjay's metadata.

🍯 Key takeaways

  • SRRIP applies one insertion/promotion rule to demand and prefetch accesses alike; PACIPV uses two.
  • Shrinking RRPV granularity from 16 (LRU-style) to 4 (RRIP-style) collapses the searchable space by ~17 orders of magnitude, turning a genetic-algorithm problem into an exhaustive one.
  • The winning IPVs are 5 numbers each — small enough that a person can read and understand the policy, unlike a 17-element LRU IPV.
  • PACIPV costs 12 KB/core (same as SRRIP + 20 bits) vs. Mockingjay's 24 KB + 32 KB metadata.
  • PACIPV can have higher LLC MPKI than every rival and still win on IPC — it's selective about which misses it keeps.
  • Retraining the same search on data-heavy (GAPS) workloads instead of instruction-heavy (CVP) ones finds a different best pair — PACIPV is a methodology, not a fixed vector.
Six everyday pictures

How to think about PACIPV

Each picture stands alone. Every card ends with an honest note about where the picture stops being true.

The core trade · RRIP vs LRU

Sorting mail into four bins, not one queue

LRU keeps every letter in a strict single-file line by exact arrival time. RRIP instead sorts mail into four coarse bins — "urgent," two "eventually" bins, and "probably junk." Coarser, but far cheaper to maintain, and less thrown off by a single long line of junk mail passing through.

Where it breaks: a handful of workloads follow a strict palindromic reuse pattern (access a0…ak, then reverse) that precise LRU ordering happens to match perfectly — RRIP's coarser bins lose that exact match, and 6 of 94 training workloads do slightly worse under PACIPV than LRU.
The mechanism · IPV vs learned predictor

A five-number recipe card vs. a trained chef

Mockingjay is like a chef who's tasted thousands of dishes and learned, block by block, when to expect a diner to come back for seconds — impressive, but it took years of training and a notebook full of rules (32 KB of predictor tables). PACIPV is a five-number recipe card, tested once against every other reasonable card, then printed and hung on the wall for good.

Where it breaks: the chef adapts online as tastes change mid-service; the recipe card is fixed at design time. PACIPV needs a fresh search (a different card) if the workload domain changes substantially — as it does moving from CVP to GAPS.
Two rulebooks · Distinct IPVs

Different trust for a knock vs. a guess

A demand access is someone actually knocking on the door — they need in, now. A prefetch access is a guess that someone might knock soon. It makes sense to answer these differently: welcome the knocker in immediately, but treat the anticipatory guest with a little more skepticism until they prove they were expected. PACIPV's two vectors encode exactly that distinction — same door, same four rooms (RRPVs), different manners.

Where it breaks: the analogy suggests prefetches should always be trusted less — but PACIPV's actual prefetch vector treats repeated prefetches to the same block as a stronger reuse signal than demand does, since a prefetcher re-requesting a block it already fetched is itself informative.
Insertion policy · Presumed dead, promoted fast

A probationary hire, promoted on the first good day

PACIPV's demand vector inserts every new block on probation — RRPV 3, the position closest to eviction, as if it's presumed unwanted. But the moment that block is touched again while still on probation, it jumps straight to RRPV 0, the most-trusted slot — one good day, full promotion. Blocks that are truly one-and-done get evicted quickly and cheaply; blocks with real reuse are recognized almost instantly.

Where it breaks: a probationary employee needs sustained good performance to earn full trust; PACIPV's rule is a single binary event (one hit while at RRPV 3), which works because instruction blocks tend to be either dead-on-arrival or hot, with little in between.
Why PC-based ideas fail here · Generalization

A witness who only ever saw one house

SHiP's PC-indexed table works like a detective cross-referencing a suspect (the PC) across many different crime scenes (data addresses), building real statistical confidence. An instruction fetch's PC is a witness who only ever visited one house — there's nothing to cross-reference, so the "witness" testimony collapses into a trivial, per-block statement with no generalizing power.

Where it breaks: some instruction-cache research does use PC-adjacent signals (e.g. control-flow history) productively — the failure is specific to load/store-style PC indexing, not to all forms of program-counter information.
Proxy vs target · MPKI vs IPC

Judging fitness by the scale, not how you feel

The bathroom scale (MPKI) is a convenient proxy, but it doesn't measure what you actually care about (feeling fast and capable, i.e. IPC). PACIPV can gain weight on the scale — more LLC misses overall — while genuinely improving performance, because it's deliberately shedding "cheap" misses (ones that overlap with others in flight) to keep the expensive, isolated ones from happening.

Where it breaks: the scale usually does correlate with fitness, and MPKI usually does correlate with IPC — this is the exception the paper flags explicitly, not the rule. Don't over-generalize "ignore MPKI."
The full explanation

How it actually works

Section by section, from the baseline it replaces to the counterintuitive result that explains why it wins.

1 · The baseline — one IPV, no distinction

SRRIP can itself be written as an IPV: [0,0,0,0,2]. Any hit, regardless of starting RRPV, jumps to 0; new blocks insert at 2. Critically, this same vector governs demand and prefetch accesses alike — SRRIP has no notion that a prefetch is a guess and a demand is a fact. That's the gap PACIPV targets.

2 · Two vectors, jointly filtered and searched

Doubling to demand + prefetch vectors squares the raw space (1,024 × 1,024). Two filters cut it down before simulation: (1) every IPV must be able to reach every RRPV — otherwise it wastes the granularity RRIP provides; (2) no IPV may demote a block on a hit — a just-accessed block should never be pushed toward eviction. Because the demand and prefetch vectors interact (they jointly decide what survives in each set), the paper filters and searches them as pairs, not independently — leaving 4,032 reasonable pairs to simulate exhaustively.

# victim selection — identical to SRRIP, no change here
find a block with RRPV == 3
if none exists:
    increment every RRPV in the set (age), retry

# PACIPV's only change: which vector answers the promotion/insertion question
on access to block at RRPV p:
    v = is_prefetch ? PREFETCH_IPV : DEMAND_IPV
    block.RRPV = v[p]              # p in 0..3 → promotion
on insertion:
    v = is_prefetch ? PREFETCH_IPV : DEMAND_IPV
    block.RRPV = v[4]              # insertion RRPV

3 · Training — split, sort, search, validate

Traces from the CVP-1 suite (commercial server/FP/crypto/integer workloads, anonymized) are split into disjoint training and testing sets, with care taken that no two traces of the same underlying benchmark cross the split. From the training set, the 100 workloads with the highest L1I average miss latency under LRU are chosen, all 4,032 candidate pairs are simulated on them, and the pair with the best geometric-mean IPC is kept. That fixed pair is then evaluated, unmodified, on the disjoint testing set's own top-100-by-L1I-latency workloads (Figure 4) — the 2.97% speedup over LRU reported there is out-of-sample.

4 · Hardware cost, side by side

💡
The 20 bits, exactly: 2 vectors × 5 elements × 2 bits/element = 20 bits, fixed at design time — not per cache line, not per set, just a one-time constant baked into the replacement logic.

5 · The counterintuitive result — higher MPKI, better IPC

On the testing set, PACIPV posts the highest LLC MPKI of every policy compared (LRU, SRRIP, DRRIP, SHiP, Mockingjay), yet also the highest IPC gain. The paper's explanation invokes memory-level parallelism (MLP): not all misses cost the same. A miss that overlaps with other outstanding misses is nearly free; an isolated miss stalls the pipeline for its full latency. PACIPV appears to sacrifice overlappable misses to protect blocks whose loss would otherwise cause expensive, isolated stalls.

🍯
Two facts ground this: PACIPV achieves the lowest average L1I demand miss latency among all compared policies despite its higher LLC miss rate. And Mockingjay's average demand miss latency is higher than SHiP's despite Mockingjay having the better speedup — the same decoupling appears there too, in the other direction. MPKI alone would rank both of these backwards.

6 · Generalizing beyond instruction-heavy workloads

Re-running the identical search on the data-heavy GAPS graph-analytics suite finds a different best pair — demand [0,0,0,1,3], prefetch [0,0,1,1,3]. Using the CVP-trained pair on GAPS ("PACIPV-I") already beats SRRIP and SHiP but lags Mockingjay by 7.8%; retraining on GAPS ("PACIPV-D") closes most of that gap, adding 6.67% speedup over the CVP pair and landing just 1.2% behind Mockingjay. The method — filter, exhaustively search, validate — is domain-agnostic; only the resulting five numbers change.

🧭
Connection to OS-managed memory tiering: this is structurally the same move as replacing a learned hot/cold page classifier with a small, exhaustively-tunable epoch/access-bit rule for DRAM↔NVM or CXL-tier placement — coarse, cheap, and re-derivable per workload class instead of one model trained once and hoped to generalize. This framing is ours, not the paper's.
Follow the numbers, step by step

Worked examples

Four traces using the paper's real vectors and figures, carried through completely.

① Tracing the demand IPV through a real set

A 4-way set holds blocks A(RRPV 3), B(RRPV 1), C(RRPV 2), D(RRPV 0), managed by the demand IPV [0,1,1,0,3]. A demand hit occurs on C, then a miss requires inserting a new block E, then E itself is hit again almost immediately.

  1. Hit on C (RRPV 2): apply V[2] = 1. C moves from RRPV 2 to RRPV 1. Set is now A=3, B=1, C=1, D=0.
  2. Miss — insert E: victim search looks for RRPV 3. Only A qualifies, so A is evicted. E is inserted at V[4] = 3. Set is now E=3, B=1, C=1, D=0.
  3. Hit on E (still RRPV 3): apply V[3] = 0. E jumps straight from 3 to 0 — full MRU trust on its very first reuse. Set is now E=0, B=1, C=1, D=0.
  4. Contrast with SRRIP's [0,0,0,0,2]: step 1 would have promoted C all the way to 0 immediately (not to 1), and step 3 would look identical (any hit → 0). The difference only shows up for a block hit while at RRPV 1 or 2 — PACIPV's demand vector is more conservative there.
🍯
Insight: PACIPV and SRRIP agree on the dramatic case (a block on death's door gets one chance) and disagree on the subtle case (partial promotion from the middle bins) — and that subtle disagreement, tuned by search rather than intuition, is worth the measured speedup.

② The search-space arithmetic

How big a deal is going from 16-way LRU IPVs to 4-state RRIP IPVs?

  1. Original (LRU, n=16): a 17-element vector, each element one of 16 values: 1617 = 268 = 295,147,905,179,352,825,856 ≈ 2.95 × 1020 vectors.
  2. RRIP-based (n=4), one vector: a 5-element vector, each element one of 4 values: 45 = 210 = 1,024 vectors.
  3. Reduction, single-vector to single-vector: 2.95 × 1020 ÷ 1,024 ≈ 2.88 × 1017 — a drop of about 17 orders of magnitude, matching the paper's own claim.
  4. Pairs (demand + prefetch): naively 1,024 × 1,024 ≈ 1.05 million pairs; the "must visit every RRPV" and "no demotion on hit" filters cut this to 4,032 reasonable pairs — small enough to simulate every one against training traces in a compute cluster run.
💡
This is why PACIPV can honestly claim to have found a global optimum within its restricted, interpretable space — something a genetic algorithm over 1020 candidates can never guarantee.

③ Retraining for a different workload domain

On the GAPS (data-heavy) suite, how much does retraining actually buy, and how close does it get to Mockingjay?

  1. Using the CVP-trained pair (PACIPV-I) on GAPS: beats SRRIP and SHiP, but trails Mockingjay by 7.8%.
  2. Retrain the identical search on GAPS traces: the winning pair changes to demand [0,0,0,1,3], prefetch [0,0,1,1,3] (PACIPV-D).
  3. Speedup gained from retraining alone: PACIPV-D adds 6.67% over the CVP-trained pair on GAPS — same mechanism, same hardware, five different numbers.
  4. New gap to Mockingjay: narrows from 7.8% down to just 1.2%.
  5. Confirmed in MPKI too: LLC demand MPKI drops from 17.78 (PACIPV-I) to 15.98 (PACIPV-D) on GAPS — the retrained vector isn't just faster on paper, it genuinely reduces misses on this workload class.
🧭
Tiering parallel (framing, not from the paper): this is the same argument for keeping migration thresholds in a CXL/NVM tiering system re-derivable per workload class rather than fixed at kernel-build time — a small, cheap-to-research parameter beats a large model trained once on the wrong distribution.

④ Why distinct IPVs matter so much

Section 5.2.4 compares the best single shared IPV against the best distinct demand/prefetch pair, tuned per benchmark.

  1. Best identical IPV (same rule for demand and prefetch): geomean speedup of 3.26%.
  2. Best distinct pair (PACIPV's actual design): geomean speedup of 12.41% — nearly 4× higher on this evaluation.
  3. Consistency: 75% of benchmarks show at least a 2-percentage-point greater speedup with distinct IPVs than with one shared vector.
  4. Reading it carefully: these numbers come from per-benchmark best-case tuning on the training set, so they're not directly comparable to the 3.3% testing-set headline — they isolate the specific value of the demand/prefetch split, not PACIPV's absolute real-world speedup.
💡
The magnitude of this gap is the strongest evidence in the paper that treating demand and prefetch accesses identically — which every prior RRIP variant does — is the real design flaw, not merely a minor inefficiency.

Problem 1 · medium
PACIPV has the highest LLC demand MPKI of every policy tested, yet the highest IPC gain. Explain how that's possible without contradiction.
Show answer
Not all misses cost the same cycle penalty. A miss that overlaps with other outstanding misses (memory-level parallelism) is nearly free; an isolated miss stalls the pipeline for its full latency. PACIPV appears to trade away cheap, overlappable misses in order to keep blocks in cache whose eviction would cause expensive, isolated misses — raising the miss count while lowering effective miss cost. This is confirmed by PACIPV having the lowest average L1I demand miss latency among all compared policies.Misconception: that MPKI is always a reliable stand-in for performance. It usually correlates with IPC, but a policy can deliberately decouple them by choosing which misses to allow.
Problem 2 · medium
SHiP-PC works well for data caches by indexing a table with the memory instruction's PC. Why does the same idea fail for instruction caches?
Show answer
A load/store PC in a data cache touches many different addresses over a program's run, giving a PC-indexed table many samples to learn a real cross-address pattern. An instruction fetch's PC effectively identifies one specific code block in the LLC — there's no second, different block for that same PC to generalize across. The table collapses into a trivial per-block record, not a learned pattern.Misconception: that PC-indexing is a generic trick applicable to any cache. It specifically depends on a many-address-per-PC relationship that data accesses have and instruction accesses don't.
Problem 3 · hard
Using demand IPV [0,1,1,0,3], a 4-way set has RRPVs A=2, B=3, C=0, D=1. A demand access hits block A. What is A's new RRPV? Then, if a new block E must be inserted immediately after (before any other access), which block is evicted, and at what RRPV does E start?
Show answer
A is at RRPV 2, so apply V[2] = 1 → A becomes RRPV 1. For the insertion, victim search looks for a block at RRPV 3: only B qualifies, so B is evicted. E is inserted at V[4] = 3.Misconception: that any hit promotes a block all the way to MRU (RRPV 0). Under this specific IPV, only a hit at RRPV 3 does that (V[3]=0) — a hit at RRPV 2 only advances one step, to RRPV 1 (V[2]=1).
Problem 4 · medium
Using one shared IPV for both demand and prefetch accesses gives a 3.26% geomean speedup; using distinct demand and prefetch IPVs gives 12.41% on the same evaluation. Why does the split matter so much?
Show answer
A demand access is a fact — the core needs this block now. A prefetch access is a guess — a predictor thought this block might be needed. Treating both with the same insertion/promotion rule either lets bad speculative guesses occupy cache space as if they were proven-needed, or under-trusts genuinely-reused demand blocks to compensate. Separate vectors let each access type be calibrated to its own reliability.Misconception: that a single, well-tuned vector should generalize across access types. Design goal (1) in the paper is explicitly to avoid this by giving demand and prefetch accesses independent rulebooks.
Problem 5 · easy
6 of 94 training workloads run slightly slower under PACIPV than under plain LRU. What access pattern does the paper hypothesize explains these, and why does it favor LRU?
Show answer
A palindromic reuse pattern — access a₀, a₁, …, aₖ, then aₖ, aₖ₋₁, …, a₁, a₀, repeated — is exactly the case precise LRU ordering was designed to exploit perfectly: it needs the exact reverse-of-access-order eviction sequence. RRIP's four coarse buckets throw away the fine-grained order this pattern depends on, so PACIPV (built on RRIP) can rank blocks slightly wrong relative to LRU for this specific pattern.Misconception: that a policy which wins on average must win everywhere. Average gains are compatible with occasional, explainable losses on workloads that match the baseline's exact assumptions.
Problem 6 · hard
The original IPV work searched a 1617 ≈ 2.95 × 1020-vector space with a genetic algorithm. PACIPV instead exhaustively searches 4,032 filtered RRIP-based IPV pairs. Name two concrete problems with the genetic-algorithm approach that exhaustive search avoids.
Show answer
(1) You can never confirm a genetic algorithm reached the global optimum — it's a heuristic over an intractable space, so the result is "good," not "best." (2) 17 free parameters over that huge a space invites overfitting to the specific training workloads, and the resulting vector is a 17-number string described in the paper as "incomprehensible to the average practitioner." Exhaustive search over 4,032 candidates guarantees the true best-in-space answer, and the resulting 5-number vector is small enough for a person to read and reason about.Misconception: that a larger, more expressive search space is always better. A deliberately restricted, fully-searchable space beat an intractable one searched heuristically, on this problem.
Quick answers

Frequently asked questions

Eight questions newcomers ask most. Tap any to expand.

Q1What exactly is an IPV?▾
An Insertion/Promotion Vector: a small lookup table, one entry per possible recency value, that says where a block moves on a hit (promotion) or where it starts on a miss (insertion). For RRIP's 4 RRPVs, an IPV is a 5-element vector. SRRIP, DRRIP, and PACIPV are all just different choices of this vector — the mechanism generalizes replacement policy design into a search problem.
Q2Isn't PACIPV just SRRIP with extra steps?▾
Structurally, yes — same RRPV bits, same aging/victim-selection logic. The entire difference is which numbers fill the IPV, and that PACIPV uses two IPVs (demand, prefetch) instead of SRRIP's one shared vector. That's the point: a tiny, principled change to existing RRIP hardware, not a new mechanism.
Q3Why separate vectors for demand and prefetch instead of just tagging blocks as "prefetched"?▾
Because reuse information lives in the access, not permanently in the block. The same physical cache line can be touched first by a prefetch and later by a demand access — PACIPV applies the matching IPV to each individual event, rather than freezing a block's classification at insertion time.
Q4Doesn't inserting new instruction blocks as "presumed dead" (RRPV 3) risk evicting useful code too soon?▾
It risks a quick eviction only if the block is never touched again — in which case nothing was lost. If it is touched again while still near RRPV 3, the demand vector's V[3]=0 rule promotes it straight to MRU on that single hit, so genuinely useful blocks recover full trust immediately rather than being evicted before they get a second chance.
Q5If Mockingjay is more accurate, why would anyone actually ship PACIPV?▾
Mockingjay's edge is small (3.2% vs. PACIPV's 3.3% with EIP; PACIPV even edges ahead) and comes at roughly 4.5× the storage overhead (56 KB total vs. PACIPV's 12 KB) plus substantial design/verification cost for its predictor logic. For instruction-heavy workloads specifically, the paper argues PACIPV captures nearly all the achievable benefit at a fraction of the engineering cost — a classic 80/20 trade in favor of the 20.
Q6Does PACIPV need the program counter like SHiP or Hawkeye?▾
No — and this is deliberate. PACIPV only needs a block's current RRPV and whether the triggering access is demand or prefetch, both already visible to any LLC controller. This matters even when a PC channel is technically buildable: if the LLC sits behind third-party licensed IP, the PC may never be exposed to it at all.
Q7Is PACIPV limited to instruction-heavy workloads?▾
No — the vectors it ships with are, but the method isn't. Retraining the identical search (filter, exhaustively simulate, pick the best pair) on the data-heavy GAPS suite finds a different winning pair that closes most of the gap to Mockingjay there too. The paper explicitly frames PACIPV as a methodology for finding good vectors, not a fixed proposal of specific ones.
Q8What's left for future work?▾
The paper mentions exploring more than 4 RRPVs (a larger, still-tractable search space), and using set-dueling to dynamically pick between multiple trained IPV pairs at runtime rather than fixing one pair statically — both left unexplored in this paper, which focuses on the static, single-domain case.

Glossary, results, and provenance

Every term in one place, the headline numbers, then a note on what's paper vs. framing.

Core terms
PACIPVPrefetch Aware Coarse-grained Insertion and Promotion Vectors — this paper's replacement policy: two RRIP-based IPVs, one for demand and one for prefetch accesses.
IPVInsertion/Promotion Vector — a table mapping a block's current recency value to its next value (on hit) or its starting value (on insertion).
RRIP / RRPVRe-Reference Interval Prediction and its 2-bit prediction value (0=near-immediate … 3=distant) — the coarse-grained recency scheme PACIPV builds on.
SRRIP / DRRIPStatic / Dynamic RRIP. SRRIP is the IPV [0,0,0,0,2] applied identically to demand and prefetch. DRRIP set-duels between two SRRIP insertion policies.
MockingjayA cache replacement policy emulating Bélády's optimal MIN policy using a sampled cache, a reuse-distance predictor, and ETA counters; the paper's state-of-the-art complexity baseline.
SHiPSignature-based Hit Predictor — indexes a table by a hash of the memory instruction's PC to predict reuse; effective for data, ineffective for instructions.
EIPEntangling Instruction Prefetcher — an aggressive instruction-cache prefetcher used alongside PACIPV in the evaluation.
MLPMemory-Level Parallelism — the degree to which multiple outstanding misses overlap in time; the proposed explanation for PACIPV's higher-MPKI-but-better-IPC result.
Supporting terms
Demand / prefetch accessA property of the individual memory request, not the cache block — demand means the core needs it now, prefetch means a predictor guessed it would.
MPKI / IPCMisses Per 1000 Instructions and Instructions Per Cycle — the miss-rate and speed scorecards; this paper's central result is that they can diverge.
ChampSimThe open-source microarchitectural simulator used for all evaluation, configured to approximate an Intel Alder Lake core.
SimPointA methodology for selecting representative program phases as short simulation traces; each trace in this study is one SimPoint.
CVP / GAPSChampionship Value Prediction traces (commercial, largely instruction-heavy) and the GAP graph-analytics benchmark suite (data-heavy) — the two workload domains PACIPV is trained and tested on.
FDIPFetch-Directed Instruction Prefetching — the decoupled front-end mechanism ChampSim models alongside EIP.
Dead block predictorA predictor guessing whether a cached block will never be referenced again — the general category PACIPV's insertion-at-RRPV-3 rule crudely but cheaply approximates.
