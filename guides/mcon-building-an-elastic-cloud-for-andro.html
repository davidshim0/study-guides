One phone's framework, borrowed by a hundred tenants

Cloud-run Android apps each drag along a full copy of the mobile OS's heavyweight framework. MCon shares one framework across tenants instead — and fakes isolation from the outside.

📄 "MCon: Building an Elastic Cloud for Android Apps" · Qiu et al. 🎓 Some OS/container basics assumed — the primers cover them ⏱ ~25 min read
📱

Consolidate the expensive, shared parts of the stack (the framework); isolate them from outside, at the IPC boundary — not by rewriting the framework itself.

1What a "mobile framework" is▾

Below the apps and above the kernel sits a huge userspace layer of shared libraries and system services (package manager, window manager, sensors, etc.) — the framework. In Android 13 it's 60+ long-running processes hosting 242 services, ~7.5M lines of code. Most privileged operations (opening a file, showing a window) route through it, though some high-throughput paths — like certain file I/O and GPU/display traffic — go straight through the kernel instead.

Now you're ready: this framework is what MCon shares across tenants instead of booting one per tenant.
2Why mobile clouds use VMs, not bare containers▾

Server GPUs (NVIDIA) ship no drivers for mobile OSes, so mobile clouds run a para-virtualized GPU inside a VM that speaks a translated graphics protocol to the real host GPU. That's why even "container" stacks like Redroid still sit inside one long-running VM.

Now you're ready: MCon keeps this same VM+para-virtual-GPU base — its contribution is what happens above and around it.
3Binder IPC and AIDL▾

Apps run sandboxed and can't call privileged code directly; they send a typed message over Binder (Android's IPC transport) to a system service, using an interface generated from an AIDL spec. Most privileged operations cross this narrow, stable boundary — though the paper notes some high-throughput paths, like GPU/display traffic and certain file operations, go straight through the kernel instead, which is why MCon also leans on UID isolation and device slicing for those.

Now you're ready: MCon's entire isolation trick lives at this boundary — it rewrites Binder traffic, not the framework's internals.
4UID sandboxing▾

Every Android app runs as its own Linux UID, and the kernel enforces normal file/process permissions between UIDs — independent of anything the framework does.

Now you're ready: MCon maps each tenant to distinct UIDs as a cheap defense-in-depth layer beneath its own IPC-level isolation.
5cgroups and resource control▾

Linux cgroups let you cap how much CPU or memory a process group can consume, without changing the code inside it.

Now you're ready: MCon uses cgroups for coarse CPU/memory quotas, plus a custom token-bucket for fine-grained IPC-call fairness.
6Namespaces, generally▾

A namespace gives a process a private view of some global resource (PIDs, network, filesystem) while a single kernel underneath still manages the real thing. Linux containers are built from several such namespaces.

Now you're ready: MCon builds its own application-level "framework namespace" the same way — a private view over a shared resource — but implements it by rewriting IPC, not kernel syscalls.
7Why elastic-compute tricks (microVMs, snapshots) don't transfer here▾

Firecracker-style microVMs shrink VMM/kernel boot to under two seconds — but mobile provisioning is dominated by framework init above that layer. Snapshot/pre-warm techniques help, but only for one fixed device profile; mobile workloads need hundreds of screen/DPI profiles, which fragments any snapshot pool.

Now you're ready: the bottleneck MCon targets is structurally different from what serverless platforms already solved.
The whole story in one place

MCon in a nutshell

The bottleneck, the fix, and how the pieces click together.

Every existing mobile cloud stack — one VM per instance, or many containers packed into one VM — still gives each tenant its own full copy of the mobile framework. That framework takes tens of seconds to initialize and eats 80% of memory and 35% of CPU per instance, so duplicating it caps both how fast you can provision instances and how many fit on a server.

MCon's fix is framework consolidation: run one framework as a shared, multi-tenant service. The hard part is that Android's existing multi-user support isn't enough: it still assumes one global package namespace, one shared device profile, and framework-wide visibility across users. MCon solves this without rewriting the framework's service internals — instead it generates and injects an IPC proxy into the framework's AIDL bindings (about 3K lines of framework-side code) that intercepts and rewrites the IPC traffic (Binder/AIDL calls) apps use to reach it — a framework namespace per tenant. Because high-throughput GPU/display traffic can't be cleanly virtualized this way without contention, MCon separately gives each tenant its own virtual device slice in its own host process.

🍯 Key takeaways

  • The bottleneck is the framework, not the VM/kernel — that's why microVM boot optimizations don't help here.
  • Framework namespaces isolate logically by rewriting IPC (names, visibility, routing) via a ~3K-LOC framework-side proxy — the framework's own service logic is never rewritten.
  • Virtual device slicing isolates performance by giving each tenant separate GPU/display processes — fixing driver lock contention.
  • Package binaries can be aliased (shared read-only) across tenants running the same app — deployment scales with distinct apps, not tenant count.
  • Threat model: single-provider, semi-trusted tenants — not mutually-distrustful public clouds.
Five everyday pictures

How to think about MCon

Each stands alone. Every card ends with where the picture stops holding.

The core idea

A shared kitchen with private lockers

A commercial kitchen (the framework) is expensive to build and run — so several food stalls share one, each with a locked pantry (a namespace) for their own ingredients. Nobody duplicates the ovens.

Where it breaks: if the shared kitchen catches fire, every stall stops cooking — a framework crash halts all co-located tenants at once.
IPC proxy

A translator at the border

App X asks for "package X"; a translator standing at the crossing rewrites it to "X.1" before the framework hears it, and translates the answer back. Neither side notices the substitution — the app still sees plain "X", while the framework only ever sees distinct virtualized names like "X.1", "X.2" for each tenant, never a naming collision.

Where it breaks: the translator must sit on the framework's side of the border, not the app's — otherwise a malicious app could just skip the translator and speak raw.
Token bucket / cgroups

A building's shared water meter

All apartments draw from one water main; each unit gets a flow cap so one long shower doesn't starve the rest. That's cgroups (CPU/memory) plus a token bucket (IPC call budget) on top of the shared framework.

Where it breaks: a cap only limits rate, not correctness — a buggy tenant can still send malformed requests within its quota, which is why default-deny validation exists separately.
Device slicing

Private lanes off a shared highway

Everyone merging onto one lane causes gridlock at busy on-ramps (shared GPU driver locks). Give each tenant its own lane (a separate device-slice process) and traffic stops blocking on other cars' bumpers.

Where it breaks: lanes still funnel onto the same physical road (one GPU) — slicing removes software contention, not the hardware's total capacity.
Complexity-aware frame pacing

Cruise control learning the road's grade

You can't trust the speedometer alone on a hilly road with traffic (noisy wall-clock GPU time); but you know the car can never go faster than the engine physically allows on flat ground. Track the minimum observed time-per-complexity to learn the true "flat-road" rate, then pace accordingly.

Where it breaks: if the road's grade changes fast (frequent shader switches), the single learned rate lags and needs to re-converge — the paper measures a 15% stdev penalty in that case.
The full explanation

How it actually works

Section by section, with the paper's real numbers.

1 · The bottleneck, quantified

Android 13's framework spans 60+ processes and 242 system services. Under top-50-app workloads it takes tens of seconds to initialize and consumes 80% of per-instance memory and 35% of CPU cycles on average. Every existing stack — one-VM-per-instance emulators or many-containers-in-one-VM systems — pays this cost per tenant, which is why baselines cap out around 8–32 instances per server and take >15s to cold-boot.

2 · Policy engine — operations on tenant-scoped objects

Instead of writing one-off rules per API, MCon classifies objects into four generic operations:

OperationEffectExample
Virtualizeappend a tenant suffixcom.app → com.app.1
Filterhide other tenants' objectsprocess/task lists
Routesend I/O to the right device slicedisplay, input
Rejectdeny global/privileged changessystem-wide settings

Of Android 13's 10,511 framework APIs, 2,473 (23.5%) touch a tenant-scoped object and get transformed; the rest pass through untouched. Only 79 of 878 framework object types are tenant-scoped — a small, auditable surface despite the framework's huge size.

⚠
Default-deny: at build time MCon records every known API signature; at runtime, an unrecognized or changed signature is rejected. This catches both missed APIs during an OS upgrade and a compromised service presenting a signature that didn't exist at build time.

3 · Why device sharing collapses performance

Stress-testing shared virtual GPUs at 128 concurrent contexts: aggregate FPS collapses to just 2.2–3.5% of peak (vSoC, GAE), with jitter (CV) of 0.192–0.374. The cause: multi-threaded GPU drivers hold process-wide locks — a "lightweight" call like glBindBuffer balloons from microseconds to ~1.2ms, with 38–46% of CPU time stuck in futex waits, >60% of it inside the closed-source NVIDIA driver. Redroid avoids locks with a single-threaded model but then plateaus at ~70% of peak from serialization.

4 · GPU frame pacing (Algorithm 1, condensed)

// per frame, complexity C from shader invocation counts
K ← sliding_min(T_real / C)        // learn true hardware rate, reject noise
T_est ← C × K                       // ideal processing time for this frame
E ← T_est − T_real + T_custom        // error vs. policy target
T_sleep ← max(T_prev_sleep + Kp·(E−E_prev) + Ki·E, 0)  // PI control
if T_sleep > 0: sleep(T_sleep)

Tracking the minimum observed time-per-complexity filters out CPU-side scheduling noise (a 10ms GPU job can look like 50ms under contention). A default policy sets T_custom to equalize GPU time across tenants; disabling pacing doesn't hurt average FPS but raises stdev by 69–107% at 16–64 tenants.

5 · Why provisioning gets so fast

Cold-allocating one tenant takes 0.99s in MCon vs. a >15s floor for baselines that must boot a full framework. Profiling the 0.99s: 60% goes to sequential multi-user setup (a defense-in-depth layer), 4% to spawning the device slice, and the rest to hotplugging and app startup.

Follow the numbers

Worked examples

Four calculations straight from the paper's reported figures.

① What does "15× faster" mean in seconds?

  1. MCon's single-tenant cold provision: 0.99 s.
  2. Paper states MCon is 15–58× faster than baselines across density levels.
  3. At the 15× end: baseline time ≈ 0.99 × 15 = ~14.9 s — matches the paper's separately stated ">15s latency floor" for baselines.
  4. At the 58× end: baseline time ≈ 0.99 × 58 ≈ 57.4 s — consistent with baselines degrading further at higher density.
🍯
Two independently reported numbers (the ratio and the floor) cross-check to within rounding — a good sign the measurement is self-consistent.

② Idle host-memory reduction

  1. MCon's marginal cost per additional idle tenant: 357 MiB host memory (beyond a one-time 2.1 GiB framework+VM cost).
  2. A baseline's per-tenant cost at the high end of its reported range: 3.0 GiB = 3072 MiB.
  3. Reduction = (3072 − 357) / 3072 = 88.4%.
  4. This falls inside the paper's reported 85–92% idle host-memory reduction — the low end of that range corresponds to baselines nearer 1.7 GiB/tenant.

③ Why only 23.5% of APIs need transforming

  1. Android 13 exposes 10,511 framework APIs total.
  2. MCon transforms 2,473 of them → 2473/10511 = 23.5%; the remaining 8,038 (76.5%) pass through untouched.
  3. This works because transformation is driven by object type, not API: only 79 of 878 object types (9.0%) are tenant-scoped.
  4. Naming heuristics for primitive arguments (e.g. plain strings) initially mis-fired: 6 false positives + 92 false negatives = 98 errors — corrected with exactly 98 explicit policies.
💡
Coverage scales with the number of object types, not the size of the API surface — which is what keeps porting across Android versions cheap (§6: only 5 tenant-scoped objects changed between Android 13 and 15).

④ Where does the 60%-multi-user cost prediction check out?

  1. Paper: multi-user setup accounts for 60% of the 0.99s single-tenant provisioning latency.
  2. Predicted latency without multi-user: 0.99 × (1 − 0.60) = 0.396 s.
  3. Paper's directly measured value with multi-user disabled: 0.40 s — matches the prediction almost exactly.
  4. Separately, the 28 µs average IPC overhead splits into 16.5 µs (58%, policy lookup) + 9.6 µs (34%, deep-copy) + 2.3 µs (8%, transform) = 28.4 µs, and 58+34+8 = 100% — the components fully account for the measured total.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Android's built-in "multi-user" already lets several accounts share a device. Why isn't that enough for MCon's cloud use case?
Show answer
Multi-user assumes mutually trusted co-users on one device: it still uses a global package namespace (two users can't run different versions of the same app) and shares one device profile and device-wide visibility (screens, process lists). MCon needs isolated, independently-configured tenants — a different requirement multi-user was never designed for.Misconception: that "multi-user" and "multi-tenant" mean the same isolation guarantee.
Problem 2 · medium
A server has 120 GiB of memory. MCon's framework costs a fixed 2.1 GiB, then 357 MiB per tenant. A baseline costs ~2 GiB per tenant with no fixed cost. Roughly how many tenants can each fit (memory only)?
Show answer
MCon: (120 − 2.1) GiB / 0.357 GiB ≈ 330 tenants. Baseline: 120 GiB / 2 GiB = 60 tenants. MCon's ~5.5× density advantage here comes entirely from amortizing the framework's fixed cost across many tenants. Caveat: this is host memory only — in the paper's actual measurements, GPU memory fragmentation and per-device limits capped real tenant density far below this host-memory-only estimate, so 330 is a ceiling on one resource, not a realistic system capacity.Misconception: that per-tenant footprint alone determines density — the one-time framework cost matters far less as tenant count grows, but other resources (GPU memory, device slots) can cap density first.
Problem 3 · medium
MCon's reported savings are much bigger for host memory (70–82%) than for GPU memory (1–33%). Why the gap?
Show answer
Host memory savings come from consolidating the framework — a huge, mostly-duplicated cost. GPU memory, by contrast, is dominated by per-tenant virtual device state (vGPU/vDisplay contexts), which MCon still provisions one-per-tenant via device slicing — it isolates GPU resources rather than sharing them. So GPU savings only reflect lighter virtual devices, not consolidation.Misconception: that MCon consolidates everything. It deliberately does the opposite for the device layer — see the hybrid architecture in §3.
Problem 4 · hard
Why does MCon need a build-time "default-deny" allowlist of API signatures, given the framework already has 79 known tenant-scoped object types?
Show answer
Classification only covers what's known at build time. Two gaps remain: (1) a version-migration gap, where an OS upgrade introduces a new or changed API that engineers missed during review; (2) runtime tampering, where a compromised service presents a signature that never existed at build time. Default-deny closes both by rejecting anything unrecognized rather than assuming it's safe to pass through.Misconception: that a correct static classification (however carefully audited) is sufficient at runtime — it isn't, without a fail-safe default.
Problem 5 · medium
§7.6 shows consolidation alone (no slicing) makes throughput 14–26% *worse* than baselines at density 16. Why would sharing the framework ever hurt performance, and what fixes it?
Show answer
Consolidation alone still routes all tenants' device commands through one shared virtual GPU/display, hitting the same driver lock contention measured in §5.1. Virtual device slicing fixes this by giving each tenant its own device process — it's a separate mechanism from framework namespaces, needed specifically because the device layer is performance-critical in a way the framework's control-plane APIs aren't.Misconception: that consolidating the framework automatically consolidates (or should consolidate) the device layer too — MCon deliberately treats them differently.
Problem 6 · hard
Redroid's single-threaded GPU driver model avoids the lock contention that hurts vSoC/GAE, yet it still plateaus at ~70% of peak FPS. Why doesn't single-threading solve the problem?
Show answer
Single-threading trades lock contention for a CPU bottleneck: one thread must serialize every tenant's commands and pay context-switch overhead, capping throughput regardless of density. Neither in-process design (multi-threaded-with-locks or single-threaded-serial) escapes the ceiling — which is why MCon moves isolation to the process level (separate address spaces) instead of tuning the threading model within one shared process.Misconception: that GPU contention is purely a locking/threading bug fixable with better in-process scheduling — the paper argues it's structural, requiring process-level separation.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does MCon share across tenants?▾
Only the mobile framework (system services, libraries) and the guest kernel/VM. Each tenant still gets its own apps, its own virtual device slice (GPU/display/input), and its own private view of framework state via a framework namespace.
Q2Why can't Firecracker-style microVMs fix mobile provisioning?▾
Mobile VMM/kernel boot is already under 2 seconds. The tens of seconds that dominate provisioning happen in the framework layer, above what microVMs optimize — a different bottleneck entirely.
Q3How does MCon isolate tenants without rewriting the framework's service internals?▾
It intercepts IPC (Binder/AIDL) calls in an auto-generated proxy layer injected into the framework's AIDL bindings (~3K LOC of framework-side code), and rewrites tenant-scoped objects (package names, process lists, etc.) before they reach or leave the framework. Individual services' own logic is never touched, but from inside the framework, each service only ever sees virtualized per-tenant identities like app.1 and app.2 — not a single unmodified "one user" view.
Q4If the framework is already shared safely, why also need device slicing?▾
Framework IPC is low-throughput and easy to isolate logically. GPU/display traffic is high-throughput and performance-critical; sharing it causes severe driver lock contention (FPS collapsing to 2.2–3.5% of peak at high density). Slicing gives each tenant a separate device process instead.
Q5Is MCon safe for public, mutually-distrustful clouds?▾
No — its threat model explicitly targets single-provider, semi-trusted deployments (internal RL training, CI/testing). The framework is inside the trusted computing base, so a framework compromise affects every co-located tenant.
Q6Why is the GPU memory saving (1–33%) so much smaller than host memory (70–82%)?▾
GPU memory is dominated by per-tenant virtual device state, which MCon still provisions per tenant (via slicing, not consolidation). Only the lighter weight of MCon's virtual devices themselves accounts for the modest GPU savings.
Q7What happens if the shared framework crashes?▾
All tenants on that framework instance are disrupted until it restarts; live app state is lost and affected apps restart. Measured MTBF is 243h at 1 tenant and 34h at 64 tenants, implying roughly 20s of outage per failure at low density and ~2.5 minutes at 64 tenants.
Q8How expensive is it to keep MCon updated across Android versions?▾
Migrating from Android 13 to 15 took ~20 developer-hours (7h reviewing API changes, 3h updating policies/tests, 10h debugging), because maintainers only need to track the stable set of ~79 tenant-scoped objects — only 5 changed between those versions — not all 10,511 APIs.

Core terms
Framework consolidationRunning the mobile framework as one shared, multi-tenant service instead of duplicating it per tenant.
Framework namespaceA per-tenant private view of framework/device resources, constructed by transforming IPC traffic — not a kernel namespace.
