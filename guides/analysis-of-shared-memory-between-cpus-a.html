The GPU with no memory of its own

NVIDIA's DGX Spark gives its GPU zero local memory and lets it reach into the CPU's DRAM directly, coherently. This is the plain-English tour of what that trade actually buys — and costs.

📄 "Analysis of shared memory between CPUs and GPUs" · Alcaraz, Hepkema, Mageirakos, Dann, Alonso 🎓 Assumes you already know memory hierarchies — no cache-101 here ⏱ ~18 min read
🔗

Don't move the data to the GPU — give the GPU a coherent path to where the data already lives, and accept the shared bandwidth ceiling that comes with it.

Before you begin

Quick glossary + what's DGX-Spark-specific

You already know caches, DRAM/NVM tiering, and coherence protocols. The primers below skip that and focus on what's specific to this platform and CUDA's memory APIs.

Quick glossary

GB10The "Grace Blackwell Superchip": 20 Arm CPU cores (10 Cortex-X925 + 10 Cortex-A725) + a Blackwell GPU on one package.
LPDDR5XThe 128 GB of conventional mobile-class DRAM on the CPU socket — the *only* memory in the system, shared by CPU and GPU.
NVLink-C2CThe coherent chip-to-chip interconnect linking Grace's CPU cores to the Blackwell GPU inside the package — faster than PCIe, but not a separate memory pool.
HBM / VRAMHigh-bandwidth memory local to a discrete GPU. DGX Spark's GPU has none — this is the whole point of the paper.
HMM / ATSHeterogeneous Memory Management / Address Translation Services — OS+hardware mechanisms letting a GPU walk host page tables directly, avoiding explicit staging.
UMCUDA "Unified Memory" (cudaMallocManaged) — a single virtual address migrated between pools on demand. On DGX Spark there's only one physical pool to migrate within.
TPC-HThe standard decision-support SQL benchmark used here to evaluate end-to-end query performance under each allocator.
ValkThe paper's own GPU meta-profiler: merges hardware counters, execution traces, and query plans into one queryable, visual performance dataset.
cudaHostAlloc — CPU-accessible sweet spot cudaMalloc — GPU-only, isolated DGX Spark machinery (NVLink-C2C, UM, Valk) malloc / explicit copy — the slow baseline
1Why DGX Spark isn't "just a small Grace Hopper"▾

Grace Hopper still gives the GPU its own local HBM, coherently linked to the CPU's LPDDR5X — two pools, one address space. DGX Spark deletes one of the pools entirely: the GPU has zero local memory. Every byte it touches lives on the CPU socket.

Now you're ready: this is a more extreme, an order-of-magnitude cheaper point in the same design space — good for reasoning about what you give up when you remove the GPU's local tier altogether.
2Five CUDA allocators, one physical pool▾

malloc, cudaHostAlloc, cudaMallocManaged, malloc+cudaHostRegister, and cudaMalloc all ultimately land in the same 128 GB of LPDDR5X on DGX Spark — they differ only in CPU-accessibility, GPU-side bandwidth, and allocation/deallocation cost, not in *where* the bytes physically go.

Now you're ready: the paper's Table 1 is a Pareto comparison across exactly these five knobs, not a comparison of memory locations.
3Why cudaMalloc still needs a copy here▾

Counterintuitively, cudaMalloc buffers are *not* directly writable from the CPU on DGX Spark, even though the underlying memory is the same LPDDR5X the CPU could otherwise touch directly. If your data originates on the CPU, a cudaMalloc destination forces an explicit cudaMemcpy.

Now you're ready: "unified physical memory" doesn't automatically mean "any allocator can be written from either side" — the driver still gates access per allocation type.
4The transfer-bottleneck literature in one line▾

On PCIe-attached GPUs, moving query data across the link accounts for 67–98% of total TPC-H-style query runtime. The field's five standard fixes: transfer less (filter first), transfer fewer bytes (compress), transfer once (cache), hide the transfer (overlap with compute), or use a faster link (Grace Hopper).

Now you're ready: DGX Spark's pitch is a sixth option — skip the transfer step entirely, at the cost of a shared, lower bandwidth ceiling. Section 3 in "How It Works" walks through why that's structurally different, not just "fix #5 again."
5Why Valk can't see "device memory traffic" here▾

Standard GPU profilers meter traffic crossing into the GPU's own VRAM. DGX Spark's GPU has no VRAM boundary to meter, and NVIDIA's profilers don't expose CPU-side LPDDR5X bandwidth either — so Valk's timeline has a genuine, acknowledged blind spot on this platform.

Now you're ready: an observability gap worth flagging if you're used to CXL/tiering telemetry (e.g. PEBS-based access counting) — the tooling here hasn't caught up to the architecture.
The whole story in one place

DGX Spark in a nutshell

What's traded away, what's gained, and where the five CPU-accessible CUDA allocators actually sit.

Discrete CPU–GPU systems keep two physical memories and move data across PCIe, a link slow enough that transferring query data costs 67–98% of runtime in relational workloads. Grace Hopper narrows this by giving the GPU its own HBM behind a fast coherent link, but at high cost. The NVIDIA DGX Spark takes the trade further: its GB10 Grace Blackwell Superchip gives the GPU no local memory at all. All 128 GB of LPDDR5X lives on the 20-core Grace CPU socket, and the Blackwell GPU reaches it entirely through the coherent NVLink-C2C link — every GPU byte is read from, and written to, CPU memory.

This is the paper's "sixth approach" to the transfer bottleneck: instead of filtering, compressing, caching, overlapping, or speeding up a transfer, DGX Spark removes the transfer step by construction — the GPU dereferences the same addresses the CPU already produced its data in. The price is a shared, nominal 273 GB/s bandwidth ceiling that CPU and GPU compete for, in a package that costs roughly one order of magnitude less than large discrete-GPU systems.

Underneath, five CUDA allocators (malloc, cudaHostAlloc, cudaMallocManaged, malloc+cudaHostRegister, cudaMalloc) all write into that one pool, but differ sharply in GPU-side bandwidth and allocation overhead — and the authors measure exactly that trade-off with microbenchmarks, then with real TPC-H queries using their own profiler, Valk.

🔶 Key takeaways

  • DGX Spark's GPU has zero local memory — everything is CPU-attached LPDDR5X, reached via coherent NVLink-C2C.
  • Nominal bandwidth is 273 GB/s, shared between CPU and GPU — a ceiling, not a per-processor allowance.
  • cudaHostAlloc is the CPU-accessible sweet spot: high GPU bandwidth, low alloc/dealloc overhead.
  • cudaMalloc is fastest for the GPU but isn't CPU-writable here — it still needs an explicit copy.
  • The pitch is a sixth fix for the PCIe transfer bottleneck (67–98% of query runtime elsewhere): eliminate the transfer, don't just shrink or hide it.
  • Price point is roughly one order of magnitude below large discrete-GPU systems.
  • Their profiler Valk exposes a real gap: no device-memory-traffic counters exist for a GPU with no device memory.
Five everyday pictures

How to think about it

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Unified memory

A studio apartment, not two rooms

A studio has one shared floor space instead of a bedroom-and-office wall to carry boxes across. DGX Spark's CPU and GPU work in one physical LPDDR5X pool — nothing to pack, ship, or unpack between them.

Where it breaks: a studio still has one front door. Both occupants share the same LPDDR5X bandwidth (273 GB/s nominal) — crowding is still possible, it just happens at the door, not in transit.
Choosing an allocator · Table 1

A shared drawer vs. a locked safe

cudaHostAlloc is a shared drawer both CPU and GPU can reach into quickly. cudaMalloc is a bank's private safe — the teller (GPU) gets in fast, but you (the CPU) need a courier (cudaMemcpy) to put anything in first.

Where it breaks: the safe isn't actually more secure or physically separate — it's the same building (same LPDDR5X). The "lock" is a software policy, not a distance.
The alternative · Explicit copy path

Renting a moving truck

malloc → cudaMalloc → cudaMemcpy is renting a truck: you get the fastest highway speed (GPU bandwidth) once loaded, but every trip costs packing and unpacking time, and nothing is usable mid-transit.

Where it breaks: a truck trip is a one-time cost for a permanent move. A GPU kernel launch may repeat this "move" every time — the overhead doesn't amortize the way a house move does.
The framing · "Sixth approach"

Not flying, instead of packing lighter

Filtering, compressing, caching, overlapping, faster links — all are ways to deal with an airline's baggage limit. DGX Spark's move is different in kind: don't fly at all, keep everything at home. It doesn't beat the baggage-limit strategies; it removes the flight.

Where it breaks: "staying home" has its own ceiling — you're bandwidth-limited by your own driveway (LPDDR5X, 273 GB/s), which can be slower than a fast enough flight (e.g. Grace Hopper's HBM path) for the biggest jobs.
The profiler · Valk

One flight recorder for four instruments

Valk merges hardware counters, system polling, execution traces, and query plans the way a flight-data recorder merges altimeter, engine, and control-surface logs into one timeline you can actually correlate.

Where it breaks: a real flight recorder has a sensor for every quantity that matters. Valk's "device memory traffic" track is empty on DGX Spark — there's no instrument for a quantity (device-local memory bandwidth) that doesn't exist on this airframe.
The full explanation

How it actually works

Topology, the five allocators, the "sixth approach," and where the profiler has to give up.

1 · Topology — one memory, reached two ways

Unlike a discrete GPU (separate VRAM behind PCIe) or Grace Hopper (separate HBM behind a fast coherent link), DGX Spark's GB10 superchip puts the only memory — 128 GB LPDDR5X — on the CPU socket. The GPU has no memory pool of its own; every access, read or write, travels the coherent NVLink-C2C link to the same DRAM the CPU uses.

2 · The five CUDA allocators, measured

Table 1 (32 GiB sequential-read microbenchmark) ranks them on GPU bandwidth, allocation/deallocation cost, and whether a data copy is needed:

AllocatorPathGPU bandwidthAlloc/dealloc costNo copy?
cudaHostAllocCPU→GPU++-✓
cudaMallocManagedCPU→GPU++---✓
mallocCPU→GPU+--✓
malloc+cudaHostRegisterCPU→GPU+-✓
cudaMallocGPU-only+++--✓ (but not CPU-writable)
malloc→cudaMalloc→cudaMemcpyexplicit copy+++--✗
🔶
cudaHostAlloc is the highest-bandwidth option that's still directly CPU-writable and cheap to allocate — the paper calls it the default mode for a CPU-write→GPU-read pipeline.

3 · Why this is a "sixth approach," not a faster fifth one

Approaches 1–5 in the literature (filter, compress, cache, overlap, faster link) all keep a transfer step and try to shrink, hide, or speed it up. DGX Spark instead places CPU-produced data directly in the memory the GPU already coherently sees — there is no staging buffer, no cudaMemcpy, no explicit device-copy call in the common path.

4 · Evaluating it: TPC-H through Valk

The authors run the full TPC-H suite under each allocation policy and inspect results in Valk, which merges hardware counters, system polling, execution traces, and query plans into one queryable profile. Its UI overlays a timeline (operators, kernels) with core utilization and instruction throughput, plus a roofline view and a SQL-queryable counter table — but its "device memory traffic" track is empty here: DGX Spark has no device-local memory boundary to meter, and NVIDIA's profilers don't expose LPDDR5X bandwidth from the CPU side either.

⚠
Observability gap: the one metric you'd most want on a shared-memory system — realized bandwidth contention between CPU and GPU — is exactly the one the tooling can't currently show.
Follow the numbers

Worked examples

Three short calculations, using the paper's actual figures.

① Sizing the microbenchmark against the memory pool

Table 1's sequential-read test uses a 32 GiB buffer. How much of the machine's total memory is that?

  1. Total unified memory = 128 GB (all of it LPDDR5X, on the CPU socket).
  2. Buffer size = 32 GiB ≈ 34.4 GB.
  3. Fraction: 34.4 / 128 ≈ 27% of the entire machine's memory in one buffer.
💡
A quarter of the whole pool is a meaningfully large working set — big enough that allocator overheads and steady-state bandwidth dominate, not caching effects. That's why the microbenchmark is a fair stress test before moving to TPC-H.

② Picking an allocator for a CPU-write → GPU-read pipeline

Given Table 1, which allocator should a data-processing pipeline that produces data on the CPU and consumes it on the GPU use?

  1. Rule out cudaMalloc and the explicit-copy path: both need a copy for CPU-produced data — extra time and an extra buffer.
  2. Compare the three CPU-accessible options by bandwidth then overhead: cudaHostAlloc (++, -), cudaMallocManaged (++, ---), malloc (+, --), malloc+cudaHostRegister (+, -).
  3. cudaHostAlloc ties for best bandwidth among CPU-accessible allocators, and has the lowest overhead of the two "++" options.
  4. Winner: cudaHostAlloc — exactly the paper's stated default mode.
💡
This is a Pareto elimination, by hand — the same reasoning behind the scatter figure in "The Big Idea."

③ What "67–98% of runtime is transfer" implies (a back-of-envelope, not a paper claim)

The cited figure (for PCIe-based systems generally, not DGX Spark specifically) is that data movement is 67–98% of relational query runtime. If a platform removed that step entirely and everything else stayed fixed, what's the naive ceiling on speedup?

  1. Take the low end: 67% of runtime is transfer. Remaining compute-only time = 33%.
  2. Naive ceiling if transfer time → 0: speedup = 1 / 0.33 ≈ 3×.
  3. Take the high end: 98% is transfer. Remaining time = 2%. Naive ceiling = 1 / 0.02 = 50×.
  4. But this is an upper bound only — it assumes the compute-only portion doesn't itself become bandwidth-bound once GPU and CPU share one 273 GB/s LPDDR5X channel instead of the GPU using dedicated HBM.
⚠
This is our extrapolation, not the paper's number. The 67–98% figure comes from prior PCIe-system literature the paper cites for motivation; the paper itself reports qualitative Table 1 trade-offs and a TPC-H evaluation, not a measured end-to-end speedup from eliminating transfers on DGX Spark.

Practice problems

Try each before opening the answer.

Problem 1 · easy
You need to write a buffer from the CPU and then read it repeatedly from the GPU. Why not just use cudaMalloc, which has the highest GPU bandwidth in Table 1?
Show answer
cudaMalloc buffers aren't directly CPU-writable on DGX Spark — writing CPU-produced data into one requires an explicit cudaMemcpy, adding a copy the "unified memory" pitch was supposed to avoid. cudaHostAlloc gives up one "+" of raw GPU bandwidth but stays directly writable with low allocation overhead.Misconception: that highest raw bandwidth is always the right axis to optimize. On this platform, CPU-accessibility is a hard constraint for a CPU-write pipeline, not a secondary consideration.
Problem 2 · medium
Why is DGX Spark's 273 GB/s nominal bandwidth a *shared* number rather than "273 GB/s for the CPU and 273 GB/s for the GPU separately"?
Show answer
Because there's only one physical memory — LPDDR5X on the CPU socket — and no GPU-local memory pool. Every GPU access travels the same DRAM channel the CPU uses, so the 273 GB/s figure describes one shared resource both processors draw from concurrently, unlike Grace Hopper where the GPU's HBM bandwidth is additive to the CPU's LPDDR5X bandwidth.Misconception: assuming "128 GB, 273 GB/s" describes two independent memory systems the way a CPU+discrete-GPU pair would.
Problem 3 · medium
The paper frames DGX Spark as a "sixth approach" to the CPU–GPU transfer bottleneck. What makes it different in kind from approach 5 (use a faster interconnect), rather than just a faster version of it?
Show answer
Approach 5 (e.g. Grace Hopper's NVLink-C2C to local HBM) still moves data — it just moves it faster. DGX Spark's approach removes the move: CPU-produced data sits in memory the GPU already coherently addresses, so there is no staging/copy step in the common path at all, only a link to traverse per access. It's the absence of a transfer, not the speed of one.Misconception: treating "coherent interconnect" as automatically meaning "faster transfer" rather than "no transfer."
Problem 4 · hard
Valk overlays kernel activity with "device memory traffic" in its UI, but the paper says this is unavailable on DGX Spark. Why, specifically?
Show answer
"Device memory traffic" counters exist on discrete GPUs because there's a physical boundary — traffic into/out of VRAM — to instrument. DGX Spark's GPU has no VRAM, so there's no such boundary to meter, and NVIDIA's profiling stack also doesn't expose the CPU-side LPDDR5X bandwidth as a substitute. The result is a genuine gap in observability, not a missing feature Valk could just add.Misconception: assuming any GPU performance counter is portable across memory architectures. Counters are built around the assumption of separate GPU memory, which doesn't hold here.
Quick answers

Frequently asked questions

Seven questions newcomers ask most.

Q1Is DGX Spark's "unified memory" the same as CUDA Unified Memory (UM)?▾
No — CUDA UM (cudaMallocManaged) is a software abstraction that migrates pages between two physical pools on demand. DGX Spark has only one physical pool (LPDDR5X on the CPU socket), so there's nothing to migrate; the GPU reaches it directly via hardware-coherent NVLink-C2C. UM still works here, but it's solving a problem (multiple pools) that doesn't actually exist on this platform.
Q2How does this differ from Grace Hopper?▾
Grace Hopper keeps a GPU-local HBM pool behind the coherent link — two memories, one address space. DGX Spark removes the GPU-local pool entirely: zero local memory, one shared LPDDR5X pool, and a correspondingly lower price point.
Q3If the GPU can reach CPU memory directly, why not always use cudaMallocManaged?▾
It has the worst allocation/deallocation overhead of the CPU-accessible options (Table 1: "---"), for the same GPU bandwidth cudaHostAlloc achieves with much lower overhead ("-"). It's dominated, not wrong — just not the default choice.
Q4Does eliminating the transfer step guarantee better performance than a discrete GPU?▾
No. The paper is explicit that this trades a transfer bottleneck for a permanently shared, lower bandwidth ceiling (273 GB/s nominal, shared) versus a discrete GPU's own dedicated HBM. Whether that's a net win depends on the workload's transfer-to-compute ratio, which is exactly what the TPC-H evaluation probes.
Q5What is Valk, concretely?▾
A GPU meta-profiler: it merges hardware counters, system polling data, execution traces, and query plans into one dataset, queryable via custom scripts/SQL and viewable through a purpose-built TPC-H-oriented UI (timeline, roofline, stall/instruction breakdowns).
Q6What benchmark do they run on it?▾
The full TPC-H query suite, executed under each of the CUDA memory allocation policies, comparing end-to-end query performance and inspecting where time goes via Valk's timeline.
Q7How does this relate to CXL-based memory tiering?▾
Our framing, not the paper's: the paper only draws this parallel briefly. Conceptually, DGX Spark's GPU is in a position similar to a CXL Type-2/3 accelerator pulling from host-attached capacity — no local tier, coherent but bandwidth/latency-bound relative to a processor's own local memory. The key difference: NVLink-C2C is a fixed, vendor-specific link inside one package, not a general CXL.mem fabric with its own switching and multi-device topology — so lessons here (allocator choice, shared-bandwidth contention) transfer conceptually to CXL tiering work, but the mechanism doesn't.
