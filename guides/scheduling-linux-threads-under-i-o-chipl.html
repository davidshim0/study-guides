Scheduling by available wire, not whoever's core looks idle

Chiplet CPUs hide a new bottleneck behind the core count: every off-chip request — memory, CXL, devices — has to cross one shared I/O chiplet. Linux's scheduler has no idea it's there. This is the plain-English story of cSwitch, which treats that chiplet like a network switch.

📄 "Scheduling Linux Threads under I/O Chiplet Wall Using cSwitch" · An, Oh, Liu 🎓 OS scheduling + chiplet basics assumed — the primers cover them ⏱ ~30 min read
🔀

Give a thread's next time slice to the path the I/O chiplet can actually SERVE right now — not whichever core merely looks IDLE.

1Why a processor even has an "I/O chiplet"▾

Instead of one giant die, modern server CPUs split into several compute chiplets (cores + private/L3 cache) plus one I/O chiplet holding memory controllers, coherence fabric, and PCIe/CXL interfaces — often on an older, cheaper process node. All off-chip traffic — DRAM, devices, CXL — has to physically cross into this one shared die.

Now you're ready: the I/O chiplet is a single shared resource sitting between every core and everything outside the package — exactly the kind of shared resource that needs deliberate scheduling.
2The I/O Chiplet Wall, defined▾

The path from core to memory/device now has extra hops: the compute–I/O link, the Network-on-Interposer (NoI), the I/O chiplet's internal crossbar, and the chiplet–memory link. Each has finite bandwidth and buffering, so they become contention points once several cores generate traffic at once — a bottleneck the paper names the I/O Chiplet Wall.

Now you're ready: this wall is the paper's whole subject — everything else (Loading Map, cFlows, Traffic Labels) exists to see through it and schedule around it.
3Credit-based flow control and backpressure▾

On-chip fabrics (NoC, NoI) use credits: a sender may only inject a new request if it holds a credit from the downstream buffer. When a memory controller gets congested, it slows credit returns — which throttles the NoI, which throttles the NoC, which finally stalls the core pipeline. Congestion doesn't stay local; it walks backward.

Now you're ready: this is why an unrelated, non-congested thread can still slow down — the paper's "congestion expansion" case (§3.4) is this backpressure chain in action.
4EEVDF, briefly▾

Linux's default CPU scheduler assigns each thread a virtual deadline based on CPU time already received (weighted by priority), then always runs whoever's deadline is earliest. It's per-CPU (each core has its own run queue) with periodic load balancing across cores, guided by idleness, cache-affinity, and NUMA heuristics.

Now you're ready: EEVDF reasons entirely about CPU time and rough locality — it has no notion of "this core's path to memory is currently congested."
5NUMA and Sub-NUMA Clustering — and their blind spot▾

NUMA (and its finer-grained cousin SNC) tells the scheduler which memory is "close" to which core. It's a static, topology-derived label. It says nothing about current traffic load on the links between them — two cores in the same SNC domain can have wildly different effective bandwidth depending on who else is using the shared path right now.

Now you're ready: this is the crux of "topology-aware affinity breaks" (§3.3) — logical closeness stops predicting performance once the I/O chiplet is loaded.
6"Cores are interchangeable" — the assumption cSwitch breaks▾

Schedulers generally treat any idle or lightly-loaded core as a fungible resource — pick whichever's free. On a chiplet CPU, a core's effective throughput depends on the load on its specific compute–I/O link and downstream memory channel, which varies dynamically and isn't visible from CPU utilization alone.

Now you're ready: two "equally idle" cores can differ 2× in achievable bandwidth (§3.2) — placement needs a bandwidth signal, not just a busy/idle bit.
7Networking vocabulary the paper borrows▾

cSwitch reframes scheduling using switch/network terms: a flow (a thread's traffic to one destination), ingress/egress channels (where traffic enters/leaves the I/O chiplet), rate control (slow a sender down before it overflows a link), and max-min fair sharing (split a congested resource's capacity fairly among competing flows). None of this is new — it's decades of datacenter networking research, retargeted at an on-package fabric.

Now you're ready: once you see "thread" as "flow" and "core" as "sender," the whole cFlow scheduler algorithm reads like congestion control.
8Inferring congestion without hardware visibility▾

Current chiplet CPUs don't expose I/O-chiplet queue occupancy to software. cSwitch instead reads delay signals — core stall cycles, L2/L3 fill-response counters, sampled service latency — and infers contention from how those numbers move, the same way TCP infers congestion from RTT or ECN rather than seeing router queues directly.

Now you're ready: the I/O Chiplet Loading Map (§4.2) is exactly this — periodic PMC sampling turned into an estimate of "is this path congested right now?"
9sched_ext and eBPF, briefly▾

sched_ext is a Linux mechanism letting a userspace/eBPF program supply scheduling decisions (placement, time slices) that the kernel then applies. cSwitch builds on it directly: the paper reimplements both ARCAS and Caladan+ atop cSwitch's own telemetry and sched_ext interface, so all three can be compared using the same measurement layer. ghOSt is part of the same userspace-scheduling lineage but is only discussed as related work, not something cSwitch runs on top of.

Now you're ready: cSwitch's policy lives in userspace Rust (planner.rs/policy.rs) and talks to the kernel through sched_ext — that's what makes it portable and programmable (§4.6).
10CXL.mem and the device path▾

Type-3 CXL memory expanders attach through PCIe/CXL lanes that also terminate at the I/O chiplet — so CXL.mem traffic shares the exact same contended fabric as DRAM traffic, just via a different egress channel. The paper measures CXL per-core bandwidth collapsing under intra-chiplet concurrency almost identically to DRAM (1.6–2.5× vs 1.7–2.4×).

Now you're ready: for anyone thinking about DRAM/CXL tiering, this is the layer beneath your tier-placement decision — cSwitch schedules around congestion on the path to whichever tier a page already lives in.
The whole story in one place

cSwitch in a nutshell

The problem, the telemetry that fixes it, and how the pieces connect.

Chiplet processors funnel every off-chip request through one shared I/O chiplet. That's the I/O Chiplet Wall: latency rises up to 2.0× under contention, throughput caps around 330 GB/s regardless of how many cores you add, congestion backpropagates into core stalls, per-core bandwidth collapses as concurrency rises, and — worst of all — there's no traffic control, so an aggressive thread can degrade a quiet neighbor's performance by up to 10.9× depending on where the interference lands (the paper measures four location-dependent pairs, from 1.2×/1.7× to 2.7×/10.9×).

EEVDF, Linux's default scheduler, is blind to all of it. It treats free cores as interchangeable and leans on NUMA/SNC locality — abstractions that describe static topology, not dynamic I/O chiplet load. The paper catalogs four concrete failure modes: idle cores that are secretly bandwidth-starved, "close" placement that backfires under load, contention that spreads to unrelated threads, and load balancing that trades CPU imbalance for memory imbalance.

cSwitch's fix: model the I/O chiplet as a software switch. Each thread becomes one or more cFlows, tagged with a Chiplet Traffic Label describing its path, demand, and observed contention. A runtime I/O Chiplet Loading Map infers ingress/egress congestion from PMC-derived delay signals (no hardware queue visibility needed). A cFlow scheduler then closes the loop every epoch: throttle flows on congested egress channels toward a max-min fair share, and if that's not enough, migrate the highest-impact flows to less-congested ingress paths via bandwidth-aware bipartite matching. MegaCFlow extends this to coordinated thread groups, and a sched_ext/eBPF interface lets other policies (including reimplementations of ARCAS and Caladan+) plug into the same telemetry.

The payoff: up to 2.7× speedup over EEVDF under load (1.2–2.7× overall), 1.4–1.7× over ARCAS/Caladan+, up to 84.5% latency reduction and 3.9× throughput/scalability gain, for roughly 3.5% CPU overhead and negligible memory footprint.

🔀 Key takeaways

  • The I/O chiplet is a single shared switch-like resource every off-chip request crosses — bandwidth caps near 330 GB/s, and it has no built-in traffic control.
  • EEVDF's core-idleness and NUMA-affinity heuristics don't see I/O chiplet load — "free" and "close" both stop meaning "fast" once the fabric is busy.
  • cSwitch turns threads into cFlows with a Chiplet Traffic Label (path + performance + contention), read from ordinary PMCs — no hardware changes.
  • The cFlow scheduler is two-phase: egress-driven rate control (throttle) first, then ingress-driven migration (bipartite matching) only if congestion persists.
  • MegaCFlow keeps coordinated threads together when it helps, splits them across paths when a single path can't carry their combined demand.
  • A sched_ext/eBPF policy interface makes cSwitch's telemetry reusable by other schedulers (the paper reimplements ARCAS and Caladan+ atop it).
  • Result: up to 2.7× vs EEVDF, up to 84.5% lower latency, 3.9× better scaling, ~3.5% CPU overhead, ~0.01% memory overhead.
Six everyday pictures

How to think about cSwitch

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · cores vs bandwidth

Three checkout lanes, one shared conveyor

A store has three open registers (cores), but all three feed one conveyor belt to the loading dock (the I/O chiplet). "Free register" doesn't mean "fast checkout" if the belt behind it is jammed. EEVDF only checks whether the register is open; cSwitch checks whether the belt behind it can actually move your cart.

Where it misleads: a real belt is one physical object; the I/O chiplet has several independent ingress/egress paths, so congestion on one register's belt doesn't imply congestion everywhere.
Backpropagation · credit-based flow control

A traffic jam that walks backward

A fender-bender a mile ahead doesn't just stop the cars near it — brake lights ripple backward, car by car, until traffic three exits behind you slows down too, even though nobody there can see the accident. Credit-based flow control does the same on-chip: a congested memory controller slows credit returns, which throttles the NoI, which throttles the NoC, which stalls a core that never touched the congested resource directly.

Where it breaks: highway backpressure is roughly uniform; on-chip credits ripple along whatever specific path is shared, so two "nearby" threads on different paths may be completely unaffected by each other.
Telemetry · inferring congestion indirectly

Judging the kitchen by how long plates take

You can't see into a restaurant's kitchen, but if your plate is taking twice as long as usual, you infer it's backed up. cSwitch can't see the I/O chiplet's internal queues either — so it watches "plate arrival time" proxies (stall cycles, sampled response latency) each epoch and infers congestion from how those numbers move.

Where it breaks: a slow plate could mean a busy kitchen or a slow waiter (a different bottleneck entirely) — cSwitch's bipartite-matching trick exists precisely to disambiguate "which downstream resource actually caused this delay."
Rate control · egress-driven throttling

A dam release schedule

A reservoir has one spillway of fixed capacity feeding several downstream farms. Rather than let every farm draw as fast as it wants (first-come, first-served, favoring whoever pumps hardest), an operator gives each farm a fair share of the spillway's throughput and throttles anyone drawing beyond it — exactly cSwitch's max-min fair egress rate control, done by shrinking a thread's CPU time slice instead of a literal valve.

Where it breaks: real reservoirs meter continuously; cSwitch re-evaluates and re-throttles only once per scheduling epoch, so it reacts to sustained congestion, not every instantaneous spike.
Migration · bandwidth-aware bipartite matching

Rerouting a delivery truck

A dispatcher sees one loading dock backed up and two others sitting half-empty. Rather than let every truck queue at the busy dock (first-come placement, EEVDF's default), the dispatcher matches the truck carrying the most cargo to whichever open dock has the most free capacity — cSwitch's greedy bandwidth-aware bipartite match between congested cFlows and under-loaded ingress channels.

Where it breaks: rerouting a truck is free; migrating a thread costs cache warmth. cSwitch only escalates to migration after rate control alone fails to relieve congestion — it's the second, costlier resort, not the first.
Coordination · MegaCFlow

A moving crew, not three solo movers

Three movers carrying one couch need to walk in step through the same doorway — split them across three different doors and the couch never gets through. A MegaCFlow keeps threads that genuinely coordinate (a producer/consumer pipeline) on the same ingress path, and only decomposes the group across paths once its combined demand actually exceeds what one path can carry.

Where it breaks: unlike movers, cFlows can be silently and automatically split mid-task when demand grows — the analogy captures the "stay together while you can" default, not the graceful decomposition mechanics.
The full explanation

How cSwitch actually works

Section by section, with the paper's mechanisms rebuilt as diagrams you can read at a glance.

1 · Why EEVDF gets this wrong

EEVDF ranks threads by virtual deadline and places them using idleness + NUMA/SNC heuristics — both static, topology-derived signals. Neither captures the dynamic state of the I/O chiplet: which ingress/egress channels are congested right now. The result is four pathological cases the paper documents directly (§3.2–§3.5): free cores that are secretly bandwidth-starved (up to 58.0% degradation), "close" placement that backfires past 80% load (4.3–4.5× slowdown), congestion that spreads to unrelated threads (up to 1.7×), and CPU-balanced load balancing that leaves the memory subsystem badly skewed (inter-chiplet bandwidth dropping from 9.5 to 4.2 GB/s under one measured skew).

2 · The I/O Chiplet Loading Map — measuring without hardware visibility

Every epoch, cSwitch samples architectural counters at each ingress channel (requests/responses to LLC, service latency, concurrent cFlows) and each egress channel (requests/responses, congestion degree from response latency). The hard part: the hardware doesn't expose which ingress traffic maps to which egress channel, especially under memory interleaving (many-to-one). cSwitch resolves this with temporal differencing — comparing consecutive snapshots — and weighting candidate ingress→egress edges by delay inflation: a flow whose latency just spiked is more likely contributing to the egress channel that's congested.

3 · The Chiplet Traffic Label — one signature per cFlow

Inspired by the HASS scheduler, each cFlow's label has three parts: (1) Communication Path — inferred ingress/egress channels; (2) Performance Attributes — request/response counts and service latency from per-core counters (L2FillRspSrc, L3_XiSampledLatency); (3) Contention — stall cycles and L3-to-L3/L3-to-DRAM delay as a pressure proxy. An EWMA with hysteresis smooths the label against transient noise, the same low-pass-filter idea used to stabilize any noisy control loop.

4 · The cFlow scheduler — rate control, then migration

Every epoch runs three phases, in order — cheap fixes first, expensive ones only if needed:

# Phase 1: egress-driven rate control
for ch in egress_channels:
    if ch.isCongested():
        shares = ch.bwMaxMinRealloc(ch.flows)          # weighted max-min fair share across all traversing flows
        for f in ch.flows:
            if f.rate > shares[f]:
                throttle(f, shares[f])                  # shrink time slice for flows over their fair share

# Phase 2: ingress-enhanced refinement (only if still congested)
for ch in ingress_channels:
    if ch.isCongested():
        candidates = [f for f in ch.flows if f.isBWIntensive()]
        mark_migratable(candidates)

# Phase 3: bandwidth-aware migration
plan = bipartiteMatch(migratable_cflows, sort_by_residual_bw(ingress_channels))
apply(plan)   # greedy max-weight match; locality tiebreaks kept
💡
Why two phases, not one? Migration costs cache warmth and disturbs placement; rate control is nearly free (just a time-slice change). cSwitch only escalates to migration when throttling alone leaves a channel congested — the two-phase design mirrors "slow down first, reroute only if that's not enough" from congestion control.

5 · MegaCFlow and the sched_ext policy interface

A MegaCFlow aggregates several threads' traffic labels into one dominant path. If its combined demand fits under the ingress/egress capacity, cSwitch schedules it as a single prioritized unit — preserving cache locality and synchronization behavior. If demand exceeds capacity, it's decomposed into sub-cFlows and packed across multiple channels by residual bandwidth, each inheriting the group's traffic label. Everything above is exposed through sched_ext + eBPF: a Rust compute_plan() consumes cSwitch's internal state and emits actions (throttle, migrate, reprioritize), which a policy.rs module translates into kernel scheduling updates — the same interface the authors used to reimplement ARCAS and Caladan+ on top of cSwitch's telemetry.

Follow the numbers, step by step

Worked examples

Five traces through the paper's own measurements — the latency tax, the throughput ceiling, backpropagation relief, scheduler overhead, and cross-baseline speedup arithmetic.

① Quantifying the I/O chiplet's latency tax

The paper reports 1.58× higher average stall cycles on the chiplet processor vs. non-chiplet, widening to 2.0× as I/O chiplet load rises. What does that mean concretely?

  1. Baseline (non-chiplet): call its stall-cycles-per-request S.
  2. Chiplet processor, average load: stalls are 1.58 × S — every request pays a ~58% latency tax just for crossing the I/O chiplet, even before contention.
  3. Chiplet processor, high load: the tax grows to 2.0 × S — doubling — because the non-chiplet processor's stalls rise "only marginally" under the same added traffic (Fig. 2b), while the chiplet processor's contention compounds.
  4. Why more in-flight requests don't fix it: modern out-of-order cores already issue enough outstanding requests that added memory-level parallelism can't hide inter-chiplet latency — the bottleneck isn't per-request latency hiding, it's shared-path capacity.
🔀
Insight: the gap between 1.58× and 2.0× is the I/O chiplet wall becoming visible — a fixed structural tax that grows under contention rather than amortizing away.

② Why bandwidth plateaus while latency keeps climbing

Aggregate memory bandwidth saturates at ~330 GB/s (Fig. 3), yet application latency keeps rising — up to 2.4× for DuckDB — even after throughput stops improving. Why don't they move together?

  1. Below the knee: as offered load rises toward 330 GB/s, the I/O chiplet keeps pace — throughput rises roughly with load, latency stays flat.
  2. At the knee: once offered load reaches ~330 GB/s, every communication entity on the path (inter-chiplet link, NoI, crossbar, chiplet-memory link) is at capacity.
  3. Past the knee: extra requests can't be serviced faster — they queue. Throughput is capped by definition (you can't serve more than capacity), so all the extra offered load shows up as queueing delay instead — this is exactly why latency, not throughput, is the metric that keeps degrading (2.4×, 1.3×, 1.3×, 1.5× across the four workloads).
  4. Takeaway for scheduling: once you're past 330 GB/s, adding more concurrent threads is pure loss — it can only add queueing latency, never recover throughput. This is precisely cSwitch's "operating regime" caveat (§4.4): near global saturation, placement options shrink and only throttling still helps.
💡
This is the same throughput/latency knee behavior known from queueing theory (M/M/1-style blow-up near ρ→1) — the paper is showing it happens on-package, not just at a network switch.

③ How much does spreading traffic across DIMMs actually buy you?

Going from 1 DIMM to all 12 DIMMs interleaved cuts DuckDB's TPC-H latency by 77.3% and core stall percentage by 29.2% (Fig. 4). What remains?

  1. Latency remaining: a 77.3% reduction leaves 100% − 77.3% = 22.7% of the original 1-DIMM latency — i.e. 12-DIMM interleaving runs at roughly 1/4.4 the original latency.
  2. Stall percentage remaining: a 29.2% drop in core stall percentage is a smaller relative win than the latency drop — stalls are reduced, but far less than proportionally to the latency improvement.
  3. Why the two don't match: spreading requests across more memory channels relieves queueing at any single channel (helping latency a lot) and improves credit return rates (relieving some backpressure-induced stalls), but doesn't eliminate the I/O chiplet's other fixed costs — crossbar arbitration, NoI hops — which stall percentage still reflects.
  4. Scheduling implication: this is the same lever cSwitch's ingress-migration phase pulls automatically — steering threads toward channels with residual capacity — except cSwitch does it per-flow at runtime instead of via static DIMM interleaving configuration.
🔀
Insight: spreading load across more egress paths is a genuinely powerful lever (¼ the latency here) — which is exactly why cSwitch's migration phase targets "channels with the most residual bandwidth" rather than just any non-congested one.

④ Is cSwitch's overhead actually modest? (tallying CPU-seconds)

For the 40-thread PageRank benchmark, the paper reports the userspace scheduler costs 6.22 CPU-seconds against 179.60 total application CPU-seconds, with planner computation using 1.75 of those. Break it down.

  1. Total scheduler overhead: 6.22 ÷ 179.60 = 3.46% of total CPU time.
  2. Planner-only cost: 1.75 ÷ 179.60 = 0.97% — this is the actual decision-making (compute_plan(): telemetry read + rate control + matching).
  3. The remainder: 6.22 − 1.75 = 4.47 CPU-seconds, or 4.47 ÷ 179.60 ≈ 2.49%, goes to the userspace scheduling runtime itself (sched_ext plumbing, not decision logic).
  4. Memory overhead, separately: ~0.01% of system memory even at 84 cores across 12 chiplets — cSwitch's per-core telemetry structures are lightweight by design (unlike a full tag-directory-style monitor, it only needs counters, not cached tags).
💡
Two-thirds of the already-small overhead (2.49 of 3.46 points) is scheduling plumbing, not the traffic-aware logic itself — meaning most of the cost is the price of running any userspace scheduler via sched_ext, not the price of being chiplet-aware.

⑤ Reading cSwitch's speedups across load regimes

The paper doesn't report one single speedup number for cSwitch — it depends on how loaded the I/O chiplet is and which baseline you're comparing against. What do the reported numbers actually say?

  1. Under light load: cSwitch is roughly comparable to ARCAS, and beats EEVDF and Caladan+ by about 1.2× and 1.9× respectively — with little contention to schedule around, chiplet-awareness and topology-awareness accomplish similar things.
  2. Under load: cSwitch pulls ahead of both baselines — about 1.4× over ARCAS and 1.7× over Caladan+ — because once dynamic I/O chiplet contention dominates, only cSwitch's runtime congestion signal can react to it.
  3. Overall vs EEVDF: 1.2–2.7× across the full load range — the low end matches the light-load number above, and the high end (2.7×) is reached only once background load pushes well past the ~60% knee.
  4. A caution on the arithmetic: the light-load and loaded-regime ratios come from separate measurement conditions, not the same workload/load point held fixed across all three schedulers — so they can't be divided against each other to back out numbers the paper doesn't report directly, like ARCAS/EEVDF or Caladan+/EEVDF in isolation.
📎
Numbers restated directly from §5.2, not derived — the paper's own light-load/loaded split is doing the explanatory work here.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Two cores are both 100% idle. EEVDF picks one arbitrarily. Can that choice still hurt performance on a chiplet CPU?
Show answer
Yes. Idleness only describes the core's own CPU utilization, not the load on its specific compute–I/O link or the memory channel it'll route to. One "idle" core's path may already be shared with a heavy neighbor's traffic, while the other's is clear — the paper measures 53.2–58.0% degradation from exactly this in the busy-core scenario (§3.2).Misconception: that "idle core" and "fast core" mean the same thing. On a chiplet CPU they can diverge sharply because bandwidth, not CPU cycles, is often the real constraint.
Problem 2 · medium
Enabling 12-DIMM interleaving instead of 1 DIMM cuts DuckDB's latency by 77.3%. What's the resulting latency as a fraction of the original, and roughly how many times faster is that?
Show answer
Remaining latency = 100% − 77.3% = 22.7% of the original, i.e. roughly 1/4.4 — about 4.4× faster. A 77% reduction is not the same as "77% as fast"; it's the fraction that's been removed.Misconception: confusing "reduced by X%" with "now running at X% speed." A 77.3% reduction leaves 22.7% of the latency, which corresponds to a much larger speedup factor than 77%.
Problem 3 · medium
Why does cSwitch run egress-driven rate control (throttling) before ingress-enhanced migration, rather than migrating threads immediately whenever a channel looks congested?
Show answer
Throttling is nearly free — it just shrinks a time slice — while migration disturbs cache locality and costs real overhead to relocate a thread. cSwitch tries the cheap fix first and only escalates to the costlier one (bandwidth-aware bipartite matching) if the channel is still congested after throttling. This mirrors congestion control's "slow down before rerouting" principle.Misconception: that placement (which core) is always the primary lever. For cSwitch, pacing (how fast a thread injects requests) is tried first because it's cheaper and often sufficient.
Problem 4 · hard
Under memory interleaving, one egress channel receives traffic from several ingress channels at once (a many-to-one mapping), but the hardware doesn't expose which ingress traffic went where. How does cSwitch attribute contention correctly anyway?
Show answer
It compares consecutive telemetry snapshots (temporal differencing) to get incremental request deltas at both ends, then weights candidate ingress→egress edges by latency inflation at the ingress side — the intuition being that a flow whose delay just spiked is more likely contributing to the downstream congestion. It's an inference, not a direct measurement, and the paper reports it's not perfectly accurate but sufficient in practice.Misconception: that cSwitch has (or needs) ground-truth visibility into hardware routing. It works entirely from indirect, counter-derived signals — the same constraint any congestion-control scheme faces without direct queue visibility.
Problem 5 · medium
CPU-centric load balancing can leave utilization perfectly even across cores while the memory subsystem becomes badly skewed. How is that possible?
Show answer
Load balancing that migrates purely on CPU utilization can still consolidate several memory-intensive threads onto the same compute chiplet (or the same compute–I/O link), because "busy" and "bandwidth-hungry" aren't the same signal. CPU load looks balanced; the shared I/O chiplet path serving that chiplet is now overloaded. The paper measures inter-chiplet bandwidth collapsing from 9.5 to 4.2 GB/s under exactly this compute-balanced-but-memory-imbalanced state (§3.5).Misconception: that balancing CPU utilization implies balancing overall system load. On a shared-fabric chiplet CPU, the bottleneck resource (I/O chiplet bandwidth) is a separate axis from CPU cycles entirely.
Problem 6 · hard
You're studying DRAM/CXL memory tiering (deciding which pages live in which tier). Does cSwitch replace or overlap with that kind of page-placement policy?
Show answer
Neither, really — they operate at different layers and are complementary. Tiering policies (e.g. hot/cold page migration between DRAM and CXL) decide where data lives. cSwitch decides which core runs which thread, and how fast it's allowed to inject requests, given the current congestion on the path to wherever that data already lives — including CXL.mem's shared I/O-chiplet path, which the paper shows degrades under intra-chiplet concurrency almost identically to DRAM (1.6–2.5× vs 1.7–2.4×). A tiering policy could place a page optimally and still have its access throttled by chiplet contention that only cSwitch-style scheduling can see.Misconception: treating "memory management" as one policy. Placement (which tier) and scheduling (which core, what rate) are separate control loops that can — and probably should — coexist, similar to how cSwitch itself coexists with (doesn't replace) NUMA policy and cgroups.
Problem 7 · easy
When the I/O chiplet is only lightly loaded (well under the 330 GB/s ceiling), how much does cSwitch typically help over EEVDF?
Show answer
Modestly — about 1.2× on average, similar to ARCAS, because at low load there's little contention to schedule around; both exploit similar topology-locality benefits. The gap widens substantially (up to 2.7×) only once background load pushes the I/O chiplet past roughly 60% — cSwitch's advantage is concentrated where contention actually exists.Misconception: that a chiplet-aware scheduler always dramatically outperforms a naive one. Its value is contention-proportional — under light load there's nothing to fix, so the two_converge.
Problem 8 · medium
Egress throttling reduces RocksDB's P99 latency by 88% in the ablation study, versus 57% for a pointer-chasing microbenchmark. Why might a request-serving workload like RocksDB benefit more from throttling than pure pointer chasing?
Show answer
Pointer chasing is latency-bound by dependent-load chains — each access must complete before the next can issue, so it naturally self-limits its injection rate regardless of throttling. RocksDB under load, by contrast, can have many independent, concurrent requests in flight; without throttling, an aggressive villain thread can flood a memory controller and starve RocksDB's queue, so capping the villain's rate directly relieves a real, avoidable queueing backlog that would otherwise inflate tail latency.Misconception: that rate control's benefit size only reflects the mechanism's power, not the workload's own concurrency profile. A workload with less exploitable memory-level parallelism has less queueing to relieve in the first place.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What exactly is the "I/O Chiplet Wall"?▾
A performance limit caused by the shared inter-chiplet communication path (compute–I/O links, the NoI, the I/O chiplet's internal crossbar, and chiplet–memory links) that every off-chip request must cross. As core and chiplet counts scale, this shared path — not raw compute — increasingly bounds latency and bandwidth.
Q2Is this the same thing as NUMA remoteness?▾
No — NUMA/SNC describes static topological distance (which memory controller is "local" to which cores). The I/O Chiplet Wall is about dynamic contention on the shared fabric itself, which can make a "local" access slow under load and a "remote" one fast when its path is clear — the opposite of what NUMA locality would predict.
Q3What is a "cFlow," concretely?▾
A thread running on one core that issues memory or I/O requests toward one target DIMM or device. It's the atomic unit cSwitch schedules — analogous to a network flow (source, destination, rate) rather than just "a runnable task."
Q4How does cSwitch see congestion if the hardware doesn't expose I/O chiplet queues?▾
It infers congestion from delay signals it can read — core stall cycles and sampled service latency from performance counters — the same indirect approach TCP uses to infer network congestion from RTT rather than seeing router queues directly.
Q5What's the difference between the rate-control and migration phases?▾
Rate control (egress-driven) throttles a congested flow's time slice — cheap, no placement change. Migration (ingress-enhanced) physically moves a thread to a core whose ingress channel has more residual bandwidth — more effective on structural hotspots, but costlier (cache warmth). cSwitch tries throttling first and escalates only if congestion persists.
Q6What is a MegaCFlow for?▾
Coordinated thread groups (e.g. producer/consumer pipelines) benefit from staying on the same communication path rather than being scheduled independently, which could fragment them and increase contention. A MegaCFlow keeps them together as one prioritized unit until their combined demand exceeds what one path can carry, at which point it splits across multiple paths.
Q7How big is cSwitch's overhead?▾
About 3.46% of CPU time on a 40-thread PageRank benchmark (of which only 0.97 points is the actual decision logic), and roughly 0.01% of system memory even across 84 cores / 12 chiplets. Telemetry sampling runs in-kernel via eBPF, while the planner and policy logic that make decisions run in userspace, applying their plans to the kernel through sched_ext.
Q8Does cSwitch replace EEVDF?▾
No — it runs as an additional scheduler class via Linux's sched_ext framework, coexisting with EEVDF and respecting existing CPU affinity, cpusets, and cgroup constraints. It adds chiplet-aware placement and rate control on top, rather than reimplementing fairness from scratch.
Q9How does it compare to ARCAS and Caladan+?▾
ARCAS is chiplet-topology-aware but has no visibility into dynamic I/O chiplet load — it relies on LLC miss signals without bandwidth headroom, so it keeps placing threads on already-congested paths. Caladan+ does µs-scale, load-aware placement but doesn't model the I/O chiplet as a shared bottleneck, and its microsecond-scale context switching adds overhead under scaling. Under light load, cSwitch is comparable to ARCAS and beats EEVDF/Caladan+ by about 1.2×/1.9×; under load, it pulls ahead of ARCAS/Caladan+ by about 1.4×/1.7×, because it directly measures and reacts to chiplet-level contention that neither baseline can see.
Q10Does cSwitch work on non-AMD chiplet CPUs?▾
The authors ported it to an Intel Xeon Gold 6530 (Emerald Rapids) with only topology and PMC-mapping changes — no architectural changes to the mechanism. Emerald Rapids exposes a single shared LLC with less inter-chiplet path visibility, so only egress throttling was evaluated there, still cutting P99 pointer-chasing latency by 33%.
Q11How does this relate to DRAM/CXL memory tiering research?▾
They're complementary layers, not competitors. Tiering systems (TPP, HeMem, Memtis, Pond, and similar) decide where a page lives — DRAM vs. a CXL tier — typically based on access frequency/hotness. cSwitch decides which core runs a thread and how fast it may inject requests, given real-time congestion on the shared path to wherever that data already sits — including the CXL.mem path, which the paper shows collapses under intra-chiplet concurrency nearly as badly as DRAM (1.6–2.5× vs 1.7–2.4×, Fig. 5). A well-placed page can still be throttled by chiplet contention a tiering policy has no visibility into.
Q12What did the paper leave for future work?▾
The evaluation focuses on multiprogrammed, single-socket workloads; the paper notes extending topology awareness to inter-socket NUMA (currently untouched) and, implicitly, deeper integration with device-side bandwidth controls like blkio, which cSwitch currently treats as managing a different resource (device bandwidth itself, vs. the resulting CPU-I/O chiplet contention).

Core terms
I/O Chiplet WallThe performance limit imposed by the shared inter-chiplet communication path (compute–I/O links, NoI, crossbar, chiplet–memory links) that mediates all off-chip access.
cSwitchThe paper's Linux scheduling framework: models the I/O chiplet as a software switch and reframes CPU scheduling as flow scheduling.
cFlowA thread's memory/IO traffic toward one target DIMM or device — cSwitch's atomic scheduling unit.
Chiplet Traffic Label (CTL)A per-cFlow signature: communication path + performance attributes + contention, refreshed via EWMA each epoch.
I/O Chiplet Loading MapRuntime telemetry: samples PMCs each epoch, infers ingress/egress congestion via temporal differencing + delay-weighted bipartite matching.
cFlow schedulerTwo-phase decision loop: egress-driven rate control (throttle), then ingress-enhanced migration (bandwidth-aware bipartite matching) if congestion persists.
MegaCFlowCoflow-inspired grouping of correlated threads, scheduled as one unit while demand fits, split across paths otherwise.
Phantom queuesA bufferless congestion-detection technique using a virtual capacity below the hardware limit to detect congestion before hardware saturation.
Supporting terms
IOC / CCI/O Chiplet (memory controllers, coherence fabric, PCIe/CXL) and Compute Chiplet (cores + private/L3 cache) — the two die types in a chiplet CPU.
NoINetwork-on-Interposer — the on-package fabric connecting chiplets across the silicon interposer.
Credit-based flow controlA sender may inject only with a credit from the downstream buffer; congestion slows credit returns and backpropagates as stalls.
EEVDF / SNCLinux's default fair-share scheduler, and its sub-NUMA-clustering locality abstraction — both blind to I/O chiplet load.
ARCAS / Caladan+Prior schedulers cSwitch is compared against — chiplet-topology-aware, and µs-scale load-aware, respectively; neither models dynamic I/O chiplet contention.
sched_ext / eBPFLinux's pluggable scheduler-class framework, letting a userspace/eBPF policy supply placement and time-slice decisions safely.
Max-min fair shareThe bandwidth-allocation rule cSwitch's rate control uses on a congested egress channel among its traversing flows.
FR-FCFSFirst-Ready First-Come-First-Served — the common memory controller scheduling policy that favors row-buffer-friendly, aggressive senders (part of why the I/O chiplet has "no traffic control" by default).
