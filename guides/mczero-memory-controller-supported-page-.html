Zeroing a page without ever writing a byte to it

Linux must scrub every new page with zeroes before handing it to you — a real memory-bandwidth tax. McZero moves that promise into a single bit in DRAM's own metadata, and lets the memory controller lie convincingly until you actually look.

📄 "McZero" · Halbuer, Ostapyshyn, Wilbert, Christ, Jung, Lohmann 🎓 OS paging + DRAM organization assumed — primers cover both ⏱ ~25 min read
🧹

Don't write the zeroes — promise them in a metadata bit, and let the memory controller make the promise true on the next read.

Quick glossary, then the fundamentals

Acronyms first — then eight collapsed primers. Skip anything you already know.

1Why the OS must zero pages at all▾

Physical memory is reused constantly — freed by one process, handed to the next. Without clearing it first, the new owner could read the previous owner's leftover data: a classic information leak. So the kernel zeroes a page frame before it's ever mapped into user space, or when it's returned to the allocator.

Now you're ready: this mandatory zeroing is pure overhead from the app's point of view — McZero's whole point is to make it (almost) free.
2Pages, huge pages, and the buddy allocator▾

Linux manages physical memory in 4 KiB page frames via a buddy allocator with orders 0–10 (order n = 2ⁿ pages). 2 MiB huge pages (order 9) reduce address-translation overhead for large allocations and can be requested explicitly or granted transparently.

Now you're ready: bigger pages mean bigger single zeroing operations — exactly where McZero's advantage grows, as you'll see in the flamegraph next.
3The flamegraph: zeroing dominates the page fault▾

Profiling Linux allocating a 2 MiB huge page shows clear_page consuming 91% of the page-fault handler's time. Nearly the entire cost of "give me memory" is "write zeroes to it."

Now you're ready: if you can shrink that 91%, you shrink almost the whole fault handler — that's the target McZero attacks directly.
4DRAM's hierarchy: banks, rows, columns, bursts▾

DRAM cells sit in arrays, addressed row-wise (a row ≈ 1–4 KiB); only one row per array can be "open" at a time. Rows split into columns, and one column is the smallest transferable unit — a burst (32 B for LPDDR6). Multiple banks share a data bus, giving parallelism.

Now you're ready: LPDDR6 hides extra bits inside every burst — that's where McZero's metadata lives.
5The memory controller's job▾

By default the MC just relays a stream of read/write requests, translating CPU addresses into bank/row/column and enforcing DRAM timing. It normally has no concept of "pages" or OS semantics at all.

Now you're ready: McZero's core move is teaching the MC one new OS-relevant concept — "this burst is logically zero" — without changing the DRAM chip itself.
6LPDDR6's new metadata field▾

Each 288-bit LPDDR6 burst carries 256 bits of data, 16 bits for link protection/DBI, and — new in this standard — 16 bits of free-form metadata, stored physically in the last 4 of 64 columns per row and normally invisible to the CPU.

Now you're ready: McZero exposes exactly this field to the OS as a second, parallel address space.
7Masked writes▾

DRAM can write less than a full burst: dedicated mask pins disable specific data lines so the excluded bytes are left untouched in the array. This is a standard LPDDR6 feature, not something McZero has to add.

Now you're ready: McZero reuses masked writes to make metadata updates behave like a safe bitwise-OR, so zeroing is irrevocable and never destroys unrelated metadata.
8Cache coherence and what "below the cache" means▾

The CPU's caches sit between it and the MC. A trick played only inside the MC is invisible to anything already cached — a stale or dirty cache line can silently undo it. Any sub-cache optimization must therefore explicitly invalidate the CPU caches for the region it touches.

Now you're ready: this is exactly why McZero needs two rounds of cache-line invalidation around every metadata write — covered in How It Works.
The whole story in one place

McZero in a nutshell

The bottleneck, the trick, and the honest limits.

Linux zeroes every page before handing it out — necessary for security, but expensive: it's 91% of the huge-page fault handler's time. The zeroes themselves carry no information; the CPU spends bandwidth and energy writing a pattern the DRAM could just as well "know" without storing.

McZero exploits a brand-new LPDDR6 feature: 16 bits of metadata riding along with every 32 B burst, normally invisible to software. McZero exposes this as a second, OS-writable address region. Setting a metadata bit marks the corresponding burst logically zero; the memory controller (MC) then intercepts reads to that burst: LPDDR6 still returns the burst's real data payload, but the MC discards it and returns zero bytes instead. A write later clears the bit transparently. Because one 16-bit metadata field can hold the zero-state for 16 bursts, and a single metadata write moves 32 B covering 256 bursts, one metadata write can retire 8 KiB of "zeroing" — and in the best case, 32 writes clear 256 KiB (a 256× reduction in bytes moved).

The catch is the CPU cache sits above the MC and doesn't know about any of this, so McZero must explicitly invalidate cache lines both before and after flipping the metadata bit — coherence overhead that eats into the theoretical win.

The payoff (gem5/DRAMSys, ARMv8 + LPDDR6, Linux 6.18): for a 2 MiB huge page, zeroing time and energy both drop by more than 95% versus Linux's default dc zva-based zeroing. For small, already-cached 4 KiB pages, McZero is actually slower — the coherence overhead outweighs the saved write.

🍯 Key takeaways

  • Zeroing is 91% of a 2 MiB page fault in Linux — a single, huge, wasted memory-bandwidth cost.
  • LPDDR6 gives every 32 B burst 16 bits of free metadata; McZero repurposes 1 bit/burst as a "logically zero" flag.
  • Dense packing: 1 metadata write (32 B) marks 256 bursts = 8 KiB zeroed; at maximum density, 32 writes clear 256 KiB.
  • Zeroing a real 4 KiB page only gets a 4× write reduction (bank/channel interleaving fragments the ideal packing).
  • Reads to zero-flagged bursts still fetch the data payload from LPDDR6, but the MC discards it and answers with zero bytes instead — the savings come from skipped writes, not skipped reads.
  • Must invalidate CPU caches twice per zeroing op (before and after) — the dominant remaining cost for small/hot pages.
  • Result: >95% less time and energy for 2 MiB pages; a net loss for tiny hot 4 KiB pages; end-to-end (hackbench) roughly a wash.
Five everyday pictures

How to think about McZero

Each stands alone. Every card ends with where the picture breaks.

The core trick · Lazy marking

An IOU instead of cash

Instead of physically handing over zero bytes, McZero leaves a signed note: "this is zero — trust me." The debt is only "paid" — the actual zero bytes materialized — the moment someone reads it, and only inside the memory controller's response.

Where it breaks: an IOU can be forged or forgotten; the metadata bit can't — it's irrevocable until an explicit write clears it, by design.
The register · Bank-local cache

A sticky note on the filing cabinet

The 2 B of metadata for a given burst isn't fetched fresh from the array on every access — it lives in a small 32 B "sticky note" register at the bank that holds the relevant metadata, which the MC keeps in sync, reading it from and writing it back to the array only when the target row changes.

Where it breaks: a real sticky note can be wrong; the register is architecturally guaranteed correct — the MC forces a write-back/reload before any access that needs a different row's note.
Density · Metadata packing

One shipping label for 256 boxes

Rather than stamping every single box "EMPTY" (one write per burst), McZero writes one label that lists the empty-state of up to 256 boxes at once, because 16 metadata bits per burst × 16 bursts of register space = 256 bits of state per single 32 B write.

Where it breaks: real pages don't line up with that ideal 256-box shipment — bank/channel interleaving splits a 4 KiB page's bursts across many banks, cutting the real-world gain from 256× down to 4×.
The threat model · Coherence

Repainting a wall someone's still leaning on

If the CPU cache still holds a "dirty" copy of a line right after you mark its DRAM burst zero, that cached copy can get written back later and silently overwrite your zero mark — like repainting a wall while someone's shoulder is still smudging it. McZero avoids this by invalidating the cache twice: once before, to prevent dirty write-back, and once after, to catch anything the prefetcher grabbed in between.

Where it breaks: repainting a wall is one clean action; two full cache-invalidation passes cost real cycles, which is exactly why McZero loses on small, already-cached pages.
The full explanation

How it actually works

From DRAM layout to the OS-side coherence dance.

1 · Where the metadata physically lives

An LPDDR6 row has 64 columns; the last 4 are reserved for metadata, so accessing "data" columns requires a non-linear address decoder that skips them. On a read, the 2 B of metadata for a burst isn't read straight from the array — it comes from a 32 B bank-local metadata register that the MC must keep synchronized with whichever row is currently targeted.

2 · MC read/write handling

On a read: if the bank's metadata register doesn't hold the target row's metadata, the MC first writes back the (possibly modified) register and reads in the correct metadata — these are data-free commands. Once the real data read completes, the MC checks the zero bit: if set, it discards the fetched payload and returns zeroes instead of the array's contents.

On a write: the same register sync happens, and the MC clears the zero bit for that burst — interpreted as a masked write touching only that bit, so the rest of the 16-bit metadata field survives untouched.

On an explicit metadata write (the OS actually setting a zero flag): the MC writes back the register first, then issues the write as a masked, bitwise-OR operation into the array — guaranteeing zeroing is irrevocable and never corrupts neighboring metadata bits.

3 · Encoding: which bit means what

A burst at row i, column j maps to a metadata bit via a fixed formula (linear index l = i·64+j, then divided into a metadata field m, target row i′, target column j′, and bit position z within the field). This keeps the mapping independent of the CPU-facing address-interleaving scheme, while still letting the MC arrange bits so that bursts adjacent from a bank's point of view land in the same metadata field — minimizing register reloads.

4 · OS integration: two memory-mapped regions

The MC exposes system memory as two consecutive mappings: the first 15/16 is ordinary data, the last 1/16 is metadata. Writing 1 to a metadata address marks the corresponding 32 B burst zero (until overwritten); writing 0 is a no-op — zeroing can't be undone through this interface. The OS still manages memory at 4 KiB page granularity, so it must translate each of a page's 128 bursts into the correct metadata address using the mapping above.

5 · Cache coherence: the two-pass dance

Setting a metadata bit is invisible to anything already sitting in a CPU cache, creating two race conditions: (1) a dirty line could be evicted right after the flag is set, writing stale non-zero data back over the flag's effect; (2) the prefetcher could load a line just before the flag is set, leaving stale data cached and readable later.

Follow the numbers

Worked examples

Four traces using the paper's own figures.

① Metadata packing: from 1 bit to 256 KiB

  1. One 32 B burst needs only 1 zeroing bit, but LPDDR6 gives it a 16-bit metadata field — enough for 16 bursts' worth of zero-flags.
  2. The register spans 16 such fields (32 B register = 16 × 16 bits), so it holds zero-state for 16 × 16 = 256 bursts = 256 × 32 B = 8 KiB.
  3. One metadata write (32 B) therefore retires 8 KiB of "zeroing" in a single request.
  4. At that density, 32 writes clear 32 × 8 KiB = 256 KiB — versus 256 KiB ÷ 32 B = 8192 writes the eager path would need. Ratio: 8192⁄32 = 256× fewer writes, matching the paper's claim exactly.

② A real 4 KiB page only gets 4×, not 256×

  1. A 4 KiB page = 128 bursts (4096 B ÷ 32 B).
  2. Bank/channel interleaving fragments them: with two channels and LPDDR6's bank layout, only every 32nd burst lands on the same bank/channel target, so a page spreads across 32 such targets with just 4 bursts each.
  3. The MC arranges those 4 bursts per target into one shared metadata field, so one metadata write per bank/channel target suffices — 32 writes total (one per bank/channel target) covering 128 bursts.
  4. Bytes moved: eager = 128 × 32 B = 4096 B; McZero = 32 × 32 B = 1024 B. 4096 ⁄ 1024 = 4× fewer bytes — exactly the paper's stated factor.

③ The >95% claim, checked against Fig. 4/5

  1. Time, 2 MiB hot page (default case): Linux 1.1 ms → McZero 46.0 µs. Reduction = 1 − 46/1100 = 95.8%.
  2. Energy, 2 MiB hot page: Linux 348 µJ → McZero 14 µJ. Reduction = 1 − 14/348 = 96.0%.
  3. Why the huge jump at 2 MiB specifically: Linux's eager writes overflow the 256 KiB shared L2 between 128 KiB and 256 KiB, so its time jumps discontinuously from 2.8 µs to 106.3 µs — McZero, which never writes the bulk zero payload through the cache hierarchy, scales smoothly instead.
  4. Both figures clear >95%, matching the abstract's claim for the 2 MiB case.

④ Why end-to-end (hackbench) is a wash

  1. Per-page zeroing times from Table 1: 4 KiB — Linux ≈1.2 µs, McZero ≈1.7 µs (McZero loses, consistent with small-cold-page overhead from coherence passes).
  2. 32 KiB — Linux ≈10.1 µs, McZero ≈2.0 µs (McZero wins by ~5×, as page size grows).
  3. But 4 KiB allocations dominate the count (~2000 vs. single-digit counts for 8/16/32 KiB), so the workload-wide total ends up statistically indistinguishable (756.3 ms vs. 769.3 ms total duration).
  4. Takeaway: McZero's win is real but concentrated in huge-page-sized zeroing — a workload dominated by tiny page faults won't see it.
Test yourself

Practice problems

Try before opening the answer — each flags the misconception it checks.

Problem 1 · easy
A process allocates and immediately writes to a 4 KiB page that was just freed and is still hot in cache. Would you expect McZero or Linux's default zeroing to be faster here?
Show answer
Linux's default (dc zva) is faster here — 49.2 ns vs 728.3 ns for a hot 4 KiB page. McZero pays two full-page cache-invalidation passes even when the page is small and already cached, while the eager path just writes 64 B cache lines directly.Misconception: that "lazy is always faster." McZero trades per-op coherence overhead for avoided memory traffic — a trade that only pays off once the region is large enough.
Problem 2 · medium
Why does one 32 B metadata write cover 8 KiB of data, not just 32 B or 512 B?
Show answer
Each burst needs only 1 zero-bit, but LPDDR6's metadata field is 16 bits wide — so one field already covers 16 bursts (512 B). The metadata register itself is 32 B = 16 such fields, so a single write to it covers 16 × 16 = 256 bursts × 32 B = 8 KiB.Misconception: confusing "1 bit per burst" with "1 write per burst." The 15 spare bits per field (only 1 is used, per-burst) are what let a single write span many bursts.
Problem 3 · hard
A 4 KiB page's bursts only achieve a 4× write reduction, far short of the theoretical 256×. What specifically causes the gap?
Show answer
Bank and channel interleaving. The address-mapping bits that select a bank/channel sit below the column bits (to exploit parallelism), so consecutive bursts of a 4 KiB page scatter across many bank/channel targets — only 4 bursts per bank/channel target end up adjacent enough to share one metadata field. So instead of one write covering 256 bursts, McZero needs 32 writes (one per bank/channel target) to cover the page's 128 bursts.Misconception: that the encoding's maximum density (256×) is what any workload sees. Real address mapping fragments it down to 4× for exactly page-sized, page-aligned regions.
Problem 4 · medium
Why does McZero need to invalidate CPU cache lines both before and after setting a metadata bit — wouldn't one pass suffice?
Show answer
The two passes guard against two independent races: (1) a dirty cache line evicted right after the flag is set would write stale data back over it (needs the before pass to kill dirty copies first); (2) the CPU's prefetcher could speculatively load a line right before the flag is set, leaving stale cached data readable afterward — a real leak risk (needs the after pass). One pass only closes one of the two windows.Misconception: treating cache coherence as a single point-in-time check. It's a race across two independent hardware behaviors (write-back and prefetch), each needing its own guard.
Problem 5 · medium
A malicious store bypasses the cache and issues a masked write to a burst that is still marked "zero" in metadata. What's the danger, and how does the paper suggest closing it?
Show answer
A masked write only touches some bytes of the burst; if the rest of the burst's array content is stale (pre-zeroing) garbage, the next full read would return the masked-in new bytes mixed with leaked old bytes. The paper's fix: have the MC intercept masked writes, check the zero bit first, and if set, transform the masked write into a full write with the remaining bytes explicitly zeroed.Misconception: assuming "zeroed in metadata" means the array itself was already cleared. It wasn't — the array content is still whatever was there before, hidden only as long as reads keep being intercepted.
Problem 6 · easy
Why doesn't McZero improve hackbench's overall runtime, even though it clearly speeds up individual larger allocations?
Show answer
Hackbench's allocation mix is dominated by ~2000 4 KiB pages versus only a handful of 8–32 KiB allocations. Since McZero is actually slower per-page at 4 KiB, and the rare larger wins are too few to matter statistically, the end-to-end duration and energy come out within noise of Linux's default.Misconception: that a component-level win (microbenchmark) automatically translates to an end-to-end win. It only shows up if the workload's allocation profile matches where the technique is strong — large pages, not small hot ones.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Does McZero require new DRAM silicon?▾
No — LPDDR6's metadata field is a standardized feature already defined by JEDEC. McZero only requires new logic inside the memory controller (which is typically integrated on the CPU die, not the DRAM chip) plus OS support. This is explicitly contrasted with RowClone, which needs DRAM-chip-level changes.
Q2Is the zeroing reversible — could an app "un-zero" a page by accident?▾
Writing a 1 to a metadata address marks a burst zero; writing a 0 is defined as a no-op. So once set, the zero flag can only be cleared by an actual data write to that burst (which the MC handles by clearing the bit automatically), never by another metadata write.
Q3Does a cold-boot attack threaten the leftover (unzeroed) data sitting in DRAM?▾
The paper argues no — LPDDR memory in these systems is soldered to the motherboard rather than on a removable DIMM, so the authors judge classic cold-boot extraction (which typically requires physically pulling a DIMM) to be impractical here. This is a risk judgment about the deployed hardware, not a claim that cold boot is physically impossible.
Q4Why is McZero slower than Linux for small hot pages?▾
For a 4 KiB hot page, Linux just writes zero cache lines directly (49.2 ns). McZero must still run its two cache-invalidation passes regardless of page hotness, plus the metadata write — overhead that a tiny already-fast operation can't amortize (728.3 ns).
Q5How much of the 16-bit metadata field does McZero actually use?▾
Only 1 bit per 32 B burst is needed for the zero flag, so McZero's one-zero-bit-per-burst requirement uses only about 5.9% of the dedicated metadata space — leaving the rest potentially reusable, e.g. for cache-tag metadata from unrelated work reusing the same LPDDR6 feature.
Q6Why is there a discontinuity in Linux's zeroing time between 128 KiB and 256 KiB?▾
The simulated L2 cache is 256 KiB. Zeroing writes below that size stay resident in cache; once the zeroed region exceeds the cache size, write-backs to DRAM start dominating, causing a jump from 2.8 µs to 106.3 µs. McZero has no equivalent cliff since it never writes the actual zero payload through the cache hierarchy.
Q7How does this compare to using a DMA/copy accelerator (like Intel DSA) for zeroing?▾
Accelerators free CPU cycles but still move the same bytes over the memory bus — bandwidth and DRAM energy costs remain. McZero instead avoids the zeroing write traffic itself: normal reads to a marked burst still transfer the data payload plus metadata over the bus, but the MC never has to write a bulk zero payload in the first place.
Q8Does this work generalize beyond zeroing?▾
The general pattern — giving the MC a cheap, OS-writable side-channel of metadata to short-circuit real memory traffic — is reused elsewhere: related work uses the same LPDDR6 metadata field to store cache tags and validity bits for a non-volatile-memory cache. The authors also flag future work on multicore systems, real-world applications, the cache-eviction costs of running on a physical machine, and larger-memory workloads.

Core terms
