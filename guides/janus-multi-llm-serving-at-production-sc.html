1Prefill vs decode, and why decode is bandwidth-bound▾

LLM inference has two phases. Prefill processes the whole prompt at once — compute-heavy, good GPU utilization. Decode emits one token at a time, each step re-reading the full weights and KV cache — memory-bandwidth-bound, not compute-bound.

Now you're ready: Janus's three resource axes (HBM capacity, compute, bandwidth) exist because prefill and decode stress different ones.
2SLOs: TTFT, TPOT, and "attainment"▾

Every request has a deadline for its first token (TTFT) and a per-token deadline afterward (TPOT). Attainment is just the fraction of requests (or tokens) that meet both. It's the primary metric — device count is secondary.

Now you're ready: Janus's headline number, 0.97–1.0 attainment, is what all its scheduling machinery is built to protect.
3MaaS: many models, one cluster, wildly different traffic▾

Instead of one team owning one cluster for one model, a MaaS platform multiplexes hundreds of models — 0.6B to 671B parameters — for many applications with independent, unpredictable traffic.

Now you're ready: the paper's three production challenges (bursts, power-law popularity, heterogeneous demand) are all symptoms of this multi-tenancy.
4Bin packing, informally▾

Given items of different sizes and bins of fixed capacity, pack items using as few bins as possible. Here, "items" are models with resource demands and "bins" are devices with capacity 1.0 on each of three axes at once — vector bin-packing.

Now you're ready: the Steady Pool's slow path is exactly this — packing tail models tightly by complementary resource shape.
5Gaussian processes as a cheap forecaster▾

A GP is a regression model that also reports how confident it is. With few data points (a newly onboarded model) it works reasonably and knows to say "I'm not sure" — which is hard for plain linear regression or historical averages.

Now you're ready: the Performance Oracle is two GPs; its calibrated uncertainty is what makes the system over-provision safely under sparse data.
6Parallel-machine deadline scheduling▾

You have several machines (prefill instances) and a backlog of jobs (requests) each with a processing time and a deadline. Maximizing the number of jobs finished on time on one machine is solvable exactly (Moore-Hodgson). On many machines it's NP-hard.

Now you're ready: LST-IMH is exactly this multi-machine problem, solved approximately by repeatedly applying the single-machine solution.
7Virtual memory, briefly▾

An OS gives a process a virtual address space and maps pages to physical memory only as needed, so allocation doesn't require pre-reserving contiguous physical memory.

Now you're ready: xTensor does this for HBM — a virtual address space that the manager backs with physical pages from a shared pool, so no model statically owns a chunk of memory.
8Cold starts and why they're slow▾

Activating a fresh model replica normally means container startup, memory allocation, loading weights from storage, and forming a collective-communication group — tens of seconds to minutes.

Now you're ready: Janus's three-state lifecycle and D2D fork exist specifically to skip most of that path for models that are already running somewhere.
9Fast and slow thinking, the analogy the paper borrows▾

Kahneman's "System 1 / System 2": a fast, reflexive response and a slower, deliberate one. Janus borrows this only as a naming device for scheduling cadence — it says nothing about how requests themselves execute.

Now you're ready: "slow path" (30 s bin-packing) and "fast path" (0.5 s autoscaling) are Janus's System 2 and System 1.
The whole story in one place

Janus in a nutshell

The problem, the dual-clock fix, and how the pieces connect.

A production MaaS cluster faces three problems that no prior system solves together: bursts that spike traffic 5–10× in seconds, power-law popularity (top 12% of applications drive 80% of requests) that makes one policy wrong for both head and tail, and heterogeneous but complementary resource demands (HBM capacity, compute, bandwidth) that scalar device allocation can't exploit.

Janus's fix is a Service–Engine co-design around dual-timescale scheduling. A Steady Pool runs the slow path: every 30 s, vector bin-packing tightly colocates low-traffic tail models by complementary resource shape. A Elastic Pool runs the fast path: every 0.5 s, an SLO-driven controller scales dedicated replicas of bursty head models. Both paths are fed by a Performance Oracle — two Gaussian-process surrogates that predict resource demand (Capacity GP) and SLO attainment vs. instance count (Elasticity GP).

Requests are dispatched by LST-IMH, a new 2-approximation algorithm for multi-instance deadline scheduling. At the Engine layer, xTensor virtualizes HBM into one pool so colocated models share memory dynamically, a three-state lifecycle (active/warm/cold) decouples model from instance lifetime, and D2D fork pulls weights directly from a running peer for sub-second scale-out.

The payoff: on a 768-device cluster replaying 603 K production requests across 62 applications, Janus holds 0.97–1.0 SLO attainment (vs. 0.80–0.92 for the best baseline) while using 27% fewer device-hours than statically-provisioned ServerlessLLM.

🕰️ Key takeaways

  • Static allocation (ServerlessLLM) and independent-scaling (BlitzScale) each solve half the problem; Janus's dual clock solves both.
  • Placement (Steady, 30 s), scaling (Elastic, 0.5 s), and routing (LST-IMH) are separate loops that must stay consistent, not one big optimizer.
  • The Oracle's two GPs never model the same quantity — one predicts a resource vector, the other predicts SLO attainment.
  • LST-IMH generalizes an optimal single-machine algorithm (Moore-Hodgson) to a provably NP-hard multi-machine problem with a 2× worst-case guarantee.
  • xTensor + D2D fork keep reactivation sub-second even for the largest model (742 ms D2D vs. 2712 ms H2D wakeup for the 671B model) — both far faster than a conventional cold-start's tens-of-seconds-to-minutes full instance initialization.
  • Result: 0.97–1.0 SLO attainment, 27% fewer device-hours than static allocation.
Six everyday pictures

How to think about Janus

Each stands alone; every one ends with where it breaks down.

The core idea · dual clocks

The store manager and the fire marshal

A store manager reorganizes shelves once a month for efficiency — slow, deliberate, global. A fire marshal reacts to an actual fire in seconds — fast, local, urgent. One person doing both jobs on one schedule would either evacuate too slowly or reorganize shelves constantly. Janus runs them as separate clocks: 30 s bin-packing for the "shelves," 0.5 s scaling for the "fire."

Where it breaks: the two clocks share the same device pool, so a slow-path decision can still starve the fast path if it doesn't leave enough spare devices — which is exactly why the Elastic Pool's budget is computed after the Steady Pool.
Placement · vector bin-packing

Packing a moving truck by weight AND shape

A mover doesn't just count boxes — a heavy, small box (HBM-heavy model) and a light, bulky one (compute-heavy model) fit together far better than two heavy boxes. Janus's bin-packing insertion rule places each new model into the bin whose remaining space best complements it on all three axes at once.

Where it breaks: a mover packs once; Janus repacks only when complementarity actually degrades (a damage-ratio threshold), not on every departure — real trucks don't get to selectively reshuffle mid-drive.
Forecasting · the Performance Oracle

A weather forecast with an honest confidence interval

A good forecaster doesn't just say "70°" — it says "70°, ±2° with 10 years of data, ±10° with 2 days of data." The Elasticity GP does exactly this: for a brand-new model with few observations, its wide uncertainty pushes the Model Scheduler to over-provision rather than guess confidently and be wrong.

Where it breaks: weather doesn't respond to the forecast; workloads sometimes do (traffic shifts because Janus scaled), so the GP is incrementally updated from fresh telemetry (Sherman–Morrison updates) rather than fit once and left static.
Dispatch · LST-IMH

Triage: treat the most time-pressured patient first

An ER doesn't take patients in arrival order — it treats whoever has the least slack before things go badly wrong. LST-IMH does the same across instances: it sorts machines by decreasing availability time (the busiest, most constrained one first) so an easy, lightly-loaded machine doesn't grab a job that only the constrained one could still finish on time.

Where it breaks: triage order is a heuristic that's good but not provably optimal for many patients/machines at once — which is exactly why LST-IMH is a 2-approximation, not an exact solver.
Memory · xTensor

An apartment building with movable interior walls

Instead of permanently walling off Unit A for tenant A, the building keeps one shared floor plan and slides partitions as tenants' needs change. xTensor is the same idea for HBM: weights grow from one end, KV caches and activations grow from the other, and free physical pages flow to whichever model needs them next.

Where it breaks: moving a real wall is slow; xTensor keeps weight moves cheap only because they're pre-registered once at startup — genuinely new physical-page mapping (37–235 μs/page) is deliberately kept off the hot KV path.
Reactivation · D2D fork

Cloning a coworker's laptop over LAN, not mailing a new one

If a coworker already has your exact setup running, copying their disk directly over the office LAN is faster than pulling a fresh image from the file server down the hall (host-pinned DRAM) — and both beat reinstalling from a box in the warehouse (a full reload from persistent storage). D2D fork pulls weights directly from an already-active peer device over the fast interconnect; H2D wakeup instead restores a warm model's weights from host-pinned DRAM — same building, slower hallway, with the real speedup ranging from roughly even to 3.7× depending on model size.

Where it breaks: cloning a laptop doesn't slow down the original; forking does cost the source device a small, brief throughput hit (up to 5.7% P99 TPOT) while it serves the transfer.
The full explanation

How it actually works

Layer by layer, with the key mechanisms rebuilt as diagrams.

1 · The Performance Oracle

Two GP families share input features (token rate, request rate, mean/variance of input and output lengths) but predict different targets. The Capacity GP maps them to a normalized resource vector v=(HBM-C, SM, HBM-BW)∈[0,1]³ for the slow path. The Elasticity GP additionally takes instance count m and predicts SLO attainment for the fast path; binary search over m finds the minimum instance count hitting a target. GPs are chosen for data efficiency (few profiling points) and calibrated uncertainty, with O(n³) one-time fit and O(n) prediction plus incremental Sherman–Morrison updates.

↗
Want the GP mechanics themselves? A companion piece — Gaussian Processes in Janus — walks through what a Gaussian process actually is, and includes a live demo of the exact behavior quoted above: watch the Elasticity GP's uncertainty band widen over unprofiled instance counts and force a more conservative (over-provisioned) choice.

2 · Slow path: bin-packing the Steady Pool

Every 30 s, models are packed onto devices as an online 3D vector bin-packing problem: each bin has capacity (1,1,1); a packing is feasible when every dimension's sum stays ≤1 per bin. A single fragmentation potential Φ drives both decisions — insertion picks the feasible bin whose residual best complements the new model (minimizing Φ's one-step increase), and departure triggers a repack only once a damage ratio ρ exceeds threshold α. A background consolidation pass runs every 30 s to reclaim devices for the Elastic Pool.

3 · Fast path: autoscaling the Elastic Pool

Every 0.5 s the scheduler queries the Elasticity GP for the minimum instance count mi per model meeting its SLO target. If Σmi exceeds the Elastic Pool's device budget B (what's left after the Steady Pool), quotas are scaled proportionally, qi = mi·B/Σmj, then rounded to integers via the Hamilton largest-remainder method so no allocation is off by more than one instance. A sliding window of the two most recent plans suppresses oscillation: a new plan is accepted only if it differs from both.

# fast path, every 0.5s
for model i: m_i = min instances s.t. Elasticity_GP(features_i, m_i) ≥ target
if sum(m_i) > B:
    q_i = m_i * B / sum(m_j)          # proportional, fractional
    round via Hamilton largest-remainder   # off by ≤1 instance each
if plan == last_plan or plan == last_last_plan:
    discard                          # anti-oscillation

4 · Request Scheduler: LST-IMH

Formal problem: m prefill instances with availability times T₁..Tm; n backlogged requests each with processing time pj and deadline dj=aj+TTFT_SLO. Maximize on-time completions — this is Pm|Ti|ΣUj, NP-hard in general. LST-IMH sorts machines by decreasing Ti (most constrained first), and on each machine solves a shifted single-machine problem (effective deadline dj−Ti) optimally via Moore-Hodgson in O(n log n); rejected jobs pass to the next machine. Total time O(mn log n). The bound holds for any ordering, but LST is what makes it good in practice.

5 · Engine: xTensor, lifecycle, and D2D fork

xTensor virtualizes HBM beneath the DL runtime's allocator: at startup, all physical pages form one pool, and a global xTensor — a virtual region sized to the full pool — is mapped once. Weight allocation/deallocation becomes reserving/releasing contiguous segments (best-fit, from the high-numbered end) with no further driver mapping. KV caches and activations use fine-grained page mapping from the low-numbered end, with a per-model cache of already-mapped pages keeping mapping off the hot path.

Each model has three states: active (weights in HBM, serving), warm (weights in host-pinned DRAM, collective group retained — fast recovery), cold (everything released except minimal framework state). H2D wakeup restores warm models by async per-layer transfer overlapped with execution. D2D fork restores active-elsewhere models by pulling weight bytes directly from a peer's global-xTensor offsets over the faster device-to-device fabric — no host staging.

💡
Why split weight and KV management? Page map/unmap costs 37/235 μs per 2 MB page — cheap once, expensive at KV's fine grain and churn rate. Pre-registering weights once and only ever mapping KV pages keeps both paths fast for their own reason.
Follow the numbers

Worked examples

Four traces through the paper's real numbers.

① Rounding fractional quotas with Hamilton's method

Elasticity GP wants m = [5, 3, 2] instances for three models; only B = 8 devices remain. What quotas does each model get?

  1. Proportional shares: q_i = m_i·B/Σm_j = 8·[5,3,2]/10 = [4.0, 2.4, 1.6].
  2. Floor each: [4, 2, 1] = 7 devices, 1 left over.
  3. Largest remainder wins it: remainders are [0.0, 0.4, 0.6] → model 3 (0.6) gets the extra device.
  4. Final: [4, 2, 2] = 8 devices, each model within 1 of its exact proportional share.
🕰️
Insight: Hamilton rounding is what stops "8.4 devices needed" from becoming an arbitrary integer decision — the largest fractional remainder gets first claim on leftover capacity.

② LST-IMH by hand, two machines

Machine A is busy until T_A=4; Machine B is free now, T_B=0. Backlog: job1 (p=3, d=5), job2 (p=3, d=10).

  1. Sort machines by decreasing T: schedule A first (T=4), then B.
  2. Shift deadlines for A: d′_j = d_j − 4 → job1: d′=1, job2: d′=6. Moore-Hodgson on A: job1 would finish at 3, already past its shifted deadline of 1 — rejected before it can even run. job2 finishes at 3 ≤ 6 — kept.
  3. A completes job2 (real finish time 4+3=7, well inside its actual deadline of 10). job1 passes to B.
  4. Machine B (T=0, no shift): job1 finishes at 3 (≤5, on time).
💡
This toy example is small enough that both jobs end up completed regardless of exactly how the machines are ordered; it demonstrates the shifted-deadline mechanism (a busy machine only keeps jobs it can truly finish before its own availability time, deferring the rest to freer machines), not a case where getting the order wrong changes how many jobs complete overall — that effect only shows up with more jobs and tighter contention.

③ D2D fork vs. H2D wakeup for a 671B model

Table 1: DeepSeek-V3 (TP=16) takes 2712 ms via H2D wakeup, 742 ms via D2D fork. How much faster, and what does that buy during a burst?

  1. Speed-up: 2712 / 742 ≈ 3.7× faster reactivation via D2D.
  2. End-to-end effect (Fig. 12a): during an actual burst, D2D fork reactivates in 0.74 s holding SLO at ~98%; H2D-only takes 2.71 s and SLO dips to ~90%.
  3. Source-side cost: forking perturbs the donor instance's P99 TPOT by at most 5.7% for the 671B case (42.6 ms → 45.0 ms), recovering immediately.
🕰️
Insight: even for the largest model in the fleet, D2D fork keeps burst reactivation under a second — the mechanism that makes 0.5 s-cadence scaling meaningful rather than theoretical. (Note: the 2.8× figure elsewhere in this guide refers to raw D2D-vs-H2D bandwidth, not latency — the actual latency speedup varies by model, from about 1.0× for small models up to this 3.7× for the largest.)

④ Device-hours: where the 27% savings comes from

Janus uses 13,440 device-hours/day; ServerlessLLM statically locks all 768 devices.

  1. ServerlessLLM: 768 devices × 24 h = 18,432 device-hours/day, all the time.
  2. Janus: reported at 13,440 device-hours/day — consistent with the trace's night trough (~390–480 devices) and day peak (~580–660).
  3. Savings: (18,432 − 13,440) / 18,432 ≈ 27.1% fewer device-hours.
  4. Same time, better SLO: Janus does this while holding 0.97–1.0 SLO attainment, vs. ServerlessLLM's 0.22–0.30 once daytime traffic arrives.
💡
The savings come from elasticity, not from doing less work — idle capacity at night is returned to the pool instead of sitting reserved.
Test yourself

Practice problems

Try before opening the answer — each names the misconception it checks.

Problem 1 · easy
Why doesn't Janus just run one fast, frequent scheduling loop for everything instead of two separate paths?
Show answer
Because the two problems have different natural timescales and costs. Bin-packing 62 applications for tight colocation is worth doing carefully but not every 0.5 s (it's not that volatile and repacking causes migrations). Scaling a bursting model can't wait 30 s. Running everything on one cadence would either react too slowly to bursts or repack too often for no benefit.Misconception: that "more frequent" scheduling is strictly better. Frequency should match volatility; matching it to the wrong subproblem wastes control-plane cost or misses bursts.
Problem 2 · medium
The Capacity GP and Elasticity GP take almost the same input features. Why not merge them into one GP?
Show answer
They predict different targets for different consumers: Capacity GP outputs a resource-demand vector for the slow-path bin-packer; Elasticity GP outputs SLO attainment as a function of workload and instance count for the fast-path autoscaler. Instance count is a meaningful input only to the second GP. Merging them would conflate a placement question with a scaling question that use different decision procedures downstream (bin-packing vs. binary search).Misconception: that shared inputs imply the models should be shared too. What matters is what's being predicted and who consumes the prediction.
Problem 3 · medium
LST-IMH sorts machines by decreasing availability time T_i. Why not increasing — schedule the free machine first?
Show answer
A free machine (low T_i) has lots of slack — nearly any job fits regardless of when it's scheduled. A busy machine (high T_i) has little slack; a job that barely meets its deadline there might miss it entirely if a light job "steals" that slot first. Scheduling the constrained machine first lets its Moore-Hodgson pass claim exactly the jobs only it can still finish on time, before easier machines grab them.Misconception: that scheduling order doesn't matter across machines since each runs its own optimal single-machine algorithm. Per-machine optimality doesn't imply global optimality — the order jobs are offered to machines does.
Problem 4 · hard
LST-IMH is a 2-approximation, not exact. Sketch why the multi-machine version is NP-hard while the single-machine version (Moore-Hodgson) is solvable exactly.
Show answer
On one machine, jobs execute in a strict sequence, so "which jobs are late" reduces to a clean exchange-argument optimum (drop the job that most postpones others once a violation occurs) — solvable greedily in O(n log n). On multiple machines, you must also decide which machine each job runs on, and that assignment interacts combinatorially with every other job's assignment and deadline — the same structure as classical NP-hard multiprocessor scheduling (P||ΣU_j generalizations). LST-IMH sidesteps this by decomposing into ordered single-machine subproblems, at the cost of no longer being exact.Misconception: that a good single-machine algorithm "obviously" extends to many machines. The extra assignment dimension is precisely what makes the multi-machine case hard.
Problem 5 · medium
A model transitions active → warm rather than active → cold when it goes idle briefly. What's the practical trade-off?
Show answer
Warm keeps weights in host-pinned DRAM plus the collective-communication group and framework context — meaning host-pinned memory is spent, but reactivation (H2D wakeup) is fast (hundreds of ms to ~1s per Table 1). Cold releases everything except minimal state, freeing DRAM but requiring a full reload from persistent storage on reactivation. The choice trades standby resource cost against reactivation latency.Misconception: that "idle" always means "release everything." The three-state design exists because idle time and reactivation urgency vary, so one blanket policy would either waste memory or waste latency.
Problem 6 · hard
Why does D2D fork reuse the global xTensor specifically, rather than allocating a fresh buffer for the transfer?
Show answer
The global xTensor's physical pages are mapped once at startup and registered with the communication backend — so any active model's weight offsets within it are already valid, driver-registered addresses. Reusing it means the source device can report offsets and the target can pull directly, with zero new page-mapping overhead (recall: naive page-by-page mapping can take up to 17.5 ms for 1 GB). A fresh buffer would need its own mapping/registration step before any transfer could start, undermining the sub-second goal.Misconception: that D2D fork's speed comes only from fast interconnect bandwidth. The bandwidth helps, but avoiding per-transfer page mapping is what the global xTensor specifically contributes.
Problem 7 · easy
If both pools have plenty of spare devices and traffic is calm, how much does Janus's machinery actually help versus a simple static split?
Show answer
Not much — if nobody is starved and no burst is happening, a static split already meets SLOs (consistent with the paper's night-time numbers, where all four systems perform similarly, 30–80 req/s goodput). Janus's advantage shows up specifically under load imbalance: bursts, power-law skew, or resource contention that a static or single-pool policy mishandles.Misconception: that a more sophisticated system always wins by a large margin. Its benefit is proportional to how much the workload actually stresses the dimensions it targets.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is the Steady Pool vs. the Elastic Pool?▾
Two disjoint sets of device instances. The Steady Pool colocates multiple low-traffic (tail) models per instance via bin-packing; the Elastic Pool dedicates each instance to one model and scales replica count for high-traffic (head) models that burst. Devices move between pools as the slow-path consolidation frees capacity.
Q2Why does the Steady Pool get priority for devices over the Elastic Pool?▾
Losing a Steady Pool instance forces evicting every colocated model on it — a hard failure. The Elastic Pool can gracefully degrade by scaling a model's replica count down by one. So the budget flows Steady-first, Elastic gets the remainder.
Q3How is LST-IMH different from just running Moore-Hodgson on every machine independently?▾
Running Moore-Hodgson independently per machine with no coordination lets an easy, lightly-loaded machine consume jobs that only a heavily-loaded machine could still finish on time, and vice versa. LST-IMH's ordering (busiest machine's shifted subproblem first) plus passing rejected jobs forward is what turns independent optimal solvers into a coordinated 2-approximation.
Q4What does "2-approximation" actually guarantee?▾
LST-IMH always completes at least half as many requests on time as the true (unknown, NP-hard-to-compute) optimum, for any machine ordering — with LST ordering additionally being what's empirically near-optimal.
Q5Why does the paper describe the two scheduling paths using "fast and slow thinking"?▾
Purely as a naming device for scheduling cadence — the slow path deliberates every 30 s, the fast path reacts every 0.5 s. It does not imply anything about how individual requests execute; the paper is explicit that the analogy describes scheduling, not execution.
Q6Does xTensor mean models share memory unsafely?▾
No — each model's tensors still have their own virtual addresses and logical isolation; xTensor only changes how virtual addresses are backed by physical pages, which are drawn from a shared pool rather than statically reserved per model. Framework logic above stays unaware of the difference (§5.3), except P/D disaggregation, which needs its KV address registration adapted.
Q7Why is D2D fork faster than H2D wakeup if H2D also uses fast interconnects?▾
On the target cluster, measured D2D bandwidth (163.6 GB/s) is 2.8× H2D bandwidth (59.0 GB/s) — device-to-device links are simply faster than host-mediated transfer on this fabric. D2D also skips host-memory staging entirely. That bandwidth ratio doesn't translate one-to-one into latency, though: measured end-to-end reactivation speedups in Table 1 range from about 1.0× for small models up to 3.7× for the largest.
Q8What happens to a request that LST-IMH can't fit anywhere?▾
It's shed — Moore-Hodgson naturally rejects jobs that would cause others to miss deadlines, so unfit requests get an immediate timeout callback (letting the application degrade gracefully), or optionally re-enqueue with a relaxed deadline ("reentry" mode) trading lower attainment for a lower outright failure rate.
Q9Does Janus always beat every baseline?▾
On the production replay and rate/SLO sensitivity sweeps, yes, by a wide margin. On some lower-load, more uniform traces (W6–W7, Poisson arrivals) the gap narrows because all systems face similar, less bursty pressure — and Prism's colocation can even edge out BlitzScale there, though Janus still leads overall.
Q10What's explicitly out of scope for this version of Janus?▾
Dynamic reconfiguration of a live model's tensor/data-parallel degree (parallelism is fixed at creation), and multithreaded workloads where threads share data — Janus targets independent, multiprogrammed applications on a CMP-like device cluster.

Where the paper flags its own limits from the paper

Fixed parallelism degree at model-creation time, no dynamic TP/DP reconfiguration, and multithreaded/shared-data workloads are explicitly out of scope per §5.2 and §7.4's framing of the system's target setting.
