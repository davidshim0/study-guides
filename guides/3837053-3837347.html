Splitting the lock, not the log

One append-only log pointer used to be fine — the SSD was the bottleneck. On a 2,600 KIOPS NVMe drive, that same log pointer becomes the bottleneck. ScaLog fixes it without touching the on-disk log at all.

📄 "Manycore Scalable Logging for Log-Structured Filesystem" · Yoo, Kim, Won 🎓 Assumes familiarity with locks, page cache, block devices ⏱ ~22 min read
📇

Don't add more logs — shrink and decouple the critical section around the one log you already have.
Split the transaction, localize the metadata, batch the request.

Before you begin

Quick glossary, then ten primers

Acronyms first — the paper leans on them constantly. Primers are collapsed; open what's unfamiliar.

Quick glossary

LFSLog-structured filesystem — writes are always appended, never overwritten in place.
F2FSFlash-Friendly File System — the Linux LFS this paper patches.
DIODirect IO — writes that bypass the page cache, going straight to the filesystem.
IOPS / MIOPS / KIOPSIO operations per second, and its millions/thousands.
NVMeThe command-queue interface modern SSDs use to accept many parallel requests.
dnodeF2FS's index node — the structure that maps a file offset to a physical block.
cp_rwsemF2FS's checkpoint rw-semaphore — writers hold it shared, checkpoint holds it exclusive.
STx / RL / MBAScaLog's three techniques: Split Transaction, per-segment Range Logging, Multi-Block Allocation.
1What a log-structured filesystem is▾

Instead of overwriting a block in place, LFS always writes new data to the next free slot at the end of a log, then updates metadata to point there. This turns random writes into sequential ones — good for flash, which erases in large blocks and wears out with overwrites.

Now you're ready: "append-only" means every write, even an overwrite of existing data, needs a *new* block — i.e. an allocation.
2The log pointer — LFS's single point of order▾

The log pointer marks the next free slot. To allocate a block, a thread must advance it — and only one thread can do that at a time, or two writers would claim the same slot. That's the seed of the whole scalability problem.

Now you're ready: every concurrent write funnels through this one pointer, no matter how many CPU cores or NVMe queues are available.
3The block bitmap▾

Alongside the log pointer, the filesystem tracks which blocks are valid via a bitmap. Allocating a block sets a bit; invalidating the old (overwritten) block clears one. In vanilla F2FS, one lock guards this entire bitmap.

Now you're ready: ScaLog's Per-segment Range Logging exists specifically to break this single global lock apart.
4Critical sections and lock granularity▾

A critical section is code that only one thread can execute at a time. The bigger the critical section (more work bundled under one lock), or the coarser its scope (one lock for a huge structure), the more threads queue up waiting for it.

Now you're ready: ScaLog's fixes are exactly this — shrink the critical section (Split Transaction) and shrink its scope (per-segment locks).
5Direct IO vs buffered IO▾

Buffered writes land in the page cache and get merged, deferred, and batched by a single writeback thread before hitting disk. Direct IO (DIO) skips the cache entirely — each application thread issues its own write straight to the filesystem, one allocation at a time, synchronously.

Now you're ready: DIO can't rely on the page cache to hide allocation cost — every DIO write pays the full allocation-serialization price, which is why databases and DNN checkpointing (both DIO-heavy) feel this bottleneck directly.
6Manycore scalability of storage▾

Modern NVMe SSDs expose per-core submission queues and sustain millions of IOPS — hardware is ready for full parallelism. The question is whether the software above it (the filesystem) can issue requests without threads blocking each other.

Now you're ready: this paper shows F2FS fails that test on fast SSDs — the device isn't the limit, a mutex is.
7Segments (F2FS's allocation unit)▾

F2FS groups blocks into segments; the log writes sequentially within a segment, then switches to a new one. Segments are the natural boundary for splitting a global structure into independent, lockable pieces.

Now you're ready: "per-segment" range lists exploit this existing boundary — no new on-disk concept required.
8Checkpoints and crash consistency▾

A checkpoint flushes dirty in-memory metadata to disk so the filesystem can recover after a crash. Writers hold cp_rwsem shared; checkpoint takes it exclusive, so checkpoint only runs once all in-flight writes finish.

Now you're ready: this is exactly the lock ScaLog leans on to prove its two-phase (Split Transaction) update never corrupts state after a crash.
9Reading a latency breakdown table▾

A write's latency splits into stages: pre-process (find where to write), allocation (claim the block + update metadata), post-process (submit IO, wait). Whichever stage's *share* grows as threads increase is the scalability bottleneck.

Now you're ready: the paper's Table 1 is the whole diagnosis in one table — allocation's share balloons from 19% to 83% as threads go from 5 to 40.
10Multi-log vs single-log scaling▾

The obvious fix to lock contention is to give each core (or thread) its own log — no shared pointer, no contention. MAX and DeLFS take this route. ScaLog instead asks: can a *single* log be made to scale, by making each allocation itself cheaper and more concurrent?

Now you're ready: ScaLog is orthogonal to multi-log designs — it could, in principle, be applied to each per-core log in a multi-log system too.
The whole story in one place

ScaLog in a nutshell

Why LFS stopped scaling, and the three-part fix.

On slow storage, F2FS's single log pointer costs nothing — the device itself is the bottleneck. On a PCIe Gen5 SSD sustaining 2,600 KIOPS, that balance flips: at 40 threads doing 4 KB Direct IO random writes, journal-disabled ext4 hits 3× F2FS's throughput, because F2FS's block allocation stage now consumes 83% of write latency (up from 19% at 5 threads).

Two design flaws cause this. Coarse-grained locking: advancing the log pointer and updating the block bitmap happen in one fused critical section, so two writers can't even overlap the *different* parts of their allocation. Fragmented logging: Direct IO allocates one block at a time, so a 1 MB write re-enters the lock 256 times — once per 4 KB block — multiplying both lock acquisitions and, when a rival thread interleaves, the number of non-contiguous IO commands issued.

ScaLog's fix is not another log (that's what MAX and DeLFS already tried) — it makes the existing single log scale via three orthogonal techniques: Split Transaction decouples log-pointer and bitmap updates into two critical sections; Per-segment Range Logging replaces the one global bitmap with per-segment range lists, committed asynchronously; Multi-block Allocation claims a whole contiguous run under one lock acquisition instead of one block at a time.

The payoff: at 40 threads, F2FS-ScaLog reaches 1.7× F2FS throughput on 4 KB random write and 6.1× on 1 MB append — all with ~1.3K LOC and zero on-disk layout changes.

🗄️ Key takeaways

  • The bottleneck is the shared log pointer + bitmap critical section, not the SSD, once IOPS get high enough.
  • Direct IO can't hide allocation cost behind the page cache — it pays serialization cost on every write.
  • More logs (MAX, DeLFS) relieve pointer contention but leave per-allocation serialization untouched.
  • Split Transaction is safe because the intermediate (pointer-advanced, bitmap-stale) state is hidden behind the dnode page lock, and checkpoint can't observe it until both halves finish.
  • Per-segment Range Logging turns one global lock into many, and represents allocation as compact (offset, length) ranges instead of per-block bits.
  • Multi-block Allocation reduces per-request lock acquisitions toward O(1), bounded by node and segment boundaries.
  • Result: 1.7× (4 KB random write) and 6.1× (1 MB append) over F2FS at 40 threads, no on-disk format change.
Five everyday pictures

How to think about ScaLog

Each ends honestly with where it stops matching the real mechanism.

Split Transaction

One clerk who scans AND bags

A checkout clerk who must scan your item, then personally walk it over and bag it before ringing up the next customer — everyone waits through both steps. Split the job: one clerk scans (advances the log pointer), a separate step bags (updates the bitmap), and the next scan can start immediately.

Where it breaks: the two steps must still finish in order for your item before you leave the store — that ordering is enforced by the dnode page lock, not by store layout.
Per-segment Range Logging

One shared ledger vs a ledger per shelf

A warehouse where every restock is logged in one shared ledger — even restocking two unrelated shelves forces workers to queue for the same book. Give each shelf (segment) its own ledger, and workers restocking different shelves never wait on each other.

Where it breaks: checking a shelf's true state now means reading both its ledger and the master inventory bitmap — cheaper writes, slightly pricier reads.
Multi-block Allocation

Checking out three items separately vs one cart

Bringing three items to the register one trip at a time means three waits in line. Load them into a cart and check out once. Multi-block Allocation claims a whole contiguous run of blocks in one lock acquisition, instead of re-entering the lock per 4 KB block.

Where it breaks: the cart can't cross into a different aisle (node) or a different store (segment) mid-trip — those boundaries still force a second checkout.
Why more logs isn't enough

Three registers, each still slow

Opening three registers (multiple logs, as in MAX/DeLFS) relieves the line at any one register. But if every register's clerk still personally scans and bags each item under one uninterruptible step, three slow registers beat one slow register — but they're still slow.

Where it breaks: ScaLog and multi-log designs aren't rivals — ScaLog's per-allocation fixes could, in principle, speed up each register in a multi-log system too.
Commit at checkpoint / background

Reconciling the till overnight

A shop doesn't update the master inventory count after every single sale — it lets the day's receipts (range-list entries) pile up, then reconciles them overnight (at checkpoint) or in a quiet moment (background commit), using every idle cashier (CPU core) to speed the reconciliation.

Where it breaks: unlike an overnight batch, ScaLog can't let receipts pile up indefinitely — past a threshold (768 of 1024 slots) a background worker forces an early reconciliation.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt.

1 · The diagnosis — two bottlenecks in one allocation

Vanilla F2FS fuses the log-pointer advance and the block-bitmap update into one critical section, guarded (among others) by curseg_mutex. Lockstat shows this lock's wait time is >90% of block-allocation latency at 40 threads. On top of that, DIO allocates one block at a time, so a 1 MB write re-enters this critical section 256 times, and a competing thread can interleave, scattering the write into non-contiguous IO commands.

2 · Split Transaction

ScaLog decouples the fused allocation into two ordered transactions:

T_log:  advance log pointer, claim new block(s)
T_meta: update block bitmap for the new block and invalidate the old block

These can now interleave across threads — one thread runs T_meta while another runs T_log. Why it's safe: no application thread can observe the gap between T_log and T_meta, because locating a block requires the dnode page lock, which the writer holds across both transactions. And no crash can observe it either, because checkpoint (the only durability point) requires the exclusive cp_rwsem, obtainable only after all in-flight writes — T_log and T_meta — complete.

3 · Per-segment Range Logging

Instead of one global bitmap under one lock, each segment gets its own range list: entries of the form (offset, length, del, mtime), each protected by a per-segment lock. Two threads allocating in different segments never contend. Ranges are committed to the real bitmap two ways: at checkpoint (using one commit thread per idle CPU, each handling disjoint segments in parallel) or in the background, triggered once a segment's list exceeds T = 768 entries (75% of the 1,024 capacity), to bound checkpoint latency spikes.

4 · Multi-block Allocation

A single T_log acquisition now claims N blocks at once:

N = min( N_req, δ_node, δ_seg )
# N_req  = blocks still needed
# δ_node = free pointers left in the current node block
# δ_seg  = free blocks left in the current segment

Repeat until N_req = 0. A node or segment boundary still forces a new acquisition — those are structural limits, not something locking can batch past.

💡
Why overwrites stay cheap despite scattering: invalidating old blocks on an overwrite can touch many different segments (worst case O(N)), but because those blocks are spread out, two threads rarely collide on the same per-segment lock — invalidation doesn't become a new bottleneck in practice.

5 · Result — where the latency actually goes now

At 40 threads, ScaLog cuts block-allocation latency by 62% (80.1 → 30 µs) for 4 KB overwrite and 82% (29 → 5.3 ms) for 1 MB append. In the ablation, Range Logging is the dominant contributor for 4 KB random write (Split Transaction alone: +9%; combined with RL: +65.9% over Split Transaction alone), while for 1 MB append Split Transaction contributes most (+167%) since every thread writes into the same segment and RL alone can't relieve that — Multi-block Allocation is what finally cuts lock acquisitions from up to 256 down to 1–2 per request.

Follow the numbers

Worked examples

Four traces through the paper's real measurements, arithmetic checked.

① Where the 40-thread write actually goes (Table 1a)

Paper reports, at 40 threads: pre-process 1.1 µs, block allocation 80.1 µs, post-process 15.4 µs, total 96.7 µs. Check consistency and confirm the 83% figure.

  1. Sum the stages: 1.1 + 80.1 + 15.4 = 96.6 µs ≈ 96.7 µs (rounding). Internally consistent.
  2. Allocation's share: 80.1 / 96.7 = 0.828 → ~83%, matching the paper exactly.
  3. Compare to 5 threads: allocation there is 4.0 / 20.9 = 19.1% ≈ 19%.
  4. Growth factor: absolute allocation latency grew 80.1/4.0 = 20× across an 8× increase in threads — worse than linear, the signature of lock contention.
🗄️
Insight: post-process latency barely moves (15.4–17.4 µs across all thread counts) — it's IO wait, not contention. Only allocation grows superlinearly, pinpointing it as the bottleneck.

② Multi-block Allocation cutting lock acquisitions

A thread issues a 1 MB write (N_req = 256 blocks). Suppose the current node has 200 free pointers left and the current segment has 50 free blocks left.

  1. First acquisition: N = min(256, 200, 50) = 50 blocks claimed under one lock. N_req → 206.
  2. Segment switches (new segment, fresh capacity): N = min(206, remaining node room, full segment) — a large batch again, not 1 block.
  3. Vanilla F2FS would need 256 separate T_log-equivalent acquisitions for this same write.
  4. Measured reality (Table 3, 1 MB append): across 1–10 threads, ScaLog issues just 1.3–1.6 lock requests per write() call — segment/node boundaries are rare enough that most 1 MB writes fit in 1–2 batches.
💡
This is the direct cause of the IO-command drop too: fewer, larger allocations mean fewer contiguity breaks, so fewer separate IO commands per write().

③ Checkpoint overhead — is committing ranges expensive?

Table 2 (40 workers): bitmap-update cost is 833 ms with no optimization (Origin), and checkpoint totals are 525 ms (F2FS) vs 702 ms (ScaLog, Par+Bg).

  1. Background-only reduction: 833 → 310 ms = 62.8% cut.
  2. Parallel-only reduction: 833 → 475 ms = 43.0% cut.
  3. Combined (Par+Bg): 833 → 177 ms = 78.8% cut — the two techniques compound rather than substitute.
  4. Net checkpoint overhead vs plain F2FS: (702 − 525) / 525 = 33.7% ≈ the paper's stated "35% higher."
⚠
The honest trade-off: ScaLog buys huge write-path wins at the cost of a one-third longer checkpoint — acceptable since checkpoints are periodic and off the hot write path, but worth remembering if checkpoint latency itself is latency-sensitive in your workload.

④ IO fragmentation at 8 threads (Table 3)

For a 1 MB write() at 8 threads: F2FS issues 221 IO commands and 256 lock requests; ScaLog issues 1.6 of each.

  1. Lock-request reduction: 256 / 1.6 = 160× fewer acquisitions.
  2. IO-command reduction: 221 / 1.6 ≈ 138× fewer non-contiguous IO submissions.
  3. Why fewer IOs matters beyond CPU: each extra IO command is a separate NVMe submission-queue entry and completion interrupt — 138× fewer means far less queue and interrupt pressure, not just less lock contention.
🌱
For the tiering reader: this per-segment-lock, batch-the-request pattern is structurally the same fix as replacing a single global buddy-allocator lock with per-NUMA-node or per-CPU freelists in the Linux page allocator — localize the lock, then batch the request so you re-enter it less often.
Test yourself

Practice problems

Try before opening the answer. Each ends with the misconception it checks.

Problem 1 · easy
On a SATA SSD (~100 KIOPS), F2FS and ext4 perform similarly under 40-thread 4 KB random write. Why doesn't the log-pointer bottleneck show up here?
Show answer
The device itself caps throughput well below what the log pointer could serialize — F2FS is even better at exploiting flash's program-after-erase behavior in this regime. The bottleneck only shifts to software once the device can sustain far more IOPS than the critical section can process.Misconception: that ScaLog's fix is universally needed. It only matters once storage is fast enough to expose the software serialization — slow devices hide it entirely.
Problem 2 · medium
Why can't Split Transaction's "pointer advanced, bitmap not yet updated" gap corrupt data after a crash?
Show answer
Durability only happens at checkpoint, and checkpoint requires the exclusive cp_rwsem, which it can only acquire after every in-flight write — including both T_log and T_meta — has completed. So no checkpoint (and thus no crash-recoverable state) can ever capture the intermediate gap.Misconception: that splitting a transaction inherently risks a torn/inconsistent on-disk state. Here, an existing lock (cp_rwsem) already provides the needed barrier, so no new consistency mechanism is required.
Problem 3 · medium
MAX provides multiple logs yet fails to scale on both workloads (Figure 2). Diagnose why, in ScaLog's own terms.
Show answer
MAX still uses (1) a global block bitmap, so allocations across its multiple logs still serialize on that shared bitmap lock, and (2) block-at-a-time allocation for DIO, so it still suffers fragmented logging even with several logs. Multiplying logs removes contention on the log pointer specifically, but leaves the per-allocation bottlenecks ScaLog targets untouched.Misconception: that "more logs" and "faster allocation" are the same fix. They address different serialization points — pointer contention vs. per-allocation cost — and a system can fix one while leaving the other broken.
Problem 4 · hard
For 1 MB append, Range Logging (RL) adds almost nothing on top of Split Transaction (STx) alone — unlike 4 KB random write, where RL is the dominant contributor. Explain the difference.
Show answer
RL's benefit comes from letting different segments' updates proceed in parallel. In 4 KB random write, overwrites' valid/invalid updates typically land in different segments, so per-segment locks unlock real parallelism. In 1 MB append, every thread is appending into the same current segment — so the per-segment lock is still shared across all of them; the contention just moves from the global lock to that one segment's lock. RL doesn't help until Multi-block Allocation also cuts how often that segment lock is even acquired.Misconception: that per-segment locking always parallelizes. It only helps when the actual access pattern spans multiple segments — a workload confined to one segment gets no benefit from finer segment-level locks alone.
Problem 5 · medium
Why does ScaLog's checkpoint use one commit thread per idle CPU, and why is this "free" in a way that background commit during normal operation is not?
Show answer
During checkpoint, the filesystem freezes all other write activity and every CPU core would otherwise sit idle. Assigning one thread per core, each handling disjoint segments (hence disjoint locks), commits range lists with zero added lock contention and zero opportunity cost — those cores had nothing else to do. Background commit during normal operation, by contrast, competes with live writers for CPU and for the very per-segment locks writers are using.Misconception: that parallel commit and background commit are redundant. They target different resource constraints — idle-core parallelism at checkpoint vs. bounding range-list growth during live traffic — which is why the paper combines both (Par+Bg) rather than picking one.
Problem 6 · easy
ScaLog needs no on-disk layout changes. Why does that matter for adoption?
Show answer
Every design change lives in in-memory structures (range lists, split transactions, batched allocation) that get reconciled into the same, unchanged on-disk block bitmap format at checkpoint. Existing F2FS partitions, recovery tools, and fsck logic keep working unmodified — a deployment can adopt ScaLog without any migration or format-version concern.Misconception: that a filesystem-scalability fix must touch the on-disk format. Here the entire fix lives in how in-memory locking and metadata bookkeeping are organized, not in what's persisted.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is ScaLog a new filesystem?▾
No — it's a patch to F2FS's in-memory block-allocation logic, about 1.3K lines of kernel code, with no on-disk format change. It could in principle apply to other LFS-style filesystems facing the same fused-critical-section problem.
Q2Does ScaLog help buffered (non-DIO) writes too?▾
The paper explicitly scopes its evaluation to Direct IO, where each thread allocates its own blocks synchronously. Buffered writes route through a single writeback thread that already merges and defers allocations differently; the authors list extending ScaLog to buffered writes as future work.
Q3Why does 1 MB append benefit more (6.1×) than 4 KB random write (1.7×)?▾
A 1 MB write is 256× a 4 KB write in size, so fragmented, block-at-a-time allocation costs it far more in vanilla F2FS — more lock re-entries, more scattered IO commands. Multi-block Allocation collapses nearly all of that into 1–2 acquisitions, so the larger the request, the larger ScaLog's relative win.
Q4What exactly is a "range" in Per-segment Range Logging?▾
A tuple (offset, length, del, mtime) representing a run of consecutive LBAs allocated or invalidated together in one operation — a compact stand-in for what would otherwise be many individual bitmap-bit flips.
Q5Does adding a range list per segment cost extra memory or read overhead?▾
Yes on reads: determining a segment's true allocation state now means checking both the bitmap and its range list. The paper treats this as an acceptable cost for moving the bitmap-update work off the write's critical path.
Q6Why cap the range list at 768 of 1024 entries?▾
Unbounded accumulation would make the eventual checkpoint's commit step spike in latency. Triggering a background commit at 75% capacity (768/1024) keeps each commit bounded and the checkpoint predictable — an empirically chosen threshold, not a hard correctness requirement.
Q7How is ScaLog different from MAX and DeLFS?▾
MAX and DeLFS multiply the number of logs to relieve log-pointer contention across threads. ScaLog keeps a single log but makes each individual allocation cheaper and more concurrent. The two approaches are orthogonal — ScaLog's techniques could combine with a multi-log design.
Q8What's the actual overhead ScaLog adds?▾
Roughly 35% longer checkpoint latency (525 ms → 702 ms at 40 workers) as the main measured cost, plus modest extra memory for per-segment range lists and slightly pricier reads of segment state. There's no extra IO and no on-disk format cost.
Q9What did the authors leave for future work?▾
Extending the technique to buffered writes, and quantifying how much Per-segment Range Logging adds to garbage-collection overhead (since GC also needs to know per-segment validity state).
