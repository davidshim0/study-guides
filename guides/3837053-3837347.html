HotStorage 2026 · A Field Guide

Making one log scale across forty cores — by splitting what a single lock had fused

In F2FS and other single-log filesystems, every write shares one log pointer. On today's million-IOPS SSDs, that pointer — not the device — becomes the bottleneck. This is the plain-English story of ScaLog, the three small changes that let F2FS's write path finally scale with the core count.

📄 "Manycore Scalable Logging for Log-Structured Filesystem" · Yoo, Kim, Won 🎓 Some LFS/locking basics assumed — the primers cover them ⏱ ~25 min read
✂️

Only make threads wait on the few bytes they truly share — split everything else into its own lock, and batch what repeats so one acquisition does the work of many.
Measure what's shared first, then decide what has to wait.

Before you begin

Quick glossary, then seven ideas the paper assumes you know

Acronyms first — skim them once, then the primers below build the mental model. Jump straight to whatever's unfamiliar.

LFSLog-structured filesystem — turns all writes, including overwrites, into appends to a log, to get sequential IO on flash. Classic designs (and F2FS) use one shared log; some newer designs use several.

1Why log-structured filesystems exist▾

Flash doesn't like small random overwrites — a block must be erased before it's rewritten, and erasing happens in big chunks. LFS sidesteps this by never overwriting in place: every write, even to an existing file block, goes to the end of an append-only log. This turns random writes into sequential ones and reduces write amplification.

The cost: every writer, no matter which file or offset, is funneling through the same log, at the same pointer.

Now you're ready: ScaLog's whole premise is that this shared pointer — not the flash chip — becomes the bottleneck once the SSD gets fast enough.
2In-place update (IPU) vs LFS — what "allocating" means▾

Under IPU (ext4), overwriting an existing file block reuses the same physical block — non-allocating. Under LFS, every write, overwrite or append, needs a new block from the log — allocating. That's why LFS pays an allocation cost that IPU mostly avoids.

Now you're ready: the paper's baseline comparison is journal-disabled ext4 — chosen specifically because it's non-allocating and shows what a filesystem looks like without this bottleneck.
3Direct IO (DIO) — why it can't hide the cost▾

Buffered writes go through the page cache: a single writeback thread can batch and defer many pages' worth of block allocation into one trip. DIO bypasses the page cache entirely — each application thread allocates and issues its own IO synchronously, one write() call at a time. There's no writeback thread to absorb or merge the allocation cost.

Now you're ready: this is why the paper studies DIO specifically — it's the mode where allocation serialization shows up directly in request latency, with nowhere to hide.
4Critical sections, and why "coarse-grained" hurts at scale▾

A critical section is a region of code protected by a lock — only one thread executes it at a time. The cost of a critical section isn't the work inside it; it's the wait other threads accumulate outside it. A critical section that bundles two logically separate updates (e.g. "advance the log pointer" and "update the bitmap") forces every thread to wait for both, even if it only needed one.

Now you're ready: ScaLog's first move, Split Transaction, is literally about shrinking what's inside the critical section — nothing more exotic than that.
5Segments and the block bitmap▾

F2FS divides its storage into segments, each a fixed 2 MB (512 4 KB blocks). The block bitmap is a single data structure recording, for every block in the whole partition, whether it's allocated. One shared bitmap means updates to any segment compete for the same lock, even when the segments involved have nothing to do with each other.

Now you're ready: ScaLog's second move, Per-segment Range Logging, replaces this one global bitmap with many small per-segment structures that don't contend with each other.
6Why manycore scalability only recently became a filesystem problem▾

NVMe SSDs expose per-core submission queues specifically so many threads can issue IO in parallel without contending on the device side. A decade ago, SSDs were slow enough that software-side serialization was invisible — the device was always the bottleneck. Modern SSDs sustain millions of IOPS; the paper's test device (Samsung 9100 Pro) sustains ~2,600 KIOPS. Now the device can outrun the filesystem's internal locks.

Now you're ready: the paper's Figure 1 makes this literal — F2FS tracks ext4 on a slow SATA SSD (~100 KIOPS) but falls far behind ext4 on the fast NVMe SSD, same code, same thread counts.
7Checkpoints and crash consistency, briefly▾

A filesystem's in-memory metadata only becomes crash-safe once it's flushed to disk at a checkpoint. F2FS serializes writes against checkpoints with a reader/writer semaphore (cp_rwsem): writers hold it shared, a checkpoint needs it exclusive, so a checkpoint can only start once every in-flight write has fully finished.

Now you're ready: this existing mechanism is what lets ScaLog defer some of its bookkeeping without weakening crash guarantees — the deferred work is always folded in before any checkpoint completes.
The whole story in one place

ScaLog in a nutshell

The problem, the three fixes, and how they fit together.

F2FS, like other single-log filesystems, routes every write through one shared log pointer. Under buffered IO this rarely matters — a writeback thread batches many pages' worth of allocation into one trip through the log. Under direct IO, each thread allocates and issues its own write synchronously, so the log's serialization lands directly on request latency, with no writeback thread to absorb it.

The paper measures exactly how badly this scales in F2FS. At 40 threads on a PCIe Gen5 SSD, block allocation consumes 83% of 4 KB random-write latency and 98% of 1 MB append latency — up from 19% and 82%, respectively, at 5 threads. Lock-wait on the log-pointer lock (curseg_mutex) accounts for over 90% of that allocation latency at 40 threads. Two design choices cause this: a coarse-grained critical section that bundles the log-pointer advance with the block-bitmap update, and a block-at-a-time allocation policy that repeats the whole critical section once per 4 KB block, regardless of request size.

ScaLog fixes both, without touching the on-disk layout. Split Transaction decouples the log-pointer update from the bitmap update into two separate critical sections, so one thread can advance the pointer while another updates a bitmap entry. Per-segment Range Logging replaces the single global bitmap with a per-segment range list, so unrelated segments stop contending, and defers the actual bitmap write out of the critical path. Multi-block Allocation claims up to N = min(Nreq, δnode, δseg) blocks under one lock acquisition instead of one block per acquisition.

The payoff: implemented in ~1.3K lines of kernel code with no on-disk changes, ScaLog reaches 1.7× the throughput of vanilla F2FS on 4 KB random write and 6.1× on 1 MB append, both at 40 threads on the same hardware.

🧰 Key takeaways

  • F2FS (and other single-log LFS designs) funnels every write through one log pointer — fine when the device is slow, a hard bottleneck once it isn't.
  • DIO exposes this directly: no writeback thread to batch allocations, so serialization shows up in request latency.
  • Two root causes: coarse-grained locking (pointer + bitmap fused in one critical section) and fragmented logging (block-at-a-time).
  • Split Transaction separates the pointer update from the bitmap update into independent critical sections.
  • Per-segment Range Logging replaces the global bitmap with per-segment range lists, committed later, off the critical path.
  • Multi-block Allocation claims up to N blocks per lock acquisition, bounded by node and segment boundaries.
  • Multiplying logs is orthogonal to ScaLog's fix — demonstrated for MAX (still a global bitmap, still block-at-a-time); DeLFS takes a different, concurrent approach the paper doesn't analyze in the same detail.
  • Result: 1.7× (4 KB random write) and 6.1× (1 MB append) over vanilla F2FS at 40 threads, <1.3K LOC, same on-disk format.
🧠
For the mm-tiering reader: the move here rhymes with per-NUMA-node freelists replacing one global zone lock in the Linux buddy allocator — shrink and localize what's shared so unrelated cores stop contending, then batch repeated small operations (here, block-at-a-time allocation; there, per-page refcounting) into coarser units. The "defer the global bitmap commit to checkpoint" trick is also structurally similar to deferred TLB shootdown / RCU-style batched reclaim: do the authoritative, expensive update lazily and in bulk, as long as nothing can observe the gap.
Five everyday pictures

How to think about ScaLog

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Split Transaction

One toll booth, one lane

Every car on a one-lane toll road must stop at the same booth, pay, and wait for the gate to log the payment in the ledger before the next car can even approach. Split those two jobs — taking payment, updating the ledger — into two booths, and cars can be mid-payment at booth one while the previous car's ledger entry is still being written at booth two. ScaLog's Split Transaction is exactly this: the log-pointer advance and the bitmap update become separate booths instead of one fused stop.

Where it breaks: the two booths aren't fully independent — a car can't be "found" on the road (a reader can't locate the block) until it's cleared both booths, because the dnode page lock spans the whole trip. The gap is real but invisible from outside.
The mechanism · Per-segment Range Logging

One shared ledger vs. one page per account

A bank with one shared ledger book makes every teller queue, even for customers with completely unrelated accounts. Give each account its own page and tellers for account A and account C never block each other. ScaLog gives each segment its own range list and lock — an overwrite's "free the old block" and "claim the new block" usually land in different segments, so they now proceed in parallel instead of both touching one global bitmap.

Where it breaks: the per-account pages still have to be reconciled into the bank's master balance sheet eventually (at checkpoint). Isolation during the day doesn't mean the books stay separate forever — and reading "what's the true state of segment B right now" means checking both the page and the ledger.
The mechanism · Multi-block Allocation

Buying stamps one at a time vs. a booklet

Buying ten stamps one at a time means ten trips to the counter, ten waits in line. Buying a booklet of ten is one trip, one wait. Vanilla F2FS buys stamps one at a time — one lock acquisition per 4 KB block, even inside one large write(). Multi-block Allocation buys the booklet: it claims N = min(Nreq, δnode, δseg) blocks under a single acquisition.

Where it breaks: booklets only come in certain sizes. You can't buy more stamps than fit in the current booklet (node) or that the post office currently has in stock (segment) — crossing either boundary forces a second, smaller purchase. That's why real traces show 1.3–1.6 acquisitions per 1 MB write, not exactly 1.
Orthogonality · Multi-log ≠ fixed allocation

Separate lanes, one shared tollgate at the end

MAX, a multi-log scheme, gives the filesystem several lanes (logs) instead of one. But every lane still funnels into one tollgate with a global ledger and a "one car processed at a time" rule (global bitmap, block-at-a-time), so the extra lanes don't help much — everyone still queues at the gate. ScaLog instead widens the gate itself. (DeLFS takes a related but distinct approach, a lane per core; the paper treats it as orthogonal future work rather than showing it hits the same jam.)

Where it breaks: the two ideas aren't competitors — lanes and a wider gate compound. The paper frames ScaLog as orthogonal to multi-log designs generally, not a replacement for them; it just hasn't been combined with one yet.
Correctness · The pencil-before-notary window

Filling out a form in pencil before it's notarized

You can write a form in pencil — tentative, not yet official — as long as nobody can read or act on it until a notary stamps it final. ScaLog's gap, where the log pointer has advanced but the bitmap hasn't caught up, is exactly this: tentative, but invisible, because no reader can even locate the block (it must look it up through the dnode, whose page lock is held across the whole operation) until both halves finish.

Where it breaks: this only works because a specific pre-existing lock (the dnode page lock) already happens to span the gap. It's not a general license to leave things unsynchronized and assume nobody's watching — it required finding (and verifying) the one lock that already does the job.
The full explanation

How it actually works

The bottleneck, each of the three fixes, and the enforcement details that keep it crash-safe.

1 · Where the time actually goes

The authors split the F2FS write path (f2fs_file_write_iter) into three stages — Pre-process (locate/read the direct node), Block allocation (advance the log pointer, update the bitmap), Post-process (submit IO, wait) — and measured each under increasing thread count.

ThreadsPre-processBlock allocationPost-processTotal
50.8 µs (4%)4.0 µs (19%)16.2 µs (77%)20.9 µs
100.9 µs (4%)8.0 µs (30%)17.4 µs (66%)26.4 µs
201.0 µs (2%)32.0 µs (66%)15.7 µs (32%)48.7 µs
401.1 µs (1%)80.1 µs (83%)15.4 µs (16%)96.7 µs

4 KB random write, F2FS. For 1 MB append the same pattern is sharper: block allocation goes from 82% of total latency at 5 threads to 98% at 40 threads. Using lockstat, the authors trace >90% of block-allocation latency at 40 threads to waiting on the log-pointer lock, curseg_mutex.

2 · Split Transaction

Vanilla F2FS holds one lock across "advance the log pointer" and "update the block bitmap." ScaLog splits this into two transactions, Tlog and Tmeta, each with its own lock, so one thread's pointer advance can overlap with another thread's bitmap update.

💡
Why this doesn't break crash consistency: the interval between Tlog and Tmeta — pointer advanced, bitmap not yet updated — is never externally observable. A reader must first look up the block's address via the file's direct node (dnode), and the writer holds the dnode's page lock from before Tlog until after Tmeta. And the state only needs to be durable at a checkpoint, which can't start until cp_rwsem confirms every in-flight write — meaning both Tlog and Tmeta — has completed.

3 · Per-segment Range Logging

The single global block bitmap is replaced with one range list per segment. Each entry is (offset, length, del, mtime) — a contiguous run of newly allocated or invalidated blocks, not a one-bit-at-a-time flip. Each list has its own lock, so segments only contend with themselves, never with each other.

Range-list entries are reflected into the real bitmap later, off the write critical path, two ways:

  • At checkpoint: one commit thread per CPU, each covering a disjoint set of segments — since different segments use different locks, all commit threads run fully in parallel with zero contention.
  • In the background: once a segment's range list exceeds a threshold T = 768 entries (75% of the 1,024-entry capacity), a background worker flushes and clears it, so no single checkpoint has to absorb an unbounded backlog.
⚠
The cost: determining a segment's current allocation state now requires checking both the bitmap and its range list — a small lookup overhead the paper accepts in exchange for removing the global bitmap lock from the write path.

4 · Multi-block Allocation

ScaLog advances the log pointer by N blocks per acquisition instead of 1, where:

N = min( N_req, δ_node, δ_seg )
# N_req  — blocks still needed for this request
# δ_node — free pointer slots left in the current direct node
# δ_seg  — free blocks left in the current segment

Crossing a node boundary needs a new node (can't be folded into one range entry); crossing a segment boundary needs a new free segment (same reason). So N is capped by whichever of the two is scarcer. Invalidating old blocks on an overwrite can still be O(N) in the worst case — the obsolete blocks may scatter across several segments — but because they're scattered, the per-segment locks involved rarely collide, so this hasn't shown up as a bottleneck in practice.

5 · What it adds up to

At 40 threads, block-allocation latency drops 62% for 4 KB overwrite (80→30 µs) and 82% for 1 MB append (29→5.3 ms). Append latency falls 1.4× at 4 KB request size and more than 5× at 256 KB and above — the gap widens with request size because that's exactly where per-block lock overhead used to pile up.

Follow the numbers, step by step

Worked examples

Four traces through the paper's own data: the latency shift, the checkpoint trade, the lock-count collapse, and the ablation story.

① Verifying the "83% of latency" claim

Table 1a reports, for 4 KB random write at 40 threads: Pre-process 1.1 µs, Block allocation 80.1 µs, Post-process 15.4 µs, Total 96.7 µs. Does block allocation really round to 83%?

  1. Sum the parts: 1.1 + 80.1 + 15.4 = 96.6 µs — matches the reported 96.7 µs total to within rounding of the individual stage measurements.
  2. Block allocation's share: 80.1 ÷ 96.7 = 0.828 → 82.8%, which the paper rounds to 83%. Checks out.
  3. Compare to 5 threads: there, allocation was 4.0 ÷ 20.9 = 19.1% ≈ 19%. So allocation's share roughly quadrupled (19%→83%) over an 8× increase in thread count, while its absolute cost grew 20× (4.0→80.1 µs) — allocation didn't just grow, it grew much faster than everything else.
🧰
Insight: pre-process and post-process barely move with thread count (they're mostly per-thread, independent work); allocation is the only stage that's shared and lock-bound, so it's the only stage whose cost explodes with concurrency.

② The lock-acquisition collapse for 1 MB append

A 1 MB append is 256 × 4 KB blocks. Table 3 reports vanilla F2FS always uses 256 lock requests per write(), while ScaLog uses 1.3–1.6 regardless of thread count. How big is the improvement?

  1. Vanilla F2FS: one curseg_mutex acquisition per block → 256 acquisitions for one 1 MB write(), at every thread count measured (1 through 10).
  2. ScaLog at low contention (1.3 acquisitions): 256 ÷ 1.3 ≈ 197× fewer lock acquisitions for the identical request.
  3. ScaLog at higher contention (1.6 acquisitions, 8–10 threads): 256 ÷ 1.6 = 160× fewer — still almost two orders of magnitude.
  4. Why it's not exactly 1.0: Multi-block Allocation's N is capped by δ_seg — a 1 MB request occasionally straddles a segment boundary, forcing a second (smaller) acquisition to finish the request. That's the entire source of the 1.3–1.6, not residual per-block contention.
💡
This single number — 160–197× fewer lock acquisitions for an unchanged 1 MB write() — is the mechanical reason the IO-command count and the append latency both collapse in lockstep (Figure 8, Table 3).

③ The checkpoint trade-off, exactly

Table 2 reports bitmap-update and total checkpoint latency at 40 workers, under four configurations. Does deferring the bitmap actually cost something back?

  1. Baseline F2FS checkpoint: 525 ms, with no separate "bitmap update" line — it's always current, so there's nothing to commit.
  2. ScaLog, no optimization (Origin): committing all the accumulated range-list entries costs 833 ms of bitmap update, pushing checkpoint to 1,358 ms. Check: 525 + 833 = 1,358 — matches exactly, confirming the bitmap commit is pure added work on top of F2FS's existing checkpoint.
  3. With both optimizations (Par + Bg): bitmap update falls to 177 ms, checkpoint to 702 ms. Check: 525 + 177 = 702 — matches again.
  4. Net overhead: (702 − 525) ÷ 525 = 33.7% higher — the paper reports this as "35% higher"; our own division lands a couple points lower, likely from rounding in the underlying per-run measurements, but the story is the same either way: a real but modest checkpoint tax.
🧰
Insight: ScaLog doesn't eliminate the bitmap-update cost, it relocates it — off the latency-critical foreground write path and onto the periodic, already-expected checkpoint. A ~34–35% checkpoint tax is a good trade for 1.7–6.1× write throughput, since checkpoints are infrequent and writes are what scales with thread count.

④ Reading the ablation study

The paper isolates each technique's contribution by adding them one at a time: Vanilla → +STx → +STx+RL → +STx+RL+MBA. The two workloads tell different stories — why?

  1. 4 KB random write: STx alone gives +9% over vanilla. Adding RL on top gives a further +65.9% over STx-alone. RL is the dominant contributor here, because an overwrite's "invalidate old block" and "allocate new block" typically land in different segments — exactly what per-segment locking was built to parallelize.
  2. 1 MB append: STx alone gives +167%. RL adds essentially nothing on top. Why: an append's blocks all land in the same current segment — there's only one segment list to contend on, so splitting the bitmap by segment doesn't relieve anything. The contention just moves from the global lock to that one segment's local lock.
  3. MBA closes the rest of the append gap: it cuts 256 lock acquisitions down to 1–2 per contiguous run, reaching the full 6.1× — the technique append actually needed was batching, not finer-grained partitioning.
💡
Insight: no single technique dominates universally — RL wins when concurrent allocations are segment-diverse (overwrites), MBA wins when they're segment-concentrated (sequential appends). The three techniques are complementary precisely because they target different sources of contention.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
Why does the paper focus on Direct IO rather than buffered writes, if both eventually allocate blocks in the log?
Show answer
Buffered writes route through the page cache and a single writeback thread, which can batch and defer many pages' allocations into fewer trips through the log — amortizing the serialization cost. DIO bypasses the page cache entirely: each application thread allocates and issues its own write synchronously, with no writeback thread to absorb the cost. The serialization shows up directly in request latency.Misconception: that buffered and direct writes face the same bottleneck equally. The page cache's batching is precisely what hides this problem for buffered IO — which is also why it had gone comparatively unaddressed.
Problem 2 · medium
Split Transaction leaves a window where the log pointer has advanced but the block bitmap hasn't been updated yet. Is this a crash-consistency bug? Why or why not?
Show answer
Not a bug, because the window is never externally observable. A reader can only locate a block by first reading the file's dnode, and the writer holds the dnode's page lock continuously from before T_log until after T_meta completes — so no other thread can see the intermediate state. And durability is gated by cp_rwsem: a checkpoint (the only point the state is made persistent) can't start until every in-flight write, including both halves, has finished.Misconception: that any gap between two related updates is automatically an inconsistency bug. Correctness depends on whether anything can observe the gap — here, a pre-existing lock (the dnode page lock) already closes that window.
Problem 3 · medium
Why does Multi-block Allocation cap N at min(N_req, δ_node, δ_seg) instead of always batching the entire write request in one acquisition?
Show answer
A single range-list entry represents one contiguous run of blocks inside one segment, referenced through one direct node's pointer slots. Crossing a segment boundary requires switching to a new (free) segment, and crossing a node boundary requires allocating a new node — both are structural changes that can't be folded into the same batch or the same range entry. So N is capped by whichever constraint — free node-pointer slots or free segment blocks — is scarcer at that moment.Misconception: that a lock acquisition can claim unlimited contiguous space. The claim is bounded by what the underlying data structures (nodes, segments) can represent as a single unit, not just by lock-holding time.
Problem 4 · hard
In the ablation study, Per-segment Range Logging (RL) gives a 65.9% gain on top of Split Transaction for 4 KB random write, but almost nothing on top of STx for 1 MB append. Explain the difference.
Show answer
4 KB random write mixes overwrites whose "invalidate the old block" and "allocate the new block" typically fall in different segments — exactly the case RL was built for, since different segments now use different locks and can proceed concurrently. 1 MB append, by contrast, writes sequentially into the same current segment for the whole request; there's only one segment's range list involved, so partitioning the bitmap by segment doesn't relieve any contention — all the append threads still queue on that one segment's lock, just as they would on a global one.Misconception: that finer-grained locking always helps proportionally. It only helps when concurrent operations actually touch different partitions; when they concentrate on one partition (sequential append → one current segment), finer granularity buys nothing.
Problem 5 · medium
ScaLog's checkpoint latency is 702 ms vs. vanilla F2FS's 525 ms (40 workers) — ScaLog is slower at checkpoint time. Is this a flaw in the design?
Show answer
It's a deliberate, bounded trade-off, not an oversight. ScaLog shifts the bitmap-update cost it saved on the write path onto the periodic checkpoint, where it must commit all the accumulated per-segment range-list entries. The paper's parallel + background commit optimizations shrink that added cost from 833 ms (unoptimized) down to 177 ms, for a net ~34–35% checkpoint increase — paid occasionally and off the latency-critical path, in exchange for 1.7–6.1× foreground write throughput that scales with thread count.Misconception: that a technique must win on every single metric to be a good design. The right comparison is where the cost is paid (rare, background checkpoint) against where the benefit accrues (every write, at scale).
Problem 6 · hard
MAX is a multi-log design, yet it fails to scale on the same benchmarks (Figure 2, Figure 6). Why doesn't multiplying logs fix the problem ScaLog targets?
Show answer
MAX removes contention on which log pointer a thread advances, but it still relies on a single global block bitmap (so updates across all logs still serialize there) and still allocates block-at-a-time for DIO writes (so it still pays one lock acquisition per block, and still fragments large requests into scattered, non-contiguous allocations). The paper's Table 1 identifies the bottleneck as the block-allocation critical section itself — its coarseness and its per-block repetition — not the count of logs contending for one pointer. Having more pointers doesn't shrink what's inside each allocation's critical section.Misconception: that log-pointer contention is the whole problem. It's one symptom; the deeper issue is what's bundled into each allocation's critical section and how many times that section runs per request — multi-log designs leave both untouched.
Quick answers

Frequently asked questions

Nine questions newcomers ask most. Tap any to expand.

Q1What's the one-sentence idea of ScaLog?▾
Stop forcing every thread through one fused, block-at-a-time critical section for log allocation: split the log-pointer update from the bitmap update (Split Transaction), localize the bitmap to per-segment range lists (Per-segment Range Logging), and batch multiple blocks per lock acquisition (Multi-block Allocation).
Q2Why can't multi-log approaches like MAX or DeLFS fix this alone?▾
Removing contention on which log pointer a thread uses doesn't automatically fix the allocation path itself. The paper measures this directly for MAX: it still relies on a global block bitmap and still allocates block-at-a-time, so it fails to scale for the same reasons as vanilla F2FS. DeLFS takes a different, concurrent approach (per-core logs) that the paper treats as orthogonal rather than analyzing in this depth — it leaves per-allocation serialization and log fragmentation as open questions there, not demonstrated failures.
Q3Does ScaLog change F2FS's on-disk format?▾
No. All three techniques are purely in-memory bookkeeping changes to how allocation is tracked and batched before it's committed to the existing on-disk block bitmap. The paper reports ~1.3K lines of kernel code added with no on-disk layout changes.
Q4What exactly is stored in a "range" entry?▾
A tuple (offset, length, del, mtime): offset and length identify a contiguous run of LBAs, del marks whether the run is being allocated or invalidated, and mtime records when. One entry can represent many blocks allocated together — the compactness that makes Multi-block Allocation's batches cheap to log.
Q5How is crash consistency preserved without the bitmap always being current?▾
Two existing F2FS mechanisms do the work: the dnode page lock hides the pointer/bitmap gap from any reader, and cp_rwsem ensures a checkpoint — the only point the state must be durable — can't begin until all in-flight writes (and their range-list entries) have completed. ScaLog adds deferred bookkeeping, not a weaker consistency model.
Q6Why was 768 chosen as the background-commit threshold?▾
It's 75% of the per-segment range list's 1,024-entry capacity — empirically set to flush a segment's backlog before it fills, bounding how much any single checkpoint has to absorb while still avoiding overly frequent background commits.
Q7Does Multi-block Allocation help overwrites the same way it helps appends?▾
Less directly. New-block allocation batches cleanly under MBA regardless of write pattern. But invalidating the old blocks of an overwrite can still be O(N) in the worst case, since those obsolete blocks may be scattered across several different segments' range lists. In practice this isn't a bottleneck, because that same scattering makes it unlikely that two threads contend on the same per-segment lock at once.
Q8Is this specific to F2FS, or would it help other log-structured filesystems?▾
The paper implements and evaluates it only in F2FS, but the three techniques target a structural property common to single-log LFS designs: a shared log pointer plus a shared allocation-tracking structure. The paper mentions NOVA only as another design that keeps multiple logs — it doesn't analyze NOVA's allocation path or show it hits the same bottleneck. Whether ScaLog's techniques port over to NOVA or other LFS designs is left as future work.
Q9What did the authors leave for future work?▾
Two open questions: whether these techniques extend to buffered writes (which already partially hide the problem via the page cache), and how much overhead Per-segment Range Logging adds to garbage collection, which the paper's DIO-focused evaluation doesn't measure.

Multi-block Allocation (MBA)Claims N = min(N_req, δ_node, δ_seg) blocks under one lock acquisition instead of one block at a time.
Range entry(offset, length, del, mtime) — a compact record of a contiguous run of blocks allocated or invalidated together.
curseg_mutexF2FS's log-pointer lock; traced to >90% of block-allocation latency at 40 threads on 4 KB DIO writes.
cp_rwsemF2FS's checkpoint reader/writer semaphore; writers hold it shared, checkpoints need it exclusive — what ScaLog's correctness argument leans on.
Supporting terms
LFS / F2FSLog-structured filesystem / the Linux LFS this paper patches. Every write is allocating.
IPU / ext4In-place update; overwrites are non-allocating. Used (journal-disabled) as the paper's ideal, allocation-free baseline.
DIODirect IO — bypasses the page cache; each thread allocates and issues its own writes synchronously.
SegmentF2FS's basic storage unit (a fixed 2 MB / 512 blocks); the granularity at which Per-segment Range Logging partitions locking.
Dnode / direct nodeThe index node holding a file's block pointers; its page lock is what makes Split Transaction's intermediate state invisible.
δ_node / δ_segFree pointer slots left in the current node / free blocks left in the current segment — the two caps on Multi-block Allocation's N.
MAX / DeLFSMulti-log LFS designs (DeLFS: one log per core) that use multiple logs instead of one shared pointer — orthogonal to ScaLog, which targets the allocation mechanism itself.
