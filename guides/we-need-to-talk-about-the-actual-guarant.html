PLOS 2026 · A Field Guide

Your extension can be perfectly safe Rust and still break your system's promises

Rust-based systems isolate kernel subsystems, sandbox serverless functions, and enforce privacy policies by leaning on the compiler. This is the plain-English story of why that lean is shakier than it looks — and one prototype tool that tries to fix it.

📄 "We Need to Talk About the Actual Guarantees of Rust-based Systems" · Tiffany, Agvanian, Song, Szabo, et al., PLOS'26 🎓 Basic ownership/borrowing assumed — primers cover the rest ⏱ ~20 min read
🦀

Rust's compiler only guarantees soundness — every other property your system leans on (encapsulation, frozen references, …) is merely incidental, and sound code is free to break it.

Before you begin

Quick glossary, then the concepts underneath it

1Soundness: Rust's one and only promise▾

Rust's central guarantee is narrow: a valid Rust program never exhibits undefined behavior (no data races, no dangling pointers, no reading uninitialized memory). Code that upholds this is called sound; code that might not is unsound.

That's it. Everything else people associate with "safe Rust" — encapsulation actually holding, references actually staying read-only — is a consequence of the compiler's soundness checks in the safe subset, not a separate promise the language makes.

Now you're ready: the whole paper hinges on the gap between "sound" and "everything a system wanted to also be true."
2Safe blocks, unsafe blocks, and safe interfaces▾

Most Rust is safe: the compiler statically rejects anything that could cause undefined behavior. Inside an unsafe block, the compiler relaxes those checks, and the developer takes over responsibility for soundness — ideally checked with tools like Miri.

Crucially, a function can wrap unsafe code behind a fully safe-looking interface (e.g. Vec::push, a mutex's lock()). From the outside, a safe interface backed by careful unsafe code is indistinguishable from a function with no unsafe code at all.

Now you're ready: this indistinguishability is exactly what lets "safe" application code accidentally invoke unsafe, guarantee-breaking behavior hidden a few calls deep in a library.
3Ownership, borrowing, and "frozen" references▾

Rust's borrow checker enforces aliasing XOR mutability: at any moment, data is either mutably borrowed by exactly one reference, or immutably borrowed by any number of references — never both. So an &T reference should mean "this data will not change while I hold it."

This isn't a separate rule the compiler bolts on for your convenience — it falls out of the borrow checker's soundness rules, but systems then treat "won't change" as something they can build guarantees on top of.

Now you're ready: RedLeaf's entire crash-recovery story depends on exactly this "immutable means frozen" assumption holding for data shared between subsystems.
4Interior mutability: the trapdoor in "frozen" references▾

UnsafeCell is Rust's only sound way to mutate data through a shared, "immutable" reference. Types like RefCell, Mutex, and Cell wrap it to offer controlled, sound mutation — e.g. a mutex mutates data behind an &T using atomics to stay race-free.

This is completely legitimate, idiomatic Rust — RefCell is a standard-library type, not an exotic hack. But it means "I hold an &T" no longer implies "this data is frozen."

Now you're ready: any Rust-based system that assumes immutable references are truly frozen must somehow rule out interior mutability — and most don't fully manage to.
5Encapsulation and private fields▾

A struct's private fields are normally accessible only from inside their defining module — the compiler enforces this directly, no borrow-checker cleverness required. This is how types like Sesame's PCon hide sensitive data behind an API.

But encapsulation only protects against normal field access. Reflection-like tricks — reading memory by its raw layout instead of by name — sidestep it entirely, and Rust doesn't forbid those tricks in sound code.

Now you're ready: a "sound" serialization macro can read a type's bytes directly and never touch its private-field boundary at all.
6What extensible systems ask of extensions▾

Systems like RedLeaf (an OS), Sesame (privacy enforcement), and NetBricks (network functions) let untrusted or semi-trusted extensions — kernel modules, endpoints, packet-processing functions — run inside a shared process, and use Rust instead of virtual machines or containers to isolate them cheaply.

They typically state a scope restriction like "extensions must be safe Rust" or "no unsafe pointer arithmetic," and assume that restriction is enough to keep their invariant intact.

Now you're ready: the paper's central claim is that these restrictions are the wrong shape — too coarse to actually name the property the system needs.
7MIR and call graphs, just enough to follow Sniffer▾

The Rust compiler lowers your code to MIR, a simplified control-flow representation, before generating machine code. A compiler plugin can hook into this stage to inspect every function body.

A call graph records which functions call which others. Building one soundly for Rust requires resolving generics (monomorphization) and trait-object/dynamic dispatch — hence "Monomorphized Call Graph," or MCG.

Now you're ready: Sniffer is essentially "walk the MCG from a few entry points, and flag any path that reaches a dangerous unsafe pattern."
8Why this isn't "just another memory-safety-bug paper"▾

A large body of work (Miri, Kani, RustBelt, Rudra, Verus, …) already targets finding unsoundness — undefined behavior hiding in unsafe code. This paper is explicitly not about that.

Its examples are fully sound — the Sesame leak, for instance, was confirmed sound with Miri — and often don't even use raw unsafe pointers directly — a standard-library RefCell or an ordinary serialization macro suffices. The bug lives one level up, in properties the system needed that Rust simply never promised.

Now you're ready: you can fix every memory-safety bug you'll ever find and still ship the vulnerabilities this paper describes.
The whole story in one place

The gap between what Rust promises and what systems assume

A mismatch that's neither a Rust bug nor purely a systems bug — it's a gap between the two.

Rust-based systems research has built kernels, sandboxes, and privacy enforcers that skip heavyweight isolation (VMs, containers) and instead lean on the Rust compiler. They work by defining a system invariant — e.g. "a subsystem can't modify data it only holds an immutable reference to" (RedLeaf), or "application code can never directly touch a policy container's fields" (Sesame) — and hoping that invariant holds over all extension code, because the compiler seems to enforce something like it.

The paper names the flaw precisely. Safe Rust code upholds two different kinds of things: soundness (no undefined behavior — Rust's actual, universal promise) and incidental properties like encapsulation, "lifetimes as aliases," and immutability of references — things the compiler happens to enforce in the safe subset, but is under no obligation to preserve in unsafe code, as long as that code stays sound. And unsafe is everywhere: more than half of the 500 most-used Rust crates invoke unsafe code even excluding the standard library.

So a "locally safe" extension — one that bans unsafe only in its own top-level code, a common and reasonable-sounding rule — can still call into a sound, idiomatic dependency that breaks the exact incidental property the system needed. The paper demonstrates this concretely: a Sesame extension leaks PCon-protected data through an ordinary serialization macro, and a RedLeaf kernel subsystem corrupts shared state through a plain RefCell.

🦀 Key takeaways

  • Rust promises soundness universally; it promises incidental properties (encapsulation, frozen refs, lifetime-as-alias) only inside fully safe code.
  • Sound, idiomatic unsafe code (mutexes, RefCell, reflection-style serialization) can violate incidental properties on purpose, for good reasons.
  • Globally safe extensions (no unsafe anywhere in the dependency tree) are safe by construction but vanishingly rare in practice.
  • Locally safe extensions (unsafe banned only at the top level) are what real systems use — and are demonstrably too brittle.
  • The fix isn't banning unsafe or ignoring it; it's naming the specific incidental property a system needs and auditing code against exactly that, not against "unsafe" as a monolith.
  • A prototype tool, Sniffer, does this via targeted static analysis and cuts a 33,735-region manual audit down to 12, catching the confirmed violations in its two evaluated case studies (the Sesame leak and RedLeaf's RefCell excerpts).
🧭
For tiering/CXL work: if you've built (or plan to build) a Rust daemon that isolates untrusted hot/cold-classification plugins from kernel or shared-state metadata — say, a CXL memory-tiering policy engine that promises plugins "read-only access to page-access-frequency tables" — this paper's warning applies directly: a plugin that idiomatically reaches for a RefCell or a reflection-style serializer can silently corrupt that "read-only" table, exactly like RedLeaf's scheduler.
Six everyday pictures

How to think about incidental properties

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core mismatch · Encapsulation

A locked diary with a photocopier down the hall

The diary's lock (private fields) keeps casual readers out. But a photocopier reproduces the pages without ever touching the lock. That's mem::transmute inside a serialization macro: it copies a PCon's bytes by memory layout, never calling a getter, so encapsulation's "no direct access" rule is never technically broken — it's simply routed around.

Where it breaks: the photocopier operator here isn't a snoop — it's a well-meaning serde helper the developer wrote to work around a third-party type lacking a Serialize impl. Nobody intended a leak.
Interior mutability · Immutability of references

A library book with a hidden erasable page

The cover says "reference copy — do not write in this." Nearly every page truly is frozen. But bound inside is one page made of whiteboard material (a RefCell/UnsafeCell): anyone holding the "read-only" book can erase and rewrite it, soundly, on purpose. RedLeaf's scheduler subsystem holds exactly this kind of book for shared thread metadata.

Where it breaks: whiteboard pages are genuinely useful — mutexes and caches need them. The problem isn't that they exist, it's that RedLeaf's rules for what may go on its shared heap don't exclude books containing one.
The tool's precision · Invariant-targeted search

A metal detector tuned to one item, not everything

A generic security wand beeps at every belt buckle and coin (every unsafe block: 33,735 of them here). A detector tuned to a specific forbidden item — say, only things reachable from a specific bag (PCon) — ignores the coins entirely and flags almost nothing: 12 call chains. That's Sniffer's invariant-targeting, versus a plain unsafe-block count.

Where it breaks: the detector doesn't prove nothing bad is happening — it can still misfire on a harmless bag shape (a false positive, like Sniffer's over-approximated dynamic-dispatch flags). A human still checks each beep.
Locally vs. globally safe · Supply chain

Checking the front door, not the delivery truck

A "no unsafe code in the extension" rule is a bouncer at the front door — thorough, but only for people walking in directly. It says nothing about what arrives by delivery truck (the dependency tree), and in Rust, the truck is where most unsafe code actually lives: over half of the top 500 crates call unsafe even excluding the standard library.

Where it breaks: the truck isn't full of contraband — it's carrying std, serde, and other widely-trusted cargo. The issue isn't trust, it's that even trusted cargo has no obligation to preserve incidental properties it's never heard of.
The limits of type-level fixes · Freeze

A nutrition label for an unopened box

The Freeze marker trait is like refusing to stock any box whose label lists an allergen — even if a specific box, opened, turns out to contain none. It bans every type containing an UnsafeCell outright, even a doubly-linked list a subsystem receives but never mutates.

Where it breaks: real safety sometimes needs behavior-level, not label-level, scrutiny — a system that wants "no interior mutation of this specific data" ends up refusing entire useful, harmless data structures under Freeze.
Three-way classification · Property preservation

A traffic light with a hidden middle setting

You'd expect two states: red (unsound, dangerous) and green (safe, fine). Rust's unsafe code actually has three: red (undefined behavior), a rarely-discussed amber (sound — no crashes — but it violates the property your system cares about), and green (sound and property-preserving). Systems that only check for red miss the amber cars entirely.

Where it breaks: which unsafe patterns count as "amber" depends on which property you're asking about — transmute is amber for encapsulation but green for immutability of references, and vice versa for UnsafeCell::get.
The full explanation

How the mismatch bites, and how Sniffer catches it

From the three-way classification, through two real leaks, to the static-analysis pipeline that flags them.

1 · Classifying code by property preservation

For any single incidental property (say, encapsulation), a piece of Rust code falls into exactly one bucket:

ClassUndefined behavior?Preserves the property?Example
UnsoundPossiblyN/A — no guarantees at alla buggy raw-pointer cast
Sound, not preservingNoNo — violates it on purposetransmute reading a PCon's bytes
Property-preservingNoYesa getter, or all safe code
💡
Why this matters: a system doesn't need to ban all unsafe code — it needs to rule out only the middle row, and only for the specific property and specific data it depends on. RedLeaf's shared-heap data must avoid immutability violations; its subsystems' purely local data need not.

2 · Case study — Sesame's PCon leak, step by step

An application developer wants to log a SubmitForm struct for debugging. One field, answer, is a PCon<String, NoLoggingPolicy> — deliberately unloggable. SubmitForm itself is annotated #[derive(Serialize)], but that derive can't reach into PCon's private fields to serialize them directly. A helper macro, serialize_any, built on serde's "remote type" feature, solves the developer's problem generically — using mem::transmute to read any type's bytes regardless of field visibility.

3 · Case study — RedLeaf's scheduler corrupts kernel state

RedLeaf lets subsystems share data via a special heap, restricted by an auto trait called RRefable that forbids raw pointers. A pluggable scheduler subsystem receives thread metadata as an immutable reference on that heap — but the metadata is wrapped in a RefCell so the base kernel can also update it. RRefable says nothing about RefCell.

Kernel
Owns thread queue; shares it as &RefCell<ThreadMeta> on the shared heap (RRefable-checked)
→
Scheduler subsystem
Calls borrow_mut() → UnsafeCell::get(), interior-mutates the queue — perfectly sound
→
Scheduler crashes
Kernel can only roll back data the scheduler owned — this mutation wasn't ownership, so it's invisible to recovery
⚠
Concrete failure: if the crash happens right after the scheduler dequeues a thread's metadata via interior mutation, that thread's metadata is permanently lost — the kernel's crash-recovery invariant is broken, using nothing but a standard-library RefCell.

4 · Sniffer's pipeline

Sniffer is a MIR-level compiler plugin. System developers specify an invariant as (a) an incidental property and (b) optionally, the specific types/entry points it applies to. Extension developers then run it over their code and dependency tree:

# 1. Build a Monomorphized Call Graph (MCG)
for each fn in extension + dependencies:
    resolve generics, soundly over-approximate dyn dispatch / fn pointers

# 2. Walk reachable function bodies from annotated entry points
for each reachable fn body (as MIR):
    visitor scans for property-violating patterns
    e.g. transmute, ptr arithmetic → encapsulation
    e.g. UnsafeCell::get/raw_get → immutability of refs

# 3. Filter using argument types (system-specific context)
if flagged_call's argument type == PCon<...>:
    report call chain           # else: likely benign, still shown for review

Sniffer is sound for this task: any reachable code that genuinely violates the property is guaranteed to be flagged (thanks to the over-approximated call graph). Its cost is false positives — from dynamic-dispatch over-approximation, or from heuristic patterns like a transmute that happens not to touch protected data.

Threat modelWho checks the extensionPrecision neededFits

🧭
A CXL/tiering daemon that loads plugins written by a small internal team (cooperative) can ship a Sniffer-style build check; one that accepts tenant-submitted policy code (adversarial) would need Sniffer paired with a runtime or formal-methods backstop — the paper discusses hardware isolation such as Intel MPK as one possible fallback, not its endorsed default.
Follow the numbers

Worked examples

The paper's own evaluation numbers, carried through the arithmetic.

① From 33,735 unsafe blocks down to 12 flagged calls

Applying three progressively targeted audit strategies to Sesame's WebSubmit endpoint (plus its full dependency tree):

  1. Syntactic scan — flag every unsafe block anywhere in the code or its dependencies: 33,735 regions. Most of this isn't reachable from the endpoint at all — the next step narrows it down.
  2. Reachability-only — keep only unsafe blocks actually callable from the endpoint: 9,982 regions, a 70.4% cut ((33,735 − 9,982) / 33,735).
  3. Sniffer's invariant-targeting — keep only flows from a PCon argument into transmute or pointer arithmetic: 12 regions — a 99.88% cut from the reachability-only count, 99.96% from the syntactic count.
  4. Of those 12: 1 is the genuine leak (the serialize_any transmute); 11 are false positives — 5 from pointer-arithmetic iterators over Vec<PCon> that never actually exfiltrate data, 6 from Sniffer's dynamic-dispatch over-approximation.
🦀
Insight: a developer reviewing 12 call chains (with a genuine hit rate of 1-in-12 ≈ 8.3%) finds the leak; a developer facing 33,735 or 9,982 undifferentiated unsafe blocks realistically never does.

② How Sniffer compares to an existing audit tool

cargo-scan, an existing crate-auditing tool, is applied to each of Sesame's dependencies individually.

  1. cargo-scan (per-dependency) reports 43,761 items to audit — a different kind of audit unit (risky effects per crate) than Sniffer's call chains, and more than even the raw syntactic unsafe count, since analyzing each crate in isolation forgoes whole-program reachability information.
  2. Roughly, that's ~3,647× more items than Sniffer's 12 — though the paper treats this as illustrative rather than a strict apples-to-apples reduction factor, since the two tools count different things.
  3. cargo-scan's "cross-package" mode, which does build a whole-program call graph, struggles to resolve trait implementations and dynamic dispatch across crate boundaries — the paper notes this mode is not meaningfully compared to Sniffer, rather than reporting a direct count against it.
💡
The gain isn't from a smarter unsafe-pattern list — it's from combining whole-program, sound reachability with invariant-specific filtering. Either alone (reachability-only: 9,982; per-crate effects-only: 43,761) leaves an unreviewable pile.

③ RedLeaf: the same technique, a different property

Because the RedLeaf codebase doesn't compile with Sniffer's supported compiler version, the authors extract small, compatible excerpts of the scheduler case study.

  1. Direct and nested RefCell — a RefCell placed directly on the shared heap, and one nested inside another struct, both mutated inline.
  2. Transitive mutation — a RefCell mutated via a helper function several calls removed from the entry point.
  3. Collection storage — a RefCell stored into and retrieved from a collection before being mutated.
  4. Result: Sniffer flags each of these scenarios as reaching UnsafeCell::get via RefCell::borrow_mut, with zero false positives on these excerpts — though the authors note the excerpts don't capture a full subsystem's complexity.
🦀
Insight: the same MCG-plus-pattern-matching machinery generalizes across incidental properties — encapsulation for Sesame, immutability of references for RedLeaf — just by swapping the flagged pattern (transmute/pointer arithmetic vs. UnsafeCell::get/raw_get).

④ What static detection buys you over a runtime tax

Before this analysis existed, Sesame's own mitigation for this exact leak class was a runtime trick: obfuscating PCon's internal pointer by XOR-ing it with a private constant.

  1. Cost: the obfuscated-pointer scheme adds a measured 2× overhead in Sesame's microbenchmarks.
  2. Coverage gap: it still doesn't stop every guarantee-breaking pattern — e.g. code that swaps a PCon's policy for a more permissive one entirely bypasses pointer obfuscation.
  3. Sniffer's alternative: a compile-time/audit-time check with zero runtime cost, flagging the 12 call chains once per build rather than paying 2× on every access.
🧭
This is the same trade-off a memory-tiering system faces when deciding between a runtime guard on every hot-path page access versus a static audit of the tiering-policy plugin at load time — the latter is strictly cheaper if it can be made sound enough for your threat model.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A dependency uses unsafe internally and has been verified sound with Miri. Does that mean a RedLeaf subsystem using it can't break RedLeaf's isolation guarantee?
Show answer
No. Soundness only rules out undefined behavior — it says nothing about whether the code preserves immutability of references, the specific incidental property RedLeaf depends on. A sound RefCell-based helper can still let a subsystem mutate data it only holds an immutable reference to.Misconception: that "sound" and "preserves my system's invariant" are the same claim. They're independent axes (Fig. 1) — you must check both.
Problem 2 · easy
Sesame's WebSubmit application itself contains zero unsafe keywords. Is it globally safe?
Show answer
No — it's locally safe. The leak in Figure 2 lives inside a dependency (a serde-remote-based logging macro), not in the application's own code. Globally safe would require the entire dependency tree to be free of unsafe, which the paper notes is empirically rare (over half of the top 500 crates use it, excluding std).Misconception: that banning unsafe at the top level of an extension is equivalent to banning it everywhere it could matter.
Problem 3 · medium
Sniffer flags 12 call chains for Sesame's endpoint, and cargo-scan (run per-dependency) flags 43,761 items — more than even the raw syntactic unsafe-block count of 33,735 for the whole app. How can auditing individual dependencies produce a bigger number than counting every unsafe block in the entire application?
Show answer
Per-dependency analysis has no whole-program reachability information: it counts every risky "effect" (unsafe operations, syscalls, etc.) inside each crate in isolation, including code the application never actually calls. The syntactic 33,735 count, by contrast, is still scoped to the app's actual dependency tree as built, and Sniffer's 12 additionally restricts to code reachable from one real entry point and one real property.Misconception: that a bigger scanned number always means a more thorough dependency tree — it more often means less pruning, not more coverage.
Problem 4 · medium
RedLeaf's RRefable auto trait already forbids sharing raw pointers on the shared heap. Why doesn't that stop the scheduler's isolation violation?
Show answer
RRefable blocks one specific unsafe primitive (raw pointers) but says nothing about interior-mutable types like RefCell/UnsafeCell. A struct wrapped in RefCell passes the RRefable check just fine while still allowing sound mutation through what the kernel believes is a frozen reference.Misconception: that an auto trait which restricts *some* unsafe primitives automatically rules out *all* violations of the property the system cares about.
Problem 5 · hard
Could Sniffer eliminate all 11 false positives in the Sesame case by building a more precise call graph?
Show answer
Only partially, and at a cost. Six of the false positives come from over-approximating dynamic dispatch — Sniffer must assume a dyn call could resolve to any type with a matching signature, or it risks missing a real violation (an unsound false negative). Tightening that approximation to eliminate false positives would risk exactly the outcome the tool exists to prevent. The other 5 (pointer arithmetic over Vec<PCon>) are inherent to the heuristic nature of the per-property patterns and need type/argument-level filtering (system-specific context) rather than a better call graph.Misconception: that a static analysis tool's false positives are simply a quality bug to be engineered away. Here, some are the deliberate, necessary cost of staying sound (no missed violations).
Problem 6 · hard
The Freeze marker trait forbids any type containing an UnsafeCell from crossing a trait bound — even a doubly-linked list a subsystem never actually mutates after receiving it. Why does the paper call this "restricting types, rather than behavior"?
Show answer
Freeze is checked once, at the type level, independent of what the code actually does at runtime. A type either contains an UnsafeCell somewhere in its structure, or it doesn't — Freeze can't see that a particular piece of code merely stores and forwards such a value without ever calling borrow_mut or get. So it over-restricts: it rejects harmless uses along with the genuinely dangerous ones, motivating tools like Sniffer that look at actual call chains (behavior) instead.Misconception: that a marker trait restricting a type is the same guarantee as restricting the operations that type's data is actually subjected to.
Problem 7 · medium
Sesame's runtime mitigation (XOR-obfuscating a PCon's pointer) costs 2× overhead and still misses policy-swap attacks. Sniffer flags the equivalent leak at zero runtime cost. Does this mean Sniffer makes the runtime mitigation obsolete?
Show answer
Not entirely — it depends on the threat model. Sniffer suits the cooperative model, where a human audits flagged code before shipping. For adversarial extensions (untrusted code the system must check before ever running it), a static audit alone may not give the "near-perfect precision" that model demands, so the paper suggests combining Sniffer's targeting with a runtime backstop (e.g. hardware isolation) rather than replacing it outright.Misconception: that a cheaper static check always replaces a runtime one. The right mix depends on whether extension developers are cooperative or adversarial.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the difference between "unsafe" and "unsound"?▾
Unsafe is syntactic — code inside an unsafe block or invoking an unsafe fn. Unsound is semantic — code that may actually exhibit undefined behavior. Most unsafe code in practice is sound (carefully written and often Miri-checked); this paper is specifically about sound unsafe code that still breaks a system's needs.
Q2Isn't finding bugs in unsafe code already solved by Miri, Kani, RustBelt, etc.?▾
Those tools target soundness — undefined behavior. This paper's case studies are fully sound (the authors verified the Sesame example with Miri) and still break their systems' guarantees. The gap is orthogonal to the one those tools close.
Q3Why can't systems just forbid all unsafe code in extensions and their dependencies?▾
That's "globally safe" code, and it's technically sound — but nearly unusable in practice. A 2020 study found the majority of the 500 most-used Rust crates call unsafe code even excluding the standard library, so banning it everywhere would rule out most of the Rust ecosystem, including std collections and common serialization/logging libraries.
Q4What exactly is an "incidental property"?▾
A property upheld by all fully safe Rust code, but whose violation does not cause undefined behavior. The paper's three examples: encapsulation, lifetimes as reliable aliases, and immutability of references. They're "incidental" because the compiler enforces them as a side effect of enforcing soundness in the safe subset — not because Rust separately promises them.
Q5How is Sniffer different from just grepping for "unsafe" or counting unsafe blocks?▾
A syntactic count treats every unsafe block as equally suspicious (33,735 for Sesame's WebSubmit app) regardless of whether it's reachable or relevant. Sniffer builds a sound call graph, keeps only code reachable from real entry points, and further keeps only flows into patterns that violate the specific property and type the system named — cutting the same case down to 12 regions.
Q6Does Sniffer prove an extension is safe, or just flag things to review?▾
It flags candidates for review — it's a targeted auditing tool, not a proof system. It's sound in the sense that it won't miss a reachable violation, but a flagged call chain still needs a human (or, per the paper's future-work discussion, a formal method like Verus) to confirm it's a real problem versus a false positive.
Q7What's the difference between cooperative and adversarial extensions?▾
Cooperative: the extension developer is trusted to run the checks and audit the output honestly (Sesame, RedLeaf, Rex). Adversarial: the system itself must verify untrusted code before loading it, with no human in the loop, demanding near-perfect precision (NetBricks, Boucher et al.'s serverless isolation). Sniffer as presented targets the cooperative model.
Q8Why does Sniffer sometimes flag benign code — is that a design flaw?▾
Partly by necessity: Sniffer must soundly over-approximate dynamic dispatch (a dyn call could resolve to anything with a matching signature) to guarantee it never misses a real violation, and that over-approximation produces some false positives. The rest come from heuristic per-property patterns that don't yet track fine-grained data flow.
Q9Is this only relevant to OS kernels like RedLeaf?▾
No — the paper documents the same class of problem in Sesame (web privacy enforcement), NetBricks and Boucher et al. (network/serverless function isolation), Cocoon and Flowistry (information flow analysis/control), and Rex (an eBPF alternative). Figure 3 lists confirmed violations across all seven systems.
Q10What would it take to use an approach like Sniffer in a new Rust-based system?▾
Name your invariant as a combination of an incidental property (encapsulation, immutability of references, lifetimes as aliases) and, ideally, the specific types/entry points it applies to — rather than a blanket "no unsafe" rule. The paper frames this as building toward a reusable "library" of properties mapped to their violating unsafe patterns, since many systems lean on the same handful of properties.
Q11Why doesn't RedLeaf's RRefable trait already solve this?▾
RRefable restricts which types may be placed on the shared heap by forbidding raw pointers — but it doesn't exclude interior-mutable types like RefCell, so it protects against one class of violation (via raw pointers) while leaving another (via interior mutability) wide open.
Q12What's next for this line of work?▾
The paper points to richer annotations (variables, specific trait impls, not just types/top-level functions), integrating variable-level information flow analysis, combining Sniffer with formal methods (turning flagged regions into local proof obligations for tools like Verus) and runtime mechanisms (hardware isolation as a fallback for flows Sniffer can't dismiss statically), and extending the idea beyond incidental properties to other assumed invariants, like panic freedom.

Incidental propertyA property (e.g. encapsulation) upheld by all safe Rust code, whose violation causes no undefined behavior — so sound unsafe code is free to break it.
EncapsulationPrivate struct fields are accessible only within their defining module. One of the paper's three example incidental properties.
Immutability of referencesData reachable through an &'a T should never mutate during lifetime 'a. Follows from the borrow checker's aliasing-XOR-mutability rule.
Lifetimes as aliasesAliases of an &'a T reference can be soundly approximated using its lifetime 'a — an incidental property that tools like Flowistry rely on for information-flow analysis.
Globally safeAn extension containing no unsafe code anywhere in its dependency tree. Guarantees all incidental properties, but is empirically rare in practice.
Locally safeAn extension whose top-level code avoids unsafe, but whose dependencies may still contain it. What most real Rust-based systems actually enforce — and, the paper shows, too brittle.
SnifferThe paper's prototype: a MIR-level compiler plugin that builds a call graph and flags reachable, invariant-violating unsafe patterns for targeted human audit.
Supporting terms
PCon<T,P>Sesame's policy container: private fields hold sensitive data (T) and its policy (P); relies on encapsulation to stay protected.
RRefableRedLeaf's auto trait restricting shared-heap types by forbidding raw pointers — but not interior-mutable types.
UnsafeCellRust's sole sound primitive for mutating data behind a shared reference; underlies RefCell, Mutex, and Cell.
MIRMid-level Intermediate Representation — the compiler stage Sniffer's plugin analyzes function bodies at.
MCGMonomorphized Call Graph — Sniffer's soundly over-approximated map of reachable functions, including through generics and dynamic dispatch.
FreezeAn unstable marker trait implemented only for types without UnsafeCell; restricts types, not behavior.
Cooperative / adversarial extensionsTwo threat models: trusted developers who self-audit vs. untrusted code the system must verify unaided before running.
Property preservationThe three-way classification of code relative to one property: unsound, sound-but-not-preserving, or property-preserving.
