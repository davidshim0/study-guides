SOSP 2026 · A Field Guide

One kitchen that can bake every recipe, under any house rules

Secure multiparty computation lets distrusting parties compute on secret data together. Today that means one specialized system per workload, per threat model. This is the plain-English story of CryptDough, the system that unifies them.

Quick glossary — up front

The acronyms you'll see everywhere

Defined once here so the rest of the guide can use them freely.

MPCSecure Multiparty Computation: several parties jointly compute a function on their private inputs, learning only the result.
ABYA semi-honest, 2-party, dishonest-majority MPC protocol (Demmler et al.) — one of CryptDough's four supported protocols.
ABY3A semi-honest, 3-party, honest-majority protocol using replicated secret sharing (Mohassel & Rindal).
F4 (Fantastic Four)A malicious-secure, 4-party, honest-majority protocol — strong active-security guarantees at lower cost than dishonest-majority protocols, bought by assuming a majority of the four parties behave honestly.
SPDZ2kA malicious-secure, dishonest-majority protocol — the most expensive but strongest guarantee CryptDough supports.
RTTRound-Trip Time: the network latency between two parties. Dominates cost in WAN deployments.
CTCommunication Thread: a dedicated thread that ships messages between parties so compute threads never block on the network directly.
EVector / SharedVectorEVector: a multi-vector container for a protocol's internal shares. SharedVector: the user-facing secret-shared vector built on top of it.
TCBTrusted Computing Base: the code that must be correct for security to hold — here, all of CryptDough's implementation.
DSLDomain-Specific Language: CryptDough's declarative, Spark/Flink-like interface for data analysts.
Before you begin

Nine ideas the paper assumes you know

Collapsed by default — open any that look unfamiliar, or read top to bottom.

CryptDough (the unified engine) mixed workload / pipeline protocol / crypto machinery specialized single-workload silo
1Secret sharing: how a value hides in plain sight▾

A data owner splits a private value s into random shares s1, s2, …, sm that individually reveal nothing, but together reconstruct s. Arithmetic sharing: shares sum to s mod 2^ℓ. Boolean sharing: shares XOR to s.

Local operations (adding two arithmetic shares, XORing two boolean shares) need no communication. Multiplying shares (or ANDing them) does — that's where the network cost lives.

Now you're ready: CryptDough's ASharedVector and BSharedVector are just typed containers for arithmetic and boolean shares, respectively.
2Threat models: who might cheat, and how many▾

Semi-honest parties follow the protocol but might passively peek at what they see. Malicious parties can actively deviate — corrupt shares, lie about results. Separately, an adversary controlling fewer than half the parties is an honest-majority setting; controlling half or more is dishonest-majority, which is strictly harder (and slower) to defend against.

These two axes cross to give four combinations, and CryptDough supports one protocol native to each: ABY (semi-honest / dishonest-majority), ABY3 (semi-honest / honest-majority), Fantastic Four (malicious / honest-majority), SPDZ2k (malicious / dishonest-majority).

Now you're ready: "supporting the full threat spectrum" means literally covering all four quadrants, not just picking the popular one.
3Oblivious control flow — no branching on secrets▾

If code branches on a secret value (if (secret_x > 0) …), the pattern of which branch executes leaks information about secret_x through timing or access patterns. Oblivious programs avoid this: every input of the same size runs the exact same sequence of operations.

A secret-dependent choice is instead expressed with a multiplexer: compute both branches, then select the right result using a secret comparison bit — extra work, but leaks nothing.

Now you're ready: CryptDough's operators (filter, join, ReLU) are all built this way — they don't skip work, they select among results already computed.
4Why communication rounds are the real bottleneck▾

Local computation on shares is fast — nanoseconds. Every secure multiplication or comparison, though, needs at least one round of message exchange between parties, and each round pays the full network round-trip time. In a WAN with tens of milliseconds of RTT, a program that needs a thousand sequential rounds can be far slower than one that needs ten, even if both send the same total bytes.

Now you're ready: this is precisely analogous to a program dominated by round trips to a remote memory tier — the fix in both worlds is the same: batch many small requests into fewer round trips.
5Vectorization: batching, not just SIMD▾

In plaintext systems, "vectorized" usually means SIMD instructions. In MPC, it means something more consequential: applying an operation to n elements at once lets all n local computations run first, so the messages for all n elements are batched together per round. That collapses what would otherwise be up to n sequential rounds down to however many rounds the underlying comparison actually needs — for the paper's compare-and-swap example, O(log|T|) rounds total, not one round per element and not necessarily a single round overall.

Now you're ready: this is the single biggest performance lever in the paper — vectorized code and non-vectorized code can send identical bytes but differ by orders of magnitude in round count.
6Beaver triples — precomputed randomness for cheap multiplication▾

Securely multiplying two shared values needs interaction. A Beaver triple is a precomputed, secret-shared triple (a, b, c) with c = a×b, generated ahead of time (the "offline phase"). During the real ("online") computation, parties mask their inputs with a and b, reveal only the masked values, and recover the product locally — the randomness cancels out algebraically, revealing nothing about the real inputs.

Now you're ready: Worked Example ① walks through the exact arithmetic with real numbers.
7Layered software, à la kernel/driver interfaces▾

An OS kernel defines a fixed interface (read, write, ioctl) that any device driver implements; filesystems above never need to know which driver is underneath. CryptDough applies the same idea to MPC: a fixed, small interface of low-level functionalities (secure add, multiply, XOR, AND) that any protocol implements, so everything built above never needs to know which protocol is underneath.

Now you're ready: this is the entire architectural bet of the paper — get that interface right, and analytics and cryptography evolve independently.
8Why mixed pipelines are hard to compose from specialized systems▾

Even two systems that support the same threat model often use different secret-sharing schemes or data encodings internally. Passing output from one into the other requires understanding and writing custom cryptographic conversion code — not just a file format change.

Now you're ready: "stitching together ORQ + TVA + Pigeon" isn't a scripting problem, it's a cryptographic-interoperability problem — which is exactly the gap CryptDough closes by keeping everything inside one runtime.
9What "outsourced MPC" deployment looks like▾

Real deployments are small: a handful of untrusted computing parties (often run by different infrastructure providers), fed secret shares by many data holders, producing output for designated output parties. Because MPC's communication cost scales with party count, deployments rarely go beyond 2–4 parties.

Now you're ready: when the paper says "party," picture one server process, not one end user — an important distinction the evaluation numbers rely on.
The whole story in one place

CryptDough in a nutshell

The problem, the layered fix, and how the pieces click together.

Real MPC deployments need mixed pipelines: an ML classification feeding a relational join, feeding a time-series aggregation. But today's MPC systems are each built for exactly one workload — ORQ for relational, TVA for time series, Pigeon/Piranha for ML inference — and each is usually wedded to one threat model too. Combining them means writing custom cryptographic glue code to convert between incompatible secret-sharing schemes, plus manual orchestration of separate runtimes. For one motivating pipeline in the paper, doing this by hand versus using CryptDough is the difference between brittle integration engineering and a single ~60-line program.

CryptDough's fix is a strict four-layer hierarchy — Low-level MPC Functionalities → Oblivious Primitives → High-level Operators → Operator Composition — where every layer above the bottom is protocol-agnostic and treats the layer below as a black box. An applied cryptographer implements a short, fixed interface (secure add, multiply, XOR, AND, share creation/opening) once per protocol; a library developer builds analytics operators (join, window, convolution) once, on top of that interface, for every protocol at once. Add a new protocol, and every existing analytics library instantly runs under its threat model, with zero changes.

The second contribution, virtual vectors, solves a subtler problem: high-level operators (sorting networks, prefix-sum patterns) need irregular, non-contiguous access into vectors — code a library developer would otherwise have to hand-parallelize themselves. A virtual vector is a declared index-mapping view W[i] = V[f(i)] onto a base vector; the runtime partitions and distributes it exactly like a real vector, with zero data copies, so developers write single-threaded-looking code and get automatic parallelization for free.

The payoff: across relational, time-series, and ML-inference workloads and all four threat models, CryptDough is competitive with — and often faster than — specialized point systems: ~1.5× over ORQ, up to 2.7× over TVA, up to 2.2× over GPU-based Piranha (single-threaded!), and up to 4.7× over the general-purpose MP-SPDZ compiler in WAN.

🥐 Key takeaways

  • Specialized MPC systems each cover one workload and usually one threat model — combining them means writing custom cryptographic glue code.
  • CryptDough's four layers are protocol-agnostic above the bottom, so protocols and analytics libraries evolve independently and compose automatically.
  • Virtual vectors (W[i]=V[f(i)]) let irregular access patterns reuse vectorized primitives without data copies, with automatic parallelization.
  • Vectorized code turns O(n·log|T|) communication rounds into O(log|T|), independent of input size — without changing total bytes sent.
  • Four protocols cover all four threat-model quadrants: semi-honest/malicious × honest-majority/dishonest-majority.
  • Result: ~1.5× over ORQ, up to 2.7× over TVA, up to 4.7× over MP-SPDZ (WAN), competitive-to-faster than GPU-based Piranha — and a typical query is still only ~800 lines of code even with CryptDough's vectorized API, versus roughly 2× that written by hand without the abstractions.
Seven everyday pictures

How to think about CryptDough

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · One kitchen

A shared kitchen, many recipes

Three chefs each built their own kitchen: one only bakes bread (relational), one only makes soup (time series), one only fries (ML inference) — and each kitchen uses different, incompatible cookware. CryptDough is one kitchen with shared pots and pans (the vector abstractions) that any recipe can use, and a shared set of food-safety rules (oblivious control flow) every dish must follow.

Where it breaks: real kitchens let a chef improvise mid-recipe. CryptDough's recipes can't branch on secret ingredients — every dish follows the same steps regardless of what's inside (Primer 3).
The layer boundary · Interfaces

A kernel's device-driver socket

An OS kernel exposes one fixed socket — read, write, ioctl — that any storage driver plugs into; a filesystem above never has to know which driver it's talking to. CryptDough's protocol interface (secure add, multiply, XOR, AND) is that same socket for cryptography: an applied cryptographer plugs in ABY, ABY3, F4, or SPDZ2k underneath, and every analytics operator above runs unmodified.

Where it breaks: device drivers all present roughly equal semantics. MPC protocols differ wildly in cost and security strength — the socket hides the mechanism, but never hides the price.
Virtual vectors · Index translation

A page table for vectors

Virtual memory lets a program use clean, contiguous addresses while a page table quietly translates them to scattered physical pages — no copying required. A virtual vector does the same for MPC arrays: W[i] = V[f(i)] lets you declare "every third element starting at offset 3" and hand it straight to a vectorized primitive, while the runtime resolves real indices analytically, with zero data movement.

Where it breaks: page tables handle arbitrary, dynamic mappings. Virtual vectors only work because oblivious programs are deterministic — the mapping f is fixed at compile time, never dependent on secret data.
Beaver triples · Preprocessing

Prepping mise en place before service

A restaurant chops vegetables and reduces stocks hours before dinner service, so the actual cooking during the rush is just fast assembly. Beaver triples are the MPC version: random correlated values (a, b, c=a×b) get generated ahead of time (offline), so the real, latency-sensitive multiplication during the "online" computation is just an interactive reveal step plus one local formula.

Where it breaks: mise en place is reusable across dishes. Each Beaver triple is consumed exactly once — reusing one leaks information, so the offline phase must keep pace with online demand.
Execution model · Mini-clusters

Sharding across NUMA-like lanes

A NUMA-aware job splits work into independent lanes that mostly compute locally and only synchronize at checkpoints, minimizing cross-node chatter. CryptDough's worker threads form mini-clusters across parties — pairs (or larger groups) of threads that own separate data partitions, run mostly independently, and synchronize with their remote partners only at the boundary between primitives.

Where it breaks: NUMA lanes stay on one machine. Mini-cluster partners live on different physical machines, so their "synchronization" is a full network round trip, not a cheap interconnect hop.
Vectorization · Coalesced round trips

One burst transfer, not many small fetches

Fetching a thousand scattered bytes one at a time from a remote memory tier is dominated by round-trip latency, not bandwidth; coalescing them into one burst transfer amortizes that latency across all thousand. Vectorized MPC does something similar: for the paper's compare-and-swap example, a thousand element-wise comparisons collapse from O(n·log|T|) sequential rounds down to O(log|T|) batched rounds — same bytes, far fewer round trips.

Where it breaks: a memory burst transfer is bounded by physical bus width. A vectorized MPC round is bounded by how many independent operations can be issued before a data-dependency forces the next round — irregular, chained comparisons don't batch as cleanly.
Threat models · A consistency spectrum

Weak-to-strong guarantees, like consistency models

Distributed systems trade off consistency strength against latency: eventual consistency is cheap but weak, linearizability is strong but expensive. MPC threat models don't sit on quite the same single line, but the cost gradient rhymes: semi-honest/dishonest-majority (ABY) is the cheapest and weakest corner the paper supports, and malicious/dishonest-majority (SPDZ2k) is the strongest and most expensive. The honest-majority protocols (ABY3, Fantastic Four) land at intermediate cost — but they get there by adding a different kind of assumption (that a majority of parties behave honestly), not by turning the same dial halfway.

Where it breaks: a consistency model is one property you can tune at will on a single system. MPC threat models are really two separate axes crossed together — semi-honest vs. malicious (how a party might misbehave) and honest- vs. dishonest-majority (how many parties you must trust) — and flattening them into one weak-to-strong ladder hides that an honest-majority protocol isn't just "a bit less secure," it rests on a trust assumption a dishonest-majority protocol doesn't need at all.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams you can read at a glance.

1 · Three data abstractions, one hierarchy

CryptDough defines three vector containers, each aimed at a different user. A Vector wraps std::vector for plaintext local operations. An EVector is a multi-vector — a container of several inner Vectors, all updated together — used by protocol developers, since some protocols keep more than one share per secret (replicated sharing) or attach MAC tags for integrity (malicious protocols). A SharedVector (specialized into ASharedVector/BSharedVector) is the secret-shared vector library developers actually program against; its operators (+, *, &) transparently trigger the right protocol communication underneath.

2 · Multiplication with a Beaver triple, concretely

ABY's semi-honest multiplication (Listing 2) pulls a fresh triple, masks both inputs, reveals the masked values, then computes the product locally:

// (a,b,c) precomputed with c = a * b
auto [a, b, c] = BTgen.getNext(n);
auto rx = reconstruct(x + a);   // reveal masked x — safe, "a" hides x
auto ry = reconstruct(y + b);   // reveal masked y — safe, "b" hides y
z = y*rx - a*ry + c;         // = x*y  (the masking noise cancels)
💡
Why it's secure: neither party ever sees x or y — only x+a and y+b, which are uniformly random given a fresh, unknown a, b. See Worked Example ① for the arithmetic that confirms z = x·y exactly.

3 · Vectorization — turning n rounds into O(log|T|)

Written elementwise, oblivious compare-and-swap on an n-element vector costs O(n·log|T|) communication rounds — one comparison's worth of rounds, repeated n times. Written with CryptDough's vectorized operators (v1 <= v2, then a masked XOR), the same computation costs O(log|T|) rounds total, independent of n, because all n local computations happen first and the resulting messages ship together across a handful of batched rounds instead of n·log|T| separate ones.

4 · Virtual vectors — irregular access without copies

Some operators (prefix networks, sorting) need to compare non-contiguous elements — e.g. every other pair at distance 3. Rather than copying those elements into a temporary vector and hand-writing the parallelization, a developer declares two virtual vectors on the same base vector V and passes them straight to the vectorized primitive:

BSharedVector<T> w1 = V.limit(7).step(2);   // indices 0,2,4,6
BSharedVector<T> w2 = V.offset(3).step(2);  // indices 3,5,7,9
cmp-swp(w1, w2);                       // updates V in place, no copies

The runtime partitions w1 and w2 for parallel workers exactly as if they were ordinary contiguous vectors — index translation is computed analytically because oblivious programs are deterministic.

5 · The execution model — mini-clusters and communication threads

Each party runs one OS process with a coordinator thread and a pool of worker threads. For every primitive, the coordinator partitions the input vectors and assigns each partition to a mini-cluster — a set of worker threads with matching partners on the other parties. Mini-clusters run independently and only synchronize with all others at a barrier between primitives; dedicated communication threads ship messages over lock-free buffers so compute threads never block directly on the network. Defaults are tuned per network: 12 batches, 4 CTs in LAN (favoring computation/communication overlap); 1 batch, 16 CTs in WAN (favoring fewer, larger round trips under high RTT).

Follow the numbers, step by step

Worked examples

Four traces using the paper's own numbers, carried all the way through.

① Verifying a Beaver-triple multiplication by hand

Take a known triple (a,b,c)=(3,5,15) (since 3×5=15) and secret inputs x=7, y=2. Confirm the ABY multiplication formula recovers z = x·y = 14 without ever revealing x or y.

  1. Mask and reveal x: rx = reconstruct(x + a) = 7 + 3 = 10. (Only 10 is ever revealed — not 7.)
  2. Mask and reveal y: ry = reconstruct(y + b) = 2 + 5 = 7. (Only 7 is revealed — not 2.)
  3. Compute locally: z = y·rx − a·ry + c = 2×10 − 3×7 + 15 = 20 − 21 + 15 = 14.
  4. Check: x·y = 7×2 = 14. ✓ The masking noise (the a/b terms) cancels exactly.
🥮
Insight: the two "reveal" steps (rx and ry) are the only communication in the whole multiplication — everything else is a local formula. The paper describes this as a single interactive reveal step; that's why Beaver triples turn multiplication into a couple of opens plus local arithmetic, rather than the heavier interaction a naive secure multiplication would otherwise need.

② How much does vectorization save on compare-and-swap?

Take n = 2²⁸ ≈ 268 million elements, 64-bit shares (log₂64 = 6). Non-vectorized cost is O(n·log|T|) rounds; vectorized cost is O(log|T|) rounds.

  1. Non-vectorized rounds ≈ n × 6 = 268,435,456 × 6 ≈ 1.61 billion rounds.
  2. Vectorized rounds = 6 rounds — total, regardless of n.
  3. Speedup in round trips = 1.61 billion ÷ 6 ≈ 2.68 × 10⁸ — for this specific comparison, the speedup works out to n itself.
  4. Bandwidth is identical in both versions — vectorization changes round count, not total bytes sent (§5.2).
💡
This is why CryptDough refuses to let users write elementwise loops over secret vectors at all (Primer 5) — one accidental non-vectorized loop can turn a millisecond op into a multi-hour one under WAN latency.

③ The mixed pipeline across the full threat spectrum

The paper's Fig. 5 runs the whole X-ray + relational + time-series pipeline (Fig. 2 / Listing 1) under all four protocols, in both LAN and WAN.

  1. Semi-honest, LAN (ABY / ABY3): the full pipeline finishes in ≈1 minute.
  2. Semi-honest, WAN: still practical, under 5 minutes — roughly a 5× slowdown from RTT alone.
  3. Malicious, honest-majority (F4), WAN: 18 minutes — about 18× the semi-honest LAN baseline, the cost of tolerating active cheating with only 4 parties.
  4. Malicious, dishonest-majority (SPDZ2k), WAN: just over 1 hour — roughly 60× the semi-honest LAN baseline, the paper's most expensive but strongest guarantee.
🥮
Insight: the ≈60× spread from cheapest to strongest security, running on the same unified codebase with no rewrite, is the paper's clearest demonstration that "configurable security" isn't just a slogan — it's a dial an operator can actually turn.

④ Reading the head-to-head comparisons

Table 2's Pigeon comparison (Trio vs ABY3) shows where CryptDough's generality costs it, and where it doesn't.

  1. AlexNet/CIFAR-10, LAN: Pigeon 0.49s vs CryptDough 0.17s → speedup = 0.49/0.17 ≈ 2.9× in CryptDough's favor.
  2. VGG16/ImageNet, LAN: 52.3s vs 51.0s → essentially parity (1.03×) even without ML-specific optimizations.
  3. AlexNet/CIFAR-10, WAN: 2.68s vs 3.92s → CryptDough is 0.68× as fast — Pigeon's custom ReLU circuit reduces communication enough to win once RTT dominates.
  4. Reading the pattern: CryptDough wins or ties where general vectorized primitives are already near-optimal (LAN); Pigeon's protocol-specific ReLU circuit pulls ahead exactly where communication volume, not round count, is the bottleneck (WAN).
💡
This is the honest trade the paper is explicit about (§7.2): generality costs a little against a workload-specific optimization in the regime that optimization targets, but nowhere else.
Test yourself

Practice problems

Try each before opening the answer — every one ends with the misconception it checks.

Problem 1 · easy
A base vector V has 10 elements. w1 = V.limit(7).step(2) and w2 = V.offset(3).step(2). List the indices each virtual vector points to, and confirm they don't overlap.
Show answer
w1 = offset 0, step 2, up to (exclusive) index 7 → indices {0, 2, 4, 6}. w2 = offset 3, step 2, no limit (runs to V's size, 10) → indices {3, 5, 7, 9}. No overlap.Misconception: thinking a virtual vector copies its elements into a new array. It's purely an index-mapping view — V itself is never duplicated.
Problem 2 · medium
Match each protocol to its threat model: ABY, ABY3, Fantastic Four, SPDZ2k → {semi-honest/dishonest-majority, semi-honest/honest-majority, malicious/honest-majority, malicious/dishonest-majority}.
Show answer
ABY → semi-honest, dishonest-majority (2-party). ABY3 → semi-honest, honest-majority (3-party). Fantastic Four → malicious, honest-majority (4-party). SPDZ2k → malicious, dishonest-majority.Misconception: assuming more parties automatically means stronger security. Fantastic Four's 4 parties buy an honest-majority assumption, not malicious security by itself — SPDZ2k gets malicious security with a weaker (dishonest-majority) assumption at higher cost.
Problem 3 · hard
CryptDough forbids for-loops and if-conditionals on secret data, yet Listing 1 clearly expresses a filter (result["CNT_COVID"] = result["P_COVID"] > 0.8). How is a conditional expressed without branching?
Show answer
The comparison > 0.8 is itself a secure primitive that returns a secret bit — not a branch. That bit then drives a secure multiplexer: both the "true" and "false" outcomes are computed, and the bit obliviously selects which one is kept. Every row is processed identically regardless of its actual value; only the final select differs, and that select itself doesn't leak which branch "happened" because both were computed.Misconception: thinking "no conditionals" means CryptDough can't express filters. It means conditionals must be compiled into always-both-branches-plus-select, not that filtering logic is impossible.
Problem 4 · medium
For a vector of n = 1024 elements with 32-bit shares (log₂32 = 5), compute the non-vectorized and vectorized round counts for compare-and-swap, and the resulting speedup.
Show answer
Non-vectorized: n × log|T| = 1024 × 5 = 5,120 rounds. Vectorized: log|T| = 5 rounds total. Speedup in round trips = 5120/5 = 1024× — exactly n.Misconception: thinking vectorization reduces the total data transmitted. It doesn't — both versions send the same bytes; vectorization only reduces how many separate round trips are needed to send them.
Problem 5 · easy
A pipeline has 3 sequential primitives P1, P2, P3, and 4 mini-clusters. Must every mini-cluster finish all of P1 before any mini-cluster starts P2? Can two mini-clusters process different batches of the same primitive at different times?
Show answer
Yes to the first — the barrier is at the boundary between primitives, so all 4 mini-clusters must complete P1 before any proceeds to P2. Yes to the second — within a single primitive, different mini-clusters process their own batches independently and don't wait for each other batch-by-batch; only the completion of the whole primitive is synchronized.Misconception: assuming the barrier is per-batch. It's per-primitive — batches inside one primitive overlap freely across mini-clusters.
Problem 6 · medium
CryptDough defaults to 12 batches / 4 CTs in LAN but 1 batch / 16 CTs in WAN. Explain the reasoning behind each choice.
Show answer
In LAN, RTT is tiny, so the real cost is keeping compute and communication overlapped — more, smaller batches let a mini-cluster's next batch compute while the previous one's messages are still in flight, with few CTs needed since each round trip is cheap. In WAN, RTT is large and dominates, so the priority flips to minimizing the number of round trips (favoring 1 large batch) while spreading the resulting bigger messages across many CTs so they ship concurrently rather than serially.Misconception: assuming these are protocol-specific tuning knobs. They're driven purely by network latency characteristics, independent of which MPC protocol is running.
Problem 7 · hard
A library developer adds a new "graph analytics" operator built entirely from CryptDough's existing oblivious primitives. Why does it automatically work under ABY, ABY3, Fantastic Four, and SPDZ2k without any changes?
Show answer
Because the operator is composed only from protocol-agnostic primitives (comparisons, multiplexers, etc.), which themselves are composed only from the fixed low-level interface (secure add/multiply/XOR/AND) that every protocol implements. The operator's code never mentions a specific protocol — it inherits whichever one is compiled in underneath, and therefore inherits that protocol's threat model automatically.Misconception: thinking each analytics operator must be reimplemented once per protocol, the way specialized systems require. CryptDough's layering is exactly designed so that reimplementation only happens at the bottom layer, once per protocol, ever.
Problem 8 · medium
Why does the paper report only online-phase time for dishonest-majority protocols (SPDZ2k), but end-to-end time for the others?
Show answer
SPDZ2k, like other dishonest-majority protocols, relies on a data-independent offline (preprocessing) phase that generates correlated randomness (analogous to Beaver triples) ahead of time and can be run whenever convenient, decoupled from when the real inputs arrive. Reporting only the online phase reflects the latency a user actually experiences once their private data is ready to be processed — the standard convention for this protocol class.Misconception: assuming this makes SPDZ2k's reported numbers directly comparable, cost-for-cost, to protocols without a separate offline phase. The offline cost is real; it's just amortized and reported separately by convention.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What does "unified" mean here — like Spark unifying batch and streaming?▾
Yes, that's the closest plaintext analogy. Just as Spark/Flink let one engine express batch, streaming, and ML with a common dataflow model, CryptDough lets one MPC runtime express relational, time-series, and ML-inference analytics with a common vector/operator model — and additionally spans multiple threat models, which plaintext engines never had to worry about.
Q2Why can't you just glue ORQ, TVA, and Pigeon together with scripts?▾
Even where threat models line up, the systems use different secret-sharing schemes and data encodings internally, so passing output from one into another requires custom cryptographic conversion code, not just file-format glue. On top of that you'd pay real overhead for spawning separate processes, re-sharing secrets between systems, and materializing intermediate results to storage between hops.
Q3What's the actual difference between Vector, EVector, and SharedVector?▾
Vector is plain local data. EVector is a protocol-internal multi-vector (it may hold several inner Vectors per secret — shares plus MAC tags, say) that only cryptographers touch. SharedVector is the user-facing secret-shared type (ASharedVector/BSharedVector) that library developers and analysts actually program against; its operators trigger the right secure primitive underneath.
Q4Why does CryptDough forbid for-loops and if-conditionals on secret data?▾
Because branching on a secret leaks information through which branch executed. Forbidding it forces every operator into a fixed, data-independent sequence of vectorized operations — which is also exactly what makes CryptDough's parallelization and batching machinery possible. Conditionals are instead expressed with secure comparisons plus multiplexers.
Q5How is a virtual vector different from just slicing an array?▾
A slice is contiguous. A virtual vector's mapping function f(i) can express arbitrary strided, repeated, cyclic, or alternating patterns (Appendix D), and — crucially — the CryptDough runtime automatically parallelizes and distributes it across worker threads exactly as if it were a real contiguous vector, with index translation computed analytically and zero data copies.
Q6How does CryptDough decide thread counts and batch sizes?▾
Defaults are network-driven, not protocol-driven: 12 batches with 4 communication threads in LAN (favor compute/communication overlap under low RTT), 1 batch with 16 communication threads in WAN (favor fewer, larger round trips and concurrent shipping under high RTT). These are configurable, not hardwired.
Q7Does CryptDough always beat the specialized systems it's compared against?▾
No. It wins or ties in most LAN comparisons (1.5× over ORQ, up to 2.7× over TVA, parity-to-faster than Piranha and Pigeon) but loses to Pigeon in WAN, where Pigeon's protocol-specific ReLU circuit reduces communication volume in a way CryptDough's general primitives don't match (§7.2, Table 2).
Q8Does CryptDough trust the servers running the computation?▾
No — that's the point of MPC. Security holds even if an administrator inspects a server's memory between or during computations; no trusted hardware or storage is assumed. The entire codebase is in the trusted computing base, though (a bug anywhere can undermine the guarantees), and the network is assumed untrusted, so channels are authenticated and encrypted via TLS.
Q9How hard is it to add a brand-new MPC protocol?▾
An applied cryptographer implements a short, fixed list of functionalities (secure add, multiply, XOR, AND, share creation/opening — Table 5/Appendix E) as methods on an abstract protocol class, with access to a built-in communicator and randomness generator. Every existing analytics library then works under the new protocol automatically, with no changes to library code.
Q10What did the authors leave for future work?▾
Fault tolerance and horizontal scaling within a single logical party (currently one server per party, restarted on failure); formal verification of the codebase; and compile-time or runtime checks that developers use virtual vectors correctly, which CryptDough doesn't currently enforce.

Core terms
CryptDoughA layered, protocol-agnostic MPC analytics engine supporting relational, time-series, and ML-inference workloads across four threat models.
Virtual vectorA declared view W[i]=V[f(i)] onto a base vector, letting irregular access patterns reuse vectorized primitives with automatic parallelization and no data copies.
Mini-clusterA set of worker threads, one per party, that form an independent computation unit; mini-clusters synchronize only at primitive boundaries.
Oblivious control flowProgram execution whose sequence of operations never depends on secret data, eliminating timing/access-pattern leakage.
Beaver tripleA precomputed secret-shared (a,b,c=a×b) that lets secure multiplication be completed with an interactive reveal step plus one local formula.
Communicator / CTThe module (and its dedicated communication threads) each protocol uses to exchange shares between parties over lock-free buffers.
Configurable securityCryptDough's principle of supporting multiple threat models within one runtime instead of committing to one.
ABB modelArithmetic Black-Box model — the standard composition argument by which CryptDough's layered operators inherit the security of their underlying primitives.
Supporting terms
Vector / EVector / SharedVectorThe three container types: plaintext, protocol-internal multi-vector, and user-facing secret-shared vector, respectively.
Semi-honest / maliciousPassive-but-curious vs. actively-deviating adversary models.
Honest / dishonest majorityWhether the adversary controls fewer than half, or half-or-more, of the computing parties.
Data holder / computing party / output partyThe three roles in an MPC deployment: who owns the data, who computes on shares, and who learns the result.
Auxiliary tag / MACExtra authentication data attached to shares in malicious-secure protocols, stored via EVector's multi-vector capability.
MultiplexerA secure circuit that obliviously selects between two already-computed results using a secret bit, replacing a conditional branch.
Offline / online phaseData-independent precomputation of correlated randomness, versus the latency-sensitive real computation that consumes it.
RCA / PPARipple-Carry Adder / Parallel-Prefix Adder — the two boolean-circuit adder designs CryptDough provides as primitives.
