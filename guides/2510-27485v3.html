arXiv:2510.27485 · ETH Zürich · A Field Guide

Turn a hardware manual into something a solver can prove — or break

SoC reference manuals run to thousands of pages of ambiguous prose, and closed-source chips never ship their RTL. Sockeye is a tiny DSL that turns the security-relevant parts into a model an SMT solver can attack or verify — on the very same specification.

📄 "Sockeye" · Fiedler et al., ETH Zürich 🎓 Some SMT/symbolic-execution familiarity assumed — primers cover it ⏱ ~30 min read
🛡️

Write the manual's security-relevant behavior once, in a tiny DSL — then ask an SMT solver to either PROVE the property holds forever, or FIND a concrete trace that breaks it.

Quick glossary — acronyms used throughout

SoCSystem-on-Chip: the multi-component chip (cores, interconnect, DMA devices, protection units) Sockeye models.
RTLRegister-Transfer Level: the hardware's actual design source. Rarely available to systems programmers, and not required by Sockeye.
TEETrusted Execution Environment: an isolated, higher-privilege context (Arm TrustZone's Secure world, x86 SMM, etc.).
SMMSystem Management Mode: x86's "ring −2," used for e.g. power management — the target of the AMD Sinkclose bug.
ASCAddress Space Controller: the ThunderX-1 unit filtering CPU↔DRAM requests by TrustZone world — the paper's running example.
DSLDomain-Specific Language: Sockeye's own language for modeling hardware, software config, and security properties, all at once.
SMTSatisfiability Modulo Theories: the class of solver (here Z3, via Rosette) that finds counterexamples or proves "unsat."
BMCBounded Model Checking: verifying a property within a fixed number of steps — what CBMC does, and what un-inducted Sockeye scenarios are.
MMU / SMMU / IOMMU(System) Memory Management Unit: address-translation hardware, abstracted (not bit-precisely modeled) in the tx1 ZIP-engine proof.
DMADirect Memory Access: a device (NIC, compression engine, …) touching memory without the CPU — a recurring TrustZone-bypass vector in §6.

1Why a reference manual is a bad substitute for RTL▾

Hardware vendors publish thousands-of-pages PDF manuals describing register semantics, interconnects, and protection units — written in prose, by hand, often with cross-references and implicit assumptions. The actual behavior lives in the RTL (the chip's real design source), which systems programmers almost never get to see.

So programmers write firmware against the manual's prose, hoping it accurately describes the silicon. Ambiguity, omission, or an outright documentation bug can all make "correct by the manual" wrong on real hardware.

Now you're ready: Sockeye's whole premise is treating the manual, not the RTL, as ground truth — and being honest that this means bugs can hide in the manual itself (§4, §4.1).
2Secure vs. Non-Secure worlds (Arm TrustZone)▾

Arm TrustZone splits execution into two isolated worlds: Secure (trusted firmware, key management, …) and Non-Secure (the regular OS, apps). It's orthogonal to user/kernel privilege levels — a CPU core can be in kernel mode in either world.

The running example throughout the paper — the ThunderX-1's Address Space Controller — exists purely to enforce this split at the DRAM level: memory tagged Secure should be unreachable from the Non-Secure world.

Now you're ready: almost every case study in §6 is some variant of "can the Non-Secure world reach data it shouldn't?"
3Modules, instances, callees — Sockeye's graph model▾

A module is a blueprint (e.g. ASC, DRAM, CPU) that can be instantiated as a named child of another module — this forms a tree, mirroring "consists of." A callee is a declared dependency to some other instance, not necessarily a child — mirroring "depends on" or "requires," and must be explicitly wired (e.g. cpu.asc -> asc;).

Requests between components are modeled as ordinary function calls, and replies as return values — a simplification of the real request/response protocol on physical wires.

Now you're ready: the signature figure in the next tab is exactly this graph for the paper's minimized ThunderX-1 example.
4Mutable state: State<T> and Array<K,V>▾

Sockeye has exactly two ways to get mutable state, both built-in "primitive modules." State<T>(init) holds one value of type T with getters/setters — used for a register, or a flag like is_secure. Array<K,V> models a large indexed collection (e.g. 16 GB of DRAM as 2³¹ 64-bit words), with symbolic backends avoiding literal allocation of billions of elements.

Now you're ready: everything you'll see modeled — region registers, DRAM contents, a "did we get a bad request" monitor flag — is just one of these two primitives.
5any<T>, assume, assert — underspecification as a feature▾

any<T> nondeterministically picks an arbitrary valid value of type T — the solver's job is to find a concrete assignment. It's how Sockeye handles technical ambiguity: if the manual doesn't pin down a value, let it range over everything valid rather than guessing.

assume(prop) restricts the search to scenarios satisfying prop; assert(prop) is a proof obligation. The solver looks for an assignment where every assume holds but some assert fails.

Now you're ready: Sockeye deliberately omits ∀/∃ quantifiers to keep queries tractable — any plus these two keywords is the entire property language.
6Bounded checking vs. unbounded proof▾

Running a scenario for a fixed number of step() calls (e.g. two) and asserting a property tells you only that within those steps, nothing goes wrong — a bounded check. To cover every possible number of steps, Sockeye uses induction: prove an invariant holds at the start (base_case), prove that if it holds before one step it holds after (inductive_step), then separately show the invariant implies the property you actually care about.

Now you're ready: "found a bug in 2 steps" and "proved safe forever" are genuinely different guarantees, and Sockeye supports both on the same spec.
7SMT solving and symbolic execution, in one paragraph▾

Symbolic execution runs a program with symbolic (unknown) values instead of concrete ones, tracking a logical formula for every branch taken. At the end, an SMT solver (Sockeye uses Z3, via the Rosette language) is asked: is there any assignment of the symbolic variables making all constraints true? If yes, that assignment is a real, concrete counterexample; if the query is unsatisfiable ("unsat"), no such execution exists.

Now you're ready: a Sockeye "bug" is literally a satisfying assignment Z3 found; a Sockeye "proof" is an unsat result on the induction queries.
8Requests, over-approximation, and soundness▾

Parts of a platform Sockeye doesn't model in fine detail (e.g. the SMMU's exact translation-table walk) are over-approximated: the model allows a superset of the real hardware's behaviors (e.g. "any write to the translation-table region can arbitrarily change the mapping"). This keeps the model sound for bug-finding — every real behavior is still a possible spec behavior — at the cost of possibly finding "bugs" that a more precise model would rule out.

Now you're ready: when Sockeye's exploit trace looks slightly too easy, over-approximation is often why — always worth checking against real hardware.
9Classifying a finding: hardware, documentation, or config bug▾

When Sockeye reports a counterexample, that's the start of triage, not the end. First, check whether changing the configuration prevents the exploit: if so, it's a config bug — the hardware and the manual are both fine, but this particular software setup fails to use them safely. If no configuration change prevents it, test the exploit's concrete inputs on real hardware. If it reproduces, the hardware genuinely is unsafe and the manual accurately described that behavior (hardware bug). If it does not reproduce, the manual predicted behavior the hardware doesn't actually exhibit (documentation bug).

Now you're ready: this triage (Fig. 4) is what turns "Sockeye found a counterexample" into "here's specifically what's wrong, and where."
The whole story in one place

Sockeye in a nutshell

The problem, the DSL that fixes it, and how bug-finding and proving share one specification.

Modern SoCs enforce security through dozens of protection mechanisms — TrustZone worlds, interconnect firewalls, secure-monitor modes — configured via memory-mapped registers whose semantics are described only in prose reference manuals. That documentation is written for humans, is frequently ambiguous, and is the only artifact most systems programmers ever see, since RTL for closed-source platforms is essentially never public. Getting the configuration right, or even knowing what "right" means precisely, is genuinely hard.

Sockeye addresses this with a single domain-specific language used to express three things at once: the hardware's behavior (transcribed from the manual), the software that configures it, and the security property you want to hold. A graph of module instances and callee wiring models the SoC's components; any<T>, assume, and assert express underspecification and intent without needing quantifiers. The same specification is then handed to SMT-based backends (chiefly Rosette/Z3, also CBMC) that either return a concrete counterexample trace — a bug — or, via a three-part induction pattern, prove the property holds for an unbounded number of steps.

The payoff: across 8 real platforms — spec sizes ranging roughly 1,096 to 9,667 lines (1,546 to 9,728 lines total including scenario and proof code) — Sockeye reproduced 2 known hardware bugs, found 2 critical documentation errors, surfaced numerous smaller ambiguities and misconfiguration risks, discovered a previously-unknown vulnerability on the Marvell ThunderX-1 (confirmed by the vendor to affect a wider family of shipping OCTEON network appliances, and since fixed), and produced 4 unbounded security proofs across 3 platforms.

🍯 Key takeaways

  • Sockeye is built for platforms with no public RTL — the manual is the only available spec, transcribed by hand.
  • One DSL expresses hardware, config, and property together — no separate modeling languages to keep in sync.
  • any<T> + assume/assert replace ∀/∃ quantifiers, keeping SMT queries tractable while still expressing confidentiality, integrity, and non-interference.
  • Bounded scenarios (a few step() calls) find bugs fast; a 3-part induction pattern (base case, inductive step, "invariant is useful") turns the same model into an unbounded proof.
  • A counterexample still needs triage: hardware bug, documentation bug, or config bug — Sockeye narrows the search, a human (or a test on real hardware) confirms which.
  • Applied to 8 platforms: 2 reproduced hardware bugs, 2 critical documentation errors, 1 new vulnerability (ThunderX-1 / OCTEON family, vendor-confirmed and fixed), 4 unbounded proofs.
  • Multiple backends (Rosette, CBMC) on the same spec double as cross-validation — agreement raises confidence the tools themselves aren't the bug.
Seven everyday pictures

How to think about Sockeye

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core problem · Manual vs. hardware

The contract's fine print vs. the court ruling

A reference manual is like a contract's fine print — written by hand, in prose, with implicit assumptions and cross-references. RTL is the actual signed behavior of the parties. Sockeye reads the contract and turns it into a checklist a lawyer (the solver) can audit precisely — but only as reliably as the contract describes reality.

Where it breaks: hardware doesn't "intend" anything. When RTL and manual disagree, the manual is simply wrong — and if Sockeye proves a property safe from a manual that's wrong in the reassuring direction, that's the one failure mode it cannot catch (§4.1's unresolved case).
The ThunderX-1 bug · Self-modifying policy

A guard who can rewrite the rulebook

The Address Space Controller's region-config registers — which decide who may access what — were readable and writable by whichever world sent the request, with no check that the requester was Secure. It's a bouncer whose ID-checking policy can be read and edited by anyone standing at the door, including the people trying to get past the bouncer.

Where it breaks: the real fix is surgical, not a blanket lockdown: it adds && r.is_secure to the is_region_config_addr(...) branch itself, before asc_region_request(r) is ever reached (§2.8/Appendix A) — gating both reads and writes to the region-config registers, not just writes.
Verification depth · Bounded vs. induction

A crash test vs. a lifetime warranty

Checking a property after 2 fixed step() calls is a crash test: cheap, informative, and it's exactly what caught the ThunderX-1 bug. But it only certifies "survived this specific test." Induction — base case, then "if it held before a step it holds after" — is a lifetime warranty: prove those two things once, and every future step, however many, is covered.

Where it breaks: a lifetime warranty only covers the invariant you thought to state. The final step — "this invariant really implies the property I care about" — is still a human judgment call Sockeye doesn't automate (§7.2).
Underspecification · any<T>

A detector set to "maybe metal"

any<T> says "I don't know exactly what value goes here, but it's a valid T" — like setting a metal detector to flag anything vaguely metallic when the exact threat model isn't pinned down yet. Deliberately imprecise, so modeling can proceed past an ambiguous manual passage instead of stalling on it.

Where it breaks: an any placed too loosely can manufacture a false alarm — a "bug" that only exists because the model permits a value real hardware never would. That's exactly what the documentation/config-bug branch of the triage workflow (§4.1) exists to catch.
Confidentiality · Two low-equivalent copies

Twins raised on the same public facts

To check for leaks, run two copies of the SoC that agree on every "public" (low-confidentiality) starting value but may differ on secrets — like twins told the same news but given different private letters. Step both identically; if a public-facing observer could ever tell them apart afterward, that difference can only have come from a secret leaking out.

Where it breaks: because Sockeye has no ∀ quantifier, "the twins agree everywhere" has to be built from two separate helper functions — assume_low_equivalent (copy values in) and assert_low_equivalent (spot-check one adversarial address with any) — a subtlety easy to get backwards (§4.2.5).
Non-interference · Air-gapped reference model

A real building vs. its air-gapped blueprint

A second technique runs two structurally different models side by side: one intertwined (real RAM as one big byte array, like a real shared building) and one obviously already separated (per-process virtual maps, like a blueprint with a literal gap between wings). Step both on the same schedule; if the tangled model ever lets one process read another's out-of-bounds data, it diverges from the blueprint model — which is provably incapable of that.

Where it breaks: this proves the tangled system behaves as if isolated at the level of values read and written — it says nothing about timing side channels, which the paper treats as an explicitly orthogonal concern (§8, citing Pensieve).
Cross-validation · Multiple backends

Three translators, one document

Rosette, CBMC, and a hand-written SMT encoding are three different translators for the same Sockeye scenario — like sending one contract to three translators and comparing results. When all three agree a spec is safe, trust rises, because a bug specific to one tool is unlikely to be replicated identically by the other two (§4, §5).

Where it breaks: agreement doesn't validate Sockeye's own compiler — a shared misunderstanding baked into how Sockeye itself translates the DSL would fool all three backends the same way. It's one of the paper's own listed soundness assumptions (§4).
The full explanation

How it actually works

From the ASC's request handler through to a triaged, classified finding — the paper's own ThunderX-1 example, followed all the way through.

1 · Modeling a request: the ASC's decision logic

Every memory access from the CPU is modeled as a Request record (is_write, is_secure, address, value) passed to the ASC's request() function, which branches on the address to decide whether it's a region-configuration access, an allowed DRAM access, or neither (Listing 3).

2 · Finding the bug automatically

A top-level scenario (Listing 4) sets up a realistic region configuration, flips the CPU to Non-Secure, snapshots DRAM, runs two nondeterministic step()s, and asserts a chosen secure address's contents are unchanged. Rosette symbolically executes this, accumulating one SMT formula; Z3 is asked for an assignment making every assume true and the final assert false.

// listing 6 — Sockeye's printf trace of the counterexample Z3 found
CPU: request is { address: 0x8000_0000_0070u48, is_secure: false,
                is_write: true, value: 1 }
ASC: Setting region3.ATTR to 1
CPU: request is { address: 0, is_secure: false,
                is_write: true, value: 0x48ad_c33c_fdc9_99d4u64 }
DRAM: Storing 0x48ad_c33c_fdc9_99d4u64 to 0
⚠
Reading the trace: the first request writes region3's ATTR register to 1 (ATTR_NONSEC) — from Non-Secure code. Region3's range is still [0,0], so it now legally covers address 0, which also sits inside Secure region0's range. The second request writes garbage straight to address 0 — accepted, because it's allowed by region3, even though it's Secure memory by region0.

3 · Classifying the finding

A counterexample alone doesn't say what's actually wrong. Sockeye's workflow (Fig. 4) routes every finding to one of three outcomes.

4 · From bounded check to unbounded proof

After the fix (adding && r.is_secure to the is_region_config_addr(...) branch, gating region-config reads and writes alike), the 2-step scenario returns unsat — but that only covers 2 steps. The induction pattern (Listing 7) covers all of them:

fn base_case() {                    // invariant holds at reset
  setup_regions(); cpu.is_secure.set(false);
  assert(invariant());
}
fn inductive_step() {                // invariant is preserved by any step
  havoc(); assume(invariant());
  step();
  assert(invariant());
}
fn invariant_is_useful() {          // invariant ⇒ the property we actually want
  havoc(); assume(invariant());
  let before = dram.storage.get(); step();
  let after  = dram.storage.get();
  assert(before[secure_addr] == after[secure_addr])
}

The chosen invariant is deliberately simple: each region either is empty/Secure-only, or its address range doesn't overlap the protected secure range. If all three checks return unsat, the property holds no matter how many steps run — a genuinely unbounded guarantee, built from three bounded SMT queries plus one human logical step (that base case + preservation + usefulness together imply "always holds").

💡
Why these invariants are easier than typical program-verification invariants: here they mostly say "this configuration register stays what it was" — not a subtle loop invariant about an algorithm's intermediate state. §4 notes this is a deliberate consequence of the domain: security-relevant hardware state changes rarely, and mostly by explicit configuration writes.

5 · Multiple backends, one spec

The same Sockeye scenario compiles to Rosette (symbolic execution over Racket, backed by Z3), to C for CBMC (a bounded model checker), and to a direct SMT encoding. Rosette usually wins on speed, but not always — running several backends functions as a portfolio: whichever finishes first is used, and agreement between tools raises confidence that a "safe" result isn't an artifact of one specific solver's blind spot.

Follow the numbers, step by step

Worked examples

Four traces, carried all the way through with the paper's real figures — decoding an exploit address, sizing specs, comparing backends, and reading a timeout fix.

① Decoding the exploit address bit-by-bit

The trace writes to 0x8000_0000_0070. Which register is that, and why does it match is_region_config_addr?

  1. Split the hex: 0x8000_0000_0070 in binary has bit 47 set (0x8000_0000_0000 = 1<<47 = CONFIG_BASE), and the low bits are 0x0070 = 0111_0000.
  2. Check the guard: is_region_config_addr requires bit 47 set, bits [46:7] all zero, and bits [2:0] all zero. 0x70's low 3 bits are 000 — passes.
  3. Extract region_id = bits[6:5]: from 0111_0000, bits 6 and 5 are both 1 → region_id = 0b11 = 3.
  4. Extract register_id = bits[4:3]: bit 4 is 1, bit 3 is 0 → register_id = 0b10 = 2, which is ATTR (0=START, 1=END, 2=ATTR).
  5. So the address is region3.ATTR — exactly what the trace's own printf confirms ("ASC: Setting region3.ATTR to 1").
🍯
Insight: the exploit isn't exotic — it's an ordinary MMIO write to a documented register, made from the wrong privilege level because the handler never checked who was writing.

② Sizing the specs (Table 1)

Spec size (S) + property/scenario code (V) = total (T) lines of code, across all 8 platforms.

  1. ryzen: S 1956 + V 127 = T 2083 — mostly modeling SMM and its protected-region registers, few properties (bounded Sinkclose repro).
  2. tx1: S 2366 + V 1160 = T 3526 — V is unusually large here because tx1 has both the bug-finding scenario and a full induction proof (ZIP-engine correctness), each needing its own invariant and helper code.
  3. jetson: S 9667 + V 61 = T 9728 — by far the largest spec (many overlapping DRAM-partitioning mechanisms: TrustZone, Video Protection Region, generalized carveouts), but almost no property code — reflecting that it was "the most difficult system to model," per §6.1, with effort going into modeling ambiguity itself rather than proofs.
  4. pico: S 1096 + V 450 = T 1546 — smallest spec, but proportionally large V, since two separate proofs (DMA isolation, TrustZone with FORCE_CORE_NS) both live here.
  5. Pattern: V is small when a platform only needs bug-finding scenarios, and grows sharply wherever an induction proof (with its invariant, base case, and "invariant is useful" checks) was written.

③ Rosette vs. CBMC — backend variance (Tables 2–3)

Runtimes, in seconds, for the same specification on two different backends.

  1. pico bug scenario: Rosette 6.4s vs. CBMC 738.1s — Rosette wins by roughly 115×.
  2. tx1 bugfix scenario: Rosette 1.1s vs. CBMC 2.6s — still a Rosette win, but only ~2.4×, showing the gap isn't constant.
  3. jetson bug scenario — the exception: Rosette 1.1s vs. CBMC 0.4s. CBMC is faster here. §7.3 explicitly flags that "Rosette outperforms CBMC in general" — not universally — which is exactly the portfolio argument for running both.
  4. Full timeouts: ryzen and aspeed bug scenarios hit CBMC's 900s timeout entirely, while Rosette solves aspeed's bug scenario in 542.4s — still slow, but two orders of magnitude inside the budget.
💡
Insight: "which backend is faster" is workload-dependent enough that neither can be dropped — this is the paper's stated rationale for treating backend choice as a portfolio problem, not a single default (§5, §7.3).

④ Escaping a timeout: the zynq case

The most general zynq bug scenario times out (>900s) on Rosette. §7.3 describes narrowing the search.

  1. Unrestricted: the scenario lets Sockeye pick any of the 8 DMA controllers and any schedule of steps — Rosette can't finish within 900s.
  2. Restrict the DMA channel to one specific controller instead of letting the solver search all 8: the bug is now found within 2 minutes (120s) — at least a 7.5× speedup versus the 900s timeout floor.
  3. Also fix one step to be "the CPU initiates a DMA transfer" (removing that nondeterministic choice too): the bug is found in under 20 seconds — roughly 45× faster than the original timeout, and over 6× faster than the channel-only restriction.
  4. Same underlying bug, three search spaces: nothing about the vulnerability changed — only how much of the solver's search Sockeye's user chose to fix with domain knowledge versus leave symbolic.
🍯
Insight: when a query times out, the fix is rarely "run it longer" — it's narrowing the any<T> choices with domain assumptions, trading generality of the search for tractability, exactly as recommended in §7.3.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
A team runs test_secure_area_unchanged for 2 steps, gets "unsat," and declares the ASC secure. Is that conclusion justified?
Show answer
No — not on its own. "Unsat after 2 steps" only means no violation exists within exactly 2 step() calls; a 3rd, 4th, or Nth step might still expose one. To conclude the property holds forever, they'd need the induction pattern: a base case, an inductive step showing the invariant is preserved, and a check that the invariant implies the property (§2.9, §7.2).Misconception: that a bounded "unsat" result is already a proof. It's evidence, and a genuinely useful one for bug-finding, but it is not the unbounded guarantee induction provides.
Problem 2 · medium
Decode which region register the address 0x8000_0000_0028 targets. (Recall: bit 47 = config-space flag, bits[6:5] = region_id, bits[4:3] = register_id where 0=START, 1=END, 2=ATTR.)
Show answer
0x0028 = 0010_1000. Bits[6:5] = 01 → region_id = 1. Bits[4:3] = 01 → register_id = 1 = END. So this address is region1.END.Misconception: reading the bit ranges from the wrong end, or assuming register_id 0/1/2/3 line up with START/END/ATTR/unused in address order rather than value order — the mapping has to be read off the case statement in Listing 3/Appendix A, not guessed.
Problem 3 · medium
Why does the fix insert && r.is_secure specifically into the is_region_config_addr(...) branch, before asc_region_request is reached — rather than, say, checking r.is_secure inside each Region's allows() function?
Show answer
The vulnerability is about who may access the policy itself — reading and writing the region config registers — not about who may access DRAM once the policy is set: Region.allows() already correctly checks is_secure against a region's ATTR for ordinary DRAM accesses. The missing check gates the entire region-config branch before asc_region_request is ever reached, so it blocks both config reads and writes — exactly the surface the bug lived on, and exactly where the fix belongs.Misconception: conflating "who can access protected data" with "who can access the rules about who can access protected data" — these are two different checks, and the bug was in the second one only.
Problem 4 · hard
Sockeye can't express always_holds(property) directly. What three scenarios replace it, and what final step is left for a human?
Show answer
base_case (the invariant holds at reset), inductive_step (assuming the invariant before one step, it still holds after), and invariant_is_useful (assuming the invariant, the actual desired property holds for one step). If all three return unsat, a human still has to conclude, by ordinary mathematical induction, that base case + preservation implies the invariant holds after any number of steps, and therefore (via usefulness) so does the property — Sockeye doesn't chain these three unsat results into a single machine-checked "always" statement (§7.2).Misconception: assuming Sockeye's induction support is fully automatic end-to-end. The SMT queries are automatic; the logical glue connecting three separate results into "always holds" is a (small, reviewer-checkable) manual step.
Problem 5 · medium
Sockeye found that the Raspberry Pi Pico 2's DMA security level appeared settable by a privileged Non-Secure core, per the manual. Testing on real hardware showed writes to that field were silently ignored. How should this finding be classified, and why does it still matter?
Show answer
It's a documentation bug, not a hardware bug: the manual describes behavior the silicon doesn't actually have (real writes are ignored, so the described attack can't be carried out as written). It still matters because it shows an ambiguity/inaccuracy in the manual that could mislead other engineers reading the same passage, and because it validates the triage workflow — Sockeye correctly generated a plausible exploit for what the manual said, and testing on hardware was what revealed the manual, not the chip, was at fault.Misconception: assuming every Sockeye counterexample that doesn't reproduce on hardware is a "false positive" to discard. It's still real information — evidence the documentation itself needs correcting (§6.1, §4.1).
Problem 6 · hard
For the jetson platform's bug scenario, CBMC (0.4s) beat Rosette (1.1s) — the opposite of the general trend. Does this mean CBMC should be the default backend?
Show answer
No. §7.3 is explicit that Rosette "usually outperforms CBMC, but this is not true in general," and attributes the variance partly to the fact that the C code Sockeye generates for CBMC might not be particularly amenable to it, plus SMT solver performance being famously sensitive to small, seemingly unrelated changes in encoding. One favorable data point (jetson) doesn't generalize — it's exactly the argument for running a portfolio of backends rather than committing to either one exclusively.Misconception: extrapolating a backend-performance ranking from a handful of benchmarks. The paper's own data shows the ranking flips per-workload, which is the whole justification for supporting multiple backends at all.
Problem 7 · medium
Sockeye's DSL deliberately has no loops. What's the direct cost of that restriction, and what's the benefit the paper claims in return?
Show answer
Cost: you can't express behavior that iterates an unbounded or data-dependent number of times within one function — everything must be expressible as sequential composition and branching. Benefit (§5): keeping the language loop-free keeps every backend's job tractable — sequential-with-branching specs are supported efficiently by symbolic execution, bounded model checking, and direct SMT encoding alike, which is why solving times in Tables 2–3 stay mostly in the single-to-low-hundreds of seconds rather than exploding.Misconception: that no loops means no expressiveness for repeated behavior. §4 notes this restriction did not prevent expressing the complex properties and proofs the paper demonstrates — repetition across time is instead modeled by re-invoking step() and using induction.
Problem 8 · hard
In the non-interference "two low-equivalent copies" technique, why can assert_low_equivalent use any<BitInt(12)> to stand in for "for all addresses," but assume_low_equivalent cannot use the same trick?
Show answer
assert is a proof obligation checked by refutation: the solver searches for a single assignment of test_addr that breaks the assertion, and if none exists (unsat), the property holds for every address — one adversarially-chosen any address, checked to unsat, is exactly how Sockeye emulates "∀ address, the property holds." assume, however, needs to encode "true for every address" as a starting condition, not a goal to refute — if it picked one any address and constrained equality there, the solver would only be told the two copies agree at that one (also solver-chosen) address, not everywhere else. The workaround is to directly copy the desired shared values into both copies' memory in assume_low_equivalent, achieving the ∀ by construction rather than by search (§4.2.5).Misconception: that any under assert is simply existential. The single symbolic value is what the solver searches over, but an unsat result on that search is precisely what establishes a universal (∀) guarantee — the quantifier Sockeye actually emulates depends on this proof-by-refutation structure, not just on which keyword wraps the any.

Q1What is Sockeye, in one sentence?▾
A domain-specific language and toolchain that lets engineers transcribe a hardware reference manual's security-relevant behavior into a model an SMT solver can either find an attack in or prove secure, without needing access to the chip's RTL.
Q2Why not just extract a formal spec straight from RTL?▾
Because for the platforms this targets — closed-source SoCs like the ThunderX-1, Ryzen, Jetson, OMAP, and others in §6 — RTL simply isn't available to the systems programmers who need to configure them securely. Sockeye is explicitly designed for the case where the manual is the only artifact you have.
Q3What's the difference between a documentation bug, a hardware bug, and a config bug?▾
Given a counterexample, Sockeye's workflow first checks whether a configuration change would prevent it — if so, it's a config bug: the hardware and manual are both fine, but this particular software setup fails to use them safely. If no configuration prevents it, it's tested on real silicon: hardware bug if it reproduces (the hardware genuinely is unsafe, and the manual described it accurately), or documentation bug if it doesn't (the manual describes behavior the hardware doesn't actually have, e.g. the pico's ignored DMA-security writes). Figure 4 in the paper is exactly this decision tree.
Q4What does any<T> do, and why is it essential for modeling manuals?▾
It nondeterministically ranges over every valid value of type T. Manuals are full of ambiguity and forward references; rather than guessing a specific interpretation, Sockeye lets the modeler write any<T> and defer the decision to the solver, which will explore all the values that matter for the property being checked.
Q5How does Sockeye avoid needing ∀/∃ quantifiers?▾
It gets the same expressive power through proof by refutation instead of explicit quantifiers. To check a ∀ claim — "this holds for every address/value" — you assert the property over an any-typed variable: the solver searches for one concrete assignment that violates the assertion, an existential counterexample search. If that search comes back unsat, no such counterexample exists, which is exactly what "holds for all values" means — so any under assert is how Sockeye emulates ∀, via a search that is itself existential. Under assume, by contrast, a single any value can't stand for "every address" as a starting condition, so Sockeye instead directly copies the shared values into both structures rather than constraining one symbolic address (§2.5, §4.2.5).
Q6What is the ThunderX-1 vulnerability, concretely?▾
The Address Space Controller's region-configuration registers (START/END/ATTR) were readable and writable by a request regardless of whether it came from the Secure or Non-Secure world. Non-Secure software could rewrite an unused region's ATTR to NONSEC and its range to overlap Secure DRAM, then access that DRAM directly — fully bypassing TrustZone. Marvell confirmed it also affects the OCTEON processor family and has since issued a fix; a CVE is pending.
Q7Does Sockeye require access to the chip's RTL or source at all?▾
No — that's the point. All 8 case studies were built from publicly available (mostly) or NDA-obtained (ThunderX-1) reference manuals, plus in most cases access to physical hardware boards for validating counterexamples, but never RTL.
Q8How does the induction proving actually work?▾
Three scenarios on the same spec: base_case shows a chosen invariant holds right after setup; inductive_step shows that if the invariant holds before any one step, it still holds after; invariant_is_useful shows the invariant implies the actual security property. If all three come back unsat, a human concludes by ordinary induction that the property holds after any number of steps.
Q9Why does Sockeye support multiple backends instead of just one?▾
Solver performance is notoriously sensitive to encoding details, and the paper's own measurements (Tables 2–3) show Rosette usually, but not always, beats CBMC — jetson's bug scenario runs faster on CBMC. Running several backends in a portfolio, and treating agreement between them as informal cross-validation of the tools, is more robust than betting on one.
Q10What does Sockeye's own analysis still assume, and where can it be wrong?▾
§4 lists the chain explicitly: the manual must actually describe the hardware; the transcription into Sockeye must be accurate; unmodeled parts must be over-approximated soundly; omitted parts must not be security-critical; and the Sockeye compiler, its backends (Rosette, CBMC, the SMT solvers), and everything underneath must themselves be correct. A break anywhere in that chain can make a bug or proof not hold in the real world.
Q11What can't Sockeye currently find or express?▾
It has no liveness properties ("something good eventually happens"), no loops (so some iterative behaviors are awkward to model), and concurrent behavior is possible but cumbersome to express faithfully (§6.3). It also can't detect the case where the manual is wrong in a way that happens to match a genuinely insecure implementation, but describes it as secure — the analysis is fundamentally bounded by the documentation it's built from (§4.1).
Q12How long does it take a new user to become productive?▾
Per §7.4, most Sockeye specifications were written by bachelor's/master's students with little prior formal-methods or SoC experience, who were able to start modeling their own platform within a few weeks. All managed to find bugs and bugfixes; writing meaningful proofs took more experience, which is why fewer platforms have proofs (Table 3) than have bug-finding scenarios (Table 2).

Core terms
SockeyeThe paper's DSL and toolchain: one specification, checked by SMT-based backends for both bug-finding and unbounded proofs.
Module / instance / calleeA module is a blueprint; instances form a containment tree ("consists of"); callees are explicitly-wired dependencies to non-child instances ("depends on").
State<T> / Array<K,V>Sockeye's only two primitives for mutable state — a single value, or a large indexed collection (e.g. DRAM).
any<T>Nondeterministically ranges over every valid value of type T — Sockeye's tool for modeling ambiguity and underspecification.
assume / assertRestriction / proof obligation. The solver seeks an assignment satisfying every assume while violating some assert.
Base case / inductive step / usefulnessThe three-scenario pattern that turns a bounded check into an unbounded induction proof.
Hardware bug / documentation bug / config bugConfig bug: a configuration change prevents the exploit. Otherwise, tested on real hardware: hardware bug if it reproduces, documentation bug if it doesn't (Fig. 4).
Over-approximationModeling an unmodeled part so it permits at least every real behavior — keeps bug-finding sound at the cost of possible false positives.
Supporting terms
ASC (Address Space Controller)The ThunderX-1's TrustZone-filtering unit for CPU↔DRAM requests, and the paper's running worked example.
RegionThe ASC's four configurable ranges, each with START, END, and ATTR ∈ {EMPTY, NONSEC, SEC}.
RosetteA Racket-based symbolic-execution language, backed by Z3, and Sockeye's primary verification backend.
CBMCA bounded model checker for C/C++, used as a second Sockeye backend for cross-validation.
Low-equivalenceTwo system states agreeing on every low-confidentiality (public) value, possibly differing on high-confidentiality (secret) ones — the basis of Sockeye's non-interference checks.
Air-gapped modelA structurally-separated reference model (e.g. per-process virtual memory) compared against a realistic, intertwined one to detect isolation bugs.
Monitor (in Sockeye's sense)A Sockeye-only wrapper interposed for analysis (e.g. around DRAM) that flags disallowed reads/writes — not a real hardware component.
havoc()Sets all of a module's state to arbitrary valid values, used before an inductive step to represent "any reachable prior state."

Related work, by contrast

Velosiraptor medium

Achermann, Chu, Mehri, Karimalis, Seltzer · ASPLOS 2025

Formalizes MMU semantics and synthesizes OS code to configure them — answers "what bits to write," while Sockeye answers "which regions need protecting in the first place."

Termite / Pancake medium

Ryzhyk et al. (SOSP 2009) / Zhao et al. (arXiv 2025)

Driver synthesis and verification for individual devices — lacks Sockeye's system-wide view of how devices interact across an SoC's interconnect.

Komodo, Cerberus, ProveriT, Arm CCA hard

Verified TEE monitors — Ferraiuolo et al. (SOSP'17); Lee et al. (CCS'22); Hu et al. (TDSC'24); Li et al. (OSDI'22)

Focus on the reference monitor itself and a single core, typically assuming memory isolation from other SoC components — Sockeye lets you formally verify that assumption.

Pensieve hard

Yang, Bourgeat, Lau, Yan · ISCA 2023

Same Rosette-based approach, aimed at microarchitectural side channels rather than direct-access confidentiality/integrity; hand-writes untyped Rosette, which Sockeye's typed DSL avoids.

Formalizing and validating Armv8 hard

Reid · FMCAD 2016 / OOPSLA 2017

A path to a functional spec for a single core's architectural behavior — a natural future integration point for Sockeye's SoC-level, cross-component modeling (§9).
