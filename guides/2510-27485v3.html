Turn a PDF manual into a solver's playground, not a guessing game

You can't get the RTL for a shipping SoC. You only get a thousand-page manual, written in prose, that may itself be wrong. Sockeye is a tiny language for turning that prose into something an SMT solver can attack — and prove safe.

1Why SoC security usually starts from a PDF, not source code▾

Modern SoCs run thousands of pages of reference-manual prose describing memory-mapped registers, interconnect firewalls, and secure-boot flows. Systems programmers configuring this hardware almost never get the RTL (the chip's actual source) — only the manual, which can be ambiguous, incomplete, or simply wrong.

That rules out most hardware-verification tools, which assume RTL access.

Now you're ready: Sockeye is built for exactly this situation — closed-source hardware, manual as the only ground truth.
2Arm TrustZone: two worlds sharing one chip▾

TrustZone splits execution into a Secure world (trusted firmware, key material) and a Non-Secure world (the regular OS, e.g. Linux). It's orthogonal to user/kernel/hypervisor privilege levels — a CPU can be Non-Secure and still run in kernel mode.

The hardware is supposed to enforce that Non-Secure code can never read or write Secure memory. Sockeye's running example is built entirely around checking exactly this.

Now you're ready: most of the paper's bugs are "Non-Secure code could touch Secure memory" in one disguise or another.
3Region-based protection units — one recurring pattern▾

Across very different SoCs, the same idea recurs: a small set of hardware regions, each with a START address, an END address, and an attribute (who may access it). A request is allowed if it falls in some region whose attribute permits the requester. The paper calls this device an ASC (Address Space Controller) on the ThunderX-1, and equivalent units — XMPU, AP registers, MPU — appear on most of the platforms studied. Not all, though: a few case studies, like AMD Ryzen/SMM's instruction-pointer-range protection and the STM32's read-out-protection/mass-erase mechanism, aren't naturally this region-check shape.

Now you're ready: once you understand one region-checking unit, you understand the shape of most of the bugs in this paper — though not every one.
4Bug-finding vs. formal proof — and why neither alone is enough▾

A bug-finder (fuzzer, static analyzer) can show you a bug but never that there are no more — an endless "whac-a-mole." A proof assistant can show absence of a whole class of bugs, but popular ones (Dafny, Verus, Rocq) don't produce counterexamples, so non-experts can't easily tell what the proof actually rules out.

Now you're ready: Sockeye's pitch is doing both from one model, so a found bug and a proof are directly comparable — if you can't insert a known bug and have the tool catch it, you shouldn't trust the proof.
5SMT solving and symbolic execution, in one sentence▾

Instead of running a program on one concrete input, symbolic execution runs it on a placeholder variable representing "any possible value," collecting the constraints that input must satisfy to reach each branch. An SMT solver (Sockeye uses Z3, via Rosette) then checks whether some combination of inputs exists that satisfies all constraints — i.e. whether a bug is reachable at all.

Now you're ready: this is literally what happens when Sockeye runs a scenario — it isn't simulating one run, it's searching over every run.
6A counterexample is a trace, not just "failed"▾

When the solver finds that a property can be violated ("SAT"), it returns a concrete assignment for every symbolic choice. Sockeye replays that assignment through its interpreter, producing an exact sequence of requests and register writes that triggers the bug — something you can literally try on real hardware.

Now you're ready: §2.6–2.7 of the paper walks through exactly this — a two-line printf trace that is the entire exploit.
7Underspecification: the any<T> escape hatch▾

Manuals are often silent or ambiguous about edge cases. Sockeye lets you write any<T> to mean "some valid value of type T, don't assume which" — a sound over-approximation. As long as the real hardware's actual behavior is one of the behaviors any permits, a proof that holds under any holds for the real hardware too.

Now you're ready: any is how Sockeye stays honest about what the manual didn't say, instead of silently guessing.
8Induction proofs: a base case plus one preserved step▾

Checking a property after 2 or 3 steps only proves it for 2 or 3 steps. To prove it holds forever, Sockeye uses induction: find an invariant that (a) holds right after setup (base case), and (b) if it holds before any single step, still holds after that step (inductive step, starting from a fully arbitrary — "havoc'd" — state). Together, these imply the invariant holds at every point in every execution.

Now you're ready: this is the only way the paper turns a bounded bug-finding scenario into an unbounded security proof.
The whole story in one place

Sockeye in a nutshell

What problem it solves, how one DSL does both jobs, and what it actually found.

Systems programmers configure security-critical hardware — TrustZone regions, SMM protections, interconnect firewalls — based on reference manuals, because the RTL is closed-source. Bugs can hide in three places: the hardware itself may be flawed, the manual may misdescribe the hardware or be ambiguous, or the software configuring it may misinterpret a correct manual. No existing tool addresses all three without RTL access.

Sockeye is a domain-specific language in which you transcribe a manual's access-control logic as a graph of stateful modules (registers, regions, DMA engines), write the system software that configures them in the same language, and state the desired security property (e.g. "Non-Secure code can never modify Secure memory"). The same specification compiles to two kinds of analysis: bug-finding via symbolic execution (did the solver find a way to violate the property within N steps?) and proof via induction (does an invariant hold forever?).

Applied to eight real SoCs — from a 48-core ARM server chip to a $1 microcontroller — Sockeye found documentation errors, reproduced two previously-known hardware bugs, and uncovered a previously-unknown vulnerability in the Marvell ThunderX-1's Address Space Controller: the registers that gate which memory regions the Non-Secure world may access are themselves writable from the Non-Secure world. Marvell confirmed it also affects their shipping OCTEON family. On the proof side, Sockeye established four memory-isolation proofs across three platforms — entirely via SMT solvers, with no interactive proof code beyond stating the invariant.

🍯 Key takeaways

  • Sockeye targets exactly the gap bug-finders and proof assistants each leave open: no RTL, needs both counterexamples and proofs.
  • One DSL expresses hardware state, configuration software, and security properties — all as module graphs and function bodies with no loops.
  • any<T> gives sound over-approximation for whatever the manual left ambiguous, instead of silent guessing.
  • A found violation ("SAT") is a concrete, replayable trace — testable on real hardware to separate documentation bugs from hardware bugs.
  • Proofs are three automatic SMT checks (base case, inductive step, invariant-implies-property) plus one manual reasoning step a human combines.
  • Backends: Rosette (symbolic execution over Z3) and CBMC (bounded C model checking) — run in parallel as a performance portfolio.
  • Result: 8 platforms modeled, a real ThunderX-1/OCTEON vulnerability found and fixed, 4 isolation proofs completed.
Six everyday pictures

How to think about Sockeye

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · Transcription

Translating a contract, clause by clause

A legal contract written in dense prose can hide ambiguity a lawyer would miss on a skim. Sockeye is like forcing a precise, formal translation of just the access-control clauses of the manual — every "may," "shall," and silently-assumed exception has to become an exact boolean expression before you can reason about it.

Where it breaks: a legal translation still trusts the original contract is the final word. Sockeye's proof is only as good as the manual — if the manual is wrong and the hardware disagrees, the translation is faithfully wrong too (§4, assumption 1).
Bug-finding · SMT search

A locksmith trying every master key

Rather than picking a lock by hand, a locksmith with a full bitting key chart can systematically try every combination that fits the lock's tolerances. Rosette and Z3 do the same to a Sockeye scenario: instead of guessing one test input, they symbolically explore every path and solve for an input combination that unlocks (violates) the stated property — and hand back the exact key that worked.

Where it breaks: the "lock" here is only the Sockeye model, not the physical chip. A key that opens the model must still be tested on real hardware to confirm it opens the actual lock (§4.1's "unsat/sat → real hardware" step).
Proof · Induction

A row of dominoes, proven by two facts

You don't need to watch all thousand dominoes fall to know they will — you just need to know the first one falls (base case) and that any falling domino knocks over the next (inductive step). Sockeye's base_case and inductive_step scenarios are exactly these two SMT checks; together they imply the invariant holds at every step, forever, without ever running the system that long.

Where it breaks: dominoes only need spacing checked once; Sockeye's inductive step must hold from a fully arbitrary (havoc'd) starting state, not just the one reached by the base case — a stronger, more careful claim than "the chain I built falls."
Underspecification · any<T>

A form with honest "TBD" boxes

When a form has a field you genuinely don't know, writing a guess is worse than writing "TBD — could be anything in this range." Sockeye's any<T> is the formal version: wherever the manual is silent or ambiguous, the spec says "assume nothing except the type," and the solver must consider every possibility. If a property still holds under every possible TBD value, it holds regardless of what the real hardware actually does there.

Where it breaks: over-using any everywhere makes properties too weak to prove (the solver can always pick the worst case) — precision has to go exactly where the manual is precise, and any only where it genuinely isn't (§3, §7.1).
Classification · Doc bug vs HW bug

A building inspector reading blueprints on site

If an inspector finds a wall isn't where the blueprint says, the question is: is the blueprint wrong, or did the builder deviate? Sockeye hits the same fork for every counterexample: it tests the exact exploit on real hardware. If the hardware behaves as the spec (and manual) said — it's a real hardware bug. If the hardware disagrees with the manual — it's a documentation bug, and the spec gets corrected.

Where it breaks: this only resolves cases where Sockeye finds a counterexample. If the spec says "safe" but the manual itself is wrong about safe hardware behavior, Sockeye has no inspector to call — that failure mode needs RTL-level tools or fuzzing instead (§4.1).
Non-interference · Air-gapped twins

Running two radios side by side

To prove one channel can't leak into another, engineers sometimes run a "clean" air-gapped reference system next to the real one, feed both the same inputs, and compare outputs — any divergence must come from unwanted coupling. Sockeye does this for isolation proofs: it runs a realistic, intertwined-state model alongside an obviously-separated "spec" model with the same schedule and inputs, and asserts they behave identically — any mismatch exposes an isolation bug.

Where it breaks: building the "obviously separate" twin model is itself extra transcription work, and the comparison can only catch divergences the chosen inputs/schedule actually exercise — it's not literally exhaustive over timing (§4.2.6, §6.3's note on concurrency).
The full explanation

How it actually works

From the module graph to the five ways of stating a property, with the paper's own ThunderX-1 example traced through.

1 · A platform is a graph of modules

A module is a blueprint for a component — anything from a single register to an entire SoC. Modules contain instances of child modules (a "consists-of" relationship) and callees, references to non-child instances that must be wired up by an ancestor (a "depends-on" relationship). Main is the one root module, instantiated exactly once; its top-level functions are the entry points for every bug-finding or proof scenario.

2 · State lives only in two primitives

Sockeye has no mutable variables of its own — just two built-in stateful modules: State<T>(init) holds one value of type T, and Array<K,V> indexes V by K, with an efficient sparse representation so a conceptually 16 GB array costs nothing until it's actually touched. Everything else — requests, responses, access decisions — is an ordinary function over this state, with no loops (every scenario completes in a bounded number of steps).

3 · Memory requests are just function calls

Where real hardware sends bits over wires, Sockeye models a request as a call and a response as a return value. The CPU builds a Request record (address, value, is_write, is_secure) and calls the ASC's request() function, which checks whether the address is a region-configuration register or a DRAM address, checks permissions, and forwards accordingly:

mut fn request(r: Request) -> Response {
  if is_region_config_addr(r.address) {
    asc_region_request(r)            // read/write START,END,ATTR
  } else if is_allowed_dram_addr(r) {
    dram_request(r)                   // forward to DRAM
  } else { { ok: false, value: any } }
}
⚠
The bug lives in the first branch. On the real ThunderX-1, is_region_config_addr(r.address) alone gates access to the region registers — with no check on r.is_secure. Any requester, Secure or not, can rewrite a region's START/END/ATTR. That single missing conjunct is the entire vulnerability (§2.3–2.7).

4 · Five ways to state a security property

Sockeye doesn't have quantifiers (∀/∃) — deliberately, to keep solving tractable — so properties are built from five recurring patterns, each usable with the solver's any, assume, and assert:

PatternWhat it checksCatches
Direct access-checkre-run the ASC's own allow-function after stepsstale/corrupted policy state
Snapshot diffcompare memory before/after N steps at an adversarial addressunauthorized writes
Monitora wrapper around DRAM that flags any disallowed accessunauthorized reads too (snapshots alone miss these)
Invariant preservationan always-true fact about config registers, proved by inductionprivilege escalation, for an unbounded number of steps
Non-interference (twins)two low-equivalent (or air-gapped) copies stay equivalentinformation leaks through shared/intertwined state

The any keyword simulates the missing ∀: to assert a property over "every address," you pick an adversarial test_addr with any<BitInt(31)> and let the solver search for the worst one. Assuming equivalence everywhere, however, needs the inverse trick — copying concrete values rather than comparing one sampled address (§2.9, §4.2, §4.2.5).

5 · Bug-finding: SAT, replay, classify

Rosette explores the scenario symbolically, accumulating one large SMT formula, and asks Z3 for an assignment that satisfies every assume and violates some assert. If Z3 finds one, Sockeye's interpreter re-runs the scenario with those concrete values substituted for every any, producing a human-readable trace (addresses, values, which assertion failed) — this is exactly how the ThunderX-1 exploit in the next tab was found.

6 · Proof: three checks, one inference the human makes

mut fn base_case() { setup(); assert(invariant()) }
mut fn inductive_step() {
  havoc();                 // start from a fully arbitrary state
  assume(invariant());
  step();
  assert(invariant())
}
mut fn invariant_is_useful() {
  havoc(); assume(invariant());
  // ...then show the invariant implies the real security property
}

If all three pass, a human combines them: base case + inductive step ⇒ invariant always holds; invariant ⇒ property ⇒ property always holds. Sockeye doesn't automate that final logical step, but the authors report it's a small fraction of review effort compared to finding the invariant itself (§7.2).

7 · Two backends, run as a portfolio

Rosette (Racket-based symbolic execution over Z3) and CBMC (a bounded C model checker, fed Sockeye-generated, memory-safe C) back every scenario. Neither dominates uniformly — see the runtimes in Worked Example ③ — so running both in parallel and cross-checking agreement is both a performance hedge and extra confidence: if two independent verifiers reach the same unsat/sat verdict, that's one less place a tooling bug could hide (§5, §4 assumption list).

🔗
If this sounds familiar: the region-based access pattern here — START/END/ATTR gating reads and writes by requester identity — is structurally the same shape as a CXL interconnect firewall or a memory-tiering controller's per-region access/migration policy. Sockeye's approach (formalize the manual, let a solver attack it) is a plausible tool for exactly that kind of platform-config verification in CXL-attached memory systems, though the paper itself doesn't study CXL.
Follow the numbers, step by step

Worked examples

Four traces through the paper's own data: the real exploit bytes, the bug taxonomy, solver runtimes, and the cost of modeling eight platforms.

① Decoding the real ThunderX-1 exploit trace

Sockeye's solver returned this trace (paper Listing 6, §2.7). What is it actually doing?

  1. First request: address 0x8000_0000_0070, is_secure:false, write, value 1. The base CONFIG_BASE = 1<<47 = 0x8000_0000_0000; the offset 0x70 = 0111_0000₂. Bits [6:5] = 11 → region_id = 3; bits [4:3] = 10 → register_id = 2 (ATTR). So this writes region3's ATTR register.
  2. The write succeeds because asc_region_request() only checks is_region_config_addr() — not r.is_secure — and value 1 (ATTR_NONSEC) passes the val ≤ 2 bounds check.
  3. Region3's range is 0..0 from setup_regions() (unused, ATTR_EMPTY originally) — so it now grants Non-Secure access to exactly address 0, which also falls inside region0's Secure range (0 .. 0xFF_FFFF).
  4. Second request: address 0, is_secure:false, write, value 0x48ad_c33c_fdc9_99d4. is_allowed_dram_addr() ORs across all four regions — region3 now says "yes," so the write to Secure memory succeeds.
  5. Two requests, one register write away from a Secure-memory compromise — exactly what test_secure_area_unchanged()'s two-step bound was built to catch.
🍯
Insight: the OR-across-regions logic is correct by itself; the vulnerability is that any region, including one the Non-Secure world controls, can grant overlapping access — a missing cross-cutting check, not a missing per-region check.

② The three-way bug taxonomy, with real cases

Sockeye's workflow (§4.1) classifies every counterexample. Three real outcomes from the eight case studies:

  1. Hardware bug — ThunderX-1 ASC (tx1): the missing is_secure check is confirmed present on real hardware; Marvell confirmed it also affects shipping OCTEON processors and issued a fix (§6.1, §2).
  2. Documentation bug — Raspberry Pi Pico 2 (pico): Sockeye's model, following the manual, found that a privileged-but-Non-Secure core could set the DMA engine's security level. Testing on a real Pico 2 showed Non-Secure writes to that register are silently ignored — the manual was wrong, the hardware was fine (§6.1).
  3. Consistent-with-documentation behavior — STM32H753 (stm): Sockeye rediscovers the known read-out-protection mass-erase erratum; this one isn't a new finding, but confirms the model matches both manual and known errata (§6.1).
💡
Only the "test on real hardware" step — not the solver — can tell these apart. The solver's job stops at "here's a trace that violates the property in this spec."

③ Reading the solver-runtime table — backends are not interchangeable

From Table 2 (bug scenarios, seconds), picking out the spread:

  1. pico: Rosette finds the bug in 6.4s; CBMC takes 738.1s — over 100× slower on the same spec.
  2. tx1: similarly lopsided — Rosette 1.2s, CBMC 64.4s.
  3. omap: the rare reversal — Rosette 74.3s, CBMC 19.7s, CBMC actually faster.
  4. ryzen and aspeed: CBMC times out entirely (>900s) on both; Rosette still finds the bug in 30.0s and 542.4s respectively.
  5. zynq's restricted search: the general scenario times out, but fixing the DMA channel to one specific one finds the bug in under 2 minutes, and additionally fixing the step to "CPU initiates DMA" brings it under 20s (§7.3).
🍯
Insight: no single backend wins consistently, which is exactly the justification for running both as a portfolio — and for letting users trade generality for speed by constraining nondeterministic choices when a search times out.

④ What eight platforms actually cost to model

From Table 1 (lines of code: S = spec, V = scenarios, T = total):

  1. Smallest: pico — S 1096, V 450, T 1546 lines. Highest scenario-to-spec ratio (V/S ≈ 0.41) — small chip, but two separate hard proofs (DMA, TrustZone) pulled V up.

Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
Sockeye finds a counterexample (SAT) to a security property on a platform spec. Does that alone tell you the real chip is vulnerable?
Show answer
No. SAT only means the spec violates the property — which could be a true hardware bug, a documentation bug (manual says something the real chip doesn't do), or a bug the authors inserted/introduced in transcription. You must replay the concrete trace on real hardware to find out which.Misconception: that a solver's counterexample is automatically a real-world exploit. It's a claim about the model, pending confirmation (§4.1).
Problem 2 · easy
Why can't Sockeye just run a bug-finding scenario for 1000 steps and call that "proof enough"?
Show answer
Because it would only establish the property for executions up to 1000 steps — it says nothing about step 1001, let alone an unbounded run. A real guarantee needs induction: a base case plus an inductive step shown to hold from any arbitrary (havoc'd) state, which together cover every reachable state at every step forever.Misconception: that more bounded steps ≈ a proof. No finite bound is a proof; only induction generalizes to "forever" (§2.9).
Problem 3 · medium
In the ThunderX-1 exploit, decode the region register address from the formula a = CONFIG_BASE + (0⁴¹ ## region_id ## 0⁵) for region_id = 2, register_id's bits coming from address[4:3]. What address writes region2's END register (register_id = 1)?
Show answer
CONFIG_BASE = 0x8000_0000_0000. region_id=2 → bits[6:5]="10". register_id=1 (END) → bits[4:3]="01". Combined low bits: 10_01_000₂ = 0x48. So the address is 0x8000_0000_0048.Misconception: that these addresses are picked by the attacker arbitrarily. They're exactly determined by the ASC's own bit-decoding logic — the solver found them, it didn't need to be told them.
Problem 4 · hard
Why does test_secure_area_unchanged() use two calls to miniTX1.step(), rather than one or ten?
Show answer
Two is the minimum needed to express this particular attack: step 1 reconfigures region3's ATTR (a Non-Secure-permitted write to a config register), step 2 exploits the now-widened region3 to write Secure memory. One step isn't enough to both reconfigure and exploit; more steps would work too but needlessly inflate the search space the solver must explore. In general, a bug-finding search tries increasing step counts until it either finds a violation or the search becomes too expensive.Misconception: that the step count is some fixed required parameter of Sockeye. It's a search-depth choice — "two" is a minimal demonstration, not a Sockeye requirement (§2.5).
Problem 5 · medium
A snapshot-diff property (compare DRAM before/after N steps) was used to catch the ThunderX-1 write bug. Would the same property catch an attacker who only reads Secure DRAM without writing it?
Show answer
No. A snapshot diff only detects changes in memory contents — an unauthorized read leaves the contents untouched, so before/after snapshots would be identical and the assertion would pass even though confidentiality was violated. You need the "monitor" pattern instead: a wrapper around DRAM that flags any disallowed access (read or write) as it happens.Misconception: that snapshot-diff is a general-purpose security check. It only expresses integrity (no unauthorized writes), not confidentiality (no unauthorized reads) — §4.2.3 exists specifically to fix this gap.
Problem 6 · medium
Why does inductive_step() call havoc() before assuming the invariant, instead of just continuing from wherever base_case() left off?
Show answer
Induction must show the step is preserved from any state satisfying the invariant, not just the one specific state reached after setup. havoc() sets every piece of state to an arbitrary value, then assume(invariant()) restricts the search to exactly the (potentially huge) set of states where the invariant holds — covering every invariant-satisfying state, including states that might not actually be reachable by any real execution, which is a stronger, more careful check than restricting to only the base case's path.Misconception: that proving "step 1 → step 2 preserves X" for one concrete trace is the inductive step. It must hold for every invariant-satisfying state, which is why havoc + assume is necessary (§2.9, Listing 7).
Problem 7 · hard
Sockeye's language deliberately has no ∀/∃ quantifiers and no loops. What's the tradeoff, and how does any partially compensate?
Show answer
Quantifiers and loops make SMT queries dramatically harder (or undecidable) to solve efficiently — Sockeye trades expressiveness for solver tractability. any<T> can emulate a single existential/universal check (e.g. "there's an address where before≠after" via one adversarially-chosen any address), but it can't directly express "for all addresses, assume they're equal" — that needs a workaround (copying concrete values in an assume_low_equiv helper) rather than a true universal assumption.Misconception: that any is a full substitute for quantifiers. It emulates existentials naturally (for assert) but needs a manual workaround to emulate a universal assumption (§4.2.5, "Working without quantifiers").
Problem 8 · easy
Rosette usually beats CBMC on Sockeye scenarios, but not always — omap is a counterexample where CBMC (19.7s) beats Rosette (74.3s). What should a user do when a backend times out?
Show answer
Run both backends as a portfolio rather than committing to one, and if a search times out, restrict the nondeterministic choices (e.g. fix a specific DMA channel, fix which component steps) to shrink the search space — as was done for zynq, cutting runtime from a timeout to under 20 seconds.Misconception: that one backend is strictly "the fast one." Relative performance flips per-platform, which is the paper's stated reason for supporting a portfolio of backends (§5, §7.3).
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1Does Sockeye need the chip's RTL source code?▾
No — that's the whole point. Sockeye is built for closed-source hardware where only a reference manual (and maybe a physical board) is available. The tradeoff is that its guarantees are only as strong as the manual's accuracy, which is why the workflow always ends with testing a counterexample on real hardware when possible.
Q2Is Sockeye a replacement for fuzzing or for interactive theorem provers?▾
Neither — it sits between them. Fuzzers find bugs but never prove absence; theorem provers (Dafny, Verus, Rocq) prove things but usually can't produce counterexamples for non-experts to sanity-check. Sockeye does both bug-finding and induction proofs from one spec, specifically so a found/inserted bug can validate that a proof actually excludes it.
Q3What's the difference between a "documentation bug" and a "hardware bug" in this paper?▾
Both start as a Sockeye counterexample. If testing the exploit on real hardware reproduces the violation, it's a hardware bug (the manual was faithful, the silicon is unsafe — e.g. ThunderX-1's ASC). If the real hardware doesn't reproduce it, the manual misdescribed the hardware — a documentation bug (e.g. the Pico 2's DMA security-level register).
Q4What exactly was the ThunderX-1 vulnerability?▾
The Address Space Controller's region-configuration registers (START/END/ATTR for each of 4 regions) were writable regardless of whether the requester was Secure or Non-Secure — only the address range, not the security mode, gated access. A Non-Secure actor could widen an unused region to overlap Secure DRAM, then write through it. Marvell confirmed it also affects their OCTEON family and issued a fix; a CVE was pending at publication.
Q5Why doesn't Sockeye support loops or quantifiers?▾
Both make SMT solving dramatically slower or undecidable. Dropping them keeps every scenario a bounded sequence of calls with branching, which Rosette and CBMC handle efficiently; the paper's third backend, direct SMT, is described as "considerably less complete and performant than Rosette or CBMC," and only Rosette/CBMC runtimes are reported in the paper's tables. The paper argues this restriction hasn't prevented expressing the security properties they needed (§3, §7.2).
Q6How does any<T> keep a proof sound if it hides real behavior?▾
any<T> is an over-approximation: it allows every possible value of type T, a superset of whatever the real hardware actually does in that spot. If a property holds for every value any permits, it necessarily holds for whichever one value the real hardware picks — soundness is preserved by over-, not under-, approximating.
Q7Why run both Rosette and CBMC instead of picking the faster one?▾
Neither backend is uniformly faster — Rosette usually wins (sometimes dramatically, e.g. pico at 6.4s vs 738.1s) but CBMC beats it on omap (19.7s vs 74.3s), and CBMC can't handle Sockeye's symbolic sparse arrays or bit-widths over 64 at all on some platforms (zynq, stm). Running both is a performance hedge and lets independent agreement increase trust in a verdict.
Q8Can Sockeye model true hardware concurrency?▾
Not comfortably yet. Requests are modeled as atomic function calls that run to completion before the next one starts, even though the top-level step() can nondeterministically pick which component acts next. The authors describe this as cumbersome for genuinely concurrent behavior and list DSL extensions for it as future work (§6.3, §9).
Q9Who actually writes these specs, and how long does it take?▾
Mostly bachelor's and master's students with little prior formal-methods or SoC experience, as part of individual research projects. With guidance, they began modeling their platform within a few weeks; the main bottleneck reported was understanding each manual's ambiguities, not learning the Sockeye language itself (§7.4).
Q10What can't Sockeye do yet?▾
No liveness properties ("something good eventually happens"), no comfortable concurrency modeling, and if a proof says "safe" but the manual itself misdescribes genuinely unsafe hardware, Sockeye has no mechanism to catch that — it would need RTL-level tools or hardware fuzzing instead. Future work also mentions LLM-assisted spec generation from manuals and SMT/ISA-spec integration (§4.1, §9).

Core terms
SockeyeThe paper's DSL + toolchain: one language for hardware state, config software, and security properties, with bug-finding and proof backends.
Module / instance / calleeA module is a blueprint; instances form the "consists-of" tree; callees are "depends-on" references wired by an ancestor.
State<T> / Array<K,V>Sockeye's two built-in primitives for mutable state — a single value, or a sparsely-represented indexed collection.
any<T>Nondeterministic choice of any valid value of type T — used for sound over-approximation of underspecified manual behavior.
assume / assertVerification-time restrictions and proof obligations over boolean expressions; the solver finds a counterexample violating an assert while satisfying all assumes.
SAT / UNSATSolver verdicts: SAT means a violating assignment exists (a bug found); UNSAT means none exists within the bound checked.
Base case / inductive stepThe two SMT checks that together prove an invariant holds forever — base case at setup, inductive step from any havoc'd invariant-satisfying state.
HavocSetting every piece of state to an arbitrary value; combined with the following assume(invariant()), it restricts the search to every invariant-satisfying state — including ones that might not actually be reachable — which is what makes the inductive step's guarantee strong.
Supporting terms
ASCAddress Space Controller — the ThunderX-1's region-based memory firewall; the paper's running example and site of its found vulnerability.
TrustZoneArm's Secure/Non-Secure world isolation mechanism, orthogonal to privilege level; the security goal behind most of the paper's properties.
RosetteA Racket-based symbolic-execution language over the Z3 SMT solver; Sockeye's primary, usually-fastest backend.
CBMCA bounded model checker for C/C++; Sockeye's second backend, fed generated, memory-safe C code.
Z3The underlying SMT solver both Rosette and Sockeye's direct-SMT backend ultimately query.
DMADirect Memory Access — device-initiated memory access that can bypass CPU-side checks; a recurring source of bugs (aspeed NIC, pico, omap, zynq).
Config bug vs hardware bug vs documentation bugSockeye's three-way classification of a found violation, resolved by re-testing on real hardware.
Low-equivalenceTwo system states agreeing on all low-confidentiality data, possibly differing on high-confidentiality data — the setup for non-interference checks.

Velosiraptor: Code Synthesis for Memory Translation medium

Achermann, Chu, Mehri, Karimalis, Seltzer · ASPLOS 2025

Formalizes MMU semantics and synthesizes OS code to configure them — answers "what bits to write," complementary to Sockeye's "which regions need protecting."

Physical Addressing on Real Hardware in Isabelle/HOL hard

Achermann, Humbel, Cock, Roscoe · ITP 2018

Introduced "decoding nets," a static address-translation model; Sockeye's dynamic module graph extends this to runtime-updatable state.

Komodo: Disentangling Secure-Enclave Hardware from Software hard

Ferraiuolo, Baumann, Hawblitzel, Parno · SOSP 2017

Verified TEE reference monitor; assumes memory-region integrity/confidentiality as a given — the kind of assumption Sockeye's proofs aim to formally establish (though the paper's ThunderX-1 induction proof targets the ZIP compression accelerator, not the ASC itself; a proof about the ASC appears only as a simplified running example assuming a hypothetical fix).

Pensieve: Microarchitectural Modeling for Security Evaluation hard

Yang, Bourgeat, Lau, Yan · ISCA 2023

Also builds on Rosette for symbolic hardware security analysis; Sockeye argues its typed DSL avoids the debugging overhead of Pensieve's untyped Rosette code.

AMD Sinkclose: Universal SMM Privilege Escalation medium

Nissim, Okupski · DEFCON 32, 2024

The real-world x86 SMM vulnerability Sockeye's ryzen model reproduces as a property of the architectural instruction pointer.
