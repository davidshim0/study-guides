HotStorage 2026 · A Field Guide

Let the tenant's label pick the reclaim unit, not the application

An FDP SSD can erase similar-lifetime data together — if someone tells it which writes are similar. Today only direct-I/O apps can tell it anything. io.stream makes the cgroup do the telling for the otherwise-unplaced writes the application never tagged, unmodified.

📄 "io.stream: cgroup-Granular FDP for Unmodified Workloads" · Son, Kim, Lee 🎓 Tiering/CXL background assumed — storage primers cover the rest ⏱ ~25 min read
🏷️

Place writes by the tenant boundary the cgroup already marks, not by whether the app bothered to tag the I/O.
A cgroup is an ownership/deployment boundary, not data lifetime itself — only a macro-level proxy. Coherence of the mapping, not the count of streams, is what buys write amplification.

Before you begin

Quick glossary, then six ideas the paper assumes

Acronyms first so nothing downstream is opaque; then primers you can open selectively.

Quick glossary — the acronyms you'll see everywhere

FDPFlexible Data Placement — NVMe feature letting the host steer writes into separate device-managed erase regions.
RUHReclaim Unit Handle — the identifier a host references in a write directive; the device's PM9D3a exposes 8.
RU / RGReclaim Unit (region erased together) / Reclaim Group (a pool of RUs).
WAFWrite Amplification Factor — media bytes written ÷ host bytes written. 1.0 is optimal; the paper's central metric.
OPOver-provisioning — spare device capacity reserved to absorb garbage collection; set to 7% in this paper's setup.
GCGarbage Collection — relocating surviving valid data out of an erase unit before wiping it; the source of WA.
blkcgThe block-layer cgroup object every bio is tagged with — the carrier io.stream reuses.
io_uringThe async I/O interface currently used to attach a write stream to one direct I/O, app by app.
jbd2 / CILext4's jbd2 journal thread runs in the root cgroup and falls to the device default; xfs's CIL and in-place metadata updates behave differently — the paper is explicit only about jbd2.
hot, short-lived tenant data (RocksDB, Postgres) cold, long-lived tenant data / coherent mapping io.stream / cgroup machinery FDP-default / incoherent mapping (the baseline)
1Why flash needs GC, and what WA costs you▾

NAND can't be overwritten in place — a block must be erased before rewriting. Erase units hold many pages; if even one page in a unit is still live, the whole unit must have its survivors copied elsewhere before it can be wiped. That copying is write amplification: every host byte becomes more than one media byte.

Now you're ready: everything in this paper is in service of one number — WAF — and the lever is deciding which data shares an erase unit.
2FDP: letting the host pick the erase unit▾

FDP exposes Reclaim Unit Handles the host can target with a placement identifier on a write. If the host routes same-lifetime writes to the same RUH, that RU empties as a block with little to relocate — WAF→1. Unlike ZNS, FDP is advisory and backward-compatible: an FDP drive still behaves like an ordinary block device.

Now you're ready: FDP gives you the knob; the open question this paper tackles is who turns it, for writes that never explicitly ask.
3Linux write streams — and their current gap▾

The block layer added a per-bio write-stream field that the NVMe driver maps to an FDP placement id. Today the only producer is user space, via an io_uring per-I/O attribute on direct I/O — there's no in-kernel producer for writeback or the iomap path without application cooperation. Buffered writes and ordinary file-system I/O leave the field unset and fall to the device default.

Now you're ready: this gap — buffered I/O has no stream producer — is exactly what io.stream fills.
4cgroup v2's I/O controller and blkcg▾

cgroup v2's io controller already throttles and prioritizes per-cgroup bandwidth (io.weight, io.max, io.latency). Every bio submitted carries a reference to its issuing cgroup's blkcg — that's how those knobs get enforced. io.stream adds a new knob to this same mechanism.

Now you're ready: io.stream isn't a new subsystem — it's one more file in a controller that already touches every write.
5Why buffered writes still carry a cgroup label▾

A buffered write dirties a page in the page cache and returns immediately; a kernel flusher thread writes it back later. You'd expect that shared kworker's I/O to be "nobody's." But cgroup writeback specifically attributes each flushed page back to the owning cgroup's blkcg, not the flusher thread — so the label survives exactly the hop that per-I/O tagging can't reach.

Now you're ready: this one kernel behavior is the paper's entire insight — the signal io.stream needs is already there on the buffered path.
6How WAF is actually measured▾

WAF = media bytes written ÷ host bytes written, read from drive-reported SMART and OCP log pages over a steady-state window (after preconditioning the drive full, so GC is active rather than idling on fresh media). Lower is strictly better; 1.0 is the floor.

Now you're ready: every number in the Worked Examples tab is this one ratio, measured the same way across arms.
The whole story in one place

io.stream in a nutshell

The gap, the reused signal that closes it, and why the mapping matters more than the mechanism.

FDP can drive write amplification toward 1.0 by grouping similar-lifetime writes into the same reclaim unit — but only for I/O that carries a placement hint. Linux's current hint producer is a per-I/O io_uring attribute on direct I/O, so buffered writes and ordinary file-system traffic — most of what real deployments actually run — fall through to the device default and, in the unmodified stack, get none of FDP's placement benefit. (FDP-default is still an FDP-mode baseline, though, and the paper notes it can differ slightly from No-FDP on file systems.)

The paper's fix doesn't add a new hint producer inside the application. It reuses one that's already running everywhere: the cgroup. Every data-write bio, including a page-cache flush performed by a shared kernel flusher thread under cgroup writeback, is already stamped with the owning tenant's blkcg — not the thread that happens to perform the I/O. io.stream is a new cgroup v2 file that lets an operator assign a block-layer write stream to that cgroup; a one-line submit-path hook then stamps every otherwise-unplaced write from that cgroup with its stream, on any I/O path, with zero application changes.

A strict precedence keeps it safe: an application that already expressed a stream via io_uring — including an explicit "use the default" — always wins; io.stream only fills in writes that said nothing. Unclassified cgroups fall through to the device default, never onto another tenant's stream.

The payoff: two isolated tenants reach WAF 1.0 on raw, ext4, and xfs — down from 1.50–1.65 at FDP-default, ~39% less media traffic. But the paper's sharper finding is about scarcity: when 14 cgroups share 7 streams, a coherent two-group mapping holds WAF at 1.00, while a lifetime-oblivious hash across all 7 streams reaches 2.36 — worse than not using FDP at all (1.62). Coherence, not stream count, is the lever.

🍯 Key takeaways

  • Per-I/O streams only reach direct I/O; io.stream reaches buffered/writeback I/O by reusing the cgroup label already on every bio.
  • Precedence sentinel (WRITE_STREAM_NONE) means io.stream is purely additive — an app's explicit stream always wins.
  • Unclassified cgroups fall back to the device default — never onto a wrong tenant's stream. Fallback, not hash.
  • ext4's jbd2 journal naturally lands at stream 0 since it runs in the root cgroup — isolation "for free," but with modest WAF impact alone; the paper cautions that xfs's CIL and in-place metadata behave differently.
  • What matters when cgroups outnumber streams is the coherence of the collapse, not how many streams are used.
  • ~300 lines, one predicated field write per bio, <1% IOPS/latency overhead.
Five everyday pictures

How to think about io.stream

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Address by tenant

Sorting mail by sender's building, not by letter

A mail room could open every envelope to decide where it goes — or just read the return address on the building. Tenants already have that building-level label (the cgroup); io.stream reads it once, at the loading dock, instead of asking every letter to carry its own sorting code.

Where it breaks: one building can house residents with very different mail habits — a single cgroup can mix a WAL and cold SSTables. The label is a deployment/ownership proxy, not a lifetime oracle.
Precedence · The sentinel

A sticky note beats the default greeting

If a caller leaves an explicit message, you act on it — even if that message is "just use the default," which is different from no message at all. Only when there's truly no explicit message do you check the sticky note left on the desk (the cgroup's assigned stream), and only then fall back to the standard voicemail.

Where it breaks: a person remembers "I already said 0"; the kernel needs a dedicated sentinel value (WRITE_STREAM_NONE, −1) distinct from the real default (0) to tell the two cases apart.
Scarcity · Coherent collapse

Seating a wedding with too few tables

Run out of tables and you must seat some guests together — the question is who. Seat the groom's rowdy cousins at one table and the quiet grandparents at another, and the dinner goes fine even with few tables. Seat them randomly, and every table has a conflict. io.stream's many-to-one collapse is picking tables by who gets along (lifetime), not by headcount.

Where it breaks: a host can watch body language and adjust; io.stream's mapping is set by the operator ahead of time from coarse knowledge, not observed in real time (a gap the paper leaves open).
Metadata · Falls through for free

The shared supply closet nobody claims

In a shared office, everyone's personal filing cabinet is labeled with a name — but the supply closet that everyone restocks has no owner. ext4's journaling thread (jbd2) works the same way: it runs outside any tenant's cgroup, so it falls to the root label and lands on the device default, automatically separated from any tenant that got a real stream.

Where it breaks: separating the unclaimed closet from labeled cabinets doesn't itself save much space — the paper measures this (Metadata-only ≈ FDP-default); the real savings come from sorting the cabinets, not isolating the closet. The paper is explicit about this for jbd2 only — it cautions that xfs's CIL and in-place metadata don't necessarily behave the same way.
Safety · Fallback, not hash

When unsure, merge into the general lane

A highway on-ramp with unlabeled traffic doesn't get randomly shuffled into one of the express lanes reserved for commuters who paid for them — it merges into the general lane. An unmapped cgroup likewise falls to the device default, never onto some other tenant's dedicated stream, so a naive or incomplete mapping can't actively hurt anyone else's placement.

Where it breaks: the general lane is still shared capacity — falling back doesn't improve that cgroup's own WAF, it just guarantees it can't corrupt a neighbor's isolation.
The full mechanism

How it actually works

From the unset bio field to a stamped FDP placement identifier.

1 · The gap on the buffered path

Linux's bio struct carries a write-stream field, and the NVMe driver maps it to an FDP placement identifier. The only producer today is user space, via an io_uring write attribute set per I/O on direct I/O — there is no in-kernel producer for writeback (the kernel's own dirty-page flusher) or the iomap file-system path without application cooperation, so those writes silently fall to the device's default stream.

2 · The interface — a per-device cgroup file

An operator writes maj:min stream into a cgroup's io.stream file. inherit (the default) adopts the parent cgroup's effective stream; writing 0 explicitly forces device-default placement for that cgroup; any other value is validated against that device's max_write_streams and rejected if out of range.

3 · Why metadata gets separated "for free"

A journaling thread like ext4's jbd2 runs in the root cgroup, not any tenant's — it has no explicit stream, so it falls through to stream 0 automatically. As long as every tenant cgroup is assigned a non-zero stream, journal traffic never mixes with tenant data on the same RU, with no file-system change. Its WAF effect alone is modest; the paper's Metadata-only control arm (tenants still sharing a stream, only the journal isolated) tracks FDP-default almost exactly (§4, Stage 1). The paper is explicit about this mechanism for ext4's jbd2 specifically; it cautions that xfs's CIL and in-place metadata updates behave differently and shouldn't be assumed to fall through the same way.

4 · Implementation and bio lifetime

~300 lines, almost entirely in block-cgroup code: a per-cgroup field in the io controller's policy data, the io.stream control file (validated against device limits, propagated down the hierarchy), and a one-line sentinel initialization. The submit-path hook is a single predicated field write after the bio is associated with its blkcg — no new fast-path allocation. A split bio inherits its parent's stream, and bios carrying different streams are never merged, so the assignment survives intact all the way to the NVMe driver.

5 · Mapping when cgroups outnumber streams

A device may expose only a handful of placement identifiers (8 here, 7 usable for tenant data) while hundreds of cgroups run concurrently. io.stream distinguishes a logical stream (what the operator assigns) from a physical stream (what the device offers) and supports direct pinning, opt-in many-to-one collapsing, and reserved identifiers for critical tenants — with the default overflow policy being fallback, never a hash, so an incomplete mapping cannot place one tenant onto another's stream.

Follow the numbers

Worked examples

Three traces from the paper's own evaluation, carried through to their conclusions.

① Stage 1 — isolating two tenants on raw, ext4, xfs

FDP-default WAF is 1.65 (raw), 1.53 (ext4), 1.61 (xfs). io.stream drives all three to 1.00. What does that save, and does it hold up under a file system?

  1. Raw savings: at WAF 1.65, writing 1 GB of host data costs 1.65 GB of media writes. At WAF 1.00 it costs 1.00 GB. Reduction = (1.65 − 1.00) / 1.65 ≈ 39% less media traffic for the same host writes.
  2. Raw and FDP-default coincide (1.65 both) — confirming the device default reproduces ordinary placement; the gain is from io.stream's assignment, not some FDP side effect.
  3. Metadata-only control (ext4/xfs): streaming both tenants together but isolating just the journal gives 1.53/1.61 — identical to FDP-default. Isolating metadata alone buys nothing; the win must come from separating tenant data.
  4. io.stream on ext4/xfs reaches the same 1.00 as raw, confirming the submit-path stamp survives the full VFS and writeback stack, not just direct I/O.
  5. Side effects: throughput rises 1.8× (raw), 1.4–1.7× (file systems); ext4 p99 latency falls from ~8.4 ms to 0.6 ms — removing GC work pays off beyond WAF alone.

② Stage 2 — 14 cgroups, 7 streams: coherence vs. count

7 hot + 7 cold cgroups must collide onto 7 streams one way or another. Five arms: FDP-default 1.62, Coherent 1.00, Fallback 1.07, Blind 1.30, Oblivious 2.36.

  1. Coherent uses only 2 streams — all hot on one, all cold on the other — and reaches the floor, 1.00. Sharing a stream isn't the problem; sharing it with the wrong neighbor is.
  2. Fallback pins the long-lived cold cgroups to dedicated streams and lets hot cgroups fall to the default (1.07) — isolating the slow-to-recycle data is what matters most for averting GC.
  3. Blind pins only 3 of 7 hot and 4 of 7 cold, letting the rest overflow — a partial, lifetime-mixed mapping gives back most of the gain (1.30).
  4. Oblivious hashes cgroup id across all 7 streams uniformly. Using every available stream, it still reaches 2.36 — worse than FDP-default's 1.62 — because hashing guarantees hot and cold co-locate somewhere.
  5. Takeaway: Coherent (2 streams, WAF 1.00) beats Oblivious (7 streams, WAF 2.36). The mapping's coherence, not its stream count, governs WAF.

③ Stage 3 — four unmodified containers on ext4

RocksDB + PostgreSQL (hot) and Kafka + MongoDB (cold) share one ext4 volume. One stream for all four: 1.70 (≈ FDP-default). Lifetime-coherent two streams {R,P}/{K,M}: 1.27. Per-app four streams: 1.23. Two lifetime-mixed two-stream pairings: 1.58 and 1.80.

  1. One stream (a): only the jbd2 journal is isolated; all tenant data still shares RUs → WAF stays near FDP-default (1.70).
  2. Coherent pairing {R,P}/{K,M} (b): two streams, hot grouped with hot, cold with cold → 1.27, closing most of the gap to full isolation.
  3. Per-app isolation (c): four streams, each container alone → 1.23. The coherent two-stream pairing (1.27) is within ~3% of this at half the streams.
  4. Mixed pairing {R,K}/{P,M} (b): co-locates one hot with one cold per stream → settles at 1.58, salvaging only part of the available gain.
  5. Mixed pairing {R,M}/{P,K} (b): the other mixed split climbs to 1.80 — worse than doing nothing (FDP-default 1.70) — once the mixed RUs accumulate enough churn to force reclaim.
💡
Same stream budget (two), same hardware, same workloads — only which containers share a stream differs. That's the whole experiment distilled to one variable.
Test yourself

Practice problems

Try before opening the answer. Each ends with the misconception it checks.

Problem 1 · easy
An app issues direct I/O entirely through io_uring and tags every write with a stream. Does io.stream do anything for this app's data writes?
Show answer
No — and that's by design. The precedence rule says an application-expressed stream (the bio's field is already a concrete value, not the WRITE_STREAM_NONE sentinel) always wins; io.stream only fills in writes that said nothing. This app has already said something for every write.Misconception: that io.stream overrides application intent. It is purely additive — it places exactly the writes the application left unplaced, nothing more.
Problem 2 · medium
A tenant writes 500 MB of host data under FDP-default (WAF 1.65) and under io.stream (WAF 1.00). How many fewer MB does the media actually receive?
Show answer
FDP-default: 500 × 1.65 = 825 MB written to media. io.stream: 500 × 1.00 = 500 MB. Difference = 325 MB, a reduction of 325/825 ≈ 39% — matching the paper's headline savings figure.Misconception: treating WAF as a small correction factor. A WAF of 1.65 means the device is doing 65% more physical writing than the host asked for — the gap compounds directly into endurance and OP headroom.
Problem 3 · hard
In Stage 2, Oblivious uses all 7 available streams and still reaches WAF 2.36 — worse than FDP-default's 1.62, which uses none. How can using more streams make things worse than using none?
Show answer
FDP-default sends everything to one device-default stream — a single, consistently mixed pool, which is how non-FDP systems already behave (WAF 1.65 on raw). Oblivious instead hashes cgroups across 7 separate reclaim units, but the hash ignores lifetime, so each of those 7 units ends up with its own careless mix of hot and cold data colliding together. Spreading writes across more streams without lifetime awareness doesn't avoid those collisions — it just multiplies where they happen, with no lifetime benefit to show for it.Misconception: that spreading data across more streams is inherently safer than using one. Spreading without coherence can multiply the places careless hot/cold collisions occur.
Problem 4 · medium
An application explicitly sets stream 0 via io_uring on a write (asking for the device default). That write's cgroup has io.stream assigned to 3. What stream does the write actually get, and why does the design distinguish this from a write that set no stream at all?
Show answer
Stream 0 — the application's explicit choice wins, even though it happens to equal the device default. The design needs a separate sentinel (WRITE_STREAM_NONE, −1) precisely to distinguish "I explicitly want the default" from "I expressed no preference," because only the latter should be eligible for the cgroup's stream (3) to fill in.Misconception: that "0" and "unset" are the same thing. Conflating them would let io.stream silently override an application's deliberate choice to use the default.
Problem 5 · medium
Stage 1's Metadata-only arm streams both tenants together but isolates only the ext4 journal, and lands at WAF 1.53 — identical to FDP-default. Why doesn't isolating the journal move the number?
Show answer
The journal (jbd2) is a small, separate stream of commit records — it's not where the bulk of write-amplifying churn happens. The tenants' actual data is still sharing reclaim units in this arm, so GC still has to relocate mixed hot/cold survivors exactly as before. Metadata isolation falls out "for free" from cgroup attribution, but it is not the mechanism that drives WAF down — tenant-data partitioning is.Misconception: that any FDP-based isolation helps proportionally. The paper uses this control specifically to rule out "it's just the journal" as the explanation for the main result.
Problem 6 · hard
Why does io.stream's overflow policy default to "fallback to device default" rather than "hash cgroup id to an available stream," given that hashing would at least spread load across more streams?
Show answer
Hashing has no notion of lifetime, so it can co-locate a hot and cold cgroup on the same stream purely by chance — and the paper's Oblivious arm shows this can perform worse than doing nothing (2.36 vs. 1.62). Fallback instead sends an unmapped cgroup to the one pool every non-FDP write already uses, which by construction cannot corrupt another tenant's dedicated, intentionally-assigned stream. It sacrifices that cgroup's own potential gain in exchange for a guarantee: an incomplete or naive mapping can never make another tenant's isolation worse.Misconception: that using more of the available streams is always progress. Without lifetime awareness behind the assignment, using more streams can actively hurt.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the actual difference from the existing io_uring stream attribute?▾
io_uring's attribute is per-I/O and application-set — it only reaches direct I/O the app explicitly tags. io.stream is per-cgroup and operator-set — it reaches buffered writes, writeback, and any file-system path, for writes the application never tagged at all. They compose: an app's explicit tag always takes precedence over the cgroup's.
Q2Does any application code need to change?▾
No. The paper evaluates unmodified RocksDB, PostgreSQL, Kafka, and MongoDB containers — placement is set purely by assigning each container's existing cgroup a stream via the io.stream file. No image, binary, or I/O engine change.
Q3How does a buffered write from a shared kernel flusher thread end up tagged with a specific tenant's stream?▾
cgroup writeback already attributes a flushed dirty page to the owning cgroup's blkcg rather than the kworker performing the flush. The submit-path hook just reads that existing attribution and stamps the bio's stream field from it — no new tracking is needed.
Q4What happens if two unrelated cgroups are assigned the same stream?▾
Their data shares a reclaim unit, same as FDP's general behavior. That's fine if their lifetimes are similar (a coherent collapse) and costly if they aren't (an incoherent one) — the paper's whole Stage 2/3 result is that this choice, not the number of streams in use, determines WAF.
Q5What happens to a cgroup that was never assigned a stream?▾
It falls through to the device's default stream — the same placement any write would get with no FDP support at all. It never lands on another tenant's dedicated stream, so an incomplete rollout can't actively harm an already-configured tenant.
Q6Does using more streams always lower WAF?▾
No — Stage 2's Oblivious arm uses all 7 available streams and reaches WAF 2.36, worse than FDP-default's 1.62 (no io.stream or per-I/O stream assigned — writes still take the device's default stream/placement). What lowers WAF is grouping similar lifetimes together, which can need as few as 2 streams (Coherent, WAF 1.00).
Q7How is journal/metadata traffic handled?▾
ext4's journaling thread (jbd2) runs in the root cgroup, not any tenant's, so it's unattributed and falls to the device-default stream automatically — separated from any tenant with a non-zero stream, with no file-system code change. The paper is explicit about this for jbd2; it cautions that xfs's CIL and in-place metadata updates behave differently and aren't claimed to fall through the same way. Either way, the WAF contribution of metadata isolation alone is modest — the larger gains come from partitioning tenant data.
Q8What's the runtime cost of io.stream?▾
One predicated field write per bio at submission time, no new fast-path allocation, and a split bio inherits its parent's stream unchanged. Measured IOPS and p99 latency deltas are under 1% versus the unmodified baseline.

Core terms
io.streamA new cgroup v2 io-controller file; an operator writes "maj:min stream" to assign a write stream to a cgroup for a given device.
Write streamA per-bio field in the Linux block layer that the NVMe driver maps to an FDP placement identifier.
Placement identifierAn FDP write directive: a reclaim group plus a placement handle, telling the device which RU to route a write's logical blocks into.
WRITE_STREAM_NONEThe sentinel value (−1) marking "no stream expressed," distinguished from an explicit request for stream 0.
Logical vs. physical streamLogical = what the operator assigns per cgroup; physical = the limited set the device actually offers. io.stream maps the former onto the latter.
Lifetime coherenceWhether a cgroup-to-stream mapping groups similar-lifetime data together. The paper's central finding: this, not stream count, governs WAF.
Fallback policyio.stream's default for unmapped/surplus cgroups: route to the device default, never onto another tenant's assigned stream.
