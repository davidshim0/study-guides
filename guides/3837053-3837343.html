HotStorage 2026 · A Field Guide

Giving each write a home by reading the name tag it already wears

An SSD can erase co-invalidated data together for free — if the host tells it which writes share a lifetime. Today only a rare, rewritten application can say so. This is the plain-English story of io.stream, which reads that answer off a label the kernel was stamping on every write anyway.

📄 "io.stream: cgroup-Granular FDP for Unmodified Workloads" · Son, Kim, Lee 🎓 cgroup v2 / block-layer basics assumed — primers cover them ⏱ ~25 min read
🏷️

Before you begin

Quick glossary, then eight ideas the paper assumes

Skim the acronyms first — you'll see them everywhere. Then the primers, in order the first time, or jump to whatever's unfamiliar.

Quick glossary

FDPFlexible Data Placement — NVMe feature letting the host steer writes into separate device reclaim units.
RUH / RU / RGReclaim Unit Handle (the thing you write to) / Reclaim Unit (region erased together) / Reclaim Group (a set of RUs).
WAFWrite-Amplification Factor — media bytes written ÷ host bytes written. 1.0 is optimal; the paper's central metric.
OPOver-provisioning — spare device capacity reserved to absorb garbage collection; costly, and what FDP aims to reduce.
GCGarbage collection — relocating still-valid data out of a reclaim unit before erasing it.
cgroup v2 / blkcgLinux's resource-control hierarchy; the block-I/O controller (blkcg) tags every bio with its owning cgroup.
bioThe kernel's basic block I/O request struct — now carries a write-stream field.
io_uringLinux's async I/O interface; currently the only way an application can set a per-I/O write stream, and only for direct I/O.
1Why flash needs erase-before-write, and what that costs▾

NAND flash can't be overwritten in place — a block must be erased before new data lands there. If an erase unit holds a mix of dead (overwritten) and live (still-needed) data, the device must copy the live survivors elsewhere before it can erase and reclaim the space. That extra copying is write amplification (WA): the media receives more bytes than the host ever sent.

Operators historically fight WA with over-provisioning (OP) — buying more flash than the user gets to use, purely as GC breathing room. It works, but it's capacity you paid for and cannot store data in.

Now you're ready: the whole paper is about avoiding that hidden extra copying without needing more OP.
2FDP — letting the host steer where writes land▾

An FDP-capable SSD exposes several Reclaim Unit Handles (RUHs), each pointing at a Reclaim Unit (RU) — a region erased as a whole. A write carries a placement identifier naming which RUH to use. If the host always sends data of similar lifetime to the same RUH, that RU becomes uniformly dead (or uniformly live) at once, so reclaiming it needs to relocate little or nothing — WA falls toward 1.0.

Unlike Zoned Namespaces, FDP is advisory: ignore it and the drive still behaves like an ordinary block device, so adoption is incremental.

Now you're ready: the entire mechanism is "tell the drive which writes belong together" — everything else is about who gets to say that, and how the answer reaches the drive.
3The block layer, the bio, and write streams▾

Every I/O request in Linux becomes a bio struct as it travels down through the block layer to the driver. Linux recently added a write-stream field to the bio, plus queue limits (max_write_streams) — the NVMe driver maps a bio's stream number to an FDP placement identifier.

The catch: only an application issuing direct I/O via io_uring can currently set that field, one I/O at a time. Everything else — buffered writes, writeback flushes, most file-system traffic — leaves it unset, falling to the device's default placement.

Now you're ready: the plumbing for FDP already exists in Linux; what's missing is a producer for the overwhelming majority of real-world writes.
4Buffered I/O and writeback — where most writes actually happen▾

Most applications don't do direct I/O. They write into the page cache (buffered I/O), and a kernel thread flushes dirty pages to disk later, asynchronously, as writeback. This is a shared mechanism — one flusher thread (a kworker) commonly drains dirty pages belonging to many different processes.

Per-I/O tagging schemes can't reach this path: the application never issues the I/O that finally hits the device, the kworker does.

Now you're ready: this is the gap io.stream targets — the path that dominates real deployments and that io_uring per-I/O tagging structurally cannot cover.
5cgroup v2's I/O controller and blkcg▾

Linux's cgroup v2 groups processes for resource control. Its I/O controller already exposes knobs like io.weight, io.max, and io.latency to manage bandwidth and QoS per group. Under the hood, every bio is associated with the blkcg (block cgroup) of whichever cgroup is responsible for it.

Crucially, cgroup writeback attributes a flushed dirty page to the owning tenant's cgroup, not to the generic kworker thread doing the flushing. So the cgroup label survives exactly the path per-I/O tagging misses.

Now you're ready: this attribution is the paper's whole insight — a label already exists on every data write, on every path, for free.
6Hot vs. cold data, concretely▾

Some workloads constantly overwrite their own data: a database's write-ahead log (WAL) recycles, and an LSM-tree's compaction rewrites SSTables — short-lived, high-churn, hot data. Others mostly append and rarely touch old data again: a log broker's segments, or documents inserted and never updated — cold, long-lived data.

Co-locating hot and cold in the same erase unit is exactly the WA-inducing mix FDP is meant to separate.

Now you're ready: "lifetime" in this paper just means how soon (or whether) written data gets invalidated — and different tenants on one node often differ sharply in this.
7Sampling a truth from limited slots▾

A device exposes only a handful of placement streams (8 on the paper's SSD, 7 usable for tenant data) while a host may run hundreds of cgroups. Many cgroups must therefore share a stream. The question is not how many streams you use, but which cgroups you put together — sharing a stream with something equally short-lived costs nothing; sharing it with something long-lived defeats the point.

Now you're ready: this "coherence over count" idea is the paper's headline finding — hold onto it, it recurs in every evaluation stage.
8WAF, throughput, and tail latency as one story▾

WAF (media bytes ÷ host bytes) is the paper's primary yardstick: 1.0 means the device wrote exactly what the host asked, with zero GC copying. Because GC steals bandwidth and adds latency spikes when it runs, a lower WAF also means higher sustained throughput and lower p99 latency — the three numbers move together throughout the evaluation.

Now you're ready: when you see "WAF 1.65 → 1.00," read it as "GC copying eliminated," which is also "throughput up, tail latency down" for free.
The whole story in one place

io.stream in a nutshell

The gap, the free signal that fills it, and how the pieces connect.

FDP lets a host tell an SSD which writes should be erased together, but Linux can currently only carry that intent through a per-I/O write-stream attribute set by an application doing direct I/O via io_uring. Buffered writes and ordinary file-system traffic — the overwhelming majority of real workloads — fall through to the device's default placement, and FDP goes unused.

The paper's insight: a cgroup label (blkcg) already rides every data-write bio, including page-cache flushes performed by a shared writeback thread on the tenant's behalf. That's exactly the signal per-I/O tagging can't reach. io.stream turns this existing label into a placement producer: a new cgroup v2 file lets an operator assign a device write stream to a cgroup, and the kernel stamps every otherwise-unplaced data write from that cgroup with it — no application rewrite, on any I/O path.

A strict precedence rule keeps this additive: a reserved sentinel value distinguishes "no stream expressed" from an explicit choice, so an application's own per-I/O tag — including an explicit request for the device default — always wins; io.stream only fills in writes the application left unclassified. When cgroups outnumber the device's physical streams (routine — 8 RUHs here, hundreds of cgroups possible), what determines write amplification is not how many streams you use but whether the cgroups sharing a stream actually share a lifetime.

The payoff: two isolated tenants hold WAF at an optimal 1.0 across raw, ext4, and xfs. When 14 cgroups must share 7 streams, a lifetime-coherent grouping matches full isolation (WAF 1.0) while a lifetime-oblivious one reaches 2.36 — worse than not using FDP at all. On four unmodified containers (RocksDB, PostgreSQL, Kafka, MongoDB), a coherent 2-stream pairing (WAF 1.27) nearly matches 4-stream per-app isolation (1.23). All for ~300 lines of kernel code and <1% IOPS/p99 overhead.

🍯 Key takeaways

  • Per-I/O write streams only reach direct I/O via io_uring — buffered/writeback I/O falls to device-default placement today.
  • The cgroup's blkcg label already tags every data-write bio, including cgroup-writeback flushes done by a shared kworker.
  • io.stream is a new cgroup v2 file: maj:min stream, with inherit and explicit 0 semantics.
  • A WRITE_STREAM_NONE (-1) sentinel keeps precedence strict: an app-expressed stream — even an explicit 0 — always wins over the cgroup's.
  • What governs WAF when cgroups outnumber streams is coherence, not stream count.
  • Fallback is safety-first: an unmapped cgroup goes to the device default, never onto another tenant's stream.
  • ~300 lines in Linux 7.0 block-cgroup code; one predicated field write per bio; <1% IOPS/p99 overhead.
Six everyday pictures

How to think about io.stream

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Free carrier

A forwarding label already on every box

A moving company doesn't need every single item individually tagged — every box already carries the apartment's forwarding label, even boxes carried by shared movers who serve several units. io.stream reads that same label (the cgroup/blkcg) instead of asking each item's owner to tag it — reaching boxes moved by a shared "mover" (the writeback kworker) that per-item tagging never touches.

Where it breaks: one apartment (cgroup) can hold mixed-lifetime belongings — a database's WAL and its SSTables both ship under the same label, so the building-level label is coarser than an item-level one.
Precedence · The sentinel

A form field left blank vs. filled with "none"

A form that lets you write literally "none" is different from one you simply never touched — a clerk can tell the two apart and only fills in the blank ones. The bio's stream field starts at a reserved sentinel, WRITE_STREAM_NONE (−1), meaning "untouched." An application that explicitly wrote a value — even the device default, 0 — is never overwritten; io.stream only fills in fields still at −1.

Where it breaks: the analogy has one clerk; here it's a single predicated write at bio-submission time, so there's no window where two different offices could disagree about who filled the field.
Coherence over count · The headline result

Recycling bins, sorted by material

Three recycling bins help nothing if you put paper, glass, and food waste in the same one — and one well-sorted bin for "paper" beats three badly-mixed bins. What matters is putting like with like, not how many bins you own. A 2-stream mapping that keeps hot tenants together and cold tenants together (Coherent) ties full 7-stream isolation; hashing tenants across all 7 streams (Oblivious) does worse than no sorting at all.

Where it breaks: real bins have no safety net; io.stream's fallback policy sends anything unclassified to the device default rather than into a random bin, so a naive rollout can't actively make things worse.
A free side-effect · Metadata isolation

The building's shared logbook stays in the lobby

A file system's journal (ext4's jbd2) runs as kernel work attributed to no tenant — the root cgroup — so as long as every tenant cgroup gets an explicit non-zero stream, the journal automatically lands on stream 0, separated from tenant data without anyone designing for it. It's a free side-effect of the same attribution mechanism, not a special case.

Where it breaks: the paper measures this gain as small — a Metadata-only arm that isolates just the journal tracked FDP-default almost exactly. The lobby logbook was never the source of the mess; the tenants' own boxes were.
Composability · Macro + micro

Zip code sorting, then street address

A postal system routes mail to a zip code first (coarse, node-wide) and only refines to a street address if one is written on the envelope (fine, within a building). io.stream is the zip-code layer — a node-wide, per-tenant policy — while an application's own per-I/O stream (say, tagging just its WAL) is the street address: more specific, and it always wins where present.

Where it breaks: real mail composes these two levels routinely; here the "street address" mechanism (per-I/O tags on buffered/writeback I/O) doesn't exist in the kernel yet — today the fine-grained layer only reaches direct I/O.
Safety net · Fallback overflow

Lost mail goes to the lost-and-found, not a stranger's box

An unlabeled parcel goes to lost-and-found, never into a random resident's mailbox — even if there happens to be room there. Likewise, a cgroup with no assigned stream (unmapped or beyond capacity) falls to the device's default placement, never onto another tenant's stream. Getting mapping wrong means missed opportunity; it never means cross-tenant contamination.

Where it breaks: lost-and-found is a dead end; the device-default stream is still a real, working placement — just an unoptimized one, which is why naive adoption is safe rather than merely harmless.
The full explanation

How it actually works

From the gap in Linux's stream support to the evaluation numbers, with the paper's key structures rebuilt as diagrams.

1 · The gap — streams exist, but only for direct I/O

Linux's block layer already carries an FDP placement decision as a per-bio write stream, which the NVMe driver maps to a hardware placement identifier. But the only producer today is an application issuing direct I/O through io_uring, one write at a time. Buffered writes and ordinary file-system I/O — iomap, writeback — leave the field unset, so those writes fall to the device default and FDP goes unused on exactly the paths that dominate real deployments.

2 · The insight — blkcg is a free, always-present carrier

Every bio is already associated with the blkcg of the cgroup responsible for it — including under cgroup writeback, where a shared flusher kworker drains a tenant's dirty pages but the bio is still attributed to that tenant's cgroup, not the kworker. This is exactly the signal missing from the per-I/O path: present on buffered and direct I/O alike, on any file system, with zero application involvement.

💡
Why the cgroup, and not something finer? A cgroup is a coarse, operator-visible boundary — one tenant may mix a hot WAL with a cold SSTable set — but across a multi-tenant node the largest lifetime gaps are usually between independently deployed tenants, not within one. The cgroup boundary is a useful macro-level proxy precisely because operators already deploy and administer at that granularity.

3 · The interface and its precedence rule

io.stream is a per-device cgroup v2 file. An operator writes maj:min stream to request a placement stream for that device; the default state inherit adopts the parent's effective stream, and an explicit 0 forces the device default. The controller validates the value against that device's max_write_streams.

Precedence is enforced by a reserved sentinel: a bio's stream field starts at WRITE_STREAM_NONE (−1). An issuer that has explicitly expressed a stream — today, via an io_uring write attribute — sets a concrete id, and that value always wins, even if the concrete id is 0. Only when the field is still −1 does the cgroup's effective stream apply; if the cgroup has none either, the submit-path hook converts −1 to 0 before the bio reaches the driver.

4 · Coherence when cgroups outnumber streams

A device offers a handful of physical streams (8 RUHs here, 7 usable for tenant data — one is reserved for unattributed default/metadata traffic). io.stream distinguishes a logical stream (what the operator assigns) from a physical one (what the device offers), and supports direct pinning when identifiers fit, opt-in many-to-one collapsing when they don't, and operator-reserved identifiers for critical tenants. The default overflow policy is fallback, not a hash: an unmapped or surplus cgroup falls to the device default — never onto another tenant's stream.

⚠
This is where naive rollout can backfire — but only if you hash. Stage 2 of the evaluation shows a lifetime-oblivious mapping across all 7 streams reaching WAF 2.36, worse than using no FDP placement at all (1.62). A lifetime-coherent 2-stream mapping instead ties the WAF-1.0 optimum. The fallback default avoids this failure mode entirely for unclassified cgroups.

5 · Implementation — small, and off the fast path

The Linux 7.0 prototype adds a per-cgroup field to the I/O controller's policy data and registers the io.stream control file in the block-cgroup code, validated against device limits and propagated across the cgroup hierarchy. The precedence hook is a single predicated field write, applied after the bio is already associated with its blkcg — no new fast-path allocation. The stamped stream survives the block layer intact: a split bio inherits its parent's stream, and bios carrying different streams are never merged, so a cgroup's placement is never diluted downstream. Total: ~300 lines, almost entirely in block-cgroup code.

6 · Evaluating it — three stages, same finding

Stage 1 (raw, ext4, xfs) checks that submission-time stamping survives the full VFS/writeback stack with two isolated tenants. Stage 2 (raw block) isolates user-data placement and sweeps mapping policies with 14 cgroups over 7 streams. Stage 3 (ext4) runs four unmodified, buffered-I/O containers — RocksDB, PostgreSQL (hot), Kafka, MongoDB (cold) — placed purely by mapping their existing cgroups to streams.

Follow the numbers, step by step

Worked examples

Four traces through the paper's real measurements — a WAF-to-bytes translation, a precedence walkthrough, and two coherence comparisons.

① Translating WAF into bytes saved

Raw block, two isolated tenants: FDP-default WAF = 1.65, io.stream WAF = 1.00. How much less does the media actually write?

  1. WAF is media bytes ÷ host bytes. At WAF 1.65, writing 100 host bytes costs 165 media bytes; at WAF 1.00, it costs exactly 100.
  2. Reduction = (1.65 − 1.00) / 1.65 = 0.65 / 1.65 = 39.4% less data written to the media for the same host workload.
  3. Where it went: that 0.65 extra bytes-per-host-byte was garbage-collection copying — relocating still-valid data out of erase units that mixed hot and cold. Isolating tenants removes it entirely.
🍯
Insight: this matches the paper's own framing (§4): "WAF 1.0 versus the baseline's 1.65 writes ∼39% less data to the media" — translating directly into longer device endurance, or headroom to cut over-provisioning at fixed endurance.

② Tracing the precedence sentinel

A cgroup is assigned stream 5. Trace what stream three different writes end up with.

  1. Write A: app issues io_uring direct I/O with an explicit stream attribute = 3. bio starts at −1, app sets it to 3. → Result: 3 (app's explicit choice always wins, even over the cgroup's 5).
  2. Write B: ordinary buffered write, flushed later by writeback. bio stays at −1 through submission — the app never touched the field. The submit-path hook checks: cgroup has an assigned stream (5). → Result: 5.
  3. Write C: app explicitly issues io_uring I/O requesting the device default, stream = 0. bio is set to 0 — a concrete, explicit value, not −1. → Result: 0 (the cgroup's 5 is never applied — an explicit 0 still counts as "expressed").
💡
Why this matters: without the −1/0 distinction, io.stream couldn't tell "the app wants the default" apart from "the app said nothing" — it would either clobber legitimate app choices or never activate for buffered I/O. The sentinel makes io.stream purely additive.

③ Why coherence beats stream count (Stage 2)

14 cgroups, 7 physical streams. Coherent WAF = 1.00 (2 streams used); Oblivious WAF = 2.36 (all 7 streams used); FDP-default WAF = 1.62 (no io.stream).

  1. Coherent vs. FDP-default: (1.62 − 1.00) / 1.62 = 38.3% less WAF — using only 2 of the 7 available streams.
  2. Oblivious vs. FDP-default: (2.36 − 1.62) / 1.62 = 45.7% worse — despite using all seven streams, hashing cgroup id to stream co-locates hot and cold in shared reclaim units, and WAF ends up worse than doing nothing.
  3. The lever isn't stream count — Coherent uses 2 streams and wins; Oblivious uses 7 and loses. What differs is whether the cgroups sharing a stream actually share a lifetime.
🍯
Insight: sharing a stream is not itself harmful (Coherent proves that); careless collisions are (Oblivious proves that). This is the paper's central empirical claim.

④ Matching full isolation with half the streams (Stage 3)

Real containers on ext4: 1-stream baseline WAF = 1.70; coherent 2-stream {R,P}/{K,M} = 1.27; per-app 4-stream isolation = 1.23.

  1. Total available gain (baseline → full isolation) = 1.70 − 1.23 = 0.47.
  2. Gain captured by the coherent 2-stream pairing = 1.70 − 1.27 = 0.43.
  3. Fraction of the ceiling reached = 0.43 / 0.47 ≈ 91.5% — with exactly half the streams (2 instead of 4).
  4. Compare to the mixed pairings: {R,K}/{P,M} settles at 1.58 (captures only (1.70−1.58)/0.47 ≈ 26% of the ceiling); {R,M}/{P,K} reaches 1.80 — worse than the 1-stream baseline.
💡
Insight: the two mixed pairings use exactly as many streams as the coherent one — the only variable is which containers share a stream. That isolates lifetime coherence as the deciding factor, not stream budget.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A database's cgroup holds both its WAL (rewritten constantly) and its SSTables (long-lived after compaction). If that whole cgroup is assigned one stream, does io.stream separate the WAL from the SSTables on the device?
Show answer
No. io.stream assigns streams per cgroup, not per file or per write purpose — everything from that cgroup gets the same stream. Separating WAL from SSTables within one application needs the finer-grained, per-I/O mechanism (an io_uring write attribute on the WAL's writes specifically), which composes with io.stream via the precedence sentinel but doesn't exist yet for buffered I/O.Misconception: that cgroup-level placement is a complete replacement for per-I/O tagging. It's a macro-level proxy — real, but coarser than per-write intent.
Problem 2 · medium
On ext4, "Metadata-only" (both tenants share a stream, only the journal is isolated) measured WAF 1.53 — identical to FDP-default's 1.53. What does this tell you about where the WAF-1.0 result actually comes from?
Show answer
Isolating the journal alone buys essentially nothing (1.53 vs. 1.53 — a 0% gain). The full WAF-1.0 result comes from separating the tenant data onto different streams, not from handling metadata specially. Journal isolation is a free side-effect of attribution (root cgroup → stream 0), not the mechanism's main lever.Misconception: that the journal is a major source of write amplification in mixed workloads. Here it's the co-mingled user data that matters — the journal's contribution is comparatively small.
Problem 3 · medium
A cgroup is assigned stream 4. An application in that cgroup explicitly issues an io_uring write with stream = 0 (device default). What stream does that write actually get, and why isn't it 4?
Show answer
It gets 0. The bio's field started at the sentinel −1; the app set it to a concrete value (0), which counts as "expressed" even though it happens to equal the device default. Precedence gives any app-expressed value priority over the cgroup's assignment — io.stream only fills in fields still at −1.Misconception: that "0" and "unset" are the same thing, so the cgroup should override an explicit 0. They're deliberately distinguished by the sentinel precisely so this doesn't happen.
Problem 4 · hard
14 cgroups (7 hot, 7 cold) share 7 physical streams. Explain, using the paper's numbers, why "use all 7 streams" (Oblivious, WAF 2.36) is worse than "use only 2, but correctly" (Coherent, WAF 1.00).
Show answer
Oblivious hashes cgroup id to stream, so each of the 7 streams typically receives a random mix of hot and cold cgroups — every reclaim unit ends up with the same lifetime-mixing problem FDP exists to avoid, just spread across more streams. Coherent puts all hot cgroups on one stream and all cold on another: each reclaim unit is now uniformly hot or uniformly cold, so GC copies almost nothing. More streams used badly is still bad; fewer streams used well is optimal.Misconception: that more available placement streams monotonically improve WAF. The number of streams is irrelevant if the mapping onto them doesn't respect lifetime.
Problem 5 · medium
A newly deployed cgroup has no io.stream entry configured, and the operator hasn't classified its workload yet. Where do its writes go, and why is that the safe default?
Show answer
They fall through to the device's default placement stream (0) — the same behavior as an unmodified system today. The fallback policy never assigns an unclassified cgroup onto another tenant's stream, so an incomplete or in-progress rollout can only fail to help (device-default WAF), never actively hurt by contaminating someone else's reclaim unit.Misconception: that unmapped cgroups get load-balanced or hashed across available streams. The default is a safe no-op, not an implicit assignment.
Problem 6 · easy
ext4's jbd2 journaling thread writes to disk constantly but was never given an io.stream entry. If every tenant cgroup on the system has an explicit non-zero stream, what stream does jbd2's traffic get, and why?
Show answer
Stream 0, the device default. jbd2 runs as kernel work attributed to the root cgroup, not to any tenant, so it's automatically excluded from every tenant's stream and falls to default — separating volatile journal traffic from long-lived tenant data with zero file-system changes.Misconception: that metadata isolation needs an explicit rule. It falls out of the same blkcg-attribution mechanism used for tenant data.
Problem 7 · hard
A bio carrying stream 3 gets split by a lower block-layer stage (e.g. for a RAID stripe boundary) into two child bios. What stream(s) do the children carry, and what would go wrong if a split bio instead reset to the sentinel?
Show answer
Both children inherit the parent's stream (3). If a split instead reset to −1, part of a single logical write could silently fall back to the device default — half the write lands in the intended reclaim unit and half doesn't, defeating the whole point of grouping it with same-lifetime data. Inheritance on split (and refusing to merge bios with different streams) is what keeps a cgroup's placement intact all the way to the device.Misconception: that stream is I/O-request-level metadata that naturally degrades under block-layer transformations. The paper treats it as an invariant that must be explicitly preserved through splits and merges.
Problem 8 · medium
RocksDB's WAL writes are tagged via io_uring with an explicit per-I/O stream, but its SSTable-flush writes (also buffered, from a background compaction thread) are left untagged. RocksDB's cgroup is assigned stream 3. What stream does each type of write end up with?
Show answer
The WAL writes keep their explicit app-set stream (precedence: app-expressed value always wins). The untagged SSTable-flush writes — still at the −1 sentinel when submitted — pick up the cgroup's assigned stream, 3. The two mechanisms compose: io.stream fills in exactly what the application left unclassified, nothing more.Misconception: that assigning a cgroup a stream overrides all of that cgroup's I/O uniformly. It only ever affects writes the application didn't already tag.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What problem does FDP actually solve?▾
Flash must be erased before rewriting. If data with different lifetimes shares an erase unit, an overwrite invalidates only part of it, and garbage collection must relocate the rest — write amplification. FDP lets the host steer same-lifetime writes into the same reclaim unit so it empties as a whole, driving write amplification toward 1.0 without needing more over-provisioning.
Q2Why can't applications already use FDP today?▾
Linux carries FDP placement as a per-bio write-stream field, but the only way to set it is a per-I/O attribute on direct I/O via io_uring. Buffered writes and normal file-system traffic — most real workloads — leave the field unset and fall to the device default, so FDP goes unused unless an application is rewritten specifically for direct I/O.
Q3What exactly does io.stream let an operator do?▾
It adds a file to the cgroup v2 I/O controller where an operator writes maj:min stream to assign a device write stream to a cgroup. From then on, every data write from that cgroup that the application itself left unclassified is stamped with that stream — no application changes, on any I/O path.
Q4How does a cgroup's label survive a page-cache flush done by a shared kernel thread?▾
Via cgroup writeback: Linux already attributes a dirty page's flush to the owning tenant's cgroup, not to the generic kworker thread performing the I/O. So the blkcg label the kernel needs is present on that bio regardless of which thread submits it — this is the paper's core enabling fact.
Q5What is the WRITE_STREAM_NONE sentinel for?▾
It distinguishes "no stream expressed" (−1) from an explicit choice, including an explicit request for the device default (0). Without that distinction, io.stream couldn't safely fill in only the writes an application left unclassified — it would risk overriding a deliberate app-level "0" or never firing for buffered I/O at all.
Q6What happens when there are more cgroups than device streams?▾
io.stream supports direct pinning when they fit, opt-in many-to-one collapsing when they don't, and reserved identifiers for critical tenants. Any cgroup left unmapped falls to the device default — never onto another tenant's stream. The evaluation shows what matters at this point is which cgroups share a stream, not how many streams are used.
Q7Is more streams always better?▾
No. In Stage 2, a coherent mapping using just 2 of 7 streams matched WAF 1.00, while a lifetime-oblivious mapping using all 7 reached WAF 2.36 — worse than not using FDP placement at all (1.62). Coherence, not stream count, governs write amplification.
Q8Does io.stream require modifying RocksDB, PostgreSQL, Kafka, or MongoDB?▾
No — that's the point. Stage 3 runs stock container images; placement is set purely by assigning each container's existing cgroup a stream. A coherent 2-stream pairing (grouping the two churn-heavy apps together and the two append-mostly apps together) reached WAF 1.27, close to 1.23 for giving every container its own stream.
Q9How much overhead does this add?▾
The Linux 7.0 prototype is about 300 lines, almost entirely in block-cgroup code, adding one predicated field write per bio and no new fast-path allocation. Measured IOPS and p99 latency deltas versus baseline are under 1%.
Q10How is this different from AutoStream or PCStream, which also assign streams automatically?▾
AutoStream infers streams from LBA access patterns and PCStream from issuing program context — both reconstruct a lifetime grouping by observation, paying per-I/O monitoring cost, without any interface change. io.stream instead makes the cgroup — which already encodes explicit operator intent about tenant boundaries — the chooser, reusing a label the kernel already attaches to every write rather than inferring one.

Glossary, results, and provenance

Every term in one place, the headline numbers, then what's the paper's and what's this guide's framing.

Core terms
io.streamThe paper's cgroup v2 file: assigns an FDP write stream to a cgroup, stamping its otherwise-unplaced data writes.
FDP (Flexible Data Placement)NVMe feature letting a host route writes into separate reclaim units by placement identifier, so co-invalidated data is erased together.
RUH / RU / RGReclaim Unit Handle (the addressable target), Reclaim Unit (region erased as a whole), Reclaim Group (a set of RUs).
WAF (write-amplification factor)Media bytes written ÷ host bytes written. 1.0 is optimal; the paper's primary metric, measured from SMART/OCP log deltas.
WRITE_STREAM_NONE (−1)The sentinel meaning "no stream expressed" on a bio, distinct from an explicit request for stream 0.
Logical vs. physical streamLogical = what the operator assigns per cgroup; physical = the finite set of identifiers the device actually offers.
CoherenceWhether cgroups sharing a physical stream actually share a data lifetime — the variable the paper shows governs WAF, not stream count.
blkcgThe block-cgroup subsystem; every bio is associated with the blkcg of its responsible cgroup, including under cgroup writeback.
Supporting terms
bioThe kernel's block I/O request structure; now carries a write-stream field consulted by the NVMe driver.
io_uring passthroughLinux's async I/O interface, extended to let applications attach a write-stream attribute to a direct I/O request.
cgroup writebackAttributes a page-cache flush to the owning tenant's cgroup rather than the generic flusher thread performing it.
jbd2 / CILext4's journaling block device layer / xfs's committed item list — the file systems' respective journal/metadata mechanisms.
Over-provisioning (OP)Spare device capacity reserved for GC headroom; FDP aims to shrink the OP needed for a given WAF target.
ZNS (Zoned Namespaces)An alternative, non-backward-compatible interface exposing flash geometry directly; FDP is advisory and keeps the ordinary block interface.
AutoStream / PCStreamPrior kernel/device schemes inferring streams from LBA patterns or program context, without any interface or cgroup involvement.
Fallback overflow policyio.stream's default when a cgroup has no stream mapped: use the device default, never another tenant's stream.

Source notes

From the paper (facts, figures, all measured numbers): the FDP/RUH/RU/RG model; the io_uring-only limitation of today's write-stream support; the cgroup-writeback attribution mechanism; the io.stream interface, sentinel precedence, and mapping/fallback design; the ~300-line implementation and split/merge invariants; every WAF, throughput, and latency number in Table 1, Fig. 2, and Fig. 3 and the Stage 1–3 experimental setup (PM9D3a SSD, 7% OP, 8 RUHs / 7 usable, i9-12900K host, 3-run means).

This guide's framing (not the paper's claims): the "shipping label," "recycling bins," "zip code/street address," and "lost-and-found" analogies; the tab structure, practice-problem misconceptions, and the interactive stream-pairing widget (which replays the paper's own Stage 3 numbers rather than inventing new ones). Readers working on OS-managed memory tiering may notice the parallel to hardware-maintained access bits: just as page-table Access bits already exist for the kernel to sample for hot/cold classification (as in PTE-scanning tiering systems), io.stream's contribution is recognizing that the blkcg label already exists on every bio — the design move in both cases is reusing an existing, cost-free signal rather than adding new instrumentation.
