Waking someone up is a hint, not a handoff

Hoare's monitors promised a signaled process runs *immediately*. Building Pilot and Mesa taught Lampson & Redell that guarantee costs too much — so they weakened it, landing on a hint-and-recheck contract that modern kernel wait-queues would later converge on independently.

Before you begin

What this paper is actually arguing

Hoare invented monitors on a whiteboard. Lampson & Redell had to make them survive a 24,000-line operating system (Pilot). This tab gets you oriented before the deep dive.

⚡ TL;DR

  • Mesa's contribution is engineering, not theory: it resolves seven concrete gaps in Hoare's monitor proposal — nested WAIT semantics, dynamic process/monitor creation (FORK/JOIN and monitored records let processes and per-object monitors be created and destroyed at runtime, instead of a fixed set decided when the program is compiled), exceptions/UNWIND, and priority scheduling (the processor always runs the highest-priority ready process — which raises the priority-inversion problem in §4.3 once locks enter the picture) — that no prior implementation had fully worked out.
  • The headline design decision is signal-and-continue: NOTIFY is a hint, not a guaranteed handoff, so a woken process must recheck its condition in a WHILE loop. WAIT costs 15 ticks and NOTIFY 4 to 9, and no extra process switches (60 ticks each) are forced, whereas Hoare's stricter rule forces several on every signal.
  • This "wakeup is a hint, recheck in a loop" pattern is why it matters beyond 1980: the same contract shows up in Linux's wait_event()/wake_up() and futex semantics — not because Mesa caused it, but because any signal-and-continue design converges on the same recheck loop.

1What a monitor is, concretely▾

A monitor bundles shared data with the only code allowed to touch it, and guarantees that at most one process executes inside that code at a time. You don't take a lock and remember to release it — calling an entry procedure takes the lock, returning releases it, automatically.

Now you're ready: everything in this paper is about what happens when that simple picture meets a real OS with nearly 40 monitors and about 15 dedicated internal processes (Pilot, which client applications also call into).
2Why WAIT exists inside a monitor▾

Sometimes an entry procedure discovers it can't proceed yet (a buffer is empty, no memory is free). It calls WAIT on a condition variable, which releases the monitor lock and blocks the process — otherwise it would hold the lock forever and deadlock everyone else.

Now you're ready: the entire second half of the paper is about exactly when a waiting process should be allowed to resume, and what it's allowed to assume when it does.
3Processes as first-class values▾

Mesa treats a running computation (a process) the same way it treats any other value: you can store it in a variable, pass it as a parameter, and later JOIN it to retrieve its result — exactly like calling a procedure, but concurrent. FORK is the concurrent analog of a call.

🔍
Not Unix fork(): Mesa's FORK doesn't clone anything. It starts a new lightweight process running a given procedure concurrently, in the same address space — closer to pthread_create or Go's go f() than to Unix fork(). Unix fork() duplicates the entire calling process (its whole address space, as a copy), producing a second, independent process that resumes from the same point fork() was called, with its own copy of every variable. fork+exec is the classic Unix idiom for running a different program: fork() makes the copy, then the child immediately calls exec(), which discards its own memory image and loads a new program in its place — the gap between the two calls exists so the child can adjust things (redirect stdin/stdout, change its environment) before the new program starts.
Now you're ready: because creating a process is this cheap and uniform, it is "feasible to program with a large number of processes, and to vary the number quite rapidly", rather than running a fixed set decided at compile time. (Pilot itself creates essentially all of its internal processes at initialization; Violet forks processes freely.)
4Mutual exclusion vs. preemptive scheduling▾

A simpler alternative to monitors is a non-preemptive scheduler: processes only switch at explicit yield points, so nothing can interleave inside a critical section. The paper rejects this — I/O interrupts need fast preemption, and non-preemption can't survive a page fault happening mid-critical-section.

Now you're ready: monitors exist specifically to give you mutual exclusion with a fully preemptive scheduler underneath.
5Priority scheduling, briefly▾

Mesa's processor always runs the highest-priority ready process. That sounds simple until a low-priority process holds a lock a high-priority process needs — then priority order can be silently subverted by whoever else is running.

Now you're ready: Section 4.3 of the paper works through exactly this scenario, called priority inversion, and its fix.
6Deadlock, the boring kind and the subtle kind▾

Two processes each WAITing for the other to NOTIFY them is an easy bug to spot. Harder: monitor M calls into monitor N, and N calls back into M — a cyclic locking dependency invisible from either monitor alone.

Now you're ready: the paper's discipline for avoiding this is the same one used everywhere locks exist: never allow cyclic lock-acquisition order.
7Exceptions meeting locks▾

Mesa has UNWIND, a mechanism for abandoning a chain of procedure calls cleanly when an exception is handled far up the stack. If one of the abandoned procedures was holding a monitor lock, that lock must still be released, or the monitor stays locked and the next caller deadlocks (the paper says the cause "is not hard to find").

Now you're ready: this is why, if the logic of the program allows an UNWIND, the programmer must supply an UNWIND handler in each entry procedure to restore the invariant; Mesa then supplies the code that releases the lock. Without a handler the lock is not released.
8One monitor, many objects▾

If you have a thousand open files, you don't want one giant monitor serializing access to all of them — that kills concurrency. But a thousand separate monitor modules is wasteful. Mesa's answer is a monitored record: an ordinary data record that carries its own lock.

Now you're ready: this is the paper's answer to "monitoring large numbers of small objects," one of the seven open problems listed in the introduction.
The whole story in one place

Mesa's monitors, in a nutshell

Hoare's monitors were a clean idea with unresolved edges. Mesa is what happens when you weld those edges shut under the pressure of a real, large system.

Hoare's original monitor proposal specified mutual exclusion and condition variables, but left unresolved exactly what a signaled process may assume, how monitors interact with nested calls, dynamic creation, exceptions, and priority scheduling. Building Pilot — Xerox's Mesa-based personal-computer OS, plus large applications like a distributed calendar and an internetwork gateway — forced Lampson & Redell to answer every one of these questions concretely.

Their central departure from Hoare is signal-and-continue: a NOTIFY is a hint, not a guaranteed handoff. The notifier keeps running; the waiter resumes "at some convenient future time" and must re-verify its condition in a WHILE loop before proceeding. This trades one extra predicate re-check for eliminating the forced process switches Hoare's stricter signal-and-wait rule requires on every NOTIFY.

What gets notified is a condition variable, not a process directly — a condition variable has no data of its own; it's just a queue of processes that called WAIT because some predicate on the monitor's shared data ("buffer non-empty," "memory available") wasn't true yet. NOTIFY on that condition variable says "something that might make a waiter's predicate true just changed" — it doesn't say which waiter, or guarantee the predicate is actually true for anyone. Hoare's original 1974 proposal specified the same two primitives (mutual exclusion plus condition variables) but bound them together tightly: his signal-and-wait rule makes the signaling process block immediately, handing the monitor and the CPU straight to a waiter, who is then guaranteed to find the exact predicate true, since nothing else could have run in between. Mesa keeps the same two primitives but cuts that binding: NOTIFY marks a waiter merely ready, to be scheduled whenever the highest-priority-ready-process rule gets around to it — which may be much later, and by then some other process may have entered the monitor and changed things again. That's exactly why the waiter must check, not assume, and why the check must be a WHILE loop rather than an IF.

Around that one decision, the paper builds a complete, coherent design: processes as cheap first-class values (FORK/JOIN), monitors as ordinary Mesa modules with an explicit lock-scope rule for nested calls, UNWIND integration so exceptions can't leak a held lock, timeouts, Abort, and BROADCAST as three cheap extensions of the same NOTIFY mechanism, a fix for priority inversion, and monitored records for cheaply monitoring many small objects.

The payoff: a monitor-guarded call costs 50 ticks versus 30 for a plain call (+67%); WAIT costs 15 ticks and NOTIFY only 4–9, versus 60 ticks for a full process switch. The design shipped as the only concurrency mechanism on a real personal computer, running everything from disk interrupt handlers to a replicated distributed database.

🍯 Key takeaways

  • NOTIFY is a hint, never a guarantee — always re-check in a WHILE loop, never branch with IF.
  • A monitor lock is released by WAIT, but not by calling out to a procedure outside the monitor module, even if that call itself waits.
  • Timeout, Abort, and BROADCAST are all just variations on "resume a waiter" — none change the verification rule.
  • Priority inversion: the paper proposes boosting a process entering a monitor to the priority of the highest-priority process that has ever entered it (it does not say whether Pilot implements this).
  • Monitored records give every object its own lock without paying for a full module instance per object.
  • FORK+JOIN costs about 37× a plain call by the table (1,100 vs 30 ticks; the paper's text says "about 38 times") because it's built in software atop monitors, not microcoded.
  • No protection is enforced beyond the type system — Mesa assumes a single, cooperative user, not a competitive multi-tenant machine.

1a · What WAIT does and doesn't do — and why the picture needs B to be independent

Easy misreading of the figure above: that A's WAIT c somehow causes B's NOTIFY c — that B is "notified by A's wait." It isn't. WAIT is purely passive: release the lock, join c's queue, done. It sends nothing to anyone. B is simply some other process that happens to call one of the monitor's entry procedures once the lock is free — for reasons of its own that have nothing to do with A. B has no idea A was ever waiting.

The two links that actually connect A and B are separate, and only one of them is a deliberate act. A's WAIT freeing the lock is mechanical plumbing — it just means the monitor is available, to B or to anyone else who wants in. What actually wakes A is a line of code someone wrote: because B's job (in the classic producer/consumer case) is to change the state A's condition depends on — e.g. produce an item into a buffer A found empty — the programmer who wrote B's entry procedure made sure it calls NOTIFY c after making that change. If B's code never called NOTIFY, A would sleep forever no matter how much the state changed. Nothing in the language forces that discipline; it only holds because whoever wrote the monitor made every state-changing procedure notify the conditions that depend on it.

⚠
This is also exactly why the WHILE loop is essential, not just cautious: once B exits and the lock is free again, anything eligible to enter — including a third process C that's just arriving fresh, unrelated to A's wait — can win the lock before A gets scheduled. Mesa's rule is strictly "run the highest-priority ready process," with no special case for "was recently notified." If C gets in first and changes the very state B just set up (e.g. consumes the item B produced), A's original reason to wake up has evaporated by the time A actually resumes. That race — someone else getting in between the NOTIFY and A's actual resumption — is the entire justification for checking in a loop instead of assuming the notify meant your exact condition is true.

1b · Is this "implementing Hoare's theory," or something else?

Worth being precise about scope: this paper isn't a faithful implementation of Hoare's 1974 proposal — it replaces Hoare's own central rule. Hoare's proposal specified mutual exclusion, condition variables, and one particular resumption discipline: signal-and-wait, an immediate guaranteed handoff. Mesa keeps the first two (monitors, condition variables) but discards the third, replacing it with signal-and-continue precisely because the forced process switches signal-and-wait requires were too expensive on real hardware. So Timeout, Abort, BROADCAST, and the wakeup-waiting switch aren't machinery needed to make Hoare's rule work — they're mechanisms Mesa's authors had to invent because Hoare's clean theoretical proposal never addressed any of these situations at all: what if nobody ever notifies you (Timeout)? What if you need to interrupt one specific process for a reason unrelated to any resource (Abort)? What if several waiters need different, unpredictable amounts of a resource (BROADCAST)? What if the thing that needs to signal you is hardware that structurally cannot take your lock (naked NOTIFY)? None of these are questions Hoare's theory poses, let alone answers.

There's a real causal link between the two kinds of change, though: signal-and-continue is exactly what makes Timeout, Abort, and BROADCAST cheap, coherent additions. Because NOTIFY was already weakened to a mere hint, adding three more ways to trigger that same hint costs nothing extra in correctness machinery — recheck the WHILE loop either way. Under Hoare's stricter guarantee, none of the three would fit cleanly: a Timeout can't promise the predicate is true (nothing changed, time just passed); BROADCAST can't promise it to every waiter simultaneously; Abort explicitly wants to interrupt regardless of whether it's true. So the theory-revision and the engineering-extensions aren't two separate stories — the revision is what makes the extensions possible.

Six everyday pictures

How to think about Mesa's monitors

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks down.

The core idea · NOTIFY as hint

A doorbell, not a summons

A summons legally compels you to appear now. A doorbell just tells you someone might want you — you finish what you're doing, walk over, and check who's actually there before opening. Mesa's NOTIFY is a doorbell: it schedules a chance to check, not an immediate compulsory appearance. The waiter must still look ("recheck the predicate") before acting.

Where it breaks: a doorbell can be ignored entirely with no consequence; a Mesa NOTIFY, if never checked, means the waiting process never proceeds — someone must eventually re-run the loop.
Mutual exclusion · Entry procedures

A single-key restroom

One key, one door, one occupant at a time. You don't have to remember to lock it behind you — the door auto-locks when you enter and auto-unlocks when you leave. That's a Mesa entry procedure: calling it grabs the monitor lock, returning releases it, with no code in between that can "forget."

Where it breaks: the restroom analogy is per-object; Mesa's LOCKS clause and monitored records let many "restrooms" share one blueprint (the module's code) while each keeps its own key.
Priority inversion · §4.3

A traffic jam behind a parked car

An ambulance (highest priority) is stuck because a delivery van (medium priority) keeps merging in front of a small car (low priority) that's parked in the only lane, blocking traffic entirely. The ambulance isn't blocked by the parked car directly — it's blocked by the van's endless stream of traffic that never lets the parked car move. Mesa's fix: give the parked car's lane the ambulance's priority the moment the ambulance needs to pass.

Where it breaks: the "lane" (monitor) gets boosted to the highest priority of anyone who has ever used it, not just the current blocker — a coarser, cheaper rule than tracking exact dependencies.
Lock scope · Nested calls

Not taking your office key on a coffee run

You lock your office (a monitor) while working inside. If you step out to grab coffee (a call to an external procedure, outside the monitor's module), the office stays locked the whole time — even if the coffee shop itself has its own separate locked door you wait behind. Only WAIT-ing inside your own office releases your own office's lock.

Where it breaks: if the coffee shop is itself a monitor that calls back into your office, you get a real deadlock — the analogy doesn't save you from that, only from the illusion that leaving unlocks things it shouldn't.
Duality · Monitors vs. messages

Two names for the same handshake

Lauer & Needham showed monitors and message-passing are duals: process ↔ message, monitor ↔ process, call/return ↔ send/reply. Choosing monitors over messages here wasn't a claim that one is fundamentally better — it was that Mesa's procedure-call-centric language made monitors the natural fit, not messages.

Where it breaks: the duality assumes "mild restrictions on programming style" — real message-passing systems (with buffering, multicast, asynchronous delivery) diverge from a clean call/return mapping.
Naked NOTIFY · §4.2

A doorbell wired straight to the porch, bypassing the lock

Normally your doorbell (NOTIFY) and your door lock (the monitor lock) are the same mechanism — one process at a time deals with the door. A device interrupt can't take that lock at all; it presses a doorbell wired directly to the porch. Without care, you can be mid-step toward the door (about to WAIT) exactly when the bell rings — and never hear it. The fix is a spring-loaded latch (the wakeup-waiting switch) that remembers a ring even if no one was listening yet.

Where it breaks: this patch is needed only because the device physically cannot acquire the lock; between two ordinary Mesa processes, the monitor lock itself already prevents this race.

How it actually works

1 · Monitor modules and the WHILE-loop discipline

A Mesa MONITOR is a module with three kinds of procedures — Mesa's term for what you'd call a function today. The three kinds split along two independent questions, not one: can code outside this module call it at all, and does it touch the monitor's protected shared data? Crossing those two questions gives exactly the three categories the paper uses:

Entry procedures are callable from outside and touch the protected data — the only combination that actually needs the lock, since it's the only one where an outsider is about to reach into shared state. Calling one acquires the monitor's lock automatically; returning releases it. Internal procedures also touch the protected data, but are private — reachable only from code already running inside the module (an entry procedure, or another internal procedure) — so they never acquire the lock themselves; they simply rely on whoever called them already holding it. External procedures are callable from outside, exactly like entry procedures, but never touch the protected data at all, so they never needed a lock in the first place regardless of who calls them. The paper's own allocator example makes this concrete: Allocate and Free are entry procedures (they touch the free-memory structure), while Expand is external — exported the same way Allocate and Free are, but it doesn't touch that structure, so it costs a plain procedure call rather than the lock protocol.

🌱
Why this split matters for correctness, not just cost: a WAIT can only appear lexically inside code that's actually part of the monitor's protected region — i.e., inside an entry or internal procedure. External procedures never touch the protected data, so there's never a WAIT on this monitor's condition variables sitting inside one. The compiler enforces this: WAIT in an external procedure is a compile-time error (§5.3). Why a call out of the monitor does not release the lock, even if the callee WAITs in another monitor, is a separate design decision with a correctness argument behind it: releasing it would force the caller to re-establish its invariant before every outside call (Part II, M8). See §2 below for the deadlock this enables when the "outside" you call into is itself another monitor.

Because NOTIFY is only a hint, every WAIT inside an entry or internal procedure must be inside a loop that re-checks its condition:

-- correct Mesa pattern --
WHILE NOT <OK to proceed> DO WAIT c ENDLOOP;

-- Hoare's stricter (and here, wrong) pattern --
IF NOT <OK to proceed> THEN WAIT c;
💡
Why the loop, not the branch: after resuming from WAIT, some other process may have entered the monitor first and changed things again. Only the monitor invariant — never the exact predicate that triggered NOTIFY — may be assumed right after a WAIT.

2 · The lock-scope rule for nested calls

If an entry procedure calls another procedure outside its own monitor module, the lock is not released — even if that outside procedure itself waits inside a different monitor. Only a WAIT executed directly inside the current monitor's own code releases its lock.

⚠
The subtle deadlock this enables: if monitor M calls into monitor N, and N then WAITs for a condition that can only become true when some other process re-enters N through M, N is unlocked (fine) but M stays locked the whole time — no one else can enter M to trigger that condition. The paper's fix: split M into a monitor M′ that holds M's shared data plus an ordinary module O that implements M's abstraction, calls M′ for access to the data, and makes the call on N itself, so no lock of M′ is held across the risky call.

3 · Timeout, Abort, and BROADCAST — three variations on NOTIFY

Once NOTIFY is defined as "resume a waiter at a convenient time," three extra ways to trigger that resumption fall out almost for free, with no change to the verification rule — the paper says so explicitly: "None of these mechanisms affects the proof rule for monitors at all." That's the key to reading this table: every one of them is just a different trigger for the same "move a process to ready, go recheck your WHILE loop" outcome — none is a stronger guarantee than an ordinary NOTIFY.

MechanismResumes when…Typical use
Timeouta per-condition-variable interval t elapses, notified or notretry logic, avoiding infinite waits
Abortanother process calls Abort[p]; next WAIT raises Abortedpolitely asking a process to clean up and stop
BROADCASTevery process waiting on the condition, not just onewhen different waiters need different, unpredictable amounts of the resource

Timeout exists because plain WAIT offers no guarantee you're ever notified — if the event you're waiting for simply never happens, or a bug drops the NOTIFY, you'd block forever. A condition variable can carry an interval t; a process that's waited longer than t resumes on its own. The paper's own design history is worth knowing: timeouts originally raised an exception, but were changed to a plain resumption because most callers just wanted to retry, not handle a special error case — which fits the WHILE-loop discipline perfectly, since a timeout-triggered wakeup gets exactly the same treatment (recheck, and if still false, wait again) as an ordinary NOTIFY-triggered one.

💡
Abort doesn't belong to the same family as the other two, and it's worth being precise about why. NOTIFY, BROADCAST, and Timeout are all condition-targeted: they operate on whoever happens to be in c's queue, and they produce a normal return from WAIT — the process goes and rechecks its predicate like nothing unusual happened. Abort[p] is process-targeted instead: it names a specific process p, regardless of which condition variable (if any) p happens to be waiting on, and it produces an exceptional return — the next WAIT p executes raises Aborted rather than returning normally, sending p into exception handling (potentially an UNWIND; see M9 in Part II below) instead of back into its WHILE loop. It only shares a section with the other three because "make a WAIT statement return" is the one lever Mesa exposes for interrupting a blocked process — not because it's solving the same problem. And true to the paper's "cooperative, not competitive" philosophy: Abort doesn't force anything. If p is running rather than blocked, Abort[p] just sets a flag that fires on p's next WAIT; and once the Aborted exception does fire, p is free to catch it and keep going, or ignore it entirely. There is no way in Mesa to forcibly kill a runaway process.
🌱
Since NOTIFY is already just a hint, BROADCAST is always correct to use instead — the only cost is waking more processes than strictly needed. The paper also says the converse can happen ("there are times when a BROADCAST is correct and a NOTIFY is not") and points at its own StorageAllocator example (Section 3.1) as having a problem that replacing NOTIFY with BROADCAST solves. M5 and M7 in Part II give the mechanisms you need to work out why.

5 · Naked NOTIFY and the wakeup-waiting switch

A device can update shared memory and NOTIFY a condition variable, but it cannot wait on the monitor lock (the paper: "it is not possible for the device to wait on a monitor lock"; it chose not to make devices take the lock, for the reason given below). Ordinarily the lock prevents a race between "check predicate, prepare to WAIT" and "update predicate, NOTIFY" — but with no lock on the device's side, that race is real: the WAIT can execute right after the device's NOTIFY, losing the wakeup forever. The fix bolts a binary-semaphore-like wakeup-waiting switch onto the condition variable, remembering an unconsumed notify.

Worth being precise about why the lock protects this normally, so it's clear exactly what a device loses: between two ordinary Mesa processes, "check predicate, prepare to WAIT" and "update predicate, NOTIFY" both happen inside an entry procedure of the same monitor, so both are guarded by the same lock — only one of those sequences can be in progress at a time, so they can never interleave badly. A device breaks that guarantee purely because it never takes the lock in the first place. Walk the exact failure: process A enters the monitor, checks the predicate, finds it FALSE, and is about to execute WAIT — right at that instant, before A's WAIT actually runs, the device updates the shared data (using nothing but atomic word-level reads/writes, since it has no lock to take) and fires its NOTIFY. Nobody is on the condition's queue yet, so that NOTIFY has no one to wake and is simply discarded. Then A executes WAIT, based on its now-stale check, and blocks — waiting for a notification that already happened and is gone for good.

The wakeup-waiting switch closes exactly that gap: it's an extra bit of state on the condition variable remembering "a NOTIFY landed and nobody had collected it." When a naked NOTIFY finds no one waiting, instead of vanishing it flips the switch on. When WAIT is about to actually block, it first checks the switch — if it's on, WAIT clears it and returns immediately, as if the NOTIFY had just landed; only if it's off does WAIT genuinely suspend. That's precisely a binary semaphore's defining property (a signal that arrives early is remembered, not lost), bolted on only to condition variables that devices notify — ordinary process-to-process condition variables don't need it, because the lock already rules the race out.

The paper also explains what they gave up to avoid this problem outright: they considered having devices acquire the monitor lock exactly like ordinary processes, which would have sidestepped the whole issue, but rejected it because mutual exclusion between things running at very different speeds caps the faster one's worst-case response time at however long the slower one holds the lock — and a device is often far faster than the Mesa process it signals. Rather than let a device's worst-case latency be held hostage by whatever critical section a slow process happens to be in, they accepted the wakeup-waiting switch's extra bookkeeping instead.

6 · Monitored objects and monitored records

The problem: say you have a thousand open files, each needing its own mutual exclusion (two threads shouldn't both be mid-write to the same file's metadata, but a write to file A and a write to file B are completely unrelated and should proceed in parallel). Two obvious designs both fail. Option A — one shared monitor over the whole collection: every entry procedure for every file goes through the same monitor lock, so a thread touching file A blocks a thread touching file B even though they share no state at all — mutual exclusion is granted at the wrong granularity, and concurrency across unrelated objects is destroyed. Option B — one Mesa module instance per file: each file gets its own monitor, so locking is correctly per-object — this is the paper's own recommended fallback when Option A costs too much concurrency — but it isn't free, for two separable reasons the paper calls out explicitly.

First, a duplication cost that has nothing to do with the file's actual data. Every Mesa module instance — even though all thousand instances run the exact same compiled code — carries its own private copy of the bookkeeping Mesa's runtime uses for program linking and code swapping (essentially, per-instance metadata describing where this instance's globals live and how its procedure entries resolve, separate from the executable code itself, which really is shared). You're not duplicating the monitor's logic — you're duplicating the runtime plumbing that lets the system link to and page in that logic, once per object, for a thousand objects that all point at identical logic. Second, and more subtly, a loss of control: module instances are allocated by the Mesa system itself, through the same general instantiation machinery used for large, distinct subsystems — not by the programmer's own code. That means you can't use whatever allocation strategy would actually make sense for a thousand small, uniform, frequently-created-and-destroyed objects (e.g. one big pre-sized array, or a custom free-list) the way you routinely could for an ordinary Mesa record. Both costs are basically fixed per instance regardless of how tiny the object's real data is, which is why the paper ranks this design second, after a single monitor ("we recommend this approach whenever possible"), and why it added monitored records: for many small objects you'd be paying a full module-instantiation's worth of linking overhead and losing your allocation freedom, just to attach one lock to each of a thousand otherwise-ordinary records.

The fix decouples the lock from the code. A monitored record is just an ordinary data record with one extra field: a lock. The procedures that operate on these records stay in a single monitor module, compiled once, shared by every file. A LOCKS clause written once at the beginning of the monitor module says how to find the lock (for example through a file parameter that every entry procedure, and every internal procedure that WAITs, receives), so calling the procedure on file A's record acquires A's lock, and calling it (even concurrently, on another process) on file B's record acquires B's separate lock. Locking granularity is now per-object, exactly like Option A avoided doing wrong, while the code itself is shared exactly once, exactly like Option B failed to do cheaply.

7 · FORK, process roots, and why "forkable" is stricter than "callable"

Mesa's exception handling is scoped to blocks, not procedures. A block is any BEGIN...END-delimited scope, and a single procedure body typically contains several of them nested inside it (a loop body, an IF branch, any inner BEGIN...END), each of which can carry its own handler. When an exception is raised, Mesa searches outward: the innermost block first, then the block enclosing it, working outward through however many blocks sit inside the current procedure — and only once that procedure is exhausted does the search escalate to the caller, where the same inside-out search repeats one level up. This is just the call stack: each "caller" the search reaches is the next frame down.

🌱
Read "block" as "any nested scope," not "procedure" — a procedure body is one block, but it's rarely the only one an exception has to climb through before the search ever reaches a caller at all.

That chain has to end somewhere, and it ends at whichever procedure is the root of the current process: the one frame with nothing beneath it, because nothing inside this process called it. The paper is explicit about what that means: "the root procedure of a process has no caller, [so] it must be prepared to handle any exceptions that can be generated in the process... If it fails to do so, the resulting error sends control to the debugger" — fine while developing, but the paper adds dryly that this is "not much comfort... when a system is in operational use."

This is where FORK and CALL genuinely diverge, even though both just "start a procedure running." A normal CALL adds a new frame on top of the existing stack, so the called procedure always has a caller above it and can safely leave some exceptions unhandled, trusting that caller (or one further up) to catch what it misses. FORK does something structurally different: it doesn't extend the calling procedure's stack at all, it starts an entirely new one, with the forked procedure as that new stack's root. The procedure that executed the FORK statement is not that root's caller in any exception-handling sense, even though it's the one that caused the process to exist — it's off running its own, separate stack. So a forked procedure inherits none of the backup handling a normally-called one gets for free.

💡
That's the entire content of "any procedure suitable for forking can also be called sequentially, but the converse is not generally true." A procedure safe to fork is, by definition, one that catches everything itself, since it can't lean on a caller that won't exist. Call that same procedure normally instead, and nothing changes for it: the caller now above it is just an unused backstop. But a procedure that's merely safe to call normally is allowed to be lazier, by letting some exception propagate up to a caller it currently happens to have. Fork that procedure and that caller vanishes; whatever it was counting on someone else to catch now falls straight through to the debugger instead. Forkable-safe is a strict subset of callable-safe, which is exactly why the implication only runs one direction. (A related but separate hazard sits on the same page of the paper: parameters passed by reference into a forked procedure become dangling pointers if the calling procedure returns, and its stack frame is reused, before the forked process finishes — a memory-safety problem, not an exception-handling one, but the same root cause: forking cuts the forked procedure loose from assumptions that hold automatically for an ordinary nested call.)

M1 · The design space: what Mesa rejected before choosing monitors

The paper opens (§1) with the requirements. Pilot, a 24,000-line Mesa operating system for a personal computer, had to support three uses of concurrency: local concurrent programming (one application as a tightly coupled group of synchronized processes), global resource sharing (independent applications sharing the processor cooperatively), and replacing interrupts (a device requests attention by waking a process, not through a separate interrupt mechanism such as a forced branch). The authors expected to "read the literature, compare the alternatives offered there, and pick the one most suitable"; that expectation "proved to be naive". Seven issues, labeled (a) to (g), were not resolved in the published work: program structure, creating processes, creating monitors, WAIT in a nested monitor call, exceptions (timeouts, aborts, UNWIND), scheduling (exact WAIT semantics and priorities), and input/output.

Three choices were made before any monitor detail, and each rejected alternative is worth knowing because exam variations often reintroduce one of them.

ChoiceRejected alternativeWhy it lost (paper's reasons)
Shared memory vs. messagesMessage passingLauer and Needham show the two are duals (message ↔ process, process ↔ monitor, send/reply ↔ call/return) "given certain mild restrictions on programming style". Mesa's main structuring tool is the procedure, so monitors integrate with the type system and control structures far more easily. The choice is about fit, not power.
Locks vs. no locksNon-preemptive scheduling as mutual exclusion (optionally with "syntactic sugar" such as pseudo-monitors to mark regions that must not yield)Four reasons, below.

The four reasons against non-preemption. Each one removes a different assumption that non-preemptive mutual exclusion depends on.

  1. It assumes one processor. Mesa was willing to run on one processor but would not "embed this restriction in our basic semantics". On two processors, two processes can be between yield points at the same time, so "no yield" no longer means "no interleaving".
  2. It needs a second scheduling regime for I/O. Voluntary switching is "too sluggish" for time-critical events, so a preemptive mechanism is needed anyway. With preemptive process scheduling, interrupts become ordinary process wakeups, which reduces total machinery and removes the awkward boundary between two regimes. This is the root of naked NOTIFY (M11).
  3. It breaks modularity. Inside a critical section you cannot call any procedure that might yield. In a large system you rarely know that about a callee, and the paper calls this restriction "intolerable".
  4. It is incompatible with virtual memory. A page fault is an involuntary yield. Using non-preemption as mutual exclusion "forbids multiprogramming across page faults", since letting another process run during a fault would insert preemption at an arbitrary point.

What changes if an assumption changes (this guide's reading). Remove virtual memory and reason 4 disappears, but 1 to 3 remain. Add hostile users and the "no protection" choice fails: processes would need hardware isolation, and process operations would stop being cheap. Restrict to a uniprocessor with no page faults and no callees that yield, and the sugared non-preemptive scheme becomes viable again: it is "extremely efficient" for simple problems, which is exactly the trade the cooperative task management paper later revisits (M18).

M2 · Processes: FORK, JOIN, Detach and the PROCESS type

Mesa "casts the creation of a new process as a special procedure activation that executes concurrently with its caller" (§2). Any procedure may be forked, except an INTERNAL procedure of a monitor. The paper's example forks a keyboard routine so the caller can compute while it waits for input:

-- sequential call                       -- concurrent version
buffer ← ReadLine[terminal];             p ← FORK ReadLine[terminal];
                                         ... <concurrent computation> ...
                                         buffer ← JOIN p;

-- the types
ReadLine: PROCEDURE [Device] RETURNS [Line];
p: PROCESS RETURNS [Line];      -- PROCESS is a type generator over result types only

What each line does. FORK ReadLine[terminal] creates a process whose root procedure is ReadLine, passes terminal exactly as a call would (same type checking), and returns at once with a process value p. The parent continues. When ReadLine returns, that return and the parent's JOIN p form a rendezvous "provided automatically": JOIN waits until the child has returned, then yields the child's results with the same typing as a procedure result. PROCESS RETURNS [Line] depends only on result types because the arguments were consumed at FORK time.

Four properties the paper claims (h to k): a process is a first-class value (assignable, storable in arrays, passable as a parameter); parameter passing and results use the procedure mechanism with strict type checking; no special declaration is needed to fork a procedure, and "because of the implementation of procedure calls and other global control transfers in Mesa, there is no extra execution cost for this generality" (M13 explains why: frames come from a heap); and process creation is moderate in cost, with storage "only twice the minimum cost of a procedure instance". Cheapness matters because, as Lauer and Needham note, many synchronization problems have straightforward monitor solutions "only when obtaining a new process is cheap".

Detach. Detach[p] declares that no one will JOIN p. When a detached process's root returns, it is destroyed "without any fuss". From the caller's side this is "similar to freeing a dynamic variable": the value of p may now dangle, because the process can finish and be destroyed at any time. If the program's design guarantees p is still alive, p remains useful as an argument to Abort. The paper reports that detached processes "have turned out to be quite popular", which is one reason JOIN is rare (M16).

Dangling references. A process value is a pointer and must not be used after the process is destroyed. Reference parameters passed to a forked process are pointers too: if they point at local variables of the forking procedure, "that procedure must not return until the process is destroyed". Mesa, like most implementation languages, gives no protection against either.

Exceptions and the root. Mesa searches for a handler from the raising block outward to the procedure body, then in the caller, and so on. The root of a process has no caller, so it "must be prepared to handle any exceptions that can be generated in the process"; otherwise control goes to the debugger. Hence "while any procedure suitable for forking can also be called sequentially, the converse is not generally true" (Part I, §7 above walks through this).

Invariant and assumptions. A process value is valid exactly while its ProcessState belongs to that process (until End, or until JOIN for a non-detached process). The design assumes one trusted user (no protection), a heap-allocated frame model (so a forked activation needs no stack of its own, M13), and programmers who keep reference arguments alive. Break the last assumption and the child reads a freed frame; Mesa will not detect it.

M3 · Monitor modules: ENTRY, INTERNAL, EXTERNAL and the monitor lock

A monitor "unifies the synchronization, the shared data, the body of code which performs the accesses" (§3). The data can be accessed only inside monitor procedures; at most one process executes a monitor procedure at a time (it is "in the monitor"); any other process calling an entry procedure is delayed. The procedures are written next to the data so a reader "can conveniently survey all the references to the data".

Scope = module. To avoid a new lexical construct, a monitor's scope is exactly a Mesa module (the unit of global program structure: procedures plus their global data). A MONITOR module has three kinds of procedures:

What monitors do not give you. They impose no order on calls. An unbounded buffer with Put and Get works for any call order (Get may wait, but that is handled inside). A tape unit with Reserve, Read, Write and Release requires Reserve first and Release last; a second Reserve is delayed, but a Read without a Reserve "will produce chaos". Monitors are "primitive building blocks for more complex scheduling policies", not the policy itself.

Invariant maintained. At most one process is executing any ENTRY or INTERNAL procedure of a given monitor (or a given monitored record, M10). It assumes every access to the protected data happens inside a monitor procedure. The language enforces that for module-global data, because the data is private to the module; it cannot enforce it for data reached through pointers that escape the monitor (inference).

M4 · The monitor invariant and the verification rule

The correctness argument for any monitor (§3.1) rests on an invariant I: a predicate on the protected data that "is always true of its data, except when some process is executing in the monitor". The lock guarantees that nobody can enter while I is false. The rule has two halves:

The paper states the Mesa rule in one sentence (§4): "The monitor invariant must be established just before a return from an entry procedure or a WAIT, and it may be assumed at the start of an entry procedure and just after a WAIT." Because waiters re-test their own predicate explicitly, "verification is actually made simpler and more localized" than under Hoare's rule, where the waiter's proof depends on what the signaler established.

Invariant versus wait predicate. These are different things. The invariant holds whenever the lock is free. The predicate a waiter needs (for example "the stack is not full") is not part of the invariant, because it is legitimately false at times; it is re-tested in the loop around WAIT. Mixing the two up is the usual error when writing an invariant.

M6 · WAIT and NOTIFY: Mesa semantics versus Hoare semantics

Hoare's definition (§4): "a process waiting on a condition variable must run immediately when another process signals that variable, and ... the signaling process in turn runs as soon as the waiter leaves the monitor." The monitor lock passes directly from signaler to waiter and back. Because nothing else can run in between, the waiter may assume a predicate stronger than the invariant (whatever the signaler established), so IF NOT ok THEN WAIT c suffices. The paper names two costs: "several additional process switches whenever a process continues after a WAIT", and the signaling mechanism must be "perfectly reliable" (a lost or spurious signal would break a proof that relies on it).

Mesa's definition. A NOTIFY "is regarded as a hint to a waiting process; it causes execution of some process waiting on the condition to resume at some convenient future time." When the waiter resumes it re-acquires the monitor lock, and "there is no guarantee that some other process will not enter the monitor before the waiting process". So "nothing more than the monitor invariant may be assumed after a WAIT", and the required pattern is WHILE NOT <OK to proceed> DO WAIT c ENDLOOP. The price is one extra evaluation of the predicate per wakeup. The return is "no extra process switches, and indeed no constraints at all on when the waiting process must run after a NOTIFY". The paper adds: "it is perfectly all right to run the waiting process even if there is no NOTIFY". Spurious wakeups are legal by definition.

-- WAIT c, inside a monitor procedure, lock L held (steps per §4 and §5.1; ordering is this guide's reconstruction)
WAIT(c):
    -- precondition: invariant I holds
    if c is device-notified and c.wakeupWaiting then c.wakeupWaiting ← FALSE; return   -- M11
    move self: ready queue → c's queue (priority-sorted)          -- these two steps are one
    release L (a process queued on L may now proceed)            -- indivisible machine operation
    -- blocked until NOTIFY, BROADCAST, timeout, or Abort moves self back to the ready queue
    when scheduled: re-acquire L, queueing on L if it is held
    if aborted then raise Aborted                                   -- M7
    return                                                       -- only I may be assumed

NOTIFY(c):     -- caller holds L and keeps it
    if c's queue is empty then return        -- 4 ticks; nothing is remembered (except via the switch, M11)
    move head of c's queue → ready queue      -- 9 ticks; no process switch is forced at equal priority

Why "release and enqueue" must be one step. If WAIT released the lock and only then joined the queue, a notifier could enter in the gap, change the state, find the queue empty and NOTIFY nobody; the waiter would then sleep with its predicate already true. Doing both inside one microcoded operation on a uniprocessor closes the gap (inference: the paper does not describe WAIT's internal step order, but the naked-NOTIFY discussion in §4.2 relies on exactly this property for ordinary processes).

Which waiter does NOTIFY pick? The paper says "some process waiting". Since every queue "is kept sorted by process priority" and removal is at the head, the natural reading is the highest-priority waiter, FIFO among equals (inference from §5.1). In particular NOTIFY does not look at what each waiter needs.

What happens right after NOTIFY (inference from the scheduling rule in §5.1, which the paper does not apply to this case). If the waiter's priority is equal to or lower than the notifier's, it sits in the ready queue and the notifier keeps running: zero switches. If the waiter's priority is higher, the processor's check before the next instruction switches to it at once; it then tries to re-acquire the lock, which the notifier still holds, and goes onto the lock queue; the notifier resumes, finishes and releases. That costs two switches for nothing, the case the lecture described as the woken thread "tripping over" the lock.

Fairness. The paper concedes that this "laissez-faire attitude to scheduling monitor accesses" may lead to unfairness and even starvation, and argues it does not matter: "in a properly designed system there should typically be no processes waiting for a monitor lock". High-level scheduling (who gets the printer next) should be done by a scheduler that records each client's requirements, delays clients on condition variables, decides, and notifies the right condition. "In such a design the data protected by a monitor is never a bottleneck."

From the lecture. Rosenblum first had the stack wait with while top == N do sleep(1) inside the monitor and asked why it fails. It spins while holding the monitor lock, so no pop can ever enter and top never changes: "a quick way to a deadlock". His mental model: "a condition variable is a list" of waiting threads; WAIT puts you on it and releases the lock, signal takes one off. The Mesa implementers found loaning the lock through the scheduler "a kind of a yucky thing to do" and made signal just wake the thread, which then has to fight for the lock. Break it (an IF) and correctness depends on an ordering Mesa never promises. M7 · Because NOTIFY is a hint: covering conditions, BROADCAST, timeouts and Abort

Once the waiter is responsible for re-checking, anything that wakes it is safe. The paper draws four consequences (§4, §4.1), and states that "none of these mechanisms affects the proof rule for monitors at all. Each provides a way to attract the attention of a waiting process at an appropriate time."

Covering condition variables. Many applications "do not trouble to determine whether the exact condition needed by a waiter has been established. Instead, they choose a very cheap predicate which implies the exact condition (for example, some change has occurred), and NOTIFY a covering condition variable." Example: processes waiting for a particular object in a set to change state share one condition covering the whole set; any change broadcasts to it. Which objects are of interest "is implicit in the states of the waiting processes, rather than having to be represented explicitly in a shared data structure". The paper says this decoupling is feasible "because the cost of waking up a process is small". Violet's file suites (M17) are built this way with one condition, CrowdLarger.

BROADCAST. "Since a NOTIFY is just a hint, it is always correct to use BROADCAST." Each woken process moves to the ready queue, then re-acquires the lock one at a time, re-tests, and either proceeds or waits again. Choosing between them, in the paper's words: NOTIFY is better "if there will typically be several processes waiting on the condition, and it is known that any waiting process can respond properly"; but "there are times when a BROADCAST is correct and a NOTIFY is not". The cost side is not quantified: the paper gives no tick count for BROADCAST, and every woken waiter pays a lock acquisition and a predicate test whether or not it proceeds. BROADCAST only makes sense under hint semantics; under Hoare's rule only one waiter can be handed the lock.

Timeouts. Each condition variable has a timeout interval (set through a runtime utility routine, §5.2). The design history: the original version raised an exception on timeout; it was changed because "many users simply wanted to retry on a timeout, and objected to the cost and coding complexity of handling the exception. This decision could certainly go either way." Implementation (§5.1): "at a fixed interval (about 20 times per second) the processor scans the table of ProcessStates and notifies any waiting processes whose timeout intervals have expired". This special NOTIFY is tricky because the processor does not know which condition variable each process is waiting on, so it cannot update that condition's queue cell. The solution is to leave the queue cell out of date and mark the process "in such a way that the next normal usage of the queue cells will notice the situation and update them appropriately". Two consequences (inference): timeouts have roughly 50 ms granularity, and a condition's queue cell may briefly name a process that has already left.

Abort. Abort[p]: "the next time the process waits, or if it is waiting now, it will resume immediately and the Aborted exception will occur." It lets one process "gently prod another, generally to suggest that it should clean up and terminate". The target "is, however, free to do arbitrary computations, or indeed to ignore the abort entirely". Abort acts only at WAITs, so a process that computes without waiting cannot be aborted: "there is no way to stop a runaway process", reflecting that Mesa processes are cooperative. The paper adds that many aspects of the design "would not be appropriate in a competitive environment such as a general-purpose timesharing system". If an aborted process is inside an ENTRY procedure when Aborted is raised, the exception rules of M9 apply.

M8 · Nested monitor calls and the three deadlock patterns

The rule (§3.1). WAIT releases the lock of the monitor it is executed in, including when executed in an INTERNAL procedure. "If, however, the monitor calls some other procedure which is outside the monitor module, the lock is not released, even if the other procedure is in (or calls) another monitor and ends up doing a WAIT." Concurrent Pascal uses the same rule.

Why. If a WAIT inside another monitor released this monitor's lock too, the invariant of this monitor "would have to be established before making the call which leads to the WAIT. Since in general there is no way to know whether a call outside the monitor will lead to a WAIT, the invariant would have to be established before every such call", which would make calling out "hopelessly cumbersome". The rule keeps a module's correctness argument local: a caller does not need to know whether a callee waits.

A rejected middle ground: the "outside block". The paper sketches a construct written inside a monitor: on entry to the block the lock is released (so the invariant must be established), the protected data is inaccessible inside it, and on exit the lock is re-acquired. It would keep the monitor procedure's local state across an outside call at the cost of one obligation (establish I before the block). It "would be easy to add to Mesa"; they left it out because they had "not seen convincing examples in which it significantly simplifies the program".

Three pairwise deadlock patterns (§3.2), plus one single-process case:

  1. Two WAITs inside one monitor, each expecting the other to notify. A local bug, "usually easy to locate and correct".
  2. Cyclic calls between monitors: M calls an entry of N while N calls an entry of M; each holds its own lock and waits for the other's. Monitors make this "neither more nor less serious". Cure: a partial order on resources such that everything a process holds at once is totally ordered and acquired in that order; for monitors this "reduces to the simple rule that mutually recursive monitors must be avoided". Concurrent Pascal checks this at compile time; Mesa cannot, "because it has procedure variables" (the callee is not known statically).
  3. Waiting in a nested call ("a more serious problem"): M calls N, and N waits for a condition that can only become true "when another process enters N through M and makes the condition true". N's lock is released by the WAIT; M's is not, so the other process blocks at M's door. A lock order does not prevent this, because only one lock acquisition is in the cycle; the other edge is a condition wait. Cure: split M into a monitor M′ holding the shared data and an ordinary module O that implements M's abstraction, calls M′ for access to the data, and makes the call on N itself, without holding M′'s lock.
  4. Self-deadlock: one process re-entering a monitor it already holds, for example a recursive entry procedure.

The paper's position: monitors are a tool for implementing constraints the programmer chooses, and "it is unreasonable to blame the tool when poorly chosen constraints lead to deadlock"; the tool should keep the structure understandable without, for example, "forcing a monitor lock to be held much longer than necessary". The experience in Pilot: "somewhere between one and two dozen distinct deadlocks", all "fixed relatively easily without any global disruption of the system's structure" (§6.1).

M9 · Exceptions: RETURN WITH ERROR and UNWIND

Raising from inside an entry procedure (§3.1). If an entry procedure raises an exception "in the usual way", the handler is called from within the monitor, as a procedure call, so the lock is still held while the handler runs. The handler "must carefully avoid invoking that same monitor, or a deadlock will result". To avoid this, an entry procedure can restore the invariant and execute RETURN WITH ERROR[(arguments)], which "returns from the entry procedure, thus releasing the lock, and then generates the exception" in the caller.

UNWIND (§3.4). Suppose P1 calls P2, which calls P3, and so on to Pn. Pn raises an exception that P2 to Pn do not handle and P1 does. Mesa lets P1's handler abandon the work of P2 ... Pn and continue in P1. Before doing so, "a distinguished exception called UNWIND is first generated, and each of P2 ... Pn is given a chance to handle it and do any necessary cleanup before its activation is destroyed." UNWIND is a sequential feature; the interaction with monitors is this: if some Pi is an entry procedure, "the invariant must be restored and the monitor lock released before Pi is destroyed." The programmer writes an UNWIND handler in Pi that restores the invariant; "Mesa will automatically supply the code to release the lock." If the programmer supplies no UNWIND handler, "the lock is not automatically released, but remains set; the cause of the resulting deadlock is not hard to find."

-- shape of an entry procedure that may be abandoned (illustrative Mesa-like syntax, not from the paper)
Withdraw: ENTRY PROCEDURE [n: INTEGER] = BEGIN
  ENABLE UNWIND => <restore the invariant>;   -- compiler appends: release the monitor lock
  IF balance < n THEN RETURN WITH ERROR Insufficient[balance];  -- I must hold here
  <update, possibly calling out of the monitor, which may raise>
  END;

Why the lock is not released when there is no handler (this guide's reading, consistent with the paper's wording). Releasing it would let the next caller enter a monitor whose invariant is possibly broken, which is silent corruption. Keeping it set turns the mistake into a deadlock at the next entry, which is loud and, on a single-user workstation with a debugger, easy to diagnose. The trade is the same one that makes an uncaught exception in a process root go to the debugger (M2).

Experience. Pilot lists "the interaction of the concurrency and exception facilities" as one of two areas that "caused annoying problems": "the reasonable and consistent handling of signals (including UNWINDs) in entry procedures represents a considerable increase in the mental overhead involved in designing a new monitor or understanding an existing one" (§6.1).

M10 · Monitored records and the LOCKS clause

The problem (§3.3). A program often has a dynamic collection of similar shared objects (files, storage volumes, virtual circuits, database views) and must serialize access to each one. The paper ranks three designs:

  1. One monitor for all instances. "We recommend this approach whenever possible." Its cost: if the objects are mostly independent, a single lock "drastically reduces the maximum concurrency that can be obtained".
  2. One instance of the monitor module per object. "Mesa makes this quite easy, and it is the next recommended approach." Its costs: a module instance carries "information that the Mesa system uses to support program linking and code swapping", duplicated per instance; and module instances "are allocated by the system", so the program cannot control their allocation the way it can for ordinary records. The code itself is shared.
  3. A monitored record. A new type constructor, "exactly like an ordinary record, except that it includes a monitor lock and is intended to be used as the protected data of a monitor". One monitor module, one copy of its code and global frame, any number of records, each with its own lock, allocated however the program likes.

The LOCKS clause. Since the lock now lives in data the monitor's code reaches at run time, the programmer must say how to find it, "written at the beginning of the module":

MONITOR LOCKS file USING file: POINTER TO FileData;          -- the paper's example
MONITOR LOCKS file.buffers[currentPage] ...                    -- any expression is allowed

-- semantics implied by §3.3 (this guide's sketch)
call of an ENTRY procedure:  acquire( lockOf(<LOCKS expression>) )
WAIT inside a monitor procedure:  release and later re-acquire lockOf(<LOCKS expression>)
return from the ENTRY procedure:  release( lockOf(<LOCKS expression>) )   -- evaluated again

"Every entry procedure of this monitor, and every internal procedure that does a WAIT, must have access to a file, so that it can acquire and release the lock upon entry or around a WAIT." There are two ways: file is a global variable of the module, or it is a parameter of every such procedure. With the parameter form, "we have effectively created a separate monitor for each object, without limiting the program's freedom to arrange access paths and storage allocation as it likes". An INTERNAL procedure that never WAITs does not need file, because it neither acquires nor releases.

The hole the paper admits. "The type system of Mesa is not strong enough to make this construction completely safe. If the value of file is changed within an entry procedure ... the return from this procedure will release not the lock which was acquired during the call, but some other lock instead." One lock stays held forever and another is released while someone else may hold it. Making file read-only would fix the direct case, "but with another level of indirection aliasing can occur and such a restriction cannot be enforced". The paper's verdict: "In practice this lack of safety has not been a problem." The invariant the clause relies on is therefore the LOCKS expression denotes the same lock at entry, around every WAIT, and at exit, and it is a programmer obligation, not a language guarantee.

Not specified in the paper: where the condition variables of a per-record monitor live (a per-record condition would naturally sit in the record), and whether anything checks that the record being accessed is the one whose lock is held. Operations that touch two records need two locks, which brings back the lock-ordering discipline of M8 (inference).

M11 · Naked NOTIFY and the wakeup-waiting switch

Setting (§4.2). Devices communicate with Mesa code through a shared data structure "whose details are determined by the hardware", used to pass commands and return status. "Since it is not possible for the device to wait on a monitor lock, the update operations on this structure must be designed so that the single word atomic read and write operations provided by the memory are sufficient to make them atomic." When the device needs attention it NOTIFYs a condition variable whose address it finds "in a fixed memory location", waking the process that plays the interrupt handler. Because the device holds no monitor lock, this is a naked NOTIFY.

The race. A process is in the monitor, finds <OK to proceed> FALSE (the device does not need attention), and is about to WAIT. In that window the device updates the shared data and NOTIFYs. "The WAIT will then be done and the NOTIFY from the device will be lost." Between ordinary processes this cannot happen: the notifier must hold the same lock to change the predicate, so it cannot act between the waiter's test and its WAIT, and WAIT's enqueue-and-release is a single step (M6).

The fix. The condition variable gets "the familiar wakeup-waiting switch" from Saltzer's 1966 thesis, "thus turning it into a binary semaphore". The switch "is needed only for condition variables that are notified by devices". The paper does not spell out the operations; the standard semantics of a wakeup-waiting switch, which matches "binary semaphore", are:

-- device side, no lock (naked)
NOTIFY(c):  if c's queue non-empty then move head to ready queue
             else c.wakeupWaiting ← TRUE                 -- remember one early wakeup

-- process side, inside the monitor
WHILE NOT deviceNeedsService[] DO WAIT c ENDLOOP;
WAIT(c):    if c.wakeupWaiting then { c.wakeupWaiting ← FALSE; return }   -- do not sleep
             else enqueue on c and release the lock, as usual

One bit suffices because the waiter re-reads the device state in its loop after every return from WAIT: several notifies that arrive while nobody waits collapse into one "go and look", and looking once sees everything the device has posted (inference). The switch adds memory only to the conditions that need it; ordinary conditions keep the "a NOTIFY with no waiter is a no-op" behavior.

The rejected alternative. Devices could "wait on and acquire the monitor lock, exactly like ordinary Mesa processes", which would avoid "both the anomalies just discussed" (the lost notify and the absence of mutual exclusion on the device data). The objection is general: with mutual exclusion between processors of very different speeds, "the faster process may have to wait for the slower one. The worst-case response time of the faster process therefore cannot be less than the time the slower one needs to finish its critical section." You can get more throughput from the faster processor, but not better worst-case real-time behavior; the authors call this "a fundamental deficiency". So there is no mutual exclusion between Mesa code and device hardware or microcode, except single-word atomic reads and writes. Their relationship is cast as producer and consumer over linked lists or arrays, which needs only the memory's own atomicity. "Clearly a change of models must occur at some point between a disk head and an application program"; the paper places it inside a small, "tightly encapsulated" piece of Mesa code.

How an interrupt actually becomes a running process (§5.1). The device's NOTIFY moves the handler process to the ready queue. The processor checks "before each instruction" whether the highest-priority ready process is the one running, and switches if not: "this is the mechanism by which interrupts are serviced". Interrupt handler processes run at high priority (the gateway's drivers are "a high priority interrupt process" plus a monitor, M17), so the switch happens on the next instruction.

The cost the paper reports. In Pilot, "the lack of mutual exclusion in the handling of interrupts" caused "subtle bugs ... due to timing races between I/O devices and their handlers". The authors suspect "the illusion of mutual exclusion provided by the casting of interrupt code as a monitor may have contributed", but still judge the "economy of mechanism" worth it (§6.1).

Invariant and assumptions. The invariant is: a device notification that arrives while no process is waiting is not lost; it is consumed by the next WAIT on that condition. It assumes the device-side update and the switch write are each single-word atomic; that there is one consumer per device condition (a binary bit cannot count wakeups for several consumers, inference); and that the consumer re-tests the device state, which the WHILE discipline already requires.

M12 · Priorities and priority inversion

The scheduler (§5.1) is "preemptive between priorities and FIFO within a given priority": before each instruction the processor makes sure it is running the highest-priority ready process. That makes priority order the system's only notion of urgency, and monitors can subvert it (§4.3). The paper's scenario uses three priority levels (3 highest) and processes P1, P2, P3, one at each level; P1 and P3 share monitor M:

  1. P1 enters M.
  2. P1 is preempted by P2.
  3. P2 is preempted by P3.
  4. P3 tries to enter M and waits for the lock.
  5. P2 runs again and "can effectively prevent P3 from running, contrary to the purpose of the priorities".

The Part I figure above (section 4) draws these steps. The structural cause: P3 is blocked on a lock, so it is not in the ready queue; the scheduler sees only P1 and P2 and correctly picks P2; P1, the only process that can release the lock, never runs while P2 is ready.

The paper's proposal. "Associate with each monitor the priority of the highest priority process which ever enters that monitor. Then whenever a process enters a monitor, its priority is temporarily increased to the monitor's priority." In the scenario, P1 runs inside M at priority 3 (once M has seen P3), so P2 cannot preempt it at step 2. This is a ceiling scheme: the boost happens on entry, before anyone is blocked, and the ceiling is learned from history (the word "ever"). Two consequences (inference): the very first time a high-priority process uses a monitor, its ceiling is not yet raised and the inversion can still occur; and every entry pays the boost and restore, even when no high-priority process is anywhere near.

Modula's alternative. Disable interrupts on entry to M, which gives the process the highest possible priority and also serves as M's lock. "This approach fails if a page fault can occur while executing in M": servicing the fault needs other processes (a fault queue and a handler process, §5.1) to run while M's holder is stuck. It also assumes one processor (inference).

Whether it is needed. "The mechanism is not free, and whether or not it is needed depends on the application." If only processes with adjacent priorities share a monitor, there is no level between them for a third process to occupy, so the scenario "cannot occur". Otherwise "the problem may occur rarely, and absolute enforcement of the priority scheduling may not be important." The paper describes the ceiling as "a simple way to avoid this situation"; it does not state whether Pilot implements it, and this guide cannot confirm that from the paper.

What breaks under other assumptions (inference). With time slicing among equal priorities (which Mesa did not have, M13) a same-priority holder would eventually run, but a lower-priority holder still would not. On a multiprocessor P1 could run on another CPU and release M, shrinking but not removing the problem.

M13 · The processor: frames, ProcessStates, queues and scheduling

Division of labor (§5). The implementation is split "more or less equally" among the compiler (syntax, static checks, implicit calls to built-in support procedures), the runtime package (less frequent operations: process creation and destruction), and the underlying machine (frequent operations: process scheduling and monitor entry and exit). The split was chosen by "frequency of use, rather than cleanliness of abstraction", yet turned out to be "a fairly clean layering, in which the birth and death of processes are implemented on top of monitors and process scheduling".

What a process is. "The existence of a process is normally represented only by its stack of procedure activation records or frames, plus a small (10-byte) description called a ProcessState." There is no other per-process structure: no kernel stack, no address space, no protection state (M1).

How frames are allocated, and why it matters for thread stacks. Frames are not carved from a contiguous per-process stack. They "are allocated from a frame heap by a microcoded allocator":

  • Frame sizes come in classes that "differ by 20 percent to 30 percent", with "a separate free list for each size up to a few hundred bytes (about 15 sizes)". A call pops a frame from its size's free list; a return pushes it back. "Allocating and freeing frames are thus very fast, except when more frames of a given size are needed."
  • If the list for a size is empty, a frame fault occurs and "the fault handler allocates more frames in virtual memory". A frame fault is handled through the fault queue like a page fault.
  • "Resident procedures have a private frame heap that is replenished by seizing real memory from the virtual memory manager." The likely reason (inference): code that runs while handling faults must not itself page fault on frame allocation.
  • "Because all frames come from the heap, there is no need to preplan the stack space needed by a process."

A process's "stack" is therefore a chain of frames linked by return links, each living wherever the allocator found it. Three consequences follow directly. A FORK is a procedure activation whose frame simply has no caller; nothing needs a new contiguous region, which is why the paper can say forking needs no special declaration and costs nothing extra in the call mechanism (§2, property j). A blocked process's frames stay where they are; switching processes changes which chain is current. And the memory a process uses at any moment is the frames it actually has live, rounded up to a size class, not a reservation sized for the worst case. The cost is internal fragmentation of up to the class spacing per frame, and an allocator operation on every call and return (inference).

ProcessStates and queues. ProcessStates live in "a fixed table known to the processor; the size of this table determines the maximum number of processes". At any time a ProcessState is "on exactly one queue" of four kinds: the single ready queue; a monitor lock queue (a process that tries to enter a locked monitor moves there from the ready queue); a condition variable queue (WAIT moves the process there); a fault queue (a process that cannot run because of a fault moves there, "and a fault handling process is notified"). The figure at the top of Part II shows the moves.

Queue structure (the paper's Figure 1). Each queue is "a simple one way circular list, with the queue cell pointing to the tail of the queue". Because the tail's link points to the head, one pointer gives O(1) access to both ends: insertion at the tail and removal at the head are quick; "more general insertion and deletion involve scanning some fraction of the queue". Queues are "kept sorted by process priority", so inserting a process ahead of lower-priority ones requires that scan. The paper argues this is fine: queues are usually short, and the ready queue, the only one that grows large, has insertion and deletion patterns that keep scanning overhead small.

The scheduling rule, exactly. "The queue cell of the ready queue is kept in a fixed location known to the processor, whose fundamental task is to always execute the next instruction of the highest priority ready process. To this end, a check is made before each instruction, and a process switch is done if necessary." The machine "thus implements a simple priority scheduler, which is preemptive between priorities and FIFO within a given priority". And: "There is no provision for time-slicing in the current implementation, but it could easily be added, since it has no effect on the semantics of processes."

Put together, a running process keeps the processor until one of these happens: it WAITs; it tries to enter a locked monitor; it takes a fault; it finishes; a process of strictly higher priority becomes ready (through a NOTIFY, a device's naked NOTIFY, a timeout, a fault being resolved, or a lock being released); or it calls Process.Yield, which the runtime provides for processes that "compute too long" (§5.2). A ready process of the same priority never preempts it; it waits its FIFO turn. Equal-priority processes are therefore scheduled cooperatively with respect to each other, while higher priorities preempt immediately (this guide's summary of the stated rules).

Other queue mechanics. Queues other than the ready list "are passed to the processor by software as operands of instructions, or through a trap vector in the case of fault queues". A monitor lock is a small record holding its queue cell and "the actual lock"; a condition variable holds its queue cell, "the timeout interval and the wakeup-waiting switch". This is the economy the paper promised when rejecting semaphores (M1): one queue mechanism serves locks, conditions, faults and the ready list.

He wanted a third: Mesa is "a lot like the Go language today": any routine can be forked onto its own thread, and with frames on the heap the forker can return without disturbing the forked thread, which runs in its own frames. M14 · The runtime: Fork, Join, End, Detach, Abort and Yield

The Process module of the runtime (§5.2) is itself written in Mesa as a monitor, using the processor's queues and monitor instructions. FORK and JOIN compile into calls of its entry procedures Process.Fork and Process.Join. The trick that makes this small: "the unused ProcessStates are treated as essentially normal processes which are all waiting on a condition variable called rebirth".

-- this guide's reconstruction of §5.2; only the quoted behavior is from the paper
Process: MONITOR = BEGIN
  rebirth: CONDITION;                       -- every unused ProcessState waits here

  Fork: ENTRY PROCEDURE [root, args] RETURNS [p: PROCESS] =
    p ← first ProcessState on rebirth's queue;
    <"brain surgery": make p start in root with args in a fresh frame>;
    NOTIFY rebirth;                         -- "to bring the process to life"

  End: ENTRY PROCEDURE =                    -- called implicitly when the root returns
    IF not detached THEN <synchronize with the joining process; hand over results>;
    WAIT rebirth;                           -- "commits suicide by waiting on rebirth"

  Join: ENTRY PROCEDURE [p] RETURNS [results] =
    <synchronize with the dying process p; retrieve its results>;

  Detach: ENTRY PROCEDURE [p] =
    <mark p so that End destroys it immediately>;
  END.

So creation is a NOTIFY on rebirth after editing a sleeping process, and death is a WAIT on rebirth. Nothing is allocated or freed in the ProcessState table at run time; its size caps the number of processes. The paper does not say what Fork does when no ProcessState is waiting on rebirth; with Mesa semantics the natural shape would be a WAIT loop, but that is a guess.

Abort and Yield "are provided to allow special handling of processes that wait too long and compute too long, respectively. Both adjust the states of the appropriate queues, using the machine's standard queueing mechanisms." Yield is how a long computation lets same-priority processes run, given no time slicing (M13). The runtime also provides utility routines to set a condition variable's timeout and to set a process's priority.

Cost. FORK plus JOIN costs at least 1,100 ticks, "about 38 times that of a procedure call", because they are written in software on top of the monitor machinery. The authors still think this was right: these facilities are "considerably more complex than the basic synchronization mechanism, and are used much less frequently (especially JOIN, since the detached processes ... have turned out to be quite popular)". Code size: FORK and JOIN together compile to 13 bytes versus 3 for a call and return, plus 2 data bytes for the process value (M16).

M15 · The compiler

The compiler (§5.3) recognizes the process and monitor constructs and emits code for them: "a MONITORENTRY instruction at the start of each entry procedure", the matching exit on return, and "an implicit call of Process.Fork for each FORK". It also performs static checks for common errors: "use of WAIT in an external procedure is flagged as an error, as is a direct call from an external procedure to an internal one". Both checks enforce the same thing: code that runs without the monitor lock may neither release it (WAIT) nor run code that assumes it is held (INTERNAL). The compiler cannot check that the lock is not re-entered (ENTRY calling ENTRY directly or through other code) or that monitors are not mutually recursive, because Mesa has procedure variables (§3.2). Because Mesa's control-transfer primitives were already general (frames on a heap, M13), adding processes and monitors "resulted in remarkably little upheaval inside the compiler".

No contended case (a monitor entry that must queue, then a switch); no cost for BROADCAST, timeouts (the 20-per-second scan), Abort, or a frame fault; nothing about multiprocessors; and no measured Hoare-style implementation to compare against. The claim that Mesa semantics saves switches is an argument from the semantics (M6), not a measurement.

The authors' verdict. The implementation "has met our efficiency goals, with the possible exception of FORK and JOIN", whose "somewhat lackluster performance" is mainly due to implementing them in software rather than in the machine; they still regard that decision as sound (M14).

From the lecture. The slides reproduced the time table. Rosenblum tied the numbers to the microcoded CPU: designers could either add microcode for an operation or write it in Mesa. NOTIFY was a single microcoded instruction, which is why an empty NOTIFY costs 4 ticks and even waking someone only 9, "sort of stunningly fast". For FORK and JOIN "they kind of chickened out" on writing microcode and wrote them in Mesa, so they cost about a thousand ticks. The slides also gave the class's picture of PARC hardware of the era (a microcoded CPU of about 5.88 MHz, 100 KB of RAM, a 2.5 MB disk); the paper itself describes Pilot's machine only as "a large personal computer".

M17 · The three applications: Pilot, Violet, Gateway

Pilot (§6.1), the operating system. Designed together with the language features. It has autonomous processes of its own and "can be called by any number of client processes of any priority, in a fully asynchronous manner". About 75 program modules contain nearly 40 monitors. About 15 dedicated processes (the number depends on the hardware configuration), mostly event handlers for three classes of events: I/O interrupts (naked notifies, M11); process faults such as page faults (fault queues, M13), which client code and the higher levels of Pilot can both cause; and internal exceptions, such as a missing entry in a resident database waking a "helper" process to fetch it from secondary storage. A few daemons wake periodically for housekeeping (for example, swapping out unreferenced pages). "Essentially all" of Pilot's processes and monitors are created at initialization, with interrupt handler processes matched to the hardware found; the running system makes no use of dynamic process and monitor creation, "largely because much of Pilot is involved in implementing facilities such as virtual memory which are themselves used by the dynamic creation software". One to two dozen deadlocks were found over the system's life, all fixed easily. The two problem areas were interrupt races and exceptions in monitors (M9, M11).

Violet (§6.2), a distributed calendar system over a replicated database. The paper's Figure 2 is a five-level hierarchy (each level calls the ones below):

The user interface has three processes. Display keeps the screen consistent with the user's views and with database changes; it only reads lower levels, never updates. Keyboard handles user-initiated changes. DataChanges is FORKed from Transactions when data being viewed changes, and disappears after reporting to Display. FileSuites builds one replicated file from representatives stored in a transactional file system, each with a version number; one monitor per file suite tracks the known representatives. On creation a suite FORKs and detaches one inquiry process per representative; each reads its representative's version, reports it to the monitor, and NOTIFYs CrowdLarger. A reader waits on CrowdLarger until it has a read quorum. A writer collects a write quorum containing the current version (again waiting on CrowdLarger), FORKs an update process per representative, then JOINs each in turn; all run in one transaction, so all or none are written. If only a read quorum is reachable, the writer FORKs copy processes to bring stale representatives up to date. Up to three processes per representative per file, yet in the normal case "only one monitor call is required to collect a quorum", and the whole structure "is held together by a single monitor containing an array of representative states and a single condition variable": a covering condition (M7) in practice.

Gateway (§6.3), an internetwork packet forwarder. Each device driver is typically "a high priority interrupt process, and a monitor for synchronizing with the device and with non-interrupt-level software". Each Ethernet driver has two processes, the interrupt process and a background process for timeouts and other infrequent events; the common-carrier line driver adds a third that makes a set of lines resemble one Ethernet by "iteratively simulating a broadcast". The dispatcher is a monitor plus a dedicated process: on input, the interrupt process handles the interrupt, notifies the dispatcher, "and immediately returns to await the next interrupt"; the dispatcher hands the packet to a socket's procedure. The router is a monitor holding the routing table (network name to next-hop gateway) plus a housekeeping process that exchanges routing packets. Output is asymmetric: the sending process itself calls into the router monitor, then directly into the driver's monitor. Forwarding a packet is input up to the dispatcher followed by a normal transmission, so "the most critical path (forwarding a message) involves only a single switch between a pair of processes".

M18 · Mechanical connections to other CS240 papers

🔗
Eraser (lockset race detection). In Eraser's terms, every ENTRY procedure is a lock acquire at entry and a release at every exit; WAIT is a release followed later by a re-acquire of the same lock; a monitored record contributes a different lock per record, chosen by the LOCKS expression at run time (M10). A thread inside M that calls an ENTRY procedure of N holds two locks, which is how a Mesa lockset can contain more than one lock. Three kinds of Mesa data fall outside the monitor-lock discipline and would be seen by a lockset checker as unprotected: data shared with devices through single-word atomic reads and writes (M11), data reached through pointers that escape a monitor, and anything an EXTERNAL procedure touches directly. Conversely, a lockset checker sees nothing wrong with logic errors made while holding the right lock, such as an IF instead of a WHILE (M6) or a check-then-act split across two separate ENTRY calls.
🔗
Cooperative task management without manual stack management (Adya et al.). That paper separates task management (preemptive versus cooperative) from stack management (automatic versus manual). Mesa sits at preemptive plus automatic, and §1 here is an explicit argument against cooperative scheduling as mutual exclusion (M1, the four reasons). Mesa's scheduler is nevertheless cooperative among equal priorities, because there is no time slicing (M13). On stack management, the relevant Mesa mechanism is where a blocked computation's state lives: in heap-allocated frames that stay put while the process waits (M13). Compare that with what an event handler must do with its live variables when it has to wait.
🔗
Threads versus events (Ousterhout; von Behren et al.). Mesa is the strongest historical case for threads: the only concurrency mechanism on the machine, cheap enough (process switch 60 ticks, FORK+JOIN 1,100) to use processes as a structuring tool, with language support to tame locking. Ousterhout's objections (locking is hard, deadlock, hard to debug) are exactly the costs M8 and M9 document, including Pilot's one to two dozen deadlocks and the "mental overhead" of exceptions in monitors. Lauer and Needham's duality, which §1 cites, is the formal version of the claim that the two styles are equivalent in power.
🔗
Receive livelock (Mogul and Ramakrishnan). Mesa's "replacing interrupts" design turns each device interrupt into a naked NOTIFY that readies a high-priority handler process, which preempts anything of lower priority at the next instruction (M11, M13). How much work runs at that priority, and whether lower-priority processing ever gets the processor, is decided entirely by which processes do the work and at what priority, by whether they ever WAIT or Yield, and by the fact that equal-priority processes never preempt each other. The gateway (M17) is a Mesa system with this exact structure: interrupt process, dispatcher process, router.

Worked examples

Four traces through the paper's own measurements and code — tick costs, byte costs, and the priority-inversion scenario, fully unpacked.

These four aren't an arbitrary sample of "numbers from the paper" — they check the paper's two central claims about cost (①②③) and its one central claim about correctness (④), each against the paper's own raw figures rather than its prose summary of them. ① and ② are both about time: ① checks whether the primitives Mesa actually optimized for (monitor entry, WAIT, NOTIFY) are cheap on the common path, and ② stress-tests that claim by checking the one primitive (FORK+JOIN) that the paper deliberately left expensive. ③ switches axes to size — bytes, not ticks — because "cheap enough to use at fine grain" is a claim about code/data footprint that the tick table can't answer. ④ is the odd one out: not a cost check at all, but a correctness trace showing why the priority-ceiling fix actually prevents the specific inversion the paper describes, step by step. Each card below opens with why that particular trace earns a place in this list before walking through what it computes.

① From plain call to full process switch — reading the tick table

🎯
Why this is a worked example: the paper's whole case for signal-and-continue over Hoare's signal-and-wait rests on the prose claim that it "avoids unnecessary process switches" — but that's qualitative. This is the one place the paper hands you tick counts for every primitive being compared (call, monitor call, WAIT, NOTIFY, switch) in the same units, so it's the only way to turn "cheaper" into an audited number instead of a claim you take on faith. Everything downstream in card ② — "37× is fine because it's rare" — presupposes that the common path checked out cheap here first.

The paper reports: simple instruction = 1 tick; call+return = 30; monitor call+return = 50; process switch = 60. What does each increment actually buy, and how big is it in percentage terms?

  1. Monitor overhead: 50 − 30 = 20 extra ticks for the entry/exit lock protocol, on top of a normal call+return. As a fraction of the base cost: 20 / 30 ≈ 67% — matching the paper's own "about 70 percent more."
  2. A monitor call is still cheaper than a process switch (50 vs 60 ticks). An uncontended monitor entry never requires switching to a different process; a switch happens only if the lock is held (the caller queues on it) or the procedure WAITs.
  3. WAIT costs 15 ticks — a quarter of a full process switch — because it does queue bookkeeping but the actual context switch is deferred until the processor picks a new highest-priority ready process, which may not even be this one.
  4. NOTIFY costs 4 ticks with no one waiting, 9 with someone waiting — cheap either way, since it never itself forces a switch under signal-and-continue.
🍯
Insight: nothing in the WAIT/NOTIFY pair costs anywhere near a full 60-tick switch — that's the entire payoff of treating NOTIFY as a hint instead of a guaranteed handoff. The bars make the shape of the argument visible: WAIT and both NOTIFYs are short, call and monitor-call are mid-height and close together, and only a full switch is tall — signal-and-continue keeps the common path down near the left three bars, paying the tall bar only when a process genuinely has nothing else to do.

② FORK+JOIN's 37× overhead — and why the paper accepts it

🎯
Why this is a worked example: once card ① shows that the primitives Mesa optimized for are cheap, the natural follow-up question is what it didn't optimize for. FORK+JOIN, at 1,100 ticks, is the single most expensive operation the paper measures — this card exists to check whether that's a design flaw the paper glossed over, or a defended tradeoff, by tracing how FORK/JOIN are built (as ordinary Mesa code sitting on top of the same WAIT/NOTIFY primitives just measured in ①, not microcode) so the paper's "it's rare" defense can be checked against its own frequency claim rather than taken on trust.

FORK+JOIN costs 1,100 ticks against a 30-tick plain call. Is that as bad as it sounds?

  1. Raw ratio: 1,100 / 30 ≈ 36.7× — the paper's text says "about 38 times"; the table's own numbers give about 37. (The word "representative" in the paper refers to the WAIT and NOTIFY figures, not to this ratio.)
  2. Where the cost comes from: FORK and JOIN are implemented as Mesa code (a monitor called Process) running atop the same WAIT/NOTIFY primitives just measured — not as microcoded machine instructions like a normal call.
  3. Compare to a process switch: 1,100 / 60 ≈ 18.3 — creating a process costs about as much as 18 ordinary context switches, consistent with "brain surgery" being performed on a dormant ProcessState.
  4. The paper's own justification: FORK/JOIN are used far less frequently than WAIT/NOTIFY/monitor-entry, so it's a deliberate engineering tradeoff, not an oversight — put the microcode budget where the frequency is.
💡
This is a direct instance of "optimize the common case": the paper explicitly names JOIN as the least-used primitive of all (detached processes that never JOIN are "popular"), which is exactly why it was acceptable to leave FORK/JOIN in software.

③ Tallying the StorageAllocator's byte cost, from the paper's own tables

🎯
Why this is a worked example: ① and ② are both about time. But the paper's stated goal for monitors — applicable "to a finer grain of concurrency" — is a claim about size: if wrapping a small data structure in a monitor costs hundreds of bytes, no one bothers except for the biggest, coarsest locks. The paper gives a complete per-construct byte-cost table and its own StorageAllocator example (Allocate/Free/Expand/moreAvailable), but never adds the two together in the text — this is the one card in the guide whose number you cannot get from the paper's prose alone; it exists to close that gap and put an actual figure on "cheap enough for fine-grained use."

The paper's own example: a monitor with 2 entry procedures (Allocate, Free), 1 external procedure (Expand), and 1 condition variable (moreAvailable), where Allocate contains one WAIT and Free contains one NOTIFY. Using the paper's cost table (module 8B data/2B code; monitor +2B data/+2B code; procedure 8B data/2B code; entry procedure 8B data/10B code; condition variable 4B data; WAIT 12B code; NOTIFY 3B code):

  1. Monitor base: module (8, 2) + monitor delta (2, 2) = 10 bytes data, 4 bytes code.
  2. Two entry procedures (Allocate, Free): 2 × (8, 10) = 16 bytes data, 20 bytes code.
  3. One external procedure (Expand): a plain procedure, (8, 2) = 8 bytes data, 2 bytes code.
  4. One condition variable (moreAvailable): 4 bytes data, plus its one WAIT site (12B code) and one NOTIFY site (3B code) = 15 bytes code.
  5. Grand total: data = 10+16+8+4 = 38 bytes; code = 4+20+2+15 = 41 bytes — the paper's per-construct overhead for two entry points, one external procedure, and one condition variable (not counting the allocator's own shared data or procedure bodies). Note that the 8 data bytes per procedure are the minimum activation record, a frame allocated from the frame heap only while that procedure is running (§5.1, §5.4), so 24 of the 38 data bytes exist only during calls.
🍯
Insight: under 80 bytes covers just the minimum overhead for the synchronization scaffolding itself — the monitor, entry-procedure, and condition-variable bookkeeping from the paper's cost table, not the allocator's actual shared data or procedure bodies — and the paper's stated goal of low local cost "so the facilities can be applied to a finer grain of concurrency" checks out arithmetically for that scaffolding alone.

④ Walking the priority-inversion scenario against the fix

🎯
Why this is a worked example: ①–③ are all about cost — whether Mesa is cheap enough to be worth using. This card is different: it checks correctness under a failure mode (priority inversion) that has nothing to do with WAIT/NOTIFY's tick cost and everything to do with combining monitors with priority scheduling. The paper states its fix — boost the monitor's effective priority to the highest of anyone who's ever entered it — as a one-line rule, which is easy to accept without seeing why it actually breaks the inversion. This example exists to run the paper's own five-step P1/P2/P3 scenario twice, once broken and once fixed, so the abstract rule becomes a mechanism you can point to at a specific step.

Using the paper's own five numbered steps (§4.3): P1 enters M; P2 preempts P1; P3 preempts P2; P3 tries to enter M and waits; P2 runs again, blocking P3 indefinitely. Where exactly does the fix intervene?

  1. Without the fix: P1 holds M's lock at low priority the entire time, but only ever gets scheduled when nothing higher-priority is ready — which, thanks to P2, is never. P3 (highest) is starved by P2 (medium), an inversion of the intended order.
  2. The fix: the moment P1 enters M, M's effective priority becomes the highest priority of any process that has ever entered it — here, P3's priority (set once P3 has entered M at least once before).
  3. Re-run step 2: P1, now running at P3's boosted priority while inside M, cannot be preempted by P2 (P2's priority is lower than P3's). P1 finishes and releases the lock quickly.
  4. Result at step 4: P3 enters M with no wait at all — the inversion never occurs, because P1 was never available for P2 to indefinitely displace.
💡
Notice the fix boosts every entrant to the monitor's ceiling, not just today's lock-holder — cheaper to implement (a single per-monitor number) than tracking the live dependency chain, at the cost of possibly over-boosting rarely-contended paths.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why must every WAIT in Mesa be written inside WHILE NOT ok DO WAIT c ENDLOOP rather than IF NOT ok THEN WAIT c?
Show answer
Because NOTIFY is only a hint under signal-and-continue: after a woken process reacquires the lock, some other process may already have entered the monitor and changed the state again before the original waiter runs. Only the monitor's invariant may be assumed after WAIT, not the exact predicate that triggered the NOTIFY — so the predicate must be re-tested, potentially waiting again.Misconception: that NOTIFY means "the thing you were waiting for is now true." It only means "something changed — go check."
Problem 2 · medium
Using the paper's tick table (call+return = 30, monitor call+return = 50), what percentage overhead does entering a monitor add over a plain procedure call?
Show answer
(50 − 30) / 30 = 20/30 ≈ 66.7%, which the paper rounds to "about 70 percent more." This is the fixed cost of the MONITORENTRY/exit protocol, independent of how many arguments are passed (each of which adds 24 more ticks separately).Misconception: computing 50/30 = 1.67× and calling that "67% of the cost." The overhead is the difference over the baseline, not the ratio itself.
Problem 3 · medium
FORK+JOIN costs 1,100 ticks. Compute its cost in units of "process switches" (60 ticks each), and explain why that comparison is more informative than comparing to a plain call.
Show answer
1,100 / 60 ≈ 18.3 process switches worth of work. This framing is more informative because FORK/JOIN's cost is dominated by the same queue-manipulation and state-saving machinery a process switch uses (creating/destroying a ProcessState, moving it between queues) — not by anything resembling a procedure call.Misconception: assuming FORK/JOIN is slow because of some inherent complexity in starting concurrent execution. It's slow specifically because it's implemented in software atop the same primitives, by deliberate design choice.
Problem 4 · hard
In the paper's priority-inversion example, why does boosting the monitor's priority to "the highest priority of any process that has ever entered it" — rather than only the priority of whoever is currently waiting to enter — fix the problem, and what does it cost?
Show answer
An alternative that reacts to the actual waiter (later called priority inheritance) would boost P1 at the moment P3 blocks on M; that also works, but needs the lock to know its holder and the scheduler to change a running process's priority when someone blocks. The paper's rule needs no such bookkeeping at block time: P1 is boosted to P3's level the instant it enters M, before P3 even tries to enter, so it's never vulnerable to P2's preemption in the first place. The cost is over-boosting: P1 runs at P3's priority even on entries where no high-priority process ever needs M that round, potentially delaying other work P1 could have yielded to.Misconception: that only a static ceiling can work. Reacting when the high-priority process blocks also fixes this scenario; the paper's ceiling is the simpler rule it proposes, learned from history, and it cannot help the very first time a high-priority process uses the monitor.
Problem 5 · medium
Why does a device's naked NOTIFY need a special "wakeup-waiting switch," when a NOTIFY from an ordinary Mesa process needs no such thing?
Show answer
An ordinary process's NOTIFY happens while it holds the monitor lock, so the monitor lock itself prevents a race: no other process can be mid-check-and-WAIT while the notifier is changing the predicate. A device cannot acquire the lock at all, so its update-and-notify can interleave freely with a process's check-and-prepare-to-WAIT — the notify can arrive in the gap and be lost. The wakeup-waiting switch (a binary semaphore) remembers an unconsumed notification so it isn't lost even without lock protection.Misconception: that NOTIFY itself is inherently unreliable. It's perfectly race-free between two lock-holding processes; the race exists only because the device can't participate in the locking protocol at all.
Problem 6 · medium
If entry procedure P1 (in monitor M) calls an external (non-monitor) procedure that happens to call into monitor N and WAIT there, does M's lock get released during that WAIT?
Show answer
No. M's lock is released only by a WAIT executed directly inside M's own monitor code. A WAIT that happens inside a different monitor (N), reached via an external call, releases N's lock but leaves M's lock held the entire time — potentially for a long, unpredictable duration.Misconception: that "waiting" always releases "the current lock," singular. Mesa tracks lock scope per monitor module; a WAIT only ever releases the lock of the monitor it's textually inside.
Problem 7 · hard
An ENTRY procedure of monitor M detects a bad argument. Compare two ways of reporting it: raising the exception directly inside the procedure, versus restoring the invariant and executing RETURN WITH ERROR. Which lock is held while the caller's handler runs in each case, and what must the handler avoid?
Show answer
Raised directly, the exception is handled by a call from within the monitor (Mesa handlers run as calls, below the raising frame), so M's lock is still held while the handler runs; if the handler calls any ENTRY procedure of M, the process deadlocks with itself. With RETURN WITH ERROR, the entry procedure first returns, which releases M's lock, and the exception is then generated in the caller, so the handler may call M freely. The price is that the procedure must re-establish M's invariant before the return, exactly as for a normal return (paper §3.1).Misconception: that raising an exception "leaves" the monitor. In Mesa it does not, until the frame is actually unwound or returns.
Problem 8 · easy
Why does Mesa give each object its own monitored record rather than using one shared monitor for a whole collection of similar objects (e.g., all open files)?
Show answer
A single shared monitor over the whole collection serializes access to every object through one lock — even operations on two completely unrelated files would block each other. A monitored record gives each object its own lock while all instances share the same compiled monitor code, restoring per-object concurrency without paying for a full separate module instance (with its linking/swapping overhead) per object.Misconception: that more monitors always means more overhead. Monitored records specifically target the case where per-object locks cost far less than the concurrency lost by sharing one lock.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What's the single biggest difference between Mesa and Hoare's original monitors?▾
Signal semantics. Hoare requires signal-and-wait: a signal immediately hands the monitor lock and the processor to the waiter, guaranteed. Mesa uses signal-and-continue: NOTIFY is a hint, the notifier keeps running, and the waiter must re-check its condition in a loop whenever it eventually resumes.
Q2Doesn't signal-and-continue risk starving waiters forever?▾
In principle yes — nothing guarantees a waiter runs soon after a NOTIFY. The authors argue this isn't a real concern in a well-designed system: monitor locks should never be used to implement high-level scheduling policy (like "who gets the printer next"); that belongs in a dedicated scheduler built with monitors as a primitive, not the monitor lock itself.
Q3Does a monitor lock get released when its code calls a procedure outside the monitor?▾
No. The lock is released only by an explicit WAIT executed directly inside that monitor's own code. A call to any procedure outside the monitor module — even one that itself waits inside a different monitor — leaves the original lock held for the call's full duration.
Q4What exactly is a "naked NOTIFY"?▾
A NOTIFY issued by a hardware device rather than a Mesa process. Since a device can't acquire the monitor lock, its notify happens outside the lock's protection, creating a possible lost-wakeup race that's patched with a small wakeup-waiting switch (effectively a binary semaphore) on the condition variable.
Q5How is priority inversion possible if the scheduler always runs the highest-priority ready process?▾
Because "ready" and "holding a needed lock" are different things. A low-priority process can hold a lock a high-priority process needs while itself sitting in the ready queue, perpetually out-prioritized by an unrelated medium-priority process — so the lock never gets released, and the high-priority process waits indefinitely even though it's "just" waiting on a medium-priority process, not directly on the low one.
Q6How does Mesa fix priority inversion?▾
The paper proposes this (§4.3) without saying whether Pilot implements it: each monitor is given the priority of the highest-priority process that has ever entered it. Any process, on entering, is temporarily boosted to that ceiling for the duration it holds the lock — so it can't be preempted by anything the monitor's real "customers" outrank.
Q7What happens if an entry procedure raises an exception without an UNWIND handler?▾
The monitor lock is not automatically released — it stays set, and the resulting deadlock is (per the paper) "not hard to find," implying it shows up quickly and visibly in testing rather than lurking silently.
Q8Why is FORK+JOIN so much more expensive than a process switch or a monitor call?▾
FORK and JOIN are implemented in Mesa itself, as a monitor called Process, sitting on top of the same WAIT/NOTIFY primitives — not microcoded into the processor like ordinary calls and switches are. The authors accepted this because FORK/JOIN are used far less frequently than the primitives they're built from.
Q9Does Mesa provide any protection between processes, like separate address spaces?▾
No. The system is designed for a single user, and the authors consider Mesa's strong static typing sufficient protection — there's no hardware isolation between processes, which is also part of why process operations are so cheap.
Q10Was this design used in a real, large system, or just proposed?▾
Both designed for and battle-tested in Pilot (a ~24,000-line Mesa OS with ~75 modules and ~40 monitors), plus large applications: Violet (a replicated distributed calendar/database) and an internetwork packet gateway — all discussed with real process/monitor counts in the paper's applications section.
Q11Why not just use semaphores instead of monitors?▾
Semaphores can solve the same problems (mutual exclusion, producer/consumer) with one primitive, but the authors found monitors impose more useful structuring discipline on large programs — bundling data, synchronization, and access code together — and found equivalent economy of mechanism in their monitor+condition-variable implementation anyway.
Connecting the dots

Why a 1980 language paper matters for memory-systems research

Four short connections from Mesa's monitor design to the OS mechanisms underneath modern tiering and memory-management work.

🐧 Signal-and-continue is Linux's wait_event()/wake_up(), forty years early

Every Linux wait_event(wq, condition) call expands to exactly the WHILE-loop-recheck pattern Mesa mandates: sleep, get woken as a hint, re-test condition, loop if false. Futex FUTEX_WAKE/FUTEX_WAIT and spurious-wakeup handling are the same contract. That's the same hint-not-guarantee semantics kernel wakeups are documented with today — a case of independent convergence on the same solution, not a traceable lineage back to this paper.

🚦 Mesa's priority-ceiling fix predates the formal priority ceiling protocol

Boosting a monitor to the highest priority of anyone who has ever entered it is a hand-built version of what Sha, Rajkumar, and Lehoczky later formalized as the priority ceiling protocol for real-time systems. The same failure mode — a low-priority lock-holder starved by an unrelated medium-priority process, blocking a high-priority waiter — is exactly what caused the 1997 Mars Pathfinder priority-inversion bug.

🧵 No hardware protection, only type safety — a trade eBPF's verifier echoes loosely

Mesa's decision to skip inter-process protection and lean entirely on the compiler's type system, in exchange for cheap process operations, echoes eBPF's bet on a static verifier instead of a hardware isolation boundary for the code it runs. The analogy is loose, though: eBPF programs still execute inside the kernel's existing protection boundary, and io_uring's speedup comes from cutting syscall and copy overhead, not from removing protection the way Mesa did.

🧠 Lock scope across page faults is the same hazard as holding a lock across a CXL.mem stall

The paper rejects non-preemptive mutual exclusion specifically because it "forbids multiprogramming across page faults" — a fault mid-critical-section would freeze everyone. Holding a spinlock across a slow CXL memory access or an NVM page-in is the modern version of exactly this hazard: a monitor lock (or spinlock) held across a stall that can take microseconds instead of nanoseconds silently converts a fine-grained lock into a system-wide bottleneck.

🍯
The throughline for tiering research: keep the "is this access safe" question (fast, local, never blocking on I/O) strictly separate from the "which tier should this page live in" question (slow, policy-level, allowed to stall) — exactly the layering Mesa's monitor/scheduler split was built to preserve.

(compare their 15-tick WAIT / 4–9-tick NOTIFY against a modern context switch's cost in cycles)
  3. Their priority-inversion fix boosts every process that enters a monitor to that monitor's historical priority ceiling, not just today's actual lock-holder — is this closer to the priority ceiling protocol or to priority inheritance, and what does it cost on a monitor that's rarely touched by high-priority processes? (Sha, Rajkumar, and Lehoczky formalized this distinction a decade later)
  4. FORK+JOIN costs about 37× a plain procedure call specifically because it's implemented in software atop the monitor primitives rather than microcoded — does that same justification ("used much less frequently") survive in a world of request-per-thread and io_uring-style servers that create and tear down execution contexts constantly? (the paper itself calls FORK/JOIN performance its one admitted weak spot)
  5. The naked-NOTIFY race requires bolting an ad hoc wakeup-waiting switch onto condition variables purely because devices can't take the monitor lock — is this a one-off patch, or does it foreshadow the same lost-wakeup races that modern lock-free kernel code still handles with memory barriers and atomic flags? (the race is "check predicate, prepare to WAIT" racing a device's out-of-band update)

Glossary & further reading

Every term in one place, then the paper's own cost tables and reading trail.

Core terms
MonitorA module bundling shared data with the only procedures allowed to touch it, guaranteeing at most one process executes inside at a time.
Entry procedureA monitor procedure callable from outside the module; calling it acquires the monitor lock, returning releases it.
Condition variableAn object with no program data of its own that processes WAIT on inside a monitor; NOTIFY resumes a waiter. Implemented as a 4-byte record: a queue cell, a timeout interval and a wakeup-waiting switch.
Signal-and-continueMesa's rule: NOTIFY is a hint; the notifier keeps running and the waiter must re-check its condition upon resuming.
Signal-and-waitHoare's original, stricter rule: a signal immediately and guaranteed hands the monitor lock and the processor to a waiting process.
Monitor invariantThe property a monitor's data must satisfy whenever no process is executing inside it; assumable at entry and right after WAIT.
FORK / JOINMesa's process-creation primitives — FORK starts a procedure running concurrently, JOIN retrieves its eventual result. Because the forked procedure becomes its own process's root, it also loses the caller-chain safety net an ordinary call would have for unhandled exceptions.
BlockAny BEGIN...END-delimited scope that can carry its own exception handler; a procedure body is one block among possibly several nested inside it.
Root procedureThe one frame at the base of a process's own stack, with no caller of its own — it must handle every exception itself, or the process falls straight into the debugger.
UNWINDMesa's mechanism for cleanly abandoning a chain of procedure activations when an exception is handled further up the stack.
Supporting terms
Monitored recordAn ordinary data record augmented with a lock, letting each object in a collection have its own monitor without a separate module instance.
Naked NOTIFYA NOTIFY issued by hardware, which can't hold the monitor lock — requires a wakeup-waiting switch to avoid a lost-wakeup race.
Priority inversionA high-priority process blocked indefinitely because a medium-priority process prevents a low-priority lock-holder from running.
BROADCASTResumes every process waiting on a condition, not just one — always correct given NOTIFY's hint semantics, useful when waiters need different amounts of a resource.
DetachMarks a forked process so it destroys itself on completion without anyone JOINing it.
ProcessStateThe small (10-byte) fixed record representing a process's existence, separate from its stack of procedure activation frames.
PilotThe Mesa-based personal-computer operating system this concurrency design was built for and validated against.
Violet / GatewayThe two large multi-process Mesa applications discussed as case studies: a replicated distributed calendar system, and an internetwork packet-forwarding gateway.
Wakeup-waiting switchA binary-semaphore-like latch added to a condition variable to make naked NOTIFYs from devices race-free.
TickThe paper's unit of execution time — one-fourth of the time for a simple statement like a ← b + c.
