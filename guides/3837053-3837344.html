HotStorage 2026 · A Field Guide

Give every queue pair its own door in and its own door out

One GPU thread that submits an NVMe command and then blocks polling for it wastes most of its own clock cycles. PLINK splits that one job into two parallel jobs — and needs 43% fewer total warps to saturate the SSD.

📄 Jung, Kang, Choi · HotStorage '26 🎓 Assumes you know NVMe queues and GPU warps — primers cover both ⏱ ~25 min read
🚪

SPLIT submission from completion, batch the doorbell once per warp, stop scanning the whole queue — instead of letting one thread serialize submit-then-poll.

Before you begin

Quick glossary, then the primers

The paper's acronyms, defined once, then eight short primers you can open in any order.

NVMeNon-Volatile Memory Express — the command protocol modern SSDs speak.
SQ / CQSubmission Queue / Completion Queue — where commands go in and results come out.
SQE / CQESubmission/Completion Queue Entry — one command, one result.
QPQueue Pair — one SQ plus its matching CQ. An SSD can expose up to 65,535.
QDQueue Depth — how many commands a queue can hold outstanding at once.
BaMBig Accelerator Memory — the GPU-initiated I/O system PLINK is built against.
SIMTSingle-Instruction Multiple-Thread — the GPU's execution model.
CIDCommand ID — the tag an NVMe command carries so its result can be matched back.
PRPPhysical Region Page — how NVMe commands point at the data buffer.
MMIO / DoorbellA write to device-mapped memory that tells the SSD "new commands are ready."
IOPSI/O operations per second — the SSD's throughput ceiling.
1NVMe's multi-queue structure▾

An NVMe drive isn't one queue — it exposes up to 65,535 independent QPs, each an SQ/CQ pair, so the device can serve many streams without lock contention. A queue can hold up to 65,536 commands in flight (its QD) before the host must wait.

Now you're ready: "NVMe parallelism" = using many queues, and keeping many commands outstanding in each one.
2Outstanding commands and asynchrony▾

Submission and completion are decoupled by design: the host writes an SQE, and later the drive writes back a CQE — the host need not wait in between. A command that's been submitted but not yet completed is outstanding. More outstanding commands means more work the SSD can overlap internally.

Now you're ready: PLINK's whole project is getting more commands outstanding per thread, instead of pinning it at one.
3GPU warps and SIMT▾

A GPU runs threads in groups of 32 called warps; all 32 threads in a warp execute the same instruction each cycle (SIMT). This is what gives GPUs their throughput — but when threads diverge, the hardware masks off whichever subset isn't on the current path, so threads sharing a path can still advance together while the rest wait. The "slowest lane" framing only holds exactly at points where the whole warp must agree before continuing, like a single warp-wide doorbell write.

Now you're ready: when PLINK "dedicates a warp" to submission or completion, that's 32 threads acting as one coordinated unit — tightly lock-stepped at synchronization points like the doorbell.
4Warp divergence▾

If threads in a warp take different paths (or finish an operation at different times), only the matching subset can progress each cycle — the rest sit masked out, burning cycles doing nothing useful.

Now you're ready: non-uniform NVMe completion latency across threads is exactly what causes warp divergence in GPU-initiated I/O — this is the paper's second-biggest villain.
5BaM's model — one thread does it all▾

BaM lets the GPU run both the control and data path for NVMe directly, no CPU involved. On a cache miss, the same thread submits the read, blocks polling its own completion, then continues — submit and wait, serialized, per thread.

Now you're ready: PLINK's first fix is literally un-merging this one job into two.
6Doorbells and PCIe MMIO writes▾

Writing an SQE into the queue doesn't tell the drive anything by itself — the host must also "ring the doorbell," an MMIO write over PCIe, to say "go look." Each doorbell write has real latency, and BaM can end up ringing it several times per warp — once per ready subset (a consecutive prefix) of threads, rather than once for the whole warp — which multiplies the cost.

Now you're ready: this is the resource PLINK's third optimization is trying to spend less of.
7Why GPUs are touching storage at all▾

Long-context LLM inference generates KV-cache entries that no longer fit in GPU memory and get swapped to NVMe; GNN workloads have a similar fine-grained access pattern. Both push storage accesses directly onto the GPU's critical path.

Now you're ready: this is the motivation, not the mechanism — PLINK's fixes apply to any fine-grained GPU-initiated I/O, KV-cache included.
8Reading a cycle-breakdown table▾

The paper instruments BaM's I/O path at cycle granularity, timestamping each phase boundary per thread, and reports the average cycles (and %) spent in each. That's how it localizes exactly where time goes, instead of treating "I/O latency" as one opaque number.

Now you're ready: the whole paper follows from one such table (Table 1) — it's worked through in Worked Examples.
The whole story in one place

PLINK in a nutshell

Why BaM wastes cycles, and the three independent fixes that recover them.

BaM's GPU-initiated I/O is serialized: a thread submits one NVMe command, then blocks polling for its own completion before issuing the next. A cycle-granularity breakdown of this path shows that over 93% of turnaround time concentrates in exactly three phases — completion polling (tCQ_POLL, 39.5%), the SQ doorbell (tSQ_DB, 21.8%), and the CQ doorbell (tCQ_DB, 31.8%) — each traced to a distinct structural cause.

PLINK attacks the three causes directly. SQ/CQ decoupling assigns separate warps to submission and completion so both halves of a queue pair advance in parallel instead of one blocking the other. Command-ID-indiscriminate polling has a thread claim a CQ slot and wait only on that slot, instead of exhaustively scanning the whole queue for a matching CID. Warp-level doorbell batching waits for all participating lanes to be ready and rings the doorbell once per warp, instead of once per ready subset.

The payoff: applied together, PLINK's I/O backend saturates a PCIe Gen 6 SSD's IOPS at 136 total warps (submission + completion), versus BaM's 238 — a 43% reduction, with each optimization's contribution isolated by adding them one at a time.

🧭 Key takeaways

  • BaM's serialized submit-then-poll keeps the SQ idle for ~71% of total I/O time.
  • tCQ_POLL alone costs 415µs against a measured 200µs device latency — more than 2× device cost is platform overhead (exhaustive CQ scan).
  • Decoupling alone (E1) raises total warp count (246 > 238) — it trades resources for per-queue rate; the other two fixes are what bring the total down.
  • Warp-level doorbell batching (E3) alone already cuts total warps 33% below BaM.
  • Combined, PLINK cuts tCQ_POLL 79%, tSQ_DB 86%, tCQ_DB 90%, and saturates at 136 vs 238 warps.
  • Saturating warps are a small fraction of a GPU's resident capacity — the real win is freeing warps for application compute.
Five everyday pictures

How to think about PLINK

Each stands alone. Every card ends with where the picture breaks.

The core fix · decoupling

One revolving door vs. two separate doors

A shop with a single revolving door forces every customer to finish leaving before the next one can enter. BaM's thread is that door: submit, then wait, in sequence. PLINK installs an entrance and an exit — a submission warp and a completion warp — so people flow both ways at once.

Where it breaks: two doors need two staff. Decoupling alone (E1) actually spends more total warps — the saving only shows up once the other two fixes make each door faster too.
The second fix · polling policy

A claimed locker number vs. checking every locker

Looking for your gym bag? If you remember your locker number, you open one door. BaM instead checks every locker in the row for a matching tag, every time. PLINK's command-ID-indiscriminate polling claims a slot up front and waits only on that slot — whichever item lands there is the one you take.

Where it breaks: you give up choosing which item you get — whichever command lands in your claimed slot is simply treated as yours, with no CID comparison performed. That's a different layer from the done[] notification bookkeeping (§3.4) used to signal individual requesters, not the same check relocated.
The third fix · doorbell batching

One honk for the whole carpool vs. every car honking

A carpool doesn't honk the horn car by car as each rider buckles up — it waits until everyone's in, then honks once. BaM rings a separate doorbell for each ready prefix of threads (threads 0,1 ready, honk; thread 2 shows up, 2,3 ready, honk again). PLINK waits for the whole warp, then rings once.

Where it breaks: waiting for the whole warp means the fastest lanes idle for the slower ones — the paper doesn't quantify or guarantee that wait as short, only that the resulting drop in MMIO writes and divergence wins out in their throughput results.
Why divergence hurts · SIMT

Synchronized swimmers waiting on the straggler

A synchronized-swim team can't move to the next figure until every swimmer finishes the current one — the fast ones float, burning time, not distance. A warp works the same way: if NVMe completion latency is non-uniform across threads, the whole warp is pinned to its slowest lane at every step that needs agreement, like a doorbell ring.

Where it breaks: swimmers can rest; masked-out GPU lanes genuinely waste clock cycles that could have run other work — there's no "float," only idle hardware.
The payoff · freed capacity

Fewer cashiers needed, more room on the floor

If checkout takes fewer cashiers to keep the line moving, the store has more floor space for shelves. A GPU has thousands of resident warps; shrinking the warps needed to saturate the SSD from 238 to 136 frees the rest for application computation — the thing the GPU was bought to do.

Where it breaks: freed warps only help if the application actually uses them for useful compute — PLINK's paper measures the I/O backend alone and leaves that conversion (per Hyperion-style scheduling) as future work.
The full explanation

How PLINK actually works

The breakdown that motivates it, then each of the three fixes with the paper's own diagram rebuilt.

The highlighted three rows sum to 93.1% of total time, and each traces to a distinct cause: SQ/CQ serialization keeps the SQ idle ~71% of the time; tCQ_POLL's 415µs is more than double the drive's measured 200µs average latency, because BaM exhaustively scans the whole CQ for a matching CID on every poll; tSQ_DB and tCQ_DB are inflated because threads arrive ready at non-uniform times, forcing multiple partial doorbell writes per warp instead of one.

2 · SQ/CQ decoupling (3.1)

Each warp is assigned exclusively to one SQ or one CQ at init and stays there. Cost for N commands drops from N×(tSQ+tCQ) to tSQ + N×tCQ — only the first submission pays tSQ, since the SQ warp keeps submitting without waiting on completions.

3 · Polling policy (3.2)

Entire-scan polling has worst-case latency O(Lmax + Ttr): Lmax is the last-arriving CQE's device latency, Ttr the time to traverse the whole queue depth looking for a CID match. PLINK's command-ID-indiscriminate polling has a thread atomically claim a CQ slot and wait only on that slot — it processes whichever command lands there, without consulting CID — cutting worst case to O(Lmax). Threads finish polling at more uniform times, so divergence after this phase drops too.

4 · Warp-level doorbell update (3.3)

BaM rings the doorbell as soon as any ready prefix exists, which can mean several partial writes per warp:

5 · Execution model (3.4)

Dedicating warps to SQ/CQ changes the programming model: a thread issues a batch of independent requests, then waits on a done[] flag per request, set by the completion warp rather than by itself. The handshake needs a device-scope memory fence (so the returned data is visible before done[] is observed set) and per-queue flags sized 2 × QD × Nq × 4 bytes — worked out in Example ③. The trade: PLINK accepts this spin-wait cost in exchange for removing the exhaustive CQ scan and the repeated doorbell writes.

Follow the numbers

Worked examples

Four calculations straight from the paper's own measurements.

① Verifying the "over 93%" claim

  1. Sum all six phases: 30.4 + 3.8 + 599.7 + 1086.3 + 154.1 + 874.7 = 2749.0k cycles.
  2. Sum the three target phases: tSQ_DB + tCQ_POLL + tCQ_DB = 599.7 + 1086.3 + 874.7 = 2560.7k cycles.
  3. 2560.7 / 2749.0 = 93.1% — matches the paper's "over 93%" exactly.
  4. SQ-idle fraction = tCQ_POLL% + tCQ_DB% = 39.5 + 31.8 = 71.3% ("roughly 71%").

③ Memory cost of the done[] handshake

  1. Per-queue flag bytes: 2 × QD × Nq × 4 bytes — the leading 2 doubles QD to hold a phase bit.
  2. Plug in the eval config: QD = 1024, Nq = 256.
  3. 2 × 1024 × 256 × 4 = 2,097,152 bytes ≈ 2 MB — matches the paper's "≈2 MB" exactly.
💡
2 MB is the price of routing completions through a dedicated CQ warp as a direct done[] index instead of per-requester completion tracking — small next to GPU memory, but worth naming since it scales with QD×Nq.

④ How much of tCQ_POLL is pure overhead

  1. Measured tCQ_POLL = 415µs; measured average device latency = 200µs (fio, same machine).
  2. 415 / 200 = 2.08× — "more than twice" the device's own service time.
  3. The ≈215µs excess is platform overhead: BaM's exhaustive CQ scan for a matching CID, not NVMe latency.
  4. That's precisely the overhead command-ID-indiscriminate polling (E2) targets, cutting tCQ_POLL 22% directly and tCQ_DB 43% as a side effect of tighter arrival alignment.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
E1 (decoupling alone) saturates the SSD at 123 submission warps vs BaM's 238 — fewer warps for the same work. Why is E1's total warp count (246) still higher than BaM's?
Show answer
Decoupling needs a dedicated CQ warp for every SQ warp, so 123 submission warps cost 123+123=246 total — 3.4% above BaM. Fewer submission warps ≠ fewer total warps once you pay for the completion side.Misconception: that any individual optimization must reduce total resource use. E1 improves per-queue request rate but spends more total warps; only combining it with E2 and E3 (which shrink per-phase cost enough to need fewer queues at all) brings the total below BaM.
Problem 2 · medium
E2 (polling policy alone) keeps BaM's serialized model. If E2 saturates at 224 total warps, why is this number both the submission-warp count and the total?
Show answer
E2 doesn't decouple — one warp still handles both submission and completion, exactly like BaM, just with cheaper polling. So there's no separate CQ-warp allocation to add; submission warps = total warps, 224 either way.Misconception: assuming every PLINK variant splits SQ/CQ. Only E1 and PLINK (which includes E1) pay the CQ-warp cost — E2 and E3 don't touch warp assignment at all.
Problem 3 · hard
Compute the done[] flag memory if the evaluation used QD=2048 and Nq=64 instead of QD=1024, Nq=256.
Show answer
2 × 2048 × 64 × 4 = 1,048,576 bytes = 1 MB — half the paper's ≈2MB figure, since the product QD×Nq fell from 262,144 to 131,072.Misconception: that this cost scales with warp count. It scales with queue depth times number of queues — a system could have few warps but deep queues, or vice versa, and the flag memory follows QD×Nq, not the warp total.
Problem 4 · medium
Command-ID-indiscriminate polling means a thread doesn't check which command actually completed into its claimed CQ slot. How does the system still deliver the right data to the right requester?
Show answer
Per §3.2, it genuinely doesn't check — whichever command lands in the slot a thread claimed is treated as that thread's result, with no CID comparison performed at all. That's a different layer from §3.4's done[] notification bookkeeping, which the batch-request interface uses to signal individual requesters once a completion is in hand — PLINK isn't relocating the same CID search elsewhere, since no search happens at either stage.Misconception: that skipping the CID check means results get scrambled, or that correctness requires an equivalent check to be hiding somewhere else. The cost removed is specifically the exhaustive scan (O(L_max+T_tr) → O(L_max)); correctness comes from the slot-claiming scheme itself, not from a relocated CID search.
Problem 5 · hard
PLINK's combined tCQ_DB reduction is 90%, far above E3 alone's 33%. Explain the compounding mechanism, referencing which phase enables it.
Show answer
tCQ_DB's divergence is inherited from tCQ_POLL: if threads finish polling at wildly different times (non-deterministic device latency), warp-level doorbell batching (E3) still has to wait for the slowest straggler to reach the doorbell step. E2's command-ID-indiscriminate polling narrows that spread first — threads arrive at tCQ_DB already closely aligned — so E3's batching in PLINK has little residual divergence left to wait out.Misconception: treating each optimization's benefit as independent and additive. Here E2 doesn't just save its own 22%/43% — it changes the input distribution that E3 operates on, producing a reduction larger than either alone would predict.
Problem 6 · easy
PLINK saturates the SSD at 136 warps, a small fraction of a modern GPU's thousands of resident warps. Does this by itself mean an LLM-serving application will run faster?
Show answer
Not automatically. The paper evaluates the I/O backend in isolation — warps doing nothing but I/O. The benefit is only realized if the freed warp capacity is actually redirected to useful application computation, which the paper names as future work (citing Hyperion's approach for GNN training as the kind of conversion needed).Misconception: that a smaller saturating warp count is itself the end metric. It's a necessary precondition for freeing GPU capacity, not a guarantee that an application harnesses it.
Quick answers

Frequently asked questions

Eight questions newcomers ask most.

Q1Is PLINK a new SSD or a new driver?▾
Neither — it's a GPU-side software I/O platform (custom GPU kernels) that talks to a standard NVMe SSD. Like BaM, it bypasses the CPU for both control and data paths, but restructures how GPU warps submit and poll.
Q2Why does decoupling alone (E1) make things worse by one measure?▾
It raises total warp count (246 vs 238) because every SQ warp now needs a paired CQ warp. It's still a real improvement in per-queue request rate (123 vs 238 submission warps for the same throughput) — just not a total-resource win until combined with E2 and E3.
Q3What exactly does "command-ID-indiscriminate" mean?▾
A polling thread claims a CQ slot atomically and waits only until that specific slot fills — per §3.2, the CID is not consulted at all; whichever command lands in the claimed slot is simply treated as this thread's result, with no comparison performed. That's distinct from §3.4's done[] notification bookkeeping, used by the batch-request interface to signal individual requesters — a separate layer, not a relocation of the CID check that indiscriminate polling removes.
Q4Does batching the doorbell add latency by making fast lanes wait?▾
It can — PLINK waits for the whole warp's active lanes before ringing once, instead of ringing immediately for whichever subset is ready. The paper doesn't measure or claim that this wait is always short; what it shows is that the resulting drop in MMIO writes and divergence wins out in their throughput measurements.
Q5Why measure the I/O backend separately from the execution model?▾
So each of the three optimizations' saturation-point and per-phase effects can be attributed cleanly, without the completion-notification cost of the application-facing batch interface (Section 3.4) muddying the comparison. That cost is described but explicitly left unmeasured — future work.
Q6How does this connect to LLM KV-cache offload?▾
Long-context inference pushes KV-cache entries to NVMe when GPU memory runs out, generating fine-grained, frequent GPU-initiated storage accesses — the access pattern PLINK is built for. The paper cites this (and GNN sampling) as the motivating workload class, though its own evaluation is a synthetic 4KB random-read microbenchmark.
Q7Is 4KB random-read representative of real workloads?▾
It's chosen deliberately as the fine-grained extreme — larger transfers need multi-page DMA chains that consume SSD resources differently and reduce IOPS, so single-page requests isolate the backend's per-command overhead cleanly. It's a stress test for the mechanism, not a claim about any specific application's access size.
Q8What's left for future work?▾
Validating the warp-savings-to-application-speedup conversion under real workloads (including the execution model's completion-notification cost), profiling SQ and CQ warps separately to tune the SQ:CQ ratio per device/workload, and extending PLINK to multi-device configurations sharing a PCIe switch.
