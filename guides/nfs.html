Remember nothing on the server, retry until it answers

Sun's NFS made remote files look local to unmodified UNIX programs by keeping the server stateless. This guide opens every mechanism that follows from that one choice, and every place where it costs speed or UNIX semantics.

Before you begin

Remote files that look local, from a server that remembers nothing

A 1985 systems paper from Sun Microsystems: the design of NFS, the kernel interface built to host it, and an honest list of what did not quite work.

⚡ TL;DR

  • Goal: let unmodified UNIX programs use files on other machines (many of them diskless Sun-2 workstations) through ordinary pathnames, with easy recovery from server crashes and speed comparable to Sun's block-level Network Disk (ND), "about 80% as fast as a local disk".
  • Core choice: a stateless server. Every request (a Sun RPC over UDP, encoded in XDR) carries everything needed: an opaque file handle, an explicit offset and count, and the caller's uid and gids. The client resends until it gets a reply, so a server crash looks like a slow server and the server does no recovery at all.
  • Consequences: the server must commit every modification to disk before replying; handles are built from (filesystem id, inode number, generation number); lookups go one pathname component at a time; there is no locking, no open or close in the protocol, and only weak cache consistency (flush on close, attributes trusted for 3 s for files and 30 s for directories).
  • Kernel side: the new VFS/vnode interface separates generic file operations from filesystem implementations (worst-case cost about 2%), so NFS is just another filesystem type next to 4.2 and an MS-DOS floppy filesystem.
  • Result: after a client buffer cache, 8 KB UDP requests, fewer copies, an attribute cache, a program-loading trick and a directory name cache, the benchmark total fell from about 570 to about 290, past the ND goal of about 300 (Figure 3). Writes stay slow (raw 40 KB/s vs 120 KB/s for reads) and make stays slow (one RPC per stat).

1Inodes, directories and links in a UNIX filesystem▾

A UNIX file is an inode: a numbered on-disk record with the owner, mode bits, size, times and pointers to data blocks. A directory is a file of (name, inode number) entries. A name is a link; a file can have several, and it is freed only when it has no links and no process has it open.

In 4.2BSD's fast file system (general knowledge, not in the paper) blocks are 8 KB, an inode holds 12 direct block pointers, and larger files go through indirect blocks full of more pointers. Writing past the direct blocks therefore also modifies an indirect block.

Now you're ready: a file handle names the inode, not the path; "synchronous write" means data block + indirect block + inode; open-file removal is about a file with zero names but a live open.
2The buffer cache and delayed writes▾

The kernel keeps recently used disk blocks in memory. A local write(2) normally copies data into a cached block, marks it dirty and returns; the disk write happens later (when the buffer is reused, or when sync runs). A crash loses those dirty blocks, which local UNIX users accept.

Now you're ready: NFS forbids exactly this on the server (a reply must mean "on disk"), but allows it on the client (write-behind, flush on close).
3Why server state makes crash recovery hard▾

If a server remembers things about clients (which files they opened, which locks they hold, what they cache), then after a server crash that memory is gone and clients must notice and rebuild it, and after a client crash the server must notice and discard it. Both need reliable crash detection, which a network cannot give (a slow machine and a dead one look the same).

Now you're ready: NFS's answer is to have nothing to rebuild. The Leases paper's answer is state that expires by itself.
4Remote procedure call and retries▾

An RPC looks like a local call: marshal the arguments, send a request, wait, unmarshal the reply. Over UDP the request or the reply can be lost. The caller's only tool is a timeout and a resend. A resend after a lost reply makes the server execute the request a second time, so the request must be safe to repeat.

Now you're ready: read, write-at-offset, lookup and getattr repeat harmlessly; remove, rename, mkdir and friends do not quite (M4).
5Mounting and pathname lookup (namei)▾

UNIX builds one directory tree out of many filesystems by mounting a filesystem's root on a directory of another. The kernel routine namei turns a pathname into a file by looking up one component at a time and, when it reaches a mount point, jumping to the mounted filesystem's root.

Now you're ready: NFS keeps mount points on the client and makes the server look up one name per call, so the server never needs to know where a client mounted anything (M12).
6The 1984 setting▾

Sun-2 workstations (Motorola 68010 at 10 MHz), 10 Mbit Ethernet, many machines without a disk. Diskless clients used ND for their private root filesystem (and, as general knowledge, their swap space). A kernel-to-kernel null RPC, after a month of tuning, took 8.8 ms round trip.

Now you're ready: every round trip and every copy is expensive here, which is why the performance section is a list of RPCs and copies removed.
The whole story in one place

Statelessness, and what it costs

One design decision explains most of the paper.

NFS wants many clients to mount filesystems from many servers. With that many machines, crashes are routine, and a protocol whose recovery needs both sides to detect each other's crashes would be fragile. So the authors made the server stateless: "The parameters to each procedure call contain all of the information necessary to complete the call, and the server does not keep track of any past requests."

Then crash recovery is trivial. When a server crashes, "the client resends NFS requests until a response is received, and the server does no crash recovery at all"; when a client crashes, nobody recovers anything. The client cannot even tell "a server that has crashed and recovered" from "a server that is slow". For this to be safe two things must hold: a retried request must have the same effect as the original (idempotence), and anything the server has acknowledged must already be on stable storage, because the client throws its copy away once it gets the reply.

The rest of the design follows. Files are named by file handles the server can decode from on-disk fields alone (with a generation number against inode reuse). Lookups pass one name at a time, so the server never needs the client's mount table. There is no open, close or lock in the protocol. Writes are synchronous on the server, which makes them slow.

The client wins back speed with caches (data blocks with flush on close, attributes for 3 or 30 seconds, directory names) and wins back most of UNIX behavior with client-side patches (rename instead of remove for open files, credentials saved at open, a retry for set-uid root programs). What it cannot win back without server state it leaves out, explicitly: file locking, intermixing-free concurrent writes, exact semantics across two clients, and synchronized clocks.

🍯 Key takeaways

  • Stateless + idempotent + commit-before-reply = a server crash costs time, never data (on a hard mount).
  • The file handle (fsid, inode, generation) is what lets a server with no tables find a file after a reboot.
  • Mounts and pathnames stay on the client: MOUNT is the only place a pathname reaches the server; NFS lookup takes a single name.
  • Consistency is weak and time-based: flush on close, attributes trusted 3 s / 30 s, no locks, writes longer than one RPC can intermix.
  • Performance came from removing RPCs and copies: total benchmark time about 570 → about 290 (ND goal about 300).
  • The paper is candid: the 3/4 solution, root mapped to nobody, time skew, shared root, and security are all listed as imperfect.
Six everyday pictures

How to think about NFS

Each stands alone. Every card ends with where the picture stops being true.

Stateless server · self-contained requests

A help desk with no case numbers

Every email you send must restate the whole problem, because the desk keeps no history. That is annoying, but if the desk loses its inbox overnight, you just resend and nothing is lost: they never had anything to lose. NFS requests carry the file handle, offset, count and credentials every time for the same reason.

Where it breaks: a human notices "you already asked me this"; the NFS server cannot, so a resent "delete my account" (remove) answers "no such account" (M4).
File handle · generation number

A coat check ticket with a date stamp

The ticket names a hook (inode number) on a rack (filesystem id). Hooks get reused. The date stamp (generation number) lets the attendant see that hook 117 now holds someone else's coat, and refuse, instead of handing it over.

Where it breaks: a coat check keeps a list of tickets issued; the NFS server keeps none. The ticket alone must be enough, which is why the stamp has to be stored with the hook (in the inode on disk).
Synchronous server writes

A notary who stamps "received" only after filing

The notary will not give you a receipt until the document is in the vault. You wait longer, but once you have the receipt you can shred your copy. The NFS client discards its data when the reply arrives, so the reply must mean "data, indirect block and inode are on disk".

Where it breaks: a notary files one document; a 24 KB write is three receipts, and another writer's documents can be filed between them (M21).
Attribute cache · fixed timeouts

Reading the departures board, then not looking for three seconds

You glance at the board and trust what you saw for a short while before glancing again. Most of the time nothing changed. If the gate changed right after your glance, you are wrong until your next glance: up to 3 s for a file's attributes, 30 s for a directory's.

Where it breaks: the board never promised anything. A lease is a board that promises not to change during your interval unless it first tells you.
Open-file removal · the 3/4 solution

Taking your name off the mailbox but still using it

You are moving out: you scratch your name off the mailbox (rename to a hidden name) but keep collecting mail until the day you leave (last close), when you hand back the key (remove). If you vanish suddenly, the unnamed mailbox sits there until the landlord's monthly sweep (a cron job).

Where it breaks: another tenant (client) who does not know you still use it can tear the mailbox out, and your next mail check fails.
No locking · intermixed writes

Two people faxing a three-page contract to the same fax

Each fax arrives page by page. If both send at once, the pages interleave and the stack holds page 1 from one sender, page 2 from the other. Locally, UNIX's inode lock makes one write arrive as a single envelope.

Where it breaks: each NFS "page" is a full 8 KB write applied atomically at the server, and the pages land at fixed offsets, so the result is a mix of whole blocks, not a shuffled stack.
The full explanation

How it actually works

Part I is the story in five steps. Part II opens every mechanism, message, rule and trick in the paper.

1 · The protocol: procedures over RPC, made safe by statelessness

NFS is a set of remote procedures (lookup, read, write, create, remove and so on, sixteen in all) defined in XDR and called with Sun RPC over UDP. Calls are synchronous. Because UDP loses packets, the client retries; because the server is stateless and the requests are (mostly) idempotent, retries are harmless and a server crash needs no recovery. Files are named by opaque file handles that the server builds from the filesystem id, inode number and inode generation number.

All 16 procedures (the paper's outline)

Every procedure names its target by file handle (fh) or directory handle (dirfh) plus explicit values, so the server needs nothing remembered from earlier calls. "New handle" marks the three procedures that hand the client a handle it did not have; the first handle of all, the filesystem root, comes from the separate MOUNT protocol.

An XDR example: what lookup(dirfh, "notes") looks like on the wire

XDR (External Data Representation) fixes how each basic type is laid out so any machine can decode it: every item takes a multiple of 4 bytes, integers are 4-byte big-endian, variable-length opaque data and strings are written as a 4-byte length followed by the bytes, padded with zeros to a 4-byte boundary, and fixed-size opaque data (like the 32-byte handle) is written as is with no length word. The protocol is written in XDR's C-like data definition language, and generated stubs marshal to and unmarshal from the byte stream. The paper describes XDR only in general terms; the declarations, sizes and procedure number below are from the later published NFS version 2 specification (RFC 1094, 1989), general knowledge, not in the paper.

/* XDR data definition language (NFS version 2) */
typedef opaque fhandle[32];        /* fixed size: exactly 32 bytes, no length word */
typedef string filename<255>;      /* variable size: length word + bytes + padding */

struct diropargs {                 /* argument of LOOKUP (procedure 4) */
    fhandle  dir;
    filename name;
};

The server's stub reads 32 bytes into an fhandle, reads the length 5, reads 5 bytes,
skips 3 bytes of padding, and calls its lookup routine with (dir, "notes").
The reply is encoded the same way: a 4-byte status, then the new 32-byte fhandle,
then the attributes (type, mode, nlink, uid, gid, size, ... as 4-byte fields).

Two things follow. First, a big-endian 68010 client and a little-endian VAX server agree on every byte, because neither side's native layout is on the wire. Second, all of this is one more copy of every argument and result; the paper's bcopy fix (M16) cut a copy by making XDR encode straight into and decode straight out of the network buffers (mbuf chains).

2 · The server: commit before replying

A stateless server cannot hold acknowledged data in its buffer cache, because a crash would lose it and the client has already moved on. So every modifying request is flushed to disk (data block, modified indirect blocks, inode) before the reply. Kernel server processes (nfsd) give the server a context to sleep in; a separate user-level MOUNT daemon checks /etc/exports and hands out the first file handle.

3 · The client: a new kernel interface

To make remote files transparent, the 4.2 kernel was split into a generic layer and filesystem types through the VFS (per filesystem) and vnode (per file) interfaces. NFS is a filesystem type that turns vnode operations into RPCs. Mount points live in the client's vnodes; pathnames are looked up one component at a time, so the server never needs the client's mount table.

4 · Getting the speed back

The first NFS kernel was far slower than ND. The fixes were client-side caching (data blocks flushed on close, attributes for 3 s or 30 s, directory names), 8 KB requests in one UDP datagram, one fewer copy per side, server read-ahead plus two program-loading tricks. The benchmark total fell from about 570 to about 290, past ND's roughly 300.

5 · Getting UNIX semantics back, mostly

Client-side patches restore most UNIX behavior without touching the server or protocol: rename instead of remove for open files (the "3/4 solution"), credentials saved at open, root mapped to nobody plus a retry for set-uid root programs. What needs server state or a shared clock is left out or pushed to other services: locking, cross-client open-file semantics, time synchronization, a shared root filesystem, strong authentication.

Background and context
  • Publication. USENIX Summer Conference, June 1985, pages 119 to 130. Authors from Sun Microsystems. The acknowledgements credit Bob Lyon (led the group, protocol issues), Steve Kleiman (filesystem interface, from Bill Joy's original design), Russel Sandberg (RPC in the kernel, the NFS virtual filesystem), Tom Lyon (protocol design), David Goldberg (user-level programs), Paul Weiss (Yellow Pages) and Dan Walsh ("the one to thank for the performance").
  • Timeline (paper). Implementation started March 1984 with the filesystem interface; the first "vnode kernel" ran by June. RPC and XDR were ported from user level into the kernel starting in March, with kernel-to-kernel calls working in June and about a month of tuning down to an 8.8 ms null RPC round trip. The first NFS kernel ran in mid-August; the NFS group started using it in September and spent the next six months on performance and administration tools. Figure 4 measures "Release 2.0".
  • Hardware (paper). Clients were Sun-2 model 100U (68010 at 10 MHz, no wait states); the server a Sun-2 120; Sun 10 Megabit Ethernet boards. Local disk comparisons used a Fujitsu Eagle with a Xylogics 450 controller and a Micropolis 42 MB drive on SCSI.
  • What came before. Sun's own ND (Network Disk) gave "block-level access to remote, sub-partitioned disks": each client gets private partitions, but a block protocol cannot let several clients share one writable filesystem (general knowledge, not in the paper: each client's buffer cache would hold its own idea of the on-disk structures). File copying utilities like rcp worked but were not transparent. Other UNIX remote file schemes named files host:path, which forces every program that parses pathnames to change.
The problem

Provide "transparent, remote access to filesystems" for a network of non-homogeneous machines. The paper's five goals: machine and operating system independence (simple enough for a PC), crash recovery (clients mount from many servers), transparent access ("No pathname parsing, no special libraries, no recompiling"), UNIX semantics maintained on the client, and reasonable performance (as fast as ND, "about 80% as fast as a local disk"; the speed that matters is "how long it takes to do normal work", not raw throughput).

The result

A public protocol (NFS plus MOUNT, on RPC and XDR), a kernel filesystem interface (VFS/vnode) with worst-case overhead of about 2%, and a client and server that by the first customer release beat the ND goal on the benchmark total (Figure 3: about 570 down to about 290 against ND's about 300). Raw transfer: 120 KB/s read, 40 KB/s write. The weakest spots: make (one RPC per stat) and writes (synchronous on the server).

Mechanisms in dependency order
  1. Foundation: RPC + XDR over UDP (M1); the procedure set (M2); the stateless server with retry until reply (M3), which needs idempotent procedures (M4).
  2. Forced by statelessness: file handles with generation numbers (M5), synchronous server writes (M6), one name per lookup (M12), no locks (M21).
  3. Plumbing: nfsd and biod kernel contexts (M7); the MOUNT protocol for the first handle (M8); client naming and mounts (M9, M10); the VFS/vnode layer that hosts the client (M11, M12).
  4. Speed: client buffer cache and flush on close (M13), attribute cache (M14), directory name cache (M15), 8 KB requests and fewer copies (M16), program-loading tricks (M17).
  5. UNIX semantics on the client: credentials and root (M18, M19), open-file removal (M20), time skew (M22), hard and soft mounts (M23).
The central trade-off

Statelessness buys trivial crash recovery, a small protocol, portability (any OS can be a client or server), and the freedom to mount from many servers. It costs synchronous disk writes on every modification, an RPC per pathname component and per attribute check unless the client caches, and every UNIX feature that needs the server to remember something (locks, open-file lifetime, exact permission semantics, cache consistency between clients). The paper recovers speed with client caches whose consistency is only time-based, and semantics with client-only patches that cover a single client but not interactions between two.

Effect of changes (whole design)
  • Server keeps state (open files, locks, who caches what): locking, exact open-file semantics and real cache consistency become possible, but both sides now need crash detection and recovery, exactly what the paper's "Basic Design" section says it wanted to avoid. Leases are the middle ground: state that expires by itself.
  • Server acknowledges writes before they reach disk: writes get several times faster, but a server crash after the reply silently loses data the client already discarded; the "data will never be lost" claim fails. It works again only if the server's fast storage is stable (inference; for example battery-backed memory).
  • A reliable transport (TCP) instead of UDP: packet loss is hidden, but a server crash still breaks the connection, so the client still retries on a new one and a request can still execute twice; idempotence is still required (inference).
  • Clients send whole pathnames: one RPC instead of one per component, but the server must know where each client mounted things (per-client state) or path resolution breaks at client mount points (paper, M12).
  • Heavy write-sharing between clients: flush on close and fixed attribute timeouts give no guarantee; long writes intermix; there are no locks. NFS was designed for files that are mostly private or read-shared.
  • Untrusted clients: the server believes whatever uid each request carries; root-to-nobody mapping does not help (the paper itself lists impersonation as an open problem).
  • Synchronized clocks: the time-skew problems in ranlib, ls and emacs vanish; NFS's own correctness never depended on clocks (attribute timeouts are local intervals).
  • Higher latency network: every synchronous call, every component lookup and every attribute refresh costs a round trip; caching and batching (the paper's proposed multi-file getattr) matter much more (inference).

M1 · Sun RPC, XDR and UDP: synchronous calls over lossy datagrams

TL;DR
ProblemDefine a remote file service that any machine and OS can implement, and keep it easy to specify and maintain.
MechanismEach file operation is a remote procedure with XDR-defined arguments and results; the caller blocks until the reply; the transport is UDP/IP; lost requests or replies are handled by retrying.
Trade-offSimple, portable, procedure-call semantics, in exchange for one round trip per call (8.8 ms for a null call), one blocked context per outstanding call, and loss handling pushed onto idempotent retries.
Breaks whenA request is not safe to repeat (M4), many requests must be in flight from one kernel (M7), or the network loses many packets (M16).
Key points
  • "The NFS protocol is defined in terms of a set of procedures, their arguments and results, and their effects." "Remote procedure calls are synchronous, that is, the client blocks until the server has completed the call and returned the results."
  • Sun RPC is "transport independent": new transports can be "plugged in" without touching the protocol code. NFS uses UDP and IP. "Since UDP is an unreliable datagram protocol, packets can get lost, but because the NFS protocol is stateless and the NFS requests are idempotent, the client can recover by retrying the call until the packet gets through."
  • XDR "defines the size, bytes order and alignment of basic data types such as string, integer, union, boolean and array"; complex structures are built from them; arguments and results are written in a data definition language "that looks a lot like C declarations".
  • Marshaling, concretely. A local call leaves its arguments in registers or on the stack and the callee reads them in place. An RPC cannot: a char *name points into the client's memory, and the server may differ in byte order (68010 big-endian, VAX little-endian), integer size and struct padding. So the client stub marshals each argument into XDR's canonical form (4-byte big-endian integers; strings and opaque data as a length followed by the bytes, padded to a multiple of 4; unions with an explicit tag) and the server stub unmarshals it into native types. Example: lookup(dirfh, "notes") goes on the wire as the 32-byte opaque handle, then the length 5, the bytes notes and 3 padding bytes (general knowledge of XDR, not spelled out in the paper). The paper's bcopy fix (M16) lives exactly here: XDR now marshals straight into and out of mbuf chains instead of a separate buffer, cutting three copies per side to two.
  • RPC also lets different authentication parameters be "plugged-in" to the packet header of each call; NFS uses a UNIX flavor that carries uid, gid and groups (M18).
  • The user-level RPC and XDR libraries were ported into the kernel; after about a month of tuning (including speed-ups to the kernel's UDP and IP code) a kernel-to-kernel null RPC took 8.8 ms round trip.
  • MOUNT (M8) and Yellow Pages (M18) are separate RPC services built the same way.

        udp_send(server, msg)
        reply = sleep_until(reply with same xid, timeout)
        if reply: return xdr_decode(reply)       # results, or an error status
        if soft_mount and too_many_tries: return ETIMEDOUT   # M23
        # hard mount: resend the identical message forever

# server kernel, inside an nfsd context (M7)
serve():
    loop: msg = udp_receive(); (xid, proc, cred, args) = xdr_decode(msg)
          res = dispatch[proc](cred, args)       # commits modifications before returning (M6)
          udp_send(sender, xdr_encode(xid, res))
  1. Call. A process calls read(fd, buf, 8192) on an NFS file whose block is not cached. The client kernel builds read(fh, 16384, 8192), XDR-encodes it with the caller's credentials, and sends one UDP datagram.
  2. Block. The process sleeps. The call is synchronous: there is no way for this process to issue its next request until this one returns (read-ahead is done by other contexts, M7).
  3. Serve. An nfsd on the server decodes the request, reads the block through the server's own vnode layer, and returns (attr, data): up to 8192 bytes plus the file's attributes.
  4. Return. The client decodes, refreshes its attribute cache from the returned attributes (M14), fills the buffer (M13) and wakes the process.
  5. Cost scale. The paper's numbers: 8.8 ms for a null call; raw sequential read of 120 KB/s, which is 8192 / (120 × 1024) ≈ 67 ms per 8 KB read from request to reply including disk and transfer (computed from the paper's numbers, assuming KB = 1024 bytes).
Assumptions it relies on
  • A1. Packet loss on the local network is rare, so retries are an exception and their cost does not matter (implicit).
  • A2. Every request is safe to repeat (stated: "the NFS requests are idempotent").
  • A3. A process can afford to block for each call; concurrency comes from many processes, not from asynchronous calls (implicit; stated as "Remote procedure calls are synchronous").
  • A4. A common external data format is cheap compared with network and disk time (implicit; later contradicted by the bcopy profile, M16).
  • A5. Round trips are short (a LAN, 8.8 ms), so one call per operation is affordable (implicit).
  • A6. The order in which independent requests are executed does not matter (implicit; UDP and retries can reorder them).
If an assumption changes
  • A1 changes (lossy or congested network): retries become common; each lost IP fragment of an 8 KB datagram forces resending the whole datagram (M16), so throughput collapses faster than the loss rate suggests (inference). Retried non-idempotent calls start producing spurious errors (M4). A reliable transport would hide loss, but crash retries remain.
  • A2 changes (some calls not repeatable): exactly the situation for remove, rename, mkdir and friends (M4). To make retries exact, the server must remember recent replies, which is state; the paper does not do this.
  • A3 changes (callers must not block, as in an event-driven kernel): the client would need asynchronous RPC with completion callbacks. The paper already hits this limit: read-ahead and write-behind need separate daemons (M7), described as "a temporary solution to the problem of handling parallel, synchronous requests in the kernel".
  • A4 changes (encoding is expensive): it was: a gprof showed bcopy as "a big consumer", and the fix was XDR straight into mbuf chains (M16). On a faster CPU this matters less (inference).
  • A5 changes (high latency): every component lookup (M12), every expired attribute (M14) and every synchronous write (M6) costs a full round trip that the caller waits for. Caches and batching become essential; the paper's own plan for make is a getattr "for multiple files in one call" (inference about magnitude; the Leases paper models the same effect with a propagation-delay term).
  • A6 changes (order matters): a delayed duplicate of an old write can arrive after a newer write and overwrite it (M4, figure). The protocol has no sequence numbers per file to prevent this (inference).
Design notes and rejected alternatives

RPC was chosen "for the same reasons that procedure calls help simplify programs". A block-level protocol (ND) was the existing alternative; it gives no sharing of writable files and no machine independence. Transport independence was kept so new transports can be plugged in. Synchronous calls keep the client code simple; the cost shows up as the daemon workaround in M7 and the per-call latency in Figures 2 to 4.

Connections

Leases: the effective lease term at a client is shortened by message propagation and processing time, the same per-call costs as here; with leases, consistency traffic rides on the same request/reply pattern. Threads vs events / cooperative task management: a synchronous RPC is the threaded style: one blocked context (stack) per outstanding call. Livelock: a UDP server that falls behind keeps receiving retransmissions of requests it has not answered yet, adding input load at exactly the wrong time (inference).

M2 · The protocol procedures

TL;DR
ProblemExpress every UNIX file operation as a self-contained request that a stateless server can execute.
MechanismSixteen procedures keyed by file handles; reads and writes carry explicit offsets and counts; lookups take one name; results carry attributes; directories are read with opaque cookies.
Trade-offNo open, close, seek or lock means no server state, in exchange for more RPCs and for UNIX semantics that the client must rebuild.
Breaks whenAn operation needs to span calls (long writes, directory scans during changes) or needs the server to remember the caller.
Key points
  • "The most common NFS procedure parameter is a structure called a file handle (fhandle or fh) which is provided by the server and used by the client to reference a file." The client "never looks at the contents".
  • New fhandles come only from lookup, create and mkdir; the first one, for the root of a filesystem, comes from the MOUNT protocol (M8).
  • There is no open, close, seek or lock procedure. read and write carry the offset, so the server keeps no file position.
  • read returns the file's attributes along with the data; write returns the attributes "after the write takes place"; lookup, create, mkdir and setattr return attributes too. These feed the client's attribute cache (M14).
  • readdir returns "up to count bytes of directory entries"; each entry has a name, a file id and an opaque cookie pointing to the next entry; a cookie of zero starts at the first entry.
  • symlink: "The server does not interpret the string argument in any way." Symbolic links are resolved by the client (this is what makes /private work, M10).
  • setattr sets mode, uid, gid, size, access time and modify time; "Setting the size to zero truncates the file."
  • The paper gives only an outline; the full specification is the separate Sun Network Filesystem Protocol Specification [2].

How it works, step by step

Trace 1: cat /usr/src/x.c on a client that mounted fiat:/usr/src on /usr/src (with /usr local), file length 11,000 bytes, cold caches.

  1. lookup(fh_srcroot, "x.c") → (fh_x, attr{size 11000, mtime ...}). The root handle came from MOUNT.
  2. read(fh_x, 0, 8192) → (attr, 8192 bytes).
  3. read(fh_x, 8192, 8192) → (attr, 2808 bytes): fewer bytes than asked means end of file (11000 − 8192 = 2808).
  4. close sends nothing for a file that was only read (no dirty blocks to flush, M13).

Trace 2: ls -l of a directory with 3 files. readdir(dirfh, 0, count) returns entries a, b, c with cookies; if count bytes did not hold them all, the next call is readdir(dirfh, cookie_of_last, count). Then ls -l needs each file's attributes, so the client issues lookup(dirfh, "a"), lookup(dirfh, "b"), lookup(dirfh, "c") (each returns attributes). Every file costs a round trip unless cached: this is the paper's explanation for why make stays slow.

Assumptions it relies on
  • A1. A file can be named by a server-made handle that stays meaningful across calls and server reboots (stated through M5).
  • A2. Each operation fits in one request: small arguments, data in pieces of at most one transfer (implicit; 8 KB after M16).
  • A3. Clients do not need the server to know a file is open (implicit; no open or close).
  • A4. Returning attributes with every reply is cheap and useful (implicit).
  • A5. A readdir cookie stays meaningful between calls without the server remembering the scan (implicit).
If an assumption changes
  • A1 changes: if handles changed on reboot, every client would need to remount after every server crash; statelessness would be gone in practice (M5).
  • A2 changes: an operation longer than one request loses atomicity: a 24 KB write is three RPCs and can interleave with another client's (paper, M21).
  • A3 changes (open/close added to the protocol): the server could keep open counts and solve open-file removal exactly (M20), but it would hold per-client state and need crash recovery (inference).
  • A4 changes (no attributes in replies): the client would need extra getattr calls; getattr was already 90% of calls before the attribute cache (M14).
  • A5 changes (directory modified between readdir calls): a cookie may now point past a removed entry or before an inserted one, so a scan can skip or repeat names. The paper does not discuss this (inference).
Design notes and rejected alternatives

"Many of the vnode procedures map one-to-one with NFS protocol procedures, while other, UNIX dependent procedures such as open, close, and ioctl do not." The procedure set is a deliberately UNIX-neutral subset: no pathnames (except in MOUNT), no file positions, no device control. Passing whole pathnames was rejected (M12).

Connections

Leases: the Leases paper notes that a lease must cover not only file data but also name-to-file bindings and permission information; in NFS those are the results of lookup and getattr, which the client caches with fixed timeouts (M14, M15).

M3 · The stateless server and retry until reply

TL;DR
ProblemClients mount from many servers, so server crashes must be easy to survive; stateful servers need both sides to detect each other's crashes.
MechanismEach call carries everything needed; the server remembers nothing between calls and commits before replying; the client resends until it gets a reply.
Trade-offZero recovery code and no lost data on a hard mount, in exchange for synchronous writes, bigger requests, and no protocol features that need memory.
Breaks whenRetried requests are not idempotent (M4), the server replies before data is stable (M6), or clients need coordination (locks, invalidations).
Key points
  • "The parameters to each procedure call contain all of the information necessary to complete the call, and the server does not keep track of any past requests."
  • Server crash: "the client resends NFS requests until a response is received, and the server does no crash recovery at all." Client crash: "no recovery is necessary for either the client or the server."
  • With state, "Both client and server need to be able to reliably detect crashes": the server to discard a dead client's state, the client to rebuild the server's state.
  • "If a client just resends requests until a response is received, data will never be lost due to a server crash." This holds because the server commits before replying (M6) and the client keeps the request until the reply.
  • "In fact the client can not tell the difference between a server that has crashed and recovered, and a server that is slow."
  • What the server does keep: the filesystem on disk (stable), a buffer cache used for reads (losing it costs nothing), /etc/exports. What it does not keep: open files, file positions, locks, which clients exist or what they cache (paper, with the list assembled by inference from the procedure set).
How it works, step by step

The signature figure on The Big Idea tab shows the full sequence. Time step by time step:

  1. t0. Client sends write(fh, 8192, 8192, data) and starts a timer. The server writes the block, the indirect block if modified, and the inode to disk, then replies. The reply is lost.
  2. t1. The timer fires. The client sends the identical request. The server crashes before handling it; the request is gone, as is everything in the server's memory.
  3. Reboot. The server comes back and simply starts serving. There is no list of clients to contact and no table to rebuild.
  4. t2. The client's timer fires again. The same request arrives; the server decodes the handle from on-disk fields (M5), writes the same 8192 bytes at the same offset (a no-op in effect), commits and replies. The client's write() returns once.
  5. Client crash instead. If the client had crashed at t1, the server would never know or care. The client loses whatever dirty blocks it had not yet sent (M13), exactly as a local crash loses unwritten buffer-cache blocks (inference).
Assumptions it relies on
  • A1. Everything needed for a request fits in the request: handle, offset, count, credentials (stated).
  • A2. Requests are idempotent (stated; partly false, M4).
  • A3. The server commits modified data to stable storage before replying (stated, M6).
  • A4. A server failure is a crash and reboot with its disk intact (implicit).
  • A5. Clients are willing to wait for a crashed server to return (implicit; true for hard mounts, M23).
  • A6. No feature needs coordination across clients through the server (implicit; locking is excluded, M21).
If an assumption changes
  • A1 changes (requests refer to server-side context, like an open file id or a current position): the server must keep tables; after a crash they are empty, so the client must detect the crash and rebuild them, and the server must detect dead clients to free their entries. This is the recovery problem the paper describes and avoids.
  • A2 changes: a retry after a lost reply executes the operation twice. For reads and writes at fixed offsets this is harmless; for remove, rename, mkdir and others it yields spurious errors, and delayed duplicate writes can overwrite newer data (M4).
  • A3 changes (reply before commit): a crash between the reply and the disk write loses data the client already threw away, and nobody finds out. The "data will never be lost" sentence becomes false while every message still looks normal (inference).
  • A4 changes (the server loses or rolls back its disk, for example a restore from backup): handles may name inodes that now hold other files or nothing; generation numbers detect reuse only if they are on disk and never go backward. No protocol mechanism recovers lost data (inference).
  • A5 changes (clients must not wait, soft mounts): the client gives up and returns an error; programs that do not check return codes misbehave, and on a write the data may be lost (M23).
  • A6 changes (clients need locks or cache invalidations): those need memory at the server about who holds what. The paper puts locking in a separate stateful service with a status monitor for crash recovery; the Leases paper shows state that expires by itself, so a crashed server only has to wait one maximum term.
Design notes and rejected alternatives

The paper explicitly compares against a stateful design and rejects it for its recovery complexity. Statelessness also keeps the protocol small and machine independent: no OS-specific session model is needed. The price list is the rest of this Part: M4, M6, M12, M20, M21.

Connections

Leases: the Leases paper places NFS among systems "not guaranteeing consistency" and notes that "the soft state required for leasing is compatible with the so-called stateless interface used in NFS"; after a crash a lease server must honor leases it can no longer remember, by delaying writes for the longest term it ever granted. Worse is better: NFS picks implementation simplicity (no recovery code) over complete semantics, and says so.

M4 · Idempotence, and the procedures that are not idempotent

TL;DR
ProblemA retry after a lost reply makes the server execute a request twice; that must not change the outcome.
MechanismMake requests absolute: explicit offsets, explicit attribute values, names instead of positions, so a repeat recomputes the same state.
Trade-offNo duplicate-detection state on the server, in exchange for spurious errors on the directory-changing calls and rare overwrite anomalies.
Breaks whenThe first execution changed the precondition (a name is gone or now exists), or another client acted between the original and a late duplicate.
Key points
  • The paper calls "the NFS requests" idempotent and relies on that for retries. It does not discuss the exceptions; the classification below is this guide's (inference from the procedure definitions).
  • Truly idempotent: null, getattr, lookup, read, readlink, readdir, statfs (they change nothing). write and setattr set absolute values, so repeating one immediately gives the same state.
  • Not idempotent: remove and rmdir (second try: no such entry), rename (second try: old name gone), link, symlink, mkdir (second try: name exists). create depends on how the server treats an existing name: it may succeed again (and if the attributes set size 0, truncate data written in between) or fail.
  • The usual symptom is a spurious error after success, not corruption. Corruption needs a delayed duplicate plus an intervening change, as in figure (b) below.
  • General knowledge, not in the paper: later NFS servers keep a small cache of recent replies keyed by RPC transaction id (a "duplicate request cache") to answer retries of non-idempotent calls. It is server state, but soft: if lost in a crash, behavior falls back to the spurious-error case.
How it works, step by step
  1. Remove, lost reply. remove(dirfh, "a") → server deletes "a", replies OK → reply lost → timeout → same call → server: no entry "a" → error. The client cannot distinguish "already done by me" from "never existed".
  2. Rename, worse case (inference). rename(d, "x", d, "y") succeeds, reply lost. Before the retry, another process creates a new "x". The retry renames the new "x" over "y", destroying the file that the first rename put there.
  3. mkdir used as a lock (inference). Programs that use "create succeeds only if the name does not exist" as mutual exclusion can be fooled: a retried mkdir whose first attempt succeeded returns "exists", so the caller concludes someone else holds the lock, while in fact it does.
  4. setattr truncate, late duplicate (inference). setattr(fh, size 0) is delayed; the client retries, succeeds, then writes 8 KB of new data; the late original arrives and truncates the file to zero again.
Assumptions it relies on
  • A1. Replies are rarely lost, so retries of non-idempotent calls are rare (implicit).
  • A2. No other client or process changes the same object between an original and its retry (implicit).
  • A3. The network does not hold a datagram longer than the client's retry timeout (implicit).
  • A4. Programs tolerate an occasional spurious error from a rare retry (implicit).
If an assumption changes
  • A1 changes (lossy network or overloaded server that answers late): retries become frequent and rm, mv, mkdir report false failures regularly; scripts that stop on error break (inference).
  • A2 changes (write-sharing): late duplicates can overwrite newer data from another client (figure, panel b) and retried renames can hit a different file. The fix needs memory of executed requests on the server (inference).
  • A3 changes (gateways that queue packets for long): a duplicate can arrive after the client has moved on; nothing in the request (no per-file sequence number) lets the server reject it (inference).
  • A4 changes (programs treat the error as fatal or as a signal): lock-by-mkdir or lock-by-exclusive-create protocols misbehave as in step 3. File-based locking over NFS is therefore unreliable even before M21's missing lock service (inference).
Design notes and rejected alternatives

Two ways to get exactly-once behavior were available in principle: remember replies (state) or redesign each call to be idempotent (for example creates that carry a unique token; general knowledge, later NFS versions did this). The paper does neither and accepts rare anomalies, consistent with its preference for simplicity.

Connections

Leases: both designs must survive lost and late messages. NFS does it by making requests repeatable; leases do it by bounding every promise in time, so a lost approval or extension costs at most one term of delay. Eraser: panel (b) is a write-write race at file-block granularity with no lock to order it.

M5 · File handles and inode generation numbers

TL;DR
ProblemA stateless server must find the right file from the request alone, even after a reboot, and must notice when a file was deleted and its inode reused.
MechanismThe handle is (filesystem id from the superblock, inode number, inode generation number); the generation number is incremented every time the inode is freed; clients treat handles as opaque.
Trade-offServer needs no handle table and handles survive reboots and renames, in exchange for two on-disk format changes and handles that die with the inode.
Breaks whenAny of the three fields is not stable on disk (fsid changes, inodes move, generation numbers reset), or a client needs to name a file that no longer has an inode.
Key points
  • "Another modification to UNIX necessary to make the server work is the addition of a generation number in the inode, and a filesystem id in the superblock." Together with the inode number they form the fhandle.
  • "The inode generation number is necessary because the server may hand out an fhandle with an inode number of a file that is later removed and the inode reused. When the original fhandle comes back, the server must be able to tell that this inode number now refers to a different file. The generation number has to be incremented every time the inode is freed."
  • The handle is opaque: "the client never looks at the contents of the fhandle". A non-UNIX server may put anything in it (machine independence).
  • The handle names the inode, not the path. It stays valid after a rename (which is why rename-on-remove keeps reads working, M20) and after a server reboot (all three fields are on disk).
  • The root handle comes from MOUNT through the getfh system call (M8); others from lookup, create, mkdir.
  • General knowledge, not in the paper: a request with an outdated handle gets the error later named "stale NFS file handle" (ESTALE).

Assumptions it relies on
  • A1. The filesystem id is unique on the server and stable across reboots (implicit).
  • A2. A file keeps its inode number for its whole life (implicit; true for 4.2).
  • A3. The generation number is stored on disk and only ever increases (stated: incremented on every free; persistence implicit).
  • A4. Clients never interpret handles (stated).
  • A5. A handle is only ever sent to the server that issued it (implicit).
If an assumption changes
  • A1 changes (fsid changes, for example a disk moved to another drive slot or a filesystem rebuilt): every outstanding handle for that filesystem fails; clients must unmount and remount. If an old fsid were reassigned to a different filesystem, handles could even resolve there (inference).
  • A2 changes (a filesystem type that relocates files internally): handles silently point to the wrong file or to nothing. Any new server filesystem type (the paper lists VMS, System V, and a planned high-performance one) must provide stable file ids to be exportable (inference).
  • A3 changes (generation kept only in memory, or reset): after a reboot the server cannot detect reuse; an old handle reads or overwrites whatever file now owns the inode, with no error anywhere (inference).
  • A4 changes (clients parse handles): server formats can no longer change and non-UNIX servers must imitate UNIX layout; machine independence is lost (inference).
  • A5 changes (replicated or migrated servers): a handle from server X is meaningless on server Y unless Y has the same fsid, inode numbers and generations; moving a filesystem breaks every client's handles (inference).
Design notes and rejected alternatives

Pathnames as file names would break on rename, require the server to parse paths (the paper wants MOUNT to be the only place pathnames reach the server), and cross client mount points (M12). A server-side table of issued handles would be state. Inode-based handles need only two small on-disk changes. General knowledge, not in the paper: because the handle is the only capability needed for access after mount, anyone who learns or guesses a handle can bypass the mount-time export check; this is part of the security weakness the paper admits.

Connections

Handles are why M3 works (no table to rebuild) and why M20 works (a rename keeps the handle). Leases: the datum a lease covers is identified the same way, by a server-chosen id; expiry, not identity, is what makes lease state soft.

M6 · Synchronous server writes

TL;DR
ProblemAfter a reply the client forgets the data; if the server held it only in memory, a crash would lose it silently.
MechanismEvery modifying request flushes all modified data to disk before the reply: for a write, the data block, any modified indirect blocks and the inode block.
Trade-offNo data lost to server crashes, in exchange for slow writes: raw write 40 KB/s versus 120 KB/s read.
Breaks whenWrites are a large share of the work, or the "disk" acknowledges before data is really stable.
Key points
  • "Because the NFS server is stateless, as mentioned above, when servicing an NFS request it must commit any modified data to stable storage before returning results."
  • "This means that, for example on a write request, not only the data block, but also any modified indirect blocks and the block containing the inode must be flushed if they have been modified."
  • The vnode interface itself had to be modified "to allow the NFS server to do synchronous write operations. This was necessary since unwritten blocks in the server's buffer cache are part of the 'client's state'."
  • The rule applies to every request that modifies the filesystem (create, remove, rename, setattr, mkdir and so on), not just write.
  • Write is one of the two remaining slow operations: "it is synchronous on the server. Fortunately, the number of write calls in normal use is very small (about 5% of all calls to the server) so it is not noticeable unless the client does a large write to a remote file."
  • Raw transfer measured: 120 KB/s for read (cp bigfile /dev/null) and 40 KB/s for write.
How it works, step by step
  1. Request. write(fh, 98304, 8192, data): offset 98304 = 12 × 8192, so this is file block 12. In 4.2BSD with 8 KB blocks and 12 direct pointers (general knowledge, not in the paper) block 12 is the first block reached through the single indirect block.
  2. Update in memory. The server allocates a disk block, copies the data into a buffer, stores the new block's address in the indirect block, and updates the inode's size and modify time.
  3. Commit. Disk write 1: the data block. Disk write 2: the indirect block (modified: it gained a pointer). Disk write 3: the block holding the inode (size and mtime changed).
  4. Reply. (attr) with the new size 106496 and new mtime. The client may now drop its copy.
  5. Rewrite. A second write to the same block (same size, existing block) modifies only the data block and the inode's mtime: two disk writes, no indirect block (inference from "flushed if they have been modified").
  6. Arithmetic. 40 KB/s means 8192 / (40 × 1024) = 0.2 s per 8 KB write request end to end, against about 67 ms per 8 KB read (computed from the paper's raw numbers). The factor of three is consistent with several synchronous disk writes per request (inference).
Assumptions it relies on
  • A1. Writes are a small fraction of server calls (stated: about 5%).
  • A2. The client keeps the data until the reply arrives, and only then discards it (implicit).
  • A3. When the disk driver reports a write complete, the data is on the platter (implicit).
  • A4. Disk is the only stable storage available (implicit, 1985).
  • A5. Client-side write-behind (M7, M13) hides the latency from most programs (implicit).
If an assumption changes
  • A1 changes (write-heavy workload, for example large builds that write many object files or a shared log): every 8 KB written waits for several disk writes; throughput per client stream stays near 40 KB/s and the server disk becomes the bottleneck (inference). The paper's remedy is future server hardware, not a protocol change.
  • A2 changes (client discards data when it sends): a server crash before commit loses the data with no retry possible; synchronous server writes are useless without the client holding the data (inference).
  • A3 changes (a disk or controller that acknowledges from a volatile write cache): the server replies "stable" while the data is not; a power failure loses acknowledged writes, and the stateless guarantee is silently broken (inference).
  • A4 changes (non-volatile memory on the server): the server may reply once data is in NVRAM; writes become fast and the guarantee holds, because the rule is "stable storage", not "disk" (inference; general knowledge: later NFS servers did this).
  • A5 changes (no write-behind): every application write() of 8 KB blocks for about 0.2 s (computed above).
Design notes and rejected alternatives

Replying early and committing later was the obvious faster alternative; it would make unflushed server buffers part of the client's state, which is precisely what statelessness forbids. General knowledge, not in the paper: a later NFS version added asynchronous writes plus an explicit commit call, and needed a server "verifier" that changes on reboot so clients can detect lost uncommitted data, a small piece of state. The paper's future work lists faster server hardware and a stand-alone NFS server with a new filesystem type "for higher performance".

Connections

Leases: its fault-tolerance argument also assumes "writes are persistent at the server across a crash", and its caches are write-through, so the same commit-before-reply rule underlies its consistency. M13 shows the client half: the client may delay sending, but once sent and acknowledged, data is durable.

M7 · Kernel contexts: nfsd on the server, block I/O daemons on the client

TL;DR
ProblemThe 4.2 kernel can only sleep in a process context, but the NFS server runs in the kernel, and the client's read-ahead and write-behind must wait on blocking RPCs.
MechanismUser-level processes enter the kernel and never return: nfsd processes serve requests on the server; block I/O daemons on the client perform asynchronous block reads and writes.
Trade-offWorks with no kernel threads, in exchange for a fixed pool of contexts that caps concurrency, and a design the authors call temporary.
Breaks whenMore requests arrive than there are daemons, or work arrives faster than the daemons drain it.
Key points
  • "NFS server daemons ... are user level processes that make an nfsd system call into the kernel, and never return. This provides a user context to the kernel NFS server which allows the server to sleep."
  • "Similarly, the block I/O daemon, on the client side, is a user level process that lives in the kernel and services asynchronous block I/O requests. Because the RPC requests are blocking, a user context is necessary to wait for read-ahead and write-behind requests to complete."
  • "These daemons provide a temporary solution to the problem of handling parallel, synchronous requests in the kernel. In the future we hope to use a light-weight process mechanism in the kernel."
  • The MOUNT server is a different, ordinary user-level daemon (M8); nfsd only borrows a process to run kernel code.
  • General knowledge, not in the paper: the client daemon is usually called biod; the number of nfsd and biod processes is set by the administrator.
How it works, step by step
# server: each nfsd process
main(): nfsd_syscall()                      # never returns
nfsd_syscall():
    loop: req = sleep_receive(nfs_socket)    # sleep until a datagram arrives
          serve(req)                          # may sleep again on disk I/O (M6)

# client: each block I/O daemon
biod_loop():
    loop: buf = sleep_dequeue(async_queue)
          if buf.is_read:  rpc read(buf.fh, buf.off, 8192)  # read-ahead
          else:            rpc write(buf.fh, buf.off, buf.len, buf.data)  # write-behind
          mark buf done; wake anyone waiting

# client: queueing async work (fallback is general knowledge)
start_async(buf): if an idle biod exists: enqueue(buf) else: do the RPC synchronously in the caller
  1. Server, 4 nfsds, 6 requests arrive at once (illustrative). Four nfsds each take one request and sleep on disk I/O; requests 5 and 6 wait in the socket's receive buffer until an nfsd finishes.
  2. Client sequential write of 24 KB with 2 daemons (illustrative). Block 0 fills → handed to daemon 1 (a write RPC of about 0.2 s, M6); block 1 fills → daemon 2; block 2 fills → no idle daemon, so the writing process does that RPC itself and blocks.
  3. Client sequential read. The process's read of block n misses and does a synchronous read RPC; the kernel also queues block n+1 for a daemon, so the next read finds it cached.
Assumptions it relies on
  • A1. The kernel has no lightweight threads; only a process can sleep (stated).
  • A2. RPCs are blocking calls (stated).
  • A3. A small fixed number of daemons covers the useful concurrency (implicit).
  • A4. Requests are independent, so any daemon can serve any request in any order (implicit; follows from statelessness).
If an assumption changes
  • A1 changes (kernel threads exist): the daemons become kernel threads; nothing else in the design changes. This is the paper's stated plan.
  • A2 changes (asynchronous RPC with completion callbacks): one context could keep many requests in flight; read-ahead and write-behind would not need daemons at all (inference).
  • A3 changes (more concurrent requests than daemons): on the server, requests queue in the UDP socket buffer; when it fills, datagrams are dropped, clients time out and retransmit, adding load. On the client, writers fall back to synchronous RPCs (inference).
  • A4 changes (requests depend on each other): two daemons could execute a client's writes out of order; with independent absolute-offset writes that is harmless, which is why the pool design works (inference).
Design notes and rejected alternatives

A light-weight process mechanism in the kernel [4] was the preferred design but was not available. The paper presents the daemons as a stopgap.

Connections

Threads vs events, cooperative task management: a blocking call needs a stack to block on; the daemons are a manually managed thread pool. Livelock: a server whose nfsds cannot keep up drops datagrams at the socket, and client retransmissions raise input load further (inference).

M8 · The MOUNT protocol and exports

TL;DR
ProblemA client needs a first handle for a remote filesystem, the server needs to control which clients get it, and pathname syntax is OS-specific.
MechanismA separate RPC protocol: the client sends a directory pathname; a user-level mount daemon checks /etc/exports and, if allowed, converts the path with the getfh system call and returns the handle.
Trade-offAccess checking and pathnames are isolated in one replaceable protocol, in exchange for checking access only at mount time.
Breaks whenExports change after clients mounted, or handles leak to hosts that never mounted.
Key points
  • "The MOUNT protocol takes a directory pathname and returns an fhandle if the client has access permission to the filesystem which contains that directory."
  • Why separate: "this makes it easier to plug in new filesystem access checking methods, and it separates out the operating system dependent aspects of the protocol." "MOUNT protocol is the only place that UNIX pathnames are passed to the server." Other OSes can replace MOUNT "without having to change the NFS protocol".
  • History: "Our first implementation of the MOUNT protocol was built into the NFS protocol." It was later broken out "into a separate, user level RPC service".
  • "The MOUNT server is a user level daemon that is started automatically when a mount request comes in. It checks the file /etc/exports which contains a list of exported filesystems and the clients that can import them. If the client has import permission, the mount daemon does a getfh system call to convert a pathname into an fhandle which is returned to the client."
  • On the client, the mount command takes a filesystem type and an options string; for NFS the options include hard or soft (M23).
  • The paper describes no per-call check that the calling host appears in /etc/exports; once a client has a handle, NFS calls are checked only by user credentials (M18) (inference from the text).
How it works, step by step
Assumptions it relies on
  • A1. Export decisions change rarely, so checking once at mount time is enough (implicit).
  • A2. A client host's identity on the network can be trusted (implicit; the paper later admits impersonation).
  • A3. Pathname syntax and access policy are the only OS-specific parts worth isolating (stated).
  • A4. The handle obtained at mount stays valid across server reboots (implicit; M5).
If an assumption changes
  • A1 changes (an export is withdrawn from a client): clients that already mounted still hold valid handles and keep working until they unmount, unless the server also checks on each call (which it would have to do from its exports list on every request) (inference).
  • A2 changes (hosts can be impersonated): the exports list protects nothing against a forged host; the paper's future work is public-key authentication.
  • A3 changes (a non-UNIX server): it implements its own MOUNT with its own path syntax; the NFS protocol is untouched (paper).
  • A4 changes (handles change on reboot): every client must remount after every server restart, and the hard-mount promise in M23 fails (inference).
Design notes and rejected alternatives

Building MOUNT into NFS was the first implementation and was abandoned for the reasons above. Automatic mounting (a filesystem type with a directory per exported filesystem, plus "automatic redirection" from the server when a mount point is reached) is listed as future work.

Connections

Supplies the root handle M5 needs and the VFS that M11 and M12 attach. The mount daemon is a user-level RPC service, unlike nfsd (M7).

M9 · Naming: bind once per filesystem, flexible names, no crossing server mount points

TL;DR
ProblemGive remote files ordinary pathnames without changing pathname structure, and keep hostnames out of programs.
MechanismDo the hostname lookup and binding once per filesystem with mount; servers export whole filesystems; clients mount any subdirectory anywhere; servers never cross their own mount points on lookups.
Trade-offTransparent names and per-mount access checks, in exchange for a mount step before access, names that can differ per client, and one mount per server filesystem.
Breaks whenClients mount inconsistently, or a user expects to see a server's nested filesystems through a single mount.
Key points
  • Schemes that name remote files host:path do "not allow real transparent access since existing programs that parse pathnames have to be modified."
  • "Rather than doing a 'late binding' of file address, we decided to do the hostname lookup and file address binding once per filesystem". Advantages: hostnames handled once, at mount; the server can limit access by checking client credentials. Disadvantage: "remote files are not available to the client until a mount is done."
  • "Servers export whole filesystems, but clients can mount any sub-directory of a remote filesystem on top of a local filesystem, or on top of another remote filesystem. In fact, a remote filesystem can be mounted more than once, and can even be mounted on another copy of itself!"
  • Policy, not mechanism: a basic set of mounts on each machine; home directories on /usr/servername (the names could have been /usr/1, /usr/2); any user can log in anywhere and find the home directory; C-shell tilde expansion works across the network.
  • "To avoid the problems of loop detection and dynamic filesystem access checking, servers do not cross mount points on remote lookup requests." So "a client has to remote mount each of the server's exported filesystems" to see the server's layout.
  • The df listing shows a diskless workstation reaching "more than a Gigabyte of disk" (F2).
How it works, step by step
  1. Server layout. Server panic has two local filesystems: one mounted at /usr, another mounted at /usr/panic (both appear in the paper's df listing as separate client mounts).
  2. Client mounts only panic:/usr on /usr. A lookup of panic in that filesystem's root is executed by the server inside the /usr filesystem. Because the server does not cross mount points, it returns the handle of the directory /usr/panic in the /usr filesystem, the mount-point directory underneath, usually empty, not the root of the filesystem mounted there (inference from the rule).
  3. Client also mounts panic:/usr/panic on /usr/panic. Now the client's own vnode for /usr/panic carries a mounted-on VFS pointer, and the client crosses into the second filesystem itself (M12). This matches the df listing.
  4. Why the rule (inference elaborated from the paper's phrase). Loop detection: if servers followed their own mounts, and a server mounted (over NFS) a filesystem that leads back to itself, a lookup chain could cycle between machines. Dynamic access checking: exports are per filesystem; crossing into another filesystem during a lookup would require checking, on every lookup, whether this client may access the new one.
Assumptions it relies on
  • A1. Users accept an explicit mount step before access (stated as the disadvantage).
  • A2. Administrators keep a consistent naming policy by convention (stated: "just policy").
  • A3. Exported filesystems are few and coarse, so one mount per filesystem is manageable (implicit).
  • A4. A server's name and address stay fixed while mounted (implicit).
If an assumption changes
  • A1 changes (users want any remote file without mounting): the paper's future "automatic mounting" filesystem type and server redirection at mount points.
  • A2 changes (each client mounts things in different places): the same file has different absolute names on different machines; scripts, symbolic links with absolute targets and shared configuration files break when moved between clients (inference).
  • A3 changes (many small exported filesystems): the client needs one mount per filesystem to see the server's tree; mount tables grow and drift (inference); again motivating automounting.
  • A4 changes (a server is renamed or moved): its hostname was resolved once at mount time, so existing mounts keep the old binding until remounted (inference).
Design notes and rejected alternatives

Late binding (host:path resolved at each access) was rejected for transparency. Crossing server mount points was rejected for loops and access checking. Hostnames inside /usr/servername are a convenience, which the paper argues does not violate transparency because the directory names are arbitrary.

Connections

M12 is the mechanism that makes per-client mount points work without server knowledge. M10 covers the one filesystem that could not be shared: root.

M10 · Root filesystems, /private, and diskless clients

TL;DR
ProblemDiskless workstations would like to share one root filesystem, but the root holds machine-specific files, /tmp and /dev.
MechanismNo shared NFS root: each client keeps a private root (local disk or ND); machine-specific files from shared filesystems move to /private and are replaced by symbolic links.
Trade-offShared /usr and home directories now, in exchange for two remote-access protocols (ND and NFS) on diskless machines.
Breaks whenA client has no private storage, or a program puts per-machine state under a shared path.
Key points
  • "Our current NFS implementation does not allow shared NFS root filesystems." Reasons given: many well-known machine-specific files on the root used by many programs; sharing /tmp is a problem "because programs create temporary files using their process id, which is not unique across machines"; sharing /dev needs remote device access.
  • Considered: making operations on device nodes appear local. Problem: "many programs make special use of the ownership and permissions of device nodes."
  • "Since every client has private storage (either real disk or ND) for the root filesystem", machine-specific files were moved "from shared filesystems into a new directory called /private" and replaced with symbolic links. Moved: /usr/lib/crontab and the whole /usr/adm directory. Clients boot "with only /etc and /bin executables local"; /usr and others are remote.
  • Future work ("Full Diskless Operation"): diskless machines "must use both ND and NFS", doubling administration; plans for TFTP booting plus NFS additions for shared root, shared remote swapping and remote device access.
How it works, step by step
  1. Symlink on the shared filesystem. /usr/adm on the server is a symbolic link whose string points into /private (the exact target string is not given in the paper).
  2. Client resolution. Client A's namei reaches adm in the remote /usr, gets a symlink, calls readlink (the server returns the uninterpreted string, M2), and continues the lookup on the client from that string. The string leads into A's own root filesystem, so A's log files land on A's private storage.
  3. Client B follows the same link to its own /private. One shared link, a different target on every machine: this works only because the client, not the server, interprets symbolic links (inference from "the server does not interpret the string").
  4. Why /tmp cannot be shared (paper's reason, worked): process 1234 on client A and process 1234 on client B both create /tmp/sh1234; on a shared /tmp it is the same file.
Assumptions it relies on
  • A1. Every client has private storage for its root (stated).
  • A2. Programs name temporary files by process id (stated).
  • A3. Programs depend on device node ownership and permissions (stated).
  • A4. Symbolic links are resolved by the client (implicit in the protocol definition).
If an assumption changes
  • A1 changes (no ND, no disk): the root itself must come over NFS, which needs everything in the "Full Diskless Operation" plan: booting, per-client root areas, swap and devices (paper).
  • A2 changes (temporary names unique across machines, for example including the host name): a shared /tmp would stop colliding, though it would still be slower than local storage and cause cross-client cache effects (inference).
  • A3 changes (device nodes were pure names): the "make device operations appear local" idea would have worked (paper's own reasoning).
  • A4 changes (server-side symlink resolution): every client would follow /private on the server, so the per-machine indirection collapses (inference).
Design notes and rejected alternatives

"There are many hard problems associated with shared root filesystems that we just didn't have time to address." Remote /dev via local interpretation was considered and rejected for the ownership and permission problem.

Connections

Relies on M2's uninterpreted symlink string and M12's client-side traversal.

M11 · The VFS/vnode interface

TL;DR
ProblemPut NFS into the 4.2 kernel so remote files behave like local ones, without special cases throughout the kernel.
MechanismA generic interface: one VFS structure per mounted filesystem with filesystem operations, one vnode per active file with file operations; each filesystem type supplies the operation tables; new types install like device drivers.
Trade-offPluggable filesystems for about 2% worst-case slowdown, in exchange for rewriting every kernel path that touched inodes or disk layout.
Breaks whenA filesystem needs semantics the operation set does not express (locking, remote consistency), or generic code assumes locks that a filesystem cannot provide.
Key points
  • "There is one VFS structure per mounted filesystem in the kernel and one vnode structure for each active node." "Using this abstract data type implementation allows the kernel to treat all filesystems and nodes in the same way."
  • Each filesystem type also provides mount and mount_root.
  • VFS operations: unmount, root (returns the root vnode), statfs, sync (flush delayed write blocks).
  • Vnode operations: open, close, rdwr, ioctl, select, getattr, setattr, access, lookup, create, remove, link, rename, mkdir, rmdir, readdir, symlink, readlink, fsync, inactive, bmap, strategy, bread, brelse. "The bmap, strategy, bread, and brelse procedures are used to do reading and writing using the buffer cache."
  • "Many of the vnode procedures map one-to-one with NFS protocol procedures, while other, UNIX dependent procedures such as open, close, and ioctl do not."
  • Cost: "in most cases the difference was not measurable, and in the worst case the kernel had only slowed down by about 2%." Most work was "finding and fixing all of the places in the kernel that used inodes directly, and code that contained implicit knowledge of inodes or disk layout."
  • Kernel changes: namei changed to use the vnode lookup operation and "cleaned up so that it doesn't use global state"; direnter (adds directory entries) fixed because it depended on namei's global state, and modified "to do directory locking during directory rename operations because inode locking is no longer available at this level, and vnodes are never locked"; a kernel memory allocator so vnode and VFS structures have no fixed limit; a new getdirentries system call, with the 4.2 readdir library routine changed to use it, so programs using readdir must be relinked (not rewritten).
  • Filesystem types built so far: 4.2, NFS, and an MS-DOS filesystem on a floppy. Suggested: VMS or System V disk packs.
How it works, step by step
# structures (fields named by the paper; spellings are general knowledge from SunOS)
struct vfs   { vfs_op;            # unmount, root, statfs, sync
                vfs_vnodecovered;  # back pointer to the vnode this fs is mounted on
                vfs_data; }        # NFS: server address, root fh, mount options
struct vnode { v_op;              # open ... brelse
                v_vfsp;            # the VFS this vnode belongs to
                v_vfsmountedhere;  # VFS mounted on this vnode, if any
                v_count; v_type;
                v_data; }          # 4.2: in-core inode; NFS: fh + cached attributes

# read(fd, buf, n) on any filesystem type
vp = file_table[fd].vnode
vp.v_op.rdwr(vp, uio, READ, flags)      # 4.2: ufs code; NFS: nfs code
  # NFS rdwr: bread(vp, blk) -> cache hit, or strategy(bp) -> read RPC (M13)

Assumptions it relies on
  • A1. All filesystem types can be expressed by one fixed operation set (implicit).
  • A2. An indirect call per operation is cheap relative to the operation (measured: worst about 2%).
  • A3. No kernel code outside a filesystem type needs inode internals or disk layout (made true by the rewrite).
  • A4. Generic code never relies on locking a vnode (stated: "vnodes are never locked").
  • A5. The operation set is UNIX-shaped (open, close, ioctl exist), while the wire protocol is not (implicit).
If an assumption changes
  • A1 changes (a filesystem with locking, access control lists or consistency callbacks): new vnode operations, or overloading ioctl; NFS itself would still have nothing to map them to (inference).
  • A2 changes (operations become very cheap relative to dispatch): the 2% grows; but in 1984 the cost was dominated by disk and network (inference).
  • A3 changes (code that still reaches into inodes): it would break on NFS vnodes, whose private data is a handle, not an inode; this is why every such place had to be found (paper).
  • A4 changes (generic code takes vnode locks for multi-step operations such as rename): NFS cannot hold a server-side lock across RPCs, so the lock would protect only this client's view; the paper instead puts directory locking for rename inside direnter (paper plus inference).
  • A5 changes (a non-UNIX client): it implements the protocol directly; the vnode layer is a UNIX implementation choice, not part of NFS (inference consistent with the machine-independence goal).
Design notes and rejected alternatives

The interface was designed so "new filesystems" can be installed "in much the same way as new device drivers". The alternative, special-casing remote files in system calls or a user-level library, was ruled out by the transparency goal ("no special libraries, no recompiling").

Connections

Mesa monitors: the local filesystem's inode lock acts like a monitor around one write (M21); the vnode layer deliberately has no such lock. M12 uses the VFS and vnode pointers to cross mount points.

M12 · Mount points in the vnode layer, and lookup one component at a time

TL;DR
ProblemAny directory on a client may be a mount point, possibly for another server; a server that resolved whole paths would need to know every client's mounts.
MechanismVnodes point to their VFS and to a VFS mounted on them; VFS root() returns the mounted root; a VFS points back to the vnode it covers; namei looks up one component per call and checks for a mount after each.
Trade-offThe server stays ignorant of client mounts, in exchange for one lookup RPC per remote component on a cache miss.
Breaks whenRound trips are expensive and paths are deep, or cached directory vnodes go stale.
Key points
  • "Each vnode contains a pointer to its parent VFS and a pointer to a mounted-on VFS. This means that any node in a filesystem tree can be a mount point for another filesystem."
  • "A root operation is provided in the VFS to return the root vnode of a mounted filesystem." It is "used instead of just keeping a pointer so that the root vnode for each mounted filesystem can be released."
  • "The VFS of a mounted filesystem also contains a back pointer to the vnode on which it is mounted so that pathnames that include '..' can also be traversed across mount points."
  • "Pathname traversal is done in the kernel by breaking the path into directory components and doing a lookup call through the vnode for each component."
  • Why not whole paths: "any component of the path could be a mount point for another filesystem, and the mount information is kept above the vnode implementation level. In the NFS filesystem, passing whole pathnames would force the server to keep track of all of the mount points of its clients in order to determine where to break the pathname and this would violate server statelessness."
  • "The inefficiency of looking up one component at a time is alleviated with a cache of directory vnodes" (M15).
How it works, step by step
# namei, simplified (structure from the paper; symlink handling is general knowledge)
vp = path starts with "/" ? root_vnode : current_dir
for name in components(path):
    if name == ".." and vp is the root of vp.v_vfsp:
        vp = vp.v_vfsp.vfs_vnodecovered          # cross back over the mount
    vp = vp.v_op.lookup(vp, name)                # NFS: name cache hit, else lookup RPC
    while vp.v_vfsmountedhere:
        vp = vp.v_vfsmountedhere.vfs_op.root()   # cross into the mounted filesystem
    if vp is a symlink (and should be followed):
        rest = readlink(vp) + remaining components # resolved on the client
        restart the walk with rest
return vp
  1. Counting RPCs, cold caches. /usr/panic/notes: usr is local (0 RPCs), panic is a lookup in panic:/usr (1), notes is a lookup in panic:/usr/panic (1). Total: 2 lookup RPCs.
  2. A deeper path. /usr/src/sys/nfs/nfs_vnops.c with fiat:/usr/src mounted on /usr/src and /usr local: sys, nfs, nfs_vnops.c are three lookup RPCs, about 26 ms at 8.8 ms per null round trip before any server work (computed, illustrative file names).
  3. With the directory cache warm (M15), sys and nfs are hits; only the final name costs an RPC.
  4. ".." out of a mount. From /usr/panic (the root of VFS 3), .. first moves to the covered vnode panic in VFS 2 via the back pointer, then looks up .. there, reaching /usr's root in VFS 2.
Assumptions it relies on
  • A1. Mount information belongs to each client and is kept above the vnode layer (stated).
  • A2. One round trip per component is affordable once a cache absorbs repeats (stated).
  • A3. Directory structure changes slowly, so cached directory vnodes stay right (implicit; M15).
  • A4. Servers never cross their own mount points (stated, M9), so every server lookup stays inside one exported filesystem.
If an assumption changes
  • A1 changes (the server knows client mounts): it could resolve a whole path in one RPC, but it holds per-client state that must be rebuilt after a crash; this is the paper's stated reason against it.
  • A2 changes (wide-area latency): an n-component miss costs n round trips in sequence, because each lookup needs the previous handle; deep paths become slow. Batching several lookups per message, or a much larger cache, is needed (inference).
  • A3 changes (directories renamed on the server by another client): a cached directory vnode still holds a valid handle, so this client keeps resolving the old path to the moved directory until a reply's attributes disagree and the cache is flushed (inference from M5 and M15).
  • A4 changes (servers cross their mounts): one client mount would expose the server's nested filesystems, but the server must detect loops and check export permissions during each lookup (paper's reasons, M9).
Design notes and rejected alternatives

"At first glance it seems like a waste of time to pass only one component with each call instead of passing the whole path and receiving back a target vnode." The authors accept the cost for statelessness and fix it with a cache. The root() operation instead of a stored root pointer lets idle root vnodes be released.

Connections

Leases: the Leases paper notes that a cache must also hold name-to-file bindings, under a lease, to support repeated opens; the NFS name cache holds those bindings with no server promise (M15).

M13 · Client buffer cache, read-ahead and write-behind, flush on close

TL;DR
ProblemWith every read and write an RPC, NFS was far slower than ND.
MechanismCache file blocks on the client; read ahead and write behind asynchronously through block I/O daemons; flush a file's dirty blocks to the server on close.
Trade-offFar fewer read and write RPCs, in exchange for consistency defined only by close and by attribute checks, and data loss if the client crashes before flushing.
Breaks whenTwo clients share a file while one is writing, or a long-lived process keeps a file open.
Key points
  • "In our first attempt to increase performance we added buffer caching on the client side to decrease the number of read and write requests going to the server. To maintain cache consistency, files are flushed on close. This helped a lot".
  • Blocks move through the buffer-cache vnode operations (bmap, strategy, bread, brelse). Read-ahead and write-behind need the block I/O daemons (M7). Separately, "read-ahead in the server" was added for sequential reads (M17).
  • What the paper does not say: how a client decides that a cached data block is out of date. The only server-provided signal is the attributes returned on replies (M14). General knowledge, not in the paper: Sun's client remembered the file's modify time when blocks were cached and discarded the cached blocks when fresh attributes (on open, or when the attribute cache entry expired) showed a different modify time; this is usually called close-to-open consistency.
  • Flush on close means the dirty blocks of that file are sent as ordinary write RPCs, each committed by the server on arrival (M6). Whether close waits for all of them, and how errors are reported, is not stated (general knowledge: close waits and returns a write error if one occurred).
  • A client crash loses dirty blocks not yet sent, as a local crash loses unwritten buffers (inference).
How it works, step by step
# NFS client data path (structure from the paper; validation rule is general knowledge)
nfs_read(vp, off, n):
    blk = off / 8192
    if attributes(vp) show a new mtime: invalidate cached blocks of vp   # see M14
    bp = bread(vp, blk)                    # hit: no RPC; miss: strategy -> read RPC
    if access looks sequential: start_async(read blk+1)   # read-ahead via daemon
    copy out

nfs_write(vp, off, n):
    bp = getblk(vp, off / 8192); copy in; mark dirty
    if block is full: start_async(write bp)  # write-behind via daemon
    else: leave dirty (delayed)

nfs_close(vp):
    for each dirty block of vp: write RPC  # "files are flushed on close"
    wait for all of them
  1. Editor saves a 20 KB file (20480 bytes), one client. write fills block 0 (8192 bytes) → handed to a daemon: write(fh, 0, 8192). Block 1 fills → write(fh, 8192, 8192). Block 2 gets 4096 bytes and stays dirty in the cache.
  2. close. The client sends write(fh, 16384, 4096) and waits for the outstanding writes. At the measured 40 KB/s, 20 KB of writes take about 0.5 s (20 / 40, computed).
  3. What the server has at each moment. Before the first reply: nothing new. After block 0's reply: block 0 new, blocks 1 and 2 old. After close: all three new. Each write RPC is applied whole; there is no grouping of the three into one atomic update (M21).
  4. Re-reading on the same client right after: all three blocks are in the client cache; no RPCs (until the cache is invalidated).
  5. Reading on another client that had cached the old version: whether it sees the new data depends on when it next fetches attributes and compares the modify time (M14 and the general-knowledge rule above); the protocol gives it no notification.
Assumptions it relies on
  • A1. Files are rarely written by one client while another client is using them (implicit).
  • A2. Sharing is sequential and bracketed by open and close: a writer closes before a reader opens (implicit; why "flush on close" is the consistency point).
  • A3. Losing unflushed writes on a client crash is acceptable, as for a local disk (implicit).
  • A4. A changed file shows a changed modify time in its attributes (implicit, for any attribute-based validation).
  • A5. Reads are often sequential, so read-ahead pays (implicit).
If an assumption changes
  • A1 changes (concurrent write-sharing): a reader can see some blocks of a write and not others, and can keep using cached blocks after the server copy changed; nothing in the protocol invalidates other clients' caches (inference).
  • A2 changes (long-lived opens, such as a log kept open by a daemon): "flush on close" never happens; data reaches the server only when write-behind or eviction pushes it (general knowledge: also the periodic sync), so other clients can lag for a long time (inference).
  • A3 changes (client crash must not lose data): the client would have to write through every write(), paying a synchronous server write each time (about 0.2 s per 8 KB) (inference from M6).
  • A4 changes (two changes within one timestamp unit, or a clock that does not advance): attribute comparison cannot see the second change, so stale blocks survive (inference).
  • A5 changes (random access, for example a database file): read-ahead wastes RPCs and cache space (inference).
Design notes and rejected alternatives

Alternatives a reader should be able to place: write-through caching (simple failure semantics, slow writes; the Leases paper assumes it), server callbacks to invalidate caches (needs server state), checking with the server on every read (many RPCs; the Leases paper's zero-term case). NFS chose delayed writes with a flush at close and time-based validation.

Connections

Leases: leases define consistency as behavior equivalent to a single uncached copy and guarantee it; NFS defines none, and the Leases paper says so. Eraser: the server sees only the read and write RPCs that miss the client cache or are flushed; client cache hits and the program's own synchronization are invisible to it.

M14 · The attribute cache

TL;DR
Problemgetattr was 90% of all calls to the server; one stat system call caused eleven RPCs, seven of them getattr on the same file.
MechanismCache attributes on the client, refresh them from every reply that carries attributes, and discard entries after 3 s for files and 30 s for directories.
Trade-offgetattr fell to about 10% of calls, in exchange for attributes up to 3 s (files) or 30 s (directories) out of date.
Breaks whenAnother client changes a file or directory inside the window and a program acts on the old size, mtime or mode.
Key points
  • "Using statistics gathered on the NFS server, we noticed that getattr (stat) accounted for 90% of the calls made to the server. In fact, the stat system call itself caused eleven RPC requests, seven of which were getattr requests on the same file."
  • "The cache is updated every time new attributes arrive from the server, and entries are discarded after three seconds for files or thirty seconds for directories. This caused the number of getattr requests to drop to about 10% of the total calls."
  • The timeouts are client-local intervals. The server promises nothing and does not know the cache exists.
  • Fixed constants in the paper (general knowledge: later clients made the interval adaptive to how recently the file changed).
  • In Figure 3 this step moves the benchmark total from about 365 to about 315 (read-off values, F4).
How it works, step by step
nfs_getattr(vp):
    ttl = vp is a directory ? 30 : 3          # seconds
    if now - vp.attr_time < ttl: return vp.attr  # no RPC
    vp.attr = rpc getattr(vp.fh); vp.attr_time = now
    return vp.attr

on_any_reply_with_attributes(vp, attr):     # lookup, read, write, setattr, create ...
    vp.attr = attr; vp.attr_time = now
  1. The stat example. Before the cache, one stat = 11 RPCs, 7 of them getattr on the same file. With the cache, the first getattr fills the entry and the other six are hits (inference about which six; the paper gives only the totals).
  2. The 90% → 10% arithmetic (inference, assuming the number of non-getattr calls stayed the same): before, 100 calls = 90 getattr + 10 other. After, getattr is 10% of the total, so 10 other calls = 90% of the total, total ≈ 11.1, getattr ≈ 1.1. That is about 99% fewer getattr calls and about 89% fewer calls overall.
  3. The make problem that remains. make stats every file it considers; each first stat of a file misses (one RPC per file), while locally the inodes of a whole directory end up in the buffer cache and stat "is just a memory reference". The authors consider "modifying the getattr operation to return attributes for multiple files in one call".
Assumptions it relies on
  • A1. A file seen by one client rarely changes on another client within 3 s (implicit).
  • A2. Directories change even less often, justifying 30 s (implicit).
  • A3. Programs tolerate size, mtime and mode values up to the window old (implicit).
  • A4. The client can measure 3 s locally; no clock agreement with the server is needed (implicit).
  • A5. Attributes in a reply are current as of that reply (implicit).
If an assumption changes
  • A1 changes (a file appended by another client, such as a shared log): A believes the old size for up to 3 s, so reads stop at the old end of file and the new tail is invisible until the entry expires or a reply refreshes it (inference).
  • A2 changes (busy shared directories, such as a mail spool): directory attributes trusted for 30 s mean the client may not notice the directory changed; names cached in M15 may refer to files another client removed, which then fail with a stale handle when used (inference).
  • A3 changes (programs that decide from mtime, such as make): a 3 s stale mtime can make a dependency look older than it is, so a rebuild is skipped (inference).
  • A4 changes (client clock jumps): only the local interval matters, so skew with the server is irrelevant here, unlike in M22 and unlike leases (inference).
  • A5 changes (replies arrive out of order): an older reply processed after a newer one could install older attributes; the paper does not discuss ordering (inference).
Design notes and rejected alternatives

No cache meant 90% of all server work was getattr. A server-driven invalidation scheme would need the server to remember which clients cache which attributes (state). A fixed client-side timeout needs no server cooperation, which fits statelessness, and bounds how long attributes can be stale only from the client's side: the server cannot shorten it before a write.

Connections

Leases: an attribute-cache entry behaves like a 3 s lease the server never agreed to: the client stops trusting it on its own timer, but the server never waits for it before allowing a write, so it guarantees nothing. The Leases paper's zero-term and infinite-term endpoints correspond to "always ask" and "never ask"; NFS sits at a fixed short term with no write-side rule.

M15 · The directory name lookup cache

TL;DR
ProblemOne lookup RPC per pathname component (M12) is slow for programs that open many files under the same directories.
MechanismCache the vnodes for remote directory names on the client; flush the cache when attributes returned by an NFS reply do not match the cached vnode's attributes.
Trade-offRepeated path prefixes cost no RPCs, in exchange for resolving through stale entries until some reply reveals a change.

  • "The directory cache is flushed when the attributes returned in a NFS request do not match the attributes of the cached vnode."
  • This is the "cache of directory vnodes" that M12 names as the remedy for one-component lookups.
  • Last improvement in Figure 3: about 300 → about 293 (read-off).
  • Not stated: whether names that do not exist are cached (negative entries), how big the cache is, or how entries are replaced.

  • A1. Directory names change rarely (implicit).
  • A2. Changes show up in attributes returned by some later reply (stated as the flush rule).
  • A3. Changing a directory's contents changes its attributes (implicit; for example its modify time).
  • A4. Programs reuse path prefixes heavily (stated: "many files with the same initial path").

  • A2 changes (all accesses hit the cache, so no reply ever carries fresh attributes for the cached vnode): the flush rule never fires; only attribute-cache expiry (M14) eventually forces an RPC that can reveal the change (inference).
  • A3 changes (a server whose directory attributes do not change on modification): the flush rule detects nothing (inference).
  • A4 changes (paths rarely shared): the cache rarely hits and M12's per-component cost returns (inference).

Leases: name-to-file bindings are part of what a lease must cover for repeated opens; renaming is a write to that binding. Here the binding is cached with no such rule.

M16 · Fewer, bigger requests and fewer copies: 8 KB UDP and XDR into mbufs

TL;DR
ProblemEven with a client cache, large files caused too many requests, and the kernel spent much of its time copying bytes.
MechanismRaise the maximum UDP packet from 2048 to 9000 bytes so one 8 KB request is one datagram that IP fragments and reassembles; encode and decode XDR directly into and out of mbuf chains, cutting three copies per side to two.
Trade-off"a big win in terms of raw throughput" and less CPU per byte, in exchange for whole-datagram loss when any fragment is lost.
Breaks whenThe network drops fragments, or routers cannot reassemble large datagrams.
Key points
  • "We were able to decrease the number of requests by changing the maximum UDP packet size from 2048 bytes to 9000 bytes (8k requests plus some overhead). This allows the NFS to send one large request and let the IP layer fragment and reassemble the packet. With a little work on the IP fragmentation code this turns out to be a big win in terms of raw throughput."
  • "A gprof of the kernel, both client and server sides, showed that bcopy was a big consumer because the NFS and RPC kernel code caused three bcopys on each side. We managed to trim that down to two copies on each side by doing XDR translation directly into, and out of, mbuf chains."
  • Figure 3 groups the larger UDP packet with the buffer cache as its first step (about 570 → 400); the bcopy step is about 400 → 365 (read-off).
  • The paper does not list which three copies there were.
How it works, step by step
  1. Before. An 8 KB block over datagrams of at most 2048 bytes, including RPC and NFS headers, needs at least 5 requests if each carries at most about 2000 data bytes, or 4 if it carries exactly 2 KB (8192 / 2048 = 4; the exact per-packet payload is not given). Each is a separate RPC with its own round trip.
  2. After. One 8 KB request in a 9000-byte UDP datagram. On 10 Mbit Ethernet with a 1500-byte maximum frame (general knowledge, not in the paper), IP carries at most 1480 data bytes per fragment, so the datagram (9000 + 8-byte UDP header = 9008 bytes) travels as ⌈9008 / 1480⌉ = 7 fragments, reassembled by IP on the far side (computed).
  3. The loss cost (inference). If any one fragment is lost the whole datagram is lost and the whole 8 KB request is retransmitted after a timeout. With independent fragment loss p, a 7-fragment datagram survives with probability (1 − p)7: 93.2% at p = 1%, 69.8% at p = 5% (computed).
  4. Copies. One plausible accounting of three copies per side (inference): user buffer ↔ buffer cache, buffer cache ↔ an XDR staging buffer, staging buffer ↔ mbufs. Encoding XDR straight into mbufs removes the staging copy, leaving two.
Assumptions it relies on
  • A1. Fragment loss on the local Ethernet is rare (implicit).
  • A2. Per-request overhead (round trip, RPC processing) dominates per-byte cost, so fewer bigger requests win (implicit).
  • A3. Both ends can fragment and reassemble 9000-byte datagrams efficiently (stated: needed "a little work").
  • A4. CPU time spent copying is a real bottleneck (stated by the gprof result).
If an assumption changes
  • A1 changes (lossy or congested network): the survival probability above falls fast and each loss costs a full 8 KB plus a timeout; smaller requests or a transport with per-segment retransmission become better (inference).
  • A2 changes (bandwidth-bound link): fewer requests save little; bytes dominate (inference).
  • A3 changes (a router between client and server that drops or cannot reassemble fragments): 8 KB requests fail entirely (inference).
  • A4 changes (a much faster CPU): the copy reduction matters less; the paper's future work says "the server CPU speed is the bottleneck", so in 1985 it mattered a lot.
Design notes and rejected alternatives

Implementing NFS-level fragmentation would add protocol state; letting IP do it keeps NFS one-request-one-datagram. The copy fix is an implementation change with no protocol effect.

Connections

Livelock: each 8 KB request now arrives as 7 receive interrupts, so a busy server's interrupt-level work per request grows (inference). M1: the null RPC tuning to 8.8 ms included "several speed ups to the UDP and IP code".

M17 · Server read-ahead, fill-on-demand clustering, and the 410/413 trick

TL;DR
ProblemMost reads were page-ins of executables, which arrive as many small requests and get nothing from sequential read-ahead.
MechanismRead-ahead in the server; cluster many small page-in requests into one large one; load small demand-paged (413) programs whole, as if they were 410 programs.
Trade-offFaster program start on both local and remote filesystems, in exchange for reading pages a small program might never touch.
Breaks whenSmall programs touch few of their pages, or memory is tight.
Key points
  • "To make sequential read faster we added read-ahead in the server. This helped somewhat but it was noted that most of the read requests being done were in demand-loading executables, and these were not benefiting from read-ahead."
  • "First, fill-on-demand clustering is used to group many small page-in requests into one large one."
  • "We treat 413 (paged in) programs as 410 (swapped in) if they are smaller than a fixed threshold size. This speeds up both the local and remote filesystems because loading a small program happens all at once, which allows read-ahead." The threshold value is not given.
  • Justification: "it can be thought of as a better initial estimate of the working set of small programs, since small programs are more likely to use all of their pages than none of them."
  • General knowledge, not in the paper: 0410 and 0413 are a.out "magic numbers"; 0413 files are demand paged from the file, 0410 files are read in at exec time.
  • Figure 3 step: about 315 → 300 (read-off).
How it works, step by step
  1. A 48 KB program, demand paged (illustrative). With 2 KB pages (general knowledge for the Sun-2; not in the paper), touching all of it means 24 page faults, each a small read; with 8 KB clustering, 6 reads.
  2. The same program treated as 410. At exec the kernel reads the whole 48 KB sequentially: 6 reads of 8 KB, and after the first, server and client read-ahead overlap the rest with execution.
  3. A large program above the threshold keeps demand paging, so a program that touches 10% of a large image does not pay for the other 90%.
Assumptions it relies on
  • A1. Small programs touch nearly all their pages before exiting (stated).
  • A2. Large programs do not, so they keep demand paging (implicit in the threshold).
  • A3. Sequential whole-file reads get read-ahead benefits (stated).
  • A4. There is enough memory to load a small program whole without hurting others (implicit).
If an assumption changes
  • A1 changes (small programs that exit early, for example on a usage error): they read pages they never use; the cost is bounded by the threshold size (inference).
  • A2 changes (large programs that touch everything): they still page in piecemeal, though clustering helps (inference).
  • A3 changes: no read-ahead benefit means the trick only saves request count (inference).
  • A4 changes (memory-poor diskless clients): eager loading pushes other pages out, which over NFS or ND must be re-read (inference).
Design notes and rejected alternatives

The authors anticipate the objection: "This may sound like a hack". Read-ahead alone was tried first and helped "somewhat". Both tricks change the virtual memory system, not NFS, and also speed up local disks, which is why the Eagle line in Figure 3 falls too.

Connections

Superpages: the same bet as eager promotion: if a region is likely to be used whole, fetch or map it whole up front; reservation-based schemes wait for evidence, as demand paging does here.

M18 · Credentials: UNIX authentication on every call, root to nobody, the set-uid retry

TL;DR
ProblemThe server must check UNIX permissions for users it has never seen log in, and a client's super-user should not own the server's files.
MechanismEvery RPC header carries uid, gid and groups; the server checks as if the caller were local; uid 0 is mapped to nobody (uid −2); on the client, a call that fails with EACCES for a set-uid root program is retried with the real uid.
Trade-offUNIX permission semantics with no server login state, in exchange for a flat uid space across the network, odd behavior for root, and security that trusts every client kernel.
Breaks whenuid maps differ between machines, or a client lies about uids.
Key points
  • "RPC allows different authentication parameters to be 'plugged-in' to the packet header of each call so we were able to make the NFS use a UNIX flavor authenticator to pass uid, gid, and groups on each call. The server uses the authentication parameters to do permission checking as if the user making the call were doing the operation locally."
  • "The mapping from uid and gid to user must be the same on the server and client. This implies a flat uid, gid space over a whole local network." Yellow Pages, "a simple, replicated database lookup service", holds /etc/passwd and /etc/group to make that manageable.
  • "the server maps user root (uid 0) to user nobody (uid -2) before checking access permission." Side effect: "root may have fewer access rights to a file than a normal user."
  • Set-uid root programs such as lpr that need user files: "we check on the client side for RPC calls that fail with EACCES and retry the call with the real-uid instead of the effective-uid. This is only done when the effective-uid is zero and the real-uid is something other than zero so normal users are not affected."
  • Remaining hole: "the super-user on a client machine can still gain access by using su to change her effective-uid to the uid of the owner of a remote file."
  • Future work: programs "can be written that impersonate a server", clients can impersonate other clients; plan: "a better authentication scheme that uses public key encryption".
How it works, step by step
# client side
r = rpc(call, cred = (euid, egid, groups))
if r == EACCES and euid == 0 and ruid != 0:
    r = rpc(call, cred = (ruid, ...))       # the set-uid retry
# server side
if cred.uid == 0: cred.uid = -2             # root -> nobody
check permissions as cred; execute
Assumptions it relies on
  • A1. Client kernels report uids honestly; the network is not hostile (implicit; the paper later lists impersonation as a problem).
  • A2. uids and gids mean the same user everywhere (stated).
  • A3. A client's super-user should not be trusted as root on the server (stated as policy).
  • A4. What a set-uid root program needs from a user's files is what that user can access (implicit in the retry rule).
If an assumption changes
  • A1 changes (a malicious client or forged packets): the attacker simply sends uid 1001 instead of 0; the root mapping does not help, as the su remark already shows (inference). Only real authentication (the public-key plan) fixes this.
  • A2 changes (each machine has its own passwd file): uid 1001 is alice on one machine and bob on another; files appear owned by the wrong people and permission checks are wrong (paper).
  • A3 changes (trusted root, no mapping): client root acts as server root; any compromised client owns every exported file (inference).
  • A4 changes (a set-uid root program that needs its own privilege on the server, for example writing a root-owned spool directory over NFS): it runs as nobody and fails; the retry with the user's uid fails too, or succeeds in a place the user could write anyway (inference).
Design notes and rejected alternatives

UNIX-style checking on both client and server was chosen "so that UNIX users would see very little difference between remote and local files". A flat uid space is called "not acceptable in the long run". The nobody mapping is described as solving the problem "but, unfortunately" with strange behavior for root.

Connections

M19 is the other half: when the check runs. M8's exports list is per host; M18's check is per user.

M19 · Permission checked on every call, and credentials saved at open

TL;DR
ProblemUNIX checks permission once, at open; a stateless NFS server checks on every call, so a change after open can break an already-open file.
MechanismSave the client credentials in the file table at open time and send those, not the current ones, on later requests for that open file.
Trade-offOpen files keep working across the opener's own credential changes, with no server state, in exchange for a fix that covers only what saved credentials can cover.
Breaks whenThe server's check against the file's current mode still denies the saved credentials.
Key points
  • "In the local case the access permission is only checked when the file is opened, but in the remote case permission is checked on every NFS call."
  • "This means that if a client program opens a file, then changes the permission bits so that it no longer has read permission, a subsequent read request will fail. To get around this problem we save the client credentials in the file table at open time, and use them in later file access requests."
  • Unresolved in the paper: saved credentials alone do not explain the paper's own example: the server still checks the file's current mode bits, and the owner's saved uid is denied by a mode that forbids the owner. General knowledge, not in the paper: Sun's server let a file's owner read and write the file regardless of mode bits, and treated execute permission as read permission for reads (because demand loading reads executables). With that server rule, the saved owner credentials make the example work.
  • What saved credentials do cover directly (inference): a process that opens a file and then changes its own uid (for example a set-uid program dropping privilege) keeps using the open file with the credentials it opened with, as UNIX would.
How it works, step by step
  1. open. Process (uid 1001) opens notes (owner 1001, mode 644). The file table entry stores {vnode, offset, flags, cred = uid 1001, gids}.
  2. chmod 000. The process removes all permissions. Locally, reads through the open descriptor still work.
  3. read. The client sends read(fh, off, 8192) with the saved credentials (uid 1001). The server checks against mode 000: a plain UNIX check denies; the owner rule (general knowledge above) allows.
  4. setuid case. A process opens a file as uid 0, then calls setuid(1001). Later reads carry the saved uid 0 (mapped to nobody, M18), not 1001 (inference about how the two rules combine).
Assumptions it relies on
  • A1. UNIX open-time permission semantics should hold for the life of an open (stated goal).
  • A2. The file table is a per-open place where the client can keep this state (implicit).
  • A3. The server's per-call check can be satisfied by the saved credentials (implicit; see the unresolved point).
  • A4. Permission changes come from the same client (implicit; another client's chmod is outside any client fix).
If an assumption changes
  • A1 changes (per-call checking is acceptable): no saved credentials needed; programs that open then chmod break (paper).
  • A2 changes: no change; this is client-local state that dies harmlessly with the client (inference).
  • A3 changes (server has no owner exception): the paper's example still fails after the fix (inference, see above).
  • A4 changes (another client changes the mode or owner): this client's next call fails; there is no way to preserve open-time semantics across clients without server state, the same limit as M20 (inference from the paper's general remark).
Design notes and rejected alternatives

Server-side open-time checks would need the server to know about opens (state). The fix is entirely in the client's file table.

Connections

Same pattern as M20: client-local state patches a UNIX semantic that the stateless server cannot provide, and the patch covers one client only.

M20 · Removing an open file: rename instead (the 3/4 solution)

TL;DR
ProblemUNIX lets a process remove a file it has open and keep using it; csh and sendmail rely on this for temporary files; the stateless server does not know the file is open.
MechanismThe client's remove checks whether the file is open; if so it renames the file to a new name instead, and removes that name when the vnode becomes inactive.
Trade-offCommon programs work with no server or protocol change, in exchange for garbage files after client crashes and no protection against other clients.
Breaks whenThe client crashes between the rename and the remove, or another client removes the file.
Key points
  • "We tried very hard to make the NFS client obey UNIX filesystem semantics without modifying the server or the protocol."
  • Open-file removal is "a disgusting bit of UNIX trivia and at first we were just not going to support it, but it turns out that all of the programs that we didn't want to have to fix (csh, sendmail, etc.) use this for temporary files."
  • "What we did to make open file removal work on remote files was check in the client VFS remove operation if the file is open, and if so rename it instead of removing it. This makes it (sort of) invisible to the client and still allows reading and writing. The client kernel then removes the new name when the vnode becomes inactive."
  • "We call this the 3/4 solution because if the client crashes between the rename and remove a garbage file is left on the server. An entry to cron can be added to clean up on the server."
  • Across clients: "if one client opens a file and another client removes that file, the first client's read request will fail even though the file is still open."
  • General knowledge, not in the paper: the hidden name is of the form .nfsXXXX in the same directory.
How it works, step by step
nfs_remove(dvp, name):
    vp = lookup(dvp, name)
    if vp is open on this client:             # references beyond this lookup
        tmp = unique hidden name
        rpc rename(dvp.fh, name, dvp.fh, tmp)
        vp.removed_as = (dvp, tmp)
    else:
        rpc remove(dvp.fh, name)

nfs_inactive(vp):                           # last reference released
    if vp.removed_as: rpc remove(vp.removed_as)
Assumptions it relies on
  • A1. Every process using the file is on the same client (stated limitation).
  • A2. Clients rarely crash between the rename and the final remove (stated as the reason for the name "3/4 solution").
  • A3. The hidden name does not collide and nobody minds seeing it (implicit).
  • A4. rename within one directory is atomic at the server and keeps the inode (implicit).
If an assumption changes
  • A1 changes (the file is open on another client): that client is unknown to the remover's kernel, so the remover sends a real remove; the server frees the inode and the other client's next read fails (paper).
  • A2 changes (frequent crashes): hidden files accumulate until cron removes them; a cron job that removes a hidden file still in use by a live client breaks that client (inference).
  • A3 changes: ls -a shows the hidden files; removing the containing directory fails with "not empty" while the file is still open (inference).
  • A4 changes (rename that changes the inode, or a cross-directory rename that fails): the client's handle would go stale and reads would fail (inference).
Design notes and rejected alternatives

Not supporting it at all was the first plan. Doing it exactly needs the server to count opens, which is state. The paper picks a client-only solution and names its gap.

Connections

Worse is better: a named, deliberately incomplete solution chosen for simplicity. M19 is the same pattern for permissions.

M21 · No file locking, and intermixed concurrent writes

TL;DR
ProblemApplications want locks, and UNIX keeps one write from intermixing with another; both need the server to hold something between requests.
MechanismNone in NFS: remote file locking is purposely left out, to be provided by separate RPC-based lock services built on the Sun status monitor.
Trade-offThe protocol stays stateless and imposes no locking style, in exchange for no locks and possible intermixing on long writes.
Breaks whenTwo clients write the same file at the same time.
Key points
  • "The NFS does not support remote file locking. We purposely did not include this as part of the protocol because we could not find a set of locking facilities that everyone agrees is correct. Instead we plan to build separate, RPC based file locking facilities."
  • "In the local filesystem, file modifications are locked at the inode level. This prevents two processes writing to the same file from intermixing data on a single write. Since the server maintains no locks between requests, and a write may span several RPC requests, two clients writing to the same remote file may get intermixed data on long writes."
  • Future work: "Since file locking is inherently stateful (the server maintains the lock information) it will be built using the Sun status monitor service."
  • Two more splitting points (inference): the client cache sends data in 8 KB blocks, so even a short write that straddles a block boundary becomes two RPCs; and when the data is sent is decided by write-behind and flush on close (M13), not by the write() call.
How it works, step by step
Assumptions it relies on
  • A1. Concurrent write-sharing between clients is rare (implicit).
  • A2. There is no locking facility everyone agrees on (stated).
  • A3. A write longer than one request is split into several RPCs (stated).
  • A4. The server applies each single RPC atomically (implicit; it goes through the local filesystem, which locks the inode for that call).
If an assumption changes
  • A1 changes (shared databases, shared logs): applications must coordinate themselves; without that, data intermixes and appends from two clients can overwrite each other, because each client computes the offset from its own idea of the file size (M14) (inference).
  • A2 changes (one locking style is agreed): it would still need lock state on the server, so it would still belong in a separate stateful service with crash recovery, as the paper plans (inference).
  • A3 changes (all writes at most 8 KB and block aligned): one write() is one RPC, so single writes no longer intermix, but sequences of writes still can (inference).
  • A4 changes (a server crash in the middle of one RPC): the client retries the whole request, which rewrites the whole block (idempotent), so partial RPCs are repaired (inference).
  • A separate lock service is added: NFS itself is unchanged by it. The lock service's state and the NFS client's caches are separate mechanisms; which data a client reads and when its writes reach the server are still governed by M13 and M14 (inference).
Design notes and rejected alternatives

Locks in the NFS protocol would make the NFS server stateful and impose one locking semantics. A separate service lets "people use the locking facility with the flavor of their choice with minimal effort" and confines crash recovery (via the status monitor) to that service.

Connections

Eraser: intermixed writes are a write-write race on file blocks with no lock held; a lockset checker needs lock acquire and release events, and the NFS protocol carries none. Mesa monitors: the local inode lock makes one write a monitor-protected operation; the NFS server's protection ends at a single RPC. Leases: a lease is a time-limited right over writes to a datum, a form of server state that recovers by expiring, unlike the lock service's status-monitor recovery.

M22 · Time skew

TL;DR
ProblemFile times come from the server's clock, but programs compare them with the client's clock.
MechanismNone in NFS: the three affected programs found (ranlib, ls, emacs) were fixed; a time synchronization protocol is planned.
Trade-offNo clock dependence in the protocol, in exchange for wrong answers in programs that mix the two clocks.
Breaks whenClocks differ by more than the time scale a program cares about.
Key points
  • "Time skew between two clients or a client and a server can cause time associated with a file to be inconsistent."
  • "ranlib saves the current time in a library entry, and ld checks the modify time of the library against the time saved in the library. When ranlib is run on a remote file the modify time comes from the server while the current time that gets saved in the library comes from the client. If the server's time is far ahead of the client's it looks to ld like the library is out of date."
  • "There were only three programs that we found that were affected by this, ranlib, ls and emacs, so we fixed them." "This is a potential problem for any program that compares system time to file modification time." Plan: limit skew "with a time synchronization protocol".
How it works, step by step
  1. Who sets which time. On a write the server sets the modify time from its own clock (paper). setattr can also set access and modify times explicitly (M2), so a client that sets times passes its own clock's values (inference).
  2. Direction matters (inference). Server ahead: false "out of date". Client ahead: the stored time is later than the modify time, so the library looks fresh even if it was really changed within the skew after ranlib ran.
  3. ls and emacs (general knowledge, not in the paper): ls -l chooses its date format by comparing file times with now; emacs checks whether a file changed on disk since it was visited.
Assumptions it relies on
  • A1. Clock skew between machines is small for most purposes (implicit).
  • A2. Few programs compare file times with the current time (stated: three found).
  • A3. NFS's own operation never compares clocks across machines (implicit; attribute timeouts are local intervals).
If an assumption changes
  • A1 changes (large skew): make, ld and backup tools that compare times misbehave (inference); a time sync protocol (the plan) fixes it.
  • A2 changes (many such programs): fixing each one stops scaling; clock synchronization becomes required (inference).
  • A3 changes (a protocol whose correctness uses clocks, as leases do): skew becomes a correctness problem rather than an application nuisance; the Leases paper bounds it with an allowance ε in the effective term.
Design notes and rejected alternatives

Using the client's clock for modify times would make times inconsistent between clients instead; the server clock is at least one clock per file (inference).

Connections

Leases: in NFS skew breaks a few programs; in leases a fast server clock or a slow client clock can break consistency itself, while the opposite errors only add traffic.

M23 · Hard and soft mounts

TL;DR
ProblemWhen a server is down, the client must either wait (the stateless retry) or give up.
MechanismA mount option: hard mounts retry NFS calls forever; soft mounts give up after a while and return an error.
Trade-offHard: no data lost, processes hang. Soft: no hangs, but errors that most programs do not check.
Breaks whenHard: the server never comes back. Soft: a program ignores the error, especially on a write.
Key points
  • "A hard mounted filesystem will retry NFS calls forever if the server goes down, while a soft mount gives up after a while and returns an error."
  • "The problem with soft mounts is that most UNIX programs are not very good about checking return status from system calls so you can get some strange behavior when servers go down."
  • "A hard mounted filesystem, on the other hand, will never fail due to a server crash; it may cause processes to hang for a while, but data will not be lost."
  • The retry count and timeouts are not given (general knowledge: configurable, with growing timeouts between retries).
How it works, step by step
  1. Hard mount, server rebooting for 2 minutes (illustrative). A process doing read waits about 2 minutes, then gets its data. Nothing else changes (M3).
  2. Soft mount, same outage. After its retries the call returns an error (general knowledge: ETIMEDOUT). A program like cat may print an error; one that ignores read errors processes a short or empty file as if it were complete.
  3. Soft mount and delayed writes (inference). A write() often returns after only copying into the client cache (M13). If the later write RPC times out, the error can surface only at a later call or at close, which many programs do not check, so data is lost silently.
Assumptions it relies on
  • A1. Servers come back (implicit).
  • A2. Users prefer a hang to lost data for important filesystems (implicit in the recommendation).
  • A3. Programs check errors (violated; stated).
  • A4. The client cannot tell a dead server from a slow one (stated, M3).
If an assumption changes
  • A1 changes (a server is permanently gone): hard-mounted processes hang until an administrator intervenes (inference; general knowledge: an "interruptible" option was later added).
  • A2 changes (availability more important, such as optional tool directories): soft mounts are reasonable for read-mostly filesystems (inference).
  • A3 changes (programs that check every error): soft mounts become safe to use broadly (inference from the paper's stated problem).
  • A4 changes (the client can detect a crash, for example from a server boot counter): it could fail fast; but with a stateless server there is nothing a client must do after a crash, so the information buys little (inference).
Design notes and rejected alternatives

Both flavors exist because neither is right for every filesystem. The options string in the extended mount command carries the choice.

Connections

Leases: leases make an unreachable client cost other clients at most one term of write delay; an NFS client on a hard mount waits an unbounded time for an unreachable server. Different parties wait, for different reasons.

C · Connections to the other CS240 papers (mechanical only)

  • Leases: soft state versus no state; attribute-cache timeouts versus lease terms (a client-only timer versus a server promise); both rely on stable server writes for crash safety. Table S above.
  • Eraser: intermixed writes are a write-write race on file blocks; the protocol carries no lock events, and client cache hits never reach the server, so a server-side observer sees only a subset of accesses and no synchronization (M13, M21).
  • Mesa monitors: the local inode lock is a monitor around one write; NFS's protection ends at one RPC; the vnode layer has no locks, so direnter does its own directory locking during rename (M11, M21).
  • Threads vs events, cooperative task management: synchronous RPC needs one blocked context per outstanding call; nfsd and the block I/O daemons are a hand-built thread pool standing in for kernel light-weight processes (M1, M7).
  • Receive livelock: an overloaded UDP server drops requests at the socket, and clients retransmit; 8 KB requests arrive as 7 fragments each. Both raise interrupt-level input load as service falls behind (inference; M7, M16).
  • Superpages: the 410/413 trick bets that a small region will be used in full and fetches it eagerly, the same bet as eager promotion versus reservation-based promotion (M17).
  • Worse is better: the 3/4 solution, root mapped to nobody, fixed timeouts and "we fixed them" for time skew are deliberate simplicity over complete semantics, stated openly (M20, M22).

Worked examples

Six calculations from the paper's own numbers. Read-off graph values are approximate.

① How much disk does a diskless workstation see?

The paper's df listing: two ND partitions (7445 and 5691 KB) and six NFS mounts (27487, 345915, 148371, 7429, 301719, 327599 KB).

  1. ND (private, block level): 7445 + 5691 = 13,136 KB, about 12.8 MB.
  2. NFS (shared, file level): 27487 + 345915 + 148371 + 7429 + 301719 + 327599 = 1,158,520 KB.
  3. Total: 1,171,656 KB ≈ 1.12 GB (1024-based), so "more than a Gigabyte" holds. NFS supplies 1,158,520 / 1,171,656 ≈ 98.9% of it.
  4. Reserve check: on /, used + avail = 5788 + 912 = 6700 = 90% of 7445; the same 90% holds on /usr/src (220122 + 91201 = 311323 ≈ 0.9 × 345915). The 4.2 filesystem holds back 10% (general knowledge).
🍯
The tiny ND root is exactly the part NFS could not share (M10); everything users actually work in comes over NFS.

② What did the attribute cache remove?

Before: getattr was 90% of all calls, and one stat caused 11 RPCs, 7 of them getattr on the same file. After: getattr about 10% of calls.

  1. Assume (inference) the non-getattr calls are unchanged. Before: 100 calls = 90 getattr + 10 other.
  2. After: the 10 other calls are 90% of the new total, so total = 10 / 0.9 ≈ 11.1; getattr ≈ 11.1 − 10 = 1.1.
  3. Result: getattr calls fell by about (90 − 1.1) / 90 ≈ 99%; total calls fell by about 89%.
  4. The stat example: 7 getattrs on one file within one system call; with a 3 s window, at most the first can miss, so at least 6 of the 11 RPCs disappear (inference about which).
💡
Figure 3 shows this step as about 365 → 315, a 14% cut in total benchmark time: the call count fell far more than the time, because the remaining calls (reads, writes, lookups) cost more each.

③ What does one request cost?

Null RPC: 8.8 ms round trip. Raw transfer: 120 KB/s read, 40 KB/s write. Requests carry 8 KB.

  1. Read: 8192 / (120 × 1024) = 66.7 ms per 8 KB read request, about 7.6 null round trips.
  2. Write: 8192 / (40 × 1024) = 200 ms per 8 KB write request, 3 times a read.
  3. Why writes cost 3× (inference): the server writes the data block plus the inode, and an indirect block when it changes, before replying (M6); a read needs at most one disk read and can be prefetched.
  4. A 1 MB copy to an NFS file at 40 KB/s takes about 25.6 s; reading it takes about 8.5 s (computed).
⚠
Writes are "about 5% of all calls", so normal work barely notices; a large remote write is exactly the case the paper says you will notice.

④ Figure 3, step by step

Read-off totals: 570, 400, 365, 315, 300, 293, 290; ND about 300; Eagle about 268 → 232.

  1. Buffer cache + large UDP: −170 (−30%), the biggest single step: most read and write RPCs vanish.
  2. bcopy: −35 (−9%). Attribute cache: −50 (−14%). 410/413: −15 (−5%). Directory cache: −7 (−2%). FCS: −3 (−1%).
  3. Overall: 570 → 290 is −49%; NFS goes from 1.9× ND to 0.97× ND, and from 2.1× Eagle to 1.25× Eagle.
  4. Diminishing returns: each later step removes a smaller slice because the earlier ones already removed the common case it would have sped up (inference).

⑤ Where did release 2.0 still lose?

Figure 4 read-off (NFS, SCSI, Eagle): make 23, 13, 15 · f77cmp 28.5, 20.5, 16.5 · smcmp 11.5, 8.5, 6.5 · matrix 25, 24, 23.5.

  1. make: 23 / 13 ≈ 1.8× SCSI, 23 / 15 ≈ 1.5× Eagle. One getattr RPC per file stat'ed; locally the directory's inodes are in memory.
  2. Compiles: f77cmp 1.73× Eagle, smcmp 1.77× Eagle: many header lookups and object-file writes, the latter synchronous on the server (inference).
  3. matrix: 25 / 23.5 ≈ 1.06×: almost no file I/O, so almost no NFS cost.
  4. Totals: NFS 174.5 vs Eagle 134 → about 1.30× overall.

⑥ What does an 8 KB datagram risk?

The maximum UDP packet went from 2048 to 9000 bytes; Ethernet frames carry at most 1500 bytes (general knowledge).

  1. Fragments: 9000 data bytes + 8-byte UDP header = 9008 bytes; at 1480 IP payload bytes per fragment, ⌈9008 / 1480⌉ = 7 fragments.
  2. Loss amplification: losing any one loses the datagram. With independent fragment loss p, success = (1 − p)7: 93.2% at p = 1%, 69.8% at p = 5%.
  3. Cost of a loss: a timeout plus resending all 8 KB, not just the missing 1480 bytes (inference).
💡
On a quiet LAN p is tiny, so the paper's "big win" holds. The same choice is a liability on a lossy or routed network.

The client times out and resends the identical request. The server has no record of the first one, so it performs the write again: same bytes, same offset, committed again, same resulting file. It replies; the client's call returns once. The file is correct because write at an explicit offset is idempotent.Misconception: that the server recognizes the retry. It cannot; it keeps no memory of past requests. Correctness comes from idempotence, not detection.

Problem 3 · medium
Client A stats log at t = 0 s (size 10000). Client B appends 5000 bytes and closes at t = 1.0 s. A calls stat at 2.5 s, does a read RPC on the file at 2.8 s, and calls stat at 3.5 s. What size does each A stat report?
Show answer
At 2.5 s: 10000, from the cache (entry from 0 s, still inside 3 s). The read reply at 2.8 s carries the file's attributes, and "the cache is updated every time new attributes arrive", so the entry becomes size 15000 at 2.8 s. At 3.5 s: 15000, from the cache (0.7 s old).Misconception: that only the 3 s timeout refreshes attributes. Any reply that carries attributes (lookup, read, write, setattr, getattr) refreshes them.
Problem 4 · medium
fiat:/usr/src is mounted on /usr/src, and (unlike the paper's df listing) /usr is a local filesystem on this client. With all caches cold, how many RPCs does cat /usr/src/sys/nfs/x.c (20,000 bytes) cost? How many if the directory name cache already holds sys and nfs?
Show answer
Cold: lookups for sys, nfs, x.c = 3 (the root handle came from MOUNT; usr and src are resolved locally and namei then crosses into the mount). Reads at offsets 0, 8192 and 16384 (the last returns 3616 bytes) = 3. Total 6. Warm directory cache: 1 lookup + 3 reads = 4. No close RPC is needed for a file only read.Misconception: that a path costs one RPC. NFS lookup takes one name, by design, so the server never needs the client's mount table.
Problem 5 · medium
A server keeps generation numbers only in memory, starting at 0 at every boot. Before a reboot, file x.c (inode 117, gen 0) is removed and y.c reuses inode 117 (gen 1). A client still holds x.c's handle (117, gen 0). The server reboots. What happens to that handle, and to handles for y.c?
Show answer
After the reboot inode 117's generation is 0 again, so the old x.c handle (gen 0) now matches and silently reads or overwrites y.c. Handles for y.c issued before the reboot carry gen 1 and are now rejected as stale even though y.c still exists. Both failures come from the generation number not being persistent; the paper's design requires it in the inode on disk.Misconception: that the generation number only needs to be unique while the server runs. Handles outlive server reboots, so everything in them must be on disk.
Problem 6 · hard
Suppose a server replied to write RPCs as soon as the data was in its buffer cache and flushed 5 seconds later. A hard-mounted client writes 24 KB and closes; the server crashes 2 s after the last reply. What does the application see, and why is this worse than a local crash?
Show answer
The application sees nothing: every write and the close succeeded. After the reboot the file lacks some or all of those 24 KB, and no error is ever reported, because the client discarded the data when the replies arrived and has nothing to resend. A local crash also loses delayed writes, but then the application and its machine crash together; here the client keeps running, believing its data is safe, and may act on it (delete the source, tell a user). This is why "unwritten blocks in the server's buffer cache are part of the 'client's state'".Misconception: that retry-until-reply protects all data. It protects only requests not yet answered; commit-before-reply protects the answered ones.
Problem 7 · hard
The server's clock is 5 minutes behind the client's. ranlib runs on the client at 10:00 (client time). At 10:02 (client time) someone appends a new object to the library without rerunning ranlib. Does ld notice that the table of contents is out of date?
Show answer
ranlib stores 10:00 in the library; the server stamps the modify time 9:55. The later append is stamped about 9:57 by the server. ld compares 9:57 with 10:00, sees the library as older than its table of contents, and does not complain, even though it really is out of date. The paper's example (server ahead) gives a false alarm; the reverse skew hides a real change.Misconception: that skew only causes spurious warnings. The direction of the skew decides whether you get false positives or missed changes.
Problem 8 · medium
Client A has /shared/t open. A process on client B runs rm /shared/t. Why doesn't the 3/4 solution protect A, and what does A see?
Show answer
The rename-instead-of-remove check runs in the remover's own kernel, which only knows about opens on that client. B's kernel sees no open, sends a real remove, the server frees the inode (incrementing its generation), and A's next read with its old handle fails, "even though the file is still open". Making this work needs the server to know A has the file open, which is state.Misconception: that the 3/4 solution is a server feature. It is purely client-side, so it protects only against removals from the same client.
Problem 9 · medium
Server panic has separate filesystems at /usr and /usr/panic. A client mounts only panic:/usr on /usr and lists /usr/panic. What does it see, and why does the server behave this way?
Show answer
It sees the directory /usr/panic as it exists inside the /usr filesystem: the mount-point directory underneath, usually empty, not the other filesystem's contents. Servers "do not cross mount points on remote lookup requests" to avoid loop detection and dynamic access checking against /etc/exports. The client must also mount panic:/usr/panic, as the paper's df listing does.Misconception: that exporting /usr exports everything below it. Exports and lookups stop at filesystem boundaries.
Problem 10 · hard
mv a b on an NFS client sends rename(d, "a", d, "b"). The server performs it but the reply is lost. Before the retry arrives, another process on another client creates a new file a in d. What does the retry do?
Show answer
The retry is executed as a fresh request: it renames the new a over b, destroying the file the first rename had just put there, and reports success. Without the other client the retry would merely fail with "no such file". rename is not idempotent because its first execution changes its own precondition; the paper does not discuss this (inference from the procedure definition).Misconception: that all NFS procedures are safe to retry because the paper says requests are idempotent. That holds for reads, writes, lookups and attribute calls, not for the directory-changing ones.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is "stateless" about the NFS server?▾
It keeps no information about clients or past requests: no open-file table, no file offsets, no locks, no list of who caches what. It does keep the filesystem itself (on disk) and a buffer cache for reads; neither needs recovery. Every request carries a file handle, offsets and credentials, so it can be served after a reboot exactly as before.
Q2If there is no open or close in the protocol, what does close do on the client?▾
It flushes the file's dirty cached blocks to the server as write RPCs ("files are flushed on close"). It also releases the vnode reference, which for a file removed while open triggers the deferred remove of its hidden name.
Q3How long can a client see stale data?▾
For attributes: up to 3 s for files and 30 s for directories after they were fetched, unless a reply refreshes them sooner. For data blocks the paper gives no rule beyond flush on close; general knowledge, not in the paper: Sun's client discarded cached blocks when fresh attributes showed a new modify time, so data staleness follows attribute staleness.
Q4Why does lookup take one name instead of a whole path?▾
Any component might be a mount point on the client, and that information lives above the vnode layer. A whole-path lookup would force the server to know every client's mounts, "and this would violate server statelessness". A client cache of directory vnodes recovers most of the cost.
Q5Why are writes so slow?▾
The server must put the data block, any modified indirect block and the inode on disk before replying, because once the client gets the reply it forgets the data. Raw write speed was 40 KB/s against 120 KB/s for reads.
Q6What is the generation number for?▾
To detect a handle for a file that was removed and whose inode was reused. The inode's generation number is incremented each time the inode is freed; a handle carrying an older number is rejected instead of reaching the new file.
Q7Are all NFS requests idempotent?▾
The paper says so, and it is true for null, lookup, getattr, setattr, read, write, readlink, readdir and statfs. It is not true for remove, rmdir, rename, link, symlink and mkdir, whose retry after a lost reply fails or acts on a different object; create depends on the server. The paper does not discuss these cases.
Q8Why isn't locking part of NFS?▾
The authors "could not find a set of locking facilities that everyone agrees is correct", and locking is "inherently stateful". It was planned as a separate RPC service using the Sun status monitor for crash recovery, so NFS itself stays stateless.
Q9Why does root get fewer rights than an ordinary user?▾
The server maps uid 0 to nobody (uid −2) before checking permissions, so a client's super-user does not own the server's files. Files readable only by their owner become unreadable to root. Set-uid root programs get a client-side retry with the real uid after EACCES.
Q10Hard or soft mount?▾
Hard: retry forever; processes hang while the server is down, but "data will not be lost". Soft: give up and return an error, which most UNIX programs do not check, producing "strange behavior". The paper's framing favors hard mounts for anything that matters.
Q11What was the VFS/vnode interface's cost?▾
"In most cases the difference was not measurable, and in the worst case the kernel had only slowed down by about 2%." The real cost was engineering: finding every place in the kernel that used inodes directly.
Q12Did NFS reach its performance goal?▾
On the benchmark total, yes: Figure 3 shows NFS at about 290 against ND's about 300 after the last improvements (read-off values). Individual benchmarks still lag local disks, worst for make and the compiles (Figure 4).
Q13Is NFS assuming one client per server? What if multiple clients share files and ordering matters?▾
Many clients per server is the normal case, but NFS gives no cross-client ordering or coherence guarantee. What it does guarantee is per RPC: each request is self-contained, applied to the server's local filesystem, and committed to disk before the reply; requests from different clients (served by several nfsd processes) are applied in whatever order they arrive. Consequences: (1) a write() larger than one request becomes several 8 KB RPCs, and with no server lock between them two clients writing the same range can end up with intermixed blocks (the paper states this); (2) client caches hide other clients' writes: dirty blocks reach the server only by write-behind or at close, and readers may use their own cached blocks or attributes trusted for up to 3 s (30 s for directories); (3) there are no locks in the protocol, so coordination needs a separate lock service that NFS knows nothing about; (4) a retransmitted or delayed request can arrive after a newer request from another client, so a late duplicate of an old write could overwrite a newer one, and nothing in the protocol (no per-file sequence numbers) prevents it (inference, not discussed in the paper); (5) UNIX behaviors patched on one client, such as removing an open file, cannot protect against actions from another client. Within one client, ordering is better behaved because RPCs are synchronous, except that the block I/O daemons can have several read-ahead or write-behind requests in flight. This gap is exactly what the Leases paper targets.
Q14What is a handle, and how is it different from a file descriptor?▾
A file handle is the server-issued name for one file or directory: a fixed-size opaque block (32 bytes in NFSv2, general knowledge) that the client stores in the file's vnode and sends back in every request. The client never interprets it, which keeps the protocol machine independent. A Sun server builds it from filesystem id + inode number + inode generation number, so it can decode any request on its own; the handle replaces the open-file table a stateful server would keep. A local file descriptor is the opposite: a small integer that indexes per-process kernel state created by open(). The first handle comes from MOUNT (root of the exported filesystem); every later one from lookup, create or mkdir on a directory handle you already hold, one name at a time. Because it names the inode, a handle survives renames; because of the generation number, a handle to a deleted-and-reused inode is rejected (the "stale file handle" error) instead of silently reaching the new file.
Q15Does one inode match one file handle?▾
Almost: one handle names one incarnation of one inode on one filesystem. The filesystem id is needed because inode numbers are only unique within a filesystem (inode 117 on /usr and on /home are different files). The generation number makes each reuse of an inode slot a new handle, so one inode slot maps to a series of handles over time and old ones go stale. Hard links (several names, one inode) all yield the same handle, which is also why a handle survives rename. On Sun's server the handle is computed from these fields, so looking up the same live file twice returns the same bytes. On the client, each handle in use lives in a vnode, the client's stand-in for the remote file (roughly what an in-core inode is locally). The paper only promises opacity; the field layout is Sun's UNIX server's choice.
Q16What is the filesystem id, and when does the generation number go up?▾
Filesystem id: one per filesystem on the server, the thing a disk partition holds (for example /, /usr and /home on separate partitions). The paper added it to the superblock. It is not per client and not per directory level: every client sees the same fsid for a given server filesystem, and every directory and file inside that filesystem shares it. It is needed because inode numbers restart in every filesystem, so (fsid, inode) is the unique pair. A server mount point is exactly where the fsid changes, which is one reason the server will not let a lookup cross its own mount points. The client's root has nothing to do with it; it is a server-side identifier. Generation number: per inode, and the paper says it "has to be incremented every time the inode is freed". So it changes only when a file is deleted and its inode returned to the free pool, never on reads, writes, truncation, chmod or rename, which all keep the same inode and the same handle. Delete then recreate under the same name: the new file gets a freshly allocated inode, either a different number or the same slot with a higher generation, so either way it has a new handle, and a client still holding the old handle gets a stale-handle error even though the pathname exists again. Overwriting in place (open with truncation and write) keeps the inode, so other clients' handles stay valid; an editor that writes a new file and renames it over the old one creates a new inode, so their old handles go stale (inference from the rule, not discussed in the paper).
Q17Why would a server have several filesystems (/, /usr, /home) instead of one tree?▾
The directory tree is one namespace, but underneath it is stitched together from several filesystems. A filesystem is a self-contained on-disk structure on one partition or disk: its own superblock, its own inode table (so inode numbers start over in each one), its own free-block map. mount attaches a filesystem's root directory onto a directory of the tree, so /usr is really "the root of the second filesystem, shown at /usr". Reasons to split in 1985 (general UNIX practice): one disk was often too small, so a second disk had to be a second filesystem; a full /home or /tmp cannot fill / and stop the system; /usr can be mounted read-only and shared; backups, dump and fsck run per filesystem, so smaller ones recover faster; and for NFS, exporting a whole filesystem such as /usr to many diskless clients is the unit of sharing. This is also why the fsid matters: (fsid, inode number) is unique on the server, the inode number alone is not.
Q18Does NFS number each created file? Can a deleted file and a new file share the same index?▾
The numbers come from the server's own UNIX filesystem, not from NFS. Each filesystem has a fixed inode table made when it was created; the inode number is just the slot index in that table. Creating a file takes a free slot; deleting it returns the slot to the free list. So yes: a deleted file and a later file can have the same inode number, because they occupied the same slot one after the other. The generation number is a counter stored in the slot that is incremented every time the slot is freed, which makes the two distinguishable. Example: file A gets slot 117 with generation 3, handle (fs 4, 117, 3). A is deleted, slot 117 is freed, generation becomes 4. File B is created and happens to get slot 117: handle (fs 4, 117, 4). A client still holding (4, 117, 3) is rejected as stale instead of reading B. If B had been given a different free slot, the old handle would point at a free slot and be rejected too. The generation number does not count files or updates; it counts reuses of one slot.
Q19If a client runs mkdir /tmp, does that create a new filesystem?▾
No. mkdir creates a directory: one new inode plus one directory entry inside whichever filesystem holds the parent. If the parent is local, it happens on the local disk. If the parent is under an NFS mount, the client sends an NFS mkdir(dirfh, "tmp", attr) RPC and the server creates the inode in that server filesystem, so the new directory shares the parent's fsid. A new filesystem only comes from formatting a partition or disk (mkfs/newfs), which creates a fresh superblock, inode table and free map; mount then attaches it at an existing directory. Mounting never creates a filesystem, it only attaches one: a client could mount its own local partition at /tmp, or a remote filesystem with NFS. In the paper's diskless setting /tmp is exactly what should not be shared: programs name temporary files by process id, which is unique only on one machine, so two clients sharing one /tmp could collide. That is one reason the paper does not support shared root filesystems and keeps per-machine files apart (the /private scheme).
Q20How can NFS be "a set of remote procedures"? Isn't it the whole system with the disks?▾
The name covers two things, and the paper separates them (its design has three pieces: protocol, server side, client side). The NFS protocol is only a contract: a list of procedures (lookup, read, write, create, ...), their arguments and results in XDR, and what each one does. It owns no disk and contains no code. The NFS implementation is code on both machines that speaks that contract: on the client, the NFS filesystem type under the vnode layer turns system calls into RPCs; on the server, the NFS server code (run by nfsd) receives each RPC and performs it with ordinary local filesystem operations through the server's own vnode layer. The disks belong to the server's normal local filesystem (UNIX 4.2 FFS), which works exactly as it would without NFS; local programs on the server use the same files directly. NFS sits on top of it, it does not replace it. Example: read(fh, 8192, 8192) arrives; the server decodes the handle into (fsid, inode, generation), finds that inode in its 4.2 filesystem, and calls the normal vnode read, which goes through its buffer cache to the disk. Defining NFS as a protocol is what makes it machine and OS independent: any machine that implements those procedures over its own storage can be a server, and any machine that issues them can be a client (compare HTTP versus a particular web server and its disk).
Q21What is the difference between ND and NFS? Aren't both disks over the network?▾
They split the work at different layers. ND (Sun Network Disk) is block level: the paper describes it as "block-level access to remote, sub-partitioned disks". The client asks for "block N of partition P"; the server just moves blocks and knows nothing about files. The client runs its own filesystem code (inodes, directories, free maps) on top, exactly as if the disk were local. NFS is file level: the server runs the filesystem and the client asks for "8 KB at offset X of the file with this handle" or "look up this name in that directory". Consequences: (1) Sharing. With ND each client caches and updates metadata (superblock, inodes, free-block maps) privately, so two clients writing one partition would corrupt it; each client gets its own sub-partition, and only read-only sharing is safe. With NFS the server owns the metadata and applies every operation itself, so many clients can share one writable filesystem. (2) Independence. An ND client must understand the on-disk format; an NFS client only needs the protocol, so different machines and OSes can share files. (3) Speed. ND was the faster baseline (raw blocks, client-side caching, no server filesystem work); the paper's goal was for NFS to match ND, which ran about 80% as fast as a local disk. (4) Diskless clients in 1985 still needed both: ND for the private root and swap, NFS for shared /usr and home directories, which doubled administration (listed as future work). Modern analogy (general knowledge): ND is like iSCSI or a SAN volume; NFS is a file server.
Q22What does "UNIX semantics" mean?▾
"Semantics" is the behavior an operation promises, what a program can rely on after calling it, as opposed to the interface (its name and arguments). NFS keeps the interface identical (same system calls, same pathnames, no recompiling), but behind that interface some behaviors change, because a remote stateless server now does the work. UNIX file semantics that local programs assume, and where NFS stands: (1) a write is visible to the next read by any process: over NFS, other clients may read cached or not yet flushed data; (2) a single write() is atomic with respect to other writers (inode lock): over NFS a large write is several RPCs and can intermix; (3) an open file stays usable after it is removed: restored on one client by renaming instead of removing (the 3/4 solution); (4) permission is checked once, at open: NFS checks on every call, patched by saving credentials at open; (5) root can access any file: NFS maps root to nobody, patched with the set-uid retry; (6) file times come from one clock: NFS uses the server's clock for file times and the client's for "now", so skew confuses programs that compare the two, such as ranlib (with ld), ls and emacs, the ones the paper names; (7) file locking exists: NFS leaves it to a separate service. "Getting UNIX semantics back, mostly" means the client kernel patches (3), (4) and (5) without changing the server or protocol; (1), (2) and (7) need server state, so they are not restored, and (6) needs synchronized clocks.
Q23How do NFS, RPC and XDR fit together? Is XDR the template the client fills in?▾
Almost: XDR is the encoding rules, not the template. Three layers, each with one job: NFS protocol says what can be asked: the 16 procedures and the type of each one's arguments and results (written in XDR's data definition language, so in that sense the "templates" are written in XDR). XDR says how any value becomes bytes: 4-byte big-endian integers, length-prefixed padded strings, fixed opaque blocks. It is used in both directions, for arguments and for results, and also for the RPC header itself. Sun RPC makes it a procedure call: a header naming the program (NFS), version and procedure number, a transaction id to match the reply to the request, and the caller's credentials; the client blocks until the matching reply arrives or retransmits on timeout. Underneath, UDP/IP carries the datagram. One call end to end: the client stub encodes the arguments with XDR behind an RPC header and sends it; the server's RPC layer reads the procedure number and dispatches; the server stub decodes the arguments into native values; the NFS server code performs the operation on its local filesystem, which is what touches the disk; the result is encoded with XDR and sent back; the client stub decodes it and returns it to the kernel code that made the call. XDR never runs on the disk: it ends at the stub, and the server works on ordinary native values from there.
Q24Why is it called "opaque" data?▾
Opaque means "you cannot see inside it". In XDR, opaque is a type for raw bytes that XDR does not interpret: it does not convert their byte order or look for fields, it copies them exactly (padded to a multiple of 4). An int, by contrast, is converted to big-endian on the way out and back to native on the way in. The file handle is declared opaque because only the server that issued it knows what is inside (fsid, inode number, generation on a Sun server). The client, XDR and RPC just carry the 32 bytes back unchanged; if a little-endian client converted them as integers, the server would no longer recognize its own handle. The same idea appears in the readdir cookie (an opaque pointer to the next entry) and in the RPC header's credential field (opaque bytes whose "flavor" tag tells the server how to read them). Opacity is what lets a non-UNIX server put a completely different layout inside a handle without any client changing.
Q25What does "transport independence" mean?▾
The transport is whatever actually carries the bytes between machines: UDP datagrams, a TCP connection, or some other network protocol. The paper says Sun RPC is "designed to be transport independent": new transports "can be plugged in" to the RPC implementation "without affecting the higher level protocol code". In layers: NFS procedures, encoded with XDR, called through RPC, carried by a transport. Swapping the transport (say UDP for TCP) changes only the bottom layer; the NFS procedures, their XDR encodings, the client and server code that call them do not change. What the transport does change is delivery behavior. UDP can lose, duplicate or reorder datagrams, so the RPC client retransmits on timeout, which is safe only because NFS requests are (meant to be) idempotent. TCP is a reliable byte stream, so loss is handled below RPC, but it needs a connection, which is state on both ends. NFS chose UDP over IP: it is cheap, connectionless (nothing to re-establish after a server crash, which fits the stateless design), and an 8 KB request fits one datagram that IP fragments. Later NFS versions also ran over TCP, exactly the kind of swap transport independence allows (general knowledge, not in the paper).
Q26What is an opaque readdir cookie?▾
A bookmark into a directory listing that only the server can read. A directory can have more entries than fit in one reply, so readdir(dirfh, cookie, count) returns up to count bytes of entries, and each entry carries a name, a file id and a cookie, "an opaque pointer to the next directory entry". To continue, the client sends back the last cookie it received; cookie 0 means "start at the first entry". Why it exists: locally, an open directory keeps its read position in the kernel. A stateless server cannot keep a cursor per client, so the position travels in every request instead, the same trick as the explicit offset in read and write. Why opaque: the client never interprets it, so each server chooses its own meaning (a UNIX server can use the byte offset of the next entry inside the directory file; another server can use something else) without any client changing. Example: a directory of 300 entries; call 1 with cookie 0 returns entries 1 to 120, each carrying its own cookie; call 2 passes the cookie carried by entry 120 (which points at entry 121) and gets 121 to 240; call 3 gets the rest. There is no separate "before" or "after" cookie: every entry has one, so the client could resume after any entry it received. How the end is signaled is not in the paper; in the published NFS version 2 specification (RFC 1094, general knowledge) every reply also carries an eof flag, and the last entry still has its cookie, so the client stops when eof is true rather than when cookies run out. Who remembers what: the client keeps the cookie of the last entry it received (client-side state, for example as the position of its open directory), and each call sends (dirfh, that cookie, count). count is only a cap on the reply size; the server packs as many whole entries as fit and never splits one, so the client does not know in advance how many entries it will get (general knowledge, not in the paper). Limit: the paper does not say what happens if the directory changes between calls; with an offset-style cookie an insertion or removal can make the client skip or repeat entries (inference).
Q27Why readdir and not just read? Can you read a directory, and is count measuring data or metadata?▾
A directory is a file. In UNIX a directory is stored like a file: an inode plus data blocks, and its data is a list of entries, each mapping a name to an inode number. So reading a directory means reading those entries. Old UNIX programs did exactly that with plain read() and parsed the bytes themselves. Why NFS needs a separate readdir. The raw bytes are the server filesystem's private on-disk format: 4.2BSD uses variable-length records, older UNIX filesystems used fixed 16-byte entries, MS-DOS uses something else again. A client on a different machine or OS cannot parse another system's layout, and a byte offset into it means nothing to the client. readdir instead returns entries in one standard XDR form (name, file id, cookie), whatever the server stores, and the cookie replaces the layout-specific byte offset. The same problem appeared locally once the kernel had several filesystem types: the paper adds a getdirentries system call that returns entries in a filesystem-independent form, and programs using the readdir library had to be relinked. Clients also cannot change a directory by writing bytes into it; directories change only through create, remove, rename, link, symlink, mkdir and rmdir, so the server keeps them consistent. What count counts. It caps the size of the reply: up to count bytes of encoded entries (names, file ids, cookies), so the answer fits one message. It is not a count of bytes on the disk and not a number of files. Data or metadata? From the directory's point of view the entries are its contents. They are not the files' attributes: size, mode, owner and times live in each file's inode and come from getattr (or with lookup), not from readdir. That is why ls -l on NFS needs a readdir plus a getattr or lookup per file, while plain ls needs only readdir.
Q28What does it mean that the server does not interpret the symlink string?▾
A symbolic link is a tiny file whose content is a pathname string, such as /usr/local/bin/cc or ../lib. symlink(dirfh, name, string) creates that file on the server and stores the string exactly as given: the server does not check that the target exists, does not resolve it, and does not follow it. readlink(fh) just hands the string back. Following the link is the client's job. The client walks pathnames one component at a time (lookup per name); when a lookup returns a symlink, the client calls readlink, splices the string into the path, and continues walking in its own namespace, with its own mounts. So an absolute link like /usr/lib is resolved against the client's root, which can differ from the server's (inference from the paper's design: lookup per component and no server-side crossing of mount points). So it is neither passing the target by value nor the server resolving names: the server is storage for an uninterpreted string, and meaning is given by whoever reads it. The paper relies on this for diskless clients: machine-specific files are moved to /private and replaced by symbolic links, which each client resolves to its own copy. Contrast a hard link, link(dirfh, name, tofh, toname): that is a second directory entry for the same inode, created and maintained by the server, and it names a file, not a path.
Q29What is a superblock, and why is a "filesystem" different from a directory?▾
Superblock: the header at a fixed place on a filesystem's partition that describes the whole filesystem: its size, block size, how many inodes it has, where the inode table and free-block maps are (for 4.2BSD, the cylinder-group layout), and status flags. Mounting reads the superblock first, because nothing else on the partition can be interpreted without it (4.2BSD keeps backup copies of it). NFS added one field there: the filesystem id. One fsid per filesystem: if /, /usr and /home are on three partitions, there are three superblocks and three fsids. If /home is just a directory on the same partition as /, it has no superblock of its own and shares /'s fsid. Filesystem versus directory: a directory is one inode whose data is a list of name to inode entries. A filesystem is a whole self-contained storage structure on one partition: superblock, inode table with its own numbering, free-space maps and data blocks, with its own root directory. The single tree you see is assembled by mounting the root of each filesystem onto a directory of another. You can tell the boundaries apart in practice (general UNIX knowledge): df lists filesystems, not directories; inode numbers restart in each filesystem (each root is inode 2); a hard link cannot cross filesystems; and rename across filesystems fails (EXDEV), so mv has to copy and delete. That is exactly why the NFS handle needs the fsid: inode 117 means nothing until you know which filesystem's inode table it indexes.
Q30What is a partition? Is it like C: and D: on one Windows disk?▾
Yes. A partition is a contiguous range of a disk's blocks, recorded in a table at the start of the disk (in 4.2BSD, the disk label with partitions a to h). The OS treats each partition as a separate device, and each can hold one filesystem, or be raw swap space with no filesystem at all. C: and D: on one physical drive are exactly this: two partitions, each formatted with its own filesystem. The superblock is then the filesystem-wide metadata at the start of each formatted partition (sizes, where the inode table and free maps are); per-file metadata lives in each file's inode, not in the superblock. The difference from Windows is presentation: Windows shows each filesystem as its own drive letter, a separate tree, while UNIX mounts them all into one tree (root partition at /, another at /usr, another at /home), so the boundaries are invisible in pathnames. A second physical disk works the same way, just one more device to mount. This also explains ND: Sun's Network Disk gave each diskless client its own sub-partition of the server's disk, a private raw block range for its root and swap.
Q31What happens to filesystems and handles when the server reboots after a crash?▾
Boot sequence (general UNIX knowledge, details vary by system): the boot ROM loads a bootstrap from the boot block at the start of the root partition, which loads the kernel. The kernel finds partition boundaries from the disk's partition table (on Sun disks, a label in the first sector), then mounts the root filesystem by reading its superblock at a fixed offset inside that partition (8 KB in, for 4.2BSD, right after the boot block) and checking its magic number. Which other partitions to mount where comes from a file on the root filesystem (/etc/fstab), not from block 0. Each mount reads that partition's superblock, and that is when the fsid is read. After a crash: buffers that were never written may leave each filesystem inconsistent (free maps, link counts, inodes), so the startup script runs fsck on every filesystem before mounting it, repairing what it can (a backup superblock is used if the primary is damaged). Then the NFS daemons (nfsd, mountd) start again. Why NFS needs nothing more: everything a handle depends on is on disk. The fsid is in the superblock and the inode number and generation are in the inode, so a handle issued before the crash still decodes to the same file afterward, and clients that were retrying simply get answers. Every write the server acknowledged was already on disk (synchronous server writes), so fsck cannot lose it. The fsid must be stable across reboots for this to work: if it were assigned at mount time (for example by mount order), every outstanding handle would go stale after a reboot. Putting it in the superblock makes it persistent.
Connecting outward

What NFS teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

"Acknowledged" must mean "inside the persistence domain"

NFS's rule that the server's unwritten buffers are "part of the client's state" is the same rule any persistent-memory or storage stack faces: an acknowledgment is only safe once the data has left every volatile buffer. A server that acks from DRAM, or a device that acks from a volatile write cache, breaks it silently. Stable non-volatile buffering (the NVRAM case in M6's A4) is the legitimate way to ack early.

Generation numbers are ABA tags

(fsid, inode, generation) is a tagged pointer: the inode number is the address, the generation is the tag that defeats reuse. The same pattern appears in lock-free structures, in mapping tables that reuse slots, and in flash translation layers that must tell a current mapping from a stale one after a slot is recycled. The requirement is also the same: the tag must persist as long as any outstanding reference can, which for NFS means on disk.

Idempotent commands make retry after timeout safe

A host that times out on a device command and reissues it faces NFS's problem exactly: writes to an explicit address repeat harmlessly; commands whose effect depends on prior state (allocate, append, rename-like remaps) do not. Making commands absolute, or keeping a small duplicate-detection record, are the two classic answers, and NFS shows the cost of choosing neither.

Time-to-live caching is not coherence

The attribute cache is a TTL cache: cheap, stateless at the home node, and correct only if writers are rare inside the window. Coherence (leases, invalidations, directories) puts state at the home node so writers can wait for or revoke readers. Any tiered memory design that caches remotely owned data makes this same choice, explicitly or not.

🍯
One-line takeaway: decide what the home node is allowed to forget, then pay for that decision in idempotence, synchronous persistence and weak caching, the way NFS did.
