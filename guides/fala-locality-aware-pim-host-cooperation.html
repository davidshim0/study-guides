MICRO 2025 · A Field Guide

Send each vertex touch to wherever it's cheap, not wherever it's convenient

Graph updates are tiny (≤8B) and scattered, but DRAM only speaks in 32B bursts. This is the plain-English story of FALA, a hardware pairing of a lightweight in-memory ALU and a locality monitor that decides — per DRAM row — whether to compute in place or fetch to cache.

📄 Shin, Song, Na, Sung, Jang, Lee · Seoul National University 🎓 DRAM/PIM/cache fundamentals assumed — primers cover graph-specific mechanics only ⏱ ~25 min read
🧭

If a DRAM row is HOT (row-locality monitor hits), fetch it to the host cache. If it's COLD (no reuse expected), reduce it in place with a one-ALU PIM unit and never bring it on-chip at all.
Decided per row, enforced with a single bit, cheap enough to run every access.

Quick glossary — the acronyms up front

FALA's alphabet soup, defined once

Cache/DRAM/LRU fundamentals are assumed. These primers cover only what's specific to graph accelerators and this paper's mechanism.

FALAFine-grAined-column-access, Locality-Aware PIM-host cooperation — the paper's full system.
PIMProcessing-in-Memory: an arithmetic unit placed inside (or beside) a DRAM bank to avoid moving data off-chip.
VCMVertex-Centric Model (Pregel-style): each iteration runs Process → Reduce → Apply over active vertices.
MATMemory Array Tile — a 512×512 DRAM cell sub-block; a bank's rows are built by ganging many MATs together.
FALUThe single, minimal ALU FALA-PIM places per bank — sized only for Reduce (add/compare), not general compute.
RLMRow Locality Monitor — a tag-only cache that tracks which DRAM rows (not cache lines) are being reused.
PCUPIM-Cache Cooperation Unit — aggregates several small requests to the same DRAM row before issuing one memory operation.
tCCDLColumn-to-column delay within the same bank group — the internal DRAM timing unit FALA-CAS's conflict cost is measured in.
1The vertex-centric model, in three functions▾

Each iteration: Process(edge weight, source property) produces a value; Reduce folds that value into the destination's temporary property (Vtemp) — associative, e.g. min or add; Apply commits Vtemp into Vprop and reactivates the vertex if it changed.

Reduce is the troublemaker: it touches Vtemp[v] at essentially random destination addresses, per edge, with almost no arithmetic per touch.

Now you're set: FALA's whole design targets offloading Reduce specifically — Process and Apply stay on the host.
2Graph tiling and its hidden tax▾

Cache-based accelerators partition the vertex set into tiles sized to fit on-chip memory, so a tile's Reduce accesses land in the cache instead of DRAM. "Perfect tiling" (tile = cache capacity) minimizes random access — but each tile re-scans the graph topology and re-fetches source properties, so total memory traffic can rise even as hit rate improves. There's no free lunch: better locality per tile, more redundant tiles.

Now you're set: this locality-vs-redundancy tension is exactly what a hybrid PIM+cache design can sidestep — send low-reuse vertices straight to PIM, keep only high-reuse ones in cache, no re-tiling needed.
3HBM2, scoped to what FALA touches▾

HBM2: 8 channels → 2 pseudochannels each → 4 bank groups → 4 banks → many subarrays → MATs (512×512 cells). An activated row spans 16 MATs, each streaming 8b/cycle, so 16B lands per DRAM-core cycle; two cycles make the standard 32B external burst. A bank holds ~16K rows of 1KB each.

Minimum external access granularity is fixed at 32B — you cannot ask DRAM for less over the standard interface, no matter how small your data actually is.

Now you're set: FALA-CAS's whole job is punching a hole in that 32B floor from inside the bank, before the burst ever leaves.
4The granularity mismatch, stated precisely▾

A vertex property is typically ≤8 bytes. A burst is 32 bytes. A naive PIM Reduce operation touches one property, uses 8 of the 32 bytes fetched, and discards the rest — 75% of the transferred bytes are wasted, every single access.

Now you're set: this 4:1 mismatch is the concrete number FALA-CAS's MatGroups mechanism is built to close.
5Cache-line locality vs row locality — a granularity choice▾

A conventional locality monitor (like the one in PEI, built on Qureshi & Patt's cache-partitioning utility idea) tracks reuse at cache-line granularity (e.g. 64B). Shrinking that to 8B granularity to match vertex properties would cost ~25% of the cache in tags alone, and fragments memory requests so neither the cache path nor the PIM path can fill a full burst.

FALA instead tracks locality at DRAM-row granularity (1KB) — a coarser unit than a cache line, but one that composes cleanly with FALA-CAS's fine-grained access within that row.

Now you're set: two different granularities solve two different problems — the monitor decides which row is worth caching; FALA-CAS decides which bytes inside it to move.
6Why real graphs make this decision worth automating▾

Real-world graphs are power-law distributed: a small number of high-degree vertices are touched constantly (excellent cache candidates), while the long tail of low-degree vertices is touched once or twice (PIM candidates, since caching them buys nothing). Any fixed policy — all-cache or all-PIM — is wrong for one half of the distribution.

Now you're set: this skew is why FALA needs a runtime classifier (the Row Locality Monitor) rather than a static split.
The whole story in one place

FALA in a nutshell

The problem, the two mechanisms that fix it, and how they cooperate.

Graph accelerators split into two camps, each with a structural blind spot. Cache-based designs tile the graph to fit reused vertex data on-chip, but tiling forces redundant re-scans of graph topology, and every fetch still moves a 32B burst to serve an ≤8B property. PIM-only designs compute inside memory to dodge the bus entirely, but with no cache they re-derive locality from scratch every iteration — devastating on graphs with real data reuse.

FALA refuses to pick a camp. It pairs a minimal per-bank PIM unit (FALA-PIM, one ALU, 16K transistors) with a fine-grained access mechanism (FALA-CAS) that splits each bank's MATs into independent odd/even groups, so a single 32B burst can carry four unrelated 8B columns instead of four sequential bytes. A PIM-Cache Cooperation Unit collects requests bound for the same DRAM row until it has enough to fill a burst, and a Row Locality Monitor — a tag-only cache tracking rows, not cache lines, at just 2 bytes/entry — decides whether that row's data is worth pulling into the host's fine-grained cache or better reduced in place.

The payoff: across PageRank, BFS, connected components, and SSSP on five real graphs, FALA delivers 2.10×, 2.39×, 1.60×, 1.56× geomean speedup over GraphDyns (cache-based), GraphPIM (PIM-only), PEI (locality-aware PIM), and Piccolo (prior hybrid SOTA) respectively — cutting off-chip memory accesses by 60.2% and energy by 35.3% versus Piccolo, for roughly 8% extra host-side die area and a DRAM-side logic overhead an order of magnitude below commercial bank-level PIM.

🍯 Key takeaways

  • Cache-based tiling trades redundant topology re-fetches for locality; PIM-only trades all locality for internal bandwidth. FALA routes per row, not per architecture.
  • FALA-PIM targets only the Reduce phase (low arithmetic intensity, associative → safe to serialize) with a single-ALU, 3-stage pipeline.
  • FALA-CAS splits a bank's MATs into odd/even groups so 4 independent 8B columns fill one 32B burst instead of one column wasting the other 24B.
  • The Row Locality Monitor tracks reuse at DRAM-row granularity (2B/entry, 0.2% overhead) — coarse enough to be cheap, matched to what FALA-CAS can already exploit inside a row.
  • The PIM-Cache Cooperation Unit is the traffic cop: it batches 4 same-row requests before issuing either a gather (cache path) or a PIM update (memory path).
  • Result: 1.56× speedup, 35.3% energy cut vs. the strongest prior hybrid (Piccolo), for <1% area beyond a conventional graph accelerator's die.
💡
For the CXL/tiering reader: the Row Locality Monitor is structurally the same move as a hot-page tracker in DRAM/NVM tiering (à la TPP's promotion hints or HeMem's sampled hotness) — a cheap, coarse-grained classifier that decides where data should live. The differences: FALA's classifier runs entirely in hardware at DRAM-row (not OS-page) granularity, and its two "tiers" are host cache vs. in-place compute rather than fast vs. slow memory.
Six everyday pictures

How to think about FALA

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · Locality routing

Sorting the day's mail

A regular's mailbox stays reserved near the front desk (cache) because they check it daily. A one-off package for a walk-in gets handled right at the loading dock (PIM) — carrying it inside just to hand it straight back out would waste a trip. FALA's Row Locality Monitor is the clerk deciding, per delivery, which desk it belongs at.

Where it breaks: a mail clerk knows the recipient by name; FALA only knows a DRAM row's recent access history — it can misjudge a regular who just changed addresses (a vertex whose reuse pattern shifts phase).
FALA-CAS · MatGroups

Two clerks, two independent shelves

Normally one clerk fetches whatever's next on the shelf — sequential items only. Split the shelf into two halves with a clerk each, and now you can grab any item from the left half and any item from the right half at the same time — two unrelated picks, one trip. That's odd/even MatGroups: each gets its own column decoder, so a single burst carries four independently-addressed 8B properties instead of four sequential bytes nobody asked for.

Where it breaks: if three of your four items are on the same half-shelf ("mat conflict"), one clerk still has to make two trips — latency doubles (tCCDL → 2×tCCDL) exactly like a real clerk can't be in two places on their own shelf at once.
PIM-Cache Cooperation Unit · Batching

Waiting for the van to fill up

Instead of dispatching a separate ride for every rider headed to the same neighborhood (DRAM row), the dispatcher (PCU) waits until four riders bound for that neighborhood have checked in, then sends one van — a single CAS or PIM operation instead of up to eight scattered round-trips.

Where it breaks: a dispatcher who waits too long strands riders; FALA doesn't wait indefinitely either — a request to a different row can force a flush of whatever's pending ("type conflict"), which happens for about 6.32% of requests on average.
Row Locality Monitor · Coarse tracking

Watching the shelf, not the book

A librarian tracking which shelves get pulled repeatedly doesn't need to log every individual book's checkout — shelf-level frequency is cheap to track and good enough to decide "keep this shelf near the front." FALA's monitor works the same way: it watches DRAM-row hotness (2 bytes of tag per 1KB row), not individual 8-byte properties — leaving fine-grained tracking to FALA-CAS, which already knows how to pick items off a hot shelf efficiently.

Where it breaks: a shelf can look "cold" overall while containing one frequently-grabbed book, or vice versa — row-granularity locality is a real approximation, not a guarantee about any single vertex.
FALA-PIM · Minimal by design

A calculator, not a workstation

Graph Reduce is usually one operation — add, min, or compare. Building a full programmable core into every DRAM bank to run it would be like installing a workstation at every cash register just to do addition. FALA-PIM instead places a single adder/comparator (FALU) per bank — 16K transistors, one instruction per algorithm — sized to exactly match what Reduce needs and no more.

Where it breaks: a calculator can't be repurposed mid-task; FALA-PIM genuinely can't run anything beyond the one Reduce operation configured for the current algorithm — it's not a general PIM engine.
Tiling sensitivity · Robustness

A road that doesn't need exact directions

A cache-based accelerator's performance is a knife's-edge function of tile size — undershoot or overshoot the cache capacity and traffic spikes. FALA barely cares: because it only caches genuinely-reused rows and reduces the rest in place, its performance stays nearly flat across a 32× range of tile sizes, like a road that gets you there whether you take exit 3 or exit 8.

Where it breaks: FALA still uses some tiling to keep working sets manageable — "doesn't need exact directions" isn't "needs no map at all."
The full explanation

How it actually works

Mechanism by mechanism, then the execution flow that ties them together.

1 · FALA-PIM — the lightweight Reduce engine

Placed per bank, FALA-PIM is a 3-stage pipeline: Read Vtemp from the activated row's sense amplifiers, Reduce it against an incoming Process result in a single FALU, Write the updated value back to the row. No input registers beyond the sense amps themselves; a data-forwarding hazard resolver lets the pipeline issue one Reduce per cycle without stalling, even under back-to-back updates to the same address. Total cost: ~16K transistors per bank — an order of magnitude below commercial bank-level PIM designs that carry full GEMV engines.

Commands: the host sends four Process results (data buffer) and four destination column offsets (offset buffer) as ordinary write data over the data bus — not the command/address bus — via a new PIM_UPDATE command built from HBM2's reserved-for-future-use (RFU) bits and the unused C8 addressing bit.

2 · FALA-CAS — punching through the 32B floor

The baseline HBM2 bank fetches 16B/cycle by having one column decoder pulse every MAT identically — inherently sequential. FALA-CAS splits each bank's MATs into an odd MatGroup and an even MatGroup, each with its own column decoder. Now two independent column addresses can be selected simultaneously, one per group, and two such selections across the internal 2-cycle prefetch window deliver four independently-addressed 8B columns in one 32B burst.

⚠
The catch — mat conflicts. If more than two of the four target columns land in the same MatGroup, that group can't serve them all in one shot: it needs two sequential internal reads (2×tCCDL delay) instead of one (tCCDL). FALA-PIM's PIM_UPDATE pessimistically always budgets for conflict (4×tCCDL total, for 2 reads + 2 writes), since it can't know the offset distribution in advance.

3 · PIM-Cache Cooperation Unit — the aggregator

An SRAM array of entries indexed by DRAM row address, each holding up to four (offset, data) fields plus a type bit (PIM vs. cache-bound), mat-conflict bits (odd/even request counts), and four writeback fields. Every miss — cache miss or PIM candidate — gets folded into the entry for its row; once four column offsets for that row are collected, the unit fires a single FALA-CAS or PIM_UPDATE operation. Because Reduce is associative, multiple requests to the same destination vertex collected this way can simply be serialized inside FALA-PIM without changing the result.

4 · Row Locality Monitor — the classifier

A tag-only cache with one entry per tracked DRAM row: 1 valid bit + 11-bit partial row address + a few LRU bits, totaling 2 bytes/entry. A request is "high locality" if its row address hits the monitor (or the real cache); otherwise it's "low locality" and routed to PIM. Every issued request updates the monitor's LRU state, so hot rows survive eviction and cold ones fall out — the same mechanism a page-hotness tracker in a tiered-memory OS uses, just implemented at DRAM-row granularity in pure hardware.

// per memory request for Vtemp[v], row R
if (cache.hit(v) || RLM.hit(R)) {
    PCU.collect(R, offset(v), type = CACHE);
    if (PCU.entry(R).count == 4) FALA_CAS.gather(R); // → fine-grained cache, then Reduce on host
} else {
    PCU.collect(R, offset(v), type = PIM);
    if (PCU.entry(R).count == 4) FALA_PIM.update(R);  // Reduce happens in-bank, only offsets+results cross the bus
}
RLM.touch(R); // promote to MRU either way
// if a later request to R disagrees with the pending type bit → flush (type conflict, ~6.32% of requests)
💡
Coherency, for free: because a row is served by exactly one path at a time (type-conflict detection forces a flush before switching), and DRAM never initiates a request on its own, Vtemp for any vertex is never simultaneously "dirty" in both the cache and memory — no directory or invalidation protocol needed.
Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own reported figures.

① Why FALA-PIM cuts off-chip traffic 8×

A conventional near-bank PIM Reduce needs to read the old Vtemp and write the updated one for each of four destination vertices. How many off-chip transactions does that cost, versus FALA-PIM's approach?

  1. Conventional: 4 reads (fetch old Vtemp) + 4 writes (store updated Vtemp) = 8 transactions, each triggering a full-granularity access even though the payload is a few bytes.
  2. FALA-PIM: the host sends everything needed in one write — 4 column offsets (8b each = 32b) plus 4 Process results (32b each = 128b) = 160 bits total, comfortably inside a single burst.
  3. Reduce happens inside the bank; nothing needs to come back off-chip except the next iteration's ordinary reads.
  4. Ratio: 8 transactions → 1 transaction = up to 8× reduction in off-chip traffic for that batch of four Reduce operations, exactly as the paper states.
🍯
Insight: the saving isn't from a faster ALU — it's from never sending the intermediate reads/writes off-chip at all.

② Sizing the Row Locality Monitor

Each monitor entry is 1 valid bit + an 11-bit partial row address + a few LRU bits, padded to 2 bytes. Suppose you want it to track locality across a 16 MB region of DRAM (1KB rows). How big is the monitor, and what fraction of that region does it cost?

  1. Rows to track: 16 MB ÷ 1 KB/row = 16,384 rows.
  2. Monitor size: 16,384 entries × 2 B/entry = 32,768 bytes = 32 KB.
  3. Overhead ratio: 32 KB ÷ 16 MB = 2 B ÷ 1 KB = 0.2% — the paper's exact reported figure, and notice it's independent of region size: both numerator and denominator scale linearly with row count.
💡
That scale-invariance is why the monitor stays cheap whether it's watching one bank or an entire pseudochannel — the ratio never moves.

③ Reading the mat-conflict timing budget

FALA-CAS needs an extra delay before the next command: tCCDL if the four target columns split evenly across odd/even MatGroups, 2×tCCDL if they don't. FALA-PIM always assumes the worst case. Why 4×tCCDL total for one PIM_UPDATE?

  1. A FALA-PIM operation needs 2 internal reads (fetch old Vtemp for 2 columns each) + 2 internal writes (store updated values, 2 columns each) = 4 internal accesses total, since it pessimistically assumes every access mat-conflicts.
  2. Each access costs tCCDL (the standard column-to-column delay within a bank group).
  3. Total: 4 accesses × tCCDL = 4×tCCDL — exactly the extra interval the paper specifies before the next command may issue (e.g., before a PRECHARGE).
  4. Contrast with a plain FALA-CAS gather (no PIM, no conflict): only tCCDL extra, since 2 columns per group still land in one internal read each, and there's no write-back phase.
🍯
Insight: FALA-PIM's timing model doesn't try to be clever about the offset distribution — it just always budgets for the worst case, keeping the command interface simple.

④ What CAS and locality-awareness add on top of PIM alone

The ablation study reports FALA-PIM alone gives a 54.6% geomean improvement over GraphPIM; the full system (PIM + CAS + locality-awareness) gives 2.39× geomean over GraphPIM. How much do CAS and locality-awareness add on top of PIM alone?

  1. FALA-PIM alone = 1 + 0.546 = 1.546× over GraphPIM.
  2. Full FALA = 2.39× over GraphPIM (Fig. 9 geomean).
  3. Additional factor from CAS + locality-awareness: 2.39 ÷ 1.546 ≈ 1.546× — coincidentally almost the identical multiplier as PIM's own contribution.
  4. Check: 1.546 × 1.546 ≈ 2.39 ✓ — the two stages of the ablation contribute roughly equal, multiplicative shares of the total gain.
💡
Neither mechanism alone gets you halfway to "hybrid done right" — fixing the granularity mismatch (CAS) and fixing the placement decision (locality-awareness) are separate, comparably-sized problems, and FALA needed both.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking.

Problem 1 · easy
A naive PIM Reduce fetches a 32B burst to update one 8B vertex property. What fraction of the transferred bytes is wasted, and does a cache-based accelerator avoid this waste automatically?
Show answer
75% of the burst (24 of 32 bytes) is unused on that access. No — a cache-based accelerator fetches the same 32B line; it only avoids the waste if a future access reuses one of the other 24 bytes before eviction. If the data has no reuse (a streaming, single-touch vertex), the cache wastes exactly the same fraction.Misconception: "cache-based" and "wastes no bandwidth" are treated as synonyms. The cache only pays off with reuse; without it, cache and naive PIM are equally wasteful.
Problem 2 · medium
You want a Row Locality Monitor to cover an 8 MB DRAM region (1KB rows, 2B/entry). Compute its size and overhead percentage. Would doubling the region to 16MB change the overhead percentage?
Show answer
8 MB ÷ 1 KB = 8,192 rows → 8,192 × 2 B = 16 KB monitor. Overhead = 16 KB ÷ 8 MB = 0.2%. Doubling to 16 MB gives 32 KB ÷ 16 MB = still 0.2% — the ratio is fixed by the 2B/1KB design constant, not the region size.Misconception: bigger tracked regions need proportionally bigger relative overhead. Because both quantities scale linearly with row count, the ratio is scale-invariant.
Problem 3 · medium
Four column requests target the same row: three land in the odd MatGroup, one in the even MatGroup. Does this cause a mat conflict, and what's the resulting latency?
Show answer
Yes — a mat conflict occurs whenever either group has more than 2 requests, not only in the fully-skewed 4/0 case. With a 3/1 split, the odd group needs two sequential internal reads to serve its three requests, so the operation costs 2×tCCDL instead of tCCDL.Misconception: only a fully one-sided (4/0) split causes conflict. Any imbalance beyond 2/2 does, because each MatGroup's single decoder can only select 2 columns per burst window.
Problem 4 · hard
Why does FALA offload specifically the Reduce phase to PIM, and not Process or Apply?
Show answer
Reduce has the worst combination of properties: it's accessed at essentially random destination addresses (per-edge, unpredictable), has minimal arithmetic (one add/min/compare), and — crucially — is associative, so multiple pending Reduce operations to the same destination can be freely reordered/serialized inside FALA-PIM without affecting correctness. Process reads the source vertex sequentially via CSR (more prefetch-friendly, host-side is fine) and Apply runs once per vertex per iteration (much lower frequency, and needs the constant Vconst which typically isn't PIM-resident).Misconception: "any low-compute phase is a good PIM target." Low arithmetic intensity alone isn't sufficient — the associativity property is what makes concurrent, reorderable in-memory execution correctness-safe.
Problem 5 · medium
Why does the Row Locality Monitor track locality at 1KB DRAM-row granularity instead of matching FALA-CAS's 8B access granularity?
Show answer
An 8B-granularity tag-only cache would cost roughly 25% of the tracked capacity in tags alone, and — more importantly — would fragment memory requests: if half of four collected requests are "cache" and half "PIM" at fine granularity, neither the cache path nor the PIM path can fill a full burst, wasting the very bandwidth the fine-grained access was meant to save. Row-granularity tracking answers a coarser but sufficient question ("is this row worth caching at all") and lets FALA-CAS handle the fine-grained part separately.Misconception: finer tracking granularity is always more accurate and therefore better. Here it's impractical (tag overhead) and counterproductive (it breaks burst formation), so a coarser granularity paired with a separate fine-grained access mechanism wins.
Problem 6 · hard
A pending PIM-Cache Cooperation Unit entry for row R is collecting cache-type requests when a new request for R arrives that the Row Locality Monitor now classifies as low-locality (a "type conflict"). FALA's response is to flush the pending entry rather than dynamically reclassify it. Why is that a reasonable trade-off?
Show answer
Type conflicts are measured to affect only about 6.32% of requests on average — real-world graphs cluster high-locality vertices together, so classification rarely flips mid-collection. Building logic to dynamically re-tag a partially-filled entry (and correctly handle any already-issued sub-operations) adds real design complexity for a rare event; flushing and starting fresh is simpler and only costs a slightly early, slightly smaller burst.Misconception: handling every edge case with full generality is "free" if you just add more logic. Given how rare the conflict is, the simpler policy is the better engineering trade-off, not a missed optimization.
Problem 7 · medium
A cache-based accelerator's total memory traffic can rise even as its cache hit rate improves when tile size shrinks. Explain why, and predict how FALA's traffic would behave under the same experiment.
Show answer
Smaller tiles fit the cache better (higher hit rate on Vtemp accesses within a tile), but each tile independently re-scans the graph topology and re-fetches source-vertex properties (Process phase) for every active vertex, every tile — so total traffic can grow even as per-tile locality improves. FALA is comparatively insensitive to tile size (stable across a 32× range, Fig. 13) because it doesn't rely on tiling to create locality in the first place — it caches whatever the Row Locality Monitor finds genuinely hot, regardless of tile boundaries.Misconception: smaller tiles are strictly better because they raise hit rate. Hit rate is only one term in total traffic; redundant re-fetching of topology/source data is the other, and it grows as tiles shrink.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is the Row Locality Monitor related to utility-based cache partitioning (UCP)?▾
Indirectly, yes. PEI's baseline locality monitor (one of FALA's four comparison points) is explicitly built on Qureshi & Patt's UCP-style tag-only tracking structure, applied at cache-line granularity. FALA keeps the "cheap tag-only tracker" idea but relocates it to DRAM-row granularity, because the thing it needs to decide (cache vs. in-place PIM) is a different question than "how many cache ways should this program get."
Q2Isn't a 1KB DRAM row far too coarse to say anything useful about an 8B vertex property?▾
The row-level decision and the byte-level access are handled by two different mechanisms. The Row Locality Monitor only answers "is this row worth pulling to cache at all" — a coarse yes/no. FALA-CAS then handles exactly which 8B columns within that row actually get moved. Neither mechanism alone would work; together they match granularity to the right layer.
Q3Why does GraphPIM (PIM-only) slow down on dense graphs like Twitter?▾
With no cache at all, every Reduce access — even to a vertex updated repeatedly within the same iteration — goes through a full memory transaction. Dense, high-reuse graphs are exactly where a cache would normally absorb most of that traffic; GraphPIM has no way to capture that benefit, so its per-transaction overhead dominates.
Q4Why does FALA-CAS's isolated benefit show up strongest on the sparsest dataset?▾
The UU dataset (avg. degree ≈2) generates the most scattered, single-use small accesses — the worst-case granularity mismatch and the best-case scenario for consolidating four unrelated 8B columns into one burst. The ablation shows FALA-CAS adding up to 1.32× there, its largest isolated contribution.
Q5How does FALA avoid contending for the command/address bus when sending four column offsets?▾
Following Piccolo's precedent, offsets are transmitted as ordinary write data over the data bus rather than as separate column-address commands over the C/A bus — one write transaction carries all four offsets plus payload.
Q6Does FALA require a new DRAM standard?▾
No — it repurposes existing reserved-for-future-use (RFU) bits and the unused C8 addressing bit within the standard HBM2 column command, adding one new command (PIM_UPDATE) whose timing is handled with extended intervals, the same trick HBM2 already uses for bank-group interleaving.
Q7Why 8B access granularity and not 4B, when many graph algorithms use 4B properties?▾
Going to 4B would require the fine-grained cache to support 4B lines and the PIM-Cache Cooperation Unit to aggregate eight (not four) requests per row before issuing a burst — the paper estimates this would add over 50% extra on-chip capacity for the host-side structures. If 4B metadata can be packed two-to-a-word instead (24-bit vertex ID + 8-bit property in one 32-bit word), FALA gets an extra 13% speedup without any granularity change.
Q8How does FALA compare to a well-tuned GPU graph framework?▾
A resource-matched comparison (FALA-L: 32MB on-chip, 768GB/s, roughly matching an RTX A6000's capacity/bandwidth) beats the GPU framework Tigr by 7.15× on average. Even a far smaller configuration (FALA-S: 4MB, 256GB/s) slightly edges out the GPU — the gain isn't just from more silicon, it's from routing decisions a general-purpose GPU memory hierarchy doesn't make.
Q9Is FALA limited to the vertex-centric programming model?▾
No — the same granularity mismatch and locality-classification problem recurs in the edge-centric model, since it also randomly updates destination vertex properties. FALA's methodology transfers with significant speedup shown against an edge-centric baseline (ForeGraph) and an edge-centric variant of Piccolo.
Q10Which single mechanism contributes the most to FALA's overall gain?▾
The ablation splits it roughly evenly: FALA-PIM alone contributes a 1.546× (54.6%) factor over GraphPIM, and CAS + locality-awareness together contribute almost exactly the same additional 1.546× factor on top. Neither mechanism dominates — the paper's central claim is that you need both.

Row Locality Monitor (RLM)A tag-only cache (2B/entry) that tracks DRAM-row reuse to classify each row as high- or low-locality.
PIM-Cache Cooperation Unit (PCU)Aggregates memory requests targeting the same DRAM row until enough are collected to issue a full-burst FALA-CAS or PIM_UPDATE operation.
Mat conflictWhen more than 2 of 4 target columns land in the same MatGroup, forcing two sequential internal reads (2×tCCDL) instead of one.
Type conflictWhen a new request to a row already pending in the PCU has a different type (cache vs. PIM) than what's collected — resolved by flushing.
Supporting terms
VCM (Process/Reduce/Apply)The vertex-centric graph processing model this paper (and most graph accelerators) targets.
Graph tiling / perfect tilingPartitioning vertices into cache-sized groups to improve locality, at the cost of redundant topology re-fetches.
MATMemory Array Tile — a 512×512 DRAM cell sub-block; 16 MATs make up an activated row's data path.
tCCDL / tCCDSColumn-to-column delay within the same / different bank group — the timing units FALA-CAS's overhead is expressed in.
Fine-grained cacheA host-side cache supporting non-contiguous 8B line management, matched to FALA-CAS's access granularity.
PIM_UPDATEThe new command FALA-PIM adds, built from HBM2's RFU bits and the unused C8 bit, carrying offsets and results as write data.
MSHRMiss-status holding register — extended in Piccolo's baseline configuration to give it a fair comparison advantage against FALA.

Related work cited in the paper

Utility-Based Cache Partitioning medium

Qureshi & Patt · MICRO · 2006 · [ref 69]

The tag-only, cheap-monitor idea that PEI's baseline locality monitor is built on; FALA generalizes the concept to DRAM-row granularity instead of cache-line utility.

GraphPIM: Enabling Instruction-Level PIM Offloading in Graph Computing Frameworks medium

Nai, Hadidi, Sim, Kim, Kumar, Kim · HPCA · 2017 · [ref 58]

The PIM-only baseline FALA is compared against; extended to HBM2 in this paper's evaluation.

PIM-Enabled Instructions: A Low-Overhead, Locality-Aware PIM Architecture medium

Ahn, Yoo, Mutlu, Choi · ISCA · 2015 · [ref 2]

PEI — the locality-aware PIM baseline whose cache-line-granularity monitor motivates FALA's row-granularity redesign.

Piccolo: Large-Scale Graph Processing with Fine-Grained In-Memory Scatter-Gather hard

Shin, Song, Jang, Kim, Sung, Kwon, Ju, Liu, Choi, Lee · HPCA · 2025 · [ref 78]

The prior state-of-the-art hybrid FALA is measured against most directly (1.56× speedup, 35.3% energy reduction).

Alleviating Irregularity in Graph Analytics Acceleration (GraphDyns) medium

Yan, Hu, Li, Basak, et al. · MICRO · 2019 · [ref 87]

The conventional cache-based baseline; also the source of FALA's own accelerator-core microarchitecture template.

Pregel: A System for Large-Scale Graph Processing easy

Malewicz, Austern, Bik, et al. · SIGMOD · 2010 · [ref 56]

Origin of the vertex-centric Process/Reduce/Apply abstraction FALA's whole pipeline is built around.

Tigr: Transforming Irregular Graphs for GPU-Friendly Graph Processing hard

Nodehi Sabet, Qiu, Zhao · ASPLOS · 2018 · [ref 59]

The GPU software framework used for FALA's cross-platform comparison (§7.6).
