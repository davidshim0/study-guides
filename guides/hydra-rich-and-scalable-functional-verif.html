eBPF'26 · A Field Guide

Verify the chain, not the monolith

Production kernels run dozens of chained eBPF programs. Checking the chain as one giant blob explodes; Hydra checks each program once and stitches the results with SMT on chains it can certify as faithful — and grounds its kernel-helper models against the real kernel instead of guessing.

📄 "Hydra" · Castanheira & Benson, CMU 🎓 Some symbolic-execution basics assumed — primers cover them ⏱ ~25 min read
🐍

Symbolically execute each program in isolation, cache its summary, and answer every chain question by STITCHING summaries in SMT — not by inlining the chain and re-running symbex on the monolith.

Quick glossary — acronyms up front

eBPFExtended Berkeley Packet Filter — sandboxed programs the kernel runs at hook points (packet arrival, socket events, etc).
XDP / TCTwo common eBPF hook points on the network path (eXpress Data Path, very early; Traffic Control, later).
symbex / SEESymbolic execution / symbolic execution engine — explores a program's paths using symbolic (unknown) input instead of concrete values.
KLEEThe symbolic execution engine (interprets LLVM IR) Hydra and prior eBPF verifiers build on.
SMT solverA solver (Z3 here) that decides whether a logical formula over symbolic variables is satisfiable — Hydra's "stitching" engine.
BPF helperA kernel function an eBPF program can call (e.g., adjust packet headroom); runs real kernel code, which symbex can't natively execute.
kcovKernel code-coverage instrumentation; records which kernel basic blocks executed for a given input.
CFGControl-flow graph — a program's basic blocks and branches; Hydra prunes it before symbex.
1What eBPF chains are, and why they exist▾

A single kernel event (a packet at XDP, a socket state change) can dispatch not one but many eBPF programs in sequence, added independently by different teams (networking, security, observability). At Meta, half of all servers run ≥180 concurrent eBPF programs.

No infrastructure-wide contract stops one program's behavior from quietly interfering with the next.

Now you're ready: Hydra's entire premise is that verification must reason about these chains, not single programs in isolation.
2The in-kernel verifier only checks safety, not semantics▾

Before loading, the kernel's own verifier checks memory safety, bounded loops, and termination — one program at a time. It says nothing about whether the program's behavior is correct, or how it interacts with programs chained before/after it.

Now you're ready: Hydra fills exactly this gap — functional, cross-program correctness — that the in-kernel verifier was never designed for.
3Symbolic execution and path explosion▾

Symbex runs a program with symbolic (unknown) inputs, exploring every feasible branch and recording each path's condition. It's precise but the number of paths grows exponentially with branches — "path explosion." A single large program (e.g., 2,000+ LoC) can already take days; chaining several multiplies the problem.

Now you're ready: path explosion is the "speed" problem Hydra spends most of its design solving.
4Compositional symbolic execution▾

Instead of symbolically executing a whole system at once, symbolically execute each unit (function, program) once, save its path summaries, then answer whole-system questions by combining summaries logically — no need to re-explore each unit's internals per query.

Now you're ready: Hydra applies this classic idea at the granularity of whole eBPF programs, with SMT doing the combining.
5BPF helper functions — and why they break symbex▾

eBPF programs call into the kernel via helper functions (e.g., adjusting packet headroom, checksumming). Symbex tools can't run real kernel code, so they substitute hand-written "stub" models of each helper. If a stub is incomplete (missing error paths), every program that calls it inherits the gap.

Now you're ready: Hydra's "accuracy" problem is entirely about making these helper stubs faithful to the real kernel.
6SMT solving as "does a satisfying input exist?"▾

An SMT solver takes a logical formula over symbolic variables and either finds a concrete assignment that satisfies it, or proves none exists. Symbex path conditions are exactly such formulas — feed the solver the conjunction of two programs' path conditions plus a violation predicate, and it either hands back a concrete counterexample or confirms no violation is possible.

Now you're ready: this is literally Hydra's "stitching" step — one SMT query per chain-level question.
The whole story in one place

Hydra in a nutshell

The problem, the fix, and why it scales.

Existing eBPF verifiers (ebpf-se, DRACO) run symbolic execution on one program — or worse, one inlined monolithic chain — at a time. Both large single programs and the combinatorial space of chains (a depth-5 chain with 5 variants per slot already has 5⁵ = 3,125 materializations) blow past what symbex can afford; a single depth-5 chain of real programs times out at 10 minutes, and a single large program (Mizar) takes days.

Hydra's fix reframes verification at the granularity of program graphs: symbolically execute each program exactly once, in isolation, producing per-path summaries (observation + path condition + verdict). A deployment's chains are then just paths through a graph of these already-summarized nodes, and answering a cross-program query — "can program B overwrite what program A wrote?" — becomes a single SMT query that stitches the relevant summaries over a shared symbolic input, rather than a fresh symbex run.

Two more optimizations make this fast in practice: query-aware pruning discards, before symbex even runs, any part of a program's control-flow graph that provably can't reach the queried observation; and summary caching means a program symbexed once for a given query is reused across every chain that program appears in for that same query — a different query needs its own pruning-and-symbex pass.

Separately, Hydra tackles accuracy: BPF helper models — previously hand-written and incomplete — are instead synthesized by an LLM from kernel source, then every emitted path is replayed through the real kernel via BPF_PROG_TEST_RUN with kcov tracing; only paths whose kernel fingerprint matches the model are trusted.

The payoff: across 12 programs and 27 synthetic program graphs, Hydra matches the monolithic baseline's verdict on every chain, with aggregate speedups from ~80× (cold) to ~1,506× (hot), and its kcov-validated helper models enumerate 2.5–6× more kernel-confirmed paths per helper than ebpf-se's manual stubs.

🍯 Key takeaways

  • Verify program graphs, not single programs and not inlined monolithic chains.
  • Symbex each program once per query; reuse that summary across every chain sharing the same query (compositional symbex).
  • Query-aware pruning cuts each program's CFG down to only what can affect the query, before symbex runs.
  • Chain-level questions become one SMT query stitching summaries over a shared symbolic input — sound only on chains where no program's behavior is steered by an earlier program's write ("faithful" chains).
  • BPF helper models come from an LLM + kernel source, validated path-by-path via BPF_PROG_TEST_RUN + kcov, not hand-written guesses.
  • Result: verdicts match a monolithic baseline exactly, 80×–1,506× faster, with 2.5–6× more validated helper paths.
Five everyday pictures

How to think about Hydra

Each stands alone; every card ends with where it breaks.

The core idea · Compositional symbex

Translating a phrasebook once

You don't re-translate "hello" from scratch every conversation — you translate it once, keep the phrasebook, and reuse the entry every time it comes up. Hydra symbexes each program once, keeps its "phrasebook" of path summaries, and reuses it for every chain that program appears in.

Where it breaks: a phrasebook entry never changes meaning with context; a program's paths can in principle be steered by an upstream write, which is exactly the "faithfulness" caveat Hydra checks for before trusting the stitch.
Speed · Query-aware pruning

Skipping rooms that don't have the fire

A fire marshal checking "did the fire reach room 5" doesn't inspect every room in the building — only rooms with a path to room 5. Hydra prunes any code path that provably can't reach the queried observation (e.g., a write to skb->mark) before symbex even explores it.

Where it breaks: pruning is query-specific — a program pruned for one query must be re-pruned (and re-symbexed) for a different observation, so the saved summary isn't universal across all possible queries.
Stitching · Shared symbolic input

Two witnesses, one interrogation room

Ask two witnesses about the same event, using the same set of facts on the table, and see if their stories contradict. Hydra's SMT query does this: it hands program A's path condition and program B's path condition the same symbolic input and asks whether a satisfying assignment exists where the query's violation predicate holds too.

Where it breaks: real chains don't share a static "event" — program B actually runs on the packet after A has modified it. Hydra's shared-input shortcut is only exact on "faithful" chains where no program's branching is steered by an earlier write.
Accuracy · kcov-grounded helper models

A rumor, checked against the security footage

An eyewitness account (the LLM's guess at a helper's behavior) might be right, exaggerated, or missing a detail. You don't take it on faith — you replay the actual security footage (BPF_PROG_TEST_RUN + kcov) and only believe the parts of the story the footage confirms.

Where it breaks: the footage itself is imperfect — BPF_PROG_TEST_RUN doesn't reproduce the full kernel environment (e.g., no skb clones), so some real kernel paths can never be confirmed or refuted this way.
Invariant execution · Silent bypass

A security checkpoint someone can slip past

If a checkpoint only runs when an earlier gate passes, and the earlier gate's rules quietly change, someone who used to always pass through both might now bypass the second one entirely — undetected, since nothing crashed. Hydra's Invariant Execution query proves whether a must-run program (e.g., stats) can be skipped by an upstream drop, for some concrete input.

Where it breaks: the query only reasons over the deployment graph's declared chains; it can't catch a chain nobody told Hydra about.
The full explanation

How it actually works

The workflow, stitched together section by section.

1 · The problem — one giant program, or one at a time

Prior symbex verifiers (ebpf-se, DRACO) either verify a single program, or — if adapted to chains — inline every materialization of the chain into one monolithic program and symbex that. Both hit path explosion: a single depth-5 chain of real (katran-sized) programs times out at 10 minutes; a single large program (Mizar, ~2,000 LoC) takes days in KLEE.

2 · Per-program symbex with query-specific instrumentation

For a given query class (Table below), Hydra instruments each program so KLEE emits, per path: (i) the query-relevant observation (e.g., a write flag for a shared field), (ii) the path condition, (iii) the path's verdict. Each program is symbexed once, in isolation — its summaries attach to its node in the deployment graph and are cached for reuse.

QueryAsks
No OverwritesIs there an input where a later program overwrites an earlier program's write to a shared field (e.g., skb->mark)?
Parallel InvarianceDo two variants of a program, deployed at the same chain slot, ever return different verdicts on the same input?
Invariant ExecutionIs there an input where a predecessor terminates the chain before a must-run program executes?

3 · Query-aware pruning — don't explore what can't matter

Before symbex runs, Hydra computes a backward reachability slice over each program's CFG from the queried observation (e.g., the write to skb->mark) and marks unreachable basic blocks for pruning. KLEE then symbexes only the pruned bitcode — producing solely the paths relevant to the query, which is what keeps single-program symbex tractable even for large real code.

4 · Soundness of the stitch — "faithful" chains only

In a real chain, program B runs on the state A actually wrote — not just on a shared abstract input. Hydra statically checks, from the pruning slice, which fields each program may write and which fields steer its branches. If no program in a chain is steered by a field an earlier program may have written, the chain is faithful: the shared-input stitch provably yields the same verdict as a true write-carrying execution. Hydra refuses to verify chains it cannot certify as faithful this way (write-propagation is future work).

5 · Faithful BPF helper models — LLM draft, kernel-checked

For each helper, an LLM drafts a model from verbatim kernel source. Every path the model emits is replayed as a concrete input through BPF_PROG_TEST_RUN against a real, kcov-enabled kernel; if the kernel's basic-block fingerprint matches the model's predicted path, it's committed as validated. Unmatched paths are flagged back to the LLM for the next refinement round rather than trusted.

# per helper, per LLM-emitted path
input = synthesize_concrete_input(path)
kernel_trace = BPF_PROG_TEST_RUN(helper, input)  # kcov-instrumented kernel
if kernel_trace.fingerprint == path.predicted_fingerprint:
    commit(path)              # kcov-validated → usable by KLEE
else:
    flag_for_refinement(path)  # hallucination, or unreproducible by the harness
💡
Why this beats hand-written stubs: a manual stub is a guess frozen at write time; the LLM+kcov loop grounds every accepted path in an actual kernel execution, catching error-return codepaths (e.g., bounds failures in bpf_xdp_adjust_head) that hand-written stubs routinely omit.
Follow the numbers

Worked examples

Four traces using the paper's own figures.

① Why the search space explodes without decomposition

A chain slot has 5 possible program variants, and a chain has depth 5 (5 slots). How many distinct chain materializations exist?

  1. Each of the 5 slots independently picks 1 of 5 variants.
  2. Total materializations = 5 × 5 × 5 × 5 × 5 = 5⁵ = 3,125.
  3. Meta's real fleet is worse: up to 10 variants per program across 20 kernel versions — the paper calls this "far below" what real deployments can reach.
  4. A monolithic verifier must inline and symbex each of these 3,125 chains separately — this is exactly what compositional reuse of per-program summaries avoids.
🍯
Insight: the combinatorics come from chains, not from any single program — which is precisely why Hydra's unit of reuse is the program, not the chain.

② Helper coverage: the "2.5–6×" claim, per helper

Fig. 1b gives kernel-validated path counts for three helpers, ebpf-se vs. Hydra:

  2. Aggregated across the full pipeline: the LLM emits 27 candidate paths total against ebpf-se's 7 (≈3.9× overall); of those 27, 23 are kcov-validated and 4 remain unconfirmed by the test harness.
💡
The gap is concentrated in error-handling paths ebpf-se's manual stubs simply never modeled (e.g., bounds-check failures) — not in the common-case success path both tools agree on.

③ Where the cold→warm→hot speedup actually comes from

Median speedups: cold 15×, warm 53×, hot 284× (aggregate: 80×, 282×, 1,506×). Why does the same algorithm get faster across modes?

  1. Cold re-symbexes every program for every chain — the 15× already comes from decomposing the chain into per-program symbex runs (rather than one monolithic run) plus query-aware pruning shrinking each of those runs.
  2. Warm symbexes each (program, version) pair once per deployment graph and reuses the cached summary for every chain that graph contains — most of the 53×/15× ≈ 3.5× extra gain is this reuse, since real graphs reuse the same programs across many chains.
  3. Hot moves symbex entirely off Hydra's critical path (precomputed by CI/CD whenever a program is built) — the reported 284×/1,506× measures only the SMT-stitching cost, which is orders of magnitude cheaper than any symbex.
🍯
Insight: the three modes aren't different algorithms — they're the same compositional pipeline with progressively more of the (expensive, reusable) symbex step amortized away.

④ Deciding if a chain is safe to stitch (faithfulness)

Chain: fw → lb → stats. fw may write skb->mark; lb's branches are steered by skb->mark; stats only reads counters it owns.

  1. Compute, per program, the fields it may write (from the pruning slice) and the fields that steer its branches.
  2. fw writes skb->mark. lb is steered by skb->mark — a field an earlier program (fw) may have written.
  3. This chain fails the faithfulness check: lb's real execution may follow a branch the shared-input stitch never considers (since the stitch doesn't simulate fw's write flowing into lb's input).
  4. Hydra declines to verify this chain via stitching and reports it as out of scope — not a false "safe" verdict.
💡
This is the honest trade Hydra makes: fast, exact verdicts on faithful chains, explicit refusal (not silent approximation) elsewhere. Write-aware stitching for exactly these chains is listed as future work.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A team adds a new program to a chain and wants to re-verify all affected properties. Does Hydra need to re-symbex every program in the chain?
Show answer
No — only the new program needs symbex. Every other program's summary is already cached from prior runs (compositional symbex) and is simply re-stitched via SMT with the new program's summary.Misconception: that "re-verifying a chain" means re-running symbolic execution on the whole chain. Compositional reuse means only the changed unit is re-analyzed.
Problem 2 · medium
Two ebpf-se helper stubs enumerate 2 and 1 paths respectively; Hydra's kcov-validated models find 7 and 6 for the same helpers. Compute both per-helper ratios and check they fall in the paper's claimed range.
Show answer
7/2 = 3.5×, 6/1 = 6.0×. Both fall inside the paper's reported 2.5–6× range (and 6.0× is the top of that range).Misconception: that "2.5–6×" is an average across all helpers rather than a per-helper spread — the paper reports it as a range because different helpers gain differently, not a single uniform multiplier.
Problem 3 · hard
A chain has program A writing field F, and program C (later in the chain) branching on F, with program B in between not touching F at all. Is this chain faithful?
Show answer
No. Faithfulness requires that no program in the chain is steered by a field an earlier program may have written — B being a no-op on F doesn't matter, since C is still steered by A's write. Hydra would decline to verify this chain via the shared-input stitch.Misconception: that only adjacent programs' write/read interactions matter. The steering relationship can skip over intermediate programs entirely.
Problem 4 · medium
Why does query-aware pruning need to run per-query rather than once per program?
Show answer
Pruning discards CFG blocks that can't reach the specific queried observation (e.g., a write to one field). A different query cares about a different observation, so the reachable/prunable blocks differ — a slice computed for "does this write skb->mark" doesn't tell you what's reachable for "does this call bpf_redirect."Misconception: that pruning is a one-time program simplification like dead-code elimination. It's query-relative, not a universal program transformation.
Problem 5 · easy
Hydra reports UNSAT for a No Overwrites query on some chain. What does that mean operationally?
Show answer
No input exists, on any chain the deployment graph permits, that causes a later program to overwrite the queried field after an earlier program wrote it — the property provably holds across the whole deployment, not just tested cases.Misconception: that UNSAT just means "we didn't find a counterexample" (like a fuzzer running out of time). SMT UNSAT is a proof of unsatisfiability, not an absence of evidence.
Problem 6 · medium
BPF_PROG_TEST_RUN doesn't reproduce skb clones. What's the consequence for the helper-modeling pipeline, and is it a correctness bug in Hydra?
Show answer
Some real kernel paths (those only reachable through skb-clone-dependent behavior) can never be confirmed or refuted by the validation harness — they stay permanently "unconfirmed," neither trusted nor discarded. It's not a correctness bug in Hydra's stitching logic; it's an acknowledged gap in the Oracle used for helper validation, explicitly listed as a limitation.Misconception: that an unconfirmed path is treated as validated by default. Hydra only commits paths whose kernel fingerprint actually matches — unconfirmed paths are excluded, not optimistically accepted.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does Hydra verify — safety or correctness?▾
Correctness (functional/semantic properties across chains), not memory safety — that's already the in-kernel verifier's job. Hydra checks things like "does a later program overwrite an earlier one's write" or "can a must-run program be silently skipped."
Q2Why can't the in-kernel verifier just do this?▾
It admits and checks programs one at a time, and only for memory safety, bounded loops, and termination — it has no notion of a chain, of another program's behavior, or of semantic (not just safety) properties.
Q3What is a "faithful" chain, and why does it matter?▾
A chain where no program's branching is steered by a field an earlier program may have written. On faithful chains, stitching summaries over one shared symbolic input gives exactly the same verdict as a real write-carrying execution would. Hydra refuses to verify chains it can't certify as faithful.
Q4Does Hydra replace ebpf-se or DRACO?▾
Hydra reuses ebpf-se's libbpf-stubbed symbex backend but replaces its manually-written helper stubs with kcov-validated ones, and adds the graph-level compositional layer neither ebpf-se nor DRACO has — both of those tools verify a single program (or inlined chain) at a time.
Q5How is a violation reported to an operator?▾
As a concrete SMT model: actual packet bytes plus any needed initial BPF map state, which the operator can literally replay locally to reproduce the violation — not just an abstract "this could fail."
Q6Is the LLM in Hydra's helper-modeling loop trusted directly?▾
No. Every path it proposes is treated as a hypothesis, replayed as a concrete input through the real kernel via BPF_PROG_TEST_RUN with kcov, and only committed if the kernel's execution fingerprint matches. Unmatched paths are neither used nor discarded — they're flagged for the LLM's next refinement pass.
Q7What's the difference between cold, warm, and hot deployment modes?▾
Cold re-symbexes every program for every chain (15× median speedup already, from per-program decomposition plus pruning — Hydra's "pushdown" and per-program symbex amortization, not caching). Warm symbexes each program once per graph and reuses the summary (53× median). Hot precomputes summaries in CI/CD entirely off Hydra's critical path (284× median). Monolithic KLEE has no equivalent reuse and is always "cold."
Q8Does Hydra scale to Meta-scale deployments (≥180 programs/host)?▾
The paper's evaluation (27 graphs, depth 3/5/7, up to 4 variants/slot) is explicitly "far below" Meta's reported complexity — the authors present it as a scalable prototype and preliminary result, not a claim of full production-scale validation.
Q9What's left for future work?▾
Write-aware stitching for chains that fail the faithfulness check (currently deferred entirely), and an automated query-compilation engine so new query classes don't require hand-written SMT formulas and pruning targets.
