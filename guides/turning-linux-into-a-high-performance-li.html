Running Linux as a library, not a relay race

Kernel-bypass systems usually get built from scratch, then spend years catching up to Linux's syscall coverage. Flux instead links Linux itself into the application — and finds that Linux was never the bottleneck. The runtime around it was.

📄 "Turning Linux into a High-Performance Library OS with Flux" · Tian et al. 🎓 Assumes some OS/scheduling background — primers cover the rest ⏱ ~30 min read
🐧

Keep Linux's subsystems INTACT; fix the SURROUNDING RUNTIME — single-level scheduling, user interrupts, and a process abstraction that keeps direct-call syscalls even under fork.

1What a library OS is▾

Normally an application asks the kernel for services (files, sockets, threads) through a syscall, which traps into a separate, protected kernel. A library OS instead links those OS services directly into the application's own address space, so a "syscall" can become an ordinary function call — no trap, no context switch.

This is what makes kernel-bypass fast: DPDK/SPDK already skip the kernel for devices; a library OS skips it for everything else too.

Now you're ready: Flux's whole pitch is "make the library OS be Linux" instead of writing a new one.
2Building a library OS from scratch vs. reusing Linux▾

Systems like Caladan and Junction build their own scheduler, TCP stack, and syscall layer from scratch. This is fast and clean, but every Linux feature an application needs (signals, futex, fork, /proc) must be reimplemented and validated by hand — expensive, and never fully done.

The alternative: link the actual Linux kernel source in as a library (this is LKL's idea), and get its mature syscalls, file systems, and drivers for free.

Now you're ready: Flux takes the reuse path, but redesigns everything around Linux, not Linux itself.
3Threads, processes, and address spaces▾

A thread is a schedulable stream of execution; several threads can share one address space (memory mappings + page tables), which is what makes them "the same process." A process in Linux is represented by mm_struct (the address space) plus one or more task_structs (the threads running in it).

fork() creates a new address space — a logical copy of the parent's — while clone() with CLONE_VM creates a new thread that shares the existing one.

Now you're ready: the paper's central puzzle is: how do you get real, isolated fork() address spaces inside a library OS that wants everything in one address space for fast function-call syscalls?
4Copy-on-write fork▾

Naively, fork() would copy the entire parent address space — slow for large processes. Linux instead marks both parent's and child's pages read-only and shares the same physical pages (copy-on-write); only when either side writes a page does the kernel copy it. Most forked children barely touch most pages, so this is cheap.

vfork() is a lighter but restricted cousin: it doesn't copy anything, but blocks the parent until the child calls execve or exits — fine for launching a new program, useless for Redis's fork-to-snapshot pattern.

Now you're ready: Nginx workers and Redis persistence both need real COW fork, not vfork — this is exactly what prior library OSes (Junction) can't offer.
5Preemptive scheduling: timers and IPIs▾

To time-slice fairly and wake sleeping threads promptly, an OS scheduler relies on periodic timer interrupts and, on multicore systems, inter-processor interrupts (IPIs) — one core telling another "reschedule now." Both normally arrive through hardware interrupt delivery straight into kernel mode.

In user space, there's no kernel mode to interrupt into by default — so a user-space OS must either poll for these events or find a way to receive real hardware interrupts.

Now you're ready: this is precisely the gap that Intel UINTR fills, and that Flux is built around (primer 7).
6Kernel-bypass I/O (DPDK, SPDK)▾

DPDK and SPDK let user-space code drive network and storage devices directly via polling, instead of routing every packet or block I/O through kernel drivers and interrupt handlers. A dedicated core (or threads) continuously polls device queues, cutting per-operation latency from microseconds of kernel overhead to near-hardware speed.

Now you're ready: Flux wires DPDK/SPDK in as Linux device drivers — so ext4 and the TCP stack run unmodified on top of kernel-bypass hardware access.
7Intel User Interrupts (UINTR)▾

UINTR is a hardware feature that lets one user-space thread send an interrupt directly to another user-space thread — no kernel trap on either the sending or receiving side. A receiver registers a handler; a sender can target it with a lightweight instruction.

Now you're ready: Flux uses UINTR for both its timer ticks and its cross-core IPIs — this is the mechanism that lets Linux's scheduler live entirely in user space without polling.
8Memory Protection Keys (MPK)▾

MPK tags pages with one of 16 protection-key IDs; a per-thread register (PKRU) then enables or disables read/write access per key, entirely in user mode — no page-table edit, no kernel entry. Flipping PKRU is a handful of cycles.

Now you're ready: Flux uses MPK to wall off its own kernel/runtime memory from the (untrusted) application, inside the very same address space — isolation without a syscall.
9TLB shootdowns and address-space switches▾

Switching which address space a core is executing in means reloading the page-table root (CR3 on x86) and invalidating stale TLB entries — a privileged operation normally reserved for the kernel. Multi-process support therefore always touches something a pure user-space program cannot do alone.

Now you're ready: this is why Flux still needs a tiny trusted kernel module — not to run Linux's logic, but to perform the handful of genuinely privileged operations (switching CR3, releasing page tables) that fork requires.
10Tail latency and SLOs▾

Datacenter services are often judged not by average latency but by a tail percentile (commonly p99 — the latency below which 99% of requests complete) against a fixed target (SLO). A system that's fast on average but has a slow scheduler can still blow its p99 budget if a request gets stuck behind someone else's timeslice.

Now you're ready: Flux's Memcached and Nginx results are reported against a 100 μs p99 SLO — throughput numbers only count if that latency bar is met.
The whole story in one place

Flux in a nutshell

Why LKL is slow, what Flux changes, and how the pieces click together.

The authors start with a diagnostic question: is Linux-as-library-OS inherently slow, or is something around it slow? They profile LKL and find the answer is the latter. LKL pairs every host thread with an internal "stub thread," serializes everyone behind one global lock, and — because it has no real interrupts in user space — polls for timers instead of receiving them. A single syscall handoff between two threads already costs >2 μs, and timer wakeups exceed 80 μs. None of that is Linux's fault; it's the two-level scheduling glue bolted around it.

Flux (Fast Linux User eXecution) keeps Linux subsystems largely untouched and fixes exactly that glue. It runs single-level scheduling: each host thread maps to one physical core and the Linux scheduler inside Flux makes every decision directly — no host scheduler, no stub threads. It replaces polling with Intel UINTR for timers and IPIs, giving microsecond-scale preemption. And it solves the harder problem — Linux-style fork with copy-on-write — by decoupling address-space management from thread scheduling: a small trusted kernel module performs the few genuinely privileged operations (switching page tables, releasing an mm_struct), while Flux itself keeps deciding who runs where.

The payoff: Flux passes 92.2% of LTP (vs. Linux's 95.6%, and far above gVisor's 41.6%), improves Nginx throughput by up to 18.5× over Linux with real multi-worker fork, and gets within 4% of Junction's from-scratch Memcached throughput under a 100 μs p99 target — all while reusing Linux's mature codebase instead of rebuilding it.

🍯 Key takeaways

  • LKL's bottleneck is the runtime around Linux (two-level scheduling, polling), not Linux subsystems themselves.
  • Flux uses single-level scheduling: Linux's own scheduler runs directly on pinned host threads.
  • UINTR replaces host-mediated polling for timers/IPIs — microsecond, not 80 μs, wakeups.
  • A new process abstraction decouples address-space switching (needs privilege) from thread scheduling (stays in Flux) — enabling real COW fork without losing direct-call syscalls.
  • MPK isolates Flux's own kernel/runtime from the untrusted application inside one address space, with no syscall on the hot path.
  • Result: 92.2% LTP pass rate, up to 18.5× Nginx throughput over Linux, within 4% of Junction on Memcached.
Seven everyday pictures

How to think about Flux

Each stands alone — read in any order. Every card ends with where the picture stops being true.

Two-level vs. single-level · Scheduling

One dispatcher vs. a relay of clerks

LKL is like routing every request through a clerk who takes a number, waits for a single shared counter, then hands off to a second clerk who represents you internally. Flux is one dispatcher who is the counter — your request goes straight to the front of the line, because your host thread and your Linux thread are the same thing.

Where it breaks: the "one dispatcher" only works because each host thread is pinned to one physical core; if the host OS ever migrated that thread mid-flight, the analogy — and the design — would need a second layer back.
UINTR · Interrupt delivery

Checking a clock vs. a direct tap on the shoulder

LKL's timer is a clock on the wall you must keep glancing at (polling an internal pending bit) — so you only notice it's time to act whenever you happen to look. UINTR is someone reaching over and tapping you on the shoulder the instant it matters. That's the difference between an 80 μs-plus polled wakeup and a microsecond-scale delivered one.

Where it breaks: the tap only works if you're wearing the right badge — UINTR is Intel-specific hardware. Without it, Flux falls back to host-mediated delivery, i.e. back to a version of "checking the clock."
Process abstraction · Shared vs. private mappings

A shared office wing with private offices

Flux's runtime, kernel stacks, and TLS live in a shared wing every process can see (so switching "processes" is fast — just walk down the hall). Each process's application memory sits in its own private office, page-table-isolated. fork makes a new private office with copy-on-write furniture; exec just redecorates the current one.

Where it breaks: real offices don't need a landlord's permission to switch which door you're in — but Flux does, because changing which private office is "active" means reloading page tables, a privileged operation the kernel module must perform.
MPK · Isolation without a trap

A badge that unlocks rooms, not new locks

Application code and Flux's kernel/runtime sit in the same address space — like two departments in one open-plan building. Instead of building walls (separate address spaces, which would cost a page-table switch), MPK gives each thread a badge (PKRU) that's instantly reprogrammed at each door (call gate) to allow or deny entry to the Flux wing — no security desk (kernel trap) involved.

Where it breaks: a badge system only has 16 possible badge types (MPK's 16 keys) — fine for 3 domains here, but it's why systems like Vessel that give each process its own key run out fast without virtualization tricks.
Kernel module · Privileged concierge

A concierge who holds the master keys

Flux makes almost every decision itself — who runs next, which process to switch to — but it can't physically reload a page-table root or free an mm_struct from user space. So it delegates just those actions to a tiny, trusted concierge (flux_mm) with the master keys, called through a narrow ioctl surface, while Flux keeps the guest list and schedule entirely to itself.

Where it breaks: a concierge who's slow to respond becomes a bottleneck; every mmap/brk and address-space switch still crosses into the module, which is why memory-mapped page faults (routed through host signals) remain one of Flux's acknowledged weak spots (§7).
Reuse vs. rebuild · Development cost

Renovating a house vs. building one from blueprints

Building a library OS from scratch (Caladan, Junction) is drafting new blueprints — clean, but every room (syscall, semantic corner case) must be designed and code-inspected by hand, and some rooms (full fork, /proc, complex ioctl) get skipped because they're expensive. Flux renovates the existing house: it keeps Linux's plumbing and wiring (subsystems) and only remodels the entryway and hallways (scheduling, syscall entry, process switching).

Where it breaks: a renovation still needs to touch structural walls sometimes — Flux does modify 40,272 lines across the arch layer, syscall paths, and drivers; it isn't a zero-change wrapper.
SLO evaluation · Throughput under a latency cap

Judging a highway by its worst traffic jam, not its average speed

A road that's fast on average but occasionally gridlocks for a minute is a bad commute. Flux and Junction are compared not by raw throughput but by how much traffic they can carry while the worst 1% of trips still finish inside 100 μs — the p99 SLO. A system can "win" on average speed and still lose this comparison if its tail is long.

Where it breaks: the analogy hides that Linux isn't just "occasionally slow" here — its default scheduler misses the SLO across most of the throughput range (Fig. 7), not just at rush hour.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals, and one live data explorer.

1 · The problem — two-level scheduling in LKL and rkt-io

LKL pairs every application (host) thread with an internal stub thread and serializes all of them behind one global CPU lock — a single-core, non-preemptive model. Handing off from one host thread's syscall to another's requires acquiring that lock and performing an internal task switch before the syscall handler even runs; on the authors' platform this whole path costs >2 μs. rkt-io adds SMP via lthread-based scheduling, but its per-core schedulers share a single global run queue — the very contention point the paper identifies — and still route cross-core IPIs through a dedicated lthread, yielding worse than 10 μs tail wakeup latency (§6.6).

🌱
Where this bites your CXL/tiering intuition: this is structurally the same tax as a software page-migration daemon that has to go through a heavyweight coordination path instead of touching hardware directly — the cost isn't in the "hot/cold" decision logic, it's in the plumbing that delivers the signal.

2 · Single-level scheduling with UINTR

Flux pins each host thread to a physical core and boots Linux's SMP path directly on it — no virtual CPU abstraction, because one host thread is one physical core. After boot, thread selection, wakeup, and context switching happen entirely inside Flux's Linux scheduler. UINTR delivers timer ticks (from one dedicated core) and inter-core IPIs (CALL_FUNCTION, RESCHEDULE) directly to target cores as hardware interrupts, decoded and dispatched by Flux's own handler — no polling loop anywhere in the critical path.

// switch_to (simplified from Listing 1) — thread + address-space switch
switch_to(prev, next) {
  switch_stack_and_callee(prev, next);
  cpu.current = next;
  // UINTR may interrupt mid-instruction, leaving xstate live
  if (prev.from_uintr && !prev.xstate_loaded) save_xstate(prev);
  if (is_user(next) && cpu.proc_key != next.proc_key)
    flux_switch_mm(cpu.proc_key, next.proc_key);   // only privileged step
  switch_tls_base(prev, next);
}
💡
Why this matters: everything in switch_to runs in Flux, except the single call into the kernel module when the address space actually changes. Thread-to-thread switches within one process never touch the module at all.

3 · Multi-process support — the process abstraction

Flux decouples address-space management from thread scheduling. All writable Flux state (runtime, heaps, kernel stacks, TLS) is mapped shared across every process's address space; only application memory is private. This means a process switch is just an address-space switch — Flux's own state is already visible on the other side.

  1. Share mappings. Flux's flux_mm kernel module converts the Flux runtime's private (MAP_PRIVATE) mappings to shared (MAP_SHARED) ones at startup, and intercepts mmap/brk to keep new Flux allocations shared too.
  2. Fork. copy_thread either inherits the caller's proc_key (for a same-process thread) or allocates a new host mm_struct via COPY_MM for a real fork — a page-table-level copy-on-write duplicate of the current address space.
  3. Switch. Flux compares a per-CPU proc_key against the next thread's; on mismatch, it calls into the module to reload page tables. Kernel-thread stacks stay in the shared region, so address-space switches happen only when scheduling user threads.
  4. Exec. Flux preserves the shared Flux mappings, loads the new ELF image into the current (private) address space, and drops the old application's private mappings via CLEAN_MM.
🍯
The key trick: because Flux's own state is shared, a fork doesn't need to duplicate Flux itself — only the small module operation (COPY_MM) and the application's private pages are new. That's what keeps direct-call syscalls alive even for a multi-process Nginx.

4 · Isolation — MPK domains and call gates

Because application code and Flux share an address space, Flux needs a wall that doesn't cost a kernel trap. It defines three MPK domains per address space: an Application Domain (untrusted app code), a Flux Domain (kernel/runtime, unreadable and unwritable while application code runs), and a Shared Domain (exchange state the app may read but only Flux may write, e.g. the syscall entry address and vDSO). Syscall and UINTR entry go through a call gate that flips PKRU via WRPKRU; the ELF loader and a scan of the binary prevent the application from forging that instruction itself, and a syscall filter in flux_mpk blocks any host syscall issued while PKRU doesn't grant Flux-Domain access.

5 · Network and storage fast paths

By default Flux runs Linux's own network stack over a DPDK driver it implements inside the Flux kernel: a dedicated core polls NIC queues and dispatches packets to worker cores via IPC. To cut latency further, Flux adds a TCP fast path (in the spirit of Caladan/Junction) while leaving ARP/ICMP on the stock Linux stack, and keeps pollable sockets so epoll still works unmodified. On storage, an SPDK-backed block driver lets ext4/XFS submit I/O directly to SPDK queue pairs, with completion-aware polling and DMA-capable page allocation to avoid extra copies.

Stacking these optimizations — DPDK dispatch, the TCP fast path, disabling preemption during polling, idle-state UMWAIT polling, zero-copy buffers, speculative polling before blocking, and per-CPU buffer caches — improves Flux's own Memcached throughput by 3.65× end-to-end (0.8 → 2.92 Mops/s), closing most of the gap to Junction (Fig. 10).

⚠
Honest limitation: device interrupts still route through host eventfd, and page faults on mmap-backed files are injected via host signals — both add real host transitions. Flux is explicit that this makes fault-heavy mmap workloads (e.g., memory-mapped databases) substantially slower under its current design (§7).
Follow the numbers, step by step

Worked examples

Four traces through the paper's real numbers — compatibility, primitive speedups, application-level wins, and the code footprint.

① Reconstructing the LTP compatibility math

The paper reports Flux passes 92.2% of LTP out of 2,563 total tests, with 131 skipped. Does the arithmetic hold together?

  1. Non-skipped tests = 2,563 − 131 = 2,432.
  2. Of those, 2,362 pass outright (the reported passing count).
  3. Pass rate over the full suite = 2,362 / 2,563 = 92.15% ≈ 92.2% — matches the headline number.
  4. The remaining 70 non-skipped tests break down as 22 functional failures + 18 broken + 6 timeouts + 24 with no explicit pass evidence = 70, which checks out (2,432 − 2,362 = 70).
  5. Compare: native Linux passes 2,450/2,563 = 95.6%; gVisor only 1,066/2,563 = 41.6%.
🍯
Insight: Flux gives up about 3.4 points of pass rate versus native Linux — mostly cgroup v1 debug-controller tests and host-integration corner cases — while reusing Linux's actual syscall table (345 of 349 valid syscalls) rather than reimplementing a subset from scratch.

② Reading Table 7 — how much does single-level scheduling buy?

Using the raw cycle counts, compute Flux's speedup over native Linux for a few primitives.

  1. yield (thread switch): Linux 2,548 cycles, Flux 573 cycles → 2,548 / 573 ≈ 4.4× faster.
  2. gettid (trivial syscall): Linux 296 cycles, Flux 34 cycles → 296 / 34 ≈ 8.7× faster.
  3. condvar wait/signal: Linux 6,893 cycles, Flux 1,266 cycles → ≈ 5.4× faster.
  4. spawn (thread creation): Linux 13,826 cycles, Flux 3,055 cycles → ≈ 4.5× faster; against rkt-io's 176,890 cycles, that's ≈ 58× faster.
💡
These are the primitives a scheduler touches constantly. The paper reports both these microbenchmark gains and separate application-level wins (Nginx, Memcached) — but it doesn't establish a precise per-request compounding relationship between the two; treat them as complementary evidence, not a derived multiplier.

③ From microbenchmarks to application wins

Do the headline application numbers make sense given the scheduling primitives above?

  1. hackbench (-pPl 10000, an IPC/scheduler stress test): Linux 25 s, Flux 8 s → 25 / 8 = 3.125×, reported as "3×."
  2. schbench p99 wakeup latency (16 cores): Linux 18 μs, Flux 4 μs → reduction = (18 − 4) / 18 = 77.8% ≈ 78%, matching the paper's claim exactly.
  3. Nginx 8-worker throughput: Flux improves it by 18.5× over Linux while keeping p99 latency under the 100 μs SLO — this is the multi-process case, requiring fork-based worker startup and semantics, that Junction's single-address-space design cannot even run.
  4. Redis persistence (fork + COW, ext4): Linux 3.04 s end-to-end, Flux+SPDK 2.86 s → (3.04 − 2.86)/3.04 = 5.9% ≈ 6.1%, matching the paper.
🍯
Insight: the persistence gain (6.1%) is much smaller than the raw fork-primitive gain, because Redis's snapshot time is dominated by object traversal/serialization, not fork itself — a reminder that a fast primitive only helps as much as the workload actually exercises it.

④ Tallying the code footprint

Is "keeping Linux subsystems largely intact" borne out by the line counts in Table 3?

  1. Total modified/added code: summing every module in Table 3 gives 40,272 LOC — confirmed by adding all nineteen entries (7,443 + 3,564 + … + 656 = 40,272).
  2. Largest single module: x86/sched at 7,443 LOC (≈18.5% of the total) — the clock, interrupt handling, and thread switching, i.e. exactly the single-level scheduling machinery.
  3. Arch-layer concentration: six x86/* and related arch modules (sched, crypto, syscalls, mmu, timer, smp) sum to ≈17,453 LOC, over 43% of the total — the paper's claim that "most changes stay in the arch layer" checks out arithmetically.
  4. Portability payoff: the paper reports porting the x86/SMP modules to Linux v6.17 took ~300 LOC and one person-day — under 1% of the total codebase, consistent with most logic living outside Linux's own subsystems.
💡
40K lines sounds large, but it's dwarfed by Linux's own multi-million-line codebase — Flux's entire value proposition is that this 40K buys back performance without reimplementing what Linux already has.

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
True or false: Flux gets its speed by rewriting Linux's scheduler with a new, custom algorithm.
Show answer
False. Flux keeps Linux's own scheduler (EEVDF, unmodified logic) and changes only how it's invoked — single-level, directly on pinned host threads, driven by UINTR instead of host-mediated polling. The scheduling policy is stock Linux.Misconception: that "fast library OS" implies a new scheduling algorithm. Flux's contribution is plumbing, not policy.
Problem 2 · medium
From Table 7: Linux's gettid costs 296 cycles, Flux's costs 34. Redis single-connection SET goes from ~X Kops/s under Linux to 3.5× that under Flux (Fig. 6). Are these two numbers measuring the same thing?
Show answer
No. The 296→34 cycle figure is a microbenchmark of one isolated syscall; the 3.5× Redis figure is an end-to-end application throughput number shaped by many syscalls, network stack behavior, and scheduling under load. They're consistent in direction (both show Flux winning) but shouldn't be multiplied together or treated as the same measurement.Misconception: that a microbenchmark speedup translates 1:1 into application speedup. It's suggestive, not a proof — always check the paper's separate end-to-end number.
Problem 3 · medium
What happens to Flux's timer and IPI delivery on hardware without Intel UINTR?
Show answer
Flux falls back to host-mediated timer and interrupt delivery — closer to what LKL/rkt-io already do — at the cost of additional host transitions and higher wakeup latency (§7). It doesn't stop working, but loses much of its headline advantage on preemption latency.Misconception: that Flux's design is hardware-independent. Its performance story is tightly coupled to Intel x86 features (UINTR, MPK); porting elsewhere needs analogous hardware (the paper mentions RISC-V's Donky for MPK-like isolation).
Problem 4 · hard
Recompute: native Linux passes 2,450/2,563 LTP tests (95.6%). Flux passes 2,362/2,563 (92.2%). If Flux additionally skips 32 tests that Linux does not skip, how many tests does each system attempt, and does skipping fewer tests always mean a higher pass rate?
Show answer
Linux skips 99 tests → attempts 2,563 − 99 = 2,464, passing 2,450/2,464 (99.4% of attempted). Flux skips 99 + 32 = 131 → attempts 2,432, passing 2,362/2,432 (97.1% of attempted). So Flux's pass rate among tests it actually runs is close to Linux's, even though its headline rate over the full suite (92.2%) looks further behind — because it's the denominator (skips) that moved, not just the pass count.Misconception: that skip count doesn't matter when comparing pass rates. Two "pass rate" numbers computed over different denominators aren't directly comparable without checking what was skipped.
Problem 5 · medium
MPK provides only 16 hardware keys. Why doesn't this limit the number of Flux processes, when it does limit systems like Vessel/Pegasus?
Show answer
Flux uses MPK for a fixed, small number of domains per address space (Application, Flux, Shared) — three keys, regardless of how many processes exist — because process isolation itself is handled by separate host page tables (independent mm_structs), not by MPK. Vessel/Pegasus instead try to give each lightweight process its own MPK key within one shared address space, so they run into the 16-key ceiling directly (and need key virtualization to work around it).Misconception: that MPK and page-table isolation are competing techniques. Flux layers them: page tables isolate processes, MPK isolates trust domains within a process.
Problem 6 · hard
Table 7 shows Flux's fork is faster than Linux's on 1 core but the text notes it's slower than native Linux on 4 cores. Why would a library OS's fork ever be slower than the kernel it's built on?
Show answer
Flux maintains two layers of address-space bookkeeping for each process — its own tracking plus the host kernel's real mm_struct (via flux_mm's reference-counted proc structures) — and that extra reference counting and module round-trip adds overhead that shows up more under four-core concurrent forking than on native Linux, which only maintains one layer.Misconception: that "reuses Linux + adds a fast path" implies Flux is faster at literally everything. Multi-process support is explicitly the paper's harder problem, and it says so directly — the win is enabling it at all with good-not-perfect fork cost, not beating Linux on every metric.
Problem 7 · easy
Does Flux require DPDK/SPDK to run at all?
Show answer
No. Flux can run with the native, unmodified Linux network driver and forward device interrupts via host eventfd (the "Base" configuration in Fig. 10) — DPDK/SPDK are optional accelerations layered on top for the fast path, not a hard requirement for Flux to function.Misconception: that "kernel-bypass library OS" always means kernel-bypass devices are mandatory. Flux's core contribution (single-level scheduling, process abstraction) is independent of whether DPDK/SPDK are in use.
Problem 8 · medium
The paper states page faults on mmap-backed files "add substantial overhead" (§7), injected via host signals and taking tens of microseconds. In your own tiering work, what's the closest analogous cost, and why does it matter here?
Show answer
It's structurally the same cost as a first-touch or promotion page fault crossing into a slow, coordination-heavy path — e.g., a minor fault that must go through a host-mediated migration daemon rather than being resolved inline by hardware or a fast in-kernel handler. In both cases, the fault handler's *dispatch* cost (crossing a privilege or process boundary) dominates, not the actual page operation. It matters here because it means Flux is a poor fit, as-is, for mmap-heavy DB engines (LevelDB, LMDB, SQLite with mmap I/O, all cited in §8) until fault delegation gets a lower-overhead path.Misconception: that a fast syscall path automatically implies fast page-fault handling. Page faults in Flux are a separate, still-host-mediated mechanism (host signals + the kernel module), explicitly called out as unsolved.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1Is Flux a hypervisor or a container runtime?▾
Neither. Flux is a user-space process that links Linux in as a library — it shares the application's address space directly, using no hardware virtualization (unlike Dune/IX-style guest-kernel approaches) and no separate sandboxed process (unlike gVisor). It runs as an ordinary process on a conventional host OS or inside a VM.
Q2Why is running Linux in user space hard in the first place?▾
Linux's scheduler assumes it can receive real hardware timer interrupts and IPIs, and that it alone controls page tables. In user space neither assumption holds by default — a naive port must either poll for these events (slow, imprecise) or route them through the host kernel (extra transitions). Flux's core engineering is solving both without giving those semantics up.
Q3What exactly makes LKL slow, if not Linux itself?▾
A two-level scheduling model: every host thread is paired with an internal "stub thread," and all of them serialize behind one global lock with an internal task switch on every handoff — over 2 μs per syscall crossing between threads — plus polling-based timers that miss wakeups by 80+ μs. The Linux subsystems being called underneath are not the bottleneck.
Q4What does "single-level scheduling" actually buy you?▾
It removes an entire layer of indirection: instead of a host scheduler deciding which host thread runs, and then an internal LKL/lthread scheduler deciding which "task" that thread represents, Flux's Linux scheduler makes the one and only decision, directly on a pinned physical core. Fewer decisions, fewer context switches, fewer chances for a wakeup to be delayed.
Q5How does UINTR let user-space code receive interrupts?▾
UINTR is an Intel hardware feature (distinct from software polling) that lets a registered user-space receiver be interrupted directly — the CPU delivers the event to a handler in user mode, without a kernel trap on the critical path. Flux uses it for both periodic timer ticks (sent by one dedicated core) and cross-core IPIs used to force a reschedule.
Q6Why is fork so much harder than everything else Flux does?▾
Flux's whole speed advantage comes from putting the application, Linux, and the runtime in one address space so syscalls are function calls. fork fundamentally needs a second, independent address space with copy-on-write — a genuinely privileged operation (new page tables) that user space cannot perform alone, and that threatens the "one address space" premise everything else relies on.
Q7How does Flux support fork without losing direct-call syscalls?▾
By splitting what's shared from what's private: Flux's own kernel, runtime, and stacks stay shared across every process's address space (so they never need duplicating), while only application memory is private and page-table-isolated per process. A small trusted kernel module (flux_mm) performs just the privileged page-table operations (copy, switch, release) on request.
Q8What is MPK protecting against, exactly?▾
Application code — trusted to run, but not trusted to behave — sharing an address space with Flux's kernel and runtime. MPK prevents that application code from reading or corrupting Flux's internal state or hijacking its control flow, using a per-thread register flip (no kernel trap) instead of a page-table-based wall.
Q9Does Flux support every Linux syscall?▾
345 of the 349 valid syscalls under the evaluated kernel config — everything except modify_ldt, kexec_load, map_shadow_stack, and perf_event_open, which need segmentation, kexec, CET, or perf-monitoring support Flux doesn't provide. 314 of the 345 reuse the stock Linux v6.6 implementation unmodified.
Q10How does Flux compare to Junction, the from-scratch alternative?▾
Junction is faster on some low-level primitives (e.g., its minimal FIFO scheduler beats Flux's yield slightly) and it pioneered the from-scratch approach's syscall breadth (170+). But Junction's single-address-space design can't support real multi-worker Nginx or Redis's fork-based persistence, which Flux handles natively — and Flux gets within 4% of Junction's Memcached throughput under the same latency SLO.
Q11What are Flux's acknowledged weak points?▾
Two, stated directly in the paper: it targets Intel x86 with UINTR specifically (falling back to slower host-mediated delivery elsewhere), and device interrupts plus page faults still route through the host (via eventfd and host signals respectively) — the latter making frequently-faulting mmap-backed workloads substantially slower.
Q12What's left for future work?▾
The paper doesn't enumerate a long future-work list the way some systems papers do, but §7's limitations point directly at it: lower-overhead device-interrupt and page-fault delegation, and eventually non-Intel platform support (the paper notes RISC-V's Donky as a candidate MPK-equivalent).

Core terms
FluxFast Linux User eXecution — a library OS that links Linux into the application's address space with a redesigned scheduling/syscall/process runtime.
Single-level schedulingFlux's model where only Linux's own scheduler (inside Flux) makes decisions, with no host scheduler layered on top.
Two-level schedulingLKL/rkt-io's model: a host scheduler plus an internal (stub-thread / lthread) scheduler, causing extra context switches and lock contention.
UINTRIntel User Interrupts — hardware-delivered interrupts to user-space receivers with no kernel trap; used for timers and IPIs.
Process abstraction (Flux)Decouples address-space management from thread scheduling: shared Flux state + private per-process application memory + host-assisted switching.
proc_keyAn integer identity shared between Flux and the kernel module, mapping to a reference-counted host mm_struct.
flux_mmThe trusted kernel module performing privileged address-space operations (copy, switch, release, clean) on Flux's behalf.
MPK domainsApplication / Flux / Shared — three protection-key regions per address space enforcing isolation without page-table changes.
Call gateThe syscall/UINTR entry trampoline that flips PKRU permissions and validates control flow before running Flux code.

rkt-ioAn enclave-based LKL derivative with DPDK/SPDK and lthread-based multicore scheduling; still two-level internally.
JunctionA from-scratch library OS (built on Caladan) implementing 170+ syscalls; the paper's state-of-the-art performance comparison point.
