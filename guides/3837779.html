Scheduling the measurement itself

Litmus tests hunt for memory-model behaviors that only surface when threads land on separate cores within a few cycles of each other. Default Linux scheduling — and even careful pinning — can silently make that window close.

📄 "Pinning Isn't Enough" · eBPF'26 Workshop 🎓 OS/arch background assumed — fundamentals skipped ⏱ ~18 min read
🎯

Pinning says WHERE a thread may run. It says nothing about WHEN — and litmus tests need both, together, as a gang.

Before you begin

Quick glossary, then five primers

You know OS scheduling and NUMA already — these primers skip that and go straight to what's specific to litmus testing and sched_ext.

Quick glossary

Litmus testA tiny concurrent program designed to surface one hardware-permitted "weak" memory reordering.
SB / MP / LB / 2+2W / IRIWCanonical litmus tests (Store Buffering, Message Passing, Load Buffering, 2+2 Write, Independent Reads of Independent Writes).
TSOx86's Total Store Order memory model — permits SB, forbids MP/LB/2+2W/IRIW.
sched_extLinux scheduling class letting a verified eBPF program implement policy outside the core scheduler.
DSQDispatch queue — sched_ext's unit for holding runnable tasks before they land on a CPU's local queue.
GangThe set of threads belonging to one test instance that must be co-scheduled.
CASCompare-and-swap — the atomic op used here to claim CPU reservations and activation locks.
Sense barrierA non-blocking, spinning barrier — tight enough for cycle-scale alignment, unlike a blocking barrier.
1Why a litmus test needs a scheduling accident to succeed▾

SB's weak outcome requires thread 0's store-then-load and thread 1's store-then-load to overlap on different cores within a handful of cycles. The test code can spin tightly, but it cannot ask the OS "please run me now, on a free core, next to my sibling." That request has always been implicit — and unenforced.

Now you're ready: everything in this paper is about making that implicit request explicit.
2Memory models in one line▾

x86-TSO permits SB but forbids MP, LB, 2+2W, and IRIW. ARM and POWER permit all of them. A litmus tool's job is to observe a forbidden outcome if the hardware allows it — absence of evidence isn't evidence of absence, so observation rate is the whole game.

Now you're ready: "the test didn't trigger" can mean "the hardware forbids it" or "the scheduler never gave it a chance" — this paper is entirely about the second case.
3sched_ext: a scheduler as a loadable, verified eBPF program▾

The kernel calls into a small set of callbacks — select_cpu, enqueue, dispatch, running, stopping — and the eBPF program decides placement and timing. Tasks move through dispatch queues (DSQs) on their way to a core's local queue. No kernel rebuild, no reboot.

Now you're ready: both schedulers in this paper are just these five callbacks, specialized for one invariant: keep a gang together.
4taskset is a nametag, not a seating chart▾

Static affinity restricts which CPUs a thread may use. It says nothing about whether its gang-mates are running at the same time. For one test alone, this rarely matters — Linux will usually find a moment to co-run two threads. Once several tests compete for the same cores, it matters a great deal.

Now you're ready: the whole paper is a case study in a requirement affinity cannot express.
5Gang scheduling, repurposed▾

Gang scheduling (Ousterhout, 1982) usually exists to stop a parallel job's threads from spin-waiting on descheduled peers. Here the motivation inverts: the goal isn't to avoid wasted spinning, it's to exploit precise co-execution so a narrow hardware race window actually opens.

Now you're ready: same mechanism, opposite motivation — a nice example of reusing an old OS idea for a new measurement purpose.
The whole story in one place

Co-scheduling in a nutshell

Placement is a first-class correctness factor for litmus tests — and sched_ext is the lever to control it.

A litmus test's sensitivity depends on a scheduling condition it cannot enforce itself: its threads must run simultaneously on different cores, within a cycle-scale window. On a multi-socket NUMA machine, the default Linux scheduler may scatter those threads across sockets by accident, collapsing the observed weak-behavior rate. Manual taskset pinning fixes this for one hand-tuned test — but affinity alone doesn't coordinate a whole campaign once multiple tests oversubscribe the available cores.

Using sched_ext, the paper builds two eBPF schedulers that make the co-scheduling invariant explicit. scx_gang reserves dedicated, NUMA-local cores per gang (spatial isolation) — automatically matching hand-tuned pinning. scx_tgang time-slices whole gangs as units when the machine is oversubscribed (temporal rotation) — something neither SCHED_FIFO nor static affinity can express.

The payoff: placement alone swings a single test's weak-behavior rate by up to 190×. scx_gang matches careful manual pinning with no topology tuning. scx_tgang keeps its per-gang median in the 11,000–18,000 weak/10⁶ range and its worst-case per-gang floor above 11,000, even at 2× oversubscription, where a static-affinity baseline livelocks completely.

🍯 Key takeaways

  • Weak-behavior rate depends on placement, not just synchronization code — a 190× swing from scheduling alone.
  • The default scheduler isn't just slower on average, it's a bimodal lottery: sometimes near-optimal, sometimes near-zero.
  • scx_gang reserves NUMA-local cores per gang and matches hand pinning automatically.
  • scx_tgang time-slices whole gangs; static affinity (taskset) livelocks under 2× oversubscription.
  • The eBPF verifier rejected the "obvious" two-phase design (-E2BIG); a single greedy pass was required instead.
  • Real ARM hardware confirms this isn't just a synthetic metric: MP/2+2W/IRIW fire nonzero on ARM, zero on x86-TSO.
Three pictures

How to think about gang scheduling

Each stands alone; each has an honest "where it breaks."

The core idea · Co-timing

Rowing in sync

A boat moves only when every oar hits the water at the same beat. Assigning each rower a seat (pinning) guarantees nothing about when they stroke — if they paddle on independent clocks, the boat barely moves even with perfect seating.

Where it breaks: real rowers watch each other and self-synchronize. Threads can't observe the scheduler's clock — the kernel has to enforce the beat.
scx_gang · Spatial

A reserved block of parking

Instead of a lottery for scattered spots across town (random NUMA placement), a whole same-neighborhood block is held for one family's cars, so they always park next to each other.

Where it breaks: the reservation is dynamic, not permanent zoning — released the moment the family leaves (gang exits), and if too many families claim the same neighborhood, it piles up (Table 2, K=8 collapse).
scx_tgang · Temporal

A relay baton for whole teams

Instead of handing the baton runner-by-runner, an entire team takes the track together for one lap, then yields it whole to the next team.

Where it breaks: a real baton pass is atomic. scx_tgang's placement is a single greedy pass — if idle cores run out mid-team, some members miss the lap (partial activation, up to 29% of passes at 2× load).
The full explanation

How it actually works

Two eBPF schedulers, one shared enrollment mechanism, and one verifier fight.

1 · Enrollment — making a gang visible to the kernel

Each thread writes its thread ID into a pinned eBPF hash-of-maps, keyed first by thread group, then by thread ID. The tuple (tgid, group) is now a gang identity both schedulers can read. Un-enrolled threads are ordinary background work.

⚠
The verifier fight. The natural design checks admission first ("does the front gang fit?") then places it — two scans. The eBPF verifier rejected this with -E2BIG and a misleading "global function doesn't return scalar" message: bounded loops + repeated map lookups + per-CPU scans exceeded its state budget. The fix was a single verifier-friendly greedy pass — at the cost of strict atomicity: a gang can be partially activated if idle cores run out mid-pass (negligible until oversubscription, then up to 29% of activations at 2×).
🔬
Measurement discipline. Every comparison in this paper holds the same non-blocking sense barrier fixed. Swapping it for a blocking barrier alone moves SB's weak-outcome rate by roughly 1000× on the unmodified default scheduler — a confound far bigger than any scheduler effect. Isolating the scheduler's contribution required controlling this first.
Follow the numbers

Worked examples

Three traces through the paper's real measurements.

① The 190× placement swing, computed

  1. Worst case: cross-socket pin, median 62 weak/10⁶ iterations.
  2. Best case: scx_gang, median 11,835.
  3. Swing: 11,835 / 62 ≈ 190.9× — same code, same barrier, only placement changed.
  4. Default scheduler gap: unpinned median 1,429 vs. same-socket pin 10,906 → 10,906/1,429 ≈ 7.6×, matching the paper's "roughly 8×".
  5. scx_gang vs. hand pin: 11,835 vs. 10,906 — automatic placement at least matches manual tuning, with zero topology-specific code.

② A floor matters more than a mean (K=4 concurrent gangs)

  1. Default scheduler's average at K=4: 4,754 weak/s.
  2. Default's worst runs at the same K: as low as 7–100 weak/s — a placement lottery, not noise.
  3. scx_gang's worst run at K=4: 7,753 weak/s — already above the default's average.
  4. For a testing tool, the floor is what matters: a silent 50–100× loss of sensitivity on an unlucky run is false confidence, not a benchmark footnote.

③ Oversubscription: who survives 2× load?

48 cores, 3 threads/gang. At K=16 gangs (48 threads) the machine is exactly full; at K=32 (96 threads) it's 2× oversubscribed.

  1. K=16 (1.0×): default 7,252 · taskset-pin 4,920 · scx_gang 12,033 · scx_tgang 17,652.
  2. K=32 (2.0×): default 15,590 (lucky accidental co-location) · taskset-pin 0 — complete livelock · scx_gang 5,105 (NUMA imbalance) · scx_tgang 14,628.
  3. scx_tgang's actual best in Table 2 is 18,365 at K=24 — higher than either the K=16 or K=32 figures above.
  4. scx_tgang retention vs. its own best: 14,628 / 18,365 ≈ 79.7% despite 2× the load. (14,628 / 17,652 ≈ 83% is retention against the K=16 exact-fit case, not against scx_tgang's true peak.)
  5. taskset-pin retention: 0 / 4,920 = 0% — static affinity pins threads to cores but not to each other, so competing gangs interleave independently and never co-run.
💡
This is the paper's central argument in one table: affinity degrades to zero exactly where temporal gang scheduling is needed most.
Test yourself

Practice problems

Each answer ends with the misconception it checks.

Problem 1 · easy
Why can't you just taskset -c 0,1 two litmus-test threads and call it solved?
Show answer
You can — that's exactly the paper's "hand-tuned same-socket pin" baseline, and it works great for one test. The gap only appears once multiple tests must share oversubscribed cores.Misconception: that pinning is useless here. It's necessary and sufficient for a single isolated test — the paper's contribution targets the multi-test regime.
Problem 2 · medium
At K=32, taskset-pin scores 0 while the unmodified default scheduler scores 15,590. Isn't static pinning supposed to be at least as good as "no policy at all"?
Show answer
Pinning fixes WHERE, not WHEN. At 2× oversubscription, two pinned gangs' threads independently time-slice the same cores, so a gang's own members are almost never co-resident — a true livelock for the sync window. The unpinned default has no fixed affinity, so it occasionally co-schedules a whole gang by chance.Misconception: affinity ⇒ co-scheduling. It only constrains location, never timing relative to other threads.
Problem 3 · medium
The verifier rejected the first scx_tgang design with "-E2BIG, global function doesn't return scalar." What actually went wrong?
Show answer
Two nested scans (check-fits, then place) combined with bounded loops and repeated map lookups exceeded the verifier's state/path budget — a resource-limit failure, not a type error. The fix was a single greedy pass.Misconception: that the verifier's error message always points at the real cause. Here it was a misleading diagnostic for a resource-exhaustion problem.
Problem 4 · hard
scx_gang collapses at K=8 (median 370) but works fine at K=4 and K=16. Why non-monotonic?
Show answer
The paper traces the K=8 collapse to a specific mechanism: the first member of each gang decides its home NUMA node, and at K=8 several gangs happen to land on the same socket, imbalancing load. It does not offer a causal explanation for why K=16 recovers — that recovery is observed in Table 2, not derived, so treat it as an open question rather than an established "exact fit balances out" effect.Misconception: that spatial reservation schedulers degrade gracefully with load, or that every bump in Table 2 has a stated cause. The paper explains the K=8 collapse but leaves other non-monotonic points unexplained.
Problem 5 · medium
Why does the paper hold the barrier type fixed across every scheduler comparison?
Show answer
Swapping blocking↔non-blocking barriers alone moves SB's rate by ~1000× on the unmodified default scheduler — bigger than any scheduler effect measured. Varying it alongside the scheduler would confound the two.Misconception: that controlling the scheduler is the only variable that matters. The sync primitive is an equally powerful hidden variable.
Problem 6 · easy
Does scx_gang/scx_tgang make the CPU reorder memory operations more often?
Show answer
No. It changes nothing about the hardware's memory model; it only removes scheduling accidents that prevented an already-possible reordering from being observed.Misconception: conflating "detect more weak behaviors" with "cause more weak behaviors" — hardware behavior is unchanged.
Quick answers

FAQ

Q1Is this a new memory model or verification tool?▾
No — it's a scheduler for running existing litmus tests (e.g. from litmus7/diy) more reliably. It doesn't generate or interpret memory-model semantics itself.
Q2Does scx_gang beat scx_tgang?▾
Not strictly by regime. scx_gang can work well when spatial placement maps cleanly onto the topology, but it isn't automatically the winner whenever gangs fit — at K=16, gangs exactly fill the 48 cores, yet scx_tgang still beats scx_gang (17,652 vs 12,033). scx_tgang wins decisively under oversubscription, where scx_gang degrades further.
Q3Why eBPF/sched_ext instead of a kernel patch?▾
Portability and iteration speed — a verified eBPF scheduler loads without rebuilding or rebooting the kernel, and the verifier catches gross bugs before they control scheduling.
Q4Does the paper formally prove the policy is correct?▾
No. It reports empirical overhead/throughput and documents a known greedy-vs-atomic tradeoff in scx_tgang (partial gang placement, up to 29% of activations at 2× oversubscription).
Q5Is the eBPF verifier a strong correctness guarantee here?▾
It stopped one bad design — but for the wrong stated reason (a misleading diagnostic for a resource-budget issue). It's primarily a safety/resource gate, not a semantic correctness oracle for the policy.
Q6Does this generalize beyond litmus testing?▾
The authors frame the benefit narrowly — specifically a NUMA + oversubscription phenomenon. But the underlying mechanism ("express these N threads must run together" as kernel policy) is general.
Q7Does it support gangs spanning multiple processes?▾
No — gangs are enrolled via a (tgid, group) key, so current support is single-process only.

Glossary & further reading

Core terms
Litmus testSmall concurrent program probing one hardware-permitted weak memory reordering; success = observing the target outcome.
GangThe complete set of threads for one litmus-test instance; must be co-scheduled for the test to be sensitive.
scx_gangSpatial sched_ext policy: reserves dedicated NUMA-local CPUs per gang via per-CPU CAS ownership; preempts other work off those cores.
scx_tgangTemporal sched_ext policy: rotates whole gangs through a shared FIFO (GANG_DSQ), activating one gang's members together per time-slice.
DSQDispatch queue — sched_ext's holding structure for runnable tasks before they reach a CPU's local queue.
Partial activationWhen scx_tgang's single-pass placement runs out of idle cores mid-gang; negligible until oversubscription, up to 29% at 2×.
Supporting terms
SB / MP / LB / 2+2W / IRIWStore Buffering, Message Passing, Load Buffering, 2+2 Write, Independent Reads of Independent Writes — canonical litmus tests.
TSOx86 Total Store Order; permits SB, forbids the other four tests above.
Sense barrierNon-blocking spin barrier; held constant across all comparisons to isolate the scheduler's effect.
eBPF verifierLinux's in-kernel static checker that every sched_ext program must pass before loading — rejects unsafe or resource-exhausting programs. The paper's -E2BIG rejection is about this Linux verifier, not the academic PREVAIL verifier (which appears elsewhere in the proceedings, not in this paper).
CASCompare-and-swap; used both for scx_gang's per-CPU ownership table and scx_tgang's single global activation lock.
