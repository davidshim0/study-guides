Handle the fault where it happens — not where a thread happens to be polling

uffd offloads page faults to a userspace thread — at the cost of two context switches and a syscall round trip on every fault. bpf_fault runs the handler as an eBPF program, in-kernel, in the faulting thread itself.

Before you begin

Quick glossary, then eight things to load

Your Linux mm background (VMAs, PTEs, COW, fault types) is assumed — the primers below skip that and focus on the eBPF and uffd machinery specific to this paper.

Quick glossary
uffduserfaultfd — the Linux syscall (2015) that offloads page fault handling to a userspace thread.
eBPFVerified, sandboxed programs the kernel can run safely — bounded loops, provably memory-safe.
struct_opsAn eBPF attachment mechanism: userspace loads a set of callback functions that the kernel invokes as a pluggable policy (used by sched_ext, cache_ext, and bpf_fault).
WP faultWrite-protect fault — a write to a PTE marked read-only, commonly used for COW and for intercepting writes (snapshots, GC).
TOCTOUTime-of-check-to-time-of-use — a race exploited when a handler can block kernel execution indefinitely, the source of most uffd CVEs.
R_RELATIVEA relocation type: patch a location with (load address + addend) — up to 99%+ of all relocations in large PIE binaries.
IPIInter-processor interrupt — used to wake a sleeping thread on another core; a fixed cost baked into every uffd round trip.
ArenaAn mmap()-able eBPF memory region shared between kernel programs and userspace, usable for dynamic data structures (e.g., an rb-tree).
bpf_fault — the fast in-kernel path eBPF / kernel machinery uffd — the slow baseline
1eBPF, in one breath▾

eBPF lets userspace load programs that the kernel verifies before running: bounded loops, no out-of-bounds memory access, no unbounded blocking by default. Once loaded, the program runs with kernel privileges but within those static guarantees. Traditional uses are networking and observability; this paper extends that to the page-fault path itself.

Now you're ready: bpf_fault's whole safety story — no TOCTOU, no runaway handler — rests on the verifier bounding what a fault handler can do.
2struct_ops — attaching a policy, not a single function▾

struct_ops lets userspace populate a struct of function pointers with eBPF programs and hand it to the kernel as one unit; an eBPF link manages its lifecycle. sched_ext uses it for schedulers, cache_ext for page-cache eviction policy. bpf_fault uses it for a fault_ops struct: one callback per fault type (missing, minor, WP, fork, …).

Now you're ready: "attach a bpf_fault handler to an address range" literally means: load a fault_ops struct_ops map and link it to a VMA range.
3uffd's three fault modes + SIGBUS + non-cooperative mode▾

Missing mode: supply content for a never-populated page (live migration, lazy restore). Write-protect (WP) mode: intercept writes to pages marked read-only via a PTE bit, without splitting the VMA (snapshots, GC). Minor mode: install an already-cached page (shmem/hugetlbfs only). SIGBUS mode turns uffd into a pure notifier — no handler thread, just a signal. Non-cooperative mode lets a separate monitor process handle faults on behalf of a target it doesn't control (needed for CRIU checkpoint/restore).

Now you're ready: bpf_fault supports all three fault types plus fork/event callbacks, but replaces uffd's message-queue protocol with direct in-kernel callbacks — no separate monitor thread needed.
4Why file-backed memory matters here▾

uffd's missing mode only covers anonymous memory (and shmem for minor mode) — it cannot intercept faults on ordinary file-backed mappings, which is how executables and shared libraries are mapped. That single gap rules uffd out for anything touching the dynamic linker.

Now you're ready: bpf_fault adds missing/minor handling for file-backed VMAs — the capability that makes the lazy dynamic-linking use case (§5.2) possible at all.
5Maps and arenas — sharing state with a kernel program▾

eBPF maps (hash maps, ring buffers) move data between kernel and userspace. A BPF arena is a shared, mmap()-able region usable by both sides for dynamic structures — allocators, trees, bitmaps — not just fixed-size records.

Now you're ready: the dynamic-linker integration keeps a per-process interval tree of relocatable segments in an arena; the GC integration keeps its live-object bitmap and forwarding table the same way.
6TOCTOU and why fault handlers are dangerous to block on▾

If a handler for a kernel-originated fault (e.g. the kernel's own read() touching an unfaulted user page) can block indefinitely, an attacker can freeze kernel execution mid-operation and widen a race window — the root cause of most uffd CVEs. Mitigations (blocking unprivileged uffd, refusing kernel-originated faults) have further narrowed uffd's usable surface.

Now you're ready: this is why bpf_fault handlers are non-sleepable (atomic, bounded) by default, and sleepable handlers are opt-in with verifier-bounded blocking only.
7Write-protect faults as a general "intercept the next write" primitive▾

Marking a page's PTE (not its VMA) read-only lets you catch exactly one specific event — the next write to that page — without fragmenting the address space the way mprotect() does. This single mechanism underlies COW, live VM snapshots (capture the pre-write image), and generational GC (catch pointer stores into old objects).

Now you're ready: §5.1 (snapshots) and §5.3.1 (GC dirty tracking) are both "install a WP handler, capture on first write" — same primitive, different payload.
8Eager vs. lazy relocation▾

Position-independent binaries embed compile-time-relative pointers that must be patched (relocated) to the actual load address before use. Linux's dynamic linker does this eagerly for every relocation at load time — touching (and dirtying, via COW) every page that contains one, whether or not the program ever runs that code. Windows and macOS instead relocate lazily, only when a page is actually touched.

Now you're ready: §5.2 builds Linux's first lazy-relocation path using bpf_fault — no ELF format change, unlike Apple's page-in linking.
The whole story in one place

bpf_fault in a nutshell

The overhead uffd can't avoid by design, the fix, and where it pays off.

uffd's architecture is fundamentally a relocation problem: fault handling logic lives in userspace, but faults happen in the kernel, so every fault pays for a trip between the two — a context switch to a dedicated handler thread, a wake-up IPI, and (for missing faults) a read()/ioctl() pair. Instrumenting a single MISSING fault shows this concretely: only 16% of the critical path is the unavoidable trap in/out of the kernel; 17% is extra syscall crossings, 43% is scheduling and IPIs, and 10% is uffd's own message-queue bookkeeping — 70% of the fault is pure protocol overhead, before any actual work is done.

bpf_fault removes the trip by moving the handler itself into the kernel, as an eBPF struct_ops program invoked directly in the faulting thread's own context. There is no handler thread, no context switch, and no IPI. The eBPF verifier — which already guarantees bounded, memory-safe execution for other in-kernel extensions like sched_ext and cache_ext — gives the same safety uffd's design sacrificed for performance, without a userspace round trip.

The payoff: 2.8–6.7× lower average fault latency than uffd, only 1.4× overhead over the kernel's own baseline fault path, and linear scalability with thread count where uffd's single handler thread becomes a serializing bottleneck (at 512 threads: 25 ms for bpf_fault vs. 859 ms for uffd — uffd is 34× slower). bpf_fault also extends fault handling to file-backed memory, which uffd cannot touch, unlocking a lazy dynamic-linking mechanism that cuts Chrome's dirty memory by up to 50% (95 MB).

🍯 Key takeaways

  • uffd's cost is structural: two context switches + IPI + syscall crossings, on every fault, regardless of what the handler actually does.
  • bpf_fault runs the handler in-kernel, in the faulting thread — a struct_ops eBPF program, not a separate thread.
  • It also handles file-backed memory, which uffd's missing mode cannot — the key that unlocks lazy dynamic linking.
  • Fault handlers are non-sleepable by default (verifier-bounded, atomic); sleepable handlers are opt-in and still verifier-bounded.
  • Cost: ~2,500 LoC of kernel changes, no new per-VMA memory overhead, nothing added to the critical path for unregistered memory.
  • Four integrations — VM live snapshots, lazy dynamic linking, JVM GC, an electric-fence memory debugger — each exploit a different fault type.
Six everyday pictures

How to think about bpf_fault

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Where the handler runs

Calling IT support vs. an in-house fixer

uffd is like reporting a problem to a remote help desk: you file a ticket (enqueue), wait for someone to pick it up (schedule + IPI), they investigate and call back (ioctl round trip) — and only then is the issue actually resolved. bpf_fault is the in-house technician already standing at your desk: the fix happens right where the problem occurred, no tickets filed.

Where it breaks: the analogy makes bpf_fault sound unconstrained. It isn't — the "technician" only knows tricks the verifier pre-approved (see next card).
Safety · The eBPF verifier

A building inspector who pre-approves the blueprint

Instead of a supervisor watching every hammer swing on-site (a runtime monitor), an inspector checks the blueprint before construction starts: bounded loops, no wiring outside the walls (out-of-bounds memory). Once approved, the crew works unsupervised, safely, because the plan itself was proven safe. That's the eBPF verifier — it guarantees memory safety and bounded execution without a kernel developer auditing each handler line by line, though loading one still requires privileged access (CAP_BPF) and the verifier says nothing about whether the policy itself is sound.

Where it breaks: a blueprint can't be checked for "will this take forever" if it involves waiting on something outside the plan — which is exactly why eBPF handlers can't read a file or a socket (§4.8).
Scalability · One handler thread vs. every thread

One teller window vs. everyone serving themselves

uffd is a bank with one teller window: no matter how many customers (faulting threads) arrive, they funnel through the same queue, and wait time balloons — going from 1.4 ms to 863 ms as threads scale from 1 to 512 (616× longer, vs. baseline's 57×). bpf_fault has no teller: each customer (thread) serves themself, in-kernel, so the line grows only as fast as the underlying work does — a constant ~1.5× gap over the unhandled baseline at every thread count.

Where it breaks: adding more tellers (uffd handler threads) does help somewhat — 16 threads cut 512-thread runtime by 36% — but at 5× the CPU cost, and still nowhere near self-service.
Lazy dynamic linking

Grading only the homework that gets turned in

Linux's dynamic linker grades the entire assignment book on day one — patching every relative relocation whether or not that code path ever runs, dirtying every page it touches. With bpf_fault, grading happens on demand: a page is relocated only the first time a student (the CPU) actually opens to that page. Chrome uses only a fraction of its 1.08M relocations at runtime, so most "homework" never gets graded at all — 50% less dirty memory.

Where it breaks: deferred grading isn't free — it moves the cost into the fault, and reading relocation entries one at a time from the table costs 500% overhead; batching in 8 KB chunks is what brings it down to 57%.
Sleepable handlers & the security model

A sticky note vs. a sealed, tracked envelope

Non-sleepable handlers (the default) are like a sticky note reply: it must be written instantly, with what's already on the desk — no leaving to fetch something. This closes off the classic uffd exploit pattern of a handler that blocks indefinitely while an attacker races the frozen kernel. Sleepable handlers are more like a tracked, sealed envelope: they can wait for something (e.g. bounded memory allocation), but that something has a guaranteed, verifier-checked upper bound on delay — never an attacker-controlled event.

Where it breaks: a real mail courier can be arbitrarily delayed; the whole point of the verifier is that a "sleepable" eBPF handler cannot be — the analogy's freedom is exactly what's engineered away.
Concurrent GC compaction

Renovating a house while the family still lives in it

Stop-the-world compaction evicts everyone, slides all the furniture (live objects) into place, then lets them back in — a pause proportional to the whole house. bpf_fault's fault-based compaction instead lets the family move back in room by room: the moment someone (a mutator thread) walks into an unfinished room, the fault handler instantly finishes compacting that room only, in-kernel, and they continue. On h2, this cuts mean GC pauses 42% below stop-the-world while running faster.

Where it breaks: the "room-by-room" setup isn't free either — every collection pays a fixed window-setup cost, which is why on benchmarks with very short pauses to begin with (xalan, lusearch), this approach is worse overall than just finishing the renovation in one go.
The full explanation

How it actually works

From uffd's protocol, to bpf_fault's two-phase fault path, to the security model that makes it safe to run in-kernel.

1 · uffd's protocol — why every fault pays for a round trip

A uffd-registered fault always crosses at least four extra kernel/user boundaries beyond the fault trap itself: the handler thread's poll() returns, it calls read() to pull the fault message, does its work, then calls an ioctl() (UFFDIO_COPY/ZERO/CONTINUE/WRITEPROTECT) to resolve it and wake the faulting thread.

  1. Register: app calls userfaultfd(), then UFFDIO_REGISTER on an address range.
  2. Fault: a thread accesses a registered page; the kernel blocks it and enqueues a fault message.
  3. Wake: the handler thread (polling the fd) wakes via IPI and scheduling.
  4. Read: handler calls read() to retrieve the fault message.
  5. Prepare: handler prepares page content in a userspace buffer.
  6. Resolve: handler issues UFFDIO_COPY (or ZERO/CONTINUE/WRITEPROTECT); kernel copies data in and installs the PTE.
  7. Retry: the original faulting thread wakes and retries the access — now a hit.

2 · bpf_fault's two-phase fault path

When a fault reaches a VMA registered with bpf_fault, the kernel's own fault handler diverts into a common protocol — no separate thread, no message queue:

PhaseWhat happensvs. uffd
1 · Release & invokeRelease the per-VMA fault lock, allocate a page if needed, call the eBPF program directly — in the faulting thread's own context.No handler thread to schedule; no IPI to wake it.
2 · Re-lock & installRe-acquire the VMA lock, verify it's still valid, install the PTE. A non-zero handler return sends SIGBUS instead.No ioctl() round trip; PTE install happens in the same call stack.

3 · The eBPF interface — writing directly into the faulting page

Each fault type gets a callback (handle_missing_fault, handle_minor_fault, handle_wp_fault, handle_fork, …) receiving a context struct (fault type, page-aligned and exact address) plus a pointer to the page itself. For missing/minor faults the page is writable (PTR_TO_MEM, bounded to PAGE_SIZE); for WP faults it's read-only (MEM_RDONLY). Returning zero installs the page; non-zero raises SIGBUS — a failure signal uffd has no equivalent for (a uffd handler that can't resolve a fault just blocks forever).

struct fault_ops {
  int (*handle_missing_fault)(struct bpf_fault_ops_ctx *ctx,
                             unsigned char *page);   // writable, zeroed
  int (*handle_minor_fault)(...);                   // writable, page-cache contents
  int (*handle_wp_fault)(...);                      // read-only mapping
  int (*handle_fork)(struct bpf_fault_fork_ctx *ctx);
  ...
};

4 · Registration and VMA integration

An application loads its handlers and attaches the struct_ops map to an address range with one libbpf call; the kernel allocates a refcounted fault context tying together the relevant VMAs, walks and validates each VMA (must be faultable, not already owned by a different context), and tags it with a VM_BPF_FAULT flag. Because bpf_fault reuses uffd's existing vm_userfault_ctx field (via a union) and its WP PTE bits rather than allocating new ones, it adds zero new per-VMA memory overhead. A single link can later register or remove additional disjoint ranges, and on fork() a lightweight inherited link (just a pointer to the parent's struct_ops) avoids setup cost in the fork fast path unless the child later calls a promoting BPF_FAULT_CLAIM.

⚠
Suppressed optimizations: like uffd, bpf_fault disables transparent huge pages, batched shmem allocation, and fault-around for registered VMAs — every page installation must pass through the handler. This only affects registered regions; the rest of the process is untouched.

5 · Security model

Fault handlers are non-sleepable by default: they execute atomically and cannot be delayed, closing off the classic uffd attack of triggering a kernel-originated fault and blocking the handler indefinitely to widen a race window. Opt-in sleepable handlers reintroduce blocking for use cases that need it, but the verifier still rejects unbounded loops, and the blocking primitives available (e.g. memory allocation) are themselves bounded — never able to wait on an attacker-controlled event. A slow handler also only delays the process that installed it; bpf_fault doesn't support cross-process registration.

Follow the numbers, step by step

Worked examples

Four traces carried through with the paper's own numbers: microbenchmark speedups, the scalability gap, dynamic-linking savings, and the snapshot latency win.

① Computing the fault-latency speedups

Table 3 reports average latencies (µs) for write-triggered faults. What speedup does bpf_fault actually deliver, per fault type?

  1. Missing (anon): uffd 11.6 µs, bpf_fault 2.7 µs → 11.6 / 2.7 = 4.30×.
  2. Write-protect: uffd 10.8 µs, bpf_fault 1.6 µs → 10.8 / 1.6 = 6.75× — rounds to the paper's headline "6.7×".
  3. Minor (shmem): uffd 10.3 µs, bpf_fault 3.7 µs → 10.3 / 3.7 = 2.78× — the paper's low end, "2.8×".
  4. Range: 2.8–6.7× — exactly the paper's headline reduction, and it now has a mechanistic explanation: WP gains most because uffd needs an extra ioctl just to lift the write-protect bit; minor gains least because both paths pay for the same folio copy.

② The scalability gap — growth rates, not just endpoints

Baseline goes from 0.3 ms (1 thread) to 17 ms (512 threads); uffd (1 handler) goes from 1.4 ms to 863 ms. How much worse does uffd actually scale?

  1. Baseline growth: 17 / 0.3 = 56.7× over a 512× increase in threads — matches the paper's "57× longer".
  2. uffd growth: 863 / 1.4 = 616.4× — matches the paper's "616× longer" exactly.
  3. Relative degradation: 616.4 / 56.7 ≈ 10.9× — uffd's serialization makes it scale roughly 10× worse than the baseline, confirming the paper's "scaling ∼10× worse" claim.
  4. bpf_fault at 512 threads: 25 ms vs. baseline's 17 ms → 25/17 ≈ 1.47×, matching the paper's "constant ~1.5× gap due to eBPF overhead" — and vs. uffd's 859 ms: 859/25 ≈ 34.4×, matching the reported "34× slower".
💡
Two different numbers for uffd's 512-thread time appear in the paper (863 ms in §3.2's raw scalability benchmark, 859 ms quoted in §6.1's comparison) — both are used above in their original context rather than silently reconciled.

③ Dynamic linking: how much work does lazy relocation actually skip?

Chrome has 1,075,978 R_RELATIVE relocations (99.1% of its total, 78.8% of linker time). Baseline startup is 36 ms, bpf_fault's is 20 ms; dirty memory drops from ~200 MB to ~100 MB.

  1. Startup speedup: (36 − 20) / 36 = 44.4% faster — matches "44% faster".
  2. Dirty memory reduction: (200 − 100) / 200 = 50%, i.e. 95 MB saved — matches "50% (95 MB)".
  3. Why it works: only pages the program actually touches get relocated; since 78.8% of linker time was previously spent on relative relocations alone, skipping untouched pages removes most of that cost outright.
  4. vs. the zygote: Chrome's process-sharing zygote amortizes relocation cost across children but still dirties pages up front; measuring proportional dirty memory (PSS_Dirty), bpf_fault still beats it by (135 − 104) / 135 ≈ 23% — with a fully generic mechanism, no zygote required.

④ QEMU snapshots: worst-case write latency, ~140 ms down to single-digit ms

Table 4: QEMU's background (uffd) mode has worst-case request latency of 124–142 ms during a snapshot; bpf_fault's is 6–7 ms.

  1. Worst-case improvement: 142 / 7 = 20.3× lower latency — matches "20× lower".
  2. Downtime: both modes achieve 3–4 ms downtime (the brief VM pause) — bpf_fault doesn't change downtime, it changes what happens after resume, while pages are still being streamed.
  3. Total time: uffd's background mode takes 3.33 s (8 GB) vs. bpf_fault's 2.33 s — nearly matching the synchronous baseline's 2.31 s, because bpf_fault's non-blocking WP handler no longer stalls the migration thread that's also streaming pages.
  4. Takeaway: the gain isn't from a smarter algorithm — it's the same background-snapshot design, just no longer paying uffd's per-write round-trip tax on the critical path of every guest write.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A Chrome-like application calls clone() directly instead of going through libc's fork(). Why does this break uffd specifically, and how does bpf_fault avoid the problem?
Show answer
When a multithreaded process calls fork(), only the calling thread is cloned into the child, so uffd's dedicated handler thread doesn't exist there either; applications typically use libc's atfork handlers to respawn it. A raw clone() call bypasses libc's fork machinery (and any atfork hooks) entirely, so nothing re-establishes the handler thread in the child, silently breaking fault handling. uffd's non-cooperative mode — a separate monitor process handling faults on a target it doesn't control — can sidestep this, but concentrates faults from potentially many targets onto one monitor, which becomes its own bottleneck. bpf_fault has no handler thread to recreate: forked children automatically get a lightweight inherited link (with BPF_FAULT_INHERIT) that references the parent's struct_ops directly, independent of how the fork happened.Misconception: that this is a minor edge case, or that atfork is uffd's only defense. It's precisely why uffd is unusable inside libraries like the dynamic linker — you can't control how every calling application forks.
Problem 2 · medium
bpf_fault removes the context switch, the handler thread, and the extra kernel-user crossings from a fault. So why does it still add 1.4× overhead (2.7 µs) over the 2.0 µs kernel baseline for a missing write fault?
Show answer
Removing uffd's overhead doesn't mean removing all overhead — invoking any eBPF program still costs something: entering the eBPF runtime, the verifier-inserted bounds checks on the page pointer, and returning back into the kernel's fault path. That's the residual 0.7 µs (2.7 − 2.0). It's real but an order of magnitude smaller than uffd's 9.6 µs of overhead (11.6 − 2.0).Misconception: that "in-kernel" means "free." bpf_fault is fast because it eliminates the specific costs of context switching and syscalls, not because eBPF execution itself has zero cost.
Problem 3 · medium
Table 3 has no baseline entry for write-protect faults. Why not — what would a "baseline WP fault" even mean?
Show answer
The "baseline" column measures the kernel's default fault path with no custom handler at all. But a WP fault only exists because some mechanism (uffd, bpf_fault, or the kernel's own COW logic) deliberately marked a PTE write-protected in the first place — there's no such thing as an "unhandled" WP fault to measure, unlike a missing fault, which always occurs on first access regardless of any handler.Misconception: assuming every row in a comparison table needs every column filled. Some fault types are inherently tied to the presence of a handler.
Problem 4 · hard
bpf_fault handlers are non-sleepable by default. Explain concretely how this closes off the TOCTOU attack pattern the paper describes for uffd, and why sleepable handlers don't simply reopen it.
Show answer
The uffd attack pattern: trigger a fault from kernel code (e.g. the kernel's own read() touching an unfaulted user page) while the userspace handler blocks indefinitely — freezing kernel execution in a known state and widening the timing window for a race elsewhere. A non-sleepable bpf_fault handler executes atomically to completion, so there's no window to freeze: the fault either resolves immediately or the process dies. Sleepable handlers reintroduce blocking, but only on verifier-bounded operations (e.g. allocation with a guaranteed bound) — never on an attacker-controlled event like a network read or another thread's action — so there's no indefinite freeze to exploit even though delay is possible.Misconception: that "sleepable" means "as dangerous as uffd." The danger in uffd was unbounded, attacker-influenced blocking, not blocking per se.
Problem 5 · medium
efency's SIGBUS mode eagerly populates every allocated page via UFFDIO_COPY at malloc() time, avoiding a handler thread. On a workload where only 10% of allocated slots are ever touched (like a hash table), why is this slower than bpf_fault, which is lazy?
Show answer
SIGBUS mode must populate 100% of allocations up front because it cannot distinguish "will be touched" from "won't" — and once populated, valid accesses generate no fault to intercept, so touched-but-unpopulated pages aren't an option in this mode. bpf_fault, by contrast, only pays a fault (and its ~1.4× overhead) for the 10% of slots actually accessed; the other 90% cost nothing beyond the bitmap check at allocation time. The paper measures bpf_fault as 3.6× faster than SIGBUS mode at 10% utilization, narrowing to 1.4× at 100% utilization — exactly the pattern this predicts.Misconception: that eager population is "safer" because it avoids kernel-originated-fault edge cases. It trades that safety concern for wasted work proportional to how much of the allocation is never used.
Problem 6 · hard
The paper says bpf_fault "adds no new fields to VMAs" and stores its fault context in the same vm_userfault_ctx field uffd already uses (via a union), and reuses uffd's WP PTE bits. Why does this design choice matter beyond just saving a few bytes?
Show answer
Two reasons beyond memory: (1) x86-64 has a limited, fixed number of software PTE bits available for kernel metadata — allocating a second, parallel set of WP bits for bpf_fault would consume a scarce resource that other kernel features also compete for. (2) Reusing the same page-table routines uffd already uses for WRITEPROTECT/COPY/ZERO avoids duplicating complex, easy-to-get-wrong PTE and TLB invalidation logic in two places. The tradeoff is that a single VMA can be registered with uffd or bpf_fault, never both, since they share the same context field.Misconception: treating shared infrastructure as purely a code-size optimization. It's also what keeps bpf_fault from competing with other extensions for the same scarce PTE bits, and from introducing a second, independently-buggy WP implementation.
Problem 7 · easy
Why can't bpf_fault (as described in the paper) implement post-copy live VM migration, even though uffd's missing mode was originally built for exactly that?
Show answer
Post-copy migration's handler needs to read the missing page's content over the network from the source host. eBPF programs currently cannot perform arbitrary socket I/O — reading from or writing to the network isn't available inside the verifier's supported operations (§4.8). The paper notes this gap is narrowing (dynptrs, a proposal for sending UDP from eBPF), but as of this paper, it's an explicit limitation, not a design choice bpf_fault made on purpose.Misconception: assuming bpf_fault is a strict superset of uffd's capabilities because it's faster. It trades away some of uffd's generality (arbitrary syscalls, network I/O) for performance and safety.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is bpf_fault a replacement for userfaultfd, or does it coexist with it?▾
Coexists at the kernel level (they even share the vm_userfault_ctx field and WP PTE bits), but a given VMA can only be registered with one or the other, not both. For new use cases the paper frames bpf_fault as the better-fitting design — the uffd developers themselves told the authors an eBPF-based approach may be a better fit than uffd's fully userspace architecture (§1).
Q2Why not just write a kernel module or patch the fault handler directly, instead of using eBPF?▾
A raw kernel module has no safety guarantees — a bug crashes the machine, and there's no standard, portable attachment mechanism. eBPF's verifier gives bounded execution and memory safety before the code runs, and struct_ops gives a standard attachment API already used by sched_ext and cache_ext. The kernel-side plumbing is still real (~2,500 LoC), loading a handler still requires privileged eBPF access (CAP_BPF), and the verifier doesn't vouch for whether a policy is semantically correct or well-behaved — but it does mean the memory-safety and termination guarantees don't rest on a kernel developer auditing each handler.
Q3How does this relate to cache_ext, mentioned in Related Work?▾
cache_ext uses the same struct_ops pattern to let eBPF programs customize page-cache eviction policy; bpf_fault applies the identical architectural idea to page fault handling. The paper calls bpf_fault "most similar" to cache_ext among the eBPF memory-management line of work (§7) — both are examples of moving a previously-fixed kernel mm policy behind a verified, pluggable interface.
Q4The paper cites ExtMem and HeMem as prior uffd-based tiered-memory systems. Does bpf_fault change what's possible for OS-managed tiering?▾
The paper's own claim (§3.3) is narrower and worth quoting precisely: uffd handlers "cannot access kernel state directly," and it gives PTE-bit inspection for informed page placement as the concrete example of what that blocks. bpf_fault handlers run in-kernel and receive the fault's address, fault type, and page contents directly through fault_ops — but the paper doesn't describe an explicit PTE-inspection helper in that interface; PTE-bit access is offered as a motivating example of the kind of kernel state uffd can't reach, not a demonstrated bpf_fault capability. Framing, not a paper claim: whether in-kernel handlers materially help hot/cold classification for tiering systems in your world (e.g. systems using multi-generational LRU or NUMA-balancing-style scanning, which don't route through page faults at all) is a promising direction the paper doesn't evaluate — it isn't demonstrated in this paper's four applications.
Q5Does bpf_fault add overhead to processes that don't use it?▾
No — for unregistered memory, bpf_fault adds no overhead (§6.1) and adds no new per-VMA memory fields (§4.4). The kernel changes are ~2,500 LoC (1,750 in mm, 750 in eBPF/libbpf), but they're only exercised on the fault path for VMAs explicitly registered with a handler.
Q6What exactly can a bpf_fault handler not do, compared to a uffd userspace handler?▾
The verifier bounds it to safe, terminating operations and (for non-sleepable handlers) atomic execution; the biggest practical gap is I/O — eBPF programs can't currently read files or the network, which is why the VM-snapshot integration streams pages to a userspace writer via a ring buffer rather than writing files directly from the handler (§4.8, §5.1).
Q7Why does WP-fault latency improve the most (6.7×) of the three fault types?▾
uffd's WP handling needs an extra round trip specifically to issue UFFDIO_WRITEPROTECT and lift the write-protect marker after saving the pre-image — on top of the same context-switch/IPI overhead every uffd fault pays. bpf_fault clears the marker directly in-kernel as part of the same handler invocation, removing that extra step entirely.
Q8How is the lazy dynamic linker different from Chrome's existing zygote optimization?▾
The zygote relocates once and shares the resulting pages across forked child processes — it amortizes cost, but still dirties pages for relocations no child ever uses, and it's Chrome-specific (requires the zygote fork architecture). bpf_fault's deferral is per-process and generic: relocations are applied only when actually touched, works without any zygote, and the paper measures it beating the zygote's proportional dirty memory by 23% (§6.3) — with Chrome's zygote disabled for that comparison.
Q9Why does Docker's startup get slightly slower with bpf_fault (§6.3)?▾
Docker's startup is dominated by Go runtime initialization, which touches nearly all of its relocated pages immediately — so deferring relocation to fault time doesn't skip much work, it just moves the same work behind a per-fault lookup (segment-tree search + batched relocation-table read), which has its own fixed overhead. With only 120K relocations and near-total page touch, there's little "unused work" left to skip.
Q10Does bpf_fault's approach to GC compaction always beat stop-the-world?▾
No — Table 5 shows it losing on runtime for xalan and lusearch, where GC pauses are already tiny (~10 ms) and happen hundreds of times; every collection pays the fault-based window's fixed setup cost, which outweighs the savings when there's little pause time to cut. It wins clearly on pause-dominated workloads like h2 (42% lower mean pause, 16% faster runtime) and pmd.
Q11What's the actual kernel engineering cost of supporting bpf_fault?▾
~2,500 lines of kernel code: 1,750 in memory management (VMA/fault-path integration, fork handling, event callbacks) and 750 in eBPF/libbpf (verifier support for bounded writes to PTR_TO_MEM, struct_ops plumbing). This is on top of infrastructure it deliberately reuses from uffd rather than duplicating.
Q12What did the authors leave for future work?▾
Closing the I/O gap as eBPF gains socket support (which would enable post-copy migration in-kernel), and extending bpf_fault to additional applications such as database checkpointing or VM memory protection (§8). They frame bpf_fault more broadly as "an experimentation platform for memory management policies that were previously locked into the kernel," with per-fault page-size selection and application-specific prefaulting given as examples of what eBPF's expanding capabilities could unlock next.

Glossary & further reading

Every term in one place, headline results at a glance, then a path to go deeper.

Core terms
bpf_faultThe paper's framework: run page-fault handlers as eBPF struct_ops programs, invoked in-kernel in the faulting thread's own context.
uffd (userfaultfd)Linux's 2015 syscall for offloading page faults to a dedicated userspace handler thread, via a message-queue protocol.
struct_opsAn eBPF interface for attaching a set of callback functions as a kernel-invoked policy; also used by sched_ext and cache_ext.
Fault contextA refcounted kernel object tying a bpf_fault handler to the (possibly multi-VMA) memory region it manages.
Missing / minor / WP faultThe three fault types bpf_fault (and uffd) handle: never-populated page, already-cached-but-unmapped page, and write to a read-only-marked PTE, respectively.
Non-sleepable handlerbpf_fault's default handler mode: executes atomically, cannot block — closes off uffd's TOCTOU attack pattern.
Supporting terms
VMAVirtual memory area — a contiguous address range with uniform permissions/backing; bpf_fault tags registered VMAs with VM_BPF_FAULT.
PTEPage table entry — holds the physical frame number and status bits (present, writable, and kernel-defined software bits like the WP marker).
COWCopy-on-write — the classic use of a write-protect fault: share a page until someone writes to it, then copy.
TOCTOUTime-of-check-to-time-of-use race, exploitable when a fault handler can block kernel execution indefinitely — the source of most uffd CVEs.
eBPF verifierStatic analysis that proves an eBPF program terminates and only makes safe memory accesses, before it's allowed to run.
BPF arenaA shared, mmap()-able memory region between eBPF programs and userspace, used for dynamic structures like bpf_fault's per-process relocation segment tree.
R_RELATIVE relocationA relocation type patching a location with load-address + addend; up to 99%+ of all relocations in large position-independent binaries.
ZygoteChrome's process-sharing optimization: relocate once, fork children that share the already-relocated pages.
