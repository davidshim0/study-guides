OSDI 2026 · A Field Guide

Watching every byte, without slowing any of them

Datacenter memory now spans DRAM, CXL expanders, and internal tiers a host can't see into. OS policies desperately need to know what's hot — but every existing way of measuring that forces a trade: cheap and rigid, or flexible and slow. This is the plain-English story of NEMO, a tiny programmable engine that lives inside the memory controller and gives the OS both.

Before you begin

Ten ideas the paper assumes you know

Each card clears up one concept NEMO builds on. They're collapsed — tap any to open. Read in order the first time, or jump to whatever looks unfamiliar.

NEMO's pipeline OS / driver control plane legacy PEBS / MBM
1What a memory controller is, and why it's a good vantage point▾

The memory controller (MC) sits between the CPU and DRAM (or CXL-attached memory), translating every load/store into the electrical signaling the memory chips understand. Every single memory access — reads, writes, prefetches, everything — physically passes through it.

That makes it a uniquely complete vantage point: unlike a CPU core, which only sees the accesses it personally issued, the MC sees every access from every core headed for the memory it controls.

Now you're ready: NEMO's whole pitch is "since the MC already sees everything, let it also count things — programmably."
2Memory tiering and CXL-attached memory▾

A server used to have one flavor of memory: local DRAM. Modern datacenter nodes increasingly attach extra memory over CXL (Compute Express Link) — expanders that behave like memory but sit further away, are slower, and may themselves compress or tier data internally, invisibly to the host.

OS "tiering" policies try to keep frequently-used ("hot") data in fast local DRAM and push rarely-used ("cold") data out to the slower CXL tier.

Now you're ready: tiering policies are exactly the kind of OS subsystem NEMO is built to feed with better signal — they need to know what's hot, cheaply and quickly.
3"Telemetry," for memory▾

Telemetry here just means: a running count of something about memory accesses — how often a page was touched, how many bytes a tenant moved, which addresses cluster together. The OS reads these counts to make decisions (migrate this page, throttle this tenant, split this hugepage).

The hard part was never wanting telemetry — it's collecting it without either missing most accesses (bad data) or burning a ton of CPU to watch closely (bad performance).

Now you're ready: the whole paper is organized around that tension, formalized as five dimensions: coverage, timeliness, granularity, flexibility, overhead.
4Sampling, and why it's a leaky abstraction▾

Rather than watching everything, a profiler can watch a small random sample of events and extrapolate. Intel's PEBS (Processor Event-Based Sampling) does this for cache misses: sample some fraction of them, reconstruct access patterns from what you caught.

The catch: PEBS misses whole categories of memory traffic (prefetches, non-temporal stores), can't see into a VM guest from the host, and gets expensive fast if you raise the sample rate — prior work shows sampling 10% of misses can slow the target program by over 50%.

Now you're ready: PEBS is the software-side baseline NEMO beats in every evaluation — flexible in principle, but its coverage/overhead trade-off never actually closes.
5Fixed-function hardware counters (MBM)▾

CPUs also expose hardware counters like Intel's MBM (Memory Bandwidth Monitoring) — cheap, accurate, and immediate, but built at chip-design time to answer one specific question (e.g. "bandwidth per socket"). If your policy needs a different granularity — per-page, per-tenant, per-arbitrary-region — MBM simply can't be reconfigured to give it to you.

Now you're ready: MBM is the hardware-side baseline; NEMO's pitch is to keep MBM's speed while dropping its rigidity.
6Transparent huge pages and hugepage bloat▾

Linux's Transparent Huge Pages (THP) automatically coalesces small 4 KiB pages into 2 MiB hugepages to cut TLB-miss overhead. The catch: if only a handful of those 4 KiB pieces are actually hot, the whole 2 MiB hugepage still gets pinned in the fast, capacity-constrained tier — "hugepage bloat." Splitting a bloated hugepage back into pieces can free most of that space for other hot data.

Now you're ready: deciding which hugepages are worth splitting is one of NEMO's three evaluated use cases (§5.2, with the MEMTIS tiering system).
7Noisy neighbors and QoS▾

In a shared/virtualized environment, one tenant hogging memory bandwidth — a noisy neighbor — can silently blow through a co-located tenant's latency SLO. Enforcing fairness needs two things: detecting the offender fast, and a lever to throttle them (e.g. Linux cgroup CPU quotas).

Now you're ready: noisy-neighbor detection and throttling is NEMO's third use case (§5.3), where its headline number is a 350× CPU-overhead reduction over polling MBM fast enough to react in time.
8Associative and commutative operations▾

An operation is commutative if order doesn't matter (3+5 = 5+3) and associative if grouping doesn't matter ((3+5)+2 = 3+(5+2)). Addition, XOR, min, and max all qualify; subtraction in a fixed order does not.

Why care: if every update to a counter has this property, you can combine partial results computed independently, in any order, and still get the right total.

Now you're ready: NEMO restricts every telemetry update to associative/commutative operations specifically so multiple memory controllers can maintain a global counter without ever coordinating with each other mid-flight.
9SRAM vs. DRAM, and why it matters here▾

SRAM is small, fast, expensive-per-bit on-chip memory (think cache); DRAM is the large, slower, cheaper-per-bit main memory. Reading/writing SRAM costs roughly one cycle with no extra bus traffic; touching DRAM for the same purpose would cost real bandwidth and latency.

Now you're ready: NEMO deliberately keeps all telemetry counters in a small SRAM budget next to the controller — big enough to be useful, small enough to update every single request without becoming a new bottleneck or stealing DRAM bandwidth.
10Match-action tables (the networking idea NEMO borrows)▾

Programmable network switches (the RMT architecture, and the P4 language built on it) solved a strikingly similar problem years ago: process every packet at line rate, but let the operator define custom matching and per-flow counters instead of hard-wiring them into the switch ASIC. The recipe is match (find which flow this packet belongs to) → action (update that flow's state).

Now you're ready: NEMO's match–update–notify pipeline is a direct descendant of that idea, applied to memory requests instead of network packets.
The whole story in one place

NEMO in a nutshell

The problem, the mechanism that fixes it, and how it all connects.

Server memory hierarchies used to be simple enough that fixed hardware counters were good enough, and when they weren't, software sampling filled the gap at a CPU cost datacenters tolerated. Neither survives contact with today's reality: multi-tier DRAM/CXL hierarchies where OS policies need fine-grained, timely, accurate signal about who's touching what — and where that signal has to change shape depending on which policy is asking.

NEMO's answer is to stop treating "what the memory controller counts" as a decision made once, in silicon, years before deployment. Instead, each MC gets a small programmable telemetry pipeline plumbed off the critical datapath, plus a modest SRAM budget to hold counter state. The OS driver installs telemetry rules — filter, translate, update, notify — and reads results back through an ordinary memory-mapped region. Multiple OS subsystems can install independent rules concurrently, and because every update operation is required to be associative and commutative, results from different controllers combine correctly no matter what order you fold them in.

The mechanism is deliberately narrow: one bounded read-modify-write per memory request, following a three-stage match → update → notify pipeline borrowed from programmable network switches. That narrowness is the whole trick — it's simple enough to run at full memory bandwidth with zero added latency, yet expressive enough (as the paper demonstrates across three very different OS policies) to beat both software sampling and fixed hardware counters at once, on every axis that used to force a trade-off.

The payoff: NEMO-based policies detect hot-set changes 5× faster, identify skewed hugepages up to 10.4× faster, and detect noisy neighbors at ~350× lower CPU overhead than the best comparable baseline in each case — translating into up to 1.7× higher throughput and 23% lower latency across three real systems (FlexKVS, FASTER KV, Silo), typically at equal or lower CPU cost than what it replaces.

🍯 Key takeaways

  • Memory telemetry has always forced a trade: software is flexible but costly; hardware counters are cheap but rigid.
  • NEMO adds a small, OS-programmable match–update–notify pipeline right inside the memory controller, off the datapath.
  • Match turns an address into a counter index (mask-shift-add + a small SRAM translation table); update applies an associative/commutative op; notify can raise an interrupt on a threshold.
  • Associative/commutative updates let independent controllers combine state in any order, with zero coordination.
  • Three real OS policies (hot-set tiering, huge-page splitting, noisy-neighbor throttling) each get their own independent telemetry rule, running concurrently on the same hardware.
  • Result: 5–10.4× faster policy reactions, ~350× lower overhead than the closest hardware baseline, up to 1.7× application throughput.
Seven everyday pictures

How to think about NEMO

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Programmable vs. fixed

A speedometer you can reprogram

Your car's factory speedometer only ever answers one question — how fast, right now. Imagine instead a dashboard where you could reprogram what the sensor reports: average speed this mile, time since last stop, distance since fuel — any of these, changed on the fly, without swapping hardware. That's the difference between fixed counters like MBM (one bolted-in question) and NEMO (an instrument you reprogram from software).

Where it misleads: a car's speedometer has effectively unlimited "memory" for its one metric; NEMO's SRAM is genuinely scarce, so it can't reprogram to track literally everything at once — see the time-multiplexing analogy below.
The pipeline · Match, update, notify

A tollbooth with a smart ledger

A car reaches a tollbooth (match: which lane/account does this belong to?), the ledger for that account gets incremented (update: read-modify-write on a counter), and if that account has now run a red flag past its balance, an alarm sounds (notify: threshold check, interrupt). The car itself was never stopped or slowed — the ledger work happens alongside, not on, its trip through the booth.

Where it misleads: a real tollbooth only has one ledger per lane; NEMO can run many independent "ledgers" (telemetries) over the same traffic simultaneously, each counting something different.
The match stage · Translation table

A library card catalog

Before computers, finding a book meant looking up its call number in a card catalog, then walking straight to that shelf slot. NEMO's translation table plays the same role: a small SRAM lookup that converts a memory address (the "title") into a counter index (the "shelf slot") — computed once per configuration, not searched from scratch on every access.

Where it misleads: a card catalog is one flat lookup; NEMO's translation is two-level (a coarse "primary region" lookup, optionally refined by a fine-grained "offset" within it) — more like a catalog that also tells you which shelf and which exact position on it.
Why order-independence matters

Adding up receipts from three cash registers

Three cashiers each ring up sales all day, then someone tallies the day's total by summing the three registers' receipts — in whatever order the slips happen to be stacked. Addition doesn't care about order, so the total is correct regardless. NEMO's update operations are deliberately restricted to this kind of order-independent (associative/commutative) math, so multiple memory controllers can each keep their own local count and combine them later, in any order, with zero coordination between registers while the day is still running.

Where it misleads: not every useful statistic is a cash-register sum — computing a maximum across registers also works this way, but something like "the median sale" does not, which is exactly why NEMO restricts itself to operations with this property rather than supporting arbitrary math.
Resource scarcity · Time-multiplexing

A spotlight sweeping a stage

A single stage spotlight can't illuminate the entire theater at once — so it sweeps, lingering on whatever's most relevant right now. NEMO's SRAM is exactly this scarce: when the OS wants to track more regions than fit in its counter budget, it reprograms the translation table between scans, "sweeping" fine-grained attention across a much larger DRAM footprint over time rather than trying to floodlight everything simultaneously.

Where it misleads: a spotlight physically can't be in two places; NEMO's static rule (the "what to count" logic) stays installed everywhere at once — only the fine-grained targets get time-multiplexed, not the whole mechanism.
Trust boundary · Passive observation

A security camera, not a bag search

A security camera watching a hallway sees everyone who walks through, but never stops, touches, or delays anyone — it just records metadata (who, when) off to the side. NEMO's pipeline works the same way: it snoops a copy of each request's address and type, off the critical datapath, while the real request proceeds untouched to DRAM or CXL. Watching adds no latency because it was never in the way.

Where it misleads: a camera is purely passive; NEMO's notify stage can actively raise an interrupt back to the OS, which is more like a camera that also has an alarm bell wired to it — still not interfering with the hallway traffic itself.
Where the design comes from

An assembly line borrowed from a different factory

Programmable network switches solved "process every packet at line rate, but let the operator define custom counters" years before NEMO existed — the match-action table architecture (RMT, and the P4 language on top of it). NEMO's match–update–notify pipeline is that same assembly-line recipe, retooled to process memory requests instead of network packets.

Where it misleads: network switches typically chain many match-action stages for complex routing logic; NEMO's prototype runs a single bounded stage per request (§6.3 discusses chaining pipelines as future work for richer telemetries like top-K tracking).
Under the hood

The match–update–notify pipeline, stage by stage

Same three stages for every telemetry — what changes between use cases is only the configuration.

Each memory controller is augmented with one or more NEMO pipelines. Every incoming memory request is broadcast (its metadata — physical address, read/write type — is copied) to all installed pipelines at once, while the request itself is routed to DRAM or CXL exactly as before. Each pipeline is replicated per memory channel, so it can process one request per cycle on every channel simultaneously — the paper's FPGA prototype sustains a full read-or-write initiation interval of 1 cycle per channel.

Stage 1 — Match: address to counter index

The match stage uses a fixed-latency mask–shift–add scheme, not a content-addressable search. A configured bitmask and shift extract the bits of the physical address that define a primary region — say, every 2 MiB hugepage in memory. Those bits index a small SRAM translation table, returning a base index into the counter array. If the OS also wants sub-region granularity (which 4 KiB basepage inside that hugepage), a second mask/shift extracts an offset that gets added to the base index to produce the final counter slot.

Translations can be one-to-many — one hugepage's 512 basepages each getting a distinct counter slot — or many-to-one — every hugepage belonging to one tenant collapsing onto the same counter slot. Same hardware, opposite aggregation shape, purely by changing what's stored in the translation table.

Stage 2 — Update: one bounded, safe operation

The update stage performs a read-modify-write on the matched counter using whichever operator the OS configured — add, subtract, XOR, bit-shift, or a comparison — restricted to associative and commutative operations. Every channel in the pipeline owns its own telemetry-state SRAM bank, so bank conflicts across channels never arise; a 1-cycle SRAM read/write latency plus value forwarding avoids data hazards when consecutive requests hit the same counter, without ever stalling the pipeline.

Stage 3 — Notify: line-rate alerting

After an update, the pipeline can evaluate a comparison predicate against the new value (e.g. "≥ threshold") and raise a hardware interrupt if true. This is what lets urgent policies (a tenant just exceeded its bandwidth cap) react immediately rather than depending on the OS to poll fast enough to catch the moment it happened.

The control plane: how the OS actually uses this

A NEMO telemetry is installed by specifying five things: a memory-request filter (read/write type, address range), a translation rule, an update operation, an optional notify predicate, and an optional read-side-effect (e.g. reset-to-zero on every poll, so each read reports only the latest interval rather than a lifetime total). The driver validates every installed rule against the kernel's existing page-ownership checks — a telemetry can only be pointed at memory the requesting subsystem actually owns.

Reading results back is deliberately unglamorous: each controller advertises a telemetry region, a physically contiguous address range backed by MC SRAM. The driver reserves this region in the kernel so it's never used for anything else, and OS subsystems simply issue ordinary loads against it — the controller intercepts these and returns live telemetry state instead of routing to DRAM.

Because every update is associative/commutative, the driver can reconstruct one logical, cross-controller value from independent per-MC states by folding them together with the same combine rule (sum for addition, XOR for XOR, and so on) — in any order, with no need for the controllers to have coordinated while the underlying requests were actually happening.

The paper's real numbers

Following three telemetries end to end

Each example builds on the last — page hotness, then within-page skew, then per-tenant bandwidth.

① Page hotness: one counter per hugepage

The simplest possible NEMO telemetry: match every read or write, derive a key from the request's physical address by masking and shifting away the offset within a 2 MiB hugepage, and increment that hugepage's counter on every access. The OS periodically polls the counter array to estimate which hugepages are hot, with the read side-effect resetting counters to zero on every poll so each interval reports fresh counts rather than a lifetime total.

This is exactly the telemetry MEMTIS-NEMO installs to replace PEBS-based hugepage-access-count sampling (§5.2) — and because NEMO counts every access rather than a 0.02%-rate sample, its signal doesn't need to "warm up" the way sampled counts do.

② Within-page skew: adding a sub-region offset

MEMTIS needs more than "is this hugepage hot" — it needs to know whether the heat is spread evenly across the hugepage or concentrated in a handful of its 4 KiB basepages (a "skewed" hugepage, worth splitting). NEMO extends example ① with a second mask/shift: the primary key still identifies the hugepage, but a sub-region offset now identifies which 4 KiB basepage inside it, giving one counter per basepage — 512 counters per tracked hugepage.

// static rule, installed once
nemo_telemetry_t t = nemo_register_telemetry({
  .filter      = {.type = R|W},
  .translation = {
    .primary = {.mask = NEMO_ALL_MEM, .shift = HP_SHIFT},  // which 2 MiB hugepage
    .sub     = {.mask = HP_BP_MASK,   .shift = BP_SHIFT},  // which 4 KiB basepage inside it
  },
  .update      = {.op = NEMO_OP_ADD, .operand = 1},
  .read_effect = {.op = NEMO_OP_RESET, .value = 0},
});

// dynamic part: retarget WHICH hugepages get basepage-level tracking
void reprogram(uint64_t hp_paddr[], int npages) {
  for (int i = 0; i < npages; i++)
    nemo_set_translation(t, /*key=*/ hp_paddr[i] >> HP_SHIFT, /*region_idx=*/ i);
}

The static rule's shape never changes; what changes, via reprogram(), is which hugepages that shape is currently pointed at. This split — fixed rule, dynamic targets — is exactly what lets a small SRAM budget cover far more of DRAM than it could hold counters for simultaneously, by retargeting between scans (worked in example ④ below).

💡

A hugepage's skewness score falls straight out of these basepage counters: if none of its 512 basepages are hot, the score is 0; the more concentrated the heat, the higher it climbs. Unlike PEBS-derived scores, which get distorted by sampling and by "cooling" (aging out old samples so stale hot pages don't look permanently hot), NEMO computes this directly from a brief window of complete counts — the paper reports this is what lets MEMTIS-NEMO find 2× more genuinely skewed hugepages than the PEBS baseline.

③ Per-tenant bandwidth: collapsing many pages to one counter

The noisy-neighbor use case (§5.3) needs the opposite aggregation shape from example ②: not "many counters per hugepage" but "one counter for every hugepage a tenant owns, no matter how many." NEMO's translation table supports this directly — map every hugepage belonging to tenant i onto the same state index, region i. The notify predicate then fires an interrupt the instant that tenant's running total crosses its allocated bandwidth cap.

nemo_telemetry_t t = nemo_register_telemetry({
  .filter      = {.type = R|W},
  .translation = {
    .primary = {.mask = NEMO_ALL_MEM, .shift = HP_SHIFT},  // many hugepages...
  },
  .update      = {.op = NEMO_OP_ADD,  .operand = 1},
  .notify      = {.op = NEMO_OP_GE,   .operand = BW_CAP},  // interrupt on cap breach
  .read_effect = {.op = NEMO_OP_RESET, .value = 0},
});

// map EVERY hugepage of tenant i to tenant i's single state slot
for (i = 0; i < n_tenants; i++)
  for (j = 0; j < tenant[i].n_hp; j++)
    nemo_set_translation(t, tenant[i].hp_paddr[j], /*region_idx=*/ i);

A userspace QoS controller then polls each tenant's counter, maintains a moving average of bandwidth, and proportionally adjusts that tenant's Linux cgroup CPU quota — the throttling lever the paper uses, chosen because Intel's Memory Bandwidth Allocation (MBA) was found inaccurate for this purpose in this and prior work.

④ How far one SRAM budget can reach (the sweep-time math)

When the region the OS wants to watch exceeds resident SRAM, the driver time-multiplexes by reprogramming translation entries between scans. The paper works out how fast one full sweep of an M-byte DRAM region takes, with P pipelines, S states of width W at granularity G, and scan period τ:

Tsweep = (M × τ × W) / (|SRAM| × G)

Plugging in the MEMTIS-NEMO prototype's actual numbers — P=7 pipelines, S=8,192 states each, τ=500 ms scan period, and using |SRAM| ≈ P×S×W to substitute for the raw SRAM capacity — a 1.4 MiB telemetry budget sweeps a full 16 GiB of DRAM in roughly 37 seconds. The two knobs that matter: the DRAM-to-SRAM ratio sets an area-vs-timeliness trade-off directly, while halving the counter width W (say, from 8 bytes down to 1–4) proportionally shrinks either the SRAM footprint needed or the sweep time, for free, since it doesn't touch P, S, or τ at all.

Check your understanding

Five questions, with answers

Try each before revealing the answer. Every answer also names the misconception it's testing for.

easy
Q1. NEMO's SRAM budget for a prototype pipeline is doubled, with everything else held constant. What happens to the sweep time Tsweep for covering a fixed DRAM region?
Reveal answer
It roughly halves. From Tsweep = (M×τ×W)/(|SRAM|×G), sweep time is inversely proportional to |SRAM| — doubling the SRAM budget lets the same scan period τ cover twice as many regions per sweep, so it takes half as long to visit them all once.Misconception check: this rules out thinking sweep time depends mainly on DRAM size alone — it's the SRAM-to-DRAM ratio that sets the trade-off, and DRAM size (M) and SRAM size trade off symmetrically in the formula.
medium
Q2. Why does NEMO restrict every update operation to being associative and commutative, rather than allowing arbitrary per-request computation?
Reveal answer
Because memory is interleaved across multiple controllers at fine granularity, and each controller only sees its own slice of traffic. Associative/commutative operations can be combined in any order without coordination, so each controller can maintain a correct local partial state, and the OS driver reconstructs one correct global value later by folding the per-controller states together — no locking or ordering protocol needed between controllers while requests are still arriving.Misconception check: this isn't primarily about hardware simplicity for its own sake (though that helps too) — it's specifically what makes multi-controller correctness possible without a synchronization protocol.
medium
Q3. A hugepage's basepage-skewness telemetry reports a score of exactly 0. What does that tell you about its access pattern?
Reveal answer
None of its 4 KiB basepages have been accessed during the current tracked interval — the hugepage looks uniformly cold from NEMO's counters, not "evenly hot." A score of 0 is what an entirely untouched (or entirely-outside-the-observation-window) hugepage produces, same as it would for a page that's simply not part of the working set right now.Misconception check: a low skewness score does NOT mean "evenly hot across all basepages" — that would actually still register as some non-zero uniform access count on every basepage. Zero specifically means no tracked basepage-level activity was observed at all.
hard
Q4. NEMO's paper argues its hardware path introduces no new observable timing side channel. What's the argument, and what's explicitly out of scope?
Reveal answer
The argument: NEMO runs entirely off the critical datapath at fixed per-request cost — it observes metadata and updates SRAM state, but memory access latency doesn't depend on what state currently exists in that SRAM, so an attacker watching access latency learns nothing new about telemetry contents that they couldn't already learn from cache and DRAM timing. Explicitly out of scope: side channels that already exist independent of NEMO — cache-timing and DRAM-timing channels are unaffected either way, and the paper's threat model assumes telemetries are configured only by a privileged operator, with a paravirtual interface validating every guest VM's telemetry requests against its own allocated memory ranges.Misconception check: "no new side channel" is a narrower claim than "no side channels exist at all" — NEMO isn't claiming to close cache/DRAM timing channels, only that it doesn't add to them.
hard
Q5. Why can't NEMO compute a running variance (e.g., of per-region access intervals) in a single pipeline the way it computes a running sum?
Reveal answer
Variance needs two pieces of running state updated together on every access — a running sum AND a running sum-of-squares — but each NEMO pipeline performs exactly one bounded read-modify-write per request, on one counter. The paper's workaround is to run two independent pipelines, one maintaining each sum (both individually associative/commutative and therefore both safely combinable across controllers), and combine the two results in software afterward to compute the variance.Misconception check: this is a limit on per-request arithmetic complexity, not a limit on what NEMO can eventually express — chaining multiple pipelines (§6.3) is the paper's sketched path to richer statistics without violating the one-bounded-op-per-request constraint.
Questions worth asking

FAQ

QHow is this actually different from Intel MBM or PEBS?▾
MBM gives fixed aggregates (per-socket or per-channel bandwidth) baked in at chip design time — you can't ask it for per-page or per-tenant numbers it wasn't built to produce. PEBS is flexible in principle (it samples real memory events) but only sees a sample, misses entire traffic classes like prefetches and non-temporal stores, can't observe from the host into a VM guest, and gets expensive fast if you push the sample rate up for better fidelity. NEMO sees every request and lets the OS define the aggregation — the combination neither existing option offers.
QDoes watching every memory request slow anything down?▾
No added latency on the actual memory access — NEMO's pipeline runs off the critical datapath, broadcasting a copy of request metadata to all its pipelines while the real request is routed to DRAM/CXL untouched. The design target was explicitly an initiation interval of 1 cycle per channel, so it never itself becomes a new bottleneck.
QWhat happens when SRAM runs out — can't NEMO track everything at once?▾
Correct, and this is the real constraint. NEMO's SRAM is small (kilobytes to a few MiB), so when the OS wants more telemetry regions than fit, it time-multiplexes by reprogramming translation-table entries between scans — exactly what MEMTIS-NEMO does to cover 112 hugepages at basepage granularity using only 8 physical pipelines. The Tsweep formula in the worked examples above quantifies the resulting area-vs-timeliness trade-off.
QCan two different OS subsystems use NEMO for different things at the same time?▾
Yes — that's the whole point of exposing it as installable rules rather than a single global mode. The paper's three use cases (HeMem tiering, MEMTIS huge-page splitting, cgroup noisy-neighbor throttling) each install their own independent telemetry with its own filter, translation, and update logic, and nothing stops them running concurrently on the same hardware, budget permitting.
QIs this only useful for CXL memory?▾
The FPGA prototype happens to be a CXL expander because that's where dev kits with CXL 2.0 Type-3 support are available today, but the design targets memory controllers generally, including integrated memory controllers (IMCs) on the CPU package. The paper notes recent Xeon processors already support delivering memory responses to additional consumers without hurting cache performance, which is the hook an IMC implementation would use to gain full-tier coverage.
QWhy not just store telemetry counters in DRAM instead of dedicated SRAM?▾
Because every update would then cost two extra DRAM accesses (one read, one write-back) on top of the original request, and would compete for the same bandwidth the OS is trying to observe and protect. Keeping counters in a small SRAM budget near the controller means updates are essentially free — no added datapath bandwidth, no interference with the traffic being measured.

THPTransparent Huge Pages — Linux's automatic coalescing of 4 KiB pages into 2 MiB hugepages.
Hugepage bloatWhen only a few base pages within a huge page are hot, but the whole huge page stays pinned in the fast tier.
RMT / P4Reconfigurable Match Tables and the P4 language — the programmable-switch architecture NEMO's pipeline design is inspired by.
Associative / commutativeOperations where grouping / order doesn't affect the result — required for NEMO updates so multi-controller states combine correctly without coordination.
Sweep time (Tsweep)How long it takes to visit every telemetry region once when time-multiplexing a limited SRAM budget across more regions than it can hold simultaneously.
Noisy neighborA co-located tenant whose memory-bandwidth usage degrades a latency-sensitive neighbor's performance.
Telemetry regionA memory-mapped SRAM range the OS reads via ordinary loads to retrieve live telemetry state from a controller.
