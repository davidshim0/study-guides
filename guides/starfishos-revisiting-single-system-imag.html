SOSP 2026 · A Field Guide

Make the pod feel like one machine — by sharing as little as possible

Eight machines, one CXL memory pool. StarfishOS makes them look like a single big computer to unmodified programs — by keeping almost everything in local DRAM and pushing only the coordination sliver onto CXL.

📄 "StarfishOS" · Wu, Yan, Dong, Cai, Xu, Xin, Chen (SJTU) 🎓 Some OS/microkernel basics assumed — primers cover them ⏱ ~25 min read
🪸

Keep state PRIVATE in local DRAM by default; put on CXL only what coordination truly requires.
Small shared state is fast to touch and cheap to make crash-safe.

Before you begin

Quick glossary, then eight primers

Acronyms first, then the background ideas the paper leans on. Primers are collapsed — open what's unfamiliar.

Quick glossary

SSISingle System Image — an OS abstraction presenting many machines as one (one address space, PID/file namespaces).
IPCInter-Process Communication — how a client invokes a server; local (context switch) or cross-machine (message passing).

1What CXL and a "CXL pod" actually are▾

CXL lets several rack-scale hosts plug into a shared memory device and access it with ordinary load/store instructions, coherently — no network stack, no serialization. A CXL pod is this cluster: several machines, each with private DRAM, plus one shared CXL memory pool they all reach directly.

Now you're ready: the whole paper is about deciding, for every piece of OS/app state, whether it lives in a machine's private DRAM or in the shared CXL pool.
2Single System Image (SSI)▾

SSI makes a cluster of machines look like one machine to software: one address space, one process-ID space, one filesystem. A multithreaded program written for a single box can run its threads on any machine in the pod, unmodified, because the OS — not the app — handles the cross-machine plumbing.

Now you're ready: StarfishOS is "the first OS-level SSI built on CXL" — it uses CXL's shared memory to make the SSI illusion efficient instead of message-passing-slow.
3Microkernel vs. monolithic kernel▾

A monolithic kernel (Linux-style) runs filesystems, drivers, and most services inside kernel space, all sharing kernel memory implicitly. A microkernel keeps the kernel to a minimum — IPC, scheduling, memory management — and runs everything else (filesystems, process managers) as ordinary user-space processes.

Now you're ready: less kernel-space state, and state that's already organized as explicit objects, is exactly what makes fine-grained "what goes on CXL" decisions tractable.
4Capabilities and capability-based state▾

In capability-based microkernels (seL4-style, and StarfishOS's base kernel ChCore), every kernel object — a thread, an address space, a memory region — is a typed, named entity, and a process holds explicit capabilities (unforgeable references) to the objects it may use. Nothing is reached through an implicit global pointer.

Now you're ready: because objects and their references are explicit, StarfishOS can place each object in DRAM or CXL individually, and reconstruct reachable state after a crash by walking capabilities.
5Local IPC vs. message-passing IPC▾

seL4/L4-style local IPC is a direct, synchronous context switch into the server thread — extremely fast, but it assumes the server's memory is right there. Traditional distributed systems instead pass messages over a network, which is slower but works across machines.

Now you're ready: StarfishOS keeps fast local IPC for same-machine calls and adds a new CXL-queue-based message-passing path only for calls that cross machines.
6Why only a small region of CXL is cache-coherent▾

Making a large memory region cache-coherent across many hosts is hardware-expensive, so real CXL deployments keep the coherent region to a few hundred MiB. Data outside it can still be accessed, just without hardware coherence guarantees.

Now you're ready: this is a second, independent reason (besides speed) to keep CXL-resident state small — it must fit in that scarce coherent region.
7Partial failure and fail-stop machines▾

In a CXL pod, a host's CPU/DRAM can fail (power loss, crash) while the CXL memory module — with its own power supply — stays alive and reachable by survivors. This is a partial failure: some of the shared state a crashed host was mid-updating may now be inconsistent, and other machines can still see it.

Now you're ready: the danger isn't "a machine dies" — it's "a machine dies while holding a CXL lock or half-writing a shared structure," which can block or corrupt everyone else.
8Lock-free & crash-consistent data structures▾

Lock-free means no thread ever holds an exclusive lock that a crash could leave stuck forever — progress uses atomic compare-and-swap (CAS) instead. Crash-consistent (here, "detectably recoverable") means after a crash, the structure's state always corresponds to some valid point in its history, and you can tell exactly how far an interrupted operation got.

Now you're ready: StarfishOS's shared IPC/scheduler/notification queues and CXL allocator are built entirely on such structures — that's how a crashed machine can't wedge the others.
The whole story in one place

StarfishOS in a nutshell

The all-or-nothing trap, the fix, and why a microkernel makes the fix practical.

CXL lets a pod of machines share memory directly, so cross-machine coordination could in principle just be normal load/store instead of message passing. The obvious way to exploit this — put all OS and application state in CXL, so any existing OS runs unmodified on the whole pod — hits two walls: CXL is 2–5× slower and thinner in bandwidth than local DRAM, so this can cost up to a 2.4× slowdown; and because CXL memory outlives a crashed host, a partial failure can leave shared structures corrupted or locked, turning one dead machine into a pod-wide outage.

StarfishOS's fix is state partitioning: keep almost everything in private per-machine DRAM, and place in CXL only the minimal state actually needed for cross-machine coordination — IPC/scheduler queues, a shared allocator, small coordination metadata, and a handful of application objects. Because that shared slice is small, it can be engineered with lock-free, crash-consistent data structures, so a crashed machine can't block or corrupt the rest.

This is easiest to do in a microkernel, because its kernel-space state is small and enumerable, and its capability-based objects (CapGroup, VMSpace, PMO, Thread, IPC, Notification) already give every piece of state an explicit type and explicit references — so "which objects go on CXL?" is a concrete, answerable question rather than an archaeology project through implicit kernel globals.

The payoff: unmodified single-machine applications (Phoenix, DB×1000, GeminiGraph) auto-scale across 8 machines with 2.0–3.5× speedup and zero code changes, beating their distributed-redesign versions by up to 5.2×, and reaching 4.1× the throughput of a CXL-optimized database rewrite (Tigon) — while using only a few hundred MiB of CXL for working sets of gigabytes.

🪸 Key takeaways

  • All-in-CXL is simple but slow (2–5× latency, thinner bandwidth) and fragile under partial failure.
  • State partitioning: private DRAM by default, CXL only for coordination — fixes speed and failure together.
  • Microkernels make partitioning tractable: small kernel state + explicit capability objects = per-object placement.
  • CXL-resident state is made partial-failure resilient with lock-free, detectably-recoverable structures.
  • Services use micro-reboot (not whole-OS reboot); applications recover with their own mechanisms, not OS magic.
  • Result: 2.0–3.5× auto-scaling speedup, up to 5.2× over distributed redesigns and 4.1× Tigon's throughput, near-zero extra code.
Six everyday pictures

How to think about StarfishOS

Read in any order. Each ends with where the picture stops being true.

The core idea · State partitioning

Packing for a shared road trip

Everyone keeps their own backpack (private DRAM) — toothbrush, clothes, stuff nobody else needs. Only what the group must coordinate — the map, the shared cooler — goes in the trunk everyone can reach (CXL). Pack the whole trunk with everyone's individual stuff and it's heavy and someone's socks block someone else's food.

Where it breaks: a backpack owner can't crash mid-trip; a machine can. So the shared trunk (CXL state) needs to survive a "backpack owner" vanishing — hence lock-free structures, not just "keep it small."
Why a microkernel · Capabilities

An itemized packing list

Instead of one duffel bag of unlabeled stuff (a monolithic kernel's implicit state), a microkernel gives you a checklist: this thread, this memory region, this IPC channel — each named, each with an owner. You can point at any one line and say "this goes in the trunk, that stays in the backpack."

Where it breaks: the paper is careful to say a monolithic kernel could do the same partitioning in principle — the list just isn't handed to you for free; you'd have to write it yourself.
Failure resilience · Lock-free queues

A relay baton dropped mid-race

If a runner collapses mid-handoff, a normal relay stalls — nobody else can pick up a baton mid-transfer. StarfishOS's shared queues are built so the "baton" (a CAS-linked node) is always either fully placed or not there at all; if the runner (a machine) drops out, any other runner can safely see exactly how far the handoff got and continue.

Where it breaks: the analogy hides that a crashed dequeuer (consumer) can still lose or leave an in-flight request half-handled — the paper resolves this per-component (retry, ABORT, or checking a log), not by magic.
Application state · Page-fault migration

Forwarding mail only when it's requested

Your mail defaults to your home address. Only when someone at another address actually asks for a specific letter does it get forwarded (migrated to CXL) — and only that letter, not your whole mailbox. StarfishOS moves a heap page to CXL only on the page fault that proves another machine needs it.

Where it breaks: forwarded mail doesn't usually come back; StarfishOS does migrate cold CXL pages back to DRAM when CXL fills up (≈80%), in batches, picking the least-shared, oldest pages first.
Service resilience · Micro-reboot

Swapping a blown fuse, not the whole panel

One blown fuse (a crashed filesystem instance) cuts power to one circuit, not the house. You replace the fuse (restart just that user-space service instance on a surviving machine) and that circuit comes back — the rest of the house never noticed.

Where it breaks: a fuse swap is instant; a stateful service like the filesystem must first reload from disk, then replay a small crash log (p-log) to catch up — that replay isn't free (hundreds of ms in the paper's test).
Failure scope · Partial failure model

Losing one branch office

A company with independent branch offices doesn't shut down headquarters when one branch loses power — that branch's ongoing work is lost, but the company and other branches keep operating. StarfishOS's failure model mirrors this deliberately: a machine crash looks like losing the processes/threads that ran there, not like losing the OS.

Where it breaks: a company can usually re-assign a branch's unfinished customer orders to another branch; StarfishOS does not transparently resume a crashed app's work elsewhere — the app must recover itself (e.g., via its own logging/replay).
The full explanation

How it actually works

Layer by layer: the two extremes it rejects, then how kernel, services, and applications each partition their state.

1 · Two extremes, both rejected

Keep all state in local DRAM and coordinate by message passing (classic SSI like Locus/Hive/fos): correct, but doesn't exploit CXL's shared-memory speed. Put all state in CXL so any unmodified OS "just works" as if on one big shared-memory machine: simple, but up to 2.4× slower (CXL is 2–5× the latency, 20–80% the bandwidth of local DRAM) and fragile — a host crash can leave a CXL-resident lock unreleased or a structure half-updated, and survivors touching it may block or crash too.

2 · The fix: partition state by layer

StarfishOS applies the same rule at every layer of the stack: only state needed for cross-machine coordination goes on CXL; everything locality-sensitive stays in private DRAM.

LayerWhat stays in DRAMWhat goes on CXLFailure handling
Kernel moduleslocal scheduling, thread contextIPC/scheduler queues, notification lists, CXL allocator metadatalock-free, detectably-recoverable queues + lock-free buddy allocator
System servicesfull per-instance state (inodes, pages, connections)global coordination metadata (e.g. mount-point ownership)micro-reboot the instance; non-uniform services replay a p-log
Applicationsthread context, stack, private heap pagesCapGroup/VMSpace/PMO + pages proven to be shared (page-fault-driven)OS reclaims reachable state; app recovers itself

3 · Kernel-space: IPC, scheduling, notification

Local IPC keeps its original seL4-style direct context switch. Cross-machine calls instead use a per-service FIFO queue in CXL: the client builds a request node, enqueues it (linearizing with one CAS), and either waits or polls for status==DONE; the server dequeues, executes, and flips the status. Scheduling works the same way — remote threads land in a per-core shared queue in CXL, and a CXL MSI (3–20 µs) wakes the target core's scheduler promptly instead of waiting for the next timer tick. Notification's waiting-list also moves to CXL, storing only a pointer-plus-CPU-ID per waiter so a remote notifier never dereferences another machine's private memory directly.

4 · Memory management: two allocators, one crash-safety plan

Kernel space keeps a normal buddy/slab allocator for DRAM, and adds a separate lock-free CXL path: a lock-free buddy system (LLFree) for page-granularity CXL allocation — 2 MiB huge-page operations update their metadata with a single CAS and are crash-safe outright, while 4 KiB page alloc/free go through multiple atomic updates and can leave the free counter momentarily inconsistent until recovery reconstructs it from the bitmap — plus a per-CPU slab layer for small objects, where cross-machine frees are logged and reclaimed asynchronously by the owner, with a small undo-log to make interrupted slab operations safely retryable. User space gets a similar DRAM/CXL-aware malloc, defaulting to local DRAM unless an application opts into CXL placement.

5 · Application state: object-by-object, then page-fault-driven for the rest

A process is a set of capability objects (Table 2 of the paper): CapGroup, Thread, VMSpace, PMO, IPC, Notification. Thread context and stacks are per-thread and stay private in DRAM. Small, infrequently-touched metadata (CapGroup, VMSpace, PMO) goes to CXL because it must be visible pod-wide. The bulky, mixed-locality regions — heap, code, .bss/.data — default to DRAM and migrate a page to CXL only on the page fault that proves a remote machine needs it, using a special "migration" PTE to block concurrent access mid-copy, then updating each machine's local page-table replica.

6 · Collaborative system services and partial-failure recovery

Each service (filesystem, network, process manager) runs as several per-machine instances, each owning a disjoint slice of the resource space (e.g. one mount point), with only an ownership map in CXL. On a machine failure, StarfishOS marks its instances offline, restarts the lost ones elsewhere via micro-reboot, and (for stateful services like the filesystem) replays a bounded 4 MiB per-instance crash log (p-log) to recover updates not yet flushed to disk. Applications get no such transparent recovery: if any of an app's threads or required DRAM state was on the failed machine, the whole app is terminated and its resources reclaimed by walking its CapGroup — recovery is left to the app's own mechanisms (logging, restart, replay).

Follow the numbers

Worked examples

Four calculations straight from the paper's measurements.

① What "2–5× slower" costs in raw numbers (Table 3)

Local DRAM: 107 ns / 52 GiB/s. Remote CXL: 383 ns / 0.3 GiB/s. What's the actual penalty?

  1. Latency ratio: 383 ns ÷ 107 ns ≈ 3.6× — squarely inside the paper's claimed 2–5× range.
  2. Bandwidth ratio: 0.3 ÷ 52 ≈ 0.6% of local DRAM bandwidth per remote-CXL channel — the real bottleneck is bandwidth, not latency.
  3. Local CXL is milder: 241 ns / 2 GiB/s — 2.25× the latency, ~4% the bandwidth of local DRAM.
🪸
Insight: the bandwidth gap (hundreds of ×) is far scarier than the latency gap (single-digit ×) — which is exactly why partitioning targets how much traffic touches CXL, not just how state is organized.

② IPC latency: where does remote overhead come from?

Read-4KiB IPC: local P50 = 2.8 µs, remote P50 = 5.5 µs, remote-concurrent P50 = 24.3 µs, P99 = 33.1 µs.

  1. Single-sender remote overhead: 5.5 − 2.8 = 2.7 µs — the cost of the CXL queue round-trip itself.
  2. Concurrency overhead: 24.3 − 5.5 = 18.8 µs at P50, mostly queueing (the paper attributes ~16 µs of this to service-side serialization, not to extra cacheline flushes).
  3. Tail cost: P99 adds a further 33.1 − 24.3 = 8.8 µs on top of the P50-concurrent case — a fatter tail under contention, as expected for a shared queue.
💡
The paper's Enq/Dequeue cost is only ~1.4 µs — the crash-recoverable queue itself is cheap; contention at the server, not the recoverability machinery, dominates tail latency.

③ How little CXL is actually used?

Table 5, 8 machines: Matrix Mult. uses 109 MiB CXL of 1 GiB total; DB×1000 uses 500 MiB of 26 GiB; GeminiGraph uses 600 MiB of 9 GiB.

  1. Matrix Mult.: 109 ÷ 1024 ≈ 10.6% of its working set touches CXL.
  2. DB×1000: 500 MiB ÷ 26 GiB ≈ 1.9% — and that figure is a deliberately imposed cap, not a measured minimum.
  3. GeminiGraph: 600 MiB ÷ 9 GiB ≈ 6.7%.
🪸
Insight: across three very different workloads, single-digit-percent CXL usage is enough to get 85–92% of an idealized all-local-DRAM configuration's performance (§9.4) — the partitioning principle generalizes.

④ Recovering a crashed LevelDB instance (§9.6, Fig. 18)

Crash detection: 19 ms. Filesystem micro-reboot + p-log replay (446 entries): 534 ms. LevelDB's own in-memory restart: 74 ms. Warm-up to steady state: ~3 s.

  1. Time until the filesystem is usable again: 19 + 534 ≈ 553 ms after the crash.
  2. Time until LevelDB itself is serving: 553 + 74 ≈ 627 ms — well under a second, without rebooting the pod.
  3. Full throughput recovery: add the ~3 s warm-up — the application layer, not the OS layer, dominates total time-to-full-speed.
💡
Most of the fast part (627 ms) is OS-level: micro-reboot plus a bounded 4 MiB p-log replay. That bound is deliberate — it keeps worst-case recovery predictable regardless of how much was written before the crash.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
"CXL is just slower DRAM, so putting everything on it is safe, just a bit slow." What's wrong with this reasoning?
Show answer
It ignores partial failure. CXL memory has its own power supply and can outlive a host crash, so state left there can be caught mid-update when its owning machine dies — unlike DRAM, which simply vanishes with its machine. Slowness is one problem; a crash corrupting or locking shared state for survivors is the other, independent one.Misconception: that CXL's downside is purely a performance number. The paper treats speed and partial-failure resilience as two separate obstacles that state partitioning happens to fix together.
Problem 2 · medium
Is a microkernel required to do state partitioning?
Show answer
No. The paper explicitly says a monolithic kernel could apply the same rule by explicitly identifying every object and dependency and building isolated service recovery — it's just impractical, because monolithic kernel state is spread across subsystems with implicit references. Microkernels are a practical engineering fit, not a logical necessity.Misconception: treating "microkernel" as part of the theorem rather than the implementation choice that makes the theorem tractable.
Problem 3 · easy
Using Table 3, roughly how much worse is remote CXL bandwidth than remote DRAM bandwidth?
Show answer
Remote DRAM is 30 GiB/s; remote CXL is 0.3 GiB/s. That's a 100× gap — far larger than the latency gap (383 ns vs 160 ns, about 2.4×). Bandwidth, not latency, is the sharper edge of CXL's cost.Misconception: assuming "2–5× slower" (the paper's headline number) describes bandwidth too. It describes latency; bandwidth degrades much more.
Problem 4 · medium
In DurableQueue, why does a producer (enqueuer) crash never block the queue, while a consumer (dequeuer) crash can lose a request?
Show answer
Enqueue's linearization point is a single CAS; if a producer dies before it, nothing was ever published (no effect); if after, the node is durably linked and any other machine can finish/help the link — so the queue structure itself is never left inconsistent. Dequeue, by contrast, involves marking a node DOING then actually handling it (e.g. running a service call); a crash mid-handle can leave that specific request incomplete, which is a semantic loss (needs retry/ABORT), not a structural corruption.Misconception: assuming "lock-free" means no request can ever be lost. It means the data structure can't be left corrupted or locked — individual in-flight requests can still need applic­ation-level recovery.
Problem 5 · medium
A heap page is created on Machine0 and never touched by any other machine. Where does it live, forever?
Show answer
In Machine0's private DRAM. StarfishOS only migrates a page to CXL when a page fault from another machine proves cross-machine access is actually happening — no access, no migration, no CXL cost at all.Misconception: assuming shared-memory-capable apps automatically push their whole heap onto CXL "just in case." Migration is strictly demand-driven.
Problem 6 · hard
Machine2 crashes. An application had 3 of its 8 threads running there, and some of its heap pages were private DRAM on Machine2. What happens to this application under StarfishOS, and why doesn't the OS just migrate its surviving 5 threads to keep it running?
Show answer
StarfishOS terminates the entire application and reclaims its resources (by walking its CapGroup), even though 5 threads were healthy. This is deliberate: the paper's failure model provides OS-level resilience, not transparent application recovery — private DRAM state lost with Machine2 (part of that app's heap) can't be reconstructed by the OS without knowing the application's semantics, so letting the other 5 threads limp on with a torn address space would risk silent corruption. Recovery is left to the app's own logging/checkpointing.Misconception: expecting the OS to "heal" a partially-crashed app automatically, the way it heals a crashed filesystem instance. Services are stateless-enough (or logged) for micro-reboot; arbitrary applications generally aren't.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is StarfishOS a hypervisor or a distributed filesystem?▾
Neither. It's an OS kernel (built on the ChCore microkernel) running across multiple physical machines connected by CXL, presenting them as one single-system-image machine. It replaces the whole OS stack — kernel, services — not just storage or virtualization.
Q2Do applications need to be rewritten?▾
No — that's the headline claim. Unmodified applications (Phoenix, DB×1000, GeminiGraph, Redis, Memcached, LevelDB) run with zero code changes; the 2.0–3.5× auto-scaling-across-the-pod result specifically covers Phoenix Matrix Mult., DB×1000, and GeminiGraph, while Redis, Memcached, and LevelDB appear in the paper's other workload, resource-utilization, and recovery experiments.
Q3Why not just use a DSM (distributed shared memory) library instead?▾
DSM libraries give programmers a shared-memory illusion too, but efficient DRAM/CXL data placement still typically requires application-specific redesign, and DSM alone can't provide pod-wide resource pooling (scheduling threads onto any idle core). OS-level SSI can do both.
Q4What exactly gets checked to decide DRAM vs. CXL placement?▾
It's not automatic profiling — it's structural. Kernel modules place only their cross-machine coordination structures (queues, allocator metadata) on CXL by design. Applications place small, infrequently-touched capability metadata (CapGroup/VMSpace/PMO) on CXL by design, and migrate heap/code/data pages to CXL only reactively, triggered by an actual remote page fault.
Q5What happens if the CXL memory pool itself is lost?▾
StarfishOS assumes CXL stays reliable (ECC, backup power) and only tolerates individual host failures. If the CXL pool is nevertheless lost or corrupted, the paper states StarfishOS restarts the entire pod — there's no recovery path for that case.
Q6How is this different from LegoOS-style resource disaggregation?▾
LegoOS disaggregates memory/storage from CPU, but each process still runs on a single CPU node — no cross-machine CPU sharing for one process. StarfishOS extends disaggregation to CPUs themselves: one application's threads can span multiple machines while keeping the ordinary process/thread interface, using stranded cores across the whole pod.
Q7Does StarfishOS guarantee an application keeps running through any single machine failure?▾
No. Only if none of the app's threads ran on the failed machine and none of its required DRAM-resident state was there does it continue unaffected. Otherwise the whole app is terminated and its resources reclaimed — the OS stays healthy, the app does not automatically survive.
Q8What's left for future work?▾
The paper keeps this broad rather than naming specific mechanisms: improving the scheduling policy, making migration more efficient, and scaling system services further.

Core terms
State-partitioned microkernelStarfishOS's architecture: kernel-space modules, user-space services, and applications each partition their own state into private-DRAM and CXL-coordination parts.
State partitioningThe design principle: state accessed by one machine stays in local DRAM; state needed for cross-machine coordination goes to CXL.
DurableQueueA lock-free, detectably-recoverable MPSC queue (built on Friedman et al.) used for StarfishOS's IPC, scheduler, and notification queues.
Micro-rebootRestarting only a failed user-space service instance, not the whole OS — feasible because microkernel services are isolated processes.
Page-fault-driven migrationMoving a heap/code/data page from private DRAM to CXL only when a remote machine's page fault proves it needs that page.
p-logA bounded (4 MiB), per-instance crash log (Ananke-style) that lets a restarted filesystem instance replay operations not yet flushed to disk.
Collaborative system serviceA service split into multiple per-machine instances, each owning a disjoint resource slice, with only ownership metadata shared via CXL.
Partial failureA host's CPU/DRAM fails while its CXL-resident state remains accessible and possibly inconsistent to surviving machines.
Supporting terms
CapGroup / VMSpace / PMOCapability objects holding a process's access rights, virtual-address-space metadata, and physical memory pages, respectively.
LLFreeA lock-free, crash-consistent page-frame buddy allocator StarfishOS uses for CXL memory.
Auxiliary/sub page tableEach machine keeps a local replica page table mapping the same global virtual address space, with entries pointing to local DRAM or CXL.
