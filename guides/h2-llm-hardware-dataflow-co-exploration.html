ISCA 2025 · A Field Guide

Giving near-memory logic exactly the area it earns, not whatever silicon leaves over

Stack a chip's logic die directly under its DRAM and you get huge bandwidth — but the wiring that carries it eats the very area you wanted for compute. This is the plain-English story of H2-LLM, an accelerator that splits that area on purpose, then routes each LLM operator to the channel that actually helps it.

📄 "H2-LLM" · Li, Yin, Wu, Zhu, Gao, Niu, Wu, Si, Xie, Zhang, Sun 🎓 Transformer/cache basics assumed — primers cover NMP + hybrid bonding ⏱ ~30 min read
🧩

Bond just enough COMPUTE onto the memory to match its BANDWIDTH — then let each operator pick its memory channel before it picks its compute engine.

Before you begin

Quick glossary, then eight ideas the paper assumes

1Prefill vs decoding — the two faces of LLM inference▾

An LLM request has two phases. Prefill processes the whole prompt (hundreds to thousands of tokens) in one shot — lots of parallel work, so it's usually compute-bound. Decoding generates one new token per step, re-reading the growing KV cache each time — very little reuse per byte fetched, so it's memory-bound.

Table 1 in the paper shows this split varies by app: code completion/chat are "decoding-heavy" (prompt and decoding length comparable), while long-context QA is "prefill-heavy" (prompt 20-100× longer than the output).

Now you're ready: H2-LLM's whole dataflow design exists because a good accelerator must handle both — and most prior work only optimized for decoding.
2Near-memory processing, and why it helps decoding▾

A conventional GPU/TPU (the paper's "centralized processor" or CP) fetches everything through one narrow external memory interface. NMP instead puts small processing engines (PEs) inside or next to the memory itself, so many banks can be read/computed in parallel — turning DRAM's bank-level parallelism into extra effective bandwidth.

This is exactly what decoding wants: it's memory-bound, so more parallel bandwidth (not more FLOPs) is the bottleneck to relieve.

Now you're ready: the question the whole paper revolves around is how much compute to give those NMP PEs, since more compute costs area that could otherwise carry more bandwidth.
3In-die NMP: PEs squeezed into the DRAM die itself▾

Commodity designs (Samsung's HBM-PIM/LPDDR5-PIM, SK Hynix's GDDR6-AiM/LPDDR5X-AiM) place PEs directly on the DRAM die, next to the memory arrays. DRAM process technology has slow transistors (3× slower than logic CMOS), low logic density (10×), and fewer metal layers — so only a sliver of area (≈25%) can be spent on PEs without hurting the DRAM's own density.

Table 2 shows the result: 4–16× more bandwidth than an external interface, but only a 1–2 FLOP/Byte computation-bandwidth ratio — a tiny compute budget per byte moved.

Now you're ready: "in-die NMP" is the paper's baseline villain — cheap and high-bandwidth, but starved for compute.
4Hybrid bonding: a separate logic die, Cu-Cu bonded to the DRAM▾

Hybrid bonding (HB) vertically stacks a DRAM die on top of a separate logic die, connected by direct copper-to-copper fusion bonding at very fine pitch (~3µm, ~110,000 connections/mm²). Because the logic die is its own die, you can customize real compute logic on it — using an older, cheaper process node if you like — instead of being stuck with DRAM's scarce transistors.

The catch: driving that many I/O pins requires memory controllers, and those controllers eat logic-die area that would otherwise go to compute. More bandwidth (more pins) directly means less room for FPUs.

Now you're ready: this compute-vs-bandwidth trade-off, unique to HB, is the architecture problem H2-LLM's design space exploration is built to solve.
5Arithmetic intensity and the roofline model▾

Arithmetic intensity = FLOPs of compute per byte of memory traffic. A roofline model plots achievable performance against it: below a device's compute-bandwidth ratio, you're memory-bound (adding compute doesn't help); above it, you're compute-bound (adding bandwidth doesn't help).

Batch size raises a GEMM's arithmetic intensity (more reuse of the same weights); so does reducing KV heads via GQA/MQA (more reuse of the same K/V). Push either far enough and a low-compute device like in-die NMP stops helping at all.

Now you're ready: this is exactly the mechanism behind Fig. 3's finding — in-die NMP loses its advantage once BS ≥ 8 or KV heads ≤ 4.
6Attention variants: MHA, GQA, MQA▾

Plain multi-head attention (MHA) gives every query head its own key/value head. GQA groups several query heads onto one shared KV head pair (fewer KV heads = less memory traffic per token). MQA is the extreme case — all query heads share a single KV head.

Fewer KV heads means less data to fetch from the KV cache per decoding step, which raises the operator's arithmetic intensity — good for the CP, but it also shrinks the memory-bound workload that NMP exists to accelerate.

Now you're ready: LLaMA3 8B (GQA, 8 KV heads) and PaLM 8B (MQA, 1 KV head) stress H2-LLM's dataflow very differently from OPT 6.7B (plain MHA).
7Operator mapping and operator fission▾

Mapping = deciding which compute engine (CP or NMP PEs) runs which operator. Most prior accelerators use a fixed mapping (e.g., "all attention to NMP, all FC to CP") baked in at design time. Operator fission instead splits one operator's output dimension across both engines simultaneously, without duplicating its weights.

Fixed mapping is simple but wastes capability when a workload's needs don't match the fixed split; fission lets both engines pull their weight on the same operator.

Now you're ready: H2-LLM's dataflow abstraction is built to explore fission ratios, not just pick a fixed engine per operator.
8Design space exploration with a genetic algorithm▾

A design space is a huge grid of choices (channel counts, PE sizes, buffer sizes, operator-to-channel bindings, …) — too large to try exhaustively. A genetic algorithm instead keeps a population of candidate designs, evaluates each, keeps the best (top-K), and generates the next generation by mutating or recombining ("crossover") those survivors.

Illegal candidates (ones that overflow a channel's capacity) are discarded before evaluation, so the search only spends time simulating designs that could actually run.

Now you're ready: this is exactly the loop H2-LLM's DSE framework runs — over both architecture parameters and dataflow choices at once.
The whole story in one place

H2-LLM in a nutshell

The problem, the architecture-dataflow co-design that fixes it, and how the pieces connect.

Edge-side LLM serving is low-batch (1–20 requests) and needs to handle both compute-heavy prefill and memory-heavy decoding well. In-die NMP — the standard fix, embedding PEs directly in the DRAM die — gets great bandwidth but almost no compute (1–2 FLOP/Byte), so its speedup evaporates as batch size grows or as GQA/MQA raise attention's arithmetic intensity: exactly the regimes edge inference lives in.

Hybrid bonding looks like the fix — a separate logic die means real, customizable compute — except the very I/O controllers that deliver HB's bandwidth eat up to 40% of that logic die's area (for 1024 pins per bank), directly trading away the compute you bonded it for. H2-LLM is the first design to treat this compute-bandwidth trade-off as a first-class part of the architecture search, alongside a data-centric dataflow abstraction that binds operators to memory channels before deciding which engine computes them — enabling flexible operator fission instead of a rigid, compute-centric fixed mapping.

A genetic-algorithm DSE framework then searches the joint architecture+dataflow space (channel counts, PE size, buffer sizes, MAG/MPG channel bindings, fission ratios) to find the best design per workload.

The payoff: across OPT 6.7B, LLaMA3 8B, and PaLM 8B on four edge datasets (batch size 1/4/16), H2-LLM beats the best enhanced in-die NMP baseline by 2.72× geomean speedup and 1.48× geomean better energy efficiency — 3.81× on decoding-heavy workloads, 1.94× on prefill-heavy ones.

🍯 Key takeaways

  • In-die NMP's speedup saturates and reverses as batch size or GQA/MQA raise arithmetic intensity — 1–2 FLOP/Byte just isn't enough.
  • Hybrid bonding trades bandwidth for logic-die area: 1024 HB I/O pins per bank ≈ 40% of the logic die spent on controllers, not FPUs.
  • Data-centric dataflow binds operators to channels first, engines second — unlocking flexible operator fission without weight duplication.
  • A genetic-algorithm DSE co-searches architecture (channels, PEs, buffers) and dataflow (bindings, fission ratios) together.
  • Result: 2.72× geomean speedup, 1.48× geomean better energy efficiency vs. enhanced in-die NMP — under 1% wasted on synchronization overhead.
Six everyday pictures

How to think about H2-LLM

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Compute vs bandwidth

An apartment above a subway station

Build a building directly over a subway stop and you get amazing transit access — but the escalator shafts eat into every floor's usable space. Hybrid bonding is the same deal: stack DRAM directly on a logic die and you get huge Cu-Cu bandwidth, but the controllers driving those pins occupy up to 40% of the logic floor. H2-LLM's job is choosing how many escalators (pins) to build, on purpose, per workload.

Where it misleads: a building's escalators are fixed once poured; H2-LLM's pin count is a design-time choice explored across many candidate chips, not a single irreversible commitment.
The mechanism · Data-centric dataflow

Booking the warehouse before the movers

A compute-centric scheme books the movers first ("GPU team" or "NMP team"), which locks that team's warehouse bay for the whole job — even if a rival team's bay had spare bandwidth. H2-LLM instead reserves the warehouse bay (memory channel) for the goods (data) first, then decides — flexibly, even splitting the job — which team lifts which boxes. That's what lets one GEMM's output columns be split between CP and NMP without duplicating the pallet of weights.

Where it breaks: real movers can't split a single box between two teams mid-lift; a GEMM's output dimension can be split cleanly because each output column is an independent computation.
The baseline · In-die NMP vs hybrid bonding

A food truck vs a full kitchen

In-die NMP crams a tiny single-burner cooktop into the delivery van itself — it can drive right up to your door (data locality), but the menu is tiny (compute). Hybrid bonding instead builds a full kitchen right beneath the dining room floor, connected by a high-throughput dumbwaiter (Cu-Cu bonding) — a much bigger menu, at the cost of the dumbwaiter shaft eating kitchen floor space.

Where it breaks: a food truck's tiny cooktop is fixed by the vehicle; H2-LLM's "kitchen size" (FPU count) is itself explored across the compute-bandwidth trade-off, not a fixed given.
Scaling · Batch size and the roofline

A canoe vs a cargo ship

A canoe (in-die NMP) is nimble and needs no engine room — perfect when the load (batch size) is light. Load it past its waterline and it stops moving no matter how hard you paddle (the compute ceiling). A cargo ship (the centralized processor) needs a big engine room to even start moving, but once loaded, its horsepower keeps paying off as cargo grows.

Where it breaks: a canoe can't be redesigned mid-voyage; H2-LLM's DSE explicitly re-balances "engine room" (compute) vs "hull space" (bandwidth) for each expected batch size.
Enforcement · Operator fission

Splitting one shipment between express and slow lanes

One customer order (one GEMM operator) can ride partly on the express lane (CP) and partly on the slow lane (NMP) at the same time — same inventory (weights), no duplication — because the output columns are independent parcels that don't need to travel together. That's operator fission: a way to use both engines on the same operator without paying for two copies of the goods.

Where it breaks: real express/slow lanes share a road; H2-LLM's two "lanes" (normal and NMP channels) are physically separate memory paths, so there's no lane-merging traffic cost between them.
The search · Genetic-algorithm DSE

Breeding show dogs across generations

Start with a random litter of candidate designs. Judge each on the metric that matters (latency), keep only the top performers, and breed the next litter from them — sometimes copying a parent with one trait tweaked (mutation), sometimes combining two parents' traits (crossover). Any pup born "overweight" for its kennel (a channel-capacity overflow) is culled before judging.

Where it breaks: dog breeding takes years per generation; H2-LLM evaluates 5,000 candidate designs per generation, for 100 generations, entirely in simulation.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals you can read at a glance.

1 · The problem — in-die NMP's compute ceiling

In-die NMP places PEs on the DRAM die itself, where transistors are 3× slower and 10× less dense than logic CMOS, and only ~25% of area can go to PEs without hurting DRAM density. The result (Table 2): 4–16× more bandwidth than an external interface, but only 1–2 FLOP/Byte of compute per byte moved. As §3.1's roofline analysis on 8 LPDDR5-PIM channels shows, in-die NMP helps FC operators up to BS < 8 and attention operators down to KV heads > 4 — past those points, the centralized processor is still memory-bound, yet NMP can no longer add anything, because it's now the one running out of compute.

🌱
Concretely: at BS=16, in-die NMP (ID-NMP) only reaches 71% of the plain centralized-processor-only (CP) baseline's performance — a heterogeneous accelerator that's worse than not having NMP at all.

2 · Hybrid bonding's integration overhead

HB stacks the DRAM die on a separate logic die via Cu-Cu bonding — real compute logic is now possible, customized on that die. But the controllers needed to drive all those HB I/O pins are expensive: a 40nm in-house implementation shows a single-bank controller occupies 4.6% / 10.7% / 19.7% / 40.2% of the logic die's area for 128 / 256 / 512 / 1024 HB I/O pins, corresponding to 6.4 / 12.8 / 25.6 / 51.2 GB/s per bank (at 0.4Gbps/pin).

The trade-off, exactly: Table 6 shows that at 51.2GB/s, a PE running at 1GHz can only fit 2 FPUs — a quarter of the 8 FPUs it could fit at 6.4GB/s. There is no free lunch: every extra byte/s of HB bandwidth is bought with FPU area.

3 · H2-LLM's architecture

The system pairs a GPU/TPU-like centralized processor with a memory system of mixed normal channels (plain DRAM) and HB-NMP channels (DRAM die stacked on a logic die). Each HB-NMP channel's DRAM banks run in one of two modes: normal mode (CP accesses via the external interface) or NMP mode (all banks accessed concurrently by their own PEs via HB) — never both at once, to avoid row-buffer interference. Each PE pairs with one bank, has its own weight/output buffers and FPUs, and shares one input global buffer per channel (avoiding duplicating inputs across banks). FPUs only do MAC — softmax, normalization, and element-wise ops stay on the CP, fused into the result-merging step.

4 · Data-centric dataflow — binding data before engines

Each transformer layer's operator graph is first split into Memory Access Groups (MAGs) — groups ordered by dependency (𝐴₀ ⪯ 𝐴₁ ⪯ …), each initially claiming all channels. Each MAG is then broken into Memory Partition Groups (MPGs) — its independent weakly-connected components — and each MPG is assigned its own disjoint subset of channels (a GCMap), preserving the parallelism that existed inside the MAG. Finally, within each MPG, operators are stratified into dependency-ordered tiers, and each tier's operators are bound to specific channels within their MPG's subset (an OCMap) — this is where fission ratios get decided.

5 · Tiling — the arithmetic behind splitting a GEMM across channels

Given an (M,K)×(K,N) GEMM and C channels, splitting K duplicates inputs; splitting N duplicates output partial sums. The paper's tiling factors 𝑇_K, 𝑇_N minimize total transfer overhead subject to 𝑇_K×𝑇_N = C:

min s·M·( K/(T_K·B_s) + N/(T_N·B_l) )   # s=element size, B_s/B_l = store/load bandwidth
s.t. T_K × T_N = C
# analytical solution:
T_K = sqrt( C × K × B_l / (N × B_s) )

Getting this wrong is expensive: on OPT's operators across 8 NMP channels, the worst tiling choice costs 1.5×–5.4× more transfer overhead than the optimal one (§7.3, Fig. 17) — with attention's SV operator hit hardest (5.4×) because its K and N dimensions are the most imbalanced.

6 · The DSE framework — genetic algorithm over architecture + dataflow

The exploration engine samples an initial population (architecture + dataflow per individual), discards any that overflow a channel's capacity, evaluates the rest with a latency/energy simulator, keeps the top-K, and evolves a new population via five genetic operators — from a full re-sample down to only re-sampling the finest-grained OCMaps and fission ratios (OP1–OP5), plus crossover between two survivors' MAGs. This repeats for a fixed number of rounds (100, with 5,000 individuals/round in the paper's main results).

Follow the numbers, step by step

Worked examples

Four calculations, each carried through with the paper's own numbers.

① Why in-die NMP's compute ratio isn't enough

Table 2 lists GDDR6-AiM's computation-bandwidth ratio as 1 FLOP/Byte. Edge processors run at a 500–1000 FLOP/Byte ratio [56]. At what arithmetic intensity does an edge CP stop being memory-bound?

  1. A device is memory-bound whenever the workload's arithmetic intensity is below its own compute-bandwidth ratio, and compute-bound above it.
  2. Edge CP's ratio is 500–1000 FLOP/Byte. So workloads need arithmetic intensity in that range before the CP's compute becomes the bottleneck instead of its bandwidth.
  3. In-die NMP's ratio is only 1 FLOP/Byte. Its compute becomes the bottleneck almost immediately — at roughly 1/500th to 1/1000th the intensity the CP needs.
  4. Consequence: across the entire range where the CP is still memory-bound (and could genuinely use NMP's help), NMP itself has already become compute-bound and stopped scaling.
🍯
Insight: this 500–1000× gap between the CP's and in-die NMP's compute ratios is exactly why §3.1 finds NMP's advantage "gradually shrinks" — it's not a coincidence, it's the roofline math.

② Tallying the HB controller's area tax

Using the paper's 40nm numbers: pin counts 128/256/512/1024 map to bandwidths 6.4/12.8/25.6/51.2 GB/s and controller areas 4.6%/10.7%/19.7%/40.2%. How much logic-die area is left for compute at each tier?

  1. 128 pins (6.4GB/s): 100% − 4.6% = 95.4% of the logic die free for FPUs — Table 6 confirms up to 8 FPUs fit at every tested frequency (0.4–1GHz).
  2. 512 pins (25.6GB/s): 100% − 19.7% = 80.3% free — still 8 FPUs fit at 0.4/0.6GHz, but only 4 at 0.8/1GHz (Table 6).
  3. 1024 pins (51.2GB/s): 100% − 40.2% = 59.8% free — now only 2 FPUs fit at 1GHz, an 4× reduction from the 128-pin tier's 8 FPUs.
  4. The trade curve is non-linear: going from 128→256 pins costs 6.1 points of area (4.6→10.7); going from 512→1024 costs more than double that (19.7→40.2, +20.5 points) for the same doubling of pins.
💡
This non-linearity is exactly why the paper's Takeaway 2 warns against over-provisioning bandwidth: past a point, each extra GB/s costs disproportionately more compute.

③ Reconciling the headline speedups

The abstract claims 2.72× geomean speedup; §7.2 reports 3.81× on decoding-heavy datasets (HE, SG) and 1.94× on prefill-heavy datasets (LB, LG), with 2.71× "across all test cases." Are these consistent?

  1. Decoding-heavy vs prefill-heavy split the four datasets in half (HE/SG vs LB/LG), each averaged across three models and three batch sizes.
  2. Geomean over the 2 categories: √(3.81 × 1.94) ≈ 2.72 — matching the "across all test cases" and abstract figures almost exactly (the paper reports 2.71 for the full set and 2.72 in the abstract, a rounding difference from the exact set of cases averaged).
  3. Why prefill-heavy gains less: when prompts dominate, more of the runtime is already compute-bound prefill on the CP, which H2-LLM's NMP-side improvements can't touch as much.
🍯
Insight: a geomean of two sub-geomeans is a useful sanity check, not a defined operation in the paper — it lands within the paper's own rounding, which is reassuring rather than exact.

④ Why the wrong tile factor costs 5.4×

Fig. 17 reports that on OPT's attention SV operator (8 NMP channels, context length 2048, batch size 4), the worst (T_K,T_N) pair costs 5.4× the optimal tiling's overhead. What's happening?

  1. SV's shape is (M,K)×(K,N) with K (context length-ish) and N (head-dim-ish) very different sizes — a lopsided GEMM.
  2. Splitting the "wrong" dimension (e.g., forcing T_N=8, T_K=1 when K ≫ N) means duplicating the huge K-side input across all 8 channels while barely reducing the small N-side output transfer — the worst of both costs.
  3. The analytical optimum T_K = √(C·K·B_l /(N·B_s)) picks a split that balances these two transfer costs instead of dumping all duplication onto one side.
  4. Result: the optimal split for SV keeps overhead near its 1× floor; the worst split (matching the lopsided shape backwards) inflates it 5.4×.
💡
This is why H2-LLM solves Eq. 1 analytically per operator rather than using one fixed tiling rule for every GEMM shape.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
A team wants to double an edge accelerator's decoding batch size to boost throughput. Why might in-die NMP's speedup actually get worse, not better?
Show answer
Doubling batch size raises FC operators' arithmetic intensity (more weight reuse per fetch), pushing them toward the compute-bound side of the roofline — exactly where in-die NMP's 1–2 FLOP/Byte ceiling caps out first. Past BS≈8, ID-NMP even falls below a CP-only baseline (71% of CP's performance at BS=16 in the paper).Misconception: that NMP is "free" extra throughput regardless of batch size. Its benefit is tied to arithmetic intensity, and higher batch size moves you away from NMP's sweet spot.
Problem 2 · medium
An engineer decides to always use 1024 HB I/O pins per bank "to maximize bandwidth." Using Table 6 and the area numbers in §3.2, explain what this costs at 1GHz.
Show answer
At 1024 pins, the controller eats 40.2% of the logic die, leaving room for only 2 FPUs per PE at 1GHz (Table 6) — a 4× drop from the 8 FPUs available at 128 pins. For workloads that are even moderately compute-bound (larger batch size), this starves the PEs and can make performance worse than a lower-bandwidth, higher-compute design.Misconception: that bandwidth is always the bottleneck worth maximizing. On hybrid bonding, bandwidth is bought with compute area — maximizing one can starve the other.
Problem 3 · medium
Compute-centric dataflow (like SpecPIM) assigns each operator to only NMP or only normal channels. Why does this hurt prefill performance even when NMP channels aren't the ones running prefill?
Show answer
Assigning some channels exclusively to NMP operators removes them from the pool of channels the CP can use for its own (mostly prefill) memory traffic — reducing the CP's effective external bandwidth. Since edge CPs have compute-bandwidth ratios of 500–1000, even a modest bandwidth cut can flip compute-bound prefill operators into memory-bound ones, directly hurting prefill latency.Misconception: that channel assignment only affects the operators explicitly mapped to those channels. It also affects every other operator competing for the shared external interface.
Problem 4 · hard
Operator fission splits a GEMM's output dimension N between CP and NMP without duplicating weights. Why couldn't you instead just duplicate the weights across both engines and run each independently?
Show answer
Weight duplication (as in prefill-decoding disaggregation for cloud serving) trades memory footprint for independence — fine when you have many model replicas and abundant memory for millions of cloud users. Edge accelerators have tightly limited on-chip and off-chip memory; duplicating every FC and attention weight matrix across CP and NMP would multiply memory footprint at exactly the platform least able to afford it. Fission avoids this by splitting one shared weight tensor's output columns, so each engine only holds the slice it computes.Misconception: that duplication and fission are interchangeable ways to use two engines. Duplication costs memory; fission costs only a bit of coordination/synchronization — and edge platforms can't pay the memory cost.
Problem 5 · medium
§7.4's resource-distribution experiment (Table 7) fixes the total compute+bandwidth budget and only varies NMP channel count (2/4/8). Why does going from 4 to 8 channels sometimes hurt performance at BS=16?
Show answer
Splitting a fixed compute/bandwidth budget across more channels shrinks each channel's individual capability (fewer FPUs, less bandwidth per channel) — the paper's Takeaway 6. At BS=16, operators are more compute-hungry, so wimpy per-channel compute hurts more than the extra parallelism helps. Additionally, making every channel an NMP channel removes any normal channels, which forecloses operator fission entirely.Misconception: that more parallel channels are always better. Under a fixed resource budget, more channels means weaker channels — there's an optimum, not a monotonic improvement.
Problem 6 · easy
§7.4 finds that increasing the weight buffer helps at BS=1/4 but not at BS=16. Why does batch size flip this result?
Show answer
At small batch size, weight reuse per load is low, so a bigger weight buffer helps overlap computation with the (relatively rare) weight fetches, cutting non-overlapped transfer time. At BS=16, weight reuse is already high (each weight tile serves many more output rows), so computation and weight loading already overlap well — a bigger buffer has little left to improve, while input/output buffer size (which scales with batch size) becomes the sensitive knob instead (Takeaway 4).Misconception: that a bigger buffer always helps for the same reason. Which buffer matters shifts with batch size, because it changes which tensor's reuse is the bottleneck.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What's the actual difference between in-die NMP and hybrid-bonding NMP?▾
In-die NMP embeds processing engines directly in the DRAM die, inheriting DRAM's slow, sparse logic resources (only ~25% area budget, 1–2 FLOP/Byte). Hybrid bonding instead bonds the DRAM die onto a separate logic die via Cu-Cu fusion, so that die can be built with real logic transistors — much more compute — at the cost of controller area for the HB I/O pins that carry the bandwidth.
Q2What does "data-centric" dataflow mean, concretely?▾
It means binding memory channels to operators first (via MAGs and MPGs), and only afterward deciding which compute engine (CP or NMP) runs each operator on those channels. This is the reverse of "compute-centric" schemes that pick the engine first and let that choice implicitly fix which channels are available.
Q3Why does prefill-awareness matter if NMP mainly targets decoding?▾
Because reserving channels exclusively for NMP operators removes them from the CP's usable bandwidth pool — even for operators the CP itself runs, like prefill. In prefill-heavy scenarios (long-context QA), prefill can dominate end-to-end latency, so starving the CP's bandwidth to feed NMP can be a net loss.
Q4What is operator fission, and why not just duplicate weights instead?▾
Fission splits one operator's output dimension between CP and NMP, so both compute part of the same result from one shared weight copy. Duplicating weights (as cloud prefill-decoding disaggregation does) avoids any coordination but multiplies memory footprint — something edge accelerators, with tight on-chip/off-chip memory, can't spare.
Q5What are MAG, MPG, GCMap, and OCMap?▾
A Memory Access Group (MAG) is a dependency-ordered chunk of a layer's operator graph. Each MAG splits into Memory Partition Groups (MPGs) — its independent sub-parts — each bound to a disjoint channel subset (a Group-Channel Map, GCMap). Within an MPG, operator tiers get their fine-grained Operator-Channel Map (OCMap), which is where fission ratios are set.
Q6Why do NMP PEs only run MAC operations, nothing else?▾
Softmax and normalization need to collect data across a whole row/vector first, giving them low parallelism and low bandwidth needs — a poor fit for many small, independent PEs. Element-wise operators can instead be fused into the result-merging step when the CP collects partial sums, so there's no benefit to running them on NMP either. Reserving NMP purely for GEMM/MAC work keeps more area for compute where it actually pays off.
Q7How does the DSE framework's genetic algorithm actually run?▾
It samples a population of architecture+dataflow designs, discards any that overflow a channel's capacity, simulates the rest for latency/energy, keeps the top-K, and generates the next generation via five operators ranging from full re-sampling to only re-sampling fine-grained bindings, plus crossover between two survivors. This repeats for a fixed number of rounds (100 in the main results).
Q8Why not just maximize NMP channel count for maximum parallelism?▾
Under a fixed resource budget, more channels means each channel gets a smaller slice of compute and bandwidth — eventually starving individual PEs. Making every channel an NMP channel also removes normal channels entirely, foreclosing operator fission. The paper's DSE finds a moderate channel count (often 4, in its case studies) balances these effects best.
Q9Does H2-LLM's approach only make sense for edge, low-batch inference?▾
The paper targets edge, low-batch inference specifically because that's where in-die NMP's low compute capacity and prior compute-centric dataflows fall shortest. The data-centric dataflow abstraction itself is stated to generalize to any NMP-based heterogeneous LLM accelerator, but the architecture co-design (HB compute-bandwidth trade-off, power-conscious PE choices) is tuned for edge constraints rather than cloud-scale, large-batch serving.
Q10What did the authors leave for future work?▾
The artifact appendix notes that NMP operator templates are currently manually designed from the execution flow described in §4.2 — automatically generating these templates is left as future work. The paper's evaluation also relies on a performance-model-based simulator rather than the full proprietary simulator, for artifact/data-privacy reasons.

Core terms
H2-LLMThe paper's hybrid-bonding-based heterogeneous accelerator, co-exploring architecture and data-centric dataflow for edge low-batch LLM inference.
Data-centric dataflowBinding operators to memory channels first (MAG/MPG), then to compute engines (OCMap) — as opposed to compute-centric mapping.
Compute-bandwidth trade-offHybrid bonding's core tension: more HB I/O pins (bandwidth) means more controller area, leaving less room for compute logic (FPUs) on the same logic die.
MAG / MPGMemory Access Group / Memory Partition Group — the two levels at which a layer's operator graph is split and bound to channel subsets.
GCMap / OCMapGroup-Channel Map / Operator-Channel Map — the formal binding of MPGs, then individual operators, to specific channels.
Operator fissionSplitting one operator's output dimension between CP and NMP engines without duplicating its weights.
DSE frameworkH2-LLM's genetic-algorithm-based search over the joint architecture + dataflow design space.
Roofline modelA performance model plotting achievable FLOPS against arithmetic intensity, with memory-bound and compute-bound regions separated by the device's compute-bandwidth ratio.
Supporting terms
In-die NMPProcessing engines embedded directly in the DRAM die — the paper's baseline, limited by DRAM's scarce logic resources.
ID-NMP / ID-NMP+The paper's two in-die NMP baselines: Samsung LPDDR5-PIM-like (ID-NMP) and SK Hynix AiM-like enhanced compute (ID-NMP+).
CPCentralized Processor — the conventional GPU/TPU-like engine handling prefill and non-NMP work.
Prefill / decodingThe two LLM inference stages: parallel prompt processing (prefill) vs. sequential one-token-at-a-time generation (decoding).
MHA / GQA / MQAAttention variants differing in how many key-value heads are shared — GQA/MQA raise attention's arithmetic intensity.
Tiling factors (T_K, T_N)How a GEMM's K and N dimensions are split across channels — chosen analytically to minimize data-transfer overhead.
FC-NMP / Attn-NMP / CC-NMPPrior dataflow baselines: offload all FC to NMP, offload all attention to NMP, and compute-centric mapping, respectively.
Weighted average (multi-workload DSE)When exploring for multiple workloads at once, individuals are judged by their weighted average performance across all of them.
