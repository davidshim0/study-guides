SOSP 1989 · A Field Guide

Consistency you can time out of, not hang on

A client caches a file. How does the server know when it's safe to change it? Broadcast-based schemes assume the network never fails; per-access checks are always safe but always slow. Leases pick a third way: a clock-bounded promise.

⚡ TL;DR

  • A lease is a time-bounded contract: the server promises a client "no one writes this without your OK, for the next t seconds" — turning a hard consistency problem into a clock-bounded one.
  • Headline result: a 10-second lease term gets total server load within about 5% of an infinite-term (never-check) system, on real V-system file-access traces.
  • Why it matters: leases give bounded, tunable fault tolerance for cache consistency without reliable broadcast or per-access server checks — the ancestor of today's TTL/lease-based coordination (DNS, distributed locks, cache invalidation).
1Why file caching needs a consistency protocol▾

A diskless client caches a copy of a server's file for speed. If another client writes the file, the cached copy is stale. "Consistent" means the system behaves as if there were only one copy — the cache is a performance trick, not a semantics change.

Now you're ready: leases are a mechanism for enforcing exactly this guarantee across machines that can crash or lose messages.
2The two bad extremes: broadcast and per-access checks▾

Shared-memory multiprocessor cache protocols assume a reliable, synchronous bus broadcast — fine on one machine, unsafe across a network that can partition. The alternative, checking with the server on every access, is always correct but throws away most of the point of caching.

Now you're ready: leases sit between these — cheap like a broadcast-based protocol, but tolerant of lost messages and dead hosts like a per-access check.
3Write-through caching▾

A write-through cache sends every write straight to the server immediately, rather than buffering it locally. It's simpler to reason about (no write can ever be lost) at some cost in write latency — the paper adopts it purely to simplify the exposition.

Now you're ready: because writes always reach the server immediately, the only question leases have to answer is "when is it safe for the server to let this write proceed?"
4Non-Byzantine failures▾

A Byzantine failure is one where a component behaves arbitrarily or maliciously — including lying. A non-Byzantine failure is more forgiving: hosts crash cleanly, messages get lost or delayed, but components don't send false information.

Now you're ready: leases guarantee correctness under non-Byzantine failures (crashes, lost messages, partitions) — but assume clocks aren't lying, which matters later.
5Physical clocks and bounded drift▾

A physical clock measures wall-clock time. It needn't be perfectly synchronized across machines — just have a known, bounded amount of disagreement (drift) with other clocks in the system.

Now you're ready: leases only need clocks synchronized within a small allowance ε, not perfectly — that assumption is what lets a lease's expiration mean the same thing to both server and client.
6False sharing (the lease version)▾

In cache-coherence terms, false sharing is overhead paid for a "conflict" that isn't real — e.g. invalidating a client's cache line because someone touched a different piece of data that happens to share a block.

Now you're ready: here, false sharing means invalidating/callback-ing a leaseholder who isn't actually using the file anymore. Short leases minimize how long this waste can persist.
7Multicast vs. unicast messaging▾

Unicast sends one message to one recipient. Multicast sends one message that many recipients receive — used here so a server can ask all leaseholders for write approval with one send instead of one message per holder.

Now you're ready: multicast is what roughly halves the number of write-approval messages (from 2×(sharers) to just (sharers)) — both still grow linearly with the number of sharers.
8Poisson arrivals — a modeling convenience▾

Modeling reads and writes as independent, memoryless random arrivals (a Poisson process) makes the math of "expected reads within a lease term" tractable, at the cost of missing burstiness (a program that reads a file, then reads it again immediately, then not for a long time).

Now you're ready: the paper's analytic model assumes Poisson access, then validates it against a real trace — and finds real access is burstier, which only makes short leases look better.
The whole story in one place

Leases in a nutshell

The problem, the fix, and why a short clock-bounded promise beats both extremes.

Distributed file caches need consistency, but existing options were unsatisfying: broadcast-based multiprocessor protocols assume reliable synchronous communication that a real network can't guarantee, while per-access consistency checks are always safe but defeat the purpose of caching. Both approaches also handle host and communication failures badly — broadcast protocols aren't designed for them at all, and per-access checking just makes every access pay the failure-handling cost.

A lease is the server's time-bounded promise to a client: "you may read this datum from your cache, and I will not let anyone write it, for the next ts seconds without your approval." Reads inside the term are free (no server contact). A write must wait until every current leaseholder has approved or its lease has simply expired — so even a totally unreachable client only delays the write by, at most, one lease term.

The paper builds a simple analytic model (it explicitly ignores queueing delays) of server load and response delay as a function of the lease term ts, validates it against a real trace from the V distributed system, and finds that a term of about 10 seconds captures nearly all the benefit of caching (within ~5% of an infinite-term system, on total server load) while keeping failure-recovery delay bounded to that same ~10 seconds.

🍯 Key takeaways

  • A lease trades a hard consistency guarantee tied to events (writes) for one tied to time — bounding, not eliminating, the cost of failures.
  • Short terms minimize failure delay, false sharing, and storage; long terms minimize extension traffic. ~10s is close to optimal for V-like access patterns.
  • Multicast write-approval roughly halves write-approval messages (2(S−1) → S) — it cuts the constant, not the underlying O(S) scaling with the number of sharers.
  • Installed files (heavily read, rarely written) get a special multicast-periodic-extension optimization, eliminating per-client bookkeeping entirely.
  • Leases only need clocks synchronized within a small, bounded drift — not perfect synchronization.
Six everyday pictures

How to think about leases

Each stands alone; each ends with where it stops being true.

The core idea · Time-bounded trust

A parking ticket, not a phone call

A parking ticket lets you park until a printed time, no calls needed. A lease works the same way: it lets a client trust its cached copy until a printed expiry, with zero server contact in between. Compare a system that phones the attendant before every single errand — always correct, always slow.

Where it breaks: a parking ticket can't be "recalled" mid-term. A lease can — the server can ask for early approval of a write — the ticket only fails to model that active-callback path.
Enforcing writes · Multicast approval

Asking all the roommates at once

To repaint a shared wall you don't call each roommate one at a time — you post one message to the house group chat and wait for replies. A write multicasts one approval request to every leaseholder instead of messaging each individually, needing only S messages (1 request + S−1 replies) instead of 2(S−1).

Where it breaks: a group chat doesn't expire your voice — a lease does. If a roommate is unreachable, the wall gets painted anyway once their lease term runs out.
Optimization · Installed files

A library's standing renewal notice

A library that mails every borrower a renewal notice every month, for books almost nobody ever returns, is cheaper than each borrower calling to renew individually. The server periodically multicasts a renewal to everyone holding leases on installed files (libraries, headers), and simply drops a lease from that multicast the moment the file needs updating.

Where it breaks: a real library doesn't need to track who has which book to send the notice; the server still benefits from not needing per-client records, which is precisely what this optimization removes.
Fault assumption · Bounded drift

Two watches, close enough

Two friends' watches don't need to show the exact same second to agree "meet at noon" — just close enough that neither shows up an hour off. Leases only need clocks synchronized within a small allowance ε, folded directly into the effective lease term at the client.

Where it breaks: if one watch runs fast at the server or slow at the client, you get real inconsistency, not just wasted trips — the two failure directions aren't symmetric (see FAQ).
The cost of length · False sharing

Reserving a meeting room you left

Booking a conference room for three hours but leaving after ten minutes means anyone who wants it must wait, or interrupt you, needlessly. A long lease held by a client no longer using the file causes exactly this: a write must trigger a callback (or wait out the term) despite no real conflict.

Where it breaks: you could just cancel the booking when you leave — real clients often don't announce they're done, which is why the fix is a shorter default term, not better manners.
Andrew's lesson · The two extremes

All-or-nothing thermostat

A thermostat that either calls the furnace company for every single degree, or is set to "always on" and never rechecked, wastes effort at one end or risks a cold house at the other. The Andrew file system prototype used a zero term (checked constantly, overloaded the server); the production version jumped to an effectively infinite term (fast, but stale on failure). Leases argue for the dial in between.

Where it breaks: a thermostat dial is continuous and free to adjust; picking and re-tuning a lease term per file/client is a real design decision the paper has to justify with data.
The full explanation

How it actually works

Section by section, with the paper's model rebuilt as visuals you can read at a glance.

1 · The gap leases fill

Shared-memory multiprocessor coherence protocols get to assume a reliable, synchronous broadcast bus — a luxury a distributed system doesn't have. The fallback, checking consistency with the server on every single access, is unconditionally safe but erases most of the benefit of caching in the first place. Leases target exactly the middle: nearly free access most of the time, with failure cost capped by a clock, not by hope that the network behaves.

2 · Defining the lease and its effective term

When a client fetches a datum, the server also grants a lease: a promise not to let anyone write that datum for ts seconds without this client's approval. But the client doesn't actually get the full ts, because the grant message itself takes time to arrive, and clocks aren't perfectly synchronized:

t_c = max(0, t_s − (m_prop + 2·m_proc) − ε)
# t_c = effective term at the cache · t_s = term stated by the server
# m_prop = propagation delay · m_proc = per-hop processing time · ε = clock-sync allowance

3 · Choosing the term — the analytic model

More reads packed into one lease amortize its extension cost; the server handles extension messages at rate 2NR/(1+R·t_c) (N clients, read rate R). Writes add a term proportional to sharing:

load(t_s) = 2NR / (1 + R·t_c)  +  N·S·W
# N = clients · R,W = per-client read/write rates · S = clients sharing the file

# a longer term reduces load whenever the "lease benefit factor" exceeds 1:
α = 2R / (S·W)          # bigger α, bigger R → short terms already do well

Installed files shortcut: for widely-read, rarely-written files (headers, binaries — almost half of V's read traffic), the server periodically multicasts one renewal to everyone instead of waiting for per-client extension requests, and simply drops that file's lease (the whole covered group) from the next multicast when it's about to change — no per-client leaseholder tracking needed at all.

5 · Fault tolerance and the clock assumption

Leases preserve correctness across message loss, partitions, and client/server crashes (writes are just delayed, never lost — provided the server persists writes durably across crashes, on top of write-through caching) — provided clocks are non-Byzantine. The two clock-error directions aren't symmetric:

⚠
Asymmetric clock failure. A server clock running fast, or a client clock running slow, can cause real inconsistency (a write let through before the client's lease has actually expired at the client). A slow server clock or fast client clock only wastes extra messages — annoying, not incorrect. The paper treats such failures as rare and detectable via synchronization protocols or timestamps.
Follow the numbers

Worked examples

Four passes through the paper's actual figures.

① From consistency load to total server traffic

At t_s=0, consistency traffic is 30% of all server traffic (S=1, V trace). A 10s term cuts consistency traffic to 10% of its zero-term value. What's the effect on total traffic, and how close does that get to an infinite lease term?

  1. Set up the split: total traffic = 70% (non-consistency) + 30%·(relative consistency load).
  2. At t_s=0: total = 70 + 30·1.00 = 100% (the baseline).
  3. At t_s=10s: total = 70 + 30·0.10 = 73% → a 27% reduction in total server traffic.
  4. At t_s→∞: relative consistency load → 0, so total → 70% — the best any lease term could do.
  5. Gap at 10s: 73% is (73−70)/70 ≈ 4.3% above the infinite-term floor — matching the paper's "just 4.5% above" claim.
🍯
Insight: because consistency was never more than 30% of total load to begin with, even a term that eliminates 90% of consistency traffic can only move total traffic by 27% — the ceiling on lease benefit is set by how big a slice consistency was in the first place.

② Multicast approval savings

A file is shared by S=10 leaseholders when a write arrives. Compare message counts with and without multicast.

  1. Without multicast: the server must message each of the other S−1=9 holders individually and get a reply: 2×9 = 18 messages.
  2. With multicast: one multicast request reaches all S−1 holders, each sending one reply, plus the requester's implicit approval: S = 10 messages.
  3. Savings: 18 − 10 = 8 fewer messages, a 44% reduction in approval traffic for this write.
  4. Scaling check: the saving grows with S — multicast turns O(S) work into O(S) messages instead of O(2S), exactly the difference the paper flags in footnote 6.
💡
This is why the load formula's write term is N·S·W and not 2N·S·W — multicast is baked into the model, not an afterthought.

③ Longer network delay — reading Figure 3

On a network with a 100ms round-trip time, the paper reports a 10s term degrades response time by 10.1% versus an infinite term, and a 30s term degrades it by only 3.6%. What does that comparison tell you?

  1. Both numbers are "extra delay vs. the best possible" — the infinite-term system is the zero-consistency-overhead reference point.
  2. Tripling the term (10s→30s) cuts the penalty roughly in third (10.1%→3.6%), consistent with the same fast-then-flat exponential shape seen in the load curve.
  3. Conclusion the paper draws: with higher propagation delay, terms should shift somewhat longer (into the 10–30s range) — but the qualitative shape, "most of the benefit early," still holds.
🍯
Insight: the "flatten fast" curve shape is robust to network delay; only where the knee sits shifts, which is exactly the paper's argument for why leases scale to future, higher-latency systems.

④ Server storage overhead

The paper states a client holding about 100 leases costs the server roughly 1 kilobyte. Extrapolate the storage cost for a server with many clients.

  1. Per-client cost: ~1 KB (100 leases × a couple of pointers each, per the paper's own estimate).
  2. For a server with, say, 1,000 clients (illustrative — not a number stated in the paper): 1,000 × 1 KB ≈ 1 MB total.
  3. Compare to memory of the era: the paper explicitly calls this overhead "modest," and notes it can be shrunk further by coarsening lease granularity if it ever became a problem.
💡
Note the client count here is my extrapolation of the paper's stated per-client rate, not a total the paper itself computes — flagged in Source Notes.
Test yourself

Practice problems

Try before opening the answer — each names the misconception it checks.

Problem 1 · easy
Why does the paper insist a zero-term lease is better than a very short (but nonzero) one, when both seem "basically the same"?
Show answer
A nonzero t_s with an effective t_c of zero means reads gain nothing (every read still has to check, since t_c=0), but writes are still penalized by having to wait for that (useless) lease to expire or be approved. Zero term skips the wait entirely. Nonzero-but-tiny gives you the worst of both.Misconception: "some lease is always better than none." A lease only pays off once t_c is actually usable — otherwise it's pure write-delay with no read benefit.
Problem 2 · medium
Suppose a hypothetical trace has relative consistency load 50% at some lease term, with consistency again 30% of zero-term traffic. What's the total traffic reduction, and how far is that from the infinite-term floor?
Show answer
Total = 70 + 30×0.50 = 85%, a 15% reduction from the 100% baseline. Infinite-term floor is still 70%. Gap = (85−70)/70 ≈ 21% above optimal — much worse than the 10s/10%-load case's ~4.3% gap, showing how nonlinear the payoff is.Misconception: assuming reduction scales linearly with lease term. Cutting consistency load in half only cuts total traffic by 15%, because consistency was never the whole load.
Problem 3 · medium
A write lands on a file shared by S=5 leaseholders. How many messages does multicast approval need, versus a pairwise scheme, and what's the percentage saving?
Show answer
Multicast: S = 5 messages. Pairwise: 2(S−1) = 8 messages. Saving = 3 messages, or 37.5%. The saving fraction grows toward 50% as S increases (since 2(S−1) grows twice as fast as S).Misconception: that multicast savings are roughly constant. They actually grow with the degree of sharing S.
Problem 4 · hard
Using α = 2R/(S·W), explain why the paper suggests a heavily write-shared file should get a lease term of zero.
Show answer
Heavy write-sharing means large S and/or large W relative to R, driving α below 1. The condition for a longer term to help (reduce load) requires α>1; when α≤1, no positive lease term reduces load — the extension savings on reads are swamped by write-approval cost across many sharers, so the server is better off skipping leasing overhead for that file entirely (t_s=0).Misconception: that longer leases always help "more caching is always better." The benefit condition (α>1) explicitly depends on the read/write ratio and sharing degree, and can fail.
Problem 5 · medium
Why does periodically multicasting lease renewals for installed files avoid the "implosion of responses" problem that per-client extension requests would create?
Show answer
If every client individually requested extension near the same expiry time, the server would face a burst ("implosion") of near-simultaneous requests. A single periodic multicast renewal sidesteps this: the server pushes the extension to everyone at a time of its choosing, and simply omits a client from the next round when it needs to write — no burst, no per-client tracking.Misconception: that this optimization is just "fewer messages." Its real value is avoiding a synchronized burst of near-simultaneous client requests.
Problem 6 · hard
Explain the asymmetry: why is a slow client clock (or fast server clock) an actual correctness bug, while a fast client clock (or slow server clock) only wastes messages?
Show answer
Correctness requires the client to stop trusting its cache no later than the server considers the lease expired. If the client's clock runs slow (or the server's runs fast), the client believes the lease is still valid after the server has already let a write through — genuine inconsistency. If the client's clock runs fast (or the server's slow), the client discards its cache and re-checks earlier than strictly necessary — wasted round trips, but never wrong data.Misconception: that any clock disagreement is equally dangerous. Only the direction that lets a client over-trust a stale cache threatens correctness.
Problem 7 · medium
The Andrew file system prototype used a zero-term lease and suffered excessive server load as it scaled; the production version moved to an effectively infinite term. What did the production version give up to get that speed?
Show answer
Guaranteed consistency after a communication failure — the server just notifies clients of changes and lets writes proceed even if a client is unreachable, so that client can silently operate on stale data until its next server contact (bounded only by a 10-minute poll). It traded a hard guarantee for good average performance, exactly the extreme leases are designed to avoid needing.Misconception: that "it worked in production" means it's correct. It's fast because it accepts a known consistency hole under failure — leases argue for the same speed without the hole.
Problem 8 · easy
A client holds a lease on a file it read once, three lease-terms ago, and never touches again. A different client now wants to write it. What happens, and what is this called?
Show answer
If the lease has expired (likely, after three terms), the write proceeds immediately with no callback needed — the server simply doesn't need approval from an expired leaseholder. If somehow still valid, the writer must wait for approval or expiry, even though the first client isn't really using the file — that unnecessary wait is false sharing.Misconception: that any lease held by a non-active reader is automatically "false sharing." It's only false sharing while the lease is still technically valid but practically unused — which is exactly why short terms minimize it.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does a lease grant?▾
Control over writes to a datum for a fixed term: the server won't let anyone write it during that term without the leaseholder's approval. It's a write veto, not a guarantee the client will always have the freshest copy forever — just for the stated term.
Q2Why not just use reliable broadcast like multiprocessor cache coherence?▾
Reliable synchronous broadcast is a property of a shared bus, not a wide-area or even local network — messages can be lost, delayed, or a host can crash mid-protocol. Leases are designed specifically to survive those failures, at the cost of only bounding (not eliminating) their performance impact.
Q3Why 10 seconds specifically?▾
It's not a universal constant — it's what the paper's analytic model plus V-system trace data show captures nearly all of caching's benefit (within ~5% of an infinite term) for that system's read/write ratio and message costs, while keeping failure-recovery delay short. Other access patterns would shift the number.
Q4What happens if the client holding a lease is unreachable when a write arrives?▾
The server waits for either that leaseholder's approval or the lease's natural expiration, whichever comes first — so the write is delayed by at most one lease term, never indefinitely.
Q5Does write-through mean writes are slow?▾
Every write reaches the server, yes, but the paper notes this cost is largely avoidable by special-casing temporary files (handled outside the lease mechanism, e.g. via local disk), since they generate most write traffic in practice.
Q6How is a lease different from a lock?▾
A lock has no built-in expiration — if the lock holder crashes, someone else must detect that and break the lock. A lease is a lock with an expiration baked in from the start, so a crashed holder's "lock" is guaranteed to release itself.
Q7Why does write-sharing matter so much to lease performance?▾
Every leaseholder on a shared file must be contacted (or timed out) before a write proceeds. More sharers (S) means more approval messages per write and more chance one is unreachable — which is exactly what the α = 2R/(SW) benefit factor captures: high sharing pushes toward shorter (or zero) terms.
Q8Do leases guarantee consistency no matter what fails?▾
Only against non-Byzantine failures (crashes, lost/delayed messages) with clocks that have known bounded drift. A clock that lies about time in the dangerous direction (server too fast, client too slow) can violate consistency — the paper argues this is rare and detectable.
Q9Are installed files handled differently?▾
Yes — since they're heavily read and almost never written (nearly half of all reads in the V trace, zero writes), the server uses one periodic multicast renewal for all their leaseholders instead of individual extension requests, removing per-client bookkeeping for them entirely.
Q10How does this compare to Andrew (AFS) and NFS?▾
Andrew's production version uses an effectively infinite term with server-pushed invalidation, risking staleness if a client is unreachable during a write. NFS doesn't guarantee consistency at all. Leases argue both could adopt a non-zero, non-infinite term and get most of the speed with a hard fault-tolerance bound.
Beyond the paper

Connections to modern OS & memory-systems design

Where this 1989 idea shows up in today's distributed and memory-tiering systems.

🔒 Ancestor of modern distributed locks

Google's Chubby and its open descendants (ZooKeeper, etcd) use lease-based locks for a similar reason to this paper's argument: a lock holder that crashes shouldn't be able to block the system forever. Their lease terms (seconds, tunable) are a modern echo of this paper's trade-off in spirit — this paper doesn't discuss them, so treat the comparison as commentary, not a claim it makes.

🌐 TTLs as leases everywhere

DNS's time-to-live is a lease without the write-veto: a client trusts cached data for a bounded time, accepting some staleness risk instead of full consistency. The paper explicitly distinguishes this ("hints," no guarantee) from true leases — a distinction worth re-drawing whenever you see a TTL in a cache-coherence-adjacent design.

🧊 Hysteresis in page-migration policy

Mirage's "minimum hold time before relinquishing a page" (cited by this paper) is structurally the same knob as the cool-down/hysteresis windows in modern hot/cold page-tiering systems (TPP, Memtis, HeMem): both trade a short delay in reacting to a real access-pattern change for avoiding wasted thrashing when the access pattern briefly stutters.

🧩 CXL-shared memory needs a lease-like bound

Speculative extension (not in the paper): multi-host CXL.mem pools raise an analogous problem — a remote host's cache line state must be reconciled without assuming a reliable coherence fabric, and a host can hang or disconnect. A time-bounded write veto, rather than a directory that waits forever for an ack, is a plausible fit for bounding fault-recovery latency in disaggregated memory, though this is an analogy drawn well outside the paper's own scope.

🍯
Takeaway for tiering research: leases are a reminder that a clock-bounded, tunable promise can replace both "assume the fabric never fails" and "check every access" — worth asking whether your tiering or coherence protocol's failure-handling is closer to broadcast-trust, per-access-check, or an explicit lease.
Walk in ready

Discussion questions

Each ties to a specific claim or number in the paper.

  1. The V trace used to validate the model has S=1 for all writes ("no writes to shared files") — how much should we trust the 10-second recommendation given the model was never validated against a trace with real write-sharing? (the paper only analytically extrapolates S=10/20/40, never traces them)
  2. The paper assumes clocks are synchronized within a small, bounded ε — is that assumption still comfortable at CXL/RDMA-fabric timescales where "bounded drift" competes with microsecond-scale operations? (the whole correctness argument leans on ε being small relative to lease terms of seconds)
  3. Andrew's production system chose an effectively infinite lease term and accepted a consistency hole on client failure — is that actually the wrong choice, or does the paper's own "10 minute poll" bound make it an acceptable, cheaper alternative to leases? (the paper argues leases are strictly better, but doesn't quantify Andrew's real-world staleness cost)
  4. The load formula ignores queueing delay entirely — at what request rate would that omission start to matter, and would it change the optimal 10-second answer? (the paper admits this limitation but doesn't bound when it breaks down)
  5. Modern lease-based locks (Chubby, ZooKeeper) use similar multi-second terms decades later on much faster networks — does that validate the paper's model, or suggest the "right" term is set more by human/operational tolerance for failover delay than by the R/W/S math? (compare the paper's α-driven derivation to how practitioners actually pick lease TTLs today)
