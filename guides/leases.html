Consistency you can time out of, not hang on

A client caches a file. How does the server know when it's safe to change it? Broadcast-based schemes assume the network never fails; per-access checks are always safe but always slow. Leases pick a third way: a clock-bounded promise.

What the paper assumes you already know

⚡ TL;DR

  • A lease is a time-bounded contract: when a client fetches a datum, the server promises that nobody will write it during the term unless the server first gets this client's approval. Inside the term the client reads its cached copy with no messages.
  • A write waits until every leaseholder has approved (approving means invalidating its copy) or that holder's lease has expired. A crashed or unreachable holder therefore delays a write by at most one term, and the system stays consistent through crashes, lost messages and partitions. The price is a clock assumption: clocks must have bounded drift.
  • Headline result (analytic model with V-system parameters): a 10-second term cuts consistency traffic to about 10% of a zero term and puts total server load within about 5% of an infinite term. Short terms also shorten failure delays, cut false sharing and shrink server state.
  • Where it sits: between protocols that assume reliable broadcast (cheap, not fault tolerant) and protocols that check with the server on every read (fault tolerant, slow). DNS time-to-live (which the paper cites as earlier work) is a time bound without the write promise, so its cached data are only hints.
Quick glossary
LeaseA time-limited promise from a server to one client: until the term ends, the server will not let the covered datum be written without first getting that client's approval.
LeaseholderA client that currently holds an unexpired lease on a datum.
DatumThe unit of data one lease covers: a file's contents, or file-system information such as a name-to-file binding or a file's permissions.
Lease term tsThe length of time a lease lasts, as granted by the server and measured on the server's clock.
Effective term tcThe part of the term the client can actually use: the term minus the time for the grant to reach the client and an allowance ε for clock uncertainty, tc = max(0, ts − (mprop + 2mproc) − ε).
ExtensionA new grant that renews a lease the client holds or recently held. Normally a reply to a client request; for installed files, multicast by the server unasked.
Approval requestThe message the server sends to leaseholders when a client wants to write a leased datum, asking each to agree to the write.
ApprovalA leaseholder's reply agreeing to a pending write. A holder that approves invalidates its cached copy. The writer's own request counts as its approval.
Write-through cacheA cache that sends every write to the server at once instead of holding modified data locally. The paper assumes one.
ConsistencyThe paper's definition: a cached system is consistent if it behaves like a single uncached copy of the data, apart from speed.
S, R, W, NParameters of the analytic model: N is the number of clients, R and W are each client's read and write rates (per second), and S is the number of caches holding the file when a write happens.
mprop, mprocModel parameters: the time a message spends crossing the network, and the time a host spends sending or receiving one message.
Lease benefit factor αA number from the model that measures how much reading outweighs write-sharing: α = 2R/(SW). A non-zero term lowers server load only if α > 1 and tc > 1/(R(α−1)).
False sharingA lease conflict that is not a real access conflict: a write has to call back, or wait for, a client that holds a lease but is no longer using the file.
Installed filesFiles that come with the standard system, such as commands, header files and libraries. They are widely shared, read heavily and written rarely.
MulticastSending one message that the network delivers to a whole group of hosts.
Clock driftThe rate at which a clock gains or loses time relative to true time, for example a few parts per million.
Clock synchronization error εThe largest difference between two hosts' clock readings at the same instant.
PartitionA network failure that splits hosts into groups that cannot reach each other while all of them keep running.
Non-Byzantine failureA failure in which a component stops or loses messages but never behaves arbitrarily: host crashes, lost messages, partitions. The paper excludes Byzantine failures, which include a clock running at the wrong rate.
Soft stateInformation a server keeps to run faster but can lose in a crash without breaking correctness, because it can be rebuilt or waited out.
1Why file caching needs a consistency protocol▾

A diskless client caches a copy of a server's file for speed. If another client writes the file, the cached copy is stale. The paper's definition: consistent means "the behavior is equivalent to there being only a single (uncached) copy of the data except for the performance benefit of the cache." With large caches, the traffic needed to keep this true "can be the dominant factor in cache performance."

Now you're ready: leases enforce exactly this single-copy guarantee across machines that can crash or lose messages.
2The two prior families: reliable broadcast and check on every read▾

Shared-memory multiprocessor protocols rely on "reliable, synchronous broadcast communication as provided by the system bus." A distributed system has partial failures (a host crashes, a message is lost), so protocols that assume reliable broadcast "do not tolerate communication failures." The other family checks consistency with the server on every read, which tolerates failures but "fail[s] to deliver good performance."

Now you're ready: leases are cheap like the first family in the common case and tolerate failures like the second, by bounding every promise in time.
3Write-through caching▾

A write-through cache sends every write to the server instead of holding it locally. The paper assumes it for two reasons: it "simplifies the explanation", and it "gives clean failure semantics: no write that has been made visible to any client can be lost." It notes that extending leases to non-write-through caches is "straightforward" and that most of the write-through cost disappears if temporary files (which get most writes) are handled specially.

Now you're ready: because every write passes through the server, the only question a lease answers is when the server may let a write proceed.
4Non-Byzantine failures▾

A Byzantine failure is arbitrary misbehavior, including sending wrong information. A non-Byzantine failure is a crash, a lost or delayed message, or a partition. The paper's claim: leases keep consistency unless hosts or the network suffer "certain Byzantine failures including clock failure."

Now you're ready: a clock that runs at the wrong rate counts as a Byzantine failure here, and it is the one failure that can break consistency.
5Physical clocks: drift versus synchronization▾

Drift is how fast a clock's rate differs from real time. Synchronization is how far apart two clocks' readings are. The paper's minimum requirement is only a known bounded drift: then the server can send the term as a duration and each side times it locally. It also regards synchronization within a small allowance ε as reasonable, and its formula for the effective term subtracts ε.

Now you're ready: correctness needs the client to stop trusting its copy no later (in real time) than the server lets a write through. A fast server clock or a slow client clock breaks that.
6False sharing (the lease version)▾

In multiprocessor caches, false sharing is coherence traffic for a conflict that is not real (two variables on one cache line). In this paper it is "a lease conflict when no actual conflict in file access exists": a client writes a file covered by another client's lease while that other client is not using the file. The write still has to wait for a callback or for expiry.

Now you're ready: shorter terms shrink the window in which an idle client's lease can get in a writer's way.
7Multicast versus unicast▾

Unicast sends one message to one host. Multicast sends one message that a group of hosts receives (the V system had host-group multicast). To get approval from S−1 other holders, multicast needs 1 request plus S−1 replies = S messages; unicast needs a request and a reply per holder = 2(S−1).

Now you're ready: multicast roughly halves approval messages for large S, but both still grow linearly with S.
8Poisson arrivals: a modeling convenience▾

The model treats each client's reads and writes as Poisson processes (independent, memoryless arrivals at rates R and W). That makes "expected reads during one term" simply R·tc, at the cost of ignoring burstiness.

Now you're ready: the paper checks the model against a trace and finds real access is burstier, which makes short terms look even better than the model says.
The whole story in one place

Leases in a nutshell

The problem, the fix, and why a short clock-bounded promise beats both extremes.

Distributed file caches need consistency, and the existing options were unsatisfying. Protocols borrowed from multiprocessors assume reliable synchronous broadcast, which a network cannot provide, so a lost invalidation or a crashed host leaves a stale copy in use. Checking with the server on every read survives failures, but every read then pays a round trip, which removes much of the point of caching.

A lease is the server's time-bounded promise to a client: "for the next ts seconds, nobody writes this datum unless I first get your approval." Reads inside the term need no server contact. A write must wait until every current holder has approved (and so invalidated its copy) or its lease has expired. Because every promise expires, even a completely unreachable client delays a write by at most one term, and nothing about failures is left unbounded. The cost is a new dependence: clocks must measure time with bounded error.

The paper builds a simple analytic model of server load and added delay as a function of the term (it ignores queueing), plugs in parameters measured on the V distributed system, and checks the model against a trace-driven simulation. A term of about 10 seconds gives a server load within about 5% of an infinite term, while keeping the failure delay to about 10 seconds. It argues that leases matter more in future systems: wider networks, faster processors and more hosts.

Questions worked through

How is a lease different from a lock?

A lease is a time-limited right that expires without any message, so a crashed holder cannot block others beyond the term. It gives no exclusivity among readers: many clients hold leases on the same datum at once, and the promise is only that nobody writes without their approval. (General framing; the paper compares leases with Xerox DFS's breakable locks, which degenerate to a zero term because clients ignore the timeout.)

So is a lease just a timeout-bound cache: every reader gets a time limit before it must go back to the server?

Half of it. A timeout-bound cache (a cache with a time-to-live, like DNS or NFS's 3-second attribute cache) gives readers a time limit, but writes go ahead whenever they arrive, so a reader can see stale data until its timeout runs out. The paper calls such cached data "hints" and says NFS does not guarantee consistency for exactly this reason.

A lease adds the other half, on the write side: during the term, the server will not let the datum be written unless the holder has approved. So the time limit is a promise both sides keep. The reader stops using its copy when the term ends, and the server holds every write until each holder has approved or its term has ended. That is what makes the cache consistent instead of merely fresh-ish.

In normal operation the time limit is not what makes writes visible: the server asks holders to approve, they drop their copies, and the write proceeds within a round trip. The timeout matters when a holder cannot answer (crash, partition, lost message). Then it bounds how long the server must wait. In short: a lease is a timeout-bound cache plus a server that respects the same timeout before writing, plus callbacks so the timeout is rarely the thing anyone waits for.

🍯 Key takeaways

  • A lease converts "wait until the holder answers" (unbounded if it crashed) into "wait until the holder answers or the term runs out" (bounded). Failures cost performance, not correctness.
  • Short terms: less write delay after client crashes, less recovery delay after server crashes, less false sharing, less server state. Long terms: fewer extension messages. About 10 s is close to optimal for the V parameters.
  • The model's lease benefit factor α = 2R/(SW) says when any non-zero term helps: α > 1 and tc > 1/(R(α−1)). Heavily write-shared files should get a term of zero.
  • Multicast approval needs S messages instead of 2(S−1); the writer's request carries its own approval, so an unshared write is a single request and reply.
  • Installed files (heavily read, rarely written) get a few directory-level leases that the server extends by periodic multicast; to update one, it stops extending and waits for expiry, with no per-client records and no flood of replies.
  • The minimum clock requirement is a known bounded drift (the term travels as a duration). A fast server clock or a slow client clock can break consistency; the opposite errors only add traffic.
Six everyday pictures

How to think about leases

Each stands alone; each ends with where it stops being true.

The core idea · Time-bounded trust

A parking permit, not a phone call

A permit lets you park until a printed time with no calls in between. A lease lets a client trust its cached copy until expiry with no server contact. Checking on every read is phoning the attendant before every errand: always correct, always slow.

Where it breaks: a permit cannot be recalled early. A lease can: the server may ask the holder to approve a write now, and the holder gives up its copy. The permit only models the "wait for expiry" path.
Enforcing writes · Multicast approval

Asking all the roommates at once

To repaint a shared wall you post once to the house chat and collect replies. The server multicasts one approval request to the other S−1 holders and collects S−1 replies: S messages, versus 2(S−1) if it asked each one separately. The roommate who asked has already agreed.

Where it breaks: a roommate who never answers can stall the house forever. A holder who never answers only stalls the write until its lease expires.
Optimization · Installed files

A radio station's "still on air" signal

A station broadcasts a periodic signal; every radio that hears it keeps playing, and the station never needs a listener list. The server multicasts an extension for installed-file leases (say, one per major directory) to all clients periodically. To change a file it simply stops including that lease and waits for it to run out.

Where it breaks: stopping a broadcast is instant for a radio; for leases the update must still wait out the last extension's term, so updates to installed files are deliberately slow.
Fault assumption · Bounded drift

Two egg timers, started apart

The server hands the client a 10-second egg timer. As long as both timers tick at nearly the right rate, the client's timer (started a moment later and set a bit short, by the message delay and the allowance ε) always rings before the server's. Nobody needs to agree on the time of day.

Where it breaks: if the server's timer runs fast or the client's runs slow, the server lets a write through while the client still trusts its copy. The reverse errors only make the client ask again early.
The cost of length · False sharing

A meeting room booked but empty

Booking a room for three hours and leaving after ten minutes means anyone who wants it must interrupt you or wait. A lease held by a client that has stopped using the file does the same: a writer must call it back or wait out the term although there is no real conflict.

Where it breaks: you could cancel the booking when you leave. Clients may relinquish leases too (the paper lists it as a client option), but on-demand leasing does not assume they do, which is why the paper's answer is a short default term.
Andrew's lesson · The two extremes

A dial, not a switch

Andrew went from a zero term in its prototype (consistency checks overloaded the server as it scaled) to effectively an infinite term in the revised system (server callbacks; stale data possible after a communication failure, limited by ten-minute polling). Leases treat the term as a dial between those two settings.

Where it breaks: a dial is free to turn; the right setting depends on R, W, S and message costs, which is what the analytic model computes, and it can differ per file and per client.
The full explanation

How it actually works

Part I is the short story with the paper's model drawn out. Part II opens every mechanism, rule, formula, figure and table.

1 · The gap leases fill

Multiprocessor coherence protocols assume a reliable, synchronous broadcast bus, which a distributed system does not have: hosts crash and messages are lost. The fallback, checking with the server on every read, is always safe but makes every read pay a round trip. Leases aim at the middle: free reads most of the time, with the cost of any failure capped by a clock rather than by the hope that the network behaves.

2 · The lease and its effective term

When a client fetches a datum, the server also grants a lease: nobody writes that datum for ts seconds unless the server first gets this client's approval. The client cannot use the full ts, because the grant takes time to arrive (processing at the sender, propagation, processing at the receiver) and clocks are uncertain by up to ε:

t_c = max(0, t_s − (m_prop + 2·m_proc) − ε)
# t_c = effective term at the cache · t_s = term at the server
# m_prop = propagation delay of one message
# m_proc = time to process a message at one end (send OR receive), so 2·m_proc per message
# ε = allowance for uncertainty in clocks

3 · Choosing the term: the analytic model

A client that reads at rate R does about R·tc more reads during one term, so one extension (a request and a reply, 2 messages at the server) is amortized over 1 + R·tc reads. Writes to a file shared by S caches cost S approval messages each (one multicast request and S−1 replies). For S > 1 and ts > 0 the server handles:

load = 2NR / (1 + R·t_c)  +  N·S·W      # formula (1), messages per second
# N = clients · R, W = per-client read and write rates · S = caches sharing the file
# zero term: load = 2NR (every read is a round trip, no approvals)

# a non-zero term beats zero term only if
α = 2R / (S·W) > 1   and   t_c > 1 / (R·(α − 1))

5 · Fault tolerance and the clock assumption

Leases keep consistency through message loss (including partitions) and client or server crashes, assuming writes are persistent at the server across a crash. Failures only delay writes. After a crash the server honors the leases it granted, most simply by delaying all writes for the longest term it ever granted. What leases cannot survive are "certain Byzantine failures including clock failure", and the two directions of clock error are not symmetric:

⚠
Asymmetric clock failure. A server clock that advances too quickly can let a write through before the lease has expired at the client; a client clock that advances too slowly keeps using a lease the server regards as expired. Both give stale reads. A slow server clock or a fast client clock only adds traffic, because the client gives up the lease before the server does. The paper calls such failures much rarer than crashes and says they can be detected by a synchronization protocol or timestamps in lease messages.

P0 · Paper map

Background and context
  • Paper: Cary G. Gray and David R. Cheriton, Stanford University, "Leases: An Efficient Fault-Tolerant Mechanism for Distributed File Cache Consistency", ACM SOSP, December 1989. The name "lease" was suggested by a colleague (acknowledgements). Gray's PhD thesis on fault tolerance in a distributed file cache was "in preparation" (reference [9]).
  • System: the V distributed system (Cheriton, CACM 1988): diskless MicroVAX II workstations on Ethernet, a file server, V inter-process communication, and host-group multicast (references [5, 6]). The trace comes from recompiling the V file server.
  • What came before: multiprocessor cache coherence (including Cheriton's own VMP-MC work, reference [3]) using a reliable bus; caching file systems that guaranteed consistency with a zero term (Sprite, RFS, the Andrew prototype) or an infinite term (later Andrew); systems that gave up consistency (NFS) or write sharing (Cedar); tokens (Burrows's MFS, Echo); breakable locks (Xerox DFS); time-to-live caches in naming (Lampson's directory service, DNS).
The problem

Keep client caches consistent (single-copy behavior) when hosts crash and messages are lost, without checking with the server on every read, and keep the consistency traffic small enough that large caches stay worthwhile.

The result
  • A lease protocol in which non-Byzantine failures "affect performance, not correctness", with their effect "minimized by short leases."
  • An analytic model of consistency load and delay versus term. With V parameters a 10-second term gives a server load "within 5 percent of that achievable with infinite term" (S = 1: total traffic 27% below zero term, 4.5% above infinite term).
  • An argument that leases matter more as systems grow: higher network delay, faster processors, more hosts. Plus an optimization for installed files.
Mechanisms in dependency order
  1. The goal: single-copy consistency, and why both prior families fall short (M1).
  2. The lease protocol itself (M2), resting on write-through (M3) and on a definition of "datum" that includes names and permissions (M4).
  3. Time: how much of a granted term the client may use (M5), and what clocks must guarantee (M6).
  4. What all this buys under failures (M7), and how the term trades failure delay against traffic (M8).
  5. The model that picks the term (M9) and its evaluation in V and for future systems (M10 to M13).
  6. Server and client policy freedom (M14), used for installed files (M15). Then related work (M16) and limitations (M17).
The central trade-off

One knob, the term. A longer term amortizes each extension over more reads, so server load and read delay fall (quickly at first, then barely). A shorter term bounds how long a failed or idle holder can hold up a writer, shortens server recovery, reduces false sharing and server state. Underneath it is a second trade: leases buy fault tolerance without reliable communication by taking on a dependence on clocks.

M1 · Consistency, and the two prior families

TL;DR
ProblemCaching makes copies; with large caches the traffic to keep them consistent can dominate cache performance.
MechanismDefine consistency as single-copy behavior. Prior protocols either rely on reliable broadcast (from multiprocessors) or check with the server on every read.
Trade-offBroadcast: cheap reads, no tolerance of lost messages or crashed hosts. Check-every-read: tolerant, but a round trip per read.
Breaks whenBroadcast: any partial failure (a lost invalidation leaves a stale copy). Check-every-read: high read rates or high latency.
Key points
  • Definition (§1): consistent means "the behavior is equivalent to there being only a single (uncached) copy of the data except for the performance benefit of the cache."
  • "With large caches, the traffic required to maintain consistency can be the dominant factor in cache performance."
  • Multiprocessor coherence "relies on reliable, synchronous broadcast communication as provided by the system bus." A distributed system "can experience partial failures: a host may crash or messages may be lost."
  • Two categories of existing file-cache protocols: those that "assume reliable broadcast, and so do not tolerate communication failures", and those that "require a consistency check for every read, and so fail to deliver good performance."
  • Leases are "a consistency protocol that handles host and communication failures using physical clocks."
  • The paper later maps prior file systems onto the term axis: check-every-read (at open granularity) is a zero term; server callbacks with no expiry are an infinite term (M16).
How it works, step by step

Reliable-broadcast style, one lost message. Clients A and B cache file F. B writes F; the server sends invalidations to A and B and proceeds when the bus "guarantees" delivery. On a network the invalidation to A is dropped. Nothing ever tells A, so A reads its stale copy until something else makes it refetch. Either the server proceeds (inconsistency) or it waits for A's acknowledgement (if A crashed, forever). The later Andrew system chose "proceed" (M16).

Check-every-read style, the cost. Every read is a request and a reply: 2 messages at the server, a delay of 2mprop + 4mproc. With V's numbers (R = 0.864 reads/s, mprop = 1 ms, mproc = 0.25 ms) that is 1.728 messages/s per client and 3.0 ms added to every read. In the model this is the zero-term load 2NR, the reference value 1.0 on Figure 1.

Assumptions it relies on
  1. A1 Each datum has one primary storage site, the server; caches hold copies.
  2. A2 The goal is strict single-copy consistency, not hints.
  3. A3 Failures are partial and non-Byzantine: crashes, lost messages, partitions.
  4. A4 (implicit) The costs that matter are messages handled by the server and delay added to client requests.
If an assumption changes
  1. If a datum were replicated on several servers, a lease from one server says nothing about writes at another; the replicas would need their own agreement protocol (inference). The paper's model has a single server.
  2. If hints are acceptable, a plain time-to-live suffices (DNS, M16): no approvals, no waiting, but readers may see stale data and must detect it some other way.
  3. If failures can be Byzantine (a client that ignores invalidations, a clock that lies), neither family nor leases can guarantee consistency; the paper excludes this.
  4. If messages were nearly free relative to the work per read, check-every-read would be acceptable and leases would gain little (inference); the paper argues the opposite trend (faster processors, M13).
Design notes and rejected alternatives

The paper rejects reliable broadcast because a protocol that waits for every cache to acknowledge either blocks forever on a crashed cache or gives up consistency when it stops waiting. It rejects check-every-read on performance. A lease keeps the "wait for acknowledgement" structure but bounds the wait in time, which is the whole idea.

Connections

NFS: neither family. Clients cache attributes for a fixed timeout (3 s for files, 30 s for directories) and flush written data on close; the server promises nothing about other clients' caches, so a reader can see stale data within the timeout. hw vs sw virtualization: the VMM's shadow page tables are a cache of the guest's page tables kept coherent by write-protecting the primary (traces); a hardware fault is never lost, so this is the reliable-delivery family inside one machine, and it needs no time bound.

Questions worked through

Why not use reliable broadcast like multiprocessor coherence?

A bus provides reliable, synchronous broadcast; a network does not. A host may crash or a message may be lost, and then a protocol that waits for every acknowledgement either blocks forever or gives up consistency. Leases bound the wait in time.

M2 · The lease protocol

TL;DR
ProblemGive clients free reads from cache while guaranteeing no write happens that a cached reader does not know about, even if some holder cannot be reached.
MechanismEvery fetch returns the datum plus a lease for a term. Reads inside the term are served locally. A write is deferred until each holder has approved (and invalidated its copy) or its lease has expired. The writer's request implies its own approval; no new leases are granted on the file while a write waits.
Trade-offCheap reads and strict consistency, paid for with extension messages, approval messages, and writes that may wait up to a term.
Breaks whenA client keeps using a datum after approving or after its term (Byzantine behavior or clock failure), or writes bypass the server.
Key points
  • "A lease is a contract that gives its holder specified rights over property for a limited period of time." For caching, it "grants to its holder control over writes to the covered datum during the term of the lease, such that the server must obtain the approval of the leaseholder before the datum may be written."
  • "When a leaseholder grants approval for a write, it invalidates its local copy of the datum."
  • A cache needs "a valid lease on the datum (in addition to holding the datum) before it returns the datum in response to a read, or modifies the datum in response to a write."
  • Fetch: the server returns the datum and "a lease guaranteeing that the data will not be written by any client during the lease term unless the server first obtains the approval of this leaseholder."
  • Read in term: if the datum is still cached, "immediate access ... without communicating with the server."
  • Read after expiry: the cache must "first extend the lease on the datum, updating the cache if the datum has been modified since the lease expired."
  • Write: "the server must defer the request until each leaseholder has granted approval or the term of its lease has expired."
  • Writer's implied approval (§3.1, footnote 5): one approval message is saved if the write request carries the requester's approval. This lets "the common case of an unshared file ... be handled with a single unicast request-response", and "a longer term always decreases the server load for unshared files."
  • No starvation (footnote 1): "the server does not grant new leases on a file when a write is waiting for approval or for leases to expire."
  • Approval by multicast (§3.1): the server multicasts one approval request to the leaseholders and processes the replies: S messages in all for S sharers (writer included).
  • Who decides what (§4): the server controls the term and "is also free to wait for a lease to expire instead of seeking approval of a write." The client decides when to request extension, when to relinquish a lease and when to approve a write.
  • Server state (§2): a record of each holder's identity and a list of the leases it holds, each lease "only a couple of pointers"; about one kilobyte per client holding about one hundred leases.
  • In the model, a client holds at most one lease per file (§3.1).
How it works, step by step
# client side (write-through cache)
read(F):
  if F in cache and now_client < lease[F].expiry:  # valid lease AND datum
      return cache[F]                              # no message
  reply = server.extend_or_fetch(F, cached_version)  # 1 request + 1 reply
  if reply.changed: cache[F] = reply.data       # "updating the cache if modified"
  lease[F].expiry = receive_time + t_c(reply.term)  # M5
  return cache[F]

write(F, data):
  server.write(F, data)                # carries this client's approval

on approval_request(F):                 # client may answer at once
  drop cache[F]; drop lease[F]; reply APPROVE

# server side
on fetch_or_extend(F, c):
  if F.write_pending: hold the request       # footnote 1 (hold vs refuse: not stated)
  holders[F][c] = now_server + t_s; reply(data if changed, t_s)

on write(F, data, w):
  F.write_pending = true
  others = { c in holders[F] : c != w and holders[F][c] > now_server }
  multicast APPROVE?(F) to others
  wait until every c in others has approved or holders[F][c] <= now_server
  apply write to stable storage; F.write_pending = false
  reply to w; serve queued requests

The pseudo-code is this guide's rendering of the §2 rules; the paper gives the rules in prose. How the server knows the datum "has been modified since the lease expired" (a version number or timestamp) and whether the writer keeps a lease after its write are not stated (inference territory). The trace below uses a 10-second term on the server's clock.

  1. t = 0. A misses on F, sends fetch(F). The server records A until 10 and replies with the data and ts = 10 s. A computes tc = 10 − 0.0015 − 0.1 = 9.8985 s (M5).
  2. t = 1, t = 2. B and C fetch F; the server records B until 11 and C until 12. Server state for F: three holders, about a couple of pointers each.
  3. t = 3. C crashes. The server does not know.
  4. t = 5. A reads F again: valid lease and cached datum, so it is served locally with zero messages.
  5. t = 6. B writes F. Its request implies B's approval. The server marks F write-pending and multicasts APPROVE?(F) to A and C (one message).
  6. t ≈ 6.003. A invalidates its copy, drops its lease and replies APPROVE. C never replies. If C had replied too the write would complete after ta = 2mprop + (S+2)mproc = 2 + 5 × 0.25 = 3.25 ms for S = 3.
  7. t = 8. D asks to fetch F. A write is pending, so no lease is granted; D's request waits.
  8. t = 12. C's lease expires on the server's clock. Every holder has now approved or expired. The server applies B's write, replies to B, and serves D: new data and a lease until 22.
  9. t = 13. A reads F: it has no lease, so it fetches and gets the new data. Consistency held throughout: nobody read the old F after the write was applied, because A gave up its copy and C's lease had run out (C's own effective term ended at 2 + 9.8985 ≈ 11.9).
Questions worked through

What exactly does a lease grant?

Control over writes to a datum for the term: the server must obtain the holder's approval before the datum may be written. That is what lets the holder read its cached copy without asking. Approving a write means invalidating the copy.

What is a "holder"? Anyone with a cached copy, or someone with exclusive or write access?

A holder (leaseholder) is a client that has been granted a lease on a datum that has not yet expired. In practice that means a client that read the datum and cached it, because the server hands out a lease with every fetch: "When a datum is fetched from the server ... the server also returns a lease."

It is not exclusive. Any number of clients can hold leases on the same file at once; that number is the model's S, "the number of caches in which the file is shared." It is also not write access. What a holder gets is a promise about other people's writes: the server will not let the datum be written during the term without first getting this holder's approval. So a lease is a right to keep reading your cached copy without asking the server, not a right to write.

It is not the same as having a cached copy either. A client whose lease has expired may still have the data in its cache, but it is no longer a holder: before using that copy it must extend the lease, and the server sends fresh data if the file changed in the meantime. Holder = cached copy plus an unexpired lease.

Writes work differently. Under the paper's write-through assumption a client writes by sending the write to the server, and the server delays it until every holder has approved (invalidating its copy) or that holder's lease has run out. The writer may itself be a holder, and then its write request counts as its own approval (footnote 5). Exclusive, write-type leases would only be needed for caches that hold writes locally (non-write-through); the paper says that extension is "straightforward" but does not describe it. The token schemes it cites (Burrows's MFS, Echo) are that kind.

When is a lease granted? Only when a client asks for the data?

Mostly yes: the lease rides on the reply to a fetch. "When a datum is fetched from the server ... the server also returns a lease." There is no separate "give me a lease" step for the first read. The same holds for the other kinds of datum: a lookup or open that fetches a name-to-file binding or permission information gets a lease on that too (Section 2).

There are four other ways a lease starts or continues:

  • Extension on demand. A client whose lease expired asks again before its next read. The server grants a new term and sends the new data if the file changed meanwhile. This is the case the analytic model assumes.
  • Anticipatory extension. A client may renew before the lease runs out, even before it needs the file, to avoid a delay on the next read, at the cost of more server load and more false sharing (Section 4).
  • Batched extension. One request can renew all the leases a client holds; the paper recommends extending "all leases over all files that it still holds" together (Section 3.1).
  • Multicast extension. For installed files the server sends extensions to all clients periodically without being asked (Section 4).

Two cases where a fetch does not get a normal lease: the server may grant a term of zero (for example to a heavily write-shared file, Section 4), which means the data is good for that one read only; and while a write to the file is waiting, the server grants no new leases on it at all (footnote 1).

Does the lease term start when someone writes, and the server then notifies the holders?

No. The term starts when the lease is granted, which is when the client fetches (or extends) the data, and it runs out on its own whether or not anyone writes. A write does not start or restart any term; it only makes the server look at which leases are still running at that moment.

Timeline with a 10 s term: at t = 0, client A reads the file and gets a lease until t = 10. From 0 to 10, A answers reads from its cache with no messages. Two cases:

  • No write. At t = 10 the lease simply expires. A's next read (say at t = 14) must ask the server to extend, which costs one round trip and starts a new 10 s term from t = 14.
  • B writes at t = 6. A's lease is still valid, so the server sends A an approval request. A approves (and drops its copy), and the write proceeds right away; or A never answers, and the server holds the write until t = 10, when A's lease expires anyway. If B had written at t = 12 instead, A's lease would already be over, and the server would let the write through with no message to A at all.

So the server contacts only holders whose terms are still running when the write arrives. That is why a short term means fewer callbacks (less false sharing) and a long term means fewer extensions: that trade-off is what Figure 1 measures.

Assumptions it relies on
  1. A1 Every write goes through the server, which is the single place writes are ordered (write-through, M3).
  2. A2 Clients honor the contract: they stop using a datum once they approve or once tc runs out (non-Byzantine).
  3. A3 Both ends can time the term with bounded error (M5, M6).
  4. A4 Most of the time holders are reachable, so writes usually finish in ta (milliseconds) rather than waiting a term; the model assumes failures are rare.
  5. A5 Writes are persistent at the server across a crash (§5).
  6. A6 Reads greatly outnumber writes, and write sharing is low (the protocol is correct regardless; the benefit needs this, M9).
  7. A7 (implicit) A request for a lease while a write is pending can be delayed without harm.
If an assumption changes
  1. Writes do not go through the server (write-back): a client could change its copy while others hold leases; approval would have to carry dirty data back, and a crash could lose writes. The paper says the extension is straightforward and points to tokens in MFS and Echo, without details (M3).
  2. A client ignores an approval request or keeps reading after approving: that client reads stale data; nothing in the protocol enforces invalidation. The server's view and the other clients stay correct (inference).
  3. Clocks misbehave: see M6; a fast server or slow client clock breaks consistency directly.
  4. Holders are often unreachable: correctness is unchanged, but many writes wait a full remaining term. This is exactly the argument for short terms (M8), and for installed files the paper argues the server should expect to wait anyway (M15).
  5. The server loses writes in a crash: clients may already have read data that no longer exists after recovery, which is not single-copy behavior; the §5 claim explicitly assumes persistent writes.
  6. Writes become common or widely shared: approval traffic NSW grows until no term helps (α ≤ 1, M9); the paper's answer is a term of zero for such files.
  7. New leases are granted while a write waits (footnote 1 removed): a steady stream of readers fetching F could keep at least one unexpired, unapproved lease outstanding at all times, and the write would starve (inference spelling out the footnote).
Design notes and rejected alternatives
  • Approval versus waiting. Asking for approval finishes a write in milliseconds when holders are up; waiting costs no messages but delays the writer up to ts. The server may choose either (§4); installed files use waiting (M15).
  • Implied approval. Without it an unshared write would need an extra message; with it, "a longer term always decreases the server load for unshared files" (footnote 5).
  • Granularity. State could be cut by "recording leases at a larger granularity, so that each client holds few leases, at the expense of some increase in contention" (§2). Footnote 8: multiple files per lease is another source of false sharing.
Connections

NFS: NFS has no approvals and no callbacks; a client learns of another client's write only when its 3 s (file) or 30 s (directory) attribute cache entry times out and fresh attributes differ, and the server never waits for anyone. The NFS timeout bounds how long a client trusts its cache; the lease adds the server-side half, a write that waits for that trust to end. Mesa monitors: the server's wait is a condition wait with a timeout ("all approved" or the deadline), the same robustness pattern as Mesa's timeouts on condition variables, where a missed notify cannot hang a process forever. Eraser: Eraser's state machine also makes read-sharing free and only acts when shared data is written (Shared to Shared-Modified); leases charge nothing for read sharing and charge at the write.

M3 · Write-through, and relaxing it

TL;DR
ProblemThe protocol must know where the current value of a datum lives at every moment, including across crashes.
MechanismAssume write-through caches: every write goes to the server, which applies it only after the approval-or-expiry rule.
Trade-offClean failure semantics and a simple protocol, at the cost of a server message per write.
Breaks whenWrites are frequent (temporary files) or clients must write while disconnected.
Key points
  • "We limit ourselves here to write-through caches, for doing so simplifies the explanation; extending the mechanism to support non-write-through caches is straightforward."
  • "Write-through gives clean failure semantics: no write that has been made visible to any client can be lost; applications must otherwise be prepared to recover from lost writes."
  • The cost of write-through "is considered prohibitive by some" (the paper cites Sprite, [16]), but "can be largely eliminated by giving special handling to temporary files [9, 24], since they receive the majority of writes."
  • In V, temporary-file operations "are handled specially by the V file cache, in a manner analogous to using a local disk for temporary files", so they do not appear in the trace (§3.2, M12).
  • Related work: tokens in Burrows's MFS and in Echo "can be regarded as limited-term leases, but supporting non-write-through caches" (§6).
How it works, step by step
  1. Write-through (the paper's case). B's process writes F. B's cache sends the data to the server; the server runs the approval-or-expiry rule, applies the write to persistent storage, then replies. The write becomes visible to anyone else only when the server applies it, so if B crashes right after, nothing anybody saw is lost.
  2. Write-back, what goes wrong (inference). B updates its cached F and lets its own processes read the new value, but has not sent it. B crashes. A value that was "made visible" (to B's processes) is gone, which is the failure semantics the paper avoids.
  3. Write-back with leases, the shape of the extension (inference; the paper only says "straightforward"). A client may hold a datum dirty only while no other client can read it, which is what a write token provides. When another client wants to read, the server's approval request must make the dirty holder send its data back before invalidating. A crash of the dirty holder then loses its unsent writes, which applications "must otherwise be prepared to recover from."
Assumptions it relies on
  1. A1 The server is reachable when a client writes.
  2. A2 Temporary files can be recognized and handled locally, so the remaining write rate is low.
  3. A3 The extra write latency is acceptable to applications.
  4. A4 The server makes writes persistent before acknowledging (needed for the §5 claim).
If an assumption changes
  1. The writer is partitioned from the server: a write-through write cannot complete; leases do nothing for a disconnected writer's availability (inference). Readers on the server's side are unaffected.
  2. Temporary files cannot be separated: W rises, so α = 2R/(SW) falls and the write-through cost is paid on the majority of writes; leases still work but help less (M9).
  3. Write latency matters more than failure semantics: move to write-back with tokens (MFS, Echo), accepting lost writes on client crash.
  4. The server acknowledges before persisting: a server crash can lose an acknowledged, visible write; consistency after recovery is not guaranteed.
Design notes and rejected alternatives

The authors choose the simpler case to make the protocol and the analysis clean, and argue the cost objection away with special handling of temporary files rather than adopting delayed writes.

Connections

NFS: the NFS client buffers writes and flushes a file on close; the NFS server must commit modified data to stable storage before replying, which is the same "writes persistent at the server" property §5 assumes. NFS gets it from statelessness; leases need it so that waiting out a term after a crash is enough.

Questions worked through

Does write-through make writes slow?

Every write reaches the server, so yes, somewhat. The paper argues the cost "can be largely eliminated by giving special handling to temporary files", which receive most writes; V's cache handles them much like a local disk.

M4 · Leases on name bindings and permissions

TL;DR
ProblemA repeated open needs more than file contents: it needs the name-to-file binding and the permission information.
MechanismCache those too and hold a lease over them; modifying them (for example renaming the file) is a write.
Trade-offOpens become free within the term, at the cost of more leases and of approvals for directory changes.
Breaks whenName or permission data are written often while widely cached (heavy write sharing of directories, inference).
Key points
  • "In order to support a repeated open, the cache must also hold the name-to-file binding and permission information, and it needs a lease over this information in order to use that information to perform the open. Similarly, modification of this information, such as renaming the file, would constitute a write." (§2)
  • The V trace includes "access to information about files (such as directory lookups)", which are "predominantly reads"; because V counts reads and writes per open and per close, directory operations are a larger fraction of logical reads and writes (§3.2).
  • Installed files are covered by "one per major directory" leases (§4), a directory-level datum.
How it works, step by step
  1. A runs latex at t = 0. To open it, A's cache needs three things, each under a lease: the binding "latex" to the file in its directory, the permission information, and the contents.
  2. A runs latex again at t = 5: all three leases are valid, so the open and the reads need no messages (the paper's own example says the cached version is used "without checking with the file server").
  3. At t = 7 another client renames the file. That is a write to the binding: the server must get A's approval (A drops the cached binding) or wait until A's lease on it expires.
  4. At t = 8 A opens "latex" again: no valid binding lease, so it must ask the server and gets the current binding.

The paper does not say how binding, permission and content leases are grouped (one lease per file, per directory entry, or per directory). This guide treats them as separate leases for clarity (inference).

Assumptions it relies on
  1. A1 Name and permission data can be cached and leased like file data.
  2. A2 They change rarely relative to how often they are used.
  3. A3 An open checks all the leases it depends on (implicit).
  4. A4 A lease granularity is chosen (per entry or per directory) that balances state against false sharing.
If an assumption changes
  1. Names are not cached: every open costs a server round trip even when contents are cached, so most of the benefit for small, frequently opened files disappears (inference).
  2. Permissions change often: each change is a write needing approval from every holder; with heavy sharing, α for that datum falls below 1 and it should get a zero term.
  3. The binding lease has expired while the contents lease is still valid: the open cannot rely on the binding, so it must revalidate the name first (inference); the contents may still be usable once the name resolves to the same file.
  4. Coarse granularity (a whole directory under one lease): creating any file in that directory is a write to everyone's lease, producing false sharing (footnote 8 notes multiple files per lease causes false sharing). Installed-file directories tolerate this because they are almost never written.
Design notes and rejected alternatives

The point of the paragraph is scope: consistency is not just about file blocks. Anything the cache uses to answer an operation must be covered, or that operation is not single-copy consistent.

Connections

NFS: NFS resolves pathnames one component per lookup call; its client directory-name cache is flushed when attributes returned by the server no longer match, and permission checks happen at the server on every call. The paper's lease covers the binding and permissions at the client with a guarantee; NFS's caches carry no guarantee.

M5 · The effective term tc

TL;DR
ProblemThe server times the term on its clock from when it grants; the client learns of the grant later and its clock is uncertain.
MechanismThe client uses only tc = max(0, ts − (mprop + 2mproc) − ε).
Trade-offSafety margin versus usable term; large delays or skew need a proportionally larger ts.
Breaks whenA grant arrives later than the subtracted delay plus ε, or clock error exceeds ε.
Key points
  • Message timing model (§3.1): processing time mproc at both sender and recipient and propagation time mprop are the same for all hosts, so "a message is received mprop + 2mproc after it is sent and a unicast request and reply takes 2mprop + 4mproc." A multicast plus n replies takes 2mprop + (n + 3)mproc.
  • mproc counts only processing "on the critical delay path"; queueing delays are ignored (footnote 3). The averages "include a normal level of retransmissions" (footnote 4).
  • The formula tc = max(0, ts − (mprop + 2mproc) − ε): tc "is shortened by the time for the cache to receive the lease mprop + 2mproc plus the allowance ε for clock skew."
  • "In systems with large propagation delays between clients and large clock skew, the server must provide a proportionally larger lease term ts if the lease term at the clients is to be effectively greater than zero."
  • §4: a lease for a distant client "could be increased to compensate for the amount the lease term is reduced by the propagation delay and for the extra delay incurred by the client to extend the lease."
How it works, step by step
  1. V on Ethernet (Table 2). mprop = 1.0 ms, mproc = 0.25 ms, ε = 100 ms. Delivery = 1.0 + 2 × 0.25 = 1.5 ms. For ts = 10 s: tc = 10 − 0.0015 − 0.1 = 9.8985 s. The clock allowance is 67 times the delivery delay.
  2. Where tc hits zero. tc = 0 whenever ts ≤ 0.1015 s. Any such term is worse than a zero term (M8).
  3. 100 ms round trip (the Figure 3 case). A request and reply take 2(mprop + 2mproc) = 100 ms, so delivery is 50 ms and tc = ts − 0.05 − 0.1 = ts − 0.15 s; a 10 s grant gives 9.85 s.
  4. Compensating a distant client (inference arithmetic for §4's suggestion). To give a client with 50 ms delivery the same 9.8985 s as a LAN client, grant ts = 9.8985 + 0.05 + 0.1 = 10.0485 s.
Assumptions it relies on
  1. A1 Grant delivery takes no longer than mprop + 2mproc (the paper uses averages that include normal retransmission).
  2. A2 Clock uncertainty over a term is at most ε (M6).
  3. A3 Terms are seconds while message times are milliseconds, so ta is not a significant fraction of ts (§3.1).
  4. A4 (implicit) The server starts its count no earlier than when it sends the grant; the client starts its count no earlier than when it receives it.
If an assumption changes
  1. A grant is delayed (for example retransmitted after 2 s): a client counting tc from receipt would believe the lease runs about 1.9 s past the server's expiry: a stale-read window. A client that counts from when it sent its request is safe whatever the delay, at the cost of a slightly shorter term (inference; the paper's formula uses average delay and does not discuss this case).
  2. ε is large (loose synchronization): tc shrinks one for one, and with ε ≥ ts leases give nothing; under the drift-only minimum the subtraction only needs to cover rate error over one term (M6).
  3. ts is comparable to message times: tc is near zero, reads gain almost nothing, writes still pay approvals; use a zero term (M8).
  4. The server timestamps the grant when the request arrived rather than when it replies: its expiry moves earlier by its own processing time, which the subtraction (2mproc covers processing at both ends) is meant to absorb (inference).
Design notes and rejected alternatives

The paper accepts a fixed per-lease loss of (delivery + ε) rather than requiring perfect clocks. It notes the loss is negligible for terms of seconds, and handles the bad cases (distant clients, large skew) by granting longer ts, not by changing the rule.

Connections

NFS: NFS's attribute timeout is measured by the client alone from when attributes arrive and promises nothing, so it needs no subtraction; a lease's term is a two-sided promise, so the client must make sure its side ends first.

M6 · Clocks: drift, synchronization, and which errors are unsafe

TL;DR
Problem"Lease expired" must happen at the client no later, in real time, than at the server.
MechanismMinimum: clocks with known bounded drift, term sent as a duration. Reasonable extra: synchronized within ε, which tc subtracts.
Trade-offFault tolerance without reliable communication, in exchange for treating clock failure as a (rare) correctness hazard.
Breaks whenThe server's clock advances too quickly or a client's too slowly beyond the margin.
Key points
  • "Leases depend on well-behaved clocks." A server clock that "advances too quickly can cause errors because it may allow a write before the term of a lease held by a previous client has expired at that client." A client clock that fails "by advancing too slowly ... may continue using a lease which the server regards as having expired."
  • "The opposite errors (a slow server clock or fast client clock) do not result in inconsistencies, but do generate extra traffic since a client will regard leases to have expired before the server does."
  • Such failures "are much less common than either crashes or communication failures"; they can be detected "by either a synchronization protocol or by including explicit timestamps in lease-related messages."
  • "We also regard it as a reasonable assumption that clocks ... are synchronized within ε which is small relative to the lease terms of several seconds." Synchronized time is needed anyway "such as the file-modified times used by the Unix make facility."
  • "As a minimum, the correct functioning of leases requires only that clocks have a known bounded drift, in which case the lease term can be communicated as its duration t."
  • Conclusion: "A key assumption is that clocks are reasonably accurate, at least in terms of drift if not mutual synchronization."
How it works, step by step

Synchronized mode. The server could send an absolute expiry; the client compares it with its own clock, and ε covers the offset between the two clocks. Drift-only mode. The server sends the duration; each side times it locally from its own event (send, receive). Offsets never matter; only the rate does.

How much rate error the V margin tolerates (arithmetic on Table 2 values, drift-only reading). Real time 0: the grant leaves. A perfect client receives at 0.0015 and stops at 0.0015 + 9.8985 = 9.9000.

  • Server clock fast by fraction f: the server reaches "10 s" at real time 10/(1 + f). Safe if 10/(1 + f) ≥ 9.9, so f ≤ 1.01%. At f = 2% the server writes at 9.804, and the client reads stale data for 96 ms.
  • Client clock slow by fraction s: 9.8985 local seconds take 9.8985/(1 − s) real seconds. Safe if 0.0015 + 9.8985/(1 − s) ≤ 10, so s ≤ 1.0%.
  • For scale (general knowledge, not in the paper): ordinary quartz oscillators drift on the order of 10−5 to 10−4, about a thousand times less than this margin. The danger is a clock that fails or is reset, not ordinary drift.
Assumptions it relies on
  1. A1 Clocks do not fail: no jumps, no rates outside the known bound (a clock failure is treated as Byzantine).
  2. A2 The drift bound is known, so the margin can be sized.
  3. A3 ε (or the drift error over one term) is small relative to terms of seconds.
  4. A4 Clock failures are rare and can be detected (synchronization protocol or timestamps in lease messages).
If an assumption changes
  1. A clock is reset: setting the server's clock forward by a minute makes every outstanding lease look expired, so the server could apply writes while clients still read cached copies; setting a client's clock back extends its trust. Timing leases with a monotonic interval timer rather than time of day avoids this (inference and general knowledge, not in the paper).
  2. The drift bound is unknown: no safe tc can be computed; the only safe choice is a zero term, which is check-on-every-read.
  3. ε is comparable to ts: tc approaches zero; either lengthen terms or improve synchronization. The drift-only mode avoids paying for offset at all.
  4. Clock faults go undetected: inconsistency is silent. The paper's remedy is detection, via synchronization or timestamps carried in lease messages, so that a client can notice a disagreement (the mechanism is only named, not specified).
Design notes and rejected alternatives

The paper deliberately uses physical time: the conclusion describes leases as reasoning based on "the availability of clocks that measure the passage of time with modest accuracy, and the ability to draw conclusions after a passage of time, possibly in the absence of communication." Anything that needs messages to establish order (rather than elapsed time) could not draw a conclusion about an unreachable host (inference).

Connections

NFS: NFS's protocol does not depend on clocks, but its time skew section shows programs that compare file times with the current time (ranlib with ld, ls, emacs) break when server and client clocks differ, and plans a time synchronization protocol. Leases' paper uses the same kind of argument (Unix make) to say synchronized clocks are needed anyway.

M7 · Fault tolerance: client crash, partition, lost messages, server crash

TL;DR
ProblemA consistency protocol must neither block writers forever nor let anyone read stale data when hosts crash, messages are lost or the network partitions.
MechanismEvery promise expires. An unreachable holder costs a write at most its remaining term. A recovering server honors leases it granted before crashing by delaying all writes for the maximum term it ever granted, or by keeping lease records on persistent storage.
Trade-offCorrectness through all non-Byzantine failures, in exchange for bounded write delays and a longer server recovery.
Breaks whenClocks fail, components behave in a Byzantine way, or writes are not persistent at the server across a crash.
Key points
  • "Leases ensure consistency provided that the hosts and network do not suffer certain Byzantine failures including clock failure. More specifically, consistency is maintained in spite of message loss (including partition), and client or server failures (assuming writes are persistent at the server across a crash)." (§5)
  • "Availability is not reduced by the caches because an unreachable client at most briefly delays write access by other clients."
  • Client failure or partition: "When the server cannot communicate with a client, the server must delay writes to a file for which the failed client holds a lease until that lease expires." (§2)
  • Server recovery: "it must honor the leases it granted before it crashed. This is most easily done if it remembers the maximum term for which it had granted a lease, and it delays writes to all files for that period, effectively increasing the time to fully recover by the maximum term."
  • Alternative: "maintain a more detailed record of leases on persistent storage, but the additional I/O traffic is unlikely to be justified unless terms of leases are much longer than the time to recover."
  • Short terms "minimize the delay resulting from client and server failures (and partitioning communication failures)." Abstract: failures "affect performance, not correctness."
  • The model assumes "the rate of failures is ... low enough to have no significant effect on the average response time, especially with short-term leases" (§3).
How it works, step by step

Every case reduces to one server rule: a write may proceed once each holder has approved or expired. The server never needs to know why a holder is silent.

Questions worked through

What happens if a holder is unreachable when a write arrives?

The server waits until that holder approves or its lease expires. Since an unreachable holder will not approve, the write waits for the rest of that lease, at most one term.

Do leases guarantee consistency whatever fails?

Against non-Byzantine failures (crashes, lost messages, partitions), assuming writes are persistent at the server across a crash. Not against clock failure: a server clock that runs fast or a client clock that runs slow can break it.

What does the server do after it crashes?

It must honor leases granted before the crash, which it no longer remembers. Simplest: delay writes to all files for the maximum term it ever granted, adding that term to recovery time. Alternative: keep lease records on persistent storage, worth the I/O only if terms are much longer than recovery time.

Why can a client keep reading during a partition?

Because its lease is still a valid promise: the server will not let anyone write until the lease expires, and the client's effective term ends before the server's. After tc the client must reach the server to read.

If the approval request is lost, or the holder is too slow to answer, does the server wrongly treat a live client as dead?

First a correction to the framing: the approval request carries no deadline, and the server never decides that anyone is dead. The deadline was fixed earlier, when the server granted the lease: the holder already knows its lease ends at the end of its term. When a write arrives, the server asks holders to approve, and if some holder does not answer, it simply waits until that holder's lease expires. After that the holder has no rights left to protect, whether it is dead, slow, or alive behind a lost message.

Approval request lost. The live holder never learns of the write. It keeps answering reads from its cache, which is correct, because the server has not let the write through yet. When its own clock says the lease has expired (it uses tc, which is shorter than the server's ts), it stops using the cached copy. Its next read must extend the lease; the server either holds that request until the pending write is done (footnote 1) or answers it afterwards, and the client gets the new data. The server finishes the write only after the lease has expired on the server's clock, which is later. Cost: the write is delayed by up to the remainder of the term. Correctness is not affected. The server may also resend the request to cut the delay; that only affects speed.

Holder too slow to answer. Same reasoning. Being slow does not let it keep the lease longer, because expiry is decided by the clock, not by message exchange. The only requirement is that the holder checks its lease against its own clock before every use of the cached copy (Section 2: a cache needs a valid lease before it returns the datum). A read that checked the lease while it was still valid returns data that was current at that moment, since no write could have happened before the server-side expiry.

What actually breaks it. Only the clock failures of Section 5: a holder clock that runs too slow, or a server clock that runs too fast, so the holder believes its lease is still valid after the server has let the write through. A modern example is a client whose whole machine or VM is paused and whose clock does not count the paused time; when it resumes, it thinks it still has seconds left. That counts as the "clock advancing too slowly" case, and it is why the paper requires bounded drift.

  1. Client crash. Holder C crashes at 3 holding a lease to 10. A write arrives at 6, the approval request goes unanswered, and the server applies the write at 10: delay 4 s, bounded by the term. When C restarts it has no lease records it can trust, so it refetches before using any cached data (inference; the paper does not discuss client restart).
  2. Partition. On the server's side it is identical to (1). On the client's side the client may keep reading its copy until its own tc ends (9.9), which is before the server's write (10), so no stale read occurs. After that, reads need the server and cannot be served while partitioned; writes cannot complete either under write-through (inference).
  3. Lost approval request or lost approval reply. Indistinguishable from a crash for the server; it waits until expiry. The model's average message times include "a normal level of retransmissions", so the server may also resend the request (inference about policy).
  4. Lost grant or extension reply. The server has recorded a lease that the client never received. The client never uses it, so it is safe; the cost is a possibly needless approval round or wait later (inference).
  5. Server crash. Lease records are in memory and lost. On recovery the server delays every write for the maximum term (simple), or reads persistent lease records (costly). Writes made before the crash must have been persistent.
Assumptions it relies on
  1. A1 Writes are persistent at the server across a crash.
  2. A2 Failures are non-Byzantine, and clocks do not fail (M6).
  3. A3 Failures are rare enough not to affect average performance (§3).
  4. A4 After a crash the server still knows the maximum term it ever granted (implicit: a configured constant, or a value kept on stable storage).
  5. A5 (implicit) A client cut off from the server cannot complete writes, because caches are write-through.
If an assumption changes
  1. Writes are not persistent: after recovery a datum may revert to an older value that clients have already seen superseded; leases cannot repair that, and the paper's claim explicitly excludes it.
  2. Byzantine client: a client that keeps using its copy after expiry or approval reads stale data itself; others remain consistent because the server's rule is unchanged (inference). A failed clock can break consistency for everyone who reads from that client's cache (M6).
  3. Frequent failures: many writes wait up to a full term and average delay rises, so shorter terms matter more; the model's averages no longer hold.
  4. The maximum term is not remembered (for example terms chosen dynamically per file and client, M14, and lost in the crash): the server must wait for a conservative global bound. Recording that one number on stable storage is cheap (inference).
  5. Partitioned clients could write locally (write-back): two sides could both write and diverge; leases alone do not resolve that (inference; M3).
Design notes and rejected alternatives
  • Later Andrew (effectively infinite term with server notification): "If communication with a client fails ... the server allows updates to proceed, possibly leaving the client operating on stale data", until the client next contacts the server; polling every ten minutes limits the interval. Footnote 2: infinite term comes "at the expense of failing to guarantee consistency after a communications failure." The paper's suggestion: a short-term lease would let Andrew defer updates "in the client failure case long enough to avoid inconsistency."
  • Persistent lease records are rejected for normal terms because each grant would cost I/O.
Connections

NFS: the NFS server keeps no client state, so a server crash needs no recovery and a client "can not tell the difference between a server that has crashed and recovered, and a server that is slow"; clients retry (hard mounts forever, soft mounts give up with an error). A lease server keeps state, but it is soft: it expires on its own, so recovery is "wait one maximum term" rather than rebuilding the holder list. The paper notes that "the soft state required for leasing is compatible with the so-called stateless interface used in NFS." Mesa monitors: bounded waits again; a timed-out wait plus a re-check is what makes the system robust to a missing signal.

M8 · Short vs long terms, zero vs tiny, false sharing

TL;DR
ProblemPick a term: longer saves extension traffic, shorter limits damage from failures and idle holders.
MechanismPrefer short terms (seconds); give a zero term rather than a tiny one; give a zero term when a client will not read again before another client writes.
Trade-offExtension overhead versus failure delay, false sharing and server state.
Breaks whenReads are rare and spread out (little amortization), or writes are heavily shared.
Key points
  • Advantages of short terms (§2): (1) they "minimize the delay resulting from client and server failures"; (2) they "minimize the false write-sharing that occurs"; (3) they "reduce the storage requirements at the server, since the record of expired leases could be reclaimed."
  • False sharing: "a lease conflict when no actual conflict in file access exists ... when a client writes to a file which is covered by a lease held by another client when the other client is not currently accessing the file." It "introduces the overhead of a callback to the leaseholder(s) (thereby delaying the requesting client and loading the leaseholder and server)". "In the extreme, a lease term should be set to zero if a client is not going to access the file before it is modified by another client."
  • Storage is "modest": about one kilobyte per client holding about one hundred leases (so roughly 10 bytes per lease, consistent with "a couple of pointers", inference arithmetic).
  • Long terms "are significantly more efficient both for the client and server on files that are accessed repeatedly and have relatively little write-sharing"; Andrew went from zero to effectively infinite.
  • Zero vs tiny (§3.1): "a zero lease term is better than a very short lease term because a non-zero ts and zero tc means that writes are penalized but reads do not benefit."
  • The §3 model ignores lease space overhead, assumes a low failure rate, and considers only on-demand extension.
How it works, step by step

False sharing, traced. A compiles foo.c: it reads the file at t = 0 (lease to 10) and finishes with it at t = 1. At t = 4, B's editor saves foo.c. A's lease is still valid, so the server multicasts an approval request to A and waits for A's reply: about ta = 2mprop + (S + 2)mproc = 2 + 4 × 0.25 = 3 ms for S = 2, plus load on A and the server. If A is unreachable, B waits until 10. With a 2 s term, A's lease would have expired at 2 and B's write would be a single unicast request and reply. With a zero term there is no lease at all, but A's reads during its one second of use each cost a round trip.

Zero vs tiny, traced with V numbers. Take S = 10, so α = 2 × 0.864 / (10 × 0.039) = 4.43. Grant ts = 0.05 s. Then tc = max(0, 0.05 − 0.1015) = 0: every read still needs an extension (load 2NR), and the server still believes a lease exists, so every write still needs approval (load NSW). Relative load = 1 + 1/α = 1.23, worse than the zero term's 1.00. The break-even is tc = 1/(R(α − 1)) = 1/(0.864 × 3.43) = 0.337 s, so ts ≈ 0.439 s.

Questions worked through

Why does write sharing matter so much?

Each write to a shared file costs S approval messages regardless of the term, so the floor of the load curve is 1/α = SW/(2R). With α near 1 (S = 40 in V) almost nothing is saved, and below 1 a zero term is best.

Is the trade-off just "short term = less time lost to a crashed holder, but more extensions; long term = the reverse"?

That is the core of it, with two corrections that explain why the paper lands on about 10 seconds.

1. Long terms cost something even when nothing fails. The longer the term, the more clients still hold a lease when a write arrives, including clients that stopped using the file long ago. Each of those is a callback the server must send and an approval the writer must wait for: false sharing. Section 2 lists four advantages of short terms: shorter delays after client and server failures and partitions, shorter server recovery (it waits out the longest term it granted), less false sharing, and less lease state on the server. Long terms buy two things: fewer extension messages (server load) and fewer reads that pay a round trip to extend (read delay, Figure 2).

2. The benefit of a longer term saturates fast. Extension traffic falls like 2NR/(1 + R·tc): each lease is amortized over the reads that land inside one term, so the first few seconds remove most of it and later seconds remove little. With V's numbers, a 10 s term cuts consistency traffic to about 10% of a zero term and leaves total server load within about 5% of an infinite term. Past the knee, a longer term buys almost nothing while its costs (failure delay, recovery time, false sharing) keep growing linearly with the term.

So the curve is lopsided, not a symmetric seesaw: go just past the knee and stop. And the right term depends on the file, not just the system: zero for a heavily write-shared file (a tiny non-zero term is worse than zero, because writes pay for approvals while reads gain nothing), effectively infinite for installed files kept alive by multicast, and longer for distant clients that lose part of the term in transit (Section 4).

Assumptions it relies on
  1. A1 Reads of a file come in clusters (temporal locality), so a short term catches most rereads.
  2. A2 Write sharing is low.
  3. A3 Failures are rare, so their delay matters less than average load (§3).
  4. A4 (implicit) Clients do not announce when they stop using a file; otherwise false sharing could be removed directly.
If an assumption changes
  1. Reads are spread out (one read every minute): a 10 s term rarely catches a reread, so almost every read pays an extension and long terms are needed for any benefit, which makes false sharing and failure delay worse (inference from 1/(1 + R·tc)).
  2. Write sharing is heavy: α ≤ 1 and the right term is zero (M9).
  3. Failures are frequent: the failure-delay argument dominates; shorter terms.
  4. Clients relinquish leases when done (a §4 client option): false sharing largely disappears and longer terms become attractive, at the cost of one extra message per relinquish (inference).
Design notes and rejected alternatives

The paper picks a short fixed term (about 10 s) as a good default for V-like workloads and leaves room for per-file and per-client terms (M14). It treats the two historical extremes, zero and infinite, as points on the same axis.

Connections

NFS: its attribute cache uses fixed timeouts (3 s files, 30 s directories) that play the role of a term, chosen without a model and without any server obligation. ESX: content-based page sharing keeps one copy for many readers until a write forces a private copy; as with leases, read sharing is free and the cost is concentrated at the write.

Questions worked through

Why 10 seconds?

With the V parameters, a 10 s term cuts consistency traffic to about 10% of a zero term and leaves total server load within about 5% of an infinite term, while longer terms add little and bring all the disadvantages of long leases. It is a result of the model with those parameters, not a constant: high sharing, different read rates or larger delays move it.

Does the "server load falls fast, then flattens" curve have only one client sharing the datum, so nothing is really shared? Were all their workloads like this?

Yes, that curve is the unshared case. It is S = 1, where S is the number of caches holding the file at the moment it is written. S = 1 means only the writer itself holds a lease, so a write needs no approval messages at all, and the only consistency cost left is extensions. That is why the curve can fall toward zero.

The sharing curves are not measured. The paper's Figure 1 also draws S = 10, 20 and 40, but those are formula (1) evaluated with the same R and W and an assumed S, "to illustrate its effect over a plausible range." Only S = 1 is checked against data: "The trace includes only one client so there are no writes to shared files," and the trace-driven simulation lands close to the S = 1 curve. With sharing, the curves flatten at 1/α instead of 0 (about 0.23, 0.45 and 0.90 of the zero-term load for S = 10, 20, 40), and at S = 40 a 10 s term is slightly worse than a zero term (break-even about 10.75 s, recomputed).

One workload. Every number in Table 2 comes from a single short trace of one job, "recompiling the V file server," on MicroVAX II workstations. Figures 2 and 3 reuse the same parameters (Figure 3 only raises the round trip to 100 ms). The paper concedes its read-to-write ratio is "almost an order of magnitude higher" than in published Unix traces and explains why: V handles temporary files locally, so most writes never reach the server; the trace counts program loading and directory lookups, which are reads; and a read or write is counted per open or close, not per block. It argues the results still carry over and cites old Multics measurements that write-sharing is low, but it lists "a simplified model of file sharing" and "relatively low degrees of sharing" as limitations. So the 10 s recommendation rests on one single-client trace plus assumed sharing.

What Figure 1 does not show
  • Any measured write sharing: S > 1 curves are pure model.
  • Failures, queueing, or more than one client.
  • CPU or byte costs: load is message count.
  • Other ε values: with ε = 100 ms fixed, every curve is shifted right by about 0.1 s.

M12 · Why V's read/write ratio is so high

TL;DR
ProblemV's read-to-write ratio is "almost an order of magnitude higher" than published Unix traces, which could make the result look too good.
MechanismExplain the difference by three properties of V's measurement and cache design, and argue the conclusion carries over.
Trade-offTwo of the three factors are design choices Unix could copy; one is a counting difference.
Breaks whenWorkloads are write-heavy or block-level semantics raise W more than R.
Key points
  1. Temporary files (a large fraction of writes) "do not appear because they are handled specially by the V file cache, in a manner analogous to using a local disk for temporary files."
  2. Program loading and directory lookups are included, "both of which are predominantly reads."
  3. Counting granularity: reads and writes are counted "when a file is opened for reading or closed (committed) with writing, as opposed to each time a block is read or written", so directory operations are a larger fraction of logical operations.
  • Considering these, the trace "is fairly consistent with those of the longer term traces of Unix systems" (references [8], [17]).
  • "Only the last factor represents a departure from the more common semantics of the Unix file system; the other two factors are consequences of the cache design in V and might be profitably employed in a Unix system."
  • Block-level Unix semantics "would give a higher absolute rate of reads, but a somewhat lower ratio of reads to writes"; performance "would be qualitatively similar; the higher rate of reads would give the curves a sharper knee, favoring fairly short terms, while the more frequent writes makes it more sensitive to sharing."
How it works: a hypothetical block-level version (inference, illustrative numbers)

Suppose block counting multiplied reads by 10 and writes by 30: R = 8.64/s, W = 1.17/s, R/W = 7.4. For S = 10: α = 17.28/11.7 = 1.48 (down from 4.43), floor 1/α = 0.68 (up from 0.23), so sharing hurts much more. But the break-even tc = 1/(8.64 × 0.48) = 0.24 s is still tiny, and the extension part at 10 s is 1/(1 + 8.64 × 9.9) = 1.2% (down from 10.5%), so the knee is sharper.   2. No name or program-load caching: R falls, so terms must be longer to amortize, and the benefit shrinks.

M14 · Options for lease management

TL;DR
ProblemThe basic protocol leaves choices open; different choices trade server load against response time.
MechanismServer: picks each term, may wait for expiry instead of asking for approval. Client: decides when to extend (on demand or in anticipation), when to relinquish, when to approve. Batch extensions; pick terms per file and per client.
Trade-offAnticipatory extension removes read delay but adds load and false sharing; per-file terms need monitoring.
Breaks whenClients are idle but keep extending, or monitored parameters are stale.
Key points
  • "The server controls the term of the leases it grants; it is also free to wait for a lease to expire instead of seeking approval of a write. The client is free in deciding when to request extension of leases, when to relinquish them, and when to approve a write. The combinations of these options give different trade-offs between load and response time." (§4)
  • Anticipatory extension: the client may "request extension before the covered file is accessed. Doing so improves response time by eliminating the added delay for reads, but it does so at the cost of increased load for the server. In particular, an idle client continues to request extensions even when files are not being accessed, and because the cache continues to hold leases it may increase the level of contention due to false sharing."
  • Batching (§3.1): one request extends many leases; "a cache should extend together all leases over all files that it still holds."
  • Per-file and per-client terms: "a heavily write-shared file might be given a lease term of zero. A lease given to a distant client could be increased to compensate for the amount the lease term is reduced by the propagation delay and for the extra delay incurred by the client to extend the lease. In general, a server can dynamically pick lease terms on a per file and per client cache basis using the analytic model, assuming the necessary performance parameters are monitored by the server."
  • Future work (§7): "adaptive policies that vary the coverage and term of leases in response to system behavior in place of static, administratively set policies."
How it works, step by step
  1. On-demand versus anticipatory load (inference arithmetic). On demand, a client with read rate R on one file sends R/(1 + R·tc) extensions per second. Anticipating expiry, it extends every tc regardless: 1/tc per second. Since R/(1 + R·tc) < 1/tc always, anticipation always costs more; for V's R at 10 s, 0.0905/s versus 0.101/s per held lease (a 12% increase), and for an idle file 0 versus 0.101/s.
  2. Per-file zero term. The server monitors a file's R, W and S and computes α; if α ≤ 1, or the best achievable tc is below 1/(R(α − 1)), it grants ts = 0 for that file (M9).
  3. Distant client. With 50 ms one-way delivery, granting 10.0485 s gives the same 9.8985 s usable term as a LAN client (M5).
  4. Relinquish. A client that finishes with a file can return the lease, so a later writer needs neither approval nor waiting; the cost is one message per relinquish (inference: the paper lists the option without analysis).
Assumptions it relies on
  1. A1 The server can measure R, W, S and message delays per file and per client.
  2. A2 Clients can batch requests for all their leases.
  3. A3 Load and response time are the right objectives (failure rate low).
  4. A4 (implicit) Different terms for different clients do not complicate correctness; the server simply records each holder's expiry.
If an assumption changes
  1. Parameters cannot be monitored: fall back on a static term such as 10 s; files that are heavily write-shared then pay for approvals they would not need at zero term.
  2. No batching: each file's extensions are separate, so effective R per request is lower and more messages are sent.
  3. Response time matters more than server load: anticipatory extension becomes attractive for busy files, at the cost of extra false sharing from idle clients.
  4. Terms vary per lease and the server crashes: it still needs the maximum term granted to recover safely (M7).
Connections

ESX: ESX also tunes its memory policies from measured statistics (sampling idle memory), the same "measure, then pick the policy parameter" approach this section proposes for terms. NFS: NFS's timeouts are fixed client-side constants, with different values for files and directories, a static version of per-class terms.

Questions worked through

Is the 10 s term fixed for the whole run and for every client?

In the paper's analysis, yes; in the design, no.

The analysis uses one term for everything: the model has one file, one server and a single ts, and Figures 1 to 3 sweep that single value. "10 seconds" is the paper's recommendation from that sweep with V's parameters, not a constant built into the protocol.

The design lets the server pick a term for each grant, because every lease carries its own term. Section 4 lists the options: "the server can set the lease term based on the file access characteristics for the requested file as well as the propagation delay to the client." A heavily write-shared file can get a term of zero; a distant client can get a longer term to make up for the part lost in transit; in general the server can "dynamically pick lease terms on a per file and per client cache basis using the analytic model," given measurements of the read and write rates. Installed files are the extreme case: their leases are renewed by multicast before they expire, so in the absence of writes they effectively never run out.

The paper's own prototype was not there yet: its conclusion lists as future work "adaptive policies that vary the coverage and term of leases ... in place of static, administratively set policies," which suggests V used a fixed, administrator-set term.

Even with one fixed ts, the usable term differs per client: tc = ts minus that client's message delay and the clock allowance, so a distant client gets less. And varying terms has a cost on recovery: the server must remember the longest term it has granted and wait that long after a crash (Section 2), so one long lease to one client makes every recovery slower (see Class Prep C4).

M15 · Installed files: periodic multicast extension

TL;DR
ProblemCommands, headers and libraries are read by everyone; per-client leases on them cost extension traffic, server records, and an implosion of approval replies when one changes.
MechanismCover them with a few leases (for example one per major directory); multicast an extension of those leases to all clients periodically; to update, drop the lease from the multicast and write once it has expired.
Trade-offNo read delay, no client requests, no per-client records, no reply storm; updates wait up to a term.
Breaks whenThe covered files are updated often, or multicast is unavailable.
Key points
  • Installed files are "commands, header files and libraries which are part of the standard system support. These files are widely shared, heavily read and only infrequently written. In the trace taken from V, they account for almost half of all reads, but no writes."
  • Use "a smaller number of leases to cover these files, such as one per major directory", and multicast "an extension covering leases on installed files to all clients periodically, eliminating the need for clients to request extensions of these leases."
  • "The server can simply eliminate a lease from the multicast extension when a file covered by the lease is to be modified. The write operation then proceeds as soon as the lease has expired."
  • This "eliminates the need for the server to contact a large number of clients when an installed file is updated and the resulting implosion of responses." Because the server would likely have to wait for a timeout anyway ("one of the many client machines is unreachable"), installed-file writes "do not necessarily experience higher delay."
  • It also "eliminates the need for the server to keep track of the leaseholders for installed files", and "eliminates added delay at the client cache for reads of installed files because, in the absence of writes to installed files, these leases do not expire."
  • Footnote 8: multiple files per lease can cause false sharing, ignored here "because the rate of update is so low." Conclusion: installed files handled "using multicast extensions from the server to extend the leases on directories of these files and delayed update to avoid the overhead of explicit lease invalidation."
How it works, step by step

Questions worked through

How are installed files different?

They are covered by a few leases (for example one per major directory) that the server extends by periodic multicast to all clients, so clients never request extensions and the server keeps no holder list. To update, it stops extending and waits for expiry.
Assumptions it relies on
  1. A1 Installed files are written very rarely, so a whole-directory lease causes negligible false sharing (footnote 8).
  2. A2 Multicast reaches nearly all clients nearly every period.
  3. A3 Updaters (administrators installing software) can wait up to a term.
  4. A4 (implicit) A client that joins or reconnects can get the lease on demand.
If an assumption changes
  1. Frequent updates (a library under active development): each update waits up to a term and invalidates the whole directory for everyone, so false sharing and blocked writes add up; per-file, on-demand leases fit better (inference).
  2. No multicast: the server would have to send N unicast extensions per period whether or not anyone reads, or fall back to on-demand extension (inference).
  3. An update cannot wait (security fix): the server could request approval explicitly, but then it must know the holders and absorb the implosion of replies that the scheme was designed to avoid.
  4. Multicasts are often lost: clients run out of lease and fall back to on-demand extension, so the scheme degrades to ordinary leases rather than becoming unsafe (inference).
Design notes and rejected alternatives

Andrew instead used "a separate immutable volume for installed files to avoid the cost of their update under the normal mechanism"; the paper argues leases handle installed files "well within the same framework." Lampson's global directory service follows the same policy (expiry, no modification before expiry) but without extension or approval.

Connections

Livelock: the "implosion of responses" is a receive-side burst: many replies arriving at once at one server, the kind of input overload the receive-livelock paper studies (inference link). NFS: NFS treats binaries like any file, validated by the 3 s attribute timeout per client; the server never pushes anything.

M17 · Stated limitations, conclusions, and what the paper leaves open

Conclusions (§7)
  • "Leasing is an efficient, fault-tolerant approach to maintaining file cache consistency in distributed systems."
  • The model estimates consistency load and delay "as a function of the lease term, the ratio of reads to writes, the degree of sharing and message times"; a trace-driven simulation gives "(partial) validation."
  • "A relatively short lease term is close to optimal" for Unix-like access dominated by software development and document preparation; with V parameters "a lease term of 10 seconds results in a server load that is within 5 percent of that achievable with infinite term."
  • Short terms have "lower write delays resulting from client crashes, lower recovery delay from server crashes and reduced false sharing."
  • Leases suit large-scale systems; for faster processors and higher-delay networks "the round-trip time to the client becomes a significant cost and potentially affects the choice of lease term." Installed files: multicast extensions and delayed update.
  • "Leases provide strict consistency in spite of non-Byzantine failures, including partitions. Failures result only in reduced performance." Key assumption: clocks "reasonably accurate, at least in terms of drift if not mutual synchronization."
Stated limitations and future work
  1. A simplified model of file sharing with evaluation focused on low degrees of sharing; exceptions worth study: "distributed transaction processing systems, distributed parallel programming systems and possibly systems that make extensive use of remote execution."
  2. The performance analysis "is only approximate, since it ignores important factors such as queueing delays."
  3. "Limited experience with the use of leases in actual system operation"; the authors are extending and tuning the V file caching service and plan adaptive policies for coverage and term.
  4. Other applications: large-scale shared-memory multiprocessors (benefits "evaluated relative to the costs of timers on memory and cache lines, and the ability of the software to handle failures"), a distributed transaction management protocol, and a transport protocol. The general idea: coordination based on real time and "the ability to draw conclusions after a passage of time, possibly in the absence of communication."
Things the paper does not resolve (this guide's list)
  • Figure 2's single curve does not match formula (2)'s write term for S = 40 (M11).
  • The base of Figure 3's 10.1% and 3.6% is not stated; it matches one round trip per operation (M13).
  • When each side starts counting a term, and how a delayed grant is handled, given the formula uses average delays (M5).
  • How a held write request is handled under footnote 1 (queued or refused), whether the writer keeps a lease after writing, and how the server detects "modified since the lease expired" (M2).
  • Retransmission of approval requests, client restart, and what a partitioned client's applications see (M7).
  • The design of the non-write-through extension, called "straightforward" (M3).
  • Concrete period and term for installed-file multicasts (M15).

① From consistency load to total server traffic

At zero term consistency is 30% of server traffic (V trace). With S = 1, what does a 10 s term do to total traffic, and how close is that to an infinite term?

  1. Effective term: tc = 10 − (0.001 + 2 × 0.00025) − 0.1 = 9.8985 s.
  2. Relative consistency load (S = 1): 1/(1 + 0.864 × 9.8985) = 1/9.552 = 0.1047, the paper's "10%".
  3. Total: 70% + 30% × 0.1047 = 73.1%, a 26.9% reduction (paper: 27%).
  4. Infinite term: consistency load → 0 for S = 1, so total → 70%.
  5. Gap: 73.14/70 = 1.045, 4.5% above the infinite-term floor (paper: 4.5%).
🍯
Insight: consistency was only 30% of the load to begin with, so even removing 90% of it moves total traffic by 27%. The ceiling on what any term can buy is set by how big a slice consistency was.

② The same with sharing, S = 10

Repeat ① for a file shared by 10 caches at each write.

  1. α = 2R/(SW) = 1.728/0.39 = 4.43; the write part of the relative load is 1/α = 0.226 at any non-zero term.
  2. At 10 s: 0.1047 + 0.2257 = 0.330. Total = 70% + 30% × 0.330 = 79.9%: 20% below zero term (paper: 20%).
  3. Infinite term: 70% + 30% × 0.2257 = 76.8%. Gap: 79.91/76.77 = 1.041, 4.1% above (paper: 4.1%).

The approval part does not shrink with the term: it is NSW messages per second whatever ts is, as long as ts > 0. Only the extension part amortizes.

③ Multicast approval savings

A write arrives for a file shared by S = 10 caches (writer included). Count approval messages with and without multicast.

  1. With multicast: one request reaches the other 9 holders, 9 replies come back, and the writer's approval is implied: S = 10 messages, taking ta = 2 × 1.0 + (10 + 2) × 0.25 = 5.0 ms.
  2. Without multicast: a request and a reply per other holder: 2(S − 1) = 18 messages (footnote 6).
  3. Saving: 8 messages, 44% (this guide's arithmetic). As S grows the saving approaches 50%, but both counts still grow linearly in S.
  4. Effect on α: unicast α = R/((S − 1)W) = 0.864/0.351 = 2.46 instead of 4.43, so the floor rises from 0.23 to 0.41 (inference arithmetic: floor = 1/α).
💡
The model's write term is NSW because multicast is built in; without multicast it would be 2N(S − 1)W.

④ When does a lease help at all? S = 40

Find the break-even term for a file shared by 40 caches.

  1. α = 1.728/(40 × 0.039) = 1.728/1.56 = 1.108. Just above 1, so some term helps.
  2. Break-even: tc > 1/(R(α − 1)) = 1/(0.864 × 0.108) = 10.75 s, so ts > 10.85 s.
  3. Check at 10 s: 0.1047 + 1/1.108 = 0.1047 + 0.903 = 1.008: slightly worse than zero term. At 30 s: 0.037 + 0.903 = 0.94.
  4. Without multicast: α = 0.864/(39 × 0.039) = 0.57 < 1, so no term ever helps; this file should get ts = 0.

⑤ Longer network delay: reading Figure 3

With a 100 ms round trip and everything else unchanged, the paper reports that a 10 s term degrades response by 10.1% over an infinite term and a 30 s term by 3.6%. Recompute.

  1. Delivery: a request and reply take 2(mprop + 2mproc) = 100 ms, so one-way delivery is 50 ms and tc = ts − 0.15 s.
  2. 10 s: fraction of operations paying a round trip = 1/(1 + 0.864 × 9.85) × 0.864/0.903 = 0.1051 × 0.957 = 0.1006. Added delay = 10.06 ms, which is 10.1% of 100 ms.
  3. 30 s: 1/(1 + 0.864 × 29.85) × 0.957 = 0.0357, so 3.57 ms or 3.6%.
  4. Shape: tripling the term cuts the penalty 2.8 times (not 3) because of the "+1" in 1/(1 + R·tc).
🍯
Insight: the base of the paper's percentages is not stated; the numbers match "added delay as a fraction of one 100 ms round trip" exactly (inference). The conclusion stands either way: 10 to 30 s terms are adequate on a slow network.

⑥ How much clock error the V margin tolerates

With ts = 10 s and ε = 100 ms, how fast may the server's clock run (or how slow the client's) before a stale read is possible?

  1. Client stops at real time 0.0015 + 9.8985 = 9.900 s (perfect client clock, grant sent at 0).
  2. Server fast by f: it reaches "10 s" at 10/(1 + f). Safe while 10/(1 + f) ≥ 9.9, so f ≤ 1.01%. At f = 2% the server writes at 9.804 s: 96 ms of possible stale reads.
  3. Client slow by s: it stops at 0.0015 + 9.8985/(1 − s). Safe while that is ≤ 10, so s ≤ 1.0%.
💡
The margin is far wider than ordinary oscillator drift (general knowledge: around 10−5 to 10−4); what it does not protect against is a failed or reset clock, which the paper treats as a Byzantine failure.

⑦ Server crash recovery and storage

The server's maximum term is 10 s. It crashes at 100 s and reboots at 103 s. Separately: how much memory do lease records cost?

  1. Simple rule: delay writes to all files for the maximum term after recovery: no writes from 103 to 113. Recovery effectively takes 3 + 10 = 13 s.
  2. Why that is enough: any lease granted before the crash was granted before 100 and ends by 110 < 113 (inference: the rule is conservative because the server does not know exactly when it crashed).
  3. Persistent records: only files with recorded live leases wait, but every grant and extension costs I/O; the paper judges this worthwhile only if terms are much longer than recovery time.
  4. Storage: about 1 KB per client holding about 100 leases (paper), so about 10 bytes per lease. For 1,000 clients (illustrative, not a paper number): about 1 MB. Recording leases at coarser granularity would cut it, "at the expense of some increase in contention."

Problem 1 · easy
Why does the paper say a zero term is better than a very short non-zero one, when both seem about the same?
Show answer
If ts is non-zero but tc = 0 (with V numbers, any ts ≤ 0.1015 s), every read still needs an extension, so reads gain nothing; but the server believes a lease exists, so every write still needs approval or must wait. Relative load is 1 + 1/α (1.23 for S = 10) against 1.00 at zero term.Misconception: "some lease is always better than none." A lease pays off only once tc is usable; otherwise it is pure write cost.
Problem 2 · medium
A hypothetical term leaves relative consistency load at 50%, with consistency again 30% of zero-term traffic and S = 1. What is the total traffic reduction, and how far is it from the infinite-term floor?
Show answer
Total = 70 + 30 × 0.50 = 85%, a 15% reduction. The floor is 70%, so the gap is 85/70 = 1.214, 21.4% above it, against 4.5% at the paper's 10 s point.Misconception: that total traffic falls in proportion to consistency traffic. Halving consistency load cuts total traffic by only 15% here.
Problem 3 · medium
A write lands on a file shared by S = 5 caches (writer included). How many approval messages with multicast, how many with unicast, and how long does multicast approval take with Table 2 values?
Show answer
Multicast: 1 request + 4 replies = S = 5. Unicast: 2(S − 1) = 8. Saving 3 messages (37.5%), approaching 50% as S grows. Time: ta = 2mprop + (S + 2)mproc = 2 + 7 × 0.25 = 3.75 ms.Misconception: that multicast makes approval cost independent of S. The request is one message, but the server still processes S − 1 replies.
Problem 4 · hard
Using α = 2R/(SW), explain why the paper says a heavily write-shared file might be given a term of zero, and give the exact condition under which any non-zero term helps.
Show answer
A non-zero term lowers load only if 2NR > 2NR/(1 + R·tc) + NSW, which simplifies to α > 1 and tc > 1/(R(α − 1)). Heavy write sharing means large S or W relative to R, pushing α to or below 1: then even an infinite term leaves the load at NSW ≥ 2NR, no better than zero term. Zero term also avoids making writers wait for approvals or expiry.Misconception: "more caching always helps." The benefit depends on the read/write ratio scaled by sharing, and can be negative.
Problem 5 · medium
For installed files, what "implosion of responses" does the periodic multicast scheme avoid, and why does the paper say updates are not necessarily slower?
Show answer
Without the scheme, updating a widely cached installed file means asking every holder for approval: one multicast out, but a flood of approval replies back to the server at once (the implosion), plus per-client records. With the scheme the server just stops including the lease in its periodic extension and writes after the lease expires: no requests, no replies, no holder list. The update waits up to a term, but with many client machines one is likely unreachable, so an approval-based update would often have waited for a timeout anyway.Misconception: that the implosion is clients asking for extensions. It is the replies to the server's approval request.
Problem 6 · hard
Why is a slow client clock (or fast server clock) a correctness bug, while a fast client clock (or slow server clock) only costs traffic?
Show answer
Correctness needs the client to stop trusting its copy no later, in real time, than the server lets a write through. A slow client clock pushes the client's stop later; a fast server clock pulls the server's write earlier: either creates an overlap in which the client reads data the server has already allowed to change. The other two errors make the client give up first, so it re-extends sooner than needed (extra traffic) but never reads stale data.Misconception: that any clock disagreement is equally dangerous. Only the direction that lets a client over-trust its copy breaks consistency.
Problem 7 · medium
The revised Andrew system used effectively an infinite term. What did it give up, and what limited the damage?
Show answer
Consistency after a communication failure (footnote 2). The server notifies clients of changes; if it cannot reach a client it lets the update proceed, and that client keeps using stale data until it next contacts the server. Polling every ten minutes limits the interval. The paper suggests a short-term lease would let the server defer the update just long enough to avoid the inconsistency.Misconception: that callbacks alone give consistency. Without a time bound, a lost callback leaves a stale reader indefinitely.
Problem 8 · easy
A client read a file once at t = 0 with a 10 s term and never touches it again. Another client writes it at t = 4, and a third writes it at t = 25. What happens each time?
Show answer
At t = 4 the first client's lease is still valid, so the server must get its approval (callback) or wait until t = 10, although that client is not using the file: false sharing. At t = 25 the lease has expired, so the write needs no approval at all.Misconception: that any idle lease is false sharing forever. It exists only while the lease is valid, which is why short terms minimize it.
Problem 9 · medium
A client is reached over a link with 200 ms one-way delivery (mprop + 2mproc), ε = 100 ms. What tc does a 10 s grant give, and what ts gives it the same tc as a LAN client (9.8985 s)?
Show answer
tc = 10 − 0.2 − 0.1 = 9.7 s. To get 9.8985 s, grant ts = 9.8985 + 0.2 + 0.1 = 10.1985 s. This is the §4 option of lengthening terms for distant clients; each extension also costs this client a 400 ms round trip, another reason to give it a longer term.Misconception: that the server's term is what the client gets. The client always loses one delivery delay plus ε.
Problem 10 · hard
An extension reply from the server is lost. Is consistency at risk? What does the server believe, and what is the cost?
Show answer
Not at risk. The server has recorded a lease the client never received; the client never uses a lease it does not have, so it simply asks again. The only cost is that until that recorded lease expires, a writer may have to get an approval from (or wait for) a client that is not actually holding anything, which is extra delay, not inconsistency. (This case is reasoned from the §2 rules; the paper does not discuss it.)Misconception: that any lost message in a consistency protocol is dangerous. Losses that make one side more conservative are safe.
Problem 11 · medium
Why does the server stop granting new leases on a file while a write is waiting? Construct the failure it prevents.
Show answer
Footnote 1: to avoid starving the write. Suppose the server kept granting leases to readers during the wait. Reader D fetches at 8 (lease to 18), reader E at 15 (lease to 25), and so on: there is always some unexpired lease whose holder must approve or expire, and with an unreachable or slow reader among them the write can be postponed indefinitely.Misconception: that a write only waits for the holders present when it arrived. Without footnote 1, new holders keep joining the set.
Beyond the paper

Connections to modern OS and memory-systems design

Where this 1989 idea shows up later. Everything on this tab is commentary, not a claim of the paper.

🔒 Lease-based coordination services

Lock and coordination services built later (Chubby, ZooKeeper, etcd) use leases or sessions with timeouts so that a crashed holder cannot block others indefinitely, the same argument as this paper's §5 (general knowledge, not in the paper). Their terms of seconds echo the trade-off here: failover delay against renewal traffic.

🌐 TTLs are leases without the promise

The paper itself draws this line: a DNS time-to-live bounds how long a client caches, but "the data may be modified during that interval", so the cached data are hints. A lease adds the server-side half, no write until the term ends or the holder approves. It is a useful test for any TTL-based cache: is the server bound by the TTL, or only the client?

🧊 Hysteresis in page-migration policy

Mirage's minimum holding time (a client keeps a lease at least that long before relinquishing it, to reduce thrashing; cited in §6) is the same knob as cool-down windows in hot/cold page tiering (TPP, Memtis, HeMem): accept a short delay in reacting to change in exchange for not ping-ponging (commentary).

🧩 Multi-host shared memory and fault bounds

Speculative (not in the paper): multi-host CXL memory pools face the problem the paper's conclusion raises for shared-memory multiprocessors, where a host can hang or disconnect while holding cached state. A time-bounded write veto bounds recovery latency, but the paper itself warns that benefits must be weighed against "the costs of timers on memory and cache lines."

🍯
Takeaway for tiering research: classify any coherence or placement protocol by how it treats an unresponsive participant: trust the fabric (broadcast family), ask every time (check family), or bound the wait with a clock (lease). The lease answer costs a clock assumption, and the dangerous direction is the one where the holder's clock runs slow.

Questions with real answers

Each one is a tricky case the paper does not spell out, but it has a definite answer you can work through from the mechanisms. The quoted block is how to ask it in class. Try your own answer before opening the worked one.

C1 · Do readers stall behind a crashed leaseholder?

Section 5 says an unreachable client "at most briefly delays write access by other clients". But footnote 1 says the server does not grant new leases on a file while a write is waiting, and Section 2 says a cache needs a valid lease before it returns data. If client A holds a lease and crashes, and B then writes the file, what happens to client C that wants to read the file during the wait? Does the rule have to be that strict?

AnswerWork it out first, then open▾

As written, C stalls too. B's write waits until A's lease expires (up to one term). During that wait the server refuses new leases (footnote 1), and C cannot read without a lease (Section 2). So a crashed leaseholder plus one pending write blocks every new reader of that file for up to a term, not only writers. Readers that still hold valid leases keep reading until their own leases run out, then they block too.

The rule can be relaxed without hurting the writer. The write cannot proceed before A's lease expires anyway, so the server can give C a lease that ends no later than that moment, or simply a zero-term lease (the paper treats zero as a valid term). C reads the current data, the write is not delayed by one more instant, and no starvation results because no granted lease outlives the time the writer was already waiting for. Footnote 1 is a sufficient rule, not a necessary one.

Where the answer comes from: Derived from footnote 1, Section 2's read rule, and Section 5. The truncated-lease relaxation is this guide's inference; the paper does not discuss it.

C2 · Updating one installed file under a per-directory lease

Installed files are covered by one lease per major directory, extended by periodic multicast. To update one file, the server drops that lease from the multicast and waits for it to expire (Section 4). Footnote 8 admits this is a kind of false sharing. Concretely, how long are reads of the other files in that directory blocked, and is the update safe for a client that missed some of the multicasts?

AnswerWork it out first, then open▾

Readers lose almost nothing. Every client keeps reading its cached copies until its own lease runs out, which happens just before the server's copy of the term runs out (the client's term is shorter by the message delay and the clock allowance). Only between that moment and the write's completion does a client that wants to read have to ask for a lease and wait (footnote 1). That gap is roughly one message delay plus the clock allowance plus the time to do the write: milliseconds, not a term.

The cost lands on the writer instead: the update waits up to a full term after the last multicast, even if nobody is reading. The paper accepts this because installed files are rarely written.

A client that missed multicasts is safe: its lease expires earlier than everyone else's, and expiring early only costs an extra lease request. The unsafe direction is a client that believes its lease lasts longer than the server does, which a missed message cannot cause.

Where the answer comes from: Derived from Section 4, footnotes 1 and 8, and the effective-term formula in Section 3.1.

C3 · When does the client's lease clock start?

The paper's effective term is tc = ts − (mprop + 2mproc) − ε, using average message times that include "a normal level of retransmissions" (footnote 4). Section 5 claims leases stay consistent despite message loss. If a lease reply is delayed much longer than average, for example the request was retransmitted twice, is a client that starts its timer when the reply arrives and subtracts the average delay still safe? What should it do instead?

AnswerWork it out first, then open▾

Not safe. The server started the term when it processed the request. If the reply took longer than the average to arrive, a client that counts from arrival and subtracts only the average believes its lease ends later than the server does, and can read after the server has let a write through. That is exactly the failure leases claim to avoid.

The safe rule needs no delay estimate at all: start the timer when the client sent the request. The server cannot have granted the lease before it received the request, so the server's term started after the client's send time, and expiry = send time + ts (shrunk by the drift bound) is always conservative. With retransmissions, use the time of the first transmission, unless replies are matched to individual transmissions by an id.

So the formula in Section 3.1 is the right one for estimating performance (how much useful term is left on average), but the correctness argument needs the send-time rule, which the paper never states.

Where the answer comes from: Derived from Section 3.1, footnote 4 and Section 5. The send-time rule is standard in later lease implementations; the paper does not state it.

C4 · Longer leases for distant clients versus crash recovery

Section 2 says a recovering server can honor old leases by remembering the maximum term it granted and delaying all writes for that long. Section 4 says the server may give a distant client a longer term to make up for propagation delay. What has to be true about how the server stores that maximum for both features to work together?

AnswerWork it out first, then open▾

The maximum must be on stable storage, and it must be updated there before the server sends any lease longer than the recorded maximum. Otherwise: the server records a 10 s maximum, grants a 30 s lease to a distant client, crashes, reboots, waits only 10 s, and lets a write through while the distant client still has 20 s of valid lease. That is a consistency violation caused purely by the ordering of a disk write and a network send.

The cheap alternative is a fixed ceiling set by configuration, so the server never needs to write anything, at the cost of never issuing a term above it. Either way, the recovery wait should also include the clock allowance, since the old leases were measured on clients' clocks.

Where the answer comes from: Derived from the recovery rule in Section 2 and the per-client term option in Section 4. The write-ahead ordering is this guide's inference.

C5 · Does creating a file need approval from directory leaseholders?

Section 2 says the cache needs a lease over the name-to-file binding to support a repeated open, and that renaming is a write. If several clients hold leases on a build directory and one client creates a new file foo.o there, a name none of them ever looked up, does the server need their approval?

AnswerWork it out first, then open▾

Yes, if the lease covers the directory's contents. A client may have cached the result of a lookup that failed: "foo.o does not exist" is also data read from the directory, and make acts on it. Creating foo.o changes that answer, so it is a write to the directory, and so are create, remove, rename and link. Each one needs approval from every client holding a lease on the directory, or a wait for those leases to expire.

Consequence: a directory where several clients both read and create files (a shared build directory, a shared /tmp) produces constant callbacks, the false sharing the paper warns about. V avoids the worst of it by handling temporary files specially, which the paper mentions when explaining its low write rate. Per-name leases would avoid it at the cost of many more leases.

Where the answer comes from: Derived from Section 2 (leases over name bindings, rename is a write) and Section 3.2 (temporary files handled specially in V). The negative-lookup argument is this guide's inference.

C6 · What would turn NFS's attribute cache into a lease?

NFS clients trust cached attributes for 3 s (files) or 30 s (directories), which looks like a short lease, but the Leases paper says NFS does not guarantee consistency. What exactly is missing, and what is the smallest change that would make NFS consistent while keeping the server's state soft?

AnswerWork it out first, then open▾

What is missing: the NFS server never delays a write. A client may use attributes or blocks for up to 3 s after another client changed the file. That is a hint with a time-to-live, like the Domain Name System example in Section 6, not a lease.

Smallest change: (1) the server remembers, per file, the last time it sent that file's attributes to any client other than the writer (soft state, losable); (2) it defers any modifying call until 3 s (30 s for directories) after that time, with no callbacks, which is exactly the paper's installed-file policy of waiting for expiry; (3) after a reboot it delays all modifications for 30 s, the recovery rule from Section 2; (4) clients must write through instead of holding dirty blocks until close (M13 in the NFS guide), because a lease only protects what is on the server.

Cost: every write to a file someone read in the last 3 s waits up to 3 s. That is why the paper argues for approval messages as well as expiry: they let a write proceed as soon as the readers say yes.

Where the answer comes from: Derived from Section 6 (NFS and DNS), Section 2 and Section 4. The four-step construction is this guide's inference.

C7 · Is ε (clock synchronization) ever really needed?

Section 5 says the minimum requirement is bounded clock drift, with the term sent as a duration, yet the formula subtracts ε for synchronization. With the send-time rule, drift is enough for leases a client asks for. Is there any lease in the paper where a duration is not enough?

AnswerWork it out first, then open▾

Yes: the multicast extensions for installed files (Section 4). Nobody asked for them, so there is no client send time to count from. If the client counts the duration from when the multicast arrives, a delayed multicast makes the client's lease end later than the server's, which is the unsafe direction. The client needs either a known bound on delivery delay to subtract, or an absolute expiry time in the message together with clocks synchronized within ε.

So for leases a client requests, bounded drift suffices; for leases the server pushes, the protocol needs a delay bound or synchronized clocks. The paper treats ε as one allowance for both cases.

Where the answer comes from: Derived from Section 5 (drift versus synchronization) and Section 4 (unsolicited multicast extensions). The distinction between requested and pushed leases is this guide's inference.

Glossary and further reading

Core terms
LeaseA time-limited contract from a server to one client: during the term, the server must obtain the holder's approval before the covered datum may be written.
Lease term ts / effective term tcts is the length of a lease as granted and enforced on the server's clock. tc, the effective term, is the part the client can use after subtracting delivery time and a clock allowance: tc = max(0, ts − (mprop + 2mproc) − ε).
ApprovalA leaseholder's reply consenting to a pending write; giving it invalidates the holder's cached copy. The writer's request carries its own approval.
False sharing (lease sense)A lease conflict without a real access conflict: the write must call back, or wait for, a holder that is not currently using the file.
Installed filesFiles that come with the standard system (commands, header files, libraries): widely shared, heavily read, rarely written. Covered by a few leases that the server extends by periodic multicast.
Lease benefit factor αA number from the analytic model measuring how much reading outweighs write-sharing: α = 2R/(SW) with multicast, R/((S − 1)W) with unicast. A non-zero term reduces load only if α > 1 and tc > 1/(R(α − 1)).
taThe time for the server to gain approval for a write: 2mprop + (S + 2)mproc for S > 1.
Non-Byzantine failureA failure in which a component stops or loses messages but does not behave arbitrarily: a crash, message loss, a partition. Clock failure counts as Byzantine here.
Supporting terms
Write-through cacheA cache that sends every write to the server at once instead of holding modified data locally, so no write made visible to a client can be lost.
MulticastSending one message that the network delivers to a whole group of hosts. With it, gaining approval costs S messages instead of 2(S − 1).
V systemA distributed operating system built by Cheriton's group at Stanford, run on diskless MicroVAX II workstations over Ethernet. Its file-access trace supplies Table 2.
Andrew File SystemA distributed file system from CMU. Its prototype checked with the server on every open (a zero term); the revised version caches indefinitely, relying on server notification plus ten-minute polling (effectively an infinite term).
Poisson processA random arrival process in which events occur independently at a constant average rate (memoryless). The model assumes reads and writes arrive this way; real access is burstier.
mprop, mprocmprop is the time a message spends crossing the network; mproc is the time a host spends sending or receiving one message, counting only the part on the critical path.
Soft stateInformation a server keeps that expires or can be discarded on its own, so a crash needs no reconstruction, only a wait.
