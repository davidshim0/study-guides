ISCA 2025 · A Field Guide

Placing every byte where the wires already are, not where a heuristic guessed

Processing-in-memory accelerators compute inside DRAM — but only if the data is laid out exactly right first. This is the plain-English story of OptiPIM, a solver that finds that layout instead of guessing it.

📄 "OptiPIM: Optimizing PIM Acceleration Using ILP" · Liu, Zhou et al. 🎓 ILP and loop-tiling basics assumed — the primers cover the PIM-specific parts ⏱ ~25 min read
🧮

Model the exact cost of every legal data layout and schedule, then let an ILP solver pick the cheapest one — not a hand-tuned heuristic's guess.
On PIM, the layout is the mapping — you can't separate them.

Before you begin

Quick glossary, then eight ideas the paper assumes you know

You already know caches, tiling, and ILP in the abstract. What's new here is what PIM does to the mapping problem. Skim the glossary, then open whichever primer looks unfamiliar.

Quick glossary

PuMProcessing-using-Memory — bit-serial compute done directly with DRAM cell operations (e.g. SIMDRAM).
NBPNear-Bank Processing — an ALU/SIMD unit sits next to each DRAM bank (e.g. HBM-PIM).

PUPIM Unit — OptiPIM's generic name for one bank/subarray-level compute+storage block.

1Why PIM makes "mapping" a layout problem, not just a scheduling one▾

On a normal accelerator, a mapper decides when and where to compute, but the memory system can fetch almost any address on demand — data layout is somebody else's problem. PIM breaks that separation: to compute on data inside a bank or row, that data must already sit in the exact columns/rows the compute unit reads. There's no "just fetch it" fallback.

Now you're ready: every mapping decision (tile sizes, loop order, which loop becomes parallel) simultaneously decides a physical data layout, and that layout has its own cost.
2Two flavors of PIM: PuM (bit-serial) vs NBP (near-bank)▾

SIMDRAM (PuM) computes by activating multiple DRAM rows at once, which implements a logic gate (e.g. majority) on whole rows in parallel — but only bit-serially: adding two P-bit numbers takes O(P) such row operations, multiplying takes O(P²). HBM-PIM (NBP) instead reads a DRAM row into normal SIMD floating-point units sitting next to the bank — one op per SIMD-width chunk, no bit-serial overhead.

Now you're ready: the same mapping can be great on one architecture and terrible on the other, because compute cost and layout cost trade off completely differently on each — OptiPIM has to model both.
3The three loop levels: PU, column, computation▾

OptiPIM forces every mapping into exactly three nested regions: level 2 (spatial, across PIM Units / banks), level 1 (spatial, across columns within one PU), and level 0 (temporal, the sequence of ops within one column). This isn't a stylistic choice — it mirrors what's actually spatial (parallel hardware) vs temporal (time-multiplexed) in a bank.

Now you're ready: "picking a mapping" = picking how much of each original loop's iteration count goes into each of these three levels — a set of small integer choices, which is exactly what an ILP wants.
4Why loop bounds are restricted to divisors▾

If an original loop runs 8 times, OptiPIM assumes it's split perfectly into three tiled levels whose sizes multiply back to 8 (e.g. 2×2×2, or 1×4×2). So each tiled bound can only be a divisor of the original loop bound — a small, enumerable set, not an arbitrary integer.

Now you're ready: this is what keeps the ILP's variable count small — instead of searching all integers, you're one-hot-picking from a short divisor list per loop, per level.
5Data indexing is itself a design choice ("comprehensive indexing")▾

Prior mapping tools assume the address of a tiled loop variable is always innermost + level1·L0 + level2·L0·L1 (stride-1). OptiPIM notices that's just one of several valid, bijective ways to combine three tile indices into one linear address — and enumerates all of them, since a different indexing choice changes how data physically lands in memory.

Now you're ready: Section 4.3's whole point is that only 6 combinations are ever valid for 3 loop levels — so this extra design freedom is nearly free to add to the ILP.
6Three costs, one objective: compute, input load, output gather▾

Every PIM mapping pays for three things: the actual arithmetic (compute), moving non-stationary operands into place (input loading), and pulling results back out to the host (output gathering). OptiPIM's ILP objective is simply their sum — but each term depends on the layout in a different, non-obvious way.

Now you're ready: the paper's central complaint about prior tools is that they estimate these layout-dependent costs sloppily (upper bounds via loop-bound products), and get them wrong by over 70% for most sampling points.
7What "solving the ILP" buys you here▾

Because loop bounds are restricted to divisors and indexing to 6 combinations, the number of decision variables per operator stays small even though the space of possible mappings is astronomically large. An ILP solver (Gurobi) can then search that structured space to a provable optimum — not "a good mapping," the best one under the model — in seconds to a few minutes.

Now you're ready: "optimal" in this paper means optimal with respect to OptiPIM's cost model, verified against exhaustive search and against a cycle-accurate simulator (Ramulator2).
8How the pipeline actually runs

A PyTorch model is lowered through Torch-MLIR to the Linalg dialect (ordinary nested affine loops), each operator is handed to the ILP pass, and the resulting mapping is turned into concrete memory-allocation + instruction traces for either HBM-PIM or SIMDRAM by a codegen pass.

Now you're ready: OptiPIM is a compile-time, per-operator (and per-network) optimizer — it needs static shapes, the same limitation most ML compilers share for kernel-level optimization.
The whole story in one place

OptiPIM in a nutshell

The problem, the fix, and how the pieces click together.

PIM accelerators promise speed by computing where the data already lives — but that only works if the data was placed exactly right beforehand. Existing tools either reuse ASIC-accelerator mapping frameworks (which never model the memory-internal layout PIM enforces) or fall back to hand-tuned heuristics and exhaustive/random search — leaving performance on the table or costing hours per operator.

OptiPIM fixes both problems at once. First, it introduces a layout-aware nested-loop representation: every mapping is forced into three levels (PU allocation, column allocation, computation scheduling) that mirror real PIM hardware, plus a comprehensive indexing scheme that considers all 6 valid ways to combine tile indices into a memory address — not just the conventional stride-1 one. Second, it adds an accurate cost model for the number of rows/columns each tensor actually needs (Eq. 11), replacing prior tools' loop-bound-product estimate that overshoots by over 70% for most sampling points with one that's off by only ~3.2%. Both are folded into a single Integer Linear Programming problem whose objective is total cost (compute + input loading + output gathering); Gurobi solves it to the exact optimum in under 4 minutes per operator.

The payoff: mappings OptiPIM generates are roughly 1.9× faster than existing heuristic/search baselines across two real PIM accelerators (SIMDRAM and HBM-PIM) and several DNNs — this is the paper's headline figure; the lowest individual reported average is actually 1.8× (HBM-PIM vs. PIM-DL) — averaging 72.8× faster than a naive heuristic on HBM-PIM (and up to ~101× on individual layers such as ResNet-50's Conv12) — while the optimization itself finishes in seconds to a few minutes, versus ~2.7 hours for exhaustive search.

🍯 Key takeaways

  • PIM enforces data layout as part of computation — ASIC mapping tools (COSA/Timeloop) don't model that at all.
  • OptiPIM's representation adds two things ASIC tools lack: layout-aware 3-level tiling and comprehensive (6-way) data indexing.
  • Its cost estimator for "how many unique elements does a tensor need" averages ~3.2% error, vs. prior tools' error, which often exceeds 70% for individual sampling points.
  • The whole mapping problem becomes one ILP: minimize compute + input-load + output-gather cost.
  • Solved to the exact optimum in ≤4 minutes/operator (1–209s typical), vs. ~2.7 hours for exhaustive search.
  • Result: ~1.9× faster mappings than heuristics/search — the paper's headline figure (individual averages range from 1.8× vs. PIM-DL to 72.8× vs. the heuristic, both on HBM-PIM).
  • Scales to multi-operator workloads and whole models (tested up to Llama-3 14B) via joint PU allocation across operators.
Six everyday pictures

How to think about OptiPIM

Each picture stands alone. Every card ends with an honest note about where it stops being true.

The core problem · Layout enforcement

Loading a truck you'll unload in one exact order

A normal warehouse can hand you any box off any shelf on request. A PIM bank is more like a delivery truck you pack once and then unload strictly in loading order — so where you put each box is the schedule. Pack it wrong (wrong tiling, wrong indexing) and you pay to re-shuffle later; ASIC-style mapping tools assume the warehouse model and never notice the truck.

Where it breaks: a real truck is one-dimensional; PIM layout is genuinely 2-D (rows × columns) with different access rules for reading vs writing — the analogy loses that texture.
The representation · 3 loop levels

Sorting mail into trucks, bins, then a delivery order

A postal depot sorts mail three ways: which truck it rides (parallel, across banks — level 2), which bin in that truck (parallel, across columns — level 1), and the order it's handed out at each stop (temporal, within a column — level 0). OptiPIM forces every mapping into exactly this three-level shape because it mirrors what's actually parallel hardware vs. time-multiplexed hardware inside a real PIM bank.

Where it breaks: real depots can improvise sort order per shipment; OptiPIM's levels are fixed in advance for the whole operator, not decided dynamically per data item.
Comprehensive indexing · 6 valid combos

Six legal ways to number houses on a block

You could number a street's houses low-to-high in walking order, or group them by side then house, or by block then side then house — several numbering schemes are all valid (every house gets a unique number, the range has no gaps), they're just different orders. OptiPIM's indexing choice is exactly this: 6 valid ways to combine three tile indices into one memory address, all bijective, all worth trying because each produces a different physical layout.

Where it breaks: house numbering is arbitrary convention with no performance cost; here each of the 6 choices genuinely changes how much data gets replicated and moved — it's not cosmetic.
The cost model · Eq. 11

Counting two carpools' riders without double-counting overlap

If carpool A has 4 riders and carpool B has 4 riders, guessing "8 total people" overcounts whoever rides in both. Prior mapping tools multiply loop-bound products the same way, overestimating a tensor's unique footprint by over 70% for most sampling points. OptiPIM instead reasons about the actual overlap structure of the indexing function (its GCD), landing within ~3.2% of the true count on average.

Where it breaks: carpool overlap is usually simple set intersection; the real formula (Eq. 11) is a number-theory bound on a linear combination's unique outputs — more subtle than plain overlap-counting, but the intuition (naive multiplication overcounts) still holds.
Why ILP, not search · Structured space

A puzzle with a small rulebook, not infinite pieces

Exhaustive search treats mapping like trying every possible jigsaw arrangement. But OptiPIM's rules — tile sizes must be divisors, indexing must be one of 6 combinations — mean there's really a short, enumerable rulebook per loop variable. An ILP solver doesn't try every arrangement; it reasons about the rulebook directly and proves which choice is best, the same way a Sudoku solver reasons about constraints instead of brute-forcing every 9×9 grid.

Where it breaks: Sudoku has one right answer; here "best" is a continuous cost trade-off the solver is minimizing, not a satisfiability check — closer to a puzzle with a price tag on every wrong move.
Scope · Static shapes

A tailored suit, not a stretchy one-size

A bespoke suit fits perfectly — for one exact set of measurements known in advance. OptiPIM's ILP needs the loop bounds fixed at compile time to enumerate divisors and index combinations, so it tailors an optimal mapping for one known operator shape. Feed it a shape it hasn't seen (a longer LLM decode sequence, say) and it needs to re-tailor, not stretch.

Where it breaks: a tailor can measure you once and be done; here re-optimizing per shape has a real one-time cost (seconds to minutes), which is why dynamic-shape workloads pre-optimize for a few representative shapes and pad, exactly like other ML compilers do.
The full explanation

How it actually works

Section by section, with the paper's own numbers rebuilt as visuals.

1 · The problem — layout is part of the answer

Figure 2 of the paper makes the point with a 1D convolution: 8 outputs, a 6-tap filter. Mapping 1 computes all 6 partial sums of one output per time step (weight-stationary, 8 time steps). Mapping 2 computes 8 partial sums per step, 2 per each of 4 outputs (2 fewer steps — 6 total) but replicates the filter across more SIMD lanes.

2 · The representation — three forced loop levels

Every OptiPIM mapping is a nested loop with exactly three regions: level 2 (spatial — PU/bank allocation), level 1 (spatial — column allocation within a PU), level 0 (temporal — computation order within a column). This isn't arbitrary structure — it's the minimum needed to describe what's physically parallel vs. sequential in a PIM bank, and it's what lets OptiPIM read off the resulting data layout directly from the loop bounds.

3 · Comprehensive indexing — six ways to place the same tile

For a loop variable split into 3 levels, the index is a linear function F(x2,x1,x0) = d·x2 + e·x1 + g·x0. Requiring F to be bijective onto the full original range turns out to allow exactly 6 coefficient combinations — proven by the paper via a linear-Diophantine-equation argument, and generalizing to l! combinations for l levels.

3 loop levels → 3! = 6 valid combinations. Each original loop variable picks one independently — a small multiplicative expansion of the design space, not an explosive one, which is why it fits cleanly into the ILP.

4 · Accurate cost modeling — Equation 11

The hardest number to estimate is how many unique elements of a tensor a linearly-indexed loop actually touches. Prior ASIC tools just multiply the relevant loop bounds — an upper bound that's usually a big overestimate. OptiPIM instead reasons about the overlap structure directly:

Num_col_input = min{ [a·(L_o,0 − 1) + b·(L_f,0 − 1)] / gcd(a,b) + 1 ,  L_o,0 · L_f,0 }
# a, b: indexing coefficients   L_o,0, L_f,0: level-0 loop bounds of o and f
⚠
The error, measured: across 1000 random samples, the naive product estimate (COSA's method) has errors exceeding 70% for most sampling points; Equation 11 averages only ~3.2% error. Below, a rough visual sense of the gap (bars are illustrative, not per-sample data):

5 · The ILP — variables, constraints, objective

Decision variables select, per loop variable: which divisor becomes each level's bound (one-hot over the divisor list), and which of the 6 index-coefficient combinations is used. Constraints keep the loop bounds' product equal to the original bound, cap the number of PUs and columns used, and cap how much fits in one column. The objective sums the three costs:

minimize  Obj = Cost_compute + Cost_output + Cost_input
# subject to: one divisor chosen per (variable, level)
#             one indexing combo chosen per variable
#             Π L_x,2 ≤ N_PU        (PUs available)
#             Π L_x,1 ≤ N_cols      (columns per PU)
#             Σ Num_col_v ≤ N_rows  (rows per column, per stored tensor v)
💡
Why this is tractable: because divisors and indexing combos are small enumerable sets, the number of binary variables per operator stays modest — Gurobi solves each operator's ILP in 1–209 seconds, versus ~9800 seconds (2.7 hours) for exhaustive search over the same space.

6 · Scaling up — multiple operators and memory capacity

For a whole network, OptiPIM extends the PU-count constraint to a sum across all operators sharing the accelerator, and minimizes total cost jointly — automatically deciding how many PUs each operator gets. Tested at 8GB/16GB/32GB memory capacities, OptiPIM's allocation beats an even 50/50-style split by 43.6% / 30.6% / 28.7% on SIMDRAM and 18.5% / 7.3% / 1.4% on HBM-PIM — the advantage shrinks as memory capacity grows and allocation stops being the bottleneck.

Worked examples

Four traces using the paper's own numbers — cost tradeoffs, the indexing estimator, a real per-layer case study, and the optimization runtime.

① Why "fewer time steps" doesn't automatically win

Mapping 1 needs 8 time steps, Mapping 2 needs 6 (paper §3.1, Figure 2). At P=16-bit precision, is Mapping 2 actually cheaper on HBM-PIM?

  1. Mapping 1 data movement: RFA read 1×6×16 bits = 96 bits = 12 B; RFB write 8×6×16 bits = 768 bits = 96 B; output read 8×1×16 bits = 128 bits = 16 B.
  2. Mapping 2 data movement: RFA read 3×8×16 bits = 384 bits = 48 B; RFB write 6×8×16 bits = 768 bits = 96 B; output read 2×4×16 bits = 128 bits = 16 B.
  3. Compare: RFB writes and output reads are identical (96 B, 16 B) in both mappings. The only difference is RFA reads: 48 B (Mapping 2) vs. 12 B (Mapping 1) — Mapping 2 pays 4× more there.
  4. Net effect: Mapping 2 trades 2 fewer time steps for a real, non-trivial jump in one specific cost term. Whether that's worth it depends on how "time step" and "byte moved" convert into cycles on this hardware — exactly the trade-off a single-metric heuristic can't see, but an ILP objective (which sums real costs) resolves automatically.
🍯
Insight: counting "steps saved" without pricing the layout it requires is precisely the mistake OptiPIM's cost model is built to avoid.

② Using Equation 11 — when does the naive estimate actually overshoot?

Section 5.3.3's own example: input indexed by a·o0 + b·f0 with a=4, b=1, L_o,0=2, L_f,0=2.

  1. Plug into Eq. 11: [4·(2−1) + 1·(2−1)] / gcd(4,1) + 1 = (4+1)/1 + 1 = 6; compare to the product cap 2×2 = 4.
  2. Take the min: min(6, 4) = 4 unique input elements — and since gcd(4,1)=1, the four values 4·o0+f0 for o0,f0∈{0,1} really are all distinct (0,1,4,5). No savings possible here; product estimate happens to be exact.
  3. Now try a=2, b=4 (gcd=2), L_o,0=3, L_f,0=3: first term = [2·2 + 4·2]/2 + 1 = 12/2 + 1 = 7; product cap = 9.
  4. Take the min: min(7, 9) = 7 — here the formula correctly predicts fewer than 9 unique elements, because a shared factor of 2 in the coefficients causes real index collisions the naive product would have missed.
💡
This is exactly the pattern behind the paper's ablation result: workloads whose indexing coefficients share a common factor (like UNet) see large accuracy gains from Eq. 11; workloads that don't (like VGG16) see almost none.

③ ResNet-50 Conv12 — reading a real cost breakdown

Paper Figure 12 gives exact costs for three mappings of the same layer on HBM-PIM. Why does OptiPIM win by ~101× over the heuristic but only ~2.1× separates the heuristic from ASIC?

  1. Totals: Heuristic = 3,784,704 + 49,536 + 14 = 3,834,254. ASIC = 1,806,336 + 936 + 3,136 = 1,810,408. OptiPIM = 18,432 + 13,248 + 6,272 = 37,952.
  2. Heuristic vs. ASIC: 3,834,254 / 1,810,408 ≈ 2.1× — ASIC's ILP found a smarter, less input-hungry filter distribution, but its input-loading term (1,806,336) is still 95× its own compute cost.
  3. ASIC vs. OptiPIM: 1,810,408 / 37,952 ≈ 47.7× — because ASIC's objective function never included layout-dependent input-loading cost as something to trade off against compute, it can't do better even though it does find the lowest possible compute cost (936 cycles) in the whole space.
  4. Heuristic vs. OptiPIM: 3,834,254 / 37,952 ≈ 101× for this specific layer — well above the paper's reported HBM-PIM average of 72.8×, since averages smooth over layers where the heuristic does relatively better.
🍯
Insight: minimizing one cost term perfectly (as ASIC does for compute) is worthless if a different, uncounted term dominates the total — the entire argument for modeling all three costs jointly.

④ How fast is "optimal," really?

OptiPIM's ILP takes 1–209 seconds per operator; exhaustive search over the same space takes ~9800 seconds (2.7 hours) on average.

  1. Best case: 9800 / 1 ≈ 9800× faster than exhaustive search.
  2. Worst case (209s): 9800 / 209 ≈ 46.9× faster — still under 3.5 minutes, consistent with the paper's headline "optimal mappings within 4 minutes."
  3. Why the range: operator size determines the divisor lists and indexing choices per loop variable, which sets the ILP's variable count — bigger, more-factorable loop bounds mean a larger (but still bounded) search.
  4. Takeaway: even the slowest per-operator solve is fast enough to sit in a normal compilation pipeline; exhaustive search is not.
💡
This is the practical argument for ILP over search: same guarantee of optimality (within the model), one to two orders of magnitude less wall-clock time.

Practice problems

Problem 1 · easy
A mapping variant needs fewer total time steps than another but the paper still calls it worse for HBM-PIM. What's the most likely reason?
Show answer
It pays much more for one of the layout-dependent costs — typically input loading — because achieving that parallelism required replicating or repacking data into a costlier layout. Time steps are only the computation term of a three-term objective; a mapping can win on compute and still lose overall.Misconception: that fewer scheduled steps always means a faster mapping. On PIM, the layout needed to get those fewer steps has its own price, which can dominate.
Problem 2 · medium
Compute Num_col_input via Equation 11 for a=3, b=6, L_o,0=4, L_f,0=2.
Show answer
gcd(3,6)=3. First term = [3·(4−1) + 6·(2−1)] / 3 + 1 = (9+6)/3 + 1 = 5 + 1 = 6. Product cap = 4×2 = 8. min(6,8) = 6 unique input elements — fewer than the naive product's 8, because the shared factor of 3 in the coefficients causes some index collisions.Misconception: that the product of loop bounds is always the right answer. It's only a safe upper bound; the real count depends on the coefficients' gcd, and can be meaningfully smaller.
Problem 3 · medium
COSA and Timeloop already use nested-loop representations and even ILP formulations for ASIC accelerators. Why can't OptiPIM just reuse them directly for PIM?
Show answer
Two independent reasons. First, their representation only describes computation scheduling across a memory hierarchy that can fetch arbitrary addresses — it has no notion of the fine-grained physical layout PIM enforces, and it only allows stride-1 indexing, ruling out most valid PIM layouts. Second, their cost model estimates data sizes via loop-bound products, which is fine for hierarchy-level buffering estimates but wrong (often by more than 70%) for the layout-dependent costs PIM cares about.Misconception: that "nested loop + ILP" is a generic recipe that transfers across accelerator classes. The representation and cost model both have to be rebuilt around what's actually enforced by the target hardware.
Problem 4 · hard
The space of all possible mappings for one operator is astronomically large, yet OptiPIM's ILP solves it in seconds. What two structural restrictions make this possible without giving up any of the design space that actually matters?
Show answer
(1) Loop bounds at each of the 3 levels are restricted to divisors of the original loop bound — a short, enumerable list per loop variable, encoded with a one-hot vector, instead of an arbitrary integer. (2) The data-indexing function per loop variable is restricted to exactly 6 valid (bijective) coefficient combinations, proven to be the complete set for 3 loop levels — not an arbitrary linear function. Together these turn an unbounded search into picking from small, fixed menus per loop variable — exactly the kind of discrete, bounded choice an ILP is built for, and neither restriction throws away a layout that could actually occur.Misconception: that ILP tractability here comes from approximating or restricting the design space in a lossy way. Both restrictions are proven complete (every valid tiling, every valid bijective indexing) — the space is described exactly, just compactly.
Problem 5 · medium
Using the Conv12 numbers (Heuristic ≈3.83M, ASIC ≈1.81M, OptiPIM ≈38K cycles), explain why ASIC — which by construction finds the lowest possible compute cost — still loses to OptiPIM by ~47.7×.
Show answer
ASIC's ILP objective only counts costs an ASIC-style memory hierarchy has: data accesses/transfers, not PIM-specific layout costs. So it happily accepts a mapping with the lowest compute cost (936 cycles) even though that mapping requires an input layout costing 1,806,336 cycles to load — a cost its objective never sees, so it never trades compute for it. OptiPIM's objective includes that term, so it accepts a slightly higher compute cost (13,248) in exchange for a much smaller input-loading cost (18,432), for a lower total.Misconception: that optimizing one cost term to its absolute minimum is always progress. It's only progress if that term is actually the bottleneck — here it isn't, and chasing it makes the real (uncounted) bottleneck worse.
Problem 6 · easy
OptiPIM's accurate cost estimator (Eq. 11) gives a 4.8–6.6× speedup on HBM-PIM for UNet, but only about 3.5× for VGG16 (and just ~2.5–4.4% on SIMDRAM for both). Why such a different payoff?
Show answer
It depends on how much of the total cost is layout-dependent in the first place, and on how much the indexing coefficients' overlap structure actually differs from the naive product estimate for that workload. On HBM-PIM, input-loading and output-gathering costs are a large fraction of total cost, so estimating them accurately (instead of overestimating by often more than 70%) can change the optimal mapping a lot — UNet's indexing coefficients happen to share common factors that Eq. 11 exploits, while VGG16's don't as much, so its gain is smaller (~3.5×). On SIMDRAM, in-memory bit-serial compute (O(P) to O(P²) AAP operations) dominates total cost for both, so even a much better layout-cost estimate barely moves the needle.Misconception: that a more accurate cost model always helps proportionally and identically across workloads. Its impact scales with how large the mismodeled cost is relative to the whole, and with how much overlap that workload's indexing actually has — negligible when either factor is small.
Problem 7 · hard
Why does OptiPIM require static, compile-time-known loop bounds, and what does that imply for a workload like LLM autoregressive decoding?
Show answer
The ILP's variables are built directly from the original loop bound's divisor list and from bijective indexing functions defined over a fixed range — both require knowing the loop bound before solving. Autoregressive decoding processes one token at a time with a KV-cache whose length changes every step, so there's no single fixed shape to optimize for ahead of time. OptiPIM's stated approach (like other ML compilers) is to pre-optimize for a handful of representative shapes and pad at runtime, rather than solve the ILP online for every new shape.Misconception: that an "optimal, compile-time" method is strictly better than a "flexible, runtime" one. It's optimal precisely because it assumes away the thing (shape variability) that runtime systems must handle — a genuine trade-off, not a strict improvement.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does OptiPIM optimize?▾
Given one tensor operator (e.g. a convolution or GEMM) expressed as a nested loop, OptiPIM picks the loop tiling across 3 hardware-aligned levels, the data-indexing scheme for each loop variable, and produces the resulting data layout and memory-operation trace for a target PIM accelerator — all chosen to minimize total cycles (compute + input loading + output gathering).
Q2What's the actual difference between SIMDRAM and HBM-PIM that OptiPIM has to account for?▾
SIMDRAM (PuM) computes bit-serially by activating multiple DRAM rows at once — cheap layout, expensive compute (O(P) to O(P²) AAP operations per op). HBM-PIM (NBP) reads a row into a near-bank SIMD unit — cheap-ish compute, but every operand must be pre-arranged into exact SIMD-width columns, making layout/data-movement cost dominate. The same mapping can be near-optimal on one and terrible on the other.
Q3Why can't existing ASIC accelerator mapping tools (Timeloop, COSA) just be pointed at PIM hardware?▾
Two gaps: their representation assumes arbitrary-address fetches are always possible (so it never models fine-grained in-memory layout) and only allows stride-1 indexing; and their cost model estimates data sizes via loop-bound products, which the paper measures as exceeding 70% error for most sampling points for PIM's layout-dependent costs. Both gaps had to be closed with a PIM-specific representation and cost model.
Q4What is "comprehensive indexing" and why only 6 combinations?▾
It's the observation that a tiled loop variable's memory address doesn't have to be computed the conventional stride-1 way (innermost-to-outermost) — any bijective linear combination of the tile indices that covers the full original range is valid. The paper proves there are exactly l! such combinations for l loop levels; with 3 levels, that's 3! = 6.
Q5How much better is OptiPIM's cost estimate than prior tools', and why does it matter?▾
Prior tools (e.g. COSA) overestimate a tensor's unique-element count by over 70% for most sampling points, using a simple loop-bound product. OptiPIM's Equation 11 accounts for index overlap via the coefficients' GCD and averages only ~3.2% error. It matters most on architectures like HBM-PIM where layout-dependent costs dominate — there the better estimate alone is worth a 4.8–6.6× speedup on UNet (less so on VGG16, about 3.5×).
Q6How fast is the optimization, and how was the cost model validated?▾
Each operator's ILP solves in 1–209 seconds on a consumer 16-core CPU (vs. ~2.7 hours for exhaustive search over the same space), and the paper's overall claim is "optimal mappings within 4 minutes" per operator. The analytical cost model was cross-checked against a cycle-accurate simulator (a modified Ramulator2) across 12,000 randomly generated valid mappings, with R² = 0.993 (HBM-PIM) and R² = 1.000 (SIMDRAM).
Q7How much faster are OptiPIM's mappings in practice?▾
Roughly 1.9× faster than existing heuristic/search baselines across both architectures — this is the paper's headline number, though it's a rounded floor: the lowest individual average is actually 1.8× (HBM-PIM vs. PIM-DL). Broken down: on SIMDRAM, 2.3× over the heuristic, 2.0× over PIM-DL's random search, 1.1× over ASIC-style ILP; on HBM-PIM, 72.8× over the heuristic, 1.8× over PIM-DL, 25.4× over ASIC-style ILP (all averages; individual layers can differ a lot, e.g. ~101× on ResNet-50's Conv12).
Q8Does OptiPIM actually find the true optimum, or just "a good" mapping?▾
Within its own cost model, yes — an ILP solver proves optimality, it doesn't just search heuristically. The paper additionally checks this against a parallelized exhaustive search over the same design space and confirms OptiPIM matches it, while taking far less wall-clock time.
Q9Can OptiPIM handle a whole network, not just one operator?▾
Yes — Section 5.6 extends the ILP with a shared PU-count constraint across all operators in a workload and minimizes their summed cost jointly, which is how the memory-capacity scalability experiments (8/16/32 GB) and the Llama-3 8B/14B prefill evaluations were run.
Q10Does OptiPIM support dynamic shapes, like LLM decoding?▾
Not directly — it's a static, compile-time optimizer requiring known loop bounds. The authors note it can adopt the same workaround mainstream ML compilers (TVM, TensorRT, XLA) use for dynamic shapes: pre-optimize for a set of representative shapes and pad operands at runtime. Their own evaluation focuses on the prefill phase, where shapes are fixed per request.
Q11How does this relate to OS-managed memory tiering or CXL work?▾
It's a related but distinct layer of the memory-system optimization stack. Tiering/CXL work decides where pages live across DRAM/NVM/CXL-attached capacity and moves them at OS or hardware granularity, mostly oblivious to what compute will touch them. OptiPIM instead decides, at compile time and for one accelerator, exactly how bytes must sit inside a bank so compute can happen there at all — a much finer-grained, computation-aware placement problem. Both wrestle with exposing internal parallelism/bandwidth to software, but tiering optimizes access latency/bandwidth for opaque data, while OptiPIM optimizes layout for computation that only works if the layout is exactly right.
Q12What's explicitly out of scope or left for future work?▾
Dynamic-shape workloads (as above), and analog crossbar-based PIM (the paper targets digital PuM/NBP, contrasting itself with tools like CiMLoop for analog PIM). The authors also note their multi-operator extension currently reasons about PU allocation across operators but assumes each operator's own internal mapping is otherwise independent.

Core terms
OptiPIMThe paper's framework: an ILP-based compiler pass that generates optimal data-layout + schedule mappings for tensor operators on PIM accelerators.
MappingA concrete choice of loop tiling, loop-level assignment (PU/column/computation), and data-indexing function for an operator on specific PIM hardware.
PIM / PuM / NBPProcessing-in-Memory (general); Processing-using-Memory (bit-serial, in-cell, e.g. SIMDRAM); Near-Bank Processing (SIMD logic beside each bank, e.g. HBM-PIM).
Layout enforcementPIM's requirement that operands already sit in the exact rows/columns the compute unit will read — the paper's central complication vs. ASIC accelerators.
Comprehensive indexingConsidering all 6 valid bijective linear functions mapping 3 tile indices to one memory address, instead of only the conventional stride-1 one.
Cost model (compute / input load / output gather)OptiPIM's three additive cost terms; the ILP objective is their sum.
ILP formulationBinary/integer decision variables selecting divisor-based loop bounds and indexing combinations, with linear constraints and a linear cost objective, solved by Gurobi.
Supporting terms
PU (PIM Unit)OptiPIM's generic term for one bank/subarray-level compute+storage component.
NBUNear-Bank Unit — HBM-PIM's SIMD floating-point block attached to a bank's data path.
AAPActivate-Activate-Precharge — the DRAM row sequence SIMDRAM uses to implement bit-serial logic.
Divisor vector D_xAll divisors of an original loop bound L_x, used to enumerate valid tiled bounds at each level via one-hot selection.
Auxiliary/analytical cost modelOptiPIM's closed-form cycle estimator, validated against cycle-accurate simulation (R²=0.993/1.000).
MLIR / Torch-MLIR / LinalgThe compiler infrastructure OptiPIM is built in — lowers PyTorch models to nested affine loops for the ILP pass.
Weight-parallel heuristicHBM-PIM's original hand-tuned mapping strategy — distributes stationary weights across SIMD lanes; the paper's weakest baseline.
COSA / ASIC-style mappingAn ILP mapping method built for conventional ASIC accelerators, adapted here without PIM-specific layout costs — the paper's strongest baseline.
PIM-DLA genetic-algorithm/random-search mapping method for PIM DNN inference — the paper's search-based baseline.
Ramulator2The cycle-accurate DRAM simulator (extended with PIM instructions) used to validate OptiPIM's analytical cost model.
