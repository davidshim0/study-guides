Slow memory is only a bargain if you do the arithmetic

CXL promises cheaper capacity, but cheaper-per-GB doesn't mean cheaper-per-job if the workload runs slower. This is the plain-English story of the break-even CXL cost model — the price at which tiering actually pays off.

📄 "To Tier, or Not?" · Poduval, Yadalam, Swift · DIMES '26 🎓 Some cost-accounting basics assumed — primers cover them ⏱ ~25 min read
⚖️

A tiered system is worth it only when the DRAM DOLLARS you removed exceed the DOLLARS WASTED by running slower — measured as a break-even price, not assumed as a discount.

Quick glossary

CXLCompute Express Link — PCIe-based interconnect used to attach extra memory ("Type-3" expanders) outside the CPU's native memory channels.
TPP / AutoNUMATransparent Page Placement — a Linux tiering policy (via NUMA balancing) that migrates hot pages to fast local DRAM and cold pages to slow CXL.
RSSResident Set Size — the memory footprint a workload actually touches (e.g. 78 GB for the graph benchmarks).
θ (theta)Normalized performance: tiered performance ÷ all-local-DRAM performance. θ=0.8 means 80% as fast.

fFraction of the workload's RSS placed on CXL memory.
cCPU cost relative to the reference system's total DRAM cost.
η (eta)Cost-effectiveness: useful work delivered per dollar spent on hardware.

1Why CXL memory exists▾

Memory-per-core is shrinking: core counts have grown via chiplets while DDR channels per socket have grown only modestly, and DRAM scaling has slowed while prices rise. CXL adds capacity over PCIe, sidestepping DDR pin limits, and can even reuse DIMMs from decommissioned servers.

Now you're ready: the paper isn't asking "does CXL work" — it's asking "when does it pay for itself."
2Tiering: TPP and AutoNUMA▾

A tiering policy watches which pages are accessed often ("hot") and migrates them to fast local DRAM, demoting cold pages to slow CXL. The paper runs real AutoNUMA-based TPP on a Linux kernel new enough for actual CXL hardware.

Now you're ready: the model is policy-independent — a better tiering policy just shifts each workload's measured performance curve, and the same break-even formula applies.
3RSS and the fast/slow split▾

A workload's RSS is split between local DRAM and CXL. The paper sweeps this split — e.g. 78 GB of graph-benchmark RSS placed anywhere from mostly-local to mostly-CXL — and measures performance at each point.

Now you're ready: "fraction of RSS in fast memory" is the x-axis of every chart in this paper.
4Cost-effectiveness (η)▾

η = useful work ÷ total resource cost (CPU + DRAM + CXL). It's a "value per dollar" score, not a raw speed score — a slower system can still win if it's proportionally much cheaper.

Now you're ready: everything downstream (χ) is just solving "what CXL price keeps η the same as an all-DRAM baseline."
5The break-even idea (χ)▾

Instead of assuming a CXL price (which isn't public), the paper solves backward: given a workload's measured slowdown, what's the most CXL could cost, relative to DRAM, and still match the all-local baseline's cost-effectiveness?

Now you're ready: χ>1 means great even at a premium; 0<χ<1 means CXL must be discounted; χ<0 means even free CXL loses.
63DS / dense DRAM and capacity scaling▾

Once a workload's memory need exceeds what standard DIMMs can provide per socket, scaling up requires denser 3DS DRAM, at ~1.5–2× the cost per bit. CXL offers a way to add capacity without paying that dense-DRAM premium.

Now you're ready: this "expansion" scenario is where the paper finds CXL's strongest economic case.
7The CPU:DRAM cost ratio (c)▾

c captures how much of total system cost is CPU vs. reference DRAM. When memory is a bigger share of total cost, replacing it with CXL saves more; when CPU dominates, the same slowdown wastes more expensive compute per dollar saved.

Now you're ready: c is why "more vCPUs" or "cheaper CPUs" can flip whether CXL is worthwhile for the exact same workload.
The whole story in one place

The break-even model in a nutshell

The disconnect, the formula that resolves it, and how the pieces fit together.

Most tiering research reports performance — hit rates, latency, throughput — but the reason operators deploy CXL in the first place is cost. That leaves a gap: does the cheaper capacity actually make the system cheaper to run, once you account for the slowdown from slower memory? Since CXL device pricing isn't public, the paper can't just plug in a price and compute savings.

Instead it derives the break-even CXL cost χ: the maximum price of CXL memory, relative to local DRAM, at which a tiered configuration matches the cost-effectiveness of an all-local-DRAM baseline. Starting from cost-effectiveness η = value ÷ cost, and setting η_tiered = η_ref, the algebra collapses to one formula in three measurable quantities:

χ = 1 − (1 + c)(1 − θ) / f
f = fraction of RSS on CXL · θ = normalized performance · c = CPU cost / reference DRAM cost

Every term is measurable without ever knowing a CXL price: f from the deployment, θ from running the real workload on real CXL hardware with AutoNUMA/TPP tiering, and c from published CPU and DRAM prices. Across five memory-intensive workloads, the paper finds break-even costs ranging from above local-DRAM cost (CXL wins even at a premium) down to below zero (even free CXL wouldn't help) — and shows that the popular 1:8 fast:slow ratio rarely lands in the good zone.

🍯 Key takeaways

  • Performance alone doesn't answer "is CXL worth it" — cost-effectiveness (η) does.
  • χ lets you evaluate CXL without knowing its price: solve for the price at which it breaks even.
  • χ > 1: cost-effective even priced like DRAM. 0 < χ < 1: needs a discount. χ < 0: not viable even free.
  • The strongest case for CXL is capacity expansion that avoids paying for dense 3DS DRAM — not blind replacement of DRAM at any ratio.
  • CPU cost matters: cheap CPUs relative to DRAM raise χ; expensive CPUs (or more vCPUs) lower it.
  • Common evaluation setups like a 1:8 fast:slow ratio are rarely the most cost-effective point and need very cheap CXL.
Six everyday pictures

How to think about break-even cost

Each stands alone. Every card ends with where the picture stops being true.

The core idea · χ

Trading in a car

A dealer offers a cheaper, slower car. You don't ask "is it cheaper" — you ask "how much longer will my commute take, and is that worth the savings?" χ is exactly that: the most the slower car could cost and still be a wash once you price in lost time.

Where it breaks: a commute has one clear cost of time; a datacenter workload's "cost of slowdown" depends on whether CPUs sit idle or keep billing regardless — captured by c, not the car analogy.
Cost-effectiveness · η

Miles per gallon

A car that's slower but sips fuel can still win a road trip's total cost, even though it loses a drag race. η = useful work ÷ dollars spent is the same idea applied to a server: raw speed isn't the metric, work-done-per-dollar is.

Where it breaks: MPG is fixed per car; η depends on the fast/slow memory mix you choose, so there's a whole curve of η values to search over, not one number.
The CPU term · c

A restaurant's cover charge

If a restaurant has a big flat cover charge, discounting the food barely moves your total bill. Likewise, when CPU cost (c) dominates a system's budget, saving on DRAM by using CXL barely moves total cost — and any slowdown wastes the expensive, fixed CPU spend.

Where it breaks: a cover charge is fixed regardless of how long you stay; CPU cost in the model interacts with runtime too, since a slowdown means paying for CPU-time longer, not just owning more CPUs.
Expansion · 3DS threshold

Upgrading apartment size

Need more space than a studio holds? The landlord doesn't charge proportionally — you jump to a pricier unit tier. Standard-DIMM local DRAM works like the studio; past its capacity, you're forced into costlier 3DS DIMMs. CXL is the storage unit down the street that lets you avoid the upgrade.

Where it breaks: a storage unit only holds boxes you rarely need; CXL capacity is still directly usable, active memory — closer to a second, slower-to-reach room than dead storage.
Pooling

A shared storage locker

Several neighbors each keep a small closet at home but share one big locker down the hall for overflow, paying only for their share. CXL memory pooling works similarly across servers — each node provisions less local DRAM and draws on a shared pool, which the paper notes can cut total memory needs by 7–9%.

Where it breaks: a storage locker has no access-time penalty; a pooled CXL device still adds latency versus local DRAM, so pooling saves cost but doesn't erase the performance side of the tradeoff.
Sensitivity · CPU:DRAM ratio

Shifting a household budget

If rent is cheap where you live, trimming your grocery bill barely dents total spending; if rent is expensive, the same grocery savings matter even less. Swap "rent" for CPU cost and "groceries" for DRAM cost: as CPU gets pricier relative to DRAM, CXL's memory savings shrink as a share of the bill.

Where it breaks: your rent doesn't get worse if your grocery trip takes longer; in the model, a slowdown wastes CPU-time directly, so the two costs interact rather than sitting side by side.
The full explanation

How the model actually works

From cost-effectiveness to the break-even formula, then the three deployment scenarios it's applied to.

1 · Total cost and cost-effectiveness

Total system cost sums CPU, local DRAM, and CXL costs (plus any other resources, held fixed here since the workloads fit in memory and don't stress storage/network). Cost-effectiveness is then:

η = V(P) / TotalCost
TotalCost = Σ(CPU_i · N_i) + Σ(Mem_j · N_j)

V(P) is useful work: total operations completed for fixed-work batch jobs (graph analytics, Silo, XSBench), or steady-state throughput for a rate-based service (FlexKVS).

2 · Deriving the break-even cost χ

Set η_tiered = η_ref and expand both costs. The reference system pays only CPU + full-footprint local DRAM; the tiered system pays CPU + reduced local DRAM + N_CXL at the unknown price χ·C_DRAM. Solving gives:

χ = 1 − (1 + c)(1 − θ) / f
f = N_CXL / RSS · θ = V(Perf_tiered)/V(Perf_ref) · c = C_CPU·N_CPU / (C_DRAM·RSS)
💡
Reading the formula: a bigger CXL fraction (f) amortizes the slowdown penalty over more replaced DRAM, pushing χ up. A bigger performance loss (lower θ) or a bigger CPU-cost share (c) pulls χ down.

3 · Three deployment scenarios

ScenarioWhat changesEffect on χ
ReplacementCXL substitutes for some local DRAM at same total capacityBaseline formula; often needs CXL below DRAM cost
ExpansionLocal DRAM would otherwise need costlier 3DS DIMMs above a capacity thresholdReference cost rises (1.5× above threshold), so χ improves
PoolingCXL capacity shared across servers, less local DRAM strandedLower effective CXL cost per node; ~7–9% total memory savings (Pond)

Compression (OCP's compressed CXL expanders) is modeled by dividing effective memory cost or usage by the compression ratio, but requires measuring performance with real compression overhead — not evaluated here for lack of hardware.

4 · Methodology

Measurements run on a single-socket AMD EPYC 9634 server: 128 GB local DRAM, 1 TB CXL memory, ~120 ns local vs ~250 ns CXL latency, 250 GB/s local read bandwidth vs 90 GB/s CXL (rising to ~115 GB/s with 1:1 read/write). AutoNUMA (numa_balancing=2, demotion_enabled=1) implements TPP-style tiering on Linux 7.0. Five workloads (Table 1) sweep 10–15 fast-memory configurations each, 8 threads by default (4 for the smaller Embedding-Reduction workload, to match memory-per-vCPU with the others).

Follow the numbers

Worked examples

The paper's own numeric example, then three extensions using its stated facts and ratios.

① The paper's worked example

80 GB RSS, 20 vCPU, $25 per vCPU ≈ $25/GB DRAM (1 vCPU costed as 1 GB DRAM here). Tiered: 60 GB CXL + 20 GB local, same 20 vCPU, achieving 80% of all-local performance.

  1. f = N_CXL / RSS = 60 / 80 = 0.75
  2. θ = 0.80 (measured performance ratio)
  3. c = C_CPU·N_CPU / (C_DRAM·RSS) = (25·20)/(25·80) = 0.25
  4. χ = 1 − (1.25)(0.20)/0.75 = 1 − 0.333 = 0.667
🍯
CXL is cost-effective here only if it costs at most 2/3 of local-DRAM price per GB — a real but not extreme discount requirement.

② How the CPU:DRAM ratio moves χ

The example above assumed 1 vCPU ≈ 1 GB DRAM cost. The paper's default model instead assumes 1 vCPU ≈ 2 GB DRAM cost (its AWS-derived ratio). Recompute c and χ for the same deployment.

  1. New CPU cost: 1 vCPU = 2 GB DRAM = $50. Total CPU cost = 20 × $50 = $1000.
  2. c = 1000 / (25·80) = 1000/2000 = 0.5 (up from 0.25).
  3. χ = 1 − (1.5)(0.20)/0.75 = 1 − 0.4 = 0.6 (down from 0.667).
💡
Same workload, same f and θ — just a pricier CPU relative to DRAM lowers χ. This is exactly the §4.4 trend: higher CPU:DRAM ratio ⇒ lower break-even cost.

③ Why Embedding Reduction needed fewer threads

ER's RSS is 22 GB — smaller than the other workloads (60–78 GB). The paper targeted 6–10 GB of memory per vCPU across workloads.

  1. At 8 threads: 22 GB / 8 = 2.75 GB/vCPU — well below the 6–10 GB target.
  2. At 4 threads: 22 GB / 4 = 5.5 GB/vCPU — much closer to parity with the other workloads.
  3. The paper reports χ was always ≤ 0 for ER at 8 threads — CXL never broke even, because memory was too small a share of total cost.
⚠
Low memory-per-core is exactly the regime where CXL is uneconomical — it's a corollary of the c term, not a special exception.

④ How the 3DS threshold pushes χ up

Reuse example ①'s numbers (f=0.75, θ=0.8, c=0.25) but suppose the reference all-local-DRAM baseline must use dense 3DS DRAM (1.5× cost) because its full 80 GB footprint exceeds the standard-DIMM threshold — while the tiered config's 20 GB local portion stays under the threshold and still costs 1×.

  1. Reference cost rises to c + 1.5 (in units of C_DRAM·RSS) = 0.25 + 1.5 = 1.75, instead of c + 1.
  2. Tiered cost is unchanged: c + (1−f) + χf = 0.25 + 0.25 + 0.75χ = 0.5 + 0.75χ.
  3. Set tiered cost = θ × reference cost: 0.5 + 0.75χ = 0.8 × 1.75 = 1.4.
  4. χ′ = (1.4 − 0.5) / 0.75 = 1.2 (up sharply from 0.667).
🍯
The jump is large, not small: once the all-local baseline is forced onto pricier dense DRAM, CXL only has to beat that 1.5× reference, not 1×. This is §4.3's strongest result — expansion is where the economic case for CXL is best, sometimes justifying a CXL price above local-DRAM cost.
Test yourself

Practice problems

Try before opening each answer. Every one names the misconception it checks.

Problem 1 · easy
A deployment has f=0.5, θ=0.9, c=1.0. Compute χ and interpret it.
Show answer
χ = 1 − (1+1)(1−0.9)/0.5 = 1 − (2×0.1)/0.5 = 1 − 0.4 = 0.6. CXL must cost at most 60% of local DRAM's price per GB to break even.Misconception: that a "good" χ must be close to 1 or higher. Any positive χ means CXL can be worthwhile — it just quantifies how much of a discount is required.
Problem 2 · easy
Two configurations have identical θ=0.85 and c=0.3, but one has f=0.2 and the other f=0.8. Which has the higher χ, and why?
Show answer
f=0.8: χ = 1−(1.3)(0.15)/0.8 = 1−0.244=0.756. f=0.2: χ=1−(1.3)(0.15)/0.2=1−0.975=0.025. The larger f (0.8) gives the much higher χ.Misconception: that using more CXL always hurts break-even cost because it usually hurts performance. Here θ is fixed — with the same slowdown, spreading it over a bigger DRAM replacement (larger f) amortizes the penalty better.
Problem 3 · medium
Explain, in terms of the formula, why break-even cost estimates get noisy and unreliable very close to the all-local-DRAM point (f near 0).
Show answer
f sits in the denominator: χ = 1 − (1+c)(1−θ)/f. As f→0, any nonzero (1−θ) is divided by a tiny number, so small measurement noise in θ produces huge swings in χ. The paper notes points near all-local are "less informative" for exactly this reason.Misconception: that break-even cost is equally trustworthy at every fast-memory ratio. It's only meaningful once a substantial amount of CXL is actually in use.
Problem 4 · medium
A workload shows χ = −0.3 at its measured configuration. What does this mean operationally, and what's the one thing that could still fix it?
Show answer
Even free CXL memory wouldn't offset the slowdown — the all-local-DRAM system is strictly more cost-effective at this configuration. The fix isn't pricing; it's the performance curve itself: a smaller f, a better tiering policy improving θ, or a different fast/slow split could move χ positive.Misconception: that a negative χ means "CXL needs an even bigger discount." Below zero, no discount (including free) helps — the only lever left is θ or f.
Problem 5 · hard
Why does the paper argue that raising vCPU count for a fixed workload can make CXL less attractive, even if it improves raw performance?
Show answer
More vCPUs raise C_CPU·N_CPU, increasing c. A higher c means (1+c) scales up the penalty term (1−θ)/f in the χ formula, so for the same performance loss, break-even cost drops. Memory becomes a smaller share of total cost, so DRAM savings from CXL matter less relative to the (now larger, fixed) CPU spend. This is exactly what happened with ER at 8 vs 4 threads.Misconception: that better raw performance is always good for the cost case. Raw speed and cost-effectiveness are different axes — more CPU can win on speed while losing on χ.
Problem 6 · medium
Why is memory pooling expected to raise per-node break-even cost compared to plain expansion at the same fast/slow ratio?
Show answer
In expansion, each node dedicates and pays for its own CXL capacity. In pooling, a node only provisions its share of a shared pool but can still draw a larger fraction when needed — lowering the realized CXL capacity (and cost) each node has to buy (Pond reports 7–9% total memory savings from this sharing). That's a change to the cost each node actually pays for CXL, not a mechanical bump to χ itself — χ is a solved break-even price, and translating pooling's benefit into it requires re-deriving the cost model around shared, pooled provisioning rather than per-node replacement/expansion.Misconception: that pooling helps by improving performance, or that it plugs directly into the base χ formula as a multiplier. It helps primarily by lowering what each node has to provision and pay for, which shifts the economic case only once the cost model accounts for shared provisioning.
Quick answers

Frequently asked questions

Nine questions newcomers ask most.

Q1What exactly does χ tell you?▾
The maximum price CXL memory could have, relative to local DRAM's price per GB, and still leave a tiered system just as cost-effective as an all-local-DRAM baseline for that specific workload and configuration.
Q2Why not just use published CXL prices?▾
CXL device pricing isn't publicly available and varies by vendor, volume, and time. Solving backward for the break-even price sidesteps that uncertainty entirely — you only need measurable performance and known CPU/DRAM prices.
Q3Does θ measure just latency, or something broader?▾
θ is whatever the workload's value metric V(P) captures — completion time for fixed-work batch jobs, or throughput for rate-based services like FlexKVS. It's not latency alone; it's "useful work delivered," normalized against the all-local baseline.
Q4Why can χ go negative?▾
When the performance penalty from using CXL outweighs any possible cost savings — even at zero CXL price — the formula produces a value below zero. It signals "don't tier this workload this way," not "tier it, but demand a discount."
Q5Why does the paper call the common 1:8 fast:slow ratio out specifically?▾
Many tiering papers evaluate at fixed, CXL-heavy ratios like 1:8 for convenience. The break-even analysis shows these configurations are rarely the most cost-effective point on a workload's curve and typically require very cheap CXL memory to be worthwhile.
Q6How is this different from Tang et al.'s CXL cost model?▾
Tang et al. fix a CXL:DRAM ratio and known device cost, then estimate how many CXL servers are needed to match non-CXL throughput. This paper instead treats CXL price as unknown and solves for the break-even value implied by measured performance — complementary, not competing.
Q7How does this differ from TierScape?▾
TierScape optimizes real-time data placement across compressed tiers subject to a TCO target — an online placement policy. This work is an offline cost-effectiveness analysis of whole-application tiering against an all-local baseline, at a different level of abstraction.
Q8Why does CPU cost matter for evaluating a memory technology?▾
Because cost-effectiveness is about total system cost, not memory cost alone. If CPU dominates the budget, a tiering-induced slowdown wastes expensive, already-paid-for compute while the DRAM savings barely register — the c term captures exactly this interaction.
Q9Why weren't pooling and compression evaluated experimentally?▾
The authors lacked hardware for CXL pooling and inline-compression memory expanders. Both are discussed as extensions to the cost model (a lower effective per-node CXL cost for pooling; a compression-ratio-scaled cost/usage term for compression) but not measured directly.
