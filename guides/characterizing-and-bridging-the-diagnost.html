Finding the mistake the verifier never named

A rejected eBPF program gets back a wall of register states and one terse error line. That line can point to nine different bugs. This is the plain-English story of bpfix, the tool that recovers what the log was already implicitly holding.

📄 Zheng, Ji, Tao et al. · "Characterizing and Bridging the Diagnostic Gap in eBPF Verifier Rejections" 🎓 Some eBPF/verifier basics assumed — the primers cover them ⏱ ~25 min read
🔍

Report the proof an instruction needed, and mark where it was won or lost — not just the line where it got rejected.

Before you begin

Acronyms first, then the concepts

A quick-reference glossary of the paper's shorthand, then eight primers on the ideas bpfix builds on. Primers are collapsed — open any, or read top to bottom the first time.

1What eBPF is, and why the kernel checks it first▾

eBPF lets a developer write a small program — for tracing, networking, or security — and load it directly into the running Linux kernel, instead of writing a kernel module. Because the code runs with kernel privilege, the kernel will not run it until a component called the verifier proves it cannot crash the system or read memory it shouldn't.

Now you're ready: everything in this paper happens at the moment the verifier says no — that's a "rejection," and it's the object of study.
2What the verifier actually does: simulate, then prove▾

The verifier walks the program's bytecode one instruction at a time, over every possible path, tracking what it can prove about the value in each register and stack slot — is it a pointer, and to what; is it a number, and in what range. At certain instructions (like a memory access), that value must satisfy a safety property — a proof — before the instruction is allowed.

Now you're ready: a "rejection" is simply the verifier reaching an instruction whose required proof does not hold, given what it has tracked so far.
3Anatomy of a rejection: two things come back▾

When the verifier rejects a program it returns a log with two parts: the recorded states it kept while checking each instruction (the per-instruction register/stack snapshot), and one verifier error message attached to the instruction that failed.

Now you're ready: the paper's central claim is about a gap between these two things — the message doesn't say what the states already show.
4Why the message can mislead: one symptom, many diseases▾

The verifier error message names the operation that failed (e.g., "invalid mem access 'scalar'") — but the same message fires for many unrelated source-level mistakes that all happen to end the same way. Reading the message tells you that something broke, not which of several possible bugs broke it.

Now you're ready: the empirical study (§2) measures exactly how often one message covers multiple distinct causes — the answer is "often."
5Four kinds of rejection, not just one▾

Not every rejection is a bug in the developer's logic. The paper sorts 235 real rejections into four categories by where the repair actually lands: source-level bug (fix the code), compiler artifact (fix a compiler flag, code was fine), environment (fix the kernel/program-type setup), and verifier (restructure around a verifier limit).

Now you're ready: bpfix reports which of these four a rejection is, not just "here's the error."
6Proof families — grouping what the verifier checks▾

Verifier checks repeat the same handful of safety claims over and over, just about different values: "this access stays inside a checked packet range," "this pointer still carries its original type," "this reference was released exactly once." bpfix groups these recurring claims into 18 proof families so it can recognize which claim a given rejected instruction needed.

Now you're ready: matching a message to a proof family is bpfix's second stage, "proof localization" (§3.2).
7Repairing with an LLM, judged by an independent oracle▾

To test whether a diagnostic actually helps, the paper gives a rejected program plus either the raw log or the bpfix diagnostic to a language model, and asks for a fix. An oracle — built independently of bpfix — then compiles, loads, and tests the candidate fix; only a fix that passes every check counts as a successful repair.

Now you're ready: bpfix is never graded on "does the explanation sound right" — only on whether it measurably raises repair success under a fixed, independent test.
8Tokens and context windows — why shorter can mean better▾

A language model's input is capped at some number of tokens (its context window); some raw verifier log prompts in this study were long enough to exceed that cap, causing the model call to fail before a repair was ever attempted. Every bpfix-diagnostic prompt, being far shorter, stayed under that cap — the paper reports zero model-call failures on the diagnostic in its evaluation, on top of the diagnostic being easier to act on.

Now you're ready: this is why the smallest model in the study (Qwen2.5 3B) repairs zero tasks from the raw log but several from the diagnostic (§5.2).
The whole story in one place

bpfix in a nutshell

The gap, the tool that closes it, and why it works.

A BPF verifier rejection returns a log with two parts — the per-instruction recorded states and a single verifier error message — but an empirical study of 235 real rejections shows the message doesn't determine the fix: the most frequent message alone (R# invalid mem access 'scalar') covers 28 cases spanning 9 distinct root causes. The states hold the missing piece, but only implicitly, as a trace of register values across instructions — recovering the cause from them is manual work that also requires knowing the verifier's own rules.

bpfix closes that gap by working from the log alone, in three stages: state reconstruction rebuilds the full per-instruction state by accumulating the deltas the log does record; proof localization matches the rejection to one of 18 recurring proof families and traces backward through the reconstructed states to the instruction where that proof broke; diagnostic generation turns the result into a Rust-style message naming the required proof and the source lines that established or lost it.

The payoff: giving three different language models the bpfix diagnostic instead of the raw log raises one-shot repair success by 11 to 21 percentage points across all of them, and on the primary model cuts total token use by at least 70.7% — all without touching the compiler or the kernel.

🍯 Key takeaways

  • 81% of real rejections (191/235) are genuine source-level bugs — but the other 19% need a compiler flag, environment fix, or verifier-aware restructuring, not a code change.
  • The verifier error message is not a diagnosis: 15 of 82 normalized message templates span more than one root cause, one spans nine.
  • bpfix never re-analyzes the program — it recovers the missing proof from the log the verifier already produced.
  • All three tested LLMs repair more tasks with the bpfix diagnostic than with the raw log, in both one-shot and retry settings.
  • The specific "help:" recommendation lines carry most of the measured gain (+12 percentage points) — the diagnosis alone, without a recommended fix, is a much weaker, statistically uncertain signal.
Six everyday pictures

How to think about bpfix

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core problem · Message vs. cause

One symptom, several diseases

"Fever" doesn't tell a doctor which of several illnesses you have — it narrows the search, nothing more. The verifier's message R# invalid mem access 'scalar' is the same: it fired for 28 real rejections that came from nine unrelated bugs. Reading the message only tells you that a proof failed, not which mistake caused it.

Where it breaks: a few messages are precise — "only read from bpf_array is supported" names the exact operation refused. The gap is a matter of degree, worst on the most common messages.
Stage 1 · State reconstruction

A flipbook missing most of its frames

The verifier's raw log only draws a full picture at a few frames — where it resumes a branch — and elsewhere shows only what changed. bpfix fills the flipbook in: start from a full frame, apply each recorded change in order, and you have every intermediate frame, not just the sparse ones the verifier kept.

Where it breaks: the accumulation restarts at every stack-frame change (a function call boundary), so the "flipbook" is really several shorter ones spliced together, not one continuous strip.
Stage 2 · Proof localization

Tracing a dropped baton backward

A relay race ends with no baton in hand — the runner who dropped it isn't necessarily the one standing at the finish line. bpfix does the same trace: it identifies the proof the finish-line instruction needed, then walks backward through the reconstructed states to the exact earlier instruction where that proof (the baton) was actually dropped — often several instructions before the rejection.

Where it breaks: sometimes the baton was never picked up at all — the proof was never established, not merely lost partway. bpfix reports that case separately.
Category · Compiler artifact vs. source bug

A correct sentence, mistranslated

A perfectly good sentence can come out garbled if the translator drops a word — the fault is the translation, not the original sentence. Some rejections work the same way: the source correctly bounds-checks a pointer, but the compiler's lowering merges two branches and loses the type the verifier tracks. bpfix flags this as a compiler artifact — fix the build, not the sentence.

Where it breaks: you can't always tell "mistranslation" from "bad sentence" just by looking at the rejection — the paper confirms the category using each rejection's actual upstream fix.
Stage 3 · What "help:" lines add

Coordinates vs. turn-by-turn directions

Knowing your GPS coordinates tells you where you are; it doesn't tell you which street to turn down. The ablation shows the same split: naming the lost proof and its source lines ("the diagnosis") helps uncertainly on its own, but adding the concrete help: recommendation — turn-by-turn directions to the fix — is what reliably moves repair success, by +12 percentage points.

Where it breaks: directions can be wrong turn-by-turn just as often as coordinates can be imprecise; the paper measures that recommendations help on average, not that any single one is guaranteed correct.
Evaluation design · The independent oracle

Blind grading

A fair exam grader doesn't know, or care, which tutor helped the student study — they just check whether the answer is right. The paper's oracle is built independently of bpfix: it compiles, loads, and tests every candidate fix, from either condition, the same way. bpfix's diagnostic is never directly scored — only whether it leads to more fixes that pass this blind check.

Where it breaks: the oracle's own checks (functional tests, log/source preservation checks) are themselves case-specific and hand-written — "independent" means independent of bpfix, not infallible.
The full explanation

How it actually works

From the raw rejection to a source-level diagnostic, stage by stage.

1 · What a rejection hands you

Take the running example from the paper: a program derives udph from either an IPv4 or IPv6 header and bounds-checks it against data_end at source line 267 — a textbook safe pattern. Yet the verifier rejects a later field read at line 270 with R5 invalid mem access 'scalar'. The recorded states already show R5 holding the scalar value 40 as early as instruction 34 — three instructions before the rejection at instruction 37 — but the message says nothing about where or why the pointer became a scalar.

🌱
This is a compiler artifact, not a source bug: the bound check at line 267 is correct, but the compiler's lowering merges the two branches into a single, type-losing value. The upstream fix changed a compiler flag, not the source logic — confirmed later in §4.2.

2 · Categorizing rejections and root causes

Across 235 reproduced real-world rejections, the paper sorts repairs into four categories by where the fix actually lands:

CategoryThe repair changesCases
Source-level bugthe program's source191
Compiler artifacta compiler flag, not the source18
Environmentthe kernel or program type14
Verifierthe program's structure12

The 191 source-level bugs further cluster into 12 root-cause categories — the three largest are unclamped scalars used as an offset/length (24 cases), corrupted or stale dynptr objects (23), and packet access missing a bound on some path (22).

3 · The pipeline: three stages, log only

bpfix never re-runs or re-analyzes the program — its input is exactly the log the verifier already returned.

4 · Proof localization and the 18 proof families

The verifier error message alone doesn't say which safety claim failed, so bpfix first matches it to one of 18 proof families — recurring kinds of claim, such as packet-bounds (an access stays inside a checked range) or pointer-provenance (a value keeps the pointer type the verifier tracks). The family gives the kind of proof; the recorded states around the rejection pin down the specific instance — in the running example, that R5 specifically had to remain a packet pointer at instruction 37. bpfix then follows that specific proof backward through the reconstructed trace until it finds the instruction where it no longer holds.

5 · Diagnostic generation, and what it changes about repair

The final stage assembles the diagnostic: the required proof, the source lines where it was established or lost, the rejection category, and — within the matched family — a finer pattern-specific recommendation (a help: line).

error[BPFIX-E006]: verifier-visible compiler lowering hides the required proof
= class: lowering_artifact
--> prog.c:270
= verifier[229]: R5 invalid mem access 'scalar'
= required proof: preserve a verifier-recognized pointer type at the
  operation that requires a pointer
help: Reacquire a verifier-tracked pointer before the rejected dereference.

Where this matters most in practice: comparing first-failure points for one-shot LLM repairs on Qwen3.6 27B, the diagnostic mainly reduces failures at verifier load and at case-specific preservation checks — the stages where a model most needs to know exactly which proof to re-establish.

Why locating where the proof broke still matters: a model told only "fix line 270" would aim at the dereference itself, three instructions too late; a model told "the pointer was lost between 31 and 34" at least knows where the trail runs cold. For this particular case, though, the developers' own upstream fix didn't edit the source at instruction 34 or anywhere nearby — it changed how the program was compiled, since the bug was a compiler lowering artifact, not a source-level mistake.
Follow the numbers, step by step

Worked examples

Four calculations, recomputed directly from the paper's tables.

① How concentrated is the diagnostic gap?

235 rejections carry 167 distinct verifier error messages, normalized into 82 templates. How narrow is the most common one?

  1. Most frequent template: R# invalid mem access 'scalar' — 28 cases, 9 distinct root-cause categories.
  2. Cases per cause = 28 ÷ 9 ≈ 3.1. Knowing this message narrows the true cause only to "one of about nine," not to a single diagnosis.
  3. Compare the next three: "invalid access to packet" = 26 ÷ 5 ≈ 5.2 cases/cause; "invalid access to map value" = 18 ÷ 4 = 4.5; "R# !read_ok" = 13 ÷ 4 = 3.25.
  4. 15 of 82 templates (≈18.3%) span more than one root cause — a minority of templates, but exactly the most frequent ones.
🍯
Insight: the gap is worst precisely where it's encountered most — the four most common messages together cover 85 of the 235 rejections (36%), and none of the four identifies a single cause.

② Recomputing the token savings (RQ2)

Table 5(a): one-shot, raw log uses ≥399,578 total tokens for 21 repairs; the bpfix diagnostic uses 117,159 tokens for 38 repairs. Two different efficiency numbers come out of this.

  1. Tokens per successful repair, raw log = 399,578 ÷ 21 ≈ 19,028 (matches the paper exactly).
  2. Tokens per successful repair, bpfix = 117,159 ÷ 38 ≈ 3,083.
  3. Per-repair reduction = (19,028 − 3,083) ÷ 19,028 ≈ 83.8% — this is the number that would answer "how much cheaper is each success," and it's a lower bound since the raw-log total is itself a lower bound (3 calls had no usage record).
  4. Total-token reduction (all calls, not just successes) = (399,578 − 117,159) ÷ 399,578 ≈ 70.7% — this is the number the paper reports and the abstract's "up to 71%" refers to.
💡
Both numbers tell the same story from different angles: the diagnostic is cheaper in total and, because it also succeeds more often, dramatically cheaper per success.

③ What the recommendation lines are worth (RQ3)

The ablation compares four inputs on the same 75 tasks, one-shot: source only (24 repairs), raw log tail (26), bpfix without help: lines (29), and the full diagnostic (38).

  1. Without-recommendations vs. raw log tail: 29/75 (38.7%) vs. 26/75 (34.7%) → a difference of 4.0 percentage points, 95% CI −4.2 to 12.1 — the interval crosses zero, so this gain alone is not statistically established.
  2. Full diagnostic vs. without-recommendations: 38/75 (50.7%) vs. 29/75 (38.7%) → a difference of 12.0 percentage points, 95% CI 3.3 to 20.2 — clearly away from zero.
  3. Token cost of adding recommendations: (125,303 − 113,974) ÷ 113,974 ≈ 9.9% more total tokens.
  4. Tokens per successful repair: without recommendations, 113,974 ÷ 29 ≈ 3,930; full diagnostic, 125,303 ÷ 38 ≈ 3,297. Reduction = (3,930 − 3,297) ÷ 3,930 ≈ 16.1% — fewer tokens per success despite the recommendation lines costing more tokens up front, because they also produce more successes.
🍯
Insight: localizing the lost proof (without recommendations) is a plausible but statistically uncertain help on its own; telling the model concretely what to do about it is the part with a clear, measured effect.

④ Checking Takeaway #1: how much of this is "just write better code"?

191 of 235 rejections are source-level bugs. How should that number be read?

  1. Source-level share = 191 ÷ 235 ≈ 81.3% — matches the paper's stated "81%."
  2. Remaining 44 rejections (18.7%) reject otherwise-correct source: 18 compiler artifacts, 14 environment issues, 12 verifier-structure issues.
  3. Within the 191, the top three of 12 root-cause categories — unclamped scalar as offset/length (24), corrupted/stale dynptr (23), packet access missing a bound (22) — together account for 69 ÷ 191 ≈ 36% of all source-level bugs.
💡
Most rejections do need a real code fix, but nearly a fifth of the time the "bug" isn't in the source at all — a diagnostic tool that only ever proposes source edits would misfire on those cases, which is why bpfix reports the category first.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
The message "invalid access to packet" appears in 26 rejections spanning 5 root-cause categories. A developer sees this message on a new rejection. What can they conclude about the fix from the message alone?
Show answer
Almost nothing specific — only that it's one of roughly five known kinds of packet-access mistake, not which one. On average each category accounts for about 26 ÷ 5 ≈ 5.2 of the 26 cases, so the message narrows the search space but doesn't name the cause. Recovering the actual cause requires reading the recorded states (or using a tool like bpfix that does it for you).Misconception: that the verifier error message is a description of the bug. It's a description of the failed operation, not the bug that caused it to fail.
Problem 2 · medium
A program correctly bounds-checks a pointer in its source, but after compilation the verifier still rejects a later access with "invalid mem access 'scalar'." Which of the four rejection categories fits, and what should the fix target?
Show answer
Compiler artifact. The source logic was already correct, so the repair should target the build (e.g., a compiler flag or attribute), not the source. This matches the Stack Overflow 53136145 case (Fig. 1 / Fig. 6(b)), where the developers' actual upstream fix changed how the program was compiled and left the source logic unchanged.Misconception: assuming every verifier rejection means the source has a bug. 18 of 235 rejections in the study were rejections of otherwise-correct source.
Problem 3 · easy
191 of 235 studied rejections were source-level bugs. What percentage is that, and what does the paper's Takeaway #1 say about fixing them?
Show answer
191 ÷ 235 ≈ 81.3% (the paper rounds to 81%). Takeaway #1 adds that most of these source-level bugs require knowledge of the eBPF verifier's own rules to fix — they generally aren't mistakes that other programming languages' compilers would catch or warn about, so general programming experience alone isn't enough.Misconception: that "source-level bug" means "an ordinary programming mistake." Many of these 12 root-cause categories (e.g., corrupted dynptr state, unpaired resource references) are specific to how the verifier tracks safety, not generic bugs.
Problem 4 · hard
Tools like PREVAIL re-verify a BPF program against their own abstract domain to prove it safe or find real bugs. Why doesn't bpfix work the same way?
Show answer
bpfix's design insight is that the verifier's own log already implicitly holds the proof a rejected instruction needed — it doesn't need to re-simulate or re-analyze the program at all. It only reconstructs states, localizes the proof, and generates a diagnostic from the log the verifier already produced. This makes it cheap and log-only, but also means it can only report what the verifier's own analysis captured — it doesn't independently re-check the program's safety the way an offline re-prover does.Misconception: that recovering a root cause from a rejection requires a second, independent safety analysis. bpfix shows the existing log already contains enough information, if read correctly.
Problem 5 · medium
One-shot, raw-log repairs cost the model ≥19,028 tokens per success; bpfix-diagnostic repairs cost ≈3,083 tokens per success. Roughly how many bpfix-based repair attempts fit in the token budget of one raw-log-based repair?
Show answer
19,028 ÷ 3,083 ≈ 6.2 — about six bpfix-diagnostic repairs for the token cost of a single raw-log repair. This lower bound likely understates the true ratio, since the raw-log total is itself a lower bound (some calls exceeded the context window and returned no usable output at all).Misconception: that a more detailed diagnostic must cost more tokens than a raw log. The diagnostic is shorter than the full log and succeeds more often — it wins on both axes.
Problem 6 · hard
The ablation shows "bpfix without recommendations" beats "raw log tail" by only 4.0 percentage points with a confidence interval crossing zero, while "full bpfix" beats "without recommendations" by 12.0 points with an interval clearly away from zero. What does this combination actually establish?
Show answer
On these 75 tasks, simply restructuring the log into a localized diagnosis (without a recommended fix) shows an uncertain, not-yet-established benefit over a same-length raw log excerpt. The benefit that is clearly established comes specifically from adding the prescriptive help: lines. In other words: localization alone might help a little, but the paper's data can only confidently credit the actionable recommendation with improving repair.Misconception: that "diagnosis" and "recommendation" contribute equally, or that a structured diagnostic automatically beats raw text of the same length. Here, specifically the actionable part carries the measured effect.
Problem 7 · easy
A BPF program is correctly written and compiled, but rejected because it calls a helper function not supported by its program type. Which of the four rejection categories is this, and why not "source-level bug"?
Show answer
Environment. The source and the compiled bytecode are both fine; the mismatch is between the program's declared type/attach point and the kernel's rules about what that type is allowed to call. The repair changes the program's type or its runtime setup, not its logic — so it falls outside the "source-level bug" category even though the fix still touches a `.c` file's attributes.Misconception: that any fix touching program code must be a "source-level bug." The category is defined by what changes to resolve the rejection, not by which file the change happens to live in.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly does a verifier rejection's "log" contain?▾
Two parts: the recorded states — a per-instruction snapshot of what the verifier could prove about each register and stack slot while checking — and one verifier error message attached to the specific instruction that failed. The message is the only part written for a human to read directly; the states are a raw trace.
Q2Why doesn't the verifier just report the root cause itself?▾
The verifier's job is to decide, instruction by instruction, whether a required safety property holds right now — it isn't designed to explain why an earlier instruction set up a bad value, only to stop when a check fails. Reconstructing "why" from its own bookkeeping is exactly the gap bpfix fills.
Q3What is a "proof" in this paper's vocabulary?▾
A safety property a specific instruction requires before it's allowed to execute — for example, "this value must still be a verifier-tracked pointer" before a dereference, or "this offset must be within a checked packet range" before a packet access. A proof "holds" when the verifier can confirm the property from what it has tracked; it's "lost" at the instruction where that confirmation stops being true.
Q4How does bpfix know which proof a rejected instruction needed, if the verifier never says so?▾
It matches the verifier error message and the recorded states around the rejection to one of 18 predefined proof families — recurring kinds of safety claim the verifier makes across many programs. The family gives the kind of proof required; the specific register/value in the log gives the exact instance.
Q5Does bpfix change the compiler or the kernel verifier?▾
No. It's a userspace command-line tool that reads the verifier's log after a rejection and produces a diagnostic — nothing about how the program is compiled or how the kernel verifies it changes.
Q6Why does the bpfix diagnostic use fewer tokens than the raw log, if it adds explanation on top?▾
The raw log isn't actually a full state dump at every instruction — at the verifier's log_level=2, a complete snapshot is only printed at a few points (like resuming a branch); elsewhere it shows just the values one instruction used. Even so, accumulated across every instruction on every simulated path, it's still long. The diagnostic instead keeps only the required proof, the handful of source lines where it was established or lost, and a short recommendation — a small, targeted summary rather than the raw trace.
Q7How do we know bpfix's reported root cause is actually correct?▾
Two different checks, for two different claims. Whether the diagnosis is correct is checked directly, by hand: case studies compare bpfix's stated proof and proof-loss location against the developers' own real fix on public issues, and it matches. Whether the diagnosis helps produce a working repair is checked separately, at scale: giving it to three independent language models and judging their fixes with an oracle bpfix had no part in building shows consistently higher repair success than the raw log. That second result is evidence the diagnostic is useful, not direct evidence its stated root cause is correct — the oracle only tests whether a candidate patch works, not whether bpfix's explanation of the cause was accurate.
Q8How is bpfix different from Pretty Verifier or the BPF Verifier Visualizer?▾
Pretty Verifier maps the verifier's own error message to a source line and a canned hint via pattern matching; the Verifier Visualizer renders the recorded states in a debugger-like interface for a human to read. Neither derives the root cause — a human still has to interpret the states or the message. bpfix's novelty is stating the required proof and the source lines where it broke, automatically.
Q9Why do the "help:" recommendation lines matter so much if the diagnosis already names the lost proof?▾
The ablation shows the diagnosis alone (without recommendations) produces an uncertain benefit over an equally long raw log excerpt, while adding the concrete recommended action produces a clear, statistically supported +12 percentage point gain. Apparently naming a cause and suggesting what to do about it are different kinds of help for a repair-writing model, and the second one is what the data can confidently credit.
Q10I work on OS memory tiering / CXL — why would this paper matter to me?▾
Many memory-tiering and CXL monitoring tools attach eBPF programs to kernel memory-management hot paths — kprobes on page-fault or reclaim functions, tracepoints around NUMA balancing, or custom hot/cold page trackers alongside things like DAMON. Any of that instrumentation can get rejected by the verifier over exactly the kinds of pointer- and stack-state proofs this paper studies (e.g., pointer-provenance loss, missing bounds on a traced buffer). A tool that shortens that same debug loop is directly useful the next time a tracing probe on the mm path won't load.
