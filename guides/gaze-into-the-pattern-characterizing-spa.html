HPCA 2025 · A Field Guide

Judging a region by how it unfolds, not just where it starts

Two regions can be touched by the exact same instruction at the exact same offset — and still turn into completely different access patterns. This is the plain-English story of Gaze, a spatial prefetcher that waits one extra access to find out which pattern it's actually looking at.

📄 "Gaze into the Pattern" · Chen, Wu, Gu, Jia, Li, Guo (SJTU) 🎓 Cache/prefetching basics assumed — primers cover them ⏱ ~30 min read
👁️

Two regions that start the same way often finish differently — so match spatial patterns by the order their first few blocks arrive in, not by where they were triggered.

Before you begin

Quick glossary, then the primers

The acronyms first, so nothing in the primers is opaque. Then eight short cards covering everything the paper assumes you already know.

RegionA 4KB memory region (Gaze's default) — same size as a typical OS page. The unit a spatial pattern is defined over.
FootprintA bit vector over a region's 64 cache-line blocks: which blocks were touched during the region's lifetime.
Trigger / second offsetThe block offset of a region's 1st and 2nd distinct accesses — the only two data points Gaze waits for before predicting.
FT (Filter Table)Holds regions seen exactly once; promotes a region to AT on its 2nd distinct access.
AT (Accumulation Table)Tracks all currently-active regions' footprints (and last two strides) until they deactivate.
PHT (Pattern History Table)Learned footprints for "normal" (non-streaming) patterns, indexed by trigger offset, tagged by second offset.
DPCT / DC (Dense PC Table / Dense Counter)DPCT tracks which trigger instructions recently produced fully-dense (streaming) footprints; DC is a separate, single 3-bit counter tracking how often dense footprints have shown up recently overall.
PB (Prefetch Buffer)Staging area holding the prefetch pattern for a region before requests are actually issued.
1Hardware prefetching and the memory wall▾

Main-memory latency hasn't kept pace with CPU speed — the "memory wall." A prefetcher watches memory accesses, learns a pattern, and fetches data into cache before the CPU asks for it, hiding that latency.

Accuracy (fraction of prefetches that get used), coverage (fraction of misses caught), and timeliness (arriving before the demand) all trade off against each other and against hardware cost.

Now you're ready: Gaze is one such prefetcher, aimed at the L1 data cache, competing on all three axes at once.
2Spatial-pattern-based prefetching, at the granularity of a region▾

Instead of tracking individual addresses, this family of prefetchers watches memory in fixed-size chunks — regions (e.g. 4KB). A region's spatial footprint is a bit vector: which of its ~64 blocks got touched while it was "active."

The idea: when a new region activates, find a previously seen region that looks similar, and reuse its footprint as the prediction — prefetch the same blocks this new region is guessed to need.

Now you're ready: the entire paper is about how you decide two regions are "similar."
3The trigger access and environmental-context matching▾

The first access to a new region is the trigger access. Classic schemes characterize a region purely by the trigger's context: the instruction (PC) that issued it, its offset within the region, or both. If a new region's context matches a previously-learned one, its footprint is predicted to match too.

PC and offset are "environmental" — properties of where the access came from — not the actual behavior that follows.

Now you're ready: Gaze's whole critique is that this environmental context is a weak stand-in for the pattern itself.
4Fine-grained vs. coarse-grained characterization, and the cost trade-off▾

Fine-grained (PC + full address, e.g. Bingo, which pairs a long PC+Address table with a shorter PC+Offset fallback): very accurate, because the exact context rarely recurs by coincidence — but it needs a huge history table (>100KB) since every distinct context gets its own slot.

Coarse-grained (offset alone, e.g. PMP; or PC+Offset, e.g. SMS): cheap (a few KB), because there are only ~64 possible offsets — but many unrelated regions collide on the same offset, causing mispredictions.

Now you're ready: Figure 1's whole point is that this is a hard trade-off along one axis — context granularity — and Gaze wants to escape it on a different axis entirely.
5Temporal locality vs. temporal correlation▾

Temporal locality: data used recently is likely reused soon. Temporal correlation (as used here): a group of addresses tends to recur in the same order — access A predicts B predicts C, in that sequence.

The paper's insight is that this correlation property isn't just true of program behavior globally — it also shows up inside a single region's own footprint: the order blocks are touched in is itself a fingerprint.

Now you're ready: "footprint-internal temporal correlation" — the paper's core term — just means "the order of the first few accesses inside one region."
6Spatial streaming and over-prefetching▾

Spatial streaming: long runs of sequential, stride-1 accesses that eventually touch almost every block in a region — extremely dense footprints. Predicting "prefetch the whole region" for a genuine stream is great.

But if a non-streaming region's pattern gets misclassified as dense, you prefetch far too much — over-prefetching, which pollutes cache and wastes bandwidth.

Now you're ready: Gaze needs a separate, cautious mechanism just for telling real streams apart from lookalikes — that's its two-stage design.
7Accuracy, coverage, and timeliness — how prefetchers are scored▾

Accuracy = useful prefetches ÷ all prefetches issued. Coverage = LLC misses eliminated ÷ total LLC misses. Timeliness = fraction of prefetches that arrive so late the CPU access beats them anyway ("late" prefetches).

These pull against each other: being more selective (like Gaze's strict matching) tends to raise accuracy but can cost coverage or delay the first prefetch (hurting timeliness) — unless something else compensates.

Now you're ready: every result chart in this paper is really a three-way balancing act between these metrics, ultimately rolled up into IPC speedup.
8ChampSim and the evaluation setup▾

ChampSim is a trace-driven, cycle-accurate simulator used by several prefetching/replacement competitions. Traces are captured once from real hardware/software runs, then replayed deterministically against different prefetcher designs so comparisons are apples-to-apples.

The paper evaluates 201 traces across SPEC06, SPEC17, Ligra, PARSEC and CloudSuite, at 200M warmup + 200M simulated instructions per core.

Now you're ready: when a number is quoted as "average across the evaluation set," it's an average over these 201 diverse traces, not a cherry-picked benchmark.
The whole story in one place

Gaze in a nutshell

The problem with context-based matching, the fix, and how the pieces fit together.

Spatial-pattern-based prefetchers guess a new region's footprint by finding a previously-seen region that looks "similar," using environmental context — the triggering instruction (PC) and/or its offset. Fine-grained context (PC+Address, as in Bingo) is accurate but needs >100KB of history tables; coarse-grained context (Offset alone, as in PMP, or PC+Offset, as in SMS) is cheap but collides constantly on complex workloads, since context alone can't tell two very different access sequences apart when they merely started at the same place.

Gaze's fix: characterize a region by its footprint-internal temporal correlation — the order its first two accesses arrive in, not just where the first one landed. Waiting one extra access resolves ambiguity that trigger-only matching can never see, without the metadata explosion of tracking full addresses. This information is folded directly into the existing lookup (trigger offset as index, second offset as tag) — no new storage structure is needed, just a slightly delayed prediction.

A second, independent problem: footprints from genuine spatial streaming are extremely dense (almost the whole region), so misapplying one causes severe over-prefetching. Gaze adds a two-stage aggressiveness control — start conservative, then promote to full aggressiveness only once the region's own recent strides confirm it really is streaming.

The payoff: across 201 traces, Gaze beats PMP and vBerti by 5.7%/5.4% single-core and 11.4%/8.8% at eight cores, at 4.46KB of storage — 31× less than Bingo, cheaper than PMP, and only 1.91KB more than Berti.

🍯 Key takeaways

  • Environmental context (PC/Offset/PC+Address) is a proxy for "similar pattern" — it can be cheap or accurate, historically not both.
  • Gaze's proxy is different: the order of the first two accesses inside the region itself (footprint-internal temporal correlation).
  • Two accesses is the sweet spot — Figure 4's sensitivity study shows 1 is too coarse and ≥3 loses more coverage than it gains in accuracy.
  • Temporal info is folded into the existing index/tag lookup — zero extra metadata for the core idea.
  • A separate DPCT/DC/two-stage mechanism handles the special case of spatial streaming, whose footprints are too dense to trust from one match.
  • Total overhead: 4.46KB — 31× less than Bingo, 0.54KB less than PMP, 1.91KB more than Berti.
  • Result: +5.7%/+5.4% vs PMP/vBerti single-core; +11.4%/+8.8% at eight cores.
Six everyday pictures

How to think about Gaze

Each stands alone — read in any order. Every card ends with where the picture breaks.

The core problem · Trigger-only matching

Two strangers who start the same sentence

Both say "So..." Are they about to tell the same story? You genuinely can't tell yet — the first word is nowhere near enough. That's a trigger-only match (PC or Offset alone): two regions "matching" on their first access tells you almost nothing about what comes next.

Where it breaks: real conversations have infinite next words; a region only has ~64 possible next offsets, so even a coarse signal narrows things down somewhat — just not reliably enough for complex workloads.
The fix · Wait for the second access

Reading two words before guessing the plot

"So, yesterday..." already narrows things dramatically compared to "So..." alone — you don't need the whole paragraph to make a confident guess, just one more word. Gaze's whole innovation is exactly this: hold prediction back by exactly one access (trigger + second offset), which resolves most ambiguity for a small, bounded delay.

Where it breaks: more words keep helping in conversation, but for Gaze a 3rd or 4th word stops paying for itself — Figure 4 shows accuracy still climbs but IPC and coverage give back more than it gains.
Hardware cost · Fine vs. coarse context

Caller ID vs. the whole call transcript

Caller ID (offset alone, PMP-style — or caller ID plus a short code, SMS-style PC+Offset) is nearly free but tells you almost nothing about the call's content — lots of unrelated calls share a caller ID. A full transcript (PC+Address, Bingo-style) tells you everything, but storing every past transcript takes a warehouse (>100KB). Gaze's "first two words of the call" sits in between: tiny to store, almost as diagnostic as the transcript.

Where it breaks: Gaze doesn't fully match a full transcript's accuracy on every workload — it still trails vBerti's L1D accuracy by about 4.2% outside CloudSuite. Two words are excellent, not omniscient.
Over-prefetching · The streaming special case

Pacing a sprinter down a hallway

A genuine sprinter (spatial streaming) benefits from being waved all the way through — prefetch the whole region. But if you wave every fast-looking jogger through the whole hallway, most of them were never actually sprinting and you've cleared space for nobody. Gaze's two-stage control gives an initial modest head start (16 blocks) and only clears the rest of the hallway once two consecutive strides confirm the runner is truly sprinting.

Where it breaks: Gaze's pacing is decided per trigger-PC (via DPCT/DC) and per-region stride history, not a literal human judgment call — the "confirmation" is two matching strides of exactly 1, nothing more nuanced.
Strict matching · No partial credit

Two witnesses, not one

Bingo and TAGE-style predictors will act on a partial match — one witness is enough to open a case. Gaze insists on both the trigger and the second offset lining up before it acts, refusing to predict off half a story. It loses a few weak leads this way, but a dedicated backup — the region's own stride history in AT — quietly picks up cases the strict match rejects.

Where it breaks: real strict witnesses have no fallback; Gaze's fallback (stride-based backup prediction) only covers simple, single-stride patterns, not arbitrary irregular ones a partial-match scheme might still catch.
The reframe · Context vs. behavior

Reading the shipping label vs. watching the box get unpacked

Environmental context (PC, address) is the shipping label — where the package came from. Footprint-internal temporal correlation is watching the first two items come out of the box — what's actually inside, in what order. Gaze doesn't throw away the label (it still uses offsets as index/tag); it just adds a peek inside before committing.

Where it breaks: Gaze only "watches" two items unpack, not the whole box — it's a cheap peek, not full inspection, which is exactly the trade-off Figure 4 quantifies.
The full explanation

How it actually works

The access flow through Gaze's structures, then the streaming-specific two-stage control.

1 · The access flow — FT, AT, and PHM

Every load first checks the AT (Accumulation Table) — is this region already being tracked? If not, check the FT (Filter Table): has this region been touched exactly once before? If yes, promote it into AT — and critically, at this exact moment Gaze already has both the trigger offset and the second offset, so it immediately sends (trigger, second, PC) to the Pattern History Module for a prediction. Conventional schemes fire their prediction off the trigger alone, one access earlier.

2 · Pattern characterization — trigger as index, second as tag

Gaze doesn't add a new table for temporal information — it repurposes the lookup that was already there. The trigger offset indexes the PHT (as it always would); the second offset becomes the tag, verified on lookup. A hit means both offsets matched, in that order — a strict, two-access confirmation, at the storage cost of a plain offset-indexed scheme (no PC field needed at all).

💡
Why stop at two? The marginal accuracy from a 3rd or 4th access keeps climbing, but coverage and IPC both give back more than accuracy gains — you wait so long confirming the pattern that you miss the chance to prefetch it in time, or the region deactivates before you're sure. Two is the point where all three metrics are simultaneously favorable.

3 · The streaming special case — DPCT, DC, and two stages

A region whose first two accesses are exactly block 0 then block 1 is flagged as a candidate for spatial streaming. When such a region deactivates, Gaze checks: was every block in the region eventually touched (fully dense)? If so, its trigger PC is recorded in the DPCT, and a separate, single DC (Dense Counter, 3 bits) — not tied to any one PC, but tracking how often recent regions overall have come out fully dense — is incremented slowly (+1). If not, DC is decremented — fast (halved) if DC was already above 2, slow (−1) if DC was already low.

⚖️
Why asymmetric decay? A high DC means recent strong evidence that dense, streaming-like regions have been common; if the very next region to deactivate turns out not to be dense, that's a real signal the behavior may be changing, so DC should drop fast to stop the over-prefetching quickly. A low DC is already cautious, so there's no need to punish it hard — a slow −1 avoids flapping.

Stage 1, on a new candidate region p: if its trigger PC is a known dense PC or DC is fully saturated, prefetch the first 16 blocks (a quarter of the 64-block region) into L1D and the rest into L2C. If DC is only half-saturated (>2 but not full), prefetch just the first 16 blocks into L2C — more cautious. If neither condition holds, issue no speculative prefetch at all, but set a stride_flag on the region in AT.

Stage 2 then watches every flagged region's ongoing accesses. Once the last two strides both equal 1 (three consecutive sequential accesses), it promotes the next 4 blocks — skipping 2 — straight into L1D. This is the same mechanism that serves as the backup predictor when the strict trigger+second match in §2 fails to find anything.

4 · Hardware overhead

All of this — FT, AT, PHT, DPCT, PB combined — costs 4.46KB (Table I: 456B + 1128B + 2304B + 15B + 668B), each table accessible within a single CPU cycle. That's 31× less than Bingo's 138.6KB, 0.54KB less than PMP's 5.0KB, and only 1.91KB more than Berti's 2.55KB. The pattern-history module (PHT+DPCT) also uses about 29% of PMP's silicon area and under 46% of its access energy, largely because each Gaze entry stores only a 64-bit footprint versus PMP's 320-bit counter vector.

Follow the numbers, step by step

Worked examples

Four traces through the paper's own numbers: the access-count trade-off, the storage tally, the streaming state machine, and how the speedups stack up under contention.

① Why two accesses, arithmetically

The paper states: using the first two accesses gives "a 3% improvement in IPC and a 35% improvement in accuracy" over using the trigger alone, whose baseline accuracy is 56%. Check the arithmetic and see why four accesses overshoots.

  1. 1-access accuracy = 56% (given). A 35% relative improvement: 0.56 × 1.35 = 0.756 ≈ 75–76% at 2 accesses — matches the paper's stated jump exactly.
  2. IPC at 2 accesses is +3% over 1 access — small, because coverage barely moves ("negligible reduction").
  3. Push to 4 accesses: accuracy keeps rising, "from 56% to 90%" — a further ~19 points beyond the 2-access level.
  4. But the text is explicit that IPC and coverage decrease as you require more aligned accesses — each extra access you wait for is a chance the region deactivates, or the CPU catches up, before you've committed to a prediction.
  5. Net result: accuracy gains past 2 accesses are real but not free — they're paid for in coverage and timeliness, which is exactly why Gaze stops at 2.
🍯
Insight: "more temporal information is always better" is false here — the paper explicitly measured the crossover point and it's at exactly 2 accesses, not more.

② Tallying Gaze's hardware overhead

Table I lists five structures. Add them up and compare against the other three prefetchers named in the abstract.

  1. FT (8-way, 64 entries, tag+LRU+hashed PC+trigger offset) = 456 B.
  2. AT (8-way, 64 entries, tag+LRU+PC+stride flag+2 offsets+2 more offsets+64-bit bit vector) = 1128 B.
  3. PHT (4-way, 256 entries, 6b tag + 2b LRU + 64b bit vector) = 2304 B.
  4. DPCT (fully-assoc., 8 entries, 12b PC + 3b LRU) = 15 B. PB (8-way, 32 entries) = 668 B.
  5. Sum: 456 + 1128 + 2304 + 15 + 668 = 4571 B ≈ 4.46 KB.
  6. Vs. Bingo (138.6 KB): 141,926 B ÷ 4571 B ≈ 31×. Vs. PMP (5.0 KB): 5120 − 4571 = 549 B ≈ 0.54 KB less. Vs. Berti (2.55 KB): 4571 − 2611 = 1960 B ≈ 1.91 KB more.
💡
All three comparisons match the paper's own stated deltas exactly — the storage overhead isn't just "small," it's precisely between the cheapest (Berti) and next-cheapest (PMP) rivals, while covering both fine-grained and streaming behavior neither of those handles as well.

③ Tracing a BFS frontier region through the streaming state machine

Ligra's BFS_forward traverses Frontier (sparse, irregular) then each vertex's neighbors (often sequential, from an adjacency array). Trace a neighbor-list region through Gaze's two stages.

  1. Region opens at neighbor-array block 0, second access hits block 1 → trigger=0, second=1 → flagged as a spatial-streaming candidate, not sent to the normal PHT path.
  2. Check DPCT for this trigger PC, and DC overall. Suppose this exact load instruction is not yet a known dense PC in DPCT, and DC — the single, workload-wide counter of how often recent regions have come out fully dense — is only half-saturated (>2, not full).
  3. Stage 1 fires conservatively: prefetch blocks 0–15 (16 of 64, one-quarter of the region) into L2C only — not L1D — since confidence isn't yet high enough to commit L1D space.
  4. Meanwhile, region's stride_flag is set in AT. As real accesses continue at blocks 2, 3, 4 (strides = 1, 1), Stage 2's condition — last two strides both equal 1 — is met.
  5. Stage 2 promotes the next 4 blocks (skipping 2, i.e. roughly blocks 7–10) directly into L1D. If this region does turn out fully dense at deactivation, its trigger PC is added to DPCT and DC gets its slow +1 nudge, making the next streaming-candidate region overall more likely to earn the full Stage-1 L1D treatment.
🍯
Insight: confidence in "this is really streaming" is built gradually across two independent signals — a global one (DC, learned over many recent regions regardless of PC), a per-instruction one (DPCT, which specific trigger PCs have recently produced dense regions), and a within-region one (stride confirmation, Stage 2) — so a single unlucky guess never triggers full over-prefetching.

④ Why the speedup gap widens under contention

Gaze beats PMP and vBerti by 5.7%/5.4% at one core, but by 11.4%/8.8% at eight cores — the gap roughly doubles. Why?

  1. Accuracy compounds under bandwidth pressure. A useless prefetch doesn't just waste one request — at 8 cores, contending for shared DRAM bandwidth, it also delays every other core's real demands and prefetches queued behind it.
  2. PMP's flaw is exactly this: its coarse offset-only characterization gives lower accuracy, and "the over-aggressiveness of PMP leads to a extreme sharp decline when bandwidth or cache size decreases" — its errors get amplified, not just repeated, as cores scale up.
  3. vBerti's flaw is different: redundant prefetches (for blocks already resident) clog the prefetch queue; under contention this queuing cost is worse, since the PQ saturates more often.
  4. Gaze avoids both — its strict two-access match keeps accuracy high, and being spatial-pattern-based (region-aware) it naturally filters out already-serviced blocks the way vBerti's per-PC delta view cannot.
  5. Result: at 8-core homogeneous mixes, Gaze beats Bingo/PMP/vBerti by 3.1%/11.7%/9.0%; at 8-core heterogeneous mixes, by 9.4%/7.8% over PMP/vBerti.
💡
For these prefetchers on these workloads, single-core accuracy advantages understate the benefit once 8-core bandwidth contention is added — a dynamic worth checking for, though not something to assume automatically, when comparing single-node vs. multi-tenant numbers on other shared-resource systems.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Regions A, B, C and D are all triggered by reading block 0 of their region, from the same trigger PC. Under an Offset-only scheme (like PMP — no PC involved at all), how many of these regions can be told apart at the moment of the trigger access?
Show answer
None — all four look identical to a context-based matcher at trigger time, since they share the same trigger offset (and, in Figure 2's scenario, the same trigger PC too). Only after observing the second access can any of them be distinguished.Misconception: that a matching trigger already implies a matching pattern. It only implies a matching start — the pattern itself is still completely unknown.
Problem 2 · medium
A region is touched exactly once, then never touched again before being evicted. Does it ever reach the AT, the PHT, or contribute training data to Gaze?
Show answer
No. FT only promotes a region to AT after its second distinct access arrives; a region touched once and never again simply ages out of FT and is discarded. It never generates a footprint, never reaches PHM, and is invisible to Gaze's learning process.Misconception: that every memory access contributes to pattern learning. Single-touch regions are filtered out entirely — they carry no spatial pattern to learn from.
Problem 3 · medium
Figure 4 shows accuracy keeps climbing all the way to 90% at 4 accesses, yet Gaze uses only 2. Explain why "highest accuracy" isn't the right design target.
Show answer
Accuracy is one of three metrics (with coverage and timeliness) that ultimately roll up into IPC — and IPC, not accuracy, is what the system actually cares about. Waiting for 3–4 aligned accesses raises accuracy but costs coverage (some regions deactivate or the CPU catches up before enough accesses are seen) and IPC declines past the 2-access peak. Optimizing accuracy in isolation would trade away net performance.Misconception: that a higher accuracy number is always a better design point. It's only better if it doesn't cost more in coverage/timeliness than it gains — here it does, past 2 accesses.
Problem 4 · hard
Gaze uses strict matching (both trigger and second offset must match, unlike Bingo/TAGE's partial-match fallback), yet loses almost no coverage. What compensates?
Show answer
The region-based stride prefetcher built into AT (§III-C, Stage 2) serves double duty: besides ramping up streaming aggressiveness, it acts as a backup predictor exactly for the cases where the strict PHT match fails to find anything. When the PHT lookup misses, AT sets the region's stride_flag anyway, so a simple constant-stride pattern still gets picked up via strides even without a PHT hit.Misconception: that strict matching necessarily trades coverage for accuracy. Here the loss is nearly eliminated because a separate, cheap mechanism catches the simplest missed cases.
Problem 5 · medium
DC (Dense Counter) increments by +1 (slow) on dense regions, but decrements by /2 (fast) when DC>2 and non-dense, or −1 (slow) when DC≤2 and non-dense. Why not just use symmetric +1/−1 updates?
Show answer
A high DC represents strong recent confidence that dense, streaming-like regions have been common lately (DC is a single counter, not tied to one trigger PC — that's DPCT's job); if the very next region to deactivate breaks the streak, that's meaningful evidence the behavior has changed, and continuing to over-prefetch based on stale confidence is costly — so DC should drop fast. But when DC is already low, there's little confidence to lose, so a small −1 avoids the counter flapping noisily between low values on ordinary variation.Misconception: that counter updates should be symmetric by default. Here the asymmetry directly encodes "how costly is being wrong at this confidence level," not just "which direction is evidence pointing."
Problem 6 · hard
Why does Stage 2 require two consecutive matching strides (three accesses) before promoting blocks, instead of promoting after just one stride-1 access?
Show answer
A single stride tells you the distance between two accesses, but not that a stable pattern is repeating — it could be coincidence. Two consecutive matching strides confirm that the same stride is recurring, which is much stronger evidence of a genuine sequential stream rather than an isolated jump that happens to land one block over. This mirrors why Stage 1 itself starts conservative — Gaze prefers to accumulate corroborating evidence before committing more aggressive (and more costly-if-wrong) prefetches.Misconception: that one match is as good as two for confirming a pattern. One match could be noise; two consecutive matches are what turns a coincidence into a trend.
Problem 7 · medium
vBerti achieves higher raw L1D accuracy than Gaze on many workloads, yet loses to Gaze in bandwidth-constrained (8-core) settings on several of them. What's the missing piece in "higher accuracy = better"?
Show answer
vBerti has no built-in check for whether a block is already resident in the L1D before issuing a prefetch, so it generates redundant requests that occupy the Prefetch Queue only to be discarded later. These redundant requests don't count against its measured accuracy (they're not "useless" data-wise) but they still consume queue slots and delay legitimate prefetches — a cost that compounds under contention. Gaze, being region/footprint-based, naturally avoids re-requesting blocks it already tracked as fetched for that region.Misconception: that the standard accuracy metric captures every source of prefetching inefficiency. Redundant (already-resident) requests are a real cost that accuracy, as measured, doesn't penalize.
Problem 8 · easy
On QMM server workloads, Gaze's spatial-pattern-based prefetching produces only a small (-1.6% average) change despite covering nearly a third of LLC misses. Why doesn't good coverage translate to a speedup here?
Show answer
The paper notes QMM server workloads are bottlenecked by instruction misses (high L1I MPKI), not data misses (relatively low LLC MPKI) — so eliminating data misses, even a substantial fraction of them, barely touches the actual bottleneck. A data prefetcher, however good, cannot fix an instruction-fetch-bound program.Misconception: that miss coverage always predicts speedup. Coverage only helps if the misses you're covering are actually on the critical performance path — here they mostly aren't.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What exactly does "footprint-internal temporal correlation" mean?▾
The order in which a region's blocks get accessed, considered as a fingerprint of the region itself. Two regions "correlate" if their accessed blocks line up both spatially (which blocks) and temporally (in what order) — starting with just the first two accesses in Gaze's case.
Q2Why is context-based matching (PC/Offset/PC+Address) not good enough on its own?▾
Context only captures where an access came from, not what pattern follows it. Coarse context (Offset, as in PMP, or PC+Offset, as in SMS) collides across unrelated regions in complex workloads; fine context (PC+Address, as in Bingo) avoids most collisions but requires a huge table (>100KB) because nearly every distinct context needs its own learned entry.
Q3Does waiting for a second access make Gaze slow to react?▾
It delays the very first prediction for a region by exactly one access — a bounded, small cost. The paper's evaluation shows this doesn't hurt timeliness overall: Gaze has the second-best (lowest) late-prefetch fraction among all evaluated prefetchers (12.3%, only 0.5 points behind vBerti's 11.8%).
Q4How does Gaze store temporal information without extra metadata?▾
It repurposes the existing PHT lookup: the trigger offset becomes the index (as any PC/offset scheme would use), and the second offset becomes the tag that's checked on lookup. The order is implicitly verified because index and tag come from two specific, ordered accesses — no separate field is needed to record "order."
Q5What's the difference between the PHT path and the DPCT/DC path?▾
PHT handles "normal case" regions (trigger ≠ 0 or second ≠ 1) using the trigger+second temporal signal. DPCT/DC handle "spatial streaming detection" (trigger = 0 and second = 1) — a special, high-density case that needs cautious, gradually-ramped aggressiveness instead of a direct footprint replay, to avoid over-prefetching.
Q6How big is Gaze's hardware overhead, really?▾
4.46KB total (FT 456B + AT 1128B + PHT 2304B + DPCT 15B + PB 668B) — 31× smaller than Bingo, 0.54KB smaller than PMP, 1.91KB larger than Berti. All tables are single-cycle accessible.
Q7Does Gaze always win?▾
No. It shows performance degradation on some irregular traces (up to 6.9% at worst, versus PMP's 27.3% and vBerti's 8.5% worst cases), and on QMM server workloads — which are instruction-fetch bound rather than data-miss bound — its data prefetching barely moves the needle (-1.6% average).
Q8Where is Gaze deployed, L1D or L2C?▾
Primarily and evaluated as an L1D prefetcher, working directly on cache loads. It can also run at L2C alongside a commercial L1D prefetcher like IP-stride, though the paper finds multi-level combinations (Group 2 in §IV-B5) don't beat using Gaze alone at L1D.
Q9Does combining Gaze with other prefetchers help?▾
Only marginally. Gaze+Bingo is the best combination tested, giving just +0.34% IPC over Gaze alone at L1D — most other combinations (with SPP-PPF, vBerti, DSPatch, PMP) fall short of standalone Gaze, and some even regress due to added L2 aggressiveness.
Q10How does this relate to OS-managed memory tiering (page hotness prediction)?▾
Structurally similar problem at a very different granularity and timescale: Gaze predicts a cache-line footprint within a 4KB region from ~2 accesses observed in nanoseconds; page-hotness classifiers like TPP's PTE accessed-bit scans, HeMem's PEBS-sampled counters, or Memtis's periodic access-frequency estimates classify whole-page "hotness" from access counts sampled over milliseconds. The common thread is using a cheap, partial signal instead of exhaustive tracking. What Gaze has that page-granularity tiering typically can't get is sub-page temporal order — hardware can see which cache line within a page was touched first, second, third; OS-visible access bits or PEBS samples generally can't resolve intra-page order at all, which is an interesting asymmetry if you're thinking about what a CXL-side hardware hint could someday expose to a page-placement policy.

Glossary & results

Every term in one place, then the headline numbers and provenance.

Core terms
GazeThe paper's prefetcher: characterizes spatial patterns via footprint-internal temporal correlation (first two accesses) instead of environmental context.
Footprint-internal temporal correlationThe order in which blocks inside one region's footprint are accessed — used here as the region's fingerprint.
Trigger / second offsetThe offsets of a region's 1st and 2nd distinct accesses; used as (index, tag) into the PHT.
Strict matchingGaze requires both trigger and second offset to match — no prediction on a partial match (unlike Bingo/TAGE).
Spatial streamingProlonged sequential (stride-1) accesses producing near-fully-dense footprints; needs cautious handling to avoid over-prefetching.
Two-stage aggressiveness controlStage 1 assigns cautious initial prefetch depth/level based on DPCT/DC; Stage 2 promotes further blocks once strides confirm streaming.
DPCT / DCDense PC Table records trigger PCs that recently produced fully-dense regions; Dense Counter (3-bit) tracks confidence, asymmetric increment/decrement.
Supporting terms
FT / AT / PHT / PBFilter Table, Accumulation Table, Pattern History Table, Prefetch Buffer — the four structures forming Gaze's pipeline.
Region4KB memory chunk (Gaze's default), the granularity spatial patterns are defined over.
Accuracy / Coverage / TimelinessUseful ÷ all prefetches; misses eliminated ÷ total misses; fraction of prefetches arriving too late to beat the demand access.
PMP / vBerti / Bingo / SMS / DSPatchRival prefetchers: coarse offset-merging, virtual-address delta-based, fine PC+Address, PC+Offset with filtering, and dual-pattern PC-based, respectively.
ChampSimTrace-driven cycle-accurate simulator used for the evaluation (201 traces, 200M warmup + 200M simulated instructions/core).
