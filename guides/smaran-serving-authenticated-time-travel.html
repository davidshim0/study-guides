SOSP 2026 · A Field Guide

Proving what the past looked like with a handful of fixed-size proofs, not one per version

A time-travel query asks what a record — a key, an account balance — looked like at some point in history. When the server can't be trusted, every returned value needs a proof, and naive designs make that proof grow with how far back you ask. This is the plain-English story of Smaran, a data structure that keeps the proof constant-size no matter the range.

📄 "Smaran: Serving Authenticated Time-Travel Queries" · Nepal, Subedi, Mishra, Kate, Meling, Gupta 🎓 Some cryptographic-commitment basics assumed — the primers cover them ⏱ ~25 min read

1What a time-travel query actually asks▾

A record — Bob's public key, Alice's account balance — evolves through a sequence of versions over time. A time-travel query asks for the versions in some interval: "what was this key on epoch 40?" or "list every balance change last year."

This is different from asking for the current value — you're asking the system to reconstruct and prove a slice of history, not just the present.

Now you're ready: Smaran's whole job is answering exactly this kind of query with a small, fixed amount of proof material — regardless of how long the interval is.
2Why "authenticated" — the trust problem▾

If you trust the server, a time-travel query is just a database lookup. Smaran targets settings where you can't: secure messaging (a malicious server could quietly hand different users different keys), or a decentralized ledger (no single node is trusted).

"Authenticated" means the response comes with a cryptographic witness — proof that the returned data is both correct (not fabricated) and complete (nothing was hidden).

Now you're ready: every design decision in Smaran trades off three costs on that witness — how big it is, how long it takes to generate, and how long it takes to verify.
3Merkle trees — the classic baseline▾

Arrange values as leaves of a binary tree; each internal node hashes its two children. The root is a commitment to everything. To prove one leaf, hand over the sibling hashes on its root path (a witness of size ∝ tree height).

Great for point queries. For a range of n values, you need n separate witnesses — cost grows linearly with the range.

Now you're ready: this O(n) blow-up on ranges is exactly the villain Smaran is built to avoid.
4Vector commitments & KZG — commit once, open anywhere▾

Encode a list of values as a polynomial P(x) with P(i)=vᵢ. A vector commitment (Smaran uses KZG) is a single group element committing to that whole polynomial. Any single position can later be opened with a proof whose size never grows — one 48-byte curve point, however long the vector.

Two catches: opening a batch of positions still costs work proportional to the batch size (one polynomial division worth of work per position, though the proof stays one group element), and the vector has a hard maximum length L fixed at setup.

Now you're ready: Smaran's trick is making the batches small (O(log n), not O(n)) via a segment tree — see primer 5.
5Segment trees — pre-summarizing ranges▾

A segment tree precomputes an aggregate for every sub-interval of a list, arranged as a binary tree. Any range query can then be answered by combining a small, fixed number of precomputed nodes per level — O(log n) nodes total, not O(n).

This is the structural trick that keeps things cheap: touch a handful of nodes, not every leaf in the range.

Now you're ready: combine this range-covering property with a vector commitment's O(1)-size proof, and a range query needs only O(log n) work to produce one small proof.
6Why plain aggregation can't be authenticated▾

Classic segment trees use associative functions like sum, count, or max. These are lossy: many different input sequences produce the same aggregate (5 = 2+3 = 4+1). Committing to a sum doesn't commit to which values produced it.

To authenticate individual versions, the aggregation function itself must be a cryptographic binding — Smaran simply hashes each node from its two children, i.e. Merkleizes the segment tree.

Now you're ready: this is exactly what "Merkleized Segment Tree" means — segment tree shape, Merkle-hash bindings at every node.
7Bounded capacity — one commitment can't hold everything▾

A KZG commitment's maximum vector length L is fixed by its setup parameters (the SRS) — in practice, around 4096 elements for common curves. History, however, grows forever.

The naive fix — stack commitments hierarchically, letting a parent commit to children's commitments — looks appealing but silently reintroduces the O(n)-witnesses problem across the boundary between levels.

Now you're ready: Smaran's hierarchical design (promoting whole roots, not just commitments) is built specifically to dodge this trap — see the How It Works tab.
8Elliptic-curve pairings are expensive — hashing is not▾

Verifying a KZG witness requires a pairing check on an elliptic curve — an operation that costs roughly 775 microseconds on the curve Smaran uses (BLS12-381). A single hash, by comparison, costs well under a microsecond.

So the number of pairing checks a scheme requires matters enormously for verification latency, separately from how many bytes the proof occupies.

Now you're ready: Smaran deliberately bounds pairing checks to O(γ) — a small constant — rather than letting them scale with the query range.
The whole story in one place

Smaran in a nutshell

The problem, the structural trick that fixes it, and how the pieces connect.

Existing authenticated structures are built for point queries. Merkle trees answer a range by generating one witness per returned value — proof size and cost both scale linearly with the range. Vector commitments alone give a constant-size proof for one position, but batching many positions still costs work proportional to the batch, and every commitment has a hard capacity ceiling.

Smaran's fix is a Merkleized Segment Tree (MST): build a segment tree (so any range is covered by only O(log n) precomputed nodes), Merkleize it (hash children into parents, so the structure is cryptographically bound), then flatten the whole tree — leaves and internal nodes alike — into one vector and commit to it with a single KZG vector commitment. A range query now needs one witness batch over just the O(log n) nodes that cover it, producing a proof whose size doesn't grow with the range at all.

Two further problems remain, and Smaran solves both structurally. Capacity: a commitment can't grow forever, so Smaran stacks MSTs into hierarchical layers, promoting a full lower-layer root into a leaf position of the parent MST — preserving the segment-tree covering property across layers, so a query touches at most two MSTs per layer no matter the range. Redundancy: most epochs see no update to a given record, so Smaran uses versioned leaves — a value plus its start/end epoch — instead of copying the last value into every idle epoch.

The payoff: in key transparency (10k users, ≤2047 key versions), Smaran cuts monitoring-query latency by up to 99.1% vs. CONIKS and 82.5% vs. OPTIKS, and payload by up to 97.0% vs. CONIKS (95.2% vs. OPTIKS). On 2.6M real Ethereum blocks, it delivers up to 589× higher throughput and 99.94% lower latency than Merkle-tree range proofs — for O(γ) 48-byte group-element proofs plus a small MPT witness, independent of the query range.

🍯 Key takeaways

  • Merkle trees: O(1) point proofs, but O(n) for a range of n versions. Vector commitments alone: O(1)-size proof, O(n) batch cost, and a hard capacity ceiling.
  • A segment tree covers any range with O(log n) precomputed nodes — Smaran Merkleizes it, then commits to the whole flattened tree with one KZG commitment.
  • A naive commitment-of-commitments hierarchy reintroduces linear witness growth; Smaran fixes this by promoting whole roots (not just commitments) into parent leaves.
  • Versioned leaves (value + start/end epoch) skip storing a copy for every idle epoch — the dominant case under power-law update patterns.
  • Result: proof size O(γ) group elements (γ = hierarchy depth, ≤4 in practice) regardless of query range; up to 589× throughput, 99.94% lower latency vs. Merkle trees.
Six everyday pictures

How to think about Smaran

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The problem · Merkle range proofs

Photocopying every page of a chapter

To prove you read chapter 3, a librarian could photocopy every single page and staple a certified stamp to each. Ask for chapter 3 through 9 and the stack of photocopies grows with how many pages you asked for. That's a Merkle range proof: one witness per version, so the response size scales with the query.

Where it breaks: a real photocopy is cheap; a cryptographic witness costs a hash chain per page — so at scale (thousands of versions) this isn't just clunky, it's genuinely too slow and too large to send.
The fix · Segment tree + vector commitment

A wax seal on a whole scroll, with tabs

Imagine a long scroll with tabs pre-glued at nested intervals — one tab per decade, per year, per month — each tab a short, verifiable summary of everything beneath it. Seal the entire scroll, tabs and all, with one wax stamp. To prove any stretch of history, you point to a handful of tabs that jointly cover it and open just those — one stamped proof, however long the stretch.

Where it breaks: the scroll (the vector commitment) has a maximum length fixed when the wax was poured — you cannot keep adding tabs forever to the same seal.
Scaling · Hierarchical MST

DRAM fills up, so you promote a summary — not everything

A fast local tier has bounded capacity, just like a KZG commitment's fixed length L. When it fills, you don't copy every byte into the next tier — you promote a compact summary (a page-table entry, a root hash) that the next tier can point to and trust, while the details stay put underneath. Smaran does exactly this: when an MST fills, its root — not the whole tree — becomes one leaf of the parent MST, so a query still only touches O(1) nodes per layer.

Where it breaks: tiered memory can freely demote or re-promote a page as access patterns shift; Smaran's promotion is one-way and permanent (append-only history), since nothing here is ever "evicted."
Redundancy · Versioned leaves

A hotel register, not a nightly headcount

A hotel doesn't stamp every guest's room every single night they stay — it logs one check-in and one check-out date. Smaran's leaves work the same way: a version is stored once, tagged with the epoch range it was valid for, instead of copying that version into every otherwise-idle epoch.

Where it breaks: a hotel register is human-readable; Smaran's tuples (value, start-epoch, end-epoch) still need to be individually hashed into the tree, so the saving is in count of entries, not in avoiding hashing altogether.
Robustness · One honest root suffices

A notarized plaque everyone already agrees on

If a town has already voted and bolted an official plaque to the wall, you don't need to poll every townsperson again to trust what it says — you just read the plaque and check that the inscription is unforged. Smaran works similarly: an agreement layer (consensus, a TEE, or an existing ledger) has already fixed the committed history, so a single server's response — with a valid witness against that already-agreed root — is enough.

Where it breaks: the plaque analogy assumes the town already agreed; Smaran explicitly does not solve that agreement problem itself — it inherits whatever safety/liveness guarantees the underlying agreement layer provides.
Cost model · Pairing checks vs. hashing

A vault door vs. a filing cabinet

Opening a bank vault takes a slow, deliberate mechanical process every time, no matter how small the item inside. Flipping through a filing cabinet is nearly instantaneous per folder. An elliptic-curve pairing check (≈775 µs) is the vault door; a hash (≈0.4 µs) is the filing cabinet. A scheme's real-world speed depends heavily on how many "vault openings" — not just how many bytes — it needs.

Where it breaks: unlike a vault, pairing cost doesn't buy extra security per use — it's pure computational overhead, which is exactly why Smaran works hard to bound the pairing-check count to O(γ) rather than reducing it to zero (impossible) or letting it scale with range (too slow).
The full explanation

How it actually works

From the three failing primitives, through the MST, to hierarchy and versioning.

1 · Why the three obvious primitives each fall short

PrimitiveProof gen.Proof sizeVerifyLimitation
Merkle treeO(n·h)O(n·h)O(n·h)one witness per returned version
Vector commitment (KZG)O(n)O(1)O(n)batch cost scales with range (gen. & verify); hard capacity L
Segment tree (plain)O(log n)——lossy aggregates (sum/max) can't authenticate individual values
Smaran (MST)O(log v + log n)O(γ)O(v + log n)γ small constant (≤4 in practice)
⚠
The lossy-aggregate trap. 5 = 2+3 = 4+1: a sum commits to a total, not to which values produced it. Smaran sidesteps this by using hashing (Merkle binding), not arithmetic aggregation, at every segment-tree node.

2 · Building the MST — Merkleize, then flatten

Each record gets its own segment tree over its versions, with every internal node set to H(left‖right). On its own this is just a Merkle tree with extra structure — still one witness per leaf. Smaran's move is to flatten the entire tree (leaves and internal nodes) into a single vector and commit to that whole vector with one KZG commitment.

3 · Scaling past capacity — promote roots, not commitments

A KZG commitment's max length L bounds how many versions one MST can hold. The naive fix — commit each lower-layer MST independently, then let an upper MST bind those commitments together as its leaves — looks clean but is a trap: a query touching k lower-layer trees now needs 1 upper witness plus k more, one per touched lower commitment (see B in the paper for the full proof). Witness count grows with range again.

Smaran's fix: promote the lower MST's root node (not just its commitment) directly into a leaf position of the parent MST. This preserves the segment-tree covering property across the layer boundary, so a query touches at most two MSTs per layer — total witnesses across γ layers: at most 2γ−1.

4 · Query & proof generation

To answer a range [i:j], Smaran does a depth-first search from the top MST down, collecting the set of MSTs touched by the range (at most 2 per layer, so ≤2γ−1 total), then generates one witness batch per touched tree:

# proof generation for range [i:j] of record k
T = MSTsTouchedBy(i, j)              # DFS, ≤2 MSTs per layer
for t in T:
    B_t = coveringNodes(t, i, j)     # nodes of t spanning its sub-range
    w_t = Witness(V_t, B_t)          .# one 48-byte proof for the whole batch
w_M = MPT.Witness(k)                 # proves C_M commits record k's MST commitment
return {versions, {(C_t, w_t) for t in T}, w_M}   # O(γ) proofs total
💡
Why the client's verification isn't free. The client must still read every returned version — an unavoidable Ω(j−i) cost — and reconstruct the internal nodes those versions imply. What Smaran removes is the proof-checking cost scaling with range: only O(γ) pairing checks are needed, not one per version.

5 · Eliminating redundancy — versioned leaves

Real update patterns follow a power law — most records change rarely. Instead of one leaf per epoch (copying the last value into every idle one), Smaran stores a leaf only when a version actually changes, tagged with the epoch range it covered:

Leaf tupleMeaning
⟨v1, 1, 3⟩Record held value v1 from epoch 1 through epoch 3
⟨v2, 4, 8⟩Value v2 from epoch 4 through 8
……
⟨v5, 20, 25⟩Value v5 from epoch 20 through 25; v6 is current as of epoch 26

The MPT entry for the record then stores H(C ‖ v6 ‖ 6) — binding the current commitment to the latest value and its version number α=6, which is what lets a client verify "α is the newest version" (non-membership of α+1) without an extra proof. (The epoch-tagged ⟨value, start, end⟩ form shown above is for the versioned leaves inside the MST — the top-level MPT entry itself only needs the version number, not the epoch.)

Follow the numbers, step by step

Worked examples

Five traces using the paper's real parameters and measurements — from capacity math to where verification time actually goes.

① How many versions fit — and how far hierarchy scales

With SRS size L = 4096 (BLS12-381, matching real deployments), how many versions fit in one MST, and across a γ = 4-layer hierarchy?

  1. Single MST leaves: a flattened MST of n versions has 2n−1 nodes. Bound: 2n−1 ≤ L=4096 ⟹ n ≤ 2048.5 ⟹ n = 2048 versions per MST — matches the paper's "up to 2047 key versions" workload.
  2. Upper-layer roots: an upper MST holds m lower roots as leaves, m−1 internal nodes, and m commitments: 3m−1 ≤ 4096 ⟹ m = ⌊4097/3⌋ = 1365 lower trees per upper MST.
  3. Across γ=4 layers: total capacity = n·m^(γ−1) = 2048 × 1365³.
  4. Compute 1365³: 1365² = 1,863,225; ×1365 ≈ 2,543,302,125.
  5. Total: 2048 × 2,543,302,125 ≈ 5.21 trillion versions — matching the paper's "more than five trillion versions" claim.
🍯
Insight: γ=4 is a small constant precisely because the capacity grows as m^(γ−1) — each added layer multiplies capacity by ~1365×, so real deployments never need more than a few layers.

② Naive hierarchy vs. Smaran — counting witnesses on a real query

For the example in Fig. 3 (L=8), a client queries versions [4:9], which spans parts of three lower MSTs: [1:4], [5:8], [9:12].

  1. MST[5:8] is fully covered and is itself a single leaf of the upper-layer MST — so Smaran authenticates it with just one witness (for commitment C2), issued as part of the upper-layer batch.
  2. MST[1:4] is only partially covered (just v4) — Smaran descends to the leaf level within that tree, producing one more witness.
  3. MST[9:12] is likewise only partially covered (just v9) — one more witness.
  4. Smaran's total: 3 witnesses for this query, regardless of how many versions [4:9] actually spans.
  5. Naive hierarchy (commitments as leaves): the same query needs a witness for the upper commitment plus a separate witness for each of the (up to 3) touched lower commitments — 4 witnesses here, and the count keeps growing as more lower trees are touched by wider ranges.
💡
The gap widens with scale: for a query spanning hundreds of lower-layer MSTs, naive hierarchy needs hundreds of witnesses; Smaran still needs at most 2γ−1 = 7 (for γ=4).

③ Key transparency: what 99.1% and 82.5% latency reduction imply

At 2047 key versions, Smaran's measured latency is 41.6 ms. The paper reports this is 99.1% lower than CONIKS and 82.5% lower than OPTIKS. What were the baselines' latencies?

  1. Solve for CONIKS: 41.6 = CONIKS × (1 − 0.991) = CONIKS × 0.009 ⟹ CONIKS ≈ 4.62 seconds.
  2. Solve for OPTIKS: 41.6 = OPTIKS × (1 − 0.825) = OPTIKS × 0.175 ⟹ OPTIKS ≈ 237.7 ms.
  3. Sanity check against complexity: CONIKS is O(T log n) with T=2047 epochs, n=10,000 users; OPTIKS is O(v log n) with v=2047 versions — both linear in history length, consistent with CONIKS being far slower (it re-authenticates per epoch, including idle ones) than OPTIKS (per version only).
  4. Smaran's search/generation cost is O(log v + log n) ≈ log₂(2047) + log₂(10000) ≈ 11 + 13.3 ≈ 24.3 tree-traversal steps to locate the record and its O(log n) covering nodes — versus OPTIKS's O(v·log n) ≈ 2047×13.3 ≈ 27,225 hash operations to walk the full version history. That ~1,100× asymptotic gap is far larger than the measured 5.7× throughput gap, because those traversal steps are themselves cheap (hash/index lookups, not pairings) on both sides; the pairing cost only shows up separately, in Smaran's O(γ) KZG witness verifications (~775 µs each) — constants, and knowing exactly where the expensive operations live, matter as much as big-O here.

④ Where verification time actually goes at large ranges

At a 600k-version query range on the Ethereum workload, Smaran's measured client-side verification time is 204 ms, versus 37.8 s for the MPT (Merkle) baseline. With γ=4, verification needs at most 2γ−1=7 MST witness checks — each a KZG pairing check (itself two pairings under the hood) — plus one hash-based MPT check. Does that account for the 204 ms?

  1. Pairing-check cost alone: 7 × 775,437 ns ≈ 5.43 ms — using Table 2's measured BLS12-381 pairing latency.
  2. So pairings are only ~2.7% of the 204 ms. The rest is the unavoidable Ω(v) "preparation" phase: reading and hashing all 600,000 returned versions into their implied MST nodes (Keccak256 at ~368 ns each ⟹ ~221 ms for 600k hashes alone — roughly matching the residual).
  3. Contrast with MPT: its 37.8 s includes both O(v) hashing and O(v) Merkle-path verification (one path per version) — the second term dominates and is exactly what Smaran's O(γ) design removes.
  4. Takeaway: Smaran can't (and doesn't try to) beat the Ω(v) cost of reading v versions — nothing can. It eliminates the second, avoidable linear term (per-version proof verification), which is where the 99.46% reduction (37.8s → 204ms) actually comes from.

⑤ Sharding: near-linear, then saturation

On the 32-core evaluation machine, ingestion throughput scales from 1 shard (~1.1K ops/s) to 1000 shards. Where does linear scaling stop, and why?

  1. 1 → 10 shards: ~1.1K → ~10.5K ops/s, a ~9.5× speedup for 10× the shards — near-linear, since per-record MST updates are embarrassingly parallel.
  2. 10 → 50 shards: ~10.5K → ~33–40K ops/s — still healthy scaling, roughly 3.5×.
  3. 500 shards: ~62–70K ops/s — diminishing returns are visible; going from 50→500 shards (10×) only yielded ~1.9× more throughput.
  4. 500 → 1000 shards: only +7.4% more throughput at 2M users — the 32-core server's compute is saturated, and Ethereum's power-law hot-account distribution means extra shards mostly just subdivide already-idle work.
🍯
This is a familiar shape for anyone who's tuned thread/shard counts against a fixed core budget and a skewed access distribution — more parallelism helps until the hardware, not the algorithm, is the bottleneck.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why can't a plain segment tree using SUM as its aggregation function be used to authenticate individual versions, even though it answers range queries in O(log n)?
Show answer
SUM is lossy: many different sequences of values produce the same total (5 = 2+3 = 4+1). Committing to a sum binds you to a number, not to which specific values produced it — so a malicious server could substitute different underlying values that still sum correctly. Smaran instead Merkleizes the tree (each node = hash of its children), which is a cryptographic binding: changing any leaf changes every ancestor hash.Misconception: that "fast range queries" and "authenticated range queries" are the same requirement. Efficiency and bindingness are separate properties, and the aggregation function must satisfy both.
Problem 2 · medium
With SRS size L = 1024, how many versions can a single MST hold? (Use the derivation from Worked Example ①.)
Show answer
A flattened MST with n versions has 2n−1 nodes, bounded by L: 2n−1 ≤ 1024 ⟹ n ≤ 512.5 ⟹ n = 512 versions.Misconception: assuming n = L (i.e., that every slot in the commitment holds one version). Half the slots are consumed by internal Merkle-hash nodes, not leaves — capacity is roughly L/2, not L.
Problem 3 · medium
A colleague proposes: "just commit each lower-layer MST independently, then have the upper MST commit to those commitments." What goes wrong for a query spanning many lower-layer trees?
Show answer
This is the naive hierarchy (paper Appendix B). Authenticating that the upper commitment C binds a given lower commitment Cᵢ takes one witness — but that only proves "Cᵢ is one of the committed values," not anything about the versions inside tree i. You still need a separate witness per touched lower-layer commitment, so total witnesses grow with the number of lower-layer trees the query spans — the exact O(range) blow-up Smaran was built to avoid.Misconception: that "committing to commitments" is free composition. Each layer boundary you cross this way adds another linear term unless you preserve the segment-tree covering property across it (which promoting full roots, not bare commitments, does).
Problem 4 · hard
Smaran's proof size is O(γ) group elements — constant in the query range. But proof generation cost is O(log v + log n), not O(1). Explain why generation cost isn't also constant.
Show answer
Proof size stays constant because a KZG batch witness is always a single group element, no matter how many positions are in the batch. But computingMisconception: conflating "the proof is small" with "the proof is free to make." The witness's cheapness is about bytes transmitted, not the CPU work behind it.
Problem 5 · medium
Ethereum account updates follow a strict power law — the most active account has 2.6M versions, but even the 100th most active has "only" 534k. Why does versioned storage (value + start/end epoch) help disproportionately here, compared to a workload where every account updates every epoch?
Show answer
Under a power law, the overwhelming majority of accounts are updated rarely relative to the number of epochs elapsed — most epochs are idle for most accounts. A scheme that materializes one leaf per epoch regardless of change pays for all those idle epochs; versioned storage pays only for actual changes. The skew means the savings compound: a handful of hot accounts see modest savings, but the long tail of rarely-updated accounts sees enormous savings, since they'd otherwise be almost entirely redundant copies.Misconception: thinking the benefit is uniform across records. The benefit scales with how idle a record is — hot, constantly-changing records see little to no savings from versioning.
Problem 6 · hard
Smaran's key-update throughput is measured to be slightly below OPTIKS at every directory size (27.0% lower at 10K users, closing to 14.8% at 1M users). Why is Smaran ever slower, and why does the gap shrink as the directory grows?
Show answer
Every key update in Smaran recomputes a KZG commitment, which involves elliptic-curve operations (multi-scalar multiplication) — inherently more expensive per-operation than OPTIKS's hash-based Merkle-prefix-tree updates. That constant-factor gap doesn't disappear. But CONIKS-style/MPT-style directory operations also grow more expensive as the directory (n users) grows, since the MPT path being updated for every key change deepens with log n; as n grows, this shared, OPTIKS-also-incurred cost becomes a larger fraction of total update time, so Smaran's fixed per-update KZG overhead shrinks in relative terms even though its absolute value is roughly constant.Misconception: that Smaran should always win because it wins on queries. Query performance and update performance stress different parts of the system — Smaran trades a bit of update speed (KZG updates) for a large win on query proofs (constant-size witnesses).
Problem 7 · easy
Why does Smaran's security analysis (Theorem 1, Appendix D) assume the commitment C was honestly generated, rather than proving binding against an adversarially chosen C?
Show answer
Because Smaran relies on a distributed-trust agreement layer (BFT consensus, a TEE, or an existing ledger) to produce and publish commitments — a malformed commitment from a single malicious server would simply be rejected by consensus before ever being published. Given that only honestly-generated commitments reach clients, the theorem only needs to rule out an adversary forging two different openings of the same honest commitment, which is a weaker (and sufficient) guarantee for this deployment model.Misconception: that this is a weaker or incomplete security proof. It's scoped correctly to the paper's threat model — the harder "adversarial C" case is explicitly deferred as future work for single-server deployments without consensus.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly does "constant number of fixed-size proofs" mean?▾
Regardless of the query range (1 version or 1 million), Smaran returns at most 2γ−1 witness batches (γ = hierarchy depth, typically ≤4) — each paired with the touched MST's 48-byte commitment C_t — plus one MPT witness of size O(|record ID|). In total that's O(γ) 48-byte group elements plus the MPT witness. The count and size don't grow with the queried interval — only the returned data (which the client must read anyway) does.
Q2Isn't the client's verification cost still linear in the range, since it reads every returned version?▾
Yes — and the paper is explicit that this is unavoidable (Ω(v) to even read v versions). What Smaran removes is the avoidable linear cost: per-version cryptographic proof-checking. Reading is O(v); checking proofs is O(γ), a small constant.
Q3Why is a segment tree needed at all — why not just use a vector commitment directly over the leaves?▾
You could, but opening a batch of n leaf positions still costs O(n) work (one polynomial-division term per position), even though the resulting proof is one group element. The segment tree's job is to shrink the batch size itself to O(log n) by giving you precomputed nodes that jointly cover any range — so you commit once but open far fewer positions per query.
Q4What stops the hierarchy from needing more and more layers as history grows?▾
Each additional layer multiplies total capacity by m (≈1365 for L=4096), not adds to it — so capacity grows exponentially in γ while γ itself stays tiny. Four layers already support roughly 5 trillion versions per record, comfortably beyond any realistic deployment.
Q5How does Smaran know a returned key/version is the latest one, not just a valid old one?▾
The MPT entry for a record doesn't just store the MST commitment C — it stores H(C ‖ v_α ‖ α), binding the commitment to the latest value v_α and its version number α. Verifying the MPT witness against this hash confirms both the commitment and that the stated version is current, which serves as the non-membership proof for "no version α+1 exists" that key-transparency monitoring queries need.
Q6Does Smaran require trusting the query server at all?▾
No — that's the point of "authenticated." The query server can behave arbitrarily (refuse, delay, fabricate), but it cannot produce a valid witness for incorrect data as long as the underlying cryptographic assumptions (collision resistance, KZG binding) and the agreement layer's guarantees hold. A single server's response is sufficient because the history it must prove against was already fixed by consensus.
Q7Why is Smaran sometimes slower than OPTIKS on updates but much faster on queries?▾
Updates require recomputing a KZG commitment (elliptic-curve operations, inherently pricier than hashing). Queries are where Smaran's structural advantage — O(γ) witnesses instead of O(v) or O(T) — pays off overwhelmingly, especially as version counts grow into the thousands or millions.
Q8What is the Structured Reference String (SRS) and why does its size matter?▾
The SRS is the public setup output of KZG's trusted-setup ceremony — a list of curve points derived from a secret that's then discarded. Its length directly bounds the maximum vector a single commitment can hold (L). A larger SRS supports longer vectors but costs more storage (roughly 96 bytes per index), which is why Smaran solves long-term growth via hierarchy rather than an ever-larger SRS.
Q9How is Smaran evaluated, and against what baselines?▾
Two settings: key transparency (10k users, ≤2047 key versions, vs. CONIKS and OPTIKS) and a decentralized ledger (2.6M real Ethereum blocks from 2024, ~60M accounts, vs. Merkle Patricia Tries, Verkle trees, and Cauchyproofs). Metrics: query/update throughput and latency, payload size, and commitment-generation throughput.
Q10What did the authors leave for future work?▾
Extending the security proof to adversarially-chosen (not just honestly-generated) commitments for single-server deployments without a consensus layer — the current Theorem 1 assumes an honest commitment, backed by the paper's distributed-trust model.

Core terms
SmaranThe system: an authenticated data structure that answers time-travel queries with a constant number of fixed-size proofs.
MST (Merkleized Segment Tree)A segment tree whose internal nodes are Merkle hashes, flattened and committed with a single vector commitment.
FlatteningArranging all MST nodes (leaves + internal) into one contiguous vector, so a single KZG commitment covers the whole tree.
Vector commitment (VC)A primitive that commits once to a list of values and later opens any position with a proof independent of vector length.
KZG commitmentThe specific pairing-based VC scheme Smaran uses (Kate, Zaverucha, Goldberg 2010); commitments/witnesses are single 48-byte curve points.
SRS (Structured Reference String)KZG's public setup parameters; its size bounds the maximum vector length L a commitment can hold.
Hierarchical MST / promoted rootStacking MSTs across γ layers by promoting a full lower-layer root (not just its commitment) into a parent leaf, to scale past L while keeping witness count bounded.
Versioned leafA leaf storing (value, start-epoch, end-epoch) instead of one entry per epoch — eliminates redundancy for idle periods.
Supporting terms
Merkle Patricia Trie (MPT)Maps record IDs to their MST commitments; only its root is published to the ledger, giving public verifiability across all records.
Agreement layerWhatever mechanism (BFT consensus, TEE, existing ledger) fixes the accepted, ordered history that Smaran proves against.
WitnessA short cryptographic proof that specific values belong to a committed set.
Pairing checkThe elliptic-curve operation used to verify a KZG witness; the dominant per-proof cost (~775 µs on BLS12-381).
Monitoring queryA key-transparency query proving a key has α versions: integrity of versions 1..α plus non-membership of α+1.
γ (gamma)Number of layers in the hierarchical MST; capacity grows as n·m^(γ−1), so γ stays small (≤4) in practice.
Range bindingThe security property (Theorem 1) that no adversary can produce two valid openings of different values at the same position under an honestly generated commitment.
Power-law update patternMost records change rarely; a few change often — the workload shape that makes versioned leaves valuable.
