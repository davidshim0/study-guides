Same bytecode, same behavior? Only if you can prove it

eBPF now runs on Linux, Windows, in user space, on microcontrollers, and in blockchain VMs — each with its own verifier and runtime. An executable F* semantics checks whether they actually agree, and — as ongoing work — aims to turn that agreement into provably faithful prose.

1What eBPF actually is▾

A way to run small, sandboxed bytecode programs inside a host (kernel, hypervisor, blockchain node) without recompiling it — a verifier checks safety before the bytecode ever executes.

Now you're ready: "cross-platform eBPF" means the same bytecode should behave the same way in every one of these hosts.
2The verifier's job▾

Before a program runs, a verifier statically rejects anything that could crash, loop forever, or read out of bounds. Different platforms built independent verifiers (Linux's, and Windows's PREVAIL).

Now you're ready: two verifiers can disagree on what's safe, or agree on safety while disagreeing on what the accepted bytecode runs as.
3RFC 9669 — what it covers, and what it skips▾

The IETF standard defines instruction encodings. It says nothing about the calling convention, register roles, stack, frame pointer, program-entry context, or helper/map interfaces — the parts a runtime needs to actually execute a program.

Now you're ready: "the standard" and "what runtimes agree on" are not the same set — the second is much bigger, informally.
4Five-plus independent runtimes▾

Linux, Windows (via PREVAIL + bpf2c), uBPF (user space; also ships as part of the Windows eBPF runtime), bpftime (user space), rBPF (microcontrollers), and Solana's SBPF (blockchain) — built separately, for different purposes.

Now you're ready: each runtime is currently its own de facto specification of "what eBPF means."
5Calling convention, registers, stack, frame pointer▾

How arguments pass between functions, which registers play which role, how the stack is laid out, and where the frame pointer sits. RFC 9669 doesn't mandate any of this — but runtimes converged on it anyway.

Now you're ready: this convergence-without-a-standard is exactly the "shared core" the paper's semantics captures explicitly.
6Helpers, kfuncs, and maps▾

Helper functions and kfuncs let a program call into the host (e.g. read a timestamp); maps are host-managed key/value stores a program can access. These sets, and their semantics, differ across platforms far more than core instructions do.

Now you're ready: this is where the paper expects — and is actively hunting for — the most divergence.
7Conformance testing▾

Feed the same bytecode to several implementations and compare the resulting register/memory state. The bpf_conformance suite already does this across real runtimes; the paper adds its F* semantics as one more target.

Now you're ready: "passes conformance" here means: run against the suite's tests, the F* semantics matches expected outcomes on par with Linux, Windows, uBPF, and bpftime — not a formal proof that all five always agree.
8F* and "executable" formal semantics▾

Most ISA formalizations are proof artifacts you reason about. An executable semantics is also a program you can literally run as an interpreter — so you can throw real bytecode at it and compare outputs, not just prove theorems on paper.

Now you're ready: this is what lets the same F* model serve as both a specification and a conformance-test participant.
The whole story in one place

One executable semantics, checked from both sides

The gap between "what eBPF is" and "what each runtime does," and how an F* model closes it.

eBPF is no longer Linux-only: it runs on Windows, in user space, on microcontrollers, and in blockchain VMs, each with an independently built verifier and runtime. RFC 9669 pins down the core instructions — in prose, with underspecified corners — but is silent on the broader execution model a runtime actually needs: calling convention, register roles, stack, frame pointer, helpers, maps. So every runtime is, in effect, its own specification, and the standard's own process lags real implementations (the signed-division overflow INT_MIN s/ -1 = INT_MIN was deferred because RFC 9669 had already been frozen, even though runtimes implement it).

The paper's fix is an executable formal semantics in F* that separates shared cross-platform behavior (calling convention, registers, stack, frame pointer — none of it in the RFC, all of it agreed on) from platform-specific behavior (helpers, kfuncs, map types, memory model, stack size) behind an F* typeclass. Because the semantics is executable, it can run the bpf_conformance test suite directly and be compared, state for state, against Linux, Windows, uBPF, and bpftime.

Two further moves extend this into a full toolchain, both in progress: also modeling each platform's verifier (Linux rewrites bytecode as it verifies; Windows's PREVAIL only accepts or rejects, deferring rewriting to a separate bpf2c compile step) so accept/reject comparisons aren't misleading; and using Meta-F* metaprogramming toward prose specifications with an auto-generated, per-instruction equivalence lemma proving the prose matches the model — a goal that, once realized, goes beyond what ISA-documentation tools like Sail guarantee.

🍯 Key takeaways

  • RFC 9669 pins down the core instructions in prose (with underspecified corners) — not the execution model runtimes actually share.
  • The shared core (calling convention, registers, stack, frame pointer) is captured explicitly, separate from platform-specific behavior, via an F* typeclass.
  • The semantics is executable: it passes the bpf_conformance suite on par with uBPF, bpftime, Linux, and Windows.
  • Covers all RFC 9669 instructions except atomics; extending to helpers/maps (more divergence expected) and to verifier modeling is in progress.
  • Meta-F* is being used to generate prose specs (spec_v1, spec_v2) with a per-instruction equivalence lemma — a goal/in-progress pipeline stronger, once complete, than tools that render docs without proving correspondence.
  • Method is runtime-agnostic: adding a new target (e.g. Solana's SBPF) needs only a thin driver.
Five everyday pictures

How to think about the project

Read in any order; each ends with where the picture breaks down.

The core idea · One translation, not five

A hub instead of five bilingual dictionaries

Instead of pairwise-comparing Linux to Windows to uBPF, build one candidate reference meaning — validated by conformance testing, not yet the official standard — and check every platform against it, like translating through a hub language instead of maintaining N² phrasebooks.

Where it breaks: the hub only helps if it's trustworthy itself — which is exactly why it's conformance-tested against real runtimes, not just asserted.
Conformance testing · Same exam, five rooms

Grading the same exam in five classrooms

Give identical bytecode to Linux, Windows, uBPF, bpftime, and the F* model, then compare final register/memory state — like giving five classrooms the same test and checking whose answer sheets match.

Where it breaks: matching answers doesn't mean the grading rules (verifiers) were equally strict — two students can reach the same final state by different, unequally safe paths.
RFC scope · Grammar without vocabulary

A style guide that skips the vocabulary

RFC 9669 is like a style guide that carefully specifies grammar (instruction encodings) but never defines half the words a real sentence needs (calling convention, stack, helpers, maps) — so writers converge on those words by custom, not decree.

Where it breaks: custom usage can still fracture — helper sets already differ across platforms, unlike grammar, which stayed uniform.
Verifiers · Editor vs. stamp

Two proofreaders — one edits, one stamps

Linux's verifier is a proofreader who rewrites the manuscript as they check it (remapping context offsets, inserting overflow guards). Windows's PREVAIL is a proofreader who only stamps "approved" or "rejected," leaving any rewriting to a separate step (bpf2c).

Where it breaks: a stamp still implies trust in a fixed manuscript; PREVAIL's "approved" bytecode is compiled to C afterward, so what finally runs isn't the stamped text either.
Prose generation · A certified translation

A contract with a certified translation

Auto-translated legal text is only useful if a certifier attests it matches the original, clause by clause. Meta-F* is being built to generate prose (spec_v1, spec_v2) and separately auto-generate, per instruction, a lemma proving that prose matches the F* semantics — work in progress toward a certification most doc-generation tools (e.g. Sail) don't provide.

Where it breaks: the certification covers correspondence to the model, not that the model itself is right — that's what conformance testing is for.
The full explanation

How it actually works

From the divergence problem to conformance testing, verifier modeling, and provably faithful prose.

1 · The problem — narrow standard, independent runtimes

RFC 9669 standardizes the core instructions, in prose with some underspecified corners, but not the execution model a runtime needs: calling convention, register roles, stack, frame pointer, program-entry context, helper/map interfaces. Its own process lags implementations too — the signed-division overflow rule INT_MIN s/ -1 → INT_MIN, which runtimes already implement, was deferred from RFC 9669 because the RFC was already frozen. Meanwhile each runtime makes its own design choices: Linux's verifier rewrites bytecode as it checks it (remapping context field accesses to kernel-struct offsets, inserting overflow guards); Windows's PREVAIL only accepts or rejects, leaving transformation to a later bpf2c compile-to-C step. What runs is not always what was written.

⚠
The stakes: this weakens eBPF's "compile-once-run-everywhere" promise and makes its safety argument platform-specific — a program verified safe on one platform isn't automatically safe, or even meaningful, on another.

2 · A cross-platform semantics in F*

The authors write one executable semantics that is cross-platform by construction: a platform-independent core plus an F* typeclass exposing platform-specific operations. Prior formal semantics each targeted one platform — rBPF for microcontrollers, a separate model for Solana SBPF, another for Linux — so this is the first designed to be shared.

Left column: nowhere in RFC 9669, yet every runtime agrees. Right column: where behavior genuinely diverges. Making this split explicit and machine-checked replaces "buried in C and Rust" with "stated once, in F*."

3 · Conformance testing — and beyond the RFC

The semantics runs the bpf_conformance test suite directly (it's executable, so it plays the role of "one more runtime") and its results are compared against Linux, Windows, uBPF, and bpftime — passing on par with all of them. Because the method is runtime-agnostic, covering a new target (e.g. Solana's SBPF) needs only a thin driver, not a new model.

But the suite only covers RFC-defined instructions. Real programs lean on helpers and maps the RFC puts out of scope, where cross-platform divergence is far more likely — for instance, Windows and bpftime happen to converge on a Linux-compatible subset of helper functions, but that convergence is informal, not standardized. The authors are extending both the semantics and the conformance suite to this territory.

4 · Modeling the verifiers, not just the runtimes

Comparing runtime outputs alone can mislead, because verifiers make the comparison subtler: Linux rewrites bytecode during verification; PREVAIL does not. So the authors are also modeling each platform's verifier on top of the semantics — capturing accept/reject decisions and any rewriting — to compare verification results faithfully, pinpoint the root cause when platforms disagree, and evaluate whether each verifier actually enforces the same safety guarantees. This work is in progress; the paper does not report completed Linux or Windows verifier models yet.

5 · Meta-F* — prose that's provably faithful

Using Meta-F* metaprogramming, the goal — work the paper's Discussion describes as in progress — is for the semantics to generate (i) a core prose-spec AST confined to stylized, machine-checkable English, and (ii) per instruction, an auto-generated lemma proving the rendered prose corresponds to the F* semantics. The AST is designed to render to multiple prose forms (spec_v1 as structured pseudo-code, spec_v2 as plain English) and parse back, with equivalence to the model checked mechanically. Once complete, this would go beyond ISA-documentation tools like Sail, which render readable docs without guaranteeing they match the model, and beyond the IETF's own ebpf-check script, which validates an instruction table's syntax against object files rather than proving semantic correspondence.

// DIV op dst, in the F* semantics
let div_result dst op =
  if (op && 0xFFFFFFFF) = 0 then 0
  else (dst && 0xFFFFFFFF) / (op && 0xFFFFFFFF)

// spec_v2, rendered by Meta-F* toward a certified-equivalent form (in progress)
"If op's low 32 bits are zero, set dst to zero;
 otherwise set dst to its low 32 bits divided by op's low 32 bits."
Follow it through

Worked examples

Three traces: a real deferred-spec bug, a conformance-testing walkthrough, and a prose-generation step.

① The INT_MIN s/ -1 overflow — shared, but not in the RFC

  1. The operation: a signed 32-bit division, INT_MIN s/ -1. Mathematically this overflows (the true result doesn't fit in 32 bits).
  2. What runtimes do: they define the result as INT_MIN rather than faulting or trapping — a deliberate, shared convention.
  3. What the RFC says: nothing yet — this case was deferred from RFC 9669 because the document was already frozen when it came up on the IETF mailing list.
  4. What the F* semantics does: encodes the runtimes' actual, shared behavior (INT_MIN) as part of the cross-platform core — not waiting for the RFC to catch up.
🍯
Insight: this is a clean instance of the paper's central claim — real shared behavior can run ahead of the standard, and an executable semantics can track that behavior directly instead of only the frozen text.

② A conformance-testing pass, step by step

  1. Pick a test from bpf_conformance: a bytecode sequence plus an expected final register/memory state.
  2. Run it five ways: through Linux's verifier+runtime, Windows's PREVAIL+bpf2c, uBPF, bpftime, and the F* semantics (as an interpreter).
  3. Compare final states. On RFC-covered core instructions, the paper reports the F* semantics passing on par with all four real runtimes.
  4. Now try a helper call. This test isn't in the core suite yet — it's exactly the territory the authors are extending to, where Windows and bpftime happen to converge on a Linux-compatible helper subset, but nothing guarantees a fourth runtime would.
💡
Passing on the core ISA validates the shared core; it says nothing yet about helpers or maps — which is precisely why that extension is called out as ongoing work, not a solved problem.

③ From F* semantics toward a certified prose sentence (in progress)

  1. Start from the executable rule for DIV op dst in the F* semantics (shown in How It Works, §5).
  2. Meta-F* builds an AST node for this instruction, capturing its structure (a branch on a zero-check, then a division).
  3. The AST renders to spec_v1 (structured pseudo-code) and spec_v2 (plain English) — both confined to a stylized, machine-checkable grammar rather than free-form text.
  4. A lemma is generated per instruction — the paper describes this equivalence-proof pipeline as work in progress — proving the rendered prose is semantically equivalent to the F* rule it came from.
🍯
Insight: the lemma is the whole point of this (in-progress) pipeline — without it, spec_v2 would be a plausible-looking English sentence with no guarantee it says what the model says.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it checks.

Problem 1 · easy
Does RFC 9669 define the eBPF stack and frame pointer? If runtimes agree on them anyway, where does that agreement come from?
Show answer
No — RFC 9669 pins down the core instructions in prose, but not the stack, frame pointer, calling convention, or register roles. Runtimes agree on these by convention/convergence, not by standard mandate. The paper's F* semantics captures this agreed-but-unstandardized behavior explicitly, as part of its platform-independent core.Misconception: assuming everything runtimes agree on must come from "the standard." Much of the real shared execution model exists outside RFC 9669 entirely.
Problem 2 · medium
Suppose an ADD instruction produces identical final register state on both Linux and Windows for every conformance test. Does this mean their verifiers enforce equivalent safety guarantees?
Show answer
Not necessarily. Linux's verifier rewrites bytecode during verification (remapping context offsets, inserting guards); Windows's PREVAIL only accepts or rejects, then a separate bpf2c step compiles the accepted bytecode to C. Two platforms can reach identical runtime state while their verifiers accepted the program through different means and enforced different things along the way — which is exactly why the authors model the verifiers separately from the runtimes.Misconception: that matching final states from conformance testing alone proves equivalent verification. Conformance tests runtime behavior, not verifier reasoning.
Problem 3 · medium
Why is it not enough to only test conformance on RFC 9669's instructions?
Show answer
Because real eBPF programs depend heavily on helper functions and maps, which RFC 9669 puts entirely out of scope — and that's exactly where cross-platform divergence is most likely, since these features aren't standardized at all (only informally converged on, e.g. Windows and bpftime sharing a Linux-compatible helper subset). Passing conformance on the core ISA validates only the narrow part of eBPF the RFC covers.Misconception: treating "the ISA" and "eBPF as used in practice" as the same scope. Helpers and maps are where most real-world portability risk lives.
Problem 4 · hard
Why use an F* typeclass to expose platform-specific operations, rather than just writing one big semantics with if/else branches per platform?
Show answer
A typeclass makes the shared/unshared boundary explicit and machine-checked: the core semantics is written once, parametrized over whatever a given platform's typeclass instance provides (its helper set, map types, memory model), and F*'s type system enforces that platform-specific code can't silently leak into or corrupt the shared core. Scattering if/else per platform inside one function would bury that boundary in code, exactly the "buried in C and Rust" problem the paper is trying to avoid.Misconception: that the goal is just code reuse. The goal is making the shared-vs-platform-specific boundary itself a checkable artifact, not an implicit convention.
Problem 5 · medium
Why is Meta-F*'s prose generation more trustworthy than a documentation-generation framework like Sail?
Show answer
Sail-style frameworks render readable prose/documentation from an ISA model but don't prove the rendered text still means what the model means — a bug in the renderer could silently produce incorrect prose. Meta-F* is being designed to additionally auto-generate, per instruction, a lemma proving the prose-spec AST is semantically equivalent to the F* semantics it was derived from (work the paper reports as in progress), so the correspondence would be machine-checked, not just assumed from the rendering process.Misconception: that any tool which auto-generates documentation from a formal model is automatically faithful. Generation alone gives no guarantee; the guarantee comes from the accompanying proof.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is "cross-platform" about this semantics?▾
It's written once, with a platform-independent core (calling convention, registers, stack, frame pointer) and an F* typeclass exposing the parts that genuinely differ (helpers, maps, memory model, stack size) — rather than one model per platform, which is how prior formal eBPF semantics (rBPF, Solana, Linux) were each built.
Q2Does RFC 9669 define the calling convention or stack?▾
No. It pins down the core instructions in prose — with underspecified corners — but not the broader execution model. Calling convention, register roles, stack, frame pointer, program-entry context, and helper/map interfaces are all out of its scope, even though runtimes agree on most of them informally.
Q3What does "passes the conformance suite on par with uBPF, bpftime, Linux, and Windows" mean?▾
The bpf_conformance test suite runs bytecode and checks the resulting register/memory state. The F* semantics, run as an interpreter, matches expected outcomes at a similar rate to these four real runtimes on the RFC-defined core instructions.
Q4Which instructions aren't covered yet?▾
Atomic operations — the semantics covers all other RFC 9669 instructions. Helper functions, kfuncs, and maps are also not yet covered, since they're outside the RFC and the target of ongoing extension work.
Q5Why does the Linux vs. Windows verifier distinction matter?▾
Linux's verifier rewrites the bytecode it accepts (remapping context field accesses, inserting guards); Windows's PREVAIL only accepts or rejects, and a separate bpf2c step compiles the result to C. Comparing runtime behavior alone can hide real differences in what each verifier actually checked and permitted — hence modeling the verifiers explicitly.
Q6Is adding a new platform (e.g. Solana's SBPF) a big undertaking?▾
Not for conformance testing — the method is runtime-agnostic, and a new target needs only a thin driver connecting it to the existing test harness. Modeling a new platform's verifier, or its helper/map semantics, is separate, ongoing work.
Q7What is Meta-F*, concretely, in this project?▾
F*'s metaprogramming layer, being used here — this pipeline is work in progress — to (i) build a prose-spec AST confined to a stylized, checkable English grammar, and (ii) emit, per instruction, a lemma proving that AST is equivalent to the underlying F* semantics, so that generated documentation would be provably faithful, not just plausible.
Q8What's left as future work?▾
Extending conformance beyond the core ISA to helpers and maps; building out verifier models (accept/reject decisions and rewriting) for Linux and Windows, which the paper describes as also in progress; and finishing the Meta-F* prose pipeline. The long-term vision is a single executable definition that runtimes, verifiers, and the prose standard can all be checked against.
