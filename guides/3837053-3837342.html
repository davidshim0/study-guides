1Why flash can't be overwritten in place▾

NAND flash reads and programs at page granularity but erases only at coarser block granularity. A page can't be rewritten until its whole block is erased, so SSDs write updates to a fresh page and mark the old one invalid — out-of-place update. This keeps foreground writes fast but defers cleanup.

Now you're ready: that deferred cleanup is garbage collection (next card) — the background cost every mechanism in this paper is ultimately trying to manage.
2Garbage collection and write amplification▾

Eventually a block full of mostly-invalid pages must be reclaimed: valid pages are copied elsewhere, then the block is erased. Those copies are writes the host never asked for — write amplification (WA). GC competes with foreground I/O for the same internal flash bandwidth, which is why it shows up as latency spikes.

Now you're ready: most mechanisms in this paper — ZNS, FDP, retention-class placement — exist to reduce GC-driven write amplification by keeping similar-lifetime data together. SplitFTL is a partial exception: it's not intrinsically a WA-reduction mechanism — it supplies the control, classification, and placement path that lets mechanisms like ZNS deliver that reduction.
3SSD controller anatomy: HIL, FTL, FCC▾

Inside the controller: HIL exchanges commands with the host over NVMe queue pairs; the FTL does address translation and flash management; FCCs turn scheduled work into chip-level commands. On-chip SRAM buffers host I/O data; off-chip DRAM holds the FTL's mapping table and GC bookkeeping; architectures that also use DRAM as an extended write buffer additionally rely on PLP supercapacitors to flush that volatile buffer to NAND on power loss.

Now you're ready: SplitFTL (card 7) is exactly this FTL being pulled apart — a thin piece stays on the device, the rest moves upstream.
4Parallelism: channels, chips, dies, planes▾

An SSD hides flash's slowness by working on many pieces of it at once. The controller fans out over several independent channels; each channel connects multiple chips (packages); each chip has multiple dies that execute commands independently; each die splits into planes holding blocks and pages. GC, host reads, and host writes all compete for this same hierarchy.

Now you're ready: this is the internal bandwidth that NAND-I/O timing (ONFI) and one-shot programming (card 6) are measured against.
5Host-directed placement — ZNS and FDP▾

Instead of letting the device guess which writes belong together, two interfaces let the host say so. ZNS divides capacity into append-only zones: the host writes each zone sequentially and resets it as a unit, so the device never needs page-level GC at all. FDP is softer: the host tags writes with a lifetime hint, and the device groups similarly-tagged data into isolated Reclaim Units — GC still happens, but write amplification drops because invalidation is less scattered.

Now you're ready: the KV-cache case study (How It Works §6) is ZNS applied to request data that is naturally either short-lived or long-lived.
6Dense media: QLC, pSLC caching, one-shot programming▾

QLC packs 4 bits per cell — more capacity, slower and more interference-prone than TLC/SLC. Drives buffer bursty writes in a faster pSLC region (cells temporarily run in single-bit mode) before "destaging" to QLC. And QLC increasingly uses one-shot programming: all four pages of a wordline are written in a single complex pass, rather than four separate passes — this changes write timing fundamentally, not just its speed.

Now you're ready: MQSim 2.0's media model (ONFI 6.0 timing + configurable pSLC + one-shot programming) is this card turned into simulator code.
7Pulling the FTL apart: SplitFTL and DPUs▾

Several production systems (Pure Storage DirectFlash, Alibaba/Solidigm CSAL, AWS Nitro, NVIDIA BlueField) move part of flash management off the SSD: a thin device-resident layer still handles ECC, bad blocks, and coarse placement, while an upstream hostFTL — on a host, array controller, or DPU — owns zone-level mapping and cross-device policy like globally coordinated GC. The paper's umbrella name for this family is SplitFTL.

Now you're ready: MQSim 2.0 treats SplitFTL as a first-class, configurable abstraction — not a special case bolted onto one simulator.
8Disaggregation over NVMe-oF/RDMA▾

NVMe-oF extends the NVMe protocol across a network fabric, commonly over RDMA (here RoCE v2), so a host's storage commands can reach SSDs it isn't directly attached to. This is how a DPU-resident SplitFTL becomes reachable from many hosts at once — but it adds a fabric hop with its own bandwidth cap and queueing behavior, on top of the backend media.

Now you're ready: the paper's disaggregated validation target is exactly this — hosts, over RDMA, to a DPU, to a 24-SSD backend pool.
The whole story in one place

MQSim 2.0 in a nutshell

The problem, the composable fix, and the numbers that back it up.

Modern storage design spans four layers that used to be studied — and simulated — mostly in isolation: the media itself (dense QLC with pSLC caching and one-shot programming), host-directed placement (ZNS, FDP), control-plane decomposition (SplitFTL across device, host, or DPU), and fabric transport (NVMe-oF/RDMA for disaggregated deployments). These layers are coupled: a change that reduces device-side garbage collection can simply expose a transport or upstream-control bottleneck instead, and host-side placement changes how much benefit a media-level optimization actually delivers.

Existing SSD simulators don't span this regime — each models a device behind a fixed interface, or extends one mechanism (ZNS, or FDP) at a time. MQSim 2.0 is a composable storage-system simulator: host interfaces, control logic, interconnect, buffering, and media are separate components with explicit timing, assembled into either a direct-attached topology or a disaggregated one (hosts → RDMA → DPU-resident SplitFTL → backend SSD pool), configured from one schema.

It's grounded against real hardware on both paths: a TLC NVMe Gen5 SSD (direct-attached) and a real 24-SSD DPU-based enclosure (disaggregated), with throughput/latency MAPE of 7.9%/3.5% and 4.4%/4.8% respectively. A KV-cache case study then uses the framework end to end — retention-aware placement on ZNS backends behind a DPU-resident classifier — cutting write amplification by 48% and P99 latency by 31% versus a conventional JBOF baseline.

🗃️ Key takeaways

  • Media, placement, control, and transport are coupled — fixing one can just relocate the bottleneck to another.
  • MQSim 2.0 models them as composable components, not one device-centric blob, covering both local and disaggregated topologies.
  • SplitFTL is modeled as a first-class abstraction: a thin device layer plus an upstream hostFTL that can run on a host, array controller, or DPU.
  • Validated against real hardware on both paths: 7.9%/3.5% (TLC SSD) and 4.4%/4.8% (24-SSD DPU enclosure) throughput/latency MAPE.
  • A single remote node's observable bandwidth caps at ~7 GB/s despite far larger backend media bandwidth — a bottleneck a device-only model would miss entirely.
  • KV-cache case study: ZNS retention-class placement behind SplitFTL cuts WA by 48%, P99 latency by 31%, vs JBOF.
  • The paper is explicit that these gains come from the evaluated end-to-end design, not an intrinsic property of SplitFTL by itself.
Seven everyday pictures

How to think about MQSim 2.0

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Composable subsystem

A modular stereo, not a boombox

A boombox is one sealed unit — swap the amplifier and you've bought a new boombox. A modular stereo has a separate turntable, amp, and speakers, each with its own spec sheet, connected by standard cables. MQSim 2.0 treats a storage system the same way: media, placement, control, and transport are separate components with their own timing, so you can swap in a DPU-resident SplitFTL or a disaggregated fabric without rebuilding the whole simulator.

Where it breaks: stereo components rarely change each other's behavior once connected; these storage layers actively do — a placement change alters how much GC the media layer does, which is the whole point of studying them together.
Host-directed placement · ZNS

A library shelf vs. a junk drawer

A library shelf is filled left to right, book by book, and emptied by removing a whole run of returned books at once — no sorting needed. A junk drawer accepts items anywhere and, when full, someone has to dig through it to find what's still useful before throwing the rest out. ZNS is the shelf: append-only, reset as a unit, no device-side GC. Conventional random placement is the drawer — exactly what garbage collection must sort through.

Where it breaks: a library shelf doesn't care about lifetime mixing within a run; ZNS's benefit specifically depends on the host grouping similar-lifetime data into a zone — a zone full of mixed-lifetime books is just a slower drawer.
Host-directed placement · FDP

Luggage tags, not boarding passes

ZNS is like requiring every passenger to board one gate in strict order. FDP is softer: you just tag your luggage "short trip" or "long trip," and ground crew sorts bags with matching tags onto the same cart — faster unloading later, without forcing passengers through a single gate. That's FDP's Reclaim Units: host-supplied lifetime hints, device-side grouping, GC still happens but on far less scrambled data.

Where it breaks: mis-tagged luggage just goes to the wrong cart; FDP hints that don't match real lifetime similarly waste the Reclaim Unit's benefit without breaking anything — unlike ZNS, where a sequential-write violation is a protocol error, not just inefficiency.
Control decomposition · SplitFTL

A branch office and a regional hub

A bank branch handles local tellers, cash drawers, and the vault combination — but account balances and fraud rules live at a regional hub that coordinates across every branch. Neither could do the other's job efficiently alone. SplitFTL mirrors this: the device keeps ECC, bad-block handling, and coarse placement local (fast, physical); the hostFTL, upstream on a host or DPU, owns zone mapping and cross-device policy like globally coordinated GC — the things that benefit from seeing the whole pool.

Where it breaks: a bank hub rarely sits on the critical path of a single withdrawal; the hostFTL does sit on the storage-control path, so the fabric hop between device and hostFTL (next card) is a real added latency, not just an administrative layer.
Disaggregation · The network cap

A reservoir behind a garden hose

A reservoir can hold — and release — enormous volumes of water, but if it drains through one garden hose, the hose decides the flow rate, not the reservoir. The paper's 24-SSD backend can deliver roughly 338 GB/s of raw media bandwidth in aggregate, but a single remote node connected over one RDMA NIC port observes throughput capped near 7 GB/s — the fabric path is the hose.

Where it breaks: a hose's limit is fixed; a fabric's isn't — more NIC ports, more remote nodes, or a different queue depth changes the cap, which is exactly the parameter space MQSim 2.0 is built to sweep.
The retention-class case study · Count-min sketch

A bouncer's mental tally, not a guest list

A bouncer at a busy club doesn't keep a perfect guest list — they keep a rough mental tally of who's come back repeatedly, good enough to separate "regular" from "one-timer" without ever writing anything down. A count-min sketch does the same for KV-cache writes: a small, approximate structure estimates reuse frequency well enough to route data into a short- or long-retention ZNS zone, without the cost of tracking every key exactly.

Where it breaks: a bouncer can be fooled by a disguise; a count-min sketch can be fooled by hash collisions (over-counting), which is why it's a probabilistic classifier, not a perfect one — acceptable here because misclassifying a few objects costs a little WA, not correctness.
Validation · MAPE, not a pass/fail stamp

A weather forecast's track record

"80% chance of rain" isn't validated by one correct or wrong day — it's validated by checking, across many forecasts, how close the predicted probability tracked reality on average. MAPE does the same for the simulator: average the percentage error across 20 measured operating points (queue depths × workload mixes), rather than demanding exact agreement at every single one.

Where it breaks: a forecast's error is usually symmetric noise; the paper's sequential offsets are systematic — sequential writes overshoot by 11–15% at larger queue depths, sequential reads deviate by 3–12% — closer to a thermometer reading consistently warm, which still supports relative comparisons but not absolute ones.
The full explanation

How it actually works

From the device-centric gap to the validated numbers, with the paper's architecture rebuilt as diagrams.

1 · Why device-centric simulation falls short

Prior SSD simulators bind host interface, control logic, buffering, and media into one device-resident model, or extend a single mechanism (ZNS, or FDP) at a time. That's adequate when the question is "how does this one SSD behave," but modern designs don't ask that question in isolation: a KV-cache request in a disaggregated serving system crosses host-directed placement, a DPU-resident hostFTL, NVMe-oF/RDMA transport, and backend flash before it completes. A device-only model can miss the actual end-to-end bottleneck entirely — exactly what happens in the paper's own 24-SSD enclosure, where the fabric path, not the media, caps observed throughput at QD=8.

2 · Two deployment topologies, one schema

MQSim 2.0 supports a local topology — a host's IOFlows reach an SSD over a simulated PCIe path, backward-compatible with MQSim 1.0 — and a disaggregated topology, where one or more hosts reach a DPU over simulated RDMA/RoCE, the DPU runs SplitFTL's hostFTL (global mapping, placement), and dispatches commands to a backend pool of SSDs over PCIe. Device interface (conventional NVMe, ZNS, FDP) and deployment topology are orthogonal: any interface can run locally or as a disaggregated backend, configured from one file.

3 · Modeling modern storage behavior

Write-path and acknowledgment: enterprise SSDs acknowledge a write once it lands in a power-protected staging layer (PLP-DRAM, SRAM), while programming to NAND continues in the background. MQSim 2.0 decouples host-visible acknowledgment timing from the actual backend program, matching microsecond-scale foreground latency while still accounting for the background resource pressure it creates.

Media and buffering: backend timing follows ONFI 6.0 NAND-I/O timing, with a configurable pSLC region (promotion/demotion policy, sizing, fold-back thresholds) and explicit one-shot programming timing for TLC/QLC — distinct from, and slower-converging than, multi-pass programming.

Host-directed interfaces: for ZNS, append-only write constraints, zone state transitions, and reset semantics are modeled so upstream logic can enforce sequential placement and its effect on GC/backend utilization can be studied directly. For FDP, host-supplied placement identifiers and controller-side segregation into reclaim groups/units are modeled to study how explicit hints affect placement and write amplification.

4 · SplitFTL as a configurable control-plane split

SplitFTL isn't a special mode — it's a first-class simulator abstraction. A thin device layer keeps media-specific work (ECC, bad blocks, coarse placement); an upstream hostFTL, instantiated on the DPU in the disaggregated topology, owns zone-level mapping and cross-device policy such as globally coordinated garbage collection. This split is what lets MQSim 2.0 study, say, retention-aware classification running on a DPU while backend SSDs run plain ZNS, without hand-wiring a one-off simulator.

5 · Validation: two targets, two scopes

The TLC NVMe Gen5 SSD (3.84 TB, 7% over-provisioning) validates the direct-attached device path: measured vs. simulated throughput and latency across random/sequential read/write sweeps and queue depths. The 24-SSD DPU-based enclosure (4 active-active DPUs, 40 GB/s RoCE v2 per DPU, unloaded fabric RTT not legible in the source extraction) validates the end-to-end disaggregated path — DPU SplitFTL, backend SSDs, and NVMe-oF/RoCE transport together. The paper is explicit that these validate the evaluated configurations end to end, not every individually configurable mechanism (notably, the pSLC and one-shot QLC models aren't independently hardware-validated in this work).

6 · The KV-cache case study, step by step

Production KV-cache workloads skew heavily: most entries are short-lived, a smaller fraction (system prompts, popular prefixes) get reused across sessions. The case study assumes 90% of entries are short-retention — an illustrative workload parameter, not a universal claim. A DPU-resident SplitFTL classifies each write using a lightweight count-min sketch, then routes it to a dedicated ZNS zone: Class A (short, reclaimed after a brief window) or Class B (long, retained ~2 weeks, reclaimed independently). Against a JBOF baseline that stripes writes blindly across SSDs and lets device-resident FTLs fight mixed-lifetime GC alone, this reduces write amplification by 48% and P99 latency by 31%. The paper attributes the gain primarily to lifetime separation via ZNS; SplitFTL supplies the classification and placement-control path across the backend pool, and the authors caution the result is the evaluated end-to-end design, not proof that SplitFTL alone is beneficial.

⚠
Scope limit the paper states directly: validation is configuration-specific, not exhaustive — it covers the evaluated end-to-end paths, and the KV-cache study uses a parameterized retention distribution rather than a production trace replay. Sensitivity to other retention distributions and backend configurations is left to future work.
Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own figures — recomputed to check they hold together.

① Why a device-only model would mislead you here

The paper reports per-SSD sequential bandwidths of 14.1 GB/s (read) / 10.6 GB/s (write), 24 SSDs in the enclosure, but a single remote node's observed throughput caps near 7 GB/s. What does the gap tell you?

  1. Aggregate raw backend bandwidth ≈ 24 × 14.1 GB/s = 338.4 GB/s of sequential read capability across the pool (each SSD is additionally shared between 2 DPUs, so per-DPU per-SSD share ≈ 7.05 GB/s).
  2. A single node's observed cap is ~7 GB/s — roughly 48× smaller than the raw backend figure.
  3. The gap isn't a media limitation — it's the single RDMA NIC port on that one remote node. The paper notes enclosure throughput saturates by QD=8 for exactly this reason.
  4. A device-centric simulator would model the 14.1 GB/s SSD correctly and still predict the wrong system throughput, because the bottleneck lives in the transport layer it doesn't represent.
💡
Insight: this is precisely the coupling argument from the Big Idea tab, now with real numbers — composability isn't a nice-to-have, it's what gets the bottleneck right.

② The write-bandwidth collapse that motivates host-directed placement

On a 16 TB QLC SSD shared by eight tenants, sequential write bandwidth has been reported to fall from 3000 MiB/s to 400 MiB/s without a host layer reshaping the stream.

  1. Absolute drop: 3000 − 400 = 2600 MiB/s lost.
  2. Relative drop: 2600 ÷ 3000 = 86.7% — the drive retains only about 13% of its rated sequential write bandwidth under concurrent multi-tenant writes.
  3. Why: unshaped small writes from eight tenants interleave into the same indirection units on a dense QLC drive, forcing far more internal GC than a single reshaped sequential stream would.
  4. The fix cited: a host-side layer (Solidigm/Alibaba's CSAL) reshapes the write stream before it reaches the drive — conceptually the same host-directed-placement idea as ZNS/FDP, applied upstream of the SSD entirely.
🗃️
Insight: an 86.7% bandwidth collapse is the kind of effect that's invisible if you only benchmark the drive in isolation — it only appears under the multi-tenant access pattern the host layer is built to reshape.

③ Sizing the page-mapping problem that motivates ZNS

For a 24-drive enclosure of 61.44 TB QLC SSDs, the paper states a conventional 4 KB page-mapped design would need "up to ~1.4 TB" of mapping DRAM across the enclosure. Check it.

  1. Total enclosure capacity: 24 × 61.44 TB = 1,474.56 TB = 1.47456 × 1015 bytes.
  2. Number of 4 KB pages: 1.47456 × 1015 ÷ 4096 = 3.6 × 1011 pages (360 billion) — note this divides out exactly.
  3. Assume a 4-byte (32-bit) physical-page-address entry per mapping, the typical minimum for page-level FTL tables: 3.6 × 1011 × 4 bytes = 1.44 × 1012 bytes ≈ 1.44 TB.
  4. Matches the paper's figure ("up to ∼1.4 TB") almost exactly — confirming the implied assumption of ~4-byte mapping entries.
💡
Why it matters: ZNS replaces this page-granular table with a zone-granular one — thousands of zones instead of hundreds of billions of pages — which is why the paper frames ZNS as simplifying flash-management metadata, not just reducing write amplification.

④ Reading the validation numbers correctly

TLC SSD throughput MAPE is 7.9% across 20 data points, with "19 of 20 points fall below 13%." What does that tell you about the distribution of error, not just its average?

  1. MAPE = 7.9% is the mean of 20 individual percentage errors — it can hide a skewed distribution.
  2. 19/20 points < 13% tells you the bulk of operating points are tightly matched, well below even the mean-adjacent threshold.
  3. The one outlier region: sequential writes at 128 KB overshoot hardware by 11–15% at larger queue depths — a single systematic offset, not random scatter.
  4. Consistent direction (overshoot, not both over and under) means relative comparisons between two simulated designs remain trustworthy even where absolute values drift.
📎
Same pattern holds for latency: read MAPE 3.1% (max 6.1%) is tighter than write MAPE 3.9% (max 12.8%, at QD=32, 90% write) — write-path queueing under heavy, write-skewed load is where the model is least precise.

Problem 1 · easy
The KV-cache case study reduces write amplification by 48% and P99 latency by 31% over JBOF. Does this prove SplitFTL, as a mechanism, is intrinsically beneficial?
Show answer
No. The paper attributes the gains primarily to lifetime separation via ZNS zones; SplitFTL supplies the architectural location for the DPU-resident classifier and placement-control path across the backend pool. The authors explicitly state the reported improvements represent the evaluated end-to-end design and should not be read as an intrinsic benefit of SplitFTL alone.Misconception: that a headline number validates the mechanism named in the section title. Read which component the paper credits the gain to, not just which section it appears in.
Problem 2 · medium
The 24-SSD backend can deliver roughly 338 GB/s of raw sequential read bandwidth, yet a single remote node observes throughput capped near 7 GB/s, saturating by QD=8. More SSDs, more throughput — so why doesn't adding SSDs help this node?
Show answer
Because the bottleneck for that measurement isn't the media pool — it's the single RDMA NIC port on the one remote node used to collect the measurement. Backend media bandwidth only helps if the path reaching the host can carry it; here that path is capped well below the pool's aggregate capability.Misconception: that backend capacity (SSD count × per-SSD bandwidth) directly predicts observed throughput. It only does so when the transport layer isn't the limiting factor — exactly the coupling a device-only simulator would miss.
Problem 3 · easy
ZNS and FDP are both described as "host-directed placement." What's the key structural difference?
Show answer
ZNS enforces sequential, append-only writes within a zone and eliminates device-side GC for zoned capacity — the host must write in order. FDP is softer: the host attaches lifetime hints to writes, and the device groups similarly-tagged data into Reclaim Units, but GC still happens — write amplification drops because invalidation is less scattered, not because GC is removed.Misconception: that ZNS and FDP are interchangeable "placement hint" mechanisms. ZNS changes the write contract (sequential-only); FDP changes only grouping, leaving random writes and device-side GC in place.
Problem 4 · medium
TLC SSD throughput MAPE is reported as 7.9% across 20 data points. One point has measured throughput 500 K IOPS and simulated 540 K IOPS. What's that single point's percentage error, and could it alone explain the 7.9% average?
Show answer
|540 − 500| ÷ 500 × 100 = 8% — close to, but not exactly, the reported overall average. One point can't "explain" the average; MAPE is the mean of all 20 individual percentage errors, so this point is just roughly in line with the aggregate, not unusually high given the paper's note that 19/20 points fall below 13%.Misconception: treating a reported MAPE as a per-point error bound. It's an average — individual points can exceed it (up to the stated max) while others fall well under it.
Problem 5 · hard
A 24-drive enclosure of 61.44 TB QLC SSDs would need up to ~1.4 TB of DRAM for a conventional 4 KB page-mapped FTL table. Walk through why zone-granular mapping (as in ZNS) avoids this without inventing a specific zone size.
Show answer
Page-level mapping needs one entry per 4 KB page — on this enclosure, 3.6 × 1011 entries, which is why the total reaches ~1.4 TB even at just 4 bytes/entry. Zone-granular mapping needs one entry per zone instead, and a zone spans many contiguous pages (commonly on the order of GBs), so the entry count drops by many orders of magnitude — thousands of zones per drive rather than tens of billions of pages. The exact DRAM savings depend on the configured zone size, which the paper doesn't fix, but the mechanism (far fewer, far coarser mapping entries) is what collapses the ~1.4 TB figure.Misconception: that ZNS's metadata benefit requires knowing an exact zone size to understand. The qualitative mechanism — fewer, coarser entries — holds regardless of the specific number; only the precise DRAM figure needs that input.
Problem 6 · medium
MQSim 2.0's authors describe using AI-assisted coding tools (via structured contributor rule files) while implementing ZNS support and refactoring to C++17. What does the paper explicitly say this workflow is — and isn't — evidence of?
Show answer
The paper states this is "an extensibility aid rather than a correctness mechanism" — it lowers the barrier for contributors (human or AI-assisted) to understand module boundaries and conventions. Simulator fidelity is assessed independently, through the hardware validation against the TLC SSD and the 24-SSD enclosure, not through the development workflow used to build it.Misconception: that "AI-assisted development" implies anything about simulator accuracy. The paper is careful to separate how the code was written from whether the resulting model is validated.
Problem 7 · medium
The paper validates MQSim 2.0 against a TLC SSD and a 24-SSD DPU enclosure. Does this mean every modeled mechanism — including the pSLC cache and one-shot QLC programming models — has been independently hardware-validated?
Show answer
No, and the paper says so directly in its limitations: validation is configuration-specific, confirming the evaluated end-to-end paths, "not every individually configurable mechanism," and explicitly calls out that this workshop paper does not provide separate hardware validation of the pSLC and one-shot QLC models.Misconception: that an overall MAPE figure certifies every sub-model used to produce it. A composite validation confirms the pipeline that was exercised, not every independently configurable component inside it.
Problem 8 · hard
Sequential write bandwidth on a shared 16 TB QLC SSD falls from 3000 MiB/s to 400 MiB/s without host-side reshaping. If a host layer like CSAL instead achieves, say, 2400 MiB/s, express that recovery two ways: as a percentage of the original 3000 MiB/s, and as a multiple of the unshaped 400 MiB/s.
Show answer
As a share of the original rating: 2400 ÷ 3000 = 80% of peak sequential write bandwidth recovered. As a multiple of the unshaped figure: 2400 ÷ 400 = 6× improvement over the unreshaped multi-tenant case. (These are illustrative numbers for the exercise, not a figure reported in the paper — the paper cites only the 3000→400 MiB/s collapse itself.)Misconception: that "percentage of original" and "multiple of the degraded baseline" are the same framing. They answer different questions — how much capability is left vs. how much better than the worst case — and papers often report only one.

Q1What's actually new in MQSim 2.0 versus MQSim 1.0?▾
MQSim 1.0 modeled a single multi-queue SSD device. MQSim 2.0 redesigns the execution model around composable subsystems, adding ZNS, FDP, QLC/pSLC media with one-shot programming, ONFI 6.0 NAND-I/O timing, DPU-resident SplitFTL, NVMe-oF/RDMA fabric transport, and multi-host shared-storage topologies — none of which the original supported (Table 1). Local-topology MQSim 1.0 workflows remain backward-compatible.
Q2Why can't you just chain existing ZNS and FDP simulators together to study this?▾
Because the layers are coupled, not independent: a placement decision changes device-side GC behavior, which changes the apparent benefit of a media-level mechanism, and a transport bottleneck can dominate both. Stitching together separate tools built around different device-centric abstractions requires extending, integrating, and re-validating each one — the gap MQSim 2.0 closes by modeling them as one composable framework from the start.
Q3What is SplitFTL, concretely, and who builds it in practice?▾
SplitFTL is the paper's umbrella term for flash-management decomposition: a thin device-resident layer (ECC, bad blocks, coarse placement) plus an upstream hostFTL (zone mapping, cross-device policy) running on a host, array controller, or DPU. The paper cites Pure Storage DirectFlash, Alibaba/Solidigm CSAL, AWS Nitro, and NVIDIA BlueField as real instances of this family.
Q4ZNS vs. FDP — when would you pick one over the other?▾
ZNS gives the strongest guarantee (no device-side GC at all) but requires the host to write strictly sequentially per zone — a bigger software change. FDP is a lighter touch: tag writes with lifetime hints and let the device group them, while GC and random writes remain possible. The paper's own KV-cache case study picks ZNS because KV-cache objects have a natural "born-together-die-together" structure that matches zone semantics well.
Q5How rigorous is the validation, and what's its scope?▾
Two real hardware targets: a TLC NVMe Gen5 SSD (direct-attached path, 7.9%/3.5% throughput/latency MAPE) and a 24-SSD DPU-based enclosure (disaggregated end-to-end path, 4.4%/4.8%). Both validate the evaluated configurations as a whole, not every individually configurable sub-model — the paper names the pSLC and one-shot QLC models specifically as not independently hardware-validated here.
Q6Where do the KV-cache case study's gains actually come from?▾
Primarily from separating short- and long-lived KV objects into distinct ZNS zones, which reduces garbage-collection interference between mixed-lifetime data. SplitFTL provides the DPU-resident classifier (a count-min sketch) and the placement-control path across the backend pool that makes this separation possible at the system level — but the paper credits the mechanism (lifetime separation) rather than SplitFTL as an abstraction in isolation.
Q7Why does the 24-SSD enclosure's throughput saturate by QD=8 when the media could clearly go faster?▾
Because all measurements in this validation come from a single remote node connected over one RDMA NIC port, capping observable aggregate bandwidth at ~7 GB/s — far below the backend's combined media bandwidth. It's a transport bottleneck specific to the measurement setup, not a property of the SSDs.
Q8What is a count-min sketch doing inside a flash controller?▾
It's a small, approximate data structure that estimates how often a key (here, a KV-cache object) has been seen, without storing exact per-key counts. The DPU-resident SplitFTL uses it to cheaply classify writes into a short- or long-retention class before routing them to the matching ZNS zone.
Q9Is the "structured AI-coding rule files" feature part of what makes the simulator accurate?▾
No — the paper is explicit that this is an extensibility aid for contributors (human and AI-assisted), used while implementing ZNS support and the C++17 refactor. Simulator fidelity is assessed separately, through the hardware validation in Section 3.5.
Q10What's left for future work?▾
The paper flags broader workload sensitivity (beyond the evaluated 90%-short-retention KV-cache parameter), additional device-level validation — specifically independent hardware validation of the pSLC and one-shot QLC models — and sensitivity across alternative retention distributions and backend configurations for the KV-cache case study.

Glossary & further reading

Every term in one place, results at a glance, then a path to go deeper.

Core terms
MQSim 2.0Composable storage-system simulator modeling media, placement, control decomposition, and fabric transport in one framework, for local and disaggregated deployments.
SplitFTLDecomposed flash management: a thin device-resident layer plus an upstream hostFTL on a host, array controller, or DPU, owning zone mapping and cross-device policy.
ZNS (Zoned Namespaces)Append-only logical zones with host-managed sequential writes; eliminates device-side GC for zoned capacity.
FDP (Flexible Data Placement)Host-supplied lifetime hints that let the device group writes into isolated Reclaim Units, reducing write amplification without a sequential-write requirement.
DPU (Data Processing Unit)Network-attached compute card that can host upstream storage-control logic (the hostFTL) reachable from multiple hosts over NVMe-oF.
MAPEMean Absolute Percentage Error — the paper's validation metric, averaged across 20 measured operating points per target.
Count-min sketchA small, approximate frequency-estimation structure; used by the DPU-resident SplitFTL to classify KV-cache writes by reuse likelihood.
JBOFJust a Bunch Of Flash — SSDs with no shared/global control plane; the paper's baseline for the KV-cache case study.
Supporting terms
FTL / HIL / FCCFlash Translation Layer, Host Interface Logic, Flash Chip Controller — the three functional blocks of a conventional SSD controller.
GC / WAGarbage collection reclaims invalidated flash pages; write amplification is the resulting ratio of physical to logical writes.
pSLC / one-shot programmingA faster single-bit-per-cell buffering region in front of dense media; one-shot programming writes all pages of a QLC wordline in one pass.
ONFI 6.0The NAND-chip I/O timing standard MQSim 2.0's backend model follows.
NVMe-oF / RDMA / RoCE v2NVMe extended over a network fabric, here via RDMA over Converged Ethernet, connecting hosts to a DPU-resident SplitFTL.
Reclaim Unit / Reclaim GroupFDP's grouping structures: writes with matching lifetime hints are segregated into a Reclaim Unit within a Reclaim Group.
PLP (Power Loss Protection)Supercapacitor-backed circuitry that flushes a volatile DRAM write buffer to NAND on unexpected power loss.
KV-cachePer-request key-value state in LLM inference serving, offloaded to networked flash under tight tail-latency constraints.
