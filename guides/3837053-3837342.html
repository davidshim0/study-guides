Before you begin

Six concepts + the acronym soup

Skips generic memory-hierarchy/OS background you already have; focuses on SSD-controller and disaggregation specifics the paper leans on.

Quick glossary
FTLFlash Translation Layer — logical→physical address mapping + flash management.
HIL / FCCHost Interface Logic (talks to NVMe queues) / Flash Chip Controller (talks to NAND chips).
ZNSZoned Namespaces — append-only logical zones; host enforces sequential writes, device GC shrinks away.
FDPFlexible Data Placement — host tags writes with lifetime hints; device groups them into Reclaim Units.
SplitFTLThis paper's term for decomposed flash management: thin device layer (ECC, bad blocks) + upstream FTL (zone mapping, cross-device policy) on host/array/DPU.
DPUData Processing Unit — a NIC-attached compute node (e.g. BlueField) that can run storage control-plane logic.
NVMe-oF / RoCENVMe over Fabrics — NVMe semantics over a network; RoCE = RDMA over Converged Ethernet, one such fabric.
pSLC / QLC / TLCPseudo-SLC = flash cells temporarily run at 1 bit/cell for speed; QLC/TLC = 4/3 bits/cell, denser but slower and touchier.
ONFIOpen NAND Flash Interface — the timing spec for chip-level NAND I/O; v6.0 is current.
JBOFJust a Bunch Of Flash — SSDs exposed with no shared control-plane logic; this paper's baseline.
MAPEMean Absolute Percentage Error — the validation-accuracy metric used throughout (lower = better fidelity).

1Why flash forces out-of-place writes▾

NAND reads/programs at page granularity but erases at block granularity, and a written page can't be overwritten until its whole block is erased. So updates go to a fresh page, the old one is marked invalid, and a garbage collector (GC) later reclaims blocks by migrating survivors and erasing. GC steals the same internal bandwidth foreground I/O needs.

Now you're ready: nearly every mechanism in this paper (ZNS, FDP, SplitFTL) exists to control when and how GC happens, or to avoid it.
2Inside the controller: HIL → FTL → FCC▾

The Host Interface Logic terminates NVMe submission/completion queues; the FTL maps LBAs to physical pages and schedules GC; Flash Chip Controllers issue chip-level commands across channels/dies/planes. SRAM buffers host I/O; DRAM (often PLP-backed) holds the mapping table.

Now you're ready: MQSim 2.0's "composable subsystem" split is this same pipeline, but pulled apart into components with explicit timing instead of one monolithic device model.
3ZNS vs FDP — two ways to expose placement▾

ZNS gives the host append-only zones: writes must be sequential per zone, and a whole zone is reset at once — this eliminates device-side GC by construction. FDP is softer: the host tags each write with a lifetime hint, and the device internally groups same-lifetime data into Reclaim Units, cutting write amplification without forcing sequential writes.

Now you're ready: the KV-cache case study (Tab 5) chooses ZNS specifically because KV objects are "born-together-die-together" — a natural fit for zone-at-a-time reclaim.
4SplitFTL — moving control off the device▾

Instead of one FTL living entirely inside the SSD, SplitFTL keeps a thin device-resident layer (ECC, bad-block handling, coarse placement) and moves zone-level mapping and cross-device policy (e.g. globally coordinated GC) upstream — to a host, array controller, or DPU. Pure Storage DirectFlash, Alibaba/Solidigm CSAL, and AWS Nitro are production instances of this pattern.

Now you're ready: this is directly analogous to OS-managed DRAM/NVM tiering, where the hardware exposes primitives (like access-bit sampling) but a host-side controller (à la TPP) owns the placement policy across devices — here it's flash management that's been pulled up into software.
5Disaggregation over NVMe-oF/RDMA▾

NVMe-oF lets a host issue NVMe commands to storage across a network fabric instead of local PCIe. RDMA (here RoCE v2) lets that happen with low CPU involvement. A DPU can sit between hosts and a pool of backend SSDs, terminating the fabric on both sides and running SplitFTL logic in between.

Now you're ready: once storage crosses a fabric, the network — not the media — can become the bottleneck. That's exactly what the 24-SSD validation shows (Tab 5, worked example 2).
6Reading a MAPE-validated simulator▾

MAPE = mean of |simulated − measured| / measured, across a set of measurement points (queue depths, R/W mixes). Low overall MAPE with a few larger systematic outliers (always in the same direction) is a normal, trustworthy result: it means trend and relative comparisons hold even where absolute numbers drift a bit.

Now you're ready: the two validation figures in Tab 5 are exactly this kind of result — read the "systematic offset" callouts as the honest bounds of the model.
The whole story in one place

MQSim 2.0 in a nutshell

The gap in prior simulators, the fix, and what it unlocked.

Modern SSD-adjacent design spans four coupled axes: media (dense QLC with pSLC caching and one-shot programming), host-directed placement (ZNS, FDP), control-plane decomposition (SplitFTL logic living on a host, array controller, or DPU), and fabric transport (NVMe-oF/RDMA for disaggregated deployments). Prior simulators model one device behind a fixed interface, or extend one of these axes at a time — so studying a design that touches all four (e.g. a DPU-mediated SplitFTL serving KV-cache traffic over NVMe-oF to ZNS-backed QLC SSDs) means gluing together disjoint tools.

MQSim 2.0 rebuilds MQSim 1.0's device-centric execution model as a composable storage subsystem: host interfaces, control logic, interconnect, buffering, and media are separate components with explicit timing, so the same framework expresses a direct-attached local SSD or a multi-host, DPU-mediated, disaggregated deployment. It adds QLC/pSLC media modeling with one-shot programming, ONFI 6.0 NAND-I/O timing, ZNS/FDP interface semantics, SplitFTL as a first-class abstraction, and an NVMe-oF fabric model.

The payoff: validated against a TLC NVMe Gen5 SSD (7.9%/3.5% throughput/latency MAPE) and a real 24-SSD DPU-based enclosure (4.4%/4.8%), it correctly reproduces both a device-side saturation knee and a fabric-side bandwidth cap — the enclosure's 24 SSDs offer far more aggregate media bandwidth than the ~7 GB/s a single remote node can actually see through one RDMA NIC port. A KV-cache case study built on the framework cuts write amplification 48% and P99 latency 31% versus a JBOF baseline, by separating short- and long-lived KV objects into distinct ZNS zones under a DPU-resident SplitFTL classifier.

🍯 Key takeaways

  • Media, placement, control-plane location, and transport are coupled — optimizing one can just move the bottleneck to another.
  • MQSim 2.0 models the SSD as a composable subsystem, not a monolithic device — same schema for local and disaggregated topologies.
  • SplitFTL is a first-class abstraction: a thin device layer + an upstream FTL (host/array/DPU) sharing zone mapping and cross-device GC policy.
  • Validated end-to-end: 7.9%/3.5% MAPE (TLC SSD), 4.4%/4.8% MAPE (24-SSD DPU enclosure).
  • A device-only model would miss the fabric cap; a fabric-only model would miss device GC effects — MQSim 2.0 captures both in the same run.
  • KV-cache + ZNS + SplitFTL case study: −48% write amplification, −31% P99 latency vs JBOF.
Five everyday pictures

How to think about MQSim 2.0

Each stands alone. Every card names where the picture stops holding.

The core idea · Coupled renovation

Renovating one room in an old house

Rewire the kitchen without checking the panel in the basement and you may just move the overload somewhere else. Media, placement, control-plane location, and network are load-bearing walls in the same house: change one and the strain shows up in another. MQSim 2.0 is built to let you renovate — and inspect — all four rooms in one model.

Where it breaks: not every study needs all four axes; a pure media-timing question can still be answered with the device path alone.
The design · Composable subsystem

Building blocks, not a sealed box

A device-centric simulator is a sealed appliance: you can measure what goes in and out, but not rewire its insides. MQSim 2.0 treats host interface, control logic, interconnect, and media as separate blocks with explicit timing and message passing, so the same block set snaps into a local SSD or a whole disaggregated topology.

Where it breaks: composability adds configuration surface — more knobs mean more ways to build an unvalidated combination (see the paper's own limitations note).
SplitFTL · Control decomposition

A regional office, not a lone shopkeeper

A single shopkeeper (a device-resident FTL) only ever sees their own shelf. A regional office (an upstream SplitFTL, on a host/array/DPU) sees inventory across every store and coordinates restocking globally — exactly what lets it run cross-device GC policy. Each store still handles its own till (ECC, bad blocks) locally.

Where it breaks: the office adds a round-trip; local decisions that don't need coordination can be slower going through it, which is why the split keeps device-local functions device-local.
Disaggregation · The real bottleneck

A ten-lane highway feeding a one-lane tollbooth

The 24-SSD enclosure's flash chips can move far more data than any single client will ever see — the measured node is capped at ~7 GB/s by its one RDMA NIC port, long before backend media saturates. A device-only model, tuned purely on chip timing, would never predict that tollbooth.

Where it breaks: add more client ports or DPUs and the cap moves; the tollbooth is a property of the measured topology, not a law of the architecture.
The case study · Sorting by lifetime

Separate bins for short- and long-stay guests

Mixing a hotel's one-night guests with its long-term residents on the same floor means constant turnover disruption near the permanent rooms. Put them on separate floors (ZNS zones) and each can be "reset" — cleared and reused — on its own schedule. The KV-cache design does exactly this: short-lived and long-lived KV objects get their own zones, so one class's churn never fragments the other's.

Where it breaks: real KV-cache retention isn't a clean binary — the paper's 90%/10% split is an illustrative workload parameter, not a universal ratio.
The full explanation

How it actually works

From composable topology, through device-behavior modeling, to the KV-cache case study.

1 · Two deployment topologies, one schema

In the local topology, a host with multiple IOFlows connects over simulated PCIe to a local SSD — backward-compatible with MQSim 1.0. In the disaggregated topology, one or more hosts talk over simulated RDMA/RoCE to a DPU running the SplitFTL hostFTL (global mapping, placement), which dispatches to a pool of backend SSDs over PCIe. Device interface (NVMe/ZNS/FDP) and deployment topology are configured independently — any SSD type can sit locally or behind the DPU.

2 · Modern device behavior

Writes are acknowledged once data reaches a power-loss-protected staging layer (PLP-DRAM / SRAM), decoupling host-visible latency from background programming. The media model adds ONFI 6.0 NAND-I/O timing, a configurable pSLC cache (promotion/demotion policy, region sizing, fold-back thresholds), and one-shot programming for TLC/QLC — where all pages of a wordline program together in one complex pass, with its own distinct timing profile rather than several independent passes.

3 · Host-directed placement

For ZNS: append-only write constraints, zone state transitions, and reset semantics, so upstream logic can enforce sequential placement and its effect on GC/backend utilization can be studied. For FDP: host-supplied placement identifiers, segregated by the controller into reclaim groups and Reclaim Units.

4 · SplitFTL as a first-class abstraction

A thin device layer (ECC, bad blocks, coarse placement) pairs with an upstream FTL (zone-level mapping, cross-device policy such as globally coordinated GC) that can run locally or DPU-resident, with configurable DPU compute budget — letting the same policy be evaluated at different control-plane locations without changing the device model underneath it.

📎
Reader's-eye framing: SplitFTL's device/upstream split is architecturally the same shape as host-driven DRAM/NVM tiering — a thin local mechanism (media ECC / hardware access tracking) paired with a policy layer elsewhere (host FTL / OS tiering daemon) that sees the whole pool and can coordinate across devices. Neither the paper nor this guide claims a direct equivalence; the parallel is structural.

5 · Validation methodology

Throughput is swept across queue depths for random/sequential read/write; latency is swept across mixed R/W ratios at fixed queue depths. MAPE is computed per point and averaged. The TLC SSD run: 7.9% throughput MAPE (19/20 points <13%), 3.5% latency MAPE, with two systematic, same-direction offsets (128 KB sequential writes overshoot 11–15% at high QD; 128 KB sequential reads deviate 3–12%). The 24-SSD enclosure run: 4.4% throughput MAPE, correctly reproducing NIC saturation by QD=8; 4.8% latency MAPE, with the largest gap (up to 14%) at QD=32/high-write attributed to cross-DPU PCIe contention the model doesn't capture in detail.

6 · The KV-cache case study

A DPU-resident SplitFTL classifies writes into two retention classes with a lightweight count-min sketch — short-lived (illustrative 90% of entries) vs long-lived (e.g. system prompts, popular prefixes). Each class maps to a dedicated ZNS zone, reclaimed on its own schedule, avoiding the mixed-lifetime placement that normally drives GC overhead. Against a JBOF baseline that stripes writes blindly across device-resident FTLs: −48% write amplification, −31% P99 latency.

⚠
Attribution, per the paper: the gain comes primarily from lifetime separation via ZNS zoning; SplitFTL supplies the DPU-resident classifier and placement-control path across the backend pool. The authors are explicit this is not evidence of an intrinsic SplitFTL performance benefit on its own.
Follow the numbers

Worked examples

Four traces through the paper's actual figures.

① Where the fabric caps the enclosure

Per-SSD sequential read bandwidth is 14.1 GB/s; the enclosure has 24 SSDs, each shared by 2 DPUs. A single remote node is measured over one RDMA NIC port.

  1. Raw aggregate media bandwidth: 24 × 14.1 GB/s = 338.4 GB/s across the enclosure (upper bound, ignoring the 2-DPU sharing).
  2. Per-DPU fabric link: 40 GB/s per DPU over RoCE v2 — already ~8.5× below raw media bandwidth.
  3. Observed single-node cap: ~7 GB/s, set by one RDMA NIC port — roughly 48× below the raw aggregate media bandwidth.
  4. Consequence: throughput "saturates by QD=8" (paper, §3.5) not because flash runs out of capacity, but because the measurement path — one port — is full.
🍯
Insight: a device-only simulator, calibrated purely on NAND timing, would predict throughput climbing well past what the fabric ever delivers — exactly the failure mode MQSim 2.0's composable model is built to avoid.

② Why host reshaping matters on dense QLC

A 16 TB QLC SSD shared by 8 tenants: sequential write bandwidth falls from 3000 MiB/s to 400 MiB/s under concurrent writes, unless a host layer (e.g. CSAL) reshapes the stream.

  1. Relative drop: (3000 − 400) / 3000 = 86.7% loss in sequential write bandwidth from tenant interleaving alone.
  2. Remaining fraction: 400 / 3000 ≈ 13.3% of nominal bandwidth survives without reshaping.
  3. Why: dense QLC's large indirection units make unshaped, interleaved small writes internally non-sequential — the exact pattern host-side write-stream shaping (or FDP/ZNS placement) is designed to prevent.
💡
This is the concrete, quoted motivation for modeling placement and media together — a media-only model can't see tenant interleaving; a placement-only model can't see the QLC penalty it's avoiding.

③ Mapping-table overhead: page-mapped vs zone-mapped

24 drives × 61.44 TB QLC, conventional 4 KB page-mapped FTL, 4-byte physical-page-number entries.

  1. Enclosure capacity: 24 × 61.44 TB = 1474.56 TB = 1.4756 × 1015 bytes.
  2. Pages at 4 KB granularity: 1.4756 × 1015 / 4096 ≈ 3.60 × 1011 pages.
  3. Mapping DRAM at 4 B/entry: 3.60 × 1011 × 4 B ≈ 1.44 × 1012 B ≈ 1.4 TB — matching the paper's figure.
  4. Zone-granularity mapping (ZNS) replaces per-page entries with per-zone entries — orders of magnitude fewer, at the cost of append-only write semantics.
📎
Production SSDs usually avoid the full 1.4 TB by using coarser mappings already — but coarsening a page-mapped FTL trades away exactly the write-amplification control that motivates ZNS in the first place.

④ The validation numbers, read correctly

TLC SSD: throughput MAPE 7.9% over 20 points, 19/20 <13%; sequential writes at 128 KB overshoot by 11–15% at larger queue depths.

  1. 19/20 points <13% error means one point is an outlier pulling on the mean, or several are near the 13% edge — either way, the bulk of the sweep is tight.
  2. "Overshoot by 11–15%, consistent in direction" is different from noisy ±15% scatter: a consistent bias means A-vs-B comparisons (e.g. "does mechanism X improve sequential-write throughput?") still hold even though absolute numbers run slightly high.
  3. Latency MAPE (3.5%) tighter than throughput MAPE (7.9%) — the paper notes this pattern holds at both validation targets, suggesting the timing model is more precisely calibrated than the large-transfer internal-bandwidth model.
🍯
Insight: "8% throughput / 5% latency MAPE" (the headline claim) is the right level of trust to bring to design-space comparisons run in this simulator — good enough for relative claims, not a substitute for hardware validation of every individually configurable mechanism (pSLC, one-shot QLC timing are explicitly not independently validated here).
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A researcher wants to study FDP placement on a dense QLC tier behind a DPU-mediated SplitFTL over NVMe-oF. Why can't a device-only ZNS/FDP simulator answer this alone?
Show answer
Because the question spans four coupled axes — media (QLC), placement (FDP), control-plane location (DPU SplitFTL), and transport (NVMe-oF) — and a device-only simulator only models the first two, missing whatever bottleneck or interaction the DPU and fabric introduce (e.g. a fabric cap masking a placement win, or vice versa).Misconception: that placement and control-plane location are independent knobs whose effects simply add. The paper's whole motivation is that they're coupled.
Problem 2 · medium
The 24-SSD enclosure offers 24 × 14.1 GB/s ≈ 338 GB/s of raw sequential-read media bandwidth, but a single remote node observes only ~7 GB/s. Is this a simulator inaccuracy?
Show answer
No — it's the real, measured behavior of the single-node RDMA NIC port used for these measurements, and MQSim 2.0 correctly reproduces it (throughput MAPE 4.4%, saturation by QD=8). The gap between media capacity and observed bandwidth is architectural (one port, shared across DPUs), not a modeling error.Misconception: that a large gap between "theoretical" and "observed" bandwidth signals a broken model. Here it's exactly what a correct model should show.
Problem 3 · medium
In SplitFTL, what stays on the device and what moves upstream?
Show answer
Media-specific functions — ECC, bad-block management, coarse placement — stay on the thin device layer. Zone-level mapping and cross-device policy, such as globally coordinated garbage collection, move to the upstream FTL on a host, array controller, or DPU.Misconception: that SplitFTL removes the device FTL entirely. It decomposes it — the device keeps the parts that need to see raw media state directly.
Problem 4 · hard
A 16 TB QLC SSD shared by 8 tenants drops from 3000 MiB/s to 400 MiB/s under concurrent unshaped writes. A colleague argues this proves QLC media is simply too slow for multi-tenant use. What's missing from that argument?
Show answer
The paper attributes the drop to unshaped, interleaved small writes hitting QLC's large indirection units — not to QLC's raw speed. A host layer that reshapes the write stream (e.g. CSAL) recovers much of the loss without changing the media. So the bottleneck is a placement/scheduling problem exposed by dense media, not an inherent media speed limit.Misconception: attributing a system-level interaction effect (interleaving × indirection-unit size) to a single component (the media) in isolation.
Problem 5 · medium
The KV-cache case study reports −48% write amplification and −31% P99 latency for SplitFTL + ZNS vs JBOF. What exactly produces the improvement, per the paper's own caveat?
Show answer
Primarily separating short- and long-lived KV objects into distinct ZNS zones, which reduces GC interference from mixed-lifetime data. SplitFTL's role is providing the DPU-resident classifier (count-min sketch) and placement-control path across the backend pool — it enables the policy but the paper explicitly does not claim the gain as an intrinsic SplitFTL benefit.Misconception: crediting the control-plane mechanism (SplitFTL) for gains that the paper attributes mainly to the placement policy (ZNS zone separation) it enables.
Problem 6 · easy
Why does MQSim 2.0 validate against two very different targets — a single TLC SSD and a 24-SSD DPU enclosure — instead of just one?
Show answer
They validate different scopes of the framework: the TLC SSD validates the direct-attached device path; the 24-SSD enclosure validates the end-to-end disaggregated path (DPU SplitFTL, backend SSDs, NVMe-oF/RoCE transport). One target alone would leave half the simulator's claimed capability unvalidated.Misconception: that one hardware validation target is enough to trust a simulator that claims to model multiple deployment topologies.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is MQSim 2.0 a replacement for MQSim 1.0?▾
It's built on MQSim 1.0 and stays backward-compatible with its local-SSD workflows, but redesigns the device-centric execution model into a composable storage-subsystem model so it can also express disaggregated, DPU-mediated deployments that MQSim 1.0 couldn't.
Q2What's the actual difference between ZNS and FDP?▾
ZNS forces append-only, sequential writes per zone and eliminates device-side GC by construction. FDP is softer: the host tags writes with lifetime hints and the device internally groups same-lifetime writes into Reclaim Units — no sequential-write constraint, but less aggressive GC reduction than ZNS.
Q3Does SplitFTL require a DPU?▾
No — it's a control-decomposition pattern (thin device layer + upstream FTL) that can be hosted on a general-purpose host, an array controller, or a DPU. MQSim 2.0 models DPU-resident SplitFTL specifically because that's the target of the 24-SSD validation and the KV-cache case study, but the abstraction isn't DPU-specific.
Q4What exactly caps the 24-SSD enclosure's observed bandwidth?▾
In this paper's measurement setup, a single remote node connects over one RDMA NIC port, capping observable aggregate bandwidth at ~7 GB/s regardless of workload — far below the backend's raw media bandwidth or even a single DPU's 40 GB/s fabric link.
Q5How trustworthy is the pSLC / one-shot QLC modeling?▾
The paper is explicit: the two validation targets exercise the evaluated end-to-end configurations, not every individually configurable mechanism. pSLC and one-shot QLC models are not separately hardware-validated in this workshop paper — treat them as reasonable but not independently confirmed.
Q6Is the 90%/10% KV-cache retention split a general finding?▾
No — the paper states this is an illustrative workload parameter used to instantiate a known skew (most KV entries are short-lived, a smaller fraction reused across sessions), not a claim that all production deployments exhibit this exact ratio.
Q7Why does ZNS reduce mapping-table DRAM, not just write amplification?▾
Zone-append semantics allow a much coarser mapping structure (per-zone rather than per-4KB-page). For the 24-drive, 61.44 TB-per-SSD enclosure, a conventional page-mapped design would need ~1.4 TB of mapping DRAM across the enclosure; zone granularity cuts that dramatically, though production SSDs often already use coarser mappings at the cost of higher write amplification.
Q8What did the authors leave for future work?▾
Broader sensitivity across alternative KV-cache retention distributions and backend configurations, and additional independent device-level validation — particularly of the pSLC and one-shot QLC models — beyond the evaluated end-to-end configurations.
