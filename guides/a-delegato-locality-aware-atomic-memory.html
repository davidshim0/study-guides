Chiplet Coherence & AMOs · A Field Guide

Don't move the line, move the operation

Delegato (Soria-Pardos et al., MICRO'25) gives a chiplet's coherence directory two new ways to run an atomic read-modify-write besides "steal the line" or "do it myself": forward the op to whoever already owns the line, or hand the line over cleanly — then teaches the directory, via a one-bit reuse trace, which of the three to pick.

1What an AMO actually is, and why every ISA has one▾

An Atomic Memory Operation is a read-modify-write (RMW) on a memory location that the ISA guarantees happens as one indivisible step, even under concurrent access: compare-and-swap (CAS), fetch-and-add (FAA), floating-point add/min/max, bitwise OR, unsigned min, and so on. Armv9, x86, RISC-V, and Nvidia PTX all expose AMO instructions, and ISAs keep extending them — x86 recently added conditional-increment AMOs (CMPccXADD), Arm added floating-point AMO extensions (LSFE).

AMOs are the hardware primitive underneath mutexes, barriers, lock-free data structures, and reduction variables — anything where many threads touch one shared word. Because they're so heavily used for synchronization, their latency and throughput directly gate how well parallel code scales.

Now you're ready: this whole paper is about where in the cache hierarchy an AMO's RMW step actually executes — not about the ISA-level semantics, which are a given.
2The directory, cache states, and AMBA CHI vocabulary▾

In a many-core system, accesses are interleaved across multiple directory structures — hardware that tracks, per cache line, who has a copy and in what state, acting as the point of coherence. This paper's baseline speaks AMBA 5 CHI, whose states map onto familiar MOESI: UD (Unique Dirty), UC (Unique Clean), SD/SC (Shared Dirty/Clean), and I (Invalid).

At the LLC/directory itself, a line can additionally be RSC/RSD/RU — Remote Shared Clean, Remote Shared Dirty, or Remote Unique — meaning "not resident here, but held upstream in SC/SD/U state by some private cache." Key transactions you'll see in the flow diagrams: ReadUnique (get exclusive ownership), AtomicLoad/AtomicStore (the ISA-level AMO request to the directory), SnpFwd/SnpUnique (snoop messages that invalidate or forward a line), and — new in this paper — SnpAMO (snoop an owner to execute an RMW on the directory's behalf).

Now you're ready: every transaction diagram below is just these primitives arranged between Requester (R), Directory (D), and Owner (O).
3Near AMOs — the incumbent baseline▾

Most systems today run AMOs the same way as any store: the L1D acquires the line in exclusive state (a ReadUnique), performs the RMW locally, and keeps the line around hoping for reuse. When one private cache already owns the line, this resolves in as few as three hops because the owner forwards data straight to the requester. Repeated AMOs from the same core are then cheap.

The problem is what happens when AMOs bounce between cores: ownership — and the whole cache line — migrates to whoever touched it last, ping-ponging across the interconnect. On a chiplet system that ping-pong crosses an expensive interposer link every time.

Now you're ready: "near AMO" = the line moves to the operation. Everything in Sections 3–4 of the paper is about not doing that when it's expensive.
4Centralized AMOs — today's only far AMO▾

Centralized AMOs send the RMW to a single fixed serialization point — typically the directory/LLC slice for that line — using an AtomicLoad/AtomicStore request. The directory recovers ownership from any current owner, performs the RMW with its own ALU, and returns the (optional) old value. When the line has no private-cache sharers and already sits in the LLC, this takes only two hops.

Centralized AMOs are the only kind of far AMO that existing commercial CHI systems (NVIDIA Grace, AWS Graviton 3/4) support. They avoid ping-pong but pay for it with (a) an invalidation round-trip whenever an owner exists, and (b) a directory-side ALU. Because every update funnels through one point, they're excellent for high-fan-in throughput but actively hostile to CAS-style retry loops, which the directory can starve.

Now you're ready: centralized = the operation moves to one fixed place, always. The paper's whole contribution is adding two more places to choose from.
5Chiplets, interposers, and why hop-counting matters▾

Chiplet designs split what used to be one monolithic die into several smaller dies connected by an interposer. This raises yield and lowers cost, but the interposer link is slower and higher-latency than on-die wires — a NUMA-like penalty inside the socket. The paper's baseline models two 16-core chiplets linked at 450 GB/s with 50 ns latency (and separately tests a 2 ns UCIe-class link).

Because crossing that link is the expensive step, the paper analyzes every AMO scheme by counting how many messages cross the interposer for a given placement of Requester (R), Directory (D), and Owner (O) relative to the two chiplets. That's the analytical tool used throughout Sections 3 and 4 — not cycle counts, but "how many high-latency hops."

Now you're ready: when you see "Case A / B / C" later, it always means one specific arrangement of R, D, O across two chiplets, and the question is always the same — how many times does a message have to cross the link?
6Coherence misses, and why CAS hates centralization▾

A coherence miss is a cache miss caused by an invalidation or downgrade, not by genuine absence of data. They matter enormously for compare-and-swap: a CAS can fail if the compared value changed since it was read, and the longer the RMW takes to complete, the more likely some other write snuck in first. Both near AMOs (via ping-pong invalidations) and centralized AMOs (via the invalidation needed to recover ownership, plus the added round-trip latency) increase this failure probability.

This is the mechanism behind a pattern you'll see repeatedly in the evaluation: policies that centralize AMOs help throughput-style workloads (FAA, high fan-in) but actively hurt CAS-heavy lock/lock-free workloads, because they inflate RMW latency exactly when latency determines the retry rate.

Now you're ready: "CAS-affine" and "CAS-disruptive" (terms the paper uses for its own results) both trace back to this one mechanism — RMW latency versus CAS failure probability.
7Coherence predictors, and DynAMO specifically▾

A coherence predictor is a hardware structure that watches access metadata and decides which coherence transaction to issue, to optimize either single-thread latency or system-wide throughput. DynAMO — the paper's main point of comparison — is one such predictor placed at the L1D: it tracks whether a line fetched by a near AMO was subsequently reused, and if not, routes future accesses to that line to a centralized AMO instead.

DynAMO's limits, per the paper: it's conservative (defaults to near AMO in most cases), it only sees local L1D history (no system-wide view), and — because it only chooses between transactions that already exist — it structurally cannot reduce coherence misses or offer anything besides near/centralized.

Now you're ready: DynAMO is the yardstick every later result is measured against. Delegato doesn't beat DynAMO by predicting better with the same two options — it wins by having two additional options (Delegate, Migrate) DynAMO's baseline hardware can't issue at all.
8Reading the evaluation: APKI, geomean speed-up, gem5▾

The paper simulates everything in gem5 (full-system mode, Arm ISA, Ubuntu 22.04 / Linux 5.4.65, Ruby for CHI coherence, HeteroGarnet for the mesh NoC) across 22 real workloads — Splash-4/PARSEC kernels, GAP graph benchmarks, lock-free data structures, and scientific kernels. APKI (atomics per kilo-instruction) tells you how AMO-heavy a workload is — from 0.10 (Dedup) to 74.71 (Histogram, Lulesh).

Every bar chart normalizes execution time to Near AMOs as the baseline (because near AMOs, not centralized, are what most real systems ship today). The "speed-up" numbers you'll see (1.80×, 1.07×, 1.13×, …) are geometric means across all 22 workloads, and a policy that helps most workloads can still individually hurt a handful — that per-workload nuance is where most of the paper's insight lives.

Now you're ready: when a section says "1.07× over centralized," it means (Delegato's geomean speed-up over Near) ÷ (Centralized's geomean speed-up over Near) — a ratio of ratios, not a subtraction. Worked Example 3 walks this arithmetic explicitly.
The whole story in one place

Delegato in a nutshell

The problem chiplets create for AMOs, the two transactions that fix it, and the trace mechanism that teaches a directory when to use which.

Chiplet-based CPUs (NVIDIA Grace, AWS Graviton 3/4) now outsell monolithic designs, but the interposer that glues chiplets together is slower than on-die wiring — a NUMA penalty inside the socket. That penalty lands hardest on Atomic Memory Operations: near AMOs ping-pong the whole cache line across the interposer every time ownership changes hands, and the industry's only alternative, centralized AMOs, funnels every update through one fixed directory location — avoiding ping-pong, but paying for it with invalidation round-trips and directory-ALU area, and actively hurting CAS-based synchronization by inflating RMW latency.

Delegato's core move is to notice that "near" and "centralized" aren't the only two places an AMO can run. The paper adds two new CHI transactions: Delegate, which forwards the RMW to whoever already owns the line so it executes locally without transferring the line or invalidating anyone, and Migrate, which behaves like a near AMO (transfers the line) but is tagged as an atomic so the directory can see and reason about it. Neither transaction requires an ALU at the directory the way centralized AMOs do — Delegate needs one at the L2, and Migrate needs none.

With four placements now available, the directory needs a policy to choose between them. The paper first explores five static policies keyed purely on the LLC/directory's cache-block state (Section 4.2), then adds a Chiplet-Aware policy that also checks where the requester and owner physically sit relative to the directory (Section 4.3) — because the best choice among Migrate/Centralize/Delegate literally depends on which side of the interposer everyone is on.

Static policies need a human to pick one per workload, which doesn't scale. So the paper's headline contribution, Delegato proper, is a tracing mechanism: every time the directory delegates an AMO, the owner's private cache reports back a single reuse_bit — is it still actively updating this line, or not? That one bit, riding for free on an existing CHI response field, lets a small predictor at the directory (two small tables, <0.06 mm² together) learn, per cache line, whether to keep delegating, pin ownership to a repeat requester, or pull the line back to the directory and centralize.

The result: across 22 gem5-simulated benchmarks, the Delegato predictor reaches a 1.80× geometric-mean speed-up over near AMOs — beating the best hand-picked static policy per workload's aggregate (1.85× is the theoretical ceiling from perfect per-workload selection, so Delegato gets most of the way there automatically), beating plain centralized AMOs by 1.07×, and beating the DynAMO predictor by 1.13× — for a hardware cost of roughly 0.17% of a 32-core chip's area.

🍯 Key takeaways

  • Four AMO placements now exist: Near (line moves), Centralized (op moves to directory, always), Migrate (line moves, but flagged as atomic), Delegate (op moves to the owner, nothing transfers).
  • Delegate and Migrate need no directory ALU for their own execution — Delegate needs an ALU at the L2 instead; Migrate needs none at all.
  • Best placement depends on cache-block state (is there an owner?) and, on chiplets, physical location of requester/owner relative to the directory.
  • Delegato = a one-bit reuse_bit fed back on every Delegate transaction, reused from an existing CHI field (effectively free), turning invisible private-cache reuse into directory-visible feedback.
  • The predictor built on Delegato cycles a line through three states: Chiplet-Aware (default) → Pinned Owner (after two consecutive same-requester AMOs) → Present Central (after a Delegate comes back with reuse_bit=0).
  • Geomean results vs. Near AMOs: DynAMO 1.60×, Chiplet-Aware (static) 1.71×, Delegato 1.80×, Best-Static-per-workload 1.85×.
  • Total hardware cost: ≈0.142 mm² on a 32-core chip (Reuse Table + Predictor Table + L2 ALU) — about 0.17% of chip area.
Six everyday pictures

How to think about Delegato

Each picture stands alone — read in any order. Every card ends with an honest note about where the analogy stops being true.

Near AMO

Borrowing the neighbor's drill, every single time

Every time you need the drill, you walk over, take it, use it, and it sits at your place until they need it back — then it walks back across the yard. Fine if only one of you ever needs it. If you alternate every five minutes, you spend more time carrying a drill across the yard than actually drilling.

Where it breaks: real ownership transfer is cheap; ping-ponging a cache line across a chiplet interposer costs real, measured nanoseconds and bandwidth — the yard-crossing is the whole performance story, not a minor inconvenience.
Centralized AMO

One notary who signs every document

Instead of everyone editing the shared ledger themselves, they mail their edit to a single notary who applies it and mails back the result. No one fights over the physical ledger — but if two people are racing to update the same line while the notary works through a queue, whichever edit was based on stale information has to be redone. The notary is fast for a flood of unrelated one-off edits, slow and failure-prone for a tight back-and-forth negotiation.

Where it breaks: a real notary doesn't need extra hardware; the paper's directory literally needs a dedicated floating-point-capable ALU (measured at 2894 μm², about 0.11% of a core tile) to actually perform the RMW.
Delegate AMO

Leaving a note for the person already holding the ladder

Your neighbor already has the ladder up against the roof. Instead of asking for it back and re-climbing yourself, you shout up "while you're there, also tighten that bolt" — they do it, hand you the old bolt if you need it, and keep the ladder. Nothing physically moves except the instruction and the answer.

Where it breaks: in the paper, Delegate is only defined for the single-owner case (the RU state); when several people share the ladder, the paper explicitly puts that extension "out of scope" rather than solving it.
Migrate AMO

A courier who stamps the package "atomic" before handing it over

The ladder still physically moves from your neighbor to you — same as a plain borrow — but the courier stamps the transfer "this is for an atomic job," so the office (the directory) knows to keep an eye on it differently than an ordinary loan. Same movement, more visibility.

Where it breaks: the paper is explicit that Migrate's traffic is identical to a plain near AMO — the entire benefit is the directory's added visibility (letting the L2 cache the line instead of the L1, and letting Delegato's predictor reason about it), not any reduction in data movement.
The trace · reuse_bit

A heartbeat monitor on the borrowed ladder

Every time the office asks your neighbor to do one more job with the ladder, they also ask "still using it a lot?" — one yes/no bit clipped onto the reply they were sending anyway. As long as the answer is "yes," the office leaves the ladder alone. The moment the answer is "no," the office reclaims it and starts handling that job centrally instead.

Where it breaks: a real heartbeat monitor is extra equipment; Delegato's bit is free — it reuses the existing DataPull field already carried by CHI's stashing-transaction responses, so no new wires are added.
The stage · chiplet placement

Two office buildings joined by one narrow bridge

All the interesting cost-accounting in this paper reduces to one question: how many times does someone have to cross that one narrow bridge? Whether the cheapest choice is to hand the job to whoever's already on the far side, or bring the job to the near side, or send just the paperwork across, depends entirely on which side the requester and the file's current owner happen to be standing on.

Where it breaks: the paper's "Case A/B/C" analysis only enumerates the placements it needs for its argument; it doesn't exhaustively cost every possible arrangement of requester/owner/directory across more than two chiplets.
Section by section

How Delegato actually works

Centralized AMOs' real shortcomings → the two new transactions → static and chiplet-aware directory policies → the reuse trace → the predictor state machine.

1 · Why centralized AMOs aren't good enough (Section 3)

Centralized AMOs avoid line ping-pong, but the paper identifies three concrete shortcomings. Interconnect traffic: because ordinary loads/stores keep migrating the line between private caches anyway, centralizing the AMO alone doesn't eliminate cross-chiplet traffic — and in the specific "Case A" arrangement (requester and owner on one chiplet, directory on the other), a centralized AMO needs four high-latency cross-chiplet messages versus two for near or delegated AMOs, because the line has to be transferred to the directory and the response has to come back. Coherence misses: centralizing a CAS operation increases its latency, which increases the chance some other write lands first and the CAS has to retry. Area cost: the directory needs its own ALU. The paper measured an extended atomic ALU (adding floating-point min/max/add) at 2894 μm² in a 7 nm process — 85.4% of that area is the floating-point RMW logic, 14.5% is simple bitwise/integer logic — which is about 0.11% of a Neoverse V1 core tile's area (worked out in Example 1).

2 · Delegate and Migrate: the transaction specification (Section 4.1)

Both new transactions can be triggered by the same AtomicLoad/AtomicStore request the directory already receives for centralized AMOs — the directory just chooses a different way to service it. Migrate replays the near-AMO flow (line transfers to the requester) but uses the AMO-flavored request instead of a plain ReadUnique, so the directory can tell "this was an atomic" apart from an ordinary store, and can choose to cache the migrated line at the L2 instead of the L1D (reducing L1D pollution). Delegate sends an SnpAMO snoop carrying the RMW operation itself to the owner; the owner answers the requester directly with a ReqAck (and, for an AtomicLoad, the original value via Resp), the requester ships its data operands to the owner via SourceData, the owner executes the RMW locally, and finally notifies the directory that the snoop completed. Delegate is defined only for the single-owner (RU) case — extending it to multiple sharers would require invalidating all but one first, which the paper explicitly leaves out of scope.

3 · Static directory policies (Section 4.2) and the design space

With three transaction types (Migrate/Centralize/Delegate) available for five directory-visible cache states — UC/UD (line only in the LLC), RSC, RSD, RU (line held upstream, shared-clean/shared-dirty/unique respectively), and I (invalid) — the paper notes Delegate can only legally apply to RU (there has to be a single owner to delegate to). That leaves 2⁴ ways to assign Migrate-or-Centralize to the other four states, times 3 ways to assign Migrate/Centralize/Delegate to RU: 2⁴ × 3 = 48 possible static policies (verified in Worked Example 2). The paper studies five of them:

All-Central defaultCCCCCEverything to the directory. Shipping today (Grace, Graviton 3/4).

Evaluated against near AMOs (Section 6.2), these split into three behavioral groups: All-Migrate barely helps (1.02×) since AMOs now run at the L2 instead of L1; Pinned Owner is "CAS-affine" (1.26×, strong on lock-free queues/stacks) because it never disturbs a genuinely active owner; and All-Central / Unowned Central / Present Central are "CAS-disruptive" but FAA-friendly (1.68×/1.69×/1.70×) because centralizing hurts retry-based CAS loops but helps high-fan-in accumulation. Picking the single best static policy per workload reaches 1.85× — the ceiling static policies can reach without a real predictor.

4 · Chiplet-Aware policy (Section 4.3)

On a chiplet system, the best choice among Migrate/Centralize/Delegate also depends on where the requester and owner physically sit. The paper works through two more placements (Cases B and C, alongside Case A above): when the owner is remote and requester+directory share a chiplet (Case B), Migrate and Centralize both cross the interposer twice (one of those crossings is a full line transfer) but Migrate finishes in one fewer message — Delegate avoids the cross-chiplet line transfer entirely. When the owner and directory share a chiplet and the requester is remote (Case C), all three schemes cross twice, but only Migrate physically moves the line across chiplets; between Centralize and Delegate, Delegate has the shorter critical path. The paper's conclusion: keeping cache-line owners on the same chiplet as their directory is what minimizes cross-chiplet line transfers overall — which is exactly the rule the Chiplet-Aware policy enforces.

5 · Delegato: turning invisible reuse into directory feedback (Section 5)

None of the policies above can see whether an owner holding a line via Delegate is actually still using it — modern private caches (up to 2 MB of L2 per core on recent designs) act as a filter, so the directory only ever observes misses and evictions, never live reuse. Delegato fixes this cheaply: on every SnpAMO, the owner's cache checks a small local Reuse Table (tag + 1 reuse bit, updated on local AMOs and reset each transaction) and returns one bit, reuse_bit, riding on the existing SnpResp message — implemented at zero extra wiring cost by reusing the DataPull field CHI's stashing transactions already carry.

At the directory, a Predictor Table (tag, last-requester ID, 2-bit policy state) turns that feedback into a decision per cache line, cycling through three states: it starts in Chiplet-Aware; if the same requester issues two AMOs in a row, the directory migrates the line to them and switches to Pinned Owner; the next time that line is delegated, if reuse_bit=0 comes back, the directory switches to Present Central, recovering ownership and centralizing future AMOs on that line until it's evicted and reset.

●
The net effect (Section 6.4–6.5). Because the predictor starts every line as Chiplet-Aware and only escalates to Pinned Owner on genuine repeat access, Delegato issues far more Migrate transactions than the static Chiplet-Aware policy alone, and — once pinned — far more Delegate transactions too, on exactly the workloads with real per-line locality. It sacrifices some of the raw data-movement reduction Chiplet-Aware achieves (which cares only about hop count, not latency) in exchange for lower AMO latency overall, and it still wins on total cross-NoC data movement in several benchmarks (LUL, FLU, RSO, HIS).

Example 1 — the directory ALU's area cost (Section 3.3)

  1. The extended atomic ALU (7 nm TSMC, 2 GHz target, synthesized with Cadence Genus/Innovus v19.11) measures 2894 μm² total, split 85.4% floating-point RMW logic and 14.5% simple bitwise/integer logic (85.4 + 14.5 = 99.9%, rounding in the source).
  2. Convert to mm²: 2894 μm² = 2894 / 1,000,000 mm² = 0.002894 mm².
  3. An Arm Neoverse V1 core tile is stated at 2.52 mm² (7 nm). Overhead fraction = 0.002894 / 2.52 = 0.001148 = 0.1148% ≈ the paper's stated 0.11%. ✓ matches.
◆
Takeaway: adding centralized-AMO support to a directory is nearly free in area — which is precisely why the paper frames Migrate/Delegate's advantage as not needing this ALU at the directory as a genuine, if small, additional win, not the main story.

Example 2 — the 48-policy design space (Section 4.2)

  1. Five directory-visible states exist: UC/UD (merged, since both mean "only at the LLC"), RSC, RSD, RU, I — four independent slots plus RU.
  2. Delegate is only legal for RU (there must be exactly one owner to delegate to). So the other four slots each choose between just 2 options (Migrate or Centralize): 2⁴ = 16.
  3. RU alone can choose any of 3 options (Migrate, Centralize, or Delegate): ×3.
  4. Total policies = 16 × 3 = 48 — matches the paper's stated "2⁴×3 = 48" exactly. The paper studies 5 of these 48: All-Central, All-Migrate (both implementable with existing CHI transactions), plus Present Central, Pinned Owner, and Unowned Central (the three genuinely new ones).
▲
Misconception it kills: reading "5 states" and assuming 3⁵ = 243 combinations. Delegate's single-owner restriction removes two of the three options from four of the five states — that constraint is exactly what shrinks 3⁵ down to 48.

Example 3 — speed-ups are ratios of ratios (Section 6.4)

All speed-ups below are geometric-mean execution time relative to Near AMOs (Figure 9). To compare two far-AMO schemes to each other, divide their Near-relative speed-ups.

  1. Delegato vs. Near: 1.80× (given). All-Central vs. Near: 1.68× (given).
  2. Delegato vs. All-Central = 1.80 / 1.68 = 1.0714… ≈ 1.07× — matches the abstract's headline "1.07× over centralized AMOs" exactly.
  3. DynAMO vs. Near: 1.60× (given). Delegato vs. DynAMO = 1.80 / 1.60 = 1.125 ≈ 1.13× — matches the abstract's "1.13× over the state-of-the-art AMO predictor" exactly.
  4. Best-Static vs. All-Central (Section 6.2's own claim) = 1.85 / 1.68 = 1.101… ≈ 1.10×, as stated in the text.
◆
Takeaway: the paper's headline numbers are all divisions of Near-relative speed-ups, never differences. "1.80× vs 1.68×" is not "12 percentage points better" — it's 7% faster than centralized on top of centralized's own gains over Near.

Example 4 — total Delegato hardware cost (Section 6.8)

  1. Reuse Table entry = 49-bit tag + 1 reuse bit = 50 bits. 128 entries × 50 bits = 6400 bits = 800 bytes — matches the paper. Measured at 743 μm² per core (7 nm, 3 GHz); for 32 cores: 743 × 32 = 23,776 μm² = 0.0238 mm² ≈ the paper's stated 0.024 mm². ✓
  2. Predictor Table entry = 49-bit tag + 5-bit requester ID + 2-bit policy state = 56 bits. 128 entries × 56 bits = 7168 bits = 896 bytes — matches. At 807 μm² per LLC slice, replicated across 32 slices: 807 × 32 = 25,824 μm² = 0.0258 mm² ≈ the paper's stated 0.026 mm². ✓
  3. The reuse_bit itself costs nothing extra — it reuses CHI's existing DataPull field.
  4. L2 ALU (same design as the directory ALU, Example 1): 2894 μm² per core × 32 cores = 92,608 μm² = 0.0926 mm².
  5. Total ≈ 0.024 + 0.026 + 0.093 = 0.143 mm², closely matching the paper's stated total of 0.142208 mm² (the small gap is rounding across the per-component μm² figures — the paper's own final number is the authoritative one).
  6. A 32-core Neoverse-V1-class chip (2.52 mm²/core × 32 = 80.64 mm²) gains 0.142208 / 80.64 = 0.00176 = 0.176% ≈ the paper's stated 0.17%. ✓

Example 5 — Delegato holds up on a faster interposer too (Section 6.6, UCIe)

Shrinking the interposer latency from 50 ns to 2 ns (a UCIe-class link) shrinks every scheme's advantage over Near AMOs, since Near's ping-pong penalty shrinks too — but the ranking barely moves.

  1. At 50 ns: Delegato 1.80×, All-Central 1.68×, Best-Static 1.85× (vs. Near).
  2. At 2 ns: Delegato 1.62×, All-Central 1.52×, Best-Static 1.65× (vs. Near).
  3. Delegato vs. All-Central at 2 ns = 1.62 / 1.52 = 1.066… ≈ 1.07× — the same 1.07× ratio the paper reports at 50 ns.
  4. Best-Static vs. Delegato at 2 ns = 1.65 / 1.62 = 1.0185… ≈ 1.02×, exactly the "only 1.02× faster than Delegato" the paper reports — i.e. Delegato closes almost the entire gap to a perfect per-workload oracle even under a much cheaper interconnect.

Warm-up
Why can a static policy legally assign "Delegate" to the RU state but never to RSC, RSD, UC, or UD?
Show answer
Delegate forwards the RMW to a single private-cache owner — that only makes sense when exactly one owner exists, which is what RU (Remote Unique) means. UC/UD mean the line is only at the LLC (no owner to delegate to), and RSC/RSD mean it's shared by potentially multiple private caches, so there's no single owner to forward to without first invalidating everyone else — which the paper explicitly puts out of scope. Catches: treating Delegate as a general-purpose "send it somewhere other than the directory" transaction. It specifically requires a unique owner; that's the whole reason the design space is 48 policies, not 3⁵ = 243.
Diagnose
A lock-free queue (like LFQ in the paper's benchmark set) has one dominant owner core doing most of the enqueue/dequeue CAS operations in a tight loop. Which static policy performs best on this kind of workload, and why does All-Central perform worse than Near AMOs here?
Show answer
Pinned Owner — the paper reports it as the best-performing static policy specifically on LFQ, because it delegates to (rather than disturbs) an owner who is clearly still active. All-Central performs worse than Near on several CAS-heavy benchmarks including LFQ because centralizing the RMW adds latency to every CAS attempt, and CAS failure probability rises with latency (a newer conflicting write is more likely to land first) — so centralization actively increases the retry rate on exactly the workloads with tight CAS loops. Catches: assuming "moves work off the critical core" always helps throughput. For CAS-based synchronization specifically, added RMW latency can make things worse, not better — this is the paper's "CAS-disruptive" pattern.
Diagnose
The abstract claims Delegato is "1.07× faster than centralized AMOs and 1.13× faster than the state-of-the-art predictor." Using only the Figure 9 geomean numbers (DynAMO 1.60×, All-Central 1.68×, Delegato 1.80×, all vs. Near AMOs), show the arithmetic behind both claims.
Show answer
Delegato vs. All-Central = 1.80 / 1.68 = 1.0714 ≈ 1.07×. Delegato vs. DynAMO = 1.80 / 1.60 = 1.125 ≈ 1.13×. Both headline numbers are ratios of Near-relative speed-ups, not differences (1.80 − 1.68 = 0.12, which is not the reported 1.07×). Catches: subtracting Near-relative speed-ups instead of dividing them. A speed-up of "1.80×" already encodes a ratio to a shared baseline, so comparing two such numbers to each other requires dividing, not subtracting.
Design
A workload has many cores round-robin updating one shared counter — no single core ever issues two consecutive AMOs to the line. Walk through what the Delegato predictor does with this line, and whether it's likely to help or hurt versus Near AMOs.
Show answer
The Predictor Table starts the line in Chiplet-Aware. Because "two consecutive AMOs from the same requester" never happens under round-robin, the line never transitions to Pinned Owner — it stays governed by the Chiplet-Aware table (Table 2) indefinitely, delegating only when the current owner happens to sit on the directory's chiplet, and centralizing or migrating otherwise. Whether this helps depends entirely on chiplet placement, not reuse — and the paper explicitly reports that Delegato degrades performance relative to Near AMOs on some low-locality benchmarks (FMM, BAR, LFQ), attributing this to cases where near AMOs were simply better suited and the predictor "can do little." Catches: assuming Delegato always beats Near AMOs. The paper is explicit that it does not — on workloads without the per-line repeat-access pattern the predictor is built to detect, an L1-level predictor like DynAMO (which the paper suggests combining with Delegato) would be needed to catch the cases Delegato's directory-side logic can't see.
Design
Explain, using Table 2, why a cache-line miss (state I) is handled differently for a local requester (Migrate) than for a remote requester (Centralize), even though both are "the line isn't anywhere yet" cases.
Show answer
For a state-I line, there is no existing copy to protect — the only decision is where the first copy should land. If the requester shares a chiplet with the directory, allocating it directly to the requester (Migrate) costs nothing extra in cross-chiplet traffic, since the directory and requester are already local to each other. If the requester is remote, migrating would mean transferring the freshly-fetched line all the way across the interposer for a single first-touch — the Chiplet-Aware policy instead centralizes, keeping the line at the directory (which, per Section 4.2's "Present Central" idea, can also be paired with allocating LLC-missed lines efficiently via direct memory transfer) rather than paying a cross-chiplet transfer for a line that hasn't even proven it will be reused. Catches: assuming Table 2's rows only depend on the cache-block state. The I column is the one place in the table where the requester's location alone — not the owner's, since there is no owner — changes the decision, which is easy to miss if you only remember "delegate when there's an owner."
Loose ends

Frequently asked

The questions that come up once the mechanism clicks.

QIsn't Delegate AMO just software delegation done in hardware?▾
Conceptually related but mechanically different. Software delegation (Section 2.2) has the programmer statically partition shared data so only one designated thread ever updates each location — it avoids data movement but adds real serialization, and someone has to design the partitioning. Delegate AMO is a coherence-protocol transaction: the directory decides, per access and dynamically, whether to forward an RMW to whoever the coherence protocol says currently owns the line — no programmer partitioning required, and the "owner" can change over time as the workload's access pattern changes.
QDoes Delegato remove the need for a directory ALU entirely?▾
No — it relocates where an ALU is needed, it doesn't eliminate the need everywhere. Migrate and Pinned-Owner-style policies need no directory ALU at all (the RMW runs in a private cache's own execution unit). Delegate specifically needs an ALU at the L2 (Section 4.1, accounted for in Section 6.8's area analysis) rather than at the directory. Present Central and Chiplet-Aware still fall back to centralizing in several states, so a directory ALU is still assumed present in the paper's baseline for those cases.
QWhat happens if a line has multiple sharers and someone wants to delegate an AMO to it?▾
The paper notes this is possible in principle — invalidate all sharers except one, who becomes the new owner and executes the RMW — but explicitly states "such implementations are out of scope of this paper." Every Delegate transaction evaluated here targets the RU (single unique owner) state only.
QIs Delegato deployed in real silicon, or is this purely a simulation study?▾
Purely a simulation study, as far as the paper describes. All results come from gem5 v23.1.0 full-system simulation of a hypothetical dual-chiplet Arm system; Delegate and Migrate are proposed extensions to the AMBA CHI protocol, not features of any shipping product. The paper does note that existing shipping systems (NVIDIA Grace, AWS Graviton 3/4) already implement Centralized AMOs and near/far AMO switching per the Neoverse N2 manual — that part is real hardware; Delegato itself is not.
QHow does the reuse_bit avoid costing extra hardware?▾
CHI's SnpResp message already carries a DataPull field, used by "stashing" transactions to tell a cache whether to install data. Delegato repurposes that existing bit for Delegate transactions instead, so no new wire or field needs to be added to the protocol — the paper states this makes the reuse-signaling mechanism free to implement.
QWhy does DynAMO underperform simple static policies like Chiplet-Aware, if it's supposed to be "smart"?▾
DynAMO can only choose between transactions the baseline hardware already supports — near AMOs and centralized AMOs. It's also deliberately conservative (only escalates to centralized when a line misses in the L1D and its own local reuse tracking says "not reused"), and it only sees L1D-local history, with no visibility into system-wide or chiplet-placement information. Chiplet-Aware, despite being a fixed (non-adaptive) policy, has access to information DynAMO's hardware simply doesn't: cache-block state and physical chiplet location, plus the ability to actually issue Delegate and Migrate transactions.
QWhy does everything get less dramatic on a UCIe-class (2 ns) interposer?▾
Every scheme's advantage over Near AMOs in this paper comes from avoiding expensive interposer crossings. Shrink the interposer latency from 50 ns to 2 ns and Near AMOs' ping-pong penalty shrinks right along with everyone else's transfer costs — so the relative gap between schemes compresses (Delegato falls from 1.80× to 1.62× vs. Near). The paper reports the ranking stays essentially the same (Delegato still beats All-Central by 1.07×), which is presented as evidence the mechanism is robust to interconnect technology, not just tuned to one latency regime.

Glossary, benchmark acronyms, a dated summary card, and the honest provenance notes.

Core terms
AMOAtomic Memory Operation — an ISA-level indivisible read-modify-write (CAS, FAA, floating-point add/min/max, etc.), fundamental to synchronization primitives.
Near AMOThe RMW executes in the requester's own L1D after acquiring the line exclusively — causes cache-line ping-pong between cores. terracotta
Centralized AMOThe RMW executes at a fixed serialization point (the directory/LLC), via an AtomicLoad/AtomicStore request — today's only shipping far AMO. honey
Migrate AMONew transaction: transfers the line like a near AMO, but flagged so the directory can distinguish it from an ordinary store. indigo
Delegate AMONew transaction: the directory sends the owner an SnpAMO, the owner executes the RMW locally using operands sent directly by the requester — no line transfer, no invalidation. teal
DirectoryThe coherence point-of-serialization that tracks per-line ownership/sharer state; in this paper's baseline it also includes an LLC slice.
RU / RSC / RSD / UC / UD / ICHI cache-block states the directory tracks: Remote Unique/Shared-Clean/Shared-Dirty (held upstream), Unique Clean/Dirty (only at the LLC), Invalid.
Chiplet-Aware policyStatic directory policy that additionally checks requester's and owner's chiplet location relative to the directory (Table 2).
Delegato-specific terms
DelegatoThe paper's tracing mechanism: owners report a 1-bit reuse_bit on every Delegate transaction, giving the directory visibility into private-cache reuse it otherwise can't see.
reuse_bitOne bit in SnpResp (reusing CHI's existing DataPull field) indicating whether the delegated line is still being actively updated.
Reuse TableSmall table at the private cache (L2) tracking per-line reuse to compute the reuse_bit; best-performing at ~64 entries in the design-space sweep.
Predictor TableTable at the directory holding tag, last-requester ID, and a 2-bit policy state per tracked line; 128 entries, 2-way associative in the best configuration.
Pinned Owner (PO) / Present Central (PC) / Chiplet-Aware (CA) statesThe three predictor states a line cycles through: CA (default) → PO (after 2 consecutive same-requester AMOs) → PC (after a Delegate reply with reuse_bit=0).
DynAMOThe state-of-the-art baseline coherence predictor (prior work): chooses near vs. centralized at the L1D using local reuse history only.
APKIAtomics per kilo-instruction — how AMO-intensive a benchmark is; ranges 0.10 (Dedup) to 74.71 (Histogram/Lulesh) in the paper's suite.
CAS-affine / CAS-disruptiveThe paper's own labels for policies that help vs. hurt compare-and-swap-heavy workloads, respectively, based on how they affect RMW latency and CAS failure probability.

📌 Summary card · as of 2026-08-30 · MICRO'25 paper

  • Problem: chiplet interposers make near-AMO ping-pong and centralized-AMO round-trips both expensive; only one far-AMO type (Centralized) existed.
  • Two new transactions: Migrate (near-AMO traffic, directory-visible) and Delegate (forward the RMW to the owner — no transfer, no invalidation).
  • Directory policy space: 2⁴×3 = 48 static policies; the paper studies 5, plus a Chiplet-Aware policy keyed on physical placement (Table 2).
  • Delegato mechanism: a free 1-bit reuse_bit fed back on every Delegate transaction, reusing CHI's existing DataPull field.
  • Predictor: Reuse Table (L2) + Predictor Table (directory), cycling each line through Chiplet-Aware → Pinned Owner → Present Central.
  • Headline results (vs. Near AMOs, gem5, 22 workloads): DynAMO 1.60×, Chiplet-Aware 1.71×, Delegato 1.80×, Best-Static-per-workload 1.85×.
  • Derived: Delegato beats Centralized AMOs by 1.07× and DynAMO by 1.13× — both exactly reproduced in Worked Example 3.
  • Cost: ≈0.142 mm² on a 32-core chip (Reuse + Predictor tables + L2 ALU) ≈ 0.17% of total area.
  • Robustness check: on a 2 ns UCIe-class interposer, absolute gains shrink but the 1.07× Delegato-over-Centralized ratio holds.
  • Known limitation (paper's own words): Delegato still degrades vs. Near AMOs on some low-locality benchmarks (FMM, BAR, LFQ) — combining it with an L1-level predictor like DynAMO is suggested future work.
