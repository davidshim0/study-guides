SOSP 2026 · A Field Guide

Let the model reason about the knobs — never let it touch the kernel directly

Bayesian and RL tuners treat CFS, DVFS, and NAPI knobs as anonymous numbers and can steer a live service into a config that's numerically fine but semantically broken. TuxBot puts an LLM in the loop as a semantic reasoner — bounded by a typed validator that decides what actually reaches the OS.

📄 Liargkovas, Joshi, Franke & Kaffes · Columbia / IBM Research 🎓 Assumes familiarity with OS internals — tuning-loop basics covered in Start Here ⏱ ~25 min read
🛡️

The LLM PROPOSES a knob update from telemetry and knob semantics; a typed validator DISPOSES — only schema-legal, constraint-satisfying updates ever reach sysctl/sysfs.
Reasoning is unbounded. Actuation is not.

1The online OS tuning loop▾

A tuner is a host-side controller that runs alongside a live application: it observes telemetry, applies knob updates, and uses the resulting measurements to pick the next update. This paper studies out-of-band, steady-state tuning — seconds-to-minutes timescales, not per-request or kernel-fast-path control (that's the job of the scheduler or a congestion controller, not the tuner).

Two classic ways to automate this loop: Bayesian optimization (fit a surrogate model over the config space, pick the next point by expected improvement) and reinforcement learning (map telemetry to a state, knob changes to actions, improve a policy from reward). MLOS and the RL baselines instantiate exactly this loop.

Now you're ready: TuxBot keeps this same loop shape (observe → decide → apply → repeat) but replaces the black-box optimizer with an LLM that reads knob meaning, not just numbers.
2The knobs themselves: CFS, DVFS, C-states, NAPI▾

The paper's default 8-knob set spans four coupled subsystems. CFS: latency_ns sets the scheduling period; min_granularity_ns sets the minimum slice inside it (they must stay consistent); wakeup_granularity_ns tunes preemption sensitivity; migration_cost_ns decides when a task is "cache-hot" enough to resist migration. DVFS: min_perf_pct/max_perf_pct bound allowed CPU frequency as a percent of max. Idle states: cstate_max caps how deep a core may sleep. NAPI: net.core.busy_poll spins on the NIC instead of waiting for an interrupt.

None of these are independent: aggressive busy polling plus shallow C-states plus a long scheduler period is a coherent-looking but often terrible combination for a latency-sensitive service.

Now you're ready: "semantically unsound" in this paper covers two distinct cases: configs that are internally contradictory (like min_perf_pct > max_perf_pct), and configs like this one — individually valid knob values that combine into a policy no expert would choose for this workload.
3Why blind numeric search struggles here▾

MLOS/Bayesian/RL tuners see each knob as an independent variable with a valid range and interpret a scalar reward. They have no notion that min_perf_pct must stay below max_perf_pct, or that busy-polling and deep sleep states fight each other. They can only discover harmful interactions by trying them live.

Now you're ready: Table 1 in the paper shows MLOS pushing Memcached's p99 from 1.43 ms to 64–68 ms this way — a >47× spike — while throughput barely moves, so the damage doesn't show up in an aggregate throughput number.
4Reward signals: direct vs. proxy metrics▾

Some services expose p99/throughput directly to the tuner. Others don't (proprietary stacks, legacy instrumentation), forcing a fallback to a hardware-counter proxy like IPC or LLC cache misses. The problem: the same IPC value can mean different things depending on scheduler behavior, memory pressure, and I/O — no single low-level counter is a reliable stand-in for application performance across workloads.

Now you're ready: on PostgreSQL/Wikipedia, swapping the app-metric reward for IPC or cache misses makes p99 about 2× worse — this motivates TuxBot reading a joint telemetry signature instead of one proxy.
5What an LLM adds: semantic reasoning▾

Given knob names, subsystem documentation, current telemetry, and recent history, an LLM can interpret a candidate configuration in context — the same way a human performance engineer would — rather than as an isolated point in a numeric space. Declared contradictions (like min_perf_pct > max_perf_pct) are still caught mechanically by the host-side validator; what the LLM adds is catching the harder case — a config that's workload-nonsensical, before it's ever tried live.

Now you're ready: this is the paper's central bet — semantic priors replace blind trial-and-error, without eliminating the need to still measure outcomes.
6Why not just give the LLM a terminal?▾

An open-ended shell interface gives the model far more ways to make a damaging, stateful mistake — in the paper's own TPC-C experiments, a terminal-enabled agent wandered into CPU offlining, huge dirty-ratio writes, and block-scheduler rewrites. Public incidents in other agentic systems show the same pattern.

Now you're ready: TuxBot's answer is a typed, validated interface — the model can only propose knob=value pairs from a known schema, never issue arbitrary commands.
7Latency and cost: why one LLM isn't enough▾

Strong reasoning models are slow and expensive to run on every control step (every 1–5 seconds here). A single slow model on the critical path reacts too late and costs too much; a single fast model reasons too shallowly and gets stuck. TuxBot's fix, covered in How It Works, is to pair a fast Instant model with a slower Reasoning model.

Now you're ready: this dual-loop idea is the paper's main systems contribution, not just a cost optimization.
8Memory without training▾

A pretrained LLM has broad systems knowledge but no memory of this workload's quirks from session to session. Without an explicit memory mechanism, it has to rediscover, every run, which counters predict this service's p99 and which knob regions are unsafe on this hardware.

Now you're ready: TuxBot stores a compact per-iteration trace of past sessions in a vector store and retrieves similar prior runs to warm-start new ones — even for workloads it has never seen before.
The whole story in one place

TuxBot in a nutshell

The problem, the architecture that fixes it, and the headline numbers.

Classical online OS tuners — Bayesian optimization, tabular Q-learning, DQN, and MLOS's SMAC3-based search — treat scheduler, power, memory, and I/O knobs as independent numeric variables and a single scalar reward. But a live OS combines these knobs into one coupled runtime policy. Numerically valid settings can be a semantically nonsensical policy (aggressive busy-polling with shallow idle states on a latency-sensitive service) or outright contradictory (min_perf_pct > max_perf_pct). Classical tuners can only discover this by living through it — and Memcached under MLOS actually did, taking a >47× tail-latency spike mid-session.

TuxBot's fix: put an LLM inside the loop as a semantic reasoner, not as an autonomous agent with shell access. A Context Manager assembles a structured prompt from knob schemas, current telemetry, recent trajectory, and prior-session memory. A dual-loop Tuner — a fast, cheap Instant model for every 1–5s tick, a slower Reasoning model for periodic strategy updates — proposes knob changes. Every proposal is checked by a host-side Parameter Validator against a typed schema and declared cross-knob constraints before it ever reaches sysctl/sysfs/debugfs. A cross-run memory (Gemini Embedding + ChromaDB, top-3 retrieval) warm-starts new sessions from similar past ones.

The payoff: across 13 live workloads and up to 41 tuned Linux knobs, on the 11 workloads where baselines don't fail catastrophically, TuxBot improves stable-phase performance by 87.2% over defaults vs. 50.5% for MLOS — a 36.7-point gap. Using only system-level metrics (no application feedback at all), TuxBot still reaches 64.0%, beating MLOS even when MLOS gets the real application metric. On the two workloads (Xapian, Memcached) where classical tuners enter severe, persistent degradation, TuxBot has zero such incidents with application feedback.

🍯 Key takeaways

  • Classical tuners optimize numeric validity; TuxBot reasons about semantic validity — whether a config makes sense for this workload, not just whether each field is in range.
  • Dual-loop control (fast Instant + slow Reasoning) avoids paying reasoning-model latency on every 1–5s tick, at roughly half the cost of an always-reasoning tuner for ~2.5pp less stable-phase gain.
  • A typed Parameter Validator is the sole write path to the OS — the model proposes, the validator disposes, and nothing reaches the kernel unvalidated.
  • Cross-run memory (top-3 retrieval) warm-starts tuning, including on workloads never seen before.
  • System-metrics-only TuxBot (64.0%) beats app-metric MLOS (50.5%) — semantic reasoning over joint telemetry substitutes for a missing direct reward.
  • As the knob surface grows from 1 to 41 parameters, MLOS's stable-phase gain collapses (119.3%→13.0% on the 4-parameter-and-up trend) while TuxBot stays strongly positive.
  • With application feedback, TuxBot recorded 0% severe-degradation incidents across all evaluated runs; MLOS, Bayesian, and Q-learning all exceeded 15%.
Six everyday pictures

How to think about TuxBot

Each stands alone. Every card ends with an honest note on where the picture breaks.

The core idea · Semantic vs numeric

A contractor reading blueprints vs. a checklist

A checklist confirms every measurement is "in range" — this beam is long enough, this wire is rated high enough. It never notices that the wiring plan routes power through where the plumbing goes. A contractor who reads the blueprint as a whole catches that instantly. Classical tuners are the checklist; TuxBot's LLM is the contractor reading knob relationships as one coherent plan.

Where it breaks: a good contractor has years of tacit experience; TuxBot's "experience" is the pretrained model's priors plus whatever cross-run memory it has retrieved — it can still misjudge a truly novel interaction.
The architecture · Dual-loop

Reflexes and deliberation

You pull your hand off a hot stove before you've consciously "decided" to — a fast reflex loop. Separately, slower deliberate thought plans your next move. Sports and driving run both at once: quick correction now, strategy revision periodically. TuxBot's Instant model is the reflex (every 1–5s); the Reasoning model is the deliberation (every tens of seconds), and the Instant loop inherits the Reasoning loop's current strategy between updates.

Where it breaks: reflexes are hardwired; TuxBot's Instant model is still a full LLM call — cheap and fast relative to Reasoning, not free. It's a cost tradeoff, not literally reflexive.
The guardrail · Typed validator

A bouncer with a guest list

A bouncer doesn't judge your character — they check your name against a list and turn you away if it's not there, no exceptions, no persuasion. The Parameter Validator works the same way: every proposal is checked against the known knob schema, type, numeric/categorical range, and declared cross-knob rules (like min_perf_pct ≤ max_perf_pct). Fail any check and the proposal is rejected outright — the current configuration stays untouched.

Where it breaks: a bouncer can't tell a well-dressed troublemaker from a legitimate guest. Likewise, validation catches schema violations, not workload unsuitability — a config can pass every check and still be a bad idea for this particular service. That judgment stays with the LLM.
Missing rewards · Joint telemetry

A doctor reading vitals together, not one gauge

A single vital sign — say, heart rate alone — can look normal while something else is badly wrong; doctors read blood pressure, oxygen, temperature, and history together. The paper's own cautionary case is MLOS on PostgreSQL/Wikipedia: swapping the app-metric reward for a single hardware-counter proxy like IPC or cache misses makes p99 roughly 2× worse. TuxBot's answer to the same missing-reward problem is to read CPU saturation, run-queue growth, memory pressure, and I/O wait together as one signature rather than trusting any single proxy — evaluated in aggregate across workloads, not as that specific Wikipedia trace.

Where it breaks: a doctor's vitals are causally linked to health by biology; the mapping from "queue growth + memory pressure" to "this specific app is slow" is inferred by the LLM from context, not guaranteed — it's still an inference, just a richer one than a single counter.
Warm starts · Cross-run memory

Consulting a few similar past cases, not one

A doctor facing an unfamiliar case does better recalling several similar past patients than fixating on the single most similar one (who might be a fluke) or averaging across dozens of loosely related ones (which dilutes the useful signal). TuxBot's memory retrieves the top-3 most similar prior sessions by early-window telemetry signature and synthesizes them into one warm-start prior — k=1 proved brittle, larger k averaged away the most relevant evidence.

Where it breaks: past patients share biology across hospitals; past tuning sessions may not share hardware or kernel version. The paper notes cross-run advice may not transfer across platforms — filtering by platform metadata is future work, not yet implemented.
Scaling · Growing the knob surface

More cooks, more ways to ruin the broth

One cook adjusting salt is low-risk. Eight cooks each adjusting salt, heat, timing, and three other spices at once, with no coordination, is a recipe (pun intended) for disaster — not because any single adjustment is wrong, but because the interactions multiply. Linux exposes over 1,200 tunable knobs; growing the co-tuned surface from 1 to 32 sharply degrades TPC-C's p99 under MLOS. TuxBot's semantic priors let it relate knob groups to subsystems and the current symptom, focusing on the handful likely to matter instead of searching blindly across all of them.

Where it breaks: even a great head chef can be overwhelmed at some scale; TuxBot's gains shrink somewhat at 32 knobs too (stable-phase +105% vs. +213% at 16) before recovering at 41 — dimensionality is mitigated, not eliminated.
The full explanation

How TuxBot actually works

Context construction, dual-loop control, typed actuation, memory, and how it scales as the knob surface grows.

1 · Building the decision context

Each tuner call gets a session specification (fixed for the run: role, goal, active knob set with types/ranges/relationships, optimization strategy, and — after the first session — a warm-start memory prior) plus a per-iteration update (refreshed every tick: current configuration, latest system/app measurement, and a recent action–response trace). Telemetry — perf stat counters, RAPL power, C-state residency, CPU-load — is collected automatically once the user specifies the CPU scope; wiring up a new workload's application-level metric typically takes under 30 minutes.

2 · Typed, validated actuation

A model reply is only a proposal. The host-side Parameter Validator checks the complete update for unknown knobs, type mismatches, out-of-range numeric or categorical values, and violated declared cross-knob constraints — for example, the rule that min_perf_pct must not exceed max_perf_pct. Any failed check rejects the whole proposal, leaves the running configuration untouched, and logs the violated rule into the next trace. Accepted proposals are translated into writes through sysctl, sysfs, debugfs, cpufreq, and intel_pstate under a host-side lock; on any write failure, TuxBot restores the last committed configuration and reads back the affected knobs.

# validator, per proposal
for knob, value in proposal:
    if knob not in active_schema: reject("unknown knob")
    if type(value) != schema[knob].type: reject("type mismatch")
    if value not in schema[knob].domain: reject("out of range")
for rule in declared_relationships:      # e.g. min_perf_pct ≤ max_perf_pct
    if not rule.holds(proposal): reject("constraint violated")
commit(proposal) # only path that ever touches sysctl/sysfs/debugfs
⚠
Validation ≠ suitability. Aggressive busy polling with shallow C-states satisfies every type, range, and ordering rule and would still pass the validator — choosing among such schema-legal-but-unwise configurations remains the LLM's semantic-reasoning job, informed by observed behavior.

3 · Cross-run memory

Every completed session's per-iteration trace (action, configuration, system and app metrics) is embedded with Gemini Embedding and stored in ChromaDB. A new session observes one tuning window, builds a bootstrap query from the goal, machine context, and first-window telemetry signature, and retrieves the top-3 nearest prior sessions. A reasoning-model call compresses those three into a short textual prior — reusable parameter relationships, promising/risky regions, early exploration advice — injected into the new session's specification. Live measurements always override a stale or weak memory prior.

Follow the numbers, step by step

Worked examples

Four traces from the paper, carried through the arithmetic.

① Reading MLOS's Memcached trace (Table 1)

Under 500,000 QPS, MLOS co-tunes 8 knobs to minimize p99. At t=10s, p99=1.43ms (stable). At t=68.38ms-worthy moments, what actually happened?

  1. t=20–25s: MLOS proposes busypoll=975 with a shallow C-state, then busypoll=702 with a 50ms scheduler timeslice. Both are numerically valid per-knob, but combine into an unsound policy for a latency-sensitive cache.
  2. Compute the tail-latency multiplier: 68.38 ms ÷ 1.43 ms ≈ 47.8× — this is exactly the ">47× tail-latency increase" the abstract reports for Memcached under MLOS.
  3. Check throughput in the same window: 466,478 req/s vs. the 499,995 req/s baseline — only a 6.7% drop. Throughput looks almost fine while p99 is nearly 48× worse.
  4. t=225s: MLOS sets min_perf_pct=70%, max_perf_pct=10% — a semantically violating configuration (the lower bound exceeds the upper bound), not just a poor choice. p99 is still 15.02ms.
  5. t=250s: the same violation recurs (63% > 3%) alongside aggressive busy polling; p99 jumps back to 54.44ms and throughput falls to 425,471 req/s.
🍯
Insight: a brief repair near t=150s (p99 back to 1.78ms) does not mean the problem is solved — MLOS revisits the same class of unsound region twice more. A near-normal throughput number can mask severe, repeated tail-latency damage.

② The 36.7-point gap, and why it becomes 104.4 points

The paper reports two different-sized advantages for TuxBot over MLOS. Where do they come from?

  1. 11-workload subset (excludes Xapian, Memcached), stable phase: TuxBot 87.22% − MLOS 50.52% = 36.70 pp. During tuning: 73.16% − 35.64% ≈ 37.5 pp — a similar-sized gap in both phases, meaning TuxBot's advantage isn't just a late-session artifact.
  2. Full 13-workload suite, stable phase: TuxBot +72.49% − MLOS −31.91% = 104.40 pp.
  3. Why the jump? Adding back Xapian and Memcached lowers TuxBot's average by only 14.73 pp (72.49% vs. 87.22% on the smaller set) but lowers MLOS's by 82.43 pp (−31.91% vs. +50.52%) — MLOS's aggregate is dominated by the two workloads where it enters severe, persistent degradation.
  4. Read it as: TuxBot degrades gracefully as harder workloads are added; MLOS's aggregate performance is fragile to a couple of catastrophic runs.
💡
This is why the paper reports both views rather than one: the 11-workload number isolates ordinary tuning quality, and the full-suite number exposes how badly classical search can fail when it hits a hard case.

③ Beating a direct metric with no direct metric at all

On the 11-workload subset, can TuxBot without any application feedback still beat MLOS with application feedback?

  1. MLOS, app metrics, stable phase: +50.5%. This is MLOS's best possible showing — direct reward, no proxy noise.
  2. TuxBot, system metrics only, stable phase: +64.0%. No p99, no throughput signal reaches the tuner — only perf stat, RAPL power, C-state residency, CPU load.
  3. Compute the gap: 64.0% − 50.5% = +13.5 pp, in TuxBot's favor, despite the informational disadvantage.
  4. Contrast with a weaker proxy: TuxBot on IPC alone reaches +47.21% — below MLOS's app-metric result, showing joint telemetry (system metrics) genuinely outperforms a single scalar-counter proxy (IPC), not just "any indirect signal is fine."
🍯
Insight: the advantage isn't just "TuxBot's LLM is smarter" — it specifically comes from reasoning over a joint telemetry signature rather than any single hardware counter, direct or proxy.

④ Is the dual loop actually worth its cost?

Single-Reasoning (always the slow model) reaches +89.7% stable at $0.42/session. The dual loop reaches +87.2% at $0.20. Which is the better deal?

  1. Cost per stable-phase percentage point, dual loop: $0.20 ÷ 87.2 ≈ $0.0023/pt.
  2. Cost per point, Single-Reasoning: $0.42 ÷ 89.7 ≈ $0.0047/pt.
  3. Ratio: 0.0047 ÷ 0.0023 ≈ 2.0× — the dual loop is roughly twice as cost-efficient per percentage point of stable-phase gain.
  4. What you give up: only 89.7% − 87.2% = 2.5 pp of stable-phase improvement, and the dual loop is actually slightly ahead during the tuning phase itself (73.2% vs. 71.2%).
💡
Single-Instant (only the fast model) is cheaper still ($0.12) but reaches just +25.4% — confirming that some deep reasoning is necessary; the dual loop's trick is timing that reasoning sparingly, not skipping it.

Problem 1 · easy
MLOS sets min_perf_pct=70%, max_perf_pct=10%. Is this the same kind of failure as "aggressive busy polling + shallow C-states + long scheduler timeslice"? Why or why not?
Show answer
No — they're the paper's two distinct failure categories. min_perf_pct > max_perf_pct is semantically violating: the configuration is internally contradictory (a lower bound exceeding an upper bound), regardless of workload. The busy-poll/C-state/timeslice combo is numerically valid but nonsensical: each field is a legal value, but the combination makes no sense for a latency-sensitive service specifically.Misconception: treating all "bad configs" as one category. The paper distinguishes them because a validator can catch the first type with a declared rule, but the second type requires workload-aware judgment.
Problem 2 · medium
Compute the throughput drop at t=250s in the Memcached trace (425,471.4 req/s vs. the 499,995.1 req/s baseline) and compare it to the p99 change at the same point (54.44ms vs. 1.43ms). What does the contrast tell you about monitoring with throughput alone?
Show answer
Throughput drop: (499995.1 − 425471.4) / 499995.1 ≈ 14.9%. p99 change: 54.44 / 1.43 ≈ 38× worse. A 15% throughput dip looks like ordinary noise on a dashboard; a 38× tail-latency spike is a severe user-facing incident. Monitoring throughput alone would miss this almost entirely.Misconception: that throughput is a sufficient health signal for a latency-sensitive service. The paper's whole Memcached example exists to show it isn't.
Problem 3 · medium
Why does TuxBot with IPC alone (47.21% stable, 11-workload subset) underperform TuxBot with full system metrics (64.0%), even though both are "indirect" signals reasoned over by the same LLM?
Show answer
The LLM can only reason as well as the information it's given. IPC is a single scalar that conflates many different underlying states (scheduler behavior, memory pressure, I/O activity can all move IPC the same direction for different reasons). System metrics give the model a joint signature — CPU saturation, queue growth, power state, I/O wait together — which disambiguates those states. Better reasoning over worse information still loses information.Misconception: that "the LLM reasons about it" fixes any signal quality problem. Semantic reasoning helps interpret telemetry, but it can't recover information that was never collected.
Problem 4 · hard
TuxBot-Trim uses TuxBot's LLM loop for only the first 10 of 30 tuning windows, then hands off to MLOS. At 41 knobs it reaches +203.9% stable but only +44.3% during tuning, versus TuxBot's +86.1% tuning / +155.9% stable. Explain the pattern using what trimming does and doesn't fix.
Show answer
Trimming narrows the active knob ranges and can fix low-impact parameters using 10 windows of live semantic reasoning — this helps MLOS's subsequent search converge to a much better stable point than MLOS alone would reach (MLOS's own 41-knob baseline, from the same three-workload scalability sweep, is far worse). But once control passes to MLOS, the remaining 20 windows of exploration are semantics-blind again: MLOS can still wander into unsound regions within the trimmed space, which drags down the tuning-phase number relative to TuxBot, which keeps semantic reasoning active for the entire session.Misconception: that reducing the search space once is equivalent to reasoning throughout. The paper's §6.4 explicitly uses this comparison to argue semantic understanding is necessary even in later tuning stages, not just at the start.
Problem 5 · medium
In the dual-loop timeline, why does the Instant tuner's visible context reset to just one reasoning entry right after a Reasoning result (e.g., I1.0 sees only R1's entry, not the I0.x entries)?
Show answer
This is the replacement policy that bounds context growth. Instant context entries are useful only until the strategy they informed is superseded — once Reasoning has "read" the accumulated Instant history and distilled it into a new persistent reasoning entry, that raw Instant history is redundant and is discarded. This keeps the unbounded part of context growth at O(|Reasoning|) rather than growing with every fast tick.Misconception: that discarding I0.x context loses information. The information was already folded into R1's reasoning entry — nothing useful is actually lost, just de-duplicated.
Problem 6 · hard
MLOS's severe-degradation incident rate is 16.7% with a persistent rate of 8.3% (still degraded at window 50). What does the gap between 16.7% and 8.3% tell you, and why measure persistence at window 50 specifically rather than just counting incidents?
Show answer
16.7% of runs entered a severe-degradation incident (≥3 consecutive windows with Q_t < 0.1) at some point; roughly half of those (8.3% of all runs) were still in that degraded state by the final window (50). The gap shows some incidents are transient — the tuner eventually recovers — while others represent a state the tuner never escapes within the session. Measuring at window 50 (the very end, after MLOS has continued tuning through windows 31–50 — while TuxBot has already frozen its configuration into its stable phase) is a strict test: it asks whether the tuner can recover, not just whether it initially avoided trouble.Misconception: conflating "had an incident" with "never recovered." The persistent rate is a stronger, distinct claim about a tuner's ability to escape a bad region it entered.
Problem 7 · easy
Single-Instant (fast model only, $0.12/session) reaches only +25.4% stable-phase improvement, far below TuxBot's dual loop (+87.2%, $0.20). Why doesn't the cheaper, faster model alone do better?
Show answer
The paper states plainly that a fast loop alone "tends to get stuck in local optima or settle for weaker configurations" — it can react quickly but lacks the deeper reasoning budget to evaluate broader strategy or recognize subtler semantic issues. Speed and reasoning depth are separate axes; being fast doesn't substitute for being thorough.Misconception: that a lower-cost, faster loop is a strictly worse version of the same thing, just cheaper. It's actually missing a different capability (strategic depth) that the Reasoning loop specifically supplies.
Problem 8 · medium
The paper cites prior work on parameter tuning in memory-tiering systems (Kanellis et al., "Striking the right chord" / "From good to great"). Why might a memory-tiering tuning problem face the same three failure modes (numeric validity, missing reward, knob-count blowup) that TuxBot targets for CFS/DVFS/NAPI?
Show answer
Memory-tiering systems (e.g., migration-rate thresholds, hot/cold classification windows, promotion/demotion batch sizes) are exactly this kind of coupled control surface: a migration threshold set too aggressively relative to a classification window can thrash pages back and forth (a numerically-valid-but-nonsensical combination), the true objective (tail latency under a specific access pattern) may not be directly observable online (forcing reliance on proxies like access-bit sampling rates), and tiering systems increasingly expose more knobs as they add NUMA-awareness, CXL-specific timers, and per-tier bandwidth controls. The same three failure modes generalize because the underlying cause — treating coupled OS/hardware controls as independent numeric variables — is not specific to CFS or DVFS.Misconception: assuming TuxBot's contribution is scheduler/power-specific. The mechanism (semantic reasoning + typed bounded actuation) is domain-general; the paper explicitly lists this connection among its related work.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly makes a knob combination "semantically unsound"?▾
Two distinct cases, both covered in the paper: (1) semantically violating — internally contradictory, like min_perf_pct > max_perf_pct; and (2) numerically valid but nonsensical for the workload, like combining extreme busy polling, shallow idle states, and a long scheduler timeslice on a latency-sensitive service. Both pass a naive per-field range check; neither would survive a human expert's review.
Q2Why not just add more validation rules to catch every bad combination?▾
The validator only catches declared relationships (like the min/max ordering rule) — it can't enumerate every possible workload-dependent bad interaction in advance, because "bad" depends on the specific service and its current load. That's precisely the judgment the paper delegates to the LLM's semantic reasoning rather than to a fixed rule set.
Q3Why two LLMs (Instant + Reasoning) instead of one?▾
A single slow, reasoning-heavy model on every 1–5s tick reacts too late and costs too much; a single fast model alone gets stuck in local optima. The dual loop lets fast exploration and correction happen every tick while deeper strategic reasoning happens only every tens of seconds, at roughly half the per-session cost of an always-reasoning tuner for about 2.5 percentage points less stable-phase gain.
Q4Can the LLM ever write directly to the kernel?▾
No. Every proposal passes through the host-side Parameter Validator, which checks it against a typed schema (known knobs, correct types, valid ranges/domains, declared cross-knob constraints) before any write via sysctl/sysfs/debugfs/cpufreq/intel_pstate. A rejected proposal leaves the current configuration untouched. There is no shell or terminal access.
Q5What happens when application metrics aren't available?▾
TuxBot falls back to system-level telemetry (perf counters, RAPL power, C-state residency, CPU load) and reasons over the joint signature rather than any single proxy. On the 11-workload subset this still reaches 64.0% stable-phase improvement — ahead of MLOS's 50.5% even with direct application feedback.
Q6Does more tuned knobs always help?▾
Not for classical tuners: MLOS's stable-phase gain falls from roughly 119% at 4 knobs down to about 13% at 41 knobs on the three-workload scalability sweep, and its tuning-phase result turns negative at 16+ knobs. TuxBot stays strongly positive across the same sweep (e.g., +213.4% stable at 16 knobs, +155.9% at 41), because semantic priors help it focus on the knobs relevant to the observed bottleneck instead of searching the whole space blindly.
Q7Why does MLOS look reasonable on 11 workloads but terrible on all 13?▾
Xapian and Memcached are where MLOS enters severe, persistent-degradation incidents — sustained regions of order-of-magnitude-worse performance. These two workloads alone drag MLOS's full-suite stable-phase aggregate from +50.5% down to −31.9%, a swing of over 82 percentage points, while TuxBot's aggregate only drops about 15 points across the same addition.
Q8Is TuxBot tied to a specific LLM?▾
No — it supports any OpenAI API, OpenRouter, or Gemini-compatible backend. On a three-workload subset, Gemini 2.5 Flash had the strongest absolute performance tested (+216.7% stable at ~$0.20/session), while Kimi K2 was the strongest cost-efficiency point; Gemini 3 Flash and Kimi K2 both remained clearly positive after convergence (+152.7% and +143.8% respectively), showing the dual-loop architecture's benefit isn't backend-specific.
Q9What counts as a "severe-degradation incident," precisely?▾
At least three consecutive 5-second windows where the normalized quality metric Q_t < 0.1 — meaning at least 15 seconds spent above 10× default latency or below one-tenth of default throughput. With application feedback, TuxBot recorded zero such incidents across all evaluated runs; MLOS, Bayesian optimization, and Q-learning all exceeded 15% incident rates.
Q10What's out of scope for TuxBot?▾
It targets one primary application per session on long-lived, steady-state services — not co-located multi-application tuning, not short-lived jobs or rapid bursty workloads requiring sub-second reactions, and not kernel fast-path controllers (the scheduler, packet scheduler, congestion control itself). It also doesn't autonomously decide when to start or stop a tuning session — that's an external trigger in the current design.
Q11How does this connect to memory-tiering tuning?▾
The paper's related-work section explicitly cites two papers on parameter tuning in memory-tiering systems (Kanellis et al., IEEE TC 2026 and DIMES 2025) as a related but orthogonal OS-side tuning problem. Memory-tiering knobs — migration thresholds, hot/cold classification windows, NUMA toggles — face the same three failure modes (numerically-valid-but-nonsensical combinations, unobservable end-to-end objectives, and a growing knob surface as CXL/tiering systems add controls) that motivate TuxBot's design, though TuxBot itself was evaluated on CFS/DVFS/NAPI knobs, not tiering-specific ones.
Q12What does running TuxBot itself cost, beyond the LLM API calls?▾
Across five Sysbench OLTP-RW runs, TuxBot's local process tree used an average of 0.03 CPU cores and 111 MB peak memory, excluding remote LLM serving. The dominant cost is the per-session API spend — about $0.20 for the default dual-loop configuration on the workloads measured.

Glossary, results, and provenance

Every term in one place, then where the numbers came from.

Core terms
TuxBotThe paper's LLM-based online OS tuner: dual-loop control, typed/bounded actuation, explicit cross-run memory.
Instant loopThe fast tuner (LLM, low reasoning budget), runs every 1–5s tuning interval for local exploration and quick correction.
Reasoning loopThe slower tuner, runs every tens of seconds, re-evaluates broader strategy over a longer history; at most one request outstanding at a time.
Context ManagerAssembles the session specification and per-iteration update from telemetry, knob schema, recent trajectory, and cross-run memory into the prompt sent to the Tuner.
Parameter ValidatorThe sole write path to the OS: checks every proposal against the typed knob schema and declared cross-knob constraints before any write.
Bounded actuationThe paper's term for restricting model authority to typed, schema-legal knob updates — never raw shell or command execution.
Cross-run memoryA vector store (Gemini Embedding + ChromaDB) of prior sessions' traces, retrieved top-3 by early-window telemetry similarity to warm-start new sessions.
TuxBot-TrimA cheaper hybrid: runs TuxBot's LLM loop for 10 windows to shrink the active knob space, then hands control to MLOS for the remaining 20.
Supporting terms
MLOSMicrosoft's tuning infrastructure, run here with SMAC3 (Expected Improvement) — the paper's strongest non-LLM baseline.
Severe-degradation incident≥3 consecutive 5s windows with normalized quality Q_t < 0.1 (≥15s at >10× default latency or <1/10 default throughput).
Q_t (normalized quality)Per-window objective normalized to the Default Parameters mean; Q_t < 1 is a "bad window."
Session specificationThe fixed part of the prompt: role, goal, active knob set/metadata, strategy, and memory prior.
Per-iteration updateThe refreshed part of the prompt: current config, latest measurement, recent action–response trace.
CFS knobslatency_ns, min_granularity_ns, wakeup_granularity_ns, migration_cost_ns — scheduling-period, slice, preemption, and migration-cost controls.
DVFS / idle-state knobsmin_perf_pct/max_perf_pct bound CPU frequency; cstate_max caps idle-state depth.
11-workload subsetThe 13-workload suite minus Xapian and Memcached, isolating ordinary tuning quality from severe-degradation-dominated aggregates.

Classical search/transfer-based DBMS autotuner; representative of the numeric-search tuning family TuxBot contrasts against.

LLM-assisted DBMS tuners that use LLMs to read manuals, prune ranges, or generate candidates before handing off to a conventional optimizer — the offline/hybrid style TuxBot's Trim variant borrows from.

SchedCP / sched-agent hard
