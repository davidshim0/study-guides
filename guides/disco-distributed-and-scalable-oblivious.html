SOSP 2026 · A Field Guide

Shred the tuple, not the table

Every prior oblivious database split a table by rows, handing each server whole tuples — so every hidden swap drags the whole tuple across the network. DISCO splits by columns instead, and the bottleneck disappears.

📄 "DISCO: DIstributed and SCalable Oblivious Joins" · Mavrogiannakis et al. 🎓 TEE / oblivious-computation basics assumed — the primers cover them ⏱ ~30 min read
🗂️

Give each server a SHARD of every tuple, not a SUBSET of whole tuples — then every oblivious primitive runs locally, with no data crossing the network mid-computation.

Quick glossary

TEETrusted Execution Environment — hardware-isolated compute (e.g. Intel SGX) that encrypts code/data from the host OS.
EPCEnclave Page Cache — the protected memory region a TEE can use before paging kicks in (128MB on SGXv1, up to 512GB on SGXv2).

ORAMOblivious RAM — hides which memory address is accessed; a heavier, sequential alternative to the primitives DISCO uses.
Doubly-obliviousStronger than "oblivious": each server's own execution trace is data-independent too, not just cross-server communication.

1What a TEE actually promises▾

A TEE lets you run code on someone else's untrusted machine while keeping the code and data encrypted from the host OS, hypervisor, and cloud operator. Intel SGX, ARM TrustZone, and AMD SEV are examples.

The catch: a TEE hides contents, but not which addresses you touch or when you send network messages. Those patterns can still leak the data.

Now you're ready: DISCO exists to close exactly that gap — hiding access patterns and communication, not just contents.
2Obliviousness — hiding *what you touch*, not just *what it is*▾

An algorithm is oblivious if, for any two inputs of the same size, its memory accesses, control flow, and communication are indistinguishable. An adversary watching everything learns nothing beyond the input size — plus whatever specific, bounded leakage a scheme explicitly permits, such as a query's final output size.

The doubly-oblivious flavor DISCO adopts goes further: each server's own local execution trace must also look identical across inputs, not just the messages between servers.

Now you're ready: "oblivious sort," "oblivious compaction," etc. mean the operation's shape never depends on the data — only on its size.
3Shared-nothing, and the paper's notation▾

DISCO runs on 𝐸servers, each with its own private memory, communicating only by sending messages. 𝑁= total tuples, 𝐵= bytes per tuple, and 𝐵𝑝= 𝐵−|𝑘| is the payload once the computation key 𝑘is set aside.

Each server normally starts with an equal slice, 𝑛= 𝑁/𝐸tuples (horizontal) — the paper's whole contribution is to also offer a per-server slice defined a different way.

Now you're ready: every cost formula in the paper is stated in 𝑁, 𝐸, 𝐵— all public, all known before you see a single tuple.
4Horizontal partitioning — the obvious way to split a table▾

Split table 𝑅into 𝐸equal groups of rows; server 𝑘gets 𝑛= 𝑁/𝐸whole tuples. Every existing distributed oblivious system does this.

Problem: oblivious primitives (sort, compaction) frequently need to swap two tuples that live on different servers, so comparison-swaps constantly cross the network — carrying the entire 𝐵-byte tuple each time.

Now you're ready: horizontal partitioning is the villain of this paper — not wrong, just structurally expensive at scale.
5Vertical partitioning — DISCO's key move▾

Instead of rows, split each tuple into 𝐸shards — one per server — and give every server one shard of every tuple. The small computation key is copied to every shard; the payload is divided among them.

Now every server already holds a piece of every tuple, so primitives like sort and compaction can run locally, with no mid-computation network traffic.

Now you're ready: this is the paper's core observation — nobody had tried it in the oblivious setting before DISCO.
6Why block size (𝐵) matters so much▾

Oblivious algorithms use constant-time conditional swaps: touch every byte regardless of whether the swap actually happens. A bigger tuple means more register operations and more cache lines touched per swap — a 1KB tuple touches 16× the cache lines of a 32B tuple.

Vertical partitioning cuts each server's shard to roughly 𝐵/𝐸bytes, directly shrinking that per-swap cost.

Now you're ready: this is why Figure 1's block-size experiment is the paper's headline chart — real databases have wide, multi-column rows.
7Bucket sort vs. bitonic sort▾

Bitonic sort: a fixed compare-exchange network, 𝑂(𝑁log²𝑁) work, great cache behavior — but needs 𝑂(log 𝐸) communication rounds, expensive once servers are far apart.

Bucket sort: shuffle into random buckets (one communication round, 𝑂(𝑁log 𝑁)), then sort each bucket locally — cheaper across a network, at the cost of some dummy-padding overhead.

Now you're ready: DISCO's hybrid sort picks whichever wins for the current block size and cluster count, per query.
8Compaction and expansion, the two data-movers▾

Compaction: given a table and a "keep this?" bit per tuple, push all the marked tuples to the front, order preserved — used by every filter and join to drop non-matches.

Expansion: given a "make this many copies" count per tuple, produce that many duplicates at the right output positions — used to materialize the 𝑎· 𝑏 output rows a duplicate join key produces.

Now you're ready: both primitives need only a tiny computation key (one bit; ⌈log 𝑀⌉bits) — exactly the case where vertical partitioning is nearly free.
9What the adversary is allowed to see▾

DISCO assumes an adversary who sees everything: all memory accesses, all execution traces, all network traffic, and the schema — but cannot tamper with the CPU itself, and hardware side-channels are out of scope.

Beyond input size, DISCO only ever reveals a small, explicitly-documented set of final output sizes where hiding them would be impractical: filters reveal the number of tuples that pass the predicate, aggregations reveal the number of groups, and non-foreign-key joins reveal the final output cardinality 𝑀 — unavoidable since that output can be as large as 𝑂(𝑁²) and padding to the worst case is impractical.

Now you're ready: every "is this oblivious?" question in the paper reduces to: does this step's cost or shape depend on anything beyond 𝑁, 𝐸, 𝐵, and the specific, permitted output-size leakage for that operator?
The whole story in one place

DISCO in a nutshell

The bottleneck, the fix, and how the pieces chain together.

Prior distributed oblivious systems all use horizontal partitioning: each server holds whole tuples for a subset of rows. Since oblivious primitives constantly need to compare and swap elements that live on different servers, this design forces full-tuple traffic across the network at every step — and that traffic gets worse as tuples get wider (real databases have multi-attribute rows, easily ≥1KB).

DISCO's fix is vertical partitioning: shard every tuple across all 𝐸servers, so each server holds a small piece of every row instead of the whole of some rows. Now compaction and expansion — two of the primitives every query operator is built from — run entirely locally, with communication confined to one exchange before and one after. Sort is more involved: DISCO uses a hybrid bucket-sort framework that still needs bucket exchanges between clusters and a final non-oblivious sort once the data's order has already been hidden by an earlier oblivious random permutation — local per-cluster, but not a single before/after exchange the way compaction and expansion are. Where tuples are already small (so sharding gains little) or the computation key is large (so replicating it costs more than it saves), a hybrid scheme blends vertical partitioning across clusters with horizontal partitioning inside each cluster.

On top of these primitives, DISCO builds joins, filters, and aggregation, plus the first cost-based query optimizer for this setting — one that only ever looks at public parameters (𝑁, 𝐸, 𝐵, query shape), so its decisions leak nothing.

The payoff: 88× faster than Jodes and 180× faster than SODA on non-foreign-key joins at 𝑁=2²⁵; the first oblivious system to scale past a terabyte, reaching 16TB.

🍯 Key takeaways

  • Horizontal partitioning (row-splitting) forces full-tuple network traffic on every oblivious swap — worse as tuples widen.
  • Vertical partitioning (shard every tuple) makes compaction, expansion, and sort run locally per server, at ~𝐵/𝐸 bytes each.
  • Hybrid partitioning blends both, tuned per operator by the query optimizer.
  • Sort still needs a hybrid design (vertical across clusters, horizontal inside) since large sort keys don't shard cheaply.
  • The optimizer's cost model uses only public parameters — no data-dependent statistics, so it stays oblivious.
  • Result: 88×/180× faster joins than Jodes/SODA, and the first oblivious system to break the terabyte barrier (16TB).
Seven everyday pictures

How to think about DISCO

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Partitioning

Shipping a binder vs. shredding it into pages

Horizontal partitioning hands each courier a stack of whole binders — heavy to carry, and if two binders need reordering between couriers, the entire binder travels. Vertical partitioning shreds every binder into pages and gives each courier one page from every binder — light, and any local reordering never needs to leave the room.

Where it breaks: shredding a thin pamphlet (small tuple) into many strips gains nothing — the strips are already smaller than the envelope they're mailed in, which is why tiny tuples favor horizontal or hybrid instead.
The bottleneck · Block size

Moving a shoebox vs. a mattress

A constant-time oblivious swap moves every byte whether or not anything actually changed — like carrying an item across a room regardless of whether you needed to. A shoebox (32B tuple) barely slows you down; a queen mattress (1KB tuple with several columns) means every "maybe-move" now costs real effort, and cache lines pile up fast.

Where it breaks: real tuples aren't monolithic the way a mattress is — you genuinely can cut them into pieces (shards) and carry the pieces separately, which a mattress can't do. That's exactly the trick vertical partitioning exploits.
Compaction · ORCompact

Bumping the "keep" cards to the front, face down

Imagine a card dealer sliding all the cards marked "keep" to the front of the deck, in their original relative order, without ever revealing to onlookers which cards moved or which stayed. That's compaction: only a single keep/drop bit is needed, and the marked tuples end up compacted at the front — used in every filter and join to drop non-matches.

Where it breaks: a real dealer doing this across multiple tables at once would need to shout coordination — DISCO avoids that shout entirely by giving every table (server) a shard of every card first, so each dealer compacts alone.
Expansion · Duplication

A photocopier that knows the print count in advance

Feed the photocopier a document plus a "make 3 copies" note, and it stamps out exactly 3 duplicates at the correct output slots — without you ever seeing whether the note said 1, 3, or 100. Expansion does this for join keys: a key appearing ℓtimes on one side needs ℓcopies pushed to the right output positions for every matching row on the other side.

Where it breaks: a real photocopier reveals the copy count by how long it runs; expansion pads its computation and communication to the total output size 𝑀so timing never leaks the per-tuple count, only the (unavoidable) grand total.
Aggregation tree · Group-wise sums

A relay race baton passed at every handoff zone

Runners within one team pass a baton (a running sum) among themselves freely — that's each server aggregating its own local tuples. But when a group of matching keys straddles two teams' territory (crosses a server boundary), only the baton itself — a tiny constant-size node — needs to cross the handoff zone, not the whole team.

Where it breaks: a real relay only passes the baton forward; DISCO's aggregation tree passes partial sums both up and back down the tree (prefix and suffix), so every runner ends up knowing the team's total, not just the anchor leg.
Sort selection · Bitonic vs. Bucket

A single-elimination bracket vs. a regional mail hub

Bitonic sort is a fixed tournament bracket — every match (compare-swap) is predetermined and fast to referee locally, but with 𝐸 far-flung competitors, results must be relayed across log 𝐸 rounds of long-distance calls. Bucket sort is a regional mail hub: one round of routing everything to the right bucket, then each hub sorts its own pile with no further cross-country calls.

Where it breaks: a real mail hub can lose a package; bucket sort instead pads each bucket with a few dummy slots so overflow probability is provably negligible (2⁻⁶⁰) — nothing is ever actually dropped.
Query optimizer · Public-parameter cost model

A road-map GPS, not a live-traffic one

A classic database optimizer reads live traffic (data statistics) to pick a route. DISCO's optimizer can only consult the road map itself — table sizes, tuple widths, server counts, all public — because looking at live traffic (the actual data) would leak information. It still finds a great route, just from map facts alone: fuse redundant turns, prune unused roads, pick the fastest highway class for the trip length.

Where it breaks: a GPS without live traffic can occasionally pick a technically-shortest route that's not the fastest in practice; DISCO's cost model compensates by using exact, measured deployment constants (bandwidth, per-swap cost) rather than guesses.
The full explanation

How it actually works

Section by section, following the paper's own pipeline.

1 · The problem — horizontal partitioning's block-size wall

Every prior distributed oblivious system (Opaque, SODA, Jodes) splits a table by rows: each server holds 𝑛= 𝑁/𝐸whole tuples. Oblivious primitives constantly need to compare-and-swap elements that live on different servers, so every such swap ships the entire tuple across the network — and constant-time obliviousness means every candidate swap pays this cost whether or not data actually moves.

📦
Concretely: swapping two 1KB tuples touches 16 cache lines each (64B lines); the same swap on 32B tuples touches one. Real database rows, with composite keys and many columns, sit at the expensive end.

2 · The fix — vertical & hybrid partitioning

DISCO instead shards each tuple across all 𝐸servers: the small computation key is replicated to every shard, the payload is split among them. Now every server already holds a piece of every tuple, so primitives execute entirely locally — communication is confined to one shard-exchange before computation and one restructure after.

When the payload is tiny or the computation key is large relative to the payload, further sharding stops paying off (alignment padding means sub-24-byte payloads gain nothing past 3-way sharding). For sorting specifically — where the key itself can be large — DISCO uses hybrid partitioning: servers are grouped into 𝐶clusters, vertically sharded across clusters, and horizontally split within each cluster.

3 · Aggregation tree — sum vs. copy

Group-wise operations (sums within matching-key groups) use a parallel prefix-sum tree. When the operation is a sum, only a constant-size node per tree layer needs to cross server boundaries — each server locally aggregates, then log 𝐸 rounds of 𝑂(1)-size messages stitch groups that straddle servers, up the tree and back down. When the operation is copy (propagating a whole tuple to every member of its group, as joins require), DISCO instead shards the tuples vertically and runs the aggregation locally per shard — the same trick as compaction/expansion.

4 · Hybrid sort — picking bucket vs. bitonic per query

DISCO's sort combines two independent optimizations: Ngai et al.'s in-place bucket swaps and linear communication pattern, and Gu et al.'s 𝑘-MergeSplit, which routes through 𝑘buckets per layer instead of 2 and removes the power-of-two constraint. Within each cluster, servers run the butterfly network's early layers locally, exchange buckets once within the cluster, finish the remaining layers, then apply a non-oblivious sort — safe only because the preceding Oblivious Random Permutation has already broken all ties with prior access patterns.

5 · Non-foreign-key join — three phases

(a) Cardinality exchange: merge both tables, sort by join key, run the aggregation tree to compute each tuple's matching-key count on the other side, then compact back into 𝑅and 𝑆. (b) Expansion: expand both tables to the final output size 𝑀using those cardinalities. (c) Alignment: compute each tuple's output slot by interleaving positions within its group, then a final sort places matching 𝑅/𝑆 rows at corresponding positions.

Because compaction and expansion are chained back-to-back, DISCO applies shard reuse: shard once at the start of the chain, reconstruct once at the end — cutting the join's middle communication term from (3𝑁+𝑀)·𝐵 down to (𝑁+𝑀)·𝐵. A foreign-key join is the same pipeline with early termination: since every foreign key matches exactly one primary key, expansion and alignment are unnecessary — the join finishes after the cardinality-exchange phase.

6 · The query optimizer — rewrite rules over public parameters

# 7 rewrite rules applied across 6 deterministic phases, all on public N, E, B, query shape
1. Operator fusion + parallel branches  # filter–join, filter–agg, join–agg fuse away redundant compactions/sorts; independent branches of the query DAG run concurrently
2. Column pruning        # B → B' = only the columns the query touches
3. Sort propagation      # skip a sort if input is already sorted(k)
4. Shard reuse           # shard once per chain of vertical operators, not per operator
5. Adaptive partitioning  # pick cluster count C per operator vs. resharding cost
6. Sort algorithm choice  # bucket vs. bitonic, by measured cost
🍯
Payoff: on TPC-H TQ6 the optimizer compounds column pruning (4 of 16 columns), filter–aggregation fusion (removes a whole compaction), adaptive partitioning, and sort selection into a 1,027× speedup over the unoptimized plan.
Follow the numbers

Worked examples

Four traces using the paper's real numbers.

① Sizing a vertical shard

A tuple is 𝐵=1024B, split across 𝐸=32 servers, with an 8B computation key replicated to every shard. How big is each shard, and how much smaller is that than the whole tuple?

  1. Payload per server = (𝐵−𝑘)/𝐸 = (1024−8)/32 = 31.75 B, rounded up for alignment ≈ 32B.
  2. Add the replicated key: shard size ≈ 32 + 8 = 40 bytes.
  3. Compare to the whole tuple: 1024/40 ≈ 25.6× smaller per server in raw bytes. Cache lines don't shrink by quite the same ratio: a 1024B tuple spans roughly 16 64-byte cache lines, while a 40B shard fits in about 1 line (alignment permitting) — closer to a 16× cut in cache lines touched per oblivious swap.
🍯
Insight: the wider the tuple, the more this ratio favors vertical partitioning — exactly why the paper's biggest speedups appear at 1024B, not 32B.

② Real speedups from Table 1 (DBLP dataset)

On the DBLP dataset (2.10M input records, 14M output records), SODA takes 7.12s, Jodes 6.49s, and DISCO-Join 0.60s. What are the actual speedup factors?

  1. vs. SODA: 7.12 / 0.60 = 11.9× faster.
  2. vs. Jodes: 6.49 / 0.60 = 10.8× faster.
  3. Scale up to Wiki (1.70GB in, 158.73GB out): DISCO-Join = 94.35s; Jodes = 935.78s → 9.9× faster; SODA doesn't finish (N.A.) at this scale.
💡
Notice the ratio holds roughly steady from small (DBLP) to large (Wiki) inputs — evidence that DISCO's advantage comes from its partitioning design, not just from being tuned for one dataset size.

③ Communication cost of compaction: naive vs. DISCO

A naive distributed adaptation of single-server compaction needs 𝑂(log 𝐸) communication rounds. DISCO's vertical compaction needs a fixed 2 rounds regardless of 𝐸. At 𝐸=32 servers, how many rounds does each need?

  1. Naive: log₂(32) = 5 rounds of 𝑂(𝑁·𝐵) communication each.
  2. DISCO: exactly 2 rounds total (shard-exchange, then restructure) — independent of 𝐸.
  3. At 𝐸=128 (the scalability experiments): naive grows to log₂(128) = 7 rounds; DISCO is still 2. The gap widens with scale.
🍯
Insight: this is why the paper reports "single-round" communication as a headline property — it's not just a constant-factor win, it's a win that grows with server count.

④ TQ6's 1,027× optimizer speedup, decomposed

TPC-H Q6 is a single-table aggregation with a filter and no GROUP-BY, touching 4 of 16 columns. How does the optimizer compound to 1,027×?

  1. Column pruning: only 4/16 columns are active → block size 𝐵′ = 𝐵/4, cutting every downstream primitive's per-swap cost.
  2. Filter–aggregation fusion: the predicate is embedded directly into the aggregation function, eliminating an entire compaction + reconstruction pass (saves 2𝑁·𝐵 bytes).
  3. Adaptive partitioning: the optimizer picks the cluster count 𝐶 that's optimal for the now-smaller 𝐵′, rather than reusing a one-size-fits-all setting.
  4. Sort algorithm selection: at this reduced block size, the cost model picks the cheaper of bucket/bitonic sort directly, rather than a default choice.
💡
No single rule explains 1,027× — it's the product of four independent savings compounding on a query where every rule happens to apply. Queries where fewer rules fire see correspondingly smaller gains: TQ3 15.4×, TQ5 10.6×, and BDB-Q3 5.1×.

Practice problems

Problem 1 · easy
A table has 32-byte tuples with a 24-byte computation key. Would vertical partitioning across 8 servers help much? Why or why not?
Show answer
Barely. The payload is only 8 bytes; splitting 8 bytes across 8 servers gives ~1 byte each, rounded up to alignment (e.g. 8 bytes) — so the shard barely shrinks, while the 24-byte key must still be replicated to every shard, adding overhead. This is the "large computation key" edge case from Section 4/8.1 — horizontal or hybrid partitioning wins here.Misconception: that vertical partitioning always helps. It helps in proportion to how much of the tuple is splittable payload versus a replicated key.
Problem 2 · medium
Why can't DISCO's oblivious compaction just reuse a full oblivious sort as a black box, even though sorting by the "keep" bit would also bring marked tuples to the front?
Show answer
It could — that's the paper's stated naive baseline — but a full sort costs 𝑂(𝑁 log 𝑁) work plus the overhead of a full oblivious routing/sort protocol, when compaction's actual information need is a single bit per tuple. DISCO's dedicated vertical compaction gets single-round communication and lets each server run ORCompact locally, which is asymptotically and practically cheaper than paying for a full sort.Misconception: that "sorting is the universal oblivious hammer." It's correct but wasteful when the underlying operation (compaction) needs far less information than a full order.
Problem 3 · easy
DISCO reveals the number of satisfying tuples for a filter, the number of groups for an aggregation, and the output size 𝑀 of a non-foreign-key join — but a foreign-key join reveals nothing beyond the public input size. Why the difference?
Show answer
A foreign-key join's output size is fixed at the input size (exactly one match per row), so it's naturally size-preserving — nothing beyond the public input size is ever revealed. Filters, aggregations, and non-foreign-key joins all have genuinely data-dependent output sizes (how many rows pass a predicate, how many distinct groups exist, or up to 𝑂(𝑁²) join matches) that would be prohibitively expensive to pad to their worst case, so DISCO accepts revealing that final count as an unavoidable, bounded leak while keeping everything else data-independent.Misconception: that "oblivious" means zero leakage ever. It means leakage is limited to what's provably unavoidable and explicitly documented — here, the final size of an operator whose output size depends on the data.
Problem 4 · hard
SODA's threat model leaks the maximum per-server cardinality, yet DISCO still outperforms it by 180× under a strictly stronger (less leaky) threat model. What does this tell you about where SODA's slowdown actually comes from?
Show answer
The extra leakage SODA accepts isn't what's costing it performance — its slowdown comes from its algorithmic design: multiple rounds of oblivious sorting, sequential computation steps, and heavy horizontal-partitioning-driven inter-server coordination. DISCO shows you can have both a stronger security guarantee and dramatically better performance, because the gain comes from a structural change (vertical partitioning) rather than from cutting security corners.Misconception: that leaking more always buys you speed. Here, DISCO proves the opposite — the partitioning strategy, not the leakage budget, was the real bottleneck.
Problem 5 · medium
The aggregation tree's "sum" mode costs 𝑂(log 𝐸) rounds of 𝑂(1) messages, but its "copy" mode switches to vertical sharding instead. Why does copy need a different strategy than sum?
Show answer
Summing only needs to pass along a running numeric total — a constant-size value per tree layer, cheap to relay across server boundaries. Copying propagates the entire tuple (all its bytes) to every member of a group, which is a full-tuple operation; relaying whole tuples across log 𝐸 rounds would reintroduce the same block-size cost that vertical partitioning was designed to avoid. So "copy" reuses the shard-generate/local-compute/restructure pattern instead.Misconception: that one aggregation-tree design fits all payload sizes. The right strategy depends on whether the propagated value is a small scalar (sum) or a full tuple (copy).
Problem 6 · easy
Why does DISCO's expansion primitive favor vertical partitioning even more strongly than sort does?
Show answer
Expansion's computation key is just the original tuple index and destination index 𝑄[𝑖] — only ⌈log 𝑀⌉ bits, tiny relative to almost any payload. Sort's computation key can be large (multi-column sort keys), which is exactly what erodes vertical partitioning's benefit. Since expansion's key stays small regardless of table width, vertical partitioning almost always wins for it.Misconception: that all primitives benefit from vertical partitioning equally. The benefit scales with how small the required computation key is relative to the payload.
Problem 7 · medium
The optimizer's "shard reuse" rule reduces the join's middle communication term from (3𝑁+𝑀)·𝐵 to (𝑁+𝑀)·𝐵. What operation sequence does this apply to, and why does it work?
Show answer
It applies to the chained compaction → expansion steps inside the non-foreign-key join. Both operate under the same vertical-partitioning layout, so instead of reconstructing tuples after compaction and re-sharding them before expansion (paying a full shard exchange twice), DISCO keeps the intermediate result sharded the whole way through and only reconstructs once at the very end of the chain.Misconception: that each primitive must always reconstruct its output before the next one runs. Chained primitives sharing a partitioning scheme can pass shards directly to each other.
Problem 8 · hard
Bucket sort pads each bucket with dummy elements to bound overflow probability to 2⁻⁶⁰. Why is this necessary for obliviousness, and what would break if buckets were sized exactly to the expected count with no padding?
Show answer
Random routing into buckets means the actual number of real elements landing in any one bucket is a random variable — it could exceed the expected count on some runs. If a bucket overflowed and had to be resized or had elements dropped, the resulting behavior (resize, drop, retry) would depend on the data's specific routing outcome, violating data-independence and leaking information. Padding to a size that makes overflow negligibly improbable (2⁻⁶⁰) ensures the bucket's capacity, and hence all downstream behavior, is fixed and public regardless of the actual data.Misconception: that padding is just a performance safety margin. It's a correctness-for-obliviousness requirement — without it, overflow handling itself would leak data-dependent information.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the one-sentence difference between horizontal and vertical partitioning?▾
Horizontal gives each server whole tuples for a subset of rows; vertical gives every server a small shard of every row — trading "fewer, fatter" per-server items for "more, thinner" ones that never need to leave the server mid-computation.
Q2Does vertical partitioning always beat horizontal?▾
No. It wins when tuples are wide and the computation key is small (compaction, expansion). It loses ground when the payload is tiny (further splitting hits alignment padding) or the computation key is large relative to the payload (sorting on wide keys) — which is exactly why hybrid partitioning and the query optimizer's adaptive-partitioning rule exist.
Q3What exactly does the query optimizer see, and what can't it see?▾
Only public parameters: total input size 𝑁, tuple size 𝐵, server count 𝐸, and the query's structure (which operators, in what order, over which columns). It never inspects the actual data values or their distribution — so its decisions are reproducible by anyone who knows the query and deployment, and reveal nothing extra.
Q4Why does DISCO care about block size (𝐵) so much more than prior systems seemed to?▾
It's not that block size didn't matter before — it's that horizontal partitioning made it unavoidable: every cross-server swap always carries the full tuple. DISCO is the first design where growing tuple size doesn't proportionally grow the per-swap network cost, because vertical partitioning shrinks the shard each server actually needs to move.
Q5What is the LRU-stack-property equivalent here — is there a similarly clever trick?▾
DISCO's core trick is different in kind: instead of one clever measurement structure, it's an observation about data layout — that vertical sharding lets every chained primitive (compaction, expansion) operate locally without reconstructing tuples in between (the "shard reuse" optimization), the closest analogue to getting something for (almost) free.
Q6How does DISCO scale to 16TB when prior systems topped out at 140GB?▾
Two things compound: vertical/hybrid partitioning eliminates most inter-server communication during computation, and each server's per-swap cost no longer scales with full tuple size. Performance still degrades once a server's working set exceeds its EPC (paging kicks in) — the scalability experiments intentionally push past that limit to find where it happens: compaction reaches 16TB, while the more communication-heavy join tops out at 8TB.
Q7Is DISCO close to non-oblivious performance, or still much slower?▾
DISCO-V is 11.9× slower than a plaintext distributed sort-merge join doing the same asymptotic work, and 52.2× slower than a plaintext hash join (which leaks access patterns). That's one-to-two orders of magnitude from non-private — much closer than prior oblivious systems, which remain 15×–180× slower than DISCO itself.
Q8Does DISCO support arbitrary SQL?▾
No — DISCO is a low-level oblivious engine operating on physical query plans (joins, filters, aggregations), with no developer-facing SQL layer. A SQL-to-physical-plan front-end is explicitly left to future work; it targets OLAP-style equi-joins over static data, not inserts/updates/deletes or band/range joins.
Q9What's left open for future work?▾
The authors flag extending the optimizer to window functions and nested subqueries, and exploring cost-based rule ordering (currently the six rewrite phases run in a fixed deterministic sequence).

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
Vertical partitioningSharding every tuple across all servers, so each server holds a piece of every row rather than whole rows for a subset — DISCO's central contribution.
Horizontal partitioningThe standard approach: each server holds whole tuples for a disjoint subset of rows. Forces full-tuple network traffic on cross-server oblivious swaps.
Hybrid partitioningVertical sharding across 𝐶 clusters, horizontal splitting within each cluster — used where pure vertical partitioning underperforms (e.g. sort with large keys).
Oblivious compactionMoves all "keep"-marked tuples to the front, order preserved, using only a single bit of information per tuple.
Oblivious expansionDuplicates each tuple a specified number of times to its target output positions — the core primitive for materializing non-foreign-key join output.
Distributed aggregation treeA parallel prefix/suffix-sum structure computing group-wise aggregates with constant communication per tree layer across server boundaries.
Hybrid sortDISCO's sort combining Ngai et al.'s bucket-sort optimizations and Gu et al.'s 𝑘-MergeSplit, chosen adaptively against bitonic sort by block size and cluster count.
Query optimizerThe first cost-based, obliviousness-preserving optimizer for distributed TEE databases — seven rewrite rules plus a public-parameter cost model.
Supporting terms
Computation keyThe column(s) a primitive operates on (e.g. join key, sort key) — kept small and replicated in vertical partitioning.
PayloadThe remaining tuple bytes after the computation key is set aside — the part vertical partitioning actually splits.
Shard reuseChaining vertically-partitioned primitives without reconstructing tuples between them, cutting redundant shard exchanges.
ORCompactSasy et al.'s state-of-the-art single-server oblivious compaction algorithm; DISCO parallelizes it across vertically-sharded servers.
𝑘-MergeSplitGu et al.'s bucket-sort optimization routing elements through 𝑘 buckets per layer, removing the power-of-two size constraint.
Column pruningThe optimizer rule that restricts execution to only the clusters/columns a query actually references, shrinking effective block size.
NFK / FK JoinNon-foreign-key joins permit duplicate keys on both sides (output up to 𝑂(𝑁²)); foreign-key joins guarantee exactly one match per row.
Doubly-obliviousOblix's strengthened notion: each server's local execution trace, not just cross-server communication, must be data-independent.
