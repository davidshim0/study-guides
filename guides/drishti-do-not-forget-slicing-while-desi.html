MICRO 2025 · A Field Guide

Give the predictor the whole picture, not just one slice

Slice a shared cache across many cores and every state-of-the-art replacement policy quietly goes half-blind — each slice learns only from what it personally sees. Drishti (Sanskrit for "focused gaze") is the fix, and it costs less hardware than what it replaces.

📄 "Drishti" · Sweta, Priyadarshini, Panda · MICRO'25 🎓 Assumes RRIP/SHiP/Belady-emulation basics — primers are quick refreshers ⏱ ~25 min read
👁️

Keep the sampled cache local to each slice, but make the reuse predictor per-core and global — and sample the sets that actually miss, not random ones.

Before you begin

Ten ideas the paper assumes you know

Quick refreshers, not a first course — you already know set-associative caches and RRIP. These cards fill in the sliced-LLC and Hawkeye/Mockingjay-specific pieces the paper builds on.

myopic / local view (the problem) global / accurate view (the fix) Drishti's machinery baseline / random sampling
1Sliced LLC and NUCA▾

Beyond a few cores, a single monolithic last-level cache doesn't scale — so it's cut into per-core slices connected by an on-chip network (a mesh, typically). An address hashes to exactly one "home" slice. AMD Zen3's 32MB L3 is eight 4MB slices shared by eight cores — this is standard on commercial many-core chips.

This is NUCA (non-uniform cache access): a slice near your core is cheap to reach; a far one costs interconnect hops. The paper's baseline gives each core its own 2MB, 16-way slice.

Now you're ready: "sliced LLC" isn't an implementation footnote — it's the whole premise. Every mechanism below (sampled cache, predictor) that used to be one structure is now duplicated, one per slice.
2Set dueling and the sampled cache▾

Set dueling: instead of testing a policy everywhere, monitor a few randomly chosen sets and infer the whole cache's preference from them. Modern policies extend this into a sampled cache — a small structure that watches a handful of LLC sets in detail (not just win/lose counts, but full reuse history per cache line) to train a reuse predictor.

Now you're ready: in a sliced LLC, "a few sampled sets" becomes "a few sampled sets per slice" — and that pluralization is where the trouble starts.
3Hawkeye: emulate Belady, predict friend-or-foe▾

Hawkeye reconstructs what Belady's (offline-optimal) policy would have done on the sampled sets' recent history, then labels each program counter (PC) that issued a load as cache-friendly (its loads would have hit under Belady) or cache-averse (would have missed). Future fills from a friendly PC get a low RRIP value (keep longer); averse PCs get a high RRIP value (evict soon).

Now you're ready: Hawkeye's predictor output is coarse — a binary-ish RRIP value per PC. That coarseness will matter later when we compare how much Drishti helps Hawkeye vs. Mockingjay.
4Mockingjay: from binary to a reuse-distance estimate▾

Mockingjay generalizes Hawkeye's binary call into a continuous one: it predicts each PC's Estimated Time Remaining (ETR) until reuse (a stand-in for Estimated Time of Arrival, ETA, since only relative ordering matters). Sampled-cache hits train the predictor with the observed reuse distance; sampled-cache misses train it with an INFINITE reuse distance.

Now you're ready: Mockingjay's predictions are fine-grained numeric estimates, not a coarse label — so they're more sensitive to noisy or incomplete training data than Hawkeye's are.
5Why PC-based reuse tracking scatters across slices▾

Both predictors key on the PC that issued the load, but the cache line an instruction touches lands wherever its address hashes — a different slice on almost every call. A loop that streams over an array from one PC will scatter its loads across most of the LLC's slices.

Now you're ready: if the sampled cache and predictor both live inside one slice, each slice's predictor only ever sees the fraction of a PC's loads that happened to land there — a fragment, not the full behavior.
6MPKI vs. MPKA▾

You likely know MPKI (misses per 1000 instructions, system-wide). The paper also uses MPKA — misses per kilo access, measured per individual LLC set. It's the local "how much is this one set being stressed" signal, and it varies wildly between sets in the same slice.

Now you're ready: MPKA-per-set is the number Drishti's dynamic sampled cache watches to decide which sets are worth sampling.
7Interconnect traffic: unicast, broadcast, bandwidth▾

A structure accessed by one requester at a time is cheap (unicast). A structure that must notify many other structures whenever it updates (broadcast) costs bandwidth proportional to the number of listeners — and that cost grows with core count. This is the standard many-core design tension: "make it global" often silently means "make it expensive to reach."

Now you're ready: Drishti's entire second design axis is choosing which structure to make global in a way that avoids broadcast.
8Saturating counters▾

A k-bit saturating counter increments toward its max and decrements toward zero, clamping at both ends instead of wrapping. It's a cheap running estimate of "which way has this been trending lately." Drishti uses one 8-bit counter per LLC set (initialized to 128), incremented on a miss to that set and decremented on a hit.

Now you're ready: after enough accesses, the sets with the highest counters are exactly the high-MPKA sets — no explicit division or averaging needed.
9ChampSim, traces, and mixes▾

The evaluation uses ChampSim, a trace-driven simulator (used in the DPC-2/DPC-3 prefetching championships), replaying real SPEC CPU2017 and GAP benchmark traces. Workloads are combined into 70 mixes per core count — 35 homogeneous (same program on every core, different simpoints) and 35 heterogeneous (different programs per core) — to stress the shared LLC realistically.

Now you're ready: every percentage in this guide is a geometric mean over these 70 mixes unless stated otherwise (e.g., "the mcf homogeneous mix" is one specific, called-out data point).
10The 2×2 design space: what's global, what's local▾

Two structures exist per slice today: the sampled cache and the reuse predictor. Each can independently be kept local (per-slice) or made global (shared view across slices), giving four combinations. Today's policies pick "local + local," which is myopic. The paper systematically walks the other three.

Now you're ready: this 2×2 grid is the paper's organizing structure — the Big Idea tab picks it up immediately.
The whole story in one place

Drishti in a nutshell

The problem slicing creates, the fix that doesn't cost bandwidth, and the numbers it buys.

State-of-the-art LLC replacement policies (Hawkeye, Mockingjay, and others) rely on a sampled cache plus a PC-indexed reuse predictor, both built for a monolithic cache. Real many-core chips slice the LLC into per-core pieces. Naively, each slice gets its own copy of both structures — and because loads from one PC scatter across slices by address, each slice's predictor is trained on only a myopic fragment of that PC's true behavior. Across 70 sixteen-core mixes, on average 66.2% of PCs per core map to just one LLC slice throughout execution — but for scattered workloads like xalancbmk that drops to ~40%, meaning the rest of its accesses are invisible to whichever slice's predictor is asked to make a call.

A second, independent problem: the LLC sets chosen for the sampled cache are picked randomly, but real workloads distribute misses very unevenly across sets (MPKA per set varies by 5× or more for mcf). Random sampling wastes half its budget on sets that barely see a miss and have nothing useful to teach the predictor.

Drishti's fix keeps the sampled cache local to each slice (no broadcast needed) but makes the reuse predictor per-core and global — one predictor per core, physically placed near that core's home slice, reachable from every slice via a dedicated low-latency interconnect (NOCSTAR, 3-cycle latency). Separately, it replaces random set selection with a dynamic sampled cache: an 8-bit saturating counter per set (miss-up, hit-down) picks the highest-MPKA sets to sample, re-picking every 128K accesses to track phase changes.

The payoff, 32 cores, 64MB sliced LLC: Hawkeye's +3.3% over LRU becomes +5.6% with Drishti; Mockingjay's +6.7% becomes +13.2% — roughly doubling Mockingjay's benefit — while reducing per-core storage by 7.25KB (Hawkeye) and 2.96KB (Mockingjay).

🍯 Key takeaways

  • Slicing a cache doesn't just split capacity — it silently splits and blinds every per-slice reuse predictor (myopic prediction).
  • Random set sampling wastes budget on low-MPKA sets that teach the predictor nothing.
  • Fix #1: keep the sampled cache local, make the reuse predictor per-core and global — avoids the broadcast a global sampled cache would need.
  • Fix #2: a dynamic sampled cache — saturating counters pick high-MPKA sets, adapting every 128K accesses; falls back to random for uniform-access workloads (e.g., lbm).
  • Needs a dedicated, low-latency interconnect (NOCSTAR, 3 cycles) — a regular on-chip mesh (~20 cycles at 32 cores) erases the gains.
  • 32-core result: Hawkeye +3.3%→+5.6%; Mockingjay +6.7%→+13.2% over LRU — with less hardware, not more.
Six everyday pictures

How to think about Drishti

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks.

Myopic prediction

Three witnesses, three separate diaries

One person's day is watched by three neighbors, each writing a private diary of only what they saw from their own window. Ask any single diary "was this person reliable today?" and you get a fragment, not the truth — because the person walked past all three windows, but no diary has the whole day. That's a per-slice predictor guessing a PC's behavior from the loads that happened to land in its own slice.

Where it breaks: diaries can be compared after the fact; Drishti needs the answer live
Centralized predictor / sampled cache

One switchboard, everybody calling in

An old telephone switchboard where every call in the building routes through a single operator. It works when the building is small. Add more floors (cores) and the operator becomes the bottleneck — every call waits, and the operator must relay ("broadcast") information back out to everyone who might care. A single centralized predictor for 32 cores sees over 65 accesses per kilo-instruction on average (max 257.76 for mcf) — the switchboard is drowning.

Where it breaks: a real switchboard operator can prioritize urgent calls; hardware bandwidth doesn't negotiate — it's a hard ceiling, which is why Drishti avoids centralization outright rather than trying to make it "smarter."
Drishti's fix · per-core, yet global predictor

A personal assistant who answers every desk

Instead of one overloaded operator, give each person (core) their own personal assistant, seated near their usual desk — but reachable by anyone in the building who needs to relay information about that person. No broadcasting: a message about person 12 goes straight to assistant 12, not to everyone. That's the per-core yet global predictor: average traffic drops to 2.46 accesses per kilo-instruction — about 26× less than the switchboard.

Where it breaks: a human assistant tolerates a slow walk down the hall; hardware doesn't — a slow path to "the assistant's desk" (interconnect latency) can erase the whole benefit, which is exactly why NOCSTAR exists.
Dynamic sampled cache

Polling the busiest precincts, not random ones

To predict an election you don't poll 32 random addresses — you weight toward the precincts that actually swing. Some cache sets ("precincts") get pounded with misses; others barely see traffic. Random set sampling polls addresses blindly; Drishti's saturating counters find the high-miss sets and sample those. On a 16-core mcf mix, targeting the top-MPKA sets beat targeting the bottom-MPKA sets by roughly 2× (16.4% vs 8.3% speedup over the random baseline).

Where it breaks: an election has one polling day; workloads have phases. Drishti re-polls every 128K accesses, but a real pollster wouldn't re-survey mid-election — hardware has to, because "which sets matter" shifts as the program runs.
Uniform-demand fallback

No point surveying if everyone agrees

If every voter in every precinct already agrees, targeted polling buys you nothing — random sampling would have told you the same story. A streaming workload like lbm hits every LLC set roughly equally (uniform MPKA). Drishti detects this (counters barely diverge, spread <100) and turns off the dynamic sampled cache, reverting to plain random sampling rather than paying for targeting that can't help.

Where it breaks: real elections rarely have that much agreement, so the analogy is a limiting case — but that's the point: it flags exactly when the "clever" mechanism has nothing left to be clever about.
"Drishti" · focused gaze, low latency

A spotlight, not a floodlight

A floodlight illuminates everything dimly and wastes power lighting up nothing in particular. A spotlight — Drishti, "focused gaze" — aims precisely where it matters and reacts fast. Both of the paper's enhancements are exactly that: a predictor that's global but individually addressed (not broadcast to everyone), and a sampled cache that watches specifically the sets under real pressure (not everywhere equally).

Where it breaks: a spotlight operator can be slow and it's just less dramatic; the hardware equivalent — interconnect latency — has a hard threshold (~20 cycles at 32 cores) past which the whole benefit reverses into a slowdown. Focus without speed doesn't help.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The problem — loads scatter, predictors go blind

A single PC issues a stream of loads; their addresses hash to whichever LLC slice owns that address, scattering across the chip. With today's design (local sampled cache + local predictor, per slice), each slice's predictor is trained only on the loads that happened to land there — a myopic, incomplete view of that PC's real reuse behavior.

2 · The 2×2 design space

Keep each structure local, or make it global (and if global, centralized or distributed). Four real options once you exclude "everything local" (myopic) and "everything global" (no different from centralizing, and unnecessary):

LocalGlobal (centralized)YesHighNo
LocalGlobal (distributed, per-core)YesLowNo
💡
Why the winner avoids broadcast: when the sampled cache is global, several slices' predictors may hold entries for the same PC (even hashed with core-ID), so any update must reach all of them — a broadcast. When the predictor is global and the sampled cache stays local, only one predictor entry exists per core; an update is a single unicast message.

3 · Enforcing it: NOCSTAR

Making the predictor per-core-yet-global still means any slice's sampled cache may need to reach any core's predictor. On the regular on-chip mesh, that adds ~20 cycles of average latency at 32 cores — enough to erase the gains (measured slowdown: 2.8% at 4 cores, 5.5% at 16, 9% at 32, up to 40% for an mcf mix). Drishti adds NOCSTAR, a dedicated, latchless, circuit-switched side-band interconnect linking every slice to every predictor with just 3 cycles of latency, at negligible area/power cost (0.005mm² and ~2.4mW combined, versus 1.85mm² and 60mW for a single 2MB slice).

4 · Enhancement II: the dynamic sampled cache

Each LLC set in a slice gets an 8-bit saturating counter, initialized to 128 (2⁸/2): +1 on a miss to that set, −1 on a hit. After ~32K accesses (one slice's worth of cache lines), the sets with the highest counters — the highest-MPKA sets — become the sampled sets. Re-selection happens every 128K accesses to track phase changes. If the spread between the highest and lowest counter is under 100, the workload is judged uniform (like lbm) and Drishti falls back to plain random sampling instead of paying for targeting that wouldn't help.

🍯
Fewer sets are needed, not more: because sampled sets are now the informative ones, Hawkeye needs only 8 sampled sets per slice (down from 64) and Mockingjay only 16 (down from 32) — smaller and more effective at once.

5 · Drishti end to end

  1. A PC's loads scatter across slices by address, as always.
  2. Each slice's local, dynamically-selected sampled cache logs hit/miss and PC for accesses that land on its own (now high-MPKA-targeted) sampled sets — nothing changes here about locality.
  3. Every logged access is routed via NOCSTAR to that core's one predictor, wherever it physically sits.
  4. The per-core predictor trains on the union of every slice's fragment — restoring the global view without a centralized bottleneck.
  5. On a fill, the predictor returns a value (RRIP for Hawkeye, an ETA/ETR counter for Mockingjay) — this replacement decision now reflects the whole PC's behavior, not one slice's slice of it.
Follow the numbers, step by step

Worked examples

Four traces through the paper's real measurements — hardware budget, set targeting, traffic, and the final performance uplift.

① The hardware budget actually shrinks

Table 3 gives per-core storage (16-way, 2MB LLC slice) with and without Drishti. Does the new saturating-counter array eat the savings?

  1. Hawkeye without Drishti: Sampled Cache 12KB + Occupancy Vector 1KB + Predictor 3KB + RRIP counters 12KB = 28KB.
  2. Hawkeye with Drishti: Sampled Cache shrinks 12KB → 3KB (8 sampled sets instead of 64); everything else unchanged, plus 1.75KB of saturating counters. Total = 3 + 1 + 3 + 12 + 1.75 = 20.75KB.
  3. Net change: 28 − 20.75 = 7.25KB saved per core — the sampled-cache shrink (9KB) more than pays for the counter overhead (1.75KB).
  4. Mockingjay without Drishti: Sampled Cache 9.41KB + Predictor 1.75KB + ETR counters 20.75KB = 31.91KB.
  5. Mockingjay with Drishti: Sampled Cache 9.41KB → 4.7KB (16 sets instead of 32), plus 1.75KB counters. Total = 4.7 + 1.75 + 20.75 + 1.75 = 28.95KB. Net saving: 31.91 − 28.95 = 2.96KB per core.
🍯
Insight: Drishti's dynamic targeting is so much more efficient than random sampling that it needs 8× fewer sampled sets (Hawkeye) or 2× fewer (Mockingjay) — the accuracy gain comes with a storage discount, not a tax.

② Which sets you sample matters more than how many

Table 1: on a 16-core homogeneous mcf mix, Mockingjay's random-sampling baseline is compared against three fixed strategies for choosing 32 sampled sets per slice.

  1. Case I — top 32 highest-MPKA sets: +16.4% speedup over the random baseline.
  2. Case II — bottom 32 lowest-MPKA sets: only +8.3%.
  3. Case III — 16 highest + 16 lowest: +9.5%, barely better than all-low despite half the sets being the good ones.
  4. Reading the gap: Case I roughly doubles Case II's gain, and mixing in low-MPKA sets (Case III) drags the all-high result down almost to the all-low level — a little noise contaminates a lot of signal.
💡
Low-MPKA sets are mostly hits — repetitive, low-information training data. High-MPKA sets see a rich mix of hits and misses, which is exactly what a reuse predictor needs to calibrate against. This experiment is the direct justification for Drishti's saturating-counter set selection.

③ Traffic and the latency cliff

Figure 10 (Mockingjay, 32 cores, averaged over 70 mixes) compares predictor access traffic for a centralized predictor vs. Drishti's per-core-yet-global one.

  1. Centralized predictor: average >65 accesses per kilo-instruction; worst case (mcf) 257.76.
  2. Per-core yet global predictor: average 2.46 accesses per kilo-instruction; worst case 8.05 per core.
  3. Reduction: roughly 65/2.46 ≈ 26× less average traffic, and 257.76/8.05 ≈ 32× less at the worst case.
  4. But latency still bites: without a dedicated interconnect, average slice-to-predictor latency is ~20 cycles at 32 cores, producing a 9% average slowdown (up to 40% for mcf) — worse than not having Drishti at all.
  5. NOCSTAR fixes it: at 3 cycles, well under the ~5-cycle threshold where the paper observes slowdown becomes negligible.
🍯
Insight: reducing bandwidth demand (26–32×) and reducing latency are two separate problems — Drishti's design solves the first, NOCSTAR solves the second, and you need both.

④ The final uplift, and why Mockingjay gains more

32-core, 64MB LLC, 70 mixes (Table 6 / Fig. 14).

  1. Weighted speedup over LRU: Hawkeye 3.3% → D-Hawkeye 5.6% (+2.3pp, a ~70% relative gain). Mockingjay 6.7% → D-Mockingjay 13.2% (+6.5pp, ~doubling its gain).
  2. Matching MPKI reduction: Hawkeye's average LLC MPKI drop over LRU goes from 10.6% → 14.1%; Mockingjay's goes from 21.2% → 24.1%.
  3. Why Mockingjay benefits more: Hawkeye's predictor outputs a coarse RRIP label (friendly/averse); Mockingjay's outputs a fine-grained numeric ETR. Fine-grained estimates are more sensitive to incomplete (myopic) or noisy (randomly-sampled) training data — so fixing both problems helps Mockingjay proportionally more.
  4. Best single case: the mcf_1554B 32-core mix hits 77% speedup with D-Mockingjay vs. 59% with plain Mockingjay — driven mostly by the dynamic sampled cache, since this mix has strongly non-uniform per-set MPKA.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
AMD Zen3's 32MB L3 is split into eight 4MB slices shared by eight cores. A single PC issues loads whose addresses hash across all eight slices roughly evenly. Under the baseline (local sampled cache + local predictor), how much of that PC's true reuse behavior does any one slice's predictor see?
Show answer
Roughly 1/8 of it — only the loads that happened to hash to that particular slice. Each slice's predictor trains and predicts based on this fragment alone, unaware the same PC generated seven other fragments elsewhere.Misconception: that slicing only affects capacity, not correctness of the replacement decision. It also fragments the training data every PC-based predictor relies on.
Problem 2 · medium
Why does Drishti choose "local sampled cache + global predictor" over "global sampled cache + local predictor," when both restore a global view?
Show answer
Because of who needs to be notified on an update. With a global sampled cache, several slices' local predictors can hold entries for the same PC (even with core-ID hashing), so every update must be broadcast to all of them. With a local sampled cache and one global predictor per core, there's exactly one destination for any given core's update — a single unicast message, no broadcast.Misconception: that "global" always means the same cost regardless of which structure you globalize. The direction of information flow (one sampled cache → many predictors, vs. many sampled caches → one predictor) determines whether you need a broadcast.
Problem 3 · easy
A saturating counter for an LLC set starts at 128 (8-bit, k=8). Over a monitoring window it sees 40 misses and 55 hits, in some order, clamped between 0 and 255. Roughly where does it end up, and is this set a good sampling candidate?
Show answer
Net change ≈ +40 − 55 = −15, landing around 113 — below the 128 start. A set that ends up below its starting value is trending toward more hits than misses (low MPKA) — a weaker sampling candidate. Drishti selects the sets with the highest ending counters (most misses relative to hits), not this one.Misconception: that any set that's been "busy" (lots of accesses) is worth sampling. It's the miss-heavy sets specifically that teach the predictor something, not merely active ones.
Problem 4 · medium
On the 16-core mcf mix, targeting the top-32 highest-MPKA sets (Case I) gave +16.4% over random sampling, while targeting the bottom-32 lowest-MPKA sets (Case II) gave only +8.3%. Why isn't Case II's number closer to 0%, given that low-MPKA sets should teach the predictor "nothing"?
Show answer
Case II still outperforms the pre-existing random baseline slightly, because random sampling mixes in even worse choices (very sparse, uninformative sets) that the deliberate "all lowest" strategy at least avoids by being an intentional, consistent policy applied to the same 32-set budget — but it captures far less signal than the miss-rich Case I sets, hence the 2× gap.Misconception: that "low-MPKA" means literally zero information. It means less information relative to high-MPKA sets — the comparison is relative, not against a null baseline.
Problem 5 · hard
Drishti disables the dynamic sampled cache and falls back to random sampling for streaming workloads like lbm. If targeted sampling is strictly at least as good as random, why bother disabling it?
Show answer
When MPKA is uniform across sets (max−min counter spread < 100), there's no signal left to exploit — the "highest MPKA" sets found would essentially be noise in the counters, not a meaningfully better sample than a random one. Continuing to re-select "high-MPKA" sets every 128K accesses under uniform demand adds tracking overhead and instability (constantly re-picking sets based on noise) for zero expected benefit, so the paper explicitly detects this case and reverts to the simpler, cheaper random scheme.Misconception: that a targeting mechanism is "free" as long as it's not actively harmful. Even neutral-benefit targeting costs tracking machinery and stability, so detecting when it can't help is worth doing.
Problem 6 · medium
Without NOCSTAR, using the regular on-chip mesh for slice-to-predictor communication produces a 9% average slowdown at 32 cores (up to 40% for mcf) compared to plain Mockingjay. What does this reveal about Drishti's core mechanism?
Show answer
It reveals that the mechanism's benefit (a globally-informed predictor) and its cost (extra interconnect hops for every sampled-set access) are both real and roughly comparable in magnitude at high latency — so the net effect depends entirely on how fast that path is. At ~20 cycles (regular mesh, 32 cores) the cost dominates; at 3 cycles (NOCSTAR) the benefit dominates. Drishti's design isn't just "add a global predictor," it's "add a global predictor reachable fast enough that its cost doesn't cancel its benefit."Misconception: that once you've solved the bandwidth problem (per-core rather than centralized), latency takes care of itself. Bandwidth and latency are independent costs — Drishti needed a separate mechanism (NOCSTAR) for each.
Problem 7 · hard
Drishti roughly doubles Mockingjay's improvement over LRU (6.7%→13.2%) but only lifts Hawkeye's by about 70% relatively (3.3%→5.6%). Both suffer from the same myopic-prediction and underutilized-sampling problems. What explains the different payoff?
Show answer
Hawkeye's predictor output is a coarse binary-ish classification (cache-friendly vs. cache-averse, mapped to RRIP values); Mockingjay's is a continuous estimate of reuse distance (ETR/ETA). Coarse classifications are more robust to noisy or partial (myopic) training data — a PC only needs to be "mostly friendly" to get classified friendly even from fragmented evidence. A numeric estimate, by contrast, is corrupted proportionally by every missing or noisy data point, so restoring a complete, well-sampled view helps it much more.Misconception: that two policies built from the same two ingredients (sampled cache + PC-based predictor) will benefit equally from the same infrastructure fix. The payoff scales with how sensitive the specific prediction — binary label vs. numeric estimate — is to noise.
Problem 8 · medium
Table 7 marks EVA (Economic Value Added) as unable to use either of Drishti's two enhancements (×, ×), while memoryless policies like RRIP/DIP can use only the dynamic sampled cache (×, ✓). What structural property explains each case?
Show answer
The per-core-yet-global predictor enhancement only makes sense for policies that already have a PC-indexed reuse predictor to relocate and reach via NOCSTAR — RRIP/DIP have no such predictor (they use set-dueling between fixed heuristics, not PC-based learning), so that enhancement doesn't apply to them, but they do have a sampled/dueling-set selection that dynamic sampling can improve. EVA prioritizes lines by a hit-distribution-derived value rather than a PC-indexed sampled-cache-and-predictor pipeline at all, so neither Drishti mechanism — which is built specifically around that pipeline — has a slot to attach to.Misconception: that Drishti is a universal "make replacement policies sliced-LLC-aware" patch. It targets a specific pipeline (sampled cache → PC-indexed predictor); policies without that pipeline need a different fix, if any.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1What exactly does "myopic" mean here?▾
A per-slice reuse predictor is trained only on the loads that happened to land on its own slice — a fragment of a PC's true behavior, not the whole picture. Because addresses scatter loads from the same PC across many slices, that fragment can badly misrepresent the PC's real reuse pattern, especially as core count (and slice count) grows.
Q2Why not just make everything global — sampled cache and predictor both?▾
The paper explicitly rules this out as unnecessary: making either one global already restores a global view, so making both global adds cost (bandwidth, broadcast, or both) for no additional benefit over the cheaper single-structure choice.
Q3Why does a global sampled cache need broadcast but a global predictor doesn't?▾
A global sampled cache serves many local predictors that may all hold an entry for the same PC, so updating it means notifying every one of them (broadcast). A global-but-per-core predictor is the single destination for a given core's PC signatures, so an update is a simple point-to-point (unicast) message.
Q4What is NOCSTAR and why not just reuse the existing NoC?▾
NOCSTAR is a dedicated, latchless, circuit-switched side-band interconnect (adapted from prior distributed-TLB work) that links every LLC slice to every core's predictor in as little as 3 cycles. The existing mesh NoC works but adds ~20 cycles of latency at 32 cores, which the paper shows erases (and can reverse) Drishti's gains.
Q5How does the dynamic sampled cache decide which sets to sample?▾
Each LLC set gets an 8-bit saturating counter, initialized to 128, incremented on a miss to that set and decremented on a hit. After a monitoring window, the sets with the highest counters (most miss-heavy) become the sampled sets; this refreshes every 128K load accesses to track phase changes.
Q6Does Drishti increase hardware cost overall?▾
No — despite adding saturating counters, total per-core storage drops: 7.25KB saved for Hawkeye, 2.96KB for Mockingjay, because far fewer sampled sets are needed once they're chosen intelligently instead of randomly.
Q7Why does the dynamic sampled cache ever turn itself off?▾
For workloads with uniform miss behavior across sets (e.g., the streaming benchmark lbm), targeting the "highest MPKA" sets finds nothing meaningfully different from a random pick, but keeps re-selecting sets based on essentially noise. Drishti detects a small max−min counter spread (<100) and falls back to random sampling to avoid that wasted churn.
Q8Does Drishti apply to any LLC replacement policy?▾
The dynamic sampled cache generalizes to any policy that uses set dueling / a sampled cache, including memoryless policies like RRIP and DIP. The per-core-global-predictor enhancement additionally requires a PC-indexed reuse predictor, so it applies to Hawkeye, Mockingjay, SHiP++, Glider, CHROME, and similar prediction-based policies, but not to memoryless policies or to EVA, whose design doesn't fit that pipeline.
Q9Does the benefit grow with core count?▾
Yes. At 4 cores Drishti's uplift over the base policy is modest (Hawkeye 3.1%→4.2%, Mockingjay 6.4%→6.9%); at 32 cores it's much larger (Hawkeye 3.3%→5.6%, Mockingjay 6.7%→13.2%), because scattering gets worse — and myopia deepens — as more slices divide the same PC's loads more finely.
Q10Why does Mockingjay benefit more than Hawkeye from the same fix?▾
Mockingjay predicts a continuous reuse-distance estimate (ETR), which is more sensitive to incomplete or noisy training data than Hawkeye's coarser binary-ish friendly/averse classification. Fixing the underlying data quality (global view, targeted sampling) pays off more for the finer-grained predictor.
Q11What did the paper deliberately leave out of scope?▾
Machine-learning and reinforcement-learning-based replacement policies (e.g., Glider, CHROME) are evaluated for compatibility (Table 8) but aren't the paper's focus; memory-level-parallelism/concurrency-aware policies (e.g., CARE) are excluded so results aren't confounded by those separate effects. The core contribution is about the sliced-LLC interaction with fundamental sampled-cache/predictor ideas, not proposing a new replacement policy.
Q12Does Drishti still work with hardware prefetching enabled?▾
Yes — the paper tests five state-of-the-art L1/L2 prefetchers (SPP+PPF, Bingo, IPCP, Berti, Gaze) and finds Drishti's gains persist alongside them, though highly accurate prefetchers (SPP+PPF, Berti) reduce the baseline's own LLC misses and thus shrink the remaining room for replacement-policy improvement in general.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
DrishtiThe paper's two enhancements: a per-core (yet global) reuse predictor over a local sampled cache, plus a dynamic (MPKA-targeted) sampled cache — for sliced LLCs on many-core chips.
Myopic predictionA per-slice reuse predictor's problem: it's trained only on the loads that happened to land on its own slice, missing the rest of a PC's scattered behavior.
Sliced LLC / NUCAA last-level cache split into per-core pieces (slices) connected by an on-chip network; access latency depends on distance to the home slice.
Sampled cacheA small structure tracking detailed reuse behavior (hit/miss, PC, timestamp) for a handful of randomly- or dynamically-chosen LLC sets, used to train a reuse predictor.
Per-core yet global predictorDrishti's fix: one reuse predictor per core, placed near that core's home slice but reachable (unicast) from any slice via NOCSTAR — restores a global view without broadcast.
Dynamic Sampled Cache (DSC)Drishti's second fix: saturating counters per LLC set (miss-up, hit-down) select the highest-MPKA sets as sampled sets, re-selected every 128K accesses.
NOCSTARA dedicated, latchless, circuit-switched side-band interconnect linking every LLC slice to every core's predictor in as little as 3 cycles.
MPKAMisses per kilo access, measured per individual LLC set — the local demand signal that drives dynamic set selection.
Supporting terms
HawkeyeEmulates Belady's optimal policy on a sampled cache; labels PCs cache-friendly/averse and maps that to an RRIP insertion value.
MockingjayExtends Hawkeye to predict a continuous Estimated Time Remaining (ETR) per PC, approximating Estimated Time of Arrival (ETA).
RRIPRe-Reference Interval Prediction — an eviction priority scheme; lower values are kept longer, higher values evicted sooner.
Set duelingMonitoring a few randomly chosen sets to infer a policy decision for the whole cache — the ancestor idea behind the sampled cache.
Saturating counterA k-bit counter that clamps at 0 and 2ᵏ−1 instead of wrapping; Drishti uses an 8-bit one, incremented on miss, decremented on hit.
Weighted speedup / HS / MIS / UnfairnessStandard multi-core evaluation metrics: sum of individual speedups, their harmonic mean, the worst individual slowdown, and the max/min speedup ratio.
ChampSimThe trace-driven simulator used for evaluation, extended with a sliced-LLC / NUCA model for this paper.
Homogeneous / heterogeneous mixA multi-core workload where every core runs the same program (different simpoints) vs. different programs per core.
