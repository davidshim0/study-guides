The big idea

By the mid-1980s, operating systems portability had stalled on memory management. Every new architecture's address-translation hardware looked different, and UNIX systems coped by picking one vendor's scheme and simulating it everywhere else: SunOS on the SUN 3 and IBM's ACIS 4.2 on the RT PC both internally emulated VAX memory mapping. That approach tied the OS's virtual memory abstractions to one hardware family, and left 4.3BSD UNIX offering little beyond simple paging support.

Mach's goal was a virtual memory subsystem portable across both uniprocessors and the shared-memory multiprocessors emerging at the time, supporting large sparse address spaces, copy-on-write, memory-mapped files, and user-level pagers, while assuming almost nothing about the underlying MMU beyond the ability to take and recover from a page fault for some page size. Earlier UNIX ports had instead hard-coded VAX-style assumptions, which is exactly what made each new port expensive and fragile.

The key idea is a strict split between machine-independent (MI) data structures, which hold everything the kernel needs to know about a task's virtual memory, and a single machine-dependent (MD) code module and header file, called pmap, which holds only a cache of the hardware's currently active address translations. Because all mapping information can be reconstructed from the MI structures at fault time, pmap is allowed to throw mappings away, delay installing new ones, or batch invalidations, whatever is cheapest on a given architecture, except for the kernel's own mappings, which must always stay complete and correct.

Four data structures carry this split: the resident page table (per-physical-page state such as modified and reference bits), the address map (a sorted, doubly linked list of map entries, each mapping a virtual address range to a region of a memory object, with per-page inheritance and protection attributes), the memory object (the abstraction for backing storage, read and written by a pager task that can be internal to the kernel or an ordinary user-level task), and pmap itself. Copy-on-write between tasks is implemented with shadow objects that collect only the pages a task has modified; true read/write sharing is implemented with sharing maps, which multiple address maps can point to in common.

The MD code for every port the paper discusses, the entire VAX family of uniprocessors and multiprocessors, the IBM RT PC, the SUN 3, the Encore MultiMax, and the Sequent Balance 21000, fits in that one module, about 6 KB of code on the VAX, roughly the size of a device driver, and none of it needed modification to add a later architecture. Despite this generality, the paper reports Mach's VM micro-operations (zero-fill, fork) and whole-kernel compile times matching or beating 4.3BSD UNIX, SunOS 3.2, or IBM ACIS 4.2a on the same hardware, across the VAX, RT PC, and SUN 3.

Key takeaways

  • All hardware-specific VM code lives in one module (pmap) and header; every port (VAX uni/multiprocessor, IBM RT PC, SUN 3, Encore MultiMax, Sequent Balance 21000) reuses the same machine-independent kernel sources unchanged.
  • pmap is a cache of hardware translations, not the authoritative state. The kernel can rebuild any mapping from machine-independent structures at fault time, so pmap may lazily evaluate or defer invalidations, with kernel mappings as the one exception that must always be accurate.
  • Copy-on-write uses shadow objects (empty objects that collect only modified pages and point back at what they shadow); read/write sharing uses sharing maps (address maps referenced by other address maps) that can be split and merged without needing garbage collection.
  • VM operations and paging are exposed through Mach's port/message IPC, so pagers, including the built-in zero-fill pager and a default pager backed by 4.3BSD file systems, can be ordinary tasks implementing a small kernel-to-pager and pager-to-kernel message interface.
  • No multiprocessor Mach ran on supported hardware TLB consistency, so the kernel enforces it in software with three strategies: forced cross-CPU interrupts, deferring reuse of a changed mapping until every CPU has taken a timer interrupt, or tolerating temporary inconsistency when the operation's semantics allow it.
Mechanism, step by step

From per-architecture VM code to one portable kernel

Mach's abstractions, its four VM data structures, the pager interface, shadow and sharing objects, the pmap interface, and what porting it actually took.

1 · Mach's five abstractions

Mach is built from five basic objects. A task is the unit of resource allocation: a paged virtual address space plus protected access to resources such as processors, ports, and virtual memory; a UNIX process is, in Mach, a task with a single thread. A thread is the unit of CPU utilization, roughly an independent program counter inside a task; all threads in a task share its resources. A port is a kernel-protected message queue and Mach's basic reference object, with Send and Receive as its only primitive operations. A message is a typed collection of data, possibly including pointers and port capabilities, exchanged between threads. A memory object is a collection of data, managed by a server, that can be mapped into a task's address space.

Everything other than sending a message is done by sending a message to a port, so system services, including the implementation of tasks, threads, and memory objects themselves, can be provided by user-level server tasks rather than built into the kernel. The paper argues this indirection is affordable specifically because Mach integrates memory management with message passing: large transfers, including whole files or whole address spaces, can move in one message by remapping rather than by copying.

2 · What an application can do to its address space

Each task has a large, sparse address space (up to 4 GB on the RT PC, 2 GB of user space on the VAX) built from an ordered set of mappings to memory objects. All operations on a region must be page-aligned, where the page size is a boot-time parameter that can be any power-of-two multiple of the hardware page size (512 B to 4 KB or more on the VAX, 8 KB or more on the SUN 3).

Inheritance and protection are both per-page. Inheritance controls what a newly created child task receives for a page: shared pages are shared read/write, copy pages are logically copied by value (implemented with copy-on-write for efficiency), and none leaves the child's corresponding address unallocated. Protection is split into a current value, which the hardware actually enforces, and a maximum value, which bounds how high current protection can later be raised; lowering the maximum below the current value also lowers the current value.

Byte offsets into memory objects, rather than any notion of a hardware page, are used throughout the MI code, which is why a "Mach page" need not equal the hardware page size, only a power-of-two multiple of it.

4 · Address maps and page faults

An address map entry's inheritance and protection must be uniform across the whole range it covers, which can force two entries to exist for adjacent regions of the same object simply because their attributes differ. The sorted linked list was chosen because it supports the three most frequent operations cheaply: page-fault lookup, copy or protection changes on a range, and allocation or deallocation of a range, and it does not penalize large, sparse address spaces. Fault lookup is sped up by caching the "last fault" location per fault type and searching outward from there.

Because each entry can cover a large range, a typical address map is small: the paper reports a typical VAX UNIX process has five mapping entries at creation, for its u-area, code, stack, initialized data, and uninitialized data. UNIX fork is implemented directly on these primitives: inheritance defaults to copy for every entry, so a forked child's address space is, by construction, a copy-on-write copy of the parent's, preserving UNIX fork semantics without an eager copy.

5 · Memory objects and the external pager interface

A memory object resembles a UNIX file: a byte-indexed repository supporting read and write, reference-counted so it can be garbage collected once no mapping references it. For frequently reused objects, such as UNIX text segments, the kernel can retain an object (and its physical page mappings) in a cache even after the last reference disappears, if the pager asks for that via pager_cache, making later reuse cheap.

Page faults and pageout for a given memory object can be handled entirely outside the kernel by a pager task, reached through a paging_object port. The kernel also keeps a paging_name port identifying the object and a paging_object_request port the pager uses to manage the object from its side.

Mach ships two built-in pagers: memory with no pager is automatically zero-filled, and pageout for ordinary memory goes to a default inode pager that uses 4.3BSD file systems directly, removing the traditional need for a dedicated paging partition.

6 · Copy-on-write via shadow objects

When a copy-on-write copy is made, both tasks' address maps simply point at the same memory object; as long as both only read, nothing else is needed. The first write by either task allocates a new page, visible only to the writer, to hold the modification. Mach tracks these modifications with shadow objects: an object created on the first copy-on-write fault, initially empty and without a pager, holding a pointer to the object it shadows. A shadow object may itself later be shadowed; a lookup that misses in one shadow follows this chain until it finds the page in some object on the list.

Left unchecked, repeated copy-on-write remapping (a process that forks repeatedly is a simple example) can build long shadow chains. Mach garbage collects an intermediate shadow once it recognizes a newer shadow completely overlaps it. The paper notes this logic is conceptually simple but complicated in practice: unnecessary chains can appear only during heavy paging and are not always visible from in-memory state alone, and letting the paging daemon collect garbage concurrently with ordinary VM operations on multiple CPUs required nontrivial object locking.

7 · Read/write sharing via sharing maps

Shadow objects handle copy-on-write, but not read/write sharing, because sharing operations may involve remapping many existing memory objects at once, and a task may share one region read/write while sharing the same data copy-on-write with a different task. Mach solves this by letting an address map entry point to a sharing map, which is itself an address map, instead of directly to a memory object; the sharing map in turn points to the shared memory objects. An operation meant to apply to every sharer is applied once, to the sharing map. Because sharing maps can be split and merged, they never need to reference other sharing maps to support arbitrary task-to-task sharing, which avoids a second garbage-collection problem on top of shadow objects.

8 · The pmap interface

All machine-dependent mapping lives in one file, pmap.c. pmap need not track every valid mapping: translations can be dropped at almost any time for space or speed, and new ones can be lazily installed, because everything is reconstructable from MI structures at fault time, with kernel mappings as the single exception that must stay complete and accurate. Hardware that makes invalidation expensive can have pmap postpone invalidating or lowering protection until it is actually required.

9 · Porting experience

  1. Mach VM was first implemented on the VAX (MicroVAX II, 11/780, and the four-processor VAX 11/784); a stable VAX version existed within CMU by February 1986.
  2. The IBM RT PC port began at the end of that same month, done by a newly hired programmer with no prior operating systems or C experience; the RT PC version was self-hosting and available to a small group of users by early May 1986, roughly two months later. By the time of writing, about 75 RT PCs were running Mach in the CMU Computer Science department.
  3. Within that RT PC port, implementing the pmap module itself took about three weeks, most of it spent understanding the requirements; the hardest part was getting exactly right the points in the code where hardware TLB validation and invalidation were required.
  4. SUN 3, Sequent Balance, and Encore MultiMax ports followed similar patterns. The Sequent port, done by an expert systems programmer, produced a bootable system just five weeks after programming started.
  5. Every target already ran either 4.2BSD or System V UNIX, which reduced the effort of building device drivers and was, in the authors' account, a significant part of why porting went quickly.

10 · Hardware quirks each port exposed

  1. VAX: a full 2 GB user address space is possible in principle but often impractical, since a linear page table for it needs 8 MB. Rather than paging the page tables themselves (VAX VMS's approach), Mach keeps page tables in physical memory but builds only the parts needed for pages currently in use, creating and destroying table pieces to save space or improve runtime; the VAX's small 512 B page also makes its page tables larger, adding complexity relative to other ports.
  2. IBM RT PC: uses one inverted, hashed page table system-wide instead of per-task tables, giving a full 4 GB address space with no extra overhead from address space size, and reducing Mach's memory needs and map-management complexity for large programs. Its drawback is that it allows only one valid mapping per physical page, so sharing a page across tasks causes extra faults as the page is repeatedly remapped to whichever task last referenced it. Mach ends up treating the inverted table as a large in-memory cache for the RT's TLB; the paper reports these extra faults are rare enough that Mach still outperforms IBM's ACIS 4.2a, which avoids the issue altogether by sharing segments instead of pages.
  3. SUN 3: combines segments and page tables to build per-task maps up to 256 MB, but only 8 hardware contexts exist at once, so more than 8 active tasks compete for contexts and take extra faults, similar to the RT PC's sharing penalty. The SUN 3's physical address space also has large holes, since display memory is addressable as "high" physical memory, which complicates the resident page table into a sparse structure; this was handled entirely inside the SUN's machine-dependent code.
  4. Encore MultiMax and Sequent Balance 21000: both use the National 32082 MMU, which limits a page table to 16 MB of virtual memory (restrictive for a large kernel address space) and limits physical memory to 32 MB (the MultiMax added special hardware to reach a full 4 GB). A chip bug also reports read-modify-write faults as read faults, which breaks Mach's reliance on distinguishing write faults for copy-on-write handling; the paper notes this was addressed in the chip's successor, the NS32382.

Evaluation

What the paper measures, its reported tables, and what they say about Mach's performance and portability cost.

Setup

The paper evaluates two things: the cost of individual VM operations on each ported machine, and the cost of a realistic whole-system workload (compiling the Mach kernel and a set of C programs) on the VAX and SUN 3. Comparisons are against the UNIX each machine originally ran, not against a single common baseline.

Result 1

Basic VM operations are as fast or faster under Mach than under the vendor UNIX, across three architectures

What it shows. Zero-fill of 1 KB: RT PC, Mach .45 ms vs. UNIX .58 ms; MicroVAX II, Mach .58 ms vs. UNIX 1.2 ms; SUN 3/160, Mach .23 ms vs. UNIX .27 ms. Fork of a 256 KB address space: RT PC, Mach 41 ms vs. UNIX 145 ms; MicroVAX II, Mach 59 ms vs. UNIX 220 ms; SUN 3/160, Mach 68 ms vs. UNIX 89 ms.

What to take from it. Mach's copy-on-write fork is roughly 3.5 times faster than the vendor UNIX fork on both the RT PC and the MicroVAX II (this summary's arithmetic), and noticeably faster, though by a smaller margin, on the SUN 3/160. These are isolated micro-operations, not application workloads, and the paper does not report variance or number of trials.

Result 2

Re-reading a file already seen once is much cheaper under Mach

What it shows. On a VAX 8200, reading a 2.5 MB file the first time costs Mach 5.2 sec system / 11 sec elapsed versus UNIX 5.0 sec / 11 sec elapsed, essentially even. Reading it a second time costs Mach 1.2 sec system / 1.4 sec elapsed versus UNIX 5.0 sec / 11 sec elapsed, unchanged from the first read. For a 50 KB file, first read is Mach .2/.7 sec versus UNIX .2/.5 sec; second read is Mach .1/.1 sec versus UNIX .2/.2 sec.

What to take from it. The large gap appears only on the second read, consistent with Mach's ability to keep a memory object's pages cached (via pager_cache) after a mapping is torn down, so a later re-read can reuse them almost for free. The paper does not explain why the UNIX second-time number for the 2.5 MB file does not improve over the first read; it is reported as measured.

Result 3

Compiling the Mach kernel and a 13-program test set is faster than 4.3BSD on the same VAX 8650, under two buffer configurations

What it shows. With 400 disk buffers: the 13 programs compile in 23 sec under Mach versus 28 sec under 4.3BSD; the Mach kernel itself compiles in 19:58 min versus 23:38 min. With the generic (default) buffer configuration: the 13 programs compile in 19 sec under Mach versus 1:16 min under 4.3BSD; the kernel compiles in 15:50 min versus 34:10 min.

What to take from it. Mach's advantage is present under both buffer settings but much larger under the generic configuration, where 4.3BSD's default buffering appears to perform worse. This is a whole-system build workload, so it reflects filesystem and scheduling behavior together with VM, not VM in isolation.

Result 4

A small compile is twice as fast under Mach as under SunOS 3.2 on the same SUN 3/160

What it shows. Compiling the fork test program (the one used for Result 1's fork measurement) takes 3 sec under Mach versus 6 sec under SunOS 3.2.

What to take from it. Consistent with the fork and zero-fill advantage reported for the SUN 3/160 in Result 1, since compiling and linking involves repeated process creation.

Result 5

The port itself was cheap: a novice produced a working system in about two months, with no machine-dependent code later needing changes

What it shows. The IBM RT PC port began at the end of February 1986, carried out by a newly hired programmer with no prior operating systems or C experience, and was self-hosting by early May 1986. Within that effort, the pmap module itself took about three weeks to implement. By the time of writing, roughly 75 RT PCs at CMU ran Mach. The Sequent Balance port, done by an experienced systems programmer, was bootable five weeks after it started. The machine-dependent module is about 6 KB of code on the VAX, and none of it needed modification across the VAX, RT PC, SUN 3, Encore MultiMax, or Sequent Balance ports.

What to take from it. The paper treats these figures as evidence that isolating machine-dependent code lowers the cost of a new port enough for even a first-time OS implementer to complete one quickly. This is a narrative, single-instance claim rather than a controlled comparison against porting a conventional, non-Mach VM system.

What the evaluation does not cover. No multiprocessor VM scalability numbers or measurement of TLB-consistency overhead under load; no performance data at all for the Encore MultiMax or Sequent Balance 21000 beyond the porting-time narrative; nothing on the non-uniform-access (BBN Butterfly, IBM RP3) or message-based (Intel Hypercube) multiprocessor classes the paper discusses, since Mach had not been ported to them; and the 2.5 MB second-read anomaly for 4.3BSD is reported without explanation.
Common questions

FAQ

Q·What problem is this paper actually solving?▾

Portability of virtual memory management. Prior UNIX systems coped with new MMU designs by simulating one vendor's scheme (SunOS and IBM ACIS 4.2 both internally emulated VAX memory mapping), which tied VM features to that hardware. Mach instead designs its VM around minimal hardware assumptions, isolating everything hardware-specific into one module.

Q·What is a pmap, concretely?▾

The single machine-dependent data structure (and the file, pmap.c, that manipulates it) representing the hardware's actual address translation state: a VAX page table, or a set of allocated IBM RT PC segment registers. It implements a small, fixed set of routines (enter a mapping, remove a mapping, change protection, and so on) that the machine-independent kernel calls.

Q·Why is it acceptable for pmap to forget mappings?▾

Because the machine-independent resident page table and address maps hold the authoritative record of every mapping. If pmap drops a translation, the next access simply faults, and the kernel reconstructs it from the MI structures. The one exception is the kernel's own mappings, which pmap must keep complete and accurate at all times, since there is no fallback "fault into the kernel map" path.

Q·How does Mach's fork avoid copying the whole address space?▾

By default every address map entry's inheritance attribute is copy. On fork, the child's address map entries are created pointing at the same memory objects as the parent's, marked copy-on-write. Only when either task writes a page does the kernel allocate a shadow object and copy that one page, not the whole space.

Q·What is the difference between a shadow object and a sharing map?▾

A shadow object implements copy-on-write: it starts empty and only accumulates pages a task has itself modified, falling back to the object it shadows for everything else. A sharing map implements genuine read/write sharing: it is itself an address map that several tasks' address map entries point to, so an operation applied to the sharing map is visible to every task sharing it.

Q·Who writes pages back to disk, the kernel or something else?▾

Either. Each memory object has an associated pager, which can be internal kernel code (the built-in zero-fill pager, or the default pager backed directly by 4.3BSD file systems) or an ordinary user-level task reached through ports. The kernel sends the pager messages like pager_data_request and pager_data_write; the pager answers with messages like pager_data_provided.

Q·Why would a protection change be allowed to apply at different times on different CPUs?▾

No multiprocessor Mach ran on could flush a remote CPU's TLB directly or guarantee TLB consistency in hardware. For operations whose semantics do not require simultaneity, such as lowering a page's protection, the kernel allows temporary inconsistency (it is fine for one task's view to change before another's) rather than paying the cost of forcing every CPU to flush immediately.

Q·What VM-related hardware problems did each port actually hit?▾

VAX page tables for a full 2 GB address space need 8 MB, so Mach builds only the needed portions in physical memory. The RT PC's inverted page table permits only one mapping per physical page, causing extra faults when a page is shared. The SUN 3 has only 8 hardware contexts and physical-address holes from display memory. The Encore MultiMax and Sequent Balance's shared National 32082 MMU caps page tables at 16 MB of virtual memory and 32 MB of physical memory, and has a chip bug that reports read-modify-write faults as read faults, which interferes with Mach's copy-on-write fault handling.

Q·How can an inverted page table help rather than hurt?▾

A conventional per-task linear page table grows with address space size; the RT PC's single system-wide inverted table, looked up by hashing the virtual address, does not, so it covers a full 4 GB address space with no extra overhead and a smaller memory footprint for large programs. Its cost is that each physical page can hold only one mapping, so sharing a page across tasks causes extra remap faults; the paper reports this cost was small enough in practice that Mach still outperformed ACIS 4.2a on the same hardware.

Q·How much code does a new port actually require?▾

A single machine-dependent module and header file, about 6 KB of code on the VAX, comparable to a device driver. The paper reports that, across every architecture it discusses, no existing machine-dependent code needed modification to support a later port.

Q·Does Mach outperforming 4.3BSD or SunOS mean Mach is simply a faster kernel?▾

The paper's claim is narrower: that making VM machine-independent did not cost performance, and in several measured cases (fork, re-read, compilation) Mach was faster than the vendor UNIX on the same hardware. It does not claim Mach is generally faster for every workload, and it reports single measurements without variance or trial counts.

Q·Could Mach's VM run on a multiprocessor with non-uniform memory access, like the BBN Butterfly?▾

At the time of writing, no: Mach had only been ported to uniform-shared-memory multiprocessors (Encore MultiMax, Sequent Balance 21000). The paper argues its integration of memory management with message passing, including copy-on-reference sharing across a network, generalizes toward looser coupling, and says experimentation and ports in that direction were underway, but reports no results for it.

Q·Did these ideas go anywhere after this paper?▾

(general knowledge) Mach's VM design, including pmap, memory objects, and external pagers, carried forward into later Mach releases and influenced BSD-derived and microkernel-adjacent systems, including Mach-based work that fed into NeXTSTEP and, later, macOS's XNU kernel. The paper itself makes no such forward-looking claim; this is added context, not a result it reports.
