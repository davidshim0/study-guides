Let SMs cooperate instead of waiting at a kernel boundary

MoE routing and variable-length batches make GPU kernel shapes wildly dynamic. The fix isn't a smarter single kernel — it's letting Streaming Multiprocessors hand off work to each other directly, mid-flight.

📄 "Taming Dynamism on GPUs" · He, Sun, Li, Du, Xia, Chen 🎓 GPU architecture basics assumed — primers cover them ⏱ ~25 min read
🔗

Don't enforce cross-phase dependencies with separate kernels and HBM round-trips — enforce them with direct SM-to-SM handoff, reduced the instant data lands.
Fuse the whole GPU, not just one SM.

Before you begin

Quick glossary + eight primers

Acronyms first, then the concepts the paper assumes. Skip anything you already know.

Quick glossary

SMStreaming Multiprocessor — a GPU's core compute unit; a modern GPU has 80–150+ of them.
SIMTSingle-Instruction-Multiple-Thread — the GPU execution model; warps of 32 threads run in lockstep.
GPCGraphics Processing Cluster — a physical group of SMs; only SMs in the same GPC have direct on-chip links.
BSPBulk Synchronous Parallel — everyone finishes phase N before phase N+1 starts. The classic (and limiting) GPU kernel model.
TMATensor Memory Accelerator — hardware unit for async, high-bandwidth memory transfers, offloaded from compute.
CTACooperative Thread Array — CUDA's term for a thread block.
MoEMixture-of-Experts — a model layer that routes each token to a subset of "expert" sub-networks.
MLA / GQA / NSAAttention variants (Multi-head Latent, Grouped-Query, Native Sparse) used in modern LLMs like DeepSeek/Qwen.
SM cooperation / cross-SM fusion (the fix) dynamic phase (split-KV, combine, MoE) Meld's machinery kernel boundary / HBM round trip (the problem)
1The thread → warp → block → grid hierarchy▾

A thread runs on a core; 32 threads in lockstep form a warp; several warps scheduled onto one SM form a thread block; many blocks form a grid (one kernel launch). Traditionally, each block runs independently on one SM — SMs don't talk to each other.

Now you're ready: Meld's whole premise is breaking that "SMs don't talk" rule.
2The memory hierarchy, and why HBM is slow▾

Registers (thread-private) → shared memory/L1 (per block) → L2 (chip-wide) → HBM/GDDR (off-chip, the slowest hop). On H100, HBM-proxied SM-to-SM transfer runs ~20 GB/s; the new on-chip SM-to-SM interconnect runs 81 GB/s with 1/7 the latency.

Now you're ready: every time a kernel boundary forces a store-then-reload through HBM, that's the slow 20 GB/s path. Meld's fix routes around it.
3Kernel launches and BSP-style boundaries▾

A kernel boundary is a hard synchronization point: every block of kernel N finishes before any block of kernel N+1 starts (BSP). It's the only tool traditional GPU programming has for enforcing "phase 2 needs phase 1's results."

Now you're ready: that hard barrier is the root inefficiency Meld attacks — it forces correctness at kernel granularity when the real dependency is much finer-grained.
4Dynamic workloads: why shapes stopped being fixed▾

Pretraining had uniform, static shapes. Inference doesn't: continuous batching mixes sequences of very different lengths, reasoning models skew that further, and MoE activates a different, skewed set of experts per batch.

Now you're ready: a kernel tuned for one shape pads or idles badly on another — this is the "long tail" problem Fig.1(a) shows.
5Multi-phase execution (split-KV / combine)▾

To fight the long tail, modern kernels split a task into sub-tasks run in parallel (partial phase, e.g. split-KV attention across sub-sequences), then merge the partial results (reduce phase, e.g. combine). This is the dominant pattern across attention, MoE, RMSNorm, top-k, and more (Table 1).

Now you're ready: the reduce/combine phase is exactly the low-parallelism bottleneck Meld targets — FlashMLA's combine phase gets only 10.3% SM occupancy.
6On-chip SM-to-SM interconnects & clusters▾

Starting with Hopper, CUDA exposes a thread block cluster: a group of up to 16 SMs that can read/write each other's shared memory directly, with hardware mbarrier synchronization. But the underlying physical grouping (GPC) is fixed and undisclosed by NVIDIA — and heterogeneous in size.

Now you're ready: a naive "always use cluster size 16" wastes most of the chip (§2.4) — Meld has to reverse-engineer and work around the real topology.
7Kernel fusion — intra-SM vs. cross-SM▾

Traditional fusion merges operators within a thread block's computation (e.g. fusing matmul + softmax), because a block only ever talks to itself. It cannot fuse across a phase boundary that spans different blocks/SMs.

Now you're ready: "cross-SM kernel fusion" is exactly what the name says — pushing fusion's scope from one SM to the whole GPU.
8Declarative vs. coupled programming▾

Compilers like Triton/TileLang let you write Y = F(X), but the mapping of work onto blocks/SMs is usually decided once, at compile time (e.g. a fixed split-K). That mapping can't adapt when X's shape changes every batch.

Now you're ready: Meld's "decoupled execution" defers that mapping to runtime, informed by the actual input shape.
The whole story in one place

Meld in a nutshell

The problem, the two insights that fix it, and how the pieces connect.

Dynamic LLM workloads (MoE routing, variable-length batching) force kernels into multiple phases — a parallel partial phase and a merging reduce phase. Because SMs traditionally can't talk to each other, the only way to guarantee phase 1 finishes before phase 2 starts is a kernel boundary — a full-GPU synchronization barrier. That barrier is expensive in three ways: it can't rebalance load within a phase, it leaves the reduce phase badly underutilized (FlashMLA's combine phase: 37% of time, 10.3% SM occupancy), and it forces every intermediate result through slow off-chip memory.

Meld's fix is cross-SM kernel fusion: use the on-chip SM-to-SM interconnect (4× the bandwidth, 1/7 the latency of HBM) to let a producer SM forward its intermediate result directly into a consumer SM's shared memory and move on to its next sub-task, instead of stopping and materializing to HBM. Because the transfer is asynchronous and hardware-tracked (mbarrier), the result is usually there before the consumer needs it — just-in-time reduction: wait-free, local, in SRAM.

This only works if the mapping of sub-tasks to SMs is decided at runtime, not compile time — so Meld pairs it with a decoupled execution model: developers declare computation as composed operators (Iter, Map, Reduce, …); the runtime scheduler decides the actual hardware mapping and cooperation plan per input shape.

The payoff: Meld beats the best existing hand-tuned kernel or compiler by 1.3× on average (up to 2.04×) across attention, MoE, NSA, RMSNorm, and cross-entropy loss, translating to up to 1.4× end-to-end inference throughput.

🔗 Key takeaways

  • Kernel boundaries enforce dependencies at the wrong granularity — coarse, phase-level, whole-GPU.
  • SM-to-SM interconnects let dependencies be enforced at sub-task granularity instead, via direct handoff.
  • Just-in-time reduction: async transfer + hardware barriers make the merge step wait-free and local.
  • GPU on-chip topology is heterogeneous and localized (GPC groups of 2–20 SMs) — naive clustering fragments the chip.
  • Decoupled execution: developers declare logic (operators); the runtime decides mapping per input shape.
  • Meld bypasses the GPU's own scheduler with per-SM instruction queues for precise, topology-aware mapping.
  • Result: 1.3× avg (up to 2.04×) kernel speedup; up to 1.4× end-to-end throughput; <1.5× compile-time cost.
Five everyday pictures

How to think about cross-SM fusion

Each stands alone. Every card ends with where it breaks down.

SM cooperation vs BSP

A relay race with a mid-track handoff

Old-style relays wait for every runner to cross a painted finish line before the next leg starts. Meld's cooperation is a baton passed hand-to-hand, mid-stride, the instant the next runner is ready — no line, no waiting for the slowest lane.

Where it breaks: real relay legs are fixed in order; SM cooperation is much more flexible — any SM in a cluster can hand off to any other, in either direction.
Just-in-time reduction

A sous chef plating as dishes arrive

Instead of waiting for every station to finish before assembling the plate, the sous chef gets each component the moment it's ready and folds it in immediately — no dish sits cooling on a pass-through shelf (HBM) waiting to be picked up.

Where it breaks: the "arrival" isn't guesswork — a hardware barrier (mbarrier) tells the consumer exactly when data is ready, so nothing is ever used before it lands.
Heterogeneous topology

Neighborhood streets vs. the post office

Houses on the same block (a GPC) can hand a package straight to a neighbor. Send it across town and it has to go through the post office (HBM) — slower, and a shared bottleneck. GPC group sizes vary from 2 to 20 SMs per GPU, so "the same block" means different things in different places.

Where it breaks: a real map is fixed; NVIDIA's firmware actually masks manufacturing-defect-driven topology differences so every chip of a given model looks identical to software.
Decoupled execution

A recipe card, not a rigid factory script

A recipe says "reduce the sauce," not "SM #12 must do it at cycle 4000." Developers write what to compute (operators like Iter/Reduce); Meld's runtime — like a chef reading the room — decides who does what, and when, based on tonight's actual orders (input shapes).

Where it breaks: the runtime's "improvising" is not ad hoc — it follows a scheduling algorithm (hierarchical, hybrid-cut) that's deterministic given the input shape and cached across steps.
Instruction queue, bypassing the scheduler

A dispatcher's clipboard, not a lottery

The GPU's own block scheduler is a black box — you can't tell it "put this exact task on that exact SM." Meld sidesteps it entirely with a per-SM instruction queue: a dispatcher's clipboard each SM reads down, task by task, exactly as planned.

Where it breaks: this only works because Meld also launches one wrapper block per SM to "hold the seat" — it still has to fully saturate the GPU first to guarantee that placement.
The full explanation

How it actually works

From the problem's root cause to the runtime that executes the fix.

1 · Root cause — dynamic cross-SM dependencies

Multi-phase kernels (split-KV → combine, MoE's GEMM-1 → GEMM-2 → weighted-sum) exist to fight the long tail of dynamic workloads. But the dependency between phases is enforced only by a kernel boundary, causing three costs: (I-1) intra-phase imbalance from static, pre-defined tiling; (I-2) a low-utilization reduce phase — FlashMLA's combine is 37% of time at 10.3% SM occupancy, NSA's top-k is 51% of time at 9.4%; (I-3) memory traffic — FlashMLA's intermediate state is 32 KB per sub-task, forced through HBM.

2 · The fix — SM cooperation and just-in-time reduction

Instead of a kernel boundary, the producer SM finishes its split-KV sub-task, asynchronously forwards the result over the on-chip link into the consumer's shared memory, and immediately proceeds to its next sub-task. The transfer uses TMA (async, hardware-tracked) and an mbarrier; the consumer performs the reduction directly in local SRAM once the barrier reports the data has arrived — waiting-free because it's already there. This decomposes one coarse, kernel-level dependency into many fine, sub-task-level ones, which is what lets long tasks be shared across SMs and short tasks fill the gaps.

3 · Programming model — operators, not hand-mapped kernels

Developers compose Iter/Map (partial), Reduce, Reshard, Gather, and Finalize operators. The chaining syntax only declares dataflow — actual sub-task partitioning and cooperation are resolved at runtime (Fig.6).

with ParallelTasks(NUM_HEAD, batch) as (head, seq):
    partial(attnSplitKV(seq, head, Q, K, V))
      .reduce(attnCombine())
      .finalize(attnFinalize(seq, head, Output))
💡
The affinity abstraction on Iter also marks ranges eligible for copy absorption — one SM loads shared data (e.g. a common KV-cache prefix) and broadcasts it over the on-chip link, instead of every SM redundantly refetching from HBM.

4 · Hierarchical scheduling

Tier-1 assigns task groups to hardware clusters via a hybrid cut of a batch-level and task-level traffic graph, minimizing off-chip traffic. Tier-2, inside each cluster, orders sub-tasks longest-first and interleaves short ones into the gaps — the fluid pipeline from tab 2's figure (b).

5 · Runtime — instruction queues and stall-less pipelining

Meld compiles operators into handlers plus one wrapper kernel that fully saturates the GPU (one wrapper block per SM). Each wrapper drains a per-SM instruction queue written by the CPU-side scheduler — this is how Meld bypasses the GPU's opaque hardware scheduler for precise, topology-aware placement. Instruction prefetching fuses the intra-SM pipeline across consecutive handlers so loading for the next sub-task overlaps the current one's compute, avoiding stalls. Scheduling itself runs asynchronously ahead of execution, with a plan cache reusing splits across transformer layers/decoding steps.

Follow the numbers

Worked examples

Three traces through the paper's own measurements.

① How idle is FlashMLA's combine phase, really?

Paper facts: combine takes 37% of total kernel time, at 10.3% SM occupancy.

  1. Think of "useful SM-work done" as time-share × occupancy: 0.37 × 0.103 ≈ 0.038.
  2. So only ~3.8% of the theoretical SM-time available during that 37%-of-total-time window is doing useful work.
  3. The other ~96% of that window is SMs sitting idle, waiting for the phase's few busy blocks to finish — exactly the tail Meld's fused pipeline eliminates by letting other sub-tasks fill those SMs.
🍯
Insight: a phase can dominate wall-clock time while barely using the hardware — time-share and occupancy are two different axes, and BSP boundaries let a low-occupancy phase stall the whole GPU regardless.

② Why HBM round-trips cost more than on-chip handoff

Paper facts: FlashMLA's intermediate state is 32 KB per sub-task (TP=4); on-chip link ≈81 GB/s, HBM-proxied ≈20 GB/s, with 1/7 the latency on-chip.

  1. Via HBM (store + reload): 32 KB / 20 GB/s ≈ 1.6 µs one-way; a round trip (write then read back) roughly doubles that to ≈3.2 µs, plus the 7× larger latency overhead per hop.
  2. Via on-chip link (direct): 32 KB / 81 GB/s ≈ 0.4 µs, one hop, no second trip.
  3. That's roughly an 8× reduction in raw transfer time for this one intermediate — before even counting the latency and kernel-launch savings from not needing a second kernel at all.
💡
Multiply this by every sub-task, every layer, every decoding step, and the HBM round-trip tax on multi-phase kernels adds up fast — which is exactly why MoE's intermediate-state traffic alone is 20% of its total memory traffic in the baseline.

③ A toy version of the topology reverse-engineering (Appendix A)

Simplify to S_max = 2. Probing finds N₁ = 10 max concurrent clusters of size 1, N₂ = 6 of size 2. Recover hardware group sizes x₂ (pairs) and x₄ (quads).

  1. Constraint for s=1: ⌊2/1⌋x₂ + ⌊4/1⌋x₄ = N₁ → 2x₂ + 4x₄ = 10.
  2. Constraint for s=2: ⌊2/2⌋x₂ + ⌊4/2⌋x₄ = N₂ → x₂ + 2x₄ = 6.
  3. Both equations are the same line scaled by 2 — so the MILP's real job (in the actual paper) is picking the minimum total groups (x₂+x₄) consistent with all S_max=16 constraints at once, which pins down a unique answer for real GPUs (e.g. H100 → 2×18, 5×16, 1×8, 4×2).
📝
This is a simplified illustration, not the paper's actual H100 numbers (Eq. 1–7) — it's meant to show why more than 2 sample sizes are needed to pin down a unique topology.
Test yourself

Practice problems

Try before opening the answer. Each ends with the misconception it checks.

Problem 1 · easy
Why can't a kernel boundary simply be made "faster" (e.g. cheaper launch) to fix the issues in §2.2?
Show answer
Launch/termination cost is only one of three issues (I-1/I-2/I-3). Even with instant launches, the boundary still forces (1) static, pre-defined tiling that can't rebalance to the actual input shape, and (2) a full round trip of intermediate state through HBM. Cheaper launches don't touch either.Misconception: that kernel boundaries are only expensive because of launch overhead — the deeper cost is the rigidity and memory traffic they force.
Problem 2 · medium
H100 has 132 SMs. If you fix CUDA's cluster size to 12 for every kernel, roughly how many SMs on H100 (whose GPCs are sized 2×18, 5×16, 1×8, 4×2) can actually host a full cluster of that size?
Show answer
Only GPCs with ≥12 SMs can fit even one 12-SM cluster: the 18-SM GPCs fit one each (12 of 18 used, 6 idle), the 16-SM GPCs fit one each (12 of 16 used, 4 idle); the 8-SM and 2-SM GPCs can't fit a 12-SM cluster at all and sit entirely idle. That's a large fraction of the chip left unusable by a single uniform cluster size — the exact fragmentation problem §2.4 describes.Misconception: that CUDA's cluster-size knob maps cleanly onto hardware. The physical GPC sizes are fixed and heterogeneous; a uniform software cluster size can't fit them all.
Problem 3 · medium
"Just-in-time reduction is wait-free — it never uses synchronization." True or false, and why?
Show answer
False. It's wait-free in the sense that the consumer doesn't sit idle waiting — but it still relies on hardware mbarriers so the consumer only reads the shared-memory slot once the barrier confirms all bytes have arrived. "Wait-free" describes the scheduling outcome (data is ready when needed), not the absence of synchronization.Misconception: conflating "no stall" with "no synchronization." The synchronization is still there — it's just overlapped with useful work instead of blocking it.
Problem 4 · hard
Fine-grained partitioning (more, smaller sub-tasks) should always improve load balance. Why does the paper call this a genuine cost tradeoff (Challenge-3, §2.3) rather than a free win?
Show answer
Smaller sub-tasks mean more intermediate results are produced and exchanged, increasing communication/synchronization overhead relative to the useful compute in each sub-task. If partitioning is too fine, this overhead can outweigh the load-balance gains, degrading rather than improving performance — hence Meld's scheduler works within a per-SM workload budget rather than partitioning maximally.Misconception: that finer granularity is strictly better for balance. Past a point, the communication cost of granularity itself becomes the bottleneck.
Problem 5 · medium
MegaKernel systems (e.g. MPK) also fuse phases into one kernel. Why doesn't that alone solve the dynamic-workload problem the way Meld does (§6.3)?
Show answer
Fusing into one kernel removes launch overhead, but MPK still uses a static partition method (a pre-defined max chunk length) and starts reduction for a long sequence only after all its partial tasks complete — so long sequences still create a tail, and SMs still wait. The fix Meld provides isn't fusion per se, it's the fine-grained, dynamically-scheduled cooperation within the fused kernel.Misconception: that "fused into one kernel" implies dynamic and balanced. Fusion removes kernel-boundary overhead but doesn't automatically remove static partitioning or tail effects.
Problem 6 · easy
For a workload with uniform, static shapes (e.g. a dense GEMM in pretraining), should you reach for Meld's runtime?
Show answer
Not necessarily. The paper explicitly scopes Meld to dynamic workloads needing SM cooperation and precise topology mapping; for homogeneous, static workloads like GEMM, relying on the GPU's native hardware scheduler (with CLC) is typically simpler and just as efficient (§6.6).Misconception: that a more sophisticated runtime is always better. Meld's benefits come from adapting to dynamism — there's nothing to adapt to in a static, uniform workload.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly is "cross-SM kernel fusion"?▾
Fusing operations that traditionally required separate kernels — because they span different SMs and phases — into one execution, using direct SM-to-SM cooperation to enforce the dependency instead of a kernel boundary.
Q2How is this different from ordinary kernel fusion?▾
Ordinary fusion (in Triton, TileLang, etc.) merges operators within one thread block's computation — intra-SM scope. Cross-SM fusion extends fusion's scope to the entire GPU, spanning many SMs and phases via the on-chip interconnect.
Q3What actually makes just-in-time reduction possible?▾
Two hardware pieces: async TMA transfers directly between SMs' shared memories, and hardware mbarriers that track when a transfer completes — so the consumer can proceed the instant its data is ready, without polling or blocking.
Q4Why not just use CUDA's native thread block cluster feature?▾
Because it forces one uniform cluster size for the whole kernel, and the real hardware groups (GPCs) are heterogeneous (2–20 SMs). A size that fits some GPCs perfectly leaves others fragmented and idle — up to 62 of 132 SMs on H100 with cluster size 10.
Q5What do developers actually have to write?▾
Computation logic as composed operators (Iter/Map/Reduce/Reshard/Gather/Finalize), similar in spirit to Spark's RDD operators. Table 5 reports this adds only 19–37 lines of code versus an equivalent TileLang implementation.
Q6How does Meld avoid the GPU's own (opaque) scheduler?▾
It launches a wrapper kernel that fully saturates the GPU (one persistent block per SM), then has each block read a CPU-populated, per-SM instruction queue and execute exactly the handlers/communication it's told to — bypassing hardware block scheduling entirely.
Q7Does Meld replace Triton or TileLang?▾
No — it's built on top of TileLang as its intra-SM compiler backend, adding the cross-SM cooperation, scheduling, and runtime layers TileLang doesn't have.
Q8What's the overhead of all this dynamism?▾
Scheduling takes under 2 ms (overlappable via async scheduling + plan caching); compilation takes 1.3–2.2× longer than TileLang's (one-time cost, since it generates handlers for multiple sub-task-shape ranges).
Q9Does Meld work on GPUs without on-chip SM links?▾
Yes, with reduced benefit — it falls back to global-memory-based communication and flag-based synchronization, still gaining from decoupled, dynamic scheduling alone (the "+decouple" ablation bar, Fig.12), just without the "+cooperate" gains from the interconnect.

Core terms
Cross-SM kernel fusionFusing phases that traditionally required separate kernels into one, using direct SM-to-SM cooperation instead of a kernel boundary to enforce ordering.
Just-in-time (JIT) reductionMerging intermediate results directly in local SRAM the moment they arrive via async transfer — wait-free because the barrier confirms readiness.
Decoupled executionSeparating declared computation logic (operators) from the hardware mapping/cooperation plan, which is decided at runtime per input shape.
Operator-based abstractionMeld's programming model: compose Iter, Map, Reduce, Reshard, Gather, Finalize to express DNN computation + cooperation semantics.
Hierarchical schedulingTier-1: assign task groups to hardware clusters minimizing off-chip traffic. Tier-2: intra-cluster stage fusion + JIT reduction ordering.
Instruction queue / wrapper kernelA per-SM list of (handler, args, comm) instructions written by the CPU scheduler; the wrapper kernel's block on each SM drains and executes it, bypassing the GPU's hardware scheduler.
Copy absorptionUsing the on-chip interconnect to broadcast data loaded once (e.g. a shared KV-cache prefix) to multiple SMs, avoiding redundant HBM fetches.

mbarrierHardware-managed barrier primitive used for fine-grained cross-SM synchronization, paired with async TMA transfers.
