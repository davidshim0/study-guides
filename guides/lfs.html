Stop seeking around the disk — just write it all as one log

Small-file writes were killing 1990s Unix — five scattered seeks just to create one file. This is the plain-English story of LFS: buffer everything, flush it as one giant sequential write, and let a smart cleaner deal with the mess later.

Before you begin

Why writing a file was so slow, and the trick that fixes it

Read the TL;DR, then work through the primers in order the first time — or skip to whatever's unfamiliar.

⚡ TL;DR

  • LFS buffers all file-system changes in memory, then flushes them to disk as one large sequential write ("the log") — the log is the file system, not just an auxiliary speedup structure — and a segment cleaner with a cost-benefit policy reclaims fragmented free space.
  • Sprite LFS uses 65–75% of raw disk bandwidth for writing (vs Unix FFS's 5–10%) and is roughly an order of magnitude faster for small-file creates/deletes, while matching or beating FFS on reads and large writes.
  • It matters because it proves the bottleneck was layout policy, not disk hardware — the same buffer-batch-reclaim playbook now underlies SSD flash translation layers, LSM-trees, and copy-on-write filesystems.

1Why seeks, not bandwidth, were the bottleneck▾

A disk write has two costs: a mechanical seek + rotational wait (milliseconds, dominated by physics) and a transfer (fast, scales with bandwidth). CPUs were getting exponentially faster through the 1980s–90s; disk access time barely improved because it's mechanical. Any workload of small, scattered writes stays slow no matter how fast your CPU gets.

Now you're ready: LFS's whole strategy is to convert many small scattered writes into one big sequential write, so the mechanical seek cost is paid once instead of five times.
2Unix FFS and the inode, briefly▾

In the Berkeley Fast File System, each file has an inode (attributes + block pointers) at a fixed disk address computed from the file's i-number. Directories are separate files mapping names to i-numbers. Creating one small file touches five separate, non-sequential places: the file's data, the file's inode (written twice for crash safety), the directory's data block, and the directory's own inode.

Now you're ready: LFS keeps the same logical structures (inodes, indirect blocks) but never gives them a fixed address — everything, including inodes, gets written wherever the log currently is.
3Write buffering and why caches shift traffic toward writes▾

Growing main memory lets file caches absorb more and more reads — once a block is cached, re-reading it costs nothing. But writes must eventually reach disk for durability. As caches grow, disk traffic becomes dominated by writes, and the cache doubles as a write buffer that can accumulate many small changes before flushing.

Now you're ready: LFS is built on exactly this assumption — batch dirty blocks in the cache, then flush the batch as one sequential transfer.
4"Log-structured" means the log is the permanent home▾

Journaling and database write-ahead logs use a log as a temporary staging area; data still lives permanently in a separate random-access structure. A log-structured file system is different: the log is the only structure on disk. There's no separate "real" location the data later moves to — the log itself contains everything, with enough indexing to read it back efficiently.

Now you're ready: this is why LFS needs a cleaner at all — a staging log gets flushed and reused, but a permanent log has to reclaim space from data that's still logically "the file system."
5Segments: the unit of free space▾

As the log fills the disk, deleted/overwritten data leaves scattered holes. LFS divides the disk into large fixed-size segments (512 KB or 1 MB in Sprite LFS). A segment is always written sequentially start-to-end, and cannot be reused until every live block in it is copied elsewhere — that copying is segment cleaning.

Now you're ready: the entire rest of the paper is about picking which segments to clean and how, since that decision determines whether LFS is fast or slow.
6Live vs. dead blocks, and how the cleaner tells them apart▾

A block is dead once it's been overwritten or its file deleted; otherwise it's live. Each segment carries a segment summary block naming which file and offset every block belongs to, so the cleaner can check the file's current inode to see if a block pointer still points there — or use a cheaper shortcut (a version number) to skip that check entirely.

Now you're ready: this is exactly what lets LFS avoid ever needing a free-block bitmap — liveness is derived, not tracked separately.
7Write cost — the paper's central scorecard▾

Write cost = disk time spent per byte of new data written, including all cleaning overhead. A write cost of 1.0 is perfect (100% of bandwidth goes to new data); a write cost of 10 means only 10% of bandwidth is usable for new data. Unix FFS on small files runs at write cost 10–20; the paper's whole goal is to keep LFS's write cost low despite the overhead of cleaning.

Now you're ready: nearly every graph in the paper plots write cost against segment utilization — how "full" of live data the cleaned segments were.
8Checkpoints and roll-forward (crash recovery, briefly)▾

Traditional Unix file systems recover from crashes by scanning the entire disk (fsck) since they don't know where the last writes landed. LFS always knows — they're at the end of the log. A periodic checkpoint marks a fully consistent state; after a crash, the system reads the checkpoint, then rolls forward through the log segments written since, replaying anything recoverable — the same pattern as a database's write-ahead redo log.

Now you're ready: the log that makes writes fast is the exact same structure that makes recovery fast — one design decision buys both.

The whole story in one place

LFS in a nutshell

The problem, the fix, the catch it introduces, and how the pieces connect.

Unix FFS lays files out to optimize for reads, at the cost of scattering the writes needed to create or update a small file across five separate, seek-separated disk locations, most of them synchronous. As CPUs got faster and disk seek time didn't, this made small-file-heavy workloads (office/engineering environments, the paper's stated target) increasingly disk-bound no matter how fast the processor was.

Log-structured file systems (LFS) fix this by buffering changes in the file cache and flushing them to disk as one large, purely sequential write — the log — which also serves as the file's only permanent storage (not a staging area, unlike database write-ahead logs). This converts nearly all write traffic from small random I/Os into large sequential transfers, using close to 100% of raw disk bandwidth.

The catch: a permanent, ever-growing log needs somewhere to reclaim space as files are deleted or overwritten. LFS divides the disk into segments and runs a segment cleaner that copies live data out of fragmented segments to free them. Which segments to clean, and in what order, turns out to be the single decision that determines whether LFS is fast or merely mediocre — a naive greedy policy (always clean the least-utilized segment) actually gets worse as locality increases, a genuinely surprising result. The fix is a cost-benefit policy that treats old, slowly-changing ("cold") data differently from young, rapidly-changing ("hot") data — cold segments are worth cleaning even at high utilization, because their freed space stays free a long time.

The payoff: Sprite LFS uses 65–75% of raw disk bandwidth for new writes (Unix FFS: 5–10%), is roughly 10× faster creating/deleting 1 KB files, and matches or beats FFS on reads and large-file writes — with one honest exception (sequential re-read of a randomly-written file) and a crash-recovery scheme that's faster, not slower, than fsck.

🍯 Key takeaways

  • Unix FFS optimizes layout for reads and pays for it with 5 scattered, often synchronous writes per small-file create.
  • LFS buffers changes and flushes them as one sequential log write — the log is the permanent home of the data, not a shortcut to it.
  • Write cost = 2/(1−u): cleaning cost explodes as the utilization of cleaned segments rises toward 1.
  • Naive greedy cleaning (pick lowest-u segment) gets worse with locality — cold segments linger just above the cleaning threshold, tying up free space.
  • Cost-benefit cleaning weighs free space reclaimed against how long it'll likely stay free (using age as a stability proxy) — this produces the bimodal "mostly full, a few empty" segment distribution that makes cleaning cheap.
  • No free-block bitmap needed anywhere — liveness is derived from inodes/uids, which also simplifies crash recovery.
  • Checkpoint + roll-forward gives fast, log-order crash recovery instead of a full-disk fsck scan.
Six everyday pictures

How to think about LFS

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Log writing

Doing all your errands in one drive

Three errands across town, done as three separate round trips, waste most of your time driving back and forth. Batch them into one loop and you drive once. LFS does this with disk writes: instead of five scattered, seek-separated writes to create a file, it collects the changes and delivers them in a single sequential pass.

Where it breaks: errands don't need to be found again later; file blocks do. The "one trip" only works because LFS also builds an index (inode map) so it can locate everything afterward — batching alone isn't enough.
Segments & cleaning

Renovating one full floor at a time

You can't reuse a floor of a fully-occupied apartment building until every remaining tenant has moved out or you've relocated them. LFS's segments work the same way: a whole segment must have all its live blocks copied elsewhere before the segment can be reused for new writes.

Where it breaks: a landlord picks which floor to renovate by convenience; the cleaner has to pick by a cold calculation of which floor gives back the most usable space for the longest time (below).
Cost-benefit · Hot vs cold

Recycling bins that fill at different rates

Empty a bin that refills in an hour and you'll be back soon; empty one that refills once a year and that space stays useful for a year. LFS's cost-benefit policy treats segments the same way — a "cold," slowly-changing segment is worth cleaning even when it's mostly full, because the space it yields stays free a long time; a "hot" segment isn't worth cleaning until it's nearly empty, since it'll refill (with dead blocks, i.e. free up more space) soon anyway.

Where it breaks: LFS estimates "how long it'll stay free" using the age of the data (older = more stable), a proxy that fails if cold data is suddenly rewritten in one burst.
Greedy vs cost-benefit

Tidying by "messiest right now" vs "going stale"

Always tidying whatever looks messiest right now (greedy) sounds sensible — but a drawer you use daily gets messy again the moment you tidy it, while a closet you rarely touch stays tidy for months once cleared. LFS's greedy policy (always clean the least-utilized segment) fell into exactly this trap: cold segments lingered forever just above the cleaning threshold, tying up free space, and adding locality made it worse, not better.

Where it breaks: real tidying has no formula; LFS's fix works specifically because "age" is a decent proxy for "won't get messy again soon" in real file-access patterns.
Crash recovery

Autosave plus a flight recorder

A video game's autosave gives you a known-good state; a flight recorder lets investigators replay exactly what happened right before an incident. LFS's checkpoint is the autosave — a fully consistent snapshot — and roll-forward is the flight recorder, replaying the log segments written since, to recover data from the seconds right before a crash.

Where it breaks: a flight recorder is read-only after the fact; roll-forward actively repairs directory/inode inconsistencies as it replays, using a dedicated directory operation log to resolve races.
The uid trick

A claim ticket that expires the moment a new one is issued

A coat-check ticket only works if it matches the currently-valid stub — an old ticket for a coat that's already been reissued is worthless without anyone checking the coat itself. Each logged block carries a uid (inode number + version); if it doesn't match what the current inode map says, the cleaner discards the block immediately — no need to open the file's inode and check block pointers.

Where it breaks: this shortcut only tells you a block is definitely dead; a match still requires the full inode check to confirm the block is genuinely live at that offset.
The full explanation

How it actually works

Section by section, with the paper's key comparisons rebuilt as diagrams.

1 · The problem — five seeks to create one file

In Unix FFS, creating a one-block file named dir/file requires writing: the file's data block, the file's inode (written twice, for crash-safety reasons), the directory's data block (new entry), and the directory's own inode (updated modify time) — five non-sequential writes, several of them synchronous. Fewer than 5% of the disk's bandwidth ends up carrying new data; the rest is seeking.

2 · Retrieving data from the log — an inode map, not fixed addresses

Sprite LFS keeps the same inode/indirect-block structure as FFS, but inodes aren't at fixed addresses — they move every time they're rewritten to the log. An inode map tracks each inode's current location; it's small enough to stay mostly cached in memory, so looking up a file rarely costs an extra disk access. A fixed checkpoint region records where the inode map's own blocks are.

3 · Free space: threading, copying, or both

Once the log wraps around the disk, free space fragments. Threading the log through the holes avoids copying but fragments free space into unusably small pieces. Copying live data out to compact it gives large free extents but costs repeated copying, especially for long-lived files. Sprite LFS does both: it copies live data within a segment to free the whole segment, but threads the log across segments — a segment full of long-lived data can simply be skipped, never re-copied.

4 · Segment cleaning mechanics

Cleaning is a 3-step loop: read several segments into memory in full; use each segment's summary block (file number + offset per block) plus the current inode map to identify which blocks are still live; write the live blocks back, compacted, into fresh segments. The now-empty segments are marked clean and reused. No bitmap or free list is needed anywhere — liveness is always derived on demand.

5 · The write-cost model, and why greedy backfires

Reading N segments (utilization u) and writing back N·u live segments frees N·(1−u) segments for new data, using 2N total bytes of disk traffic (N read + N written back, live and new combined) — giving:

write cost = 2 / (1 − u)      # u = fraction of cleaned segments' bytes that are still live

The naive greedy policy — always clean the least-utilized segment — sounds reasonable, but the paper's simulations found it gets worse, not better, as file-access locality increases. Under greedy, every segment (hot or cold) is only cleaned once it drops to the same low threshold utilization — but cold segments' utilization drops so slowly that they linger just above that threshold for a long time, tying up free blocks that could otherwise be reclaimed.

6 · The cost-benefit formula, and checkpoint/roll-forward recovery

The cost-benefit policy scores each candidate segment by estimated benefit (free space reclaimed × how long it'll likely stay free, using the segment's most-recently-modified block as an age proxy) against cost (1 read + u writes to preserve live data):

cost / benefit = (1 + u) / ((1 − u) × age)   # clean segments with the LOWEST cost/benefit first

Live blocks are then sorted by age before being rewritten, segregating hot data from cold — reinforcing the bimodal distribution above. Separately, crash recovery uses checkpoints (periodic fully-consistent snapshots) plus roll-forward (replaying segment summary blocks written since the last checkpoint). A dedicated directory operation log records create/link/rename/unlink events explicitly, because a crash can catch an inode's reference count and its directory entry on opposite sides of a write — ordinary block logging alone can't resolve that race.

💡
Why age, not access frequency? Age (time since last write) is cheap to track per segment and correlates with "won't be touched again soon" — a genuinely different signal from LRU-style recency, which tracks reads, not writes.
Follow the numbers, step by step

Worked examples

Four calculations built from the paper's figures, tables, and formulas — one (marked below) uses illustrative numbers to demonstrate a formula rather than measured values.

① Deriving the FFS reference points on the write-cost curve

The paper states Unix FFS today runs at write cost 10–20, and an "improved" FFS could reach write cost 4. What utilizations does that imply, using write cost = 2/(1−u)?

  1. Solve for u at cost 10: 10 = 2/(1−u) → 1−u = 0.2 → u = 0.8.
  2. Solve for u at cost 20: 1−u = 0.1 → u = 0.9. So "FFS today" corresponds to effectively cleaning at u = 0.8–0.9.
  3. Solve for u at cost 4 ("FFS improved"): 1−u = 0.5 → u = 0.5.
  4. Interpretation: LFS must keep the segments it actually cleans below u ≈ 0.8 to beat today's FFS, and below u ≈ 0.5 to beat an improved FFS — exactly the thresholds the paper states.
🍯
Insight: the entire cleaning-policy design problem reduces to one goal: keep the utilization of segments you clean low, however you manage it.

② Cost-benefit ratio: why a fuller cold segment beats an emptier hot one

Compare a cold segment (u=0.75, age=1000 time-units) against a hot segment (u=0.15, age=10 time-units) using cost/benefit = (1+u)/((1−u)×age). Lower is better (cleaned first). (These specific age/u values are illustrative, chosen to demonstrate the formula's behavior — not measured values from the paper.)

  1. Cold segment: (1+0.75) / ((1−0.75)×1000) = 1.75 / 250 = 0.007.
  2. Hot segment: (1+0.15) / ((1−0.15)×10) = 1.15 / 8.5 = 0.135.
  3. Compare: 0.007 ≪ 0.135 — the cold segment, despite having 5× the live data to copy, is roughly 19× more favorable to clean.
  4. Why: its huge age multiplier means the space it frees will likely stay free 100× longer than the hot segment's — worth paying more copy cost up front.
💡
This is exactly why cost-benefit lets cold segments be cleaned at ~75% utilization while hot segments wait until ~15% (paper, §3.5) — the opposite of what a naive "clean the emptiest one" rule would ever choose.

③ How much CPU headroom does Sprite LFS have left?

On the 10,000×1KB-file benchmark, SunOS FFS keeps the disk 85% busy while using only 1.2% of its bandwidth for new data; Sprite LFS keeps the disk only 17% busy while saturating the CPU. How much faster could each get from a faster CPU alone?

  1. SunOS FFS: disk is already 85% busy — at best a faster CPU buys back the remaining 15% of time, i.e. roughly 1.15–1.2× speedup before the disk becomes the hard limit.
  2. Sprite LFS: disk is only 17% busy; the CPU is the current bottleneck. Headroom before the disk saturates ≈ 1/0.17 ≈ 5.9×.
  3. Paper's claim: "performance of Sprite LFS will improve by another factor of 4–6 as CPUs get faster" — matches this estimate closely.
  4. Takeaway: the same disk hardware has wildly different remaining headroom depending purely on how writes are laid out.

④ Sanity-checking Table 2's production write costs

The /swap2 file system had 66% of its cleaned segments come back totally empty (u=0) and the other 34% average u=0.535 (Table 2), yet the measured write cost was 1.6. Does that reconcile with write cost = 2/(1−u)?

  1. Empty segments need no read at all — with no live data to preserve, cleaning one costs only the write of new data into it: 1 unit of traffic, yielding 1 full segment of new/free space. 66 segments → traffic 66, free space 66.
  2. Non-empty segments always cost 1 read + 1 write — you read the whole segment (1), then write back a full segment's worth: the preserved live data (u) plus new data filling the freed space (1−u), which sums to 1. Total traffic per segment = 2, regardless of u; free space produced = (1−u) = 0.465. 34 segments → traffic 34×2=68, free space 34×0.465≈15.8.
  3. Write cost = total traffic ÷ total new/free data — not an average of per-segment costs: (66+68) / (66+15.8) = 134 / 81.8 ≈ 1.64, matching the measured 1.6 almost exactly.
  4. Why the naive average is wrong: averaging 0.66×1.0 + 0.34×4.3 ≈ 2.1 weights each segment equally, but empty segments produce far more free space per segment than partially-full ones — the aggregate ratio has to weight each segment's contribution by how much free space it actually yields, not just count it once.
🍯
Takeaway: Table 2's numbers aren't a mysterious extra gap beyond the formula — they're exactly what 2/(1−u) predicts once you weight segments correctly by the free space each one contributes.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Using write cost = 2/(1−u), what write cost corresponds to u = 0.9, and how does that compare to "FFS today" (write cost 10–20)?
Show answer
2/(1−0.9) = 2/0.1 = 20. That's at the high end of FFS's reported range — meaning if LFS cleaned segments at 90% utilization, it would be no better than the worst FFS behavior it's trying to beat.Misconception: that any use of a log automatically makes writes fast. Without a good cleaning policy keeping u low, LFS's write cost can be just as bad as FFS's.
Problem 2 · medium
Why did adding more locality to the access pattern make the greedy cleaning policy's write cost worse, not better?
Show answer
Under greedy, every segment — hot or cold — only gets cleaned once its utilization drops to the same fixed threshold. Cold segments' utilization drops very slowly (their data barely changes), so with more locality they spend a very long time hovering just above that threshold, tying up free space that should have been reclaimed sooner. More locality means more segments behave this way, worsening the problem.Misconception: that grouping related/similar data together (locality) is always good for a storage system. Here it actively defeats a cleaning policy that isn't designed to account for it.
Problem 3 · medium
A segment has u=0.9 and age=5. Another has u=0.3 and age=500. Using cost/benefit = (1+u)/((1−u)×age), which gets cleaned first?
Show answer
First segment: (1.9)/((0.1)×5) = 1.9/0.5 = 3.8. Second: (1.3)/((0.7)×500) = 1.3/350 ≈ 0.0037. The second (mostly-live but very old) segment has a far lower cost/benefit and is cleaned first, despite having 3× the live data to copy.Misconception: that "how full" a segment is (utilization alone) determines cleaning priority. Age/stability can dominate the decision entirely.
Problem 4 · hard
Explain how Sprite LFS can discard a dead block during cleaning without reading the file's current inode at all, using the uid mechanism.
Show answer
Each segment summary block records, per block, the uid (inode number + version number) that was current when the block was written. During cleaning, if the inode map's current version number for that inode number doesn't match the uid stored in the segment, the file has since been deleted/truncated — the block is provably dead, full stop, with no need to open the inode and check block pointers. Only when the uid does match must the cleaner check the inode to see if that specific block offset is still referenced.Misconception: that liveness always requires consulting the file's inode. The uid check is a cheap short-circuit that skips the expensive check in the common "clearly dead" case.
Problem 5 · medium
Sprite LFS has no free-block bitmap or free list at all. What does Unix FFS reserve 10% of disk space for, that LFS doesn't need?
Show answer
Unix FFS keeps 10% of the disk permanently unallocated so its free-space allocation algorithm (finding a good, low-fragmentation block to place new data) stays efficient as the disk fills. LFS never searches for free blocks this way — it always writes to the current end of the log, and liveness/free-space bookkeeping is derived from segment summaries and the segment usage table rather than maintained as a separate structure that needs slack space to stay efficient.Misconception: that reserving free space is an inherent cost of any file system. It's specifically a cost of FFS's block-allocation strategy, not of storage management in general.
Problem 6 · hard
Why does Sprite LFS need a dedicated directory operation log, rather than just logging the changed directory block and inode normally?
Show answer
A directory entry (name → i-number) and the target inode's reference count are two separate on-disk structures that must stay consistent, but a crash can occur after one is written to the log and before the other is. Ordinary logging of "whatever blocks changed" doesn't record the intent of the operation (create/link/rename/unlink) needed to detect and repair that specific inconsistency. The directory operation log records the intent explicitly and is guaranteed to be written before the corresponding directory/inode blocks, so roll-forward can always tell what should have happened and finish the job.Misconception: that logging the raw changed blocks is always enough for crash consistency. Some invariants span two structures and need the operation's intent logged separately.
Problem 7 · easy
Why is read performance in Sprite LFS about the same as Unix FFS, given that writes are handled so differently?
Show answer
Both systems use the same logical lookup structure — find the inode, then follow direct/indirect block pointers to the data. The only difference is that LFS's inode isn't at a fixed address and must be found via the inode map, which is small enough to usually stay cached in memory. Once the inode is found, the number of disk I/Os to read the file is identical in both systems.Misconception: that a completely different write strategy must come with a completely different (and presumably worse) read strategy. LFS deliberately preserves FFS's read-side structures.
Problem 8 · medium
Why does Sprite LFS perform worse than Unix FFS specifically when a file is read back sequentially after being written randomly?
Show answer
LFS achieves temporal locality — blocks written around the same time end up near each other on disk, regardless of which file they belong to. FFS achieves logical locality — blocks of the same file end up near each other, regardless of when they were written. Random writes to one file, in LFS, get scattered across the log in write order, not file-offset order; reading the file back sequentially (by offset) then requires seeking around the log. FFS, by contrast, always keeps a file's blocks together on disk, so sequential reads stay cheap even after random writes.Misconception: that sequential-log writing always implies sequential-file-order layout. Temporal and logical locality are different things, and they only coincide when a file is written in the same order it's later read.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly makes a file system "log-structured"?▾
The log is the only permanent structure on disk — not a staging area that data later moves out of. Files are written once to the log and stay there; the only way data "moves" is when the cleaner copies still-live blocks to a fresh segment, which is still just another log write.
Q2Isn't this the same as journaling?▾
No. A journaling file system logs metadata (or data) changes temporarily for crash recovery or write-ordering, then commits the permanent copy elsewhere in a traditional layout. LFS has no "elsewhere" — the log entry itself is the permanent data. Database write-ahead logs work like journaling, not like LFS.
Q3Why divide the disk into segments instead of one giant log?▾
Segments are large enough that the transfer time dwarfs the one seek needed to reach them, so whole-segment reads/writes run at near-full disk bandwidth regardless of where on disk the segment sits. This lets the log be threaded — segments can be visited in any order — without losing sequential-write efficiency within each segment.
Q4What is "write cost" measuring, exactly?▾
The average disk-busy-time per byte of genuinely new data written, including all cleaning overhead. 1.0 is perfect (zero cleaning overhead, full bandwidth for new data); higher numbers mean more of the disk's time is spent moving old live data around rather than writing anything new.
Q5Why did the "obviously reasonable" greedy cleaning policy do so badly?▾
Greedy cleans whichever segment currently has the least live data, with no regard for why it's low or how long it'll stay that way. Cold, rarely-changing segments drop toward the cleaning threshold extremely slowly and then linger there, hoarding free space that a smarter policy could reclaim earlier and put to better use.
Q6How does the cost-benefit policy actually decide?▾
It ranks segments by cost/benefit = (1+u)/((1−u)×age), and cleans the lowest-ranked (best) ones first. This lets a mostly-full but very old (cold) segment beat out a mostly-empty but very young (hot) segment — because the cold segment's freed space will likely stay free far longer.
Q7Does LFS need a bitmap or free list like FFS?▾
No — this is one of its simplifications. Liveness is always derived from segment summary blocks plus the current inode map (or the uid shortcut), and the segment usage table just tracks aggregate live-byte counts and ages per segment for cleaning decisions, not individual free blocks.
Q8How is crash recovery faster than fsck?▾
fsck must scan the entire disk because traditional file systems don't record where the last operations landed. LFS always knows: the last writes are at the end of the log. Recovery reads the last checkpoint, then rolls forward through only the segments written since — a bounded amount of work tied to the checkpoint interval, not the disk size.
Q9Is LFS only good for small files?▾
No — it was designed around small-file workloads (where FFS struggles most) but the paper shows it matches or beats FFS on large sequential writes and reads too, since large files are naturally efficient to log sequentially. The one weak spot is reading a file sequentially right after writing it randomly, where temporal and logical locality diverge.
Q10Was Sprite LFS just a simulation, or did it actually run?▾
Both. The cleaning-policy design was worked out via simulation first (Section 3), then implemented as a real, production file system inside the Sprite network operating system, used by about thirty users across five disk partitions for months, with measurements confirming (and in some ways beating) the simulated predictions.

Four short connections to ideas you'll recognize from tiering and persistent-memory work.

🔧 Segment cleaning ≈ SSD garbage collection

LFS's write-cost curve (2/(1−u)) is a striking analogue of an SSD flash translation layer's write amplification factor — both punish reclaiming space from mostly-live regions, and both fix it the same way: never overwrite in place, batch writes sequentially, and garbage-collect opportunistically. If you've ever tuned an SSD's over-provisioning percentage, you were tuning the same fundamental tradeoff LFS identified for disks — not because one mechanism descends from the other, but because the same math shows up wherever in-place updates get replaced by an append-only log.

🌡️ Age-as-stability ≈ hot/cold page classification

The cost-benefit policy's core move — treat data differently based on how stable it's likely to be, using a cheap recency/age proxy instead of predicting the future — is exactly what DRAM/NVM tiering systems do when classifying pages as hot or cold for migration. LFS's "greedy gets worse with locality" surprise is a useful cautionary tale: a naive recency-only heuristic can misfire in the same way a naive LRU-based tiering policy can be fooled by scans or bursty cold-data rewrites.

💾 Checkpoint + roll-forward ≈ persistent-memory logging

The checkpoint/roll-forward pattern — a periodic consistent snapshot plus replay of everything since — has a clear echo in persistent-memory file systems like NOVA and PMFS, which use lightweight per-inode logging and periodic snapshots for the same reason LFS did: cheap, log-order recovery without scanning the whole device. Copy-on-write filesystems like ZFS and btrfs solve a related durability problem, but with a different mechanism — atomic transactional updates to an immutable tree, not checkpoint-plus-log-replay — so the resemblance there is looser, more a shared "never overwrite in place" philosophy than the same recovery algorithm.

📚 Sequential batching ≈ LSM-trees and page migration batching

Never-overwrite-in-place plus periodic compaction is also the definition of a log-structured merge tree (the design behind RocksDB/LevelDB). In tiering systems, the same principle shows up when batching cold-page migrations into large sequential transfers to amortize CXL/NVM fabric latency, rather than migrating pages one at a time.

🍯
LFS's real lesson isn't "logging is fast" — it's that reclamation policy, not raw media speed, determines whether a write-heavy storage layer performs well. That's precisely the design tension in OS-managed DRAM/NVM tiering: deciding which cold pages to migrate, and whether the migration cost is worth paying, is a cost-benefit problem with the same shape as choosing which segment to clean.

Sharp questions to raise

Each references a specific claim or number from the paper.

  1. Given that Sprite LFS's production write costs (1.2–1.6, Table 2) came out noticeably better than the paper's own simulated predictions (2.5–3), how much of the real-world win is the cost-benefit policy itself versus the paper's admission that its uniform-file simulator model is "much harsher than reality"? (worth asking which of the two the authors are actually claiming credit for)
  2. Greedy cleaning got measurably worse as locality increased (Figs. 4–6) — the opposite of the authors' own initial expectation — so what would a workload look like that defeats the cost-benefit policy's age-as-stability heuristic in the same surprising way? (think: cold data that's suddenly rewritten in one large burst)
  3. The production system uses a 30-second checkpoint interval that the authors themselves call "probably much too short," and Table 4 shows the inode map alone eats 7.8% of log bandwidth as a direct result — what would a principled way to pick that interval look like, instead of picking by feel? (there's a real tradeoff curve here between checkpoint overhead and recovery time bound)
  4. Sequential-read-after-random-write is the one workload where LFS loses to FFS (Fig. 9), because temporal locality diverges from logical locality — is this the same tension that shows up as read amplification in log-structured merge trees, and would idle-time re-sorting eliminate the gap or just relocate the cost to a different point in time? (connects directly to LSM-tree compaction tradeoffs)
  5. The paper's entire premise rests on "files are cached in memory, so disk traffic becomes write-dominated" — does that assumption still hold on modern NVMe SSDs and CXL-attached memory, where read latency is far closer to DRAM than 1991 disk read latency was, and if it doesn't, does the paper's central argument for the log even still apply? (a chance to connect 1991 disk economics to today's memory/storage economics)

Glossary, results, & further reading

Every term in one place, then a path to go deeper.

Core terms
LFS (Log-Structured File System)The paper's technique: write all changes sequentially to a log that is the only permanent structure on disk.
SegmentA large fixed-size disk extent (512 KB–1 MB); the unit the log is written in and the unit the cleaner reclaims.
Segment cleaningCopying live blocks out of fragmented segments so those segments can be reused for new writes.
Write costDisk-busy-time per byte of new data written, including cleaning overhead: 2/(1−u) in steady state.
Utilization (u)Fraction of a segment's bytes still live when the cleaner reads it — the key driver of write cost.
Cost-benefit policyCleaning rule: pick segments minimizing (1+u)/((1−u)×age), favoring old (cold) segments even at high utilization.
Segment usage tableOn-disk structure tracking live-byte counts and last-modified time per segment, feeding the cost-benefit calculation.
CheckpointA periodic, fully consistent on-disk snapshot: inode map + segment usage table locations, plus a log pointer.
Roll-forwardReplaying segment summary blocks written after the last checkpoint to recover recent data after a crash.
Supporting terms
Unix FFSBerkeley Fast File System — the fixed-address-inode baseline LFS is compared against throughout.
Inode / inode mapPer-file attribute+pointer structure; in LFS its address moves, so a separate map tracks its current location.
Segment summary blockPer-segment index naming the file/offset of every block written, used to identify live data during cleaning.
uidInode number + version number stamped per block, letting the cleaner spot dead blocks without an inode lookup.
Directory operation logDedicated log records for directory create/link/rename/unlink, resolving inode-vs-directory-entry race conditions.
Threading vs copyingTwo free-space strategies: skip over live data (threading, fragments free space) or relocate it (copying, costs bandwidth). LFS combines both.
Temporal vs logical localityGrouping by "written at the same time" (LFS's natural layout) vs "belongs to the same file" (FFS's natural layout).
SpriteThe UC Berkeley research network operating system Sprite LFS was built into and measured within, in production.
