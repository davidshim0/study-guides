Write everything once, in order, and make the cleaner pay later

Sprite LFS treats the whole disk as a log: every change, data and metadata alike, is buffered in memory and written in one sequential transfer. This guide opens every mechanism, the cleaning cost model, every figure and table, and every assumption the design leans on.

Before you begin

Write everything at the end of a log, and pay for it by cleaning

Rosenblum and Ousterhout's 1991 paper from Berkeley: Sprite LFS, a file system with no fixed home for anything except two checkpoint regions and a superblock. It follows the FFS paper you just read, and uses FFS as its main point of comparison.

⚡ TL;DR

  • The paper's premises: CPU speed is rising "at a nearly exponential rate" while disk access time, set by "mechanical motions that are hard to improve", barely moves. Memories are growing, so file caches absorb more of the reads and "disk traffic (and disk performance) will become more and more dominated by writes." Office and engineering workloads are dominated by small files (mean sizes "of only a few kilobytes").
  • The two problems it names in existing file systems (Section 2.3): (1) information is spread around the disk: Unix FFS lays each file out sequentially but "physically separates different files", and keeps the inode and the directory entry apart from the data, so creating one file takes "at least five separate disk I/Os, each preceded by a seek" and small-file writes use "less than 5% of the disk's potential bandwidth"; (2) metadata (inodes, directories) is written synchronously, so applications wait on the disk.
  • The idea: collect changes in the file cache and write all of them (data, inodes, indirect blocks, directories, and an inode map that says where each inode now is) to disk "sequentially in a single disk write operation". The log is the only structure on disk; after an inode is found, reads cost the same number of I/Os as in FFS.
  • The hard part is free space: the disk is divided into segments of 512 KB or 1 MB; a cleaner reads segments, uses a segment summary block and a per-file version number to tell live blocks from dead ones, and writes the live ones out compacted. The cost per byte of new data is 2/(1−u), where u is the live fraction of the segments cleaned.
  • Choosing what to clean: picking the emptiest segment (greedy) got worse as access locality increased. The cost-benefit policy picks the highest (1−u)·age/(1+u) and sorts live blocks by age; it produces a bimodal distribution (hot segments cleaned at about 15% live, cold ones at about 75%) and cuts write cost "by as much as 50%". Crash recovery uses checkpoints in two alternating fixed regions plus roll-forward through the log written since.
  • Results: on a Sun-4/260 with a Wren IV disk, Sprite LFS is "almost ten times as fast as SunOS" for creating and deleting 1 KB files and faster for all large-file writes; reads match except a sequential reread of a randomly written file (about 215 versus 520 KB/s, read off Figure 9). Over four months of production use, write costs were 1.2 to 1.6 and more than half of the cleaned segments were already empty: about 70% of the disk's bandwidth goes to new data, versus "5-10%" for Unix systems.

Quick glossary
LogAn append-only sequence of blocks on disk, written in order at its head. In LFS it is the file system's only data structure: every new or changed block is appended, never overwritten in place.
SegmentA large fixed-size extent of the disk (512 KB or 1 MB in Sprite LFS) that is always written sequentially from start to end and must be emptied of live data before it is written again.
Partial-segment writeA log write that fills only part of a segment, issued when the file cache does not hold enough dirty blocks to fill a whole one; each carries its own summary block.
InodeThe per-file record of attributes (type, owner, permissions, times) plus the disk addresses of the file's first ten blocks and of its indirect blocks. Same format as in FFS, but in LFS it lives in the log, not at a fixed place.
Inode mapA table indexed by inode number whose entries hold the inode's current disk address, a version number and the last access time. Its blocks are themselves written to the log; the active part is cached in memory.
Checkpoint regionOne of two fixed places on disk that hold the addresses of all inode map and segment usage table blocks, a timestamp, and a pointer to the last segment written: the starting point after a reboot.
Segment summary blockA block written inside each segment (one per log write) that lists, for every block in that write, which file it belongs to and which block of the file it is, plus the file's uid.
Live block / dead blockA block is live if some current inode or indirect block still points to it; it is dead once the file was deleted or the block was overwritten (a newer copy exists further along the log).
Version number, uidA counter in each inode map entry, incremented when the file is deleted or truncated to zero. The pair (inode number, version) is the uid, an identifier for one incarnation of a file's contents.
Segment cleanerThe process that reads segments, keeps the live blocks, writes them back compacted into fewer segments, and marks the old segments clean (free).
Utilization uThe fraction of a segment's bytes that are live. The paper distinguishes u of the segments being cleaned from the overall disk capacity utilization.
Write costThe disk time spent per byte of new data, including cleaning, as a multiple of the time the bytes would take at full bandwidth with no seeks. 1.0 is perfect; 10 means a tenth of the bandwidth carries new data.
Greedy policyA cleaning policy that always cleans the least-utilized segments.
Cost-benefit policyA cleaning policy that cleans the segments with the highest (1−u)·age/(1+u), where age is the time since the youngest block in the segment was modified.
Age sortWriting the live blocks found by the cleaner in order of their last modification time, so blocks of similar age end up in the same new segments.
Segment usage tableA per-segment table of live bytes and most recent modification time, kept in the log and located through the checkpoint region; the cleaner's input for choosing segments.
Roll-forwardThe recovery step that scans the log written after the last checkpoint and folds the complete changes it finds (new inodes, their data, directory operations) back into the inode map and usage table.
Directory operation logA stream of small log records, one per directory change (create, link, rename, unlink), each written before the directory block or inode it describes, so roll-forward can make directories and link counts agree.
Synchronous writeA write the application must wait for until the disk has completed it, as opposed to one copied into the cache and written later in the background.
Temporal locality vs logical localityTwo ways to place data on disk: by when it was written (LFS: blocks written together sit together) or by how it is expected to be read (FFS: a file's blocks in order, files of a directory nearby).
Short primers (tap to open)
1Where a 1990 disk spends its time▾

The FFS primer still holds: every request pays a seek (move the arm), a rotational wait, then the transfer. The paper's test disk is a Wren IV: "1.3 MBytes/sec maximum transfer bandwidth, 17.5 milliseconds average seek time." At 3600 rpm (general knowledge for this drive class, not in the paper) the average rotational wait is 8.3 ms.

So a 4 KB write to a random place costs about 17.5 + 8.3 + 3.1 = 29 ms, of which 3.1 ms moves data: about 11% of the bandwidth. A 1 KB write uses about 3%. A 1 MB write after the same positioning takes about 770 ms of transfer, so positioning is about 3% of the time (this guide's arithmetic).

The paper's argument rests on a trend: "Disk transfer bandwidth can be improved substantially with the use of disk arrays and parallel-head disks but no major improvements seem likely for access time". Large transfers will keep getting faster; small transfers separated by seeks will not.

Now you're ready: LFS's whole design is a way to turn many 29 ms small writes into a few long transfers.
2What FFS does when you create a small file▾

From the FFS guide: the disk is cut into cylinder groups, each with a fixed inode area and a free-space bitmap (FFS M5). A new file's inode goes in its directory's group (M10), and its data near its inode (M11), chosen by the local allocator (M12). Every inode therefore has a fixed home: inode number → group → slot, a calculation.

Creating dir/f changes four separate structures: f's inode, f's data block, the directory's data block (the new entry), and the directory's inode (size, times). They sit in different places, even within one group. FFS also writes metadata in a fixed order so that fsck can repair a crash (FFS M2: "staging modifications to critical file system information"), and the LFS paper says those inode and directory writes are synchronous. The FFS paper itself never measured creates or deletes.

Now you're ready: the LFS paper's count of "at least five separate disk I/Os, each preceded by a seek" is these four structures, with the new inode written twice.
3The file cache, write-back, and what "synchronous" costs▾

The kernel keeps file blocks in memory (the file cache, FFS's buffer cache). A read that hits in the cache costs no disk I/O. A write can be asynchronous: copied into the cache, with the disk write later, perhaps combined with others. Or it can be synchronous: the call returns only after the disk write completes, so the program runs at the disk's pace.

Delaying writes risks losing them in a crash. The paper accepts that: "we will assume that crashes are infrequent and that it is acceptable to lose a few seconds or minutes of work in each crash; for applications that require better crash recovery, non-volatile RAM may be used for the write buffer."

Now you're ready: LFS makes almost every write asynchronous and uses the cache as a large write buffer, which is what lets it batch.
4Logs, checkpoints and redo, as databases use them▾

A database (general knowledge, and Section 6 of the paper) appends a record of each change to a log before changing the data in place. After a crash it starts from a checkpoint, a known consistent state, and redoes the logged changes made since. Once changes reach their permanent location, the log space is reclaimed. Group commit writes many transactions' log records in one disk write.

Earlier logging file systems (Cedar, Episode) did the same: a log for speed and recovery, plus a traditional layout as the permanent home. LFS's difference: "a log-structured file system stores data permanently in the log: there is no other structure on disk."

Now you're ready: because the log is the permanent home, LFS cannot simply discard old log space; it must find and move the live data first. That is the cleaner.
5Copying garbage collection and the generational idea▾

A copying collector (general knowledge; the paper cites Baker 1977) reclaims memory by copying the reachable objects out of a region and then treating the whole region as free. Its cost is proportional to what survives, not to what died.

A generational collector (the paper cites Lieberman and Hewitt) relies on an observation: most objects die young, and objects that have survived a while tend to keep surviving. So it collects the young region often and the old region rarely.

Now you're ready: the LFS cleaner is a copying collector over segments, and the cost-benefit policy is the generational idea applied to disk blocks, with "age" standing in for expected lifetime.
6The 1991 setting: Sprite, Sun-4, SunOS▾

Sprite was Berkeley's network operating system for workstations, with large file caches on clients and servers and many diskless clients (the paper's /swap2 and /tmp serve 40 diskless workstations). Sprite LFS was implemented starting in late 1989 and in production from fall 1990 on five partitions used by about thirty people.

The benchmark machine is a Sun-4/260 (8.7 integer SPECmarks, 32 MB of memory) with a Wren IV disk. The comparison system is SunOS 4.0.3, "whose file system is based on Unix FFS", using 8 KB blocks; Sprite LFS uses 4 KB blocks and 1 MB segments.

Now you're ready: when the paper says "Unix FFS" in the measurements, it means SunOS 4.0.3's FFS-derived file system on this machine.
The whole story in one place

Make every write sequential, then keep free space in big pieces

Read caching takes care of most reads; LFS reorganizes the disk around writes and pays for it with a cleaner.

The paper starts from technology, not from FFS. Processors are getting faster "at a nearly exponential rate". Disks are improving "primarily in the areas of cost and capacity rather than performance": transfer bandwidth can grow with disk arrays, but access time "is determined by mechanical motions that are hard to improve". Main memory is growing exponentially, which has two effects. Larger file caches absorb a greater fraction of reads, and since "most write requests must eventually be reflected on disk for safety", disk traffic becomes dominated by writes. And the cache can serve as a write buffer, collecting many modified blocks to write "in a single sequential transfer with only one seek". The workload that matters is office and engineering work, dominated by small files of a few kilobytes, whose creation and deletion "are often dominated by updates to file system metadata".

Against that background the paper names two problems in current file systems, with Unix FFS as the example. First, they "spread information around the disk in a way that causes too many small accesses": FFS "is quite effective at laying out each file sequentially on disk, but it physically separates different files", and a file's inode is separate from its contents, "as is the directory entry containing the file's name". Creating one file takes at least five separate disk I/Os, each preceded by a seek, and small-file writes use "less than 5% of the disk's potential bandwidth". Second, they "tend to write synchronously": FFS writes data blocks asynchronously, but directories and inodes synchronously, which ties applications to disk speed; such writes "defeat the potential use of the file cache as a write buffer".

Sprite LFS answers both at once. It buffers a sequence of changes in the file cache and writes all of them, data blocks, inodes, indirect blocks, directory blocks, to the end of a log in one large sequential write. Nothing has a fixed home any more, so an inode map records where each inode currently is; its active part stays in memory, and once the inode is found, reading a file takes the same I/Os as in FFS. Only the superblock and two checkpoint regions sit at fixed places.

The price is free space. When the log wraps around the disk, the free space is scattered among live blocks. Sprite LFS divides the disk into 512 KB or 1 MB segments and runs a cleaner that reads segments, keeps only live blocks (identified with a summary block per write and a version number per file), and writes them back compacted. Cleaning segments that are a fraction u live costs 2/(1−u) times the ideal per byte of new data, so the cleaner wants nearly empty segments. Simulation showed that the obvious choice, always clean the emptiest segment, gets worse when some files are hot and others cold. The cost-benefit policy instead weighs free space by how long it will stay free, using the age of the data, and drives segments into a bimodal distribution: most nearly full, a few nearly empty.

Crash recovery becomes a short job: read the newer of two checkpoint regions, then roll forward through the log written after it, using summary blocks and a directory operation log to finish or drop half-done operations. Measured on a Sun-4 with a Wren IV disk, Sprite LFS creates and deletes small files roughly ten times faster than SunOS, writes large files faster, and reads at the same speed except in one case. In four months of production use, cleaning cost was low (write cost 1.2 to 1.6) because more than half of the segments cleaned were already empty.

The one case is the conceptual heart of the paper's evaluation. FFS achieves logical locality: it assumes how data will be read and "pays extra on writes, if necessary" to lay it out that way. LFS achieves temporal locality: what is written together sits together. When the two agree, as for a file written and read sequentially, they perform alike; when a file is written randomly and then read sequentially, LFS must seek and is much slower.

Questions worked through

Is scattering writes an optimization for reads? Isn't it just an outcome of small-file workloads on a layout with fixed homes, rather than a chosen optimization?

You are right: it is an outcome, not a chosen optimization. What FFS chose, and argued for in its own paper, was a layout of fixed homes picked for read locality: each inode at a fixed slot in a cylinder group, a file's inode in its directory's group, its data near its inode, consecutive blocks at rotationally optimal positions (FFS guide M5, M9 to M12). Every goal there is stated in terms of reading: fewer seeks for ls -l, faster sequential reads, the 47% read bandwidth of Table II.

Writes then follow from two further properties. FFS updates in place: once a block or inode has a home, every later change to it is written back to that home. And a small-file create changes several structures that have different homes: the new file's inode, its data block, the directory's data block, and the directory's inode. So one create touches four places (five writes, since the paper says the new inode is written twice), no matter how well each place was chosen. With 1 KB files the data block is a small part of what is written, and most of the time goes to positioning; that is the paper's "less than 5%". The FFS paper never discusses this case at all; it measured large files.

The synchronous metadata writes are a separate choice, made for crash consistency, not for layout: metadata is written in a fixed order so that fsck can repair a crash (FFS guide M2). The LFS paper lists it as a separate problem (problem 2), and its "FFS improved" estimate keeps the fixed-home layout but adds "logging, delayed writes, and disk request sorting", raising small-file write bandwidth to "about 25%". That shows the two costs are separable.

The LFS paper's own framing matches yours. Section 2.3 calls the scattering a problem: current file systems "spread information around the disk in a way that causes too many small accesses", and FFS "is quite effective at laying out each file sequentially on disk, but it physically separates different files." The only place it ties write cost to read layout is Section 5.1, in the Figure 9 discussion: "A traditional file system achieves logical locality by assuming certain access patterns (sequential reading of files, a tendency to use multiple files within a directory, etc.); it then pays extra on writes, if necessary, to organize information optimally on disk for the assumed read patterns. In contrast, a log-structured file system achieves temporal locality: information that is created or modified at the same time will be grouped closely on disk." "Pays extra on writes, if necessary" describes a price accepted to keep the read layout, not an optimization whose purpose is scattering. The one place FFS deliberately spreads things (new directories to emptier groups, large files hopping groups every megabyte, FFS guide M10 and M11) is to keep room near each home for later allocation, which again serves reads.

🍯 Key takeaways

  • The premise is a trend: CPUs and memory grow fast, disk access time does not, and big caches turn disk traffic into mostly writes.
  • FFS's two small-file problems are separate: fixed homes spread one create over five I/Os, and metadata is written synchronously for crash consistency.
  • LFS writes all changes, metadata included, as one sequential log write; an inode map (cached) replaces fixed inode locations, so reads cost the same once the inode is found.
  • Free space is the hard part: segments plus a copying cleaner, with write cost 2/(1−u) for the segments cleaned.
  • The obvious "clean the emptiest" policy fails under locality; cost-benefit with age sort gives a bimodal distribution and, in production, write costs of 1.2 to 1.6.
  • LFS trades logical locality for temporal locality: fast random writes, slow sequential reads of randomly written files.
Six everyday pictures

How to think about a log-structured file system

Each stands alone. Every card ends with where the picture stops being true, tied to a mechanism in How It Works.

The log · the inode map

A lab notebook you never erase, with an index card in front

Every change is written on the next blank line, never over an old entry. A correction is a new entry further on. To find the current version of an experiment you check the index card, which says which page holds it. Writing is fast (always the next line); reading needs one look at the card, then one page turn. That is LFS: append-only writes, and an inode map telling where each file's newest inode is.

Where it breaks: the index card is itself rewritten into the notebook every time it changes, and the notebook runs out of pages; LFS must copy still-current entries forward to reuse old pages (M5, M10).
Synchronous writes · the cache as a write buffer

Waiting at the post office counter for a receipt on every letter

If you must hand each letter over and wait for a stamped receipt before writing the next, your speed is set by the queue at the counter. Dropping letters in a bag and mailing the bag once an hour lets you work at your own pace. FFS's synchronous inode and directory writes are the counter; LFS's file cache is the bag, emptied in one large write.

Where it breaks: a bag can be lost before it is mailed; the paper accepts losing "a few seconds or minutes of work" in a crash, or suggests non-volatile RAM for the bag (M3, M4).
Segment cleaning · write cost 2/(1−u)

Emptying half-full storage units so you can return whole ones

You rent identical storage units and always want a completely empty one ready. When several units are mostly empty, you load the remaining boxes from two units into a third and hand back the two. The work is proportional to what you must carry: units that are 10% full are cheap to consolidate, units that are 80% full cost a lot of carrying for little freed space. That is the cleaner, whose cost per freed byte grows as 2/(1−u).

Where it breaks: a unit whose boxes have all been thrown away needs no visit at all; in LFS such a segment (u = 0) is reused without being read, so the write cost is 1.0, not 2 (M12).
Cost-benefit cleaning · hot and cold data

Reorganizing the freezer, not the fridge

Your fridge is 30% full but its contents will be eaten this week, so the space frees itself soon; tidying it now buys little. Your freezer is 75% full, but nothing in it will move for months. Consolidating the freezer's half-empty shelves costs more carrying, yet the space you free stays free. The cost-benefit policy reasons the same way: free space is worth more in a segment of old, stable data.

Where it breaks: you know what is in your freezer; LFS only knows how long ago data was last written and assumes "the older the data in a segment the longer it is likely to remain unchanged", using one modification time per file, not per block (M16, M17).
Two checkpoint regions · alternation

A game with two save slots, used in turn

You save to slot A, next time to slot B, then A again. If the power fails in the middle of a save, the slot being written may be garbage, but the other slot holds the previous good save, and the loader picks whichever slot has the later timestamp. Sprite LFS keeps two checkpoint regions and alternates between them for exactly this reason.

Where it breaks: the trick works only because the timestamp is in "the last block of the checkpoint region", so an interrupted save keeps its old time; a game that wrote the timestamp first could load a half-written save (M18).
Temporal versus logical locality

A diary versus an encyclopedia

A diary is written in time order, so writing is effortless and rereading one week is quick, but collecting everything you wrote about one topic means flipping through months. An encyclopedia puts each topic in its place, so writing a new fact means finding the right page, but reading a topic is one stop. LFS is the diary; FFS is the encyclopedia. The paper, on a file written randomly and then read sequentially: "the reads require seeks in Sprite LFS, so its performance is substantially lower than SunOS."

Where it breaks: a diary never gets reorganized, but the LFS cleaner rewrites live data and could regroup it, for example by directory; the paper names that option and chose age sorting instead (M11, M23).

Questions worked through

Can Table 1 be read as a lifecycle: when is each structure created, how is it updated, and is it ever deleted?

Yes, and one rule covers six of the eight: anything in the log is never modified where it is. A change is written as a new copy at the head of the log, the pointer to it (in the inode, the inode map, or the checkpoint region) is updated, and the old copy becomes dead space that the cleaner later reclaims by copying the still-live blocks out of its segment. Nothing in the log is "deleted" as such; deletion is just the moment the last pointer to a copy goes away, which the segment usage table records by lowering that segment's live-byte count.

The two exceptions are at fixed addresses: the superblock, written once and never again, and the two checkpoint regions, the only places ever overwritten in place, alternately, at each checkpoint. Deleting a file touches three things: its directory entry (a new directory block), its inode map entry (version number incremented, so all of the file's blocks fail the liveness check), and the usage counts of the segments that held its blocks.

What is a block, what size is it, and how does it relate to a segment?

A block is the file system's unit of storage and addressing: the fixed-size piece in which it stores file contents and metadata, and the thing every pointer points to. An inode's pointers name blocks, the segment summary has one entry per block, the cleaner decides live or dead block by block, and the file cache holds blocks. In the paper's measurements "Sprite LFS used a four-kilobyte block size and a one-megabyte segment size" (SunOS used eight-kilobyte blocks).

So the units nest: a disk sector is 512 bytes (the smallest piece the disk itself reads or writes, general knowledge); a 4 KB block is 8 sectors; a 1 MB segment is 256 blocks (Sprite LFS also supports 512 KB segments, 128 blocks). A segment holds a mix of block types: file data blocks, directory blocks, indirect blocks, blocks holding inodes, inode map and segment usage table blocks, and the segment summary blocks that describe the rest.

The two sizes do different jobs. The block is the unit of naming and bookkeeping, small enough that a 1 KB file does not waste much space. The segment is the unit of writing and cleaning, large enough that one seek is amortized over a long transfer (the paper picks a size so the transfer time is much larger than the seek). A segment is not one write of one file: it is filled with whatever dirty blocks have accumulated, from many files, and if not enough are dirty a partial segment is written with its own summary block.

1 · Why writes became the problem

CPUs are getting much faster, disk access time is not, and growing memories let file caches absorb most reads, so disk traffic is mostly writes. Office and engineering workloads write many small files. In FFS each small-file create costs at least five separate I/Os with seeks (inode twice, data, directory data, directory inode), using under 5% of the bandwidth, and the metadata writes are synchronous, so the application waits for each (M1 to M3).

2 · Write everything as one log; find it again with the inode map

Changes collect in the file cache. One log write carries data blocks, inodes, indirect blocks, directory blocks and inode map blocks, sequentially, with one seek. Inodes therefore move every time they are written, so an inode map records each inode's current address; its blocks are also in the log, and two fixed checkpoint regions record where the map blocks are. The active part of the map is cached, so reads cost what they cost in FFS (M4, M5).

3 · Keep free space in large pieces: segments and a cleaner

Threading the log through holes would fragment it; copying everything forward would recopy long-lived data on every pass. Sprite LFS does both at different scales: segments of 512 KB or 1 MB are written whole and cleaned whole, and the log skips from segment to segment. The cleaner reads segments, uses the summary block and a per-file version number to keep only live blocks, and writes them into fewer clean segments. There is no free list and no bitmap (M6 to M10).

4 · Decide what to clean: write cost and the cost-benefit policy

Cleaning segments with live fraction u costs 2/(1−u) disk time per unit of new data written. A simulator showed that cleaning the emptiest segments (greedy) is worse when access has locality, because cold segments stay just above the cleaning point for a long time. Rating segments by (1−u)·age/(1+u) and sorting live blocks by age makes the distribution bimodal and lowers write cost up to 50%. A segment usage table keeps each segment's live bytes and newest modification time (M11 to M17).

5 · Recover after a crash, and what was measured

A checkpoint writes all modified metadata to the log, then writes a checkpoint region (alternating between two). Recovery reads the newer region and rolls forward through later segments, using summary blocks and a directory operation log; it takes about a second for typical amounts of data instead of an fsck scan of the whole disk (M18 to M20). The measurements: small-file creates and deletes about ten times faster than SunOS, large-file writes faster, reads equal except rereading a randomly written file, and a production write cost of 1.2 to 1.6 (M21 to M25).

P · Paper map

Background and context
  • Mendel Rosenblum and John K. Ousterhout, UC Berkeley. Presented at the 13th ACM Symposium on Operating Systems Principles (1991) and published in ACM Transactions on Computer Systems 10(1), February 1992. The course copy is the version dated July 24, 1991.
  • Built inside the Sprite network operating system: implementation began in late 1989, operational by mid-1990, in production since fall 1990 on five partitions used by about thirty people.
  • Comparison system throughout: "the Berkeley Unix fast file system (Unix FFS)", the subject of the previous paper, chosen "because it is well documented in the literature and used in several popular Unix operating systems". The measurements use SunOS 4.0.3, "whose file system is based on Unix FFS".
  • Prior work it builds on: logging file systems with a separate home for data (Cedar, Episode), write-once optical file systems (Swallow, Finlayson and Cheriton's log files), database write-ahead logging and group commit, copying and generational garbage collectors.
The problem

Disk access time is not improving while CPUs and memories are, so file systems whose small writes each pay a seek will become the bottleneck. For small files, FFS uses "less than 5% of the disk's potential bandwidth" for new data because one create touches five separate places (problem 1), and it makes applications wait for synchronous metadata writes (problem 2).

The result

Sprite LFS writes all changes sequentially to a log. It "outperforms current Unix file systems by an order of magnitude for small-file writes while matching or exceeding Unix performance for reads and large writes", with the one exception of sequential reads after random writes. "Even when the overhead for cleaning is included, Sprite LFS can use 70% of the disk bandwidth for writing, whereas Unix file systems typically can use only 5-10%." Crash recovery examines only the end of the log.

Mechanisms in dependency order
  1. Diagnose (M1 to M3): technology and workload trends; information spread around the disk; synchronous metadata writes.
  2. Write as a log, read through an index (M4, M5): batch all changes into one sequential write; the inode map replaces fixed inode locations.
  3. Create free space (M6 to M10): threading versus copying; segments as the hybrid; summary blocks and uids to find live data; the cleaner, with no bitmap or free list.
  4. Choose what to clean (M11 to M17): the four policy questions; write cost 2/(1−u); utilization of cleaned segments versus the disk; the simulator; greedy's failure under locality; cost-benefit with age sort; the segment usage table that feeds it.
  5. Recover (M18 to M20): checkpoints in two alternating regions; roll-forward; the directory operation log.
  6. Measure (M21 to M25): implementation experience; small-file and large-file benchmarks; four months of production cleaning; recovery time and metadata overhead.
The central trade-offs
  • Write speed versus cleaning cost: every write is sequential, but every byte that stays live in a segment being cleaned must be read and written again.
  • Space versus performance: "if disk space is underutilized, higher performance can be achieved but at a high cost per usable byte; if disk capacity utilization is increased, storage costs are reduced but so is performance."
  • Temporal versus logical locality: data written together is read together fast; data written in a different order from the one it is read in is slow to read.
  • Durability versus batching: buffering writes in memory makes them sequential and asynchronous but loses "a few seconds or minutes of work" in a crash; recovery time grows with the checkpoint interval.
Effect of changes (whole design)
  • If caches stop absorbing reads (working sets larger than memory), the premise that "disk traffic will become dominated by writes" fails, and LFS's read layout matters more (inference; see M23).
  • If applications force writes to disk often (fsync, NFS servers committing before replying), each log write is small and LFS loses much of its batching (inference; see M3, M4).
  • If the disk is nearly full of live data that keeps changing, cleaned segments have high u and write cost rises without bound as u → 1 (M12, M13).
  • If seeks become free (flash, general knowledge), the seek argument disappears but out-of-place writing and cleaning reappear in the device itself; F2FS (11/5) is the CS240 example.

M1 · The premises: faster CPUs, slow disk access, big caches, small files

TL;DR
ProblemWhich part of the system will limit file system performance in the 1990s, and for which workload?
MechanismA model of trends: CPU speed rising nearly exponentially, disk access time nearly flat, memory growing so caches absorb reads and can buffer writes; office and engineering workloads of small files.
Trade-offDesign for small-file writes and leave large-file bandwidth "to hardware designers", accepting the loss of buffered writes in a crash.
Breaks whenCaches do not absorb most reads, applications insist on immediate durability, or the workload is large sequential transfers.
Key points
  • Processors: "their speed is increasing at a nearly exponential rate, and the improvements seem likely to continue through much of the 1990's. This puts pressure on all the other elements of the computer system to speed up as well, so that the system doesn't become unbalanced."
  • Disks: "the improvements have been primarily in the areas of cost and capacity rather than performance." Transfer bandwidth "can be improved substantially with the use of disk arrays and parallel-head disks but no major improvements seem likely for access time (it is determined by mechanical motions that are hard to improve)."
  • Consequence: "If an application causes a sequence of small disk transfers separated by seeks, then the application is not likely to experience much speedup over the next ten years, even with faster processors."
  • Memory, first effect: "larger file caches alter the workload presented to the disk by absorbing a greater fraction of the read requests. Most write requests must eventually be reflected on disk for safety, so disk traffic (and disk performance) will become more and more dominated by writes."
  • Memory, second effect: caches "can serve as write buffers where large numbers of modified blocks can be collected before writing any of them to disk. Buffering may make it possible to write the blocks more efficiently, for example by writing them all in a single sequential transfer with only one seek."
  • The cost accepted: "we will assume that crashes are infrequent and that it is acceptable to lose a few seconds or minutes of work in each crash; for applications that require better crash recovery, non-volatile RAM may be used for the write buffer."
  • Workload: "Office and engineering applications tend to be dominated by accesses to small files; several studies have measured mean file sizes of only a few kilobytes." "Small files usually result in small random disk I/Os, and the creation and deletion times for such files are often dominated by updates to file system 'metadata'."
  • Large files are set aside: "A number of techniques exist for ensuring that such files are laid out sequentially on disk, so I/O performance tends to be limited by the bandwidth of the I/O and memory subsystems rather than the file allocation policies." The authors "decided to focus on the efficiency of small-file accesses, and leave it to hardware designers to improve bandwidth for large-file accesses."
How it works, step by step: why a faster CPU does not help a program that waits on small writes
  1. Today (illustrative): a program step uses 40 ms of CPU and then waits for 5 synchronous metadata writes of about 12 ms each = 60 ms. Total 100 ms per step.
  2. CPU 10× faster: 4 ms of CPU + the same 60 ms of disk waits = 64 ms. Only 1.6× faster, because the disk part did not shrink (Amdahl's law, general knowledge).
  3. Same machine with the writes buffered: the step takes 4 ms of CPU; the disk writes happen later, batched. The program's speed is now set by how fast the disk can absorb the batched writes, which is what LFS makes nearly the full sequential bandwidth.
  4. The paper's measured version of this: in Figure 8, SunOS kept the disk 85% busy creating files while LFS kept it 17% busy with the CPU saturated, so LFS is predicted to scale 4 to 6× with faster CPUs and SunOS hardly at all (M22).
Assumptions it relies on
  • A1. Growing memory lets caches absorb most reads (stated, citing trace studies [1, 6]).
  • A2. Access time will not improve much, while transfer bandwidth can (stated).
  • A3. Losing a few seconds or minutes of work per crash is acceptable (stated).
  • A4. Small files dominate the hard workloads (stated, citing measured mean sizes).
  • A5. Large-file throughput is a hardware problem, not a layout problem (stated).
If an assumption changes
  • A1 changes (reads miss the cache): read traffic returns to the disk, and LFS's placement by write time can make some reads slower than FFS's placement by expected read order (M23). The design's whole tilt toward writes loses its justification (inference).
  • A2 changes (access time becomes small, as on flash; general knowledge): the seek argument for large sequential writes weakens, but a device that cannot overwrite in place still benefits from out-of-place writing and pays a cleaning cost of the same 2/(1−u) form (inference; F2FS).
  • A3 changes (applications need data durable when a call returns): each forced write becomes a small partial segment with its own summary block and seek, so the batching that LFS depends on disappears unless non-volatile RAM holds the buffer, as the paper suggests (inference from M4, M8).
  • A4 changes (large sequential files dominate): the paper says LFS still "works well", and very large files deleted whole leave whole empty segments that cost nothing to clean (Section 7).
  • A5 changes (layout matters for large files after all): LFS lays a large file out in write order, which is good for sequential writes followed by sequential reads but not for random writes followed by sequential reads (M23).
Design notes and rejected alternatives

The paper treats "technology" and "workload" as the two forces that govern file system design and derives its focus from both: a component that will not speed up (access time) and a workload that hits it hardest (small files). It explicitly does not try to improve large-file bandwidth, which FFS had spent most of its effort on.

Connections

FFS: the previous paper's premise was the opposite: large files on a 1984 VAX, where positioning delays during reads were the problem and the CPU became the limit after the fix. Rethink the Sync (10/29): revisits A3, when a write must really be durable. Livelock: the same "CPU got faster, the slow component now dominates" argument, applied there to interrupts (inference).

M2 · Problem 1: information spread around the disk

TL;DR
ProblemA small-file create in FFS changes several structures that each have their own place on disk, so it costs several small writes, each with a seek.
Mechanism (of the problem)FFS lays each file out sequentially but physically separates different files, and keeps the inode and the directory entry apart from the file's data. Each change is written to its own home.
Trade-offGood layout for reading one file or one directory, paid for by positioning delays on every small write.
Breaks whenMost writes are small files: then "less than 5% of the disk's potential bandwidth is used for new data".
Key points
  • "First, they spread information around the disk in a way that causes too many small accesses. For example, the Berkeley Unix fast file system (Unix FFS) is quite effective at laying out each file sequentially on disk, but it physically separates different files. Furthermore, the attributes ('inode') for a file are separate from the file's contents, as is the directory entry containing the file's name."
  • "It takes at least five separate disk I/Os, each preceded by a seek, to create a new file in Unix FFS: two different accesses to the file's attributes plus one access each for the file's data, the directory's data, and the directory's attributes."
  • "When writing small files in such a system, less than 5% of the disk's potential bandwidth is used for new data; the rest of the time is spent seeking."
  • Figure 1's caption: for two single-block files in two directories, "Unix FFS requires ten non-sequential writes for the new information (the inodes for the new files are each written twice to ease recovery from crashes)".
  • "The problems presented in this section are not unique to Unix FFS and can be found in most other file systems."
How it works, step by step: creating dir/f with 1 KB of data in FFS
  1. The new inode is written in its slot in the directory's cylinder group (FFS guide M10): access 1.
  2. The directory's data block gets the new (name, inode number) entry: access 2.
  3. The directory's inode (modification time, perhaps size) is rewritten in its own slot: access 3.
  4. The file's data block is written near the inode (FFS guide M11): access 4.
  5. The file's inode again, now with the data block's address and size: access 5. The paper gives the count and the reason ("to ease recovery from crashes"), not the order; the order above is this guide's illustration.
  6. Cost on a Wren IV (illustrative): with short in-group seeks of about 5 ms plus 8.3 ms average rotation, five writes take about 5 × 14 = 70 ms to store 1 KB of data: 1 KB / 70 ms ≈ 15 KB/s ≈ 1.1% of 1.3 MB/s. With average 17.5 ms seeks it would be about 0.6%. Figure 8 measured "about 1.2%" for SunOS (this guide's arithmetic; the in-group seek time is an assumption).
Assumptions it relies on
  • A1. Each structure (inode, directory block, data block) has a fixed home and is updated there (implicit in FFS).
  • A2. Files are small, so the data is a small part of what a create writes (stated).
  • A3. Each change reaches the disk as its own I/O (implicit; follows from problem 2).
If an assumption changes
  • A1 changes (homes are co-located, for example the inode stored inside the directory entry): a create touches fewer places and needs fewer seeks; later research file systems tried this (general knowledge, not in the paper).
  • A2 changes (large files): the data dominates and FFS writes it sequentially, so the five metadata accesses are amortized; this is why FFS's own measurements looked good.
  • A3 changes (writes delayed and sorted): several creates' changes to the same group can be merged and ordered; the paper's "FFS improved" estimate, with "logging, delayed writes, and disk request sorting", reaches "about 25% of the bandwidth" (M12).
Design notes and rejected alternatives

The paper does not claim FFS chose to scatter writes. It says FFS lays out files well and that the separation of files, inodes and directory entries "causes too many small accesses" when files are small. See The Big Idea, "Questions worked through", for why the scattering is an outcome of fixed homes plus update in place, and Section 5.1's own framing (M23).

Connections

FFS: the cylinder-group policies (FFS guide M10 to M12) keep a file's inode, its data and its directory's other files in one group, so the five accesses are short seeks, not long ones; the paper's complaint is their number, not their distance. NFS: an NFS server's synchronous create is exactly this sequence, done before replying (inference).

M3 · Problem 2: synchronous metadata writes

TL;DR
ProblemApplications wait for disk writes, so they run at disk speed and cannot benefit from faster CPUs or from a large cache.
Mechanism (of the problem)FFS writes data blocks asynchronously, but directories and inodes synchronously; NFS added more synchronous writes.
Trade-offSimpler crash recovery in exchange for write performance.
Breaks whenThe workload has many small files, so "the disk traffic is dominated by the synchronous metadata writes".
Key points
  • "The second problem with current file systems is that they tend to write synchronously: the application must wait for the write to complete, rather than continuing while the write is handled in the background."
  • "For example even though Unix FFS writes file data blocks asynchronously, file system metadata structures such as directories and inodes are written synchronously. For workloads with many small files, the disk traffic is dominated by the synchronous metadata writes."
  • "Synchronous writes couple the application's performance to that of the disk and make it hard for the application to benefit from faster CPUs. They also defeat the potential use of the file cache as a write buffer."
  • "Unfortunately, network file systems like NFS have introduced additional synchronous behavior where it didn't used to exist. This has simplified crash recovery, but it has reduced write performance."
  • On the Andrew benchmark, "Most of the speedup is attributable to the removal of the synchronous writes in Sprite LFS" (Section 5).
How it works, step by step: what synchronous metadata does to a burst of creates
  1. Program creates 100 small files in a loop. With synchronous metadata, each creat returns only after its inode and directory writes reach the disk.
  2. The disk sees them one at a time: there is never more than one create's metadata pending, so the driver cannot sort or merge requests from different creates (general knowledge about disk queues, as in the FFS guide's primer 3).
  3. Measured: SunOS creates 1 KB files at about 15 per second with the disk 85% busy (Figure 8, read off); about 57 ms of disk time per file (this guide's arithmetic).
  4. With asynchronous metadata the 100 creates would return at CPU speed and the dirty blocks would wait in the cache, where they could be merged and written in fewer, larger I/Os. That is what LFS does, and it goes further by writing them all in one place (M4).
Assumptions it relies on
  • A1. FFS needs metadata ordering for crash recovery and gets it by waiting for each write (implicit; FFS guide M2: updates staged so fsck can repair them).
  • A2. Applications do not need their data durable when a call returns, so waiting is not required by the application (stated as an assumption for LFS in Section 2.1).
If an assumption changes
  • A1 changes (ordering obtained another way): a file system can keep FFS's layout but order metadata with a log or with dependency tracking in the cache; later BSD did the latter (soft updates, general knowledge, not in the paper). LFS gets ordering from the log itself and from the directory operation log (M20).
  • A2 changes (applications do need durability): the write must reach the disk before returning in any design; LFS can at best make that one sequential write rather than five scattered ones, which still helps (inference).
Design notes and rejected alternatives

The paper separates this problem from problem 1: a file system could keep fixed homes and drop synchronous writes, or write synchronously to a log. The "FFS improved" estimate (M12) is the first option; LFS takes neither path half-way and changes both.

Connections

NFS (10/22): the paper names NFS's server-side synchronous writes as "additional synchronous behavior". Rethink the Sync (10/29): argues durability can be delayed until it is observable, the most direct follow-up to A2 (inference). FFS: the ordered metadata writes come from the "staging modifications" in FFS guide M2.

M4 · The core move: buffer the changes, write them as one sequential log write

TL;DR
ProblemMany small, scattered, synchronous writes per operation.
MechanismCollect dirty blocks of all kinds in the file cache; write them together at the head of a log in one sequential transfer; never overwrite in place.
Trade-offNearly full disk bandwidth for writes, in exchange for losing buffered data in a crash, finding moved data through an index (M5), and reclaiming free space (M6 onward).
Breaks whenToo little dirty data accumulates between forced writes, or there is no large free extent to write into.
Key points
  • "The fundamental idea of a log-structured file system is to improve write performance by buffering a sequence of file system changes in the file cache and then writing all the changes to disk sequentially in a single disk write operation."
  • "The information written to disk in the write operation includes file data blocks, attributes, index blocks, directories, and almost all the other information used to manage the file system."
  • "For workloads that contain many small files, a log-structured file system converts the many small synchronous random writes of traditional file systems into large asynchronous sequential transfers that can utilize nearly 100% of the raw disk bandwidth."
  • Two issues follow: "how to retrieve information from the log" (Section 3.1) and "how to manage the free space on disk so that large extents of free space are always available for writing new data. This is a much more difficult issue".
  • Figure 1: for dir1/file1 and dir2/file2, "Sprite LFS performs the operations in a single large write", which also contains "new inode map blocks to record the new inode locations".
  • The introduction's contrast with earlier logging file systems: "these other systems use the log only for temporary storage; the permanent home for information is in a traditional random-access storage structure on disk. In contrast, a log-structured file system stores data permanently in the log: there is no other structure on disk."
How it works, step by step: the two creates of Figure 1
  1. Creates return immediately. creat("dir1/file1") and a 4 KB write dirty four cache blocks: file1's data, file1's inode, dir1's directory block, dir1's inode. The same for dir2/file2. Nothing has gone to disk.
  2. A log write is triggered (the paper does not specify the trigger beyond partial-segment writes "when the number of dirty blocks buffered in the file cache is insufficient to fill a segment" and the 30-second checkpoints; Sprite's cache writing back dirty blocks after about 30 seconds is general knowledge).
  3. The blocks are laid out in order at the log head: data, then the inode that points to it, for each file and directory, then an inode map block recording the four inodes' new addresses, plus a summary block describing them (M8).
  4. One I/O: about 10 blocks of 4 KB = 40 KB. On the Wren IV: about 26 ms positioning + 40 KB / 1.3 MB/s ≈ 30 ms transfer ≈ 56 ms, compared with ten separate writes of about 14 to 26 ms each, 140 to 260 ms, in FFS (this guide's illustrative arithmetic).
  5. With more files in the batch, the single positioning delay is shared by more data: the cost per file approaches its transfer time, which is why LFS's create rate in Figure 8 is limited by the CPU, not the disk.
Assumptions it relies on
  • A1. Enough dirty data accumulates between writes to amortize one positioning delay (implicit).
  • A2. Losing the buffered changes in a crash is acceptable (stated, M1).
  • A3. A large free extent is always available at the log head (stated as a requirement: "it must ensure that there are always large extents of free space available").
  • A4. Every structure can be found again after it moves (stated; solved by M5).
If an assumption changes
  • A1 changes (writes forced after every operation): each log write holds a few blocks plus a summary block, so it is a small write again, though still one positioning delay instead of five (inference).
  • A2 changes: put the buffer in non-volatile RAM, as the paper suggests, so batching survives a crash.
  • A3 changes (no clean segment available): new writes must wait for the cleaner; the paper's thresholds start cleaning early to avoid this (M11).
  • A4 changes (no index): a file could only be found by scanning the log, the impression the paper dismisses: "Although the term 'log-structured' might suggest that sequential scans are required to retrieve information from the log, this is not the case in Sprite LFS."
Design notes and rejected alternatives

The rejected alternative is a log plus a home location (Cedar, Episode): it keeps reads simple but writes data twice, and "Logging file systems like Episode or Cedar are likely to be somewhat more complicated than either Unix FFS or Sprite LFS, since they include both logging and layout code." Section 6 adds that collecting data and writing it in large writes "is similar to the concept of group commit in database systems".

Connections

Rethink the Sync (10/29): batching in memory until an output is externally visible (inference). F2FS (11/5): a log-structured layout for flash. Hints (12/1): "batch processing" and "use a log" are both among Lampson's hints (general knowledge).

M5 · Finding files again: inodes in the log, located by the inode map

TL;DR
ProblemInodes move every time they are written, so the inode number no longer gives the inode's address by arithmetic.
MechanismAn inode map, indexed by inode number, holds each inode's current address (plus version number and access time). Its blocks are written to the log; the checkpoint region lists them; the active part is cached in memory.
Trade-offOne more level of indirection, nearly free when cached, in exchange for being able to write inodes anywhere; the map blocks themselves add log traffic (7.8% on /user6).
Breaks whenThe active part of the map does not fit in memory, so lookups need disk reads.
Key points
  • "The basic structures used by Sprite LFS are identical to those used in Unix FFS: for each file there exists a data structure called an inode, which contains the file's attributes (type, owner, permissions, etc.) plus the disk addresses of the first ten blocks of the file; for files larger than ten blocks, the inode also contains the disk addresses of one or more indirect blocks".
  • "Once a file's inode has been found, the number of disk I/Os required to read the file is identical in Sprite LFS and Unix FFS."
  • "In Unix FFS each inode is at a fixed location on disk; given the identifying number for a file, a simple calculation yields the disk address of the file's inode. In contrast, Sprite LFS doesn't place inodes at fixed positions; they are written to the log."
  • "The inode map is divided into blocks that are written to the log; a fixed checkpoint region on each disk identifies the locations of all the inode map blocks. Fortunately, inode maps are compact enough to keep the active portions cached in main memory: inode map lookups rarely require disk accesses."
  • Table 1: the inode map "Locates position of inode in log, holds time of last access plus version number."
  • Table 4 (/user6): the inode map is 0.2% of live data but 7.8% of the log bandwidth (M25).
How it works, step by step
  1. Mount: read the newer checkpoint region (M18); it lists the addresses of all inode map blocks and segment usage table blocks. Read the map blocks into memory as needed.
  2. Open file 42: look up entry 42 in the in-memory map: inode address A, version number, last access time. No disk access when the block is cached.
  3. Read: fetch the inode at A (one I/O, or zero if the inode is cached), then the block at the address it lists, as in FFS.
  4. Write: the new data, the new inode and the dirty map block are all appended in the next log write; the old copies become dead.
  5. Access time lives in the map: Table 1 says the map entry "holds time of last access". So a read that updates the access time dirties a map block, not the inode, and many such updates share one map block (inference about the reason; the paper states only where it is kept).
  6. Size estimate (illustrative): if an entry took 16 bytes, a 4 KB map block would cover 256 inodes, and a file system with 50,000 files would have a map of about 200 blocks, 800 KB, so a few hundred KB of active entries fits easily in a 32 MB machine. The paper gives no entry size.
Assumptions it relies on
  • A1. The active part of the inode map fits in memory (stated: "compact enough").
  • A2. A fixed checkpoint region can always locate every map block (stated).
  • A3. The rest of the read path is unchanged from FFS: ten direct addresses, then indirect blocks (stated).
  • A4. Rewriting the map blocks is cheap relative to data (implicit; Table 4 shows it is 7.8% of the log on /user6).
If an assumption changes
  • A1 changes (millions of files accessed at random): map misses add one disk read per open, and LFS reads become slower than FFS, whose inode address needs no lookup (inference).
  • A2 changes (a checkpoint region is damaged): the other one is still valid but older; roll-forward from it recovers more (M18, M19).
  • A3 changes: none in the paper; any other index (extent trees, general knowledge) could be logged the same way.
  • A4 changes (many files touched, each by a little): each touched inode dirties a map block; with spread-out inode numbers, many map blocks are rewritten per log write, which the paper suspects is why the map takes 7.8% of the log with a 30-second checkpoint interval (M25).
Design notes and rejected alternatives

Keeping inodes at fixed places would bring back in-place writes, the thing the log removes. Putting the map at a fixed place would do the same for the map. Logging the map and anchoring it in a small fixed region leaves exactly two fixed-place writes per checkpoint. The paper's goal for reads: "Our goal was to match or exceed the read performance of Unix FFS."

Connections

FFS: replaces FFS's fixed inode table per cylinder group (FFS guide M5, M10), where "a simple calculation yields the disk address". x86 VMM, ESX, Superpages: the inode map is an indirection table like a page table: move the object, update one entry (inference). F2FS (11/5): keeps a node address table for the same reason (general knowledge). Hints: cache the map so the indirection costs nothing in the common case (inference).

Questions worked through

Isn't a read one more indirection in LFS, because of the inode map? How can Figure 1 claim both systems need the same number of reads?

You are right that there is an extra level: FFS computes an inode's disk address from its number, while LFS must first look the address up in the inode map. The claim of equal reads assumes the lookup hits in memory. The paper says so directly: "Fortunately, inode maps are compact enough to keep the active portions cached in main memory: inode map lookups rarely require disk accesses."

With the map block cached, reading a file is the same in both systems: the inode, then the data block (plus directory reads to resolve the name, also the same). On a miss, LFS pays one extra read for the map block; one map block covers many inodes, so the miss is amortized across them. The paper gives no entry size; at around 16 bytes per entry (illustrative), a 4 KB map block covers about 256 files, and the map for 100,000 files is about 1.6 MB, small enough to cache (this guide's arithmetic).

M6 · When the log reaches the end of the disk: threading versus copying

TL;DR
ProblemAfter one pass over the disk, free space exists only as small holes left by deleted or overwritten files.
MechanismTwo options: thread the log through the holes, leaving live data in place, or copy live data out of a region to make one large free extent (the paper's Figure 2).
Trade-offThreading costs nothing extra but fragments free space until writes are no faster than FFS; copying keeps writes large but recopies long-lived data on every pass of the log.
Breaks whenThreading: holes are small. Copying: much of the disk holds data that never changes.
Key points
  • "The most difficult design issue for log-structured file systems is the management of free space. The goal is to maintain large free extents for writing new data."
  • "Initially all the free space is in a single extent on disk, but by the time the log reaches the end of the disk the free space will have been fragmented into many small extents corresponding to the files that were deleted or overwritten."
  • Threading: "leave the live data in place and thread the log through the free extents. Unfortunately, threading will cause the free space to become severely fragmented, so that large contiguous writes won't be possible and a log-structured file system will be no faster than traditional file systems."
  • Copying: "copy live data out of the log in order to leave large free extents for writing. For this paper we will assume that the live data is written back in a compacted form at the head of the log; it could also be moved to another log-structured file system to form a hierarchy of logs, or it could be moved to some totally different file system or archive."
  • "The disadvantage of copying is its cost, particularly for long-lived files; in the simplest case where the log works circularly across the disk and live data is copied back into the log, all of the long-lived files will have to be copied in every pass of the log across the disk."
  • Figure 2's caption, on threading: "Pointers between the blocks of the log are maintained so that the log can be followed during crash recovery."
How it works, step by step: 16 blocks, 7 still live, 9 new blocks to write (illustrative)
  1. State after one pass: blocks 0, 1, 3, 7, 8, 12, 13 are live; the other 9 are holes left by deletes and overwrites.
  2. Threading: the 9 new blocks go into holes 2, 4 to 6, 9 to 11, 14 to 15: four separate runs, so four positioning delays for one log write, and runs get shorter as the disk ages.
  3. Copying: read all 16 blocks, write the 7 live ones back contiguously, then write the 9 new ones after them: one long run, but 16 blocks read and 7 written to make room for 9.
  4. Long-lived data under circular copying: if 60% of a disk is files that never change, every pass of the log rereads and rewrites that 60% to reclaim the other 40%, a cost that buys nothing (this guide's illustration of the paper's "copied in every pass").
Assumptions it relies on
  • A1. Deleted and overwritten data leaves small, scattered holes (stated).
  • A2. Copying cost is proportional to the live data moved (implicit; made exact in M12).
  • A3. Some data lives much longer than the rest (stated: "particularly for long-lived files").
If an assumption changes
  • A1 changes (files deleted whole leave large holes): threading would work well; this is the case Section 5.2 finds in practice, where whole-file deletes leave entire segments empty (M24).
  • A2 changes (copying could skip dead data cheaply): the cost of reading would fall at low utilization; the paper notes "it may be faster to read just the live blocks" but did not try it (M12).
  • A3 changes (all data has the same lifetime): nothing is gained by skipping regions, and simple circular copying is as good as anything (inference; the uniform simulation in M15 is close to this case).
Design notes and rejected alternatives

The paper rejects pure threading because it ends up no faster than a traditional file system, and pure circular copying because of the repeated copying of long-lived files. It mentions, without pursuing, moving copied data to a second log or to an archive (a hierarchy of storage). The next mechanism combines the two options at different granularities.

Connections

Garbage collection: the paper says segment cleaning "acts much like scavenging garbage collectors"; copying is the compacting collector, threading is a free-list allocator over holes (inference). F2FS (11/5): uses both, switching to threaded writes into holes when free segments run low (general knowledge, not in this paper). FFS: FFS's free-space bitmap with layout policies is the "traditional" way to use holes; the paper's claim is that a threaded log would degrade to that.

Questions worked through

What does "copied and compacted" mean: just extracting the valid data that is left, or some kind of compression?

Extracting the valid data. No bytes are encoded or shrunk. The cleaner reads whole segments, keeps only the blocks that are still live (still pointed to by a current inode or indirect block), and writes those blocks back to the log one after another with no gaps. What gets "compacted" is the free space: the dead blocks scattered across several segments disappear, and the live blocks that were spread over those segments now fill fewer segments. The rest become empty, ready for new writes.

The paper uses the word "compress" in this sense too ("regenerates empty segments by compressing the live data from heavily fragmented segments"), and describes the live data as "written back in a compacted form at the head of the log". Both mean squeezing out the holes, not data compression.

Example (the M10 figure): three segments with 40%, 30% and 20% of their blocks live hold 9 live blocks in 30 slots. The cleaner reads all 30, writes the 9 live ones into one new segment, and frees all three old segments, a net gain of about two segments. The data in those 9 blocks is byte-for-byte the same; only their disk addresses change, so the inodes (or indirect blocks) that point to them, and the inode map entries for those inodes, are rewritten with the new addresses.

M7 · Segments: thread between them, copy within them

TL;DR
ProblemGet large sequential writes without recopying long-lived data on every pass.
MechanismDivide the disk into large fixed-size segments. Each segment is written sequentially start to end and must be emptied of live data before reuse (copying); the log moves from segment to segment in any order, skipping segments full of long-lived data (threading).
Trade-offWhole-segment transfers run at nearly full bandwidth regardless of order, in exchange for having to clean at segment granularity.
Breaks whenSegments are too small relative to positioning time, or long-lived data cannot be collected into its own segments.
Key points
  • "Sprite LFS uses a combination of threading and copying. The disk is divided into large fixed-size extents called segments. Any given segment is always written sequentially from its beginning to its end, and all live data must be copied out of a segment before the segment can be rewritten."
  • "However, the log is threaded on a segment-by-segment basis; if the system can collect long-lived data together into segments, those segments can be skipped over so that the data doesn't have to be copied repeatedly."
  • "The segment size is chosen large enough that the transfer time to read or write a whole segment is much greater than the cost of a seek to the beginning of the segment. This allows whole-segment operations to run at nearly the full bandwidth of the disk, regardless of the order in which segments are accessed."
  • "Sprite LFS currently uses segment sizes of either 512 kilobytes or one megabyte." The benchmarks used a 4 KB block size and 1 MB segments.
How it works, step by step: sizing a segment for the Wren IV
  1. Positioning per segment: about 17.5 ms seek + 8.3 ms rotation ≈ 25.8 ms (seek from the paper, rotation assumed as in Step 0).
  2. Transfer: 1 MB at 1.3 MB/s ≈ 769 ms; 512 KB ≈ 385 ms; 64 KB ≈ 48 ms.
  3. Efficiency = transfer / (transfer + positioning): 1 MB: 769 / 795 ≈ 97%; 512 KB: 385 / 411 ≈ 94%; 64 KB: 48 / 74 ≈ 65%. Only the first two meet "much greater than the cost of a seek".
  4. Break-even size (transfer time = positioning time) = 1.3 MB/s × 25.8 ms ≈ 34 KB. A segment needs to be about 15 to 30 times that to waste only 3 to 6% (this guide's arithmetic).
  5. How many segments: the benchmark disk of about 300 MB holds about 300 segments of 1 MB; the cleaner's thresholds of "a few tens" and "50-100" clean segments (M11) are roughly 10% to 30% of that disk (this guide's arithmetic).
Assumptions it relies on
  • A1. A segment transfer is much longer than one seek, so segment order does not matter (stated).
  • A2. Long-lived data can be collected into its own segments, which are then skipped (stated as a condition: "if the system can collect").
  • A3. Fixed-size segments are an acceptable unit for both writing and cleaning (implicit).
If an assumption changes
  • A1 changes (disks get faster at transfer but not at seeking, exactly the paper's own trend): the break-even size grows with bandwidth × access time, so a fixed 1 MB segment slowly loses efficiency; segment size must grow with the disk (inference from M1's trend and the arithmetic above).
  • A2 changes (long-lived and short-lived data mixed in every segment): every segment eventually needs cleaning and long-lived blocks are copied again and again, the pure-copying cost the hybrid was meant to avoid; this is the simulation's hot-and-cold problem in M15.
  • A3 changes (variable-size extents): cleaning would need a free-space map at finer granularity, which the paper avoids by never reusing part of a segment (M10) (inference).
Design notes and rejected alternatives

The paper chooses the hybrid over either extreme and makes the cleaning policy responsible for A2: collecting long-lived data so that its segments can be skipped is the purpose of age sorting and the cost-benefit policy (M16).

Connections

FFS: FFS's large blocks (FFS guide M3) made each transfer worth its positioning delay; LFS applies the same arithmetic at a thousand times the size. F2FS (11/5): segments (2 MB, general knowledge) matched to flash erase units. Superpages: keeping large contiguous regions available, here by cleaning rather than by allocation policy (inference).

M8 · Segment summary blocks and partial-segment writes

TL;DR
ProblemThe cleaner and the recovery code find raw blocks in a segment and must know whose they are and where they belong.
MechanismEvery log write includes a summary block listing, for each block written, the file number and block number (and the file's uid); a segment filled by several writes has several summary blocks.
Trade-offAbout 0.5% of log bandwidth on /user6, in exchange for cleaning and roll-forward without any separate ownership map.
Breaks whenLog writes are tiny (one summary block per write becomes a large fraction), or a block can belong to more than one file.
Key points
  • "As part of segment cleaning it must be possible to identify which blocks of each segment are live, so that they can be written out again. It must also be possible to identify the file to which each block belongs and the position of the block within the file; this information is needed in order to update the file's inode to point to the new location of the block."
  • "Sprite LFS solves both of these problems by writing a segment summary block as part of each segment. The summary block identifies each piece of information that is written in the segment; for example, for each file data block the summary block contains the file number and block number for the block."
  • "Segments can contain multiple segment summary blocks when more than one log write is needed to fill the segment. (Partial-segment writes occur when the number of dirty blocks buffered in the file cache is insufficient to fill a segment.)"
  • "Segment summary blocks impose little overhead during writing, and they are useful during crash recovery (see Section 4) as well as during cleaning." Table 4: 0.6% of live data, 0.5% of log bandwidth.
  • The summary also records each block's uid (M9) and "the age of the youngest block written to the segment" (Section 3.6, for age sorting).
How it works, step by step: one 1 MB segment filled by two log writes
  1. Write 1 (a 30-second flush, illustrative): summary block S1 plus 120 blocks. S1 has 120 entries such as (file 7, block 0), (file 7, inode), (file 9, block 2), (inode map block 3). The segment's next free block is now 121.
  2. Write 2 (later): summary S2 plus 80 blocks, starting at block 121. Each write is still one sequential transfer, but the segment now has two positioning delays instead of one.
  3. Segment full: after further writes reach 256 blocks (1 MB of 4 KB blocks), the log moves on to another clean segment.
  4. Overhead: one 4 KB summary per 120 blocks is under 1%; a forced write of 3 blocks would carry a 4 KB summary for 12 KB of data, 25% extra (illustrative sizes; the paper does not give the summary's format).
Assumptions it relies on
  • A1. A block belongs to at most one file at a time (stated in Section 6: Sprite LFS "can exploit the fact that blocks can belong to at most one file at a time").
  • A2. The summary is written in the same log write as the blocks it describes (implicit in "as part of each segment" and in its use during roll-forward).
  • A3. Log writes usually contain many blocks (implicit; Table 4 confirms 0.5%).
If an assumption changes
  • A1 changes (blocks shared between files, as in snapshots or deduplication; general knowledge): one owner per block in the summary is no longer enough to find all pointers that must be updated when the block moves (inference).
  • A2 changes (summary written separately): a crash between the two writes leaves blocks no one can identify, so roll-forward could not use them (inference).
  • A3 changes (frequent tiny forced writes): summaries become a large share of the log, and each partial write pays its own positioning delay (inference).
Design notes and rejected alternatives

The summary replaces any global "which file owns this block" table: ownership is recorded once, next to the data, at the moment of writing. That is why there is no bitmap: nothing needs to be updated in place when a block dies (M10).

Connections

F2FS (11/5): keeps a segment summary area for the same purpose (general knowledge). Garbage collection: the summary plays the role of object headers that let a copying collector know what it is moving (inference).

M9 · Is this block live? The pointer check, and the version uid that skips it

TL;DR
ProblemThe cleaner must decide for each block whether it is still in use, without a bitmap.
MechanismA block is live if the file's inode (or indirect block) still points to it. As a shortcut, each file has a version number in the inode map, bumped on delete or truncate to zero; if the block's uid in the summary does not match the map's, the block is dead with no inode read.
Trade-offNo per-block free-space state to maintain, in exchange for one inode (or indirect block) read per block whose uid still matches.
Breaks whenMost dead blocks come from overwrites rather than deletes, so the uid shortcut rarely applies.
Key points
  • "Once a block's identity is known, its liveness can be determined by checking the file's inode or indirect block to see if the appropriate block pointer still refers to this block. If it does, then the block is live; if it doesn't, then the block is dead."
  • "Sprite LFS optimizes this check slightly by keeping a version number in the inode map entry for each file; the version number is incremented whenever the file is deleted or truncated to length zero. The version number combined with the inode number form an unique identifier (uid) for the contents of the file."
  • "The segment summary block records this uid for each block in the segment; if the uid of a block does not match the uid currently stored in the inode map when the segment is cleaned, the block can be discarded immediately without examining the file's inode."
How it works, step by step
  1. Read the summary of the segment being cleaned. Entry for b1: (inode 9, version 4, block 0).
  2. Compare with the inode map: entry 9 now says version 5, because file 9 was deleted (and its inode number reused). uid (9, 4) ≠ (9, 5): b1 is dead. No disk read.
  3. b2 = (7, v2, block 0): versions match, so read inode 7 (through the map). Its block 0 pointer equals b2's address: live.
  4. b3 = (7, v2, block 1): versions match; inode 7's block 1 pointer holds a newer address, because block 1 was overwritten after this segment was written: dead. The version did not change, because an overwrite is not a delete or a truncate to zero.
  5. b4 = (12, v1, block 30): block 30 is past the ten direct blocks, so the pointer is in an indirect block: read it, compare, live.
  6. Result: b2 and b4 are copied to a clean segment; the files' inode (or indirect block) is updated with the new addresses; b1 and b3 are dropped.
Assumptions it relies on
  • A1. The inode map's current versions are at hand, usually in memory (stated in 3.1 for lookups; implicit here).
  • A2. The version changes on every event that kills all of a file's blocks at once: delete, truncate to zero (stated).
  • A3. The pointer check is authoritative: a block that no pointer refers to is dead (stated).
If an assumption changes
  • A1 changes (map not cached): each uid comparison needs the map block; still cheaper than reading the inode, since one map block covers many files (inference).
  • A2 changes (version not bumped on truncation to zero): those blocks would fall through to the pointer check and still be found dead; only speed is lost. The uid is an optimization, not needed for correctness (the paper: "optimizes this check slightly").
  • A3 changes (other references exist, for example a snapshot pointing at old blocks; general knowledge): the inode check would wrongly call a referenced block dead; the cleaner would need to consult every reference (inference).
Design notes and rejected alternatives

Why the pointer check alone is correct even when an inode number is reused: a new file's pointers can only name blocks written after it was created, and those are described by newer summary entries; an old block's address in a segment not yet rewritten cannot appear in them (this guide's reasoning). A per-block version would not help further, because the pointer check already handles overwrites; the per-file version exists to make whole-file deletes cheap.

Connections

NFS (10/22): NFS file handles carry an inode generation number for the same reason, so a handle to a deleted file does not silently name the file that reused its inode number (inference connecting the two). Garbage collection: the paper notes LFS's garbage identification is "much simpler" than a language collector's because a block has at most one owner.

Questions worked through

So: from the inode I get its inode map entry and uid; if the uid matches the summary block, the block is valid and copied, otherwise it is stale and skipped? Is there a summary block per segment with about 256 (file, block) entries? And from a file, how do I find its inode?

Almost, with two corrections. First, the chain starts from the block, not the inode. The cleaner walks the segment's summary block; each entry says which file the block belonged to (the "file number", which is the inode number) and which block of that file it was, plus the version at write time. The file number is how you find the inode: it indexes the inode map, which gives the inode's current address in the log and the file's current version.

Second, a matching uid does not prove the block is live. The version only changes when the file is "deleted or truncated to length zero", so a mismatch proves the block is dead (skip it without reading the inode), but a match only says the file still exists. The block may still have been overwritten: the file has a newer copy of that block elsewhere. So on a match the cleaner reads the inode (and the indirect block, for blocks past the direct pointers) and checks "if the appropriate block pointer still refers to this block". Only then is it live. In the figure, slot 1 has a matching version but is dead.

On the counts: every segment has at least one summary block ("writing a segment summary block as part of each segment"), and more than one if the segment was filled by several partial writes, each of which gets its own. A full 1 MB segment of 4 KB blocks holds 256 blocks, so its summary describes roughly 250 of them (a few slots are the summary blocks themselves). The paper does not give the entry size; at about 12 bytes (file number, block number, version), 250 entries are about 3 KB, which fits in one 4 KB block (this guide's arithmetic).

This is how it works without per-block free-space metadata: nothing records "free" or "in use", but nothing has to. Each block's identity was recorded once when it was written, and the file system's own pointers say what is current; liveness is the comparison of the two.

Reading question: segment S contains a live inode 5 that points to data block 10. Is block 10 live? Do we also have to check generation numbers, or does a live inode guarantee it?

Yes, block 10 is live, and no generation (version) check is needed. The paper's test for a live block is whether the file still points to it: the cleaner checks "if the appropriate block pointer still refers to this block". A live inode is the current copy of inode 5, the one the inode map points to, so its pointers are by definition the file's current block addresses. If it points to block 10, block 10 is live.

The version number (what the question calls a generation number; the paper says "version number") is only a shortcut in the other direction. It changes when the file is "deleted or truncated to length zero", so a mismatch between a block's recorded uid and the inode map proves the block dead without reading the inode. It can never prove a block live, and here it is implied anyway: if the current inode still points to block 10, the file was not deleted or truncated to zero since block 10 was written, so the versions match.

The word that matters is "live" inode. If S held an old copy of inode 5 (one the inode map no longer points to), that copy would be dead and its pointer to block 10 would prove nothing; the cleaner would follow the inode map to the current inode 5 and check its pointer instead. Also note that block 10 does not have to be in S: if it is, the cleaner copies both block 10 and inode 5 out, and the rewritten inode 5 points to block 10's new address.

Where is the version number saved? Is the liveness check just comparing the inode map entry's version with the segment summary's?

The current version lives in the inode map: Sprite LFS keeps "a version number in the inode map entry for each file" (Table 1 also lists the inode map as holding the "time of last access plus version number"). The segment summary holds a second copy, frozen at write time: it "records this uid", the inode number plus the version, for each block in the segment.

Comparing the two is the first step, but only half the check. A mismatch settles it: the block is dead. A match only says the file has not been deleted or truncated to zero since the block was written; the block may still have been overwritten by a newer copy. So on a match the cleaner goes on: it uses the inode map to find the current inode, reads it (and the indirect block if needed), and checks whether the pointer for that block number still holds this block's address. Live only if it does (slot 1 versus slot 0 in the figure above).

If we look at the latest inode map, wouldn't a version match mean it is the latest data?

No. The version is per file, not per block, and it changes only when the file is "deleted or truncated to length zero". An ordinary overwrite does not change it. Trace: file 7 has version 2, and its block 0 is written into segment 40, so segment 40's summary records (file 7, block 0, v2). Later the program overwrites block 0. LFS writes the new block 0 at the head of the log, say in segment 52, and writes a new inode 7 pointing there. The inode map entry gets the new inode address, but its version stays 2. When the cleaner examines segment 40, the summary says v2 and the map says v2: a match, yet that copy of block 0 is dead. Only reading inode 7 shows that block 0 now points to segment 52, not segment 40 (slot 1 in the figure above).

So the version identifies which life of the file a block belongs to, not whether the block is the newest copy. Why not bump the version on every write? Because it is one number for the whole file: bumping it when block 0 changes would make the file's untouched blocks (block 1, block 2, ...) mismatch too, and the cleaner would discard live data. To decide liveness for each block, you need a current address for each block, and that is exactly what the inode's pointers are. The version check is a cheap filter for the common case of deleted files, and the pointer check is the real test (this guide's reasoning from the paper's description of Section 3.3).

Reading question: segment S contains a dead inode 5 that points to data block 10. Is block 10 dead?

Not necessarily; you cannot tell from the dead inode. An inode copy becomes dead whenever the file's inode is rewritten, not only when the file is deleted or truncated: any change to the file (a new block, a size change, a modification time) writes a whole new copy of inode 5 at the head of the log and moves the inode map to it, leaving the old copy dead. That old copy still points to whatever the file's blocks were at the time, and most of them are usually still current.

Trace: inode 5 (copy A, in S) points to block 10. The program appends a block 11 to the file, so LFS writes copy B of inode 5 elsewhere, pointing to both block 10 and block 11. Copy A in S is now dead, but block 10 is live, because copy B still points to it. Block 10 would be dead only if the current inode 5 no longer points to it (block 10 was overwritten, or the file was truncated or deleted).

The rule: liveness is always decided by the current inode, found through the inode map. A dead copy of an inode tells you nothing about the blocks it points to, in either direction. When the cleaner meets block 10, it uses block 10's own summary entry (file 5, its block number, version), and checks the current inode 5's pointer, never copy A.

Does "dead inode 5" mean a stale copy in the log, with a newer inode 5 later in the log? But then wouldn't the new copy point to a new data block (say 11) instead of 10?

Yes, a dead inode is a stale copy: an older version of inode 5 that the inode map no longer points to. The newer copy is later in the log.

Whether the new copy still points to 10 depends on which block changed. An inode holds one pointer per block of the file (block 0, block 1, and so on). "Block 10" is a disk address that one of those pointers holds, say the pointer for the file's block 0. When the file changes, LFS writes new copies only of the data blocks that changed, plus a whole new copy of the inode. The new inode copies every pointer from the old one, then replaces only the pointers for the rewritten blocks.

  • If the program overwrote block 0: block 0's new contents go to a new address (11), the new inode's block 0 pointer says 11, and address 10 is dead.
  • If the program changed something else (wrote block 1, appended, changed the size or modification time): block 0 was not rewritten, so the new inode's block 0 pointer is still 10, and 10 is live. The inode moved; the data block did not.

That is why a dead inode cannot settle the question. Only the current inode says which case happened.

So changes to other blocks keep block 10 alive, and appending to a file in LFS writes a new inode that copies the old one plus a pointer for the new block?

Yes, with three refinements.

  • The inode copies pointers, not data. The new inode is the old inode's fields (size, times, the list of block addresses) with the changed entries replaced and a new pointer added. The old data blocks are not read or rewritten; the new inode just records their unchanged addresses. An inode is much smaller than a block (Unix inodes of the era were 128 bytes; general knowledge, not in the paper), so rewriting it is cheap.
  • A partial last block is rewritten on append. LFS writes whole 4 KB blocks. If the file ends partway through a block, appended bytes go into that block first, so it gets a new copy at a new address and its old copy dies (inference from whole-block writes; the paper does not discuss partial blocks). Only blocks that are entirely new are pure additions.
  • More than the inode may change. If the file grows past its direct pointers, an indirect block is written (and rewritten whenever one of its pointers changes), and the inode map block holding inode 5's entry gets a new copy because the inode moved. Sprite LFS buffers changes "in the file cache" and writes them in one segment, so several changes to one file between flushes cost one new inode, not one per change.

A terminology note: a 4 KB block is not a sector. A sector is the disk's own unit (512 bytes on disks of that era); a file system block is several sectors (eight, for 4 KB) that the file system always handles together.

M10 · The cleaner's three steps, and why there is no bitmap or free list

TL;DR
ProblemTurn several partly dead segments into fewer full ones and some entirely clean ones.
MechanismRead a number of segments into memory, identify the live data (M8, M9), write it back to a smaller number of clean segments at the log head, update the owners' inodes, and mark the old segments clean.
Trade-offFree space is only ever whole clean segments, so no block-level free map is needed, at the price of reading and rewriting live data.
Breaks whenThe segments chosen are mostly live (M12), or no clean segment is left for the cleaner's own output.
Key points
  • "The process of copying live data out of a segment is called segment cleaning. In Sprite LFS it is a simple three-step process: read a number of segments into memory, identify the live data, and write the live data back to a smaller number of clean segments. After this operation is complete, the segments that were read are marked as clean, and they can be used for new data or for additional cleaning."
  • The file and position of each block are needed "in order to update the file's inode to point to the new location of the block."
  • "This approach to cleaning means that there is no free-block list or bitmap in Sprite. In addition to saving memory and disk space, the elimination of these data structures also simplifies crash recovery. If these data structures existed, additional code would be needed to log changes to the structures and restore consistency after crashes."
  • Section 5: "Sprite LFS has additional complexity for the segment cleaner, but this is compensated by the elimination of the bitmap and layout policies required by Unix FFS".
How it works, step by step
  1. Choose segments (policy, M11 to M16): here segments 17, 23 and 31, with 4, 3 and 2 live blocks of 10.
  2. Read all 30 blocks into memory (the paper assumes whole segments are read; M12).
  3. Identify the 9 live blocks with the summary and the uid and pointer checks (M9).
  4. Write the 9 live blocks into one clean segment at the log head (with age sorting, in order of age; M16), and append updated inodes for their files.
  5. Mark segments 17, 23 and 31 clean in the segment usage table (M17). Net gain: 3 segments freed − 0.9 segment used = 2.1 segments, 21 blocks, for new data.
  6. Cost per block of new data: (30 read + 9 written + 21 new written) / 21 new = 60 / 21 ≈ 2.86, the same as 2 / (1 − 0.3) (M12).
Assumptions it relies on
  • A1. Memory can hold the segments being cleaned (implicit: "read a number of segments into memory").
  • A2. Every moved block's owner can be updated (stated; it is why the summary records file and block number).
  • A3. A clean segment is available for the cleaner's output (implicit; the thresholds in M11 keep some).
  • A4. Space inside a segment is never reused until the whole segment is clean (implicit in "all live data must be copied out of a segment before the segment can be rewritten").
If an assumption changes
  • A1 changes (little memory): fewer segments per pass, so fewer chances to regroup data: "the more segments cleaned at once, the more opportunities to rearrange" (Section 3.4).
  • A2 changes (owners unknown): live blocks could not be moved; the segment could not be reclaimed (inference).
  • A3 changes (the disk has no clean segment left): the cleaner cannot write its output and the file system is stuck; real implementations reserve segments for the cleaner (general knowledge, not in the paper).
  • A4 changes (reuse holes inside segments): this is threading inside segments; it would need a block-level free map again, the structure the paper is glad to have eliminated (inference).
Design notes and rejected alternatives

FFS needs a bitmap because it chooses specific free blocks near a target (FFS guide M5, M12). LFS never chooses individual blocks: it writes at the head of a clean segment. The only free-space information it needs is per segment, kept in the segment usage table (M17). The paper counts this as a simplification of crash recovery too: there is no free map to make consistent.

Connections

FFS: replaces the free-space bitmap (FFS guide M5) and the layout policies (M10 to M12). Garbage collection: the paper's own comparison to "scavenging garbage collectors". F2FS (11/5): foreground and background cleaning of segments (general knowledge).

Questions worked through

Is there really no free-block list or bitmap? Isn't the free-space information just spread out per segment (summary blocks, the usage table) so it sits closer to the data?

The per-block free-space record is really gone. Nothing on disk or in memory says "block 12 of segment 40 is free" or "is in use". What remains is coarser, and of a different kind:

  • Per segment, a count, not a map: the segment usage table keeps each segment's live bytes and newest write time (Section 3.6). It tells the cleaner how full a segment is, not which blocks in it are live, and a segment whose count reaches zero "can be reused without cleaning".
  • Per block, an identity, not a status: the segment summary block records what each block was when it was written (file number and block number, plus the uid). It is written once and never updated, so a block that dies later looks exactly the same in its summary.

Whether a block is live is computed when needed, from the pointers that are the real source of truth: the cleaner compares the summary's uid with the inode map (a mismatch means dead), and otherwise checks whether the file's inode or indirect block still points to that address (Section 3.3). Allocation does not need a per-block structure either, because new data never goes into individual free blocks: it always goes into whole clean segments at the log head. So LFS replaces "keep a record of every free block" with "never write into partly free space, and derive liveness from the file system's own pointers".

The paper's reason, quoted: "This approach to cleaning means that there is no free-block list or bitmap in Sprite. In addition to saving memory and disk space, the elimination of these data structures also simplifies crash recovery. If these data structures existed, additional code would be needed to log changes to the structures and restore consistency after crashes." One nuance: the segment usage table is still a counter that must be right after a crash, and roll-forward does adjust it ("The roll-forward code also adjusts the utilizations in the segment usage table read from the checkpoint", Section 4.2). So it is not free of crash-consistency work, but it is one counter per segment instead of one bit per block. An overcount only makes the cleaner choose less well; an undercount that reached zero would let a segment still holding live data be reused without cleaning, which is why roll-forward must get it right (inference).

M11 · The four policy questions, and how Sprite LFS answers the first two

TL;DR
ProblemThe cleaning mechanism leaves four choices open: when to clean, how many segments at once, which segments, and how to group the live blocks written out.
MechanismWhen and how many: start below a threshold of clean segments ("a few tens"), clean "a few tens" at a time, stop above a second threshold ("50-100"). Which and how to group: the subject of M12 to M16.
Trade-offSimple thresholds that the authors found insensitive, leaving the effort for the two choices that decide performance.
Breaks whenA burst of writes uses up the clean segments faster than the cleaner can produce them (not studied in the paper).
Key points
  • The four questions, verbatim: "(1) When should the segment cleaner execute? Some possible choices are for it to run continuously in background at low priority, or only at night, or only when disk space is nearly exhausted." "(2) How many segments should it clean at a time? Segment cleaning offers an opportunity to reorganize data on disk; the more segments cleaned at once, the more opportunities to rearrange." "(3) Which segments should be cleaned? An obvious choice is the ones that are most fragmented, but this turns out not to be the best choice." "(4) How should the live blocks be grouped when they are written out?"
  • For (4) the paper names two options: "enhance the locality of future reads, for example by grouping files in the same directory together into a single output segment", or "sort the blocks by the time they were last modified and group blocks of similar age together into new segments; we call this approach age sort."
  • "In our work so far we have not methodically addressed the first two of the above policies. Sprite LFS starts cleaning segments when the number of clean segments drops below a threshold value (typically a few tens of segments). It cleans a few tens of segments at a time until the number of clean segments surpasses another threshold value (typically 50-100 clean segments)."
  • "The overall performance of Sprite LFS does not seem to be very sensitive to the exact choice of the threshold values. In contrast, the third and fourth policy decisions are critically important: in our experience they are the primary factors that determine the performance of a log-structured file system."
How it works, step by step: thresholds on a disk of about 300 segments
  1. Steady writing consumes clean segments at the log head; the count falls from, say, 80 to 30 (illustrative values inside the paper's ranges).
  2. Below the low threshold (a few tens), the cleaner starts. It reads a few tens of segments, writes their live data into fewer segments, and marks the read ones clean.
  3. It repeats until the clean count passes the high threshold (50 to 100), then stops.
  4. In between, writes proceed without cleaning. Over the long run, the cleaner must produce one clean segment for each segment of new data written (the steady-state condition of M12).
Assumptions it relies on
  • A1. Performance is insensitive to the exact thresholds (stated as an observation).
  • A2. Some clean segments are always kept, so writing rarely waits for cleaning (implicit in the low threshold).
  • A3. Which segments are chosen and how their data is grouped matter much more (stated).
If an assumption changes
  • A1 changes (bursty load): the paper itself suggests cleaning "at night or during other idle periods, so that clean segments are available during bursts of activity", but says "We do not yet have enough experience with Sprite LFS to know if this can be done" (Section 5.2).
  • A2 changes (a burst larger than the clean reserve): new writes wait while the cleaner works, so write latency suddenly includes cleaning (inference).
  • A3 changes: none; the remainder of Section 3 is the evidence for it.
Design notes and rejected alternatives

For grouping, the paper considered regrouping by directory to help future reads and chose age sorting to help future cleaning. Section 5.2 adds that the number of segments cleaned at a time, which it has "not yet carefully analyzed", "may impact the system's ability to segregate hot data from cold data".

Connections

F2FS (11/5): distinguishes background cleaning in idle time from foreground cleaning when space runs out (general knowledge). Garbage collection: when to trigger a collection is the same open question (inference).

M12 · Write cost: why it is 2/(1−u), and why it is 1.0 at u = 0

TL;DR
ProblemA single number to compare cleaning policies with each other and with FFS.
MechanismWrite cost = disk time per byte of new data, as a multiple of the ideal. With large segments it is bytes moved ÷ new bytes = 2/(1−u), where u is the live fraction of the segments cleaned; 1.0 if u = 0 (nothing to read).
Trade-offCleaning is cheap only when the segments cleaned are mostly dead: u = 0.5 costs 4, u = 0.8 costs 10.
Breaks whenThe segments cleaned are above 0.8 live (worse than FFS today) or above 0.5 (worse than the paper's improved FFS).
Key points
  • "The write cost is the average amount of time the disk is busy per byte of new data written, including all the cleaning overheads. The write cost is expressed as a multiple of the time that would be required if there were no cleaning overhead and the data could be written at its full bandwidth with no seek time or rotational latency. A write cost of 1.0 is perfect".
  • "A write cost of 10 means that only one-tenth of the disk's maximum bandwidth is actually used for writing new data; the rest of the disk time is spent in seeks, rotational latency, or cleaning."
  • "For a log-structured file system with large segments, seeks and rotational latency are negligible both for writing and for cleaning, so the write cost is the total number of bytes moved to and from the disk divided by the number of those bytes that represent new data."
  • "In the steady state, the cleaner must generate one clean segment for every segment of new data written. To do this, it reads N segments in their entirety and writes out N*u segments of live data (where u is the utilization of the segments and 0 ≤ u < 1). This creates N*(1−u) segments of contiguous free space for new data."
  • Formula (1): write cost = (total bytes read and written) / (new data written) = (read segs + write live + write new) / (new data written) = (N + N*u + N*(1−u)) / (N*(1−u)) = 2/(1−u).
  • "we made the conservative assumption that a segment must be read in its entirety to recover the live blocks; in practice it may be faster to read just the live blocks, particularly if the utilization is very low (we haven't tried this in Sprite LFS). If a segment to be cleaned has no live blocks (u = 0) then it need not be read at all and the write cost is 1.0."
  • Reference points: "Unix FFS on small-file workloads utilizes at most 5-10% of the disk bandwidth, for a write cost of 10-20". "With logging, delayed writes, and disk request sorting this can probably be improved to about 25% of the bandwidth or a write cost of 4." "the segments cleaned must have a utilization of less than .8 in order for a log-structured file system to outperform the current Unix FFS; the utilization must be less than .5 to outperform an improved Unix FFS."
  • Figure 3's caption: "Write cost for Unix FFS is not sensitive to the amount of disk space in use."
How it works, step by step: the derivation with N = 10 and u = 0.75
  1. Read 10 segments in full: 10 segments of disk time.
  2. Write back the live data: 10 × 0.75 = 7.5 segments.
  3. Free space created: 10 − 7.5 = 2.5 segments, which new data then fills: 2.5 segments written.
  4. Write cost = (10 + 7.5 + 2.5) / 2.5 = 20 / 2.5 = 8 = 2 / (1 − 0.75). The numerator is always N + Nu + N(1−u) = 2N, which is where the 2 comes from: every cleaned segment is read once, and its whole extent is written once, either as live data or as new data.
  5. u = 0: no read and no live data; the segment is simply reused: (0 + 0 + N) / N = 1.0. The formula's limit as u → 0 is 2, not 1, because for any u > 0 the whole segment is still read. The curve is discontinuous at 0.
  6. If only live blocks were read (the untried option), and ignoring the extra positioning that reading scattered blocks would cost: (Nu + Nu + N(1−u)) / N(1−u) = (1 + u)/(1 − u): 1.0 at u = 0, 3.0 at u = 0.5 instead of 4.0 (this guide's arithmetic).
  7. From write cost to bandwidth: the share of the disk's bandwidth carrying new data is 1/write cost: 1.4 → 71%, 4 → 25%, 10 → 10%.
Assumptions it relies on
  • A1. Segments are large enough that seeks and rotation are negligible for both writing and cleaning (stated).
  • A2. Steady state: one clean segment produced per segment written (stated).
  • A3. Segments are read whole (stated, "conservative").
  • A4. u is the live fraction of the segments being cleaned, not of the whole disk (stated; M13).
  • A5. Only data blocks count: the inodes and inode map blocks the cleaner must rewrite when it moves blocks are not in the formula (implicit).
If an assumption changes
  • A1 changes (small segments): each segment read or written pays a positioning delay; with 64 KB segments on the Wren IV that is about 0.54 of a segment's transfer time, so every term grows by about half and the floor of the cost rises above 1 even with no cleaning (this guide's arithmetic from M7).
  • A2 changes (cleaning in idle time): the cost moves to idle periods and the write cost seen by bursts can be near 1.0, which is why the paper calls its production numbers "if anything, over-pessimistic" (M24).
  • A3 changes (read only live blocks): (1+u)/(1−u), better at low u, but each live block may need its own positioning delay, so at high u reading the whole segment is faster (inference).
  • A4 changes: using the overall disk utilization in the formula gives the "No variance" curve of Figure 4, a pessimistic bound (M13, M15).
  • A5 changes (account for metadata): moving blocks of many small files rewrites many inodes, each of which also kills the old copy of that inode elsewhere; the true cost is somewhat above the formula (inference; Table 4 shows inodes, inode map and usage table together at 12.6% of the log on /user6, though the paper attributes much of that to checkpoints).
Design notes and rejected alternatives

Write cost puts LFS and FFS on one scale: for FFS it is mostly positioning and is "not sensitive to the amount of disk space in use"; for LFS it is mostly cleaning and depends entirely on u. The "FFS improved" line is the authors' own estimate, citing [12] (Seltzer, Chen and Ousterhout, "Disk Scheduling Revisited").

Connections

F2FS (11/5): the same cost appears as flash garbage-collection overhead; SSD write amplification follows the same 1/(1−u)-shaped law (general knowledge). FFS: FFS's performance falls sharply only when the disk is nearly full (the 10% reserve, FFS guide M8); LFS's falls steadily with u.

Questions worked through

What exactly is u, and why is the write cost 2/(1−u)?

u is a property of the segments the cleaner picks, not of the whole disk: "the utilization (the fraction of data still live) in the segments that are cleaned". If a 1 MB segment still holds 800 KB of live blocks and 200 KB of dead ones, its u is 0.8. The paper stresses the difference: u "is not the overall fraction of the disk containing live data; it is just the fraction of live blocks in segments that are cleaned". Because some segments are emptier than average and the cleaner picks those, u is normally below the disk's overall utilization; in the paper's simulation, at 75% of the disk full "the segments cleaned have an average utilization of only 55%".

"Cleaned" applies to the segment, not to the blocks. Cleaning a segment means emptying it so it can be reused. Its dead blocks are simply abandoned; its live blocks are not thrown away but copied to a new segment at the head of the log, and their inode or map pointers updated. So "a segment with u = 0.8 is cleaned" means: the cleaner empties that segment, and 80% of its blocks are live data that must be moved out first. u is the fraction of the segment that has to be copied, which is exactly why it drives the cost.

Write cost is defined as how long the disk is busy per byte of new data, relative to writing that byte with no overhead at all. With large segments the paper ignores seeks and rotation, so it becomes simple counting: total bytes moved to or from the disk, divided by the bytes of those that are new data.

The count. To make room, the cleaner (1) reads N whole segments: N segments of transfer. (2) It writes their live blocks back out, compacted: N·u segments. That frees N − N·u = N·(1−u) segments, and (3) new data fills them: N·(1−u) segments. Total moved: N + N·u + N·(1−u) = 2N. New data: N·(1−u). Ratio: 2N / (N·(1−u)) = 2/(1−u). The "2" is because every segment is touched twice, once read and once written (either as copied live data or as new data); the "1−u" is the share of that work that ends up as new data. N cancels, so the number is a property of u alone.

Plugging in. u = 0.5: 2/0.5 = 4, as costly as the paper's estimate for an improved FFS. u = 0.8: 2/0.2 = 10, as costly as FFS today. u = 0.9: 20. As u approaches 1 the cost grows without bound, because cleaning reads a whole segment to gain almost nothing. The one exception is u = 0 exactly: an empty segment "need not be read at all", so steps (1) and (2) vanish and the cost is 1.0, not the 2.0 the formula would give at u near 0. That jump is why the paper wants a bimodal distribution, with the segments cleaned nearly empty.

One caveat the paper states: reading whole segments is "the conservative assumption"; reading only the live blocks could be cheaper at low u, but Sprite LFS did not try it.

M13 · Disk utilization is not segment utilization: the bimodal goal and the space-performance trade

TL;DR
ProblemAt 75% overall disk use, formula (1) with u = 0.75 predicts a write cost of 8. Is a full disk doomed to expensive cleaning?
MechanismNo: the cleaner chooses which segments to clean, and segments differ. If most segments are nearly full and a few nearly empty (bimodal), the cleaner works on the empty ones and u of the cleaned segments stays low.
Trade-offHigher disk utilization lowers cost per usable byte but raises write cost; the bimodal distribution is how to get both.
Breaks whenSegments all drift to similar utilizations, so the cleaner has no cheap choice.
Key points
  • "It is important to note that the utilization discussed above is not the overall fraction of the disk containing live data; it is just the fraction of live blocks in segments that are cleaned. Variations in file usage will cause some segments to be less utilized than others, and the cleaner can choose the least utilized segments to clean; these will have lower utilization than the overall average for the disk."
  • "Even so, the performance of a log-structured file system can be improved by reducing the overall utilization of the disk space."
  • "Log-structured file systems provide a cost-performance tradeoff: if disk space is underutilized, higher performance can be achieved but at a high cost per usable byte; if disk capacity utilization is increased, storage costs are reduced but so is performance. Such a tradeoff between performance and space utilization is not unique to log-structured file systems. For example, Unix FFS only allows 90% of the disk space to be occupied by files."
  • "The key to achieving high performance at low cost in a log-structured file system is to force the disk into a bimodal segment distribution where most of the segments are nearly full, a few are empty or nearly empty, and the cleaner can almost always work with the empty segments."
How it works, step by step: the same 75% disk, two distributions (illustrative)
  1. Disk: 100 segments holding 75 segments' worth of live data.
  2. Even spread: every segment is 0.75 live. Whatever the cleaner picks has u = 0.75: write cost 2 / 0.25 = 8.
  3. Bimodal spread: 70 segments are completely full (70 units of live data) and the other 30 hold the remaining 5 units, average u = 5 / 30 ≈ 0.17. The cleaner picks among the 30: write cost ≈ 2 / 0.83 ≈ 2.4.
  4. Same space, a factor of 3.3 in write cost. And if some of the 30 are completely empty, those cost 1.0 each, lower still. This is what Table 2 later shows in production: more than half of the cleaned segments were empty (M24).
Assumptions it relies on
  • A1. Segment utilizations vary (stated: "Variations in file usage").
  • A2. The cleaner knows each segment's utilization without reading it (implicit here; provided by the segment usage table, M17).
  • A3. Spare space can be traded for performance (stated).
If an assumption changes
  • A1 changes (no variance): the write cost follows formula (1) with the overall utilization, the "No variance" curve of Figure 4: 4 at 50%, 8 at 75%, 20 at 90%.
  • A2 changes (no usage table): the cleaner would have to read segments to learn their u, paying the read cost even for segments it then decides not to clean (inference).
  • A3 changes (disk must be run nearly full): u of the cleaned segments approaches the overall utilization from below and the write cost climbs steeply; at 90% overall even cost-benefit is near 6 in Figure 7 (M16).
Design notes and rejected alternatives

The paper frames the goal as shaping the distribution, not as cleaning faster. The next three mechanisms (the simulator, greedy's failure, cost-benefit) are the search for a policy that produces the bimodal shape.

Connections

FFS: the paper itself compares this trade to FFS's 10% reserve (FFS guide M8). F2FS and SSDs: over-provisioning is the same trade (general knowledge).

M14 · The simulator: 4 KB files, uniform or hot-and-cold overwrites

TL;DR
ProblemCompare cleaning policies under controlled conditions, without waiting months for a real file system to age.
MechanismA file system of a fixed number of 4 KB files at constant overall utilization; each step overwrites one file chosen uniformly, or with a hot-and-cold pattern (10% of the files get 90% of the writes); a cleaner runs when clean segments run out.
Trade-offClean comparisons of policies, with a model the authors call "much harsher than reality".
Breaks whenReal files are multi-block and deleted whole, or real cold data is never written: both make reality cheaper than the simulation (M24).
Key points
  • "The simulator's model does not reflect actual file system usage patterns (its model is much harsher than reality), but it helped us to understand the effects of random access patterns and locality, both of which can be exploited to reduce the cost of cleaning."
  • "The simulator models a file system as a fixed number of 4-kbyte files, with the number chosen to produce a particular overall disk capacity utilization. At each step, the simulator overwrites one of the files with new data".
  • Uniform: "Each file has equal likelihood of being selected in each step." Hot-and-cold: "Files are divided into two groups. One group contains 10% of the files; it is called hot because its files are selected 90% of the time. The other group is called cold; it contains 90% of the files but they are selected only 10% of the time. Within groups each file is equally likely to be selected. This access pattern models a simple form of locality."
  • "In this approach the overall disk capacity utilization is constant and no read traffic is modeled. The simulator runs until all clean segments are exhausted, then simulates the actions of a cleaner until a threshold number of clean segments is available again. In each run the simulator was allowed to run until the write cost stabilized and all cold-start variance had been removed."
How it works, step by step: one step, and how hot "hot" is
  1. Pick a file by the access pattern; write its new 4 KB block at the log head. Its old block, somewhere in an older segment, becomes dead, so that segment's u drops by one block.
  2. When no clean segment is left, the cleaner runs with the policy under test until the threshold number of clean segments exists again, and the bytes it read and wrote are added up.
  3. Write cost = (new bytes + bytes the cleaner read + bytes it wrote) / new bytes, measured once it has stabilized.
  4. How hot: per file, a hot file is selected with probability 0.9 / (0.1 F) and a cold one 0.1 / (0.9 F) for F files, a ratio of 81 to 1 (this guide's arithmetic). For the "95% of accesses to 5% of data" variant, the ratio is (0.95 / 0.05) / (0.05 / 0.95) = 361.
  5. Not given: the number of files, the segment size and the exact thresholds the simulator used; the curves are reported only against utilization.
Assumptions it relies on
  • A1. Every file is one block (stated: "all the files in the simulations were just a single block long", Section 5.2).
  • A2. Writes are spread evenly within each group (stated).
  • A3. Overall utilization is constant and reads are irrelevant (stated).
  • A4. Write cost has reached a steady state (stated).
If an assumption changes
  • A1 changes (multi-block files deleted whole): deleting a file longer than a segment leaves whole empty segments, which cost nothing to clean; this is the first reason the paper gives for production doing better (M24).
  • A2 changes (many files never written): very cold segments are never cleaned at all; in the simulator "every segment eventually received modifications and thus had to be cleaned" (M24).
  • A3 changes (reads modeled): placement would matter for read cost too; for example grouping by directory might help reads but hurt cleaning (inference; question (4) in M11).
  • A4 changes (cold start): a fresh disk has a write cost near 1.0 because nothing needs cleaning; the authors removed this effect in the simulator and waited "several months" before measuring production systems (M24).
Design notes and rejected alternatives

Single-block files and smooth access within groups make every segment decay gradually, the hardest case for a cleaner. The authors chose a harsh model on purpose to understand random access and locality, and then checked the policy against production (M24).

Connections

FFS: FFS measured only aged production file systems, never a model (FFS guide M2, M13); LFS does both: a harsh model to choose a policy, then production data to check it (M24).

M15 · Greedy cleaning, and why locality made it worse

TL;DR
ProblemPick segments to clean. The obvious policy is greedy: always the least-utilized ones.
MechanismGreedy, with live blocks rewritten in their original order (uniform) or sorted by age (hot-and-cold).
Trade-offSimple and best for uniform access, but with locality cold segments sit just above the cleaning point for a long time, holding free space hostage.
Breaks whenAccess has locality: the more skewed, the worse.
Key points
  • Uniform runs: "The cleaner used a simple greedy policy where it always chose the least-utilized segments to clean. When writing out live data the cleaner did not attempt to re-organize the data: live blocks were written out in the same order that they appeared in the segments being cleaned".
  • "Even with uniform random access patterns, the variance in segment utilization allows a substantially lower write cost than would be predicted from the overall disk capacity utilization and formula (1). For example, at 75% overall disk capacity utilization, the segments cleaned have an average utilization of only 55%. At overall disk capacity utilizations under 20% the write cost drops below 2.0; this means that some of the cleaned segments have no live blocks at all and hence don't need to be read in."
  • Hot-and-cold runs used the same greedy choice "except that the live blocks were sorted by age before writing them out again ... we thought that this approach would lead to the desired bimodal distribution of segment utilizations."
  • "Figure 4 shows the surprising result that locality and 'better' grouping result in worse performance than a system with no locality! We tried varying the degree of locality (e.g. 95% of accesses to 5% of data) and found that performance got worse and worse as the locality increased."
  • The explanation: "Under the greedy policy, a segment doesn't get cleaned until it becomes the least utilized of all segments. Thus every segment's utilization eventually drops to the cleaning threshold, including the cold segments. Unfortunately, the utilization drops very slowly in cold segments, so these segments tend to linger just above the cleaning point for a very long time." "The overall result is that cold segments tend to tie up large numbers of free blocks for long periods of time."
How it works, step by step: why cold segments linger (illustrative numbers, thresholds from Figure 5)
  1. Greedy's cleaning point settles where the least-utilized segment usually sits when cleaning starts: about 0.55 for uniform and about 0.6 for hot-and-cold at 75% overall (read off Figure 5, where each distribution starts).
  2. A hot segment (age-sorted, so it holds hot blocks) loses live blocks quickly: from 1.0 to 0.6 in, say, a few thousand steps. It is cleaned as soon as it reaches the point.
  3. A cold segment loses blocks 81 times more slowly per block (M14). It drifts from 1.0 to 0.65 and stays above 0.6 for a very long time, because a hot segment always reaches 0.6 first.
  4. Meanwhile each such cold segment holds 35% free space that cannot be used. Many cold segments do this at once, so the free space the cleaner can reach is concentrated in hot segments at the cleaning point, and the cleaning point itself must be higher to keep enough clean segments: Figure 5's hot-and-cold distribution has many more segments piled just above 0.6.
  5. Result: at 75% overall, the hot-and-cold greedy write cost is higher than uniform greedy (about 5 versus about 4.4 in Figure 4, read off).
Assumptions it relies on
  • A1. The value of cleaning a segment is its free space alone (implicit in greedy).
  • A2. Age sorting will separate hot from cold data (stated as the authors' hope).
  • A3. All segments eventually decay to the cleaning point (true in the simulator by A1 and A2 of M14).
If an assumption changes
  • A1 changes (value also depends on how long space stays free): this is the insight that leads to cost-benefit (M16).
  • A2 changes (no age sorting): hot and cold blocks mix in every segment, the distribution looks more like uniform, and greedy does about as well as with no locality (inference from the comparison in Figure 4).
  • A3 changes (truly cold data never written): those segments never decay and never need cleaning, so greedy's problem shrinks; this is one reason production beat simulation (M24).
Design notes and rejected alternatives

The paper presents greedy as the baseline and then as the cautionary result. The key observation, from Figure 5, is that what matters is not how empty a segment is now but how long the space it yields will stay empty.

Connections

Garbage collection: the generational hypothesis, which the paper cites, is the observation that greedy ignores (inference). Superpages (10/13): a page reservation that fills slowly also ties up contiguous memory for a long time, and the Superpages paper preempts such reservations (inference).

M16 · Cost-benefit selection with age sort: (1−u)·age / (1+u)

TL;DR
ProblemGreedy cleans hot segments too early and cold segments too late.
MechanismScore each segment by benefit/cost = (free space generated × age of data) / cost = (1−u)·age / (1+u), age being the time since the youngest block in the segment was modified; clean the highest scores; write live blocks sorted by age.
Trade-offCold segments are cleaned at higher u (about 75%) and hot ones held until about 15%, giving a bimodal distribution and up to 50% lower write cost, at the cost of tracking ages (M17).
Breaks whenAge does not predict future stability, for example data that is old but about to be rewritten.
Key points
  • "Free space in a cold segment is more valuable than free space in a hot segment because once a cold segment has been cleaned it will take a long time before it re-accumulates the unusable free space." "it is less beneficial to clean a hot segment because the data will likely die quickly and the free space will rapidly re-accumulate; the system might as well delay the cleaning a while and let more of the blocks die in the current segment."
  • "The value of a segment's free space is based on the stability of the data in the segment. Unfortunately, the stability cannot be predicted without knowing future access patterns. Using an assumption that the older the data in a segment the longer it is likely to remain unchanged, the stability can be estimated by the age of data."
  • "The benefit has two components: the amount of free space that will be reclaimed and the amount of time the space is likely to stay free. The amount of free space is just 1−u ... We used the most recent modified time of any block in the segment (ie. the age of the youngest block) as an estimate of how long the space is likely to stay free. The benefit of cleaning is the space-time product formed by multiplying these two components. The cost of cleaning the segment is 1+u (one unit of cost to read the segment, u to write back the live data)."
  • benefit / cost = (free space generated × age of data) / cost = (1−u)·age / (1+u). "We call this policy the cost-benefit policy; it allows cold segments to be cleaned at a much higher utilization than hot segments."
  • "The cleaning policy cleans cold segments at about 75% utilization but waits until hot segments reach a utilization of about 15% before cleaning them. Since 90% of the writes are to hot files, most of the segments cleaned are hot." Figure 6's caption: "most of the segments cleaned had utilizations around 15%."
  • "Figure 7 shows that the cost-benefit policy reduces the write cost by as much as 50% over the greedy policy, and a log-structured file system out-performs the best possible Unix FFS even at relatively high disk capacity utilizations. We simulated a number of other degrees and kinds of locality and found that the cost-benefit policy gets even better as locality increases."
  • Implementation detail (Section 3.6): "the segment summary information records the age of the youngest block written to the segment. At present Sprite LFS does not keep modified times for each block in a file; it keeps a single modified time for the entire file. This estimate will be incorrect for files that are not modified in their entirety."
How it works, step by step: scoring four segments (illustrative ages, in arbitrary time units)
  1. Hot segment H1: u = 0.15, youngest block 10 old: (0.85 × 10) / 1.15 = 7.4.
  2. Hot segment H2: u = 0.40, age 5: (0.60 × 5) / 1.40 = 2.1.
  3. Cold segment C1: u = 0.75, age 200: (0.25 × 200) / 1.75 = 28.6.
  4. Cold segment C2: u = 0.90, age 400: (0.10 × 400) / 1.90 = 21.1.
  5. Order: C1, C2, H1, H2. Greedy would pick H1, H2, C1, C2. Cost-benefit picks the cold segments first even though each frees less space, because that space stays free.
  6. Break-even: a 75% cold segment beats a 15% hot one when (0.25 ac) / 1.75 > (0.85 ah) / 1.15, that is when ac > 5.2 ah (this guide's arithmetic). The policy's two humps in Figure 6 are where this balance settles in the simulation.
  7. Age sort on output: live blocks from C1 (old) and from H1 (young) are written in age order, so the oldest go into one new segment that will itself be cold and rarely need cleaning.
Assumptions it relies on
  • A1. Older data is likely to stay unchanged longer (stated: "Using an assumption that the older the data ...").
  • A2. The youngest block's age is a good summary of a segment's stability (stated as the estimate used).
  • A3. One modification time per file is close enough to per-block times (stated as a current limitation).
  • A4. Cleaning cost is 1 + u: a full read plus the live write (stated; same conservative assumption as M12).
If an assumption changes
  • A1 changes (old data is rewritten in bulk, for example a monthly job; general workload knowledge): the policy cleans "cold" segments at high u just before their data dies, copying data that would have freed itself (inference).
  • A2 changes (one hot block in a cold segment): a single recent write makes the whole segment look young, so it is treated as hot and left to decay (inference).
  • A3 changes (files appended a little at a time): the file's single modification time makes its old blocks look young, so they are sorted with hot data; the paper says the estimate "will be incorrect for files that are not modified in their entirety" and plans per-block times.
  • A4 changes (only live blocks read): cost would be about 2u instead of 1 + u, raising the scores of low-u segments; the ranking between hot and cold would shift (inference).
Design notes and rejected alternatives

Benefit is a space-time product: free space multiplied by how long it is expected to stay free. The paper tested the policy in simulation first: "The simulation experiments convinced us to implement the cost-benefit approach in Sprite LFS." Section 6 relates it to generational garbage collection: cost-benefit selection and age sorting separate "files into generations".

Connections

F2FS (11/5): separates hot, warm and cold data into different logs at write time and uses a cost-benefit victim selection for background cleaning (general knowledge). Garbage collection: generational collectors (paper's citation). ESX: the idle memory tax reclaims first from VMs whose pages sampling shows are not in use, another case of using past behavior to predict which space will stay unneeded (inference).

M17 · The segment usage table

TL;DR
ProblemThe cost-benefit policy needs every segment's u and age without reading the segments.
MechanismA table with, per segment, the number of live bytes and the most recent modified time of any block in it; counts are decremented on deletes and overwrites; the table's blocks are written to the log and located through the checkpoint region.
Trade-offCheap segment selection, and free reuse of segments whose count reaches zero, in exchange for 2.1% of the log bandwidth on /user6.
Breaks whenThe counts are wrong after a crash, until roll-forward fixes them (M19).
Key points
  • "In order to support the cost-benefit cleaning policy, Sprite LFS maintains a data structure called the segment usage table. For each segment, the table records the number of live bytes in the segment and the most recent modified time of any block in the segment."
  • "These two values are used by the segment cleaner when choosing segments to clean. The values are initially set when the segment is written, and the count of live bytes is decremented when files are deleted or blocks are overwritten. If the count falls to zero then the segment can be reused without cleaning."
  • "The blocks of the segment usage table are written to the log, and the addresses of the blocks are stored in the checkpoint regions".
  • Table 4: "Seg Usage map", 0.0% of live data, 2.1% of log bandwidth; marked as having an equivalent in Unix FFS.
How it works, step by step: segment 17 over time (illustrative)
  1. t = 1000: segment 17 is written with 1,000,000 bytes of live blocks. Entry: live = 1,000,000, modified time = 1000 (the youngest block).
  2. File F is deleted; 100 of its 4 KB blocks were in segment 17: live −= 409,600 → 590,400. The decrement happens at deletion time; the cleaner never has to look inside the segment to know this.
  3. 50 blocks of file G are overwritten (new copies go to the log head): live −= 204,800 → 385,600, u ≈ 0.37 of a 1 MB segment.
  4. Cleaner's view: u ≈ 0.37 and age = now − 1000, enough to compute the cost-benefit score with no I/O.
  5. If the remaining blocks also die, live = 0 and segment 17 is reused directly: no read, write cost 1.0 for the space it provides (M12's u = 0 case).
  6. The table is itself logged: its changed blocks are written to the log at checkpoints, and the checkpoint region records their addresses (M18).
Assumptions it relies on
  • A1. Every delete and overwrite knows which segment the old block was in (implicit: the old block's address identifies its segment).
  • A2. The table is small enough to keep in memory (implicit; 2.1% of log bandwidth, 0.0% of live data).
  • A3. After a crash, roll-forward can repair the counts (stated in Section 4.2).
If an assumption changes
  • A1 changes (the old address is not known when a block dies, for example a whole-file delete of an uncached file): the file's inode and indirect blocks must be read to find its blocks' segments (inference; the paper does not discuss this cost).
  • A2 changes (very large disks): one entry per segment is still small; a 1 GB disk with 1 MB segments has 1024 entries (this guide's arithmetic).
  • A3 changes (no roll-forward, as in the production system): the system reverts to the last checkpoint's table, which is consistent with the last checkpoint's state, so nothing is wrong, only the newer data is lost (Section 5).
Design notes and rejected alternatives

The table is the only free-space information Sprite LFS has; it replaces the bitmap at segment granularity. Keeping it in the log, rather than at a fixed place, preserves the rule that only the superblock and checkpoint regions are written in place.

Connections

FFS: the per-cylinder-group free counts and bitmaps (FFS guide M5) answer "where is free space"; this table answers "which segment is cheapest to free". F2FS (11/5): a segment information table plays the same role (general knowledge).

M18 · Checkpoints, in two regions used alternately

TL;DR
ProblemAfter a crash, find a point in the log where all structures are consistent and complete, without scanning the disk.
MechanismTwo phases: write all modified data, indirect blocks, inodes, inode map and usage table blocks to the log; then write a checkpoint region at a fixed place with the addresses of all map and usage table blocks, the time, and a pointer to the last segment written. Two regions, used in turn; the time is in the region's last block.
Trade-offFrequent checkpoints shorten recovery but add metadata writes; Sprite LFS uses 30 seconds, "probably much too short".
Breaks whenThe region's last block can reach the disk before the rest of it (the scheme assumes it cannot).
Key points
  • "In traditional Unix file systems without logs, the system cannot determine where the last changes were made, so it must scan all of the metadata structures on disk to restore consistency. The cost of these scans is already high (tens of minutes in typical configurations), and it is getting higher as storage systems expand."
  • "In a log-structured file system the locations of the last disk operations are easy to determine: they are at the end of the log." Sprite LFS "uses a two-pronged approach to recovery: checkpoints, which define consistent states of the file system, and roll-forward, which is used to recover information written since the last checkpoint."
  • "A checkpoint is a position in the log at which all of the file system structures are consistent and complete. Sprite LFS uses a two-phase process to create a checkpoint. First, it writes out all modified information to the log, including file data blocks, indirect blocks, inodes, and blocks of the inode map and segment usage table. Second, it writes a checkpoint region to a special fixed position on disk. The checkpoint region contains the addresses of all the blocks in the inode map and segment usage table, plus the current time and a pointer to the last segment written."
  • "In order to handle a crash during a checkpoint operation there are actually two checkpoint regions, and checkpoint operations alternate between them. The checkpoint time is in the last block of the checkpoint region, so if the checkpoint fails the time will not be updated. During reboot, the system reads both checkpoint regions and uses the one with the most recent time."
  • "Sprite LFS performs checkpoints at periodic intervals as well as when the file system is unmounted or the system is shut down." "Sprite LFS currently uses a checkpoint interval of thirty seconds, which is probably much too short. An alternative to periodic checkpointing is to perform checkpoints after a given amount of new data has been written to the log; this would set a limit on recovery time while reducing the checkpoint overhead when the file system is not operating at maximum throughput."
How it works, step by step
  1. t = 30 s, checkpoint into A. Phase 1: flush every dirty data block, indirect block, inode, inode map block and usage table block to the log. Phase 2: write region A: addresses of every map and usage table block, a pointer to the last segment written (say 120), and, in its last block, time 30.
  2. t = 60 s, checkpoint into B the same way: last segment 133, time 60.
  3. t = 90 s, checkpoint into A again. Phase 1 completes (segments up to 146). Phase 2 starts overwriting A, and the system crashes before A's last block is written. A's time still reads 30, and its other blocks are a mix of old and new.
  4. Reboot: read both regions, compare times: 30 versus 60. Use B. Its map and usage table addresses all point to blocks that were completely written before B was.
  5. Without roll-forward (the production configuration), everything after segment 133 is ignored: up to about 30 seconds of work lost, as the paper accepts in Section 2.1.
  6. With roll-forward, segments 134 to 146 are scanned (M19); even the metadata flushed in the failed checkpoint's phase 1 is recovered.
Assumptions it relies on
  • A1. The last block of a checkpoint region reaches the disk only after the rest of the region and after phase 1's log writes (implicit in "if the checkpoint fails the time will not be updated").
  • A2. At most one region is being written at any moment, so one is always intact (stated: "alternate between them").
  • A3. The directory operation log is consistent with directories and inodes at each checkpoint (stated in Section 4.2; enforced by blocking directory changes during checkpoints, M20).
  • A4. Losing the work since the last checkpoint is acceptable when roll-forward is off (stated, M1).
If an assumption changes
  • A1 changes (the disk or driver reorders writes; general knowledge for drives with write caches): the time block can land before the address blocks, so a crash leaves a region that looks newest but holds a mix of addresses. Recovery would load a corrupt map. The fix is to wait for the body (and phase 1) to complete before issuing the time block, or to checksum the region (inference; the paper does not discuss it).
  • A2 changes (one region, overwritten in place): a crash during the write leaves no valid checkpoint at all, the reason for having two.
  • A3 changes: a checkpoint could record a directory entry without the matching link count, which roll-forward from that checkpoint would never revisit (M20).
  • A4 changes (applications need recent writes to survive): roll-forward, or a shorter interval, or non-volatile RAM (M1, M19).
Design notes and rejected alternatives

Interval choice: "A long interval between checkpoints reduces the overhead of writing the checkpoints but increases the time needed to roll forward during recovery; a short checkpoint interval improves recovery time but increases the cost of normal operation." The paper proposes checkpointing by amount of data written instead of by time, and Section 5.4 suspects the 30-second interval is why the inode map takes 7.8% of the log (M25).

Connections

FFS: replaces fsck's full scan (FFS guide M2), which the paper says already takes "tens of minutes". Database logging: the paper's own comparison: checkpoints plus a redo log. F2FS (11/5): also keeps two checkpoint packs used alternately (general knowledge). Rethink the Sync (10/29): what may be lost between checkpoints is exactly the durability question it revisits (inference).

Questions worked through

Do disks have endurance limits too? Will LFS's fixed blocks wear out sooner, since they are rewritten every 30 seconds?

Not on a magnetic disk. Magnetic recording does not wear out with the number of writes to a sector the way flash cells do; a disk's lifetime is limited mainly by its mechanics (heads, spindle bearings, the arm actuator), and manufacturers rate it by mean time between failures and, on modern drives, by a total workload per year rather than per-sector write cycles (general knowledge, not in the paper). Rewriting the checkpoint regions every 30 seconds is about 2,880 writes a day, about a million a year, which is harmless for a sector of a hard disk.

On flash it would matter. A NAND flash block survives only a limited number of program/erase cycles, from a few thousand for dense cells to about a hundred thousand for single-level cells (general knowledge). A checkpoint block rewritten a million times a year at one physical location would wear out in days to months. That is why flash devices remap: a flash translation layer writes each update to a different physical page, so a fixed logical address does not mean a fixed physical cell. F2FS keeps LFS-style fixed checkpoint areas at fixed logical addresses and relies on that remapping (see the F2FS guide). The LFS paper predates this concern; it was written for magnetic disks.

M19 · Roll-forward: recovering what was written after the checkpoint

TL;DR
ProblemA checkpoint alone loses everything written since it.
MechanismScan the segments written after the checkpoint; for each new inode found in a summary block, point the inode map at it (which adopts its data blocks); ignore data blocks with no new inode; fix the usage table; then append the changes and write a new checkpoint.
Trade-offRecovers recent work in time proportional to what was written since the checkpoint, not to the disk size, at the cost of more recovery code (not installed in production when the paper was written).
Breaks whenA file's data reached the log but its inode did not: that data is dropped.
Key points
  • "In principle it would be safe to restart after crashes by simply reading the latest checkpoint region and discarding any data in the log after that checkpoint. This would result in instantaneous recovery but any data written since the last checkpoint would be lost. In order to recover as much information as possible, Sprite LFS scans through the log segments that were written after the last checkpoint. This operation is called roll-forward."
  • "During roll-forward Sprite LFS uses the information in segment summary blocks to recover recently-written file data. When a summary block indicates the presence of a new inode, Sprite LFS updates the inode map it read from the checkpoint, so that the inode map refers to the new copy of the inode. This automatically incorporates the file's new data blocks into the recovered file system."
  • "If data blocks are discovered for a file without a new copy of the file's inode, then the roll-forward code assumes that the new version of the file on disk is incomplete and it ignores the new data blocks."
  • "The roll-forward code also adjusts the utilizations in the segment usage table read from the checkpoint. The utilizations of the segments written since the checkpoint will be zero; they must be adjusted to reflect the live data left after roll-forward. The utilizations of older segments will also have to be adjusted to reflect file deletions and overwrites (both of these can be identified by the presence of new inodes in the log)."
  • "The recovery program appends the changed directories, inodes, inode map, and segment usage table blocks to the log and writes a new checkpoint region to include them."
  • Section 5: "roll-forward has not yet been installed in the production system. The production disks use a short checkpoint interval (30 seconds) and discard all the information after the last checkpoint when they reboot."
How it works, step by step: rolling forward from region B (segments 134 to 146, illustrative)
  1. Load region B: the inode map and usage table as of t = 60 s.
  2. Segment 134's summary lists data blocks 0 to 2 of file 7 and a new inode 7. Map entry 7 now points to the new inode, whose pointers name the new blocks: file 7's update is recovered.
  3. Usage table: segment 134 was recorded with 0 live bytes at the checkpoint; set it to the bytes of those blocks and the inode. The segment that held file 7's old inode and old blocks 0 to 2 loses those bytes.
  4. Segment 139 holds two data blocks of file 12 but no new inode 12 anywhere after the checkpoint: the blocks are ignored; file 12 stays as it was at the checkpoint.
  5. Directory operation records found on the way are applied to make directory entries and link counts agree (M20).
  6. Finish: append the changed inode map, usage table, inode and directory blocks, write a new checkpoint region. Recovery is done.
Assumptions it relies on
  • A1. Summary blocks identify new inodes as well as data blocks (stated).
  • A2. A file's new inode is written no earlier than its new data, so a new inode means a complete new version (implicit in "assumes that the new version of the file on disk is incomplete" when the inode is missing).
  • A3. The segments written after the checkpoint can be found in order, starting from "a pointer to the last segment written" (stated for the pointer; how the next segments are found is not described).
  • A4. Deletions and overwrites can be inferred from new inodes (stated).
If an assumption changes
  • A1 changes: without the summary, roll-forward could not tell inodes from data and could not use the segment (M8).
  • A2 changes (inode written before its data): roll-forward would adopt an inode pointing at blocks never written, exposing garbage; writing data before the inode in the log avoids it (inference).
  • A3 changes: if the log moved to a segment that cannot be found from the previous one, roll-forward would stop early and lose later writes. The paper's Figure 2 caption says a threaded log keeps "pointers between the blocks of the log ... so that the log can be followed during crash recovery"; the format Sprite LFS uses between segments is not given (inference).
  • A4 changes (a delete that writes no new inode): a deleted file's blocks would stay counted as live in old segments until the next cleaning pass found them dead; only cleaning efficiency suffers (inference).
Design notes and rejected alternatives

The rejected alternative is the instantaneous restart that discards everything after the checkpoint, which is what the production system did. Section 6: "Rather than redoing the operation to the separate data copy, Sprite LFS recovery insures that the indexes point at the newest copy of the data in the log." Roll-forward redoes nothing to data; it only redirects pointers.

Connections

Database logging: redo from a checkpoint (paper, Section 6). FFS: fsck must examine every inode because it cannot know which were changed; roll-forward examines only the log's tail. F2FS (11/5): roll-forward recovery for fsynced data (general knowledge).

M20 · The directory operation log

TL;DR
ProblemA crash can leave an inode's link count and the directory entry that names it out of step, since they are separate blocks that may be in different log writes.
MechanismBefore the directory block or inode, log a record per directory change: operation (create, link, rename, unlink), entry location, entry contents, new link count. Roll-forward completes operations whose blocks were not both written.
Trade-offDirectory and link-count consistency, and an easy atomic rename, for 0.1% of log bandwidth and extra synchronization with checkpoints.
Breaks whenA create's inode never reached the log: the operation cannot be completed, so the directory entry is removed.
Key points
  • "Each inode contains a count of the number of directory entries referring to that inode; when the count drops to zero the file is deleted. Unfortunately, it is possible for a crash to occur when an inode has been written to the log with a new reference count while the block containing the corresponding directory entry has not yet been written, or vice versa."
  • "To restore consistency between directories and inodes, Sprite LFS outputs a special record in the log for each directory change. The record includes an operation code (create, link, rename, or unlink), the location of the directory entry (i-number for the directory and the position within the directory), the contents of the directory entry (name and i-number), and the new reference count for the inode named in the entry."
  • "Sprite LFS guarantees that each directory operation log entry appears in the log before the corresponding directory block or inode."
  • "if a log entry appears but the inode and directory block were not both written, roll-forward updates the directory and/or inode to complete the operation." "The only operation that can't be completed is the creation of a new file for which the inode is never written; in this case the directory entry will be removed."
  • "In addition to its other functions, the directory log made it easy to provide an atomic rename operation."
  • "each checkpoint must represent a state where the directory operation log is consistent with the inode and directory blocks in the log. This required additional synchronization to prevent directory modifications while checkpoints are being written."
  • Table 4: "Dir Op Log" is 0.0% of live data and 0.1% of log bandwidth. (Table 1 calls it the "Directory change log".)
How it works, step by step: three crash cases after creat("d/f") (illustrative inode numbers)
  1. Logged first: record (create; directory d = inode 20, position 3; entry "f" → inode 80; new count 1).
  2. Case 1, inode 80 written, directory block not: roll-forward sees the record and inode 80, adds entry "f" → 80 at position 3 of d. The create completes.
  3. Case 2, directory block written, inode 80 not: the entry exists but no inode was ever written for it. This is the one case that cannot be completed: the entry is removed.
  4. Case 3, neither written, only the record: roll-forward would need the inode to complete the create; since it was never written, the create is dropped (consistent with case 2; nothing to remove) (this guide's reading).
  5. Rename: one record describes both the new entry and the removal of the old, so roll-forward can always finish it; a crash never leaves the file under both names or neither (inference from the record contents and "made it easy to provide an atomic rename").
Assumptions it relies on
  • A1. Each record precedes its directory block and inode in the log (stated guarantee).
  • A2. Checkpoints are taken only in states where the records, directories and inodes agree (stated; enforced by blocking directory changes).
  • A3. The record has everything needed to redo the change (stated contents).
If an assumption changes
  • A1 changes (record written after the blocks): a crash between them leaves a mismatched link count with no record to repair it (inference).
  • A2 changes (checkpoint during a directory change): recovery starts from a state where an entry and its count disagree, and roll-forward, which begins after the checkpoint, would not see the record that explains it (inference).
  • A3 changes (record without the new count): roll-forward could add the entry but not set the link count, so a later unlink might delete a file still named elsewhere (inference).
Design notes and rejected alternatives

FFS keeps directories and link counts consistent by ordering synchronous writes and running fsck afterward (problem 2, M3). LFS replaces that with a small redo record written ahead in the same asynchronous log. The cost the paper names is synchronization: "additional synchronization to prevent directory modifications while checkpoints are being written."

Connections

FFS: FFS added an atomic rename system call (FFS guide M18), implemented with ordered updates; LFS gets atomicity from the log. Database logging: a logical redo record ahead of the data (paper, Section 6). Journaling file systems: log metadata changes before applying them (general knowledge).

M21 · Building it: complexity, production use, and the Andrew benchmark

TL;DR
ProblemIs a log-structured file system practical: how hard to build, and does it help real users?
MechanismSprite LFS in production since fall 1990 on five partitions, about thirty users; all features implemented, roll-forward not installed in production.
Trade-offA cleaner added, a bitmap and layout policies removed: "no more complicated than Unix FFS". Users notice little because the machines are not disk-bound.
Breaks whenThe workload is CPU-bound: on the modified Andrew benchmark, only 20% faster than SunOS.
Key points
  • "We began the implementation of Sprite LFS in late 1989 and by mid-1990 it was operational as part of the Sprite network operating system. Since the fall of 1990 it has been used to manage five different disk partitions, which are used by about thirty users for day-to-day computing."
  • "All of the features described in this paper have been implemented in Sprite LFS, but roll-forward has not yet been installed in the production system."
  • "Sprite LFS turns out to be no more complicated than Unix FFS: Sprite LFS has additional complexity for the segment cleaner, but this is compensated by the elimination of the bitmap and layout policies required by Unix FFS; in addition, the checkpointing and roll-forward code in Sprite LFS is no more complicated than the fsck code that scans Unix FFS disks to restore consistency."
  • "Logging file systems like Episode or Cedar are likely to be somewhat more complicated than either Unix FFS or Sprite LFS, since they include both logging and layout code."
  • "In everyday use Sprite LFS does not feel much different to the users than the Unix FFS-like file system in Sprite. The reason is that the machines being used are not fast enough to be disk-bound with the current workloads. For example on the modified Andrew benchmark, Sprite LFS is only 20% faster that SunOS using the configuration presented in Section 5.1. Most of the speedup is attributable to the removal of the synchronous writes in Sprite LFS. Even with the synchronous writes of Unix FFS, the benchmark has a CPU utilization of over 80%, limiting the speedup possible from changes in the disk storage management."
How it works, step by step: the complexity ledger and the Andrew bound
  1. Added in LFS: the cleaner (segment selection, liveness, copying), the inode map, the segment usage table, checkpoints, roll-forward, the directory operation log.
  2. Removed relative to FFS: the free-space bitmap, the cylinder-group layout policies and rotational tables (FFS guide M5, M9 to M12), and fsck's whole-disk scan, which roll-forward replaces.
  3. Andrew bound (this guide's arithmetic): if the CPU is busy more than 80% of the time under SunOS, the disk-wait part is under 20% of the run, so even removing all of it would give at most 1 / 0.8 = 1.25×. The measured 20% speedup is close to that ceiling, which fits the paper's explanation.
Assumptions it relies on
  • A1. Complexity is comparable by components (the paper's argument is qualitative; no line counts are given).
  • A2. Users' machines are CPU-bound for their workloads (stated).
  • A3. The production system can run without roll-forward by checkpointing every 30 seconds (stated).
If an assumption changes
  • A1 changes (measured by code size): the paper offers no numbers, so the claim cannot be checked from the paper (observation).
  • A2 changes (faster CPUs, the paper's own prediction): the disk becomes the limit and LFS's advantage grows; Figure 8(b) projects 4 to 6× for small-file creates (M22).
  • A3 changes (users need writes to survive a crash): roll-forward must be installed, and Section 5.3 shows its time is short (M25).
Design notes and rejected alternatives

The paper uses the Episode and Cedar comparison to argue that a log as the only structure is simpler than a log plus a traditional layout, because the latter needs both sets of code.

Connections

FFS: the elimination list is FFS's machinery (FFS guide M5, M9 to M12). Livelock, NFS: the "CPU over 80%" bound is the same reasoning as asking where the time goes before optimizing a component (inference).

ProblemDoes the log deliver the promised order of magnitude on the workload it was designed for?
MechanismMicro-benchmark on a Sun-4/260 with a Wren IV disk: create 10,000 files of 1 KB, read them back in creation order, delete them; Sprite LFS (4 KB blocks, 1 MB segments) versus SunOS 4.0.3 (FFS-based, 8 KB blocks). No cleaning during the runs.

How it works, step by step: where the time goes in the create phase (this guide's arithmetic on read-off rates)
  1. SunOS: about 15 creates per second with the disk 85% busy: 0.85 / 15 ≈ 57 ms of disk time per file. New data: 1 KB per 57 ms ≈ 18 KB/s, about 1.3% of 1.3 MB/s, close to the paper's "about 1.2%" (the difference is read-off error).
  2. Is 57 ms five seeks? Five I/Os at the average 17.5 ms seek plus 8.3 ms rotation would be about 130 ms. 57 ms means about 11 ms per I/O: short seeks within a cylinder group plus partial rotations. FFS's locality is working; the count of I/Os is the problem (inference; rotation speed assumed).
  3. Sprite LFS: about 155 creates per second with the disk 17% busy: 0.17 / 155 ≈ 1.1 ms of disk time per file, of which 1 KB of data at 1.3 MB/s is 0.75 ms; the rest is the file's share of inodes, directory blocks, map blocks and positioning.
  4. CPU: 1 / 155 ≈ 6.5 ms of CPU per create, the limit.
  5. Headroom: the disk could absorb about 1 / 0.17 ≈ 5.9 times the rate before saturating, which is the top of the paper's "factor of 4-6". Figure 8(b) shows 4× at 4× CPU speed.
  6. Ratios: create ≈ 155 / 15 ≈ 10×; delete ≈ 167 / 22 ≈ 7.6×; read ≈ 98 / 71 ≈ 1.4×. "Almost ten times" fits create; delete is closer to 8× on the read-off values.
Assumptions it relies on
  • A1. No cleaning during the runs (stated; "best-case").
  • A2. Files are read in the order created (stated; the reason reads are faster).
  • A3. CPU speed scales and the disk does not (stated, the basis of Figure 8(b)).
  • A4. Both systems are measured on the same hardware (stated).
If an assumption changes
  • A1 changes (cleaning active): divide the LFS disk-limited rate by the write cost; with production write costs of 1.2 to 1.6 (M24) the disk-bound limit drops by that factor, but at 17% disk use the create rate here would not change until CPUs get faster (inference).
  • A2 changes (files read in another order): LFS loses its read advantage and may fall behind (M23).
  • A3 changes (faster disk access): SunOS would improve too; the projection assumes access time stays put, the premise of M1.
  • A4 changes: none; but block sizes differ (4 KB versus 8 KB), which for 1 KB files mostly affects space, not time (inference).
Design notes and rejected alternatives

The paper is explicit that these are best-case numbers and devotes Section 5.2 to the missing cleaning cost. Figure 8(b) is a projection, not a measurement.

Connections

FFS: the FFS paper never measured file creation; this is the first measurement of FFS (via SunOS) on small-file metadata-heavy work in the CS240 sequence. Livelock: "saturating the CPU" with the device idle is the opposite of the I/O-bound state, and the paper treats it as the desirable one (inference).

M23 · Large files, and logical versus temporal locality

TL;DR
ProblemDoes writing in time order hurt large files, which FFS lays out so carefully?
MechanismA 100 MB file: sequential write, sequential read, 100 MB of random writes, 100 MB of random reads, sequential reread. LFS places blocks by when they were written (temporal locality); SunOS by their position in the file (logical locality).
Trade-offLFS writes faster in every phase and reads at the same speed when write order and read order agree; it is much slower when a randomly written file is read sequentially.
Breaks whenData is read in an order different from the order it was written in.
Key points
  • "Sprite LFS has a higher write bandwidth than SunOS in all cases. It is substantially faster for random writes because it turns them into sequential writes to the log; it is also faster for sequential writes because it groups many blocks into a single large I/O, whereas SunOS performs individual disk operations for each block (a newer version of SunOS groups writes and should therefore have performance equivalent to Sprite LFS)."
  • "The read performance is similar in the two systems except for the case of reading a file sequentially after it has been written randomly; in this case the reads require seeks in Sprite LFS, so its performance is substantially lower than SunOS."
  • "A traditional file system achieves logical locality by assuming certain access patterns (sequential reading of files, a tendency to use multiple files within a directory, etc.); it then pays extra on writes, if necessary, to organize information optimally on disk for the assumed read patterns. In contrast, a log-structured file system achieves temporal locality: information that is created or modified at the same time will be grouped closely on disk."
  • "If temporal locality matches logical locality, as it does for a file that is written sequentially and then read sequentially, then a log-structured file system should have about the same performance on large files as a traditional file system. If temporal locality differs from logical locality then the systems will perform differently."
  • "Sprite LFS handles random writes more efficiently because it writes them sequentially on disk. SunOS pays more for the random writes in order to achieve logical locality, but then it handles sequential re-reads more efficiently. Random reads have about the same performance in the two systems, even though the blocks are laid out very differently. However, if the nonsequential reads occurred in the same order as the nonsequential writes then Sprite would have been much faster."
How it works, step by step: the five phases
  1. Sequential write (≈815 vs ≈585 KB/s): LFS issues large I/Os; SunOS "performs individual disk operations for each block". LFS reaches about 63% of the 1.3 MB/s bound (this guide's arithmetic; the paper does not explain the rest).
  2. Sequential read (≈505 vs ≈520): both files are laid out in file order, LFS because it was written in that order. Equal.
  3. Random write (≈820 vs ≈380): LFS appends every block at the log head, so random writes cost the same as sequential ones; SunOS seeks to each block's home. The old copies in LFS become dead, which later costs cleaning (not measured here; write cost was 1.0).
  4. Random read (≈250 vs ≈260): every read seeks in both systems. Equal.
  5. Sequential reread (≈215 vs ≈520): SunOS's blocks are still in file order; LFS's blocks of consecutive offsets are wherever the random writes put them. If each read fetched one 4 KB block, 215 KB/s is about 54 blocks per second, about 19 ms each: a positioning delay per block (this guide's arithmetic; the request size is not given).
  6. The paper's what-if: had the reads followed the order of the random writes, they would have been sequential in the log, close to LFS's sequential read rate (≈505) (inference from "Sprite would have been much faster").
Assumptions it relies on
  • A1. Read order usually matches write order for files that matter (implicit bet; true for files written once sequentially).
  • A2. Caches absorb most reads, so the bad case is rarely seen by the disk (stated premise, M1).
  • A3. No cleaning interferes (stated for these benchmarks).
If an assumption changes
  • A1 changes (databases or swap files updated in place and scanned later): the reread case becomes the common case; LFS reads such files at under half of SunOS's speed until the cleaner happens to rewrite them (inference). The cleaner could restore logical locality by regrouping live blocks in file order, the option the paper named and set aside in M11.
  • A2 changes (working sets exceed memory): every miss pays LFS's layout; the design's premise weakens (inference).
  • A3 changes: 100 MB of random overwrites leaves 100 MB of dead blocks spread over many segments; cleaning them costs write bandwidth later (M12).
Design notes and rejected alternatives

This is the paper's own statement of the trade-off between the two designs: FFS "pays extra on writes, if necessary" to keep a layout chosen for expected reads; LFS pays on reads when the expectation of reading in write order fails. The parenthetical about a newer SunOS that "groups writes" (McVoy and Kleiman, reference [16]) concedes that the sequential-write gap is not inherent to FFS's layout.

Connections

FFS: FFS's rotational layout and block placement (FFS guide M9, M11) are the "logical locality" the paper describes. F2FS (11/5): later log-structured systems separate data by temperature and type at write time, partly to keep related data together (general knowledge). Exokernel (11/10): argues that applications, which know their read patterns, should control layout (inference).

M24 · Cleaning in production: four months on five file systems

TL;DR
ProblemThe benchmarks had no cleaning; what does cleaning really cost?
MechanismStatistics from five production file systems over four months, after several months of use: segments cleaned, fraction empty, u of the non-empty ones, overall write cost.
Trade-offReal workloads, with less control; the paper calls these numbers "if anything, over-pessimistic" because cleaning was not moved to idle time.
Breaks whenA workload rewrites parts of large files in place at random, as /swap2 does: u of cleaned segments rises to 0.535.
Key points
  • The five: /user6 ("Home directories for Sprite developers. Workload consists of program development, text processing, electronic communication, and simulations."), /pcs ("Home directories and project area for research on parallel processing and VLSI circuit design."), /src/kernel ("Sources and binaries for the Sprite kernel."), /swap2 ("Sprite client workstation swap files ... virtual memory backing store for 40 diskless Sprite workstations. Files tend to be large, sparse, and accessed nonsequentially."), /tmp ("Temporary file storage area for 40 Sprite workstations.").
  • "In order to eliminate start-up effects we waited several months after putting the file systems into use before beginning the measurements. The behavior of the production file systems has been substantially better than predicted by the simulations in Section 3. Even though the overall disk capacity utilizations ranged from 11-75%, more than half of the segments cleaned were totally empty. Even the non-empty segments have utilizations far less than the average disk utilizations. The overall write costs ranged from 1.2 to 1.6, in comparison to write costs of 2.5-3 in the corresponding simulations."
  • Table 2's caption: "These write cost figures imply that the cleaning overhead limits the long-term write performance to about 70% of the maximum sequential write bandwidth."
  • Two reasons: "all the files in the simulations were just a single block long. In practice, there are a substantial number of longer files, and they tend to be written and deleted as a whole. ... In the best case where a file is much longer than a segment, deleting the file will produce one or more totally empty segments." And "there are large numbers of files that are almost never written (cold segments in reality are much colder than the cold segments in the simulations). A log-structured file system will isolate the very cold files in segments and never clean them."
  • "If the measurements of Sprite LFS in Section 5.1 were a bit over-optimistic, the measurements in this section are, if anything, over-pessimistic. In practice it may be possible to perform much of the cleaning at night or during other idle periods".

Design notes and rejected alternatives

The authors attribute the gap between simulation (2.5 to 3) and reality (1.2 to 1.6) to two features of real workloads that the simulator left out on purpose: whole-file deletion of multi-block files and truly cold data. Both make the bimodal distribution easier to reach than the simulation suggested.

Connections

FFS: FFS also measured only aged, production file systems (FFS guide M13) because the problem it fixed appeared with age; LFS's cleaning cost likewise appears only after the log wraps. F2FS (11/5): flash file systems report the same pattern of many segments emptied by whole-file deletes (general knowledge).

M25 · Recovery time and metadata overhead (Tables 3 and 4)

TL;DR
ProblemHow long does roll-forward take, and how much of the log is metadata rather than data?
MechanismCrash a special build after creating 1, 10 or 50 MB of fixed-size files, time recovery (Table 3); break down /user6's live data and log bandwidth by block type (Table 4).
Trade-offRecovery in seconds, growing with the number of files since the checkpoint; metadata is 1% of live data but about 13% of log writes, inflated by 30-second checkpoints.

Key points
  • "Although the crash recovery code has not been installed on the production system, the code works well enough to time recovery of various crash scenarios. The time to recover depends on the checkpoint interval and the rate and type of operations being performed."
  • "The different crash configurations were generated by running a program that created one, ten, or fifty megabytes of fixed-size files before the system was crashed. A special version of Sprite LFS was used that had an infinite checkpoint interval and never wrote directory changes to disk. During the recovery roll-forward, the created files had to be added to the inode map, the directory entries created, and the segment usage table updated."

If an assumption changes
  • A1 changes (directory blocks were written): roll-forward would find more already done and run faster, so Table 3 is a conservative case (inference).
  • A2 changes (longer interval with roll-forward installed): the paper expects "the log bandwidth overhead for metadata to drop substantially". The cost moves to longer recovery: by Table 3's rates, about one second per 3 MB of 10 KB files written since the checkpoint.
  • A3 changes (a workload of tiny files): inodes and map entries would be a larger share of both columns (inference).
Design notes and rejected alternatives

The paper proposes bounding recovery by checkpointing after a given amount of data rather than every 30 seconds (M18). Table 4 is the evidence that 30 seconds is too short: the inode map is rewritten into the log at 39 times its share of live data.

Connections

FFS: fsck time grows with the disk ("tens of minutes"); roll-forward time grows with the files written since the checkpoint. F2FS (11/5): the same checkpoint-interval trade-off (general knowledge). Rethink the Sync (10/29): bounding what is lost versus what is written synchronously (inference).

L · Stated limitations and future work

What the paper itself says is unfinished or weak
  • Sequential reads after random writes are "substantially lower than SunOS" (Figure 9); the only exception to "at least as fast as Unix in all cases".
  • Crash window: buffered writes are lost in a crash; "for applications that require better crash recovery, non-volatile RAM may be used for the write buffer."
  • Cleaning at high utilization: write cost grows as 2/(1−u); "if disk capacity utilization is increased, storage costs are reduced but so is performance." Even cost-benefit is ≈ 5.8 at 90% overall in simulation (Figure 7).
  • Untuned policies: "we have not methodically addressed the first two of the above policies" (when to clean, how many segments); "we have not yet carefully analyzed the policy issue of how many segments to clean at a time"; cleaning "at night or during other idle periods" is untested: "We do not yet have enough experience with Sprite LFS to know if this can be done."
  • Age estimate: one modified time per file, "incorrect for files that are not modified in their entirety"; per-block times are planned.
  • Whole-segment reads: reading only live blocks "may be faster ... (we haven't tried this in Sprite LFS)".
  • Checkpoint interval: 30 seconds is "probably much too short"; checkpointing by amount of data written is proposed; metadata log overhead is expected to "drop substantially" with roll-forward installed and a longer interval.
  • Roll-forward not in production: "roll-forward has not yet been installed in the production system".
  • Simulation realism: the simulator is "much harsher than reality"; the micro-benchmarks "are synthetic so they do not represent realistic workloads".
What the evaluation does not cover (this guide's list)
  • No benchmark with the cleaner running: Section 5.1's write cost was 1.0, and Section 5.2 reports only long-run averages, not the effect of cleaning on the latency of foreground writes.
  • No measurement at very high disk utilization in production (the highest is 75%).
  • No workload with frequent forced writes (fsync, NFS service), where log writes become small partial segments.
  • No measurement of read performance when the inode map does not fit in memory, or of how often reads miss the cache in the production systems.
  • "FFS improved" is an estimate, not a measured system; the newer SunOS that "groups writes" is mentioned but not measured.
  • Figure 8(b) is a projection; the complexity claim has no code-size numbers; only one disk model is measured; 512 KB and 1 MB segments are not compared.
  • Recovery times come from a special build with directory writes disabled, not from the production system.

Worked examples

Eight calculations from the paper's own numbers. Read-off values from plots are marked ≈; hardware details not in the paper are labeled.

① Deriving 2/(1−u), and the jump at u = 0

Paper, Section 3.4: the cleaner "reads N segments in their entirety and writes out N*u segments of live data"; "If a segment to be cleaned has no live blocks (u = 0) then it need not be read at all and the write cost is 1.0."

  1. N = 10, u = 0.75: read 10, write 7.5 live, which frees 2.5 segments for 2.5 of new data. Bytes moved = 10 + 7.5 + 2.5 = 20; new = 2.5; write cost = 8 = 2 / 0.25.
  2. General: N + Nu + N(1−u) = 2N, divided by N(1−u): 2/(1−u). u = 0.5 → 4; u = 0.8 → 10; u = 0.9 → 20.
  3. u = 0.01: read 10 whole segments to recover 0.1 of live data: (10 + 0.1 + 9.9) / 9.9 ≈ 2.02.
  4. u = 0: nothing to read or copy: (0 + 0 + 10) / 10 = 1.0. The curve jumps from about 2 to 1.
  5. Reading only live blocks (untried in the paper; ignoring the extra positioning): (u + u + (1−u)) / (1−u) = (1+u)/(1−u): 1.02 at u = 0.01, 3.0 at u = 0.5 (this guide's arithmetic).
💡
The 2 is "read once, write the whole extent once": every cleaned segment is read in full, and its space is written in full, partly with old live data and partly with new data.

② Rebuilding Table 2's write costs from its own columns

Table 2 gives, per file system, the fraction e of cleaned segments that were empty and the average u of the non-empty ones.

  1. Per segment cleaned: new space = e + (1−e)(1−u); reads = (1−e) whole segments; live writes = (1−e)u.
  2. Write cost = 1 + (1−e)(1+u) / (e + (1−e)(1−u)).
  3. /user6 (e = .69, u = .133): 1 + 0.351 / 0.959 = 1.37 (paper 1.4). /pcs (.52, .137): 1 + 0.546 / 0.934 = 1.58 (1.6). /src/kernel (.83, .122): 1 + 0.191 / 0.979 = 1.19 (1.2). /tmp (.78, .130): 1 + 0.249 / 0.971 = 1.26 (1.3). /swap2 (.66, .535): 1 + 0.522 / 0.818 = 1.64 (1.6).
  4. Bandwidth for new data: 1/1.64 = 61% to 1/1.19 = 84%; the caption's "about 70%" is the middle of that range.
  5. Without the empty segments (e = 0), /user6 would be 2 / (1 − 0.133) = 2.31: the empty segments cut the cost by more than a third.
🍯
Every row reproduces, so the table's write cost counts exactly the cleaner's reads and copies plus new data, with whole-segment reads of non-empty segments, the model of formula (1).

③ How big must a segment be on the Wren IV?

Paper: 1.3 MB/s, 17.5 ms average seek. Assumed: 3600 rpm, 8.3 ms average rotational wait (general knowledge). Efficiency = transfer / (transfer + positioning).

  1. Positioning: 17.5 + 8.3 ≈ 25.8 ms per segment.
  2. 4 KB: 3.0 ms transfer → 3.0 / 28.8 ≈ 10%. 64 KB: 48 ms → 48 / 74 ≈ 65%.
  3. 512 KB: 385 ms → 94%. 1 MB: 769 ms → 97%.
  4. Break-even (transfer = positioning): 1.3 MB/s × 25.8 ms ≈ 34 KB. For 97%, a segment must be about 32 times that.
  5. A future disk with ten times the bandwidth and the same access time would need ten times larger segments for the same efficiency (the paper's own trend, M1).
💡
"Much greater than the cost of a seek" is a ratio, so the right segment size grows with bandwidth × access time, and access time is the part the paper expects not to improve.

④ Where the disk time goes in Figure 8's create phase

Paper: SunOS disk 85% busy, "about 1.2%" of bandwidth for new data; LFS disk 17% busy with the CPU saturated. Rates read off Figure 8: LFS ≈ 155, SunOS ≈ 15 creates/s.

  1. SunOS: 0.85 / 15 ≈ 57 ms of disk time per 1 KB file → ≈ 18 KB/s of new data ≈ 1.3% of 1.3 MB/s.
  2. Per I/O: five I/Os in 57 ms ≈ 11 ms each, much less than 17.5 + 8.3 = 25.8 ms: short seeks inside a cylinder group (inference).
  3. LFS: 0.17 / 155 ≈ 1.1 ms of disk time per file; 1 KB of data alone is 0.75 ms.
  4. CPU per create in LFS: 1 / 155 ≈ 6.5 ms.
  5. Headroom: the LFS disk can take 1 / 0.17 ≈ 5.9× more before saturating, the top of the paper's "factor of 4-6".
🍯
SunOS's problem is the count of I/Os, not their distance; LFS removes the count and leaves the CPU as the limit.

⑤ Cost-benefit versus greedy on four segments

Score = (1−u)·age / (1+u). Illustrative ages in arbitrary units.

  1. H1 u = 0.15, age 10 → 0.85 × 10 / 1.15 = 7.4. H2 u = 0.40, age 5 → 0.6 × 5 / 1.4 = 2.1.
  2. C1 u = 0.75, age 200 → 0.25 × 200 / 1.75 = 28.6. C2 u = 0.90, age 400 → 0.1 × 400 / 1.9 = 21.1.
  3. Greedy order: H1, H2, C1, C2. Cost-benefit order: C1, C2, H1, H2.
  4. Break-even age ratio for a 0.75 cold segment against a 0.15 hot one: (0.85/1.15) / (0.25/1.75) = 0.739 / 0.143 ≈ 5.2.
  5. Cost per unit of space freed: C1 costs 1.75 / 0.25 = 7 units per unit freed; H1 costs 1.15 / 0.85 = 1.35. Cost-benefit accepts the 5× higher price because C1's space stays free about 20× longer (age 200 versus 10).
💡
Benefit is a space-time product: the policy buys free space by the hour, not by the byte.

⑥ Why cost-benefit at 75% is not 2/(1−0.15)

Figure 6: hot segments cleaned at about 15%, cold at about 75%. Figure 7: cost-benefit write cost ≈ 3.2 at 75% overall (read off).

  1. All hot: 2 / 0.85 ≈ 2.35. All cold: 2 / 0.25 = 8.
  2. A mix with fraction x of cleaned segments cold: write cost = 1 + (x·1.75 + (1−x)·1.15) / (x·0.25 + (1−x)·0.85).
  3. Solve for 3.2: 1.15 + 0.6x = 2.2 × (0.85 − 0.6x) → 1.92x = 0.72 → x ≈ 0.375.
  4. So about 3 in 8 cleaned segments are cold (most are hot, as the paper says), but they supply only 0.375 × 0.25 / (0.375 × 0.25 + 0.625 × 0.85) ≈ 15% of the reclaimed space while causing about half of the cleaning traffic.
🍯
A two-point model on read-off values (this guide's arithmetic): treat x as approximate. The point stands: cold cleaning is expensive per byte, and it pays only through how long its space stays free.

⑦ Recovery time: checking "one second per 70 seconds"

Table 3 and Section 5.3: maximum observed write rate 150 MB/hour.

  1. Data per 70 s: 150 MB/hour × 70 / 3600 ≈ 2.9 MB.
  2. Recovery rate needed: 2.9 MB per second.
  3. Table 3 rates: 10 KB files: 10 MB in 3 s (3.3 MB/s), 50 MB in 17 s (2.9 MB/s): matches. 1 KB files: 10 MB in 21 s (0.48 MB/s): 2.9 MB would take about 6 s. 100 KB files: 50 MB in 8 s (6.3 MB/s): about 0.5 s.
  4. So the claim holds for files of about 10 KB, near Table 2's average file sizes (10.5 to 68.1 KB).
  5. The one-hour claim: /user6 writes 3.2 MB/hour, about 140 files of 23.5 KB; at a few hundred files per second, under a second.
💡
Recovery cost is per file (map entry, directory entry, usage table), so a checkpoint policy based on bytes written, as the paper proposes, should also count files.

⑧ Figure 1 in milliseconds

Problem 1 · easy
The cleaner works on segments with u = 0, 0.2, 0.5 and 0.8. What is the write cost in each case, and what fraction of the disk's bandwidth carries new data?

Which Sprite LFS structures are written at fixed places on disk, and what does the checkpoint region contain?
Show answer
Only the superblock and the two checkpoint regions (Table 1). A checkpoint region holds "the addresses of all the blocks in the inode map and segment usage table, plus the current time and a pointer to the last segment written". Problem 3 · easy
FFS needs a free-space bitmap. Why does Sprite LFS have neither a bitmap nor a free list, and what does it keep instead?
Show answer
LFS never allocates individual free blocks: it writes at the head of a clean segment, and a segment is reused only after all its live data has been copied out. So the only free-space information needed is per segment: live bytes and newest modification time, in the segment usage table. The paper adds that removing the bitmap "simplifies crash recovery", since there is no free map to keep consistent.Misconception: that the cleaner needs a bitmap to find dead blocks. It uses the summary block plus the uid and pointer checks.
Problem 4 · medium
A segment being cleaned holds block 2 of file 30 (uid 30.v3), block 0 of file 41 (41.v1), and block 7 of file 55 (55.v2). Show answer

Region A holds a checkpoint with time 200, region B one with time 230. At time 260 the system starts a checkpoint into A and crashes while writing it. What does reboot use, and what is lost in the production configuration of 1991?

Connecting outward

What LFS teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make. Facts about later devices are general knowledge.

Write cost is write amplification, and its law is 1/(1−u)

Any store that writes out of place and reclaims space by copying pays the same price: to free space in a region that is u live, it must move u of live data per 1−u of space gained. LFS measured it as write cost 2/(1−u) on a disk; flash translation layers call it write amplification and see the same steep rise as the victim blocks fill. The levers are also the same: keep spare space (the paper's cost-performance trade, an SSD's over-provisioning), and make victims nearly empty by separating data that will die soon from data that will not.

Indirection buys the freedom to move data, and the map has its own write traffic

The inode map is what lets every block land wherever the log head is. It costs almost nothing to read when cached, but every move rewrites a map entry, and on /user6 the map was 7.8% of everything written while holding 0.2% of the live data. Page tables, flash mapping tables and remapping layers in memory controllers face the same split: lookups are cheap if cached, updates are a steady tax proportional to how often things move. Batching map updates (the paper's longer checkpoint interval) is the main remedy.

Age is a usable predictor of stability

Cost-benefit cleaning rests on one assumption: "the older the data in a segment the longer it is likely to remain unchanged." It worked better in production than in simulation because real cold data is colder than the model's. For any tiered or asymmetric memory, where writes are expensive or wear the medium, the same signal decides placement: data that has not been written for a long time is the best candidate for the tier that dislikes writes, and the worst candidate for repeated copying. The paper also shows the limit: one timestamp per file misjudges files that are only partly rewritten.

Where data sits encodes a bet about the order it will be read in

FFS places data by expected reading order and pays on writes; LFS places it by writing order and pays on reads that do not follow it (215 versus 520 KB/s for a sequential reread of a randomly written file). Neither is free. Any placement policy, for disk blocks, pages in a memory tier, or entries in a write-optimized index, should be judged by how often its implied order matches the real access order, and the cleaner or migration engine is the one place to repair the mismatch later.

Design for the component that will not speed up

The paper's argument starts from trends: CPUs and memory grow, access time does not. It then moves all costs onto transfers and the CPU, which do scale, and measures success as disk idle while the CPU is saturated (17% busy versus 85%). The same reasoning applies whenever one device characteristic (latency, write endurance, write energy) is fixed by physics while bandwidth or capacity keeps growing: batch to amortize the fixed cost, and keep the fixed-cost operations off the critical path.

Recovery should cost what was recently written, not what is stored

fsck scans all metadata ("tens of minutes", and growing with disks); LFS reads a checkpoint and the log written after it (about a second for an hour of typical traffic). Checkpoint plus log is the general pattern: bound the work after a failure by the amount of change since a known-good state, and choose the checkpoint frequency by the recovery time you can tolerate, since Table 3 shows the work is per file, not per byte.

C1 · Can Table 2's write costs be rebuilt from its own columns?

Table 2 gives, for each production file system, the fraction of cleaned segments that were empty and the average utilization of the non-empty ones, plus an overall write cost. Formula (1) is 2/(1−u), but plugging in u = .133 for /user6 gives 2.31, not the table's 1.4. Is the table consistent with the paper's own cost model, and what does that tell us about how the write cost was counted?

AnswerWork it out first, then open▾

Yes, once the empty segments are treated as the paper's u = 0 case. Per segment cleaned, a fraction e is empty (not read, all of it freed) and 1 − e is read whole and has u written back. New space = e + (1−e)(1−u); extra traffic = (1−e)(1+u); write cost = 1 + (1−e)(1+u) / (e + (1−e)(1−u)).

/user6: 1 + 0.351/0.959 = 1.37 (table 1.4); /pcs 1.58 (1.6); /src/kernel 1.19 (1.2); /tmp 1.26 (1.3); /swap2 1.64 (1.6). All five match. So the reported write cost counts exactly whole-segment reads of non-empty segments, live data written back, and new data: the model of Section 3.4 with no metadata term. It also shows where the low cost comes from: with e = 0, /user6 would be 2.31; the empty segments (69% of those cleaned) remove more than a third of the cost.

Where the answer comes from: Arithmetic on Table 2's columns using the u = 0 rule and formula (1) from Section 3.4.

C2 · Is the version number needed for correctness, or only for speed?

The cleaner compares each block's uid (inode number plus version) with the inode map and drops the block if they differ; the version is bumped only on delete or truncate to zero. If a file is deleted, its inode number reused, and the new file written, could the pointer check alone ever wrongly keep an old block alive? And what happens to blocks of a file truncated from 20 blocks to 5, where the version does not change?

AnswerWork it out first, then open▾

The version is only an optimization; the paper says it "optimizes this check slightly". The pointer check alone is correct: a block is live only if the current inode (or indirect block) points to its exact address. A new file reusing the inode number has pointers only to blocks written after it was created, at the log head; an address inside a segment that has not been rewritten since cannot appear in them. So an old block can never be mistaken for the new file's.

Truncation to 5 blocks leaves the version unchanged, so blocks 5 to 19 fall through to the pointer check: the cleaner reads the inode (and the indirect block for blocks past the tenth), finds no pointer to them, and drops them. Same for overwritten blocks. What the version saves is reading an inode for every block of a deleted or zero-truncated file: one in-memory comparison per block instead.

Where the answer comes from: Section 3.3's liveness rule and version-number definition; the argument about reused inode numbers is this guide's reasoning from the append-only rule.

C3 · How much older must a cold segment be before cost-benefit cleans it ahead of a hot one?

Figure 6 says cost-benefit cleans cold segments at about 75% utilization but waits for hot ones to reach about 15%. Greedy would never pick a 75% segment while a 15% one exists. Using the formula (1−u)·age/(1+u), at what age ratio does a 75%-full segment start to beat a 15%-full one, and what is the cost per unit of freed space for each?

AnswerWork it out first, then open▾

Equal scores when 0.25·a_c/1.75 = 0.85·a_h/1.15, so a_c/a_h = (0.85/1.15)/(0.25/1.75) = 0.739/0.143 ≈ 5.2. A cold segment whose youngest block is more than about five times older than the hot segment's is cleaned first.

Price per unit of space freed: cold 1.75/0.25 = 7 units of disk work, hot 1.15/0.85 = 1.35. Cost-benefit pays five times more per byte for cold space because it expects that space to stay free much longer; greedy only looks at the price. The two humps of Figure 6 are where the simulation settles this balance.

Where the answer comes from: Arithmetic on Section 3.5's cost-benefit formula with Figure 6's two utilizations.

C4 · What if the disk writes the checkpoint region's blocks out of order?

The checkpoint region is several blocks, and "the checkpoint time is in the last block of the checkpoint region, so if the checkpoint fails the time will not be updated." Many later disks have write caches and reorder writes. If the time block reaches the platter before the address blocks and the system crashes, what does reboot do, and what is needed to make the scheme safe?

AnswerWork it out first, then open▾

Reboot reads both regions and takes the one with the newer time. The half-written region now shows the newest time, so it is chosen, but its address blocks are a mix of the new checkpoint's and the previous one's (two checkpoints ago, since regions alternate). The inode map and usage table loaded from it can point at blocks that were since overwritten or cleaned: a corrupted file system, with no error detected.

The scheme assumes ordered completion. To keep it safe on a reordering disk, the time block must be issued only after the rest of the region (and phase 1's log writes) are known to be on disk, using a cache flush or write barrier, or the region must carry a checksum so a torn region is rejected and the other one used (general knowledge of disk write caches; the paper does not discuss reordering).

Where the answer comes from: Section 4.1's checkpoint rules; the reordering behavior of write-cached disks and the fixes are general knowledge.

C5 · SunOS kept the disk 85% busy at about 15 creates per second. Does that fit "five I/Os, each preceded by a seek"?

Section 2.3 says a create in FFS takes at least five separate disk I/Os each preceded by a seek, and the Wren IV's average seek is 17.5 ms. Figure 8 shows SunOS creating about 15 files per second with the disk 85% busy. Do these numbers agree, and what do they say about where FFS's time goes?

AnswerWork it out first, then open▾

Disk time per create = 0.85 / 15 ≈ 57 ms. Five I/Os at an average seek plus half a rotation (17.5 + 8.3 ms at 3600 rpm, an assumed speed) would be about 130 ms, more than twice that. So the five I/Os average about 11 ms each: short seeks within a cylinder group plus partial rotations. FFS's placement policies are doing their job.

The numbers agree with the paper's diagnosis, read precisely: the cost is the number of separate I/Os, not their distance. New data is 1 KB per 57 ms ≈ 18 KB/s, about 1.3% of 1.3 MB/s, matching the paper's "about 1.2%".

Where the answer comes from: Figure 8 read-offs (≈ 15 files/s), the 85% figure from Section 5.1, the Wren IV seek time; 3600 rpm is an assumption (general knowledge).

C6 · Does "one second of recovery per 70 seconds of checkpoint interval" follow from Table 3?

Section 5.3 says that at the maximum observed write rate of 150 MB/hour, maximum recovery time grows by one second for every 70 seconds of checkpoint interval. Table 3 gives recovery times for 1, 10 and 50 MB of 1 KB, 10 KB and 100 KB files. Is the claim consistent with Table 3, and for which file size?

AnswerWork it out first, then open▾

70 s at 150 MB/hour is 150 × 70 / 3600 ≈ 2.9 MB, so the claim needs recovery at about 2.9 MB/s. Table 3: 10 KB files recover 10 MB in 3 s and 50 MB in 17 s (3.3 and 2.9 MB/s): a match. 1 KB files recover at 0.48 MB/s (10 MB in 21 s), so 2.9 MB would take about 6 s; 100 KB files at 6.3 MB/s, about 0.5 s.

So the claim is right for files of about 10 KB, close to Table 2's average file sizes, and off by about 6× for 1 KB files. Since recovery is "dominated by the number of files", a bound on recovery time needs a bound on files written, not just bytes.

Where the answer comes from: Arithmetic on Table 3 and the 150 MB/hour figure in Section 5.3.

C7 · Cost-benefit cleans mostly at 15%: why is Figure 7's write cost at 75% not 2/(1−0.15)?

Figure 6's caption says "most of the segments cleaned had utilizations around 15%", which by formula (1) is a write cost of 2.35. But Figure 7's cost-benefit curve at 75% disk utilization reads about 3.2. Where does the extra come from, and roughly what share of cleaned segments must be cold?

AnswerWork it out first, then open▾

From the cold segments cleaned at about 75%, each costing 2/0.25 = 8 on its own. With a fraction x of cleaned segments cold, write cost = 1 + (1.75x + 1.15(1−x)) / (0.25x + 0.85(1−x)). Setting it to 3.2 gives 1.92x = 0.72, x ≈ 0.375: about 3 in 8 cleaned segments are cold, so "most" (5 in 8) are hot, as the paper says.

Those cold segments yield only about 15% of the reclaimed space (0.375 × 0.25 out of 0.625) but about half the cleaning traffic. The write cost is set by the mix, not by the mode of the distribution. Treat x as approximate: it rests on a two-point model and a read-off of 3.2.

Where the answer comes from: Figures 6 and 7 (read-off value ≈ 3.2) and formula (1); the two-point mixture is this guide's arithmetic.

Glossary, results, and provenance

Every term in one place, then where the numbers came from, what this guide found inconsistent in the paper, and corrections to the 10/27 companion outline.

Core terms
Log-structured file systemA file system whose only on-disk data structure is a log: every new or modified block, including all metadata, is appended at the log head, and nothing is updated in place except a superblock and checkpoint regions.
Log headThe position in the current segment where the next log write will go.
SegmentA fixed-size extent of the disk (512 KB or 1 MB in Sprite LFS), written sequentially from start to end and reused only after all its live data has been copied out; the unit of writing and cleaning.
Partial-segment writeOne log write that fills only part of a segment, made when the cache has too few dirty blocks to fill one; it carries its own summary block.
InodeThe per-file record of attributes and of the addresses of the first ten blocks and of indirect blocks; same format as FFS, but stored in the log.
Inode mapAn array indexed by inode number whose entries hold each inode's current disk address, a version number and the last access time; divided into blocks that are written to the log and cached in memory.
Checkpoint regionOne of two fixed-location records holding the addresses of all inode map and segment usage table blocks, a pointer to the last segment written, and (in its last block) the time of the checkpoint.
CheckpointA position in the log at which all file system structures are consistent and complete, created by flushing all modified metadata to the log and then writing a checkpoint region.
Segment summary blockA block in each log write that names, for every block in that write, its file number, block number and uid, and identifies inodes and other metadata blocks.
Version number, uidA per-file counter kept in the inode map and incremented on delete or truncate to zero; with the inode number it forms the uid, which identifies one incarnation of a file's contents.
Live blockA block that a current inode or indirect block still points to; any other block in the log is dead.
Segment cleanerThe process that reads segments, keeps their live blocks, writes those compacted to clean segments at the log head, updates their owners' inodes, and marks the read segments clean.
Threading / copyingThe two ways to reuse fragmented free space: threading writes the log into the holes between live data; copying moves live data out to create large empty extents. Sprite LFS threads between segments and copies within them.
Utilization uThe fraction of a segment's bytes that are live; distinct from overall disk capacity utilization, the fraction of the whole disk holding live data.
Write costDisk busy time per byte of new data, including cleaning, as a multiple of the time at full bandwidth with no positioning; 2/(1−u) for cleaned segments of utilization u, 1.0 for empty ones.
Bimodal segment distributionA state in which most segments are nearly full and a few are nearly empty, so the cleaner can almost always work on nearly empty ones.
Greedy policyA segment selection rule that always cleans the least-utilized segments.
Cost-benefit policyA segment selection rule that cleans the segments with the highest (1−u)·age/(1+u), where age is the time since the youngest block in the segment was modified.
Age sortOrdering the live blocks written out by the cleaner by their last modification time, so blocks of similar age share segments.
Segment usage tableA logged table with one entry per segment: live bytes and most recent modification time of any block in it; the cleaner's input, and the only free-space record.
Roll-forwardThe recovery pass over the segments written after the last checkpoint that adopts new inodes into the inode map, ignores data without a new inode, fixes usage counts and completes directory operations.
Directory operation logLog records, one per directory change, giving the operation, the entry's location and contents, and the inode's new link count, each written before the directory block or inode it describes.
Temporal locality (on disk)A placement in which "information that is created or modified at the same time will be grouped closely on disk", as LFS produces.
Logical locality (on disk)A placement chosen for an assumed read pattern (file blocks in order, files of a directory together), as FFS produces, paying "extra on writes, if necessary".
Supporting terms
Unix FFSThe Berkeley Fast File System of the previous paper: cylinder groups with fixed inode areas, free-space bitmaps and layout policies; the paper's example of a current file system.
SunOS 4.0.3Sun's Unix release used as the comparison system; its file system "is based on Unix FFS" and used 8 KB blocks in the benchmarks.
SpriteBerkeley's network operating system for workstations, with large client and server file caches and many diskless clients; Sprite LFS was built inside it.
File cacheKernel memory holding recently used file blocks; it absorbs reads and, in LFS, buffers dirty blocks until a log write.
Synchronous writeA write for which the caller waits until the disk has completed it.
Asynchronous (delayed) writeA write copied into the cache, with the disk write done later in the background, possibly together with others.
Metadata"the data structures used to locate the attributes and blocks of the file": inodes, indirect blocks, directories, maps and tables, as opposed to file contents.
Indirect blockA block of block addresses, used for files larger than the ten blocks addressable from the inode.
SuperblockThe fixed-location record of static configuration, such as the number of segments and the segment size.
Seek, rotational latency, transferThe three parts of a disk access: moving the arm, waiting for the sector to come around, and moving the bytes.
Wren IVThe SCSI disk in the benchmarks: 1.3 MB/s maximum transfer bandwidth and 17.5 ms average seek time.
Sun-4/260The benchmark workstation: 8.7 integer SPECmarks, 32 MB of memory.
fsckThe Unix file system checker, which scans all metadata on disk after a crash to restore consistency.
Write-ahead logging, redo logDatabase techniques in which changes are logged before being applied to a separate data area, and replayed from a checkpoint after a crash.
Group commitA database technique that writes the log records of many transactions in one disk write.
Generational garbage collectionA memory reclamation scheme that collects recently allocated objects more often than old ones, on the observation that most objects die young.
Non-volatile RAMMemory that keeps its contents without power; the paper's suggested write buffer for applications that cannot lose recent writes.
Modified Andrew benchmarkA file-system-intensive benchmark (copying, scanning and compiling a source tree), cited from Ousterhout [11]; LFS was 20% faster than SunOS on it.
Write amplification(general knowledge) The ratio of bytes a device or file system physically writes to bytes the user wrote; LFS's write cost counts reads as well.

Inconsistencies found in the paper

(1) FFS's small-file write efficiency is given three ways: "less than 5%" (Section 2.3), "at most 5-10% ... write cost of 10-20" (3.4), and "5-10%" (abstract); Figures 3, 4 and 7 draw "FFS today" at 10, the most favorable end, while Figure 8 measured about 1.2% (a write cost near 80). (2) "almost ten times as fast as SunOS for the create and delete phases": create is about 10× on the read-off bars, delete about 7.6×. (3) Table 1 lists the segment summary under Section 3.2, but it is described in 3.3; the same structure is the "directory change log" (Table 1), "directory operation log" (4.2) and "Dir Op Log" (Table 4). (4) Table 2's caption calls the column "the average daily write traffic rate", but its unit is MB/hour. (5) Table 2's traffic and segment counts do not balance under a simple steady-state reading: /swap2 at 13.3 MB/hour for about 2,900 hours is roughly 39 GB written on a 309 MB disk, yet only 4,701 segments (at most about 4.7 GB at 1 MB each) were cleaned; the paper does not say whether segments reused without cleaning (live count zero, Section 3.6) or writes absorbed in the cache explain it (this guide's arithmetic; the segment size per file system is not given). (6) Table 4: "More than 99% of the live data" is data plus indirect blocks, but the printed values sum to exactly 99.0%. (7) The bandwidth claim is "70%" (abstract, Table 2 caption) and "65-75%" (introduction); the measured write costs 1.2 to 1.6 imply 62% to 83%. (8) "Unix FFS only allows 90% of the disk space to be occupied by files" simplifies FFS: the 10% reserve binds only non-administrators and can be changed while mounted (FFS guide M8).
