SOSP 2026 · A Field Guide

Proving a controller correct alone isn't the hard part — proving it doesn't step on its neighbors is

Kubernetes runs dozens of independently-written controllers that quietly interfere with each other. Welder is the first formal method that verifies whole compositions of controllers — so adding one more controller extends a proof instead of restarting it.

📄 Cai, Date, Gu, Rivera, Chajed, Padon, Xu, Sun · SOSP 2026 🎓 Some TLA / formal-methods exposure assumed — primers cover the rest ⏱ ~30 min read
🧩

Verify each controller's CORE — reconciliation liveness (ESR) plus a rely/guarantee non-interference contract — on its own. Composing two CORE-compliant controller sets then needs only a compatibility check between their contracts, never a redo of either liveness proof.

Before you begin

Quick glossary, then ten ideas the paper assumes

First, the acronyms you'll see everywhere. Then primers you can open in any order — read straight through the first time, or jump to whatever's unfamiliar.

🔤 Quick glossary — the acronyms up front

CORECOmpositional REconciliation — Welder's specification: a controller set reconciles the cluster correctly and doesn't interfere with others.
ESREventually Stable Reconciliation (from Anvil) — a controller reaches its desired state and then stays there, given a stable desired state.
TLATemporal Logic of Actions — the logic used to state "always" (□) and "eventually...then" (written ;, "leads-to") properties of infinite executions.
RoC loopRetry-on-Conflict — a code pattern that retries a version-conflicted update until it wins, simulating an atomic transaction.
RS / Deploy / STSReplicaSet / Deployment / StatefulSet — three core Kubernetes controllers Welder verifies.
Rely / GuaranteeA contract pair: Rely = what a controller assumes others won't do; Guarantee = what it promises about its own requests.
ReplicaSet — lower-layer controller Deployment — depends on ReplicaSet CORE / Welder's proof machinery interference / liveness violation
1What a cluster control plane actually does▾

A control plane like Kubernetes doesn't execute your deployment once — it runs forever, continuously nudging the cluster's current state toward a user-declared desired state. This loop (observe → diff → act) is called reconciliation, and it's implemented not by one program but by a fleet of independent controllers, each owning a slice of the resources.

Now you're ready: Welder's whole subject is proving these loops actually converge — both alone, and while sharing state with each other.
2Desired state, current state, and objects▾

Kubernetes stores everything as versioned objects (Deployments, ReplicaSets, Pods, ...) in a datastore (etcd), fronted by an API server. A controller watches for changes to objects it cares about and reacts by creating, updating, or deleting other objects.

Now you're ready: a "liveness dependency" between two controllers just means one controller's desired-state object is written by another controller.
3Liveness vs. safety, the two flavors of correctness▾

Safety properties say "nothing bad ever happens" (e.g., a controller never deletes an object it doesn't own). Liveness properties say "something good eventually happens" (e.g., the cluster eventually matches the desired state). Liveness is harder to verify because it's a claim about infinite executions, not a single bad state to rule out.

Now you're ready: CORE bundles both — ESR is its liveness half, the Guarantee condition is its safety half.
4Two TLA operators: □ (always) and ; (leads-to)▾

TLA states properties over infinite traces of system states. □P means "P holds now and forever." P ; Q ("leads-to") means "whenever P holds, Q is guaranteed to eventually hold." ESR is written entirely with these two: □desire(d) ; □match(d) — "once the desired state stops changing, the cluster eventually matches it and stays matching."

Now you're ready: every formula in this guide is built from just these two operators plus ordinary logic (∧, ⇒, ∀).
5Rely-guarantee reasoning, in one sentence▾

To verify one piece of a concurrent system without re-verifying everyone else, you assume a rely condition about what your neighbors won't do, and in exchange you promise a guarantee about what you will do. If two components' rely and guarantee line up, you can compose their proofs without re-opening either one.

Now you're ready: CORE is exactly rely-guarantee reasoning adapted from concurrent programs to cluster controllers.
6Parent references — Kubernetes' ownership mechanism▾

Every object can carry a parent reference pointing to the object that "owns" it — e.g., a ReplicaSet's parent reference points to its Deployment. This is the existing Kubernetes mechanism Welder repurposes: "don't touch objects you don't own" becomes a concrete, checkable condition on requests.

Now you're ready: CORE's rely/guarantee conditions are defined almost entirely in terms of parent references — no new bookkeeping needed.
7Version-based optimistic concurrency▾

etcd (Kubernetes' datastore) tags every object with a version number. An update must supply the version it read; if another writer updated the object first, the version has moved and the update is rejected as a conflict. This is fast and lock-free, but it means two controllers racing to update the same object can starve one of them.

Now you're ready: this is exactly the setup that makes proving liveness about shared objects surprisingly hard (see the "Retry-on-Conflict" primer later, in How It Works).
8Fairness assumptions▾

Liveness proofs need to rule out infinitely unlucky executions — e.g., a message that's never delivered even though nothing stops it. Weak fairness says: if an action stays perpetually possible, it eventually happens. Fairness assumptions are what make "eventually" a meaningful, provable claim instead of vacuously false.

Now you're ready: standard fairness turns out to be too weak for one specific pattern (racing version updates) — that gap is one of Welder's three proof contributions.
The whole story in one place

Welder in a nutshell

The problem, the specification that fixes it, and how the pieces click together.

A cluster control plane is not one program — it's a fleet of independently developed controllers reconciling shared state. Prior work (Anvil) could verify that a single controller, running alone in a hardcoded, quiescent environment, eventually reconciles its desired state (ESR). But real control planes never run one controller alone: a ReplicaSet controller and a Deployment controller share objects, and arbitrary third-party controllers can be installed alongside them at any time. Anvil's proof says nothing about what happens when they interact — and interaction bugs are exactly where real outages come from.

CORE (COmpositional REconciliation) closes this gap. For a set of controllers S, CORE states: if nothing outside S touches the objects S owns (Rely), and any controllers S depends on have already reconciled (Depend), then every controller in S reconciles successfully (ESR) — and, unconditionally, S never touches objects it doesn't own (Guarantee). The key property: if two disjoint controller sets each satisfy CORE and their rely/guarantee contracts are compatible, their union satisfies CORE too — with a compose proof, not a redo.

The payoff: Welder verified four real Kubernetes controllers (ReplicaSet, Deployment, StatefulSet, a custom RabbitMQ operator) — 37,916 lines of machine-checked proof — yet composing all four together cost only 429 extra lines (about 1.1% of the total). An analysis of 188 real bugs found by prior controller-testing tools shows CORE would have precluded 178 of them (95%).

🍯 Key takeaways

  • Anvil verifies one controller's ESR alone, in a hardcoded environment; CORE verifies a controller set, against arbitrary co-controllers.
  • CORE = (Rely ∧ Depend) ⇒ ESR, plus an unconditional Guarantee — a liveness half and a safety half.
  • Rely/Guarantee are defined via Kubernetes' existing parent-reference ownership mechanism — no new bookkeeping.
  • Three new proof techniques make CORE provable: Iter-ESR (liveness dependencies with iterative updates), a transactional abstraction (object sharing under version conflicts), and a state-preservation invariant (interference).
  • Composition is cheap by design: Compose and Compose-Dep turn two CORE proofs into one, given only a compatibility check.
  • Result: 4 controllers, 1.5 person-years, 95% of known bug classes precluded, composition proof <1.2% of total effort.
Six everyday pictures

How to think about Welder

Each stands alone — read in any order. Every card ends with an honest note on where the picture stops being true.

The spec · Rely-guarantee

Roommates with a lease clause

Two roommates each sign a clause: "I won't touch your stuff, and here's exactly what counts as mine." Neither needs to know the other's daily habits — just that the clause holds. CORE's Rely and Guarantee are this clause, written per-controller using parent references as the "whose stuff is whose" test.

Where it breaks: roommates can renegotiate anytime; CORE's contracts are fixed at verification time — a controller can't be "trusted more" later without re-proving.
Compositionality · Interlocking bricks

Lego bricks, not poured concrete

Poured concrete: change one part, re-pour everything. Lego: each brick is independently solid, and two solid bricks click into a solid structure without either being rebuilt. CORE's Compose rule is the click — given each set's CORE and a compatibility check, the union's CORE follows for free.

Where it breaks: bricks click along any edge; controllers only compose cleanly when their scopes are disjoint — overlapping ownership needs a different (harder) argument.
ESR · Progress + stability

A thermostat, not a light switch

A light switch is instantaneous; a thermostat takes time to reach the target temperature but then holds it — it doesn't overshoot back and forth forever. ESR captures exactly this two-part promise: eventually reach the desired state (progress), then never leave it (stability) — as long as the target itself stops moving.

Where it breaks: a thermostat's target is set once by a human; a controller's "target" is often set by another controller, and that target might keep moving — which is precisely the puzzle the next analogy solves.
Iter-ESR · Liveness dependency

Climbing a ladder one rung at a time

You don't need the ladder to be motionless before you can prove you'll reach the top — you just need each rung to be reachable from the one below, and only finitely many rungs. The Deployment controller nudges the ReplicaSet's replica count up rung by rung, waiting at each one; Iter-ESR is the induction that says: finitely many, strictly-decreasing rungs means you provably reach the top and stay there.

Where it breaks: a real ladder's rungs are fixed in advance; here the "top" (desired replica count) could itself change externally — Iter-ESR only applies once that top is proven stable, which is the very thing it's used to establish upstream.
RoC loop · Fair object sharing

A deli-counter ticket, not a shoving match

Without a ticket system, two customers can keep cutting in front of each other forever — no rule technically breaks, but neither is ever served. The Retry-on-Conflict loop is a ticket system: a controller retries a version-conflicted write until it wins, and Welder just assumes the loop terminates — a far weaker, more realistic assumption than "the other customer eventually stops showing up."

Where it breaks: a real ticket system guarantees order; the RoC assumption doesn't promise fairness between competitors, only that this customer's own loop eventually stops looping.
State-preservation invariant

A "do not disturb" sign, proved not just posted

A hotel room stays as you left it not because you trust everyone's goodwill, but because housekeeping is contractually bound to skip rooms with the sign up. The state-preservation invariant is a proved version of that sign: any request not from the controller's own reconciliation for desired state d is shown to leave d's managed objects untouched — so progress proofs never need to re-examine every possible interfering request type by hand.

Where it breaks: the sign only covers objects the invariant names as "managed by d"; interference on objects outside that boundary still needs its own argument.
The full explanation

How it actually works

Section by section, following the paper's own structure — spec, then the three proof challenges, then composition.

1 · The problem — liveness bugs that only show up together

Figure 3 in the paper shows two failure patterns between the Deployment and ReplicaSet controllers that a single-controller proof cannot see. First, unsatisfied liveness dependency: if the ReplicaSet controller never converges (crashed, buggy, or just not yet verified), the Deployment controller waits forever — its own logic is fine, but its promise was conditional on a neighbor it silently assumed would work. Second, interference-driven oscillation: if a third, external controller repeatedly modifies the shared ReplicaSet object, both controllers can be kept perpetually reconciling a moving target and never stabilize.

2 · Defining CORE — Rely, Depend, ESR, Guarantee

For a controller set S, CORE is:

CORE_S ≜ Model_S ⊨ ((Rely_S ∧ Depend_S) ⇒ ESR_S) ∧ Guarantee_S

Rely_S: no controller outside S ever sends a request touching an object S owns. Depend_S: any controller S depends on (outside S) has already satisfied its own ESR. ESR_S: every controller in S eventually reconciles its desired state and keeps it stable. Guarantee_S: S never sends a request touching an object it doesn't own — unconditionally, not just when things go well.

Rely and Guarantee are built from Kubernetes' parent-reference mechanism: req_rely_c(r) forbids a request r from creating/updating/deleting an object owned by c, or transferring ownership to c; req_guarantee_c(r) is the mirror image for c's own requests.

🌱
Why not weaker rely conditions? One might hope "others eventually stop interfering" suffices. But the StatefulSet controller's naming scheme shows this fails: if another controller once creates a Pod with a reserved name, that Pod's mere continued existence blocks StatefulSet forever, even after the interferer stops acting. Hence the always-on □ in the Rely definition.

3 · Challenge 1 — liveness dependencies and Iter-ESR

The Deployment controller's rolling-update feature iteratively raises a ReplicaSet's replicas field and waits after each raise for the ReplicaSet controller to catch up — but ESR's premise requires the desired state to be already stable before promising convergence. That looks circular: proving Deployment's ESR needs ReplicaSet's ESR, which needs stability that Deployment itself is still in the middle of producing.

The fix is an induction on x = the gap between the target replica count and the ReplicaSet's current value. Because Deployment's updates are monotonic (only increase replicas), x strictly decreases every time Deployment acts, and stays put while it waits. Welder generalizes this into a reusable proof rule, Iter-ESR, whose four premises are: (1) the base ESR-like leads-to fact parameterized by n, (2) monotonicity — the gap never increases, (3) if the gap is nonzero and the lower controller has caught up, the upper controller eventually acts again, and (4) the conclusion — from any starting gap, the state eventually stabilizes at gap 0 forever.

4 · Challenge 2 — object sharing and the RoC abstraction

When Deployment and ReplicaSet update disjoint fields of the same versioned object, a naive environment model allows an execution where one controller always loses the version race — and neither TLA's weak nor strong fairness rules this out, because the blocked action (the API server accepting the update) is never always enabled; it's enabled, then invalidated by the winner, over and over.

Welder's fix is a transactional abstraction: model the update as an atomic check-then-update, and justify it by proving that a Retry-on-Conflict (RoC) loop — read, check a condition, write with the read's version, retry on conflict — refines that abstraction under one new fairness assumption: the RoC loop itself eventually terminates. This is strictly weaker than assuming other controllers stop writing, and it lets developers write and verify liveness proofs against the clean transactional model without ever reasoning about version conflicts directly.

5 · Challenge 3 — interference and the state-preservation invariant

Proving a controller's update actually sticks requires ruling out two kinds of interference: external (another controller overwrites or deletes the object) and internal (the same controller's reconciliation for a different desired state accidentally touches the same object). Rather than case-splitting on every request type, Welder proves one lemma once: any request not sent by controller c's reconciliation for desired state d preserves the cluster state that d manages. Progress proofs then apply this single invariant instead of re-deriving non-interference at every step.

6 · Composition — Compose and Compose-Dep

Given CORE★_S1 and CORE★_S2 (CORE with no external liveness dependency) for two disjoint sets, and a proof that their Rely/Guarantee pairs are compatible (each one's Guarantee implies it satisfies the other's Rely), the Compose rule yields CORE★_{S1∪S2} directly. When S2 depends on S1's liveness, Compose-Dep additionally requires ESR_S1 ⇒ Depend_S2 — usually trivial, since Depend_S2 is defined to be ESR_S1. Compatibility proofs reduce to checking requests: if a request satisfies one controller's guarantee, does it satisfy the other's rely? This is local, syntactic, and — per Table 1 — cheap: composing all four controllers cost 429 lines against 37,487 lines of individual CORE proofs.

Follow the numbers

Worked examples

Four passes through the paper's actual figures — the induction, the composition arithmetic, the bug analysis, and the performance cost.

① The Iter-ESR induction, concretely

Deployment wants ReplicaSet at 3 replicas; ReplicaSet currently reports 1. Walk the induction that proves this stabilizes.

  1. Gap: x = desired (3) − current (1) = 2. Define S(n): "if the gap is n, replicas eventually becomes stable."
  2. Base case S(0): if the gap is already 0, Deployment has nothing left to raise — it stops updating, so replicas is stable now.
  3. Inductive step, case A: Deployment updates again — it can only increase replicas (monotonicity), so the gap strictly shrinks, e.g. 2 → 1. By the inductive hypothesis S(1) (already proved for a smaller gap), we get S(2).
  4. Inductive step, case B: Deployment never updates again from this point on — then replicas is trivially stable from here.
  5. Conclusion: S(2) holds, so starting from a gap of 2, replicas provably reaches 3 and stays there — before ReplicaSet's own ESR is ever invoked.
🍯
Insight: the induction never needed to assume replicas was stable up front — it derives stability from monotonicity plus a finite starting gap, which is exactly what unblocks applying ReplicaSet's ESR next.

② Why composition is cheap: the 429-line arithmetic

Table 1 reports proof sizes (Model + Conformance + CORE, with the ESR-only portion in parentheses) for each of the four controllers.

  1. Per-controller CORE proofs (Model+Conf+CORE): ReplicaSet 8,263 lines, Deployment 11,080, StatefulSet 13,725, RabbitMQ 8,755. Summed: 41,823 lines of individual proof effort (including each controller's own conformance and model).
  2. The composition step — applying Compose-Dep twice (RS+Deploy, STS+RabbitMQ) then Compose once (merging both pairs) — costs only 429 lines, all of it compatibility-checking, none of it re-proving ESR.
  3. As a fraction: 429 ÷ (429 + individual CORE proof of 37,487) ≈ 1.14% of the grand total of 37,916 CORE-related proof lines.
  4. Contrast: without compositionality, verifying the four-controller composition from scratch would in principle require re-deriving each controller's ESR inside a single monolithic model — instead, Welder reuses each proof unchanged.
💡
This is CORE's central promise made numeric: proving a new controller "slots in" costs a compatibility check, not a rewrite of existing liveness proofs.

③ What CORE actually catches — the 188-bug analysis

The authors checked CORE against all 188 bugs found by prior controller-testing tools (Acto, Sieve).

  1. 178 of 188 bugs (≈ 94.7%, reported as 95%) would be precluded by CORE.
  2. Root causes fall into three buckets: failing on corner-case input, failing to recover from crash-induced intermediate states, and acting on stale observed state.
  3. Why CORE catches them: each bucket either blocks progress forever (violating ESR_S) or causes the controller to wrongly modify an object it doesn't own (violating Guarantee_S) — CORE's two halves cover both failure shapes.
  4. The remaining ~5% are bugs CORE's feature coverage doesn't reach — CORE only guarantees what's encoded in the ESR's match predicate, so a feature never modeled there isn't checked (see Discussion, §9).
🍯
Insight: CORE isn't a bug-pattern checklist — it's a semantic property that happens to imply the absence of most bug patterns testing tools find, because those bugs are liveness or ownership violations in disguise.

④ The cost of being verified — proof effort and runtime overhead

Two different "costs" the paper measures: person-time to write the proofs, and CPU/latency overhead at runtime.

  1. Verification effort: 1.5 person-years total. About one year to build Welder itself plus verify ReplicaSet and Deployment; with that experience, StatefulSet and the ported RabbitMQ controller (40 days) went much faster.
  2. Proof-to-exec ratio (proof lines ÷ implementation lines) ranges 5.4× (RabbitMQ, simple uniform "get-then-create-or-update" logic, lemmas reused across object types) to 30.4× (Deployment, whose rolling-update feature needs the extra Iter-ESR machinery).
  3. Runtime overhead — reconcile() time: verified controllers are modestly slower per reconcile call than the unverified references (e.g., ReplicaSet 0.85s vs 0.12s; Deployment 0.12s vs 0.04s), except RabbitMQ, which is faster (0.54s vs 0.92s) because it implements fewer features.
  4. Runtime overhead — end-to-end: negligible. All four controllers' full-system reconciliation times differ from their references by less than one standard deviation (e.g., StatefulSet: 121.93s vs 123.56s, diff −1.63±7.90s) — because reconcile() is a small fraction of total time dominated by container startup and image pulls.
💡
The proof-writing cost is real (person-years); the deployed-system cost is essentially zero — verified controllers are drop-in replacements.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Anvil already proves ESR for the Deployment controller. Why isn't that proof enough to conclude the real, multi-controller Kubernetes cluster reconciles correctly?
Show answer
Anvil's ESR proof is done in a hardcoded, eventually-quiescent environment where every other component is fixed and assumed non-interfering. It says nothing about what happens if the ReplicaSet controller it depends on never converges, or if a third controller repeatedly modifies the shared ReplicaSet object — both are real liveness violations (Fig. 3) that a single-controller proof simply doesn't model.Misconception: that "verified controller" implies "verified control plane." Verifying one component in isolation says nothing about its composition with others unless the proof is explicitly compositional.
Problem 2 · medium
Why can't CORE's rely condition be relaxed to "other controllers might interfere at first, but eventually stop"?
Show answer
The StatefulSet naming-scheme example: even after an interfering controller stops creating Pods with reserved names, the Pods it already created still exist and permanently block StatefulSet's own Pod creation. The harm isn't the ongoing action, it's the lingering effect — so the rely condition needs to hold always (□), not just "eventually."Misconception: that liveness violations always come from repeated bad actions. A single bad action with a permanent effect is enough.
Problem 3 · medium
Two controllers race to update the same versioned object. Standard TLA weak fairness says "if an action stays enabled, it eventually happens." Why doesn't that rule out one controller losing the race forever?
Show answer
Weak fairness is about a single action staying continuously enabled. Here, the losing controller's "apply my update" action is enabled — but the moment the API server handles the winner's update first, the loser's action becomes disabled (its version is now stale) and a fresh one becomes enabled instead. The action is never continuously blocked; it's repeatedly invalidated. Weak (and strong) fairness simply don't speak to this pattern.Misconception: that fairness assumptions are a generic "nothing gets starved forever" guarantee. They apply to specific actions staying enabled — a race with constantly-changing "the current enabled action" slips through.
Problem 4 · hard
Welder's fix assumes "the Retry-on-Conflict loop eventually terminates." Explain why this is weaker (and more realistic) than Anvil's original assumption that other controllers "eventually stop updating the shared object."
Show answer
Anvil's assumption blocks all competing controllers from ever touching the object again — unrealistic for objects that legitimately need periodic updates from multiple controllers, and it also breaks compositionality by privileging one controller over another. The RoC-termination assumption only says this specific update attempt eventually stops retrying — it says nothing about whether the other controller keeps writing to the object afterward, since a terminating retry loop is compatible with the other controller continuing to write in later, unrelated rounds.Misconception: that avoiding version conflicts requires freezing out competitors. It only requires that each individual write attempt is eventually resolved, one way or another.
Problem 5 · medium
The state-preservation invariant says "any request not sent by c's reconciliation for d preserves d's managed state." Why does this reduce proof burden compared to reasoning about every request type directly?
Show answer
Without the invariant, a progress proof would need to case-split on every possible request (create/update/delete, from every other controller and from the same controller's other reconciliations) and show each one doesn't disturb d's state — repeated at every step of the reconciliation. With the invariant proved once, progress proofs just cite it as a black box: "this step isn't from c's reconciliation for d, so by the invariant, state is preserved" — no re-derivation needed.Misconception: that non-interference has to be re-argued at every proof step. Factoring it into one reusable lemma is what makes the proof modular.
Problem 6 · hard
Composing all four Welder controllers cost 429 extra lines against 37,487 lines of individual CORE proofs. What specifically makes composition proofs cheap — what do they not have to re-derive?
Show answer
Compose and Compose-Dep only require checking compatibility: for any request satisfying one controller's Guarantee, does it satisfy the other's Rely? This is a local, syntactic check on the request predicates (built from parent references) — it never touches either controller's ESR proof, which is where almost all the proof effort (>94% of each controller's CORE proof, per the paper) lives. The composition rule is designed so liveness proofs are reused verbatim, not re-verified in a bigger combined model.Misconception: that composing proofs means re-running verification on the union of the systems. CORE's rely-guarantee structure is specifically built so that never has to happen.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the one-sentence difference between Anvil and Welder?▾
Anvil proves one controller's ESR alone in a hardcoded, non-interfering environment; Welder proves a whole set of controllers' CORE (ESR plus non-interference) against an arbitrary, open set of co-controllers, and lets that proof compose with newly added controllers.
Q2Is CORE a safety property or a liveness property?▾
Both. Its ESR component is pure liveness ("eventually reconciles, then stays reconciled"). Its Guarantee component is pure safety ("never touches an object it doesn't own"). CORE needs both: liveness alone doesn't rule out a controller that "reconciles" by stealing another controller's objects.
Q3Why does CORE conjoin ESR for every controller in a set, instead of just the top-level one a client cares about?▾
Because a client relying on, say, the Deployment controller implicitly needs the "internal" controllers it depends on (ReplicaSet) to also behave. Conjoining all of them keeps the composition rules simple and lets the target set grow incrementally without redefining what's exposed.
Q4How does Welder handle the fact that Verus doesn't support variadic generics, but the environment model needs to plug in an arbitrary number of controllers?▾
It simulates variadic generics with a single opaque type, OpaqueT, representing any controller's local state, plus per-controller encode/decode functions related by an axiom (decode(encode(t)) = Some(t)). Developers still write their controller's state in a natural type; the opaque wrapper is only for the shared environment model.
Q5Do the verified controllers implement every feature of the real Kubernetes ones?▾
No — feature parity isn't the goal. ReplicaSet, for instance, skips Pod adoption/release and batched creation/deletion. CORE's guarantee only covers what's encoded in the ESR's match predicate; unmodeled features simply aren't covered by the proof, which developers can extend later (§9, Discussion).
Q6What's the actual runtime cost of using a verified controller in production?▾
Essentially none end-to-end. Per-reconcile call, verified controllers are sometimes slower (e.g., ReplicaSet 0.85s vs 0.12s for its reference), but full-system reconciliation time is dominated by container startup and image pulls, so end-to-end differences are all within one standard deviation across all four controllers. CPU consumption stayed under 3% for both verified and reference controllers.
Q7Does Compose-Dep require the two controller sets to have no interaction at all?▾
No — it explicitly handles the case where one set (S2) has a liveness dependency on the other (S1): it requires ESR_S1 ⇒ Depend_S2, which is usually trivial since Depend_S2 is defined to literally be ESR_S1. What it does require is that S1 and S2's Rely/Guarantee contracts be compatible (no un-modeled interference) — that's the Compat proof obligation shared with plain Compose.
Q8What did verification actually find — any real bugs?▾
Yes, seven, including one inherited from the official Kubernetes StatefulSet controller: a naming collision that lets ReplicaSet and StatefulSet controllers fight over ownership of the same Pod (later independently confirmed by Kubernetes developers). Six of the seven bugs were undetectable by prior controller-testing tools — either the triggering condition was too complex to hit by testing, or the failure was silent and slipped past the testing oracles.
Q9What's explicitly left out of scope / future work?▾
CORE targets multiprogrammed control planes (independent controllers), not multithreaded controllers or threads sharing data. The authors also flag: reasoning about circular liveness dependencies (Compose-Dep only handles acyclic dependency chains — cyclic ones need the non-waiting-action technique from McMillan's prior work), using separation logic instead of rely-guarantee for finer-grained composition, and further automating proofs with AI agents, which the authors report can currently help with sub-tasks (finishing invariant proofs, generating liveness-proof skeletons) but not the full CORE proof end-to-end.

Weak fairnessAn always-enabled action eventually happens — insufficient alone for version-race liveness (§4.2).
Auxiliary componentsWelder's parametric environment model, Anvil's TLA embedding, and Verus — the trusted base Welder builds on.
PodMonkeyWelder's fault-injection model of arbitrary Pod creation/deletion/update, used to verify core controllers tolerate Pod failures.
CompatThe proof obligation for composing two controller sets: each set's Guarantee implies it satisfies the other's Rely.

Source notes — what's the paper's, what's this guide's framing

From the paper directly: the CORE specification and its formal definition (eq. 1–4); the three proof challenges (Iter-ESR, RoC transactional abstraction, state-preservation invariant) and their solutions (§4); the Compose/Compose-Dep rules (§4.4); all numbers in Tables 1–3 (proof line counts, testing counts, performance timings); the 188-bug/178-precluded analysis and the seven bugs found (§3.3, §6); the 1.5 person-year and 40-day verification-effort figures (§6, §7.1).

This guide's framing: the "roommates / Lego bricks / ladder / deli ticket / do-not-disturb sign" analogies, the redrawn Fig. 3 timeline diagram, the CORE-composition signature figure, and the derived percentages (composition ≈1.1%/1.14% of total proof, ESR ≈96.6% share) computed from the paper's raw Table 1 figures — the ratios themselves aren't stated verbatim in the paper but follow directly from its reported numbers.
