Balanced branches, unbalanced hardware

Two SGX branch paths can look byte-for-byte identical — same pages, same instruction types, same counts, aligned stores. There's still one thing you forgot to balance: a tiny 4-bit counter deep in the out-of-order engine that remembers which store just aliased which load.

📄 "MDPeek" · Liu, Feng, Li, Wang, He, Lyu, Carlson 🎓 SGX + out-of-order execution basics assumed — primers cover them ⏱ ~30 min read
🕵️

A store whose address isn't ready yet, followed by a load — and the Memory Disambiguation Unit silently remembers whether they aliased, in a counter keyed only by 8 bits of the load's PC. Branch balancing never touched that counter.

Acronyms and ideas the paper assumes you know

1What an SGX enclave protects — and what it can't hide▾

SGX carves out an enclave: memory the OS can't read or write, even though the OS still schedules it, handles its page faults, and manages its page tables. That's the catch — SGX's threat model has always assumed a malicious OS, so anything the OS can observe (page access patterns, interrupt timing, shared hardware state) is fair game unless software explicitly defends against it.

The victims in this paper — Libjpeg, MbedTLS, WolfSSL — run inside such an enclave, but their code still contains branches whose direction depends on secret data (an RSA key, an image's pixel values).

Now you're ready: MDPeek's attacker is exactly this "malicious OS" — full page-table control, but no ability to read enclave memory directly.
2Out-of-order execution and the ROB▾

Modern CPUs don't execute instructions strictly in program order — they dispatch into a Reorder Buffer (ROB) and execute whichever instructions have their inputs ready, retiring results in order only at the end. This is how a slow instruction (say, waiting on a cache miss) doesn't stall everything behind it.

The ROB has a fixed size (224 entries on the Skylake CPU used in this paper) — only so many in-flight instructions can be "in the air" before older ones must retire.

Now you're ready: the MDU only updates when a store and a load are both sitting in the ROB at once — which is why ROB size caps how far apart exploitable instructions can be.
3Why a load might need to guess about a store▾

If a store writes to address X and a later load reads address Y, and the CPU already knows X ≠ Y, it's safe to execute the load early (out of order) — it can't see stale data. But if the store's address isn't computed yet, the CPU doesn't know whether X = Y. Waiting is always safe but slow; guessing "not aliased" and running the load early is faster but risky.

Memory disambiguation is the name for this guess. Get it wrong, and the CPU must roll back and re-execute the load with correct data — a "machine clear."

Now you're ready: the MDU is the predictor that makes this specific guess, and its 4-bit counters are exactly a record of how often a given load has aliased in the past.
4Secret-dependent branches, and "balancing" them▾

A secret-dependent branch takes different paths depending on private data — an RSA prime being odd or even, whether an image block is all one color. If the two paths differ in any observable way (which pages they touch, how many instructions they run, which addresses they store to), an attacker watching the CPU can infer the secret one branch at a time.

Branch balancing tries to erase those differences: same instruction types on both paths, same instruction counts between pages, store program-counters aligned to the same 16-byte boundary.

Now you're ready: this paper's entire premise is that balancing done against known channels (pages, instruction counts, store PC) still leaves an unknown one — the MDU — completely open.
5Flushing microarchitectural state▾

The other standard SGX defense: when a context switch happens (the OS interrupts the enclave), the enclave's exit code deliberately clears out structures known to leak — cache lines via eviction sets, branch predictor history, prefetcher state — so the next process can't read anything left behind.

This only works for structures researchers have already found and characterized. Anything undocumented survives untouched.

Now you're ready: the MDU was exactly this kind of blind spot — known to exist since 2021, but never flushed, because nobody had shown it leaked anything.
6Page faults as an attacker's clock (SGX-Step)▾

An OS with page-table control can mark a page "not present," forcing a page fault the instant the enclave touches it — even mid-instruction. SGX-Step uses this to single-step or coarsely interrupt an enclave at chosen points, without needing SGX to trust the interrupt source.

Between two page faults, the attacker fully controls the CPU and can run its own code — including code that reads or resets hardware predictor state.

Now you're ready: MDPeek's whole workflow is "fault before the branch → let it run → fault after → probe" — the same primitive earlier SGX attacks used, aimed at a new target.
7Timing side channels and PMC-based detection▾

Many microarchitectural attacks don't read secret bits directly — they read time. If two internal CPU states cause a measurably different number of cycles for the same instruction sequence, an attacker who can measure cycles precisely can distinguish the states, and from that infer which one occurred.

Performance Monitor Counters (PMCs) — like MACHINE_CLEARS.COUNT — give an even more direct read on internal events (here, misprediction rollbacks), which is invaluable for reverse engineering, though the end-to-end attacks rely on plain timing.

Now you're ready: the paper's probing code measures a ~150-cycle gap between two MDU states (Fig. 11) — small, but stable enough to read out reliably.
8The BEEA modular-inverse algorithm▾

RSA key generation needs a modular inverse (e.g. 𝑒⁻¹ mod λ). The Binary Extended Euclidean Algorithm computes it with a loop of subtract-and-shift steps, where each "sub-step" branches on which of two values is larger — and that comparison depends on the secret primes.

Both MbedTLS and WolfSSL use variants of BEEA, and both have already source-balanced this branch (dummy operations on the untaken path) — exactly the kind of "balanced" code MDPeek targets.

Now you're ready: recovering the branch direction at every BEEA sub-step, iteration by iteration, is literally how MDPeek reconstructs the RSA primes 𝑝 and 𝑞.
9Compiler optimization levels and inlining▾

Compilers (here, LLVM/Clang) offer optimization levels -O0 through -O3. Higher levels remove redundant memory traffic, allocate more values to registers, and — importantly — inline small functions directly into their callers, eliminating the call but exposing the callee's local variables as new stack stores/loads at the call site.

This matters because "the code looks balanced at the source level" doesn't mean the compiled code is: a function call that -O3 decides to inline can inject brand-new, unbalanced store/load pairs.

Now you're ready: this is exactly why MbedTLS and WolfSSL — both written with side-channel resistance in mind — only become exploitable under -O3.
The whole story in one place

MDPeek in a nutshell

A new leakage source, a reverse-engineering effort to characterize it, and three real attacks that survive existing defenses.

SGX developers have two solid, general-purpose defenses against control-flow leaks: flush known leaky hardware state at context switches, and balance both branch paths so they look identical to any known channel (pages, instruction counts, store PC alignment). Both work — against known channels.

MDPeek targets a channel nobody had characterized well enough to defend against: the Memory Disambiguation Unit (MDU), 256 4-bit counters (one per value of a load's low 8 PC bits) that predict whether a load can race ahead of an earlier, address-pending store. The counter resets to 15 whenever the store and load truly alias, and otherwise decrements by one each time they don't — a saturating history of "did this load ever collide with a store here." Reading that counter's state via timing tells an attacker exactly what a balanced, flushed branch was hiding: which path executed.

To build the attack, the authors first reverse-engineer when the MDU turns on and updates (Section 4) — conditions no prior work had nailed down — then build a static-analysis pass over compiler output that flags loads capable of triggering an update (Section 5), and finally chain page-fault-driven interrupts (SGX-Step) with a calibrated timing probe into full attacks on Libjpeg, MbedTLS, and WolfSSL (Section 6).

The payoff: 98.76% pixel accuracy recovering a JPEG image, near-100% accuracy recovering 2048-bit RSA/RSA-CRT primes from a single trace — and a proposed fix, store-to-load coupling, that cuts mitigation overhead from ~140% (naive fencing) to ~20%.

🔥 Key takeaways

  • The MDU is 256 4-bit counters, selected purely by the lowest 8 bits of a load's PC — a granularity no existing defense targets.
  • Enabling the MDU needs a store whose address generation is delayed past its load's, with the dependence still unresolved.
  • Updating it further needs the store and load co-resident in the ROB and the load's address TLB-hit.
  • A delay-capacity model (how long can op@rd stall a store's address?) lets LLVM statically flag exploitable loads in real binaries.
  • Because the leak is a hardware counter, not a cache line, it survives both flushing and branch balancing.
  • Attacks succeed from a single trace — critical for one-shot secrets like freshly generated RSA keys.
  • Store-to-load coupling (a cheap artificial dependency) blocks the leak for ~7× less overhead than fencing.
💡
If you work on OS-managed tiering: the closest architectural cousin here is page-fault-based hotness tracking (the same mechanism TPP/HeMem-style systems use for access sampling). SGX-Step repurposes that exact primitive — deliberately faulting pages to regain control at precise instants — for microarchitectural forensics instead of counting accesses. Same lever, opposite intent.
Seven everyday pictures

How to think about MDPeek

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · MDU counters

A doorman with a good memory

A doorman who's watched the same doorway for years learns which regulars always show ID and which never need to — he waves the "never-aliases" crowd straight through. The MDU counter is that doorman's memory for one specific load: each time the preceding store turns out unrelated, his confidence (the counter) ticks down; the moment they truly collide, he resets to full suspicion (15).

Where it breaks: a real doorman remembers a person; the MDU only remembers a PC address's low byte — it can't tell two unrelated loads apart if they happen to share that byte, and it forgets nothing about which store aliased, only that one did.
Why balancing fails · Alignment mismatch

Twins in matching uniforms

Balance both branch paths perfectly — same clothes, same posture, standing 16 inches apart on marked tiles (the Frontal Attack's 16-byte store alignment). A guard checking uniforms sees identical twins. But the MDU isn't checking uniforms; it's checking a different, coarser identifier entirely — the load's low 8 PC bits, a 256-byte granularity nobody aligned for.

Where it breaks: real twins share every visible trait by construction; here the two "identical" branch paths were never actually made identical at the MDU's chosen granularity — balancing solved the wrong dimension.
Store-load races · Memory disambiguation

Crossing a one-lane bridge blind

A car (the load) approaches a narrow bridge and can't yet see if another car (the store) is already crossing from the other side because fog (delayed address generation) hides it. Cross now and save time, or wait and be safe? The MDU is the driver's learned instinct, built from every past crossing at this exact bridge — go if it's rarely collided before, wait if it often has.

Where it breaks: a real driver's instinct is about this bridge; the MDU's instinct is shared by every load whose PC happens to share the same low byte — different bridges, same gut feeling.
Delay capacity · Instruction chains

A relay race, not a straight sprint

If one runner (one imul) covers 6 meters of "stall time," you might expect two runners in sequence to cover 12. But a relay has handoffs — each runner must wait for the baton (the register result) before starting, so the whole chain's effective delay compounds past simple addition: two chained imuls reach 20, not 12.

Where it breaks: real relay handoffs lose time; this chain gains disproportionate delay-capacity as instructions stack, because each extra multiply both adds its own latency and pushes the whole dependent chain further from being ready — the opposite intuition from lost momentum.
SGX-Step · Page-fault interrupts

Freezing a film, frame by frame

Jam the projector deliberately (a page fault) and you can pause the film wherever you like, peek at the frame, then let it resume. Do this at exactly the two moments that bracket a secret branch, and you've isolated one instruction's worth of execution for inspection — without ever asking the projectionist's permission.

Where it breaks: pausing a real film erases nothing; halting a CPU still leaves microarchitectural residue (the MDU counter update already happened) behind in hardware that a re-run of the frame won't undo — that residue is exactly what gets read.
The defense · Store-to-load coupling

Tying a short leash between them

Instead of forbidding the dog (the load) from moving until the owner (the store) is fully settled — which is what a fence instruction does, freezing everything — clip a short leash between them: an explicit, cheap arithmetic dependency that makes the load's address provably derived from the store's. Now the CPU never has to guess; there's nothing left to predict.

Where it breaks: a leash constrains motion continuously; the coupling instruction only has to delay the store's address by a few cycles, not restrain the whole pipeline — which is exactly why it's ~7× cheaper than a full fence.
Coverage · Cache/BPU/prefetcher flushing

Sweeping a room you know has dust

You clean the shelves, the floor, and behind the couch — everywhere you already know dust collects. A room you've never inspected stays untouched, not because it's clean, but because nobody thought to check it. SGX's flushing defenses sweep the cache, branch predictor, and prefetcher — every place prior research had already proven leaks.

Where it breaks: a room's hiding spots are finite and eventually all get found; a modern CPU has dozens of undocumented predictors, so "we flush everything known" is a moving, never-complete target — MDPeek is simply the next spot found.
The full explanation

How MDPeek actually works

From reverse-engineered hardware logic to a working, single-trace attack.

1 · What makes the MDU turn on and update

Reverse engineering (Section 4) pinned down two separate logic blocks. Enable logic fires when: the store and load are both in the ROB, the store's virtual address isn't generated yet, the load's address is valid and translated, and the CPU genuinely can't resolve their dependence. Delays anywhere except store-address generation (execution, retirement, even TLB misses on the store) don't matter — only an address-generation delay that exceeds the load's triggers it.

Update logic then fires only if the store's address is valid, or — surprisingly — even if it's invalid, as long as its page offset differs from the load's by at least 4 bytes. If they're the same physical address, the counter resets to 15 (alias); otherwise it decrements by one (no alias).

2 · The delay-capacity model — finding exploitable code statically

To decide whether a given store [rd]; …; load [rs] sequence in compiled code can trigger an update, the paper defines two distances: the LS distance (store to load) and the Def distance (the instruction that last wrote rd, to the store). Each instruction type has an empirically measured delay capacity — the largest Def distance at which it still keeps the store's address "not yet ready" more than half the time.

Def distance + LS distance < Delay Capacity of op@rd   # → the load is flagged exploitable

Delay capacity varies hugely by instruction — div exceeds imul by roughly 60 — and compounds non-linearly across dependent chains (a single imul: capacity 6; two chained: capacity 20, not 12). An LLVM backend pass computes this over every basic block (using Floyd's all-pairs shortest path, O(n³) in basic blocks) and flags loads whose measured margin exceeds the LS distance.

3 · What that analysis found in real applications

Read the pattern, not just the numbers. Libjpeg (never designed for side-channel resistance) starts with many exploitable loads at -O0 and mostly loses them to optimization. MbedTLS and WolfSSL (source-balanced) start at zero — until -O3's function inlining injects fresh stack-spill loads at the call sites of mp_sub / s_mp_sub. "More optimized" is not "more secure."

4 · The probing primitive

To read a counter reliably in a single trace (no averaging across repeated runs), the authors auto-search chains of data-dependent instructions placed before the store and after the load, scoring candidates with an evaluation function that rewards a large, stable gap between the two counter states:

F(T1,T2) = W(T1,T2) − 1/5·(V(T1)+V(T2)) − 1/4·(M(T1)+M(T2))
# W = Wasserstein distance between the two timing distributions
# V = variance (want low)  ·  M = mean (want low, i.e. fast overall)

The winning code repeats lea 50 times before the store and 50 times after the load, producing a stable ~150-cycle separation between "counter = 0" and "counter > 0" — accurate enough to drive single-trace attacks on secrets that never repeat, like a fresh RSA key.

5 · End-to-end: three applications, one workflow

  1. Synchronize. Use SGX-Step to fault the enclave right before and right after the target branch, based on a pre-known, secret-independent page-fault sequence.
  2. Initialize. In the attacker's own address space, run 3 aliased store-load pairs (256-byte-aligned load PC, matching the victim's vulnerable load) to force the shared counter to 15.
  3. Let the victim run. Resume the enclave through the branch; whichever path executes updates (or doesn't update) the shared counter.
  4. Probe. Regain control at the second fault, re-run the timing primitive, and classify the counter's state.
  5. Reconstruct. Repeat per iteration/block, then decode the recovered branch sequence into pixels (Libjpeg) or RSA primes (MbedTLS, WolfSSL).
Follow the numbers, step by step

Worked examples

Four calculations, each using the paper's own reported figures.

① Why MbedTLS's Table 2 entry is exactly 6

Table 2 reports 6 vulnerable loads in MbedTLS's mbedtls_mpi_inv_mod under -O3. Section 6.3 separately states: "for each sub-step, there are three exploitable loads in each branch direction." Do these agree?

  1. One BEEA sub-step has two branch directions (the "then" and "else" paths of the comparison).
  2. Each direction independently exposes 3 exploitable loads, per the paper's own description of the attack (Fig. 13b).
  3. Total per sub-step = 3 loads × 2 directions = 6 — exactly Table 2's reported count.
  4. Why it matters: the attacker doesn't need all 6; any single one leaks the branch direction, and having several lets them vote to cancel noise (see example ③).
🔥
Insight: Table 2's static count and the dynamic attack description cross-check exactly — good evidence the LLVM analysis pass is finding the same loads the manual attack actually uses.

② Timing the Libjpeg attack, block by block

The paper reports 7.8 minutes to leak a 640×480 image, interrupting jpeg_idct_islow "twice" per invocation. What does that imply about the per-probe cost?

  1. Blocks per image: IDCT processes 8×8 pixel blocks: 640⁄8 × 480⁄8 = 80 × 60 = 4,800 blocks.
  2. Interrupts per image: 2 page-fault interrupts per block (per Fig. 13a's caption) → 4,800 × 2 = 9,600 interrupts.
  3. Total attack time: 7.8 min = 468 seconds.
  4. Time per interrupt cycle: 468 s ÷ 9,600 ≈ 48.75 ms — the round trip of fault, probe, resume, per branch readout.
💡
That ~49 ms figure is our arithmetic from the paper's stated totals, not a number the paper states directly — it's in the same ballpark as other SGX-Step page-fault attacks' per-fault overhead, which is a useful sanity check that the MDU probe itself isn't the bottleneck.

③ How voting turns 97% into "nearly 100%"

MbedTLS: a single load reaches >97% success; using two loads' votes gets "nearly 100% accuracy." WolfSSL: a single load exceeds 95%; five-plus loads "approach 100%." Where do those combined numbers come from?

  1. MbedTLS, single load: error rate ≤ 3%.
  2. Two independent loads both wrong: 0.03 × 0.03 = 0.0009 → combined accuracy ≈ 99.91%, matching "nearly 100%."
  3. WolfSSL, single load: error rate ≤ 5%.
  4. Five independent loads all wrong: 0.05⁵ ≈ 3.1×10⁻⁷ → combined accuracy effectively 100%, matching "approaches 100%."
⚠
Caveat: this independent-error multiplication is our illustrative model of "why voting works," not a formula the paper states — if the loads' errors were correlated (e.g. all disturbed by the same interrupt jitter), the gain from voting would be far smaller than this math suggests.

④ Verifying the "7×" defense claim

The abstract claims store-to-load coupling gives "a 7× latency reduction compared to naive techniques like serialization." Figure 14 reports store-fencing (lfence) at ~140% overhead, load-fencing at ~170%, balancing at ~160%, and coupling at ~20%. Which comparison gives exactly 7×?

  1. Store-fencing overhead: ~140%.
  2. Coupling overhead: ~20%.
  3. Ratio: 140 ÷ 20 = 7.0 — exactly the paper's headline number.
  4. Careful distinction: this is a ratio of added overhead, not of total runtime — a program running at 2.40× baseline (store-fencing) versus 1.20× baseline (coupling) is only a 2× difference in wall-clock time, even though the overhead itself dropped 7×.
🔥
Insight: a "7× cheaper defense" and "2× faster program" are both true simultaneously — always check which baseline a speedup ratio is taken against.

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
The Frontal Attack defense aligns every store's PC to a 16-byte boundary from the branch. Why doesn't this stop MDPeek?
Show answer
MDU counters are selected by the load's PC, specifically its lowest 8 bits — a 256-byte granularity, not 16 bytes, and not the store's PC at all. Aligning stores to 16 bytes says nothing about which of the 256 MDU counters a given load will hit.Misconception: assuming a PC-alignment defense generalizes across every PC-indexed hardware structure. Different predictors key on different address bits and even different instructions (store vs. load) entirely.
Problem 2 · easy
Table 2 shows MbedTLS and WolfSSL have 0 vulnerable loads at -O0 through -O2, but 6 and 18 respectively at -O3. Why would more optimization make security-conscious code less safe?
Show answer
Both libraries already balance their secret-dependent branches at the source level. At -O3, LLVM inlines small helper functions (like mp_sub) directly into their callers. Inlining doesn't add new logic — but it does expose new stack-spill store/load pairs at the former call site, and those weren't present (or weren't a store-load pair at all) in the un-inlined, lower-optimization builds.Misconception: "more optimized" implies "strictly better" along every axis including security. Optimization decisions are made for speed, and can silently reshape the very memory-access patterns that source-level balancing was trying to control.
Problem 3 · medium
Inserting an lfence right after the delayed store defeats MDU updates, but costs 140–170% overhead. Which of the MDU's four enable conditions does it break, and why is it so expensive compared to store-to-load coupling?
Show answer
It breaks "store and load co-resident in the ROB, with the dependence unresolved" — the fence forces the store (or load) to fully retire/resolve before anything after it can issue, so the pair is never simultaneously in-flight with an open question between them. It's expensive because it blocks all out-of-order execution around that point, not just the one correlated load — every independent instruction nearby pays the cost too. Coupling, by contrast, only delays the store's own address generation by a few cycles via a cheap dependency.Misconception: that a "correct" fix must be architecturally blunt. Coupling proves you can remove exactly the ambiguity the predictor exploits without touching anything else in the pipeline.
Problem 4 · medium
An attacker resets a shared MDU counter to 15, then a test snippet runs 15 non-aliased store-load pairs using a different code region that happens to share the same load PC low byte. What happens to the counter, and what does this imply for placing MDPeek's own probing code?
Show answer
The counter decrements 15 times regardless of which code triggered each access — it reaches 0. This is because the MDU only tracks the lowest 8 bits of the load's PC (256 buckets across the entire address space), so unrelated code sharing that byte perturbs the same counter as the victim's load. For MDPeek's probe to read the victim'sMisconception: assuming a hardware predictor this narrow (256 buckets) is effectively private per code location. It's shared and collidable across the whole address space, which is a vulnerability but also an implementation constraint the attacker must respect.
Problem 5 · hard
A single imul has delay capacity 6; a chain of two dependent imuls has delay capacity 20, not 2×6=12. Why does the model need to precompute chains empirically instead of just summing single-instruction capacities?
Show answer
Delay capacity isn't a simple "time budget" that adds linearly — each instruction in a dependent chain must wait for the previous one's result, so the chain's total time-to-generate-the-final-address compounds superlinearly with pipeline latencies and instruction-queuing effects, not just instruction count. A purely additive model would systematically underestimate how long real dependent chains can stall a store's address, causing the LLVM pass to miss genuinely exploitable loads.Misconception: treating instruction latency as a purely additive resource, like a time budget you spend serially. Dependent chains interact with the pipeline non-linearly, which is exactly why the paper measures chains directly rather than deriving them from single-instruction numbers.
Problem 6 · medium
If a single vulnerable load reveals the correct branch direction 97% of the time, and using 2 loads' majority vote gets you to ~99.9%, what hidden assumption makes that math valid — and when would it fail?
Show answer
The math (0.03² = 0.09% combined error) assumes the two loads' errors are largely independent — caused by unrelated noise sources. If instead both counters are perturbed by the same event (e.g. the same page-fault interrupt jitter, or the same OS scheduling hiccup), their errors would be correlated, and a wrong reading on one load would likely coincide with a wrong reading on the other — voting would gain far less than the independent-error math predicts.Misconception: that adding more redundant measurements always multiplies down the error rate. It only does so cleanly when the error sources are close to independent; correlated noise defeats the benefit of voting.
Problem 7 · hard
Section 7.2 claims MDPeek doesn't need APIC-based single-stepping, unlike some prior SGX attacks — yet it still uses SGX-Step. What's the actual difference in required capability?
Show answer
MDPeek still needs page-granularity control (deterministic page faults to regain the CPU at known points around the branch) — that's the SGX-Step part. What it doesn't need is instruction-granularity single-stepping via a precisely-timed local APIC timer interrupt, which some prior attacks require to isolate individual instructions. Because the MDU's counter state persists across the coarser page-fault window regardless of exactly which instruction triggered the fault, a coarser, simpler interrupt primitive is sufficient.Misconception: "doesn't need complex configuration" means no privileged capability at all. The attacker still needs root-level page-table control — just not the more fragile, finer-grained single-instruction timer trick.
Problem 8 · easy
SGX developers already flush the cache, BPU, and prefetcher state at every context switch. Why doesn't this stop MDPeek?
Show answer
Flushing only clears structures that researchers have already identified as leaky and written eviction code for. The MDU had been discovered (2021) but never shown to leak information via a side channel before this paper, so nobody had written — or thought to write — code to flush it during enclave exits. It's not that flushing is broken; it simply never covered this unit.Misconception: that "flush known microarchitectural state" means flushing everything the CPU has. It means flushing everything researchers have already found — which by definition excludes any undiscovered predictor.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What exactly does the MDU predict?▾
Whether a load can execute out of order ahead of an earlier store whose target address hasn't been computed yet. If the CPU predicts "no alias" and is right, it saved time; if wrong, it must roll back and re-execute the load (a machine clear).
Q2How is a specific MDU counter chosen?▾
By the lowest 8 bits of the load's program counter — giving 256 possible counters, each 4 bits wide. Two loads whose addresses share that low byte, anywhere in the whole program, share the same counter.
Q3Why can MDPeek bypass branch balancing when so many prior attacks couldn't?▾
Balancing (Table 1) was designed against every channel researchers had previously found: pages, instruction type/count, store-PC alignment. The MDU is indexed and updated by mechanisms none of those match — a load-PC-selected hardware counter that neither pages, instruction mix, nor 16-byte store alignment happens to control.
Q4What conditions actually trigger an MDU update?▾
The store's address generation must be delayed past the load's, the dependence must be genuinely unresolved, both instructions must be co-resident in the ROB (within its 224-entry size on Skylake), and the load's address must be TLB-hit and valid. If the store's own address is invalid, the update can still happen provided its page offset differs from the load's by ≥4 bytes.
Q5How does the paper find exploitable code without running the victim first?▾
A "delay capacity" model, measured empirically per instruction (and per dependent chain), predicts how long a given instruction sequence can keep a store's address "not ready." An LLVM backend pass then checks every load in compiled code against this model and flags the ones whose preceding store-defining chain plausibly stays unresolved long enough.
Q6Why do the three attacked applications differ so much in exploitable-load count?▾
Libjpeg was never written with side-channel resistance in mind, so its unoptimized code is full of exploitable loads (16 per branch at -O0). MbedTLS and WolfSSL both explicitly balance their secret-dependent branches at the source level, so they show zero vulnerable loads until -O3's function inlining reintroduces some.
Q7How accurate and fast are the real attacks?▾
Libjpeg: ~7.8 minutes to recover a 640×480 fingerprint image at 98.76% pixel accuracy. MbedTLS RSA-CRT (2048-bit): ~830 ms per attack, single-load accuracy >97%, near-100% with 2 loads voting. WolfSSL RSA (2048-bit): ~880 ms per attack, single-load accuracy >95%, approaching 100% with 5+ loads.
Q8Why does MDPeek work reliably from a single trace, unlike some earlier attacks?▾
The MDU's counter state is comparatively insensitive to interrupt/context-switch noise: the paper finds 210 of 256 counters stay stable (unchanged or predictably decreasing) across a page fault with 95% probability. That stability, plus a carefully-tuned timing primitive, is what lets MDPeek skip the hundreds-to-thousands of repeated trials other SGX side channels need — essential for one-shot secrets like a freshly generated RSA key.
Q9What is store-to-load coupling, and why is it cheaper than fencing?▾
It inserts a cheap arithmetic instruction (e.g. an AND) that makes the load's address explicitly, artificially depend on the store's address, so the CPU can resolve their relationship deterministically instead of guessing. This only delays the store's own address generation slightly, rather than serializing the entire pipeline (lfence, ~140–170% overhead) or destroying spatial locality (256-byte balancing, ~160% overhead) — coupling measures at ~20%.
Q10Does disabling speculative store bypass (SSBD) stop this attack?▾
SSBD can disable the MDU, but under this paper's threat model the attacker is a root-privileged, malicious OS — exactly the entity that controls whether SSBD is even enabled. An attacker can simply turn it off, so it's not an effective mitigation here.
Q11Is the MDU unique to Intel CPUs?▾
No — ARM and AMD have their own memory-disambiguation predictors, but with different designs: ARM's has no counters at all, and AMD's is indexed by physical address rather than PC bits, which the authors note would change (and likely complicate) the attack. The paper leaves an AMD-specific version for future work.
Q12What did the authors report to Intel, and what's left open?▾
They disclosed the MDU vulnerability to Intel under a 90-day disclosure period; Intel confirmed it and reiterated the importance of side-channel-resistant code. Open questions include MDPeek's applicability to Intel TDX and future TEEs, hardware-level fixes (e.g. dynamically detecting unresolved store-load pairs), and whether similar attacks are practical on AMD's physical-address-indexed predictor.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
MDPeekThe paper's attack: probing MDU counter state via timing to recover secret-dependent branch directions in SGX, bypassing flushing and balancing.
Memory Disambiguation Unit (MDU)256 4-bit counters, indexed by a load's low 8 PC bits, predicting whether that load can bypass an address-pending store.
Enable logicThe conditions under which the MDU makes a prediction at all — a delayed, unresolvable store-load pair with both in the ROB.
Update logicThe conditions under which the MDU actually changes a counter's value after the true dependence is resolved.
Delay capacityThe maximum instruction distance an instruction (or chain) can keep a store's target address unresolved, measured empirically per instruction type.
Def / LS distanceDef distance = gap from a store's address-defining instruction to the store; LS distance = gap from the store to the following load.
Store-to-load couplingMDPeek's proposed defense: an explicit, cheap arithmetic dependency between a store and load's addresses that removes the CPU's need to predict.
Supporting terms
ROB (Reorder Buffer)Holds in-flight instructions to enable out-of-order execution with in-order retirement; 224 entries on Skylake.
Branch balancingMaking both paths of a secret-dependent branch identical in pages touched, instruction type/count, and store-PC alignment.
Microarchitectural flushingClearing known-leaky hardware state (cache, BPU, prefetcher) at SGX context switches.
SGX-StepAn attack framework using page-table manipulation to interrupt an enclave deterministically at page granularity.
Machine clearA pipeline rollback triggered by a mispredicted memory dependence (or other speculation failure), detectable via the MACHINE_CLEARS.COUNT PMC.
BEEA sub-stepThe subtract/shift phase of the Binary Extended Euclidean Algorithm, whose branch direction MDPeek recovers to reconstruct RSA primes.
Speculative Store Bypass (SSB) / SSBDThe underlying speculative mechanism behind Spectre-V4, and the Intel control bit that can disable it (and the MDU).
