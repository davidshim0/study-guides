SOSP 2026 · A Field Guide

Blame the fallback, not every dependency that touched the error

A failed downstream call can silently take down a critical service. This is the plain-English story of RPCShield, a static analysis deployed across 6,000+ Uber microservices that finds exactly which dependency is to blame — before it causes an outage.

📄 "RPCShield: Defending Microservices Against Cascading Failures" · Chabbi et al. 🎓 Distributed-systems basics assumed — the primers cover the rest ⏱ ~30 min read
🔗

A dependency is only to blame for a failure if the endpoint would have SUCCEEDED had it (and everything after it) succeeded — not merely because its error passed through on the way out.
Ask "but for this call failing…?" — don't just trace where the error went.

Before you begin

Quick glossary, then the primers

The paper leans on a handful of acronyms from the start. Skim these once, then work through the primers below — collapsed by default, open any that look unfamiliar.

Quick glossary — the acronyms you'll see everywhere

1Microservices and RPCs▾

A microservice architecture splits one big application into many small, independently deployed services that talk to each other over the network via RPCs. Uber runs over 6,000 of them, handling tens of trillions of RPCs a week.

Each service exposes inbound endpoints (functions other services call on it) and may issue outbound RPCs (calls it makes to its own dependencies). A single inbound request can trigger a chain of outbound calls several services deep.

Now you're ready: RPCShield analyzes, for one service at a time, how its inbound endpoints react when its own outbound RPCs fail.
2Fail-open vs. fail-close▾

When an outbound RPC fails, the calling code has two broad choices: recover gracefully (return cached data, a default, or a partial result — fail-open) or propagate the failure upward, making the caller's own endpoint fail too (fail-close).

Fail-close isn't automatically wrong — sometimes a service genuinely cannot proceed without that dependency. It only becomes a problem in a specific circumstance covered next.

Now you're ready: the whole paper is about detecting fail-close dependencies in code and deciding which of them are actually dangerous.
3Criticality tiers and failover preemption▾

Uber classifies every service into a tier from T0 (most critical infrastructure) to T5 (test/auxiliary). During a regional failure or capacity crunch, Uber's differentiated failover design frees capacity by preempting (shutting down) lower-tier services to give critical ones room to run.

This only works if a T1 service doesn't secretly depend on a T4 service staying up. If it does, preempting the T4 service takes the "critical" T1 service down with it — the exact failure mode the paper targets.

Now you're ready: a fail-close violation is a fail-close dependency where the caller's tier is strictly more critical than the callee's — a real safety hazard for this preemption strategy.
4Static call graphs, briefly▾

A call graph is a structure recording which functions can call which others, built by reading source code rather than running it. Following a call graph from an inbound endpoint out to an outbound RPC site traces every syntactically reachable path between them — an over-approximation that includes some infeasible paths, later pruned away (e.g., by SCCP-based reachability analysis).

Building an accurate call graph is genuinely hard — virtual/interface calls, dependency injection, and lambdas all obscure who calls whom. RPCShield's Go implementation builds this graph in under 15 seconds even for services with over a million call-graph nodes.

Now you're ready: RPCShield's "call path" is just a route through this graph, from an inbound handler to a place where an outbound RPC's result is consumed.
5Counterfactual ("but-for") reasoning▾

Courts use a "but-for" test for causation: would the harm have happened but for this specific act? Apply the same idea to code: would this endpoint have succeeded had this specific RPC (and everything after it) succeeded instead?

This distinguishes "the error passed through here" (mere reachability) from "this call is actually why we failed" (causation) — crucial when a handler makes several calls and only one of them is truly responsible.

Now you're ready: RPCShield's entire formal definition of fail-close (§3 of the paper) is this counterfactual test, made precise.
6Gray failures and cross-system interaction bugs▾

A gray failure is a defect that stays invisible during normal operation and only surfaces under a specific, rare condition — like a fail-close dependency, which behaves fine until the one day its dependency actually goes down.

Prior research at Google/Azure/AWS found unhandled error propagation across service boundaries to be a leading cause of production incidents — exactly the bug class RPCShield targets, but before it ships.

Now you're ready: RPCShield exists because you can't wait for the rare failure to observe the bug — you have to find it by reading the code.
7Why not analyze the whole fleet at once?▾

The obvious approach — trace an error from where it originates in one service, across the network, to where a user notices it in another — requires a consistent snapshot of every service's source at once, a call graph spanning RPC and language boundaries, and re-analysis whenever any service changes. At 6,000+ services this is untenable.

RPCShield's key move is showing that the property it cares about doesn't require this: it only needs to look inside one service at a time.

Now you're ready: this per-service decomposition is the paper's central scalability insight — everything else follows from it.
8Go errors vs. Java exceptions▾

Go's idiom returns an explicit error value from every fallible call; a function must check it and decide what to do — errors are data, visible in the code's structure. Java instead throws exceptions, which propagate implicitly up the call stack until some catch block intercepts them.

Both are analyzable, just differently: Go needs data-flow tracking of nil-ness, Java needs tracking of which exception types survive each try/catch.

Now you're ready: RPCShield ships two separate implementations of the same formal model — one per language idiom (§5).
The whole story in one place

RPCShield in a nutshell

The problem, the formal fix, and how it scales to a 6,000-service fleet.

When a handler calls an outbound RPC and something goes wrong, a naive analysis (taint tracking, "does the error reach the return statement?") blames every RPC whose error could possibly reach an error exit. But real handlers often try a primary RPC and, if it fails, fall back to a secondary one — and only the fallback's failure should be blamed, not the primary's, since the primary's failure alone is recoverable.

RPCShield's fix is a precise, counterfactual definition: endpoint L has a fail-close dependency on an RPC event if there exists some request where (1) that RPC failed and the endpoint returned an error, (2) intervening to make that RPC (and everything after it) succeed would have made the endpoint succeed, and (3) it's the last RPC in the trace to fail. That third condition is what correctly attributes a fallback pattern to the fallback, not the primary.

The second insight is what makes this tractable at Uber's scale: fail-close is a property of one service's own code — the oracle abstraction means a dependency's failure only matters through the success/failure outcome it hands back, never through why it failed. So the property decomposes into thousands of independent, parallelizable, intra-service analyses — no cross-service, cross-language call graph required.

Static analysis has no runtime oracle to consult, so RPCShield substitutes calling contexts for program states and control/data-flow "what-if" analysis for the counterfactual: assume the RPC fails (and later calls succeed) — does an error exit? Then assume it succeeds — does a success exit become reachable? Four checks per (function, call site) — reachability, non-suppression, attributability, causation — compose along a call path into one verdict.

The payoff: deployed across 6K+ Go and Java microservices, RPCShield has found over 3,800 cross-tier fail-close violations, of which service owners have fixed more than 1,300, at a manually-verified false-positive rate around 5%. In 2025, after over a year in production, zero production incidents were attributed to a cross-tier fail-close violation — a failure class that had recurred roughly ten times a year before. The paper is careful to flag this as a correlation, not a proven causal effect: tiering/re-tiering and other reliability work were happening concurrently, so the drop to zero can't be attributed to RPCShield alone.

🔶 Key takeaways

  • Naive taint analysis blames every RPC an error touches; RPCShield's counterfactual test blames only the RPC that caused the failure.
  • A fallback pattern (try A, then B on failure) is fail-close only on the last failing call — the paper's "last-failure" rule.
  • Fail-close is a mechanism, a fail-close violation is a policy breach: it's only a problem when a more-critical caller depends on a less-critical callee.
  • Because the oracle only sees success/failure, the property decomposes into independent per-service static analyses — no whole-fleet call graph needed.
  • Each (function, call site) is checked against four conditions: reachability, non-suppression, attributability, causation.
  • Deployed at Uber: 3,842 violations found, 1,359 fixed, ~5% false-positive rate, zero attributed incidents in 2025 (correlation, not proven causation).
Six everyday pictures

How to think about RPCShield

Each stands alone — read in any order. Every card names where the picture stops being true.

The core idea · Counterfactual attribution

The backup generator

Main power fails; the backup generator kicks in and the lights stay on — no outage. But if the backup also fails, the building goes dark, and you'd rightly blame the generator's failure, not the original outage (which power failures happen all the time and are recoverable). RPCShield reasons the same way about a primary RPC and its fallback: only the last thing that had to fail for the outcome gets the blame.

Where it breaks: if two independent systems must both fail together for the lights to go out (a conjunctive check), there's no single "last" point of blame — the model falls back on program order to pick one, which is a modeling compromise, not a physical truth (see FAQ Q7).
§3.2 · Counterfactual causation

A detective's "but for" test

A detective doesn't just note that a suspect was near the scene (reachability) — they ask "would the crime still have happened had this person been elsewhere?" If yes, that suspect isn't the cause. RPCShield's Interv(O,U) is exactly this: replay the request with just this one RPC (and everything after it) forced to succeed, and check whether the endpoint's fate actually changes.

Where it breaks: a detective reasons about one crime scene; RPCShield's "replay" is a static what-if over a control-flow graph, not a real re-execution — it can only be as precise as the alias and branch analysis backing it (§4.1's soundness discussion).
§2.2 · Tiering & failover

A VIP tied to the general line

An airline can bump economy passengers to make room during overbooking — unless, unbeknownst to the gate agent, the VIP's connecting flight is crewed by someone in the economy cabin being bumped. Preempting "non-critical" capacity is only safe if nothing critical secretly needs it. That's the whole rationale for flagging cross-tier fail-close: it's the hidden thread tying the VIP to the general line.

Where it breaks: the VIP metaphor implies malice or oversight; most fail-close dependencies are just faithful, well-intentioned error reporting that happens to cross a tier boundary the code owner didn't design against (§2.2).
§3.3 · Per-service locality

Grading essays without reading the bibliography

To judge whether an essay's argument holds together, you don't need to verify every fact in its footnoted sources — you only need to know whether each citation "checked out" (true/false) as the essay's author believed. RPCShield treats a dependency the same way: it only cares whether the outbound RPC returned success or failure, never why. That's what lets each service be graded — I mean, analyzed — on its own, in parallel.

Where it breaks: some real incidents are genuinely multi-hop (a fail-close chain through two services). RPCShield deliberately reports each hop separately rather than chaining them (§7) — a limitation, not an error.
§4.5 · Fresh errors & control dependence

A compass, not a paper trail

Sometimes an error has no paper trail — the code just constructs a brand-new ErrNotFound instead of forwarding the RPC's original error object. You can't follow a value that was never carried forward. Instead you follow the guard: which condition, checking which RPC's outcome, is the reason this return statement is even reachable? That's a compass bearing, not a paper trail — control dependence instead of data dependence.

Where it breaks: the compass can point past irrelevant guards (like a string comparison on mode) — RPCShield has to specifically skip non-RPC conditions to find the right bearing (Appendix A.2.3).
§6.2 · False positives / negatives

A pre-flight checklist vs. flying and seeing

A pre-flight checklist (static analysis) catches problems before takeoff but might flag a switch that's actually fine because the manual didn't anticipate one specific wiring, or miss a fault that's only visible once you're airborne. RPCShield's manually-reviewed 5% false-positive rate is the checklist's "false alarm" rate; its 2.5% estimated gap against a production-traffic baseline is the "faults you'd only see in flight."

Where it breaks: the "flying and seeing" baseline (runtime dependency analysis) isn't ground truth either — it infers dependencies from correlation, not causation, and can't attribute a violation to one call site, so RPCShield's 2.5% is not a bound in either direction — neither a floor nor a ceiling on its true miss rate (§6.3).
The full explanation

How it actually works

From the formal model to the four-phase pipeline, with the paper's key mechanics visualized.

1 · The formal model — traces, oracles, and intervention

An endpoint's execution produces a trace: a sequence of outbound RPC events, each recording the program state, target dependency, and outcome, ending in an inbound response (Ok or Error). Since dependencies are non-deterministic, an oracle fixes the outcome of every RPC for one particular run — a choice of oracle is a choice of failure scenario.

The intervention Interv(O,U) takes a trace and a position U, and produces a new oracle that agrees with the original up to U, then forces success for the U-th RPC and everything after it. Comparing the real trace's response to the intervened trace's response is the counterfactual test (Definition D1). A fail-close dependency (Definition D2) additionally requires that in the witnessing trace, the tested RPC is the last one to fail — this is what correctly blames a fallback over its (also-failing) primary.

2 · From formal model to static analysis (§4.1)

Static analysis has no runtime states or oracles to query, so RPCShield substitutes two things:

Model conceptStatic-analysis stand-in
Program state at an RPC eventCalling context — a chain of function calls from the inbound endpoint to the outbound RPC site, built over a whole-program call graph
Oracle / interventionA what-if analysis: assume the RPC under test fails (all later RPCs succeed) → check for a reachable error exit; then flip it to succeed → check for a reachable success exit
⚠
Asynchrony complicates the context. An async RPC is issued at one point but its outcome is consumed at a separate wait point (a Wait() call, a channel receive). The analysis synthesizes one calling context that splices the spawned task's outbound segment onto the wait point, so it can be traversed exactly like a synchronous call chain (§4.1, §5.1).

3 · The per-function summary — four checks (§4.5)

For each function f on a call path and each call site c within it, RPCShield asks: if c's RPC fails, does the failure survive to f's exit, and does it genuinely trace back to c?

  1. Reachability — at least one return (or throw) statement is reachable when c's call fails.
  2. Non-suppression (witness) — on that path, the error was not overwritten to a success value.
  3. Attributable — the returned error is traceable to c, either by data flow (derived from c's value) or control dependence (the return is reached because a branch on c's error took the failing arm).
  4. Causation — when c succeeds instead, a non-error return becomes reachable, confirming c actually controls the outcome (not just correlates with it).

If all four hold, f is fail-close with respect to c. Summaries are cached per (function, call site) and reused across every call path that shares that function — since many paths pass through common helpers, this caching is what keeps the analysis tractable on million-node call graphs.

4 · Scaling the call graph — RTA, async, DI, lambdas (§5)

Standard Rapid Type Analysis (RTA) resolves a virtual call only to types actually instantiated on some reachable path — precise enough to be useful, cheap enough to scale, unlike whole points-to analysis. But production code breaks three of RTA's assumptions, and each language's implementation patches a different set:

Gap in standard RTAGo's fixJava's fix
Async control flow invisible to the call stackGraph enrichment: synthetic edges from goroutine wait points (Wait(), channel receive) to task closuresModel the CompletableFuture DAG; resolve continuations to their lambdas
Stubs instantiated by a framework, not application codeRecover bindings from constructor type signaturesScan Spring @Configuration/@Bean methods and @Qualifier annotations
Indirect calls through higher-order functionsN/A (Go closures tracked via SSA)Match functional-interface call sites to type-compatible reachable lambdas
💡
Why graph enrichment, not a new analysis? An async pattern with an explicit wait (a Wait() call, a future's continuation) is behaviorally equivalent to a synchronous call followed by error consumption. Adding synthetic edges lets the same synchronous error-flow analysis traverse async code — no separate async-aware analysis was needed (§5.1). Go's coverage here (goroutines, errgroup, CFF) is fully productionized; the paper notes that Java's async-path handling, while modeled, has not been fully productionized.

5 · Outbound resolution and the tier policy (§4.6, §2.2)

Finding a fail-close dependency is only half the job — RPCShield must also know which deployed service the outbound stub targets and its tier. It exploits IDL-generated type information (stub type → service interface → build target → deployed service) as the primary resolver, falling back to config-file parsing or name matching for protocols like HTTP that lack compile-time contracts.

Only after resolution does policy enter the picture: the analysis itself is policy-agnostic (it labels every dependency fail-close or fail-open), and a separate comparison step flags a dependency as a violation only when the caller's tier is strictly more critical than the resolved callee's tier.

Follow the numbers, step by step

Worked examples

Four traces through the paper's own numbers: an attribution by hand, the fleet-wide violation breakdown, why per-service analysis is unavoidable at this scale, and the accuracy/remediation numbers.

① Attributing Listing 1's fallback by hand

Handler tries rpcA; if it fails, tries rpcB; if that also fails, returns a fresh ErrNotFound. Take the oracle where both calls fail.

  1. Witness trace Q: rpcA fails → rpcB fails → response = Error. Both RPC events have outcome failure (D1.1 satisfied for both).
  2. Test rpcB (U=2): intervene so rpcB succeeds. The handler returns r2, nil → response flips to Ok. causes(2,Q) holds. No RPC follows event 2, so the last-failure condition (D2.2) holds vacuously. rpcB is fail-close.
  3. Test rpcA (U=1): intervene so rpcA succeeds. The handler takes the early-return branch and returns r1, nil → response also flips to Ok. causes(1,Q) holds too.
  4. But check D2.2 for rpcA: the later event (rpcB, at position 2 > 1) has outcome failure in the real trace Q — the last-failure condition fails. rpcA is not blamed.
  5. Result: RPCShield's report names only rpcB — exactly the intuition that a fallback, not the thing it's falling back from, is the actionable dependency.
🔶
Insight: reachability alone (does the error data-flow to the return?) would have blamed both. The last-failure rule is the one extra check that turns a noisy taint analysis into an actionable one.

② Reading the fleet-wide violation table

Table 4 breaks 3,842 detected cross-tier violations down by caller/callee tier over a 20-month deployment.

  1. Total across all tier pairs: 68 (T0 callers) + 2,545 (T1 callers) + 1,229 (T2 callers) = 3,842 violations.
  2. T1 dominates: 2,545 / 3,842 ≈ 66% of all violations originate from T1 (critical user-facing) services — matching the paper's observation that T1 alone generates ~66% of all cross-tier traffic to lower tiers.
  3. The single largest cell is T1 → T2: 1,701 violations, or 1,701 / 3,842 ≈ 44% of the total — a critical service quietly depending on a "merely business-critical" one.
  4. Resolution: 2,540 of 3,842 (66%) reached a terminal ticket state; of those, 421 were fixed in code and 938 by re-tiering the callee, for 1,359 total remediated (matches "more than 1,300").
💡
Re-tiering (938) outpaces code fixes (421) roughly 2-to-1 — often the fastest safe fix isn't touching the error-handling code at all, it's admitting the callee actually deserves a higher tier.

③ Why per-service analysis is the only tractable option

Corpus statistics (Table 2, §6.2) show just how large "one service" already is at Uber.

  1. Median Go service: 2.8M lines of code (monorepo-wide transitive build deps); P95 reaches 35.4M lines.
  2. Call graph size at P95: ~1.2M nodes and 209.7M edges for Go; Java is smaller (P95 ≈ 31.9K nodes, 355.1K edges) but still substantial.
  3. Now imagine chaining that across services. A whole-fleet call graph spanning 3,944 analyzable services, two languages, and RPC boundaries would need to be rebuilt from a consistent snapshot every time any one of 6,000+ services changes.
  4. Per-service analysis sidesteps this entirely: the oracle abstraction (§3.4) means a callee's own fail-close behavior can never influence whether the caller is fail-close on it — so each service's ~1M-node graph can be analyzed independently, in parallel, and re-analyzed only when that one service changes.
🔶
Insight: the scalability isn't an engineering afterthought bolted onto a whole-fleet analysis — it falls directly out of the formal definition's locality property (§3.4).

④ Accuracy and what happens after a report

Numbers from the intrinsic (§6.2) and extrinsic (§6.3–6.4) evaluations.

  1. False positives: manual review of the last 200 detected Go violations found a rate < 5%; of the true positives actually filed as tickets, zero were rejected by the owning team as false alarms.
  2. False negatives (estimated): comparing against an independent production-traffic-based runtime analysis as a reference set, RPCShield's reported set differs from that method's by about 2.5% — though that baseline itself isn't ground truth (it infers dependencies from correlation, not causation, and is incomplete), so 2.5% is not a bound in either direction on RPCShield's true miss rate.
  3. Time to fix, once picked up: a developer survey found 72% of fixes took 5 days or fewer (21% under 1 day); yet the median ticket lifetime is 60 days — meaning the bottleneck is queueing behind other priorities, not the fix itself.
  4. Shift-left effect: once RPCShield was added as a commit-time CI check, of 449 violations it flagged before merge, 101 (22%) were fixed before the code ever shipped — violations that never reached deployment or needed a ticket at all.
💡
Precision (5% FP) is what earned developer trust; the 60-day median ticket lifetime is a reminder that even a trusted, accurate tool still competes with a team's existing roadmap.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
A T2 service calls a T1 service and propagates that dependency's errors unmodified. Is this a fail-close violation?
Show answer
No. This is a fail-close dependency (the caller does fail when the callee fails), but it's not a violation, because the callee (T1) is strictly more critical than the caller (T2) — the policy only flags a caller depending on a strictly less critical callee. A less-critical service failing along with a more-critical one it depends on is expected and safe.Misconception: conflating "fail-close dependency" (a code-level, mechanism-level fact) with "violation" (a tier-policy judgment applied afterward). The analysis reports the former for every dependency; the latter only for cross-tier cases in the wrong direction (§2.2).
Problem 2 · medium
A handler makes two unconditional RPCs, A and B, and returns an error if either fails (a disjunctive check, like Listing 5). Which RPC(s) does RPCShield blame?
Show answer
Both, independently. Take a witness where A fails and B succeeds: the disjunction is true (Error), and intervening on A alone flips it to Ok; since B is the only later event and it already succeeded, the last-failure condition holds. Symmetrically, a witness where B fails and A succeeds blames B. Because the two RPCs are unconditional and independent, each can individually be "the last thing that had to fail."Misconception: assuming a fallback-style last-failure rule always yields exactly one culprit. It only does that when failures are causally chained (a primary/fallback pattern); independent disjunctive checks can name multiple, separately-witnessed causes.
Problem 3 · hard
Now suppose the same handler uses a conjunctive check — it returns an error only if both A and B fail (Listing 6). Walk through why RPCShield blames only B, and why that's a compromise rather than a clean derivation.
Show answer
Test A: the only witness where A fails and the endpoint returns Error also requires B to fail (otherwise the conjunction is false and the endpoint returns Ok) — so B, a later event, also fails, which violates the last-failure condition (D2.2). No valid witness exists for A. Test B: let both fail; B is the last event, so D2.2 holds vacuously, and intervening on B alone (leaving A's failure in the prefix) flips the conjunction to false → Ok. So B passes. But both failures were equally necessary — B is blamed only because it happens to come last in program order, which the paper admits is "causally arbitrary" (§7). RPCShield's actual implementation departs from the model here: for data-dependent aggregation it attributes every contributor, applying the strict last-failure rule only to the control-dependent fallback shape.Misconception: assuming the formal model always identifies the "true" sole cause. For genuinely conjunctive failures, program order — not causal necessity — breaks the tie, and the paper is explicit that this is an intentional simplification, not a causal discovery (§7, Appendix A.1.4).
Problem 4 · medium
Why can RPCShield analyze one service at a time instead of building a fleet-wide call graph spanning RPC and language boundaries?
Show answer
Because the oracle in the formal model abstracts every outbound call to a single success/failure outcome (§3.1) — the caller's response depends on the oracle only through those outcomes, never through how or why a dependency failed. So whether dependency P is itself fail-close on some further downstream service cannot influence whether the caller is fail-close on P (§3.4, "fail-close is a local property"). Each service's analysis only needs to know "did my RPC succeed or fail," which its own oracle already supplies — no need to inspect the callee's source.Misconception: thinking scalability came from an engineering trick (sampling, caching, approximation). It's a direct mathematical consequence of the oracle abstraction in the formal definition — the locality is a property of the model, not an implementation shortcut.
Problem 5 · easy
A function catches an exception and re-throws it as a different exception type (Listing 18, Java). Does this count as suppression?
Show answer
No. Suppression means the exception no longer exits the function at all — e.g., a catch block that swallows it and returns a normal default value (Listing 17). Re-throwing under a different type still lets an exception exit the function, so it still counts as propagation. RPCShield's per-function summary explicitly records this as a type transformation (Q → R) rather than removing Q from the outgoing exception set, and attribution follows through the wrapping constructor's cause argument.Misconception: assuming "there's a catch block here" implies the error was handled. A catch block that transforms and re-throws is not handling — only a catch that returns a normal value without re-throwing suppresses the failure (§5.2, Appendix C.2).
Problem 6 · medium
RPCShield reports a 5% false-positive rate. Name two of the three sources the paper attributes these to.
Show answer
Any two of: (1) error handling that happens inside library code the static analysis doesn't examine; (2) paths through dead code that can never actually execute; (3) imprecision in virtual-call resolution that includes call targets that are syntactically reachable but infeasible in practice.Misconception: assuming false positives mostly come from the counterfactual logic itself being wrong. In practice they trace back to call-graph and reachability imprecision — the same soundness trade-offs (may-analysis, no heap-escape tracking) any interprocedural static analysis makes (§4.1, §6.2).
Problem 7 · hard
The paper reports "0.83% of inbound-to-outbound dependencies hit the permutation threshold" and "SCCP pruning removes 88% of candidate paths." What problem do these two numbers each solve, and why are both needed?
Show answer
Path enumeration between an inbound endpoint and an outbound RPC site can explode combinatorially — many different orderings of the same set of intermediate functions are really the same underlying path. Permutation detection (fingerprinting paths by XOR-ing function pointers, so order-independent duplicates collapse) caps that blow-up; only 0.83% of dependencies are large enough to even hit this safeguard, but without it, those rare cases would exhaust memory and kill the analysis. Separately, SCCP-based reachability pruning discards paths that are syntactically present in the call graph but provably infeasible given the code's actual branch conditions — this removes 88% of candidates overall, and a median of 99% in the roughly one-third of the corpus with heavily conditional code. One controls combinatorial explosion from path structure; the other controls false candidates from static over-approximation — different failure modes, both necessary for scalability.Misconception: treating "path explosion" as a single problem with a single fix. It's actually two distinct sources (representational duplication vs. infeasible branches), each requiring its own technique (§4.4, §6.2).
Problem 8 · medium
A team requests a "policy exception" instead of fixing or re-tiering after a fail-close violation is reported. Is this evidence the tool produced a false positive?
Show answer
Not necessarily. RPCShield's classification of "fail-close" is a code-level fact, independent of policy; the tier-violation flag is a separate judgment about whether that fact is currently acceptable. A team might have a legitimate reason the violation is low-risk in practice (the endpoint is non-critical despite living in a critical service, or it's slated for deprecation) — the paper explicitly tracks "deferred resolution" (31.93% of acknowledged violations) as a distinct, non-dismissive outcome from a false positive. Zero tickets in the survey period were rejected by owning teams as false positives.Misconception: assuming every unresolved or exception-requested report is a tool error. The paper's remediation taxonomy (Table 5) deliberately separates "deferred" and "closed without attribution" from actual false positives, which are tracked separately via manual review (§6.3).
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does "fail-close" mean?▾
An endpoint is fail-close on a specific outbound RPC if, for some request, that RPC's failure is the last failure in the trace and is what caused the endpoint to return an error — meaning had that RPC (and everything after it) succeeded, the endpoint would have succeeded too. It's a code-level, per-call-site property, not a vague "this service seems fragile" judgment.
Q2Isn't fail-close always bad?▾
No — most fail-close dependencies in the fleet are benign. A service faithfully reporting a downstream failure to its own caller is often exactly correct behavior. It only becomes a violation under Uber's specific policy: a more-critical service (T0–T2) must not fail-close on a strictly less-critical one, because that breaks the assumption that less-critical services are safe to preempt during failover.
Q3Why can't a taint analysis just do this?▾
Plain reachability ("can this RPC's error reach an error return?") blames every RPC an error touches, including ones that were actually recovered by a later fallback (Listing 1's rpcA). RPCShield adds the counterfactual "but-for" test plus the last-failure rule specifically to exclude the recovered primary and blame only the true cause.
Q4How does RPCShield avoid needing to analyze the whole 6,000-service fleet at once?▾
The formal model's oracle abstracts every outbound call to a success/failure outcome — a dependency's own internal fail-close behavior can never influence whether the caller is fail-close on it. That makes fail-close a property decidable from one service's own source code, so each service is analyzed independently and in parallel, with no cross-service or cross-language call graph required.
Q5Does RPCShield handle asynchronous code (goroutines, futures)?▾
Largely, yes. It identifies the wait point where an async task's outcome is actually consumed (a Wait() call, a channel receive, a CompletableFuture continuation) and enriches the call graph with synthetic edges connecting the task's outbound RPC to that wait point — letting the ordinary synchronous error-flow analysis traverse it unchanged. Go's async patterns (goroutines, errgroup, CFF) are fully productionized this way; the paper notes that Java's CompletableFuture support exists in the model but its async-path analysis has not been fully productionized.
Q6What happens when an error is freshly constructed rather than passed through?▾
When no data-flow chain connects the returned error to the RPC's error value (e.g., a handler returns a hardcoded ErrNotFound), RPCShield falls back to control dependence: it walks outward from the return statement to find the nearest condition that checks an RPC-derived error, skipping unrelated conditions (like a string comparison), and attributes the fresh error to that RPC.
Q7What if two RPCs must both fail for the endpoint to fail (a conjunctive check)?▾
The model's last-failure rule then falls back on program order, formally blaming only the later of the two calls — even though both failures were equally necessary. The paper acknowledges this is "causally arbitrary" in that specific pattern (§7). In practice, the implementation departs from the strict rule here: when the returned error is data-dependent on both RPCs, it attributes every contributor rather than picking one.
Q8How accurate is RPCShield in practice?▾
Manual review of the last 200 detected Go violations found a false-positive rate under 5%, and no ticket filed against a true positive was rejected by the owning team. Compared against an independent, production-traffic-based runtime analysis, RPCShield's reported set differs from that method's by about 2.5% — though that baseline is itself imperfect and incomplete (it infers dependencies from correlation, not causation), so this 2.5% figure is not a bound in either direction on RPCShield's true miss rate.
Q9Does it run once, or continuously?▾
Both. A recurring pipeline scans T0–T2 services — 1,399 of them in the paper's extrinsic evaluation benchmark, which excludes stateful/storage services and services without analyzable build targets — and files tickets for cross-tier violations. Separately, a commit-time check runs on every code review, surfacing about 10 new violations a week; 22% of those are fixed before the change even merges, avoiding the need for a ticket at all.
Q10Can fail-close dependencies chain across multiple services?▾
In principle, yes — if A is fail-close on B, and B is fail-close on C, a failure of C can surface at A. RPCShield deliberately does not stitch these together automatically, because each hop is witnessed by a specific request and code path, and there's no guarantee the request A sends to B drives B down its witnessing path. It reports each hop separately; in practice, since every hop in a chain must be fail-close for it to matter, fixing any single hop breaks the chain (§7).
Q11What kinds of criticality problems does RPCShield not catch?▾
Anything not expressed as error propagation. A callee that stays technically available but misses its latency target can still blow a caller's SLO; a low-tier caller can exhaust a high-tier callee's capacity or rate limits. Both are real "criticality inversions" invisible to an error-propagation analysis — they'd require reasoning about latency and request volume instead (§7).
Q12What's the measured business impact?▾
In 2025, after over a year of deployment, no production incident was attributed to a cross-tier fail-close violation — a category that had caused roughly ten high-severity, customer-facing outages a year from 2020–2023. The paper is explicit that this is a correlation, not a proven causal effect: tiering/re-tiering and other reliability work happened concurrently, so the drop can't be attributed to RPCShield alone. Separately measured, Uber has reclaimed roughly 1 million of 4 million CPU cores by oversubscribing lower-tier services onto spare capacity, a move whose safety depends on eliminating cross-tier fail-close violations.

Glossary, results, and further reading

Every term in one place, the headline numbers, then a path to go deeper.

Core terms
Fail-close dependencyA code-level property: an inbound endpoint's failure is caused by a specific outbound RPC's failure, per Definition D2's counterfactual + last-failure test.
Fail-close violationA fail-close dependency where the caller's criticality tier is strictly higher than the callee's — the policy-level judgment RPCShield flags for remediation.
Counterfactual causationThe "but-for" test (Definition D1): an RPC event causes the endpoint's error if intervening to make it (and later RPCs) succeed would have changed the response to Ok.
Last-failure condition (D2.2)The tested RPC must be the last one to fail in the witnessing trace — what correctly attributes a fallback pattern to the fallback, not the primary.
OracleA function resolving each outbound RPC's non-determinism to success/failure for one execution — a choice of oracle is a choice of failure scenario.
Calling contextThe static stand-in for a runtime program state: a chain of function calls from an inbound endpoint to an outbound RPC site.
Wait pointWhere an asynchronous task's outcome is actually consumed (vs. its invocation point) — the relevant error-handling code surrounds this, not the spawn.
RTA (Rapid Type Analysis)The call-graph construction algorithm: resolves virtual/interface calls to types actually instantiated on some reachable path.
Supporting terms
Gray failureA defect invisible during normal operation, surfacing only under a rare condition — fail-close dependencies are a textbook example.
Criticality tier (T0–T5)Uber's classification of service importance; T0 most critical, T5 least. Determines who may be preempted during failover.
Attribution (data vs. control dependence)Two ways to trace a returned error back to an RPC: the value flows from it directly, or a branch on its outcome controls reachability of the return.
Per-function summaryA cached, reusable verdict for one (function, call site) pair: does an error from this call site survive to this function's exit, attributably and causally?
CFF / errgroup / raw goroutineThree Go concurrency patterns RPCShield handles via call-graph enrichment, each with a different wait-point shape.
Set / permutation fingerprintingDeduplicating call paths that are the same set of functions in a different order, to contain combinatorial path explosion.
Commit-time analysisRPCShield running on a code review's diff, surfacing new violations before they merge — the "shift-left" extension of the recurring pipeline.
