PLOS 2026 · A Field Guide

Trace once, then fork your way into a thousand tiny tests

A system runs for hours. Somewhere inside it, one procedure misbehaves. This is the plain-English story of ACF, a tool that watches a long run once, then replays any single call from it as a cheap, isolated unit test.

📄 "ACF: Infrastructure for Debugging Long-Running Systems" · Vašut & Parízek 🎓 Some C/C++ and LLVM basics assumed — the primers cover them ⏱ ~20 min read
🔀

Don't single-step through an hours-long run. TRACE every call once, then FORK the running process at each call site to turn every recorded input into its own cheap, disposable unit test.

1What fault localization actually means▾

When a program misbehaves, fault localization is the process of narrowing "something is wrong" down to specific statements or inputs responsible. It's usually manual: reproduce the error, inspect logs, step through code.

Now you're ready: ACF automates the "narrow it down" part by turning one long, ambiguous run into many small, single-cause tests.
2Dynamic analysis and instrumentation▾

Dynamic analysis observes a program while it runs, rather than just reading its source. Instrumentation is how you do it: insert extra code (probes) that records events — here, procedure calls and their argument values — without changing the program's logic.

Now you're ready: ACF's probes are inserted by compiler plugins, so every call of a chosen procedure gets recorded automatically.
3AST vs IR — two views of the same code▾

Clang parses source into an AST (structure close to the source text — knows about types like this pointers and unsigned-ness). LLVM later lowers that to IR, a simpler, typed assembly-like form that's easier to rewrite mechanically but has lost some source-level detail.

Now you're ready: ACF needs both — a Clang plugin reads AST details the IR no longer has, and an LLVM IR pass does the actual code insertion.
4What fork() gives you for free▾

POSIX fork() clones a running process — memory, call stack, open state and all — into a new child process that continues from the exact same point. The clone is a perfect snapshot; the two processes then run independently.

Now you're ready: ACF forks right before a target procedure's call, so the child inherits a fully valid, hard-to-construct program state for free — no test-driver setup code needed.
5Procedure-level unit tests and call sites▾

A unit test exercises one procedure in isolation. A call site is a specific place in the code where that procedure is invoked — the same procedure may have several call sites, and each site may be reached many times at runtime with different arguments.

Now you're ready: ACF records distinct argument tuples for the target procedure, then forks at every dynamic call site for every one of those tuples — so a site invoked 50 times against 12 distinct recorded tuples can yield far more than 50 tests, not one test per call.
6IPC basics: shared memory and sockets▾

Separate processes can't just share variables; they need explicit channels. Shared memory is a fast region mapped into multiple processes; sockets pass messages, often used for control and synchronization.

Now you're ready: ACF's central server, hooklib, and each forked test child talk to each other over exactly these two channels to exchange recorded values and results.
7Replay vs fuzzing — two ways to pick test inputs▾

Fuzzing generates new, often random or mutated inputs to explore behavior the program hasn't shown you yet. Replay, by contrast, re-uses inputs actually observed at runtime — it can't discover new paths, but it's guaranteed relevant to the real bug.

Now you're ready: ACF is fundamentally a replay tool — every argument value it injects was really observed somewhere in the run — but because it injects recorded tuples at every dynamic call site, a given test can pair a real call location with a tuple that was actually recorded elsewhere, so not every individual test corresponds to something that literally happened together.
8Why long-running systems break interactive debuggers▾

Tools like GDB are built around single-stepping and breakpoints — great for short runs, painful when reaching the interesting moment takes hours, and worse when you need to go back and inspect an earlier point again.

Now you're ready: ACF's whole premise is to run the system a fixed, small number of times total — two trace passes plus one fork-testing pass — rather than re-running it from scratch for every hypothesis, then let a developer inspect any single recorded call without restarting the system.
The whole story in one place

ACF in a nutshell

The problem, the trace-then-fork fix, and what it bought in practice.

Debugging a system that runs for hours means every interactive-debugger iteration also takes hours: run, wait, inspect, tweak, re-run. Worse, you rarely know in advance which procedure calls, among possibly thousands, matter for the bug.

ACF's workflow splits the problem in two. First, dynamic analysis runs the target system twice: a first full run that just lists which procedures get called, then a second full run that captures every argument tuple for the one procedure the developer picks. Second, ACF exploits fork(): it runs the system a third time, and at every dynamic call site of the target procedure it forks the live process once for each distinct recorded argument tuple, injecting that tuple before letting the call proceed. Each fork reuses a perfectly-set-up state — no test driver, no reconstructed state — because the fork already has the real call stack and heap; that call-site/tuple pairing becomes one isolated test.

The result is a report: one row per test executed, pass or fail, pointing back to the exact argument values responsible. A monolithic, hours-long execution becomes a table of small, independent tests a developer can scan for the one that stands out.

🔀 Key takeaways

  • The system runs three times per target procedure — two trace passes, then one fork-testing pass — but forking within that third run turns it into many independent tests in one go, instead of one full rerun per test.
  • Forking at the call site reuses the real, already-valid program state — sidestepping the hardest part of unit testing: constructing a realistic input state.
  • Built on LLVM/Clang: a Clang AST plugin extracts source-level detail, an LLVM IR pass inserts the actual probes.
  • Coverage is bounded by what was observed — ACF only injects argument values it actually recorded, though it may recombine a value with a call site where it wasn't originally seen; it doesn't invent unseen values (unlike fuzzers).
  • Current prototype: single-threaded only, limited data types (numerics, std::string, a little STL).
  • Evaluated on three real C/C++ systems: KeePassXC, GNU find, and the Yaga SMT solver.
💡
For the memory-tiering reader: this "trace once, replay a slice cheaply" pattern rhymes with instrumenting kernel hot paths (e.g. migrate_pages(), promotion/demotion decisions) with ftrace/eBPF and then re-driving just that function with recorded arguments — rather than re-running a whole workload to reproduce a tiering decision. ACF does it for userspace C/C++ via LLVM; the kernel analogue would need a fork-equivalent for kernel context, which is nontrivial. This connection is framing, not a claim from the paper.
Five everyday pictures

How to think about ACF

Each stands alone. Every card ends with where the picture stops being true.

Fork-based testing

Cloning the chef mid-recipe

Instead of writing out a whole new recipe (test driver) from scratch, you clone the chef at the exact moment the sauce is ready, then hand the clone a different spice to add. The clone already has every prior step done. ACF's fork() at the call site does exactly this: the forked test inherits a fully valid call stack and heap for free.

Where it breaks: cloning a kitchen with two chefs mid-conversation (multithreading) is much harder — ACF's released version only reliably handles single-threaded programs.
Two-phase dynamic analysis

Casting call, then wardrobe fitting

First you find out who's available (phase 1: list called procedures), then you bring back just the one actor you picked for detailed measurements (phase 2: capture that procedure's argument values). Doing it in two separate full runs avoids recording everything about everyone upfront in a single expensive pass.

Where it breaks: this costs three full runs of the system total (trace, capture, fork-test) — each as long as the original; the picture doesn't show that cost adding up on truly long jobs.
Deconstructing monolithic runs

A marathon video cut into sprint clips

A single hours-long recording is hard to scan. ACF chops the run into one short clip per observed call — each independently playable, each showing exactly one input and its outcome. Scanning a table of clips is much faster than scrubbing through the whole marathon.

Where it breaks: you only get clips of moments the camera actually caught — no clip exists for a call pattern the traced run never exercised.
Replay vs. statistical ranking

A lineup photo vs. a full reenactment

Statistical fault-localization tools (like Tarantula) compare many pass/fail test runs and rank suspicious statements from a distance — like studying a photo lineup. ACF instead reenacts calls using recorded inputs — real values captured somewhere in the run — letting the developer see actual behavior rather than a suspicion score, though a given reenactment may pair a real call location with a tuple originally recorded at a different site.

Where it breaks: ACF doesn't rank anything itself — a developer still has to scan the report and recognize which reenactment looks wrong.
vs. full-trace time-travel debuggers

Rewinding only the reel you filmed

Time-travel debuggers like Expositor let you scrub freely through an execution, but they need the whole trace recorded first — expensive for long runs. ACF instead keeps only argument tuples for one chosen procedure and regenerates the surrounding state by forking a live rerun — far cheaper to store.

Where it breaks: you can only "jump" to recorded call sites of the target procedure, not step forward/backward through arbitrary points — that finer-grained navigation is future work.
The full explanation

How it actually works

The two-phase trace, the three-piece architecture, and the fork-based test mechanics.

1 · Two-phase dynamic analysis

Both phases use the same static instrumentation, inserted once before any run. Phase 1 runs the system and just records which procedures get called — enough for the developer to pick one target by name. Phase 2 re-runs the system with recording switched on for that one target, capturing every argument tuple (and return value) at every call.

2 · Three-piece architecture

hooklib (runtime library) stores observed values and forwards them over IPC. Clang/LLVM plugins do the instrumentation — a Clang AST pass extracts source-level facts LLVM IR no longer carries (e.g. presence of a this pointer, which arguments are unsigned), handing that to an LLVM IR pass that actually inserts the hook calls. The llcap-server is the central coordinator: it launches the instrumented binary and manages tracing and testing via shared memory and sockets.

3 · Fork-based test execution, mechanically

  • Static instrumentation marks every call site of the target procedure in advance.
  • At runtime, just before the call executes, the process forks once for each distinct recorded argument tuple for that procedure; the parent continues normally between forks, and each child is one test.
  • Each child has one recorded argument tuple injected in place of the real arguments, then the call proceeds exactly as instrumented.
  • The child terminates right after the target procedure returns (also arranged by instrumentation) — so each test costs only the work inside that one call, not a restart of the whole system.
  • Per-test and global timeouts guard against hangs, since forked tests run real code that could loop or block.

This mirrors a performance trick already used in the fuzzer AFL++ (forking to skip process-startup cost), but ACF repurposes it for correctness — to obtain a realistic input state for free, not just for speed.

4 · The iterative loop (Algorithm 1)

while not done:
    instrument target procedure p
    trace(system) -- collect argument tuples V1..Vn
    tests = createTests(p, V1..Vn)
    for T in tests: run T, record pass/fail
    if all passed: done = validateFix()
    else: -- developer inspects failing tests, edits source

Everything except the marked lines — picking the target, inspecting failures, editing source, judging whether a fix is correct — is automated by ACF; those remaining steps stay with the developer.

Follow it through, step by step

Worked examples

The paper's own heartbeat bug, then three exercises built from Table 1's real numbers.

① The heartbeat service bug, end to end

Listing 1: a server echoes received payloads back to clients via two receive-send pairs at lines 17–19 (safe) and 21–24 (a CVE-2025-14847-inspired vulnerability).

  1. Select: developer marks recv_hb and send_hb as target procedures (Step 1).
  2. Trace: dynamic analysis records each call's arguments — for the first pair, len1 (actual received length) and resp1 (sent length); for the second, len2 and resp2 (Step 2).
  3. Generate tests: one test per observed receive-send pair — here, two scenarios (Step 3).
  4. Execute & compare: pair 1 shows resp1 == len1 (safe). Pair 2 shows resp2 (= hb_msg.length, client-controlled) can exceed len2 (the actual received bytes) — leaking uninitialized buffer content.
  5. Root cause: line 23 trusts a client-supplied length instead of the value actually returned by recv_hb at line 21 — the fix is to use len2, not hb_msg.length.
🔀
Notice the bug is only visible by comparing two different call sites of the same pair of procedures — exactly what tracing every call (not just one) and testing each separately exposes.

② Amortized cost per test, from Table 1

Running time reported includes a fresh build plus all three runs. Roughly, how much does each system "cost" per test?

  1. find: 65 minutes ÷ 70,225 tests ≈ 0.055 s/test.
  2. Yaga: 102 minutes ÷ 112,559 tests ≈ 0.054 s/test — nearly identical to find, despite Yaga being a very different kind of program (an SMT solver vs. a file-tree walker).
  3. KeePassXC: 18 minutes ÷ 23 tests ≈ 47 s/test — roughly 850× higher per-test cost.
  4. Why the gap: KeePassXC's 18 minutes is dominated by fixed overhead (building a GUI application, launching it, the single trace run) that isn't amortized over many tests, unlike find/Yaga where tens of thousands of forked tests share that fixed cost.
💡
The paper doesn't state this ratio explicitly — it's a straightforward recomputation from Table 1's own numbers, useful for judging where ACF's fork-based approach pays off most (high call-count targets).

③ A numeric oddity worth checking: does "tests = calls" hold?

Section 4's text states test count "corresponds to the number of calls observed at runtime." Table 1 reports both — do they match?

  1. find: calls = 265. 265² = 70,225 — exactly the reported test count.
  2. Yaga: calls = 360. 360² = 129,600 — but the reported test count is 112,559, about 13% lower.
  3. KeePassXC: calls = 211. 211² = 44,521 — wildly different from the reported 23 tests.
  4. Conclusion: the text's "tests correspond to calls" claim does not hold as a simple equality across all three systems in the paper's own table. It's closer to the paper's actual mechanism — forking at every dynamic call site for every distinct recorded argument tuple — where test count scales with occurrences × distinct tuples rather than with calls alone; find's exact square (265²) is consistent with that if nearly every call produced a distinct tuple, but Yaga's and especially KeePassXC's numbers show it isn't a clean, universal formula, since the paper doesn't spell one out.
⚠
Read critically: this is a genuine tension between the paper's prose and its own reported data, not something to paper over — worth keeping in mind when citing Table 1's numbers.

④ Tracing Algorithm 1 for the heartbeat example

Walk one iteration of the top-level loop for target procedure send_hb.

  1. CreateInstrumentation(send_hb) inserts probes at both call sites (lines 19 and 24).
  2. RunDynamicAnalysis yields two argument tuples: (buf=hb_msg.payload, len=resp1) and (buf=hb_msg.payload, len=resp2).
  3. CreateTests builds two tests, one per tuple, each forking at its call site.
  4. ExecuteTest runs both; the first passes (payload matches expectation), the second fails or shows an out-of-bounds read — allPassed = false.
  5. Loop continues: developer inspects the failing test, edits line 23 to use len2, and the loop re-runs until allPassed and the fix validates.
Test yourself

Practice problems

Try each before opening the answer; every one ends with the misconception it checks.

Problem 1 · easy
Why does forking at the call site avoid writing a test driver, when a normal unit test for the same procedure would need one?
Show answer
A test driver's job is to construct a realistic input state (call stack, heap objects, globals) before invoking the procedure. Forking a live, already-running process gives you that exact state for free — the fork inherits the real memory and stack up to that point — so no driver code needs to be written.Misconception: that ACF "generates" input state. It doesn't construct state at all — it reuses state that already existed at runtime.
Problem 2 · medium
A target procedure is called 40 times during the traced run, with 12 distinct argument tuples among those calls. Roughly how many tests does ACF's testing phase execute, and why not just 40 or just 12?
Show answer
Closer to 40 × 12 ≈ 480 — not 40 (one per call occurrence) and not 12 (one per distinct tuple). ACF forks at every dynamic call site the run reaches, and at each of those 40 occurrences it tests every one of the 12 distinct recorded tuples, not just the one that actually appeared there — so the count is closer to occurrences × distinct tuples than to either number alone (the exact figure depends on implementation details not spelled out in the paper).Misconception: that a test count should equal either the number of calls or the number of distinct tuples. ACF's exhaustive design tries every recorded tuple at every call site, which multiplies rather than just counts.
Problem 3 · hard
The paper says ACF "closely replicates observed behavior" and is "limited to execution paths observed by the dynamic analysis." What kind of bug could ACF never find, no matter how many tests it runs?
Show answer
A bug triggered only by an argument value or call sequence that never occurred during the traced run — e.g. an edge case like an empty string or a value combination the production workload never exercised. ACF is a replay tool, not a fuzzer; it can isolate and clarify bugs that already manifested, but it cannot discover inputs the system never actually produced.Misconception: that more tests from ACF means more coverage of possible inputs. Test *count* can be huge (see find/Yaga) while input *diversity* is still bounded by one traced run.
Problem 4 · medium
For the KeePassXC experiment, tracing used the GUI variant but testing used the CLI variant (keepassxc-cli). Why not use the GUI for both?
Show answer
ACF's testing phase (the fork-based part) cannot yet reliably handle multi-threaded programs. The paper reports using the GUI application for tracing (observation only) but switching to the CLI tool, keepassxc-cli, for the fork-based testing phase — consistent with needing a variant compatible with ACF's single-threading limitation, though the paper doesn't spell out the exact threading model of either binary.Misconception: that tracing and testing require the exact same binary or mode — only the testing phase's forking is restricted by threading; observation-only tracing is less sensitive to it.
Problem 5 · hard
Using Table 1, compute tests-per-call for find (70,225 / 265) and Yaga (112,559 / 360). What do the two ratios suggest about how "tests" are actually counted, given Section 4's claim that count should equal number of calls?
Show answer
find: 70,225/265 = 265 tests per call — i.e., exactly calls again (consistent with calls²). Yaga: 112,559/360 ≈ 312.7, not equal to 360. Since the text claims tests should equal calls (a 1:1 ratio, not calls-per-call), neither ratio actually matches the stated 1:1 relationship — reinforcing that Table 1's "Tests" column reflects something more complex (likely combinatorial across multiple call sites and tuples) than the prose describes.Misconception: that a paper's summary sentence about its own table is always literally exact — here the arithmetic shows it isn't, at least not uniformly.
Problem 6 · easy
What must a developer still do themselves after ACF produces its test report?
Show answer
Inspect the failing tests and surrounding source code to determine the actual root cause, write the code fix, and validate that the fix resolves the issue (Algorithm 1's "developers will inspect... and edit source code" step). ACF automates tracing, test creation, and execution — not diagnosis or repair.Misconception: that ACF is a fully automated bug-fixing tool. It narrows the search space; a human still closes the loop.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the difference between the two dynamic-analysis phases?▾
Phase 1 just lists which procedures get called during a run, so the developer can pick one by name. Phase 2 re-runs the system and records full argument (and return) values for calls of that one chosen procedure. Splitting them avoids capturing detailed data for every procedure up front.
Q2Why fork() instead of a conventional test harness?▾
A harness has to construct a realistic input state manually — often the hardest part of unit testing a procedure deep inside a large system. Forking the live process at the call site reuses the real state (stack, heap, globals) for free, then just swaps in a different recorded argument tuple.
Q3What data types and library features does ACF currently support?▾
Built-in numeric primitive types, std::string, and a small part of STL (collections). Other data types and library procedures require extending ACF through its extension mechanism — full support for complex nested object graphs is future work.
Q4Does ACF work for multi-threaded programs?▾
The released version reliably handles only single-threaded programs. Multi-threading support, based on check-pointing with a modified control schema between server, coordinator, and forked tests, is under development and raises open questions about thread-interleaving-dependent recorded data.
Q5How is ACF different from a fuzzer like AFL++?▾
Both use process forking to skip expensive startup, but for different goals: AFL++ forks to generate and try new, often random inputs to find crashes. ACF forks to replay inputs it already observed at runtime, to isolate and clarify a specific known misbehavior — it's a diagnosis tool, not primarily a bug-discovery one, though the authors note fuzzing could extend it.
Q6How does ACF compare to a scriptable debugger like Expositor?▾
Expositor requires recording full execution traces up front to enable scripted, bidirectional time-travel over them — costly for long runs. ACF instead records only argument tuples for a chosen procedure and reconstructs surrounding state on demand by re-running and forking, trading full-trace navigation for much lower storage cost.
Q7What happens if a forked test never returns?▾
ACF implements per-test timeouts (killing a hung forked child) as well as a global timeout for the central server (llcap-server), so a single non-terminating test doesn't stall the whole testing phase.
Q8Does ACF automatically find the bug, or just narrow the search?▾
It narrows the search. ACF produces a report where failing tests point to the exact argument tuples that trigger the observed behavior; a human developer still inspects those, reads the related source, and writes the fix.
Q9Why is a central coordinator (llcap-server) needed at all?▾
It launches the instrumented target, coordinates the tracing and testing runs, and manages inter-process communication (shared memory, sockets) between the running target, its forked test children, and the recorded data — a role no single component could fill on its own.
