Stop guessing which pages are hot — snoop the bus instead

Software tiering guesses hotness from page faults and LRU lists; PHASE emulates hardware that watches every memory access directly, then plugs that clean signal into TPP and Nomad to see who actually wins.

📄 Tzafrir, Patel, Nider, Fedorova · DIMES'26 🎓 Assumes CXL tiering, NUMA, mm-stack basics ⏱ ~20 min read
🎯

Measure hotness precisely, in hardware and migrate conservatively — precision beats eager guessing once the memory bus becomes the bottleneck.

1Why tracking hotness is hard without special hardware▾

General-purpose CPUs have no built-in per-page access counter. The only options are unmapping pages to force a hint fault (cheap-ish but coarse and CPU-visible) or sampling PEBS hardware counters (also CPU-cycle-consuming). Both cost cycles on the very thread you're trying to speed up.

Now you're ready: M5-style hardware sidesteps this entirely by snooping the memory bus in the CXL controller — zero host CPU involvement.
2The ANB → TPP → Nomad lineage▾

ANB hints on every remote access and calls it hot almost immediately (false positives). TPP filters that noise through the kernel's LRU active/inactive lists before promoting, and demotes asynchronously. Nomad keeps TPP's LRU filter but makes promotion asynchronous too, using a "shadow" copy of the slow-tier page so a later demotion is a free PTE remap.

Now you're ready: each step removed one synchronous, CPU-blocking operation — PHASE asks what's left to remove once even the detection step is hardware.
3M5's top-k tracker & the Count-Min Sketch▾

Instead of one counter per physical page (too much SRAM), a Count-Min Sketch hashes each PFN into a small grid and increments buckets; reading the minimum bucket across hash functions estimates that page's frequency. A sorted top-k array then tracks only the k hottest candidates.

Now you're ready: k isn't a page-count cap — it's the batch size of hot candidates reported per polling epoch.
4The metrics that matter here▾

Locality = fast-tier hit rate (higher looks better, but is misleading alone). PPMA = migrations per million accesses (proxy for bus/thrashing cost). Plus stable/transient latency and steady-state bandwidth.

Now you're ready: the paper's central twist is that low locality + low PPMA can beat high locality + high PPMA on real bandwidth and latency.
5Why "free" hardware isn't free in emulation▾

Real M5 hardware snoops passively with zero CPU cost. QEMU/KVM can't trap passive bus reads, so PHASE forces a VM-exit via an MMIO write per observed access — which itself perturbs timing and pollutes host caches/TLBs.

Now you're ready: this is exactly why PHASE subtracts tracker time from the guest clock (kvmclock) and samples accesses rather than trapping every one.
6PHASE's three-part architecture (preview)▾

A Remote Tier Tracker (emulated PCI device) detects accesses; a Zero-Copy Communication Bridge (a lock-free ring buffer) hands hot PFNs to the guest; an In-Kernel Promotion Engine batches and calls migrate_pages(). Detailed with diagrams in "How It Works."

Now you're ready: any hardware tracker (M5-like or otherwise) can plug into this same pipeline — that modularity is PHASE's own contribution, distinct from the evaluation results.
The whole story in one place

PHASE in a nutshell

What's broken, what PHASE builds, and the counter-intuitive result it surfaces.

A decade of memory-tiering research improved migration: TPP fixed ANB's lack of proactive demotion, and Nomad fixed TPP's synchronous, blocking promotion with asynchronous shadow paging. But all three still detect hotness in software — via page-table scans and hint page faults — which costs CPU cycles that scale with working-set size. Meanwhile M5 showed hardware can track hotness with near-zero CPU overhead, but no one had combined it with these mature migration policies.

PHASE is a QEMU-based platform that does exactly that: an emulated M5-style top-k tracker (Count-Min Sketch + sorted top-k, with MEMTIS-inspired epoch-based cooling) feeds hot PFNs through a zero-copy ring buffer into TPP or Nomad's promotion path, replacing their software scanning.

The headline finding is counter-intuitive: the hardware tracker achieves lower fast-tier locality than software methods (e.g. 67–71% vs. TPP/Nomad's 100%/74–96%), yet still delivers up to 5.6× higher bandwidth and 6× lower latency. Why: precise, conservative tracking collapses PPMA from the hundreds-of-thousands (TPP: 224,195 in Large WSS) down to single digits (N-top-64: 3.4), eliminating thrashing and freeing the bus and the CPU (System CPU falls from TPP's 45.24% to N-top-5's 0.26% in Large WSS).

🍯 Key takeaways

  • Perfect locality isn't the goal — low PPMA (few, well-chosen migrations) is what actually buys bandwidth and latency.
  • Software methods (ANB/TPP/Nomad) over-migrate because their signal (recency/LRU) is too eager relative to true reuse.
  • The hardware tracker's conservatism is the feature: fewer, more confident promotions avoid ping-pong thrashing.
  • Once migration volume (PPMA) is low, TPP's synchronous-promotion weakness barely matters — T-top-k ≈ N-top-k on most workloads.
  • Nomad's shadow-paging advantage over TPP only shows up under real capacity pressure (Medium WSS), not everywhere.
  • PHASE's contribution is the platform itself: a modular way to swap hardware trackers under existing kernel policies.
Five pictures

How to think about PHASE

Each stands alone. Every card ends with where the picture stops being true.

📹
Detection · hardware vs. software

A doorbell camera vs. a sign-in sheet

ANB/TPP/Nomad make every visitor (memory access) stop and sign a sheet (a hint page fault) — informative, but it slows down foot traffic. M5's hardware tracker is a doorbell camera: it watches from the bus, unnoticed, at zero cost to the visitor.

Where it breaks: PHASE's camera is emulated — QEMU can't passively watch KVM guest memory, so each sampled access still forces a real VM-exit. The "free camera" costs something until you run it on real silicon.
🚦
Sampling rate · Table 1

Stopping every car vs. every 100th car

Trapping every access (sampling rate 1) is like a tollbooth that stops every car to count it — perfect data, backed-up traffic. Sampling every 100th car keeps traffic flowing with nearly the same estimate; that's why PHASE settles on a rate of 100.

Where it breaks: too sparse isn't free either — in the Medium WSS, sampling rate 500 actually drops bandwidth from 8,328 to 7,869 MB/s versus rate 100, because it starts missing genuinely hot pages, not just easing congestion.
🔑
Enforcement · Nomad's shadow copy

Keeping a spare key after you move

Nomad doesn't delete the old (slow-tier) copy of a page when it promotes it — it keeps a "shadow." If the page must be demoted later, that's just handing back the spare key (a PTE remap), not paying movers again.

Where it breaks: a real spare key costs nothing to hold; the shadow copy occupies real slow-tier capacity indefinitely, which is a genuine (if usually cheap) tradeoff Nomad accepts.
📚
Hardware · Count-Min Sketch

A tally sheet with only five shelves for a million books

Instead of one counter per page, the CM-Sketch hashes each page onto a few shared "shelves" and increments a tally. Reading the smallest tally across shelves gives a good frequency estimate without a counter per book.

Where it breaks: shared shelves mean a cold book that hashes onto the same shelf as a hot one can look artificially popular (a collision) — which is exactly why K (tracking granularity) and sketch width are tuned, not maximized blindly.
⏱️
Emulation fidelity · kvmclock

Pausing the stopwatch, not the runner

PHASE freezes the guest's logical clock during tracker emulation so the workload's reported time excludes the tracking overhead — like pausing a stopwatch while a runner ties their shoe.

Where it breaks: the runner's muscles still got cold. Pausing the clock hides the software cost of the VM-exit but can't undo the real host-cache and TLB displacement it caused — hence PHASE still needs sampling to limit how often this happens.
The full explanation

How PHASE actually works

The pipeline, the emulation trick that makes it plausible, and the tracker's internals.

1 · Three components, one pipeline

A guest access to slow-tier memory triggers an MMIO write to a PCI device (the Remote Tier Tracker), forcing a VM-exit into QEMU where the C-level tracker logic runs. Hot PFN candidates are periodically pushed into a Zero-Copy Communication Bridge — a lock-free ring buffer built on Linux's u-dma-buf, shared as guest physical memory. A guest-side kernel thread, the In-Kernel Promotion Engine, polls this buffer, converts PFNs to page structures in O(1), and batches them for migrate_pages().

2 · Why sampling, not full tracking

Freezing the guest clock during tracker emulation (kvmclock subtraction) hides reported execution time, but can't undo the host cache/TLB pollution each VM-exit causes. So PHASE traps only a sample of accesses; Table 1 shows continuous tracking (rate 1) tanks bandwidth across all workload sizes, while rate 100 recovers most of it.

3 · Hardware tracker internals

Each access hashes its PFN into the CM-Sketch, increments buckets, and the minimum bucket value estimates that page's frequency. A sorted top-k list is maintained via localized "bubble-up" insertion — O(N) in software, approximating the O(1) CAM comparator array of real hardware. Three hyperparameters govern freshness: aging shift (decay aggressiveness, dividing scores by 2shift), reset interval (how often decay applies), and publish period (accesses between OS interrupts with new candidates). Best found: shift 400-cycle reset interval, aggressive (shift=5) decay, 1,000-access publish period.

4 · Plugging into TPP and Nomad

N-top-k and T-top-k replace Nomad's and TPP's software page-table scanning with polling the hardware's top-k list — everything downstream (asynchronous migration, shadow paging for Nomad) is unchanged. The kernel's page-table insertion batch size was raised from 8 to 512 pages (matching a 2MB huge page) to avoid PT spinlock thrashing under the hardware tracker's higher promotion rate.

💡
Why T-top-k ≈ N-top-k on most workloads: Nomad's whole reason for existing was to fix TPP's synchronous-promotion bottleneck under heavy migration. Once the hardware tracker drives PPMA down to single digits, that bottleneck is rarely triggered — so TPP's simpler machinery performs nearly as well as Nomad's.
Follow the numbers

Worked examples

Four calculations straight from Tables 2–3 and §4.4.

① How much does the hardware tracker cut migration volume?

Large WSS PPMA: TPP = 224,195; N-top-64 = 3.4.

  1. Ratio = 224,195 ÷ 3.4 ≈ 65,940× fewer promotions per million accesses.
  2. Nomad (189,739 PPMA) is only modestly better than TPP — still five orders of magnitude above N-top-64.
  3. This is the paper's core mechanism: precision, not faster migration machinery, is what removes the thrashing.

② The headline latency claim, traced to a table row

Large WSS stable latency: Nomad = 2,719 ns; N-top-64 = 504 ns; TPP = 7,838 ns; N-top-5 = 491 ns.

  1. Nomad → N-top-64: 2,719 ÷ 504 ≈ 5.4× lower latency — the row that best matches the abstract's "6× lower" claim.
  2. TPP → N-top-5: 7,838 ÷ 491 ≈ 16× — an even larger gap against the weaker baseline.
  3. Both use the identical migration mechanism as their software counterpart (Nomad's or TPP's) — only the hotness signal changed.

③ CPU overhead, Large WSS

System (kernel) CPU: TPP 45.24%, Nomad 15.40%, N-top-5 0.26%.

  1. TPP → N-top-5: 45.24 ÷ 0.26 ≈ 174× less kernel CPU spent.
  2. Kernel counters confirm the cause: millions of NUMA hint faults drive TPP/Nomad's System CPU; the hardware tracker generates none.
  3. User CPU differs far less (11.38% vs 7.17%) — the overhead is almost entirely in fault-handling, not application logic.

④ Tracking granularity K — locality isn't free

Medium WSS: K=64 → 41% locality / 8,412 MB/s; K=1024 → 52% / 8,007 MB/s; K=4096 → 66% / 7,626 MB/s.

  1. K=64 → K=4096: locality gains +25 points (41%→66%), bandwidth loses ~9.3% (8,412→7,626 MB/s).
  2. More hardware tracking granularity costs SRAM (sketch collisions) and, past a point, actively hurts bandwidth.
  3. The paper settles on K=64 — direct numeric evidence that maximizing locality is the wrong objective.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
TPP achieves 100% locality on the Small WSS, yet its steady-state bandwidth still trails the No-Migration baseline. Why?
Show answer
Locality only measures hit rate, not cost. TPP's page-table scanning and occasional synchronous promotions consume CPU cycles even when migrations are infrequent, and that overhead eats directly into achievable bandwidth despite a perfect hit rate.Misconception: that maximizing locality (fast-tier hit rate) is equivalent to maximizing performance. It's necessary but not sufficient — the cost of achieving that locality matters just as much.
Problem 2 · medium
The hardware tracker has lower locality than Nomad in every WSS, yet dramatically lower PPMA. What does that combination tell you about its migration decisions?
Show answer
It migrates far less often, but when it does, those migrations are more confidently "worth it" — the tracker only surfaces the genuinely top-k hottest pages via the CM-Sketch, rather than promoting on the first or second repeated access like LRU-based filtering. Some potential hits are sacrificed (lower locality) to avoid speculative, soon-reversed migrations (thrashing).Misconception: that hardware tracking works by migrating faster or more efficiently. It works by migrating less, more selectively.
Problem 3 · medium
Compute the stable-latency ratio between Nomad and N-top-64 for the Large WSS (2,719 ns vs. 504 ns), and state which headline claim in the abstract it corresponds to.
Show answer
2,719 ÷ 504 ≈ 5.4×. This is the table row behind the abstract's claim of "up to... 6× lower memory access latency using the same migration strategy as Nomad" (i.e., comparing the hardware tracker against Nomad specifically, holding the migration mechanism constant).Misconception: that the 5.6×/6× headline numbers come from comparing against the weakest baseline (TPP/ANB). They're specifically hardware-tracker-vs-Nomad, the paper's strongest software baseline.
Problem 4 · hard
In the Medium WSS, N-top-k noticeably trails T-top-k less than expected, but N-top-k still beats T-top-k on latency (464 ns vs. 501 ns for top-64). Why does Nomad's advantage persist here but barely elsewhere?
Show answer
Medium WSS is capacity-constrained enough that demotions actually happen at a non-trivial rate even with a precise tracker. Nomad's shadow-paging means those demotions are free PTE remaps; TPP must physically copy data back to the slow tier. In Small and Large WSS, demotion volume is low enough (or, in Large, the WSS is nearly all "hot" with little cold data) that this difference rarely triggers.Misconception: that Nomad's shadow-paging benefit is a constant multiplier. It only matters when demotions are frequent — i.e., under genuine capacity pressure.
Problem 5 · medium
Why did the authors exclude MEMTIS from their empirical evaluation rather than just running it?
Show answer
Prior work already showed Nomad outperforms MEMTIS in most tiered-memory scenarios; for the remaining high-pressure workloads where MEMTIS reportedly beats Nomad, the authors argue the no-migration baseline outperforms MEMTIS anyway — so adding MEMTIS wouldn't change any conclusion, only cost implementation effort.Misconception: that exclusion implies MEMTIS is a weak design. It's excluded on relevance grounds (already-known relative ordering), not a judgment about its ideas — several of which (dynamic histograms, cooling) PHASE's own tracker borrows.
Problem 6 · easy
M5's real hardware supposedly has "near zero overhead," yet PHASE still needs to sample accesses instead of tracking every one. Why isn't the emulation just as free?
Show answer
Real M5 hardware physically snoops the memory bus outside the CPU pipeline. QEMU/KVM guest memory accesses don't natively trap, so PHASE must force a VM-exit (an MMIO write) to observe each access — which does cost real host CPU time and pollutes host caches/TLBs, unlike passive silicon snooping.Misconception: that an emulator can perfectly reproduce a hardware property like "zero overhead." Emulation can reproduce the logic of hardware, but the discussed absence of cost is a property of silicon, not of software standing in for it.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is PHASE a new tiering algorithm?▾
No — it's an emulation platform. Its contribution is letting a hardware hot-page tracker (modeled on M5) plug into existing software policies (TPP, Nomad) inside QEMU with minimal kernel changes, so the two can be evaluated together for the first time.
Q2Why does the hardware tracker have lower locality but still win?▾
Because locality alone ignores the cost of achieving it. The hardware tracker trades some hit rate for a drastically lower promotion volume (PPMA), which avoids thrashing and frees both the memory bus and the CPU — and that dominates overall bandwidth and latency.
Q3What exactly is PPMA measuring?▾
Promotions Per 1 Million Accesses at steady state — how often the system moves a page into the fast tier, normalized by access volume. High PPMA under memory pressure signals thrashing (ping-ponging pages between tiers).
Q4Why is TPP paired with the hardware tracker (T-top-k) almost as good as Nomad paired with it (N-top-k)?▾
Nomad's asynchronous, shadow-paged migration exists specifically to solve TPP's synchronous-promotion bottleneck under heavy migration. With the hardware tracker driving PPMA down to single digits, that bottleneck rarely fires, so TPP's simpler design performs nearly as well — except under real capacity pressure (Medium WSS), where Nomad's free demotions still help.
Q5Why sample accesses instead of tracking every one, if the goal is "hardware precision"?▾
In real silicon, sampling wouldn't be necessary — snooping is free. In QEMU emulation, every tracked access forces a VM-exit, which is not free; continuous tracking floods the host with context switches and artificially tanks bandwidth (Table 1, rate 1). Sampling at rate 100 balances telemetry coverage against this emulation-specific cost.
Q6What real applications did they test beyond microbenchmarks?▾
A YCSB-A Redis key-value workload (N-top-5: 89.32K ops/s vs. TPP's 63.27K and Nomad's 79.81K, with far fewer promotions per million ops) and a PageRank graph workload (N-top-5 delivered a 1.38× speedup over TPP, versus Nomad's 1.04× and no-migration's 1.22×).
Q7What's the purpose of the epoch-based aging mechanism?▾
It lets the tracker adapt to workload phase changes without M5's hard resets. Periodically right-shifting (halving-style decaying) the CM-Sketch and top-k values lets newly hot pages quickly outrank historically hot but now-inactive ones, governed by three tuned hyperparameters (aging shift, reset interval, publish period).
Q8What are PHASE's acknowledged limitations?▾
The emulated MMIO-trap approach for "snooping" introduces timing artifacts that active overhead subtraction only partially corrects (host cache/TLB pollution remains). Results are also preliminary and reported for one hardware tracker family (M5-style top-k with MEMTIS-inspired aging) — the paper positions itself as a platform for further exploration, not a final verdict on all hardware/software combinations.
