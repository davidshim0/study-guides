Cloning packets in the driver, not after the kernel's slow lane

XDP can fan a packet out to many interfaces — but it can't hand you an independently-editable copy. This is the plain-English story of XDP_CLONE, two new XDP actions that duplicate packets before the kernel ever allocates a socket buffer.

📄 "XDP_CLONE: Efficient In-Driver Packet Duplication" · Mazzella et al. 🎓 Some eBPF/XDP basics assumed — the primers cover them ⏱ ~20 min read
🧬

Duplicate packets as in-driver pages, before any sk_buff exists — not as sk_buffs cloned after TC already paid the allocation tax.
Pay the fixed cost once, keep the per-copy cost tiny.

XDP_CLONE (in-driver, fast) TC / bpf_clone_redirect() (baseline) driver machinery
1Where XDP runs, and why that matters▾

XDP code runs inside the NIC driver's receive routine, before the kernel builds any per-packet structures. That's what makes it fast: a program can inspect, rewrite, drop, or transmit a packet using only the raw page the NIC DMA'd the data into.

Now you're ready: XDP_CLONE adds two new things a driver can do at this exact point — duplicate the page before anything heavier gets built.
2The sk_buff, and why allocating one is expensive▾

Once a packet needs to travel further into the kernel stack (routing, sockets, TC), it gets wrapped in an sk_buff — a large, general bookkeeping structure. Building one is one of the most expensive steps in the whole RX path.

Now you're ready: every duplicate produced via TC needs its own sk_buff. That per-copy allocation is the paper's main target.
3The TC hook and bpf_clone_redirect()▾

TC is a second eBPF attachment point, deeper in the stack, that runs after the sk_buff already exists. Its bpf_clone_redirect() helper is the only kernel-native way to replicate a packet with per-copy edits — but each call allocates a fresh sk_buff.

Now you're ready: TC is the paper's baseline. Its cost has two parts — the fixed cost of reaching TC at all, and a per-clone sk_buff cost — both of which XDP_CLONE targets.
4XDP's return codes (actions)▾

An XDP program ends by returning one action: XDP_DROP, XDP_PASS (to the kernel stack), XDP_TX (retransmit out the same NIC), XDP_REDIRECT, or XDP_ABORTED. Exactly one packet results — none of these actions multiply the packet.

Now you're ready: XDP_CLONE adds two new actions to this list, XDP_CLONE_PASS and XDP_CLONE_TX, the first XDP verdicts that produce more than one outgoing packet.
5The RX page pool▾

Modern NIC drivers recycle a small pool of memory pages for incoming packets (page_pool_dev_alloc_pages()) instead of hitting the general kernel allocator every time — much faster, but finite.

Now you're ready: each XDP_CLONE copy needs one fresh page from this pool. Once demand for copies outruns the recycled cache, allocation falls back to the slow path — the paper's "page-pool cliff."
6One-to-many patterns: broadcast and pub-sub▾

Two common networking patterns need to turn one incoming packet into several outgoing ones: an MPI-style broadcast (one sender, many HPC ranks) and a publish-subscribe broker (one publish message, one copy per topic subscriber).

Now you're ready: these are exactly the two applications the paper builds on XDP_CLONE to demonstrate real-world gains.
7Throughput and latency, the two scorecards▾

Throughput (Mpps) is how many packets per second a pinned core can push without drops. Latency (µs/ms) is how long one packet — and, here, all its replicas — take to return. The paper's loss-free criterion is stricter than it sounds: for K input packets and n requested copies each, a run only counts if all K(n+1) packets — including every original — come back.

Now you're ready: every chart in this guide plots one of these two against the number of clones requested.
8Re-injection: running a program more than once per packet▾

Normally an XDP program runs exactly once per received packet. XDP_CLONE's core trick is to let the driver call bpf_prog_run_xdp() again — once per requested copy — feeding the same program a fresh, page-backed clone each time.

Now you're ready: this re-injection loop, with a numbered tag in the packet's metadata, is the entire mechanism — covered in depth in "How It Works."
The whole story in one place

XDP_CLONE in a nutshell

The problem, the fix, and how the pieces connect.

XDP can broadcast a packet to many interfaces via bpf_redirect_map() with BPF_F_BROADCAST — but every replica is byte-identical, and the original can't simultaneously be delivered locally and duplicated. Anything requiring per-copy edits or "keep one, send the rest" logic has always had to fall back to TC, where bpf_clone_redirect() replicates packets — at the cost of one sk_buff allocation per clone, on top of the one the kernel already built to reach TC at all.

XDP_CLONE adds two new XDP actions — XDP_CLONE_PASS and XDP_CLONE_TX — that ask the driver itself to produce n in-driver copies, created as page-backed xdp_buffs without any sk_buff allocation at creation time (a clone whose re-run verdict is XDP_PASS will still pick up an sk_buff further up the stack, like any packet reaching that point). Each copy is tagged with its index in the packet's metadata and fed back through the same XDP program, which decides its fate independently with an ordinary XDP verdict. The original then follows its usual path (PASS or TX) — though the program is free to rewrite it first, as the pub-sub broker does before calling XDP_CLONE_TX(N-1) to address it to the first subscriber.

The payoff: XDP_CLONE sustains 2.6× the throughput of TC even at 64 copies, cuts end-to-end latency by up to ~40%, and — on two real applications (an MPI-like broadcast and a pub-sub broker) — reaches up to 2.3× the throughput of TC-based replication, for 189 lines of driver code and no eBPF verifier changes.

🍯 Key takeaways

  • TC's cost has a fixed part (reaching TC, one sk_buff already built) and a per-copy part (one sk_buff per clone, ~700 ns each).
  • XDP_CLONE removes the fixed part entirely and replaces the per-copy sk_buff with a page-pool memcpy.
  • Past 4 clones, the RX page pool's recycled cache runs out and allocation falls back to the slow path — a visible cliff in throughput.
  • No eBPF verifier changes needed — XDP already treats the return code as an opaque 32-bit scalar; safety (no nested cloning) is enforced in the driver.
  • XDP_CLONE_PASS = keep the original locally + clone; XDP_CLONE_TX = retransmit the original + clone, entirely in-driver.
  • Demonstrated on XuDP (MPI-like broadcast) and a pub-sub broker, both beating TC by up to ~2×–3.6× depending on workload.
Five everyday pictures

How to think about XDP_CLONE

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Fixed vs per-copy cost

The print shop across town

TC is a print shop on the other side of the city: every job pays a trip there (the fixed cost of reaching TC, sk_buff already built) plus a fee per copy. XDP_CLONE is a copier in the room right next to you — no trip, and each extra page costs far less than TC's per-copy sk_buff fee.

Where it breaks: the office copier still runs out of paper, and paper isn't free even before then. Past 4 copies the page pool empties too — RTT climbs to 59 µs at 64 copies — and XDP_CLONE has to send someone to the supply closet (the slow allocator).
Metadata tagging · num_copy

Numbered raffle tickets

Before re-running the program on each clone, the driver staples a numbered ticket to it — 1, 2, …, n — in the packet's metadata region. The program reads the number and knows exactly which copy it's holding, so it can address copy #1 to subscriber A, #2 to subscriber B, without any shared state between them.

Where it breaks: the original packet carries no ticket at all (no metadata present) — the program must check for that explicitly to tell "original" from "clone."
Page pool exhaustion · the cliff

The valet with four free spots

A valet stand keeps a handful of pre-parked cars ready to hand back instantly — fast, as long as you ask for few. Ask for a fifth in a hurry, and the valet has to jog to the far garage (the slow page allocator) for it. That's exactly why XDP_CLONE's throughput holds strong through 4 clones, then roughly halves by 8.

Where it breaks: a real valet stand's capacity is fixed by headcount; the page pool's "4-ish" threshold is a property of its recycled-cache size and could shift with driver tuning.
Pub-sub fan-out · XDP_CLONE_TX

A receptionist photocopying a memo

One memo arrives addressed to "all subscribers." The receptionist doesn't need to read it into her own files (no local delivery needed) — she just photocopies it n−1 times, writes a different name on each copy, and sends every copy straight back out. That's XDP_CLONE_TX: the broker never touches user space.

Where it breaks: a receptionist can misfile a copy without much cost; a dropped network clone is a lost message — reliability for these patterns is left to the application (e.g. XuDP's ACK/NACK channel).
XuDP · Ring vs Linear broadcast

A bucket brigade vs a firehose

Ring broadcast is a bucket brigade: each person keeps a bucket (delivers locally via XDP_CLONE_PASS, n=1) and passes one more down the line — steady but the line takes N hops to empty. Linear broadcast is a single firehose at the first junction, spraying N−2 copies out at once (n=N−2) — fast, but all the pressure is on that one node.

Where it breaks: a real firehose doesn't slow down with more nozzles; XDP_CLONE's linear broadcast does hit the page-pool cliff once N−2 exceeds ~4, just like any other high-fan-out clone.
The full explanation

How it actually works

From the cost breakdown to the driver's clone loop to the two demo applications.

1 · Where TC's cost actually comes from

Without any cloning at all, plain XDP_TX already beats bpf_redirect() at TC by 5× (10 vs 2 Mpps) — that gap is the fixed cost of reaching TC and building one sk_buff, paid on every packet regardless of replication. On top of that, each bpf_clone_redirect() call adds roughly 700 ns and one more sk_buff — the per-copy cost, which accumulates linearly as clone count grows.

2 · The two new actions

XDP_CLONE_PASS(n) and XDP_CLONE_TX(n) differ only in what happens to the original packet — handed to the local kernel stack (as XDP_PASS would) or retransmitted out the NIC (as XDP_TX would). Each encodes the copy count n and the verdict for the original in a single 32-bit return value — no eBPF verifier changes required, since XDP return codes are already just opaque scalars to the verifier; all safety checks live in the driver.

3 · Life cycle of a cloned packet, in order

  1. Page allocation. For each of the n copies, the driver pulls a fresh page from the pool and memcpys the original packet's bytes into it — no sk_buff allocated at this step.
  2. Failure handling. If the pool can't satisfy an allocation, that one copy is dropped (reported via the xdp_exception tracepoint); the original packet, already on its own page, is unaffected.
  3. Metadata tagging. The driver writes the clone's index i ∈ [1,n] into the packet's data_meta region, just before the packet data.
  4. Re-injection. The driver calls bpf_prog_run_xdp() again on this one clone's buffer — the same program, a fresh invocation.
  5. Per-clone verdict. The returned action must be a standard one (TX/PASS/DROP/REDIRECT); a clone action here is rejected as XDP_ABORTED.

4 · The programming model, side by side

At TC, replicating n times costs n+1 helper calls and n sk_buff allocations, on top of the one the kernel already built:

SEC("tc")
int tc_clone(struct __sk_buff *skb) {
  // one helper call (+ one sk_buff alloc) per clone
  for (i = 0; i < n_clone; i++)
    bpf_clone_redirect(skb, skb->ifindex, 0);
  return bpf_redirect(skb->ifindex, 0); // forward original
}

With XDP_CLONE, the whole duplication is one return value; the driver handles the loop:

SEC("xdp")
int xdp_clone(struct xdp_md *ctx) {
  if (data_meta + sizeof(__u32) <= data) {
    __u32 num_copy = *(__u32*)data_meta;      // which clone am I?
    if (num_copy > 0 && num_copy <= n_clone)
      return XDP_TX;                        // per-clone verdict
  }
  return XDP_CLONE_TX(n_clone);             // original path
}
💡
Why this matters: the eBPF program never allocates anything and never loops over clones itself — it just branches on whether metadata is present, and picks one verdict either way.

5 · The two demo applications

XuDP (§4.1) reproduces MPI's broadcast collective over UDP using XDP_CLONE_PASS: the original reaches the local process (as a real receiver would need), while the in-driver copies fan out to the rest of the ring or the remaining linear-broadcast neighbors. Reliability rides on a parallel TCP control channel: every receiver sends a single end-of-broadcast ACK or NACK, so in the common loss-free case the root just collects N−1 ACKs — there are no per-packet acknowledgments or timers on the fast path.

The pub-sub broker (§4.2), built on BPF-Broker, is pure forwarding — the publish message never needs to reach user space — so XDP_CLONE_TX is the natural fit: every subscriber gets an independently re-addressed copy, transmitted straight back out, collapsing what used to be a two-hook (XDP + TC) pipeline into one.

Follow the numbers

Worked examples

Four calculations straight from the paper's own reported figures.

① TC's per-copy cost, from the endpoints

TC's RTT is 15 µs with no cloning and 99 µs at 64 copies. The paper says each bpf_clone_redirect() adds "roughly 700 ns."

  1. Total added latency: 99 − 15 = 84 µs across 64 clones.
  2. Effective per-copy cost: 84 µs ÷ 64 = 1.31 µs/clone — higher than the quoted ~700 ns helper cost alone, since each clone also carries extra buffer bookkeeping and queuing beyond the helper call itself.
  3. Takeaway: even the "roughly 700 ns" figure, taken as a floor, means 64 clones add at least 44.8 µs — TC's per-copy tax is structural, not incidental.

② XDP_CLONE's ~40% latency reduction

XDP_CLONE's RTT: 8 µs baseline, 59 µs at 64 copies.

  1. Effective per-copy cost: (59 − 8) ÷ 64 = 0.80 µs/clone — about 40% below TC's 1.31 µs/clone.
  2. Reduction at 64 clones: (99 − 59) ÷ 99 = 40.4% — matches the paper's headline "~40% reduction" exactly.
  3. Where the saving comes from: avoiding both TC's fixed 7 µs entry cost (15 − 8) and roughly 40% of the per-clone cost, by copying a page instead of allocating an sk_buff.

③ The page-pool cliff, quantified

XDP_CLONE throughput goes from ~11 Mpps at 4 copies to 5 Mpps at 8 copies.

  1. Drop: (11 − 5) ÷ 11 ≈ 55% throughput loss from doubling the clone count once.
  2. Cause: each copy needs a page from page_pool_dev_alloc_pages(); past 4 concurrent copies the recycled cache is exhausted and the slower general allocator becomes the bottleneck.
  3. Still ahead of TC: even post-cliff, 5 Mpps (at 8 copies) and 4.0 Mpps (at 64) both comfortably beat TC's 1.5–2.5 Mpps range — the cliff shrinks the lead, it doesn't erase it.

④ Pub-sub fan-out at 64 subscribers

At N=64 subscribers: XDP_CLONE = 2.28 Mpps, TC = 0.97 Mpps, user-space baseline = 0.47 Mpps.

  1. vs TC: 2.28 ÷ 0.97 ≈ 2.35× — matches the paper's headline "2.3×" (and the abstract's "up to 2.3x" claim).
  2. vs baseline: 2.28 ÷ 0.47 ≈ 4.85× — matches the paper's "4.8×."
  3. Why TC plateaus early: at high fan-out, TC's core spends its cycles allocating one sk_buff per subscriber rather than transmitting — the same per-copy tax measured in the microbenchmark, now bottlenecking a real application.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why can't bpf_redirect_map() with BPF_F_BROADCAST alone replace XDP_CLONE?
Show answer
It produces sk_buff-free replicas too, but every replica is byte-identical and the program gets no chance to edit each one or deliver the original locally while duplicating. XDP_CLONE re-runs the program per copy, so each one can be independently addressed.Misconception: that XDP already "does duplication." It does uniform broadcast, not programmable per-copy duplication.
Problem 2 · easy
A clone's XDP invocation itself returns XDP_CLONE_TX(3) — what happens?
Show answer
The driver rejects it as XDP_ABORTED and raises the xdp_exception tracepoint. Nested cloning is explicitly disallowed to bound per-packet work and prevent unbounded recursion.Misconception: that clones can themselves be cloned, producing a fan-out tree. The mechanism is strictly one level deep.
Problem 3 · medium
TC's RTT goes from 15 µs to 99 µs across 64 clones. Roughly how much of that 84 µs increase would be explained by the paper's "~700 ns per clone" figure alone?
Show answer
700 ns × 64 = 44.8 µs — only about 53% of the 84 µs actually observed. The rest comes from other TC-layer overheads (redirect bookkeeping, queuing) that scale with clone count beyond the helper call itself.Misconception: that the quoted per-helper cost fully explains the measured slope. It's a lower bound, not the whole story.
Problem 4 · medium
What distinguishes XDP_CLONE_PASS from XDP_CLONE_TX, and which does the pub-sub broker use?
Show answer
They differ only in the original packet's fate: PASS hands it to the local kernel stack, TX retransmits it out the NIC. The broker uses XDP_CLONE_TX, because a publish message is pure forwarding and never needs to reach a local user-space process.Misconception: that the two actions differ in how clones are produced. Clone production is identical; only the original's path differs.
Problem 5 · hard
Why does linear broadcast's completion time grow much faster with N than ring broadcast's, under both TC and XDP_CLONE?
Show answer
In linear broadcast, one node fans out N−2 copies in a single burst, so that node's clone-count — and its exposure to per-copy overhead (sk_buff cost for TC, page-pool pressure for XDP_CLONE) — scales directly with N. Ring broadcast spreads the work into N single-copy hops, so no one node's per-packet cost grows with N; only the hop count does.Misconception: that fewer total "rounds" (linear) is strictly better. Concentrating fan-out on one node trades hop-count for a much steeper per-node clone cost.
Problem 6 · medium
At N=1 subscriber, the paper reports identical 0.4 Mpps for both the TC-based broker and the XDP_CLONE broker. Why no difference here?
Show answer
With a single subscriber there's nothing to duplicate — both brokers just rewrite the destination and return a plain XDP_TX from the XDP fast path, doing identical work. The two paths only diverge once N≥2 and actual cloning (and its differing costs) begins.Misconception: that XDP_CLONE always wins. It only pays off once duplication is actually required.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Does XDP_CLONE replace the existing XDP_* actions?▾
No — it adds two new ones (XDP_CLONE_PASS, XDP_CLONE_TX) alongside the existing five. A non-cloning program is unaffected; the new actions are opt-in.
Q2Does using XDP_CLONE require eBPF verifier changes?▾
No. For XDP programs the verifier only checks that the return value is a 32-bit scalar, so the new encoded values pass through unchanged. All new safety logic (rejecting nested clones) lives in the driver, not the verifier.
Q3Can a clone be modified independently of the original and its siblings?▾
Yes — each clone lives on its own page and is re-run through its own invocation of the XDP program, so edits to one copy are invisible to the others and to the original.
Q4What happens if the page pool can't satisfy a clone's allocation?▾
That single copy is dropped: the driver releases the page, returns XDP_ABORTED for it, and raises the xdp_exception tracepoint. The original packet, which already has its own page and verdict, is unaffected.
Q5Does XDP_CLONE preserve TCP semantics for cloned streams?▾
No — it's transport-agnostic and duplicates raw frames. Stateful semantics like TCP sequencing are left entirely to the program or application above it; this is why XuDP is built on UDP plus its own lightweight ACK/NACK channel.
Q6Why is UDP chosen for XuDP instead of TCP?▾
UDP carries no per-connection state, so XDP can freely inspect, modify, and re-transmit packets without breaking a session abstraction. TCP's sequencing and connection state would be disrupted by in-driver duplication and rewriting.
Q7How much driver code did XDP_CLONE actually take to implement?▾
189 additional lines in the mlx5 driver, handling the clone loop, re-running the XDP program per copy, and acting on the returned verdict — publicly available on GitHub.
Q8Why does the linear broadcast's single fan-out node concentrate all the work?▾
Because XDP only fires on packet reception — the root sends one datagram to one neighbor, and only that neighbor's XDP program runs and produces the remaining N−2 copies. There's no way to trigger fan-out work on a node that hasn't received anything.
Q9Is XDP_CLONE limited to two-way duplication (original + 1 clone)?▾
No — n can be any count the driver and page pool can support; the paper benchmarks up to 64 clones per packet, and the linear broadcast use case requests N−2 clones in a single call.
