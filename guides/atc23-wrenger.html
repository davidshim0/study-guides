Free a page without asking anyone

Linux's page-frame allocator — the thing that hands out every physical 4 KiB page in the system — still runs on a 1960s idea: the buddy system, protected by locks, with state scattered across a 64-byte record for every single page frame. On a 26-core machine, that design can make a parallel 2 MiB allocation 27 times slower than it should be. This is the plain-English tour of LLFree, a lock- and log-free redesign that keeps every allocation inside a single cache line — and, as a side effect, makes crash-consistent allocation on persistent memory nearly free.

📄 "LLFree: Scalable and Optionally-Persistent Page-Frame Allocation" · Wrenger et al. (Leibniz Universität Hannover / TUHH) 🎓 The Knuth buddy-allocator primer is useful background, not required ⏱ ~30 min read
🔒

Don't share a lock and hope it stays fast — make every allocation and every free a single atomic change to one cache line, owned by one CPU.

Before you begin

Eight ideas the paper assumes you know

Each card clears up one concept LLFree builds on. They're collapsed — tap any to open. If you've read the Knuth buddy-allocator primer, cards 1–2 will feel familiar.

1What a page-frame allocator actually does▾

Every time the kernel needs physical memory — for a process's heap, a kernel buffer, a huge page — it asks the page-frame allocator for N contiguous, MMU-aligned frames. On AMD64 that means orders 0 through 10: 4 KiB "base frames" (order 0) up to 4 MiB "giant frames" (order 10), with 2 MiB "huge frames" (order 9) the other size hardware actually cares about.

Now you're ready: LLFree is specifically a page-frame allocator, not a general-purpose malloc — it only ever hands out these fixed, hardware-aligned sizes.
2The Linux buddy allocator, in one paragraph▾

Linux's allocator is the classic buddy system (formalized by Knuth in TAOCP Vol. 1 §2.5 — see the companion guide): free blocks are kept in per-order doubly-linked lists; an allocation splits a larger free block in two if nothing the right size is available; a free tries to recursively re-merge a block with its "buddy" before shelving it. One spinlock per memory zone serializes every split and merge.

Now you're ready: LLFree doesn't reject the buddy idea's aligned-power-of-two sizing — it rejects the lock and the scattered linked-list state that Linux built around it.
3struct page: one 64-byte record per 4 KiB frame▾

Linux tracks metadata for every physical page frame in a struct page — 64 bytes on AMD64, repurposed by whichever kernel subsystem currently owns that page (LRU list pointers when free, mapping info when allocated, and so on). The buddy allocator itself uses those same 64 bytes to store its free-list pointers.

Now you're ready: this is why a "complete scan" of Linux's allocator state means touching one cache line per page frame — 33.5 million cache lines on a 128 GiB machine, versus LLFree's 67,754.
4Cache lines, false sharing, and why locks don't scale▾

Modern CPUs move memory between cores in fixed 64-byte cache lines. When two cores write to data sharing a cache line — even different bytes of it — the line ping-pongs between their private caches (false sharing), and a shared spinlock forces every core wanting it to wait in line, one at a time.

Now you're ready: the paper's Figure 1 shows exactly this cost — Linux's 4 KiB allocation time grows tenfold from 1 to 26 parallel threads, purely from lock contention and false sharing.
5Compare-and-swap (CAS): an atomic "if it's still X, make it Y"▾

A CAS instruction atomically checks whether a memory location still holds an expected value and, only if so, replaces it with a new one — all in one indivisible hardware step, no lock required. If another core changed the value first, CAS fails and the caller retries.

Now you're ready: LLFree's entire design is built so that one allocation or one free is exactly one CAS on exactly one cache line — that's what "lock-free" means here in concrete terms.
6NVRAM, crash consistency, and why logging is expensive▾

Byte-addressable non-volatile RAM (NVRAM, e.g. Intel Optane) keeps its contents across a power loss — so an allocator's bookkeeping state also survives a crash, and had better still be internally consistent afterward. The usual fix is write-ahead logging (record the intent before acting), which costs extra writes on every single operation.

Now you're ready: LLFree's pitch is that it needs zero logging for crash consistency — the trick is explained in How It Works.
7Huge-frame fragmentation▾

A 2 MiB huge frame only exists if all 512 of its constituent 4 KiB base frames are free and contiguous. If even one of those 512 is still allocated, the whole huge frame is unavailable — and the buddy system's per-order free lists have no concept of "almost-free" huge frames, so it can't prioritize completing them.

Now you're ready: this is "Problem 4" in the paper's own framing, and it's what LLFree's passive defragmentation behavior (Worked Example 5) is measured against.
8Per-CPU caches — Linux's existing scalability patch▾

To reduce contention on the per-zone lock, Linux gives each CPU a small local cache of free order-0-through-3 (and, since 5.13, order-9) frames, refilled/drained from the shared buddy structure in batches. It helps single-frame reuse a lot, but hides frames from defragmentation and adds its own synchronization cost.

Now you're ready: these caches are exactly why stock Linux can occasionally beat LLFree in the narrow best case (Worked Example 4) — and exactly what LLFree's design avoids needing at all.

The whole story in one place

LLFree in a nutshell

The problem, the two-level mechanism that fixes it, and how it all connects.

The paper's argument is blunt: the Linux buddy allocator was "well-founded when [it was] made," but five problems have compounded since. It mixes concerns — using the same buddy structure for both natural hardware sizes and arbitrary kernel-object sizes. Its merge cost is steep: forming one 2 MiB frame from scratch can require 511 recursive buddy-merge operations. Its scalability is bad — a single per-zone lock serializes every split and merge across every core. It suffers huge-frame fragmentation because per-CPU caches hide frames from the merge process. And its scattered, lock-protected, doubly-linked state makes it fundamentally unsuitable for persistent allocations, where a crash mid-operation must never leave the structure inconsistent.

LLFree answers all five with one structural idea: split the allocator into a lower level that does crash-consistent de/allocation, and an upper level, kept only in volatile DRAM, that provides scalability. The lower level packs 512 base frames into one 64-byte-aligned bit field (one cache line) plus a small counter; a base-frame allocation is one CAS on that bit field, a huge-frame allocation is one CAS on a 16-bit counter+flag pair. The upper level groups memory into 64 MiB "trees" that CPUs can pin as their own preferred source — so normal allocations touch no cache line any other CPU cares about.

The payoff, as measured: up to 88% faster 4 KiB allocation and 98% faster 2 MiB allocation than the Linux buddy allocator at 26 cores, a state footprint of 4.1 MiB versus Linux's 516 MiB on a 128 GiB/52-core machine, 64% fewer page-copy operations needed for memory compaction, and full crash recovery in 1,000 out of 1,000 injected-crash trials — with no write-ahead logging at all.

🍯 Key takeaways

  • Linux's buddy allocator has five compounding problems: mixed concerns, expensive merges, poor lock-bound scalability, huge-frame fragmentation, and unsuitability for persistent memory.
  • LLFree splits into a crash-consistent lower level (bit fields + child counters, one cache-line CAS per operation) and a scalability-providing upper level (per-CPU-reserved 64 MiB trees), kept only in volatile DRAM.
  • Reserve-on-free (frees return to their origin tree) and a free/partial/allocated tree classification keep allocations conflict-free without ever taking a lock.
  • Crash consistency falls out "for free": every de/allocation is already a single atomic write to a single cache line, so there's no window where a crash can leave state inconsistent — no logging needed.
  • Result: up to 88%/98% faster (4 KiB/2 MiB) than Linux at 26 cores, ~125× smaller state footprint, 64% less compaction cost, 1000/1000 successful crash recoveries — though not every scenario favors LLFree (Worked Example 4).
Six everyday pictures

What LLFree feels like

Every analogy below is useful for one part of the intuition and wrong for another — the "where it breaks" line is as important as the picture itself.

Hotel room blocks

Each front desk gets its own floor

Instead of every front-desk clerk fighting over one master reservation ledger, each clerk is handed their own floor of rooms to fill first. Only when a floor fills up does a clerk need to check with another floor. That's a CPU's "preferred tree" — a 64 MiB chunk it can allocate from without touching anyone else's bookkeeping.

Where it breaks: floors in a hotel don't get reassigned; LLFree's reservation can migrate to a different tree if the current one fills up or gets "stolen" under memory pressure.
A seating chart vs. a stack of tickets

One card instead of 512 slips of paper

Tracking whether 512 concert seats are taken with one master seating chart (a 512-bit field, one cache line) is instantly and atomically checkable. Tracking the same 512 seats with 512 individual paper ticket stubs scattered around the building (Linux's per-frame struct page records) means walking the building to know anything for certain.

Where it breaks: a real seating chart isn't updated by 26 ushers simultaneously — LLFree's version specifically has to survive that concurrent-write case atomically.
A librarian who never asks "may I?"

Compare-and-swap as a single confident motion

A librarian who knows exactly which shelf slot is empty reaches in, checks it's still empty, and places the book — all in one continuous motion, without needing to ask a supervisor's permission first. That's a CAS: a single atomic "if it's still empty, take it" with no lock, no waiting in line.

Where it breaks: if two librarians reach for the exact same slot at once, one of them has to notice the slot changed and try again — a CAS can fail and retry, unlike a real uninterruptible motion.
Returning a rental to the branch you took it from

Reserve-on-free exploits where things came from

A car-rental network that always routes a returned car back toward the branch it was originally rented from (rather than wherever the drop-off happens to be) keeps each branch's inventory naturally balanced over time — no central coordinator required. LLFree frees a page back to its origin tree for the same reason.

Where it breaks: LLFree assumes a page freed by CPU A was likely allocated by (and near other pages from) the same tree — a workload with truly random alloc/free patterns weakens this benefit.
Fuel gauge, not a fuel-tank inspection

One counter instead of scanning every frame

Knowing how much gas is left doesn't require opening the tank and measuring — the gauge (a running free-frame counter per tree) already tells you. LLFree's trees are classified free / partial / allocated purely by reading this one counter, no scan required.

Where it breaks: a gauge can't tell you which specific frames are free within the tank — for that, LLFree still needs the bit field one level down.
A power-outage-proof notebook

No "half-written sentence" is ever left behind

If every entry in a notebook is written in one indivisible stroke — nothing is ever half-written when the lights go out — you never need a separate "draft log" to recover from a power cut; you just read what's there. LLFree's single-cache-line CAS gives it exactly this property, which is why it needs no write-ahead log for crash consistency.

Where it breaks: this only holds for the paper's "natural" sizes (4 KiB, 2 MiB); non-natural kernel-object sizes need multiple CAS steps and lose the single-stroke guarantee (How It Works, step 10).
Mechanism, step by step

From "give me a page" to a single CAS

Eleven steps, from the two-level layout to what happens after a crash.

  1. The allocator has two levels. A lower level performs actual de/allocation and must be crash-consistent (only it needs to live in NVRAM for a persistent-memory zone). An upper level provides scalability by managing which CPU allocates from where — it always lives in volatile DRAM, even on a persistent-memory zone, since it can be rebuilt after a crash.
  2. Lower level: one bit field per 2 MiB child. Memory is divided into "children" of 512 base frames (2 MiB) each. Each child gets a 512-bit field (one bit per 4 KiB frame: 0 = free, 1 = allocated) — exactly 64 bytes, one cache line — plus a small free-count and an "allocated as huge frame" flag packed into a 16-bit child-table entry.
  3. Upper level: trees of 32 children. N=32 children are grouped into a "tree" spanning 64 MiB, chosen so the tree's own child array also fits in one cache line. Each tree root tracks a free-base-frame count and a "reserved" flag.
  4. Each CPU pins a preferred tree. To avoid false sharing on the child array, a CPU that needs a new tree "reserves" one (sets the reserved flag) and moves that tree's free counter into a CPU-local copy — subsequent allocations and frees from that CPU only touch its own local counter, not the shared one.
  5. Allocating a 4 KiB base frame. The CPU atomically decrements its local free counter (bailing out to reserve a new tree if it hits zero), then sequentially searches the corresponding bit field for a zero bit and sets it with a CAS — touching one or two cache lines total, no lock.
  6. Allocating a 2 MiB huge frame. This is even cheaper: a single 16-bit CAS changes the child's free-count from 512 to 0 and sets the "allocated" flag — one atomic operation, one cache line, no bit-field scan needed.
  7. Choosing which tree to reserve: free / partial / allocated. When a CPU needs a new tree, trees are classified by their free-count: free (>87.5% free), partial (12.5–87.5%), or allocated (<12.5% free). The search heuristic prefers partial trees first (they're least likely to still yield huge frames if left alone), then free ones, searching neighboring cache-line-adjacent trees first, then the whole array, and finally stealing a reservation from another CPU as a last resort.
  8. Freeing: reserve-on-free. A freed frame's bit is always cleared in the tree it originally came from — not necessarily the freeing CPU's own preferred tree — on the empirically-motivated assumption that frees exhibit locality with their original allocation. If a CPU's frees repeatedly land in some other tree (four times in a row, in the paper's tuned threshold), that tree becomes its new preferred one.
  9. Crash consistency, concretely. Because every de/allocation is already one atomic write to one cache line, there's no intermediate state a crash could ever observe as "half-done." Recovery just re-derives the volatile upper level from the persistent lower level: for each child, if its "allocated huge frame" flag is set, the whole child is huge-allocated; otherwise its bit field is the authoritative record, and its free-count is recomputed from a population count over the 512 bits. No write-ahead log, ever.
  10. The exception: non-natural orders.
    ⚠
    Linux's kernel-object allocations need every order 0–10, not just 0 and 9. LLFree handles orders 1–6 like order 0 (searching for an aligned run of zero bits), but orders 7, 8, and 10 need 2–4 chained CAS operations with rollback-on-failure — which the paper explicitly notes breaks the single-cache-line persistence guarantee for those specific sizes. It's an accepted, narrow trade-off, not swept under the rug.
  11. The net effect on Linux. Integrating LLFree meant Linux no longer needs its buddy allocator's per-zone locks, per-CPU caches, or "high-atomic" huge-page-protection heuristics for the zone LLFree manages — those mechanisms existed specifically to paper over problems LLFree's structure doesn't have in the first place.
Real numbers from the paper

Seven ways to see the difference

Every number below is from the paper's own evaluation (DELL PowerEdge R750, 2× Xeon Gold 5320, 256 GiB DRAM + 1 TiB Optane, 26 cores/socket) — including the one case where LLFree loses.

1 · State dispersion: 4.1 MiB vs. 516 MiB

On a 128 GiB / 52-core machine, LLFree's entire metadata footprint is 4.14 MiB (0.0032% of DRAM): 4.0 MiB of bit fields, 128 KiB of child counters, 32 bytes of per-tree data. Enumerating it all touches 67,754 distinct 64-byte cache lines. Linux's buddy allocator, by contrast, stores most of its state inside struct page — 512 MiB just for the free-list pointers it repurposes there, for a total of 516 MiB (0.39% of DRAM) spread across 33,554,169 separate cache lines, since each struct page lives on its own line.

2 · 4 KiB allocation latency under parallel load

With all 26 cores of one socket allocating 4 KiB frames in parallel, Linux's per-frame time grows roughly tenfold as core count rises (94 ns → 984 ns). LLFree's allocation and free reservation system keeps this almost flat, translating into up to an 88% reduction in allocation time for concurrent 4 KiB allocations versus the Linux buddy allocator.

3 · 2 MiB allocation: the gap widens

For 2 MiB huge-frame allocations, Linux's parallel slowdown is worse still — up to 27× slower at 26 cores versus one. LLFree reduces 2 MiB allocation time by up to 98% compared to Linux, and the paper's abstract highlights a 53× speedup for concurrent 2 MiB DRAM allocations specifically at 26 cores.

4 · Where LLFree actually loses. In the "repeat" benchmark — each core allocates and frees a single frame as fast as possible, the best possible case for Linux's per-CPU caches — Linux beats LLFree for the cached orders (0–3, 9). For order 0 specifically: 112 ns (Linux) versus 183 ns (LLFree). The paper is upfront that this is also the least realistic workload: real programs do lazy allocation via demand paging with bulk or random frees, not tight single-frame reuse loops.

5 · Passive defragmentation of huge frames

Starting from a worst-case fragmented state (90% of a 125 GiB region randomly allocated, then half freed) and cycling 10% of memory through 100 random-reallocation iterations: Linux's buddy allocator recovers only 1 additional huge frame over the entire run, with compaction cost dropping just 3.3%. LLFree recovers 46.6% of the initially-fragmented huge frames passively — with no active compaction step at all — purely as a side effect of its subtree-allocation policy.

6 · Crash recovery: 1,000 for 1,000

The paper injected 1,000 simulated crashes (random SIGKILL during concurrent alloc/free on a DAX-mapped NVRAM region) and recovered allocator state correctly in every single case — losing at most one frame per active core in about half the trials, the theoretical worst case for any lock-free design. Full recovery (rebuilding the DRAM upper level by scanning every child entry) took 2,460 µs on average; a routine (non-crash) restart, which can trust the upper level, took only 477 µs.

7 · Does it actually help a real application?

Running the memtier benchmark against memcached (a realistic Get/Set workload), the paper found no significant throughput difference between LLFree and the stock Linux buddy allocator. The honest explanation given: the page-fault handler that invokes the allocator is only 5.3% of total runtime in a flame-graph breakdown (most time goes to struct mm rw-locks, LRU/cgroup bookkeeping, and reverse-mapping updates) — so a faster allocator alone can't fix a bottleneck that lives elsewhere in the memory-management stack.

Check your understanding

Five questions, misconceptions flagged

Try answering before revealing — each answer names a specific misconception it's checking for.

Medium
Q1. Does LLFree eliminate Linux's struct page entirely?
Show answer
No. Other kernel subsystems still rely on struct page for allocated frames (mapping info, reference counts, etc.), and the paper explicitly leaves full elimination as future work. What LLFree removes is the need to touch struct page during de/allocation of free frames — that's where the state-dispersion win comes from.Misconception checked: assuming "much smaller state footprint" means "struct page is gone."
Medium
Q2. Is LLFree a persistent-memory-only allocator?
Show answer
No — it's a general-purpose allocator for volatile DRAM that optionally provides crash consistency when deployed on an NVRAM zone. The same design runs identically either way; persistence is a property of where you put the lower-level data, not a separate code path.Misconception checked: conflating "supports persistence" with "requires persistent memory to work at all."
Hard
Q3. Why not just give LLFree more per-CPU caches, the way Linux did to fix its own scalability?
Show answer
Per-CPU caches hide frames from defragmentation (a cached frame can't be merged into a huge frame while it's sitting in someone's cache) and would reintroduce exactly the crash-consistency problem LLFree avoids — a crash mid-cache-drain would need to reconcile a redundant, possibly-inconsistent cached copy against the authoritative structure. LLFree's per-CPU-reserved trees get similar contention avoidance without a separate redundant cache to keep in sync.Misconception checked: assuming any two "give each CPU its own copy" schemes are interchangeable.
Hard
Q4. Does LLFree still do the classic buddy split/merge dance (halving and recombining blocks)?
Show answer
No. LLFree has no recursive buddy-merge chain at all — there's no scenario analogous to needing 511 buddy-merge operations to assemble one 2 MiB frame from 4 KiB pieces. A huge frame's availability is read directly off one child's free-counter; a base-frame's availability is read directly off one bit in the bit field. Nothing is split or merged as a multi-step operation.Misconception checked: assuming LLFree is "the buddy system, but faster" rather than a structurally different two-level scheme.
Easy
Q5. Is LLFree strictly faster than the Linux buddy allocator in every measured scenario?
Show answer
No — in the repeat benchmark's best case for Linux's per-CPU caches (single-frame reuse, cached orders), stock Linux is faster: 112 ns versus 183 ns for order 0 at scale. LLFree wins broadly and especially under real contention or bulk/random patterns, but the paper doesn't claim a universal win.Misconception checked: treating a paper's headline numbers as true in every workload, not just the ones it wins.
Common questions

FAQ

Q·What does "LLFree" actually stand for?▾
Log- and Lock-Free — the two properties the design is built around. Every operation is a single atomic hardware instruction (no locks) and crash consistency requires no write-ahead log (no logging).
Q·How does this relate to the classic buddy allocator (Knuth, Linux)?▾
LLFree is explicitly framed as a critique and replacement of that lineage — it keeps the idea of power-of-two-aligned, hardware-sized allocation units, but replaces the buddy system's linked free-lists, per-zone lock, and recursive split/merge with a two-level, cache-line-atomic structure. See the companion Knuth buddy-allocator primer for the classic scheme this paper is answering.
Q·Is LLFree actually merged into mainline Linux?▾
No — it's a research prototype: 2,199 lines of safe Rust (plus 25 unsafe lines for initialization and address translation) implementing the allocator itself, integrated into a modified Linux 6.0 kernel by replacing page_alloc.c's core logic (changing 415 lines, adding a 942-line wrapper module). It is not upstream.
Q·Why did they write it in Rust?▾
The authors explicitly wanted to explore whether Rust's stricter memory-safety guarantees (versus C) were viable for a performance-critical kernel module, and report that Rust's safety properties simplified development without compromising the performance results.
Q·What hardware guarantee does the "no logging needed" claim actually lean on?▾
eADR (enhanced Asynchronous DRAM Refresh), available on the paper's Gen-3 Xeon Gold + Optane Gen-2 test platform. eADR guarantees that once a write is visible to other cores (memory consistency), it's also guaranteed to reach NVRAM on a power loss (persistence consistency) — letting LLFree skip explicit cache-flush instructions (like clwb) that older non-eADR NVRAM platforms would require.
Q·What's the honest catch?▾
Two, both acknowledged directly in the paper. First, non-natural allocation orders (needed for kernel objects, not just hardware page sizes) require multi-step CAS sequences that break the single-cache-line persistence guarantee for those sizes. Second, end-to-end application benchmarks (memtier/memcached) showed no significant throughput improvement, because the allocator itself is a small fraction of total memory-management overhead in a real workload.
