A vulnerability threshold that quietly drifts — not one that holds still

Every RowHammer/RowPress defense assumes you can pin down the exact number of activations that breaks a DRAM row. 160 real DDR4 chips and 4 HBM2 chips say otherwise: that number wanders, unpredictably, for tens of thousands of measurements.

📄 "Variable Read Disturbance" · Olgun et al., ETH Zürich / Rutgers 🎓 Some DRAM circuit basics assumed — the primers cover them ⏱ ~30 min read
🎯

A DRAM row's read disturbance threshold is not a fixed number — it's a moving target sampled from a noisy process, and one or a few measurements will not find its worst case.
Measure it 100,000 times, and it still might surprise you on the 100,001st.

Quick glossary, then the primers

The acronyms first, so nothing below is opaque. Then eight collapsed cards covering the DRAM-circuit background the paper assumes — open whichever looks unfamiliar.

1Activating a DRAM row (ACT/PRE, wordline, charge restoration)▾

A DRAM cell stores a bit as charge on a capacitor. Asserting a row's wordline (an ACT command) connects every cell in that row to its sense amplifier so the data can be read/written; a PRE command closes it again. Activating a row briefly disturbs its own cells' charge, which must be restored — this restoration process is also what disturbs neighboring rows electrically.

Now you're ready: read disturbance is a side effect of this restoration process repeatedly happening on one row while a physically adjacent row silently loses charge.
2RowHammer vs. RowPress▾

RowHammer: activate an aggressor row many times (tens of thousands) and a nearby victim row flips bits. RowPress: keep the aggressor row open for a long single interval (tAggOn) instead, and far fewer activations are needed. Both are "read disturbance" — they just trade activation count for open time.

Now you're ready: this paper's hammer-count metric (RDT) is measured under both regimes — a range of tAggOn values from minimum tRAS up to 9×tREFI.
3Read Disturbance Threshold (RDT), precisely▾

RDT is a single number per row: the hammer count (activations per aggressor row) needed to produce the first bitflip in that row's victim. Every mitigation technique — refresh-based or otherwise — needs to know this number, because it tells the defense how many activations it can safely allow before acting.

Now you're ready: the entire paper is about whether "the RDT of a row" is even a well-defined, stable number you can measure once and trust.
4Double-sided hammering, aggressor and victim rows▾

The standard test pattern activates the two rows physically adjacent to a victim row, alternately, many times — double-sided RowHammer. Because logical row addresses don't map straightforwardly to physical layout, finding the true physical neighbors requires reverse-engineering the manufacturer's address mapping first.

Now you're ready: "hammer count" in this paper always means activations per aggressor row in this double-sided pattern, using one of four fixed data patterns (Rowstripe0/1, Checkered0/1).
5Why the authors disable TRR and refresh▾

Real chips ship with on-die defenses (e.g., TRR) that refresh suspected victim rows before a bitflip appears — precisely the kind of mitigation this paper studies the security of. To measure the true, un-mitigated RDT, the authors disable periodic refresh (which disables all known on-die defenses) and confirm no on-die ECC is silently correcting bitflips.

Now you're ready: every RDT number in this paper is the chip's raw physical vulnerability, isolated from any defense — the number a mitigation technique like PRAC would need to know accurately.
6Why one measurement isn't a measurement — sampling intuition▾

If a quantity is itself the outcome of a random process, one observation only tells you one sample from a distribution, not the distribution's extreme value. To find a distribution's minimum with confidence, you need many independent draws — and even then, the more times you draw, the more likely you are to eventually hit an unusually low value.

Now you're ready: this paper's central experiment is exactly this — treating each RDT measurement of the same row as a draw from an unknown distribution, then asking how many draws it takes to find the true minimum.
7Coefficient of variation and autocorrelation▾

CV (std ÷ mean) is a unitless way to say "how spread out" a row's repeated RDT values are — CV = 0 means every measurement gave the same value; CV = 0.5 means the spread is comparable to the mean itself. ACF asks a different question: does today's value help predict tomorrow's? An ACF that looks like pure noise means no — each measurement is statistically independent of the last.

Now you're ready: the paper uses CV to quantify how much a row's RDT varies, and ACF to argue that the variation isn't a hidden cycle you could learn to predict and exploit.
8Guardbands and error-correcting codes▾

A guardband configures a mitigation with a threshold smaller than the observed minimum RDT, as a safety margin — e.g., "assume the row breaks at 900 activations even though we measured 1000." SECDED ECC corrects one bit-error and detects two per codeword; Chipkill-like SSC can correct an entire failed chip's worth of bits in a codeword, at higher cost.

Now you're ready: the paper's proposed stopgap is exactly this combination — guardband plus ECC — and it quantifies what that combination costs in performance.
The whole story in one place

Variable Read Disturbance, in a nutshell

The assumption everyone made, the experiment that breaks it, and what's left to do about it.

Every read-disturbance mitigation — from software patches to the JEDEC-standardized PRAC now shipping in DDR5 — rests on one assumption: that a DRAM row's read disturbance threshold (RDT) is a fixed, measurable physical property, like the distance between two rows. Measure it once (or a few times), configure the defense with that number, and the defense holds.

This paper tests that assumption directly, characterizing 160 DDR4 chips and 4 HBM2 chips from all three major manufacturers with up to 100,000 repeated RDT measurements per row. The result: RDT is not fixed. It changes significantly and unpredictably across successive measurements — a phenomenon the authors name Variable Read Disturbance (VRD). For one tested row, the minimum RDT across 1,000 measurements is 3.5× smaller than the maximum observed for that same row. Across all tested rows, the true minimum can take as many as 94,467 measurements to appear even once.

VRD gets worse in higher-density chips and more advanced technology nodes, and it shifts with data pattern, aggressor row on time, and temperature — so a comprehensive profile of even one row requires re-testing it under many conditions. Because exhaustively profiling every row this way is prohibitively slow (tens of days per bank, per test condition), the authors evaluate a stopgap: a guardband below the observed minimum RDT, combined with error-correcting codes. A guardband of just 10% is nearly free in performance but leaves real, if small, uncorrectable-error probability; a guardband large enough to feel safe (50%) costs up to 45% performance in a state-of-the-art mitigation technique.

🍯 Key takeaways

  • RDT is not a fixed property of a row — it changes unpredictably across repeated measurements (VRD).
  • 97.1% of all tested rows exhibit VRD across every combination of test parameters.
  • The minimum RDT can take up to 94,467 measurements to appear; a row's max/min ratio can reach 3.5×.
  • A single measurement has, for the median row, only a 0.2% chance of hitting the true minimum.
  • VRD worsens with higher density and more advanced technology nodes; it also shifts with data pattern, tAggOn, and temperature.
  • The data resembles independent draws from a Gaussian — statistically noise-like, with no exploitable repeating pattern (yet mechanistically unexplained).
  • A guardband + ECC stopgap trades security margin for performance: ~6% loss at 10% guardband, up to 45% at 50%.
Six everyday pictures

How to think about VRD

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · VRD itself

A combination lock that drifts overnight

Imagine a safe whose correct combination isn't the one you set — it wanders a little each time you check it, never settling. Checking it once tells you almost nothing about whether tomorrow's combination will be higher or lower. That's a DRAM row's RDT: not a fixed number waiting to be discovered, but a value that keeps re-drawing itself.

Where it breaks: a real lock's drift would eventually be learnable; the paper finds no such learnable pattern (§4.1) — the "drift" looks statistically like independent random draws, not a slow slide.
Sampling · Probability of finding the minimum

Guessing tomorrow's weather from one glance

Glance outside once and you'll estimate today's weather — but you won't learn the coldest temperature the year could produce. You'd need many days of readings, and even then, an unusually cold day could still be waiting past your last observation. A single RDT measurement is exactly this one glance: for the median tested row, it has only a 0.2% chance of hitting the true minimum found across 1,000 tries.

Where it breaks: weather has seasonal structure you could eventually learn; the paper's ACF analysis (§4.1) finds RDT measurements don't — each is closer to an independent draw than a trend you can anticipate.
Predictability · Autocorrelation

Static between two radio stations

Tune a radio to dead air between stations and you hear hiss — no melody, no repeating beat, just noise that resembles the same statistical shape moment to moment. That's what the paper finds when it checks whether one RDT measurement predicts the next (autocorrelation): the series looks like the hiss, not a song. A Chi-square test also can't reject that the values are normally distributed (p ≥ 0.18 for every tested chip).

Where it breaks: radio static truly has no hidden cause; the authors explicitly do not claim RDT is causeless — they hypothesize an underlying physical mechanism (charge traps, akin to variable retention time) that current data simply can't yet confirm (§4.2).
Mitigation · Guardband + ECC

A parachute, plus a spare — still not zero risk

A skydiver's spare parachute doesn't make the jump risk-free; it converts a likely disaster into an unlikely one. A guardband (configuring a defense below the observed minimum RDT) plus ECC works the same way: at a 10% margin with SECDED, the paper's own worst empirically observed error rate still yields a small but non-zero probability of an uncorrectable error (1.48×10⁻⁵) — smaller, not zero.

Where it breaks: a skydiver's spare-chute failure rate is roughly fixed; here the "failure rate" itself is estimated from a limited number of measurements on a limited set of chips — the true tail risk could be worse than what was observed (§6.5).
Scaling trend · Density & technology node

Packing more tenants into the same building

Squeeze more apartments into the same floor plan and shared walls get thinner — noise leaks between units more easily. DRAM scaling is similar: as density rises and technology nodes advance, cells and their neighbors pack closer together, and the paper finds VRD's profile measurably worsens — e.g., one manufacturer's median expected error at a single measurement rises from 1.06× to 1.08× the true minimum as density/node advances (Finding 11).

Where it breaks: thinner apartment walls affect every tenant roughly equally; VRD's severity varies row-by-row even within the same chip, so density is a trend across chips, not a uniform per-row multiplier.
Practicality · Exhaustive testing cost

Recalling every car for a one-in-a-million defect

A manufacturer chasing an intermittent, rare defect can't just inspect each car once — they may need to stress-test each one repeatedly, for a long time, before the defect reliably shows. Profiling every row's RDT with enough measurements to trust the minimum is the same kind of expensive: even a modest 94,467-measurement profile of one bank's 256K rows takes about 29 days — for just one data pattern, one tAggOn, one temperature.

Where it breaks: a car recall is a one-time event; a DRAM chip must be profiled (in principle) continuously as it ages and its behavior potentially shifts further — a car doesn't need to be re-recalled every few months.
The full explanation

How the characterization actually works

Section by section, with the paper's key numbers and diagrams rebuilt as visuals you can read at a glance.

1 · The two-step testing algorithm

To study temporal variation, the authors first find a relatively vulnerable row (find_victim), then hammer it thousands to hundreds of thousands of times in a loop (test_loop), recording the RDT found on every pass:

# Step 1: find a vulnerable row (10 quick measurements, Checkered0 pattern)
for row in bank:
    RDTguess = mean(measure(row, 10 times))
    if RDTguess < 40,000: return row, RDTguess

# Step 2: repeatedly re-measure that one row
range = [RDTguess/2, RDTguess*3], step = RDTguess/100
for i in 1..100,000:
    search hammer-count range for the first bitflip
    record that hammer count as this pass's RDT

This yields a series of up to 100,000 independent RDT observations for one row — the raw material for every finding below.

2 · A row's RDT has multiple discrete states

Histogramming the 100,000-measurement series per row shows RDT doesn't cluster at one value — it visits a handful to dozens of distinct values (e.g., 21 unique values on module M1). For 13 of 14 closely studied rows, values cluster around a mean (roughly bell-shaped); one HBM2 chip shows a bimodal pattern instead.

📊
How often does it change? Across all tested rows, 79.0% of consecutive measurement pairs yield a different RDT value. A row keeping the same RDT for 14 measurements in a row happened exactly once, across the entire dataset.

3 · Is the variation predictable?

Two independent checks say no. First, a Chi-square goodness-of-fit test asks whether each row's histogram resembles a normal distribution derived from its own mean and standard deviation; the minimum p-value across all tested chips is 0.18 — comfortably above the α = 0.05 threshold for rejecting that hypothesis. Second, the autocorrelation function (ACF) of a 100,000-measurement series looks statistically indistinguishable from the ACF of 100,000 independently drawn normal random numbers — no repeating structure at any time lag.

💡
These two results together support the paper's central claim: RDT variation isn't slow drift or a hidden cycle you could learn and route around — each measurement behaves like an independent sample from a stable, unpredictable distribution.

4 · How many measurements does it take to find the minimum?

Using Monte Carlo resampling (10,000 iterations per row, drawing N < 1,000 samples from each row's 1,000-measurement series), the authors compute the probability that N measurements surface the true minimum RDT.

5 · What makes VRD worse

Beyond the base phenomenon, four factors systematically shift how bad VRD is for a given row:

FactorDirectionExample (median row, N = 1 measurement)
Die density / nodeHigher density, more advanced node → worseMfr. M: 1.06× → 1.08× expected value as density/node rises

Not a factor: true-cell vs. anti-cell layout (how a "1" is physically encoded) shows no significant effect on RDT distribution in the one module tested for it (Finding 17).

6 · The guardband + ECC stopgap, quantified

Simulating four state-of-the-art mitigations (Graphene, PRAC, PARA, MINT) at RDT = 128 with increasing guardbands:

And even a large guardband isn't provably sufficient: at N = 500 measurements, the minimum (worst-case row) probability of landing within a 50% safety margin of the true minimum is only 74.91% — not 100%. At the empirically observed worst bit-error rate (7.6×10⁻⁵, from 5 bitflips in a 64 Kibit row at a 10% margin), even Chipkill-like SSC ECC leaves a 5.66×10⁻⁵ probability of an uncorrectable error.

⚠
The honest bottom line (§6.5): the authors explicitly do not claim a guardband + ECC combination is guaranteed safe — their measurement budget (1K–10K samples, 164 chips) can't rule out worse tail behavior than observed.
Follow the numbers, step by step

Worked examples

Four calculations, carried through with the paper's own numbers.

① Why exhaustive profiling takes 29 days for one bank

The paper states 94,467 measurements take ~9.5 seconds for one row averaging RDT ≈ 1,000. How long to do this for every row in a 256K-row bank?

  1. Per-row time: 9.5 seconds for 94,467 measurements of one row.
  2. Scale to the bank: 9.5 s × 256,000 rows = 2,432,000 seconds.
  3. Convert: 2,432,000 s ÷ 3600 = 675.6 hours ÷ 24 = 28.15 days ≈ 29 days — matching the paper exactly.
  4. But that's only one test condition. VRD also shifts with data pattern (4 patterns), tAggOn (3 values), and temperature (3 levels) — a fully comprehensive profile multiplies this by up to 36×, into years.
🍯
Insight: "just measure more" is not a free lunch — the paper's own Appendix A shows even a single, narrower RowHammer sweep (1K measurements, all 32 banks) takes 15 hours, while the RowPress equivalent takes 48 days.

② Reading the headline 3.5× number

The abstract's "3.5× smaller" claim comes from one specific row (Fig. 7b, P100). Its 1,000 measurements ranged from 3,242 to 11,498. Verify the ratio and connect it to CV.

  1. Ratio: 11,498 ÷ 3,242 = 3.547 ≈ 3.5× — confirmed.
  2. This row's CV is reported as 0.52 — the highest (worst) observed across all tested rows.
  3. Contrast with the P50 (median) row in the same figure: range 1,740–2,040, ratio 1.2×, CV = 0.03 — an order of magnitude tighter spread.
  4. Takeaway: "the average row is fine" and "the worst row is fine" are very different claims — a guardband sized for the median row would be badly wrong for the P100 row.
💡
This is exactly why mitigation techniques need the minimum RDT across all rows, not a typical or average one — one bad row breaks the security guarantee for the whole chip.

③ The diminishing return of more measurements

Probability of finding the true minimum (median row): 0.2% at N=1, 75.3% at N=500. Is testing 500× as long worth it?

  1. N=1 → N=10: a 10× increase in measurements moves probability from 0.2% to 2.1% — roughly proportional.
  2. N=10 → N=500: a further 50× increase in measurements moves probability from 2.1% to 75.3% — a much bigger jump, but still short of certainty.
  3. Cost check: at ~9.5 s per ~94,000-measurement campaign for one row, 500 measurements of one row (with a similarly-scaled hammer sweep) is on the order of seconds — cheap for one row, but multiply by every row in a bank (256K) and it's back to hours-to-days territory.
  4. And it's still not 100%: even at N=500, some individual rows only reach ~50% probability — meaning "test 500 times" is not a proof of safety, just a much better bet.
🍯
Insight: there is no N at which the probability of finding the minimum provably reaches 100% — this is a fundamentally probabilistic guarantee, not a deterministic one.

④ Pricing the guardband + ECC stopgap

Compare a "cheap and risky" 10% guardband against a "safer but expensive" 50% guardband, using the paper's own performance and error-rate numbers.

  1. Performance at 10% guardband (RDT=128): Graphene −1.0%, PRAC 0.0%, PARA −5.9%, MINT 0.0% — nearly free.
  2. Performance at 50% guardband: Graphene −8.5%, PRAC −7.6%, PARA −35.0%, MINT −45.0% — the worst case is a near-halving of throughput.
  3. Safety at 10% guardband + SECDED: at the observed worst bit-error rate (7.6×10⁻⁵), uncorrectable-error probability = 1.48×10⁻⁵, undetectable = 2.64×10⁻⁸.
  4. Safety at 10% guardband + Chipkill-like SSC: uncorrectable = undetectable = 5.66×10⁻⁵ — worse than SECDED's undetectable rate here, because SSC's 144-bit codeword spans more symbols that can each fail.
  5. Verdict: going from 10% to 50% buys a large drop in the probability of missing the true minimum (per §6.4, min-probability-within-margin rises from 48.62% to 74.91% at N=500) at the cost of up to 45% performance — and even then, isn't proven safe.
💡
This is the paper's core policy tension: security margin and performance trade off directly, and no tested combination reaches certainty — only lower risk.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A manufacturing test measures a row's RDT once, gets 8,000, and configures a mitigation technique with that value. Is this safe?
Show answer
No. A single measurement has, for the median row, only a ~0.2% chance of matching the true minimum RDT found across 1,000 repeated measurements — and the true minimum could be significantly lower than 8,000. Configuring a defense above the true minimum RDT of any row on the chip means that row's bitflips are no longer prevented.Misconception: that RDT is a fixed physical property (like row spacing) rather than the outcome of a noisy, repeatable-but-not-identical process.
Problem 2 · medium
Two rows are both reported to have "typical" VRD behavior on average. Row A has CV = 0.03, Row B has CV = 0.52. Explain why an "average" characterization can be misleading here.
Show answer
CV (std ÷ mean) measures spread, not central tendency — two rows can have similar mean RDT but wildly different worst-case behavior. Row B (CV = 0.52, the paper's worst observed case) has a max/min ratio of 3.5× across 1,000 measurements, while Row A (CV = 0.03) varies only ~1.2×. A guardband or defense sized around "typical" behavior (like Row A) would badly under-protect a Row-B-like outlier.Misconception: that reporting a mean or "typical" case captures the risk that matters — security requires reasoning about the worst row, not the average one.
Problem 3 · medium
A colleague says "if 29 days is too slow for one test condition, just parallelize across more banks." What's still missing from a truly comprehensive profile even with unlimited parallel banks?
Show answer
VRD's profile shifts with data pattern (4 tested), aggressor row on time (3 tested), and temperature (3 tested) — a comprehensive characterization needs to re-run the measurement campaign across all combinations of these, not just parallelize one fixed condition across banks. Parallelizing banks addresses the row-count dimension of the cost, not the parameter-combination dimension.Misconception: that testing cost is purely about "more rows" rather than "more rows × more conditions" — VRD's dependence on data pattern, t_AggOn, and temperature (Takeaways 3–4) multiplies the problem.
Problem 4 · hard
A 10% RDT guardband combined with SECDED ECC is proposed as "safe enough." Using Table 3's numbers, evaluate that claim.
Show answer
At the empirically observed worst bit-error rate (7.6×10⁻⁵), a 10% guardband with SECDED still yields a 1.48×10⁻⁵ probability of an uncorrectable error and 2.64×10⁻⁸ probability of an undetectable one — small, but not zero. The authors explicitly caution (§6.5) that these numbers come from a limited measurement budget (10,000 repeated tests, 50 rows/module) and cannot rule out worse tail behavior on unmeasured rows or under unmeasured conditions. "Safe enough" is a judgment call about acceptable residual risk, not a guarantee.Misconception: that a nonzero-but-small probability from a limited experiment constitutes a proof of safety — the paper is careful to call this "likely unsafe" for small margins, not disproven-risky.
Problem 5 · medium
Higher-density chips show worse VRD (Finding 11). A researcher hypothesizes this is because denser chips use more anti-cells (rather than true-cells) for data encoding. Does the paper support this?
Show answer
No. Finding 17 directly tests this: comparing 20 rows with anti-cells against 30 rows with true-cells in the same module (M0) shows no significant difference in RDT distribution across data patterns, temperatures, or aggressor row on times. The density/technology-node effect (Finding 11) is a separate, confirmed trend; cell-encoding polarity is a tested and rejected explanation, at least in this module.Misconception: assuming any two correlated-sounding technology trends (density scaling, cell encoding) must share a causal explanation — the paper tests this specific hypothesis and finds no support for it.
Problem 6 · hard
The paper reports that RDT's autocorrelation function resembles that of Gaussian random noise, and a Chi-square test can't reject a normal-distribution fit. Does this mean VRD's physical cause is now understood?
Show answer
No. These are statistical descriptions of the outcome — the shape of the measurement series — not a mechanistic explanation of why it happens. The authors explicitly frame their charge-trap hypothesis (§4.2) as unconfirmed: "we are not aware of any device-level study of temporal variations in read disturbance vulnerability, so we cannot definitively confirm this hypothesis." Statistical noise-likeness and physical-mechanism understanding are different claims.Misconception: conflating "behaves statistically like noise" with "we know what causes it" — the paper is explicit that device-level confirmation is future work.
Problem 7 · easy
Does testing at a single fixed temperature and single fixed tAggOn give a complete picture of a row's worst-case RDT?
Show answer
No. Both temperature and aggressor row on time independently shift a row's VRD profile (Findings 14–16) — e.g., temperature rising from 50°C to 80°C worsened the expected minimum-RDT estimate for a tested module, and t_AggOn's effect can go either direction depending on the manufacturer. A profile taken under one fixed condition doesn't bound behavior under other realistic operating conditions.Misconception: that RDT characterization is a single-axis problem (just "measure enough times") when it's actually multi-dimensional across pattern, timing, and environment.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly did the authors discover?▾
That a DRAM row's read disturbance threshold (RDT) — the hammer count needed to induce the first RowHammer or RowPress bitflip — changes significantly and unpredictably across repeated measurements of the very same row, under identical test conditions. They name this Variable Read Disturbance (VRD).
Q2Is VRD the same thing as RowHammer or RowPress?▾
No. RowHammer and RowPress are the mechanisms that cause bitflips (repeated activation vs. prolonged open time). VRD is a separate, newly-identified phenomenon about the measurement of the threshold at which those mechanisms cause a bitflip — VRD is orthogonal to which mechanism you're testing.
Q3Is VRD the same as variable retention time (VRT)?▾
The paper explicitly declines to equate them. VRD "may differ" from VRT (data-retention-time variability); the authors say there isn't enough scientific information yet to confidently explain the relationship, and recommend studying VRD independently while hoping future device-level work clarifies the connection.
Q4Why can't we just test each row enough times to find the true minimum?▾
Because "enough times" can be enormous (up to 94,467 measurements for some rows) and testing time scales with rows × conditions. Exhaustively profiling one bank (256K rows) at that scale takes ~29 days for a single test-parameter combination — and VRD's profile shifts with data pattern, t_AggOn, and temperature, multiplying that cost further.
Q5Does this break PRAC, the current JEDEC DDR5 standard mitigation?▾
The paper's point is conditional: PRAC's (and any mitigation's) security guarantee depends on being configured with an accurately identified minimum RDT. If that value was identified from too few measurements, PRAC would eventually fail to prevent a bitflip on a row whose true minimum RDT is lower than assumed. The paper doesn't claim PRAC as deployed is already broken — it questions the measurement process feeding into it.
Q6What physically causes VRD?▾
Unconfirmed. The authors' hypothesis is that electron migration/injection into the victim cell — already known to be assisted by charge traps near the aggressor/victim shared region — has traps whose occupied/unoccupied state changes randomly over time, similar to the accepted explanation for variable retention time (VRT). They're explicit this needs device-level confirmation.
Q7Does a bigger guardband just solve the problem?▾
It reduces risk but doesn't eliminate it, and it's expensive. A 50% guardband still leaves a 25.09% chance (at N=500 measurements) that the true minimum RDT falls outside that margin for the worst-case row, and costs up to 45% performance in the paper's simulations. The authors do not recommend relying on guardbands alone.
Q8Does VRD get better or worse as DRAM technology advances?▾
Worse, generally. Higher chip density and more advanced technology nodes correlate with worse VRD profiles (Finding 11) — which is concerning because both trends are expected to continue, potentially making the guardband-and-ECC stopgap even costlier over time (§6.5).
Q9Is this only a DDR4 phenomenon, or does it affect HBM2 too?▾
Both. The study covers 160 DDR4 chips across 21 modules and 4 HBM2 chips, from all three major DRAM manufacturers, and finds VRD in both DRAM types.
Q10Does this connect to online memory-tiering or CXL work? (framing, not a paper claim)▾
The paper itself doesn't discuss CXL or tiering. But structurally, its central tension — a per-row signal that must be tracked cheaply, online, under a noisy/time-varying process, where under-sampling silently degrades a system-level guarantee — is the same shape of problem as classifying page hotness for tiering decisions under noisy access-frequency signals. The paper's own proposed direction, "efficient online profiling," is the read-disturbance analogue of online hot/cold classification. This is our framing, drawn from the paper's stated open problem, not a claim the paper makes.

Autocorrelation Function (ACF)Measures whether a data series correlates with a delayed copy of itself — used here to test for repeating VRD patterns (found: none).
GuardbandConfiguring a mitigation with an RDT value smaller than the observed minimum, as a safety margin against unmeasured worse cases.
SECDED / SSC (Chipkill-like)Error-correcting codes evaluated alongside guardbands: single-error-correct/double-detect, vs. single-symbol (whole-chip) correction.
Supporting terms
TRRTarget Row Refresh — legacy on-die RowHammer defense, disabled during testing to observe raw RDT.
PRACPer-Row Activation Counting — the JEDEC DDR5-standardized in-DRAM mitigation whose security assumes accurately known RDT.
Graphene / PARA / MINTOther read disturbance mitigation techniques evaluated for guardband performance overhead alongside PRAC.
Data pattern (Rowstripe/Checkered)Fixed bit patterns written to victim/aggressor rows during testing, known to affect measured RDT.
DRAM BenderThe open-source FPGA-based DRAM testing infrastructure used to issue precisely-timed commands to real chips.
Die revision / densityManufacturer-coded indicators of chip generation and capacity; later revisions generally indicate more advanced technology nodes.
Expected normalized value of the minimum RDTThe paper's metric: how much higher (as a multiple) an N-measurement estimate tends to be versus the true 1,000-measurement minimum.
Working assumption (challenged)That RDT is a fixed, once-measurable property of a row — the assumption this paper's entire experiment is designed to test.
