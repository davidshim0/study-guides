Teaching the packet filter to look inside the tunnel, not just at its wrapper

pcap-filter can match an outer IP header, but has no syntax for what's nested inside a GTP-U tunnel, an SRv6 segment list, or a protocol that appears twice. This is the plain-English story of Kunai, a DSL that describes that structure directly — and still compiles to bytecode the Linux eBPF verifier accepts.

📄 "Kunai" · Hayasaka, Uda, Hayasaka, Kotani · eBPF '26 🎓 eBPF/kernel basics assumed — primers cover them ⏱ ~25 min read
🗡️

Give every field a RECORDED, run-time offset — never a FIXED, guessed one — and never scan further than a COMPILE-TIME BOUND the verifier can check in advance.

Before you begin

Quick glossary, then ten ideas the paper assumes you know

First, the acronyms you'll hit on every page. Then ten collapsed primers — read in order the first time, or jump to whatever's unfamiliar.

1What the eBPF verifier actually checks▾

Before the kernel will run an eBPF program, the verifier statically walks every possible execution path and proves two things: every memory access stays within a provably valid range, and every loop terminates within a bound it can check ahead of time. It refuses anything it can't prove, even if the access would in fact always be safe at run time.

This is stricter than "will it crash." A perfectly correct C-like loop over packet bytes can still be rejected if the verifier simply can't derive a static bound for it.

Now you're ready: Kunai's whole design is about emitting code the verifier can prove safe — not just code that happens to be safe.
2XDP and tc — where a filter program runs▾

XDP attaches at the earliest point in the NIC driver, before the kernel has even built a socket buffer (skb). tc attaches later, once an skb exists — and by then, the kernel may have already pulled some fields (like an outer VLAN tag) out of the raw bytes and into skb metadata.

Both are valid places to run a filter; which one you pick changes what the raw packet bytes still contain.

Now you're ready: Kunai targets both attach points, and one of its compile-time rules exists specifically because of what tc does to VLAN tags (§5.3 of the paper).
3pcap-filter and why it stops at fixed offsets▾

tcpdump's filter language, pcap-filter, compiles down to cBPF and gives you byte-offset access into the packet — ip[9] for the protocol byte, and so on — so a hand-built condition against one specific, known layout is often possible. What it lacks is structured syntax for "the header after this variable-length one," "the second occurrence of this protocol," or a repeated/variable-length walk.

That's fine for a plain TCP/IP packet, but breaks down once a header's start depends on the packet's own contents rather than a layout you can write down in advance.

Now you're ready: Kunai exists to cover exactly the packets pcap-filter can't describe — see the layer-chain syntax next.
4Nested encapsulation and repeated protocols▾

A tunnel wraps one packet inside another: an Ethernet frame carrying an outer IPv4/UDP header, then a tunnel header (GTP-U, Geneve, GRE), then an entire inner packet with its own IPv4 and TCP headers. The same protocol — IPv4 — can legitimately appear twice in one packet.

The inner header's start offset depends on the outer header's length and the tunnel header's (often variable) length — it is not a constant you can write down at compile time.

Now you're ready: this is the running example throughout the paper — filtering on the inner IPv4 destination of a GTP-U tunnel (filter F7 in the evaluation).
5data_end, bounds checks, and PTR_TO_PACKET▾

An XDP/eBPF program receives a packet as a pointer pair, data and data_end. Before dereferencing any byte at data + offset, the program must first compare data + offset + width against data_end — a "does this fit" check the verifier can follow.

The verifier tracks the pointer's proven range (PTR_TO_PACKET) through this comparison. If offset came from packet contents rather than a bound the verifier can pin down, it can't complete that proof.

Now you're ready: every field read Kunai generates is, in the end, exactly this pattern — a bounds check immediately before a load.
6Variable-length structures: lists, options, and TLVs▾

Some structures aren't just "one more header of unknown length" — they're a list of entries whose count or individual lengths vary: an SRv6 segment list (N fixed-size 16-byte addresses, N given by a header field), or TCP/IPv4 options and Geneve options (a sequence of self-describing type-length-value entries).

Reading a specific element, or a specific option by name, means walking the list at run time.

Now you're ready: Kunai's any()/all() quantifiers and proto.options.NAME.field syntax exist to describe exactly these walks.
7Loops in eBPF, and bpf_loop▾

A loop whose trip count the verifier can't bound at compile time is rejected outright. Two escapes exist: unroll the loop into straight-line code up to a small constant bound, or call bpf_loop, a kernel helper that itself takes a bound and invokes a callback that many times — letting the verifier check the loop's safety once, regardless of how large the bound is.

Unrolling grows the program's instruction count with the bound; bpf_loop keeps it constant but adds a helper-call indirection.

Now you're ready: Kunai picks between these two lowerings automatically, based on the bound's size — one of its two core code-generation patterns.
8P4: headers, parsers, and transitions▾

P4 describes packet formats as header layouts (named, sized fields) and a parser state machine that reads one header, then uses transition select(...) to decide which header comes next based on a field it just read (like an EtherType or a protocol number).

This is a natural notation for "how do I know what follows," which is exactly the information a filter compiler needs to resolve field offsets.

Now you're ready: Kunai reuses a subset of P4 syntax for protocol definitions rather than inventing a new description language — existing P4 headers serve as a starting reference.
9ParserCounter and counted walks▾

Some P4 parsers track a remaining-element count explicitly: seed a counter from a header field (like SRv6's last_entry + 1), then decrement it once per loop iteration until it hits zero. This is a counted walk — the element count is known the moment the counter is seeded, before any element is read.

Contrast this with a walk that instead reads each element's own length field and doesn't know in advance how many elements remain (TCP options).

Now you're ready: Kunai classifies a parser loop into one of these two shapes automatically when it loads a protocol definition — no annotation needed.
10Verifier-safety as a compiler property▾

A DSL that compiles to eBPF can fail in a way a normal compiler can't: it can produce code that is logically correct but that the verifier refuses to load. A compiler is verifier-safe if every well-formed program in its source language is guaranteed to compile into bytecode the verifier accepts — not just usually, but as a design property.

This is a recent, explicit demand on kernel-extension DSL compilers, not yet a solved or formally guaranteed problem for arbitrary inputs.

Now you're ready: Kunai's two code-generation patterns — recorded offsets and constant-bounded scanning — are its answer to this demand, checked empirically, not proven formally.
The whole story in one place

Kunai in a nutshell

The gap pcap-filter leaves, the two tricks that close it, and how the pieces fit together.

Modern networks nest one packet inside another: a GTP-U tunnel wraps a mobile subscriber's entire IPv4/TCP packet inside an outer IPv4/UDP header; SRv6 carries a list of routing addresses of run-time-determined length; TCP and Geneve carry options as a sequence of self-describing entries. pcap-filter has byte-offset access and can sometimes hand-build a condition for one specific, known layout, but it has no structured syntax for nested encapsulation, repeated protocols, or variable-length walks.

Kunai fixes the expressiveness gap with a layer-chain DSL: one expression names the order headers should appear in (eth/ipv4@outer/udp/gtp/ipv4@inner/tcp), disambiguates repeated protocols with labels (@outer, @inner), and scans variable-length lists with any()/all(). Field offsets are resolved against protocol layouts written in a subset of P4, so Kunai doesn't need to invent its own protocol-description syntax.

But expressiveness alone isn't enough — the result must still pass the eBPF verifier. Kunai's compiler lowers every dynamic access into two verifier-friendly patterns: it records each header's start offset into a stack slot at run time rather than guessing a constant, and it bounds every variable-length scan by a compile-time constant — unrolled in place when the bound is small, or run through bpf_loop when it's large — with a bounds check placed before every packet read.

The payoff: across ten representative filters and a 77-expression regression suite, the generated bytecode was accepted by the verifier on six Linux kernels (6.1–7.0) at both the XDP and tc attach points, matched and rejected packets correctly, and — where pcap-filter could express the same filter at all — ran within a few percentage points of it in per-packet cost.

🗡️ Key takeaways

  • pcap-filter's fixed-offset model can't express nested encapsulation, repeated protocols, or variable-length lists/options; Kunai's layer-chain DSL can.
  • Protocol layout comes from a subset of P4 — existing header/parser definitions carry over, no bespoke description language.
  • Recorded-base addressing: each header's start offset is written to a stack slot at run time and read back as layer_start[ℓ] + field_offset, always with a bounds check first.
  • Constant-bounded scanning: small bounds unroll in place; larger/unbounded ones lower to a bpf_loop callback — chosen from the parser's shape (counted list vs. TLV), automatically.
  • The same generated bytecode loaded unchanged across six kernels × two attach points (6.1–7.0, XDP and tc).
  • Overhead where comparable to pcap-filter: within 1.3 percentage points of throughput; instruction count 2.7×–14.7× larger, driven by bounds-checking, not verifier risk.
  • Adding a protocol needs a new P4 definition only — the code generator itself is unchanged.
Seven everyday pictures

How to think about Kunai

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core problem · Nested encapsulation

Nesting dolls that change size

Ordinary nesting dolls are predictable — the second doll always starts where the first one's shell ends. Now imagine the outer doll's shell thickness changes every time you pick it up. That's a GTP-U tunnel: the inner IPv4 header's start shifts with the outer header's length and the tunnel's optional fields. You can't write down "open 4cm in" once and reuse it.

Where it breaks: real dolls only nest once; packets can nest a protocol inside itself (IPv4-in-IPv4), which is exactly what Kunai's @outer/@inner labels exist to disambiguate.
Verifier discipline · Bounds check before every load

A bridge with a posted weight limit

A truck doesn't find out a bridge can't hold it by driving onto it — the limit is checked before the truck is allowed on. Kunai's generated code works the same way: every packet read is preceded by a comparison against data_end, proving the access fits before the load happens, never after.

Where it breaks: a bridge's limit is one fixed number; a packet's valid range (data_end) moves with every packet, so the "sign" has to be re-read and re-compared on every single access, not posted once.
Recorded-base addressing · Stack slots

Trail markers, not a trail map

On an unfamiliar hike you can't print a map with exact distances in advance — footing and switchbacks vary. Instead you drop a marker at each landmark as you pass it, recording how far you've actually walked. Kunai does the same with header offsets: it writes each header's start into a stack slot the moment parsing reaches it, then every later field reference reads from that marker, not a guessed distance.

Where it breaks: a hiker's markers are just notes; Kunai's stack slots are what let the verifier's static proof succeed — without them, the offset is unprovable, not just imprecise.
Constant-bounded scanning · unroll vs. bpf_loop

An elevator with a fixed top floor

An elevator button panel only goes up to the building's actual top floor — it physically cannot be asked to go further, no matter what's pressed. Kunai's scans work the same way: every walk over a variable-length list or option sequence carries a compile-time constant cap, so the verifier can always see the highest floor in advance, whether the walk is unrolled in place or handed to bpf_loop.

Where it breaks: the elevator's cap is fixed at construction; Kunai's cap is a compiler parameter chosen per structure, so raising it (say, to scan a longer SRv6 segment list) means recompiling, not redesigning the building.
TLV self-loop · TCP / Geneve options

A row of parcels, each labeled with its own size

You can't guess where the third parcel in a row starts just from its index — you have to read each parcel's own size label and step past it to find the next one. TCP options, IPv4 options, and Geneve options work identically: Kunai's generated walk reads each option's kind and length at the current cursor, checks it's well-formed, and only then advances by that option's own length.

Where it breaks: a mislabeled parcel is just annoying; a malformed option (a length of 0 or 1, or one that runs past the packet) must make the walk stop — Kunai's stop condition treats this the same as reaching the end.
Disambiguation · @outer / @inner labels

Twins wearing name tags

Identical twins are indistinguishable by "the person named Sam" alone — you need a tag. A packet carrying two IPv4 headers (outer and inner, around a GTP-U tunnel) has the same problem: ipv4.dst alone doesn't say which one. Kunai requires a label, @outer/@inner, whenever a protocol repeats, and rejects the unqualified reference before it ever reaches code generation.

Where it breaks: twins keep their tags forever; a label in Kunai is scoped to one filter expression's chain, not a persistent identity — the same physical header is "outer" only relative to that particular chain.
Protocol definitions · A subset of P4

Reusing an architect's blueprint notation

A contractor building an addition doesn't invent a new drafting notation — they read the original blueprint's existing symbols. Kunai describes each protocol's header layout and parser transitions in a subset of P4 rather than a bespoke language, so existing P4 header definitions and tooling carry over largely unchanged.

Where it breaks: a blueprint describes a whole building; Kunai only reads the subset of P4 that describes layout and parser transitions — the rest of the P4 pipeline model (tables, actions, full targets) is out of scope.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams you can read at a glance.

1 · The problem — a naive lowering doesn't survive the verifier

Write the obvious C-like eBPF for "read the inner IPv4 destination behind a GTP-U tunnel" and the offset to that field is a run-time value — it depends on the outer header's options and the tunnel header's extensions. A naive translation either hard-codes an offset (wrong whenever the variable parts are non-empty) or computes the offset at run time without a form the verifier can bound (rejected outright, since it can't prove the resulting pointer stays inside data_end).

⚠
Concretely: this is exactly filter F7 in the evaluation — eth/ipv4@outer/udp/gtp/ipv4@inner/tcp where inner.dst == 10.0.0.1. pcap-filter cannot express it at all; a hand-rolled eBPF program can express it but only survives the verifier with the two patterns below applied by hand.

2 · What the DSL expresses — layer-chains and quantifiers

A Kunai filter is a layer-chain (protocols in order, joined by /, with optional labels, quantifiers, and bracket predicates) followed by an optional where-clause over fields of any layer in the chain. Table 1's reference forms — proto.field, label.field, proto.<stack>[N].field, proto.<stack>.field inside any()/all(), and proto.options.NAME.field — cover a unique field, a labeled (disambiguated) field, a static index into a list, a scanned element, and a named option lookup.

The compiler validates this before touching code generation: it rejects references to fields that don't exist, unqualified references to a protocol that repeats, type-mismatched comparisons, and an any()/all() that scans zero or more than one un-indexed list.

3 · Protocol definitions — a P4 subset supplies the layout

Each protocol is defined once, in P4 syntax, as a header layout plus a parser with transition select(...) dispatch. For SRv6, the parser seeds a ParserCounter from last_entry + 1 and extracts one 16-byte segment per iteration into an array — so the element count, the segment width, and the array's capacity bound all fall out of the parser definition itself, with no Kunai-specific annotation. Adding GTP-U, Geneve, or a new tunnel protocol means writing one such definition; the compiler itself does not change.

4 · Recorded-base addressing

Whenever a layer follows one with a variable-length layout, Kunai marks its start offset as run-time-only during resolve. The generated bytecode then writes that start offset into a stack slot the instant the header is parsed — layer_start[ℓ] — and every later field reference on that layer becomes layer_start[ℓ] + field_offset, read back from the slot. Every such read is preceded by the bounds check against data_end described in primer 5. (See the signature figure on the Big Idea tab, reproducing the paper's Figure 4.)

5 · Constant-bounded scanning — classify, then lower

When the compiler loads a protocol definition, it classifies each parser loop by the shape of its states — no per-protocol code is needed in the generator itself:

// shared skeleton every walk fills in (Algorithm 1)
r ← ⊥; off ← base
for i ← 0 to cap−1:                 // cap: compile-time bound
    if stop(i, off): break          // count reached, or end/malformed
    ptr ← data + off
    if ptr + w > data_end: break   // w: bytes this step reads — the bounds check
    r ← step(ptr); break if r decides   // compare, or record an option's position
    off ← off + stride(ptr)          // constant width, or this option's own length
return r
💡
Counted aux-list walk (SRv6): stop = i ≥ count, stride = constant 16 bytes, step compares the segment's address field. TLV self-loop (TCP options): stride is read from the option's own length byte; stop fires at the options' end, an END option, a malformed length, or the iteration cap.

6 · Unroll vs. bpf_loop — the other axis

Separately from what fills the skeleton, the compiler picks how to emit the loop from the bound's size: a small compile-time bound is unrolled in place (each iteration becomes straight-line instructions — about 16 per unit of quantifier cap, about 68 per stacked SRv6 segment); a larger or unbounded one is lowered to a single bpf_loop callback whose code size no longer grows with the bound. Every emitted form still places a bounds check before every packet load, so the verifier can confirm both the loop bound and the range of each access.

🛡
Cross-kernel portability: Kunai also avoids instructions only newer kernels understand — e.g. it emits the older BPF_END byte-swap instruction rather than the BSWAP instruction introduced in Linux 6.6 — so the same bytecode loads unchanged on all six evaluated kernel versions.
Follow the numbers, step by step

Worked examples

Four traces through the paper's actual measurements — instruction counts, a bounded segment walk, verifier headroom, and where the datapath cost really comes from.

① Reading Table 2's instruction-count ratios

The paper states Kunai generates "2.7× to 14.7× as many instructions" as pcap-filter on the filters both can express. Check it against the table.

  1. F5 (ICMP type check): Kunai 85 instructions, pcap-filter 31. Ratio = 85 ÷ 31 = 2.74× — the low end.
  2. F1 (TCP dport): Kunai 199, pcap-filter 42. Ratio = 199 ÷ 42 ≈ 4.74×.
  3. F3 (IPv6 prefix match): Kunai 339, pcap-filter 23. Ratio = 339 ÷ 23 ≈ 14.7× — the largest gap, matching the paper's "the largest gap at the IPv6 prefix match of F3."
  4. Why F3 is the outlier: the paper reports F3 as the largest gap without explaining the mechanism behind it — it's plausible that resolving a run-time-recorded offset and a masked comparison costs more instructions than cBPF's compact prefix check, but that reasoning isn't in the paper itself.
🗡️
Insight: the extra instructions are bounds checks and load sequencing, not algorithmic bloat — every filter still sits far below the verifier's roughly one-million-instruction limit (F3 uses 339).

② Budgeting a bounded SRv6 segment walk

Each SRv6 segment adds about 68 instructions to a stacked segment walk. How many instructions for a chain scanning up to 8 segments, and how close is that to the verifier's instruction limit?

  1. Per-segment cost: ~68 instructions (the bounds-checked 16-byte extract plus the comparison step, per the paper's §5.4 figure).
  2. Eight segments: 8 × 68 ≈ 544 instructions for the walk body alone.
  3. Plus fixed overhead (chain prefix, header parsing before the walk starts) brings the total to what the paper reports directly: "even eight stacked walks stay near 800 instructions."
  4. Against the limit: 800 ÷ 1,000,000 ≈ 0.08% of the verifier's roughly one-million-instruction budget.
💡
Because every walk is capped by a compile-time constant, program size scales with that cap, not with the packet — the walk cannot silently grow past what the compiler promised the verifier.

③ Verifier headroom: F10's TCP-MSS option walk

Table 2 lists F10 (tcp.options.MSS.value == 1460) with a verifier cost of 206,733 instructions processed, the peak across six kernels — far above every other filter, including F8's SRv6 walk at 3,987.

  1. Raw bytecode size: F10 is only 231 instructions — smaller than F7's 406 or F9's 351.
  2. Verifier cost is separate from bytecode size: it grows with path exploration through the TLV self-loop's branchy kind/length dispatch, and — per the paper — "moves with the kernel version itself, by two orders of magnitude for F10 across the six kernels."
  3. The reported peak: ~207k instructions, on Linux 6.18, the worst of the six.
  4. As a fraction of the limit: 206,733 ÷ 1,000,000 ≈ 20.7% — matching the paper's description, "about a fifth of the one-million limit."
  5. Contrast: the pcap-filter baselines "stay below 300" for every filter — they have no branchy option dispatch to explore.
⚠
Takeaway: a TLV self-loop is cheap to run but relatively expensive to prove safe — the kind/length branching gives the verifier many more paths to check than a fixed-width counted walk like SRv6's.

④ Where the datapath overhead actually comes from

On the 100 GbE test, an XDP program that copies the packet head into a per-CPU scratch window and drops every packet — with no filter at all — already cost 7.7% of throughput versus a bare accept-all baseline. Decompose the total cost for the worst Kunai filter, F8 (SRv6, run as bpf_loop).

  1. Fixed cost, no filter: the per-CPU head copy alone: 7.7% rate reduction — paid regardless of which filter runs.
  2. Measured on top of that same-copy baseline, F8's SRv6 walk adds a further 7.3% — the largest of F7–F10's 3.9–7.3% range. The paper reports F8 as the costliest filter and notes its SRv6 walk runs as bpf_loop, but it doesn't isolate how much of that 7.3% is helper-call overhead versus the walk's other work.
  3. For filters expressible in both languages (F1–F5), Kunai "stayed within 1.3 percentage points of pcap-filter" — the gap from bounds-checking is small next to the fixed copy cost.
  4. Isolated from the NIC entirely, BPF_PROG_TEST_RUN timed a 611–614 ns filterless baseline; each filter added at most 13 ns/pkt — about 13 ÷ 612 ≈ 2.1%.
🗡️
Insight: most of the per-packet cost in the 100 GbE test is the scratch-window copy, not Kunai's filter logic — the paper copies the packet head the way an operational fentry/tc observer would, and reports Kunai's overhead relative to that same-copy baseline rather than a raw accept-all number.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why can't ip[9] == 6 and inner_ip[9] == 6-style byte-offset pcap-filter syntax express "match the inner IPv4 header's destination behind a GTP-U tunnel"?
Show answer
Because inner_ip's byte offset is not a constant — it shifts with the outer IPv4 header's option length and the GTP header's optional extensions, both of which vary per packet. pcap-filter does give you byte-offset access and can hand-build a condition for one specific, known layout, but it has no structured way to say "wherever the inner header turns out to start" — that requires expressing a run-time-computed offset, which its syntax doesn't support.Misconception: that a longer or cleverer byte-offset expression could eventually reach the inner header for any packet. A fixed offset only works for the specific outer-header/tunnel-extension lengths it was written against; it breaks for any packet where those lengths differ.
Problem 2 · medium
A filter chain is eth/ipv4@outer/udp/gtp/ipv4@inner/tcp. Why does Kunai reject a bare reference to ipv4.dst in the where-clause, and what must the author write instead?
Show answer
Because ipv4 appears twice in the chain (outer and inner), ipv4.dst doesn't uniquely identify which header's destination field is meant. The compiler rejects this at the analysis stage, before code generation, and requires a label-qualified reference instead — inner.dst or outer.dst — using the @outer/@inner labels declared in the chain.Misconception: that Kunai "picks" one occurrence by some default rule (like first-match or last-match). It does neither — it refuses to guess and requires the filter author to disambiguate explicitly.
Problem 3 · medium
A programmer argues: "The inner IPv4 header is always at a fixed offset for this specific deployment's typical GTP-U traffic — just hard-code it, it'll practically always be within bounds." Why does the verifier reject that anyway, even though the access would usually be safe at run time?
Show answer
The verifier proves safety for every possible input the program could receive, not just the packets a deployment typically sees. A hard-coded offset is only safe when the outer header and tunnel extensions happen to have a specific length; for any packet where they don't, the read could land past data_end. Since the verifier can't assume "typical" packets, and the offset used has no bounds check tied to the actual variable-length parts, it refuses the load outright.Misconception: that the verifier reasons about likely or average-case traffic. It only accepts what it can prove holds for all possible inputs — "usually fine" is not a category it has.
Problem 4 · hard
Why doesn't Kunai just always unroll every variable-length walk to some generous constant bound, instead of ever using bpf_loop?
Show answer
Unrolling makes the generated program's instruction count grow linearly with the chosen bound — a chain quantifier adds about 16 instructions per unit of cap, and a stacked SRv6 segment walk about 68 per segment. A "generous" bound (say, scanning a long TLV option list or a deep chain quantifier) could push instruction count up substantially, and every additional instruction is also additional work for the verifier to trace through every path. bpf_loop keeps code size constant regardless of the bound, trading that for one helper-call indirection per iteration — which is exactly why Kunai reserves it for the larger/unbounded cases rather than using it (or unrolling) unconditionally.Misconception: that bigger unrolled bounds are "free" as long as they're still under the verifier's one-million-instruction ceiling. Verifier processing cost (as F10's 206,733-instruction peak shows) can vastly exceed raw program size, so a larger bound isn't free just because it's still under the ceiling.
Problem 5 · medium
Explain the difference in meaning between any(P and Q) and any(P) and any(Q) when scanning SRv6's segment list, and give a segment list where they disagree.
Show answer
any(P and Q) requires a single segment to satisfy both P and Q at once. any(P) and any(Q) only requires that some segment satisfies P and some (possibly different) segment satisfies Q. Take a segment list [fc00::1, fc00::2]: with P = "addr == fc00::1" and Q = "addr == fc00::2", any(P and Q) is false (no single segment is both addresses), but any(P) and any(Q) is true (the first segment satisfies P, the second satisfies Q).Misconception: that "any element matches P and Q" and "P holds for some element and Q holds for some element" are just two ways of writing the same condition. They diverge exactly when different elements are needed to satisfy each half.
Problem 6 · hard
A filter reads a VLAN tag's field value (e.g. vlan[tci==100]) and is attached at tc. The paper says Kunai rejects this at compile time. Why, and what is still allowed?
Show answer
At the tc attach point, the kernel has already extracted the outer VLAN tag out of the raw packet bytes and into skb metadata before the eBPF program runs — so the tag's value is no longer reliably present at its "usual" offset in the packet bytes Kunai's bytecode reads. Rather than generate a read that might silently see the wrong (or absent) bytes, Kunai rejects any filter that reads a VLAN/QinQ field's value from packet bytes when targeting tc. A tag reference with no value condition — i.e., just checking a VLAN layer is present — stays matchable, since presence doesn't depend on reading the stripped value.Misconception: that this is a bug Kunai failed to work around. It's a deliberate compile-time restriction — reading the right answer isn't available from packet bytes alone at that attach point, so Kunai refuses rather than guesses.
Problem 7 · medium
F10 (TCP MSS option) reads a single 16-bit field, yet its verifier cost (up to 206,733 instructions) dwarfs F8's SRv6 segment walk (3,987 instructions), which reads a whole list of 16-byte addresses. Why is "reading one small field" more expensive to verify here?
Show answer
The cost isn't about how much data is read, but how many distinct execution paths the verifier must trace. F10's TLV self-loop dispatches on each option's kind byte and re-reads a run-time length to decide the next cursor position — a branchy structure the verifier must explore across many possible kind/length combinations. F8's SRv6 walk is a counted loop over fixed-size, fixed-stride elements with a single comparison per iteration — far fewer branches for the verifier to consider, even though it touches more total bytes.Misconception: that verifier cost scales with the amount of packet data a filter reads. It scales with the branching complexity of the code path, which a TLV walk's per-option dispatch has far more of than a fixed-stride counted walk.
Problem 8 · easy
Does Kunai make pcap-filter obsolete for every use case?
Show answer
No. The paper notes pcap-filter's one expressiveness axis Kunai does not follow is raw byte-offset access — a hand-written condition against a specific packet layout can sometimes be built in pcap-filter even for structures Kunai handles more generally. Kunai is also scoped to stateless packet filtering; stateful filtering, deep packet inspection, and aggregation are explicitly out of scope, per the paper's limitations.Misconception: that "more expressive for nested/variable-length structures" means "strictly more expressive in every respect." Kunai trades away arbitrary byte-offset access for structured, protocol-aware, verifier-safe filtering — it's a different tool, not a strict superset.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What exactly is Kunai?▾
A packet-filter DSL plus a compiler: you write one expression describing a packet's expected layer structure and field conditions, and the compiler resolves field offsets against P4-subset protocol definitions and generates eBPF bytecode that the Linux verifier will accept.
Q2What does "verifier-safe" mean here, precisely?▾
Following Solleza et al.'s usage: a well-formed Kunai filter should compile to bytecode the eBPF verifier accepts. The paper establishes this empirically — every generated program was accepted across six kernels and two attach points — rather than proving it holds for every conceivable filter.
Q3How is this different from just writing the eBPF program by hand?▾
The bounds-checking and loop-bounding patterns Kunai generates are standard practice for hand-written eBPF — programmers already place a data_end check before each access and bound every loop. Kunai's contribution is deriving and applying these patterns automatically from the filter's resolved structure, so the filter author writes neither the offset bookkeeping nor the bounds checks by hand.
Q4Why P4 for protocol definitions instead of a new description language?▾
So Kunai can lean on P4's existing header/parser notation rather than inventing a bespoke syntax (the approach earlier packet-description languages like binpac or NetPDL took). That reuse is partial, not automatic: Kunai only understands a subset of P4, and its loop classification (counted aux-list vs. TLV self-loop) depends on the parser being written in one of the idioms it recognizes — an existing P4 definition may still need adapting before Kunai can use it.
Q5How does recorded-base addressing avoid guessing an offset?▾
The compiler marks any layer following a variable-length one as run-time-only. The generated bytecode writes that layer's actual start offset into a BPF stack slot the instant it finishes parsing that header, and every later field reference reads the offset back from the slot rather than from a compile-time constant.
Q6What's the difference between a counted aux-list walk and a TLV self-loop?▾
A counted aux-list walk (e.g. SRv6 segments) knows its element count up front from a seeded counter, and every element has the same fixed width. A TLV self-loop (e.g. TCP/IPv4/Geneve options) doesn't know the count in advance — it reads each entry's own length at the cursor and steps past it, stopping on an end marker, a malformed entry, or the iteration cap.
Q7Why unroll some loops but use bpf_loop for others?▾
A small compile-time bound is cheap to unroll in place — straight-line code the verifier can trace directly. A larger or unbounded structure would make unrolled code grow with the bound; bpf_loop keeps the generated code's size constant instead, at the cost of a helper-call indirection per iteration. Kunai's choice is threshold- and structure-based — small compile-time bounds are unrolled, larger or unbounded walks go through bpf_loop — rather than the output of a cost model proving one option cheaper.
Q8Does the same bytecode really run unchanged across kernel versions?▾
Yes, for the filters and regression suite tested (Linux 6.1–7.0, XDP and tc). Kunai deliberately avoids instructions only newer kernels understand (e.g. it emits BPF_END rather than the BSWAP instruction added in 6.6), so the generated program doesn't need to be regenerated per target kernel.
Q9How much overhead does Kunai add versus pcap-filter?▾
Where both can express the same filter (F1–F5), Kunai's datapath rate reduction stayed within 1.3 percentage points of pcap-filter's, and per-packet latency added at most 13 ns over a ~612 ns filterless baseline. Instruction count is larger (2.7×–14.7×), but that's bounds-checking overhead, not a verifier risk — every filter stays far under the instruction-count limit.
Q10What can pcap-filter express that Kunai can't?▾
Arbitrary byte-offset access. pcap-filter can sometimes hand-build a condition for one specific, known packet layout using raw byte offsets; Kunai instead requires a protocol definition and structured field references, which is more general for nested/variable structures but doesn't expose that raw byte-offset escape hatch.
Q11Why can't a Kunai filter read a VLAN tag's value at the tc attach point?▾
By the time a tc-attached program runs, the kernel has already extracted the outer VLAN tag into skb metadata, so its value is no longer reliably present in the packet bytes Kunai's bytecode reads. Kunai rejects such filters at compile time for tc rather than generate a read that might silently see the wrong bytes; a VLAN/QinQ layer with no value condition (checking presence only) still works.
Q12What's left for future work?▾
The paper lists: a formal guarantee of verifier acceptance for arbitrary filters (currently established only empirically); Geneve option TLVs and the tc-stripped outer VLAN tag as not-yet-supported filter targets; and that bytecode correctness is only as good as the underlying protocol definition, since p4c checks P4 syntax, not RFC conformance.
