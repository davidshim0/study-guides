Watching every GPU cycle without ever stopping it

Profiling a production LLM cluster the usual way means putting stopwatches on the GPU — and every stopwatch is a barrier that stalls the thing it's timing. This is the plain-English story of LMTracer, which turns the stopwatch into just another kernel riding the same execution graph.

📄 "LMTracer: Fine-Grained and Real-Time Performance Profiling for Production LLM Systems" · Liu et al. 🎓 GPU/CUDA fluency assumed — primers cover the LLM-serving-specific plumbing ⏱ ~25 min read
🛰️

Make every profiling probe a GPU KERNEL that rides the execution graph — never a BARRIER that stops it to check the time.
Measure from inside the stream, not from outside it.

Before you begin

Quick glossary, then eight primers

You already know GPU architecture and the mm stack cold. What's paper-specific is the LLM-serving plumbing (CUDA/HIP Graphs, kernel fusion, TP/PP/DP) and the profiling-overhead problem it creates — that's what these primers target.

Quick glossary — acronyms used everywhere below

TP / PP / DPTensor / Pipeline / Data Parallelism — the three ways an LLM's compute is split across GPUs.
TTFTTime To First Token — latency from request arrival to the first generated token; the serving-side SLA metric.
MLPMulti-Layer Perceptron — the feed-forward block in each transformer layer (up-proj, activation, down-proj).

1GPU asynchronous execution▾

CPUs enqueue kernels onto a GPU stream in a non-blocking way — the CPU moves on immediately, and the GPU executes the queue in order without waiting for the CPU to check in. This is what lets a training loop overlap Python-side bookkeeping with GPU compute.

Now you're ready: LMTracer's entire design exists to avoid breaking this non-blocking property. Any profiling technique that forces the CPU to wait on the GPU (or vice versa) mid-stream reintroduces the idle time this model was built to eliminate.
2Kernel fusion▾

A layer-norm computed naively is four separate ops (power, add, rsqrt, multiply) — four kernel launches, four rounds of memory traffic. Compilers like PyTorch Inductor fuse these into one kernel that does all four in registers, cutting launch overhead and memory round-trips.

Now you're ready: fusion is exactly what makes profiling hard — once four ops become one kernel, a profiler that only sees kernel boundaries loses all visibility into which "op" inside took the time. LMTracer's stack-aware compilation exists to recover that visibility.
3CUDA/HIP Graph execution▾

Beyond fusing ops into kernels, frameworks capture an entire sequence of kernels into a graph during a warm-up iteration, then replay the whole graph with a single CPU-side launch call on every subsequent iteration — reported to improve LLM performance up to 3×.

Now you're ready: a probe that isn't itself a normal GPU kernel can't be captured into this graph, so it either falls outside the graph (and reintroduces launch overhead) or forces a break in the replay. Probe kernels are designed to be indistinguishable from user kernels at capture time.
4Why timing a kernel usually means a barrier▾

The standard way to time a GPU kernel is a CUDA/HIP Event: record a timestamp before and after, then query it. Querying (or synchronizing on) an event from the CPU forces a wait — a barrier — because the CPU can't know the GPU has reached that point without asking and blocking.

Now you're ready: this is the paper's root-cause diagnosis — every existing tool, in one form or another, inserts something that requires the CPU and GPU to rendezvous, and that rendezvous is what costs the 5–90%+ overheads you'll see in §7.
5LLM training/serving pipelines (TP/PP/DP)▾

DP replicates the whole model across GPU groups; PP splits layers into sequential stages across GPUs; TP splits individual layers across GPUs that must communicate (e.g. AllReduce) on every forward/backward pass. Serving adds a prefill phase (build the KV cache) followed by autoregressive decode.

Now you're ready: LMTracer's bottleneck analysis (§5.3) reconstructs exactly this structure from trace data — grouping GPUs by TP/PP role to compute per-stage bubble and straggler metrics.
6Compile-time call stacks▾

When a compiler like PyTorch Inductor traces user code to generate kernels, it symbolically executes that code, meaning every operator it emits can be traced back to a call stack of Python source locations — which function, which file, which line — even after the operator is fused away into a larger kernel.

Now you're ready: this compile-time-only information is the raw material LMTracer's stack-aware compilation reads to decide where a fused kernel's boundaries map to user-defined regions like "attention" or "norm."
7GPU clock registers and drift▾

GPUs expose a free-running clock register readable directly from kernel code (globaltimer on NVIDIA, s_memtime on AMD) — no driver call, no host round-trip. But GPU clocks are not synchronized with the CPU's or with each other's, since deviations don't matter for compute correctness.

Now you're ready: reading this register from inside a kernel is the cheapest possible timestamp (0.7–0.9 µs), but using it across devices requires the one-time clock-offset calibration in §5.2 — otherwise timestamps from different GPUs aren't comparable.
8Producer-consumer double buffering▾

The classic way to let a fast producer and a slower consumer overlap without either blocking the other: two buffers, the producer fills one while the consumer drains the other, then they swap. This trades a fixed memory cost for eliminating a synchronization point.

Now you're ready: LMTracer's shadow buffers are exactly this pattern, plus a lightweight "doorbell" notification so the consumer (CPU) doesn't have to poll the producer (GPU) constantly — see §5.2.
🧭
If you're coming from memory-tiering / CXL work: the doorbell-and-shadow-buffer pattern here is the same shape as doorbell registers on RDMA NICs or CXL Type-3 device queues — a producer that writes to a ring buffer and pings the consumer only when there's something to collect, instead of the consumer polling or the producer blocking on an acknowledgment. It's the same low-overhead notification primitive, applied to trace data instead of memory requests.
The whole story in one place

LMTracer in a nutshell

The problem, the fix, and how the pieces connect.

Production LLM providers need to watch GPU execution closely — a 20% GPU slowdown during training can inflate cost by 38%, and a 1-second latency spike in serving can drop a large fraction of user requests. But the profiling tools available (CUPTI, Nsight Systems, CUDA/HIP Events, PyTorch Profiler) all share a root cause of failure: to get an accurate timestamp, they insert something — an event query, a barrier, a Python-runtime hook — that forces the CPU and GPU to rendezvous. Because modern LLM execution is asynchronous and streamlined (kernels fused together, entire iterations captured into CUDA/HIP Graphs), every rendezvous either breaks that fusion or stalls the pipeline, producing overheads from 5% up past 90%.

LMTracer's fix is graph-embedded probing: make the profiling logic itself a probe kernel — an ordinary GPU kernel, captured into the same execution graph as the code it measures, executed in the same order, with no barrier required to read it. Two engineering problems make this work in practice. First, inserting probes at arbitrary points would break kernel fusion, so stack-aware compilation statically traces compile-time operator call stacks to find the safe boundary kernels to attach probes to. Second, getting the collected data off the GPU without a barrier requires doorbell-assisted shadow buffering: two GPU-side buffers that probe kernels fill in turn, with a lightweight doorbell signal telling an async CPU poller when one is ready to drain — no query, no synchronize.

The payoff: deployed in production for eight months across vLLM, SGLang, and Megatron-LM (7B–671B parameters, O(1k) GPUs), LMTracer averages 0.9% overhead — an 11.6× reduction versus Nsight Systems and PyTorch Profiler at comparable accuracy — while still resolving kernel-level, code-mapped traces. It has proactively caught 15 production issues; fixing them yielded 21.2% latency reduction and 24.5% throughput improvement.

🍯 Key takeaways

  • The root cause of profiling overhead isn't "too much data" — it's barriers forcing CPU-GPU rendezvous, which breaks kernel fusion and graph replay.
  • Probe kernels are ordinary GPU kernels: they get captured into CUDA/HIP Graphs and cost only ~0.7–0.9 µs to read a clock register — vs ≥13 µs for a vendor-tool instrumentation point.
  • Stack-aware compilation uses compile-time call stacks (not runtime hooks) to place probes at fused-kernel boundaries without breaking fusion.
  • Doorbell-assisted shadow buffering moves data off the GPU with zero synchronization — two buffers, one doorbell flag, one async CPU poller.
  • Bottleneck analysis (bubble fraction, straggling fraction) turns the raw trace into "which GPU/stage is the problem," not just "here's a timeline."
  • Result: 0.9% average overhead, 11.6× lower than rival profilers, 15 production issues found, 21.2%/24.5% latency/throughput gains after fixes.
Seven everyday pictures

How to think about LMTracer

Each stands alone — read in any order. Every card ends with where it stops being true.

The core idea · Probe as fellow traveler

A speed camera embedded in the road, not a checkpoint

A police checkpoint measures your speed accurately — by making you stop. A speed camera embedded flush in the pavement measures it just as accurately while every car drives straight through at full speed. A probe kernel is the camera: it rides in the traffic (the execution graph) instead of blocking it.

Where it breaks: a real camera captures one instant; a probe kernel still costs a small, nonzero amount of GPU time (0.7–0.9 µs) to execute — it's cheap, not free.
Stack-aware compilation

A relay race baton handoff

Runners don't stop to compare watches at the handoff — the baton (call-stack context: "we're inside attention now") passes cleanly at the zone boundary while both runners keep moving. Stack-aware compilation finds those natural handoff zones — fused-kernel boundaries — and puts the probe exactly there, never mid-stride inside a runner's leg.

Where it breaks: in a race the baton carries no data, just position; the probe kernel does carry data (a timestamp + region hash), so the "handoff" has real payload, not just semantics.
Doorbell-assisted shadow buffering

Two mailboxes, alternating

A busy office worker keeps two out-trays. She fills tray A while the courier empties tray B; when A is full she flips to B and rings a bell for the courier to come collect A. Neither she nor the courier ever waits on the other — GPU probe kernels fill one shadow buffer while the CPU drains the other, swapping on a doorbell signal.

Where it breaks: if the courier never shows up (both trays fill), the office worker in this analogy would jam; LMTracer instead overwrites old data rather than blocking — a lossy, not a lossless, guarantee.
Doorbell vs. polling

A doorbell instead of knocking every five seconds

You could check the front porch every few seconds to see if a package arrived — wasteful, and you're never doing anything else while checking. Or the courier can ring the doorbell exactly once, when it's actually there. LMTracer's CPU poller waits on a lightweight doorbell flag instead of actively querying GPU state.

Where it breaks: a doorbell is a true interrupt; LMTracer's "doorbell" is still a flag in CPU-GPU mapped memory that a background thread checks — closer to efficient polling of a cheap flag than a hardware interrupt.
Clock calibration

Comparing watches once at the start of a race

Race officials at different checkpoints don't re-synchronize their watches every mile — they set them together once at the start line and trust the drift is small over the race's duration. LMTracer records each GPU's clock offset relative to a master GPU once, via an AllGather at startup, and reuses that offset for the whole run.

Where it breaks: race officials' watches barely drift; the paper explicitly notes GPU clock drift up to ~2 ms/month is expected and tolerated — and unusually large drift is itself treated as a symptom of a hardware issue, not just noise to average out.
Bottleneck analysis

A conveyor line with a hesitant worker

Watch a factory line long enough and you can see who's slow: everyone downstream of them waits, creating a visible gap on the belt. LMTracer's bubble fraction and straggling fraction metrics measure exactly this — idle gaps in the GPU timeline, and skew in when GPUs finish their step relative to each other.

Where it breaks: a factory worker being slow is usually the direct cause; a GPU "gap" can be caused by something entirely off the belt — a flaky NIC, a scheduling policy — which LMTracer still has to trace back to the actual root cause, not just the symptom.
Why plain kernel names aren't enough

A shipping label that only says "Warehouse B"

A package labeled only with the warehouse it left from tells you nothing about which shelf, which order, which customer. A fused kernel named ampere_bf16_s1688gemm... is the same: accurate, but semantically empty. LMTracer's stack-aware mapping is the itemized packing slip stapled back onto that label.

Where it breaks: a packing slip is static paperwork; the kernel-to-region mapping has to be recomputed at every compilation (fusion decisions can change across runs, models, and frameworks).
The full explanation

How it actually works

The two hard engineering problems, then how the traces become actionable answers.

1 · Stack-aware compilation — placing probes without breaking fusion

Users specify code regions to profile at module, function, or line granularity (e.g. an attn region spanning a whole attention module, a norm region around RMSNorm). When the compiler (e.g. PyTorch Inductor) fuses operators into kernels, LMTracer hooks the compilation process: for each fused kernel, it recursively backtracks the call stack of every operator inside it, checking whether that stack passes through a user-defined region's *_start/*_end markers.

A fused kernel can therefore be associated with zero, one, or several nested regions. LMTracer inserts an Enter probe the first time a region's call stack is activated by a kernel, and an Exit probe the first time a kernel's operators no longer intersect that region. Adjacent probes at the same kernel boundary (e.g. an Attn Exit and a Norm Enter that both land at the start of the same fused kernel) are merged into a single probe kernel to further cut launch overhead.

2 · Doorbell-assisted shadow buffering — moving data with zero barriers

Probe kernels write the region hash + the raw GPU clock-register value into one of two GPU-side shadow buffers — no calibration happens at write time; that comes later, computed from the initial CPU/GPU clock offsets recorded once at startup (§5.2). When a buffer fills, LMTracer issues __threadfence_system() (guaranteeing all prior writes are visible system-wide) and then writes a doorbell flag into CPU-GPU mapped memory. A background CPU poller thread watches that flag; on seeing it set, it asynchronously copies the full buffer to CPU memory in a separate stream — while probe kernels keep writing, uninterrupted, into the other buffer.

3 · Executor binding — attaching probes transparently

GPU kernels can only be launched from the process that owns the GPU context, so probe kernels must share the user's process. LMTracer uses Python's site-specific configuration hooks to watch package-import events and detect a framework's executor class (e.g. vLLM's Worker, SGLang's ModelRunner) — the component every mainstream LLM framework uses to bind one GPU per process. Once detected, LMTracer patches the executor before initialization so probes share its context, requiring no code changes from the user.

4 · Bottleneck analysis — turning traces into answers

LMTracer reconstructs kernel wait-for dependencies from the trace timeline and groups counterpart operations across GPUs within a parallelism group (TP/PP/DP). Two metrics quantify inefficiency:

BubbleFraction = 1 − ( Σ dᵢ ) / ( t_N − t_1 + d_N )   # idle-time share of the window; dᵢ = i-th kernel's duration
StragglingFraction = (max sg − min sg) / (max eg − min sg)  # start-time skew across GPUs in a parallel group g

A high bubble fraction points to scheduling or data stalls; a high straggling fraction points to an imbalanced or misbehaving GPU. LMTracer also places probes around communication kernels (AllReduce, AllGather), so the same machinery doubles as network observability.

🍯
Ablation confirms the design, not just the headline number. Removing probe merging, shadow buffers, the doorbell, or async copy each independently pushes overhead back up (worked out in the Examples tab) — none of the four components is redundant.
Follow the numbers, step by step

Worked examples

Four traces through the paper's real measurements — verifying the headline number, checking tail latency, separating per-probe cost from end-to-end cost, and finding the highest-leverage design choice.

① Verifying the 0.9% headline overhead

Qwen3-32B serving on low-end GPUs, vLLM with TP=8: throughput drops from 3,157 to 3,128 tokens/s with LMTracer enabled. Does that match the paper's claimed 0.9%?

  1. Tokens lost per second: 3157 − 3128 = 29 tokens/s.
  2. Relative degradation: 29 / 3157 = 0.00918 → 0.92%, matching the paper's reported "0.9%."
  3. Cross-check on a second config: vLLM TP=4/PP=2 goes 3743 → 3721, a drop of 22, i.e. 22/3743 = 0.59% ≈ paper's "0.6%".
  4. And SGLang TP=8: 3103 → 3090, drop of 13, i.e. 13/3103 = 0.42% ≈ paper's "0.4%".
🍯
Insight: the "0.9% average" isn't a single measurement — it's consistent across frameworks (vLLM, SGLang) and parallelism configurations, which is what makes it a credible production number rather than a cherry-picked one.

② TTFT tail impact — LMTracer vs. the alternatives

GPT-OSS-120B on mid-range GPUs (Fig. 11): Default mean TTFT = 52.70 ms; LMTracer mean = 56.09 ms; PyTorch Profiler mean = 116.21 ms.

  1. LMTracer's absolute TTFT cost: 56.09 − 52.70 = 3.39 ms — relative increase 3.39/52.70 = 6.4%.
  2. PyTorch Profiler's absolute cost: 116.21 − 52.70 = 63.51 ms — relative increase 63.51/52.70 = 120.5%, i.e. it more than doubles TTFT.
  3. Matches the paper's own framing: "the other profiling tools cause up to 63.5 ms TTFT increase," exactly the PyTorch Profiler delta computed above.
  4. Nsight Systems' cost, for comparison: mean 80.66 − 52.70 = 27.96 ms, a 53% relative increase — worse than LMTracer's 6.4%, but far better than PyTorch Profiler's 120%.
💡
The paper's own words: a 3.39 ms average TTFT increase "can hardly be noticed by users" — this is the number that makes "always-on in production" a credible claim rather than a lab-only result.

③ Per-probe speedup vs. end-to-end overhead reduction

Fig. 4: a vendor-tool instrumentation point costs ≥13 µs; an embedded probe kernel costs 0.7–0.9 µs. The paper separately claims an 11.6× end-to-end overhead reduction. Are these the same number?

  1. Per-instrumentation-point speedup: 13 / 0.9 = 14.4× to 13 / 0.7 = 18.6× — this measures only the cost of one clock-read-and-record event.
  2. End-to-end overhead reduction: the paper's 11.6× compares whole-workload overhead (e.g. LMTracer's 0.9% vs. an average rival overhead in the ~8–10% range) — it folds in everything: how many probes fire per iteration, buffer management cost, and how much of total runtime instrumentation touches at all.
  3. Why 11.6× is lower than 14–19×: not 100% of the overhead gap comes from the per-point read; some GPU-side probe cost and CPU-side buffer draining remain even in LMTracer, so the realized end-to-end ratio is smaller than the idealized per-instrumentation-point ratio.
⚠
Don't conflate the two numbers when citing this paper — 14–19× is a microbenchmark of one design choice (kernel-based clock reads); 11.6× is the true end-to-end result across the whole profiling pipeline.

④ Ablation — finding the highest-leverage component

Baseline LMTracer overhead: ≈0.9% (serving) / ≈1.5% (training). Disabling each design choice one at a time (§7.3):

DisabledServing degradationΔ vs. baseline (0.9%)Training degradationΔ vs. baseline (1.5%)
Probe merging2.9%+2.0 pts3.0%+1.5 pts
Dual shadow buffer12.8%+11.9 pts5.7%+4.2 pts
Doorbell signal16.2%+15.3 pts18.2%+16.7 pts
Async copy13.3%+12.4 pts8.7%+7.2 pts
  1. Largest single jump: removing the doorbell signal (forcing active polling instead) costs the most on both workloads — +15.3 and +16.7 percentage points.
  2. Second-largest: disabling async copy (+12.4 / +7.2 pts) — confirming that even with two buffers, a synchronous copy call reintroduces most of the barrier cost.
  3. Smallest but still real: probe merging only saves ~2 points, because it reduces kernel-launch count, not the fundamentally cheaper data-movement path.
🍯
Insight: the doorbell and async copy are doing the real work of eliminating barriers; shadow buffering and probe merging are secondary optimizations layered on top. If you were reimplementing this for a different accelerator, the doorbell + async-copy pair is the part to get right first.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
A colleague says "just insert a CUDA Event before and after the kernel — reading a hardware timer is basically free." Why does this still cause double-digit overhead in production?
Show answer
Reading the event's value from the CPU forces a query or synchronize, which is a genuine CPU-GPU rendezvous — a barrier. Even if writing the timestamp is cheap, an Event also isn't a normal user kernel, so it can't be fused with neighboring operators and can break CUDA/HIP Graph capture, reintroducing per-kernel launch overhead on top of the sync cost.Misconception: that overhead comes from the cost of reading a clock. It actually comes from breaking asynchrony and graph fusion — which is exactly why LMTracer's fix is a kernel captured into the same graph, placed without breaking existing fusion, not a smarter event that still needs a query.
Problem 2 · medium
Why can't LMTracer just insert a probe kernel immediately before and after every user-defined code region, at the exact source-code boundary?
Show answer
By the time the compiler fuses operators into kernels, a code region's operators may be interleaved inside a larger fused kernel alongside operators from unrelated regions — there's no longer a clean boundary at the source-code line. Inserting a probe there would either be impossible without splitting the fused kernel (which the paper says is rare, <2% of trace points, and only used for offline debugging) or would force fusion to break around it, losing the launch-overhead savings fusion existed for.Misconception: that source-code regions map 1:1 onto kernels. Stack-aware compilation exists precisely because fusion erases that mapping, so LMTracer finds the nearest safe kernel boundary instead.
Problem 3 · medium
Why does LMTracer use two shadow buffers instead of one large one that's copied out once at the very end of the run?
Show answer
One buffer flushed only at the end would need to hold the entire run's trace data in GPU memory — the paper explicitly rejects this as unsuitable for real-time monitoring, since you'd get no data until the job finishes, and memory usage would grow unbounded for long-running production jobs. Two buffers let one be actively written while the other drains continuously, giving both real-time visibility and bounded memory (a 1 MB buffer per monitor).Misconception: that avoiding barriers just means "collect everything, ship it later." That trades the overhead problem for an observability-latency and memory problem — the two-buffer design solves both at once.
Problem 4 · hard
The doorbell removes the need for the CPU to synchronize with the GPU. Why does removing the doorbell (forcing periodic active queries instead) cost even more overhead (16.2%/18.2%) than removing the dual buffer entirely (12.8%/5.7%)?
Show answer
Without a doorbell, the paper's fallback is to have the CPU "actively query the GPU to check whether one of the trace buffers is full after each LLM iteration" — this reintroduces a per-iteration CPU-GPU rendezvous, the exact barrier LMTracer was built to eliminate, regardless of how many buffers exist. Removing dual buffering, by contrast, just forces synchronous flushing after every record — costly, but it doesn't force the constant CPU-GPU check-ins that removing the doorbell does. The doorbell isn't just an optimization on top of the buffers; it's what makes the buffer scheme barrier-free at all.Misconception: that all four design choices contribute roughly equally. The ablation shows the doorbell and async copy are structural (they remove barriers); probe merging and buffering are incremental refinements on top.
Problem 5 · medium
LMTracer calibrates GPU-CPU clock offsets once, before execution, rather than continuously. Under what condition would this one-time calibration silently produce wrong bottleneck-analysis results?
Show answer
If a GPU's clock drifts substantially during the run — beyond the ~2 ms/month the paper treats as typical and tolerable — then timestamps calibrated at start-up would increasingly misalign with reality, and cross-GPU comparisons (like the straggling fraction) could misattribute a clock-drift artifact as a real performance straggler. The paper's own framing turns this into a feature, though: since drift is normally tiny, unusually large drift is itself flagged as evidence of an underlying GPU hardware problem, not just noise to filter out.Misconception: that a one-time calibration is a shortcut that trades accuracy for speed. The paper argues it's sufficient because distributed LLM workloads only need relative timing, and real GPU clock drift over realistic run lengths is small enough not to matter.
Problem 6 · hard
Nine of the 15 production issues LMTracer found "would be missed by sampled Nsight Systems or PyTorch Profiler runs." Why does sampling (running the heavyweight profiler for a short window periodically) fail here, when it's a standard technique elsewhere?
Show answer
Sampling assumes the phenomenon you're looking for recurs often enough that a short window has a good chance of catching it. But issues like KV cache eviction storms, prefill blocking, transient RNIC flapping, and imbalanced PP scheduling are tied to specific, intermittent request patterns or runtime conditions — they may not occur at all during a short sampled window, however carefully timed. Always-on, low-overhead tracing is the only way to guarantee you're watching when a rare-but-real event happens.Misconception: that sampling profiling overhead down to an "acceptable" rate is equivalent to solving the overhead problem. If the profiler is only safe to run intermittently, you've traded overhead for blind spots — LMTracer's whole value proposition is not needing that trade at all.
Problem 7 · easy
Framework-level telemetry (token throughput, iteration time) is nearly free to collect. Why isn't it sufficient on its own for production performance monitoring?
Show answer
Telemetry tells you that something is wrong (throughput dropped) but not why — it can't distinguish an inefficient kernel from suboptimal scheduling from a network bottleneck, because it has no visibility below the whole-iteration level. LMTracer's kernel-level, code-mapped granularity is what lets you go from "throughput dropped" to "the AllReduce on GPU 14 is slow because of a flaky NVLink."Misconception: that overhead is the only axis that matters when choosing a profiling tool. Telemetry has near-zero overhead but also near-zero diagnostic resolution — the paper's contribution is moving the whole overhead/granularity tradeoff curve, not picking a different point on the old one.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What is a "probe kernel," concretely?▾
A lightweight GPU kernel, written in raw GPU assembly, that reads the GPU's hardware clock register (globaltimer on NVIDIA, s_memtime on AMD) and writes the value plus a region identifier into a shadow buffer. It does not touch the registers, shared memory, or local memory of the user kernels it's placed next to, so it doesn't require saving/restoring any user kernel state.
Q2Why is a barrier so much more expensive than the actual work of reading a timestamp?▾
Because a barrier forces the CPU and GPU — which are designed to run asynchronously and overlap — to rendezvous, stalling whichever side got there first. It also breaks CUDA/HIP Graph capture, since only a normal kernel — not an event — can be captured into the graph and placed there without disrupting the existing fusion around it, reintroducing per-kernel launch overhead the graph mechanism was built to remove. The timestamp read itself costs under a microsecond; the synchronization around it is what costs tens of microseconds to tens of percent.
Q3How does LMTracer know where to put probes without the user rewriting their model code?▾
Stack-aware compilation hooks into the framework's compiler (e.g. PyTorch Inductor) during normal kernel fusion, tracing each operator's compile-time call stack back to user-defined regions in a configuration file. It never requires editing the model's source.
Q4Does profiling with LMTracer change training or inference correctness?▾
No — the paper verifies this two ways: training loss curves with and without LMTracer are effectively identical (Fig. 13), and inference output tokens are byte-identical given the same prompts and random seeds. Probe kernels never modify user kernel registers or memory.
Q5What happens if both shadow buffers fill up before the CPU drains either?▾
LMTracer uses a "backpressure-free" policy: new trace data overwrites old data rather than blocking GPU execution. In eight months of production use, the authors report never having observed both buffers full simultaneously, and inactive-buffer occupancy stays under 5%.
Q6How is this different from just enabling Nsight Systems' "graph-node profiling" mode?▾
Nsight's graph-node profiling mode lets it see execution time inside a CUDA graph, and it's the mode enabled in the paper's main comparison — but even so, Nsight (along with runtime-event-based tools) still causes >7% serving and >17% training degradation on average, because it remains a vendor tool built around external instrumentation rather than graph-embedded probes. Disabling graph-node profiling instead drops Nsight's overhead to >3.6%, but then Nsight loses visibility into kernel execution time altogether — a tradeoff LMTracer avoids entirely.
Q7What are "bubble fraction" and "straggling fraction" actually measuring?▾
Bubble fraction is the share of a monitoring window where the GPU has no active kernel running — idle time from stalls, scheduling, or data waits. Straggling fraction is the normalized skew in when different GPUs in the same parallel group (e.g. a TP or PP group) start their work — a proxy for load imbalance or hardware degradation.
Q8Does LMTracer replace tools like Nsight Systems or PyTorch Profiler entirely?▾
No — the authors frame it as filling an observability gap for always-on production monitoring, not replacing offline deep-dive tools. Nsight/PyTorch Profiler remain useful when you can afford a controlled offline run and want maximum diagnostic detail; LMTracer is for the always-on case where any nontrivial overhead is unacceptable.
Q9Which frameworks and model scales has LMTracer actually been run on?▾
vLLM, SGLang, and Megatron-LM, covering both training and serving, on models from 7B to 671B parameters, across O(1k) GPUs in production, for eight months at the time of writing.
Q10Why does LMTracer's overhead differ between intra-host (TP=8) and inter-host (TP=4,PP=2) configurations?▾
The paper observes LMTracer's overhead is often lower under inter-host pipeline-parallel configurations, because the inherent pipeline bubbles between hosts give probe kernels and data transfer more slack to hide inside — whereas other profilers can't exploit this since they rely on intra- and inter-host synchronization regardless of topology.
Q11What kinds of issues has LMTracer actually caught in production?▾
Fifteen issues across configuration, framework, and hardware layers — e.g. improper pipeline-stage placement, not using CUDA graphs, unbalanced request scheduling, KV cache eviction storms, prefill blocking raising TTFT, a failing NVLink causing a straggling PP instance, and intermittent RNIC flapping. Fixing all of them yielded 21.2% latency reduction and 24.5% throughput improvement.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
LMTracerThe paper's system: a fine-grained, real-time profiler for production LLM systems built on graph-embedded probing.
Graph-embedded probingThe core idea: implement profiling logic as ordinary GPU kernels captured into the same execution graph as the code they measure, instead of external barriers.
Probe kernelA lightweight GPU kernel that reads a hardware clock register and writes a timestamp + region ID to a shadow buffer, without touching user kernel state.
Stack-aware compilationCompile-time analysis that backtracks operator call stacks through kernel fusion to find safe, fusion-preserving locations to insert probe kernels.
Doorbell-assisted shadow bufferingTwo GPU-side buffers filled in alternation by probe kernels, drained asynchronously by a CPU poller triggered by a lightweight doorbell flag — no CPU-GPU synchronize call.
Bubble fractionThe fraction of a monitoring window where a GPU has no kernel actively executing — a measure of idle/stall time.
Straggling fractionNormalized start-time skew across GPUs in a parallel group — a measure of load imbalance or hardware degradation.
Executor-binder abstractionThe mechanism that transparently attaches probe kernels to an LLM framework's GPU-owning process by hooking Python import events.
Supporting terms
Kernel fusionCombining multiple logical operators into a single GPU kernel to cut launch overhead and memory round-trips.
CUDA/HIP GraphA captured sequence of GPU kernels replayable with a single CPU-side call, avoiding per-iteration launch overhead.
TP / PP / DPTensor / Pipeline / Data parallelism — the ways LLM compute is split across GPUs during training and serving.
TTFTTime To First Token — the serving-side latency metric LMTracer's probes are shown to barely perturb.
Release-acquire orderingThe memory-ordering guarantee (via __threadfence_system()) ensuring buffer writes are visible to the CPU before the doorbell is set.
Clock offset calibrationA one-time AllGather-based exchange of GPU clock values relative to a master GPU, used to make cross-device timestamps comparable.
