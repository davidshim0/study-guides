SOSP 2026 · A Field Guide

Test the controllers against a cluster that's simulated, not one that's merely slow

Kubernetes control planes are built from independent controllers that quietly race each other. The bugs live in orderings and stale caches a real cluster can't hold still long enough to explore. This is the plain-English story of Kamera, a system that runs real controller code against a fake, fast-forwardable cluster.

📄 "Testing Custom Control Planes Without the Cluster" · Goodwin, Kuper, Quinn 🎓 Some Kubernetes basics assumed — the primers cover them ⏱ ~30 min read
🎥

Give controllers a cluster you can rewind, replay, and rig — not one that's real, slow, and impossible to hold still.

Quick glossary

CCPCustom Control Plane — a set of controllers a team builds on top of Kubernetes to automate a domain (deploy pipelines, autoscaling, self-service platforms).
CRDCustom Resource Definition — how a CCP registers its own object types (e.g., NodeClaim) into the cluster's API.
API ServerThe single REST gateway all controllers read/write through; it persists everything into etcd.
etcdThe strongly-consistent key-value store that is the cluster's single source of truth.
ListWatchThe protocol controllers use to replicate cluster state into a local cache: list once, then watch a stream of changes.
DFSDepth-first search — the naive exhaustive-exploration strategy Kamera's authors tried first (§3.4) and found too slow.
TOCTOUTime-of-check/time-of-use — a race where a decision is correct at the moment it's made but stale by the time it's acted on.
LOCLines of code — used in the paper to size each CCP project and its Kamera integration harness.

1Declarative desired state, and why it's different▾

Instead of issuing step-by-step commands, you declare what you want ("3 replicas of this pod") and let the platform figure out how to get there and stay there. This is the core Kubernetes idea, and it's what makes the system self-healing: if something drifts, the platform just re-runs the same convergence logic.

Now you're ready: a CCP is a bunch of extra "what I want" specifications, each with its own convergence logic (a controller) bolted onto core Kubernetes.
2The reconciler pattern — a controller's one function▾

Every controller boils down to one function, Reconcile(): look at current state, compare it to desired state, take a corrective action if needed. It's called level-triggered because it only ever looks at the current level of state — it never asks "what happened since last time," only "what's true right now."

Now you're ready: Kamera's execution model (§3) is built entirely around modeling calls to this one function, across many controllers.
3Local caches and eventual consistency▾

Controllers don't read etcd directly on every reconcile — they keep a local, asynchronously-replicated cache for speed. That cache can lag behind the true state, and — critically — it can lag by different amounts for different resource types, since each type's watch stream replicates independently.

Now you're ready: "cache staleness" isn't one number per controller — it's a vector, one lag value per resource type it watches. That's exactly what Kamera perturbs.
4Level-triggered vs. edge-triggered coordination▾

Level-triggered controllers are great in isolation — resilient, idempotent, self-healing. But they have no built-in notion of "step 3 of a 9-step rollout." Coordinating a multi-controller task (like Knative shifting traffic to a new function version) means encoding an implicit sequence into a system that fundamentally doesn't think in sequences.

Now you're ready: this coordination gap is the paper's motivating problem — the bugs Kamera hunts live exactly here.
5Nondeterminism has two independent knobs▾

Two things vary between runs of the same CCP: ordering (which of several pending reconciliations fires next) and staleness (what each controller's cache shows when it fires). Different orderings and different staleness combinations can lead to different final cluster states.

Now you're ready: Kamera's whole design is about being able to control both knobs deliberately instead of at the mercy of network timing.
6State-space explosion, briefly▾

If you tried to try every ordering and every possible cache view, the number of paths grows combinatorially with the number of controllers and resource types involved — fast enough that trying them all is hopeless for real systems (the paper's back-of-envelope: 8 programs and 32 ways already gives 15M+ splits in the analogous cache-partitioning problem; CCP execution spaces are worse, since the queue itself grows as execution proceeds).

Now you're ready: Kamera doesn't try to search everything — it gives you dials to search a targeted slice on purpose.
7Simulation testing, the FoundationDB idea▾

Run the real application code, but replace its environment (network, disk, or — here — the Kubernetes cluster) with a fast, fully-controllable in-process model. You give up some fidelity to the real world, but you gain the ability to force any ordering, any fault, any timing, deterministically and instantly.

Now you're ready: this is exactly Kamera's "partial simulation" — real controllers, fake cluster.
8LLM agents as a stand-in for developer intuition▾

Knowing where to look for a bug — which controllers, which depth window — normally comes from a developer's mental model of their own system. The paper uses an LLM agent, guided by structured "skill" documents, to approximate that intuition when testing projects the authors didn't write themselves.

Now you're ready: the agent is a workflow layered on top of Kamera, not part of Kamera's core testing mechanism — a human expert could drive the same loop by hand.
The whole story in one place

Kamera in a nutshell

The coordination gap, the state-space explosion it causes, and the simulation trick that makes testing it tractable.

Custom Control Planes (CCPs) compose many independent Kubernetes controllers to automate complex tasks. Each controller is individually well-behaved — level-triggered, idempotent, self-healing — but their interactions are not directly designed; they emerge from asynchronous, racy reads and writes through a shared API server. Bugs hide in specific reconcile orderings and specific stale-cache combinations that a live cluster produces nondeterministically and can't be made to hold still.

The paper's fix, Kamera, models a CCP's execution as a state machine over a triple S = (R, Q, L) — cluster resources, pending reconciliations, and each controller's local cache — then executes that model using partial simulation: real, unmodified controller code runs against an in-process, fully-controllable stand-in for the Kubernetes API server. Because the simulator — not the network — decides ordering and staleness, Kamera can force any specific execution on demand, deterministically, in milliseconds instead of minutes.

Exhaustively trying every ordering and cache view is still intractable (queue growth compounds combinatorially), so Kamera instead exposes tunable perturbation parameters — which controllers, which depth window — and an iterative, hypothesis-driven workflow (optionally run by an LLM agent) targets them at the interactions most likely to hide bugs.

The payoff: across five real-world CCPs (Karpenter, Crossplane, Kratix, KRO, KCP), Kamera found 31 new bugs (20 confirmed by maintainers, 7 fixed), and reproduced known bugs 1,781× faster (geometric mean) than the cluster-based tool Sieve — on a 2020 MacBook Pro.

🎬 Key takeaways

  • Level-triggered controllers compose badly for multi-step orchestration — the gap is structural, not a bug in any one controller.
  • A CCP's execution has exactly two knobs of nondeterminism: reconcile ordering and cache staleness (per resource type, per controller).
  • Partial simulation = real controller code + simulated API server, interposed at the client interface — not mocking, because shared, evolving state is preserved.
  • Exhaustive exploration is intractable (queue growth compounds combinatorially); Kamera instead offers targeted perturbation parameters.
  • Two convergence oracles (eventual, deterministic) catch non-termination and path-dependent outcomes — but not silently-wrong single outcomes, which need explicit invariants.
  • An LLM agent, guided by "skill" documents, approximates a developer's intuition for where to point the perturbations — and the fewer controllers it targets, the bigger its speedup over exhaustive search.
  • Result: 31 new bugs across 5 projects, 1,781× geomean speedup over live-cluster testing.
Six everyday pictures

How to think about Kamera

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Partial simulation

A flight simulator, not a mockup cockpit

A flight simulator runs the real avionics software; it only fakes the sky, the wind, and the runway. That's different from a cardboard mockup cockpit, which fakes the software too. Kamera runs real controller code (the avionics), but swaps the real cluster (the sky) for a model it fully controls — so it can conjure any storm (ordering, staleness) on demand.

Where it breaks: a simulator's fidelity gap is a known, bounded engineering problem (aerodynamics is well understood). Kubernetes's runtime has more emergent surface area — Kamera's fidelity gaps had to be discovered empirically, twice producing false bug reports (§6.1.2, §7).
The model · State triple (R,Q,L)

A shared whiteboard, an in-tray, and a stack of sticky-note copies

Cluster resources are the whiteboard everyone can see and edit (R). Pending reconciliations are the in-tray of "you should look at this" notes waiting to be handled (Q). Each controller's local cache is its own photographed snapshot of the whiteboard, taken at a slightly different time (L) — so two controllers can be looking at photos from different moments while the whiteboard itself has already moved on.

Where it breaks: a photo is static; a controller's cache is a live, incrementally-updated stream (ListWatch) — it's less "one stale photo" and more "a video feed running at its own independent lag," different per resource type.
Why exhaustive fails · State-space growth

A conversation where everyone keeps interrupting

Try to write down every possible way a five-person conversation with constant interruptions could unfold, including who half-heard what. The number of transcripts explodes almost immediately — and every interruption spawns more potential interruptions. A CCP's pending-reconciliation queue behaves the same way: each mutation can enqueue new reconciles for every controller watching that resource type, so the queue can grow faster than exhaustive search can drain it.

Where it breaks: a conversation eventually exhausts itself; some CCP bugs are literally unbounded interruption loops (the paper's "update cycling" bug class) — the conversation never ends, which is exactly what the eventual-convergence oracle is built to catch.
Scaling · Agent-guided perturbation

Metal detecting a beach vs. a spot a friend points to

Sweeping an entire beach for one buried coin takes forever and mostly finds nothing. A friend who watched where it landed can point you to a two-meter patch. Exhaustive perturbation sweeps every controller and every depth; the agent reads the source, forms a hypothesis about which controllers actually interact, and narrows the perturbation scope accordingly — matching the paper's 4×–55× speedups, which grow with how many controllers the exhaustive sweep would otherwise have to cover.

Where it breaks: the friend might be wrong. An agent's hypothesis is just a hypothesis — if the true bug lives outside its guessed scope, it's missed, same as Kamera itself missing bugs "outside targeted regions" (§4).
A bug class · Crash recovery failure

A recipe interrupted after step one of two

A recipe says "write down who's getting a slice, then cut the cake." If you're interrupted right after writing the names but before cutting, and you come back later assuming the writing means the cutting already happened, some guests never get cake — and nobody notices, because the ledger looks complete. KRO-2 is exactly this: metadata recorded, child resources never created, and recovery logic can't tell "crashed here" apart from "user deleted these on purpose."

Where it breaks: a dinner host would eventually notice hungry guests. A silently-incomplete Kubernetes object often surfaces no error at all — which is precisely why this bug class needs fault injection perturbation to find, not just careful reading.
A limitation · Oracle scope

A spellchecker that can't catch a wrong fact

Spellcheck flags typos, not falsehoods — a perfectly-spelled sentence can still be untrue. Kamera's built-in oracles are the spellchecker: they flag non-termination and path-dependent outcomes, but a CCP that converges cleanly to one wrong-but-well-formed state (e.g., silently exceeding a configured node limit) sails right past them. Catching that requires the tester (or agent) to write down the actual fact that must hold — an invariant — and check it by hand.

Where it breaks: a fact-checker needs to already know the true fact. Here, the "fact" (the invariant) has to be reverse-engineered from source and docs first — which is exactly the domain-knowledge step the agent workflow exists to approximate.
The full explanation

How it actually works

From the coordination gap to the interactive scope explorer, grounded in the paper's own examples.

1 · The problem — coordination without a sequencing model

A controller's Reconcile() is deliberately blind to history: it only ever sees the current level of state. That's what makes it idempotent and self-healing. But high-level CCP features (Knative shifting traffic to a new function revision across nine controllers) are inherently sequential tasks. Developers close this gap with bespoke, implicit ordering assumptions baked into their reconcile logic — assumptions that hold under the orderings and cache views they happened to test, and silently fail under others.

2 · The execution model — a state triple that makes staleness explicit

Kamera represents a moment in a CCP's execution as S = (R, Q, L): resources in etcd, pending reconciliations, and each controller's local cache vector. A transition consumes one pending (c,k), runs c's Reconcile() against c's own view L_c, and produces effects that update R, enqueue new pending work into Q, and extend the event history each L is derived from.

3 · Why exhaustive search fails — the queue grows as you drain it

Two knobs of nondeterminism, both explosive. Ordering: the queue's branching factor doesn't shrink as you execute — every mutation can enqueue new reconciles for every controller watching that type, so reachable states grow at least factorially in queue size over steps. Views: each new mutation adds one more possible cache position per subscribed controller, so possible view combinations grow exponentially in the total number of watch subscriptions.

⚠
The authors tried this first (§3.4) and it lost. A bounded depth-first search kept growing its stack faster than it could clear it. Worse, because Reconcile() was treated as an opaque black box, the search couldn't safely skip repeat resource states — it had no way to know whether an unseen (Q,L) pair at an already-seen R might still produce a new R′. Most time went to intermediate states that led nowhere new.

4 · Kamera's fix — partial simulation at the client boundary

Controllers already talk to their environment through one narrow interface: the API client. Kamera interposes there with a simulation client that satisfies the same interface but reads from and writes to an in-process model of cluster state — reproducing concurrency control, deletion semantics, garbage collection, and API invariants like uniqueness constraints. Because that interface is the only way controller code touches its environment, no controller source code has to change.

This is not mocking. A mock replaces one dependency with a canned response; Kamera maintains the shared, evolving cluster state that multiple controllers genuinely interact through — the thing that makes multi-controller bugs possible in the first place.

5 · Perturbation capabilities — three modes over the same tree

With full control over ordering and views, Kamera can run one deterministic reference path, an exhaustive sweep of every ordering at every depth, or a focused sweep scoped to specific controllers and a specific depth window.

6 · The execution engine, step by step

# one transition, §4.4
(c, k) := select_pending(Q)             # lexicographic by default
effects := c.Reconcile(L[c])            // real controller code runs here
R' := apply(effects, R)
Q' := enqueue_matching_subscriptions(R, R')
L' := advance_caches(L, R, R')
record(trace, S, (c,k), S')
S := (R', Q', L')

7 · Two oracles, and where they stop

OracleFlagsMisses

This is why 3 of the paper's 8 semantic-violation bugs needed tester-supplied invariants on top of the built-in oracles — a CCP can converge perfectly cleanly to a state that still breaks a domain rule like a configured node limit.
Follow the numbers, step by step

Worked examples

Four calculations, each recomputed from the paper's own tables and figures.

① How many local views can one controller have? (Fig. 2's numbers)

etcd has logged 3 Deployment mutations and 2 Service mutations. A controller watches both types. How many distinct local-view combinations could it possibly be showing?

  1. Deployment prefixes: the controller could have replicated 0, 1, 2, or all 3 events — 4 possible positions.
  2. Service prefixes: similarly, 0, 1, or all 2 events — 3 possible positions.
  3. Views are independent per resource type (§2.1, §3.3), so combinations multiply: 4 × 3 = 12 possible local views for this one controller.
  4. Scale this up: add a third watched type with 4 events (5 positions) and it's 4×3×5 = 60 — exponential in the number of watch subscriptions, exactly as §3.3 states.
🎬
Insight: "cache staleness" isn't a single dial — it's a per-type combination lock, which is exactly why an exhaustive sweep over views alone is already exponential before ordering is even considered.

② Checking the speedup arithmetic (Table 6)

Sieve needed 512 s to reproduce RabbitMQ's unobserved-state-1 bug on a real cluster; Kamera reproduced it in 111 ms. Does the paper's reported 4,613× check out?

  1. Convert to matching units: 111 ms = 0.111 s.
  2. Divide: 512 ÷ 0.111 = 4,612.6× — the paper reports 4,613×. ✓
  3. Do it again for Cassandra's intermediate-state-1: 842 s ÷ 0.344 s = 2,447.7× — paper reports 2,448×. ✓
  4. Why the gap is so large: Sieve's time is dominated by cluster infrastructure — Cassandra pods alone need ~300 s just to become ready, which "has nothing to do with the bug" being tested. Kamera pays none of that cost because there's no real pod to boot.
💡
The 1,781× figure across all 11 bugs is a geometric mean (appropriate for ratios spanning 637× to 4,613×) — a plain average would be skewed upward by the largest outliers.

③ Recomputing the agent's speedup over exhaustive search (§6.3)

Three case studies, three different speedup claims — do the paper's own numbers reproduce them?

  1. KCP-4: exhaustive = 28 min = 1,680 s. Agent = 65 s total. 1,680 ÷ 65 = 25.8× → paper says "26×". ✓
  2. KRO-2: exhaustive = 6.2 min = 372 s. Agent = 99 s inference + 0.279 s execution ≈ 99.3 s. 372 ÷ 99.3 = 3.75× → paper says "4×". ✓
  3. KAR-12: exhaustive times out at 2 h = 7,200 s (a lower bound — it never actually finished). Agent = 2.2 min + 0.194 s ≈ 132.2 s. 7,200 ÷ 132.2 = 54.5× → paper says "55×". ✓
  4. The trend: speedup grows with controller count (2 → 6 → 14 controllers gives 4× → 26× → 55×+), because exhaustive cost scales with the whole CCP while the agent's targeted scope stays small regardless of how big the system is.
🎬
Insight: almost all of the agent's wall-clock time is inference (reading code, forming a hypothesis), not simulation — Kamera's own execution is consistently sub-second across all three.

④ Tallying the bug taxonomy (Tables 3–5)

Do the per-category and per-project bug counts actually add up to 31?

  1. By category (Table 3): 17 data races + 8 semantic violations + 4 crash-recovery failures + 2 update cycles = 31. ✓
  2. By project: Karpenter 12 + Crossplane 5 + Kratix 6 + KCP 6 + KRO 2 = 31. ✓
  3. By detection method (Table 4): 26 via deterministic-convergence oracle + 2 via eventual-convergence oracle + 3 via invariant checks = 31. ✓
  4. Confirmation rate: 20 of 31 confirmed by maintainers = 64.5% ≈ 65%; of those, 7 fixed so far = 35% of confirmed bugs already resolved.
💡
84% of bugs (26/31) were caught by the deterministic-convergence oracle alone — the single cheapest signal (does re-ordering change the outcome?) does most of the work.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
Sieve and Acto both execute controllers on a real cluster and both are well-regarded tools. Why can't they simply be pointed at a CCP's nine controllers together to find multi-controller bugs?
Show answer
They test one controller at a time by design — their oracles compare a single controller's behavior against a reference. Even running all nine controllers side by side on a real cluster wouldn't help, because a live cluster gives you no way to force a specific ordering or a specific cache-staleness combination; you get whatever the network happens to produce.Misconception: that the limitation is about scale ("just run more controllers"). It's actually about controllability — the real cluster's nondeterminism can't be steered, only observed.
Problem 2 · medium
Q starts with 3 pending reconciliations. After the first one executes, its mutation triggers 2 new reconciles for other watching controllers. Why does the paper say reachable states grow "at least factorially in the queue size over the number of steps," rather than just factorially in the initial 3?
Show answer
Because Q isn't fixed — every transition can add new pending work faster than it removes the one just consumed. So the branching factor at step 2 isn't "2 remaining choices," it's "however many are now in Q," which itself grew. The naive "3 controllers → 3! orderings" intuition only holds if the queue never grows, which it does.Misconception: treating the initial queue size as the whole story. The queue's growth-while-draining behavior is exactly what makes exhaustive search intractable in practice (§3.3), not just slow.
Problem 3 · medium
The authors' first exhaustive search tool applied memoization but it barely helped. Why didn't caching repeated resource states (R) save the search much time?
Show answer
Because Kamera treats each controller's Reconcile() as a black box, it can't prove that an unseen (Q, L) pair at an already-visited R is redundant — that pair might still, for all the search knows, produce a brand-new R′. So it has to actually execute every (R,Q,L) triple even when R repeats often, because R alone isn't enough information to skip anything safely.Misconception: that "we've seen this resource state before" is enough to prune. Soundly pruning requires knowing something about the controller logic itself, which black-box execution deliberately doesn't have.
Problem 4 · hard
KAR-12 (the stale-read node deletion) is described as a time-of-check/time-of-use race where "the check and the binding are both correct in isolation." Explain what that phrase means and why it makes the bug hard to spot by code review.
Show answer
The disruption controller's "is this node empty?" check is a correct implementation of emptiness-checking against whatever it currently sees. The scheduler's pod-binding write is a correct implementation of scheduling. Neither piece of code has a bug on its own — the failure only exists in the gap between them: the disruption controller's cache hadn't yet replicated the binding when it made its decision. Code review of either controller alone would find nothing wrong.Misconception: that TOCTOU bugs are "bugs in the check" or "bugs in the use." They're bugs in the unstated assumption that the two happen atomically relative to each other — which is precisely the class of bug that requires perturbing cache staleness to surface, not reading source code.
Problem 5 · medium
A scenario converges to exactly one terminal state every time you run it — no matter the ordering or staleness perturbations. Karpenter has provisioned 5 more nodes than its configured limit allows in that one state. Will either convergence oracle flag this?
Show answer
No. Deterministic convergence only checks whether different executions reach different terminal states — here they all agree, so it's satisfied. Eventual convergence only checks that execution terminates — it does. Both oracles pass cleanly on a single, consistently wrong answer. Catching this requires an explicit invariant ("node count ≤ configured limit") checked against the trace — which is exactly how 3 of the paper's 8 semantic-violation bugs were found.Misconception: that "the built-in oracles didn't fire" means the scenario is correct. Convergence (even deterministic convergence) says nothing about whether the converged state is the *right* state.
Problem 6 · easy
Why does the paper describe Kamera's LLM agent as replaceable by "a developer using their knowledge of the target system directly"? What is the agent's role, precisely?
Show answer
The agent isn't part of Kamera's testing mechanism — it's a workflow layered on top, approximating the domain knowledge a project's own developer would normally supply for free: which controllers plausibly interact, which scenarios are worth trying, and how to interpret a trace. Kamera itself just executes scenarios and perturbations regardless of who or what chose them.Misconception: that Kamera "requires AI" to work. The paper is explicit that the agent is there because the authors weren't the original developers of the five CCPs — it substitutes for missing insider knowledge, not for a missing capability in Kamera.
Problem 7 · hard
The agent's speedup over exhaustive search was 4× for KRO-2 (2 controllers) but 55× for KAR-12 (14 controllers), even though both used roughly similar amounts of agent inference time. Why does the speedup grow with system size rather than staying constant?
Show answer
Exhaustive search's cost scales with the combinatorics of the whole system — more controllers and resource types means more orderings and more view combinations, so its wall-clock cost grows steeply (and, for KAR-12, didn't even finish in 2 hours). The agent's cost is roughly the same regardless of system size: read the code, identify the handful of genuinely interacting controllers, run a scoped sweep over just those. As the denominator (exhaustive cost) grows and the numerator (agent cost) stays flat, the ratio — the speedup — necessarily grows too.Misconception: that the agent "got smarter" on the bigger system. The agent's approach didn't change; the exhaustive baseline just got combinatorially more expensive to compare against.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most.

Q1What exactly is a "Custom Control Plane"?▾
A collection of custom Kubernetes controllers a team builds to automate a domain — Karpenter for node autoscaling, Crossplane for cloud-provider APIs, Kratix for internal developer platforms, and so on. Each registers its own resource types (CRDs) and reconciles them, composing to deliver a higher-level feature no single controller implements alone.
Q2Why can't more integration tests on a real cluster just solve this?▾
A real cluster exercises exactly one execution path per run, and developers don't control which path — reconcile ordering is nondeterministic and cache staleness depends on network conditions and API server load. A test can pass reliably for months and still mask a bug that only manifests under one specific ordering you never happened to hit.
Q3How is "partial simulation" different from mocking dependencies in a unit test?▾
Mocking replaces a dependency at some interface with a canned, static response. Kamera's simulation client instead maintains the shared, evolving cluster state that multiple controllers read and write through — preserving the actual interaction surface where multi-controller bugs live, rather than removing it.
Q4What does Kamera give up by not running a real API server?▾
Fidelity below the client interface — real networking effects, and any behavior that depends on lower-level mechanisms Kamera doesn't model. The paper reports this cost as two false-positive bug reports (later corrected) out of 31 findings, and notes the fidelity gap is intrinsic to the approach, not fully eliminable.
Q5Is the LLM agent required to use Kamera?▾
No. The agent approximates the domain knowledge a CCP's own developer would normally bring to testing; a developer can run the same reference-then-perturb workflow by hand using their own knowledge of the system. Kamera's core mechanism — the simulator and its perturbation controls — doesn't depend on an agent at all.
Q6What do the two convergence oracles actually check, and what do they miss?▾
Eventual convergence: does execution terminate within a depth bound? Deterministic convergence: do all executions from the same start reach the same terminal state? Neither catches a scenario that converges consistently to one state that's simply wrong by some domain rule — that needs an explicit, tester-supplied invariant.
Q7How does Kamera guarantee a specific bug-triggering execution is reproducible?▾
Every finding is backed by a concrete scenario plus a perturbation configuration (which controllers, which depth window, which staleness) that deterministically replays the exact triggering schedule — unlike a live cluster, where the same test can take a different path on the next run.
Q8Are the 31 bugs newly discovered, or bugs Sieve/Acto already knew about?▾
New. Sieve reproduction (§6.2) is a separate speedup experiment on 11 already-known bugs in different projects (ZooKeeper, RabbitMQ, Cassandra operators), used purely to benchmark Kamera's speed. The 31-bug count comes from applying Kamera to five different, previously-untested CCPs (Karpenter, Crossplane, Kratix, KRO, KCP).
Q9Why is Kamera implemented in Go?▾
To directly interoperate with controller-runtime, the framework most real-world CCP projects (including all five evaluated ones) are built on — the same language and, where possible, the same interfaces, minimizing the adapter code needed to wire in unmodified controller source.
Q10How does Kamera compare to model checkers like Kivi (which uses SPIN)?▾
Kivi models both Kubernetes and the CCP in a specification language and checks the model — thorough, but it can only find bugs that the model itself expresses, not ones hiding in behavior the model-writer didn't anticipate. Kamera instead executes the CCP's actual, unmodified implementation, at the cost of not exploring exhaustively.
Q11Is Kamera sound and complete?▾
Explicitly neither. It's not complete because exhaustive exploration remains intractable even under simulation, so targeted perturbation can miss bugs outside its scope. It's not sound in the strict sense because simulator or harness fidelity gaps can produce false positives — two occurred during the paper's evaluation and were corrected after maintainer feedback.
