SOSP 2026 · A Field Guide

Fixing crash consistency by cloning the kernel, not the cache

Databases bypass the OS I/O cache and build their own to get fast, safe writes. VoliStorM asks: what if instead of a second cache, you gave the write path a second, minimal kernel — one that shares the very same cache?

📄 Toljaga, Derumigny, Aggoun, Bacou, Thomas · SOSP '26 🎓 Some virtualization/page-cache basics assumed — primers cover them ⏱ ~30 min read
🖥️🖥️

SHARE the I/O cache between two kernels instead of DUPLICATING it into a second, user-space cache.
The general-purpose kernel keeps the cache smart; a tiny latency kernel keeps the write path fast.

1The I/O cache is a page cache, not just a lookup table▾

Linux's page cache holds file-backed pages the same way it holds anonymous pages: via the page tables, subject to eviction, read-ahead, and — critically — write-back. A dirty file page isn't just "cached data," it's a promise to eventually write itself to disk, on a schedule the kernel controls, not the application.

That write-back scheduling is exactly what breaks crash consistency: a page can flush at any moment, independent of the application's notion of "this update is done."

Now you're ready: every problem in this paper traces back to write-back timing being decided by the kernel's LRU/MGLRU logic, not by the application's failure-atomic sections.
2Failure-atomic sections: the semantic gap▾

An application thinks in terms of high-level operations (a bank transfer: debit + credit). The storage system only sees individual byte writes. A failure-atomic section is the contract that says: either every write inside it is durable after a crash, or none are.

The page cache has no notion of "section" — it evicts and flushes individual pages. So something has to bridge the gap between "durable per-page" and "durable per-transaction." That something is normally a log.

Now you're ready: VoliStorM's fas_start/fas_end pair is this contract, implemented with a classic redo log instead of ad hoc per-object bookkeeping.
3Redo logging in one sentence▾

To make a section atomic: (1) collect the pages it modified (the write set), (2) copy them to a separate durable log, (3) mark the log committed, (4) only then apply the log to the real file, at your leisure. If you crash before commit, the log is discarded and nothing changes; if you crash after, you replay the log — safely, since applying it twice is harmless (idempotent).

Now you're ready: steps 1–3 are latency-critical (the app is blocked); step 4 is throughput-critical (it runs async). VoliStorM optimizes each with a different technique — this split shows up constantly in §3.2.3 of the paper.
4Two-level paging under virtualization▾

You already know a single-level page table maps VA→PA. Under hardware virtualization, the processor walks two tables per access: the guest's own page table (GPT, GVA→GPA) and the hypervisor's EPT (GPA→HPA) — nested, both active at once. This is the mechanism CXL/tiering research also leans on for memory isolation, but here it's repurposed for something else entirely: giving two independent kernels two independent page tables on hardware that only has room for "one" from a plain OS's point of view.

Now you're ready: the G-kernel owns the EPT (it manages real memory); the L-kernel owns the GPT (it only needs to know what the process wrote). Neither has to touch the other's structure.
5Dune-style syscall delegation▾

A process running inside a lightweight VM (à la Dune) can't call the host kernel directly — there is no host kernel inside the VM. The trick: forward the syscall out to a regular process running natively, which executes it and returns the result. Done naively (exit the VM, ask KVM, re-enter), this is slow; VoliStorM instead keeps a native sibling thread permanently alive per vCPU thread, communicating over shared memory.

Now you're ready: this is what makes libvolimem "transparent" — open(), read(), networking, everything except the write-path internals behaves exactly as it would outside the VM.
6MAP_PRIVATE vs MAP_SHARED, and why it matters here▾

MAP_SHARED file mappings are exactly the page cache: dirty a page, and the kernel may write it back to the file whenever it likes. MAP_PRIVATE mappings are copy-on-write: the kernel loads pages from the file but never writes them back — from Linux's perspective they become indistinguishable from anonymous memory once dirtied.

That "never writes back" property only rules out one thing: Linux flushing the page to the file on its own. It does not stop the G-kernel's LRU from touching the page at all — a dirty private page still looks like ordinary anonymous memory to the reclaim path, so under memory pressure it can still be swapped out even though VoliStorM already has it safely logged. Closing that gap is a separate mechanism (see Primer 6's "ready" note and §5 of How It Works).

Now you're ready: VoliStorM's crash-consistent mappings are MAP_PRIVATE. A separate MAP_SHARED mapping of the same file, opened only by the async apply thread, is what actually reaches disk.
7Dirty bits, page faults, and two ways to collect a write set▾

To know which pages a section touched, you can (a) make pages read-only up front and let the first write fault, tagging the page in the fault handler (Detect-On-Write), or (b) leave pages writable and, at commit time, walk the page table reading hardware dirty bits (Dirty-Collection). (a) pays a fault per page but is cheap for sparse writes; (b) pays a full table walk but is cheap when writes cluster together (e.g., Zipfian access).

Now you're ready: DOW vs. DC is a workload-dependent knob, not a fixed design choice — the paper picks whichever wins per benchmark (§4.5, "Flexibility").
8Linearizability, "durable" vs. "buffered"▾

Durable linearizability: when a write call returns, its effect is guaranteed on disk — the strongest, slowest guarantee. Buffered (a.k.a. "eventual" or "relaxed") mode: the state will eventually be consistent after a crash, but the very latest updates since the last snapshot may be lost. Redis's synchronous AOF is durable-linearizable; its RDB snapshotting is buffered.

Now you're ready: when you see VoliStorM compared "at 10 ms" vs. Redis AOF "at 1 s," that's buffered mode with a much tighter durability window — and VoliStorM still wins on throughput despite committing 100× more often.
The whole story in one place

VoliStorM in a nutshell

The conflict, the architectural trick that resolves it, and how the pieces click together.

Storage got fast (NVMe: µs, PMEM: ~1 µs per page write), but the software above it didn't. Reading is fine — the L-kernel-worthy insight is that the G-kernel's I/O cache makes reads nearly free. Writing durably is the problem. A single msync on ext4 costs 89 µs, on btrfs 337 µs — 8.5× to 32× the raw 10.5 µs NVMe round trip. That tax isn't a bug: it's the price of a general-purpose kernel synchronizing every dirty page with AutoNUMA, MGLRU, adaptive read-ahead, KSM, and copy-on-write — dozens of subsystems with no reason to care about your failure-atomic section.

The standard escape hatch is the out-kernel design: build a second cache in user space (Redis, PostgreSQL, RocksDB all do this) and bypass the kernel's I/O cache entirely for writes. It works, but at a steep engineering cost — Redis spends 3,482 lines just on persistence — and it throws away 35 years of kernel cache tuning, plus creates a semantic gap where Linux can swap out pages that are already safely on disk.

VoliStorM's move: instead of doubling the cache, double the kernel. A minimal L-kernel runs alongside the G-kernel, sharing the exact same physical pages, but tracking writes through its own independent page table — so it never has to synchronize with any G-kernel subsystem. Hardware virtualization is what makes "two independent page tables, one process" possible: the G-kernel manages the EPT (GPA→HPA), the L-kernel manages the GPT (GVA→GPA), and they're stacked, not shared.

The payoff: across Redis, memcached, PMEM key-value stores, and three language runtimes, VoliStorM matches or beats the out-kernel design's throughput — often by double digits, though it's up to 2.2× slower than PMDK on a write-intensive, uniform-distribution tree-map workload — while cutting the persistence-specific code by roughly 45× (Redis: 137 vs. 3,482+2,721 lines) and reusing the kernel's read-side optimizations for free.

🍯 Key takeaways

  • Software, not hardware, is the storage bottleneck now: 88–97% of a durable msync is kernel overhead, not device time.
  • That overhead is structural: a general-purpose kernel must synchronize every dirty page with its many mm subsystems.
  • Out-kernel designs dodge the overhead but pay in engineering cost, lost kernel optimizations, and a swap-related semantic gap.
  • VoliStorM's fix: two independent page tables (GPT for the L-kernel, EPT for the G-kernel), stacked via KVM virtualization, sharing one physical cache.
  • MAP_PRIVATE + a redo log (collect → log → commit → async apply) keeps the latency-critical path off G-kernel write-back entirely — though the async apply phase deliberately routes through a MAP_SHARED mapping and msync.
  • Net result: dual-kernel ≥ dual-cache on performance, at a fraction of the code, across databases, caches, and three language runtimes.
Six everyday pictures

How to think about VoliStorM

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core move · Two kernels, one warehouse

One warehouse, two staff badges

A warehouse (the I/O cache) already has an efficient staff running it. Instead of building a second warehouse next door duplicating the same inventory, you give one badge-holder a private side office (the L-kernel) with just enough paperwork to know which shelves changed — no duplicate inventory, no second building. Everyone still shares the one warehouse.

Where it breaks: the side office genuinely needs its own filing system (a page table) to avoid queueing behind the main staff — that's the part a metaphor alone can't motivate; it needs real hardware support (virtualization).
The mechanism · Two-level paging

A locker inside a locked room

Your address is "locker 12, room 4." Two independent keyholders manage the two locks: the building manager (G-kernel) controls which physical room a numbered room maps to (EPT); a tenant (L-kernel) controls which locker number maps to which slot inside their own room (GPT). Neither needs the other's key to do their job — but reaching the actual shelf always requires walking through both locks.

Where it breaks: normally you'd want fewer locks for speed, not more. VoliStorM accepts the two-lock tax (mitigated with huge pages and packed page directories) because the alternative — one lock shared by two untrusted parties — is exactly the synchronization it's trying to avoid.
Design discipline · Latency vs. throughput phases

The express line and the restocking cart

At checkout, the express line (collect + log, at commit time) needs to be as fast as humanly possible because a customer is standing there waiting — every second counts. Restocking the shelves afterward (applying the log to the real file) doesn't need to be instant; it needs to be efficient, so it runs on a separate cart, in the background, at whatever pace keeps up.

Where it breaks: in a real store the cart can always keep up. Here, if the restocking cart (NVMe apply) is much slower than checkout (PMEM logging), the backlog — the log — can grow enormous (163,000 pages in the paper's hybrid config), which the metaphor doesn't warn you about.
Isolation · MAP_PRIVATE

Your own photocopy, not the original

Instead of writing directly on the master document (the real file, which the librarian might refile at any moment), you work on your own photocopy. Nobody will ever "helpfully" refile your photocopy for you — it just sits there until you decide it's safe to throw away, i.e. once the master has been safely updated through the proper channel (the async apply thread).

Where it breaks: photocopies don't cost real memory; private COW pages do. That's exactly why the optional memory-release step (shredding old photocopies via madvise(DONTNEED)) exists — and why it needs a careful check that nothing changed since the copy was made, to avoid shredding a photocopy someone quietly updated.
Correctness · Idempotent replay

A grocery list you can safely re-read twice

A well-written to-do list is safe to redo from the top even if you're not sure how far you got — "buy milk" twice just means you check the fridge and skip it if already done. VoliStorM's log is written so that re-applying a committed transaction after a crash produces the same state whether it runs once or twice — which is exactly what makes "replay everything committed" a safe, simple recovery procedure.

Where it breaks: the grocery list works because buying milk twice is harmless. Idempotent replay works because it's engineered to be — the redo log always writes the same final bytes, never "increment by one," which would double-apply incorrectly.
Why not just SPDK · The read side matters

Don't fire the whole kitchen staff to speed up one order

Bypassing the kernel entirely (SPDK-style) is like closing the whole restaurant's kitchen to personally cook one urgent dish faster — it works for that dish, but now every other order (ordinary reads, read-ahead, page reuse) has no kitchen at all and must be reinvented from scratch. VoliStorM keeps the kitchen (G-kernel cache) fully staffed for reads and only adds a dedicated fast lane for the one urgent thing: durable writes.

Where it breaks: a kitchen doesn't have anything like page-table synchronization costs; the analogy captures "don't discard working infrastructure" but not why the fast lane specifically needs its own page table rather than just a fast queue.
The full explanation

How it actually works

From the diagnosis, through the two-kernel architecture, to the redo-log mechanics.

1 · Why the G-kernel alone can't be fast here

Reading is nearly free: a cached 4 KB page load takes 1.1 µs vs. 16 µs with O_DIRECT — a 15× win from the cache alone, and MMIO on top of that turns a 2.6 s read loop into 7 ms (>350×). The trouble starts on write-back. Mapping a fresh page into a file-backed inode takes 5.1 µs total: 0.7 µs for the page-fault handler and page-table update, 1.4 µs to allocate the page, and 3 µs — the majority — updating the inode's xarray and linking the page into the MGLRU subsystem. If 0.7 µs is the floor, roughly 87% of that latency is pure subsystem bookkeeping that has nothing to do with the write itself.

🌱
Concretely: forcing a page durable end-to-end (via msync) costs 89.4 µs on ext4 (journaling) and 337 µs on btrfs (copy-on-write) — 8.5× and 32× the raw 10.5 µs NVMe round trip. Even fully bypassing the filesystem, raw device access through Linux still costs 21 µs, 2× the device floor.

2 · The out-kernel escape hatch, and its cost

Since the G-kernel path is inherently taxed, production systems (Redis, PostgreSQL, MySQL, RocksDB, Infinispan) simply build a second cache in user space and manage durability themselves via write-ahead logging. It's effective — but it forces manual dirty-object tracking (no page-table dirty bits available), duplicate data copies, and abandons kernel cache optimizations like MGLRU entirely. Redis alone carries 3,482 lines just for persistence; adding PMEM support tacked on another 2,721.

3 · Two page tables, one process — the enabling mechanism

A CPU normally walks one page table. Hardware virtualization walks two: the guest's GPT (GVA→GPA) nested inside the hypervisor's EPT (GPA→HPA). VoliStorM assigns the EPT to the G-kernel (it manages real memory, isolation, swap) and the GPT to the L-kernel (it only needs to know what the process wrote). libvolimem bootstraps this by loading the process natively first, then remapping its segments at identical addresses across HVA, GPA, and GVA — so a pointer means the same thing everywhere.

4 · The redo-log pipeline: collect → log → commit → apply

At fas_end, VoliStorM runs the latency-critical half of the pipeline entirely inside the L-kernel:

// step 1 — collect (GPT only, no VM exit)
write_set = DOW ? faulted_pages() : DC ? dirty_bits_walk() : ...

// step 2 — log to durable storage
for page in write_set:
    log.append(page.content, page.pfn)         // optionally: diff only changed cache lines
log.mark(committed)                       // fas_end can now return

// step 3 — apply, asynchronously, throughput-optimized
for entry in log.committed_transactions():
    shared_mapping[entry.pfn] = entry.content
    msync(shared_mapping, entry.pfn)            // via a 2nd, MAP_SHARED mapping
💡
Why split step 2 from step 3? Step 2 blocks the application, so it's tuned for latency (skip the G-kernel path entirely, optionally log only dirty cache lines). Step 3 doesn't block anyone, so it's tuned for throughput — it deliberately uses the G-kernel's ordinary msync, because at this point there's no latency to protect, only bandwidth to maximize.

5 · Closing the semantic gap: memory release

Because the crash-consistent mapping is MAP_PRIVATE, the G-kernel sees an ever-growing pile of dirty pages it's forbidden to write back — and under memory pressure, its only option is to swap them out, even if VoliStorM already safely persisted them. VoliStorM's optional fix: once a page is logged and applied to the real file, call madvise(MADV_DONTNEED) to drop the private copy and reconnect the address to the clean, up-to-date shared inode mapping — but only after atomically confirming the private and logged copies still match (removing write access briefly, at the cost of a TLB shootdown) to avoid discarding a page the application already overwrote again. Reclaiming a page that's merely been logged but not yet applied would risk discarding state newer than what's actually on disk — the apply step must complete first.

⚠
The trade-off: under light memory pressure, this costs throughput for nothing (15→12 Kops/s in one measurement). Past ~74% memory occupancy, it wins big — up to 55% higher throughput than unoptimized VoliStorM, and 3.4× Redis AOF — because it's the only configuration that avoids swapping already-persisted pages. (§4.7)
Follow the numbers, step by step

Worked examples

Four traces straight from the paper's tables, recomputed to check the claims.

① How much of a durable write is "software tax"?

Table 1: NVMe round trip 10.5 µs; ext4 (data journal) 89.4 µs; btrfs (flushoncommit) 337 µs. What fraction of each is pure software overhead?

  1. ext4: software time = 89.4 − 10.5 = 78.9 µs. Fraction = 78.9 / 89.4 = 88.3%.
  2. btrfs: software time = 337 − 10.5 = 326.5 µs. Fraction = 326.5 / 337 = 96.9%.
  3. Both land inside the paper's own quoted range: "88–97% of the time is spent in software." ✓
  4. btrfs's copy-on-write metadata commit adds nearly 4× ext4's overhead on top of an already-taxed baseline — stronger consistency, steeper price.
🍯
Insight: even the "cheap" journaling filesystem spends 9 out of every 10 µs on bookkeeping that has nothing to do with the physical write.

② Where does the 87% figure for page-fault mapping come from?

Mapping a fresh page: 0.7 µs (fault handler + page table) + 1.4 µs (page allocation) + 3.0 µs (xarray + MGLRU link) = 5.1 µs total.

  1. Bare minimum (per the paper): 0.7 µs — just the fault handler and page-table update.
  2. Everything else: 5.1 − 0.7 = 4.4 µs is allocation + subsystem bookkeeping.
  3. Fraction: 4.4 / 5.1 = 86.3%, matching the paper's rounded "87%."
  4. Biggest single piece: the 3 µs xarray/MGLRU link alone is 58.8% of the total — more than 4× the actual page-table update.
💡
This is the concrete evidence behind "35 years of accumulated subsystems": one mapping operation touches at least three independent pieces of bookkeeping before the fault handler is even done.

③ Memcached: the cost of the strongest durability setting

"eachop" commits every single operation (durable linearizability, 0 ms interval). Volatile memcached: 7.5 Kops/s (load), 8.7 Kops/s (run). eachop: 6.0 Kops/s (load), 7.5 Kops/s (run).

  1. Load-phase slowdown: (7.5 − 6.0) / 7.5 = 20.0% — matches the paper exactly.
  2. Run-phase slowdown: (8.7 − 7.5) / 8.7 = 13.8% — the paper rounds this to "15%"; close, within measurement/rounding noise.
  3. Both are worst-case numbers: eachop is deliberately the most durable, least practical setting for a cache whose whole point is that losing data is tolerable.
🍯
Insight: even VoliStorM's hardest setting only costs 14–20% — for a workload (per-operation durability on a cache) that arguably never needs it. Realistic settings (1–100 ms) show no measurable cost at all.

④ Log growth: why hybrid storage needs a bigger log

Table 2, buffered (10 ms) mode: PMEM log = 545.89 pages, recovery 2.484 ms; NVMe log = 3609.03 pages, recovery 29.671 ms.

  1. Log-size ratio: 3609.03 / 545.89 = 6.6× — the paper describes this as "grows to 7× the size," consistent within rounding.
  2. Recovery-time ratio: 29.671 / 2.484 = 11.9× — matching the paper's "roughly 12× longer."
  3. Why: NVMe's higher per-write latency means more transactions accumulate in the log before the apply phase can drain them — the log fills at the app's speed but drains at NVMe's speed.
  4. Worst case — Hybrid CL-U (durable): log balloons to 163,000 pages because logging to PMEM is fast but applying to NVMe is slow; the log must be sized for that gap or the application will block once it fills.
💡
This is a direct, quantitative version of the "express line vs. restocking cart" analogy: whenever the express line is faster than the restocking cart, the backlog (log) grows until something gives.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks for.

Problem 1 · easy
NVMe write latency is ~10.5 µs. Why does a "safe" write through ext4 with journaling take 89.4 µs — 8.5× longer — when the drive itself hasn't gotten any slower?
Show answer
Because the extra 78.9 µs isn't device time at all — it's the general-purpose kernel synchronizing the write with its many subsystems (page-table updates, the xarray, MGLRU linking, journal transaction bookkeeping) before and after the actual I/O. The hardware got faster; the software layered on top of it did not.Misconception: that slow durable writes mean slow storage. The paper's whole motivation is the opposite — modern storage is fast; the kernel's generality is what's slow.
Problem 2 · medium
Why can't VoliStorM simply add a second, independent page table structure inside ordinary (non-virtualized) Linux, avoiding KVM entirely?
Show answer
A processor's MMU only walks one active page table (pointed to by one control register, e.g. CR3 on x86) per address space at a time — there's no hardware path for "two independent, simultaneously-active page tables for one process" without virtualization's two-level paging (GPT nested in EPT). Software could emulate a second table, but every translation would then require trapping into software on every access — exactly the synchronization overhead VoliStorM is trying to eliminate.Misconception: that page tables are a purely software data structure you can just duplicate. They're software data read directly by hardware — duplicating them for free requires hardware support for exactly that, which is what virtualization provides.
Problem 3 · easy
Why does VoliStorM map its crash-consistent file with MAP_PRIVATE instead of the usual MAP_SHARED?
Show answer
MAP_SHARED lets Linux write dirty pages back to the file whenever its own LRU/write-back logic decides to — completely independent of the application's failure-atomic sections, which is exactly the source of the semantic gap. MAP_PRIVATE pages are copy-on-write and Linux never writes them back; from the kernel's point of view they behave like anonymous memory. That guarantees the only path from memory to the file is VoliStorM's own controlled redo-log apply step.Misconception: that MAP_PRIVATE means "not durable." It's actually what makes VoliStorM's durability controllable — durability comes from the log, not from the mapping type.
Problem 4 · medium
In hybrid storage (PMEM log + NVMe data), the log grows to 163,000 pages under durable linearizability (Table 2, CL-U) — far larger than either pure-PMEM or pure-NVMe configurations. Why?
Show answer
Logging (to PMEM) is much faster than applying (to NVMe), so committed transactions pile up in the log faster than the async apply thread can drain them to the slower device. When log and data share one device (pure PMEM or pure NVMe), logging and applying run at the same speed, so the log stays small. Mixing fast-log with slow-apply removes that natural balance.Misconception: that a faster log device is strictly better. It's better for latency, but it can make the log grow unboundedly if the paired apply path can't keep pace — the log must be provisioned for the slower of the two.
Problem 5 · hard
On a write-intensive, uniformly-distributed tree-map workload, VoliStorM is up to 2.2× slower than PMDK (§4.5). Doesn't this undermine the paper's claim that the dual-kernel design is "at least as efficient" as specialized approaches?
Show answer
No — the paper's claim is scoped: VoliStorM is competitive with the out-kernel dual-cache approach (Redis/AOF, PMEM-Redis, memcached, PMThreads), and it explicitly reports PMDK as a case where hand-declared write sets (no runtime collection needed) beat automatic collection on pure-write workloads. The honest conclusion (§4.5) is "no clear winner" between VoliStorM and PMDK: VoliStorM wins reads (up to 2.7×) by keeping a volatile cache; PMDK wins heavy writes by skipping write-set collection entirely, at PMDK's much higher engineering cost (explicit instrumentation of every persistent write).Misconception: that "as efficient as" means "faster in every single measurement." The paper is precise about which comparison (vs. out-kernel designs) that claim covers, and separately reports where a lower-level, higher-effort library still wins.
Problem 6 · medium
Why does the paper measure "getpid" overhead (980 ns) specifically, when no real application calls getpid in a hot loop?
Show answer
getpid is chosen precisely because it does almost no work — it's the closest thing to a pure measurement of libvolimem's syscall-delegation overhead (the sibling-thread handoff via shared memory) with none of the delegated work's own cost drowning it out. It's a deliberate worst case: any syscall that does more actual work (like I/O) will show proportionally less overhead, as the paper confirms by noting I/O syscalls show no measurable slowdown at all.Misconception: that a synthetic worst-case microbenchmark is meant to predict real workload behavior directly. It's meant to isolate and bound one specific cost, which the paper then contextualizes against costs that matter more in practice.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1Is the L-kernel a full kernel, or just a thin shim?▾
It's deliberately minimal: it manages a page table (GPT) and enough machinery to collect write sets and log them. It has no scheduler of its own, no device drivers, no filesystem — every syscall other than the write-path internals is forwarded transparently to the G-kernel via a sibling thread. "Kernel" here means "owns an independent page table and interrupt path," not "reimplements an OS."
Q2Why not just run the whole application inside a normal VM?▾
A normal VM gives you an isolated guest OS and its own (separate) page cache — which is the dual-cache problem all over again, just moved into a VM boundary. VoliStorM's point is the opposite: keep one shared cache (managed by the host G-kernel) and use virtualization only to get a second page table for write-set tracking, not a second full OS environment.
Q3How does the L-kernel "see" writes without any help from Linux?▾
It uses its own GPT, which the MMU consults on every guest memory access, independent of the G-kernel's EPT. When a page is written, the L-kernel's own page-fault handler (or a page-table walk at commit time) observes it directly through hardware — no syscall, no VM exit, no Linux subsystem in the loop.
Q4Does VoliStorM replace ext4/btrfs journaling entirely?▾
Not at the filesystem level — files still live on whatever filesystem you choose. VoliStorM adds its own crash-consistency layer above the page cache (via the redo log), so the file's own journaling/COW mechanics become largely redundant for VoliStorM-managed writes; the paper measures plain ext4/btrfs journaling latency specifically to show why bypassing it is worth the engineering effort.
Q5What actually happens on a crash?▾
On reboot, VoliStorM scans the durable log: any transaction never marked "committed" is discarded (as if it never ran); every committed transaction is re-applied to the file. Because apply is idempotent, replaying a transaction that was already partially or fully applied before the crash is harmless. In the memcached demo, this recovery step took about 5 seconds before the application itself could resume.
Q6Why not bypass the kernel entirely, like SPDK-based systems do?▾
Bypassing the kernel for reads too throws away 35 years of read-side optimization (adaptive read-ahead, MGLRU, the multi-queue block layer) that the paper shows is genuinely valuable — cached sequential NVMe reads are nearly as fast as anonymous memory. VoliStorM's dual-kernel design keeps that read-side machinery fully intact and only adds a specialized fast path for the specific operation (durable writes) that the general-purpose kernel is bad at.
Q7Does VoliStorM handle multiple threads well?▾
Yes, but with a caveat: it counts threads inside a failure-atomic section and only snapshots once the last one exits, serializing new sections against an in-progress snapshot to avoid capturing half-finished state. Under high concurrency this becomes a bottleneck — the paper measures up to 41% overhead at 10 threads with per-operation commits — and explicitly leaves MVCC-based concurrency control as future work.
Q8How much application code actually needs to change?▾
It varies by depth of integration: 137 lines for Redis (wrapping state-changing operations), 168 for memcached (persistent allocation + three locks), 9 lines to make C++'s STL containers persistence-aware, 193 lines for a Rust typing layer, and 159 lines inside the CPython runtime itself (out of 1.45M total) to persist the entire heap.
Q9Is this portable beyond x86_64?▾
libvolimem is x86_64-specific today (it manages control registers like CR3, GDT, IDT directly) and runs on both Intel and AMD since KVM abstracts their virtualization differences. Porting to ARM or RISC-V is architecturally plausible — both have equivalent two-level paging — but would require re-implementing the low-level register management from scratch.
Q10Why does virtualization sometimes make things faster (Fig. 11's memory benchmark)?▾
The paper's hypothesis: under virtualization, GVA→HPA translations get cached in TLB entries reserved for the guest, which aren't shared with (and evicted by) other host processes the way ordinary TLB entries are. It's a side effect, not a designed feature — and the paper controls for it by always comparing against the volatile baseline running inside VoliStorM too.
Q11Does VoliStorM always beat the out-kernel dual-cache approach?▾
On Redis and memcached, yes, consistently. Against PMDK specifically (a lower-level library, not a full dual-cache system) on pure write-intensive PMEM workloads, PMDK can still win by up to 2.2× — because it skips runtime write-set collection entirely via manual instrumentation. The trade is PMDK's much higher engineering cost.
Q12What does this have to do with OS-managed memory tiering or CXL?▾
Same root cause, different symptom: a general-purpose kernel's mm subsystems (page tables, LRU generations, NUMA balancing) impose synchronization costs that only show up once the underlying hardware gets fast enough to expose them — µs-scale NVMe here, ns-scale CXL/PMEM tiering in your own work. VoliStorM's answer — give the latency-critical path its own page table instead of teaching the shared one to be faster for everyone — is structurally similar to giving a tiering hot-path its own promotion/demotion bookkeeping instead of routing every decision through the general page-reclaim path.

Every term in one place, the measured gains, then exactly what's the paper's and what's this guide's framing.

Core terms
VoliStorMThe paper's system: a crash-consistent I/O cache built from a general-purpose kernel plus a minimal latency-oriented kernel sharing the same cache.
G-kernelThe general-purpose kernel (Linux) — owns the shared I/O cache and the EPT.
L-kernelThe minimal, latency-oriented kernel VoliStorM adds — owns the GPT and collects write sets without touching G-kernel subsystems.
libvolimemThe component that transparently turns a legacy process into a lightweight KVM virtual machine (~500 LOC), Dune/Virtines-style.
Crash-consistency managerThe component that turns the shared I/O cache into a crash-consistent one via a redo log over MAP_PRIVATE mappings.
GPT / EPTGuest Page Table (GVA→GPA) and Extended Page Table (GPA→HPA) — the two independently-owned, simultaneously-active page tables under virtualization.
Failure-atomic section (FAS)A code region with all-or-nothing durability semantics, delimited by fas_start/fas_end (or msync as shorthand).
DOW / DCDetect-On-Write (page-fault-triggered) vs. Dirty-Collection (page-table-walk-triggered) write-set collection strategies.
Supporting terms
LINEARIZABLE / BUFFEREDDurable-linearizable mode persists before fas_end returns; buffered mode guarantees eventual, all-or-nothing consistency with a bounded delay (default 10 ms).
C / L / U phasesCollect, Log, Update — VoliStorM's redo-log pipeline stages; naming like CL-U marks which phases share a thread vs. run in parallel.
MAP_PRIVATE trickMapping the crash-consistent file copy-on-write so Linux never writes it back on its own, avoiding the semantic gap.
Memory-release optimizationOptional madvise(MADV_DONTNEED) reclamation of clean, logged private pages to avoid swapping already-persisted data.
MGLRU / AutoNUMA / KSMLinux mm subsystems (multi-generational LRU, NUMA balancing, memory de-duplication) that must synchronize with every dirty page in the general-purpose path.
YCSB workloads A/B/CWrite-heavy (50/50), read-heavy (95/5), and read-only access patterns from the Yahoo! Cloud Serving Benchmark.
