When the worker crashes, let the memory keep living

A GPU job dies, the OS reclaims its memory, a new process reloads everything from a checkpoint. But if the GPU never actually broke, why throw the data away at all? This is the plain-English story of Anchor.

📄 "Anchor: Mitigating GPU Shallow Disruptions with Decoupled Memory" · Ma, Gao, et al. 🎓 CUDA/IPC basics covered inline ⏱ ~25 min read
⚓

Decouple memory OWNERSHIP from the failure-prone worker process — a daemon anchors the data on the GPU, so a crash reclaims the PROCESS, never the data.

Before you begin

Quick glossary, then eight ideas the paper assumes

You already know OS memory management cold — the primers below skip that and focus on where CUDA's process model and ML-serving internals diverge from it.

Quick glossary — acronyms up front

IPC memory — CUDA/HIP mechanism to share a GPU allocation's physical pages across process contexts (cudaIpcGetMemHandle / OpenMemHandle).
KV cache — the stored key/value attention tensors from previously processed tokens in LLM inference.
PagedAttention — vLLM's paged KV-cache allocator; writes are append-only per slot.
ZeRO-3 — DeepSpeed's optimizer-state sharding scheme; updates proceed in fixed-size chunks.
CoW — copy-on-write; here, backing up a memory region before a kernel overwrites it.
BFS access path — a Python object-graph traversal used as a stable cross-restart tensor identifier.
MPS — NVIDIA Multi-Process Service; multiplexes GPU clients through one server process.
SDC — silent data corruption; a fault class explicitly out of this paper's scope.
anchored/surviving GPU memory shallow disruption (worker crash) Anchor's machinery (daemon/rebinder) checkpoint baseline / destructive failure
1CUDA contexts and fate-sharing▾

A CUDA context is the GPU-side analog of a process's page table: it owns every allocation the process makes. When the process dies, the context is torn down and the driver reclaims all of it — there's no "orphan mapping" survival path like a mmap'd file can have on the CPU side.

Now you're ready: the paper's whole problem is that GPU memory fate-shares with the process, unlike page-cache-backed CPU memory, which can outlive a process via the file it's backed by.
2The GPU IPC mechanism — reference counting + page-table remap▾

cudaIpcGetMemHandle exports a handle to an allocation; another context calling OpenMemHandle inserts the same physical pages into its own GPU page table. The driver reference-counts the region — exit of one sharer only decrements the count, and access afterward is served by ordinary MMU/TLB hardware, at zero extra runtime cost.

Now you're ready: this is the single hardware feature Anchor exploits — it's structurally the same trick as a shared, refcounted mapping in a CXL memory pool, just at the GPU page-table layer.
3What a "shallow disruption" is▾

Not every failure is equal. A shallow disruption — a Python exception, an NCCL timeout, a user hitting Ctrl-C to tweak code — kills the worker process but leaves the GPU device, driver, and OS kernel untouched. A destructive failure (ECC error, driver crash, node loss) takes the hardware itself offline and needs migration.

Now you're ready: the paper's traces show shallow disruptions are 65.8–98.8% of interruptions — the common case existing recovery treats as if it were the rare, destructive one.
4Checkpoint/restart, and why it's the wrong tool here▾

Standard recovery: periodically copy state off-GPU (checkpoint), and on failure, restart and copy it back (reload). This is unavoidable when hardware is actually gone. But for a shallow disruption the data never left the GPU — checkpointing pays a round-trip cost purely because the OS's process model forces it.

Now you're ready: Anchor's target is exactly this wasted round trip — same GPU, same data, only the owning process changed.
5PagedAttention and the KV cache▾

An LLM inference engine caches the key/value tensors of every token it has already processed, organized into fixed-size pages (blocks) — literally paged virtual memory applied to attention state. New tokens only ever append into fresh slots; existing slots are never mutated in place.

Now you're ready: this "append-only" property is what lets Anchor guarantee inference consistency almost for free (§4.3.3) — no copy-on-write needed.
6ZeRO-3 sharded optimizer updates▾

DeepSpeed's ZeRO-3 shards model weights and optimizer state across GPUs. Each rank updates its shard through a fixed sequence of chunks (grouped by sub_group_size, default ~10⁹ elements), gated behind a synchronization point — the gradient-finalization boundary — after which gradients are frozen for the rest of that step.

Now you're ready: "frozen gradients after finalization" is the invariant Anchor's training protocol exploits as a free redo log (§4.3.2).
7Python's object graph and access paths▾

Every live Python object is reachable from some root variable via a chain of attribute/index accesses (e.g. engine.kv_cache['layer_0']). That chain is the object's access path. Because frameworks build tensors dynamically at runtime rather than declaring them statically, there's no compile-time name to hang an identity on — the access path has to be computed by walking the live graph.

Now you're ready: Anchor's rebinder uses exactly this path, computed by BFS, as a stable cross-restart identifier (§4.2).
8Fault domains and daemon processes▾

A "fault domain" is the set of things one failure takes down with it. Running user CPU/GPU logic inside a shared server (as NVIDIA MPS does for multiplexed clients) means one client's fatal fault can force every co-resident client to exit too — they share a fault domain.

Now you're ready: Anchor's daemon deliberately executes no user kernels, so it has a much narrower fault domain than the worker it's minding — that asymmetry is what makes it trustworthy to hold the memory.
The whole story in one place

Anchor in a nutshell

The problem, the mechanism that fixes it, and the two engineering hurdles it had to clear.

Large GPU clusters running LLM jobs fail constantly, but failure traces from Alibaba, ByteDance, and Shanghai AI Lab show 65.8–98.8% of interruptions are shallow disruptions: the worker process crashes while GPU hardware and the OS kernel stay intact. Existing recovery is failure-agnostic — it checkpoints and reloads state as if every failure were destructive, even though the data never actually left the GPU. Restarting Qwen3-235B inference this way costs 143.78 s.

Anchor's fix: decouple memory ownership from the worker. A lightweight daemon process — one per GPU, running no user kernels — allocates GPU memory on the worker's behalf and hands it access via the GPU's native IPC mechanism. Because IPC memory is reference-counted, a worker crash only drops a reference; the daemon still owns the pages. A restarted worker reconnects to the same daemon and remaps the same physical memory — with zero overhead on the normal execution path, since access is served directly by the GPU's page-table hardware.

Two problems remain before this works on real ML systems. Identity resolution: the daemon only sees raw memory objects, but frameworks operate on dynamically-created tensors — Anchor resolves each tensor's Python access path via BFS traversal to get a stable cross-restart name. Consistency: a worker can crash mid-write, so Anchor pairs a general copy-on-write fallback with cheap, semantics-aware protocols — a chunk-level undo/redo log for training, and a metadata-only commit point for inference's append-only KV cache.

The payoff: recovery time drops 60.7% on average for inference (27.85 s for Qwen3-235B, a 5.16× speedup) and 26.6% for training, at a steady-state cost of only ~5% GPU memory / ~2.6% step time for training and ~0.45% memory / ~2% throughput for inference.

🍯 Key takeaways

  • Most GPU-job failures are shallow — worker dies, GPU/driver/kernel survive — not destructive.
  • Checkpointing is failure-agnostic: it pays a full save+reload even when data never left the GPU.
  • GPU IPC's reference counting + page-table remap let a daemon outlive the worker and hand memory back for free.
  • Access-path identity resolution re-binds dynamically-created tensors to daemon-held objects after restart.
  • Semantics-aware consistency (finalized-gradient redo log; append-only KV cache) beats generic CoW's memory cost.
  • Result: 60.7% faster inference recovery, 26.6% faster training recovery, <5% steady-state overhead.
Five everyday pictures

How to think about Anchor

Each stands alone. Every card ends with an honest note on where it breaks down.

The core idea

A landlord, not the tenant, owns the apartment

A tenant (the worker) rents furnished rooms from a landlord (the daemon). If the tenant moves out unexpectedly, the furniture stays — the landlord still owns it, and the next tenant moves right in without re-buying a couch. GPU memory under Anchor works the same way: the daemon holds the lease.

Where it breaks: a landlord can inspect and repair furniture; Anchor's daemon deliberately does not touch the data's contents — it only manages the lease (allocation/IPC), never runs computation on it.
Identity resolution

A house number, not the order you moved in

Matching tensors by allocation order is like identifying houses by "the third one built" — renumber the street (add a buffer, remove a layer) and every later house is misidentified. An access path is the house's actual street address (kv_cache['layer_0']): stable no matter what gets built around it.

Where it breaks: if the street address stays the same but the house behind it is rebuilt differently (same tensor name, changed semantics, e.g. a KV-cache layout swap), the address alone can't detect that — Anchor documents this exact gap (§6.4, case h).
Consistency

A ledger, not a photograph

A general CoW backup is like photographing the entire warehouse before every shipment — safe, but expensive to keep doing at scale. Anchor's training and inference protocols instead keep a small ledger: only the one in-progress entry needs an undo note, because everything already "committed" (finalized gradients; committed KV metadata) is trusted as-is.

Where it breaks: the ledger trick only works because these systems have a clean commit boundary (gradient finalization; append-only KV writes). A framework that mutates state in place with no such boundary (e.g. fused optimizer updates, recurrent linear-attention state) needs the full CoW fallback.
Enforcement · append-only KV

A guestbook, not an eraser

PagedAttention's KV cache is written like a guestbook: each new visitor writes on a fresh line, nobody erases or edits an old one. So if the pen slips mid-signature (a crash), the fix is simple — just have that same visitor sign again; nothing else on the page needs touching.

Where it breaks: a guestbook page, once dirty, can't be un-dirtied without erasing — Anchor doesn't erase, it just overwrites the slot on re-execution, which is safe here only because nothing downstream depends on the old bytes before the retry.
Fault domains

A shared kitchen vs a separate pantry

NVIDIA MPS is like several cooks sharing one stove (one server process): if one cook starts a fire, everyone's dish is ruined. Anchor's daemon is a separate pantry that no cook ever enters to prepare food — it only stocks and hands out ingredients, so a kitchen fire (worker crash) never touches the pantry.

Where it breaks: the pantry isn't fireproof either — if the daemon itself dies (e.g. host OS fault), Anchor has nothing to fall back on but the ordinary checkpoint path.
The full explanation

How it actually works

Section by section, with the paper's mechanisms as diagrams.

1 · Anchoring a single tensor

Instead of the worker allocating its own GPU memory, the daemon allocates it and grants the worker access via IPC. The worker computes on the tensor exactly as if it owned it — zero overhead, because the IPC mapping is resolved once, in the page table, not on every access. When the worker exits, the daemon's reference keeps the pages alive; a restarted worker reconnects and remaps the same physical memory.

2 · Naming by access path, with aliases and deferral

Allocation order breaks when code changes; source-line naming breaks under refactors and loops; PyTorch's state_dict only sees registered nn.Parameters, missing raw structures like a KV cache dict. So Anchor names each object by its access path — the chain of attribute/index accesses from a root variable — computed via BFS from the call stack's live frames, expanding same-level nodes in lexicographic order, with a visited set to break aliasing cycles.

💡
Why BFS, and why lexicographic order? Determinism. The same object graph must always assign the same path to the same object, run after run, regardless of dict-iteration or GC quirks — lexicographic tie-breaking makes the traversal reproducible.

3 · Log-based training consistency

After the gradient-finalization boundary, gradients are frozen for the rest of the step, so they can serve as a free redo log. Each rank keeps only a single undo buffer for the chunk currently being written, plus a persistent cursor marking the last committed chunk.

# ApplyChunk(i) — per rank, chunk[], grad[], undo_buf, cursor survive in the daemon
undo_buf ← Copy(chunk[i])
undo_chunk ← i              # publish complete undo
Optimizer.Apply(chunk[i], grad[i])
cursor ← i + 1               # commit

# Recovery
if cursor < N:
    if undo_chunk == cursor:
        chunk[cursor] ← Copy(undo_buf)   // rollback the in-progress chunk
    for j = cursor to N-1:
        ApplyChunk(j)                     // redo from finalized gradients
🍯
Why this beats full CoW: the undo buffer is one recovery chunk (bounded by sub_group_size, default 10⁹ elements) — not a copy of the whole model. The redo log costs nothing extra: it's the gradient buffers the framework already keeps until the step finishes.

4 · Blind-write inference consistency

Under PagedAttention, KV writes are append-only — the engine writes new tokens' keys/values into fresh slots and never depends on a slot's old value. So Anchor only needs to persist small CPU-side metadata (block table mappings, sequence cursor) at each commit point. On recovery, it rolls the page-table view back to the last committed metadata and re-executes the interrupted forward pass — any partially-written slot is simply overwritten with correct data, no cleanup required.

⚠
Assumption this relies on: the target framework must never read a KV slot before writing it (true for PagedAttention). Frameworks with in-place recurrent state (e.g. linear attention) violate this and need the general CoW path instead.

5 · The daemon's narrow failure surface

The daemon runs no user CPU logic or GPU kernels — only allocation and IPC bookkeeping — so it is far less likely to crash than the worker it serves. Anchor's coverage is explicitly bounded: it falls back to the application's ordinary checkpoint mechanism whenever a failure is destructive, the daemon itself is dead, or the failure can't be confidently classified as shallow. Silent data corruption is out of scope entirely.

Follow the numbers

Worked examples

Four small calculations straight from the paper's tables.

① The Qwen3-235B headline number

Table 1 / §6.2: KV-memory recovery takes 143.78 s; Anchor takes 27.85 s. Quantify the win.

  1. Absolute drop: 143.78 − 27.85 = 115.93 s saved per shallow disruption.
  2. Percentage reduction: 115.93 ÷ 143.78 ≈ 80.6% for this specific model — steeper than the 60.7% average across all four inference models, because recovery cost grows with model scale and Anchor's win grows with it too.
  3. Speedup multiple: 143.78 ÷ 27.85 ≈ 5.16× — matches the paper's stated figure exactly.
💡
The bigger the model, the more state a checkpoint scheme must move — and the more Anchor's "just remap it" trick is worth.

② Chunk copy vs full checkpoint (Table 2)

For Llama3.2-3B: DeepSpeed native save = 66.20 s; Anchor's chunk copy = 0.07 s.

  1. Ratio: 66.20 ÷ 0.07 ≈ 946× less blocking time on the normal path.
  2. Caveat (the paper flags this explicitly): these aren't equivalent operations — DeepSpeed materializes the entire model+optimizer state; Anchor only backs up one in-progress chunk. The 946× isn't a "same task, faster" speedup; it's evidence that chunk-granularity protection is cheap enough to run on every optimizer step, which full checkpointing never could be.

③ Sizing the state Anchor avoids re-loading

§2.2: mixed-precision Adam training costs 16–20 bytes per parameter (weights+gradients+optimizer state combined). Qwen2.5-14B has ~14 billion parameters.

  1. Lower bound: 14×10⁹ × 16 B ≈ 224 GB of state.
  2. Upper bound: 14×10⁹ × 20 B ≈ 280 GB of state.
  3. Anchor's steady-state add-on: §6.5 measures only +4.9% GPU memory for this model class — i.e. a few GB of undo-buffer overhead against a 224–280 GB baseline, not a second full copy.
📎
For readers used to reasoning in tiering terms: this is the same "hot state is huge, but the delta you must protect per step is tiny" argument that motivates fine-grained dirty tracking over full-page copy-on-write in page-migration systems.

④ Rebinding correctness (Table 3)

Across 8 program-change scenarios: allocation-order matching gets 2/8 correct; access-path matching (Anchor) gets 6/8 correct outright (2 more are safely rejected rather than silently wrong).

  1. Naive scheme accuracy: 2/8 = 25%.
  2. Anchor's accuracy: 6/8 = 75% correct, plus 1/8 safely rejected (metadata conflict) — only 1/8 (case h, a silent layout change) is a genuine blind spot for both schemes.
  3. Net gain: 6/8 − 2/8 = 4 of 8 cases flipped from wrong to right just by switching identifiers, with zero change to the underlying IPC mechanism.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A node loses ECC-uncorrectable errors on one GPU. Should Anchor's fast path handle this, or should it fall back to checkpointing?
Show answer
Fall back. This is a destructive failure — the hardware itself is compromised, so the GPU memory Anchor would try to reattach to may no longer be trustworthy or even present. Anchor's design explicitly falls back to the application checkpoint in exactly this case.Misconception: that Anchor replaces checkpointing entirely. It only replaces it for the common shallow-disruption case; destructive failures still need the full mechanism.
Problem 2 · medium
Why does a worker crash only decrement the IPC reference count instead of freeing the memory immediately?
Show answer
Because IPC memory can be shared by multiple GPU contexts simultaneously, the driver tracks how many contexts still hold a live mapping. The daemon's own OpenMemHandle call counts as one holder that never exits, so the count never reaches zero when only the worker dies — the memory stays resident until the daemon itself releases it.Misconception: that "the process died" and "the memory is freed" are the same event on a GPU. They're only the same event if nobody else holds a reference — which is exactly the property Anchor engineers around.
Problem 3 · medium
A developer adds a new LoRA adapter's weights right after the base model in their init code, without deleting or reordering anything else. Would allocation-order matching succeed here? Would access-path matching?
Show answer
Both succeed (Table 3, case a). Since the new tensor is appended without disturbing the order or names of prior allocations, sequence-based matching still lines up correctly, and the access paths of existing objects don't change either. This is the one case in the table where the naive scheme isn't wrong.Misconception: that allocation-order matching is always broken. It happens to work when changes are purely additive at the end — it breaks under insertions, removals, or reordering anywhere earlier in the sequence.
Problem 4 · hard
Why can't Anchor's rebinder detect case (h) — a silent KV-cache layout change (NHD→HND) via an attention-backend swap?
Show answer
The access path identifies which object a tensor is, and the metadata check (shape, dtype) confirms it's the right size and type — but neither says anything about how the bytes inside are laid out semantically. A layout swap changes only the internal interpretation of unchanged bytes under an unchanged name and unchanged shape/dtype, so it's invisible to both identity resolution and the metadata-conflict check.Misconception: that matching identifier + matching metadata guarantees semantic compatibility. It only guarantees "same slot, same size" — semantic layout is a level below what either check inspects.
Problem 5 · medium
Why does the inference consistency protocol need no GPU-side backup buffer at all, while the training protocol needs one undo chunk?
Show answer
KV-cache writes are append-only and blind-write: a crash mid-write leaves a slot that gets unconditionally overwritten by the retried forward pass, so there's nothing to "undo" — the correct data simply arrives on redo. Optimizer chunk updates are read-modify-write: the update depends on the chunk's previous value, so if a crash catches it mid-update, that previous value must be explicitly restored before redoing, requiring an undo copy.Misconception: that any in-place write needs an undo buffer. Only read-modify-write updates do; blind (unconditional) overwrites don't, because redo alone reaches the correct state.
Problem 6 · hard
NVIDIA MPS also lets multiple processes concurrently use a GPU. Why doesn't MPS already solve the shallow-disruption problem?
Show answer
MPS multiplexes GPU execution across clients through a shared server for throughput, but the clients sharing a GPU also share MPS's fault domain — a fatal fault in one client can force every co-resident client on that GPU to exit. MPS was never designed to let one client's memory outlive that client's own crash; it solves concurrent access, not memory persistence across a process's death. Anchor's daemon, by contrast, executes no user kernels at all, so it isn't in the crashing client's fault domain in the first place.Misconception: that any cross-process GPU-sharing mechanism implies memory survives a crash. Sharing access and surviving a fault are different guarantees — MPS gives you the first, IPC reference counting (as Anchor uses it) gives you the second.
Quick answers

Frequently asked questions

Q1Does Anchor replace checkpointing?▾
No — it complements it. Anchor handles the common case (shallow disruptions, 65.8–98.8% of interruptions) fast, and falls back to the existing checkpoint mechanism for destructive failures, a dead daemon, or failures it can't confidently classify as shallow.
Q2Does the daemon add overhead during normal execution?▾
Very little: after the initial IPC mapping is established, worker accesses are served directly by GPU hardware (MMU/TLB) with no daemon involvement. Measured steady-state overhead is ~4.9% GPU memory / ~2.6% step time for training and ~0.45% memory / ~2.0% throughput for inference.
Q3What happens if the daemon itself crashes?▾
Anchor treats a dead daemon as one of its explicit fallback triggers — recovery reverts to the application's ordinary checkpoint. The daemon's narrow job (allocation + IPC bookkeeping, no user kernels) is meant to make this rare, not impossible.
Q4Why not just use a generic copy-on-write scheme everywhere?▾
It's correct but expensive: general CoW (à la PhoenixOS) backs up the entire region a kernel is about to touch, which for weights or optimizer state can mean duplicating tens of gigabytes. The application-aware protocols get the same guarantee for one chunk's worth of memory (training) or CPU-side metadata only (inference).
Q5Does this work outside CUDA/NVIDIA?▾
Yes — §6.6 reproduces the training experiments on an AMD MI100 via ROCm/HIP IPC, with recovery latencies of 17.3–19.0 s vs 19.9–28.7 s for baselines, showing the mechanism isn't tied to CUDA specifically.
Q6How much code does integrating Anchor take?▾
About 200–300 lines of modification per ML framework (DeepSpeed, vLLM) — mainly wrapping initialization code in a managed_scope and adapting the optimizer step to the consistency protocol.
Q7What failure types are explicitly out of scope?▾
Silent data corruption (SDC) and incorrect writes from buggy kernels — these don't surface through worker exits or health signals, so Anchor has no trigger to act on. The paper points to specialized GPU diagnosis and application-level validation as the right tools there.
Q8Can identical tensor names ever be silently wrong after rebinding?▾
Yes — if code changes the semantic meaning of a tensor without changing its access path, name, shape, or dtype (e.g. swapping the KV-cache memory layout via a different attention backend), Anchor has no signal to detect it (Table 3, case h). This is a documented, fundamental limitation, not a bug.
