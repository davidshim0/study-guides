Give a few GPUs the real job, and let a whole cluster play itself

A 2,048-GPU training run, faithfully reproduced on a couple of machines — because most of those GPUs don't need to be real, they just need to behave real.

Before you begin

Quick glossary + primers

Acronyms first, then eight collapsible primers. Skip anything already familiar.

RankOne per-GPU worker process in a distributed job; ranks together form the training job.
DP / TP / PP / EPData / Tensor / Pipeline / Expert Parallel — the four ways a training job splits work across ranks.
VPPVirtual Pipeline Parallel — extra interleaving stages within a PP schedule.
NCCLNVIDIA's Collective Communication Library — implements all-reduce, all-to-all, send/recv over GPUs.
MoEMixture-of-Experts — a model where each token is routed to a subset of "expert" sub-networks.
MFUModel FLOPs Utilization — fraction of peak GPU compute actually used; the efficiency scorecard.
OOMOut-Of-Memory — a run crashes because GPU memory is exhausted.
RDMA / PCIe / HBMThe three data paths that matter: network fabric, GPU↔host bus, and GPU's own fast memory.
CRIU / cuda-checkpointTools to snapshot and restore a process's (or GPU context's) full state.
Sandbox / assistant GPUCrystalLLM's two roles: sandbox runs real ranks; assistant hosts replayed virtual ranks.
1Why LLM training needs thousands of GPUs▾

A model's weights, activations, and optimizer state are split across ranks using DP/TP/PP/EP so they fit in aggregate GPU memory and finish in reasonable time. More GPUs let you train bigger models faster — but every added dimension of parallelism also reshapes communication and memory layout.

Now you're ready: CrystalLLM's whole problem is that reproducing a specific parallelism configuration's behavior seems to require that many GPUs.
2NCCL collectives: all-reduce, all-to-all, send/recv▾

Ranks exchange gradients (all-reduce), routed tokens (all-to-all, for MoE), and activations between pipeline stages (send/recv). NCCL implements these efficiently using ring or tree topologies, where data hops rank-to-rank.

Now you're ready: CrystalLLM must replay these exact traffic patterns, or a "real" rank would stall waiting for a partner that never sends.
3Why downscaling and simulation both fall short▾

Downscaling a job (fewer GPUs) forces you to shrink DP/TP/PP/EP too, which changes memory sharding, batch scheduling, and bottlenecks — the exact things you wanted to study. Simulators avoid that by modeling behavior analytically or from traces, but the model itself must be built and kept current as kernels, frameworks, and hardware change.

Now you're ready: CrystalLLM's angle is to keep the real code and real GPUs, and shrink only the quantity of physical hardware.
4Execution traces / graphs▾

A trace records what a program did: which operations ran, in what order, and for how long. A graph adds dependency edges between operations (this op waits on that one). Once captured, a graph can be replayed to reproduce timing without re-running the original computation.

Now you're ready: CrystalLLM's core artifact, CrystalTrace, is exactly this: a graph over computation and communication spans.
5GPU context switching & checkpointing▾

A GPU can only actively run one process's context at a time (practically speaking, for our purposes). To time-share it across many logical ranks, you must save one rank's full GPU state (its "context") and load another's — the same idea as OS process context switching, but for an 80GB GPU instead of a few KB of registers.

Now you're ready: CrystalLLM multiplexes hundreds of logical ranks onto a handful of physical GPUs exactly this way, using tools like cuda-checkpoint and CRIU.
6MoE routing and load imbalance▾

In an MoE layer, a gating function decides which experts each token visits. Real traffic is rarely perfectly balanced — some experts get more tokens than others — so different ranks end up holding different amounts of data after dispatch, and thus different peak memory.

Now you're ready: CrystalLLM has to reproduce this imbalance (not just the average case) to get memory predictions right — hence its "mock router."
7Why scale changes behavior, not just speed▾

At larger scale, the bottleneck itself can shift — e.g. from compute-bound to communication-bound or memory-capacity-bound — because the ratio of work-per-rank to communication-per-rank changes with the parallelism configuration.

Now you're ready: this is why a downscaled experiment can give a directionally wrong answer, not just a noisier one.
8Determinism and why it matters here▾

If a program, given the same configuration, always issues the same sequence of operations, then a graph captured once can be replayed safely — nothing about the recorded structure will surprise a later run.

Now you're ready: this is CrystalLLM's foundational assumption; it's also why RL-style workloads with data-dependent control flow are out of scope.
The whole story in one place

CrystalLLM in a nutshell

The dilemma, the two-phase fix, and why it works.

LLM engineers need to reproduce production-scale behavior constantly — to debug a stall, validate an optimization, or tune a configuration — but production GPUs are scarce and downscaled tests distort exactly the things that matter: parallelism structure, memory layout, communication patterns. Simulation avoids the hardware cost but pays it back in modeling effort that must be redone as the stack evolves.

CrystalLLM's insight: large-scale interaction structure doesn't require all ranks to run on physical GPUs simultaneously. A small set of sandbox ranks can run the unmodified real program, while the remaining thousands are virtual ranks that replay a pre-captured execution graph (CrystalTrace) — showing up exactly when and how the real ranks expect a communication partner to.

Getting that graph is the chicken-and-egg problem: capturing full-scale behavior seems to need full scale. CrystalLLM solves it with context switching — time-sharing a handful of GPUs across all logical ranks to record what happens and in what order — then a separate slice-by-slice timing pass, run with real hardware on rotating subsets of ranks, to recover accurate durations, stitched together with cross-slice calibration.

The payoff: across models from 235B to 1.01T parameters and scales up to 2,048 GPUs, CrystalLLM predicts iteration time within 0.58% average error (max 1.98%) and peak GPU memory within <0.01% error, while emulating clusters up to 8,192 GPUs using a small constant footprint of physical nodes.

🔶 Key takeaways

  • Scale is virtualized: only ranks you're watching need real GPUs; the rest are replayed.
  • CrystalTrace records only what replay needs — communication/computation spans and dependencies, GPU-side timing only — not full operator traces.
  • Phase 1 (offline): context-switched collection gets the graph's shape; slice-by-slice timing + calibration gets accurate durations.
  • Phase 2 (online): hybrid emulation runs sandbox ranks for real while virtual ranks replay timing and perform real communication.
  • Two tricks keep virtual ranks cheap: NCCL group reduction (only instantiate groups touching the sandbox) and neighbor-only pruning (only instantiate ranks adjacent on the ring/tree), with compensating math to preserve numerical correctness.
  • Result: 0.58% iteration-time error, <0.01% memory error, <1% of the physical GPUs required.
🧊
For your tiering work: the sandbox/assistant split mirrors a pattern you'll recognize from CXL/tiering research — treat the "hot," observed component as ground truth and virtualize the vast "cold" surrounding state cheaply (much like emulating a large NVM tier's aggregate behavior around a small instrumented DRAM slice), as long as a "timely data supply" assumption (here, PCIe prefetch bandwidth > NIC bandwidth) holds.
Five everyday pictures

How to think about CrystalLLM

Each stands alone. Every card ends with where it breaks.

The core idea

Lead actor and stunt doubles

A film only needs the lead actor (sandbox rank) to actually perform the close-up; the crowd of extras (virtual ranks) just needs to be in the right place, doing the right motion, on cue. CrystalLLM records the crowd's choreography once, then replays it around whichever actor is being filmed.

Where it breaks: if the "crowd" changes its behavior in response to the actor (data-dependent control flow), a fixed choreography can't follow — hence CrystalLLM needs deterministic execution.
Graph collection

One actor, three costumes, one stage

A tiny theater company plays a dozen roles by having one actor change costume and re-enter between scenes. The audience never sees all twelve at once, but the play's structure is fully captured. That's context switching: a few GPUs "wear" one logical rank's state, run until blocked, then swap.

Where it breaks: costume changes (checkpointing an 80GB context) take real time — minutes, not seconds — so the timing recorded this way is discarded and recovered separately.
Neighbor-only pruning

A bucket brigade needs only its neighbors

Passing water down a line, each person only interacts with the person to their left and right — not the whole line. Ring all-reduce is the same: a sandbox rank only ever exchanges data with its ring neighbors, so only they need to be real (or realistically replayed); everyone further away can be skipped, as long as the two neighbors compensate for the missing links.

Where it breaks: tree-based collectives have a different neighbor structure (parent/child, not left/right) — CrystalLLM handles this with separate root/leaf/intermediate compensation rules.
Slice timing + calibration

Splicing film reels shot on different days

You shoot scene A on Monday and scene B on Tuesday, each with correct local timing, but the two reels' clocks aren't synchronized to a single story clock. An editor uses continuity cues (a phone rings in scene A, is answered in scene B) to align them. CrystalLLM aligns slices the same way: a receive's timestamp is shifted to occur after the send it depends on.

Where it breaks: without this step, iteration time can be off by >10% — the raw per-slice timings alone are locally accurate but globally inconsistent.
DP symmetry

Sampling one identical twin

If a factory stamps out perfectly identical parts on N parallel lines, you only need to inspect one line to know all N. Data-parallel replicas produce structurally identical execution graphs, so CrystalLLM captures just one replica and reuses its graph everywhere — cutting collection time by exactly the DP factor.

Where it breaks: this assumes steady-state pretraining; a straggler or transient hardware fault on one replica is, by design, averaged away rather than captured.
The full explanation

How it actually works

Two phases: build a high-fidelity graph on a few GPUs, then replay it around the ranks you care about.

1 · CrystalTrace — the minimal graph for replay

For each rank, CrystalTrace records only what replay needs: computation/communication spans (id + GPU-measured duration), and two kinds of dependency edges — directional (A finishes before B starts) and synchronization (all participants must arrive before any proceeds, e.g. a collective). Timing is captured on the GPU side only: CPU stalls (data loading, kernel-launch queuing) still show up, as longer gaps between GPU events, without needing separate CPU instrumentation. This is far lighter than full operator-level profiling — the paper measured up to 20.04% iteration-time overhead from PyTorch Profiler on a 128-GPU job, overhead CrystalTrace avoids by not tracing anything replay doesn't use.

2 · Stage 1 — collecting the bare graph via context switching

A coordinator keeps a pool of logical ranks, only N of which are ever active on the N available GPUs. An active rank runs until it blocks on a communication point (e.g. waiting for all-reduce partners); the coordinator then checkpoints its state, swaps in a different rank — prioritizing whichever unblocks the most pending work — and resolves the collective on the CPU once every participant has arrived. Repeating this until all ranks finish one iteration yields the full graph's structure (what, and in what order) but not accurate timing, since context switching itself distorts duration.

💾
Cost of naive context switching: replaying a 128-GPU job this way needs up to ~10TB of host memory to hold swapped-out GPU contexts, and checkpointing a near-full 80GB context can take 2+ minutes. CrystalLLM's opt-out — letting advanced users inject known-good communication tensors directly — cut a 235B-model, 2,048-GPU graph collection from ~9 hours to ~64 minutes, then to ~1 minute once DP symmetry (§1 primer 8) is exploited.

3 · Stage 2 — timing fill and cross-slice calibration

To recover accurate durations, CrystalLLM partitions ranks into slices and runs each slice with real hardware: a subset executes for real on sandbox GPUs while the rest are replayed (using the bare graph) on assistant GPUs, giving locally-accurate timing for the real subset. Iterating slices round-robin (e.g. ranks 0–7, then 8–15, …) gives every rank an accurate measurement exactly once. Because each slice's clock starts independently, dependency edges (a receive must follow its matching send) are then used to shift timestamps into one globally consistent timeline — inter-slice calibration.

4 · Hybrid emulation — replay at full logical scale

With a calibrated graph in hand, emulation runs once: sandbox ranks execute the unmodified program; virtual ranks on assistant GPUs traverse the graph, waiting out computation-node durations and performing real communication at communication nodes. A prefetch pipeline stages the needed tensor data (recorded or user-injected) onto the assistant GPU ahead of time, relying on PCIe bandwidth (e.g. 64GB/s) exceeding the network bandwidth consuming it (e.g. 50GB/s/NIC) — the "timely data supply" assumption.

Two optimizations keep this cheap even at thousands of virtual ranks:

  • NCCL group reduction: instantiate only communicator groups that overlap the sandbox — for 2,000 virtual ranks, this cut active groups from 8,617 to 82.
  • Neighbor-only pruning: within a group, instantiate only ring/tree neighbors of the sandbox; a designated leader rank fakes barrier participation and topology exchange on behalf of everyone pruned.
🔶
Pruning introduces no non-determinism: the sandbox issues the same number and size of transmissions as the original collective, deterministically placed — repeated runs differ only by ordinary hardware jitter.
Follow the numbers

Worked examples

Four calculations straight from the paper's reported figures.

① NCCL group reduction at 2,000 virtual ranks

  1. Baseline (uninstantiated pruning): 8,617 active NCCL groups.
  2. CrystalLLM (only groups overlapping the sandbox): 82 active groups.
  3. Reduction factor: 8617 ÷ 82 ≈ 105× fewer groups.
  4. As a percentage cut: (8617−82)/8617 ≈ 99.0% of groups skipped entirely.
💡
This is what makes thousands of virtual ranks initializable in seconds instead of hours — most groups never touch the sandbox and are simply never created.

② Graph collection speedup for a 235B model, 2,048-GPU target

  1. Pure context switching (32 collection GPUs): ~9 hours = 540 minutes.
  2. With user-specified communication tensors: 64 rounds × ~1 minute = ~64 minutes.
  3. Exploiting DP symmetry (only one 32-rank model replica needs collecting): a single round, ~1 minute.
  4. Total speedup vs. naive context switching: 540 ÷ 1 = 540×.
💡
Two independent optimizations stack multiplicatively: skip re-execution (context-switch avoidance) and skip redundant replicas (DP symmetry).

③ Virtual rank initialization: 512 ranks (baseline) vs. 8,192 ranks (CrystalLLM)

  1. Baseline (standard NCCL) at 512 ranks: 756.0s init time, 103.7GB GPU memory, 544.5GB CPU memory — and it OOMs beyond this scale.
  2. CrystalLLM at 16× more ranks (8,192): 44.3s init time — 756.0 ÷ 44.3 ≈ 17× faster, despite the larger logical cluster.
  3. GPU memory per device: 5.4GB vs. baseline's 103.7GB at a fraction of the scale — 103.7 ÷ 5.4 ≈ 19× less memory, serving 16× more ranks.
  4. Net effect: CrystalLLM's footprint is constant in logical cluster size; the baseline's grows linearly until it can't run at all.

④ Iteration-time accuracy (Table 4, real vs. predicted)

  1. Baseline case: 5.62s measured vs. 5.70s predicted → error = (5.70−5.62)/5.62 ≈ +1.4%.
  2. Flash-Attention off: 7.74s measured vs. 7.70s predicted → error ≈ −0.5%.
  3. Offload-optimizer case: 11.98s vs. 11.61s → error ≈ −3.1% (largest of Table 4's cases, still within the paper's reported 1.98% max across the main Fig. 7 sweep for other configs).
  4. Peak memory across all Table 4 rows matches to the reported bytes — 0% observable error at this precision.
📎
These per-configuration errors bounce around the paper's headline 0.58% average — a reminder that the average masks some rows harder to predict than others (compute-light or interleaved-optimization cases).
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Does CrystalLLM run a smaller version of the training job?
Show answer
No. The logical job stays at full scale (same DP/TP/PP/EP, same batch size); only the number of physical GPUs shrinks. Sandbox ranks run the exact production code unmodified; everyone else is replayed.Misconception: confusing CrystalLLM with downscaling. Downscaling shrinks the job itself and distorts its behavior; CrystalLLM keeps the job's logical scale fixed.
Problem 2 · medium
Do virtual ranks perform real matrix multiplications and other GPU computation?
Show answer
No. Virtual ranks wait out each computation node's recorded duration (from the calibrated graph) rather than executing it, but they do perform real NCCL communication with sandbox ranks so the sandbox observes genuine network behavior.Misconception: assuming "hybrid emulation" means partial computation everywhere. Compute is skipped for virtual ranks; only its timing and the real communication it triggers are reproduced.
Problem 3 · medium
Why does CrystalLLM need a whole separate "timing fill" stage instead of just timing the context-switched collection directly?
Show answer
Context switching itself introduces overhead — checkpoint/restore delays, CPU-resolved collectives — that has nothing to do with the job's real performance. Stage 1 only needs to be structurally correct (what happens, in what order); Stage 2 re-runs slices with real hardware specifically to recover undistorted durations.Misconception: assuming any execution on real GPUs yields real timing. Timing is only trustworthy when nothing artificial (like a checkpoint pause) is on the critical path being measured.
Problem 4 · hard
A team wants to use CrystalLLM to study an RL post-training job where the reward model dynamically changes which experts get how much data each step. Is this a good fit?
Show answer
No — the paper explicitly excludes this. CrystalLLM assumes deterministic execution: the same configuration must always issue the same operation sequence, so a graph captured once can be replayed safely. If runtime data changes control flow or communication structure (as in some RL workloads), a fixed graph can't track it.Misconception: assuming any distributed training job qualifies. Fixed-graph replay requires the execution and communication structure to not depend on runtime values.
Problem 5 · medium
Why does pruning non-neighbor ranks in a ring all-reduce not corrupt the numerical result the sandbox sees?
Show answer
Because ring all-reduce's reduction stage only requires each rank's own assigned chunk to end up correct — the leftmost virtual neighbor pre-compensates (subtracting values that would have arrived from now-pruned ranks) so that by the time data reaches the sandbox, it already carries the fully-reduced value for the sandbox's chunk. Chunks the sandbox doesn't own can be arbitrary.Misconception: assuming every rank in a collective must be "really" present for correctness. Only the value at the boundary the sandbox observes has to be correct — everything upstream of that boundary can be synthesized.
Problem 6 · easy
If a training job runs on 512 GPUs with DP=16, how many GPUs' worth of graph does CrystalLLM actually need to collect (ignoring further sub-sampling)?
Show answer
512 ÷ 16 = 32 GPUs — one data-parallel replica. Because DP replicas are structurally identical, capturing one replica's graph and reusing it across all 16 replicas is sufficient (DP symmetry).Misconception: assuming every one of the 512 ranks must be individually captured. Only asymmetric dimensions (PP, TP, EP) need per-rank capture; DP is captured once and reused.
Problem 7 · hard
CrystalLLM claims it can localize a faulty (thermally-throttled) node in production. How, if it never runs the actual production-scale job during the check?
Show answer
It compares each candidate node's measured iteration time, as a sandbox running the real code against the recorded normal baseline graph, to every other candidate's. A node that's slower than the reproduced normal behavior (6.40s vs. a 5.70s median across other pairs, in the paper's incident) stands out as anomalous — the graph supplies the "expected normal," and each node pair is tested for real, one at a time, in ~20 minutes.Misconception: assuming CrystalLLM "simulates" the fault. It doesn't predict faults — it gives a fast, faithful normal baseline against which a real re-execution on suspect hardware can be compared.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the difference between CrystalLLM and a simulator?▾
A simulator models behavior (bandwidths, kernel durations, allocator logic) analytically or from prior profiles, without running the real program. CrystalLLM runs the actual, unmodified training code on real GPUs for the ranks of interest — it only replaces the quantity of physical hardware, not the artifact being measured.
Q2How can CrystalLLM capture large-scale behavior without large-scale hardware?▾
Two-stage split: context switching gets the graph's structure cheaply (timing discarded), and a separate slice-by-slice pass — run with real hardware on rotating rank subsets — recovers accurate timing, later stitched together via dependency-based calibration.
Q3Why is peak memory prediction so much more accurate (<0.01% error) than iteration time (0.58%)?▾
Memory allocation follows deterministically from tensor sizes, shapes, and lifetimes, all preserved exactly in the sandbox's real execution — there's no timing variance to average over. Iteration time additionally depends on cross-rank synchronization and replay fidelity, which carries small residual error.
Q4Does emulating more GPUs (say 8,192) take proportionally longer?▾
No — CrystalLLM scales assistant nodes proportionally with target scale (1:1 with sandbox), keeping wall-clock emulation time stable (under 80 minutes up to 8,192 GPUs) instead of growing linearly with pipeline depth.
Q5What happens to CPU-side bottlenecks (data loading, kernel launch overhead) in replay?▾
They aren't discarded — CrystalTrace records only GPU-side timestamps, so CPU stalls simply show up as longer gaps between recorded GPU events, and are replayed as-is without needing explicit CPU instrumentation.
Q6Can CrystalLLM predict convergence or numerical drift over many iterations?▾
No. The paper explicitly scopes this out — genuine multi-iteration compute, joint congestion from all ranks' real traffic, and transient-straggler distributions require full-scale execution. CrystalLLM targets one or a few iterations of performance/memory behavior.
Q7How does CrystalLLM compare against Phantora and SimAI?▾
Phantora runs the program against mocked CUDA/NCCL backends and shows up to 64% error as GPU-side pressure drops (it can't model CPU-Python contention). SimAI averages 77.2% error on the paper's MoE+PP workloads because its workload-file format omits PP bubbles and MoE-specific operation costs. CrystalLLM keeps real execution throughout, avoiding both gaps.
Q8What training stacks does CrystalLLM support today?▾
PyTorch programs communicating via NCCL — validated on Megatron-LM; DeepSpeed and FSDP are named as in-scope stacks. Fused compute-communication kernels aren't yet supported.
Q9Why must the sandbox be provisioned at "node granularity"?▾
Tightly-coupled intra-node parallelism (TP/EP over NVLink) communicates at microsecond, per-layer cadence — fine enough that a virtual peer risks perceptibly perturbing timing. Keeping a full tightly-coupled group real avoids that, while inter-node traffic can still be safely replayed by an assistant node.
Q10What's left for future work?▾
The paper mentions extending to broader training frameworks and more asymmetric workloads; fused kernels and non-deterministic (e.g. some RL) workloads remain explicitly out of scope for now.

Related systems (from the paper's related work)

SimAI / vTrain / ASTRA-sim medium

profiling-driven & analytical simulators

Replay measured kernel timings inside a model rather than executing real code — cheap per-configuration but limited by model fidelity (§7.4 comparison).

Phantora medium

NSDI'26

Runs the unmodified program against mocked CUDA/NCCL backends; the closest prior system in spirit, but execution stops being real at the backend.

CrystalNet hard

Liu et al., SOSP'17

Boots real switch firmware for a changed scope and mocks the rest — the network-emulation ancestor of CrystalLLM's neighbor-pruning idea.

FireSim / SimBricks hard

ISCA'18 / SIGCOMM'22

Push boundary emulation to cycle-accurate hardware simulation; each mocked device acts from a static snapshot rather than a full-job dependency graph.

MimicNet hard

Zhang et al., SIGCOMM'21

Simulates one cluster fully and approximates the rest with a learned model; CrystalLLM replaces that approximation with real execution instead.

Megatron-LM easy

Shoeybi et al., 2019 / Narayanan et al., SC'21

The pretraining framework CrystalLLM is evaluated against (DP/TP/PP/EP parallelism); understanding it helps interpret the S.A–S.D strategy table.
