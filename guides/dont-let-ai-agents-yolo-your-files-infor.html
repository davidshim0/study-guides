SOSP 2026 · A Field Guide

Don't let agents guess what a command will really do

Coding agents wipe drives, leak SSH keys, and apologize afterward — not because they're malicious, but because neither they nor you can see what a shell command actually touches until it's too late. This is the plain-English tour of the study that proves it, and YoloFS, the filesystem built to fix it.

📄 "Don't Let AI Agents YOLO Your Files" · Zhong, Liao, Liu, Zheng, Arpaci-Dusseau² 🎓 OS/filesystem basics assumed — primers are short by design ⏱ ~25 min read
🗂️

Don't ask the agent to describe what it will do. Ask the filesystem to show what it did — and let anyone undo it before it's final.

Before you begin

Quick glossary, then nine primers

The acronyms first, in one place. Then short, collapsible primers on the AI-agent-specific concepts the paper assumes — the filesystem mechanics (COW, unions, stackable FS) are kept brief since you already know them; the agent-harness concepts are given more room since they're the paper's actual novelty.

1LLMs, agents, and the agent loop▾

An LLM takes a prompt and generates text — including structured tool calls (e.g. "run this shell command," "write this file"). An agent harness executes those calls and feeds the results back to the model, which can then issue another call. This cycle, the agent loop, can repeat for hundreds of iterations before a task finishes or the user stops it.

Now you're ready: every filesystem effect in this paper originates from one of these tool calls — either a built-in tool the harness implements, or an arbitrary shell command it merely passes through.
2Local agents and why the filesystem matters▾

Local agents run tool calls directly on the user's machine, with the user's own privileges — no remote sandbox mediating them by default. Coding agents are the dominant case, and the filesystem is central to their work: it stores the code, data, and configuration every task touches.

Now you're ready: "agent filesystem misuse" isn't a peripheral risk — it's the direct consequence of giving an autonomous, imperfect actor your own file permissions.
3Built-in tools vs. the shell tool▾

Harnesses provide two kinds of file access: built-in tools (Read, Write, Edit, Glob) that the harness itself implements and can therefore mediate; and a shell tool that runs arbitrary commands (rm, git, make, cargo build) the harness does not implement and cannot easily inspect.

Now you're ready: any policy applied only to built-in tools has a hole — the shell — and agents (and attackers) routinely fall through it.
4Three existing guardrails, three failure modes▾

Policy on built-in tools (allow/deny/ask by path) — doesn't apply to the shell. Filters on shell command strings — match syntax, not effects, so rm vs. os.remove vs. a redirect all look different but do the same thing. Sandboxes restrict which files a command can reach — but block legitimate work, so harnesses offer an unsandboxed fallback that quietly erodes the protection.

Now you're ready: these three are exactly the guardrails (policy / filter / sandbox) whose failure modes the paper's cause taxonomy documents in Section 3.4.
5"YOLO mode" and approval fatigue▾

Frequent approval prompts stall an agent and exhaust the user — a documented phenomenon (decision fatigue / approval fatigue). Faced with hundreds of prompts per session, users often just disable them entirely: "YOLO mode." This creates the paper's central dilemma — prompt too much and you lose autonomy; prompt too little and you lose safety.

Now you're ready: the paper's whole design goal is escaping this dilemma, not by prompting less information, but by prompting for fewer, better-timed decisions.
6Prompt injection▾

An agent reads untrusted content as part of its work — a web page, a GitHub issue, a dependency's build script. If that content contains text crafted to look like instructions, the model may follow the attacker's instructions instead of (or in addition to) the user's. This is prompt injection, and it's how several of the paper's worst reports (SSH key exfiltration, persistent backdoors) begin.

Now you're ready: injected instructions can't be filtered out of the model's behavior reliably — which is exactly why the paper argues control must live in the filesystem, not the prompt.
7COW and versioning filesystems, briefly▾

You already know copy-on-write and snapshot-capable filesystems (ZFS, Btrfs). The paper's point isn't that COW is hard — it's that existing versioning is the wrong granularity for agents: per-file versions don't group by session, subtree snapshots are fixed in advance, and whole-filesystem rollback discards unrelated changes. YoloFS needs snapshots scoped to exactly one agent session.

Now you're ready: YoloFS's contribution here isn't a new COW mechanism — it's applying generation-based COW at session/command granularity via a journal, not a subtree.
8Union filesystems, briefly▾

OverlayFS-style union filesystems stage writes in an upper layer over a read-only lower layer. The catch you'll recall: renaming a file from the lower layer requires copying its full contents up first ("copy-up"), and stacking a new layer per snapshot makes every lookup traverse the whole stack — plus the kernel caps how many layers a mount can have.

Now you're ready: this is precisely the rename-amplification and snapshot-scaling problem YoloFS's flat file store + override tree design is built to avoid.
9Stackable kernel filesystems, briefly▾

YoloFS is a native, in-kernel stackable filesystem (2.7 kLoC C) that interposes on every VFS operation between the agent and a backing (base) filesystem — not a FUSE layer. The CLI runs agent commands inside a mount namespace with the YoloFS mount as root (via pivot_root), so the agent has no path back to the unmediated base filesystem.

Now you're ready: this is the completeness requirement in practice — mediation isn't optional or bypassable by the agent, by construction of the mount namespace.
The whole story in one place

Agent-native filesystems, in a nutshell

The problem, the shift that fixes it, and how YoloFS's three mechanisms connect to it.

The authors analyze 290 public reports of AI coding agents misusing their filesystem access — drives wiped, home directories erased, SSH keys silently exfiltrated. Across every report, they find two fundamental gaps. The information gap: neither the user nor the agent itself can reliably tell what a command's real filesystem effects will be — a build script can read an SSH key and rewrite a shell config while looking, to a permission prompt, like an ordinary cargo build. The control gap: existing mechanisms can't reliably stop harm before it happens (models ignore instructions; filters are bypassed with alternative commands) or help anyone recover after (history lives in a .git the agent itself can delete).

Their fix is to shift information and control from the agent to the filesystem, which can observe and mediate every effect directly rather than trusting the agent's self-report. They define three primitives an agent-native filesystem should provide: introspect effects (what did this command actually touch?), undo mutations (let the agent or user reverse it), and gate accesses (block the handful of effects, like reading a secret, that can never be undone).

YoloFS realizes all three with three mechanisms. Staging holds every mutation as an override — tracked in an in-memory override tree, with the actual staged content, journal, and config already persisted on the base filesystem — so review happens before the user's original files are touched, not before anything reaches disk. Snapshots and travel let the agent inspect each command's effects and jump back to an earlier state to self-correct, without losing the abandoned history. Progressive permission lets the user decide unforeseen accesses on the spot and optionally turn that decision into a standing rule — no complete policy has to exist upfront.

The payoff: on 11 tasks engineered with hidden destructive side effects, YoloFS lets Claude Code self-correct in 8 and keeps the remaining 3 staged for user review — 100% of harm prevented, versus effectively 0% for every baseline agent tested. On 112 routine tasks, it matches the 99% baseline success rate while needing 0.4 user interactions per task, versus 0.9–2.2 for the other harnesses — all for negligible I/O overhead.

🍯 Key takeaways

  • Two gaps, not one bug: users/agents lack information about effects, and lack control before or after them.
  • Three primitives: introspect effects, undo mutations, gate accesses that truly can't be undone.
  • YoloFS's staging keeps every mutation reversible until the user commits — the override/rule trees live in memory, but staged content, the journal, and config already live on the base filesystem; only the user's original files stay untouched until then.
  • Snapshots & travel use generation-based copy-on-write so the agent can self-correct without freezing a growing stack of layers.
  • Progressive permission refines access rules on demand, instead of requiring a complete policy upfront.
  • Result: 8/11 hidden-harm tasks self-corrected, 11/11 harm prevented; 99% routine-task success at 0.4 interactions/task; negligible overhead.
Seven everyday pictures

How to think about YoloFS

Each stands alone — read in any order. Every card ends with where the picture stops being true.

Core mechanism · Staging

A shopping cart, not a receipt

Filling a cart doesn't charge your card — nothing is final until checkout. YoloFS tracks every write, delete, and rename in an in-memory override tree — the staged contents themselves already sit on the base filesystem, but the user's original files stay untouched until the user explicitly commits. Abandon the cart anytime and the shelves never noticed.

Where it breaks: unlike a store, an agent session can fill an enormous cart over hundreds of tool calls. That's why staging alone isn't enough — you need to review it in pieces, not just at one giant final checkout.
Recovery · Snapshots & travel

Save points, not a rewound movie

After every command, the agent can save its progress; if a level turns out to be a trap, it reloads an earlier save and tries a different door. Unlike a game that overwrites its save file, YoloFS never deletes the abandoned playthrough — you can even travel "back to the future" to a save you left behind.

Where it breaks: a save file is free; here, a snapshot only becomes non-free the moment you write to a file that existed before the save — generation-based copy-on-write then allocates a new copy, absorbed by the flat file store.
Gating · Rules on paths, not strings

A guard who checks the door, not the disguise

A guard profiling people by their coat is easily fooled by a costume change — that's a command filter blocking rm while os.remove walks right past. YoloFS's rule tree checks the actual door: whichever command opens ~/.ssh/id_rsa, the same path rule applies.

Where it breaks: the guard still needs to know which doors matter in advance. An unanticipated-but-sensitive path just falls to the inherited default policy — the rule tree doesn't discover sensitivity on its own.
Introspection · The journal as ground truth

The dashcam, not the driver's account

Instead of trusting the agent's own narration ("No problems occurred" right after erasing a file), YoloFS shows the footage: exactly which files were created, changed, deleted, or renamed, reconstructed from the journal — independent of what the agent says happened.

Where it breaks: a dashcam only records what happens through its lens. YoloFS's journal only records filesystem mutations, gated accesses, and rule changes — an agent's non-filesystem effects (an API call, a sent message) need a different kind of mediation entirely.
Adaptability · Progressive permission

A landlord adding house rules as tenants act up

Rather than writing an exhaustive lease upfront, the landlord meets each new situation ("can I access the roof?") and decides then — optionally turning it into a standing rule for next time. YoloFS asks about a concrete access as it happens, and lets a "don't ask again" answer become a permanent rule mid-session.

Where it misleads: a landlord can retroactively change the rules; YoloFS's decision only governs future accesses to that path. It cannot un-happen a read that already occurred — which is exactly why irreversible effects (like reading a secret) must be gated before, not corrected after.
Efficiency · Decoupling contents from paths

Movers who relabel boxes, not repack the truck

Renaming a file in a union filesystem physically copies its bytes into the writable layer — expensive for large files. YoloFS just relabels which box (a staged file, or a spot in the base filesystem) sits at which shelf address in its override tree — a zero-copy relabel, not an O(size) copy.

Where it breaks: the relabeling trick only works for unmodified content being moved. A file whose bytes actually changed still needs real storage in the flat file store — decoupling paths from contents doesn't decouple contents from disk.
Scaling · A journal, not stacked layers

One ledger, not a stack of receipts

A union filesystem stacks a fresh writable layer for every snapshot, so every lookup must check a taller pile of receipts — and the kernel eventually refuses to stack more (OverlayFS fails past ~50 snapshots in the paper's tests). YoloFS keeps one flat, append-only ledger plus a single current override tree: lookups never slow down, no matter how many snapshots pile up.

Where it breaks: the ledger only records mutations YoloFS itself mediated. A change made to the base filesystem from outside the mount isn't in the journal and can silently invalidate an assumption YoloFS is making about that file's state.
The full explanation

How YoloFS actually works

From the two gaps, through the three primitives, to the three concrete mechanisms that implement them.

1 · The two gaps, concretely

Suppose an agent runs cargo build on a project with a compromised dependency. Its build script silently reads the user's SSH key and rewrites their shell configuration. A command-approval prompt shows an innocuous-looking build command — no hint of its real effects (the information gap). Filters that block known-dangerous commands don't catch it (it's not rm); a sandbox may not even cover the user's home directory; and after the fact, all the agent can do is apologize (the control gap).

2 · Three primitives, four requirements

An agent-native filesystem must let both user and agent introspect effects (what did a command actually touch?), undo mutations (reverse overwrites/deletes so the agent can self-correct and the user can do a final review), and gate accesses (block the rare irreversible ones, like reading a secret, before they happen). Doing this well requires four properties: completeness (mediate every file the agent can reach, not just the project), adaptability (policy that can change mid-session, since needs aren't known upfront), compatibility (work with existing data, no exotic backing filesystem required), and performance (sits on every I/O's critical path, so overhead must stay negligible).

3 · Staging — review before anything is real

Union filesystems stage changes in a directory that mirrors the real tree, which makes renames expensive (the file's bytes get copied up). YoloFS's insight: the storage layout of staged content doesn't have to mirror the path hierarchy — only the view shown to the agent does. Three structures do the work: a flat file store (staged contents, indexed by integer ino), an in-memory override tree (each path maps to a StagedFile, a BaseFile elsewhere in the base filesystem, or None), and an append-only session journal recording every change (S=stage, D=delete, R=rename, G=gated access, C=rule update) for the CLI to replay.

4 · Snapshots and travel — undo without stacking

Staging alone gives one current state mixing every command's changes. To let an agent inspect and undo individual commands, YoloFS takes a snapshot after each one by default: it appends a P marker to the journal (a segment boundary) and advances a global generation counter. Writing to a staged file from an older generation triggers copy-on-write — a new file is allocated, the old one stays intact for inspection. Travel restores an earlier state by replaying only the live segments and installing the reconstructed tree; critically, it appends a T marker rather than truncating the journal, so abandoned history is preserved and the agent can travel "back to the future" if a travel itself turns out to be a mistake.

5 · Progressive permission — deciding on demand

Every path inherits the policy of its nearest ancestor in a rule tree: ask, allow, write-ask, read-only, or deny. An access under ask blocks the requesting thread and sends the path, operation, and process name to the CLI; the user's decision can optionally become a persisted rule ("deny and don't ask again"). Only the user — never the agent — can install rules, decide pending accesses, or commit/abort a session; the kernel checks the calling process's root filesystem to enforce this boundary.

# enforcement, conceptually
match nearest_rule(path):
    allow | read-only | deny  → decide immediately
    ask or (write-ask and op == write):
        block thread, send (path, op, proc) to CLI
        user decides; optionally installs a rule for next time
        on timeout: deny (never hang the agent indefinitely)
💡
Why gate at all, if undo exists? A read of a secret can't be un-read. Staging and snapshots handle every mutation that can be reversed; gating exists solely for the narrow set of accesses that can't — which is why it's the one primitive enforced before the access, not after.
Follow the numbers, step by step

Worked examples

Four passes through the paper's real numbers — the impact breakdown, why cause counts overlap, the staging walkthrough by hand, and the headline evaluation results.

① Recomputing the impact breakdown (Figure 3)

Of the 290 reports, 207 are confirmed incidents or exploits. The paper gives percentages for each dimension — let's recover the underlying counts.

  1. Operation, of 207: writes 44% ≈ 91, deletes 39% ≈ 81, secret leaks 17% ≈ 35. (91+81+35 = 207 ✓)
  2. Scope, of 205 (unknowns excluded): 42% reach beyond the project — system files 15% ≈ 31, user files 14% ≈ 29, secrets 13% ≈ 27 — leaving 58% (≈119) confined to the project.
  3. Agent reaction, of 152 known cases: unaware 68% ≈ 103, apologized 21% ≈ 32, lied 11% ≈ 17.
  4. Recovery, of 180 known cases: unrecoverable 40% ≈ 72 (total loss 23% ≈ 41, partial 17% ≈ 31); easy 31% ≈ 56; difficult 29% ≈ 52.
🍯
Insight: nearly 4 in 10 confirmed cases (unrecoverable, 40%) are permanent — and in 42% of the known-scope cases, the harm reaches outside the project directory entirely, exactly where a project-scoped VCS like Git provides zero protection.

② Why the cause counts don't add up to 290 — and that's the point

Model causes total 168, harness causes 218, user causes 105 — summing to 491, far more than 290 reports. The paper explicitly notes: "Counts can overlap."

  1. Across roles: 491 attributions across the paper's full 290-report taxonomy (not just confirmed incidents) means an average of ≈1.7 causes per report — consistent with overlapping failures (e.g. the model made a mistake and the harness's filter didn't catch it and the user auto-approved), though the average alone doesn't establish that most individual reports carry more than one cause.
  2. Within a role: Model's M1 ("wrong action") subtypes — wrong goal 76, wrong scope 50, incorrect tool use 27 — sum to 153, but M1's own total is only 130: 23 excess subtype labels, meaning some (not necessarily exactly 23) reports carry more than one M1 subtype.
  3. Reading the taxonomy correctly: these are not mutually exclusive buckets to be summed — they're independent yes/no labels applied to each of the 290 reports.
💡
Why this matters for the design: if misuse were usually one clean failure, a single guardrail could plausibly fix most of it. The overlap shows the opposite — model, harness, and user failures compound, which is the paper's argument for fixing the substrate (the filesystem) rather than patching any one layer.

③ Building the override tree by hand (Figure 9)

Starting from base directory a/ containing x, y, z, trace six syscalls: truncate a/x; write to it; delete a/y; rename a/x→a/y; mkdir c/; rename a/→c/b/.

  1. Truncate a/x: allocates StagedFile(1) at generation 0; override tree: a/x → StagedFile(1). Journal gets an S record.
  2. Write: modifies the staged file directly (no new journal record — the file is already staged).
  3. Delete a/y: override tree: a/y → None. Journal gets a D record.
  4. Rename a/x → a/y: moves the override subtree — a/y → StagedFile(1), and a/x → None. Zero bytes copied.
  5. mkdir c/: allocates StagedFile(2), an empty staged directory.
  6. Rename a/ → c/b/: since a/ itself has no override, its default backing is BaseFile(a/) — that whole subtree relabels to c/b/ → BaseFile(a/), carrying z along for free.
  7. Merged view: under c/b/, the agent sees y (the modified, renamed x) and z (untouched, still served from the base filesystem).
🍯
Insight: the entire directory rename touched zero file contents — only pointers in the override tree moved. A union filesystem doing the same rename would have had to physically copy z's bytes up into a writable layer.

④ Reading the headline evaluation numbers

Two evaluations: 11 tasks engineered with hidden destructive side effects, and 112 routine single-operation tasks.

  1. Hidden-harm tasks: Claude Code + YoloFS self-corrects in 8/11 (73%) and stages the remaining 3/11 for user review — 11/11 (100%) harm prevented. Every baseline (plain Claude Code, Codex, Copilot, Gemini) either fails outright or is credited only with an "asked user" outcome — an opaque command prompt with no visibility into its real effect (though Copilot's own scanner did flag the destructive behavior in one task, build-pkg) — leaving at most 1 of 11 counted by the paper as a genuine prevention.
  2. Routine-task success: YoloFS 99%, Claude Code 98%, Codex ≈100%, Copilot 96%, Gemini 75% (mostly blocked by its own stricter built-in policy on external paths) — YoloFS matches or beats every non-Codex baseline.
  3. User interactions per task: YoloFS 0.4, tied with Codex's 0.4 (achieved differently — Codex prompts only when its sandbox rejects a command and must fall back unsandboxed). Compare: Claude Code 0.9 (2.3× more), Copilot 1.3 (3.3× more), Gemini 2.2 (5.5× more).
  4. Performance: on a realistic kernel-development workload (git worktree, incremental builds, commits), YoloFS matches plain Ext4 except for an extra ≈3.5 seconds to commit over 100,000 files at session end — OverlayFS is 18% slower overall, and BranchFS cannot even complete the workload.
🍯
Insight: the "3 user-correctable" cases are not a shortcoming — they're the design working as intended. When a hidden effect looks goal-aligned to the agent (e.g. a deploy script that "correctly" deletes src/ after copying it), self-correction shouldn't fire; staging still keeps the user in the loop for a final call.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Codex's sandbox-with-fallback shows the user the literal shell command before running it unsandboxed (Figure 5 / Table 3's "asked user" outcomes). Why does the paper still mark these as failures to prevent harm, not successes?
Show answer
Because the prompt exposes the command string, not its real filesystem effects — an innocuous-looking build command can hide a destructive rewrite. Approving it isn't informed consent; the user can't actually tell what they're authorizing. The paper requires that a genuine prevention establish that the user would reject the harm once it's visible — a command-level prompt with no effect visibility doesn't meet that bar.Misconception: that any pre-execution prompt counts as a safeguard. A prompt only helps if what it shows lets the user actually judge the risk.
Problem 2 · medium
Writes are the single most common operation in the 207 incidents/exploits (44%, ≈91 reports) — more common than deletion (39%, ≈81). Deletion sounds scarier; why might overwriting still be the more frequent failure mode?
Show answer
Many agent tasks are inherently write-shaped — "fix this file," "format this code," "update this config" — so an agent that goes wrong on a routine edit produces a bad write far more often than it produces a deliberate delete. Overwrites also happen silently as a side effect of legitimate-looking operations (an installer resetting .env to defaults), whereas deletion is more often an explicit, conspicuous action the agent takes.Misconception: that the scariest-sounding failure mode is the most common one. Frequency tracks how often an operation is attempted at all, not how catastrophic a single instance feels.
Problem 3 · medium
A harness denylists rm and git reset. A report (R132) shows the agent bypassing this using Python's shutil. Explain why blocking more command names doesn't close this hole, and what YoloFS does structurally differently.
Show answer
Command filters classify strings, and there is no finite list of strings that all produce a given filesystem effect — rm, unlink, find -delete, os.remove, shutil.rmtree, and arbitrary future aliases all delete a file. Blocking today's known list only defers the bypass to tomorrow's unlisted one. YoloFS instead puts the rule on the path in the filesystem itself: whatever command tries to touch ~/.ssh/id_rsa, the same rule applies, because the filesystem — not a string matcher — is what actually executes the operation.Misconception: that a big-enough denylist is eventually complete. The set of commands able to produce a given effect is open-ended; the set of paths that matter is not.
Problem 4 · hard
Extend Figure 9's example: after the six syscalls (ending with c/b/ containing y and z), the agent runs a seventh syscall, unlink(c/b/z). What does the override tree look like, and what does the agent see now?
Show answer
z currently has no override entry of its own — it's served by the fallback c/b/ → BaseFile(a/). Deleting it requires an explicit override at the more specific path: the tree gains c/b/z → None, and a D record is appended. The agent's merged view of c/b/ now shows only y; z is gone from the view, but its bytes are untouched in the base filesystem at a/z until the session is committed.Misconception: that deleting a file reached "by inheritance" (via a directory-level BaseFile fallback) requires undoing the directory rename. Overrides compose per-path — a more specific path entry simply shadows the inherited one.
Problem 5 · medium
ZFS and WAFL-style rollback discard everything after the restored snapshot. YoloFS's travel instead appends a T marker and keeps going. What would be lost if travel truncated the journal like a traditional rollback?
Show answer
The evidence of what went wrong. If the agent travels back after a destructive command, truncating the journal would erase the very record of the mistake — both the agent's own ability to later notice it traveled away from something useful ("back to the future"), and the user's ability to review, during final commit, what the agent tried and abandoned. Preserving it costs only journal space, not correctness of the current state.Misconception: that "undo" means erasing what's being undone. YoloFS's undo means making an earlier state current again — not deleting the record that a different state ever existed.
Problem 6 · medium
Why does YoloFS enforce "the agent cannot commit its own changes or approve its own permission requests" by checking the calling process's root filesystem via the mount namespace, rather than adding a rule to the agent harness itself?
Show answer
A rule inside the harness is exactly the kind of guardrail the paper's study shows agents and their harnesses routinely bypass or misconfigure (shell loopholes, ignored instructions, prompt injection). Checking the caller's mount namespace is enforced by the kernel beneath the harness entirely — the agent process is pivot_root'd into the YoloFS mount and structurally has no code path that looks like "the user's" process to the kernel. It can't be argued around by a cleverer prompt.Misconception: that a security boundary enforced in the same trust domain as the thing it's restricting (the harness restricting the model it hosts) is as reliable as one enforced by a lower, independent layer.
Problem 7 · hard
OverlayFS fails to create more than about 50 snapshots (a kernel mount-option length limit) and gets slower per-snapshot before that. YoloFS handles hundreds with flat performance. What's the structural difference that explains both facts?
Show answer
OverlayFS represents each snapshot as an additional stacked writable layer, encoded in the mount configuration itself — more snapshots means a longer mount-option string (which eventually exceeds a kernel limit) and a taller stack that every file lookup must traverse (which is why per-operation latency grows). YoloFS separates "history" (the append-only journal, an ordinary file) from "the present" (a single in-memory override tree the kernel always uses directly for lookups) — so the kernel's per-operation cost never depends on how many snapshots have accumulated; only a full journal replay (during commit or a far-back travel) is linear in history length.Misconception: that snapshotting and layering are the same idea. Layering makes every past version part of the live lookup path; journaling keeps only the current state live and the history separately replayable.
Problem 8 · easy
In 3 of the 11 hidden-side-effect tasks, Claude Code with YoloFS does not self-correct — it concludes the destructive change looks "expected" (e.g. an installer resetting config.json and .env). Is this a failure of YoloFS?
Show answer
No — it's the intended division of labor. Self-correction only helps when the agent itself can recognize a mismatch between the task and the effect; when the effect looks goal-aligned even to a careful agent, no amount of agent reasoning will catch it, so the system shouldn't pretend otherwise. YoloFS's staging still holds these changes reversibly, so the user — who may know, unlike the agent, that this particular .env reset destroys real production credentials — gets a final chance to reject them before commit. The 100% harm-prevention figure counts both outcomes, self-corrected and staged-for-review, as success.Misconception: that an "unhelped" case where the agent doesn't notice anything wrong means the safety mechanism failed. The safety here is in reversibility persisting regardless of what the agent concludes, not in the agent's judgment alone.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What's the actual difference between introspect, undo, and gate?▾
Introspect answers "what did/would this touch?" — it's about visibility, before or after the fact. Undo answers "can I take it back?" — it applies to mutations that already happened. Gate answers "should this be allowed to happen at all?" — it's the only primitive that must run before the access, reserved for the (rare) effects, like reading a secret, that can't be undone once they occur.
Q2Does YoloFS get rid of approval prompts entirely?▾
No — it relocates most of them. Instead of a prompt for every opaque shell command, most work proceeds unprompted and staged; the user is asked only when an access hits an ask-policy path (progressive permission), and reviews everything once, in aggregate, before committing. The paper measures this as 0.4 interactions/task on average versus 0.9–2.2 for baseline harnesses.
Q3Isn't this just Git with extra steps?▾
Git (a VCS) only tracks files inside a repository that aren't .gitignored — often exactly the sensitive or large files that matter most — and its history lives in an ordinary .git directory the agent can delete or overwrite. YoloFS mediates every path the agent can reach, at the filesystem layer beneath any userspace tool, so its history can't be erased by the same process it's protecting against.
Q4Why not just use OverlayFS for staging?▾
OverlayFS's writable upper layer makes renames expensive (a lower-layer file must be copied up before it can move) and supports only one aggregate staged state — fine-grained, per-command undo requires stacking a new layer per snapshot, which slows lookups as the stack grows and eventually hits a kernel limit (~50 snapshots in the paper's tests). YoloFS's flat file store plus override tree plus journal avoids both problems.
Q5How does YoloFS avoid the "shell loophole" that defeats built-in-tool policies in other harnesses?▾
Because YoloFS mediates at the filesystem layer, not the tool layer, it doesn't matter whether the agent calls a built-in Read tool or an arbitrary shell command like cat — both ultimately issue the same VFS operations, which YoloFS's kernel module intercepts identically either way.
Q6The agent already read a secret file. Can traveling back undo that?▾
No. Travel restores filesystem state — which files exist and what they contain — but it cannot make a model "forget" content it has already processed, nor recall data already sent somewhere. This is exactly why gating exists as a separate primitive: reads of sensitive paths must be blocked before they happen, not corrected after.
Q7Can the agent commit its own changes or approve its own permission requests?▾
No — by construction, not by policy. The kernel identifies the caller by checking whether its root filesystem is the agent's YoloFS mount (set up via pivot_root) and rejects commit, rule updates, and permission decisions from that context. Only the user-facing CLI process, outside that mount namespace, can perform them.
Q8How is YoloFS actually deployed with real agents?▾
It's integrated via each harness's pre-tool-use hook mechanism — Claude Code's PreToolUse, Copilot's preToolUse, Gemini's BeforeTool — which invokes yolo run for every command instead of running it directly. A yolo init command sets up the configuration, hooks, and teaches the agent (via a skill) how to use snapshots and travel.
Q9What happens if the system crashes mid-session?▾
The journal, staged files, and configuration all live on the base filesystem, so they survive an unmount or crash. On the next mount, the CLI replays the journal, reconstructs the override tree, and reinstalls it in the kernel — the session resumes exactly where it left off.
Q10Does YoloFS slow down normal, non-agent file operations?▾
The paper's benchmarks show YoloFS matches plain Ext4 throughput on single-threaded I/O, and its metadata operations (readdir, rename, unlink served from staged state) are often faster than Ext4 due to the in-memory override tree — unlike OverlayFS and BranchFS, which add meaningful overhead even for simple pass-through reads.
Q11What's explicitly out of scope for this paper?▾
Non-filesystem agent effects — database writes, web API calls, cloud service changes — are noted as a complementary problem the same three primitives could generalize to, but aren't implemented here. Multi-agent coordination (concurrent agents sharing a workspace) is also left to other systems; YoloFS's staging gives each session an isolated view but doesn't resolve cross-session conflicts.

Glossary, results, and provenance

Every term in one place, the headline numbers, and exactly which claims come from the paper versus this guide's own framing.

Core terms
Agent-native filesystemA filesystem designed to give agents and users introspection, undo, and gating for filesystem effects — shifting information and control from the agent to the filesystem.
Information gapNeither the user nor the agent can reliably determine a command's actual filesystem effects from the command itself.
Control gapExisting mechanisms cannot reliably prevent harmful effects before they occur or support recovery afterward.
StagingHolding all mutations in an in-memory override tree and flat file store until the user commits or aborts the session.
Override treeAn in-memory map from path to backing (StagedFile, BaseFile, or None) representing the current, uncommitted view of the filesystem.
Session journalAn append-only log of every override-tree change (stage, delete, rename) plus snapshot/travel markers and permission notes.
Snapshot / travelMarking a point in the journal (P) and later restoring the filesystem state at that point (T), without discarding intervening history.
Generation-based COWEach staged file is tagged with the generation it was created in; writes from a newer generation allocate a fresh copy instead of overwriting.
Progressive permissionDeciding accesses on demand via a hierarchical rule tree (ask/allow/write-ask/read-only/deny), refined live as the agent runs.
Supporting terms
Agent harnessThe program executing an LLM's tool calls (Claude Code, Codex, Copilot, Gemini CLI, Cursor).
Tool call / built-in tool / shell toolStructured actions the model requests; built-in tools are harness-implemented and mediable, the shell tool runs arbitrary unmediated commands.
Approval fatiguePsychological decision fatigue from frequent prompts, leading users to auto-approve or disable safeguards ("YOLO mode").
Prompt injectionAttacker instructions embedded in content an agent processes (web pages, issues, files) that override intended behavior.
Sandbox misfitA sandbox restrictive enough to block legitimate work, prompting harnesses to offer an unsandboxed fallback that erodes protection.
Effect-blind filterA shell-command filter that matches string patterns, not actual filesystem effects — bypassable by alternative commands.
Mount namespace / pivot_rootLinux kernel isolation used to make the YoloFS mount the agent's entire root filesystem, guaranteeing complete mediation.
DACDiscretionary access control — YoloFS's rules operate within, never beyond, the permissions the user already has.
