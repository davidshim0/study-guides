eBPF '26, Prague · Workshop Paper · A Field Guide

Letting untrusted bytecode into a kernel that refuses to trust itself

Asterinas is a Rust "framekernel" built to keep almost all its code memory-safe by construction. This paper asks: can you bolt eBPF — Linux's sandboxed-extension mechanism — onto it, without reopening the door that framekernels exist to close?

📄 Chen & Lee, "Towards eBPF Support in a Memory-Safe OS" · eBPF '26 🎓 Assumes OS/kernel + Rust background — no networking-stack primer needed ⏱ ~18 min read · 3-page workshop paper
🛡️

Let an untrusted program reach into the kernel through a CHECKED, narrow hook — never through a RAW pointer into kernel memory.
The whole paper is what happens when that second path sneaks back in anyway.

1What eBPF actually is, in one sentence▾

eBPF lets a user submit a small bytecode program that a verifier statically checks (bounded loops, in-range memory access, valid jumps), and that the kernel then runs at chosen hook points — packet arrival, syscall entry, scheduler events — either via an interpreter or by JIT-compiling it to native code.

On Linux, that verifier front-loads most of the work: pass it once at load time and the kernel largely trusts the program to run, with only a few checks (like array bounds) still enforced live. This paper's prototype strikes a different balance — no comprehensive verifier yet, just a load-time jump-bounds check plus per-instruction runtime memory bounds checks doing the safety work instead.

Now you're ready: everything in this paper is about how much of that safety story can be pushed to load time — and how much, here, still has to happen at runtime instead.
2Framekernel — Asterinas's answer to "minimize unsafe Rust"▾

Safe Rust's compiler guarantees (no use-after-free, no data races, no out-of-bounds access) only hold for code that never uses unsafe. A framekernel is Asterinas's architecture for confining all unsafe code to one small, heavily audited core (the TCB), while the rest of the OS — drivers, networking, filesystems — is ordinary safe Rust that cannot violate memory safety even if buggy.

This is a much stronger guarantee than Linux's monolithic C kernel, where any subsystem bug can corrupt arbitrary kernel memory.

Now you're ready: the central tension of this paper is that eBPF support threatens to pull code back into that minimal unsafe core — see primer 5.
3Interpreter vs JIT — and why this prototype only has one▾

An interpreter walks the bytecode instruction-by-instruction, decoding and dispatching each one — simple to implement and verify, but slower. A JIT compiler translates the whole bytecode program into native machine code once, then runs it at full speed — but generating and executing arbitrary native code from untrusted input is a much bigger attack surface to get right.

Linux's eBPF supports both. This paper's prototype uses only the interpreter (rbpf), deliberately deferring JIT.

Now you're ready: "safe JIT without expanding the TCB" is explicitly called out as unsolved future work — it's the hard research problem the paper sets up but doesn't attempt.
4Hook points and verdicts (the netfilter-style model)▾

A hook is a fixed point in kernel code where control is handed to an attached eBPF program with a read-only(-ish) context struct describing the current event, and the program returns a small verdict (accept/drop, allow/deny) that the hook enforces. Linux's nf_hook() on the packet transmission path is the canonical example.

Hooks are deliberately narrow: the program never gets a raw pointer to kernel structures, only a curated context — that's what keeps hook-based extension safe even for untrusted code.

Now you're ready: this paper's one hook lives in UdpSocket::send(), explicitly modeled on Linux's UDP-egress nf_hook() call.
5Why an interpreter needs unsafe at all▾

eBPF memory instructions (ldx/stx) address a program's scratch memory using arbitrary integer offsets computed at runtime. To bounds-check these safely, an interpreter must either (a) do pointer arithmetic on real host addresses and manually verify the result stays in range — which requires unsafe Rust — or (b) keep everything as offsets into a sandboxed byte buffer, checked by the type system, which safe Rust can express directly.

rbpf, as embedded here, takes approach (a): it computes raw host addresses and checks them at runtime, which is why the integration needs unsafe blocks.

Now you're ready: this is exactly the gap the paper flags — and "bounded relative address calculation" (approach b) is the fix it proposes for future work.
6A speculative bridge to tiering/CXL work — guide framing, not the paper's▾

This connection is this guide's framing, not something the paper itself discusses — the paper never mentions memory tiering, CXL, DAMON, or page-access telemetry. Two threads may still be worth keeping in mind for your own work: first, eBPF is already a common instrument for hot/cold page-access observability elsewhere in the kernel ecosystem (perf-events-via-eBPF, DAMON-adjacent tooling), so whether a memory-safe kernel can host eBPF at all is relevant background if you ever wanted that kind of telemetry there. Second, the paper's TCB-minimization goal sits on the same design axis as page-table/NVM-management code in Linux mm: less trusted code touching raw addresses means a smaller blast radius for bugs.

Now you're ready: treat the rest of this guide as "how much raw-address code does a monitoring/extension mechanism need, and can that be confined" — a question that generalizes past networking, but is this guide's extrapolation, not a claim the paper makes.
7What "preliminary work" means for this paper▾

This is a 3-page workshop paper reporting a functional prototype, not a systems paper with performance numbers. There's no throughput/latency evaluation, no comparison against native Linux eBPF speed, and no formal verification claim — the contribution is demonstrating feasibility (it loads, attaches, and enforces verdicts correctly) and mapping out exactly where the hard problems remain.

Now you're ready: don't expect quantitative benchmarks in the Worked Examples tab — the "numbers" here are architectural (syscall commands implemented, hook points, safety layers), not performance figures.
8ABI compatibility vs implementation freedom▾

Asterinas aims to run unmodified Linux binaries, which for eBPF means: keep the instruction set and the bpf() syscall surface compatible, so existing toolchains (clang, llvm-objcopy) work unchanged — the paper's own evaluation uses exactly this C + clang + llvm-objcopy pipeline, not a claim that libbpf-based workflows are supported. Hook contexts — the structs a program reads at each hook point — are Asterinas-internal implementation details with no ABI promise, so they're free to diverge from Linux's.

Now you're ready: this is why the paper can reuse standard eBPF binaries end-to-end while still writing a hook interface from scratch.
The whole story in one place

eBPF on Asterinas, in a nutshell

What was built, why it's harder than it looks, and where the safety guarantee currently leaks.

eBPF's whole value proposition is safe kernel extensibility: untrusted bytecode, checked once by a verifier, then trusted to run. Porting that model outside Linux tests whether the safety story travels with it, or was quietly leaning on things specific to Linux's C implementation.

The authors build three pieces inside Asterinas, a Rust framekernel that confines almost all unsafe code to a minimal Trusted Computing Base (TCB): a bpf() syscall implementing two sub-commands (BPF_PROG_LOAD, BPF_LINK_CREATE), an in-kernel execution runtime built on the existing rbpf interpreter, and a single hook inside UdpSocket::send() — the UDP transmission path — modeled directly on Linux's nf_hook().

The result works end-to-end: standard eBPF binaries, compiled with an unmodified Linux toolchain, load through the custom syscall and correctly accept or drop UDP packets based on metadata or payload content. That's the feasibility result.

But the paper is equally honest about the catch: rbpf's memory-safety checks compute raw host addresses at runtime, which forces the integration to use unsafe Rust — precisely the category of code a framekernel is designed to minimize. That raw-address computation falls outside Asterinas's spatial-safety guarantees and limits how fully the eBPF runtime integrates with the framekernel's safety model, and closing that gap (plus adding a real bytecode verifier, and eventually safe JIT) is the paper's stated future work, not something it has solved.

🍯 Key takeaways

  • Three modules: bpf() syscall (load + attach) → rbpf-based runtime (interpret) → UDP-egress hook (enforce accept/drop).
  • Linux compatibility is kept at two layers — the instruction set and the bpf() syscall surface — so standard toolchains work unmodified; hook contexts are free to diverge.
  • Two safety layers exist today: a static load-time jump-bounds check, and a runtime memory-access bounds check — but no bytecode verifier, no termination checking.
  • The runtime computes raw host addresses for bounds checks → needs unsafe blocks → falls outside the spatial-safety guarantees the framekernel was built to give the rest of the OS. This is the paper's central open problem.
  • Validated with 3 filtering scenarios (unconditional, metadata/port, content/payload) on QEMU — all behaved as expected. No performance numbers are reported; this is a feasibility study.
  • Future work: more hooks, helpers/maps for stateful programs, sandboxed (relative) address calculation to reach fully-safe Rust, and safe JIT without growing the TCB.
Six everyday pictures

How to think about this integration

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core tension · TCB leakage

A vault with a guest window

A bank vault's whole value is that only audited staff ever touch the safe. Add a little pass-through window so customers can slide in a request form, and you've built a new access path — the vault is only as secure as that window's checks. Asterinas's framekernel is the vault (minimal audited unsafe); the eBPF hook is the window. The paper shows the window works — but also that its latch (raw-address bounds checking) isn't yet built from vault-grade material.

Where it breaks: a vault window is a fixed, small opening; eBPF programs are Turing-incomplete but still arbitrary logic, so "the window" has far more internal complexity than a physical slot.
The design choice · ABI vs implementation

A universal power plug, local wiring

A travel adapter keeps the plug shape (instruction set, bpf() syscall surface) standardized worldwide so any device works anywhere — but the wiring behind the wall socket is entirely local. The paper does the same split deliberately: keep eBPF bytecode and the bpf() commands Linux-compatible (existing toolchains plug in unmodified), while hook contexts — the "wiring" — are free to be Asterinas-specific.

Where it breaks: a plug shape is fixed once; the bpf() syscall surface here is only a subset (two of many commands), so compatibility is partial, not a finished standard.
The two-layer safety model

A bouncer plus a metal detector

One check at the door (guest list, ID) and a second check as you walk through (metal detector) are complementary: the first catches who shouldn't be there at all, the second catches what shouldn't come in even with a valid invite. This prototype's two layers mirror this: a static load-time check (jump targets stay in-bounds — "is this a valid program at all?") and a runtime memory check (every load/store is bounds-checked as it executes — "is this specific access in-bounds right now?").

Where it breaks: a real bouncer also profiles intent and behavior over time; this prototype has no equivalent of a full verifier — no termination checking, no defense against adversarially crafted bytecode patterns.
The proposed fix · address calculation

Coordinates on a map, not a literal address

Telling a courier "go to (3rd row, 5th seat)" inside a stadium lets you validate the coordinates against the stadium's known bounds before anyone moves; telling them a raw street address requires trusting they'll interpret and clamp it correctly themselves. rbpf's current approach computes something like the raw address and manually checks it (needs unsafe); the proposed fix — bounded relative/sandboxed addressing — keeps everything as checked offsets into a known buffer, which safe Rust's type system can enforce without any unsafe at all.

Where it breaks: this is future work, not implemented — the paper proposes the fix but the current prototype still uses raw addresses.
Deferred optimization · interpreter vs JIT

Reading the recipe vs memorizing it

Following a recipe card step-by-step every time is slower than a chef who's memorized it and moves on muscle memory — but the chef had to practice (compile) first, and mistakes made while memorizing are harder to catch. The interpreter reads eBPF bytecode instruction-by-instruction every run (slower, simple to reason about); JIT "memorizes" it as native code once (fast, but generating trustworthy native code from untrusted input is the hard, unsolved part).

Where it breaks: a chef's memorization doesn't need an external safety proof; JIT-compiled native code needs the compiler itself to be trusted not to introduce exploitable bugs — a much higher bar.
The placement choice · why UDP egress first

A checkpoint at the one shared doorway

Rather than posting a guard in every room of a building, you put one checkpoint at the single doorway everyone must pass through on their way out. UDP send() is exactly that doorway in Asterinas's stack: placing the hook inside the thin aster-bigtcp wrapper — not inside smoltcp itself — checks every outgoing UDP datagram without touching the third-party TCP/IP library's code at all.

Where it breaks: a building has many doorways (ingress, TCP, other protocols) that still need their own checkpoints — this prototype covers only the one UDP-egress doorway; everything else is unhooked for now.

Follow the paper's own numbers

Worked examples

This is a feasibility paper, not a benchmarks paper — so the "numbers" worked here are architectural: syscall coverage, safety layers, and the three validation scenarios traced end to end.

① Tracing the three validation scenarios

The paper validates with a UDP receiver and three filtering programs of increasing specificity. What does each one actually check, and how is success measured?

  1. Scenario 1 — Unconditional. The program ignores the context entirely and always returns Accept (or always Drop). This exercises only the "hook is reliably reached, verdict is honored" path — no metadata or payload access at all.
  2. Scenario 2 — Metadata-based. The program reads the packet's destination port from the context and returns Drop if it matches a configured value, Accept otherwise. This is the first test to actually exercise context-metadata reads.
  3. Scenario 3 — Content-based. The program reads the payload's first byte and returns Drop unless it equals ASCII 'a'. This is the strictest test: it requires correct payload-view access, not just metadata.
  4. Success criterion, uniformly: a dropped datagram must produce a timeout at the receiver (nothing arrives); a permitted one must be delivered unchanged. Both outcomes were observed correctly in all three scenarios.
🍯
Insight: the three scenarios form a deliberate escalation — reachability → metadata access → payload access — each one a strictly harder test of the same hook and context design.

② How much of Linux's bpf() surface is actually covered

Linux's bpf() syscall has dozens of sub-commands (program load, map operations, link management, BTF, iterators…). How much does this prototype implement?

  1. Implemented: 2 commands. BPF_PROG_LOAD (submit bytecode) and BPF_LINK_CREATE (attach to a hook) — the minimum pair needed to get a program from disk to running at a hook point.
  2. Not implemented: maps. No BPF_MAP_CREATE or map-access helpers exist yet, so attached programs are stateless between invocations — every packet is evaluated independently, with no way to, say, maintain a per-flow counter.
  3. Not implemented: helper functions. No helper-call surface (e.g. reading other kernel state, timestamps) is exposed to programs — the context struct is the entire information a program can see.
  4. Net effect: the three validation scenarios are exactly the class of program this coverage supports — pure functions of one packet's metadata/payload to a verdict, nothing more. Stateful filtering (rate limiting, connection tracking) is explicitly out of scope until maps/helpers land.
💡
This is a useful sizing exercise: the "minimum viable eBPF" slice is syscall load/attach + one hook + zero helpers/maps — everything else is deliberately deferred.

③ Where the TCB gap actually sits

The paper states the runtime "requires unsafe Rust blocks" because it computes raw host addresses for bounds checks. Walk through why, concretely.

  1. An eBPF load/store instruction carries a register value (a runtime-computed offset into the program's scratch memory) plus a static displacement.
  2. To check "is this access in-bounds," the interpreter needs to compute the effective host address: base_ptr + register_value + displacement. Computing and dereferencing that address is exactly what Rust's borrow checker cannot verify statically — hence unsafe.
  3. The runtime check happens anyway (paper §2.1: "intercepts memory load and store instructions to enforce runtime out-of-bounds checks") — so a malformed access is still caught before it does damage.
  4. But the code performing the check is itself outside the compiler's safety guarantee. A bug in that specific bounds-check logic would not be caught by Rust's type system the way a bug in the surrounding safe-Rust kernel code would be.
  5. The proposed fix — sandboxed/relative address calculation — would instead index into a fixed-size buffer using safe Rust slice indexing (which panics safely on out-of-bounds, and needs no unsafe), eliminating this specific gap.
⚠
Why this matters more than it sounds: this single mechanism is the entire reason the eBPF runtime doesn't yet meet the framekernel's own design goal. It's a small amount of code, but it's exactly the kind of small amount of code a framekernel exists to eliminate.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A colleague says "Asterinas now supports eBPF, so it has the same safety guarantees as the rest of the framekernel." What's wrong with that claim?
Show answer
The eBPF runtime currently requires unsafe Rust blocks to compute raw host addresses for its bounds checks, so that logic falls outside the framekernel's spatial-safety guarantees rather than being confined to ordinary safe Rust like the rest of the OS. The paper is explicit that this is a limitation, not a solved problem.Misconception: that "integrated into a memory-safe kernel" means "inherits full memory safety." Safety is a property of the specific code path, not something that spreads automatically by proximity.
Problem 2 · medium
Why does the hook live inside UdpSocket::send() in aster-bigtcp rather than somewhere inside smoltcp itself?
Show answer
aster-bigtcp is Asterinas's own thin wrapper around the third-party smoltcp stack. Placing the hook in the wrapper confines the integration entirely to code the Asterinas team owns and maintains, avoiding any modification to the external smoltcp codebase — lower maintenance burden and no fork to keep in sync.Misconception: that the hook placement was arbitrary. It's a deliberate boundary choice to avoid touching third-party code, mirrored on Linux's own layered hook placement (nf_hook at the IP layer, not inside the NIC driver).
Problem 3 · medium
The prototype implements BPF_PROG_LOAD and BPF_LINK_CREATE. Why are these specifically the two commands needed for the three test scenarios to work, no more?
Show answer
BPF_PROG_LOAD gets compiled bytecode from the user-space loader into the kernel; BPF_LINK_CREATE binds that loaded program to the UDP-egress hook so it actually executes. Together they cover the full path from "compiled binary on disk" to "running at the hook" — which is exactly what the accept/drop test scenarios exercise. Nothing about the tests needs maps or helpers, so those commands weren't needed yet.Misconception: that a "subset of the bpf() syscall" means an arbitrary or incomplete slice. It's the precise minimum slice needed for the paper's own validation, not a random partial implementation.
Problem 4 · hard
Why is safe JIT compilation described as a harder problem than the current interpreter, rather than just "the fast version of the same thing"?
Show answer
An interpreter's trust boundary is small and fixed: the interpreter code itself is written once and reviewed, and it merely decodes/dispatches instructions at runtime — the bytecode never becomes executable machine code. A JIT compiler instead generates new native machine code from untrusted bytecode and then executes it directly — so a bug in the code generator can let a malicious program produce native instructions that escape all the eBPF-level safety checks entirely. Making that code generator itself provably safe (without expanding the TCB) is a much larger verification problem than bounds-checking interpreted loads and stores.Misconception: that JIT is "the same logic, compiled." JIT introduces an entirely new class of correctness requirement — trusting a code generator — that interpretation avoids by construction.
Problem 5 · medium
The paper says hook contexts are allowed to diverge from Linux's, while the instruction set and bpf() syscall surface stay compatible. What's the practical consequence of this split?
Show answer
Existing eBPF toolchains (clang, llvm-objcopy, and the bytecode they produce) work unmodified against Asterinas, because the parts a compiler/loader cares about are kept compatible. But an eBPF program written against Linux's specific UDP-hook context struct would need to be rewritten for Asterinas, because that struct's exact layout and fields are implementation-specific and not part of any compatibility promise.Misconception: that "Linux ABI-compatible" means every eBPF program is drop-in portable. Compatibility is scoped to the syscall/bytecode layer, not to every hook-specific data structure.
Problem 6 · hard
Construct a bytecode pattern that the current two safety layers (static jump-bounds check + runtime memory bounds check) would fail to catch, illustrating why a full verifier still matters.
Show answer
An infinite loop with no out-of-bounds memory access anywhere in it: all jump targets stay within the bytecode (passes the static check), and it never touches memory outside its allocated region (passes the runtime check) — but it never terminates, hanging the kernel thread executing it forever. Neither implemented layer does termination checking, which the paper explicitly lists as a gap. A full verifier (like Linux's) statically proves loop bounds or restricts control flow to guarantee termination before the program ever runs.Misconception: that "bounds checking" is the whole safety story for eBPF. Memory safety and termination are separate properties; this prototype addresses the first but not the second.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1Is this a full eBPF implementation for Asterinas?▾
No — it's explicitly preliminary work: one hook point (UDP egress), two bpf() sub-commands, no maps or helper functions, interpreter-only execution, and no comprehensive bytecode verifier. The paper's contribution is demonstrating feasibility and identifying the open problems, not delivering a production-ready subsystem.
Q2What is Asterinas, in one line?▾
A Linux-ABI-compatible OS kernel written in Rust that confines almost all unsafe code to a small, audited "framekernel" core, so the rest of the OS is provably memory-safe by the Rust compiler.
Q3Why UDP, and why the send path specifically?▾
It's the smallest representative slice of "a packet-processing hook that needs a verdict": a single well-defined function (UdpSocket::send()) in a thin wrapper the authors own, mirroring Linux's well-known nf_hook() pattern on egress — a natural, low-risk first hook to validate the whole pipeline before adding more.
Q4Does the prototype support real Linux eBPF programs unmodified?▾
Yes, at the toolchain level: programs are written in C, compiled with standard clang, and converted with llvm-objcopy into standard eBPF binaries, then loaded through the custom bpf() syscall without any modification to that pipeline. What's Asterinas-specific is only the hook's context structure, which a program must be written against.
Q5What exactly is rbpf, and did the authors write it?▾
rbpf is a pre-existing, open-source Rust-based eBPF interpreter (by Quentin Monnet). The authors did not write the interpreter itself — they embedded it as Asterinas's in-kernel execution engine and built the surrounding syscall/hook integration around it.
Q6Why is the lack of a bytecode verifier a big deal if the runtime checks bounds anyway?▾
Runtime bounds checks catch bad memory accesses as they happen, but they don't prevent other classes of malicious or malformed programs — like ones that never terminate, or that are structured to probe/exploit the runtime's own unsafe bounds-check code. A real verifier rejects such programs before they ever execute; this prototype currently cannot.
Q7Are there any performance numbers in this paper?▾
No. It's a 3-page workshop paper reporting functional correctness (programs load, attach, and enforce verdicts correctly across three scenarios) on a QEMU VM — there's no throughput, latency, or overhead measurement, and JIT (needed for competitive performance) isn't implemented yet.
Q8What would "sandboxed address calculation" actually change?▾
Instead of computing a raw host pointer and manually verifying it's in-bounds (which needs unsafe), the interpreter would treat an eBPF program's memory as offsets into a fixed-size buffer, using ordinary safe-Rust slice indexing — which the compiler and runtime bounds-check automatically, with no unsafe block required. This is listed as future work, not yet built.
Q9Could this approach generalize to hooks other than networking?▾
Architecturally, yes — the pattern (context struct in, verdict out, enforced at a fixed kernel location) isn't networking-specific. The paper explicitly lists "additional hook points beyond UDP egress" as near-term future work, without committing to which ones.
Q10What's the single biggest open research question this paper leaves?▾
How to get safe JIT compilation — needed for eBPF to be performance-competitive — without reintroducing the same TCB-expansion problem the interpreter currently has, and ideally solving that problem for the interpreter too via safe address calculation.
