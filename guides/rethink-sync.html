Make it durable before anyone sees it, not before the call returns

A synchronous file system blocks every program until its data reaches the disk. Rethink the Sync keeps the same guarantee for whoever is watching the screen or the network, lets the program run ahead, and holds back only the output that depends on data not yet committed. The result, xsyncfs on Linux ext3, is as safe as a synchronous mount with write barriers and within a few percent of an asynchronous one.

Before you begin

Keep the synchronous guarantee, but give it to the person watching instead of the program calling

A 2006 paper from the University of Michigan: a Linux file system (xsyncfs, a modified ext3) that returns from every write at once, tracks which later output depends on data not yet on disk, and holds only that output back until the disk commit finishes.

⚡ TL;DR

  • Problem: a synchronous file system blocks the caller until each change is on disk, which made a small-file benchmark (PostMark) take about 1,661 s instead of about 8 s when the disk's cache is flushed properly. Asynchronous file systems are fast but let users see output (a "saved" message, a network reply) that depends on data a crash can still destroy. Worse, on the paper's 2006 Linux, even fsync and a synchronous mount only reached the drive's volatile 2 MB cache, and cutting power could corrupt ext3's journal.
  • Redefinition: an I/O is externally synchronous if nothing an outside observer sees (screen, network, the disk image after a crash) could distinguish it from synchronous I/O. A system call returning is internal to the computer, so the OS may return before the commit.
  • Mechanism: each write joins the current journal transaction and returns; the writing process gets a commit dependency on that transaction. Dependencies spread through pipes, files, UNIX sockets, other processes and shared memory (reusing the dependency tracking of the authors' earlier Speculator system). Output from a process with dependencies is buffered in the kernel and released when every transaction it depends on has committed.
  • When to commit: output-triggered commits. The file system waits (up to ext3's usual 5 s) until some buffered output or a blocked process depends on the active transaction, then commits at once. With nobody watching it batches for throughput; with someone watching it commits for latency.
  • Results (Pentium 4, one 7,200 rpm disk, ext3 journaled mode, write barriers for the durable configurations): PostMark within 7% of asynchronous ext3 and about 190× faster than synchronous ext3 with barriers; an Apache source build within 3%; MySQL running TPC-C 3× faster with one client than on ext3 with barriers, 22% with 20 clients; SPECweb99 throughput within 8% of asynchronous ext3 adding on average no more than 33 ms per request.
  • Limits: a process that never produces output can lose up to 5 s of work in a crash (as with asynchronous ext3); media errors surface after the program has moved on; dependencies are tracked on one machine only, so every network message waits for the disk; shared memory is handled conservatively.

Quick glossary
DurabilityA property of a completed update: it survives a later OS crash or power failure, meaning it is on non-volatile media when the crash happens.
OrderingA property of a sequence of updates: after any crash, if an update B that causally followed A is present, A is present too. It is separate from durability: both A and B may be lost, but never A alone lost with B kept.
Synchronous I/OA file system call that does not return to the calling program until its changes are committed to disk; defined by the paper as the usual "implementation" definition (the caller blocks).
Asynchronous I/OA file system call that returns once the change is in kernel memory; the kernel writes it to disk later (ext3: within about 5 s).
External synchronyThe paper's model: an I/O is externally synchronous if the computer's external output cannot be distinguished from output it could have produced had the I/O been synchronous.
External outputAnything that leaves the computer's internal state where an outside entity can observe it: bytes sent to the screen, the network or another external device, and (by the paper's definition) every disk commit, because a crash makes it visible.
CommitThe act that makes a file system transaction durable and atomic: in ext3, writing the transaction's blocks to the on-disk journal followed by a commit record; after the commit record is on the platter, recovery will apply the whole transaction.
Journal transaction (compound transaction)The unit ext3 commits: one in-memory set of modified blocks gathered from many file system operations, committed atomically. At most one is "active" (accepting changes) and at most one is "committing" at a time.
Group commitCommitting many updates with one disk commit, so the fixed cost of the commit (positioning, cache flushes) is shared among them.
Commit dependencyA kernel record linking some kernel state (a process, a pipe, a file, buffered output) to an uncommitted file system transaction whose data influenced it; the state is "uncommitted" while any such record remains.
Uncommitted (process or object)A process or kernel object that has one or more commit dependencies; its external output is buffered in the kernel.
Output-triggered commitxsyncfs's commit policy: commit the active transaction immediately when output (or a blocked process) depends on it, otherwise wait for ext3's 5-second timer or a full journal.
Drive (write) cacheVolatile memory inside the disk drive (2 MB on the test drive) that holds written sectors before they reach the platter; the drive reports a write complete when the data is in this cache and may write cached sectors to the platter in any order.
Write barrierA file system ordering point implemented, in the paper's port, by flushing the drive cache before and after writing each transaction's commit record, so that the commit record never reaches the platter before the blocks it vouches for.
fsyncA system call that asks the kernel to make one file's changes durable before returning; on ext3 it forces a commit of the current transaction.
SpeculatorThe authors' earlier kernel extension (SOSP 2005) that lets a process run ahead on a predicted result of a slow operation, tracking every kernel object the process influences and buffering its output until the prediction is confirmed.
Undo logSpeculator's per-object list of entries recording which speculations (here, commit dependencies) the object depends on and, in Speculator proper, how to undo changes; in xsyncfs it holds buffered output and dependency links but no undo data.
xsyncfsThe paper's externally synchronous file system: Linux ext3 (kernel 2.4.21) in journaled mode with write barriers, modified to report transactions to Speculator and to commit when Speculator reports buffered output.
Short primers (tap to open)
1Durability versus ordering, and the two kinds of crash▾

Durability answers "if the call said it finished, is the data still there after a crash?" Ordering answers "after a crash, can I see a later change without an earlier one?" They are independent. A system can lose the last five seconds of work but keep everything before that in order (ordered, not durable). Another can keep each change it acknowledged, but if two unacknowledged changes are in flight the later one may survive alone (durable for what was acknowledged, not ordered).

The paper uses Lamport's happens-before relation for "earlier": A happens before B if the same process did A first, or A's effects reached B through communication, or through a chain of such steps (general knowledge; the paper cites Lamport). Its ordering check in the power-cut test is concrete: after reboot, if a block of the file is present, every block written before it must be present too.

Two crash types matter. An OS crash (kernel panic) loses kernel memory but the disk keeps everything it has accepted, including its own cache, which it finishes writing. A power failure also loses the disk's volatile cache. Much of the paper's Section 4.2 is about that difference.

Now you're ready: "durable" always needs the qualifier "against which crash", and "ordered" is a separate promise that journaling alone does not make.
2What a disk's write cache does, and why it lies▾

A 2006 ATA disk (the test drive is a 7,200 rpm, 120 GB Western Digital with a 2 MB cache) accepts a write into its own DRAM and immediately reports "done". It then writes cached sectors to the platter in whatever order minimizes arm movement and rotation. One revolution at 7,200 rpm is 60 / 7,200 s = 8.33 ms, so waiting for the platter costs milliseconds, while writing into the cache costs microseconds (general knowledge).

Two consequences. First, a write the OS believes is on disk can vanish in a power failure. Second, writes the OS issued as A then B can reach the platter as B then A. The OS can force the issue with a cache flush command (wait until everything in the cache is on the platter) or by turning the cache off. Linux 2.6.11 added write barriers that do this around each journal commit; the paper ports them to its 2.4 kernel.

The paper's Figure 3 shows the effect: without barriers, ext3 is not durable on power failure in any mode, "even if fsync commands are issued by the application after every write", and in two runs a power cut corrupted file data or metadata including the superblock.

Now you're ready: every "sync" configuration in the evaluation is either "waits for the drive cache" (ext3-sync, fast but not durable) or "waits for the platter" (ext3-barrier, durable but slow).
3Journaling, and ext3's modes▾

A file system operation such as creating a file changes several blocks (a directory block, an inode, a bitmap). If a crash lands between those writes, the on-disk structure is inconsistent. A journal (write-ahead log) fixes this: first write the new contents of all the changed blocks to a separate log area, then a commit record saying "this transaction is complete", and only afterwards write the blocks to their home locations (checkpointing). After a crash, recovery replays every transaction whose commit record is in the log and ignores any without one (general knowledge of ext3's JBD layer).

ext3 batches the changes of many operations into one compound transaction and commits it every 5 seconds, on fsync, or when the journal is full. The paper describes two modes: ordered (the default; only metadata goes in the journal, and file data is written to its home location before the transaction's metadata commits) and journaled (data and metadata both go in the journal). ext3 also has a third, writeback mode, with no ordering for data at all (general knowledge; not in the paper).

ext3 uses value logging: "when a transaction commits, only the latest version of each block is written to the journal." A block changed 50 times in one transaction is logged once.

Now you're ready: a journal makes a group of changes atomic; it does not by itself make them durable when they are acknowledged, nor keep their order if the drive reorders the log writes.
4Commit cost, and why batching trades latency for throughput▾

A durable commit on a single disk needs at least one write that reaches the platter, plus (with barriers) cache flushes before and after the commit record. Each costs on the order of a revolution or more, so a commit takes milliseconds to tens of milliseconds whether it carries one small change or a thousand (general knowledge; the paper gives no per-commit time).

So there are two ways to run a disk-backed system. Commit each change alone: low latency for that change, terrible throughput when changes arrive faster than one per commit. Or wait and commit many together (group commit): high throughput, but each change waits for the batch. The paper: "Delaying a group commit in the hope that more modifications will occur in the near future can improve throughput by amortizing more modifications across a single commit. However, delaying a commit also increases latency."

A synchronous file system cannot batch the changes of one single-threaded program at all, because the program does not issue the second change until the first has committed.

Now you're ready: the paper's commit policy is a way of choosing, per transaction, between those two ends, using who is waiting as the signal.
5What "output" means here, and what does not count▾

The paper splits the system into the kernel and applications (internal) and the external interfaces: the screen, the network, "or other external device". Writing to a terminal, sending a packet to another machine, and (as a special case) committing to disk are external output. Writing into a pipe, a file in the page cache, a local UNIX socket, or another process's memory is not; those only change internal state, which the OS tracks instead.

A system call returning is the key thing that does not count. In the usual "application-centric" view the program is outside the OS and sees the return; in the paper's "user-centric" view the program is inside the box, and only what reaches a device can be seen.

The OS can enforce this because programs reach external devices only through it: "either directly by making a system call or indirectly by mapping an externally visible device."

Now you're ready: when the paper says output is "buffered", it means bytes headed for a terminal or the network sit in kernel memory, while the process that wrote them keeps running.
6Speculator in one page▾

Speculator (Nightingale, Chen and Flinn, SOSP 2005) was built to hide network round trips in distributed file systems. Instead of waiting for a server's answer, the client file system predicts it (for example, "my cached copy is still valid"), checkpoints the process with a copy-on-write fork, and lets it continue. If the prediction is confirmed, the checkpoint is discarded; if not, the process is rolled back and the operation retried.

To make that safe, Speculator tracks every kernel object a speculative process touches. A speculation object records what depends on one prediction; each touched object (a pipe, a file, another process) gets an undo log entry. Writing a pipe tags the pipe; reading the pipe tags the reader. Output a speculative process sends to the screen or network is buffered until its speculations are resolved, and a system call it cannot track makes the process block.

Rethink the Sync keeps the tracking and buffering and drops the predictions, checkpoints and rollback: a commit dependency is a "speculation" that is certain to come true unless the machine crashes.

Now you're ready: xsyncfs is ext3 plus about four hooks into Speculator: transaction created, modification added, transaction committed, and "output was buffered, please commit".
The whole story in one place

Move the wait from the program to the output

Synchronous file I/O gives the right guarantee to the wrong party. Give it to the observer, and the program never has to stop.

File systems have offered two models. A synchronous file system blocks the calling program until its change is committed to disk, so anything the program does afterwards (print "saved", send a reply) happens only once the data is safe, and changes reach the disk in the order they were made. It is also very slow: the paper measures disk-intensive benchmarks running up to two orders of magnitude slower. An asynchronous file system returns at once and writes later, so it is fast, but the user can see output that depends on data a crash will destroy, and programs that care must add fsync calls and build their own group commit. Almost every system defaults to asynchronous. On top of this, the paper shows that on its Linux 2.4 machine neither fsync nor a synchronous mount was durable against power failure, because the disk acknowledged writes from a volatile cache.

The paper's move is to ask who the guarantee is for. The usual definition is about implementation: the caller is blocked until the I/O completes. The paper defines it by observable behavior instead. The program is inside the computer; its state, including the fact that a system call returned, is visible to nobody. What people (or other computers) can observe is external output: the screen, the network, and the disk itself after a crash. So an I/O is externally synchronous if every external output has the same value, in the same causal order, as some execution in which that I/O had been synchronous.

That definition permits a different implementation. The write is validated and applied to the in-memory file system exactly as before, then added to ext3's current journal transaction, and the call returns without waiting. The process is marked with a commit dependency on that transaction. If it writes to the terminal or the network, the kernel buffers the bytes and lets the process keep running. If it passes information to another process through a pipe, a file, a UNIX socket or shared memory, the receiver inherits the dependency. When the transaction commits, the dependency is removed and buffered output whose last dependency is gone is released. If a process makes a system call whose effects cannot be tracked (an ioctl), it blocks until its data commits. This tracking already existed in the authors' earlier Speculator system, which did the same thing for speculative execution; xsyncfs strips out its checkpoints and rollback.

Two performance effects follow. First, a single program's many changes can be group committed as one atomic transaction, which a synchronous file system can never do because the program is stopped after the first change. Second, the system now knows when a commit matters. Until some output depends on the active transaction, committing it would change nothing anyone can see, so xsyncfs waits (up to ext3's usual 5 seconds) and batches. As soon as output is buffered, it commits at once. This output-triggered commit policy gives throughput when output goes to a file and low latency when a person is watching.

The implementation, xsyncfs, uses ext3's journaled mode (data and metadata both journaled, which is needed for ordering) and write barriers ported back from Linux 2.6, so its commits are durable even against power loss. It matches asynchronous ext3 within 7% on PostMark and 3% on an Apache build, is about 190 times faster than synchronous ext3 with barriers on PostMark, runs MySQL's TPC-C three times faster with one client than MySQL's own commits on ext3 with barriers (because it can batch one client's sequential transactions, which MySQL cannot), and adds on average no more than 33 ms to SPECweb99 requests. The price: a crash can still lose up to 5 seconds of work that nobody has seen, media errors are reported after the program has moved on, and every network message waits for the disk because dependencies are tracked on one machine only.

🍯 Key takeaways

  • Define synchronous I/O by what an outside observer can see, not by whether the caller blocked; a system call return is not observable.
  • Commits count as output (a crash exposes them), so they must also happen in causal order; ext3's journaled mode and one-at-a-time commits provide that.
  • Commit dependencies follow information from process to process through kernel objects; output carrying a dependency waits in the kernel, and untrackable calls block.
  • Once the program does not block, one program's changes can be group committed, and the commit can wait until someone would see the result (output-triggered commits).
  • Real durability needed write barriers: without them, ext3 lost acknowledged data and sometimes corrupted itself on power failure.
  • Measured: within 3 to 8% of asynchronous ext3; on PostMark about 15× faster than synchronous ext3 and about 190× faster than synchronous ext3 with barriers (read off Figure 4); 3× for single-client MySQL. Where computation or the network dominates, the gaps are smaller: synchronous ext3 is 46% slower on the Apache build and 6% faster on SPECweb99.
Six everyday pictures

How to think about external synchrony

Each stands alone. Every card ends with where the picture stops being true.

Output buffering · the program never stops

A live broadcast on a short delay

Live television is often aired a few seconds late so that something can be cut before viewers see it. The performers do not stop and wait; they keep going, and the station holds the picture. xsyncfs does the same with a program's terminal and network output: the program keeps running, and the kernel holds each line until the disk commit it depends on is done, so no viewer ever sees a claim the disk cannot back up.

Where it breaks: a broadcast delay is fixed and applies to everything; xsyncfs holds only output that carries a commit dependency, and only until that transaction commits, which output itself hurries along (M7, M15).
Commit dependencies · propagation through IPC

A news embargo that travels with the information

A reporter who has read an embargoed report may not publish until the embargo lifts, and anyone the reporter briefs is bound by the same embargo. In xsyncfs, a process that wrote uncommitted data is bound; a pipe it writes into is bound; a process that reads that pipe is bound; and each bound party's terminal or network output waits until the transaction commits, at which point all of them are released together.

Where it breaks: for shared memory the kernel cannot see who read what, so everyone with read access to the region is bound the moment a writer is, whether or not they looked (M18).
Group commit · output-triggered commits

A ferry instead of a taxi per passenger

A synchronous file system is a taxi for each change: one trip to the disk per write, and the program waits at the curb each time. xsyncfs is a ferry: changes board the current transaction, and the ferry leaves as soon as someone on the far bank is waiting to see a result, or every 5 seconds regardless. When nobody is waiting, the ferry fills up and the trip is cheap per passenger.

Where it breaks: there is only one ferry: if it is mid-crossing, the next load waits for it to return before leaving, so an urgent passenger can wait for up to two crossings (M12).
Volatile drive cache · write barriers

A mail clerk who says "sent" when it is in the outbox

You hand the clerk a letter and get "sent" back immediately, but it is only in the outbox, and the clerk mails the outbox in whatever order is convenient. If the building loses power, the outbox is emptied. The disk's 2 MB cache behaves this way: fsync on the paper's Linux 2.4 kernel stopped at the outbox. A write barrier is telling the clerk "mail everything in the outbox now, then mail this commit notice, then mail that too before you say sent."

Where it breaks: a clerk mailing out of order is merely late; a disk that puts a journal's commit record on the platter before the blocks it describes makes recovery install garbage, which the paper observed (M2, M14).
The user-centric view · what a crash may lose

A magician working behind a curtain

What happens behind the curtain does not matter, only what the audience sees when it opens. A program's internal state, including whether its last system call has returned, is behind the curtain. The curtain opens only for output to the screen or network, and the OS makes sure that anything shown then is already backed by the disk. The audience cannot tell whether the magician paused at each step.

Where it breaks: if the theater loses power before the curtain opens, the audience saw nothing wrong, but up to 5 seconds of unseen work is gone; a user who knows the program ran for those seconds may still be surprised (M5, M19).
Journaled mode versus ordered mode

A bound ledger versus loose receipts

A bound ledger records every entry, money and paperwork alike, in sequence, so a later entry can never exist without the earlier ones. Loose receipts filed in any order can leave next week's receipt in the drawer while last week's is lost. Journaled mode puts data and metadata into the log, in order; ordered mode journals only metadata and lets data blocks reach the disk in any order, so after a crash a later write (B) can be present without an earlier one (A).

Where it breaks: a ledger costs writing everything twice, so one would expect it to be slower; in the paper's benchmarks journaled mode was faster than ordered mode in every case (M13).

What "synchronous" meant on the paper's Linux, in one list
  • ext3 mounted async (default): every call returns from memory; ext3 commits if "the oldest modification in the transaction is more than 5 seconds old", on fsync, or when the journal is full.
  • ext3 mounted sync: "the writing process is blocked until its modifications are committed to the drive cache." Survives an OS crash; not a power cut.
  • fsync on either: on Linux 2.4, "commits data to the volatile hard drive cache rather than to the disk platter."
  • Write barriers: a Linux 2.6.11 option, not on by default, that flushes the drive cache "before and after writing each transaction commit record"; the authors ported it to their 2.4.21 kernel. Disabling the drive cache gives the same safety but was slower in every case they tried.

1 · Two models, and a durability gap underneath both

Synchronous I/O blocks the caller until its change commits, which gives durability and causal ordering and costs up to two orders of magnitude on disk-heavy work. Asynchronous I/O returns immediately and commits within about 5 seconds; it is fast but shows users output that a crash can contradict. Underneath both, on the 2006 test machines, the drive acknowledged writes from a volatile cache, so neither "sync" nor fsync survived a power cut, and a power cut could even corrupt ext3 because the drive put commit records on the platter before the data they covered (M1, M2).

2 · Redefine synchrony by what an observer can see

Treat the kernel and applications as internal and only the screen, network, other devices and disk commits as observable. An I/O is externally synchronous if the observable outputs have the same values in the same causal order as some synchronous execution. Because the file system still validates and applies each change in memory, programs get the same return values and so compute the same outputs; only the timing of commits and the release of output change. After a crash, the observer can never have seen anything that the restored disk contradicts (M3, M4, M5).

3 · Let the program run ahead: group commit, buffered output, commit dependencies

Each change joins the active transaction and the call returns. The process gets a commit dependency on that transaction; dependencies follow information through pipes, files, UNIX sockets, other processes and shared memory. Terminal and network output from a dependent process is buffered in the kernel and released when its dependencies are gone; calls that cannot be tracked block. The machinery is Speculator's, minus checkpoints and rollback. One program's changes can now share one commit (M6 to M11).

4 · The file system side: ext3 transactions, journaled mode, barriers, and when to commit

xsyncfs is ext3 with Speculator hooks. It uses journaled mode so that a causally later change can never commit before an earlier one, and write barriers so that commits are durable. It commits every 5 seconds like ext3, unless Speculator reports buffered output or a blocked process depending on the active transaction, in which case it commits immediately. sync and fsync become "attach a dependency" and return at once. Because the kernel sees both a database server and its local client, xsyncfs can group commit one client's sequential transactions, which the database itself cannot safely do (M12 to M17).

5 · The edges, and the evaluation

Shared memory and threads get conservative propagation (every reader inherits a writer's dependencies); a 5-second timer bounds how much unseen work a crash can lose; two file systems would need blocking between them; catastrophic media errors arrive after the program has moved on (M18 to M21). The evaluation runs a power-cut durability test, PostMark, an Apache build, MySQL TPC-C and SPECweb99, and compares output-triggered with eager commits (F1 to F9).

The problem

"File systems serve two opposing masters: durability and performance." Synchronous I/O gives "a clean abstraction" but "can degrade the performance of disk-intensive benchmarks by two orders of magnitude"; asynchronous I/O "is fast, but not safe." Defaults are asynchronous, and even explicit fsync on the paper's platform reached only the volatile drive cache.

The result

xsyncfs "provides the same durability and ordering guarantees as those provided by a synchronously mounted ext3 file system" (with write barriers), yet "even for I/O-intensive benchmarks, xsyncfs performance is within 7% of ext3 mounted asynchronously." Single-client MySQL TPC-C runs three times faster than on ext3 with write barriers.

  5. Build the file system (M12, M13, M14): ext3's transaction pipeline, journaled mode for ordering, write barriers for durability.
  6. Decide when to commit (M15, M16, M17): output-triggered commits; sync as a dependency; group commit across processes an application cannot see.
  7. Handle the edges (M18 to M21): shared memory and threads, the 5-second backstop, two file systems, media failure.
The central trade-offs
  • Throughput versus latency of commits: "Delaying a group commit in the hope that more modifications will occur in the near future can improve throughput ... However, delaying a commit also increases latency." Output-triggered commits pick per transaction, by whether output is waiting.
  • Precision versus cost of tracking: exact tracking through shared memory would need page protection and faults; the paper accepts over-propagation instead. Untrackable calls block.
  • Guarantee to observers versus guarantee to programs: a program learns of a failed write (or a crash's loss) later than under synchronous I/O, or never; the paper argues that the observer is who matters and handles media failure in the OS.
Effect of changes (whole design)
  • If the disk had a non-volatile cache or were flash with fast durable writes, the absolute cost of a commit drops and synchronous I/O's penalty shrinks; the paper still expects synchronous ext3 to be no faster than its volatile-cache bar, so buffering and group commit still help (Section 4.3). With very fast persistence the 7% tracking overhead becomes a larger share (inference).
  • If most output goes to the network (servers), every reply waits for a commit, and the benefit relies on many requests sharing a commit; SPECweb99 shows 33 ms added to small requests and 7% below asynchronous throughput (F7, F8).
  • If processes communicate through channels the kernel cannot see (device memory, user-level shared memory protocols), the design must either block them or over-propagate; correctness depends on the OS mediating every path to the outside (M3, M18).
  • If dependencies could cross machines (a distributed version), a reply to a local client could be released before commit as long as the client's own output is held; the paper does not do this (inference; see S for the NFS comparison).

M1 · Synchronous and asynchronous I/O: what each promises

TL;DR
ProblemPrograms need durability and ordering for some data; disks make every durable write cost milliseconds.
MechanismSynchronous: block the caller until its change commits. Asynchronous: return at once, commit within about 5 s, and offer fsync for programs that need more.
Trade-offSynchronous is simple and safe but up to two orders of magnitude slower; asynchronous is fast but lets users see output that a crash can contradict, and pushes durability work onto programmers.
Breaks whenSynchronous: a single-threaded program issues many small changes (each waits for its own commit). Asynchronous: a crash follows output that announced a change.
Key points
  • "A synchronous file system (e.g., one mounted with the sync option on a Linux system) guarantees durability by blocking the calling application until modifications are committed to disk."
  • For users: "Any file system operation they observe to complete is durable", that is, "data will not be lost due to a subsequent OS crash or power failure."
  • Ordering: "if one operation causally precedes another, the effects of the second operation are never visible unless the effects of first operation are also visible."
  • Cost: "blocking due to synchronous I/O can degrade the performance of disk-intensive benchmarks by two orders of magnitude."
  • Asynchronous: "This is fast, but not safe. Users view output that depends on uncommitted modifications." Programmers "must insert explicit synchronization operations such as fsync" and "must sometimes implement complex group commit strategies to achieve reasonable performance."
  • Defaults: "most local file systems provide an asynchronous I/O abstraction by default because synchronous I/O is simply too slow."
How it works, step by step: a mail program saves a message, then says "Message sent"
  1. Synchronous mount: write() of the message, then rename() into the outbox, each block until committed. With barriers each commit costs at least a revolution or two of a 7,200 rpm disk (8.33 ms each; general knowledge), so the message line appears tens of milliseconds later; the program does nothing in between.
  2. Asynchronous mount: both calls return in microseconds; "Message sent" appears at once. ext3 commits within 5 s. A power cut 2 s later loses the message although the user was told it was sent.
  3. Asynchronous mount plus fsync: the programmer adds fsync after the write and after the rename (the directory must be synced too, general knowledge). On the paper's Linux 2.4 without barriers, both return when the data is in the drive cache, so the power cut can still lose it (M2).
  4. Many messages: under the synchronous mount, 1,000 saves cost at least 2,000 commits in sequence; a mail server wanting throughput must write its own group commit to batch them (illustrative numbers).
Assumptions it relies on
  • A1. The caller is the party that needs the guarantee (implicit in the "implementation" definition the paper cites from Silberschatz and Galvin).
  • A2. A commit is expensive relative to the work between file operations (stated: "applications frequently block waiting for mechanical disk operations").
  • A3. "Committed to disk" means on stable media (implicit; false on the test platform, M2).
If an assumption changes
  • A1 changes (the guarantee is for whoever sees the output): the caller need not block, which is the paper's whole idea (M3).
  • A2 changes (commits are cheap, e.g. battery-backed RAM): synchronous I/O's penalty shrinks; the paper's related work lists Rio and Conquest, which give durability "only as long as the computer has power or the batteries remain charged."
  • A3 changes (the drive cache is volatile): synchronous I/O silently loses its promise on power failure, which is exactly what the paper measured (M2).
Design notes and rejected alternatives

The paper does not propose a new API: "No application modification is required." Transactions (QuickSilver, TABS, Locus, transactional file systems) give the same guarantees plus atomicity, "However, transactional systems typically require that applications be modified to specify transaction boundaries."

Connections

FFS: the paper's related work credits FFS and the original UNIX file system with introducing "a main memory buffer cache to hold writes until they are asynchronously written to disk"; FFS itself writes metadata synchronously for crash safety, the cost LFS later attacks (general knowledge, not in this paper). NFS: an NFS server must commit each write before replying, the synchronous model applied across a network (see S).

M2 · The volatile drive cache: why "synchronous" was not durable

TL;DR
ProblemThe disk reports a write complete when it is in its 2 MB volatile cache and writes cached blocks to the platter in any order.
Mechanism(Of the failure.) A power cut loses the cache; reordering can put a journal transaction's commit record on the platter before its blocks, and recovery then installs garbage.
Trade-offDefault systems keep the cache on and unflushed for speed; flushing it ("write barriers") or disabling it is safe but slow.
Breaks whenPower fails (not just the OS): ext3 without barriers loses acknowledged data in every mode, and sometimes corrupts data or metadata.
Key points
  • "on most desktop operating systems, even executing an explicit synchronization command such as fsync does not protect against data loss in the event of a power failure." "This behavior is not a bug, but rather a conscious design decision to sacrifice durability for performance."
  • "on fsync, the Linux 2.4 kernel commits data to the volatile hard drive cache rather than to the disk platter." MySQL therefore recommends disabling the drive cache.
  • "While MacOS X and the Linux 2.6 kernel provide mechanisms to explicitly flush the drive cache, these mechanisms are not enabled by default due to the severe performance degradation they can cause."
  • Measured (Section 4.2): "without write barriers, ext3 does not guarantee durability. This result holds in both journaled and ordered mode, whether ext3 is mounted synchronously or asynchronously, and even if fsync commands are issued by the application after every write."
  • Corruption: "In one experiment, a block in the file being modified was silently overwritten with garbage data. In another, a substantial amount of metadata in the file system, including the superblock, was overwritten with garbage." The machine "failed to reboot until the file system was manually repaired."
  • Cause: "the commit block for a transaction being written to the disk platter before all data blocks in that transaction are written to disk. Although the operating system wrote the blocks to the drive cache in the correct order, the hard drive reorders the blocks when writing them to the disk platter." Recovery then commits the transaction anyway: "Effectively, this overwrites disk blocks with uninitialized data."
  • Ordering also fails: "Journaled mode alone is insufficient to provide ordering since the order of writing transactions to the disk platter may differ from the order of writing transactions to the drive cache."
How it works, step by step: the paper's power-cut experiment
  1. Setup: "a test computer continuously writes data to its local file system. After each write completes, the test computer sends a UDP message that is logged by a remote computer."
  2. Cut power, reboot, compare the file system to the remote log. Durability fails if the log has a message for a write whose data is missing: "an external observer (the remote computer) saw output that depended on data that was subsequently lost."
  3. Ordering check: "for each block in the file, ordering is violated if the file does not also contain all previously-written blocks."
  4. Trials: four per configuration of Figure 3, "two in journaled mode and two in ordered mode."
  5. Outcome: durability only with write barriers; corruption twice without them; xsyncfs "provides both durability and ordering." (Full table in F3.)
Assumptions it relies on
  • A1. The drive's write cache is enabled and volatile (stated for the test drive: "2 MB on-disk cache"; the paper's results show it is volatile).
  • A2. The drive may reorder writes in its cache (stated: "the hard drive reorders the blocks").
  • A3. The OS does not flush the cache unless asked (stated: flush mechanisms "are not enabled by default").
If an assumption changes
  • A1 changes (cache disabled, or non-volatile): synchronous ext3 becomes durable. The paper tried disabling the cache: write barriers "were faster than disabling the drive cache since the drive cache improves read times and reduces the frequency of writes to the disk platter." With a non-volatile cache, barriers are unnecessary, but synchronous ext3 would still be "no better than the third bar in Figure 4" (ext3-sync).
  • A2 changes (drive writes in arrival order): no corruption from reordering, but a power cut still loses whatever was in the cache; journaling would then give ordering but not durability (inference).
  • A3 changes (flushes on by default): every fsync and every synchronous commit pays two flushes, which is the ext3-barrier configuration: about 1,661 s on PostMark versus about 132 s without barriers (read off Figure 4).
Design notes and rejected alternatives

The paper's evaluation consistently pairs "durable" with barriers: "we measured the performance of ext3 both using write barriers and with the drive cache disabled. In all cases write barriers were faster ... Thus, we report only results using write barriers." It does not argue against ext3-sync's speed; it shows that it buys speed by not being durable on power loss.

Connections

FFS and LFS: both assume a write the disk acknowledged is on the platter, in order; FFS's synchronous metadata writes and LFS's checkpoint ordering would both be undermined by this cache behavior (inference). Hints: an acknowledgment that is only a hint ("done, probably") is fine for performance and wrong for correctness, unless something checks it (inference). F2FS: a flash file system faces the same question one layer down, because flash devices also buffer writes in volatile memory and need explicit flushes for durability (general knowledge).

M3 · The user-centric view: what counts as observable

TL;DR
ProblemDefining synchrony by "the caller blocks" forces the program to wait even when nobody could see the difference.
MechanismTreat kernel and applications as internal state; only output to external devices is visible. A system call return is not an observable event.
Trade-offFrees the program to run ahead, in exchange for the OS having to see and hold every path to the outside.
Breaks whenA program can reach the outside without the OS noticing at the moment of output (for example through a mapped device), or the "user" is a program on the same machine that expects durability on return.
Key points
  • Two principles: "First, we define externally synchronous I/O by its externally observable behavior rather than by its implementation. Second, we note that application state is an internal property of the computer system."
  • "Synchronous I/O is usually defined by its implementation: an I/O is considered synchronous if the calling application is blocked until after the I/O completes."
  • Definition: "an I/O is externally synchronous if the external output produced by the computer system cannot be distinguished from output that could have been produced if the I/O had been synchronous."
  • Application-centric view: two partitions, "the kernel, which is considered internal state, and the user level, which is considered external state. Using this view, the return from a system call is considered an externally visible event."
  • "However, users, not applications, are the true observers of the computer system." The user-centric view "divides the computer system into three partitions, the kernel and applications, both of which are considered internal state, and the external interfaces, which are considered externally visible."
  • Enforceability: "The operating system can implement user-centric guarantees because it controls access to external devices." Applications reach them "either directly by making a system call or indirectly by mapping an externally visible device."
How it works, step by step: classifying the events of a make run
  1. gcc writes foo.o: internal (a file in the page cache). Not observable. The write returns without waiting.
  2. gcc exits, make's wait() returns: internal (process state). Not observable, but make has now observed gcc's state, so it inherits gcc's commit dependencies (M8).
  3. make prints "Linking foo" to the terminal: external output. It must not appear before foo.o's transaction commits, so the kernel buffers it.
  4. The journal commit of foo.o: also external output, because a crash would make it visible (M4). It must occur before the buffered line is released.
  5. The user's view: lines appear in the same order and with the same contents as under a synchronous mount, each a little after its data is safe (this walk-through is the guide's; the rules are the paper's).
Assumptions it relies on
  • A1. Every external output passes through the kernel at a point where it can be held (stated: the OS "controls access to external devices").
  • A2. Observers judge only by values and order of outputs, not by when the program's internal steps happened (implicit; the paper later concedes "temporal expectations", M19).
  • A3. Programs on the same machine are not observers in their own right; they are inside the box (stated by the three-partition view).
If an assumption changes
  • A1 changes (a process writes to a memory-mapped frame buffer or device): stores are invisible to the kernel. The safe option under Speculator's rule is to block when the kernel cannot transfer dependencies or buffer output; the paper names mapping a device as a path to the outside but does not say how xsyncfs handles one (inference).
  • A2 changes (observers care about timing): a user watching a progress bar sees bursts released at commit times; the 5-second timer limits how long unseen work can lag (M19).
  • A3 changes (a local program is the "observer", e.g. a test harness that kills the machine after write returns): it will find data missing after a crash; the guarantee was never made to it. The paper's own durability test uses a remote logger for exactly this reason (inference).
Design notes and rejected alternatives

The paper borrows the observer-based definition from fault tolerance: "Fault tolerance researchers have long defined consistent recovery in terms of the output seen by the outside world." It explains why the idea had not reached general-purpose I/O: in fault tolerance "the scope of recovery is the entire process", while general-purpose applications recover only their own I/O, so "it is feasible (though still slow) to issue each I/O synchronously"; and fault tolerance's standard "should lose no visible output", while general-purpose systems accept asynchronous I/O.

Connections

Leases: a lease bounds what a client may assume without asking; here the kernel bounds what an observer may assume without seeing (inference). Hints: the end-to-end flavor: guarantee what the endpoint (the user) can check, not what an intermediate layer sees (inference). x86 VMM and ESX: a virtual machine monitor sits in the same position as this kernel, between guest output and real devices, and could buffer a guest's network output the same way (inference; later systems such as Remus do, general knowledge).

M4 · The equivalence criterion: same values, same causal order, and commits are output

TL;DR
Problem"Indistinguishable from synchronous" needs a precise test, including what an observer can learn from the disk after a crash.
MechanismOutputs must have (a) the same values and (b) the same Lamport happens-before order as in a synchronous execution; disk commits count as outputs.
Trade-offPrecise and checkable, but it forces commits to happen in causal order and any output to wait for every commit it causally follows.
Breaks whenThe system can commit a later change before an earlier one (ordered mode, a reordering drive, two independent journals).
Key points
  • "We say that external output of an externally synchronous system is equivalent to the output of a synchronous one if (a) the values of the external outputs are the same, and (b) the outputs occur in the same causal order, as defined by Lamport's happens before relation."
  • "We consider disk commits external output because they change the stable image of the file system. If the system crashes and reboots, the change to the stable image is visible. Since the operating system cannot control when crashes occur, it must treat disk commits as external output."
  • In Figure 1(a) "there are three external outputs: the two commits and the message displayed on the screen."
  • Values: "The file system does all processing that would be done for a synchronous I/O, including validation and changing the volatile (in-memory) state of the file system, except that it does not actually commit the modification to disk before returning." So the program sees the same results and produces the same output.
  • Order: "if an external output causally follows an externally synchronous file I/O, then that output cannot be observed before the file I/O has been committed to disk. In the example, this means that the second file modification made by the application cannot commit before the first, and that the screen output cannot be seen before both modifications commit."
How it works, step by step: checking Figure 1(b) against the criterion
  1. Synchronous run's outputs: commit(M1) → commit(M2) → screen("done"), each happening before the next.
  2. Externally synchronous run's outputs: one atomic commit containing M1 and M2, then screen("done").
  3. Values: the screen shows the same bytes because both writes returned the same results (validated in memory first).
  4. Order: the atomic commit makes M1 and M2 visible together, so M2 is never visible without M1; the screen output comes after both. Every causal pair from step 1 is respected. The two commits are "fused" into one event, which an observer cannot distinguish from a crash-free synchronous run in which nothing was looked at between them (this reading of "fusing" is the guide's; the paper's justification is that "the commit is atomic").
  5. A violation for contrast: if M2 alone reached the platter and the machine crashed, the observer would see M2 without M1, which no synchronous run can produce.
Assumptions it relies on
  • A1. Programs are deterministic given the same system call results, so same results imply same outputs (implicit; nondeterminism such as timing or randomness would produce different outputs in any two runs, synchronous or not).
  • A2. Validation in memory catches every error a synchronous commit would report (stated as the design; media errors are the exception, M21).
  • A3. The stable image after a crash is the only way an observer sees commits (stated).
If an assumption changes
  • A1 changes (a program measures its own elapsed time and prints it): its output differs because writes return faster, but it would differ between two synchronous runs as well; "could have been produced" allows any legal synchronous timing (inference).
  • A2 changes (a write fails on the platter after validation): a synchronous system "could propagate such failures to the application", xsyncfs cannot; the paper notes ext3 itself did not detect such errors (M21).
  • A3 changes (an observer can read the disk while the machine runs, e.g. a shared SAN volume): commits become visible without a crash, which is still consistent with treating them as output; but the reader must not read uncommitted home locations (inference).
Design notes and rejected alternatives

The criterion is deliberately about outputs, not about states, and it explicitly includes the disk. That single choice is what rules out ordered mode (M13) and what forces a policy for two file systems (M20).

Connections

Eraser: Eraser checks a property (a consistent lockset) dynamically over a run; here the property is a causal order over outputs, enforced rather than checked (inference). LFS: LFS's roll-forward recovers a prefix of the log, which is a causal-order-preserving recovery in exactly this sense (inference).

M5 · What a crash loses, and why that matches a synchronous system

TL;DR
Problemxsyncfs returns from writes before they commit, so a crash loses changes the program thought were done. The design must show this is not visible as a broken promise.
MechanismOn reboot the disk holds every committed transaction, in order. Every output that was released depended only on committed transactions. So the observer's record matches a synchronous run that crashed at the last commit point.
Trade-offThe program's own work since the last commit (up to 5 s if it produced no output) is lost, more than a synchronous system would typically lose; no observer saw any of it.
Breaks whenAn observer can learn about the lost work through a path the kernel did not hold, or simply knows how long the program ran (the paper's "temporal expectations").
Key points
  • "An external observer never sees output that depends on uncommitted modifications. Since external synchrony commits modifications to disk in the order they are generated by applications, an external observer will not see a modification unless all other modifications that causally precede that modification are also visible."
  • "As defined so far, an externally synchronous file system could indefinitely delay committing data written by an application with no external output. If the system crashes, a substantial amount of work could be lost. Xsyncfs therefore commits data every 5 seconds, even if no output is produced."
  • Figure 3: "A 'Yes' indicates that the file system provides durability if an OS crash or power failure occurs", and xsyncfs gets "Yes" for both write and fsync, in the sense of the experiment: no remotely logged message ever referred to lost data.
  • The paper does not walk through a crash scenario step by step; the walk-through below is this guide's application of the stated rules.
How it works, step by step: what survives a power cut at time X
  1. Committed transactions (commit record on the platter, thanks to barriers): replayed by ext3 recovery; all present.
  2. The committing transaction, if its commit record did not reach the platter: discarded entirely by recovery. Output that depended on it was still buffered, so nobody saw a claim about it.
  3. The active transaction: in memory only; lost. Any output depending on it was buffered (and its existence had already triggered a commit of it, or would at the next commit opportunity).
  4. Buffered output in undo logs: lost with kernel memory. Because it was never released, the observer's record ends at the last released output, all of which depends only on committed data.
  5. Ordering: transactions commit one at a time in creation order, and journaled mode puts a causally earlier change in the same or an earlier transaction (M13), so the surviving state is a causal prefix.
  6. OS crash instead of power cut: the same reasoning; the drive keeps its cache, which only means some transactions that were mid-commit may survive (inference).
Assumptions it relies on
  • A1. Recovery applies exactly the transactions whose commit records are on the platter, all or nothing (implicit; ext3 journaling, general knowledge).
  • A2. Commits reach the platter in transaction order (stated: only one transaction commits at a time, with barriers).
  • A3. No released output depended on an uncommitted transaction (stated; enforced by M7 and M8).
  • A4. Observers do not count elapsed time as information (implicit; acknowledged as "temporal expectations").
If an assumption changes
  • A1 changes (a drive tears the commit record or reorders it, as without barriers): recovery can apply a partial transaction, producing states no synchronous run produces: the corruption of M2.
  • A2 changes (two transactions commit concurrently): a later one could survive without an earlier one, breaking the prefix property; ext3's "only one transaction may be committing at any given time" prevents this (M12).
  • A3 changes (a dependency path is missed, e.g. an untracked IPC): an observer can see output about data the crash then destroys, a real violation.
  • A4 changes (the user knows the job ran for 4 minutes and printed nothing): losing the last few seconds may surprise them; the 5-second timer caps it, as with asynchronous ext3 (M19).
Design notes and rejected alternatives

The paper could have made write's return the commit point (synchronous I/O) or never bounded the loss; it chose the observer as the commit point with a 5-second ceiling. A user-visible consequence the paper does not discuss: on reboot, the program's own log of what it had done may be ahead of the disk if that log lived in memory or on another machine through an untracked path (inference).

Connections

LFS: LFS's checkpoint plus roll-forward also recovers a causal prefix, losing whatever was written after the last segment reached disk (inference). NFS: an NFS client whose server crashes retries until the server replies; since the server committed before replying, nothing the client was told is lost. xsyncfs keeps that "nothing you were told is lost" property for its observers without the server-side blocking (see S).

M6 · Group commit: one program's changes in one atomic transaction

TL;DR
ProblemA synchronous file system pays a full commit per change, because a single-threaded program cannot issue its second change until the first has committed.
MechanismReturn from each call at once and add the change to ext3's active compound transaction; commit many changes with one atomic commit.
Trade-offCommit cost is shared and some writes vanish before reaching disk, in exchange for a crash losing the whole group (none of which anyone saw).
Breaks whenEvery change is followed immediately by output, so each transaction holds one change (SPECweb99 comes close; F9).
Key points
  • "First, the two modifications are group committed as a single file system transaction. Because the commit is atomic, the effects of the second modification are never seen unless the effects of the first are also visible."
  • Benefits listed: "the commit of all modifications is done with a single sequential disk write, writes to the same disk block are coalesced in the log, and no blocks are written to disk at all if data writes are closely followed by deletion."
  • "ext3 employs value logging", meaning "when a transaction commits, only the latest version of each block is written to the journal. If a temporary file is created and deleted within a single transaction, none of its blocks are written to disk."
  • "In contrast, a synchronous file system cannot group multiple modifications for a single-threaded application because the application does not begin the second modification until after the first commits."
  • Group commit becomes transparent: "programmers do not need complicated group commit strategies to achieve acceptable performance. Group commit is provided transparently by xsyncfs."
How it works, step by step: a compiler writes a temporary file, then the object file
  1. cc1 creates /tmp/cc123.s and writes 40 KB to it: the directory block, inode, bitmap and ten 4 KB data blocks join the active transaction T (illustrative sizes).
  2. as reads cc123.s (inheriting T, M8) and writes foo.o, 20 KB: five more data blocks, another inode, the same directory block again (coalesced: one copy in T).
  3. cc unlinks cc123.s: its blocks are freed in memory. Under value logging the freed data blocks need not be logged at all; the bitmap and directory blocks are logged once in their final state.
  4. Commit: one sequential journal write of the final versions of perhaps a dozen blocks, plus barriers. A synchronous mount would have committed each step separately and written the temporary file's data before deleting it.
  5. If the machine crashes before the commit: all of it is gone, atomically, and nothing that depended on it was shown (M5).
Assumptions it relies on
  • A1. The commit is atomic: all modifications in the transaction appear after a crash or none do (stated).
  • A2. A commit's cost is mostly fixed (positioning, flushes), not per byte (implicit; general knowledge).
  • A3. The program has more file system work to do before anyone looks (implicit; true for builds and PostMark, less so for request/response servers).
If an assumption changes
  • A1 changes (non-atomic batches): a crash could expose the second change without the first, breaking ordering; this is why grouping is tied to a journal transaction rather than just a write-back batch.
  • A2 changes (commit cost proportional to data): batching saves little; only coalescing and deletion-before-commit still help (inference).
  • A3 changes (output after every change): transactions shrink to one change each; the remaining benefit is that the program is not blocked while the commit runs (M7) and that changes made during a commit pile into the next one (M12).
Design notes and rejected alternatives

Group commit is not new; ext3 already did it for asynchronous I/O and the paper cites Cedar's "logging and group commit." What is new is getting it for a single synchronous program, which is possible only because the program no longer blocks.

Connections

LFS: the same amortization, batching many small writes into one large sequential write, applied to the whole file system rather than the journal (inference). Livelock: batching per interrupt to amortize fixed costs, at the price of latency, is the same trade-off (inference). vLLM: batching requests for throughput while bounding latency is a recurring scheduler problem (inference).

M7 · Buffering output instead of blocking: terminal, network, and calls that cannot be buffered

TL;DR
ProblemOutput that causally follows an uncommitted write must not be seen before the commit; blocking the program until then would waste its time.
MechanismWhen an uncommitted process sends bytes to the screen, the network or another external device, the kernel keeps them in the process's undo log and lets the process continue; it releases them when their last commit dependency is removed.
Trade-offThe program overlaps computation and more I/O with the commit, in exchange for kernel memory for held output and added latency for the observer (about one commit).
Breaks whenThe call cannot be held or tracked (an ioctl); then the process blocks until its data commits.
Key points
  • "The second optimization is buffering screen output. ... One way to enforce this ordering would be to block the application when it initiates external output. However, the asynchronous nature of the output enables a better solution. The operating system instead buffers the output and allows the process that generated the output to continue execution."
  • "If the process writes to the network, screen, or other external device, its output is buffered by the operating system. The buffered output is released only after all disk transactions on which the output depends commit."
  • "Any external output inherits the commit dependencies of the process that generated it", and the OS "buffers the output until the last dependency is resolved by committing modifications to disk."
  • Where it lives: "The output is buffered in the undo log" (Figure 2 discussion).
  • Latency: "In most cases, output is delayed by no more than the time to commit a single transaction", which "is typically less than the perception threshold of a human user."
  • Network: "Since xsyncfs only tracks causal dependencies on a single computer, it must buffer each message until the file system data on which that message depends has been committed."
How it works, step by step: three kinds of output from one uncommitted process
  1. Terminal: the process calls write(1, "done\n", 5) on a tty. The kernel sees the process is uncommitted, copies the 5 bytes into its undo log with the process's current dependency set, returns 5, and notifies xsyncfs (which commits; M15). The terminal shows nothing yet.
  2. Network: the process calls send() on a TCP socket to another host. Same treatment: the payload is held with the current dependencies. A reply to a web request therefore waits for the commit of anything the server process had written (SPECweb99: 33 ms on small requests, F8).
  3. Local IPC is not output: a write to a pipe or a UNIX-domain socket to a local process is not held; the receiving object is marked instead (M8). The paper switched its MySQL benchmark to UNIX sockets because this "allows xsyncfs to propagate commit dependencies between the client and server"; that suggests a loopback TCP connection was not tracked and would have been treated as output (inference).
  4. Untrackable call: an ioctl on a device might externalize something or move information in ways Speculator cannot follow, so the process blocks until its modifications commit; the block also triggers a commit.
  5. Release: when a transaction commits, each held output whose dependency set is now empty goes to its device. Within one process, later output has a dependency set at least as large as earlier output's until commits shrink it, and transactions commit in order, so held output is released in the order it was written (inference from the rules).
Assumptions it relies on
  • A1. Output is asynchronous from the program's point of view: a write to a terminal or socket needs only a byte count back, not confirmation of delivery (stated: "the asynchronous nature of the output").
  • A2. Every external output passes through a system call the kernel can intercept (implicit; M3's A1).
  • A3. Held output is small enough to keep in kernel memory for one commit (implicit; the paper gives no limit).
If an assumption changes
  • A1 changes (the program waits for an answer, e.g. a request to a remote server): the request is held until commit, so the program waits for the commit plus the round trip; buffering cannot hide the latency when the reply is needed to continue (inference; this is the SPECweb99 situation seen from a client).
  • A2 changes (output through a mapped device): nothing to intercept; the process would have to be blocked or denied the mapping while uncommitted (inference).
  • A3 changes (a process streams megabytes to the network between commits): held output grows with the commit interval times the output rate; but output itself triggers a commit, which bounds the interval to about one commit time (inference).
Design notes and rejected alternatives

Blocking at output is the rejected alternative, named in the paper. Blocking would still be correct and would still allow group commit of everything before the output, but it would stop the program from computing during the commit. Section 4.6 makes the network case explicit: since only one machine is tracked, every message to another machine is output and waits for the data it depends on.

Connections

Leases and NFS: an NFS server replies only after committing; xsyncfs would let the server compute the reply and hold only the packet (see S). Exokernel: the kernel's control of device access is what makes buffering possible; in an exokernel where applications drive devices more directly, a library OS would have to do this holding itself (inference). Dune: a process with direct access to hardware features (as in Dune) could bypass system-call interception, the A2 problem (inference).

M8 · Commit dependencies and their propagation rules

TL;DR
ProblemOutput from process Q may depend on data process P wrote, if information flowed from P to Q. The kernel must know which output waits for which transaction.
MechanismWriters get a dependency on the transaction; objects they modify get their dependencies; processes that observe those objects inherit them; output inherits its process's set; untrackable calls block.
Trade-offPrecise for system-call IPC and cheap (most of PostMark's 7% overhead), in exchange for conservative handling where flows are invisible.
Breaks whenInformation flows through a channel the kernel does not mediate; or dependencies are tracked too coarsely and hold output that did not need to wait.
Key points
  • "When a process writes to the file system, it inherits a commit dependency on the uncommitted data that it wrote."
  • "When a process with commit dependencies modifies another kernel object (process, pipe, file, UNIX socket, etc.) by executing a system call, the operating system marks the modified objects with the same commit dependencies."
  • "Similarly, if a process observes the state of another kernel object with commit dependencies, the process inherits those dependencies."
  • "If a process with commit dependencies executes a system call for which the operating system cannot track the flow of causality (e.g., an ioctl), the process is blocked until its file systems modifications have been committed."
  • "Any external output inherits the commit dependencies of the process that generated it."
  • Definitions: "a commit dependency represents the causal relationship between kernel state and an uncommitted file system modification. Any kernel object that has one or more associated commit dependencies is referred to as uncommitted."
  • Lifecycle: "When the file system commits the transaction to disk, the commit dependency is removed." "When the last commit dependency for a process is discarded, Speculator marks the process as committed."
  • IPC named in the introduction: "pipes, the file cache, or shared memory."
How it works, step by step: a shell pipeline sort big.txt > out.txt; grep x out.txt | wc -l
  1. sort writes out.txt: sort inherits a dependency on T (rule 1); out.txt's cached pages are part of T.
  2. sort exits; the shell's wait() returns: the shell observed sort's state (exit status) and inherits {T} (rule 3; process termination as an observation is the guide's reading of "observes the state of another kernel object").
  3. The shell forks grep and wc: children inherit the parent's dependencies (inference: a fork is the parent modifying a new process object, rule 2).
  4. grep reads out.txt (rule 3 again) and writes matches into the pipe (rule 2); wc reads the pipe (rule 3).
  5. wc prints "42" to the terminal: held with {T} (rule 5); the callback commits T; the user sees "42" a commit time later. If T was already committed when grep ran, no dependency is inherited and "42" appears at once.
Assumptions it relies on
  • A1. Processes interact only through the kernel (stated: "Speculator can track causal dependencies because processes can only interact through the operating system").
  • A2. Each system call's information flow is known: whether it modifies an object, observes one, or both (implicit; true for the calls Speculator handles, false for ioctl).
  • A3. Over-propagation is safe; under-propagation is not (implicit; any extra dependency only delays output).
If an assumption changes
  • A1 changes (shared memory): loads and stores bypass the kernel; the paper falls back to a conservative rule based on permissions (M18).
  • A2 changes (a call with unknown effects): blocking is the fallback; correctness holds, but the process loses the benefit and a commit is forced.
  • A3 changes (if output had to be released early for some reason, such as a heartbeat): any missed dependency becomes a visible violation; the design has no "release anyway" path (inference).
Design notes and rejected alternatives

Tracking is per kernel object, not per byte: once a pipe has a dependency, every reader of that pipe inherits it, even if the bytes it reads were written before the dependency arose (inference from object-level marking). This is coarse but cheap, and the paper reports that "the overhead of tracking causal dependencies in the kernel accounts for most of the difference" between xsyncfs and asynchronous ext3 on PostMark (about 7%).

Connections

Eraser: both instrument a running system to follow shared state, Eraser per memory word and lock, this per kernel object and transaction; both accept imprecision (Eraser's false alarms, xsyncfs's over-propagation) for low cost (inference). Mesa: monitors make shared-state access explicit; shared memory without system calls is the case this tracking cannot see (inference). Hints: Lampson's "When in doubt, use brute force" fits the fallback: block on any call you cannot classify (inference).

M9 · Speculator: the machinery being reused

TL;DR
Problem(Speculator's.) Distributed file system clients block on network round trips whose results are usually predictable.
MechanismPredict the result, checkpoint the process, run ahead; track every object the speculative process affects in undo logs; buffer its external output; roll back on a wrong guess.
Trade-offHides latency, in exchange for checkpoints (copy-on-write forks), undo data, and blocking on anything it cannot track.
Breaks whenPredictions fail often, or processes interact in ways that cannot be checkpointed (shared memory, multithreading).
Key points
  • "Rather than block during a remote operation, a file system predicts the operation's result, then uses Speculator to checkpoint the state of the calling process and speculatively continue its execution based on the predicted result. If the prediction is correct, the checkpoint is discarded; if it is incorrect, the calling process is restored to the checkpoint, and the operation is retried."
  • Two data structures: "A speculation object tracks all process and kernel state that depends on the success or failure of a speculative operation. Each speculative object in the kernel has an undo log that contains the state needed to undo speculative modifications to that object."
  • Pipe example: "if a speculative process writes to a pipe, Speculator creates an entry in the pipe's undo log that refers to the speculations on which the writing process depends. If another process reads from the pipe, Speculator creates an undo log entry for the reading process that refers to all speculations on which the pipe depends."
  • "Speculator ensures that speculative state is never visible to an external observer." Output is buffered "until the outcome of the speculation is decided"; a call it cannot handle "by either transferring causal dependencies or buffering output" blocks the process "until it becomes non-speculative."
How it works, step by step: Speculator's original use
  1. An NFS-style client opens a cached file; normally it would ask the server whether the cache is valid, one round trip (Speculator's SOSP paper; details general knowledge).
  2. Speculate: assume "still valid", create speculation S, checkpoint the process with a copy-on-write fork, return from open.
  3. Track: the process writes a pipe (pipe's undo log references S), another process reads it (its undo log references S), that process prints (output held under S).
  4. Resolve: the server's reply arrives. If valid, S is discarded with all checkpoints and the held output is released. If invalid, every process and object depending on S is restored from its undo log or checkpoint and the open is redone.
Assumptions it relies on
  • A1. The kernel mediates interaction (stated).
  • A2. Process state can be checkpointed cheaply with copy-on-write (stated: "copy-on-write fork").
  • A3. Speculations usually succeed (implicit in the design; the SOSP paper's premise, general knowledge).
If an assumption changes
  • A1 changes: same problem as M8; Speculator does not propagate speculative dependencies through shared memory at all, "due to the complexity of checkpointing at arbitrary states in a process' execution."
  • A2 changes (multi-threaded processes): "checkpointing multi-threaded processes for speculative execution is a thorny problem", so Speculator restricts what speculative processes may do.
  • A3 changes (frequent mis-speculation): rollbacks waste work; irrelevant for commit dependencies, which always "succeed" unless the machine crashes (M10).
Design notes and rejected alternatives

The key observation is that "speculation" and "not yet durable" have the same shape: state that must not leak to the outside until some event. Speculator releases output "based on correctness"; external synchrony releases it "based on durability."

Connections

NFS and Leases: Speculator's target was exactly the round trips NFS clients make to validate caches, which leases also aim to reduce (inference). x86 VMM: binary translation speculates that code will not change and must detect when it does; the same "run ahead, detect, undo" structure (inference).

M10 · From speculation to synchronization: stripping out checkpoints and rollback

TL;DR
ProblemSpeculator bundles tracking and buffering with checkpoint and rollback, which external synchrony does not need and which "come at a substantial performance cost."
MechanismFactor out the common functionality; let each file system choose the extra features it needs; for commit dependencies, keep the many-to-many links and buffered output but no checkpoints and no undo data.
Trade-offCheap propagation and support for more kinds of interaction (threads, shared memory), in exchange for being unable to roll a process back (for example on a media error, M21).
Breaks whenSomething does need undo, such as recovering an application from a failed write.
Key points
  • "Speculator ties dependency tracking and output buffering to other features, such as checkpoint and rollback, that are not needed to support external synchrony. Worse yet, these unneeded features come at a substantial performance cost."
  • "We modified the Speculator interface to allow each file system to specify the additional Speculator features that it requires. This allows a single computer to run both a speculative distributed file system and an externally synchronous local file system."
  • "before a process inherits a new speculative dependency, Speculator must checkpoint its state with a copy-on-write fork. In contrast, when a process inherits a commit dependency, no checkpoint is needed since the process will never be rolled back."
  • "Speculator maintains the same many-to-many relationship between commit dependencies and undo logs as it does for speculations and undo logs. Since commit dependencies are never rolled back, undo logs need not contain data to undo the effects of an operation."
  • Undo logs "only track the relationship between commit dependencies and kernel objects and reveal which buffered output can be safely released."
  • "This simplicity enables Speculator to support more forms of interaction among uncommitted processes than it supports for speculative processes."
How it works, step by step: what changes when process Q reads an uncommitted pipe
  1. Under speculation: before Q inherits speculation S, Speculator checkpoints Q (copy-on-write fork: copy the page tables, mark pages read-only, general knowledge); it adds an undo log entry with what is needed to restore Q; Q continues.
  2. Under external synchrony: Q's undo log gets an entry linking it to commit dependency D (for transaction T). No fork, no saved state.
  3. Resolution under speculation: either discard the checkpoint or restore Q from it.
  4. Resolution under external synchrony: T commits, D is removed from every undo log that references it; if Q has no remaining dependencies it is marked committed and any of its held output with no dependencies left is released.
Assumptions it relies on
  • A1. A commit dependency is always resolved positively, unless the machine crashes, in which case all volatile state is gone anyway (implicit; stated as "never rolled back").
  • A2. Both uses can share one kernel infrastructure with per-file-system feature flags (stated).
If an assumption changes
  • A1 changes (a commit can fail without a crash, e.g. a media error): there is nothing to roll back to; the paper considered adding checkpoints for exactly this and rejected it (M21).
  • A2 changes (a process depends on both a speculation and a commit): the paper says one machine can run both file systems but does not describe a process with both kinds of dependency; presumably its output waits for both conditions (inference).
Design notes and rejected alternatives

Using Speculator unchanged would have checkpointed a process with a copy-on-write fork "before a process inherits a new speculative dependency", that is, each time a writer or reader picked up a dependency on a new transaction, not on every write. The paper says only that the unneeded features "come at a substantial performance cost"; it does not quantify that cost, so the claim that the factoring is what keeps PostMark's overhead near 7% is this guide's inference.

Connections

Exokernel: separating mechanism (tracking, buffering) from policy (when to release: correctness or durability) is the exokernel's argument in miniature (inference). Superpages and ESX: copy-on-write is the same page-table trick those papers rely on; avoiding it per write matters for the same reason, TLB and page-table costs (inference).

The figure shows the worst case for latency: output b was produced just after T1 started committing, so b waits for the rest of T1's commit and then all of T2's. The introduction's "no more than the time to commit a single transaction" holds "in most cases"; this case takes up to two (inference from the one-committing rule; see M12).

M12 · ext3's transaction pipeline: one active, one committing

TL;DR
Problemxsyncfs needs well-defined units to attach dependencies to and a fixed commit order.
Mechanismext3 gathers modifications into a single active compound transaction; a commit starts on a 5 s age limit, fsync, or a full journal; while it commits, new modifications open the next active transaction, which waits for the commit to finish.
Trade-offCommits are atomic and strictly ordered, and work done during a commit is batched into the next, in exchange for output that arrives just after a commit starts waiting up to two commit times.
Breaks whenCommits are long (large transactions, slow flushes) and output arrives continuously: latency approaches two commit times.
Key points
  • "Modifications from many different file system operations may be grouped into a single compound journal transaction that is committed atomically. Ext3 writes modifications to the active transaction" and "at most one transaction may be active at any given time."
  • "A commit of the active transaction is triggered when journal space is exhausted, an application performs an explicit synchronization operation such as fsync, or the oldest modification in the transaction is more than 5 seconds old."
  • "After the transaction starts to commit, the next modification triggers the creation of a new active transaction. Only one transaction may be committing at any given time, so the next transaction must wait for the commit of the prior transaction to finish before it commits."
  • The journal was 400 MB "for both ext3 and xsyncfs."
  • The eager baseline (Section 4.7) exploits the same pipeline: "multiple modifications are grouped into a single file system transaction while the previous transaction is committing."
How it works, step by step: what triggers a commit in each configuration
  1. ext3 async: 5 s age, full journal, or an fsync (which here waits for the drive cache only).
  2. ext3 sync: effectively every operation, since each must be committed before returning; with one operation per transaction there is nothing to batch for a single-threaded program.
  3. ext3-barrier: the same, plus two cache flushes per commit.
  4. xsyncfs: 5 s age, full journal, or a Speculator callback (output buffered, or a dependent process blocked); sync/fsync do not trigger by themselves (M16).
  5. xsyncfs eager variant (evaluation only): "triggers a commit whenever the file system is modified", still batching whatever arrives during the current commit.
Assumptions it relies on
  • A1. One committing transaction at a time gives a total commit order (stated).
  • A2. The journal is large enough that "journal space is exhausted" rarely forces commits (implicit; 400 MB was chosen).
  • A3. A commit takes far less than the 50 ms perception threshold (implicit; the paper's latency claim depends on it).
If an assumption changes
  • A1 changes (concurrent commits): more throughput on devices with parallelism, but commit order would have to be enforced separately for ordering (M5) (inference).
  • A2 changes (small journal): commits are forced by space regardless of output, reducing batching; with PostMark-size workloads this would push xsyncfs toward the eager behavior (inference).
  • A3 changes (slow commits, e.g. large transactions with barriers): worst-case output delay of two commits could exceed what users notice; the paper's single-disk measurements keep it at tens of milliseconds.
Design notes and rejected alternatives

xsyncfs adds no new transaction mechanism; it reuses ext3's and adds three notifications to Speculator ("when a new journal transaction is created", when a modification is added, "and when the transaction commits") plus one new trigger. The worst-case "two commits" delay is a consequence the paper does not spell out (inference).

Connections

LFS: LFS's segment writes are also strictly sequential and one at a time, which gives its log a total order for roll-forward (inference). Livelock: a pipeline where new work queues behind work in progress; under heavy output the system stays in "always committing" mode, the analogue of eager commit (inference).

M13 · Journaled mode rather than ordered mode, for ordering

TL;DR
ProblemIn ext3's default ordered mode, data blocks are written in place in any order, so after a crash a causally later write B can be on disk while an earlier write A is not.
MechanismUse journaled mode: data and metadata of every operation go into the journal transaction before the operation completes, so B is in A's transaction or a later one.
Trade-offOrdering by construction, in exchange for writing data twice (journal, then home location; general knowledge). In the paper's benchmarks journaled mode was nonetheless faster than ordered mode.
Breaks whenThe drive reorders transactions in its cache, which barriers prevent (M14).
Key points
  • "In its default ordered mode, ext3 writes only metadata modifications to its journal. In its journaled mode, ext3 writes both data and metadata modifications."
  • "Xsyncfs uses journaled mode rather than the default ordered mode. This change guarantees ordering; specifically, the property that if an operation A causally precedes another operation B, the effects of B should never be visible unless the effects of A are also visible. This guarantee requires that B never be committed to disk before A."
  • "Since journaled mode adds all modifications for A to the journal before the operation completes, those modifications must already be in the journal when B begins (since B causally follows A). Thus, either B is part of the same transaction as A ... or the transaction containing A is already committed before the transaction containing B starts to commit."
  • "In contrast, the default mode in ext3 does not provide ordering since data modifications are not journaled. The kernel may write the dirty blocks of A and B to disk in any order as long as the data reaches disk before the metadata in the associated journal transaction commits. Thus, the data modifications for B may be visible after a crash without the modifications for A being visible."
  • Methodology: "we measured ext3 executing in both journaled and ordered mode. Since journaled mode executed faster in every benchmark, we report only journaled mode results."
How it works, step by step: the paper's argument, applied
  1. A completes (its write returns): in journaled mode all of A's modified blocks, data included, are already in the active transaction, say T1.
  2. B starts after A causally (same process later, or another process that inherited A's effects).
  3. Case 1: T1 is still active. B joins T1; the commit is atomic, so B is never visible without A.
  4. Case 2: T1 has started committing. B joins T2, which "must wait for the commit of the prior transaction to finish before it commits." On the platter (with barriers), T1's commit record precedes T2's.
  5. Ordered mode, by contrast: A's and B's data blocks are written back by the kernel "in any order as long as the data reaches disk before the metadata in the associated journal transaction commits", so a crash between those write-backs leaves B without A.
Assumptions it relies on
  • A1. All of an operation's modifications enter the transaction before the operation returns (stated for journaled mode).
  • A2. Transactions commit to the platter in order (stated for ext3's pipeline; needs barriers on a caching drive).
  • A3. Writing data twice costs less than the ordering problems it avoids (implicit; supported by "journaled mode executed faster in every benchmark").
If an assumption changes
  • A1 changes (data written outside the journal, as in ordered or writeback mode): ordering is lost for data, as the paper shows.
  • A2 changes (no barriers): "Journaled mode alone is insufficient to provide ordering since the order of writing transactions to the disk platter may differ from the order of writing transactions to the drive cache."
  • A3 changes (large sequential writes dominate): journaling data doubles the bytes written and could make journaled mode slower than ordered; the paper's benchmarks are small-file and metadata heavy (inference).
Design notes and rejected alternatives

Why journaled mode was faster is not explained in the paper. A plausible reason is that for workloads with many small synchronous writes, writing data sequentially into the journal is cheaper than seeking to each file's home blocks before the commit, as ordered mode requires (inference).

Connections

LFS: LFS takes journaled mode to its limit: the log is the only copy, so data is written once and always in order; the price is a cleaner (inference). F2FS: F2FS's checkpointing and its handling of fsync face the same ordering question for data versus metadata (inference). FFS: FFS ordered its metadata writes synchronously and let data go asynchronously, the same split that ordered mode makes (inference).

M14 · Write barriers, ported back to the 2.4 kernel

TL;DR
ProblemWithout flushing the drive cache, a commit is neither durable on power failure nor ordered on the platter (M2).
MechanismFlush the drive cache before and after writing each transaction's commit record; ported from Linux 2.6.11 to the 2.4.21 kernel Speculator runs on.
Trade-offTrue durability and ordering, in exchange for two synchronous flushes per commit, which xsyncfs pays per group rather than per operation.
Breaks whenThe drive ignores flush commands (general knowledge: some consumer drives have been reported to), or commits are so frequent that flushes dominate (eager commit with heavy output).
Key points
  • "In the Linux 2.4 kernel, durability can be ensured only by disabling the drive cache. The Linux 2.6.11 kernel provides the option of using write barriers to flush the drive cache before and after writing each transaction commit record."
  • "Since Speculator runs on a 2.4 kernel, we ported write barriers to our kernel and modified xsyncfs to use write barriers to guarantee that all committed modifications are preserved, even on power failure."
  • Cost: "Since write barriers synchronously flush the drive cache twice for each file system transaction, ext3's performance is over two orders of magnitude slower than that of xsyncfs" (PostMark, synchronous ext3 with barriers).
  • Barriers versus no cache: "In all cases write barriers were faster than disabling the drive cache since the drive cache improves read times and reduces the frequency of writes to the disk platter."
  • Result: "ext3 provides both durability and ordering when write barriers are combined with some form of synchronous operation (either mounting the file system synchronously or calling fsync after each modification)."
How it works, step by step: one commit with barriers
  1. Write the transaction's journal blocks (descriptor and logged blocks) to the drive; the drive caches them.
  2. Flush 1: wait until the drive has written its whole cache to the platter. Now every block of the transaction is durable.
  3. Write the commit record.
  4. Flush 2: wait until the commit record is on the platter. Only now is the transaction committed; xsyncfs tells Speculator, which removes dependencies and releases output.
  5. Cost per commit: two waits for the platter, each at least part of a revolution plus any queued data (8.33 ms per revolution at 7,200 rpm; general knowledge). Spread over a transaction of hundreds of operations it is negligible; per operation, as in ext3-barrier, it is ruinous: about 1,661 s versus 132 s on PostMark (read off Figure 4).
Assumptions it relies on
  • A1. The drive honors cache flush commands (implicit).
  • A2. Ordering between transactions follows from ordering within each (implicit: T2's journal blocks are written only after T1's second flush, because T2 cannot start committing earlier).
If an assumption changes
  • A1 changes (the drive lies about flushes): nothing in software can restore durability; the guarantee is only as good as the device (inference).
  • A2 changes (pipelined commits that overlap): the second flush of T1 would also have to precede T2's commit record, which the one-committing rule provides for free (inference).
Design notes and rejected alternatives

Disabling the drive cache was the alternative available on 2.4 and the one MySQL recommends; it was slower in every measured case. Non-volatile caches (Hitz et al.) remove the need for barriers, but the paper expects synchronous ext3 on such hardware to be "no better than the third bar in Figure 4," so xsyncfs would still help.

Connections

FFS: FFS's ordering of synchronous metadata writes assumes the disk writes them in issue order; a caching drive breaks that assumption the same way (inference). F2FS: later file systems, F2FS among them, issue explicit cache-flush or force-unit-access writes at commit points for the same reason (general knowledge, not in this paper).

M15 · Output-triggered commits: commit when someone is waiting to see

TL;DR
Problemext3's 5-second commits give throughput but could make a user wait 5 s for output; committing on every change gives latency but wastes throughput.
MechanismCommit every 5 s as ext3 does, unless Speculator reports that it buffered output from, or blocked, a process depending on the active transaction; then commit immediately.
Trade-offThroughput when nobody watches and latency when someone does, decided automatically, at the cost of the tracking needed to know who depends on what.
Breaks whenOutput is continuous (every transaction is "watched", so it behaves like eager commit) or arrives through an untracked path.
Key points
  • "Latency is unimportant if no external entity is observing the result. Specifically, until some output is generated that causally depends on a file system transaction, committing the transaction does not change the observable behavior of the system."
  • "If xsyncfs were to use the default ext3 commit strategy, disk throughput would be high, but the user might be forced to wait up to 5 seconds to see output. This behavior is clearly unacceptable for interactive applications."
  • "Speculator provides callbacks to xsyncfs when it buffers output or blocks a process that performed a system call for which it cannot track the propagation of causal dependencies (e.g., an ioctl)." "The receipt of a callback triggers a commit of the active transaction."
  • Adaptation: output to the screen means frequent commits; "If the user instead redirects the output to a file, xsyncfs optimizes for throughput by committing every 5 seconds." With tail watching the file, "Speculator would track the causal relationship through the kernel data structures from tail to the transaction."
  • Novelty claim: xsyncfs "is the first file system to use the causal relationship between file modifications and external output to decide when to commit data."
  • Measured benefit over eager commits (Figure 9): 14% PostMark, 2% Apache, 35% MySQL with 1 client, 11% with 20 clients, 0% SPECweb99.
How it works, step by step: the paper's three scenarios
  1. Output to the screen: each line printed by a process that depends on the active transaction causes a callback, which commits the transaction. The line appears after about one commit (up to two, M12). Changes between lines are batched.
  2. Output redirected to a file: the program's writes to that file are just more file system changes, not output. Nothing triggers early commits, so xsyncfs commits every 5 s, maximizing throughput. "the only event the user can observe is the completion of the application", and if that completion is visible (for example, the shell prints a prompt) it triggers a commit.
  3. tail -f on the file: tail reads the file (inheriting its dependencies, M8) and writes to the screen; that output is buffered and triggers a commit. The file system switches to latency mode only for as long as someone is watching.
  4. Blocked process: a dependent process that calls ioctl is blocked; the same callback commits the transaction so it is not stuck for up to 5 s.
Assumptions it relies on
  • A1. Output is the only reason latency matters (stated: "Latency is unimportant if no external entity is observing the result").
  • A2. The kernel knows, for each held output, which transaction it waits on (stated; M8 and M11).
  • A3. Output is intermittent for many workloads, so there is slack to batch (implicit; false for SPECweb99).
If an assumption changes
  • A1 changes (memory pressure or journal space also make delay costly): ext3's journal-full trigger still applies; dirty memory is also bounded by the 5 s timer (inference).
  • A2 changes (untrackable dependencies): the conservative path (blocking) also triggers a commit, so latency is still bounded.
  • A3 changes (output with nearly every change): output-triggered and eager converge; SPECweb99: 311 versus 312 Kb/s (Figure 9).
Design notes and rejected alternatives

The eager strategy is the alternative the paper measures; it "attempts to minimize the latency of a single operation", and "sacrifices the opportunity to improve throughput." A fixed short timer would be a third option; the paper does not test one. The combination of output buffering and causal tracking, used together to decide commit timing, is what the paper presents as its contribution over the fault-tolerance techniques it borrows.

Connections

Livelock: the Livelock paper switches from interrupts to polling under load; output-triggered commits switch from batching to prompt commits when someone is watching. Both are adaptive policies keyed on a signal from the outside (inference). Leases: a lease term is a fixed bound like the 5 s timer, while a callback (lease revocation on a write) is like the output trigger (inference).

M16 · Rethinking sync: a commit dependency instead of a disk write

TL;DR
ProblemOn a synchronous file system, sync, fsync and fdatasync are redundant, but on xsyncfs a user who types sync still expects it to finish quickly and mean something.
MechanismOn a synchronization call from the VFS layer, create a commit dependency between the caller and the active transaction and return; the caller's next visible event (its exit, its output) triggers the commit.
Trade-offThe call returns "almost instantaneous"ly, and the guarantee still holds for whatever the caller shows afterwards, in exchange for the caller not knowing when the disk write actually happened.
Breaks whenA program uses fsync's return to time something only the program sees (it gets no durability at return), or relies on fsync to flush data to a device another machine reads directly (inference).
Key points
  • "In a synchronous file system, such synchronization operations are redundant since ordering and durability are already guaranteed for all file system operations. However, in an externally synchronous file system, some extra support is needed to minimize latency. For instance, a user who types 'sync' in a terminal would prefer that the command complete as soon as possible."
  • "When xsyncfs receives a synchronization call such as sync from the VFS layer, it creates a commit dependency between the calling process and the active transaction. Since this does not require a disk write, the return from the synchronization call is almost instantaneous. If a visible event occurs, such as the completion of the sync process, Speculator will issue a callback that causes xsyncfs to commit the active transaction."
  • Programmers "do not need explicit synchronization calls to provide ordering and durability since xsyncfs provides these guarantees by default for all file system operations."
  • Figure 3: xsyncfs is durable "on fsync" in the same observer sense as on write.
How it works, step by step: a user types sync in a shell
  1. The sync process (which wrote nothing itself) calls sync(). xsyncfs gives it a dependency on the active transaction T, which contains everyone's recent changes.
  2. The call returns at once. The process exits.
  3. The exit is observed by the shell's wait(); the shell inherits {T} and prints its prompt. That prompt is output from a process depending on T, so it is held and triggers a commit.
  4. T commits (with barriers); the prompt appears. The user experiences sync as taking one commit time, and when they see the prompt, everything written before the sync is durable, exactly as with a real sync.
  5. The paper says the completion of the sync process is the visible event; the shell-prompt detail is this guide's reading of how that completion becomes output.
Assumptions it relies on
  • A1. The purpose of sync is to make later observations safe, not to make the return itself mean anything (implicit in the user-centric view).
  • A2. The active transaction contains all changes the caller could care about (implicit; earlier transactions are already committed or committing ahead of it).
If an assumption changes
  • A1 changes (a program calls fsync and then pulls power via an ioctl, or signals hardware): the ioctl is untrackable, so the process blocks until its dependencies commit; correctness holds (inference from the blocking rule).
  • A2 changes (a transaction is committing when sync is called): the dependency on the active transaction suffices, because it commits after the committing one (M12).
Design notes and rejected alternatives

Making sync force a commit immediately would also be correct and would cost one commit of latency inside the call; the paper prefers returning at once and letting the visible event trigger the commit, so a script that calls sync many times without output does not pay for many commits (the script example is inference).

Connections

NFS: NFS clients flush on close so that another client opening the file sees the data; on xsyncfs the analogous guarantee is to observers, not to the next opener (inference). Hints: keep the interface (synchronous semantics) and change the implementation, a recurring Lampson theme (inference).

M17 · Seeing past one process: group commit an application cannot do

TL;DR
ProblemA database server must make each transaction durable before replying, because it cannot know whether the client will show the reply to anyone. With one client, there is nothing to batch.
MechanismOn xsyncfs the server's commit and reply carry a dependency to the client (over a UNIX socket); only the client's eventual external output forces a commit, so several of the client's sequential transactions share one commit.
Trade-offUp to 3× throughput for one client, in exchange for client and server having to be on the same machine with tracked IPC.
Breaks whenThe client is on another machine (the reply is external output and waits for a commit) or many clients already give the server enough to batch (20 clients: +22%; 32: no gain).
Key points
  • "Of course, a hand-tuned strategy might offer better performance than the default policies provided by xsyncfs. However ... there are some instances in which xsyncfs can optimize performance when an application solution cannot."
  • "an application-specific commit strategy cannot determine the visibility of its actions beyond the scope of the currently executing process; it must therefore conservatively commit modifications before producing external messages."
  • "consider a client that issues two sequential transactions to a database server on the same computer and then produces output. Xsyncfs can safely group the commit of both transactions. However, the database server (which does not use output-triggered commits) must commit each transaction separately since it cannot know whether or not the client will produce output after it is informed of the commit of the first transaction."
  • Measured (Section 4.5): "With a single client, MySQL completes 3 times as many NOTPM using xsyncfs." "MySQL cannot benefit from group commit with a single client because it must conservatively commit each transaction before replying to the client."
How it works, step by step: two sequential transactions from one local client
  1. Client sends txn 1 over a UNIX socket. The server executes it, appends to InnoDB's log, and calls fsync.
  2. On ext3: fsync commits (with barriers) before returning; the server replies; the client sends txn 2; another commit. Two commits, in sequence, for two transactions.
  3. On xsyncfs: fsync gives the server a dependency on the active transaction T and returns (M16). The reply over the UNIX socket marks the socket, and the client inherits {T} when it reads (M8). The client sends txn 2 immediately; the server's log append joins T.
  4. The client produces output (prints a result, or sends to the network): it is held; the callback commits T, which contains both transactions. One commit for two transactions; the observer sees the result only after both are durable.
  5. With many clients: MySQL's own group commit batches across clients, so the advantage shrinks: 22% at 20 clients, none at 32.
Assumptions it relies on
  • A1. Client and server are on the same machine and communicate through tracked IPC (stated: "we modified the benchmark to use UNIX sockets").
  • A2. The client's output is infrequent relative to transactions (implicit; the benchmark client does not print per transaction, as far as the paper says).
  • A3. The data set fits in memory, so the disk does only log writes (stated: "creating a data set that fits completely in memory").
If an assumption changes
  • A1 changes (remote client): each reply is network output and waits for a commit, so per-client throughput falls back to one commit per transaction; batching then comes only from many clients, as in SPECweb99 (inference).
  • A2 changes (client prints after every transaction): each print triggers a commit; xsyncfs still avoids blocking the server, but batching per commit drops toward eager behavior: Figure 9's eager MySQL is 3,323 NOTPM with 1 client versus 4,498 output-triggered.
  • A3 changes (data set larger than memory): random reads compete with commits for the disk, and both systems slow; the relative gain is not measured (inference).
Design notes and rejected alternatives

The paper's general claim is modest: "a hand-tuned strategy might offer better performance." The specific advantage is information: the kernel can see that nobody outside has looked yet, which a single process cannot know. The measured conclusion: applications "that use a custom group commit strategy can benefit from external synchrony if the number of concurrent transactions is low to moderate."

Connections

Salus (the course's GPU-sharing paper): Salus runs every deep learning job on a GPU through one execution service, which can interleave iterations of different jobs, something no single job can arrange for itself; here the kernel plays that role because it sees client and server together (inference). The 10/29 outline's description of Salus as a durability system with pipelined commit refers to a different, 2013 Salus paper. Exokernel: the opposite philosophy: give the application the information and let it decide; here the OS has information the application cannot get (inference).

M18 · Shared memory, mapped files and threads: conservative propagation

TL;DR
ProblemLoads and stores to shared memory never enter the kernel, so it cannot see when one process reads another's uncommitted data.
MechanismAssume writers write and readers read continuously: when any process with write permission to a region inherits a dependency, every process with read permission inherits it at once. Same for memory-mapped files; within a process, all threads share every dependency.
Trade-offNo page faults or protection changes, in exchange for dependencies (and so delayed output) that were not strictly needed.
Breaks whenA large shared region links many otherwise independent processes; every output from any of them then waits for every writer's transaction.
Key points
  • "Speculator does not propagate speculative dependencies when processes interact through shared memory due to the complexity of checkpointing at arbitrary states in a process' execution. Since commit dependencies do not require checkpoints, we enhanced Speculator to propagate them among processes that share memory."
  • "when processes interact through shared memory regions, only the sharing and unsharing of regions is visible to the operating system. Thus, Speculator cannot readily intercept individual reads and writes to shared memory."
  • Rejected: "marking a shared memory page inaccessible when a process with write permission inherits a commit dependency that a process with read permission does not have", transferring dependencies on the resulting faults. "We felt this mechanism would perform poorly because of the time needed to protect and unprotect pages, as well as the extra page faults that would be incurred."
  • Chosen: "We make a conservative assumption that processes with write permission for a shared memory region are continually writing to that region, while processes with read permission are continually reading it. When a process with write permission for a shared region inherits a new commit dependency, any process with read permission for that region atomically inherits the same dependency."
  • "Speculator uses the same mechanism to track commit dependencies transfered through memory-mapped files." For threads, Speculator "is conservative when propagating dependencies for multi-threaded applications", in that "any dependency inherited by one thread is inherited by all."
  • The MySQL benchmark "measures the efficacy of xsyncfs's support for shared memory", because MySQL and the TPC-C client are multi-threaded.
How it works, step by step: a multi-threaded database and a shared buffer pool
  1. Thread 3 of the server appends to the log file: it inherits D. Under the thread rule, the whole server process (all threads) now has {D} (stated rule).
  2. A second process maps the server's shared buffer pool read-only (illustrative): it inherits {D} at that instant, by the permission rule.
  3. A different thread of the server replies over a UNIX socket to client A for a transaction unrelated to thread 3's: the reply carries {D} (over-propagation), so client A's next output waits for D's commit too.
  4. Effect on performance: waiting output triggers a commit sooner, and more processes are tied to the same commit; correctness is never at risk, since extra dependencies only delay release (inference).
  5. Measured: MySQL on xsyncfs still beats MySQL on ext3 with barriers at every client count up to 20 (F6), so over-propagation did not cancel the gain there.
Assumptions it relies on
  • A1. Over-propagation is harmless to correctness (implicit).
  • A2. Sharing relationships are few and coarse enough that the extra waiting is tolerable (implicit; MySQL result supports it).
  • A3. Mapping and unmapping are visible to the kernel (stated).
If an assumption changes
  • A1 changes: it does not; but if output had deadlines (a heartbeat must go out every 100 ms), unnecessary dependencies could miss them (inference).
  • A2 changes (a system-wide shared segment, e.g. a large shared cache used by many daemons): any writer's file system activity delays every reader's output; the system tends toward one big dependency set (inference).
  • A3 changes (memory shared through a device or user-level RDMA): the kernel cannot see the sharing at all; such processes would have to be blocked or excluded (inference).
Design notes and rejected alternatives

The rejected page-protection scheme is exact and is the kind of mechanism Speculator could not use for speculation either. The paper chose cost over precision because, for commit dependencies, imprecision costs only latency. Section 3.5 says commit dependencies make multi-threaded tracking "substantially simpler" than checkpointing threads, which was "a thorny problem."

Connections

Eraser: Eraser instruments every shared-memory access in software to see what the kernel here cannot; it pays a large slowdown for that precision (inference). ESX: content-based page sharing and write protection are the same page-table tools as the rejected design (inference). Mesa: threads in one address space share everything, which is why the paper gives all threads one dependency set (inference).

M19 · The 5-second backstop: bounding unseen loss

TL;DR
ProblemTaken literally, external synchrony lets a program with no output go forever without a commit; a crash would then lose all its work.
MechanismCommit at least every 5 seconds even without output, the same interval ext3 uses when mounted asynchronously.
Trade-offCaps unseen loss at about 5 s of work, in exchange for some commits nobody needed (slightly less batching for long silent jobs).
Breaks whenA user's expectation is tighter than 5 s, or the job is so write-heavy that 5 s of changes is a lot of data to redo.
Key points
  • "Another limitation of external synchrony is that the user may have some temporal expectations about when modifications are committed to disk."
  • "As defined so far, an externally synchronous file system could indefinitely delay committing data written by an application with no external output. If the system crashes, a substantial amount of work could be lost."
  • "Xsyncfs therefore commits data every 5 seconds, even if no output is produced. The 5 second commit interval is the same value used by ext3 mounted asynchronously."
  • ext3's rule, which xsyncfs keeps, is age based: a commit when "the oldest modification in the transaction is more than 5 seconds old."
How it works, step by step: an overnight simulation that writes checkpoints and prints nothing
  1. Without the backstop: only journal-full commits would occur; with a 400 MB journal that could be minutes or hours of work (inference).
  2. With it: a commit whenever the oldest uncommitted change reaches 5 s, so at most about 5 s plus one commit time of changes is in memory at any moment.
  3. Power fails at 3:00 am: the disk holds everything up to the last commit, less than about 5 s old. The same bound as asynchronous ext3, with the difference that nothing the user saw claimed more.
  4. PostMark's case: its whole run takes about 8.7 s on xsyncfs and produces no output until the end, so the timer fires about once or twice (worked example ⑥).
Assumptions it relies on
  • A1. Users already accept asynchronous ext3's 5 s window for unseen work (implicit, by matching it).
  • A2. A commit every 5 s costs little throughput (implicit; true for these workloads).
If an assumption changes
  • A1 changes (a user expects 1 s): the interval is a parameter; shortening it trades throughput for a smaller window (inference).
  • A2 changes (very large transactions): a 5 s transaction with barriers could take long enough that output arriving during it waits noticeably (M12) (inference).
Design notes and rejected alternatives

The paper treats this as a limitation of the definition, not a bug in the implementation: the definition says nothing about time. The fix is pragmatic and matches the existing default.

Connections

LFS: LFS also checkpoints periodically (every 30 s in Sprite LFS; LFS paper) to bound roll-forward work, a similar time bound on what recovery must handle (connection; the 30 s figure is from the LFS paper, not this one). Leases: a time bound standing in for a guarantee the system cannot otherwise make (inference).

M20 · Two file systems, one process: blocking to keep commits in order

TL;DR
ProblemEach file system has its own journal; a change to file system 2 that causally follows a change to file system 1 could commit first.
Mechanism(Proposed.) Map each dependency to its file system; before a process modifies a second file system, block it until its dependencies on the first have committed.
Trade-offSimple and correct, in exchange for blocking processes that alternate between file systems; a shared journal or two-phase commit would avoid the block at much higher complexity.
Breaks whenA workload ping-pongs between two file systems (for example, compiling from one disk to another), paying a commit per switch.
Key points
  • "A final limitation of external synchrony is that modifications to data in two different file systems cannot be easily committed with a single disk transaction."
  • "Potentially, we could share a common journal among all local file systems, or we could implement a two-phase commit strategy. However, a simpler solution is to block a process with commit dependencies for one file system before it modifies data in a second."
  • "Speculator would map each dependency to a specific file system. When a process writes to a file system, Speculator would verify that the process depends only on the file system it is modifying; if it depends on another file system, Speculator would block it until its previous modifications commit."
  • The conditional wording ("would") suggests this was a design rather than a measured implementation; the paper does not say it was built.
How it works, step by step: cp /home/a.txt /mnt/usb/ on two externally synchronous file systems
  1. The shell earlier saved /home/a.txt; cp reads it and inherits a dependency on Thome (M8).
  2. cp is about to write /mnt/usb/a.txt: it depends on a different file system, so it blocks; the block also triggers a commit of Thome (M15).
  3. Thome commits; cp now has no dependency on /home and proceeds, inheriting Tusb.
  4. Why it matters: commits are external output (M4). If Tusb could commit before Thome, a crash could leave the copy on the USB disk while the original edit on /home is lost: the effect without its cause.
Assumptions it relies on
  • A1. Each file system commits independently (stated).
  • A2. Cross-file-system writes are rare enough that blocking is acceptable (implicit).
If an assumption changes
  • A1 changes (one shared journal): no blocking needed; both changes can be in one transaction (the paper's first alternative).
  • A2 changes (frequent alternation): each switch costs a full commit with barriers; such a process runs at synchronous speed (inference).
Design notes and rejected alternatives

Two-phase commit and a shared journal were named and set aside as more complex. Note that the rule as stated only checks dependencies when a process writes; a process that depends on file system 1 and only reads file system 2 is not blocked, which is fine because reading creates no commit on file system 2 (inference).

Connections

NFS: mounting a remote file system adds a third party whose commits xsyncfs cannot order at all; its writes are network output and are held (inference).

M21 · Catastrophic media failure: the error arrives after the program moved on

TL;DR
ProblemA write can be validated in memory and then fail on the platter; with external synchrony the program has already continued and cannot be told through the return value.
Mechanism(Of the paper's position.) Leave it to the OS: panic, or preferably write the data elsewhere. Checkpointing every process with Speculator so it could be rolled back was considered and rejected.
Trade-offKeeps external synchrony simple and fast, in exchange for application-specific recovery from media failure being harder.
Breaks whenAn application relies on a write error code to take a recovery action.
Key points
  • External synchrony "complicates application-specific recovery from catastrophic media failure because the application continues execution before such errors are detected."
  • "Although the kernel validates each modification before writing it to the file cache, the physical write of the data to disk may subsequently fail. While smaller errors such as a bad disk block are currently handled by the disk or device driver, a catastrophic media failure is rarely masked at these levels."
  • "Theoretically, a file system mounted synchronously could propagate such failures to the application. However, a recent survey of common file systems found that write errors are either not detected by the file system (ext3, jbd, and NTFS) or induce a kernel panic (ReiserFS)."
  • "An externally synchronous file system could propagate failures to applications by using Speculator to checkpoint a process before it modifies the file system. If a catastrophic failure occurs, the process would be rolled back and notified of the failure. We rejected this solution because it would both greatly increase the complexity of external synchrony and severely penalize its performance."
  • "it seems best to handle them in the operating system, either by inducing a kernel panic or (preferably) by writing data elsewhere."
How it works, step by step: the journal area develops a bad region mid-commit
  1. The program's write succeeded (validated, in memory, in T) and it printed "saved" (held).
  2. T's commit fails on the platter. The printed line must not be released, because the data is not durable.
  3. Options the paper names: panic (the held output is lost with memory; the observer saw nothing false) or write T elsewhere and complete the commit, then release the output.
  4. On a synchronous ext3 of the time: per the cited survey, the error would often go undetected, so the program would be told "success" anyway; so in practice the synchronous mount's theoretical advantage was not realized (this guide's reading of why the paper cites the survey).
Assumptions it relies on
  • A1. Media failures are rare and catastrophic, not routine (stated: small errors are masked by the disk or driver).
  • A2. Applications are not the best place to handle them (stated as the authors' view: "it is unclear that catastrophic failures are best handled by applications").
If an assumption changes
  • A1 changes (frequent write failures, as on worn flash): the OS must be able to redirect writes reliably, or held output piles up; the flash translation layer usually handles this below the file system (inference).
  • A2 changes (an application with its own replication wants the error): it would need a synchronous path; the paper does not offer one (inference).
Design notes and rejected alternatives

The rejection of checkpointing is consistent with M10: the whole performance story depends on not checkpointing on every write.

Connections

Hints: "end-to-end" error handling versus handling in a lower layer, a classic Lampson-style trade-off (inference).

L · Stated limitations and future work

What the paper itself says
  • Catastrophic media failure: the application "continues execution before such errors are detected"; checkpoint-and-rollback was rejected for complexity and performance (M21).
  • Temporal expectations: without output, commits could be delayed indefinitely; fixed with a 5 s commit interval (M19).
  • Two file systems: cannot be committed in one transaction; a shared journal or two-phase commit is possible, blocking is proposed (M20; described with "would").
  • Single computer: "xsyncfs only tracks causal dependencies on a single computer", so every network message is buffered until its data commits (Section 4.6).
  • Untrackable calls block the process (Section 2.3); shared memory propagation "might transfer dependencies when not strictly necessary" (Section 3.5).
  • Hand tuning: "a hand-tuned strategy might offer better performance than the default policies provided by xsyncfs" (Section 3.4); MySQL gains only "if the number of concurrent transactions is low to moderate."
  • Future directions, by implication: other journaling file systems ("external synchrony could improve the performance of synchronous I/O with other journaling file systems such as JFS or ReiserFS"), flash file systems ("it is likely that xsyncfs could also improve performance for flash file systems"), and hybrid NVRAM systems.
What the evaluation does not cover (this guide's list)
  • Output latency for interactive use is asserted ("output appears promptly") but not measured for the Apache build; only SPECweb99 has latency numbers.
  • PostMark is small: about 8.7 s on xsyncfs with 1 GB of RAM and a 400 MB journal, so only one or two timer commits occur and much of the data may never be written before deletion; a longer or larger PostMark run would weigh commit cost more (inference; Worked Example ⑥).
  • Memory cost of held output and of dependency tracking is not reported; nor is the tracking overhead broken out beyond "most of" PostMark's 7%.
  • Heavy shared-memory workloads with many processes (where over-propagation would bite) are not measured; MySQL is one server process plus a client.
  • A remote database client is not measured; the MySQL gain depends on UNIX sockets on one machine.
  • OS crashes are covered only by Figure 3's table; the power-cut experiment's four trials per configuration are a small sample for a probabilistic failure such as drive reordering.
  • One disk model, one kernel version (2.4.21); no RAID, no SSD, no non-volatile cache (argued about but not measured).
  • The two-file-system rule is not evaluated (it may not be implemented).
  • Mapped devices and GUI stacks (an X server writing to a mapped frame buffer) are not discussed, although the paper names mapping a device as a path to the outside (Section 2.1).

S · Side by side: NFS's synchronous server writes and external synchrony

The NFS paper (10/22) is the course's clearest example of the application-centric guarantee. Its rule, from the NFS paper: "Because the NFS server is stateless ... when servicing an NFS request it must commit any modified data to stable storage before returning results." Rethink the Sync does not discuss NFS; the comparison is this guide's.

That is close to what the SPECweb99 experiment measures for a web server.

C · Connections to the other CS240 papers (mechanical only)

  • FFS (background for 10/27): cited by this paper as one of the "early file systems" that "introduced the use of a main memory buffer cache to hold writes until they are asynchronously written to disk"; FFS kept metadata consistency by writing metadata synchronously in a careful order, the cost that journaling (and this paper's group commit) amortizes (inference for the second half).
  • NFS (10/22): synchronous server writes before replying; see S.
  • Leases: a lease bounds staleness by time, as the 5 s timer bounds unseen loss; a callback on conflict is like the output trigger (inference).
  • LFS (10/27): cited by this paper as adding "a write-ahead log to enable fast, consistent recovery"; LFS's segment writes are group commit for the whole file system, and its 30 s checkpoints bound recovery like the 5 s timer (inference).
  • F2FS (11/5): a flash file system where fsync cost dominates many workloads; this paper predicts "it is likely that xsyncfs could also improve performance for flash file systems" (the F2FS link is inference).
  • Eraser: dynamic tracking of shared state, with imprecision accepted for cost (M8, M18; inference).
  • Mesa: threads sharing memory are why all threads of a process share one dependency set (M18; inference).
  • Livelock: adaptive batching under load, and per-event fixed costs amortized by batching (M6, M15; inference).
  • Superpages and ESX: page protection and copy-on-write are the tools behind the rejected shared-memory scheme and Speculator's checkpoints (M10, M18; inference).
  • x86 VMM: a monitor sits between guest output and devices and could buffer output the same way; later systems such as Remus do (general knowledge; inference).
  • Exokernel and Dune: giving applications direct device or hardware access removes the kernel's ability to intercept output, the assumption M3 and M7 rely on (inference).
  • Salus (11/17, GPU sharing): keeps each job's small persistent memory resident and switches jobs only at iteration boundaries, when ephemeral memory is free: a split between state that must survive a switch and state that need not, as xsyncfs splits state that must survive a crash (anything an observer saw) from state that need not (inference). The 10/29 outline's "strong durability and ordering with pipelined commit" describes a different, 2013 Salus paper, not the course's.
  • vLLM: batching for throughput under a latency budget (M6; inference).
  • Hints: keep the interface, change the implementation; use a safe fallback (block) when in doubt; end-to-end placement of guarantees (M3, M8, M16; inference).
Follow the numbers

Worked examples

Seven calculations from the paper's own numbers. Chart values are read off the PDF's vector drawing (approximate); anything not in the paper is labeled.

① PostMark: checking "within 7%", "an order of magnitude" and "two orders"

Figure 4, read off: ext3-async 8.12 s, xsyncfs 8.67 s, ext3-sync 132.1 s, ext3-barrier 1,661 s. Figure 9 gives xsyncfs as 8.668 s.

  1. xsyncfs versus async: 8.67 / 8.12 = 1.067, so 6.7% slower: "within 7%".
  2. ext3-sync versus xsyncfs: 132.1 / 8.67 = 15.2×: "over an order of magnitude slower", even though ext3-sync is not durable on power failure.
  3. ext3-barrier versus xsyncfs: 1,661 / 8.67 = 192×: "over two orders of magnitude".
  4. Cost of barriers alone: 1,661 / 132.1 = 12.6× between the two synchronous configurations, the price of two cache flushes per commit.
  5. Per operation (illustrative): PostMark's run is roughly 40,000 file system operations (10,000 creates, 10,000 transactions of two operations each, about 10,000 final deletes; PostMark's structure is general knowledge, the count is approximate). 1,661 s / 40,000 ≈ 42 ms per operation with barriers, about five revolutions of a 7,200 rpm disk; 132 s / 40,000 ≈ 3.3 ms without.
🍯
The same ext3 code spans a 200× range on one benchmark depending only on when it is allowed to return; xsyncfs sits at the fast end while keeping the slow end's guarantee.

② Apache build: separating I/O from computation with RAMFS

Figure 5 totals, read off: ext3-async 106.2 s, xsyncfs 109.4 s, ext3-sync 159.9 s, ext3-barrier 1,287.7 s, RAMFS 101.6 s.

  1. Computation floor: RAMFS does no disk I/O, so about 101.6 s is computation and memory work. The paper: RAMFS is "only 8%" faster than xsyncfs (109.4 / 101.6 = 1.077).
  2. I/O time per configuration = total − 101.6: async 4.6 s, xsyncfs 7.8 s, sync 58.3 s, barrier 1,186.1 s.
  3. Ratios of I/O time: sync / xsyncfs = 58.3 / 7.8 = 7.5× (the paper's "7.5 times"); barrier / xsyncfs = 1,186 / 7.8 = 152× ("over two orders of magnitude").
  4. Whole-run ratios: 1.46× and 11.8×. Amdahl's law shrinks a 7.5× I/O slowdown to 46% because I/O is only about 7% of xsyncfs's run.
  5. A gap the headline hides: xsyncfs's I/O time is 7.8 / 4.6 = 1.7× async's. "Within 3%" is true of the whole run, not of the I/O part (this guide's arithmetic).
💡
Isolating I/O with RAMFS is how the paper shows its Apache ratios match PostMark's; the same subtraction exposes xsyncfs's own overhead relative to async.

③ MySQL with one client: proving the transactions share commits

Figure 6, read off: 1 client, xsyncfs 4,499 NOTPM, ext3 async with barriers 1,298. Paper: total transactions ≈ 2 × NOTPM. Figure 9: eager xsyncfs 3,323.

  1. Transactions per second: ext3: 2 × 1,298 / 60 = 43.3/s, so 23.1 ms each. xsyncfs: 2 × 4,499 / 60 = 150/s, so 6.7 ms each. Eager xsyncfs: 2 × 3,323 / 60 = 111/s, 9.0 ms each.
  2. One revolution at 7,200 rpm is 8.33 ms (general knowledge). A durable commit with barriers needs at least one platter write and two flushes, so it cannot complete in less than a good fraction of a revolution, and typically takes more.
  3. On ext3: 23.1 ms per transaction is consistent with one barrier commit per transaction, each a few revolutions; MySQL "must conservatively commit each transaction before replying."
  4. On xsyncfs: 6.7 ms per transaction is less than one revolution, so transactions cannot each be getting their own commit; several share one (inference from the arithmetic, consistent with the paper's explanation).
  5. Ratio: 4,499 / 1,298 = 3.47, which the paper reports as "3 times".
🍯
A throughput above one transaction per revolution, from a single sequential client, is direct evidence of group commit across that client's transactions, which MySQL itself cannot do.

④ Where the speedup comes from: not blocking, then deferring

Combine the slowest durable configuration (ext3-barrier) with Figure 9's eager and output-triggered xsyncfs. Eager commits as soon as anything changes, so its gain over ext3-barrier comes from the program not blocking.

  1. PostMark: 1,661 s → eager 9.879 s (168×) → output-triggered 8.668 s (another 1.14×).
  2. Apache: 1,287.7 s → eager 111.41 s (11.6×) → output-triggered 109.42 s (another 1.02×).
  3. MySQL, 1 client: 1,298 → eager 3,323 NOTPM (2.56×) → output-triggered 4,498 (another 1.35×).
  4. MySQL, 20 clients: 3,326 → eager 3,646 (1.10×) → 4,052 (another 1.11×).
  5. Reading: with eager commits, changes made while one commit is in flight pile into the next transaction, because nothing waits for them; that pipelining gives the large factor. Output-triggered deferral adds 2 to 35% (this guide's decomposition; the paper reports the two steps separately, not this way).
💡
The paper's title idea (move the wait from the program to the output) is worth two orders of magnitude on PostMark; the commit-timing policy is a refinement. Both rely on the same dependency tracking.

⑤ SPECweb99: what 33 ms means, and why eager and output-triggered tie

Figure 8 latencies (seconds) and Figure 7 throughputs (read off). Section 4.6: about 150,000 file system transactions in a 45-minute run.

  1. Added latency per bucket: 0.097 − 0.064 = 33 ms; 0.180 − 0.150 = 30 ms; 1.094 − 1.084 = 10 ms; 10.072 − 10.253 = −181 ms.
  2. Relative: +52%, +20%, +0.9%, −1.8%. The fixed delay matters only for small requests.
  3. Throughput: xsyncfs 310.4 versus async 334.6 (−7.2%), sync 329.4 (sync is 6.1% faster), barrier 291.0 (xsyncfs 6.7% faster).
  4. Rate of file system transactions: 150,000 / (45 × 60 s) = 55.6 per second, one every 18 ms. With replies (output) going out continuously, nearly every transaction has a waiting observer, so a commit is almost always pending, the regime where eager and output-triggered behave alike (Figure 9: 312 versus 311).
🍯
When output is continuous, external synchrony degenerates gracefully into "commit back to back, never block the server"; the 7% throughput cost is what is left.

⑥ How many commits does PostMark get on xsyncfs?

PostMark on xsyncfs runs 8.668 s (Figure 9), "does not generate any output" until it reports, and xsyncfs commits when the oldest change is 5 s old, on output, or when the 400 MB journal fills.

  1. Timer commits: the first change is at about t = 0, so the first timer commit starts at about 5 s. The next transaction's oldest change is at about 5 s, so its timer would fire at about 10 s, after the run ends.
  2. Output commit: PostMark's final report is output that depends on the last transaction, so it triggers one more commit.
  3. Total: about two commits, plus any forced by a full journal (the paper does not report journal usage). ext3-sync and ext3-barrier commit for essentially every operation, tens of thousands of times.
  4. Consequence: files that PostMark creates and deletes within the same transaction never reach the disk at all (value logging), so part of PostMark's I/O simply disappears under xsyncfs and async ext3 alike (inference).
💡
PostMark at this size mostly measures in-memory file system work plus one or two big commits; a run lasting minutes would weigh commit cost more, though the paper's ratios would still favor batching (inference).

⑦ From "at most 33 ms" to a commit time (a simple model)

Model, not from the paper: commits run back to back (as in ⑤), each taking C. A reply that becomes dependent at a random moment waits for the rest of the current commit (C/2 on average) plus its own transaction's commit (C).

  1. Average wait = C/2 + C = 1.5 C. Worst case = 2 C (M12).
  2. Set the average to the measured 33 ms: C ≈ 33 / 1.5 = 22 ms.
  3. Sanity check: a barrier commit needs two flushes plus the journal write; at 8.33 ms per revolution, 22 ms is about 2.6 revolutions, plausible for two flushes on a single disk (general knowledge).
  4. Worst case under this model: 2 C ≈ 44 ms, still under the 50 ms threshold the paper cites, but close to it.
🍯
The paper's "no more than the time to commit a single transaction" describes the typical case; the guaranteed bound is two commits, and on this disk both are tens of milliseconds.
Test yourself

Practice problems

Try each before opening the answer. Each answer ends with the misconception it checks.

Problem 1 · easy
On the paper's Linux 2.4 test machine, an application on ext3 calls write and then fsync, and fsync returns. Power fails one second later. For which configurations in Figure 3 is the data guaranteed to be there after reboot?
Show answer
Only "Synchronous with write barriers" and "External synchrony" (for xsyncfs, in the observer sense: nothing that was shown depended on data that is missing). Asynchronous and synchronous ext3 without barriers are both "Not on power failure" on fsync: the data may still be in the drive's 2 MB volatile cache.Misconception: that fsync returning means the data is on the platter. On this platform it meant "in the drive cache"; durability needed write barriers or a disabled cache.
Problem 2 · easy
Which of these are external output in the paper's user-centric view? (a) write() to a pipe; (b) printf to a terminal; (c) a UDP packet to another host; (d) write() to a file on xsyncfs; (e) the return of a write() system call; (f) a journal transaction's commit record reaching the platter.
Show answer
(b), (c) and (f). Terminal and network output reach external devices; disk commits are treated as output "because they change the stable image of the file system", which a crash makes visible. (a) and (d) modify kernel objects, which the OS tracks instead of holding; (e) is a change to application state, which is internal.Misconception: that a system call return is something the user sees. In the user-centric view only output to external devices (and commits) is observable.
Problem 3 · easy
ext3 already does group commit. Why can a synchronously mounted ext3 not group commit the changes of a single-threaded program, while xsyncfs can?
Show answer
On a synchronous mount the program blocks in each call until that call's change commits, so it cannot issue its second change while the first is pending; each transaction holds one change. On xsyncfs each call returns at once, so the program issues many changes that accumulate in the active transaction and share one commit. The paper: "the application does not begin the second modification until after the first commits."Misconception: that group commit is a property of the file system alone. It needs several changes to be pending at once, which blocking prevents.
Problem 4 · medium
Process P writes /data/x (transaction T5, uncommitted), then writes "x saved" into a pipe. Process Q reads the pipe and sends the line to a remote logging server. Process R, unrelated, reads /etc/hosts (last changed a week ago) and prints it to the terminal. Which outputs are held, and what triggers T5's commit?
Show answer
P depends on T5 (it wrote). The pipe is marked with {T5} when P writes it. Q inherits {T5} when it reads the pipe. Q's network message is external output with {T5}, so it is held; holding it triggers the Speculator callback, which commits T5 immediately. R has no dependencies (/etc/hosts is committed data), so its terminal output goes out at once.Misconception: that all output is delayed under xsyncfs. Only output from processes that causally depend on uncommitted data waits.
Problem 5 · medium
A process overwrites block 1 of a file (A), then block 2 (B). The machine crashes before anything is known to be committed. List the possible states of the two blocks after recovery under ext3 ordered mode and under journaled mode with barriers.
Show answer
Ordered mode: data blocks are written in place "in any order", so any combination is possible: neither, A only, B only, or both. B-only violates ordering. Journaled mode with barriers: A's data is in the journal before write returns, B is in the same or a later transaction, and transactions commit in order, so only neither, A only, or both.Misconception: that any journaling mode gives ordering. Ordered mode journals only metadata; an overwrite changes no metadata worth journaling, so nothing orders the two data writes.
Problem 6 · medium
A long compile prints progress to the terminal. The user reruns it with output redirected to build.log, then, halfway through, starts tail -f build.log in another window. How does xsyncfs's commit frequency change across these three phases?
Show answer
Terminal phase: each progress line is held output depending on the active transaction, so commits happen frequently (latency mode). Redirected phase: writes to build.log are file system changes, not output; nothing triggers early commits, so xsyncfs commits every 5 s (throughput mode). With tail -f: tail reads the uncommitted log, inherits its dependencies, and its terminal output is held, triggering commits again. The paper describes exactly these cases in Section 3.3.Misconception: that redirecting output to a file makes it "output". Only bytes headed to an external device count; a file write is internal until someone displays it.
Problem 7 · medium
On xsyncfs, a user types sync. How long does the sync() call take, and how long until the shell prompt reappears? When the prompt appears, is everything written before sync durable?
Show answer
The call is "almost instantaneous": xsyncfs only attaches a dependency on the active transaction to the calling process. The process exits; the shell observes the exit, inherits the dependency, and its prompt is held output, which triggers a commit. The prompt appears after about one commit (up to two), and yes, at that point everything in that transaction (and all earlier ones) is on the platter.Misconception: that a fast sync means a broken sync. The guarantee moved from the call's return to the next thing the user sees.
Problem 8 · medium
Process W maps a shared region read-write; process R maps it read-only but has not read it for an hour. W writes a file (uncommitted) and so inherits dependency D. R then prints "hello". Is R's line held? Would it be under the page-protection scheme the paper rejected?
Show answer
Under the chosen rule, yes: "When a process with write permission for a shared region inherits a new commit dependency, any process with read permission for that region atomically inherits the same dependency." R has {D}, so "hello" waits for D's commit. Under the rejected scheme, R would inherit D only on an actual read (a page fault), so "hello" would go out immediately; that precision was rejected because protecting pages and taking faults "would perform poorly."Misconception: that conservative propagation can produce wrong output. It can only delay output; correctness is unaffected.
Problem 9 · hard
Assume every commit takes 20 ms and commits are triggered immediately by output. A process prints a line that depends on the active transaction 2 ms after another transaction started committing. How long is the line held? What if no transaction was committing?
Show answer
Only one transaction may be committing at a time, so the active transaction waits for the current commit's remaining 18 ms, then takes its own 20 ms: 38 ms. With nothing committing, the commit starts at once: 20 ms. The worst case approaches two commit times (40 ms).Misconception: taking "output is delayed by no more than the time to commit a single transaction" as a bound. The paper says "in most cases"; the pipeline rule allows nearly two.
Problem 10 · hard
From Figure 5's totals (ext3-async 106.2 s, xsyncfs 109.4 s, ext3-sync 159.9 s, ext3-barrier 1,287.7 s, RAMFS 101.6 s), compute the I/O-only slowdowns of ext3-sync and ext3-barrier relative to xsyncfs, as the paper does. Then compute xsyncfs's I/O time relative to ext3-async.
Show answer
Subtract RAMFS: xsyncfs 7.8 s, sync 58.3 s, barrier 1,186.1 s, async 4.6 s. sync / xsyncfs = 7.5×, barrier / xsyncfs = 152×, matching "7.5 times" and "over two orders of magnitude". xsyncfs / async = 1.7×: in I/O time alone, xsyncfs costs about 70% more than async, which "within 3%" of total time does not show.Misconception: that a small whole-run overhead means a small overhead on the part being changed. Computation dilutes it (Amdahl).
Problem 11 · hard
A process edits /home/notes.txt (uncommitted, file system 1) and then copies it to /backup/notes.txt (file system 2). Both are externally synchronous with separate journals. Without the paper's proposed rule, what crash outcome becomes possible, and why does it violate the equivalence criterion? What does the rule cost?
Show answer
File system 2 could commit the backup before file system 1 commits the edit. A crash between the two commits leaves the new text in /backup while /home has the old version: the effect without its cause. Commits are external outputs, and this pair of outputs appears in an order no synchronous run produces. The rule blocks the process before it modifies file system 2 until its file system 1 changes commit (the block also triggers that commit), so the copy pays one commit's latency.Misconception: that ordering only matters within one file system. The criterion is about all outputs of the computer, and every disk commit is one.
Problem 12 · hard
A program performs writes w1 and w2, prints "2 done", then performs w3, w4, w5 and computes silently. Power fails 3 s after "2 done" appeared. What is on the disk after reboot, what did the user see, and which synchronous execution has the same observable history?
Show answer
"2 done" triggered a commit of the transaction holding w1 and w2 and was shown after it committed. w3 to w5 went into the next transaction; with no further output, it would commit only when its oldest change reached 5 s, which had not happened. After reboot: w1 and w2 on disk, w3 to w5 lost. The user saw "2 done" and nothing else. A synchronous run that committed w1, w2, printed "2 done", and crashed while blocked in w3's commit leaves the same disk and the same screen.Misconception: that xsyncfs never loses acknowledged writes. It loses writes whose only acknowledgment was a system call return, which no observer saw; up to about 5 s of them.

What Rethink the Sync teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make. Facts about other systems are general knowledge.

Visibility and durability are different events, and the contract decides which one a caller waits for

The paper separates "the program has been told" from "the data is on stable media" and makes only externally visible events wait for the second. Persistent-memory programming has the same split one level down: a store is visible to other cores once it is in the cache, durable only after a cache-line write-back and a fence, and persistency models (strict, epoch, buffered) differ exactly in which of those a later event must wait for (general knowledge). External synchrony is a buffered model whose ordering points are I/O to devices. When a new memory tier makes durable writes slow, the same question comes back: what must actually wait for durability, and what only needs to look as if it did?

Every cache in the path needs an explicit definition of "done"

The paper's most practical result is that "synchronous" ext3 was not durable because the drive acknowledged writes from a volatile 2 MB cache, and that reordering in that cache corrupted the journal. The same trap exists wherever a device acknowledges from volatile buffering: SSD DRAM caches, controller write-back caches, CPU write-combining and store buffers (general knowledge). A flush or barrier is a contract between layers, and the paper shows what happens when the upper layer assumes it without asking: a commit record on the platter vouching for blocks that are not.

Most of the win comes from not stalling; the policy is a refinement

Figure 9's eager variant still beats synchronous ext3 with barriers by 168× on PostMark, and output-triggered commits add 14% on top (Worked Example ④). That is the store-buffer story: let the producer continue, let later writes coalesce behind the one in flight, and enforce order only at fences. A processor's store buffer drains at a fence; xsyncfs's transactions drain when output depends on them. The decomposition is worth remembering when evaluating any "decouple the writer" design: measure the pipelining and the deferral separately.

Track at the granularity you can observe cheaply, and over-approximate elsewhere

System calls are cheap to intercept, so dependencies through pipes, files and sockets are tracked per object. Loads and stores are not, so shared memory gets a permission-based over-approximation instead of page-fault tracking. Coherence directories make the same choice with coarse sharer vectors, and taint-tracking systems with page-level tags (general knowledge). The rule that makes over-approximation acceptable here is that an extra dependency only delays output; it never releases anything early. A tracking scheme where imprecision causes wrong answers cannot take this shortcut.

Test durability with real power cuts and an outside witness

The power-cut experiment is simple: write, send a UDP message to another machine after each write, cut power, compare the disk with the remote log. The remote log is the external observer that the definition is about, and it caught both lost data and corruption that local checks would have missed. Any claim that a memory or storage tier is persistent deserves the same treatment: crash at arbitrary points, under load, with the evidence recorded somewhere the crash cannot touch.

Slow durable writes are an opportunity for the OS, not only for the device

The paper's related work notes that eNVy found flash writes "prohibitively slow" and needed a battery-backed cache, and predicts xsyncfs "could also improve performance for flash file systems." The general lesson for tiers with asymmetric costs (fast reads, slow durable writes): the OS sees who is waiting on what, so it can let writers run ahead and batch durable writes, without the device needing a non-volatile buffer. The cost is a dependency-tracking layer in the kernel, measured here at about 7% on a write-heavy benchmark.

Questions with real answers

Each one is a tricky case the paper does not spell out, but it has a definite answer you can work through from the paper's own numbers and rules. The quoted block is how to ask it in class. Try your own answer before opening the worked one.

C1 · Figure 3 says xsyncfs is "durable on write". Is the data on the platter when write returns?

Figure 3 gives xsyncfs "Yes" for "Data durable on write", the same as synchronous ext3 with write barriers, and the caption says "Yes" means durability "if an OS crash or power failure occurs". But xsyncfs returns from write before committing. If power fails 10 ms after my write returns, before any commit, is my data there after reboot? If not, how does xsyncfs still pass the experiment behind Figure 3?

AnswerWork it out first, then open▾

No. The change is only in the active transaction in memory, and it is lost. xsyncfs passes because of how the experiment defines failure: the test machine sends a UDP message to a remote logger after each write, and durability fails only "if the remote computer logs a message for a write operation, but the test computer is missing the data written by that operation."

Under xsyncfs that UDP message is external output from a process that depends on the uncommitted transaction, so it is held in the kernel until the commit. If power fails first, the data and the message are lost together, and the remote log never mentions the write. So "Yes" means "no observer was ever told about data that was then lost", which is the paper's definition, not "on the platter at return". The observable history matches a synchronous run that crashed while blocked inside that write.

Where the answer comes from: Section 4.2's experiment and failure criterion, Figure 3's caption, and the buffering rule of Section 2.3.

C2 · Why would a reply to a static GET wait for a disk commit?

Figure 8 shows xsyncfs adding about 33 ms to 0 to 1 KB requests. Many SPECweb99 requests are GETs for static files, which only read. Under the paper's propagation rules, why does the reply to a read-only request have to wait for a commit at all? Which process wrote what?

AnswerWork it out first, then open▾

Because the process sending the reply has usually written to the file system recently. Section 4.6 notes "the normal log data written by Apache" plus a log record per POST. An Apache worker writes an access-log entry for each request it serves (general knowledge: Apache logs after sending the response), so after serving request N the worker depends on the active transaction (rule 1: a writer inherits a dependency on what it wrote).

When the same worker then sends the reply to request N+1, even a static GET, that network output inherits the worker's dependencies and is held until the transaction containing request N's log entry commits. In steady state almost every worker is uncommitted, so almost every reply waits about a commit time; only a worker with no uncommitted writes since the last commit could reply at once. The 33 ms is that wait, not a cost of reading.

Where the answer comes from: Section 2.3's rules and Section 4.6's description of the workload; Apache's logging order is general knowledge.

C3 · Figure 2 links output b only to Commit Dep 2. Is that a bug?

In Figure 2(a), output b points only to Commit Dep 2 (FS Ops 2 and 3, the active transaction). But b was written after FS Op 1 as well, and Section 2.3 says "Any external output inherits the commit dependencies of the process that generated it", which at that moment were Dep 1 and Dep 2. Is the figure missing a link, and could b ever be released before FS Op 1 is on disk?

AnswerWork it out first, then open▾

By the stated rule, b carries both dependencies, so the figure omits the link to Dep 1. It cannot matter for release time: ext3 lets only one transaction commit at a time and the active transaction "must wait for the commit of the prior transaction to finish before it commits", so Dep 2 can only be removed after Dep 1 has been. An implementation can drop a dependency on an older transaction of the same file system without changing behavior.

The omission would matter if the two dependencies were on different file systems, whose commits are not ordered with each other. That is exactly the case Section 2.5 handles by mapping "each dependency to a specific file system" and blocking a process before it writes a second one.

Where the answer comes from: Figure 2, the propagation rule in Section 2.3, ext3's commit pipeline in Section 3.2, and the two-file-system limitation in Section 2.5.

C4 · Is one commit time really the bound on output delay?

The introduction says "In most cases, output is delayed by no more than the time to commit a single transaction." Section 3.2 says only one transaction may be committing at a time. If a process prints a dependent line just after a transaction starts committing, how long can the line be held, and does the paper's own Figure 2 show this case?

AnswerWork it out first, then open▾

Up to nearly two commit times. The line depends on the active transaction, which cannot start committing until the current commit finishes; it then needs its own full commit. With commits of time C, the hold is (remaining part of current commit) + C, approaching 2C when the line is printed just after the commit started.

Figure 2(a) is exactly this situation: output a triggered T1's commit, and outputs b and c were produced while T1 was committing, so they wait for T1 and then T2. Using SPECweb99's 33 ms average as about 1.5C gives C of about 22 ms and a worst case near 44 ms (a simple model, see Worked Example 7). "In most cases" is doing real work in the introduction's sentence.

Where the answer comes from: Section 1's latency sentence, Section 3.2's one-committing rule, Figure 2, and Figure 8 for the scale.

C5 · Prove that single-client MySQL on xsyncfs is sharing commits between transactions.

Figure 6 shows about 4,500 New Order Transactions Per Minute for one client on xsyncfs, and the paper says total transactions are about twice NOTPM. The disk is 7,200 rpm. Can I show from these numbers alone that xsyncfs is not committing each of this one client's transactions separately? And what makes it safe for MySQL to reply to the client before its transaction is durable?

AnswerWork it out first, then open▾

2 × 4,499 / 60 s = 150 transactions per second, one every 6.7 ms. A revolution takes 60 / 7,200 s = 8.33 ms, and a commit with write barriers needs a platter write plus two cache flushes, so it takes at least a sizable fraction of a revolution and typically more. One sequential client finishing a transaction every 6.7 ms therefore cannot be paying a separate durable commit per transaction; commits must cover several. On ext3 with barriers the same client gets 1,298 NOTPM, 23.1 ms per transaction, consistent with one commit each.

It is safe because the reply travels over a UNIX socket, which is internal: the client inherits the server's dependency instead of seeing durable state. Only when the client produces external output does that output wait for the commit covering all its transactions. With a remote client, the reply itself would be network output and would be held, and the single-client advantage would disappear.

Where the answer comes from: Figure 6 values read off the PDF drawing, the 2× ratio from Section 4.5, the UNIX socket change from Section 4.5; the rotation time is general knowledge.

C6 · Why is synchronous ext3 15× slower on PostMark but 6% faster on SPECweb99?

On PostMark, ext3 mounted synchronously takes about 132 s versus about 8.7 s for xsyncfs. On SPECweb99 it gets 6% higher throughput than xsyncfs. Same machine, same 2 MB drive cache. What explains the reversal, and does it survive if ext3 must actually be durable?

AnswerWork it out first, then open▾

ext3-sync only waits until data reaches the drive cache. PostMark writes a lot of data quickly, so the 2 MB cache fills and "subsequent writes block until some data in the cache is written to the disk platter": each operation ends up waiting for the platter anyway, one at a time. SPECweb99 "writes little data to disk, so most writes are buffered by the drive cache": each synchronous write returns in microseconds. xsyncfs, by contrast, always commits with write barriers, so every reply waits for the platter.

So the 6% is the price of real durability on a workload where the non-durable configuration never touches the platter. With durability required (ext3-barrier), xsyncfs is 7% faster on SPECweb99 and 192× faster on PostMark.

Where the answer comes from: Sections 4.3 and 4.6 and Figures 4 and 7 (read off).

C7 · Causality through the user: can a crash reorder two unrelated processes' writes?

Dependencies are tracked only through the kernel. Suppose process A writes file X and prints "X saved, now run B". I read it and run B, which writes file Y. The kernel never links A to B. After a crash, can Y be on disk without X?

AnswerWork it out first, then open▾

No. A's message is output depending on the transaction holding X, so it is released only after that transaction has committed. I can only start B after seeing the message, so B's write of Y begins after X is already on the platter, and committed transactions are never undone. Y without X is impossible.

This is why buffering output is enough even though tracking stops at the machine boundary: any causal chain that leaves the machine passes through released output, and released output already implies the commit. The same argument covers a remote computer that receives a message and then sends a request back.

Where the answer comes from: Inference from the release rule (Section 2.3) and the definition of happens-before the paper uses (Section 2.2); the scenario is this guide's.

C8 · Eager commit also commits "immediately". Why is it 168× faster than ext3-barrier?

Section 4.7's eager variant "triggers a commit whenever the file system is modified", and synchronous ext3 with barriers also commits every modification before moving on. Both use write barriers. Yet on PostMark eager xsyncfs takes 9.879 s and ext3-barrier about 1,661 s. Where does a factor of 168 come from if both commit as soon as possible?

AnswerWork it out first, then open▾

From who waits. Under ext3-barrier the process is blocked until its change commits, so each transaction contains exactly one operation and every operation pays two cache flushes in sequence. Under eager xsyncfs the process keeps running; while one transaction commits, everything the process does lands in the next active transaction, which then commits as one unit. Commits run back to back, each carrying hundreds of operations.

So most of xsyncfs's advantage comes from not blocking the program, which turns sequential commits into a pipeline with natural batching; output-triggered deferral adds only the last 14% (9.879 to 8.668 s). The same split holds for single-client MySQL: 1,298 to 3,323 NOTPM from not blocking, 3,323 to 4,498 from deferral.

Where the answer comes from: Figure 9 combined with Figure 4 (read off) and Figure 6; the decomposition is this guide's arithmetic.

Glossary, results, and provenance

Every term in one place, the evaluation on one scale, then where each number came from, what this guide found inconsistent in the paper, and what the 10/29 companion outline gets wrong.

Core terms
External synchronyThe paper's model of local file I/O: a criterion on observable behavior under which an I/O counts as synchronous if every external output the computer produces could also have been produced had that I/O been synchronous. It says nothing about whether the caller blocked.
xsyncfsThe paper's externally synchronous file system: Linux ext3 on kernel 2.4.21, run in journaled mode with write barriers, modified to tell Speculator when a transaction is created, when a modification joins it and when it commits, and to commit the active transaction early when Speculator calls back.
Application-centric viewThe conventional way of dividing a computer into two parts, the kernel (internal state) and user-level programs (external observers); under it, the return from a system call is an externally visible event, so durability must be in place before the call returns.
User-centric viewThe paper's three-part division of a computer: the kernel and applications are both internal state, and only the external interfaces (screen, network, other devices) are visible. A system call return is a change to application state, not an observable event.
External outputAn event an entity outside the computer can observe: bytes sent to the screen, the network or another external device, and, by the paper's definition, every disk commit, because a crash exposes the file system's stable image.
Happens-before (causal order)Lamport's partial order on events: A happens before B if one process did A and then B, if A is the sending of a message that B receives, or through a chain of such steps. The paper requires externally synchronous outputs to occur in the same causal order as some synchronous run.
DurabilityA property of a completed update: it is on non-volatile media, so it survives a later OS crash or power failure. In xsyncfs it is promised to observers: no observer sees output that depends on an update that is not yet durable.
OrderingA property of a sequence of updates: after any crash, if an update B that causally followed A is present, A is present too. It is separate from durability; a system can lose both A and B without violating it.
Commit dependencyA kernel record linking a process, a kernel object (pipe, file, UNIX socket, another process) or a piece of buffered output to one uncommitted file system transaction whose data causally influenced it. It is removed when that transaction commits; it is never rolled back.
Uncommitted (process or object)The state of a process or kernel object that holds one or more commit dependencies. Its external output is buffered in the kernel; when its last dependency is removed, Speculator marks it committed.
Buffered (held) outputBytes that an uncommitted process sent to an external device, kept in kernel memory in that process's undo log together with their commit dependencies, and released to the device when the last of those dependencies is removed. The process continues running meanwhile.
SpeculatorThe authors' earlier Linux kernel extension (SOSP 2005) for speculative execution in distributed file systems: it lets a process continue on a predicted result of a remote operation, records every kernel object the process influences, buffers its external output, and rolls the process back from a copy-on-write checkpoint if the prediction was wrong.
Speculation objectSpeculator's kernel data structure for one speculative operation; it records all process and kernel state that depends on whether that operation's prediction succeeds.
Undo logSpeculator's per-object kernel list of entries naming the speculations (in xsyncfs, the commit dependencies) that an object depends on. In Speculator proper it also holds the state needed to undo changes; in xsyncfs it holds no undo data, only dependency links and buffered output.
Journal (write-ahead log)An on-disk region where ext3 first writes the new contents of a transaction's blocks and then a commit record, before writing those blocks to their home locations; after a crash, recovery replays every transaction whose commit record is present. 400 MB in the paper's setup.
Compound journal transactionext3's unit of atomic commit: one in-memory set of modified blocks gathered from many file system operations, committed together so that after a crash all of it or none of it is applied.
Active and committing transactionThe two roles a transaction can have in ext3's pipeline. The active transaction is the single one accepting new modifications; the committing transaction is the single one being written to the journal. When a commit starts, the next modification opens a new active transaction, which must wait for the current commit to finish before it can commit.
Commit record (commit block)The journal block written after all of a transaction's logged blocks, marking the transaction complete; recovery applies a transaction only if its commit record is on the platter.
Journaled modeThe ext3 mode in which both data and metadata modifications are written to the journal before reaching their home locations. xsyncfs uses it because it puts every block an operation changed into the active transaction before the operation returns, which gives ordering.
Ordered modeext3's default mode, in which only metadata goes into the journal and file data is written in place, in any order, before the metadata of its transaction commits; a crash can therefore leave a later data write present and an earlier one missing.
Drive write cacheVolatile DRAM inside the disk drive (2 MB on the test drive) that holds written sectors before they reach the platter. The drive reports a write complete when the data is in this cache, loses its contents on power failure, and may write cached sectors to the platter in a different order than they arrived.
Write barrierAs used in the paper: a commit procedure, introduced in Linux 2.6.11 and ported by the authors to 2.4.21, that flushes the drive's write cache before and after writing each transaction's commit record, so that the record never reaches the platter before the blocks it covers and the commit is durable when it completes.
Group commitA commit that makes many modifications durable at once, so the fixed cost of a commit (positioning, cache flushes) is shared among them. ext3 group commits by design; a synchronous mount cannot group a single-threaded program's changes because the program waits after each one.
Value loggingA journaling style in which a commit writes only the latest version of each modified block, so repeated writes to one block are logged once and blocks of a file created and deleted within one transaction are not written at all. ext3 uses it.
Output-triggered commitxsyncfs's commit policy: commit the active transaction at once when Speculator reports that it buffered output from, or blocked, a process that depends on that transaction; otherwise commit only by ext3's rules (oldest modification older than 5 s, journal full).
Eager commitThe comparison policy the authors built for Section 4.7: trigger a commit whenever the file system is modified. Modifications that arrive while the previous transaction is committing are still grouped into the next one.

Synchronous I/O (implementation definition)File I/O in which the calling program is blocked until its change has completed (been committed to disk); the definition the paper takes from Silberschatz and Galvin and replaces.
Asynchronous I/OFile I/O in which the call returns once the change is in kernel memory and the kernel writes it to disk later; ext3's default, which commits within about 5 s.
ext3-asyncThe evaluation configuration of ext3 mounted asynchronously (journaled mode, no barriers): the speed reference, durable against neither crash type at return.
ext3-syncThe evaluation configuration of ext3 mounted with the sync option and no barriers: each call blocks until its modifications reach the drive cache, which survives an OS crash but not a power failure.
ext3-barrierIn Figures 4, 5 and 7, ext3 mounted synchronously with write barriers, the configuration that matches xsyncfs's guarantees. In Figure 6 the same label means ext3 mounted asynchronously with barriers, with MySQL calling its own synchronization.
fsync, fdatasync, syncSystem calls that ask the kernel to make data durable: fsync one file's data and metadata, fdatasync one file's data (and only the metadata needed to read it back), sync everything (general knowledge for the distinctions). On xsyncfs each only attaches a dependency on the active transaction to the caller.
ioctlA catch-all system call for device-specific control operations whose effects the kernel cannot classify generically. Speculator cannot tell where information flows through it, so an uncommitted process that calls it is blocked until its modifications commit, and the block triggers a commit.
VFS layerThe kernel's file-system-independent layer that receives file system system calls and dispatches each to the specific file system's implementation (general knowledge); xsyncfs receives sync from it.
Page cache (file cache)Kernel memory holding the contents of file blocks; writes change it first and reach disk later. The paper's "the file cache" is one of the IPC channels through which dependencies flow.
PlatterThe spinning magnetic disk surface where written data is non-volatile; one revolution takes 8.33 ms at the test drive's 7,200 rpm (general knowledge for the arithmetic).
Copy-on-write forkA copy of a process that initially shares all memory pages with the original, marked read-only, and copies a page only when either side writes it; Speculator's checkpoint mechanism, which xsyncfs does not need.
Shared memory regionA range of physical pages mapped into several processes' address spaces, through which they exchange data by ordinary loads and stores that the kernel never sees; only mapping and unmapping are visible to it.
Memory-mapped fileA file whose pages are mapped into a process's address space, so reads and writes of the file are loads and stores; the paper tracks dependencies through it with the same permission-based rule as shared memory.
PipeA kernel byte buffer with a write end and a read end, connecting processes on one machine; writing it marks it with the writer's dependencies, reading it gives the reader the pipe's dependencies.
UNIX (domain) socketA kernel communication endpoint for processes on the same machine, used like a network socket but never leaving the kernel. Because the kernel sees both ends, dependencies propagate through it; the authors switched the TPC-C client to UNIX sockets for that reason.
Catastrophic media failureA failure of the disk medium large enough that the drive and device driver cannot mask it by remapping, so a write that the kernel already validated never reaches stable storage.
Kernel panicThe kernel halting the whole machine on an error it cannot handle; the paper names it, or (preferably) writing the data elsewhere, as the OS's response to catastrophic media failure.
IRON file systems surveyPrabhakaran et al. (SOSP 2005), the study the paper cites showing that ext3, its journaling layer jbd and NTFS did not detect write errors, while ReiserFS panicked on them.
Battery-backed RAM (NVRAM cache)Memory kept powered by a battery so that its contents survive a power failure for as long as the battery lasts; Rio, Conquest and Hitz et al.'s file server use it to make writes durable without waiting for a disk.
Soft UpdatesAn alternative to journaling that tracks dependencies between metadata blocks in memory and orders their disk writes so that the on-disk state is always recoverable (cited in related work).
Two-phase commitA protocol that makes one decision atomic across several independent participants: each first durably prepares, then all commit (general knowledge); the paper names it as a way to commit across two file systems and does not use it.
Output commit problemThe fault-tolerance requirement that before a message is sent to the outside world, the state from which it is sent must be preserved; the paper's model applies the same rule to file I/O.
PostMarkA file system benchmark (version 1.5 here) that models small-file workloads such as mail and news: it creates a pool of files (10,000), runs transactions of reads, writes, creates and deletes on them (10,000), then removes them. Single-threaded, no output until the end.
Apache build benchmarkThe paper's "Andrew-style" benchmark: untar the Apache 2.0.48 source, run configure and make in an object directory, then remove everything; it mixes disk I/O, computation and heavy screen output.
RAMFSA Linux file system that keeps all files in memory and never writes to disk; the paper uses it as a lower bound that measures the Apache build's computation alone.
TPC-C and NOTPMTPC-C is a database benchmark that models order entry with several transaction types and requires ACID semantics; NOTPM (New Order Transactions Per Minute) counts one type, and total transactions are about twice NOTPM. The paper runs a modified OSDL version (Database Test 2).
InnoDBMySQL's transactional storage engine (MySQL 5.0.16 here), which keeps its own log and calls the file system's synchronization to make each commit durable (general knowledge for the mechanism).
SPECweb99A web server benchmark in which clients issue a mix of HTTP GET requests (static and dynamic, up to 1 MB) and POST requests; here one client machine emulates 50 connections to Apache 2.0.48 over a 100 Mb/s switch, and each POST writes a log record.
Perception thresholdThe delay below which a person does not notice that a response was late; the paper cites the commonly used figure of 50 ms (from Flautner and Mudge).
90% confidence intervalA range computed from repeated trials that, under the usual statistical assumptions, contains the true mean with 90% probability; the paper's error bars for 5-trial results and Figure 8. Figure 7's bars instead show the highest and lowest of 3 trials.

Inconsistencies found in the paper

(1) The label "ext3-barrier" means ext3 mounted synchronously with barriers in Figures 4, 5 and 7, but in Figure 6 it is ext3 mounted asynchronously with barriers, with MySQL issuing its own synchronization (Section 4.5).

(2) Figure 6's x-axis reads "Number of Threads"; the text and caption speak of clients.

(3) The introduction says MySQL runs "up to three times faster than when it runs on top of ext3 mounted asynchronously"; Section 4.5 shows the 3× is against ext3 mounted asynchronously with write barriers. Against plain asynchronous ext3 the gain is 11% at 1 or 2 clients and nothing from 4 clients up.

(4) The introduction says xsyncfs is "up to an order of magnitude faster than the default version of ext3 mounted synchronously"; Section 4.3 says synchronous ext3 "is over an order of magnitude slower than xsyncfs" (about 15× read off Figure 4).

(5) The introduction compares PostMark and the Apache build against "the default asynchronous implementation of ext3", but Section 4.1 reports only journaled-mode ext3, and the default is ordered mode. Since journaled mode "executed faster in every benchmark", the reported comparison is the harder one, so the claim is not weakened.

(6) "In most cases, output is delayed by no more than the time to commit a single transaction" is qualified, but Section 3.2's rule that "Only one transaction may be committing at any given time" allows nearly two commit times, and Figure 2 itself depicts that case (outputs b and c produced while transaction 1 is committing).

(7) Figure 2 links output b only to Commit Dep 2, although by Section 2.3's rules b also depends on FS Op 1's transaction. With in-order commits the missing link changes no release time.

(8) Figure 9 reports a 0% speedup for SPECweb99, but output-triggered (311 Kb/s) is slightly below eager (312), −0.3%, inside both intervals; "every benchmark except SPECweb99" is consistent with that.

(9) The 5-second rule is stated three ways: a commit when "the oldest modification in the transaction is more than 5 seconds old" (Section 3.2), "ext3 commits its journal every 5 seconds" (Section 3.3), and xsyncfs "commits data every 5 seconds" (Section 2.5). The first, age-based form is the precise one.

(10) Figure 3's caption defines "Yes" as durability "if an OS crash or power failure occurs", but xsyncfs gets "Yes" for write although write returns before any commit. The "Yes" holds only in Section 4.2's observer sense (no remotely logged message refers to lost data).

Not an inconsistency but unexplained: in Figure 8, xsyncfs is faster than ext3-async for 100 to 1000 KB requests (10.072 versus 10.253 s) with non-overlapping 90% intervals; the paper does not comment.

Corrections to the 10/29 companion outline

The outline is accurate on most points and was used as a checklist. These items are wrong or imprecise (outline section numbers in parentheses).

(1) Latency bound (3.g.i.4; 5.c.iv.1 says "typically"): output delay "up to one transaction commit". The paper says "in most cases"; with one committing transaction at a time, output produced just after a commit starts waits for the rest of that commit plus its own, nearly two (M12, Worked Example ⑦).

(2) Group commit limits (5.b.i.4): a failure can lose the whole group, "which is fine because no output depended on it". Output may well have depended on it; it is fine because that output was still held in the kernel and is lost with the group, so no observer saw it (M5).

(3) Figure 2 walk-through (6.d.iii.1.b): "Outputs b and c depend on commit dependency 2" repeats the drawing; by the Section 2.3 rule they also depend on dependency 1, which is harmless only because transactions commit in order (M11).

(4) Speculator factoring (7.f.iv.2): "every write to xsyncfs would pay for a copy-on-write checkpoint fork". Speculator checkpoints "before a process inherits a new speculative dependency", so roughly once per new transaction a process becomes dependent on, not per write (M10).

(5) Methodology (13.d, 13.e): "Journaled mode and write barriers are used throughout" and "ext3-barrier (synchronous with write barriers, so durable on power failure)". Barriers are used only by xsyncfs, ext3-barrier and the MySQL baseline; ext3-async and ext3-sync run without them, which is the point of the comparison. In Figure 6 "ext3-barrier" is the asynchronous mount with barriers (the outline's own 16.b.iii says so). Also, Figure 7's error bars are the highest and lowest of 3 trials, not 90% confidence intervals.

(6) PostMark (15.a.ii.2.d): ext3-barrier "about 1,600 seconds". The drawn bar is about 1,661 s, 192× xsyncfs (F4).

(7) Apache arithmetic (15.b.iii.1): 100 s of computation plus 10 s of I/O, with I/O 7.5× slower, gives 175 s, which is 59% slower than the 110 s run, not 75% (75% is relative to computation alone). The paper's 7.5× is also relative to xsyncfs's I/O time, not async's.

(8) NFS comparison (21.b): "External synchrony instead lets the server reply early and holds back only the visible effects." A reply to another machine is itself external output: "Since xsyncfs only tracks causal dependencies on a single computer, it must buffer each message" until its data commits. What runs ahead is the server process, not the reply (S).

(9) Salus (21.j and the connections it feeds): "Salus also aims for strong durability and ordering with pipelined commit" describes the 2013 Salus scalable block store. The course's Salus (11/17) is Yu and Chowdhury's GPU-sharing paper (MLSys 2020), as the 11/17 outline itself notes. This guide's Salus connections were written against the course paper.

(10) Flash (21.d): "xsyncfs could likely help flash file systems such as those that need battery-backed write caches". The paper's example is eNVy, which added a battery-backed RAM write cache because flash writes were "prohibitively slow"; its claim is general: "it is likely that xsyncfs could also improve performance for flash file systems."
