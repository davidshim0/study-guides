OSDI 2006 · A Field Guide

Return control instantly — but never let the outside world peek early

Every file system forces a choice: block the app until data is safe (slow), or return instantly and risk losing it (unsafe). External synchrony shows the choice was a false one — buffer the output, not the application, and you get both.

📄 "Rethink the Sync" · Nightingale, Veeraraghavan, Chen, Flinn 🎓 Some OS/FS basics assumed — the primers cover them ⏱ ~25 min read
🔐

A write can RETURN before it's durable — but nothing that DEPENDS on it may leave the machine until it is.
Guarantee the observer's view, not the caller's wait.

What the paper assumes you already know

⚡ TL;DR

  • External synchrony lets a file I/O return before the write commits to disk — rarely blocking the caller, much like async I/O — while guaranteeing durability and ordering that, to an external observer, are identical to synchronous I/O, by buffering any output that causally depends on the uncommitted write instead of blocking the process that issued it.
  • Xsyncfs, the Linux implementation, is within 7% of asynchronous ext3 on I/O-heavy benchmarks yet up to two orders of magnitude faster than ext3 mounted synchronously with the write barriers needed for real durability.
  • It requires zero application changes — programmers write to the simple synchronous abstraction and get near-async performance without touching a line of code, even beating hand-tuned group-commit code (MySQL/TPC-C ran 3× faster).

Quick glossary — the terms you'll hit immediately
xsyncfsThe paper's modified ext3 that implements external synchrony on Linux.
SpeculatorAn earlier OS mechanism (checkpoint + causal dependency tracking) the authors repurpose, minus its rollback machinery, to build xsyncfs.
Commit dependencyA tag the kernel attaches to a process/object meaning "don't let this leave the machine until transaction X is on disk."
Write barrierA kernel command that forces the disk's volatile cache to actually flush to the platter — without it, "durable" writes can vanish on power loss.

1Synchronous vs. asynchronous I/O▾

Synchronous I/O blocks the caller until data is committed to disk — safe, but every write pays a full disk-rotation-scale delay. Asynchronous I/O returns instantly and writes back later — fast, but a crash before the write lands loses data the user already saw.

Now you're ready: the whole paper is about erasing this tradeoff rather than picking a side.
2fsync and why it can still lose data▾

fsync is supposed to force data to stable storage. But by default, Linux 2.4's fsync only pushes data to the drive's volatile cache, not the platter — a power failure can still lose it. This is a real, documented default, not a bug.

Now you're ready: "durable" in this paper always means "survives power failure," which requires write barriers, not just fsync.
3Causal order / happens-before▾

If operation A causally precedes B (B depends on A, e.g., A's result was used to compute B), a correct system must never let an observer see B's effects without also seeing A's. Lamport's happens-before relation formalizes this.

Now you're ready: external synchrony's entire correctness argument is "never violate happens-before for anything an outside observer can see."
4Journaling file systems (ext3)▾

Ext3 writes modifications to a journal before (or instead of) the main file system, so a crash mid-write can be replayed/recovered cleanly. It groups multiple operations into one compound transaction committed atomically.

Now you're ready: xsyncfs is built by modifying ext3's transaction machinery, not by replacing it.
5Speculative execution & checkpoint/rollback▾

Speculator's original job: predict the result of a slow remote operation, let the process keep running on that guess, and roll it back if wrong. This requires checkpointing state and tracking every dependency the speculative process creates.

Now you're ready: xsyncfs reuses Speculator's dependency-tracking half but throws away the expensive checkpoint/rollback half, since a commit (unlike a network guess) is never "wrong."
6Group commit and why single-threaded apps can't do it▾

Batching writes into one transaction amortizes disk cost. But a single-threaded synchronous app can't group its own writes — it can't start operation 2 until operation 1's blocking call returns.

Now you're ready: external synchrony gets group commit for free because it never blocks the app between operations 1 and 2.
7ACID transactions & TPC-C▾

ACID databases (like MySQL/InnoDB) need durability and ordering guarantees on their own log writes. TPC-C is a standard benchmark that measures database throughput (NOTPM) under concurrent client load.

Now you're ready: the MySQL benchmark tests whether external synchrony helps even an application that already implements its own careful commit logic.
The whole story in one place

External synchrony in a nutshell

Redefine who the guarantee is for, and the performance problem disappears.

Synchronous I/O defines its guarantee application-centrically: the calling process must block until its write is durable. Asynchronous I/O drops that guarantee for speed, silently exposing users and programmers to data loss and reordering. External synchrony observes that the guarantee only actually matters to entities outside the computer — a user watching the screen, or another machine on the network. Application state itself is invisible until it becomes external output.

So xsyncfs lets a write return before it commits to disk — rarely blocking the caller, much like async I/O, though it can still block on operations it can't track (an ioctl) or when a dependency crosses two local file systems. It also tags the calling process — and, transitively, anything it talks to via pipes, shared memory, or the file cache — with a commit dependency. Any output that dependency-chain tries to send to the screen, network, or another device is buffered inside the kernel and released only once the underlying disk transaction commits. An outside observer literally cannot tell the difference from true synchronous I/O.

To balance throughput and latency, xsyncfs uses output-triggered commits: delay committing (for group-commit throughput) until some buffered output actually depends on the transaction — then trigger that commit right away, since a real observer is now waiting. The commit itself still has to finish — disk transaction and write barriers included — before the buffered output is released; only the trigger is immediate.

The payoff: within 7% of ext3-async on I/O-intensive PostMark, within 3% on an Apache build, within 8% on SPECweb99 — while being up to two orders of magnitude faster than ext3 mounted synchronously with the write barriers real durability requires, and up to 3× faster for MySQL's own TPC-C benchmark.

🍯 Key takeaways

  • Sync I/O guarantees durability to the application; external synchrony guarantees it to the external observer instead.
  • The mechanism is commit dependencies: tag processes/kernel objects as "uncommitted," buffer their output, release it once the disk transaction lands.
  • Output-triggered commits delay disk writes for throughput until an observer is actually about to see the result, then trigger the commit right away — the commit itself still has to finish before that output is released.
  • Requires journaled ext3 mode (not the default ordered mode) to guarantee causal ordering between transactions.
  • Needs no application changes — and can even outrun hand-tuned group-commit code (MySQL) at low-to-moderate concurrency.
  • Limits: catastrophic media failure can't be reported back to the app; still commits every 5s regardless of output; two local file systems can't share one transaction.
Five everyday pictures

How to think about external synchrony

Each stands alone. Every card names where the picture stops being true.

The core idea · User-centric guarantee

A check that's cleared before you text "paid"

A bank could make you wait at the counter until a check clears (synchronous). Or it could let you walk out immediately (async) and risk telling your landlord "paid!" before it's real. External synchrony lets you walk out immediately — but silently holds your "paid!" text until the check actually clears.

Where it breaks: the bank still has to define "walking out" — for xsyncfs that's any observable I/O; if you interact through a channel it can't track (an ioctl), it must make you wait at the counter after all.
Enforcement · Commit dependency

A hospital wristband that follows the patient

Tag a patient "under observation" and every department they visit — radiology, pharmacy — inherits that flag automatically until it's cleared. A commit dependency works the same way: it propagates through pipes, shared files, and shared memory to every process that touches the uncommitted data, so nothing downstream can leak output early.

Where it breaks: real wristbands are removed by a nurse's judgment; xsyncfs's rule for shared memory is deliberately blunt — any reader of a page a writer has tagged inherits the tag, even if it didn't read the new bytes yet.
Scheduling · Output-triggered commit

A chef who plates only when the waiter shows up

A chef could rush every dish out the instant it's cooked (low latency, wasted trips), or batch-cook everything and plate on a fixed timer (high throughput, occasionally cold food waiting). Better: keep cooking and batching, but the moment a waiter actually appears to collect a dish, start plating it right away. Xsyncfs commits the same way — batch for throughput until output is about to leave, then start that commit right away; the dish still has to finish cooking before it goes out.

Where it breaks: the chef still checks the clock every so often regardless (xsyncfs's 5-second fallback commit) — a dish with genuinely no waiter still can't sit in the kitchen forever.
Correctness · Journaled mode & ordering

Numbering letters so they can't arrive out of order

If letter 2 references letter 1, the post office must never deliver 2 before 1 — even if it's tempting to send whichever truck fills up first. Ext3's journaled mode logs data (not just metadata) so that anything causally after a transaction is provably already queued behind it, guaranteeing the delivery order matches the writing order.

Where it breaks: the drive's own write cache can still reorder physical writes to the platter — this is exactly why write barriers, not journaling alone, are needed for true durability.
Design principle · Free performance

Autocorrect that never shows you a typo

You keep typing at full speed (never blocked); the system fixes things invisibly before you see the sentence rendered. External synchrony's promise is similar: programmers keep writing the naive synchronous code, and the file system quietly makes it fast without ever exposing an inconsistent view.

Where it breaks: autocorrect can silently choose the wrong word; xsyncfs never silently changes correctness — it only ever changes when output appears, never what it says.
The full explanation

How xsyncfs actually works

From the two-principle definition to the concrete kernel mechanism.

1 · Redefining what counts as "external"

Traditional OS design is application-centric: the kernel is internal, user-level is external, and a syscall return is an externally visible event. External synchrony instead takes a user-centric view: the kernel and the application are both internal — only output that actually leaves the machine (screen, network, another device) is external. A syscall returning early is no longer a problem, because nobody outside the box saw it happen.

2 · Commit dependencies and buffered output

When a process writes to xsyncfs, the kernel validates the write, updates in-memory state, and returns before the write reaches disk — rarely blocking the caller, much like async I/O (though it can still block on operations it can't track, like an ioctl, or when crossing two local file systems). It also creates a commit dependency linking the process to the still-uncommitted transaction. Any kernel object that process subsequently touches (a pipe, another process via IPC, a shared memory page, the file cache) inherits the same dependency. If the process (or anything downstream of it) tries to write to an external device, the kernel buffers that output instead of sending it — the output is released only once every transaction it depends on has committed.

💡
Why this preserves ordering: since xsyncfs commits transactions in the order applications generate them, and buffered output isn't released until its own transaction commits, an observer can never see effect B without also having seen everything that causally preceded it.

3 · Output-triggered commits

Ext3 normally commits every 5 seconds — great for throughput, unacceptable latency for a screen update. Xsyncfs instead commits the active transaction the moment Speculator reports that some process buffered output or blocked (e.g., on an untrackable ioctl) because of it — otherwise it keeps batching for up to 5 seconds.

# on every write
create/extend active transaction; return to app immediately
tag app with commit_dependency → active transaction

# on any attempt to externalize output
if output depends on an uncommitted transaction:
    buffer output in kernel
    trigger immediate commit of that transaction   # the commit still has to finish before output is released
else:
    send output normally

# on transaction commit
release all output buffered on it to its destination
discard resolved commit_dependencies
# fallback: commit every 5s even with no output, so nothing waits forever

4 · Guaranteeing durability: write barriers

A commit alone isn't durable if it only reaches the disk's volatile cache — a power failure can still lose or even corrupt it (the paper measured real superblock corruption from cache write reordering). Xsyncfs uses write barriers to force the drive to flush its cache to the platter around each transaction commit, which the paper confirms empirically is the only tested configuration that survives real power-cut experiments on both a plain write and an fsync.

⚠
The scary part: without barriers, the drive can reorder the commit-record write ahead of the data blocks it depends on, so recovery replays a "committed" transaction that's actually missing data — the paper observed both a garbage data block and a corrupted superblock this way.

5 · Limits, by design

  • Catastrophic media failure can't be reported to the app after the fact, since it already resumed execution past the write — the authors rejected using checkpoint/rollback to fix this because of the complexity and performance cost.
  • A 5-second commit floor still applies even with zero output, matching ext3-async's default, so an app that never produces output can't delay its data indefinitely.
  • Two local file systems can't share one transaction — xsyncfs instead blocks a process before letting it write to a second file system while it still depends on an uncommitted transaction in the first.
Follow the numbers

Worked examples

Four traces through the paper's own measurements.

① Reading the durability matrix

Figure 3: why does fsync on plain synchronous ext3 still not survive a power failure?

  1. "Synchronous" only means "blocked until committed." Committed, in the default 2.4 kernel, means written to the drive's volatile cache — not the platter.
  2. Power failure erases the volatile cache. So the commit the app waited for can vanish anyway.
  3. fsync inherits the same weakness — it forces a commit, but the same volatile-cache limitation applies, so it's also "not durable on power failure."
  4. Only adding write barriers fixes it (row 3), by forcing an actual platter flush — and xsyncfs adopts exactly this (row 4).
🍯
Insight: "synchronous" and "durable" are not the same guarantee — the paper's whole durability argument hinges on keeping that distinction sharp.

② Isolating the true I/O cost (Apache build)

The paper reports: xsyncfs is within 3% of ext3-async; RAMFS (no disk at all) is only 8% faster than xsyncfs; ext3-sync is 46% slower than xsyncfs overall, but 7.5× slower once you isolate I/O.

  1. Set xsyncfs's total time = 100. RAMFS, being 8% faster, is ≈92 — this is roughly the compute-only floor, since removing the disk barely helps.
  2. So xsyncfs's own I/O overhead ≈ 100 − 92 = 8 (illustrative units) — nearly all of its time is computation, not disk waiting.
  3. ext3-sync, 46% slower overall, totals ≈146. Subtracting the same ≈92 compute floor leaves its I/O overhead at ≈54.
  4. Compare I/O costs alone: 54 vs. 8 ≈ 6.75× — in the same ballpark as the paper's stated 7.5× (the small gap is rounding from the coarse 46%/8% figures; the paper's own bar-chart data gives the precise 7.5×).
💡
Subtracting a computation-only baseline (RAMFS) is what turns "46% slower overall" into the much starker "7.5× slower for I/O alone" — the true cost synchronous I/O imposes once you stop letting computation hide it.

③ Why MySQL's advantage shrinks with more clients

TPC-C: xsyncfs is 3× faster at 1 client, 22% faster at 20 clients, and matches ext3-barrier at 32 clients. Why does the gap close?

  1. At 1 client, MySQL must commit each transaction before replying — it has nobody else's work to batch with. Xsyncfs alone can defer that commit past the reply (output-triggered), so its group-commit advantage is largest: 3×.
  2. At 20 clients, MySQL itself can now group-commit transactions from different clients — it no longer needs xsyncfs's trick as badly. The gap narrows to 22%.
  3. At 32 clients, the paper reports ext3 mounted async with barriers matches xsyncfs's throughput: with enough concurrent clients, MySQL's own group-commit can batch transactions across many clients at once, closing the gap that xsyncfs's single-client trick used to provide.
🍯
Insight: external synchrony's biggest wins are exactly where hand-written group commit is hardest — low concurrency, single-threaded or lightly-threaded I/O.

④ Output-triggered vs. eager commits (Figure 9)

Speedup of output-triggered commits over an "eager" strategy (commit on every modification): PostMark 14%, Apache 2%, MySQL@1-client 35%, MySQL@20-clients 11%, SPECweb99 0%.

  1. MySQL@1-client gets the biggest win (35%). With only one client and little output, there's the most room to batch writes before anything forces a commit.
  2. SPECweb99 gets ~0% benefit. It already produces near-continuous output (HTTP responses, POST logs), so a transaction is triggered almost immediately either way — eager and output-triggered converge.
  3. Apache's build gets only 2% because it's dominated by computation (see example ②), so commit strategy barely matters to overall wall time.
💡
The pattern confirms the design logic directly: output-triggered commits help exactly in proportion to how much "silent" time exists between when data is written and when it's actually observed.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A process writes to xsyncfs, then immediately writes "done" to the screen. Under external synchrony, when does the user actually see "done"?
Show answer
Not immediately — "done" is buffered because it causally depends on the uncommitted write. It's released only after that write's transaction commits to disk (with write barriers). The process itself returns without waiting for the disk, but the screen output waits.Misconception: that external synchrony means "nothing ever waits." Only the application stops waiting; the output still waits exactly as long as true synchronous I/O would have made the app wait.
Problem 2 · medium
Why does xsyncfs need ext3's journaled mode rather than its default, faster ordered mode?
Show answer
Ordered mode journals metadata only, so it can't guarantee that data blocks for causally-earlier operation A reach disk before operation B's transaction starts to commit. Journaled mode logs data too, so A's modifications are provably already in the journal by the time a causally-later B is even created — guaranteeing B never commits before A.Misconception: that any journaling mode gives ordering. Ordering specifically requires data (not just metadata) to be journaled in causal sequence.
Problem 3 · hard
MySQL's own group-commit advantage over xsyncfs shrinks from 3× (1 client) to ~0% (32 clients). Explain why using what output-triggered commits actually optimize.
Show answer
Output-triggered commits help most when there's otherwise no way to batch — a single client must wait for its own reply, so xsyncfs's ability to delay that reply's dependency is pure win. With 32 concurrent clients, MySQL can already batch many clients' transactions into one commit on its own, achieving the same throughput benefit without needing xsyncfs's causal buffering.Misconception: that xsyncfs always beats a database's custom logic. It wins specifically in the low-concurrency regime where custom group commit has nothing to batch with.
Problem 4 · medium
SPECweb99 throughput with xsyncfs is within 8% of async — but ext3 mounted synchronously (no barriers) actually beats xsyncfs by 6%. Why?
Show answer
SPECweb99 writes relatively little data to disk, so most writes — sync or not — are largely absorbed by the drive's cache; the paper attributes plain sync's edge here to that small I/O footprint, not to any specific mechanism inside xsyncfs. Whatever small tracking overhead xsyncfs carries isn't offset by I/O savings in a workload this write-light.Misconception: that xsyncfs always dominates any synchronous configuration, or that the gap is specifically about per-syscall dependency-tracking cost — the paper doesn't pin the 6% down to a mechanism that precise. When true I/O cost is already small, unsafe sync mode can edge it out.
Problem 5 · easy
A process performs an ioctl that Speculator cannot track causal dependencies through. What happens?
Show answer
The process is blocked until its file system modifications commit — external synchrony falls back to ordinary synchronous blocking whenever it cannot guarantee the output-buffering mechanism will work.Misconception: assuming external synchrony never blocks anything. It blocks precisely when it can't safely buffer output instead.
Problem 6 · hard
Why can't xsyncfs simply group-commit a transaction that spans two different local file systems?
Show answer
Each file system keeps its own separate journal, so there's no single atomic commit point spanning both without a shared journal or two-phase commit — both of which the authors judged too complex/costly. Instead, xsyncfs blocks a process before it modifies a second file system while it still carries a commit dependency on the first.Misconception: that this is solved automatically the same way IPC dependencies are propagated. Cross-filesystem atomicity needs an entirely different (and here, simpler/blunter) mechanism.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's external synchrony in one sentence?▾
A file I/O model where writes return before they commit to disk — rarely blocking the caller, much like async I/O — but any output that depends on an uncommitted write is buffered by the kernel until it's durable, so an outside observer sees exactly what synchronous I/O would have shown.
Q2Does the application need to be rewritten?▾
No. Programmers write ordinary synchronous-style code with no extra fsync calls or group-commit logic; xsyncfs provides the durability and ordering guarantees. That's not free, though — the paper reports real overhead: within 7%/3%/8% of async on PostMark/Apache/SPECweb99, up to 33ms of added request latency in some benchmarks, and even a 6% loss to unsafe synchronous ext3 on SPECweb99.
Q3What exactly is a commit dependency?▾
A kernel-tracked link between a process (or pipe, shared memory region, file, etc.) and an uncommitted disk transaction. Anything tagged with one cannot externalize output until the transaction commits; the tag propagates automatically through IPC and shared memory.
Q4What triggers a commit besides the 5-second timer?▾
An "output-triggered commit": whenever Speculator reports that some process buffered output, or blocked on an operation it can't track (like an ioctl), because it depends on an active transaction.
Q5Why keep the 5-second fallback commit at all?▾
Without it, a process that produces file writes but never any external output could have its data sit uncommitted indefinitely, risking a large loss on crash. The 5-second interval matches ext3-async's own default.
Q6How does xsyncfs handle multi-threaded or shared-memory processes?▾
Conservatively: any thread inheriting a commit dependency propagates it to all threads in the process, and any reader of a shared memory page a dependent writer touches inherits the same dependency — simpler than the checkpointing needed for speculative rollback, at the cost of some potentially unnecessary buffering.
Q7Does xsyncfs protect against catastrophic disk failure?▾
Not by notifying the application — since the app already resumed execution before the physical write completes, the authors chose not to add checkpoint/rollback to propagate such failures back, judging the complexity and performance cost not worth it.
Q8Why write barriers instead of just disabling the drive cache?▾
Both provide durability, but the paper found write barriers consistently faster in every benchmark, since disabling the cache also removes its read-caching and write-coalescing benefits.
Q9Does this help across a network, e.g., between two machines?▾
Xsyncfs only tracks causal dependencies within a single local computer. Network output is buffered until local commit (as tested in SPECweb99), but there's no cross-machine commit-dependency propagation for distributed file systems.
Q10Does xsyncfs ever hurt performance compared to plain synchronous I/O?▾
In SPECweb99, ext3 mounted synchronously (unsafely, no barriers) edges out xsyncfs by 6%. The paper attributes this to the workload writing little data — most writes are absorbed by the drive's cache regardless of mount mode — rather than to a specific overhead mechanism in xsyncfs.
Beyond this paper

Where this connects to modern OS/memory-systems design

Four short bridges from 2006's disk problem to today's memory-tiering problems.

io_uring and completion-based durability

io_uring also decouples "issued" from "visible," but pushes ordering reasoning onto the application (linked SQEs, IOSQE_IO_DRAIN). External synchrony's contribution is doing that reasoning transparently in the kernel via causal dependency tracking — a reminder that "async but still correct" can be a systems-layer guarantee, not just an API contract.

Persistent memory ordering (clwb/sfence)

CXL-attached and NVM-backed memory face the exact same commit-boundary question at cacheline granularity instead of disk-block granularity: a write is "in the store buffer" long before it's durable, and something must track when downstream observers may see it. Xsyncfs's commit dependency is a coarse-grained ancestor of the fine-grained persistence-ordering primitives PM programming models require.

Output-triggered commit ≈ access-triggered promotion

Delaying a disk commit until something actually depends on its visibility is structurally the same move as delaying a page migration/promotion decision in a tiered-memory system until the page is actually about to be touched, rather than migrating on a fixed periodic scan (à la classic NUMA balancing). Both trade a periodic, blind cost for an event-driven, precise one.

Transparency as the actual deliverable

Xsyncfs's headline result isn't a new API — the paper's claim is narrower and more precise: no application modification, and output an external observer can't distinguish from a synchronously mounted ext3 file system, made fast. That's the same bar OS-managed memory-tiering systems (TPP, HeMem, Memtis) hold themselves to: move a correctness- or performance-critical decision below the application without touching a single line of its code.

🍯
The generalizable pattern for tiering research: track a causal/consistency obligation implicitly in the kernel, and only pay its cost at the moment an external observer would actually notice — not on every write, and not on a blind periodic clock.

Sharp questions to raise in discussion

Each references a specific claim or number from the paper.

  1. The paper attributes most of xsyncfs's 7% PostMark gap to kernel dependency-tracking overhead — does this overhead scale per-syscall or per-concurrently-uncommitted-object, and how would that hold up on a many-core box running dozens of independent write-heavy processes at once? (the single-core 2006 test rig may hide a scalability cost)
  2. MySQL's xsyncfs speedup collapses from 3× at 1 client to ~0% at 32 clients — is output-triggered commit's benefit fundamentally just "the group commit a well-tuned application would eventually build anyway," and if so what's left of the paper's contribution at high concurrency? (the crossover point itself is the interesting data)
  3. The authors explicitly reject sharing one journal or 2PC across two local file systems, opting to block a process instead — what breaks if this were extended to a distributed or networked file system, given commit dependencies never cross machines today? (no cross-node causal tracking exists in this design)
  4. Speculator's shared-memory rule is deliberately conservative — any reader of a page a dependent writer touches inherits the dependency, even without reading the new bytes — how much throughput does this likely cost a producer-consumer ring buffer, and was that ever measured? (only TPC-C's shared-memory use was benchmarked, not a stress case)
  5. They rejected checkpoint/rollback for propagating catastrophic media failures back to applications, citing complexity and performance cost in 2006 — does that tradeoff still hold now that fast local checkpointing (CRIU, userfaultfd) is far cheaper than it was then? (a "reconsider with modern primitives" question)
