PLOS 2026 · A Field Guide

Turning "deterministic by construction" into deterministic by proof

Replicated systems need every replica to reach the same state from the same log — even when execution is parallel. DeterV is the first system to back that claim with a machine-checked proof, in Verus, against a real Rust runtime.

Before you begin

Quick glossary, then ten ideas to prime you

Acronyms first, then collapsible primers — open only what's unfamiliar.

DeterVThis paper's verified deterministic parallel runtime, built in Rust and proved in Verus.
RSMReplicated State Machine — every replica applies the same log to reach the same state.
GSMGlobal State Machine — DeterV's middle proof layer, tracking one version counter per object.
Verus / VerusSyncA verification framework for Rust; VerusSync adds resource-algebra tooling for concurrent proofs.
IrisA concurrent-separation-logic framework supplying the "authoritative resource algebra" DeterV's ghost state is built on.
Ghost stateProof-only bookkeeping, erased at compile time, used to reason about concurrent behavior.
DAGDirected acyclic graph — the task dependency graph a deterministic scheduler derives from the log.
ktps / μsKilo-transactions-per-second and microseconds — DeterV's throughput and latency units in §5.2.
1Why replicated systems want determinism▾

A replicated state machine keeps several copies of a service in sync by feeding each replica the same ordered log of operations. If every replica applies the log deterministically, they all end up in the same state — no extra coordination needed after ordering is agreed.

The paper's stakes: sequencing layers (consensus, blockchains) are now fast enough that single-threaded execution becomes the bottleneck, so replicas need to execute the log in parallel while still reaching the exact state single-threaded execution would.

Now you're ready: DeterV's whole job is proving that a parallel engine's output always equals what running the log one task at a time would produce.
2Pessimistic vs optimistic scheduling▾

Pessimistic ("schedule-execute"): analyze dependencies or take ordered locks up front, then run — no aborts, but you need predeclared read/write sets. Optimistic ("execute-validate-commit"): run speculatively first, then validate and possibly abort/retry — no scheduling assumptions, but contention causes aborts.

Now you're ready: DeterV's runtime is pessimistic (DORADD-style); the paper argues its verified core — the commit boundary — would work for an optimistic design too.
3Object versions as the unit of ordering▾

Given a log T1:w(x), T2:w(x), T3:w(y), only tasks touching the same object must respect log order — T2 must follow T1 (both write x), but T3 is independent. DeterV models each object as walking a version sequence v0 → v1 → v2 … induced by the log, one bump per write.

Now you're ready: "global determinism" becomes "every object's version sequence matches what sequential execution would produce" — a much smaller claim to prove per object.
4Hoare logic and contracts, briefly▾

A Hoare-style contract states a precondition (what must be true before a function runs) and a postcondition (what's guaranteed true after). Verifiers like Verus check, statically, that every call site satisfies the precondition and that the function body actually establishes the postcondition.

Now you're ready: DeterV wraps its single commit function in exactly one contract — that's the entire enforcement point for determinism.
5Iris's authority/fragment pattern▾

Iris's authoritative resource algebra splits a piece of ghost state into one authority (the single global truth, e.g. "x is at version 5") and any number of fragments (partial, exclusive claims about that truth). Because the resource is exclusive, two fragments can never disagree with the authority at once — this is what makes concurrent reasoning sound.

Now you're ready: DeterV gives each object one authority (•v) living in an invariant, and hands out one fragment (◦v) at a time to whichever task currently owns that version.
6Linear types and ownership (Rust/Verus)▾

A linear (non-Copy) value can exist in exactly one place at a time — moving it elsewhere leaves nothing behind. Verus's type system enforces this even for ghost values, so a fragment token literally cannot be duplicated or silently invalidated by another thread.

Now you're ready: the "stability" DeterV needs for its version claims comes for free from Rust/Verus's ownership rules, not from extra runtime checks.
7Linearization points / effect boundaries▾

In concurrent-correctness proofs, a linearization point is the single instant at which an operation's effect becomes visible to everyone else, even though the operation's code may span many instructions. Picking the right linearization point is often what makes a proof tractable.

Now you're ready: DeterV calls its linearization point the effect boundary — the moment a task's writes become visible — and the paper argues every design (pessimistic or optimistic) has one, though only the pessimistic case is implemented and verified here.
8Refinement proofs, in one sentence▾

A refinement proof shows that a concrete, complicated system's observable behavior is always an instance of a simpler, trusted specification's behavior. It's often done in layers: concrete implementation → intermediate model → abstract spec, each step proved to "refine" the one above.

Now you're ready: DeterV's three layers (runtime → global state machine → sequential spec) are exactly this sandwich, following the IronSync methodology.
9Async Rust readiness signaling (Notify)▾

Tokio's Notify is a lightweight primitive that carries no data — it just wakes up a task waiting on it. It's a common building block for expressing "task B can't run until task A finishes" without heavier locks.

Now you're ready: the unverified baseline uses one Notify per object-version to gate dependent tasks; DeterV's proof design reuses that same dependency-signal slot to also carry proof tokens — though the verified Rust port replaces Notify itself with synchronous Mutex/Condvar primitives, since Verus didn't support Tokio's async components (§4.6, §5.1).
10Reading proof-to-code ratios & benchmark plots▾

A proof-to-code ratio is proof lines of code ÷ executable lines of code — a rough measure of verification cost. Benchmark plots here show latency (μs, lower better) vs throughput (ktps, higher better), swept over transaction contention (Zipf skew) and objects touched per transaction.

Now you're ready: DeterV reports 3:1 proof-to-code and near-zero latency overhead, with throughput overhead growing as transactions touch more objects — both explained in Worked Examples.
The whole story in one place

DeterV in a nutshell

The problem, the two insights that make it tractable, and how the pieces connect.

Deterministic parallel runtimes (pessimistic schedule-execute or optimistic execute-validate-commit) all claim that parallel execution equals sequential execution in log order — but that claim has only ever rested on informal argument. A scheduling, validation, or commit-order bug can silently break replica agreement, which for blockchains and payment systems is exploitable, not just embarrassing.

The obstacle to proving this properly is combinatorial: a proof that reasons about the full space of thread interleavings does not scale. DeterV's fix rests on two insights. (I1) Localize by object, then compose: since the log only forces ordering between tasks that touch the same object, correctness reduces to proving each object independently walks its own version sequence 𝑣0→𝑣1→…, then composing all objects' guarantees into one global result. (I2) Verify at the effect boundary: the paper argues every design, pessimistic or optimistic, funnels its externally-visible writes through one commit_effects-style operation — so a single Hoare-style contract on that one function should suffice to enforce and prove ordering regardless of design, though only the pessimistic runtime is actually implemented and verified this way; the optimistic case is left to future work.

Concretely, DeterV represents each object's version as ghost state backed by Iris's authoritative resource algebra: one authority per object (the single truth, inside an invariant) and one exclusive fragment per object-version a task currently holds (a transferable claim) — a task can hold fragments for every object in its write set at once. commit_effects's precondition demands the task's fragments already match the authorities; its postcondition advances both by one. A three-layer refinement (concrete runtime → global state machine → sequential spec) then proves that any schedule's final store equals sequential execution's — without ever enumerating interleavings.

The payoff: implemented in a Rust runtime inspired by DORADD, a state-of-the-art unverified deterministic runtime, DeterV attains a 3:1 proof-to-code ratio, verifies in 4.5s, adds no measured latency overhead, and costs up to 24% throughput at high per-transaction contention (10 objects/txn) versus its own unverified version — not verified DORADD itself.

🍯 Key takeaways

  • Global determinism reduces to per-object version-sequence correctness, composed — not per-schedule reasoning.
  • The paper argues every deterministic design has one effect boundary (commit_effects), and that a single Hoare contract there could cover both pessimistic and optimistic runtimes — though only the pessimistic design is implemented and verified; the optimistic case is future work.
  • Ghost state = Iris authority (global truth, in an invariant) + exclusive fragment (a task's transferable, linear claim).
  • Fragments move between tasks via a VerusSync tokenized state machine, riding the same dependency-signal slot already used for readiness — Notify in the unverified baseline, a synchronous Mutex/Condvar pair in DeterV's verified port.
  • Correctness is proved by a 3-layer refinement: concurrent runtime → global state machine (per-object head versions) → sequential spec.
  • Result: 3:1 proof-to-code, 4.5s verification, ~0% latency overhead, up to 24% throughput overhead at high contention. Safety only — not liveness.
Six everyday pictures

How to think about DeterV

Each stands alone; every card is honest about where it breaks.

Core idea · Object versions

Two separate elevator shafts

Object x has its own elevator, stopping at floors v0, v1, v2 in order; object y has a completely separate shaft with its own floors. Nobody needs to coordinate the two shafts unless a task rides both — that's the only place ordering must be checked.

Where it breaks: a task that writes both x and y must move in both shafts atomically — DeterV's contract opens all touched objects' invariants together for exactly this reason.
I2 · Effect boundary

One teller window

A bank may have many clerks preparing paperwork in back rooms — that's fine, do it however you like. But only one teller window actually posts a transaction to your balance. Verify that window's rules (check the slip matches your current balance, then update it) and it doesn't matter how the paperwork upstream was prepared.

Where it breaks: real tellers serve one customer at a time; commit_effects can post a whole multi-object write set atomically in one step — stronger than any single teller window.
Ghost state · Authority + fragment

The master ledger and your claim ticket

A coat-check has one master ledger (authority) recording exactly which coat is where, and hands each customer a numbered claim ticket (fragment). Your ticket is worthless unless it matches the ledger, and only one ticket exists per coat — no duplicates possible. That's the whole trick behind proving no two tasks silently disagree about an object's version.

Where it breaks: a real ticket is inert paper; a fragment is a linear Verus value whose exclusivity is enforced by the type system itself, so "photocopying" it is a compile error, not just bad manners.
Fragment lifecycle · Slot handoff

A relay baton passed at the handoff zone

A relay baton is handed off exactly once, at a fixed zone, and the incoming runner never starts before receiving it. DeterV's slot reuses that very same dependency-signal slot — Notify in the unverified baseline, a synchronous Mutex/Condvar pair in DeterV's verified port — which already orders "predecessor finished, successor may run," to also carry the version fragment: deposit travels with the signal, withdraw happens when the wait returns, so no extra coordination is needed.

Where it breaks: a baton can physically only go one way; DeterV enforces the one-way, exactly-once handoff instead through a VerusSync state machine (empty → deposited → withdrawn), which is what actually rules out double-use.
Proof architecture · Refinement layers

A chain of translators

Picture three translators in sequence: the concurrent runtime "speaks" in raw commits and threads; the GSM translator restates that as clean per-object version bumps; the sequential-spec translator restates that as "just run the log in order." Prove each adjacent pair says the same thing, and the outermost and innermost layers are provably equivalent — without ever directly comparing raw threads to the sequential spec.

Where it breaks: real translation loses nuance at each hop; refinement proofs are lossless by construction — each layer is proved, not approximated.
Trusted scope · Unverified components

The load-bearing wall vs the furniture

DeterV verifies the commit_effects effect boundary, the fragment lifecycle, and the three-layer refinement down to the sequential spec — but leaves the thread pool, channels, and dependency hashmap as trusted, unverified "furniture" — widely-used, standard components not the target of the proof. The proof's guarantee only holds as strongly as this trusted boundary; DeterV also proves safety, not liveness (it won't prove the system never deadlocks, only that if it produces output, that output is correct).

Where it breaks: unlike furniture, a bug in a "trusted" library (e.g. the concurrent hashmap) could still violate the theorem's assumptions — trust here means "out of scope," not "proven safe."
The full explanation

How it actually works

Section by section, following the paper's own build order (§4.1–§4.7).

1 · The unverified baseline — dispatcher + workers + Notify

A single dispatcher consumes the log in order, assigns each task's object versions, resolves its dependency set, and spawns it as an async task on a worker thread pool. Each worker awaits its predecessors' Notify signals, runs the task body, applies writes to the store, then signals its own successors. Because only the dispatcher reads the log and assigns versions, it alone serializes the reference order — but nothing here is proved to preserve it.

🧵
The runtime design is inspired by DORADD, a high-throughput, low-latency deterministic runtime that achieves this without batching — DeterV's chosen Rust implementation follows a similar structure and adds proof machinery on top.

2 · Reframing correctness per object

Proving global determinism directly means reasoning over every possible interleaving of concurrent commits — intractable. Per I1, DeterV instead projects the log onto each object: the tasks that write object x, in log order, define x's version sequence v0→v1→v2… Correctness for x means the runtime advances it along exactly that sequence, never skipping or reordering. If every object individually does this, the whole store is correct by composition (proved in §4.7).

3 · Ghost state — Iris authority and fragment

A worker needs to soundly claim "object x is at version v" under concurrency, where a plain shared variable would be unsound (another worker could change it mid-check). DeterV uses Iris's Auth(Ex(Version)): one authority •v_x per object — the unique global record, living inside a per-object invariant — and a matching fragment ◦v_x, realized as the Verus types GhostVarAuth<Version> / GhostVar<Version>. The fragment's exclusivity (no two valid copies) comes from it being a non-Copy linear value — Verus's type system, not runtime checks, guarantees stability.

4 · Fragment lifecycle — deposit, withdraw, reuse the signal slot

A fragment for version v only exists after the authority has advanced to v — so fragments can't be pre-generated, only transferred from producer to consumer along the dependency edge, exactly once. DeterV models this as a VerusSync tokenized state machine with states empty → deposited → withdrawn: the producer gets a deposit capability, the consumer a withdraw capability, and reachability (withdrawn only via deposited) is itself the proof that deposit happened first. The slot rides the runtime's existing per-version readiness signal — Notify in the unverified baseline, but a synchronous Mutex/Condvar pair in DeterV's verified port, since Verus did not support Tokio's async primitives at the time: deposit travels with the readiness signal, withdraw happens when the wait returns — reusing an edge that already exists rather than adding new synchronization.

5 · Global refinement — three layers

Following IronSync's methodology, DeterV proves refinement through: (a) the trusted sequential spec, sequential_exec(log), whose one step applies the next log task deterministically; (b) the GSM, a state machine over head: Map<ObjId,Version> whose single step advance_head bumps every object in a commit's write set by one, atomically; (c) the concurrent runtime, which carries the GSM's ghost tokens in pieces and calls commit_effects to execute one GSM step per task. Because commits are atomic and each fragment is held by exactly one task, the check "does my fragment match head(o)" stays stable across concurrent commits — so a run's commit trace, ordered and inducted over the log, always ends in the sequential spec's store. No cross-object obligation is needed.

💡
Why this matters beyond DeterV: the same per-object versioning and single-commit-point pattern shows up whenever a system must serialize a global effect (log order, epoch bump, page migration) without serializing every interleaving that leads up to it — a shape familiar from tiered-memory systems that must prove a migration or promotion decision is applied exactly once, in the right order, per page or object.
Follow the numbers

Worked examples

Four traces using the paper's own log, code, and measurements.

① Which tasks must serialize?

Log: T1:w(x), T2:w(x), T3:w(y). What can run in parallel?

  1. Project onto object x: writers are T1, T2, in that order — x starts at v0, T1 advances it to v1, then T2 advances it to v2: v0 → v1(T1) → v2(T2).
  2. Project onto object y: writer is T3 alone — y starts at v0 and T3 advances it to v1: v0 → v1(T3).
  3. T2 must wait for T1 because both touch x; skipping or reordering them would desync x's version sequence from the log.
  4. T3 shares no object with T1 or T2, so its version sequence for y is independent — it may run fully in parallel with either.
🍯
Insight: this is exactly I1 in miniature — the dependency DAG the dispatcher builds is nothing but "read off which objects overlap," per object.

② The commit_effects contract, with numbers

Task T2 writes objects x and y. Suppose the authorities currently read •v_x = 4, •v_y = 7, and T2 holds fragments ◦v_x = 4, ◦v_y = 7.

  1. Precondition check: for every touched object, fragment must equal authority: 4==4 ✓, 7==7 ✓ — permits_match_inv holds.
  2. Physical write: store.apply(writes) applies T2's writes to x and y in the real store.
  3. Ghost advance: both invariants open together; authorities become •v_x = 5, •v_y = 8; T2's fragments become ◦v_x = 5, ◦v_y = 8.
  4. Postcondition check: advanced[o].v == permits[o].v + 1 for both — 5==4+1 ✓, 8==7+1 ✓.
  5. Atomicity: because both invariants opened in the same call, no other worker ever observes x at v5 while y is still at v7 (or vice versa) mid-commit.
💡
This is Listing 2 (§4.5) run by hand — the whole determinism guarantee lives in these four checks, on one function.

③ The 3:1 proof-to-code ratio, computed

Table 1 reports: unverified runtime 371 LOC; DeterV proof 1,467; DeterV exec 469; DeterV trusted 374; DeterV total 2,310.

  1. Proof-to-exec ratio: 1,467 ÷ 469 ≈ 3.13 — for every line of executable logic, about 3 lines of proof. Matches the paper's headline "3:1."
  2. Total blow-up vs baseline: 2,310 ÷ 371 ≈ 6.2× more lines than the unverified system — most of that growth (1,467 of 1,939 new lines) is proof, not new behavior.
  3. Trusted scope stays small: 374 lines (thread pool, channels, Mutex/Condvar, concurrent hashmap) are outside the proof — about 16% of the total, and not the correctness target.
  4. Verification speed: despite ~1,900 lines of proof obligations, Verus discharges them in 4.5 seconds — fast enough for routine iteration.

④ Why throughput drops 24% at 10 objects/txn

§5.2's YCSB benchmark (10M-key store, m5d.8xlarge, 16 cores) shows no latency overhead anywhere, but throughput overhead grows with objects touched per transaction, reaching a 24% max drop at 10 objects/txn.

  1. Root cause: the unverified baseline's per-version Notify (no payload, lightweight) is replaced by heavier Mutex/CondVar blocking primitives to carry the fragment handoff, because Verus doesn't yet support Tokio's async primitives.
  2. Per-transaction cost scales with objects touched: a transaction touching 10 objects performs up to 10 such heavier one-shot signals instead of 10 Notify calls — the per-signal overhead compounds.
  3. At 2 objects/txn the paper reports negligible overhead — too few signals per transaction for the heavier primitive to matter.
  4. Conclusion: the cost isn't in the proof logic itself (commit_effects adds no latency) — it's in trading an async-native signal for a synchronous one to fit Verus's current feature set.
🧵
A tiering-systems parallel: this is the classic cost of swapping a lock-free/wait-free fast path for a coarser synchronization primitive purely to make a component verifiable/portable — the same trade shows up when a memory-tiering hot path must fall back to a heavier barrier for correctness instrumentation.
Test yourself

Practice problems

Try before opening the answer — each checks a specific misconception.

Problem 1 · easy
Log: T1:w(x), T2:r(y), T3:w(y), T4:w(x). Which pairs of tasks must respect log order?
Show answer
T1 and T4 (both touch x). T2 and T3 (both touch y) — a read still requires ordering against writers to see the right version. T1/T4 are independent of T2/T3 since they share no object.Misconception: that only writes create ordering constraints. A task that reads an object still needs that object's version sequence respected, so reads count too.
Problem 2 · medium
Why can't DeterV pre-generate the fragment for object x's version 7 before any task has committed version 6?
Show answer
A fragment ◦v_x=7 is only a valid claim once the authority •v_x has actually advanced to 7 — the fragment is produced as part of the ghost transition in commit_effects, not handed out speculatively. Pre-generating it would let a task claim a version that doesn't exist yet, breaking the invariant that fragment and authority always agree.Misconception: that fragments are just labels the dispatcher can assign upfront (like it assigns physical version numbers). Ghost fragments are proof artifacts created only by the real ghost transition.
Problem 3 · medium
A task holds fragments for objects x and y but commit_effects opens x's invariant, updates it, closes it, then opens y's invariant separately. What guarantee is lost?
Show answer
Atomicity of the multi-object commit. Between closing x's invariant and opening y's, another worker could observe x already advanced while y is still at its old version — a "half-committed" write set. DeterV avoids this by opening all touched objects' invariants together in one step, so the whole write set advances as one atomic GSM transition.Misconception: that per-object correctness only requires each object's own contract to hold, independently and in any order. Cross-object atomicity is a separate, necessary property for a task with multiple writes.
Problem 4 · hard
Would DeterV's exact same commit_effects contract and ghost-state design work unmodified for an optimistic (execute-validate-commit) runtime? What would have to change?
Show answer
The contract's shape can stay the same — I2 is designed to be scheme-agnostic — but how the precondition gets established changes. A pessimistic runtime establishes "fragment matches authority" by construction, before execution (dependencies are resolved upfront). An optimistic runtime would instead need to establish it via post-hoc validation: after speculative execution, check that the versions the task assumed still match, and only then present the matching fragment to commit_effects. The paper notes this optimistic path is not yet implemented.Misconception: that "verify the effect boundary" only fits designs that resolve dependencies before running. The insight is explicitly meant to unify both scheduling philosophies behind one interface.
Problem 5 · medium
DeterV proves safety but not liveness. Give a concrete bad outcome this leaves possible.
Show answer
A deadlock or livelock — e.g. two tasks each waiting forever on a dependency signal that never fires due to a scheduling bug — is not ruled out. Safety only guarantees that if the system produces a final state, that state equals sequential execution's; it says nothing about whether the system is guaranteed to terminate or make progress.Misconception: that "formally verified" means "provably correct in every respect." Verification targets are scoped explicitly — here, determinism/safety, not progress.
Problem 6 · easy
Why does DeterV treat the concurrent hashmap used for dependency tracking as "trusted" rather than verifying it?
Show answer
It's a widely-used, standard component not specific to DeterV's novel correctness claim — verifying it would spend proof effort on infrastructure rather than the paper's actual contribution (the versioning and commit-boundary machinery). Trusting well-established libraries is a normal, explicit scoping decision in verification projects, not an oversight.Misconception: that anything unverified in the codebase is a gap in the proof. Trusted components are a deliberate, disclosed boundary — the theorem holds relative to them behaving correctly.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does DeterV prove?▾
That under any schedule, the concurrent runtime's final store state equals the state produced by sequential_exec(log) — running the log one task at a time, in order. This is proved as a safety property (not liveness) via a three-layer refinement.
Q2Why can't you just reason about thread interleavings directly?▾
The number of possible interleavings across many concurrently-committing workers is combinatorially large, so a proof enumerating them doesn't scale. DeterV avoids this by localizing correctness to individual objects (I1) and composing, rather than reasoning globally.
Q3What is the "effect boundary" and why is it special?▾
It's the single point — commit_effects — where a task's writes become visible to the rest of the system and successors are unblocked. The paper argues every deterministic design (pessimistic or optimistic) has one, so verifying just this one function's Hoare contract should be enough to isolate the proof from the runtime's internal scheduling choices — though only the pessimistic runtime is actually implemented and verified this way.
Q4What's the difference between the authority and the fragment?▾
The authority (•v_x) is the single, always-defined global truth about object x's version, kept inside a per-object invariant. The fragment (◦v_x) is a task's exclusive, transferable claim that x is at a given version. commit_effects requires them to agree, then advances both together.
Q5Why reuse the existing dependency signal to move fragments?▾
The unverified baseline already orders "producer finished, consumer may proceed" via Tokio's Notify. DeterV's proof design piggybacks the ghost fragment's deposit/withdraw on that same signal slot — though the verified Rust port replaces Notify with a synchronous Mutex/Condvar pair, since Verus didn't support Tokio's async components. Either way, this reuses an existing happens-before edge instead of introducing new synchronization, and guarantees the consumer never withdraws from an empty slot.
Q6What are the three refinement layers, one line each?▾
Sequential spec (trusted reference: run the log in order); GSM (per-object version counters, one atomic step per commit); concurrent runtime (the real, concurrently-executing implementation, carrying the GSM's ghost tokens in pieces).
Q7Is DeterV's overhead really "trivial"?▾
Latency overhead is essentially zero across all tested settings. Throughput overhead is small at low contention (2 objects/txn) but grows with objects touched per transaction, up to a 24% maximum drop at 10 objects/txn — from swapping the lightweight Notify for heavier Mutex/CondVar blocking, not from the proof logic itself.
Q8Why isn't Tokio (async Rust) used directly in DeterV?▾
At the time of writing, Verus did not support the async primitives (Notify, the async runtime) the unverified baseline relies on, so DeterV was ported to a synchronous thread pool with heavier blocking primitives. Async support for Verus was in progress (cited as pending).
Q9What's left unverified ("trusted")?▾
crossbeam-channel and std::thread (thread pool), Mutex/Condvar (one-shot blocking signals), and a concurrent hash map used for dependency tracking — all standard, widely-used components, not the paper's correctness target.
Q10Does DeterV work for more than two runtime designs?▾
The implemented runtime is pessimistic (schedule-execute, based on DORADD). The paper argues, but has not yet implemented, that the same commit_effects API and ghost-state machinery would work for an optimistic (execute-validate-commit) design, since both funnel through one effect boundary.
Q11How is this different from proving linearizability (e.g. vMVCC, DaisyNFS, Armada)?▾
Those systems verify that concurrent operations behave as if executed atomically in some valid order (linearizability/serializability). DeterV verifies something stronger and more specific: that parallel execution reproduces the outcome of one particular, pre-agreed order — the log order — which those systems don't establish.
Q12What's next for this line of work?▾
Verifying an optimistic deterministic runtime and measuring how much of DeterV's machinery is reusable versus needing new proof effort, and extending the approach from a single multicore node to a distributed setting.
