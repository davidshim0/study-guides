Renting out a server you don't fully own

Ten virtual machines think they each have a dedicated box. Only one physical machine actually exists. This is the plain-English story of how VMware's ESX Server lies to every guest OS convincingly enough that they never notice — and reclaims memory from them anyway.

Before you begin

What this paper assumes you already know

A TL;DR, a glossary of the essential terms, then eight short primers. Skip anything you're already solid on.

⚡ TL;DR

  • ESX Server manages memory for unmodified guest VMs using four coordinated mechanisms — ballooning (guest-cooperative reclaim), demand paging (forced fallback), content-based page sharing (dedup), and an idle memory tax layered on proportional shares — so machine memory can be safely overcommitted.
  • Ballooning tracks non-ballooned performance within 1.4–4.4% overhead; content-based sharing found up to 67% content overlap across 10 identical VMs (reclaiming nearly 60% of memory) and reclaimed 7.2–32.9% of memory in three production deployments; raising the idle tax from 0%→75% boosted a starved VM's throughput by over 30%.
  • It matters because it's the first system to reclaim memory intelligently from unmodified commodity OSes — no guest source changes, no new APIs — which is exactly the constraint any OS-transparent memory-tiering system faces today.

1Virtual machines and the VMM▾

A virtual machine monitor sits below one or more guest operating systems, exporting a virtual hardware interface so each guest believes it owns the machine. Unlike VMware Workstation's hosted architecture (which piggybacks on a host OS for I/O), ESX Server manages hardware directly for full control over resource management.

Now you're ready: that direct control is exactly what lets ESX intercept and reshape memory allocation decisions the guest OS thinks it's making unilaterally.
2Guest "physical" memory vs. real machine memory▾

A guest OS expects a zero-based physical address space. ESX gives it that illusion via a per-VM pmap mapping PPNs (guest "physical" page numbers) to MPNs (real machine pages). The guest never sees or controls this second layer of indirection.

Now you're ready: every trick in this paper — ballooning, sharing, remapping — works by silently rewriting PPN→MPN mappings behind the guest's back.
3Page tables, TLBs, and shadow page tables▾

Hardware TLBs cache virtual-to-physical translations read from page tables. ESX intercepts the guest's attempts to install page-table entries and maintains a separate shadow page table with true virtual-to-machine mappings, so ordinary memory accesses hit the TLB directly with no per-access overhead.

Now you're ready: the extra indirection is essentially free at access time — the cost only shows up when ESX decides to remap something.
4Paging and swapping, the classic version▾

When memory is scarce, an OS picks victim pages, writes them to a swap device, and frees the RAM. A replacement policy (LRU, clock, etc.) decides which pages to evict, trading off accuracy against bookkeeping cost.

Now you're ready: ESX could just page VM memory to its own swap disk — but doing so from outside the guest, with no idea which pages the guest cares about, is the core problem ballooning is built to avoid.
5Working sets▾

Denning's classic notion: at any moment, a program is actively using only some fraction of the memory it has ever touched — its working set. Pages outside it are cold and safe to reclaim without much performance cost.

Now you're ready: ESX's idle memory tax is entirely about estimating each VM's working-set fraction cheaply, without any cooperation from the guest OS.
6Proportional-share resource allocation▾

Clients own shares (tickets); a client with twice the shares of another is entitled to roughly twice the resource, degrading gracefully under contention. Min-funding revocation reallocates a resource from whoever has the lowest "shares-per-unit" price to whoever has the highest.

Now you're ready: ESX's memory allocation is proportional-share at its core — the idle tax is just an adjustment to each VM's effective price-per-page.
7Copy-on-write and content hashing▾

Two mappings can point at one physical page marked read-only (COW); a write triggers a fault that makes a private copy. To find candidates for sharing without knowing where duplicates come from, hash each page's contents and look for matches in a table — far cheaper than comparing every page to every other page.

Now you're ready: ESX applies exactly this to find identical pages across unrelated VMs, with no guest OS help at all.
8Overcommitment and admission control▾

Overcommitment means the sum of configured VM memory exceeds physical RAM — useful for consolidation, dangerous if unmanaged. Admission control refuses to start a new client unless the system can still guarantee existing commitments (e.g. reserving a minimum plus overhead before power-on).

Now you're ready: everything else in this paper exists to make overcommitment safe and efficient rather than a recipe for thrashing.
The whole story in one place

ESX memory management in a nutshell

Four mechanisms, one coordinating policy, and a hard constraint: never touch the guest's source.

ESX Server needed to overcommit memory across virtual machines running unmodified commodity operating systems — no source changes, no new APIs, no guest cooperation it couldn't opt out of. A naive approach — a meta-level page-replacement policy that picks victim pages from outside each VM — is fundamentally under-informed: only the guest OS knows which of its own pages are least valuable, and a second, uncoordinated eviction policy can even cause the same page to be paged out twice (the "double paging" problem).

💡
Does ESX manage overcommitment, or prevent it? Manage it — overcommitment isn't a failure mode ESX tolerates, it's the entire point. The abstract says so directly: these techniques "are combined to efficiently support virtual machine workloads that overcommit memory." The reason overcommitment is worth supporting at all is precisely the instinct that most VMs are configured for their peak need but rarely touch all of it at once — statistical multiplexing, the same bet server consolidation always makes. Every mechanism in this guide exists to exploit that gap safely: idle VMs' unused pages get taxed away and handed to active ones, identical pages across VMs get deduplicated, and only a forced, randomized fallback kicks in when a VM's actual demand can't be satisfied any other way. But "manage" doesn't mean "anything goes" — admission control (§5 below) puts a hard floor under it: before a VM is even allowed to power on, ESX reserves real machine memory for its guaranteed min size plus overhead, and reserves disk swap space for the rest (max − min), so that no matter how aggressively the system overcommits above that floor, every VM's minimum commitment can always be honored, worst case via paging. Overcommitment is embraced, not capped at zero — just bounded so it can never become a promise ESX can't keep.

ESX's answer is ballooning: a tiny driver installed in the guest inflates on command, forcing the guest's own memory manager to decide what to reclaim, using its native paging device if needed. When ballooning isn't available or fast enough, ESX falls back to demand paging to its own swap area — this fallback runs entirely on the host side: it's ESX itself swapping a VM's machine pages out to ESX's own disk, using randomized replacement, with the guest never involved or even aware it happened.

Layered on top, an idle memory tax extends proportional-share allocation with a statistically-sampled working-set estimate, so idle VMs are charged more per page and their unused memory drifts to active VMs — without breaking each VM's minimum-share guarantee. Two more mechanisms conserve memory system-wide: content-based page sharing deduplicates identical pages across VMs by hashing content, and hot I/O page remapping moves frequently-DMA'd pages into low, DMA-addressable memory to avoid bounce-buffer copies.

The payoff: ballooning tracks native performance within 1.4–4.4% overhead; page sharing found up to 67% content overlap among identical VMs (reclaiming nearly 60% of their memory) and reclaimed 7.2–32.9% of memory in three production deployments, at under 0.5% space overhead and negligible CPU cost; raising the idle tax from 0% to 75% increased a memory-starved VM's throughput by over 30%.

🍯 Key takeaways

  • Ballooning reclaims memory by letting the guest OS choose the victim pages — sidestepping meta-level policy mismatch entirely.
  • Demand paging is the forced fallback, using randomized (not "smart") replacement to avoid fighting the guest's own algorithms.
  • Working-set fraction is estimated via cheap statistical sampling (100 pages / 30s), not per-page tracking.
  • The idle memory tax (default 75%) reconciles proportional-share fairness with efficient utilization.
  • Content-based page sharing dedups by hashing page contents — no guest hooks, no API changes needed.
  • Hot I/O remapping avoids bounce-buffer copies for DMA into high memory.
  • A four-threshold (high/soft/hard/low) state machine coordinates when to use ballooning vs. paging vs. blocking VMs outright.
Six everyday pictures

How to think about ESX memory management

Each stands alone; each ends with where it breaks down.

Ballooning

Asking a tenant to declutter their own storage unit

Instead of a landlord rummaging through boxes deciding what to throw out, you tell the tenant "free up 30 cubic feet" — they know their own junk best. The balloon driver is that request: it inflates inside the guest, and the guest's own memory manager decides what to page out.

Where it breaks: the tenant might be asleep (guest still booting), have moved out the "manager" (driver disabled/uninstalled), or be too overwhelmed to respond fast enough — exactly ballooning's known limitations.
Content-based page sharing

Two students, one photocopied chapter

A librarian doesn't need to know who photocopied what or when — she just notices two "different" copies have identical text and merges them into one shared original, splitting only if someone starts writing in the margins (copy-on-write). ESX does this by hashing page contents, oblivious to which VM or process the page came from.

Where it breaks: the librarian check ("do the hashes match?") is nearly free, but comparing every page to every other page directly would be O(n²) — which is why hashing, not brute force, is essential.
Idle memory tax

Property tax on an empty lot

Own a big empty lot and you still pay tax on it — more than someone actively farming a small plot, if the town wants land in productive use. ESX's idle tax raises the effective shares-per-page "price" of memory a VM isn't touching, so unused pages drift, via revocation, toward VMs that would actually use them — without ever seizing the whole lot.

Where it breaks: a town sets tax rates by policy vote; ESX's default 75% is a single global knob (tunable per-VM in the implementation but not exposed) — a coarser lever than true differentiated pricing.
Statistical working-set sampling

A pollster, not a full census

You don't interview every citizen to estimate a national opinion — a modest random sample, refreshed periodically, tracks the true trend closely. ESX samples ~100 random pages per VM every 30 seconds, checks how many were touched, and estimates active-memory fraction from that ratio — no per-page tracking of all of memory.

Where it breaks: a pollster assumes voters don't change their mind the instant they're asked; ESX addresses the analogous risk with three moving averages (slow/fast/current) and takes the max, to react fast to growth without over-reacting to noise.

Moving your most-used files to the desk drawer

Documents you touch constantly belong in the drawer nearest you, not the far filing cabinet down the hall — the trip cost adds up fast. The full explanation

How it actually works

Mechanism by mechanism, with the paper's numbers.

0 · ESX, VMkernel, and VMM — who's who

"ESX Server" is the umbrella name for the whole product. Underneath that name are two distinct kinds of component: one VMkernel, shared across the whole host, which is the privileged resource-management kernel that schedules CPU, allocates memory, and multiplexes disk/network across every VM running on that machine; and one VMM (virtual machine monitor) per running VM, which is the component that does the actual low-level virtualization work for that one VM specifically, trapping its privileged instructions and maintaining its pmap and shadow page table. So "the VMM" and "the VMkernel" are not the same thing, and neither is simply "ESX" — ESX is VMkernel + one VMM per VM + a thin management layer on top.

This is also a bare-metal (type-1) design, not hosted (type-2), and the difference matters for everything in this guide. Compare them directly:

The shape above (apps/OS pairs, on virtual hardware, on one VMM layer, on the real machine) is a generic VMM teaching diagram, not specific to ESX, VMware, or even x86, and predates ESX Server by years. ESX's actual contribution isn't this stack shape, which Section 8 of the paper itself traces back through Disco to IBM's VM/370; it's everything in this guide about how memory specifically gets managed within that stack for unmodified guests.

1 · Virtualizing memory — one extra layer of indirection

ESX gives each VM a zero-based "physical" address space backed by a per-VM pmap translating PPNs to MPNs. Guest attempts to manipulate page tables or the TLB are intercepted; a separate shadow page table holds true virtual-to-machine mappings for the hardware to use directly, so ordinary accesses incur zero extra overhead. This indirection is what makes every later trick possible: ESX can remap a "physical" page's backing MPN completely transparently to the guest.

Where does each of these three things actually live? The guest's own page tables (VPN→PPN) are guest-managed and guest-visible: they physically occupy some of the guest's own "physical" pages, exactly like any OS's page tables occupy real RAM on bare metal, and the guest reads them freely. ESX only intercepts writes to them, by write-protecting those pages, so it can observe every change the guest makes. The pmap and the shadow page table are the opposite: both are maintained entirely by the VMM, in the hypervisor's own privileged memory, completely outside the guest's address space — one instance of each per VM (recall from earlier: ESX runs one per-VM VMM instance per running virtual machine), but "per-VM" means the VMM keeps a separate copy of its own bookkeeping for each VM, not that the bookkeeping lives inside that VM. The guest has no instruction, no API, and no memory access that can read or touch its own pmap or shadow page table; as far as the guest can tell, neither one exists.

How a guest page-table write actually reaches the shadow table: when the guest installs a new VPN→PPN entry (or switches address spaces by writing a new page-table-base register value, CR3 on x86), that write hits one of the pages ESX write-protected, so it traps straight into the VMM. The VMM's trap handler reads what the guest was trying to write, looks up the current MPN for that PPN in the pmap, completes the guest's own store into its page table (the guest will read that entry back later, so it must really be there), and updates or drops the composed VPN→MPN entry in the shadow page table, all before letting the guest's instruction stream continue. (The paper says only that such instructions are intercepted and the shadow tables kept consistent; write-protection is the standard way to intercept, see Part II M2.) The guest never knows this handoff happened; from its side, the write just... took effect, same as it would on real hardware.

Did ESX invent this indirection? No — the pmap and shadow-page-table substrate predates the paper. The authors cite Disco (Bugnion, Devine, Govil, Rosenblum, 1997, from the same Stanford lab that founded VMware) as the direct ancestor of the PPN→MPN "physical-to-machine" mapping, and VMware's own first product, VMware Workstation, already used shadow page tables to virtualize the MMU for unmodified x86 guests years before ESX Server existed. The paper's actual contribution sits on top of this known substrate: ballooning, the idle memory tax, production-scale content-based sharing, and hot I/O remapping. Pmap isn't the novelty here, it's the foundation the novelty is built on.

Why pmap is essential to everything else in this guide: every mechanism below is really just a different policy for deciding when to rewrite a pmap entry. Ballooning clears a PPN's entry once the balloon driver has pinned it, there's nothing left to back. Demand paging does the same, but first records where the evicted data went on disk, then refills the entry on the resulting fault. Content-based sharing points two VMs' PPNs at one shared MPN through pmap, splitting them again (fresh MPN, fresh entry) on a copy-on-write fault. Hot I/O remapping (§6) just swaps which MPN a PPN's entry points to. Without this layer, a guest's page tables would point straight at real machine memory as on bare metal, and ESX would have no lever to reclaim, share, or relocate anything without modifying the guest, exactly the constraint the paper opens with.

2 · Reclamation: ballooning first, paging as forced fallback

ESX prefers ballooning: a guest-resident driver polls once per second for a target size, then allocates (or frees) pinned pages via native OS interfaces (get_free_page() on Linux; MmAllocatePagesForMdl() on Windows). The guest's own memory manager decides what to evict to satisfy that allocation — sidestepping the fundamental problem that only the guest knows which of its pages are least valuable.

When ballooning is unavailable (driver missing, guest booting, insufficient headroom), ESX falls back to demand paging to its own swap area, using deliberately randomized replacement — not a "smarter" policy — specifically to avoid the double-paging pathology and unintended interference with the guest's native algorithms.

🖥️
Where does demand paging actually run? Entirely on the host side — it's the VMkernel/VMM itself, not the guest, choosing a victim machine page, writing its contents out to ESX's own disk-based swap file, and clearing that PPN's pmap entry. The guest OS has no part in this and no idea it happened; it's a completely separate mechanism from whatever paging the guest OS does to its own virtual disk-backed swap device. Two independent swap systems exist stacked on top of each other: the guest's own (which ballooning deliberately leans on), and ESX's forced fallback underneath it, invisible to the guest.

What exactly happens on the later fault — does the guest just get a fresh blank page? Only for ballooning; demand paging is different, and it's worth keeping the two straight. Clearing a PPN's pmap entry is step one in both mechanisms, and both make the next guest access to that PPN fault into the VMM — but what happens next depends on why the entry was cleared. If the page had been ballooned, nothing meaningful was ever written there (the driver just pinned it and let it sit), so ESX can satisfy the fault with any fresh, zeroed machine page — correctness doesn't depend on the old contents at all, since there weren't any that mattered. If the page had instead been demand-paged out, its actual contents are sitting in ESX's own swap file, and the guest may very well come back and touch it again expecting to see what it wrote — so the fault handler has to perform a real page-in: read that page's data back off disk into a newly-allocated machine page, then repoint the pmap entry at it, before letting the faulting instruction continue. Same trigger (a cleared pmap entry, a guest access, a VMM-handled fault), but one path is a free zero-fill and the other is an actual, I/O-bound restore — which is also exactly why ESX prefers ballooning whenever it can: a ballooned reclaim never has to pay this round-trip back.

What if the VM reboots or crashes before touching that page again? Same fault, same fresh-zero-page handling, nothing reboot-specific about it. ESX has no notion of "this VM just rebooted" as a distinct event; from its side, a reboot just means a new guest kernel instance eventually touches that PPN like any ordinary allocation, trapping in because no valid mapping exists, and gets a fresh zeroed MPN exactly as described above. The paper's own framing is that the balloon gets "popped": the next interaction with any instance of the driver, old or new, resets its state rather than assuming it can pick up where a previous instance left off, which matters because the new boot genuinely has no memory of the earlier arrangement.

And for a VM's ordinary (non-ballooned) memory — does rebooting notify ESX and clear out the pmap or shadow page table? No notification, and nothing gets proactively deleted; this follows from the mechanism rather than being a separate case the paper calls out. A reboot, at the hypervisor level, is indistinguishable from the new kernel simply writing a fresh set of its own VPN→PPN page tables, exactly as any OS does on boot. ESX intercepts those writes the same way it intercepts any guest page-table write, and rebuilds the shadow page table's VPN→MPN entries to match, incrementally, as the new kernel's writes arrive, not as a bulk flush triggered by "reboot." The pmap (PPN→MPN) underneath doesn't need to change at all: those machine pages are still allocated to that VM exactly as before, still holding the previous kernel's now-irrelevant bytes, which the new kernel just overwrites as it uses them. The only way reboot touches the pmap is if some of those PPNs happen to have been separately reclaimed by ESX itself (ballooned or demand-paged) before the reboot, in which case the fresh kernel's first touch hits exactly the stale-pmap-entry fault path just described, no different for being "ordinary" memory instead of a balloon page.

If ballooning exists specifically because only the guest knows which pages matter, why does demand paging turn around and pick its own victim anyway — isn't that the same mistake? It would be, if ESX tried to pick well. It deliberately doesn't. Building a smarter meta-level victim-selection policy for the fallback path would reintroduce the exact problem the paper's §3.1 already identifies: the host still has no way to know which of a VM's pages the guest values least, so any attempt to be clever is just as uninformed as the "naive approach" the paper opens by rejecting, with the added risk of actively fighting the guest's own policy (the double-paging pathology from the paper's §3.1). Random sidesteps that by not pretending to be informed at all — it's cheap, it can't be gamed by a mismatch with guest behavior, and because the paper expects paging to be a rare, short-lived fallback rather than the system's everyday mechanism, the cost of an occasional suboptimal pick is small compared to the cost (and risk) of building and maintaining a second decision-making layer that's trying to solve a problem ballooning already solves better whenever it's available. So it isn't "ballooning trusts the guest, then paging takes the decision back" — it's "ballooning gets it right by asking the only party with real information, and paging is a deliberately dumb safety net for the moments that party isn't available to ask."

Why "ballooning," and whose code is it? The name describes the driver's own footprint inside the guest: "inflating" means pinning more and more pages, which squeezes out other consumers of the guest's fixed-size memory exactly like a balloon expanding inside a sealed box displaces whatever else is in there; "deflating" shrinks that pinned region back down and frees the space for ordinary use. The driver itself (vmmemctl, shipped as part of VMware Tools) runs inside the guest kernel, using the guest's own allocation APIs — ESX distributes it, but it executes entirely in guest context, not inside the hypervisor. The VMM side only ever talks to it over a private channel to set a target size; it never touches guest memory directly.

What "target" actually means. It's each VM's target allocation — how much machine memory that VM is currently entitled to hold — not a quota of how much it owes back. Targets differ per VM: they fall out of the same shares-plus-idle-memory-tax formula from §4, so a low-share, mostly-idle VM gets a lower target than a high-share, fully-active one, and a VM starting up gets whatever target the admission-control reservation guarantees it. Ballooning and demand paging are just the two mechanisms that nudge a VM's actual holdings toward its current target — inflating/paging when actual exceeds target, deflating when a VM's target rises and it needs memory back.

Does the guest ever think it's giving up "idle" memory, or could it try to reclaim a ballooned page later? No — ownership genuinely passes to the driver, by the guest's own rules, which is exactly why the trick works:

  1. 1 · New target arrives. ESX sends the driver a new target size over their private channel.
  2. 2 · An entirely ordinary allocation call. The driver requests pages via the guest kernel's own allocation routine — the identical API any other kernel driver would use. Nothing about the call looks special to the guest.
  3. 3 · The guest's own eviction, if it's needed at all. The guest's memory manager satisfies the request exactly like any legitimate one: free pages first, or evicting/swapping something out under its own native policy if it's genuinely under pressure.
  4. 4 · The pages become "owned," not idle. Once granted, the guest's own bookkeeping marks them as allocated to the driver — not free, not idle. The guest will never try to hand them to anyone else or page them out later; as far as it knows, they're a legitimate driver's pinned buffer, same as any other.
  5. 5 · The driver reports those PPNs to the VMM. It tells the hypervisor exactly which guest-physical pages it's now holding.
  6. 6 · The machine page is reclaimed — with zero I/O. Since the driver never writes anything meaningful into a ballooned page, there's no content worth preserving, so ESX can unmap the real machine page behind it immediately. No swap write, unlike real paging.
  7. 7 · Deflation reverses it. When the VM's target rises again, ESX shrinks the balloon, the driver frees its pinned pages back to the guest's ordinary allocator, and the VMM lazily backs any newly-touched page with a fresh machine page on demand.
💡
Ownership is never secretly taken out from under the guest — its belief that the driver owns that memory is correct by construction. The only thing missing is on the host side: what's actually backing the page behind the scenes.
⚠
Ballooning's real limits: the driver can be disabled, uninstalled, unavailable during boot, or simply too slow to keep pace with sudden pressure — which is exactly when the hard paging fallback kicks in.

3 · Content-based page sharing

ESX hashes each scanned page's contents (a 64-bit hash) and looks it up in a global table. A match triggers a full byte comparison to rule out hash collisions, then both PPNs are remapped to one MPN and marked copy-on-write; a subsequent write faults and creates a private copy. Unmatched pages are kept as cheap hint frames rather than immediately marked COW, avoiding needless write-fault overhead. Each table entry is a compact 16 bytes, and highly-shared pages (like the all-zero page) use a small reference count with overflow, keeping total space overhead under 0.5% of system memory.

What's a hint frame, exactly? You're right that an unmatched page has nothing to do with copy-on-write yet, that's exactly the point. A hint frame is just a cheap table entry recording "this PPN had this hash, as of the last scan" — the page itself stays completely ordinary: full read/write access, not write-protected, not shared, not COW. Write-protecting it only pays off if something else eventually matches; if ESX write-protected every scanned page up front on the chance of a future match, the owning VM's very next ordinary write to that page would trigger a write fault for no reason, since nothing was actually being shared yet. So the hash is stored as a lightweight hint and the page keeps running untouched. Only when a second page is later scanned and its hash matches an existing hint does ESX do the expensive part — the full byte comparison, then write-protecting both pages and remapping them to one shared MPN. A hint frame is essentially a sharing opportunity on hold, promoted into real COW sharing only the moment a second match actually shows up.

4 · Shares, idle memory, and the tax

Pure proportional-share allocation partitions memory by shares alone — an idle client with many shares can hoard memory while an active, low-share client starves. ESX fixes this with an idle memory tax: idle pages are charged more than active ones in the shares-per-page ratio used by min-funding revocation:

rho = S / ( P · (f + k·(1 − f)) )      where  k = 1 / (1 − tau),  0 ≤ tau < 1
# S = shares, P = pages allocated, f = active fraction, so P·f active pages + k·P·(1−f) idle pages are "charged"
# tau = 0     → k = 1: pure share-based allocation (idle pages cost the same as active ones)
# tau = 0.75  → k = 4: each idle page is charged like four active pages (the default)
# tau → 1     → k → ∞: all of a client's idle memory can be reclaimed

Working-set fraction (active_pages ÷ total) is estimated by sampling: each period, ~100 random pages have their mappings invalidated; the next touch is intercepted and counted, giving a statistical estimate at negligible cost (≤100 minor faults per 30-second period).

What exactly gets counted. The "100" is 100 distinct pages, chosen at random up front for that period, not 100 accesses. Each sampled page gets a binary check for the whole period: touched at least once, or never touched, there's no count of how many times. A page hit once and a page hit a million times both register identically as "active." So two edge cases fall out directly: if a VM's entire real workload hammers just one page nonstop, the estimate still depends on whether that one page happened to land in this period's random 100 — if it did, that's 1 of 100 touched, roughly 99% idle; if it didn't (far more likely when a VM has thousands of pages total), 0 of 100 touched, meaning the sampler estimates the entire VM as idle, despite that one page being hammered constantly. That's not a blind spot to worry about, it's the correct answer to the question the tax is actually asking: a VM whose real working set is one page genuinely doesn't need the rest of its allocated memory, no matter how hot that one page runs. Conversely, if all 100 sampled pages get touched at least once, the estimate is 100% active for that period, correctly signaling a workload with a genuinely broad footprint.

Is it the same 100 pages every period, or a fresh draw? A fresh draw, every single period — "at the start of each sampling period, a small number of the VM's pages are selected randomly," not once at VM boot. Two things follow directly from that. First, there's no permanent blind spot: a page that didn't happen to land in this period's sample of 100 can still land in next period's, and over enough 30-second periods essentially all of a VM's memory gets a turn. Second, each period's estimate is consequently a fresh, independent, somewhat noisy draw rather than a running tally — which is exactly why the system can't just trust one period's number outright and instead keeps three separate moving averages (slow, fast, and a fast one that also folds in the current period's partial counts) and reports the max of the three. That combination is what lets a VM that goes from idle to active ramp up its allocation quickly (the fast average reacts at once) while a VM that goes from active to idle only loses its allocation gradually (the slow average drags it down slowly) — reacting fast to growth, cautiously to shrinkage, which is the deliberately asymmetric behavior the paper wants.

5 · Coordinating it all — thresholds and admission control

Free memory is tracked against four thresholds — high (6%), soft (4%), hard (2%), low (1%) of system memory. Above high, no reclamation occurs; in the soft state, ballooning is used to proactively reclaim memory; in the hard state, paging is used to forcibly reclaim; below low, VMs above their target are additionally blocked from running. Hysteresis prevents state flapping. Before any VM powers on, admission control reserves machine memory for its min size plus overhead (typically ~32 MB: 4–8 MB frame buffer, the rest virtualization data structures) and disk swap space for max − min, guaranteeing the system can always honor commitments.

Where do the specific numbers 6/4/2/1% come from — is it just heuristics? Mostly yes, and the paper says so directly rather than deriving them: "most operating systems attempt to maintain a minimum amount of free memory. For example, BSD Unix normally starts reclaiming memory when the percentage of free memory drops below 5% and continues reclaiming until the free memory percentage reaches 7%... ESX Server employs a similar approach." So the starting point isn't a formula, it's existing OS practice — BSD's own single hysteresis band (reclaim below 5%, stop at 7%) is the direct ancestor of ESX's thresholds and the reason they're percentages of total memory rather than fixed MB amounts (so the same policy scales automatically from a small host to a huge one). What ESX adds on top of that borrowed idea is structural, not numerical: instead of BSD's one on/off band, ESX splits the space below the "stop reclaiming" line into four graduated bands, so the response gets progressively more aggressive as the situation gets worse — nothing, then gentle/guest-cooperative (ballooning), then forceful/host-side (paging), then an emergency measure (blocking VMs above target) — rather than jumping straight from "fine" to "forced eviction." The specific spacing (6, 4, 2, 1) gives each adjacent pair of thresholds enough of a gap to serve as its own hysteresis band (the system only climbs back to a higher, calmer state after significantly exceeding it, not the instant it ticks back over), so thresholds also do double duty as anti-flapping margins, not just severity labels. Nothing in the paper suggests 6/4/2/1 specifically were tuned against a cost model; they read as "a reasonable, BSD-flavored default that shipped," with the real engineering content being the four-state graduated structure and the hysteresis rule, not the exact percentages.

6 · Hot I/O page remapping — a performance trick, not a capacity one

Some DMA-capable devices (the paper's example: 32-bit PCI NICs) can only address the lowest 4 GB of physical memory, a hardware address-line limit, not a software one. If a page involved in a transfer is backed by machine memory outside that low range, the device can't DMA to it directly, so the transfer has to be staged through an intermediate bounce buffer sitting in low memory: incoming data is DMA'd into the bounce buffer first, then CPU-copied up to its real destination; outgoing data is copied down to the bounce buffer first, then DMA'd out. The data is said to be "bounced", it takes that detour through the intermediate buffer instead of going straight to where it actually needs to be, the same sense as a "bounced check" getting redirected through an extra stop. That detour costs a full extra memory-to-memory copy on every single transfer.

ESX tracks a per-page bounce count, and once a page crosses a threshold (it's "hot"), it transparently relocates that page's backing MPN into low, DMA-addressable memory, via the same pmap rewrite used everywhere else in this guide, copying the data over once at remap time. After that, the device can DMA straight into or out of the page, with no bounce copy, on every future transfer. It's done ahead of time specifically so the copy never has to happen again.

🔗
How this relates to ballooning: it doesn't, directly, and that's worth being explicit about. Ballooning, demand paging, and content-based sharing are all about capacity, freeing or deduplicating machine memory so VMs can be overcommitted. Hot I/O remapping saves no memory at all, it's purely a performance trick that trades a page's location for eliminating a redundant copy during I/O. The only thing it shares with the capacity mechanisms is the underlying lever: pmap indirection lets ESX relocate a page's backing MPN for any reason, whether that reason is reclaiming memory or avoiding a bounce-buffer copy.
⚠
Where it breaks: low memory is finite and can itself become scarce as more pages get promoted into it, so ESX also has to weigh evicting cold low-memory pages back up to high memory, a cost/benefit tradeoff the paper leaves partly as future work.

M1 · Three address spaces and the pmap

Three kinds of page number appear in every mechanism below. A VPN is a virtual page number inside a guest process. A PPN is a guest "physical" page number: the guest believes it owns a zero-based, contiguous physical memory of its configured max size, and PPNs number that illusion, separately for each VM (PPN 7 in VM 1 and PPN 7 in VM 2 are unrelated). An MPN is a real machine page. The guest's page tables map VPN → PPN. ESX's per-VM pmap maps PPN → MPN. The terms "machine" and "physical" are borrowed from Disco. (Paper §2)

What a pmap entry has to record. The paper names the pmap's job (PPN → MPN) and, in different sections, the extra states an entry can be in. Collected in one place:

Allocation rules for a new MPN (footnote 2). ESX zeroes every newly allocated machine page so that no data leaks from one VM to another, and it respects the guest's cache coloring: when possible, distinct PPN colors are mapped to distinct MPN colors. Coloring matters because the guest OS spent effort placing virtually adjacent pages on PPNs of different colors; if ESX backed them with MPNs of one color, the physically indexed cache would see conflicts the guest thought it had avoided.

The pmap is a forward map. For private pages ESX could keep a reverse record (which VM and PPN a machine page belongs to), and hint frames do store a back reference (VM, PPN). But for a shared machine page ESX keeps only a reference count, deliberately unlike Disco, which kept a backmap of every sharer (§4.3). Consequence (inference): ESX can drop one sharer's reference (a COW break, a balloon allocation) but cannot enumerate the PPNs that point at a shared MPN without searching every pmap. Anything that wants to move a shared MPN in place, rather than give one sharer its own copy, runs into this.

Invariant. At every moment each PPN of each VM is in exactly one of the states in the table, and any guest access to a PPN that has no MPN traps to ESX before it can complete. That trap is what makes every mechanism transparent: ESX can take the MPN away for any reason, as long as it can restore correct contents (zeroes for an untouched or ballooned page, the swap copy for a paged-out page, a private copy for a COW page) before the access completes.

Cost. The pmap and shadow page tables are part of each VM's overhead memory, which admission control reserves up front: typically 32 MB per VM, of which 4 to 8 MB is the virtual frame buffer and the rest implementation data structures; more for VMs larger than 1 GB (§6.2).

M2 · Shadow page tables: what is cached where

Why they are needed at all. On IA-32 the hardware itself walks the in-memory page tables on a TLB miss and reloads the TLB (paper footnote 1). The walker reads one table format, Intel's, and performs one translation, VPN → frame. It cannot be told "first translate through the guest's table, then through the pmap." So the VMM must hand the hardware a real page table whose entries already contain MPNs. That table is the shadow page table, and the hardware CR3 register points at it, not at the guest's table. This is what the lecture slide means by "required to use Intel MMU." (On an architecture with a software-reloaded TLB, such as the MIPS machines Disco ran on, a VMM can instead compose the two maps in software on each TLB miss; this guide's note, not the paper's.)

The paper's claim for the design is precise: ordinary memory references run "without additional overhead, since the hardware TLB will cache direct virtual-to-machine address translations read from the shadow page table" (§2). The costs land elsewhere: on guest page-table updates, on guest context switches (CR3 loads), and on every pmap change.

    only then free or reuse the old MPN

Invariant. Every shadow PTE and every TLB entry equals the guest's PTE composed with the current pmap entry, and grants no more rights than either: an entry is writable only if the guest PTE allows writes and the PPN is private. A COW-shared PPN is mapped read-only even where the guest thinks the page is writable; that is how the write fault in M8 happens. A PPN being sampled for the idle estimate (M11) has its cached mappings removed entirely, which is exactly the paper's wording: sampling invalidates "any cached mappings associated with its PPN, such as hardware TLB entries and virtualized MMU state."

The ordering rule, and what breaks without it. When ESX takes a machine page away, the pmap update and the invalidation of every cached translation must happen before the MPN is reused. If a stale shadow PTE or TLB entry survived, the VM could keep reading or writing a machine page that now belongs to another VM: a direct isolation failure. This is the single property all of ballooning, paging, sharing and remapping lean on.

Granularity. Every mechanism in the paper acts on one PPN, one 4 KB page, at a time: the balloon driver reports individual PPNs, sharing compares whole 4 KB pages, paging and sampling select individual PPNs, and COW protection is per page. The paper does not discuss large pages at all. Keep this in mind for the 10/13 superpages lecture: a single large-page TLB entry needs a contiguous, aligned run of frames with one set of protections, and nothing in the pmap keeps a guest's contiguous PPNs on contiguous MPNs.

M3 · The life of a guest page

Every mechanism in the paper is a transition between the pmap states of M1. Drawing them as one state machine makes two things visible. First, every arrow is taken either by ESX on its own initiative or by a guest access that traps; the guest never takes an arrow knowingly, which is the transparency requirement. Second, the arrows that need disk I/O at ESX's level are exactly the two that touch the swapped state; ballooning reaches "no MPN" without ESX writing anything.

M4 · Why a second, independent pager goes wrong

The classic way to overcommit a VMM is a second level of paging: the VMM moves some guest "physical" pages to its own swap disk (§3.1 cites VM/370 and Cellular Disco). The paper gives two separate reasons this is a poor primary mechanism.

1. It is uninformed. A meta-level pager has to choose both the VM to take memory from and the particular pages. The best information about which pages are least valuable is held only by the guest OS. The paper's point is that cleverness does not fix this: "this is actually the crux of the problem." A sophisticated meta-level policy is likely to cause anomalies through unintended interactions with the guest's own policy, and guest policies are diverse, often undocumented, vary across versions, and may depend on application hints.

2. Double paging, which happens "even when the meta-level policy is able to select the same page that the native guest OS policy would choose." Step by step:

# double paging, one page p of one VM
t0  ESX picks p, writes it to the ESX swap area, frees p's MPN      # disk write #1 (ESX)
t1  guest comes under its own pressure and picks the same p as its victim
t2  guest reads p to copy it to its virtual disk → p has no MPN → trap
    ESX allocates an MPN and reads p back from its swap area         # disk read  #2 (ESX)
t3  guest writes p to its own virtual paging device                  # disk write #3 (guest)
t4  guest reuses p's frame for something else; ESX's copy is garbage
# result: three disk transfers to move one page that the guest alone would have moved with one

This guide's reading of the quoted condition: the more closely ESX's victim choice agrees with the guest's (for example both approximate LRU over the same reference stream), the more often t1 picks the page ESX already took, so a "better" meta-level policy makes double paging more frequent, not less. ESX's random victim choice (M6) does not make double paging impossible; it makes ESX's choice uncorrelated with the guest's, so coincidences stay at chance level instead of being systematic. Ballooning (M5) removes the problem at its root, because ESX never holds the swapped contents of a page the guest might itself decide to evict: all eviction decisions and all paging I/O stay inside the guest.

M5 · Ballooning, precisely

Components. A small balloon module loaded into the guest "as a pseudo-device driver or kernel service." It has no interface inside the guest; it talks to ESX over a private channel. ESX shipped drivers for Linux, FreeBSD and Windows. Each driver polls the server once per second for a target balloon size and limits its allocation rate adaptively to avoid stressing the guest. It allocates with standard kernel interfaces: get_free_page() on Linux, MmAllocatePagesForMdl() or MmProbeAndLockPages() on Windows. (§3.2)

# guest side (balloon driver), once per second
target = ask_esx_over_private_channel()
if size < target:                                    # inflate
    for a rate-limited batch:
        page = guest_alloc_pinned_page()                  # native API; the guest's own VM system
                                                          # chooses what to free or page out to satisfy it
        tell_esx(ppn_of(page))
elif size > target:                                  # deflate
    for a batch: page = pop_my_list(); guest_free_page(page)

# ESX side
on balloon_report(vm, ppn):
    annotate pmap[vm][ppn] = BALLOONED; invalidate cached mappings; free the MPN   # no disk I/O
on guest access to a BALLOONED ppn:                       # should not happen; "rare"
    "pop" the balloon: next interaction with any instance of the driver resets its state
    back the ppn with a new zeroed MPN, "just as if the page was touched for the first time"

What the guest experiences. Only memory pressure. When it has plenty of free memory, it satisfies the driver from its free list and nothing is lost. When memory is scarce, it must reclaim, and it does so with its own policy, paging to its own virtual disk if needed. The design goal is stated as an ideal: a VM whose memory was reclaimed "should perform as if it had been configured with less memory."

Invariant and what it does not depend on. A ballooned PPN never has an MPN and never holds data the guest needs. ESX does not rely on the guest honoring the pin for correctness: if the guest touches a ballooned page, the access traps, ESX pops the balloon and backs the page with a zeroed MPN. Guest good behavior affects efficiency, never ESX's correctness or isolation between VMs. A useful what-if (inference): a buggy driver that reported a PPN the guest was still using would make ESX free a live page; the next access would trap and get a zero page, corrupting that one guest, but no other VM could see or lose data, because the replacement MPN is freshly zeroed.

M6 · ESX demand paging, the fallback

When it runs. "When ballooning is not possible or insufficient" (§3.3). In the soft reclamation state ESX pages only where ballooning is not possible; in the hard state it relies on paging (M12). Admission control has already reserved swap space for every VM's max − min, so a page-out never fails for lack of space.

Mechanism. An ESX swap daemon receives a target swap level for each VM from the higher-level policy module, selects candidate pages, and coordinates asynchronous page-outs to the swap area, using "conventional optimizations" to keep free slots available and to cluster disk writes. Victims are chosen at random, to avoid the interference described in M4 and because paging is expected to be uncommon; the paper mentions investigating smarter and per-VM policies as future work. Before paging a page out, ESX always tries to share it (§4.3), which costs a hash and maybe a compare instead of a disk write and is very effective for zero pages (325 MB of zero pages shared versus 35 MB written in Figure 8).

# swap daemon for one VM (sketch; selection and ordering details beyond the paper are inference)
while swapped(vm) < target_swap(vm):
    ppn = random PPN of vm that currently has an MPN
    if try_share(vm, ppn): continue                    # "share before swap"
    invalidate cached mappings of ppn                    # the guest must not write during the copy-out
    slot = take a free slot; start async clustered write of the MPN to slot
    on write complete: pmap[ppn] = SWAPPED(slot); free the MPN
on guest access to a SWAPPED ppn:                        # an invisible fault (M7)
    mpn = allocate; read slot into mpn; pmap[ppn] = mpn; free slot; resume the vCPU

Invariant. A page's current contents are always recoverable from exactly one place, its MPN or its swap slot. The ordering inside the sketch follows from that (inference): mappings must be removed before the copy-out starts, or a guest write during the asynchronous write would be lost when the MPN is freed; the MPN may be freed only after the write completes.

Cost compared with ballooning. A ballooned page costs ESX no I/O at all, and the guest's own paging (if any) happens on pages the guest judged cold. An ESX-paged page costs a write now and a synchronous read later on any guest touch, and that read stalls the whole virtual CPU (M7). That asymmetry, plus M4, is why ballooning is "a common-case optimization" and paging the fallback.

M7 · Invisible (ESX-induced) versus visible (guest) page faults

Two very different events both look like "a page fault" from far away. The paper does not discuss this contrast explicitly; it follows from M2 and M6, and this section is this guide's reading.

A visible fault happens when the guest's own PTE does not allow the access: the guest paged the page out itself, never mapped it, or protected it. The VMM reflects the fault into the guest, and the guest OS's page-fault handler runs. The guest knows the faulting process is waiting for disk; it marks that process blocked, starts the read on its virtual disk, and schedules some other runnable process. When the read completes, an interrupt wakes the faulting process.

An invisible fault happens when the guest's PTE is fine but the pmap has no usable MPN: the page was paged out by ESX, is shared and being written (COW), is being sampled, was never touched, or was ballooned and is touched anyway. ESX resolves it and resumes the guest at the same instruction. Most invisible faults are cheap (a zero-fill, a 4 KB copy for COW, re-establishing a sampled mapping). The expensive one is an ESX swap-in, which must wait for a disk read. During that wait the virtual CPU executes no guest instructions at all. The guest OS gets no control, so it cannot run another of its processes, cannot service its own timer on that virtual CPU, and later sees only that time passed. ESX itself can run a different VM on the physical CPU in the meantime.

M8 · Content-based page sharing, in full

The idea and its price. Identify copies by content, so pages can be shared "regardless of when, where, or how those contents were generated." This needs no guest modification and finds every shareable page by definition. The price is scanning work: comparing every page with every other is O(n²), so ESX hashes. (§4.2)

Data structures (§4.3, Figure 3). One global hash table holds a frame for every scanned page, with chaining for collisions. Each frame is 16 bytes.

Frame typeFieldsWhy those fields
Shared frame64-bit hash · MPN of the shared page · 16-bit reference count · chain linkFinding a match needs the full hash; using the match needs the MPN; freeing it needs the count. No list of sharers is kept (Disco kept a backmap; ESX does not).

Total space overhead is under 0.5% of system memory. (This guide's arithmetic: one 16-byte frame per 4096-byte page is 0.39%, so even a frame for every page stays under the bound.)

The hash and the "unique hash" simplification. A fast, high-quality 64-bit hash (Bob Jenkins) is computed per scanned page. Footnote 3: with random 64-bit values, the chance of any collision does not reach 50% until about √(2⁶⁴) = 2³² distinct pages are hashed; for a static snapshot of the largest IA-32 configuration, 2²⁴ pages (64 GB), it is below 0.01%. So ESX assumes every shared page has a unique hash value. A page that produces a false match (same hash, different bytes) is simply declared ineligible for sharing. That keeps the table simple: one hash value names at most one shared frame. Correctness never depends on the hash, because every merge is preceded by a full byte comparison.

# one scan step (§4.2, §4.3; ordering details are the paper's prose turned into steps)
def try_share(vm, ppn):
    h = hash64(contents(vm, ppn))
    f = table.lookup(h)
    if f is None:
        table.insert(HINT(trunc(h), vm, ppn))            # page stays private and writable
    elif f.kind == SHARED:
        if bytes_equal(contents(vm, ppn), f.mpn):
            old = pmap[vm][ppn]; pmap[vm][ppn] = COW(f.mpn); f.refs += 1   # overflow table past 16 bits
            invalidate cached mappings of ppn; free(old)   # the redundant copy is reclaimed
        else: mark ppn ineligible                          # a false match
    else:                                                # f is a HINT for (vm2, ppn2)
        if hash64(contents(f.vm, f.ppn)) != h:           # rehash: has the hinted page changed?
            table.remove(f)                              # stale hint (then this page can become a hint)
        elif bytes_equal(contents(vm, ppn), contents(f.vm, f.ppn)):
            m = pmap[f.vm][f.ppn]
            replace f by SHARED(h, m, refs = 2)
            pmap[f.vm][f.ppn] = COW(m); pmap[vm][ppn] = COW(m)
            invalidate cached mappings of both; free the MPN that backed (vm, ppn)

on guest write to a COW ppn:                              # "transparently creating a private copy"
    new = allocate MPN; copy 4 KB from the shared MPN; pmap[ppn] = new (writable)

Why hints instead of marking every scanned page COW. Marking an unmatched page COW "in anticipation of some future match" would make every later write to every scanned page take a fault, for pages that may never match anything. A hint costs nothing until a second page with the same hash shows up; then the hint is revalidated by rehashing, and only an unchanged, byte-identical pair is write-protected. The lecture slide asks exactly this: "Why don't they hash or enter every scanned page?" (as COW).

Scan policy. The paper lists options (scan at a fixed rate; sequentially, randomly, or by heuristics such as pages the guest marked read-only or pages that executed code; only in idle cycles). The implementation scans guest pages randomly, with configurable maximum per-VM and system-wide scan rates set so that sharing costs negligible CPU. It also always tries to share a page before paging it out.

A simple model explains every shape (this guide's model, not the paper's): if a fraction s of each VM's M MB is common to all N VMs, then shared ≈ s·N·M, the copies kept ≈ s·M, and reclaimed ≈ s·(N − 1)·M. As percentages: shared → s (flat once N ≥ 2), reclaimed = s·(N − 1)/N (rising toward s), shared − reclaimed = s/N (falling). With s ≈ 0.67 this predicts about 33% reclaimed at two VMs and 60% at ten; the plot shows about 36% and nearly 60%. The paper's own observations: some sharing already happens inside a single VM (nearly 5 MB, about 55% of it zero pages); after the jump from one to two VMs total sharing grows linearly; little of the sharing is zero pages, so most is redundant code and read-only data.

Production numbers and cost. The Figure 5 table is in Part I §3. The extra detail: of workload B's 345 MB reclaimed, 70 MB was zero pages; of workload C's 120 MB, 25 MB was. With sharing disabled versus enabled, aggregate throughput of CPU-bound benchmarks showed no significant difference (0.5% higher with sharing on average, from 1.6% lower to 1.8% higher), possibly because sharing improves locality in physically indexed caches.

Isolation, precisely. Functional isolation holds by construction: a shared MPN is never writable through any mapping, and any write produces a private copy for the writer only, so no VM can change what another VM reads. Sharing is keyed only on page contents; the scanner knows nothing about VM boundaries or about which guest process a page belongs to, so it shares within one VM as well as across VMs (the Conclusions say "within and between VMs"). What the paper does not discuss is timing: a write to a shared page takes a COW fault and a copy that a write to a private page does not, and one shared MPN means one shared cache footprint. Those differences are observable, which is the basis of the later side-channel concern discussed in this guide's Questions tab, Q1.

Versus Disco. Disco found sharing where data was created, which required guest changes: a hooked bcopy() for buffer-cache sharing, a special large-packet network interface for data passed between VMs on a virtual subnet, and interposition on shared non-persistent disks. Content-based sharing needs none of this and also catches sharing those paths miss, such as independently zeroed pages (§4.1, §8).

M9 · Shares and min-funding revocation

Why not just run an OS-style global replacement policy? A traditional OS adjusts allocations to optimize an aggregate, system-wide metric. Server consolidation needs quality-of-service guarantees for clients of different importance, so "it can be preferable to penalize a less important VM, even when that VM would derive the largest performance benefit from additional memory" (§5).

Shares. Each client (here a VM) holds shares. It is entitled to consume memory in proportion to its shares and is guaranteed a minimum fraction equal to its fraction of all shares. Shares are relative: their value depends on how many shares are contending. Allocations degrade gracefully under overload, and clients benefit proportionally when others underuse their allocations (§5.1).

Min-funding revocation (from Waldspurger's thesis work). When a client demands more space, a victim relinquishes some of its allocation, and the victim is the client with the fewest shares per allocated page, ρ = S / P. In the paper's economic analogy ρ is a price: memory moves from clients paying a low price per page to clients willing to pay more.

# min-funding revocation, with the paper's min and max constraints (sketch)

    victims = { v ≠ c : alloc(v) > min(v) }

    reclaim one page from v (balloon or page it, M5/M6); give it to c   # c never exceeds max(c)
# repeated revocation drives the system toward equal rho for everyone who wants more,
# i.e. P(v) proportional to S(v): with equal shares, equal allocations (Figure 7: 179 MB each)

The limitation that motivates M10. Pure proportional share ignores whether memory is used. "Idle clients with many shares can hoard memory unproductively, while active clients with few shares suffer under severe memory pressure." Earlier attempts to carry idleness compensation over from proportional-share CPU scheduling had not worked (Sullivan and Seltzer, ref. [25]).

M10 · The idle memory tax

The tax charges a client more for an idle page than for an active one. Min-funding revocation uses an adjusted shares-per-page ratio. For a client with S shares and P allocated pages, of which a fraction f is active:

rho = S / ( P · ( f + k · (1 − f) ) )        k = 1 / (1 − tau),   0 ≤ tau < 1
#  P·f       active pages, charged once each
#  P·(1−f)   idle pages,   charged k times each
#  tau = 0    → k = 1   pure share-based isolation
#  tau = 0.5  → k = 2
#  tau = 0.75 → k = 4   the ESX default
#  tau → 1    → k → ∞   all idle memory may be reclaimed ("tau ≈ 1" in the paper)

Why τ is "the maximum fraction of idle pages that may be reclaimed." The paper states this meaning; here is the derivation (this guide's). Suppose a client would be entitled to E pages under pure shares, actively uses A of them, and competes against fully active clients whose price stays at S/E. Revocation stops when its adjusted price matches theirs, so its charged pages equal E: A + k·(P − A) = E. Then its idle pages are P − A = (E − A)/k = (1 − τ)·(E − A). It keeps a fraction 1 − τ of the idle part of its entitlement and loses τ of it. At the default τ = 0.75 it keeps a quarter of its idle entitlement. If the competitors are themselves partly idle, they are taxed too, and less is taken (Figure 7 below).

Why not 100%. The default of 75% "allows most idle memory in the system to be reclaimed, while still providing a buffer against rapid working set increases, masking the latency of system reclamation activity such as ballooning and swapping." A VM that wakes up uses its idle buffer immediately while ESX deflates its balloon (M13 shows this happening). Footnote 5: the rate is uniform across VMs; the implementation supports per-VM rates, but they were not exposed.

The tax decides how much, not which. ESX never identifies which particular pages are idle ("specific active and idle pages need not be identified individually," §5.3). The tax only lowers a VM's target. The guest then chooses which pages to give up when its balloon inflates. Statistical estimation of how much plus guest choice of which is the division of labor that makes the whole scheme work without guest cooperation on the estimate.

M11 · Measuring idle memory: the sampling estimator

Why not ask the guest. Native guest interfaces are impractical: different guests use different activity metrics, those metrics focus on per-process working sets rather than the whole VM, and guest monitoring typically relies on page-table access bits, which DMA by devices bypasses (§5.3).

The procedure (per VM, independently). The sampling period is measured in units of VM execution time (inference about why: a VM that is descheduled is not judged idle just because it was not running). At the start of each period, choose n of the VM's "physical" pages uniformly at random. Invalidate every cached mapping of each sampled PPN, including hardware TLB entries and the virtualized MMU state (the shadow PTEs). The next guest access to a sampled page traps, the touched count t is incremented, and the mapping is re-established, so each sampled page costs at most one minor fault per period. At the end of the period f = t / n. Defaults: n = 100 pages per 30-second period, so at most 100 minor faults per period.

How noisy one period is (this guide's arithmetic). t is a binomial count, so the standard error of one period's f is √(f(1 − f)/n), at most 0.05 when n = 100, regardless of how large the VM is. That is why a single period is not trusted and why estimates are smoothed.

Smoothing. Inspired by work on balancing stability and agility in network estimation, ESX keeps separate exponentially weighted moving averages with different gains: a slow average for a stable estimate, a fast average that adapts quickly, and a version of the fast average that also folds in the current period's counts as they arrive, to catch rapid intra-period changes. The estimate is the maximum of the three. Increases are therefore followed quickly (the fast averages pull the maximum up), decreases slowly (the slow average holds it up). A VM that starts using memory ramps up to its share quickly; a VM whose working set shrinks loses its idle memory gradually through the tax.

Lineage. Using page faults to maintain reference bits in software goes back to Babaoglu and Joy's VAX work (ref. [2]); ESX's addition is to sample a small random subset and compute an aggregate estimate rather than track every page.

M12 · Parameters, admission control and the reclamation states

Three parameters per VM (§6.1). Max is the "physical" memory the guest was configured with; it cannot change after the guest boots, because 2002 commodity OSes could not change their physical memory size. A VM gets its max whenever memory is not overcommitted. Min is a guaranteed lower bound, honored even under overcommitment. Shares set the proportional entitlement between min and max (a VM with twice the shares gets about twice the memory, provided both actively use what they get).

Admission control (§6.2), checked before a VM powers on:

admit(vm) only if:
    unreserved machine memory ≥ min(vm) + overhead(vm)    # overhead ≈ 32 MB: 4–8 MB frame buffer + pmap, shadow PTs, ...
    unreserved ESX swap space ≥ max(vm) − min(vm)          # room to page out everything above min
# invariant over all running VMs:  Σ(min + overhead) ≤ machine memory,  Σ(max − min) ≤ swap
# so every VM can always be held at ≥ min in RAM with the rest on disk, "under any circumstances"

The reservations are used only for admission; actual allocations still vary dynamically, unused reservations are not wasted, and in practice only a small fraction of the reserved swap is ever written. If the swap reservation were dropped, a burst of demand could leave ESX with memory it must reclaim and nowhere to put it, and the only remaining options would be to stall or kill VMs (inference).

Worked example from the Figure 8 setup (numbers from §6.3; the arithmetic is this guide's). Two Exchange VMs at 256 MB and three VMs at 320 MB give 1472 MB of max; each min is half its max, 736 MB in all; overhead is 160 MB. Reserved machine memory is 736 + 160 = 896 MB, under the 1 GB made available, so all five power on; reserved swap is 1472 − 736 = 736 MB. Configured memory plus overhead is 1632 MB against 1 GB, which the paper describes as overcommitted by more than 60%.

When targets are recomputed (§6.3): on administrator changes to system-wide or per-VM parameters, when a VM is added or removed, when free memory crosses one of the thresholds below, and periodically to pick up new idle-memory estimates.

The four reclamation states. Thresholds are percentages of system memory: high 6%, soft 4%, hard 2%, low 1%. In the high state free memory is sufficient and nothing is reclaimed. In soft, ESX reclaims by ballooning and pages only where ballooning is not possible. In hard, it relies on paging to reclaim forcibly. In the rare low state (free memory transiently below 1%), it keeps paging and additionally blocks every VM that is above its target allocation. In every state, targets are computed to push aggregate free memory back above the high threshold. A move to a lower state happens "when the amount of free memory drops below the lower threshold"; a move back up happens only "after significantly exceeding the higher threshold." This guide reads the lower threshold as the threshold that names the next state down (consistent with the paper's description of the low state as entered when free memory falls below the low threshold), so the band between two thresholds acts as hysteresis.

# state update on each free-memory change (this guide's reading of §6.3)
down = { HIGH: (SOFT, 4%), SOFT: (HARD, 2%), HARD: (LOW, 1%) }
up   = { SOFT: (HIGH, 6%), HARD: (SOFT, 4%), LOW: (HARD, 2%) }
if state in down and free < down[state].threshold:              state = down[state].next
elif state in up and free > up[state].threshold + margin:      state = up[state].next   # "significantly exceeding"
# actions: HIGH none · SOFT balloon (page only if no balloon) · HARD page · LOW page + block VMs above target

M14 · I/O page remapping

The hardware problem (§7). IA-32 PAE mode lets the processor address up to 64 GB with 36-bit physical addresses, but many DMA devices can address only part of it; a NIC on a 32-bit PCI interface reaches only the lowest 4 GB. Some high-end systems have an I/O MMU that can remap DMA targets. More commonly, I/O to "high" memory above 4 GB is copied through a temporary bounce buffer in "low" memory, which costs latency, throughput or CPU.

Why virtualization makes it worse. A VM configured with less than 4 GB believes all its PPNs are DMA-reachable, so the guest never bounces anything itself, yet ESX may back those PPNs with high MPNs. ESX must therefore bounce on the guest's behalf, invisibly. The same indirection fixes it: ESX can move the backing of a PPN from high to low memory without the guest knowing.

# hot I/O page remapping (§7; the copy-and-invalidate steps are the generic pmap change of M2)
on network transmit from (vm, ppn):
    mpn = cached PPN→MPN mapping for transmits             # an existing software cache...
    if mpn is high:
        copy through a low bounce buffer; copies[ppn] += 1    # ...augmented with a copy count
        if copies[ppn] > THRESHOLD:                           # the page is "hot"
            low = allocate low MPN; copy 4 KB once
            pmap[vm][ppn] = low; invalidate cached mappings; free the high MPN
# from now on the device DMAs straight to or from the page: no more copies for it

Results and limits. The scheme works well for guests that use a limited set of pages as network buffers; for some network-intensive workloads the number of pages copied fell by several orders of magnitude. Remapping increases demand for low memory, which can itself become scarce, so it may be worth pushing some low pages back to high memory to make room for currently hot I/O pages; the paper was exploring policies from random replacement to adaptive cost-benefit schemes. This mechanism saves copies, not memory.

An interaction the paper does not discuss (inference). If the hot page is COW-shared, ESX cannot simply move the shared MPN to low memory, because it does not know which other PPNs point at it (M1: refcount, no backmap). Remapping would give this PPN its own low copy, which costs one sharer's worth of savings.

🎓
From the lecture. Prof. Rosenblum explained the history: Intel widened the page-table entry so physical addresses could exceed 32 bits, but old devices still did DMA with 32-bit addresses, so only the bottom of memory was reachable for I/O. Because ESX interposes on everything, it had two options for a guest page backed in high memory: do the I/O through another buffer and copy, or remap the page low and let the device DMA to it directly. It chose to remap when the copying was actually a burden, that is, for hot pages.

M16 · Connections to the other CS240 papers

Superpages (10/13). A superpage TLB entry needs a contiguous, aligned run of physical frames with a single set of protections, one reference bit and one dirty bit. Every ESX mechanism is defined per 4 KB PPN: COW protection, balloon reports, sampling invalidations, swap victims and the PPN → MPN map itself. Nothing keeps a guest's contiguous PPNs on contiguous, aligned MPNs. Keep both papers' granularity assumptions side by side when reading the superpages reservation and promotion machinery.

Adams and Agesen, software versus hardware virtualization (10/15). The shadow page tables of M2 are kept coherent by write-protecting guest page-table pages ("tracing") and by handling hidden page faults; that paper measures what those traps cost and why first-generation hardware support did not remove them. The professor's "another level of indirection in hardware" is the nested paging that later did.

Threads versus events, cooperative task management. M7's invisible fault is the same structural problem as a blocking call inside a user-level or cooperative scheduler: the layer that blocks is not the layer that knows other work is runnable.

Mesa monitors. Hint frames follow Mesa's hint discipline: a signal that something might be true is rechecked before it is acted on (M8).

Livelock (10/6). The professor tied the balloon idea to the memory an ordinary NIC driver allocates for its device's ring buffers, the LANCE example from that lecture. ESX also sits on the network transmit path, which is where the copy counts for I/O remapping are kept (M14).

Follow the numbers

Worked examples

Four traces using the paper's own measurements.

① Ballooning overhead, from the dbench experiment

A 256 MB VM is ballooned down to 128 MB and to 224 MB; compare against VMs natively configured at those sizes.

  1. At 128 MB: ballooned throughput trails native-128MB by 4.4%.
  2. At 224 MB (32 MB balloon): the gap shrinks to 1.4%.
  3. Why the gap shrinks with balloon size: most of the overhead comes from guest kernel data structures sized for the VM's configured max (256 MB), not its ballooned size — a 256 MB-configured VM has slightly more overhead than a genuinely 128 MB one, and that fixed cost matters less as the balloon shrinks.
🍯
Insight: ballooning isn't free, but its cost is a small, mostly-fixed data-structure tax — not a fundamental performance penalty from reclaiming memory the "wrong" way.

② The idle memory tax, worked through the formula

Two VMs, equal shares, 256 MB each configured, ~360 MB machine memory available. VM1 (Windows) sits idle; VM2 (Linux) runs dbench.

  1. Tax rate = 0%: idle pages count exactly the same as active pages — pure share allocation — so both VMs converge on the identical 179 MB allocation, despite VM1 using almost none of it.
  2. Tax rate raised to 75%: VM1's idle pages now count as 4× (k = 1/(1 − 0.75) = 4) in the denominator of its shares-per-page ratio, inflating its apparent holdings and making it "cheaper" (lower shares-per-page) to reclaim from.
  3. Min-funding revocation kicks in: pages move from VM1 (idle) to VM2 (active), reallocating machine memory toward genuine demand.
  4. Measured effect: VM2's dbench throughput increases by over 30% after the tax change — with VM1's guaranteed min size untouched.
💡
Pure proportional-share allocation is provably fair by shares but can be arbitrarily wasteful; the tax is the minimal fix that keeps the fairness guarantee while fixing the waste.

③ Content-based sharing across ten identical VMs

Ten identical 40 MB Linux VMs running SPEC95 benchmarks, sharing scanned over 30 minutes.

  1. With just one VM, ~5 MB is already reclaimed — 55% of that from shared all-zero pages alone.
  2. As VMs are added, total shared memory grows roughly linearly (each new VM mostly duplicates existing content).
  3. At ten VMs, sharing approaches 67% of aggregate VM memory (roughly two-thirds overlap), and nearly 60% of all VM memory is actually reclaimed back to the free pool.
  4. In production (heterogeneous real workloads), the effect is smaller but still substantial: 10 Windows NT VMs reclaimed 32.9%; 9 Linux VMs reclaimed 18.7%; 5 Linux VMs reclaimed 7.2%.
🍯
Insight: homogeneity drives sharing — identical guest OS + application stacks overlap heavily, which is exactly the common case in server consolidation.

④ Admission control reservation, by the numbers

A VM is configured with min = 128 MB, max = 256 MB, typical overhead ~32 MB.

  1. Machine memory reserved at power-on: min + overhead = 128 + 32 = 160 MB, guaranteed regardless of system load.
  2. Disk swap space reserved: max − min = 256 − 128 = 128 MB, ensuring the system can always page out the rest if needed.
  3. In practice only a small fraction of that swap reservation is ever actually used — it's a worst-case guarantee, not an expected cost.
💡
Admission control turns "we probably have enough memory" into a guarantee, which is what makes aggressive overcommitment (the five-VM experiment overcommitted by >60%) safe to run in production.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why can't ESX simply run a clever meta-level LRU policy from outside each guest, instead of bothering with ballooning?
Show answer
Only the guest OS truly knows which of its own pages are least valuable — its policy may depend on undocumented heuristics or even application hints. A meta-level policy is uninformed by comparison and can conflict with the guest's own decisions, causing the "double paging" problem where a page gets faulted back in only to be immediately paged out again.Misconception: that a sophisticated enough algorithm can substitute for guest knowledge. The problem isn't algorithm quality — it's an information asymmetry no external policy can close.
Problem 2 · medium
A VM's balloon driver crashes and the guest reboots without the driver noticing. What does ESX do with the pages it had already reclaimed via that balloon?
Show answer
Any subsequent guest access to a ballooned PPN faults, since ESX deallocated the backing MPN. ESX treats this as the balloon having been "popped" — the next interaction with the (freshly booted) driver resets its state, and the fault is handled by allocating a brand-new MPN, as if the page were being touched for the first time.Misconception: that a crash leaves the guest permanently short of memory. ESX's fault handler safely and transparently re-establishes normal memory on demand.
Problem 3 · medium
Two VMs have equal shares, but VM A is 90% idle and VM B is fully active. With tax rate = 0%, describe their allocations; with the tax rate pushed close to 100%, describe them.
Show answer
At 0%, allocations are purely proportional to shares — equal shares mean equal allocation regardless of activity, so VM A keeps its half even mostly unused. As the tax rate approaches 100%, the idle-page cost k = 1/(1 − τ) grows without bound (the paper defines τ only for 0 ≤ τ < 1), so VM A's idle pages dominate the denominator of its shares-per-page ratio and nearly all its unused memory becomes reclaimable and drifts to VM B via min-funding revocation — while VM A's guaranteed min size is still respected.Misconception: that a near-100% tax rate means the idle VM gets nothing. It still keeps its min size and its actively-used pages — only genuinely idle memory beyond that is reclaimable.
Problem 4 · hard
ESX's content-based sharing hashes page contents rather than comparing pages directly. Why does the "false match" risk not matter in practice, and what's the mitigation anyway?
Show answer
With a good 64-bit hash, collision probability doesn't exceed 50% until roughly 2^32 distinct pages are hashed; even at the largest IA-32 memory configuration (64 GB ≈ 2^24 pages), the collision probability is under 0.01%. As a belt-and-suspenders mitigation, ESX still performs a full byte-for-byte comparison before actually sharing two pages, so even a freak hash collision can never cause silent data corruption — it only costs a wasted comparison.Misconception: that hash-based matching risks merging different pages. The full comparison after every hash match makes that impossible; the hash is only a cheap pre-filter.
Problem 5 · medium
Why does ESX sample only ~100 pages every 30 seconds per VM instead of tracking access bits on every page?
Show answer
Guest-OS access bits are unreliable from outside (DMA I/O bypasses them, and semantics vary by OS), and full per-page tracking at every access would be expensive. A small random sample gives a statistically sound estimate of the active fraction at a cost of at most 100 minor page faults per period — negligible overhead for an estimate accurate enough to drive tax decisions.Misconception: that more precision requires tracking every page. Statistical sampling deliberately trades a small, bounded error for a large reduction in overhead — the same logic behind any monitoring system that samples rather than exhaustively measures.
Problem 6 · easy
Why does ESX use randomized rather than "smart" replacement for its own demand-paging fallback?
Show answer
A sophisticated meta-level replacement policy is exactly the mechanism the paper argues against for the same reason ballooning was invented: it risks unintended, pathological interactions with the guest's own memory management (including double paging), and paging is expected to be a rare event anyway, so the payoff from cleverness is low relative to its risk.Misconception: that any eviction is better than random eviction. Interference with the guest's own policy can make an "informed" but uncoordinated choice actively worse than a neutral random one.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the difference between ballooning and ordinary paging?▾
Ballooning reclaims memory by asking the guest OS to give up pages it considers least valuable, using its own algorithms. Ordinary (demand) paging reclaims memory from outside the guest, with no idea which pages matter to it — used only as a forced fallback.
Q2Does ballooning require modifying the guest OS?▾
No — it requires installing a small, unprivileged driver (a pseudo-device or kernel service) inside the guest, using entirely standard, documented OS interfaces for allocating pinned memory. The guest OS kernel itself is never modified.
Q3How can two unrelated VMs end up sharing a memory page?▾
If their contents happen to be byte-identical — e.g. both running the same OS kernel binary, shared library, or an all-zero page — ESX's content-hashing scan will find the match regardless of which VM created the page or when, and merge them via copy-on-write.
Q4Is the idle memory tax a hard cap or a bias?▾
A bias, layered on top of proportional shares. It changes the effective "price" of idle vs. active pages within the min-funding revocation algorithm; it never overrides a VM's configured minimum size.
Q5What happens if the system runs out of memory faster than reclamation can respond?▾
Free memory drops through the four thresholds. Below the rare "low" threshold, ESX not only forces paging but also blocks execution of VMs currently above their target allocation, buying time for reclamation to catch up.
Q6Does page sharing slow the system down?▾
Measured overhead was negligible — in controlled experiments, aggregate throughput was actually ~0.5% higher with sharing enabled (better physical cache locality from consolidated pages), ranging from 1.6% lower to 1.8% higher across runs.
Q7Why is hot I/O page remapping needed at all?▾
Some DMA-capable devices (e.g. 32-bit PCI NICs) can only address the lowest 4 GB of memory. Without remapping, I/O to pages in high memory requires an extra copy through a low-memory bounce buffer; remapping "hot" pages into low memory eliminates that copy for frequently-transferred data.
Q8What guest OSes did ESX Server 1.5 actually support unmodified?▾
The paper reports production use with unmodified Microsoft Windows 2000 Advanced Server and Red Hat Linux 7.2 on the Intel IA-32 architecture.
Q9What did the authors leave for future work?▾
Using page remapping/coloring to manage cache allocation to VMs, exploiting remapping for NUMA locality and fault containment, higher-level VM grouping abstractions, multi-resource tradeoffs, and adaptive feedback-driven workload management.
Beyond this paper

Connections to modern memory-systems research

Short, specific links to today's OS-managed memory tiering and disaggregation work.

Ballooning vs. transparent tiering reclaim

Ballooning solves guest-cooperative reclaim by asking the OS what it values least — but modern OS-transparent tiering (TPP, AutoTiering) reclaims/demotes pages via PTE Accessed-bit scanning with zero guest cooperation. ESX's central lesson — meta-level policies mismatch native ones — is exactly the failure mode transparent hot/cold classifiers must avoid when demoting to CXL-attached or NVM tiers.

Idle memory tax as a hotness signal

The idle tax's core move — charge more for pages you aren't touching — is structurally the same idea as hotness-based page placement in tiering systems like Memtis or HeMem: idleness (or its inverse, access frequency) is the currency both use to decide who deserves fast memory. ESX just applies it economically (shares-per-page) rather than spatially (DRAM vs. NVM).

Statistical sampling as a general low-overhead trick

Sampling 100 pages per 30 seconds to estimate a whole VM's working set is the same tradeoff modern tiering systems make when they sample a subset of pages or use PEBS-based hardware sampling instead of scanning every PTE — bounded overhead for a statistically-sound hotness estimate at scale.

Content-based sharing and memory pooling

ESX dedups identical pages within one physical machine; CXL-based memory pooling extends the same intuition — memory as a shared, poolable resource across hosts — but now with real network/fabric latency and coherence costs the single-machine hashing scheme never had to consider.

🍯
The through-line for tiering research is more modest than "transparent signals can replace cooperation": ESX's preferred reclamation mechanism, ballooning, still leans on the guest to pick victim pages. Its genuinely guest-transparent piece — statistical sampling — only decides how much memory each VM gets, not which pages to evict. That narrower bet — that cheap, transparent activity signals are good enough to drive allocation and placement decisions — is exactly what OS-managed DRAM/NVM/CXL tiering systems rely on today.

Questions worth chasing further

A place for open "does this still hold up / what would change" questions raised while studying this paper — each one researched, not guessed. Unlike Class Prep (discussion prompts anchored to the paper's own claims), these follow a question wherever it leads, including well past 2002.

Q1 · This worked with 256 MB of DRAM. With hosts now running hundreds of GB to multiple TB, plus NVMe and CXL as extra tiers below DRAM — does any of this still work, and what had to change?

Short answer: the core allocation framework — shares, an idle-memory tax, ballooning as the preferred mechanism, a forced fallback underneath it — is still running, in essentially the same shape, in vSphere today. It scales to modern hosts mostly "for free," because its two central quantities were never expressed in raw bytes. The four reclamation thresholds are percentages of host memory, and vSphere's own resource-management docs (through at least 6.7) still list the identical defaults from the 2002 paper: high 6% (no reclamation), soft 4% (ballooning), hard 2% (ballooning + swapping), low 1% (swapping), each scaling automatically with host size since they're fractions, not fixed MB figures. And the working-set estimator is a fraction (touched ÷ sampled), so a 100-page random sample produces a statistically meaningful estimate whether the VM holds 256 MB or 256 GB — sample-size accuracy is a function of the sample, not the VM.

Three things did genuinely change, though — two for reasons that have nothing to do with raw capacity:

Content-based page sharing was deliberately weakened for security, not scale. Starting with ESXi 5.1 Update 3, and by default from ESXi 6.0 onward, VMware stopped sharing pages across VMs by default. The reason was a side-channel finding: academic researchers showed that when two VMs on the same core shared a page, an attacker VM could use cache-timing (flush-and-reload) measurements against that shared page to recover bits of the other VM's AES key. VMware called the real-world risk low but changed the default "out of an abundance of caution." Sharing still runs within a single VM's own pages by default, and an administrator can re-enable the old cross-VM behavior — but the paper's headline 60–67% cross-VM dedup numbers no longer apply out of the box. Separately, modern guests default to 2 MB "large" pages for TLB efficiency, and two byte-identical 2 MB pages are far rarer than two identical 4 KB ones, so in practice sharing often doesn't engage until memory pressure is high enough to force large pages to break apart — a wrinkle the original 4KB-page-only design didn't need to consider.

NUMA is a wholly new axis the paper doesn't address. The 2002 system predates mainstream multi-socket x86 virtualization hosts at today's scale; ESXi's NUMA scheduler now actively places a VM's vCPUs and its machine memory on the same NUMA node for locality — a concern the original uniform pmap model has no vocabulary for at all, since it only tracks which MPN backs a PPN, never where that MPN sits relative to a core.

A genuinely new tier was inserted between DRAM and disk — which is the direct answer to "multiple tiers." vSphere 8.0 Update 3 shipped a tech-preview feature, Memory Tiering over NVMe (the production descendant of 2021's "Project Capitola"), that extends the paper's own forced-fallback idea by one more step. Instead of the fallback's only destination being a disk-based swap file, it now has an intermediate stop: DRAM is "Tier 0," a fast local NVMe device is configured as "Tier 1," sized as a percentage of DRAM (Mem.TierNvmePct, default 25% — roughly a 4:1 DRAM:NVMe ratio), and the whole thing is described as transparent to the guest and its applications, same transparency promise the 2002 paper insisted on. Conceptually it's the identical lever — pmap-style indirection lets ESX quietly relocate what backs a page — just with a softer landing spot than disk for a page that's cold but not necessarily rare. The same underlying idea (treat ever-slower, ever-cheaper memory as another rung of the same ladder) is what's driving CXL-attached memory work industry-wide: VMware demoed a CXL-based accelerator ("Project Peaberry") in 2024 where roughly 40% of a VM's memory was served through the CXL tier at an average ~10% performance cost — one step colder than local NVMe, same transparent-tiering philosophy.

What's not publicly confirmed: how the NVMe tier actually decides hot vs. cold. VMware's own materials say only that the hypervisor "already knows which pages are hot and which are cold" and places them accordingly — they don't say whether that's the same statistical random-sampling estimator from 2002, something hardware-assisted, or a new design.

💡
Sharpening this into a more specific question: the original sampler was explicitly justified because paging was framed as a rare fallback — getting an occasional victim wrong was cheap, which is exactly why random replacement was an acceptable choice for it. But NVMe tiering is pitched as routine, always-on effective capacity (a default 4:1 DRAM:NVMe ratio implies VMs are expected to keep a real fraction of their working set resident in Tier 1 regularly, not just during a rare emergency). That flips the cost-benefit entirely: a misclassified "cold" page in the 2002 design costs one page fault, ever, if it's wrong; a misclassified "cold" page living on the NVMe tier costs a real device round-trip on every single access until it's reclassified. So the sharper question is: did vSphere's NVMe memory tiering keep the original coarse, periodic random-sampling estimator unchanged, or did the changed economics of being wrong force it onto a finer-grained, more frequent, or hardware-assisted hot/cold classifier (e.g. CPU access/dirty-bit scanning) — and if VMware shipped the tech preview with the old sampler unchanged, is that a known weakness of the current design? Nothing in the public blog posts or docs answers this; it would need VMware's own engineering writeups or a deeper technical disclosure to resolve.

Q2 · Following on from Q1 — which of ESX's metadata structures grow as DRAM size grows, and which were deliberately built to stay flat?

Splitting the paper's own structures into the two buckets:

Grows with memory size. The content-based-sharing hash table is the clearest case, and the paper states it in exactly these terms: "the total space overhead for page sharing is less than 0.5% of system memory" — a percentage, which by definition means the table's absolute size tracks total memory up or down. Concretely, it holds one 16-byte frame per page that's been scanned (hint or shared), plus a small overflow table for pages with unusually large reference counts (like the all-zero page), so more machine memory → more candidate pages → more frames, in direct proportion. The pmap and shadow page table are the second case, but with a caveat worth being precise about: they scale with each VM's configured max size (how many "physical" pages that guest believes it has), not with host DRAM directly. §6.2's admission-control accounting makes this explicit — the ~32 MB per-VM overhead reservation (4–8 MB framebuffer, the rest "implementation-specific data structures," i.e. pmap + shadow PT) grows for VMs over 1 GB. So pmap/shadow-PT footprint only grows with host DRAM indirectly, through the usual reason you'd add DRAM: to configure bigger or more VMs.

Deliberately kept flat. The idle-memory-tax's working-set sampler is the one piece of metadata the paper goes out of its way to keep constant regardless of memory size, and says so explicitly when justifying the design: a VM is sampled with "a small number" — by default 100 — of its pages every 30-second period, "resulting in at most 100 minor page faults per period," specifically instead of the alternative of tracking a reference bit per page across all of memory, which would scale linearly with VM size (more pages → more bits to maintain and scan). The three moving averages (slow, fast, current) layered on top are likewise just three fixed scalars per VM, not three scalars per page — so the entire estimator's footprint and overhead stay the same whether the VM holds 256 MB or 256 GB. That's precisely the property this guide's Q1 above leans on to explain why the sampler still works unmodified at today's memory scale: it was never sized relative to memory in the first place.

One structure outside the paper's own scope, flagged as general systems reasoning rather than a paper claim: any hypervisor also needs some per-physical-page bookkeeping for the raw machine memory itself (ownership, state, coloring) — that frame-table-style structure is inherent to managing RAM at all and necessarily grows one entry per machine page, i.e. linearly with host DRAM, but the 2002 paper doesn't discuss its size or format, so this point is inference, not citation.

Q3 · Most OSes expose a generic mpin(void* va, unsigned len) syscall that pins a VA range in physical memory. Could that replace the need to write a custom balloon driver per guest OS?

Partly, and the design is worth walking through because the obvious version of it doesn't work, and the version that does work turns out to be a thin reskin of the real driver rather than something fundamentally different. This is a design exercise, not a paper claim; nothing below is from Waldspurger's text.

The mechanism. ESX sends a guest-resident agent a target size over a private channel, same as today. The agent requests that much memory through the guest's own ordinary allocation call (whatever the OS provides), which is what actually forces the guest's own memory manager to decide what to give up under pressure, exactly as get_free_page()/MmAllocatePagesForMdl() do in the real driver. Only once it has a VA range from that call does it call mpin(va, len) on it, fixing that VA's mapping to a PPN so the guest's own OS won't relocate or swap it later. The agent reports the resulting PPNs back to ESX over the channel, and ESX reclaims the backing MPNs.

Why the report-back step can't be skipped. ESX already intercepts every guest page-table write to maintain the shadow page table, so it's tempting to think it could just notice the pin happening. But pinning an existing VA-to-PPN mapping doesn't necessarily produce a new write ESX would see: it only promises the mapping won't change in the future, it doesn't have to create it. So there's no free signal in the page-table trap stream, and the guest still has to actively tell ESX which PPNs it pinned.

Why "ESX just picks the address directly" doesn't work at all. The tempting alternative is to skip asking the guest and have ESX hand the agent a specific VA to pin. But mpin only locks whatever is already backing that address; it doesn't evict or free anything by itself. If ESX picks an address the guest happens to be actively using, pinning it doesn't make that memory reclaimable, it just freezes live data in place. Getting back to reclaimable memory still requires something to have first decided that address was safe to give up, which puts the guest's own allocator right back in the loop, i.e. straight back into the exact "only the guest knows which pages are least valuable" problem the paper's naive meta-level policy runs into in §3.1. There's no way to route around guest cooperation on selection this way, only on mechanism.

Advantage: portability. mpin is close to a standard syscall across guest OSes, so the agent becomes one small, largely OS-independent piece of code instead of a custom kernel driver with a distinct implementation per guest OS (Linux and Windows need different code today). The underlying logic is unchanged, the guest's own allocator still makes the real decision, but the engineering and maintenance cost of supporting a new guest OS drops substantially.

Disadvantage: a reclaim ceiling the original design doesn't have. Generic pinning syscalls are typically resource-limited or privilege-gated in real OSes (POSIX mlock() is capped per-process by RLIMIT_MEMLOCK), precisely because letting an arbitrary process lock unbounded physical memory threatens the rest of the system. vmmemctl sidesteps this entirely by running inside the guest kernel itself, with no external ceiling. An mpin-based agent running as an ordinary process would likely hit exactly that kind of cap well below what ESX might want to reclaim, unless it's specifically granted elevated privilege or raised limits on every guest it runs in, which claws back some of the per-OS setup cost portability was supposed to remove.

Core terms
BallooningA guest-resident driver that pins pages on ESX's command so the guest's own OS chooses what to reclaim — the primary, cooperative reclamation mechanism.
Demand paging (ESX)Forced reclamation to ESX's own swap area with randomized replacement, used only when ballooning is unavailable or too slow.
Content-based page sharingHashing page contents to find and merge identical pages across VMs via copy-on-write, without any guest OS knowledge.
Idle memory taxA charge on idle (vs. active) pages within the proportional-share allocation formula, defaulting to 75%, that lets idle memory drift to active VMs.
Hot I/O page remappingTransparently moving frequently-DMA'd "hot" pages into low, DMA-addressable memory to avoid bounce-buffer copies.
pmapESX's per-VM PPN-to-MPN translation table, the extra level of indirection that makes all of the above transparent.
Supporting terms
PPN / MPN"Physical" (guest-visible) page number vs. actual machine page number.
Shadow page tableESX's virtual-to-machine translation table used directly by hardware, kept consistent with the pmap.
Double pagingThe pathology where an uncoordinated meta-level policy and the guest's own OS both page out the same data independently.
Min-funding revocationThe proportional-share algorithm that reallocates a resource from the client with the lowest shares-per-unit price.
Hint frameA cheap, non-COW record of an unmatched scanned page's hash, checked lazily on the next potential match.
Admission controlRefusing to power on a VM unless min-size machine memory, overhead, and disk swap space (max − min) can be reserved.
High / soft / hard / low thresholdsFour free-memory levels (6%/4%/2%/1%) that determine whether ESX reclaims nothing, prefers ballooning, forces paging, or additionally blocks VM execution.
PAE / bounce bufferIA-32's 36-bit addressing extension, and the low-memory staging buffer some DMA-limited devices require for high-memory transfers.
