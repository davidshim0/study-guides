Proof modules that only know about their own state, not everyone's

A distributed transaction system has dozens of sub-protocols sharing global state. The textbook TLA+ approach makes every invariant depend on everything. PSM borrows an idea from concurrent programming — permissions — to cut that dependency down to just what each piece actually needs.

Before you begin

Acronyms first, then the concepts

This paper sits at the intersection of distributed systems and formal verification — two vocabularies at once. The glossary below defines every acronym you'll hit; the primers after it build the concepts up from nothing.

Quick glossary — key acronyms
PSMPermissioned State Machine — this paper's approach: TLA-style protocol specs where invariants are scoped by explicit permissions.
CSLConcurrent Separation Logic — the program-logic tradition PSM borrows "permissions" and the frame rule from.
TLA(+)Temporal Logic of Actions — Lamport's style of specifying a system as state + initial state + step function ("actions"), plus invariants.
IRInconsistent Replication — TAPIR's replication scheme where each replica may log operations at different log positions; no consistent snapshot exists.
2PCTwo-Phase Commit — the classic prepare-then-commit protocol Tulip uses to atomically commit a transaction across shards.
MVCCMulti-Version Concurrency Control — keeping multiple timestamped versions of each key instead of overwriting in place.
TAPIRTransactional Application Protocol for Inconsistent Replication — the prior (unverified) system Tulip is modeled on and benchmarked against.
IPMIris Proof Mode — the tactic library for writing separation-logic proofs in the Rocq (Coq) proof assistant; Tulip's proof is built with it.
RTTRound-Trip Time — network latency for one request/response; wide-area experiments are reported in RTTs between AWS regions.

1State machines, TLA-style▾

Specify a system as: a set of state variables, an initial state, and a set of actions — legal transitions from one state to another. To prove correctness, you pick an invariant (a property that should always hold) and show every action preserves it.

This is exactly how Figure 1's Paxos spec is written: variables Proposals and Votes, actions Action2a/Action2b, invariants Inv2a/Inv2b.

Now you're ready: PSM keeps this exact skeleton — it only changes how invariants are allowed to reference the state.
2Invariance proofs and why they get expensive▾

Proving a state machine correct means checking, for every action and every invariant, that running the action from a state satisfying the invariant lands in another state that still satisfies it. With A actions and I invariants that's up to A×I proof obligations — and in a monolithic spec, every invariant typically mentions every shared variable, so every pair is live.

Now you're ready: the single-decree Paxos example has just 2 actions and 2 invariants — already 4 pairs. Tulip has 25 actions and many more invariants; monolithic reasoning doesn't scale.
3Concurrent separation logic (CSL) in one paragraph▾

CSL specifies a function as a Hoare triple {P} fn {Q}: precondition P, postcondition Q. Its key extra idea is resources — things like a heap cell x ↦ v — that a piece of code must own to touch. Owning a resource is exclusive by default.

Now you're ready: PSM treats abstract protocol state (like "the proposal set") as a CSL resource too, not just physical memory.
4The frame rule — CSL's modularity trick▾

If you have x↦v_x ∗ y↦v_y (∗ = "separately, both held") and call a function that only touches x, you can "frame away" y↦v_y, hand over just x↦v_x, and get it back unchanged — without the function's spec ever mentioning y.

Now you're ready: this is the exact mechanism PSM wants for protocol proofs: prove an action against only the permissions it needs, leave the rest of the system's state untouched and unmentioned.
5Permissions and fractional ownership▾

A permission is a piece of evidence about part of the state, with rules for who may hold it and what it lets you conclude or do. Fractional permissions split ownership of one variable into halves (e.g. one half held by "the protocol," one by "the implementation lock"); only with both halves reunited can you mutate it.

Now you're ready: Paxos's voted list uses exactly this: a↪l (protocol half) and a↪l (implementation half) — merge to get write access, split to give each side read-only access.
6Stable (monotonic) permissions▾

A permission is stable if, once you hold it, no future action can invalidate it — usually because it describes a fact about state that only grows (an append-only log, a value that's fixed forever once set). Stable permissions are also duplicable: you can copy them freely, unlike exclusive permissions.

Now you're ready: "proposal ⟨n,v⟩ is fixed forever" is a stable permission. It's what lets an acceptor's proof (Action2b) rely on a fact from the proposers' module without re-deriving it or needing exclusive access.
7Paxos vocabulary: proposers, acceptors, quorums▾

Single-decree Paxos agrees on one value among processes split into proposers (who propose ⟨number, value⟩ pairs) and acceptors (who vote). A value is chosen once a quorum (typically a majority) of acceptors votes for it — quorum overlap is what prevents two different values from both being chosen.

Now you're ready: Tulip runs Multi-Paxos to replicate commit decisions, and a Fast-Paxos variant (§A.2) to make prepare decisions stable across possibly-failed coordinators.
8Sharding, replication, and two-phase commit▾

Sharding splits a database across independent groups for scalability; replication copies each shard across several machines for fault tolerance. When a transaction touches keys in more than one shard, two-phase commit (2PC) coordinates them: a prepare phase where every participant agrees it's able to commit, then a commit (or abort) phase that's final.

Now you're ready: Tulip's whole protocol is essentially "2PC, but the prepare phase uses inconsistent replication for speed and the commit phase uses Paxos for consistency."
9Multi-version concurrency control (MVCC) and strict serializability▾

Instead of overwriting a key's value, MVCC keeps a version per write, tagged with a timestamp; reads at timestamp t see the version written by the latest transaction ≤ t. Strict serializability is the strongest correctness guarantee: every transaction appears to run atomically at some point between when it started and ended, respecting real time.

Now you're ready: Tulip's whole client-visible contract is one sentence: "your code executes as if under strict serializability" — everything else in the paper is what it takes to make that sentence true of the implementation.
10Machine-checked proofs: Rocq, Iris, Goose, Grove▾

Rocq (formerly Coq) is a proof assistant — every step is checked by a computer, no informal hand-waving allowed. Iris is a CSL framework built inside Rocq; Goose translates real Go source into a Rocq model so you can prove things about the actual executable; Grove is a library of verified network/file/RPC primitives Tulip's proof builds on.

Now you're ready: "machine-checked" here means literally: Tulip's 42,131 lines of proof were checked by Rocq's kernel, not just reviewed by a human.
The whole story in one place

PSM in a nutshell

The problem, the fix borrowed from concurrent programming, and how it scales to a real system.

Verifying a distributed protocol the standard way means writing a single monolithic TLA+ spec: all state variables global, every invariant free to mention any of them. That's fine for toy examples, but real systems are composed of largely independent sub-protocols (Multi-Paxos inside a replicated key-value store, prepare logic inside two-phase commit) that all happen to touch the same shared variables. The result: every invariant must be re-checked against every action that could possibly touch its variables — a proof burden that grows roughly with actions × invariants, and that gives the developer no way to work on one sub-protocol without the whole spec in view.

The paper's fix, the permissioned state machine (PSM), imports two ideas from concurrent separation logic: permissions (named, restricted views of shared state, rather than raw access to all of it) and the frame rule (reason about only the resources a piece of code touches, leave the rest untouched and unmentioned). Concretely, each PSM module owns some state exclusively and refers to other modules' state only through stable permissions — duplicable facts about state that, once true, stay true forever (an append-only log has grown; a proposal has been fixed to a value). Because stable facts can't be invalidated, an invariant built on them is automatically preserved by any action that doesn't touch that fact directly — no need to check it against the whole action set.

On the code side, PSM's permissions are literally CSL resources, so a proof of the concurrent Go implementation can pass permissions in and out of protocol-level "action lemmas" through ordinary Hoare-triple reasoning — no separate translation layer between protocol proof and code proof.

The payoff: Tulip — a sharded, replicated, multi-versioned transaction system with crash recovery and coordinator recovery — is specified and verified against a one-line client contract (strict serializability). The proof is decomposed into 10 types of modules; of Tulip's 25 actions, 13 depend on only one module. The whole system is 3,956 lines of Go with 42,131 lines of machine-checked Rocq proof — about 10.6× the code, comparable to prior strongly-layered verified systems, despite Tulip being the most feature-complete verified distributed transaction system to date.

🍯 Key takeaways

  • Monolithic TLA+ specs force an action × invariant cross-product; PSM breaks that by scoping invariants to explicit permissions.
  • Stable permissions (duplicable facts about monotonic state) are the crux — they hold forever, so they're safe to hand across module boundaries.
  • Fractional permissions connect protocol-level reasoning to concurrent code (e.g. half owned by the protocol, half by a mutex's lock invariant).
  • PSM's permissions are literal CSL resources, so protocol proofs plug directly into Hoare-triple code proofs — one framework, not two.
  • Tulip: 10 module types, 21 shared state variables (13 via stable permissions), 25 actions (13 single-module).
  • Result: a machine-checked proof of strict serializability for a TAPIR-competitive system, at ~10.6× the LOC of the implementation.
Seven everyday pictures

How to think about PSM

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Permissions vs a global memo

Need-to-know badges

A company could pin one memo to the wall that every rule in every department must consult before changing anything — that's the monolithic spec. Instead, give each department a badge naming exactly the files it may read or write. Payroll's badge says nothing about Shipping's files, so Shipping can reorganize freely without anyone re-checking Payroll's rules. PSM's permissions are those badges.

Where it breaks: real badges are usually static; PSM permissions can be split, merged, and converted (e.g. exclusive → stable) by explicit rules mid-proof — more like a badge that can be photocopied once it's been notarized.
Stable permissions · Duplicability

A notarized copy

Once a document is notarized, the original will never change, so the notary can hand out unlimited certified photocopies — everyone who wants one gets one, and nobody can dispute what it says. PSM's FixProposal rule does exactly this: convert the mutable, exclusive "proposal n has value v" into the notarized, duplicable "proposal n is fixed to v forever." Any module can hold a copy.

Where it breaks: real notarization costs a trip to an office; in PSM the conversion is free and instantaneous, but only eligible facts — about state that provably never regresses — can ever be notarized this way.
Fractional permissions · Merge / split

Splitting a lease

Two roommates each keep half of a signed lease in a drawer. Either one alone can show their half as proof they live there (read access), but to sign an amendment (mutate the agreement) they must bring both halves back together. PSM's protocol/implementation split works the same way — MergeVoted reunites the halves for a write, SplitVoted hands them back out afterward.

Where it breaks: a lease has exactly two copies; PSM permissions can be split into arbitrarily many fractions with more elaborate algebra (resource algebras) than a simple half-half lease.
Avoiding the cross-product · Modularity

Org chart vs. an all-hands

Imagine every policy change at a company required re-approving it in front of the entire staff, cross-checked against every other department's policy — that's the monolithic action × invariant cross-product. An org chart instead lets Shipping's manager approve Shipping's own policy changes without convening the whole company, and only escalates when a change genuinely crosses department lines.

Where it breaks: a company's org chart is fixed at hire time; PSM's module boundaries are a design choice the developer makes when picking permissions — a bad choice can accidentally recreate the all-hands meeting.
Quorums & ranks · Fast Paxos

Petition thresholds

A town council resolution needs signatures from a simple majority of members (a classic quorum) to pass at a scheduled meeting. In an urgent case, residents can instead get it approved immediately with a bigger supermajority (a fast quorum) — no meeting required, but you need more signatures to be safe that no conflicting resolution could also have passed.

Where it breaks: petitions don't have "ranks" — Tulip's Fast Paxos lets a slow-path (classic-quorum) proposal at a higher rank override an earlier fast-path attempt, something a one-shot petition can't model.
MVCC · Monotonic history

An append-only ledger, not a whiteboard

A whiteboard that gets erased and rewritten makes it hard to reason about "what did this key say at 3pm?" — the old answer is gone. A bank ledger instead never erases: every deposit and withdrawal is a new dated line, and you can always look back. Tulip's value history abstraction is the ledger: instead of a mutable key-value store, the proof tracks the full timestamped history, so "prefix stable" permissions can describe old entries that will never change.

Where it breaks: the physical implementation still overwrites/compacts storage for efficiency; the ledger is a proof-only abstraction, reconstructed logically, not literally kept forever on disk.
2PC over IR · Early voting vs. certified tally

Early voting vs. the official tally

Early-voting locations record ballots inconsistently — different locations, different times, no shared log — yet the final outcome only ever depends on a simple deterministic rule ("count every valid ballot"). Tulip's prepare phase is the early-voting locations (inconsistent replication, one network round-trip); the commit outcome is the deterministic commit requirement: commit iff every participant group prepared. Because the rule is deterministic, the client can announce the outcome the instant it knows all groups prepared — the "official tally" (Paxos-replicated commit record) can catch up in the background.

Where it breaks: early-voting locations don't need to interact; Tulip's replicas do, via locks and validation, so "inconsistent" here means inconsistent logging, not inconsistent correctness — mutual exclusion is still enforced by quorum overlap.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals you can read at a glance.

1 · The two challenges with monolithic state machines

Take single-decree Paxos (Figure 1): two global variables, Proposals and Votes; two invariants, Inv2a† and Inv2b†; two actions, Action2a† and Action2b†. Since every invariant references both variables, proving correctness in principle requires checking all 2×2 = 4 action-invariant pairs. Worse, the natural modules — "proposers" and "acceptors" — are undermined because both directly depend on both shared variables, so you can't verify one without the other in view. Tulip has 25 actions and dozens of invariants; the monolithic approach doesn't scale past a toy example.

2 · Borrowing permissions and the frame rule from CSL

PSM attaches a permission to each abstract state variable: a named, restricted view that specifies who may hold it, what it lets the holder conclude, and how it composes with other permissions via interaction rules. Figure 3/4's Paxos permissions: psls (full ownership of the proposal set, held by the proposers module), ⟨n,v⟩ (point-wise, mutable view of one proposal), and ⟨n,v⟩fix (the same fact, but stable and duplicable once fixed). On the votes side: a↪l / a↪l (protocol/implementation halves) and a↪l (stable "at least a prefix" fact).

Why this matters: the two stable rows are exactly what let ProposersMach and AcceptorMach avoid depending on each other's mutable, exclusive state — they only ever exchange the frozen, duplicable facts.

3 · Specifying protocols with permissions — the 4 → 2 reduction

Figure 5 rewrites the Paxos spec as two separate PSM modules. ProposersMach's invariant Inv2a no longer says "∀⟨n,v⟩∈Proposals, EqLatest(n,v,Votes)" over the global Votes; it says EqLatest holds for some existentially-quantified lower bound votes, witnessed by the stable permission a↪l. Likewise AcceptorMach(a)'s Inv2b uses the stable ⟨n,v⟩fix instead of the global proposal set. Neither module's invariant is defined over the other's exclusive state, so Action2a only ever needs to be checked against Inv2a, and Action2b only against Inv2b — the 2×2 = 4 obligations collapse to 2.

4 · Connecting protocol proofs to code proofs

Because PSM permissions are CSL resources, a Go function's Hoare-triple proof can directly consume and produce them. Figure 7's RecvMessage2a starts by locking a mutex (obtaining a↪voted plus the physical field px.termc), checks a guard, then has exactly the permissions ActionPropose... sorry — Action2b requires: it opens the program invariant AcceptorMach(a), calls the already-proved action lemma, gets back a↪voted′, updates the physical struct fields to match, and re-seals the invariant before unlocking. After unlocking, other threads may run concurrently — but the proof doesn't need to reason about them, because it now holds the stable permission a↪voted′, obtained via WitnessVoted, which nothing else can invalidate.

🍯
The pattern that repeats everywhere in Tulip's code proof: acquire lock → gather permissions from the lock invariant → apply a pre-proved protocol action lemma → update physical state to match → release lock, keeping only the resulting stable permission for later use.

5 · Scaling to Tulip — 10 module types, 25 actions

Tulip decomposes into 6 transaction-level module types (replica, replica's on-disk state, replica group, key, network, overall transaction system) and 4 Multi-Paxos module types (proposers, acceptor, on-disk state, network) — instantiated once per replica/key/group as needed. Its protocol proof shares 21 state variables across modules: 13 via stable permissions over monotonic state (prepare decisions, value histories, command logs...), and 8 via fractional or other permissions (mirroring the lock-protected voted list pattern).

6 · Coordinator recovery as a Fast-Paxos instance

If a client crashes mid-prepare, a replica notices a stalled lock and spawns a backup coordinator. The core correctness property, prepare stability, says every coordinator — original client or any backup — must reach the same prepare/unprepare decision for a given group. The paper proves this exactly like single-decree Paxos safety: any two chosen values at different ranks must agree, by induction on rank plus quorum intersection (any classic quorum overlaps any other classic quorum, and a value chosen by a fast quorum must already have a majority within every classic quorum).

7 · The commit requirement removes replication from the critical path

Once a transaction has stably prepared on every participant group, its outcome is a pure function of those decisions — commit iff every group prepared. Because that function is deterministic and the prepare decisions are already stable, the client can report success immediately and let the actual commit record replicate through Multi-Paxos in the background. InvCommit/InvAbort (§A.1) capture this: a committed entry in the transaction result map must be backed by a stable "prepared" permission from every participant group.

Follow the numbers, step by step

Worked examples

Four traces using the paper's real numbers — the Paxos proof reduction, Tulip's LOC ratio, quorum-driven fault tolerance, and a latency coincidence explained by arithmetic.

① From 4 proofs to 2 — modularizing single-decree Paxos

Figure 1's monolithic spec has 2 invariants and 2 actions. How many proof obligations does PSM actually need, and why?

  1. Monolithic count: every invariant may depend on both Proposals and Votes, and every action may update either. Obligations = invariants × actions = 2 × 2 = 4: (Inv2a†,Action2a†), (Inv2a†,Action2b†), (Inv2b†,Action2a†), (Inv2b†,Action2b†).
  2. PSM splits state: ProposersMach owns psls exclusively; AcceptorMach(a) owns each acceptor's voted list exclusively. Neither invariant is defined over the other's exclusive state.
  3. Cross-module facts become stable permissions: Inv2a depends on votes only via the stable a↪l; Inv2b depends on the proposal set only via the stable ⟨n,v⟩fix.
  4. Result: Action2a only needs to preserve Inv2a (its own module); Action2b only needs to preserve Inv2b. Obligations drop to 2 — exactly half, and each is provable with only one module in view.
🍯
Why this matters at scale: the monolithic count grows as actions × invariants; PSM's count grows roughly with the number of modules an action actually touches — which the paper measures directly for Tulip in example ③.

② Tulip's proof-to-code ratio

Figure 12 reports 3,956 lines of Go and a proof split into 25,238 lines of "code proof" and 16,893 lines of "protocol proof." Check the paper's headline numbers by hand.

  1. Total proof: 25,238 + 16,893 = 42,131 lines of Rocq — matches the abstract's "∼42,000 lines."
  2. Proof-to-code ratio: 42,131 ÷ 3,956 ≈ 10.65× — matches the paper's "about 11×."
  3. Code proof's share: 25,238 ÷ 42,131 ≈ 59.9% — matches "code proofs account for about 60% of the total proof."
  4. Sanity-check one component: the Multi-Paxos library alone is 748 lines of Go against 4,929 (code) + 4,148 (protocol) = 9,077 lines of proof — a 12.1× ratio, higher than Tulip's overall average, consistent with Multi-Paxos being reused as a general-purpose, more heavily-specified library.
💡
The paper is explicit that line count and developer time diverge: code proofs are the bulk of the lines (mechanical symbolic execution), but protocol proofs — far fewer lines — are where the paper says most design effort actually goes.

③ Quorum math behind the failure-recovery experiment

§7.4 runs 5 replicas (2 US, 2 EU, 1 AP) and crashes/recovers one every 10 seconds. Reconstruct why the latency graph (Figure 18) moves when it does.

  1. Quorum sizes at n=5: classic = ⌈(5+1)/2⌉ = 3; fast = ⌈3·5/4⌉ = ⌈3.75⌉ = 4.
  2. t=10s, 1 US replica crashes (4 live): still ≥ 4, so a fast quorum is reachable — but now it must include the AP replica, adding a wait for a US-AP RTT (218 ms).
  3. t=20s, 1 EU replica also crashes (3 live = exactly the classic quorum, below the fast quorum of 4): Tulip falls back to the slow path — 2 round-trips through the leader, each a US-AP RTT, since the 3 survivors span US and AP.
  4. t=30s, the US replica recovers (back to 4 live): a fast quorum is reachable again in a single US-AP RTT (218 ms).
  5. t=40s, the AP replica crashes (3 live: US,US,EU): slow path again, 2 round-trips, but now each is a US-EU RTT (109 ms) — total 2×109 = 218 ms, which happens to equal the single US-AP RTT from step 4, so the graph shows no visible change in latency at t=40s even though the code path is different.
🍯
Insight: the flat-looking stretch of Figure 18 around t=30–40s isn't a coincidence of measurement — it's the arithmetic coincidence 2 × (US-EU RTT) = 1 × (US-AP RTT), i.e. 218 ms = 218 ms, given the specific AWS regions chosen.

④ Quorum intersection guarantees prepare stability

Prepare stability (§A.2) relies on "any two quorums intersect." Verify this holds for Tulip's classic quorum at n=5, and see why it would fail at a smaller size.

  1. Classic quorum size at n=5: 3 (from example ③).
  2. Do any two 3-out-of-5 quorums always share a replica? Worst case, they're as disjoint as possible: 3 + 3 = 6 replicas needed to avoid overlap, but only 5 exist. By pigeonhole, they must share at least 6 − 5 = 1 replica.
  3. Why that's exactly what the proof needs: Figure 24's argument finds a replica in both the quorum that chose p₁ and the quorum that validated a supposedly-conflicting p₂ — that shared replica can't have voted for two different values, contradiction.
  4. What if the quorum were only size 2 (i.e. not a true majority)? 2 + 2 = 4 ≤ 5, so two disjoint quorums of size 2 can exist among 5 replicas — the intersection argument fails, and two different values could both be "chosen." This is exactly why classic quorum must be a strict majority, ⌈(n+1)/2⌉, not just "some quorum."
💡
This is the same quorum-intersection fact underlying ordinary majority-vote Paxos — PSM doesn't change the distributed-systems argument, it just lets the proof state it as a stable permission (InvProposal) scoped to the group module, instead of a global fact about all 21 shared variables.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
You hold the exclusive permission ⟨n,v⟩ for a Paxos proposal. Can you conclude that proposal n's value will always be v?
Show answer
No. ⟨n,v⟩ is the mutable, exclusive point-wise view — UpdateProposal can still change it to ⟨n,v′⟩. Only after applying FixProposal to get the stable ⟨n,v⟩fix can you conclude the value is frozen forever, and that permission is then duplicable.Misconception: confusing "I have a permission naming value v" with "the value is v forever." Exclusivity and stability are separate properties — check which one a permission actually has before relying on it.
Problem 2 · medium
A replica group has n = 7 replicas. Compute the classic and fast quorum sizes, and the maximum number of replica crashes each path can tolerate while still making progress.
Show answer
Classic quorum = ⌈(7+1)/2⌉ = 4, so up to 7 − 4 = 3 crashes tolerated (slow path). Fast quorum = ⌈3·7/4⌉ = ⌈5.25⌉ = 6, so only 7 − 6 = 1 crash tolerated before falling back to the slow path.Misconception: assuming quorum size scales the same way for both paths. Fast quorum grows faster than classic quorum (¾n vs. ½n), so larger deployments get proportionally less fault tolerance on the fast path, not more.
Problem 3 · medium
Why can Tulip report a transaction as committed to the client before the commit record has finished replicating through Multi-Paxos?
Show answer
Because of the commit requirement: the outcome is a deterministic function of the (already stable) per-group prepare decisions — commit iff every participant group prepared. Once the client observes stable "prepared" permissions from every group, the outcome is fixed regardless of what happens next; replicating the commit record is just making that already-determined fact durable and visible to backup coordinators.Misconception: assuming "committed" must mean "durably logged everywhere." Tulip decouples logical commitment (determined by stable permissions) from physical replication (which can safely lag, since any future backup coordinator will derive the same outcome).
Problem 4 · hard
A transaction's locks are released on commit or abort — so why does the paper give the per-replica "validation set" permission history (monotonic) semantics instead of current-state semantics?
Show answer
Because "currently holding the lock" is not monotonic — it becomes false when the lock is released, so a permission asserting it couldn't be stable. The paper redefines the meaning to "has, at some point, obtained the lock" — a fact about the past that, once true, is true forever, even after the lock is released. This reformulated fact is monotonic, so it can be captured as a stable, duplicable permission usable in the mutual-exclusion argument without tracking the lock's current status at all.Misconception: assuming stable permissions can only describe state that never changes. They can describe historical facts about state that does change, as long as the fact itself (something happened at some point) never becomes false.
Problem 5 · medium
Using Figure 12, is it true that the module with the most implementation code also has the most protocol-proof code? Check Transaction vs. Multi-Paxos.
Show answer
No. Transaction has 882 Go lines and 4,442 protocol-proof lines (ratio ≈5.0×); Multi-Paxos has 748 Go lines but 4,148 protocol-proof lines (ratio ≈5.5×) — comparable despite less code. Backup coordinator has zero listed Go lines of its own (folded into Transaction) yet 4,445 protocol-proof lines — the largest protocol proof in the table. Protocol-proof size tracks the complexity of the correctness argument (e.g. coordinator recovery's Fast-Paxos stability argument), not lines of implementation.Misconception: assuming proof size scales with code size. It scales with the subtlety of the property being proved — a small, tricky module (coordinator recovery) can dominate the protocol proof.
Problem 6 · easy
What's the difference between the permission a↪l (protocol half) and a↪l (stable prefix), both about acceptor a's voted list?
Show answer
a↪l is one half of an exclusive fractional pair — it says "the voted list is exactly l," and only grants mutation rights when reunited with its other half. a↪l is a stable, duplicable witness that the voted list is at least l (a prefix) — it never claims to know the exact current list, only a lower bound, which remains true forever since the list only grows.Misconception: treating "prefix" permissions as weaker versions of exact-value permissions. They're a different kind of claim entirely — deliberately weaker in what they assert, which is exactly what makes them stable.
Problem 7 · hard
Explain the "timestamp-inversion" bug class (as in TAPIR) in one sentence, and explain structurally why Tulip's proof would get stuck if it were present.
Show answer
Timestamp inversion happens when a transaction with a smaller timestamp linearizes after one with a larger timestamp, violating the rule that linearization order must respect timestamp order. Tulip's value-history abstraction is built by extending the history — filling in intermediate indices, then appending strictly in timestamp order (ActionWrite's lextend). An out-of-order write would be an attempt to insert a value at an index the extension function has already passed, which the action's precondition (len(h) ≤ t) simply does not permit — the proof cannot proceed, forcing the bug to surface at verification time rather than in production.Misconception: thinking formal verification "checks for" specific known bug classes like a linter. Here, the bug is ruled out as a side effect of a monotonicity precondition chosen for an unrelated reason (enabling stable permissions) — not because anyone wrote a rule targeting timestamp inversion specifically.
Problem 8 · medium
Of Tulip's 25 actions, 13 depend on a single module and 6 depend on two. What can you conclude — and not conclude — about the remaining 6?
Show answer
You can conclude the remaining 6 actions depend on three or more of the 10 module types (25 − 13 − 6 = 6). You cannot conclude those 6 are equally hard to prove, or that they touch most of the 10 module types — the paper notes that even multi-module actions are often provable "module-by-module" without opening every dependency simultaneously, and that developers can take just the required permissions out of a module rather than importing all its variables and invariants.Misconception: equating "depends on N modules" with "proof difficulty scales with N." PSM's whole point is that even multi-module actions stay tractable because each dependency is a narrow, explicit permission, not the full state of another module.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What exactly is a "permission" in PSM?▾
A named, structured piece of evidence about (part of) the abstract protocol state, with explicit rules for who may hold it, what it lets the holder conclude, and how it can be split, merged, or converted into other permissions. Formally it's a resource in the Iris separation-logic sense — the same machinery used for ordinary heap ownership, just applied to abstract protocol variables like "the proposal set" or "the value history."
Q2How is PSM different from writing a plain TLA+ spec?▾
Same skeleton — variables, initial state, actions, invariants — but every invariant in PSM must declare exactly which permissions (slices of state) it depends on, instead of being free to reference the entire global state. That scoping is what breaks the action × invariant cross-product and enables per-module proofs.
Q3How is PSM different from just applying CSL directly to the code?▾
Applying CSL straight to code means every Hoare-triple proof mixes protocol-level reasoning ("is this prepare decision safe?") with implementation details (locks, structs, RPC retries) at once. PSM inserts a layer in between: prove protocol-level action lemmas once, using only permissions, then reuse those lemmas — as ordinary CSL resources — inside the code proof. Protocol reasoning and code reasoning stay separated.
Q4Why do stable permissions matter so much?▾
Because they're both duplicable (any module can hold a copy) and immune to invalidation (no future action can make them false). That combination is exactly what lets one module's invariant depend on a fact from another module without needing exclusive access to that module's state or being re-checked every time that module acts.
Q5What is inconsistent replication (IR), and why not just use Paxos everywhere?▾
IR lets each replica log an operation at whatever point suits it — no consistent ordering across replicas is required — which lets a client commit a prepare in a single round-trip by talking to every replica directly. Paxos, by contrast, needs a leader and (for correctness) an agreed order, which costs an extra round-trip. Tulip uses IR only where consistency isn't needed (prepare) and Paxos where it is (the final commit/abort decision).
Q6Does Tulip's proof cover liveness (that transactions eventually finish)?▾
No — explicitly out of scope. The proof is a safety property: strict serializability holds for whatever transactions do commit or abort. It does not guarantee every transaction eventually reaches a decision (that would require reasoning about timeouts, network delivery, and fairness, which the paper leaves to future work).
Q7Why is the proof about 10.6× the size of the implementation — is that unusually large?▾
The paper compares this ratio favorably to other verified systems with "strong layering" like Grove — it's not considered unusually large for a machine-checked, code-level (not just protocol-level) proof of a system this complex. The point of PSM is precisely to keep this ratio from exploding as Tulip's feature set (sharding, crash recovery, MVCC, coordinator recovery) grew.
Q8What real bugs did verification actually catch?▾
Three are named: (1) an ambiguous "timestamp 0 means fast path" encoding that couldn't distinguish a fast read from a legitimate quorum read of the first version; (2) transactions releasing locks they never acquired, inherited from code originally written for 2PC-over-Paxos (which always locks all replicas) but reused for 2PC-over-IR (which only locks a quorum); and — by construction, since the proof would get stuck — the class of timestamp-inversion bugs that affected TAPIR despite its own TLA+ proof.
Q9How does Tulip's performance compare to TAPIR?▾
In the same datacenter, a non-strict variant of Tulip matches TAPIR's throughput-latency curve on the Retwis workload; the strict-serializable variant adds only the ~40µs clock-skew wait. In the wide-area setting, Tulip actually beats TAPIR for US/EU clients because it implements a single-RTT fast-quorum optimization that the TAPIR prototype doesn't.
Q10Does PSM only apply to Paxos-style protocols?▾
No — the paper states PSM can specify anything expressible as a state machine, the same class TLA+ handles. Paxos is the running example because it's small enough to show the technique clearly; the payoff is demonstrated at scale on Tulip's much larger, non-Paxos-specific transaction protocol.
Q11When is PSM overkill, per the paper's own "Limitations" section?▾
Two cases: (1) there's no plan to connect the protocol proof to a concurrent implementation, or (2) the protocol has few actions/invariants, or has clean enough layering to use coarse-grained refinement (as in IronFleet's IronRSL or Verdi's VST) instead of PSM's fine-grained permission sharing.
Q12What's the practical workflow for using PSM, according to the authors' own experience?▾
Three steps, in order: (1) identify the abstract state needed by understanding the sub-protocols and their real interactions (easy to overlook entangled properties, as happened with 2PC's mutual-exclusion vs. prepare-stability); (2) break the protocol into actions, each producing one or two stable permissions with clear meanings; (3) write the implementation and annotate where each action lemma will be invoked before proving it, so program proofs — not protocol formulations — absorb most late-stage fixes.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
PSM (Permissioned State Machine)TLA-style protocol spec where every invariant is scoped by explicit permissions rather than free to reference all shared state.
PermissionNamed evidence about part of the abstract state, with rules for ownership, what it licenses, and how it composes (merge/split/convert).
Stable permissionA duplicable permission describing a fact that, once true, remains true forever — typically about monotonic (append-only, fix-once) state.
Fractional permissionOwnership of a variable split into fractions (e.g. protocol half / implementation half); full ownership (all fractions reunited) is required to mutate.
Frame ruleCSL's core modularity rule: resources not mentioned in a function's spec are left untouched and can be "framed away" from reasoning about that call.
Action lemmaA proved theorem that an action's preconditions (permissions in) imply its postconditions (permissions out) while preserving its module's invariants — the interface between protocol and code proofs.
Commit requirementThe rule that a transaction's outcome is a deterministic function of its per-group prepare decisions, letting commit replication happen off the critical path.
Fast PaxosA Paxos variant with a fast round (bypass the leader, needs a bigger quorum) and classic rounds (go through a leader, majority quorum); Tulip specializes it for prepare-decision stability.
Supporting terms
Quorum (classic / fast)A subset of replicas large enough to guarantee overlap with any other quorum of its kind — ⌈(n+1)/2⌉ for classic, ⌈3n/4⌉ for fast, at n replicas.
Value historyTulip's per-key monotonic abstraction: a list of values indexed by timestamp, standing in for the mutable MVCC database for proof purposes.
Validation setA per-replica, per-key logical (proof-only) record of which transactions have, at some point, acquired locks — given history semantics to stay monotonic.
Ranked prepare decisionsPer-replica list, indexed by coordinator rank, of accepted prepare/unprepare decisions — the Fast-Paxos analogue of a Paxos acceptor's voted list.
Command pool / command logMulti-Paxos's abstract state: the set of submitted commands vs. the append-only agreed-upon log; InvSubsume requires log ⊆ pool.
Coordinator recoveryThe backup-coordinator protocol that finalizes a transaction whose original client coordinator has failed, without violating prepare stability.
Owner bit / lock invariantPer-replica mutex protecting physical state; the CSL "lock invariant" is what's guaranteed true whenever the lock is free.
Goose / Grove / Iris / RocqThe verification toolchain: Goose (Go→Rocq model), Iris (CSL framework in Rocq), Grove (verified network/file/RPC library), Rocq (the proof assistant, formerly Coq).
