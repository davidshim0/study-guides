Before you begin

Let the kernel protect resources, and let libraries in each application manage them

A 1997 paper from the MIT Laboratory for Computer Science: the second-generation exokernel (Xok, for x86 PCs), its default library operating system (ExOS), the disk-multiplexing system XN, and the first end-to-end measurements of real applications on an exokernel.

⚡ TL;DR

  • Claim: a kernel should only protect resources (allocation, revocation, sharing, ownership tracking) and leave management (policies, abstractions) to unprivileged library operating systems (libOSes) linked into each application. The 1995 exokernel paper argued this with microbenchmarks; this paper asks whether real applications, unmodified UNIX programs, and the whole multi-program system come out ahead.
  • The hard case is the disk. The kernel must decide who owns each block without knowing the file system's metadata format. XN (the authors' fourth design) has each library file system describe its metadata types with templates whose ownership function, owns-udf, is an untrusted deterministic function (UDF) the kernel runs before and after every proposed change. XN also enforces two crash-ordering rules (via "tainted" blocks and a "will free" list) and keeps a system-wide buffer cache registry so applications can share cached blocks.
  • Unmodified UNIX programs: an 11-step software-install workload takes 41 s on Xok/ExOS, 51 s on OpenBSD with the same C-FFS file system, and about 60 s on stock OpenBSD and FreeBSD. Removing all protection (XN and inserted checks) cuts system calls from 300,000 to 81,000 but time only from 41.1 s to 39.7 s.
  • Specialized applications: the Cheetah web server runs its own TCP (Transmission Control Protocol) and file system code: its file cache doubles as the retransmission pool, checksums are precomputed and stored with each file, acknowledgments ride on responses, and embedded images are placed next to their page on disk. It is claimed 8× faster than the best OpenBSD server for small documents (Figure 3's unclipped bars show about 6×) and reaches over 29.3 MB/s on three 100 Mbit/s Ethernets with the CPU over 30% idle; the XCP copy program is 3× faster than cp on the same system.
  • Global performance: with 7 to 35 randomized jobs, total time on Xok/ExOS roughly matches FreeBSD for ordinary programs (Figure 4) and is far lower when some programs use C-FFS aggressively (Figure 5).
  • Costs the authors name: interfaces take several redesigns, exposed kernel structures are not a stable interface, information is lost when the kernel cannot tell what a page is for, and some ExOS state was still unprotected shared memory when measured.

Quick glossary
KernelThe program that runs in the processor's privileged mode, the only code allowed to change page tables, talk to devices directly and handle interrupts; everything else reaches those powers through system calls.
OS abstractionA software object the operating system builds on top of raw hardware and presents instead of it, such as a file (instead of disk blocks), a process (instead of a CPU and page tables) or a socket (instead of network packets).
ExokernelA kernel whose interface is as close to the hardware as possible: it multiplexes physical resources (pages, disk blocks, CPU time slices, packets) among applications and checks ownership, but implements no high-level abstractions itself.
ProtectionThe enforcement of who may use which resource: refusing an application access to pages, blocks or packets it does not own or has not been granted.
ManagementThe policy decisions about resources an application is allowed to use: which disk block to place a file in, which page to evict, when to write back, how to schedule its own threads.
Library operating system (libOS)An ordinary, unprivileged library linked into an application that implements OS abstractions (files, processes, sockets) on top of the exokernel's low-level interface. The paper's is ExOS.
XokThe paper's exokernel for Intel x86 PCs, the successor to Aegis (for MIPS DECstations).
ExOSXok's default libOS, a library implementing most 4.4BSD UNIX abstractions so that unmodified UNIX programs run on Xok after relinking.
EnvironmentXok's kernel structure for one running process: the hardware-specific state needed to run it (such as an exception stack) and to deliver events (interrupts, exceptions) to it.
Physical nameThe hardware's own identifier for a resource (a physical page number, a disk block number) as opposed to a virtual name the kernel translates (a virtual address, a file descriptor).
Secure bindingAn authorization check performed once, when a resource is attached to an application (for example when a page is entered into its page table), so that later uses go through the hardware without further checks.
XNXok's in-kernel stable storage system: the part of the kernel that multiplexes the disk at block granularity, decides which principal owns each block, enforces crash-ordering rules, and maintains the buffer cache registry.
LibFSA library file system: the part of a libOS that implements a particular on-disk format and file policies on top of XN.
TemplateXN's description of one metadata type of one libFS (for example "FFS Inode"), stored on disk in a type catalogue and unchangeable once installed; it consists of three functions.
UDF (untrusted deterministic function)A small function, written by an untrusted libFS in a restricted pseudo-RISC (reduced instruction set computer) assembly language, whose output the kernel can trust because it depends only on its input. owns-udf maps a metadata block to the set of blocks it points to.
Buffer cache registryA kernel table, mapped read-only into every application, recording which disk block is cached in which physical page and that entry's state (dirty, out of core, uninitialized, locked). It holds mappings, not data.
Tainted blockA metadata block that points to an uninitialized block or to another tainted block; XN refuses to write it to disk while it is reachable from a persistent root.
Wakeup predicateA small boolean expression an application downloads into Xok; the kernel evaluates it just before scheduling that environment and skips the environment while it is false.
Software regionAn area of memory that can only be read or written through system calls, which gives protection at granularity smaller than a page.
C-FFSThe co-locating fast file system: a libFS derived from the Berkeley Fast File System (FFS), and ExOS's local file system. That it keeps a directory's small files and their inodes physically together comes from its own paper by Ganger and Kaashoek (general knowledge, not in this paper).
CheetahThe authors' HTTP/1.0 (Hypertext Transfer Protocol) web server, built on their extensible I/O library XIO and its own TCP and file system code.
Short primers (tap to open)
1What a kernel abstraction is, and what it costs to have only one▾

Hardware offers raw resources: physical pages of memory, numbered disk blocks, a network card that receives packets, a CPU that runs whatever its program counter points at. A conventional kernel never hands these to programs directly. It builds abstractions on top of them and exports only the abstractions: a file is a name plus a byte array, behind which the kernel picks disk blocks, caches them in pages it chooses, and writes them back when it decides; a socket hides packets, retransmission buffers and checksums; a process hides page tables and scheduling.

Abstractions do two jobs at once. They make programming easy, and they are the unit of protection: the kernel checks permissions on the file, so it never needs to check individual blocks. The cost is that every program gets the same policies. A database that wants its own buffer replacement, a web server that wants to send file pages straight to the network, or a copy program that wants to schedule all disk reads at once must "trick" the kernel or do without. The paper's opening argument: "An interface designed to accommodate every application must anticipate all possible needs", and "such anticipation is infeasible".

Now you're ready: the exokernel question is whether protection can be kept while the abstractions move out of the kernel.
2Protection versus management▾

Take physical memory. Protection is the set of facts the kernel must enforce so that one program cannot harm another: page 7,000 belongs to process A; B may read it but not write it; when A exits the page is reclaimed. Management is everything else: which page A should give up when memory is short, whether to prefetch, whether a page caches a file block or holds heap data, whether to compress it before paging it out.

In a conventional kernel both live in the same code, so the kernel's management choices are imposed on everyone. The exokernel draws the line at the minimum: the kernel keeps "allocation, revocation, sharing, and the tracking of ownership", and every policy moves to the application. The design problem is that the minimum is not always low level: protecting a file requires knowing which disk blocks the file's metadata points to, which is a property of the file system's format, not of the hardware.

Now you're ready: each mechanism in this paper is a way to let the kernel check a protection fact without adopting a management policy.
3Library operating systems, versus microkernels and virtual machines▾

A libOS is OS code compiled as a normal library. A UNIX program calls read(fd, ...); instead of trapping into a kernel, the call runs ExOS code in the same address space, which looks up its own file descriptor table, finds the cached block, and copies bytes. Only when it needs a protected resource (a new page, a disk read, a page-table change) does it make a Xok system call. Because the library is unprivileged, a bug or a deliberate change in it affects only the program that linked it, and different programs on one machine can use different libOSes.

Two older structures look similar but are not. A microkernel moves OS services into separate privileged user-level servers; applications still get the server's fixed interface (the paper: servers "can be viewed as fixed kernel subsystems that happen to run in user space"). A virtual machine monitor gives each guest OS its own emulated hardware; the guests can be customized, but "emulation hides information" and virtual machines (VMs) cannot share abstractions such as processes or files except through network-style protocols. The exokernel keeps one machine with shared files and processes, and pushes customization into each application.

Now you're ready: the paper's worry is the flip side: a libOS can trust its own application, but not the other libOSes it shares a file or a pipe with.
4x86 page tables and the TLB (general knowledge, not in the paper)▾

On the 32-bit x86 of 1997, a virtual address is split 10 / 10 / 12 bits. Register CR3 holds the physical address of a page directory of 1024 entries; the top 10 bits pick one, which points to a page table of 1024 entries; the next 10 bits pick a page table entry (PTE), which holds the physical page number; the low 12 bits are the offset in that 4 KB page. Each PTE also carries permission bits (present, writable, user-accessible), bits the hardware sets (accessed, dirty), and three bits the hardware ignores and leaves "available" to software.

The translation lookaside buffer (TLB) caches recent translations. On a TLB miss the x86 hardware walks the tables itself; the format is fixed by the processor and the kernel never sees the miss. MIPS, the processor of the earlier exokernel Aegis, instead traps to software on every TLB miss, so Aegis could let applications define their own page-table format. This difference explains several of Xok's design choices: applications cannot write x86 page tables directly (the hardware would trust any physical page they named), so they change them through system calls that Xok checks.

Now you're ready: a PTE is the prototype "secure binding": checked once when written, then used by hardware millions of times with no further checks.
5Disk blocks, metadata, and who owns a block▾

A UNIX-style file system stores data in fixed-size blocks and records which blocks belong to which file in metadata: an inode lists the first few block numbers and points to indirect blocks that list more; directories map names to inode numbers; a free map records unused blocks. Ownership of a data block is therefore not stored with the block. It is implied by the fact that some inode (or indirect block) owned by some user points to it.

In a normal kernel this is easy to check, because the kernel's file system code knows the inode format. If file systems become untrusted libraries with formats of their own, the kernel can no longer read the pointers. A malicious library could write an inode that points at someone else's block and then read it "as its own file". There is also a crash problem: if a pointer to a block reaches the disk before the block itself is initialized, or after the block has been given to someone else, a crash leaves one user's metadata pointing at another user's data. Ganger and Patt's rules (never reuse a block before nullifying old pointers to it; never write a pointer before its target is initialized; when moving, set the new pointer before clearing the old) prevent this.

Now you're ready: XN must answer "may this principal touch block b?" and enforce the crash rules, for metadata formats it cannot parse.
6What a web server does with TCP (general knowledge, not in the paper)▾

TCP is the reliable byte-stream protocol that runs on top of IP (the Internet Protocol, which carries individual packets). An HTTP/1.0 client opens a TCP connection, sends one request ("GET /index.html"), receives the document, and the connection closes. TCP splits the document into segments of at most about 1460 bytes each on Ethernet. Every segment carries a checksum computed over its payload, so normally the CPU reads every byte of the file to compute it. The receiver sends acknowledgments (ACKs); until a segment is acknowledged the sender must keep a copy so it can retransmit it if it was lost. In a conventional kernel that copy lives in the socket's send buffer, separate from the file cache, so a file sent over the network exists in the file cache and again in the socket buffer, with a CPU copy between them.

ACKs are small packets of their own unless they can ride on a data packet going the same way ("piggybacking"); TCP implementations delay ACKs briefly in the hope of doing so. For tiny documents, control packets (connection setup, ACKs, teardown) are a large share of all packets. A 100 Mbit/s Ethernet carries at most 12.5 MB/s of raw bits, less after headers.

Now you're ready: Cheetah's three optimizations each remove one of these costs: the copy, the extra control packets, and the disk seeks between a page and its images.
The whole story in one place

Protect at the lowest level, manage in the application

The exokernel keeps only what protection needs. This paper asks whether that pays off for real programs, and shows how to protect the one resource whose ownership the hardware cannot express: files on disk.

In a conventional operating system the kernel owns every abstraction: files, sockets, processes, the buffer cache. Applications get one implementation of each, with one set of policies. The exokernel architecture, proposed by Engler, Kaashoek and O'Toole in 1995, splits the work differently: the kernel protects resources and applications manage them. The kernel's interface is "as close to the hardware as possible": it allocates physical pages, disk blocks and CPU slices, tracks who owns them, lets owners share them, and takes them back. Everything above that, including the UNIX abstractions themselves, lives in unprivileged library operating systems linked into each application, which can be "modified or replaced at will".

The 1995 paper described Aegis, a MIPS research prototype that "performed significantly better than Ultrix on microbenchmarks". This paper builds Xok for x86 PCs and ExOS, a libOS rich enough to compile the whole system on itself, and asks four questions: do ambitious applications gain a lot, do unmodified UNIX programs lose, does global performance suffer without a central policy, and does integrity suffer when shared structures have no central manager. The answers are measured against FreeBSD and OpenBSD on the same 200 MHz Pentium Pro.

Most resources map cleanly onto hardware protection: a page can be checked when it is entered into a page table, a packet is claimed by a downloaded filter. The disk does not. A block's owner is whoever's metadata points to it, and metadata formats belong to the file system, which is now an untrusted library. The authors' answer after three failed designs is XN: each library file system registers templates for its metadata types, and each template includes owns-udf, a deterministic function in a restricted language that, given a metadata block, lists the blocks it points to. To allocate a block, the libFS proposes a byte-level change to its metadata; XN runs owns-udf on the old and the changed copy and accepts only if the difference is exactly the requested block. The kernel never learns the format, but it cannot be fooled about ownership. XN also enforces crash-ordering rules (no pointer to uninitialized data reaches disk; no freed block is reused while an on-disk pointer to it survives) and keeps a buffer cache registry, so that different libraries share one cached copy of each block.

The measurements support the architecture on the authors' workloads. Unmodified UNIX programs run as fast as on OpenBSD with the same file system, and faster than stock BSDs because ExOS's file system (C-FFS) is better: 41 s versus about 60 s for an install-a-compiler workload. Protection is cheap in practice: removing it cuts system calls by 73% but time by only 3.4% (this guide's arithmetic from the paper's 300,000 versus 81,000 calls and 41.1 versus 39.7 s). Applications that exploit control gain more: Cheetah sends file pages straight from the file cache with precomputed checksums and does not keep a separate retransmission copy, and is claimed to be eight times faster than the best OpenBSD web server on small documents. With many programs competing, Xok/ExOS keeps up with FreeBSD.

The authors are explicit about the costs: interface design took several iterations (XN is the fourth disk design), exposed kernel data structures are not a stable application programming interface (API), the kernel can lose information about what pages are used for, and some ExOS tables were still unprotected shared memory, with protection cost estimated by inserting system calls. Their main lesson is that the gains come from control over expensive operations such as I/O, not from fast system calls.

🍯 Key takeaways

  • The kernel's job shrinks to "allocation, revocation, sharing, and the tracking of ownership"; abstractions and policies move into replaceable libraries.
  • Protection that does not map to hardware (file ownership, modification times) is done with kernel software abstractions and small pieces of application code the kernel can trust: deterministic UDFs, wakeup predicates, packet filters.
  • XN lets untrusted file systems share one disk: ownership by owns-udf before and after each change, crash ordering by tainted blocks and deferred frees, cache sharing by a registry of block-to-page mappings.
  • Unmodified UNIX programs lose nothing measurable (41 s vs 51 s on the same file system) and protection costs little (41.1 s vs 39.7 s without it).
  • Applications that use the control gain most: Cheetah claims 8× on small documents, XCP 3×; both win by avoiding copies and scheduling I/O themselves.
  • The price is interface design effort, unstable exposed structures, lost information, and, in this prototype, some still-unprotected shared state.
Six everyday pictures

How to think about an exokernel

Each stands alone. Every card ends with where the picture stops being true, tied to a mechanism in How It Works.

Separate protection from management · libOSes

A landlord who rents bare rooms

A furnished hotel decides your bed, your desk and when the room is cleaned. A landlord who rents bare rooms only checks your key, records which rooms are yours, and takes a room back if you stop paying. You bring your own furniture, or buy the standard kit from the store next door (ExOS) if you do not care. The landlord's job is protection; the furniture is management.

Where it breaks: tenants share walls, plumbing and a common hallway. Shared things (a file, a pipe, the process table) need rules the landlord must enforce even though the tenants built them, which is why Xok needs software abstractions and downloaded checks, not only keys (M7, M8).
UDFs · owns-udf · templates

A notary who cannot read your language but can run your counting rule

You keep your property records in a format only you understand. The notary will not learn it. Instead you file, once, a mechanical rule that, given any page of your records, lists the parcels it claims. When you want to add a parcel, you show the page before and after your edit; the notary runs your rule on both and stamps the edit only if the only new parcel is the one you asked for, and it was unowned.

Where it breaks: a human could be fooled by a rule that answers differently on different days; XN's rule language is checked to be deterministic and the template can never be changed after it is filed (M11).
Buffer cache registry

A library catalogue that lists which reading room holds each book

Every reader can look up the catalogue; it says "volume 812 is on the desk in room 4". The catalogue holds no books. A reader allowed to see volume 812 may walk into room 4 and read it; nobody fetches a second copy from the stacks. Who owns the desk in room 4, and when it is cleared, is up to the reader who set it up.

Where it breaks: a reader without the right to annotate a volume cannot just put "their" copy on a desk and list it, or others would read a forgery; such readers must ask the librarian to fetch the volume onto their desk and set its protection ("read and insert", M13).
Tainted blocks · ordered writes

Never publish a phone directory listing a number that is not connected yet

If the directory goes to print first and the phone line is installed later, anyone who calls in between gets a stranger, or nothing. So the line is installed first, then the listing printed. XN applies this to disk: a metadata block that points to an uninitialized block is "tainted" and may not be written until its target is.

Where it breaks: a directory that nobody can find yet (an unattached subtree) or a temporary one that is shredded every night (a temporary file system) can be printed in any order, and XN skips the checks for exactly those (M12).
Wakeup predicates

Leaving "wake me when the laundry is done" with the front desk

Instead of walking downstairs every ten minutes to check the dryer, you leave a simple condition with the front desk, which glances at the dryer's panel each time it would otherwise knock on your door. Xok evaluates the downloaded predicate when the environment is about to be scheduled and does not run it until the condition holds.

Where it breaks: the front desk will only accept conditions it can check at a glance: predicates have no loops, and Xok translates their addresses to physical ones in advance and keeps those pages from being freed while the predicate exists (M17).
Cheetah · merged file cache and retransmission pool

A bookstore that mails the shelf copy and pre-weighs every book

A normal shop photocopies each book into the mailroom, weighs the copy, and keeps the photocopy until delivery is confirmed in case it is lost. Cheetah mails straight from the shelf, with the postage (the checksum) already written on each book, and if a parcel is lost it simply mails from the shelf again.

Where it breaks: the shelf copy must not change while a parcel is in transit (inference), and only an application that owns both the shelf (file cache) and the mailroom (TCP) can arrange that; a general-purpose kernel cannot assume it (M22).

1 · The principles: protect, expose, and get out of the way

The kernel provides "primitives at the lowest possible level required for protection", restricts its own management to "allocation, revocation, sharing, and the tracking of ownership", and exposes allocation, physical names, revocation and information to applications. Checks happen at bind time (secure bindings), so that the steady state runs at hardware speed (M1 to M5).

2 · Abstractions in libraries, with protected sharing

ExOS implements UNIX in a library. Where libOSes share state (the process table, pipes, file metadata), the kernel offers uniform access control with hierarchically named capabilities, software abstractions that bind resources together, downloaded code, software regions, wakeup predicates and robust critical sections. How much defense a shared abstraction needs depends on whether the sharers trust each other mutually, in one direction, or not at all (M6 to M9).

3 · The disk: XN

XN decides ownership of every block using templates and deterministic functions supplied by untrusted library file systems, enforces two crash-ordering rules with tainted blocks and deferred frees, and keeps a registry mapping cached blocks to the physical pages that hold them so that libFSes can share one copy. C-FFS adds UNIX-specific invariants on top (M10 to M15).

4 · Xok and ExOS: memory, predicates, CPU, UNIX

On the x86 the hardware fixes the page-table format, so Xok mediates page-table writes but exposes the memory management unit (MMU) bits and kernel structures; wakeup predicates let libOSes sleep on arbitrary conditions; the CPU interface is time slices with upcalls and directed yields; ExOS builds processes, fork, pipes and file descriptors on these, with some shared tables still unprotected (M16 to M19).

5 · What control buys, and the global picture

A binary emulator runs OpenBSD programs at near-native speed; XCP copies files 3× faster by scheduling disk I/O itself and never touching the data; Cheetah serves web pages up to 8× faster than the best OpenBSD server. Under multiprogramming the kernel enforces global policy only through allocation and revocation, plus exposed global least-recently-used (LRU) information (M20 to M23). Background and context
  • Kaashoek, Engler, Ganger, Briceño, Hunt, Mazières, Pinckney, Grimm, Jannotti and Mackenzie, MIT Laboratory for Computer Science. 16th ACM Symposium on Operating Systems Principles (SOSP-16), Saint-Malo, France, October 1997, pages 52 to 65.
  • It evaluates the architecture "proposed in [11]" (Engler, Kaashoek and O'Toole, SOSP 1995), which "described a research prototype that performed significantly better than Ultrix on microbenchmarks" but "left many questions unanswered".
  • Three exokernels built over three years: Aegis (MIPS DECstations), Glaze (the Fugu multiprocessor) and Xok (Intel x86), the system measured here.
  • Related approaches named: better microkernels (L4-style, citing Liedtke and Härtig), virtual machines (citing Disco and Goldberg), and safe downloading of code into the kernel (SPIN, Vino).
The problem

"In traditional operating systems, only privileged servers and the kernel can manage system resources. Untrusted applications are restricted to the interfaces and implementations of this privileged software. This organization is flawed because application demands vary widely." The open questions after 1995: do real applications gain; do unmodified UNIX programs lose; is global performance compromised "when no centralized authority decides scheduling and multiplexing policies"; and does the lack of central management of shared structures "lower the integrity of the system"?

The result

"Most unmodified UNIX applications perform comparably on Xok/ExOS and on FreeBSD or OpenBSD. Some applications, however, run up to a factor of four faster on Xok/ExOS." Cheetah "performs up to eight times faster than the best UNIX HTTP server we measured on the same hardware." Experiments with many concurrent applications "show that exokernels can offer competitive global system performance." The paper also contributes XN's interface for multiplexing disks among untrusted file systems.

The central trade-offs
  • Power versus protection: "It generally takes several iterations to obtain a satisfactory interface, as the designer struggles to increase power and remove unnecessary functionality while still providing the necessary level of protection."
  • Decentralized management versus global information: "if virtual memory and the file system are completely at application level, the exokernel may be unable to distinguish pages used to cache disk blocks and pages used for virtual memory."
  • Exposure versus stability: "Because exposed data structures do not constitute a well-defined API, software that directly relies on them ... may need to be recompiled or modified if the kernel changes."
  • Trust versus defensive code: libOSes can resemble monolithic kernel code when sharers trust each other, and must be defensive when they do not.
Effect of changes (whole design)
  • If kernel crossings become much cheaper or much more expensive: the paper's own lesson is that application speed came from control over I/O, not fast system calls, so the conclusions should hold either way for I/O-bound programs; system-call-heavy libOS operations (fork's batched page-table updates, protected pipes) would move with the crossing cost (inference).
  • If the hardware defined less (a software-refilled TLB, as on MIPS): page tables could move to user level, as on Aegis, which the paper reports made libOSes "tricky" (M16).
  • If most sharing were between mutually distrustful processes: the cheap "mutual trust" implementations would not apply and more abstractions would need XN-like kernel support (M9).
  • If devices gained their own layers of indirection (later disks and solid-state drives, SSDs, remap blocks internally, general knowledge), physical block numbers would no longer reveal physical locality, weakening XCP's and C-FFS's layout optimizations but not XN's ownership checks (inference).

M1 · Separate protection from management

TL;DR
ProblemA kernel interface designed for every application "must anticipate all possible needs", and its implementation must "resolve all tradeoffs"; mistakes are costly and applications cannot fix them.
MechanismThe kernel exports "primitives at the lowest possible level required for protection" and restricts its own management to "allocation, revocation, sharing, and the tracking of ownership". All other management moves to unprivileged libraries.
Trade-offApplications choose their own policies and abstractions; in exchange, the kernel interface is hard to design and libraries must defend any invariant they share with others.
Breaks whenProtection itself requires understanding a high-level format (files, modification times), which forces the kernel to accept code or abstractions from outside (M7, M11).
Key points
  • "Exokernels separate protection from management: they protect resources but delegate management to applications. For example, each application manages its own disk-block cache, but the exokernel allows cached pages to be shared securely across all applications."
  • "The goal of an exokernel is to give efficient control of resources to untrusted applications in a secure, multi-user system."
  • "Exokernels provide primitives at the lowest possible level required for protection, ideally, at the level of hardware (disk blocks, context identifiers, TLB, etc.). Resource management is restricted to functions necessary for protection: allocation, revocation, sharing, and the tracking of ownership."
  • "These principles apply not just to the kernel, but to any component of an exokernel system. Privileged servers should provide an interface boiled down to just what is required for protection."
  • On microkernels: "If applications are restricted to inadequate interfaces, it makes little difference whether the implementations reside in the kernel or privileged user-level servers ... For example, it is difficult to change the buffer management policy of a shared file server."
  • XN as the worked case: "XN controls only what is necessary to enforce these protection rules. All other abilities (I/O initiation, disk block layout and allocation policies, recovery semantics, and consistency guarantees) are left to untrusted libFSes." (The paper sets the list off with dashes; rendered here with parentheses.)
How it works, step by step: sorting one resource's decisions
  1. Take the disk and list every decision a file system makes about it: which block a new file gets; whether to read ahead; which cached block to evict; when dirty blocks go to disk; in what order metadata is written; what the on-disk format is; who may read the file.
  2. Ask of each: can a wrong choice by application A hurt application B? Block placement: no, as long as A places only into blocks it owns. Eviction policy for A's own cache pages: no. Format: no, if the kernel can still tell which blocks A owns. Who may read a file: yes. Writing a pointer to an uninitialized block: yes, after a crash it can expose another user's old data (M12).
  3. The "yes" items stay in the kernel as protection: ownership of each block, access checks, two crash-ordering rules, coherent sharing of cached blocks. These are XN's responsibilities.
  4. The "no" items leave the kernel as management: C-FFS chooses its layout, XCP chooses its disk schedule, Cheetah chooses to keep checksums in its files.
  5. The same sort for memory leaves Xok with page ownership and page-table checks, and moves paging policy, copy-on-write, and the choice between disk cache and VM backing store to the libOS (M13, M16).
Assumptions it relies on
  • A1. Protection can be stated in terms of low-level resources, or in terms the kernel can verify without adopting a policy (implicit; strained for files, which is why XN exists).
  • A2. Most applications are content with a standard libOS; only some need custom management (stated: "not all applications need customized resource management").
  • A3. Application programmers will write or modify OS libraries (stated as a hope: "there are several orders of magnitude more application programmers than OS implementors").
  • A4. Global goals can be met with allocation and revocation alone (stated in Section 8; M23).
If an assumption changes
  • A1 changes (a resource whose protection depends on its contents): the kernel needs downloaded, verifiable code (UDFs, packet filters) or a kernel software abstraction; each such addition took several design iterations in the authors' experience.
  • A2 changes (every program needs custom management): the architecture still works, but the development effort shifts to many libOS variants (inference).
  • A3 changes (few people write libOS code): ExOS becomes a de facto fixed OS in a library; unmodified programs still benefit from whatever ExOS does better (C-FFS), which is the Section 6.2 result.
  • A4 changes (global goals need more than allocation and revocation): the kernel needs information it may have lost, such as whether a page caches a block or holds heap data (Section 9.2).
Design notes and rejected alternatives

The paper rejects three alternatives as not giving control: microkernel servers (fixed interfaces in user space), virtual machines (emulation hides information, and VMs cannot share abstractions "such as processes or file descriptors"), and downloading code alone, which it calls "complementary" because exokernels themselves download code "to let the kernel leave decisions to untrusted software". It also notes that a determined kernel programmer could implement any optimization; the claim is that libraries make it easier: "porting C-FFS to OpenBSD took more effort than designing C-FFS and implementing it as a library file system."

Connections

Hints: Lampson's "Leave it to the client" and "Don't hide power" ("The purpose of abstractions is to conceal undesirable properties; desirable ones should not be hidden") state the same split for interfaces in general; the exokernel paper cites Lampson among the "classic rationales" for extensibility (connection is this guide's). FFS: FFS is the opposite case, with all layout policy (cylinder groups, rotational placement) inside the kernel and tuned with hardware parameters only the kernel sees (inference). Dune: also hands applications privileged hardware, but its paper says "Dune differs because its goal is not extensibility".

M2 · Expose allocation, and use physical names

TL;DR
ProblemA kernel that allocates implicitly (on page fault, on file write) decides placement for the application; a kernel that hands out virtual names must translate them on every use.
Mechanism"Applications allocate resources explicitly. The kernel allows specific resources to be requested during allocation." And "Exokernels use physical names wherever possible."
Trade-offApplications control placement and avoid translation, in exchange for handling details (which block, which page) that a conventional kernel hides.
Breaks whenA physical name stops carrying physical meaning (remapped devices), or two applications want the same specific resource.
Key points
  • "Expose allocation. Applications allocate resources explicitly. The kernel allows specific resources to be requested during allocation."
  • "Expose names. Exokernels use physical names wherever possible. Physical names capture useful information and do not require potentially costly or race-prone translations from virtual names."
  • "Applications communicate with the kernel using low-level physical names (e.g., block numbers); the kernel interface is as close to the hardware as possible. LibOSes handle higher-level names (e.g., file descriptors) and supply abstractions."
  • On XN: "A libFS selects blocks to allocate by reading XN's map of free blocks, allowing libFSes to control file layout and grouping."
How it works, step by step: C-FFS places a small file next to its directory
  1. Read the free map. XN exports "free maps and other on-disk structures"; C-FFS reads which blocks near its directory's blocks are free, say blocks 10,240 to 10,250 (illustrative numbers).
  2. Request a specific block. C-FFS asks XN to allocate block 10,241 into the directory's metadata, passing the proposed change (M11). The request names the block; XN does not choose.
  3. XN checks that 10,241 is free, that the caller may modify that metadata, and that the change claims exactly 10,241.
  4. The libFS keeps physical names in its own metadata and in its own cache index; there is no kernel translation from a file offset to a block on later reads.
  5. Contrast: a UNIX write() past end of file lets the kernel pick a block by its own policy; the program never sees the block number (general knowledge).
Assumptions it relies on
  • A1. Physical names reveal something useful (stated: they "capture useful information"), for example that consecutive disk blocks are close on the platter (implicit).
  • A2. Applications can see enough of the free state to pick well (stated for disk: XN exports its free map).
  • A3. Conflicts between requests are rare or cheap to retry (implicit).
If an assumption changes
  • A1 changes (the device remaps names): requesting block 10,241 no longer means "next to 10,240" physically; layout choices lose their effect while protection is unaffected (inference).
  • A2 changes (free state hidden): applications would have to allocate blindly, losing the C-FFS and XCP layout benefits (inference).
  • A3 changes (heavy contention for specific resources): a request for a block another libFS just took fails and must be retried with fresh free-map data; the paper does not measure this (inference).
Design notes and rejected alternatives

The alternative is virtual names with translation, which the paper calls "potentially costly or race-prone". Physical names also make sharing simple: the registry is indexed by block number, so any libFS that knows the block number can find a cached copy (M13).

Connections

FFS: FFS's allocator chooses blocks inside the kernel from cylinder-group bitmaps; under XN the equivalent bitmap search would be C-FFS code reading XN's free map (inference). Superpages: requesting specific physical pages is what a libOS would need to build its own superpage reservations (inference). F2FS: F2FS's node address table exists precisely to add a translation layer; XN's interface would expose the physical block numbers that table maps to (inference).

M3 · Expose revocation (what this paper says, and what it does not)

TL;DR
ProblemWhen the kernel needs a resource back, a conventional kernel picks the victim (a page, a buffer) itself, so the application's knowledge of what is valuable is wasted.
Mechanism"Exokernels expose revocation policies to applications. They let applications choose which instance of a resource to give up."
Trade-offBetter victims chosen with application knowledge, in exchange for a protocol in which the kernel must wait for, and may have to override, the application.
Breaks whenThe application cannot respond (paged out, buggy, malicious), or the kernel takes a resource while the application's own code depends on it (self-paging, Section 9.2).
Key points
  • "Expose revocation. Exokernels expose revocation policies to applications. They let applications choose which instance of a resource to give up. Each application has control over its set of physical resources."
  • CPU: Xok divides time into "round-robin-scheduled slices with explicit notification of the beginning and the end of a time slice". The end-of-slice notification is the CPU's form of visible revocation (inference connecting this to the 1995 paper's term).
  • Global policy: "Since an exokernel controls resource allocation and revocation, it has the power to enforce global policies. Quota-based schemes, for instance, can be trivially enforced using only allocation denial and revocation."
  • Self-paging: "Careful planning is necessary to ensure that libOSes can quickly select and return a page to the exokernel, and that there is a facility to swap in processes without knowledge of their internals."
  • What is not in this paper: the terms "visible revocation" and "abort protocol" do not appear. They come from the 1995 exokernel paper, summarized below as general knowledge.
How it works, step by step: the 1995 protocol (general knowledge, not in this paper)
  1. Visible revocation: when the kernel wants physical pages back, it asks the libOS ("please return 2 pages") instead of silently taking them. The libOS picks the victims (for example clean cache pages it can re-read), writes back anything dirty, removes its own mappings, and returns the pages.
  2. Contrast, invisible revocation: a conventional kernel takes the page, saves it if needed, and the application never knows. The 1995 paper argues visible revocation costs a round trip but lets the application keep the pages it values.
  3. Abort protocol: if the libOS does not comply in time, the kernel takes the resources by force, breaking the secure bindings (removing mappings), and records what it took in a repossession vector the libOS can inspect, so the libOS can repair its own data structures.
  4. On Xok in this paper: the CPU slice end is announced; global LRU information is offered "that applications can use when deallocating resources"; the paper does not describe the memory or disk revocation path further.
Assumptions it relies on
  • A1. The application knows better than the kernel which instance to give up (stated as the motivation).
  • A2. The application can respond quickly (stated as a requirement in Section 9.2, "quickly select and return a page").
  • A3. The kernel can always fall back to forced reclamation (implicit here; explicit in the 1995 abort protocol).
If an assumption changes
  • A1 changes (the kernel knows better, for example global LRU across all programs): the kernel can still advise; Xok "tracks global LRU information that applications can use" (M23).
  • A2 changes (the libOS is itself paged out): the paper's self-paging warning: paging "can be caused by external entities (e.g., the kernel touching a paged-out buffer that a libOS provided)"; a libOS that must page in its own code to answer a revocation request can deadlock without careful design (inference from Section 9.2).
  • A3 changes (no forced path): a malicious libOS could hold resources indefinitely; quotas by "allocation denial" still bound how much it can hold (Section 8).
Design notes and rejected alternatives

The paper states the principle and uses revocation as a lever for global policy, but gives no revocation measurements. When a question asks for "visible revocation" or "abort protocol" details, the honest source is the 1995 paper; this paper's evidence is the CPU interface ("time slices, initiation/termination upcalls, and directed yields has proven its value repeatedly") and the self-paging cost.

Connections

ESX: ballooning is visible revocation retrofitted onto a guest OS that was not designed for it: the hypervisor asks a driver inside the guest to allocate pages, so the guest's own policy chooses victims (inference connecting the two papers). Livelock: end-of-slice upcalls give an application the chance to stop at a clean point, the same concern as bounding interrupt work (inference).

M4 · Expose information, and map kernel data structures read-only

TL;DR
ProblemLibraries managing their own resources need information only the kernel has (free lists, which pages cache which blocks, global usage), and asking by system call is slow and limited to what the kernel designer anticipated.
Mechanism"Exokernels expose all system information and collect data that applications cannot easily derive locally." Xok maps kernel and hardware data structures into libOS address spaces.
Trade-offNo system-call cost and access to unanticipated information, in exchange for exposed structures that are "not a well-defined API".
Breaks whenThe kernel changes a structure's layout, or a structure contains information the reader is not entitled to.
Key points
  • "For example, applications can determine how many hardware network buffers there are or which pages cache file blocks. An exokernel might also record an approximate least-recently-used ordering of all physical pages, something individual applications cannot do without global information."
  • Xok exposes "the capabilities of the hardware (e.g., all MMU protection bits)" and "many kernel data structures (e.g., free lists, inverse page mappings)". The buffer cache registry "is mapped read-only into application space".
  • "The benefits of mapping data structures are two-fold. First, exposed data structures can be accessed without system call overhead. More importantly, however, mapping the data structures directly allows libOSes to make use of information the exokernel did not anticipate exporting." Caveat: "these structures must not contain sensitive information to which the application lacks privileges."
  • "The use of 'wakeup predicates' has forcefully driven home the advantages of exposing kernel data structures. Frequently, we have required unusual information about the system. In all cases, this information was already provided by the kernel data structures."
  • The cost and its precedent: UNIX tools "such as top, gated, lsof, and netstat already make use of private kernel data structures through the kernel memory device /dev/kmem. Administrators have simply learned to reinstall these programs whenever major kernel data structures change."
How it works, step by step: ps on ExOS
  1. The process table is "partitioned across application-reserved memory of Xok's environment structure, which is mapped readable for all processes and writeable for only the environment's owning process."
  2. ps "is implemented by reading all the entries of the process table": ordinary loads from the mapped region, no system call per process.
  3. Updating a parent's or child's entry uses Xok IPC ("ExOS uses Xok's IPC to safely update parent and child process state"), because each process may write only its own entry.
  4. On UNIX the same listing goes through a system call or /dev/kmem, the latter requiring privilege (general knowledge).
Assumptions it relies on
  • A1. Exposed structures hold nothing secret, or secrets are separated out (stated as a requirement).
  • A2. Kernel changes mostly add structures rather than change existing ones (stated as an expectation: "new device drivers or hardware-oriented functionality, which expose new structures rather than modify existing ones").
  • A3. Code that depends on layouts lives in dynamically linked libOSes, not in applications (stated).
  • A4. Readers tolerate seeing a structure mid-update (implicit; read-only mappings give no atomic snapshot).
If an assumption changes
  • A1 changes: a mapped structure leaks, for example, another user's file block numbers; the kernel would need to split it or fall back to filtered system calls (inference).
  • A2 changes (a structure's layout changes): every libOS that reads it must be recompiled; the paper concedes "some aggressive applications may not work across all versions of the exokernel".
  • A3 changes (statically linked applications): each binary carries the old layout and breaks on a kernel update (inference).
  • A4 changes (readers need consistency): a reader needs a version counter or a lock in the structure; the paper does not describe one (inference).
Design notes and rejected alternatives

The alternative is a system call for each query, which is slower and, more importantly, limited to queries the kernel designer anticipated. Section 9.3 adds a related lesson: "Provide space for application data in kernel structures", for example "Xok lets libOSes use the software-only bits of page tables, greatly simplifying the implementation of copy on write."

Connections

Hints: "Keep secrets of the implementation" warns that there is "a tension with the desire not to hide power"; exposing kernel structures chooses power and pays in stability, exactly that tension (connection is this guide's). vLLM: a block table that the scheduler reads directly to know which blocks are resident is the same kind of shared index (loose inference).

M5 · Secure bindings: check once, at bind time

TL;DR
ProblemApplications access resources directly, so a check on every access (every load from a cached page, every block read) would cost a kernel crossing each time.
Mechanism"XN uses secure bindings [11] to move access checks to bind time rather than checking at every access." The permission to read a cached block is checked when its page enters the libFS's page table.
Trade-offSteady-state accesses run at hardware speed; the kernel must keep every binding consistent when ownership or permission changes.
Breaks whenPermissions change after binding, or a resource is reused while an old binding still points at it.
Key points
  • Requirement 1 of XN: "To prevent unauthorized access, every operation on disk data must be guarded. For speed, XN uses secure bindings [11] to move access checks to bind time rather than checking at every access. For example, the permission to read a cached disk block is checked when the page is inserted into the page table of the libFS's environment, rather than on every access."
  • "Access control is performed when a libFS attempts to map a physical page containing a disk block into its address space, rather than when that block is requested from disk. That is, registry entries can be inserted without requiring that the object they describe be in memory."
  • "Xok's protection mechanism guarantees that a process can only access a cache page if it has the same level of access to the corresponding disk block."
  • Downloaded code is a binding mechanism too: packet filters are "downloaded code fragments used by applications to claim incoming network packets. Because they are in the kernel, the kernel can inspect them and verify that they do not steal packets intended for other applications."
  • This paper uses the term only for XN and cites [11] for its definition. The 1995 paper's three implementation techniques (hardware mechanisms such as TLB entries, software caching of bindings, and downloaded code such as packet filters) are general knowledge, not in this paper.
How it works, step by step: C-FFS maps a cached inode block
  1. Registry lookup: C-FFS sees in the read-only registry that block 812 is cached in physical page 7,000 (illustrative numbers).
  2. Bind request: C-FFS asks Xok to map page 7,000 into its address space, read-only, presenting its capabilities (all Xok calls carry "explicit credentials").
  3. The check: XN confirms that the caller has read access to block 812 (via the parent metadata and its acl-uf, M11) and, because 812 holds metadata, refuses write mode: "XN specifically disallows metadata blocks from being mapped read/write."
  4. The binding: Xok writes the PTE. Every later read of the inode is a load through the TLB.
  5. Changes to the inode still go through XN calls carrying the proposed bytes, so they are checked each time; only reads are bound.
Assumptions it relies on
  • A1. Bindings are long-lived relative to accesses (implicit; the whole benefit).
  • A2. Hardware can enforce the bound right (stated for pages: the x86 PTE permission bits).
  • A3. The kernel can find and remove every binding of a resource when it changes hands (implicit; Xok exposes "inverse page mappings", which is the data structure that makes this possible, inference).
If an assumption changes
  • A1 changes (a binding used once): the check costs as much as a per-access check; nothing is gained but nothing much is lost (inference).
  • A2 changes (protection finer than a page): hardware cannot enforce it, so the resource needs a software region, where every access is a system call (M8).
  • A3 changes (bindings cannot be found): a page freed by one owner and reused by another could still be mapped by the first: a protection hole. The predicate rule above shows Xok delays freeing a page while a binding to it exists.
Design notes and rejected alternatives

The disk-level alternative, a capability stored with every block, was rejected because a separate table "can require two disk accesses" and co-locating it "would prevent blocks from being multiples of the page size" (M10). Binding at map time lets XN check against the libFS's own metadata, once.

Connections

x86 VMM (hwsw): shadow page tables are secure bindings built by the VMM: the guest's mapping is checked when the shadow entry is created, then used by hardware (inference). Dune: uses the extended page tables so a process can write its own page tables safely, because the EPT "exposes only the normal process address space": the binding is checked by a second level of hardware translation instead of at PTE write time (connection is this guide's; quote from the Dune paper). NFS and Leases: a lease is a time-limited binding: checked once, trusted until it expires (inference).

M6 · Library operating systems, and ExOS's shared-library scheme

TL;DR
ProblemMost programs want ordinary UNIX abstractions, but those abstractions must not be fixed in privileged code, and carrying a whole OS in every binary would waste memory and slow process creation.
MechanismExOS implements 4.4BSD abstractions as an unprivileged library; it is linked at a reserved address in every application and shared through one on-disk file.
Trade-offAny function can be overridden by the application and OS development drops the reboot ("the 'reboot' is replaced by 'relink'"); in exchange each libOS must protect the invariants of state it shares, and the shared-library scheme is "simple but primitive".
Breaks whenA program depends on cross-process OS state that a library cannot protect by itself (the file descriptor table, sockets, the mount table in this version).
Key points
  • "we expect most programs to be linked with libraries that hide low-level resources behind traditional operating system abstractions. However, unlike traditional implementations of these abstractions, library implementations are unprivileged and can therefore be modified or replaced at will."
  • "LibOSes also allow incremental, selective adoption of new OS features: applications link with the libOSes that provide what they need; new OS functionality is effectively distributed with the application binary." (dash in the original replaced by a semicolon)
  • ExOS "supports most of the abstractions found in 4.4BSD", runs "all of the applications that are needed to build the complete system (kernel, ExOS, and applications) on itself", "most shells, file utilities (wc, grep, ls, vi, etc.), and many networking applications (telnetd, ftp, etc.)". Missing: "full paging, process swapping, process groups, and a windowing system".
  • "To allow applications to override any implementation feature, we made the system entirely library based, rather than place objects such as process tables in non-customizable servers."
  • Shared libraries: "ExOS is linked as a stand-alone executable with its base address starting at a reserved section of the application's address space. Its exported symbols are then extracted and stored in an assembly file. To resolve calls to library routines, the application links against this assembly file. During process creation the application is loaded and ExOS maps the library at its indicated address." Result: multiple applications "share the same on-disk copy and, more importantly, any cached disk blocks from this file", executables are "roughly that of normal UNIX applications" in size, and "procedure calls are no more expensive than for normal code since they do not require the use of a relocation table."
  • Development: "the 'reboot' is replaced by 'relink'"; the conclusion adds that one libOS can "be developed and debugged from another one running on the same machine."
How it works, step by step: read(fd, buf, 4096) in an unmodified program
  1. The call is an ordinary procedure call into ExOS at its fixed address, resolved at link time through the extracted symbol file. No trap.
  2. ExOS looks up fd in the global file descriptor table (in shared memory in this version) and calls the entry's read method through its function-pointer table.
  3. C-FFS translates the file offset to a block number using its own metadata and looks in the registry. If the block is cached in a page this process may read and already has mapped, the data is copied with no kernel involvement.
  4. If not cached, C-FFS asks XN to install a registry entry (checked with owns-udf, M14) and start the read; it can then sleep on a wakeup predicate until the entry changes from "in transit" to "resident", which is the paper's own predicate example (M17).
  5. Total kernel crossings for a cached hit: zero after the page is bound, against at least one trap for every read() in a monolithic kernel (inference from the mechanism).
Assumptions it relies on
  • A1. The libOS can trust the application it is linked with: "Library implementations of abstractions have the advantage that they can trust the applications they link with and need not defend against malicious use." (stated)
  • A2. Errors stay local: "on an exokernel, if an application passes the wrong arguments to a libOS, only the application will be affected." (stated)
  • A3. The reserved address range is free in every application (implicit in the fixed-address scheme).
  • A4. Most libOS state is private to one process; the part that is shared can be protected (stated as a plan: "we partitioned most of the UNIX kernel state and made it private to each process. The remainder is shared.").
If an assumption changes
  • A1 changes (a malicious application corrupts its own libOS): harmless to others by design, as long as nothing shared is writable; it is exactly the unprotected shared tables (fd table, mount table) that break this (M19).
  • A2 changes (a libOS bug corrupts shared state): every process sharing that state is affected; this is why the paper inserted system calls before shared writes when measuring (M19).
  • A3 changes (an application needs that address range): it cannot be linked with this ExOS build without relinking ExOS at another base (inference).
  • A4 changes (more shared state): more abstractions need kernel support of the XN kind, which the paper found hard to design.
Design notes and rejected alternatives

Servers holding the process table were rejected as "non-customizable". Traditional dynamic linking was not used; the fixed-address scheme avoids relocation tables. The paper's footing for "libraries are simpler than kernels" is the edit-compile-debug cycle and isolation, noting that "Untrusted user-level servers in microkernel-based systems also have this benefit."

Connections

Dune: libDune is also a library that a process links to use privileged hardware, but it runs on an unmodified Linux kernel, which keeps all its abstractions (general knowledge of Dune's structure; inference). NFS: ExOS's NFS client is "library based" too, and shares blocks through the same registry.

M7 · Kernel software abstractions, and hierarchically named capabilities

TL;DR
ProblemMany resources a UNIX system protects are high-level ("Files, for instance, consist of metadata, disk blocks, and buffer cache pages, all of which are guarded by access control on high-level file objects"); hardware alone cannot express those rules.
MechanismThree techniques: one access-control scheme for all resources; kernel "software abstractions to bind hardware resources together" (the registry); and downloaded code "for abstractions whose protection does not map to hardware abstractions".
Trade-offUNIX-level protection without fixing an implementation, as long as the abstraction neither hinders low-level access nor "unduly restrict[s] the semantics" of what it protects.
Breaks whenAn abstraction must impose a policy to protect (for example a specific on-disk format), which would violate the principles.
Key points
  • "One of the main challenges in designing exokernels is to find kernel interfaces that allow such higher-level access control without either mandating a particular implementation or hindering application control of hardware resources."
  • "Xok meets this challenge with three design techniques. First, it performs access control on all resources in the same manner. Second, Xok provides software abstractions to bind hardware resources together. ... Third, and most general, some of Xok's abstractions allow applications to download code. This is required for abstractions whose protection does not map to hardware abstractions. For example, files may require valid updates to their modification times."
  • "The key to these exokernel software abstractions is that they neither hinder low-level access to hardware resources nor unduly restrict the semantics of the protected abstractions they enable. Given these properties, a kernel software abstraction does not violate the exokernel principles."
  • Placement: they "could also be implemented in trusted user-level servers. This microkernel organization would cost many additional context switches; these are particularly expensive on the Intel Pentium Pro processors on which Xok runs."
  • Capabilities: "Unlike Aegis, Xok performs access control through hierarchically-named capabilities [31]; despite the name, these capabilities more closely resemble a generalized form of UNIX user and group ID than traditional capabilities [9]. All Xok calls require explicit credentials."
  • In Section 3.3: the exokernel "allows on-the-fly creation of hierarchically-named capabilities and requires that these capabilities be specified explicitly on each system call. Thus, a buggy child process accidentally requesting write access to a page or software region of its parent will likely provide the wrong capability and be denied permission."
How it works, step by step: a buggy child after fork (illustrative naming)
  1. Before fork, the parent's pages and its pipe's software region are guarded by the parent's capability, call it u100/p1 (the naming scheme here is invented for illustration; the paper does not describe its syntax).
  2. At fork, ExOS creates a new capability for the child on the fly, u100/p1/c1, and the child's own pages are guarded by it.
  3. The child, through a bug, issues a system call to write a page that belongs to the parent. Because every call names its credential explicitly, it passes u100/p1/c1, which does not authorize the parent's page. Xok refuses.
  4. Contrast with UNIX, where authority is ambient: any process with the same user ID may ptrace another and write its memory (the paper's own example of mutual trust, M9).
  5. C-FFS uses the same scheme for files: it "maps the UNIX representation and semantics of access control (uids and gids, etc.) to those of exokernel capabilities" (M15).
Assumptions it relies on
  • A1. Bugs, not attacks, are the common threat between related processes (stated: "a buggy child process accidentally requesting").
  • A2. A small set of kernel abstractions (registry, XN, predicates) covers what cannot be checked in hardware (stated as experience, with future work on "lightweight protected methods like UDFs").
  • A3. Context switches to user-level servers are expensive (stated for the Pentium Pro).
If an assumption changes
  • A1 changes (a malicious child): explicit credentials still stop it from using authority it does not hold; "likely provide the wrong capability" becomes "cannot provide", since it never received the parent's capability (inference; the paper does not describe capability transfer).
  • A2 changes (each new shared abstraction needs a new kernel abstraction): the kernel grows, which is what the principles try to avoid; the paper's response is downloadable checks instead of new kernel code.
  • A3 changes (cheap context switches): the same abstractions could run as trusted user-level servers with little cost, which the paper itself allows.
Design notes and rejected alternatives

The authors say their capabilities are closer to generalized UNIX user and group IDs than to traditional capabilities, and that they "hope to demonstrate" in future work that this scheme simplifies secure applications; the paper does not evaluate it.

Connections

Salus: also shrinks what must be trusted, by checking an untrusted component's results instead of trusting its code (inference). Hints: "Use procedure arguments to provide flexibility in an interface. They can be restricted or encoded in various ways if necessary for protection or portability"; downloaded code is that hint applied across a protection boundary (connection is this guide's).

M8 · Software regions and robust critical sections: keeping shared invariants without trusting the sharer

TL;DR
ProblemA libOS that shares state with others (a pipe buffer, a table) must keep its invariants even if another sharer is buggy or crashes mid-update; page protection is too coarse, and locks require trusting whoever holds them.
MechanismFour kernel mechanisms: software regions (memory readable and writable only by system call), hierarchically named capabilities (M7), wakeup predicates (M17), and robust critical sections implemented "by disabling software interrupts".
Trade-offSub-page protection and no need to trust lock holders, in exchange for a system call per access to a software region.
Breaks whenShared state is accessed very frequently (every access is a crossing), or truly concurrent sharers on several processors need mutual exclusion (inference).
Key points
  • "The exokernel provides four mechanisms libOSes can use to maintain invariants in shared abstractions. First, software regions, areas of memory that can only be read or written through system calls, provide sub-page protection and fault isolation." The other three: capabilities, wakeup predicates ("can ensure that a buggy or crashed process will not hang a correctly behaved one"), and "robust critical sections: inexpensive critical sections that are implemented by disabling software interrupts. Using critical sections instead of locks eliminates the need to trust other processes."
  • Section 9.3: "ExOS implements such critical sections by disabling software interrupts (e.g., time slice termination upcalls). Using critical sections instead of locks removes the need to communicate to manage a lock, to trust software to acquire and release locks correctly, and to use complex algorithms to reclaim a lock when a process dies while still holding it." It is also "the basis of Fugu's fast message passing".
  • Pipes use them: "Pipes are implemented using Xok's software regions, coupled with a 'directed yield' to the other party when it is required to do work (i.e., if the queue is full or empty)."
  • Measured cost (Table 2, M19): the 1-byte pipe latency is 13 µs in plain shared memory and 30 µs with software regions and a wakeup predicate on every read, against 34 µs on OpenBSD.
  • Plans: "Using software regions, we plan to make this shared state fully protected in the near future" (process map, file descriptor table, sockets, terminals (TTYs), mount table, System V shared memory table).
How it works, step by step: appending to a shared pipe queue
  1. Enter a robust critical section: the writer disables its software interrupts, so its time slice will not end (with its upcall) in the middle of the update. Nothing is communicated to the reader.
  2. Write through the region: the writer issues a system call that copies its bytes into the software region holding the queue and updates the tail index. Xok checks the writer's capability and the bounds; a stray store from either process cannot reach the region by ordinary memory access.
  3. Leave the section and, if the queue was empty, perform a directed yield to the reader.
  4. If the writer crashes between steps, no lock is left held; the reader's wakeup predicate (queue not empty, or a clock bound) keeps it from hanging forever.
  5. Why disabling interrupts suffices here (inference): on a uniprocessor, the only way another process can run in the middle of the update is a preemption, which is exactly the upcall being disabled. The paper cites Bershad et al.'s fast mutual exclusion for uniprocessors [3]. Whether the kernel bounds how long a section may run is not stated.
Assumptions it relies on
  • A1. One processor: preemption is the only source of interleaving (implicit; the paper's lessons note the same approach on Fugu, a multiprocessor, for message passing, without details).
  • A2. Critical sections are short (implicit).
  • A3. Shared-region accesses are infrequent enough that a system call per access is acceptable (implicit; Table 2 is the evidence).
If an assumption changes
  • A1 changes (two processors run writer and reader simultaneously): disabling one CPU's software interrupts does not stop the other CPU; the region's system calls would need to serialize in the kernel (inference).
  • A2 changes (a long or looping section): the process delays its own preemption; unless the kernel enforces a bound, it could monopolize the CPU (inference; the paper does not discuss this).
  • A3 changes (hot shared state): the crossing per access dominates; the 1-byte pipe already pays 30 µs versus 13 µs unprotected.
Design notes and rejected alternatives

Locks were rejected for shared libOS state because of trust and dead-holder recovery. Page protection was rejected as too coarse ("sub-page protection"). The paper calls its own pipe test "gratuitous use of Xok's protection mechanisms" because the predicate on every read is "unnecessary even with mutual distrust".

Connections

Mesa: monitors assume trusted code that always releases the lock; robust critical sections avoid holding anything another process must wait on (inference). Eraser: detects lock-discipline bugs among trusted threads; here the concern is a sharer in another protection domain (inference). Livelock: disabling software interrupts to protect a short update is the same tool kernels use for interrupt handlers (inference).

M9 · Three levels of trust

TL;DR
ProblemA libOS "cannot necessarily trust all other libOSes with access to a particular resource", but defending against everyone everywhere would make common cases slow and code complex.
MechanismMatch the implementation to the trust relationship: mutual trust (code like a monolithic kernel), unidirectional trust (slight modifications), mutual distrust (defensive implementations or kernel help).
Trade-offCheap code in the common cases; careful kernel abstractions only where mutual distrust is real (disk files).
Breaks whenThe trust relationship is misjudged, for example a child that drops privileges is treated as mutually trusted.
Key points
  • "When libOSes guarantee invariants about their abstractions, they must be aware of exactly which resources are involved, what other processes have access to those resources, and what level of trust they place in those other processes."
  • Mutual trust: "any two UNIX programs run by the same user can arbitrarily modify each others' memory through the debugger system call, ptrace. ... This reduces the problem of guaranteeing invariants from one of security to one of fault-isolation, and consequently allows libOS code to resemble that of monolithic kernels implementing the same abstraction."
  • Unidirectional trust: "a privileged process accepts network connections, forks, and then drops privileges ... In the example of copy-on-write, for instance, the trusted parent process must retain exclusive control of shared pages and its own page tables, preventing a child from child making [sic] copied pages writable in the parent. While this requires more page faults in the parent, it does not increase the number of page copies or seriously complicate the code."
  • Mutual distrust: libOSes "must include defensive implementations that give reasonable interpretations to all possible actions by the foreign process (for instance a socket write larger than the buffer can be interpreted as an end of file)."
  • "Fortunately, sharing with mutual distrust occurs very infrequently for many abstractions. Many types of sharing occur only between child and parent processes ... In the remaining cases, as is the case for disk files, we have carefully crafted kernel software abstractions to help libOSes maintain the necessary invariants."
How it works, step by step: copy-on-write under each trust level
  1. Setup: a parent with 400 data pages forks (illustrative). ExOS marks the shared pages copy-on-write in both page tables (M19).
  2. Mutual trust (same user, both keep privileges): either process may update shared page-table state for the pair; when one writes a page, it copies the page and remaps its own copy. Code resembles a kernel's copy-on-write.
  3. Unidirectional trust (child dropped privileges): the parent keeps "exclusive control of shared pages and its own page tables". If the child could change the parent's page tables, it could make a shared page writable in the parent and then modify data the parent relies on. So the parent handles its own faults and the child handles only its own; the parent takes more page faults (it cannot rely on the child to fix up its mappings), but the number of page copies is unchanged.
  4. Mutual distrust (unrelated processes): they do not share pages copy-on-write at all; sharing happens through abstractions such as sockets with defensive interpretations, or through XN for files.
Assumptions it relies on
  • A1. Trust relationships are known when sharing is set up (stated: libOSes "must be aware").
  • A2. Mutual distrust is rare and off the critical path (stated).
  • A3. A defensive "reasonable interpretation" exists for every foreign action (stated as a requirement).
If an assumption changes
  • A1 changes (privileges dropped after sharing began): pages shared under mutual trust are now shared with a less trusted process; the parent must re-take control of its page tables at the moment privileges drop (inference).
  • A2 changes (a server shares heavily with untrusted clients): defensive checks land on the critical path, and more abstractions need XN-style kernel support (inference).
  • A3 changes (no reasonable interpretation exists): the abstraction cannot be shared safely by libraries alone and needs the kernel, which is how the authors treated disk files.
Design notes and rejected alternatives

The levels are a design guide, not a kernel mechanism; the kernel supports them with the four mechanisms of M8. The rejected alternative is a single fully defensive implementation for every abstraction, which would pay distrust costs in the common parent-child case.

Connections

Dune: its sandbox runs untrusted code inside a process that the Dune-using parent controls fully, a unidirectional-trust arrangement enforced with hardware privilege rings (inference). Salus: mutual distrust between clients and storage servers is handled by end-to-end checks rather than defensive interpretations (inference).

M10 · Why the disk is the hard case: XN's requirements and its four designs

TL;DR
Problem"The most difficult requirement for XN is efficiently determining the access rights of a given principal to a given disk block", when "files have application-defined metadata layouts". Partitioning is no answer: "each file would require its own partition."
MechanismAfter per-block capabilities, self-descriptive metadata and declarative templates, XN uses templates whose description is code: untrusted deterministic functions (UDFs) that translate each metadata type into a form the kernel understands.
Trade-offAny metadata layout can be protected, at the cost of running interpreted functions on metadata operations and of an interface the authors needed four tries to get right.
Breaks whenOwnership cannot be computed from one metadata block alone, or the function language cannot express a format (the declarative version's failure).
Key points
  • "Designing a flexible exokernel stable storage system has proven difficult: XN is our fourth design."
  • Four requirements: new file formats "simple and lightweight", requiring no special privilege; libFSes can "safely share files at the raw disk block and metadata level"; efficiency "as close to raw hardware performance as possible"; and cache sharing with easy handling of "cache coherence, security, and concurrency".
  • "XN must prevent a malicious user from claiming another user's disk blocks as part of her own files. On a conventional OS, this task is easy, since the kernel itself knows the file's metadata format."
  • "UDFs allow the kernel to safely and efficiently handle any metadata layout without understanding the layout itself."
How it works, step by step: the four designs
DesignIdeaWhy it was dropped (paper's words)
1a. Capability per block, stored separatelya table maps each block or extent to a capability or an access control list (ACL)"accessing a block can require two disk accesses (one to fetch the capability and one to fetch the block)"; caching helps, but "we are nervous about its overhead on disk-intensive workloads"
1b. Capability stored before each blockco-locate the capability "immediately before a disk block's data""reserving space for a capability would prevent blocks from being multiples of the page size, adding overhead and complexity to disk operations"
2. Self-descriptive metadataeach metadata instance says, e.g., "the next ten integers are disk block pointers""unacceptable amounts of space overhead" and "excessive effort to modify existing file system code"
3. Templates in a declarative languagedescribe each type once per file system, not once per instance"the system made too many tradeoffs": which base types, pointer sizes, how layout changes, how extents are specified; "it seems unlikely that any fixed set of components will ever be enough"
4. Templates with UDFs (XN)each type's description is a function in "a more expressive, interpreted language"current design: "XN merely verifies that libFSes track block ownership correctly"
  1. Why 1a costs a second access: an inode read on a cold cache reads the block, then the table block holding its capability, unless cached (inference from the quote).
  2. Why 1b breaks page alignment: with 4 KB blocks and, say, a 16-byte capability prefix, a block occupies 4,112 bytes and no longer fits a page or a power-of-two disk sector run (illustrative sizes; general knowledge that sectors and pages are powers of two).
  3. Insight for 3 and 4: "each file system is built from only a handful of different on-disk data structures, each of which can be considered a type", so describing types costs little.
  4. Lesson the authors draw from 3: making too many trade-offs is "an indication that applications do not have enough control", which is the exokernel argument applied to XN's own interface.
Assumptions it relies on
  • A1. A file system has few metadata types (stated).
  • A2. Ownership is a tree: every block is owned through pointers from metadata reachable from a registered root (stated in the root catalogue design, M14).
  • A3. Disk-intensive workloads cannot afford an extra access per block (stated as the authors' worry).
If an assumption changes
  • A1 changes (hundreds of types): still workable, since each type is one template installed once; only installation effort grows (inference).
  • A2 changes (shared blocks with several owners, such as copy-on-write snapshots or deduplication): a block reachable from two trees has two parents; XN's reference counts on pointers (M12) suggest this can be expressed, but the paper does not discuss multi-owner blocks (inference).
  • A3 changes (a large in-memory capability cache): design 1a's second access disappears for hot blocks, but formats would still need per-block capability updates on every allocation (inference).
Design notes and rejected alternatives

The rejected designs are listed above. The paper's Section 9.2 generalizes the experience: "Most of our major exokernel interfaces have gone through multiple designs over several years." Future work tests whether XN is "powerful enough to support concurrent use by radically different file systems" (log-structured file systems, RAID (redundant arrays of disks), memory-based file systems).

Connections

LFS and F2FS: both are listed (LFS by name, F2FS by kind) among file systems whose formats XN would need to describe; LFS's inode map and F2FS's node address table are extra indirection layers that a UDF would have to walk (inference). FFS: its cylinder-group bitmaps and fixed inode tables are exactly a "handful" of types: superblock, cylinder group block, inode block, indirect block, directory block, data block (inference).

M11 · Templates and UDFs: owns-udf, acl-uf, size-uf, and the allocation check

TL;DR
ProblemXN must verify that a libFS's change to its own metadata "actually does what it says it does", for example allocates block b and nothing else, without understanding the format.
MechanismEach metadata type T has a template with owns-udfT (deterministic: which blocks, of which types, does this metadata point to), acl-ufT (may these credentials make this change) and size-ufT (size in bytes). XN runs owns-udf before and after the proposed change and compares.
Trade-offExact ownership enforcement for any layout; the libFS cannot write its own metadata directly and each change runs interpreted code.
Breaks whenA function's answer could change for the same input (prevented by the determinism check), or a template must evolve (forbidden: "Once a template is specified, it cannot be changed").
Key points
  • "UDFs are stored on disk in structures called templates. Each template corresponds to a particular metadata format; for example, a UNIX file system would have templates for data blocks, inode blocks, inodes, indirect blocks, etc. Each template T has one UDF: owns-udfT, and two untrusted but potentially nondeterministic functions: acl-ufT and size-ufT."
  • "The limited language used to write these functions is a pseudo-RISC assembly language, checked by the kernel to ensure determinacy." The two non-UDF functions "can have access to, for example, the time of day."
  • "owns-udfT(m) returns the set of blocks which m points to and their respective template types. UDF determinism guarantees that owns-udf will always compute the same output for a given input: XN cannot be spoofed by owns-udf."
  • "Each tuple constitutes a range: a block address that specifies the start of the range, the number of blocks in the range, and the template identifier for the blocks in the range. Because owned sets can be large, XN allows libFSes to partition metadata blocks into disjoint pieces such that each set returned is (typically) a single tuple."
  • The check: "XN runs owns-udfT(m); makes the proposed modification on m′, a copy of m; and runs owns-udfT(m′). It then verifies that the new result is equal the old result plus b."
  • "XN runs the proper acl-uf function before any metadata modification. acl-ufs can implement access control lists, as well as providing certain other guarantees; for example, an acl-uf could ensure that inode modification times are kept current by rejecting any metadata changes that do not update them." "The size-uf function simply returns the size of a data structure in bytes."
How it works, step by step: the honest and the cheating request
  1. Request: the libFS calls XN with metadata block m, block b = 57, and "the proposed modification to m (specified as a list of bytes to write into m)".
  2. Free check: XN "checks that the requested blocks are free".
  3. Permission: XN runs acl-ufT(m, modification, credentials); for C-FFS this enforces UNIX permissions (M15).
  4. Ownership: owns-udf(m) = {(10, 2, data)}; apply bytes to copy m′; owns-udf(m′) = {(10, 2, data), (57, 1, data)}; equal to old plus 57, so the change is applied to m, 57 leaves the free map, and if 57 is a metadata block it is marked tainted (M12).
  5. Cheating: the same call with bytes that write 90 gives {(10, 2, data), (90, 1, data)}; not old plus 57; rejected. Writing 57 and also overwriting 11 with 90 gives {(10, 1, data), (57, 1, data), (90, 1, data)}; rejected for the same reason. Only the exact requested difference passes.
  6. Tuple count: if the inode's blocks were 10, 11, 57, a later allocation of 58 extends the second range, (57, 2, data). Scattered blocks need one tuple each, which is why the paper lets libFSes partition metadata so that each piece returns "(typically) a single tuple" (this guide's reading).
Assumptions it relies on
  • A1. Ownership of children can be computed from the parent block alone (stated: owns-udf's input is m).
  • A2. Determinism can be checked mechanically in the restricted language (stated).
  • A3. Formats are fixed for the life of the file system type (stated: templates cannot be changed).
  • A4. Running the interpreted functions twice per change is cheap relative to disk I/O (implicit; the paper gives no separate UDF timing, only the overall 41.1 s versus 39.7 s with and without XN and checks).
If an assumption changes
  • A1 changes (a format where a pointer's meaning depends on another block, such as LFS's inode map giving inode locations): owns-udf of an inode-map block must list the inode blocks it points to, which works; but anything depending on two blocks at once cannot be expressed (inference).
  • A2 changes (nondeterministic owns-udf): a function that read the clock could report 57 at check time and 90 later; XN would be spoofed. This is why only owns-udf must be deterministic.
  • A3 changes (a format upgrade): the libFS must install a new template under a new name and convert data into it (inference).
  • A4 changes (metadata-heavy workloads such as creating thousands of small files): every creation runs UDFs several times; the paper's 300,000 versus 81,000 system calls suggest XN calls are numerous, yet the total time difference was 1.4 s (M19).
Design notes and rejected alternatives

The functions are described in "a more expressive, interpreted language" than the declarative templates they replaced. The paper's Section 9.3 explains why downloaded code is trusted: "since the kernel can ensure that UDFs are deterministic and do not change, it can trust their output without having to understand what they do." The benefit "is not execution speed, but rather trust and consequently power".

Connections

Hints: "Use procedure arguments": Lampson's Spy example installs untrusted patches that are checked to contain "no loops" and to store only into a designated region; UDFs and wakeup predicates are restricted procedures of the same kind (connection is this guide's). Salus: verifying an untrusted party's state change by recomputing a property over before and after states (inference).

M12 · Ordered disk writes: deferred frees and tainted blocks

TL;DR
ProblemA crash must not "incorrectly grant a libFS access to data it either has freed or has not allocated", but forcing synchronous writes to guarantee order is slow, and libFSes should choose their own order.
MechanismXN enforces Ganger and Patt's first two rules: freed blocks wait on a "will free" list until no on-disk pointer to them remains; a block that points to an uninitialized or tainted block is "tainted" and cannot be written while reachable from a persistent root.
Trade-offIntegrity across crashes for everyone while each libFS picks any order satisfying the rules; in exchange XN tracks taint and reference counts, and some writes are refused.
Breaks whenA libFS never writes the parent that would release a freed block, or needs the third rule (moves), which XN leaves to the libFS.
Key points
  • The rules: "First, never reuse an on-disk resource before nullifying all previous pointers to it. Second, never create persistent pointers to structures before they are initialized. Third, when moving an on-disk resource, never reset the old pointer in persistent storage before the new one has been set."
  • "The first two rules are required for global system integrity (and thus must be enforced by XN) while a file system violating the third rule will only affect itself." (dashes in the original replaced by parentheses)
  • "a naive implementation will incur frequent costly synchronous disk writes. XN allows libFSes to address this by enforcing the rules without legislating how to follow them. In particular, libFSes can choose any operation order which satisfies the constraints."
  • Rule 1: "implemented by deferring a block's deallocation until all on-disk pointers to that block have been deleted; a reference count performed at crash recovery time helps libFSes implement the third rule." Deallocation: "If there are no on-disk pointers to a deallocated disk block, XN places it on the free list. Otherwise, XN enqueues the block on a 'will free' list until the block's reference count is zero. Reference counts are decremented when a parent that had an on-disk pointer to the block deletes that pointer via a write."
  • Rule 2: "XN keeps track of tainted blocks. Any block is considered tainted if it points either to an uninitialized block or to a tainted block. LibFSes must not be allowed to write a tainted block to disk."
  • Exceptions: whole file systems marked "temporary" ("they are not required to adhere to any of the integrity rules. This technique allows memory-based file systems to be implemented with no loss of efficiency."), and "unattached subtrees", where "XN does not track tainted blocks in an unreachable tree until it is connected to a persistent root."
  • On write: "The write also fails if any of the blocks are tainted and reachable from a persistent root. ... If the block was previously tainted and now is not (either by eliminating pointers to uninitialized metadata or by becoming initialized itself), XN modifies its state and removes it from the tainted list."
How it works, step by step: deleting a file and reusing its block
  1. State on disk: inode I (on disk) points to data block 42. The libFS deletes the file.
  2. Deallocate 42: XN checks the deallocation with UDFs "analogously to allocate operations". There is still an on-disk pointer (I on disk still lists 42), so 42 goes on the "will free" list, not the free list.
  3. Try to reuse 42 for another user's new file: not possible, because 42 is not in the free map. Without this rule, a crash after the other user's data reached 42 but before I's change reached disk would leave the old file's inode pointing at the new user's data.
  4. Write I (now without the pointer). The write decrements 42's reference count to zero, and XN moves 42 to the free list.
  5. Rule 3 is the libFS's business: moving a block (allocate new, copy, point to new, then free old) in the wrong order risks only that libFS's own file; XN's crash-time reference count helps it repair.
Assumptions it relies on
  • A1. Every persistent block is reachable from a registered root (stated: "After a crash, XN uses these roots to garbage-collect the disk").
  • A2. XN can see every on-disk pointer, through owns-udf (stated).
  • A3. The disk writes each block atomically (implicit; general knowledge that ordering arguments assume block-atomic writes).
  • A4. LibFSes eventually write parents that drop pointers (implicit; otherwise "will free" blocks stay unusable).
If an assumption changes
  • A1 changes (a libFS forgets to register its root): its tree is "unattached"; XN imposes no ordering on it, and after a crash recovery frees all of its blocks (inference from the root-catalogue rule).
  • A2 changes (a pointer owns-udf does not report): XN neither protects it nor counts it; the target can be freed and reused under it, but the hidden pointer also grants no access (Class Prep C1).
  • A3 changes (torn block writes): a half-written metadata block could contain a mix of old and new pointers; neither rule covers that (inference).
  • A4 changes (a libFS keeps the parent dirty forever, or exits): the block stays on "will free". Because XN lets any process flush "unowned" dirty blocks of exited processes, a daemon can write the parent and release it (M13).
Design notes and rejected alternatives

The rejected alternative is synchronous writes for every metadata update. The crash-recovery traversal can itself be skipped: "If rebuilding the free map after a crash needs to be fast, this step can be eliminated by ordering writes to the free map." Taint tracking is skipped where persistence is absent (temporary file systems, unattached subtrees), so memory file systems pay nothing.

Connections

FFS: FFS met the same rules with synchronous metadata writes in a fixed order and fsck afterward; the LFS paper's complaint about FFS's synchronous inode and directory writes is the cost XN tries to let libFSes avoid (inference connecting the papers). LFS: sidesteps ordering by writing everything in a log and recovering from a checkpoint plus roll-forward; under XN the cleaner's moves fall under Rule 3, which XN leaves to the libFS (Class Prep C8). Rethink the Sync: another way to keep crash guarantees while avoiding synchronous waits (inference).

M13 · The buffer cache registry

TL;DR
Problem"if two applications obliviously cache the same disk block in two different physical pages, then modifications will not be shared", but a kernel-owned buffer cache would take caching policy away from applications.
MechanismAn in-kernel, system-wide table that "only records the mapping, not the disk blocks themselves", plus each entry's state; the data lives in application-managed physical pages; the table is mapped read-only into every application.
Trade-offOne shared copy per block with application-chosen eviction and prefetching, in exchange for access checks at mapping time and entry locking by libFSes.
Breaks whenA process without write access tries to install its own copy of a block (prevented by "read and insert"), or the owner of a dirty page disappears (handled by flushing "unowned" blocks).
Key points
  • "The registry tracks the mapping of cached disk blocks and their metadata to physical pages (and vice versa). ... The registry tracks both the mapping and its state (dirty, out of core, uninitialized, locked). To allow libFSes to see which disk blocks are cached, the buffer cache registry is mapped read-only into application space."
  • "registry entries can be inserted without requiring that the object they describe be in memory. Blocks can also be installed in the registry before their template or parent is known. As a result, libFSes have significant freedom to prefetch."
  • Two ways to install: "an application that has write access to a block can directly install a mapping to it", and others "can indirectly install an entry for it by performing a 'read and insert,' which tells the kernel to read a disk block, associate it with an application-provided physical page, set the protection of that page appropriately, and insert this mapping into the registry. This latter mechanism is used to prevent applications that do not have permission to write a block from modifying it by installing a bogus in-core copy."
  • "XN does not replace physical pages from the registry (except for those freed by applications), allowing applications to determine the most appropriate caching policy. Because applications also manage virtual memory paging, the partitioning of disk cache and virtual memory backing store is under application control." Default: "XN maintains an LRU list of unused but valid buffers. By default, when libOSes need pages and none are free, they recycle the oldest buffer on this LRU list."
  • "XN allows any process to write 'unowned' dirty blocks to disk (i.e., blocks not associated with a running process), even if that process does not have write permission for the dirty blocks." Three benefits: registry contents survive process exit; a libFS "can rely on a daemon of its choice to flush dirty blocks even in difficult situations (e.g., if the application containing the libFS is swapped out)"; and different write-back policies.
  • Concurrency: "libFSes can lock cache registry entries. (Future work will explore optimistic concurrency control based on versioning.)"
How it works, step by step: two compiles share a header file
  1. Process 1 (gcc) opens stdio.h; C-FFS finds its blocks absent from the registry, installs entries (checked by owns-udf from the parent inode), supplies its own pages, and starts the reads.
  2. Process 2 (another gcc) opens the same file a moment later; C-FFS in process 2 sees the entries already present (state "in transit" or "resident") and, after the read completes, maps the same pages read-only. No second disk read, no second copy.
  3. Process 1 exits. Its pages and their registry entries stay: "the contents of the registry can be safely retained across process invocations rather than having to be brought in and paged out on creation and exit."
  4. A third process needs memory and has no free pages: by default it recycles the oldest buffer on XN's LRU list of unused but valid buffers, which may be the header's page if nobody has it mapped.
  5. Contrast with VM-style isolation: under a VMM, two guests would each read and cache the file separately (the paper's point that VMs cannot share abstractions).
Assumptions it relies on
  • A1. Access to a cached page should equal access to the block (stated).
  • A2. LibFSes cooperate on locking registry entries for multi-step updates (stated as the current approach, with optimistic concurrency as future work).
  • A3. Physical pages holding cached blocks belong to someone who will manage them; unowned ones fall back to the LRU list (stated).
  • A4. Exposing which blocks are cached is not a leak (implicit: the registry is mapped read-only to everyone).
If an assumption changes
  • A1 changes (a process should read a cached copy but not the disk block): not expressible; the rule ties the two (inference).
  • A2 changes (a libFS ignores locks): it can still only change metadata through XN calls, which run owns-udf and acl-uf, so the damage is limited to semantics that acl-uf does not check (inference).
  • A3 changes (no daemon ever flushes): dirty unowned blocks stay in memory; data written by an exited process is lost on a crash, as it would be in UNIX before sync (inference).
  • A4 changes (cache contents are sensitive): anyone can see which block numbers are cached, a side channel the paper does not discuss (inference).
Design notes and rejected alternatives

The rejected alternatives are per-application caches (incoherent) and a kernel buffer cache (fixed policy). The registry's choice to record only mappings is what keeps the cache "application-managed". "Since applications control what is fetched and what is paged out when (and in what order), they can control many disk management policies and can enforce strong stability guarantees."

Connections

FFS and NFS: the kernel buffer cache those papers assume is replaced by this registry plus application pages (inference). Superpages and ESX: a global map from physical pages to their uses is what both papers need to make placement or sharing decisions; here it is exposed to applications (inference). Section 8 adds that an exokernel "can unify the many space-partitioned caches in current systems (e.g., the buffer cache, network buffers, etc.)".

M14 · XN's operations, from installing a file system to recovering from a crash

TL;DR
ProblemThe pieces (templates, taint, registry) must fit into ordinary file system operations without forcing a particular order or layout.
MechanismType creation and root registration once; then startup, two-stage reads, speculative raw reads, allocation, writes and deallocation, each checked as in M11 to M13; after a crash, a traversal from the roots rebuilds the free map.
Trade-offLibFSes control prefetching, layout and write order; every block must be reached through a chain of parents already in the registry.
Breaks whenA libFS wants to use a block before its parent is known (it can read it raw, but cannot use it), or recovery time matters on a huge disk.
Key points
  • Type creation: "The libFS describes its types by storing templates ... into a type catalogue. Each template is identified by a unique string (e.g., 'FFS Inode'). Once installed, types are persistent across reboots."
  • LibFS persistence: "a libFS can register the root of its tree in XN's root catalogue. A root entry consists of a disk extent and corresponding template type, identified by a unique string (e.g., 'mylibFS')."
  • Recovery: "After a crash, XN uses these roots to garbage-collect the disk by reconstructing the free map. It does so by logically traversing all roots and all blocks reachable from them: reachable blocks are allocated, non-reachable blocks are not."
  • Read, stage 1: "the libFS creates entries in the registry by passing block addresses for the requested disk blocks and the metadata blocks controlling them (their parents). The parents must already exist in the registry ... XN uses owns-udf to determine if the requested blocks are controlled by the supplied metadata blocks and, if so, installs registry entries." Stage 2: "the libFS initiates a read request, optionally supplying pages to place the data in. Access control through acl-uf is performed at the parent (e.g., if the data loaded is a bare disk block), at the child (e.g., if the data is an inode), or both."
  • Speculative read: "a libFS can issue a raw read command. If the block is not in the registry, it will be marked as 'unknown type' and a disk request initiated. The block cannot be used until after it is bound to a parent by the first stage of the read process."
  • Write: prevented if "the blocks are not in memory, or they have been pinned in memory by some other application"; fails "if any of the blocks are tainted and reachable from a persistent root".
How it works, step by step: reading /a/b on a cold cache
  1. Startup: the libFS "loads its root(s) and any types it needs from the root catalogue into the buffer cache registry. Usually both will already be cached."
  2. Root directory block: stage 1 with parent = root entry; owns-udf(root) must list the directory block; entry installed. Stage 2 reads it; acl-uf checks the caller may read.
  3. Down the path: the libFS parses each directory block itself (XN never reads names) and repeats stage 1 one level at a time: a's inode block with the root directory block as parent, a's directory block with that inode as parent, then b's inode block with a's directory block as parent.
  4. Prefetching: guessing where b's blocks are (for example because its own layout puts a small file's data next to its inode), the libFS issues raw reads for them in parallel; they enter the registry as "unknown type" and cannot be mapped until stage 1 binds them to b's inode.
  5. Use: stage 1 for b's data with the inode as parent turns the raw reads into typed, checked entries; the data are already in memory.
  6. Count: after the root entry, five dependent stage-1 installs (root directory block, a's inode block, a's directory block, b's inode block, b's data blocks), the same chain of pointer dereferences a kernel file system would follow (inference). C-FFS embeds inodes in directory blocks (general knowledge of its own paper), which would merge each inode step into its directory's step.
Assumptions it relies on
  • A1. Every access path starts from a registered root (stated).
  • A2. Recovery by full traversal is acceptable, or the libFS orders free-map writes to avoid it (stated).
  • A3. Parents can be kept in the registry while children are used (stated: "The parents must already exist in the registry").
If an assumption changes
  • A1 changes (blocks reachable only through a structure XN cannot follow, such as a hash index in data blocks): the libFS must model the index as metadata with its own template, or XN will treat the blocks as free after a crash (inference).
  • A2 changes (multi-terabyte disks): traversing every reachable block at boot is slow; the paper's own escape hatch is ordered free-map writes (inference about scale).
  • A3 changes (memory pressure evicts parents): reading a deep block requires reloading the chain of parents first (inference).
Design notes and rejected alternatives

Separating the two read stages lets libFSes issue I/O early and bind it later, which is the "significant freedom to prefetch" the paper claims. Metadata blocks may be read but "XN specifically disallows metadata blocks from being mapped read/write", so all metadata changes go through the checked allocate, modify and deallocate calls.

Connections

FFS: fsck also rebuilds free state by traversing from the root, but with built-in knowledge of the format; XN's traversal uses each libFS's owns-udf (inference). LFS: recovery from a checkpoint avoids a full traversal, the same goal as XN's "ordering writes to the free map" (inference).

M15 · C-FFS on XN: adding UNIX invariants on top

TL;DR
ProblemXN guarantees integrity of ownership and crash order, but "real-world file systems often require other, file-system-specific invariants", for example unique names in a directory, legal directory entries, current modification times.
MechanismC-FFS adds access control (UNIX uids and gids mapped to capabilities), well-formed updates, atomicity (locking), and implicit updates; it "currently downloads methods into the kernel to check its invariants".
Trade-offFull UNIX semantics for mutually distrustful sharers with code that is "mainly ... a small number of if-statements"; the methods are kernel-resident code for one libFS.
Breaks whenAn invariant spans many blocks (name uniqueness scans every directory block), or a second libFS sharing the files does not follow the same rules (the downloaded checks are what force it to).
Key points
  • "C-FFS makes four main additions to XN's protection mechanisms: 1. Access control: it maps the UNIX representation and semantics of access control (uids and gids, etc.) to those of exokernel capabilities. 2. Well-formed updates: C-FFS guarantees UNIX-specific file semantics: for example, that directories contain legal, aligned file names. 3. Atomicity: C-FFS performs locking to ensure that its data is always recoverable and disk writes only occur when metadata is internally consistent. 4. Implicit updates: ... modification times are updated when file data are changed, and ... renaming or deleting a file updates the name cache."
  • "It is not difficult to implement UNIX protection without significantly degrading application power. C-FFS protection is implemented mainly by a small number of if-statements rather than by procedures that limit flexibility. The most intricate operation (ensuring that files in a directory have unique names) is less than 100 lines of code that scans through a linked list of cached directory blocks to ensure name uniqueness." (dashes replaced by parentheses)
  • "We are currently developing a system similar to UDFs that can be used to enforce type-specific invariants in an efficient, extensible way."
  • C-FFS's performance features (embedding inodes in directories and grouping small files) come from the authors' 1997 USENIX paper [15], not from this one (general knowledge of that paper); this paper credits C-FFS for the Section 6 gains: "ExOS's performance improvements are due to its C-FFS file system."
How it works, step by step: two processes create notes in the same directory
  1. Process 1 locks the directory block's registry entry (atomicity), scans the cached directory blocks for notes, finds none.
  2. It proposes adding an entry to the directory block. XN runs C-FFS's downloaded checks: the name is legal and aligned (well-formed), the caller's uid has write permission (access control, through acl-uf and capabilities), and the directory's modification time changes in the same update (implicit update).
  3. Process 2 waits on the lock, then scans and finds notes; its create fails with "file exists".
  4. A malicious libFS sharing the directory that tries to add a second notes directly is stopped by the downloaded uniqueness check, not by politeness (inference from "downloads methods into the kernel to check its invariants").
Assumptions it relies on
  • A1. UNIX invariants are local enough to check cheaply (stated: if-statements, under 100 lines for the hardest).
  • A2. The directory blocks needed for a check are cached (stated: the uniqueness check scans "cached directory blocks").
  • A3. All sharers' changes pass through the same downloaded checks (implicit).
If an assumption changes
  • A1 changes (a global invariant such as a per-user quota across many files): a per-block check cannot see it; it would need state of its own (inference).
  • A2 changes (a huge directory partly on disk): the scan must first load every block of the directory (inference).
  • A3 changes (another libFS uses a different template for the same files): the C-FFS methods would not run on its updates; sharing files with full UNIX semantics requires using C-FFS's types (inference).
Design notes and rejected alternatives

The paper lists the places such a guarantee could live: "in the kernel, in a server, or, in some cases, by simple defensive programming." C-FFS chose downloaded methods. "Our experience with C-FFS shows that, even with the strongest desired guarantees, a protected interface can still provide significant flexibility to unprivileged software."

Connections

FFS: C-FFS is an FFS descendant that keeps FFS's on-disk ideas and changes placement; the OpenBSD/C-FFS comparison isolates the OS structure from this file system difference (M19). NFS: NFS servers face the same question of who enforces unique names across clients and solve it by doing every directory operation at the server (inference).

M16 · Xok's physical memory on the x86: hardware page tables, system-call updates, exposed bits

TL;DR
Problem"Unlike the MIPS architecture, the x86 architecture defines the page-table structure", refills the TLB in hardware, and "does not verify that the physical page of a translation can be mapped by a process".
MechanismApplications may not write page tables directly; they "must instead use system calls", which Xok checks. Xok exposes "all MMU protection bits", free lists and inverse page mappings, and lets libOSes use the software-only PTE bits.
Trade-offLess extensible than Aegis (no custom page-table formats), but simpler libOSes; paging policy remains entirely in the application.
Breaks whenAn operation needs many PTE changes (fork), where per-call overhead accumulates, or environments need to share page tables (not yet supported).
Key points
  • "Since x86 TLB refills are handled in hardware, this structure cannot be overridden by applications. Additionally, since the hardware does not verify that the physical page of a translation can be mapped by a process, applications are prevented from directly modifying the page table and must instead use system calls. Although these restrictions make Xok less extensible than Aegis, they simplify the implementation of libOSes (see Section 9) with only a small reduction in application flexibility."
  • "Xok's low-level interface means that paging is handled by applications. As such, it can be done from disk, across the network, or by data regeneration. Additionally, applications can readily perform per-page transformations such as compression, verification of contents using digital signatures (to allow untrusted nodes in a network to cache pages), or encryption."
  • Lesson: "User-level page tables are complex. If page tables are migrated to user level (as on Aegis), a concerted effort must be made to ensure that the user's TLB refill handler can run in unusual situations. ... User-level page tables made the implementation of libOSes tricky on Aegis; since the x86 has hardware page tables, this issue disappeared on Xok/ExOS."
  • Fork: "ExOS's fork performance suffers because Xok does not yet allow environments to share page tables. Fork takes six milliseconds on ExOS, compared to less than one millisecond on OpenBSD."
How it works, step by step: paging out one page by compressing it (illustrative)
  1. Choose a victim: the libOS reads Xok's exposed structures (free lists, inverse page mappings) and its own access history, and picks heap page 0x0805_3000 in physical page 9,120 (values illustrative).
  2. Transform it: compress the 4 KB into, say, 1.3 KB kept in another page of its own: a per-page transformation the kernel knows nothing about.
  3. Unmap: a system call clears the PTE (several such updates can be batched, as ExOS does for fork). The libOS marks the PTE's software-only bits to say "compressed, slot 17".
  4. Free: the libOS returns physical page 9,120 to Xok.
  5. Fault later: a touch of 0x0805_3000 raises a page fault delivered to the libOS's handler, which allocates a page, decompresses, and asks Xok to map it.
Assumptions it relies on
  • A1. Xok can check a PTE write by knowing who owns the physical page (stated as the reason for system calls).
  • A2. Page-table updates are rare enough, or batched enough, that system calls do not dominate (implicit; fork is the counterexample measured).
  • A3. The libOS's fault handler is always runnable (stated as a difficulty in Section 9.2, self-paging).
If an assumption changes
  • A1 changes (a second hardware level checks mappings, as later nested paging does): applications could write their own tables directly and the system-call path would disappear; this is the route Dune takes with the extended page tables of Intel's virtualization extensions (VT-x) (general knowledge and connection, inference).
  • A2 changes (fork-heavy workloads): six milliseconds per fork; the Modified Andrew Benchmark (MAB) advantage shrinks for exactly this reason (M19).
  • A3 changes (the handler's own code is paged out): the libOS cannot service its own fault; the paper warns that self-paging libOSes need "careful planning".
Design notes and rejected alternatives

Aegis's user-level page tables (possible because MIPS refills the TLB in software) were not carried over. The authors present the x86 restriction as a simplification, not a loss: "only a small reduction in application flexibility". Section 9.2 notes a consequence: on a software-refilled TLB the kernel "can approximate LRU page ordering by tracking the insertion of translations into the TLB", which x86 hardware refill does not report (see Class Prep C6).

Connections

Dune: gives processes direct, hardware-checked access to their own page tables, which Xok could not on 1997 x86 hardware (inference). Superpages: a libOS controlling physical allocation could form superpages itself, but on Xok every mapping change still costs a system call (inference). ESX: the information-loss problem in reverse: ESX cannot see inside guests, Xok cannot always tell what a libOS uses a page for (Section 9.2).

M17 · Wakeup predicates

TL;DR
Problem"Applications often want to sleep until a condition is true. Unfortunately, it may be difficult for an application to express this condition to the kernel", and on an exokernel most conditions concern libOS state the kernel does not interpret.
MechanismApplications "inject" boolean expressions into Xok; they are "evaluated by the kernel when an environment is about to be scheduled. The application is not scheduled if the predicate does not hold."
Trade-offNo address-space switch just to test a condition, and no kernel change for new kinds of waits; predicates must be loop-free and their pages are pinned.
Breaks whenA condition needs iteration over a structure (no loops), or the referenced memory is remapped (Xok keeps the old physical page alive).
Key points
  • "Like dynamic packet filters, Xok compiles predicates on-the-fly to executable code. The significant overhead of an address space context switch is eliminated by evaluating the predicates in the exokernel and pre-translating all predicate virtual addresses to their associated physical addresses."
  • "When a virtual page referenced in a predicate is unmapped, the physical page is not marked as free until a new predicate is downloaded or until the application exits."
  • "the implementation of wakeup predicates is simple (fewer than 200 lines of commented code) because careful language design (no loops and easy to understand operations) allows predicates to be easily controlled."
  • "none of the new uses of wakeup predicates required changes to Xok. For example, to wait for a disk block to be paged in, a wakeup predicate can bind to the block's state and wake up when it changes from 'in transit' to 'resident.' To bound the amount of time a predicate sleeps, it can compare against the system clock. The composition of multiple predicates allows atomic checking of disjoint data structures."
  • Integrity role (Section 3.3): "Wakeup predicates can ensure that a buggy or crashed process will not hang a correctly behaved one."
How it works, step by step
  1. Download: C's libOS passes the predicate to Xok, which checks it (no loops), translates each referenced virtual address (here the registry entry for 913, which is mapped into C) to a physical address, and compiles it.
  2. Pin: the physical pages it reads are kept allocated until a new predicate replaces it or C exits.
  3. Schedule: at each scheduling decision for C, Xok runs the compiled code. False: skip C, no switch into C's address space.
  4. Wake: the disk interrupt updates the registry state; at C's next turn the predicate is true and C runs, finds its block resident, and continues.
  5. Timeout: if the disk never answers, the clock clause makes it true after 50 ms, so a crashed partner cannot hang C.
Assumptions it relies on
  • A1. The condition can be read from memory the kernel can see (stated: Xok's exposed structures have always held the needed information).
  • A2. Evaluation is cheap enough to do at every scheduling decision (stated through the design: compiled code, no loops).
  • A3. A torn read of the watched state is harmless, since the predicate is re-evaluated each time (implicit; "composition of multiple predicates allows atomic checking of disjoint data structures" addresses the multi-structure case).
If an assumption changes
  • A1 changes (the condition depends on another process's private memory): the waiter cannot reference it; that process must publish the state in shared, mapped memory (inference).
  • A2 changes (hundreds of sleeping environments with predicates): each scheduling pass evaluates many predicates; the paper gives no measurements of this (inference).
  • A3 changes: a predicate could see a half-updated pair of fields and wake spuriously; the libOS must re-check after waking, as with condition variables (inference).
Design notes and rejected alternatives

Alternatives are a fixed set of kernel events (which would need kernel changes for each new kind of wait) and polling (an address-space switch each test). The paper reports that predicates "have provided us with a robust wakeup facility" with no kernel changes for new uses. The pinning rule is the secure-binding discipline applied to predicate memory: a translation done once stays valid because the page cannot be reused.

Connections

Mesa: a predicate is the condition of a Mesa WAIT, evaluated by the scheduler instead of by the waiting thread; as with Mesa semantics, a woken process should re-check (inference). Hints: Lampson's Spy patches were checked to contain "no loops" and to be short, the same restrictions (connection is this guide's). Livelock: evaluating cheap checks in the kernel to avoid scheduling work that would immediately stop is a theme of that paper's polling design too (inference).

M18 · CPU and network multiplexing, and what downloaded code is for

TL;DR
ProblemThe CPU and the network must be shared without imposing a thread scheduler or a protocol stack on applications.
MechanismCPU: round-robin time slices "with explicit notification of the beginning and the end", plus upcalls and directed yields. Network: dynamic packet filters, timers, upcalls and packet rings, on which ExOS builds user-level UDP (User Datagram Protocol) and TCP.
Trade-offApplications schedule their own work within a slice and run their own protocols; global CPU policy is simple round robin.
Breaks whenA packet filter would need to be trusted to claim packets fairly (solved by kernel inspection), or downloaded interrupt handlers are expected to speed things up (the paper found they did not matter).
Key points
  • "The CPU is multiplexed by dividing time into round-robin-scheduled slices with explicit notification of the beginning and the end of a time slice. Environments provide the hardware-specific state needed to run a process (e.g., an exception stack) and to respond to any event occurring during process execution (e.g., interrupts and exceptions). The network is multiplexed with dynamic packet filters [10]."
  • "The combination of time slices, initiation/termination upcalls, and directed yields has proven its value repeatedly. ... We have used the primitives for inter-process communication optimization (e.g., two applications communicating through a shared message queue can yield to each other), global gang-scheduling, and robust critical sections."
  • "Inter-machine sockets are implemented through user-level network libraries for UDP and TCP. The network libraries are implemented using Xok's timers, upcalls, and packet rings, which allow protected buffering of received network packets." Local sockets use "a shared buffer".
  • "Downloaded code is powerful. ... The main benefit of downloaded code is not execution speed, but rather trust and consequently power: The kernel can invoke downloaded code in cases where it cannot trust application code." Packet filters: "the kernel can inspect them and verify that they do not steal packets intended for other applications. The alternative, asking each application if it claims a given packet, is clearly unworkable".
  • "Downloaded interrupt handlers are of questionable utility on exokernels. ... On current generation chips, however, the latency of I/O devices is large compared to the overhead of kernel crossings, making the first benefit negligible. The second does not require downloading code, only an upcall mechanism."
  • "Fast applications do not require good microbenchmark performance. ... We heavily tuned Aegis to achieve excellent microbenchmark performance. Xok, on the other hand, is completely untuned. Nevertheless, applications perform well."
How it works, step by step: a packet arrives for Cheetah
  1. Install: Cheetah's TCP library downloads a filter matching "TCP, destination port 80" (illustrative). Xok compiles it and checks it does not overlap other applications' filters (the inspection the paper describes).
  2. Arrival: the network card interrupts; Xok runs the filters over the packet header; Cheetah's matches.
  3. Deliver: the packet goes into Cheetah's packet ring (protected buffering); if Cheetah is not running, it sees the packet at its next slice, or an upcall notifies it.
  4. Protocol: Cheetah's own TCP processes the segment, using its knowledge of HTTP to delay or merge ACKs (M22).
  5. End of slice: Xok notifies Cheetah before taking the CPU, so it can stop at a consistent point; if it is inside a robust critical section, it has disabled that upcall (M8).
Assumptions it relies on
  • A1. Kernel crossings are cheap compared with device latency (stated as the reason downloaded interrupt handlers do not help).
  • A2. Packet ownership can be decided from headers by a checkable filter (stated).
  • A3. Round robin is an acceptable global CPU policy (implicit; Section 8's experiments use it).
If an assumption changes
  • A1 changes (very fast devices, for example microsecond-latency networks): the kernel crossing becomes a large share of per-packet cost, and the first benefit of downloaded handlers returns; the paper itself says they are more useful where crossings are expensive (inference about later hardware).
  • A2 changes (ownership needs payload inspection or connection state): filters grow complex and harder to verify (inference).
  • A3 changes (latency-sensitive mixes): Figure 4's minimum latencies are the only evidence; no priorities are evaluated (inference).
Design notes and rejected alternatives

Aegis's heavy use of downloaded interrupt handlers (application-specific handlers, ASHs, citing Wallach et al.) is the rejected path; the authors keep upcalls and drop the downloading. The broader rejected alternative for networking is a kernel TCP stack; user-level stacks are cited as related work (U-Net and others).

Connections

Livelock: a user-level protocol stack fed from the kernel by filters moves receive processing out of interrupt context, which is one of the remedies that paper explores in its own setting (inference). Hints: "Leave it to the client. As long as it is cheap to pass control back and forth, an interface can combine simplicity, flexibility and high performance": the upcall-based CPU interface depends on exactly that condition (connection is this guide's).

M19 · ExOS's UNIX abstractions, and what their protection costs

TL;DR
ProblemUNIX semantics (fork, pipes, signals, shared file descriptors, a process table) must be built from user-level code with only part of the state shared and protected.
MechanismMost state is private per process; critical shared state is protected with Xok mechanisms; the rest (process map, fd table, sockets, TTYs, mount table, System V shared memory) is plain shared memory, and its protection cost is approximated by three inserted system calls before every write.
Trade-offComparable speed to OpenBSD with UNIX semantics for cooperating programs, at the cost of incomplete protection in this prototype and a slow fork.
Breaks whenA malicious process writes the shared fd table or mount table directly (possible in this version), or a workload is fork-bound (6 ms per fork).
Key points
  • "Most critical shared state (inode table, file system metadata, page tables, buffer cache, process table, and pipes), is protected using Xok's protections mechanisms. However, for some shared state (the process map, file descriptor table, sockets, TTYs, mount table, and system V shared memory table), ExOS uses shared memory. ... A limited degree of fault isolation is provided for these abstractions by mapping shared data at addresses far from the application text and data."
  • "To compensate for the effects of shared state on performance, measurements in Sections 6 and 8 include the cost of inserting system calls before all writes to shared state." Section 6.3: "we inserted three system calls before every write to these shared tables."
  • Fork: "ExOS scans through its page tables, which are exposed by Xok, marking all pages as copy-on-write except those data segment and stack pages that the fork call itself is using. These pages must be duplicated so as not to generate copy-on-write faults while running the fork and page fault handling code. Groups of page table entries are updated at once by batching system calls to amortize the system call overhead over many updates."
  • Exec: "creating a new address space for the new process, loading on demand the disk image of the process into the new address space, and then discarding the address space that called exec."
  • File descriptors name "entries in a global file descriptor table, which is currently stored in shared memory"; each entry has a function-pointer table, and "unlike UNIX, ExOS allows applications to install their own methods". Files: C-FFS locally, NFS remotely, "Both file systems are library based." Mount table: "currently unprotected".
  • Cost of all protection: running Figure 2's benchmarks "without XN or any of the extra system calls ... reduces the overall number of Xok system calls from 300,000 to 81,000, but only changes the total running time from 41.1 seconds to 39.7 seconds. Real workloads are dominated by costs other than system call overhead."
  • Table 2 (pipe latency, µs): 1 byte: shared memory 13, protection 30, OpenBSD 34; 8 KB: 150, 148, 160. "even with gratuitous use of Xok's protection mechanisms, user-level pipes can still outperform OpenBSD."
How it works, step by step: fork in a library
  1. Create the child environment through Xok and a new capability for it (M7).
  2. Copy immediately the data-segment and stack pages that the fork code itself is touching, so fork never takes a copy-on-write fault on its own working pages.
  3. Mark every other page copy-on-write in both address spaces: read-only PTEs plus a mark in the software-only PTE bits. The libOS reads its page tables directly (exposed) but writes them through system calls, batched "to amortize the system call overhead".
  4. Publish the child in the process table (its own entry is writable only by it) and in the shared process map that translates UNIX pids to Xok environment numbers.
  5. Result: about 6 ms per fork on ExOS versus under 1 ms on OpenBSD, because environments cannot share page tables, so every PTE of the child must be created rather than shared (the cause is the paper's; the "every PTE" elaboration is inference).
Assumptions it relies on
  • A1. Three system calls per shared write approximate the cost of real protection (stated as the method; not validated against a protected implementation).
  • A2. Processes sharing the unprotected tables are cooperative (implicit; "ExOS cannot guarantee UNIX semantics for these abstractions until they are protected from arbitrary writes by other processes").
  • A3. The workload is not dominated by fork (implicit; the I/O benchmark is dominated by file work and the compile, while MAB "stresses fork").
If an assumption changes
  • A1 changes (real protection needs copies or validation, not just a crossing): the 41.1 s figure would understate the cost; for this I/O-bound workload, even doubling the per-call cost of 219,000 calls would add seconds, not tens of seconds (inference; arithmetic in Worked Example ①).
  • A2 changes (a hostile process): it can corrupt another's file descriptor entries or redirect the mount table, the integrity question the introduction raises.
  • A3 changes (a shell script spawning thousands of processes): at 6 ms versus under 1 ms, 1,000 forks cost about 6 s versus under 1 s (this guide's arithmetic).
Design notes and rejected alternatives

Pipes use software regions plus directed yield; signals are layered on Xok IPC. The protected pipe in Table 2 "installs a wakeup predicate on every read (something unnecessary even with mutual distrust)" (parentheses in the original), so it overstates protection cost. The 8 KB row's protected time (148 µs) is slightly below the unprotected one (150 µs), which suggests the difference at that size is within measurement noise (inference).

Connections

Dune: also gives a process direct access to its own page tables, and its evaluation compares its sthread creation against fork (connection is this guide's). Superpages: sharing page tables between environments, the missing feature here, is the same kind of structure sharing that large mappings need (inference). NFS: ExOS's NFS client lives in the library and caches through the registry.

M20 · The binary emulator: OpenBSD programs without source, faster than native

TL;DR
ProblemPrograms without source cannot be relinked against ExOS.
MechanismXok "reroute[s] specific INT instructions" to an emulator that runs in the program's own address space and turns OpenBSD system calls into procedure calls into ExOS.
Trade-offNo privilege needed and "a few percent" overhead; only 90 of about 155 system calls supported.
Breaks whenA program uses an unsupported system call.
Key points
  • "Although the emulator is only partially completed (it supports 90 of the approximately 155 OpenBSD system calls), initial results are promising: it has been able to execute large programs such as Mosaic."
  • "The main interesting feature of the emulator is that it runs in the same address space as the emulated program, and consequently does not need any privilege. Measurements show that most programs on the emulator run only a few percent slower than the same programs running directly under Xok/ExOS."
  • "the trivial 'get process id' system call takes 270 cycles on OpenBSD and 100 cycles on the emulator running on Xok/ExOS (on a 120-MHz Intel Pentium)." Reason: "ExOS can omit many expensive checks that UNIX must perform in order to guard against application errors (on an exokernel, if an application passes the wrong arguments to a libOS, only the application will be affected)."
How it works, step by step: getpid() in an OpenBSD binary
  1. The binary executes OpenBSD's system-call trap instruction (an INT, general knowledge: int 0x80).
  2. Xok reroutes that specific INT back into the same address space, to the emulator's entry point, instead of treating it as a Xok call.
  3. The emulator decodes the OpenBSD call number and arguments and calls ExOS's getpid as an ordinary function.
  4. ExOS returns the pid from its own state, with no argument validation needed for kernel safety.
  5. Cost: 100 cycles = 0.83 µs at 120 MHz versus 270 cycles = 2.25 µs on OpenBSD (this guide's arithmetic).
Assumptions it relies on
  • A1. The hardware lets Xok redirect particular trap vectors (stated: "reroute specific INT instructions").
  • A2. ExOS semantics are close enough to OpenBSD's (stated implicitly by sharing "most of libc" and applications with OpenBSD).
If an assumption changes
  • A1 changes: every emulated call would go through Xok first, adding a crossing and losing the "faster than native" result (inference).
  • A2 changes (an OS with very different semantics): the emulator must reproduce them in user code; possible, but no longer a thin layer (inference).
Design notes and rejected alternatives

A privileged emulator in the kernel (the conventional approach) was unnecessary. The 270-versus-100 cycle comparison is on a different processor (120 MHz Pentium) from the rest of the paper's measurements.

Connections

x86 VMM (hwsw): both intercept guest system calls, but the VMM does it below an unmodified OS and pays a world switch, whereas this emulator stays in user space (inference). Dune: its sandbox intercepts system calls of untrusted code inside a process, a similar in-process interposition with hardware support (inference).

M21 · XCP: a "zero-touch" copy that schedules the disk itself

TL;DR
ProblemA UNIX copy reads and writes one file at a time through the read/write interface: artificial ordering, small disk requests, two CPU copies per byte, and waits.
MechanismEnumerate and sort all source blocks; issue large asynchronous reads; allocate destination files during the reads; build large writes straight from the buffer cache pages, so the disk controller moves the data by direct memory access (DMA) and "the CPU never touches the data".
Trade-off"a factor of three faster than the copy program (CP) on Xok/ExOS that uses UNIX interfaces", whether or not files are in core; requires knowing physical block numbers and owning the cache pages.
Breaks whenBlock numbers do not reflect physical layout, or the copy must transform data.
Key points
  • "It exploits the low-level disk interface by removing artificial ordering constraints, by improving disk scheduling through large schedules, by eliminating data touching by the CPU, and by performing all disk operations asynchronously."
  • "First, it enumerates and sorts the disk blocks of all files and issues large, asynchronous disk reads using this schedule. (If multiple instances of XCP run concurrently, the disk driver will merge the schedules.) Second, it creates new files of the correct size, overlapping inode and disk block allocation with the disk reads. Finally, as the disk reads complete, it constructs large writes to the new disk blocks using the buffer cache entries. This strategy eliminates all copies; the file is DMAed into and out of the buffer cache by the disk controller (the CPU never touches the data)." (dash replaced by parentheses)
  • 3× "irrespective of whether all files are in core (because XCP does not touch the data) or on disk (because XCP issues disk schedules with a minimum number of seeks and the largest contiguous ranges of disk blocks)."
  • "Because XN was developed recently, the applications in this section were not measured with XN."
  • The broader claim: OS vendors have shown "reluctance ... to provide useful, simple improvements to their interfaces (e.g., prefetching, asynchronous reads and writes, fine-grained disk restructuring and 'sync' operations)."
How it works, step by step
  1. Enumerate: for files f1 (blocks 500 to 509), f2 (100 to 104), f3 (300 to 302), XCP reads their metadata and lists all 18 source blocks (illustrative).
  2. Sort and read: one ascending schedule 100 to 104, 300 to 302, 500 to 509, issued as large asynchronous reads into buffer cache pages.
  3. Allocate meanwhile: create three new files of the right sizes, choosing destination blocks 900 to 917 contiguously, while the reads are in flight.
  4. Write from the same pages: as reads complete, build large writes from those pages to 900 to 917; "the file is DMAed into and out of the buffer cache by the disk controller".
  5. In core already? Then step 2 is skipped for cached blocks and the saving is the two CPU copies per byte; on disk, the saving is mostly seeks.
Assumptions it relies on
  • A1. Sorting by block number minimizes seeks (implicit; true when block numbers follow physical position).
  • A2. The copier may read source metadata and use source cache pages as write buffers for destination blocks (implicit; requires read access to the source and write access to the destination).
  • A3. Memory is large enough to hold a large schedule's worth of pages (implicit).
If an assumption changes
  • A1 changes (an SSD or a remapping array): seek savings vanish; the zero-copy part still saves CPU (inference).
  • A2 changes (destination must be encrypted or compressed): the CPU must touch the data and "zero-touch" no longer applies (inference).
  • A3 changes (files larger than memory): XCP must split the schedule into memory-sized batches, each a sorted sweep (inference).
Design notes and rejected alternatives

The paper presents XCP as something a library file system makes easy and a vendor kernel would rarely offer. It was not measured with XN, so the 3× does not include XN's checks.

Connections

LFS: batching many small writes into one large sequential write is LFS's core idea, there done by the file system for everyone, here by one application for itself (inference). FFS: FFS lays out files to make sequential reads fast; XCP instead reorders reads across files to follow whatever layout exists (inference).

M22 · Cheetah: a web server that owns its TCP and its file system

TL;DR
ProblemA web server on a general-purpose OS copies file data into socket buffers, computes checksums over every byte, keeps a separate retransmission copy, sends extra control packets, and cannot place files by how pages reference each other; servers must "trick" the OS.
MechanismOn the XIO library: a merged file cache and retransmission pool with precomputed checksums stored with each file; knowledge-based packet merging (delayed ACKs piggybacked on responses); HTML-based (HyperText Markup Language) file grouping on disk.
Trade-offClaimed 8× over the best OpenBSD server for documents of 1 KB or less, and network-limited (29.3 MB/s, CPU over 30% idle) for large ones; in exchange, a server-specific file format and TCP.
Breaks whenFiles change often (precomputed checksums go stale), the file cache misses most requests (then grouping helps instead), or the workload is not HTTP.
Key points
  • XIO "is designed to allow application writers to exploit domain-specific knowledge and to simplify the construction of high-performance servers by removing the need to 'trick' the operating system into doing what the application requires (e.g., Harvest [7] stores cached pages in multiple directories to achieve fast name lookup)."
  • "Merged File Cache and Retransmission Pool. Cheetah avoids all in-memory data touching (by the CPU) and the need for a distinct TCP retransmission pool by transmitting file data directly from the file cache using precomputed file checksums (which are stored with each file). Data are transmitted (and retransmitted, if necessary) to the client directly from the file cache without CPU copy operations. (Pai et al. have also used this technique [34].)"
  • "Knowledge-based Packet Merging. ... it avoids sending redundant control packets by delaying ACKs on client HTTP requests, since it knows it will be able to piggy-back them on the response. This optimization is particularly valuable for small document sizes, where the reduction represents a substantial fraction (e.g., 20%) of the total number of packets."
  • "HTML-based File Grouping. Cheetah co-locates files included in an HTML document by allocating them in disk blocks adjacent to that file when possible. When the file cache does not capture the majority of client requests, this extension can improve HTTP throughput by up to a factor of two."
  • Results: the default socket and file system implementations on XIO "perform significantly better than the OpenBSD implementations of the same interfaces (by 80-100%)"; "Cheetah gains a four times performance improvement for small documents (1 KByte and smaller), making it eight times faster than the best performance we could achieve on OpenBSD"; "While the socket-based implementation is limited to only 16.5 MByte/s with 100% CPU utilization, Cheetah delivers over 29.3 MByte/s with the CPU idle over 30% of the time."
  • "The optimizations performed by Cheetah are architecture independent. In Aegis, Cheetah obtained similar performance improvements over Ultrix web servers [24]."
How it works, step by step: one small-document request
  1. Request arrives through Cheetah's packet filter into its TCP library. A normal stack would ACK the request segment soon; Cheetah, knowing a response follows, delays the ACK.
  2. Find the document in its own file cache (XIO caches "pointers to file cache blocks" at application level). The file's checksum was computed when the file was stored.
  3. Send: build TCP and IP headers, combine the stored checksum with the header checksum, and point the network card at the cache page. The delayed ACK rides in this segment.
  4. Loss: if the client's ACK does not come, retransmit from the same cache page.
  5. Miss path: if the document is on disk, its embedded images were allocated in adjacent blocks when stored, so fetching the page and its images costs few seeks.
  6. Packet count: the paper gives only "e.g., 20%" fewer packets for small documents; one removed packet out of five is 20% (this guide's illustration, not a count from the paper).
Assumptions it relies on
  • A1. Documents change rarely relative to how often they are sent (implicit in precomputed checksums).
  • A2. The file cache page does not change while a segment from it might be retransmitted (implicit; inference).
  • A3. The server knows its request-response pattern (stated: "per-request state transitions").
  • A4. HTML structure predicts which files are fetched together (stated for grouping).
If an assumption changes
  • A1 changes (dynamic pages): each response needs a fresh checksum and the zero-touch path is lost for that content (inference).
  • A2 changes (a document is rewritten while being sent): a retransmitted segment could carry new bytes under an old checksum or mix versions; Cheetah must defer the update until in-flight data is acknowledged (inference).
  • A3 changes (HTTP/1.1 pipelining or long-lived connections): ACK piggybacking still works but the "known next step" assumption is weaker (inference).
  • A4 changes (pages assembled from many unrelated sources): grouping cannot place a shared image next to every page that uses it; the paper's "when possible" covers this.
Design notes and rejected alternatives

Cheetah is built incrementally on default libraries: "The extensibility of ExOS's default unprivileged TCP/IP and file system implementations made it possible to achieve these performance improvements incrementally and with low complexity." Section 7 applications were not measured with XN.

Connections

Livelock: receive processing in a user-level TCP library, fed by packet filters, is the kind of structure where receive livelock must be avoided by scheduling, not interrupt priority (inference). FFS: HTML-based grouping is FFS's idea of placing related data together, with application-level knowledge of what is related (inference). Hints: "Don't hide power": a stack that hides the file cache from TCP hides the power to send without copying (connection is this guide's).

M23 · Global performance without a central policy

TL;DR
ProblemIf every application manages its own resources, selfish ones might degrade the whole system, and the kernel lacks the central policy (buffer cache, scheduler) that normally balances them.
MechanismThe kernel keeps allocation and revocation, enough to enforce crude global policies (quotas "using only allocation denial and revocation"), and offers global information such as LRU order that applications can use when giving resources back.
Trade-offApplications keep control; the kernel's global decisions are coarse, and the hard part is "deriving the information needed to decide what enforcement involves".
Breaks whenThe kernel cannot tell what a resource is used for (information loss), or applications ignore the advice and only crude limits apply.
Key points
  • "The central challenge in an exokernel system is not enforcing a global system policy but, rather, deriving the information needed to decide what enforcement involves and doing so in such a way that application flexibility is minimally curtailed."
  • "Fortunately, the crudeness of successful global optimizations allows global schemes to be readily implemented by an exokernel. For example, Xok currently tracks global LRU information that applications can use when deallocating resources."
  • Four reasons the authors "believe" an exokernel can do better globally: local optimization frees resources; applications can orchestrate each other (e.g., "make" could orchestrate a build); "an exokernel can unify the many space-partitioned caches"; and applications can know when resources are scarce (a web server could stop caching documents in virtual memory "when its cache does not fit in main memory"). "Future research will pursue these issues."
  • Method: total time for a randomized set of jobs as throughput, minimum and maximum per-job time as interactive latency, identical pseudo-random schedules on both systems, each job in its own directory "to avoid cooperative buffer cache reuse", compared with FreeBSD only, which "always performs better than OpenBSD, because of OpenBSD's small, non-unified buffer cache".
  • Results (read in F5, F6): first pool "roughly comparable to UNIX, despite being mostly untuned for global performance"; second pool "global performance on an exokernel system does not degrade even when some applications use resources aggressively. In fact, the relative performance difference between FreeBSD and Xok/ExOS increases with job concurrency."
How it works, step by step: a memory-hungry job meets a quota (illustrative)
  1. Quota: Xok limits each environment to, say, 4,000 pages (16 MB of the 64 MB machine). Enforcement is "allocation denial": the 4,001st allocation fails.
  2. Pressure: free memory runs low. Xok asks environments to return pages (revocation), offering its global LRU order as advice. The paper states only that revocation and global LRU exist; this request path is illustrative.
  3. Choice: a well-behaved libOS returns its least valuable pages, for example cached blocks it can re-read; a selfish one ignores the advice but cannot exceed its quota.
  4. What the kernel cannot do: tell whether a page caches a disk block or holds heap data, if both are managed at application level ("information loss"), so it cannot prefer to evict cache pages globally unless libOSes tell it.
Assumptions it relies on
  • A1. Crude policies are enough (stated: "the crudeness of successful global optimizations").
  • A2. Applications act on the global information in good faith (implicit).
  • A3. The chosen job mixes represent "substantial load where selfish applications are consuming large resources" (stated as the intent).
If an assumption changes
  • A1 changes (a workload needing fine-grained fairness, such as interactive priority): round-robin slices and quotas do not express it; the paper evaluates only min and max latency (inference).
  • A2 changes (adversarial applications): only the hard limits (quotas, revocation) remain; the paper does not test malicious behavior (inference).
  • A3 changes (a memory-bound mix larger than 64 MB): ExOS lacks "full paging" and "process swapping", so such a mix could not be run as is (inference from Section 5.2).
Design notes and rejected alternatives

The authors chose throughput and latency of randomized mixes because "Global performance has not been extensively studied", and say the comparison with one system "does not guarantee that an exokernel can compare to any centralized system" but "does offer a useful relative metric". The second pool's advantage comes from applications that "benefit from C-FFS's performance advantages" (pax and cp), so it mixes a file-system advantage into the global result (inference).

Connections

ESX: global memory policy across mutually unaware managers (guests) is ESX's problem too, solved with ballooning, idle memory taxes and sharing (general knowledge; inference connecting the papers). vLLM: a central block manager that preempts and swaps sequences when memory runs out is the centralized counterpart (inference).

  • Figure 4: totals match within about 7%, with FreeBSD slightly ahead at 28/4 and 35/5; Xok/ExOS has the lower worst-case job time at every concurrency above 1 and lower or equal best-case times. Supports "roughly comparable to UNIX, despite being mostly untuned for global performance."

Supports "does not degrade even when some applications use resources aggressively" and "the relative performance difference ... increases with job concurrency", in Xok/ExOS's favor.

By that measure Figure 5 is mixed: Xok/ExOS's shortest job is longer than FreeBSD's at 7/1 (≈0.4 vs ≈0.2 s) and 35/5 (≈1.2 vs ≈0.6 s) shorter at 21/3 and 28/4, and about equal at 14/2. The text does not comment on this.

L · Stated limitations and future work

What the paper itself says is unfinished or costly
  • Shared global state: the process map, file descriptor table, sockets, TTYs, mount table and System V shared memory table are unprotected shared memory; "ExOS cannot guarantee UNIX semantics for these abstractions until they are protected"; protection cost is approximated by inserted system calls.
  • "the system is research, not production quality"; missing "full paging, process swapping, process groups, and a windowing system".
  • Fork is slow (6 ms) because "Xok does not yet allow environments to share page tables".
  • No explanation yet for Xok/ExOS beating OpenBSD/C-FFS on pax, cp and diff.
  • Section 7's applications "were not measured with XN"; the emulator covers 90 of about 155 system calls.
  • XN future work: more file systems (log-structured, RAID, memory-based) to test whether the interface suffices; "lightweight protected methods like UDFs" for higher-level checks; optimistic concurrency instead of registry locks; C-FFS's invariant checks are downloaded methods pending a UDF-like system.
  • Costs named in Section 9.2: interface design takes several iterations; information loss (the kernel may not tell cache pages from VM pages; on Glaze also from message buffers); self-paging libOSes are hard. Exposed structures are not a stable API.
  • Global performance: "has not been extensively studied"; one comparison system; the better-than-current claims are stated as belief with "Future research".
What the evaluation does not cover (this guide's list)
  • No adversarial test: no malicious libOS attacks the shared tables, XN, or the registry; integrity (question four of the introduction) is argued, not measured.
  • No microbenchmark of XN itself (UDF execution time, taint bookkeeping, registry operations); its cost is folded into the 1.4 s total.
  • No crash or recovery experiment: the ordering rules and the free-map rebuild are described, not exercised; no recovery time is given.
  • Only one file system (C-FFS) on XN; whether two different libFSes can share files efficiently is untested.
  • Memory pressure is avoided: 64 MB, no paging; global LRU and revocation are not exercised by the global-performance runs.
  • Figure 3 has no error bars and one bar ends at the axis maximum; the 8× headline cannot be read from the figure.
  • The OS-structure effect and the file system effect are separated only by the OpenBSD/C-FFS port, and that port's total (51 s) is not reproduced by its bars.

C · Connections to the other CS240 papers (mechanical only)

  • FFS (background for 10/27): all layout policy in the kernel, parameterized by hardware; the exokernel moves the same decisions into libFSes and keeps only ownership and ordering (S).
  • LFS (10/27): named by the paper as a future libFS on XN. Its cleaner's moves are Rule 3 operations that XN leaves to the libFS; its checkpoint-based recovery avoids the full traversal XN uses (M12, M14, Class Prep C8).
  • Rethink the Sync (10/29): XN removes forced synchronous writes by enforcing order rules instead of write timing; external synchrony also keeps guarantees while avoiding synchronous waits (inference).
  • F2FS (11/5): a log-structured, flash-aware layout with a node address table; under XN its node address table (NAT) and segment structures would be templates, and its hot/cold separation a libFS policy (inference).
  • Dune (11/12): the same goal of giving applications privileged hardware (page tables, exceptions, privilege modes), achieved with VT-x inside a process on Linux instead of a new kernel; its paper says "its goal is not extensibility" but using hardware "in concert with the OS" (M5, M16).
  • Hints (12/1): "Don't hide power", "Leave it to the client", "Use procedure arguments" (with the loop-free Spy patches) and the tension with "Keep secrets of the implementation" map onto M1, M4, M11 and M17.
  • x86 VMM (hwsw) and ESX: the virtual-machine alternative the paper rejects because "emulation hides information"; ESX's ballooning is visible revocation added back (M3).
  • Superpages: physical page allocation and contiguity are exactly what an exokernel would give a libOS to manage (M2, M16).
  • NFS and Leases: ExOS's NFS client is a library sharing blocks through the registry; a lease is a time-limited binding (M5).
  • Livelock: packet filters plus a user-level TCP move protocol work out of interrupt context; downloaded interrupt handlers were judged not worth it (M18).
  • Mesa and Eraser: robust critical sections and wakeup predicates avoid trusting lock holders; predicates are kernel-evaluated condition waits (M8, M17).
  • Salus: both verify untrusted components by checking results (owns-udf before and after) rather than trusting code (M11).
  • vLLM: a centrally managed block table and preemption is the centralized counterpart to libOS-managed pages with kernel-tracked ownership (M23).
Follow the numbers

Worked examples

Eight calculations from the paper's own numbers and from values measured off its figures (marked ≈). Where a number is illustrative or general knowledge, it is labeled.

① What does protection cost per system call, at most?

Paper, Section 6.3: without XN or the inserted calls, Xok system calls drop from 300,000 to 81,000 and time from 41.1 s to 39.7 s. 200 MHz Pentium Pro.

  1. Calls removed: 300,000 − 81,000 = 219,000 (73% of all calls).
  2. Time removed: 41.1 − 39.7 = 1.4 s = 3.4% of 41.1 s.
  3. Upper bound per removed call: 1.4 s / 219,000 ≈ 6.4 µs ≈ 1,280 cycles at 200 MHz. This bound includes everything removed with the calls (trap, XN's UDF runs, taint bookkeeping), so the trap alone costs less.
  4. What would make protection matter: for protection to cost 20% of this workload (8.2 s), each call would need to cost 8.2 s / 219,000 ≈ 37 µs, about 6× the measured bound (this guide's arithmetic).
🍯
"Real workloads are dominated by costs other than system call overhead": three-quarters of the calls disappear and the clock barely moves, because the disk and the CPU work of gcc and gzip dominate.

② Where do the 19 seconds come from?

Figure 2, values read off (≈). Paper: Xok/ExOS 41 s, "19 seconds faster than FreeBSD and OpenBSD".

  1. OpenBSD minus Xok, per step: pax unpack 9.13 − 1.69 = 7.4 s; cp -r 6.98 − 2.06 = 4.9 s; rm tree 9.54 − 5.28 = 4.3 s; diff 0.8 s; rm binaries 0.3 s; gzip 0.9 s; pax pack 0.4 s; cp small 0.4 s; gcc 0.2 s; gunzip −0.2 s; cp large −0.4 s.
  2. Sum: ≈ 18.9 s, matching the paper's 19 s. Of it, ≈16.6 s (88%) comes from three metadata-heavy steps: unpack, tree copy and tree delete.
  3. Same file system, different OS: OpenBSD/C-FFS minus Xok on those three steps: 3.4 + 1.6 − 0.1 = 4.9 s. So most of the 19 s is C-FFS versus FFS, not library versus kernel.
💡
The paper's own framing agrees: "ExOS's performance improvements are due to its C-FFS file system." The exokernel's contribution is that C-FFS could be deployed as a library, not that a library OS runs faster.

③ Cheetah's small-document ratios, from the bars

Figure 3, requests/s read off (≈). Claims: "four times" over the base server and "eight times faster than the best performance we could achieve on OpenBSD" for documents of 1 KB or less.

  1. 0 B: Cheetah ≈7,878; Socket/Xok ≈2,518 → 3.1×; best BSD (Socket/BSD) ≈1,236 → 6.4×.
  2. 1 KB: ≈6,753 vs ≈1,944 → 3.5×; vs ≈1,141 → 5.9×.
  3. 100 B: the Cheetah bar ends exactly at the 8,000 top of the axis. Ratios ≥ 3.7× and ≥ 7.0×. Reaching 4× needs ≥ 8,624; reaching 8× needs ≥ 9,128 (8 × 1,141).
  4. Conclusion: the figure supports about 6 to 7× over OpenBSD and 3 to 3.5× over the base server; 4× and 8× could only hold for the 100-byte point, whose value the plot does not show.
🍯
The headline gain is real and large, but the round numbers in the text are the top of the range, possibly from a clipped bar.

④ Large documents: how close to the wire is 29.3 MB/s?

Paper: three 100 Mbit/s Ethernets; Cheetah "over 29.3 MByte/s with the CPU idle over 30% of the time"; socket version "16.5 MByte/s with 100% CPU utilization". Frame overheads are general knowledge.

  1. Raw link capacity: 3 × 100 Mbit/s = 300 Mbit/s = 37.5 MB/s (106 bytes).
  2. TCP payload ceiling (general knowledge): a full Ethernet frame carries 1,460 bytes of TCP payload in 1,538 bytes of wire time (preamble 8, header 14, IP 20, TCP 20, frame check sequence 4, inter-frame gap 12), 94.9% → about 35.6 MB/s.
  3. Cheetah: 29.3 / 35.6 ≈ 82% of the payload ceiling (86% if the paper's MByte means 220 bytes), with per-connection setup, request packets and HTTP headers still to pay for.
  4. CPU per MB: socket version 100% / 16.5 ≈ 6.1% of the CPU per MB/s; Cheetah at most 70% / 29.3 ≈ 2.4% per MB/s. Cheetah uses at most 40% of the CPU per byte (this guide's arithmetic).
💡
The CPU saving per byte is what removing the copy and the checksum pass buys; the network, not the server, becomes the limit.

⑤ The protected pipe in cycles

Table 2 (µs): 1 byte: shared memory 13, protection 30, OpenBSD 34; 8 KB: 150, 148, 160. 200 MHz.

  1. Protection overhead, 1 byte: 30 − 13 = 17 µs = 3,400 cycles. That buys software-region system calls and a wakeup predicate on every read.
  2. Against OpenBSD: 34 − 30 = 4 µs = 800 cycles left over even with the overhead.
  3. 8 KB: if protection added a fixed 17 µs, the protected column would read about 167 µs; it reads 148. So the overhead is not a fixed per-operation cost at this size, or the difference is noise (inference).
  4. Per-byte cost implied: (150 − 13) / 8,191 ≈ 0.017 µs per byte ≈ 60 MB/s through the pipe (this guide's arithmetic, assuming the 1-byte time is the fixed part).

⑥ Why an emulated system call can beat the native one

Section 7.1: getpid 270 cycles on OpenBSD, 100 cycles on the emulator, 120 MHz Pentium.

  1. Times: 270 / 120 MHz = 2.25 µs; 100 / 120 MHz = 0.83 µs.
  2. Saving: 170 cycles = 1.4 µs per call, 2.7× faster.
  3. Where it goes: the native path traps to the kernel and validates arguments against hostile callers; the emulator is reached by the rerouted INT in the same address space and calls ExOS as a procedure, skipping checks that protect only the caller.
  4. Scale: a program making 1 million such calls saves 1.4 s; for "most programs", the emulator is "a few percent slower" overall, so the trap-free path does not dominate real runs (inference).

⑦ Fork: how much of a fork-heavy job is fork?

Section 6.2: fork 6 ms on ExOS, under 1 ms on OpenBSD; MAB 11.5 s on Xok/ExOS, 12.5 s on OpenBSD/C-FFS. The fork count is illustrative.

  1. Per fork, extra cost: at least 6 − 1 = 5 ms.
  2. If a MAB run forked 200 times (illustrative), fork would cost ExOS at least 1.0 s more than OpenBSD/C-FFS.
  3. Observed: Xok/ExOS is still 1.0 s faster on MAB. So without the fork penalty it would be about 2 s faster, closer to the 20% advantage of the I/O workload (41 vs 51 s) under this assumption.
  4. Cause named by the paper: environments cannot share page tables, so the child's tables are built by batched system calls.
🍯
A libOS can be slower than a kernel at operations that need many protected updates; the paper's fix (shared page tables) is a kernel feature, not a library one.

⑧ How many tuples does owns-udf return, and why partition metadata?

Section 4.1: owns-udf returns a set of (start, count, template) ranges; XN lets libFSes partition metadata so each set is "(typically) a single tuple". Block numbers illustrative.

  1. A C-FFS-style inode with 12 direct pointers to blocks 800 to 811 (contiguous): one tuple (800, 12, data).
  2. The same inode after aging, pointers 800, 803, 820, 821, 822, 900, ... : up to 12 tuples, one per run of consecutive blocks.
  3. An indirect block of 1,024 pointers (4 KB of 4-byte pointers, general knowledge) scattered over the disk: up to 1,024 tuples per owns-udf call, run twice per allocation (before and after).
  4. Partitioning: if the libFS declares each 4-byte pointer slot (or each small group) as its own metadata piece, each call examines one piece and returns one tuple, so the before/after comparison costs the same no matter how fragmented the file is (this guide's reading of the paper's sentence).
💡
The kernel's checking cost depends on how the libFS describes its metadata, which is one more decision the exokernel leaves to the application.

Problem 2 · easy
Why can't Xok let applications write x86 page tables directly, when Aegis let applications manage translations on MIPS?
Show answer
On the x86 the hardware walks the tables on a TLB miss and "does not verify that the physical page of a translation can be mapped by a process". Problem 4 · medium
A libFS creates a file: it allocates inode block I in directory block D and data block X in I. It then tries to write D, then I, then X, in that order. Which writes does XN refuse, and what order works?
Show answer
D is tainted (points to uninitialized I), so write(D) fails. I is tainted (points to uninitialized X), so write(I) fails. write(X) succeeds. After X is initialized on disk, I is no longer tainted and can be written; after I, D can be written. Working order: X, I, D. Problem 10 · hard

Connecting outward

What the exokernel teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

Exposing a device's asymmetries is a protection problem first

The exokernel's case for physical names and explicit allocation is the general case for letting software see what a device really is: which blocks are near each other, which pages cache what. For a memory tier whose reads and writes cost very different amounts, or whose cells wear out, the same tension appears: placement policy wants device details, but the system must still prevent one tenant from reaching another's cells. The paper's answer is to expose the names and keep only ownership and a few ordering rules in the kernel; the evidence that this works is that its biggest wins (C-FFS, XCP, Cheetah) are all placement and scheduling decisions made with device-level names.

Ownership can be checked without understanding the format

XN's before-and-after owns-udf comparison is a reusable pattern: let the untrusted party describe its own data structure with a deterministic, frozen function, and verify only the difference a proposed change makes. Any multi-tenant system that stores tenant-defined metadata (translation tables, allocation maps, object indexes) and must stop tenants from claiming each other's physical units faces the same problem the authors spent four designs on, and the lesson of the declarative attempt applies: a fixed description language "made too many tradeoffs".

Separate the map of what is cached from the memory that holds it

The buffer cache registry records block-to-page mappings and state but owns no data. That split lets each application choose eviction while still sharing one physical copy, and it lets the kernel answer "who may map this page" from "who may read this block". The same structure (a global, read-only index plus owner-managed frames) is what any shared cache across protection domains needs, from page caches shared across containers to key-value block caches in inference servers.

Enforce crash invariants, not write schedules

XN does not tell a file system when to write; it refuses only writes that would leave a persistent pointer to uninitialized data, and it delays reuse of a freed block until no persistent pointer to it remains. Stating durability requirements as invariants on what may reach persistent media, rather than as mandatory synchronous writes, is the approach that later soft-updates-style systems and many persistent-memory designs take (general knowledge), and it is directly applicable wherever a write-ordering rule protects other parties.

Copies, not traps, are where I/O time goes

Removing 73% of system calls saved 3.4% of runtime; removing the copy and the checksum pass from Cheetah's send path, and the two copies from XCP, saved factors of 2 to 8. For anyone who counts memory bandwidth, this is the paper's most transferable result: once I/O is involved, per-byte work dominates per-operation work, and the fastest path is the one where the CPU never touches the data ("the CPU never touches the data").

Decentralized management loses information the system needs

The authors list "information loss" as a real cost: if paging and file caching are both in applications, the kernel cannot tell a cached block from a heap page. Any tiered memory system that lets applications or runtimes manage placement faces the same issue for global decisions such as which tier to shrink under pressure. The paper's partial remedies (global LRU kept by the kernel, approximate access tracking, exposure of state in shared structures) are the ones still used, and each requires the kernel to keep some observation hook that the hardware provides (on the x86, accessed bits rather than TLB fills, Class Prep C6).

C1 · A libFS installs an owns-udf that hides one of its pointers. What can it do with the hidden pointer?

XN trusts owns-udf because it is deterministic and frozen in the template, but nothing forces it to be complete. Suppose my libFS's inode template has an owns-udf that simply skips the last pointer slot, and I write the block number of another user's data into that slot with an ordinary allowed modification: owns-udf before and after return the same set, so XN sees no change. Have I just given myself a pointer to someone else's block? What does XN let me do with it, and who gets hurt?

AnswerWork it out first, then open▾

Nothing useful, and only the libFS itself is at risk. Every way of touching a block goes through the same function. Reading requires stage 1, where "XN uses owns-udf to determine if the requested blocks are controlled by the supplied metadata blocks"; a pointer owns-udf does not report is not "controlled", so XN will not install a registry entry for it under this parent. A raw read only marks the block "unknown type", and "The block cannot be used until after it is bound to a parent by the first stage of the read process." Mapping a cached copy needs the same access level as the block. So the hidden slot is just bytes, not a capability.

The damage runs the other way: XN's ownership and crash bookkeeping also come from owns-udf, so any block the libFS reaches only through a hidden slot is, to XN, unowned. After a crash, the free-map rebuild treats it as unreachable and frees it, and it can be allocated to someone else while the libFS still holds the stale number. Determinism protects other users from a lying function; it does not protect the liar from its own incompleteness.

Where the answer comes from: Sections 4.1, 4.3.3 and 4.4 (read stages, raw reads, recovery traversal); the scenario is constructed, the conclusion follows from the stated rules.

C2 · A crash hits while a freed block is on the "will free" list. Who owns it after reboot?

XN delays reuse of a freed block until all on-disk pointers to it are gone, keeping it on a "will free" list. The paper never says that list is persistent, and recovery rebuilds the free map by traversing from the roots. If I delete a file and the machine crashes before the inode block without the pointer is written, what does XN think about that block after reboot, and could it end up in two files?

AnswerWork it out first, then open▾

Ownership after reboot is decided only by what is on disk: "reachable blocks are allocated, non-reachable blocks are not." If the old inode (still pointing at the block) is reachable from a persistent root, the block is allocated to that file again, so the delete is simply lost. If the directory change that unlinked the inode reached disk but the inode change did not, the inode is unreachable and both it and the block are freed. Either way the result matches the disk.

It cannot end up in two files, because Rule 1 kept the block out of the free map until the old pointer was nullified on disk; no new owner could have been written before the crash. Whether the will-free list itself survives is irrelevant (and is not stated), since the traversal recomputes everything it encodes.

Where the answer comes from: Sections 4.3.2 and 4.4 (deferred deallocation, recovery by traversal from the root catalogue); persistence of the list is not stated and is not needed for the answer.

C3 · If metadata blocks can never be mapped read/write, how does C-FFS update a modification time?

The paper says "XN specifically disallows metadata blocks from being mapped read/write", and C-FFS's acl-uf can reject any change that does not keep inode modification times current. So when a program writes one byte into a file, what exactly does C-FFS do to the inode, and how does that differ from writing the data byte itself?

AnswerWork it out first, then open▾

The data byte goes into the data block's cached page, which C-FFS may map writable (it is a data block and the process has write access), so it is an ordinary store. The inode change cannot be a store: C-FFS calls XN with the inode block and the proposed modification as "a list of bytes to write" (the new mtime, and size if it grew). XN runs acl-uf (which for C-FFS checks permission and that the mtime is updated) and, if pointers change, owns-udf before and after, then applies the bytes to the registry copy.

So every metadata change is a system call carrying a byte-level diff, while data changes are free once bound. That asymmetry is plausibly part of why the protected run makes 300,000 Xok calls against 81,000 without XN and the inserted checks (the inserted shared-table calls are the other part), and removing them all still saves only 1.4 s on this disk-bound workload (the attribution is inference; the paper does not break down the calls).

Where the answer comes from: Sections 4.1, 4.4 and 4.5 (proposed modifications as byte lists, acl-uf for mtimes, metadata not mappable read/write) and Section 6.3's call counts.

C4 · Can Figure 3 show the "eight times faster" claim?

The abstract and Section 7.3 say Cheetah is eight times faster than the best OpenBSD server for documents of 1 KB or less, and four times faster than the same server without optimizations. Figure 3's y axis stops at 8,000 requests per second, and the best OpenBSD bars in that range are around 1,100 to 1,200. Which bars could support 8x and 4x, and can the figure confirm it?

AnswerWork it out first, then open▾

Measured from the figure: at 0 bytes Cheetah is about 7,880 against Socket/BSD about 1,240 (6.4x) and Socket/Xok about 2,520 (3.1x); at 1 KB about 6,750 against 1,140 (5.9x) and 1,940 (3.5x). At 100 bytes the Cheetah bar ends exactly at the 8,000 top of the axis, against best BSD about 1,140 and Socket/Xok about 2,160, so its ratios are at least 7.0x and 3.7x.

8x at 100 bytes would need about 9,130 requests/s and 4x about 8,620, both above the plotted range. So only the possibly clipped 100-byte point can carry the round numbers; the unclipped points support 5.9 to 6.4x and 3.1 to 3.5x. The gain is large either way; the specific factors are not readable from the figure.

Where the answer comes from: Bar heights measured from a 600 dpi render of Figure 3 (about 8 requests/s per pixel row); the claims are quoted from the abstract and Section 7.3.

C5 · Bind-time checks: does a reader keep access after the owner revokes permission?

XN checks read permission once, when a cached block's page is entered into a libFS's page table, and never on later loads. Suppose user A has page p (caching block 812 of file F) mapped read-only, and F's owner then removes A's read permission. Does A keep reading? Does A see the owner's later writes to 812? Is that weaker than UNIX?

AnswerWork it out first, then open▾

A keeps reading as long as the mapping exists, and because p is the single shared physical page for 812, A also sees the owner's later writes into p. Nothing in the paper says a permission change walks the page tables to remove derived mappings; the check is "at bind time rather than checking at every access".

This matches UNIX semantics for an open file: permissions are checked at open, and a process holding an open descriptor keeps reading, including later writes, after a chmod (general knowledge). What must never happen is a binding outliving the page's ownership: if p is freed and reused for other data, A's PTE must go first. Xok exposes "inverse page mappings", the structure that finds such PTEs, and it shows the discipline elsewhere: a physical page referenced by a wakeup predicate "is not marked as free until a new predicate is downloaded or until the application exits".

Where the answer comes from: Section 4.3.1 (secure bindings at page-table insertion), Section 5.1 (inverse page mappings, predicate page rule); UNIX open-time checks are general knowledge.

C6 · How can Xok track global LRU on the x86 if it never sees TLB refills?

Section 9.2 says that if page tables are managed by the application, "the exokernel can approximate LRU page ordering by tracking the insertion of translations into the TLB", and Section 8 says "Xok currently tracks global LRU information". But on the x86 TLB refills are done by hardware. Can Xok use the TLB-insertion technique at all, and if not, what does it have instead?

AnswerWork it out first, then open▾

Not the TLB technique: on the x86, "TLB refills are handled in hardware", so a TLB insertion is invisible to the kernel; that method fits a software-refilled TLB such as Aegis's MIPS. Xok has two other signals. First, every page-table update goes through a Xok system call (applications "must instead use system calls"), so Xok sees when pages are mapped and unmapped, a coarse recency signal. Second, x86 hardware sets the accessed bit in a PTE when a translation is used (general knowledge); since Xok owns the page tables' contents, it can scan and clear these bits periodically, the standard clock approximation of LRU.

The paper does not say which Xok uses. The definite part is that the method Section 9.2 describes requires software TLB refill, and the x86 removes it, so global information on Xok must come from page-table state, not from TLB events.

Where the answer comes from: Sections 5.1, 8 and 9.2; accessed bits and clock-style LRU approximation are general knowledge of the x86 and of OS paging.

C7 · Is 29.3 MB/s on three 100 Mbit/s Ethernets near the limit?

Section 7.3 says Cheetah's large-document performance "is limited by the available network bandwidth (three 100Mbit/s Ethernets) rather than by the server hardware", at over 29.3 MB/s with the CPU idle over 30% of the time. Three links are 37.5 MB/s raw. Is 78% of raw the network limit, and what does the 16.5 MB/s socket figure at 100% CPU tell us?

AnswerWork it out first, then open▾

Close to it. Raw is 3 x 12.5 = 37.5 MB/s, but a full Ethernet frame carries 1,460 bytes of TCP payload in 1,538 bytes of wire time (8 preamble, 14 Ethernet header, 20 IP, 20 TCP, 4 checksum, 12 inter-frame gap; general knowledge), so the payload ceiling is about 35.6 MB/s. 29.3 is about 82% of that, and each 100 KB document also costs connection setup and teardown packets, the request, and HTTP headers, which plausibly accounts for most of the rest.

The socket server's 16.5 MB/s at 100% CPU is a CPU limit: about 6.1% of the CPU per MB/s versus at most 2.4% for Cheetah (70% busy at 29.3), so Cheetah spends at most 40% as much CPU per byte, which is what removing the copy and the checksum pass predicts. Note that Figure 3's Socket/Xok bar at 100 KB reads about 205 requests/s, about 20 MB/s, so "the socket-based implementation" in the text is ambiguous.

Where the answer comes from: Paper Section 7.3 and Figure 3 (read off); Ethernet, IP and TCP header sizes are general knowledge.

C8 · LFS as a libFS on XN: who keeps the cleaner's moves safe?

The paper names log-structured file systems as future libFSes for XN. The LFS cleaner moves every live block it finds into a new segment and then reuses the old segment. Of Ganger and Patt's three rules, XN enforces only the first two and leaves the third, "when moving an on-disk resource, never reset the old pointer in persistent storage before the new one has been set", to the libFS. Can a buggy LFS libFS hurt anyone else during cleaning, and when can it reuse a cleaned segment?

AnswerWork it out first, then open▾

It cannot hurt other users. A move is three XN-checked steps: allocate the new block (owns-udf check; the new copy's parent is tainted until the copy is written), write the copy, then deallocate the old block. Rule 2 stops any persistent pointer to the new location before the copy is on disk, and Rule 1 keeps the old block on the "will free" list until every on-disk pointer to it (the old inode, or the inode map block that pointed to it) has been rewritten. Violating Rule 3 can only lose that libFS's own data, which is why "a file system violating the third rule will only affect itself".

So a cleaned segment becomes reusable, block by block, only after the metadata that pointed into it has been rewritten on disk, in LFS terms after the new inode-map blocks and checkpoint referring to the new locations are written. That is the same condition LFS needs for its own crash safety (general knowledge of LFS), so XN's rule costs LFS nothing extra; what XN adds is that an LFS that gets it wrong cannot leak the segment to another user.

Where the answer comes from: Section 4.3.2 (the three rules and which XN enforces) and Section 4.6 (log-structured file systems as future work); LFS's checkpoint and inode map are from the LFS paper (general knowledge for this guide).

Glossary, results, and provenance

Every term in one place, then where the numbers came from, what this guide found inconsistent in the paper, and what it corrected in the 11/10 companion outline.

Core terms
ExokernelAn operating system kernel that securely multiplexes physical resources at the lowest level needed for protection and implements no high-level abstractions; its management is limited to allocation, revocation, sharing and ownership tracking.
ProtectionThe enforcement of who may use which resource and how, independent of how the resource is used.
ManagementThe policy choices about resources an application holds: placement, caching, eviction, scheduling, write-back, data format.
Library operating system (libOS)An unprivileged library, linked into an application's address space, that implements OS abstractions on the exokernel's low-level interface and can be replaced per application.
XokThe exokernel for Intel x86 computers measured in this paper, successor to Aegis.
ExOSXok's default libOS: a library implementing most 4.4BSD abstractions (processes, files, pipes, sockets) so that unmodified UNIX programs run after relinking.
EnvironmentXok's per-process kernel structure holding the hardware state to run a process and to deliver interrupts and exceptions to it; it also reserves space for libOS data such as the process table entry.
Physical nameThe hardware's own identifier for a resource, such as a disk block number or physical page number, used directly in the kernel interface instead of a translated virtual name.
Secure bindingAn authorization decision made once, when a resource is attached to a principal (for example a page entered into a page table), after which accesses proceed without further checks.
Visible revocation (1995 paper)A revocation protocol in which the kernel asks the libOS to give a resource back and lets it choose which instance; not described in this paper, which states only "Expose revocation".
Abort protocol (1995 paper)The kernel's fallback when a libOS does not comply with a revocation request: forced removal of its bindings, recorded so the libOS can repair its state; not described in this paper.
XNXok's in-kernel stable storage system: the code and state that decide block ownership with templates and UDFs, enforce two crash-ordering rules, export the free map, and maintain the buffer cache registry.
LibFSA library file system: the part of a libOS that implements one on-disk format and its policies on top of XN.
TemplateXN's persistent, unchangeable description of one metadata type of one libFS, named by a unique string and consisting of owns-udf, acl-uf and size-uf.
UDF (untrusted deterministic function)A function supplied by an untrusted libFS, written in a kernel-checked pseudo-RISC language, whose output depends only on its input so the kernel can trust it without understanding it.
owns-udfA template's UDF that maps a piece of metadata to the set of blocks it points to, as (start, count, template) ranges; XN runs it before and after each proposed change.
acl-ufA template's possibly nondeterministic function that approves or rejects a proposed metadata modification given credentials; it can enforce access lists or rules such as current modification times.
size-ufA template's function that returns the size in bytes of a data structure of that type.
Tainted blockA block that points to an uninitialized block or to a tainted block; XN refuses to write it while it is reachable from a persistent root.
"Will free" listXN's queue of deallocated blocks that still have on-disk pointers to them; a block leaves it for the free list when its reference count reaches zero.
Buffer cache registryA system-wide kernel table, mapped read-only into applications, of cached disk block to physical page mappings with their state (dirty, out of core, uninitialized, locked); it holds no data.
Read and insertThe registry operation by which a process without write access has the kernel read a block into the process's page, set its protection and record the mapping.
Root catalogueXN's persistent list of each libFS's root (a disk extent plus template type, named by a string), from which recovery traverses to rebuild the free map.
Type catalogueXN's persistent store of installed templates, each identified by a unique string such as "FFS Inode".
Software regionA memory area that can be read or written only through system calls, giving sub-page protection for shared libOS state.
Hierarchically named capabilityXok's credential, created on the fly and passed explicitly on every system call, closer to a generalized UNIX user and group ID than to a traditional capability.
Wakeup predicateA loop-free boolean expression downloaded into Xok, compiled with its addresses pre-translated to physical ones, and evaluated when its environment is about to be scheduled.
Robust critical sectionA section of libOS code protected by disabling the process's software interrupts (such as the end-of-slice upcall) rather than by a lock.
C-FFSThe co-locating fast file system: a libFS derived from FFS, with downloaded checks for UNIX invariants; its placement of small files and their inodes together comes from its own paper (general knowledge).
XCPThe authors' file copy program that sorts all source blocks into one schedule, reads asynchronously, and writes from the same cache pages with no CPU copy.
CheetahThe authors' HTTP/1.0 server on the XIO library, with a merged file cache and retransmission pool, precomputed checksums, packet merging and HTML-based file grouping.
Supporting terms
AegisThe earlier exokernel for MIPS-based DECstations, with user-level page tables and downloaded interrupt handlers, tuned for microbenchmarks.
GlazeThe exokernel for the Fugu multiprocessor, the third system the authors built.
MicrokernelA kernel that provides little beyond IPC, scheduling and protection, with OS services in privileged user-level servers.
Virtual machine monitor (VMM)Privileged software that runs each guest OS on an emulated copy of the hardware, isolating guests from each other.
Page table entry (PTE)One record in an x86 page table holding a physical page number, permission bits, hardware-set accessed and dirty bits, and bits reserved for software.
TLB (translation lookaside buffer)The processor's cache of recent virtual-to-physical translations; on the x86 the hardware refills it by walking the page tables.
Copy-on-writeA sharing technique in which two address spaces map the same physical page read-only, and a write fault makes a private copy for the writer.
Directed yieldA CPU primitive that hands the rest of the caller's time slice to a named environment, used by ExOS pipes when the other side must run.
UpcallA kernel-initiated call into an application at a known entry point, used by Xok to announce the start and end of a time slice.
Dynamic packet filterA small downloaded program that the kernel compiles and runs on incoming packet headers to decide which application owns each packet.
Packet ringA protected buffer in which Xok queues received packets for the application whose filter claimed them.
Ganger and Patt rulesThree ordering rules for crash integrity: no reuse before old pointers are nullified, no persistent pointer before initialization, no clearing an old pointer before a new one is set when moving.
Process mapExOS's shared table from UNIX process identifiers to Xok environment numbers, unprotected in the measured version.
Process tableExOS's per-process records (pid, parent, arguments, run status, children) kept in each environment's reserved area, readable by all and writable only by the owner.
File descriptor tableExOS's global table of open-file entries, each with a function-pointer table that applications may override; stored in unprotected shared memory in this version.
XIOThe authors' extensible I/O library for building servers on Xok, with default socket and file implementations that applications can specialize.
Retransmission poolThe memory where a TCP sender keeps unacknowledged data so it can resend it; in BSD it is the socket send buffer (general knowledge).
Piggybacked ACKA TCP acknowledgment carried in the header of a data segment going the same direction instead of in a separate packet.
Modified Andrew Benchmark (MAB)A standard file-system-and-compile benchmark that copies a source tree, scans it and compiles it; it forks many processes.
NCSA httpd, HarvestA widely used 1990s web server and a hierarchical web proxy cache, the paper's two external comparison servers.
