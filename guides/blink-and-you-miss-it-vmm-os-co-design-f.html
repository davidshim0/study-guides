PLOS 2026 · A Field Guide

Booting a VM in 18 ms by refusing to carry baggage neither side needs

A generic hypervisor supports any guest; a generic guest OS boots on any hypervisor. Both pay for that flexibility in milliseconds. Uhyve is a VMM specialized for the HermitOS unikernel, and Hermit in turn carries Uhyve-specific code — together they boot in 18ms, 3–7× faster than the same Hermit kernel running on other hypervisors.

📄 Klimt et al., "Blink and you miss it" · PLOS '26 🎓 Some OS/virtualization basics assumed — primers cover them ⏱ ~20 min read
⚡

Don't build a VMM that supports every guest and a guest that supports every VMM — co-design both for exactly each other, and delete everything neither needs.

1Why serverless needs isolation at all▾

FaaS runs strangers' code on shared hardware, so a customer's function must not read another customer's memory. Containers share the host kernel — fast, but a kernel bug lets one tenant escape into another's data. VMs add a hardware-enforced boundary (a separate virtual CPU, page tables, memory) that a shared kernel can't give you.

Now you're ready: the paper's whole premise is: VMs give real isolation, but at a startup-time cost most FaaS workloads (milliseconds of actual work) can't afford.
2Hypervisor vs. VMM — who does what▾

The paper is precise about a distinction people blur: the hypervisor (here, KVM, in the Linux kernel) uses CPU virtualization extensions to actually run guest instructions. The VMM is the userspace process on top — it allocates guest memory, emulates or exposes devices, and decides how the VM is configured and controlled.

Now you're ready: Uhyve is a VMM, always sitting on KVM. Everything the paper optimizes at the VMM layer is about doing less work in that userspace layer, not replacing KVM.
3Why a normal VM boot is slow▾

A "generic" VM boot walks the same path real hardware would: 16-bit real mode → 32-bit protected mode → 64-bit long mode, BIOS/UEFI-style device probing, ACPI table parsing, then a full guest OS boot (init system, drivers, services) before your code runs at all. None of this exists to help your function — it exists so the VM can pretend to be arbitrary hardware for an arbitrary OS.

Now you're ready: Uhyve's whole approach is deleting this chain because it knows in advance exactly what guest it's booting.
4Unikernels and library OSes▾

A unikernel compiles your application together with a minimal OS (a libOS) into one flat binary with no user/kernel split, no unrelated drivers, no shell. It runs "bare metal" inside the VM at the highest privilege level. HermitOS is one such unikernel, written in Rust.

Now you're ready: a unikernel already removes most guest-side overhead. The paper's insight is that the VMM side still wasn't optimized to match it — that's the gap Uhyve closes.
5Hypercalls, in one line▾

A hypercall is a guest-to-VMM function call — the guest writes to a special memory or I/O address, which traps out of the VM and into the VMM, which handles it (e.g. "print this string," "open this file," "shut down with exit code 3"). It's the virtualization equivalent of a syscall.

Now you're ready: Uhyve replaces emulated legacy devices (UART, NICs) with hypercalls almost everywhere except networking, which uses virtio-net.
6What a VM snapshot actually is▾

A snapshot freezes a running VM: a dump of guest memory, the state of virtual devices, and every vCPU register. Restoring one means loading that state back instead of running the boot sequence from scratch — you resume mid-execution rather than starting over.

Now you're ready: the paper's "application templates" are snapshots taken right before a function's actual work begins, so restoring skips the kernel boot and the app's own startup/import time.
7Copy-on-write, the mechanism that makes restore cheap▾

Instead of copying a snapshot's whole memory image into every new VM, CoW maps all new VMs onto the same physical pages, read-only. Only when a guest writes to a page does the kernel copy that one page for it. Untouched pages (most of them, for a short-lived function) are never duplicated.

Now you're ready: this is exactly why restoring an already-loaded snapshot is O(1) — no dependence on VM memory size at all, only on how much the guest actually writes.
8Why a tiering researcher should care▾

The snapshot-restore path is a CoW-mmap over a memory image, faulted in page by page as the guest touches it — mechanically the same primitive that page-fault-driven hot/cold tiering and promotion systems (TPP, HeMem-style) build on. Here the "cold" side isn't NVM/CXL, it's a snapshot file or a not-yet-touched shared mapping; the fault path is what turns static bytes into live, private memory on demand.

Now you're ready: read the CoW-restore section with that lens — it's the same lazy-materialization trick your tiering work uses, applied to VM boot instead of a page cache.
The whole story in one place

Uhyve in a nutshell

The problem, the co-design fix, and the snapshot extension on top of it.

Serverless functions run for milliseconds, but isolating each one in a VM means paying VM boot cost every time. That cost has three sources: the raw virtualization overhead, host-side device emulation, and guest-side OS duplication (a full kernel + userspace booting just to run one function). General-purpose VMMs (QEMU, Firecracker, Cloud Hypervisor) minimize some of this, but they still boot Linux-shaped guests through a Linux-shaped boot protocol — even when the actual guest is a tiny unikernel that doesn't need any of it.

Uhyve is a VMM co-designed with HermitOS so that neither has to support anything the other doesn't need: it starts the VM directly in 64-bit mode (no 16→32→64 chain), loads the guest ELF and builds its page tables itself (no bootloader, no in-kernel remap), skips CPU/ACPI detection the guest would otherwise do, and starts every core simultaneously. Legacy devices are replaced by lightweight hypercalls plus virtio-net for networking. The result: a "Hello World" HermitOS VM boots, runs, and shuts down in ≤20ms — under half the second-fastest hypervisor running the same kernel, and ~10× faster than a minimal Linux boot.

On top of that, application templates use instruction-accurate snapshots taken right before a function's real work starts. Restoring a snapshot already in RAM is an O(1), copy-on-write operation — skipping kernel boot and app/runtime startup — pushing time-to-first-packet down to ~2ms, about 50× faster than Linux on the fastest general-purpose hypervisor.

🍯 Key takeaways

  • Overhead has three sources: virtualization cost, host device emulation, guest OS duplication.
  • Co-design lets you delete boot-protocol steps entirely instead of just emulating them faster.
  • Uhyve Hello-World boot: 18ms fresh, 15ms with a template — vs ~5.3s for a full Linux VM.
  • Application templates = instruction-accurate snapshot + CoW restore ⇒ O(1), ~2ms time-to-first-packet.
  • Speedups vs other Hermit VMMs: 3–7× (boot), 8–16× (fresh TTFP), 32–62× (snapshot TTFP).
  • Memory scales ~10× lower for the unikernel; templates cut multi-instance memory 4–34× further via CoW sharing.
  • Trade-off: Hermit's static 1500B MTU caps network throughput below Linux's path-MTU-discovery numbers.
Five everyday pictures

How to think about Uhyve

Each stands alone. Every card ends with where the picture breaks down.

The core idea · Co-design

A universal power adapter vs. a matched charger

A universal travel adapter works everywhere but is slow and bulky — it must negotiate voltage, plug shape, region for every device. A charger designed for exactly one phone can be tiny and fast because it never has to ask "what am I plugged into?" Uhyve+Hermit is the matched charger: since Uhyve only ever boots Hermit, it never negotiates a boot protocol, it just wires the two together.

Where it breaks: the paper is explicit that the individual steps are Hermit-specific, but the concept generalizes to other unikernel/VMM pairs — it's not a one-off hack tied to this exact pair.
Snapshots · Freeze-frame

Pausing a movie vs. rewinding to the start

Restarting a VM from scratch is rewinding a whole movie to frame one every time you want to watch "just this scene." An application template is hitting pause right before the interesting part and handing out that exact paused frame to everyone who asks — they all start from the same point instantly instead of re-watching the intro.

Where it breaks: every "viewer" needs slightly different subtitles (new IP/MAC, new args) — the paper's snapshot hypercall exists precisely to patch in those per-instance differences after resuming.
CoW restore · Sharing until you don't

Photocopying a book only when someone writes in the margin

A library keeps one master copy and hands every reader the same physical book — until a reader wants to scribble a note, at which point only that page gets photocopied for them. A hundred readers barely cost more than one, as long as they mostly just read. That's how a hundred VMs can restore from one snapshot without duplicating its whole memory image.

Where it breaks: a function that writes to most of its memory (not just reads) gets little benefit — it forces most pages to be copied anyway, same as the paper's Python-import case still paying real time for parsing new input.
Network · MTU trade-off

Moving boxes with a big truck vs. many small trips

Linux negotiates the biggest "truck" (packet, via path-MTU discovery, up to ~65KiB) it can, so it moves the same data in fewer trips. Hermit always uses the same small default truck (1500-byte packets), so it makes more trips for the same load — explaining why Hermit's raw throughput trails Linux even when the VMM is the same.

Where it breaks: this isn't a VMM limitation at all — it's purely a guest network-stack configuration choice, orthogonal to everything else Uhyve optimizes.
The full explanation

How it actually works

Following the paper's own structure: co-design, then application templates on top.

1 · What Uhyve deletes from the boot path

Because Uhyve only ever boots Hermit, it can skip every step that exists solely to support arbitrary guests:

// what a generic VMM+guest must do
16-bit real mode → 32-bit protected → 64-bit long mode
bootloader loads & relocates kernel image
guest kernel builds its own page tables
guest probes CPU config, parses ACPI for topology
cores started one at a time

// what Uhyve does instead
VM created directly in 64-bit mode
Uhyve extracts & loads the Hermit ELF itself
Uhyve pre-builds identity-mapped page tables
Hermit skips CPU/ACPI detection entirely
all application cores start simultaneously with CPU 0
💡
Free ASLR: because Hermit uses identity-mapped page tables, simply loading the kernel to a random physical address (done by Uhyve, not the guest) implements address-space randomization from the VMM side — no guest-side ASLR machinery needed.

2 · Hypercalls replace emulated devices

Uhyve exposes filesystem access (open/read/write), serial output, and VM shutdown with exit codes as hypercalls — memory- or port-mapped I/O writes that trap into the VMM, with the argument struct pointer passed in rdi. File access is sandboxed: paths must be whitelisted and mapped (Docker-bind-mount style), reinforced by landlock kernel-level whitelisting. The only emulated device is virtio-net for real networking; there's no UART or legacy NIC to emulate.

3 · Application templates — the snapshot hypercall

A new Snapshot hypercall lets the running application itself decide the freeze point — right before its real work starts, after imports/setup finish. Two requirements make this usable: R1, an instruction-accurate snapshot of VM state at that exact point; R2, a way to hand the restored instance new parameters (arguments, a fresh IP/MAC) without re-running setup. The hypercall's return value carries R2's new parameters back into the resumed guest.

🌱
Why restore is O(1): once loaded, the snapshot's memory is mmap'd with copy-on-write semantics, so handing a new VM that memory image costs a page-table mapping, not a copy — independent of snapshot size. Loading/deserializing from a file is the one step that scales with size, which is why the paper assumes the snapshot is "warm" (already in RAM) for its serverless numbers.
Follow the numbers

Worked examples

Four calculations traced through using the paper's own measurements.

① Adding up the fresh-boot microseconds (Fig. 3)

Sum the listed per-step timings for a new Uhyve VM: 1060 + 6 + 3 + 107 + 702 + 50 + 1 + 2420 + 2680 + 7 + 21 µs.

  1. Early setup (page tables, FDT, ELF load, random address, file mapping): 1060+6+3+107+702+50+1 = 1929 µs.
  2. Peripherals + backend: creating VM peripherals (2420 µs) + starting the virtualization backend (2680 µs) = 5100 µs — the dominant cost.
  3. vCPUs + boot info: 7 + 21 = 28 µs.
  4. Total: 1929 + 5100 + 28 = 7057 µs ≈ 7.06 ms — matches the paper's stated "~7ms."
🍯
Peripheral/backend setup alone is ~72% of a fresh boot — the biggest remaining target if Uhyve were optimized further.

② Snapshot restore is ~3× faster than a fresh VM — before boot even starts

Sum the snapshot-from-RAM steps: 10 + 42 + 1 + 693 + 1450 µs.

  1. CoW memory + file mapping + peripherals: 10+42+1 = 53 µs.
  2. vCPUs + backend re-create: 693+1450 = 2143 µs.
  3. Total: 53+2143 = 2196 µs ≈ 2.2 ms — matches the paper's "~2ms."
  4. Speedup vs. fresh VM creation: 7057/2196 ≈ 3.2× — and this is before subtracting the kernel boot + application startup that a fresh VM still has to run afterward.

③ Time-to-first-packet speedups (Fig. 5)

Hermit time-to-first-packet: QEMU 124ms, QEMU microVM 108ms, Cloud Hypervisor 67ms, Firecracker 98ms, Uhyve 8ms, Uhyve-snapshot 2ms.

  1. Fresh-VM speedups (Uhyve = 8ms): 124/8≈15.5×, 108/8=13.5×, 67/8≈8.4×, 98/8≈12.3× — spanning the paper's stated 8×–16×.
  2. Snapshot speedups (2ms): 124/2=62×, 108/2=54×, 67/2≈33.5×, 98/2=49× — spanning the paper's stated 32×–62×.
  3. Sanity check against the abstract: "as little as 2ms — 50× less than Linux on the fastest hypervisor" ⇒ implies a Linux TTFP near 100ms — but that's a Linux baseline, not a Hermit one: Fig. 5's minimal-Linux TTFP is actually ~138–165ms, while the ~98–108ms figures above are Hermit running on Firecracker/QEMU microVM, not Linux itself.

④ Python example — reconstructing the 5× and 10× claims

The paper states a 5× speedup vs. plain Uhyve and "close to 10×" vs. QEMU, with a 10ms NumPy compute step and typical import overhead of ~250–500ms.

  1. Uhyve-snapshot skips the Python import entirely (frozen after imports, before compute): end-to-end ≈ import-free overhead + 10ms compute ≈ tens of ms.
  2. Plain Uhyve must still pay boot (~18ms) + an import over Uhyve's own filesystem hypercalls (no virtiofsd — that's QEMU's backend) + compute (~10ms) — Fig. 8 puts this fresh-Uhyve run at ~272ms end-to-end, roughly 5× the snapshot's time, matching the stated ratio.
  3. QEMU+Hermit adds QEMU's own boot overhead (~126ms) on top of a similar import cost — this time over virtio-fs/virtiofsd, QEMU's filesystem backend — ⇒ "close to 10×" the snapshot's time.
💡
The lesson generalizes beyond Python: any workload whose real bottleneck is one-time setup (imports, config parsing, connection handshakes) is exactly what an application template is built to amortize away.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why can't Firecracker or Cloud Hypervisor simply adopt Uhyve's boot-chain shortcuts (skip 16/32-bit modes, skip ACPI detection) for any guest they run?
Show answer
Because they're general-purpose VMMs designed to boot arbitrary guests (typically Linux), which do expect a real boot-mode chain and ACPI tables to configure themselves. Skipping those steps only works because Uhyve's only guest, Hermit, was co-designed to not need them.Misconception: that the boot-chain steps are wasted work in general. They're only wasted when the guest is known in advance not to need them.
Problem 2 · medium
Uhyve loads the Hermit kernel to a random physical address each boot. Why does this alone give ASLR, when a normal OS needs its own ASLR machinery?
Show answer
Hermit uses identity-mapped page tables — a virtual address always equals its physical address. So randomizing where the VMM physically places the kernel directly randomizes its virtual layout too, with no separate relocation logic needed inside the guest.Misconception: that ASLR always requires guest-kernel support. Here it's pushed entirely into the VMM because of a specific memory-mapping choice.
Problem 3 · medium
A snapshot restore from RAM takes ~2.2ms, but reading the same snapshot cold from disk takes ~94ms. When does an application template actually save time overall?
Show answer
Only when a snapshot is reused across many invocations while it stays resident in RAM — exactly the serverless pattern of "one template, many calls." A single one-off VM would pay the ~94ms disk load, which is worse than just booting fresh (~7ms + kernel/app boot).Misconception: that snapshots are always faster. The paper explicitly assumes the snapshot is already in RAM for its headline numbers — the disk-load cost is real and must be amortized.
Problem 4 · hard
CoW restore makes handing a snapshot's memory to a new VM an O(1) operation. What breaks this O(1) property, and where in the paper's own results does this show up?
Show answer
Any guest write to a shared page forces a real copy of that page — so a function that writes to most of its memory (not just reads) degrades toward O(n) in written pages. This shows up in the Python example: the snapshot is taken right before the NumPy computation, so imports are already skipped, but the computation itself still takes real, size-dependent time after restoring the template, because it happens after the freeze point and touches new memory.Misconception: that CoW makes the whole restored VM free. Only the untouched, shared portion of memory is free; written pages still cost real copy time.
Problem 5 · medium
Hermit's network throughput trails Linux's on identical hardware and VMMs. Is this a flaw in Uhyve's design?
Show answer
No — the paper attributes it to Hermit's network stack using a static 1500-byte MTU, while Linux negotiates much larger packets via path-MTU discovery. It's a guest network-stack configuration difference, unrelated to Uhyve's VMM-level optimizations (which actually match or slightly beat Cloud Hypervisor/Firecracker for send throughput).Misconception: conflating "VMM is fast" with "guest network stack is fast." They're independent layers, measured separately in the paper.
Problem 6 · hard
In the scaling experiment, total execution time only shows "relevant scaling effects" past 32 concurrent instances, on a 32-core machine. Why would the core count of the machine matter here?
Show answer
Up to the core count, instances can run truly in parallel, each on its own core, so total wall-clock time stays roughly flat as instance count grows. Past the core count, instances start contending for CPU time (time-sharing), so total execution time begins climbing — the scaling curve bends exactly where hardware parallelism runs out.Misconception: that "scaling" results are purely about the VMM/OS. Here the inflection point is a hardware capacity limit (32 cores), not a software one.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is Uhyve a hypervisor or a VMM?▾
A VMM. It always runs on top of KVM (the hypervisor), and its job is setting up VM memory, loading the Hermit ELF, configuring devices/hypercalls, and controlling the VM's lifecycle from userspace.
Q2Why not just use Firecracker, which is already fast?▾
Firecracker is fast for a general-purpose Linux microVM, but it still boots a full Linux guest through a Linux-shaped boot protocol. Even running the same Hermit unikernel on Firecracker (56–101ms depending on the metric) is 3–7× slower than Uhyve, because Firecracker can't skip the generic steps Uhyve was specifically designed to remove.
Q3What exactly does an application template skip that a fresh boot doesn't?▾
A fresh boot pays for VM creation, kernel boot, and application startup (imports, runtime init). A template's snapshot is taken after all of that, right before the real work — so restoring it skips kernel boot and application startup entirely. It doesn't skip VM setup outright: Fig. 3 shows restore still redoes CoW memory mapping, file mapping, peripherals, vCPUs, and backend recreation (~2.2ms total) before resuming, plus re-initializing the small pieces that must differ per instance (network identity, arguments).
Q4How does a restored instance get a different IP/MAC than the one it was snapshotted with?▾
Via the same Snapshot hypercall's return path: when the VM resumes, the hypercall returns new parameters (including network identity) to the guest, which re-initializes just its network stack with the updated values — a small, explicit modification the application must support (Listing 1).
Q5Is running as one process for many VMs (as with Uhyve-snapshot) less isolated?▾
The paper runs Uhyve-Snapshot as a library linked directly into the benchmarking harness to reflect a serverless-framework integration pattern — the VM isolation boundary (KVM + Hermit) is unchanged; what differs is which process hosts the VMM logic, not the guest's isolation guarantee.
Q6Why does Hermit sometimes take longer than Linux in network-heavy tests?▾
Not because of Uhyve — Hermit's network stack uses a fixed 1500-byte MTU while Linux negotiates much larger packets via path-MTU discovery, so Linux moves the same data in fewer, bigger packets.
Q7Does this replace containers for serverless entirely?▾
The paper positions this as enabling a "purely VM-based" architecture (no container layer at all) as a viable alternative once VM boot is fast enough — not a claim that containers disappear, but that the traditional VM-is-too-slow argument for skipping VM isolation weakens substantially.
Q8What security mechanisms does Uhyve add beyond the VM boundary itself?▾
Filesystem hypercalls are sandboxed to an explicit whitelist of paths, reinforced by landlock kernel-level file-access restriction — defense-in-depth on top of, not instead of, VM-level isolation.
Q9Does the co-design approach only work for Hermit?▾
The specific implementation is Hermit-specific, but the paper states the underlying concept — designing the VMM and guest boot path jointly rather than for generic compatibility — applies to other unikernel/VMM pairs.
Q10What's left unsolved / future work?▾
The paper doesn't list explicit future-work items beyond positioning this as "a foundation to containerless VM-only FaaS architectures" — open questions implied by the results include closing the network-throughput gap (MTU) and extending templates to more complex, stateful applications.
