Making a KV-SSD's map shrink, not explode, when keys get bigger

Every key-value SSD keeps a small in-DRAM map to find data in flash. Today's designs assume tiny keys and huge values. Flip that ratio and the map itself outgrows the DRAM. This is the plain-English story of AnyKey, a redesign that keeps the map's size fixed no matter how the keys grow.

📄 "AnyKey: A Key-Value SSD for All Workload Types" · Park, Lee, Liu, Kang, Kandemir, Choi 🎓 SSD/flash basics assumed — primers cover them ⏱ ~30 min read
🗺️

Give one metadata entry to a whole GROUP of sorted keys, never one entry per individual key — then the map's size is capped by the DRAM, not by how many (or how big) the keys are.

Before you begin

Quick glossary, then eight primers

The acronyms first, then the concepts they sit on. Primers are collapsed — open whatever's unfamiliar.

KV-SSDKey-Value SSD — an SSD that stores/retrieves KV pairs directly, with the KV store logic running inside the device firmware.
LSM-treeLog-Structured Merge-tree — the flash-friendly, out-of-place-update indexing structure nearly all modern KV-SSDs use.
SSTableSorted String Table — the file format classic (host-side) LSM-trees use to store sorted KV pairs; KV-SSDs need a device-native substitute.
V/K ratioValue-to-key size ratio. This paper's central variable: "high-v/k" = tiny keys, big values (the assumed norm); "low-v/k" = keys comparably sized to (or bigger than) values.
PPAPhysical Page Address — the flash location of a page, used throughout the metadata to point at where data actually lives.
IOPS / tail latencyI/O operations per second (throughput), and the 95th/99.9th-percentile response time (the slow outliers that matter for SLAs).
GCGarbage Collection — reclaiming flash blocks by relocating still-valid pages and erasing the rest.
OP capacityOver-Provisioned capacity — extra flash beyond the advertised size, normally used to absorb updates when the drive is "full."
FEMU / uNVMeThe flash emulator and low-overhead NVMe driver used to build and evaluate this paper's testbed without needing real KV-SSD hardware.
1Why put a KV store inside the SSD at all?▾

Normally a key-value store (RocksDB, LevelDB) runs on the host and talks to a plain block-based SSD through the full storage stack. A KV-SSD instead moves the store's indexing logic into the device: the host just says "get/put this key," and the SSD figures out where the bytes live in flash.

Benefits: a shorter software path (lower latency), less host CPU/DRAM spent on indexing (better scalability — add more KV-SSDs), and SSD-aware tuning (better write amplification, longer device lifetime).

Now you're ready: AnyKey is a KV-SSD design — all the cleverness lives in the device firmware, not the host.
2Flash basics: chips, blocks, pages▾

An SSD has several flash chips, each holding thousands of blocks (the erase unit), each block holding hundreds of pages (the read/write unit — 8 KB by default here). KV pairs are stored directly in pages.

Flash can't be updated in place efficiently — old pages are marked invalid and new data goes to fresh pages, which is why out-of-place update structures like LSM-trees fit flash so well.

Now you're ready: both PPA-based addressing and the whole compaction/GC story below only make sense in terms of pages and blocks.
3What an LSM-tree is, and why "compaction" exists▾

Writes land first in a small DRAM buffer (called L0). When it fills, its KV pairs are flushed, sorted, into level L1. As levels fill past a threshold, two neighboring levels are merged — read, sorted, and rewritten into the lower level — a process called compaction. Over time this keeps each level sorted while amortizing the cost of random updates.

The core LSM-tree tradeoff: fast, sequential writes now, at the cost of periodically re-reading and rewriting data later (compaction I/O).

Now you're ready: the paper's entire "compaction overhead" story — and AnyKey's value log fix — is about making that periodic rewrite cheaper.
4The metadata problem: you need a map to find your data▾

Because KV pairs live scattered across flash pages, a KV-SSD needs metadata — a map from key → physical location — kept in device-internal DRAM for speed. If the map doesn't fully fit in DRAM, looking something up may require extra flash reads just to find where the real read should happen.

DRAM in an SSD is small and expensive relative to flash — typically sized around 0.1% of the SSD's total capacity (e.g. 64 MB of DRAM for a 64 GB SSD in this paper).

Now you're ready: the whole paper is about keeping that map inside a fixed, tiny DRAM budget.
5Why value-to-key ratio matters▾

Existing KV-SSD designs were tuned on workloads like YCSB (20-byte key, 1000-byte value) — tiny keys, big values, so keys barely add up. But many real workloads (caches, social-graph stores, blockchain indexes) have keys comparable in size to values, or bigger.

Since the map has to store (at least) the key for every entry, when keys get relatively bigger, the map gets bigger too — even though the actual payload (values) hasn't grown.

Now you're ready: "low-v/k" isn't an edge case, it's the paper's whole motivation — and it's exactly the regime where old designs break.
6Hashing, briefly▾

A hash function maps an arbitrary-length input (a key) to a fixed-size number (e.g. 32 bits), deterministically. Two different keys can occasionally produce the same hash — a collision — but with a big enough hash space, collisions are rare within any bounded group of keys.

Storing a short hash instead of a full key is cheaper — but you must handle the rare collision case correctly.

Now you're ready: AnyKey's whole metadata-shrinking trick hinges on storing short hashes instead of full (potentially large) keys.
7Tail latency: why the 95th percentile matters▾

Average latency hides the worst cases. The 95th-percentile ("tail") latency tells you how slow the slowest 5% of requests are — the ones that violate an SLA or make a user notice lag. A design that's fast on average but has occasional multi-flash-access lookups can have a terrible tail.

Now you're ready: this paper's headline numbers (e.g. PinK's tail latency jumping from 891μs to 8,904μs) are tail-latency numbers, not averages.
8Range queries and locality▾

A range query ("scan") asks for many consecutive keys at once. Performance depends on whether those keys' data is physically close together in flash (few pages to read) or scattered (many pages to read).

Now you're ready: AnyKey's design of grouping sorted KV pairs together is a direct win for range queries, not just point lookups.
The whole story in one place

AnyKey in a nutshell

The problem, the fix, and how the pieces connect.

The state-of-the-art KV-SSD design, PinK, keeps a full copy of every key's location in metadata (meta segments + level lists), sized in DRAM if possible, spilled to flash if not. That's fine when keys are tiny relative to values — but as the value-to-key (V/K) ratio drops, the collective size of that metadata grows large enough to overflow the fixed, tiny device DRAM (about 0.1% of SSD capacity). Once metadata spills to flash, every lookup can cost several extra flash reads just to locate the real read — tail latency and IOPS collapse.

AnyKey's fix: stop giving every key its own metadata entry. Instead, group many sorted KV pairs into a data segment group (32 flash pages), and keep just one metadata entry — a small hash-based index — per group, not per key. The number of groups is fixed by the flash capacity and page size, not by key size, so the metadata's total size stops growing as keys get bigger. AnyKey uses short 32-bit hashes (16 bits inside the compact level-list entries) to sort and index within a group instead of storing full keys.

Grouping KV pairs this tightly makes LSM-tree compaction expensive (moving a group means moving all its values). AnyKey's answer is a value log — a separate flash area that lets recently-written values sit untouched instead of being dragged through every compaction. A further refinement, AnyKey+, adds a compaction-chain guard so this doesn't backfire on workloads with big values.

The payoff: across eleven low-v/k workloads, AnyKey improves 95th-percentile tail latency by 56% and IOPS by 299% over PinK; AnyKey+ pushes IOPS gains to 315% on low-v/k and 15% on high-v/k workloads — meaning one design now wins on both ends of the value-to-key spectrum.

🍯 Key takeaways

  • PinK's metadata size scales with how many keys and how big each key is — it grows without bound as V/K drops.
  • AnyKey's metadata size is capped by the DRAM itself — one entry per group of KV pairs, not per key.
  • Short 32-bit (and 16-bit, inside level lists) hashes replace full keys inside groups to keep entries tiny.
  • A separate value log avoids re-moving values during ordinary LSM-tree compaction.
  • AnyKey+ prevents "compaction chains" so large-value (high-v/k) workloads don't regress.
  • Result: same device DRAM, same flash, a KV-SSD that no longer falls over when keys get big.
Six everyday pictures

How to think about AnyKey

Each stands alone — read in any order. Every card ends with an honest note about where the picture breaks.

The core idea · Grouping

A phonebook vs. a street directory

A phonebook lists every person by name (one entry each — grows with the population). A street directory instead lists streets, and you walk the street to find the house. AnyKey stops keeping a "phonebook" entry per key and keeps a "street directory" entry per group of sorted keys — the number of streets is fixed, no matter how many people live on them.

Where it breaks: a street directory still lets you glance at housenumbers; AnyKey needs an extra hashed index (the hash list) to avoid walking every house in the group.
Shrinking each entry · Hashing

A luggage tag instead of a passport

Airport baggage handlers don't staple your passport to your suitcase — they clip on a short barcode tag that's cheap to read and (almost always) uniquely identifies your bag. AnyKey does the same with keys: instead of storing a long, arbitrary key inside the DRAM index, it stores a short 32-bit hash (even shorter, 16-bit, in the level lists) — cheap, fast to compare, and unique enough within a bounded group.

Where it breaks: luggage tags never collide by design; hashes occasionally do (0.075% of groups here) — so AnyKey still needs a fallback (checking a neighboring page) for the rare case two tags match.
Why grouping is cheap to search · Sorted groups

A warehouse pallet, not loose boxes

A warehouse worker doesn't hunt for one small box lost among thousands on the floor — boxes are palletized, and the manifest for a pallet tells you which pallet has your item, then you check just the pallet's few boxes. AnyKey's data segment group is the pallet: 32 flash pages holding up to a few thousand sorted KV pairs, located as a unit.

Where it breaks: a pallet manifest is free to update; re-palletizing (rebuilding a whole data segment group) during LSM-tree compaction is real work — which is exactly the cost the value log exists to reduce.
Avoiding wasted moves · Value log

Moving apartments without re-boxing the furniture each floor

If your movers had to unpack and repack your couch every time they passed a landing, moving would take forever. AnyKey's compaction similarly re-sorts and rewrites KV pairs constantly as the LSM-tree grows. The value log is the trick of leaving the "furniture" (values) sitting in one place and only moving the light "shipping label" (the key + a pointer) during ordinary reshuffling — the couch moves only when it truly must.

Where it breaks: eventually the log fills up and the furniture does have to be moved into the new place (data segment groups) — that's the log-triggered compaction, not a free lunch, just a deferred one.
The failure mode · Compaction chains

A snowball rolling downhill

Push a small snowball off a slope and it can pick up enough snow to trigger a second, bigger slide below it. AnyKey's log-triggered compaction, when it dumps a large volume of values into the next LSM-tree level, can push that level over its own threshold — triggering another compaction, and possibly another. That's a compaction chain.

Where it breaks: real snowballs can't be stopped mid-roll; AnyKey+ literally watches the destination level's size mid-compaction and diverts the "extra snow" (values) back into the log before the chain starts.
Fast range scans · Sorted, grouped data

A library shelf, not a card catalog scattered across town

If a library's books were shelved randomly across ten branches, retrieving "everything from Austen to Bronte" means driving all over town. Shelve them together, sorted, and one visit gets the whole range. AnyKey keeps a range of keys' values physically together in the same data segment group — so a range query touches a handful of pages, not one page per key.

Where it breaks: if a value has been detached into the value log (to dodge compaction cost), a range scan may still need a second stop to fetch it — the log trades some scan locality for compaction efficiency.
The full explanation

How it actually works

Section by section, with the paper's own worked examples rebuilt as diagrams.

1 · Why PinK breaks under low-v/k workloads

PinK keeps two DRAM-resident metadata structures: meta segments (sorted keys + PPAs of KV pairs, one flash page's worth at a time) and level lists (one entry per meta segment, pointing to its DRAM or flash location). Because every individual key needs an entry somewhere in this chain, the collective size of meta segments + level lists is proportional to the number of keys and their size.

2 · AnyKey's structures: group first, hash to search inside

AnyKey replaces per-key metadata with per-group metadata. A data segment group combines 32 flash pages (256 KB), holding 100–5,000 sorted KV pairs depending on the workload. Each level list entry (in DRAM) now describes a whole group: {smallest key, PPA of first page, list of 16-bit hash prefixes — one per page}. A hash list (also DRAM, filling whatever space remains) records every actual key-hash in the group, so AnyKey can confirm a key is really present before reading flash.

3 · The value log: decoupling values from the sort order

Because a data segment group physically re-sorts all its KV pairs on every compaction, moving values around is expensive. AnyKey detaches values into a separate flash region, the value log — new writes land there first; a KV entity in a data segment group can hold either the value directly or a pointer into the log. AnyKey reserves half of the SSD's remaining capacity for the log by default (falling back to half of the over-provisioned space if the drive is full).

4 · The failure mode AnyKey+ fixes: compaction chains

When a log-triggered compaction dumps a large volume of values into the destination level (common under high-v/k, where values are big), that level can itself cross its own size threshold mid-merge — triggering a second, tree-triggered compaction immediately after. AnyKey+'s fix: during a log-triggered compaction, monitor the destination level's size; once it reaches threshold × α, stop merging values in and write the rest back to the log instead — the chain never starts. AnyKey+ also changes which level it targets for log-triggered compaction (most invalid values in the log, not just most values), to keep reclaiming log space efficiently despite writing some values back.

Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own figures, carried all the way through.

① Where the paper's "38MB" hash overhead comes from

The paper claims: with 10 million KV pairs on a 64GB SSD, AnyKey's 32-bit key hashes total 38MB — 0.05% of SSD capacity. Verify it.

  1. One hash per key = 32 bits = 4 bytes.
  2. 10,000,000 keys × 4 bytes = 40,000,000 bytes of hash data.
  3. Convert to MiB (the unit the paper uses): 40,000,000 ÷ 1024 ÷ 1024 ≈ 38.1 MB. Matches.
  4. As a fraction of 64GB (65,536 MB): 38.1 ÷ 65,536 ≈ 0.058% ≈ the paper's "0.05%".
🍯
Insight: even at ten million keys, the raw hash overhead is a rounding error against the SSD. The problem was never the hashes — it's the per-key metadata entries in PinK's design that don't scale this cleanly.

② Why the group-location info is "<1% of group size"

The paper: a group of 1,000 KV pairs across 32 8KB pages needs 2KB of location info for range queries — verify "<1% of the entire group size."

  1. Group size = 32 pages × 8KB = 256KB.
  2. Per-key location info = {target page (5 bits, since 32 pages), page offset (13 bits, since 8KB = 2¹³ bytes)} ≈ 18 bits ≈ 2.25 bytes.
  3. 1,000 keys × 2.25 bytes ≈ 2,250 bytes ≈ 2KB — matches the paper exactly.
  4. As a fraction of the group: 2KB ÷ 256KB ≈ 0.78% — comfortably under 1%, as claimed.
💡
This is the price of making range queries fast without re-sorting by key at query time (Section 4.2.5) — a rounding error added on top of an already-shrunk metadata design.

③ How much smaller is AnyKey's metadata, and does the gap grow?

Using Table 1's three measured points, compute the PinK/AnyKey ratio at each value-to-key setting.

  1. V/K = 4.0 (160B key / 40B value): PinK 372MB vs AnyKey 64MB → 5.8× smaller.
  2. V/K = 2.0 (120B / 60B): PinK 531MB vs AnyKey 64MB → 8.3× smaller.
  3. V/K = 1.0 (80B / 80B): PinK 703MB vs AnyKey 64MB → 11.0× smaller.
  4. Trend: AnyKey's number never moves (it's pinned to the 64MB DRAM); PinK's grows roughly linearly as keys get relatively bigger. The advantage compounds — the worse the workload gets for PinK, the better AnyKey looks by comparison.
🍯
Insight: this is the same shape of problem as translation/metadata overhead scaling in memory systems generally — a design that indexes at a coarser granularity (per-group instead of per-key) decouples metadata size from the raw item count, the same way a huge page or superpage decouples page-table size from the number of 4KB frames it maps. That connection is this guide's framing, not a claim the paper makes.

④ Scaling to a 4TB SSD

The paper states: running Crypto1 on a 4TB SSD, AnyKey's metadata is 3.65GB while PinK's is 25.2GB. Put that against a DRAM budget scaled the same way as the 64GB case (0.1% of capacity).

  1. Scaled DRAM budget: 0.1% of 4TB = 4GB.
  2. AnyKey's 3.65GB fits under that 4GB budget — metadata stays resident in DRAM.
  3. PinK's 25.2GB is 6.3× the DRAM budget — the overwhelming majority must spill to flash, each spill costing extra flash accesses per lookup.
  4. Ratio check: 25.2 ÷ 3.65 ≈ 6.9× — consistent with (in fact slightly larger than) the 64GB case's 5.8–11× range, confirming the gap doesn't shrink as capacity scales up.
💡
This is the practical argument for AnyKey beyond the paper's small 64GB emulated testbed: the metadata-bounding property is what makes the design viable at production SSD capacities, where DRAM stays a fixed tiny fraction of flash.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Two workloads store the same number of KV pairs on the same SSD. Workload A has 20-byte keys and 1000-byte values; workload B has 80-byte keys and 80-byte values. Under PinK, which has bigger metadata, and why?
Show answer
Workload B — even though its total data volume is far smaller (160B vs 1020B per pair), its metadata (which stores keys, not values) is dominated by its 80-byte keys vs A's 20-byte keys, and B's low value-to-key ratio means little of that cost is hidden by bulky values.Misconception: assuming metadata scales with total data size. It scales with key size and count — value size is nearly irrelevant to metadata cost.
Problem 2 · medium
The paper reports hash collisions occur in only 0.075% of data segment groups, and same-16-bit-prefix collisions in only 0.01% of level list entries. Why does AnyKey still need explicit collision handling (the hash collision bits) if it's this rare?
Show answer
Because "rare" isn't "never" — across millions of groups, 0.075% still means real collisions happen regularly in aggregate, and an unhandled collision would silently return the wrong KV pair. AnyKey's 2 collision bits per page let it always check the neighboring page when a hash match is found at a page boundary, guaranteeing correctness at negligible cost, rather than betting on rarity.Misconception: that a low probability event can be ignored in a system design. Correctness mechanisms are sized by consequence-of-failure, not just frequency.
Problem 3 · medium
Why does detaching values into a value log help low-v/k (small value) workloads less than high-v/k (large value) workloads, per the paper's sensitivity study (Section 5.8)?
Show answer
The value log's benefit is avoiding repeatedly moving large values during compaction. If values are already small (low-v/k), even a small log rarely fills up, so log-triggered compactions are infrequent and there's little to save. As values get larger (high-v/k), the log fills faster and would trigger compactions more often without detachment — so keeping values separate saves proportionally more.Misconception: that the value log is AnyKey's "core" innovation for the low-v/k problem. It's actually aimed at controlling compaction overhead broadly — the metadata-shrinking design (groups + hashes) is what solves the low-v/k problem specifically.
Problem 4 · hard
A compaction chain occurs more often under high-v/k workloads than low-v/k ones. Explain why, tracing through what a log-triggered compaction actually moves.
Show answer
A log-triggered compaction merges a source level's values (currently in the log) into the destination level's data segment groups. Under high-v/k, those values are large, so merging them adds a lot of bytes to the destination level quickly — often enough to push it over its own size threshold mid-merge, triggering a second, tree-triggered compaction immediately (the "chain"). Under low-v/k, values are small, so the same merge adds much less bulk, rarely tipping the destination level over.Misconception: that grouping and value separation always trade off cleanly. The interaction between the two mechanisms (a log-triggered merge dumping into a level that's independently near its tree-trigger threshold) is what creates the chain — neither mechanism alone causes it.
Problem 5 · medium
The paper explicitly rejects using Bloom or Cuckoo filters to verify key membership, even though they'd use less DRAM than the hash list. Why?
Show answer
Building (and maintaining, as the tree changes) Bloom/Cuckoo filters requires intensive computation, and a KV-SSD's internal processor is a small, weak embedded core (e.g. a 1.2GHz ARM Cortex-A53) — that computation would burden the SSD's limited internal resources. PinK's authors identified the same problem and made the same choice. AnyKey instead spends a bit more DRAM (the hash list, filled from whatever space remains) to get membership-checking for free via simple binary search.Misconception: that the "best" data structure is whichever uses least memory. On a resource-constrained embedded core, compute cost can matter more than memory footprint.
Problem 6 · easy
In the multi-workload partitioning experiment (Section 5.10), AnyKey improves W-Pink's 99.9th-percentile tail latency by 14% but ZippyDB's by 216%, versus PinK. Given their key/value sizes (Table 2: W-Pink 32B/1024B, ZippyDB 48B/43B), explain the gap.
Show answer
W-Pink is a high-v/k workload (ratio 32) — PinK's metadata for it was already small and mostly DRAM-resident, so there's little headroom for AnyKey to improve on tail latency. ZippyDB is a low-v/k workload (ratio ~0.9) — exactly the regime where PinK's metadata overflows into flash and tail latency balloons, so AnyKey's metadata-capping fix has a huge effect.Misconception: that AnyKey is uniformly "better," so gains should look similar across workloads. Its advantage is concentrated precisely where PinK's design assumption (tiny keys) fails — high-v/k workloads see only modest gains because PinK wasn't broken there to begin with.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most.

Q1What exactly is a "low-v/k" workload?▾
One where the value-to-key size ratio is low — keys are comparably sized to, or bigger than, values. Examples from the paper: Cache15 (Twitter, 38B key/38B value, ratio 1.0), Crypto1 (76B/50B, ratio 0.66), RTDATA (24B/10B, ratio 0.42). Contrast with "typical" benchmarks like YCSB (20B/1000B, ratio 50).
Q2Why does a bigger key cause more problems than a bigger value?▾
Because metadata (the DRAM-resident map used to locate data) stores keys, not values — the value itself is only read once you already know where it is. A bigger key directly enlarges every metadata entry that references it; a bigger value only affects the (much cheaper, flash-resident) data segment.
Q3How does AnyKey guarantee metadata never exceeds the DRAM?▾
It doesn't grow metadata per key at all — level list entries exist per data segment group, and the number of groups is fixed by flash capacity ÷ group size, independent of key size. The remaining DRAM space is then filled, best-effort, with hash lists (dropped for lower levels first if space runs out) — so total DRAM usage is bounded by construction, not by workload.
Q4What happens if the hash list can't cover every level?▾
For levels without a hash list, AnyKey can't rule out a false match before reading flash — so occasionally (rarely, in measured workloads) it takes one extra flash access to confirm a key isn't actually in a candidate group. This is the same problem PinK has for every key, all the time; AnyKey just narrows it to a residual case.
Q5Why introduce a value log instead of just living with bigger data segment groups?▾
Without the log, every LSM-tree compaction would physically re-sort and rewrite every value in the affected data segment groups — expensive when values are large or updates frequent. The log lets recently-written/updated values sit untouched through ordinary tree-triggered compactions, only migrating into groups when the log itself needs reclaiming.
Q6Does AnyKey use more flash writes overall because of the value log?▾
No — AnyKey+ reduces total page writes by 50% on average versus PinK (Fig. 13), because avoiding repeated whole-group rewrites during ordinary compaction outweighs the log's own eventual reclaim writes.
Q7What's the difference between AnyKey and AnyKey+?▾
Same core data structures. AnyKey+ adds one behavioral fix: during log-triggered compaction, it monitors the destination level's size and stops merging values in once a threshold is crossed (writing the rest back to the log), and it targets the level with the most invalid log values rather than simply the most log values — both aimed at preventing compaction chains, which mainly hurt high-v/k (large-value) workloads.
Q8Does AnyKey ever lose to PinK?▾
The base AnyKey (without the AnyKey+ fix) can lose IOPS to PinK on some high-v/k workloads, because it's prone to compaction chains there. AnyKey+ closes that gap and wins on both high-v/k (+15% IOPS) and low-v/k (+315% IOPS) workloads, per the paper's results.
Q9Does grouping hurt or help range queries?▾
It helps, and more so for longer ranges. Because a data segment group holds many sorted, physically-co-located KV pairs, a range query touches only a few flash pages. PinK's KV pairs are scattered across flash, so a range query there touches roughly one page per key. AnyKey also precomputes per-key location info in each group specifically to serve range queries without needing to re-sort by key at query time.
Q10Can AnyKey and PinK coexist for different workloads on the same physical SSD?▾
Yes — the paper demonstrates a two-partition scenario where each partition is managed by an independent firmware (PinK or AnyKey), letting a low-v/k workload get AnyKey's benefit and a high-v/k workload run under either, without redesigning the whole device.
Q11Is this evaluated on real KV-SSD hardware?▾
No — commodity KV-SSD hardware with open internals isn't publicly available, so the paper builds an emulation testbed (FEMU, a flash emulator) plus uNVMe/FIO to generate KV requests bypassing the normal host I/O stack, implementing both PinK and AnyKey inside it for a controlled, apples-to-apples comparison.
