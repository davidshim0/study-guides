ISCA 2025 · A Field Guide

Letting every cache row be compute or storage, whichever it's needed for

In-cache computing turns SRAM arrays into tiny vector processors — but existing designs carve out half a cache forever, whether or not the app is using it. This is the plain-English story of MagiCache, which lets that decision happen one cacheline at a time, at runtime.

📄 "MagiCache: A Virtual In-Cache Computing Engine" · Fan, Cui, Li, Wang, Li 🎓 Cache/LRU/tag basics assumed — primers cover the in-cache-computing-specific parts ⏱ ~30 min read
🧮

Don't reserve whole SRAM arrays for compute up front — let each cacheline, at runtime, be a vector-register segment or a normal cacheline, based on what's actually in use right now.

Before you begin

Seven ideas specific to in-cache computing

You already know caches, sets/ways, tags, and LRU. These primers cover the pieces that are specific to SRAM-based in-cache computation and the RISC-V vector ISA that MagiCache builds on.

cacheline / storage space computing line / vector register virtual engine machinery SplitCache / array-level baseline
1Bit-line computation: how an SRAM array computes without leaving itself▾

Normally, activating one word-line reads one row out to the sense amplifiers. Bit-line computation activates two word-lines at once: both rows' bits fight it out on the shared bit-lines, and the sense amplifiers read off the analog result as logic AND and NOR of the two rows. Add a bit more peripheral circuitry (adders, shift registers, latches) around the array and you get addition, multiplication, even floating point — all computed inside the array, never leaving it for the processor.

Now you're ready: "in-cache computing" means treating cache rows as inputs to this bit-line trick, not treating the cache as a place to just store operands.
2The in-cache computing lineage: Compute Cache → Neural Cache → EVE/Duality Cache▾

Compute Cache first showed logic/search/copy in SRAM arrays. Neural Cache added fixed-point arithmetic with a bit-serial layout (one element spread down a bit-line) to accelerate neural nets. Duality Cache and EVE — MagiCache's direct baseline — went further: they pre-configure the computing arrays as a bank of vector/SIMT registers and run a real ISA (PTX-like, or RISC-V vector) against them.

Now you're ready: EVE is exactly the state of the art MagiCache is compared against — it's the "SplitCache" baseline throughout this guide.
3Array-level partitioning — the problem this paper attacks▾

EVE's approach: pick some whole SRAM arrays, dedicate every row of them to computing (as vector registers), and leave the rest as ordinary cache. This is a partition at the granularity of an entire array — coarse and static, fixed before the program runs.

Now you're ready: "array-level" = whole arrays committed to one role for the whole run. MagiCache's alternative is "cacheline-level" = individual rows switch roles at runtime — that's the entire contribution of this paper in one contrast.
4RISC-V vector ISA basics: vl, vtype, and access patterns▾

A vector instruction like vadd.vv operates on a whole vector register at once. vset(i)vl(i) sets the effective vector length (how many elements are actually active) and vtype (element width, etc.) in control-status registers. Memory accesses come in three shapes: unit-stride (one contiguous run — coalesces nicely into few cachelines), strided (fixed skip between elements — scatters across many lines), and indexed/gather (address per element — worst case).

Now you're ready: strided accesses (used by k-means and backprop in the evaluation) will matter a lot later — they can't be coalesced the way unit-stride can.
5MSHRs and why "bursty" vector accesses are a problem▾

A Miss Status Handling Register (MSHR) tracks one in-flight cache miss. The evaluated L1 caches have 16 MSHRs each, while the L2/LLC has 32. A vector instruction can touch hundreds or thousands of elements in one shot — if many miss simultaneously, they compete for that small, fixed pool (32 at a typical L2) and everything else stalls until some free up.

Now you're ready: in-cache computing multiplies this problem, because instead of one core generating bursts, dozens of computing arrays can all miss on their vector-load segment at once.
6Liveness analysis — a compiler concept borrowed for hardware▾

Compilers already compute, for every variable, the range of instructions across which its value might still be read (its "live range") — this is exactly how register allocators decide when a register can be reused. MagiCache's compiler pass reuses this unmodified to find where each vector register's last use is, and inserts an instruction there to release it.

Now you're ready: this is why the paper claims "negligible overhead" for figuring out register lifetimes — it's not new analysis, it's a byproduct of analysis compilers do anyway.
7Tag bits beyond valid/dirty: presence and coherence for compute regions▾

A vector engine sitting at L2 and a scalar core's L1 cache can both want the "latest" copy of a line. Vector machines solve this the same way MagiCache does: a presence bit per L2 line records whether the scalar core (L1) or the vector engine currently owns the freshest copy; crossing that boundary triggers a snoop to fetch/invalidate the other side's copy.

Now you're ready: MagiCache adds exactly one such bit (plus one "computing" bit) to every L2 tag — that's the entire hardware cost of making cachelines dual-purpose.
The whole story in one place

MagiCache in a nutshell

The problem, the fix, and how the pieces connect.

Existing in-cache computing architectures (Neural Cache, Duality Cache, EVE) statically dedicate some whole SRAM arrays to computation, and the rest to storage. Two problems fall out of this: first, that fixed ratio can't be right for every app — a matmul-heavy kernel wants more compute capacity, a cache-hungry one wants more storage, and the paper shows the ideal ratio is 62.5% for one benchmark and 50% for another. Second, most vector programs only actually use a couple of the 32 architectural registers, so within the "computing" half of the cache, most rows sit idle anyway.

MagiCache's fix is cacheline-level partitioning: each SRAM array becomes a fused array where any row can be either a normal cacheline or a computing line (a vector-register segment), switchable via two extra tag bits. A virtual engine sits above the physical arrays and, using a vector register mapping table (VRMT), allocates rows to registers lazily — only when an instruction actually uses them — so unused registers cost no cache capacity (the VRMT itself is fixed-size hardware overhead regardless of how many registers a kernel uses). Finally, an instruction chaining technique lets each fused array execute asynchronously once its own data is ready, instead of all arrays waiting in lockstep for the slowest one's memory access to finish.

The payoff: MagiCache (with chaining) is 1.19×–1.61× faster than EVE-style SplitCache (geomean 1.39×), lifts average cache utilization from 55.9% to 97.1%, cuts miss rates 10%–40% across access patterns, and reduces average memory-access time 2%–27% — for just 6.5 KB of extra storage in the evaluated L2.

🧮 Key takeaways

  • EVE-style architectures partition by whole SRAM array; MagiCache partitions by individual cacheline.
  • No static ratio is right for every app — matmul wants ~62.5% compute capacity, backprop wants ~50%.
  • Most vector programs use only a few of 32 registers, so array-level schemes waste most of their "computing half."
  • Lazy initialization (via a VRMT) allocates cache rows to registers only on actual first use.
  • Instruction chaining lets fused arrays run asynchronously, cutting synchronization stalls ~45%.
  • Result: 1.19×–1.61× speedup (geomean 1.39×), 97.1% average cache utilization, for 6.5 KB extra storage.
Six everyday pictures

How to think about MagiCache

Read in any order — each ends with where the picture stops being literally true.

The core idea · Array vs cacheline granularity

Booking whole floors, vs. booking desks

EVE's approach books entire floors of a building as "office" and the rest as "storage," permanently, before anyone moves in. Most of those office floors sit empty most of the day. MagiCache instead lets any individual desk (cacheline) switch between office and storage use as needed — the building's capacity is the same, but almost nothing sits idle.

Where it breaks: switching a real desk's function takes effort; MagiCache's row-role switch costs just a few tag bits and 2 cycles — the analogy undersells how cheap the conversion really is.
Why utilization is low · Sparse register use

A toolbox where you only ever grab two tools

You own a 32-slot toolbox but every job only needs the hammer and the screwdriver. If your workshop reserves a whole shelf-width for "toolbox," 30 slots sit empty regardless. Vector programs are the same: matrix multiply in the paper's example only touches registers v0 and v1. Lazy initialization means MagiCache only ever "shelves" the tools you actually pick up.

Where it breaks: some kernels genuinely use many registers at once (loop unrolling, blocking) — then the toolbox really is full and there's little idle space left to reclaim.
The mechanism · The virtual engine & VRMT

A coat-check ticket, not an assigned locker

An assigned locker system reserves locker #7 for you whether or not you show up with a coat. A coat-check counter instead hands you a numbered ticket and puts your coat wherever there's room right now. The vector register mapping table (VRMT) is that ticket system: register v0's segment 1 isn't nailed to a fixed row — the VRMT just remembers which row currently holds it, so allocation stays flexible.

Where it breaks: a coat-check attendant searches intelligently; MagiCache's allocator (FFA) just scans circularly for the first free or available slot — it's simple by design, not clever.
Why FFA, not LRU · Huge candidate pools

Grabbing the nearest empty locker, not the least-used one

In a gym with only 8 lockers, it's worth remembering exactly which one hasn't been touched in the longest time. In a gym with 256 lockers, that bookkeeping gets expensive fast — grabbing the first one you see that's empty is nearly as good and far cheaper. That's why the allocator scans for a free-first, then any-available row (FFA) instead of tracking true LRU/pseudo-LRU order across all 256 rows of a fused array.

Where it breaks: FFA isn't free of cost — the paper measures it against pseudo-LRU and finds it loses less than 1% in L2 miss rate. It's "nearly as good," not identical.
Instruction chaining · Asynchronous execution

An assembly line where fast stations don't wait for slow ones

Without chaining, every station on the line must finish its current part before any station starts the next one — so one slow memory fetch stalls all the others in lockstep. Instruction chaining lets each fused array move on to its next instruction as soon as its own data is ready, only re-synchronizing when instructions actually conflict (a length change, a data shuffle, or overlapping stores).

Where it breaks: the assembly line still can't skip ahead across those three conflict types — a config change or a cross-element shuffle forces every station to wait, same as before.
Coherence · The presence bit

A "who has the master key" sign on the door

A scalar core and the vector engine both keep their own working copy of a room's contents (L1 vs. L2). A presence bit is like a sign on the door saying who currently holds the master key: if the vector engine wants in but the scalar side holds the key, it has to fetch the latest copy and take the key back before proceeding.

Where it breaks: a physical sign doesn't stop someone from also editing through a side door — that's why MagiCache still needs explicit fence instructions to stop the out-of-order scalar core from racing ahead of a pending vector read.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams.

1 · The cacheline-level architecture — two extra tag bits

MagiCache adds a computing bit (C) and a presence bit (P) to every L2 tag. Converting a cacheline into a computing line is a 4-step process: evict it if dirty, clear its other indicator bits, mark its LRU bits invalid (so the replacement policy skips it), then set C=1. Converting back just clears C and marks the line least-recently-used again.

2 · The virtual engine — lazy allocation via the VRMT

The virtual engine sits between the scalar core's decoded vector instructions and the physical fused arrays. Its vector register mapping table (VRMT) is a 32-row × Q-column table (32 registers × Q segments each); each entry records a valid bit and the row index currently holding that segment. Segment j of every register is always mapped to fused array (j mod N) — though the specific row it occupies within that array is allocated dynamically and tracked by the VRMT — so all 32 registers' segment j can compute together in parallel.

MaxVectorLength = Q × W        # W = cacheline width in bits
Size(VRMT) = 32 × Q × (1 + log₂H) bits  # H = rows per fused array
MaxOccupancy = 32 × Q / (N × H)       # N = number of fused arrays

Allocation is lazy: a register's segments are only claimed from the array (via the FFA scan described in the primers) the first time an instruction actually reads or writes them, and a compiler liveness pass inserts release instructions at the point each register is last used. Unused registers — for most vector kernels, the majority of the 32 — simply have invalid VRMT entries and occupy no cache rows; the VRMT itself is fixed-size storage regardless of how many registers are in use.

3 · Instruction chaining — breaking the lockstep

Without chaining, every fused array must finish an instruction (including all its MSHR-limited memory traffic) before the group can commit and move to the next one — so the whole engine runs at the pace of its slowest array. Chaining packs adjacent, conflict-free instructions into a group and lets each fused array execute the entire group independently, synchronizing only at group boundaries.

4 · Guardrails — associativity floor, coherence, OS integration

Two safety mechanisms keep cacheline-level allocation from backfiring. First, a minimum-associativity threshold per set: once a set's available (non-computing) associativity hits that floor, the allocator stops picking cachelines from it, so no set is starved down to zero storage lines. Second, the presence bit (see primer 7) manages L1/L2 coherence between scalar and vector accesses, backed by fence instructions so the out-of-order scalar core can't race ahead of a pending vector read/write.

For OS context switches, MagiCache exposes a 32-bit read-only CSR, vreg_valid, recording which of the 32 vector registers are actually initialized. Save/restore only touches valid registers — without this, the OS would have to conservatively save/restore all 32 every switch, erasing the benefit of lazy initialization.

Follow the numbers, step by step

Worked examples

Four calculations, using the paper's own configuration numbers and equations.

① Deriving the VRMT size and occupancy for Chain-4

Chain-4 (Table 4) uses N=32 fused arrays, each H=256 rows, cacheline width W=512 bits, and k=4 segments-per-array-per-register (the paper's stated max for a 256-row array). What are its max vector length, VRMT size, and occupancy?

  1. Segments per register, Q = k × N = 4 × 32 = 128.
  2. Max vector length = Q × W = 128 × 512 = 65,536 bits (2048 32-bit elements) — matches Table 4 exactly.
  3. VRMT entry size = 1 + log₂H = 1 + log₂256 = 1 + 8 = 9 bits (1 valid bit + 8-bit row index).
  4. VRMT size = 32 × Q × 9 bits = 32 × 128 × 9 = 36,864 bits = 4608 bytes = 4.5 KB — exactly the "4.5 KB for the vector register mapping table" the paper reports.
  5. Max occupancy = 32Q / (N×H) = (32×128)/(32×256) = 4096/8192 = 50% — matches Table 4's Fused-4/Chain-4 occupancy.
🧮
Insight: the paper's headline "6.5 KB" overhead = this 4.5 KB VRMT + 2 KB of tag bits (computing + presence bits across the L2). Everything traces back to three simple equations.

② Why Chain-4 beats Split-8 by 1.39× (geomean)

Table 6 reports Chain-4's geomean speedup over Split-8 as 1.39× (Fused-4, without chaining: 1.31×). Where does that gap come from?

  1. Doubling parallelism: Split-8 uses 16 computing arrays; MagiCache's fused-array pool has 32. Fig. 9 shows Split-8's computation time is roughly double every other configuration's — inversely proportional to array count.
  2. That alone gives Fused-4 its 1.31× geomean gain over Split-8, before chaining is even applied.
  3. Instruction chaining removes lockstep waiting: §6.1 reports it cuts average synchronization time by 45.3%, on top of the parallelism gain.
  4. Combined effect: 1.31× (parallelism) → 1.39× (parallelism + chaining) geomean — the extra 8 points come almost entirely from that 45.3% cut in sync stalls translating into fewer total cycles.
  5. Per-benchmark spread (Table 6): matmul gains the most (1.50× → 1.61×) because it's compute-dense with clean unit-stride access; backprop gains the least (1.12× → 1.19×) because its strided accesses limit how much chaining can overlap.
💡
Two independent levers — more usable compute parallelism, and less time spent waiting in lockstep — stack multiplicatively, not additively, which is why chaining's contribution looks small in isolation (10% avg) but compounds with the parallelism gain.

③ Stacking up the area overhead

The paper reports several overheads separately. What's the total, relative to a vanilla L2 cache?

  1. Fused-array circuit overhead: one 128×256 sub-array costs 17.7% extra area over vanilla SRAM; because a standard 256×256 fused array shares circuits between two sub-arrays, this halves to 8.9%.
  2. SplitCache (EVE-style) baseline: converting half the arrays to computing arrays costs 6.0% area over a conventional L2 — this already includes the 8.9% fused-array cost applied to only half the cache.
  3. MagiCache's addition on top of SplitCache: 6.5 KB storage (VRMT + tag bits) + virtual engine control logic (~1%) = 6.8% additional area over SplitCache.
  4. Compounding the two reported percentages (not stated directly in the paper, but implied by "SplitCache: +6.0% over L2" and "MagiCache: +6.8% over SplitCache"): 1.060 × 1.068 ≈ 1.132, i.e. roughly +13% over a vanilla L2 cache, total.
  5. Sanity check on the 6.5 KB figure: from Worked Example ①, VRMT ≈ 4.5 KB; the remaining 2 KB is the computing + presence tag bits added across all L2 lines.
⚠
Caveat: step 4's ~13% combined figure is this guide's arithmetic, not a number stated explicitly in the paper — the two percentages describe different baselines (L2 vs. SplitCache) and the paper never adds them for you.

④ Why backprop and k-means barely move as vector length grows

Table 7 shows Chain-4 raises average vector MSHR usage from 5.00 (Split-8) to 7.76 — a gain of 2.76 entries. But backprop's runtime barely changes across Chain-1/2/4. Why?

  1. Unit-stride coalesces: the paper states a unit-stride access in Fused-1 generates 32 coalesced memory requests (one per fused array).
  2. Strided accesses don't coalesce: the same configuration's strided access "can generate up to 512 requests with a large enough stride" — 16× more traffic per instruction.
  3. backprop and k-means use strided accesses (Table 5), so their elements scatter across many separate cachelines that can't be merged into one memory request.
  4. Result: these two applications' fused arrays can't overlap their memory requests with each other — they run "near-serially" regardless of how long the vector is, so total load/store time stays roughly fixed as Chain-1 → Chain-4 increases vector length.
  5. Confirmed by Table 7: backprop's MSHR usage barely changes across Chain-1 (13.55), Chain-2 (13.50), Chain-4 (13.52) — essentially flat, unlike every unit-stride benchmark.
🧮
Insight: MagiCache's gains from more parallelism and longer vectors are real, but access pattern gatekeeps how much of that parallelism can actually be exploited in memory.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
A vector program uses only registers v0 and v1 throughout its whole run. Under EVE-style SplitCache with 50% of arrays fixed as computing arrays, how much of that computing half is actually doing useful work?
Show answer
Very little. SplitCache statically divides the computing arrays' full capacity among all 32 architectural registers whether or not they're used — so with only v0 and v1 active, roughly 30/32 of the reserved computing capacity sits idle for the whole run.Misconception: that "50% dedicated to compute" means 50% of the cache is doing computation. It means 50% is reserved for it — actual usage depends entirely on how many registers the kernel touches.
Problem 2 · medium
Using the same equations as Worked Example ①, compute the VRMT size, max vector length, and occupancy for a Fused-2/Chain-2 configuration (N=32, H=256, W=512 bits, k=2).
Show answer
Q = k×N = 2×32 = 64. Max vector length = Q×W = 64×512 = 32,768 bits (matches Table 4). VRMT size = 32×Q×9 bits = 32×64×9 = 18,432 bits = 2304 bytes = 2.25 KB. Occupancy = 32Q/(N×H) = (32×64)/(32×256) = 2048/8192 = 25% (matches Table 4).Misconception: assuming VRMT size scales with occupancy percentage rather than with Q directly — it's linear in Q (and thus in k), which happens to track occupancy here because N and H are fixed.
Problem 3 · medium
Why doesn't MagiCache use true LRU or pseudo-LRU to pick which cacheline becomes a new vector-register segment, given that LRU is the cache's own replacement policy elsewhere?
Show answer
LRU/pseudo-LRU tracking is normally cheap because a cache replacement policy only chooses among 2-16 ways in one set. The allocator here instead searches an entire fused array — typically 256 cachelines — where maintaining true recency order would need significant extra state and logic. The simpler find-first-available (FFA) policy scans existing tag states with no extra bookkeeping, and the paper measures its cost at under 1% additional L2 miss rate versus pseudo-LRU — an acceptable trade.Misconception: that a "better" algorithm is always worth using. FFA is worse than pseudo-LRU here, but the candidate pool is 16-32× larger than a normal replacement decision, so the bookkeeping cost of the better algorithm outweighs its small accuracy gain.
Problem 4 · hard
jacobi-2d and pathfinder gain little from instruction chaining, and Chain-1 even loses ~1% versus Fused-1 for these two. Explain why, referencing what these two benchmarks have in common.
Show answer
Both applications contain cross-element "slide" instructions (Table 5) that shuffle data between fused arrays — one of the three conflict types (alongside config changes and interleaved stores) that force a group boundary and block chaining. With little chainable work between forced syncs, the benefit of asynchronous execution is small. At Chain-1's shortest vector length, the extra bookkeeping for asynchronous execution can even introduce discontinuous, slightly-longer-latency memory accesses than the simpler lockstep Fused-1 scheme, causing the small 1% regression.Misconception: that instruction chaining is a strictly-better drop-in optimization. It only helps when there's a run of conflict-free instructions to chain — permutation-heavy kernels have few such runs, and can occasionally pay a small overhead cost instead.
Problem 5 · medium
The scalar core is out-of-order and vector instructions without writeback don't block its scoreboard. Construct a hazard this creates, and explain MagiCache's fix.
Show answer
Consider a vector read immediately followed (in program order) by a scalar write to the same location. Because the vector read doesn't block the scalar scoreboard, the out-of-order core might execute the scalar write before the slower vector read actually completes — so when the vector read finally runs, it sees the write's newer value instead of the value that should have been visible before the write, violating program order. This is exactly the scalar-write-after-vector-read hazard the paper describes. MagiCache's fix is a fence instruction: when the scalar core hits a fence, it must wait until the MagiCache backend finishes all outstanding vector instructions before proceeding.Misconception: assuming out-of-order scalar execution and asynchronous vector execution naturally stay consistent because both target the "same" cache. Ordering has to be explicitly enforced (via fences); the hardware doesn't infer it.
Problem 6 · easy
A set's available (non-computing) associativity has hit MagiCache's configured minimum threshold. What happens the next time a vector instruction wants a new segment from that set, and why does this rule exist?
Show answer
The allocation policy will not select any cacheline from that set for conversion — it looks elsewhere. The rule exists so that no single set gets starved down to zero (or near-zero) storage associativity by heavy vector-register demand, which would badly hurt any scalar or vector accesses that happen to map to that same set.Misconception: that lazy allocation alone guarantees fair space sharing. Lazy allocation controls total occupancy, but without a per-set floor, one hot set could still be entirely consumed by computing lines.
Problem 7 · hard
Two-core evaluation (§6.2) shows Chain-4 completing 11 loop iterations of k-means+mmul in the same 1500-cycle window where Split-8 completes 9. Table 8 says Chain-4's cache utilization averages 97.1% vs. Split-8's 55.9%. Are these two facts describing the same thing?
Show answer
No — they're related but distinct. Cache utilization (Table 8) measures what fraction of occupied cache space holds data actually being used at a moment in time; it's a space-efficiency metric. The 11-vs-9-iteration result is a throughput/performance metric. Higher utilization is the cause: because MagiCache reclaims unused reserved-register space as real cache, both the vector k-means and the scalar mmul suffer fewer evictions and misses, which is what lets more loop iterations complete in the same wall-clock window.Misconception: treating "utilization" and "speed" as interchangeable. Utilization is what MagiCache directly controls (via cacheline-level allocation); speed is the downstream consequence of fewer misses that follows from it.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What's the actual difference between "array-level" and "cacheline-level" partitioning?▾
Array-level (EVE, Duality Cache): whole SRAM arrays are permanently dedicated to computing or storage before the program runs. Cacheline-level (MagiCache): any individual row within an array can be either role, switchable at runtime by flipping a tag bit. Same physical circuits either way — the difference is entirely in the granularity and timing of the decision.
Q2Why does MagiCache use a bit-parallel data layout instead of bit-serial like Neural Cache?▾
Bit-parallel lays out an element the same way ordinary cachelines do (all its bits on one row), so a computing line and a cacheline share an identical physical layout. That's what makes cheap, tag-bit-only conversion between the two roles possible. Bit-serial (transposed, spread down a bit-line) gets higher raw throughput but would require a costly data transpose to move between cache and register form.
Q3What does the virtual engine actually add on top of a normal cache controller?▾
Four things: an instruction queue (so vector instructions don't block the scalar core), vector CSRs (vl, vtype), a request generator (turns one vector instruction into per-element memory addresses), and the VRMT (tracks which physical row backs each register segment right now). None of it changes how normal scalar cache accesses work.
Q4How does MagiCache stop the scalar core and vector engine from seeing stale data from each other?▾
A presence bit per L2 line records which side (scalar L1 or vector engine) currently holds the freshest copy. Crossing that boundary triggers a snoop that fetches the latest data and invalidates the stale copy — the same coherence approach used in classic vector machines like Tarantula.
Q5Why not just use LRU for choosing which cacheline becomes a vector register?▾
LRU/pseudo-LRU over a whole 256-row fused array would need real extra state and update logic. The simpler find-first-available (FFA) scan needs none — it just reads existing tag bits — and costs under 1% extra L2 miss rate versus pseudo-LRU, which the authors judge an acceptable trade for the much lower overhead.
Q6How big is the overhead, concretely?▾
6.5 KB of extra storage in the evaluated L2 (4.5 KB VRMT + 2 KB of tag bits), plus about 8.9% extra area on each fused array's peripheral circuits and roughly 1% for the virtual engine's control logic — on top of SplitCache's own 6.0% area overhead versus a vanilla L2.
Q7Does instruction chaining always help?▾
No. It helps whenever there's a run of instructions free of the three conflict types (config changes, cross-element permutes, interleaved stores) to chain together. Kernels dominated by slide/gather instructions (jacobi-2d, pathfinder) see little benefit, and the shortest vector-length configuration can even lose ~1% versus non-chained execution on those two.
Q8What happens to vector register state on an OS context switch?▾
MagiCache exposes a 32-bit CSR, vreg_valid, listing which registers are actually initialized. The OS saves/restores only those, preserving the benefit of lazy initialization. Without this CSR, the OS would have no choice but to conservatively save/restore all 32 registers every switch.
Q9Is this tied specifically to RISC-V's vector extension?▾
The evaluation implements the RISC-V vector ISA specifically, but the underlying contribution — cacheline-level fused arrays plus a virtual engine for lazy space management — is presented as reusable across "various data layouts, peripheral circuits, and programming frameworks," not tied to one ISA.
Q10What are the paper's acknowledged limitations?▾
Strided and indexed memory accesses (backprop, k-means) don't coalesce, so they run near-serially regardless of vector length or chaining, capping the achievable speedup for those access patterns. Cross-element permutation instructions similarly limit how much instruction chaining can overlap. The FFA allocation policy also costs a small (<1%) miss-rate penalty versus a full LRU-style policy it deliberately avoids implementing.

OccupancyThe static fraction of total cache rows reserved for vector registers, per Table 4's configurations (12.5%–50%).

Related work cited in the paper

Compute Caches medium

Aga et al. · HPCA · 2017

The first in-cache computing architecture: logic, search, compare, and copy operations directly in SRAM arrays.

Neural Cache: Bit-Serial In-Cache Acceleration of DNNs medium

Eckert et al. · ISCA · 2018

Introduces the bit-serial layout and fixed-point arithmetic in the L3 cache — the layout MagiCache deliberately avoids in favor of bit-parallel.

Duality Cache for Data Parallel Acceleration hard

Fujiki, Mahlke, Das · ISCA · 2019

Floating-point in-cache arithmetic and a GPU-like SIMT framework — one of MagiCache's two direct baselines.

EVE: Ephemeral Vector Engines hard

Al-Hawaj et al. · HPCA · 2023

Vector-register pre-configuration and micro-code execution for RISC-V vector extensions — the exact "SplitCache" baseline MagiCache is measured against.

BLADE: An In-Cache Computing Architecture for Edge Devices medium

Simon et al. · IEEE TC · 2020

Local bit-lines to prevent data corruption in multi-row access without reducing operating frequency.

Tarantula: A Vector Extension to the Alpha Architecture medium

Espasa et al. · ISCA · 2002

The classic vector-machine coherence design (presence-bit-style scalar/vector ownership) that MagiCache's coherence scheme follows.
