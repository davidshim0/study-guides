Stopping secrets from programming the machine hiding in your cache

Every load your program issues also feeds a second, invisible computer made of cache state. This is the plain-English tour of a type system that refuses to let secrets steer it.

📄 Gollamudi, "Making Weird Machines Untypeable" · PLOS'26 🎓 Assumes cache/architecture fluency — focuses on the PL/security machinery ⏱ ~25 min read

Before you begin

Quick glossary, then eight primers

You already know caches and TLBs cold. What's new here is the PL/security apparatus layered on top — symbols and vocabulary first, then the concepts they encode.

IFCInformation-Flow Control — type systems that track how secret (H) data can influence public (L) outputs.
WMWeird machine — a computation that runs on hidden state not part of the intended programming model.
ℓ, L ⊑ HA two-point security lattice: Low (public) below High (secret); ⊑ is "no more secret than."
pcProgram-counter label — tracks whether current control flow already depends on a secret.
ΓTyping context mapping variables to security labels.
ε (effect)A static term approximating the set of weird-machine traces a command may induce.
Fill(s) / Probe(s)Weird-machine actions: install cache set s (Fill) or time it (Probe).
lev(s)Whether cache set s is attacker-observable (L) or hidden (H).
π_LLow projection — erases H-labeled trace events, leaving what the attacker actually sees.
⇓_A / ⇓_WBig-step judgments for architectural execution and induced weird-machine execution, respectively.
Low / public / accepted the weird machine itself type-and-effect machinery High / secret / rejected
1Side-channel IFC vs. this paper's question▾

Standard timing-sensitive IFC asks: "can an attacker observe a difference caused by a secret?" It models one channel (say, execution time) and proves secrets don't move it. This paper asks a different question: what computation does the program induce on the hidden machine, not just whether one particular channel happens to reveal a difference. The theorem it actually proves is still stated relative to a fixed low-observer projection π_L; being secure against every conceivable future projection at once is a further, more speculative goal the paper only sketches.

Now you're ready: the paper's whole reframing is: stop reasoning about observations one channel at a time; reason about the induced computation directly.
2What a "weird machine" is▾

A weird machine is a computational device that exists by accident of implementation, not by design — its state evolves in response to inputs it was never "programmed" to accept. Caches, branch predictors, and speculative-execution buffers all qualify: programmers never write to them directly, yet their state is a deterministic function of ordinary execution.

Now you're ready: this paper's weird machine is deliberately the simplest possible one — cache residency — so the type theory stays tractable.
3Reading big-step judgments ⟨c, σ⟩⇓σ′▾

"⟨c, σ⟩ ⇓ σ′" means: running command c starting in state σ terminates in state σ′. The paper uses two parallel versions of this judgment — ⇓_A for ordinary architectural execution, and ⇓_W, which additionally produces a trace t of weird-machine actions: ⟨c, σ⟩⇓_W⟨σ′, t⟩.

Now you're ready: every rule you'll see in Section 4 (How It Works) is just one of these two judgments, defined structurally over the command.
4The two-point security lattice and the pc label▾

Labels ℓ ∈ {L, H} with L ⊑ H form the simplest possible IFC lattice. The program-counter label pc tracks "have we already branched on a secret?" Once inside a secret-guarded branch, pc becomes H, and that H infects the labels used to type everything nested inside it (via pc ⊔ ℓ).

Now you're ready: pc is exactly how "implicit flows" are usually caught in IFC — and here it also gates whether weird-machine effects need extra scrutiny.
5Effect systems, briefly▾

An effect system attaches to each typed term a description of the side effects it may cause — allocation, I/O, exceptions — going back to Lucassen & Gifford and Talpin & Jouvelot. This paper repurposes that machinery: the "side effect" being tracked isn't I/O, it's the trace of actions induced on the cache-residency weird machine.

Now you're ready: when you see "Γ; pc ⊢ c : ε", read ε exactly like any other effect annotation — an overapproximation of what happens on the side.
6Noninterference, the classical statement▾

Classical noninterference: if two initial states agree on all low (public) variables, then running the same well-typed program from each must produce low-equivalent final states — secrets cannot influence what a low observer sees. This paper proves the same shape of theorem, but for induced weird-machine traces instead of final variable states.

Now you're ready: "weird-machine noninterference" (Theorem 2) is architecturally the same proof strategy, retargeted at a new kind of output.
7Why loads are special: address vs. value▾

A memory load x := [a] does two things: it reads a value from address a into x (an architectural effect), and it touches the cache set associated with a (a weird-machine effect). Crucially the cache effect depends only on the address, not the loaded value — so a load can leak through the cache even when the value it fetches is never used or is itself public.

Now you're ready: this is exactly why the type system gives every load a nontrivial effect Fill(s), regardless of the label on the value being loaded.
8Why loops are a distinct threat▾

A secret-guarded conditional picks between exactly two traces. A secret-guarded loop picks among infinitely many — the iteration count itself becomes an attacker-visible signal (a classic timing/counting channel). The type system needs a rule general enough to catch this, not just the two-branch case.

Now you're ready: Section 5's while-rule is the paper's answer — it's stricter than the if-rule precisely because the space of possible traces is unbounded.
The whole story in one place

Two machines, one program

The reframing, the concrete example that motivates it, and how the pieces chain into a theorem.

Microarchitectural attacks — Prime+Probe, Flush+Reload, Spectre, Meltdown — are usually described as side channels: secret-dependent behavior leaks through timing or other observable perturbations of hidden processor state. Recent work on microarchitectural weird machines suggests a sharper framing: those hidden structures (caches, branch predictors) are themselves computational machines, and ordinary program execution is indirectly programming them.

This paper asks: what should a type system guarantee about that hidden computation, not just about what an attacker can observe of it? It defines a small imperative language, gives it two parallel semantics — ordinary architectural execution (⇓_A) and an induced weird-machine trace semantics (⇓_W) that records cache actions like Fill(s) — and builds a type-and-effect system, Γ; pc ⊢ c : ε, whose effect ε overapproximates the traces a command can induce. The central rule: a secret may not select between two low-distinguishable induced traces.

Two examples carry the whole paper. if h then x:=[A] else skip induces Fill(set(A)) on one branch and ε on the other — if that cache set is attacker-observable, the two traces are distinguishable, and the type system rejects the program, even though architecturally there's no explicit flow to a low variable. By contrast, if h then x:=[A] else y:=[A] induces the same trace, Fill(set(A)), on both branches — the secret still steers architectural state, but not the weird machine's low-observable behavior, so it's accepted.

🍯 Key takeaways

  • Reframe attacks as induced computations on a hidden machine, not merely observations of it.
  • Loads always induce a cache effect Fill(s), regardless of the label on the value they load — the address is the leak vector.
  • The type-and-effect judgment Γ; pc ⊢ c : ε overapproximates induced traces the same way ordinary effect systems overapproximate I/O.
  • The conditional rule's teeth: under a secret guard, both branches' low projections must be equal and a singleton.
  • The while rule is stricter still — the whole Kleene-star effect ε* must have a singleton low projection, because loop count is itself a channel.
  • Theorem: well-typed programs cannot induce attacker-distinguishable weird-machine traces (weird-machine noninterference).
  • Future direction: Conjecture 1 (weird-machine deadness) sharpens Theorem 2 into one statement — fixing the public input, the π_L-observable behavior is the same across every secret — while a separate, more speculative discussion sketches an even stronger, projection-independent goal beyond the conjecture itself.
Six everyday pictures

How to think about induced weird machines

Each stands alone — read in any order. Every card names where the picture stops being literally true.

The core idea · Induced computation

A jukebox wired to your footsteps

Imagine a jukebox that plays a song not when you press a button, but based on which floor tile you happen to step on as you walk through a room. You never "chose" a song — yet the jukebox's state changed because of you. Ordinary program execution wires the cache the same way: a secret-dependent branch doesn't program the cache on purpose, but it still selects which cache-state "song" plays.

Where it breaks: a jukebox has one observable output (the song). A real weird machine's state can be read through many different, not-yet-invented instruments — which is exactly the motivation for the paper's future "projection-independent" goal.
lev(s) · Observable vs. hidden sets

A room with some windows painted over

lev(s) partitions every cache set into "windows an attacker can see through" (L) and "windows painted over" (H). Fill(s) always happens, whether the window is clear or painted — but π_L only lets clear-window events through. A secret-dependent Fill on a painted-over set is architecturally real but invisible to this particular attacker.

Where it breaks: paint doesn't move; which sets are "L" versus "H" in practice depends on your threat model (co-tenant isolation, cache partitioning) and can itself be attacked if the partition is imperfect.
Loops · Counting as a channel

A telegraph key with a secret number of taps

A loop guarded by a secret is like a telegraph operator tapping a key some secret number of times — an eavesdropper doesn't need to decode the message, just count the pulses. while h do x:=[a] induces Fill(s) once per iteration; the trace length alone reveals information about h, independent of anything x or a "mean."

Where it breaks: a telegraph tap is always observable. Whether loop-count leaks in practice depends on lev(s) — if s is hidden (H), the pulses are on a wire the attacker can't tap, and the loop typechecks fine.
Effects · Overapproximation

A packing list, not a photo of the suitcase

An effect ε isn't a recording of what happened — it's a declared upper bound on what could happen, checked once at compile time. Like a packing list that says "clothes, toiletries, maybe a laptop," the effect Fill(s)⊔ε for a conditional says "either this set gets filled, or nothing does" without committing to which, until Effect Soundness (Theorem 1) guarantees every real run's trace is actually inside that declared set.

Where it breaks: a packing list can be checked by opening the bag. Checking that a runtime trace lies in ⟦ε⟧ isn't something you do by inspection — it's exactly what the soundness proof establishes once, for every run, not per-run.
Deadness · A future-proof goal

A vending machine with the display ripped out

Imagine a vending machine where every coin, regardless of value, dispenses the exact same snack — the internal gears still turn (real computation happens), but no input to the machine changes what comes out the slot. That's a "dead" weird machine: it still runs, but it's no longer programmable by secrets. The paper's noninterference theorem is a step toward this; full "deadness" (Conjecture 1) is the stronger, still-open target.

Where it breaks: a vending machine has one slot. Conjecture 1 itself is still stated relative to one fixed slot (the π_L projection) — it just asks for a single snack across every secret, rather than agreement between pairs of secrets. The paper separately sketches an even more speculative goal: the same guarantee holding no matter which slot (projection) the attacker probes.
Two layers · Orthogonal checks

A building inspector who checks wiring separately from plumbing

Standard IFC (the assignment rule's pc ⊔ ℓ ⊑ Γ(x) check) is one inspector, checking that secrets don't leak through explicit variable flows — the "wiring." The weird-machine effect checks are a second, independent inspector, checking that secrets don't leak through induced cache behavior — the "plumbing." A program can pass one inspection and fail the other.

Where it breaks: real inspectors sign off independently; here the two checks interact through pc — a secret that raises pc also tightens what the cache-effect checks will tolerate in nested code. They're separable in intent but coupled in the rules.
The full explanation

How it actually works

Section by section, with the paper's key rules and two grounding diagrams.

1 · Two semantics for one program

The source language is a small imperative calculus — skip, assignment, sequencing, memory load x:=[a], conditionals, and while-loops — with no cache primitives in it. Two big-step judgments run over the same syntax. Ordinary architectural execution, ⟨c,σ⟩⇓_A σ′, ignores caches entirely. The induced weird-machine trace semantics, ⟨c,σ⟩⇓_W⟨σ′,t⟩, additionally threads a trace t through every rule, and is the one place the cache enters the picture — via the load rule:

m(a) = v    set(a) = s
────────────────────────────────
⟨x:=[a], (ρ,m)⟩ ⇓_W ⟨(ρ[x↦v], m), Fill(s)⟩

Every other rule (skip, assignment, sequencing) just propagates ε or concatenates sub-traces; only the load rule generates a nonempty trace.

2 · The cache-residency weird machine

Traces are built from Fill(s) (an induced access to set s), Probe(s) (a timing observation of s — included for future extensions though this calculus never generates one), ε, and concatenation. Each set carries an observation level lev: Set → {L,H}. The low projection π_L keeps L-labeled events and erases H-labeled ones:

3 · The type-and-effect system

Command typing has the form Γ; pc ⊢ c : ε. Most rules are direct: skip gets ε, assignment gets ε (assignments don't touch the cache — only loads do), sequencing concatenates ε₁·ε₂, and a load gets Fill(s) for set(a)=s. The two rules that carry the paper's real content are the conditional and the loop:

-- conditional: guard has label ℓ, both branches typed under pc⊔ℓ
Γ ⊢ e : bool^ℓ   Γ;pc⊔ℓ ⊢ c1:ε1   Γ;pc⊔ℓ ⊢ c2:ε2
ℓ=H ⟹ π_L(⟦ε1⟧) = π_L(⟦ε2⟧)  ∧  |π_L(⟦ε1⟧)| = 1
────────────────────────────────────────────────
Γ;pc ⊢ if e then c1 else c2 : ε1 ⊔ ε2

-- while: guard has label ℓ, body typed under pc⊔ℓ
Γ ⊢ e : bool^ℓ   Γ;pc⊔ℓ ⊢ c:ε
ℓ=H ⟹ |π_L(⟦ε*⟧)| = 1
────────────────────────────────────────────────
Γ;pc ⊢ while e do c : ε*

Read the conditional's side condition in two parts. "π_L(⟦ε1⟧) = π_L(⟦ε2⟧)" says the two branches' low-observable behaviors must match. "|π_L(⟦ε1⟧)| = 1" additionally requires each branch's own low-observable behavior to already be a single value. A well-typed command under pc=H is guaranteed to be low-constant on its own (Lemma 3) — so this isn't guarding against some other failure mode; it's exactly the property that has to be established at this rule application so that Lemma 3 keeps holding one level further out, if this whole conditional is itself nested inside a further high-guarded branch. The while rule applies the same idea to the whole Kleene-star effect ε*, catching the iteration-count channel discussed in the primers.

4 · Why the loop rule has to look at the whole star

Consider while h do x:=[a] with set(a)=s and lev(s)=L. Each iteration induces Fill(s), so n iterations induce Fill(s)ⁿ, and the loop's effect denotes the infinite family {ε, Fill(s), Fill(s)², Fill(s)³, …}. Because lev(s)=L, none of these project away — π_L of that whole set has infinitely many distinct elements, violating |π_L(⟦ε*⟧)|=1. The secret picks the iteration count, and the iteration count is exactly what an attacker counting Fills would read off.

5 · From soundness to noninterference

The metatheory chains four results. Effect soundness (Thm 1): every runtime trace t from a well-typed command lies in the effect's denotation, t ∈ ⟦ε⟧. Low-projection soundness (Lemma 2) lifts this through π_L. High-PC low constancy (Lemma 3): anything typed under pc=H already has a low-constant effect — this is what makes the system compositional, since code nested inside a secret branch inherits pc=H automatically. Combining these yields weird-machine noninterference (Thm 2): for low-equivalent initial states, well-typed programs induce low-equivalent traces. The corollary restates this as a typability guarantee: no well-typed program can induce an "attacker-programmable weird computation" (Definition 6) — two low-equivalent runs with distinguishable low traces.

6 · Reading it as secure compilation — and the limits

The discussion section offers a secure-compilation reading: architectural execution induces a weird-machine computation P ⇝ W(P), and the type system guarantees well-typed source programs cannot induce attacker-distinguishable W(P) behavior. The authors are explicit about scope: the cache-residency model abstracts away replacement policy, associativity, coherence, and speculative execution, and the metatheory proves noninterference for this one weird machine and this one projection — not yet a channel-independent guarantee.

Follow the derivations, step by step

Worked examples

Four derivations from the paper's own examples, carried through to a typing verdict.

① The rejected example, traced fully

Command: if h then x:=[A] else skip, with set(A) = s, lev(s) = L, and h : bool^H.

  1. Type the branches. Γ;pc⊔H ⊢ x:=[A] : Fill(s) (load rule). Γ;pc⊔H ⊢ skip : ε.
  2. Compute low projections. π_L(⟦Fill(s)⟧) = {Fill(s)} since lev(s)=L. π_L(⟦ε⟧) = {ε}.
  3. Check the conditional's side condition. {Fill(s)} ≠ {ε} — the equality π_L(⟦ε1⟧)=π_L(⟦ε2⟧) fails.
  4. Verdict: rejected. The type system refuses to assign any effect to the conditional; the program is untypeable.
  5. Confirm against Definition 6. Take σ1 with h=true, σ2 with h=false (low-equivalent, since they agree on all L variables). Runtime traces: t1=Fill(s), t2=ε. π_L(t1)≠π_L(t2) — this is precisely an attacker-programmable weird computation, so rejection is exactly right.
⚠
Note: if instead lev(s)=H, step 2 changes to π_L(⟦Fill(s)⟧)={ε}=π_L(⟦ε⟧), the condition holds, and the program typechecks — the cache set being hidden is what saves it.

② The accepted example, traced fully

Command: if h then x:=[A] else y:=[A], same address A, set(A)=s, lev(s)=L.

  1. Type the branches. Both are loads from A: Γ;pc⊔H ⊢ x:=[A] : Fill(s) and Γ;pc⊔H ⊢ y:=[A] : Fill(s).
  2. Low projections. π_L(⟦Fill(s)⟧) = {Fill(s)} for both branches — identical sets, each a singleton.
  3. Check the condition. π_L(⟦ε1⟧)=π_L(⟦ε2⟧)={Fill(s)} ✓, and |{Fill(s)}|=1 ✓.
  4. Verdict: accepted. Combined effect ε1⊔ε2, denoting {Fill(s)} — the whole conditional has a single, secret-independent low-observable trace.
  5. What still differs architecturally: x holds the loaded value when h is true, y holds it when h is false — a real (typed, permitted) explicit flow to whichever variable is high enough to receive it. The weird machine just never finds out which branch ran.
💡
This pair of examples is the entire paper's thesis in miniature: identical architectural "shape," opposite induced weird-machine behavior, opposite verdicts.

③ The loop that programs the cache via its iteration count

Command: while h do x:=[a], set(a)=s, lev(s)=L. Compare h that makes the loop run 0 times vs. 3 times.

  1. Body effect. Γ;pc⊔H ⊢ x:=[a] : Fill(s).
  2. Star denotation. ⟦Fill(s)*⟧ = ⋃_{n≥0} ⟦Fill(s)⟧ⁿ = {ε, Fill(s), Fill(s)·Fill(s), Fill(s)·Fill(s)·Fill(s), …}.
  3. Concrete instance, n=0: trace = ε. Concrete instance, n=3: trace = Fill(s)·Fill(s)·Fill(s).
  4. Project both. Since lev(s)=L, π_L leaves each trace untouched: π_L(ε)=ε, π_L(Fill(s)³)=Fill(s)³ — visibly different lengths.
  5. Check the while rule. π_L(⟦Fill(s)*⟧) = {ε, Fill(s), Fill(s)², Fill(s)³, …}, which has infinitely many elements — |π_L(⟦ε*⟧)|=1 fails badly. Verdict: rejected.
🍯
Insight: this failure mode has nothing to do with the value loaded — it's purely about how many times the weird machine gets "tapped." Making lev(s)=H is one fix; another is rewriting the loop body so it induces no low-observable effect at all (e.g. a body of just skip or plain assignments), or otherwise restructuring it so the starred low projection collapses to a singleton — lev(s)=H is only the fix specific to this load-in-a-secret-loop pattern, not the only way to satisfy the rule while still branching on h.

④ Chaining the metatheory on the rejected example

Confirm concretely how Lemma 3, Theorem 1, and Theorem 2 relate for a command that does typecheck: if h then x:=[A] else y:=[A] nested inside a larger program with pc=L at the top.

  1. Apply Lemma 3 (High-PC low constancy) to the branches. Both branches are typed under pc⊔H = H; each individually has effect Fill(s), and indeed |π_L(⟦Fill(s)⟧)|=1 — consistent with the lemma's guarantee that anything typed under pc=H is low-constant.
  2. Apply Theorem 1 (Effect soundness) to the whole conditional. Any terminating run, for any h, produces a trace t with t ∈ ⟦Fill(s)⊔Fill(s)⟧ = {Fill(s)}. There is exactly one possible runtime trace.
  3. Apply Lemma 2 (low-projection soundness). π_L(t) ∈ π_L(⟦ε⟧) = {Fill(s)} for every run — again forced to a single value.
  4. Apply Theorem 2 (weird-machine noninterference). For any σ1≈_L σ2 (in particular, differing only in h), the resulting traces t1, t2 satisfy π_L(t1)=π_L(t2)=Fill(s). Noninterference holds exactly as promised.
  5. Apply Corollary 1. Since the program is well-typed under pc=L, it cannot induce an attacker-programmable weird computation — matching what we verified by hand in step 4.
💡
Each metatheorem is doing a small, checkable job. Stacked together, they turn "I checked one example by hand" into "this holds for every well-typed program, automatically."
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking.

Problem 1 · easy
A load x:=[a] assigns the fetched value to a high (secret) variable x. Does the load rule still record Fill(set(a))? Why does that matter?
Show answer
Yes — the load rule always emits Fill(s) for s=set(a), regardless of Γ(x). The cache effect is a function of the address, not the label of the destination variable — so the cache footprint can leak even when the fetched value is never architecturally observed. (This calculus fixes each load's address statically via set(a)=s; it doesn't itself model secret-indexed addressing like an array read a[h], though that would be an even more direct real-world leak vector.)Misconception: that assigning to a high variable "contains" the leak. The weird-machine channel is orthogonal to where the value ends up.
Problem 2 · medium
Is if h then x:=[A] else x:=[B] typable when set(A) ≠ set(B) and both sets are lev=L?
Show answer
No. The branches induce Fill(set(A)) and Fill(set(B)), two distinct singleton sets; π_L(⟦ε1⟧) = {Fill(set(A))} ≠ {Fill(set(B))} = π_L(⟦ε2⟧). The equality side-condition fails, so it's rejected — even though both branches are "the same shape" (a single load), touching different observable sets is enough to leak h.Misconception: that "both branches do a load" is enough to typecheck. The trace must match exactly, set for set, not just structurally.
Problem 3 · medium
Revisit if h then x:=[A] else skip but now with lev(set(A)) = H. Typable?
Show answer
Yes. π_L(⟦Fill(s)⟧) = {ε} because lev(s)=H erases the event, and π_L(⟦ε⟧) = {ε} already. Both sides of the equality condition are {ε}, a singleton — accepted.Misconception: that any secret-dependent Fill is automatically forbidden. It's only forbidden when the affected set is attacker-observable; hiding the set (e.g., via cache partitioning) is itself a valid defense the type system can certify.
Problem 4 · hard
The conditional rule requires both π_L(⟦ε1⟧)=π_L(⟦ε2⟧) and |π_L(⟦ε1⟧)|=1. Why isn't the equality alone enough?
Show answer
By Lemma 3, anything typed under pc=H is already guaranteed to have a low-constant effect, so on its own each branch's π_L(⟦εᵢ⟧) is already a singleton — the "singleton" half of the side condition isn't rejecting some violation that could otherwise sneak through equality alone. It's there because this rule application is exactly where that guarantee for the combined effect ε1⊔ε2 gets established in the first place: if this conditional is itself nested one level further inside another high-guarded branch, the next application of the rule needs to be able to assume this conditional's own effect is already low-constant, and that's only true because it was checked explicitly here rather than left to follow from equality.Misconception: that equality between the two branches is doing all the work. Equality alone says the branches agree with each other; the singleton check is what makes that agreement inductively reusable as programs nest deeper.
Problem 5 · medium
Why does the while-rule need to check |π_L(⟦ε*⟧)|=1 rather than just requiring the loop body's own effect to be low-constant?
Show answer
Even a body with a perfectly low-constant single-iteration effect can generate infinitely many distinct low projections once repeated a secret-dependent number of times — Fill(s)ⁿ for varying n are pairwise distinguishable if lev(s)=L, regardless of any property of a single iteration in isolation. The check has to be on the whole starred effect ε*, because the new channel (iteration count) only exists at the level of the loop, not the body.Misconception: that checking each iteration's body once is equivalent to checking the whole loop. Repetition itself creates a new signal (the count) that per-iteration checks can't see.
Problem 6 · medium
State Lemma 3 (High-PC low constancy) in your own words, and explain why it's needed for the system to be compositional.
Show answer
Lemma 3: any command typed entirely under a high program-counter label (Γ;H ⊢ c:ε) automatically has a low-constant effect — |π_L(⟦ε⟧)|=1 — with no extra side-condition needed at that point. It matters because once you're nested inside a secret-guarded branch, pc becomes H for everything inside, and the outer typing rules (e.g., a further conditional wrapping this one) need to be able to rely on the inner effect already being low-constant, without re-deriving it from scratch each time.Misconception: that low-constancy has to be re-checked freshly at every nesting level. Lemma 3 shows it falls out automatically once pc=H, which is what lets the metatheory scale to arbitrarily nested programs.
Problem 7 · hard
How does the future "weird-machine deadness" notion (Conjecture 1) differ from the noninterference theorem (Theorem 2) already proved in this paper?
Show answer
Theorem 2 is stated pairwise: for any two low-equivalent initial states, the induced low traces agree. Deadness restates this as a single global property: fixing the public input σ_L and ranging over every possible secret σ_H, the set of induced low-observable behaviors L_W(P,σ_L), after projection, is a singleton. These are close to the same claim for this calculus — the paper frames deadness as a conjecture because it's the shape of property the authors want to carry forward into richer languages, additional weird machines, or multiple simultaneous projections, where establishing it may require more than restating Theorem 2.Misconception: that Conjecture 1 is an unresolved doubt about this paper's own theorem. It's better read as a forward-looking generalization target, not a gap in Theorem 2 itself.
Problem 8 · easy
Does y := h (assigning a secret to a low variable) ever get caught by the weird-machine effect rules?
Show answer
No — assignment always has effect ε regardless of labels; this leak is caught by the ordinary IFC side-condition on the assignment rule, pc⊔ℓ ⊑ Γ(x), which fails here since Γ(y)=L but the right-hand side is H. It has nothing to do with weird-machine traces.Misconception: that the effect system subsumes or replaces standard IFC checks. The two layers are complementary — explicit/implicit architectural flows are still caught by ordinary label checks; the effect system adds a second, independent check for induced cache behavior.
Quick answers

Frequently asked questions

Ten questions newcomers to this framing tend to ask.

Q1What's a "weird machine," in one sentence?▾
A computation whose state evolves in response to inputs it wasn't designed to be programmed by — here, cache residency changing in response to ordinary loads, none of which were written with the cache in mind.
Q2How is "computation-centric" security actually different from calling this a side channel?▾
Side-channel framing asks whether an attacker can observe a secret-dependent difference through one specific channel (timing, say). This paper instead reasons about the induced trace itself, independent of how it's later read out — the object of study is the hidden computation, not a particular measurement of it.
Q3Why does assignment (x:=e) have effect ε even when e depends on a secret?▾
Assignment in this calculus only touches the variable environment ρ, never memory or the cache — there's no address involved, so there's nothing for the cache-residency weird machine to react to. Only loads (x:=[a]) touch an address and therefore a cache set.
Q4Why is Probe(s) in the trace grammar if the language never generates it?▾
Probe(s) represents the attacker's own timing measurement of set s — a natural action in cache attacks (Prime+Probe, Flush+Reload) even though the victim program never issues one. Including it in the grammar keeps the trace model ready for extensions that let an attacker-controlled component interleave probes with victim fills.
Q5Does this model capture real cache timing, replacement policies, or speculative execution?▾
No — the paper is explicit that the cache-residency model abstracts away replacement policy, associativity, coherence protocols, and speculation. The goal is to isolate the PL principle (type systems can constrain induced hidden computation) in the simplest possible weird machine, not to model a specific microarchitecture precisely.
Q6What does lev(s)=H correspond to physically?▾
The paper doesn't commit to a specific mechanism — lev(s)=H is an abstraction over any resource that ends up partitioned away from, or otherwise hidden from, the attacker's view (for instance, way-locked/partitioned cache regions). It's a placeholder for whichever isolation boundary you're modeling, not a claim about any particular hardware feature such as enclave-private caches.
Q7How does this relate to Spectre and Meltdown?▾
Spectre and Meltdown are cited as motivating examples of attacks that exploit speculative/out-of-order execution's hidden side effects. This paper's calculus doesn't model speculation at all — it targets the simpler, non-speculative cache-residency channel that underlies classic Prime+Probe/Flush+Reload attacks, as a first step.
Q8Is there an implementation or a tool that typechecks real programs with this system?▾
No — this is a foundational, proof-oriented paper (type-and-effect rules, effect soundness, noninterference, all proved on paper/in a technical report). It establishes the theory for a small calculus; building a checker for a real language is future work.
Q9What's the difference between the noninterference theorem and the "weird-machine deadness" idea in the future-work section?▾
Noninterference (proved, Theorem 2) compares pairs of low-equivalent runs. Deadness (conjectured) asks for a single, projection-independent statement that the whole induced machine is secret-independent, so that the guarantee would automatically extend to attacker observation channels not yet invented.
Q10Does the type system forbid all cache activity from depending on secrets?▾
No — it forbids secrets from choosing between attacker-distinguishable cache behaviors. A secret can still influence which address is touched, as long as every secret-dependent path ends up touching the same low-observable set(s), or touches only hidden (H) sets.

Glossary, provenance, and further reading

Every term in one place, then a clear line between the paper's claims and this guide's framing.

Core terms
Weird machineA computational device whose state evolves in response to inputs outside its intended programming model — here, the cache responding to ordinary loads.
Induced weird-machine traceThe sequence of Fill(s)/Probe(s) actions a command produces via ⇓_W, alongside its ordinary architectural result.
Cache-residency weird machineThe paper's concrete weird machine: state = which cache sets are resident, actions = Fill(s), Probe(s).
lev(s)Observation level of cache set s ∈ {L, H}; determines whether a Fill/Probe on s survives low projection.
Low projection π_LErases H-labeled trace events; the formal stand-in for "what the attacker actually sees."
Type-and-effect judgment Γ;pc⊢c:εAssigns each command an effect ε overapproximating its induced weird-machine traces, alongside standard IFC typing.
Low-constant effectAn effect ε whose denotation's low projection π_L(⟦ε⟧) is a singleton — the invariant enforced at every secret-guarded branch/loop.
Effect soundness (Thm 1)Every runtime trace of a well-typed command lies in its static effect's denotation.
Weird-machine noninterference (Thm 2)Low-equivalent initial states, run through a well-typed program, induce low-equivalent weird-machine traces.
Attacker-programmable weird computationA pair of low-equivalent runs whose induced traces are low-distinguishable (Def. 6) — exactly what Corollary 1 rules out for well-typed programs.
Weird-machine deadness (Conjecture 1)The stronger, future-work property that a program's low-observable induced behavior is a single value independent of all secret inputs, for a fixed public input.
Supporting terms
IFC / noninterferenceInformation-Flow Control: type-based enforcement that secrets can't influence public outputs; noninterference is the classical security theorem it targets.
Security lattice L ⊑ HThe two-point lattice used throughout: Low (public) is no more secret than High.
pc labelProgram-counter label tracking whether control flow already depends on a secret; joined into branch/loop-body typing via pc ⊔ ℓ.
Prime+Probe / Flush+ReloadClassic cache side-channel attack techniques motivating the weird-machine framing (Osvik–Shamir–Tromer 2006; Percival 2005; Yarom–Falkner 2014).
Spectre / MeltdownSpeculative/out-of-order execution attacks cited as motivating examples of hidden microarchitectural computation (Kocher et al. 2019; Lipp et al. 2018).
Effect systemsType discipline tracking side effects statically, tracing to Lucassen & Gifford (1988) and Talpin & Jouvelot (1994); repurposed here for weird-machine traces.
Secure compilation / hyperpropertiesFrameworks for reasoning about attacker contexts and observational equivalence across compilation, invoked in the paper's P ⇝ W(P) discussion (Abate et al. 2019; Clarkson & Schneider 2010).
Contributions, at a glance
  • Formulates microarchitectural attacks as induced computations on hidden weird machines, not merely side-channel observations.
  • Defines a small architectural language plus an induced weird-machine trace semantics.
  • Presents a type-and-effect system whose high-control rules prevent secret-dependent low-observable hidden computations.
  • Proves effect soundness and weird-machine noninterference for well-typed programs.
