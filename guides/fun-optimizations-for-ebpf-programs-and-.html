eBPF '26 · A Field Guide

Let the compiler finish the job after the guard says safe

The eBPF verifier has to statically prove a program is safe — so the compiler is forced to generate code the verifier can follow, not the fastest code it could. This is the plain-English story of post-verification optimization (PVO): check once, then optimize freely.

📄 "Fun Optimizations for eBPF Programs" · Shahinfar, Panda, Antichi · eBPF'26 🎓 Basic compiler/OS background assumed — primers cover eBPF specifics ⏱ ~22 min read
🛂

The verifier only needs to check the program ONCE. A correct optimizer cannot change program behavior — so optimize freely after it says safe, instead of restricting the code the verifier ever sees.

Before you begin

Quick glossary, then six ideas the paper assumes

Acronyms first, so nothing downstream is a mystery word. Then six collapsible primers — open whichever looks unfamiliar.

Quick glossary — the acronyms you'll see everywhere

eBPFExtended Berkeley Packet Filter — a sandboxed bytecode VM inside the Linux kernel for safely running custom code (networking, monitoring, scheduling, OOM handling).
JITJust-In-Time compiler — translates verified eBPF bytecode to native CPU instructions; the in-kernel JIT here stays deliberately conservative.
LLVMThe compiler infrastructure (via Clang) that compiles eBPF source to eBPF bytecode and applies almost all optimizations, before the kernel ever sees the program.
ISAInstruction Set Architecture — eBPF bytecode is its own ISA, distinct from the host CPU's; the JIT does the ISA-to-ISA translation.
BTFBPF Type Format — kernel metadata describing types/functions, used by the verifier and by potential future annotation-based tooling.
PVOPost-Verification Optimizer — this paper's proposal: a trusted, userspace optimizer that runs on bytecode after it has already passed the verifier.
DCEDead-Code Elimination — removing unreachable/unused code; done by Clang, and by the kernel's own verifier since Linux 5.1.
PGOProfile-Guided Optimization — restructuring code using runtime profiles; cited as prior eBPF compiler work (e.g. Morpheus).
1What eBPF is, and why it's verified▾

eBPF lets userspace load custom code into the Linux kernel — for packet processing, tracing, scheduling, and more — without writing a kernel module. Because this code runs with kernel privileges, a buggy or malicious program could crash or corrupt the whole machine.

So before any eBPF bytecode runs, a static verifier walks every possible execution path and proves it's safe: no out-of-bounds memory access, no unbounded loops, bounded complexity.

Now you're ready: the paper's whole argument is about what this safety check costs in lost performance — and how to get some of it back.
2The compile → verify → JIT pipeline▾

Source code goes through Clang, which compiles it to eBPF bytecode and applies most compiler optimizations (constant propagation, dead-code elimination, etc.). The kernel's verifier checks that bytecode for safety. If it passes, the in-kernel JIT translates it to native machine code — conservatively, mostly just translation, not re-optimization.

Now you're ready: almost all optimization happens before verification — which means it must produce code the verifier can still understand.
3What the verifier actually checks▾

The verifier does symbolic analysis of every code path: tracking value ranges, pointer bounds, and loop termination. It also enforces hard complexity limits — e.g. it gives up once it has processed roughly 1 million instructions across all paths.

It reasons about the code's structure, not just its final behavior — so two programs that always compute the same thing can still get different verdicts if one is shaped in a way the verifier can't follow.

Now you're ready: this is exactly the property compiler optimizations exploit and violate — they change structure while preserving behavior.
4Compiler optimizations 101, and why -O2▾

Compilers rewrite code to run faster without changing its output: folding constants, deleting dead code, hoisting loop-invariant work, unrolling loops to amortize branch overhead. The paper uses Clang's -O2 throughout, because -O0 skips transformations the verifier actually needs to pass programs, while -O3 is considered unstable for eBPF.

Now you're ready: "more optimization" isn't free here — it's a knob the verifier's capabilities constrain from both ends.
5Why optimized code can confuse a static verifier▾

An optimizer might replace two separate bound checks with one combined check before a loop, or turn a two-condition loop test into a single precomputed comparison. The result is equivalent — but the verifier's symbolic analysis loses the chain of reasoning ("this value is bounded because of that check over there") that let it prove safety on the unoptimized version.

Now you're ready: this gap — correct-but-unprovable — is the entire tension the paper documents.
6The JIT is not a second optimizer▾

Unlike a normal compiler backend, the in-kernel eBPF JIT deliberately avoids restructuring code. It mostly translates verified bytecode instruction-by-instruction to native ISA, because any bug in a post-verification rewrite could silently introduce unsafe behavior that the verifier never checked.

Now you're ready: that conservatism is precisely the gap PVO proposes to fill.
The whole story in one place

PVO in a nutshell

The problem, the measured cost, and the fix — in a few paragraphs.

The eBPF verifier statically proves safety by tracing every code path with symbolic analysis. To stay provable, the compiler has to generate code shaped a certain way — which means it sometimes has to skip optimizations it knows are beneficial, and developers sometimes have to reach for slower, verifier-friendly runtime abstractions instead of natural code.

The paper measures this cost with a compute-heavy Fibonacci benchmark. Manually unrolling a bounded loop that Clang's own unroller can't get past the verifier delivers up to 42–43% higher throughput under a large-iteration workload — headroom a program stuck with the un-unrolled, verifier-legible shape simply can't reach. Being forced to use a flexible-but-runtime-checked loop API (bpf_loop, the BPF Iterator) instead of a plain loop costs up to 88% throughput in the worst case.

The fix doesn't touch the verifier at all. Post-Verification Optimization (PVO) proposes inserting a trusted, userspace optimizer after the verifier has already approved the bytecode, on the premise that a correct optimizer preserves program behavior and so shouldn't need to be re-checked. The paper is careful to frame this as an optimistic starting point rather than a proof: showing an optimizer is correct is itself hard, PVO's output may not be verifier-legible if re-checked, and the authors say additional mechanisms are still needed before this gives the same guarantee the verifier gives today.

🍯 Key takeaways

  • The verifier reasons about code structure, not just final behavior — so equivalent-but-differently-shaped code can be rejected.
  • Manual loop unrolling: up to 42–43% higher throughput than the un-unrolled, verifier-legible baseline on a large-iteration workload.
  • Runtime loop APIs (bpf_loop, BPF Iterator) needed to express variable-length loops: up to 88% lost throughput.
  • PVO = the paper's proposal to optimize after verification, in trusted userspace, on the premise that a correct optimizer can't introduce unsafe behavior — flagged by the authors as a starting premise that still needs more machinery, not an established guarantee.
  • Trust is delegated to the user who already has capability to load eBPF — not proven by the kernel.
Four everyday pictures

How to think about PVO

Each stands alone. Every card ends with where the picture stops being true.

The core tension · Verifier vs. optimizer

A guard who only reads blueprints

A building inspector approves a floor plan by tracing every hallway on paper — they never watch people actually walk it. If a contractor "simplifies" the blueprint (merging two doors into one, say) the inspector can no longer trace the paths they need to, even though the building is just as safe. The verifier is that inspector: it reasons about code structure, so structural shortcuts the optimizer takes can make a perfectly safe program illegible to it.

Where it breaks: a building inspector could just re-walk the new plan; the verifier's symbolic analysis genuinely can't follow certain transformations (e.g. reversed arithmetic reasoning) — it's a capability limit, not laziness.
The fix · Post-verification optimization

Airport security, then repack freely

Security scans your packed bag once. Once it's cleared, nobody minds if you repack it more efficiently on the other side — same contents, safer to carry, just better organized. PVO does the same to eBPF bytecode: the verifier scans it once; a trusted optimizer then reorganizes the already-approved bytecode for speed, and since nothing was added or removed, the original clearance still holds.

Where it breaks: security re-scans you on re-entry; eBPF doesn't re-verify PVO's output at all — trust is delegated up front to the (already-privileged) user who registered the optimizer, not re-checked.
Developer's dilemma · bpf_loop / BPF Iterator

A courier told to stop at every light

You have a highway pass for straight-through driving, but for one delivery type the dispatcher insists you take the surface road and stop at every light — because that's the only route they can guarantee is safe. It gets you there, but each stop (a callback function call/return) adds real overhead. That's bpf_loop: the runtime, not the verifier, guarantees loop termination, at the cost of a call per iteration. The BPF Iterator is a related but separate API for a different job — walking a kernel object list (like all open sockets) rather than looping a fixed number of times — and the paper measures it alongside bpf_loop as another verifier-driven abstraction with its own overhead.

Where it breaks: a courier can switch routes at will; a developer often has no equivalent-performance verifier-legible alternative for a genuinely variable-length loop — the slow route may be the only legal one.
Scope · What PVO can and can't fix

Straightening a hallway after the inspector left

The inspector approved a zig-zag hallway because that's the only shape they could trace safely. Once they're gone, a contractor can straighten it into a direct corridor — same rooms, same exits, just less walking. PVO is that post-approval renovation: it optimizes bytecode the verifier already blessed, without needing the verifier's understanding at all.

Where it breaks: a renovation contractor is trusted by reputation alone; PVO's safety story still needs some mechanism (certificates, sandboxing) beyond "trust the renovator" before it's production-ready — the paper flags this as open work.
The full explanation

How it actually works

From the baseline pipeline, to where it breaks, to the proposed fix.

1 · The baseline pipeline

Source code compiles (via Clang, -O2) to eBPF bytecode; the kernel verifier statically checks safety; the in-kernel JIT translates approved bytecode to native instructions. Almost all optimization happens in the first step — and must produce code shaped so the second step can still reason about it.

2 · Where optimizations help the verifier — and where they hurt it

Not all optimization fights the verifier. Some passes actively help by pruning paths and reducing memory accesses the verifier would otherwise have to reason about; others restructure code into shapes the verifier's symbolic analysis can't follow, or blow past its hard complexity limits.

CategoryExample passesEffect on the verifierVerdict
Dead-code eliminationdce, adce, globaldceShrinks the program before the kernel's own DCE pass runs✔ Helps
Code motion / instr. simplifylicm, sink, instcombineReorders or merges ops into shapes the verifier sometimes can't trace♣ Mixed
Control-flow reasoningjump-threading, loop-unswitchCuts branches, but can exceed the ~8K-jump / 1M-depth path limits♣ Mixed
Loop optimizationloop-unroll, loop-fusionAmortizes per-iteration jump cost, but can blow the ~1M-instruction budget or hide loop bounds♣ Mixed
⚠
Concretely: a program reading 20 bytes from a packet, with an explicit bound check before every byte read, is rejected across Clang 17–22 — the optimizer collapses all the checks into one packet-size check before the loop, and the verifier can't work backward from "size ≥ 20" to "every individual offset is in bounds." Error: pointer arithmetic on pkt_end prohibited.

3 · Forced runtime abstractions: bpf_loop and the BPF Iterator

Unbounded or data-dependent loops simply can't be expressed as ordinary source-level loops — the verifier can't prove they terminate. bpf_loop works around this by turning the developer's logic into a callback function: the runtime's own bounded control-flow (which the verifier can reason about) drives the iteration, and each call into the callback costs a real function call/return plus register pressure. The BPF Iterator is a related but distinct API, built for walking kernel object lists (sockets, tasks, maps) rather than for arbitrary bounded iteration; the paper measures it as a separate loop-replacement option without describing it through that same callback-checked-in-isolation mechanism.

4 · The fix: insert an optimizer after the verifier

PVO's key move is timing: run an extra optimization pass on bytecode that has already passed verification, in trusted userspace. The paper's proposal is that the PVO then generates an executable that the existing JIT machinery can run (Figure 8 leaves the exact interface — whether that's more bytecode handed to the JIT, or something closer to a finished binary — underspecified). The premise is that, since a correct optimizer preserves behavior, the safety already proven for the unoptimized version should carry over to the optimized one without re-verification — but the paper stresses this is a premise to build on, not a guarantee it has already established: proving an optimizer correct is itself hard, and the authors say additional mechanisms are still needed to reach an equivalent safety guarantee.

💡
Why userspace? It reuses mature optimizer infrastructure (e.g. LLVM/BOLT-style binary optimization) instead of requiring the kernel to ship and trust a full optimizing compiler. It's off the critical path — it runs once per program load, not once per execution.
Follow the numbers

Worked examples

Three traces through the paper's real measurements.

① How much does refusing to unroll actually cost?

Baseline vs. Unroll-1 throughput (M Op/s): Workload A 1.4→2.0, Workload C 9.8→10.1.

  1. Workload A: (2.0 − 1.4) / 1.4 = 0.429 → +43%.
  2. Workload C: (10.1 − 9.8) / 9.8 = 0.031 → +3%.
  3. Range: 3%–43% — matching the paper's reported "3% to 42% increased performance."
  4. Why the gap: Workload A has far more iterations (0–1024) than C (0–16), so the per-iteration jump savings from unrolling compound over more loop passes.
🍯
Insight: the verifier-imposed cost of "no unrolling" isn't fixed — it scales with how many iterations the workload actually takes.

② Unroll-3 on Workload A vs. Workload C — the same trick, opposite verdicts

Unroll-3 restructures the loop to minimize branches at the cost of extra computation.

  1. Workload A, vs. baseline: 3.1 / 1.4 = 2.21× → roughly doubles throughput.
  2. Workload A, vs. Unroll-2: (3.1 − 2.3) / 2.3 = 0.348 → +35%, matching "34% faster than Unroll-2."
  3. Workload C, vs. Unroll-2: (9.9 − 10.3) / 10.3 = −0.039 → −4%. Unroll-3 is now the worst unrolling strategy.
  4. Why it flips: Unroll-3's extra computation per branch avoided pays off only when there are enough iterations to amortize it. With ≤16 iterations, the extra work costs more than the branches it removes.
💡
This is the paper's core lesson in miniature: the best code shape depends on workload characteristics, but the verifier only ever sees one fixed shape, chosen ahead of time.

③ Where does "−88%" actually come from?

Workload A throughput (M Op/s): for-loop 1.417, bpf_loop 0.2, BPF Iterator 0.17.

  1. bpf_loop vs. for-loop: (0.2 − 1.417) / 1.417 = −0.859 → −86%.
  2. BPF Iterator vs. for-loop: (0.17 − 1.417) / 1.417 = −0.880 → −88%, exactly the paper's headline number.
  3. Why Workload A specifically: it has the most iterations (0–1024), so the per-iteration callback overhead (a function call/return plus register spilling) is paid the most times.
  4. Sanity check on Workload C (fewest iterations): (6.46 − 9.83)/9.83 = −34% for bpf_loop — same mechanism, far fewer call/returns to amortize the overhead over.
🍯
Insight: "the loop API costs up to 88%" isn't a fixed tax — it's per-iteration overhead multiplied by iteration count, exactly like the unrolling gains in examples ① and ②.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Figure 2's loop checks both i < repeat (variable) and i < CONSTANT_BOUND (constant). Why add the redundant constant check at all?
Show answer
Without a compile-time-known bound, neither the verifier nor the compiler can reason about how many times the loop can run: the verifier can't prove termination, and the compiler can't judge whether unrolling is profitable. Adding CONSTANT_BOUND gives both an upper bound they can work with, even though the variable check is still needed for the actual logic.Misconception: that the constant check is pure redundancy since the variable bound already limits iterations. It's redundant for correctness, but essential for provability and optimizability.
Problem 2 · medium
Manually repeating the loop body (Unroll-1) passes the verifier, but telling Clang to unroll via a pragma does not — even though both produce "unrolled" code. What's the structural difference?
Show answer
Unroll-1 repeats the entire per-iteration code, including both the constant and variable bound checks, unmodified — so the verifier can trace termination the same way it did for one iteration, just more times. Clang's pragma-driven unroll interacts with its other optimization passes, which additionally collapse the two checks into one precomputed comparison — the same transformation that breaks Figure 5's example — so the verifier loses the reasoning chain entirely.Misconception: that "unrolled" is a single well-defined code shape. The verifier cares about exactly how the checks are structured, not just whether the loop body is repeated.
Problem 3 · medium
Figure 4's program checks bounds before every single byte read, yet gets rejected. Why doesn't having a correct per-access bound check guarantee verification?
Show answer
The compiler notices all the per-byte checks are implied by one upfront "is the packet ≥ 20 bytes" check, and optimizes the redundant ones away, leaving only the packet-size check plus unguarded reads. The verifier then sees reads it can't directly tie to a bounds check — it can't reconstruct that the packet-size check made them safe.Misconception: "if the source code has correct bounds checks, the program is verifier-safe." Verification operates on the compiled bytecode the optimizer produced, not the source's intent.
Problem 4 · hard
Why can't the verifier just be extended to understand every safe optimization, eventually?
Show answer
Static verification of arbitrary program properties runs into fundamental decidability limits (the paper cites Rice's theorem): no general algorithm can decide every nontrivial semantic property of arbitrary programs. Verifier improvements can shrink the set of rejected-but-safe programs, but can't eliminate it entirely — which is exactly why the paper proposes a complementary mechanism (PVO) rather than betting everything on verifier improvements.Misconception: that the verifier's restrictiveness is just an unfinished engineering project. Some of the gap is structural, not a bug list.
Problem 5 · medium
On Workload B, bpf_loop achieves 1.43 M Op/s versus 5.9 for a plain for-loop, while on Workload A it's 0.2 vs 1.417. Which workload suffers the larger relative penalty, and why?
Show answer
Workload A: (0.2−1.417)/1.417 ≈ −86%. Workload B: (1.43−5.9)/5.9 ≈ −76%. Workload A suffers more because it has more iterations on average (range 0–1024 vs 0–128), so more callback invocations occur, and the fixed per-call overhead is paid more times.Misconception: that abstraction overhead is a constant percentage tax. It's a constant per-iteration cost, so its relative impact grows with iteration count.
Problem 6 · hard
PVO's design lets the kernel trust a user-supplied optimizer without re-verifying its output. Is this actually safe, or does it break eBPF's safety model?
Show answer
The paper doesn't claim this is fully safe — it explicitly says additional mechanisms are needed to give equivalent guarantees to today's verifier. Its narrower, more careful argument is that the design leans on the judgment of an already-privileged user (one who can load eBPF programs and has separately registered and opted into an optimizer), and that this is "not unreasonable" because that same privileged user already has other ways to compromise the system if they choose to. That's weaker than "doesn't introduce a new class of attacker" — it's closer to "we're extending trust to a role that was already trusted," while leaving open exactly what guarantees PVO's output needs before it matches verified bytecode.Misconception: the paper claims PVO preserves eBPF's safety model as-is. It's careful to flag this as an open problem, not a solved one.
Quick answers

Frequently asked questions

Eight questions newcomers ask most.

Q1What exactly does the eBPF verifier protect against?▾
Out-of-bounds memory access, unbounded loops/hangs, and other behaviors that could crash or corrupt the kernel — since eBPF programs run with kernel privileges. It proves these properties statically, before any code executes, via symbolic path analysis.
Q2Why can't the verifier just trust that the compiler produced safe code?▾
Compilers have bugs, and a compromised or buggy toolchain could otherwise smuggle unsafe bytecode into the kernel. The verifier re-derives safety independently from the bytecode itself, regardless of what produced it — that independence is the whole point of having a verifier.
Q3What is PVO, concretely, and where does it run?▾
Post-Verification Optimizer: the paper's proposed userspace optimizing compiler (not yet upstream) that would receive already-verified eBPF bytecode and produce a more efficient version for the JIT to run — on the premise that a correct optimizer preserves behavior, though the paper notes this still needs additional safety machinery before it matches today's guarantees.
Q4Why exactly does loop unrolling get blocked?▾
Clang's unrolling collapses the loop's two termination checks into one precomputed comparison, and the verifier's symbolic analysis can't follow that transformation backward to confirm the loop still terminates within bounds — so it rejects the unrolled bytecode, even though the source-level logic is unchanged.
Q5If bpf_loop/BPF Iterator are slower, why do they exist?▾
They make genuinely variable-length or unbounded loops expressible at all. bpf_loop does this by turning the developer's logic into a callback: the runtime guarantees termination of its own control-flow, so the verifier only has to check that callback in isolation, trading per-iteration call overhead for expressiveness. The BPF Iterator solves a related but different problem — walking a kernel object list rather than an arbitrary bounded loop — and the paper measures it as a separate abstraction with its own overhead, not simply another instance of the same callback mechanism.
Q6Is PVO implemented and available today?▾
No — this paper presents it as a proposal and a measured motivation (§4–5), not a shipped kernel feature. It discusses open questions (how to provide equivalent safety guarantees, how annotations could help PVO find missed optimizations) as future work.
Q7Why -O2 and not -O0 or -O3 for eBPF?▾
-O0 skips transformations (like constant folding) that are often required for a program to pass the verifier at all. -O3 is considered unstable for eBPF code generation. -O2 is the de-facto working compromise the paper (and most eBPF developers) use.
Q8How would PVO guarantee the same safety the verifier provides?▾
This is explicitly an open problem in the paper: since PVO's output may not itself be verifiable, extra mechanisms are needed — e.g. the optimizer emitting correctness certificates, or sandboxing the executing code as a backstop. The paper surveys these directions without picking one.

Core terms
PVOPost-Verification Optimizer — this paper's proposed extra compilation phase, running in trusted userspace after the verifier has approved the bytecode.
VerifierThe kernel component that statically proves eBPF bytecode safety via symbolic analysis of every code path, subject to hard complexity limits (~1M instructions processed, ~8K jumps, ~1M path depth).
Structural reasoning gapThe paper's core tension: optimizations preserve behavior but change code structure, and the verifier's proofs depend on structure, not just behavior.
bpf_loopA runtime helper that separates loop control-flow (guaranteed by the kernel) from application logic (a callback the verifier checks in isolation) — enabling variable-length loops at the cost of a call per iteration.
BPF IteratorA related but distinct runtime abstraction, built specifically for walking kernel object lists (e.g. sockets) rather than for arbitrary bounded iteration.
Dynptr / ArenaOther eBPF safety abstractions: Dynptr for safe access to kernel-owned buffers/objects; Arena for custom data structures with kernel-managed memory.
