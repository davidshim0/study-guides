MICRO 2025 · A Field Guide

Giving every domain its own moat, without drowning the castle in guard rows

Rowhammer breaks the assumption every allocator relies on: that unrelated data placed side by side in DRAM stays unrelated. Citadel is a memory allocator that puts physical distance — not permissions — between things that don't trust each other, at a cost small enough to actually ship.

📄 Saxena, Wang, Daglis · Georgia Tech 🎓 Assumes you know buddy allocators & NUMA-ish page management ⏱ ~25 min read
🏰

Two untrusting domains are safe only if they are colocated in the exact same DRAM row or separated by ≥NG guard rows — everything else in Citadel exists to make that affordable.

Before you begin

What the paper assumes you already know

You already know buddy allocators, NUMA nodes, and the Linux mm stack cold — these primers skip that and focus on the Rowhammer-specific and Citadel-specific machinery layered on top of it.

🔑 Quick glossary — acronyms you'll hit immediately

RHRowhammer — repeated activation of a DRAM row flips bits in physically nearby rows.
NGNumber of guard rows required on each side of a row to stop RH crossing a boundary (paper assumes 2 in its main evaluation).
GRTGlobal Row Table — Citadel's lookup table from logical row-ID to physical DRAM row location(s).
PT / PTHammerPage Table (page); PTHammer flips bits in page tables via RH to escalate privilege.
PPRPost-Package Repair — DRAM's internal mechanism for swapping out rows found to be faulty.
PFNPage Frame Number — the physical page identifier the kernel uses internally.
TRR / PRACTarget Row Refresh / Per-Row Activation Counters — in-DRAM hardware RH mitigations, both shown to be imperfect or costly.
cgroupLinux control group — Citadel's prototype uses one cgroup ≈ one security domain.
protected domain data guard row / attacker adjacency Citadel's allocator machinery headline number / core rule
1Rowhammer, in one sentence▾

Hammering (rapidly, repeatedly activating) one DRAM row disturbs its physical neighbors enough to flip bits in them — no exploit of a software bug required, just electrical interference between adjacent hardware cells. It's been reproducible on every major DRAM vendor and node since 2014, and a 2022 study found all tested DDR4 chips vulnerable despite in-DRAM defenses.

Now you're ready: Citadel's entire design exists to control physical adjacency in DRAM — everything else follows from that one constraint.
2The global row — the OS/hardware bridge▾

A 4KB OS page is striped across many DRAM banks for parallelism (Fig. 2 of the paper), but every bank-fragment of that page shares the same row-ID. A global row is the set of same-row-ID fragments across all banks — effectively "row X, everywhere." In this paper's server config, one global row is 1MB (128 banks × 8KB rows).

Now you're ready: Citadel reserves and isolates memory in units of global rows, not physical addresses — this is the whole trick that lets a software allocator control DRAM-level adjacency.
3Guard rows▾

A guard row is a global row deliberately left unmapped — never assigned to any process — so that RH-induced bit flips land in empty space instead of another domain's data. The number needed per side, NG, is a security parameter: the paper notes that at least two guard rows are typically needed because of attack patterns like Half-Double, assumes NG=2 in its main evaluation, and separately studies NG=4 as a more conservative setting.

Now you're ready: guard rows are pure overhead — capacity you pay for and never use. The whole design problem is amortizing that cost.
4Two prior approaches, two failure modes▾

ZebRAM stripes memory into alternating guard/data rows everywhere — simple, but a flat 50% capacity loss (worse against advanced attack patterns). Siloz instead reserves whole DRAM subarrays (hundreds of physically-isolated rows) per domain — no guard rows needed, but each domain's reservation is GB-scale, so small domains waste almost all of theirs. The paper calls that waste memory stranding.

Now you're ready: Citadel's whole pitch is landing between these two failure modes — pay for guard rows only where needed, and reserve chunks small enough that stranding stays low.
5Security domains and zones▾

A security domain is anything that must be protected from RH originating outside it — typically one process, but also each page table page, or a programmer-chosen sub-region. A domain's memory may not be contiguous; each contiguous piece is a zone. Citadel's per-page-allocation rule: every page carries a domain-ID and can only be served from that domain's zones.

Now you're ready: this is finer-grained than Siloz's "domain = VM" and more general than ZebRAM's "everything is isolated identically" — Citadel wants domains of any size, from a 4KB page table to a multi-GB process.
6The zero-distance security insight▾

RH's threat model is about a row disturbing its neighbors — it says nothing about a row disturbing itself. So two domains sharing the exact same global row (distance 0) cannot RH each other by definition, even with zero guard rows between them.

Now you're ready: this is the loophole Citadel's "zonelet" primitive exploits later to protect millions of tiny domains cheaply — see primer 9.
7Why not just isolate whole DRAM banks?▾

Modern memory controllers deliberately stripe each page's cache lines across many banks (Fig. 2) to exploit bank-level parallelism — a single page never lives in one bank. Isolating by bank would mean either breaking that striping (killing single-thread performance) or being incompatible with how real memory controllers already work. Citadel instead isolates by row-ID, which is orthogonal to bank striping.

Now you're ready: Citadel's isolation unit (the global row) was chosen specifically to be compatible with performance features the memory controller already does for you.
8The buddy allocator's role▾

You already know the buddy allocator serves power-of-2 page runs from per-order free lists. Citadel doesn't replace this abstraction — it overrides six entry points (rmqueue(), __free_one_page(), etc.) so that "which physical page do I hand back" is additionally constrained by domain and row-ID, not just order and NUMA node.

Now you're ready: Citadel is a drop-in allocator-policy change, not a new memory model — same kernel APIs (alloc_pages(), free_page()), different physical-placement logic underneath.
9Loss vs. stranding — the two overhead currencies▾

Capacity loss = memory permanently sacrificed as guard rows, never usable by anyone. Stranding = memory reserved for one domain but not currently used by it, and therefore unusable by anyone else. A scheme that minimizes one tends to maximize the other (ZebRAM: all loss, no stranding; Siloz: no loss, lots of stranding) — Citadel's every design decision is tuning this one knob.

Now you're ready: when you see a number in this guide, ask whether it's loss or stranding — the paper always reports both separately, because the fix for each is different.
10Complex DRAM addressing (skim on first pass)▾

Real DRAM chips sometimes internally remap rows — mirroring, inversion, and scrambling — meaning a single logical row-ID can occupy up to four different physical locations across ranks. Citadel handles this with a lookup table (the GRT) rather than assuming addresses are identity-mapped; you can safely treat the main design (§4–5) as if mapping were simple and come back to this later.

Now you're ready: everything in tabs 2–5 assumes simple addressing; the FAQ and Reference tabs cover what changes under complex addressing.
The whole story in one place

Citadel in a nutshell

Why "isolate everything the same way" fails, and the two-level fix.

Software-based Rowhammer defense boils down to one move: physically separate domains that don't trust each other in DRAM, so an attacker hammering their own rows can't reach anyone else's data. The hard part is at what granularity. Isolate at row granularity (ZebRAM) and you pay a flat 50% capacity tax in guard rows everywhere, even for domains that never needed that much separation. Isolate at DRAM-subarray granularity (Siloz) and guard rows nearly disappear, but every domain's minimum reservation balloons to hundreds of MB — with 1K-row subarrays that's just 128 subarray groups per bank, capping you at a couple hundred domains; this paper's own evaluation instead approximates Siloz with 512-row subarrays, yielding 256 domains on a 128K-row system — and either way, small domains strand almost all of their reserved subarray (31% of memory, on average, in this paper's evaluation).

Citadel's insight is that most systems have a bimodal footprint distribution: a handful of large processes hold most of the memory, while hundreds of background daemons and thousands of page-table pages each need only KBs–MBs (Fig. 1b). One reservation size can't serve both well. So Citadel uses two reservation primitives at once: a coarse, guard-row-amortizing reservation chunk (16 contiguous global rows by default) for normal-sized domains, and a fine-grained zonelet (one data row + NG guard rows) for tiny domains, exploiting the fact that domains sharing a data row can't hammer each other at all.

The payoff: on a 128GB, 128K-row server, Citadel supports thousands — even up to 10.48 million if all memory were devoted to zonelets alone — of arbitrarily-sized domains, at just 7.2% average memory overhead (1.5% loss + 5.7% stranding), with essentially no performance loss (actually a 4.1% average speedup). ZebRAM and Siloz each fail outright on several of the paper's 11 workload mixes; where they do work, they cost 4–6× more memory.

🏰 Key takeaways

  • The security rule is physical: colocate in the same global row (distance 0), or separate by ≥NG guard rows. Nothing else matters.
  • Chunk = coarse reservation unit (16 global rows) that amortizes guard-row cost over many rows.
  • Zonelet = fine-grained unit (1 data + NG guard rows) for KB–MB domains, exploiting same-row colocation.
  • Zone expansion greedily grows a domain's existing zone into adjacent free chunks instead of paying for a fresh guard row.
  • Chunk size = 16 rows is the measured sweet spot: bounds guard-row loss to 12.5% worst case while keeping stranding low.
  • Result: 7.2% avg overhead (up to 16%), 9.8×/4.5× lower than ZebRAM/Siloz, 100% of workload mixes supported (vs. 36%/55%), no perf loss.
Six everyday pictures

How to think about Citadel

Each stands alone — read in any order. Every card names where the picture stops being literally true.

The core rule · Guard rows as a moat

A castle's moat

A moat only has to be wide enough that no attacker's ladder reaches the wall — dig it wider than that and you've just wasted land you could've built on. Guard rows are the moat: NG rows wide is exactly enough to stop RH's blast radius, and every row wider is pure capacity thrown away. ZebRAM builds a moat around every single room; Citadel builds one moat around a whole neighborhood of rooms (a chunk) instead.

Where it breaks: a moat is static; Citadel's guard rows move as domains grow/shrink (zone expansion/splitting), which a real moat can't do.
Reservation granularity · Chunks vs. stranding

Renting by the floor vs. by the office

A landlord who only leases entire floors gets simple bookkeeping, but a two-person startup leasing a floor uses 5% of it — the rest sits stranded, unrentable to anyone else. Lease by the individual office instead, and you need a security deposit (a "guard wall") for each office, which adds up fast if offices are small. Siloz leases floors (subarrays); ZebRAM leases with a deposit per office (guard row per data row); Citadel leases in 16-row "suites," a size chosen so the deposit-per-suite is cheap but suites rarely sit half-empty for long.

Where it breaks: real office leases don't automatically merge when a tenant expands into the office next door — Citadel's zone expansion does exactly that, for free.
Zero-distance rule · Zonelets

Roommates with no wall at all

Two strangers sharing a dorm room can't "hammer" each other by being loud in their own room and disturbing the room itself — disturbance only travels to neighboring rooms. So the cheapest possible isolation for two tiny, distrustful tenants is: no wall between them, just make sure the rooms on either side of this shared room are empty. That's a zonelet — many small domains packed into one data row, protected only at the row's edges.

Where it breaks: real roommates can still interfere with each other in the room (theft, noise) — Citadel's guarantee is specifically about RH bit flips, not general isolation; other side channels are out of scope (§2.3).
Amortizing guard rows · Zone expansion

Knocking through to the office next door

If you already rent an office and the one next door becomes free, knocking through the shared wall to expand is cheaper than renting a brand-new office across the building (which needs its own new deposit/guard wall). Citadel always tries this first: grow an existing zone into an adjacent free chunk, so the NG guard rows already paid for the first chunk cover the whole enlarged zone too.

Where it breaks: real office expansion is permanent; Citadel can also shrink and split a zone back into pieces when a domain frees memory, which physical renovation can't easily undo.
Complex DRAM addressing · The GRT

A city with renumbered streets

If a city occasionally renumbers a whole city block (mirroring/inversion) or reshuffles house numbers within it (scrambling), you can't assume "house #12" is in the same physical spot everywhere — you need a directory that maps the logical address you care about to wherever it actually lives today. The Global Row Table is exactly that civic directory, built once at boot from the DIMM's known remapping scheme.

Where it breaks: a city directory is looked up occasionally; the GRT is consulted on every single page (de)allocation, though the paper notes this is cheap and off any hot path.
Loss vs. stranding · The universal trade-off

A thermostat with only two settings

Set your reservation chunk size very small and you pay a deposit (guard row) constantly — high loss, low stranding, like ZebRAM. Set it very large and you rarely pay a deposit but often rent far more space than you use — low loss, high stranding, like Siloz. There's no setting that eliminates both; Citadel's 16-row default is simply the point on that dial the paper measured as cheapest overall.

Where it breaks: a thermostat has one dial; Citadel effectively has two (chunk size and the zonelet switch threshold), tuned somewhat independently.
The full mechanism

How Citadel actually works

From the physical row rule to the kernel code path that enforces it.

1 · The physical rule, precisely

Citadel's one assumption: RH effects reach rows at a distance of 1 to NG from an activated row, and no further. From that, its enforcement rule is: isolate domains either by colocating them in the same global row (distance 0 — safe by definition), or by separating them with ≥NG unmapped guard rows. Every zone in the system starts with NG guard rows before any of its data rows — so two zones are always separated by at least NG unmapped rows, regardless of what sits between them.

2 · Chunk size: the guard-row-loss vs. domain-count trade-off

Every zone's first chunk pays NG guard rows regardless of chunk size, so worst-case capacity loss is simply NG / chunk_size. Smaller chunks mean more, smaller reservations — more supported domains, but a bigger fraction of each reservation is guard row.

These are worst-case, unamortized numbers. Measured average loss stays under 2% even at chunk size 8, because zone expansion (§3 below) usually avoids paying for a fresh guard row at all.

3 · Allocation flow: zone reuse before zone expansion before new zone

On every allocation request, Citadel tries the cheapest option first:

if domain's footprint < switch_threshold (12MB):
    serve from a zonelet                      # 1 data row + N_G guard rows
else:
    if existing zone has free space:  serve from it        # cheapest: 1
    elif an adjacent chunk is free:   expand the zone        # cheapest: 2
    else:                            reserve a new chunk,
                                    starting a new zone          # pays N_G guard rows again

To make future expansion likely to succeed, Citadel checks the chunks adjacent to a candidate location before committing a new zone there, favoring spots with free neighboring chunks it can later grow into. Deallocation runs the same logic backwards: shrink a zone by dropping an empty trailing chunk, or split it in two if a hole opens in the middle, using only bitvector operations (no data movement).

4 · Zonelets: protecting millions of tiny domains

A dedicated 16-row chunk for a domain that uses one row is 93% wasted (14 unused data rows + 2 guard rows, out of 16). Below the switch threshold, Citadel instead stripes an available chunk into alternating guard/data rows — a zonelet per data row — so each chunk of size c yields ⌊c/(NG+1)⌋ zonelets. Zonelets have high relative loss (67% with NG=2) but the domains using them are collectively a tiny fraction of total memory (Fig. 1b), so the absolute impact stays small — with zonelets alone, Citadel can protect up to 10.48 million 4KB-scale domains.

💡
Why this matters if you work on tiered/CXL memory: "stranding" as a named cost is the same concept Berger et al. use for CXL memory-pool fragmentation (cited as ref. [6] in this paper) — a domain/tenant reserving a pool slice it doesn't fully use. Citadel's two-tier chunk/zonelet split is structurally the same fix pattern as giving small tenants a shared, finely-sliced pool while large tenants get dedicated coarse-grained slices.

5 · Complex DRAM addressing (the GRT)

Under mirroring/inversion, a logical global row occupies up to 4 physical locations; under scrambling, row-ID bits within each 8-row group get hashed. Citadel's fix is a 256KB Global Row Table, populated once at boot from the known DIMM mapping, that translates a logical row-ID to its physical location(s) — looked up only at (de)allocation time, never on the hot access path. The practical cost: the natural chunk-size ceiling drops to 32MB (bounded by the 8-row groups that scrambling can't cross), and worst-case guard-row loss rises to 25% at NG=2, since a chunk may now need guarding from up to 4 physical neighbors instead of 2.

Follow the numbers

Worked examples

Four calculations straight from the paper's own parameters, done by hand.

① Why 16 rows, and not 4 or 64?

Guard-row loss = NG / chunk_size. With NG=2, what does that give you at the extremes the paper mentions?

  1. 4-row chunks: 2/4 = 50% worst-case loss — the paper explicitly flags this as the reason very small chunks are unusable.
  2. 8-row chunks: 2/8 = 25% — still steep.
  3. 16-row chunks: 2/16 = 12.5% — the chosen default, and the point where loss stops dominating.
  4. 32-row chunks: 2/32 = 6.25% (paper rounds to "6%") — lower loss, but chunks this large start stranding more for small-to-medium domains.
  5. Domain count constraint: to exceed "over a thousand domains" from 128K global rows, chunk size must stay under 128 rows — 16 clears that with wide margin (8,192 max domains) while still balancing loss.
🏰
Insight: 16 isn't a magic number — it's the crossover point in a monotonic loss-vs-stranding trade-off, picked by measuring both sides (§8.4.2) rather than derived analytically.

② Zonelet loss, and why it's still cheap overall

A zonelet is 1 data row + NG guard rows. What's its loss at NG=2 versus the NG=4 the paper studies as a more conservative setting?

  1. NG=2: total rows = 1 + 2 = 3; loss = 2/3 = 66.7%, which the paper rounds to "67%."
  2. NG=4: total rows = 1 + 4 = 5; loss = 4/5 = 80% — even steeper.
  3. But zonelets are only used below the 12MB switch threshold — background processes and page-table pages, which Fig. 1b shows are a small slice of total system memory (most memory sits in a few large processes, which use chunks, not zonelets).
  4. So a 67–80% loss rate applies to a small base, keeping its contribution to the system-wide 7.2% average modest — this is the same amortization-by-scale logic as primer 9's "high demand ≠ high system cost."
💡
This is the same reasoning as batching cold, tiny objects in a slab allocator: paying high relative overhead on a small aggregate footprint beats paying even modest overhead across the whole system uniformly.

③ Static metadata for a 128GB server

Table 1's formula: chunk metadata = 544 bytes/chunk (a 512-byte free-page bitvector + ~32 bytes of flags/pointers). With 128GB capacity, 1MB global rows, and 16-row chunks:

  1. Number of chunks: C = 237 / 220 / 16 = 217 / 16 = 8,192 chunks.
  2. Chunk metadata total: 8,192 × 544 B = 4,456,448 bytes ≈ 4.25 MB.
  3. Chunk occupancy bitvector: 8,192 / 8 = 1,024 bytes (1 bit per chunk, allocated/free).
  4. Plus ~68 B misc (locks, domain list, stats) → total ≈ 4,457,540 bytes ≈ 4.25 MB, matching the paper's reported 4.26 MB static overhead (the GRT's 256KB only applies under complex addressing, and is excluded here).
  5. As a fraction of 128GB: 4.25MB / 131,072MB ≈ 0.003% — Citadel's bookkeeping is essentially free next to the loss/stranding budget.
🏰
Insight: almost the entire 7.2% overhead is loss/stranding from the security design, not implementation bookkeeping — the allocator itself is nearly weightless.

④ Scaling to 57,000 domains (mix9)

Mix9 emulates ~56,300 page-table domains plus 512 background processes — about 57K domains total. Per-domain dynamic metadata is 56 bytes; per-zone is 48 bytes. Roughly how much dynamic metadata should that cost?

  1. Domain metadata: 57,000 × 56 B ≈ 3.19 MB.
  2. Zone metadata (assume ~1 zone/domain for mostly-small, single-chunk-or-zonelet domains): 57,000 × 48 B ≈ 2.74 MB.
  3. Back-of-envelope total: ≈ 5.9 MB — some domains fragment into more than one zone (shrink/split), which accounts for the paper's slightly higher measured peak.
  4. Paper's reported max: 7.5 MB, for a system managing 57K domains — the same order of magnitude, confirming metadata scales roughly linearly with domain count, not with total memory.
💡
This is exactly the scaling property that matters if you were designing per-tenant metadata for a CXL-pooled or tiered-memory system: cost tracks the number of isolation units, not the pool's total capacity.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
Using loss = NG/chunk_size with NG=2, what's the worst-case guard-row loss for a 64-row chunk?
Show answer
2/64 = 3.125%. Notice the trend: doubling chunk size always halves worst-case loss — but Fig. 12b shows stranding rises as chunk size grows, so this isn't a free lunch.Misconception: that bigger chunks are strictly better because loss keeps shrinking. Loss and stranding move in opposite directions with chunk size — you're choosing a point on a trade-off curve, not approaching an optimum.
Problem 2 · medium
A system has 131,072 global rows. If Citadel used 8-row chunks instead of 16, how many domains could it support at most, and what's the worst-case loss trade-off for that choice?
Show answer
Max domains = 131,072 / 8 = 16,384 (double the 16-row case). Worst-case loss = 2/8 = 25% (double the 16-row case's 12.5%). You get roughly 2× the domain ceiling at roughly 2× the theoretical loss — though the paper measures actual average loss under 2% at chunk=8 thanks to zone expansion, so the real-world cost is much smaller than the worst case suggests.Misconception: that "worst-case loss" is what you'll actually pay. Zone expansion means most zones never pay a second guard row, so measured loss tracks far below the theoretical ceiling.
Problem 3 · hard
Recompute zonelet loss for NG=4 (the more conservative guard-row count the paper separately studies). Is a zonelet still worth using at that NG?
Show answer
Total rows per zonelet = 1 data + 4 guard = 5; loss = 4/5 = 80%. It's still "worth it" in the sense that it's the only option for domains small enough to need row-level isolation — the alternative (a full 16-row chunk for a <1MB domain) would strand even more of the chunk. But 80% loss on the (small) zonelet population pushes total system overhead up — the paper measures overall overhead rising to ~9% at NG=4 across all its chunk sizes, not just zonelets.Misconception: that a single overhead number (loss %) tells you whether a mechanism is "good." What matters is loss × (fraction of total memory using that mechanism) — a high rate on a small base can still be the cheapest available option.
Problem 4 · medium
A domain has been allocated a full 16-row chunk (NG=2, so 14 usable data rows) but currently only uses 2 rows of actual data. What fraction of the whole chunk is stranded?
Show answer
Unused-but-reserved rows = 14 − 2 = 12. Stranding as a fraction of the whole 16-row chunk = 12/16 = 75%. (If you instead measure stranding only against the 14 usable data rows, it's 12/14 ≈ 86% — the paper measures relative to total memory capacity, so use the 16-row denominator.)Misconception: that stranding only matters for "wrong-sized" domains. Even a domain that will eventually grow into its whole chunk is, in the meantime, stranding real memory other domains can't use — Citadel's zone-shrink/split logic exists specifically to recover this while it's happening.
Problem 5 · hard
A workload mix reserves 20GB spread across 500 medium-sized domains using 16MB chunks. Each domain's last (partially-filled) chunk averages 50% empty of its 14MB usable data space. Estimate total stranded memory, in GB, and as a fraction of the 20GB reserved.
Show answer
Per domain: 50% of 14MB usable data ≈ 7MB stranded in the trailing chunk. Across 500 domains: 500 × 7MB = 3,500MB ≈ 3.4 GB stranded. As a fraction of the 20GB reserved: 3.4/20 ≈ 17% — notably higher than the paper's measured system-wide averages, because this scenario assumes every domain has a half-empty trailing chunk (a worst-case, not a measured average).Misconception: that per-domain stranding examples generalize directly to system-wide averages. Real workload mixes have domains at all stages of filling their chunks — some nearly full, some just-created — which is why measured averages (5.7% system-wide) are far below this single-domain worst case.
Problem 6 · medium
Doubling NG from 2 to 4 doubles worst-case guard-row loss at any fixed chunk size, yet the paper's measured average overhead only rises from 7.2% to about 9%, not 14.4%. Why the gap?
Show answer
Two reasons. First, zone expansion means most zones' guard-row cost is amortized over many chunks, not paid per-chunk — so the theoretical per-chunk worst case rarely materializes at scale. Second, the paper notes that higher NG sometimes reduces stranding, because chunks with fewer usable data rows fill up (and free up) faster, giving more opportunities to shrink/split zones. The two overhead currencies (loss up, stranding sometimes down) partially offset.Misconception: that a single-parameter change (NG) scales linearly through the whole system. Citadel's optimizations (expansion, shrink/split) sit between the raw parameter and the measured outcome, and they don't respond linearly.
Problem 7 · hard
Domain A occupies rows 4–5 of a chunk whose row 3 is a guard row. Domain B wants to start a new zone in row 6, immediately after A's chunk. Does row 6 need its own guard row separating it from A, or can B's zone simply begin there?
Show answer
B's zone must begin with its own NG guard rows, because A and B are different (untrusting) domains — the zero-distance exception only applies to data from the same domain sharing a row, or to rows already separated by guard rows. Placing B directly adjacent to A's data row without a guard row would violate Citadel's core isolation rule and defeat the whole design.Misconception: that "adjacent chunk" and "adjacent domain-data" are the same question, or that guard rows are only needed between chunks, not between domains. The rule is about domain trust boundaries, not chunk boundaries — chunk boundaries just happen to be where Citadel is willing to place a domain boundary.
Problem 8 · easy
Citadel is a pure software change to the Linux kernel's memory allocator. Why doesn't it need any new DRAM hardware to provide real security guarantees?
Show answer
Because RH's root cause is physical row adjacency, and physical row placement is exactly what the OS's memory allocator already controls — which physical page backs which allocation. Given a known (or reverse-engineered) DRAM address mapping, the allocator can simply refuse to ever place two untrusting domains' data within NG rows of each other. No new counters, refresh logic, or DRAM circuitry are required — only correct bookkeeping of where things are.Misconception: that stopping a hardware-level attack requires a hardware-level fix. Rowhammer's disturbance is physical, but the choice of which data lives where physically is a software decision the allocator was already making — just not with security in mind.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does Citadel guarantee?▾
That no Rowhammer-induced bit flip caused by activity in one security domain can land in another domain's data — by construction, because any two domains are either in the exact same global row (safe by the RH threat model) or separated by ≥NG unmapped guard rows. It does not protect against microarchitectural self-hammering (e.g., a domain evicting its own cache lines) or non-RH side channels.
Q2How is this different from just running everything in separate VMs or containers?▾
VM/container isolation is a virtual-memory and permissions concept — it says nothing about where the underlying physical pages land in DRAM. Two containers can be logically isolated yet have their physical pages sitting in adjacent DRAM rows, fully exposed to RH. Citadel adds the missing physical-placement guarantee underneath whatever logical isolation you already have.
Q3Why can domains sharing the same row skip guard rows entirely?▾
Rowhammer's disturbance model is about a hammered row disturbing its neighbors — there's no mechanism by which a row disturbs itself. So two domains' data living in the same row are at "distance 0," which is inherently safe under the paper's threat model. This is the loophole zonelets exploit to protect many tiny domains cheaply.
Q4How many domains can Citadel actually support?▾
Thousands of full-sized (chunk-based) domains — 8,192 max at the default 16-row chunk size on a 128K-row system — or, if all memory were instead devoted to zonelets, up to 10.48 million KB–MB-scale domains like individual page tables. That 10.48M figure is the ceiling if zonelets alone consume the whole system, not an amount added on top of the 8,192 chunk-based domains; in practice a real system splits memory between both mechanisms.
Q5What is memory "stranding," and where does the term come from?▾
Stranding is memory reserved for one domain but currently unused by it, and therefore unavailable to anyone else — distinct from guard-row "loss," which is memory nobody can ever use. The paper borrows the term from CXL memory-pool literature (Berger et al., cited as ref. [6]), where the same phenomenon shows up when a tenant's pool allocation exceeds its actual usage.
Q6Does Citadel slow anything down?▾
In the paper's measurements, no — allocation/deallocation logic consumes under 1% of runtime, and across 40 workloads performance differed by at most +15%/−13%, averaging a 4.1% speedup over the stock buddy allocator (the authors note they couldn't fully pin down the cause, but observed it consistently across servers).
Q7Why does Citadel need to know the DRAM address mapping?▾
Because "isolate by physical row" only works if you actually know which physical DRAM row a given OS page maps to. All software-based RH domain-isolation schemes (ZebRAM, Siloz, Citadel) share this dependency; the mapping is typically obtained from published DIMM specs or DRAM-testing infrastructure (FPGA-based testers, RH profilers), not derived at runtime.
Q8What happens under "complex" DRAM addressing (mirroring, scrambling)?▾
A logical global row can map to up to 4 physical locations, and a chunk can have up to 4 physical neighbors instead of 2 — meaning zone expansion succeeds less often, and worst-case guard-row loss can rise toward 25%. Citadel remains applicable (via the Global Row Table) but with higher overhead than the simple-mapping case evaluated in the main results.
Q9Does Citadel support huge pages?▾
2MB huge pages are naturally supported, since they map to consecutive global rows within an 8-row group that even complex addressing preserves. 1GB pages are not supported in the prototype under complex addressing (would need a costly, contrived scheme); the authors suggest a hybrid design using Siloz-style subarray isolation for a TB-scale system's 1GB-page portion instead.
Q10What about shared memory between processes?▾
Shared memory is disabled by default in the prototype — the paper notes that sharing is commonly disabled in RH-isolation designs because it would otherwise imply cross-domain physical access, and disabling it eliminates many attacks outright. The authors measured under 0.1% of pages with refcount > 1 in their workloads, so the missing feature has negligible impact on their results — extending Citadel to place shared pages in zonelets is described as a modest, feasible extension.
Q11How does Citadel compare to hardware RH defenses (TRR, PRAC)?▾
Hardware defenses like TRR have been repeatedly circumvented (e.g., TRRespass), and JEDEC's newer PRAC framework adds ~9% DRAM area and turns every activation into a read-modify-write, hurting performance — and still isn't universally deployed or guaranteed secure. Citadel is a complementary, software-only layer deployable today, on existing hardware, independent of what mitigations (if any) the DRAM itself implements.
Q12What's left for future work?▾
The authors flag: fully implementing per-page-table-page domains (currently emulated in the evaluation), a flexible API letting a single process request multiple domains for sub-region protection, RH-safe shared memory support, and more robust automated tools for reverse-engineering DRAM address mappings — especially for DDR5, where inducing RH bit flips (needed by current profilers) is harder.

Glossary & provenance

Every term in one place, then which numbers came from the paper vs. this guide's framing.

Core terms
Security domainA memory footprint that must be protected from RH originating outside it — typically a process, but also individual page-table pages or programmer-chosen sub-regions.
ZoneOne contiguous physical-memory region belonging to a domain; a domain may own several non-contiguous zones.
Reservation chunkCitadel's coarse memory-reservation primitive — a configurable run of contiguous global rows (16 by default), amortizing guard-row cost.
ZoneletCitadel's fine-grained primitive — one data row plus NG guard rows — for KB–MB domains, exploiting same-row colocation safety.
Global rowThe set of physical DRAM rows sharing the same row-ID across all banks in a NUMA domain; the OS/hardware bridge unit Citadel reserves and isolates in.
Guard row (NG)An unmapped global row left empty to absorb RH disturbance; NG = how many are needed per boundary (paper assumes 2 in its main evaluation, and separately studies 4).
Capacity lossMemory permanently sacrificed to guard rows — never usable by any domain.
Memory strandingMemory reserved for a domain but not currently used by it, and thus unavailable to others; term borrowed from CXL memory-pool literature.
Zone expansionGrowing an existing zone into an adjacent free chunk instead of creating a new (guard-row-paying) zone.
Global Row Table (GRT)A boot-time-populated lookup table mapping logical row-IDs to physical DRAM locations, needed under complex (mirrored/scrambled) addressing.
Supporting terms
Buddy allocatorLinux's default physical-page allocator, serving power-of-2 page runs from per-order free lists; Citadel overrides its core entry points.
Switch thresholdPer-domain footprint (12MB default) below which allocations use zonelets, above which they use zones/chunks.
ZebRAMPrior work isolating every data row with an adjacent guard row — simple, but 50%+ capacity loss.
SilozPrior work reserving whole DRAM subarrays per domain — no guard-row loss, but GB-scale minimum reservations and heavy stranding.
PTHammerAn RH exploit flipping bits in page tables to escalate privilege — the reason each page-table page needs its own domain.
Half-DoubleAn RH attack pattern reaching two rows away, motivating NG≥2 and studies recommending NG=4.
PRACJEDEC's Per-Row Activation Counter hardware framework — principled but costly (~9% DRAM area) in-DRAM RH mitigation.
Row-ID stripingMemory controllers spread a page's cache lines across many banks sharing one row-ID, for bank-level parallelism — the reason Citadel isolates by row-ID, not bank.
