SOSP 2026 · A Field Guide

Giving GPU-kernel agents a compiler that checks their work, not just a scoreboard

An LLM can write a GPU kernel that passes its tests and still be 14× too slow — or "pass" by quietly calling PyTorch underneath. This is the plain-English story of Ave, which gives the agent a compile-time proof obligation instead of a pass/fail grade.

📄 "Ave: Guiding Agentic GPU Optimization Using Data-Flow Invariants" · Mai et al. 🎓 Some GPU-microarchitecture basics assumed — the primers cover them ⏱ ~30 min read
🏷️

Tag every value with what it's supposed to be, propagate the tag through every transform, and let an SMT solver flag the exact spot where two tags stop agreeing.
Zero runtime cost — the tags never exist once the kernel actually runs.

Before you begin

Quick glossary + nine ideas the paper assumes you know

You already know memory hierarchies and OS-level tiering; this paper reuses that intuition inside a single GPU kernel, plus a compiler-verification layer on top. The acronym list is a lookup table — skim it, then open whichever primer looks unfamiliar.

1Why a "correct" kernel can still be far from fast▾

An LLM can generate a GEMM kernel that produces numerically correct outputs and still run 1.8–14.3× slower than AMD's hand-tuned hipBLASLt on the same GPU. Correctness and peak throughput are separate goals — the second requires coordinating shared-memory staging, pipelining, and instruction scheduling all at once, without breaking the first.

Now you're ready: Ave's whole premise is that closing this gap needs more than "did the unit test pass" — it needs feedback that can localize which transformation broke which property.
2The GPU memory hierarchy — a familiar shape, a different timescale▾

A GPU kernel moves data through three tiers per thread block: global memory (HBM, slow, huge), shared memory / LDS (fast, on-chip, kilobytes, explicitly staged by the programmer), and registers (fastest, thread-private). This is structurally the same three-tier shape you already reason about with DRAM/NVM/CXL tiering — except here the "promotion policy" is fully static: the kernel author (or agent) decides at compile time exactly which bytes move to which tier and when, rather than an OS heuristic reacting to runtime access patterns.

Now you're ready: every optimization in this paper — pipelining, staging, vectorized loads — is really a decision about which tier holds which tile of data at which point in the kernel, made once, at compile time.
3Wavefronts, tiles, and matrix cores▾

A 64-thread wavefront (AMD's warp) executes in lockstep; several wavefronts share an LDS as a workgroup. Peak throughput comes from MFMA matrix-core instructions, which multiply small tiles (e.g. 32×32×8) per instruction — but only if operands arrive in a fixed, hardware-swizzled layout. A tile is just a memory region plus a layout function mapping logical coordinates to physical offsets, the same abstraction CuTe and Triton use.

Now you're ready: most of Ave's optimizations exist purely to reshape data into the layout MFMA expects — and reshaping is exactly where correctness bugs creep in.
4Why unit tests and profiles are "sparse" feedback▾

A failing test says "wrong answer somewhere." A profile says "slow somewhere." Neither says which line, which thread, which transformation caused it. For a kernel combining ten interacting optimizations, an agent debugging from only these two signals is effectively guessing.

Now you're ready: Ave's core bet is that a third, denser signal — a compile-time invariant check with a concrete counterexample — turns guessing into localized repair.
5Tag functions — labels that ride along with data▾

A tag function attaches a symbolic label (built from coordinates or expressions) to a tensor element. Tags don't exist at runtime — they're a purely compile-time bookkeeping device that the analysis propagates through every assignment, memory move, and shared-memory store.

Now you're ready: "checking correctness" in Ave means checking that tags still agree where they're supposed to, after all the staging and reshuffling.
6Tag assertions — conformity and non-conformity▾

A conformity assertion requires two tags to match (e.g., the Q and K elements fed into one MFMA must share the same head and reduction index). A non-conformity assertion requires tags to differ (e.g., two concurrent producers must not write the same shared-memory slot).

Now you're ready: these two assertion kinds cover the two failure modes that plague hand-optimized GPU code — mismatched operands, and data races.
7Abstract interpretation and SMT, in one sentence each▾

Abstract interpretation means analyzing a simplified model of the program (here, symbolic tags) instead of running it. An SMT solver (Z3) then decides whether a set of tag constraints is satisfiable, and if not, returns a concrete assignment — a witness — showing exactly how it fails.

Now you're ready: Ave's compiler doesn't run the kernel to find bugs; it solves a system of symbolic equations about the kernel and reports the first inconsistency it finds.
8Path-sensitive vs. path-insensitive analysis▾

A path-sensitive analysis tracks every branch combination separately — precise but explosive for heavily-optimized code with many conditionals. A path-insensitive analysis merges information at control-flow joins into one summary per point, trading some precision for tractability.

Now you're ready: Ave deliberately chooses path-insensitive analysis with a specific merge rule (⊥ ≤ concrete tags < ⊤) so it stays fast enough to run every optimization round.
9In-context learning and in-context reinforcement learning▾

In-context learning (ICL): an LLM adapts to a new task from examples in the prompt, no weight updates. ICRL goes further: the prompt itself is treated as a learnable policy, edited after each round based on a reward signal (via "text gradients" — natural-language critiques that rewrite the prompt).

Now you're ready: Ave's planner never retrains a model; it rewrites its own instructions after every optimization round, using invariant violations and runtime speed as the reward.
The whole story in one place

Ave in a nutshell

The problem, the compile-time fix, and how the numbers actually stack up.

LLM agents can generate GPU kernels that pass correctness tests, but "passing tests" and "reaching peak throughput" are different bars. Getting from one to the other means applying intrusive, coordinated transformations — software pipelining, shared-memory staging, instruction scheduling — each of which can silently break a global property like "these two MFMA operands must come from the same logical position." Unit tests and profiles only report the aggregate outcome, not which transformation broke what.

Ave's fix is to make those global properties explicit as data-flow invariants: tag functions attach symbolic labels to tensor elements, tags propagate through every assignment and memory move, and tag assertions require the right tags to agree (or disagree) at each use site. A compiler pass — flow-sensitive, path-insensitive, backed by an SMT solver — checks these assertions entirely at compile time and, on failure, returns a concrete witness: the exact thread ID, coordinate, and program point where two tags disagree.

An ICRL planner proposes optimizations and invariant templates from a curated knowledge base; a lowering agent implements them and instantiates the templates as real tag functions and assertions. A reward combining compilation, invariant, test, and speedup signals drives a text-gradient update to the planner's prompt after every round — no model weights change.

The payoff: on AMD MI300X, across GEMM, flash attention, and MoE — up to 90% of GPU time in LLM inference — Ave's kernels reach 89–99% of hand-optimized-library throughput and beat uncontaminated agentic baselines by 1.62–1176× in geometric mean. On 200 KernelBench tasks, Ave solves 100% of Level 1 and 88% of Level 2 within three attempts.

🍯 Key takeaways

  • Unit tests + profiles give sparse, end-to-end feedback; data-flow invariants give localized, compile-time feedback with a concrete witness.
  • Tags are symbolic and purely compile-time — checking them costs zero runtime overhead.
  • The analysis is deliberately flow-sensitive but path-insensitive to stay tractable on heavily optimized kernels.
  • An ICRL planner (not a fine-tuned model) proposes optimizations and rewrites its own prompt after each round via text gradients.
  • Reward = compiles + invariant score + tests pass + measured speedup — four independent signals, not just "faster."
  • Result: 89–99% of expert-library throughput, 1.62–1176× over uncontaminated agentic baselines, for <1% area-equivalent effort — the checks run in 10–40 ms.
Seven everyday pictures

How to think about Ave

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Tag functions & assertions

Matched luggage claim tags

A checked bag and your claim ticket both carry the same printed code; the loading machine confirms they match before the bag goes on the plane. Ave's tag functions do the same for tensor elements: a Q element and a K element each carry a symbolic tag (head, reduction index), and the assertion at the MFMA use site checks they still match — no matter how many times the data was staged or reshuffled on the way.

Where it breaks: a real luggage tag is checked once, on one bag. Ave's compiler proves the match holds for every thread and every coordinate at once, symbolically — no bag is ever actually scanned.
Compile-time vs. runtime feedback

Spell-check as you type

A spell-checker flags the misspelled word the instant you type it, underneath the cursor. Proofreading after printing 10,000 copies also finds the typo — but tells you nothing about whereit is until you re-read everything. Data-flow invariants are the spell-checker: they flag a mismatched operand at its exact use site during compilation, instead of waiting for a wrong answer or a slow profile at the end of the run.

Where it breaks: spell-check can't fix a bad plot, and invariants can't invent a better algorithm — both only catch violations of properties someone already specified.
The SMT witness

A crash dump, but before the crash

A crash dump tells an engineer the exact register values and line number where a program died. Ave's SMT solver produces the same kind of concrete evidence — thread ID, loop index, coordinate, program point — for a property that was never actually executed. It solved a symbolic model of the kernel and found the assignment of variables that breaks it.

Where it breaks: a real crash dump comes from an execution that happened. This "dump" is manufactured entirely from the compile-time abstraction — it's a proof of what would go wrong, not a record of what did.
Merging at control-flow joins

A "no comment" doesn't override a known fact

If one witness gives a firm account and another simply has "no comment," the firm account stands — it isn't contradicted by silence. Ave's merge rule works the same way: a constant (⊥) merges with any concrete tag to produce that tag unchanged, while two different concrete tags merge to ⊤ ("conflict, don't trust this value"). That's exactly why rQ = 0 if OOB else Q[...] keeps Q's real tag — the zero branch is silence, not a contradiction.

Where it breaks: real testimony can be partially reliable; the lattice has no middle ground — it's either the one true tag, a harmless constant, or "no longer trustworthy," full stop.
Familiar shape, different timescale

A three-tier memory system, resolved once

Global memory, shared memory, and registers form the same tiered shape as DRAM/NVM/disk — slowest-and-biggest at the bottom, fastest-and-smallest at the top. But GPU "tiering" here is a compile-time decision baked once per kernel launch, on a microsecond timescale, not a heuristic reacting to access patterns over an application's lifetime the way an OS memory manager does.

Where it breaks: there's no analogue of a hot/cold page classifier here — the mapping of which tile lives in which tier is fully static, chosen by the agent and checked by the compiler, not adapted at runtime.
Tiles and layouts

A floor plan, not a wiring diagram

An architect's blueprint labels rooms symbolically — "kitchen here, pantry there" — without specifying every stud and wire; a builder computes the concrete details later from that plan. Ave's tiles work the same way: a layout function maps logical coordinates ("row 5, column 12") to physical byte offsets, letting the DSL express reshuffles algebraically instead of enumerating every address.

Where it breaks: the floor plan is advisory; Ave's layout algebra is executable and exact — every coordinate really does resolve to one physical offset, checked by the compiler, not just implied.
The ICRL loop

A coach rewriting the game plan, not retraining the players

A coach doesn't rebuild a player's muscles after a loss — they rewrite the notes for next game based on film review. Ave's planner keeps the same fixed LLM weights every round; only the benchmark-local prompt changes, edited by a text-gradient critique built from invariant violations and measured speed.

Where it breaks: a coach's notes are informal intuition. ParameterUpdate is a constrained edit driven by an explicit numeric reward (compile + invariant + test + speedup), not a vibe.
The full explanation

How it actually works

From DSL syntax to SMT witness to prompt update — with the paper's own example threaded through.

1 · Tags and assertions in the DSL

A tag function maps tensor coordinates to symbolic tags. For flash attention's Q and K tensors, the tags are the attention-head and reduction-dimension indices — the two things that must match for a valid dot product:

TQ = Q[sq,hq,d] → (hq/gqa, d)
TK = K[sq,hkv,d] → (hkv, d)
# at the MFMA use site:
assert tag(etK[...]) == tag(etQ[...])  # conformity: must agree

The assertion doesn't check values — it checks that the two operands are, symbolically, "the same head, same reduction position," regardless of how many times the data was staged through shared memory or transposed on the way there.

2 · Propagating tags — flow-sensitive, path-insensitive

The compiler lowers the DSL to MLIR and tracks tags through every assignment and shared-memory access, byte by byte. At a control-flow join, it merges incoming tags with a small lattice: constants (⊥) never conflict, matching concrete tags stay themselves, and mismatched concrete tags collapse to ⊤ ("no longer trustworthy").

merge(t1, t2) =
    t1              if t2 ≤ t1
    t2              if t1 < t2
    ⊤               otherwise   # e.g. two different concrete tags
📎
Merging (not enumerating branches) is what keeps this tractable on kernels with many conditionals — the trade-off is precision: Ave can miss a violation that only occurs on one specific branch combination, in exchange for analyzing every optimized kernel in milliseconds.

3 · The reward function

Each optimization round produces one candidate kernel, scored on four independent signals: does it compile (𝐶ₜ), what fraction of invariant assertions pass (𝐼ₜ), do unit tests pass (𝑈ₜ), and — only if all three hold — how much faster is it (Δₜ)?

I_t = 1 − |V_t| / |A_t|     # fraction of assertion sites that failed
Δ_t = (ℓ* − ℓ̂_t) / ℓ*      # latency improvement, only if C_t=U_t=1 and V_t=∅
R_t = C_t + I_t + U_t + Δ_t
💡
Why four terms, not one? A single "did it get faster" reward can't distinguish "close but one operand mismatch" from "completely broken" — both look like zero. Splitting the reward gives the planner a gradient even when the candidate never reaches the profiler.

4 · The agentic loop, and the paper's own worked round

Planner → Selector → Lowering agent → Validate → Profile, with the reward feeding a text-gradient update back into the planner's prompt for the next round. Section 6 of the paper walks through exactly one failure-then-fix cycle for flash attention's QKᵗ step — carried through with real numbers in the next tab.

Worked examples

Four traces using the paper's own figures — a failed round, a fixed round, the real cost of skipping invariants, and where "1176×" actually comes from.

① The paper's own failed round — computing the reward

Section 6: the lowering agent stages K in shared memory but reads it back with the wrong layout. Compilation succeeds; the single tag assertion at the MFMA site fails; tests never run.

  1. Compilation succeeds: 𝐶ₜ = 1.
  2. One assertion site, one failure: |𝐴ₜ| = 1, |𝑉ₜ| = 1 → 𝐼ₜ = 1 − 1/1 = 0.
  3. Tests never run because 𝑉ₜ ≠ ∅ → 𝑈ₜ = 0, and profiling never happens → Δₜ = 0.
  4. Reward: 𝑅ₜ = 𝐶ₜ + 𝐼ₜ + 𝑈ₜ + Δₜ = 1 + 0 + 0 + 0 = 1. (The paper states 𝑅ₜ = 1 + 𝐼ₜ < 2, consistent here since 𝐼ₜ = 0.)
  5. The witness the solver returns: i=0, j=1, tid=0, wid=wtid=0, idxq=idxh=0 — pinpointing the exact thread and loop index where tag(K) ≠ tag(Q).
🍯
Insight: a reward of 1 (out of a possible ~4) tells the planner "it compiles but something concrete is wrong" — far more useful than a bare test failure, and it comes with the exact repair target attached.

② Round two — the fix, and its reward

Guided by the witness, the planner's next proposal reinterprets K's shared-memory layout as (2,32,8,2) and reads it by the correct index; the same assertion now passes, tests pass, and the kernel profiles successfully.

  1. Compilation succeeds: 𝐶ₜ = 1.
  2. The one assertion now passes: |𝑉ₜ| = 0 → 𝐼ₜ = 1 − 0/1 = 1.
  3. Tests run and pass: 𝑈ₜ = 1. Profiling now runs, producing a measured latency ℓ̂ₜ.
  4. Suppose the fix is also 5% faster than the prior best kernel: Δₜ = (ℓ* − ℓ̂ₜ)/ℓ* = 0.05.
  5. Reward: 𝑅ₜ = 1 + 1 + 1 + 0.05 = 3.05 — the maximum possible band, plus a small speed bonus. This is the candidate that replaces the current best kernel.
💡
Same optimization intent, one layout bug apart — the reward swings from 1 to just over 3. That gap is the localized feedback signal the paper argues unit tests alone can't provide.

③ What skipping invariants costs — Table 4, KernelBench

Ave's ablation reruns the same 60 selected GEMM/convolution tasks with the invariant templates stripped out (no tag functions, no witnesses — only compile/test feedback survives).

  1. Level-2, GPT-5.6 Sol, no invariants: 12 of the tasks reach a kernel that applies all three requested transformations (MFMA + pipelining + OOB-guarded loads).
  2. Same tasks, same model, with invariants: success rises to 25.
  3. That's more than double — (25 − 12)/12 ≈ 108% more tasks solved — from adding a compile-time signal, with no change to the model or the knowledge base.
  4. Cost moves the other way too: Table 4 shows invariants reduce mean turns (6.50 → 6.12) and tokens (0.25M → 0.22M) for this group — cheaper and more reliable.
🍯
Insight: the invariants aren't just a correctness safety net that costs extra agent effort — they actively reduce the trial-and-error the agent needs, because the failure signal is already localized.

④ Tracing "1.62–1176×" back to Table 1

The abstract's headline range spans two very different comparisons. Where do the endpoints come from?

  1. Low end (1.62×): GEMM, GPT-5.6 Sol. Ave = 0.89 normalized throughput, KernelFalcon = 0.55. 0.89 / 0.55 = 1.618… ≈ 1.62×.
  2. High end (1176×): flash attention, GPT-5.6 Sol. Ave = 0.99, CUDAForge = a rounded 0.001 in the printed table. 0.99 / 0.001 = 990× using the rounded figure alone — the paper's unrounded 1176× reflects CUDAForge's true (smaller) unrounded value.
  3. Sanity check with a cleaner pair: fused MoE, GPT-5.6 Sol. Ave = 0.94, KernelFalcon = 0.12. 0.94 / 0.12 ≈ 7.83×, matching the paper's stated "8× relative to KernelFalcon" for MoE.
  4. Takeaway: the same invariant machinery produces a modest multiple against a reasonably strong baseline (Triton-backed KernelFalcon) and an enormous one against a baseline that essentially fails the workload (CUDAForge on attention/MoE) — both are honestly the same underlying gap, just measured against different denominators.

Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
Does checking a tag assertion add any instructions to the compiled GPU kernel that runs on the device?
Show answer
No. Tags are purely symbolic, compile-time constructs tracked by the MLIR-based analysis pass; they are never materialized as data or checked by generated device code. All checking happens in the compiler, before the binary exists.Misconception: confusing tag assertions with runtime assert() calls or bounds checks, which do cost cycles. Ave's invariants cost exactly zero at runtime by design.
Problem 2 · medium
Given rQ = 0 if isOOB(...) else Q[i], where Q[i] carries tag t and the literal 0 carries tag ⊥, what tag does rQ get after the merge, and why?
Show answer
rQ keeps tag t. The merge rule says merge(⊥, t) = t whenever t is concrete — a constant never overrides or conflicts with a real tag, it simply defers to it. Only two different concrete tags merging would produce ⊤.Misconception: assuming any branch in a merge "dilutes" or invalidates the tag. Constants are transparent to the lattice; only genuine tag disagreement is.
Problem 3 · medium
A candidate kernel compiles, has 4 assertion sites with 1 failing, passes no tests (because testing is gated on invariants), and was never profiled. Compute R_t.
Show answer
C_t = 1. I_t = 1 − |V_t|/|A_t| = 1 − 1/4 = 0.75. U_t = 0 (tests didn't run). Δ_t = 0 (never profiled). R_t = 1 + 0.75 + 0 + 0 = 1.75.Misconception: thinking the reward only reflects "did it get faster." Three of the four terms fire before speed is even measured — the reward is dense long before profiling.
Problem 4 · hard
A kernel passes every unit test and every invariant check, and profiles 40% faster than the prior best. Should Ave trust it as a genuine optimization win, with no further scrutiny?
Show answer
Not automatically. The paper explicitly flags reward hacking — a kernel can pass tests and invariants while taking a shortcut such as a PyTorch fallback, a precomputed/zeroed output, or branching on benchmark-specific values, none of which the declared invariants necessarily cover. Ave's evaluation pairs automated checks with a manual review for known shortcut patterns; data-flow invariants reject shortcuts that violate a declared use-site relationship, but the paper is explicit that neither mechanism is exhaustive.Misconception: "passed unit tests + passed invariants" = "definitely a correct, non-hacked optimization." The paper treats this as necessary, not sufficient — invariants only catch violations of properties someone thought to encode.
Problem 5 · easy
Why can't Ave write a data-flow invariant asserting that every <expert, token> tuple in an MoE kernel lands in the correct sorted bucket?
Show answer
Ave's analysis tracks tags through registers and shared memory but does not model the full heap or track tags written to global memory, to keep the analysis tractable. MoE routing sorts tuples through global memory, so this property falls outside what Ave's current vocabulary can express — the paper lists it explicitly as a known limitation, not an oversight caught late.Misconception: assuming data-flow invariants can express any correctness property. They're scoped to what the flow-sensitive, path-insensitive analysis over registers/shared-memory can track.
Problem 6 · medium
Why is Ave's analysis path-insensitive rather than path-sensitive, and what real failure mode could this choice miss?
Show answer
Path-sensitive analysis would enumerate every branch-condition combination separately, which is intractable for heavily optimized kernels with many conditionals (pipelining stages, OOB guards, wavefront specialization). Path-insensitive merging keeps analysis fast enough to run every round. The cost: a violation that only manifests on one specific, rare combination of branches could be masked by the ⊥/concrete-tag merge rule if that branch happens to carry a harmless constant tag elsewhere, and would not be caught.Misconception: treating Ave's compile-time checks as a full formal-verification guarantee. The paper is explicit that this is a tractable approximation, not a proof of correctness for every execution path.
Problem 7 · hard
Using Table 1's GEMM row for GPT-5.6 Sol (Ave = 0.89, KSearch = 0.36, CUDAForge = 0.07, all normalized to hipBLASLt), compute how many times faster Ave's kernel is than each.
Show answer
Ave / KSearch = 0.89 / 0.36 ≈ 2.47×. Ave / CUDAForge = 0.89 / 0.07 ≈ 12.7×. Both are consistent with — and smaller than — the paper's reported overall range of 1.62–1176×, since that range spans all three workloads and all three models, not just this one cell.Misconception: assuming every pairwise ratio in the paper should land near the headline 1.62–1176× range. That range is the extremes across the whole evaluation grid, not a typical single comparison.
Problem 8 · medium
Why does Ave separate "algorithm selection" (e.g., restructuring naïve attention into tiled flash attention with online softmax) from "invariant-guarded low-level optimization," rather than applying invariants from the very first draft?
Show answer
Data-flow invariants validate that a given concrete transformation preserves a declared property — they don't propose algorithmic restructurings. The paper notes that applying invariants while the algorithm itself is still changing could constrain exploration prematurely, since the invariant templates are written against a specific implementation shape. So the pipeline runs algorithm selection and initial kernel generation first (handled by the planner/knowledge base), then guards subsequent low-level optimizations with invariants once the algorithmic shape is settled.Misconception: thinking invariants are a general-purpose tool for discovering better algorithms. They're a guardrail for preserving correctness across transformations of an already-chosen algorithm — algorithmic creativity stays with the LLM planner.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What exactly is a "data-flow invariant" here?▾
A compile-time relationship among symbolic tags that must hold wherever a tag assertion is written — e.g., "the Q and K operands feeding this MFMA must carry the same head and reduction-index tag." It's checked once, statically, by the compiler; it never exists as a runtime check.
Q2How is this different from a regular unit test?▾
A unit test runs the kernel and compares outputs — it tells you the final answer was wrong, not which transformation or line caused it. A tag assertion is checked symbolically at compile time and, on failure, returns a witness naming the exact thread, coordinate, and program point — localized feedback instead of an end-to-end verdict.
Q3Doesn't tracking symbolic tags through a whole kernel get expensive?▾
The paper reports invariant checks taking 10–40 ms per kernel — negligible next to LLM inference latency. The two design choices that make this cheap are path-insensitive merging (no branch enumeration) and byte-granularity tracking scoped to registers and shared memory, not the full heap.
Q4What is ICRL, and how is it different from fine-tuning the model?▾
In-context reinforcement learning treats the prompt, not the model weights, as the thing being optimized. After each round, a reward (compile + invariant + test + speedup) drives a text-gradient edit — a natural-language critique that rewrites the benchmark-local prompt. The underlying LLM (e.g. GPT-5.6 Sol) never changes.
Q5Can Ave invent a new algorithm, like flash attention itself?▾
No — the paper is explicit that discovering new algorithmic optimizations is outside Ave's scope. Data-flow invariants validate concrete transformations of an already-chosen algorithm; algorithm selection is left to the planner and its knowledge base, informed by prior human-designed techniques.
Q6Why is the analysis "path-insensitive," and is that a weakness?▾
It's a deliberate tractability trade-off: merging tag information at control-flow joins (rather than tracking every branch combination) keeps the analysis fast enough to re-run after every optimization round. The cost is that a violation confined to one rare branch combination could, in principle, be missed — Ave targets actionable, dense feedback, not full formal verification.
Q7What can't Ave's invariants express?▾
Properties depending on values written to global memory or the full heap — e.g., that MoE token-routing tuples land in the correct sorted bucket, or that multi-GPU cross-device buffers (as in COMET) are exchanged correctly. Byte-granularity tracking also means packed sub-byte formats like FP4 are invisible to invariants at the nibble level.
Q8How does the SMT solver factor in?▾
Propagated tags and assertions are encoded as SMT constraints over the layout algebra; Z3 checks satisfiability. If unsatisfiable, Z3 returns a concrete assignment — the witness — that shows exactly which symbolic variables (thread ID, loop index, coordinate) make the assertion fail.
Q9Does Ave's approach generalize beyond AMD MI300X?▾
Yes. The authors added NVIDIA Hopper and AMD CDNA4 backends with localized changes — roughly one person-week each — by exposing new hardware intrinsics (WGMMA/mbarrier for Hopper, FP4 for CDNA4) and adding architecture-specific knowledge-base entries; the core DSL, invariant analysis, and ICRL loop are unchanged.
Q10What is "reward hacking" here, and does Ave prevent it?▾
Reward hacking is when a candidate inflates its measured speedup or test pass rate through a shortcut — a PyTorch fallback, a precomputed output, a branch on benchmark-specific values — rather than genuine optimization. Data-flow invariants reject shortcuts that violate a declared relationship, but the paper pairs this with manual, qualitative review; neither mechanism is claimed to be exhaustive.
Q11How does Ave's DSL relate to Triton or CuTe?▾
Ave's DSL is Pythonic and tile-based like both, reusing CuTe's layout algebra for tiles and Triton-like syntax so LLMs can transfer in-context knowledge from their training data. What it adds on top is tag functions, tag assertions, and explicit low-level controls (instruction scheduling barriers, register-class selection) that Triton abstracts away.
Q12What did the authors leave for future work?▾
Modeling global-memory-resident properties (MoE routing, multi-GPU communication buffers like COMET) as explicit producer-consumer queues; supporting NVIDIA Blackwell's dynamically-managed TMEM via a shared-memory-like lifetime heuristic; and exploring polyhedral analysis as a faster alternative to the current SMT-based validation.

Core terms
AveThe paper's agentic framework: uses compile-time data-flow invariants as guardrails while an ICRL-driven agent optimizes GPU kernels.
Data-flow invariantA compile-time relationship among symbolic tags that must hold throughout execution — expressed as tag functions plus tag assertions.
Tag functionAttaches a symbolic label (from coordinates or expressions) to tensor elements; tags propagate through data and control flow.
Tag assertionA conformity ("must match") or non-conformity ("must differ") requirement between tags at a use site, checked at compile time.
WitnessA concrete assignment (thread ID, coordinate, program point) that the SMT solver returns when an assertion fails, guiding the agent's repair.
ICRL plannerA fixed LLM whose benchmark-local prompt is edited after each round via text-gradient updates, using compile/invariant/test/speed reward.
Lowering agentImplements the planner's chosen optimizations in the DSL and instantiates their invariant templates as concrete tag functions/assertions.
Reward function R_tC_t + I_t + U_t + Δ_t — compiles, invariant pass fraction, tests pass, and measured speedup, combined into one training signal.
Supporting terms
Tile / layout functionA memory region paired with a function mapping logical coordinates to physical offsets — the DSL's core abstraction, from CuTe's layout algebra.
MFMAMatrix Fused Multiply-Add — AMD's tensor-core instruction; requires operands in a fixed swizzled layout.
Wavefront / LDSAMD's 64-thread warp equivalent, and its on-chip shared memory (Local Data Share).
VGPR / AGPRVector / Accumulation general-purpose registers — two register pools; explicit AGPR selection roughly doubles available vector registers.
Path-insensitive analysisMerges tag information at control-flow joins instead of tracking every branch combination — the tractability trade-off behind Ave's speed.
Text gradientA natural-language critique used to edit a prompt, in place of a numeric gradient over model weights (from TextGrad).
Knowledge baseCurated, human-audited hardware facts, DSL references, and optimization recipes with invariant templates, retrieved per round.
Reward hackingA candidate that inflates its measured score via a shortcut (fallback call, precomputed output, benchmark-specific branch) rather than genuine optimization.
Results at a glance
Source notes — what's from the paper vs. our framing
📎
From the paper, verbatim or directly recomputed: all normalized-throughput figures (89–99%, Table 1 cells), the reward formula and its four terms, the tag-merge lattice rule, the Section 6 walkthrough (tag mismatch, witness, revised binding), Table 4's invariant-ablation success counts, and every arithmetic ratio in the Worked Examples tab (e.g. 0.89/0.55 ≈ 1.62×).

Our framing, not the paper's wording: the "luggage tag," "spell-check," "crash dump," "coach," and memory-tiering analogies; the choice to visualize results as "gap to parity" bars; and the specific round-2 speedup value (5%) used in Worked Example ② to illustrate the reward formula, since the paper doesn't give that exact figure for that specific round — the formula and its qualitative outcome (R_t rising from 1 to just over 3) are drawn directly from the text.
Concepts to shore up first

SIMT execution and the GPU memory hierarchy easy

explainer · 30–45 min

Registers, shared memory/LDS, and global memory; wavefronts and occupancy. Search "GPU SIMT architecture explained" or read Ch. 2–3 of a GPU-programming text — this underlies every optimization Ave applies.

Abstract interpretation and SMT solving medium

explainer · 30 min

What it means to analyze a symbolic model instead of executing a program, and how a solver like Z3 turns "is this satisfiable" into a concrete counterexample. Foundational to how Ave's compiler checks invariants.

Related papers

CUTLASS / CuTe layout algebra medium

NVIDIA · ongoing

The layout-function algebra (composition, logical division/projection) that Ave's tile abstraction directly reuses.

Triton: an intermediate language and compiler for tiled neural network computations medium

Tillet, Kung, Cox · MAPL 2019

The block-level DSL whose automation Ave's evaluation uses as a baseline, and whose syntax Ave deliberately stays close to for LLM in-context transfer.

TileLang: Bridge Programmability and Performance in Modern Neural Kernels medium

Wang et al. · ICLR 2026

A sibling tile-based DSL exposing hardware instructions and compiler policies, one of Ave's direct design influences.

HipKittens: Fast and Furious AMD Kernels hard

Hu et al. · arXiv 2511.08083

A hand-optimized AMD kernel library used as an expert reference baseline in Ave's evaluation.

KernelBench: Can LLMs Write Efficient GPU Kernels? easy

Ouyang et al. · ICML 2025

The 200-task benchmark (Level 1/2) Ave uses to test cross-kernel generality beyond its three production workloads.

TextGrad: Automatic "Differentiation" via Text medium

Yuksekgonul et al. · arXiv 2406.07496

The general text-gradient framework Ave's ParameterUpdate step applies to edit the planner's prompt.

Making Information Flow Explicit in HiStar hard

Zeldovich et al. · OSDI 2006

The information-flow-security lineage (labels, propagation, partial order) that Ave adapts from security enforcement to kernel-optimization correctness.
