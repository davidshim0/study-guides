ACM SOSP 1983 · A Field Guide

Don't look for the best design. Avoid the terrible one

Butler Lampson's essay distills a decade of Xerox PARC systems (the Alto, Dorado, Ethernet, Bravo, Pilot, Star, Grapevine) into 26 slogans about interfaces, speed and fault tolerance. This guide treats each slogan as a mechanism: what problem it solves, the paper's own example traced step by step, the assumptions behind it, and the point where it stops being good advice.

Before you begin

Twenty-six slogans, each backed by a system that worked or one that did not

An essay, not a system paper: Butler Lampson's advice from building and studying systems at Berkeley and Xerox PARC, organized by why a hint helps (functionality, speed, fault tolerance) and where in a design it helps (completeness, interfaces, implementation). There are no benchmarks; the evidence is the examples.

⚡ TL;DR

  • Stance: "There probably isn't a 'best' way to build the system, or even any major part of it; much more important is to avoid choosing a terrible way, and to have clear division of responsibilities among the parts." The hints are "not novel (with a few exceptions)", not "consistent", not "guaranteed to work".
  • Functionality (Section 2): an interface is "the set of assumptions that each programmer needs to make about the other program". Keep it to "the minimum essentials", with a predictable cost: six layers that each cost 50% more than reasonable miss "by more than a factor of 10" (1.56 = 11.4). Example: the Alto's 900-line file system and 500-line paging versus Pilot's 11,000-line mapped files that "often" take two disk accesses per page fault.
  • Speed (Section 3): split resources, analyze statically, translate dynamically, cache answers, use hints (saved results that may be wrong but are checked against the truth before any unrecoverable action), brute force, background work, batching, and stay below about two-thirds of any resource's capacity, shedding load rather than overloading.
  • Fault tolerance (Section 4): end-to-end (only the application-level check is "absolutely necessary"; lower-level checks are "strictly for performance"), log updates as calls of functional procedures, and make actions atomic or restartable using a log and a commit record.
  • Best-known numbers in the examples: a Smalltalk call-site hint is right about 96% of the time; Cedar's conservative frame scan wrongly keeps under 1% of storage; a 58 MB disk pack is copied at Cambridge in 20 minutes with only an end-to-end check; over 250K lines of code, interface change "becomes intolerable".

Quick glossary
InterfaceThe boundary between an implementation of an abstraction and its clients; in the paper's definition, the set of assumptions each side's programmer must make about the other to show their own program correct. It is a contract for both function and (undocumented) reasonable cost.
AbstractionA simplified model of a resource or service (a file, a virtual page, a monitor) that clients program against without seeing how it is built.
ClientA program that uses an interface; in the paper, often an application or a higher layer.
SecretAn assumption about an implementation that clients are not allowed to make, and which the implementer may therefore change.
CacheAn associative store of saved triples [f, x, f(x)] that is kept correct: when f(x) changes, the entry is invalidated or updated.
HintA saved result of a computation that, unlike a cache entry, may be wrong and need not be found by associative lookup; it is checked against the truth before any action that cannot be undone.
The truthInformation that must be correct, kept in a form optimized for checking and reconstruction rather than fast use (for example, the label on each Alto disk sector).
LogAn append-only sequence of records of updates, written to stable storage; when it holds the truth, the current state can be rebuilt by replaying it.
Atomic action (transaction)An action that either completes or has no effect, so recovery never sees its intermediate states.
Restartable (idempotent) actionAn action that can be partly executed any number of times before one complete execution without changing the result: storing values is restartable, incrementing is not.
Commit recordThe log record that states whether an atomic action is in progress, committed or aborted; its state change is the moment the action logically happens.
End-to-end checkA check made by the application at the endpoints of an operation (for example, comparing checksums of the source and destination files), which covers every intermediate step at once.
Virtual memory, page faultVirtual memory is the mapping of a program's addresses onto main memory pages backed by disk; a page fault is the trap taken when a referenced page is not in main memory, which the system services by reading it from disk.
MicrocodeLow-level programs inside a processor that implement its instruction set; the Alto and Dorado were microprogrammed, so new "instructions" such as BitBlt could be added in microcode.
MonitorA synchronization construct: a module whose procedures run with mutual exclusion, plus condition variables on which processes wait and are signaled.
Load sheddingDeliberately refusing or discarding some demand (users, jobs, packets) so that the work that is accepted gets adequate service.
ThrashingThe state of a paging system whose running jobs' working sets do not fit in memory, so it spends nearly all its time waiting for the disk.
Short primers (tap to open)
1Xerox PARC around 1973 to 1983, and the systems in the examples▾

Most examples come from Xerox's Palo Alto Research Center, where Lampson worked. The Alto was a small microprogrammed personal computer with a bitmapped display, a removable disk pack and an Ethernet connection; one user had one machine. The Dorado was a much faster successor personal computer. On the Alto ran the single-user Alto OS, the Bravo editor (an early what-you-see-is-what-you-get editor) and Smalltalk, with printing on the Dover laser printer; the Alto OS file system was later "extended for Interlisp-D", a Lisp system for PARC's later machines (paper; the machine detail is general knowledge). Later came Mesa (a strongly typed systems language), Pilot (the OS written in Mesa for the Star), the Star office system, Cedar (a programming environment with garbage collection), the Pup internetwork protocols and Grapevine, a replicated mail and name service (general knowledge, not in the paper, apart from the names and roles the paper itself gives).

Older examples come from time-sharing: the SDS 940 system at Berkeley, Tenex on the PDP-10, Cal on the CDC 6400, Multics and Unix; and from networks: the Arpanet.

Now you're ready: when the paper says "the Alto" or "Pilot", picture a 1970s single-user machine and its operating system; the How It Works Step 0 map places every named system.
2Interfaces as contracts, and why they are "a small programming language"▾

The paper defines an interface by what the two sides may assume about each other (paraphrasing Britton et al.). Assumptions include the obvious ones (argument types, results) and quiet ones: how long an operation takes, which errors can occur, what happens on a page fault inside a call. Because an interface "defines a set of objects and the operations that can be used to manipulate the objects", designing one has every difficulty of designing a language except concrete syntax.

The paper sets three requirements that conflict: an interface should be simple, complete, and admit a sufficiently small and fast implementation. Most functionality hints are ways of trading among these three.

Now you're ready: when a hint says "the interface", read "the full set of assumptions, including cost".
3Disk pages, labels and file maps on the Alto▾

An Alto disk sector held a small label next to its data: the identifier of the file that owns the page and the page's number within that file (paper, Section 3). Page zero of each file, the leader page, records the file's name and directory. Together these are enough to reconstruct everything else by scanning the whole disk, which the Alto's Scavenger program does. A directory maps names to (file identifier, address of first page); each file's page-to-disk-address map lets the system go from page n to n + 1 quickly.

The disk controller could compare a sector's label with an expected value before transferring the data, at no cost in transfer speed (paper). That is what makes the faster structures safe to be wrong.

Now you're ready: "use hints" is about the directory and map; "the truth" is the labels.
4Logs, commit records and recovery in one paragraph▾

To make a multi-step update survive a crash, first append a description of each step to a log on stable storage, then append a commit record; only after that apply the steps to the real data. After a crash, recovery reads the log: actions with a commit record are redone, others are undone or ignored. Redoing must be safe even if the step was already partly or fully applied, which is why log entries should be restartable (store a value, do not add to one).

The CS240 file system papers you have read use this pattern: LFS's checkpoint regions with a time stamp in the last block, F2FS's checkpoint pack with a version number in header and footer, ext3's journal under xsyncfs (Rethink the Sync).

Now you're ready: Section 4 of the paper is this pattern, plus the argument for checking at the ends.
5Networks without the networking class: packets, best effort, collisions▾

A packet is a bounded chunk of data with source and destination addresses. A store-and-forward network (Arpanet, Pup internet) passes it from node to node; each node holds it in a buffer and picks the next hop from a routing table. If buffers fill, a node can drop the packet. Best-effort delivery means the network tries but may lose or corrupt packets without notice; reliable streams are built on top by the endpoints, which number packets, check them and retransmit.

The original Ethernet is one shared cable. A station listens for a carrier (someone else transmitting) and sends only when the cable is quiet; if two start at once, both detect the collision, stop, wait a random time and retry.

Now you're ready: the paper's network examples (Arpanet routing, Ethernet backoff, Pup, the Arpanet delivery guarantee) are all about who is responsible for reliability.
6Queueing in one picture: why "two-thirds of capacity"▾

If requests arrive at random and a server is busy a fraction ρ of the time, waiting grows like 1 / (1 − ρ) in the simplest queueing model (M/M/1, general knowledge, not in the paper): at ρ = 0.5 the average request spends 2 service times in the system, at 2/3 it spends 3, at 0.9 it spends 10, at 0.99 it spends 100. The curve is flat on the left and nearly vertical on the right.

The paper's rule, "A system cannot be expected to function well if the demand for any resource exceeds two-thirds of the capacity, unless the load can be characterized extremely well", sits where the curve begins to bend.

Now you're ready: "safety first" and "shed load" are about staying on the flat part of this curve.
The whole story in one place

Simple interfaces with predictable cost, fast normal cases checked against the truth, and reliability decided at the ends

The paper is a catalogue, but three ideas run through almost every slogan.

Lampson starts from a claim about the problem, not the solution: a computer system, unlike an algorithm, has a vague and changing requirement, many internal interfaces, and no clear measure of success, so there is no "best" design. What matters is to avoid a terrible design and to divide responsibility clearly among the parts. The hints are rules of thumb for doing that, each tied to a system that followed or ignored it.

The first idea is that an interface is a contract about cost as well as function. Clients depend on "incurring a reasonable cost", which is "usually not documented anywhere", and costs compound across layers. So an interface should do one thing well, promise only what its implementer knows how to deliver, expose rather than bury what the lower level does fast, and leave the rest to the client through procedure arguments or plain fast primitives. The Alto's simple file and paging code (900 and 500 lines, one disk access per fault) against Pilot's general mapped files (11,000 lines, often two accesses) is the paper's main exhibit.

The second idea is to make the normal case fast and the worst case merely make progress. Caches store answers that must be kept correct; hints store answers that may be wrong and are checked against a slower truth before anything irreversible happens. Normal-case shortcuts (Cedar's uncounted local pointers, Bravo's piece table, Smalltalk's call-site guess) are paired with crude but sure fallbacks (a trace-and-sweep collector at coffee breaks, a cleanup that rewrites the file, a full method lookup). Resources should be split, overprovisioned and protected from overload rather than optimized, because "a general-purpose system cannot optimize the use of resources".

The third idea is that reliability is decided by the application at the ends. A file copy is right only if the bits on the destination disk match the source; every check in between is "strictly for performance". The truth is best kept in a log of updates written as calls of functional procedures on immutable values, and multi-step actions are made atomic with a commit record and restartable log entries, or, where the application tolerates it, with something weaker such as Grapevine's rule that "Each update message is time-stamped, and the latest one wins".

The paper's Figure 1 arranges the 26 slogans by why they help (functionality, speed, fault tolerance) and where (completeness, interface, implementation). The arrangement is the paper's own and is not entirely consistent with the text: "Make it fast" is argued in the functionality section but placed in the speed column, and "End-to-end" is placed under speed and fault tolerance but discussed only in Section 4 (see Reference, Source notes).

🍯 Key takeaways

  • Aim to avoid a terrible design, not to find the best one; the hints are folk wisdom, explicitly not "consistent" and not "always appropriate".
  • An interface promises a cost as well as a function. Keep it minimal, predictable, and honest about what the implementer can deliver; costs multiply across layers (1.56 ≈ 11).
  • Make the normal case fast with caches and hints, and give the worst case a crude path that still makes progress.
  • A hint may be wrong; it is safe because it is checked against the truth before any unrecoverable action.
  • Plan resources for safety, not optimality: stay under about two-thirds load and shed demand rather than collapse.
  • Only the end-to-end check is needed for correctness; every other check buys performance. Keep the truth in a log and make actions atomic or restartable.
Six everyday pictures

How to think about the hints

Each stands alone. Every card ends with where the picture stops being true, tied to a mechanism block in How It Works.

Use hints · the truth

A sticky note that says which drawer a folder is in

The note is fast and usually right. Before you shred or file anything, you read the label on the folder itself; if the label is wrong, you search every drawer and rewrite the note. The note is the Alto's directory entry and page map; the folder label is the sector label holding the file identifier and page number.

Where it breaks: reading the folder label costs you nothing extra only because the Alto disk checks labels "without slowing down the data transfer"; if checking were as slow as searching, the note would buy nothing (M18).
Cache answers · incremental update

The running total at the bottom of a ledger

You do not re-add a thousand entries when one changes: you subtract the old amount and add the new one. That is the paper's g(x, [i, v], sum) = sum − xi + v. A cached answer is worth keeping when updating it is far cheaper than recomputing it.

Where it breaks: a line of text is not a ledger entry: one edit can move every later line break, so Bravo cannot patch its line cache and instead invalidates every entry whose characters the edit touched and recomputes (M17).
End-to-end

Checking the boxes against the inventory at the new house

However careful the movers, the move succeeded only if what arrives matches the list you wrote at the old house. Checks at the depot or the truck are useful only because they catch a broken box early, so less has to be shipped again. That is reading the copy back from B's disk and comparing checksums with A's.

Where it breaks: you can only rely on the end check if it is cheap and failures are rare; with frequent errors the whole move is repeated again and again, which is why the paper keeps intermediate checks "strictly for performance" (M24).
Normal and worst cases separately · reserve under a mattress

Cash under the mattress

Day to day you pay by card, the fast path. The cash is touched only when the card stops working, and you keep exactly enough to deal with one emergency at a time. A paging system normally frees clean pages for nothing; when every page is dirty, it uses a fixed reserve to clean one page at a time.

Where it breaks: the reserve has a size only if the resources needed to free one item are bounded; if writing one page out could need unbounded tables, no mattress is big enough (M13).
Safety first · shed load

A restaurant that stops seating before the kitchen is swamped

A kitchen run at full capacity serves everyone late, and late food is often refused. Turning people away at the door keeps the seated tables happy. The paper's rule is to keep demand for any resource under about two-thirds of capacity and, past that, refuse new users, limit jobs to what fits in memory, or drop packets.

Where it breaks: the door is the only safe place to refuse; the Arpanet promised delivery once a packet was accepted, which made deadlock "very hard to avoid" when buffers filled inside the network (M23).
Keep a place to stand · world-swap debugger

A mechanic's own toolbox, not the broken car's

If your diagnostic tools ran on the car's battery, a dead battery would leave you blind. The world-swap debugger saves the target's whole memory to disk and loads a separate debugger that depends on nothing in the target except the swap itself.

Where it breaks: the swap itself must still work in the broken system; the paper's tele-debugging variation puts a small "nub" in the target, which must survive whatever went wrong (M8).

1 · Interfaces: keep them small, honest about cost, and stable

The functionality hints all concern what to put in an interface. Do one thing well and do not promise more than you know how to deliver (M1); be aware of what each abstraction costs, because composing cheap-looking pieces can produce O(n2) (M2). Prefer fast basic operations to slow powerful ones (M3), expose what the lower level does quickly (M4), take procedures as arguments instead of inventing a parameter language (M5), and leave policy to the client (M6). Once clients exist, keep interfaces stable, and if you must change them keep a compatibility layer or a debugger that depends on almost nothing (M7, M8).

2 · Implementations: expect to redo them, and hide what may change

Plan to throw the first one away (M9); keep secrets so parts can be improved separately, knowing that every extra assumption you forbid may cost speed (M10); split problems that do not fit into pieces that do (M11, the Alto Scavenger and the Dover printer's bands); reuse an idea in a specialized form rather than generalizing its code (M12); and handle the normal and worst cases with different mechanisms (M13).

3 · Speed: dedicate, precompute, remember, guess and check

Dedicated resources are faster and more predictable than shared ones (M14). Analyze statically when you can, and fall back to a dynamic scheme when you cannot (M15). Translate a convenient representation into a fast one on demand and cache the result (M16). Cache answers, and organize the cache so a small change invalidates little (M17). Use hints that may be wrong, checked against the truth (M18). Prefer brute force to fragile cleverness (M19), defer work to the background (M20), and batch it (M21).

4 · Load: avoid disaster instead of optimizing

No general-purpose system can optimize its resource use, but any system can be overloaded. Keep demand for each resource under about two-thirds of capacity and buy cheap memory as cushion (M22), and when demand still exceeds capacity, refuse some of it at the door (M23).

5 · Fault tolerance: check at the ends, keep the truth in a log, make actions atomic

Only the application's end-to-end check is needed for correctness; lower-level checks pay only in performance (M24). The truth about an object is best kept as a log of calls of functional update procedures with value arguments (M25), and multi-step changes are made atomic with a commit record and restartable log entries, or replaced by a weaker scheme when the application can live with temporary disagreement (M26).

P · Paper map

Background and context
  • Butler W. Lampson, Computer Science Laboratory, Xerox Palo Alto Research Center. Presented at the 9th ACM Symposium on Operating Systems Principles; the footnote says it "appeared in Operating Systems Review 15, 5, Oct. 1983, p 33-48" and that "the present version is slightly revised." The PDF is that revised version, dated July 1983 in the running footer, 27 pages.
  • Not a system paper and not an experiment: an essay of hints, "most ... part of the folk wisdom of experienced designers", illustrated by systems Lampson built or studied, with "references for nearly all the specific examples but for only a few of the ideas".
  • Decorated with quotations from Hamlet, "taken from Polonius' advice to Laertes", each meant "to apply to the text which follows it". They carry no technical content and are omitted here except where the paper uses one to make a point.
  • What it deliberately leaves out: "exhortations to modularity, methodologies for top-down, bottom-up, or iterative design, techniques for data abstraction, and other schemes that have already been widely disseminated."
The problem it addresses

"Designing a computer system is very different from designing an algorithm": the requirement is "less precisely defined, more complex, and more subject to change"; there is "much more internal structure, and hence many internal interfaces"; and "the measure of success is much less clear." So the designer is "floundering in a sea of possibilities", and "There probably isn't a 'best' way to build the system ... much more important is to avoid choosing a terrible way, and to have clear division of responsibilities among the parts."

The "result"

There is no measured result. The paper's claim is the 26 slogans themselves, each justified by one or more systems: the ones that followed the hint and worked (the Alto file system, monitors, the piece table, Ethernet backoff, the Pup internet), and the ones that ignored it and paid (PL/1's unpredictable cost, Tenex's password interaction, Pilot's mapped files, the Arpanet delivery guarantee).

The slogans in dependency order (this guide's grouping)
  1. What an interface is and why it is hard (Section 2 intro): it is a contract of assumptions, including cost, and is "a small programming language".
  2. Keep the interface small and honest (M1, M2): minimum essentials, predictable cost, get the implementation right.
  3. Shape the interface for speed and flexibility (M3 to M6): fast primitives, expose power, procedure arguments, leave policy to the client.
  4. Keep it stable (M7, M8): do not change basic interfaces; keep a compatibility layer or a self-sufficient debugger when you must.
  5. Build the implementation expecting change (M9 to M12): throw one away, keep secrets, divide and conquer, reuse the idea.
  6. Handle all the cases (M13): fast normal case, worst case that makes progress.
  7. Make it fast (M14 to M21): dedicate, analyze, translate, cache, hint, brute-force, background, batch.
  8. Do not collapse under load (M22, M23): stay below two-thirds, shed the rest.
  9. Keep working through failures (M24 to M26): check at the ends, log the truth, make actions atomic.
The central tensions the paper itself names
  • Keep secrets versus don't hide power (M4, M10): hiding an implementation lets you change it, but burying a fast capability makes it unusable. "Striking the right balance remains an art."
  • Simple versus complete versus small-and-fast implementation: the three requirements on an interface, which "conflict".
  • More assumptions for speed versus modularity (M10): "One way to improve performance is to increase the number of assumptions that one part of a system makes about another", but then parts cannot be improved separately.
  • Static versus dynamic (M15): static analysis is faster when it works, but "when a good static analysis is not possible, don't delude yourself with a bad one".
  • Normal versus worst case (M13): "The normal case must be fast. The worst case must make some progress."
When the whole essay's advice shifts (this guide)
  • When hardware is dear rather than cheap (the paper's own era boundary): "safety first" and "use brute force" rest on "hardware is cheap and getting cheaper"; under a tight hardware budget the optimizing that the paper discourages comes back (inference).
  • When the load is extremely well characterized: the paper's exceptions (the 360/50 APL system) show that its anti-optimization advice is specifically for general-purpose systems (stated).
  • When a cheap end check does not exist: end-to-end "requires a cheap test for success"; without one, the argument does not deliver its simplicity (stated).

M1 · Do one thing well, and don't generalize

TL;DR
ProblemAn interface that undertakes too much gets an implementation that is "large, slow and complicated", and clients who do not want the extra power pay for it anyway.
MechanismCapture "the minimum essentials of an abstraction"; do not generalize; give the service a predictable cost; never promise "more than the implementer knows how to deliver".
Trade-offSimplicity and predictable cost in exchange for features only some clients wanted, which a better implementer "ten years later" might supply.
Breaks whenThe interface is seldom used (then functionality may outweigh speed), or you already know from existing use that it matters and know how to make it fast.
Key points
  • "An interface should capture the minimum essentials of an abstraction. Don't generalize; generalizations are generally wrong."
  • Cost is part of the contract: clients "depend on incurring a reasonable cost ... the definition of 'reasonable' is usually not documented anywhere." And it compounds: "If there are six levels of abstraction, and each costs 50% more than is 'reasonable', the service delivered at the top will miss by more than a factor of 10." (1.56 = 11.39; the arithmetic is this guide's, the claim is the paper's.)
  • Predictable cost makes a language usable: "A language like Pascal or C is much easier to use, because every construct has a roughly constant cost that is independent of context or arguments." PL/1 by contrast "got into serious trouble by attempting to provide consistent meanings for a large number of generic operations across a wide variety of data types."
  • The main exhibit, mapped files: the Alto OS has "an ordinary read/write-n-bytes interface to files" and Interlisp-D "an ordinary paging system that stores each virtual page on a dedicated disk page." Both are small ("about 900 lines of code for files, 500 for paging") and fast ("a page fault takes one disk access"). Pilot instead maps "virtual pages ... to file pages", so its implementation "is much larger (about 11,000 lines of code) and slower (it often incurs two disk accesses to handle a page fault and cannot run the disk at full speed). The extra functionality is bought at a high price."
  • The cause is "avoiding circularity: the file system would like to use the virtual memory, but virtual memory depends on files." General solutions exist but "are tricky and easily lead to greater cost and complexity in the normal case."
  • Exemptions: "these observations apply most strongly to interfaces that clients use heavily, such as virtual memory, files, display handling, or arithmetic." A seldom-used interface (password checking, command interpreting) may trade speed for function, and "research whose object is learning how to make better implementations" is exempt, "but ... others mustn't depend on its success."
How it works, step by step: the Interlisp-D page fault (the paper's fast case)
  1. A reference misses: the program touches virtual page v that is not in memory; the hardware traps.
  2. Find the disk page: the fault handler looks up v's disk address. In Interlisp-D "real memory is dedicated to this purpose" (M14), so this is a memory lookup, "a small fraction of the disk access time".
  3. One disk access: read v's dedicated disk page into a free frame.
  4. Resume. Because there is exactly one access and little computing, "the client can fairly easily run the disk at full speed." In Pilot the same fault "often" needs a second access because the map itself lives in paged virtual memory.
Assumptions it relies on
  • A1. The abstraction has a small set of essentials that most clients want (stated; files as read/write-n-bytes).
  • A2. The interface is used heavily, so its cost dominates (stated: virtual memory, files, display, arithmetic).
  • A3. The implementer does not yet know how to make the general version both small and fast (stated for Pilot: "designed and coded by several highly competent and experienced people").
If an assumption changes
  • A1 changes (no small essential set): there is no minimal interface to extract; the designer must choose which clients to serve, which is the completeness-versus-simplicity tension.
  • A2 changes (seldom used): the rule relaxes. "It is all right to sacrifice some performance for functionality in a seldom used interface such as password checking", as long as the cost is still predictable.
  • A3 changes (you know how to make the general one fast): then "it's worth a lot of work to make a fast implementation of a clean and powerful interface", but "only for an interface whose importance is already known from existing uses". This is the next hint's precondition (BitBlt, Dorado; covered under M3's key points).
Design notes and rejected alternatives

The rejected alternative is exactly Pilot's: fold file I/O into virtual memory for a cleaner model. The paper does not call it wrong, only costly, and says so: "This is not to say that a good implementation of this interface is impossible, merely that it is hard." The BitBlt and Dorado examples are the counterweight: heavy investment in a clean, powerful interface pays off when its importance is already proven, though even the Dorado's high I/O bandwidth was "in retrospect ... not worth the cost."

Connections

Exokernel (11/10): the same objection to rich, mandatory abstractions, taken to its limit: the kernel exports hardware and lets a library OS build files and virtual memory, so a client that wants read/write-n-bytes is not forced through mapped files (inference; the outline lists this connection). Superpages (10/13): mapping files into virtual memory is the mechanism superpages optimize; the cost the paper flags (two accesses, circularity) is the kind of complexity a unified buffer cache accepts for the generality (inference). vLLM (11/19): PagedAttention adds "20–26% higher attention kernel latency" from block-table indirection, a measured instance of a more general interface costing the common path (inference).

M2 · Get it right: abstraction is no substitute

TL;DR
ProblemA clean abstraction can hide a terrible cost, so composing individually reasonable pieces can produce an O(n2) disaster.
MechanismKeep "a lively awareness of its cost" for every abstraction; "Neither abstraction nor simplicity is a substitute for getting it right."
Trade-offLayers of clean abstractions in exchange for the risk of hidden super-linear cost; the paper insists this "is not an argument against abstraction".
Breaks whenAn abstraction's cost is not constant and a client composes it in a loop without knowing.
Key points
  • The cautionary tale: documents embed named fields encoded like {name: contents}, and FindNamedField finds the one with a given name. "One major commercial system for some time used a FindNamedField procedure that ran in time O(n2), where n is the length of the document."
  • How: a procedure FindIthField "must take time O(n) if there is no auxiliary data structure", and FindNamedField was built as a loop calling FindIthField for i = 0, 1, 2, ... until the names match.
  • The lesson: "Once the (unwisely chosen) abstraction FindIthField is available, only a lively awareness of its cost will avoid this disaster."
How it works, step by step: the O(n2) trace
  1. The building block: FindIthField(k) scans from the document start counting field markers until it reaches the k-th; with no index this is a scan of up to the whole document, O(n).
  2. The composition: to find the field named "address", the natural loop calls FindIthField(0), checks its name, then FindIthField(1), and so on. Each call restarts the scan from the beginning.
  3. The cost: reaching the m-th field does m scans of O(n) each. If the number of fields grows with document length, this is O(n2). A worked count (illustrative, not in the paper): 1,000 fields, each scan averaging half the document, is about 1,000 half-document scans; double the document and both the scan length and the field count double, so the time quadruples.
  4. The fix: one pass that records each field's name as it goes, or an index, finds the field in O(n) total.
Assumptions it relies on
  • A1. The programmer who composes abstractions can know their costs (implicit; the whole point is that the cost was not visible).
  • A2. Cost predictability is part of the interface contract (stated in M1).
If an assumption changes
  • A1 changes (cost cannot be known): then the interface is underspecified; the remedy is to document the cost or provide the right primitive (FindNamedField directly), not to forbid abstraction.
  • A2 changes (cost is outside the contract): every library call inside a loop is a latent quadratic, which is the general form of this bug (inference).
Design notes and rejected alternatives

The rejected design is the "very natural" loop; the correct one is a single-scan FindNamedField or a field index. The point generalizes: a clean interface (FindIthField) can be exactly the wrong primitive to expose, because it invites quadratic composition.

Connections

FFS (field guide): the old file system's free list is an abstraction ("give me a free block") whose cost model hid the real cost, a seek per block once the list was scrambled; FFS replaced it with a request for a free block near a preferred one, putting the cost the client cares about into the interface (inference). Eraser (10/6): a dynamic race detector is the "get it right" response to concurrency, where the correct behavior is not visible from the clean lock interface (inference).

M3 · Make it fast, rather than general or powerful

TL;DR
ProblemA slow, powerful operation taxes the client who does not want the power, and "usually ... the powerful operation is not the right one."
MechanismProvide basic operations that run quickly; "If it's fast, the client can program the function it wants, and another client can program some other function."
Trade-offThe client writes more code, in exchange for speed and flexibility; "a fast, powerful operation is best, if you know how to get it."
Breaks whenYou cannot tell which operations are the frequent basic ones (needs measurement), or a powerful primitive really is both fast and the right one.
Key points
  • The RISC argument: "many studies ... have shown that programs spend most of their time doing very simple things: loads, stores, tests for equality, adding one." Machines like "the 801 ... or the RISC ... can run programs faster (for the same amount of hardware) than machines like the VAX with more general and powerful instructions that take longer in the simple cases. It is easy to lose a factor of two in the running time of a program, with the same amount of hardware."
  • You must measure to know where to spend effort: "it is normal for 80% of the time to be spent in 20% of the code, but a priori analysis or intuition usually can't find the 20% with any certainty." With good tools, "The performance tuning of Interlisp-D sped it up by a factor of 10."
  • The counterweight, when heavy investment in a clean powerful interface is justified (this is the exemption M1's A3 pointed to): BitBlt (RasterOp) "costs about as much microcode as the entire emulator for the Alto's standard instruction set", yet runs "nearly as good" as the special-purpose routines it replaced; the Dorado memory system took "850 MSI chips and ... several man-years", justified by "extensive prior experience (30 years!)" that "memory access is usually the limiting factor", though "in retrospect ... the high I/O bandwidth is not worth the cost."
How it works, step by step: BitBlt as the paid-off investment
  1. Before: each display need (characters, scrolling, rectangles) required its own special-purpose character-to-raster microcode; a new need meant new microcode.
  2. The clean interface: after "several years of experimenting with the Alto's high-resolution interactive display", Ingalls devised one rectangular bit-array operation, BitBlt, that expresses them all.
  3. The investment: its microcode cost about as much as the entire Alto instruction-set emulator, and "a lot of skill and experience".
  4. The payoff: performance "nearly as good as the special-purpose ... operations that preceded it", and every display application became easier to build. The precondition held: importance "already known from existing uses", and the designer knew how to make it fast.
Assumptions it relies on
  • A1. The common operations are simple and frequent (stated; the instruction-mix studies).
  • A2. The client can cheaply compose basic operations into what it needs (implicit).
  • A3. For the counterweight: importance is proven and you know how to make the powerful version fast (stated).
If an assumption changes
  • A1 changes (the heavy work is one complex operation): then a powerful primitive (BitBlt, a vector instruction) can be right, provided it is fast; the hint explicitly allows "a fast, powerful operation is best".
  • A2 changes (composing is expensive): pushing work to the client stops being free; this is the limit the "leave it to the client" hint (M6) states as "as long as it is cheap to pass control back and forth".
  • A3 changes (importance unproven): the Dorado I/O path is the warning: a justified-looking investment can still miss: "in retrospect ... the high I/O bandwidth is not worth the cost".
Design notes and rejected alternatives

The rejected design is the CISC-style rich instruction (the VAX, the iAPX 432, which "do even worse"). The paper's nuance is that a fast, powerful operation beats a fast, simple one when you can get it, so this guide reads the hint as: fast first, then as powerful as you can afford.

Connections

Exokernel (11/10) and Dune (11/12): both argue for fast low-level primitives over general abstractions; Dune reports intercepting a system call "with 25× less overhead" than ptrace by exposing the hardware trap directly (inference; outline lists these). x86 VMM (hwsw): classic trap-and-emulate was impossible on x86 because some sensitive instructions do not trap, so VMware used binary translation; the paper then finds the newer hardware support (VT-x), a more general mechanism, often slower than the tuned software path because each exit is expensive (general knowledge of the Adams and Agesen paper; the mapping to this hint is inference).

M4 · Don't hide power

TL;DR
ProblemA higher abstraction that buries a fast low-level capability inside something more general makes that capability unreachable.
Mechanism"The purpose of abstractions is to conceal undesirable properties; desirable ones should not be hidden." Deliver "all or nearly all" of a resource to a single client "with only slight loss of performance."
Trade-offMultiplexing a resource "necessarily has some cost", but the fast path must remain reachable; tension with keeping secrets (M10).
Breaks whenExposing the capability also exposes an assumption that must stay changeable, or the resource cannot be delivered whole.
Key points
  • The Alto disk: "The Alto disk hardware can transfer a full cylinder at disk speed. The basic file system can transfer successive file pages to client memory at full disk speed, with time for the client to do some computing on each sector; thus with a few sectors of buffering the entire disk can be scanned at disk speed."
  • What that enabled: "a scavenger that reconstructs a broken file system, to programs that search files for substrings that match a pattern." Also "Loaders, compilers, editors and many other programs depend for their performance on this ability to read large files quickly."
  • The stream level is a higher abstraction that still does not hide the speed: it reads or writes n bytes, and "any portions of the n bytes that occupy full disk sectors are transferred at full disk speed." "At this level the client gives up the facility to see the pages as they arrive; this is the only price paid for the higher level of abstraction."
How it works, step by step: searching a large file for a pattern
  1. Page level: the client receives each sector as it arrives and scans it for the pattern while the next sector is still being transferred, so the whole file is scanned at full disk speed with only a few sectors of buffer.
  2. Stream level: the client asks for n bytes; every full sector in that range still moves at disk speed, but the client sees the bytes only after the transfer completes.
  3. The one cost: at the stream level the client "gives up the facility to see the pages as they arrive". It does not give up the speed. The abstraction hid the sector boundaries (undesirable detail) but not the transfer rate (desirable capability).
Assumptions it relies on
  • A1. The lower level has a capability worth exposing (stated: full-cylinder transfer).
  • A2. Exposing it does not force a harmful assumption onto clients (implicit; the tension with M10).
  • A3. The resource can be delivered nearly whole to one client (stated).
If an assumption changes
  • A1 changes (no special low-level power): nothing to expose; a plain abstraction is fine.
  • A2 changes (exposure leaks a secret): the conflict with M10 bites; the paper admits "there is a tension with the desire not to hide power" and "the right balance remains an art."
  • A3 changes (resource must be shared, not handed over): multiplexing cost appears; the hint still asks that a single client be able to get "nearly all" of it.
Design notes and rejected alternatives

The rejected design is a general per-byte file interface with built-in caching and prefetching, which would cost speed for clients that need the raw rate. The paper's resolution is layering: a low interface that exposes the power and a higher one (the stream) that hides only inessential detail.

Connections

Exokernel (11/10): the Exokernel paper's test for its in-kernel abstractions is that they "neither hinder low-level access to hardware resources nor unduly restrict the semantics of the protected abstractions they enable", close to this hint (the pairing is the outline's and this guide's, not Lampson's). Dune (11/12): exposes page tables, rings and TLB tags to a process for the same reason (inference). FFS (field guide): FFS reports the "optimal I/O size" to applications so the Standard I/O library can transfer whole blocks, a small instance of not hiding the device's preferred unit (inference).

M5 · Use procedure arguments to provide flexibility

TL;DR
ProblemAn interface that handles many cases with a jumble of parameters becomes "a small programming language".
MechanismLet the client pass a procedure; it "can be restricted or encoded in various ways if necessary for protection or portability."
Trade-offA simpler, more flexible interface in exchange for the cost of calling client code and the need to guard against misbehaving procedures.
Breaks whenA specialized language "is more amenable to static analysis for optimization" (database query languages).
Key points
  • Basic case: for an enumeration procedure that returns all the elements of a set satisfying some property, "The cleanest interface allows the client to pass a filter procedure that tests for the property, rather than defining a special language of patterns or whatever."
  • The Spy monitoring facility in the Berkeley 940 system "allows an untrusted user program to plant patches in the code of the supervisor. A patch is coded in machine language, but the operation that installs it checks that it does no wild branches, contains no loops, is not too long, and stores only into a designated region of memory dedicated to collecting statistics." So a student "can fine-tune his measurements without any fear of breaking the system".
  • FRETURN in the Cal system: "From any supervisor call C it is possible to make another one CF that executes exactly like C in the normal case, but sends control to a designated failure handler if C gives an error return." CF "can do more ... but it runs as fast as C in the (hopefully) normal case."
  • Caveat: "It may be better to have a specialized language ... if it is more amenable to static analysis for optimization. This is a major criterion in the design of database query languages."
How it works, step by step: installing a Spy patch
  1. Submit: a user writes a machine-language patch (illustrative; the paper gives no specific patch) that increments a counter in the statistics region whenever a chosen supervisor routine runs, and asks the Spy to install it.
  2. Check, not trust: the installer verifies the patch has "no wild branches", "no loops", bounded length, and stores "only into a designated region". These restrictions make the patch a safe procedure argument.
  3. Run inside the supervisor: all checks pass, so the patch runs in supervisor context "without any fear of breaking the system, or even perturbing its operation much".
  4. Rejected input: a patch with a backward branch (a loop) is refused at install time, so it can never hang the supervisor. The restrictions are what make an untrusted procedure safe to call.
Assumptions it relies on
  • A1. Control transfer to client code is cheap enough (implicit; shared with M6).
  • A2. The procedure can be restricted enough to be safe (stated; the Spy's checks).
  • A3. Static optimization across the procedure boundary is not needed (stated caveat).
If an assumption changes
  • A1 changes (calls are expensive): passing a procedure per element can dominate; batch the calls or inline, or use a data description instead (inference).
  • A2 changes (cannot restrict it): an unchecked procedure in the kernel can crash or stall it, which is exactly why the Spy verifies patches.
  • A3 changes (optimization matters): switch to a specialized language the system can analyze, the database-query case the paper names.
Design notes and rejected alternatives

The rejected design is the "jumble of parameters" that becomes a pattern language. A procedure argument lets the client express any computation while the interface decides only when to call it. The Spy's verified machine code is an early version of the downloaded-code idea that recurs in later systems.

Connections

Exokernel (11/10): downloaded code (UDFs, wakeup predicates, packet filters) is the Spy idea generalized; a UDF is restricted to a checked pseudo-RISC language and must be deterministic, just as the Spy forbids loops and wild branches (inference; outline lists this). Dune (11/12): user-level handlers invoked by hardware traps raise the same "is the downloaded code safe" question (inference).

M6 · Leave it to the client

TL;DR
ProblemAn interface that solves several problems at once imposes its policy on every client.
Mechanism"As long as it is cheap to pass control back and forth", solve one problem and leave the rest to the client; this "can combine simplicity, flexibility and high performance".
Trade-offThe client writes or links the features it needs and "pays for what it needs", in exchange for not paying for ones it does not.
Breaks whenControl transfer between interface and client is not cheap.
Key points
  • Parsers: "many parsers confine themselves to doing context free recognition and call client-supplied 'semantic routines' to record the results of the parse", rather than "always building a parse tree that the client must traverse".
  • Monitors: their success "is partly due to the fact that the locking and signaling mechanisms do very little, leaving all the real work to the client programs in the monitor procedures." If the client needs "buffer allocation, resource accounting or other frills, it provides these functions itself or calls other library facilities, and pays for what it needs."
  • The non-feature as a feature: "The fact that monitors give no control over the scheduling of processes waiting on monitor locks or condition variables, often cited as a drawback, is actually an advantage, since it leaves the client free to provide the scheduling it needs (using a separate condition variable for each class of process), without having to pay for or fight with some built-in mechanism that is unlikely to do the right thing."
  • Unix: it "encourages the building of small programs that take one or more character streams as input, produce one or more streams as output, and do one operation", leaving the client to combine them.
  • "The end-to-end slogan discussed in section 3 is another corollary of keeping it simple." (The paper's own cross-reference; end-to-end is actually in Section 4.)
How it works, step by step: writers-first scheduling with a bare monitor (illustrative; the paper states only "a separate condition variable for each class of process")
  1. The need: a client has two classes of waiting process, readers and writers, and wants writers served first.
  2. With a bare monitor: it declares a separate condition variable for each class and signals the writers' variable first when the resource frees. The monitor provided only mutual exclusion and signaling.
  3. With a built-in FIFO queue instead: the client would "fight with" the queue discipline, which cannot know that writers should win.
  4. The result: the simple monitor stays fast and small, and the client gets exactly the scheduling it wants by building it, not by configuring a general mechanism.
Assumptions it relies on
  • A1. Passing control between interface and client is cheap (stated, the explicit precondition).
  • A2. The client knows its own policy better than the interface can (stated; "unlikely to do the right thing").
If an assumption changes
  • A1 changes (control transfer is expensive): leaving work to the client costs a crossing each time; bundle the work or move it inside (inference). On a machine where a kernel crossing is dear (the Exokernel paper keeps its software abstractions in the kernel partly because the extra context switches of user-level servers "are particularly expensive on the Intel Pentium Pro"), this limit is real.
  • A2 changes (the interface does know best): then a built-in policy is fine, for example a scheduler for a known, uniform workload (the APL system in M22).
Design notes and rejected alternatives

The rejected design is a monitor that also schedules, allocates buffers and accounts resources; every client would pay for all of it. Leaving these out is why monitors stayed simple and fast.

Connections

Mesa (course): the paper's monitor reference is Hoare's monitors and the Lampson and Redell Mesa paper; Mesa's condition-variable semantics are the mechanism here (the course pairing is the outline's, not the paper's). Exokernel (11/10): library operating systems are "leave it to the client" applied to an entire OS (inference). Eraser (10/6): because the monitor leaves locking discipline to the client, a tool is needed to check the client got it right (inference).

M7 · Keep basic interfaces stable

TL;DR
ProblemAn interface embodies assumptions shared by many parts, so changing it breaks them; yet designs need to improve.
MechanismDo not change basic interfaces. As a system grows, "break the system into smaller pieces related only by interfaces that are stable for years."
Trade-offStability in exchange for the freedom to improve the interface itself.
Breaks whenThe system is small enough, or the language's type-checking strong enough, that change is still affordable.
Key points
  • Without type-checking, "it is nearly out of the question to change any public interface because there is no way of tracking down its clients and checking for elementary incompatibilities, such as disagreements on the number of arguments or confusion between pointers and integers."
  • "With a language like Mesa ... that has complete type-checking and language support for interfaces, it is much easier to change an interface". But type-checking only detects a broken assumption; "a programmer must still correct the assumption."
  • The scale limit: "When a system grows to more than 250K lines of code the amount of change becomes intolerable; even when there is no doubt about what has to be done, it takes too long to do it. There is no choice but to break the system into smaller pieces related only by interfaces that are stable for years."
  • "Traditionally only the interface defined by a programming language or operating system kernel is this stable."
How it works, step by step: adding an argument to a widely used call
  1. The change: a call used at, say, 400 sites gains one argument (illustrative count, not in the paper).
  2. With type-checking: the compiler flags all 400 sites, so none is silently wrong. But a person must still edit and retest each one, and "it takes too long".
  3. Past 250K lines: the per-change cost makes even an agreed change "intolerable"; the design must stop depending on changing that interface.
  4. The remedy: split the system into pieces joined only by interfaces "stable for years", so a change inside one piece touches only that piece. The stable boundaries are the language and kernel interfaces.
Assumptions it relies on
  • A1. Many parts share the interface's assumptions (stated; that is why it is "basic").
  • A2. Clients cannot all be found and fixed cheaply (stated; worse without type-checking).
  • A3. The system is large (stated; the 250K-line threshold).
If an assumption changes
  • A1 changes (few clients): a private interface can change freely; the rule is about public, basic ones.
  • A2 changes (clients are trackable, strong types): change is "much easier", though still not free; Mesa is the paper's example.
  • A3 changes (small system): below the threshold, change is affordable and the rule relaxes.
Design notes and rejected alternatives

The rejected approach is to improve basic interfaces freely; the cost is paid by every client of every change. The paper places this under "Continuity", framing it as a standing tension with the desire to improve a design.

Connections

Dune (11/12) and x86 VMM (hwsw): both build on the most stable interface there is, the hardware instruction set and its privilege model; Dune works "with unmodified Linux kernels" precisely because that interface does not change (inference; outline lists these). NFS (10/22): NFS froze a protocol interface so clients and servers from different vendors interoperate for years, the networked version of a stable basic interface (inference).

M8 · Keep a place to stand: compatibility packages and the world-swap debugger

TL;DR
ProblemWhen interfaces must change, old programs still need to run, and the lowest layers still need to be debugged.
MechanismKeep something stable to stand on: implement the old interface on the new system, or keep a debugger that "does not depend on the correct functioning of anything in the target except the very simple world-swap mechanism."
Trade-offA small implementation effort in exchange for keeping old software usable and the lowest layers debuggable.
Breaks whenEven the minimal mechanism it stands on (the simulator's correctness, the swap, the tele-debugging nub) fails.
Key points
  • Compatibility package: "implements an old interface on top of a new system", so old programs keep working. "Many new operating systems (including Tenex ... and Cal ...) have kept old software usable by simulating the supervisor calls of an old system (TOPS-10 and Scope, respectively)", and "it is not hard to get acceptable performance."
  • Taken further: "the IBM 360/370 systems provided emulation of the instruction sets of older machines like the 1401 and 7090. Taken a little further, this leads to virtual machines, which simulate (several copies of) a machine on the machine itself."
  • World-swap debugger: it "works by writing the real memory of the target system ... onto a secondary storage device and reading in the debugging system in its place", then "mapping each target memory address to the proper place on secondary storage." It is "clumsy" but lets "very low levels of a system ... be debugged conveniently", and "is especially useful during bootstrapping."
  • Variations: a "tele-debugging nub in the target world that can interpret ReadWord, WriteWord, Stop and Go commands arriving from the debugger over a network", or, if the target is a time-sharing process, a debugger "in a different process."
How it works, step by step: a world swap after a kernel crash
  1. Trigger: the target crashes deep in the kernel, where its own file system and scheduler cannot be trusted.
  2. Swap out: the world-swap mechanism writes the target's entire memory to a secondary storage device.
  3. Swap in the debugger: the debugging system is read into memory. It depends on nothing of the target except the swap itself.
  4. Inspect: the programmer examines target address X; the debugger reads the corresponding saved location on secondary storage.
  5. Resume: "With care it is possible to swap the target back in and continue execution."
Assumptions it relies on
  • A1. A simulator of the old interface is far cheaper than reimplementing the old software (stated).
  • A2. A minimal mechanism (the swap, or a nub) can be made reliable even when the rest is broken (stated).
If an assumption changes
  • A1 changes (simulation is as hard as rewriting): the compatibility package stops paying off; then porting the software may be better (inference).
  • A2 changes (the minimal mechanism itself breaks): the debugger is blind, which is why the nub is kept as simple as ReadWord/WriteWord/Stop/Go.
Design notes and rejected alternatives

The rejected alternative is a debugger that uses the target's own services (file system, scheduler), which fail exactly when needed. Virtual machines are the generalization of the compatibility idea, which the paper names explicitly.

Connections

x86 VMM (hwsw) and ESX (course): virtual machines are the generalization the paper points at: "simulate (several copies of) a machine on the machine itself" (the paper's words; the pairing with these course papers is the outline's and this guide's). Dune (11/12): uses virtualization hardware to give a process a "place to stand" with direct hardware access while keeping the Linux interface (inference).

M9 · Plan to throw one away; you will anyhow

TL;DR
ProblemIf anything about a system's function is new, "the first implementation will have to be redone completely" to be acceptably small, fast and maintainable.
MechanismPlan for a prototype (sometimes two), and "copy a lot from a previous system" where you can.
Trade-offThe cost of building a throw-away, in exchange for a good final system; planning for it "costs a lot less".
Breaks whenThere is nothing new, so the first build can be the last; or innovation is so heavy that even two prototypes are not enough.
Key points
  • From Brooks: "Plan to throw one away; you will anyhow." "Unfortunately, sometimes two prototypes are needed, especially if there is a lot of innovation."
  • Copying helps: "Tenex was based on the SDS 940", and "This can even work even if the previous system was too grandiose; Unix took many ideas from Multics."
  • Revisit even success: "it pays to revisit old decisions as the system evolves; in particular, optimizations for particular properties of the load or the environment (memory size, for example) often come to be far from optimal."
How it works, step by step: planning the discard (illustrative, in the paper's spirit)
  1. Decide up front that the first version is a prototype to be discarded, so design effort does not go into polishing what will be thrown away.
  2. Build and use it; this is where the real requirement and the wrong central decisions become visible (for example, the wrong main data structure).
  3. Rebuild from a clean start, copying what worked from a previous system where possible (as Tenex copied the SDS 940).
  4. Keep revisiting: an optimization tuned to a small memory becomes "far from optimal" when memory grows, so old decisions are re-examined as the environment changes.
Assumptions it relies on
  • A1. The function is new, so the first design will be wrong in ways only use reveals (stated).
  • A2. A previous system exists to copy from (stated as helpful, not required).
If an assumption changes
  • A1 changes (nothing new): no throw-away is needed; copy a known design.
  • A2 changes (no predecessor): more prototypes may be required; "sometimes two prototypes are needed".
Design notes and rejected alternatives

The rejected approach is to ship the first implementation and patch it for years, so that its flaws become the interface clients depend on (this guide's inference; the paper says only that planning a prototype "costs a lot less"). Planning the throw-away is cheaper than being surprised by it.

Connections

LFS (10/27): a redesign of file-system layout after experience with FFS-style systems, the throw-and-rebuild pattern across a decade (inference; outline lists this). F2FS (11/5): LFS redone again for flash, revisiting decisions tuned to spinning disks (inference).

M10 · Keep secrets of the implementation

TL;DR
ProblemClients that rely on implementation details force the implementation to stay the same.
MechanismSecrets are "assumptions about an implementation that client programs are not allowed to make"; the interface "defines the things that cannot change".
Trade-offEasier to modify each part separately, in exchange for harder interface design and performance left on the table.
Breaks whenExtra assumptions between parts would buy a large speedup, or exposing power (M4) is more valuable than hiding it.
Key points
  • Definition (paraphrased from Britton et al.): "Secrets are assumptions about an implementation that client programs are not allowed to make. In other words, they are things that can change."
  • The cost of secrecy: "One way to improve performance is to increase the number of assumptions that one part of a system makes about another; the additional assumptions often allow less work to be done, sometimes a lot less. For instance, if a set of size n is known to be sorted, a membership test takes time log n rather than n."
  • The balance: "This technique is very important in the design of algorithms and the tuning of small modules. In a large system the ability to improve each part separately is usually more important. Striking the right balance remains an art." Dijkstra's line is the warning: "An efficient program is an exercise in logical brinkmanship."
  • Explicit tension with M4: "there is a tension with the desire not to hide power."
How it works, step by step: sortedness as a secret or an interface
  1. The fast assumption: a set module keeps its elements sorted, so a client that may assume sortedness can do membership by binary search in about log n comparisons; for n = 1,000,000 that is about 20 instead of up to 1,000,000 (the paper's example; the specific counts are this guide's).
  2. The cost: once clients depend on sortedness, the module can no longer switch to a hash table (faster for membership but unsorted) without breaking them.
  3. The choice: if sortedness is a secret, the module stays free to change representation, but clients cannot exploit it. If it is in the interface, clients get the speed but the representation is frozen.
  4. The rule: in a large system, keeping the secret (freedom to improve each part) usually wins; in a tuned small module, exposing it can be worth the lock-in.
Assumptions it relies on
  • A1. Parts will need to be improved independently over time (stated; the large-system case).
  • A2. The speedup from an exposed assumption is not essential (implicit; otherwise expose it).
If an assumption changes
  • A1 changes (the part never changes): hiding the detail buys nothing, and exposing it for speed is fine; this is the tuned-small-module case.
  • A2 changes (the speedup is critical): put the assumption in the interface deliberately, accepting the frozen representation, which is "don't hide power" winning the trade (M4).
Design notes and rejected alternatives

The two hints M4 and M10 pull opposite ways: expose desirable capabilities, hide changeable details. The paper does not resolve this; it says the balance "remains an art", and the designer decides per interface which assumptions are secrets.

Connections

Eraser (10/6): a locking discipline is an assumption that is usually a secret (that every shared variable is protected by some lock); Eraser is a tool to state and check it rather than leave it implicit (inference). Mesa (course): Mesa's interface modules make the secret-versus-interface line explicit in the language, the mechanism this hint relies on (inference; outline lists these).

M11 · Divide and conquer

TL;DR
ProblemA hard problem, or one too big for the available resources, cannot be solved in one piece.
MechanismReduce it to easier subproblems (usually recursive); when resources are limited, "bite off as much as will fit, leaving the rest for another iteration."
Trade-offThe complexity of partitioning in exchange for solving a problem that would not otherwise fit.
Breaks whenA single indivisible piece still does not fit (for the Scavenger, "a single file's index").
Key points
  • The Alto Scavenger "scans the disk and rebuilds the index and directory structures of the file system from the file identifier and page number recorded on each disk sector." A rewrite builds "one entry for each contiguous run of disk pages that is also a contiguous set of pages in a file"; "Normally files are allocated more or less contiguously and this structure is not too large." If the disk is "badly fragmented" and it will not fit, "the Scavenger discards the information for half the files and continues with the other half", repeating; "the method fails only if a single file's index won't fit."
  • The Dover printer "scan-converts lists of characters and rectangles into a large m x n array of bits ... m=3300 and n=4200, so the array contains fourteen million bits and is too large to store in memory. The printer consumes bits faster than the available disks can deliver them, so the array cannot be stored on disk." The array is cut into "16 x 4200 bit slices called bands", with "two one-band buffers"; objects are sorted into one bucket per band, and "Objects that spill over the edge of one band are added to the next bucket; this is the trick that allows the problem to be subdivided."
  • Quantizing a resource is a related device: "Sometimes it is convenient to artificially limit the resource, by quantizing it in fixed-size units; this simplifies bookkeeping and prevents one kind of fragmentation. The classical example is the use of fixed-size pages for virtual memory, rather than variable-size segments." Why paging won: "The reasons for this are complex and have not been systematically studied."
How it works, step by step: printing one band
  1. Sort: each character or rectangle goes into the bucket of the band it starts in.
  2. Fill: scan-convert the objects in band k's bucket into buffer A.
  3. Handle spill: an object that extends past band k's bottom edge has its remainder added to band k+1's bucket, so nothing is lost at the boundary.
  4. Play out and swap: buffer B (the previous band) is streamed to the printer and zeroed while A fills; then the buffers swap roles for band k+1. The printer "consumes bits faster than the available disks can deliver them", and it is fed from the two buffers alone; that the paper moving through it cannot wait for a late band is general knowledge about laser printers, not stated in the paper.
Assumptions it relies on
  • A1. The problem splits into pieces that each fit, with a cheap rule for the parts that cross a boundary (stated; spill into the next bucket, discard half the files).
  • A2. For the Scavenger, files are "more or less contiguously" allocated, so the normal structure is small (stated).
If an assumption changes
  • A1 changes (an indivisible piece is too big): the method fails, as the paper says for "a single file's index".
  • A2 changes (badly fragmented disk): the run structure grows and must be split repeatedly; the Scavenger "discards the information for half the files" and recurses.
Design notes and rejected alternatives

The paper rules out the two obvious places to put the page: memory (the array "is too large to store in memory") and disk (the printer is faster than "the available disks"). A larger memory would also have worked; that it cost too much in 1980 is this guide's inference. Quantizing (fixed pages over variable segments) is divide-and-conquer applied to a resource: equal pieces simplify bookkeeping and avoid external fragmentation, at the price of internal fragmentation.

Connections

Superpages (10/13): the paging-versus-segmentation choice the paper names is exactly the base-page-versus-superpage trade; superpages reintroduce a larger quantum for TLB reach (inference). vLLM (11/19): PagedAttention quantizes the KV cache into fixed 16-token blocks for the same bookkeeping and fragmentation reasons, and the question Lampson says has "not been systematically studied" gets a measured answer for one workload there (inference; outline lists this). LFS (10/27) and F2FS (11/5): the fixed-size segment is the quantum the cleaner works over (inference).

M12 · Use a good idea again instead of generalizing it

TL;DR
ProblemGeneralizing one mechanism to fit every use produces a bloated one.
MechanismReuse the idea (not the code) in a specialized form for each setting; "A specialized implementation of the idea may be much more effective than a general one."
Trade-offSeveral specialized implementations in exchange for each being simple, effective and free of circular dependence.
Breaks whenThe settings are similar enough that one implementation really does serve all without penalty.
Key points
  • Replication reused three ways: "A small amount of data can easily be replicated locally by writing it on two or more disk drives." For large or cross-machine data, Gifford "shows how to solve this problem by building replicated data on top of a transactional storage system", and "The transactional storage itself depends on the simple local replication scheme to store its log reliably. There is no circularity here, since only the idea is used twice, not the code." A third use: "store the commit record on several machines."
  • The Star user interface: "a small set of operations (type text, move, copy, delete, show properties) that apply to nearly all the objects in the system." The meaning "varies with the class of object" (copying a document to an out basket "causes it to be sent as a message"; moving a line endpoint makes it "follow like a rubber band"), and "the implementations are quite different in many cases." The generic operations "represent a view of what operations are possible and how the implementation of each class of object should be organized."
How it works, step by step: replication used three times without circularity
  1. Idea, use 1 (local): the smallest, most reliable form, writing data to two or more drives, stores the transaction log.
  2. Idea, use 2 (large, cross-machine): replicated data is built on top of transactional storage, so an arbitrarily large update is one atomic operation.
  3. Idea, use 3 (commit record): the commit record is stored on several machines.
  4. Why no cycle: use 2 depends on use 1 (the log needs the simple local scheme), but they are different implementations of the same idea, so "There is no circularity here, since only the idea is used twice, not the code."
Assumptions it relies on
  • A1. The idea admits a cheaper specialized form in each setting (stated).
  • A2. Reusing the idea rather than the code avoids coupling and circular dependence (stated).
If an assumption changes
  • A1 changes (settings are alike): one implementation may serve all with no penalty, so sharing code is fine.
  • A2 changes (sharing code is safe): then generalize; but a general replication layer that used itself to store its own log would be circular, which is the trap the hint avoids.
Design notes and rejected alternatives

The rejected design is one general replication mechanism; it would be larger and slower than each specialization, and risks circular dependence. Using the idea, not the code, keeps the layers independent.

Connections

Salus (11/17): replication of storage with verification layered on top is the same layered reuse of a reliability idea (inference; outline lists this). LFS (10/27): the log idea appears as both the on-disk structure and the crash-recovery mechanism, reused in specialized forms (inference).

M13 · Handle normal and worst cases separately

TL;DR
Problem"The requirements for the two are quite different", so one mechanism satisfying both is complex and slow.
Mechanism"The normal case must be fast. The worst case must make some progress." Use a different, often cruder strategy for the worst case, backed by "a little something in reserve under a mattress".
Trade-offOccasional bad behavior (unfairness, a crash, a slow recovery) in exchange for a fast common path.
Breaks whenThe resources needed to free one item in the worst case are not bounded, so no fixed reserve suffices.
Key points
  • The paper accepts failure in the worst case: "In most systems it is all right to schedule unfairly ... or even to deadlock the entire system, as long as this event is detected automatically and doesn't happen too often." "one crash a week is usually a cheap price to pay for 20% better performance", provided there is "decent error recovery (an application of the end-to-end principle)".
  • Cedar's reference-counting collector skips counting local-frame pointers ("most pointer assignments are to local variables"), scanning frames at collection instead, and even assumes every local variable is a pointer; "Measurements show that less than 1% of the storage is incorrectly retained." But reference counting "cannot reclaim circular structures", so Cedar "therefore has a conventional trace-and-sweep collector as well", used "during coffee breaks" because it "stops the entire system for many seconds".
  • The mattress reserve: freeing a resource can need extra resources ("some table might have to be swapped in to find out where to write out a page"). "Keep a little something in reserve under a mattress, bringing it out only in a crisis." "It is necessary to bound the resources needed to free one item; this determines the size of the reserve under the mattress". "When the crisis arrives, only one item should be freed at a time, so that the entire reserve is devoted to that job".
  • Bravo's piece table is a normal-case representation ("The strings are never modified during normal editing"; edits split pieces) with a worst-case cleanup: "After hours of editing there are hundreds of pieces and things start to bog down ... cleanup ... writes a new file containing all the characters of the document in order", replacing the table with one piece.
How it works, step by step: the mattress reserve in a paging system
  1. Normal case: a page fault needs a free frame and takes a clean one from the cushion at no cost.
  2. Cushion gone: all pages are dirty, so freeing one requires writing it out, which may itself need a table paged in, which needs a frame.
  3. Bring out the reserve: use the fixed reserve, sized to "bound the resources needed to free one item", to write exactly one page out.
  4. One at a time: devote the whole reserve to that single eviction; this "may slow things down a lot but it ensures that progress will be made." Once a clean frame exists, normal operation resumes.
Assumptions it relies on
  • A1. The worst case is rare, so its cost is amortized away (stated; "doesn't happen too often").
  • A2. There is "decent error recovery" for the crashes the fast path allows (stated; an end-to-end requirement).
  • A3. The resources to free one item are bounded, so the reserve has a finite size (stated).
If an assumption changes
  • A1 changes (the worst case is common): the fast path's shortcuts stop paying; you must make the general case efficient instead.
  • A2 changes (no recovery): allowing crashes for speed is unsafe; the paper ties the whole hint to end-to-end recovery being present anyway.
  • A3 changes (unbounded work to free one item): no mattress is big enough, and the system can deadlock freeing memory; this is the failure the reserve is designed to prevent.
Design notes and rejected alternatives

Designing one mechanism for both cases makes the normal case slow; designing only for the normal case makes the worst case a disaster unless a fallback exists. The pattern is a fast path plus a crude but sure path: reference counting plus trace-and-sweep, the piece table plus cleanup, the cushion plus the reserve.

Connections

Livelock (10/6): receive livelock is a worst case where an overloaded host spends its time on input interrupts and delivers almost nothing to applications (general knowledge of the Livelock paper); the fix (limit interrupt work so the protocol stack still runs) is "the worst case must make some progress" applied to a network host (inference; outline lists this). LFS (10/27): the segment cleaner is the background worst-case path paired with the fast append-only normal path, like Bravo's cleanup (inference). ESX (course): ballooning and swapping are the worst-case reserve for memory overcommit (inference).

M14 · Split resources in a fixed way if in doubt

TL;DR
ProblemSharing a pool is slower to allocate, often slower to access, and less predictable than dedicated resources.
MechanismAllocate dedicated resources: "It is usually faster to allocate ... often faster to access them, and the behavior of the allocator is more predictable."
Trade-off"More total resources are needed ... than if all come from a common pool", but often the extra cost is small or less than the multiplexing overhead.
Breaks whenThe resource is scarce and expensive, so the fragmentation from dedicating it outweighs the overhead of sharing.
Key points
  • Registers: "it is always faster to access information in the registers of a processor than to get it from memory, even if the machine has a high-performance cache." In "the approved modern style with lots of small procedures, 16 registers are nearly always enough", and "With n sets of registers arranged in a stack, saving is needed only when there are n successive calls without a return."
  • "Input/output channels, floating-point coprocessors, and similar specialized computing devices are other applications of this principle. When extra hardware is expensive these services are provided by multiplexing a single processor, but when it is cheap, static allocation of computing power ... is worthwhile."
  • The Interlisp virtual memory keeps the virtual-to-disk map in dedicated real memory rather than in paged virtual memory (as Pilot does), because "the need to avoid circularity makes this rather complicated. Instead, real memory is dedicated to this purpose. Unless the disk is ridiculously fragmented the space thus consumed is less than the space for the code to prevent circularity." (This is the dedicated memory that made M1's Alto fault a single disk access.)
How it works, step by step: the register stack (the paper's example)
  1. Dedicate a set per call: with, say, n = 4 register sets in a hardware stack (illustrative), the running procedure holds set 0; its call to A takes set 1, A's call to B takes set 2, B's call to C takes set 3, each with no save to memory.
  2. No save until the stack is full: C's call to D is the fourth successive call without a return, and only now is a save needed: "saving is needed only when there are n successive calls without a return", so the oldest set spills to memory.
  3. Why it is faster: the common case (shallow nesting) never touches memory, and allocation is trivial because each call gets a whole dedicated set rather than fighting for a shared pool.
  4. The cost: more total registers than a shared file would need; the paper's point is that this cost is usually small and buys speed and predictability.
Assumptions it relies on
  • A1. The extra total resource is cheap, or cheaper than the multiplexing overhead (stated).
  • A2. The per-client demand is bounded and predictable (implicit; 16 registers "nearly always enough").
If an assumption changes
  • A1 changes (resource is scarce and dear): dedicating it wastes too much; sharing with reclamation is better. The paper's own counter-setting is tight memory, where it argues for a cushion but not for static per-job splits (M22).
  • A2 changes (demand is unbounded or bursty): a fixed split either starves or wastes; dynamic sharing adapts, which is the ESX position for memory (inference).
Design notes and rejected alternatives

The rejected design is a shared pool with an allocator; it needs less total resource but is slower to allocate, slower to access and less predictable. The hint is hedged ("if in doubt"): it is a default, not a law.

Connections

ESX (course): an explicit counterexample in a setting where memory is scarce: ESX overcommits and reclaims (ballooning, sharing) rather than splitting statically, because the fixed split would waste the scarce resource (inference; outline lists this). FFS (field guide): cylinder groups are a fixed partition of the disk that trades some balance for locality and predictable local allocation, the same instinct (inference). Salus (11/17): GPU lanes dedicate memory regions so allocation within a lane is predictable (inference).

M15 · Use static analysis if you can

TL;DR
ProblemA decision made at run time costs time on every execution.
MechanismAnalyze the program in advance for properties that improve performance; "when a good static analysis is not possible, don't delude yourself with a bad one, but fall back on a dynamic scheme."
Trade-offBetter performance when the analysis succeeds, in exchange for the analysis cost and sometimes lost robustness.
Breaks whenThe analysis cannot succeed, or it depends on an invariant that a bug or hardware fault can falsify.
Key points
  • Registers again: "the compiler can easily decide how to allocate them, simply by putting the local variables and temporaries there." But without a register stack, "good allocation is then much more difficult, requiring an elaborate inter-procedural analysis that may not succeed ... So a little bit of dynamic analysis (stacking the registers) goes a long way."
  • Sequential access: "A program can read data much faster when it reads the data sequentially ... it is easy to predict what data will be needed next and read it ahead into a buffer. Often the data can be allocated sequentially on a disk, which allows it to be transferred at least an order of magnitude faster." These gains "depend on the fact that the programmer has arranged the data so that it is accessed according to some predictable pattern".
  • A sharp negative result: "Many attempts have been made to analyze programs after the fact and optimize the disk transfers, but as far as I know this has never worked. The dynamic analysis done by demand paging is always at least as good."
  • The robustness caveat: "Some kinds of static analysis exploit the fact that some invariant is maintained. A system that depends on such facts may be less robust in the face of hardware failures or bugs in software that falsify the invariant."
How it works, step by step: register allocation with and without a stack
  1. With static analysis (easy case): the compiler puts P's locals x, y in registers R1, R2 at compile time, with no run-time check, because it can see the whole procedure.
  2. The cross-procedure problem: on a machine without register stacking, a call from P to Q needs inter-procedural analysis to know whether Q clobbers R1 and R2; that analysis "may not succeed and ... must be redone each time the program changes."
  3. Fall back to dynamic: a register stack moves each call to a new set, so no analysis is needed; "a little bit of dynamic analysis ... goes a long way."
  4. The warning: do not fake the static analysis. A wrong assumption gives wrong code or poor performance, and an invariant-based optimization can break under a fault.
Assumptions it relies on
  • A1. A good static analysis is actually possible for the property (stated precondition, "if you can").
  • A2. The program arranges data predictably (stated; sequential access).
  • A3. The invariant the analysis relies on really holds (stated caveat).
If an assumption changes
  • A1 changes (analysis cannot succeed): "fall back on a dynamic scheme"; the paper's strongest claim is that after-the-fact disk optimization "has never worked" and demand paging is at least as good.
  • A2 changes (access is unpredictable): prefetching and sequential layout lose their gain; demand paging adapts instead.
  • A3 changes (invariant falsified): the optimized path produces wrong results under a bug or fault; robustness drops.
Design notes and rejected alternatives

The rejected approach is a bad static analysis dressed up as a good one. The paper repeatedly prefers a small amount of dynamic work (register stacking, demand paging) to an elaborate static scheme that may not succeed.

Connections

Exokernel (11/10) and Dune (11/12): both let applications apply knowledge of their own access patterns, static analysis moved to where it can succeed (inference; outline lists these). FFS (field guide): FFS's sequential layout is exactly the "arrange the data so static analysis (prefetch) is possible" case (inference). Superpages (10/13): contiguity is a static property the system tries to maintain so larger mappings are possible (inference).

M16 · Dynamic translation

TL;DR
ProblemA representation that is convenient (compact, easy to modify or display) is slow to interpret.
MechanismTranslate from the convenient representation to a fast one on demand and cache the result, "a variation on the old idea of compiling."
Trade-offTranslation time and cache space in exchange for fast execution without giving up the convenient form.
Breaks whenTranslated code is not reused enough to repay the translation.
Key points
  • The general scheme: "always do the translation on demand and cache the result; then only one interpreter is required, and no decisions are needed except for cache replacement."
  • An experimental Smalltalk implementation "uses the bytecodes produced by the standard Smalltalk compiler as the convenient (in this case, compact) representation, and translates a single procedure from byte codes into machine language when it is invoked. It keeps a cache with room for a few thousand instructions of translated code." The break-even rule: "the cache must be large enough that on the average a procedure is executed at least n times, where n is the ratio of translation time to execution time for the untranslated code."
  • The C-machine stack cache translates operand addresses as instructions load: an address "relative to the local frame pointer FP is converted into an absolute address, using the current value of FP", and if it lies in the stack data cache the operand becomes register mode. "The FP value is concatenated with the instruction address to form the key", so multiple activations of one procedure still work.
How it works, step by step: the Smalltalk break-even (the paper's rule, worked)
  1. Convenient form: a procedure is kept as compact bytecodes, easy to ship and store.
  2. Translate on first call: when the procedure is invoked, translate it to machine code and put it in the cache of "a few thousand instructions".
  3. Reuse: later calls run the cached machine code directly. If the cache is too small, the procedure is evicted and retranslated, and the scheme loses.
  4. Break-even: translation pays if a procedure runs at least n times, n = translation time / untranslated execution time. Illustrative numbers (not in the paper): if translating costs 50 microseconds, interpreting costs 5 per call and translated code costs 1, the saving per call is 4, so translation repays after 50/4 = about 13 calls; the paper's simpler rule gives n = 50/5 = 10.
Assumptions it relies on
  • A1. The convenient form is worth keeping (compact, shippable, editable) (stated).
  • A2. Translated code is reused enough to cross the break-even (stated).
  • A3. The cache holds the active translated code (stated; otherwise thrash).
If an assumption changes
  • A1 changes (no need for the convenient form): compile ahead of time instead; the on-demand scheme adds no value.
  • A2 changes (little reuse): translation never repays, so interpret directly.
  • A3 changes (cache too small): the system retranslates repeatedly "and loses"; grow the cache or interpret.
Design notes and rejected alternatives

The alternatives are pure interpretation (slow) and full ahead-of-time compilation (loses the compact, editable form). On-demand translation plus a cache keeps the convenient form and pays the translation only where it is reused, hidden behind the cache.

Connections

x86 VMM (hwsw): binary translation of guest code with a translation cache is this hint applied to virtualization; the companion outline for that session (the binary-translation question quoted in the brief) is the same mechanism, including detecting modified translated code (inference; outline lists this). vLLM (11/19): caching computed KV state to avoid recomputation is a related "translate once, reuse" idea (inference).

M17 · Cache answers to expensive computations

TL;DR
ProblemRecomputing an expensive function repeatedly wastes time.
MechanismStore "the triple [f, x, f(x)] in an associative store with f and x as keys"; if f is not functional, "invalidate or update a cache entry if the value of f(x) changes."
Trade-offMemory for entries and the burden of keeping them valid, in exchange for speed that scales with how expensive f(x) is.
Breaks whenThe cache is too small for the active values (it "thrashes"), or invalidation cannot be done precisely and cheaply.
Key points
  • Non-functional f needs update or invalidation, via "an equation of the form f(x + ∆) = g(x, ∆, f(x)) in which g is much cheaper to compute than f." The paper's example: x is 1000 numbers, f the sum, ∆ = [i, v]; then "g(x, [i, v], sum) is sum - xi + v."
  • Size adaptively: a too-small cache "will thrash", so "choose the cache size adaptively, making it bigger when the hit rate decreases and smaller when many entries go unused for a long time."
  • The classic cases: hardware caches (entries "[Fetch, address, contents of address]", invalidated after a store) and virtual memory ("main storage plays the role of the cache, disk plays the role of main storage").
  • The organizing principle for interactive systems: "recompute the entire state after each change but cache all the expensive results of this computation ... The secret of success is to organize the cache so that small changes invalidate only a few entries."
  • Bravo's DisplayLine cache: one entry per displayed line, "and sometimes a few lines just above or below." "An edit that changes characters i through j invalidates any cache entry for which [firstChar .. lastCharUsed] intersects [i .. j]." Unused entries at the end are discarded: "not invalid, but ... no longer interesting because the line breaks have changed." Pagination uses the same idea with [paragraph, ParagraphShape(paragraph)] entries ("three or four bytes" each, "about 1k bytes" for a 30-page chapter).
How it works, step by step: the sum cache (the paper's example, traced)
  1. Cached state: x is an array of 1000 numbers and the cached answer is sum = 5000.
  2. A small change: element i = 7 holds 12 and is changed to 20, so ∆ = [7, 20].
  3. Incremental update: g computes 5000 − 12 + 20 = 5008 in constant time, instead of re-adding 1000 numbers (O(n)).
  4. Why it works: the update equation f(x + ∆) = g(x, ∆, f(x)) exists and g is far cheaper than f; where no such equation exists, the entry must be invalidated and f recomputed.
Assumptions it relies on
  • A1. f(x) is reused before the entry is evicted (stated; otherwise no gain).
  • A2. When f is not functional, a cheap, precise invalidation or update rule exists (stated).
  • A3. The cache holds the active working set (stated; size adaptively).
If an assumption changes
  • A1 changes (no reuse): the cache costs memory and invalidation for nothing; do not cache.
  • A2 changes (invalidation is imprecise): "invalidate more entries at the price of more computing", or the cache goes stale and gives wrong answers.
  • A3 changes (too small): it thrashes and "performance will suffer badly"; this is where a hint (M18), which needs no invalidation protocol, can be cheaper.
Design notes and rejected alternatives

The rejected approach is ad-hoc incremental update of a complex state, which is "extremely error-prone". The disciplined version is: conceptually recompute everything, but cache every expensive result and invalidate precisely. A cache differs from a hint (M18) in that it must be kept correct; a hint may be wrong and is checked on use.

Connections

NFS and Leases (10/22): the client attribute cache is a cache of a non-functional value (a file another client may change); NFS invalidates by a short timeout (3 or 30 seconds) and Leases by a time-limited promise, two answers to the paper's need to "invalidate or update a cache entry if the value of f(x) changes" (inference; outline lists this). Superpages (10/13) and x86 VMM (hwsw): the TLB is a cache of address translations, invalidated on a mapping change (inference). vLLM (11/19): the KV cache is a cache of expensive attention computation, with reuse via shared prefixes (inference).

M18 · Use hints to speed up normal execution

TL;DR
ProblemA cache is only useful if kept correct; keeping it correct can be expensive or impossible.
MechanismA hint is "the saved result of some computation" that "may be wrong, and ... is not necessarily reached by an associative lookup"; it is "checked against the 'truth'" before "any unrecoverable action", and must be "correct nearly all the time."
Trade-offSpeed on the usual path in exchange for a check on every use and the ability to reconstruct or fall back.
Breaks whenThere is no cheap check, or the hint is often wrong, so it fails the paper's requirement that it "must be correct nearly all the time".
Key points
  • Alto and Pilot file systems: "each file has a unique identifier, and each disk page has a 'label' field whose contents can be checked before reading or writing the data without slowing down the data transfer. The label contains the identifier of the file that contains the page and the number of that page in the file." Page zero, the leader page, holds the name and directory. "This is the truth".
  • The directory and the page map are hints: finding a file id from a name, or the address of page i, otherwise needs a whole-disk scan. "Information obtained from any of these hints is checked when it is used, by checking the label ... If it proves to be wrong, all of it can be reconstructed by scanning the disk." Even "the bit table that keeps track of free disk pages is a hint; the truth is ... a special value in the label of a free page", checked before the label is overwritten.
  • Arpanet routing: each node's best-route table "is updated by periodic broadcasts" that "are not synchronized and are not guaranteed to be delivered", so "the nodes may not have a consistent view at any instant." The truth is that "each node knows its own identity"; routing "does the best it can", "nearly optimal" when things change slowly.
  • Ethernet: "lack of a carrier signal on the cable is used as a hint that a packet can be sent." On a collision both back off; "If n successive collisions occur, this is taken as a hint that the number of senders is 2n", and each sets its mean delay to 2n times its initial value, the "exponential backoff".
  • Smalltalk method lookup: the call site caches the last type and procedure as immediate values; each procedure begins by checking t ≠ lastT and only then does the full lookup. "Measurements show that this cache hits about 96% of the time", and when right "the call is as fast as an ordinary subroutine call." The S-1's branch-prediction bit per cached instruction is "the same idea in a different guise."
How it works, step by step: opening an Alto file through the directory hint
  1. Use the hint: the directory says file "memo" is id 7 with its first page at disk address 1200. Go straight to sector 1200 (illustrative addresses).
  2. Check against the truth: read sector 1200's label; it must say file 7, page 0, and the leader page must say the name "memo". The check rides along with the read "without slowing down the data transfer".
  3. Hit (the 96%-style common case): the label matches, so the hint was right; proceed.
  4. Miss: the label says a different file (the file was moved), so the hint is wrong. Take no unrecoverable action; fall back to the truth by scanning the disk labels, then rebuild the directory and map hints.
  5. Free-page case: before writing a page the allocator thinks is free (a bit-table hint), it checks that the target label still holds the special free value, so a stale free-bit never clobbers live data.
Assumptions it relies on
  • A1. A cheap check against the truth exists (stated; the label ride-along).
  • A2. The hint is right nearly all the time (stated; 96% for Smalltalk).
  • A3. The truth can reconstruct the hint after a miss (stated; scan the disk).
If an assumption changes
  • A1 changes (no cheap check): a hint is unsafe, because a wrong one could cause an unrecoverable action; use a cache with real invalidation instead (M17).
  • A2 changes (often wrong): every use pays the check and then the slow path as well, so the hint can cost more than having no hint (inference from "it must be correct nearly all the time").
  • A3 changes (truth cannot rebuild it): a miss is unrecoverable; the hint discipline requires a reconstructable truth.
Design notes and rejected alternatives

A hint needs no invalidation protocol, which is its advantage over a cache: a stale hint is merely slower, not wrong, because every use is checked. The rejected design is to keep the fast structures correct at all times (locking, protocols); the hint moves that cost to a cheap per-use check plus a rare rebuild.

Connections

NFS and Leases (10/22): a file handle carries a generation number so a stale handle is detected and rejected rather than trusted, exactly a hint checked against the truth; cached attributes are hints refreshed by any reply (inference; outline lists this). Ethernet to Livelock (10/6): backoff under overload is the same load-shedding instinct Livelock applies to a host (inference). FFS (field guide): a global policy's preferred block is a hint the local allocator checks and falls back from (inference). Exokernel (11/10): XN does not trust a library file system's claims about which blocks its metadata names; it runs the libFS's UDF on the metadata itself before an update, a claim checked against the truth (inference).

M19 · When in doubt, use brute force

TL;DR
ProblemA complex, poorly characterized solution works well only when its assumptions hold.
MechanismPrefer "a straightforward, easily analyzed solution that requires a lot of special-purpose computing cycles", "especially as the cost of hardware declines."
Trade-offWasted cycles in exchange for predictability and simplicity.
Breaks whenThe brute-force cost is too high for the hardware available (the paper's own qualifier is "especially as the cost of hardware declines").
Key points
  • Belle: "Ken Thompson's chess machine Belle relies mainly on special-purpose hardware to generate moves and evaluate positions, rather than on sophisticated chess strategies. Belle has won the world computer chess championships several times."
  • Personal computers over time-sharing: "the latter include much more cleverness and have many fewer wasted cycles, but the former are increasingly recognized as the most cost-effective way to do interactive computing."
  • Asymptotics are not everything: "There is an algorithm that multiplies two n x n matrices faster than O(n2.5), but the constant factor is prohibitive." And "the 7040 Watfor compiler uses linear search to look up symbols; student programs have so few symbols that the setup time for a better algorithm can't be recovered." (The 2.5 exponent is restored from the page image; the PDF text layer flattened it.)
How it works, step by step: Watfor's symbol lookup (the paper's example)
  1. The simple method: look up each symbol by scanning the symbol table linearly.
  2. The clever method: a hash table turns each lookup into roughly constant time, but needs hashing, allocation and setup.
  3. The actual load: student programs "have so few symbols" that, for a table of, say, 20 entries, linear search averages 10 comparisons (illustrative), which the hash table's setup cost cannot beat.
  4. The choice: brute force wins because it is simple, predictable, and the data is small; cleverness would add setup cost that "can't be recovered."
Assumptions it relies on
  • A1. Hardware (cycles, chips) is cheap relative to the value of simplicity (stated).
  • A2. The input is small or the constant factors favor the simple method (stated; Watfor, matrix multiply).
If an assumption changes
  • A1 changes (hardware is scarce or dear): the wasted cycles matter and cleverness repays; this is the pre-cheap-hardware regime the paper notes it is moving away from.
  • A2 changes (large input): the asymptotically better algorithm wins once n is large enough to overcome the constant factor.
Design notes and rejected alternatives

The rejected approach is a complex method tuned to assumptions that may not hold. Brute force is "straightforward, easily analyzed", while the alternative is "complex, poorly characterized" and "may work well if certain assumptions are satisfied", and the paper bets on declining hardware cost to pay for it.

Connections

Dune (11/12): using ordinary virtualization hardware instead of building a custom kernel is brute force in the paper's sense, taking the simple, available mechanism (inference; outline lists this). Exokernel (11/10): letting applications do their own management rather than building clever general policies into the kernel is a related simplicity bet (inference).

M20 · Compute in background when possible

TL;DR
ProblemWork done before responding delays the response, and load varies so idle time exists later.
Mechanism"Do as little work as possible before responding to a request"; defer the rest to background processes.
Trade-offSynchronization between foreground and background in exchange for response time.
Breaks whenThe background work falls behind, so the foreground must wait anyway, or the synchronization needed is intricate.
Key points
  • Two reasons: "a rapid response is better for the users", and "the load usually varies a great deal, so there is likely to be idle processor time later".
  • Examples "with successively less need for synchronization": "The Interlisp and Cedar garbage collectors ... do nearly all their work this way"; "Many paging systems write out dirty pages and prepare candidates for replacement in background"; "Electronic mail can be delivered and retrieved by background processes, since delivery within an hour or two is usually acceptable"; "Many banking systems consolidate the data on accounts at night".
  • "As the amount of synchronization increases more care is needed ... an extreme example is the on-the-fly garbage collection algorithm". But "in most cases a simple producer-consumer relationship between two otherwise independent processes is possible."
How it works, step by step: background page cleaning
  1. With background work: a daemon continuously writes dirty pages to disk and keeps a pool of clean frames.
  2. A fault arrives: it takes a clean frame from the pool immediately and reads the needed page: one disk wait.
  3. Without background work: the fault must first write out a dirty page, then read the new one: two disk waits, about double the wait (illustrative).
  4. The limit: if faults outrun the daemon, the clean pool empties and the foreground waits anyway; background work helps only when there is idle time to do it.
Assumptions it relies on
  • A1. Load varies, so idle time appears later (stated).
  • A2. The deferred work tolerates delay (stated; mail "within an hour or two").
  • A3. Foreground and background can be loosely coupled (stated; producer-consumer).
If an assumption changes
  • A1 changes (constant full load): there is no idle time, so the background falls behind and the foreground waits.
  • A2 changes (work is urgent): it cannot be deferred; it must be on the response path.
  • A3 changes (tight coupling needed): intricate synchronization is required, "an extreme example is the on-the-fly garbage collection algorithm".
Design notes and rejected alternatives

The rejected approach is doing all the work before responding. Deferring it to a loosely coupled background process shortens the response, at the cost of the synchronization needed to hand work across.

Connections

LFS (10/27) and F2FS (11/5): the segment cleaner runs in background (F2FS splits foreground greedy cleaning from background cost-benefit cleaning) exactly to keep it off the write path (inference; outline lists this). Rethink the Sync (10/29): external synchrony lets the file system do durability work asynchronously and block only external output, deferring the cost off the application's path (inference).

M21 · Use batch processing if possible

TL;DR
Problem"Doing things incrementally almost always costs more".
MechanismCollect work and do it together; "disks and tapes work much better when accessed sequentially", and "batch processing permits much simpler error recovery."
Trade-offLatency (results are not current until the batch runs) in exchange for lower cost and simpler recovery.
Breaks whenResults must be current, so the batch delay is unacceptable.
Key points
  • "The Bank of America has an interactive system that allows tellers to record deposits and check withdrawals. It is loaded with current account balances in the morning and does its best to maintain them during the day. But early the next morning the on-line data is discarded and replaced with the results of night's batch run."
  • "This design makes it much easier to meet the bank's requirements for trustworthy long-term data, and there is no significant loss in function."
How it works, step by step: the bank teller system (the paper's example, traced)
  1. Morning load: the on-line system starts with an account balance of, say, 1000 from the previous night's batch.
  2. During the day: a deposit of 200 and a withdrawal of 50 are recorded on line; the on-line balance shows 1150. This is the fast, interactive path.
  3. Night batch: the authoritative balance is recomputed from the day's records in one sequential batch run, which is cheaper and easier to make trustworthy.
  4. Next morning: the on-line data is discarded and reloaded from the batch result. Any error in on-line processing is erased each night; the batch run is the truth and the on-line copy behaves like a hint (this guide's reading, which the companion outline also notes).
Assumptions it relies on
  • A1. A delay before results are authoritative is acceptable (stated; overnight).
  • A2. Sequential batch access is much cheaper than incremental access (stated).
If an assumption changes
  • A1 changes (must be current): batching is unacceptable, and the system must maintain authoritative state continuously, which is harder to make trustworthy.
  • A2 changes (random access is as cheap): the main benefit shrinks to the simpler error recovery.
Design notes and rejected alternatives

The rejected approach is to maintain authoritative long-term data incrementally and continuously, which is harder to make trustworthy. Batching makes the on-line copy provisional and the nightly run the source of truth, simplifying recovery.

Connections

LFS (10/27): writing many changes as one large sequential segment is batching for the same reason the paper gives, that "disks and tapes work much better when accessed sequentially" (inference; outline lists this). Rethink the Sync (10/29): group commit batches many modifications into one journal transaction, trading latency for throughput (inference). F2FS (11/5): checkpointing collects metadata and writes it together (inference).

M22 · Safety first: avoid disaster rather than attain an optimum

TL;DR
Problem"A general-purpose system cannot optimize the use of resources", yet it is easy to overload one and "drastically degrade the service."
Mechanism"In allocating resources, strive to avoid disaster rather than to attain an optimum"; provide excess capacity because "hardware is cheap and getting cheaper."
Trade-offWasted capacity in exchange for avoiding collapse.
Breaks whenThe load "can be characterized extremely well" (then cleverness works).
Key points
  • The capacity rule: "A system cannot be expected to function well if the demand for any resource exceeds two-thirds of the capacity, unless the load can be characterized extremely well."
  • The paging lesson: people had visions of "squeezing the most out of every byte" (co-locating procedures, predicting references). "No one ever learned how to do this. Instead, memory got cheaper, and systems spent it to provide enough cushion for simple demand paging to work. We learned that the only important thing is to avoid thrashing".
  • Where cleverness did work: the 360/50 APL system, with "the same size workspace for each user and common system code", "makes all the system code resident, allocates a contiguous piece of disk for each user, and overlaps a swap-out and a swap-in with each unit of computation."
  • Scheduling: tuning by "priority ... working set size, memory loading, past history" and so on "failed"; "Only the crudest parameters produce intelligible effects". "The most successful schemes give a fixed share of the cycles to each job and don't allocate more than 100%". The quote: "The nicest thing about the Alto is that it doesn't run faster at night" (J. Morris).
How it works, step by step: planning a disk to the two-thirds rule
  1. Capacity: a disk serves 100 requests per second (illustrative).
  2. Plan to 2/3: keep the expected load near 67 requests per second, on the flat part of the queueing curve, where a request waits about 3 service times.
  3. Push to 95: at 95 per second random bursts frequently exceed capacity; the queue and response time grow sharply (about 20 service times at ρ = 0.95).
  4. The lesson: the extra 33% of unused capacity is the price of staying off the cliff, which is cheaper than the service collapse, because "hardware is cheap and getting cheaper".
Assumptions it relies on
  • A1. Hardware is cheap enough to over-provision (stated).
  • A2. The load is general-purpose and cannot be characterized exactly (stated; the exception is the APL system).
If an assumption changes
  • A1 changes (hardware is dear): over-provisioning is costly, so optimization comes back, the pre-1980s regime; but the paper warns the optimizations "No one ever learned how to do".
  • A2 changes (load is extremely well known): cleverness works, as in the APL system or a fixed-share scheduler for a uniform workload.
Design notes and rejected alternatives

The rejected approach is to optimize resource use (clever swapping, elaborate scheduling), which "failed" for general-purpose systems. The paper's choice is cushion plus avoid-thrashing, and a fixed share for scheduling, with the personal computer as the limit (one processor per user).

Connections

ESX (course): memory overcommit with reclamation is a policy for exactly the thrashing problem; it earns back some of the wasted cushion while still avoiding collapse (inference; outline lists this). Livelock (10/6): a host driven past capacity by interrupts collapses to zero throughput, the network version of exceeding the two-thirds point (inference). vLLM (11/19): admission and preemption keep GPU memory demand under capacity (inference).

M23 · Shed load to control demand

TL;DR
ProblemAn overloaded system serves nobody well.
Mechanism"Shed load to control demand, rather than allowing the system to become overloaded." A corollary of safety first.
Trade-offSome work is refused in exchange for adequate service to the rest.
Breaks whenA promise to not shed load (the Arpanet guarantee) makes deadlock "very hard to avoid".
Key points
  • "There are many ways to shed load. An interactive system can refuse new users, or even deny service to existing ones. A memory manager can limit the jobs being served so that all their working sets fit in the available memory. A network can discard packets. If it comes to the worst, the system can crash and start over more prudently."
  • Bob Morris's red button: a terminal button that, when pushed, forces the system to "either improve the service or throw the user off; it makes an equitable choice over a sufficiently long period", the idea being "to keep people from wasting their time in front of terminals that are not delivering a useful amount of service."
  • The Arpanet lesson: the original spec guaranteed delivery of any accepted packet "unless the recipient machine is down or a network node fails while it is holding the packet. This turned out to be a bad idea. This rule makes it very hard to avoid deadlock in the worst case ... the client does not benefit, since it still has to deal with packets lost by host or network failure (see section 4 on end-to-end). Eventually the rule was abandoned." The Pup internet "has always ruthlessly discarded packets at the first sign of congestion."
How it works, step by step: a memory manager shedding load
  1. The demand: 10 jobs each have a 20 MB working set; memory is 128 MB (illustrative).
  2. Admitting all: 200 MB of working sets in 128 MB forces constant paging; the system thrashes and all ten run slowly.
  3. Shed: admit six jobs (120 MB) and hold four, so the six have their working sets resident and run efficiently.
  4. Rotate: over time, admit the held jobs as others finish; refusing some demand now is what lets the accepted work proceed, rather than serving nobody.
Assumptions it relies on
  • A1. Refused clients can retry or wait (implicit).
  • A2. Load can be refused at a chokepoint (the door, the admission control, the queue).
If an assumption changes
  • A1 changes (clients cannot retry): shedding loses work permanently; this is why the Arpanet tried to guarantee delivery, and why that guarantee failed (clients had to handle loss anyway).
  • A2 changes (no chokepoint): load cannot be refused cleanly, and the system is driven past capacity, the collapse M22 warns about.
Design notes and rejected alternatives

The rejected design is the Arpanet delivery guarantee: promising never to drop an accepted packet. It made deadlock hard to avoid and did not help the client, which needed end-to-end recovery regardless. The Pup internet's "best efforts, drop early" is the accepted design.

Connections

Livelock (10/6): dropping packets early, before investing work in them, is exactly load shedding at the right place; the paper's Pup example is the principle (inference; outline lists this). vLLM (11/19): preempting and evicting sequences under memory pressure is load shedding for GPU memory (inference). NFS (10/22): a client retransmitting after a timeout is the retry side of shedding: a refused or dropped request is not lost if the client can send it again (inference).

M24 · End-to-end

TL;DR
ProblemLow-level reliability measures are neither sufficient nor necessary for a reliable system.
Mechanism"Error recovery at the application level is absolutely necessary for a reliable system, and any other error detection or recovery is not logically necessary but is strictly for performance" (Saltzer).
Trade-offIntermediate checks cost work and complexity but cut the amount of work repeated after an error.
Breaks whenThere is no cheap test for success, or the end-only design hides a performance defect "until the system ... is placed under heavy load."
Key points
  • The file-transfer argument: to be sure the right bits are on B's disk, "read the file from B's disk, compute a checksum of reasonable length (say 64 bits), and find that it is equal to a checksum of the bits on A's disk." Checking A's disk to A's memory, A to B over the net, or B's memory to B's disk "is not sufficient, since there might be trouble at some other point, the bits might be clobbered while sitting in memory". Those checks "are not necessary either, since if the end-to-end check fails the entire transfer can be repeated."
  • Intermediate checks are performance only: "if errors are frequent, intermediate checks can reduce the amount of work that must be repeated. But this is strictly a question of performance". At Cambridge "it is customary to copy an entire disk pack of 58 MBytes with only an end-to-end check; errors are so infrequent that the 20 minutes of work very seldom needs to be repeated."
  • Hints are an application of this (link back to M18): checking a sector label before writing "ensures that the disk address for the write is correct", and precautions to make the hint more likely correct "do not affect the reliability of the file system."
  • The Pup internet adopts best-efforts delivery at several levels; it still provides "a modest amount of error control (a 16-bit checksum)" and discard notifications, but "since they too are best efforts, they don't complicate the implementation much."
  • Two problems with the strategy: "First, it requires a cheap test for success. Second, it can lead to working systems with severe performance defects that may not appear until the system becomes operational and is placed under heavy load."
How it works, step by step: the Cambridge 58 MB copy
  1. Transfer: copy the whole 58 MB disk pack with no per-hop checking, about 20 minutes.
  2. End check: read the copy back from the destination and compare a checksum with the source's checksum.
  3. Equal: done. Because "errors are so infrequent", this is the usual outcome and the expected extra cost is tiny (illustrative: at a 1-in-100 failure rate, 0.01 x 20 = 0.2 minutes of rework on average).
  4. Different: repeat the entire transfer. Per-hop checks would reduce how much is redone, but the end check is still needed, so they buy only performance.
Assumptions it relies on
  • A1. A cheap end-to-end test for success exists (stated; the checksum compare).
  • A2. Errors are rare enough that repeating the whole operation is acceptable (stated; Cambridge).
If an assumption changes
  • A1 changes (no cheap end test): the strategy loses its simplicity; you may be forced into intermediate checks after all.
  • A2 changes (errors are frequent): repeating the whole transfer is too costly, so intermediate checks are added "strictly for performance", not for correctness.
  • Hidden under load: an end-only design can pass its tests and show "severe performance defects" only under heavy load, when retried whole operations pile up.
Design notes and rejected alternatives

The rejected design is to rely on a low-level guarantee (the Arpanet's guaranteed delivery, per-hop reliability) for application correctness. Only the endpoints know what "correct" means for the application, so the application-level check is necessary and the rest is optimization.

Connections

Rethink the Sync (10/29): external synchrony defines correctness by externally observable output, the end the user sees, and does internal work asynchronously, an end-to-end framing of durability (inference; outline lists this). Salus (11/17): end-to-end verification in a block store checks the data at the application boundary rather than trusting intermediate layers (inference). NFS (10/22): the client is responsible for completing a request (retransmit on timeout) because only it knows the operation succeeded, the end-to-end responsibility (inference).

M25 · Log updates to record the truth

TL;DR
ProblemCurrent state held in complex structures can be lost or corrupted in a crash.
MechanismRecord every update as a log entry, "the name of the update procedure and its arguments"; the log holds the truth, and the current state "is very much like a hint" (but with no cheap check).
Trade-offA little writing in exchange for reliable recovery and cheap duplication.
Breaks whenThe update procedures are not functional, or the arguments are not values (references to mutable objects).
Key points
  • Why a log: "a very simple data structure that can be reliably written and read, and cheaply forced out onto disk or other stable storage ... Because it is append-only, the amount of writing is minimized, and it is fairly easy to ensure that the log is valid no matter when a crash occurs."
  • Two requirements: "The update procedure must be a true function": "Its result does not depend on any state outside its arguments" and "It has no side effects, except on the object in whose log it appears." And "The arguments must be values": immediate values (copied entirely into the entry) or "references to immutable objects."
  • Versions: "a particular version of an object is immutable", named by "[object identifier, number of updates]"; replaying that many entries yields the version, and "as long as each update refers only to existing versions, there won't be any cycles and this process will terminate."
  • Bravo has "exactly two update functions": Replace(old: Interval, new: Interval) and ChangeProperties(where: Interval, what: FormattingOp), where an Interval is "[document version, first character, last character]". "Thus only two kinds of log entries are needed. All the editing commands reduce to applications of these two functions." (This works because the piece table in M13 never modifies the stored strings.)
How it works, step by step: replaying a Bravo document (the paper's two functions)
  1. Version 0 is the empty document.
  2. Entry 1: Replace([v0, 1, 0], [k3, 1, 5]) replaces the empty interval at the start of version 0 with characters 1 to 5 of k3, an immutable version of the scratch text that holds the typed "Hello" (both arguments are Intervals, as the paper requires; the scratch version k3 is illustrative). The result is version 1.
  3. Entry 2: ChangeProperties([v1, 1, 5], italic := true) italicizes it, producing version 2.
  4. After a crash: replay entry 1 then entry 2 from version 0; because each procedure is functional and its arguments are values, the result is the same version 2.
  5. Counter-case: an entry "insert the current time" reads state outside its arguments, so replaying it later gives a different result; the fix is to record the time value itself as an argument.
Assumptions it relies on
  • A1. Updates can be expressed as functional procedures (stated; the first requirement).
  • A2. Arguments are immediate values or references to immutable versions (stated; the second requirement).
  • A3. The log can be forced to stable storage and is cheap to write (stated).
If an assumption changes
  • A1 changes (non-functional update): replay gives a different result, so recovery is wrong; the entry must be rewritten to be functional.
  • A2 changes (argument is a mutable object): the referenced object may have changed by replay time, breaking determinism; use a version reference instead.
  • A3 changes (log not reliably durable): the truth itself can be lost, defeating the scheme; the log is the one structure that must survive.
Design notes and rejected alternatives

The rejected approach is to keep only the complex current state, which a crash can corrupt beyond repair. The log is easy to make durable and to validate, and every other structure can be rebuilt from it; the current state becomes, in effect, a hint derived from the log.

Connections

LFS (10/27): the log is the file system; the current state (inode map, data) is rebuilt from the log at recovery, exactly "the current state is like a hint" (inference; outline lists this). F2FS (11/5): a log-structured file system for flash with the same log-is-truth structure (inference). Rethink the Sync (10/29): xsyncfs uses ext3's journal (journaled mode) to order and recover updates (inference). Salus (11/17): a transactional log underlies replicated storage, the layered reuse of the log idea (inference).

M26 · Make actions atomic or restartable

TL;DR
ProblemA failure in the middle of a multi-step action leaves intermediate states recovery would have to understand.
MechanismMake actions atomic ("one that either completes or has no effect") with a log and a commit record; make log entries restartable so recovery can re-apply them.
Trade-offLogging and bookkeeping in exchange for recovery that never sees intermediate states.
Breaks whenFull atomicity is too expensive and a weaker, cheaper method (Grapevine: "Each update message is time-stamped, and the latest one wins") suffices.
Key points
  • The scheme: "assign a unique identifier to each atomic action and use it to label all the log entries associated with that action. A commit record for the action tells whether it is in progress, committed ... or aborted ... An action cannot be committed unless there are log entries for all of its updates. After a failure, recovery applies the log entries for each committed action and undoes the updates for each aborted action."
  • Restartable entries: "a log entry usually needs to be restartable ... it can be partially executed any number of times before a complete execution, without changing the result; sometimes such an action is called 'idempotent'." "storing a set of values into a set of variables is a restartable action; incrementing a variable by one is not."
  • The Alto file system "in effect uses the disk labels and leader pages as a log and rebuilds its other data structures from these"; "only the file allocation and directory actions that are atomic". The Juniper file system "goes much further, allowing each client to make an arbitrary set of updates as a single atomic action", using "shadow pages", moving data pages into files "simply by changing the pointers to them in the B-tree".
  • A weaker, cheaper method, Grapevine: a replicated database updated "at one site and propagated to other sites using the mail system", so updates "eventually arrive" though the order "may vary greatly". "Each update message is time-stamped, and the latest one wins." Sites may disagree during propagation, but "Such occasional disagreements and delays are not very important to the usefulness of this particular system."
How it works, step by step: a transfer made atomic (the paper's scheme)
  1. Log the updates: action T1 moves 30 from account A (balance 100) to account B (balance 0) (illustrative). Append [T1, store A := 70] and [T1, store B := 30], labeled with T1's identifier.
  2. Commit: once all of T1's update entries are in the log, append [T1, commit]. This record is the moment T1 logically happens.
  3. Crash before commit: recovery sees T1 (or T2) in progress with no commit record and undoes any of its updates that reached the data, leaving A = 100 and B = 0.
  4. Crash after commit: recovery re-applies T1's entries. Because each stores a value rather than incrementing, applying one twice is harmless, so a partial earlier application does not matter.
  5. The weaker option: if the application tolerates temporary disagreement, Grapevine's rule ("Each update message is time-stamped, and the latest one wins") avoids the commit machinery entirely and still converges once all updates arrive.
Assumptions it relies on
  • A1. Updates can be logged with a commit record on stable storage (stated; builds on M25).
  • A2. Log entries can be made restartable (stated; store, do not increment).
  • A3. The application needs true atomicity (implicit; else a weaker method is cheaper).
If an assumption changes
  • A1 changes (no durable log): there is no commit record to decide on, so atomicity cannot be guaranteed across crashes.
  • A2 changes (entries not restartable): a crash during recovery makes recovery run again, so an entry like "add 30 to B" can be applied twice (B = 60), corrupting the state (illustrative); entries must store values or be otherwise idempotent.
  • A3 changes (temporary disagreement is fine): use the cheaper Grapevine method and skip commit records; the paper offers this explicitly.
Design notes and rejected alternatives

The paper argues atomic actions "are not nearly as hard as their public image suggests" but "not trivial"; the commit record is the one entry whose state decides whether the action happened (this guide's phrasing of "A commit record for the action tells whether it is in progress, committed ... or aborted"). Shadow pages (Juniper, "first used in the Cal system") make applying a large update cheap: data pages already written to the log become file pages by changing the pointers to them in the B-tree, with no copying. And "Sometimes a weaker but cheaper method will do": Grapevine.

Connections

NFS (10/22): idempotent requests are M26's restartability applied to a stateless protocol: a retried write with an explicit offset has the same effect as the original, so a lost reply is harmless (inference; outline lists this). LFS (10/27) and F2FS (11/5): checkpoints plus roll-forward are the commit-and-redo scheme; LFS keeps two checkpoint regions with the time in the last block, F2FS a checkpoint pack with a version number, so a crash during a checkpoint is survived (inference). Rethink the Sync (10/29) and Salus (11/17): both concern when an action's effects may become visible, the atomic-and-durable boundary (inference).

L · Stated limitations and what the essay does not cover

What the paper itself says is limited
  • The disclaimer: "These are not novel (with a few exceptions)", nor "foolproof recipes", nor "laws of system design or operation", nor "precisely formulated", "consistent", "always appropriate", "approved by all the leading experts", or "guaranteed to work" (the paper's list, one item per line).
  • Named tensions the paper does not resolve: keep secrets versus don't hide power ("the right balance remains an art"); more assumptions for speed versus modularity; static versus dynamic analysis.
  • End-to-end "requires a cheap test for success" and "can lead to working systems with severe performance defects that may not appear until ... heavy load."
  • The Dorado memory system, built on "extensive prior experience (30 years!)": "it seems in retrospect that the high I/O bandwidth is not worth the cost".
  • Paging beat segmentation, and "The reasons for this are complex and have not been systematically studied."
  • Research aimed at better implementations is exempt from the caution against complex interfaces, "but ... others mustn't depend on its success."
  • The conclusion's own verdict: "Such a collection of good advice and anecdotes is rather tiresome to read; perhaps it is best taken in small doses at bedtime", and Lampson has "ignored most of these rules at least once, and nearly always regretted it."
What the essay does not cover (this guide's list)
  • No benchmarks, no controlled comparison: every claim is an anecdote from one or two systems, chosen by the author.
  • Selection bias: the examples are mostly systems Lampson built or liked; failures of the hints themselves are not catalogued.
  • No guidance on which hint wins when two conflict (the disclaimer says they are not "consistent" but does not say how to choose).
  • Concurrency and distribution appear only through specific examples (monitors, Grapevine, the Arpanet); there is no general treatment.
  • Security appears only incidentally (the Tenex bug, the Spy's checks); it is not a theme.
  • The numbers are era-bound (disk-speed assumptions, "hardware is cheap"), and some hints (safety first, brute force) rest explicitly on that economics.

Follow the numbers

Worked examples

Eight calculations from the paper's own numbers. Where the paper gives only a figure of merit, the arithmetic is labeled as this guide's; illustrative inputs are labeled too.

① The compounding of cost: why six layers miss by ten

Paper: "If there are six levels of abstraction, and each costs 50% more than is 'reasonable', the service delivered at the top will miss by more than a factor of 10."

  1. Per layer: each multiplies the cost by 1.5.
  2. Six layers: 1.56 = 1.5 × 1.5 × 1.5 × 1.5 × 1.5 × 1.5 = 11.39.
  3. So the top costs about 11.4 times the reasonable minimum, "more than a factor of 10", as claimed (this guide's arithmetic).
  4. Flip it: to stay under 10x over six layers, each layer must cost at most 101/6 = 1.47 times reasonable, so even a 50% overrun per layer is too much. This is why the hint asks for "the minimum essentials", not merely reasonable ones.
🍯
Cost multiplies through layers, so a tolerable-looking overrun per layer is intolerable in the whole. Predictable, minimal per-layer cost is the only defense.

② The Tenex password trick: 512 tries instead of 1016

Paper: the trick "finds a password of length n in 64n tries on the average, rather than 128n/2 (Tenex uses 7 bit characters in strings)." Exponent restored from the page image.

  1. Alphabet: 7-bit characters give 27 = 128 possible values per position.
  2. Brute force: guessing a whole n-character password blind averages 128n/2 tries. For n = 8: 1288/2 = 256/2 = 255 ≈ 3.6 × 1016.
  3. The trick: place the first unknown character at the last byte of a page whose next page is unassigned, and try each value. A wrong value returns BadPassword; the right value makes CONNECT read into the unassigned page, reported to the attacker. So each position costs at most 128 tries, 64 on average.
  4. Total: 64 × n positions. For n = 8: 64 × 8 = 512 tries. That is about 7 × 1013 times fewer than brute force.
💡
The speedup comes from turning one n-character secret into n independent one-character secrets: the page-fault report leaks whether each character matched, so the search is linear in n, not exponential. The flaw is the interaction of three "innocent-looking" features, not any one.

③ Pilot's extra disk access: how much slower a page fault gets

Paper: the Alto page fault is "one disk access"; Pilot "often incurs two disk accesses to handle a page fault and cannot run the disk at full speed."

  1. Alto: 1 disk access per fault; the map is in dedicated real memory (M14), so lookup is "a small fraction of the disk access time".
  2. Pilot, map not resident: 2 disk accesses (map page, then data page).
  3. Ratio: when the map misses, a Pilot fault costs about 2x the disk time of an Alto fault, since disk time dominates. The paper does not give a frequency for "often", so the average lies between 1x and 2x (inference).
  4. Code size: 11,000 lines versus 900 + 500 = 1,400, about 8x more code for the more general interface (this guide's ratio).
🍯
The generality (files mapped into virtual memory) costs both a second disk access in the common fault and 8x the code, the concrete price behind "the extra functionality is bought at a high price."

④ The Dover printer: two buffers instead of 14 million bits

Paper: the page is 3300 x 4200 bits, "fourteen million bits", cut into "16 x 4200 bit slices called bands" with "two one-band buffers".

  1. Full page: 3300 × 4200 = 13,860,000 bits (the paper's "fourteen million").
  2. Bands: 3300 / 16 = 206.25, so about 207 bands per page (this guide's arithmetic).
  3. One band: 16 × 4200 = 67,200 bits.
  4. Two buffers: 2 × 67,200 = 134,400 bits, which is 134,400 / 13,860,000 = 0.97%, about 1/103 of the full page.
  5. Why two and not one: one is played out to the printer while the other is filled, so the buffers swap each band; the paper says the printer "consumes bits faster than the available disks can deliver them", so the next band must already be in a buffer.
💡
Divide and conquer shrinks the working memory by about 100x; the spill rule (objects added to the next band's bucket) is what makes the division valid at the boundaries.

⑤ When dynamic translation pays: the break-even call count

Paper: "the cache must be large enough that on the average a procedure is executed at least n times, where n is the ratio of translation time to execution time for the untranslated code." Numbers below are illustrative.

  1. Costs (illustrative): translate a procedure once = 50 us; interpret untranslated = 5 us per call; run translated = 1 us per call.
  2. Paper's rule: n = translation / untranslated execution = 50 / 5 = 10 calls.
  3. Exact break-even: translating saves (5 − 1) = 4 us per call, so it repays after 50 / 4 = 12.5, about 13 calls (this guide's arithmetic; slightly more than the paper's simpler rule because the rule ignores the 1 us run cost of translated code).
  4. Cache implication: the cache must hold translated code long enough that each procedure averages at least that many calls before eviction; otherwise it retranslates and loses.
🍯
The paper's n = (translation / untranslated run) is a lower bound on the true break-even (12.5 calls here, against n = 10), because it ignores the running time of the translated code: reaching n calls is necessary but not quite sufficient. Both say a procedure must be hot enough to repay its one-time translation.

⑥ The sum cache: constant-time update instead of O(n)

Paper: x is "an array of 1000 numbers", f the sum, ∆ "a pair [i, v]", and "g(x, [i, v], sum) is sum - xi + v."

  1. Cached: sum of 1000 numbers = 5000 (illustrative value).
  2. Change: element 7 was 12, set to 20, so ∆ = [7, 20].
  3. Recompute from scratch: add 1000 numbers again, 999 additions, O(n).
  4. Incremental: g = 5000 − 12 + 20 = 5008, two operations, O(1). For n = 1000 that is about 500x fewer operations (this guide's arithmetic).
💡
A cache pays only when an update equation g exists that is much cheaper than f. Where none does (the line-break cache in Bravo), the entry must be invalidated and recomputed instead.

⑦ Why two-thirds: the waiting time at each load

Paper: "A system cannot be expected to function well if the demand for any resource exceeds two-thirds of the capacity." The queueing model is general knowledge, not in the paper.

  1. Model: average time in system ÷ service time = 1 / (1 − ρ) for the simplest M/M/1 queue (general knowledge).
  2. At ρ = 1/2: 1 / 0.5 = 2 service times.
  3. At ρ = 2/3: 1 / (1/3) = 3 service times, still modest.
  4. At ρ = 0.9: 1 / 0.1 = 10; at ρ = 0.95: 20; at ρ = 0.99: 100.
  5. So the two-thirds point (3 service times) is the last place where waiting is small; past it the curve bends sharply, which is why the rule puts the ceiling there (this guide's reconstruction of the paper's rule of thumb).
🍯
The 33% of capacity left unused is the price of staying on the flat part of the curve, far cheaper than the service collapse past the knee, because "hardware is cheap and getting cheaper".

⑧ The end-to-end copy: expected rework from one check

Paper: at Cambridge "an entire disk pack of 58 MBytes" is copied "with only an end-to-end check" in "20 minutes", and "very seldom needs to be repeated."

  1. One transfer: 20 minutes, then one checksum compare.
  2. Rework (illustrative failure rate 1 in 100): expected extra time = 0.01 × 20 = 0.2 minutes per copy on average.
  3. With per-hop checks: a failure would redo only one hop, not the whole 20 minutes, but the end check is still required, so per-hop checks can save at most part of that 0.2 minutes of expected rework.
  4. Conclusion: at this error rate the intermediate checks buy almost nothing; they pay off only when errors are frequent enough that redoing the whole transfer is costly, exactly the paper's "strictly a question of performance" (this guide's arithmetic on the paper's numbers).
💡
The end check is mandatory for correctness and cheap; the per-hop checks are optional and justified only by the expected rework they save, which is tiny when errors are rare.

Problem 1 · easy

Which of these log entries are restartable in the paper's sense: (a) store balance := 150; (b) add 50 to balance; (c) set bit 7 of the free map to 0; (d) append record R to the end of list L; (e) store the pair (x := 3, y := 4)?

Problem 6 · medium
Bravo's cache holds four lines with [firstChar .. lastCharUsed] = [0 .. 40], [40 .. 82], [82 .. 121], [121 .. 160] (illustrative). Character 82 is the first character of line 3. An edit changes only character 82. Which entries are invalidated?
Show answer
Lines 2 and 3. Line 3 displays character 82, and line 2 examined it (its lastCharUsed is 82) to decide where to break. The rule is that an edit to characters i through j "invalidates any cache entry for which [firstChar .. lastCharUsed] intersects [i .. j]": [40 .. 82] and [82 .. 121] both contain 82. Problem 7 · medium

Problem 8 · medium
Smalltalk's call-site hint hits about 96% of the time. Suppose (illustrative costs) a direct call costs 1 unit, the type check is free when it succeeds, and a full LookupAndCall costs 20 units more. What is the average cost per call with the hint, without it, and with the hint at a 50% hit rate?

Problem 9 · medium

One. End check only: expected 20 / (1 − 0.5) = 40 minutes. Per-hop: each stage fails with q where (1 − q)4 = 0.5, so q ≈ 0.159; each stage takes 5 / (1 − q) ≈ 5.95 minutes on average, about 23.8 minutes in total (this guide's arithmetic). They do not remove the end check: bits can still be "clobbered while sitting in memory" between checks. The saving is pure performance, exactly as the paper says, and at Cambridge's error rate it would be near zero.Misconception: that per-hop checks make the end check redundant. They are "not sufficient" and "not necessary" for correctness; they only reduce the work repeated when errors are frequent.
Problem 12 · hard
A Bravo log entry is ChangeProperties([v7, 10, 50], leftMargin := leftMargin + 10). Does it meet the log requirements of "Log updates" (functional, value arguments)? Is it restartable in the sense of "Make actions atomic"? What does recovery have to do differently from a store-only log?
Show answer
It meets the log requirements: a FormattingOp is "a function from properties to properties", and the Interval names an immutable version, v7, so replaying it on v7 always produces the same v8. It is not restartable against the current state: applied to a document that already has the change, it adds another 10. So recovery must replay from a known version (the version reference in the entry tells it which), rather than blindly re-applying entries to whatever state the crash left. A store-only entry (leftMargin := 30) could be applied to the current state; the paper says "Restartable log entries can be applied to the current state of the object; there is no need to recover an old state."Misconception: that "functional" and "restartable" mean the same thing. Functional means the same input version gives the same output; restartable means repeating it on its own output changes nothing.
Connecting outward

What Hints teaches a memory and storage systems person

These connections are this guide's framing, not claims Lampson makes. Facts about later systems are general knowledge, not in the paper.

A label per block is a truth you can rebuild everything from

The Alto stored, in every sector's label, which file and page the sector belonged to, and treated the directory, the page maps and the free bit table as hints checked against those labels (M18). Flash translation layers do the same thing with the spare area of each flash page: it records the logical address the page holds, so the logical-to-physical map in DRAM can be lost and rebuilt by a scan. The design question is the same in both: what is the smallest per-block record that makes every other structure a hint, and can the device check it during the transfer at no extra cost, as the Alto controller did?

Cost is part of the interface, and devices with asymmetric costs make that explicit

The paper's interface includes "a reasonable cost", undocumented and compounding across layers (M1). Memory and storage tiers whose reads and writes cost very differently (flash, phase-change and other non-volatile memories) put this to the test: an interface that presents them as uniform pages hides a desirable property (cheap reads) together with an undesirable one (slow, wearing writes). "Don't hide power" (M4) and "keep secrets" (M10) pull in opposite directions here, and the paper's answer, two levels such as the Alto's page and stream interfaces, is one concrete way to expose the asymmetry without freezing the device's internals.

The mattress is a reserve for reclamation

The paper's worst case is freeing memory when freeing itself needs memory (M13): keep a bounded reserve and free one item at a time. Operating systems keep reserves of free pages that only the reclaim path may use, and SSDs keep spare blocks so garbage collection always has a destination for the valid pages it moves. In each case the reserve's size follows the paper's rule: bound the resources needed to free one item, and the reserve is a fixed cost of multiplexing.

Two-thirds is an over-provisioning rule

"A system cannot be expected to function well if the demand for any resource exceeds two-thirds of the capacity" (M22). Write buffers, flash garbage collection and memory overcommit all fall off the same queueing cliff: the closer utilization gets to 100%, the more each new request waits behind work the system must do to make room. SSD spare area, the FFS free-space reserve, and admission control in vLLM are the same choice the paper describes: spend cheap capacity to stay on the flat part of the curve, rather than optimize allocation near full.

Logs must be restartable because recovery can crash

The paper's log entries are calls of functional procedures with value arguments (M25), and they must be restartable, store not increment, so recovery can be run again after a crash in the middle of recovery (M26). Persistent-memory logging, journaling file systems, and the checkpoint schemes of LFS and F2FS rely on the same property. The paper's distinction is worth keeping exact: a functional entry replays correctly from a known version; only a restartable entry can be applied to whatever state the crash left.

Never put the map that locates pages in the memory it maps

Pilot kept its file-to-disk map in virtual memory and paid "often ... two disk accesses" per fault; Interlisp-D dedicated real memory to the map and paid one (M1, M14). Many systems since keep the structures that locate pages out of the paged pool: Linux, for example, never swaps out page tables, and SSD controllers hold their mapping tables, or the hot part of them, in dedicated DRAM. The paper's condition for the dedicated split is the one to check in a new design: unless the device is "ridiculously fragmented", the map is smaller than the code it would take to avoid the circularity.

Questions with real answers

Each one is a tricky case the paper does not spell out, but it has a definite answer you can work through from the paper's own examples and rules, with any general knowledge labeled. The quoted block is how to ask it in class. Try your own answer before opening the worked one.

C1 · Why must the Tenex page be unassigned, not just paged out?

The Tenex trick puts the guessed character at the end of a page whose next page is unassigned. Why does it need an unassigned page rather than one that is merely not in memory? And what is the smallest change to CONNECT that closes the leak while keeping all four features: user-visible traps, system calls as extended instructions, arguments by reference, and the three-second delay?

AnswerWork it out first, then open▾

A page that is assigned but not resident is brought in by ordinary demand paging inside the system, invisibly to the program, and the call simply continues (general knowledge of demand paging). Only "a reference to an unassigned virtual page" is reported "by a trap to the user program", and because a system call is viewed as an extended instruction, the report happens even when CONNECT makes the reference. CONNECT reads character i + 1 of the argument only if character i matched, so the report arrives exactly when the guess was right.

The fix is to make the argument references independent of the password: touch, or copy into system memory, the whole argument before the first comparison. Then any unassigned-page report happens whatever the guess, and the four features stay. Comparing all characters without an early exit also works. The paper's diagnosis points at this: the interface of a memory reference in system code includes "the possibility that an improper reference will be reported to the client without any chance for the system code to get control first." Copying arguments in before using them is standard practice in later kernels (general knowledge).

Where the answer comes from: The feature list and the CONNECT loop in Section 2.1; the paging behavior and the fixes are general knowledge and inference.

C2 · Four bits that count to seven

For reference counts that overflow, the paper proposes an overflow count table and says "even with as few as four bits there is room to count up to seven, and the overflow table is touched only in the rare case that the count swings by more than four." Four bits can hold 15. Where did the rest go, what is one unit in the overflow table worth, and what is the trace for an object that gains 9 references and then loses all of them?

AnswerWork it out first, then open▾

The numbers fit if one of the four bits is the overflow flag that the paper says is "set in the object", leaving three bits for the count, 0 to 7 (this guide's inference; the paper does not say which bits). "When the count reaches its limit it is reduced by half, the overflow count is increased by one": an increment from 7 would make 8, so the count becomes 4 and the object's entry in the hash table goes up by one. One table unit is worth 4 references, and the true count is count + 4 × overflow.

Trace: references 1 to 7 count normally. The 8th: count 8 becomes 4, overflow 1, flag set (4 + 4 = 8). The 9th: count 5 (5 + 4 = 9). Removals: 4, 3, 2, 1, 0; at zero with the flag set "the process is reversed": count back to 4, overflow 0, flag cleared (total 4). Four more removals reach 0 and the object is free. Between table touches the count must move 4 steps from its reset value of 4, up to 8 or down to 0, which is the paper's "swings by more than four"; the paper's wording is approximate at the boundary.

Where the answer comes from: Section 2.5's description of the overflow count table; the bit split is this guide's inference, and the trace is arithmetic on the stated rule.

C3 · A crash between the label and the bit table

The Alto free-page bit table is a hint; the truth is a special value in each free page's label. Suppose a crash happens after page 500's label was rewritten to say file 7, page 3, but before the bit table was updated, so the table still says page 500 is free. What happens the next time the allocator picks page 500? And in the opposite case, where the table says allocated but the label says free?

AnswerWork it out first, then open▾

The allocator checks the label "when the page is allocated and before the label is overwritten with a file identifier and page number". It finds file 7's identifier instead of the free value, so the hint was wrong: it does not write, it corrects the bit, and it takes another page. File 7's data is never touched.

In the opposite case no check ever fires, because the allocator never picks a page the table calls allocated. The page is simply lost to allocation until the bit table is rebuilt from the labels, which the paper says is always possible ("all of it can be reconstructed by scanning the disk"). So a hint that is wrong in the dangerous direction is caught by the check, and one wrong in the safe direction costs only space. Ordering the two writes so the table says allocated whenever the label does (set the bit before writing a file label; clear it only after writing the free value) makes every crash leave the safe kind of error (inference).

Where the answer comes from: Section 3, "Use hints", on the Alto and Pilot file systems; the write-ordering remark is this guide's inference.

C4 · A call site that alternates between two types

Smalltalk's call-site hint hits about 96% of the time. Exactly what happens on a miss, and who rewrites lastType and lastProc? What is the hit rate at a call site that sees Circle, Square, Circle, Square, and is a miss ever unsafe?

AnswerWork it out first, then open▾

The call site pushes format, x and lastType and calls lastProc. The called procedure, say Circle's Print, pops lastT and x and compares the type of x with lastT. If they differ it calls LookupAndCall(x, "Print"), which finds Square's Print and calls it, and "LookupAndCall should store the type of x and the code address it finds back into the lastType and lastProc fields."

With alternating types, every call finds the fields set by the previous call for the other type: every call misses, does the full lookup and rewrites the fields, so the hit rate is 0%. It is never unsafe, because the type test runs before the body; a wrong hint costs only time. The 96% depends on the observation that "usually the type of x is the same as it was last time." Later language implementations keep several (type, procedure) pairs per call site for this case, called polymorphic inline caches (general knowledge, not in the paper).

Where the answer comes from: Section 3, "Use hints", the Smalltalk example; the alternating case is worked from the stated code.

C5 · What the label check does not prove

In Section 4 the paper says the Alto's label check before a write "ensures that the disk address for the write is correct", so any other precaution about addresses is for performance only. If a bit in the data buffer is flipped in memory before the write, does the label check catch it? What end-to-end claim is the paper actually making here?

AnswerWork it out first, then open▾

No. The label holds the file identifier and page number; checking it verifies where the data goes, not what the data is. A corrupted buffer is written to the right page and passes the check.

The claim is limited to the file system's own invariant, that no page is overwritten by the wrong file: precautions about the address "do not affect the reliability of the file system." For the user's data, the end is the application, and the paper's own file-transfer example says to read the copy back and compare checksums, because bits "might be clobbered while sitting in memory". So the label check is the end-to-end check for the file system's structure and only an intermediate check for the contents.

Where the answer comes from: Section 4, "End-to-end": the file-transfer example and the paragraph linking it to the Alto label check.

C6 · Grapevine with a slow clock

Grapevine propagates updates by mail, time-stamps each one, and "the latest one wins." At 10:00 real time, site X adds Alice to a distribution list; at 10:05 site Y removes her, but Y's clock is ten minutes slow. Once all the mail has arrived, is Alice on the list, and do all sites agree?

AnswerWork it out first, then open▾

X's add is stamped 10:00 and Y's remove 9:55. Every site applies the update with the larger stamp last, so every site ends with the add in force: Alice is on the list everywhere. The sites agree, as the paper promises ("After enough time has passed, all the sites will receive all the updates and will all agree"), but on the outcome that real-time order would reverse. The rule guarantees convergence, not real-time order; "latest" means largest time stamp.

One more consequence: a site that receives the remove first must remember its stamp, or the older add arriving later would be applied and the sites would diverge. Replicated stores of this kind keep a time-stamped record of deletions for this reason (general knowledge, not in the paper). The paper accepts such errors because "occasional disagreements and delays are not very important to the usefulness of this particular system."

Where the answer comes from: Section 4, the Grapevine paragraph; the clock-skew case is worked from the stated rule, and the deletion record is general knowledge.

C7 · How many disk scans does the Scavenger make?

When the Scavenger's table of contiguous runs does not fit in memory, it "discards the information for half the files and continues with the other half", rebuilds those, then repeats for the other files, subdividing further if needed. If the full table would need 3 times the available memory, and runs are spread evenly over files (illustrative), how many passes over the disk does it make? What is the minimum possible?

AnswerWork it out first, then open▾

Four. Reading it as recursive halving: halves need 1.5 times memory each (too big), quarters need 0.75 (fit), so four quarter-sized passes. Reading it as halving until the current set fits and then continuing with all the rest: pass 1 keeps 0.75 of the 3 units; pass 2 keeps 0.56 of the remaining 2.25; pass 3 keeps 0.84 of the remaining 1.69; pass 4 takes the last 0.84. Both readings give 4 (this guide's arithmetic).

No method can do fewer than 3, since each pass can hold at most one memory's worth of runs. Halving costs at most about twice the minimum. Each pass re-reads the labels of the whole disk, because the discarded information must be collected again (inference from "the process is repeated for the other files"); that is affordable because the Alto can scan the entire disk at disk speed (M4).

Where the answer comes from: Section 2.4, "Divide and conquer"; the pass counts are arithmetic on the stated halving rule.

C8 · Why does the size of Interlisp-D's map depend on fragmentation?

Interlisp-D stores "each virtual page on a dedicated disk page" and keeps the virtual-to-disk map in dedicated real memory, and the paper says "Unless the disk is ridiculously fragmented the space thus consumed is less than the space for the code to prevent circularity." If every virtual page has its own disk page, why would fragmentation change the map's size? What does that sentence tell you about how the map is stored?

AnswerWork it out first, then open▾

With one entry per virtual page, the map's size would be fixed by the size of the virtual address space, and fragmentation could not matter. The sentence makes sense only if the map records runs: one entry per range of consecutive virtual pages that sits on consecutive disk pages, the same common case Pilot's B-tree exploits ("consecutive file pages occupy consecutive disk pages"). This is this guide's inference; the paper does not describe the map's format.

Then the map's size grows with the number of runs: a few entries when the backing pages are contiguous, up to one entry per page when the disk is "ridiculously fragmented". With 32,768 virtual pages and 4-byte entries (illustrative), that is a few bytes in the good case and 128 KB in the worst, which is when dedicating real memory stops being cheaper than code that avoids circularity.

Where the answer comes from: Section 3, "Split resources", read against the Pilot B-tree in "Use hints"; the run-length reading and the sizes are inference and illustration.

Glossary, numbers, and provenance

Every term in one place, then the paper's few hard numbers, where everything in this guide came from, and what it found inconsistent in the paper and in the companion outline.

Core terms
InterfaceThe boundary between an implementation and its clients, defined by the paper (after Britton et al.) as the set of assumptions each side's programmer must make about the other to show their own program correct; it includes an undocumented expectation of reasonable cost.
AbstractionA simplified model of a resource or service (a file, a virtual page, a monitor) that clients program against without seeing how it is built; the paper says its purpose is "to conceal undesirable properties".
ClientA program or higher layer that uses an interface and depends on both its function and its cost.
SecretAn assumption about an implementation that clients are not allowed to make, and which the implementer is therefore free to change.
CacheAn associative store of saved results [f, x, f(x)], looked up by f and x, that is kept correct: when f is not functional, an entry is updated or invalidated whenever f(x) changes.
HintA saved result of a computation that may be wrong and need not be found by associative lookup; because it may be wrong, it is checked against the truth before any action that cannot be undone.
The truthThe information a system keeps strictly correct, in a form chosen for checking and reconstruction rather than speed (on the Alto, the label of every sector and each file's leader page).
Label (Alto sector label)A small field stored with each disk sector, separate from its data, holding the identifier of the file that owns the page and the page's number in that file (or a special free value); the controller can compare it with an expected value during the transfer.
Leader pagePage zero of every Alto and Pilot file, holding among other things the file's string name and the directory it is in.
LogAn append-only sequence of records of updates on stable storage; in the paper each record is the name of a functional update procedure plus value arguments, so replaying the log reproduces the object.
Object versionOne immutable state of a mutable object, named by the pair [object identifier, number of updates] and reconstructed by replaying that many log entries.
Atomic action (transaction)An action that either completes or has no effect, so recovery never has to deal with its intermediate states.
Commit recordThe log entry, labeled with an atomic action's unique identifier, that says whether the action is in progress, committed or aborted; its change of state is itself logged.
Restartable (idempotent) actionAn action that can be partly executed any number of times before a complete execution without changing the result, such as storing values; incrementing is not restartable.
Shadow pagesA technique in which new data pages are written elsewhere and then made part of the file by changing the pointers to them in the file's map, so a large update becomes visible in one step without copying.
End-to-end checkA test of success made by the application at the two ends of an operation (for a file copy, comparing checksums of the source and the copy read back), which covers every intermediate step at once.
Load sheddingDeliberately refusing or discarding some demand (users, jobs, packets) so that the demand accepted gets adequate service.
ThrashingThe state of a paging system whose active jobs need more memory than exists, so it spends nearly all its time waiting for the disk.
Mattress reserveA fixed amount of a resource held back for the worst case, sized by the most it can take to free one item, and used to free one item at a time when the normal cushion is gone.
Piece tableBravo's representation of a document: an array of pieces, each a file address and a length pointing at an unchanging string of characters, so edits split pieces instead of modifying text.
BandOn the Dover printer, a slice of the page bitmap 16 rows by 4200 bits, the unit in which the page is scan-converted into one of two band buffers.
Dynamic translationConverting a convenient representation (such as compact bytecodes) into one that runs fast, on demand, and caching the result so the translation is paid once per cached unit.
Overflow count tableA hash table keyed on object address that holds the high part of reference counts too large for their field in the object; it is touched only when a count crosses its limit or returns to zero with the overflow flag set.
Register stackSeveral sets of processor registers arranged as a stack, one set per active procedure call, so registers are saved to memory only after n successive calls without a return.
Compatibility packageCode that implements an old interface (for example an old system's supervisor calls) on top of a new system so old programs keep running.
World-swap debuggerA debugger that saves the target system's entire memory to secondary storage, runs in its place, and maps target addresses to the saved image, depending on nothing in the target but the swap mechanism.
