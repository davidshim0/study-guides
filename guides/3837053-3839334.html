Sealing the evidence where the attacker can't follow

An audit log is written by the very host an intruder is trying to own. This is the plain-English story of a position paper arguing the fix isn't a smarter host-side seal — it's moving the seal off the host entirely, onto the storage device itself.

📄 Chen, Wan & Zhao · "Print-Time Audit-Log Integrity Below the OS" · HotStorage'26 🎓 Some OS/storage basics assumed — primers cover them ⏱ ~25 min read
🔒

Bind each record to its kernel-stamped identity and SEAL it on the device, the instant it lands — not in host software's own time, after the attacker already has root.
Shrink the window, don't just hash it faster.

1What an audit log is, and why it's evidence▾

An audit log (e.g. Linux's auditd) records security-relevant events as they happen: who logged in, which process opened which file, which syscall ran. After an intrusion, it's the primary evidence base for figuring out what happened, who did it, and whether it's reportable under compliance.

That's exactly why it's a target: an intruder who reaches root doesn't just exploit the system, they typically also clean up after themselves by deleting or rewriting the log.

Now you're ready: this paper is about defending that one specific file against the one specific adversary who has every incentive, and the ability, to falsify it.
2"Host root" — what compromise actually grants▾

Gaining root (kernel-level control) on a host isn't just "can run more commands." It means the attacker now controls the CPU, all of memory, the filesystem, and the syscall path — including any process, key, or buffer that lives in host memory, no matter how privileged that process was a moment ago.

Any defense that keeps its signing key, its enclave, or its seal logic inside that same host is, at the moment of root compromise, inside the blast radius.

Now you're ready: the paper's whole argument is about which side of the host/device boundary a thing sits on — because that boundary is exactly what root compromise does and doesn't cross.
3Tamper-evident logging (hash chains)▾

Chain each new log record's hash to the previous record's hash (a Merkle-style structure). Afterwards, anyone can verify the chain and detect if a record was altered or removed — tampering becomes evident, even if not prevented in advance.

The catch: this only protects a record once it's in the chain. If sealing happens in batches (e.g. once an hour), a root adversary who strikes mid-batch can rewrite the buffer before it's ever hashed — and the eventual seal faithfully commits the falsified version.

Now you're ready: the paper isn't questioning hash chains — it's questioning where and when the chaining happens.
4TEEs / enclaves as a trust anchor▾

A TEE (like Intel SGX) runs code in hardware-isolated memory the host OS can't read or modify, even with root. Prior systems (CUSTOS, SGX-Log) put the log-sealing logic inside an enclave, shrinking the trusted base from "the whole OS" to "the enclave."

But the enclave is still scheduled by the host OS, and a record still has to cross untrusted host memory to reach it. The window between record creation and enclave ingestion remains host-controlled.

Now you're ready: this is the paper's closest prior art, and the gap it identifies — a host-resident anchor, however well-isolated — is precisely what motivates going one layer further, to the device.
5Trusted Computing Base (TCB) — why smaller is safer▾

The TCB is everything a security guarantee depends on being correct. A guarantee resting on "the entire host OS, every driver, every service" is only as strong as the weakest of all of those. Shrink the TCB to a small, dedicated, independently-administered component, and there's simply less surface for an adversary to subvert.

This is the move this paper makes explicit: relocate the TCB for log integrity from the host OS to the storage device's firmware.

Now you're ready: every design choice in this paper (device-held keys, device-only append) is in service of shrinking that one number — what must be trusted for the forensic record to survive.
6Computational storage and DPUs▾

Modern storage isn't just a dumb block device anymore. A SmartSSD can embed an FPGA or Arm core beside the flash; a DPU sits on the PCIe/network path with its own CPU, memory, and OS, physically separate from the host. Both already run isolated firmware and offload tasks like compression or encryption for performance; select devices additionally expose persistent, host-inaccessible private key state.

The paper assumes, for devices like these, that this isolation holds end to end — the host reaching the device only through its I/O interface, with no host-controllable path into firmware or key store. That's an assumption to be verified by attestation, not a property the paper claims every shipping SmartSSD or DPU already guarantees.

Now you're ready: the paper's core move is to reuse this existing, performance-motivated hardware boundary for a security purpose — forensic integrity — instead of building new hardware.
7Kernel-stamped identity vs. app-supplied claims▾

Linux's audit subsystem stamps certain fields on a record independently of the application — auid (login UID), uid, session ID, syscall number. These come from the kernel, not from whatever the logging application chooses to say about itself.

An application can also attach its own attribution (e.g. "this action was performed by user X"). That claim might be forged; the kernel-stamped fields, stamped before the record ever reaches the device, are much harder for a later compromise to retroactively rewrite.

Now you're ready: this is the whole trick that lets a device — which only ever sees raw bytes — still say something meaningful about "who did this": it checks the app's story against the kernel's stamp, not against the real world.
8Sequence numbers and append-only gap detection▾

Give every record a strictly increasing sequence number. An append-only receiver that has seen numbers 1, 2, 4 knows immediately that 3 is missing — the gap is visible the instant a later record arrives, without needing to inspect contents.

This doesn't stop an adversary from never sending record 3 in the first place (silent suppression) — for that you need an independent heartbeat or a maximum-silence policy.

Now you're ready: this is exactly the mechanism behind "sequence continuity," one of the three guarantees the device provides — and exactly why the paper is careful to list what it does not guarantee.
The whole story in one place

Print-time integrity in a nutshell

The problem, the proposed fix, and how its pieces fit together.

Every audit-log defense to date — plain files, tamper-evident hash chains, even TEE-backed enclaves — seals a record after it has already lived, mutable, inside the host it's meant to indict. Formally, if t_emit, t_submit, and t_seal mark when a record is produced, crosses the device boundary, and becomes immutable, the race window is W = t_seal − t_emit = W_submit + W_device. A decade of defenses has shrunk that window; none has closed it — each still leaves some residual gap before its own seal point, whether that's a batch flush, enclave ingestion, or (as with remote shipping) a network round-trip to a remote collector's acknowledgment.

The paper's position: move bind-and-seal onto the storage device or DPU itself — a trust domain a host-root compromise cannot enter. As each record crosses the I/O interface, the device reads the kernel-stamped identity already attached to it (login UID, session, syscall — stamped independent of the application), checks any app-supplied attribution against it, and appends the bound record to a device-resident, tamper-evident hash chain under a key the host never sees. A compromised host can still stop future logging, but it can no longer retroactively alter, delete, or reattribute anything already acknowledged.

Because they were targeting a real SmartSSD/DPU prototype rather than a new storage stack, the authors are explicit that this is a position + research agenda (HotStorage'26, 7 pages) — three essential assumptions (device isolation, pre-crossing stamping, attested firmware), three guarantees the device provides (immutability, delivered-provenance binding, sequence continuity), and five open research questions (RQ1–RQ5) about the interface, the minimal check's real strength, line-rate feasibility, key/attestation plumbing, and lifecycle/availability.

For a reader who thinks in terms of OS-managed tiers and CXL-attached memory/storage expanders: this is a similar move of pushing a trust boundary into hardware (the paper itself talks about computational storage and DPUs, not CXL — the comparison is this guide's, not the paper's) — except here the payload crossing the boundary is forensic identity, not a cache line or a page, and the property being bought is non-rewritability, not latency.

🔑 Key takeaways

  • The race window W = W_submit + W_device exists in every prior defense as the gap before its own seal point — a batch flush, enclave ingestion, or remote ack — not only when the seal itself is host-resident software.
  • Faster host-side signing lowers latency, not trust — the key and the record still touch host memory a root adversary controls.
  • The fix: bind each record to its kernel-stamped identity and seal it in a device-resident hash chain, under a device-held key, past the host's last point of control.
  • Guarantees are precise: immutability, delivered-provenance binding, sequence continuity — and explicitly not truth, availability, or stopping a consistent lie.
  • This is a position paper: three assumptions, three guarantees, five research questions (RQ1–RQ5) — no built system, no benchmark numbers yet.
  • Feasible now because computational storage (SmartSSDs, DPUs) already ships isolated firmware for performance; the paper additionally assumes (and leans on attestation for) a host-inaccessible key store, which it doesn't claim every such device already provides.
Seven everyday pictures

How to think about print-time sealing

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core problem · Whose machine, whose evidence

The getaway car with the dashcam

The dashcam that would record the crime is bolted inside the very car the thief is stealing. Of course it's the first thing disabled. An audit log produced by the host being attacked has the same structural flaw: the evidence of the break-in lives inside the thing being broken into, available to whoever just broke in.

Where it breaks: a real dashcam can't fight back once unplugged. The device-side seal can — it can keep running even after the "car" (host) is fully compromised, because it isn't bolted to the same chassis.
Why "seal faster" isn't enough · Timing vs. trust

Notarizing after the photocopy

A notary who stamps a document is only meaningful if the document hasn't already been swapped. Signing every record inline on the host, right before the write, feels like a fix — but the record and the signing key both still sat in a room (host memory) the forger controls. A faster notary doesn't help if the forger photocopies and swaps the page first.

Where it breaks: a notary can't verify the document's content is honest, only that it wasn't altered after stamping. Same here — device sealing stops post-ack rewriting, not a lie that was consistent from the start (§3, non-guarantees).
The trust domain · Device isolation

A hotel safe the front desk can't open

You can put things in the in-room safe, and the front desk can even see a light indicating it's locked — but they have no master key and no mechanism to open it themselves. A storage device's private signing key is the same: the host can submit records to it through the I/O interface, but has no path to the key, the firmware, or the sealed chain itself.

Where it breaks: a real hotel safe can be drilled out by someone with physical access and enough time. The paper's guarantee assumes device isolation and attested firmware (§3) — it's a cryptographic/architectural boundary, not a literal physical one.
Append-only · WORM vs. device binding

A ballot box with a slot, not a hinge

You can post a ballot in; nobody — including the building owner — can reach back in and swap one out. A device-sealed hash chain works the same way after acknowledgment: records go in through the slot, the chain only grows, and nothing that's already inside can be edited or removed.

Where it breaks: a ballot box can't tell a fraudulent ballot from a real one — it just can't be tampered with after the fact. Likewise, the device can't verify a record's content is true, only that it wasn't altered post-ack; this is exactly why the paper distinguishes device sealing from plain WORM storage (§8).
The semantic gap · Checking the claim, not the world

The bouncer who checks your ID, not your story

A bouncer doesn't verify your life story — just that the name on your ID matches the name you gave. The device does the same: it can't reconstruct "what really happened" from raw bytes, but it can check the application's claimed attribution against the kernel-stamped identity that was already attached before the record crossed the interface, and flag a mismatch.

Where it breaks: a bouncer is fooled by a convincing fake ID. If an attacker's forged record keeps the host-claimed fields mutually consistent with the kernel stamp, the device accepts it — sealed, but not exposed as false (§3, §6 RQ2).
Sequence continuity · What a gap reveals

A numbered-ticket queue

A deli counter hands out numbered tickets. If ticket 3 is never called, everyone notices the moment number 4 shows up. A device watching strictly increasing sequence numbers detects a missing record the same way — the instant a later one arrives, no inspection of content required.

Where it breaks: the deli can't tell if ticket 3's customer simply left (host stopped logging silently) versus was skipped. That needs an independent signal — the paper's external heartbeat / maximum-silence policy, not the sequence counter alone.
Design boundary · Trust relocation, not elimination

Moving the vault, not removing it

You haven't eliminated the question "can I trust the bank?" by moving your valuables from a desk drawer to a vault — you've made it a smaller, more specific, more testable question: can I trust this vault's construction and operator? That's exactly the shift here: from "can I trust this host's log?" to "can I trust this device's firmware and supply chain?"

Where it breaks: a vault's steel doesn't update itself; device firmware does, on its own cadence. The paper leans on attestation to keep that promise measurable rather than assumed — a malicious manufacturer isn't ruled out, only made harder to substitute silently (§8–§9).
The full explanation

How it actually works

Section by section, with the paper's two diagrams rebuilt, and the precise guarantees spelled out.

1 · The race window, precisely

Define t_emit (record produced), t_submit (crosses the device boundary), t_seal (immutably committed). Then W = t_seal − t_emit = W_submit + W_device. W_submit covers host scheduling, daemon queues, and page-cache/I/O delay; W_device ends at the device's durable acknowledgment. A dedicated, back-pressured synchronous audit queue is required to bound W_submit — with asynchronous writeback, device sealing still protects whatever was already acknowledged, but host-side buffering stays part of W.

⚠
Why not just seal faster? Signing every record inline on the host, right before fsync, keeps the key and the record in host memory — a root adversary signs its own forgeries. Faster signing lowers latency, not trust; it doesn't change which side of the boundary the seal sits on.

2 · Threat model, assumptions, guarantees

The adversary gains host privilege (including kernel control) at some time and thereafter controls everything host-resident. Three assumptions delimit what the design rests on: (a) device isolation — reachable only through the I/O interface, no host path to firmware/key/state; (b) pre-crossing stamping — the kernel stamps identity fields before a record crosses the interface; (c) attested device — firmware is attested so a verifier can tell genuine from emulated.

Given those, the device provides three guarantees: (i) immutability — an acknowledged record can't be altered without reaching protected device state; (ii) delivered-provenance binding — each record is bound to the kernel-stamped identity delivered with it; (iii) sequence continuity — a missing earlier number becomes visible when a later one arrives.

∅
Equally important — the non-guarantees: the device cannot recover a record the host never sent (silent suppression needs an external heartbeat); host-generated sequence numbers alone don't prove every event was submitted if the kernel itself is compromised; and a forgery whose host-supplied fields are mutually consistent with the kernel-stamped ones is accepted — sealed, but not exposed as false.

3 · The bind-and-seal engine, on-device

As each record crosses the interface, the device performs two steps before acknowledging: bind — read the kernel-stamped identity fields (principal, login UID, session, syscall), seal them alongside the record, and flag a record whose app-supplied attribution contradicts the stamped one; seal — append the bound record to a device-resident, append-only hash chain under a key held only in the device, periodically publishing a signed root for external anchoring.

4 · Submission and recovery semantics

Each queue entry carries a monotonically increasing sequence number and a segment ID. The device acknowledges the highest contiguous sequence only once both the record and updated chain state are durable.

# on lost ack: retry, not ambiguous append
if retransmit matches prior record tuple:
    device returns the prior result     # idempotent
elif retransmit conflicts with prior tuple:
    device rejects the payload

# on a sequence gap
start bounded timer; export gap with next signed root

# on device reset
resume from last durable chain head
reject any record that would move sequence backward
💡
These rules give at-least-once transport with exactly-once incorporation into the sealed log — without asking the host to decide which writes survived a crash. A clean shutdown closes the current segment only after the queue drains.

5 · Where to place it, and coexisting with other offloads

A DPU is the primary first deployment — it can receive typed records before filesystem buffering and front unmodified drives. An in-SSD core or FPGA can later shorten W_device at the persistence path itself; a split design lets the DPU bind while the drive seals. The audit path should use a reserved queue, bounded device memory, and an independently scheduled sealing context — not borrowed, unbounded resources from compression, encryption, or tenant offloads. Backpressure begins before the reserved ring overflows, so overload is visible rather than silently dropping records; a high-assurance service can then fail closed, while a general service continues with a signed loss marker.

Follow the scenario, step by step

Worked examples

This is a position paper, not a benchmark report — so the "numbers" to trace are the paper's own timeline and its precise guarantee logic, walked through concretely.

① Why hourly sealing fails the 02:00 intruder

An intruder exploits a service at 02:00, gains root, and by 02:01 deletes the exploit's auditd records and rewrites the auth log to implicate a maintenance account. The host seals an hourly tamper-evident manifest.

  1. 02:00 — exploit lands. The relevant audit records are written to the host's log buffer, inside host memory.
  2. 02:01 — root achieved. The attacker now has full read/write over that buffer, since it hasn't been sealed yet (next seal isn't due until 03:00).
  3. The attacker edits the buffer: deletes the exploit records, rewrites the auth log entries to a different (innocent) account.
  4. 03:00 — the seal runs over whatever is in the buffer right now — which is the already-falsified version. The hash chain is computed faithfully over a lie.
  5. Conclusion: the cryptography didn't fail — it ran correctly, just too late. The entire interval 02:00→03:00 was inside W, and nothing protected the buffer during it.
🔑
Insight: shrinking the seal interval (e.g. sealing every minute instead of every hour) helps only asymptotically — as long as sealing runs in host software, there's always some interval during which a rooted host can edit before the next seal.

② Decomposing W, and why submission must be synchronous

W = W_submit + W_device. Why does bounding W_submit specifically require a synchronous, back-pressured queue, rather than just a fast asynchronous one?

  1. W_device ends cleanly at the device's durable acknowledgment — that part is bounded by design, regardless of queue discipline.
  2. W_submit covers everything before that: host scheduling, daemon queues, page-cache/I/O delay. With asynchronous writeback, a record can sit unsent in host memory indefinitely under load.
  3. During that unsent interval, the record is exactly as mutable as it was before this design existed — the device can't protect a record it hasn't received yet.
  4. A synchronous, back-pressured queue makes the logging task wait for the device's ack before completing, converting an unbounded, hidden delay into an explicit, measurable one — and applying backpressure before the queue overflows keeps unrelated I/O pressure from silently reopening the window.
  5. Conclusion: async writeback still protects whatever got acknowledged, but only synchronous submission makes the strongest, bounded version of the guarantee — the trade is submission latency, made visible, in exchange for a known W_submit.

③ Replaying the 02:00 attack under device sealing

Same intruder, same timeline, now with print-time integrity in place.

  1. 02:00 — exploit lands. Each audit record traverses the synchronous queue and is acknowledged by the device before the attacker has root (root is only achieved after the exploit completes).
  2. 02:01 — root achieved. The attacker tries to erase the records: it can delete its own host-side copy, but the device's sealed chain already holds the acknowledged originals, outside host reach.
  3. The attacker forges a new record blaming a maintenance account. The device checks the forged record's app-supplied attribution against the kernel-stamped identity fields delivered alongside that same forged record — it has no way to compare against the original event's already-sealed UID.
  4. Case A — fields don't match: the mismatch is flagged (not silently dropped) and sealed as a flagged record. Case B — the attacker keeps the fields mutually consistent: the forgery is accepted, but it's immutably placed after the already-anchored prior history — its position in the chain, not a trustworthy device-asserted timestamp, is what marks it as post-compromise.
  5. Either way, the investigator receives an immutable account of what the machine actually emitted — including the post-compromise forgery itself as evidence — rather than a history the attacker revised afterward.
💡
The shift in one line: "the log says what the attacker last wrote" becomes "the log says what the machine actually emitted, sealed as it happened."

④ Tracing submission/recovery semantics through a lost ack and a gap

Suppose the host submits records with sequence numbers 1, 2, 3, then an ack for record 2 is lost over PCIe, then record 3's submission is delayed, then the device reboots.

  1. Record 2, ack lost: the host retransmits the identical tuple. The device recognizes it matches the already-durable record and returns the prior result — no duplicate append, no ambiguity.
  2. Record 3 delayed: the device has seen 1 and 2 but not yet 3. It starts a bounded timer; if 3 doesn't arrive in time, the gap is exported alongside the next signed root as a visible, timestamped anomaly.
  3. Record 3 eventually arrives and is appended normally — sequence continuity is restored, and the earlier gap remains permanently visible in the exported history (it isn't erased retroactively).
  4. Device reboots mid-sequence: firmware resumes from the last durable chain head, and will reject any subsequent record whose sequence number would move backward — preventing a replay attack that tries to re-submit stale records as if they were new.
  5. Net effect: at-least-once delivery from the host's perspective, exactly-once incorporation into the sealed chain — achieved without the host ever needing to decide for itself what survived the crash.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A system seals a tamper-evident manifest every 10 minutes instead of every hour. Does this close the race window W, or just shrink it?
Show answer
Just shrinks it. W still spans the interval between record creation and the next seal, and a root adversary who strikes inside that interval can still rewrite the buffer before it's hashed. Moving the seal itself off the host bounds — rather than eliminates — the window: it ends the host's ability to rewrite a record after the device acknowledges it, so W_device collapses to that acknowledgment, but W_submit (the time before the record ever reaches the device) still exists and must be bounded separately, e.g. with a synchronous, back-pressured queue.Misconception: that a short enough seal interval is "good enough," or that device sealing eliminates the race window outright rather than bounding the remaining host-mutable portion to W_submit.
Problem 2 · medium
Three assumptions underpin the design: (a) device isolation, (b) pre-crossing stamping, (c) attested device. A malicious kernel module replaces the audit hook so it stamps a forged auid before a record ever crosses the device interface, keeping every field internally consistent. Does this violate assumption (b), and why doesn't device-side immutability alone save the investigator?
Show answer
No — assumption (b) only requires that stamping happen before the record crosses the interface, not that the kernel be uncompromised; the forged auid is still stamped pre-crossing, so the assumption technically holds. What's actually happening is the paper's explicitly stated non-guarantee: a compromised kernel can produce a record that's internally consistent from the device's point of view, and binding has no way to detect that the "kernel-stamped" field is itself a lie. Immutability only guarantees the record can't be rewritten after acknowledgment — it says nothing about whether the content was honest at submission time.Misconception: that "kernel-stamped" means "kernel-guaranteed-true." It names a structural/timing property — stamped by a component trusted to run before the interface — not a correctness guarantee once that component itself is compromised.
Problem 3 · medium
Why isn't "sign every record inline on the host, right before fsync" an equivalent alternative to device-side sealing?
Show answer
The signing key and the unsealed record both still live in host memory, which is exactly the resource a root adversary controls. A root adversary can forge a record, sign it with the same host-resident key, and the signature will verify — because the "trust anchor" (the key) never left the compromised machine. Faster or earlier signing reduces latency, not the attacker's reach.Misconception: that cryptographic signing is itself the security boundary. The boundary is whoever holds the key and touches the plaintext before sealing — and in this scheme, that's deliberately not the host.
Problem 4 · hard
Sequence continuity lets the device detect a missing record once a later one arrives. Construct a scenario where this detection mechanism provides zero protection, and explain what the paper proposes to close that gap.
Show answer
A root adversary gains control, then permanently stops the audit producer from submitting any further records — no record 'after' the stopped point ever arrives, so there's no later sequence number to reveal a gap. Sequence continuity only detects a gap between observed records; it says nothing about silence after the last one. The paper's answer is an external heartbeat or maximum-silence policy — a signal independent of the sequence counter itself, so that "no new records have arrived in too long" becomes its own detectable, external event.Misconception: that an append-only, gap-detecting log is automatically also an availability guarantee. Detecting gaps and detecting silence are different problems requiring different mechanisms.
Problem 5 · medium
An attacker forges a record and, knowing the device checks app-supplied attribution against the kernel-stamped auid, crafts the forgery so both fields agree. What does the device do, and is this a flaw in the design?
Show answer
The device accepts and seals it — there's no inconsistency to flag. This is not a flaw but an explicitly stated non-guarantee: the device is not an oracle on truth, only on non-rewritability after acknowledgment. The forgery is still immutably placed in the chain, positioned after previously anchored history, so its timing (arriving suspiciously soon after a compromise, say) remains available for an investigator to interpret — just not automatically flagged as false.Misconception: that "tamper-evident" means "lie-proof." The guarantee is about preventing retroactive edits to history, not about validating the truth of what's submitted.
Problem 6 · medium
Why does the paper prefer a split design option — "DPU binds, drive seals" — over putting both steps on a single device, as one item in the design space rather than the only answer?
Show answer
Placement is a trade-off across latency, compute cost, and coverage, not a single fixed answer. A DPU sits early on the path and can bind records before filesystem buffering even occurs, giving broad coverage without touching the drive. Moving sealing (persistence) into the drive itself can shorten W_device further since it eliminates one more hop. A split design lets each component do the part it's best positioned for — binding close to record creation, sealing close to durable storage — while reusing the same record format and verifier across placements.Misconception: that the paper prescribes one fixed hardware location. It explicitly frames placement as a trade-off space (DPU-first, in-SSD, or split) to be explored, not a solved question.
Problem 7 · easy
Why should the audit path use a reserved queue with its own backpressure, rather than sharing the device's general I/O scheduler with compression, encryption, and tenant workloads?
Show answer
A shared, unbounded queue means an unrelated burst of tenant I/O or compression work can silently starve or delay audit submissions, invisibly expanding W_submit. A reserved queue with explicit backpressure makes overload visible to both the kernel and an external monitor before anything is dropped, so the deployment can make a deliberate policy choice — fail closed for high-assurance services, or continue with a signed loss marker for general ones — rather than silently losing records inside a shared scheduler.Misconception: that any sufficiently fast device will "just handle it." Without isolation, audit traffic competes for the same resources as workloads that have no reason to prioritize forensic latency.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1Is this a built system, or just a proposal?▾
A proposal — this is a HotStorage position paper (7 pages), laying out the argument, the threat model, and a research agenda (RQ1–RQ5), not reporting a working prototype or benchmark numbers. The authors are explicit that a convincing answer still requires building and measuring it on a real SmartSSD or DPU.
Q2How is this different from a TEE/enclave-based logger like CUSTOS or SGX-Log?▾
Those shrink the trusted base to an enclave, but the enclave is still scheduled by the host OS and ingests records that first traverse untrusted host memory — the window before ingestion remains host-controlled. This position moves the anchor one layer further, to a storage device or DPU reached only through the I/O interface, so there's no host-scheduled component in the loop at all.
Q3Does the device understand what a log record "means"?▾
No, and deliberately so — the device sees blocks, not semantics. It relies on the kernel having already stamped the forensically decisive fields (who, what, which action) independent of the application, before the record crosses the interface. The device's job is to seal those delivered fields and check consistency, not to reconstruct program behavior from raw bytes.
Q4Can a rooted host still do anything bad to the log?▾
Yes — it can stop submitting new records (silent suppression, needing an external heartbeat to detect) and it can submit a forgery whose fields are internally consistent (accepted, but immutably placed after prior anchored history). What it cannot do is retroactively alter or delete anything already acknowledged by the device.
Q5Why does this need special hardware — can't software alone fix it?▾
Any purely host-software seal, however fast or well-isolated in an enclave, still shares host-reachable memory and scheduling with the adversary at some point before the seal. The paper's argument is that the fix is structural (which trust domain holds the key and the seal logic), not computational (how quickly the hash runs) — which is why it requires moving the function to hardware the host doesn't control.
Q6What's the performance cost?▾
Unmeasured as of this paper — that's exactly RQ3. The proposed evaluation plan is to report host CPU utilization, queue depth, throughput, and p99 emit-to-ack latency under concurrent incumbent device workloads (compression, encryption, tenant traffic), and to find the maximum sustainable audit-event rate before queueing enlarges W_submit.
Q7How is this different from WORM storage?▾
WORM makes a record immutable after it's written, but the host still composes what gets written — it can forge content before the commit, and WORM faithfully freezes the forgery. This design additionally binds each record to a kernel-stamped identity the host can't retroactively alter, and checks claimed attribution against it, which plain write-once media does not do.
Q8What about remote log shipping to a separate collector?▾
Shipping moves trust off the host too, but adds network latency and durability risk before the remote ack, and the collector still ingests host-originated bytes it has no way to bind to a kernel stamp. This position keeps the data path local (lower latency, no network dependency) while still moving the trust boundary off the host.
Q9Who has to trust what, in the end?▾
The device's firmware and its supply chain become the new trust root, so firmware attestation (and confidence in who built it) moves squarely into scope — a smaller, more specific, more testable question than "can I trust this entire host OS."
Q10Does this relate at all to CXL or computational storage used for performance?▾
Not directly — the paper itself discusses computational storage (SmartSSDs) and DPUs, not CXL. Its feasibility argument leans on the fact that such devices already ship isolated firmware and in-path compute for performance and multi-tenancy reasons, and that select devices expose persistent private key state — which this position repurposes for a security property (non-rewritable forensic history) rather than a performance one. The CXL connection is this guide's own analogy (a separate hardware-management domain outside direct host control), not something the paper argues.
Q11What's the very next step the authors propose?▾
An incremental three-step path: Step 1, place the engine in a DPU in front of unmodified drives (buildable on current hardware, moves the trust boundary immediately); Step 2, use a thin typed interface (RQ1) to make sealing identity-bound; Step 3, move the seal into the SSD controller itself to reduce the persistence component of W.

Glossary & further reading

Every term in one place, the guarantees laid out precisely, then a path to go deeper.

Core terms
Race window (W)W = t_seal − t_emit = W_submit + W_device — the interval during which a record is mutable by a host-root adversary, between production and immutable commitment.
Print-time integrityBinding and sealing a record at the moment it physically lands on the storage device, rather than later in host software.
BindThe device step of reading a record's kernel-stamped identity fields and checking any app-supplied attribution against them before sealing.
SealAppending the bound record to a device-resident, append-only tamper-evident structure under a key the host never sees.
Delivered-provenance bindingOne of the three device guarantees: each record is bound at print time to the kernel-stamped identity delivered with it, preventing silent retroactive reattribution.
Sequence continuityThe guarantee that a missing earlier sequence number becomes visible once a later record arrives at the device.
Semantic gapThe device sees raw blocks, not records; bridging it means carrying kernel-stamped fields across a thin typed interface rather than having the device reconstruct meaning.
Device isolation / pre-crossing stamping / attested deviceThe three assumptions the design rests on: no host path to device internals; correct identity stamped before the interface; firmware measurably genuine.
Supporting terms
TCB relocationMoving the trusted computing base for log integrity from the full host OS to a smaller, independently administered device domain.
Lookahead-style incremental pathThe paper's three-step rollout: DPU-first (buildable now) → typed interface (RQ1) → in-SSD seal (reduces persistence latency).
Non-guaranteeExplicitly what the device does not provide: truth-checking of a consistent lie, or detection of a host that simply stops submitting.
auid / uid / ses / syscallThe versioned header fields the paper's concrete typed path carries: login UID, current UID, session ID, and the syscall number, plus source, sequence, timestamp, and length.
Dedicated audit queueA reserved, back-pressured submission path isolated from compression/encryption/tenant offloads, bounding W_submit and making overload explicit.
Signed rootA periodically published, externally-anchored digest of the device's hash chain, letting a verifier detect a rolled-back or substituted device.

Open research agenda (§6)

RQ1 — The integrity interface design

What must the I/O path carry so the device can bind and seal a record? A thin, typed audit-write interface co-designed between the kernel audit subsystem and the device.

RQ2 — What binding alone buys analysis

The device runs no behavioral model — how much forensic strength does kernel-stamp binding alone deliver, and which forgeries slip through as internally consistent?

RQ3 — End-to-end line rate systems

Host CPU utilization, queue depth, throughput, and p99 emit-to-ack latency under concurrent incumbent device workloads; the maximum sustainable audit-event rate before queueing enlarges W_submit.

RQ4 — Keys, attestation, anchoring systems

A device-held signing key, authenticated firmware measurement, and externally anchored roots, adapted from TEE/tamper-evident techniques to a storage controller's resource budget.

RQ5 — Availability and lifecycle systems

Segment rotation, retention, device failure and reboot recovery, and the maximum permitted silence — without quietly reopening the window.
