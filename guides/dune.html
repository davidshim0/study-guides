Giving a process the keys to the kernel's toolbox — without becoming a whole machine

Two ways to let software touch page tables and privilege rings: hand it a virtual machine, or hand it a badge. Dune bets on the badge — using VT-x to keep a process a process while it borrows the CPU's most privileged features.

Before you begin

What the paper assumes you already know

Collapsed by default — open whatever's unfamiliar. Read in order the first time.

⚡ TL;DR

  • Dune uses Intel VT-x virtualization hardware to give a normal Linux process (not a VM) direct, hardware-enforced access to page tables, privilege rings, and exceptions — a process abstraction, not a machine abstraction.
  • Headline numbers: page faults deliver ~4.8× faster than SIGSEGV, syscall interposition is 25× cheaper than ptrace, user-level VM primitives are ~7× faster — all from a 2,509-line kernel module that needs zero kernel source changes.
  • It matters because it's a template for handing userspace cheap, fine-grained control over paging/dirty-bits/TLB — exactly the primitives OS-managed memory-tiering systems (hotness tracking, page placement) are still fighting the kernel for today.

Quick glossary
VT-xIntel's hardware virtualization extension; gives the CPU a lower-overhead way to trap into and out of privileged code than software emulation.
VMX root / non-root modeThe two CPU modes VT-x adds — root runs the hypervisor-like code, non-root runs the guest with its own private rings 0–3.
VMCSVM Control Structure — an in-memory record of a virtualized context's state and which events should trigger a trap back to root mode.
VM exit / entryThe hardware-managed transition into (entry) and out of (exit) non-root mode — the VT-x analogue of a syscall trap.
EPT (Extended Page Table)A second, hypervisor-controlled layer of address translation sitting underneath a guest's own page table, so the guest can't escape its sandbox even with raw page-table access.
Hypercall / VMCALLAn instruction a guest uses to deliberately request a VM exit — Dune repurposes it to mean "make a normal Linux system call."
PCIDA hardware TLB tag Dune exposes to user programs so they can switch among multiple page tables without a full TLB flush.
VPIDA separate hardware TLB tag Dune uses internally to tag TLB entries for Dune processes, hypercalls, and context switches — keeping VM entries/exits from forcing a flush.
Dirty / accessed bitsPer-page-table-entry flags set by hardware on write/read — the raw signal garbage collectors and memory-tiering systems both want cheap access to.
1Rings, privilege modes, and why user code can't touch page tables▾

x86 has protection rings (0 = kernel, 3 = user). Only ring 0 can load page tables, handle raw interrupts, or write control registers — that's the whole basis of process isolation. Normally, touching that hardware means asking the kernel via a syscall.

Now you're ready: Dune's whole premise is letting ordinary ring-3-bound code get ring-0-like power over specific hardware, safely.
2What a hardware virtual machine monitor (VMM) does▾

A VMM (hypervisor) runs one or more guest OSes, each believing it owns a whole machine. VT-x lets most guest instructions run directly on real hardware, with the VMM only stepping in (via a VM exit) for genuinely privileged operations.

Now you're ready: Dune reuses this exact hardware mechanism, but for a process instead of an OS — no guest kernel, no emulated devices.
3Two-level address translation (EPT/NPT)▾

A VM's guest page table maps guest-virtual → guest-physical. The VMM can't trust that mapping to point at real memory, so a second table, the EPT, maps guest-physical → host-physical, invisibly to the guest. Every memory access now walks two page tables instead of one.

Now you're ready: this doubled walk is Dune's main source of overhead — and it reappears anywhere software adds an extra translation layer for isolation.
4ptrace and signal-based introspection▾

Linux lets one process observe or intercept another's syscalls (ptrace) or be notified of hardware faults (signals like SIGSEGV). Both route through the kernel's generic trap-and-signal machinery, which is general-purpose but not cheap.

Now you're ready: Dune's ring-based interception and hardware exception delivery are faster replacements for exactly these two mechanisms.
5Why kernel modifications are risky▾

Patching a production kernel like Linux to expose a new hardware feature to userspace is intrusive: it can destabilize the whole system, and if two applications need conflicting kernel changes, they may not compose.

Now you're ready: Dune's constraint — an unmodified kernel plus a loadable module — is a direct response to this risk.
6Garbage collection via memory protection▾

Some garbage collectors use page-protection faults as "write barriers" — trap the first write to a page, record it, then unprotect. Knowing which pages were touched (dirty bits) since the last collection can replace this trap-heavy approach entirely.

Now you're ready: this is exactly the machinery Dune speeds up for the Boehm GC case study.
The whole story in one place

Dune in a nutshell

The problem, the trick that fixes it, and how the pieces connect.

Lots of applications — sandboxes, privilege-separation systems, garbage collectors — would benefit hugely from touching "kernel-only" hardware: page tables, privilege rings, exception vectors. The traditional options are both bad: patch the kernel (risky, doesn't compose across apps), or run inside a full virtual machine (breaks process integration — no shared file descriptors, no easy IPC, a whole second kernel to maintain).

Dune's move: use VT-x, the same hardware VMMs use, but expose a process abstraction instead of a machine abstraction. A small kernel module (2,509 LOC) puts the kernel in VMX root mode and lets any process opt into "Dune mode" via an ioctl — an irreversible switch into VMX non-root mode, where it gets its own private ring 0–3, direct page-table access, and hardware-delivered exceptions. It's still recognizably the same Linux process at the interface level — same file descriptors, same process abstraction — but underneath it now owns a user-controlled guest-virtual page table sitting atop an EPT, a compressed guest-physical layout, and some new constraints on syscall arguments, signal handling, and pthread/libDune interoperation; system calls themselves go via VMCALL instead of SYSCALL.

A userspace library, libDune (5,898 LOC), helps manage this environment: page-table manager, ELF loader, exception/signal shims. Because only one page table needs to change (not a whole guest OS's worth of virtualized devices), the EPT can be kept close to the real address space, and most instructions never trap at all.

The payoff: page faults deliver ~4.8× faster than SIGSEGV, user-level virtual-memory primitives run ~7× faster, syscall interposition is 25× cheaper than ptrace, a sandbox runs SPEC2000 at 2.9% average overhead, and a modified Boehm GC gets up to 40.7% faster — all while requiring zero changes to the Linux kernel itself.

🍯 Key takeaways

  • Dune = VT-x used to virtualize a process, not a machine — no guest OS, no emulated devices.
  • A Dune process keeps the same Linux process interface: shared fds, IPC — only syscalls change (VMCALL), though its address-space plumbing (guest page table + EPT) is new underneath.
  • EPT overhead (double page walks) is the main cost; large pages mostly erase it.
  • Three case studies — sandbox, Wedge privilege separation, Boehm GC — each get simpler and faster.
  • Everything ships as a loadable kernel module; the host kernel is never patched.
Six everyday pictures

How to think about Dune

Each stands alone. Every card admits where it stops being accurate.

The core idea · Process vs machine

A backstage pass vs a second theater

A backstage pass lets one performer through doors ordinary ticket-holders can't use — the theater, audience, and box office stay exactly as they were. Building a second theater gives the same access, but now you're running lighting, ushers, and ticketing twice. Dune is the pass: one process gets privileged doors opened, everything else about the "theater" (fds, IPC, the file system) is untouched.

Where it breaks: a real backstage pass doesn't need hardware to enforce its boundary — Dune's "pass" is enforced by the EPT, which does real translation work on every access.
EPT · Two-level translation

A hotel key card, not a master key

A guest with a raw master key could open any room. A key card instead gets re-checked at every door against a central table it can't edit. That's the EPT: Dune lets a process write its own page table freely, but every resulting address still passes through the EPT's independent check before it touches real memory — the process can misconfigure its own map, never the hotel's.

Where it breaks: a key-card check is instant; the EPT check is a second full page-table walk, roughly doubling the cost of a TLB miss (35.8 → 86.4 cycles in the paper's benchmark).
Dirty bits · Passive signal vs active check

A doorbell, not a guard walking every hallway

To know if anyone entered a room, you can install a doorbell (a bit that flips on entry) or pay a guard to walk every hallway every few minutes. Linux offers no doorbell for user programs — the Boehm GC either patrols with mprotect+signal traps, or on some OSes gets a coarse whole-address-space sweep. Dune exposes the actual hardware dirty bit, so the GC reads a doorbell instead of dispatching a patrol.

Where it breaks: hardware dirty bits are binary and per-page, not per-object — they tell you a page was touched, not what inside it changed, so some GC logic still needs the coarser mprotect trap as backup.
Interception · ptrace vs ring trap

A border checkpoint vs an escort shadowing every step

ptrace is an escort: the kernel stops the tracee, wakes the tracer, round-trips a message, and resumes — for every syscall. Dune's ring-based interception is a border checkpoint the untrusted code walks straight into: the syscall instruction itself traps to the sandbox runtime in the same process, no kernel round-trip needed unless the call is actually allowed through.

Where it breaks: a checkpoint you build yourself must also defend itself — the sandbox runtime has to validate every argument by hand, exactly the trust boundary a kernel-mediated ptrace gets "for free."
PCID/VPID · Tagged TLB

Labeled lockers instead of clearing the room

Without tags, switching between page tables means dumping everyone's belongings (flushing the whole TLB) because you can't tell whose entry is whose. Intel's PCID labels TLB entries by page-table owner, so Dune exposes it to let a user program switch among several of its own page tables without a flush. VPID is a separate tag Dune uses internally, to keep its own hypercalls and context switches between Dune processes from forcing a flush.

Where it breaks: labels are a finite resource (a limited number of PCID/VPID tags), so at high enough switching fan-out you eventually run out of lockers and fall back to flushing anyway.
Threat model · Same door, shorter hallway

A shortcut, not a new door

Dune's threat model rests on a simple claim: anything a Dune process can do, an ordinary process could already do through the same sequence of system calls — Dune just removes the hallway (kernel round-trips) in between. It's a faster path to a door that was already unlocked, not a new door.

Where it breaks: exposing hardware privilege rings does add something genuinely new — a process can now build its own internal privilege boundary (ring 0 vs ring 3) that didn't exist in the plain-process model at all.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals.

1 · Entering Dune mode

A process opts in via an ioctl on /dev/dune, supplying a page-table root. The transition is irreversible: once in Dune mode, the process stays there (a fork's child starts back outside Dune and can re-enter if needed). From then on, the process runs in VMX non-root mode with its own private ring 0–3 and a VMCS the module maintains per-thread.

2 · What gets exposed

FeaturePrivileged instructionsBenefit
ExceptionsLIDT, LTR, IRET, STI, CLIHardware-delivered page faults, ~4.8× faster than SIGSEGV
Virtual memoryMOV CRn, INVLPG, INVPCIDDirect page-table writes; batched TLB invalidation; PCID tagging
Privilege modesSYSRET, SYSEXIT, IRETReal ring 0/ring 3 boundary inside one process
SegmentationLGDT, LLDTLegacy; exposed but not emphasized
🌱
Only exceptions and privilege-mode transitions are already implicitly available in VMX non-root mode — Dune doesn't need per-instruction traps for them. Virtual memory is different: the module must explicitly grant %CR3 access via the VMCS before a Dune process can touch it. Segmentation is exposed but the paper doesn't discuss it further.

3 · Preserving OS interfaces

Normal syscall instructions trap only within the process (no VM exit) — so Dune redirects them: user code must issue VMCALL, which the module vectors through the kernel's ordinary syscall table, occasionally doing cleanup first (e.g. on exit). Signals are reworked too: hardware faults replace many of them outright (SIGSEGV → page fault), while others (SIGINT) are injected as fake hardware interrupts — which composes correctly with privilege modes, since hardware automatically promotes ring 3 back to ring 0 to service them safely.

4 · Enforcement in the three case studies

# Sandbox: trusted runtime in ring 0, untrusted binary in ring 3
on syscall_attempt(by untrusted):
    trap to ring-0 runtime          # no kernel round-trip needed
    validate args against policy
    if safe: VMCALL to real kernel
    else: deny

# Wedge: sthread = pre-checkpointed, policy-scoped lightweight process
create_sthread() = restore_from_checkpoint()   # not fork()
switch_sthread()  = swap page tables, tagged TLB avoids a flush  # no full flush
💡
Why sthreads beat fork: fork's cost is mostly page-table setup + TLB invalidation for a fresh process; recycling an already-checkpointed sthread skips the setup work entirely, which is why creation is ~40× faster. Context switches get a separate ~3× win from Dune's tagged-TLB support avoiding a full flush (Table 5).

5 · EPT overhead and the large-page fix

Dune's sandbox showed a 2.9% average SPEC2000 slowdown, but outliers like mcf (20.9%) and ammp (10.1%) came from high TLB-miss rates hitting the doubled EPT walk. Backing large allocations with 2MB pages (in both the EPT and the user page table) brought Dune within 0.1% of Linux running the same large-page configuration — the EPT cost didn't disappear, it just got amortized over far fewer, bigger translations.

Follow the numbers

Worked examples

Four traces carried through with the paper's own cycle counts.

① The syscall interposition speedup (ptrace vs ring trap)

  1. Linux ptrace, forwarding a syscall (getpid) to the kernel: 27,317 cycles (Table 3).
  2. Dune, intercepting and forwarding the same syscall via VMCALL: 1,091 cycles.
  3. Speedup: 27,317 ÷ 1,091 ≈ 25× — the paper's headline claim. Both sides still forward the syscall to the kernel, so this isolates the cost of the tracer/tracee ptrace round-trip versus Dune's in-process ring trap + VMCALL.
  4. A separate, larger win for "just check, don't forward": when the syscall is only inspected and allowed/denied without being forwarded, PTRACE_SYSEMU costs 13,592 cycles versus Dune's ~180 cycles — about 75×, a different comparison from the 25× headline number.
🍯
Insight: the 25× gain removes the ptrace tracer/tracee round-trip, not the kernel round-trip — Dune still forwards the syscall to the kernel via VMCALL. The kernel round-trip disappears entirely only in the "just check" case, where Dune beats PTRACE_SYSEMU by ~75×.

② Page fault delivery (Dune's ">4×" claim)

  1. Linux SIGSEGV delivery latency: 2,821 cycles (Table 3, "trap").
  2. Dune hardware page-fault trap: 587 cycles.
  3. Ratio: 2,821 ÷ 587 ≈ 4.8× — consistent with the abstract's "more than 4×."
💡
This single number is why GC write-barriers and sandboxes both get faster under Dune: both lean on fault delivery as their core signal.

③ Appel & Li user-level VM benchmarks (the "7×" claim)

  1. appel1 (TRAP/PROT1/UNPROT): Linux 701,413 cycles → Dune 94,496 cycles ⇒ 701,413 ÷ 94,496 ≈ 7.4×.
  2. appel2 (PROTN/TRAP/UNPROT): Linux 684,909 → Dune 94,854 ⇒ 684,909 ÷ 94,854 ≈ 7.2×.
  3. Average ≈ 7×, exactly the paper's summary figure, combining faster faults with direct page-table writes (no mprotect syscall detour).
🍯
Insight: this benchmark stacks two wins — faster exceptions (§2) and direct page-table access (no syscall to change protection) — which compound to more than either alone.

④ Boehm GC: where the 40.7% figure comes from

  1. HashMap benchmark, baseline execution time: 14,160 ms (Table 6).
  2. Dune "dirty bit" version (reads hardware dirty bits directly, skips mprotect/signal traps entirely): 8,391 ms.
  3. Improvement: (14,160 − 8,391) ÷ 14,160 ≈ 40.7% faster — the paper's best-case GC number.
  4. Contrast with XML parser: allocation (1,753 MB) ≈ heap size (1,737 MB) in that workload — little memory is actually recycled, so there's little garbage-collection work for the dirty-bit trick to speed up, and EPT overhead alone causes a 0.2–19% slowdown instead.
💡
The lesson generalizes: Dune's wins scale with how much a workload leans on the exact primitive it accelerates (faults, dirty bits, TLB control) — not a fixed tax or bonus.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A colleague says "Dune basically replaces the Linux kernel with something faster." What's wrong with that claim?
Show answer
Dune deliberately preserves OS interfaces — syscalls still go to the same Linux syscall table, just via VMCALL instead of SYSCALL. It accelerates specific hardware-adjacent operations (faults, page tables, privilege transitions); everything else — file systems, networking, scheduling — is still ordinary Linux.Misconception: that "faster kernel access" means "different kernel." Dune's whole design goal is an unmodified kernel.
Problem 2 · medium
If a Dune process never touches privileged instructions at all, should it still pay any overhead versus a normal process?
Show answer
Yes, on memory: every TLB miss now requires the hardware page walker to traverse both the user page table and the EPT (35.8 → 86.4 cycles per walk), because the EPT sits underneath all guest-physical accesses, not just privileged ones. Compute-only, cache-resident code is unaffected; large working sets or poor locality feel it.Misconception: that EPT overhead is opt-in. It's a property of being in VMX non-root mode at all, independent of which privileged features you actually use.
Problem 3 · medium
Why can't the EPT just be pointed at the same page root as the kernel's normal page table, avoiding the whole compression scheme?
Show answer
Two hardware limits: the EPT uses a different binary entry format from the standard x86 page table, and Intel caps guest-physical address width at the machine's physical RAM width (e.g. 36 bits) — narrower than the 48-bit host-virtual space Dune wants to expose. So Dune builds the EPT lazily from EPT-fault VM exits and compresses heap/mmap/stack into the first ~12GB of guest-physical space.Misconception: that EPT and page tables are "the same kind of table twice." They're different formats with different addressable ranges.
Problem 4 · hard
Wedge's sthread creation is 40× faster than fork. Is that speedup coming mainly from avoiding TLB flushes, or something else?
Show answer
Mainly something else: sthread creation reuses a pre-checkpointed, already-initialized sthread instead of building a fresh process from scratch, reducing creation to "restore some dirty memory." The tagged TLB is what makes context switching between sthreads 3× faster — a separate, smaller win. Conflating the two overstates what the tagged TLB alone buys.Misconception: that one hardware feature (tagged TLB) explains the whole 40× number. Creation and context-switch speedups come from two different mechanisms.
Problem 5 · medium
A forked child of a Dune process does not start in Dune mode. Why might that be the safer default rather than an oversight?
Show answer
Dune mode is irreversible and changes fundamental process behavior (syscalls become hypercalls, privilege rings become meaningful). Silently propagating that to every forked child — including children never designed to manage privileged hardware — could break assumptions in ordinary code paths. Requiring an explicit re-entry keeps the powerful, irreversible transition opt-in at every generation.Misconception: that inheritance would be "more convenient" with no downside. It would silently spread an irreversible, behavior-changing mode.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is Dune a hypervisor?▾
Loosely — the paper calls it a type-2 hypervisor since it runs atop an existing kernel. But it's not virtualizing an OS; it's virtualizing one process's privilege boundary. No guest kernel, no emulated devices.
Q2Does Dune require kernel source changes?▾
No — it's a loadable kernel module (2,509 LOC) working with an unmodified Linux kernel (tested on 3.2). That's a deliberate design constraint to make adoption easy.
Q3Can a Dune process attack the rest of the system?▾
The paper's threat model claims no: anything achievable in Dune mode was already achievable via ordinary syscalls — Dune just shortens the path. The EPT still bounds all guest-physical memory to that process's normal address space.
Q4Why is EPT overhead sometimes large and sometimes negligible?▾
It scales with TLB miss rate. Compute-bound, cache-friendly code (most of SPEC2000) barely notices; workloads with large working sets or poor locality (mcf, ammp) pay real cost from the doubled page walk. Large pages shrink this by reducing the number of walks needed.
Q5How does Dune compare to Native Client for sandboxing?▾
Native Client reports 5% average SPEC2000 overhead (12% worst case) via binary verification, and needs no virtualization hardware. Dune's sandbox averages 2.9% (worst case 20.9% without large pages, ~1.4% with), but requires VT-x and a kernel module — a different tradeoff between portability and overhead.
Q6What does "hypercall" mean in Dune specifically?▾
In most VMMs a hypercall is a paravirtualized, VMM-specific API. In Dune it means exactly one thing: "make this normal Linux system call," vectored through the kernel's regular syscall table via VMCALL.
Q7Why does the GC case study need three different Dune versions?▾
Each unlocks a different feature: a direct port just gets faster faults; a TLB-optimized version adds single-page INVLPG flushes instead of full flushes; a dirty-bit version skips memory protection traps entirely by reading hardware dirty bits. They're cumulative demonstrations, not competing designs.
Q8What hardware features did Dune leave unexposed?▾
Cache control, debug registers, and direct DMA-capable device access (via IOMMU/SR-IOV) — flagged as future work, useful mainly in special situations like preventing cache-based information leakage or reducing IO latency.
Q9Does Dune work on ARM or AMD?▾
The implementation targets 64-bit x86/Intel VT-x only. AMD's SVM offers an analogous NPT mechanism and is discussed as a plausible port target; ARM's Virtualization Extensions differ more (a separate deeper "Hyp" mode, no automatic state save/restore), making an ARM port a bigger redesign.
Beyond this paper

Connecting Dune to memory-systems design

Short, deliberately narrow connections — not a survey.

🔁 EPT's doubled page walk previews CXL's translation tax

Dune's 35.8 → 86.4 cycle page-walk cost from adding one extra translation layer is a small-scale preview of what CXL.mem and disaggregated-memory tiering pay for indirection: every extra hop between a CPU's page table and a tiering layer's own address mapping adds walk latency that page-placement heuristics (TPP, HeMem) have to amortize by promoting hot pages to cheaper paths.

🩹 Direct dirty-bit access is exactly what tiering systems still lack

Dune shows real value in letting userspace read hardware dirty/accessed bits directly instead of going through kernel-mediated, coarse interfaces (or none at all, as with Linux at the time). Modern hotness-tracking tiering systems still largely rely on kernel-side PTE scanning or PEBS sampling — a Dune-style direct, cheap, per-page access bit would remove a real source of tracking overhead.

🧩 "Preserve OS interfaces" is the same constraint CXL-tiering software faces

Dune's insistence on staying a normal process (shared fds, IPC, no second network stack) mirrors why memory-tiering research avoids library-OS or unikernel-style redesigns for CXL memory: breaking POSIX process semantics to gain a performance primitive is rarely worth it if it isolates the system from the rest of the software stack.

🔓 Safe privileged access without kernel patches parallels eBPF's philosophy

Both Dune and eBPF solve the same meta-problem — give userspace/extensions safe access to kernel-adjacent power without patching or destabilizing the kernel — via different mechanisms: hardware-enforced ring/EPT boundaries versus a verified bytecode sandbox. Extensible-kernel tiering policies (deciding promotion/demotion in-kernel via eBPF) inherit the same tradeoff Dune names explicitly: composability across multiple applications wanting the same hook.

🍯
Dune's real lesson for tiering research: the primitives that matter (fast faults, direct dirty bits, tagged TLBs) are worth exposing to userspace without redesigning the process model — the same principle that should guide how CXL-tiering hotness signals get surfaced.

Sharp questions to raise in class

Each ties to a specific number or design decision — not a generic reaction.

  1. Given the EPT forces a 12GB compressed guest-physical layout because of the 36-bit-physical-vs-48-bit-virtual mismatch, how much of Dune's implementation complexity is really an artifact of 2012-era address widths? (worth asking whether wider physical address spaces on modern server CPUs make this whole workaround unnecessary today)
  2. The XML benchmark slows down under all three Dune GC variants (19.0%, 12.2%, 0.2%) specifically because allocation (1,753MB) is nearly equal to heap size (1,737MB), meaning little memory gets recycled — does this suggest Dune's dirty-bit trick only helps allocation-heavy, low-turnover workloads are the wrong target? (push on whether the paper's own explanation fully accounts for the regression, or if EPT cost alone should dominate)
  3. Wedge's sthread creation is 40× faster than fork mainly via checkpoint-and-recycle, not the tagged TLB — does the paper's evaluation adequately separate these two contributions, or does bundling them into one number overstate what VT-x specifically buys? (the paper's Table 5 lists only aggregate numbers, not an ablation)
  4. Dune's sandbox averages 2.9% SPEC2000 overhead but mcf and ammp hit 20.9% and 10.1% from EPT/TLB pressure — given modern CPUs added nested-paging caches specifically to fix this, would Dune's headline numbers even reproduce on today's hardware? (good chance to connect to later 2-dimensional page-walk caching work cited in §7)
  5. The paper explicitly parks direct IOMMU/SR-IOV device access as future work — what would a Dune-style userspace path to CXL.mem or an NVMe queue (io_uring-style) need beyond what EPT already provides? (a natural bridge from Dune's 2012 scope to today's kernel-bypass I/O designs)
