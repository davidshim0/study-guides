Give a process the kernel's hardware, and keep it just a process

Dune runs an ordinary Linux process in the CPU's virtual-machine mode, so the process gets its own ring 0, page table, exception vectors and TLB tags, while the kernel keeps control of memory through a second translation layer it alone writes.

Before you begin

Use virtual-machine hardware to give one process the kernel's tools, without making it a virtual machine

A 2012 Stanford paper: a 2,509-line Linux kernel module puts a process into the CPU's guest mode, where page tables, exception vectors and privilege rings belong to the process, and a user-level library (libDune) helps it use them. Three applications show what that buys: a sandbox, a privilege separation system (Wedge), and a garbage collector.

⚡ TL;DR

  • Problem: many programs want "kernel-only" hardware (page tables, page faults, TLB control, privilege rings). Getting it means changing the kernel (intrusive, may not compose with other changes) or moving the program into a virtual machine (it loses file descriptors, fork, shared files, Unix sockets, and someone has to write a guest kernel).
  • Idea: use Intel VT-x to provide a process, not a machine. The kernel runs in VMX root mode; a process that opens /dev/dune and calls an ioctl moves, irreversibly, into VMX non-root mode, ring 0. There it can load its own interrupt table, write its own page table and %CR3, flush its own TLB entries, and run untrusted code in ring 3 below it.
  • Safety: every address the process uses goes through a second translation, the EPT, which only the kernel writes and which mirrors the process's normal Linux address space. So "any external effects produced by a Dune-enabled process could be produced without Dune through the same series of system calls."
  • Costs (Table 2, cycles): a system call becomes a VMCALL hypercall, so getpid goes from 138 to 895; a kernel-handled page fault from 2,687 to 5,093; a TLB-miss page walk from 35.8 to 86.4 because the walk now crosses two page tables.
  • Gains (Table 3, cycles): intercepting and forwarding a system call 27,317 → 1,091 (25×); delivering a page fault to the program 2,821 → 587 (4.8×); Appel and Li user-level virtual memory tests about 7× faster.
  • Applications: sandbox at 2.9% average SPEC2000 slowdown (within 0.1% of Linux once both use 2 MB pages) and under 2% on lighttpd; Wedge sthreads created 40× faster than fork with 3× faster context switches in 750 lines; Boehm GC up to 40.7% less run time using hardware dirty bits.

Quick glossary
Privilege ring (CPL)The x86 processor's current privilege level, a 2-bit number from 0 (most privileged, where kernels run) to 3 (least, where applications run). Certain instructions and pages marked supervisor-only are usable only at ring 0.
Privileged instructionAn instruction the CPU executes only at ring 0, such as loading the interrupt table (LIDT), writing %CR3, or invalidating a TLB entry (INVLPG); at ring 3 it raises a general-protection fault.
VT-xIntel's virtualization extension to the x86 instruction set: two new CPU operating modes, a per-virtual-CPU control structure in memory, and instructions to switch between the modes.
VMX root / non-root modeThe two VT-x operating modes. Root mode behaves like a normal x86 CPU plus the VT-x instructions; non-root mode is a restricted copy of the whole CPU, with its own rings 0 to 3, in which chosen events force a switch back to root mode.
VMM (hypervisor)The software that runs in root mode and controls guests. A type-2 hypervisor runs on top of an existing OS kernel; the paper says the Dune module "could be considered a type-2 hypervisor".
VMCS (VM control structure)A memory-resident data structure, one per virtual CPU, holding the guest's saved registers, the host's registers to restore on exit, and the configuration bits that decide which guest events cause an exit.
VM entry / VM exitThe hardware transitions between modes: an entry (VMLAUNCH or VMRESUME) loads guest state from the VMCS and runs the guest; an exit saves guest state, loads host state and jumps to the VMM's entry point.
Hypercall (VMCALL)An instruction a guest executes to request a VM exit on purpose, the guest-to-VMM counterpart of a system call. In Dune it is how a process makes Linux system calls.
EPT (extended page table)A second page table, written only by root-mode software, that the hardware applies after the guest's own page table to turn guest-physical addresses into real RAM addresses. AMD's equivalent is the nested page table (NPT).
Guest-virtual, guest-physical, host-virtual, host-physicalThe four kinds of address in Dune: what the Dune process's instructions use; what its own page table produces; what normal processes and the kernel use; and the real RAM address.
TLBThe CPU's cache of recent virtual-to-physical translations. A miss starts a hardware page walk through the page table in memory.
PCIDProcess-context identifier: a 12-bit tag the OS puts in %CR3 so TLB entries from different page tables can coexist and a page-table switch need not flush the TLB.
VPIDVirtual-processor identifier: a tag the VMM stores in the VMCS so the TLB can hold a guest's translations and the host's at the same time, and VM entries and exits need not flush it.
IDT (interrupt descriptor table)The in-memory table, located by the IDTR register, that tells the CPU which handler address and privilege level to use for each exception and interrupt number.
Supervisor bit (U/S)A bit in each page-table entry; when it marks a page supervisor-only, code running in ring 3 cannot read, write or execute that page.
Accessed and dirty bitsBits in a page-table entry that the hardware sets on the first access to a page and on the first write to it, so software can later tell which pages were used or modified.
MSR (model-specific register)One of many x86 configuration registers read and written with RDMSR/WRMSR. MSR_LSTAR is the one holding the address the SYSCALL instruction jumps to.
MMU notifierA Linux kernel callback chain that tells registered subsystems (KVM, Dune) when the kernel changes or removes a process's page mappings, so they can update their own copies.
ptraceThe Linux system call that lets one process (a tracer, such as a debugger) stop another at each system call or signal and inspect or change its state.
Dune modeThe state of a Linux process (more exactly, of each of its threads) after it has entered VMX non-root ring 0 through the Dune module. It cannot be left.
libDuneThe paper's user-level library (5,898 lines), untrusted by the kernel: a page-table manager, an ELF loader, a page allocator, and helpers for exceptions and system calls.
sthreadWedge's unit of isolation: a lightweight compartment with its own memory and system-call permissions set by a policy, meant to have "fork-like isolation with pthread-like performance".
Short primers (tap to open)
1Rings, privileged state, and what "kernel-only hardware" means▾

An x86 CPU is always running at a privilege level from 0 to 3. Linux uses two: the kernel at ring 0, applications at ring 3. A handful of registers and instructions are reserved for ring 0 (general knowledge, not in the paper):

  • %CR3 holds the physical address of the current page table's root. Writing it switches address spaces.
  • The IDT, loaded with LIDT, lists the handler for each exception (page fault is vector 14, divide error 0, breakpoint 3) and interrupt.
  • INVLPG drops one translation from the TLB; CLI/STI mask and unmask interrupts; LTR loads the task-state segment that says which stack to use when an interrupt arrives from ring 3.
  • Page-table entries have a supervisor bit: pages marked supervisor-only are invisible to ring 3.

Ring 3 code that tries any of these takes a fault into the kernel. That is the whole basis of process isolation: the kernel alone decides the mappings, the handlers and the stacks. It is also why an application that wants a page-fault handler (a garbage collector's write barrier) or its own mappings must ask the kernel through system calls and signals, which costs thousands of cycles each time.

Paper's Table 1 lists exactly these as what Dune hands to the process: exceptions (LIDT, LTR, IRET, STI, CLI), virtual memory (MOV CRn, INVLPG, INVPCID), privilege modes (SYSRET, SYSEXIT, IRET), and segmentation (LGDT, LLDT).

Now you're ready: Dune's question is how to let a process execute those instructions for real without letting it reach memory or devices that are not its own.
2System calls, exceptions, signals, and hypercalls▾

System call. On 64-bit x86, a program loads a call number and arguments into registers and executes SYSCALL. The CPU switches to ring 0 and jumps to the address in MSR_LSTAR, the kernel's entry point; SYSRET returns. A null call like getpid costs about 138 cycles on the paper's machine (Table 2).

Exception. When an instruction faults (a page fault, a divide by zero), the CPU looks up the IDT entry for that vector, switches to the handler's ring and stack, pushes the faulting state, and jumps. The handler returns with IRET.

Signal. If the kernel decides a user program should handle the event (for example SIGSEGV after an mprotected page is touched), it builds a frame on the user stack and returns to the program's handler; the handler later calls sigreturn. Linux spends 2,821 cycles just getting the page-fault signal to the program (Table 3, "trap").

Hypercall. A guest running under a VMM executes VMCALL to cause a deliberate VM exit, like a system call one level further down. In a normal VMM, hypercalls are a paravirtual interface for guest kernels ("register an interrupt handler for a virtual network device"). In Dune the hypercall is a Linux system call ("call read on a TCP socket"), because inside the guest, SYSCALL goes to the process's own ring 0, not to Linux.

Now you're ready: in Dune the same instruction (SYSCALL) becomes a cheap in-process trap, and reaching Linux costs a VM exit; that swap explains both Table 2's slower getpid and Table 3's faster interposition.
3VT-x: root and non-root mode, the VMCS, entries and exits▾

The x86 VMM paper (Adams and Agesen) contrasted VMware's binary translation, which rewrites guest kernel code so privileged instructions call into the VMM, with first-generation hardware virtualization, which runs guest code directly and traps to the VMM on chosen events. VT-x is that hardware (general knowledge connecting the two papers).

VT-x splits the CPU into VMX root mode ("does not change CPU behavior, except to enable access to new instructions for managing VT-x") and VMX non-root mode ("restricts CPU behavior and is intended for running virtualized guest OSes"). Each mode has its own rings 0 to 3, so a guest kernel really runs at ring 0 of non-root mode.

Following IBM's interpretive execution, "as many instructions as possible, including most that access privileged state, are executed directly in hardware without any intervention from the VMM" because the hardware keeps "a 'shadow copy' of privileged state." The VMM controls which events still leave the guest through the VMCS: for example, HLT can be set to exit or not. The IDT and privilege modes "are exposed implicitly in VMX non-root mode and never generate VM exits when accessed."

A VM entry (VMLAUNCH/VMRESUME) loads guest state from the VMCS; a VM exit saves it and jumps to the VMM. "Hardware automatically saves and restores most architectural state during both types of transitions." That save and restore is why a round trip costs hundreds of cycles (general knowledge): Table 2's getpid grows by 895 − 138 = 757 cycles (this guide's arithmetic).

Now you're ready: Dune runs no guest OS at all. It uses the same mode split to put an ordinary process at non-root ring 0, and configures the VMCS so that only kernel-bound events exit.
4Page tables, the TLB, and tags (global bit, PCID, VPID)▾

x86-64 translates a 48-bit virtual address with a 4-level tree (general knowledge): 9 bits index each level (PML4, PDPT, page directory, page table) and the last 12 bits are the offset in a 4 KB page. A 2 MB "large page" stops one level early. So a TLB miss costs up to 4 dependent memory reads, which the paper measures as 35.8 cycles on average on Linux (Table 2; most reads hit in the caches).

The TLB caches finished translations. When software changes a page-table entry, it must remove the stale TLB copy: INVLPG for one page, or a %CR3 reload to drop everything except entries marked global. Kernels mark their own pages global so they survive address-space switches; clearing those needs a heavier operation (the paper: disabling paging, which Dune therefore allows).

Tags let entries from different contexts coexist so that switches need no flush. PCID tags each entry with the page table it came from (12 bits in %CR3), so one program can keep several page tables live at once (Dune exposes this to processes). VPID tags entries with the virtual processor, so VM entries and exits need no flush; the Dune module uses it so "hypercalls and context switches do not require TLB invalidations."

The hardware also sets the accessed and dirty bits in page-table entries. Linux gave user programs no way to read them in 2012 (the paper: "Linux provides no user-level access at all to dirty bits"); in Dune the program owns its page table and can read them directly.

Now you're ready: the GC and Wedge results come from three of these: per-page INVLPG instead of full flushes, tagged switches, and reading dirty bits.
5The EPT and the two-dimensional page walk▾

If a guest could write %CR3 freely, its page table could point at any physical address, "including memory that belongs to the VMM." Before nested paging, VMMs kept shadow page tables, write-protecting the guest's page tables and rebuilding real ones on each change; the x86 VMM paper found these page-table traces among the most expensive operations for both of its VMMs (general knowledge, not in this paper). VT-x's EPT adds "a second, underlying, layer of address translation that can only be configured by the VMM": guest page table maps guest-virtual → guest-physical, then the EPT maps guest-physical → host-physical.

The price is the TLB miss. Every pointer in the guest page table is itself a guest-physical address, so the hardware must walk the EPT to find each guest page-table page, and once more for the final data page. With 4 levels in each table that is 4 × (4 + 1) + 4 = 24 memory references in the worst case instead of 4 (general knowledge; the paper's reference [8] is the standard analysis). Caches of partial walks hide most of this, which is why the paper measures 86.4 versus 35.8 cycles (2.4×), not 6×.

Large pages shorten both dimensions: one fewer level in each table. That is the fix the paper applies in the sandbox (2 MB pages "both in the EPT and the user page table").

Now you're ready: the EPT is both Dune's safety guarantee and its one cost that applications cannot avoid by changing their code (only their page sizes).
6Process abstraction versus machine abstraction▾

A machine abstraction is what a VMM gives a guest: CPUs, flat physical memory starting at 0, and devices (disks, network cards, a graphics card). The guest must bring a kernel, file system, network stack, drivers and a boot process to make use of it.

A process abstraction is what Linux gives a program: a virtual address space that can be sparse and shared with other processes, threads, file descriptors inherited from a parent, the ability to fork and exec, signals, a shared file system, and IPC such as Unix-domain sockets. The kernel provides all the services; the program never sees hardware.

Dune's claim is that hardware built for the first can provide the second. "A Dune process is a normal Linux process, the only difference being that it uses the VMCALL instruction to invoke system calls." It keeps its pid, files, sockets and memory semantics, and it gains the hardware a kernel would have, but only over the memory Linux would already give it.

Now you're ready: each design choice in Section 3 (the EPT mirroring the process's own mappings, system calls as hypercalls, no device emulation) follows from "process, not machine."
The whole story in one place

Virtualization hardware, pointed at a process

The Linux interface stays the same. What changes is which ring the process runs in, and who owns the page table it uses.

Garbage collectors, sandboxes, privilege-separation systems, checkpointers and distributed shared memory all want hardware that only the kernel may touch: page tables, page-fault delivery, TLB invalidation, the dirty bits the MMU sets, and privilege rings. Ordinary processes reach these through system calls and signals (mprotect, SIGSEGV, ptrace), and each round trip costs thousands of cycles. The two escapes both hurt. A kernel patch is intrusive, can destabilize the whole machine, and may not compose with another application's patch. A virtual machine gives a guest kernel the hardware, but the program stops being a process: it loses inherited file descriptors, fork, the shared file system and Unix-domain sockets, and someone has to write a kernel for it.

Dune's move is to use VT-x to provide a process, not a machine. A loadable kernel module turns on VT-x with Linux in VMX root mode. A process that asks (an ioctl on /dev/dune) is moved, permanently, into VMX non-root mode at ring 0. There, exceptions go straight through the process's own IDT, page-table entries are ordinary memory the process writes, INVLPG and PCID-tagged %CR3 switches are available, and ring 3 below it can hold untrusted code. None of these operations leaves the process, so they run at hardware speed: a page fault reaches the program in 587 cycles instead of 2,821.

Safety comes from the EPT, which only the kernel writes. Every address the process issues goes through its own page table and then through the EPT, and the Dune module builds the EPT lazily from Linux's own record of that process's mappings, keeping it in step through the same MMU-notifier hooks KVM uses. The process can map anything it likes in its page table, but the only RAM it can reach is RAM Linux would have given it anyway. The threat model follows: "Any external effects produced by a Dune-enabled process could be produced without Dune through the same series of system calls." The one new power is inside the process: hardware-enforced separation between its ring 0 and ring 3.

The process keeps being a Linux process because system calls become hypercalls. SYSCALL inside the guest traps to the process's own handler, so to reach Linux the process executes VMCALL, and the module dispatches it through the kernel's ordinary system-call table. Signals become injected hardware interrupts. Because Dune presents no machine, it needs no device emulation, saves and restores less state on each transition, and maps a sparse, shareable process address space instead of flat guest RAM. The cost is fixed and measurable: a null system call rises from 138 to 895 cycles, and a TLB miss from 35.8 to 86.4 cycles because the hardware walks two page tables.

The applications show where the trade pays. A sandbox puts a trusted runtime at ring 0 and an untrusted Linux binary at ring 3 in one address space; SPEC2000 runs 2.9% slower on average, and within 0.1% of Linux once both use 2 MB pages to tame the EPT. Wedge's sthreads use rings, page tables, dirty bits and the tagged TLB to be created 40× faster than a fork in 750 lines of code. The Boehm garbage collector gains in steps: flushing single TLB entries cuts run time by up to 23.8%, and reading the hardware dirty bits directly instead of write-protecting pages by up to 40.7%, unless the program allocates so little garbage that EPT misses dominate (the XML parser, up to 19% slower).

🍯 Key takeaways

  • VT-x's non-root mode is a complete second set of rings, IDT, %CR3 and TLB tags. Dune gives that set to one Linux process instead of to a guest kernel.
  • The EPT is the security boundary: the module fills it on demand from Linux's own page tables for that process, so the process's private page table can only rearrange memory it already owns.
  • Everything that stays inside the process gets faster (faults, protection changes, TLB flushes, system-call interposition); everything that must reach Linux gets a fixed VM-exit tax (757 extra cycles on getpid).
  • TLB misses cost about 2.4× more because walks cross two page tables; 2 MB pages in both tables remove the difference on SPEC2000.
  • Three applications: a near-zero-overhead sandbox, Wedge sthreads 40× cheaper to create than fork, a GC up to 40.7% faster, each in tens to hundreds of lines.
  • Dune is not an extensibility system like Exokernel or SPIN: it adds hardware access "in concert with the OS" rather than replacing the OS's abstractions.
Six everyday pictures

How to think about Dune

Each stands alone. Every card ends with where the picture stops being true.

User page table over the EPT

A tenant who may rearrange the furniture but not move the walls

Inside the apartment, the tenant decides which cupboard holds what and relabels drawers at will: that is the process writing its own page table. The walls, the doors and which apartment is theirs are the landlord's: that is the EPT, written only by the kernel and mirroring exactly the memory Linux gave the process. No arrangement of furniture reaches the neighbor's flat.

Where it breaks: this landlord builds each wall only when the tenant first walks into it (an EPT fault fills one entry at a time), and silently removes rooms when Linux reclaims pages; the tenant's furniture plan still points at them (M7).
System calls as VMCALL hypercalls

An embassy that uses the host country's post office

Inside the embassy its own rules apply and its own staff handle incidents (exceptions go to the process's IDT). To mail a letter, though, it must go out through a formal gate to the host country's post office: a VMCALL that exits to Linux, which runs the ordinary system call. The gate is slower than a citizen walking to the counter (895 versus 138 cycles for getpid).

Where it breaks: the letter must carry an address valid in the host country, not the embassy's internal room numbers: system-call arguments must be host-virtual addresses even if the process has remapped its own view (M13).
Sandbox: ring 0 runtime, ring 3 untrusted binary

A host who rents one room to a stranger

The host keeps the keys to the rest of the house (runtime pages marked supervisor-only) and tells the guest: anything you need from outside, ask me. Every request (a SYSCALL from ring 3) arrives at the host first, who checks it does not touch the host's rooms and then phones the city on the guest's behalf (VMCALL).

Where it breaks: a careful host would unpack a stranger's suitcase for inspection; the Dune sandbox does the opposite on purpose, letting the guest unpack (ELF-load) its own binary inside the room with ld-linux.so, so a booby-trapped header can only hurt the room (M17).
Two-dimensional page walk

A library catalog whose shelf numbers are themselves in code

Finding a book normally takes four lookups: floor, aisle, shelf, slot. Now every number you read is written in a code that must be looked up in a second four-step catalog before you can walk there, and so is the final slot. Up to 24 lookups instead of 4 (general knowledge). That is a TLB miss under the EPT.

Where it breaks: real librarians remember recent decodings (partial-walk caches) and most catalog pages are already on the desk (the data cache), so the measured cost is 2.4×, not 6× (86.4 versus 35.8 cycles, M20).
Wedge sthread recycling with dirty bits

Hotel housekeeping that only redoes the rooms marked "used"

Instead of building a new room for each guest (a fork, 81 µs), the hotel keeps a photo of the room as it was first made up. When a guest leaves, housekeeping restores only what the "used" tags (hardware dirty bits) say was touched. The next guest gets a pristine room in 2 µs.

Where it breaks: a hotel does not care if a previous guest left a note behind the wardrobe; Wedge must restore every piece of state an exploit could have changed (memory, registers, descriptors), and a page the photo missed is a leak between users (M18).
VPID and PCID tagged TLBs

Coat-check tickets with the owner's name on them

A coat check that throws out every coat whenever the shift changes forces everyone to re-hang their coats; one that writes the owner's name on each ticket keeps them all. VPID names the virtual processor, so leaving and re-entering the guest on a hypercall keeps the process's translations; PCID names the page table, so a Wedge context switch between sthreads can keep both sets (which tag Wedge relies on is this guide's inference, M18).

Where it breaks: tags avoid flushes but not capacity: a tagged TLB is no bigger, so many tags just compete for the same slots; and a tag says nothing about whether an entry is stale after a page-table edit, which still needs INVLPG (M11).

How it actually works

1 · The problem: kernel-only hardware, and two unsatisfying ways to get it

The paper's motivating users: Azul Systems' garbage collector (which modified Linux to get fast faults and batched page-table changes), process migration (which benefits from page faults and system calls), and IBOS (which moves browser abstractions into the lowest OS layer). Changing the kernel is intrusive, risks whole-system stability, and two applications' kernel changes may not compose. Packaging the application as a virtual machine gives safe hardware access but breaks process semantics (inherited file descriptors, spawning processes, shared files and devices, Unix-domain sockets) and requires writing or modifying a kernel (M1 to M5).

2 · Dune mode: an ordinary process placed at VMX non-root ring 0

A loadable module enables VT-x with the kernel in VMX root mode. A process opens /dev/dune and issues an ioctl with the root of a page table it has built; from then on it runs in non-root mode, ring 0, with its own VMCS, and cannot go back. Forked children start as normal processes. The module handles VM exits: system calls, EPT faults, HLT, interrupts (M3, M15).

3 · Memory: three translations, and an EPT that mirrors Linux's view of the process

The process's page table maps guest-virtual to guest-physical; the EPT maps guest-physical to host-physical. The module starts with an empty EPT, fills an entry on each EPT fault from what Linux's page-fault handler reports, and evicts entries when Linux's MMU notifier says a mapping changed. Because the EPT's guest-physical space is limited to the physical address width (36 bits on many Intel CPUs) while process addresses are 48 bits, Dune maps only three 4 GB regions (code/data/heap, mmap area, stack) into the first 12 GB of guest-physical space (M6 to M8).

4 · What the process gets, and what still goes to Linux

Exceptions and privilege modes need no configuration in non-root mode; %CR3 access is granted in the VMCS. The process can install an IDT, write page-table entries, flush single TLB entries, use PCID, run code in ring 3 with supervisor-only pages above it, and read the TSC directly. Control registers mirror the kernel's settings (with two exceptions), MSRs other than FS/GS base are not writable, and MSR_LSTAR is read-only. System calls go to Linux by VMCALL; signals arrive as injected interrupts (M9 to M14).

5 · libDune, three applications, and the price

libDune (5,898 lines, untrusted by the kernel) builds the initial page table, loads a GDT, IDT and TSS after entry, and provides a page-table manager, ELF loader and page allocator (M16). On top of it: a sandbox with a ring 0 runtime and a ring 3 binary (M17), Wedge sthreads (M18), and three Boehm GC ports (M19). The price is a fixed VM-exit cost on each kernel entry and 2.4× more expensive TLB misses (M20).

Background and context
  • Adam Belay, Andrea Bittau, Ali Mashtizadeh, David Terei, David Mazières and Christos Kozyrakis, Stanford University. OSDI 2012 (10th USENIX Symposium on Operating Systems Design and Implementation). Shepherd: Timothy Roscoe. Funded by DARPA CRASH and a gift from Google.
  • Platform: Linux on 64-bit Intel CPUs with VT-x; evaluation machine a single-socket Intel Xeon E3-1230 v2 (four-core Ivy Bridge, 3.3 GHz), 16 GB of RAM, Debian with Linux 3.2, frequency scaling disabled.
  • Prior work it builds on or contrasts with: VT-x and IBM's interpretive execution; KVM (shares low-level VT-x code); Appel and Li's user-level virtual-memory primitives; Azul's C4 and Pauseless collectors; Wedge (Bittau is an author of both); Native Client, Vx32, ptrace sandboxes; Exokernel, SPIN, Fluke.
  • Paper structure: 2 hardware background and the three exposed features; 3 the kernel module (overview, threat model, VMM comparison, memory, hardware access, OS interfaces, implementation); 4 libDune; 5 applications; 6 evaluation; 7 reflections on hardware; 8 related work.
The problem

Applications that benefit from "kernel-only" hardware must either modify the kernel ("kernel changes can be fairly intrusive and, if done incorrectly, affect whole system stability"; "if multiple applications require kernel changes, there is no guarantee that the changes will compose") or move into a virtual machine, which offers "poor integration with the host operating system" and requires producing a kernel, "no small task."

The result

A 2,509-line loadable module and a 5,898-line library that give a Linux process exceptions, virtual memory and privilege modes at hardware speed while it remains a Linux process. Microbenchmarks: 4.8× faster page-fault delivery, 25× cheaper system-call interposition, about 7× on Appel and Li; costs of 757 extra cycles per system call and 2.4× per TLB miss. Applications: a sandbox at 2.9% average SPEC2000 overhead (within 0.1% with large pages), Wedge with 40× faster sthread creation, a GC with up to 40.7% shorter run time.

Mechanisms in dependency order
  1. The hardware substrate (M1, M2): non-root mode with its own rings and IDT; the VMCS to pick which events exit; the EPT as a second translation only root mode writes.
  2. Turn it into a process (M3 to M5): enter by ioctl, irreversibly; the threat model (no new external effects); four deliberate differences from a VMM.
  3. Make memory a process address space (M6 to M8): three translations; an EPT filled from Linux's page tables and kept current by MMU notifiers; the 4 GB × 3 compressed layout forced by the address-width limit.
  4. Hand over the hardware, keep the OS (M9 to M14): exceptions, rings, page tables and TLB, which registers are mirrored or locked, system calls by VMCALL, signals as injected interrupts.
  5. Build it and use it (M15 to M19): the KVM-derived module, VMCS per thread, VPID; libDune and bootstrapping; sandbox, Wedge, GC.
  6. Measure the price (M20): VM-exit cost and two-dimensional walks, and when they matter.
The central trade-offs
  • In-process speed versus kernel-entry cost: everything that stays inside the process gets faster, everything that must reach Linux pays a VM exit. "For system calls, the time spent in the kernel tends to be a larger cost than the fixed VMX mode transition costs."
  • Safety versus TLB reach: the EPT makes direct page-table access safe, but "for application with poor memory locality or a large working set, more frequent TLB misses result in a measurable slowdown."
  • Process integration versus generality: Dune "is not capable of supporting a normal guest OS, but this permits Dune to be lighter weight and more flexible."
  • Power versus portability: "user programs require more architecture-specific code, potentially reducing portability"; Native Client "is more portable than Dune because it does not require virtualization hardware or kernel changes."
Effect of changes (whole design)
  • If the machine is itself a VM (most cloud instances, general knowledge): Dune needs nested VT-x, and every Dune VM exit becomes an exit to the outer hypervisor; the paper leaves the performance of that configuration as "an interesting topic of future consideration."
  • If EPT and regular page tables had the same address width (as Section 7 asks): the 4 GB per-region limit and the compressed layout would disappear (M8).
  • If the application is system-call heavy (many short calls): the 757-cycle tax per call dominates; lighttpd loses under 2%, but a workload of null calls would run about 6.5× slower (inference from Table 2).
  • If the working set exceeds TLB reach with 4 KB pages: EPT walks show up directly (mcf 20.9%, XML parser 19%); 2 MB pages in both tables are the fix the paper uses (M20).
  • If hardware sets EPT accessed/dirty bits (the paper notes Intel had just added them): swapping of Dune processes no longer has to assume every page is dirty (M7).

M1 · VT-x as Dune configures it: two modes, the VMCS, entries and exits

TL;DR
ProblemA process should execute privileged instructions for real, yet the kernel must regain control for anything that affects the rest of the machine.
MechanismRun Linux in VMX root mode and the process in non-root mode; use the VMCS to make only kernel-bound events (system calls by VMCALL, EPT faults, HLT, host interrupts) cause VM exits, and save and restore only the state a process needs.
Trade-offPrivileged operations inside the process run at hardware speed, in exchange for a VM exit and entry on every kernel crossing (getpid 138 → 895 cycles).
Breaks whenThe CPU lacks VT-x, the host is itself a VM without nested VT-x, or the application crosses into the kernel so often that exits dominate.
Key points
  • "VMX root mode is generally used to run the VMM and does not change CPU behavior, except to enable access to new instructions for managing VT-x. VMX non-root mode, on the other hand, restricts CPU behavior and is intended for running virtualized guest OSes."
  • "When the VMM executes the VMLAUNCH or VMRESUME instruction, hardware performs a VM entry; placing the CPU in VMX non-root mode and executing the guest. Then, when action is required from the VMM, hardware performs a VM exit, placing the CPU back in VMX root mode and jumping to a VMM entry point."
  • "Hardware automatically saves and restores most architectural state during both types of transitions. This is accomplished by using buffers in a memory resident data structure called the VM control structure (VMCS)."
  • "some hardware interfaces, such as the interrupt descriptor table (IDT) and privilege modes, are exposed implicitly in VMX non-root mode and never generate VM exits when accessed. Moreover, a guest can manually request a VM exit by using the VMCALL instruction."
  • VT-x follows IBM's interpretive execution: "as many instructions as possible, including most that access privileged state, are executed directly in hardware without any intervention from the VMM. This is possible because hardware maintains a 'shadow copy' of privileged state. The motivation for this approach is to increase performance, as traps can be a significant source of overhead."
  • Dune's narrower interface lets it shrink transitions: "we can limit the differences in guest and host state because processes using Dune have a narrower hardware interface. This results in reductions to the overhead of performing VM entries and VM exits." Section 7: "we were able to aggressively optimize hypercalls."
  • "timer interrupts and other exceptions intended for the kernel will still cause a VM exit", so a Dune process cannot monopolize the CPU.
How it works, step by step: a Dune process calls getpid
  1. In the guest: the process, at non-root ring 0, loads the system-call number into %rax and executes VMCALL (the paper's optional modified libc does this directly; with an unmodified libc, the SYSCALL traps to libDune in ring 0, which redirects it as a hypercall).
  2. VM exit: hardware stores the guest's registers into the VMCS guest-state area, loads the host state (Linux's stack, segments, %CR3) from the host-state area, records the exit reason (VMCALL) and jumps to the Dune module's exit handler (general knowledge for the exact fields).
  3. Dispatch: the module "vectors hypercalls through the kernel's system call table", here calling Linux's getpid handler for the thread that executed the hypercall.
  4. VM entry: the module writes the result into the guest's %rax and executes VMRESUME; hardware reloads guest state and the process continues after the VMCALL.
  5. Cost: 895 cycles in total, 757 more than Linux's 138. A program making one million null calls per second would lose 757 × 106 / 3.3 × 109 ≈ 23% of a core to transitions (this guide's arithmetic).
Assumptions it relies on
  • A1. The host CPU has VT-x and Linux runs on bare hardware (stated: "it cannot be used inside a VM unless there is support for nested VT-x").
  • A2. Target applications cross into the kernel rarely compared with how often they use the exposed hardware (implicit; stated as an outcome: "VMX transition costs had only a small effect on the performance of the applications we evaluated").
  • A3. The hardware implements VT-x correctly (stated in the threat model).
  • A4. VT-x can be turned on per core without disturbing other users of it (stated: "it is possible to run a VMM on the same machine as the Dune module, even if the VMM requires VT-x, because VT-x can be controlled independently on each core").
If an assumption changes
  • A1 changes (a cloud VM): with nested VT-x, the outer hypervisor must emulate each of Dune's VMLAUNCH/VMRESUME and VMCS accesses, so each Dune exit costs several outer exits (inference; the Turtles paper the authors cite as [6] measures nested exits, general knowledge). Without nested VT-x, Dune does not load at all.
  • A2 changes (system-call-heavy code): the worst case is Table 2's 6.5× on getpid; lighttpd, which makes "several system calls per connection", loses 1.3 to 1.4% (Table 4, M20).
  • A3 changes (a hardware flaw): the paper acknowledges "in rare cases exploitable hardware flaws have been identified"; a flaw in non-root isolation would give a Dune process whatever it gives a VM guest (inference, M4).
  • A4 changes (one owner of VT-x per core): the Dune module and KVM could not run side by side; the authors' claim that they can depends on each core's VMX state being independent (paper) and on each driver restoring the per-core state it found (inference).
Design notes and rejected alternatives

The trap-everything design ("introduce a mechanism for trapping each instruction that accesses privileged state so that emulation can be performed by a VMM") is what VT-x itself rejected for performance; Dune benefits because the instructions it wants to expose are exactly the ones VT-x lets a guest run without exits. The authors found VT-x "a surprisingly flexible hardware mechanism" and list only two hardware wishes: lower EPT overhead with full address width, and lower exit and entry latency. AMD's SVM is similar but was not implemented.

Connections

x86 VMM (hwsw): that paper found first-generation VT-x often slower than binary translation because exits were frequent and costly and there was no nested paging (general knowledge of that paper). Dune uses later VT-x (with EPT and VPID) and avoids most exits by not emulating a machine: there is no guest kernel touching page tables, devices or control registers. Livelock: host interrupts still force exits, so interrupt handling stays in Linux, where the Livelock paper's concerns apply unchanged (inference).

M2 · The EPT: a second translation only the kernel writes, and the two-dimensional walk

TL;DR
ProblemLetting a guest write its own %CR3 would let its page table reach any physical address.
MechanismVT-x's extended page table applies "a second, underlying, layer of address translation that can only be configured by the VMM": guest-physical → host-physical.
Trade-offDirect, safe page-table access for the guest, in exchange for TLB misses that walk two page tables (35.8 → 86.4 cycles per walk).
Breaks whenThe working set exceeds TLB reach and pages are small, so walks are frequent (mcf, ammp, the XML parser).
Key points
  • "Virtual memory is perhaps the most difficult hardware feature for a VMM to expose safely. A straw man solution would be to configure the VMCS so that the guest has access to the page table root register, %CR3. However, this would place complete trust in the guest because it would be possible for it to configure the page table to access any physical memory address, including memory that belongs to the VMM."
  • "VT-x includes a dedicated hardware mechanism, called the extended page table (EPT), that can enforce memory isolation on guests with direct access to virtual memory." AMD's equivalent is the nested page table (NPT).
  • Cost: "using the EPT makes TLB misses more expensive because, in some cases, the hardware page walker must traverse two page tables instead of one."
  • Table 2: page walk 35.8 cycles on Linux, 86.4 in Dune, measured by "a random page-aligned walk across 216 memory pages" so that "nearly every memory access results in a last-level TLB miss", dividing page-walk cycles from a performance counter by memory references.
  • "For applications with good memory locality or a small working set, it has no impact because the TLB hit rate is sufficiently high." Section 7: "Hardware modifications have been proposed to mitigate EPT overhead [2, 8]."
How it works, step by step: one TLB miss in a Dune process
  1. The program loads from guest-virtual address V; the TLB has no entry tagged with this process's VPID (and PCID) for V's page.
  2. Guest root: %CR3 holds guest-physical address G4 of the process's level-4 table. The walker translates G4 through the EPT (reads 1 to 4) to a host-physical address, then reads the guest level-4 entry (read 5), which yields G3.
  3. Repeat for G3, G2, G1: each costs 4 EPT reads and 1 guest read (reads 6 to 20), ending with the guest-physical address of V's data page.
  4. Final translation: the data page's guest-physical address goes through the EPT once more (reads 21 to 24). The TLB caches the combined V → host-physical translation, so the next access to that page costs nothing extra.
  5. Measured: 86.4 cycles per walk versus 35.8 natively, so each miss costs about 50.6 extra cycles (this guide's arithmetic). The ratio is far below 24/4 = 6 because upper-level entries of both tables are reused across walks and hit in caches (general knowledge).
Assumptions it relies on
  • A1. Only root-mode software can write the EPT (stated: "can only be configured by the VMM"), and the EPT pages are not mapped in the guest (implicit).
  • A2. Most programs have a TLB hit rate high enough that walk cost does not matter (stated).
  • A3. Guest-physical addresses are wide enough to name everything the guest needs (implicit for a VMM; false for Dune, M8).
  • A4. Large pages are available in both dimensions when needed (implicit; used in M20).
If an assumption changes
  • A1 changes (the EPT is reachable from the guest): the process could map any RAM, and the whole threat model (M4) collapses. The module must never place EPT pages in the process's address space (inference).
  • A2 changes (random access over a large heap): SPEC2000's mcf runs 20.9% slower in the sandbox; the XML parser with a 1,737 MB heap runs 19.0% slower under the direct GC port (M19, M20).
  • A3 changes: Dune must compress the process address space into 12 GB of guest-physical space (M8).
  • A4 changes (only 4 KB pages): the large-page remedy is unavailable; with 2 MB pages in both tables the worst case falls from 24 to 15 references and TLB reach grows 512× (general knowledge), which is why sandbox and Linux end up "within 0.1%".
Design notes and rejected alternatives

The rejected alternative is the straw man above: trust the guest's %CR3. The classic VMM alternative, shadow page tables (the VMM write-protects guest page tables and maintains a combined table), avoids two-dimensional walks but makes every guest page-table write a trap (general knowledge), which would defeat Dune's purpose of making page-table changes cheap. Dune takes the walk cost and recommends large pages.

Connections

x86 VMM (hwsw): that paper's hardware VMM had no EPT and used shadow page tables with traces; the EPT is the later hardware fix (general knowledge). Superpages: TLB reach is the same problem, and here a TLB miss is 2.4× more expensive, so superpages pay off sooner (inference). ESX: ESX's pmap (guest "physical" page → machine page) is the software analogue of the EPT's guest-physical → host-physical step (general knowledge of ESX; inference connecting them).

M3 · Dune mode: entering it, forking from it, and threads

TL;DR
ProblemOnly some processes need privileged hardware, and they should not have to be started specially or disturb anyone else.
MechanismA process enters "Dune mode" at any point "through an ioctl on the /dev/dune device"; the transition is irreversible; forked children start in normal mode; each thread gets its own VMCS.
Trade-offOpt-in and zero cost for everyone else, in exchange for a one-way door: a Dune process stays in non-root mode, paying the VM-exit cost on every system call, for the rest of its life.
Breaks whenA program needs privileged hardware only briefly, or a forked child expects to inherit its parent's Dune environment.
Key points
  • "Dune extends the kernel with a module that enables VT-x, placing the kernel in VMX root mode. Processes using Dune are granted direct but safe access to privileged hardware by running in VMX non-root mode. The Dune module intercepts VM exits, the only means for a Dune process to access the kernel, and performs any necessary actions such as servicing a page fault, calling a system call, or yielding the CPU after a HLT instruction."
  • "We apply Dune selectively to processes that need it; processes that do not use Dune are completely unaffected. A process can enable Dune at any point by initiating a transition through an ioctl on the /dev/dune device, but once in Dune mode, a process cannot exit Dune mode."
  • "Whenever a Dune process forks, the child process does not start in Dune mode, but can re-enter Dune if the use case requires it."
  • The introduction calls it "an irreversible transition in which, through virtualization hardware, safe and fast access to privileged hardware features is enabled, including privilege modes, virtual memory registers, page tables, and interrupt, exception, and system call vectors."
  • Implementation (Section 3.7): "it was easiest for us to create a VMCS for each thread instead of merely each process. One interesting consequence is that it is possible for both threads using Dune and threads not using Dune to belong to the same process."
How it works, step by step: life of a Dune process
  1. Start as a normal process at root ring 3, like any Linux program.
  2. Prepare: libDune builds a page table that maps the process's current addresses to the compressed guest-physical layout (M8, M16).
  3. Enter: the program calls the entry ioctl on /dev/dune, passing the page-table root. The module allocates a VMCS for the calling thread, sets up an empty EPT for the process, and VM-enters with "the provided page table root as the initial %CR3". The thread is now at non-root ring 0, executing the next instruction of the same program.
  4. Run: libDune loads a GDT, IDT and TSS and sets the GS base; the program then uses exceptions, page tables, rings and the TLB directly. Each system call is a VMCALL.
  5. Fork: the child is a normal process (root ring 3). If it needs Dune, it calls the ioctl itself.
  6. Other threads: a thread that never entered stays a normal thread of the same process, sharing the address space with Dune threads.
  7. Exit: the process cannot leave Dune mode; it ends with the exit system call, during which "Dune performs cleanup tasks" before calling Linux's handler.
Assumptions it relies on
  • A1. A process knows when it wants Dune and wants it from then on (implicit in "irreversible").
  • A2. A child usually does not need its parent's privileged state (implicit in "does not start in Dune mode").
  • A3. Per-thread VMCS state is enough; nothing needs a process-wide hardware context beyond the shared EPT (stated as the implementation choice).
  • A4. Linux is otherwise unmodified; only the module is loaded (stated: "works with unmodified Linux kernels").
If an assumption changes
  • A1 changes (privileged hardware needed only during one phase): the program pays the VM-exit tax on every later system call; there is no way out short of re-execing as a new process (inference).
  • A2 changes (a sandbox that forks): the child would come up outside the sandbox, at root ring 3 with the parent's memory; a sandbox must therefore intercept fork and make the child re-enter (inference; the paper's sandbox supports "most single-threaded Linux applications" and does not discuss fork).
  • A3 changes (process-wide privileged state, such as one IDT shared by all threads): each thread's VMCS must be set up the same way; libDune's page-table manager is "not yet thread-safe" (Section 4.2), which is where this shows up today.
  • A4 changes (the module is unavailable): no Dune; a program written for libDune cannot fall back, since its code assumes ring 0 (inference).
Design notes and rejected alternatives

The paper gives no reason for irreversibility. One plausible reason (inference): the process's page table, IDT and GDT are meaningful only in non-root mode with the compressed guest-physical layout, so returning to root ring 3 would mean undoing every remapping the process made, and Linux has no record of them. The per-thread VMCS was chosen because Linux threads are "nearly identical to processes except they have a shared address space."

Connections

Exokernel: an exokernel application is built on a library OS from the start; Dune lets an existing Linux process switch into a library-OS-like mode midway (inference). Mesa / threads: mixing Dune and non-Dune threads in one process means the same memory is reached through two translation paths (Linux's page table and the EPT plus the process's page table), and both must agree for shared data (inference).

M4 · The threat model: no new external effects

TL;DR
ProblemHanding a process its own ring 0, IDT and page table must not let it harm the kernel or other processes.
MechanismEverything with an external effect still passes through Linux: memory through the kernel-built EPT, services through system calls, the CPU through host interrupts that always exit. libDune is untrusted.
Trade-offThe OS's security model is unchanged and inside the process new separation becomes possible, in exchange for trusting the module (new kernel code) and the CPU's virtualization hardware.
Breaks whenThe EPT ever grants more than Linux's page tables would, a module exit handler has a bug, or the hardware's guest isolation is flawed.
Key points
  • "Dune exposes privileged CPU features without affecting the existing security model of the underlying OS. Any external effects produced by a Dune-enabled process could be produced without Dune through the same series of system calls. However, by exposing hardware privilege modes, Dune enables additional privilege-separation techniques within a process that would not otherwise be practical."
  • "We assume that the CPU is free of defects, although we acknowledge that in rare cases exploitable hardware flaws have been identified [26, 27]."
  • "Letting applications write their own page tables does not affect security because the underlying EPT exposes only the normal process address space, which is equally accessible without Dune."
  • libDune "is completely untrusted by the kernel".
  • Exceptions and interrupts: "This does not, however, allow a Dune process to monopolize the CPU, as timer interrupts and other exceptions intended for the kernel will still cause a VM exit."
How it works, step by step: five things a malicious Dune process might try
  1. Map someone else's RAM: it writes a page-table entry pointing at guest-physical address G outside its regions. The EPT has no entry for G, so the access causes an EPT fault (a VM exit). The module asks Linux's page-fault handler about the corresponding host-virtual address; Linux has no mapping there, so no EPT entry is created (paper for the mechanism; what the process then receives is not stated, inference).
  2. Install a hostile IDT, or CLI and spin: its IDT governs only exceptions in its own context. Host timer interrupts still cause VM exits regardless (paper), so Linux's scheduler runs as usual.
  3. Redirect system calls of other processes: MSR_LSTAR is read-only for Dune processes (paper: "Dune does not allow modification to MSRs"). This matters because Dune avoids switching most MSRs on each transition, so the guest sees the same LSTAR value Linux uses; a write the module allowed would also redirect Linux's own system-call entry until something restored it (inference from "to avoid the relatively high overhead of saving and restoring them").
  4. Ask Linux for something forbidden: a VMCALL runs the ordinary system-call handler with the process's ordinary credentials, so file permissions and every other check apply as before (inference from "vectors hypercalls through the kernel's system call table").
  5. Touch a device directly: Dune exposes no devices; I/O instructions and device memory are not in the EPT or are configured to exit (inference; the paper lists DMA-capable devices as future work behind an IOMMU).
Assumptions it relies on
  • A1. The CPU's isolation between non-root and root mode is correct (stated).
  • A2. The EPT never grants more than Linux's page tables for that process, including permissions (implicit; the design aims to "reflect" the kernel's translation "and permission").
  • A3. The module's 2,509 lines handle every exit correctly (implicit; it is new kernel code).
  • A4. Every event that must reach Linux is configured to exit (implicit in "timer interrupts ... will still cause a VM exit").
If an assumption changes
  • A1 changes (a hardware flaw in guest isolation): a Dune process is a guest that controls its own page tables, so it has the same reach as a malicious VM kernel. For example, the 2018 L1 Terminal Fault flaw let a guest controlling its page tables read data in the L1 cache through not-present entries (general knowledge, after the paper); a Dune process is in that position (inference).
  • A2 changes (an EPT entry writable where Linux's is read-only): a copy-on-write page shared with a parent after fork would be written in place, corrupting the parent's memory: a new external effect, exactly what the model forbids (inference).
  • A3 changes (an exit-handler bug): it is a kernel bug reachable by any process that can open /dev/dune (inference); the paper does not discuss who may open the device.
  • A4 changes (host interrupts not exiting): a process that executes CLI in its ring 0 could stall a core (inference).
Design notes and rejected alternatives

The model is relative, not absolute: Dune promises no new power outside the process, not that the process is safe. The new power inside, ring 0 versus ring 3 in one address space, is the point for the sandbox and Wedge, and those applications, not the kernel, are responsible for using it correctly ("libDune receives an exception and jumps into a handler provided by the sandbox runtime").

Connections

Exokernel: the EPT plays the role of a secure binding: protection is checked by hardware when a mapping is used, and management (the process's own page table) is left to the application (inference connecting the papers). Eraser: both papers are about catching what untrusted or buggy code does without trusting it; Eraser at run time in software, Dune's sandbox in hardware (inference, loose).

M5 · Process, not machine: four differences from a VMM

TL;DR
ProblemA VMM's job (present a whole machine so an unmodified OS can boot) brings device emulation, full state switching and a separate address space, none of which a process needs.
MechanismHypercalls are Linux system calls; no device emulation (fall back on the OS); a narrower guest/host state difference; an EPT that reflects a process address space rather than flat RAM.
Trade-offLighter, faster transitions and full integration with the host, in exchange for being unable to run a guest OS at all.
Breaks whenA program needs a different kernel underneath it, or hardware that cannot be exposed without VMM intervention.
Key points
  • "Dune exposes a process environment instead of a machine environment. As a result, Dune is not capable of supporting a normal guest OS, but this permits Dune to be lighter weight and more flexible."
  • Hypercalls: "a VMM might provide a hypercall to register an interrupt handler for a virtual network device, whereas a Dune process would use a hypercall to call read on a TCP socket."
  • No emulation: "only hardware features that can be directly accessed without VMM intervention are made available; in cases where this is not possible, a Dune process falls back on the OS." Example: no virtual graphics card; "Dune processes employ the normal OS display service, usually an X server accessed over a Unix-domain socket and shared memory."
  • State: "A typical VMM must save and restore all state that is necessary to support a guest OS. In Dune, we can limit the differences in guest and host state ... This results in reductions to the overhead of performing VM entries and VM exits."
  • Memory: "VMMs place each VM in a separate address space that emulates flat physical memory. In Dune, we configure the EPT to reflect process address spaces. As a result, the memory layout can be sparse and memory can be coherently shared when two processes map the same memory segment."
  • "Despite these differences, the Dune module could be considered a type-2 hypervisor [22] because it runs on top of an existing OS kernel."
How it works, step by step: the same request in a VM and in Dune
  1. A program reads 4 KB from a TCP socket, in a VM: the guest kernel's read runs inside the guest; its network driver talks to an emulated or paravirtual NIC; the VMM (or host) receives the packet in its own network stack and copies it into guest memory. Two network stacks, two kernels (general knowledge; the paper's lighttpd explanation: "each network request must traverse two network stacks, one in the guest and one in the host").
  2. The same read in Dune: the process executes VMCALL with read's number; the module calls Linux's read, which copies from the socket buffer to the process's buffer at a host-virtual address. One network stack.
  3. Shared memory with an X server, in Dune: the segment is mapped in both processes by Linux; the EPT of the Dune process points at the same host-physical pages as the X server's page table, so stores are coherent with no copying (paper's "coherently shared").
  4. Result on lighttpd (Table 4): VMware Player serves 734 and 5,763 requests/s (1 and 100 clients), the Dune sandbox 2,206 and 24,255, Linux 2,236 and 24,609.
Assumptions it relies on
  • A1. The application wants Linux's services, not a kernel of its own (stated: "For applications that fit its paradigm").
  • A2. Every needed device service is available through system calls (stated: "a Dune process falls back on the OS").
  • A3. The host's address-space features (sparse layout, sharing) can be expressed in the EPT (stated; limited by M8).
If an assumption changes
  • A1 changes (the program wants a custom scheduler or file system): Dune cannot help; the paper points to Exokernel and SPIN for extensibility, and to Fluke for nesting.
  • A2 changes (the program wants direct, low-latency device access): not supported; Section 7 proposes using the IOMMU and SR-IOV to expose devices safely.
  • A3 changes (an unusual layout): address ranges outside the three 4 GB regions are unreachable (M8).
Design notes and rejected alternatives

The rejected alternative is the paper's own "another strategy": bundle the application into a VM image with a specialized kernel (Libra, Disco-style). Section 1 rejects it for poor integration and for the effort of writing a kernel with "a file system, a networking stack, device drivers, and a bootstrap process."

Connections

ESX: ESX presents whole machines and spends its effort on memory it cannot see into (ballooning, content-based sharing); Dune avoids the problem because Linux still manages the process's memory and the EPT only mirrors it (inference connecting the papers). x86 VMM (hwsw): device emulation and full state switching are what made that paper's VMMs expensive on I/O; Dune deletes both rather than accelerating them (inference). NFS: like NFS keeping the UNIX file interface while changing what is underneath, Dune keeps the process interface while changing the hardware mode under it (inference, loose).

M6 · Three translations: the process's page table above, the EPT below

TL;DR
ProblemGive the process direct control of its page table while keeping "a normal process memory address space by default" and preventing "arbitrary access to physical memory".
MechanismSplit translation in two: a user-controlled page table maps guest-virtual → guest-physical; the kernel-managed EPT maps guest-physical → host-physical. Isolation lives entirely in the EPT; application tricks live entirely in the user page table.
Trade-offThe process can remap, protect and inspect its pages freely, in exchange for a second table the kernel must keep consistent with Linux's own and a more expensive TLB miss.
Breaks whenThe kernel's page table and the EPT cannot be the same structure (they cannot: different format, different address width), so Dune must build and maintain the EPT separately (M7, M8).
Key points
  • "Memory management is one of the biggest responsibilities of the Dune module. The challenge is to expose direct page table access to user programs while preventing arbitrary access to physical memory. Moreover, our goal is to provide a normal process memory address space by default, permitting user programs to add just the functionality they need instead of completely replacing kernel-level memory management."
  • "One translation is specified by the kernel's standard page table. In virtualization terminology this is the host-virtual to host-physical (i.e., raw memory) translation. Host-virtual addresses are ordinary virtual addresses, but they are only used by the kernel and normal processes. For processes using Dune, a user controlled page table maps guest-virtual addresses to guest-physical. Then the EPT, managed by the kernel, performs an additional translation from guest-physical to host-physical."
  • "All memory references made by processes using Dune can only be guest-virtual, allowing for isolation and correctness to be enforced in the EPT while application-specific functionality and optimizations can be applied in the user page table."
  • "If it were permitted by hardware, we would simply point the EPT and the kernel's page table to the same page root. Unfortunately, two limitations make this impossible. First, the EPT requires a different binary format from the standard x86 page table. Second, Intel x86 processors limit the address width of guest-physical addresses to be the same as host-physical addresses."
How it works, step by step: who can change what
  1. The process changes its page table with ordinary stores (it is just memory in its address space). It can unmap 0x7EFF_8000_1000, mark it read-only, alias it at a second guest-virtual address, or point it at a different guest-physical page it owns.
  2. None of that reaches Linux. Linux's own page table for the process still says host-virtual 0x7EFF_8000_1000 maps the RAM page, and the EPT still maps guest-physical 0x1_8000_1000 to it.
  3. Linux changes its page table (munmap, swap-out, copy-on-write break); the MMU notifier tells the module, which removes the EPT entry (M7). The process's page table may still point at 0x1_8000_1000; the next access will EPT-fault and be resolved against Linux's new state.
  4. What the process can never do: produce a guest-physical address the EPT maps to RAM Linux has not given this process. The worst it can do is make its own memory inaccessible or aliased.
Assumptions it relies on
  • A1. The process's page table is consistent with the guest-physical layout the module uses (stated; libDune builds it, M16).
  • A2. Linux remains the single authority on what memory the process owns (stated: "a normal process memory address space by default").
  • A3. Application-specific memory tricks need only rearrange, protect or inspect memory the process already owns (implicit).
If an assumption changes
  • A1 changes (a buggy libDune maps guest-virtual to the wrong guest-physical page): the process corrupts only itself; the guest-virtual ≠ host-virtual mismatch also breaks system calls that pass pointers (M13).
  • A2 changes (the process wants memory Linux did not give it): it must still ask Linux (mmap by VMCALL); there is no Dune path to physical memory.
  • A3 changes (the application wants physical contiguity or cache coloring): guest-physical addresses are a compressed alias of host-virtual addresses, not physical frames, so the process cannot choose real frames (inference); the paper's Section 7 lists cache control as unexposed.
Design notes and rejected alternatives

The ideal, sharing one root between the EPT and the kernel's page table, is rejected only by hardware. The paper's split is what makes the threat model simple: the EPT carries the policy, the user page table carries the mechanism the application wants.

Connections

Exokernel: Exokernel applications name physical pages and the kernel checks ownership on each TLB load; Dune applications never see physical names at all (inference connecting the papers). vLLM: PagedAttention's block table is a software page table an application keeps over memory it already owns, which is the same division as Dune's user page table over the EPT, in software (inference, mechanical analogy).

M7 · Filling the EPT from Linux's page tables, and keeping it current

TL;DR
ProblemThe EPT must reflect exactly what Linux has mapped for the process, but it has a different format and Linux's mappings change all the time.
MechanismStart with an empty EPT; on each EPT fault, ask Linux's page-fault handler for the translation and permission and write one EPT entry; hook the MMU-notifier chain (as KVM does) to evict entries when Linux unmaps, and report access/dirty status back.
Trade-offAlways correct and lazy, in exchange for an extra VM exit on the first touch of each page (kernel-handled fault 2,687 → 5,093 cycles) and, in this implementation, conservative access/dirty reporting.
Breaks whenThe workload touches many fresh pages, or memory pressure makes swapping decisions depend on accurate accessed/dirty bits.
Key points
  • "Our solution to EPT format incompatibility is to query the kernel for process memory mappings and to manually update the EPT to reflect them. We start with an empty EPT. Then, we receive an EPT fault (a type of VM exit) each time a missing EPT entry is accessed. The fault handler crafts a new EPT entry that reflects an address translation and permission reported by the kernel's page fault handler."
  • "Occasionally, address ranges will need to be unmapped. In addition, the kernel requires page access information, to assist with swapping, and page dirty status, to determine when write-back to disk is necessary. Dune supports all of these cases by hooking into an MMU notifier chain, the same approach used by KVM [30]. For example, when an address is unmapped, the Dune module receives an event. It then evicts affected EPT entries and sets dirty bits in the appropriate Linux page structures."
  • "One limitation in our implementation is that we cannot efficiently detect when EPT pages have been modified or accessed, which is needed for swapping. Intel recently added hardware support for this capability, so it should be easy to rectify this limitation. For now, we take a conservative approach and always report pages as modified and accessed during MMU notifications in order to ensure correctness."
  • Table 2, "page fault": "the time it took to fault in a pre-zeroed memory page by the kernel": 2,687 cycles on Linux, 5,093 in Dune. "Page fault overhead is also not much of a concern, as page faults tend to occur infrequently during normal use."
How it works, step by step: cost of touching fresh memory
  1. Per page: 5,093 − 2,687 = 2,406 extra cycles for the first touch of each 4 KB page (this guide's arithmetic on Table 2).
  2. A program that touches 1 GB of fresh memory: 262,144 pages × 2,406 ≈ 6.3 × 108 cycles ≈ 0.19 s extra at 3.3 GHz, on top of Linux's own 262,144 × 2,687 cycles ≈ 0.21 s.
  3. With 2 MB pages in the EPT (as in the sandbox's large-page mode, M20), one EPT fault covers 512 small pages, so the same gigabyte needs 512 EPT faults instead of 262,144 (inference, assuming one EPT fault per 2 MB EPT entry).
  4. Why the extra cost exceeds one hypercall's 757 cycles: the paper does not break it down. A plausible account is the EPT-violation exit plus a page-table lookup on the host side plus writing an EPT entry (inference).
Assumptions it relies on
  • A1. The module can ask Linux's page-fault handler to resolve a host-virtual address on behalf of the process (stated as the mechanism).
  • A2. Every change Linux makes to the process's mappings is announced through the MMU-notifier chain (stated: the KVM approach).
  • A3. First touches are rare relative to later accesses (stated: "page faults tend to occur infrequently during normal use").
  • A4. Reporting every page as accessed and dirty is acceptable until hardware support is used (stated).
If an assumption changes
  • A1 changes: the module would need its own copy of Linux's VMA logic (permissions, file mappings, copy-on-write), which is what the paper avoids by asking the kernel (inference).
  • A2 changes (a missed notification): a stale EPT entry would keep pointing at a page Linux has freed and reused, letting the process read or write another process's data. This is the single most security-critical piece of bookkeeping in the module (inference).
  • A3 changes (allocation-heavy code): 0.19 s per fresh gigabyte; a garbage collector that unmaps and remaps its heap would pay it repeatedly (inference).
  • A4 changes (memory pressure): Linux's reclaim uses accessed bits to find cold pages and dirty bits to skip writing clean ones. If every Dune page always looks accessed and dirty, reclaim cannot age them and writes clean pages back (inference from the paper's statement).
Design notes and rejected alternatives

Eagerly copying all of Linux's mappings into the EPT at entry would cost time proportional to the address space and still need notifiers for later changes; the lazy fill costs only for pages actually touched. The paper also notes the format problem could not be solved by sharing a root. The A/D limitation is a deliberate interim choice of correctness over swap efficiency.

Connections

ESX: ESX must guess which guest pages are idle (it samples them for its idle-memory tax) because it cannot see inside the guest; Dune has the opposite problem, Linux owns the memory but cannot see the hardware's EPT accessed bits (inference connecting the papers). LFS / F2FS: treating all pages as dirty is the same conservative choice as a cleaner that cannot tell live from dead data: correct, but it does extra write-back (inference, loose).

M8 · The address-width limit, and the 12 GB compressed layout

TL;DR
ProblemGuest-physical addresses can be only as wide as host-physical ones (36 bits, 64 GB, on many Intel CPUs), but a process uses 48-bit virtual addresses spread across a huge range.
MechanismMap only three regions: the start of the process (code, data, heap), the mmap region and the stack, each up to 4 GB, packed into the first 12 GB of guest-physical space; the process's page table expands them back to their original virtual addresses.
Trade-offOrdinary programs keep their ordinary addresses, in exchange for unreachable memory outside the three regions and a 4 GB cap on each.
Breaks whenA program maps memory at "nonstandard portions of the address space", or needs more than 4 GB in one region.
Key points
  • "In a standard virtual machine environment this would not be a concern because any machine being emulated would have a realistically bounded amount of RAM. For Dune, however, the problem is that we want to expose the full host-virtual address space and yet the guest-physical address space is limited to a smaller size (e.g., a 36-bit physical limit vs. a 48-bit virtual limit on many contemporary Intel processors)."
  • "We note that this issue is not present when running in 32-bit protected mode, as physical addresses are at least as large as virtual addresses."
  • "we only permit addresses from the beginning of the process (i.e., the heap, code, and data segments), the mmap region, and the stack. Currently, we limit each of these regions to 4GB, allowing us to compress the address space to fit in the first 12GB of the EPT. Typically the user's page table will then expand the addresses to their original layout."
  • "This could result in incompatibilities in programs that use nonstandard portions of the address space, though such cases are rare."
  • Rejected for now, proposed for later: "pack each virtual memory area into the guest-physical address space in arbitrary order and then provide the user program the additional information required to remap the segment to the correct guest-virtual address in its own page table, thus avoiding the possibility of unaddressable memory regions."
  • Section 7: "modifying the EPT to support the same address width as the regular page table would reduce the complexity of our implementation and improve coverage of the process address space."
How it works, step by step: translating one mmap address (illustrative numbers)
  1. Suppose the mmap region's top is host-virtual 0x7F00_0000_0000, so its 4 GB window is [0x7EFF_0000_0000, 0x7F00_0000_0000), assigned guest-physical [4 GB, 8 GB) = [0x1_0000_0000, 0x2_0000_0000).
  2. A pointer 0x7EFF_8000_1000 lies 0x8000_1000 (2 GB + 4 KB) into the window, so its guest-physical address is 0x1_0000_0000 + 0x8000_1000 = 0x1_8000_1000.
  3. libDune's page table maps guest-virtual 0x7EFF_8000_1000 → guest-physical 0x1_8000_1000, so the program's pointer is unchanged.
  4. On an EPT fault for 0x1_8000_1000, the module inverts the rule (slot 1, offset 0x8000_1000 → host-virtual 0x7EFF_8000_1000) and asks Linux about that page (M7).
  5. Capacity: 12 GB is 0x3_0000_0000, well under 236 = 64 GB; the user half of a 48-bit space is 247 = 128 TB, about 10,900 times larger than 12 GB (this guide's arithmetic).
Assumptions it relies on
  • A1. Programs keep their memory in the three standard regions (stated: "such cases are rare").
  • A2. No region needs more than 4 GB (stated as the current limit).
  • A3. The process runs in 64-bit mode (stated: the issue does not arise in 32-bit protected mode).
  • A4. Physical address width stays below virtual width (stated for "many contemporary Intel processors").
If an assumption changes
  • A1 changes (a JIT or allocator that places mappings at fixed high addresses outside the mmap window): those addresses have no guest-physical slot, so the process cannot reach them (inference from "incompatibilities").
  • A2 changes (a 6 GB heap allocated with mmap): the mmap window holds 4 GB, so the rest is unaddressable, even though the program uses only "standard" regions. The evaluation's largest heap, 1,737 MB for the XML parser, stays under the cap. With 64 GB of guest-physical space in the paper's 36-bit example, the 4 GB choice is an implementation limit, not a hardware one (inference).
  • A3 changes (32-bit process): no compression would be needed, but Dune supports only 64-bit long mode ("32-bit mode are possible future additions").
  • A4 changes (EPT with full virtual width, Section 7's wish): the EPT could use host-virtual addresses as guest-physical ones directly and the compression would disappear.
Design notes and rejected alternatives

Identity mapping guest-virtual to guest-physical is impossible because guest-physical cannot exceed 36 bits. The "more sophisticated solution" (pack each memory area anywhere and tell the program where) was deferred; it avoids unaddressable regions but makes libDune's page table depend on a list of areas that changes with every mmap (inference).

Connections

Superpages: region sizes that are multiples of 2 MB keep large-page alignment intact between guest-virtual and guest-physical, which the sandbox's 2 MB EPT pages require (inference). ESX: a VMM gives a guest a small, dense "physical" space and lets the guest kernel lay out virtual memory; Dune must fit an already-laid-out sparse space into the dense one, which is the inverse problem (inference).

M9 · Exceptions delivered in hardware, through the process's own IDT

TL;DR
Problem"reporting an exception to a user program requires privilege mode transitions and an upcall mechanism (e.g., signals)", which is slow.
MechanismIn non-root mode the IDT and privilege modes are the guest's, so a fault inside the process vectors straight to a handler the process installed with LIDT; the handler returns with IRET.
Trade-offException delivery at hardware cost (587 versus 2,821 cycles for a page fault), in exchange for the process having to provide a working IDT, stacks and handlers itself.
Breaks whenThe fault is one only Linux can resolve (an EPT fault, a page not yet given by Linux), which still exits to the kernel.
Key points
  • "Efficient support for exceptions is important in a variety of use cases such as emulation, debugging, and performance tracing. Normally, reporting an exception to a user program requires privilege mode transitions and an upcall mechanism (e.g., signals). Dune can reduce exception overhead because it uses VT-x to deliver exceptions directly in hardware."
  • "The net result is that software overhead is eliminated and exception performance is determined by hardware efficiency alone. As just one example, Dune improves the speed of delivering page fault exceptions, when compared to SIGSEGV in Linux, by more than 4×. Several other types of exceptions are also accelerated, including breakpoints, floating point overflow and underflow, divide by zero, and invalid opcodes."
  • "Exceptions and privilege modes are implicitly available in VMX non-root mode and do not require any special configuration."
  • Table 3, "trap": "the time it takes for a process to get an exception for a page fault. We compare the latency of a SIGSEGV signal in Linux with a hardware-generated page fault in Dune." Linux 2,821, Dune 587 cycles (4.8×, this guide's arithmetic).
How it works, step by step: two different page faults in a Dune process
  1. A guest page-table fault: the process cleared the present bit or the write bit in its own entry for page V (for a GC barrier). A store to V raises vector 14 in non-root mode. Because the exception is not configured to exit (general knowledge: the VMCS exception bitmap), the CPU vectors through the process's IDT to its ring 0 handler, with the faulting address in %CR2. 587 cycles to get there.
  2. The handler (libDune's exception routines, then the application's) records the event, sets the write bit, and executes IRET. Raising a permission needs no INVLPG: a stale read-only entry can only cause one more fault, and x86 drops the faulting translation when it delivers a page fault (general knowledge; M11). Write-protecting a page again later does need INVLPG. No kernel code runs.
  3. An EPT fault: the process's entry is fine but the guest-physical page has no EPT entry. This is not a guest exception at all; it is a VM exit handled by the module and Linux (M7), costing 5,093 cycles for a fresh page.
  4. Other vectors (breakpoint 3, divide error 0, invalid opcode 6, floating-point errors) follow the same in-process path as step 1 (paper lists them; vector numbers are general knowledge).
Assumptions it relies on
  • A1. The process installs a valid IDT, stacks and handlers before faulting (stated: libDune "loads an IDT so that hardware exceptions can be captured" and "sets up a separate stack in the TSS to handle double faults").
  • A2. Exceptions the kernel needs (for example, those caused by host interrupts) still exit (stated).
  • A3. Applications want exceptions often enough that 2,234 saved cycles each matter (stated use cases: emulation, debugging, tracing, GC, Appel and Li).
If an assumption changes
  • A1 changes (a broken handler or stack): a fault inside the handler becomes a double fault on the TSS's separate stack; if that also fails, a triple fault, which in non-root mode causes a VM exit rather than a machine reset (general knowledge), so only the process dies (inference).
  • A2 changes: without exiting host interrupts, a process with a bad IDT could hang a core (M4).
  • A3 changes (rare exceptions): no gain, and the process still pays M20's costs.
Design notes and rejected alternatives

The alternative is a faster signal path in the kernel (the paper cites Azul's kernel changes that let "hardware exceptions ... bypass the kernel and be handled directly by usermode"). Dune gets the same effect with no kernel change other than loading the module. The paper names SIGSEGV as the main signal "largely" subsumed by hardware page faults.

Connections

Exokernel: Aegis dispatches exceptions to application-level handlers through a minimal kernel path; Dune removes even that path by letting the hardware dispatch inside the guest (general knowledge of Exokernel; inference connecting them). Livelock: the cost difference is the per-event cost of crossing into the kernel, the same overhead the Livelock paper fights for interrupts (inference).

M10 · Privilege rings inside a process

TL;DR
ProblemA process cannot protect part of itself from another part; kernel/user separation exists only between the process and the kernel.
MechanismNon-root mode "maintains its own set of privilege rings": trusted code runs at ring 0, untrusted code at ring 3, supervisor-only page-table entries hide ring 0's memory, and SYSCALL from ring 3 "trap[s] to the process itself, rather than to the kernel".
Trade-offHardware-enforced isolation and system-call interposition at trap cost (180 cycles to intercept, 1,091 to intercept and forward), in exchange for writing kernel-style code (handlers, argument validation) inside the application.
Breaks whenMore than one level of nesting is needed, or the ring 0 code trusts pointers from ring 3.
Key points
  • "On x86, the most important privilege modes are ring 0 (supervisor mode) and ring 3 (user mode), although rings 1 and 2 are also available. Two motivating use cases for privilege modes are privilege separation and sandboxing of untrusted code, both evaluated in this paper."
  • "Dune can support privilege modes efficiently because VMX non-root mode maintains its own set of privilege rings. Hence, Dune allows hardware-enforced protection within a process in exactly the way kernels protect themselves from user processes. The supervisor bit in the page table is available to control memory isolation."
  • "Moreover, system call instructions trap to the process itself, rather than to the kernel, which can be used for system call interposition and to prevent untrusted code from directly accessing the kernel. Compared to ptrace in Linux, we show that Dune can intercept a system call with 25× less overhead."
  • Section 4: "user code runs in ring 0. Despite changing the behavior of certain instructions, this does not typically result in any incompatibilities for existing code. Ring 3 is also available and can optionally be used to confine untrusted code."
  • Section 6.2: intercepting without forwarding, "PTRACE_SYSEMU is 13,592 cycles. In Dune this can be implemented by handling the hardware system call trap directly, with a latency of just 180 cycles. This reveals that most of the Dune ptrace benchmark overhead was in fact forwarding the getpid system call via a VMCALL rather than intercepting the system call."
  • Section 8: "the hardware that Dune exposes can only support a single level instead of the multiple levels available in Fluke."
How it works, step by step: ring 3 code makes a system call
  1. Untrusted code at ring 3 executes SYSCALL for open. The CPU switches to ring 0 and jumps to the address in MSR_LSTAR, which in a Dune process is read-only and still holds Linux's entry address; libDune has mapped its own handler at that guest-virtual address (M12).
  2. The stack: SYSCALL does not switch stacks (general knowledge), so the ring 0 handler starts with ring 3's stack pointer and must load a trusted stack before using it, for example from per-thread data found through the GS base that libDune configures (inference).
  3. Policy: the runtime checks the call and its arguments (180 cycles is the paper's cost of this trap with no forwarding).
  4. Forward: if allowed, the runtime executes VMCALL to run Linux's open (about 900 more cycles; 1,091 total for getpid), then returns to ring 3 with SYSRET or IRET.
  5. Memory: while ring 3 runs, every page of the runtime is marked supervisor-only in the process's page table, so ring 3 loads and stores to it fault into the runtime's page-fault handler.
Assumptions it relies on
  • A1. Ring 3 can reach ring 0 only through traps the ring 0 code controls (hardware; implicit).
  • A2. The ring 0 code marks all of its memory supervisor-only and validates every pointer ring 3 passes (stated for the sandbox: "validating each system call argument").
  • A3. One level of separation is enough (stated against Fluke).
  • A4. Running ordinary application code at ring 0 is harmless (stated: "does not typically result in any incompatibilities").
If an assumption changes
  • A1 changes: any ring 3 path to ring 0 (a writable IDT, a writable page table) would hand the untrusted code the whole process; the page-table pages and IDT must themselves be supervisor-only (inference).
  • A2 changes (an unchecked pointer): the runtime, running at ring 0, can write any page; a ring 3 read whose buffer points into the runtime would make Linux overwrite the runtime's memory, the "corrupt or disable the sandbox runtime" case the paper guards against.
  • A3 changes (a sandbox inside a sandbox): rings 1 and 2 exist, but with 64-bit paging the supervisor bit separates only ring 3 from rings 0 to 2 (general knowledge), so the extra rings give no memory isolation from ring 0 (inference); the paper says only "a single level".
  • A4 changes (code that relies on ring 3 behavior): for example, privileged instructions that would fault in ring 3 now succeed, so a program that probes for them gets different results (inference from "changing the behavior of certain instructions").
Design notes and rejected alternatives

The alternatives the paper lists for sandboxing are ptrace, kernel modifications, binary translation (Vx32) and binary verification (Native Client); each pays a kernel or software cost on every interposed event. Using the CPU's own ring check is the reason interception costs 180 cycles. Section 4 also describes libDune's redirection: "a mechanism that can detect when a system call is performed from ring 0 and automatically redirect it to the kernel as a hypercall."

Connections

x86 VMM (hwsw): a binary-translating VMM confines guest kernel code in software at some cost per instruction; Dune's sandbox confines untrusted code with hardware rings at cost per trap (inference). Exokernel / SPIN: SPIN runs extensions in the kernel with language safety; Dune's sandbox runs untrusted code below trusted code in one process with hardware rings (inference).

M11 · Page tables, TLB control and PCID in the process's hands

TL;DR
ProblemUser-level virtual-memory techniques (checkpointing, GC, compression paging, distributed shared memory) pay a system call for each protection change and get no access to accessed/dirty bits or TLB control.
MechanismPage-table entries are ordinary memory the process writes: translations, permissions, global bits, accessed/dirty bits. The process issues its own INVLPG, decides when to flush, and switches among page tables with PCID-tagged %CR3 writes.
Trade-offAbout 7× faster on Appel and Li's benchmarks and batched invalidation, in exchange for the application taking responsibility for TLB consistency.
Breaks whenThe application gets TLB consistency wrong, for example a stale entry on another core of a multithreaded process (inference).
Key points
  • "Dune improves virtual memory access by exposing page table entries to user programs directly, allowing them to control address translations, access permissions, global bits, and modified/accessed bits with simple memory references. In contrast, even the most efficient OS interfaces [17] add extra latency by requiring system calls in order to perform these operations." ([17] is AVM, application-level virtual memory, by Engler, Gupta and Kaashoek.)
  • "Dune also gives user programs the ability to manually control TLB invalidations. As a result, page table updates can be performed in batches when permitted by the application. This is considerably more challenging to support in the kernel because it is difficult to defer TLB invalidations when general correctness must be maintained."
  • "Dune exposes TLB tagging by providing access to Intel's recently added process-context identifier (PCID) feature. This permits a single user program to switch between multiple page tables efficiently."
  • "using Dune results in a 7× speedup over Linux in the Appel and Li user-level virtual memory benchmarks [5]. This figure includes the use of exception hardware to reduce page fault latency."
  • Section 3.5: "virtual memory requires access to the %CR3 register, which can be granted in the VMCS"; "we allow user programs to disable paging because it is the only method available on x86 to clear global TLB entries."
  • Table 3: appel1 ("TRAP, PROT1, and UNPROT ... 100 protected pages are accessed, causing faults. Then, in the fault handler, the faulting page is unprotected, and a new page is protected") 701,413 → 94,496 cycles; appel2 ("PROTN, TRAP, and UNPROT ... 100 pages are protected. Then each is accessed, with the fault handler unprotecting the faulting page") 684,909 → 94,854.
How it works, step by step: one appel1 iteration
  1. Per iteration on Linux: 701,413 / 100 ≈ 7,014 cycles: a SIGSEGV delivery (2,821 from Table 3), an mprotect to unprotect the page, an mprotect to protect another, and sigreturn, so roughly 4,200 cycles for the three system calls together (this guide's arithmetic, assuming the "trap" figure applies inside the benchmark).
  2. Per iteration in Dune: 94,496 / 100 ≈ 945 cycles: the hardware fault into the process's handler (587), then two page-table entry writes, an INVLPG for the protected page, and IRET, together about 358 cycles (this guide's arithmetic; the steps are inferred, the paper does not list them).
  3. Why unprotect needs no flush (general knowledge): raising permissions leaves at worst a stale more-restrictive TLB entry, which faults again and is then refilled; lowering permissions (protect) must invalidate, or the old writable entry would let the write through.
  4. Ratios: 701,413 / 94,496 = 7.4×; 684,909 / 94,854 = 7.2×; the paper rounds to 7×.
Assumptions it relies on
  • A1. The application knows when a stale TLB entry is harmless and can therefore batch or skip invalidations (stated: "when permitted by the application").
  • A2. TLB invalidations the process issues cover every core that might hold the entry (implicit; INVLPG is local to one core, general knowledge).
  • A3. The CPU supports PCID (stated as "recently added").
  • A4. Global bits set by the process cannot leak translations to other processes (implicit; entries are also tagged by VPID, M15).
If an assumption changes
  • A1 changes (the application flushes too little): a write to a page it believes is protected succeeds through a stale entry, silently breaking a GC write barrier (inference).
  • A2 changes (a multithreaded Dune process on several cores): after one thread protects a page and runs INVLPG, another core can still write through its cached entry. A kernel would send an inter-processor interrupt (a TLB shootdown); Dune exposes no IPI instruction, so the other thread must be reached some other way, for example a signal by hypercall (inference). The paper's page-table utilities are "not yet thread-safe."
  • A3 changes (no PCID): each page-table switch flushes the non-global TLB entries; Wedge's context switch would lose its main advantage (M18).
  • A4 changes (no VPID): nothing leaks, because without VPID the hardware itself flushes the TLB, global entries included, on every VM entry and exit (general knowledge of VT-x); the cost moves instead to a TLB refill after every hypercall (M15).
Design notes and rejected alternatives

The paper's argument for batching is that in the kernel "it is difficult to defer TLB invalidations when general correctness must be maintained", while an application knows its own invariants. On the "disable paging" exception: in 64-bit mode paging cannot be turned off without leaving long mode, and toggling CR4.PGE is the usual way to flush global entries (both general knowledge); the paper does not explain how a 64-bit Dune process uses this, which presumably reflects what its mirrored CR4 allows (inference; see Reference → inconsistencies).

Connections

Exokernel: the paper's reference [17], AVM, is the Exokernel group's application-level virtual memory; Dune gets the same control without a new kernel. Superpages: the process can set the page-size bit in its own entries, so the superpage policy decisions of that paper become application decisions, but the EPT's page size remains Linux's choice (inference). Hints: "Don't hide power": the TLB is exposed, not wrapped (inference).

M12 · Control registers, MSRs, MSR_LSTAR and the TSC: what is mirrored, locked or raw

TL;DR
ProblemExposing every privileged register would let a process break its own environment (a 64-bit process disabling long mode) or make each transition slower (saving and restoring many MSRs).
MechanismMirror the kernel's control-register settings, with two exceptions (paging may be disabled; some floating-point control). Disallow MSR writes except FS and GS base. Make MSR_LSTAR read-only. Expose the TSC raw. One VMCS per process (per thread in the implementation).
Trade-offA normal process environment and cheap transitions, in exchange for a process that cannot reconfigure the CPU like a real kernel can.
Breaks whenAn application needs a register Dune locks (its own syscall entry address, performance-counter MSRs, cache control).
Key points
  • "We maintain a separate VMCS for each process in order to allow for per-process configuration of privileged state and to support context switching more easily and efficiently."
  • "x86 includes a variety of control registers that determine which hardware features are enabled (e.g., floating point, SSE, no execute, etc.) Although we could have permitted Dune processes to configure these directly, we instead mirror the configuration set by the kernel. This allows us to support a normal process environment; permitting many configuration changes would break compatibility with user programs. For example, it makes little sense for a 64-bit process to disable long mode."
  • Two exceptions: "we allow user programs to disable paging because it is the only method available on x86 to clear global TLB entries. Second, we give user programs some control over floating point hardware in order to allow for support of lazy floating point state management."
  • "Dune does not allow modification to MSRs in order to avoid the relatively high overhead of saving and restoring them during each system call. The FS and GS base registers are exceptions because they are not only used frequently but are also saved and restored by hardware automatically."
  • "MSR LSTAR, which contains the address of the system call handler, is a special case where Dune allows read-only access. This allows a user process to map code for a system call handler at the existing address (by manipulating its page table) instead of changing the register to a new address and, as a result, harming performance."
  • "Dune exposes raw access to the time stamp counter (TSC). By contrast, most VMMs virtualize the TSC in order to avoid confusing guest kernels, which tend to make timing assumptions that could be violated if time spent in the VMM is made visible."
How it works, step by step: what each register access does

  1. Why LSTAR read-only helps: if a process could write LSTAR, the module would have to restore Linux's value on every VM exit (and the process's on entry), adding an MSR save/restore to every system call. Instead the process reads LSTAR and maps its own handler at that guest-virtual address, which is free because guest-virtual addresses near Linux's kernel addresses are unused by the process (inference about why that range is free).
  2. Why the raw TSC is fine: a Dune process is not a kernel keeping time; the hypercall gap shows up as elapsed time, which is the truth (inference).
Assumptions it relies on
  • A1. Ordinary programs need the kernel's CPU configuration, not their own (stated).
  • A2. MSR save/restore on transitions is expensive enough to avoid (stated: "relatively high overhead").
  • A3. No exposed register lets the process affect anything outside itself (implicit; M4).
If an assumption changes
  • A1 changes (a program wants a feature the kernel disabled): it cannot enable it; Dune is not a way to change CPU configuration.
  • A2 changes (cheap MSR switching in hardware): more MSRs could be exposed, for example performance-monitoring controls for user-level profiling (inference).
  • A3 changes (an MSR with global effect, such as one controlling power or a shared cache): exposing it would break the threat model, which is one reason a blanket "no MSR writes" rule is safer than a list (inference).
Design notes and rejected alternatives

The paper describes these as performance and compatibility choices, not security ones: "In some cases, Dune restricts access to hardware registers for performance reasons." Rejected: letting the process configure control registers freely ("would break compatibility with user programs") and changing LSTAR ("harming performance").

Connections

x86 VMM (hwsw): a VMM running a guest OS must virtualize the TSC and every control register the guest kernel touches; Dune can expose the raw TSC because there is no guest kernel to confuse (inference). ESX: ESX virtualizes time and device state for guests; Dune keeps all of that in Linux (inference).

M13 · System calls through VMCALL

TL;DR
ProblemInside non-root mode, SYSCALL goes to the process's own ring 0, not to Linux, yet the process must keep every Linux service.
MechanismSystem calls are made with VMCALL; the module "vectors hypercalls through the kernel's system call table," with extra work for a few calls (cleanup on exit). libDune redirects a ring 0 SYSCALL to a hypercall; an optional modified libc issues VMCALL directly.
Trade-offThe whole Linux interface is preserved unchanged, in exchange for a VM exit per call (757 extra cycles on getpid) and the rule that pointer arguments must be host-virtual.
Breaks whenThe process's guest-virtual addresses differ from host-virtual ones for a buffer it passes to Linux, or the workload is dominated by short system calls.
Key points
  • "Normal system call invocation instructions will only trap within the process itself and do not cause a VM exit. Instead, processes must use VMCALL, the hypercall instruction, to make system calls. The Dune module vectors hypercalls through the kernel's system call table. In some cases, it must perform extra actions before calling the system call handler. For example, during an exit system call, Dune performs cleanup tasks."
  • "To simplify supporting this change, we provide a mechanism that can detect when a system call is performed from ring 0 and automatically redirect it to the kernel as a hypercall." "We also provide an optional, modified version of libc that uses VMCALL instructions instead of SYSCALL instructions in order to get a slight performance benefit."
  • "One unanticipated challenge with working in a Dune environment is that system call arguments must be valid host-virtual addresses, regardless of how guest-virtual mappings are setup. In many ways, this parallels the need to provide physical addresses to hardware devices that perform DMA. In most cases we can work around the issue by having the guest-virtual address space mirror the host-virtual address space. For situations where this is not possible, walking the user page table to adjust system call argument addresses is necessary."
  • Section 6.1: "For system calls, the time spent in the kernel tends to be a larger cost than the fixed VMX mode transition costs."
How it works, step by step: three ways a Dune process reaches Linux, and an argument that needs fixing
  1. Unmodified libc in ring 0: read() executes SYSCALL; the CPU enters the handler libDune mapped at LSTAR's address; libDune sees the call came from ring 0 and issues VMCALL with the same registers. Two transitions: one in-process trap and one VM exit.
  2. Modified libc: read() executes VMCALL directly. One VM exit: the "slight performance benefit."
  3. Ring 3 code in a sandbox: its SYSCALL goes to the runtime's ring 0 handler, which validates and then issues VMCALL (M17): 1,091 cycles for getpid end to end (Table 3).
  4. An argument that does not mirror: suppose a GC has aliased a buffer at guest-virtual 0x6000_0000_0000 (outside every region) whose page maps to the guest-physical page of host-virtual 0x7EFF_8000_1000 (illustrative). read(fd, 0x6000_0000_0000, 4096) passed straight through would make Linux write to host-virtual 0x6000_0000_0000, which is unmapped there, so the call fails with EFAULT or, worse, hits a different mapping. libDune must walk its page table: 0x6000_0000_0000 → guest-physical 0x1_8000_1000 → host-virtual 0x7EFF_8000_1000, and pass that.
  5. A buffer that crosses a page boundary in such an alias may map to two non-adjacent host-virtual pages; one Linux call cannot express that, so it must be split or copied (inference).
Assumptions it relies on
  • A1. Guest-virtual mirrors host-virtual for any memory passed to the kernel (stated as the usual workaround).
  • A2. Kernel work per call is larger than the transition cost (stated for typical calls).
  • A3. Linux's system-call handlers work correctly when called from the module's exit handler instead of the normal entry path (implicit; "extra actions" for some calls).
If an assumption changes
  • A1 changes: every pointer argument, including pointers inside structures (an iovec array for readv, a msghdr), needs translation, like a driver translating addresses for DMA (paper's analogy; the nested-pointer cases are inference).
  • A2 changes (null or very short calls): getpid is 6.5× slower; gettimeofday-style calls that Linux normally serves in user space without entering the kernel (the vDSO, general knowledge) would be unaffected only if the vDSO page is mapped in the process's page table (inference).
  • A3 changes (a call that depends on the entry path, such as one that manipulates the caller's register frame): the module needs special handling, which is what "extra actions" refers to; the paper names only exit.
Design notes and rejected alternatives

Making SYSCALL itself exit to Linux was not an option the paper considers, and it would remove the in-process trap that makes interposition cheap (M10). The paper contrasts its hypercalls with paravirtualization: there the guest kernel calls VMM services; here "the hypercall mechanism invokes normal Linux system calls."

Connections

Exokernel: a library OS reaches the exokernel through a small set of primitive calls; a Dune process reaches Linux through the whole ordinary system-call table (inference). NFS: argument translation here resembles marshaling: the callee interprets addresses in its own name space, so the caller must convert them (inference, loose).

M14 · Signals as injected hardware interrupts

TL;DR
ProblemLinux delivers signals by writing a frame onto the user stack and jumping to a handler, which assumes a normal ring 3 process; a Dune process has its own rings and IDT.
MechanismFaults the process can see directly need no signal ("hardware page faults largely subsume the role of SIGSEGV"); other signals (for example SIGINT) arrive as "fake hardware interrupts" the module injects, handled through the process's IDT.
Trade-offEfficient delivery that composes with rings (ring 3 code is lifted to ring 0 to handle it), in exchange for a non-standard signal API (dune_signal instead of signal/sigaction).
Breaks whenUnmodified code relies on sigaction semantics, or the process has interrupts masked when a signal arrives.
Key points
  • "Dune completely changes how signal handlers are invoked. Some signals are obviated by more efficient direct hardware support. For example, hardware page faults largely subsume the role of SIGSEGV. For other signals (e.g., SIGINT), the Dune module injects fake hardware interrupts into the process."
  • "This is not only an efficient mechanism, but also has the advantage of correctly composing with privilege modes. For example, if a user process were running in ring 3 to sandbox untrusted code, hardware would automatically transition it to ring 0 in order to service the signal securely."
  • Section 4.2: "we have not fully integrated support for signals despite the fact that they are reported by the Dune module. Applications are required to use dune_signal whereas a more compatible solution would override several libc symbols like signal and sigaction."
How it works, step by step: Ctrl-C while sandboxed code runs at ring 3
  1. Linux marks SIGINT pending for the thread. The thread is running in non-root mode; at its next VM exit (a timer interrupt guarantees one), the module sees the pending signal.
  2. Injection: the module sets the VMCS's VM-entry interruption field to an interrupt vector chosen for signals and re-enters the guest (the mechanism is general knowledge of VT-x; the paper says only "injects fake hardware interrupts").
  3. Delivery: the CPU, now in the guest at ring 3, takes the interrupt through the process's IDT. Because the handler is a ring 0 gate, the CPU switches to ring 0 and to the ring 0 stack in the TSS (general knowledge), so untrusted code never sees or controls the handler's stack.
  4. Handling: libDune's interrupt routine calls the handler registered with dune_signal, then returns with IRET to ring 3.
  5. If the process had executed CLI at ring 0: a VMM may inject an external interrupt only when the guest's interrupt flag is set, so delivery waits until the process re-enables interrupts (general knowledge of VT-x; the paper does not discuss it).
Assumptions it relies on
  • A1. The process has installed an IDT entry and handler for the signal vector (implicit; libDune sets up the IDT).
  • A2. Applications can be changed to use dune_signal (stated as the current limitation).
  • A3. The process eventually exits to the module so pending signals are noticed (implicit; timer interrupts exit).
If an assumption changes
  • A1 changes: an injected interrupt with no valid gate causes a general-protection fault inside the guest, then a double fault (inference).
  • A2 changes (unmodified binaries using sigaction): handlers registered with Linux are never called the normal way; the paper's fix is to override libc's signal functions.
  • A3 changes: without host-interrupt exits, a spinning Dune process would never see its signals; SIGKILL, which Linux handles itself, would also be delayed (inference).
Design notes and rejected alternatives

Linux's frame-on-the-stack delivery is rejected because it would run the handler at whatever ring the process was in; injecting an interrupt makes the hardware pick the privileged handler and stack, which is the "securely" in the paper's sentence.

Connections

Exokernel: Aegis delivers exceptions and interrupts to application-level handlers with the application saving its own state; Dune's injected interrupt is the same idea built from VMM event injection (general knowledge of Exokernel; inference). Mesa: an asynchronous signal handler at ring 0 interrupts whatever the process was doing, the same reentrancy hazard Mesa's monitors address for interrupt handlers (inference, loose).

M15 · The module's implementation: KVM code, a VMCS per thread, VPIDs

TL;DR
ProblemBuild the module without changing Linux, cheaply enough to run thousands of Dune processes, and with fast transitions.
MechanismA loadable module (2,509 lines) reusing KVM's low-level VT-x code; one VMCS per thread; a VPID per Dune process so hypercalls and context switches need no TLB flush; MMU notifiers for EPT upkeep.
Trade-offSmall, deployable and light, in exchange for implementation limits: Intel 64-bit only, conservative accessed/dirty reporting, and no nested use inside a VM.
Breaks whenThe CPU is AMD, the process is 32-bit, or swap performance matters (M7).
Key points
  • "Dune presently supports Linux running on Intel x86 processors in 64-bit long mode. Support for AMD CPUs and 32-bit mode are possible future additions. In order to keep changes to the kernel as unintrusive as possible, we developed Dune as a dynamically loadable kernel module."
  • "Our implementation is based partially on KVM [30]. Specifically, it shares code for managing low-level VT-x operations. However, high-level code is not shared with KVM because Dune operates differently from a VMM. Furthermore, our Dune module is simpler than KVM, consisting of only 2,509 lines of code."
  • "it was easiest for us to create a VMCS for each thread instead of merely each process. One interesting consequence is that it is possible for both threads using Dune and threads not using Dune to belong to the same process."
  • "Our implementation is capable of supporting thousands of processes at a time. The reason is that processes using Dune are substantially lighter-weight than full virtual machines. Efficiency is further improved by using virtual-processor identifiers (VPIDs). VPIDs enable a unique TLB tag to be assigned to each Dune process, and, as a result, hypercalls and context switches do not require TLB invalidations."
How it works, step by step: Linux switches between two Dune processes on one core
  1. Process A's thread is preempted by a timer interrupt: VM exit to the module, which returns to Linux's normal interrupt path; the scheduler picks process B's thread.
  2. Before running B, the current VMCS on this core is switched to B's (with VMPTRLD; KVM handles this with scheduler hooks, general knowledge). A's VMCS keeps A's guest state for later.
  3. VM entry into B: B's VPID differs from A's, so the TLB entries A left behind are not used for B and need not be flushed; when A runs again, its entries may still be there.
  4. Hypercall in B: the VM exit to Linux and back does not flush B's entries either, because Linux's own entries carry VPID 0 (general knowledge).
  5. Scale: VPID is a 16-bit field (general knowledge), so up to 65,535 distinct tags, comfortably more than "thousands".
Assumptions it relies on
  • A1. KVM's low-level VT-x code can be reused without its VMM logic (stated).
  • A2. The hardware supports VPID (implicit).
  • A3. Per-thread VMCS is cheap enough for thousands of threads (stated as an outcome).
If an assumption changes
  • A1 changes: Dune would have to carry its own VMX setup code, likely larger than 2,509 lines (inference).
  • A2 changes (no VPID): every VM entry and exit flushes the TLB (general knowledge for VT-x without VPID), so every system call would also cost a TLB refill; with 86.4-cycle walks this could multiply the hypercall cost (inference).
  • A3 changes: a VMCS occupies a 4 KB region (general knowledge), so 10,000 Dune threads cost about 40 MB of VMCS memory, small on a 16 GB machine (this guide's arithmetic).
Design notes and rejected alternatives

The paper says per-process VMCS is the design (Section 3.5) and per-thread is the implementation (Section 3.7), chosen because Linux threads are nearly processes. Note that the paper attributes the tagged TLB both to PCID (inside a process, Section 2.2) and to VPID (between processes and across hypercalls, Section 3.7); they are different tags for different switches.

Connections

x86 VMM (hwsw): first-generation VT-x had no VPID, so each exit flushed the TLB, part of why exits were expensive there (general knowledge); Dune relies on the later feature. Hints: reusing KVM's VT-x layer and Linux's system-call table is "use a good idea again" (inference).

M16 · libDune and bootstrapping: entering Dune is like booting an OS

TL;DR
ProblemAfter the transition the process is at ring 0 with nothing set up: no page table it built, no IDT, no stacks for faults. Writing that by hand is kernel programming.
MechanismlibDune, a 5,898-line library untrusted by the kernel: it builds the initial page table for the compressed layout, enters via ioctl, then loads a GDT, IDT, TSS (with a double-fault stack) and GS base; it also provides a page-table manager, ELF loader, page allocator and exception and system-call helpers.
Trade-offDune applications become "application programming, not kernel programming", in exchange for x86-specific code in the application and some missing pieces (signals, thread safety).
Breaks whenSeveral threads manipulate the page table at once, or unmodified code expects standard signal APIs.
Key points
  • "libDune is a library created to make it easier to build user programs that make use of Dune. It is completely untrusted by the kernel and consists of a collection of utilities that aid in managing and configuring privileged hardware features. Major components of libDune include a page table manager, an ELF loader, a simple page allocator, and routines that assist user programs in managing exceptions and system calls. libDune is currently 5,898 lines of code."
  • "In many ways, transitioning a process into Dune mode is similar to booting an OS. The first issue is that a valid page table must be provided before enabling Dune. A simple identity mapping is insufficient because, although the goal is to have process addresses remain consistent before and after the transition, the compressed layout of the EPT must be taken into account."
  • "After a page table is created, the Dune entry ioctl is called with the page table root as an argument. The Dune module then switches the process to Dune mode and begins executing code, using the provided page table root as the initial %CR3. From there, libDune configures privileged registers to set up a reasonable operating environment. For example, it loads a GDT to provide basic flat segmentation and loads an IDT so that hardware exceptions can be captured. It also sets up a separate stack in the TSS to handle double faults and configures the GS segment base in order to easily access per-thread data."
  • Limitations (Section 4.2): signals not fully integrated (dune_signal); "although we support pthreads, some utilities in libDune, such as page table management, are not yet thread-safe"; system-call arguments must be host-virtual (M13); "libDune currently provides an x86-centric API, so it is already compatible with AMD machines."
How it works, step by step: why the page table must exist first
  1. The instant of entry: the next instruction is fetched by guest-virtual address through the new %CR3. If the code page were not mapped, the very first fetch would fault, and there is no IDT yet to handle it.
  2. Which mapping: the code's virtual address (say 0x40_1000 in the code region) must map to the guest-physical slot the module will translate back to host-virtual 0x40_1000 (code region slot 0 makes this 0x40_1000 → 0x40_1000, illustrative); the stack page and any mmap'd data similarly map to slots 2 and 1 (M8).
  3. Before the IDT exists, any exception triple-faults; in non-root mode that is a VM exit, not a reset (general knowledge), so a bootstrap bug kills only the process (inference).
  4. The double-fault stack: a separate stack in the TSS means that even if the current stack is unusable (for example, a stack overflow into an unmapped page), the double-fault handler still has somewhere to run (general knowledge of x86 interrupt stacks).
Assumptions it relies on
  • A1. libDune knows the compressed layout the module uses (stated, implicitly shared by both).
  • A2. Bugs in libDune can harm only the process (stated: "completely untrusted by the kernel").
  • A3. One thread manipulates page tables at a time (stated as a current limitation).
  • A4. Applications accept an x86-specific API (stated).
If an assumption changes
  • A1 changes (the module's layout changes): every libDune build must match; this is an ABI between the module and an untrusted library (inference).
  • A2 changes: it does not; that is the point of putting this code in an untrusted library rather than in the module.
  • A3 changes (multithreaded allocation): two threads updating one page table without locking can lose entries; the paper says this "could be resolved with further implementation."
  • A4 changes (ARM): libDune would need "an efficient architecture independent interface", which the paper leaves to future work.
Design notes and rejected alternatives

Putting this logic in the kernel module would make the module larger and trusted; putting it in an untrusted library keeps the trusted part at 2,509 lines. The modified libc is optional, which keeps unmodified binaries runnable through the ring 0 SYSCALL redirection.

Connections

Exokernel: libDune is a small library OS over exposed hardware, sitting beside Linux rather than replacing it (inference). Hints: keeping the trusted module small and moving policy into an untrusted library follows "keep basic interfaces stable" and "leave it to the client" (inference connecting the papers).

M17 · The sandbox: a trusted runtime at ring 0, an untrusted binary at ring 3

TL;DR
ProblemConfine native 64-bit Linux binaries (memory and system calls) cheaply, without kernel changes or binary rewriting.
MechanismRuntime at ring 0 with its pages supervisor-only; binary at ring 3 in the same address space; system calls and privileged operations trap to the runtime, which validates arguments and forwards allowed calls by VMCALL; the binary is loaded by ld-linux.so running inside the sandbox.
Trade-off2.9% average SPEC2000 overhead (within 0.1% of Linux with large pages) and under 2% on lighttpd, in exchange for portability (needs VT-x and the module) and incomplete system-call coverage (most single-threaded programs).
Breaks whenThe binary is TLB-miss heavy with 4 KB pages (mcf 20.9%), multithreaded, or uses system calls the runtime does not yet validate.
Key points
  • "The sandbox enforces security through privilege modes by running a trusted sandbox runtime in ring 0 and an untrusted binary in ring 3, both operating within a single address space ... Memory belonging to the sandbox runtime is protected by setting the supervisor bit in appropriate page table entries. Whenever the untrusted binary performs an unsafe operation such as trying to access the kernel through a system call or attempting to modify privileged state, libDune receives an exception and jumps into a handler provided by the sandbox runtime."
  • Two ELF loaders: "the sandbox runtime uses a minimal ELF loader (part of libDune), that only supports static binaries, to load a second ELF loader into the untrusted environment. We choose to use ld-linux.so as our second ELF loader because it is already used as an integral and trusted component in Linux. Then, the sandbox runtime executes the untrusted environment, allowing the second ELF loader to load an untrusted binary entirely from ring 3. Thus, even if the untrusted binary is malicious, it does not have a greater opportunity to attack the sandbox during ELF loading than it would while running inside the sandbox normally."
  • "For system call filtering, a large concern is to prevent execution of any system call that could corrupt or disable the sandbox runtime. We protect against this hazard by validating each system call argument, checking to make sure performing the system call would not allow the untrusted binary to access or modify memory belonging to the sandbox runtime. We do not yet support all system calls, but we support enough to run most single-threaded Linux applications."
  • Policies: a "null policy that allows system calls to pass through but still validates arguments" (used for all measurements) and a "userspace firewall" that inspects bind and connect. Extension: a checkpointing system "approximately 450 SLOC with 50 of those being enhancements to the sandbox loader"; the firewall "around 200 SLOC with half of that being the firewall rules parser."
  • Results: SPEC2000 "averaging only 2.9% percent slower than Linux"; mcf 20.9% and ammp 10.1% "explained by EPT overhead"; with 2 MB pages in both tables, sandbox and Linux (also with large pages via libhugetlbfs) "nearly identical (within 0.1%)". lighttpd: "less than 2% for both the latency and throughput test"; VMware Player "67% for the latency test and 77% for the throughput test".
How it works, step by step: what the runtime must check for read(fd, buf, n)
  1. Trap: ring 3 executes SYSCALL; the runtime's handler runs at ring 0 (M10).
  2. Range check: [buf, buf + n) must not overlap any runtime page. If it did, Linux (writing at host-virtual buf) would overwrite the runtime: the "corrupt or disable the sandbox runtime" attack. With buf pointing 16 bytes before a runtime page and n = 4096, the call must be refused even though buf itself is untrusted memory (illustrative).
  3. Calls that change mappings (mmap, mprotect, munmap) must not touch runtime ranges either; a munmap of the runtime would "disable" it (inference about which calls need checks; the paper says "each system call argument").
  4. Forward: VMCALL with the same arguments, which are valid host-virtual addresses because the sandbox keeps guest-virtual equal to host-virtual (M13).
  5. Cost at the application level: lighttpd 2,236 → 2,206 requests/s with 1 client (1.3%) and 24,609 → 24,255 with 100 clients (1.4%) (this guide's arithmetic on Table 4).
Assumptions it relies on
  • A1. Every route from ring 3 to the outside passes through the runtime: system calls trap, privileged instructions fault, runtime memory is supervisor-only (stated).
  • A2. Argument validation is complete for every supported call (stated as the defense).
  • A3. The untrusted program is single-threaded (stated: "most single-threaded Linux applications").
  • A4. ld-linux.so can run unprivileged inside the sandbox (stated: it loads the binary "entirely from ring 3").
If an assumption changes
  • A1 changes (a page-table page or the IDT left writable at ring 3): the binary could rewrite its own permissions and take over ring 0 (inference).
  • A2 changes (one unchecked call): the classic system-call-interposition pitfalls apply (the paper cites Garfinkel's "Traps and Pitfalls" [21] in related work): a missed argument or a nested pointer lets the binary make Linux write into the runtime.
  • A3 changes (multithreaded binary): a second ring 3 thread could change a buffer after the runtime checked it and before Linux used it, a time-of-check-to-time-of-use race (inference; the paper says "nothing prevents supporting multi-threaded programs in the future").
  • A4 changes: the runtime would need its own dynamic loader at ring 0, putting complex header parsing back into trusted code, which is what the two-loader design avoids.
Design notes and rejected alternatives

Compared alternatives (Section 8): ptrace (27,317 cycles per interposed call versus Dune's 1,091), kernel modifications, binary translation (Vx32), binary verification (Native Client: "an average SPEC2000 overhead of 5% with a worst case performance of 12%"). Dune claims to be "the first system to support sandboxing entirely through user-level access to hardware protection." Native Client "is more portable than Dune because it does not require virtualization hardware or kernel changes."

Connections

x86 VMM (hwsw): VMware Player's 67 to 77% lighttpd loss is a hardware-assisted VMM paying for two network stacks, the device-emulation cost Dune avoids by being a process (inference). Exokernel: downloading untrusted code into a protection domain (Exokernel's ASHs, SPIN's extensions) versus running it in ring 3 of the same process (inference).

M18 · Wedge on Dune: sthreads recycled with dirty bits, switched with tagged TLBs

TL;DR
ProblemPrivilege separation per request (for example, one compartment per web client) needs isolation like fork at a cost like a thread.
Mechanismsthreads with their own page tables and system-call policies; created by recycling a checkpoint taken while pristine, restoring only pages whose dirty bits are set; switched without TLB flushes thanks to tagged TLBs; policies enforced with ring protection.
Trade-offCreation 81 → 2 µs (40×), context switch 0.49 → 0.15 µs (3×), web request 454 → 362 µs (20%), in 750 lines of user code; the guarantee depends on the restore covering every bit of state.
Breaks whenAn sthread can change state the recycler does not restore, or requests are long enough that creation cost does not matter.
Key points
  • "Wedge [10] is a privilege separation system. Its core abstraction is an sthread which provides fork-like isolation with pthread-like performance. An sthread is a lightweight process that has access to memory, file descriptors and system calls as specified by a policy."
  • "Fast creation can be achieved through sthread recycling. Instead of creating and killing an sthread each time, an sthread is checkpointed on its first creation (while still pristine and unexploited) and restored on exit so that it can be safely reused upon the next creation request. Doing so reduces sthread creation cost to the (cheaper) cost of restoring memory."
  • "Ring protection is used to enforce system call policies; page tables limit what memory sthreads can access; dirty bits are used to restore memory during sthread recycling; and the tagged TLB is used for fast context switching."
  • Table 5 (µs): create fork 81, Dune sthread 2; context switch 0.49 and 0.15; http request 454 and 362. "In Dune sthreads are created 40× faster than processes and the context switch time is 3× faster. In previous Wedge implementations sthread creation was 12× faster than fork with no improvement in context switch time [9]. Dune is faster because it can leverage the tagged TLB and avoid kernel calls to create sthreads."
  • Code size: "The original Wedge implementation consisted of a 700-line kernel module and a 1,300-line library." A userspace-only version was "a very complicated 5,000-line implementation" because "POSIX did not offer adequate APIs for memory and system call protection." On Dune: "only 750 lines of user code."
How it works, step by step: where the 92 µs saved per web request come from
  1. Total saving: 454 − 362 = 92 µs per request, 20.3% (Table 5; this guide's arithmetic).
  2. Creation: 81 − 2 = 79 µs of it, if each request creates one compartment.
  3. Switching: 0.49 − 0.15 = 0.34 µs per switch; even 10 switches per request would explain only 3.4 µs (illustrative count).
  4. Remainder: about 9 to 13 µs is not explained by Table 5's microbenchmarks; plausible sources are the kernel work of tearing down a forked process (exit, wait) and copy-on-write faults after fork, which recycling avoids (inference).
  5. Cycles: 0.15 µs × 3.3 GHz ≈ 495 cycles per sthread switch; 0.49 µs ≈ 1,617 cycles per process switch (this guide's arithmetic).
Assumptions it relies on
  • A1. The checkpoint is taken "while still pristine and unexploited" (stated).
  • A2. Dirty bits identify every page that may have changed (implicit: the hardware sets them on every write through the sthread's page table).
  • A3. All non-memory state (registers, descriptors, policy) is also restored (stated as "state").
  • A4. The CPU has PCID-style tags so switching sthread page tables needs no flush (stated as "tagged TLB").
If an assumption changes
  • A1 changes (checkpoint taken after handling input): an exploit present at checkpoint time would be restored into every later sthread, so recycling would spread it (inference).
  • A2 changes (a page written through a second mapping, or by Linux on the sthread's behalf through a system call): a kernel write to a buffer goes through Linux's page table, not the sthread's, so the sthread's dirty bit is not set (inference); the recycler must treat system-call output buffers as dirty or restore them anyway. The paper does not discuss this.
  • A3 changes (a file descriptor opened during a request is left open): the next user's request inherits it, a cross-user leak (inference).
  • A4 changes (no tagged TLB): context switch returns to process-like cost, as in "previous Wedge implementations ... with no improvement in context switch time."
Design notes and rejected alternatives

Rejected: fork per request ("the system call used today to implement privilege separation") and the earlier Wedge implementations (a kernel module, or a 5,000-line user-only version). Note which tag does the work: sthreads live inside one Dune process, so VPID (one per process) cannot distinguish them; switching between sthreads' page tables uses PCID (inference from Sections 2.2 and 3.7; the paper says only "tagged TLB").

Connections

Rethink the Sync: both restore a known earlier state cheaply, there by speculation and rollback of output, here by restoring dirty pages from a checkpoint (inference, loose). Mesa / threads: sthreads invert the thread default, isolation first and sharing by policy (inference). ESX: restoring from a pristine snapshot by copying only changed pages is the same idea as copy-on-write snapshots (inference).

M19 · The garbage collector: Boehm GC with fast faults, single-page flushes, and hardware dirty bits

TL;DR
ProblemCollectors use memory protection for read and write barriers and need to know which pages were written; on Linux that means mprotect plus SIGSEGV, and Linux gives "no user-level access at all to dirty bits."
MechanismThree Boehm GC ports: a direct port (protection by page-table writes, faults handled in hardware), a TLB version (single-page INVLPG instead of full flushes), and a dirty-bit version (no protection at all; read the hardware dirty bits).
Trade-off10.9 to 23.8% (TLB) and 26.4 to 40.7% (dirty) shorter run times, in exchange for EPT walk cost that can outweigh the gains when the program collects little.
Breaks whenThe program allocates about as much as its heap and so rarely collects: the XML parser runs 19.0%, 12.2% and 0.2% slower.
Key points
  • Features GCs want: "Fast faults", "Dirty bits", "Page table" (free the frame but keep the virtual page to catch stale references; remap to reduce fragmentation), "TLB control" ("mapping manipulations can be effectively batched").
  • "A direct port to Dune already gives a performance improvement because mprotect can directly manipulate the page table and a page fault can be handled directly without needing an expensive SIGSEGV signal. The GC manipulates single pages 90% of the time, so we were able to improve performance further by using the INVPLG instruction to flush only a single page instead of the entire TLB. Finally, in Dune, the Boehm GC can access dirty bits directly without having to emulate this functionality." ("INVPLG" is the paper's typo for INVLPG.)
  • Lines changed: "The direct port required changing 52 lines, the TLB optimized version 91 lines, and the dirty bit version 82 lines."
  • "Other than the XML Parser, the TLB version improves performance between 10.9% and 23.8%, and the dirty bit version between 26.4% and 40.7%." XML: "a slowdown under Dune for all three versions: 19.0%, 12.2% and 0.2% slower ... This appears to be caused by EPT overhead, as the benchmark does not create enough garbage to benefit". With "ten 150MB XML files as input, the dirty bit version of the Boehm GC showed a 12.8% improvement in execution time over the baseline."
  • Azul's C4 kernel changes (fast faults, batched page tables with a prepare/commit API, shatter/heal of large pages, freeing physical frames under live virtual pages): "All of the above techniques and interfaces can be implemented efficiently on top of Dune, with no need for any kernel changes other than loading the Dune module."
How it works, step by step: one incremental collection with each port
  1. Linux baseline: to learn which pages the program writes between collections, Boehm write-protects the heap with mprotect; the first write to each page raises SIGSEGV (2,821 cycles to deliver), the handler records the page and calls mprotect to unprotect it.
  2. Direct port: the same algorithm, but "mprotect" is a page-table write and the fault is a hardware exception to the process (587 cycles); every flush is a full TLB flush; every TLB miss costs a two-dimensional walk.
  3. TLB port: because 90% of manipulations touch one page, use INVLPG for that page and keep the rest of the TLB, saving refills (each refill is now 86.4 cycles, M20).
  4. Dirty-bit port: no protection and no faults: clear the dirty bits in the page table after a collection, and at the next collection read them to find written pages. The hardware does the tracking.
  5. Why the XML parser loses: 10 collections over 1,753 MB allocated with a 1,737 MB heap, so there is little GC work to accelerate while every TLB miss over a 1.7 GB heap pays the EPT walk. If all of the direct port's 1,267 ms loss were walk cost at 50.6 extra cycles per miss, that would be 1,267 ms × 3.3 GHz / 50.6 ≈ 83 million extra misses in 7.9 s, about 10 million per second (this guide's arithmetic, an upper-bound reading).
Assumptions it relies on
  • A1. The workload collects often enough that faster barriers and dirty tracking outweigh EPT walk cost (stated through the XML counterexample).
  • A2. Most page manipulations touch one page (stated: 90%).
  • A3. The hardware dirty bit in the process's page table records every write the GC must know about (implicit).
  • A4. The collector runs in one thread, or handles cross-core TLB consistency itself (implicit; Boehm supports parallel collection, but the paper does not say whether the measurements used it).
If an assumption changes
  • A1 changes: XML parser case: up to 19% slower. The paper's fix is more garbage (ten files), which turns the result into a 12.8% gain; large pages for the heap would attack the walk cost directly (inference, by analogy with the sandbox).
  • A2 changes (bulk remapping, as in a compacting collector): batched updates with one full flush become better than many INVLPGs; Dune allows either, which is the "batched page table" point in the Azul list.
  • A3 changes (writes by the kernel into the heap, such as read() into a heap buffer): Linux writes through its own page table, so the process's dirty bit for that page may stay clear and the GC would miss a pointer stored there (inference). Linux's own mprotect-based scheme has the matching problem: the kernel's write would fail with EFAULT instead of faulting (general knowledge of Boehm's caveats).
  • A4 changes (parallel marking threads on several cores): stale writable TLB entries on other cores can let writes skip the barrier (M11).
Design notes and rejected alternatives

The original two Boehm options were "(i) utilizing mprotect and signal handlers to implement its own dirty bit tracking; or (ii) utilizing OS provided dirty bit read methods such as the Win32 API call GetWriteWatch." OS interfaces are not always a good match: "SunOS examines the entire virtual address space rather than permit queries for a particular region." Azul instead modified the kernel and its system-call interface.

Connections

Superpages: the Azul "shatter/heal" item is superpage demotion and promotion under application control, which Dune makes possible in the process's page table (inference connecting the papers). LFS / F2FS: dirty tracking to limit what must be rescanned parallels tracking dirty segments to limit cleaning (inference, loose). vLLM: freeing a physical frame while keeping a virtual mapping that traps is the hardware version of vLLM's block-table indirection (inference).

M20 · The cost model, measured: VM-exit cost and two-dimensional walks

TL;DR
ProblemRunning in non-root mode costs something; the question is how much and when it matters.
MechanismTwo sources: "VT-x increases the cost of entering and exiting the kernel", and "using the EPT makes TLB misses more expensive". Measured with getpid, a fresh-page fault, and a random-page walk tool; mitigated with 2 MB pages.
Trade-offFixed overheads (757 cycles per hypercall, 2,406 per kernel-handled fault, 50.6 per TLB miss) in exchange for the in-process speedups of Table 3.
Breaks whenShort system calls dominate, or the working set is large with poor locality and pages are 4 KB.
Key points
  • "First, VT-x increases the cost of entering and exiting the kernel" (then, in the same sentence) "VM entries and VM exits are more expensive than fast system call instructions or exceptions. As a result, both system calls and other types of faults (e.g., page faults) must pay a fixed cost in Dune. Second, using the EPT makes TLB misses more expensive because, in some cases, the hardware page walker must traverse two page tables instead of one."
  • Methods: "For system calls, we manually performed getpid, an essentially null system call (worst case for Dune), and measured the round-trip latency. For page faults, we measured the time it took to fault in a pre-zeroed memory page by the kernel. Finally, for page table walks, we measured the time spent filling a TLB miss."
  • Walk tool: "a random page-aligned walk across 216 memory pages. This models a workload with poor memory locality, as nearly every memory access results in a last-level TLB miss. We then divided the total number of cycles spent waiting for page table walks, as reported by a performance counter, by the total number of memory references."
  • Interpretation: "the time spent in the kernel tends to be a larger cost than the fixed VMX mode transition costs"; page faults "tend to occur infrequently"; for EPT, "For applications with good memory locality or a small working set, it has no impact ... However, for application with poor memory locality or a large working set, more frequent TLB misses result in a measurable slowdown. One effective strategy for limiting this overhead is to use large pages."
  • Large pages: "We then adjusted the sandbox to avoid EPT overhead by backing large memory allocations with 2MB large pages, both in the EPT and the user page table. Supporting this optimization was straightforward because we were able to intercept mmap calls and transparently modify them to use large pages. Such an approach does not cause much memory fragmentation because large pages are only used selectively."
How it works, step by step: sizing the walk benchmark and its result
  1. Footprint: 216 pages × 4 KB = 256 MB. A last-level TLB of 512 entries (typical for this generation, general knowledge) covers 2 MB, so a random page access misses about 99% of the time.
  2. Leaf entries: 65,536 page-table entries × 8 bytes = 512 KB of guest PTEs, plus a similar amount of EPT leaf entries, which fit in the processor's 8 MB last-level cache (cache size general knowledge), so walks mostly hit in cache. This is why the cost is tens of cycles, not hundreds.
  3. Result: 35.8 → 86.4 cycles, +50.6 per miss, a 2.4× ratio. A program that misses once per 100 cycles of useful work would slow by about 50.6 / (100 + 35.8) ≈ 37%; once per 1,000 cycles, about 4.9% (this guide's arithmetic, illustrative miss rates).
  4. With 2 MB pages in both tables: TLB reach grows 512× and the worst-case walk shrinks from 24 to 15 references; SPEC2000 sandbox and Linux (both with large pages) are "within 0.1%".
Assumptions it relies on
  • A1. getpid is the worst case for system calls (stated).
  • A2. The random walk isolates walk cost (stated method), and real programs miss far less often (implicit).
  • A3. Large pages can be applied transparently to large allocations (stated, via mmap interception in the sandbox).
If an assumption changes
  • A1 changes: calls that block (a read that sleeps) also pay a VMCS switch when the thread is rescheduled, which getpid never exercises (inference).
  • A2 changes (graph or pointer-chasing workloads): mcf's 20.9% is the measured example.
  • A3 changes (memory that must stay 4 KB, such as pages the GC protects individually): the GC's per-page protection and large pages conflict, which may be why the GC ports were not combined with large pages (inference).
Design notes and rejected alternatives

The paper chose to report worst cases (null system call, random walk) alongside best cases (Table 3). Section 7 lists hardware fixes it would like: proposed two-dimensional walk accelerations [2, 8], an EPT with full address width, and lower exit and entry latency, while noting "VMX transition costs had only a small effect on the performance of the applications we evaluated."

Connections

Superpages: the same remedy, with the same caution about fragmentation ("only used selectively"). x86 VMM (hwsw): that paper's lesson that hardware virtualization moves costs into exits and page-table handling is visible here as two fixed overheads (inference). Livelock: a per-event fixed cost that is negligible at low rates and dominant at high rates is the Livelock shape (inference).

L · Stated limitations and future work

What the paper itself says is unfinished
  • Needs VT-x; "cannot be used inside a VM unless there is support for nested VT-x"; that configuration's performance is "an interesting topic of future consideration."
  • Intel, 64-bit long mode only; "Support for AMD CPUs and 32-bit mode are possible future additions."
  • No efficient detection of EPT accessed/dirty status; pages are always reported "as modified and accessed during MMU notifications."
  • Only three 4 GB regions are mapped; "incompatibilities in programs that use nonstandard portions of the address space"; a packing scheme or a full-width EPT would remove this.
  • libDune: signals require dune_signal; page-table management "not yet thread-safe"; system-call arguments must be host-virtual; "x86-centric API".
  • Sandbox: not all system calls supported; "most single-threaded Linux applications"; multithreading possible in the future.
  • Unexposed features: cache control ("only be effective if CPU affinity could be controlled"), MONITOR/MWAIT, debug registers, direct device access through the IOMMU and SR-IOV.
  • Other architectures: ARM's virtualization extensions (a Hyp mode under the guest kernel, a System MMU comparable to the EPT, software state save), Itanium, Power.
  • Only one extra level of privilege, unlike Fluke's nesting.
What the evaluation does not cover (this guide's list)
  • Multithreaded or multicore Dune workloads, and the TLB-consistency questions they raise (M11).
  • Memory pressure and swapping, where the conservative accessed/dirty reporting would matter (M7).
  • fork/exec-heavy workloads, signal latency, and blocking system calls (only getpid is measured).
  • Large pages for the GC benchmarks, where the XML parser's EPT cost might disappear.
  • Any security evaluation of the sandbox (no attacks attempted, no audit of argument validation), and who may open /dev/dune.
  • Comparison with KVM or with in-kernel filtering mechanisms; the only VMM measured is VMware Player, on lighttpd and SPEC (SPEC numbers for VMware are described as "very similar drops" without data).
  • Variance: all tables give averages with no spread or run counts.

S · Dune beside Exokernel (the 11/10 reading)

Dune's related work names Exokernel first (citing the 1995 SOSP paper), and the Exokernel paper assigned on 11/10 (Kaashoek et al., SOSP 1997, on Xok/ExOS for x86; David Mazières is an author of both papers) contains the precise problem Dune solves. Xok could not let applications write x86 page tables: "since the hardware does not verify that the physical page of a translation can be mapped by a process, applications are prevented from directly modifying the page table and must instead use system calls" (Exokernel paper), batching those calls to amortize them. C · Connections to the other CS240 papers (mechanical only)

  • x86 VMM (hwsw): Dune runs on the hardware-assisted side of that paper's comparison, with the later additions (EPT, VPID) that removed shadow paging and per-exit TLB flushes; and it avoids the remaining exit sources by not emulating a machine (M1, M2, M15).
  • ESX: ESX's pmap and Dune's EPT are both a second translation owned by the hypervisor layer; ESX must reclaim guest memory blindly (ballooning, sharing), while Dune's EPT follows Linux's own memory management through MMU notifiers (M5, M7).
  • Exokernel (11/10): see S; Xok's x86 page-table restriction is exactly what the EPT lifts. The paper's reference [17], AVM, is from the same group (M11).
  • Superpages: TLB reach matters more when a miss costs 86.4 instead of 35.8 cycles; Dune's remedy is selective 2 MB pages in both tables, with the same fragmentation caution (M2, M20).
  • Livelock: host interrupts always exit, and every system call pays a fixed transition cost, the per-event overhead pattern that paper analyzes (M1, M20).
  • Hints: "Don't hide power" (expose the TLB and page tables), "use a good idea again" (VT-x for processes; KVM's code; Linux's system-call table), and "keep it simple" (a small trusted module, an untrusted library) (inference).
  • vLLM (11/19): PagedAttention keeps a software block table over memory it owns; Dune lets a process keep a hardware page table over memory it owns (M6, M19).
  • LFS / F2FS: tracking dirty units to bound later work (cleaning segments there, rescanning or restoring pages here) (M18, M19, inference).
  • Rethink the Sync: cheap restoration of a known state (sthread recycling) parallels that paper's speculation and rollback, loosely (M18).
  • Salus (11/17): Salus builds fine-grained GPU sharing in a user-level service because GPUs lack hardware sharing primitives; Dune is the case where the CPU already has the primitive (VT-x) and the work is exposing it (inference, loose).
  • Mesa, Eraser: Wedge's sthreads take the opposite default from shared-memory threads: isolation first, sharing by policy, which removes the data races Eraser looks for between compartments (inference).
  • NFS, Leases, FFS: no mechanical link beyond keeping an existing interface (the process ABI) while changing what is under it.

Problem 1 · easy
A Dune process does each of the following. Which ones cause a VM exit? (a) touches a page it write-protected in its own page table; (b) executes LIDT; (c) executes VMCALL for write; (d) the host timer interrupt fires; (e) first touch of a page it just mmapped; (f) executes INVLPG.
Show answer
(c), (d) and (e). (a) is a guest page fault delivered through the process's own IDT; (b) and (f) are privileged instructions that run directly in non-root mode (Table 1). (c) is a hypercall, (d) is an interrupt meant for the kernel ("timer interrupts ... will still cause a VM exit"), and (e) has no EPT entry yet, so it is an EPT fault, a type of VM exit.Misconception: that every page fault in a Dune process goes to the kernel. Only faults the EPT cannot satisfy do; faults in the process's own page table never leave the process.
Problem 2 · easy
How long is a getpid in Dune and on Linux at 3.3 GHz, and how many null system calls per second would cost one full core of extra time in Dune?
Show answer

Extra 757 cycles per call; one core supplies 3.3 × 109 cycles per second, so 3.3 × 109 / 757 ≈ 4.4 million calls per second would consume a whole core in transitions alone.Misconception: that the VM exit cost is a percentage. It is a fixed cost per crossing; how much it matters depends only on how often the program crosses.
Problem 3 · easy
A Dune process can write %CR3 and any page-table entry it likes. Why can it still not read another process's memory?
Show answer
Its page table produces only guest-physical addresses, and the hardware then translates them through the EPT, which only the kernel writes and which the module fills from Linux's own mappings for this process. A guest-physical address with no EPT entry causes an EPT fault; Linux has no mapping for another process's memory in this process, so no entry is created.Misconception: that controlling %CR3 means controlling physical memory. Under the EPT, %CR3 and every page-table pointer are guest-physical.
Problem 4 · medium
A sandboxed program at ring 3 executes SYSCALL for getpid. List the transitions until it gets its answer, and estimate the cycles.
Show answer
(1) SYSCALL traps from ring 3 to the runtime's handler at ring 0 of non-root mode (no VM exit); (2) the runtime checks the call; (3) VMCALL exits to the module, which runs Linux's getpid; (4) VM entry back to the runtime; (5) return to ring 3. Problem 5 · medium
A Dune process calls fork(). In which mode does the child run, what is its page table, and what does it need to do to use Dune?
Show answer

Problem 6 · medium
Using the illustrative layout (code/data/heap in guest-physical 0 to 4 GB, mmap region in 4 to 8 GB with window [0x7EFF_0000_0000, 0x7F00_0000_0000), stack in 8 to 12 GB), what guest-physical address does host-virtual 0x7EFF_C000_0000 get? What happens to a mapping at 0x7EFE_8000_0000?
Show answer

Problem 7 · medium
Wedge's sthread context switch is 0.15 µs instead of 0.49 µs "because TLB flushes are avoided by using the tagged TLB." The module gives each Dune process a VPID. Is VPID the tag that helps here?
Show answer
No. All sthreads live inside one Dune process, which has one VPID, so VPID cannot tell their translations apart. Problem 8 · medium

Show answer

Problem 10 · hard
The sandbox runtime's pages start at guest-virtual 0x5000_0000. Untrusted code calls read(fd, 0x4FFF_FFF0, 4096). It also calls mmap(0x5000_0000, 4096, PROT_READ|PROT_WRITE, MAP_FIXED|MAP_ANONYMOUS, ...). What must the runtime do with each, and why?
Show answer
Refuse both (or rewrite them). The read buffer starts in untrusted memory but its last 4,080 bytes fall inside the runtime; Linux writes through its own page table at host-virtual addresses and does not see the supervisor bit in the process's page table, so it would overwrite the runtime. The MAP_FIXED mapping would replace the runtime's page with a fresh zero page. These are the "corrupt or disable the sandbox runtime" cases the paper's per-argument validation exists for.Misconception: that supervisor-only pages protect the runtime from everything. Problem 11 · hard
A multithreaded Dune process has threads on cores 0 and 1 sharing one page table. Thread 0 clears the write bit for page P and executes INVLPG P. Thread 1, which wrote P a moment ago, writes it again. Does the write fault?
Show answer
Not necessarily. INVLPG invalidates the entry only in core 0's TLB (general knowledge); core 1 may still hold a writable translation and complete the store without a fault. A kernel would send an inter-processor interrupt so core 1 runs its own invalidation (a TLB shootdown). Dune exposes no IPI, so thread 0 would have to reach thread 1 another way, for example by a signal sent by hypercall and delivered as an injected interrupt, and wait for it. The paper says libDune's page-table management is "not yet thread-safe".Misconception: that a TLB invalidation is global. It is per core, and owning the page table makes shootdowns the application's job.
Problem 12 · hard
Under memory pressure, Linux's reclaim looks for pages that have not been accessed recently and avoids writing back clean pages. What does Dune's current choice to "always report pages as modified and accessed during MMU notifications" do to a Dune process with a large, mostly idle, file-backed mapping?
Show answer
Every page looks recently accessed, so reclaim cannot tell idle pages from hot ones and ages the Dune process's pages poorly; and every page looks dirty, so even clean file pages are written back before being dropped, adding I/O. Correctness is kept (nothing modified is lost) at the cost of reclaim quality and extra writes. The paper says hardware support for EPT accessed/dirty bits should fix it.Misconception: that a conservative answer is free. "Assume dirty" is always correct but turns reclaim of clean pages into writes.
Connecting outward

What Dune teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

Split translation into a protection layer and a policy layer

Dune's EPT says only "which frames may this process touch, with what rights"; the process's own page table says "how do I want to arrange them." That split lets an untrusted party exploit a device's properties without being trusted with the device. The same structure fits any proposal that exposes memory-device asymmetries (read/write cost, endurance, persistence) to software: let the upper layer choose placement and remapping, and keep a lower, privileged mapping that bounds what it can name. Dune also shows the condition for it to work: the lower layer must be kept exactly coherent with the real owner's view (MMU notifiers), or it becomes a hole.

Every translation layer is paid for on the miss path

Two page tables turn a 4-reference walk into up to 24 and a measured 35.8 into 86.4 cycles; mcf loses 20.9% and a 1.7 GB-heap program 19%. Any extra indirection between the CPU and memory (a device-side remap table, a tiered-memory translation, a second-level IOMMU table) has the same signature: invisible when the TLB hits, dominant when the working set outruns it. The fix is also the same: larger mapping units in every layer at once, applied selectively to avoid fragmentation.

Hardware access tracking beats protection-fault tracking

The Boehm GC's biggest win (26.4 to 40.7%) came from reading the dirty bits the MMU already sets, instead of write-protecting pages and taking a fault on the first write. Hot/cold page classification for tiering, write tracking for checkpoints and incremental persistence, and wear accounting all face the same choice. Dune's own limitation is the mirror image: because it could not read EPT accessed/dirty bits, it reported every page as accessed and dirty, which is correct but blinds the kernel's reclaim. Whoever cannot see the access bits must assume the worst.

A fixed crossing cost decides where work should live

757 cycles per hypercall is negligible for read on a socket and ruinous for a stream of null calls. The paper's design follows directly: put frequent, small operations (faults, protection changes, TLB invalidations, system-call interception) inside the process, and let only infrequent, heavy ones cross. The same arithmetic governs batching flushes and fences to persistent memory, or doorbells to a device: amortize a fixed cost by moving the frequent path to the side of the boundary that does not pay it.

Address widths do not match across layers, and someone must compress

A 48-bit virtual space had to be squeezed into 36 bits of guest-physical space, so Dune mapped three 4 GB windows and made everything else unreachable. Memory systems hit the same mismatch whenever a device or interconnect exposes a smaller window than the space that uses it (host-managed device memory windows, address decoders, small on-device remap tables). Dune's two options are the general ones: fixed windows (simple, with hard caps) or packing arbitrary regions and telling the upper layer where they went (flexible, with more bookkeeping).

Expose hardware without inventing a new OS

Exokernel moved the OS into libraries to give applications control; Dune kept Linux and gave a process one slice of the hardware. For research that wants the OS to see device characteristics, Dune is a template for prototyping without a kernel fork: a small module that owns the safety-critical mapping, an untrusted library for the rest, and an unchanged system-call interface for everything that does not need to change.

C1 · SYSCALL does not switch stacks: what stack does the sandbox runtime start on?

In the sandbox, untrusted code at ring 3 executes SYSCALL and lands in the runtime's ring 0 handler at the address in MSR_LSTAR. But SYSCALL, unlike an interrupt, does not load a new stack pointer. So the trusted handler's first instruction runs with a stack pointer the attacker chose, maybe pointing into the runtime's own data. How does the runtime avoid using that stack, and why does an injected signal not have the same problem?

AnswerWork it out first, then open▾

On x86-64, SYSCALL saves the return address in %rcx and the flags in %r11 and changes privilege, but leaves %rsp untouched (general knowledge). The handler must therefore not push anything until it has loaded a trusted stack pointer from somewhere ring 3 cannot change. Linux does this with SWAPGS and a per-CPU area; libDune's setup that "configures the GS segment base in order to easily access per-thread data" gives the runtime the same kind of anchor (the exact code is not in the paper).

Interrupts and exceptions are different: when a ring 0 gate is taken from ring 3, the CPU loads the ring 0 stack pointer from the TSS before pushing anything (general knowledge). That is why libDune loads a TSS, why it keeps "a separate stack in the TSS to handle double faults", and why the paper can say an injected signal makes "hardware ... automatically transition it to ring 0 in order to service the signal securely."

Where the answer comes from: x86 semantics of SYSCALL and interrupt gates (general knowledge, stated as such), applied to Sections 4.1, 3.6 and 5.1.

C2 · Table 1 exposes CLI. Can a Dune process disable interrupts and keep the CPU?

Table 1 lists STI and CLI among the instructions a Dune process may execute. A kernel that runs CLI and spins owns the core. The paper says a Dune process cannot monopolize the CPU because "timer interrupts and other exceptions intended for the kernel will still cause a VM exit." How is that true after the process has cleared its interrupt flag, and what does its CLI actually mask?

AnswerWork it out first, then open▾

The guest's interrupt flag only governs interrupts delivered to the guest. With VT-x's external-interrupt exiting enabled, a physical interrupt (the host timer, a NIC) causes a VM exit regardless of the guest's flag (general knowledge of VT-x), so Linux's handler and scheduler run and can preempt the thread.

What CLI does mask is what Dune injects: the "fake hardware interrupts" used for signals such as SIGINT. A VMM may inject an external interrupt only when the guest's interrupt flag is set, so the module must hold the signal until the process re-enables interrupts (general knowledge of VT-x; the paper does not discuss it). SIGKILL is unaffected because Linux handles it itself at the next exit.

Where the answer comes from: Section 2.2's statement about timer interrupts, Table 1, Section 3.6 on injected interrupts, and VT-x's interrupt-exiting and injection rules (general knowledge).

C3 · Which tag makes Wedge's context switch 3× faster: VPID or PCID?

Section 3.7 says the module gives each Dune process a VPID so that "hypercalls and context switches do not require TLB invalidations." Section 6.3.2 says sthread switches are fast because "TLB flushes are avoided by using the tagged TLB." But Wedge's sthreads all run inside one Dune process. Which tag is actually doing the work in Table 5's 0.15 µs, and what would happen to that number on a CPU with VPID but no PCID?

AnswerWork it out first, then open▾

PCID. All sthreads share the process's single VPID, so VPID cannot keep their translations apart. Switching sthreads means loading a different page table into %CR3, which the process can do without a VM exit (access to %CR3 "can be granted in the VMCS"); with a PCID in %CR3, the other sthread's entries stay in the TLB (Section 2.2: PCID "permits a single user program to switch between multiple page tables efficiently").

Without PCID, every sthread switch would flush the process's non-global entries, and the switch would approach the process-switch cost of 0.49 µs plus refills at 86.4 cycles each, which is what "previous Wedge implementations ... with no improvement in context switch time" saw. VPID still matters for the other half: a hypercall from an sthread does not flush its entries.

Where the answer comes from: Sections 2.2, 3.5, 3.7 and 6.3.2; the conclusion about which tag applies is derived from the fact that sthreads share one process.

C4 · "1.4% worst case" versus "20.9% for mcf": which comparison is the Native Client claim?

Section 6.3.1 reports the sandbox at 2.9% average SPEC2000 slowdown, with mcf at 20.9% and ammp at 10.1%. Section 8 then says Dune achieved "nearly zero average overhead (1.4% worst case) for the same benchmarks" and contrasts it with Native Client's 5% average and 12% worst case. Both cannot describe the same configuration. Which one does Section 8 use, and is the comparison with Native Client like for like?

AnswerWork it out first, then open▾

Against ordinary Linux with 4 KB pages, the worst case is 20.9%.

So the 1.4% number compares Dune against a large-page Linux baseline, while Native Client's published 5% and 12% are against an ordinary build. On the like-for-like 4 KB comparison, Dune's 2.9% average and 20.9% worst case are not obviously better than Native Client's 5% and 12%; with large pages on both sides Dune's sandbox costs almost nothing. The paper's own anecdote that Native Client showed "higher overheads on modern microarchitectures" is unquantified.

Where the answer comes from: Figure 3 read off at high resolution (values approximate), Section 6.3.1's text, and Section 8's sentence.

C5 · 24 references per TLB miss, but only 2.4× the cycles: why, and what changes with 2 MB pages?

A 4-level guest page table under a 4-level EPT needs up to 24 dependent memory reads to fill one TLB miss instead of 4, a factor of 6. Table 2 measures 35.8 versus 86.4 cycles, a factor of 2.4, using a random walk over 216 pages. Why is the measured ratio so much smaller, and how many references would remain if both tables used 2 MB pages?

AnswerWork it out first, then open▾

Most of the 24 reads are to upper-level entries that are shared by every walk: the same few guest top-level entries and the EPT entries that translate them. Processors cache partial walks (paging-structure caches and, for EPT, cached guest-physical translations), so these are rarely fetched from memory (general knowledge). The benchmark's footprint is 216 × 4 KB = 256 MB; its guest leaf entries are 65,536 × 8 B = 512 KB, and the EPT leaves are similar, so even the leaf reads mostly hit the 8 MB last-level cache of the E3-1230 v2 (cache size general knowledge). What is left is roughly one extra leaf-level EPT lookup per miss, about 50 cycles (inference from the measured difference).

With 2 MB pages in both tables, n = m = 3 and the worst case is 3·3 + 3 + 3 = 15 references; and because each TLB entry covers 512 times more memory, misses become far rarer. That combination is why the sandbox with large pages lands "within 0.1%" of Linux with large pages.

Where the answer comes from: Table 2 and the benchmark description in Section 6.1; the walk structure and caching behavior are general knowledge (the analysis in the paper's reference [8]).

C6 · One thread invalidates, another core keeps writing: who does the TLB shootdown?

Dune lets a process control TLB invalidation and batch it, which the paper says a kernel cannot easily do. libDune supports pthreads. Suppose thread A on core 0 write-protects page P in the shared page table (say, a GC write barrier) and executes INVLPG; thread B on core 1 wrote P a microsecond ago and writes it again. Is B's write guaranteed to fault? If not, what does Dune give the process to fix it?

AnswerWork it out first, then open▾

No. INVLPG affects only the TLB of the core that executes it (general knowledge). Core 1 may still hold a writable translation for P and complete the store without consulting the page table, silently bypassing the barrier. A kernel fixes this with a TLB shootdown: an inter-processor interrupt makes every core that might cache the entry invalidate it, and the initiator waits.

Dune exposes no way to send an IPI (not in Table 1), so a Dune process must reach core 1 indirectly, for example by sending thread B a signal with a hypercall, which the module delivers as an injected interrupt, and waiting for B's handler to run INVLPG; that costs hypercalls and exits, which erodes the benefit of user-level control. The paper sidesteps the issue: libDune's page-table utilities "are not yet thread-safe", and the sandbox supports "most single-threaded Linux applications."

Where the answer comes from: x86 TLB semantics (general knowledge), Table 1, Section 3.6 on signals, and Section 4.2's thread-safety limitation; the workaround is this guide's inference.

C7 · The dirty-bit GC and a read() into the heap: does the collector see the write?

The best GC port "reads the dirty bits directly" from the process's own page table instead of write-protecting pages. Suppose that between two collections the program calls read(fd, buf, 4096) with buf in the heap, and the data read contains a pointer the GC must trace. Does the hardware set the dirty bit in the process's page-table entry for that page?

AnswerWork it out first, then open▾

No. The program's own stores go through its page table (guest-virtual → guest-physical) and the MMU sets the dirty bit there. But read is executed by Linux after a VMCALL, in root mode, writing to buf as a host-virtual address through Linux's page table. The process's page-table entry is never used, so its dirty bit stays clear (general knowledge of how dirty bits are set; the paths are from Sections 3.4 and 3.6).

So a dirty-bit collector on Dune must treat buffers passed to system calls as dirty, or wrap such calls. The mprotect-based original has a related problem in a different form: the kernel's write into a protected page fails with EFAULT instead of faulting into the handler (general knowledge of Boehm's virtual-dirty-bit caveats). The paper does not discuss either case.

Where the answer comes from: Mechanics of dirty-bit setting (general knowledge) combined with Dune's two translation paths (Figure 2) and system calls as hypercalls (Section 3.6).

C8 · Disabling paging as "the only method available on x86 to clear global TLB entries": is it, and can a 64-bit process do it?

Section 3.5 says Dune lets processes disable paging "because it is the only method available on x86 to clear global TLB entries." The same section says it "makes little sense for a 64-bit process to disable long mode." Is disabling paging really the only way to flush global entries on x86, and can a process in 64-bit mode turn paging off without leaving long mode?

AnswerWork it out first, then open▾

On x86 generally it is not the only way: toggling the PGE bit in CR4 flushes all TLB entries including global ones, and INVPCID (listed in Table 1) has an all-contexts-including-globals type on CPUs that support it (general knowledge; INVPCID first shipped with Haswell, so the paper's Ivy Bridge test machine could not execute it). And in IA-32e mode, paging cannot be disabled directly: software must first drop to compatibility mode, and clearing CR0.PG then deactivates long mode (general knowledge).

The consistent reading is narrower than the sentence: because Dune mirrors the kernel's control-register settings, a Dune process presumably cannot toggle CR4.PGE, so turning paging off is the only CR-based method left to it, and doing so means briefly leaving 64-bit mode, the very thing the paper calls senseless. A per-page INVLPG also removes a global entry for that page. The paper does not say which of these libDune uses.

Where the answer comes from: Section 3.5's two sentences and Table 1, checked against x86 control-register and long-mode rules (general knowledge); the reconciliation is this guide's inference.

Glossary, results, and provenance

Every term in one place, then where the numbers came from and what this guide found inconsistent in the paper.

Core terms
DuneA system made of a loadable Linux kernel module (2,509 lines) and a user-level library (libDune, 5,898 lines) that runs selected Linux processes in VT-x non-root mode so they can use privileged CPU features directly.
Dune moduleThe kernel module that enables VT-x with Linux in root mode, owns each Dune thread's VMCS and each Dune process's EPT, and handles every VM exit (hypercalls, EPT faults, HLT, interrupts). It reuses KVM's low-level VT-x code.
Dune modeThe irreversible state of a Linux thread after the entry ioctl on /dev/dune: running in VMX non-root ring 0 with its own page table root, IDT and privilege rings, reaching Linux only through VM exits.
Dune processA Linux process with at least one thread in Dune mode; it keeps its pid, file descriptors, signals and shared memory, and differs from a normal process in using VMCALL for system calls.
libDuneAn untrusted user-level library linked into Dune processes: a page-table manager, an ELF loader for static binaries, a page allocator, and exception and system-call helpers, plus the bootstrap code that loads a GDT, IDT and TSS after entry.
VMX root modeThe VT-x operating mode in which the hypervisor (here Linux plus the Dune module) runs; it behaves like an ordinary x86 CPU plus instructions for managing VT-x.
VMX non-root modeThe VT-x operating mode for guests: a full copy of x86 execution, with its own rings 0 to 3, IDT and control registers, in which events chosen in the VMCS force a VM exit to root mode.
VMCSThe in-memory VM control structure for one virtual CPU: guest-state and host-state save areas plus execution controls that select which guest events exit. Dune keeps one per thread.
VM exit / VM entryThe hardware transitions out of and into non-root mode, saving and loading state through the VMCS. A getpid that includes one exit and one entry costs 895 cycles in Dune.
Hypercall (VMCALL)An instruction that deliberately causes a VM exit. In Dune it is the system-call instruction: the module dispatches it through Linux's system-call table.
EPT (extended page table)A page table in Intel's EPT format, written only by root-mode software, that the CPU applies after the guest's page table to translate guest-physical to host-physical addresses. In Dune it mirrors Linux's mappings for the process.
EPT fault (EPT violation)A VM exit raised when a guest-physical address has no EPT entry or lacks the needed permission. Dune uses it to fill the EPT lazily from Linux's page-fault handler.
Guest-virtual / guest-physical addressThe address a Dune process's instructions use, and the address its own page table translates that into; guest-physical is a compressed alias of host-virtual in three 4 GB windows.
Host-virtual / host-physical addressAn ordinary Linux virtual address (used by the kernel, normal processes, and every system-call argument) and a real RAM address.
Two-dimensional page walkThe hardware walk on a TLB miss under nested translation, in which each guest page-table pointer is itself translated through the EPT: up to 24 memory references for 4-level tables in both dimensions.
MMU notifierA Linux kernel callback chain that informs subscribers such as KVM and the Dune module when a process's page mappings are invalidated or aged, so second-level mappings can be updated.
VPIDA 16-bit virtual-processor tag stored in the VMCS and attached to TLB entries, so guest and host translations coexist and VM transitions need no TLB flush. Dune assigns one per Dune process.
PCIDA 12-bit process-context tag held in the low bits of %CR3 and attached to TLB entries, so switching page tables need not flush them. Dune lets processes use it directly.
Sandbox runtimeThe trusted part of Dune's sandbox: code running at ring 0 of the Dune process, with supervisor-only pages, that receives the untrusted binary's system calls and faults and validates them.
sthreadWedge's compartment: a lightweight execution context with its own page table and a policy listing the memory, file descriptors and system calls it may use; on Dune it is recycled from a pristine checkpoint.
Supporting terms
VT-xIntel's hardware virtualization extension to x86: the two VMX modes, the VMCS, the VMX instructions, and features such as EPT and VPID.
SVM / NPTAMD's virtualization extension and its nested page table, the counterparts of VT-x and EPT; not supported by Dune's implementation.
Interpretive executionIBM's mainframe virtualization design, cited as VT-x's model, in which most privileged instructions run directly in hardware against a shadow copy of privileged state instead of trapping.
Type-2 hypervisorA hypervisor that runs on top of a host operating system rather than directly on hardware; the paper says the Dune module could be considered one.
ParavirtualizationA virtualization technique in which the guest OS is modified to call VMM interfaces (hypercalls) that are cheaper than emulating hardware.
Ring 0 / ring 3The x86 supervisor and user privilege levels. In Dune, ordinary application code runs at non-root ring 0, and ring 3 is available for confined code.
IDTThe table of exception and interrupt handler descriptors located by the IDTR register; each entry gives a handler address and privilege level.
GDT / LDTThe global and local descriptor tables that define x86 segments; libDune loads a GDT with flat segments.
TSS (task-state segment)An x86 structure, loaded with LTR, that holds the stack pointers the CPU switches to on interrupts from lower privilege, including separate stacks for faults such as double faults.
Double faultThe exception the CPU raises when delivering one exception causes another; a failure to deliver a double fault is a triple fault, which in non-root mode causes a VM exit.
%CR3The x86 control register holding the physical (in a guest, guest-physical) address of the current top-level page table, plus the PCID when enabled.
INVLPG / INVPCIDInstructions that remove TLB entries: one page's entry on the executing core, or entries for a given PCID (or all contexts).
Global pageA page-table entry with the global bit set, whose TLB entry survives ordinary %CR3 reloads.
TLB shootdownThe procedure by which one core asks others, by inter-processor interrupt, to invalidate a TLB entry after a page-table change.
MSR_LSTARThe model-specific register holding the 64-bit address that SYSCALL jumps to; read-only for Dune processes.
TSCThe time-stamp counter, a per-core cycle counter read with RDTSC; Dune exposes the raw value.
Event injectionA VT-x feature by which the VMM asks the CPU to deliver an interrupt or exception to the guest at the next VM entry; Dune uses injected interrupts for signals.
SIGSEGVThe UNIX signal for an invalid memory access; user-level virtual-memory tricks on Linux receive faults as this signal.
PTRACE_SYSEMUA ptrace mode that stops the traced process at each system call and lets the tracer emulate it without the kernel executing it.
Appel and Li benchmarksMicro-benchmarks from a 1991 paper on virtual-memory primitives for user programs: TRAP (take a protection fault), PROT1/PROTN (protect one or N pages), UNPROT (unprotect one page).
Boehm GCA widely used conservative mark-sweep garbage collector for C and C++ that supports parallel and incremental collection and tracks written pages to limit rescanning.
WedgeA privilege-separation system (Bittau et al., NSDI 2008) that splits an application into sthreads with least-privilege policies.
Native ClientGoogle's sandbox for native x86 code that verifies binaries before running them; reported 5% average SPEC2000 overhead.
libhugetlbfsA Linux library that backs program memory with large (2 MB) pages without changing the program; used for the Linux large-page baseline.
IOMMU / SR-IOVA memory-management unit that translates and checks device DMA addresses, and a PCIe feature that splits one device into several virtual functions; proposed for safe device access from Dune.

Inconsistencies found in the paper

(1) Section 8 claims "nearly zero average overhead (1.4% worst case)" for SPEC2000, while Section 6.3.1 reports a 2.9% average with mcf at 20.9%; the 1.4% figure matches only the sandbox-with-large-pages versus Linux-with-large-pages comparison read off Figure 3, so the contrast with Native Client's 5% and 12% is not like for like. (2) Section 3.5 says disabling paging "is the only method available on x86 to clear global TLB entries", but toggling CR4.PGE and the INVPCID that Table 1 lists also do so, and in 64-bit mode paging cannot be disabled without leaving long mode, which the same paragraph calls senseless for a 64-bit process (general knowledge; the sentence is consistent only as "the only method Dune leaves available"). (3) Section 3.7 assigns VPIDs per process while VMCSs are per thread, and Section 6.3.2 credits "the tagged TLB" for sthread switches inside one process, where only PCID (Section 2.2) can help. (4) "67% for the latency test" for VMware Player is the drop in requests per second with one client; as latency it is 3.05× longer. (5) Table 2's "page fault" (Dune 1.9× slower) and Table 3's "trap" (Dune 4.8× faster) are different events, an EPT fault handled by the kernel versus a guest fault handled by the process; the paper does not point this out. (6) "INVPLG" in Section 5.3 is a typo for INVLPG. (7) The lighttpd slowdowns do not follow from the per-call hypercall cost with the paper's numbers: 27 hypercall-equivalents per request at 1 client and 2.6 at 100 clients (Worked Example ①). (8) "SPEC2000" in Figure 3 is 16 of SPEC CPU2000's 26 benchmarks (the C and C++ ones), which the paper does not state.
