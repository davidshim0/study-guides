DIMES '26 · A Field Guide

Paying for microseconds you rarely need to spend

RDMA-backed swap is 5–7× faster than an NVMe SSD. But it turns out to matter most exactly when your application's SLO is already blown. Here's the plain-English story of why SSD is a serious baseline once you hold performance fixed — and where RDMA still earns its keep.

📄 "RDMA vs. SSD Swap" · Yang, Lepers, Zwaenepoel · DIMES '26 🎓 Basic OS/networking assumed — primers cover the rest ⏱ ~20 min read
💾

Compare swap backends only in the performance-preserving regime — not in the already-degraded regime where the fast backend looks most impressive.

Before you begin

Quick glossary + seven primers

The acronyms first, then the concepts the paper leans on. Skip anything you already know.

Quick glossary

RDMARemote Direct Memory Access — lets one machine read/write another's memory over the network without involving its CPU. Needs InfiniBand or RoCE NICs.
SSD / NVMeSolid-state drive; NVMe is the fast PCIe protocol modern SSDs use. Here it's the local, cheap swap device.
SwapLinux mechanism that evicts cold pages from DRAM to a backing device, fetching them back on a page fault.
SLOService Level Objective — a target like "retain ≥80% of no-offload throughput."
λin / λoutSwap-in / swap-out rate (pages per second) — the paper's model variables.
θ-performance-preservingThe paper's definition: a backend+budget pair that keeps ≥θ fraction of no-offload performance.
PSI / TMOPressure Stall Information / Transparent Memory Offloading — Meta's production system that reclaims memory based on measured application stall, not just memory savings.
SSD-backed swap RDMA-backed swap the model / methodology SLO / performance target
1What "far memory" via swap actually does▾

Instead of every server carrying enough DRAM for its peak, an application's cold pages get evicted to a remote or local device, and transparently fetched back on the next access via the normal page-fault path. No application rewrite needed — that's the whole appeal.

Now you're ready: the only question this paper asks is which device that "backing tier" should be — remote DRAM over RDMA, or a local NVMe SSD.
2The page-fault round trip▾

Touch an evicted page → MMU raises a page fault → kernel fetches the page from the backing device → thread resumes. The fetch latency (SSD read or RDMA read) sits directly on this critical path; that's what Table 2's numbers measure.

Now you're ready: the paper's core variable, DB, is exactly this fetch latency, and it differs hugely between backends.
3RDMA in one sentence▾

RDMA lets a machine read/write another machine's memory directly over the network, bypassing the remote CPU. Over a 100 Gbps InfiniBand link it delivers ~4 μs page reads — but it requires an RNIC, provisioned network, and (usually) a dedicated memory server.

Now you're ready: RDMA-backed swap systems (Infiniswap, Hermit, Mage) exploit this to make "far" memory feel almost local.
4NVMe SSD as a swap device▾

Conventional Linux swap to a local SSD. Slower per page (~27 μs read) but needs no network, no remote server, and costs about 1/25th as much per GiB as DRAM ($0.50 vs $12.3/GiB, per the paper's pricing).

Now you're ready: the paper's central question is whether RDMA's speed advantage is worth that 25× price premium once you look at application-level performance.
5Swap-in vs. swap-out (and why they're treated differently)▾

Swap-in (fetching an evicted page back) blocks the faulting thread — it's on the critical path. Swap-out (reclaim: choosing a victim, writing it back) is mostly asynchronous background work — it costs CPU cycles, not direct stall time, unless the CPU is already saturated.

Now you're ready: this asymmetry is exactly why the paper's model (Eq. 1) treats λin and λout with different cost terms.
6Performance-preserving offloading (θ)▾

A backend+budget is θ-performance-preserving if it keeps ≥θ fraction of the no-offload throughput. The paper mostly uses θ = 0.8 (retain ≥80%), echoing how production systems like TMO gate reclaim on measured application-visible stall, not raw memory saved.

Now you're ready: almost every comparison in this paper is really "how much can each backend offload while staying above the 80% line?" — not "which backend is faster in isolation?"
7Reading the raw numbers (Table 2)▾

SSD 4 KiB read: 27.15 μs avg, 2231 MiB/s. RDMA 4 KiB read: 4.05 μs avg, 11774 MiB/s. That's ~6.7× lower latency and ~5.3× higher bandwidth for RDMA — a large, real gap at the device level.

Now you're ready: the paper's twist is that this large device-level gap doesn't translate proportionally into application-level benefit once swap traffic is kept low enough to preserve SLOs.
The whole story in one place

The finding, compressed

Why RDMA's device-level win doesn't automatically become an application-level win.

RDMA-backed remote DRAM is unambiguously faster than a local NVMe SSD as a raw swap backend: ~6.7× lower read latency, ~5.3× higher bandwidth (Table 2). Under heavy swap traffic — pages being faulted back in constantly — that speed advantage shows up directly in application throughput, sometimes dramatically (RDMA 161% faster than SSD for PMBench-uniform at 20% offload).

But heavy swap traffic is also the regime where transparent offloading has already wrecked performance: at that same 20%-offload point, both backends are running at a tiny fraction of no-offload speed (SSD at 1/95 ≈ 1.05%, RDMA at 1/37 ≈ 2.7%). No real deployment with an SLO would operate there. Once you restrict comparison to the performance-preserving regime (≥80% of baseline), swap-ins become rare, and the paper's simple model explains why the backend gap collapses: the RDMA-vs-SSD benefit scales with the swap-in rate, which is exactly the thing an SLO forces down.

Measured across four workloads, the amount of extra memory RDMA lets you offload while staying above 80% is small for three of them (≤1 percentage point — XSBench specifically goes from 3% to 4%) and meaningful for only one (Spark, +20 points), a workload the paper suggests is unusually sensitive to page-fault latency because JVM garbage collection sweeps large portions of the heap.

🍯 Key takeaways

  • RDMA is 5–7× lower latency, 5–9× higher bandwidth than SSD — at the device level.
  • RDMA's application-level edge grows with swap traffic — but high swap traffic usually means SLOs are already violated.
  • At the 80%-of-baseline line, the RDMA-vs-SSD gap in offloadable memory is small — ≤1 percentage point for PMBench, XSBench (3%→4%), and PageRank — but 20 points for Spark, where GC pressure appears to make it unusually latency-sensitive.
  • The model: gap ≈ λin·(DSSD − DRDMA) — the backend latency gap only matters when multiplied by a swap-in rate that SLOs try to keep near zero.
  • DRAM costs ~25× more per GiB than NVMe SSD ($12.3 vs $0.50) — a premium a small performance gap rarely justifies.
  • Implication: hybrid tiering — cold pages to (pooled) SSD, RDMA reserved for workloads/phases where it demonstrably extends the performance-preserving region.
Five everyday pictures

How to think about the RDMA-vs-SSD gap

Each stands alone. Every card ends with where the picture breaks.

The core finding

Paying for overnight shipping

Overnight shipping is always faster than standard mail. But if you only ever mail things a month in advance, you never notice — the "fast" option only earns its premium the day you're already running late. RDMA is the overnight tier; its value is proportional to how often you're caught needing a page right now, which an SLO deliberately tries to make rare.

Where it breaks: shipping speed doesn't feed back into how often you're late; here, a slow backend feeding more stalls can itself increase how "urgent" future accesses feel (compounding), which the paper's linear model doesn't fully capture.
The model, Eq. 2

A toll lane that only saves time you spend driving

A fast toll lane saves you five minutes per trip — but if you only drive once a month, that's five minutes a month, not a life-changing amount. The savings scale with trip frequency (λin), not just the lane's speed advantage. RDMA's per-fault latency edge (DSSD − DRDMA) only accumulates into something visible when swap-ins happen often.

Where it breaks: toll lanes don't change how many trips you need; heavy paging can itself add secondary costs (TLB shootdowns, reclaim CPU) that the simple multiplication in Eq. 2 sets aside as second-order.
Reframing the comparison

Judging a diet by the crash-day binge

You wouldn't judge two diets by how much damage a single binge day does — you'd compare them on the days you're actually sticking to the plan. Comparing RDMA vs. SSD only under severe memory pressure is like comparing diets on binge days: technically real data, but not the regime anyone intends to live in. The paper insists on comparing "on-plan" — inside the 80%-SLO region.

Where it breaks: unlike a diet, an operator might deliberately accept a "binge day" for a best-effort batch job that can tolerate a big slowdown — RDMA's advantage there is real and legitimate, not a measurement artifact.
Cost, not just speed

Economy vs. first class for a five-minute flight

First class is nicer on every flight, but on a five-minute hop the extra comfort barely registers — while the price difference is enormous. RDMA (remote DRAM) is ~25× the per-GiB cost of an NVMe SSD; the "comfort" (latency edge) is real, but on a workload whose swap-ins are rare, it buys almost nothing per dollar.

Where it breaks: for Spark, the paper suggests the "flight" is genuinely turbulent (GC pressure) — there the comfort difference is large enough that paying for first class (RDMA) is measurably worth it.
The hybrid takeaway

A pantry and a fridge

You don't refrigerate everything — shelf-stable goods sit in the pantry (SSD), perishables that you'll reach for constantly go in the fridge (RDMA/remote DRAM). Most of a working set is "pantry" (cold, rarely revisited); only a hot sliver benefits from the pricier, faster tier. The paper's proposed hybrid design is exactly this split, chosen by page reuse.

Where it breaks: groceries don't change shelf life mid-week; real workloads shift which pages are "hot" over time (phases), so a static cold/hot split needs ongoing reclassification the paper flags as future work.
The full explanation

How the study actually works

Methodology, results, and the model that ties them together.

1 · Measuring the raw gap (Table 2)

4 KiB random reads/writes, direct I/O, measured with fio (SSD) and the perftest RDMA suite (RDMA), on a testbed with a Samsung PM983 NVMe SSD and a 100 Gbps ConnectX-6 InfiniBand link. Result: RDMA read at 4.05 μs vs. SSD at 27.15 μs (6.7× lower latency); 11774 vs. 2231 MiB/s bandwidth (5.3× higher). This confirms RDMA's raw superiority — and sets up the paper's real question: does it survive contact with an SLO?

2 · The memory-pressure sweep

For each of five workloads (PMBench uniform/hotspot, XSBench, PageRank, Spark logistic regression), local DRAM budget is progressively shrunk from the no-offloading baseline, with the rest served by either SSD-backed swap or RDMA-backed swap (via Hermit). Acceptable performance is defined as ≥80% of no-offload throughput — the SLO line used throughout.

3 · Two regimes, one pattern (Table 4)

The trap: the "large gap" regime (bottom row) is exactly the regime an SLO-respecting deployment would never operate in. Evaluating backends only there overstates RDMA's practical value.

4 · The model (Eq. 1 & 2)

L_B ≈ λ_in·(K_fault + D_B) + α·λ_out·K_reclaim + Q_B   # application-visible slowdown

# comparing backends, ignoring second-order Q_B:
L_SSD − L_RDMA ≈ λ_in·(D_SSD − D_RDMA)

λin/λout are swap-in/out rates; Kfault is backend-independent fault overhead; DB is the backend read latency RDMA reduces; Kreclaim is per-page reclaim CPU cost, scaled by α (how much spare CPU is available). The punchline of Eq. 2: RDMA's advantage is the latency gap multiplied by the swap-in rate — small λin (the SLO-preserving regime) mechanically shrinks RDMA's payoff.

6 · Why Spark is the exception

Spark's logistic-regression workload does substantial computation between memory-intensive phases, so it tolerates some paging near baseline. It also runs on the JVM, and the paper suggests that when garbage collection sweeps large fractions of the heap, the resulting frequent, latency-sensitive page-fault bursts are where RDMA's lower DB appears to pay off — a proposed explanation rather than an independently isolated cause. Either way, Spark is the one workload where the hybrid picture (SSD by default, RDMA for GC-heavy phases) clearly favors RDMA.

Follow the numbers

Worked examples

Four calculations straight from the paper's own numbers.

① The raw device gap, from Table 2

  1. Latency ratio: 27.15 μs (SSD read) ÷ 4.05 μs (RDMA read) = 6.7×.
  2. Bandwidth ratio: 11774 MiB/s (RDMA) ÷ 2231 MiB/s (SSD) = 5.3×.
  3. Write side: 16.47 μs (SSD) ÷ 3.21 μs (RDMA) = 5.1× lower latency.
🍯
These confirm the paper's "5–7× lower latency, 5–9× higher bandwidth" claim — a real, large device-level advantage for RDMA.

② PMBench-uniform: a big relative gain in an unusable regime

  1. At 1% offload: SSD retains 15% of baseline, RDMA retains 26% — both catastrophic relative to the 80% SLO.
  2. At 20% offload: paper states performance is reduced 95× (SSD) and 37× (RDMA) vs. baseline: SSD ≈ 100/95 = 1.05%, RDMA ≈ 100/37 = 2.7%.
  3. Check the "+161%" claim: 2.7% ÷ 1.05% ≈ 2.57×, i.e. RDMA is ~157–161% faster than SSD at that point — matches the paper's annotation.
  4. But: both numbers are far below 80%. The headline "+161%" describes a regime no SLO-respecting system would run in.

③ Applying the model with real DB values

  1. Latency gap: DSSD − DRDMA = 27.15 − 4.05 = 23.1 μs per swap-in.
  2. Low swap-in rate (λin = 100 pages/s, a cold-data regime): gap ≈ 100 × 23.1 μs = 2.31 ms/s — under 0.3% of one second, negligible.
  3. High swap-in rate (λin = 100,000 pages/s, a hot-data regime): gap ≈ 100,000 × 23.1 μs = 2.31 s/s — the application is stalling more than it's running.
  4. Same latency gap, two-order-of-magnitude different outcome — exactly Eq. 2's message: the swap-in rate, not the backend, is what dominates.

④ Is Spark's extra 20 points of offload worth the DRAM price premium?

  1. Spark's footprint is 44.4 GiB. At the 80% SLO line, SSD tops out at 20% offload while RDMA reaches 40% — so a fully-provisioned RDMA deployment is serving 40% × 44.4 GiB ≈ 17.8 GiB from remote DRAM, not just the incremental 8.9 GiB beyond SSD's ceiling.
  2. Component price, not a deployment cost model: at the paper's listed purchase prices (DRAM $12.3/GiB, SSD $0.50/GiB), that 17.8 GiB of remote DRAM prices out to ≈ $219, versus ≈ $4 for the 8.9 GiB SSD could offload before breaching the SLO. This ignores RNICs, a memory-server host, and network provisioning — the paper is pricing components, not a full deployment.
  3. Interpretation: for Spark specifically, RDMA buys real offload headroom that SSD simply can't reach while preserving the SLO — unlike PMBench/XSBench/PageRank, where the same component-price premium buys ≤1 percentage point of extra headroom.
💡
This is the calculation a far-memory system should report, per the paper's discussion: memory saved at a fixed SLO, and the extra cost incurred to get there — not just raw backend speed.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A system offloads 40% of memory and RDMA outperforms SSD by 200%. Should you conclude RDMA is clearly the better purchase here?
Show answer
Not necessarily — check whether performance at that offload level is still above the SLO (e.g. 80%). It depends on the workload: PageRank stays above the 80% line out to ~46% offload for both backends, and Spark with RDMA hits exactly 40% offload at the 80% line, so 40% isn't automatically an unusable regime. But for workloads like PMBench, 40% offload is already far below any usable SLO. A large relative RDMA advantage at a given offload % says nothing on its own — you have to check where that offload level sits on the workload's own performance curve.Misconception: that a bigger relative gap always means a more important result. The gap must be read alongside the absolute performance level, which varies by workload.
Problem 2 · medium
Using Eq. 2, explain in one sentence why doubling the SSD-RDMA latency gap (e.g. with a slower SSD) does not double RDMA's benefit at low memory pressure.
Show answer
Because the benefit is λin·(DSSD−DRDMA); at low memory pressure λin is small, so even a doubled latency gap is multiplied by a tiny swap-in rate and stays negligible in absolute terms.Misconception: that the latency gap alone determines the benefit. It's the product of the gap and the swap-in rate that matters.
Problem 3 · medium
Why does the paper treat swap-out (reclaim) latency differently from swap-in (fault) latency in its model?
Show answer
Swap-in blocks the faulting thread directly — it's on the critical path. Swap-out/reclaim is assumed mostly asynchronous background work; it costs CPU cycles (scaled by α, spare-CPU-dependent) rather than a direct stall, unless the async assumption breaks down (captured by Q_B).Misconception: that write-back latency to the swap device matters as much as read latency. Under the async-reclaim assumption, it mostly doesn't — until Q_B's assumptions fail.
Problem 4 · hard
PageRank can offload 46% of memory with either backend before falling below 80% (Δ<1%), while Spark's Δ is 20%. What structural difference between the workloads explains this?
Show answer
PageRank's footprint appears to be mostly cold/idle data early on (a large fraction can be offloaded with almost no performance loss, then performance collapses sharply once critical pages are touched) — so swap-in rate stays low across a wide offload range for both backends, keeping the RDMA edge small. For Spark, the paper suggests its JVM garbage collector periodically sweeping large portions of the heap creates high swap-in bursts even at moderate offload, which is where D_B differences (Eq. 2) would become visible.Misconception: that Δ is determined by footprint size alone. It's determined by how often reused/hot pages get evicted and re-faulted, i.e. λ_in, not by total memory offloaded.
Problem 5 · medium
A colleague argues "RDMA far memory is obviously worth the 25× DRAM cost premium because it's always faster." What's missing from that argument?
Show answer
"Always faster" is true at the device level, but the paper shows the application-level benefit collapses when swap-in rate is kept low to preserve an SLO. The argument needs to specify the operating regime (swap traffic / offload %) and show the RDMA-vs-SSD performance gap actually persists there — as it does for Spark but not for PMBench/XSBench/PageRank.Misconception: conflating a device-level benchmark result with an application-level, SLO-constrained deployment decision.
Problem 6 · easy
Why does the paper insist on measuring backends at a fixed performance target (θ=0.8) rather than at a fixed memory-offload percentage?
Show answer
A fixed offload percentage can land in wildly different performance regimes depending on the workload and backend (e.g. 20% offload is near-baseline for PageRank but catastrophic for PMBench). Fixing the performance target instead makes comparisons meaningful across workloads, since it always asks the same operationally relevant question: how much memory can I save while an SLO still holds?Misconception: that offload % is a workload-independent proxy for pressure. It isn't — the same % means very different things across workloads.
Quick answers

Frequently asked questions

Q1Is the paper saying RDMA far memory is useless?▾
No. It's saying RDMA's benefit over SSD is concentrated in a regime (high swap traffic) that usually violates SLOs. RDMA remains valuable for best-effort/elastic jobs that tolerate slowdown, for workloads like Spark where it demonstrably extends the performance-preserving region, or when the app also competes for SSD I/O bandwidth.
Q2What exactly does "θ-performance-preserving" mean?▾
A backend B and memory budget M are θ-performance-preserving if running with B and M achieves at least a fraction θ of the application's no-offloading performance. The paper mostly uses θ = 0.8.
Q3Why use NVMe SSD prices from specific vendor listings?▾
To ground the ~25× DRAM-vs-SSD cost premium ($12.3/GiB vs $0.50/GiB) in concrete, checkable public prices (ServerSupply listings for the PM983 SSD and a comparable server DRAM module) rather than an unsourced estimate.
Q4Which RDMA swap system does the paper actually use?▾
Hermit — a feedback-directed, asynchronous RDMA swap system (Qiao et al., NSDI '23) — configured with remote DRAM as the backing tier.
Q5Why does PMBench show such extreme drops compared to XSBench?▾
PMBench is nearly a pure memory-touching workload with little computation to hide page-fault latency, so even 1% offloading puts the swap backend squarely on the critical path. XSBench does much more computation per memory access, amortizing fault cost over useful work, so its drop is more gradual.
Q6What is Q_B in the model, and why is it usually ignored?▾
Q_B captures cases where the async-reclaim assumption breaks — e.g. reclaim falling behind swap-in demand, or the application generating its own I/O on the same SSD. The paper's main analysis assumes these are small (the "regime of interest") and focuses on the dominant λ_in(K_fault+D_B) term.
Q7Does polling vs. interrupt-driven completion matter?▾
Yes — SSD swap typically uses interrupt-driven completion (thread sleeps, gets woken), while optimized RDMA swap often polls to cut latency, keeping the CPU busy while waiting. So D_RDMA can be lower in elapsed time but higher in CPU cost per fault — a nuance the paper flags but doesn't fully separate out.
Q8What's the "hybrid" design the paper proposes?▾
Route cold, rarely-reused pages to (possibly pooled) NVMe SSD, since their low swap-in rate makes backend latency unimportant; reserve RDMA-backed remote DRAM for workloads or phases where it measurably extends the performance-preserving region (like Spark) or absorbs short-lived pressure on warmer data.
Q9Is this result specific to this exact testbed?▾
The specific numbers are testbed-specific (this PM983 SSD, this ConnectX-6/100 Gbps link), but the paper argues the qualitative mechanism — benefit scaling with swap-in rate times the latency gap — generalizes; newer hardware would shift where curves cross, not remove the effect.

Core terms
Performance-preserving offloadingDefined via θ: a backend+budget keeping ≥θ fraction of no-offload performance. The paper's central evaluation lens.
Swap-in rate (λ_in)Pages per second faulted back into local DRAM. The multiplier that determines how much a faster backend actually matters (Eq. 2).
D_BBackend-dependent page-read latency — what RDMA primarily reduces relative to SSD.
K_fault / K_reclaimBackend-independent per-page software costs for fault handling and reclaim (victim selection, unmapping, TLB shootdown).
αCoefficient converting reclaim CPU usage into application-visible lost work; high when CPU-saturated, low with spare cores.
Q_BResidual term for cases where async reclaim falls behind demand, or the app also uses the swap device for its own I/O.
