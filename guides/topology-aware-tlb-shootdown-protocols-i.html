Handing the interrupt storm to a tree, not to one lonely core

Every TLB shootdown funnels through a single initiator core that must serially notify every other core. On a machine with 192 logical CPUs (96 physical cores), that core becomes the bottleneck. This is the plain-English story of why — and why the fix (route the broadcast through hardware topology) turns out to have no universal answer.

📄 "Topology-aware TLB Shootdown Protocols" · Ding, Seltzer, Achermann 🎓 Paging/VM basics assumed — primers focus on shootdown mechanics ⏱ ~25 min read
📡

The bottleneck is INITIATOR bookkeeping, not IPI hardware — so spread the sending work across a topology-shaped tree. But which tree wins depends on the platform, the workload, and how many cores are even still in play.
No single strategy is universally best.

Before you begin

Quick glossary, then eight ideas the paper assumes

Virtual memory and paging are assumed background. These primers are scoped to shootdown-specific mechanics: what actually happens between a page-table write and "coherent again."

Quick glossary — acronyms used throughout

TLBTranslation Lookaside Buffer — per-core cache of virtual→physical translations.
MMUMemory Management Unit — hardware that walks the page table on a TLB miss.
IPIInter-Processor Interrupt — the hardware mechanism one core uses to interrupt another.
CSDCall Single Data — the per-target Linux struct that carries a pending IPI callback.
mm_cpumaskBitmap tracking which cores have recently used an address space (and so might hold stale translations).
NUMA nodeA socket-sized region with its own local memory; cross-node access is slower.
CCD / L3 clusterCore Complex Die — AMD's chiplet grouping; cores in one CCD share an L3 cache.
MPMMulti-Processing Module — Apache's request-handling model (here, the "event" MPM).
Intel Xeon Platinum 8260 (4 sockets × 48 logical CPUs) AMD EPYC 7643 (2 sockets × 8 CCDs × 12 logical CPUs) tree / propagator machinery native Linux baseline / bottleneck
1Why a TLB shootdown has to happen at all▾

TLBs are not coherent — unlike caches, there's no snooping protocol keeping them in sync. When the OS changes a page-table entry (unmapping a page, changing protection, migrating a physical frame), any core that cached the old translation will keep using it unless told otherwise. That's a correctness bug, not just a performance one: a process could keep reading memory it should no longer have access to.

A TLB shootdown is the OS explicitly interrupting every core that might hold the stale entry and telling it to invalidate.

Now you're ready: the paper isn't about avoiding shootdowns (prior work did that) — it's about making the ones you can't avoid finish faster.
2The IPI — how one core actually interrupts another▾

An inter-processor interrupt is the hardware primitive: core A writes to its local Interrupt Control Register (ICR) targeting core B; core B's execution is interrupted, it jumps to a handler, does the work (here: flush the TLB), and signals completion.

Sending an IPI has real cost — writing the ICR takes cycles, and it takes even more cycles for the interrupt to actually land on a remote, possibly cross-socket, core.

Now you're ready: Section 3.2's whole point is that IPI cost is not uniform — it depends on where the sender and target sit in the topology.
3The CSD and the "bookkeeping" phase▾

Before sending any IPI, Linux must prepare a small per-target struct (the CSD, Call Single Data) describing the callback, and atomically enqueue it onto that target's per-CPU callback queue. This happens per target core, done by the initiator, one at a time.

This is the bookkeeping phase — and because each target's CSD lives in that target's own per-CPU memory, enqueueing to a far-away core means a remote memory write and cache-line ownership transfer.

Now you're ready: bookkeeping is the paper's headline villain — up to 74% of total shootdown latency, and it scales linearly with target-set size because one core does it all, serially.
4mm_cpumask and lazy TLB mode▾

Linux tracks which cores might have an address space's translations cached in a bitmap, mm_cpumask. A core is added when it switches into that address space. But cores don't get removed immediately when they stop using it — a core that's gone idle or switched to the kernel's "lazy" context can defer invalidation, since it isn't actively touching that memory right now.

Critically: the lazy filter only skips sending the IPI to that core this round — it does not remove the core from mm_cpumask. That happens only later, on an actual context switch.

Now you're ready: this is the quiet second bottleneck the paper finds — a target set that only grows, never shrinks, until something removes stale cores.
5NUMA nodes vs. L3/CCD clusters — two different notions of "close"▾

A NUMA node is socket-sized: its own local memory controller, and a real latency penalty to cross into another node. On a chiplet design (AMD), each socket is further subdivided into CCDs (Core Complex Dies), each with its own L3 cache shared by a dozen cores. Crossing a CCD boundary — while staying in the same socket — is a second, smaller hop.

Intel's platform here has no such sub-socket split: all 48 logical CPUs in a socket share one L3. So for Intel, "NUMA-level" and "L3-level" locality are the same thing; for AMD, they're two nested levels.

Now you're ready: this asymmetry is exactly why the paper needs three different broadcast strategies, and why the winner differs by platform.
6Tree-based broadcast — spreading the sending work▾

Instead of the initiator preparing and enqueueing CSDs for every target itself, a tree structure has the initiator notify a handful of propagator cores, which then do the CSD/IPI work for their own assigned subset — in parallel, on different cores.

The initiator's serial workload shrinks from "N targets" to "a few propagators"; the rest of the work happens concurrently, off the critical core.

Now you're ready: the paper's three concrete trees (NUMA-clustered, L3-clustered, Adaptive) are just different ways of choosing who the propagators are and how many hops deep the tree goes.
7Smelt and the adaptive tree▾

Smelt is a prior system for generating broadcast trees tailored to measured pairwise communication costs between cores, rather than to static topology boundaries. Given a cost matrix (like the pairwise IPI latencies in Fig. 3), it greedily builds a tree that reaches expensive (far) destinations early and in parallel, and fills in cheap (near) destinations locally.

The paper precomputes one such tree per possible initiator at boot, then prunes it at shootdown time to fit the actual target set.

Now you're ready: the twist is that this cost-tailored tree does not clearly win in practice — pruning it at runtime erodes the careful boot-time structure, especially in the raw shootdown microbenchmark.
8Reading a speedup chart with a crossover▾

Several figures in this paper show a strategy that's worse than baseline at small scale and better at large scale, crossing 1.0× somewhere in the middle. That's not noise — it's a real trade-off: tree-based dispatch has a fixed setup cost (selecting propagators, building/traversing the structure) that only pays for itself once the serial bookkeeping it replaces gets expensive enough.

Now you're ready: whenever you see "up to 1.9× ... down to 0.55×" for the same strategy, that's describing the two ends of one crossover curve, not two different experiments.
The whole story in one place

Topology-aware shootdowns, in a nutshell

The problem, the fix, and why the fix has an asterisk.

Linux's TLB shootdown (and Solaris's, OpenBSD's, XNU's) funnels all coordination through the initiator core: it alone identifies targets, prepares and enqueues a callback (CSD) for each one, sends the IPIs, then polls until every target acknowledges. Instrumenting this on two machines with 192 logical CPUs each (96 physical cores) shows bookkeeping — CSD preparation and enqueueing — dominates, accounting for up to 74% of total latency and scaling linearly with target-set size, because one core does all of it, serially.

The fix is structural, not algorithmic: build a tree so the initiator only has to notify a handful of propagator cores, who forward the rest in parallel. The paper builds three such trees — NUMA-clustered (propagators per socket), L3-clustered (a second level per chiplet), and Adaptive (a Smelt-generated tree tailored to measured pairwise IPI costs) — and measures them against native Linux on an Intel Xeon Platinum 8260 (4 sockets × 48 logical CPUs, uniform intra-socket L3) and an AMD EPYC 7643 (2 sockets × 8 CCDs × 12 logical CPUs, a real chiplet sub-level).

The result has a catch: tree-based broadcast cuts raw shootdown latency by up to 1.9× at large target sets — but L3-clustered wins on AMD while NUMA-clustered wins on Intel, and the Smelt-generated Adaptive tree loses on both platforms in the raw shootdown microbenchmark, because runtime pruning erodes its careful boot-time tailoring (on AMD's Sysbench results, Adaptive tracks L3-clustered's trend more closely). At small target sets, every tree strategy is worse than doing nothing. And application-level gains (Apache, Sysbench) are smaller still — because a second, independent factor turns out to matter just as much: how aggressively stale, "lazy" cores get removed from the shootdown target set in the first place.

🍯 Key takeaways

  • Native Linux serializes shootdown coordination on one core; bookkeeping (CSD prep + enqueue), not IPI hardware, is the bottleneck (up to 74% of latency).
  • IPI cost is highly non-uniform: inter-NUMA is up to 3.5× intra-NUMA; on AMD, crossing a chiplet (CCD) but staying in-socket is up to 2× within-chiplet.
  • Tree-based broadcast distributes bookkeeping across propagator cores — up to 1.9× faster raw shootdown latency at large target sets, but worse than native at small ones.
  • No single tree wins everywhere: NUMA-clustered best on Intel (1.38×), L3-clustered best on AMD (1.90×); the Smelt-generated Adaptive tree loses on both platforms' shootdown microbenchmark (though on AMD's Sysbench results it tracks L3-clustered's trend more closely).
  • A second, largely independent factor: eagerly shrinking the target set (removing stale lazy-TLB cores from mm_cpumask) explains a large share of Apache's real throughput gain — once applied as the baseline, the tree's own advantage nearly disappears.
  • Application-level gains are modest (up to ~14% Apache throughput) even where raw shootdown latency improved by up to 1.9× — the gap between kernel-level and app-level wins is itself a finding.
🔗
Speculative extension — not discussed in the paper: promotion/demotion daemons in DRAM–NVM/CXL tiering (systems like TPP, HeMem, Memtis, though this paper does not engage with them) also mutate PTEs on hot/cold migration, and each mutation needs a shootdown across whatever cores share that address space. If that pattern holds, the same initiator-bookkeeping bottleneck this paper measures would plausibly tax migration throughput too — a topology-aware broadcast is one plausible (unverified) lever for cutting migration-induced shootdown cost in those systems.
Six everyday pictures

How to think about topology-aware shootdowns

Each stands alone. Every card ends with where the picture stops being true.

The bottleneck · Initiator contention

One clerk, a long line

Picture one clerk who must personally write, stamp, and hand every notice to every recipient before the line can move — even though delivering a notice takes another employee no time at all. The clerk's own writing-and-stamping is the queue, not the walk across the room. That's bookkeeping: preparing and enqueueing each CSD, one at a time, on the initiator.

Where it breaks: the clerk analogy suggests infinite parallel helpers would fix everything — but a tree only helps up to a point; too many levels adds its own forwarding delay (why Adaptive's extra hops hurt it).
Non-uniform cost · NUMA vs L3

Shouting down the hall vs. calling another building

Getting a colleague's attention two desks away costs almost nothing. Reaching someone across the building — down stairs, through doors — costs real time, even though it's "only" one more hop conceptually. That's IPI propagation: within-chiplet is cheap, crossing a chiplet within the same socket costs up to 2× more, and crossing sockets entirely costs up to 3.5× more than staying local.

Where it breaks: a building has one obvious distance metric; AMD's chiplets add a second nested level (CCD, then socket) that Intel's flat, single-L3-per-socket design doesn't have — so the "how many buildings away" question has a different shape per platform.
The fix · Tree-based propagation

A phone tree, not a call list

An old-fashioned phone tree: the organizer calls two people, each of them calls two more, and within a few rounds hundreds are notified — without the organizer ever dialing more than two numbers. Compare that to one person working through a call list of 191 names alone. UCP-for-shootdowns is exactly this: NUMA-clustered and L3-clustered fix the tree shape to the org chart (socket, then chiplet); Adaptive tries to build a custom tree from measured "who's fastest to reach whom."

Where it breaks: a real phone tree doesn't care about wire distance — hardware does. That's why the tree's shape (who calls whom) has to match hardware topology, not just minimize hop count.
The second bottleneck · Lazy TLB / mm_cpumask

A mailing list you're never removed from

You stop actively reading a mailing list, but no one unsubscribes you — so every future blast still includes you, costing the sender a little more each time, forever, until someone finally cleans the list. That's a lazy-mode core: skipped for this shootdown's IPI, but left in mm_cpumask, quietly inflating every future target set until a context switch removes it.

Where it breaks: an unwanted email costs the reader nothing; a stale core in the target set costs the sender real bookkeeping time on every subsequent shootdown — which is why Apache's gains came largely from list-cleaning, not the tree.
Why cost-tailored loses · Adaptive tree pruning

A custom suit, altered on the way out the door

A tailor measures you precisely and builds a suit that fits perfectly — for the body you have today. Now imagine that every time you wear it, someone quickly re-hems it to fit whoever happens to be in the room, in a rush, without re-measuring. It still roughly fits, but the careful tailoring is compromised. That's the Adaptive/Smelt tree: precisely built at boot from measured pairwise costs, then hastily pruned at shootdown time to whatever the actual (usually smaller) target set is.

Where it breaks: off-the-rack (the static NUMA/L3 trees) isn't "worse tailoring" here — it's tailoring to something stable (socket/chiplet boundaries) that doesn't need re-measuring every time, which is exactly why it holds up better under runtime pruning.
The crossover · Fixed cost vs. payoff

Renting a moving truck for one box

Hiring a moving crew and truck is a great deal if you're relocating a whole house — and a terrible deal if you're moving one box down the hall, where you'd have been done before the truck even arrived. Tree-based propagation has the same shape: real setup cost (selecting propagators, building the structure) that only pays off once the serial alternative (native, one core) is slow enough to beat.

Where it breaks: a moving crew's overhead is roughly fixed regardless of house size; the tree's setup cost and native's serial cost both scale with target-set size, just at very different rates — which is why the crossover point itself shifts by platform.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The native path — three phases, one core

Linux's default TLB shootdown (Algorithm 1 in the paper) runs entirely coordinated by the initiator:

1. Identify targets
Scan mm_cpumask; drop lazy-mode cores from this round's dispatch (they stay in the bitmap)
→
2. Bookkeeping
Acquire + fill each target's CSD, enqueue on its callback queue — serially, up to 74% of total time
→
3. Send IPIs
Write the ICR for each target set
→
4. Wait
Poll every CSD busy bit until cleared — includes remote propagation + handler + invalidation
⚠
Why "wait for completion" isn't free either: that phase includes IPI propagation delay, interrupt-handler entry, the actual TLB flush, and the completion signal — so even a perfectly fast initiator still waits on the slowest remote target.

2 · Why locality matters — the cost matrix

Measured with a Smelt-style pairwise experiment across 1000 trials, both send time (initiator's cost to enqueue+dispatch) and propagation time (issue → target's handler entry) depend heavily on where sender and target sit. On both platforms, inter-NUMA IPIs cost up to 3.5× more than intra-NUMA ones. On AMD specifically, crossing a chiplet (CCD) boundary while staying in the same socket costs up to 2× more than staying within one chiplet. SMT-sibling communication is cheapest on both platforms. Measured propagation times span roughly 2,500–6,000 cycles; send times span roughly 600–2,000 cycles (Fig. 3 heatmap ranges).

3 · Propagator selection and load balancing

For NUMA-clustered, up to four propagators per NUMA node are chosen by round-robin across successive shootdowns, so forwarding work doesn't repeatedly concentrate on the same cores under concurrent shootdowns. For L3-clustered on AMD (8 CCDs × 12 logical CPUs per node), one propagator per CCD is selected statically as the lowest-indexed participating CPU — round-robin isn't needed since the measured within-L3 latency variation is already small. The first-layer propagator forwards to at most 7 peer CCD propagators plus 11 cores in its own CCD; each second-layer propagator then handles at most 11 remaining cores.

4 · Implementation — hooking Linux 5.15

A hook in flush_tlb_mm_range() selects the propagation strategy at runtime; disabling it falls back to native Linux. Because invoking the dispatch interface from inside an IPI handler risks deadlock, propagators use irq_work to notify their children rather than recursing directly. All topology metadata is pre-allocated per-CPU at boot — no allocation or synchronization is added to the shootdown's critical path.

5 · The second factor — eager target-set reduction

Because the lazy-TLB filter skips dispatch but not mm_cpumask membership, a workload like Apache's event MPM — many threads, few active at once — accumulates stale cores in the target set over time, making every future shootdown more expensive regardless of broadcast topology. Applying eager cleanup (removing lazy cores from the mask, not just skipping their IPI) shrinks the target set directly. Re-run against this eager-flat baseline instead of native, and the tree strategies' advantage on Apache almost entirely disappears — most of the real-world gain came from the smaller target set, not the broadcast shape.

💡
Why this is a genuinely separate finding: broadcast topology parallelizes sending to a fixed target set; eager reduction shrinks the target set itself. They're independent levers — and for workloads with lots of idle-but-still-tracked cores, the second lever turns out to matter more.
Follow the numbers

Worked examples

Four traces through the paper's actual figures — where the time goes, what the cost matrix implies, how much a tree really flattens the fan-out, and what "no universal winner" costs in practice.

① Where does shootdown time actually go?

Figure 1 shows bookkeeping's share of total latency climbing as target-set size grows on both platforms, reaching up to 74% of total duration at large core counts.

  1. Bookkeeping = CSD acquire + fill + enqueue, done one target at a time on the initiator alone.
  2. It scales linearly with target-set size — twice the targets, roughly twice the serial bookkeeping work.
  3. Send IPIs and Wait for completion don't scale the same way — IPI delivery is partially hardware-parallel, so their combined share shrinks relative to bookkeeping as the target set grows.
  4. At 74% bookkeeping, even a magic zero-cost IPI mechanism could only remove up to ~26% of total latency — the other ~74% is purely an initiator-side software bottleneck.
🍯
Insight: this is why the paper's fix targets bookkeeping specifically (spread it across propagators) rather than trying to make IPIs themselves faster — bookkeeping is where nearly three-quarters of the time already lives.

② Reading the IPI cost matrix

Figure 3's pairwise heatmaps report propagation times spanning ~2,500–6,000 cycles and send times spanning ~600–2,000 cycles, with two named multipliers: up to 3.5× for inter-NUMA vs. intra-NUMA, and up to 2× for cross-chiplet-same-node vs. within-chiplet (AMD only).

  1. Cheapest case (both platforms): an IPI to your own SMT sibling — near the bottom of the ~2,500-cycle floor.
  2. On AMD, cross a CCD boundary but stay in the same socket: up to 2× that floor — consistent with landing in the upper half of the measured 2,500–6,000 cycle range.
  3. Leave the socket entirely (inter-NUMA), on either platform: up to 3.5× the intra-NUMA baseline — the paper's largest reported multiplier, and the reason both static trees keep the first hop inter-socket and everything after it local.
  4. Consequence for tree design: the Adaptive tree spends exactly one expensive inter-NUMA hop per remote node, then fans out cheaply. The static trees follow the same spirit but not the same strict bound — NUMA-clustered and L3-clustered use up to four propagators per NUMA node, so the initiator can issue a handful of inter-NUMA sends to the same remote node rather than exactly one; still far fewer than one per target, just not a hard one-hop-per-node guarantee.
💡
This is precisely the "shout down the hall vs. call another building" analogy made numeric: the tree's whole design goal is to pay the 3.5× penalty as few times as possible per remote socket, not once per remote core.

③ How much does a tree actually flatten the initiator's fan-out?

AMD EPYC 7643: 2 sockets × 8 CCDs × 12 logical CPUs = 192 logical CPUs (96 physical cores). Under L3-clustered, the first-layer propagator forwards to at most 7 peer CCD propagators plus 11 logical CPUs in its own CCD; each second-layer propagator then handles at most 11 more.

  1. Native, worst case: the initiator alone must bookkeep up to 191 other logical CPUs, serially, on one core.
  2. L3-clustered, first-layer propagator's direct fan-out: 7 (peer CCD propagators, one per other CCD in its own NUMA node) + 11 (own CCD) = 18 direct sends, maximum — no single core, native or tree, ever sends more than that.
  3. Reduction in the busiest single core's direct workload: 191 ÷ 18 ≈ 10.6× fewer direct bookkeeping operations on the hottest core, compared to native's single initiator.
  4. The remaining targets in that initiator's own 96-logical-CPU NUMA node (up to 77 more) are handled by its 7 peer CCD propagators in parallel, each doing ≤11; the other NUMA node's ~96 logical CPUs are covered by a mirrored propagator structure rooted in that node, not by these same second-layer propagators.
🍯
Insight: this ~10.6× reduction in the busiest core's direct fan-out is the structural reason tree-based propagation can approach a 1.9× wall-clock speedup even though the underlying IPI hardware hasn't changed at all.

Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A shootdown targets only 6 cores. Should you expect the tree-based strategies to beat native Linux here?
Show answer
No — at small target-set sizes, native Linux is fastest in the paper's measurements. Tree-based dispatch has a fixed setup cost (propagator selection, tree traversal) that only pays off once serialized bookkeeping over many targets gets expensive enough to outweigh it. At 6 targets, that crossover hasn't happened yet.Misconception: that a "smarter" broadcast structure is strictly better. It's a trade of fixed overhead for parallelism — a bad trade below the crossover point.
Problem 2 · medium
Bookkeeping accounts for up to 74% of total shootdown latency. If you could magically make IPI hardware instantaneous (zero send + zero propagation), what's the maximum possible latency reduction?
Show answer
At most ~26% — the remaining share (send + wait, which includes propagation, handler entry, and the actual flush). Since bookkeeping is purely initiator-side, software-serialized work, eliminating IPI hardware cost entirely still leaves the dominant 74% untouched. This is exactly why the paper attacks bookkeeping via parallelism (trees) rather than IPI mechanics.Misconception: that shootdown latency is primarily an interrupt/hardware cost. The measured bottleneck is software bookkeeping on the initiator, not IPI delivery itself.
Problem 3 · medium
Apache's event MPM shows large gains from tree-based broadcast versus native — but those gains nearly vanish when compared against an "eager-flat" baseline. Explain both results without contradiction.
Show answer
Apache leaves many threads idle in lazy TLB mode, so its target sets grow stale over time under native Linux's default lazy filter (which skips dispatch but not cpumask removal). Tree-based strategies happened to also eagerly clean the target set as part of their implementation, so most of the "topology" gain versus native was actually target-set shrinkage. Once the baseline itself eagerly cleans the mask (eager-flat — a strictly more demanding baseline than native), the target sets are already small for everyone, and the tree's remaining advantage — pure broadcast-shape parallelism on an already-small set — is minor, consistent with the "small target set" case from Problem 1.Misconception: that the apparent Apache win proves topology-aware broadcast matters most in practice. Target-set maintenance was doing most of the work; broadcast shape is a secondary, smaller effect at app level.
Problem 4 · hard
The Adaptive tree is built from measured, fine-grained pairwise IPI costs — strictly more information than the static NUMA/L3-clustered trees use. Why does it still underperform both static trees in the shootdown microbenchmark on both platforms?
Show answer
The Adaptive tree is precomputed once per possible initiator at boot time, assuming a full/static core set, then pruned at each shootdown to fit the actual (usually smaller, workload-dependent) target set. That pruning is naive and doesn't reconstruct an equally good tree for the reduced set — it just removes non-participating nodes from the original structure. The result carries extra construction/traversal overhead without reliably preserving the careful cost-based tailoring that made it a strong candidate for the full set in the first place. Static trees, by contrast, are cheap to build for any subset because they follow fixed structural boundaries (socket, CCD) that don't need re-derivation. (On AMD's Sysbench benchmark, by contrast, Adaptive's results track L3-clustered's trend fairly closely — the clear loss shown here is specific to the raw shootdown microbenchmark.)Misconception: that more precise input data (measured costs vs. structural boundaries) guarantees a better runtime result. A tree built from tighter input data that degrades under practical constraints (dynamic target sets, hot-path pruning) can lose to a cruder but more robust one.
Problem 5 · medium
On Intel, Sysbench shows tree-based broadcast performing worse than native at large core counts, while the same trees clearly help on the microbenchmark. What's a plausible reason, per the paper?
Show answer
The paper's data is consistent with a phase trade-off: tree-based propagation mainly reduces sender-side (bookkeeping) contention, but can increase completion-side latency (more hops before a distant target's acknowledgment is visible). If Sysbench's workload makes "wait for completion" the dominant phase on Intel — rather than bookkeeping, which the microbenchmark isolates — then the tree's sender-side win is outweighed by its completion-side cost. Different workloads stress different phases of the same shootdown.Misconception: that a technique validated on a clean microbenchmark automatically transfers to any application workload. Which phase dominates depends on the workload, not just the platform.
Problem 6 · easy
Why does the paper build a separate L3-clustered strategy specifically for AMD, rather than reusing NUMA-clustered everywhere?
Show answer
AMD's EPYC 7643 has a chiplet design: each socket is split into 8 CCDs, each with its own L3 cache shared by 12 logical CPUs — a real, measurable sub-socket locality boundary (up to 2× cost difference crossing it). Intel's Xeon Platinum 8260 has no such split; all 48 logical CPUs per socket share one L3, so NUMA-clustered and L3-clustered are structurally equivalent there (the paper notes L3-clustered is the same as one-propagator-per-node NUMA-clustered on Intel, just with extra overhead). Building L3-clustered captures a real topology feature that only exists on chiplet designs.Misconception: that "more levels in the tree" is a universal improvement. It's only useful where the hardware actually has that extra level of locality to exploit.
Problem 7 · hard
Suppose a future CPU architecture adds hardware-broadcast TLB invalidation (like ARM's broadcast TLBI or AMD's INVLPGB) across the whole chip. Does that make this paper's tree-based approach obsolete?
Show answer
Not necessarily. The paper notes both AMD (INVLPGB) and ARM provide partial hardware assistance, yet software IPI broadcasts remain necessary on many platforms — including for shootdown-adjacent mechanisms like CPU hotplugging and RCU grace periods that this paper's authors suggest could also benefit from tree-based propagation. Even with hardware broadcast support, some coordination (e.g., knowing when all targets are done, handling heterogeneous or partial target sets) may still route through software, and the paper explicitly suggests its techniques could extend to speeding up hardware-assisted shootdowns rather than being replaced by them.Misconception: that hardware acceleration of one phase (invalidation) automatically eliminates the software coordination bottleneck the paper studies. The bookkeeping problem is about coordinating which cores need to act, not just how fast the invalidation itself executes.
Quick answers

Frequently asked questions

Nine questions newcomers ask most.

Q1Why can't TLBs just be made coherent, like caches?▾
Cache coherence protocols (snooping, directories) exist and are pervasive in hardware; TLBs historically haven't had an equivalent because translations change far less often than data and the hardware cost of full TLB coherence hasn't been judged worth it on most platforms. So software (the OS) is left to explicitly synchronize — the shootdown.
Q2What exactly is being measured as "bookkeeping"?▾
The initiator's per-target work before any IPI is even sent: waiting for that target's CSD structure to be free, filling it with the flush request, and atomically enqueueing it on the target's per-CPU callback queue. Because each target's CSD lives in that target's own memory, doing this for a remote-socket core involves a remote memory write and cache-line transfer — expensive, and done one target at a time.
Q3Why does the best broadcast topology differ between Intel and AMD?▾
The platforms have genuinely different topologies: Intel's 4 sockets each share one flat 48-logical-CPU L3 domain, so a single propagator layer (NUMA-clustered) already matches the hardware's real locality boundary. AMD's 2 sockets are each split into 8 chiplets (CCDs) with their own L3 — a real second level of locality that L3-clustered's extra tree layer is built to exploit, and that NUMA-clustered alone leaves on the table.
Q4Isn't the Smelt-generated Adaptive tree, built from precise measured costs, supposed to always win?▾
The paper doesn't claim Adaptive is optimal — it's a cost-informed tree generated by the Smelt algorithm from measured pairwise IPI costs, then pruned at runtime to fit the actual target set. TLB shootdown target sets vary shootdown-to-shootdown, and that naive pruning doesn't preserve the careful boot-time tailoring, adding overhead without the matching benefit. It underperforms both static trees in the shootdown microbenchmark on both platforms, though on AMD's Sysbench results it tracks L3-clustered's trend more closely.
Q5What's the difference between "native" and "eager-flat" as baselines?▾
"Native" is Linux's unmodified protocol, including its default lazy-TLB filter, which skips sending IPIs to lazy-mode cores but leaves them in mm_cpumask indefinitely. "Eager-flat" is the same flat (non-tree) send pattern, but with that filter changed to also eagerly remove lazy cores from the cpumask — a stronger, more demanding baseline than native, since it already captures much of the apparent tree advantage. Comparing tree strategies against eager-flat isolates the broadcast-topology effect from the target-set-size effect.
Q6Does this only apply to Linux?▾
The implementation is Linux-specific (a hook in flush_tlb_mm_range() on Linux 5.15), but the paper notes Solaris, OpenBSD, and XNU all use structurally similar sequential, initiator-centric shootdown protocols — so the same initiator-contention problem, and plausibly the same tree-based fix, likely generalizes.
Q7Could this same tree idea speed up things other than TLB shootdowns?▾
The authors explicitly suggest yes — any IPI-based broadcast notification mechanism could benefit, naming CPU hotplugging/offlining and RCU grace periods as candidates, since both also rely on notifying many cores from one initiator.
Q8Why does a good micro-level result (1.9× raw latency) turn into a modest app-level result (~14% throughput)?▾
Application throughput depends on far more than shootdown latency alone — total shootdown frequency, how much other work overlaps with a shootdown, and (per the Apache findings) how much of the "real" cost was actually target-set bloat rather than broadcast shape. A 1.9× win on an isolated, worst-case microbenchmark doesn't linearly translate to end-to-end throughput.
Q9What did the authors leave for future work?▾
Automatic, workload-aware selection of the best topology (a lightweight cost model rather than manual choice); a lighter-weight dynamic variant of the Smelt tree idea, periodically rebuilt off the hot path; reversing inter-/intra-socket send ordering; evaluating non-fully-connected platforms; and extending the approach to hardware-assisted shootdown mechanisms and other IPI-based kernel notification paths.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
TLB shootdownThe OS-driven procedure that interrupts every core that might cache a now-stale translation and forces it to invalidate that entry.
InitiatorThe core that starts a shootdown: identifies targets, prepares callbacks, sends IPIs, and waits for completion in native Linux.
BookkeepingPer-target CSD acquisition + enqueueing work done serially by the initiator — the dominant cost (up to 74% of total latency).
PropagatorA core, chosen from the target set, that forwards the shootdown request to a sub-group of targets on the initiator's behalf.
NUMA-clustered treeTwo-level tree with up to 4 propagators per NUMA node, selected round-robin across successive shootdowns.
L3-clustered treeThree-level tree adding a per-CCD/L3-domain propagator layer beneath NUMA-clustered — matches AMD's chiplet structure.
Adaptive treeA per-initiator tree generated via the Smelt algorithm from measured pairwise IPI costs, precomputed at boot and pruned per shootdown.
Eager target-set reductionRemoving stale, lazy-mode cores from mm_cpumask proactively rather than only on their next context switch.
Supporting terms
IPIInter-processor interrupt — the hardware mechanism used to notify a remote core; cost is non-uniform across topology.
CSD (Call Single Data)Linux's per-target struct describing a pending cross-core callback; acquiring/enqueueing it is the "bookkeeping" cost.
mm_cpumaskBitmap tracking which cores might hold cached translations for an address space; grows on use, shrinks only on context switch-out.
Lazy TLB modeA core state where a process's translations are treated as deferred/inactive; skipped for the current shootdown's IPI, but not removed from mm_cpumask.
NUMA node / socketA processor package with local memory; crossing to another node costs up to 3.5× more than staying local (this paper).
CCD (Core Complex Die)AMD's chiplet unit; cores within one CCD share an L3 cache — the extra locality level L3-clustered targets.
flush_tlb_mm_range()The Linux kernel entry point hooked to select the propagation strategy at runtime.
irq_workLinux mechanism propagators use to defer forwarding rather than recursing inside an IPI handler (avoiding deadlock).
Bandwidth / latency speedupThe paper's two application-level metrics: normalized Apache bandwidth speedup, and Sysbench average per-operation latency speedup, both relative to native Linux, reported per platform and thread count.
