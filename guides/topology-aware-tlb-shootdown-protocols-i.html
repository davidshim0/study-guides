One core shouldn't have to tell 192 cores to forget

Every page-table update that touches a shared mapping forces the OS to chase down every core that might have cached the old translation. Linux does this with one core serially notifying everyone. This is the plain-English story of what happens when you let the notification spread instead.

📄 "Topology-aware TLB Shootdown Protocols" · Ding, Seltzer, Achermann · PLOS'26 🖥 192-logical-core Intel Xeon & AMD EPYC testbeds ⏱ ~22 min read
📡

SPREAD the sending work across cores that already sit close to the targets — but only when the target set is big enough that one core sending alone would be the bottleneck.

Before you begin

Quick glossary, then six primers

The acronyms first, since the paper leans on them constantly; then short primers on the mechanics. You know the mm stack — these are compressed on purpose.

Quick glossary

1Why TLBs aren't coherent▾

Caches for data are kept coherent by a hardware protocol (MESI and friends). TLBs are not — there's no snooping between per-core translation caches. When the kernel changes a page-table entry (unmap, protect, migrate), any core's TLB may still hold the old mapping and keep using it silently.

Now you're ready: the OS, not hardware, is on the hook for TLB coherence — that software procedure is the shootdown this paper is about.
2What a shootdown actually does▾

One core (the initiator) figures out which other cores might have the stale translation, sends each an IPI, and waits for all of them to invalidate and acknowledge. Algorithm 1 in the paper: build target_cores from mm_cpumask, enqueue a callback (CSD) per target, fire IPIs, poll for completion.

Now you're ready: three phases — bookkeeping, send, wait — and the paper measures each separately.
3IPIs and why they're not free▾

An IPI interrupts the remote core's execution and forces it to run a handler — real latency to deliver, plus the remote core's own time to invalidate and reply. The initiator's side (updating a target-indexed CSD, enqueueing on the target's per-CPU queue) also touches remote memory, so it isn't free even before the interrupt fires.

Now you're ready: both ends of an IPI cost something, and both scale with how far apart the two cores are.
4Sockets, CCDs, and L3 domains▾

Intel Xeon 8260: 4 sockets × 48 logical cores, one shared L3 per socket. AMD EPYC 7643: 2 sockets × 8 CCDs × 12 logical cores, one L3 per CCD — an extra hierarchy level inside each socket. Crossing a socket is expensive on both; on AMD, crossing a CCD boundary within a socket is also measurably more expensive than staying inside one.

Now you're ready: any "topology-aware" scheme has to know about this extra AMD level, not just sockets.
5mm_cpumask and the lazy-TLB trap▾

mm_cpumask records cores that have recently used a given mm and might still have cached translations for it. A core in lazy-TLB mode (not actively using that mm) is skipped during a shootdown — but Linux doesn't remove it from mm_cpumask at that point; removal only happens later, on a context switch. So stale cores can silently accumulate in the target set across many shootdowns.

Now you're ready: target-set size can grow for reasons that have nothing to do with the broadcast topology — that's the paper's second, independent lever.
6Broadcast trees (Smelt's idea)▾

Instead of one sender messaging N recipients directly, pick a few recipients as "propagators" who relay the message onward — a shallow tree instead of a flat fan-out. Smelt (OSDI'16) builds such trees for generic multicore broadcast using measured pairwise latencies. This paper adapts that idea specifically to TLB shootdown's IPI path.

Now you're ready: the three strategies in this paper (NUMA-clustered, L3-clustered, Adaptive) are three different ways to build that tree.
The whole story in one place

Topology-aware shootdown in a nutshell

The bottleneck, the fix, and the honest caveat that no fix wins everywhere.

Linux's native TLB shootdown is serialized on the initiator: one core must acquire a CSD, enqueue a callback, and track completion for every single target, one at a time, before any IPI even goes out. The paper instruments this and finds bookkeeping — not interrupt delivery — dominates, accounting for up to 74% of total shootdown latency at scale, because it grows linearly with target-set size and touches remote per-CPU memory for distant cores.

The fix is structural, not algorithmic: instead of the initiator messaging every target directly, hand off batches of targets to a few propagator cores that forward concurrently. Three tree shapes are tried — NUMA-clustered (propagators per socket), L3-clustered (an extra layer per L3/CCD), and Adaptive (a Smelt-generated tree using measured pairwise IPI costs). Orthogonally, the paper also pushes eager removal of lazy-TLB cores from mm_cpumask, shrinking the target set itself.

The payoff: up to 1.9× microbenchmark latency speedup (AMD, L3-clustered) and 1.38× (Intel, NUMA-clustered) at 192 threads, plus up to 14% higher Apache throughput. The catch: no tree wins everywhere — at small target sets, or when remote completion rather than sending dominates (Sysbench on Intel), native Linux is still better, and trees can actively hurt.

🍯 Key takeaways

  • Native Linux's bottleneck is initiator bookkeeping (CSD acquire + enqueue), up to 74% of latency — not IPI delivery itself.
  • Three tree topologies trade forwarding overhead for sender parallelism; none dominates across platform + workload.
  • Intel: NUMA-clustered best, up to 1.38×. AMD: L3-clustered best, up to 1.90×, because the chiplet layer matters there.
  • Trees lose when the target set is small, or when remote completion (not sending) dominates latency (Sysbench, Intel).
  • Target-set size is a second, independent lever: eagerly dropping lazy-TLB cores from mm_cpumask explains most of Apache's apparent gain.
  • Apache throughput: up to 1.14× (Intel) / 1.06× (AMD) vs native; against an eager-cleanup baseline, Intel collapses to ~1.00× while AMD actually drops below it, to ~0.92–0.93×.
Five everyday pictures

How to think about topology-aware shootdown

Each stands alone. Every card ends with where the picture stops being true.

The bottleneck · Serial initiator

One cashier, a long line

One clerk must personally walk a form to every desk in the building before closing the register — even though each desk only needs ten seconds of attention. The clerk's walking time, not the ten seconds, is what makes the line slow. That's bookkeeping: it scales with the number of targets, not with the cost of the interrupt itself.

Where it breaks: at a small building (few targets), sending a runner (a propagator) to split the walk isn't worth the extra coordination — the clerk alone is still faster.
The fix · Tree broadcast

A phone tree

Instead of the school secretary calling all 200 parents, she calls 10 class reps, each of whom calls their 20 families. Everyone hears the news much sooner, in parallel — at the cost of one extra hop for most people. UCP's — sorry, this paper's — propagators are exactly those class reps.

Where it breaks: a bad rep (a propagator across a slow link) delays everyone under them — which is why who you pick as a propagator (near or far) matters as much as having propagators at all.
Non-uniform cost · NUMA / L3 locality

A phone call across town vs. next door

Calling the person in the next cubicle feels instant; calling a branch office across the country has real lag, even on the same phone system. IPIs behave the same: inter-socket is up to 3.5× slower than intra-socket, and on AMD, even crossing a chiplet boundary inside the same socket costs up to 2× more than staying within one.

Where it breaks: "across town" is a fixed geography; chip topology differs by vendor — Intel's single per-socket L3 has no AMD-style extra chiplet hop, so the same analogy needs an extra layer on AMD.
The hidden cost · Lazy TLB residue

Guests who never check out

A hotel skips cleaning a room whose guest is "checked out but not departed" — but if the front desk never updates the registry, that room keeps appearing on every future housekeeping list, slowing down rounds that have nothing to do with it. Lazy-TLB cores are exactly this: skipped during one shootdown, but left in mm_cpumask until a context switch finally evicts them.

Where it breaks: a hotel registry is corrected on checkout; mm_cpumask is only corrected opportunistically, so the "stale guest list" can persist across many shootdowns, not just one.
The caveat · No universal winner

No single wrench fits every bolt

A mechanic doesn't carry one universal wrench — the right size depends on the bolt in front of them. Same here: NUMA-clustered wins on Intel, L3-clustered wins on AMD, and at small target sets or completion-bound workloads, the plain flat approach (native Linux) beats both trees.

Where it breaks: a mechanic can usually tell the bolt size by looking; picking the right shootdown strategy at runtime needs a cost model the paper explicitly leaves as future work.
The full explanation

How it actually works

The baseline bottleneck, the two testbeds' topology, the three tree strategies, and target-set reduction.

1 · The baseline protocol and its bottleneck

Algorithm 1: build the target set from mm_cpumask (skipping lazy cores but not removing them from the mask), acquire/enqueue a CSD per target, fire IPIs, poll for completion. Instrumenting smp_call_function_*() splits latency into three phases:

Bookkeeping   // acquire + fill + enqueue each target's CSD — scales linearly, up to 74% of total
Send IPIs     // time issuing interrupts through the ICR
Wait          // propagation + handler entry + invalidation + ack, polled by the initiator
⚠
Bookkeeping dominates because each target-indexed CSD lives in that target's per-CPU memory — notifying a distant core means a remote memory access and cache-line ownership transfer before the IPI is even sent.

2 · Two topologies, two different extra costs

PlatformSocketsPer-socket structureLogical coresExtra hop?
Intel Xeon 8260448 logical cores share one L3192None beyond socket
AMD EPYC 764328 CCDs × 12 logical cores, each CCD its own L3192CCD boundary, up to 2× extra

Inter-socket IPIs are up to 3.5× slower than intra-socket on both machines. On AMD, crossing a CCD boundary inside the same socket adds up to another 2× — the chiplet layer Intel doesn't have.

3 · Three tree strategies

StrategyStructureBest platform (paper's finding)
NUMA-clusteredUp to 4 propagators per socket; remaining targets in that socket are split among the initiator and propagators (2-level)Intel, up to 1.38×
L3-clusteredAdds a 3rd level: one propagator per CCD/L3 cluster, forwarding within itAMD, up to 1.90×
AdaptiveSmelt-generated, per-initiator, using measured pairwise IPI costs; reaches each remote NUMA node via its lowest-cost core firstNeither — pruning/forwarding overhead outweighs its savings
🌱
On Intel, where one L3 already spans the whole socket, L3-clustered degenerates to NUMA-clustered with one propagator per node — just with extra bookkeeping overhead for no structural benefit.

4 · Target-set reduction (P4) — the second lever

Apache's event-driven worker model leaves many threads idle (and their cores in lazy-TLB mode) at any moment. Because lazy cores linger in mm_cpumask, Apache's shootdown target sets grow over time even though few cores are truly active. Eagerly dropping lazy cores from the mask shrinks the target set directly — and when the paper re-baselines against this "eager-flat" variant instead of native Linux, the tree strategies' apparent advantage mostly disappears: most of the original gain was target-set size, not topology.

💡
Why this matters beyond this paper: any mechanism that invalidates a mapping on a specific shared address space — page migration between tiers, THP splitting, mprotect-based tiering hints — inherits the same two independent costs: how many cores you must notify, and how you notify them.
Follow the numbers

Worked examples

Four traces through the paper's real figures — phase breakdown, AMD fan-out arithmetic, speedup-to-latency-cut conversion, and disentangling Apache's gain.

① What 74% bookkeeping actually implies

The paper states bookkeeping accounts for "up to 74%" of total shootdown latency at large target-set sizes. What does that bound on the other two phases, and why does it matter for tree design?

  1. Bookkeeping ≤ 74% of total latency at the measured worst case (large core counts, Fig. 1).
  2. So send + wait together ≥ 26% of total latency at that point — nontrivial, but clearly the minority contributor.
  3. A tree that only parallelizes bookkeeping (splits the enqueue work across propagators) is attacking the majority term — consistent with why NUMA/L3 trees help at large scale.
  4. But 26% isn't zero — if a strategy's extra forwarding hops inflate "wait," it can erase bookkeeping's savings. That's exactly the Sysbench-on-Intel failure mode in §5.3.
🍯
Insight: a tree only pays off if the phase it speeds up (bookkeeping) is actually the bottleneck for that workload — which is why the same strategy helps on one platform/workload and hurts on another.

② AMD's three-level fan-out, in numbers

AMD EPYC 7643: 2 sockets × 8 CCDs × 12 logical cores = 192 logical cores. Trace the L3-clustered tree's maximum fan-out at each level.

  1. Level 0 → 1 (NUMA propagators): initiator sends to the first-layer propagator(s) of each remote socket — 1 inter-socket IPI per remote node.
  2. Level 1 (first-layer propagator): forwards to up to 7 other CCD propagators in its own socket (8 CCDs − itself = 7), plus directly notifies the 11 other cores in its own CCD (12 − itself).
  3. Level 2 (each second-layer CCD propagator): notifies up to 11 remaining cores in its own CCD (12 − itself).
  4. Worst-case depth: initiator → remote first-layer propagator → remote CCD propagator → remote core = 3 hops, vs. native Linux's 1 hop from an overloaded initiator to every target.
💡
More hops, but each hop's fan-out (≤11, ≤7) is small enough that total wall-clock time drops — the whole bet of tree broadcast is trading hop count for parallel width.

③ Converting speedup multipliers to latency cuts

The paper reports 1.38× (Intel, NUMA) and 1.90× (AMD, L3) as the peak microbenchmark speedups. How much latency does each actually remove?

  1. Speedup S means new latency = old / S. So the fraction of latency removed is 1 − 1/S.
  2. Intel, 1.38×: 1 − 1/1.38 = 1 − 0.725 = 27.5% latency cut.
  3. AMD, 1.90×: 1 − 1/1.90 = 1 − 0.526 = 47.4% latency cut — nearly half the shootdown time, at 192 threads.
  4. At the low end (0.55–0.60×, small target sets): that's negative — new latency = old/0.55 ≈ 1.8× worse. Trees actively hurt when there's little bookkeeping to parallelize.
🍯
Insight: AMD's bigger multiplier isn't a better algorithm — it reflects that AMD's extra CCD layer gives L3-clustered more structural work to parallelize than Intel's flatter, single-L3-per-socket design.

④ How much of Apache's gain was really the broadcast tree?

Apache throughput vs. native Linux: 1.14× (Intel, L3) / 1.06× (AMD, L3). Vs. the eager-flat baseline (native Linux, lazy-TLB filter removed, same topology): ~1.00× (Intel) / ~0.92–0.93× (AMD).

  1. Gain vs. native: Intel +14%, AMD +6% — this is what a reader would naively credit to the broadcast topology.
  2. Gain vs. eager-flat: Intel ≈ 0%, AMD negative (−7 to −8%) — once target-set bloat is already fixed, the tree adds no further benefit and on AMD even costs a little (extra forwarding overhead with nothing left to parallelize).
  3. Conclusion: target-set reduction (P4), not the broadcast topology (P1–P3), explains essentially all of Apache's measured gain.
💡
This is the paper's most important caution for anyone building on this work: measure target-set size before crediting a latency win to the broadcast structure.
Test yourself

Practice problems

Try before opening the answer. Each ends with the misconception it checks.

Problem 1 · easy
A shootdown targets only 6 cores, all on one socket. Should you expect a tree-based strategy to help?
Show answer
No — probably not. The paper shows native Linux wins at small target-set sizes (e.g. ~8 threads), because tree construction and propagator coordination add fixed overhead that a tiny serial loop doesn't need to amortize. Trees pay off once bookkeeping cost, which scales with target count, becomes the dominant term.Misconception: that "topology-aware" always means "faster." It's conditional on target-set size being large enough to need parallelizing.
Problem 2 · medium
Why does L3-clustered collapse to NUMA-clustered (with extra overhead) on the Intel platform specifically, but not on AMD?
Show answer
L3-clustered adds a third tree level based on L3/CCD boundaries. On Intel Xeon 8260, all 48 logical cores in a socket share one L3 — there's no finer L3 boundary within a socket to exploit, so the extra level is structurally a no-op, just added bookkeeping. On AMD EPYC 7643, each socket has 8 separate L3 domains (one per CCD), so the extra level does real work, clustering propagation within each 12-core CCD before crossing to others.Misconception: that a strategy's name describes a fixed structure. L3-clustered's actual shape depends entirely on how many L3 domains a given platform has.
Problem 3 · medium
On Sysbench, tree-based strategies hurt performance on Intel at large thread counts but help on AMD. What does the paper suggest as the explanation?
Show answer
A phase trade-off: tree strategies primarily reduce sender-side (bookkeeping) contention but can increase remote completion ("wait") time due to extra forwarding hops. The paper's data suggests waiting time dominates Sysbench's shootdown latency on Intel, so trees lose more on the wait phase than they gain on bookkeeping. This trade-off is less pronounced on AMD.Misconception: that reducing one phase's cost always reduces total latency. If a different phase dominates for a given workload, speeding up the wrong phase can net negative.
Problem 4 · hard
The Adaptive (Smelt-derived) tree uses measured pairwise IPI costs to build an in-principle optimal propagation order, yet it performs worst of the three strategies on both platforms. Why?
Show answer
Smelt assumes a static core set and fixed communication costs when building its tree offline. TLB shootdown target sets vary per call, so the paper precomputes a full tree per possible initiator at boot and prunes it at dispatch time to fit the actual target set. That naive pruning doesn't preserve the tree's balance/cost guarantees, so the resulting structure's extra pruning and forwarding overhead outweighs whatever initiator-side savings it achieves.Misconception: that a theoretically better-optimized tree is automatically better in practice. Implementation cost (pruning a precomputed structure on the hot path) can erase an algorithm's theoretical advantage.
Problem 5 · medium
A core is in lazy-TLB mode and gets skipped during a shootdown. Is it removed from mm_cpumask at that point?
Show answer
No. The lazy-TLB filter only excludes the core from that specific shootdown's IPI dispatch — it stays in mm_cpumask and can reappear as a target in every subsequent shootdown until it's explicitly removed, which happens later on a context switch.Misconception: that "skipped" means "forgotten." Skipping avoids one unnecessary IPI but doesn't fix the underlying target-set bloat, which is why eager removal (P4) is a separate, additional optimization.
Problem 6 · hard
Apache's throughput gain from tree-based strategies nearly vanishes once compared against an "eager-flat" baseline. Does this mean the tree-based broadcast work (P1–P3) was pointless?
Show answer
Not pointless — just not what explains Apache specifically. The microbenchmark (§5.2) isolates target-set size and still shows trees winning at large counts (up to 1.9×), so the topology-aware propagation genuinely helps when target sets are large and stable. Apache's workload happens to have a large share of its overhead coming from lazy-TLB bloat rather than raw target-set size, so for *that* workload, P4 dominates. The paper's point is that both factors are real and largely independent — crediting either one requires isolating the other, as the eager-flat re-baseline does.Misconception: that one experiment showing a smaller effect invalidates the mechanism elsewhere. The two factors (topology, target-set size) have different weight in different workloads.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Why can't TLBs just be made hardware-coherent, like data caches?▾
They're not architected that way on x86 — there's no snooping protocol for translation entries. Some newer ISAs/extensions (AMD INVLPGB, Arm broadcast TLBI) offer partial hardware-assisted invalidation, but the paper notes software IPI broadcasts remain necessary on many platforms and are reused for other kernel mechanisms (CPU hotplug, RCU, scheduling), so the software path still matters.
Q2Is this paper proposing a new algorithm, or a new implementation structure?▾
Structure, mainly. The three strategies don't change what gets invalidated or when — they change who sends the IPI to whom. It's a broadcast-topology change layered under the existing Linux shootdown semantics via a hook in flush_tlb_mm_range().
Q3Why does bookkeeping scale with target count rather than being constant?▾
Each target gets its own CSD struct living in that target's per-CPU memory. The initiator must touch (acquire, fill, enqueue) one CSD per target, serially, including remote memory accesses and cache-line ownership transfers for distant cores — so the work is inherently O(targets), one core at a time.
Q4What's the actual difference between "send" and "wait" in the measurements?▾
Send is strictly the initiator-side time to issue IPIs via the Interrupt Control Register and return. Wait starts after dispatch and covers everything else: propagation delay, the remote handler starting, the actual TLB invalidation, and the completion signal — ending only when all target CSD busy bits clear.
Q5Do the propagator sets change between shootdowns?▾
Yes, deliberately. If the same cores were always propagators, they'd become hotspots under concurrent shootdowns. The NUMA-clustered tree round-robins among up to four propagators per node; the L3-clustered tree picks statically (lowest-indexed participating CPU per CCD) since AMD's per-CCD fan-out is already small enough that round-robin isn't needed there.
Q6Does the paper give a way to automatically pick the best strategy at runtime?▾
No — explicitly left as future work. The authors describe the ideal as a lightweight cost model trading sender parallelism against forwarding/completion overhead, but note building an accurate, cheap version of it is nontrivial.
Q7Why does the Intel platform show a performance dip, and AMD show an inflection around 96 threads?▾
Both platforms have 96 physical cores; beyond that, additional "threads" are SMT siblings sharing core resources. The paper attributes a relative performance increase for most tree-based strategies beyond 96 threads to greater contention for the initiator's core-local resources, which hurts the single-core-bottlenecked native strategy more than the distributed tree strategies.
Q8Is eager target-set cleanup specific to Apache, or general?▾
General — it's P4, one of the paper's four design principles, implemented as removing the lazy-TLB filter's "skip but don't evict" behavior. It matters most for workloads like Apache's event MPM that leave many threads/cores idle (lazy) at any given time, since those idle cores would otherwise accumulate in mm_cpumask.
Q9What platforms/OSes besides Linux have this same initiator-bottleneck structure?▾
The paper notes Solaris, OpenBSD, and XNU all implement an inherently sequential shootdown procedure concentrating coordination on a single core — the bottleneck this paper targets isn't Linux-specific, though the implementation (hooked into flush_tlb_mm_range()) is.
Q10Could this broadcast-tree idea apply beyond TLB shootdowns?▾
The authors suggest yes — any IPI-based notification mechanism with a similar fan-out pattern, such as CPU hotplug/offlining or RCU grace-period signaling, could in principle benefit from the same tree-based propagation, though this isn't evaluated in the paper.

For the tiering/CXL reader

Why this matters beyond TLB shootdown alone

framing, not in the paper

Any page-migration path in a DRAM/NVM or CXL tiering system (promotion/demotion, like TPP- or HeMem-style hot/cold moves) still has to shoot down the moved page's old translation on whichever cores might have cached it — not literally every core sharing that mm, but however that migration design tracks or approximates its target set. This paper's two levers — bookkeeping cost scaling with target-set size, and lazy-TLB residue inflating that target set — apply directly: a tiering engine that migrates pages touched by many threads pays the same initiator-bottleneck tax, and stale mm_cpumask entries from idle threads can make migration shootdowns look more expensive than the true active footprint.
