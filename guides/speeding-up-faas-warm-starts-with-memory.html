DIMES 2026 · A Field Guide

Waking a VM only where it actually walks, not page by page

An idle FaaS VM sits compressed in memory to save DRAM. The instant a new request arrives, it must decompress itself back to life — one costly page fault at a time. This is the plain-English story of MRT, which learns the route in advance and restores it in one parallel burst.

📄 "Speeding up FaaS Warm Starts with Memory Restoration Templates" · Prasad, Subramoney, Kumar, Kervinen 🎓 Some virtualization/OS basics assumed — the primers cover them ⏱ ~25 min read
🧳

Learn which pages a warm start actually touches, then restore that set in one parallel burst — instead of discovering them one fault at a time.
Measure the route once, replay it fast every time after.

Before you begin

Quick glossary, then ten ideas the paper assumes

Acronyms first — glance at them once. Then the primer cards, collapsed by default; read in order the first time, or jump to whatever looks unfamiliar.

Quick glossary

FaaSFunction-as-a-Service — cloud model where small pieces of application logic run on demand inside isolated sandboxes.
VM / VMMVirtual Machine and Virtual Machine Monitor (e.g. Firecracker) — the isolation boundary for a function and the host process managing it.
CSPCloud Service Provider — operates the servers, packs VMs onto them, and pays for every byte of idle memory.
zswapLinux's in-kernel compressed swap cache — cold pages are compressed and kept in a memory pool instead of going to disk.
IAAIntel In-Memory Analytics Accelerator — hardware with multiple engines that (de)compress pages, fastest when fed many jobs in parallel.
MRTMemory Restoration Templates — this paper's mechanism: a recorded page-fault sequence used to bulk-restore a VM in one parallel burst.
RSSResident Set Size — the DRAM a process actually occupies right now (as opposed to its total virtual size).
VM exitA trap from guest to host triggered by, e.g., a page fault on a compressed page — costly because it interrupts guest execution.
TCOTotal Cost of Ownership — memory is 33–50% of a data center's TCO, which is why idle-VM memory matters so much.
ASLRAddress Space Layout Randomization — if disabled, a VM's virtual addresses stay stable across restarts, which is what lets a template be replayed.
MRT — the fix hot start — the reference baseline template/kernel machinery on-demand IAA — the warm-start baseline being replaced
1FaaS and VM-based sandboxes▾

A FaaS function is a small piece of logic that runs in response to an event. For security, each function runs isolated — often inside a lightweight VM like Firecracker (a "microVM"), which boots a minimal guest kernel under a thin hypervisor. Some setups use user-space sandboxes like gVisor instead; this paper targets the VM case.

Now you're ready: MRT operates on VM (or VM-like) memory — pages backed by a regular host process that can be swapped and compressed.
2The hot / warm / cold start spectrum▾

A hot start reuses an idle VM whose memory is still fully resident in DRAM — fastest (3–381 ms in this paper). A cold start boots a brand-new VM from scratch — slowest (1.3–2.6 s, ~62× slower, gmean). A warm start reuses an idle VM whose memory has been compressed away — faster than cold, slower than hot.

Now you're ready: MRT's whole goal is to pull warm starts as close to hot-start latency as possible, without paying hot start's memory cost.
3Why idle VMs are a memory problem▾

Unlike CPU time, memory is held even when nothing runs. An idle VM kept around to enable fast hot starts still occupies its full DRAM footprint, capping how many active VMs (of other users) fit on the same server. Terminating idle VMs frees that memory but forces a slow cold start on the next request.

Now you're ready: this is the exact trade-off MRT is built to dissolve — keep the VM's identity and state, but shrink its footprint while idle.
4Memory compression and zswap▾

Instead of writing cold pages to disk, Linux's zswap compresses them and keeps them in a compressed memory pool in DRAM. Each compressed page becomes a "swap entry" in its page table; touching it later triggers a page fault that decompresses it back.

Now you're ready: MRT places an entire idle VM's pages in zswap instead of on disk — no disk round-trip, just a decompression cost on first touch.
5Page faults, swap-in, and VM exits▾

Accessing a compressed page faults; the host must trap the access (a VM exit for guest memory), allocate a page, find and decompress the data, and update the page table before resuming the guest. Doing this one page at a time, serially, for every touched page is expensive — both in decompression time and in accumulated VM-exit overhead.

Now you're ready: this serial, one-page-at-a-time path is exactly what on-demand IAA restoration does, and exactly what MRT bypasses.
6Hardware compression accelerators (IAA) and parallelism▾

Intel's IAA has multiple independent (de)compression engines. It only reaches peak throughput when many jobs are submitted at once — one page per fault submits one job at a time, so most of the accelerator's engines sit idle.

Now you're ready: MRT's entire performance story is "give IAA many jobs simultaneously" instead of one job per fault.
7Readahead — sequential prefetching, and why it can fail here▾

A classic trick: on a fault at page X, also prefetch X+1, X+2, …, betting on spatial locality. This works well for many programs, but inside a VM the guest's virtual addresses and the host's virtual addresses are related through two levels of indirection — sequential in the guest need not be sequential on the host.

Now you're ready: this is why the paper's IAA-b8 (batch readahead) baseline barely helps — it's solving the wrong locality.
8Working-set record-and-prefetch (prior art)▾

Before MRT, systems like REAP and FaaSnap recorded which pages a snapshot-restored VM touched on its first invocation. REAP bulk-loads that recorded working set from disk on later invocations, reducing scattered on-demand disk reads; FaaSnap instead tracks which of those pages are still resident in the host page cache, to handle input-dependent variation in what a function actually touches.

Now you're ready: MRT borrows this "record once, replay in bulk" idea but applies it to a live, already-initialized VM restoring from an in-memory compressed pool via a hardware accelerator, not from disk.
9Profiling and frequency thresholds▾

A single profiling run gives a usable template, but page-fault sequences vary slightly run to run (different inputs, background daemon activity). Profiling multiple warm starts and keeping only addresses that recur across most of them (e.g. a 90% threshold) filters out noise while capturing the stable, function-critical pages.

Now you're ready: this filtering is what keeps templates from restoring pages nobody needs, and from encoding one-off housekeeping faults.
10Tail latency — why p95/p99 matters more than the average▾

At scale, most requests hit an already-warm VM (fast), but some land on a still-compressed one mid-restoration (slow). Averages hide this; the 95th/99th percentile latency captures exactly the unlucky tail of requests — the ones users actually notice.

Now you're ready: MRT's at-scale results are reported as tail-latency reductions, because that's where on-demand restoration actually hurts.
The whole story in one place

MRT in a nutshell

The trade-off, the fix, and the numbers that make it convincing.

CSPs keep idle FaaS VMs around so the next request gets a fast hot start — but every idle VM still occupies its full DRAM footprint, limiting how many active VMs fit on a server (memory is 33–50% of data-center TCO). The paper's fix is to compress an idle VM's pages into zswap instead of terminating it or snapshotting it to disk. That shrinks its footprint, but the next invocation now has to decompress its way back to life — and doing that one page fault at a time, with a guest-to-host VM exit per page, is slow: 2.63× hot-start latency (gmean), up to 7.7× for some functions. Simple sequential readahead barely helps (2.51×), because guest-sequential addresses aren't host-sequential.

MRT instead profiles a VM's warm starts, records the sequence of virtual addresses that actually fault, and — on the next invocation's very first fault — bulk-restores that whole recorded set asynchronously, submitting many decompression jobs to IAA's engines in parallel instead of one at a time. Addresses that don't recur across multiple profiling runs are filtered out and left to the ordinary on-demand path; the paper treats this as a quality/effort trade-off rather than a free lunch — more profiling runs cost more but better filter out one-off noise, and it leaves quantifying that trade-off to future work. Over-aggressive filtering can also strip out pages that were legitimately input-dependent rather than noise.

The payoff: warm-start latency drops to 1.62× hot start — eliminating 62% of the overhead on-demand restoration added — while idle-VM memory footprint still falls 57% (gmean) via compression. At scale, MRT cuts 95th- and 99th-percentile latency by 70% and 58% relative to on-demand IAA, at a template storage cost of roughly 0.2% of the memory it restores.

🍯 Key takeaways

  • Compressing idle VMs into zswap (not disk) shrinks memory footprint by 57% gmean without terminating the VM.
  • On-demand, one-page-at-a-time IAA restoration is 2.63× hot-start latency — serial VM exits and idle accelerator engines are the culprits.
  • Sequential readahead (IAA-b8) barely helps (2.51×) — guest-sequential ≠ host-sequential across two levels of address indirection.
  • MRT profiles real warm-start fault sequences into a template, then bulk-restores them via IAA's engines in parallel — 1.62× hot start, 62% of the added overhead eliminated.
  • Templates are cheap: one 8-byte virtual address per tracked 4 KiB page ≈ 0.2% of restored memory.
  • At scale, tail latency (p95/p99) is where on-demand restoration hurts most — and where MRT's gains concentrate (70%/58% cut vs IAA).
💡
For a tiering researcher: MRT is a promotion policy for a compressed "far tier" (zswap), triggered by an application-level event (function invocation) rather than a hardware access-bit scan. It's a narrower, workload-specific cousin of the hot-set prediction problem that DRAM/NVM tiering systems solve continuously — and the paper's own future-work section explicitly floats placing the compressed pool in a byte-addressable CXL far-memory tier.
Seven everyday pictures

How to think about MRT

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Restore only what's used

A day-bag, not the whole closet

You pack a small bag with exactly what a weekend trip needs — not your entire closet. MRT restores only the subset of pages a function's template says it will actually touch, not the whole VM's memory. The rest stays compressed, decompressed only if genuinely needed.

Where it breaks: if a function's behavior drifts (new code path, unusual input), the bag is missing something — that page just falls back to an ordinary, slower on-demand fault.
Profiling → template

A grocery list from last week's trip

Instead of wandering the aisles deciding what you need as you go, you write down what you actually bought last time and follow that list directly. MRT profiles real warm starts and records the exact sequence of faulting virtual addresses — the "list" that future warm starts replay.

Where it breaks: the list is written for this store's layout — a different host has different virtual-address mappings for the same VM, so the template must be re-recorded there, not copied over.
Why on-demand IAA is slow · parallelism

One courier vs a loading dock of trucks

A single courier walking one package over at a time is slow no matter how many delivery trucks (accelerator engines) are parked and ready. On-demand IAA restoration submits exactly one decompression job per fault — so most of IAA's engines sit idle. MRT instead hands the whole recorded template to the dock at once, filling every truck.

Where it breaks: the trucks still need somewhere to unload — DRAM capacity and bandwidth are finite, so restoring an enormous template at once isn't free either.
Why readahead fails · address indirection

Two street grids overlaid at an angle

Your mental map of a neighborhood (the guest's virtual addresses) doesn't line up with the delivery company's internal warehouse map of the same packages (the host's virtual addresses). "Next door" on your map can be anywhere on theirs. Grabbing the "next few pages" after a fault (readahead) assumes the two maps are aligned — they usually aren't.

Where it breaks: the two grids aren't always misaligned — some functions do have sequential guest access patterns, which is why readahead isn't zero benefit, just unreliable (2.51× vs 2.63×).
Filtering noise · frequency threshold

Counting hands raised, keeping the consistent votes

Ask the same question in several rounds and keep only the answers that came up almost every time — a one-off outlier (a background daemon's stray fault) gets dropped. MRT profiles multiple warm starts and keeps addresses that recur across, say, 90% of them, filtering out housekeeping noise without any explicit hints from the guest.

Where it breaks: a function whose real logic branches on input (different code paths each run) can have legitimately variable page needs — the threshold can't distinguish "noise" from "input-dependent behavior" on its own.
Where compressed pages live · in-memory pool vs disk

Vacuum-sealed in the same closet, not shipped across town

Vacuum-sealing off-season clothes keeps them in the same closet, compact but reachable in seconds — shipping them to a storage unit across town saves more space but costs a slow trip to retrieve. Compressing an idle VM's pages in zswap (same machine, same DRAM) avoids the "trip" that disk-based snapshotting requires.

Where it breaks: the vacuum bag still needs a moment to reopen — decompression cost doesn't vanish, it's just far cheaper than a disk trip. That remaining cost is exactly what MRT is built to hide.
Reusing templates · sibling instances

A relay handoff you've rehearsed

Once one runner has rehearsed the exact handoff, any teammate running the identical leg can reuse that same choreography. A template recorded from one VM instance can restore any other instance of the same user, function, runtime, and VM configuration on the same host, since they share the same virtual-address layout.

Where it breaks: move to a different host and the "track" itself changes — virtual-address layouts differ machine to machine, so the template must be freshly recorded there.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt as visuals you can read at a glance.

1 · The trade-off — keep idle VMs alive, or reclaim their memory?

CSPs reuse idle VMs to serve requests as fast hot starts rather than paying a cold start's ~62× (gmean) latency penalty for forking and booting a fresh VM. But every idle VM held in reserve keeps consuming its full DRAM footprint — memory alone is 33–50% of data-center TCO — capping how many active VMs of other users fit on the box. Terminating idle VMs frees that memory, at the cost of the next request paying full cold-start latency.

2 · The proposed middle ground — compress, don't terminate

Rather than a disk-based snapshot (slow, scattered reads) or outright termination, the paper places an idle VM's pages in a zswap compressed memory pool, backed by Intel IAA for fast hardware (de)compression. This is the warm start: faster than cold, but still slower than hot, because the first accesses after reactivation each fault, trap to the host (a VM exit), and decompress serially.

⚠
The catch: IAA reaches peak throughput only with many parallel jobs. A fault-driven path submits one job per page — exactly the case where the accelerator is starved of work, regardless of how fast it could otherwise run.

3 · Triggering restoration

Restoration fires just in time: the idle VM's very first page fault after a new invocation triggers the kernel to bulk-restore the entire template, asynchronously, in the background, submitting many decompression jobs to IAA's engines in parallel. Templated pages touched after asynchronous restoration completes are already resident and pay no fault; but any access — templated or not — that arrives before restoration finishes still falls back to the ordinary on-demand fault path.

🌱
Where CSP-side invocation prediction is available (e.g. Azure's time-series forecasting of next invocation time), restoration can start even earlier — before the first fault — hiding the cost entirely. The paper treats this as a further, optional optimization on top of the just-in-time trigger.
PathNormalized latency (gmean)MechanismLimitation
Hot start1.00×VM & runtime already resident in DRAMRequires paying full idle-VM memory cost

MRT1.62×Bulk, parallel restore of a profiled templateFirst fault still pays a cost; untemplated pages still fault on demand

4 · Template management and size

A template stores one 8-byte virtual address per tracked 4 KiB page, in the order it first faulted. It's kept in a per-VM buffer, uploaded to the kernel through a /proc/<vm_pid>/ interface, and remains valid as long as the function, runtime, and VM configuration it was recorded for don't change (with ASLR disabled, so virtual addresses stay stable). A control file lets the cloud management software trigger, reset, or disable restoration.

# restoration, triggered on the VM's first post-invocation fault
on first_fault(vm):
    pages = template[vm.user, vm.function, vm.runtime, vm.config]
    submit_parallel(pages, iaa_engines)   # many jobs at once, async
    resume_guest()                        # faulting page decompresses inline; rest in background

# any access to a not-yet-restored, non-templated page
on other_fault(vm, page):
    decompress_one(page)                  # ordinary on-demand fallback — no correctness impact
💡
Why this doesn't need to be perfect: template-based restoration is purely a performance optimization. A restored-but-unused page (false positive) just wastes some decompression bandwidth and DRAM; an accessed-but-untemplated page (false negative) simply falls back to the regular fault path. Correctness never depends on the template being exactly right.

5 · Why gains vary by function

The size of MRT's improvement tracks the ratio of page-restoration overhead to compute time. Millisecond-scale functions (dd, LR-Serving, pyaes, chameleon, RNN-Serving — all ≤16 ms hot-start latency) spend nearly all of their warm start serving serialized faults, so eliminating those faults yields the largest relative gains. Compute-dominated functions (float, matrix-mul, video-proc; 119–381 ms hot-start latency) already amortize the same restoration cost over a much longer execution, so their warm-start penalty is small to begin with (1.11–1.24× even with plain on-demand IAA) and MRT has less room to improve — though it still brings float and video-proc within 3% of hot-start latency.

Follow the numbers, step by step

Worked examples

Five calculations, each using the paper's real reported numbers.

① Turning "2.63× → 1.62×" into "62% of overhead eliminated"

The paper claims MRT eliminates 62% of the overhead on-demand IAA restoration adds over a hot start. Check it.

  1. Overhead is measured above the 1.00× hot-start floor. IAA's overhead = 2.63 − 1.00 = 1.63 (hot-start units).
  2. MRT's overhead = 1.62 − 1.00 = 0.62.
  3. Fraction eliminated = (1.63 − 0.62) / 1.63 = 1.01 / 1.63 ≈ 62.0%.
🍯
Insight: reporting relative to hot start (the true floor) rather than raw latency is what makes "62%" meaningful — it isolates the restoration overhead from the function's own unavoidable compute time.

② Function-specific gains: LR-Serving vs dd

The paper reports LR-Serving improves from 7.7× to 2.3× hot start, and dd from 7.3× to 2.5×, under MRT. How much overhead did each eliminate?

  1. LR-Serving: IAA overhead = 7.7 − 1 = 6.7; MRT overhead = 2.3 − 1 = 1.3. Eliminated = (6.7 − 1.3)/6.7 ≈ 80.6%.
  2. dd: IAA overhead = 7.3 − 1 = 6.3; MRT overhead = 2.5 − 1 = 1.5. Eliminated = (6.3 − 1.5)/6.3 ≈ 76.2%.
  3. RNN-Serving is reported to match its hot-start latency under MRT — essentially 100% of its overhead eliminated.
  4. All three beat the 62% gmean, because they're millisecond-scale functions where restoration serialization dominates — exactly where MRT's parallel bulk restore helps most.
💡
The gmean (62%) blends these large wins with the smaller wins on compute-dominated functions (see example ③) — always check whether a headline average includes both regimes.

③ Compute-dominated functions have less room to improve

float, matrix-mul, and video-proc have hot-start latencies of 119–381 ms and only 1.11–1.24× warm-start penalty even with plain on-demand IAA. Why does MRT help them so much less in relative terms?

  1. Take a representative case: hot-start = 200 ms, IAA warm-start = 1.20× → 240 ms. Restoration overhead ≈ 40 ms.
  2. That same ≈40 ms of restoration work exists whether the function computes for 16 ms (dominates the warm start) or 200 ms (a small fraction of it).
  3. MRT can only remove restoration overhead, not compute time — so shaving even most of that 40 ms barely moves a 240 ms total, while for a 16 ms function the same 40 ms removed is the whole story.
  4. Consistent with the paper: MRT still brings float and video-proc to within 3% of hot-start latency — a real, if smaller, win.
🌱
Illustrative arithmetic above; the paper reports the ranges (1.11–1.24× IAA overhead, within 3% under MRT) without a single per-function breakdown for these three.

④ Memory footprint reduction from raw RSS numbers

Idle-VM RSS drops from 157–351 MB to 64–147 MB across functions (57.3% gmean). Check the reduction at both ends of the range.

  1. Largest VM: 351 MB → 147 MB. Reduction = (351 − 147)/351 ≈ 58.1%.
  2. Smallest VM: 157 MB → 64 MB. Reduction = (157 − 64)/157 ≈ 59.2%.
  3. Both bracket the reported 57.3% gmean — consistent because compression ratio depends on how compressible each VM's guest-OS and runtime state is under deflate, not on absolute VM size.
  4. In absolute terms this is a 2.2–2.6× reduction in resident memory per idle VM instance — memory the paper argues can let CSPs host more active VMs per system, though it doesn't evaluate a direct capacity conversion, and other resources (CPU, network) may bind first.

⑤ Template storage cost — the 0.2% figure

The paper states a template's size is bounded by ~0.2% of the memory it restores. Derive it.

  1. Per tracked page: one 8-byte virtual address is stored.
  2. Each tracked page is 4 KiB = 4096 bytes of restored memory.
  3. Ratio: 8 / 4096 = 0.001953… ≈ 0.20%.
  4. So a template for, say, a 150 MB restored footprint costs roughly 150 MB × 0.2% ≈ 300 KB — negligible next to the memory it manages, and completely independent of VM size.
🍯
Insight: because the ratio (8 B / 4 KiB) is fixed by page size, not by workload, template overhead scales linearly and predictably with however much of the VM the template ends up covering.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it checks.

Problem 1 · easy
Does MRT decompress a VM's pages before any new request even arrives?
Show answer
Not by default — restoration triggers just in time, on the VM's first page fault after a new invocation arrives. (The paper does note that ahead-of-time restoration is possible if a CSP already has invocation-time prediction infrastructure, like Azure's, but that's an additional optimization, not the core mechanism.)Misconception: that "template-based" means "pre-restored." The template only changes how restoration happens (bulk, parallel) — not that it happens before any access at all.
Problem 2 · medium
A function's on-demand-IAA warm start is 5.0× hot start, and MRT brings it to 1.8×. What fraction of the added overhead did MRT eliminate?
Show answer
IAA overhead = 5.0 − 1 = 4.0. MRT overhead = 1.8 − 1 = 0.8. Fraction eliminated = (4.0 − 0.8)/4.0 = 3.2/4.0 = 80%.Misconception: computing the fraction directly on the raw multipliers (e.g. (5.0−1.8)/5.0 = 64%) instead of on the overhead above the hot-start floor. The paper's own "62%" figure uses the overhead-above-floor method.
Problem 3 · medium
Why does IAA-b8 (readahead batching of 8 pages) barely beat plain on-demand IAA (2.51× vs 2.63×), even though it also submits multiple decompression jobs?
Show answer
Submitting 8 jobs helps only if those 8 pages are actually going to be needed. Readahead grabs the 8 pages spatially adjacent to the faulting address in the host's address space — but because guest-sequential accesses aren't host-sequential (two levels of address indirection), most of those 8 pages aren't on the function's real access path. It parallelizes decompression, but of mostly the wrong pages.Misconception: that "submitting multiple jobs in parallel" is the whole fix. Parallelism only pays off if the batch is the right set of pages — which is exactly what a profiled template provides and spatial readahead doesn't.
Problem 4 · hard
A CSP wants to reuse a template recorded on VM instance A for a fresh sibling VM instance B of the same user. Under what conditions is this safe, and why?
Show answer
Safe when B has the identical function, runtime, and VM configuration as A, on the same host, with ASLR disabled so both instances get the same virtual-address layout. The recorded addresses are meaningful only relative to that specific mapping; move to a different host (different address-space layout) or a different configuration, and the same addresses no longer correspond to the same logical pages, so the template must be regenerated locally.Misconception: that templates are portable data, like a config file, that can ship anywhere. They're tied to a specific host's virtual-address mappings for a specific configuration — not globally portable.
Problem 5 · medium
A page is restored by MRT's template but the function never actually touches it during that invocation. Does this cause a bug?
Show answer
No. This is a false positive, and template-based restoration is purely a performance optimization with no correctness implications — the page is decompressed unnecessarily, costing some decompression bandwidth and DRAM until it's reclaimed again, but nothing is wrong or inconsistent.Misconception: that imperfect templates risk correctness. Only performance is at stake; the on-demand fault path remains available as a safety net for anything the template gets wrong in either direction.
Problem 6 · hard
At scale, median latency across Hot Start, IAA, IAA-b8, and MRT is roughly the same (42–46 ms), yet 95th/99th percentile latencies differ dramatically. Explain why, in terms of which VMs a given request lands on.
Show answer
Most requests arrive after the pool of idle VMs has already been restored (or never went idle), so they hit an already-warm instance regardless of which restoration mechanism is configured — hence similar medians. The tail (p95/p99) is made up of the unlucky requests that land on a VM still mid-restoration right after it transitions from idle to active; that's precisely where the restoration mechanism's speed matters, and where MRT's bulk parallel restore dramatically outperforms serial on-demand IAA.Misconception: that similar medians mean the mechanisms perform similarly overall. Averages/medians can hide a mechanism's entire benefit if that benefit is concentrated in a minority of requests — exactly the case here.
Problem 7 · medium
Why does the paper place idle VM pages in zswap rather than snapshotting to disk, as prior systems like REAP do?
Show answer
Disk-based snapshot restoration means scattered, on-demand reads from a much slower medium, plus cold-fork reconstruction that may not preserve live state such as network/socket connections. Placing pages in an in-memory compressed pool (zswap) keeps the VM live and already-initialized — restoration only has to pay a decompression cost, not a disk I/O cost, and no state needs to be reconstructed.Misconception: that "compressed" and "snapshotted to disk" are the same idea with different storage media. They differ in whether the VM stays live: zswap keeps a live, running VM's pages compressed in DRAM; disk snapshotting checkpoints and later reconstructs a new instance from scratch.
Problem 8 · easy
Does the size of an MRT template depend on how large the VM's total memory is?
Show answer
Not directly — it depends on how many pages are actually tracked (i.e. how many pages faulted across profiling and passed the frequency filter), not on the VM's total memory. At a fixed 8 bytes per tracked 4 KiB page (≈0.2%), a VM with a small but heavily-used working set and a VM with a huge one produce templates roughly proportional to the number of pages the function's execution genuinely touches.Misconception: that template size scales with total VM memory. It scales with the number of pages the profiled template actually needs to restore — which is typically a small fraction of a VM's full footprint.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What problem is MRT actually solving?▾
CSPs want to keep idle FaaS VMs around for fast hot starts, but idle VMs still consume full DRAM, limiting how many active VMs fit per server. MRT lets CSPs compress idle VMs into a memory pool (shrinking footprint 57% gmean) while keeping the resulting warm-start latency close to hot start (1.62× vs 2.63× for naive on-demand decompression).
Q2What's the difference between hot, warm, and cold starts?▾
Hot: an idle VM whose memory is still fully resident in DRAM (3–381 ms). Cold: booting a brand-new VM from scratch (1.3–2.6 s, ~62× slower gmean). Warm: an idle VM whose memory was compressed away and must be decompressed on this invocation — faster than cold, slower than hot, and exactly what MRT optimizes.
Q3Why not just decompress pages as they're needed (on demand)?▾
Because each fault costs a guest-to-host VM exit plus a decompression, and doing this serially, one page at a time, both accumulates VM-exit overhead and starves IAA of the parallel job submissions it needs to reach peak throughput. This is exactly the 2.63× hot-start latency baseline MRT improves on.
Q4Why doesn't simple sequential readahead fix this?▾
Readahead assumes accesses adjacent in the guest's virtual address space are also adjacent in the host's — but two levels of address indirection mean that's often false in a virtualized setting. The paper measures readahead (IAA-b8) at 2.51× hot start — barely better than plain on-demand (2.63×).
Q5How is an MRT template built?▾
The host profiles one or more real warm starts of a VM, recording the virtual addresses that fault (via perf or ftrace). Addresses that recur across a high fraction of profiling runs (e.g. ≥90%) are kept, in their original fault order; infrequent ones are dropped and left to the on-demand path.
Q6What happens to pages that aren't in the template?▾
They're restored the ordinary way: a page fault triggers on-demand decompression when the page is actually accessed. This is a graceful fallback, not an error — it's exactly how the system behaved before MRT existed.
Q7Can one template be reused across multiple VM instances?▾
Yes, for sibling instances of the same user/function/runtime/VM-configuration running on the same host (with ASLR disabled so virtual-address layouts match). CSPs commonly run many identical instances of a user's VM to serve parallel requests, so one recorded template can restore all of them.
Q8Does MRT ever produce incorrect execution?▾
No — it's purely a performance optimization. A restored-but-unused page just wastes some bandwidth/DRAM; an accessed-but-untemplated page falls back to the normal fault path. Correctness never depends on the template being accurate.
Q9How big is a template, and what does it cost?▾
One 8-byte virtual address per tracked 4 KiB page — about 0.2% of the memory it restores. Per-VM buffers add negligible overhead on top. It's small enough that the paper doesn't report it as a meaningful cost anywhere in the evaluation.
Q10How does MRT relate to REAP, FaaSnap, and Sabre?▾
REAP records a snapshot-restored VM's working set and bulk-loads it from disk on later invocations. FaaSnap instead tracks which of those pages remain resident in the host page cache, to handle input-dependent variation in what a function touches. Sabre uses IAA to compress snapshot pages but still hides decompression behind disk I/O and retains cold-fork reconstruction. MRT instead restores a live, already-initialized VM directly from an in-memory compressed pool, avoiding disk entirely, while borrowing FaaSnap's idea of tolerating input variability via recurrence-based filtering.
Q11What's left for future work?▾
When to compress (timing policy, possibly informed by per-function invocation-pattern prediction), faster accelerators, placing the compressed pool in a byte-addressable far-memory tier such as CXL to further improve VM density, finer-grained characterization of decompression vs VM-exit cost and template hit rate, and how templates should adapt as function behavior drifts.
Q12Where does MRT sit in the system — guest, host, or hardware?▾
Entirely in the host: the host kernel monitors and records page faults, stores templates in per-process buffers exposed via a /proc/<vm_pid>/ interface, and drives bulk restoration through the IAA accelerator. The guest VM is unmodified and unaware that restoration is templated at all.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
MRT (Memory Restoration Templates)The paper's mechanism: a recorded, filtered sequence of page-faulting virtual addresses, used to bulk-restore a VM's pages in parallel via a hardware accelerator.
Warm startReusing an idle VM whose memory was placed in a compressed pool — faster than a cold boot, slower than a fully DRAM-resident hot start.
TemplateAn ordered list of 8-byte virtual addresses that reliably fault during a VM's warm start, filtered by recurrence across multiple profiling runs.
zswapLinux's compressed-swap subsystem; stores cold pages compressed in a DRAM pool rather than on disk.
IAAIntel In-Memory Analytics Accelerator; hardware with multiple parallel (de)compression engines, used here as a zswap backend.
Frequency thresholdThe recurrence rate (e.g. 90%) an address must meet across profiling runs to be included in the template.
Bulk restoreDecompressing a whole template's pages together, submitting many jobs to IAA's engines at once rather than one per fault.
Supporting terms
Hot / cold startHot: idle VM already DRAM-resident, fastest. Cold: fresh VM boot from scratch, ~62× slower (gmean) than hot.
VM exitA trap from guest execution to the host, triggered here by a page fault on a compressed page — costly on the on-demand path.
Readahead (IAA-b8)Prefetching spatially adjacent pages after a fault; largely ineffective here due to guest/host address indirection.
RSSResident Set Size — the DRAM footprint a VM (or VMM process) currently occupies.
VMMVirtual Machine Monitor process (e.g. Firecracker/QEMU) whose heap/stack hold vCPU and device state.
False positive / false negative (template)A restored-but-unused page, or an accessed-but-untemplated page — both are performance-only, not correctness, issues.
Tail latency (p95/p99)Latency of the slowest 5%/1% of requests — where MRT's gains concentrate at scale, even though medians look similar across configs.
