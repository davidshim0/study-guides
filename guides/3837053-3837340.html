Don't ask "is Rust safer." Ask what the three gates say about this driver

null_blk and its Rust rewrite rnull are matched as closely as upstream allows — both configured without memory backing, since rnull doesn't yet support it. Run them through KOxI's three evidence gates and they don't agree — and that disagreement, not a verdict, is the useful output.

Acronyms first, then the concepts

A quick-reference glossary, then ten short primers on what the paper assumes you already know. Collapsed by default — open what's unfamiliar.

1What a kernel block driver does, and why storage is a hot target for R4L▾

A block driver sits between the kernel's block layer and a device, translating I/O requests (read/write at some offset) into device operations. It runs on a hot path exercised millions of times a second, and decades of C drivers have accumulated real bug surface — exactly the profile R4L points at.

Now you're ready: KOxI targets this class of driver, using the smallest example — a synthetic block device with no physical hardware behind it.
2Memory safety, unsafe Rust, and what R4L actually guarantees▾

Safe Rust statically rules out out-of-bounds access, use-after-free, double-free, and data races at compile time. Code the compiler can't verify goes in explicit unsafe blocks — R4L keeps almost all of that confined to shared, audited abstraction crates, not driver code.

Now you're ready: the safety gate asks how much of a driver's historical bug surface falls into the class Rust's type system removes automatically — not how safe Rust is in the abstract.
3CWE classification — labeling a bug's mechanism, not its severity▾

A CWE ID names how a bug happens (CWE-190 = integer overflow, CWE-476 = NULL dereference) independent of how bad it turned out to be. Li et al.'s ACSAC taxonomy sorts CWEs into three super-classes: auto-eliminated by Rust, needs Rust's discipline but isn't automatic, or entirely language-unaffected (logic, validation, races).

Now you're ready: the safety gate is just this taxonomy applied to one driver's fix commits — a mechanical count, not a judgment call.
4Coverage-guided fuzzing and why crash attribution is hard▾

syzkaller mutates syscall sequences and uses kernel coverage feedback to steer toward new code paths, flagging crashes automatically. But a fuzzing VM also shakes bugs out of the harness, unrelated subsystems, and the hypervisor — raw crash counts overstate what the driver under test is responsible for.

Now you're ready: the fuzzing gate reports only the target-attributable stream (crashes whose report names the driver), separated from infrastructure noise.
5fio and the submit/complete path▾

fio issues I/O at controlled block size, access pattern, and queue depth, and reports IOPS/latency. Against a driver with no real data movement (like null_blk), fio isolates almost purely the per-operation cost of the block-layer plumbing — submit, complete, bookkeeping — rather than device throughput.

Now you're ready: the performance gate's deltas should be read as abstraction-layer overhead, not "Rust storage is slower."
6Statistical significance vs effect size (MWU and A12)▾

Mann–Whitney asks "is this difference distinguishable from noise?" (a p-value). Vargha–Delaney A12 asks "how big is the difference, in a scale-free way?" (0.5 = no difference; larger values mean the Rust sample more often produces the "greater" outcome — for the fuzzing gate specifically that outcome is more target-attributable crashes, so a bigger A12 is worse, not better). Requiring both a small p and a large A12 avoids flagging a regression that's statistically real but practically tiny.

Now you're ready: KOxI's fuzzing gate fails only on p<0.05 and A12≥0.71 — statistically distinguishable and practically large.
7Bootstrap confidence intervals and the Holm correction▾

A bootstrap CI resamples the observed data thousands of times to estimate how much a statistic (like median IOPS delta) would vary on repeat measurement — no assumption about the underlying distribution. When you test many cells at once (here 18), roughly one will look "significant" by chance alone; the Holm correction tightens the per-cell significance bar to control that family-wise error.

Now you're ready: the performance gate's "fail" isn't one lucky/unlucky cell — it survives correction across all 18.
8Why a matched C/Rust pair is rare and valuable▾

Comparing Rust's benefit against C usually means comparing different drivers, kernels, or configurations — confounded by everything else that differs. null_blk (C) and rnull (Rust) are, to the authors' knowledge, the only public, upstream, behavior-matched pair: same synthetic device, same purpose, different language.

Now you're ready: this is the smallest faithful end-to-end test of KOxI — not a claim that this pair represents all R4L storage drivers.
9Phase 1 screening vs Phase 2 gates — two different questions▾

Phase 1 asks "is this driver worth Rust's attention at all?" using four cheap lenses (historical risk, static unsafe surface, dynamic robustness, tractability) scored 0–3 each. Phase 2 only runs once a matched Rust driver exists, and asks the harder question: does this specific rewrite actually deliver on safety, robustness, and cost?

Now you're ready: a driver can screen as a strong Phase 1 candidate (null_blk does, 12/12) and still fail two of three Phase 2 gates — screening flags interest, gates verify delivery.
10Worst-of aggregation — why the gates aren't averaged▾

KOxI doesn't combine the three gate outcomes into one score. It reports them side by side, and the overall verdict is "evidence-supported" only if all three pass — any single failure makes the driver "not ready for direct replacement." A safety win can't be traded off against a performance loss.

Now you're ready: this is why null_blk/rnull's mixed profile (fail/pass/fail) resolves to a clear "not ready" — even though one gate looks great.
The whole story in one place

KOxI in a nutshell

The problem, the three gates, and what they found on the smallest possible test case.

R4L migration decisions currently rest on scattered, non-comparable evidence: an aggregate safety study here, a fuzzing dashboard there, ad hoc fio numbers posted per patch. None of it is matched (same driver, same kernel, same config), thresholded (a pre-declared pass criterion), or composed (a shared per-driver profile) — so the actual decision is still a mailing-list judgment call.

KOxI is an evidence-gated pipeline that fixes this by composing exactly three per-driver gates — safety, fuzzing, and performance — each with a declared threshold, preceded by a cheap Phase 1 screen that flags which drivers are worth the Phase 2 investment. The gates are reported separately and aggregated worst-of: any failing gate blocks a "ready" verdict, because a win on one axis can't compensate for a loss on another.

Run on the only public, upstream, behavior-matched C/Rust storage pair — null_blk and Hindborg's rnull — Phase 1 flags null_blk as a maximal-score candidate (12 of 12), and the three gates then disagree: the safety gate fails (Rust's type system retires only 2 of 11 CWE-classified fix commits, 18.2%, below the 34.2% bar), the fuzzing gate passes (no statistically distinguishable, practically large regression across ten 24-hour campaigns), and the performance gate fails (all 18 matched fio cells regress, median −14.36%, worst −25.46%).

The point isn't the verdict on rnull specifically — it's that even on a small, well-matched, synthetic driver, three orthogonal evidence axes told three different stories. That disagreement is exactly the signal R4L upstreaming needs before scaling this kind of decision across hundreds of drivers.

🍯 Key takeaways

  • Existing R4L evidence is real but unmatched, unthresholded, uncomposed — KOxI's core contribution is the composition and thresholding, though the paper also reports new matched syzkaller/fio measurements and artifact data for the null_blk/rnull case.
  • Phase 1 screens candidates cheaply on 4 lenses (0–3 each); Phase 2 only runs the 3 gates when a matched Rust driver exists.
  • Safety gate: share of CWE-classified fix commits that are auto-eliminated by Rust's type system, vs. a 34.2% ACSAC-derived bar.
  • Fuzzing gate: do-no-harm framing — fails only on a statistically and practically large regression (MWU p<0.05, A12≥0.71).
  • Performance gate: matched fio, bootstrap CIs, Holm-corrected across 18 cells, fails if any cell's lower CI bound drops below −5%.
  • Aggregation is worst-of, deliberately not weighted — disagreement across gates is preserved, not averaged away.
  • On null_blk/rnull: safety FAIL (18.2%) · fuzzing PASS (p=0.37, A12=0.45) · performance FAIL (median −14.36%, worst −25.46%).
Six everyday pictures

How to think about KOxI

Each stands alone — read in any order. Every card ends with where the picture breaks.

The core idea · Worst-of aggregation

Three exams, one degree

A school could average three exam scores, letting an A in one course paper over an F in another. KOxI refuses that trade: it's more like requiring a pass in each of three separate qualifying exams. Ace the safety exam and still fail the program if you bomb performance — the transcript shows all three grades, not a GPA.

Where it breaks: real qualifying exams are pass/fail by design; KOxI's underlying metrics are continuous (percentages, effect sizes), and the thresholds that turn them into pass/fail are tunable policy, not fixed law.
Safety gate · Elimination rate vs claim

A warranty that covers some parts, not the car

"Rust eliminates memory-safety bugs" sounds like a bumper-to-bumper warranty. The safety gate reads the fine print: it covers exactly the auto-eliminated CWE classes (buffer overflow, NULL deref, use-after-free) — 2 of null_blk's 11 classified historical fixes. The rest (validation logic, races, resource leaks) are outside what the warranty structurally covers, even in a genuinely well-written Rust rewrite.

Where it breaks: a warranty is binary coverage; Rust's "discipline" super-class (leaks, unchecked returns) is a spectrum — the language makes these easier to get right without eliminating them automatically, which the gate's denominator choice deliberately doesn't credit.
Fuzzing gate · Do-no-harm framing

A clean bill of health, not a cure

A checkup that finds nothing wrong doesn't prove you're invincible — it means nothing measurable is wrong today, at the sensitivity of the tests run. Ten 24-hour campaigns finding no statistically-and-practically-large regression (p=0.37, A12=0.45) is exactly this: rnull didn't get measurably worse under fuzzing. It's evidence of no harm, not evidence of proven robustness.

Where it breaks: a checkup has known sensitivity limits doctors can quote; N=10 campaigns bounds what regressions are detectable (large effects only) far more informally — a real but smaller regression could hide under this sample size.
Performance gate · Abstraction cost

A toll booth on an empty road

null_blk moves no real data — it's an empty road. Every fio cell that still shows a slowdown is measuring pure toll-booth cost: the overhead of crossing the submit/complete abstraction itself, not congestion from actual traffic. That's precisely why the deltas (−9% to −25%) should be read as an upper bound on abstraction overhead, not a promise that a real, data-moving NVMe driver would regress the same amount.

Where it breaks: a real device adds its own "traffic" (DMA, interrupts, media latency) that can amortize the toll — the paper explicitly notes upstream's memory-backed benchmarks showed near-parity, so the toll matters most exactly where null_blk is measuring it: the empty road.
Phase 1 vs Phase 2 · Triage vs specialist

An ER triage nurse, not the surgeon

Triage doesn't diagnose — it decides who sees a specialist first, using vitals that are fast to collect (historical risk, code size, cached fuzzing/tractability). null_blk's 12-of-12 score says "see a specialist now," not "the surgery will succeed." The three Phase 2 gates are the specialist's actual tests, run only once a matched Rust driver exists to examine.

Where it breaks: triage vitals are broadly validated across huge patient populations; Phase 1's 0–3 cutoffs are calibrated on internal observation only, not validated against an external driver corpus — the paper is explicit about this.
Holm correction · Multiple comparisons

Eighteen lottery tickets

Buy eighteen lottery tickets and expect roughly one "win" by pure chance, even with terrible odds per ticket. Testing 18 fio cells at the usual p<0.05 bar has the same problem — about one cell would look "significant" from noise alone. The Holm correction raises the bar per ticket so that, family-wise, a false alarm across all 18 stays rare — which is why the performance gate's failure (surviving correction on multiple cells) is trustworthy, not a fluke.

Where it breaks: the lottery is independent draws; the 18 fio cells share a common cause (the same abstraction layer), so correlated failures across cells are expected and, if anything, strengthen the case beyond what independent-draw intuition suggests.
The full explanation

How KOxI actually works

Section by section — the screen, then each gate's mechanics, then how disagreement gets aggregated.

1 · Phase 1 — candidate screening

Four lenses, each scored 0–3, mean determines the band (≥2.5 strong, ≥1.5 moderate, else weak); the strong-candidate cutoff additionally requires a raw total of at least 10 of 12.

ScoreHistorical riskStatic surfaceDynamic robustnessTractability
3≥40%>2000 LoC"target-attrib."2 caches, ≥10 runs
2≥20%>800 LoC"unknown-class"2 caches
1anynon-empty"infra-only"1 cache
0noneemptynonenone
🌱
The historical-risk lens uses a broad regex (fix/leak/race/overflow/UAF/null-deref) — wider than the safety gate's CWE-classified subset. That's deliberate: the screen asks whether there's any pain in the history; the gate asks how much of it Rust structurally retires. Keeping them separate lets the two later disagree, which is the point.

2 · The safety gate — elimination rate against a declared bar

Each historical fix commit that can be assigned a specific CWE is mapped to one of three ACSAC super-classes:

Super-classExample CWEs
Auto-eliminated787, 416, 415, 476, 457, 190
Needs Rust discipline401, 252
Language-unaffected20, 125, 362 family, 772, 843
 
elimination_rate = auto_eliminated_commits / classified_commits
pass if elimination_rate > 0.342   # ACSAC-derived expectation for driver CVEs in aggregate

The gate also records residual unsafe LoC in the Rust driver and its abstraction layer, so a passing rate can't hide unsafe surface merely relocated rather than removed. A per-commit manual_cwe override supersedes the automatic regex classification when provided.

3 · The fuzzing gate — matched campaigns, do-no-harm

N=10 independent 24-hour syzkaller campaigns per driver, each spawning 4 QEMU/KVM guests (4 vCPU, 4 GiB, sandbox=none) with virtio-blk as the device under test and a 9pfs host share for corpus/logs. Raw crash reports are split into target-attributable (regex-matched to driver name/path tokens), infrastructure noise, and unknown.

# regression declared only if BOTH hold
if mannwhitney_p < 0.05 and vargha_delaney_A12 >= 0.71:
    gate = FAIL   # statistically distinguishable AND large effect
else:
    gate = PASS   # "do no harm" — the default outcome
💡
Why the double bar? With N=10 campaigns, a lone p<0.05 could easily be noise; requiring a large A12 too means the gate only fires on regressions both real and big enough to matter — the appropriate bar at this sample size, not a weaker or stronger one.

4 · The performance gate — matched fio, Holm-corrected

fio 3.41 sweeps an 18-cell matrix (3 block sizes × 2 patterns × 3 queue depths) on a 512 MiB target, 30 repetitions × 30 s per cell, warm-ups dropped. Per cell: bootstrap 95% CI (B=10,000), Mann–Whitney p, Vargha–Delaney A12; p-values are Holm-corrected across the 18-cell family.

# pass only if BOTH hold, for EVERY cell
for cell in matrix_18_cells:
    if bootstrap_ci_lower(cell) <= -0.05 or holm_corrected_p(cell) < 0.05:
        gate = FAIL; break
gate = PASS if not failed else FAIL

Both drivers run without memory backing (upstream rnull's only supported mode at the time), so deltas isolate per-operation submit/complete cost rather than data-path throughput — an explicit upper bound on abstraction overhead, not a device-throughput comparison.

5 · Aggregation — worst-of, never weighted

The three Phase 2 outcomes are reported side by side; the overall verdict is worst-of: all three pass ⇒ "evidence-supported," any single failure ⇒ "not ready for direct replacement." Every numeric threshold above — the Phase 1 cutoffs, 34.2%, the MWU/A12 pair, the −5% ceiling — lives in one editable knob file, treated as per-driver policy, not universal constants.

Follow the numbers, step by step

Worked examples

Four traces using the paper's actual figures — the screen, the safety math, the performance math, and the sensitivity check.

① Scoring null_blk through Phase 1

Does null_blk clear the 10-of-12 strong-candidate bar?

  1. Historical risk: 69 of 106 observed commits carry a safety signal = 65.1%. That's ≥40% ⇒ score 3.
  2. Static surface: 119 functions, 2,491 LoC, 1,071 implicit unsafe operations. LoC >2000 ⇒ score 3.
  3. Dynamic robustness: cached fuzzing data already shows target-attributable crashes ⇒ score 3.
  4. Tractability: both caches present, ten prior campaigns (≥10) ⇒ score 3.
  5. Total: 3+3+3+3 = 12 of 12 (mean 3.0) — clears both the mean≥2.5 and total≥10 bars. Strong candidate.
🍯
Insight: a perfect Phase 1 score says "worth investigating," not "will pass Phase 2" — exactly what the gates go on to test.

② The safety gate's elimination rate

11 of null_blk's 69 safety-signal commits could be assigned a specific CWE (Table 4 in the paper). Does the rate clear 34.2%?

  1. Auto-eliminated (2): a CWE-190 integer-overflow fix (sector_t truncation) and a CWE-476 NULL-dereference fix.
  2. Needs Rust discipline (3): two CWE-401 reference-leak fixes and one CWE-252 unchecked-return fix — Rust makes these easier to avoid but doesn't rule them out automatically.
  3. Language-unaffected (6): validation (CWE-20 ×2), an out-of-bounds read (CWE-125), a poll-timeout race (CWE-362), a cleanup-order bug (CWE-772), and a union-confusion bug (CWE-843).
  4. Rate = 2 / 11 = 18.2%. Threshold is 34.2%. 18.2% < 34.2% ⇒ gate fails.
💡
Most of this driver's classified history lives in the two classes Rust doesn't structurally retire — validation and resource-lifetime bugs, not memory corruption. That's the concrete content behind "18.2%."

③ The performance gate's median and worst case

All 18 fio cells regress. What are the median and worst-case deltas, and do they clear the −5% ceiling?

  1. Sort the 18 cell deltas ascending: worst is 4K randwrite/Q32 at −25.46%; best is 1M randread/Q1 at −8.83%.
  2. Median (18 values, average of the 9th and 10th sorted): (−15.32% + −13.39%) / 2 = −14.36%.
  3. Threshold check: the gate needs every cell's bootstrap CI lower bound > −5%. Even the best cell (−8.83%) is well past that, so all 18 fail the ceiling.
  4. Holm correction: across 18 simultaneous comparisons, the per-cell significance bar tightens; the regressions survive correction rather than being a family-wise false alarm.
  5. Result: gate fails — small-block, high-queue-depth writes (4K, randwrite) hurt most (~−25%), large sequential reads least (~−9%), consistent with per-operation abstraction overhead mattering most when the op count per second is highest.
🍯
Insight: the gradient across cells (4K worse than 1M, writes worse than reads) is itself evidence the deltas measure submit/complete overhead, not something pattern-independent.

④ The sensitivity check on the safety classification

Two commits are borderline calls (a CWE-125 logical-bound read, a CWE-843 union-confusion bug). How much would reclassifying them change the verdict?

  1. Current: 2 of 11 auto-eliminated = 18.2%, fails the 34.2% bar.
  2. Reclassify one (say CWE-125) as auto-eliminated: 3 of 11 = 27.3% — still below 34.2%. Still fails.
  3. Reclassify both: 4 of 11 = 36.4% — now above 34.2%. Only this double move flips the gate.
  4. Conclusion: the safety verdict is robust to any single reclassification, but not to two simultaneous ones — a useful bound on how much a single-author classification pass could be moving the result.
💡
This is exactly the kind of check a worst-of, thresholded pipeline invites: because the bar is explicit, you can ask precisely how fragile a "fail" is, instead of arguing about it qualitatively.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
A driver's rewrite retires 40% of its CWE-classified historical fixes — well above the 34.2% safety bar — but its fio numbers regress on every matched cell beyond the −5% ceiling. What does KOxI's aggregation report?
Show answer
"Not ready for direct replacement." Aggregation is worst-of, not averaged: the performance gate's failure isn't offset by the safety gate's pass. Both outcomes are reported side by side so a reviewer sees exactly which axis blocked the verdict.Misconception: that a strong safety win should "count for more." KOxI deliberately treats the three axes as non-commensurable — no exchange rate between them.
Problem 2 · medium
A fuzzing campaign shows Mann–Whitney p=0.02 (significant) but A12=0.58 (small effect, near coin-flip). Does the fuzzing gate fail?
Show answer
No — it passes. The gate only fails when both p<0.05 and A12≥0.71 hold. Here the difference is statistically distinguishable but practically small (0.58 is close to the 0.5 no-difference baseline), so it doesn't meet the "large effect" half of the criterion.Misconception: that any statistically significant p-value means a real regression. With enough campaigns, tiny real differences become "significant" without being practically meaningful — which is exactly why the gate also requires a large A12.
Problem 3 · medium
A driver has 20 CWE-classified commits, 6 auto-eliminated. Does the safety gate pass?
Show answer
6/20 = 30%. The threshold is 34.2%, so 30% < 34.2% ⇒ the gate fails, narrowly. (Compare to null_blk's actual 18.2% — this hypothetical driver would be a much closer call.)Misconception: that "close to the bar" rounds up. The threshold is a hard cutoff by design — that's what makes the gate auditable rather than a judgment call.
Problem 4 · hard
Why does the performance gate report Holm-corrected p-values across all 18 cells instead of testing each cell independently at p<0.05?
Show answer
Because with 18 simultaneous comparisons, roughly one cell is expected to cross p<0.05 by pure chance even if nothing is actually regressing — a family-wise false-positive problem. The Holm correction raises the effective significance bar per cell so the family-wise error rate (the chance of any false alarm across all 18) stays controlled, making a "fail" trustworthy rather than a statistical fluke from testing many cells at once.Misconception: that more test cells always means more evidence. Without correction, more cells just means more chances for a spurious "significant" result — correction is what keeps the extra cells honest.
Problem 5 · medium
The safety gate's denominator is 11 (CWE-classified commits), not 69 (all safety-signal commits). Why not use 69, and what would the rate become if it did?
Show answer
The other 58 commits carry a safety signal (matched by the broad fix/leak/race/etc. regex) but couldn't be assigned a specific CWE, so there's no basis to say whether Rust's type system would have caught them. Using 69 as the denominator would silently assume all unclassified commits are "not auto-eliminated," understating the rate with unjustified certainty. KOxI restricts the gate's denominator to what was actually classified: 2/11 = 18.2%, not 2/69 = 2.9%.Misconception: that a bigger denominator is always more rigorous. Here it would smuggle in an unsupported assumption — the narrower, classified-only denominator is the more honest one.
Problem 6 · medium
Upstream's own RFC benchmarks of rnull in a memory-backed configuration reported near-parity across 432 configurations, yet KOxI's performance gate fails badly. Are these findings in conflict?
Show answer
Not necessarily. KOxI's comparand runs without memory backing (the only mode upstream rnull supported at the time), which isolates per-operation submit/complete abstraction cost rather than data-path throughput. A memory-backed, data-moving configuration gives that overhead something to amortize against, which is consistent with upstream's near-parity result in a memory-backed configuration. The paper treats re-running the gate on the feature-parity series (which adds memory backing) as the natural next step, not a contradiction to resolve.Misconception: that a "no-op" driver and a memory-backed configuration should show the same relative overhead. Removing the data path removes exactly what would normally dilute a fixed per-operation cost.
Problem 7 · hard
Phase 1's cutoffs are "calibrated on internal observation, not validated against an external driver corpus," per the paper's own limitations. What's the practical risk of using KOxI's screen to prioritize which drivers get Phase 2 attention?
Show answer
The screen could misrank drivers — flagging one as "strong" that turns out uninteresting at Phase 2, or burying one that would have been a good rewrite target, because the 0–3 lens cutoffs were set by observation on a small set rather than validated broadly. The paper notes the all-3s profile is robust to small perturbations for null_blk specifically, and that two further in-tree drivers land in weaker bands in their artifact — but that's a spot check, not external validation.Misconception: that a numeric score implies calibrated confidence. A declared threshold makes a decision auditable; it doesn't by itself make the threshold correct.
Problem 8 · easy
A maintainer says "Rust drivers regress performance" based on this paper. Is that a fair generalization from the null_blk/rnull result?
Show answer
No. The paper explicitly limits its claims to this one synthetic pair, running in a specific virtualized, no-memory-backing configuration; it states that what transfers to other drivers is the pipeline's structure (the gates, attribution method, audit trail), not the specific delta magnitudes or pass/fail outcomes. Generalizing "Rust storage regresses" from one matched pair is exactly the kind of unstructured leap KOxI is built to replace with a per-driver profile.Misconception: that one faithful case study licenses a category-wide claim. The contribution is the pipeline; the result is a data point, deliberately the smallest one available.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1Is KOxI saying rnull is a bad rewrite?▾
No — the paper is explicit that the contribution is the pipeline, not a verdict on rnull. rnull adds zero residual unsafe LoC and, across ten 24-hour fuzzing campaigns, shows no statistically distinguishable and practically large target-attributable regression (smaller regressions could still go undetected at that sample size); it simply doesn't yet clear the safety-elimination and performance bars in this no-memory-backing configuration. Those are real findings about the current state of a work-in-progress upstream series, not a condemnation.
Q2Why null_blk/rnull specifically, out of all R4L drivers?▾
Because, to the authors' knowledge, it's the only public, upstream, behavior-matched C/Rust storage driver pair — same synthetic device, same purpose, different language, at pinned revisions. That match is what lets KOxI's gates isolate the language/rewrite effect rather than confounding it with driver differences.
Q3What does "auto-eliminated" actually mean for a CWE class?▾
It means Rust's compile-time checks (bounds checking, ownership/borrowing, no null pointers without Option) structurally prevent that bug class from compiling in safe code — not that a careful C programmer couldn't also avoid it, but that Rust makes the class unrepresentable rather than merely discouraged.
Q4Why is 34.2% the safety bar instead of, say, 50%?▾
It's the ACSAC-derived expectation for Rust's automatic contribution to kernel driver CVEs in aggregate (Li et al.'s corpus). The gate asks whether this driver's history is at least as Rust-eliminable as driver CVEs are on average — a relative bar, not an arbitrary round number, and it's one of the values kept in KOxI's editable knob file.
Q5Couldn't a regex miscount safety-signal or target-attributable commits/crashes?▾
Yes — the paper names this directly as a limitation. Both the safety gate's commit classification and the fuzzing gate's crash attribution default to regex matching for scale, with an audited override path (a manual_cwe field, a validated_crashes.csv) for contested cases. The default numbers in this paper reflect a single-author classification pass, not multi-reviewer adjudication.
Q6Why does the fuzzing gate use a "do-no-harm" default instead of requiring proof of improvement?▾
Because the realistic question for a migration decision is "does the rewrite make dynamic robustness worse," not "does it make it better" — a faithful port is expected to preserve behavior, not necessarily improve it. Framing the gate as do-no-harm matches that expectation and avoids penalizing a correct, behavior-preserving rewrite for not also fixing unrelated robustness issues.
Q7Are the fio performance deltas representative of real-world storage workloads?▾
Only as an upper bound on submit/complete abstraction cost. Both drivers run without memory backing on a synthetic, no-data-movement device in a virtualized guest — deltas measure per-operation overhead in the most sensitive possible setting, not what a physical NVMe or HDD-class device would show once data movement and media latency are in the mix.
Q8What's the difference between the historical-risk lens (Phase 1) and the safety gate (Phase 2)?▾
The historical-risk lens counts all safety-signal commits broadly (69 of 106, 65%) to ask "is there pain in this driver's history at all." The safety gate narrows to the 11 commits with a specific assigned CWE and asks how much of that subset falls in Rust's auto-eliminated class (2 of 11, 18.2%). They're deliberately different questions with different denominators.
Q9Can KOxI's thresholds be changed per driver class?▾
Yes, by design. Every numeric threshold — Phase 1 cutoffs, the 34.2% elimination bar, the fuzzing MWU/A12 pair, the per-cell −5% performance ceiling — lives in one editable knob file, treated as policy. The paper notes a latency-bound NVMe driver and a synthetic test driver shouldn't share the same performance threshold, and the fio workload matrix itself is a knob (an HDD-class device would need sequential-heavy cells).
Q10What's the natural next step for this case study?▾
Re-running the gates once rnull's 79-patch feature-parity series (adding memory backing, under review as of February 2026) lands, and pointing Phase 1 at not-yet-migrated block drivers to rank where the next Rust investment would pay off.

Core terms
KOxIThe paper's evidence-gated pipeline: a Phase 1 screen plus three Phase 2 gates (safety, fuzzing, performance), aggregated worst-of.
Phase 1 screenFour 0–3 lenses (historical risk, static surface, dynamic robustness, tractability); ≥10/12 total flags a strong candidate.
Safety gateShare of CWE-classified historical fix commits in the auto-eliminated ACSAC super-class; passes above 34.2%.
Fuzzing gateMatched syzkaller campaigns; fails only on p<0.05 and A12≥0.71 target-attributable regression (do-no-harm).
Performance gateMatched, Holm-corrected fio deltas across an 18-cell matrix; fails if any cell's bootstrap CI lower bound is below −5%.
Worst-of aggregationOverall verdict passes only if all three gates pass; deliberately not a weighted sum.
Target-attributable streamThe subset of fuzzing crashes whose report names the driver under test, separated from infra/unknown noise.
Elimination rateauto_eliminated_commits / CWE-classified_commits — the safety gate's headline number.
