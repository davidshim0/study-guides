SOSP 2026 · A Field Guide

Keeping the lock tiny when the pool is huge

Sixteen hosts share one CXL memory pool, but the hardware that keeps caches coherent across them only covers a few hundred megabytes of it. This is the plain-English story of XTRA, the directory that makes a sliver of coherence cover a terabyte of transactions.

📄 "XTRA" · Yang, Hua, Zhang, Chen, Chen, Tong · SOSP'26 🎓 CXL/pod basics assumed — the primers cover the transaction-system side ⏱ ~25 min read
🗂️

Don't put a lock on every byte — put a tiny LOCK + VERSION in a compact coherent directory, and leave the DATA in the big non-coherent pool. One version check on read proves "my transaction is still valid" — and, once the object is tracked in the Shadow Directory, that same check proves "my cached copy is fresh" too.

Before you begin

Quick glossary, then six primers

You already know CXL pods, pooling, and the DRAM/NVM tiering stack — this guide skips that. It leans instead on the distributed-transaction vocabulary the paper layers on top.

Quick glossary — the acronyms you'll see everywhere

HCCHardware Cache Coherence — the cross-host coherence CXL 3.0 provides, but only for a device-limited region.
NHCCNon-Hardware-Cache-Coherent memory — the large remainder of the CXL pool, with no automatic cross-host coherence.
CDCoordination Directory — XTRA's compact array of lock+version slots, decoupled from the data it protects.
SDShadow Directory — a host-local DRAM structure that remembers which CD-slot version each cached object was last validated against.
OCCOptimistic Concurrency Control — read without locking, validate versions at commit, lock only the write set briefly.
2PLTwo-Phase Locking — once a lock is acquired, hold it through execution and commit. XTRA's contrast case for OCC: the long hold time, not upfront lock knowledge, is what makes CD-slot collisions costlier.
CASCompare-And-Swap — the atomic primitive that needs a coherent memory view to work correctly across hosts.
P50 / P99Median and 99th-percentile latency — P99 exposes rare but severe stalls that averages hide.
1CXL pods, recapped in one breath▾

A CXL pod attaches multiple hosts to one shared, TB-scale memory pool over PCIe via CXL.mem; hosts use ordinary load/store and can cache hot lines locally. You've seen this substrate before in tiering work — the twist here is multiple hosts, not one host's near/far memory.

Now you're ready: the paper's whole problem is that "shared memory across hosts" doesn't automatically mean "coherent memory across hosts."
2The snoop filter — coherence's bounded tracking structure▾

CXL 3.0 adds cross-host coherence via a device-side snoop filter: it tracks which hosts cache which lines and issues back-invalidations on writes. That tracking state lives in on-device SRAM, so — exactly like a TLB or a hot-page tracker — its capacity is physically bounded (practically, hundreds of MB), not a config knob you can turn up to cover a TB pool.

Now you're ready: every design in this paper is a response to one hard fact: HCC is a small, fixed-size window, and the data pool is not.
3OCC vs 2PL — two ways to serialize transactions▾

2PL: lock each record as you touch it, and hold every lock you've acquired through execution and commit. Safe, but a lock sits held for the rest of the transaction's length, widening the window for collisions. OCC: read freely without locking, remember a version per object you read, lock only the write set briefly at commit, then check all remembered versions are unchanged. If anything moved, abort and retry.

Now you're ready: OCC's "brief locking, long lock-free reading" shape is exactly what lets XTRA tolerate a directory where unrelated objects sometimes share a slot.
4Why CAS needs coherence to mean anything▾

Compare-and-Swap atomically checks a memory location and updates it only if it still holds an expected value — the textbook building block for locks. But the "check" half is only meaningful if every observer sees the same, up-to-date value. Without cross-host coherence, two hosts' CAS attempts can both believe they won.

Now you're ready: this is why locking schemes outside the HCC region can't just use ordinary CAS — XTRA has to reinvent exclusion in software for that case (§4.4 in the paper).
5Write-ahead redo logging, briefly▾

To survive a crash mid-transaction, a system writes a record of its intended updates (a redo log) to durable/shared storage before applying them. After a crash, a recovering process can tell which transactions finished logging (replay them) versus didn't (abort them) — no guesswork needed.

Now you're ready: XTRA puts its redo logs in the shared NHCC pool itself, so any surviving host can recover a crashed one without waiting for a reboot.
6Lamport's fast mutual exclusion▾

A classic algorithm for mutual exclusion using only ordinary loads/stores (no atomics): each participant sets a flag, writes its ID to a shared "latch" variable, then re-checks both to detect races, falling back to a slow path only under contention. It needs Ω(N) space — one flag per participant.

Now you're ready: this is the exact mechanism XTRA repurposes to manage its directory on CXL 2.0 hardware that has no cross-host atomics at all.
The whole story in one place

XTRA in a nutshell

The problem, the decoupling that fixes it, and how coherence and concurrency control end up being the same check.

Distributed transactions need fine-grained synchronization — locks and versions — to detect conflicts across hosts. The conventional recipe provisions that metadata per record, which works fine under full hardware cache coherence. But in a CXL pod, cross-host HCC is either absent (CXL 2.0) or capacity-limited to a sliver of the pool (CXL 3.0 — practically hundreds of MB against a TB-scale dataset). The prior state of the art, Tigon, copes by migrating records into that sliver on demand — which puts network-style coordination right back on the transaction's critical path the moment the working set outgrows the HCC budget.

XTRA's move: stop provisioning metadata per record. Observe that although any record might need synchronization eventually, only a bounded number are ever participating in active synchronization at any instant — every read maps to a CD slot and records a version too, whether or not that slot is currently contended. So consolidate all synchronization state into a small, fixed-size Coordination Directory (CD) — a flat array of 64-bit lock+version slots — and leave every record's actual data in the large NHCC pool untouched. Every host hashes an object's pool offset to the same CD slot, so contention is always detected, even though many unrelated objects now share one slot.

That directory also solves a second problem for free. Caching NHCC data locally in CPU caches risks staleness without HCC. A transaction's OCC version check ("has this object changed since I read it?") and a cache-coherence check ("is my cached copy still fresh?") turn out to ride on the same version counter — but a matching version only proves freshness for an object the Shadow Directory is already tracking. XTRA's Shadow Directory reuses the OCC check as a lazy, on-read coherence check for tracked objects, and falls back to a one-time CLFLUSH-and-install for untracked ones — no eager invalidation broadcasts needed either way.

The payoff: up to 15.6× higher throughput and 4.0×/283.9× lower P50/P99 latency than Tigon, scaling 3.7–6.1× from 1 to 8 hosts where baselines collapse, and remaining robust down to just 10 MB of HCC capacity.

🍯 Key takeaways

  • Tigon ties metadata to migrated records; XTRA ties metadata to a bounded directory that covers the whole pool regardless of dataset size.
  • HCC capacity now bounds only active synchronization, not total protected data — an 8 MB CD gives ~10⁶ slots, enough for thousands of concurrent threads at <10% load.
  • CD-slot collisions cause only false contention (a performance cost), never missed conflicts (never a correctness cost).
  • OCC's version check doubles as a lazy cache-coherence check — the Shadow Directory makes this safe despite per-thread/per-host scope mismatches.
  • The same CD abstraction runs on CXL 3.0 (HCC + CAS) or CXL 2.0 (software mutual exclusion) without changing the transaction protocol above it.
  • Result: up to 15.6× throughput, 4.0×/283.9× lower P50/P99 latency, <1% of the paper's evaluated workloads needing more than 10 MB of HCC to stay fast.
Five everyday pictures

How to think about XTRA

Each stands alone — read in any order. Every card ends with where the picture stops being true.

Decoupled sync · The claim-check

A valet's claim ticket

The valet doesn't hand you a lock for your actual car — he hands you a numbered ticket, and the car waits in a lot somewhere else. The ticket is small, fits in his coherent little booth, and is all two people need to agree "this car is claimed." XTRA's CD slot is that ticket: a 64-bit lock+version proxy for an object that may be megabytes away in the NHCC pool.

Where it breaks: a valet lot never double-books a ticket number to two cars on purpose. XTRA's hashed slots sometimes do (by collision) — tolerable because OCC only pays for it as false contention, never a lost conflict.
Scaling · Bounded hot-set thinking

One front-desk ledger, not a tag on every room

A hotel doesn't bolt a lock-status sensor to every one of its thousand rooms — the front desk keeps one ledger sized for rooms currently occupied or being cleaned. This should feel familiar from your own work: it's the same move as a bounded hot-page tracker in memory tiering, sized for the active working set rather than the whole address space.

Where it breaks: a hotel ledger entry maps 1:1 to a room. XTRA's hash-based mapping lets many "rooms" (objects) share one ledger line, trading a little false contention for a directory whose size doesn't have to track the dataset at all.
Unified coherence · One question, two answers

Checking a wine seal, not re-tasting the bottle

You don't need two separate tests to know both "is this bottle still the one I opened" and "is it safe to pour from the glass I already filled" — one unbroken-seal check answers both. XTRA's version check is that seal: if a CD slot's version hasn't moved since you read it, your transaction's read is valid and, for a glass you've already labeled as sampled, your CPU-cached copy of that object is fresh. One check, two guarantees, no separate invalidation message.

Where it breaks: a seal is per-bottle and per-person. A CPU's last-level cache is shared across all local threads, so one person's "already checked" doesn't automatically cover someone else's glass — that gap, plus the fact that an unlabeled glass still needs a first taste before anyone trusts it, is exactly why the Shadow Directory exists.
Shadow Directory · A local memo pad

A sticky note that says "already checked today"

Instead of re-verifying a shared fact every single time, you jot "checked v=7, OK" on a sticky note by your desk; any colleague at the same desk can glance at the note instead of re-checking from scratch. The Shadow Directory is that note — one per host, in local DRAM, remembering the last CD-slot version each cached object was validated against, shared across that host's threads.

Where it breaks: a sticky note doesn't expire on its own. If the shared fact changes (the slot's version advances), every note referencing it must be torn up — which is exactly the "stale version → clear all entries" branch of the protocol, not something free.
Software mutex · Local heat before the relay

A relay race, not a full staff meeting

To decide who runs next, a relay team doesn't call every runner on every team into one meeting — teammates sort it out among themselves first (cheap, local), and only the chosen runner steps up to the shared track (expensive, shared). XTRA's hierarchical synchronization on CXL 2.0 does the same: local threads elect a winner with fast local atomics, and only that winner contends on the slow, high-latency inter-host software latch.

Where it breaks: a relay has one baton. XTRA's local round can still have multiple hosts' winners colliding on the shared latch — Lamport's algorithm handles that contended case, just less often than if every thread raced directly.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The problem — on-demand sharing stalls on the critical path

Tigon partitions data across hosts' local DRAM by default. A remote access first probes the shared HCC region; on a hit, it proceeds with CAS-based locking; on a miss, the transaction stalls, asks the owner host to migrate the record into the HCC region, and waits for both data movement and metadata installation. Because a transaction is bottlenecked by its slowest access, a single miss forces it to keep holding every other lock it's already acquired — widening the contention window for everyone else.

⚠
Measured cost: at 10M keys with 10-key transactions, the "Perfect Hit" ratio (all remote accesses hit HCC) drops exponentially as transaction length grows from 1 to 9 keys — even while the per-key hit ratio stays near 70%. Stall time ends up over 87% of transaction latency.

2 · The Coordination Directory — one slot, many objects

The CD is a flat array of 64-bit slots. Each object's pool offset is hashed to a slot: slot = Hash(offset) mod N — deterministic across hosts, constant-time, no application semantics needed.

3 · Decoupled OCC — execution, validation, commit

Reads are lock-free: check the CD slot isn't locked, record its version, read the object. Writes are buffered locally until commit, when the transaction CASes the write-set slots' lock bits, re-validates every read-set slot's version, then writes a redo log, applies updates, and releases each slot with a single store that clears the lock and bumps the version.

// per access during execution
slot = CD[Hash(offset) % N]
if slot.locked: abortTx()
readSetVersions[offset] = slot.version   // remembered, not enforced yet
value = readNHCC(offset)

// commit
for s in writeSet: CAS(s.lock, 0 → 1)      // any failure → abort
for (offset, v) in readSet:
    if CD[offset].locked_by_other or CD[offset].version != v: abortTx()
writeRedoLog(); applyUpdates()
for s in writeSet: s.store(lock=0, version=v+1)  // one store, both effects
💡
Why OCC, specifically: slot collisions only cost something when a colliding access is a write — reads never block or advance a version. Confining write-locking to a brief commit window (rather than the whole transaction, as 2PL would) keeps collision-induced false contention small even at non-trivial directory load factors.

4 · Unified coherence — the Shadow Directory

An SD mirrors the CD structurally, one shadow slot per CD slot, sized to fit one 64 B cacheline: an 8-byte header (shadow version, lock, entry count) plus up to 7 tracking entries (8 bytes each: NHCC address, size, access counter).

5 · Generalizing to CXL 2.0 — software mutual exclusion

Without HCC or cross-host CAS, XTRA keeps the CD in NHCC memory, explicitly flushes cached copies before reading a slot, and replaces hardware locking with Lamport's fast mutex per slot. Because Ω(N) participant flags per latch would otherwise require one 64 B cacheline per flag per host (to avoid blind cacheline-granular overwrites), XTRA packs flags column-major across adjacent CD slots so metadata stays compact rather than exploding with host count. A hierarchical scheme further lets same-host threads resolve contention locally before one winner per host touches the slow inter-host latch.

🍯
Net effect: the same decoupled-OCC and unified-coherence protocols run unmodified above either substrate — only the atomic-slot implementation swaps between hardware CAS and software exclusion.

6 · Fault tolerance — logs in the pool, recovery from the directory

Under a fail-stop model, a crashed host may leave CD locks unreleased and partial updates applied. Recovery scans the compact CD for locks held by the failed host, then checks whether each associated transaction's redo log is complete in the shared NHCC log area: complete → replay and release; incomplete → just release. No reboot wait, because both data and logs are globally visible in the pool.

Follow the numbers

Worked examples

Four computations straight from the paper's own figures.

① Sizing the Coordination Directory

The paper says an 8 MB directory provides ~10⁶ slots, and stays under 10% load even with 8,192 threads each touching a dozen objects. Check the arithmetic.

  1. Slots per MB: each slot is 64 bits = 8 bytes, so 8 MB = 8 × 1,048,576 bytes ÷ 8 B/slot = 1,048,576 slots ≈ 10⁶. Matches the paper exactly.
  2. Max concurrent threads: 32 hosts × 256 threads/host (the field widths from Fig. 4) = 8,192 threads.
  3. Active slots if each touches 12 objects: 8,192 × 12 = 98,304 simultaneously-active slot references.
  4. Load factor: 98,304 ÷ 1,048,576 ≈ 9.4% — under the paper's "below 10%" claim.
🍯
Insight: the directory's size tracks concurrency (thousands of threads), not data volume (millions to billions of records) — that decoupling is the whole trick.

② Why Perfect Hit collapses faster than the per-key hit ratio

At the 10M-key dataset, per-key HCC hit ratio stays near 70% as transaction length grows, yet the paper reports Perfect Hit (all keys in a transaction hit) collapsing from 70% toward 6% as length goes from 1 to 9 keys. Why does one number fall so much faster than the other?

  1. Model it as independent per-key hits: Perfect Hit(n) ≈ (per-key hit ratio)ⁿ.
  2. At n=1: 0.7¹ = 70% — matches the reported starting point exactly.
  3. At n=9: 0.7⁹ ≈ 0.7² × 0.7⁴ × 0.7³ ≈ 0.49 × 0.24 × 0.343 ≈ 4% — in the same ballpark as the paper's reported 6% (real accesses aren't perfectly independent, but the exponential shape is exact).
  4. Why it matters: because a transaction stalls the moment any one access misses, and atomicity forces it to hold every other lock meanwhile, the Perfect Hit ratio — not the per-key hit ratio — is the number that predicts Tigon's throughput.
💡
This is the same exponential-tail logic as any "all N components must succeed" reliability calculation — the per-key number flatters the system; the all-keys number explains its P99 latency blowing up 182× over the same length range.

③ How robust is XTRA to a shrinking HCC budget?

The paper shrinks HCC capacity from 200 MB to 0 MB at fixed (S-scale) dataset size. What happens to XTRA versus Tigon?

  1. 200 MB → 100 MB: Tigon still competitive — its working-set metadata still fits.
  2. Below 100 MB: Tigon and Sundial-CXL's metadata overflows HCC, triggering message-based migration and collapsing throughput.
  3. Down to 10 MB: XTRA keeps sustaining high throughput, outperforming Tigon by 1.2–31.5× — because its CD only needs to be large enough for active synchronization, which 10 MB (~1.25M slots) comfortably covers.
  4. At 0 MB (no HCC at all): Tigon and Sundial-CXL cannot run — they require HCC atomics. XTRA falls back to XTRA-NHCC with a 200 MB NHCC-resident CD, at a 43.9–53.0% throughput cost relative to XTRA at 10 MB HCC (software exclusion replacing hardware CAS).
🌱
Counterintuitive bonus: shrinking the CD slightly can sometimes improve XTRA's throughput — a smaller CD occupies less CPU cache space, leaving more room for NHCC data and reducing CXL accesses.

④ What unified coherence actually buys you

Compare XTRA's lazy, on-read invalidation against a "NonTemporal" baseline that bypasses the CPU cache entirely for NHCC reads (safe, but slow).

  1. NonTemporal: every read goes straight to CXL memory — no staleness risk, but pays full CXL latency (over 2× local DRAM) every time.
  2. XTRA: reuses the OCC version check already on the read path, so a "tracked" hit (Shadow Directory confirms freshness) serves straight from the CPU cache.
  3. Measured gain: 1.5–3.9× higher throughput, 1.4–4.1× lower P50 latency, 1.5–4.2× lower P99 latency across KVS/SmallBank/TPCC.
  4. Where it's smallest: TPCC, because most of its accesses target warehouse-private tables kept in local DRAM and never touch the shared CXL pool at all.
🍯
Insight: the gain is biggest exactly where reuse is highest and writes are rarest (KVS) — write-heavy SmallBank sees smaller gains because frequent version bumps force frequent re-sanitization.
Test yourself

Practice problems

Each ends with the misconception it's checking for.

Problem 1 · easy
Why can't CXL 3.0 simply enlarge its snoop filter to cover the whole TB-scale pool and make this entire paper unnecessary?
Show answer
The snoop filter is on-device SRAM — a fixed, physically bounded tracking structure, not a software cache you resize at will. Scaling it to TB-scale would require SRAM capacity far beyond what's practical on a CXL endpoint, which is exactly why vendor guidance and prior systems treat HCC as covering only a limited region (hundreds of MB).Misconception: that HCC capacity is a configuration knob. It's a hardware area/cost constraint, the same kind of wall that bounds TLB or hot-page-tracker sizes in tiering hardware.
Problem 2 · medium
A pod has 16 hosts × 128 threads each, and a 2 MB CD (64-bit slots). If every thread concurrently touches 20 objects, what's the directory load factor, and should you worry about collisions?
Show answer
Slots: 2 MB ÷ 8 B = 262,144 slots. Active references: 16 × 128 × 20 = 40,960. Load factor ≈ 40,960 ÷ 262,144 ≈ 15.6% — higher than the paper's 9.4% example, but still low enough that write-write collisions (the only kind that cost anything under OCC) remain rare events, not the common case.Misconception: that any load factor above single digits is alarming. What matters is the probability two concurrently-writing transactions collide, which stays low even at this load because most accesses are reads.
Problem 3 · medium
XTRA uses OCC, but §5.5 shows OCC slightly underperforms 2PL in SmallBank. What property of SmallBank explains that, and why doesn't it generalize to "2PL is better"?
Show answer
SmallBank is short and write-intensive (85% of transactions read-write, touching at most 3 records). OCC pays for conflicts with aborts discovered late (at validation), and frequent read-write conflicts in a write-heavy workload mean frequent wasted work. 2PL's pessimistic locking avoids that wasted work by blocking early instead. But 2PL still loses badly elsewhere (KVS, TPCC) because it holds locks for the whole transaction, which is catastrophic for CD-slot false contention as HCC shrinks — up to 50.6× worse than OCC at 10 MB HCC.Misconception: that one concurrency-control style is universally superior. The right choice depends on write intensity and directory pressure — XTRA's contribution is making OCC's lock-free-read property compatible with decoupled, collision-prone metadata, not declaring OCC always wins.
Problem 4 · hard
Explain, in terms of atomicity and the "slowest access" property, why Tigon's P99 latency rises 182× (at 10M keys, length 1→9) much faster than its throughput falls 6.8× over the same range.
Show answer
Throughput is an average over many transactions; P99 is dominated by the worst 1%. As transaction length grows, the Perfect Hit ratio collapses exponentially (Problem/Example 2's math), so an increasing fraction of transactions suffer at least one migration stall — and because atomicity forces them to hold all other acquired locks during that stall, those transactions get disproportionately slow, not just "a bit slower." Throughput absorbs this as a declining average; P99 — tracking exactly the transactions experiencing the stall — explodes.Misconception: that throughput and tail latency should move together proportionally. They diverge precisely when a failure mode (HCC miss) is rare-but-severe and amplified by atomicity, which is the common shape for any lock-holding system under partial unavailability.
Problem 5 · medium
XTRA never broadcasts an invalidation message when a transaction commits a write. How does a different host's stale cached copy ever get noticed?
Show answer
It's noticed lazily, on the next read. The reader's OCC path already fetches the CD slot's current version to validate its own transaction; if that version is higher than the reader's locally-remembered shadow version, the Shadow Directory clears its tracking entries for that slot and re-sanitizes (CLFLUSH) before trusting any cached copy again. No message is ever sent to the writer's side — the cost of staleness detection is paid entirely by the next reader, only when it actually reads.Misconception: that any non-coherent caching scheme needs an active invalidation protocol with sender-side broadcasts. Piggybacking on a check the reader was already going to do (OCC validation) eliminates that need.
Problem 6 · hard
Thread A on host H reads object O for the first time and finds V_slot == V_shadow. Can it safely skip CLFLUSH and read O directly from the CPU cache? Why or why not?
Show answer
Not automatically — it depends on whether O is already tracked in the Shadow Directory. If V_slot == V_shadow but O has no tracking entry, some other local thread (or a hardware prefetch) may have populated the LLC with O before this host last advanced V_shadow, and thread A has no record that this specific object was sanitized under the current version. That's the spatial mismatch: version-matching alone only proves no remote write happened since V_shadow was last set — it says nothing about which local cachelines are trustworthy. Thread A must sanitize-on-entry (CLFLUSH, then add a tracking entry) exactly once; only then can later local threads skip the flush.Misconception: that a version match is sufficient proof of freshness by itself. It closes the temporal gap (no remote update) but not the spatial gap (shared LLC across local threads) — both gaps have to be closed, which is why the SD tracks per-object entries, not just per-slot versions.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does "decoupling synchronization from data" mean?▾
Instead of giving every record its own lock-and-version word, XTRA keeps all synchronization state in one bounded array (the CD) and maps objects onto it by hashing their pool offset. The data stays put in the large non-coherent pool; only the small CD needs to live somewhere coherent (or software-protected).
Q2Why can't CXL 3.0 just coherence the whole pool?▾
The snoop filter that implements cross-host coherence is on-device SRAM with fixed capacity — practically hundreds of MB. Scaling it to a TB pool isn't a software fix; it's a hardware cost/area constraint the paper designs around rather than waits for.
Q3What happens when two unrelated objects hash to the same CD slot?▾
Nothing, if both accesses are reads — OCC reads are lock-free and don't touch the version. If either is a write, the other transaction may see the slot locked or its version changed, and conservatively aborts even though its own object wasn't really touched. This is false contention: a performance cost, never a correctness bug, since no true conflict is ever missed.
Q4How is this fundamentally different from Tigon's on-demand sharing?▾
Tigon still ties synchronization metadata to the records themselves — it just moves the records into the HCC region on demand. The metadata footprint still scales with the working set, which eventually exceeds HCC capacity as the dataset grows. XTRA's CD size scales with concurrency instead, so it doesn't grow with the dataset at all.
Q5Why OCC instead of 2PL, and when does that choice lose?▾
OCC's lock-free reads and brief commit-time write-locking minimize how long a CD-slot collision can cause false contention. It loses slightly in write-intensive, short-transaction workloads like SmallBank, where frequent read-write conflicts mean frequent late-discovered aborts — 2PL's early pessimistic blocking avoids that specific cost.
Q6Does the Coordination Directory need to be durable?▾
No — it's lock/version state, not data, and it's shared rather than host-private, so it survives a host crash untouched. Durability comes from the redo logs in the NHCC pool: recovery scans the CD for locks the failed host never released, inspects that host's log buffers to see which associated transactions finished logging, replays or discards each accordingly, then releases the lock. The CD is never reconstructed — only cleaned up.
Q7Does XTRA work on CXL 2.0 hardware available today?▾
Yes — that's the point of XTRA-NHCC, which places the CD in ordinary non-coherent memory and manages it with software mutual exclusion (Lamport's fast mutex, hierarchically optimized), preserving the same OCC and unified-coherence protocols above it.
Q8Is caching NHCC data in local CPU caches ever unsafe?▾
Only if a thread trusts a cached copy without validating it through the CD/SD path first. The protocol's "untracked" and "stale version" branches exist precisely to force a sanitization step (CLFLUSH) before any first trusted use, so by construction a transaction never knowingly reads a stale cacheline.
Q9What happens if the shared dataset is bigger than the whole CXL pool?▾
The paper explicitly scopes this as future work: XTRA's current design assumes the shared data fits in the pool, with host-private data free to live in local DRAM (as TPCC's warehouse-private tables do). Beyond-capacity datasets would need a separate caching/tiering layer managing residency between the pool and a backing tier — XTRA's CD stays bounded regardless, since it tracks active synchronization, not total objects.

Tigon — A Distributed Database for a CXL Pod hard
