SOSP 2026 · A Field Guide

Expose the thread, not the core

Every context switch, scheduling decision, and thread wakeup today is a software detour costing microseconds. This is the plain-English story of threadlet and Loom, hardware that treats software threads as first-class, schedulable citizens.

📄 "Computation Is Fast, Use Threadlet!" · Yao, Qin, Fan et al., SOSP'26 🎓 OS scheduling & cache-coherence basics assumed — primers fill the hardware-threading gaps ⏱ ~28 min read
🧵

Hardware should expose schedulable units of execution (threads), not just computational resources (cores).
Then switching, scheduling, and waking threads become hardware operations — not software detours.

Before you begin

Quick glossary, then eight primers

The paper mints several new acronyms; look them up here first. Then work through the primers — each clears one piece of background the design assumes.

Quick glossary — the paper's own acronyms

LoomOSThe research OS (built on a small Rust RISC-V kernel) that drives Loom — replaces schedulers, locks, and I/O paths with threadlet-native versions.

1What "architectural context" means▾

A running thread's context is everything the CPU needs to resume it exactly where it left off: general-purpose registers, the program counter, the stack pointer, and a handful of control/status registers (page-table base, privilege level). Bigger contexts (like x86's floating-point/vector state) can run 2–16× larger than the general-purpose registers alone.

Now you're ready: threadlet's whole design is about shrinking this context to only what's critical — everything else is dropped or shared (§3.3).
2Context switching — why it's slow▾

Multiplexing many software threads on one core means saving the outgoing thread's registers to memory and loading the incoming thread's registers back in. Even in the best case (no cache pollution), this round-trip to memory costs real cycles — the paper measures 0.6 µs on real Linux hardware.

Now you're ready: Loom's fix is to never spill the active set of threads to memory at all — it keeps a few resident in the register file (§4.3).
3How an OS scheduler picks the next thread▾

Linux's default scheduler, EEVDF, tracks each task's virtual runtime (CPU time received, weighted by priority) and virtual deadline (when its next slice should finish), then picks the eligible task with the earliest deadline — using a red-black tree for fast lookups. Correct, but not free: the paper measures 1.0 µs per decision.

Now you're ready: Loom's fast path replaces the red-black tree with a fixed 3-tuple (priority, deadline, time slice) that hardware can rank directly (§3.4).
4Interrupts vs. polling — the notification tradeoff▾

When an event happens (I/O completes, a lock is released), software finds out one of two ways. Interrupts are cheap when idle but expensive to service (asserting APIC, entering/exiting a softirq — the paper measures 1.46 µs). Polling is fast to notice but burns a CPU core continuously checking, even when nothing has happened.

Now you're ready: Loom's memory notification is designed to match polling's latency without wasting the CPU — the exact tradeoff §2.3 sets up (§3.5).
5Cache coherence & snooping▾

On a multicore chip, each core's private cache must see a consistent view of memory. When one core writes to a cache line another core holds, a coherence protocol sends an invalidation message to that core so it drops its (now-stale) copy. Every core's cache controller can "snoop" these messages as they pass by.

Now you're ready: threadlet's tlet_monitor first pulls the target cache line into the core's own cache; Loom's Address Monitor Table (MAT) then reacts the instant a coherence invalidation arrives for that specific, registered address — not a passive feed of every write in the system (§4.5).
6Hardware multithreading (SMT), and why threadlet isn't that▾

SMT (e.g., Intel Hyper-Threading) gives a core two or so hardware-resident thread contexts to interleave, hiding pipeline stalls. It's a microarchitectural trick for utilization, capped at a handful of contexts because each one needs its own full register file slot.

Now you're ready: threadlet solves a different problem — software's scheduling and notification overhead, not pipeline utilization — and scales to hundreds per core precisely because most threadlets stay off-chip (§7).
7Spinlocks vs. blocking locks▾

A thread that fails to acquire a lock can either spin (busy-loop rechecking — fast to notice release, wastes CPU) or block (yield the core and get woken later — CPU-efficient, but only if the wakeup itself is cheap). Because wakeups have historically been slow, most production lock implementations just spin.

Now you're ready: Loom's cheap memory notification is what finally makes blocking locks competitive with spinning (§5.4).
8TLB shootdowns & IPIs▾

Most hardware doesn't keep per-core TLBs coherent automatically. When a page table changes, the OS must send an inter-processor interrupt (IPI) to every other core so each can flush its stale translation — a costly, latency-sensitive broadcast.

Now you're ready: the paper flags TLB shootdown as a promising but unimplemented use case for threadlet's cheap thread-to-thread notification (§5.6).
The whole story in one place

Threadlet & Loom in a nutshell

Four inefficiencies, one insight, one tiered-storage trick that makes it practical.

The conventional threading model has two layers: hardware exposes cores as computational resources, and privileged software multiplexes threads onto them. That extra layer of indirection is invisible to hardware, so every context switch, scheduling decision, and notification must be mediated by software — and at µs-scale, that mediation dominates. The paper measures four such taxes on a real Linux box: context switching (0.6 µs), scheduling (1.0 µs), thread-to-thread notification (1.5 µs), and device-to-thread notification (1.46 µs).

The fix, threadlet, is a lightweight hardware representation of a software thread — general-purpose registers, a few control registers, and a small 3-tuple of scheduling metadata (priority, deadline, time slice), with floating-point/debug/performance-counter state deliberately dropped or shared. Loom is the architecture that hosts them: a core keeps a handful (8) of loaded threadlets resident in the register file, one staged threadlet pre-fetched and ready, and the rest — up to 512 per core — sit unloaded in the memory hierarchy.

This works because of one measured fact: in real µs-scale workloads with heavy thread oversubscription, only 1.5%–1.9% of threads are runnable at any instant (Figure 5). So a small on-chip "hot set" plus asynchronous prefetching of the next-most-likely thread covers the common case almost for free, while the memory hierarchy absorbs the long tail. Loom then unifies both flavors of notification — thread-to-thread and device-to-thread — through cache-coherence snooping on a monitored memory address, matching polling's latency without its CPU waste.

The payoff: built on an FPGA (Rocket RISC-V core) with a research OS, LoomOS outperforms prior software and hardware approaches by 3× to 47× on end-to-end networking and key-value-store (LMDB) throughput, plus up to 28.5× lower lock latency and a 46.2% cut in delegation-syscall overhead — for about 5.8 KB of on-chip storage per core and a measured 5% increase in total on-chip power.

🧵 Key takeaways

  • Conventional threading pays four taxes: context switching, scheduling, thread-to-thread notification, device-to-thread notification.
  • threadlet = a minimized hardware execution context (registers + PC + a 3-tuple scheduling metadata), not a full thread or a full core.
  • Loom keeps 8 loaded + 1 staged threadlets on-chip; the rest stay unloaded in memory — because usually <2% of threads are runnable.
  • Scheduling has a hardware fast path (rank by the 3-tuple) and a software slow path (a dedicated scheduling threadlet that adjusts the 3-tuple for policies like EEVDF).
  • Memory notification unifies thread-to-thread and device-to-thread wakeups via cache-coherence snooping on a monitored address.
  • Result: 3×–47× on real workloads, ~5.8 KB on-chip storage, <5% power increase, nothing hard-wired to one policy.
Seven everyday pictures

How to think about threadlet & Loom

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Tiered residency

The green room, not the greenroom of everyone

A theater has one small green room (8 seats) for actors about to go on stage, one "on deck" chair for whoever's next, and a much larger backstage area for the rest of the cast. Loom's register file is the green room — a fixed, tiny set of loaded threadlets — with the staging buffer as the on-deck chair and the memory hierarchy as backstage.

Where it breaks: actors decide their own cues; Loom's controller computes who's next from explicit priority/deadline metadata, not from watching for a signal — it's a ranking, not a queue.
For the tiering-minded reader

A memory tiering system, for threads

Loaded / staged / unloaded is structurally the same shape as hot/warm/cold page tiering: a small fast tier, an async promotion buffer, and a large slow tier holding the rest. Just as a tiering system promotes a "hot" page from NVM to DRAM before it's touched, Loom promotes the highest-ranked threadlet before it needs to run.

Where it breaks: page tiering usually infers "hotness" statistically (access-bit sampling, PEBS counters); Loom's ranking is deterministic and software-declared (priority + deadline), and the unit moved is a few-hundred-byte context, not a 4 KB page.
Notification · Coherence snooping

A doorman watching one registered door, not the whole street

A doorman doesn't watch every door in the neighborhood — only the ones he's been asked to. Registering a delivery (tlet_monitor) makes him first walk over and stand by that specific door (pulling the cache line local); from then on he only reacts when that door's intercom (a coherence invalidation) buzzes, not to traffic on every other door in the building.

Where it breaks: a real doorman never mistakes packages; if a monitored cache line is silently evicted (not written), Loom still wakes the waiter — a "spurious wakeup," the cost of using an imperfect proxy signal.
Scheduling · The 3-tuple

Airport boarding groups

Boarding works on three signals: your group number (priority), your specific boarding time (deadline), and how long you're allotted at the jet bridge (time slice). Gate staff never re-derive your itinerary from scratch — they just compare these three numbers. Loom's hardware scheduler does exactly this three-field comparison in a fixed few cycles.

Where it breaks: airlines rarely recompute your whole boarding priority mid-flight; EEVDF's virtual runtime evolves continuously, so LoomOS's software "scheduling threadlet" must periodically recompute and reprogram the 3-tuple — the gate staff occasionally get new instructions from the airline.
Lightweight context · Shared state

A shared checked bag, with a claim ticket

Cutting weight for a µs-scale "trip," threadlet leaves the floating-point/vector registers, debug, and performance-counter state at home — they're bulky and rarely needed. If a threadlet does need them, it can't just grab them; it must explicitly acquire ownership (a claim ticket) via tlet_acq_state, use them, and release with tlet_rel_state.

Where it breaks: an unclaimed suitcase just sits there; forgetting to release the shared FPU state blocks every other threadlet on the core from using it — it behaves like a lock, not idle luggage.
Enforcement · Context switching without moves

Changing lanes, not changing cars

When both the current and next threadlets already sit in registers, "switching" is just redirecting instruction fetch to a different lane of the same highway — no cargo (register data) ever moves. That's why LoomOS's context switch costs 17 cycles: it's a fetch redirect, not a save/restore.

Where it breaks: if the next-ranked threadlet is unloaded (not one of the 8 in registers), you genuinely do need to "get a new car" — swap it in from memory, which is exactly the slower, asynchronous path Loom hides behind the staging buffer.
The full explanation

How it actually works

From the four measured inefficiencies through Loom's tiered storage, scheduling, and notification mechanisms.

At peak load, the paper's networking workloads see up to 900,000 notifications/sec and an average context-switch interval as low as 5.5 µs — so these four costs are not rare, they're the steady state.

2 · A minimized execution context

A threadlet keeps only what's critical: all general-purpose registers, a few control/status registers (PC, stack pointer, page-table register, privilege level), and a 3-tuple of scheduling metadata. It deliberately drops floating-point/vector registers, debug registers, and performance counters — sharing them among sibling threadlets via explicit acquire/release instructions instead.

3 · Tiered storage — the register-file challenge

Supporting 512 threadlets by simply expanding the register file is a non-starter: CACTI modeling (Figure 5a) shows register-file access latency and area both grow rapidly with the number of hardware-resident contexts, which would slow down every instruction. Loom instead exploits the DeathStarBench observation that only 1.5%–1.9% of threads are runnable on average (up to 15.4% at peak) — so it keeps just 8 loaded threadlets in the register file, 1 staged in a staging buffer, and lets the rest sit unloaded in the memory hierarchy.

Ranking is a simple total order over four fields, evaluated in a three-level compare-select tree (≤2 cycles for the 8 loaded threadlets):

# compare two threadlets; higher rank wins
def compare_threadlet_rank(a, b):
    # 1. runnable beats blocked
    if a.is_runnable != b.is_runnable: return a if a.is_runnable else b
    # 2. higher priority wins
    if a.priority != b.priority: return a if a.priority > b.priority else b
    # 3. earlier deadline wins
    if a.deadline != b.deadline: return a if a.deadline < b.deadline else b
    # 4. round-robin distance from CTID breaks ties
    return a if RR_dist(ctid, a.tid) < RR_dist(ctid, b.tid) else b
💡
Why a staging buffer? Without it, every rank change (a threadlet blocking, waking, or changing priority) would need to scan all unloaded threadlets to see if anyone now outranks a loaded one. With a staged 9th-ranked threadlet held ready, most rank changes only need one comparison — against the staged one — done asynchronously, off the execution critical path.

4 · Scheduling: hardware fast path + software slow path

Scheduling triggers at two points: every 32-cycle tick, or when the current threadlet yields/blocks/terminates. The fast path just re-ranks the loaded set (above). The slow path is a dedicated, highest-priority scheduling threadlet the OS registers to fire on key events (creation, wakeup, blocking) — it computes complex policies (like EEVDF's virtual deadlines) and writes the result back into the 3-tuple via tlet_set_sched. Convex, simple policies (round-robin, EDF) need the slow path rarely; EEVDF needs it once per round.

5 · Notification via coherence snooping

A threadlet registers a memory address with tlet_monitor — which brings that cache line into the core's own cache — then yields via tlet_wait. Loom's per-core Address Monitor Table (MAT) remembers which threadlet is waiting on which address. When a subsequent write invalidates that specific, now-local cache line, the coherence invalidation is matched against the MAT, and the controller wakes the corresponding threadlet directly, without OS mediation.

Worked examples

① The headline speedups, recomputed

Figure 7 gives raw cycle counts for LoomOS vs. Linux baselines. Do the paper's "×" claims check out?

  1. Context switch: LoomOS 17 cycles vs. Linux 728 cycles → 728 ÷ 17 = 42.8×.
  2. Scheduling: LoomOS 92 cycles (20 select + 72 amortized policy maintenance) vs. Linux 2,315 cycles → 2315 ÷ 92 = 25.2×, matching the paper's stated "25× lower."
  3. Thread-to-thread notification vs. IPI: LoomOS 73 cycles vs. IPI 6,201 cycles → 6201 ÷ 73 = 84.9×, exactly the paper's cited figure.
  4. Device-to-thread notification vs. interrupt: LoomOS 82 cycles vs. interrupt 1,312 cycles → 1312 ÷ 82 = 16.0×, again matching.
🧵
Insight: these four ratios (42.8×, 25.2×, 84.9×, 16.0×) are Loom's per-mechanism microbenchmark speedups from Figure 7 — not the abstract's headline. The abstract's 3×–47× describes separate, end-to-end real-application measurements (networking, LMDB, locking); notably, Figure 7's own 84.9× already exceeds the abstract's 47× ceiling, since the two number sets answer different questions.

② Storage cost as a fraction of the prototype's cache

The paper states Loom costs ~5.8 KB per core. Where does that number come from, and how small is it really?

  1. TPT: 512 threadlets × (2-bit priority + 16-bit deadline) = 512 × 18 bits = 9,216 bits = 1,152 bytes ≈ 1.2 KB (paper's rounding).
  2. MAT: stated directly — a 512-entry, 8-way set-associative table with 48-bit physical addresses costs 2.8 KB.
  3. Register file growth: stated directly as +1.8 KB (8 loaded contexts' worth of extra general-purpose registers).
  4. Total: 1.2 + 2.8 + 1.8 = 5.8 KB — matches the paper's "around 5.8 KB."
  5. As a fraction of the FPGA prototype's 512 KB L2 (§4.7): 5,800 ÷ 524,288 ≈ 1.1% — in the same ballpark as UCP's "<1% area" for cache partitioning, a familiar order of magnitude for cheap per-core hardware bookkeeping.
💡
None of these structures sit on the instruction critical path — Vivado reports the critical path stays in Rocket's existing DTLB/L1D logic, with only a 5% total on-chip power increase.

③ How rare is a spurious wakeup?

The paper estimates spurious-wakeup frequency from SPEC CPU2017's L2 miss rate. Recompute it.

  1. Given: 8.1 L2 misses per 1,000 instructions, a 3 GHz core, IPC = 1 (so instructions/sec = cycles/sec = 3×10⁹).
  2. Misses/sec = 8.1/1000 × 3×10⁹ = 24.3 million misses/sec.
  3. Bandwidth (assuming a standard 64 B line, consistent with the paper's own figure): 24.3M × 64 B ≈ 1.56 GB/s ≈ the paper's stated "about 1.6 GB/s."
  4. Time to fill a 1 MiB L2: 1,048,576 B ÷ 1.6×10⁹ B/s ≈ 655 µs ≈ the paper's "about 0.7 ms."
  5. Conclusion: spurious wakeups fire roughly once every 0.7 ms per monitored line — far less often than genuine µs-scale wakeups, so they're not a meaningful tax.

Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why does Loom keep only 8 threadlets loaded in the register file instead of, say, 64?
Show answer
CACTI modeling (Figure 5a) shows register-file access latency and area grow with the number of hardware-resident contexts — a bigger register file slows down every instruction, which is unacceptable for µs-scale computing. Since usually <2% of threads are runnable, 8 loaded slots already covers the common case; the rest live cheaply off-chip.Misconception: that more on-chip contexts is strictly better. Register-file size trades off against per-instruction latency for every thread, not just the extra ones.
Problem 2 · medium
The TPT stores only priority and deadline per threadlet, yet LoomOS implements EEVDF, which also needs a virtual runtime per task. Where does virtual runtime live?
Show answer
It's maintained in software by the scheduling threadlet (the slow path), not in the hardware 3-tuple. At the end of each round, the scheduling threadlet advances every threadlet's virtual runtime, recomputes virtual deadlines, and programs only the resulting deadline/time-slice fields into Loom via tlet_set_sched. The hardware fast path never sees virtual runtime directly.Misconception: assuming Loom's hardware tracks full EEVDF state. It only tracks the derived 3-tuple; the policy's real bookkeeping stays in software, invoked infrequently.
Problem 3 · hard
Thread-to-thread notification (1.52 µs) is slower than device-to-thread notification (1.46 µs) in Figure 2, even though waking a sleeping thread sounds simpler than servicing an interrupt. Why?
Show answer
Thread-to-thread wakeup pays 0.94 µs just updating kernel wait/run-queue state, plus 0.58 µs "wait for a tick" — a woken thread must wait for the next scheduler tick (often a timer interrupt) before it actually runs. Device notification instead runs the interrupt handler immediately (its overhead is APIC/softirq machinery, not a waiting period). The "wait for tick" tax is what makes even a conceptually simple wakeup surprisingly slow.Misconception: that conceptual simplicity predicts latency. Both paths are OS-mediated; the specific mediation steps (and whether you must wait for a periodic tick) determine cost, not how "simple" the event feels.
Problem 4 · easy
True or false: Loom expands the register file enough to hold all 512 threadlets a core can manage.
Show answer
False. The register file only grows enough to hold 8 loaded threadlets (+1.8 KB). The other up to 503 threadlets a core can support stay unloaded in the memory hierarchy and are swapped in only when they rank into the top 8 (or become the staged 9th).Misconception: conflating "supports 512 threadlets per core" with "512 hardware-resident contexts." Support means addressable and manageable, not simultaneously resident.
Problem 5 · medium
Why does Loom need a dedicated staging buffer, rather than just promoting directly from the unloaded pool into the register file whenever a rank change happens?
Show answer
Promoting from the unloaded pool requires a sequential scan (via find-first-set over the 512-bit placement bitmap plus TPT lookups) that can take on the order of 100+ cycles for tens of unloaded threadlets — too slow to do synchronously on every rank change. The staging buffer holds the current 9th-ranked candidate so that most rank changes only need a cheap comparison against it; the expensive scan of the unloaded pool happens asynchronously, off the critical path.Misconception: that the staging buffer is just "one more loaded slot." Its role is specifically to absorb the asynchronous scan latency, not to add scheduling capacity.
Problem 6 · medium
A monitored cache line gets evicted (not written) — Loom still wakes the waiting threadlet. Is this a bug?
Show answer
No — it's a deliberate, conservative design choice, analogous to x86's MWAIT behaving the same way. Since Loom can't distinguish "the data changed" from "the line just left the cache," it errs toward waking the threadlet (a spurious wakeup) rather than risking a missed wakeup. The back-of-envelope analysis shows this happens roughly once per 0.7 ms per monitored line for typical workloads — rare enough to be a non-issue.Misconception: that any spurious wakeup indicates incorrect hardware. It's the safe default for an imperfect proxy signal, and its cost is bounded and small.
Problem 7 · hard
Switching between threadlets on the same core doesn't require rewriting page-table registers or flushing in-flight instructions from other threadlets, unlike a full process switch. Why?
Show answer
Each threadlet carries its own ASID, page-table base register (PTBR), and privilege level as part of its (small) on-chip metadata, and every in-flight instruction is tagged with its threadlet ID and privilege level. The MMU uses that per-instruction tag to select the right address space and check permissions, so multiple threadlets' in-flight instructions can coexist in the pipeline without a global address-space reload.Misconception: that switching execution contexts always implies switching address spaces the way a process switch does. Loom decouples "which threadlet is fetching" from "flush the pipeline for a new address space" by tagging instructions individually.
Problem 8 · hard
For a reader working on DRAM/NVM tiering: how is Loom's loaded/staged/unloaded threadlet storage similar to — and different from — page-level memory tiering?
Show answer
Similar: both use a small fast tier (register file / DRAM), an async promotion mechanism to hide movement latency (staging buffer / migration or prefetch queue), and a large slow tier for the long tail (memory hierarchy / NVM). Different: (1) the "hotness" signal — Loom uses explicit, deterministic software metadata (priority + deadline), while page tiering typically infers hotness statistically from access-bit sampling or hardware counters; (2) the unit size — a threadlet context is a few hundred bytes vs. a 4 KB page, so the cost/benefit ratio of movement is very different; (3) Loom's promotion is triggered by scheduling rank changes (an event), whereas page tiering is often triggered by periodic scans or access-frequency thresholds.Misconception: assuming any "hot/cold tiered storage" system uses the same signal and granularity. The mechanism shape can repeat across very different abstraction levels while the actual hotness signal and unit size differ substantially.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1Is a threadlet the same thing as a hardware thread (SMT context)?▾
No. SMT contexts are a microarchitectural trick — a fixed handful of full hardware thread slots to hide pipeline stalls and maximize utilization. threadlet is an OS-visible abstraction carrying scheduling semantics (priority, deadline, time slice) and full manageability (create/delete/wake instructions), and it scales to hundreds per core precisely because most stay off the pipeline entirely. The paper notes they're complementary and can coexist (§4.8, §7).
Q2Why not just make the register file bigger to hold every thread?▾
Register-file access latency and area both scale up with the number of resident contexts (Figure 5a), which would slow down every instruction — unacceptable at µs-scale. Since typically under 2% of threads are runnable at once, a small resident set (8) plus off-chip storage for the rest is far cheaper without sacrificing common-case performance.
Q3How does Loom fix all four inefficiencies at once?▾
By removing the software-thread layer of indirection. Context switching becomes a fetch redirect among on-chip contexts (no memory round-trip). Scheduling becomes a fixed hardware comparison over a 3-tuple. Both notification types collapse into one mechanism — coherence-snooped memory monitoring — since hardware can now interface directly with the threads themselves.
Q4What happens when more than 8 threadlets are runnable?▾
The controller swaps threadlets between the register file and memory as scheduling ranks change, using the staging buffer to hide the swap latency asynchronously. If more than 512 threadlets are needed on one core, LoomOS migrates some to another core in software.
Q5Isn't memory-address monitoring just MWAIT/MONITOR?▾
Similar in spirit — both watch a memory address and go idle until it's written — but MWAIT primarily targets power savings during idle loops and still leaves the OS to do the actual thread bookkeeping. threadlet's tlet_monitor/tlet_wait directly transitions the threadlet to blocked and lets Loom's own scheduler pick the next one, with no OS involvement at all.
Q6Does Loom replace the OS scheduler entirely?▾
No — it replaces the fast, per-tick decision with hardware, but the OS (via the scheduling threadlet) still defines and periodically recalibrates the policy. This "fast path in hardware, slow path in software" split is what lets Loom stay flexible instead of hard-wiring one scheduling policy.
Q7What happens to floating-point/vector state, since threadlets don't carry it?▾
It's shared among sibling threadlets on a core. A threadlet must explicitly acquire ownership (tlet_acq_state) before using it and release it afterward (tlet_rel_state); accessing it without acquiring triggers an exception. This mirrors Linux's existing lazy-FPU-switching optimization.
Q8Can Loom migrate threadlets across cores?▾
Not in hardware — Loom itself has no cross-core migration support. LoomOS implements it in software: create a new threadlet on the target core, copy over architectural and scheduling state, then delete the original. The paper flags generic hardware support for this as future work.
Q9What's the total overhead of adding Loom to a core?▾
About 5.8 KB of on-chip storage per core (1.8 KB register file growth + 1.2 KB TPT + 2.8 KB MAT), roughly 1% of the 512 KB L2 in their FPGA prototype. Vivado reports a 5% increase in total on-chip power, and the critical path stays in the baseline Rocket core's existing DTLB/L1D logic — nothing new is added to it.
Q10What's still missing / left for future work?▾
Cross-core migration support in hardware (currently software-only), TLB shootdown and microkernel IPC use cases (designed but not yet implemented), and extending Loom to SMT/out-of-order cores beyond the in-order Rocket prototype used for evaluation (§4.8 sketches the direction).

Glossary, results, and provenance

Every term in one place, the headline numbers, and where each claim in this guide comes from.

Core terms
threadletA hardware abstraction representing a unit of execution: general-purpose registers, key control registers, and a 3-tuple of scheduling metadata — lighter than a software thread or a hardware core.
LoomThe supporting architecture: a threadlet controller, an enlarged (but still small) register file, the TPT, and the MAT, integrated into a core.
Loaded / staged / unloadedLoom's three-tier storage for threadlet state: 8 resident in the register file, 1 pre-fetched in a staging buffer, up to 503 more in the memory hierarchy.
3-tupleA threadlet's scheduling parameters — priority, deadline, time slice — that hardware ranks directly to pick the next threadlet to run.
Scheduling threadletAn OS-registered, highest-priority threadlet that runs on key scheduling events to implement policies (e.g., EEVDF) too complex for the hardware fast path alone.
Memory notificationthreadlet's unified mechanism for thread-to-thread and device-to-thread wakeups: monitor an address, yield, and be woken by a coherence-detected write.
Spurious wakeupA wakeup triggered by eviction (not a true write) of a monitored cache line — a conservative, infrequent side effect of the monitoring mechanism.
Supporting terms
LoomOSThe research OS (9,517 LOC, extending a small Rust RISC-V kernel) that exercises Loom across networking, locking, scheduling, and syscalls.
TPTThreadlet Policy Table: per-threadlet priority + deadline, 1.2 KB for 512 threadlets.
MATAddress Monitor Table: per-core, 512-entry, 8-way set-associative table mapping monitored addresses to threadlet IDs, 2.8 KB.
CTIDCurrent Threadlet ID register (9 bits); also the round-robin tie-break pointer.
Placement bitmapA 512-bit bitmap tracking which runnable threadlets are currently unloaded, scanned via find-first-set.
EEVDFEarliest Eligible Virtual Deadline First — Linux's default scheduler, which LoomOS re-implements on top of the 3-tuple.
FlexSC / delegation syscallsA model where dedicated cores handle system calls via shared memory, avoiding trap overhead; LoomOS realizes this without the spinning FlexSC/io_uring otherwise require.
MCS lockA classic scalable queue-based lock; LoomOS implements a blocking variant (MCS-B) using memory notification instead of spinning.
