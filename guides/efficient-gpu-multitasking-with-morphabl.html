SOSP 2026 · A Field Guide

Letting a GPU kernel breathe, instead of freezing its footprint at launch

Two GPU tasks share one device. Today's rule fixes each kernel's SM footprint the instant it launches — forcing schedulers to choose between rigid partitions and expensive kernel slicing. This is the plain-English story of MorphX, a system that lets a running kernel change shape.

📄 Ren, Fan, Guo, Xie, Gao, Shu, Lu — Tsinghua University 🎓 GPU/CUDA basics assumed — primers cover them ⏱ ~30 min read
🧬

Let a kernel YIELD or RECLAIM SMs while it runs — instead of FREEZING its footprint the moment it's launched.
No relaunch, no slicing — the kernel itself becomes the scheduling object.

1Kernels, thread blocks, and SMs▾

A GPU task is a sequence of kernels. Each kernel is organized as a grid of thread blocks, and the driver decides how many blocks can sit concurrently on one SM based on the kernel's register and shared-memory needs. Once a block lands on an SM, it cannot move until it finishes.

Now you're ready: MorphX's whole trick is turning "thread blocks placed once by hardware" into "thread blocks fetched repeatedly by software," so their SM assignment can change mid-flight.
2CUDA streams and "concurrent" kernels▾

Kernels in the same stream run strictly in order; kernels in different streams may run concurrently, but nothing guarantees how the hardware interleaves them — even with stream priorities.

Now you're ready: "best-effort" scheduling just means launching two tasks in two streams and hoping the hardware scheduler shares SMs sensibly. It usually doesn't.
3Kernel launch overhead — why slicing is expensive▾

Every kernel launch costs host-side setup and driver bookkeeping — the paper measures upwards of 10 µs per launch. Slice a kernel into many small pieces to get fine-grained control, and those 10 µs charges compound. The paper measures aggressive slicing inflating a matrix-multiply's latency by 5.317×.

Now you're ready: this is the exact cost morphable kernels are built to avoid — adjusting SMs without any extra launch.
4The rigid-footprint assumption▾

Every existing scheduler — best-effort, static partitioning (Green Context/MPS/MIG), even kernel preemption — treats a launched kernel's SM footprint as fixed until it exits or is fully torn down. Preemption can stop a kernel, but it doesn't let two co-running kernels trade SMs while both keep executing.

Now you're ready: this single assumption is the "rigid constraint" the paper's title implies breaking.
5Compute-bound vs memory-bound (the Roofline model)▾

A kernel's performance is capped by whichever resource it exhausts first: compute throughput (FLOPs/s) or memory bandwidth (bytes/s). Operational intensity — operations per byte moved — decides which ceiling applies. Low intensity ⇒ memory-bound; high intensity ⇒ compute-bound.

Now you're ready: reducing a kernel's SM count lowers its compute ceiling but not its memory ceiling — so a kernel can flip from compute-bound to memory-bound as SMs are taken away. That flip is the basis of MorphX's whole performance model.
6Static SM partitioning today (Green Context, MPS, MIG)▾

NVIDIA's Green Context API, MPS, and MIG let you pin a fixed set of SMs to a context or kernel before it launches. This gives explicit, guaranteed isolation — but the split can't change while the kernel runs, even if the co-runner's demands shift a moment later.

Now you're ready: these are the "kernel-wise static" baselines MorphX is compared against — correct in spirit, just frozen in time.
7Host–GPU asynchrony▾

The CPU launches kernels and immediately moves on — it doesn't wait for them to finish, and by default has no idea which kernel is executing on the GPU at any given instant.

Now you're ready: this is why MorphX needs its own lightweight, GPU-side progress counters rather than relying on the CPU's natural sense of "what's running now."
8Compiler IR and why MorphX rewrites kernels there▾

LLVM compiles code through an intermediate representation (IR) before producing GPU machine code. Transforming a kernel at the IR level (rather than hand-editing machine code) keeps the change portable across GPU backends and avoids manual register-allocation mistakes.

Now you're ready: MorphX's compiler plugin rewrites ordinary __global__ functions into morphable ones automatically, with no source changes from the programmer.
The whole story in one place

MorphX in a nutshell

The constraint, the abstraction that breaks it, and why that unlocks both utilization and latency wins.

When two GPU tasks share a device, every existing scheduler inherits one assumption: once a kernel launches, its SM footprint is fixed until it exits. Best-effort scheduling (CUDA streams) can't guarantee any particular split; static partitioning (Green Context, MPS, MIG) fixes a split but can't adapt when the co-runner's demands change moments later; kernel slicing adapts, but at the cost of a fresh kernel launch — and its ~10 µs overhead — for every slice.

The paper's fix is morphable kernels: a kernel whose thread blocks are dispatched by a software micro-scheduler on each SM, pulling from a shared work pool, instead of being placed once by hardware. Shrinking the SM range (minSM/maxSM) makes SMs outside it finish their current block and stop — no relaunch. Growing it uses a small reclaim queue kernel that shares the same work-pool counters, so growth doesn't cause head-of-line blocking on other pending kernels.

To decide how to split SMs, MorphX reuses those same micro-interfaces (fetched, finished) for in-place profiling: it watches how a kernel's per-wave latency changes as its SM count changes, fits a simple Roofline-style model, and derives each kernel's normalized compute intensity — all with under 5% overhead, versus the 400×–1590× overhead of profilers like NCU or NvBit.

The payoff: up to 2.24× higher background-task throughput at the same foreground latency versus the SotA (Orion), up to 63.3% lower task latency under heavy pressure, and up to 70.6% lower P99 latency versus vLLM in prefill–decode-disaggregated LLM serving.

🧬 Key takeaways

  • Every prior scheduler treats a launched kernel's SM footprint as fixed; MorphX makes it runtime-adjustable with no extra launch.
  • The mechanism: a per-SM micro-scheduler pulls thread blocks from a shared pool; shrinking = stop fetching; growing = a high-priority reclaim instance sharing the same counters.
  • The measurement: in-place profiling reads per-wave latency through 4 device-resident integers, accessed via GDRCopy — no CUPTI, no binary instrumentation.
  • The decision: a Roofline-style model derives each kernel's normalized compute intensity and solves for the SM split that saturates both compute and bandwidth.
  • Extra launches are bounded at ≤2× the original kernel count (only on reclaim) — versus tens to hundreds of slice-launches in kernel-slicing systems.
  • Result: 2.24× background throughput, ≤63.3% latency reduction under pressure, ≤70.6% P99 reduction vs vLLM, monitoring overhead <5%.
Six everyday pictures

How to think about morphable kernels

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Elastic staffing

Calling in extra staff mid-shift

A restaurant kitchen doesn't close and reopen to add a cook when a rush starts — a worker who's mid-task finishes that plate, then a new hire steps in at the same station. Morphable kernels work the same way: an SM finishes its current thread block, then either keeps pulling from the shared queue or steps aside — no need to shut the kitchen (relaunch the kernel) to change staffing.

Where it breaks: a cook can improvise; a micro-scheduler can only fetch the next block from a fixed pool. There's no creative reassignment of half-finished work — correctness requires each block run start-to-finish on one SM.
Reallocation · Reversible highway lanes

Lanes that flip with rush hour

Some highways reverse a center lane's direction depending on morning vs evening traffic — no new road is built, the same lanes just get relabeled live. MorphX's minSM/maxSM signals do the same to SM ranges: as one kernel's demand rises and another's falls, the boundary between them slides, using the same physical SMs.

Where it breaks: a lane reversal is instantaneous once signs change; an SM only actually frees up after its current thread block finishes — there's a short, bounded lag, not an instant cutover.
Reclaim without HoL blocking · Priority lane

An ambulance lane at a toll plaza

A stalled toll booth backs up every car behind it. Emergency vehicles get a dedicated fast lane instead, so they don't wait behind whatever's jammed. MorphX's reclaim queue is that fast lane: a new, high-priority kernel instance grabs newly-freed SMs immediately, without waiting behind unrelated pending kernels queued in the original stream — avoiding head-of-line blocking.

Where it breaks: the ambulance lane is empty by design; the reclaim instance actually shares live progress counters (fetched/finished) with the original kernel, so it's not really a separate vehicle — it's the same trip, continuing through a different gate.
Cheap monitoring · Vitals vs a full workup

A pulse oximeter, not an MRI

A nurse doesn't order an MRI to check if a patient is stable — a cheap clip-on sensor reading pulse and oxygen, checked continuously, is enough to catch trouble in real time. MorphX's in-place profiling is the pulse oximeter: four integers (fetched, finished, minSM, maxSM) read via GDRCopy, versus a full diagnostic workup like NCU or NvBit that's accurate but far too slow (up to 1590× and 409× overhead respectively) to run continuously.

Where it breaks: vitals are a fixed, small set of signals; MorphX's "vitals" (wave latency at varying SM counts) had to be specifically engineered so that this one cheap signal is enough to infer compute-vs-memory-bound behavior — it isn't a generic health check.
Roofline model · The ceiling that follows your headcount

A factory's output cap depends on staff and supply trucks

A factory's daily output is capped by whichever runs out first: workers on the line, or the trucks delivering raw material. Hire more workers and output rises — until the trucks can't keep up, at which point extra hires do nothing. That's exactly what happens to a GPU kernel as SMs (workers) increase: performance rises until memory bandwidth (the delivery trucks) becomes the limit.

Where it breaks: a factory's truck capacity is usually fixed; on a GPU, memory bandwidth is shared with the co-located kernel, so the "truck capacity" available to one kernel shrinks whenever its neighbor also needs deliveries — that interaction is exactly what Equation 2's combined intensity term captures.
Kernel slicing's cost · Paying a toll every block

A toll booth on every block of the highway

Imagine a road with a toll booth every block instead of one at the entrance — fine-grained control over who's on which segment, but you pay a fixed fee and stop-and-go delay at every single booth. Kernel slicing gets fine SM control the same way: one relaunch (with real driver overhead) per slice, every time the allocation should change.

Where it breaks: a toll booth's fee is fixed regardless of the car; a kernel launch's ~10 µs cost is fixed regardless of the slice's actual work, so slicing hurts most on kernels that are naturally small or should be split often — exactly the case the paper measures as a 5.317× latency inflation.
The full explanation

How MorphX actually works

Section by section, with the paper's mechanisms rebuilt as diagrams you can read at a glance.

1 · The key observation — thread blocks as a movable work pool

A kernel's thread blocks can be remapped across SMs during execution without breaking correctness, as long as each block still runs start-to-finish on some SM. MorphX exploits this directly: instead of the hardware placing blocks once, a micro-scheduler deployed on each SM repeatedly fetches the next unclaimed block from a shared, atomically-incremented index.

2 · Reclaiming SMs — the reclaim queue

Yielding is easy; regrowing is the hard direction. Relaunching the same kernel in its original stream risks head-of-line (HoL) blocking — other kernels already queued behind it would have to wait. MorphX instead launches a second instance, K′, into a dedicated, higher-priority internal stream. Crucially, K′ shares the same fetched/finished counters as the original K, so its micro-schedulers just keep consuming the same logical work pool — it's the same execution, continuing through a different launch.

💡
Why this stays cheap: reclaim only fires when a co-located kernel exits, so extra launches are bounded at ≤2× the original kernel count — nowhere near the tens-to-hundreds of per-slice launches in kernel-slicing systems.

3 · Compile-time transformation — five passes, no source changes

An LLVM compiler plugin rewrites every __global__ function automatically: ➊ force-inline __device__ callees; ➋ append four micro-interface parameters (fetched, finished, minSM, maxSM) plus the original grid dimensions; ➌ wrap the body in a work-fetching while loop that checks the SM range and increments the counters; ➍ remap all uses of blockIdx/gridDim to the fetched index; ➎ redirect every return to the loop's exit point. The transformation is independent of the kernel's actual logic.

🌱
Kernel switching: the injected loop adds negligible overhead on long kernels but becomes noticeable on very short ones. MorphX keeps both the original and transformed binary and, using profiled wave latency, launches the plain kernel when a kernel is too small to be worth morphing — the paper reports 5 of 26 distinct kernels in a Llama-3-8B serving workload are dominant enough (first-wave latency >50 µs) to warrant morphing, accounting for 85% of total GPU time.

4 · Real-time resource monitoring — in-place profiling

MorphX measures the latency of each wave (one round of concurrently-executing blocks) directly from the micro-interfaces. On a kernel's first execution, it deliberately assigns a decreasing number of SMs to successive waves (at most a 2× slowdown, once) and fits Equation 1's Roofline-style model to the observed latencies, extracting the kernel's normalized compute intensity Ic. Memory-intensive kernels (Ic<1) show flat latency until an SM threshold, then rising latency past it; compute-intensive kernels (Ic>1) show latency falling smoothly with more SMs and never hit that memory ceiling within the device's range.

Compute-intensive kernels can't have their Ic measured standalone (there's no bandwidth ceiling to hit alone), so MorphX derives it later, during actual co-location, from how much the other, memory-intensive kernel slows down — solving Equation 3 for the compute-intensive kernel's implied bandwidth demand.

5 · The scheduler — three policies on top of one model

# throughput-oriented (Eq. 4): saturate both compute and bandwidth
n_p + n_q = 1
n_p * Im_p + n_q * Im_q = 1          # Im = 1/Ic ; solve for n_p, n_q

# bandwidth isolation for a high-priority task p (Eq. 5)
minimize n_p
subject to n_p ≥ w_p_compute,
           (n_p*Im_p) / (n_p*Im_p + (1-n_p)*Im_q) ≥ w_p_bandwidth

# user hint: pin a stream's desired SM% directly
if conflict: prioritize the later-launched kernel

By default MorphX runs the throughput-oriented policy transparently on the first two kernels at the head of each stream's queue (checking two, not one, to hide host–device communication latency). It can also enforce bandwidth isolation for a latency-critical task, or accept a manual SM-percentage hint from the user for cases (like LLM batch-size tuning) where raw utilization isn't the only goal.

Follow the numbers, step by step

Worked examples

Four traces using the paper's own measured values — profiling, refinement, scheduling, and overhead.

① Reading compute intensity off the profiled kernels

Figure 16 profiles three matrix-multiply kernels (varying dimension M) by sweeping SMs per wave. Two are memory-intensive, with fitted Ic = 0.247 and Ic = 0.753.

  1. Ic < 1 means memory-bound — the kernel hits its bandwidth ceiling before using all the SMs.
  2. Ic = 0.247: by Eq. 1, performance saturates once x/Ic ≥ 1, i.e. x ≥ 0.247 — just 24.7% of SMs already saturate this kernel's bandwidth.
  3. Ic = 0.753: saturates once x ≥ 0.753 — this kernel needs 75.3% of SMs before bandwidth caps it, since it moves less data per unit of compute.
  4. A third kernel showed flat latency at every SM count tested — the signature of a compute-bound kernel (Ic > 1), whose ceiling isn't reachable within the device's SM range alone.
🧬
Insight: two numbers (Ic for each kernel) are enough to predict the entire SM-vs-latency curve — that's what makes real-time profiling tractable.

② Deriving a compute-bound kernel's intensity via co-location (Eq. 3)

Kernel (c) can't be profiled standalone. Co-located with memory-intensive kernel (a) at a 1:1 SM split (x = 0.5), kernel (a)'s wave latency rises by 43%. The paper reports the derived Ic(c) = 1.19.

  1. Kernel (a) is deep in its saturated regime at x=0.5 (Ic(a)=0.247, so x·Im(a) = 0.5×(1/0.247) ≈ 2.02, and Eq. 3's min(·,1) clamps the numerator to 1).
  2. Latency up 43% ⇒ throughput ratio P̂/P* ≈ 1/1.43 ≈ 0.699 (same work, more time).
  3. Solve Eq. 3 for the denominator: 1/(1+0.5·Im(c)) = 0.699 ⇒ Im(c) ≈ 0.86.
  4. Invert: Ic(c) = 1/Im(c) ≈ 1.16 — within rounding of the paper's reported 1.19 (small gaps come from the coarse "43%" figure).
💡
This is the whole point of in-place profiling: a compute-bound kernel's demand is inferred purely from how much it hurts its neighbor — no standalone experiment needed.

③ Solving for the optimal SM split (Eq. 4)

Co-locate memory-intensive kernel (b) (Ic=0.753, so Im(b)=1/0.753≈1.328) with compute-intensive kernel (c) (Ic=1.19, so Im(c)=1/1.19≈0.840).

  1. Set up Eq. 4: n_b + n_c = 1, and n_b·1.328 + n_c·0.840 = 1.
  2. Substitute n_c = 1 − n_b: n_b·1.328 + (1−n_b)·0.840 = 1.
  3. Solve: n_b·(1.328−0.840) = 1−0.840 ⇒ n_b·0.488 = 0.160 ⇒ n_b ≈ 0.328.
  4. So n_c ≈ 0.672 — roughly a 33/67 split, memory kernel to compute kernel, saturating both compute and bandwidth at once.
🧬
Insight: this matches the paper's own motivating example of an optimal ~3:1 (CI:MI) ratio for co-located GEMM kernels (§3) — the exact ratio just depends on each kernel's measured intensity.

④ Tallying overhead: monitoring and launches

Is the machinery actually cheap? Add it up.

  1. Micro-interface size: 4 integers (fetched, finished, minSM, maxSM) — 16 bytes, entirely in device memory.
  2. Polling cost: ~10 µs per GDRCopy poll, transferring 8 bytes ⇒ ≈0.8 MB/s of PCIe traffic, versus ~25 GB/s peak — about 0.0032% of peak bandwidth.
  3. Launch overhead: reclaim adds at most 2× the original kernel count in extra launches (only on exit); kernel slicing launches a fresh kernel per slice, and the paper measures this inflating a matrix-multiply's latency by 5.317×.
  4. Profiling overhead measured end-to-end: MorphX <5% across DNN/GEMM/GEMV/GGNN/LLM workloads (<0.5% for GEMM/GGNN), versus NCU's 2.23×–1590× and NvBit's >409×.
💡
The punchline: a scheduling signal worth up to 2.24× throughput costs a few dozen bytes and microseconds of polling — orders of magnitude cheaper than the profilers it replaces.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
Two kernels are launched in separate CUDA streams with different stream priorities. Why doesn't this guarantee they share SMs in a complementary (compute+memory) way?
Show answer
Streams only order kernels within themselves; across streams, the hardware's thread-block placement is best-effort and not exposed to software. Priority can influence scheduling timing but gives no explicit control over which SMs each kernel occupies, so the achieved split is whatever the hardware happens to produce — often leaving one resource idle.Misconception: that stream priority is a resource-allocation knob. It's a scheduling hint, not a partitioning mechanism.
Problem 2 · medium
A memory-intensive kernel has Ic = 0.247. If MorphX allocates it x = 0.5 (50%) of the SMs, what is its performance P*(x), and what does that imply about giving it more SMs?
Show answer
By Eq. 1 (Ic<1): P*(x) = min(x/Ic, 1) = min(0.5/0.247, 1) = min(2.02, 1) = 1 — already fully saturated. Giving it more than ~24.7% of SMs buys nothing; any SMs beyond that threshold are wasted on this kernel and should go to a co-runner instead.Misconception: that more SMs always helps. A memory-bound kernel's performance flatlines past its bandwidth-saturation threshold, exactly like a saturating cache-utility curve.
Problem 3 · medium
Co-locate memory-intensive kernel (a) (Im=4.049, from Ic=0.247) with compute-intensive kernel (c) (Im=0.840, from Ic=1.19) using Eq. 4. What SM split saturates both?
Show answer
n_a + n_c = 1; n_a·4.049 + n_c·0.840 = 1. Substituting n_c=1−n_a: n_a·(4.049−0.840) = 1−0.840 ⇒ n_a·3.209 = 0.160 ⇒ n_a ≈ 0.050, n_c ≈ 0.950. Kernel (a) is so memory-hungry it saturates bandwidth with only ~5% of the SMs — the rest should go to the compute-bound kernel.Misconception: that a "fair" split should be closer to 50/50. The optimal split depends entirely on each kernel's measured intensity, and can be extremely lopsided.
Problem 4 · hard
MorphX bounds extra kernel launches at ≤2× the original kernel count. Explain why this bound holds, and why it can't be tighter (≤1×) in general.
Show answer
Reclaiming is only triggered when a co-located kernel exits and SMs become free — so each original kernel can trigger at most one reclaim launch (its own K′) over its lifetime, giving ≤2× total (1 original + 1 reclaim). It can't generally be bounded at ≤1× because the reclaim instance is a genuinely separate launch, required specifically to avoid head-of-line blocking in the original stream — reusing the original launch would risk exactly the HoL stall MorphX is designed to prevent.Misconception: that "no extra launch overhead" means zero extra launches. MorphX minimizes launches to a small constant factor, not to zero — the win is relative to slicing's much larger per-slice count.
Problem 5 · easy
Why does MorphX skip morphable transformation for small kernels ("kernel switching"), even though it could apply the same mechanism uniformly?
Show answer
The injected work-fetching loop and micro-interface bookkeeping cost a small, roughly fixed overhead per kernel. On a long-running kernel that cost is negligible; on a very short kernel it can dominate the actual work. Since short kernels also finish quickly and barely interfere with co-runners, MorphX profiles the relative overhead and falls back to the untransformed original kernel when it exceeds a threshold — dominant kernels alone accounted for 85% of GPU time in the paper's Llama-3-8B example.Misconception: that "transparent" means "always transform." MorphX is selective, applying morphing only where its cost is worth paying.
Problem 6 · hard
LithOS (kernel slicing) keeps LLM latency competitive under light ANNS load but its tail latency worsens sharply under heavy load — sometimes worse than static MPS. Explain why.
Show answer
Slicing creates more scheduling points by atomizing long kernels, which helps isolate latency-critical work at first. But every atom requires its own kernel launch and host-side synchronization. As background pressure rises, more atoms must be scheduled and launched, and those fixed per-atom costs accumulate; allocation can only be revised at atom boundaries, not continuously. Eventually the compounding launch overhead outweighs the benefit of finer-grained control, pushing tail latency above even a static, coarse-grained partition.Misconception: that finer granularity is always better. Granularity bought via extra launches has a cost that scales with load — at some point it exceeds the benefit.
Problem 7 · medium
NCU can measure exact memory read/write sizes per kernel but incurs 2.23×–1590× overhead. Why is that disqualifying for MorphX's use case, even though NCU is more precise?
Show answer
MorphX needs to re-decide SM allocation continuously, in real time, alongside normal execution — precision that costs orders-of-magnitude slowdown defeats the purpose, since the measurement itself would dominate and distort the very performance it's trying to optimize. A cheap, slightly approximate signal (per-wave latency via 4 counters, <5% overhead) that's available continuously beats a precise one that can only be used offline.Misconception: that more accurate profiling is strictly better. For a runtime control loop, low overhead and continuous availability matter more than precision.
Problem 8 · easy
Two co-located kernels are both memory-intensive with Im well above 1. Can Equation 4's throughput-oriented split find an allocation with Îm exactly 1?
Show answer
No — Îm = n_p·Im_p + n_q·Im_q is a weighted average of Im_p and Im_q with weights summing to 1; if both Im values exceed 1, every possible weighted average also exceeds 1, so bandwidth demand always outstrips supply regardless of the split. Balancing to Îm=1 only works when the two kernels have complementary (one high, one low) intensities.Misconception: that MorphX can always find a "perfect" split. It can only balance kernels with complementary resource profiles — two memory-hungry kernels together will always contend for bandwidth no matter how SMs are divided.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1What exactly is a "morphable kernel"?▾
A GPU kernel compiled so that its thread blocks are dispatched by a software micro-scheduler on each SM, pulling from a shared work pool, instead of being placed once by hardware. This lets the host scheduler shrink or grow the kernel's active SM range (minSM/maxSM) while it's still executing — no relaunch required.
Q2How can software control SM placement when GPUs have no interrupt mechanism?▾
MorphX doesn't interrupt anything — it bypasses the hardware's thread-block placement entirely. Every SM's micro-scheduler polls two host-writable variables (minSM, maxSM) before fetching its next block; if it's outside that range it simply stops fetching. Control happens between blocks, not via a hardware interrupt.
Q3What are fetched/finished and minSM/maxSM?▾
Four integers appended to every transformed kernel, living in device memory. fetched is atomically incremented by micro-schedulers claiming the next thread block; finished increments when a block completes. minSM/maxSM are written by the host to set the currently allowed SM range. Together they're a lightweight, bidirectional control-and-monitoring channel.
Q4Why not just relaunch with a new Green Context SM setting instead?▾
A relaunch is a genuinely new kernel: it costs a driver-level launch (~10 µs), and worse, kernels already queued behind it in the same stream would need to be drained or reordered. Morphable kernels change allocation for an already-running kernel with no launch and no disruption to the surrounding stream.
Q5What is the reclaim queue and why does it need higher priority?▾
When SMs free up and a kernel should grow back into them, MorphX launches a second instance sharing the original's fetched/finished counters into a dedicated internal stream with higher priority than any user stream. High priority lets it occupy the freed SMs immediately, ahead of whatever kernel was next in the queue that just vacated them — avoiding head-of-line blocking.
Q6How does MorphX classify a kernel as compute- or memory-bound without offline profiling?▾
On first execution, it assigns progressively fewer SMs to successive waves and fits the observed per-wave latencies to a Roofline-style model (Eq. 1), extracting the normalized compute intensity Ic. Compute-intensive kernels (whose Ic>1 threshold is unreachable standalone) get their intensity refined later during actual co-location, from how much they slow down a co-running memory-intensive kernel (Eq. 3).
Q7Why transform kernels at the LLVM IR level instead of PTX or machine code?▾
IR-level transformation generalizes across GPU backends (the same passes can target NVIDIA or, with minimal changes, AMD) and avoids the performance pitfalls of manually managing registers that hand-editing PTX would require.
Q8Why do small kernels skip the morphable transformation?▾
The injected work-fetching loop adds overhead that's negligible on long kernels but non-trivial on very short ones. MorphX keeps both versions in the compiled binary and, using profiled wave latency, launches the plain original kernel when the relative overhead would exceed a threshold — since short kernels also cause little interference anyway.
Q9Does MorphX manage GPU memory capacity too?▾
No — it only manages SM (compute) allocation. HBM capacity management and swapping are treated as an orthogonal research direction in the paper; MorphX's transformation and profiling could in principle extend to I/O-bound kernels, but the performance model and scheduling policy would need adaptation.
Q10How is this different from MPS or MIG?▾
MPS and MIG (and Green Context) let you pin an SM allocation before launch — explicit and guaranteed, but frozen for that kernel's whole execution. MorphX makes the allocation itself a runtime-adjustable property of the running kernel, so it can track a co-runner's changing demands without relaunching.
Q11Can MorphX schedule kernels across separate processes or containers?▾
The evaluated prototype coordinates streams within one process via a background host thread. The paper notes this could extend to multiple processes/containers through established GPU API-remoting techniques, treated as orthogonal engineering.
Q12Does MorphX work on non-NVIDIA GPUs?▾
The prototype targets NVIDIA GPUs, but the design is largely software-based and doesn't depend on NVIDIA-specific hardware features. Since the transformation is implemented in LLVM (which AMD GPUs also compile through), the paper suggests migration would mainly require updating intercepted API names.

Core terms
Morphable kernelA kernel whose occupied SM count can be changed while it runs, via a software micro-scheduler on each SM, with no relaunch.
MorphXThe paper's prototype: compile-time kernel transformation + in-place profiling + a scheduler that solves for SM splits.
Micro-schedulerA per-SM, per-kernel loop that fetches thread blocks from a shared work-pool index, checking the current SM range before each fetch.
Reclaim queueA dedicated, high-priority internal stream used to relaunch a kernel instance sharing the original's progress counters, avoiding head-of-line blocking on regrowth.
Micro-interfacesFour device-resident integers (fetched, finished, minSM, maxSM) forming the host–device control/monitoring channel.
Normalized compute intensity (Ic)A Roofline-derived threshold: the SM fraction at which a kernel's compute ceiling meets its bandwidth ceiling. Ic<1 ⇒ memory-bound; Ic>1 ⇒ compute-bound.
In-place profilingMeasuring per-wave latency through the micro-interfaces while sweeping SM counts, to fit the compute-intensity model without CUPTI or binary instrumentation.
Kernel switchingFalling back to the original, untransformed kernel for short kernels where the morphing overhead isn't worth paying.
Supporting terms
WaveOne round of concurrently-executing thread blocks on a kernel's currently-assigned SMs.
GDRCopyNVIDIA library letting the CPU read/write GPU device memory directly, without using compute units — how the host reads/writes the micro-interfaces cheaply.
Roofline modelClassical performance model capping a kernel's throughput by whichever of compute or memory bandwidth is exhausted first, based on operational intensity.
HoL (head-of-line) blockingA later, ready kernel stuck waiting behind an earlier, stalled one in the same stream — what the reclaim queue avoids.
Green Context / MPS / MIGNVIDIA driver features for statically pinning SMs to a context or process before launch — the "kernel-wise static" baseline category.
Prefill / decodeLLM serving's two phases: prefill (processing the prompt, typically compute-heavy) and decode (generating tokens one at a time, typically memory-bandwidth-heavy at low batch size).
P99 / TPOT99th-percentile tail latency, and time-per-output-token — the paper's LLM-serving latency metrics.
