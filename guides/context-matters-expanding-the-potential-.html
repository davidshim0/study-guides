eBPF'26 Workshop · A Field Guide

Giving I/O requests a memory of why, not just what

Two threads write to the same file. By the time their data reaches disk, the kernel has merged, batched, and reordered it until nobody — not even eBPF — can say whose intent survives. This is the plain-English story of a proposal to give eBPF a way to carry application context all the way down the I/O stack.

📄 "Context Matters: Expanding the Potential of eBPF" · Machado et al. 🎓 Position/vision paper — no prototype shipped yet ⏱ ~15 min read
🏷️

Attach a CONTEXT TAG to a request at its origin, and carry it through every kernel layer and async boundary — instead of guessing it back later from size and timing.
Right now, the kernel only remembers "what" happened to a block. It forgets "why."

Before you begin

Quick glossary, then ten ideas the paper assumes you know

First the acronyms, so nothing below is opaque. Then the primers — collapsed, tap any to open. Read in order the first time, or jump to whatever looks unfamiliar.

Quick glossary

eBPFExtended Berkeley Packet Filter — sandboxed, verifier-checked programs the kernel JIT-compiles and runs at hook points, without writing a custom kernel module.
VFSVirtual File System — the kernel layer that presents a uniform interface over different filesystems (ext4, xfs, …).
BIOBlock I/O — the layer where reads/writes become block-layer requests sent to the storage device (often aggregating several writes into one).
kworkerA generic kernel worker thread that runs deferred work — notably flushing dirty page-cache pages to disk — detached from whichever thread originally wrote them.
WALWrite-Ahead Log — a database's sequential commit log (e.g. Postgres), an example of a latency-critical write stream worth distinguishing from housekeeping I/O.
COWCopy-on-Write — a filesystem technique where a "write" actually allocates a new block instead of overwriting in place, multiplying one logical write into several physical ones.
cgroupControl group — a Linux mechanism for grouping processes to apply resource limits/priorities (e.g. IOCost) at task-group granularity.
kfuncA kernel function explicitly exposed for eBPF programs to call, extending what BPF bytecode can do beyond its built-in helpers.
sched_extA recent mainline Linux subsystem letting eBPF programs implement entire CPU schedulers — proof that "modify the kernel to support eBPF natively" is a viable, shipped path.
QoSQuality of Service — differentiated treatment (priority, bandwidth) for different request classes.

1What eBPF actually is▾

eBPF lets you load small, sandboxed programs into the kernel at runtime, attached to specific hook points (syscall entry, network packet arrival, scheduler decisions, …). A verifier statically checks the program can't crash or escape its sandbox before it's JIT-compiled to native code.

Originally for observation (tracing, packet filtering), eBPF increasingly acts — shaping CPU scheduling, storage, and memory management directly, not just watching them.

Now you're ready: this paper is about extending what eBPF can carry with it as it acts along the storage path — specifically, application-level meaning.
2The Linux I/O stack, top to bottom▾

A write from an application descends through several distinct kernel layers: the syscall boundary, the VFS (generic file interface), the filesystem (here ext4), and finally the block I/O (BIO) layer, which issues block-layer requests to the device — often aggregating several smaller writes into one larger request.

eBPF can attach a trace point at each of these layers independently — but each layer today sees the request in isolation, with no memory of what happened one layer up.

Now you're ready: "context propagation" means carrying one tag through all four of these layers, not re-deriving it at each one.
3The page cache and asynchronous writeback▾

A normal buffered write doesn't go to disk immediately — it lands in the page cache as a "dirty" page, and the kernel flushes dirty pages to disk later, in the background, via kworker threads.

This is good for performance (batching, merging) but it means the thread that issued the write is long gone by the time the actual disk I/O happens — a different thread (a kworker) does the real work, with no record of who asked for it.

Now you're ready: this is the paper's central obstacle. Anything keyed to "the issuing thread" breaks the moment writeback happens asynchronously.
4eBPF maps and task storage▾

eBPF maps are key-value stores eBPF programs use to exchange data with user space or across hook points. Task storage maps let you attach metadata to a specific kernel task (thread), read back later from another eBPF program.

This works fine as long as the same task is still involved. It breaks across the writeback boundary (a kworker, not the original task, issues the real I/O) and can't distinguish two different application-level requests handled by the same thread.

Now you're ready: maps are the paper's starting point, and its first argument is precisely that they "are not enough" on their own.
5cgroups and I/O priority classes▾

Linux already lets you attach some context to I/O: a process's cgroup membership, or its I/O priority class (e.g. via IOCost). Both are genuine, existing forms of "context" the kernel carries.

But both operate at coarse granularity — per task or per cgroup, not per individual request — and offer a limited vocabulary (a handful of priority tiers), not arbitrary application-level meaning like "this is a foreground write for tenant X's checkout transaction."

Now you're ready: the paper isn't proposing something from nothing — it's arguing the existing mechanisms are too coarse and too narrow, and proposing finer, richer, per-request tags.
6Why size/timing correlation is tempting — and fragile▾

Without a native tag, you might try to reconstruct context after the fact: "ten consecutive 4 KiB writes probably produced this one 40 KiB block request." Sizes and timing can suggest which syscalls fed which block request.

But this is a guess, not a guarantee — multiple unrelated requests of the exact same size can appear around the same time from unrelated kworker threads, and there's no way to tell them apart from size and timing alone.

Now you're ready: the paper's motivating experiment is built specifically to expose this failure, using an unrelated 40 KiB request from a different kworker as the counter-example.
7Journaling and copy-on-write: one write, many writes▾

A single application-level write doesn't always become a single kernel-level write. Journaling filesystems may write the data and a journal/metadata record; copy-on-write filesystems allocate new blocks rather than overwriting.

So the mapping from "one syscall" to "kernel writes" can be one-to-many, not one-to-one — any context tag has to survive being split across several physical writes, not just carried along a single path.

Now you're ready: the paper names this "semantic ambiguity" as one of three cross-cutting challenges any design must handle.
8Distributed tracing — the userspace precedent▾

Systems like Google's Dapper, Jaeger, and Zipkin solve an analogous problem across networked services: a single user request is tagged with a trace ID at its entry point, and that ID is propagated across every service boundary it crosses, so you can reconstruct the whole request's path afterward.

The paper's proposal is the same idea, one layer down — propagating a tag not across network service boundaries, but across kernel I/O layers and asynchronous boundaries like page-cache writeback.

Now you're ready: if distributed tracing already solved this for service meshes, the open question is what's different about doing it inside the kernel.
9Why "modify the kernel for eBPF" isn't crazy: sched_ext▾

sched_ext is a real precedent: Linux's core scheduler subsystem was modified specifically so eBPF programs could implement entire custom CPU schedulers, and that work is now part of mainline Linux.

This matters because one of the paper's two proposed directions is exactly this pattern — extend the kernel's core data structures to natively carry a context tag, sacrificing some portability for richer semantics.

Now you're ready: when the paper proposes "modifying eBPF and the kernel" as one design direction, it's pointing at a path that has already succeeded once, for a different subsystem.
10Why storage optimizations usually live in user space today▾

Databases and key-value stores already do exactly this kind of context-aware optimization themselves — e.g. distinguishing latency-critical foreground writes from background compaction/housekeeping (as in LSM-tree stores), or tuning their own write-ahead log flushing.

They do it in user space because the kernel gives them no way to express "this write matters more" below the syscall boundary. That forces every application to reinvent similar logic, non-portably, rather than the kernel offering it generically.

Now you're ready: the payoff the paper is chasing is moving these already-proven application-level optimizations into the kernel, where they'd work for any application, not just the one that implemented them.
The whole story in one place

Context propagation in a nutshell

The problem, the motivating experiment that exposes it, and the proposal that follows.

eBPF can trace an I/O request across the syscall, VFS, ext4, and BIO layers with thread-level context. But once writes land in the page cache, they may be merged and later flushed by kworker threads unrelated to the issuing thread — and a single thread may itself be serving several logically distinct requests (different clients, different transactions) that the kernel can't tell apart. Existing mechanisms (task storage maps, cgroups, I/O priority classes) are either tied to a task that may no longer be the one doing the real work, or too coarse-grained and too narrow in vocabulary to express application-level meaning.

The paper's motivating experiment makes this concrete: two threads each issue five sequential 4 KiB writes to the same file (P1), sleep long enough for the kernel to flush dirty pages (P2), then each issue one final write before one thread calls fsync (P3). Trying to infer which BIO request came from which thread using size alone is unreliable — an unrelated 40 KiB request from a different kworker (kworker 166) is indistinguishable by size from the application's own merged 40 KiB request. Most of the trace — syscall, VFS, and ext4 — is visible to plain eBPF; write buffers are hashed at those layers and matched against the BIO segment's contents, which eBPF cannot read directly, so only that last step needs a custom kernel module. That match reveals the true picture: writes from both threads end up merged into a single final block request, attributed in the trace to only one of them.

The proposal: extend eBPF so a context tag — a request identifier, priority class, or arbitrary application-defined label — can be attached at the point a request originates, and read back by any eBPF program at any lower layer, surviving asynchronous boundaries like page-cache writeback, without hand-rolled per-layer reconstruction or custom kernel modules.

The payoff, if built: application-aware optimizations currently confined to user space — observability with true root-cause attribution, per-request I/O scheduling instead of per-task, and workload-specific tuning like prefetching for scans but not random access — become possible generically, inside the kernel, for any application.

🏷️ Key takeaways

  • eBPF can already trace thread-level context through syscall → VFS → ext4 → BIO — but loses it across async boundaries like page-cache writeback.
  • eBPF maps and task storage aren't enough: writeback decouples requests from the issuing thread, and one thread can serve several distinct requests.
  • cgroups / I/O priority are real but too coarse (task/group-level) and too narrow (a handful of classes, not arbitrary meaning).
  • Size/timing correlation after the fact is unreliable — demonstrated by an unrelated same-size kworker request in the paper's own experiment.
  • Proposal: a context tag attached at the origin, propagated through every layer and async boundary, readable anywhere — without custom kernel modules.
  • Two design directions: modify eBPF/the kernel natively (precedent: sched_ext) vs. a transparent middleware layer (more portable, harder correlation problem).
  • Three cross-cutting challenges: safety (verifier/kernel integrity), performance (critical I/O path), semantic ambiguity (journaling/COW split one write into many).
💡
Why this matters beyond storage (this guide's extrapolation, not the paper's claim): the same references this paper cites for eBPF acting on the kernel include memory-management examples — FetchBPF (customizable prefetch policies) and cache_ext (customizing the page cache) — which arguably face an analogous problem: a page-cache or page-fault decision has no visibility into why a page was touched. The paper itself only cites these works as evidence that eBPF is acting on kernels, not as instances of its context-propagation problem. For readers working on OS-managed memory tiering (DRAM/NVM placement, CXL), the missing ingredient may be similar — application-level intent that doesn't survive past the point a request enters the kernel — but that link is this guide's own framing, not the paper's.
Seven everyday pictures

How to think about context propagation

Each picture stands alone — read them in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · A tag that survives the trip

Baggage tags at a sorting hub

An airline tag survives being thrown onto a conveyor, sorted by machine, and reloaded onto a different plane — because the tag is physically attached to the bag, not remembered separately by the person who checked it in. A kernel write has no such tag today: once it's queued in the page cache and later flushed by a kworker, nothing travels with it to say which application, thread, or request it came from.

Where it breaks: a real bag tag is unique and unambiguous. A proposed context tag must also survive being split — one write can fan out into several physical writes (journaling, COW) — which no physical luggage tag has to handle.
Where it's lost · BIO merging

Two kitchen tickets, one delivery tray

Table 4's order and table 7's order are cooked separately, but if the kitchen is slow, a runner might stack both onto one tray for a single trip to the pass. The tray itself carries no memory of which items go where — a server has to already know. The BIO layer is that tray: ten small writes from two different threads can be merged into one 40 KiB block request, and nothing about the request itself says whose data is whose.

Where it breaks: a server usually still remembers verbally which plate is whose. The kernel has no equivalent memory at all — that's precisely the gap the paper is trying to close.
Why maps aren't enough · One task, many requests

One reporter, two bylines

Task-storage maps key context to a thread ID — like filing every article under a reporter's name. That works if one reporter writes one story at a time. But a single thread can be serving two unrelated application requests in interleaved fashion (two different clients' transactions), just like one reporter might be juggling two stories — filing everything under "the reporter" loses which paragraph belongs to which story.

Where it breaks: real bylines are usually one-to-one with an article; the analogy is honest about the failure mode (task-level granularity is too coarse) but a thread isn't literally forbidden from single-tasking — it's just that nothing stops it from interleaving, and current tools don't distinguish the case.
The proven precedent · Trace-ID propagation

A relay race baton

In distributed tracing (Dapper, Jaeger, Zipkin), a request gets a trace ID at the front door, and every service it touches hands that ID to the next one, like runners passing a baton — so afterward you can reconstruct the whole race, leg by leg, service by service. The paper proposes exactly this baton-passing, one level down, inside the kernel, between syscall/VFS/ext4/BIO instead of between microservices.

Where it breaks: a relay baton is handed off deliberately, runner to runner, by design. Kernel layers today hand off data without any equivalent deliberate act — the "baton" (context tag) doesn't exist yet to be passed; this analogy describes the goal, not the current reality.
Why the workaround fails · Size-based guessing

Guessing who walked through from a footprint size

If you only measure shoe-print size, you can't tell two different people with the same shoe size apart — you need something unique to each of them, like a name tag. The paper's own experiment hits exactly this: an unrelated 40 KiB block request from kworker 166 has the same size as the application's genuinely merged 40 KiB request, so size-based correlation alone can't tell them apart.

Where it breaks: footprints are at least tied to something physical (a specific shoe); block request sizes are tied to nothing unique at all — this analogy actually understates how fragile the workaround is.
The hidden multiplier · Journaling / COW

One shipment, repacked into two boxes

You ship one order, but the warehouse's process means it goes out as a data box and a separate paperwork box — one logical shipment, two physical parcels. Journaling filesystems do this to writes: one application write can become a data write and a journal/metadata write; copy-on-write filesystems allocate fresh blocks instead of overwriting, multiplying further.

Where it breaks: shipment splitting is usually predictable (always exactly two boxes); the paper is explicit that this "semantic ambiguity" is workload- and filesystem-dependent and not a fixed multiplier — any context-tag scheme must handle a variable one-to-many mapping, not a known constant.
Why coarse context isn't enough · cgroups / IO priority

Same job title, very different projects

A company org chart tells you someone's job title ("engineer") but not which specific project, client, or deadline they're working on right now. cgroups and I/O priority classes are the job titles of the kernel: real, useful, but coarse — they say which group a task belongs to, not which individual request, from which tenant, with which urgency, is in flight.

Where it breaks: a job title is usually stable for months; an I/O priority class can be reconfigured per workload — the coarseness is about granularity (group vs. request), not about being static, so don't stretch the analogy into "cgroups never change."
The full explanation

How it actually works

The motivating experiment, why today's tools fall short, the proposal's three requirements, and the two design directions the paper weighs against each other.

1 · The motivating experiment, precisely

Two application threads issue sequential 4 KiB writes to the same file across three phases. In P1, each thread issues five 4 KiB writes concurrently. In P2, both threads sleep long enough that the kernel flushes dirty pages from the page cache. In P3, each thread issues one final write, and then one thread (labeled 21719 in the trace) calls fsync.

eBPF can trace thread-level context through syscall, VFS, ext4, and BIO. The trouble starts once writes are buffered: they may be merged and flushed asynchronously by kworker threads, and a naive attempt to correlate the resulting BIO request (block_rq_issue) with the writes that produced it — by matching sizes (ten 4 KiB writes ≈ one 40 KiB BIO request) — is unreliable, because unrelated 40 KiB BIO requests can appear from other kworkers at the same time.

2 · Why existing eBPF mechanisms fall short

MechanismGranularitySurvives async boundary?Vocabulary
Task storage mapper taskNo — kworker ≠ issuing taskarbitrary (if it survives)
cgroup membershipper task groupPartially — group persistsnone (just grouping)
I/O priority classper task/groupPartially — attached to taska handful of tiers

🌱
None of the top three rows are wrong tools — they solve different problems. The gap is specifically: per-request, async-boundary-surviving, arbitrary-vocabulary context. Nothing existing hits all three at once.

3 · The proposal's three requirements

  1. Attach context at a request's origin (e.g. at the syscall boundary), as a tag or set of tags — a request identifier, a priority class, or an arbitrary application-defined label.
  2. Propagate it through VFS, the filesystem, and the BIO layer, surviving asynchronous boundaries such as page-cache writeback and kworker dispatch — the part that breaks today.
  3. Extract it at any layer, so an eBPF program running at the BIO layer, for instance, can read back the same tag an eBPF program attached at the syscall layer, without manual per-layer bookkeeping.

4 · Three challenges that apply to either direction

⚠
Safety. Any new eBPF capability must still pass the verifier and preserve kernel integrity — a context-carrying mechanism is new surface area the verifier has to reason about.
⚠
Performance overhead. Attaching, propagating, and reading a tag happens on or near the I/O critical path — any overhead here competes directly against the point of using eBPF (acting inline, cheaply).
⚠
Semantic ambiguity. A single user-space write may become multiple kernel-level writes (journaling, copy-on-write) — a scheme that assumes one-tag-per-one-write will misattribute the extra writes.

5 · What this would unlock

  • Observability and data provenance: end-to-end root-cause analysis of I/O anomalies, pinpointing exactly which kernel layer(s) and application request(s) were responsible — something today's distributed tracing tools leave opaque below the kernel boundary, and today's kernel-only tracing tools can only partially correlate offline or with no application-level semantics.
  • Application-aware I/O scheduling: today's in-kernel schedulers reason about PID and request size; per-request context tags would let them make priority/fairness decisions per individual request or tenant, reducing interference.
  • Specialized I/O optimizations: the right tuning (e.g. read-ahead/prefetching) often depends on the workflow — scans benefit from prefetching, random access doesn't — and context tags would let the kernel apply per-request tuning instead of one-size-fits-all heuristics.
Follow the numbers, step by step

Worked examples

Four passes through the paper's own motivating experiment and its consequences — the merge arithmetic, the failure of size-matching, the fsync moment, and the journaling multiplier.

① The merge arithmetic behind "40 KiB"

In P1, thread A issues five sequential 4 KiB writes, and thread B issues five more, to the same file, concurrently.

  1. Thread A alone: 5 writes × 4 KiB = 20 KiB.
  2. Thread B alone: 5 writes × 4 KiB = 20 KiB.
  3. Combined, both threads: 10 writes × 4 KiB = 40 KiB total dirtied in the page cache.
  4. The page cache may merge these ten small dirty regions into a single block request when flushed — exactly the paper's own example of "ten consecutive 4 KiB writes may produce a single 40 KiB BIO request."
  5. The arithmetic checks out, but notice what it can't tell you: whether that 40 KiB came from one thread doing 10 writes, or two threads doing 5 each. The size alone is silent on origin.
🏷️
Insight: the size math that makes correlation tempting is the same math that makes it insufficient — a correct total byte count is consistent with many different underlying request patterns.

② Why the 40 KiB match still fails

At the BIO layer, the trace shows a 40 KiB block_rq_issue event around the time P1's writes should have flushed. Is it safe to attribute it to threads A and B?

  1. Candidate 1: the genuine merged write from threads A + B — 40 KiB, matches.
  2. Candidate 2: an unrelated request from kworker 166, flushing something else entirely — also 40 KiB, also matches on size.
  3. Nothing in the eBPF-visible fields of block_rq_issue (size, device, sector, timing) distinguishes candidate 1 from candidate 2.
  4. Only the paper's custom kernel module — hashing the actual buffer contents at syscall/VFS/ext4 and matching those hashes at the BIO layer — can tell them apart, because it looks at data eBPF cannot directly access in block_rq_issue.
  5. Conclusion: without a native tag, correct attribution required stepping outside eBPF entirely. That's the paper's central piece of evidence that eBPF, as it stands, needs a new capability here.
💡
This is the paper's strongest empirical claim in an otherwise conceptual/position paper: a concrete false-positive (kworker 166) that size-matching cannot rule out.

③ The P3 fsync moment — attribution breaks down completely

In P3, each thread issues one more write, then thread B (21719) calls fsync, forcing a flush. The resulting final block_rq_issue is attributed in the trace to thread 21719 (thread B) alone.

  1. By trace alone: the event's PID field says "thread B (21719)" — as far as plain eBPF is concerned, this is entirely thread B's write.
  2. By content hash (the custom module): the block actually contains data written earlier by thread A too — its dirty pages were still pending and got swept up in B's forced flush.
  3. So the true picture is: one BIO request, contributed to by two threads, credited by the kernel's own bookkeeping to only one of them.
  4. A single-ID tag might not fully fix this — the paper's own wording allows for "a tag, or set of tags," which fits cases like this one where a request could need multiple origin tags, though the paper doesn't explicitly derive that wording from this example.
🏷️
Insight: this is the sharpest illustration in the paper that "who issued this I/O" is not always a single answer — any context-tag design has to represent a set, not just a scalar ID.

④ The journaling/COW multiplier — why one tag isn't automatically one write

Take one application-level write to a journaling filesystem. How many kernel-level writes might actually happen, and what does that mean for a context tag?

  1. 1 syscall write → at minimum, the data block itself needs writing: 1 physical write.
  2. Journaling filesystems may also record a journal/metadata entry for crash consistency, turning that one write into multiple physical writes — the paper gives this as an example, not a fixed rule.
  3. Copy-on-write filesystems can similarly allocate a fresh block rather than overwriting in place — potentially touching metadata blocks (e.g. indirect pointers) as well: another possible multiplier, filesystem- and workload-dependent.
  4. Net effect: the paper's point is narrower than "every write is multiplied" — it's that one user write may translate into multiple kernel write requests, so a context tag attached once at the syscall must be able to reach every resulting physical write when this happens, not just the first one the kernel issues.
💡
This is exactly the "semantic ambiguity" challenge named in §2 — the paper frames it as a possibility ("may translate into multiple kernel write requests"), using journaling and COW as examples, not as a universal rule for every write.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the common misconception it's checking for.

Problem 1 · easy
An eBPF program attaches metadata to the issuing thread using a task storage map at write time. Why might this metadata be unreadable by the time the data actually reaches disk?
Show answer
Because a buffered write doesn't go to disk immediately — it's marked dirty in the page cache and flushed later by a kworker thread, not by the original issuing thread. Task storage is keyed to a task; once the real work is done by a different task (the kworker), that key no longer resolves to anything useful.Misconception: that "the thread that called write()" is still involved by the time the block actually hits the device. Buffered I/O explicitly decouples these in time and in which task performs the work.
Problem 2 · medium
Thread A issues 7 sequential 4 KiB writes and thread B issues 3 sequential 4 KiB writes to the same file, all buffered together. A trace shows one 40 KiB block_rq_issue event. Using size alone, can you tell how the 40 KiB splits between A and B?
Show answer
No. (7+3) × 4 KiB = 40 KiB is consistent with A:B = 7:3, but it's equally consistent with 5:5, 10:0, or any other split totaling ten 4 KiB writes — and also consistent with an entirely unrelated 40 KiB request from a different source, as the paper's kworker 166 example shows. Size is a necessary but not sufficient signal.Misconception: that matching totals implies matching origin. A correct sum is compatible with infinitely many underlying request patterns.
Problem 3 · medium
Why don't cgroups or I/O priority classes already solve this problem, given that they are genuine, existing forms of kernel-level context?
Show answer
They operate at the wrong granularity and with the wrong vocabulary for this problem. cgroups and I/O priority classes are attached per task or per task-group, not per individual request — so they can't distinguish two different transactions handled by the same thread. And their vocabulary is a small fixed set of tiers/classes, not arbitrary application-defined meaning (like a specific request ID or a free-form tag).Misconception: that any existing "context" mechanism is interchangeable with what's needed. The paper's argument isn't "there is no context today" — it's "the context that exists is too coarse and too narrow."
Problem 4 · hard
Construct a scenario, different from the paper's own kworker-166 example, where relying on request timing (instead of size) to correlate a BIO request with its originating writes would also fail.
Show answer
Any scenario with concurrent, unrelated background I/O defeats timing-based correlation just as size does: e.g. a separate process's periodic log rotation, or another filesystem's own journal commit, happening to fire in the same short window as your application's flush. Timing narrows the search but doesn't uniquely identify — exactly the same structural weakness as size, because neither is actually tied to the request, only correlated with it under normal conditions.Misconception: that a "smarter" heuristic (timing instead of size, or both combined) fixes the fundamental problem. Any purely inferential signal remains probabilistic; only a carried, native tag is guaranteed.
Problem 5 · medium
Compare Direction A (modify eBPF and the kernel) and Direction B (transparent middleware) on exactly one axis: which one has to solve the "how do I know these two layer events are the same request" problem from scratch, and why?
Show answer
Direction B does. Because Direction A adds native carriers — new kernel struct fields and kfuncs that travel with the request by construction — the "same request" question is answered by the carrier itself. Direction B deliberately avoids touching core kernel structures, so it must reconstruct cross-layer association using only identifiers that already exist (PIDs, inode numbers) — which the paper explicitly says are insufficient, making this Direction B's harder open problem.Misconception: that avoiding kernel modification is a strictly easier path. It trades one hard problem (kernel modification risk/maintenance) for another (reliable request identification without a native carrier).
Problem 6 · hard
A context tag is attached once, at the syscall boundary, to a single write() call on a journaling filesystem. Explain concretely why a design that assumes "one tag maps to exactly one physical write" will misattribute part of the resulting I/O.
Show answer
Journaling filesystems commonly turn one logical write into at least two physical writes: the data block itself, and a journal/metadata record for crash consistency. If the tag is only propagated to "the" resulting write (singular), the journal write — which is just as much a consequence of this same application request — ends up untagged, or wrongly treated as a separate, unrelated kernel-internal write. Any correct scheme must let one tag fan out to every physical write the original request causes, however many there turn out to be.Misconception: that context propagation is a simple 1:1 relay. The paper explicitly calls this out as "semantic ambiguity" — a structural challenge, not an edge case to patch over later.
Problem 7 · easy
What does sched_ext's existence in mainline Linux tell us about Direction A (modifying eBPF and the kernel natively), and what does it NOT tell us?
Show answer
It tells us that adding native kernel support specifically so eBPF programs can do more (there, implement whole schedulers) is a path the kernel community has accepted before, so it's not an unprecedented ask. It does NOT tell us that context propagation specifically will be accepted, or that it's equally feasible — sched_ext solved a different problem (scheduling) with its own design and review history; it's evidence of viability-in-principle, not a ready-made template.Misconception: that a precedent in one subsystem guarantees success in another. Precedents establish plausibility, not a free pass.
Problem 8 · medium
Why does "application-aware I/O scheduling" require per-request context, when today's schedulers already use PID-based priority successfully in many systems?
Show answer
PID-based priority works when one thread's I/O is uniformly one priority class — but a single thread (e.g. a database connection handler) can issue both latency-critical foreground writes and background housekeeping writes (like SILK's distinction for LSM-tree stores). A scheduler keyed only to PID must treat all of that thread's I/O identically, even though the application itself knows some of it matters far more right now. Per-request tags let the scheduler see the distinction the application already has.Misconception: that per-task priority is "basically" per-request priority as long as most threads are single-purpose. Real data-intensive applications routinely interleave multiple purposes per thread.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1Is this paper presenting a working implementation?▾
No. It's a 3-page position/vision paper for the eBPF'26 workshop. It presents a problem (context is lost across the kernel I/O stack), a motivating experiment using a custom kernel module to expose the problem, and two possible design directions — without committing to or shipping either.
Q2What exactly is wrong with eBPF maps?▾
Not that they're useless — they're the mechanism the paper builds on. The problem is specifically that task-keyed maps assume the issuing task is still involved when the real I/O happens, which buffered writeback (via kworker threads) breaks, and that one task can serve multiple distinguishable requests that task-level keying can't separate.
Q3Why can't you just track the writing thread's PID all the way to the block layer?▾
Because the thread that issued a buffered write is often not the thread that eventually flushes it — that's a kworker thread, dispatched asynchronously, with no built-in record of which application thread's data it's flushing.
Q4What precisely is the "async boundary" the paper keeps referring to?▾
The point where a request stops being handled synchronously by the issuing thread and becomes deferred work handled later by a different kernel thread — concretely, when a buffered write is marked dirty in the page cache and later flushed by a kworker rather than the original caller.
Q5Why did the authors need a custom kernel module for their experiment if the paper is about eBPF?▾
Precisely to demonstrate the gap: they wanted ground truth (which writes' content ended up in which block request) to check whether plain eBPF tracing would have gotten it right. Since eBPF cannot directly inspect BIO segment contents, they used a kernel module only to establish that ground truth for the experiment — not as part of their proposed solution.
Q6What are the two proposed design directions, in one line each?▾
(A) Modify eBPF and core kernel structures to natively carry context tags across layers and async boundaries — richer, but less portable. (B) Build a transparent middleware service with a stable API that eBPF programs call into, without changing core kernel data structures — more portable, but must solve request identification without a native carrier.
Q7What does sched_ext have to do with any of this?▾
It's cited as precedent that Direction A (kernel modification specifically to empower eBPF) is not purely hypothetical — sched_ext already extended the kernel's scheduler subsystem for eBPF-based custom schedulers, and that work is now part of mainline Linux.
Q8What is "semantic ambiguity" and why is journaling the classic example?▾
It's the challenge that one user-space write doesn't always correspond to one kernel-level write. Journaling filesystems may issue a data write plus a separate journal/metadata write for the same logical operation; copy-on-write filesystems allocate new blocks rather than overwriting. Any context tag must fan out correctly across this one-to-many relationship.
Q9Which concrete use-cases would context propagation unlock?▾
Three are named: end-to-end observability and data provenance (root-causing I/O anomalies across kernel layers and application requests), application-aware I/O scheduling (per-request rather than per-task priority/fairness decisions), and specialized I/O optimizations (e.g. tuning prefetching per workload pattern rather than uniformly).
Q10How is this different from existing distributed tracing tools like Jaeger or Zipkin?▾
Those propagate trace context across network/service boundaries in user space, but leave the kernel I/O path opaque once a request enters it. Systems that do look inside the kernel either correlate user- and kernel-level events offline after the fact, or propagate purely kernel-internal IDs with no application-level meaning attached. The paper's gap is specifically application-level context propagated live, inside the kernel, across async boundaries.
Q11Does the paper propose a specific format for the context tag?▾
No — it deliberately stays general: "a tag, or set of tags (e.g., request identifier, priority class, or arbitrary tag)." The set framing fits cases like the fsync example, where a single BIO request could carry more than one origin's data — though the paper doesn't explicitly draw that connection itself.
Q12Why should someone working on OS memory management (not storage) care about this paper?▾
The same references this paper draws on for eBPF "acting" on the kernel include memory-management examples (FetchBPF for prefetch policy, cache_ext for page-cache customization). This guide's own extrapolation — not a claim the paper makes — is that those systems face an analogous root problem: a kernel-level decision (what to prefetch, what to evict, where to place a page) has no visibility into the application-level intent that produced the access.

Glossary & further reading

Every term in one place, then a path to go deeper.

Core terms
Context propagationThe paper's proposal: carrying an application-level tag with a request as it descends the kernel I/O stack, including across asynchronous boundaries.
Context tagA request identifier, priority class, or arbitrary application-defined label attached at a request's origin and readable at any lower layer.
Async(hronous) boundaryThe point where a request stops being handled by the issuing thread and becomes deferred work for another kernel thread — chiefly, page-cache writeback via kworkers.
Semantic ambiguityThe challenge that one application-level write can become multiple physical kernel writes (journaling, copy-on-write), so a tag must fan out correctly.
Direction A (native)Extend eBPF and core kernel data structures (new fields, kfuncs, wrapped kworker dispatch) to carry context tags — richer semantics, less portable. Precedent: sched_ext.
Direction B (middleware)A transparent middleware service behind a stable API that eBPF programs call to attach/retrieve context, without modifying core kernel structures — more portable, harder request-identification problem.
Supporting terms
Page cache / writebackBuffered writes are held as "dirty" pages in memory and flushed to disk later by kworker threads, decoupling issuance from execution.
kworkerA generic kernel worker thread performing deferred work, notably dirty-page flushing, detached from the originating application thread.
Task storage mapAn eBPF map keyed to a kernel task, used to attach and later read back per-thread metadata — breaks across async boundaries.
cgroup / IOCostLinux mechanisms for grouping processes and assigning I/O cost-based weights/QoS at the group level — coarser than per-request.
sched_extA mainlined Linux subsystem letting eBPF programs implement CPU schedulers — cited as precedent for native kernel modification to empower eBPF.
BIO / block_rq_issueThe block I/O layer and the tracepoint marking a block request's dispatch to the device — where the paper's correlation experiment focuses.
Content-hash correlationThe paper's experimental technique: hashing write buffer contents at the syscall/VFS/ext4 layers (traceable with eBPF) and matching those hashes against BIO segment contents — which requires a custom kernel module, since eBPF can't read BIO segment contents directly — to get ground truth eBPF alone couldn't provide.
Distributed tracing (Dapper/Jaeger/Zipkin)Userspace systems that propagate a trace ID across service/network boundaries — the precedent pattern this paper proposes replicating inside the kernel.
