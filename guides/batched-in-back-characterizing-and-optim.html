SOSP 2026 · A Field Guide

The GPU work that isn't in a hurry — until you serve it like it is

Bulk translation, log summarization, millions of queued requests — offline LLM jobs don't need a fast first token. Feed them the same latency-obsessed scheduler built for chatbots anyway, and you throw away up to 45% of the throughput they could have had. This is the production story of ACDC, deployed across tens of thousands of GPUs at Alibaba.

📄 "Batched in Back" · Yang, Li, Qian et al. · SOSP '26 🎓 LLM-serving concepts assumed — the primers cover them ⏱ ~30 min read

Serve each request by the deadline it actually has — task completion time for offline, per-token latency for online — not by whichever policy was easiest to reuse.

Before you begin

Quick glossary, then the concepts

This paper lives in LLM-serving systems, not memory tiering — so the acronyms and mechanisms below are the vocabulary you're missing, not the concepts you already have (caches, LRU, locality). Skim the glossary, then open whichever primer looks unfamiliar.

🔤 Quick glossary — acronyms used throughout

TTFTTime To First Token — latency until the first output token arrives. The metric online SLOs guard most tightly.
TPOTTime Per Output Token — steady-state per-token decode latency. The other online SLO.
SLOService Level Objective — a latency target (e.g. TTFT < 10 s) the provider commits to meet.
MaaSModel-as-a-Service — a cloud provider (here, Alibaba Model Studio) serving foundation models via API.
KV cachePer-request key/value tensors cached in GPU memory so each new token doesn't re-process the whole prompt.
TP / DP / EPTensor / Data / Expert Parallelism — three ways to split a model's compute across GPUs.
MoEMixture-of-Experts — a model where only a subset ("activated parameters") of total weights runs per token.
PD disaggregationRunning the prefill and decode phases of inference on physically separate GPU instances.
FCFSFirst-Come-First-Served — the simplest queue discipline; ACDC uses it only across tasks, not within one.
M/D/1 queueQueueing-theory model: Markovian (random) arrivals, Deterministic service time, 1 server — used to model prefill.

1Prefill vs. decode — two phases, two bottlenecks▾

Serving an LLM request has two phases. Prefill processes the whole input prompt in one parallel pass — it's compute-bound (lots of matrix math, one shot). Decode then generates output tokens one at a time, each requiring a full pass over the model weights and the growing KV cache — it's memory-bandwidth-bound (loading, not computing, dominates).

This split matters because the two phases want different hardware configurations, and — critically for this paper — they fail differently: prefill's batch size is usually kept near 1 (to return the first token fast), which is exactly what creates idle "bubbles."

Now you're ready: ACDC's resource orchestration (§4.1) picks a TP/DP/EP configuration per task based on its input/output length distribution (not separately per phase), and its hybrid-serving mechanism (§5) specifically harvests idle time inside the prefill phase.
2TTFT, TPOT, and why they fight throughput▾

To keep TTFT low, a system must avoid queueing requests behind each other in prefill — so it processes them nearly one at a time, leaving the GPU under-packed. To keep TPOT low, decode batches must stay small enough that no single step takes too long. Both constraints directly oppose throughput, which wants big batches running flat-out regardless of any single request's wait.

Removing these constraints (i.e., not caring about any individual request's latency) is precisely what offline serving can do — and the paper measures the loss from keeping them at 45.1% of potential throughput for one config (roughly an 82% throughput uplift once removed).

Now you're ready: "throughput-oriented" isn't a vague goal — it's the mathematical consequence of deleting the TTFT/TPOT terms from the optimization.
3Continuous batching and why batch size is everything▾

Modern LLM engines (vLLM, SGLang) run continuous batching: many requests' decode steps are packed into the same GPU forward pass, streaming requests in and out of the batch as they finish. Bigger batches amortize the cost of loading model weights across more useful work — which is why decode throughput scales with batch size, up to memory limits.

The limiting resource for batch size is usually not compute but KV cache capacity — every concurrent request holds its own growing KV tensors in GPU memory.

Now you're ready: this is why §4.1's parallelism choice (more TP → more spare memory → bigger batch) directly targets decode throughput, and why §6's "memory capacity as a first-class constraint" lesson matters so much.
4Tensor / Data / Expert Parallelism, briefly▾

Tensor Parallelism (TP) splits each layer's weight matrices across GPUs — every GPU does a slice of every request's compute, communicating after each layer. Data Parallelism (DP) instead replicates the whole model and splits requests across replicas — no per-layer communication, but no memory pooling either. Expert Parallelism (EP) is specific to MoE models: different "expert" sub-networks live on different GPUs, and tokens get routed to whichever GPU holds the expert they need.

These three combine (e.g. "T4-D2-E8" = TP=4, DP=2, EP=8), and which combination is fastest depends entirely on the workload's input/output length ratio — there is no universally-best setting.

Now you're ready: ACDC's whole resource-orchestration axis (§4.1) is: pick the TP-DP-EP combination per task, and re-pick it when the task's length distribution shifts mid-flight.
5Prefix caching (you already know this — the twist is task structure)▾

If two requests share a common prompt prefix (e.g. the same instruction template), the KV cache for that prefix can be computed once and reused — skip re-running prefill on tokens you've already processed. This is the LLM-serving analog of any content-addressed cache: same key, same result, don't recompute.

The twist here is where the sharing lives: essentially zero prefix overlap across different offline tasks, but >80% median overlap within one task (same instruction, different documents). That locality structure is exactly what task-scoped scheduling can exploit and a generic LRU cache cannot.

Now you're ready: §4.2's whole design — build one prefix tree per task, schedule depth-first, discard it at completion — follows directly from "sharing is intra-task, not global."
6Speculative decoding, in one paragraph▾

A small, cheap "draft" model guesses the next γ tokens; the real (target) model then verifies all γ guesses in a single forward pass instead of γ separate ones. If most guesses are accepted, you've generated several tokens for roughly the cost of one target-model invocation — a big win when decode is memory-bandwidth-bound (long contexts, large batches, one invocation loading the same weights regardless of γ).

But invoking the draft model and verifying multiple tokens has fixed overhead. If decode is already compute-bound (short contexts, large batches under high TP), that overhead is pure loss — speculative decoding can make things slower.

Now you're ready: §4.3's central finding — that the best γ, and even whether to speculate at all, depends on input length and batch size — is this exact compute-bound-vs-memory-bound tension made concrete.
7Prefill-decode (PD) disaggregation and "bubbles"▾

Running prefill and decode on the same GPU creates interference: a long decode batch delays a newly-arrived prompt's prefill, hurting TTFT. PD disaggregation fixes this by dedicating separate instances to each phase, connected by fast KV-cache transfer. It's now a standard production pattern (Splitwise, DistServe, Mooncake).

The cost: because prefill instances keep batch size near 1 for TTFT, and online request arrivals are bursty, a prefill GPU frequently has nothing to do for tens to hundreds of milliseconds between requests — a bubble. Bubbles are wasted compute that latency-sensitive online traffic structurally cannot fill (there's nothing else online to run), but that patient offline work could.

Now you're ready: §5's entire hybrid-serving contribution is quantifying these bubbles and slotting offline chunks into them without breaking online TTFT.
8M/D/1 queueing, just enough of it▾

An M/D/1 queue has random (Markovian) arrivals but a fixed, deterministic service time — a decent model for a prefill instance serving requests one at a time. The textbook Pollaczek–Khinchine result for this queue gives the expected wait E[W] = ρs / (2(1−ρ)) where ρ = λs is utilization (arrival rate × service time) and s is the service time. Total latency is E[T] = E[W] + s.

The key qualitative fact: as ρ → 1 (the server gets busy), E[W] blows up nonlinearly. So meeting a fixed TTFT bound forces ρ to stay well below 1 — which is a formal way of saying "bubbles are unavoidable if you want good tail latency."

Now you're ready: §5.1 solves this equation backward from real production numbers (s=756ms, TTFT=1.41s) to show ρ≈63%, i.e. ~37% of prefill capacity is structurally idle — you'll redo that algebra yourself in Worked Example 3.
The whole story in one place

ACDC in a nutshell

The mismatch, the three fixes, and the extra harvest hiding in online's own idle time.

Offline LLM tasks — bulk translation, log summarization, dataset labeling — now consume up to 30% of production GPU capacity at Alibaba, yet almost nobody had studied them systematically. The default move was to serve them with whatever engine already served online chat, just with slacker deadlines. The paper's core finding is that this default is quietly expensive: serving offline work under online SLOs forfeits 45.1% of the throughput it could otherwise achieve — an ~82% uplift once those constraints are removed — because latency and throughput are fundamentally at odds, and offline tasks pay latency's tax for no reason.

Offline tasks have two properties online requests don't: inherent determinism — the entire set of thousands of requests in a task is known at submission, before a single token is generated — and throughput orientation — users care about total completion time (minutes to days), not any individual request's TTFT. ACDC is built to exploit exactly these two properties, along three independent axes: resource orchestration (pick TP/DP/EP per task's length profile, +22.5%), cache management (reorder requests by shared prefix instead of leaving reuse to chance, +35.5% hit rate), and execution flow (tune speculative decoding's γ to the task instead of a fixed online default, +13.1%). Together these beat the strongest prior offline-scheduling baseline by at least 14.2%, and in production deliver up to 3.9× higher output cost-efficiency.

ACDC then goes further than isolated off-peak deployment. Under production PD-disaggregation, prefill instances run at low utilization to protect TTFT — the paper measures up to 38.3% of prefill capacity sitting idle as "bubbles," unusable by online traffic but perfectly usable by patient offline chunks. A hybrid scheduler estimates bubble-duration distributions from a 24-hour sliding window of historical observations and opportunistically inserts chunked offline prefill work into detected bubbles, lifting offline throughput by up to 90.0% over a naive baseline and 35.7% over BatchLLM+C, an enhanced baseline combining BatchLLM with bubble insertion (the actual prior hybrid-serving system, HyGen, is beaten by up to 5.6×) — with online TTFT tail latency degraded by under 0.7% at P999.

Reader's-eye framing (mine, not the paper's): the KV-cache reordering problem in §4.2 is structurally the same problem as promotion/demotion in tiered memory — deciding what stays "hot" (in fast GPU memory) versus what gets evicted, except ACDC gets to cheat by knowing the entire future access sequence in advance. That's the LLM-serving equivalent of running Belady's OPT instead of LRU, because the task boundary makes the future observable. The hybrid bubble-harvesting mechanism (§5) is the same idea one level up: opportunistically reclaiming idle capacity from a latency-critical tier (online prefill) for a throughput-tolerant consumer (offline), without violating the critical tier's SLO — the same shape as harvesting idle CXL-pooled memory bandwidth for background work.

🍯 Key takeaways

  • Offline ≠ "online with a longer deadline." Determinism (full task known upfront) and throughput orientation change what the optimal policy is.
  • Applying online scheduling to offline tasks forfeits ~45% of achievable throughput (§3.1) — a pure policy-mismatch cost, not a hardware limit.
  • Three orthogonal levers: task-aware TP/DP/EP (+22.5%), prefix-tree-ordered KV cache reuse (+35.5% hit rate), adaptive speculative decoding γ (+13.1%).
  • Combined, ACDC beats the best prior offline scheduler (BatchLLM) by ≥14.2%, and beats the pre-ACDC production baseline by up to 3.9× output cost-efficiency.
  • Even at online peak, PD-disaggregated prefill leaves up to 38.3% capacity idle as "bubbles" — harvestable without violating online SLOs.
  • Hybrid bubble-harvesting: +90.0% vs. naive baseline, +35.7% vs. BatchLLM+C (an enhanced constructed baseline, not a prior hybrid system), up to 5.6× vs. the actual prior hybrid-serving system HyGen, online TTFT P999 impact <0.7%.
Six everyday pictures

How to think about ACDC

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core distinction · Determinism

The full guest list vs. a walk-in line

A wedding caterer with the whole RSVP list in hand can plan every course, buy exactly the right quantities, and seat tables efficiently. A diner serving whoever walks in must staff for the busiest plausible minute and can't batch shopping trips. Offline tasks hand ACDC the full guest list — every request known at submission — so it can plan (parallelism, ordering) instead of reacting.

Where it breaks: the guest list can still surprise you mid-meal — output length isn't known until generation finishes, and multi-turn agent workloads reveal their "guests" one at a time (§6), eroding the very clairvoyance this analogy celebrates.
Cache management · Prefix-tree DFS scheduling

Running errands by neighborhood

If you run errands in the order they occurred to you, you criss-cross town. Group them by neighborhood first, and each stop stays "warm" — you're already parked there. ACDC builds a prefix tree over a task's requests and serves siblings (shared-prefix requests) back-to-back, so the KV cache blocks loaded for one request are still hot for the next, instead of decaying under FCFS while unrelated requests intervene.

Where it breaks: neighborhoods don't disappear after your last errand there, but a task's prefix tree does — it's built once at submission and discarded at completion, because sharing essentially never crosses task boundaries (§3.4).
Execution flow · Speculative decoding's sweet spot

Betting on autocomplete

Autocomplete guesses your next few words; you either accept them (fast) or type over them (no worse than typing alone) — but summoning and checking the suggestion still takes a beat. If you already type fast (short prompts, small batches, plenty of spare compute), that beat is pure overhead and slows you down. If you type slowly relative to how fast a reader could check your work (long contexts, memory-bound decode), betting on autocomplete is a clear win.

Where it breaks: autocomplete's payoff is roughly monotone in confidence; speculative decoding's isn't — the paper finds a genuine sweet-spot γ per task (peaks then falls) rather than "more guessing is always better, up to some point."
Bubble math · The single teller line

One bank teller, kept deliberately underworked

A single teller serving randomly-arriving customers cannot run near 100% busy without the line exploding — the M/D/1 queueing result. To guarantee a short wait, the branch keeps the teller idle a good fraction of the time on purpose. Those idle stretches ("bubbles") are the price of a latency guarantee, not a bug — and they're exactly what a production prefill instance measures at up to 38.3% idle.

Where it breaks: a bank can't reroute an idle teller to sort mail mid-shift without retraining; ACDC's whole hybrid-serving trick is that a GPU idle teller can be handed unrelated (offline) work in sub-second slices, because chunked prefill lets it drop that work instantly when a real customer (online request) shows up.
Hybrid serving · Backhaul freight

Filling the truck's empty return trip

A delivery truck drives back mostly empty after its scheduled run. A freight broker who knows the route and the empty capacity in advance can slot in backhaul cargo — as long as it can be dropped instantly if the truck gets recalled. ACDC's scheduler does this with offline prefill chunks: sized to fit inside a predicted bubble, dropped without cost if an online request preempts them, because prefill executes layer-by-layer and can stop at any layer boundary.

Where it breaks: a real backhaul broker guesses at demand; ACDC's scheduler actually solves a benefit-maximization formula per bubble (Eq. 4–5) using measured chunk-latency profiles and bubble-duration distributions — closer to a routing optimizer than a broker's hunch.
The memory lesson · Finish before you start

Too many half-washed loads

A shared laundromat with limited machines: starting five new loads at once feels efficient, but each holds a machine hostage until its cycle finishes — you end up with no free machine when someone urgently needs one. ACDC's early hybrid scheduler made exactly this mistake, greedily starting new offline request chunks (which run fast, since they have no accumulated KV state) while old ones sat half-finished, hogging GPU memory until preempted.

Where it breaks: laundry machines don't get evicted mid-cycle losing your progress; half-finished offline requests did — preemption discarded all prior compute. The fix (the max(k_r) penalty term, §5.2) isn't just "finish loads first," it's "don't even start a new one if finishing the old ones is at risk."
The full explanation

How it actually works

Section by section, following the paper's own three-axis structure plus the hybrid-serving extension.

1 · Why porting online (or classical batch) systems fails

vLLM, SGLang, and TensorRT-LLM are optimized around meeting TTFT/TPOT SLOs for online serving, leaving offline throughput headroom on the table. Naively reusing them for offline work leaves throughput on the table (the 45.1% experiment, §3.1). The obvious alternative — reuse classical big-data frameworks like MapReduce/Spark — fails for a different reason: their DAG-based pipeline parallelism (PP) assumes fixed, content-independent stage costs. LLM decode is neither: output length is unknown until generation finishes, and speculative decoding's acceptance rate is content-dependent, causing up to 3.69× throughput variation for the same nominal workload (§3.5, Fig. 9). Increasing PP degree in an LLM pipeline actually degrades throughput through added pipeline bubbles (Fig. 8) — the opposite of the classical-systems intuition.

2 · What the 1.5M-task measurement study actually found (§3.2–3.4)

Scale varies by over 20× across models with no consistent relationship between task count and request count (Model-C: 579K tasks / 9,136M requests; Model-D: 72K tasks / 432M requests). Task completion times span three orders of magnitude even within one model. But within a single task, request lengths cluster tightly — different tasks on the same model can look completely different, while requests inside one task look alike. And prefix sharing is sharply bimodal: near-zero across tasks, >80% median within a task (text); image duplication is much lower (<20%) and highly task-dependent. Every one of ACDC's three optimization axes is a direct response to one of these findings.

3 · Resource orchestration (§4.1)

The optimal TP-DP-EP split flips with the workload's compute/memory balance. Short-input, prefill-dominated tasks favor maximizing DP (many independent replicas, minimal cross-GPU communication); long-input tasks shift toward maximizing TP (spread the compute-heavy pass across more GPUs). For decode-heavy tasks, more TP frees more GPU memory per device for KV cache, raising sustainable batch size — but only up to the model's number of GQA (grouped-query attention) heads; beyond that, TP just replicates a KV head across GPUs for no capacity gain, while still paying communication overhead.

RegimeBest configWhy
Short input (100 tok), prefill-dominatedT1-D8-E8Minimize communication; DP scales linearly, no per-layer sync cost
Long input (100K tok), prefill-dominatedT8-D1-E8Compute-bound; larger TP shares the heavy pass across more GPUs

Long output (100K tok), decode-heavyT4-D2-E8KV capacity is the bottleneck, but TP=8 > GQA heads (4) wastes it

ACDC operationalizes this as warmup → adapt → rotate: sample 5% of a task to pick an initial config from a historical database, monitor the remaining 95% for distribution drift, and — since switching parallelism normally requires an engine restart (minutes of downtime) — pre-stage a KV cache on a reserved "rotating host" so switching is live and non-disruptive.

4 · Execution flow: adaptive speculative decoding (§4.3)

Fixing γ (number of speculative tokens) globally is wrong in both directions. For short-input tasks, decode is compute-bound under large batches; verifying more speculative tokens costs more than it saves, and throughput falls monotonically as γ grows — even at a fixed, favorable acceptance rate. For longer-input tasks, decode is memory-bandwidth-bound, speculative decoding amortizes weight-loading across more tokens per invocation, and there's a genuine non-monotonic sweet spot (peaking around γ=2–4 depending on input length, then declining). ACDC profiles acceptance rates on a 5% warmup sample, picks an initial γ from a historical database keyed on batch size, and re-evaluates every 5% of task progress — adjusting γ within a bounded range to avoid oscillation.

5 · Hybrid serving: modeling and harvesting bubbles (§5)

Model one PD-disaggregated prefill instance as an M/D/1 queue: random arrivals, fixed service time s, single server. Utilization ρ = λs, and:

E[W] = ρs / (2(1−ρ))         # expected queueing delay
E[T] = E[W] + s               # expected TTFT
ρ    = 2(E[T]−s) / (2E[T]−s)  # solved backward from a measured TTFT target

Because E[T] grows nonlinearly as ρ→1, hitting a TTFT target caps ρ well below full utilization — the gap (1−ρ) is bubble time. ACDC's scheduler then decides, per detected bubble, which chunk of which queued offline request to insert, maximizing an expected benefit that discounts for preemption risk:

Benefit = t_c(i,0) · (1 − P)
# P = probability of preemption: bubble too short, OR insufficient GPU memory
#     for this chunk + any pending online arrival + all in-flight offline chunks

The prefix-tree queue from §4.2 doubles as the offline candidate list, so bubble-filling also gets prefix-cache reuse for free. Decode stays fully separated: online decode uses continuous batching + bin-packing to hold TPOT; offline decode reuses §4's task-oriented parallelism and adaptive speculation to maximize throughput.

Follow the numbers, step by step

Worked examples

Four calculations, each using the paper's own reported numbers.

① The 45.1% throughput gap, decoded

The paper says removing TTFT/TPOT constraints "forfeits 45.1% of potential throughput." What does that imply about how much throughput the SLO-constrained system actually achieves?

  1. "Forfeits 45.1% of potential" means: lost = 0.451 × max, where max is the unconstrained throughput.
  2. So the SLO-constrained system achieves max − lost = max × (1 − 0.451) = 0.549 × max.
  3. In other words, serving offline work under online SLOs captures only ~54.9% of what the same GPUs could deliver.
  4. Equivalently: going from SLO-constrained to unconstrained is a throughput multiplier of 1/0.549 ≈ 1.82×, not just "+45%" — the percentage is relative to the bigger (unconstrained) number.
🍯
Insight: this single number is the entire justification for building a purpose-built offline system rather than tuning knobs on an online one — the ceiling being left on the table is comparable in size to the floor already being used.

② Why the best parallelism strategy flips with input length

Using Figure 11a's measured per-instance input throughput (tokens/s): Task 1 (100-token input) — T1-D8-E8 = 31,775 vs. T8-D1-E8 = 24,842. Task 4 (100,000-token input) — T1-D8-E8 = 7,603 vs. T8-D1-E8 = 14,103. Quantify the flip.

  1. Task 1: T1-D8-E8 beats T8-D1-E8 by (31775 − 24842)/24842 = 27.9%. Maximizing DP (replication, no cross-GPU sync) wins on short, cheap prefill.
  2. Task 4: T8-D1-E8 beats T1-D8-E8 by (14103 − 7603)/7603 = 85.5%. On a 100K-token prompt, splitting the heavy compute across 8-way TP dominates.
  3. The crossover is not gradual noise — it's a >2× swing in relative ranking driven purely by input length. A single fixed config would be badly wrong at one extreme or the other.
💡
This is exactly what motivates ACDC's warmup-then-adapt selection: sample 5% of a task's length distribution before committing, because the "right answer" for Task 1 is the wrong answer for Task 4 by a factor of nearly 2.

③ Solving the M/D/1 queue for the production bubble number

Given: service time s = 756 ms, measured average TTFT E[T] = 1.41 s (§5.1). Find the implied utilization ρ and the theoretical bubble fraction.

  1. Rearranging E[T] = ρs/(2(1−ρ)) + s for ρ gives ρ = 2(E[T]−s) / (2E[T]−s).
  2. E[T] − s = 1.41 − 0.756 = 0.654 s.
  3. Numerator: 2 × 0.654 = 1.308. Denominator: 2 × 1.41 − 0.756 = 2.064.
  4. ρ = 1.308 / 2.064 ≈ 0.634 → 63.4% theoretical utilization — exactly the paper's reported value.
  5. Theoretical bubble fraction = 1 − ρ ≈ 36.6%. The paper's measured utilization was slightly lower still (61.7%), giving an observed bubble fraction of 38.3% — the queueing model and the real system agree within ~2 points.
🍯
Insight: a first-year queueing-theory model, fed two measured numbers (s and E[T]), reproduces the paper's headline "38.3% idle" finding almost exactly — the bubbles aren't a bug in the implementation, they're a mathematical consequence of guaranteeing a TTFT.

④ Checking the "3.4–3.9× output cost-efficiency" claim

Figure 18b reports output cost-efficiency (tokens/GPU/min) before and after ACDC. Model-B: 3,100 → 11,987. Model-D: 2,847 → 9,635. Verify the paper's claimed range.

  1. Model-B: 11987 / 3100 = 3.867× ≈ 3.9× — matches the paper's upper bound exactly.
  2. Model-D: 9635 / 2847 = 3.385× ≈ 3.4× — matches the paper's lower bound exactly.
  3. Both endpoints of the claimed "3.4–3.9×" range check out against the underlying figure — the headline number isn't a rounded-up outlier, it's the honest span across the models measured.
💡
Worth noting for a systems reader: this multiplier is entirely attributable to §4's three software optimizations — no new hardware, no larger GPU allocation, same models, same traffic.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Model-C has 579K tasks and 9,136M requests — by far the most of any model in Table 1. Does this mean Model-C's offline traffic should get the largest, most aggressive resource allocation?
Show answer
Not necessarily. Raw request volume tells you nothing about per-task urgency, completion-time budget, or per-request cost — a model handling one narrow task type (Model-C is mostly text classification) at huge volume may need a completely different, simpler parallelism strategy than a model with far fewer requests but wildly varying task shapes (e.g. multimodal Model-M). ACDC allocates per-task, not by model-wide volume.Misconception: that total traffic volume determines resource priority. It's the task's own length distribution and deadline that determine the right strategy — volume is a scheduling-fairness question (FCFS across tasks), not a per-task optimization input.
Problem 2 · medium
A prefill instance has service time s = 500 ms and is run at ρ = 0.8. What is the expected TTFT, and what happens if ρ climbs to 0.95?
Show answer
At ρ=0.8: E[T] = ρs/(2(1−ρ)) + s = (0.8×0.5)/(2×0.2) + 0.5 = 0.4/0.4 + 0.5 = 1.0 + 0.5 = 1.5 s. At ρ=0.95: E[T] = (0.95×0.5)/(2×0.05) + 0.5 = 0.475/0.1 + 0.5 = 4.75 + 0.5 = 5.25 s — a 3.5× latency blowup for a 15-percentage-point utilization increase.Misconception: that utilization and latency trade off linearly. The M/D/1 waiting term has (1−ρ) in the denominator, so latency accelerates sharply as ρ approaches 1 — small utilization gains near capacity cost disproportionate latency.
Problem 3 · medium
Why does increasing pipeline-parallelism (PP) degree, a classical MapReduce/Spark-style optimization, actually reduce LLM decode throughput (§3.5, Fig. 8)?
Show answer
Pipeline parallelism splits the model across stages and relies on keeping every stage busy with a steady stream of micro-batches to hide per-stage latency. LLM decode generates one token per request per step and depends on tight, low-latency communication between stages every single step; higher PP degree means more stage boundaries, each adding a pipeline "bubble" (idle wait) before the next token can be produced. Unlike a batch MapReduce job where a stage runs once on a large chunk of data, decode's stages must synchronize on every token — so PP's benefit (parallel stages) is outweighed by its cost (per-step bubbles) at LLM decode's fine granularity.Misconception: that pipeline parallelism, a proven big-data technique, generalizes to any repeated computation. It generalizes to coarse-grained, infrequently-synchronized stages — LLM decode is the opposite: fine-grained and synchronized every step.
Problem 4 · hard
ACDC's first implementation had parallel-strategy selection and speculative-decoding adaptation both trigger on "observed throughput degradation," and the system oscillated forever. What was the actual bug, and what's the general lesson for designing multiple independent adaptive controllers?
Show answer
Both controllers watched the same signal (throughput). Any change by either one perturbed throughput, which the other interpreted as its own cue to act, cascading indefinitely. The fix: give each controller an independent, causally upstream indicator — parallelism selection reacts to input/output length-distribution shifts (observable without depending on runtime performance), speculative decoding reacts to batch size. Neither watches a signal the other one moves.Misconception: that "monitor the end-to-end metric you care about" is always the right trigger for an adaptive controller. When multiple controllers share an outcome metric, each one's corrective action is indistinguishable, to the others, from a new problem — triggers must be decoupled to causes, not effects.
Problem 5 · medium
Task 1 in Figure 13 has a short input (100 tokens) and speculative decoding hurts it monotonically as γ increases, even at a fixed 0.5 acceptance rate. Why does a fixed, "good" acceptance rate not save it?
Show answer
With short inputs and large batch sizes, decode is compute-bound, not memory-bandwidth-bound — invoking the draft model and verifying γ candidate tokens costs real compute regardless of how many are accepted. A 0.5 acceptance rate still means half the speculative work is wasted, and even the "useful" half doesn't amortize a memory-bandwidth cost that wasn't the bottleneck to begin with. Speculative decoding's entire value proposition (amortize one expensive weight-load across multiple tokens) doesn't apply when weight-loading isn't the expensive part.Misconception: that acceptance rate alone determines whether speculative decoding helps. It only helps when decode is memory-bandwidth-bound; under a compute-bound regime, even a favorable acceptance rate can't offset the added compute of drafting and verification.
Problem 6 · hard
ACDC's early hybrid scheduler optimized purely for "fill the next bubble" and ended up with worse overall bubble utilization than a more conservative design. Explain the mechanism, and what changed.
Show answer
First chunks of a fresh offline request execute faster (no accumulated KV state to load/extend), so a pure bubble-filling objective kept preferring to start new requests over finishing in-flight ones. This filled GPU memory with many half-finished offline requests, each holding KV state that couldn't be released until completion. When online requests arrived and needed memory, these half-finished offline requests were preempted — discarding all their prior computation. The fix added a max(k_r) penalty term to the scheduling formula, discouraging new admissions while any offline request remains incomplete, so the scheduler finishes existing work before starting more.Misconception: that maximizing each individual scheduling decision (fill this bubble as well as possible right now) maximizes the aggregate outcome. Myopically optimal per-bubble choices created a memory-pressure buildup that caused expensive preemptions later — the objective needed a lookahead penalty, not just a greedy per-event rule.
Problem 7 · easy
Text prefix caching gets a dedicated prefix tree and DFS scheduling; images get a much simpler "cache between first and last use" rule. Why the asymmetry?
Show answer
The measurement study (§3.4, Figs. 6–7) found text prefix sharing is abundant and structured (median >80% intra-task hit rate, driven by recurring instruction templates), justifying the overhead of building and traversing a full prefix tree. Image duplication is much lower (generally <20%) and less structured — mostly a handful of repeated images accessed a few times each (multi-round Q&A over one image) rather than a rich sharing hierarchy. A lightweight "cache between first and last reference, evict immediately after" rule captures nearly all the achievable benefit without the complexity a full tree would add for a much smaller payoff.Misconception: that a good cache-management scheme should be modality-agnostic. The right amount of caching machinery should match the actual reuse structure of the data, not be applied uniformly out of consistency.
Problem 8 · medium
The paper's §6 lesson on "clairvoyance" says ACDC's mechanisms "split along their reliance on visibility" for multi-turn agent workloads. What does that mean concretely for parallelism selection vs. prefix-aware global ordering?
Show answer
Parallelism selection only needs a stable estimate of the input/output length distribution — it can keep working on whatever sub-sequence of requests has arrived so far, re-profiling as more arrive, since it doesn't need the literal complete set. Global prefix-aware ordering, by contrast, assumes the entire request set is known up front so it can build one prefix tree and schedule optimally across all of it; with requests trickling in from an agentic pipeline, there's no "whole tree" to build ahead of time, so this mechanism needs rethinking (e.g. incremental tree updates) rather than simply degrading gracefully.Misconception: that "clairvoyance" is a single binary property a system either has or doesn't. Different mechanisms depend on different amounts of future knowledge — some need only a stable statistic, others need the literal complete set — so partial visibility breaks them unevenly.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most. Tap any to expand.

Q1What exactly counts as an "offline" LLM task?▾
A batch of thousands to millions of requests submitted together (e.g. summarize every document in a corpus, translate a dataset), where the user cares about total completion time — minutes to over 1,000 minutes in production — rather than any single request's latency. The entire request set is fully known at submission, unlike an online chat session.
Q2Why can't we just run offline tasks on the existing online engine with relaxed timeouts?▾
Because the scheduler's internal decisions (batch sizing, parallelism choice, eviction policy) are all tuned to protect TTFT/TPOT, and throughput is fundamentally at odds with those latency guarantees. The paper measures this directly: under online SLOs, offline work forfeits 45.1% of the throughput it could otherwise achieve — same engine, same hardware — an ~82% uplift once those constraints are removed. "Relaxed timeout" doesn't remove the scheduler's latency-protective behavior; only purpose-built scheduling does.
Q3What's the actual difference between resource orchestration, cache management, and execution flow?▾
They're independent axes targeting different resources: resource orchestration (§4.1) decides how GPUs are split across a task via TP/DP/EP; cache management (§4.2) decides the order requests run in to maximize KV cache reuse; execution flow (§4.3) decides a runtime decoding parameter (speculative-decoding γ). None of the three subsumes another — a task can have the wrong parallelism, poor cache ordering, and a bad γ simultaneously, and each is fixed separately.
Q4Why does the best TP/DP/EP configuration change mid-task?▾
Because a task's requests aren't always uniform — the input/output length distribution can drift as the task progresses. ACDC monitors completed requests in 5%-of-task windows and triggers a live parallelism switch (via a pre-warmed "rotating host") if the observed distribution has diverged enough from the one the current config was chosen for.
Q5Why is prefix sharing so different between text and images?▾
Text prompts within a task are often built from a shared instruction template with only the document changing, so the shared prefix is long and nearly universal (median >80% hit rate). Images are typically distinct per request except for occasional multi-round questioning about the same image — the "reuse graph" is sparse and shallow rather than a shared trunk, so it doesn't benefit from a full prefix tree the way text does.
Q6What is a "bubble," precisely, and why can't online traffic fill it itself?▾
A bubble is an idle interval on a PD-disaggregated prefill instance between finishing one request's prefill and the next one arriving — a structural consequence of keeping batch size near 1 to protect TTFT. Online traffic can't fill its own bubbles because, by construction, there's no other online work queued during that gap (if there were, it wouldn't be a bubble) — the idle time only exists because arrivals are bursty and unpredictable.
Q7Does harvesting bubbles for offline work ever hurt online latency?▾
By design, minimally: offline chunks are only inserted when a bubble is detected, are sized (via bubble-duration distributions estimated from a 24-hour sliding window of historical observations) to probabilistically fit inside it, and are preempted at the next layer boundary the instant an online request needs the GPU, with already-computed KV cache preserved. Production measurements show online TTFT tail latency increases by only 0.48% (P95), 0.67% (P99), and 0.69% (P999) — well inside the SLO budget.
Q8How is ACDC's hybrid serving different from HyGen, Echo, or ConServe?▾
Those systems co-locate prefill and decode on the same GPU and rely on preemption-based scheduling to protect online SLOs when offline work is inserted — which incurs heavy preemption overhead (an average of 259 preemptions per offline request against HyGen in the paper's test) and doesn't map onto the now-common PD-disaggregated production architecture. ACDC targets PD-disaggregation specifically, inserting offline work only into structurally idle prefill bubbles, which sidesteps most preemption entirely and beats HyGen's throughput by up to 5.6×.
Q9What happens for a brand-new model with no historical profiling data?▾
ACDC defaults to a conservative configuration during the mandatory 5%-of-task warmup window used by both parallelism selection and speculative-decoding tuning. The throughput penalty from this cold start is bounded to that small warmup slice and amortized over the whole (often hour-plus) task duration, so its end-to-end impact is negligible.
Q10Does ACDC always beat plain LRU/FCFS scheduling for offline tasks?▾
In every reported comparison, yes — but its advantage scales with how much intra-task structure (length clustering, prefix sharing) exists to exploit. The gains are largest for prefix-tree reuse specifically at small TP (35.5% hit-rate improvement), where limited KV cache capacity makes eviction-order mistakes most costly; at larger TP, more memory means fewer eviction mistakes in the first place, narrowing the gap.
Q11What's the "clairvoyance" caveat the authors flag for future work?▾
ACDC's biggest wins (global prefix-tree ordering, one-shot parallelism profiling) depend on knowing the entire task's request set at submission. Emerging multi-turn agentic workloads emit requests incrementally, each depending on a prior output, which partially breaks that assumption — the authors note some mechanisms degrade gracefully to observed sub-sequences (parallelism selection) while others (global ordering) need genuine rework for partial visibility.

Core terms
ACDCThe paper's offline-serving system, tailored along three axes: resource orchestration, cache management, execution flow, plus a hybrid-serving extension.
Inherent determinismThe property that an offline task's entire request set is known at submission, before execution begins — enables planning impossible for online traffic.
Throughput orientationOffline users care about total task completion time, not per-request TTFT/TPOT — the property that lets ACDC discard latency-protective scheduling.
Task-oriented parallel strategyACDC's resource-orchestration mechanism: pick and dynamically re-pick TP/DP/EP per task's input/output length profile.
Prefix-aware KV cache reusingACDC's cache-management mechanism: build a per-task prefix tree, schedule depth-first, evict subtrees with no remaining descendants first.
Adaptive speculative decodingACDC's execution-flow mechanism: tune the speculative-token count γ per task based on batch size and profiled acceptance rate.
Resource bubbleAn idle interval on a PD-disaggregated prefill instance between online request arrivals, caused by keeping batch size near 1 to protect TTFT.
Hybrid-serving mechanismACDC's extension that opportunistically schedules chunked offline prefill into detected online bubbles, decoding offline separately.
Supporting terms
TTFT / TPOTTime To First Token / Time Per Output Token — the two online latency SLOs offline work is exempt from.
TP / DP / EPTensor / Data / Expert Parallelism — the three axes ACDC tunes jointly per task (e.g. "T4-D2-E8").
GQA headsGrouped-Query Attention heads; the count that caps how much KV-cache capacity gain further TP actually buys.
PD disaggregationRunning prefill and decode on separate GPU instances to eliminate cross-stage interference — the setting that creates harvestable bubbles.
M/D/1 queueQueueing model (random arrivals, deterministic service, one server) used to formalize prefill's utilization/latency trade-off.
Chunked prefillSplitting a long prefill into fixed-size chunks (here, 2048 tokens) so it can be interleaved with other work — the mechanism that makes bubble-harvesting fine-grained.
Speculative decoding / γGenerating γ candidate tokens with a cheap draft model, verified in one target-model pass; γ is the tunable speculation depth (EAGLE-3 used here).
FCFSFirst-Come-First-Served — ACDC's policy across tasks (fair queueing); within a task, requests are freely reordered for cache benefit.
max(k_r) penaltyThe scheduling-formula term that discourages starting new offline requests while others remain incomplete, preventing memory-pressure preemption cascades.
Cost-efficiencyTokens processed per GPU per minute — ACDC's production evaluation metric, directly tied to serving cost.

Paper facts

My framing (added, not the paper's claim)

The connections to OS memory tiering — prefix-tree eviction as an oracle/Belady-style analog to LRU-based promotion/demotion, bubble-harvesting as analogous to opportunistic capacity/bandwidth harvesting in CXL-pooled memory, and the "finish before you start" memory-pressure lesson as structurally identical to thrashing from over-eager hot-tier promotion — are my analogies for a reader with that background, not claims the authors make. The paper itself frames its work entirely within LLM-serving systems.
