Beat the CPU's guesswork: hammer quietly, not loudly

Load-based Rowhammer just went silent on Intel's newest chips. ρHammer explains why — and revives it with async prefetches, a DRAM-mapping trick that works in seconds, and a technique that out-thinks speculative execution.

📄 "ρHammer: Reviving Rowhammer Attacks on New Architectures via Prefetching" · Chen et al. 🎓 Some DRAM/µarch basics assumed — the primers cover the security-specific vocabulary ⏱ ~30 min read
🔓

Map the DRAM blind in seconds, hammer with async prefetches instead of blocking loads, then out-maneuver the CPU's own speculation. That's how a "dead" attack comes back to life.

Before you begin

Quick glossary + what the paper assumes

You already know DRAM organization and the mm stack; these are the security-specific pieces the paper leans on. Acronyms first, then six short primers — open any that look unfamiliar.

Quick glossary — key acronyms, up front

AIBActivation-induced bit flip — the formal name for a Rowhammer flip: repeated row activations leak charge into a neighbor.
TRRTarget Row Refresh — the in-DRAM defense that refreshes rows it detects as frequently activated.
SBDRSame-Bank-Different-Row — the slow-timing access pattern used as the reverse-engineering side channel.
MCMemory Controller — issues activate/precharge/refresh commands and owns the (secret) address mapping.
OoO / ROBOut-of-order execution / Reorder Buffer — lets the CPU execute ahead of program order while committing results in order.
BTB / PHTBranch Target Buffer / Pattern History Table — the structures branch prediction uses to guess where code goes next.
LFBLine Fill Buffer — where a prefetch's request sits while the L1-D awaits the DRAM data, letting the CPU move on immediately.
pTRR / RFMPseudo-TRR (Intel's platform-level mitigation) / Refresh Management — DDR5's stricter, doubled refresh-based defense.

1Rowhammer, in one paragraph▾

Repeatedly opening ("activating") the same DRAM row leaks a tiny amount of charge into physically adjacent rows via capacitive coupling. Do it enough times before the next refresh and a neighboring cell's bit flips — an AIB. You never touch the victim address; you just hammer its neighbor.

TRR is the standard countermeasure: the DRAM chip itself watches for suspiciously hot rows during refresh and proactively refreshes their neighbors. Non-uniform hammering (Blacksmith, ZenHammer) defeats TRR by using an irregular mix of aggressor frequencies/offsets that confuses the sampler about which row is the real threat.

Now you're ready: ρHammer doesn't invent a new bypass pattern — it takes an existing non-uniform pattern and asks "why won't this fire on my 12th/14th-gen Intel box?"
2The SBDR side channel▾

Only one row per bank can sit in the shared row buffer at a time. Access two addresses in the same bank, different row (SBDR) and the second must wait for a precharge + new activate — measurably slower than a same-row hit or a different-bank access. That timing gap is a side channel: it tells you, for any two addresses, "did I just change the row (and stay in-bank)?"

Now you're ready: every reverse-engineering step in Section 3 is just: pick two addresses that differ in a chosen set of bits, time them, and ask "was that an SBDR delay?"
3DRAM address mapping & bank functions▾

A physical address doesn't map to (bank, row, column) as contiguous bit ranges — the memory controller XORs several bits together to pick the bank ("bank function"), partly to spread traffic evenly. Some bits overlap between row and bank addressing. This mapping is undocumented and CPU-specific, and it's a prerequisite for Rowhammer: you can't target "the row next to my aggressor" without it.

On DDR5-capable Alder/Raptor Lake, the paper finds bank functions ballooned from 2 bits per function (older DDR4 controllers) to up to 7, and total bank bits from 19 to 32 — likely in response to DDR5's added bank groups, though the paper doesn't establish this as a demonstrated cause.

Now you're ready: that explosion is exactly why brute-force reverse-engineering (try every candidate function) stops scaling, motivating ρHammer's structured Duet/Trio/Quartet method.
4x86 software prefetch instructions▾

PREFETCHh instructions (T0/T1/T2/NTA) are explicit hints: "start fetching this line into cache, but don't make me wait." Unlike a load, a prefetch retires as soon as address translation completes and the request is handed to the L1-D's line fill buffer (LFB) — it does not stall on the DRAM round-trip the way a load's destination register does.

Now you're ready: this asynchrony is the whole engine behind ρHammer's speed advantage — more hammer attempts fit in the same wall-clock time, i.e. a higher activation rate.
5Speculative execution as an adversary▾

Two mechanisms reorder your carefully-sequenced hammer loop: branch prediction (guesses loop control flow ahead of resolution, using the BTB for targets and the PHT for taken/not-taken history) and out-of-order execution (issues independent instructions ahead of program order, tracked/committed via the ROB). Both scramble the intended aggressor-access order — and Intel's SDM states that prefetches aren't ordered with respect to fences or other prefetches at all, unlike loads.

Now you're ready: this is Challenge III of the paper — a plain MFENCE/LFENCE can't fix prefetch ordering the way it (sort of) helps loads, so a different trick is needed.
6Fuzzing vs. sweeping (the paper's two experiments)▾

Fuzzing: generate many pseudo-random non-uniform patterns, keep any that flip a bit at a few physical locations, and report the best pattern found — this measures how hard it is to find a working pattern at all. Sweeping: take one proven-good pattern (encoded as relative row offsets) and repeat it across a large range of physical locations — this measures reliability/practicality, i.e. what a real exploit would experience.

Now you're ready: the headline "200K+ bit flips" numbers come from fuzzing; the "187K/min flip rate" numbers come from sweeping.

The whole story in one place

ρHammer in a nutshell

Three stacked problems, three stacked fixes, and why the result is a genuine revival — not an incremental tweak.

Conventional Rowhammer tooling — load instructions plus memory-barrier ordering — is quietly failing on the newest Intel desktop parts. The paper traces this to a bottleneck that earlier work didn't isolate: activation rate, the number of row activations you can cram into one refresh interval. On Alder/Raptor Lake, load-based non-uniform hammering (the Blacksmith/ZenHammer style attacks) fails to reproduce meaningful, sweeping bit flips — Table 6's fuzzing runs show only sparse, occasional flips at best — even against DIMMs that are demonstrably still vulnerable.

ρHammer fixes three things end-to-end. (1) Mapping: a layout-agnostic reverse-engineering method (pairwise SBDR timing + structured deduction, no assumptions about bank-bit count or overlap) recovers full DRAM address mappings on Alder/Raptor Lake in under 10 seconds — where every prior public tool fails outright. (2) Throughput: replacing load instructions with asynchronous x86 PREFETCHh instructions, further amplified by multi-bank parallelism, breaks the activation-rate ceiling. (3) Order: because prefetches suffer even worse speculative disorder than loads and can't be fenced, a counter-speculation technique (branch-predictor obfuscation + tuned NOP "pseudo-barriers") restores enough access order to make the higher throughput actually count.

The payoff: over 200K additional bit flips in 2-hour fuzzing on Comet Lake; 112.4× and 47.1× higher sweep flip rates on Comet/Rocket Lake (187K/min, 47K/min); and — the headline result — the first reproducible Rowhammer flips on Raptor Lake at all, at a stable 2,291 flips/min, plus 995/min on Alder Lake, where the load-based baseline fails to reproduce any meaningful, sweeping flips.

🍯 Key takeaways

  • Load-based hammering is activation-rate-bound, not just "TRR-bound" — the newest platforms expose that bottleneck brutally.
  • DRAM mapping recovery scales polynomially with pairwise SBDR measurements, not exponentially via brute-force bank-function search.
  • x86 software prefetches are asynchronous and retire early (via the LFB) — on their own, this roughly doubles attack speed at peak cache-miss rates; the full 47×–112× gains reported below also include multi-bank parallelism and counter-speculation.
  • Multi-bank hammering helps prefetching in two ways: parallelism, and — less obviously — disorder mitigation via inter-bank pipeline latency.
  • Prefetches aren't architecturally ordered by fences at all; ρHammer instead saturates the ROB with tuned NOPs and confuses the branch predictor.
  • Result: Rowhammer revived on Raptor Lake (2,291 flips/min) where baselines fail to reproduce meaningful, sweeping flips.
Seven everyday pictures

How to think about ρHammer

Each stands alone. Every card ends with an honest note about where the picture breaks.

The engine · Load vs. prefetch

Standing in line vs. mailing a letter

A load is like standing at the post-office counter until your package is handed over — you can't do anything else meanwhile. A prefetch is dropping a letter in the mailbox: you walk away instantly, and it arrives whenever it arrives. Because Rowhammer only cares about triggering the activation, not consuming the data, the mailbox approach lets you fire off far more requests per second.

Where it breaks: a real mailed letter always arrives; a prefetch can be silently dropped if the CPU decides the line is already "in the cache" from a reordered flush — see the "nullified prefetch" analogy.
Mapping recovery · Duet/Trio/Quartet

Twenty Questions, not a phone book

Old reverse-engineering tools brute-force every candidate bank function — like reading the phone book front to back looking for one number. ρHammer instead asks a sequence of targeted yes/no timing questions (Duet: "do these two bits form a bank function together?" Trio/Quartet: "does adding this bit break or preserve the SBDR state?") and deduces the whole mapping structurally, the way Twenty Questions narrows an unknown object fast.

Where it breaks: it relies on bank functions being simple XORs with the SBDR side channel reliably distinguishing them; a fundamentally different (non-XOR) addressing scheme would need new questions.
Throughput · Multi-bank parallelism

Four checkout lanes instead of one

A single grocery lane processes customers fast per-customer but caps total throughput. Open four lanes (banks) and total customers-per-minute rises, even though each lane individually slows a bit due to interleaving. Distributing hammer accesses across banks buys the same kind of aggregate speedup — plus, as a bonus, spacing accesses out per bank quietly reduces how tangled the speculative reordering gets.

Where it breaks: too many lanes and each one is nearly idle — Comet Lake's peak was 3 banks, not 8; overshooting the optimum degrades results just like an overstaffed, under-used store.
Counter-speculation · Branch obfuscation

A magician's misdirection

A magician keeps varying which hand looks like it holds the coin so the audience (your branch predictor) can never build a reliable guess. ρHammer generates runtime randomness (via rdrand/rdtscp) to scramble which code path each loop iteration takes, continually invalidating the BTB's cached targets and the PHT's learned history — forcing the CPU back toward conservative, in-order execution.

Where it breaks: unlike a magician, ρHammer still needs its trick (the loop) to actually complete every iteration — the obfuscation must never change what gets hammered, only confuse when the CPU thinks it will.
Counter-speculation · NOP pseudo-barriers

Speed bumps, not a wall

A wall (a hard, blocking barrier) would stop traffic dead and tank throughput. Speed bumps slow cars just enough to keep them in a sane order without stopping the road. NOPs inserted between prefetches consume reorder-buffer slots without doing real work, gently serializing execution — too few bumps and cars still weave (disorder wins); too many and traffic crawls (throughput dies). The paper finds a genuine sweet spot: 390 NOPs on Raptor Lake.

Where it breaks: the "right" number of bumps is road-specific — the optimal NOP count is platform-dependent (different ROB sizes/OoO depth) and must be retuned per architecture, sometimes per pattern.
The primitive · SBDR side channel

Two doors vs. one revolving door

Leaving through two separate doors, people pass freely. Funnel them through one revolving door and the second person waits for the first to clear it. A DRAM bank's row buffer is that single revolving door: hit the same bank with a different row and you pay a measurable, extra "door-clearing" delay — that delay is the signal that lets you tell rows and banks apart from the outside.

Where it breaks: real timing measurements are noisy (thermal drift, other traffic), so ρHammer averages 16 random pairs × 50 accesses per measurement rather than trusting a single timing sample.
Methodology · Fuzzing vs. sweeping

Prospecting vs. mining a known vein

Fuzzing is prospecting: try thousands of quick, cheap samples across a wide search space to find one promising vein (a pattern that flips any bit). Sweeping is mining: once you've found a vein, dig along it exhaustively — repeat that same pattern at hundreds of physical locations to see how reliably it pays off in practice.

Where it breaks: mining assumes the vein runs consistently through the rock. Rowhammer susceptibility does vary by physical location on a chip, which is exactly why the paper sweeps across many base addresses rather than trusting one lucky spot.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams.

1 · Reverse-engineering the mapping

Prior tools brute-force candidate bank functions — a search space that exploded 8,192× (213, from 19 to 32 bank bits) and 23,800× in function-search overhead going from older to newest Intel mappings. ρHammer instead resolves three sub-objectives with one primitive, T_SBDR(M, B_diff) — the average access timing over random address pairs differing only in the bit-set B_diff:

  1. Duet (O1 — row-inclusive bank functions): test every bit pair {bx, by}. An SBDR-slow pair means both bits belong to the same bank function and at least one is a row bit — this also reveals the full row-bit range (O2).
  2. Trio (start of O3 — non-row bits): "borrow" a known bank-function pair from Duet as a baseline SBDR state, then add one more candidate bit at a time. A fast (DB) timing means that bit is a bank bit not yet classified — a non-row candidate.
  3. Quartet (finish O3): pair up the non-row candidates and test them together against the borrowed baseline; an SBDR-slow result means the pair belongs to the same (new) bank function. Merge all discovered pairs into complete functions.
🧭
No brute force, no assumption about function size or row/bank overlap — this is what keeps the method working as Alder/Raptor Lake's mappings grow more intricate, recovering full mappings in 4–9 seconds versus hundreds of seconds (or outright failure) for prior tools.

2 · Multi-bank prefetch hammering

Spreading a non-uniform pattern's aggressor accesses across several banks does two things at once: it exploits bank-level parallelism directly, and it inserts inter-bank pipeline latency between consecutive same-bank hammer attempts, which incidentally reduces disorder. On Comet Lake, cache-miss rate (a proxy for "did this access truly reach DRAM, un-reordered") climbs steadily from 1 to ~3 banks before per-bank activation rate losses start to dominate — 3 banks is the empirical sweet spot for that platform (51,911 flips in 2h fuzzing, vs. far fewer at 1 or 8 banks).

3 · Counter-speculation hammering

Two mechanisms stacked together restore usable ordering to prefetch-based hammering:

// control-flow obfuscation: scramble which path each iteration takes
idx = obfuscate(rdrand(), rdtscp());  // invalidates BTB targets + PHT history each loop

// counter-speculation hammer loop (per aggressor)
for i in 0..num_of_act:
    prefetch(aggr_row_addrs[idx]);
    NOP × OPTIMAL_COUNT;        // saturates ROB, forces near-serial execution
    clflushopt(aggr_row_addrs[idx]);
    idx = obfuscate(...);          // re-randomize control flow

The NOP count is tuned empirically per platform: too few and OoO execution still reorders around them (0 flips); too many and per-loop overhead sinks the activation rate (0 flips again). Table 3 shows why fences don't substitute for this: CPUID-based serialization is architecturally correct per Intel's manual but far too slow (2,104 ms vs. ~212 ms for NOPs), and LFENCE's apparent benefit turns out to be a side effect — it orders the load used to compute the next prefetch's address, not the prefetches themselves.

🔗
For your tiering/CXL lens (speculative — not in the paper): the paper only invokes DDR5's Refresh Management (RFM) as the reason it found no working DDR5 patterns yet; it doesn't connect RFM to DRAM/NVM tiering, write endurance, or latency models. The narrower, genuinely relevant thread is that a concurrent side-channel study found RFM timing leaks structure on GDDR6/LPDDR5 — worth tracking if you're deriving refresh-related side channels in pooled CXL memory.
Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's tables, walked through in full.

① Why the search space explodes without structured deduction

The paper claims going from 19 to 32 total bank bits (with per-function size growing from 2 to 7 bits) yields an 8,192× larger search space and a 23,800× larger function-search overhead. Where do these come from?

  1. Total bit-position search space scales with 2(extra bits): 32 − 19 = 13 extra bits, and 213 = 8,192× — exactly the paper's figure.
  2. Per-function combination count (choosing which bits form one function) is roughly a binomial coefficient. Small functions (size 2) from 19 bits: C(19,2) = 171 candidate pairs.
  3. Larger functions (size 7) from 32 bits: C(32,7) = 3,365,856 candidate combinations.
  4. Ratio: 3,365,856 ÷ 171 ≈ 19,684× — in the same order of magnitude as the paper's reported 23,800× (their exact figure folds in additional per-bit brute-force factors this simplified count omits).
🍯
Insight: brute force isn't just "slower" on new architectures — it's exponentially/combinatorially worse, while ρHammer's pairwise deduction stays polynomial (fixed-size Duet/Trio/Quartet probes) regardless of how large the bank-bit space grows.

② Reconstructing the baseline flip rate from the headline multiplier

The paper reports ρHammer hits 187K flips/min on Comet Lake, "112.4× improvement over the baseline." What was the baseline's actual rate?

  1. Set up the ratio: 187,000 ÷ baseline = 112.4.
  2. Solve: baseline ≈ 187,000 ÷ 112.4 ≈ 1,664 flips/min — a real, working load-based attack, just an order of magnitude slower.
  3. Repeat for Rocket Lake: 47,000 ÷ 47.1 ≈ 998 flips/min baseline.
  4. Contrast with Alder/Raptor Lake: there, the baseline fails to reproduce meaningful, sweeping flips (Table 6's fuzzing runs show only sparse, occasional flips) — so no meaningful ratio can be computed. That qualitative jump (a working-but-slow baseline vs. one that can't sustain a sweep) is the real story, not just "bigger multiplier."
💡
This is why the paper frames Alder/Raptor Lake as a "revival" rather than an "improvement" — for those two architectures there's no baseline number to divide against.

③ How much did multi-bank + prefetching amplify total flips (Table 6)

On Comet Lake, DIMM S4, the single-bank load baseline (BL-S) totals 50,700 flips in 2-hour fuzzing; ρHammer multi-bank (ρ-M) totals 257,881. What's the amplification, and what does it hide?

  1. Raw ratio: 257,881 ÷ 50,700 ≈ 5.09× more total flips — from just switching the hammering primitive and adding multi-bank.
  2. Best single pattern also grew: BL-S's best pattern found 7,839 flips; ρ-M's best pattern found 13,880 — a 1.77× jump in per-pattern potency, smaller than the aggregate ratio.
  3. What explains the gap between 5.09× and 1.77×? With a higher activation rate, the 2-hour fuzzing budget can try far more candidate patterns in the same wall-clock time — so more of the total gain comes from finding more good patterns, not just each pattern hitting harder.
🍯
Insight: activation rate compounds — it doesn't just make each attempt more damaging, it lets the fuzzer explore the pattern space faster within any fixed time budget.

④ Sanity-checking the mapping-recovery speedup

Table 5: DRAMDig takes 867.6s on Comet Lake (i7-10700K); ρHammer takes 8.5s. How large is the speedup, and does it hold up on newer chips?

  1. Comet Lake speedup: 867.6 ÷ 8.5 ≈ 102× faster — "more than two orders of magnitude," matching the paper's claim.
  2. Rocket Lake: DRAMDig 1,329.9s vs. ρHammer 6.1s ≈ 218× faster.
  3. Alder/Raptor Lake: DRAMDig, DARE, and DRAMA all report "–" (fail or abort) — no denominator exists, so the comparison becomes qualitative: ρHammer succeeds in 4.1–4.6s where nothing else produces a correct mapping at all.
💡
Runtime keeps dropping (8.5s → 4.1s) as architectures get newer in this table — the structured method doesn't just survive growing bank-bit complexity, it appears to pay off more as brute-force alternatives get comparatively worse.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking.

Problem 1 · easy
The paper disables nothing about the CPU's hardware prefetcher — it runs at default BIOS settings throughout. Why doesn't the (uncontrollable) hardware prefetcher interfere with ρHammer's attack?
Show answer
ρHammer uses explicit software prefetch instructions (PREFETCHh), which the attacker directly controls the address and timing of. The hardware prefetcher is a separate, transparent unit that speculatively fetches based on observed access patterns — it's a confound the paper explicitly sets aside ("we do not discuss hardware prefetching... it is much less controllable"), not a component of the attack itself.Misconception: conflating "prefetching" as a single concept. Software prefetch instructions and hardware prefetchers are different mechanisms with different controllability.
Problem 2 · medium
For a 16-bank DRAM, the SBDR/non-SBDR ratio in a well-aligned sample region is 1/(#Banks−1). What fraction of randomly sampled address pairs should show SBDR timing, and why isn't it 1/16?
Show answer
1/(16−1) = 1/15 ≈ 6.7%. It's not 1/16 because SBDR requires the pair to land in the same bank but a different row — given a random pair already shares a bank (probability roughly 1/16 for the "reference" bank), the remaining condition is "different row within that one bank," and the denominator counts the 15 other banks that would instead give fast different-bank (DB) timing.Misconception: treating "same bank" and "SBDR" as the same probability. SBDR is a stricter condition nested inside "same bank."
Problem 3 · medium
Why does the Trio step need to "borrow" an already-known bank-function pair (b_BF, b'_BF) instead of just testing each unclassified bit b_x on its own?
Show answer
A single unclassified bit flipped alone doesn't reliably create or destroy an SBDR condition by itself — you need an existing SBDR state to perturb. By starting from a confirmed row-inclusive bank-function pair (which alone yields a slow SBDR baseline), adding b_x and checking whether the timing flips to fast (DB) reveals whether b_x is itself a bank bit: if it is, adding it changes which bank you land in and breaks the SBDR condition.Misconception: thinking each candidate bit can be classified in isolation. The method is inherently differential — it always tests a bit's effect against a known reference state.
Problem 4 · hard
The AsmJit hammering primitive (immediate addressing, no index-counter dependency) executes measurably faster per instruction than the C++ primitive, yet produces far fewer bit flips on Comet/Rocket Lake. Explain the paradox.
Show answer
Raw instruction throughput isn't what matters — intended access order is. The C++ primitive's index-counter creates a genuine data dependency between successive loop iterations (computing the next address requires the prior iteration's counter), which imposes pipeline latency that partially neutralizes the CPU's speculative reordering. AsmJit's immediate addressing has no such dependency, so OoO execution and branch prediction can freely reorder hammer/flush pairs — collapsing the effective activation rate on the rows the attacker actually intended to target, even though the CPU is "doing more work per second."Misconception: assuming faster code execution always means a more effective attack. For Rowhammer specifically, disordered-but-fast access can be strictly worse than ordered-but-slower access.
Problem 5 · medium
Table 6 shows BL-M (baseline, multi-bank) sometimes performing worse than BL-S (baseline, single-bank) on Comet Lake, while ρ-M always beats ρ-S. Why the opposite trend?
Show answer
Load-based hammering is already activation-rate-bound at the load-queue level; spreading it across more banks divides an already-scarce resource further, so per-bank activation rate can drop faster than parallelism gains it back. Prefetch-based hammering isn't queue-bound the same way (prefetches retire immediately via the LFB), so it has throughput headroom to spend on multi-bank parallelism, and additionally benefits from the disorder-mitigating side effect of bank interleaving.Misconception: assuming "more banks" is a universally good knob. Its benefit depends on whether the hammering primitive has spare throughput to actually exploit the added parallelism.
Problem 6 · hard
Intel's SDM states PREFETCHh instructions are not ordered with respect to fences or other prefetches — yet Table 3 shows LFENCE giving Alder Lake ~8,113 flips, close to the NOP technique's 5,250. Is the SDM wrong?
Show answer
No — the paper verifies this by reusing the AsmJit primitive (no address-dependency chain) with LFENCE inserted, and flip counts collapse. LFENCE's apparent benefit with the normal C++ primitive is indirect: it orders the load that computes the next prefetch's target address (an explicit memory read, which fences do order) before the prefetch is issued — not the prefetch's own DRAM access. Remove that dependency chain and LFENCE has nothing left to order.Misconception: inferring a direct causal mechanism from a correlated performance number. The paper's control experiment (swap in AsmJit) is exactly what's needed to rule out the naive "LFENCE orders prefetches" explanation.
Problem 7 · medium
A concurrent study found multi-threaded hammering is less effective than single-threaded on TRR-protected DDR4, worsening with more threads — the opposite of older DDR3 wisdom. Why does ρHammer stick to single-threaded hammering?
Show answer
TRR-bypassing non-uniform patterns depend on a precise, ordered sequence of aggressor accesses. Multiple threads hammering concurrently create asynchronous, colliding requests in the memory-controller queue that disrupt this order and can trigger extra TRR refreshes; adding synchronization (locks/semaphores) to restore order re-serializes the threads anyway, at a rate below what single-threaded prefetching already achieves.Misconception: assuming more parallelism (threads) is strictly better for Rowhammer, the way it often is for raw bandwidth benchmarks. Precise ordering, not raw thread count, is the binding constraint here.
Problem 8 · easy
The load-based baseline fails to reproduce meaningful, sweeping flips on Raptor Lake. Does this mean the tested DIMMs are Rowhammer-immune on that platform?
Show answer
No. ρHammer, using the same DIMMs and the same set of non-repeating row addresses in the sweep, achieves a stable 2,291 flips/min. The DIMMs were vulnerable all along — the baseline's failure to sustain flips reflects an insufficient activation rate and unmanaged speculative disorder in the attack tooling, not immunity in the hardware.Misconception: treating "my exploit doesn't work" as proof "the target is safe." Absence of flips under a weak attack methodology says nothing about the underlying vulnerability.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1What is ρHammer in one sentence?▾
A Rowhammer framework that revives attacks on the newest Intel architectures (Alder/Raptor Lake) by fixing three bottlenecks: slow DRAM-mapping recovery, an activation-rate ceiling from load-based hammering, and severe speculative-execution disorder in prefetch-based hammering.
Q2Why do load-based attacks fail specifically on Alder/Raptor Lake?▾
The paper attributes it to more aggressive speculative execution mechanisms on these newer cores combined with an activation rate that was already marginal for load-based hammering — the newer, more complex DRAM mapping (more bank bits, DDR5 support) compounds the problem by making it harder to even locate the right rows in the first place.
Q3How is the reverse-engineering method different from DRAMA/DRAMDig/DARE?▾
DRAMA brute-forces bank functions from scratch; DRAMDig assumes pure row bits exist to prune the search (they don't, on newer mappings); DARE makes assumptions that produce non-deterministic or partially wrong results. ρHammer's Duet/Trio/Quartet method makes no assumptions about bank-bit count, per-function size, or bank/row overlap, and runs in polynomial time.
Q4What exactly is the SBDR side channel measuring?▾
Whether two addresses, differing only in a chosen set of bits, land in the same bank but different rows. Same-bank-different-row accesses are slower because only one row per bank can occupy the shared row buffer at a time, forcing a precharge before the second access.
Q5If a prefetch causes a cache hit, doesn't that mean no DRAM access happened — so how does it hammer anything?▾
That's exactly the earlier misconception (from prior work) that ρHammer corrects. When properly ordered and combined with flushes, prefetches still reach DRAM at a lower cache-miss rate than one might assume from raw speed alone — and even accounting for cache hits, the paper shows prefetching still roughly doubles attack speed at peak cache-miss saturation, meaning the throughput gain is real, not just a hit-rate artifact.
Q6What is actually being reordered, mechanically?▾
The sequence in which aggressor-row prefetch (or load) and flush instructions execute relative to each other. Out-of-order execution can issue independent instructions ahead of program order; branch prediction can speculatively continue past loop-control branches before they resolve. Both can interleave or skip hammer/flush pairs in ways that don't match the carefully-tuned non-uniform pattern the attacker designed.
Q7Why can't a simple MFENCE or LFENCE fix prefetch ordering?▾
Per Intel's SDM, PREFETCHh instructions are architecturally not ordered with respect to fence instructions or other prefetches — only with respect to serializing instructions like CPUID, which are far too slow for hammering (Table 3: ~2,104ms vs. ~212ms for the NOP approach). LFENCE's apparent partial benefit is a side effect of ordering the address-computing load, not the prefetch itself.
Q8What does the NOP pseudo-barrier actually do at the microarchitectural level?▾
Each NOP still occupies a slot in the finite reorder buffer (ROB). Enough NOPs between two instructions saturate the ROB, forcing near-serial commitment and thus restoring intended order — without doing meaningful computational work that would add its own overhead.
Q9Does multi-bank hammering always help?▾
No — there's an optimal bank count per platform/DIMM (e.g., 3 for Comet Lake in the paper's setup), beyond which per-bank activation rate losses outweigh the parallelism and disorder-mitigation gains. It also hurts load-based baselines in some cases, since loads are already activation-rate-bound before adding banks.
Q10Is this attack still exploitable after responsible disclosure?▾
The authors disclosed to Intel, MSI, and Samsung; MSI's PSIRT shipped a fix. The paper's own mitigation discussion recommends enabling the BIOS "Rowhammer Prevention" option (Intel's pseudo-TRR), which eliminated nearly all observed flips on their MSI Alder/Raptor Lake board.
Q11Does ρHammer work on DDR5?▾
Not demonstrated in this paper — the authors found no effective pattern on their DDR5 setups, attributing it to DDR5's stricter refresh-based defenses (Refresh Management, RFM) and needing further reverse-engineering work for extra sub-channel functions. They flag it as concrete future work, including a possible new RFM-based timing side channel from concurrent research.
Q12What real-world impact does this enable?▾
Combined with the Rubicon massaging technique, the authors demonstrate end-to-end page-table-entry (PTE) corruption on Alder and Raptor Lake, achieving page-table read/write capability in an average of ~3min 8s and ~51s respectively across five independent trials — without relying on superpages.

Core terms
ρHammerThis paper's framework: DRAM-mapping reverse-engineering + prefetch-based hammering + counter-speculation, together reviving Rowhammer on Alder/Raptor Lake.
Activation rateRow activations achievable per DRAM refresh interval — the metric the paper identifies as the real bottleneck for load-based hammering on new platforms.
SBDRSame-Bank-Different-Row access; the slower of the three access-timing classes (SR/SBDR/DB), used as the reverse-engineering side channel.
Duet / Trio / QuartetρHammer's three-stage pairwise SBDR measurement procedure that recovers row-inclusive and non-row bank functions without brute force.
Non-uniform hammeringTRR-bypassing pattern style (Blacksmith/ZenHammer) using varied aggressor frequencies/offsets to confuse the refresh sampler.
Counter-speculation hammeringρHammer's technique combining branch-predictor obfuscation and tuned NOP pseudo-barriers to restore access order for prefetch-based hammering.
Fuzzing / sweepingSearch for an effective pattern (fuzzing) vs. repeating a found pattern broadly to test reliability (sweeping).
Supporting terms
TRR / pTRRTarget Row Refresh (in-DRAM) / pseudo-TRR (platform-level, BIOS-controlled) mitigations that proactively refresh suspected victim rows.
RFMRefresh Management — DDR5's stricter refresh-based Rowhammer defense, doubling refresh rate under pressure.
AIBActivation-induced bit flip — the formal term for a Rowhammer bit flip.
MACMaximum Activation Count — a DIMM's claimed Rowhammer tolerance rating; the paper notes all tested DIMMs claim "unlimited," derived from weaker load-based testing.
ROB / BTB / PHTReorder buffer (tracks in-flight instruction order) / branch target buffer / pattern history table — the OoO and branch-prediction structures ρHammer's counter-speculation targets.
LFBLine Fill Buffer — where a prefetch's pending request lives in L1-D while the CPU continues executing.
PREFETCHhThe x86 software prefetch instruction family (T0/T1/T2/NTA); ρHammer primarily uses PREFETCHT2/NTA.
PTE corruptionFlipping a bit inside a page table entry to gain unauthorized memory access — the paper's end-to-end exploitation target, via the Rubicon massaging technique.
