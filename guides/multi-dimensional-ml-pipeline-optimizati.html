CXL / NUMA Memory Tiering · A Field Guide

Don't binary-search the memory tier — let a Gaussian process do it

Every ML inference pipeline on a CXL-attached NUMA box hides a knob per stage: what fraction of its pages sit in local DRAM vs. the CXL pool, and how many threads to run. This paper turns that knob-per-stage into one continuous, SLA-constrained search problem — and answers it from inside the kernel, with Bayesian Optimization, in minutes instead of hours.

📄 Huo et al., MICRO '25 (Seoul) 🎓 Assumes you know NUMA, CXL.mem, and page placement ⏱ ~40 min read
🎛️

Model each pipeline stage's DRAM:CXL ratio and the thread count as one vector, let a Bayesian-Optimization core search it under an SLA-penalized objective (Phase 1), then hand the top-k configs to a Pareto-optimality pass that trades a little throughput for real power savings (Phase 2) — all measured by an eBPF monitor that lives in kernel space so watching costs almost nothing.
The knob was always there. The paper's contribution is refusing to tune it by hand.

Before you begin

Nine ideas this paper builds on

You already know NUMA and CXL memory pooling, so these skip straight to the paper's specific machinery: the weighted-interleave knob, eBPF as a monitor, and why Bayesian Optimization — not a trained model, not binary search — is the right tool for this exact search problem. Tap any open; read in order the first time.

1CXL as "just another NUMA node" — and why that's the whole trick▾

CXL.mem's Home Agent presents attached memory to the OS as ordinary NUMA-node memory, reachable by normal load/store — no new syscalls. The paper's Figure 1 puts local DRAM access at roughly 80–140 ns and the CXL/remote path at roughly 170–250 ns. Because it's "just a node," every existing NUMA tool — numactl, cpubind/membind, interleaving — already applies to it.

Now you're ready: the entire optimization problem in this paper is really "how many pages on node 0 (DRAM) vs. node 1 (CXL)" — a page-placement ratio, not a new abstraction.
2The literal knob: weighted interleave▾

Linux 6.9 added weighted interleave: instead of plain round-robin interleaving (50:50), you set an explicit N:M ratio between NUMA nodes, and the page allocator enforces that ratio when placing new pages. The paper writes this into /kernel/mm/weight_interleave and drives it via numactl --weight_interleave=N,M.

Now you're ready: every "Stage[N:M]" you'll see in this guide means exactly that — N parts of that stage's pages go to local DRAM, M parts to CXL, committed through this one sysfs-style interface.
3An ML pipeline is a DAG of "stages," each wanting a different ratio▾

DLRM = Bottom MLP → Top MLP → Sparse-Length-Sum (embedding) stages; Stable Diffusion = encoder → ViT/U-Net → decoder. The paper's running example (its "C1" challenge): a compute-intensive stage (DenseNet-like) wants low-latency local DRAM, while a bandwidth-intensive stage (SparseNet-like, or DLRM's embedding lookup) wants CXL's extra pooled bandwidth.

Now you're ready: one system-wide NUMA policy can't be optimal for a pipeline whose stages disagree about what they want — the search vector must have one ratio per stage.
4eBPF, compressed to the essentials▾

eBPF programs attach to kernel events (syscalls, tracepoints, kprobes), are JIT-compiled to native code, and exchange data with user space through BPF maps (per-CPU hash maps, perf event arrays, ring buffers) instead of triggering a context switch per event. That's the whole reason it's used here instead of a traditional profiling daemon.

Now you're ready: "monitor in kernel space" isn't a stylistic choice — it's how the paper avoids the 2–8× overhead the paper attributes to daemon-based tools like auditd.
5The search space, and why it explodes▾

Each stage's DRAM:CXL ratio ranges from 1:100 to 100:1; thread count ranges 1–192. The paper states plainly: a 3-stage pipeline over just the ratio dimension already gives a search space of 100³; adding thread count for even a modest number of stages pushes it "over 1 million combinations." Brute force — or 1990s-style binary search over one ratio at a time — is not viable here.

Now you're ready: this is challenge C1 in the paper's own framing — a genuinely high-dimensional, continuous-ish, nonlinear space, not the small 1-D space that prior binary-search approaches (e.g., Caption) were built for.
6Bayesian Optimization, in one paragraph▾

BO fits a Gaussian Process surrogate model, f(x) ~ GP(μ(x), k(x,x')), over the (expensive-to-evaluate) objective, then uses an acquisition function to pick the next point to actually try — trading off "likely good" (exploitation) against "uncertain, could be great" (exploration). The paper uses Expected Improvement: α_EI(x) = E[max(0, f(x) − f_best)].

Now you're ready: BO needs only a handful of real measurements (each one is a live deployment!) to model the whole space — unlike DQN/RL, which needs far more training data than a per-workload tuner can afford.
7SLA-aware objectives: hard vs. soft penalty▾

The naive objective zeroes out any configuration that violates the latency SLA: f(x)=QPS(x) if L_max(x) ≤ L_SLA, else 0. That's overly punitive — a config that misses the SLA by a hair gets thrown away even if it's otherwise excellent. The paper's fix is a soft penalty: f(x) = QPS(x) · exp(−λ·max(0, L_max(x) − L_SLA)), which decays smoothly instead of cutting off.

Now you're ready: the objective the optimizer actually maximizes already has the SLA baked in — "maximize throughput" in this paper always means "maximize throughput, discounted for how close you are to breaking the SLA."
8Pareto optimality, for the second phase▾

Phase 2 is a genuinely different objective: minimize power at a tolerable throughput cost. A configuration is Pareto-optimal if you cannot improve one objective (power) without worsening the other (QPS). The output isn't a single "best" answer — it's a frontier of tradeoffs, from which an operator picks a point.

Now you're ready: Phase 1's job is "find the best throughput"; Phase 2's job is "given several near-best throughput configs, find which one is also power-cheap" — two different searches, chained.
9Why the prior art falls short (the paper's C1–C3)▾

C1 — limited search space: Caption's binary search adjusts one CXL-allocation ratio at a time and can converge to a local minimum in a high-dimensional space. C2 — lack of generality / high overhead: vendor tools (Intel PCM, AMD uProf) don't cross platforms, and daemon-based monitors (sysdig, auditd) cost 2–8× overhead. C3 — unawareness of dynamic behavior: datacenter load shifts bottleneck type (compute-bound ↔ bandwidth-bound) through the day; prior "outlier"/"noisy-neighbor" detectors don't adapt continuously.

Now you're ready: the paper's four contributions map 1:1 onto these three gaps — that mapping is the spine of the next tab.
The whole story in one place

The paper in a nutshell

The problem, the two-phase framework that solves it, and why Bayesian Optimization specifically wins against the space's usual competitors.

CPUs still run most lightweight inference in datacenters — the paper cites roughly 70% of such workloads — and increasingly they sit on NUMA hosts with CXL-attached memory as an extra, bandwidth-heavy but higher-latency tier. Every multi-stage ML pipeline (DLRM's MLPs and embedding lookups; Stable Diffusion's encoder/ViT/U-Net/decoder) then has, per stage, a page-placement ratio between local DRAM and CXL, plus a global thread count. Getting this right by hand — or with a binary search built for a much smaller space — doesn't scale: the paper measures search spaces exceeding a million configurations even for modest pipelines.

The paper's answer is a two-phase, self-adaptive auto-tuner. An eBPF-based monitor lives entirely in kernel space, hooking per-thread execution via bpf_get_current_pid_tgid()/bpf_ktime_get_ns() and tracking per-stage memory allocation via kmalloc events — so it can compute QPS and coordinate stage transitions without expensive kernel↔user context switches (measured at 4.7% overhead vs. 25.1% for the Linux auditd baseline). Those measurements feed Optimization Phase 1: a customized Bayesian Optimization core that treats the configuration vector x = (w₁,…,wₙ,t) — one DRAM:CXL weight per stage plus one thread count — as a black-box function to maximize, subject to an SLA-penalized objective. The resulting top-k throughput configurations then feed Optimization Phase 2, which applies Pareto optimality to trade a small amount of throughput for real power savings, because CXL's power profile relative to DRAM is genuinely ambiguous (it depends on DDR generation and refresh-rate vs. voltage effects) and hand-picking the power-efficient point isn't obvious.

The upshot: across DLRM, Stable Diffusion, LPQ, Amber Alert, Video QA, and a synthesized OLAP workload, the BO-driven framework reaches 90% of a 27,000-configuration pseudo-exhaustive baseline's throughput at just 23% of its search cost (5–17 minutes), beats a state-of-the-art CXL binary search (Caption), PSO, and a Genetic Algorithm at every search budget, and — against TPP and plain NUMA interleaving on real-world traces — delivers up to 48% higher QPS with far fewer SLA violations, plus up to 7.3% (CXL-preferred power model) or 4.2% (DRAM-preferred model) power savings at a small throughput cost from Phase 2. (The paper's abstract separately states "up to 14.3% power savings" — flagged as a discrepancy in Reference § Source notes; the number reproduced in the body text and Figure 11 discussion is 7.3%.)

🍯 Key takeaways

  • Config vector x = (w₁,…,wₙ,t): one DRAM:CXL weight per pipeline stage, plus one global thread count.
  • Two phases, two objectives: Phase 1 (BO) maximizes SLA-penalized QPS; Phase 2 (Pareto) trades some QPS for power.
  • eBPF monitor runs entirely in kernel space: 4.7% overhead vs. 25.1% for auditd, transferring only 96 bits/event, batched 16 at a time.
  • BO hits 90% of a 27,000-config pseudo-exhaustive baseline's throughput at 23% search cost — 5–17 minutes across workloads.
  • Against Caption/TPP/NUMA-interleave baselines: up to 48% higher QPS, up to 77% lower search cost, up to 7.3% power savings (CXL-preferred model).
  • Weighted interleave (Linux 6.9) turns "CXL is just another NUMA node" into a literal, per-stage N:M ratio the optimizer can dial.
  • Not a GPU-replacement pitch: the paper explicitly reserves GPUs for compute-heavy, high-load workloads (LLMs, Stable Diffusion at scale) when budget allows.
Six everyday pictures

How to think about the framework

Each picture stands alone — read in any order. Every card ends with an honest note about where the analogy stops being true.

The literal knob · weighted interleave

The two-tap mixing valve

Weighted interleave is a kitchen faucet with a hot (DRAM) and cold (CXL) tap and one dial that sets the mix — not a binary "hot or cold" switch, and not a fixed 50:50 mixer like plain NUMA interleaving. Set it to 99:1 for a latency-picky stage, 29:71 for a bandwidth-hungry one. Every "Stage[N:M]" in the paper is one setting of one such valve, and a pipeline has one valve per stage.

Where it breaks: a real mixing valve responds instantly; the OS's version has to actually place new pages under the new ratio, so changing a stage's mix mid-flight requires waiting for that stage's allocation to complete first (the paper's inter-stage semaphore handshake) — you can't just spin the dial while water is running.
The engine · Bayesian Optimization

The blindfolded taste tester with a notebook

Imagine tasting a soup with an unknown, adjustable spice ratio, but every taste costs you a real production deployment. A brute-force cook tries every ratio in order. BO's taster instead keeps a notebook (the GP surrogate) of every taste so far, sketches a confidence curve over the untried ratios, and always samples wherever the curve says "probably great, or I truly don't know yet" — never wasting a taste in a region already known to be mediocre.

Where it breaks: a real taster's notebook doesn't need calculus; the GP's confidence curve is a genuine probability distribution that gets recomputed (not just glanced at) after every single taste — that recomputation is exactly what a trained RL model can't afford to redo per new workload.
The monitor · eBPF vs. daemon tools

The in-house auditor vs. the outside inspector

An outside inspector (auditd/sysdig) has to badge in through the front door every time they want to check something — a context switch, a real cost, every event. eBPF is an auditor who already lives in the building (JIT-compiled kernel code), scribbling notes on the office whiteboard (BPF maps) and only occasionally walking a stack of notes over to the user-space team, in batches.

Where it breaks: the in-house auditor still isn't free — the paper measures 4.7% overhead, not 0%. "Lives in the building" reduces the tax; it doesn't eliminate it, and the batching (16 events/transfer, 96 bits/event) is a deliberate design choice, not a law of nature.
The tradeoff · Pareto optimality

Trading the V8 for the V6

You're not looking for the single "best" car — you're looking at a lineup where every model that's cheaper to run also happens to be slower, and vice versa. The V6 trim saves real fuel for a bit less horsepower; the true V8 is fastest but drinks the most. Every trim on the lineup is defensible; a trim that's both slower and thirstier than another one isn't — that's what falls off the Pareto frontier.

Where it breaks: car trims are fixed by the manufacturer; the paper's Pareto frontier is discovered empirically from whatever configurations Phase 1 already evaluated, so it's only as complete as that sample — a genuinely better tradeoff point that Phase 1 never tried simply won't appear on the frontier.
The objective · soft SLA penalty

A late fee that scales with how late you are

A hard SLA penalty is a library that burns your book the instant it's overdue, even by a minute — full value one second, zero the next. A soft penalty is a normal late fee: a little late costs a little, very late costs a lot, but a barely-late return that was otherwise a fantastic loan isn't thrown away entirely. That's exactly the shape of QPS(x)·exp(−λ·max(0, L_max−L_SLA)) — smooth decay, not a cliff.

Where it breaks: a library late fee is capped; the exponential penalty keeps shrinking toward (but never quite reaching) zero, so a config that's wildly over the SLA still contributes an infinitesimally positive score rather than being formally excluded — which is why the paper also offers the hard-constraint formulation (max QPS(x) subject to L_max(x) ≤ L_SLA) as an alternative.
The failure mode · local minima

Hill-climbing in fog

A step-and-adjust binary search (Caption) is a hiker in dense fog who only feels the slope underfoot: step, check if it's higher, keep going the same way if yes, reverse with a smaller step if no. That hiker can absolutely summit a nearby hill and declare victory — with no idea a taller mountain sits just past the valley they'd have to cross to find it. BO instead builds a rough map of the whole range (the GP surrogate) before committing to a direction.

Where it breaks: the fog-bound hiker's algorithm is cheap — one step per taste; BO's mapmaking costs real computation between samples (fitting/updating the GP). The paper's tradeoff is explicitly "spend a bit more thinking per sample to spend far fewer samples overall" — not a free lunch, a different budget.
Section by section

How the framework actually works

Problem formalization → the eBPF data path → Phase 1 (Bayesian Optimization) → Phase 2 (Pareto power) → from optimizer output to a running numactl command.

1 · Problem formalization

The system models an ML pipeline as n stages C = {c₁,…,cₙ}. Each stage cᵢ has a weight wᵢ ∈ [w_min, w_max] — its DRAM:CXL allocation ratio — and the whole system shares one thread-count parameter t ∈ [t_min, t_max]. The full configuration vector is x = (w₁,…,wₙ,t). Let Q(x) be throughput (QPS) and L(x) be latency under configuration x. The constraints are exactly what you'd expect: L(x) ≤ L_SLA, each wᵢ within its bounds, and t within its bounds. The goal is to maximize Q(x) subject to those constraints — a continuous, high-dimensional, non-linear, constrained optimization problem.

◆
Why not a trained model (DQN/RL)? The paper's stated reasoning: the search space is continuous and demands a large volume of training data, and training a fresh model per new workload is both inefficient and impractical for a system meant to adapt to whatever pipeline shows up. BO instead models the objective directly from a small number of live measurements — no training corpus required.

2 · The eBPF data path

The monitor bootstraps into the kernel, attaches to all NUMA cores, and spawns an instance timer per application thread. For the target function, it calls bpf_get_current_pid_tgid() for per-thread identification and bpf_ktime_get_ns() to time execution, from which QPS is derived (execution time × batch size). Separately, it tracks kmalloc events to know when a pipeline stage has finished its memory allocation — the signal that it's safe to change the NUMA configuration for the next stage without corrupting the current one's in-flight allocation. Stage-to-stage handoff itself uses POSIX semaphores (sem_init/sem_wait/sem_post) over shared memory: a producer stage posts after writing intermediate data, the consumer stage waits before reading it.

3 · Phase 1 — Bayesian Optimization

The optimizer treats the objective as a black box: it observes tuples ⟨Stage₁[N:M], Stage₂[N:M], t, Q(x)⟩, fits a Gaussian Process surrogate f(x) ~ GP(μ(x), k(x,x')) over them, and uses the Expected Improvement acquisition function α_EI(x) = E[max(0, f(x) − f_best)] to choose the next configuration to actually deploy and measure. Because sampling is adaptive rather than a fixed grid, BO might probe ratios at steps like 1, 37, 67 instead of sweeping 1, 25, 50, 75, 100 — concentrating measurements where the surrogate model expects them to matter. Thread-count effects are handled the same way: BO has no built-in notion that "more threads eventually hurts," but once it observes a performance drop past some thread count, that observation is folded straight into the GP and future sampling avoids that region.

SLA compliance is enforced through the objective itself (Primer 7): either the smooth penalty f(x) = Q(x)·exp(−λ·max(0, L_max(x) − L_SLA)), or, equivalently, a hard-constrained formulation that prunes any SLA-violating configuration from consideration outright. Each candidate configuration is evaluated by actually deploying it and sampling N (default 10) throughput measurements per stage — this is why each BO iteration has real wall-clock cost, and why minimizing the number of iterations (not just finding a good answer eventually) is a first-class design goal.

4 · Phase 2 — Pareto power optimization

Once Phase 1 has identified strong-throughput configurations, Phase 2 reformulates the problem as multi-objective: maximize QPS while minimizing power, still under the SLA constraint. Power modeling for CXL is genuinely uncertain, so the paper evaluates both directions: a CXL-preferred model where DDR4-based CXL's lower refresh rate dominates and it costs only 90% of DDR5 DRAM's power, and a DRAM-preferred model where DDR4's higher supply voltage (1.2V vs. DDR5's 1.1V) plus CXL-interface overhead dominates instead, costing 1.1× DRAM's power. The Pareto frontier is then traced over the throughput-optimal configurations already found by Phase 1, and an operator (or the framework, given a power budget) picks a point on it.

●
Why bother with two separate phases instead of one combined objective? Phase 1's job (find near-peak throughput) and Phase 2's job (find where power can be shaved without much throughput loss) use genuinely different objective shapes and act on a much smaller candidate set in Phase 2 — it explores the Pareto frontier only among Phase 1's already-good configurations, rather than re-searching the whole space with a blended objective from scratch.

5 · From optimizer output to a running command

Once a configuration is selected, its parameters map directly onto system mechanisms: the target N:M ratios are written into the kernel's weighted-interleave interface, which the kernel reads back and uses to program each NUMA node's per-core allocation weights; the page allocator then enforces an N:M round-robin policy across nodes for new pages. The optimizer emits an actual shell command — numactl --weight_interleave=0,1 --cpunodebind=0 app_name — and a generated shell script configures each stage's page-mapping behavior via echo commands into the kernel interface, with the thread parameter t determining how many threads are launched and bound to cores.

◇
Overhead accounting, so the "low-overhead" claim isn't hand-waved. Shared-memory setup for inter-stage handoff (shm_open, ftruncate, shm_unlink, mmap) completes in under 7 ms — about 2% of DLRM's stated 0.4 s SLA. The eBPF monitor itself costs 4.7% vs. 25.1% for auditd. Both costs are paid continuously during normal operation, separate from — and much smaller than — the one-time cost of a BO search converging (minutes, per §4.1.2).
Put real numbers on it

Worked examples

Five calculations grounded in the paper's own numbers, then an interactive widget for the SLA soft-penalty. All arithmetic is shown; anything not directly stated in the paper is marked illustrative.

Example 1 — the search space, two ways

The paper gives the DRAM:CXL ratio range as 1:100 to 100:1 (≈100 discrete values per stage) and the thread range as 1–192.

  1. Ratio-only, 3 stages (§2.5.2): 100 × 100 × 100 = 100³ = 1,000,000 combinations — matches the paper's own "search space of 100³" statement, before thread mapping is even considered.
  2. Ratio + threads, 2 stages (§3.5): 100 × 100 × 192 = 1,920,000 combinations — consistent with the paper's claim that "N model units … already creates over 1 million combinations" once thread count is folded in, even for modest N.
  3. The point: both readings clear a million configurations well before you've modeled a realistic 3+-stage pipeline with thread tuning — brute force was never viable, and neither was a 1-D binary search built for a single ratio.
◆
Takeaway: the exact multiplier (100³ vs. ~1.9M) depends on exactly which dimensions you fold in — but every reasonable reading the paper offers lands at "well over a million," which is the qualitative point it's making with C1.

Example 2 — how far BO's efficiency actually goes

The paper's baseline is a 27,000-configuration pseudo-exhaustive sweep (itself "a small fraction" of the ~10⁹ theoretically possible configurations). BO reaches 90% of that baseline's throughput at 23% search cost.

  1. Configurations actually evaluated: 23% × 27,000 = 6,210 configurations — not 27,000, and nowhere near 10⁹.
  2. As a fraction of the ~10⁹ theoretical space: 6,210 / 10⁹ ≈ 0.0006% of the full space, for 90% of the near-exhaustive throughput.
  3. Wall-clock: the paper reports this 90%-throughput point is reached in 5–17 minutes across the studied workloads — i.e., each of those ~6,210-scale evaluations corresponds to real, fast, live deployments, not a simulation.
▲
Misconception it kills: "search cost %" in the paper's Figure 6 is relative to the 27K pseudo-exhaustive baseline, not the full ~10⁹ combinatorial space — don't read "23% search cost" as "searched 23% of everything possible."

Example 3 — eBPF's overhead advantage, recomputed

Measured overheads (§4.1.1): eBPF 4.7%, Linux auditd 25.1%. Data volume: 96 bits/event (32-bit pid + 64-bit QPS), default batch size 16.

  1. Overhead ratio: 25.1% / 4.7% ≈ 5.34× — matches the paper's contributions claim of "over 5× less overhead than traditional Linux daemon-based tools."
  2. Bits per batched transfer: 16 events × 96 bits = 1,536 bits = 192 bytes moved across the kernel/user boundary per transfer, instead of 16 separate context switches.
  3. Why this matters for the optimizer, not just the app: the monitor's own overhead is paid on every query while BO is searching — a 5.3× cheaper monitor doesn't just look good in a table, it means the throughput numbers BO is optimizing against are less polluted by the act of measuring them.

Example 4 — SLA soft-penalty vs. hard-penalty, side by side

Formulas from §3.6.2: hard penalty f(x) = Q(x) if L_max ≤ L_SLA else 0; soft penalty f(x) = Q(x)·exp(−λ·max(0, L_max−L_SLA)). Take an illustrative L_SLA = 0.4 s (the paper's stated DLRM SLA), Q(x) = 5,000 QPS, and λ = 15 — the paper does not specify a value for λ, so this walkthrough picks one for arithmetic clarity.

  1. Config A, L_max = 0.39 s (under SLA): hard penalty keeps 5,000; soft penalty also keeps the full 5,000 (no excess latency, so the exponent is 0).
  2. Config B, L_max = 0.42 s (20 ms over): hard penalty zeroes it out — 0 QPS, discarded entirely. Soft penalty: 5,000 × exp(−15 × 0.02) = 5,000 × exp(−0.30) ≈ 5,000 × 0.741 ≈ 3,704 — a real, comparable score.
  3. Config C, L_max = 0.55 s (150 ms over, badly violating): hard penalty still 0. Soft penalty: 5,000 × exp(−15 × 0.15) = 5,000 × exp(−2.25) ≈ 5,000 × 0.1054 ≈ 527 — small, but non-zero.

Example 5 — which power model "pays off" more per unit of throughput given up?

Section 4.2: CXL-preferred saves 7.3% power for 4.5% QPS sacrificed; DRAM-preferred saves 4.2% power for 2.7% QPS sacrificed.

  1. CXL-preferred "exchange rate": 7.3 / 4.5 ≈ 1.62% power saved per 1% QPS given up.
  2. DRAM-preferred "exchange rate": 4.2 / 2.7 ≈ 1.56% power saved per 1% QPS given up.
  3. Reading it: the two rates are close (1.62 vs. 1.56), but CXL-preferred offers a larger absolute power-savings ceiling (7.3% vs. 4.2%) for a correspondingly larger throughput sacrifice — which model actually applies to a given deployment depends on real DDR generation and voltage/refresh characteristics the paper says are hardware-specific, not something the framework can assume.
Check yourself

Practice

Work the answer before opening it. Each answer ends with the misconception the question is designed to catch.

Warm-up
A pipeline has 2 stages, each with a DRAM:CXL ratio range of 1:100 to 100:1 (≈100 discrete values), and a thread range of 1–192. How many total configurations are in the search space, and does this clear "over a million"?
Show answer
100 (stage 1 ratio) × 100 (stage 2 ratio) × 192 (threads) = 1,920,000 configurations — yes, well over a million, matching §3.5's claim for even modest pipelines. Catches: assuming "only 2 stages" means a small space. The thread dimension alone (192 values) is enough to push a 2-stage pipeline past a million combinations.
Diagnose
In Figure 6, Caption's throughput starts around 75–82% at moderate search cost but falls to 16–41% at the highest search cost — it gets worse with more search budget. Why would a search algorithm perform worse with more time, and why doesn't BO have this problem?
Show answer
Caption is a 2-D binary search: it adjusts the CXL allocation percentage with a step-and-reverse rule (continue if performance improves, reverse with a smaller step if it degrades). In the paper's genuinely high-dimensional space (per-stage ratios × threads), that local, greedy rule can walk itself into a local minimum and keep refining around it — more iterations just polish a bad answer. BO avoids this because its Gaussian Process surrogate models the whole space from all past observations, so its next sample is chosen for expected global improvement, not local slope-following. Catches: assuming "more search iterations" is monotonically good for any algorithm. It's only true for algorithms that use the extra budget to look more broadly, not ones that just refine a local direction.
Diagnose
Batch size for eBPF map updates defaults to 16, and each event is 96 bits. Someone proposes setting batch size to 1 "for freshness." What does the paper's own reasoning say this would cost, concretely?
Show answer
Batch size 1 means every single 96-bit event triggers its own bpf_perf_event_output() transfer instead of amortizing 16 events into one — which reintroduces exactly the per-event kernel↔user crossing overhead the batching was designed to avoid (the same class of cost that makes daemon-based tools like auditd measure 25.1% overhead vs. eBPF's 4.7%). It wouldn't be as bad as auditd (no full context switch, still eBPF-native), but it gives up a real, deliberate design choice for a freshness benefit the paper never claims BO's iteration cadence actually needs. Catches: treating "in-kernel" as automatically free regardless of transfer frequency. The mechanism (eBPF) reduces overhead; the batching policy (16 events/transfer) is what actually amortizes it, and the two are separate levers.
Design
The paper's C1 example: in a DLRM-like pipeline, one stage is compute-intensive (wants low-latency local DRAM) and another is bandwidth-intensive (wants CXL's pooled bandwidth). Explain concretely why a single, system-wide NUMA interleave policy (as opposed to the paper's per-stage weighted interleave) cannot be Pareto-optimal for both stages simultaneously.
Show answer
A system-wide policy sets one ratio for the whole process — say a 50:50 interleave. The compute-bound stage would prefer close to 100:0 (all local DRAM, minimizing per-access latency since it isn't bandwidth-starved); the bandwidth-bound stage would prefer something closer to 30:70 or lower (leaning on CXL's pooled bandwidth to avoid saturating local DRAM channels). Any single system-wide ratio is a compromise that under-serves at least one stage relative to what a per-stage ratio could achieve — which is precisely why the paper's configuration vector x = (w₁,…,wₙ,t) has one weight per stage, not one weight for the whole pipeline, and why the eBPF monitor tracks per-stage kmalloc completion to safely retarget each stage's NUMA configuration independently. Catches: assuming "NUMA interleaving is good" is a single fact rather than a per-workload, even per-stage, tradeoff. The paper's entire architecture exists because "good" here is stage-dependent.
Design
The paper models CXL power two ways: CXL-preferred (CXL costs 90% of DDR5 DRAM's power, refresh-rate effects dominate) and DRAM-preferred (CXL costs 1.1× DRAM's power, voltage/interface overhead dominates). Why does the framework need to support both models rather than picking the physically "correct" one?
Show answer
The paper is explicit that which effect dominates — DDR4-based CXL's lower refresh rate (saves power) vs. its higher supply voltage and CXL-interface overhead (costs power) — depends on the specific CXL implementation and DDR generation in a given deployment, and can genuinely go either direction. There isn't one "correct" model across all hardware; a framework that hardcodes one assumption would give wrong power-optimization guidance on hardware where the other effect dominates. Supporting both models lets Phase 2's Pareto search be re-parameterized per deployment rather than re-derived from scratch. Catches: assuming "CXL uses cheaper DDR4, so CXL is more power-efficient" as a universal law. The paper's own DRAM-preferred model is a direct counterexample it takes seriously enough to evaluate.
Loose ends

Frequently asked

The questions that come up once the two-phase mechanism clicks.

QIs this the same thing as TPP, or Pond, or Memstrata?▾
No — related, but different layers. TPP [40] is a page-placement/promotion mechanism the paper directly compares against as a real-world baseline (and beats by up to 48% QPS, 23.9% lower average latency). Pond [37] and Memstrata [85] are capacity-driven memory-pooling systems for multi-VM environments, allocating remote memory until performance drops — the paper notes (§2.5.3) they don't target bandwidth-intensive workloads like model inference, which is exactly this paper's focus. Caption [69] is the closest prior CXL-tuning approach and is the paper's main search-algorithm baseline (the binary search compared throughout §4.1).
QWhy not just train an RL agent (DQN) once and reuse it everywhere?▾
The paper's stated reasoning (§3.6): the configuration space is continuous and RL-style training methods need a large volume of training data, so training a fresh model per new workload is impractical for a system meant to handle whatever pipeline shows up next. BO instead builds its model directly from a handful of live measurements of the workload in front of it — no offline training corpus, no assumption the new workload resembles past ones.
QWhat does "weighted interleave" give you that plain numactl --interleave doesn't?▾
Plain NUMA interleaving is round-robin — effectively a fixed 50:50 split (or equal split across however many nodes are listed). Weighted interleave (Linux 6.9) lets you set an explicit N:M ratio, so a stage can lean 99:1 toward local DRAM or 29:71 toward CXL — the fine-grained control the paper's per-stage optimization actually needs. It's also vendor-agnostic, unlike NPS-mode-style hardware partitioning.
QDoes this mean CPUs beat GPUs now?▾
Not as a blanket claim — the paper is careful here (§5.1). It argues CPU+CXL inference wins on cost and throughput specifically for: bandwidth-intensive stages, lightweight ML mixed with non-ML stages, low-load or intermittent pipelines, and budget-constrained deployments (17–19× better cost-efficiency for DLRM at batch sizes 8–64, in the paper's tenant-cost analysis). For compute-intensive, high-load workloads — LLMs, Stable Diffusion at scale — it explicitly recommends GPUs when capital budget allows.
QHow expensive is running the optimizer itself, on top of the app?▾
Two separate costs, both small. Steady-state monitoring: eBPF overhead of 4.7% (vs. 25.1% for auditd), and inter-stage shared-memory handoff under 7 ms (~2% of DLRM's 0.4 s SLA). One-time search cost: BO reaches 90% of near-exhaustive throughput at 23% search cost — 5 to 17 minutes across the studied workloads, not hours.
QIs the power savings 14.3% or 7.3%? The paper seems to say both.▾
This guide flags it as a genuine discrepancy rather than silently picking one. The abstract states "up to 14.3% power savings"; the intro's contributions list and §4.2's actual Pareto-frontier discussion report a maximum of 7.3% (CXL-preferred model, at a 4.5% QPS cost) and 4.2% (DRAM-preferred model, at a 2.7% QPS cost). No passage in the body text reproduces "14.3%." Treat 7.3% as the number backed by the paper's own detailed results; see Reference § Source notes.
QDoes this extend to NVM or other tiers — relevant to LtRAM-style multi-tier memory?▾
Forward-looking, not evaluated in this paper. §5.3 states the framework "can be readily extended to accommodate such heterogeneous memory configurations, since our algorithms are designed based on a high-dimensional search space," explicitly naming NVM and SSD as CXL-attachable device types, with the OS treating each as a NUMA memory node with its own latency configuration. No NVM/SSD experiments are reported — this is discussion, not a result, but it's the paper's own stated generalization path and lines up with a DRAM/NVM/CXL tiering research agenda.

Glossary, a dated summary card, further reading, and the honest provenance notes.

Core terms
QPSQueries Per Second — the paper's primary throughput metric, computed from per-thread execution time and batch size via the eBPF monitor.
SLA / P99 latencyService Level Agreement on latency; P99 is the 99th-percentile (worst-case-ish) latency, the metric used to judge whether a config is acceptable, not just fast on average.
Weighted interleaveLinux 6.9 NUMA feature: an explicit N:M page-placement ratio between nodes, set via numactl --weight_interleave, enforced by the page allocator.
Stage[N:M]The paper's notation for one pipeline stage's DRAM:CXL allocation ratio — the per-stage unit the optimizer searches over.
Bayesian Optimization (BO)Phase 1's search method: a Gaussian Process surrogate plus an acquisition function, used to find near-optimal configs in far fewer evaluations than brute force.
Gaussian Process (GP) surrogatef(x) ~ GP(μ(x), k(x,x')) — the probabilistic model BO fits over observed (config, throughput) pairs to predict unobserved configs.
Expected Improvement (EI)The acquisition function used here: α_EI(x) = E[max(0, f(x) − f_best)], balancing exploring uncertain regions against exploiting known-good ones.
Pareto frontier / optimalityPhase 2's output: the set of configs where QPS can't be improved without hurting power (or vice versa) — a set of tradeoffs, not one answer.
Supporting terms
eBPFExtended Berkeley Packet Filter — JIT-compiled kernel programs attached to kernel events; the paper's monitoring substrate, chosen for low, hardware-agnostic overhead.
BPF maps / perf event arrayKernel-resident data structures eBPF uses to store metrics and batch-transfer them to user space via bpf_perf_event_output().
kmalloc trackingHow the monitor detects that a pipeline stage has finished allocating memory — the signal it's safe to retarget the NUMA config for the next stage.
CXL-preferred / DRAM-preferredThe paper's two power models for CXL memory: 90% of DDR5 DRAM's power (refresh-rate dominated) vs. 1.1× DRAM's power (voltage/interface-overhead dominated).
Caption [69]Prior CXL-tuning baseline using a binary-search-like algorithm over a single CXL-allocation ratio; the paper's main search-algorithm comparison point.
TPP [40]"Transparent Page Placement" — a real-world page-placement baseline for CXL-tiered memory, compared against in the paper's real-trace evaluation (§4.1.4).
NUMA Interleave (NI)The classic 50:50 round-robin interleaving policy, used as a simpler baseline alongside TPP.
PPW optimizationLabel appearing in the paper's Figure 4 for the power-aware allocation step inside Phase 2; the paper does not spell out the acronym in the source text — noted here as uncertain rather than guessed.

📌 Summary card · as of 2026-08-30 · MICRO '25

  • What: a two-phase auto-tuner that finds, per ML-pipeline stage, a DRAM:CXL page-placement ratio plus one thread count, using Bayesian Optimization (throughput, SLA-constrained) then Pareto optimality (power).
  • Why: the search space exceeds a million configurations even for modest pipelines; prior binary search (Caption) converges to local minima there; vendor tools and daemon monitors don't generalize or are too costly.
  • Monitor: eBPF, entirely in kernel space — 4.7% overhead vs. 25.1% for auditd (~5.3× less), 96 bits/event, batched 16 at a time.
  • Phase 1: GP surrogate + Expected Improvement over x=(w₁,…,wₙ,t), SLA baked into the objective via a soft exponential penalty (or a hard constraint, alternatively).
  • Phase 2: Pareto frontier over Phase 1's best configs, trading QPS for power under two competing CXL power models.
  • Headline results: 90% of a 27K-config pseudo-exhaustive baseline's throughput at 23% search cost (5–17 min); up to 48% higher QPS and 77% lower search cost vs. TPP/NI/Caption/GPU baselines; up to 7.3% (CXL-preferred) or 4.2% (DRAM-preferred) power savings.
  • Real-trace results (§4.1.4, DLRM): 23.9% lower average latency vs. TPP, 6.1% lower vs. NI; P99 latency 0.39 s (45.5% better than TPP, 24.7% better than NI); SLA violations 4.76% vs. TPP's 28.9% and NI's 16.45%.
  • Not a GPU-replacement claim: CPU+CXL wins for bandwidth-bound, lightweight, low-load, or budget-constrained workloads; GPUs still recommended for compute-heavy, high-load workloads (LLMs, Stable Diffusion) when budget allows.
  • Discrepancy flagged: abstract says "up to 14.3%" power savings; §4.2's actual results max out at 7.3% — see Source notes.
  • Forward-looking: the paper states (not evaluates) extension to NVM/SSD-based heterogeneous memory, multi-tenancy, and GPU/XPU nodes via CXL Type 2.
