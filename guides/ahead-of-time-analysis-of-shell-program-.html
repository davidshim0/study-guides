SOSP 2026 · A Field Guide

Finding the rm -rf /* before it runs

Shell scripts quietly delete home directories, wipe drives, and brick systems — not from malice, but from an empty variable or a failed cd. This is the plain-English story of SaSh, a system that symbolically runs your script ahead of time and flags the disaster before you do.

📄 "Ahead-of-Time Analysis of Shell Program Effects" · Lazarek et al. 🎓 Basic shell scripting assumed — the primers cover the rest ⏱ ~30 min read
🐚

Warn only about behavior that's dangerous even in the program's own best case — not every theoretically possible failure.

1Why the shell is uniquely dangerous▾

Almost every shell command can fail without stopping the script — no exceptions, no crashes, just quiet continuation with whatever state resulted. That's flexible, but it means a script can sail through an error state (like an empty variable) straight into something catastrophic, like deleting /*.

Now you're ready: SaSh's entire job is to notice these "quiet continuations" that lead somewhere bad, before the script actually runs.
2Word expansion, in one sentence▾

Before the shell runs a command, it rewrites the raw text: ~ becomes your home directory, $VAR becomes a value, $(cmd) becomes that command's output, *.txt becomes matching filenames — and then the result gets split into separate words wherever $IFS characters (usually spaces) appear. This whole process is called expansion.

Now you're ready: Expansion is dynamic and largely unknowable ahead of time — SaSh's whole "abstract expansion domain" (§5) exists to reason about it anyway, approximately.
3Field splitting — the classic bug source▾

If a variable's value contains a space, e.g. X="my path/", then rm $X (unquoted) doesn't pass one path — the shell splits it on the space, and rm receives two separate arguments: my and path/. Quoting (rm "$X") prevents this.

Now you're ready: "Dangerous word split" is one of SaSh's eight misbehavior classes — it directly targets this exact failure mode.
4Symbolic execution, briefly▾

Instead of running a program with one concrete input, symbolic execution runs it with a symbol standing for "any possible value," tracking constraints on that symbol as it flows through the program. At the end, a solver checks which outcomes are actually reachable.

Now you're ready: SaSh runs the whole shell script this way — $HOME, $1, command outputs, and more all start as unconstrained symbols.
5External commands are opaque binaries▾

A shell script is mostly glue: rm, mv, cd, cat are separate compiled programs the shell can't see inside. To reason about what they do, you either run them for real (too late, too risky) or you know their behavior some other way.

Now you're ready: SaSh's answer is hand-written specifications — small pre/post-condition triples per command (§4.1) — that stand in for actually executing the binary.
6Optimistic vs. pessimistic analysis▾

A pessimistic analysis flags anything that could possibly go wrong in some environment — which, for shell, is nearly every line, since almost any command could fail for some malicious input. A useful analysis instead asks: does this go wrong even under favorable, everyday conditions?

Now you're ready: This is SaSh's central design choice — "optimistic symbolic execution" (§3.2) — and it's what keeps false positives at zero across the evaluation.
7Path explosion, quickly▾

Every conditional command introduces a branch (did it succeed or fail?). String a few dozen commands together and the number of distinct execution paths grows exponentially — exploring all of them is infeasible for any real-sized script.

Now you're ready: SaSh's "risk-directed exploration" (§6) exists specifically to avoid exhaustively walking this tree — it picks the branch most likely to be dangerous and explores that first.
8A bug vs. a "misbehavior"▾

Because the shell tolerates so many error states silently, most real shell bugs aren't crashes — they're perfectly legal executions with unwanted effects: an unintended deletion, a silent overwrite, a command that was always going to fail.

Now you're ready: SaSh defines eight such misbehavior classes (Tab. 1) — from critical-path deletion to bad control flow — and checks for all of them at once.
The whole story in one place

SaSh in a nutshell

The problem, the trick that makes it tractable, and how the pieces connect.

Shell scripts run with almost no safety net: a failed cd, an empty variable, or an unquoted expansion can turn an innocuous-looking rm -rf "$DIR/"* into a system-destroying rm -rf /*. These bugs are severe, often irreversible, and mostly invisible to syntactic linters like ShellCheck — which caught only 36.2% of a documented set of 116 real-world bugs, and can be defeated by trivial rewordings.

SaSh instead symbolically executes the script itself. It tracks unknown values — environment variables, command outputs, user input — as symbols, and simulates each external command's effect using a small hand-written specification (pre/post-conditions over a symbolic filesystem model). To handle the shell's dynamic word expansion without exploding the state space, it approximates every expansion result down to just three facts: a concrete prefix, a concrete suffix, and a range on how many fields it might split into.

The key design choice is optimism: SaSh assumes commands either fully succeed or fully fail (no fine-grained partial failure), and — except for irreversible destructive effects — only flags behavior that's dangerous under the program's own best-case conditions, not under some adversarial environment. That's what keeps it from drowning developers in "this could theoretically fail" noise. A final optimization, risk-directed exploration, steers the search toward branches containing destructive commands, so SaSh reaches deeply buried bugs (like one 342 lines from its root cause) in seconds instead of never.

The payoff: across 61 real buggy programs with 116 documented bugs, SaSh finds 115 (99.1%) with zero false positives — against ShellCheck's 42 (36.2%). Applied in the wild for three weeks, it has already surfaced 104 new bugs in 50 open-source projects including PyTorch, Kubernetes, and vLLM.

🐚 Key takeaways

  • Most real shell bugs are misbehaviors — legal executions with unwanted effects — not crashes.
  • Optimistic symbolic execution (assume success outside explicit branches; flag only what fails even ideally) is what keeps false positives at zero.
  • Opaque external commands are modeled with hand-written specification triples over a flat, non-hierarchical filesystem model.
  • Word expansion is approximated by an abstract domain: concrete prefix + concrete suffix + a field-count range — enough to catch dangerous splits without full enumeration.
  • Risk-directed exploration prioritizes branches containing destructive commands, finding deeply buried bugs fast.
  • Result: 115/116 (99.1%) documented bugs found, 0 false positives, vs. ShellCheck's 36.2% — plus 104 new real-world bugs.
Six everyday pictures

How to think about SaSh

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · Simulate before you run

Walking a rope bridge blindfolded

Before you cross a rickety bridge, you'd rather have someone walk it first, symbolically, and tell you exactly which plank is rotten. SaSh does this for shell scripts: it "walks" the program's logic with an SMT solver standing in for reality, so it can tell you which line deletes everything before you ever run it.

Where it breaks: the walker only checks the planks SaSh has a specification for (70% of observed invocations) — for unmodeled commands, it optimistically assumes the bridge is fine there too.
Command specs · Not reading the binary

A one-line movie synopsis

You don't need to read a director's shooting script to know a movie's plot — a one-line synopsis ("the hero saves the town") is enough for most purposes. SaSh treats rm, mv, cd the same way: instead of understanding their C source, it uses a short specification — "if given a file, it deletes it" — sufficient for bug-finding.

Where it breaks: synopses lose nuance a full script has. SaSh's specs are hand-written by experts and only cover common invocation shapes — an unusual flag combination falls outside every synopsis, and gets no coverage.
The filesystem model · Flat, not a tree

A hotel's key-card log, not its floor plan

A hotel's front desk doesn't need a 3D floor plan to know "room 214 is occupied" — a flat log of room→status suffices. SaSh's filesystem model is the same: no directory hierarchy, no nesting — just a flat map from each path to a state (file/dir/deleted, read/unread). Simple, but enough to catch "you deleted something you never read."

Where it breaks: a flat log can't tell you a room's floor collapsed and took three rooms below it — the model has no notion of one path containing another, so certain structural bugs (like deleting a parent implicitly emptying children) aren't directly modeled.
Expansion · Approximating the unknowable

A redacted document you can still reason about

A heavily redacted memo still tells you something — "the memo starts with 'CONFIDENTIAL' and ends with a signature, and has between 2 and 5 paragraphs" — even with the middle blacked out. SaSh's abstract domain for expansion does exactly this to $1/usr: keep the known prefix and suffix, blank out the unknown middle, and track a range for how many words it could split into.

Where it breaks: if $IFS itself (the redaction rule) is unknown, even this approximation fails — SaSh gives up and substitutes a fully unconstrained symbol, warning that it couldn't reason precisely.
Risk-directed exploration · Follow the smoke

A firefighter following the smoke, not the floor plan

A firefighter entering a burning building doesn't search room-by-room in floor-plan order — they follow the smoke toward where the fire is most likely to be. SaSh does the same across a script's branches: at every if, it scores each side by whether it literally contains a destructive command (like rm) and explores that side first.

Where it breaks: smoke can mislead — a branch that looks safe (no destructive commands mentioned) can still call a function that calls rm indirectly, which the local, syntactic risk score can miss until later, non-prioritized exploration reaches it.
SaSh vs. linters · Semantics vs. pattern-matching

A doctor's exam vs. a symptom checklist

A paper checklist ("does the patient have a fever? a cough?") catches only what it explicitly lists — rephrase the symptom slightly and it misses it. A doctor's actual exam reasons about the underlying physiology and catches variations no checklist anticipated. ShellCheck is the checklist (syntactic patterns); SaSh is the exam (semantic execution) — which is why moving one slash in the Steam bug defeats ShellCheck but not SaSh.

Where it breaks: exams are slower than checklists — SaSh's median analysis is far slower than ShellCheck's instant syntax scan, though still far faster than an LLM's.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams.

1 · Four challenges (C1–C4)

Analyzing shell ahead-of-time runs into four compounding difficulties: (C1) almost any command can fail without halting execution, so naively warning on every possible failure floods developers with noise; (C2) commands are opaque binaries that read and write global environment/filesystem state; (C3) word expansion is highly dynamic and its results are, in general, unboundable; (C4) every command implicitly branches on success/failure, so paths explode exponentially even in moderate-length scripts (the Steam updater has 83 explicit branch points across 450 lines).

2 · Optimistic symbolic execution (§3)

SaSh's engine has three cooperating pieces: the interpreter walks the AST over symbolic state; the expander turns words into symbolic strings (calling back into the interpreter for command substitution); the assertion checker encodes accumulated constraints in SMT and reports unsatisfiable ones as bugs.

Two optimism choices keep this tractable: commands are treated as succeeding or failing atomically (not partially), and — except for irreversible destructive effects — SaSh only reports what's dangerous under the program's own successful conditions, not under an adversarial environment. Explicit control-flow (if, &&, case) still forks both branches, which is where real bugs like Steam's failed cd get discovered.

🌱
Concretely: for cmd1 && cmd2, SaSh forks into a success state (cmd1 succeeded, cmd2 runs) and a failure state (cmd1 failed, cmd2 skipped) — exactly the fork that exposes STEAMROOT="" in the Steam bug.

3 · Command specifications & the filesystem model (§4)

Each modeled command maps to a specification triple: a usage assertion (violated ⇒ bug), a success postcondition, and a failure postcondition. SaSh's library currently covers 13,425 of 19,150 (70%) observed invocation shapes; unmodeled commands fall back to an empty specification (optimistically assumed harmless), so SaSh degrades gracefully instead of crashing on unfamiliar tools.

4 · The abstract expansion domain (§5)

Rather than enumerate every possible expansion outcome, SaSh reduces each symbolic string to three facts: a concrete prefix, a concrete suffix, and a range on the number of resulting fields. For $1/usr, that's prefix = "" (unknown $1), suffix = "/usr", field-count ∈ [1,∞] — enough to notice that if $1 splits into multiple words, rm $1/usr could delete something other than intended.

5 · Risk-directed exploration & other optimizations (§6)

Before full symbolic execution, SaSh runs a fast targeted pass: at every branch, it scores each side by counting literal, pre-expansion commands with a destructive specification, and explores only the higher-scoring side. It also merges equivalent forked states and filters trivially-satisfiable assertions before ever calling the solver, cutting overhead. A fixed time budget is split across these stages (risk-directed ≤ 1/3, symbolic execution up to 1/2, the rest to solving).

Follow the numbers, step by step

Worked examples

Four real calculations from the paper's evaluation, carried through in full.

① The Steam updater: depth, branches, and detection time

The full updater is 450 lines with 83 explicit branch points between the STEAMROOT assignment (line 2) and the dangerous rm (line 345) — 342 lines apart. How does SaSh still find the bug in seconds?

  1. Naive exploration is hopeless: 83 binary branches means up to 2⁸³ possible paths — far beyond exhaustive search.
  2. Risk-directed exploration prunes aggressively: at each branch, SaSh keeps only the side whose region contains a destructive command (like rm), collapsing the search dramatically.
  3. The rm branch is always kept — it's the line containing the destructive command — so the targeted pass reaches line 345's forked states (both cd-succeeds and cd-fails) directly.
  4. Result: SaSh reports "Line 345: Deletion of /* due to empty $STEAMROOT" in 4.8 seconds on the full 450-line program — and produces no such warning on the fixed version, in a similar time.
🐚
Insight: the "2 to 450 lines" gap is exactly what risk-directed exploration is for — it turns an intractable path-explosion problem into a few-second analysis by refusing to waste time on branches that can't be dangerous.

② Specification coverage: 70% by the numbers

Across the evaluation, SaSh observes 19,150 distinct command invocations. How much of the real world does its specification library actually cover?

  1. Specified invocations: 13,425 out of 19,150.
  2. As a fraction: 13,425 ÷ 19,150 ≈ 70.1%.
  3. The remaining 30% (≈5,725 invocations) fall back to an empty specification — SaSh optimistically assumes they're benign rather than guessing.
💡
This is why SaSh still finds 115/116 documented bugs despite only modeling 70% of invocations: bugs concentrate around a small set of high-risk, well-specified commands (rm, mv, cd), not the long tail.

③ SaSh vs. ShellCheck: the exact detection gap

SaSh identifies 115 of 116 documented bugs; ShellCheck identifies 42. On semantically-equivalent variants of those 42 bugs, ShellCheck identifies zero. What's the gap in percentages?

  1. SaSh's rate: 115 ÷ 116 = 99.1%.
  2. ShellCheck's rate on originals: 42 ÷ 116 = 36.2%.
  3. On the 42 syntactic variants (same bugs, reworded): SaSh still finds 42/42 = 100%; ShellCheck finds 0/42 = 0%.
  4. The gap widens, not narrows, once syntax changes — proof that ShellCheck's checks are pattern-matches, not semantic reasoning.
🌱
Even ShellCheck's fix-recognition is imperfect: of the 42 bugs it identifies, it still (incorrectly) warns on 7 of their fixed versions — SaSh has zero false positives across the entire benchmark.

④ LLMs are slower and less reliable — and comments make it worse

GPT-5.6 Sol finds 87.0–91.3% of bugs on original programs across three trials, dropping to 64.3–69.6% after adding benign explanatory comments. How much does that cost, and how does it compare in time?

  1. Bugs missed, original: out of 115 SaSh-detectable bugs, GPT-5.6 Sol misses 10–15 per trial (13% average miss rate).
  2. Bugs missed, commented: misses jump to 35–41 per trial (roughly 32% average miss rate) — a ~24% average drop in find-rate from comments alone.
  3. Median time: 54.5× slower than SaSh on originals, 81.2× slower once commented (more tokens to process).
  4. Qwen 3.5 (9B), a laptop-scale model, fares far worse: just 2.6–12.2% of bugs found originally, dropping further with comments.
⚠
The key finding: non-behavioral changes (comments that don't alter what the script does) measurably degrade LLM bug-finding, while SaSh's semantic analysis is unaffected — it never even looks at comments.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking for.

Problem 1 · easy
A script runs rm "$USER_FILE" where $USER_FILE could, for some malicious environment, equal "/". Does SaSh flag this?
Show answer
Not necessarily. SaSh's optimistic model only flags what's dangerous under the program's own everyday, successful conditions — not every conceivable malicious environment. If nothing in the program's own logic forces $USER_FILE toward "/", SaSh won't warn just because it's theoretically possible; that would flag nearly every script.Misconception: that SaSh is a security tool searching for adversarial inputs. It's a bug-finder tuned for everyday, high-signal mistakes — not a threat model against malicious environments (except for irreversible destructive effects, where it does check "may occur").
Problem 2 · easy
Why does rm $X (unquoted) behave differently from rm "$X" (quoted) when $X = "my path/"?
Show answer
Field splitting. Unquoted, the expanded value is split on $IFS characters (space by default), so rm $X receives two arguments: my and path/. Quoted, the whole string is passed as one argument. SaSh's abstract domain tracks exactly this via the field-count range — an unquoted variable with unknown content gets field-count [1,∞], flagging the possible split.Misconception: that quotes are just style. They change how many arguments a command receives — the root cause of SaSh's "dangerous word split" misbehavior class.
Problem 3 · medium
In the Steam bug, why does SaSh need to fork into two states at the && rather than just picking the "likely" outcome?
Show answer
Because the bug only manifests on the failure path (cd fails → STEAMROOT=""), and that's exactly the branch a "pick the likely outcome" heuristic would probably skip. SaSh forks both explicit-control-flow branches so it can check every reachable state's assertions — this is necessary, not optional, for correctness on this exact bug class.Misconception: that SaSh only explores "normal" execution. It explores both branches of every explicit conditional; the optimism is about not exploring implicit failure modes outside conditionals, not about skipping conditionals themselves.
Problem 4 · medium
A specification triple has a usage assertion, success postcondition, and failure postcondition. For rm -rf $p, the failure postcondition is ⊤ (a no-op). Why?
Show answer
Because of SaSh's optimistic execution model: if a command fails, SaSh assumes it had no effect at all (rather than partially deleting some of its arguments) — that avoids exploring the combinatorially many partial-failure states a multi-argument rm could have. It trades some precision for tractability, consistent with treating command outcomes as all-or-nothing.Misconception: that "⊤ for failure" means rm can't fail. It means SaSh doesn't model what a partial/fine-grained failure would do — it only tracks whether the command succeeded wholesale or not.
Problem 5 · medium
SaSh's filesystem model tracks a "read/unread" bit per path. What misbehavior class does this enable, and why is it needed?
Show answer
Data loss detection. If a command's postcondition overwrites or deletes a path that's still marked "unread" (i.e., nothing has consumed its contents yet), that's a strong signal of silent data loss — e.g. two sequential mv a x.txt; mv b x.txt overwrites the first move's target before anything read it. Without the read bit, SaSh couldn't distinguish "this overwrite is fine because we already used the old data" from "this overwrite just destroyed something."Misconception: that any overwrite is suspicious. Only overwriting/deleting unread targets is flagged — the model deliberately allows normal read-then-overwrite patterns.
Problem 6 · hard
The second Debian debootstrap bug (deleting a user-supplied target directory under --print-debs) is the one bug SaSh misses. Why, given SaSh's approach?
Show answer
The bug depends on developer intent, not on any violated invariant SaSh checks by default: deleting a user-supplied path is, in general, completely normal and desired behavior for many scripts — flagging every such deletion by default would flood users with false positives. SaSh could be configured to treat positional-parameter-derived paths as critical, but chooses not to, to preserve its zero-false-positive track record.Misconception: that missing this bug is a technical limitation of symbolic execution. It's a deliberate precision/recall tradeoff — the underlying mechanism (marking a path critical) already exists, it's just not turned on by default.
Problem 7 · hard
Why does risk-directed exploration only look at commands "appearing literally in the region AST pre-expansion"? What class of bug might this miss?
Show answer
Scoring pre-expansion, on the literal AST, is cheap — it's a syntactic scan, not a symbolic-execution pass, so it can run fast enough to prioritize before the expensive engine even starts. The tradeoff: a branch that calls a function (or expands a variable) which indirectly invokes rm won't score as risky at the syntactic level, even though it's just as dangerous — that danger is only discovered later, once full (non-prioritized) symbolic execution reaches it.Misconception: that risk-directed exploration is SaSh's only line of defense. It's a fast first pass to find bugs quickly; full symbolic execution still runs afterward and can catch what the syntactic risk score missed, given enough time budget.
Problem 8 · easy
SaSh unrolls loops a fixed number of times (three, by default) unless the iteration count is statically known. Why not just fully unroll every loop?
Show answer
A loop over a dynamically-sized, unknown collection (e.g. iterating over glob results) has no static bound — fully unrolling it is impossible in general. Capping at a small fixed number (three) trades completeness for tractability: SaSh explores enough iterations to catch most real bugs (which tend to manifest early or with a fixed pattern) without risking infinite unrolling.Misconception: that SaSh always finds loop-related bugs regardless of iteration count. A bug that only manifests on, say, the 10th iteration could be missed under the default cap of three.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1Does SaSh actually run the shell script?▾
No. SaSh symbolically interprets the parsed AST itself — it never invokes a real shell or executes real external binaries. Command effects are simulated via hand-written specifications, so analysis is entirely side-effect-free on the host system.
Q2What exactly counts as a "misbehavior" vs. a normal error?▾
Misbehaviors are legal, non-crashing executions with unwanted effects: deleting a critical path, a dangerous word split, silent data loss, a command guaranteed to fail, IO mismatches, a missing command, identifier misuse, or degenerate control flow (Tab. 1). They differ from linter "code smells" because they're defined semantically over possible executions, not syntactic patterns.
Q3Why does SaSh assume commands succeed by default?▾
Because almost any command could fail in some environment, and reasoning about every fine-grained failure mode is both intractable (combinatorial partial failures) and uninformative (nearly every script would get flagged). SaSh only explores failure explicitly at conditional control constructs (if, &&, ||, case) — where the developer already anticipated failure.
Q4How does SaSh know what rm, mv, or cd do?▾
Via hand-written specification triples (usage assertion, success postcondition, failure postcondition) that domain experts wrote by hand. SaSh currently has specs covering 70% of observed real-world invocation shapes; the paper notes that scaling this via crowd-sourcing or automated synthesis from man pages is future work.
Q5What happens with a command SaSh has no specification for?▾
SaSh falls back to an empty specification — no usage assertion, no effect on the filesystem model — consistent with its optimistic model. This lets SaSh analyze scripts that call tools it doesn't know about, at the cost of missing bugs that live entirely inside those unmodeled commands.
Q6How does SaSh handle the shell's word expansion without exploding?▾
It maps every expansion result to an abstract domain of just four pieces: a concrete prefix, a concrete suffix, a symbolic variable for the unknown middle, and a range on the number of resulting fields. This is coarse but sufficient to catch dangerous splits and critical-path deletions without enumerating every possible concrete outcome.
Q7What is risk-directed exploration, concretely?▾
A fast pre-pass that, at every conditional branch, computes a risk score (the count of literal commands in that branch with a destructive specification) and explores only the higher-scoring side. It's what lets SaSh find bugs 342 lines deep in a 450-line script within seconds instead of never.
Q8Why does SaSh beat ShellCheck so decisively on "variants"?▾
Because ShellCheck matches syntactic patterns — moving a slash, or renaming a comment character, is enough to dodge its checks entirely (0/42 on variants). SaSh reasons about the underlying semantics of execution, so a trivial rewording that preserves behavior still triggers the same warning (42/42 on variants).
Q9Are LLMs a viable replacement for SaSh?▾
The paper's experiments say no, for now: GPT-5.6 Sol misses 9–13% of bugs SaSh catches and runs ~55–81× slower; a laptop-scale model (Qwen 3.5, 9B) misses 88–97%. Both degrade further when benign comments are added — a non-behavioral change that shouldn't matter but does, unlike SaSh's semantic analysis.
Q10Does SaSh ever produce false positives?▾
Zero, across the entire documented-bug benchmark: when SaSh is run on the fixed version of every buggy program, it does not warn about the now-resolved bug. This discriminative power comes directly from the optimistic model — it only reports what's provably inconsistent or dangerous, not merely "possible."
Q11What does SaSh not handle?▾
It doesn't interpret trap at all (signal handlers can fire at arbitrary points), handles eval/. only with fully concrete arguments, omits a few orthogonal POSIX features (shift, times, most set options besides -e/-u), and unrolls loops only a bounded number of times by default (three) unless the iteration count is statically known.
Q12What's left for future work?▾
The paper flags scaling the specification library (crowd-sourcing or automated synthesis from man pages / NLP), and — implicitly — extending coverage of unmodeled commands, deeper handling of function calls under ambiguous binding, and refining risk scoring beyond syntactic, pre-expansion command counts.

For the memory-tiering reader: SaSh's core bet — that ahead-of-time, effect-aware analysis beats reactive, pattern-based checking — echoes a tension familiar from OS memory management: reactive tiering policies (TPP, HeMem, Memtis) react to observed access patterns after the fact, the same way ShellCheck reacts to observed syntax after the fact. SaSh's optimistic symbolic execution is closer in spirit to profile-guided or ahead-of-time page classification — predicting an effect's consequence before committing to it, rather than migrating/evicting and correcting later.
