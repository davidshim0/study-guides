The syscall boundary isn't the bottleneck — the mitigations guarding it are

Unikernels replace system calls with function calls. This paper carefully rebuilds a traditional syscall, mechanism by mechanism, inside a libOS to find out exactly what that boundary costs — and what actually eats your latency instead.

📄 Kröning, Feinendegen, Lankes, Simon, Klimt, Monti — RWTH Aachen 🎓 x86-64 privilege rings / TLB / VM basics assumed — primers cover them ⏱ ~20 min read
🧮

An unmitigated traditional syscall costs ~37 ns more than a libOS function call. CPU vulnerability mitigations alone add roughly 190–400+ ns — 5–10× more.
Blame the mitigations, not the boundary.

Before you begin

Quick glossary, then ten primers

The acronyms first, then short accordions on the mechanisms the paper dissects. Skip anything you already know.

Quick glossary — the paper's acronyms

libOSLibrary operating system: OS code linked directly into the application, replacing syscalls with function calls.
SASOSSingle-Address-Space OS — one process runs in kernel mode, so no inter-process isolation is needed internally.
PTIPage Table Isolation — unmaps the kernel from user page tables to mitigate Meltdown; forces an address-space switch per syscall.
TSCTime Stamp Counter — a cheap, high-resolution x86 cycle counter used to measure nanosecond-scale latencies.
TLB / PCIDTranslation Lookaside Buffer (cached address translations) / Process-Context ID (tags TLB entries so a CR3 switch needn't flush them all).
COWCopy-On-Write — pages shared between processes until one writes, then privately copied.
TSOTCP Segmentation Offload — the NIC splits large sends into packets, saving CPU/guest work.
UKLUnikernel Linux — links an application directly into the Linux kernel image, Linux's own answer to unikernels.
SRSOSpeculative Return Stack Overflow — an AMD speculative-execution vulnerability ("Inception"); its mitigation dominates this paper's Linux syscall latencies.
LPELocal Privilege Escalation — a class of kernel bug motivating a move from containers to VM-strength isolation.

1Rings, syscall, and swapgs▾

x86-64 CPUs have privilege rings: ring 0 (kernel, full access) and ring 3 (user, restricted). The syscall instruction jumps from ring 3 to a fixed kernel entry point at ring 0. Because the kernel can't trust the user's stack pointer, it must switch onto its own stack first — done via swapgs, which swaps the GS base register with a saved kernel value so the kernel has a private scratch register to bootstrap from.

Now you're ready: the paper's H3–H7 steps are exactly these mechanisms, added one at a time.
2Why unikernels can skip all of this▾

A unikernel typically runs only one application process, statically linked to a libOS. With no other mutually-distrusting process inside the VM, there's no reason to run the application at a lower privilege than the "kernel" — everything can run in ring 0, and an OS "call" is just an ordinary function call. The VM boundary (not the ring boundary) provides the isolation.

Now you're ready: this paper measures exactly the cost of reintroducing the ring boundary the unikernel skipped.
3Meltdown, Spectre, SRSO, and mitigations▾

Meltdown let user code read kernel memory via speculative execution; PTI mitigates it by unmapping the kernel from user page tables (forcing an address-space switch per syscall). Spectre and SRSO ("Inception," an AMD return-stack-overflow bug) are related speculative-execution flaws with their own mitigations. These defenses run on every syscall, not just risky ones.

Now you're ready: the paper's central finding is that these mitigations, not the syscall mechanism itself, dominate the cost.
4CR3, address spaces, and TLB flushes▾

CR3 is the x86 register pointing to the current page table. Reloading it switches address spaces — and, without process-context IDs (PCIDs), flushes the entire TLB, since old cached translations may now be wrong. Refilling the TLB from scratch afterward is slow. PTI-style mitigations reload CR3 on every kernel entry/exit.

Now you're ready: the paper's H8 "Synthetic CR3 Reload" approximates exactly this cost, deliberately without PCID optimizations — a pessimistic but instructive stand-in for PTI.
5What "incremental system calls" means▾

Instead of comparing a finished unikernel to a finished Linux VM (which differs in a hundred ways), the authors start from Hermit's fast libOS-call path and add one traditional-syscall mechanism at a time — a lookup table, then the syscall instruction, then a stack switch, then swapgs, then the ring switch, then a simulated CR3 reload — measuring the latency delta after each step.

Now you're ready: this is the paper's core methodological contribution — controlled, additive attribution of overhead.
6Hermit, UKL, and Unikraft, briefly▾

Hermit is a Rust-based libOS used here as the experimental platform because its call path can be transformed incrementally. UKL (Unikernel Linux) links an application directly into the Linux kernel image — "Linux acting like a unikernel." Unikraft is an extremely specialized, minimal unikernel used only as an image-size/networking reference point.

Now you're ready: H-configs = Hermit's ladder; U-configs = UKL; L-configs = plain Linux; K1 = Unikraft.
7getpid() as a near-pure overhead probe▾

getpid() does almost no kernel work — in Hermit it just returns a hardcoded value. That makes its latency an almost-clean measurement of just the call-path overhead, uncontaminated by the work a real syscall does.

Now you're ready: Figure 1a's getpid() numbers are what the whole overhead-attribution chain (Figure 4) is built from.
8Why TCP/HTTP benchmarks, and why they're not apples-to-apples▾

Microbenchmarks show raw per-call overhead; TCP/HTTP benchmarks ask whether that overhead is even visible once real application work and I/O dominate. But cross-kernel TCP/HTTP comparisons also mix in driver maturity and network-stack optimizations (e.g. TSO), so they can't isolate syscall cost alone across different kernels — only across Hermit's own H-configs, which share everything else.

Now you're ready: read the Hermit-internal comparison as clean; read the cross-kernel comparison as "does everything else outweigh the syscall boundary."
9fork() and why H9 exists▾

H8's CR3 reload is a synthetic approximation — no real second address space exists yet. H9 adds real fork()/process-loading support to Hermit (via copy-on-write page duplication) so the ring-switch path (H7) can be validated against a genuine multi-process scenario, without the synthetic CR3 reload.

Now you're ready: H9's latency landing close to H7 and L5 is the paper's cross-check that H7's numbers are representative.
10Image size vs. runtime overhead — two different claims▾

Unikernels are often sold on small images and fast boot, a claim about specialization, separate from the claim that eliminating syscalls speeds up running code. This paper's central move is separating those two: it can be true that unikernels stay small while also being true that syscall elimination alone doesn't win the runtime race against a well-tuned Linux VM.

Now you're ready: Table 1's image sizes and Figures 1–3's latencies are answering two different questions, not one.
The whole story in one place

The idea in a nutshell

What's actually expensive at the syscall boundary — and what isn't.

Unikernels argue that running one process in kernel mode lets them replace traditional syscalls with plain function calls, avoiding a costly privilege-level boundary crossing. This paper tests that argument directly: starting from Hermit's fast libOS function-call path (2.92 ns for a no-op call), the authors incrementally reintroduce every traditional mechanism — a dispatch table, the syscall instruction, a kernel-stack switch, swapgs, and a ring 3/0 switch — arriving at a full traditional syscall (40.2 ns) after adding roughly 37 ns total.

Then they add one more step: a synthetic reload of CR3 (the page-table-base register) to approximate page-table isolation (PTI), a mitigation against Meltdown, deliberately without PCID optimizations. That single synthetic step adds 394.33 ns — about ten times the entire unmitigated syscall overhead. Real Linux configurations point the same direction, though with smaller measured numbers: enabling default CPU vulnerability mitigations pushes getpid() latency from ~48 ns to ~237 ns (an added cost of roughly 189 ns), and configurations that also carry the newer SRSO/"Inception" mitigation on AMD climb further still, into the 300–400+ ns range — the same order of magnitude as Hermit's synthetic H8 estimate, even though H8 itself is not a direct measurement of any real Linux configuration.

Crucially, none of this unmitigated overhead is even visible in TCP or HTTP application benchmarks — Hermit's bandwidth and request latency stay essentially flat across all nine incremental configurations. When Hermit is compared against a minimal, distroless Linux VM, Linux's mature drivers and network stack (e.g. virtio-net TSO) outweigh any function-call advantage. The paper's conclusion is not that unikernels are pointless — extremely specialized images stay far smaller, and the authors suggest this might translate into shorter boot times, though that isn't directly measured here — but that eliminating the syscall boundary alone should not be expected to produce measurable application speedups.

🍯 Key takeaways

  • Unmitigated traditional syscall vs. libOS call: ~37 ns of added overhead (H1 2.92 ns → H7 40.2 ns).
  • CPU vulnerability mitigations add roughly 190 ns (Linux's real default-mitigation delta) up to 400+ ns (heavier PTI/SRSO configurations, and Hermit's synthetic CR3-reload estimate) — 5–10× the unmitigated syscall cost.
  • The single biggest jump among Linux system-call latencies on this AMD machine comes from the SRSO ("Inception") mitigation, introduced in Linux 7.0.
  • The synthetic CR3 reload (approximating PTI, no PCID) alone costs 394.33 ns — the largest single step in Hermit's own H1–H9 ladder.
  • None of the unmitigated syscall overhead is measurable in TCP or HTTP application benchmarks.
  • A minimal, distroless Linux VM outperforms function-call unikernels in these workloads — driver/network-stack maturity dominates.
  • Unikernels retain a real, measured advantage in image size — and, the authors suggest, potentially shorter boot times, though that isn't directly measured here — plus value as a research platform, but not an automatic runtime win.
Five everyday pictures

How to think about this paper

Each stands alone; each ends with where it breaks down.

The method · Incremental reconstruction

Rebuilding a door, hinge by hinge

Instead of comparing a screen door to a bank vault door (too many differences at once), the authors start with the screen door and bolt on one vault feature at a time — a lock, a deadbolt, reinforced hinges — timing how much each addition slows the swing. That's H1→H8: one mechanism added per step.

Where it breaks: a real vault door's features interact (a heavier door needs stronger hinges); the paper's steps are mostly additive, but H8's CR3 reload is explicitly a rough approximation, not a fully-optimized mechanism.
Mitigations vs. mechanism

The door vs. the security checkpoint

Walking through an unlocked door costs almost nothing. Walking through an airport security checkpoint — ID check, bag scan, pat-down — costs real time, and that time has nothing to do with the door itself. The syscall instruction is the door; PTI/SRSO mitigations are the checkpoint bolted in front of it.

Where it breaks: unlike a checkpoint, mitigations can't simply be skipped on a shared, potentially hostile Linux host — they exist because the threat (Meltdown/Spectre/SRSO) is real, not bureaucratic overhead.
CR3 reload · TLB flush

Re-shelving the whole library

A translation lookaside buffer is like a librarian's memorized shelf locations — fast, until you switch libraries (address spaces) and every memorized location is now wrong. Without PCIDs to tag "which library" each memory applies to, the safest thing is to forget everything and relearn shelf locations from scratch. That's the CR3 reload's real cost: not the register write, but the TLB refills afterward.

Where it breaks: real hardware often does have PCIDs to avoid full flushes; H8 deliberately models the unoptimized case to bound the worst-case mitigation cost, not the best case.
Why bandwidth stayed flat

A speed bump on an empty road vs. a traffic jam

A 37-ns speed bump is irrelevant on a highway already crawling at rush hour — the bottleneck elsewhere swamps it. Hermit's TCP/HTTP benchmarks are the traffic jam: driver overhead, interrupt handling, and network-stack maturity dominate, so the syscall speed bump never shows up in the total travel time.

Where it breaks: in a workload with vastly more, tinier syscalls (e.g. a hot loop issuing millions of tiny operations with no I/O wait), the speed bump could still add up — this paper's workloads simply aren't that.
Image size vs. speed

A tiny suitcase that still takes the slow train

Packing light (a small unikernel image) is genuinely valuable for boot time and storage — but it says nothing about how fast the train itself runs once you're aboard. Unikraft's featherweight 0.5 MiB image is real and useful; it doesn't imply Unikraft's HTTP server outruns a tuned Linux VM.

Where it breaks: for boot-time-critical serverless workloads, the suitcase size genuinely is the dominant metric — the analogy only cautions against conflating it with steady-state runtime speed.
The full explanation

How the dissection actually works

The Hermit ladder, the UKL/Linux comparison axis, and why the plots have broken y-axes.

1 · The Hermit ladder — H1 to H9

Starting from Hermit's default libOS-call path (H1), each configuration adds exactly one traditional-syscall mechanism, keeping everything else fixed: a separate application allocator (H2, isolates malloc() from the measurement), a centralized dispatch table entered via a normal call (H3), the same dispatch entered via the syscall instruction (H4), a switch to a dedicated kernel stack (H5), a swapgs to protect the GS-based stack-switch mechanism (H6), and a genuine ring 3→0→3 privilege switch via sysretq (H7). H8 layers a synthetic CR3 reload atop H7 to approximate PTI. H9 is a separate validation branch, not a further step in the same ladder: it branches off H7 to add real fork()-based multi-process support, deliberately without H8's synthetic CR3 reload, so H7's ring-switch numbers can be checked against a genuine multi-process scenario.

2 · Why the plots have broken y-axes

Figures 1–3 all group configurations into two separate y-axis ranges. This isn't cosmetic: it's the paper's finding made visible. Configurations without heavyweight mitigations (H1–H9, U1–U4, L1, L2, L5) cluster in a low range (tens of ns for latency); configurations with PTI-like or SRSO mitigations active (L3, L4, L6, L7, H8) jump into a range 5–10× higher. A single, non-broken axis would either crush the interesting low-range detail or need to be inconveniently tall.

3 · From Hermit numbers to application impact

The getpid() microbenchmark isolates pure overhead; a file-I/O microbenchmark (open+write+lseek+read+close) shows the same story at a larger absolute scale, since it involves more syscalls per operation. The TCP and HTTP benchmarks then ask the practical question: does any of this show up once the application does real work? Across Hermit's own H1–H9 configurations, TCP bandwidth and HTTP request duration stay essentially unchanged — the syscall-path overhead is too small relative to network I/O and driver costs to matter.

🖥️
Connect to tiered-memory work: the CR3-reload/TLB-flush story here is structurally the same trade-off you see invalidating TLB entries after migrating a page between DRAM and NVM/CXL tiers — a "fast path" (stay resident) vs. a rare but expensive "boundary crossing" (flush + refill) whose cost is dominated by a global invalidation, not the instruction that triggers it.
Follow the real numbers

Worked examples

Three traces using the paper's actual measurements.

① Reconstructing H7's 40.2 ns from six increments

Figure 4 gives six overhead increments (ns): system-call table 3.69, syscall instruction 12.31, stack switch 0.31, swapgs 9.69, ring switch 11.23, synthetic CR3 reload 394.33. H1's baseline is 2.92 ns. Does the ladder actually add up?

  1. Start at H1/H2: 2.92 ns (app-allocator swap doesn't touch the syscall path).
  2. + system-call table (H3): 2.92 + 3.69 = 6.61 ns.
  3. + syscall instruction (H4): 6.61 + 12.31 = 18.92 ns.
  4. + stack switch (H5): 18.92 + 0.31 = 19.23 ns.
  5. + swapgs (H6): 19.23 + 9.69 = 28.92 ns.
  6. + ring switch (H7): 28.92 + 11.23 = 40.15 ns — matches the paper's reported 40.2 ns almost exactly.
🍯
Insight: the six named increments aren't just illustrative — they sum to the independently measured H7 latency, which is the paper's evidence that its attribution is internally consistent, not just a post-hoc story.

② The CR3 reload alone costs ~10× the whole syscall boundary

Continue the ladder one more step, onto H8.

  1. H7 total (from above): ≈ 40.15 ns.
  2. + synthetic CR3 reload: 40.15 + 394.33 = ≈434.5 ns for H8.
  3. Compare the two additions: the entire H1→H7 journey added 37.23 ns; the single H7→H8 step adds 394.33 ns — ≈10.6× as much as every other mechanism combined.
  4. Sanity-check against real Linux: default-mitigation configurations (L4) land near 237 ns and PTI-heavy configurations (L6, L7) land in the 200–400 ns band shown in Figure 1a — the same order of magnitude as this synthetic estimate, though H8 is a Hermit-only synthetic figure, not a direct measurement of any of these Linux configurations.
💡
H8 is deliberately pessimistic (no PCIDs, full TLB flush), so it's an upper bound rather than a precise PTI model — but the order-of-magnitude gap versus the ~37 ns syscall boundary is the point, and it survives even generous adjustment.

③ Image size: where unikernels actually win

Using Table 1's uncompressed sizes: Ubuntu cloud image 598.8 MiB, Linux L4 kernel + initramfs 24.5 + 0.9 MiB, Hermit H1 unikernel 12.5 MiB, Unikraft K1 unikernel 0.5 MiB.

  1. Distroless Linux vs. the cloud image: (24.5+0.9) / 598.8 ≈ 4.2% of the size — most of the "unikernel is smaller" story is really "distroless is smaller."
  2. Hermit vs. distroless Linux: 12.5 MiB vs. 25.4 MiB — Hermit is ≈2× smaller, a real but modest gap.
  3. Unikraft vs. distroless Linux: 25.4 / 0.5 ≈ 51× smaller — this is where extreme specialization actually delivers a dramatic number.
  4. Takeaway: the size advantage scales with how specialized the unikernel is, not with whether it merely avoids syscalls — Hermit (compatibility-oriented) gains little over distroless Linux; Unikraft (extremely specialized) gains a lot.
🍯
Insight: this mirrors the paper's main message about latency — the benefit tracks the degree of specialization, not the mere presence or absence of a syscall boundary.

Practice problems

Try each before revealing the answer.

Problem 1 · easy
A colleague claims "unikernels are fast because they skip system calls." Using this paper's numbers, what's the strongest one-sentence correction?
Show answer
Skipping the syscall instruction path saves only ~37 ns per call; the far larger cost (roughly 190–400+ ns) comes from CPU vulnerability mitigations layered onto that path, which a unikernel running untrusted multi-tenant code would still need in some form. Unikernels' one real, measured advantage in this paper is image size — the authors also suggest short boot times might be possible, though that isn't directly measured here — not per-call latency.Misconception: conflating "no ring switch" with "no mitigation cost" — the mitigations, not the ring switch, are the expensive part.
Problem 2 · medium
Given the six Figure 4 increments (3.69, 12.31, 0.31, 9.69, 11.23, 394.33 ns), which single step should you optimize first if you must keep some form of address-space isolation, and which step is barely worth bothering with?
Show answer
Optimize the CR3-reload/PTI-equivalent step (394.33 ns) — e.g. via PCIDs to avoid full TLB flushes — since it dwarfs everything else combined (37.23 ns total for the other five). The stack switch (0.31 ns) is essentially free and not worth engineering effort.Misconception: assuming all "syscall overhead" sources are comparable in size — they span three orders of magnitude, and effort should follow the numbers.
Problem 3 · medium
Hermit's TCP bandwidth is nearly identical across H1 through H9, even though their getpid() latencies alone range from 2.92 ns (H1) up past 400 ns (H8's synthetic mitigation step). Does this mean syscall overhead never matters for networked applications?
Show answer
No — it means it doesn't matter for this workload, where network I/O and driver/interrupt handling costs dwarf even a several-hundred-ns per-call difference. A workload issuing vastly more, smaller syscalls with little I/O wait (e.g. a tight compute loop making frequent OS calls) could still see the overhead show up; the paper is explicit that its TCP/HTTP benchmarks are chosen to make syscall overhead maximally visible, and even there it's invisible.Misconception: generalizing a null result on two specific benchmarks to "syscall overhead is always negligible."
Problem 4 · hard
L2→L3 is just a kernel version bump (6.3-based config → Linux 7.0.11), yet it's enough to move a configuration from the low-latency axis to the high-latency axis in Figure 1a. Why, and what does this imply for benchmarking practice?
Show answer
Linux 7.0.11 introduces a mitigation against the SRSO ("Inception") vulnerability on AMD processors, which the paper identifies as having the biggest effect among Linux system-call latencies on their machine — added independent of any application or unikernel design choice. This implies that comparing kernel versions (or distros) without controlling for default mitigation policy can attribute a mitigation-driven latency jump to unrelated architectural differences.Misconception: treating "same kernel family, newer version" as latency-neutral — a single CVE-driven mitigation can dominate an entire version bump's effect.
Problem 5 · medium
UKL (U1–U4) runs were sometimes unstable, crashing with general protection faults under load. How did the authors handle this, and why does it matter for interpreting the UKL results?
Show answer
They treated any run that crashed before completion as failed and excluded its partial data, using only completed runs; as a result they present UKL results as contextual data points rather than a fully representative, stable baseline. Readers should weight UKL comparisons with more caution than the Hermit or Linux results, which didn't have this instability.Misconception: treating all reported numbers in a paper as equally reliable — the authors themselves flag UKL's data as lower-confidence.
Problem 6 · easy
Unikraft's HTTP server image is roughly 50× smaller than a distroless Linux kernel+initramfs. Does this paper's data support the claim that Unikraft is also 50× faster at serving HTTP requests?
Show answer
No — image size and runtime latency are measured separately in this paper and don't move together. The paper explicitly separates "specialization benefits" (image size, boot time) from "runtime speedup from syscall elimination," and argues the latter doesn't automatically follow from the former.Misconception: assuming a dramatic win on one axis (size) implies a proportional win on an unrelated axis (speed).
Quick answers

Frequently asked questions

Tap any to expand.

Q1What's the single headline number from this paper?▾
An unmitigated traditional syscall costs about 37 ns more than a libOS function call; CPU vulnerability mitigations alone add roughly 190–400+ ns depending on which mitigations are active — five to ten times more. The syscall boundary is a small cost; the mitigations bolted onto it are the big one.
Q2Why not just compare a finished unikernel to a finished Linux VM directly?▾
Because a finished unikernel and a finished Linux VM differ in dozens of ways (drivers, network stack, scheduler, allocator, syscall path) at once — any latency difference could be caused by any of them. The paper's incremental H1→H8 sequence changes exactly one mechanism at a time within the same libOS, isolating the syscall-boundary contribution specifically; H9 is a separate validation branch off H7 that adds real fork()/process-loading support — without H8's synthetic CR3 reload — to confirm H7's numbers hold up in a genuine multi-process setting.
Q3What does the "synthetic CR3 reload" (H8) actually simulate?▾
It approximates page-table isolation (PTI), the Meltdown mitigation that unmaps the kernel from user page tables and forces an address-space switch on every syscall. H8 reloads CR3 without process-context IDs, which flushes the entire TLB — a deliberately pessimistic, simplified stand-in for a real, optimized PTI implementation.
Q4Why does upgrading from Linux 6.3 to 7.0 matter so much here?▾
Linux 7.0.11 adds a mitigation for the SRSO ("Inception") speculative-execution vulnerability on AMD CPUs. On the paper's AMD EPYC test machine, this single mitigation has the largest measured effect among Linux system-call latencies specifically — though within Hermit's own H1–H9 ladder, H8's synthetic CR3-reload step is still the single largest jump of anything measured in the study.
Q5Did system-call overhead measurably affect the TCP/HTTP benchmarks?▾
No. Across Hermit's H1–H9 configurations — spanning pure function calls (H1) up through a full traditional syscall plus a synthetic mitigation-like CR3 reload (H8), and a real fork()/process-loading variant (H9) — TCP bandwidth and HTTP request duration stayed effectively flat. Application-level I/O and driver costs dominate long before syscall latency becomes visible.
Q6Does a distroless Linux VM beat unikernels, then?▾
In these workloads, yes: a single-process, distroless, VM-optimized Linux kernel outperformed the function-call-based unikernels, because Linux's mature drivers and network-stack optimizations (like virtio-net TSO) outweigh the syscall-elimination advantage. Unikernels still win on image size and potentially boot time.
Q7Why was UKL treated as "contextual" rather than a stable baseline?▾
Some UKL runs crashed with general protection faults under load before completing. The authors excluded incomplete runs and only plotted completed ones, but flag the overall UKL dataset as less reliable than Hermit's or Linux's — worth keeping in mind when comparing numbers.
Q8What is fork() support (H9) for, if H8 already models the address-space switch?▾
H8's CR3 reload is synthetic — there's no real second address space. H9 branches from H7 (not from H8) to add genuine fork()/process loading (via copy-on-write page duplication) so the ring-switch path from H7 can be validated in a real multi-process setting, deliberately without H8's synthetic reload. H9's latency landing close to H7's and to L5 (no mitigations) confirms H7 is representative.
Q9So do unikernels have any value left, per this paper?▾
Yes — extremely specialized unikernels (like Unikraft) can be an order of magnitude smaller in image size, which the authors suggest matters for boot time and cold-start-sensitive deployments (though boot time itself isn't directly measured here); language-specific libOSes also enable systems research (e.g. Rust async I/O at the syscall level) that's hard to do in C. The paper's caution is narrower: don't expect broad runtime speedups from syscall elimination alone in compatibility-oriented unikernels.
