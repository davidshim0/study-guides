Locking whoever's contending right now — not every record that might someday need it

Hosts in a CXL pod can all touch one shared memory pool — but hardware cache coherence only covers a sliver of it. XTRA's fix: stop giving every record its own lock, and spend that scarce coherent sliver on synchronization, not on data.

📄 Yang, Hua, Zhang, Chen, Chen, Tong · SOSP'26 🎓 Some CXL/transaction basics assumed — primers cover them ⏱ ~30 min read
🗂️

Give the scarce coherent hardware to whoever is ACTIVELY SYNCHRONIZING right now — not to every record that MIGHT EVENTUALLY need a lock.

Before you begin

Nine ideas the paper assumes you know

Each card clears up one concept XTRA builds on. Collapsed by default — read in order the first time, or jump to whatever's unfamiliar.

XTRA (decoupled sync) the scarce HCC region CD / SD machinery Tigon / on-demand sharing
1CXL and the shared memory pool▾

Compute Express Link (CXL) rides on PCIe and lets a host map device memory into its own address space, then touch it with ordinary load/store instructions (the CXL.mem protocol). A "CXL pod" wires up to 16 hosts to one shared, TB-scale memory pool this way — no network stack, no message passing, just loads and stores.

Frequently touched lines still get pulled into the host's own L1/L2/L3 CPU caches, exactly like local DRAM.

Now you're ready: the whole paper lives in the gap between "any host can load/store any byte in the pool" and "caching that byte locally is safe."
2Hardware cache coherence (HCC), and why it's normally free▾

On a single machine, when one core writes a cacheline, the hardware automatically invalidates any stale copy in another core's cache — that's cache coherence, and it's what makes atomics like Compare-and-Swap (CAS) work across cores.

It's "free" on one machine because a small on-chip snoop filter can track every line every core might cache. Across hosts, that tracking has to live in the CXL device itself, in limited SRAM.

Now you're ready: CXL 3.0 does add cross-host HCC, but only for a region small enough for the device's snoop filter to track — reported as hundreds of MB, not TB.
3HCC region vs. NHCC region — one pod, two zones▾

Because the snoop filter can't cover the whole pool, a CXL 3.0 pod ends up split: a small HCC region where cross-host coherence and atomics work, and a much larger NHCC (non-hardware-cache-coherent) region where they don't. CXL 2.0 pods have no HCC region at all — just pooling.

Now you're ready: XTRA's central design question is: given a tiny HCC sliver, how do you synchronize transactions over the whole TB-scale pool?
4Distributed transactions: read sets, write sets, serializability▾

A transaction bundles several reads and writes so they behave as one atomic step: it sees a consistent snapshot (its read set), and its updates (its write set) become visible to everyone else all at once, at commit. Serializability means the outcome looks as if transactions ran one at a time, even though they overlapped.

Now you're ready: XTRA's whole job is guaranteeing this abstraction for hosts sharing a CXL pool, without full-pool hardware coherence.
5Optimistic (OCC) vs. pessimistic (2PL) concurrency control▾

2PL (two-phase locking) grabs a lock before touching a record and holds it until commit — safe, but locks sit around for the whole transaction. OCC (optimistic concurrency control) lets reads proceed lock-free and only acquires locks for the write set at commit time, then validates that nothing it read has changed since.

Now you're ready: XTRA is built on OCC specifically because lock-free reads keep its shared directory's inevitable collisions cheap.
6Why cross-host locks can't just use CAS▾

CAS ("if the value is still X, swap it for Y") is how single-machine lock-free code works — but it's only atomic because coherent hardware guarantees every core sees the same memory state. Without cross-host HCC, two hosts can each believe they won a CAS on the same word.

Now you're ready: this is exactly why the NHCC region can't host ordinary locks — and why XTRA needs a software substitute for it (§4.4).
7Per-record metadata vs. a bounded directory — the core insight▾

Conventional transaction systems give every record its own lock and version word. That's fine when coherent hardware is unlimited. But if only a sliver of the pool is coherent, per-record metadata for a TB-scale dataset simply can't fit. XTRA's move: only the records currently being contended need synchronization state at any instant — so consolidate that state into one small, shared, reusable structure.

Now you're ready: that structure is the Coordination Directory (CD) — the single idea the rest of the paper builds on.
8Deterministic addressing across hosts▾

Each host maps the shared CXL pool at its own virtual address, so pointers can't be raw VAs. But an object's offset from a base pointer inside the pool is the same for every host. Systems in this space already exchange pointers as pool offsets, not VAs.

Now you're ready: XTRA hashes that offset to pick a directory slot — the same slot, on every host, for the same object.
9"Perfect Hit," and why transaction atomicity punishes even one miss▾

Under on-demand sharing (Tigon's design), a transaction achieves a Perfect Hit only if every one of its remote-key accesses already has metadata resident in the HCC region. Because a transaction is atomic, even a single miss forces it to stall for remote migration while still holding its other already-acquired locks — one slow access blocks the whole transaction, and everyone waiting on those locks.

Now you're ready: this atomicity amplification is why longer transactions and bigger datasets hurt on-demand sharing disproportionately — the motivating problem XTRA is built to avoid.

The whole story in one place

XTRA in a nutshell

The tension, the two-part fix, and how it connects to what you already know about CXL memory pools.

A CXL pod lets any host load/store any byte in a shared TB-scale pool — but cross-host hardware cache coherence covers only a small HCC region (hundreds of MB), leaving the rest NHCC. Conventional transaction designs give every record its own lock and version word, so their synchronization footprint scales with the dataset. Once the dataset outgrows the HCC region — which happens fast at TB scale — that design collapses: Tigon, the prior state of the art, loses 4.3× throughput at 5M keys and 30× at 40M keys versus its 2.4M-key peak, with P99 latency rising up to 588×.

XTRA's fix has two parts. First, decouple synchronization from data: instead of per-record metadata, consolidate locks and versions into a bounded Coordination Directory (CD), with every object deterministically hashed to one of its slots. The CD's size now depends on how much concurrent contention you expect, not on dataset size — an 8 MB CD provides roughly 10⁶ slots (8 MiB ÷ 8 B ≈ 1.05 million), enough for thousands of concurrent threads with room to spare. Second, unify cache coherence with OCC: rather than eagerly broadcasting invalidations when NHCC data changes, XTRA notices that OCC's version check ("has anything I read changed?") already answers the coherence question ("is my cached copy stale?") — so it reuses that one check, lazily, on read.

The payoff: across KVS, SmallBank, and TPCC at three dataset scales, XTRA delivers 1.3–15.6× higher throughput and 1.3–4.0×/1.2–283.9× lower P50/P99 latency than Tigon, while also beating an RDMA-based shared-everything baseline (Motor) by 1.1–11.5× throughput. It generalizes to CXL 2.0 (no HCC at all) via software mutual exclusion, at a real but bounded cost.

🗂️ Key takeaways

  • HCC covers a fixed sliver (hundreds of MB); per-record metadata scales with the dataset — that mismatch is the whole problem.
  • XTRA's CD decouples synchronization from data: bounded by expected concurrency, not dataset size.
  • Objects map to CD slots via deterministic hashing of their pool offset — same slot, every host, no coordination needed to agree.
  • OCC's version check doubles as a cache-freshness check — no eager invalidation broadcasts required.
  • A Shadow Directory per host makes that lazy check safe across threads sharing one physical LLC.
  • Software mutual exclusion + column-major layout + hierarchical sync generalize XTRA to CXL 2.0 (no HCC at all).
  • Result: up to 15.6× throughput, 4.0×/283.9× lower P50/P99 latency vs. Tigon; scales gracefully where on-demand sharing collapses.
🧭
For readers coming from single-node tiering: TPP and Memtis manage page placement for one host across a DRAM/CXL tier under CXL 1.0-style single-host tiering — deciding what lives where. Pond sits one layer over: CXL 2.0 multi-host memory pooling, sharing raw capacity across hosts rather than deciding per-host placement. XTRA assumes that pooling/placement problem is solved and instead asks a different question: once several hosts share the pool, how do they agree on who's allowed to write what, right now? Different layer, same substrate.
Seven everyday pictures

How to think about XTRA

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Decoupling sync from data

A coat check, not a name tag on every coat

A theater doesn't sew a lock into every coat — it hands out a small set of numbered tickets and tracks "ticket 42 → rack B." XTRA does the same: instead of a lock word glued to every record, a compact Coordination Directory hands out a bounded set of "tickets" (slots), and every host hashes an object's pool offset to the same ticket number.

Where it breaks: a real coat check has one ticket per coat. CD slots are shared by hashing, so two unrelated objects can land on the same ticket — a collision the paper accepts as a concurrency cost, never a correctness one.
Why coupling collapses · HCC capacity

One guard station, a whole apartment block

If your building assigns one guard-with-a-key per apartment, that plan is fine for ten units and impossible for ten thousand — the guard station (the HCC region) has fixed capacity, but "one guard per unit" scales with the number of units, not the station's size. Tigon hits exactly this: guards run out once the working set exceeds the ~200 MB HCC budget, so units start waiting for a guard to become free (migration stalls).

Where it breaks: a real guard station can't be resized at runtime; the HCC region actually can be, at deployment time — the paper still shows XTRA holding up down to 10 MB, far smaller than 200 MB.
Unified coherence · Lazy vs eager invalidation

Check if the paint dried — don't repaint your neighbor's fence for them

You don't call every neighbor the moment you repaint your fence; you just expect that anyone who cares will look before they lean on it. XTRA's transactions already have to check "has this version changed?" for OCC's sake — so on the next read, that same check also answers "is my cached copy stale?" No separate invalidation broadcast is ever sent.

Where it breaks: a neighbor who never looks stays fooled forever; a thread that never re-reads through OCC could too — which is exactly why the Shadow Directory tracks state at the object level, not just per-transaction.
Unified coherence · Shadow Directory

A shared sticky note that says "already checked"

Two roommates share one desk. If roommate A checks that a drawer's contents match the label and leaves a sticky note saying so, roommate B doesn't need to re-check — until the label changes. The Shadow Directory is that sticky note, shared across all threads on a host: it bridges the gap between a transaction's brief lifetime and the CPU cache's continuous, shared lifetime.

Where it breaks: a sticky note doesn't expire on its own; the SD's shadow version does — the moment the CD's real version moves ahead, every "already checked" entry for that slot is cleared, forcing fresh sanitization (CLFLUSH) before reuse.
Generalizing to CXL 2.0 · Hierarchical sync

Settle it in the office first, then send one rep to headquarters

If every employee across every branch office called headquarters to settle a dispute, the phone lines would jam. Better: employees at the same branch settle among themselves first (fast local atomics), and only the local winner calls headquarters (the slow, contended, CXL-wide software latch). XTRA's hierarchical synchronization caps the number of hosts contending on the CXL path at one representative per host.

Where it breaks: real headquarters calls don't scan a full participant list; Lamport's fast mutex still has to check every host's flag on its slow path — hierarchy shrinks the participant count, it doesn't eliminate the scan.
Generalizing to CXL 2.0 · Column-major layout

A shared logbook, one column per writer

If every writer needs their own page, a logbook shared by eight people needs eight times the paper. But if each writer instead owns one column running down every page, no one's ink ever overlaps another's — and the book stays one size regardless of how many entries it logs. XTRA packs mutex flags the same way: one host's flags share a cacheline safely, because only that host ever writes to it, avoiding CAS-free cross-host overwrites without needing a whole cacheline per flag.

Where it breaks: a logbook column is free to make wider; CXL cachelines are fixed at 64 B, which is precisely the constraint the column-major trick is working around.
Correctness · Deterministic mapping

A locker number drawn from your ticket, not your name

A locker room assigns you locker #91 by running your ticket number through a fixed formula — anyone with the same ticket number gets the same locker, no attendant needed to coordinate. XTRA hashes each object's pool offset the same way: slot = Hash(offset) mod N, computed independently and identically on every host.

Where it breaks: lockers rarely collide; hash slots do, by design, once concurrency approaches the directory's size — which is why the paper sizes N for the expected active-thread count, not the dataset.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams you can read at a glance.

1 · The Coordination Directory — structure and mapping

The CD is a flat array of 64-bit slots living in the HCC region (CXL 3.0) or NHCC region (CXL 2.0). Each shared object — a data record or an index node — is deterministically hashed to one slot by its pool offset: slot = Hash(offset) mod N. That slot's 64 bits carry everything needed to synchronize the object.

2 · Decoupled OCC — the transaction lifecycle

Every access resolves an object's CD slot instead of an embedded lock. The lifecycle runs in three phases:

1 · Execution
Speculative reads/writes against NHCC objects; read slot versions are recorded; writes buffered locally; no locks yet
→
2 · Locking & validation
CAS-lock (or software mutex) each write-set slot; validate read-set slots are unlocked and unchanged; any mismatch aborts
→
3 · Commit
Flush redo log, apply writes with CLWB+SFENCE, release each slot with one store that clears the lock bit and bumps the version

Because reads never lock, an inter-transaction collision (two transactions on distinct objects that map to the same slot) only forces a false abort if at least one side writes. An intra-transaction collision (one transaction touching two objects on the same slot) is handled by making slot locks reentrant — the transaction simply keeps the lock it already holds, and only ever releases it after its entire write set is visible, so no intermediate state leaks.

3 · Unifying coherence — the Shadow Directory

OCC validation is transient (scoped to one transaction) and per-thread; CPU caches are persistent and shared by every thread on a host. The Shadow Directory (SD) bridges both gaps: one shadow slot per CD slot, holding a shadow version and a small table of tracked NHCC addresses (capacity M=7, chosen so an 8-byte header + 7×8-byte entries = 64 bytes — exactly one cacheline).

Tracked (versions match)
Object already in SD table → direct load from CPU cache, guaranteed fresh
→
Untracked (versions match)
CLFLUSH the object's lines (sanitize), then add a tracking entry
→
Stale (slot version advanced)
Clear all entries for that shadow slot, update shadow version, fall back to sanitize-on-entry

4 · Generalizing to CXL 2.0 — software mutual exclusion

Without HCC, XTRA replaces CAS-based locking with Lamport's fast mutual-exclusion algorithm, run per CD slot. A naive implementation needs Ω(N) space per lock (one flag per participant), and cacheline-granularity writeback means each host's flags must live in separate cachelines — over 512 B per latch on an 8-host pod. Two optimizations make this practical: latch metadata is provisioned per CD slot (bounded), not per object, and flags are packed column-major so one host's flags across many slots share a cacheline without cross-host overwrite risk. Hierarchical synchronization then caps the number of hosts that ever contend on the slow, CXL-latency path to at most one representative per host.

5 · Fault tolerance — redo logs and bounded recovery

XTRA assumes fail-stop hosts and an available memory pool. At commit, a transaction flushes its redo log to shared NHCC before applying updates. On a detected host failure, recovery only needs to: (1) scan the CD for locks held by the failed host, and (2) check whether each associated redo log is complete — rolling forward (replay + release) if complete, or aborting (just release) if not. Because both the CD and the logs are small and pool-resident, recovery avoids any host-reboot wait.

Follow the numbers, step by step

Worked examples

Four traces using the paper's own numbers: directory sizing, the on-demand-sharing collapse, the transaction-length penalty, and the HCC-capacity floor.

① Sizing the Coordination Directory and its load factor

An 8 MB CD, on a 32-host pod with 256 threads per host, all concurrently running transactions that each touch a dozen objects. Is 8 MB enough?

  1. Slots available: each slot is 64 bits = 8 bytes, so 8 MiB ÷ 8 B = 1,048,576 slots ≈ 10⁶ slots. (The paper's "10⁶" is a round-number approximation, not an exact count — and it treats MB here as MiB, i.e. 2²⁰ bytes, not a decimal 10⁶-byte megabyte.)
  2. Maximum concurrent threads: 32 hosts × 256 threads/host = 8,192 threads.
  3. Objects actively referenced: if each thread's in-flight transaction touches ~12 objects, that's 8,192 × 12 ≈ 98,300 active references.
  4. Load factor: 98,300 ÷ 1,000,000 ≈ 9.8% — under the paper's cited <10% figure for this exact scenario.
  5. Why this matters: at under 10% load, slot collisions (and the false contention they cause) stay rare, even though the CD is a thousand times smaller than a per-record scheme would need.
🗂️
Insight: the CD is sized to the concurrency level, not the dataset — that's the whole reason it fits comfortably inside even a shrunken HCC budget.

② Why Tigon collapses as the dataset grows

Tigon peaks at 2.4M keys with a 200 MB HCC budget. Trace what happens as the dataset scales to 5M and then 40M keys.

  1. At 2.4M keys: the working set's per-record metadata fits inside 200 MB of HCC. Remote accesses are almost always HCC hits — Perfect Hit ratio near 100%, per-key hit ratio 100%.
  2. At 5M keys: the working set now exceeds 200 MB. Per-key hit ratio starts falling; migrations become common. Throughput drops 4.3×; P99 latency rises 4.2×.
  3. At 40M keys: per-key hit ratio has fallen to 34%, and the Perfect Hit ratio — needing every access in a transaction to hit — collapses to near zero.
  4. Atomicity amplifies it: stall time now accounts for over 90% of transaction latency, because one migration stalls the whole transaction while it holds its other locks.
  5. Net effect: throughput falls 30×, P99 latency rises 588×, purely from the mismatch between a fixed 200 MB HCC budget and a growing per-record metadata footprint.
💡
Nothing about the workload changed — only the dataset size. That's the signature of a design whose synchronization cost scales with data, not concurrency.

③ Why longer transactions hurt on-demand sharing even more

Fix the dataset at 10M keys. Per-key hit ratio holds steady at 70% regardless of transaction length. Why does throughput still fall 6.8× as transactions grow from 1 to 9 keys?

  1. Perfect Hit needs every access to hit. With a steady 70% per-key hit rate, the probability all n accesses hit shrinks like 0.7ⁿ: at n=1 that's 70%; the paper reports the measured Perfect Hit ratio falls from ~70% to just 6% by n=9.
  2. Even one miss stalls the whole transaction — and the more keys a transaction touches, the more chances for at least one to miss.
  3. Stall time dominates: at n=9, stall time is over 87% of transaction latency, even though per-key hit ratio never moved.
  4. Result: throughput falls 6.8× and P99 latency rises 182× from n=1 to n=9 — a purely structural penalty from transaction length, independent of the per-key hit rate.
🗂️
Insight: this is exactly why XTRA's shared-everything design (every access goes directly through the CD, no migration wait) matters more as transactions get longer — the failure mode gets structurally worse, not just linearly worse, under on-demand sharing.

④ How far can the HCC budget shrink before XTRA breaks?

Shrink the HCC capacity from 200 MB toward 0 MB (fixing the dataset at S scale). Compare Tigon's and XTRA's behavior.

  1. 200→100 MB: Tigon's working-set metadata still fits — performance stays competitive.
  2. Below 100 MB: Tigon's metadata no longer fits; migrations spike and throughput collapses. At 0 MB, Tigon cannot run at all — it requires HCC atomics.
  3. XTRA down to 10 MB: the CD simply shrinks with the HCC budget; XTRA sustains high throughput, outperforming Tigon by 1.2–31.5× across this whole range.
  4. XTRA at 0 MB: falls back to XTRA-NHCC (a 200 MB CD placed in NHCC, managed by software mutual exclusion) — a 43.9–53.0% throughput drop versus XTRA at 10 MB HCC, but still operational.
  5. Bonus effect: shrinking the CD can occasionally improve XTRA's throughput slightly — a smaller CD leaves more CPU cache space for NHCC data itself, raising cache hit rates.
💡
Tigon needs HCC to exist at all. XTRA needs HCC to be fast — but degrades to software mutual exclusion rather than failing outright when HCC shrinks to nothing.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Does XTRA remove the need for locks in a CXL pod's distributed transactions?
Show answer
No. XTRA still uses locks — via OCC's write-set locking, implemented with CD-slot CAS (CXL 3.0) or software mutual exclusion (CXL 2.0). What XTRA removes is per-record lock/version metadata; the CD still performs real locking, just for a bounded set of slots instead of the whole dataset.Misconception: "decoupled" means "lock-free." It means "synchronization state is consolidated," not eliminated.
Problem 2 · medium
A CD is sized at 4 MB. How many 64-bit slots does it provide, and what does that number actually bound — dataset size or something else?
Show answer
4 MB ÷ 8 B/slot = 4,194,304 ÷ 8 = 524,288 slots (roughly half of the paper's 8 MB → ≈10⁶-slot example). This bounds the amount of concurrently active synchronization the directory can distinguish without collision — not the size of the protected dataset, since any object can map to any slot via hashing, so CD size alone doesn't cap dataset size. (The paper's own prototype and evaluation still assume the shared dataset fits within the CXL pool's total capacity; a dataset exceeding the whole pool is future work requiring a separate residency/tiering layer, §6.)Misconception: that directory size limits how much data XTRA can manage. It only limits how much simultaneous contention can be resolved without false conflicts — and even that has a ceiling: total pool capacity.
Problem 3 · medium
Increasing Zipfian skew from θ=0.7 to θ=0.9 boosts Tigon's throughput 3.3× in SmallBank, but pushing to θ=0.99 hurts every system, including XTRA. Why the reversal?
Show answer
Moderate skew concentrates the hot set, so for Tigon more of that hot metadata fits in the 200 MB HCC region (more Perfect Hits) — that's a capacity effect, favoring Tigon specifically. But extreme skew (θ=0.99) means many transactions contend on the same few hot objects simultaneously, driving up write-write conflicts and aborts for everyone — a concurrency-contention effect that no amount of HCC capacity or directory design fixes.Misconception: that skew is uniformly good or bad. It helps Tigon's HCC-fit problem up to a point, then a completely different problem (write contention) takes over and hurts everyone.
Problem 4 · hard
HCC capacity is reduced all the way to 0 MB. What exactly happens to Tigon, and what happens to XTRA?
Show answer
Tigon cannot run at all — its lock acquisition (2PL via CAS) fundamentally requires cross-host atomics, which require HCC. XTRA falls back to XTRA-NHCC: it places a 200 MB CD entirely in the NHCC region and manages it with software mutual exclusion instead of hardware CAS. It keeps working, at a real cost — 43.9–53.0% lower throughput than XTRA running with just 10 MB of real HCC.Misconception: that XTRA "requires" CXL 3.0 hardware. HCC only makes XTRA's CD faster; the same CD abstraction works, more slowly, without any HCC at all.
Problem 5 · medium
Fixing the dataset at 10M keys, per-key hit ratio in Tigon stays at 70% no matter the transaction length. Why does the Perfect Hit ratio still crash from 70% to 6% as transaction length grows from 1 to 9 keys?
Show answer
Perfect Hit requires every access in the transaction to be an HCC hit. If each access independently hits with probability ~0.7, the chance all n accesses hit falls roughly geometrically with n (0.7¹, 0.7³, 0.7⁵…) — even though the per-access rate never moves. At n=9 the paper measures this compounding effect bringing Perfect Hit down to 6%.Misconception: that a stable per-access hit ratio means stable transaction-level performance. Under an atomicity requirement, the weakest single access in the whole transaction determines the outcome.
Problem 6 · hard
A transaction writes to two distinct objects, O1 and O2, that happen to hash to the same CD slot. Walk through what happens during locking, and explain why this doesn't deadlock the transaction against itself.
Show answer
The transaction attempts to lock the shared slot for O1 — succeeds. It then attempts to lock the same slot again for O2. XTRA treats CD-slot locking as reentrant: since the transaction already holds the lock, the second acquisition succeeds automatically rather than blocking on itself. The commit protocol only releases the slot after all buffered writes (both O1 and O2) are applied and visible — so no intermediate, half-updated state is ever exposed to a concurrent reader.Misconception: that slot collisions always mean blocking. Intra-transaction collisions are handled for free by reentrancy; only inter-transaction write collisions cause an abort.
Problem 7 · medium
Shrinking the CD from 200 MB to 10 MB sometimes slightly improves XTRA's throughput rather than hurting it. Why?
Show answer
A smaller CD occupies less space when its slots are cached in the CPU's caches, leaving more cache capacity available for NHCC data itself. That increases the CPU cache hit rate for the actual shared data, reducing accesses to CXL memory — a gain that can outweigh the (small) extra collision risk from having fewer slots, as long as load factor stays low.Misconception: that a bigger synchronization structure is always safer or faster. Past the point needed to keep collisions rare, a bigger CD just competes with real data for CPU cache space.
Problem 8 · easy
In the highly write-intensive SmallBank benchmark, XTRA's OCC protocol slightly underperforms a 2PL ablation. Why would pessimistic locking ever beat optimistic concurrency control?
Show answer
OCC's whole advantage is cheap, lock-free reads — but that advantage only pays off if most transactions actually validate successfully. When writes are frequent and conflicts are common (as in write-intensive SmallBank), OCC transactions frequently fail validation at commit time and must abort and retry, wasting the work already done. 2PL avoids this by acquiring locks pessimistically up front, preventing the conflict from ever being discovered late.Misconception: that OCC is a strictly better default. It wins when conflicts are rare (its lock-free reads pay off); it can lose when conflicts are common (its late-discovered aborts get expensive).
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1Why can't CXL 3.0 just extend HCC to cover the whole pool?▾
Cross-host coherence requires a device-side snoop filter tracking which host caches which line, so it can issue back-invalidations on writes. That tracking state lives in limited on-device SRAM and grows with the number of hosts and tracked lines — vendor guidance and practical implementations expect it to cover only hundreds of MB, nowhere near a TB-scale pool.
Q2What's the one-sentence difference between XTRA and Tigon?▾
Tigon keeps data partitioned across hosts' local DRAM by default and migrates records into the HCC region on demand, putting migration on the critical path when metadata isn't already there. XTRA leaves data everywhere in the shared NHCC pool and instead consolidates synchronization state into a small, bounded, always-available directory — so there's no Tigon-style migration into the limited HCC region for shared data already resident in the CXL pool. (A dataset that exceeds the pool's total capacity is a separate problem the paper leaves to a future caching/tiering layer, §6.)
Q3Does XTRA require CXL 3.0 hardware to run at all?▾
No. XTRA-NHCC generalizes the exact same Coordination Directory abstraction to CXL 2.0 (no HCC at all) using software mutual exclusion. It's slower than hardware-accelerated XTRA, but the upper-layer OCC and coherence protocols are unchanged.
Q4What happens when two unrelated objects hash to the same CD slot?▾
A "slot collision." If both accesses are reads, nothing happens — OCC reads are lock-free and don't touch the version. If either is a write, the other transaction may be forced to conservatively abort even though the objects were unrelated. This only costs concurrency, never correctness: no true conflict is ever missed, because any two accesses to the same object always map to the same slot.
Q5How does lazy invalidation avoid stale reads without ever broadcasting to other hosts?▾
It doesn't need to broadcast, because the reader — not the writer — is the one who checks. Every read already fetches the object's CD-slot version for OCC validation; XTRA piggybacks a coherence check onto that same fetch. If the version hasn't moved since the reader last established freshness, the cached copy is guaranteed fresh; if it has, the reader invalidates locally before trusting anything cached.
Q6What exactly is the Shadow Directory for, if OCC validation already checks versions?▾
OCC validation is scoped to one transaction's short lifetime and one thread. But the physical CPU cache is shared by every thread on a host and persists across transactions. The SD closes both gaps: it remembers "this object was validated fresh under version V" across transactions (temporal), and shares that knowledge among all local threads (spatial) — so one thread's earlier check can safely be reused by another.
Q7Why does XTRA use OCC instead of 2PL for its concurrency control?▾
Because CD-slot collisions are unavoidable in a bounded, hashed directory, and OCC minimizes their damage: reads stay lock-free (a collision on a read costs nothing), and write locks are held only briefly, from validation to commit — not for the whole transaction. 2PL would hold locks (and thus collisions) for a transaction's entire duration, amplifying false contention. The one exception is write-heavy workloads, where OCC's late-discovered aborts can cost more than 2PL's up-front blocking (see Practice, Problem 8).
Q8How big is the Coordination Directory in practice?▾
Matched to the paper's HCC budget assumption of 200 MB. But the paper also shows XTRA sustaining strong performance with the CD (and HCC budget) shrunk all the way to 10 MB — the CD's necessary size tracks expected concurrency (an 8 MB directory already provides ≈10⁶ slots), not the dataset.
Q9What happens if a host crashes mid-transaction?▾
Its held locks would otherwise block every other host forever. XTRA's recovery scans the CD for locks owned by the failed host, then checks the completeness of that host's redo log in shared NHCC memory: a complete log means the transaction rolls forward (replay + release); an incomplete log means it never touched the data, so recovery just releases the lock. Since both the CD and the failed host's logs remain available in shared memory, surviving hosts don't wait for a reboot.
Q10Does XTRA handle a failure of the CXL memory pool itself?▾
Not in its current form — the paper explicitly assumes the pool stays available after a host failure, and discusses pool-level fault tolerance (checkpoint-and-log recovery, or cross-pool replication) only as future work, noting it wouldn't need to change XTRA's decoupled OCC or unified coherence protocols.
Q11Is XTRA the same kind of system as a memory-tiering scheme like TPP, Memtis, or Pond?▾
No — different layer entirely. TPP and Memtis decide where pages should physically live (DRAM tier vs. CXL tier) for a single host, under CXL 1.0-style tiering. Pond is CXL 2.0 multi-host memory pooling — sharing capacity across hosts, not deciding per-host placement. XTRA assumes that pooling/placement problem is already handled and instead solves cross-host agreement: once several hosts share the same pool, who's allowed to read/write what, right now, without corrupting each other's view. The paper explicitly scopes datasets exceeding CXL capacity as a separate, combinable tiering problem (§6).
Q12What did the authors leave for future work?▾
Two directions: (1) supporting shared datasets that exceed the entire CXL pool's capacity, by combining XTRA with a separate caching or tiering layer for data residency; and (2) tolerating failures of the CXL memory pool itself, via checkpoint-and-log recovery or cross-pool replication — without needing to change XTRA's core decoupled OCC or unified coherence design.

Glossary & further reading

Every term in one place, then a path to go deeper — plus a note on what's the paper's and what's this guide's framing.

Core terms
XTRAThe paper's system: decouples synchronization from data into a bounded Coordination Directory, and unifies OCC validation with lazy cache coherence.
Coordination Directory (CD)A flat array of 64-bit slots (1-bit lock, 5-bit host ID, 8-bit thread ID, 50-bit version) that objects hash to for synchronization.
Shadow Directory (SD)Host-local structure mirroring the CD, tracking which cached NHCC objects are known-fresh under the current slot version.
Decoupled OCCXTRA's concurrency control: lock-free reads validated against CD-slot versions; write locks acquired only at commit.
Deterministic mappingslot = Hash(pool-offset) mod N — every host derives the same CD slot for the same object, independently.
Slot collisionTwo distinct objects mapping to the same CD slot; causes false contention (a performance cost), never a correctness violation.
Unified cache coherenceReusing OCC's "has this changed?" version check as a lazy cache-freshness check, avoiding eager invalidation broadcasts.
Software mutual exclusionLamport's fast mutex, applied per CD slot with column-major flag layout and hierarchical (per-host, then cross-host) contention, generalizing XTRA to CXL 2.0.
Supporting terms
On-demand sharing (Tigon/Pasha)Partition data in host-local DRAM; migrate records into the HCC region on remote access. XTRA's main baseline.
Perfect HitA transaction whose every remote access hits HCC-resident metadata, requiring no migration.
Sanitization-on-entryCLFLUSH-then-track: the SD's response to an untracked-but-version-matching object, before trusting a CPU-cached copy.
Redo loggingWrite-ahead logs in shared NHCC memory, enabling any surviving host to recover a crashed host's in-flight transactions.
Reentrant lockingA transaction re-acquiring a CD slot lock it already holds succeeds automatically, avoiding self-deadlock on intra-transaction collisions.
Load factorActive concurrent references ÷ CD slot count; kept under ~10% in the paper's worked concurrency scenario to keep collisions rare.
P50 / P99 latencyMedian vs. tail latency; XTRA's biggest wins over Tigon show up specifically in P99 (up to 283.9×), reflecting fewer catastrophic stalls.
Fail-stop modelHosts crash cleanly (no Byzantine behavior); XTRA's fault tolerance model, assuming the CXL pool itself stays available.
