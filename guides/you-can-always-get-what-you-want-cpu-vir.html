SOSP 2026 · A Field Guide

Renting out the room without ever letting it look occupied

A pinned core looks 100% busy to the host even when the guest inside is doing nothing. This is the plain-English story of DDVM, the production system that safely shares that hidden idle time — 92,000 servers, three years, without touching the SLO.

Share a core only when profiling PROVES it's idle, never because host-side CPU% LOOKS low.

Before you begin

Quick glossary + eight primers

Acronyms first, then short expandable primers. Read in order or jump to what's unfamiliar.

IOPS/CPU ratioDDVM's workload signature: high ratio = small-packet, latency-critical (don't share); low = safe to share.

1Dedicated VMs and CPU pinning▾

A Dedicated VM's vCPU is statically pinned to one physical core (pCPU) — no other VM ever runs there. This removes "double scheduling" (guest scheduler + host scheduler fighting over the same core) but also means the core is locked even when the guest has nothing to do.

Now you're ready: DDVM's whole premise is unlocking that locked-but-idle time without giving up the pinning guarantee when the VM is actually busy.
2VM exits, HLT/MWAIT, and idle passthrough▾

Normally, when a guest executes HLT (halt until interrupt), it traps to the hypervisor (a VM exit) so the host can give the core to someone else. Idle passthrough disables that trap for Dedicated VMs — the guest stays "inside" during idle, avoiding wake-up latency, but the host can no longer see or reclaim the idle time. Host-side CPU utilization then reads ~100% regardless of actual guest demand.

Now you're ready: this is exactly why DDVM can't just watch host CPU% — it has to infer idleness a different way (Primer 6).
3Posted Interrupts and the IOMMU▾

Device passthrough lets a VM talk to hardware (e.g. a NIC) directly. Posted Interrupts let that hardware deliver an interrupt straight into the running vCPU via the IOMMU, with no hypervisor round-trip — fast, but it assumes the target vCPU is actually running on its core.

Now you're ready: once two vCPUs share one core, that assumption breaks — one of them is asleep half the time. Mediated PI (§4.3) is the fix.
4Tail latency and P99▾

P99 latency = the value below which 99% of requests complete; it captures the slow outliers that average latency hides. Cloud SLOs and support tickets are almost always about the tail, not the mean — which is why DDVM's scoring formula weights P99 heaviest (§3.2).

Now you're ready: nearly every chart in this guide is a P99 (or P99-weighted) comparison.
5Oversubscription ratio▾

Mapping more vCPUs than physical cores. 1.1× means 48 vCPUs sharing 44 pCPUs — a modest 4-core deficit spread across the pool, not a wholesale doubling. DDVM's deployed target is deliberately this conservative.

Now you're ready: every SLO number in this guide is measured at 1.0×–1.33×, never higher — that ceiling is a design choice, not a hardware limit (§7).
6Why host CPU% can't detect idleness▾

With idle passthrough on, an idle vCPU never exits, so the host's own accounting shows the core pinned to full. DDVM instead learns each vCPU's idle-loop return address (from the guest RSP, sampled off a timer interrupt) and treats repeated hits on that address as "idle."

Now you're ready: this RSP-signature trick, plus the IOPS/CPU ratio, together form "workload signature profiling" (§4.2).
7NUMA nodes▾

A multi-socket server splits memory and cores into NUMA nodes; accessing local memory is faster than remote. DDVM only pairs and reschedules vCPUs within the same NUMA node to keep migration cheap and avoid cross-node memory penalties.

Now you're ready: "NUMA-local re-pinning" costs ~11µs; crossing nodes means a full live migration instead, which DDVM treats as a rare escalation.
8Lock-holder/waiter preemption hazards▾

When a vCPU holding a lock (LHP) or waiting on one (LWP) gets descheduled mid-critical-section, every other thread waiting on that lock stalls — a classic virtualization pathology, alongside blocked-waiter wakeup (BWW) and RCU-reader preemption (RRP).

Now you're ready: DDVM doesn't detect these individually; it just shortens the preemption window (idle reclaim + mediated PI) and restricts sharing to VMs already profiled as idle, so these hazards rarely get a chance to form.
The whole story in one place

DDVM in a nutshell

The tax, the fix, and how the pieces connect.

Dedicated VMs get near-bare-metal performance from three hardware passthrough tricks — CPU pinning, interrupt passthrough, idle passthrough — but those same tricks lock a physical core to one VM permanently. In production, 74% of Dedicated VMs average below 10% CPU utilization, yet they occupy 95% of physical hosts. The capacity is there; the mechanism that makes it fast also makes it unshareable and, worse, invisible — idle passthrough means the host sees a fully busy core no matter what the guest is actually doing.

DDVM (Dynamic-Dedicated VM) resolves this without relaxing the SLO contract. Each vCPU can move between dedicated mode (owns a core alone, exactly like today) and shared mode (time-multiplexes a core with one other vCPU), decided by three mechanisms: workload signature profiling to find genuinely idle vCPUs (CPU%, IOPS/CPU ratio, and an idle-instruction signature — never just one signal), mediated posted interrupts to bound wake-up latency when a vCPU is preempted, and occupancy-aware idle reclamation to decide, per pairing, whether HLT should stay passthrough or trap to the host.

The payoff, at a conservative 1.1× oversubscription: +10.5% fleet-wide CPU utilization across 92,000 nodes (37 regions, 3+ years), an SLO score of 83.5 (above the 83.3 acceptance bar), 67.1% lower P99 latency than naive oversubscription, and a mature-deployment ticket rate of just 0.00035%/month.

🍯 Key takeaways

  • Passthrough gives Dedicated VMs bare-metal speed but makes idle time both unshareable and invisible to the host.
  • Low host-side CPU% is not a reliable idle signal — it must be combined with an IOPS/CPU ratio and an idle-instruction signature.
  • Sharing means time-multiplexing, never simultaneous co-running on sibling SMT threads of two different tenants.
  • Mediated PI bounds interrupt latency for a preempted vCPU; occupancy-aware idle reclaim trades passthrough for fast wake-up only while sharing.
  • Deployed target: SLO score ≥83.3 (≤20% tail-latency degradation) at 1.1× oversubscription — a policy choice, not a hardware ceiling.
  • Result: +10.5% utilization, ~500,000 vCPUs reclaimed fleet-wide, 0.00035% monthly ticket rate after 32 months at full deployment.
Six everyday pictures

How to think about DDVM

Each stands alone. Every card ends with where the picture breaks.

The core tension

The "do not disturb" sign that never flips

A hotel guest hangs "Do Not Disturb" once and the sign never turns back even after they leave — housekeeping (the host) has no way to know the room is actually empty. That's idle passthrough: it hides the guest's true occupancy from the host, so the host must go find another way to check the room.

Where it breaks: a real sign is binary; DDVM's signal is a fused, multi-second judgment (CPU%, IOPS/CPU, idle signature), not one flip.
Workload signature

Two "busy" desks, only one really working

Two employees both look occupied at their desks. One is deep in spreadsheets (low keystrokes, steady output — like Redis: small CPU footprint but frequent urgent messages). The other is shuffling papers with nothing due. CPU% alone can't tell them apart; DDVM's IOPS/CPU ratio can — a flood of small I/O per unit of CPU flags "don't interrupt this one."

Where it breaks: the ratio is a proxy, not a direct read of latency sensitivity — the paper itself flags this as the piece it would revisit first.
Mediated Posted Interrupt

A doorman who runs to fetch you

Standard posted interrupts are like a doorbell buzzed into your apartment — useless if you've stepped out. Mediated PI is a doorman who, seeing you're not home, immediately goes and gets you rather than leaving the package waiting for your next scheduled return.

Where it breaks: the doorman also wakes your whole household (all of a VM's vCPUs), not just you — deliberate, because interrupt top/bottom halves can land on different cores.
Occupancy-aware idle reclaim

A shared desk, ready to spring up

One desk, two roommates. While only one uses it, they can lounge there freely (idle passthrough). The moment they're sharing the desk with someone waiting, lounging stops — every pause is a chance to hand the chair over immediately (idle exit), so the waiting person never sits in the hallway.

Where it breaks: DDVM tried finer-grained toggling (switch mode per sleeping vCPU) and found the switching itself too costly — the real system only toggles per pairing, not per nap.
The 1.1× ceiling

A crowded elevator, not a packed one

1.1× oversubscription is like an elevator rated for 10 that occasionally carries 11 — noticeably tighter, never dangerous. Push it to 1.33× and you're regularly overcapacity: still moving, but everyone feels it (SLO score falls from 63.7 to 49.3).

Where it breaks: the elevator's limit is structural; DDVM's is a policy choice bound by profiling accuracy and the two-way sharing cap, not physics — it could rise with a better signal.
Correlated spikes

A fire drill with three exits

If every colocated VM wakes at once (a flash sale), DDVM doesn't panic — it un-pairs within one 400ms epoch, then tries the nearest free NUMA-local core, and only as a last resort evacuates the whole VM to another host. Three widening exits, used in that order.

Where it breaks: unlike a real fire drill, nobody is ever "dropped" mid-evacuation — the vCPU keeps time-sharing its core the whole time, just more tightly, until a wider exit opens.
The full explanation

How it actually works

Mechanism by mechanism, with the paper's key flows rebuilt as diagrams.

1 · Detecting real idleness

At vCPU init, DDVM briefly re-enables idle exits and records the guest RSP on each HLT/MWAIT trap. Because a guest's idle loop has a stable return address, five consecutive matching exits establish an idle signature. Passthrough is then re-enabled, and DDVM instead samples RSP off the periodic millisecond timer interrupt — if it matches the signature, the vCPU is idle, with no guest memory inspected and no new trust boundary crossed.

2 · Qualifying for sharing

A VM becomes eligible only when all three hold: CPU usage typically below 10% per core, IOPS/CPU ratio below 100 (rules out Redis-like small-packet services), and a consistently matching idle signature. Eligible VMs are then paired, every 400ms epoch, with the lowest-load partner on the same NUMA node — two highly active VMs are never colocated.

⚠
Robustness bias: every threshold is tuned toward false negatives. Misclassifying a busy VM as idle only forgoes reclaimable capacity — it never risks an SLO, because the three signals must be defeated simultaneously.

3 · Mediated Posted Interrupt

Native Posted Interrupt delivery assumes the target vCPU is running; if it's blocked (asleep on a shared core), the interrupt is queued for the next scheduler tick — unbounded latency. DDVM's step 4 detects the blocked target and immediately boosts and reschedules it, preempting whoever currently holds the core. It boosts all of that VM's vCPUs, not just the target, because interrupt top-half (hard IRQ) and bottom-half (soft IRQ, e.g. via RPS) often run on different cores.

4 · Occupancy-aware idle reclamation

Idle passthrough helps a Dedicated VM (no exit overhead) but hurts a shared one: an idle vCPU keeps its time slice, so a co-located vCPU's interrupt can't be handled until that slice expires — even with Mediated PI immediately making the target runnable, the VM-exit for the idle sleeper still sits on the critical path. DDVM's rule: passthrough while exclusive, reclaim (trap on HLT) while shared. More fine-grained toggling (per sleep event) was tried and rejected — the switching overhead outweighed the benefit.

💡
Net effect: a colocated idle vCPu's HLT becomes a normal, fast VM exit, so an interrupt for its partner needs only one VM-entry instead of waiting out a full time slice.

5 · Safety net for correlated spikes

If a shared vCPU turns CPU-intensive or latency-sensitive mid-epoch, DDVM breaks the pairing (within ~400ms), then searches the local NUMA node for the lowest-load core (~11µs typical re-pin cost), and only escalates to cross-host live migration if nothing local is free. Across 39 months, NUMA-level migration stayed below 0.5% on all but three days — each a nationwide sales event.

Follow the numbers

Worked examples

Five calculations straight from the paper's data, carried through step by step.

① Computing the SLO score at 1.1×

Table 4 reports aggregate degradation factors at 1.1× oversubscription: S̄avg = 1.48, S̄99 = 1.80, S̄max = 1.20. Using the §3.2 formula, what's the SLO score?

  1. Weight each factor: 1·1.48 + 1.2·1.80 + 0.5·1.20 = 1.48 + 2.16 + 0.60 = 4.24.
  2. Normalize by the weight sum (1 + 1.2 + 0.5 = 2.7): S̄ = 4.24 ÷ 2.7 = 1.570.
  3. Convert to score: SLO Score = 100 ÷ 1.570 = 63.7 — matches Table 4 exactly.
  4. Compare to the bar: 63.7 < 83.3, so this benchmark set alone falls below the acceptance threshold, even though the deployed ticket rate stays low (§5.4 explains the gap: eligibility here is forced, not profiled).

② Why the 20% tolerance line sits at 83.3

A uniform 20% latency increase means every S term equals 1.2. Plug that in.

  1. All three degradation factors = 1.2: 1·1.2 + 1.2·1.2 + 0.5·1.2 = 1.2·(1+1.2+0.5) = 1.2 · 2.7 = 3.24.
  2. Normalize: 3.24 ÷ 2.7 = 1.2 (the weighting cancels perfectly for a uniform degradation).
  3. Score: 100 ÷ 1.2 = 83.3 — the acceptance bar is, by construction, "no metric degrades by more than 20% on average."

③ IOPS/CPU: telling Redis apart from a busy-looking VM

Two VMs both look "active." VM P: CPU = 2%, IOPS = 50/s. VM Q (Redis-like): CPU = 3%, IOPS = 900/s. Which is safe to share?

  1. VM P's ratio: 50 ÷ 2 = 25 — well under the 100 threshold. Low CPU, low I/O pressure: genuinely idle, safe to share.
  2. VM Q's ratio: 900 ÷ 3 = 300 — over the threshold despite similarly low CPU usage.
  3. Conclusion: CPU usage alone (2% vs 3%) makes the two VMs look nearly identical. Only the IOPS/CPU ratio exposes that VM Q is a small-packet, latency-critical service that must stay dedicated.

④ Steal-rate: a sevenfold rise from a tiny base

Table 5: Steal_Rate₅ is 0.86‱ for Dedicated VMs, 6.1‱ for DDVM at 1.1×.

  1. Relative increase: 6.1 ÷ 0.86 ≈ 7.1× — sounds alarming in isolation.
  2. Absolute scale: 6.1‱ = 6.1 samples per 10,000, i.e. <0.1% of samples cross even the loosest (5%) steal threshold.
  3. Convergence at higher X: at X=50, Dedicated = 0.06‱, DDVM = 0.12‱ — only 2×, because severe contention is rare at 1.1× regardless of sharing.
  4. Cross-check against tickets: the monthly ticket rate (0.00035%) did not rise as these steal samples became more frequent — the increase stays below what tenants perceive.

⑤ Re-pinning cost vs. profiling epoch

NUMA-local re-pinning takes ~11µs on average; the profiling epoch is 400ms.

  1. Convert the epoch to µs: 400ms = 400,000µs.
  2. Fraction consumed by one re-pin: 11 ÷ 400,000 ≈ 0.0028% of one epoch.
  3. Fleet-wide savings: ~500,000 vCPUs reclaimed ÷ 92,000 nodes ≈ 5.4 vCPUs per node on average, at a per-split cost too small to matter operationally.
🍯
The engineering bet pays off precisely because the corrective action (re-pin) is ~36,000× cheaper than the decision interval (epoch) — the system can afford to be wrong briefly and correct fast.
Test yourself

Practice problems

Try each before opening the answer.

1 · easy
A host reports a Dedicated VM's pCPU at 100% utilization around the clock. Does that mean the guest is truly compute-bound?
Show answer
Not necessarily. With idle passthrough enabled, an idle vCPU still holds its core without exiting, so host-side accounting reads 100% whether or not the guest has real work. DDVM has to infer true idleness via RSP-signature sampling instead.Misconception: host CPU% is ground truth. Under passthrough it's a ceiling artifact, not a demand measurement.
2 · medium
Two hypothetical runs at some ratio give S̄avg=1.3, S̄99=1.5, S̄max=1.1. Compute the SLO score and say whether it clears the acceptance bar.
Show answer
Weighted sum = 1·1.3 + 1.2·1.5 + 0.5·1.1 = 1.3+1.8+0.55 = 3.65; ÷2.7 = 1.352; score = 100÷1.352 ≈ 73.9. That's below 83.3, so it would not clear the bar.Misconception: eyeballing the raw factors (all "close to 1.x") as "fine." The P99 weight (1.2) dominates, and 73.9 vs the 83.3 bar is a meaningful 9-point miss.
3 · easy
Does DDVM ever place two different tenants' vCPUs on sibling hyperthreads of the same physical core?
Show answer
No. Sharing in DDVM means time-multiplexing — at any instant one VM owns the entire core including both sibling threads. Two VMs alternate ownership at scheduling boundaries; they never co-run simultaneously.Misconception: "core sharing" implies SMT co-tenancy. DDVM deliberately avoids the cross-tenant SMT side-channel concern by never doing that.
4 · medium
Why does Mediated PI boost every vCPU of the target VM, not just the one the interrupt is addressed to?
Show answer
Interrupt handling has a top half (hard IRQ, bound to a specific core) and a bottom half (soft IRQ, e.g. distributed by Receive Packet Steering across other cores). If only the addressed vCPU were boosted, the bottom-half processing on a different, still-preempted vCPU would remain delayed, so DDVM wakes the whole VM.Misconception: one interrupt = one vCPU's concern. The two-phase IRQ model means end-to-end latency depends on multiple cores.
5 · medium
Why does DDVM disable idle passthrough specifically when two vCPUs share a core, but keep it enabled for an exclusive vCPU?
Show answer
When exclusive, an idle guest's HLT costs nothing to pass through — no one else needs the core. When shared, an idle vCPU that keeps passthrough still occupies its time slice, delaying its partner's interrupt handling until the slice naturally expires. Trapping HLT to the host while shared lets the partner get a fast VM-entry instead of waiting out the slice.Misconception: idle passthrough is strictly good. It's good only when there's no one else waiting for the core.
6 · hard
Table 5 shows Steal_Rate at X=5 rising 7× under DDVM, yet the ticket rate stayed flat at 0.00035%/month. Reconcile this.
Show answer
Steal_Rate is a leading, provider-side proxy for contention, not a direct SLO measurement — CSPs can't read tenant-level latency, so they watch this instead. A 7× rise from an extremely small base (0.86‱→6.1‱) still means under 0.1% of samples cross even the loosest 5% threshold; the increase is real but stays below the level that translates into tenant-visible degradation, which is what tickets measure. It's a canary the team watches before widening rollout, not a rollout blocker on its own.Misconception: any statistically significant increase in a proxy metric implies user harm. Magnitude and base rate matter as much as the ratio.
7 · hard
§5.4 forces every VM in the test harness to share regardless of workload type, and gets SLO scores of 63.7–49.3 — below the 83.3 bar. Does this mean the deployed 1.1× system is actually unsafe?
Show answer
No — that experiment measures the cost of sharing if the profiler were bypassed, i.e. an upper bound on harm. In production, the profiler excludes exactly the I/O-heavy, latency-sensitive workloads (like the YCSB core / Memcached mix) that drove those low scores, via the IOPS/CPU signal. The deployed system's real-world proxy — the 0.00035% ticket rate over 32 months — reflects the profiled, selective version, not the forced-sharing benchmark.Misconception: a benchmark number and the deployed system's behavior are interchangeable. §5.4 explicitly measures a different (unfiltered) condition.
8 · medium
The paper says the 1.1× ceiling is "a policy choice... not an architectural limit." What three constraints does it name as currently binding that ratio?
Show answer
(1) Sharing is capped at two vCPUs per core, since SLOs degrade sharply beyond that; (2) eligibility quality is bounded by the IOPS/CPU proxy, which is not a direct latency-sensitivity measurement — §5.4 shows real cost when eligibility is forced; (3) DDVM doesn't model cache or memory-bandwidth interference, so pushing density further would stress a resource it can't currently see.Misconception: 1.1× is a hardware or algorithmic ceiling. It's the ratio these three constraints currently justify — better signals or added partitioning could raise it.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does "Dynamic" mean in DDVM?▾
Each vCPU can move at runtime between dedicated mode (exclusive core ownership, like a conventional Dedicated VM) and shared mode (time-multiplexed with one other vCPU), based on live profiling — never a permanent, provisioning-time choice.
Q2Is this the same as spot/preemptible instances or harvesting VMs?▾
No. Spot and harvesting systems place best-effort work on reclaimed capacity and accept it can be preempted or evicted — a weaker service class. DDVM never degrades the tenant's tier: reclaimed capacity stays inside the Dedicated-VM SLO contract.
Q3Why can't the host just watch CPU utilization to decide when to share?▾
Idle passthrough makes host-observed CPU% read ~100% for a pinned core regardless of guest demand. A separate signature (idle-instruction RSP matching) is needed to see through it, plus an IOPS/CPU ratio to catch I/O-bound workloads that look idle on CPU alone but are latency-critical.
Q4Does DDVM inspect guest memory or require guest cooperation?▾
No. It reads only VMCS state already visible to the hypervisor (guest RSP) and virtio ring descriptors on the DPU. No guest modification, no new information-leakage concerns, no paravirtualization.
Q5What happens if a "shared" vCPU suddenly becomes busy?▾
The profiler detects it within one 400ms epoch and breaks the pairing, restoring exclusive ownership. If no local NUMA core is free, DDVM migrates the vCPU to the lowest-load core in-node; only as a last resort does it live-migrate the whole VM across hosts.
Q6Why is 1.1× the deployed ratio and not something more aggressive?▾
It's the ratio the paper's three current constraints justify: a hard 2-way sharing cap, an IOPS/CPU proxy that isn't a direct latency measurement, and no cache/bandwidth interference modeling. Higher ratios show sharply falling SLO scores (63.7→55.1→49.3 at 1.1×/1.2×/1.33×).
Q7How is this different from posted interrupts alone?▾
Native posted interrupts assume the target vCPU is running; if it's blocked on a shared core, delivery waits for the next scheduler tick — unbounded. Mediated PI adds an explicit boost-and-reschedule step the moment a blocked target's interrupt arrives.
Q8Does idle reclamation hurt Dedicated (non-shared) VMs?▾
No — it's occupancy-aware: idle passthrough stays enabled whenever a vCPU exclusively owns its core, exactly as in a conventional Dedicated VM. Reclamation (trapping HLT) only activates while that core is actively shared.
Q9What does the paper identify as its weakest link?▾
The IOPS/CPU ratio used for latency-sensitivity detection — it's a useful proxy for the network-bound services that dominate support tickets, but not a direct measurement of latency sensitivity. The authors say a more direct signal would likely allow sharing more aggressively than 1.1×.
Q10Does DDVM address cache or memory-bandwidth contention between colocated VMs?▾
Not currently — it arbitrates only CPU time between pinned vCPUs. The authors note this as complementary future work, pointing to cache/bandwidth partitioning systems like Heracles and PARTIES (§6).
