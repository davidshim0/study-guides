SOSP 2026 · A Field Guide

Skills are code. LLMs are heterogeneous processors with no compiler.

118,000 agent skills get pasted as raw text into whatever model happens to be running. The same skill can score 100 on one model-harness pair and 0 on another. SkillVM gives skills the compiler and runtime that code has always had.

📄 "Skill VM: Write Once, Run Everywhere Efficiently" · Chen, Feng, Xia, Chen (SJTU IPADS) 🎓 OS/compiler background assumed — primers focus on the agent-skill domain ⏱ ~30 min read
🧩

Don't fix the skill's prose for one model. Profile the target's capabilities, then compile the skill against that profile — AOT at install, JIT at runtime.

Before you begin

Quick glossary, then the domain you don't already know

You know compilers, JIT/AOT, and OS scheduling cold — the primers below skip that and focus on the agent-skill ecosystem SkillVM operates in.

Quick glossary — key acronyms, up front
SkillA distributable Markdown pack (metadata + instructions + bundled scripts) that teaches or constrains an agent for one task class.
Agent harnessThe runtime between model and world: manages the LLM connection, registers tools, dispatches calls, controls context window. E.g. Claude Code, OpenCode, Codex.
ReAct loopReason → act (tool call) → observe → reason again, repeated until the task is done. The execution model every agent harness implements.
AOT / JITAhead-of-time (compiled once, at skill install) vs. just-in-time (compiled/adapted at runtime, using execution feedback).
DAGDirected acyclic graph — here, a skill's steps as nodes and data dependencies as edges, extracted to expose parallelism.
P1 / P2 / P3The paper's three mismatch failure modes: model, harness, environment (dependency) mismatch.
Ch1 / Ch2 (paper's §3 challenges)The two challenges that make fixing P1–P3 hard: combinatorial target space, and skills being unstructured natural language. Not the same "C1/C2" as Appendix A's recompilation admission gate (recurrence/generality/no-trade-off) — the paper reuses the labels for two unrelated pairs of conditions.
SOTAState-of-the-art — here, top-tier models like Claude Opus 4.6 or DeepSeek-V3.2, contrasted against "mid-tier" and "small" model tiers.
1What a "skill" actually is▾

Structurally: metadata (name/description/triggers) for discovery, an instructions body (multi-step workflow in prose), and bundled resources (scripts, templates). No weight modification — it's pure prompt-level augmentation, loaded via progressive disclosure when the harness decides it's relevant.

Over 118,000 exist across two platforms the paper studies (clawhub.ai, skills.sh), both long-tailed: most skills get <100 downloads.

Now you're ready: think of a skill as a source file with no formal grammar — the compiler has to recover structure from prose before it can do anything else (this is the paper's Challenge 2 from §3 — not the same "C2" used later for the recompilation gate's generality condition).
2Why the same skill behaves differently per model/harness▾

A skill is written once, with implicit assumptions baked in about what the executing model can do and what tools the harness exposes. Today, agents just concatenate the skill text into context — no adaptation layer exists.

Concretely: enabling skills degrades 15% of tasks overall, leaves 17% unchanged, and yields no improvement on 87% of tasks for at least one tested model. Weaker models misread library APIs as CLIs; richer harnesses' extra tool documentation can push an otherwise-fine model into a formatting failure.

Now you're ready: this is the fragility SkillVM's capability-based compilation exists to close — matching skill assumptions to a measured target profile instead of hoping they align.
3What "primitive capability" means here▾

Not a benchmark score — an indivisible, demand-side unit describing one dimension of model/harness behavior (e.g. tool.exec, reason.arithmetic, follow.procedure), each with ordered proficiency levels L1<L2<L3 where a higher level's requirement can't be satisfied by a lower one.

26 of these, derived empirically from 15,063 skills, cover 95% of the corpus. Think of it as an ISA feature list — except the "instructions" are things like "can this model correctly resolve a relative file path inside a tool call."

Now you're ready: capability profiling is literally a microbenchmark suite per primitive, run once per target and cached — analogous to cpuid feature detection before dispatching to a code path.
4Compensation vs. substitution▾

Two transform strategies the compiler picks between once it knows the gap between a skill's required capability level and the target's measured level. Compensation: target has the capability but at a lower level — rewrite the skill to need less of it (more explicit instructions, examples, tighter constraints). Compensation is preferred because it keeps the skill's original approach.

Substitution is the fallback: capability absent, or the gap too large to compensate — swap in a different implementation path from a pre-identified equivalence class (e.g. python-pptx → PptxGenJS).

Now you're ready: this is like choosing between a software-emulated instruction (compensation — slower, but preserves semantics) and rewriting the routine to avoid the missing instruction entirely (substitution).
5Code solidification, in one sentence▾

75% of skills embed code whose shape repeats across invocations with only parameters changing (a curl template, a PDF-merge script). Solidification watches the model regenerate that shape across consecutive invocations; once it's consistent enough (a code-signature match streak), the runtime swaps in a compiled template function, skipping LLM code generation for that call — though per Appendix B, the template's output still goes back to the model for validation/acceptance before it's used.

Now you're ready: this is a tracing JIT's hot-path compilation, except the "trace" is LLM-generated source code and the "deoptimization" trigger is a signature mismatch or an output the model itself rejects.
6Why adaptive recompilation needs a strict admission gate▾

An LLM-authored "fix" to a skill is not a proof — it's a proposal that could just as easily regress a task that used to pass. SkillVM's runtime only accepts a recompiled skill variant if it clears a formal gate (Appendix A): the failure must recur across runs (not be one bad rollout), the fix must be stated generally (not hard-coded to one failing task), and no previously-passing task may regress beyond a tolerance.

Now you're ready: this is profile-guided recompilation with a correctness contract, not just "let the model edit its own prompt and hope."
7Three levels of parallelism SkillVM extracts▾

Script-level: one step applies the same op to many independent items — rewrite with ordinary language parallelism (xargs -P, multiprocessing), no harness support needed. Tool-level: independent steps each need one tool call — batch them into a single LLM turn, requires harness batch-dispatch support. Agent-level: independent multi-turn sub-tasks — spawn sub-agents, requires harness sub-agent support.

Now you're ready: this is dependency-graph-driven ILP extraction, except the "instructions" are workflow steps in prose and the "issue width" is bounded by what the harness can actually dispatch concurrently.
The whole story in one place

SkillVM in a nutshell

The mismatch problem, the compiler/runtime that fixes it, and how the pieces connect.

Agent skills are treated as raw context: the same Markdown file gets pasted into whatever model and harness happen to be running, with zero adaptation. Because models and harnesses vary wildly in what they can reliably do, this fragility is measurable — skills degrade 15% of tasks, leave 17% unchanged, and fail to help on up to 87% of tasks for at least one tested model.

SkillVM's framing: skills are code, LLMs are heterogeneous processors, and what's missing is the compiler and runtime that every other code form has had since assembly. It builds one: an AOT compiler that runs once per skill-target pair at install time (capability-based compilation, environment binding, concurrency extraction), and a JIT optimizer that runs continuously during execution (code solidification, adaptive recompilation, resource-aware scheduling).

The capability layer is the crux: the compiler decomposes a skill's needs into 26 primitive capabilities at graded proficiency levels, profiles the target model+harness against the same set with microbenchmarks, and closes any gap with compensation (rewrite to need less) or substitution (swap implementation path) — whichever preserves the skill's intent best.

The payoff: across ten LLMs and four harnesses on 118 tasks, SkillVM improves task completion by an average of 15.3%, cuts token consumption up to 40% on tasks that already succeed, and delivers 3.2× speedup from parallelism plus 19–50× latency reduction from code solidification.

🧩 Key takeaways

  • Raw-text skill injection is "interpreted execution only" — no target-specific compilation happens at all today.
  • Primitive capabilities (26, four categories, L1<L2<L3) are the abstract vocabulary that makes cross-target adaptation tractable.
  • Compensation (rewrite to need less) is preferred over substitution (swap implementation) because it preserves the skill's original intent.
  • Environment binding pre-installs dependencies via a generated script, instead of leaving the model to diagnose missing packages live.
  • Concurrency extraction turns sequential prose into a validated DAG, mapped to script/tool/agent-level parallelism.
  • Code solidification promotes stable, repeated LLM-generated code into compiled functions that bypass inference.
  • Adaptive recompilation only ships a fix that clears a formal recurrence + generality + no-regression gate.
  • Result: +15.3% completion, up to 40% fewer tokens, 3.2× parallel speedup, 19–50× solidification speedup.
Six everyday pictures

How to think about SkillVM

Each stands alone — read in any order. Every card ends with where the picture breaks down.

The core idea · Capability profiling

cpuid before dispatch

Code that branches on a hardware feature flag doesn't guess — it probes first. SkillVM does the same for skills: it microbenchmarks each primitive capability once per target, caches the profile, and only then decides whether a skill's tool.exec requirement can run as-is or needs a fallback path.

Where it breaks: CPU feature flags are binary and stable across a boot session; LLM capability is graded (L1–L3), fuzzy, and can drift between requests — which is exactly why JIT-time adaptive recompilation exists as a second line of defense.
The transform choice · Compensation vs. substitution

Trap-and-emulate vs. rewrite the routine

Hit an unsupported instruction, and a VM has two options: trap and emulate it in software (slower, but the program's logic is untouched), or recompile the routine to avoid needing it at all. SkillVM's compensation mirrors trap-and-emulate — add explicit instructions, absolute paths, worked examples until the model can clear the gap. Substitution mirrors the rewrite — swap python-pptx for PptxGenJS when the gap is unbridgeable.

Where it breaks: instruction emulation is deterministic; "compensating" a model with a clearer prompt is probabilistic — it raises the odds of success, it doesn't guarantee it, which is why the admission gate on recompilation still measures outcomes before shipping.
Recompilation safety · The admission gate

PGO with a regression suite, not vibes

Profile-guided optimization only ships a hot-path recompile if it actually helps on representative traffic. SkillVM's adaptive recompilation applies the same discipline to an LLM-authored skill edit: the failure must recur (not one bad rollout), the fix must be statable without referencing the specific failing input, and no previously-passing task may regress past a tolerance — Algorithm 1's three-gate contract (C1/C2/C3).

Where it breaks: PGO's "representative traffic" is a fixed corpus you control; a skill's task distribution in the wild can shift after deployment, so the gate is necessary but not sufficient — it's evaluated against a held-out task set the compiler had access to, not the true future workload.
Code solidification · Trace-based JIT

A tracing JIT for LLM-generated code

V8/HotSpot watch a loop execute the same bytecode shape repeatedly, then compile the hot trace to machine code. SkillVM watches the model regenerate the same code signature (regex over structure, not literal text) across consecutive invocations; once it matches N=3 times running, the compiler's pre-built template is promoted to a callable function and subsequent calls skip the LLM entirely.

Where it breaks: a tracing JIT's guard checks are cheap machine comparisons; here the "guard" is a full LLM turn whose output must match a signature, so promotion amortizes cost only across enough repeat invocations — and demotes (falls back to the LLM) after M=3 consecutive execution or acceptance failures.
Concurrency extraction · ILP-style dependency analysis

Building a dependency DAG out of prose

A superscalar core doesn't execute instructions strictly in program order — it builds a dependency graph and issues independent ones in parallel. SkillVM does the analogous analysis on a skill's numbered steps: build a DAG from data dependencies, validate it (acyclic, no dangling nodes), then map independent branches to script-, tool-, or agent-level parallelism depending on what the harness actually supports.

Where it breaks: a CPU's dependency graph is derived from a formal ISA with precise read/write sets; the DAG here is LLM-inferred from natural-language steps, so a wrongly-inferred independence is possible — which is why the compiler validates structurally (acyclic, no orphans) before trusting it, and unsupported opportunities fall back to sequential.
Environment binding · Config management, not the LLM

A provisioning script, run before the app starts

You don't ask your application to apt-get install its own missing library at runtime and hope it guesses the right package name — a setup script checks and repairs the environment before the app ever launches. Environment binding is exactly that: presence-check each dependency (pip show, which), generate an idempotent repair script, and run it before the skill's context is even loaded.

Where it breaks: a Dockerfile's dependency list is author-declared and (mostly) trusted; here 59% of skills that use an external dependency declare it incompletely or not at all, so the compiler treats the author's manifest as evidence, not ground truth, and probes the actual host state directly.
The full explanation

How it actually works

Section by section, with the paper's mechanisms rebuilt as diagrams.

1 · Where the fragility comes from

A skill's instructions implicitly assume a level of model competence, a set of harness tools, and a provisioned environment. None of the three is checked before execution. Across 15,063 classified skills: 52% are tool-reference, 28% procedural, 20% generative; 76% contain explicit procedural structure (numbered steps, branches); 75% embed repeatable code-like fragments; 53% require an external package or tool, and of those, 59% declare their dependencies incompletely or not at all.

🌱
Concretely: the pptx-creation skill recommends PptxGenJS. Opus 4.6 and Gemini 3 Flash both score 100. Devstral-small misreads it as a CLI, repeatedly runs the wrong commands — but scores 95 with no skill at all, defaulting to python-pptx. The skill's implicit assumption (model can distinguish a library API from a CLI) holds for frontier models, not weaker ones.

2 · Defining primitive capabilities — and their levels

A primitive capability is an indivisible, demand-side unit — composable, general (broad enough across many skills), and semantically independent (structural correctness, not output quality). Derived in two stages: 50 curated skills → 19 initial primitives via LLM-assisted decomposition and manual review against the three principles; validated against the full 15,063-skill corpus, adding a primitive only if it covers ≥1% of skills. Converged on 26 primitives across four categories, covering 95% of the corpus.

PrimitiveL1L2L3
gen.code.shellBasic commands (ls, cat)Pipes, redirection, loopsComplex pipelines (sed, awk)
reason.arithmeticSingle-step opsMulti-stepCompound
tool.execSingle commandParams and relative pathsChained multi-step execution
follow.procedure3 sequential steps5–7 with branchesLoops and verification
⚠
Levels are strictly ordered. An L(n+1) requirement cannot be satisfied by L(n) ability — if the microbenchmark suite shows a model passing a higher-level test while failing a lower-level one, the paper treats the hierarchy itself as miscalibrated and revises it.

3 · Capability-based compilation — the transform decision

At install time, the compiler extracts the skill's capability requirements by decomposing it into concrete tasks and mapping each to primitives+levels, then compares against the cached target profile. For each requirement: if the target supports the capability but at a lower level, apply compensation (add explicit instructions, examples, tighter constraints — reduces required level, preferred because it preserves intent). If the capability is absent or the gap too large, apply substitution (switch to a pre-identified equivalence-class implementation using capabilities the target does have).

4 · Code solidification — the three-stage pipeline

Stage 1 (offline, AOT): the compiler analyzes skill code segments for parameterized patterns, emitting a JIT candidate per eligible segment: keywords (relevance filter), a code signature (structural match pattern), a template (parameter slots), and a parameter schema. Stage 2 (online, invocations 1…N−1): the runtime monitor keyword-filters, then matches generated code against the signature; a hit increments a streak counter, any miss resets it. Stage 3 (invocations N…): after N=3 consecutive matches, the template is instantiated into a callable function — subsequent calls extract parameters from context and run the compiled function instead of having the model generate code from scratch, though (per Appendix B) the template's output is still returned to the model for validation/acceptance before use.

5 · Adaptive recompilation — the correctness contract

The runtime logs every failure/retry. A failure only triggers recompilation if it's systematic (recurs across runs or tasks) rather than task-specific. Appendix A's Algorithm 1 runs up to K=3 rounds, each executing tasks R=2 times; a headless diagnosis agent proposes an edit only if three conditions hold: C1 recurrence (same criterion fails ≥2 clean runs of one task, or ≥2 distinct tasks), C2 generality (fix statable without referencing the failing task's literals), C3 no trade-off (must not knowingly risk a currently-passing task). A round is admitted only if it improves the primary score by ≥δ=0.1, or matches within δ at ≥γ=15% lower cost — and any task regressing more than ρ=0.09 disqualifies the round outright.

# adaptive recompilation, abridged (Algorithm 1)
for round in 1..K:
    F = FailureProfile(prev_execution)      # deterministic, no LLM
    D = Diagnose(skill, F, capability_profile)
    if D.abstains: break            # C1/C2/C3 not satisfied
    skill = D.editedSkill
    E = Execute(skill, tasks, R=2)
    if Primary(E) >= tau(0.95): break
ship Select(rounds)                 # admission gate: δ, γ, ρ
💡
Why the gate is this strict: an LLM-generated diff is a proposal, not a proof. Without C3's no-regression check, a recompilation that fixes one failing task could silently break three that used to pass — the gate makes that trade-off explicit and measured, not assumed.
Follow the numbers, step by step

Worked examples

Real numbers from the paper, carried through arithmetic you can check.

① Compensation vs. substitution on the PPTX skill

Skill needs 5 capabilities; target matches 4 exactly, but tool.exec requires L2 (resolve relative paths) and the target profiles at L1. Which transform, and why?

  1. Check for substitution first: PptxGenJS (via gen.code.javascript L3) would replace python-pptx and drop the tool.exec requirement to L1 — a valid alternative exists.
  2. But the gap is only one level (L2 → L1), and compensation is preferred whenever it can plausibly bridge the gap, because it preserves the skill's original intent (keep python-pptx).
  3. Diagnose the specific L1/L2 failure: profiling shows this model fails specifically at resolving relative file paths during tool execution.
  4. Apply the targeted fix: rewrite the skill to use absolute paths rooted at the skill directory — a compensation transform, not a library swap.
  5. Result: 4 of 5 capabilities already matched, 1 gap closed by compensation, 0 substitutions needed.
🧩
Insight: substitution is available but not automatically preferred — the compiler checks compensation viability first because it's the smaller, intent-preserving edit.

② Solidification speedup, computed from Figure 14

PDF-extract's LLM path ranges 10,469–15,116 ms; solidified path ranges 206–568 ms. What's the actual speedup range, and does it match the paper's "19–50×" headline?

  1. Fastest observed solidified call vs. its LLM counterpart: 10,469 ms ÷ 206 ms ≈ 50.8× — matches the paper's "up to 50×."
  2. Worst-case bound: pairing the fastest LLM call against the slowest solidified call gives the floor of the range: 10,469 ms ÷ 568 ms ≈ 18.4× — this, not 15,116÷568, is the true lower bound, and it lines up with the paper's reported "19–50×" headline.
  3. Contrast with weather-current: ~9,000 ms → ~2,000 ms ≈ 4.5× only — because the call is network-bound (external weather API), so the LLM-inference savings can't remove that latency floor.
  4. Contrast with weather-forecast: it never promotes — the model's more flexible output format never matches the code signature across even 3 consecutive invocations, so all 8 invocations in the trace stay on the LLM path.
💡
Insight: solidification's payoff is bounded by how much of the latency is actually LLM-inference time — network- or I/O-bound calls see modest gains, pure-computation calls (PDF parsing) see the largest.

③ Environment mismatch's token tax

Removing a required dependency (Figure 4): Qwen models drop to 33–67% success and generate 2–4× more output tokens; Claude Opus 4.6 still succeeds every run but generates 56–69% more output tokens. What does environment binding save?

  1. Weak model, dependency present: baseline success rate and token count (the "Complete" bars in Fig. 4).
  2. Weak model, dependency removed: success collapses to 33–67%, and the failed attempts still cost 2–4× the tokens of a clean run — the model burns tokens diagnosing and retrying, then still fails a third to two-thirds of the time.
  3. Strong model, dependency removed: Opus 4.6 recovers every time (100% success) but pays a 56–69% token tax doing so — diagnosis-and-install isn't free even for a capable model.
  4. With environment binding: the presence check + idempotent repair script runs before the skill's context is even loaded, so neither model ever sees the missing-dependency state — this restores task scores to the provisioned ("Complete") baseline and substantially cuts the token tax back down, though the paper doesn't claim exact token-cost parity with the Complete baseline.
🧩
Insight: leaving dependency diagnosis to the model turns every missing package into a repeated tax on both correctness and efficiency — moving it to a pre-execution script prevents the model from ever hitting the missing-dependency state in the first place, substantially cutting the tax rather than merely reducing it after the fact.

④ Parallelism speedup across nine tasks

Figure 16 reports per-task speedups: Batch Analysis 0.9×, Log Parsing 1.5×, Metrics Profiler 1.3×, Code Scanner 1.0×, Dep Audit 2.5×, Lint Checker 3.2×, Multi-Svc Debug 1.7×, Test Suites 2.4×, CLI Debug 2.4×. What pattern explains the spread?

  1. Batch Analysis actually regresses slightly (0.9×) — script-level parallelism's overhead (spawning workers) can exceed its savings when the parallel portion is a small share of total latency, exactly the paper's caveat that script-level parallelism overlaps <30% of end-to-end latency on average.
  2. Lint Checker hits 3.2×, the paper's headline number — consistent with tool-level parallelism (batched independent tool calls) giving the largest mean speedup, since it removes both model round-trips and per-call latency.
  3. Multi-Svc Debug (1.7×) sits below Dep Audit/Test Suites/CLI Debug (2.4–2.5×) despite agent-level parallelism's coarser grain — consistent with the paper's note that sub-agent spawn cost and joining on the slowest sub-agent (not the average) bounds the gain.
💡
Insight: the "3.2× speedup" in the abstract is the ceiling of a real spread, not a typical case — tool-level parallelism is the strongest lever, script-level is the weakest and can even regress on latency-dominated tasks.
Test yourself

Practice problems

Try each before opening the answer. Every one flags the misconception it's checking.

Problem 1 · easy
A team adds more detailed tool documentation to their harness's system prompt, expecting every skill to work better as a result. On Gemini 3 Flash's workday-scheduling task, the opposite happens: 100 on the minimal harness, 0 on the richer one. Why?
Show answer
The richer harness (OpenCode) prepends extensive tool documentation on top of the skill, and the longer combined context induces a malformed-JSON formatting error that the minimal harness (BareAgent) never triggers. More context isn't strictly better — it's a different target with a different capability profile, and P2 (harness mismatch) is exactly this: harness choice materially changes outcomes independent of the model.Misconception: that richer tooling/context always helps. SkillVM's fix isn't "add more docs" — it's profiling the actual target and compiling to it.
Problem 2 · medium
A skill's tool.exec requirement is L2. The target profile shows L1 for tool.exec but L3 for gen.code.javascript (an equivalence-class alternative). Compensation could plausibly bridge one level. Which transform does SkillVM prefer, and under what condition would it switch?
Show answer
Compensation is preferred by default because the gap is only one level and it preserves the skill's original intent (same library, clearer instructions). SkillVM would switch to substitution only if compensation proved unable to bridge the gap reliably — i.e. if the level gap were larger, or if profiling showed the model still fails the L2 microbenchmark even after compensation-style rewrites.Misconception: that any available substitute is automatically used. Substitution is the fallback, not the default — the compiler tries the smaller edit first.
Problem 3 · medium
A model passes the microbenchmark for reason.arithmetic L3 (compound multi-step reasoning) but fails the L1 microbenchmark (single-step ops) on a different run. What does SkillVM's methodology say to do?
Show answer
Treat the level hierarchy itself as miscalibrated for this primitive and revise the level definitions, then re-evaluate — because by construction, L(n+1) requirements cannot be satisfiable when L(n) fails; passing a "harder" test while failing an "easier" one means the ordering assumption is broken, not that the model is inconsistent.Misconception: that the model's behavior is the bug. The hierarchy definition is the thing under test here, not just the model.
Problem 4 · hard
A code segment matches its solidification signature on invocations 1, 2, and 4, but not on invocation 3. With N=3 for promotion, is it promoted after invocation 4?
Show answer
No. The promotion counter requires consecutive matches — invocation 3's non-match resets the streak to 0 (Algorithm 2, line 8: "any non-matching run resets"). After invocation 4's match, the streak is only 1, not 3. Promotion needs three matches in a row, so it would need invocations 5, 6, and 7 to also match before promoting after invocation 7.Misconception: that N=3 means "3 matches total." It means 3 matches with zero interruptions — a single miss anywhere in the streak restarts the count.
Problem 5 · medium
Across two runs of the same task, one fails on a JSON-formatting criterion and the other fails on an unrelated file-path criterion. Does this satisfy C1 (recurrence) for adaptive recompilation?
Show answer
No. C1 requires the same evaluation criterion to fail in at least two clean runs of one task, or in at least two distinct tasks. Two different criteria failing across two repeats does not satisfy C1 — each is potentially task-specific noise, not a systematic pattern, so recompilation should not trigger on this evidence alone.Misconception: that any repeated failure counts as recurrence. The criterion has to match, not just "something went wrong twice."
Problem 6 · hard
A recompiled skill variant scores 0.03 higher than the baseline (δ=0.1 required) but costs 20% less to run (γ=15% required), with no task regressing beyond ρ=0.09. Is this round admitted?
Show answer
Yes. The admission rule accepts a round if it improves the primary score by ≥δ, or if its score is within δ of the baseline (0.03 < 0.1, satisfied) and its cost is at least γ lower (20% ≥ 15%, satisfied). Since no task regressed beyond ρ, the round clears the gate via the cost-reduction path, not the score-improvement path.Misconception: that admission always requires a score win. A cost-neutral-or-better round that's meaningfully cheaper is explicitly admissible — this is how SkillVM captures token/latency wins, not just accuracy wins.
Problem 7 · medium
A skill step reads 15 independent CSV files and runs the same analysis on each; a different step in the same skill runs three independent, unrelated diagnostic tool calls. The harness supports batch tool dispatch but not sub-agent spawning. Classify the parallelism for each step.
Show answer
The CSV step is script-level parallelism — same operation over independent data items, rewritten with a language-level primitive (multiprocessing, Promise.all); it needs no special harness support, so it's always viable. The diagnostic-tool-calls step is tool-level parallelism — independent steps each needing one tool call, batched into a single LLM turn; this requires harness batch-dispatch support, which is present here, so it's also viable. Neither needs sub-agent spawning, so the harness's missing capability there is irrelevant to this skill.Misconception: that more "steps in parallel" always means agent-level parallelism. The granularity (data-item vs. tool-call vs. multi-turn subtask) determines the level, not just "independence."
Problem 8 · easy
On a SOTA model + rich harness pair where the original skill already scores 95–100 on most tasks, how much should you expect SkillVM's capability-based compilation to move the completion-rate needle?
Show answer
Very little — the paper explicitly notes that for stronger model–harness configurations, improvements are more modest because these models already handle tasks competently; SkillVM's main contribution there shifts to reducing token consumption and execution latency rather than raising completion rate, since there's little capability gap left to close.Misconception: that SkillVM always produces a large completion-rate jump. Its biggest completion-rate wins are concentrated on weaker models; on strong ones the win is mostly efficiency, not correctness.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is SkillVM literally a virtual machine, like a JVM?▾
Structurally analogous, not literal — it doesn't define bytecode or execute instructions itself. It's a compilation and runtime system: an AOT compiler that produces target-specific skill variants at install time, and a JIT layer that optimizes execution using runtime feedback. The "processor" it targets is the LLM + harness pair, and the "compiled artifact" is still natural-language skill text plus optional compiled code fragments (solidified templates).
Q2Does SkillVM modify the model's weights?▾
No. Everything operates at the prompt/skill level — capability-based compilation rewrites the skill text, environment binding generates a setup script, concurrency extraction annotates the skill with a DAG, and code solidification produces standalone callable functions that bypass the model for specific calls. The model itself is untouched.
Q3How is a primitive capability different from a general benchmark score?▾
A benchmark score is holistic and outcome-based. A primitive capability is a narrow, demand-side unit (e.g. "resolve a relative file path during a tool call") with an explicit level hierarchy, derived specifically so that a skill's requirements can be expressed as a combination of them and compared directly against a target's measured profile — the granularity is what makes gap-closing transforms (compensation/substitution) computable.
Q4What happens if the target's capability profile changes (e.g. a model update)?▾
The paper doesn't describe automatic invalidation; profiling results are cached and reused for all skill compilations against that target. A materially different model version would need re-profiling to get an accurate profile — otherwise compiled variants would be optimized against a stale profile, similar to running AOT-compiled code against a CPU with a different microarchitecture than it was tuned for.
Q5Does code solidification work for generative skills (e.g. frontend design)?▾
Poorly, by design. Solidification targets code whose structure repeats with only parameters varying (75% of skills have this). Generative skills' quality depends on the model's own creative output each time — there's no stable "signature" to match against, so these segments simply never accumulate a consecutive-match streak and stay on the LLM path, as seen with weather-forecast's more flexible output format.
Q6Is AOT compilation done per task, or per skill?▾
Per skill, against a target (model–harness–environment triple), not per individual task instance. That's why the cost is described as a one-time investment: 90K tokens (~$0.56) per skill for AOT compilation, amortized across every future task invocation of that skill on that target.
Q7What if the harness doesn't support batch tool dispatch or sub-agent spawning?▾
The concurrency opportunity for that granularity simply falls back to sequential execution. The compiler still identifies the DAG and the opportunity, but only emits the rewrite for parallelism levels the target's harness can actually support — script-level parallelism is always viable since it needs no special harness capability.
Q8Can adaptive recompilation make a skill worse over time?▾
The admission gate is designed to prevent this: a round only ships if it clears C1 (recurrence)+C2 (generality)+C3 (no-trade-off) during diagnosis, and then passes a numeric admission check (score improvement ≥δ, or cost reduction ≥γ within δ of baseline score, with no task regressing beyond ρ). If no round in a cycle qualifies, the original skill is kept — recompilation is opt-in on evidence, not automatic.
Q9How is this different from prompt optimizers like DSPy or Cognify?▾
Those tune a program for one specific application using training data and a task-specific metric — the tuned result serves that one task. SkillVM compiles a skill against a target's measured capability profile, with no per-task training data, so every task that later invokes the same skill benefits from one compilation. It also restructures execution itself (parallelism extraction, code solidification) rather than only tuning prompt/skill content.
Q10What is a "systematic" vs. "task-specific" failure, concretely?▾
Task-specific: the failure arises from one task's particular input or constraints and wouldn't recur elsewhere. Systematic: the same underlying cause can recur across tasks (e.g. the model consistently mishandles a certain library's API). Only systematic failures — detected via the C1 recurrence check — trigger adaptive recompilation; task-specific ones are left alone since "fixing" them risks overfitting the skill to one input.
Q11Does SkillVM eliminate the need for a strong underlying model?▾
No — it narrows the gap, it doesn't erase it. Weaker models benefit more in absolute terms (SkillVM addresses gaps in non-logical proficiency like JSON formatting or dependency handling), but the paper still shows a capability floor: some tasks simply need a level of reasoning or code generation no amount of compensation or substitution can substitute for.
Q12Is the work reproducible / open?▾
Yes — the paper states SkillVM's source is publicly available (github.com/SJTU-IPADS/SkVM), implemented in 36,200 lines of TypeScript, with an adapter layer supporting OpenClaw, Hermes Agent, OpenCode, Pi Coding Agent, Codex, and Claude Code.

Glossary & further reading

Deeper terms not covered in the Start Here glossary, then results at a glance and provenance.

Core mechanism terms
SkillVMThe paper's compilation + runtime system: AOT compiler (capability-based compilation, environment binding, concurrency extraction) plus JIT optimizer (code solidification, adaptive recompilation, resource-aware scheduling).
Primitive capabilityAn indivisible, demand-side unit of model/harness behavior (e.g. tool.exec) with ordered proficiency levels L1<L2<L3; 26 total, covering 95% of a 15,063-skill corpus.
Capability profileThe per-target result of running the microbenchmark suite for all 26 primitives, cached and reused across all skill compilations for that target.
CompensationRewrite a skill's instructions (more explicit steps, examples, constraints) to lower its required capability level — preferred transform, preserves intent.
SubstitutionFallback transform: switch to an alternative implementation path from a pre-identified equivalence class when compensation can't bridge the gap.
Environment bindingAOT pass that extracts a dependency manifest, presence-checks it, and generates an idempotent repair script run before skill execution.
Concurrency extractionAOT pass that builds a validated workflow DAG from a skill's steps and maps parallel opportunities to script/tool/agent-level primitives.
Code solidificationJIT mechanism promoting repeated LLM-generated code patterns (after N=3 consecutive signature matches) into compiled functions that bypass inference.
Adaptive recompilationJIT mechanism that recompiles a skill only for systematic failures, gated by a recurrence + generality + no-regression admission contract.
Supporting terms
Progressive disclosureThe standard skill-loading mechanism (metadata first, full instructions loaded when relevant) that SkillVM's compiled variants still flow through.
Resource-aware schedulerRuntime component that throttles new sub-agent launches and suspends running ones under CPU/memory/API rate-limit pressure.
Workflow DAGNodes = skill steps, edges = data dependencies; validated for acyclicity and no dangling nodes before being trusted for parallelization.
Code signatureA structural match pattern (not literal text) used to test whether newly generated code matches a solidification candidate's expected shape.
C1/C2/C3 (recompilation gate)Recurrence, generality, and no-trade-off — the three conditions a diagnosis agent's proposed skill edit must satisfy before it's even proposed.
Admission gate (δ, γ, ρ, τ)Numeric thresholds (score improvement, cost reduction, max regression, convergence target) that decide whether a recompiled round actually ships.
Skill-CreatorAnthropic's existing skill-optimization tool, used as a baseline comparison — SkillVM's improvement over it grows as model capability decreases.
