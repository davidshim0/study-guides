SOSP 2026 · A Field Guide

Filing DNA by content, not by address

A file's location in a folder tree shouldn't cost six rounds of DNA sequencing to resolve. ProbeFS encodes the whole ancestry into the strand itself, so one hybridization finds the file — or the entire subtree.

📄 Li, Zhang, Dong, Hao, Wang, Fan, Chen · SOSP '26 🧬 Molecular biology basics assumed — primers cover them ⏱ ~25 min read
🧬

Encode each file's ancestry into the DNA itself so a probe resolves it directly — instead of paying for hierarchy with sequential lookups or cascading rewrites.

Before you begin

Quick glossary + the primers you need

You know file systems and storage hierarchies already — these primers focus on the biochemistry ProbeFS depends on, plus how conventional hierarchy maps onto DNA.

Acronyms, up front
PCRPolymerase Chain Reaction — exponentially amplifies strands sharing a primer. Destructive, single-use, ~2% pool loss per read.
NGS / SequencingReading base sequences from a DNA pool. Slow (minutes–hours) and, with synthesis, dominates DNA storage latency.
SC (Strand Collection)All strands sharing a primer pair inside one storage spot — the coarse unit PCR retrieves as a whole.
SPR / HPRSerial / Hash-based Path Resolution — the two conventional ways to resolve a hierarchical path, both borrowed from disk file systems.
PPRProbe-based Path Resolution — ProbeFS's replacement: one probe, one hybridization, no traversal.
NUPACKA thermodynamic simulator used to test probe selectivity at scale without wet-lab cost.
1Hybridization: DNA's built-in content search▾

Two DNA strands bind into a double helix only if their bases are complementary (A–T, C–G) — this is hybridization. A short probe strand binds any longer strand containing its complement, anywhere within it, without needing to know the strand's address.

Now you're ready: DNA is content-addressable by nature — like a hardware associative-memory lookup, except the "tag compare" happens via chemistry in a test tube, and thousands of comparisons happen at once.
2Synthesis and sequencing: the two slow, costly ops▾

Synthesis writes new strands (13–23h per strand); sequencing reads them back (20min–2h per round). Both dominate cost and latency; selecting/amplifying strands is comparatively cheap. An efficient DNA file system minimizes serial sequencing rounds and the volume of strands read per operation — not raw IOPS.

Now you're ready: think of synthesis/sequencing like NVM's write/read asymmetry, but pushed to a wild extreme — hours instead of nanoseconds, and round-trips (not bytes moved) are the currency to minimize.
3PCR vs. probes: two ways to pull strands out of a pool▾

PCR amplifies everything sharing a fixed-position primer — a whole-strand-collection retrieval, destructive, single-use. A probe hybridizes to a target subsequence anywhere in a strand, is non-destructive, and its magnetic-bead complex is reusable up to 6×. Probes give ProbeFS fine-grained, cheap, repeatable selection that primer-only PCR designs lack.

Now you're ready: most prior DNA file systems used primers (PCR) as filenames — a flat, whole-collection retrieval, though alternatives like CRISPR-based access have also been explored. ProbeFS instead embeds path structure into a probe-searchable subsequence.
4Spots and Strand Collections: the DNA storage hardware model▾

A DNA storage chip is a 2D array of spots, each holding a pool of strands. Strands sharing a primer form a Strand Collection (SC) — the unit one PCR round retrieves. write(spot, sequence) synthesizes; read(spot, primer) amplifies and sequences.

Now you're ready: reading "the wrong SC" means sequencing far more data than you need — this is the read-amplification problem ProbeFS attacks directly.
5Hierarchy on conventional media: SPR vs. HPR▾

SPR (like ext4/UFS) walks the tree level by level: each level is one more lookup. HPR (like distributed metadata stores) hashes the full path straight to a location, skipping traversal — at the cost that renaming a directory must recompute and migrate every descendant's hashed address.

Now you're ready: on fast RAM/SSD, this SPR-vs-HPR tradeoff is a footnote. On DNA, where each lookup step is a sequencing round costing minutes to hours, it becomes the whole design problem (§3).
6The metrics that matter here▾

Latency and throughput measure the lab apparatus, not the design — apparatus speed varies by orders of magnitude across setups. ProbeFS instead reports serial sequencing count (rounds that must run one-after-another) and read amplification (strands read ÷ strands actually needed) — both platform-independent and design-specific.

Now you're ready: every result in this guide is framed in these two currencies, converted to hours only at the end (§5.6) using published per-step latencies.
The whole story in one place

ProbeFS in a nutshell

The dilemma, the encoding that dissolves it, and how the pieces fit.

Hierarchy creates cross-file dependencies: a file's identity depends on its whole chain of ancestor directories. On DNA, resolving that dependency is brutal either way: SPR pays it at read time with roughly two sequencing/access rounds per directory level; HPR pays it at write time, since renaming a directory forces discovering and migrating every descendant serially, one PCR at a time, because their identities aren't known in advance.

ProbeFS's fix is the path identifier: a DNA subsequence built from a file's depth, its ancestor directories, and its filename, each mapped to a fixed-length "probe unit" and concatenated. Because siblings and descendants share subsequences by construction, a single complementary probe can hybridize to exactly the file you want (exact probe), every direct child of a directory (immediate probe), or an entire subtree at any depth (subtree probe) — all in one parallel reaction, without ever needing a directory-entry list.

The payoff: up to 5,124× less read amplification and 54× fewer serial sequencing rounds than SPR/HPR/LiqSD baselines, landing end-to-end retrieval at 1.3–2.7 hours — the tier of Amazon S3 Glacier Flexible Retrieval, not Deep Archive.

🍯 Key takeaways

  • Hierarchy's cost on DNA is cross-file dependency, paid at read time (SPR) or write time (HPR) — never eliminated by conventional designs.
  • The path identifier makes ancestry part of the DNA sequence itself, so hierarchy is resolved by chemistry, not traversal.
  • Three probe types — exact / immediate / subtree — cover file lookup, directory listing, and recursive retrieval, each in one hybridization.
  • Chained delta updates avoid re-synthesizing whole immutable strands for small edits.
  • Probe specificity stays ≥0.91 up to 100K files and on a real 92K-file Linux kernel tree.
Six everyday pictures

How to think about ProbeFS

Each stands alone. Every card ends with where the picture stops being true.

The core idea · Path identifiers

A shared family surname

Siblings sharing a surname can be rounded up by calling out that one name — no need to check each person's address individually. Path identifiers give files under the same directory a shared "surname" (depth + ancestor subsequences), so a probe for that surname sweeps up every relative in one call.

Where it breaks: real surnames don't encode how many generations back a shared ancestor is; ProbeFS's depth field does — that's what lets a probe distinguish "direct children" from "any descendant."
Content addressability · Probes

A magnet tuned to one shape

A probe is like a magnet whose bead only grabs onto strands carrying its exact complementary subsequence — it doesn't care where in the pool that strand sits, only what it contains. Elute and reuse the same bead up to six times, no reagents burned, unlike PCR's single-use, pool-degrading amplification.

Where it breaks: a magnet only picks what you designed it to match; a poorly-chosen probe unit length (too short) grabs unintended strands too — hence the §5.7 tuning of unit length.
SPR vs HPR · The dilemma

Turn-by-turn directions vs. a street that got renamed

SPR is like following turn-by-turn directions — reliable, but you must ask at every intersection (every directory level), one at a time. HPR is like giving everyone a GPS coordinate straight to their door — fast to look up, but if the street is renamed, every resident's coordinate must be recomputed and re-issued, one at a time, because you don't know who lives there until you go look.

Where it breaks: real GPS coordinates don't depend on the street name; HPR's hashed addresses do (they're computed from the full path) — that dependency is exactly the design flaw ProbeFS removes.
One-shot retrieval · Parallelism

Casting a net, not a single hook

A single hook catches one fish whose exact identity you already know. A net cast once catches every fish of the right species swimming through it, regardless of which individual fish they are. One-shot retrieval's immediate/subtree probes are that net — they capture a whole directory's children (or subtree) without the system ever knowing the filenames in advance.

Where it breaks: a physical net can't distinguish "depth 2 exactly" from "depth greater than 2" — ProbeFS's depth encoding deliberately engineers a shared suffix so a probe can make that distinction (§4.2).
Immutability · Chained delta updates

Sticky notes on a stone tablet

You can't erase a stone tablet, but you can stick timestamped notes on top with corrections. Reading the tablet means reading the base plus every note, in order. DNA strands are the tablet (write-once); delta strands are the sticky notes, chained by timestamp and merged at read time — avoiding a full re-synthesis for every small edit.

Where it breaks: sticky notes never expire; delta strands do accumulate as garbage until a threshold triggers reconstruction (§4.6) — the tablet occasionally does get re-carved.
Massive parallelism · Hybridization at scale

A stadium PA, not a hallway relay

A hallway relay passes a message person to person — serial, and slow to reach the back. A stadium PA reaches every seat simultaneously. Millions of probe-target hybridizations proceed concurrently in one reaction tube — that's what lets one-shot retrieval and massively parallel re-synthesis (during rename) stay cheap even at 100K-file scale.

Where it breaks: a PA system doesn't get noisier as the crowd grows; hybridization specificity does degrade slightly with pool complexity — hence the NUPACK sweep confirming specificity stays ≥0.91 up to 100K files.
The full explanation

How it actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams.

1 · Strand format — where the path identifier lives

Metadata strands carry: primer pair, path identifier, attributes (full path, size, timestamps, permissions), and the data address. Data strands carry primer, type (initial or delta), timestamp, index, and content. ProbeFS avoids the naive design of storing directory entries as directory-file content — directory structure is instead implicit in the path identifiers of the files inside, eliminating a whole class of strands SPR/HPR must maintain and traverse.

2 · Probe-based path resolution (PPR) & one-shot retrieval

To resolve a single file, hash its path to find the spot, then generate the exact probe complementary to its full path identifier and filter that spot's pool — no per-level traversal. To list a directory's children, generate an immediate probe matching only depth + ancestor segments (all direct children share these exactly). To retrieve an entire subtree (needed for rename), generate a subtree probe matching the depth-suffix (depth > target) plus the ancestor prefix — this captures descendants at any depth in one hybridization, without ever knowing their filenames.

3 · Chained delta updates

Since DNA strands are immutable once synthesized, an edit doesn't rewrite the strand — it appends a new delta strand sharing the same path identifier, tagged with a timestamp and type (update/insert/delete) plus just the changed region. Reads sequence the initial strand and all its deltas, then merge them in timestamp order to reconstruct current content.

type=0 init:    "ATCGCAGGAATCT"                    # the tablet
type=1 update:  pos:2 len:3 "AAG"                # sticky note 1
type=2 insert:  pos:1 len:2 "TG"                 # sticky note 2
type=3 delete:  pos:7 len:2                      # sticky note 3
read = merge(init, deltas sorted by timestamp)
💡
Why not just rewrite the whole strand? Re-synthesizing an entire file means re-running the dominant-cost operation (synthesis, 13–23h per 200-base strand) for every strand the file spans, on data that mostly hasn't changed. Deltas pay only for the diff.

4 · Discussion: collisions, crashes, and garbage

  • Hash/path-identifier collisions: bounded strand length forces truncation of very deep paths; NUPACK confirms specificity ≥0.91 up to 100K files, and the rare false positive is filtered by cheap CPU-side verification against the full path stored in attributes.
  • Crash consistency: synthesis/sequencing steps are individually atomic; ProbeFS logs a redo log to an external SSD before each operation and replays it after a crash — safe because re-reading/re-writing the DNA pool never corrupts existing strands.
  • Garbage collection: delta chains accumulate stale strands; GC triggers when a spot's stale fraction passes a threshold (0.2 in evaluation), re-synthesizing only the latest valid version. On a 146M-op trace this fired only ~100 times.
Follow the numbers

Worked examples

Four traces using the paper's real figures.

① Generating a path identifier

Create /A/C/file1.txt. What goes into its path identifier?

  1. Parse the path: depth = 3 (three ancestor levels: /, /A, /A/C).
  2. Encode depth as its fixed-length nucleotide sequence, e.g. ATCCGTGTCA.
  3. Encode each ancestor in order: / → CGTAG, A → GATCG, C → TTACG.
  4. Encode the filename the same way: file1.txt → ATCGA.
  5. Concatenate: depth‖dir1‖dir2‖dir3‖filename = the full path identifier, embedded in the metadata strand.
🍯
Insight: any file under /A/C automatically shares the first three segments with this one — that shared prefix is what a probe exploits later, at zero extra cost. (Paper Fig. 7.)

② Lookup latency vs. directory depth

Using the §5.6 model (SPR: 2 rounds/level × 65min; HPR: 2 rounds × 65min constant; ProbeFS: 2 rounds × 80min constant):

  1. d = 3: SPR = 6 × 65min = 390min = 6.5h. HPR = 2 × 65min = 2.2h. ProbeFS = 2 × 80min = 2.7h.
  2. d = 10: SPR = 20 × 65min = 1300min = 21.7h. HPR and ProbeFS are unchanged — they don't traverse levels.
  3. Crossover: SPR passes the 12h "deep archive" threshold once d ≈ 12h ÷ 2.17h/level ≈ 6 levels — deeper than many real hierarchies (e.g., DICOM's 4-level structure, which the paper cites only as motivation for why hierarchy matters, not as a system near this latency tier).
💡
HPR looks free here — its cost shows up on the write side instead, which example ③ makes concrete.

③ Why renaming punishes HPR, not ProbeFS

In the ECFS trace, a directory rename affects on average 499 files (p99: 4,802; max: 143,300), yet renames are only 0.05% of all operations.

  1. HPR: every descendant's address is a hash of its full path, so each must be individually rediscovered and migrated — roughly 2 rounds per level of subtree depth. At subtree depth l=5: 10 rounds × 65min ≈ 10.8h.
  2. ProbeFS: a single subtree probe captures every descendant's metadata regardless of subtree size or depth — exactly 1 round × 80min ≈ 1.3h, whether the rename touches 3 files or 143,300.
  3. Serial sequencing count, FSL homes-cache trace: LiqSD = 49.7, ProbeFS = 0.92 → 49.7 ÷ 0.92 ≈ 54× fewer serial rounds — matching the paper's headline number exactly.
🍯
Insight: the gap doesn't come from a faster probe reaction — it comes from never needing to discover descendants one at a time in the first place.

④ Probe specificity in the real world

On the 92K-file Linux kernel v6.19.10 source tree, ls /fs/ (an immediate probe) reports sensitivity 1.00, specificity 0.97.

  1. Sensitivity 1.00 means every true child of /fs/ was captured — nothing was missed.
  2. Specificity 0.97 means 3% of captured strands were non-targets — off-target hybridization from the 92K-strand pool's chemical competition.
  3. Resolving the 3%: a cheap CPU-side check decodes each captured strand's Attr field (the stored full path) and discards mismatches — negligible overhead against hours-long sequencing.
  4. At 100K files (NUPACK sweep), specificity across exact/immediate/subtree probes stays above 0.91 — the design holds four orders of magnitude beyond the 30-file wet-lab validation.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it checks.

Problem 1 · easy
Why can't ProbeFS just use a PCR primer encoding the full path, the way prior DNA file systems used labels?
Show answer
PCR primers require exact flanking matches and retrieve the whole strand collection destructively per query; they can't do partial (prefix/suffix) matching for directory listing, and each query burns ~2% of the pool. Probes hybridize to subsequences non-destructively and are reusable up to 6×.Misconception: that primers and probes are interchangeable "filename" mechanisms — primers are whole-collection, destructive, exact-match; probes are subsequence, non-destructive, reusable.
Problem 2 · medium
Why does an immediate probe for /A's children require matching an exact depth (=2), while a subtree probe matches a depth range (>2)?
Show answer
Direct children share both the same ancestor path and the same exact depth (parent depth + 1). Descendants at any level share the ancestor prefix but vary in depth, so the probe must match "depth greater than k" — which only works because depth codes above k share an engineered common suffix (§4.2).Misconception: conflating "one level down" with "any depth" — they need different fields of the encoding to match.
Problem 3 · hard
Why does the depth field deliberately give every depth beyond a threshold k the same suffix, rather than a fully unique code per depth?
Show answer
A subtree probe needs to hybridize to any depth greater than the target directory's — that's only possible with one short probe if all those depths share a common subsequence to match against. A fully unique per-depth code would make "any depth > k" require a separate probe per depth, destroying one-shot retrieval.Misconception: assuming more unique encoding is strictly better — deliberately collapsing distinctions here is what enables single-hybridization subtree capture.
Problem 4 · medium
HPR resolves any file lookup in a constant 2 sequencing rounds, independent of depth. So why is it worse overall than ProbeFS?
Show answer
The dependency doesn't disappear — it moves to write time. Renaming a directory means every descendant's hashed address depends on its full path, so all descendants must be individually discovered and migrated, serially, because HPR has no way to enumerate children without walking already-known entries.Misconception: "flat, fast lookup" implies the whole design is cheap — hierarchy's cost is conserved, not eliminated, by hashing.
Problem 5 · easy
A rename in the ECFS trace affects 4,802 files at the 99th percentile. Why can't HPR just fire off all 4,802 PCR reactions in parallel?
Show answer
Parallel PCR requires knowing each target's primer in advance. Under HPR, the descendants' identities are only discovered by reading the directory structure first — you can't set up 4,802 targeted reactions for files you haven't found yet, so discovery must proceed serially.Misconception: assuming parallelism is a hardware capability you can just invoke — it requires knowing target identities upfront, which is exactly what ProbeFS's subtree probe provides and HPR doesn't.
Problem 6 · medium
Chained delta updates never rewrite the initial strand. Over years of edits, what happens to storage, and how does ProbeFS bound it?
Show answer
Obsolete delta strands accumulate in the spot. ProbeFS triggers garbage collection once a spot's stale-strand fraction crosses a threshold (0.2 in evaluation), re-synthesizing only the current valid version. This is rare — about 100 events across a 146M-operation trace.Misconception: thinking deltas accumulate forever with no reclamation — GC bounds the overhead, triggered lazily by staleness, not on a fixed schedule.
Problem 7 · hard
Probe unit length L=6 minimizes read amplification. What goes wrong at L=12, and separately at L=2?
Show answer
The path identifier has a bounded total length. Larger L leaves room for fewer ancestor components, so deep paths get truncated and lose the segments that would distinguish them — collisions inflate read amplification for deep files. Smaller L makes each unit less specific, so probes bind unintended strands sharing a short subsequence — inflating amplification for shallow files. L=6 balances the two.Misconception: "more specific per-component encoding is always better" — unit length is a shared, bounded budget traded against the number of path components representable.
Problem 8 · easy
Why does the paper report retrieval latency instead of raw sequencer throughput as its headline number?
Show answer
Throughput and latency of the underlying lab apparatus vary by orders of magnitude across labs and platforms — they measure the equipment, not the file system design. Serial sequencing count and read amplification are platform-independent design metrics; latency is only derived from them at the end (§5.6), using published per-step timings, purely to compare against commodity cold-storage tiers.Misconception: that faster hardware alone would fix SPR/HPR's problems — the bottleneck is the number of serial, dependent rounds required by the design, not the speed of any one round.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1What exactly is a "path identifier"?▾
A DNA subsequence built by concatenating fixed-length codes for a file's depth, each ancestor directory, and its filename, embedded in the metadata strand. Files sharing ancestors share subsequences of it, which is what makes probe-based hierarchical retrieval possible.
Q2How is this different from just hashing the whole path (HPR)?▾
A hash destroys structure — you can't tell from a hash alone whether two files share an ancestor. A path identifier preserves structure by construction, so a probe can match "any file under this prefix" directly, without needing to already know which files exist.
Q3Why do exact, immediate, and subtree probes need different subsequences?▾
Exact matches the full identifier (one file). Immediate matches exact depth + ancestor prefix (direct children only). Subtree matches a depth-suffix (depth > target) + ancestor prefix (any descendant at any depth). Each targets a different "shape" of file set.
Q4Isn't PCR enough on its own — why add probes?▾
PCR retrieves a whole strand collection sharing a primer — coarse, destructive, single-use. Probes select by subsequence content at finer granularity, non-destructively, and are reusable — exactly what's needed to filter one file's metadata out of a spot holding many.
Q5Does renaming still require touching every file in the subtree?▾
Yes — every descendant's metadata strand encodes the old path and must be re-synthesized with the new one. What ProbeFS eliminates is the serial discovery step; re-synthesis itself is massively parallel and doesn't add much latency.
Q6What happens when path identifiers collide?▾
Rare in practice (specificity ≥0.91 up to 100K files). The few false positives are filtered by a cheap CPU-side check against the full path stored in the metadata's Attr field.
Q7How does ProbeFS handle a file edited many times?▾
Each edit appends a timestamped delta strand rather than rewriting the immutable initial strand. Reads merge the initial strand with all its deltas in timestamp order; garbage collection reclaims space once staleness crosses a threshold.
Q8Why compare against Amazon S3 Glacier instead of SSDs?▾
DNA storage today targets cold, archival workloads, the same niche as Glacier-class cloud storage. ProbeFS's 1.3–2.7h retrieval lands in "standard cold storage" territory (comparable to Glacier Flexible Retrieval), versus SPR/HPR/LiqSD's worst cases, which reach ~11–24h (e.g., HPR's fast 2.2h file lookup balloons to ~10.8h for subtree retrieval at depth 5) — deep-archive-tier territory.
Q9Is ProbeFS validated only in simulation?▾
No — wet-lab experiments (up to 30 files) validate physical feasibility for all three probe types; NUPACK thermodynamic simulation extends confidence to 100K files and a real 92K-file Linux kernel tree; in silico system evaluation covers large-scale, real traces (ECFS, FSL Homes).
Q10What's still open for future work?▾
The paper focuses on single-user archival semantics; concurrent multi-writer consistency, larger-scale wet-lab validation beyond 30 physical files, and tighter integration with emerging enzymatic (faster) synthesis are natural next steps, though not detailed as explicit future work in the text.
