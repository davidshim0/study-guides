SOSP 2026 · A Field Guide

Cleaning a zone in parallel, not one block at a time

Zoned SSDs moved garbage collection off the device and onto the filesystem — at roughly 1000× the old scale. GAZE shows the decades-old GC code was never built for that jump, and rebuilds it around three ideas: pipeline the CPU work, stop borrowing the kernel's page cache, and stop blocking writes that don't actually need free space yet.

📄 "GAZE" · Kim, Yoo, Yoo, Won (KAIST) 🎓 Some filesystem/kernel basics assumed — primers cover them ⏱ ~20 min read
🧹

Reclaim a zone the way you'd clean a shared room: don't stand in the doorway blocking everyone while you tidy — pipeline the work, bring your own supplies, and only turn people away when there's truly nowhere left to put them.

1Zones and the append-only constraint▾

A zoned SSD (ZNS) splits storage into zones. Inside a zone you may only write at the current write pointer — sequentially, never in place. This is a deliberate trade: the device gives up fine-grained random writes, and in exchange gets coarse zone-granularity address mapping and no internal garbage collection of its own.

To empty a zone, the host issues reset. If the zone still holds live data, the host must first copy that data elsewhere — that copying is exactly the "filesystem-level garbage collection" this paper is about.

Now you're ready: GC used to be the SSD's private problem. ZNS hands it to the filesystem — and zones are gigabytes, not megabytes.
2Log-structured filesystems and segment cleaning▾

A log-structured filesystem (LFS) never overwrites in place — it always appends new writes to the end of a log. Old versions of a block become invalid (superseded) but their space isn't reclaimed until a cleaning process, traditionally called segment cleaning, migrates the still-valid blocks out and frees the rest.

Because LFS already writes sequentially, it was the obvious filesystem to adapt to ZNS: just make the cleaning unit match the zone size.

Now you're ready: GAZE isn't a new filesystem — it's a rearchitected garbage collector for the segment-cleaning step of an LFS (F2FS), scaled up to zone size.
3F2FS's units: segments, sections, and the metadata that finds valid blocks▾

F2FS groups blocks into 2 MB segments, and segments into sections — the actual unit of garbage collection. To find which blocks in a victim section are still valid, F2FS consults a block bitmap, a reverse mapping (SSA), and the NAT (address table) to check and update ownership.

Now you're ready: every valid block GAZE migrates still goes through this same bitmap/SSA/NAT bookkeeping — that per-block bookkeeping is exactly the CPU work the paper measures.
4How F2FS migrates a valid block today (read phase, write phase)▾

F2FS's GC has two phases. In the read phase, for each valid block it: checks validity, allocates a physical page (kernel page allocator), inserts that page into the page cache, then issues a read. In the write phase, it: re-checks validity, waits for the read to finish, allocates a new disk location, and issues a write. Both phases run in one thread, one segment at a time.

Now you're ready: every one of those steps — check, allocate, insert, wait — is a candidate for GAZE's pipeline or page pool to speed up.
5Per-CPU page lists, the buddy allocator, and the page cache▾

To get a free physical page, Linux first tries a per-CPU page list; if that's empty it falls back to the buddy allocator, which splits/merges power-of-two page groups. A freshly allocated page is zero-filled (to avoid leaking old data) and inserted into the page cache, indexed per-file by an xarray.

All of this is general-purpose machinery, built to serve arbitrary-sized, arbitrary-lifetime requests safely and efficiently — at a real CPU cost per call.

Now you're ready: GC doesn't need any of this generality — the block count is known in advance, and the data is never re-read. That's the entire argument for the Garbage Collection Page Pool.
6Buffered, direct, and synchronous writes — and delayed allocation▾

A direct write (O_DIRECT) or synchronous write (O_SYNC) needs a real disk block right away. A buffered write just copies data into the page cache and returns — the filesystem uses delayed allocation to pick the actual disk block later, at writeback time, not at write() time.

Now you're ready: if buffered writes don't need free space immediately, why does today's F2FS make them wait for GC anyway? That contradiction is the whole motivation for Selective Blocking.
7Pipelining and producer-consumer threads▾

A pipeline splits a task into stages, each run by its own thread, connected by bounded queues in a producer-consumer relationship. If one stage is CPU-bound and the next is I/O-bound, running them as separate concurrent stages lets the CPU keep working while I/O for earlier items is still in flight — instead of one thread alternating between the two and leaving each resource idle in turn.

Now you're ready: this is precisely GAZE's Pipelined Garbage Collection — four stages, four threads, overlapping CPU work with disk I/O.
8Dirty pages, writeback, and the kernel's soft/hard limits▾

Buffered writes accumulate as dirty pages in memory until a writeback thread flushes them to disk. Linux throttles this with two thresholds: a soft limit (default 10% of RAM) that wakes the writeback thread, and a hard limit (default 20%) that blocks the writing application outright.

Now you're ready: these limits are the real safety net for buffered writes — which is exactly why it's safe to let them proceed during GC instead of blocking them pre-emptively.
The whole story in one place

GAZE in a nutshell

The mismatch, the measurement that exposed it, and the three fixes.

Log-structured filesystems were designed to reclaim megabytes at a time — F2FS segments are 2 MB, and classic LFS reclamation units range from 64 KB to 8 MB. Zoned SSD zones are 32 MB to several gigabytes. Reclaiming a 1 GB zone at 40% utilization means repeating F2FS's per-block migration logic roughly 100,000 times — and in the paper's measurement, that 1 GB zone takes 283× longer than reclaiming one 2 MB segment (1.7 sec vs. 6.0 msec). That's not a superlinear blowup — it roughly tracks the ~500× jump in size — but because none of that per-block CPU work gets any cheaper as the unit grows, it adds up to over a second and a half of stalled latency at zone scale.

The authors trace this to three design habits baked into every log-structured filesystem, each reasonable at megabyte scale and each a bottleneck at gigabyte scale: serial, single-threaded cleaning; borrowing the kernel's general-purpose page cache and allocator to hold victim blocks; and blindly blocking every write — buffered, direct, or synchronous — while GC runs.

GAZE's fix is three matching techniques. Pipelined Garbage Collection restructures GC into a four-stage pipeline (preread → read → prewrite → write) so CPU-bound and I/O-bound stages overlap instead of alternating. Garbage Collection Page Pool pre-allocates its own pages and, for GC's own bounded migration path, sidesteps the general page cache in favor of simple O(1) arrays — bypassing the buddy allocator and xarray for that path, while still checking and pinning pages that are genuinely present in the real page cache. Selective Blocking lets buffered writes proceed during GC — because a log-structured filesystem's blocks are really valid / invalid / free, not just valid / free, and a buffered write doesn't need a free block the moment it's issued.

The payoff: GAZE cuts GC latency to about 1/3 of F2FS's, and beats F2FS-with-ZNS, ZNS+, and P-GC by up to 3×, ScaleLFS by up to 4.4× (FIO), and IPLFS by up to 1.9× (YCSB-A) — with no change to the on-disk layout and no special hardware.

🧹 Key takeaways

  • Zone-scale GC is CPU-bound, not I/O-bound: 73% of read-phase and 84% of write-phase latency is CPU, not disk time.
  • Pipelined GC splits the four steps into four concurrent threads, overlapping CPU stages with I/O stages — 51% latency reduction alone.
  • GC Page Pool bypasses the kernel's page allocator and general page cache for GC's own bounded migration path, using pre-owned pages and O(1) arrays instead — 25% latency reduction alone.
  • Selective Blocking exploits the ternary (valid/invalid/free) block model: buffered writes don't need free space at write() time, so they needn't wait for GC.
  • Combined: GC latency drops to about 1/3 of F2FS's, and FIO throughput improves by 95% during GC.
  • No on-disk layout changes, no specialized hardware, no non-standard device interface.
Six everyday pictures

How to think about GAZE

Read in any order. Each ends with an honest note on where the picture stops being true.

Core idea · Pipelined Garbage Collection

An assembly line, not one cook

One cook checking, plating, and serving each dish in sequence spends half their time waiting on the oven. Four cooks — one per step — keep working continuously, each handing off as soon as their step is done. GAZE's preread/read/prewrite/write stages run the same way, as four threads instead of one, so CPU work on block N+1 overlaps with disk I/O on block N.

Where it breaks: GAZE deliberately caps this at four stages, not more — more cooks (cores) means more interference with the foreground application, so the pipeline is sized for minimal footprint, not maximal parallelism.
Core idea · Garbage Collection Page Pool

Your own supply closet, not the general warehouse

Need a bucket and mop every day? Keep them in a closet by the door instead of filing a requisition with the warehouse each time — no waiting for staff to pick, log, and hand it back. GAZE's page pool pre-owns exactly as many pages as a partition needs and tracks them with a plain array, skipping the buddy allocator's search-and-zero-fill and the page cache's tree lookup entirely.

Where it breaks: the closet only holds so much — sized to one partition (32 MB). If GAZE tried to pool an entire gigabyte zone at once, the "closet" itself would become the memory-pressure problem it was built to avoid.
Core idea · Selective Blocking

Order now, pay when the food arrives

A diner who says "just put my order in, I'll settle up when the food's ready" doesn't need a free table reserved this instant. One who demands a table right now, immediately, does. Legacy log-structured filesystems treat both the same — blocked writes stem from a binary valid/free model. GAZE gives the "settle later" (buffered) write its due: with a ternary valid/invalid/free model, invalid blocks that GC will soon free count too, so a buffered write can proceed and only truly urgent (direct/sync) writes wait.

Where it breaks: the restaurant isn't infinite — the kernel's dirty-page hard limit (20% of RAM) still eventually says "kitchen's full, please wait," so Selective Blocking defers the wait, it doesn't abolish it.
Design detail · Intra- and inter-segment overlap

A relay where the baton hands off mid-stride

A strict relay waits for the full baton pass before the next runner moves. GAZE's writer starts writing block 1 the moment the reader has dispatched its read — not waited for it to complete — and the next segment's prereader starts scanning while the current segment's writer is still finishing up. It's less a clean handoff, more a bucket brigade in motion.

Where it breaks: this overlap is exactly why the pipelined prewrite and write stages individually get longer in isolation (they now absorb wait time the old serial code hid) — the total drops, but per-stage numbers alone can be misread as a regression.
Why not just reuse the page cache

A card catalog vs. a numbered coat check

A library's card catalog (the xarray) is built to find any book, by any key, in a collection that grows and shrinks unpredictably — worth its O(log n) search cost. A coat check simply hands you numbered ticket #14 and you fetch coat #14 directly — O(1), but only because the domain is small and bounded in advance. GAZE's valid/pending page maps are the coat check: they work because a partition's block count is known the moment GC starts.

Where it breaks: a general-purpose file's page cache can't assume a bounded, pre-sized domain — which is exactly why GAZE doesn't replace the page cache everywhere, only inside GC's own bounded scope.
The paper's core empirical move

Patching the tire that isn't flat

Decades of LFS work polished read-ahead and asynchronous writes — the I/O side of GC. That's fixing the tire that goes flat slowly. But at zone scale, the paper measures the CPU side — identifying blocks, allocating pages, bookkeeping — consuming 73–84% of GC's time. That's the tire that's actually flat, and nobody had been pumping it.

Where it breaks: which tire is flat depends on the vehicle. On the mobile platform (slower ZUFS storage, less RAM), GAZE's own results show the bottleneck partly shifts back toward I/O — the CPU fix still helps, just less dramatically.
The full explanation

How GAZE actually works

Section by section, with the paper's key mechanisms rebuilt as diagrams.

1 · Pipelined Garbage Collection

GAZE splits GC into four stages, each its own thread, connected by producer-consumer bounded buffers: preread (scan the block bitmap, check validity), read (allocate a page, issue read I/O), prewrite (re-check validity, wait for the read to land), write (allocate a new disk block, issue write I/O). Preread and prewrite are CPU-bound; read and write are I/O-bound — separating them lets CPU work on later blocks overlap with disk I/O on earlier ones.

Pipelining needs a bounded buffer between read and write. To keep that buffer's size manageable — instead of gigabytes — GAZE reclaims a zone in fixed-size partitions (32 MB), one partition at a time in serial fashion, sized just large enough to keep the pipeline full without excess memory pressure (Table 1, worked out in the next tab).

2 · Garbage Collection Page Pool

Instead of routing GC's victim-block migration through the kernel's per-CPU page list, buddy allocator, and general page cache, GAZE pre-allocates a fixed free page pool at mount time and tracks victim blocks with two plain arrays — a valid page map (blocks in the victim partition) and a pending page map (blocks being written to the destination) — plus a cache bitmap marking blocks that happen to already be in the regular page cache, which GAZE still checks and pins rather than bypassing. Both maps give O(1) lookup, versus the page cache's O(log n) xarray traversal.

Correctness detail — shadow copies. If a user read()/write() misses the page cache while a block sits in the Page Pool, GAZE copies it into a real page-cache page (a "shadow copy") before servicing the request — so the pool never has to impersonate the page cache's full semantics, only lend it a page on demand.

3 · Selective Blocking

In-place-update filesystems have two block states: valid or free — so every write() reasonably checks for free space up front. Log-structured filesystems actually have three: valid, invalid, free. An invalid block isn't free yet, but GC will make it free soon. GAZE lets a buffered write count on that: it reserves space against free blocks plus soon-to-be-freed invalid blocks, copies data into the page cache, and returns — without pre-emptively triggering or waiting on GC. Direct and synchronous writes, which need a real block immediately, still wait.

Follow the paper's own numbers

Worked examples

Four traces through the evaluation section, arithmetic shown.

① What the Page Pool actually saves (Fig. 12)

Vanilla F2FS vs. F2FS with the GC Page Pool, same FIO workload:

  1. Page allocation: 0.21 sec → 0.05 sec. Reduction = (0.21 − 0.05)/0.21 = 76% — bypassing the per-CPU list and buddy allocator.
  2. Page insertion: 0.073 sec → 0.005 sec. Reduction = (0.073 − 0.005)/0.073 ≈ 93% — an O(1) array write instead of an xarray traversal.
  3. Read-phase total: 0.97 sec → 0.66 sec. Reduction = (0.97 − 0.66)/0.97 ≈ 32%, matching the paper's headline claim exactly.
🧹
Insight: the two costs eliminated (alloc + insert) are exactly the kernel-service overheads the paper flagged as unnecessary — none of it involves the disk.

② Why 32 MB partitions (Table 1)

GC latency by partition size: 4→1.07s, 8→0.92s, 16→0.85s, 32→0.77s, 64→0.75s, 128→0.73s, 256→0.73s.

  1. Total possible gain from largest buffer: 1.07 − 0.73 = 0.34 sec (4 MB down to the 256 MB plateau).
  2. Gain achieved at 32 MB: 1.07 − 0.77 = 0.30 sec = 88% of the total possible gain.
  3. Gain left on the table going from 32 MB all the way to 256 MB: only 0.77 − 0.73 = 0.04 sec (a further 5%) — for 8× the buffer memory.
  4. Conclusion: 32 MB captures nearly all the benefit of a large bounded buffer at a fraction of the memory cost — exactly the tradeoff the paper picks.
💡
This is a diminishing-returns curve: the pipeline just needs enough buffered blocks to never starve, not the whole zone in flight at once.

③ Stacking the two techniques (Fig. 14, 15)

GC latency: Vanilla 1.70s, +Page Pool 1.27s, +Pipeline 0.83s, +Both 0.58s. FIO throughput: Vanilla 83.0 KIOPS → combined 162.0 KIOPS.

  1. Page Pool alone: (1.70 − 1.27)/1.70 = 25% latency reduction.
  2. Pipeline alone: (1.70 − 0.83)/1.70 = 51% latency reduction.
  3. Combined: (1.70 − 0.58)/1.70 ≈ 66% reduction — i.e., 0.58/1.70 ≈ 1/3 of the baseline, matching the abstract's headline number.
  4. Throughput: (162.0 − 83.0)/83.0 ≈ 95% improvement — and standard deviation drops from 66.2 to 17.0 KIOPS, a 74% reduction in variability, once Selective Blocking is added on top.
🧹
Insight: neither technique alone prevents the dirty-page buffer from filling (blocking still happens eventually); only combining faster GC with Selective Blocking keeps the application from stalling at all.

④ Why the mobile gains are smaller (Fig. 20)

On SM8750 mobile storage: throughput 56.02 → 68.38 KIOPS; GC-time latency 3.10 → 0.42 sec.

  1. Throughput gain: (68.38 − 56.02)/56.02 ≈ 22% — much smaller than the server's 95%.
  2. Latency reduction: (3.10 − 0.42)/3.10 ≈ 87% — actually a larger relative cut than the server's 66%.
  3. Why the mismatch: the mobile platform has only 12 GB RAM (vs. 64 GB on the server), so Selective Blocking's dirty-page buffer fills sooner; and Zoned UFS has lower bandwidth than the server's NVMe, shifting the bottleneck partly back toward I/O — right where GAZE's CPU-focused fixes help least.
💡
A tiering parallel: this is the same shape of tradeoff as reducing hot/cold-classification or migration-bookkeeping overhead in a DRAM/NVM tiering system — the payoff is largest when the interconnect (here, NVMe; there, CXL/DRAM bandwidth) is fast enough that software overhead, not raw transfer time, is the bottleneck. Slow the device down and the same optimization has less room to matter. (This connection is our framing, not the paper's.)
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking.

Problem 1 · easy
Why doesn't simply making F2FS's segment size equal to the zone size (without any other changes) solve the zone-scale GC problem?
Show answer
Segment size determines the reclamation unit, but every valid block within that unit still runs the same per-block software path — bitmap check, page allocation, xarray insertion — one at a time, on one thread. Scaling the unit up ~500× in size doesn't come for free: reclaiming the 1 GB zone still takes 283× longer than the 2 MB segment, because that per-block CPU work has to run for every one of the ~100,000 valid blocks in the zone instead of a couple hundred. The point isn't that latency scales worse than the size ratio — it's that CPU-bound, per-block overhead is what turns "more data" directly into "more wall-clock time," and at zone scale that's over a second and a half of stalling.Misconception: that reclamation unit size is "just a number" and per-block cost is negligible. Because the per-block work dominates, latency tracks the block count almost one-for-one — there's no shortcut from simply calling the unit "bigger."
Problem 2 · medium
The paper notes that in the baseline, "the write phase begins once read requests have been dispatched rather than completed" — so read and write already overlap somewhat. Why does Pipelined GC still cut latency by 51%?
Show answer
That overlap is confined to a single segment, and even there it's partial — the write phase for a segment can't start until every valid block's read has been dispatched, and segments themselves are still reclaimed strictly one after another. Pipelined GC overlaps at both intra-segment (writer starts on the very first loaded block) and inter-segment (next segment's preread starts before the current segment fully finishes) granularity, across four distinct threads instead of one thread's brief overlap window.Misconception: "some overlap already exists, so there's nothing left to gain." The existing overlap is narrow and single-threaded; pipelining is overlap by design, across stages and across segments.
Problem 3 · medium
Figure 6 shows FIO throughput and dirty-page memory utilization both drop sharply when GC starts — even though there's 64 GB of RAM and the dirty-page ratio never nears the hard limit. What's the real cause?
Show answer
The buffered write() itself is blocked before it even gets to copy data into the page cache, because legacy F2FS pre-emptively secures free disk space (step 3 of write servicing) regardless of write type, and that check collides with the already-running GC. The application literally never gets the chance to generate dirty pages — it's not that memory is full, it's that the write path never reaches memory.Misconception: "if memory utilization is low, memory isn't the bottleneck." Here the bottleneck is a blocking check upstream of memory use entirely.
Problem 4 · easy
True or false: Selective Blocking removes the free-space check for buffered writes entirely.
Show answer
False. It defers the check's consequence, not the check itself — the filesystem still reserves against free blocks plus invalid blocks that can be reclaimed (step 1) to guarantee the write won't hit ENOSPC later, it just no longer pre-emptively triggers or waits on GC to secure literal free blocks at write() time (step 3). And the kernel's existing dirty-page hard limit still throttles the application if too many buffered writes accumulate before writeback.Misconception: "selective" means "none" — it actually means "only for writes that truly need it right now" (direct/sync), not "no blocking anywhere."
Problem 5 · hard
The GC Page Pool replaces the page cache's xarray with plain O(1) arrays. Why doesn't the kernel just do this for the whole page cache, everywhere, all the time?
Show answer
The array trick works because GC's domain is small and known in advance — the exact number of blocks in one 32 MB partition, fixed before the migration starts. The general page cache has no such bound: files grow and shrink unpredictably, offsets are sparse and arbitrary, and the structure must support efficient lookup, insertion, and lockless concurrent reads (via RCU) across an open-ended key space. A flat array sized for "one partition's worth of blocks" simply doesn't generalize to "any file, any size, any access pattern."Misconception: "if a simpler structure works for GC, it's just better." It's better only within GC's specifically bounded, short-lived, single-purpose context.
Problem 6 · medium
GAZE shows smaller relative gains on the mobile platform (22% throughput, though 87% latency reduction) than on the server (95% throughput, 66% latency reduction). Does this mean GAZE's design principles don't apply to mobile storage?
Show answer
No — it means the relative size of the CPU bottleneck GAZE targets is smaller there. The mobile platform has less RAM (12 GB, limiting how much Selective Blocking's deferred writes can buffer) and lower-bandwidth Zoned UFS storage (shifting some of the latency back toward genuine I/O time, which GAZE's techniques don't shrink). The paper's own framing — "GAZE is most effective when CPU overhead dominates garbage collection latency" — predicts exactly this outcome; it's a confirmation of the model, not a contradiction of it.Misconception: "smaller gain = design failure." A CPU-overhead fix should show a smaller gain wherever CPU overhead is a smaller share of the total latency — that's the mechanism working as described, not against it.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly makes zone-scale GC different from ordinary segment cleaning?▾
Scale, not kind. The same read-phase/write-phase logic runs, but a 1 GB zone at 40% utilization requires roughly 100,000 repetitions of the per-block migration steps, versus only around 205 valid blocks in a 2 MB segment (512 total 4 KB blocks at 40% utilization) — and the paper measures that as a 283× latency increase (1.7 sec vs. 6.0 msec), roughly tracking that ~500× jump in scale, because per-block CPU overhead — not disk time — dominates and simply has to run 100,000 times over.
Q2Is GC really CPU-bound, given SSDs are so fast?▾
Yes, according to the paper's measurements: 73% of read-phase latency and 84% of write-phase latency is CPU time (identifying valid blocks, allocating pages, filesystem bookkeeping), leaving only 27%/16% as actual disk I/O. Decades of LFS work optimized the I/O side (read-ahead, async writes); GAZE targets the CPU side instead.
Q3Why exactly four pipeline stages, not more or fewer?▾
The authors split GC into four stages — enough to separate every CPU-bound step (preread, prewrite) from every I/O-bound step (read, write) with minimal dependency between adjacent stages, unlocking concurrency without using more CPU cores than necessary or interfering more with the foreground application. The paper doesn't claim four is provably minimal, just that it's the natural split along the CPU/I/O boundary.
Q4How does the Garbage Collection Page Pool avoid breaking read()/write() correctness?▾
By "shadow copying": if a user request touches a block still sitting in the Page Pool (not yet flushed to its new location), GAZE first copies it into a real page-cache page via the normal allocation path, then services the request from there — so the Page Pool never needs to reimplement the page cache's full read/write semantics, only lend it pages on demand.
Q5What's the difference between Selective Blocking and "not blocking at all"?▾
Selective Blocking still blocks direct and synchronous writes during GC — they genuinely need a free block immediately. It only exempts buffered writes, which use delayed allocation and don't need a disk block until writeback, long after GC may have already freed enough space.
Q6Does GAZE require a new on-disk layout, custom hardware, or a non-standard device interface?▾
No — this is an explicit design goal. GAZE is built entirely on F2FS's existing metadata and the standard ZNS interface (open/read/write/close/reset), unlike ZNS+ or ZMS (which offload work to the device) or ScaleLFS (which changes the on-disk layout).
Q7Why do ZNS+ and P-GC underperform GAZE despite also targeting GC overhead?▾
P-GC parallelizes with 32 threads but serializes on a per-file lock, so a single-file workload gets no real concurrency benefit. ZNS+ offloads block copying to the device (helpful mainly on slow PCIe 2.0 links) but pays a "post-GC checkpoint" that blocks all requests until every device-side copy completes — a cost GAZE avoids by keeping victim blocks pinned in memory until writes finish.
Q8Why are GAZE's gains smaller on the mobile platform?▾
Less RAM (12 GB) limits how much Selective Blocking can defer, and Zoned UFS has lower bandwidth than the server's NVMe SSD, shifting part of the bottleneck back to genuine storage I/O — exactly where a CPU-overhead fix has less to offer. GAZE still improves mobile throughput 22% and cuts GC-time latency 87%.
Q9How is the 32 MB partition size chosen, and what does it trade off?▾
It bounds the size of the buffer needed between the pipeline's read and write stages. Table 1 shows 32 MB already captures about 88% of the maximum possible latency reduction from a larger buffer, while using only 1/8 the memory of the 256 MB option that captures the rest.
