SOSP 2026 · A Field Guide

Let the fast path guess, let a verifier notarize

Two runs of the same prompt on the same GPUs can return different text. The fix everyone reaches for — rewrite every kernel to be batch-invariant — is a fixed tax on every request. LLM-42 pays that tax only for the requests that actually need it.

📄 "LLM-42: Enabling Determinism in LLM Inference with Verified Speculation" · Gond, Kamath, Ramjee, Panwar 🎓 LLM serving internals assumed unfamiliar — primers cover them ⏱ ~30 min read
🎲

Decode with whatever's fastest, then replay under a fixed batch size to check — commit what matches, roll back only what doesn't.
Determinism becomes a per-request choice, not a global tax.

Before you begin

Quick glossary + what the paper assumes you know

This paper lives in LLM-serving systems, not OS memory management — the glossary below front-loads its acronyms, then the primers cover the mechanisms.

1Prefill vs. decode▾

An LLM request has two phases. Prefill processes the whole prompt in parallel in one pass — compute-bound, embarrassingly parallel. Decode is autoregressive: one new token per step, each step reusing the KV cache — memory-bound, one token at a time.

Now you're ready: LLM-42 treats these phases differently — prefill can be made deterministic almost for free; decode is where the fast-path/verify machinery lives.
2Dynamic (continuous) batching▾

To keep GPUs busy, a serving system doesn't run one request at a time — it groups whichever requests are in flight into a batch at each iteration, adding and removing requests as they arrive and finish. The batch's size and composition therefore changes almost every step.

Now you're ready: this is the throughput technique the paper refuses to sacrifice. Disabling it would fix determinism trivially but tank performance — so the paper works around it instead.
3Floating-point non-associativity▾

In finite-precision arithmetic, (a+b)+c can differ from a+(b+c) by a tiny rounding error. Harmless in isolation — but if a GPU kernel sums a batch's numbers in a different order depending on batch size, the same logical computation yields slightly different results.

Now you're ready: this is the root cause. Combined with dynamic batching (different batch size every run) it means the same token can come out numerically different across runs.
4Reduction schedules and GPU kernels▾

A GEMM, attention pass, or normalization all involve a reduction (summing partial results). High-performance kernels choose how to parallelize that reduction — e.g., split-K partitions the summed dimension across more thread blocks at low batch sizes to keep the GPU busy. Different batch shapes → different chosen schedule → different accumulation order → different rounding.

Now you're ready: this is exactly the mechanism from primer 3, made concrete. It's also why "just disable split-K everywhere" (batch-invariance) throws away real performance — split-K exists for a reason.
5Speculative decoding▾

To speed up autoregressive decoding, a cheap draft model guesses several tokens ahead; the expensive target model then verifies all of them in one parallel pass. Matching tokens are accepted; the rest are discarded and regenerated. Output distribution is unchanged — it's a scheduling trick, not an approximation of the model.

Now you're ready: LLM-42 borrows this exact decode→verify→accept/reject shape, but repurposes it to fix determinism rather than to save compute.
6Self-speculative decoding▾

A variant that skips the separate draft model: the target model drafts against itself, typically via an approximation (skipped layers, early exit, pruned context). Because the draft is an approximation, errors compound fast, so speculation depth is usually limited to just 2–8 tokens.

Now you're ready: LLM-42 uses the same model for both roles too — but its "fast path" isn't an approximation, only a different (nondeterministic) execution of the exact same forward pass. That's why it can safely speculate 32–64 tokens deep instead of 2–8.
7Batch-invariance, the existing fix▾

The prior approach (He et al.) forces every kernel to use one universal reduction schedule regardless of batch size — e.g., disabling split-K entirely. This guarantees identical numerics for any batch composition, at the cost of the very parallelism split-K exists to provide.

Now you're ready: this is the paper's foil throughout — like LRU in the UCP paper's world, it's the sensible-sounding default that turns out to be needlessly costly once you look closely.
8Compute-bound vs. memory-bound▾

A kernel is memory-bound when it spends more time moving data than computing on it (typical of tiny batches / single-token decode); it's compute-bound when arithmetic dominates (typical of large batches / prefill). The same operator can be memory-bound at batch 1 and compute-bound at batch 1024.

Now you're ready: this is the entire reason grouped verification exists — verifying a tiny window is memory-bound and wasteful; verifying many tokens together is compute-bound and cheap per token, much like read-modify-write batching in any bandwidth-limited system you've profiled.
The whole story in one place

LLM-42 in a nutshell

The problem, the trick that fixes it cheaply, and how the pieces connect.

Nondeterminism in LLM inference comes from floating-point non-associativity interacting with dynamic batching: GPU kernels pick different reduction schedules (e.g., split-K) depending on batch shape, so the same token can compute to a numerically different value on different runs. The existing fix, batch-invariant computation, forces every kernel onto one fixed schedule for every batch size — eliminating the variable, but also the parallelism it enables. Measured on H100s, batch-invariant GEMM kernels reach only 533–785 TFLOPS versus 801 TFLOPS for ordinary cuBLAS kernels — a slowdown of up to 7.21× — and the penalty is paid by every request, whether or not it needs determinism.

LLM-42's insight: two things are usually true anyway. First (O1), if two runs have produced the same tokens so far, they will very likely agree on the next one too — divergence is rare, though once it happens it compounds. Second (O2), most kernels are position-invariant: fixed batch size ⇒ fixed reduction schedule ⇒ every token in that batch computed the same way regardless of its position. So LLM-42 lets requests decode on a fast, nondeterministic path under ordinary dynamic batching, then periodically replays a fixed-size window of decoded tokens through a verifier running at a fixed batch size. Tokens that match the verifier's deterministic replay are committed; tokens that don't are rolled back and regenerated from the verifier's own (consistent) output.

Because determinism is now a property of scheduling, not kernel design, it can be applied selectively — only requests tagged is_deterministic=True ever pay the verification cost, and existing high-performance kernels (cuBLAS GEMM, fused MoE, FlashAttention-3, RMSNorm) are reused unmodified.

🍯 Key takeaways

  • Nondeterminism = FP non-associativity × batch-shape-dependent reduction schedules (split-K, attention tiling, RMSNorm reductions).
  • Batch-invariance fixes it by forcing one global schedule — up to 7.21× GEMM slowdown, and it's a tax on every request.
  • LLM-42 fixes it by scheduling: nondeterministic fast path + periodic deterministic verify + rollback on mismatch (DVR).
  • Position-invariance (fixed batch size ⇒ same schedule for every token in it) is what makes a cheap fixed-batch verifier a valid deterministic reference.
  • Grouped verification batches many requests' small windows together — cheap rollback of small windows, cheap-per-token compute of large ones.
  • Determinism becomes selective, via a per-request is_deterministic flag — no global mode switch.
  • Result: within ~10% of nondeterministic throughput at realistic (<10%) deterministic traffic, vs. up to 52% overhead for SGLang's batch-invariant mode.
Six everyday pictures

How to think about LLM-42

Read in any order. Each ends with an honest note on where the picture stops being literally true.

Core idea · Decode-Verify-Rollback

Speculate now, notarize later

You sign a contract in pencil right away so the deal can move fast; a notary later stamps the pages that hold up and voids the ones that don't. LLM-42's fast path is the pencil signature (quick, provisional); the verifier is the notary stamp (slow, authoritative, but only invoked when it matters).

Where it breaks: a notary checks against an external, fixed standard. The verifier checks against itself, run under a fixed batch size — it's authoritative only because that replay is guaranteed reproducible, not because it's independently "true."
Observation O1 · Divergence amplification

The domino chain

Line up dominoes and tip the first: as long as none falls out of line, the chain stays perfectly ordered. But the moment one domino tips sideways, everything downstream goes with it. Two decoding runs stay token-for-token identical for long stretches — then one tiny flip, and the tail rarely re-aligns (the paper's "second consistent span" is ≤1 token for 80% of requests once a mismatch occurs).

Where it breaks: real dominoes never self-correct; a decoding run occasionally does re-converge by chance (that's the other 20%). The chain is likely to fall further, not certain to.
Why nondeterminism exists · split-K / reduction order

A print run that retypesets itself

A small print job might set the type in four separate blocks and glue them together (fast, parallel, but a different pasteup than a single continuous run); a big job runs continuously top-to-bottom. Same content, different assembly order — and if the "gluing" isn't perfectly commutative, tiny seams appear. GEMM kernels do the same: split-K assembles a sum from several parallel partial blocks at low batch sizes, but sums it straight through at high ones — different orders, different rounding.

Where it breaks: a print run's seams are visible and fixable by hand; a reduction-order seam is a bit-level rounding difference invisible until it flips a sampler's argmax.
Observation O2 · Position-invariance vs. batch-invariance

Cooking for tonight's headcount, the same way every time

A chef who varies the recipe by headcount but cooks every plate at tonight's table identically — that's position-invariance: fixed batch size ⇒ one schedule for every token in it, so any two tokens processed together get the exact same treatment. A chef who insists on the exact one-plate recipe regardless of headcount (batch-invariance) never uses their big pots — precise, but wasteful.

Where it breaks: a real chef's dishes are independent; here, "how you cooked tonight" (the batch's shape) must itself be reproducible across runs, which is exactly what LLM-42's fixed-size verifier window guarantees and the freely-varying fast path doesn't.
Grouped verification · memory- vs. compute-bound

A copy-editor reviewing a stack, not one page at a time

Handing an editor one page at a time wastes most of their attention on picking the page up; handing them a thousand-page manuscript in one sitting means one bad paragraph forces a reread of everything after it. Grouped verification hands the editor a modest stack from several different manuscripts at once: each manuscript's own reread stays short (small per-request window), while the sitting itself is efficient (many tokens verified per pass).

Where it breaks: real editors get tired; GPUs don't — the trade-off here is purely arithmetic-intensity (memory-bound vs. compute-bound), not fatigue.
Observation O4 · Selective determinism

A hall pass, not a school-wide lockdown

If one classroom needs a fire drill, you don't lock down the entire school for the day. SGLang's global deterministic mode is the lockdown: every request pays the batch-invariant tax the moment any request needs determinism. LLM-42's is_deterministic flag is the hall pass — only the tagged request goes through the extra check.

Where it breaks: a hall pass costs nothing for everyone else; here, a deterministic request still shares GPU time with nondeterministic ones, so heavy deterministic traffic does slow the whole batch down — just proportionally, not globally.
The full explanation

How it actually works

Section by section, from root cause to the grouped-verification knob you can tune yourself below.

1 · Where the nondeterminism comes from

GEMM, attention, normalization, and AllReduce all involve reductions. High-performance GEMM kernels use split-K to parallelize the reduction dimension across extra thread blocks — but whether split-K fires, and how many splits, depends on the input shape. Different shape ⇒ different reduction tree ⇒ different floating-point rounding for the "same" logical computation. Under dynamic batching, a request's batch shape varies run to run, so this is not a rare edge case — it's the default.

⚠
Measured cost of the naive fix: forcing every kernel onto one batch-invariant schedule drops GEMM throughput from 801 TFLOPS (cuBLAS) to 533 TFLOPS (Triton batch-invariant) — up to 7.21× slower at specific shapes — and end-to-end throughput by up to 33–52%, paid by every request regardless of need.

2 · The two observations that make a cheap fix possible

ObservationClaimWhy it holds
O1Same tokens so far ⇒ likely same next token; once tokens diverge, they rarely re-convergeNumerical drift is small; it only flips a token when it crosses the sampler's decision boundary — rare, but autoregression compounds any flip
O2Position-invariance: fixed batch size ⇒ every token in it uses the same reduction scheduleKernels pick schedule by shape, not by content — so replaying the same tokens at a fixed batch size reproduces the same numbers every time
🌱
O1 justifies speculating first and checking later. O2 justifies that the "checking" step (the verifier) can itself be a small, cheap, deterministic reference — a much weaker requirement than making every kernel batch-invariant.

3 · Decode-Verify-Rollback, mechanically

# fast path: ordinary dynamic-batched decode, W tokens
for i in 1..W: T'[i] = decode_step(nondeterministic_batch)

# verify: replay the SAME W tokens at a fixed batch size
T[1..W+1] = verifier_forward_pass(prompt_prefix + T'[1..W], batch=fixed)

# reconcile
k = first index where T[k] ≠ T'[k]   # or W+1 if all match
commit T[1..k]                        # includes verifier's own new token at k
discard T'[k..W]; overwrite KV cache entries [1..k] with the verifier's
resume fast-path decoding from position k
💡
Guaranteed forward progress: even in the worst case where every speculated token mismatches, the verifier still emits one fresh, consistent token (T[1]) — so DVR never stalls, no matter how adversarial the rollback pattern.

4 · Grouped verification — the efficiency knob

A lone verification pass over a small window is memory-bound (low arithmetic intensity ⇒ high per-token cost); a lone pass over a huge window is compute-bound but rolls back a huge amount on any mismatch. Grouped verification batches several requests' small windows into one pass: each request keeps a short, cheap rollback, while the pass overall is large enough to be compute-bound.

5 · Operator-specific fixes (small, one-time)

Most kernels need no change — they're already position-invariant. Three exceptions get a one-time, reused-everywhere substitution: attention uses FlashAttention-3 with a fixed KV-split tile size (no dynamic tiling); collectives use multimem-based AllReduce (CUDA 13+), which is already both batch- and position-invariant, replacing the position-dependent ring AllReduce; sampling uses a fixed-seed multinomial and a deterministic tie-break for argmax. None of this touches GEMM, FusedMoE, or RMSNorm kernels.

Follow the numbers, step by step

Worked examples

Four calculations, each traced through the paper's own measured numbers.

① The 45% you get from selective determinism

Figure 5: 8 nondeterministic requests hit 1495 tok/s; adding a 9th (still nondeterministic) reaches 1775 tok/s. If all 9 must be deterministic (SGLang-det), throughput is 1192 tok/s. If only 1 of the 9 needs determinism (LLM-42), throughput is 1733 tok/s.

  1. Cost of going fully deterministic: (1775 − 1192) / 1775 = 32.8% lower than the 9-request nondeterministic baseline — matches the paper's "33% lower."
  2. LLM-42's gain over SGLang-det: (1733 − 1192) / 1192 = 45.4% higher — matches the paper's "45% higher."
  3. LLM-42's gap from the nondeterministic ceiling: (1775 − 1733) / 1775 = 2.4% — within the paper's "3%."
  4. Insight: one request in nine needing exact reproducibility cost almost nothing, because only that one request's tokens ever reach the verifier.

② Reading Table 4: verification overhead scales with deterministic traffic, not model size alone

Table 4 (Llama-3-70B, window 32, group 16) reports verification passes as a % of total forward passes, by workload and deterministic fraction.

  1. At 10% deterministic traffic: ShareGPT needs 10.3% extra forward passes; ArXiv needs only 4.9%. Long-context ArXiv prompts are prefill-dominated (deterministic for free), so a smaller share of total work is decode that needs verifying.
  2. At 100% deterministic traffic: ShareGPT rises to 25.9%; ArXiv to 35.0% — ArXiv's decode-side verification now dominates once every request needs it.
  3. Synthetic (4K,4K) stays low even at 100% (17.6%): with 4K output tokens, the fixed per-window verification overhead amortizes over a much longer decode.
  4. Insight: overhead is roughly proportional to deterministic-traffic fraction at low ratios — exactly the "pay only for what you tag" property the batch-invariant baseline can't offer.

③ Why the paper's default (window 32, group 16) is nearly optimal

From the ablation (Fig. 13, Llama-3-8B, all traffic deterministic): the global-best cell is (group 32, window 16) at 1.00× normalized throughput / 2.91% recompute. The paper ships (group 16, window 32) instead.

  1. Look up (group 16, window 32): throughput = 0.99× of the global peak; recompute cost = 6.66%.
  2. Compare to global best (group 32, window 16): 1.00× throughput, 2.91% recompute — technically better on both axes, but only by 1 percentage point of throughput.
  3. Compare to no grouping at the same window (group 1, window 32): throughput collapses to 0.27×, recompute rises to 8.23% — grouping, not window size, is what buys most of the gain.
  4. Insight: LLM-42's performance is not razor-sensitive to the exact (window, group) choice — many configurations land within a couple of points of peak, as long as the window isn't huge (recompute blow-up) and the group isn't tiny (under-utilization).

④ What "7.21× slowdown" and "2.78× slowdown" actually mean

Figure 4 reports GEMM slowdown of batch-invariant kernels vs. cuBLAS, for the QKV projection of Llama-3-70B, at various batch sizes and tensor-parallel degrees.

  1. Peak throughput comparison: cuBLAS reaches 801 TFLOPS; the Triton batch-invariant kernel peaks at 533 TFLOPS — a ceiling gap of 801/533 ≈ 1.50× even at best case.
  2. Worst case (TP=8, low batch): the Triton kernel's slowdown reaches 7.21× — far worse than the peak-to-peak ratio, because split-K's benefit is largest exactly where batches are smallest and TP is highest (least per-GPU work to parallelize).
  3. DeepGEMM (CUDA, not Triton) narrows this to a maximum of 2.78× at the same shape — better engineering recovers some of the gap, but never eliminates it, since split-K itself is still disabled.
  4. Insight: the batch-invariant tax is worst exactly in the low-batch, high-TP regime that latency-sensitive interactive serving depends on — the opposite of where you'd want a fixed overhead to land.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Disabling dynamic batching would make inference deterministic. Why doesn't LLM-42 do this?
Show answer
Dynamic batching is the dominant throughput optimization in LLM serving — disabling it "severely degrades throughput" (the paper's own framing). LLM-42's entire design goal is determinism in the presence of dynamic batching, not instead of it: the fast path keeps full dynamic batching, and only the verifier runs at a fixed batch size, and only for tagged requests.Misconception: that eliminating the variable (batching) is the only way to eliminate its symptom (nondeterminism). LLM-42 instead makes the consequence of variability checkable and correctable.
Problem 2 · medium
O1's data shows the "second consistent span" is ≤1 token for 80% of requests once a mismatch occurs. Why does this make DVR's rollback cost manageable rather than catastrophic?
Show answer
It means once a request diverges, it's very unlikely to immediately re-align with the reference — so there's no point trying to "resync" token-by-token after a mismatch. Instead, DVR just discards everything after the first mismatch and resumes from the verifier's own fresh token. Combined with O1's first consistent span typically covering many tokens, most windows need zero rollback, and when rollback does happen it discards only the (small) remainder of that window, not the whole request.Misconception: that a mismatch means the whole speculative run was wasted. Only the tokens after the divergence point are discarded — everything before it, and the verifier's own next token, are kept.
Problem 3 · medium
Ring-based AllReduce is neither batch-invariant nor position-invariant. Multimem-based AllReduce is both. What's the difference between the two invariance properties, using this example?
Show answer
Batch-invariant would mean: the reduction order is identical no matter the batch size. Position-invariant would mean: for a given fixed batch size, every element gets the same reduction order regardless of where it sits in the batch. Ring AllReduce reduces different chunks of a tensor in different orders around the ring — so even within one fixed batch, position along the ring changes the order (fails position-invariance), and of course varies with batch size too (fails batch-invariance). Multimem AllReduce fixes both because its reduction tree doesn't depend on chunk position or batch size.Misconception: that batch-invariance implies position-invariance or vice versa. They're independent properties — LLM-42 only needs the weaker one (position-invariance).
Problem 4 · hard
In the grouped-verification ablation, every measured (window, group) pair satisfies window × group ≤ 1024. Why would the authors cap the product at 1024, and what does the triangular shape of their heatmap tell you?
Show answer
Total tokens verified per pass = window size × number of grouped requests — this is the effective batch size of the verifier's forward pass. Capping it at 1024 keeps the verification pass within a GPU-batch size the hardware/scheduler already handles efficiently (and matches the max output length used in their experiments); beyond that, a single verification pass would itself become an outsized, disruptive batch that starves the fast path of GPU time. The triangular shape is a direct visualization of that constraint: every cell on the diagonal boundary has exactly window × group = 1024, and cells beyond it were never measured.Misconception: that bigger windows and bigger groups are simply "better, up to some point you'd have to guess." The paper's own design already encodes a principled ceiling — the verifier pass size — rather than treating window and group as unboundedly independent knobs.
Problem 5 · medium
Why must LLM-42 overwrite the KV cache entries produced by the fast path with the verifier's own, even for tokens that passed verification?
Show answer
A passing token means its output matched — but the KV cache entry stored during the fast-path decode was still computed under nondeterministic, dynamically-batched execution, and could carry tiny numerical differences from what a fixed-batch computation would have produced. If left in place, that KV entry could influence future tokens' attention computation in a way that eventually causes a divergence the token-level check never caught. Overwriting with the verifier's own KV entries keeps the entire state — not just the emitted text — consistent going forward.Misconception: that verifying the output token is the same as verifying the underlying computation. Two different reduction orders can occasionally produce the same rounded output token while leaving slightly different internal state.
Problem 6 · hard
Using the paper's weighted-harmonic-mean formula for a separate deterministic/nondeterministic GPU pool split, explain qualitatively why LLM-42 (single-pool) tends to win only when the deterministic fraction p is below ~0.5.
Show answer
The separate-pool throughput is the weighted harmonic mean of T_d (deterministic pool throughput) and T_n (nondeterministic pool throughput), weighted by p and (1−p). A harmonic mean is dominated by the smaller of its inputs, but only in proportion to its weight — so when p is small, the (slow) T_d term contributes little and T_Sep stays close to T_n. LLM-42, by contrast, pays a cost roughly proportional to p directly (only p-fraction of traffic hits the verifier) rather than through the batch-invariant tax T_d bakes into 100% of one pool's traffic. As p grows past ~0.5, the separate deterministic pool is now serving mostly-deterministic traffic at its own (still batch-invariant, but at least undiluted) rate, which can beat LLM-42's shared-pool overhead once most requests need verification anyway.Misconception: that one architecture (single shared pool vs. separate pools) is strictly better. It's a genuine crossover governed by traffic mix — the paper reports LLM-42 wins for p < 0.5, which covers realistic (<10%) deterministic-traffic deployments but not majority-deterministic ones.
Problem 7 · easy
The paper found that SGLang's batch-invariant deterministic mode is not actually deterministic on the MoE model Qwen3-30B-A3B. What does this tell you about batch-invariance as a guarantee?
Show answer
Batch-invariance is only a guarantee for the kernels that were actually rewritten to be batch-invariant. MoE models add extra shape-dependent machinery (routing tokens to experts, variable tokens-per-expert) that the existing batch-invariant kernel set didn't fully cover — so nondeterminism leaked back in through an un-audited operator. LLM-42, by contrast, was empirically verified deterministic on the same model across 90K requests, because its correctness doesn't depend on auditing every kernel — only on the verifier's fixed-batch replay being reproducible.Misconception: that "uses batch-invariant kernels" and "is deterministic" are the same claim. The first is an implementation detail that can silently miss operators; the second is what actually needs verifying end-to-end.
Problem 8 · medium
At verification window size 1024 (no grouping), recompute cost for Llama-3-8B is 102.59% — meaning recomputation exceeds the original decode work. How is that possible, and why doesn't the paper recommend this setting?
Show answer
Recompute cost is measured as (extra tokens generated due to rollback) ÷ (tokens that were ultimately kept), not capped at 100%. With a 1024-token window, a single mismatch anywhere in that huge span discards everything after it — on average, more than half the window on a per-mismatch basis — and this can happen more than once per request's total output, so total wasted work can exceed the useful output length. This is exactly why the paper pairs window size with grouping and picks a modest default (32) rather than maximizing window size for compute efficiency alone.Misconception: that "recompute cost" behaves like a bounded percentage (0–100%). It's a ratio of wasted-to-useful work, and a big-enough window can waste more than it keeps.
Quick answers

Frequently asked questions

Eleven questions newcomers ask most.

Q1Is LLM-42's output the same distribution as ordinary nondeterministic decoding?▾
Yes for a fixed prompt and seed: every committed token is either a real forward-pass output (fast path, verified to match) or the verifier's own forward-pass output (on rollback) — never an approximation. The sampling hyperparameters are unchanged; only floating-point rounding, not the sampling policy, is being controlled. Different temperature/top-k settings still change output intentionally, as they should.
Q2How is this different from ordinary speculative decoding for speedup?▾
Ordinary speculative decoding uses a separate, weaker draft model to generate candidates cheaply and a stronger target model to verify — the goal is fewer expensive forward passes. LLM-42 uses the same model and the same forward computation for both roles, and its goal is bit-level reproducibility, not fewer passes; the verifier pass is pure overhead paid to buy determinism, not compute saved.
Q3Why doesn't prefill need a verifier?▾
Prefill processes all prompt tokens for one request in parallel within a single forward pass; as long as the system avoids arbitrarily batching prefill tokens from unrelated requests together in ways that vary run to run, prefill's own computation is already deterministic. So determinism for prefill is "free" — no speculate-and-check needed, only careful scheduling.
Q4What exactly triggers a rollback?▾
A mismatch between a fast-path token and the verifier's replayed token at the same position, within a verification window. On mismatch, everything from that position onward in the window is discarded; the token the verifier itself produced at that position is accepted instead, and decoding resumes from there.
Q5How expensive is the verifier compared to normal decoding?▾
Per-token verification cost depends heavily on window size: at window 16 it's memory-bound and costs up to 0.6ms/token (Llama-3-8B) or 2.7ms/token (Llama-3-70B, TP-8); at window 1024 it's compute-bound and drops to 0.025ms and 0.06ms respectively — a 24–45× reduction. Grouped verification lets you get most of that efficiency without the huge-window rollback penalty.
Q6Does LLM-42 require new GPU kernels?▾
Almost none. GEMM, fused MoE, and RMSNorm kernels are reused completely unmodified, since determinism is enforced by scheduling, not kernel rewriting. Only attention (fixed KV-split tile size), collectives (multimem AllReduce), and the sampler (fixed-seed, deterministic tie-break) needed a one-time swap — and these are shared across all models, not re-derived per model.
Q7Does LLM-42 always beat SGLang's batch-invariant mode?▾
Not universally — at very high deterministic-traffic fractions (approaching 100%) the always-on verifier's overhead grows, and for some workloads (e.g. ShareGPT's many short prefills) LLM-42 can lag. But across the paper's realistic operating range (≤20% deterministic traffic, which the authors expect to dominate in practice) it consistently and often substantially outperforms both SGLang-det variants, and scales especially well for the 70B model.
Q8Why is nondeterminism a genuine problem, given LLMs are already stochastic by design?▾
The paper's target is a narrower guarantee: identical output for identical inputs and fixed sampling hyperparameters (e.g., temperature=0, or a fixed seed). Changing those hyperparameters intentionally changes output — that's fine. The problem is that today, even holding everything fixed, outputs still vary — breaking reproducibility for debugging, evaluation, RL training, and compliance-sensitive deployments.
Q9What is "grouped verification" solving, exactly?▾
A pure trade-off between two costs that both scale with the verification window: per-token verification cost (high for small windows — memory-bound) and recomputation cost on rollback (high for large windows — more gets discarded per mismatch). Grouping many requests' small windows into one verifier pass gets the low per-token cost of a large batch while each request individually keeps the low rollback cost of a small window.
Q10Was record-and-replay of exact batch sizes considered instead?▾
Yes, and rejected. Logging the batch size used at every one of a request's decode iterations and replaying it exactly would work, but fundamentally conflicts with dynamic batching's ability to add/remove requests every iteration — replaying a mismatched batch size would force padding (wasted compute) or preempting/migrating other in-flight requests (added complexity), for every deterministic request, every step.
Q11What's MarginGate, and how does it extend LLM-42?▾
A follow-on optimization: token flips concentrate almost entirely on decode steps where the top-1/top-2 logit margin is small (only 0.3–1.3% of steps actually flip). MarginGate flags the ~15–19% of steps with a small margin as the only ones needing verification, skipping the always-on verifier for high-margin steps — reported at 2.23× (Llama-3.1-8B) and 1.99× (Qwen2.5-14B) overhead reduction versus LLM-42's always-verify baseline.

Glossary, results, and provenance

Every term in one place, then where the numbers actually came from.

Core terms
DVR (Decode-Verify-Rollback)LLM-42's protocol: speculate on a nondeterministic fast path, replay under a fixed batch size to verify, roll back mismatches.
Fast pathOrdinary, high-throughput dynamically-batched decoding — nondeterministic, but usually correct in the sense of matching a fixed-batch replay.
VerifierA forward pass over a fixed-size window at a fixed batch size, producing the deterministic reference output for that window.
Batch-invarianceForcing one universal reduction schedule for a kernel regardless of batch size — deterministic, but discards batch-size-dependent optimizations like split-K.
Position-invarianceFor a fixed batch size, every element gets the same reduction schedule regardless of its position in the batch — the weaker property LLM-42 relies on.
Grouped verificationBatching several requests' small per-request verification windows into one verifier pass — cheap rollback per request, cheap compute per token overall.
is_deterministic flagPer-request API flag (default False) that opts a request into verification — the mechanism behind selective determinism.
Supporting terms
O1–O4The paper's four observations: consistent-span persistence (O1), kernel position-invariance (O2), position-consistency sufficing for determinism (O3), and the all-or-nothing failure of existing systems (O4).
split-KA GEMM optimization partitioning the reduction dimension across more thread blocks at low batch sizes — a major source of batch-shape-dependent rounding.
Consistent spanThe run of leading tokens that match between two runs of the same request; the "second consistent span" measures re-alignment after a first mismatch.
Forward progress guaranteeEvery verification pass yields at least one new, consistent token, even under worst-case rollback — DVR can never stall.
MoE routingToken-to-expert assignment in a Mixture-of-Experts model; variable tokens-per-expert is an extra source of shape-dependent kernel behavior.
MarginGateA follow-on scheme that verifies only decode steps with a small top-1/top-2 logit margin, since flips concentrate there.
