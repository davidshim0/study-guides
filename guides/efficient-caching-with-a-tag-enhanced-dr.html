HPCA 2025 · A Field Guide

Read the label first — don't haul the whole line to find out

Every DRAM cache in production today has to read an entire 64B line just to learn whether it's a hit or a miss. This is the plain-English story of TDRAM, tiny fast tag memory built right onto the DRAM die that answers "hit or miss?" without ever moving the data.

📄 Babaie, Akram, Elsasser, Haukness, Miller, Song, Vogelsang, Woo, Lowe-Power · HPCA'25 🎓 Cache/tiering concepts assumed — DRAM-device internals refresher included ⏱ ~25 min read
🏷️

Put a tiny copy of the tag in its own fast on-die memory — check it there, and only move the 64B of real data across the bus when the tag says you actually need it.

Before you begin

Quick glossary, then the DRAM internals you need

Cache and tiering vocabulary (hit/miss, LLC, working set) is assumed. What's new here is DRAM device vocabulary — mats, activate, bank groups — and the specific tag-storage problem this paper solves.

1Why DRAM is being asked to play "cache"▾

SRAM last-level caches are hitting a scaling wall, so systems like Intel's Sapphire Rapids now use a slab of HBM DRAM as a cache in front of DDR5 main memory — bigger and higher-bandwidth than SRAM, sitting between the on-chip caches and the real backing store.

If your own work is about OS-managed DRAM/NVM tiering over CXL: this is the same "fast tier in front of a slower, bigger tier" shape, except the placement decision — is this line here or do I have to fetch it? — happens entirely in hardware, at DRAM-cache-line granularity, in nanoseconds, with no page table involved.

Now you're ready: TDRAM is about making that hardware-only, line-granularity decision cheap to check.
2DRAM internals: banks, rows, mats, activate/read/write▾

A DRAM bank is built from many small subarrays called mats. An activate (ACT) command moves an entire row from a bank's mats into that bank's sense amplifiers; a read/write command then selects a column-sized slice of that row to transfer. Smaller mats have shorter wordlines and bitlines, so they activate faster — that single fact is the physical basis for TDRAM's speed-up.

Now you're ready: "tag mats" are just smaller, faster mats living on the same die as the data mats — same technology, different geometry.
3What "tag" means in a DRAM cache▾

A DRAM cache here is block-based and direct-mapped: each 64B line in the backing store maps to exactly one line in the DRAM cache. The tag is a compressed record of "which backing-store address currently lives here," plus valid/dirty bits — conceptually like an SRAM cache's tag array, just for a much bigger, DRAM-sized cache.

Now you're ready: the whole paper is about where that tag lives and how fast you can read it — not about the caching policy itself.
4The problem in one sentence▾

Existing DRAM caches (e.g. Intel Cascade Lake) store the tag in the same DRAM row as the data it describes. So learning "hit or miss?" requires activating that row and reading out the cache line's tag together with its data — before the controller even knows whether it needs the data.

Now you're ready: that single design choice is the villain of §II — it's what causes the miss-penalty, bandwidth, and queueing problems the paper measures next.
5Why it hurts twice: reads and writes▾

Read misses pay a DRAM read just to discover they missed. Writes are worse: every write — even a clean hit — must first read the line, because the controller can't risk overwriting dirty data it hasn't checked. That serialized read-before-write is what causes DQ bus turnaround bubbles.

Now you're ready: TDRAM's flush buffer and lockstep ActWr exist specifically to break this read-before-write dependency, avoiding the write→read→write DQ turnaround it causes.
6HBM3's interface: channels, pseudo-channels, buses▾

HBM3 has 16 independent channels, each with a 64-bit DQ bus split into two 32-bit pseudo-channels (PCs) that share one row (R) and column (C) command bus. Each PC natively delivers 32B per access — half a 64B CPU cache line.

Now you're ready: this mismatch (32B granularity vs 64B lines) is exactly why TDRAM has to pair up banks across bank groups and stagger their access.
7The competitive landscape, briefly▾

Cascade Lake hides tags in unused ECC bits. Alloy streams tag+data together in one wider (80B) burst. BEAR skips the tag check for write-hits only, using extra LLC↔DRAM coherence messages. R-Cache and eTag move tags off DRAM entirely (RRAM, or on-processor eDRAM) but hit speed or scalability limits. NDC is the closest relative — separate DRAM tag banks with in-DRAM comparison — but it lacks early tag probing.

Now you're ready: only Cascade Lake, Alloy, BEAR, NDC, and an Ideal baseline are actually evaluated against TDRAM in §V's simulations — R-Cache and eTag are discussed as related work, not simulated head-to-head.
8How the paper measures all this▾

Unlike much prior DRAM-cache work, this paper uses a full-system, execute-in-execute gem5 simulation (not traces), with LoopPoint sampling to pick representative regions of real multithreaded HPC codes — GAPBS graph kernels and NAS Parallel Benchmarks (NPB) at large problem sizes, 0.1–80 GiB footprints against an 8 GiB DRAM cache.

Now you're ready: the workload-by-workload bars you'll see throughout (bc, bfs, cg, ft, …) are 28 distinct HPC workloads, each run once per design for a fair comparison.
The whole story in one place

TDRAM in a nutshell

The problem, the fix, and how the pieces connect.

Existing DRAM caches (Cascade Lake, Alloy) store a line's tag in the very same DRAM row as its data. So determining hit-or-miss requires reading the line's tag together with its data — and that access sits on the critical path of every demand, not just misses: read misses pay it to no benefit, clean read/write misses pay for data they'll discard, and every write pays it up front to avoid clobbering dirty data. The result, measured directly in this paper: DRAM-cache tag checks queue up behind each other, inflating miss penalty, and up to 5× of the bytes moved per demand are wasted (§II).

TDRAM's fix: put the tags and metadata in their own small, low-latency mats on the same die as the data mats — separate storage, but still scaling automatically with DRAM capacity (unlike SRAM- or eDRAM-based tag stores). New ActRd/ActWr commands activate tag and data mats in lockstep; an on-die comparator determines hit/miss immediately and reports it over a new Hit-Miss (HM) bus — before the data has even left the sense amps. Column decode to the data mats is then gated on that result: no data moves unless the tag said it's needed.

Two more mechanisms round it out: early tag probing fills otherwise-idle command/HM-bus slots to check tags ahead of their turn, hiding latency and shrinking read-queue occupancy; a flush buffer holds dirty data displaced by write misses so writes never have to stall for a bus turnaround.

The payoff (all vs. state-of-the-art baselines, geo-mean over 28 HPC workloads): tag checks up to 2.65× faster, 1.23× system speedup, and 12–21% less energy — for 8.24% extra die area and a 9.7% signal-count increase, with nothing new on the data critical path.

🍯 Key takeaways

  • The villain: existing DRAM caches co-locate tag and data, so hit/miss determination requires reading the line's data together with its tag.
  • TDRAM's fix: small, fast tag mats on the same die, activated in lockstep with data via new ActRd/ActWr commands.
  • A new HM bus reports hit/miss + metadata separately from data — enabling conditional data response (skip the DQ transfer entirely on a clean read miss).
  • Early tag probing uses idle bus slots to learn hit/miss before a request's official turn, cutting queueing delay.
  • A flush buffer removes the write-then-read turnaround bubble for the rare write-miss-to-dirty case.
  • Result: 2.65× faster tag checks, 1.23× speedup, 21% less energy vs. Cascade Lake — for 8.24% die area, off the critical path.
Seven everyday pictures

How to think about TDRAM

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Tag with vs. apart from data

Checking the claim ticket

Baggage claim with tag sewn onto the suitcase: to read the tag, you must first haul the whole bag off the carousel. Baggage claim with a separate ticket: you check the ticket number first, and only walk over to the actual bag once you know it's yours. TDRAM's tag mats are that separate ticket — checked before the "bag" (the 64B line) is ever moved.

Where it breaks: the ticket still lives at the same terminal (die) as the bag — TDRAM doesn't move tags off-chip; it just gives them their own fast lane on-die.
Why it's faster · Mat geometry

The express lane

A big warehouse aisle takes longer to walk end-to-end than a small closet. Tag mats are built the same way as data mats, just physically smaller — shorter wordlines and bitlines — so an activate finishes faster. It's not a different technology, just a shorter walk.

Where it breaks: smaller mats aren't free — more of them are needed to cover the same tag capacity, which is exactly where the paper's die-area overhead comes from.
Decoupling · The HM bus

A text before the truck

"Your order shipped" arrives as a two-second text, long before the delivery truck itself pulls up. TDRAM's HM bus is that text: a few bytes reporting hit/miss and metadata, sent the moment the tag compare finishes — while the much bigger 64B "delivery" on the DQ bus is still optional and still to come.

Where it breaks: the text and the truck share the same warehouse (die) and much of the same road (bus timing budget) — the HM bus rides on the same clock as DQ, it's just a separate, narrower lane.
Saving bandwidth · Conditional response

Don't dispatch an empty truck

A well-run warehouse doesn't send a delivery truck out until stock is confirmed. TDRAM gates the data-mat column decode on the HM comparison result: on a clean read miss (read-to-invalid), no data crosses the DQ bus at all. That's the mechanism directly behind the bandwidth-bloat reduction in Table IV.

Where it breaks: a miss-to-a-dirty line still must send its old data back (to the flush buffer) — you can't skip the truck when there's something valuable to retrieve first.
Hiding latency · Early tag probing

Reading mail while the kettle boils

You don't stand and stare at the kettle — you sort mail during the wait, using time that would otherwise be wasted. TDRAM's command/HM buses are idle more often than its data mats are busy (tag mats are faster, and HM packets are much smaller than DQ ones), so the controller slots in tag-only probes for other pending requests during those gaps, getting an early hit/miss verdict.

Where it breaks: you can only sort mail that's already arrived — probing only helps requests already queued, and it introduces a small (<1% measured) chance of a bank conflict.
No write stalls · The flush buffer

A nightstand, not a round trip

Swapping books mid-read, you don't walk the old one back to the shelf before grabbing the new one off the cart — you set it on the nightstand and keep moving. On a write-miss to a dirty line, TDRAM drops the displaced dirty data into a small flush buffer instead of shipping it back to the controller immediately, so the incoming write proceeds with no DQ-bus turnaround bubble.

Where it breaks: the nightstand isn't infinite — a full flush buffer (rare; sized for 16 entries) does force an explicit unload, so this trick only works because write-miss-to-dirty is a genuinely uncommon event.
Filling in the gap · Bank pairing

Two movers, one couch

Two people carrying a couch each take a 32B "half," but they time their steps so both halves arrive at the truck together as one 64B whole. TDRAM pairs a bank in one bank group with a bank in another, staggering an ACT/RD across them, so a 32B-granularity HBM pseudo-channel delivers a 64B CPU cache line at lower latency than two separate back-to-back accesses.

Where it breaks: the two movers can't be in the same bank group — pairing is deliberately across groups, which is also what avoids back-to-back accesses to one group.
The full explanation

How it actually works

Section by section, with the paper's mechanisms rebuilt as diagrams.

1 · The interface — three changes to HBM3

TDRAM keeps HBM3's electrical and packaging conventions and changes three things: (1) it merges the separate row (R) and column (C) buses into one CA bus, DDR-style; (2) each of HBM3's 32 pseudo-channels becomes its own independent channel with its own 8-bit CA and 32-bit DQ bus; (3) a new 4-bit unidirectional HM bus is added per channel, carrying tag-compare result, status bits, and (on a dirty miss) the evicted tag — all at full data rate.

2 · Tag storage & lockstep access

Tags live in dedicated mats at the edge of each (even) bank, sized at 1/2 the wordline/bitline dimensions of data mats (about 4× smaller in area), sharply cutting wordline/bitline delay. A single ActRd or ActWr command activates the tag row and the data row together; on-die comparators in the tag mats' IOSA area do the compare and gate the data mats' column decode logic (the same trick as SALP subarray-level parallelism) — so column decode for data literally does not happen on a clean miss.

3 · Read and write protocol

Reads: on a hit or a dirty-miss, data streams out normally after the HM result; on a clean miss, no RD is issued to the data mats at all, and the controller can start the main-memory fetch the instant the HM bus reports the miss. Writes: ActWr triggers an internal read-then-write only when the tag says the line is dirty — moving the displaced data into the flush buffer — otherwise it's a single internal write, no read at all.

4 · Early tag probing

Because tag banks are faster than data banks and HM packets (3B) are far shorter than DQ bursts (64B), the CA and HM buses have unused cycles even while the DQ bus is saturated with back-to-back transfers. TDRAM fills those gaps with PROBE slots — tag-only accesses for queued requests, picked youngest-first to minimize queueing delay — so a request's hit/miss verdict can arrive before its official MAIN slot, letting a main-memory fetch start earlier and letting the request leave the read queue sooner.

5 · What it costs

Scaling the tag mats down by 1/2 in each dimension costs a 24.3% area penalty on the banks that carry them; since only even bank groups need tags, and banks are ~66% of total die area, the net die-area impact works out to about 8.24% (worked through in Worked Examples). On the interface side, TDRAM adds 192 new signals (a 4-bit HM bus + 2 extra CA bits per 32-bit channel), lifting the total pin/signal count by 9.7% — comfortably inside HBM3's existing spare bump sites.

Follow the numbers, step by step

Worked examples

Four calculations straight from the paper's own numbers.

① Why tags-in-SRAM can't scale, but tags-in-DRAM can

A 64 GiB block-based DRAM cache uses 64B cache lines and needs 3B of tag+metadata per line. How much tag storage is that, and how does it compare to today's biggest on-chip SRAM caches?

  1. Number of 64B lines in 64 GiB: 64 GiB ÷ 64 B = 1,073,741,824 lines (2³⁰).
  2. Tag storage needed: 2³⁰ lines × 3 B = 3,221,225,472 B ≈ 3 GiB — exactly the paper's own figure.
  3. Compare to SRAM LLCs today: AMD EPYC 9654P has 384 MiB of L3; Intel Xeon Platinum 8468H has 105 MiB. 3 GiB of tags alone is ~8× bigger than AMD's entire cache.
  4. Conclusion: putting tags in SRAM (on the processor die) caps DRAM-cache capacity at whatever tag capacity the processor chip can spare — the opposite of what a "bigger, cheaper tier" is supposed to buy you.
🍯
Insight: this is the paper's core scalability argument (§II-A) — tags must live somewhere that scales with the DRAM cache, not against it. That's the whole reason to put tags inside the DRAM itself.

② TDRAM's own tag entry — the same 3B, in a faster place

For a 1 PB address space with a direct-mapped cache, what does one TDRAM tag entry actually hold?

  1. Tag bits needed: 1 PB address space ÷ 64B lines → 14-bit tag uniquely identifies the backing-store line.
  2. Add status bits: + 1 valid bit + 1 dirty bit = 16 bits total for tag+status.
  3. Add ECC: 3B (24 bits) total budget − 16 bits = 8 bits left for ECC on the tag/metadata — enough for symbol-based Reed-Solomon, separate from the data's own ECC.
  4. Same 3B as example ① — but now sitting in a small, fast tag mat with its own comparator, instead of hidden in ECC bits or a shared row with the data.
💡
Same storage budget as the naive scheme — the entire win comes from where those 3 bytes physically live, not from storing less.

③ The die-area bill: 24.3% → 8.24%

Scaling tag mats to 1/2 size in each dimension costs 24.3% more area on the banks that hold them. How does that become an overall die-area impact of just 8.24%?

  1. Start with the mat penalty: smaller tag mats cost 24.3% extra area — but only on the banks that actually carry tags.
  2. Only even bank groups get tags: multiply by 0.5 (half the bank groups) → 24.3% × 0.5 = 12.15% of bank area.
  3. Banks are ~66% of total die area (the rest is TSVs, IOSAs, ECC, column decoders): 12.15% × 0.66 = 8.02% of total die area.
  4. Add wire routing for carrying hit/miss results from the even group to its paired odd group: 8.02% → 8.24% total — the paper's headline area number.
🍯
Insight: nearly all of the area cost comes from halving the mats and only paying it on half the banks — a deliberate design choice, not an unavoidable tax.

④ Reading the bandwidth-bloat table

At high miss ratio, Table IV lists Cascade Lake's bandwidth bloat factor as 2.75 and TDRAM's as 2.06. What does that mean, and what's the % reduction?

  1. What "2.75" means: 2.75 total bytes moved for every 1 useful byte — i.e. Cascade Lake moves 1.75× more data than a demand strictly requires, mostly wasted tag-check reads on misses and clean hits.
  2. TDRAM's number, 2.06, comes from skipping the DQ transfer entirely on clean read misses — closer to, but not exactly, 1.0 (real overhead remains from read hits, write hits, and dirty writebacks, which all still move data).
  3. Percent reduction: (2.75 − 2.06) / 2.75 = 0.69 / 2.75 ≈ 25.1% — matching the paper's stated geo-mean reduction vs. Cascade Lake at high miss ratio.
  4. Same arithmetic vs. Alloy (3.43 → 2.06): (3.43−2.06)/3.43 ≈ 39.9% — Alloy's 80B burst (64B data + 8B tag + 8B ignored) makes its baseline bloat worse to begin with.
💡
Bandwidth bloat converts directly to wasted energy — this is the arithmetic underneath the paper's 21% (Cascade Lake) / 12% (BEAR) energy-savings headline numbers.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Why does storing the tag in the same DRAM row as the data hurt write performance even more than read performance?
Show answer
Because every write — even one that will hit cleanly — must first read the line to confirm it isn't overwriting unflushed dirty data. Reads only pay the extra cost on a miss; writes pay it unconditionally, every single time, which is what causes DQ-bus turnaround bubbles (read-then-write direction changes) on top of the extra DRAM access.Misconception: that only misses are expensive. Writes are expensive by default in tag-with-data designs, regardless of hit or miss.
Problem 2 · medium
TDRAM adds a separate HM bus instead of just sending the tag-compare result back over the existing DQ bus. Why does that separation matter?
Show answer
The HM bus lets hit/miss information leave the DRAM the moment the tag compare finishes, independent of whether or when the (much bigger, much slower) 64B data transfer happens — or whether it happens at all. If the result rode the DQ bus, it would be stuck behind the data-transfer scheduling and granularity, defeating the whole point of early, cheap hit/miss signaling.Misconception: that any bus can carry the result equally well. The DQ bus's timing is dictated by 64B bursts; HM is a narrow, independent channel precisely so it isn't.
Problem 3 · easy
On a read that turns out to be a "miss to a clean line," does TDRAM ever issue an RD command to the data mats?
Show answer
No. The tag comparison result gates the column decode logic for the data mats — on a clean miss, no RD command is issued and no data crosses the DQ bus at all. The unused DQ slot can even be reused to opportunistically unload the flush buffer.Misconception: that the DRAM always transfers data and the controller just discards it if unneeded. TDRAM prevents the transfer from happening in the first place — the saving is in the DRAM protocol, not the controller.
Problem 4 · medium
A colleague says "early tag probing is basically a predictor, like MAP-I." What's the key difference?
Show answer
A predictor like MAP-I guesses hit/miss speculatively and can be wrong, so writes must still conservatively read data to avoid corrupting dirty lines, and reads must still verify before committing a fill. Early tag probing is not speculative — it performs a real tag comparison ahead of a request's official turn, using otherwise-idle bus slots, so its result is deterministic and correct, with none of a predictor's misprediction penalty or need for a fallback verification.Misconception: that "early" implies "speculative." Probing is earlier in time, not earlier in certainty — it's a real answer, just fetched opportunistically.
Problem 5 · hard
The paper reports TDRAM's bandwidth bloat factor is identical to NDC's (1.13 at low miss ratio, 2.06 at high), yet TDRAM is still 1.82× faster on tag checks and 1.08× faster overall. What accounts for the gap if they move the same amount of data?
Show answer
Bandwidth bloat only measures how much data moves, not how quickly a request learns its hit/miss status. NDC ties its hit/miss indication to the RD/WR command itself and has no early tag probing, so requests wait longer in the read buffer before their tag check even starts. TDRAM's HM bus plus early probing gets the same eventual data movement pattern, but reports the result — and can therefore kick off a main-memory fetch — sooner and with less queueing delay.Misconception: that "moves the same data" implies "same performance." Latency and bandwidth are separate axes; TDRAM wins on the former even when tied on the latter.
Problem 6 · medium
Why does TDRAM need a flush buffer at all — why not just always read the old dirty data back to the controller immediately, like existing designs do?
Show answer
Sending the dirty data back immediately forces a DQ-bus turnaround (write direction → read direction → back to write) for every write-miss-to-dirty, stalling the sequence of incoming writes. The flush buffer instead stashes that dirty data locally and unloads it opportunistically — during refresh, during read-miss-clean slots where DQ would otherwise carry nothing — so the controller's write stream never has to pause for it.Misconception: that "handle write-miss-dirty correctly" and "handle it fast" are the same requirement. TDRAM decouples correctness (never lose dirty data) from performance (never stall for it).
Problem 7 · easy
Does TDRAM's 8.24% die-area overhead apply uniformly across the whole DRAM die?
Show answer
No — only the even-numbered bank groups get the smaller, faster tag mats (odd groups are unchanged, data-only). The 8.24% is the net effect after accounting for that 50% split and for banks being roughly two-thirds of total die area; the local overhead on an affected bank is much higher (24.3%) before those reductions are applied.Misconception: reading a single headline area number as if the whole chip were modified equally. Overheads that are locally large can still be small in aggregate if they're applied selectively.
Problem 8 · hard
The paper finds that set-associative TDRAM (2/4/8/16-way) performs about the same as direct-mapped for its HPC workloads. Does that mean set-associativity is useless for TDRAM in general?
Show answer
No — the paper explicitly attributes this to its tested workloads having negligible conflict misses on the DRAM cache, not to any limitation of TDRAM's design. TDRAM supports set-associative tag comparison in parallel (one comparator per way) with no fundamental change to the mechanism; workloads with higher conflict-miss rates would be expected to benefit from associativity the same way any cache does.Misconception: generalizing "no benefit measured here" to "no benefit exists." The result is workload-dependent, not mechanism-dependent — it says more about the HPC benchmark suite's access patterns than about TDRAM's ceiling.
Quick answers

Frequently asked questions

Twelve questions newcomers ask most.

Q1What exactly is wrong with today's DRAM caches?▾
They store tags in the same DRAM row as the data, so determining hit/miss requires reading the line's tag together with its data — on the critical path of every read miss and every write. This inflates miss penalty, causes read-buffer contention, and wastes bandwidth transferring data nobody needed (up to 5× access amplification, per prior work cited in the paper).
Q2Why not just put the tags in on-chip SRAM instead?▾
A 64 GiB DRAM cache needs ~3 GiB of tags — far more than any current processor's entire SRAM LLC (384 MiB on AMD EPYC 9654P, 105 MiB on Intel Xeon Platinum 8468H). Tags-in-SRAM designs like eTag also tie DRAM-cache capacity to how much tag SRAM the processor die can spare, which caps scalability exactly where DRAM caching is supposed to help.
Q3Why not RRAM for tag storage, like R-Cache?▾
Tag comparison sits on the critical path, so tag read/update latency must be minimal — and tags are updated frequently. RRAM is both slower than DRAM and wears out faster under frequent updates, making it a poor fit despite its density advantages.
Q4Is TDRAM a new memory technology, or an extension of existing DRAM?▾
An extension. TDRAM deliberately builds on HBM3's existing bank microarchitecture, protocol, and ecosystem rather than redesigning DRAM from scratch — the goal is a lower-cost, lower-risk, incrementally adoptable change, not a new memory class.
Q5How does TDRAM compare to NDC, its closest prior relative?▾
Both put tags in DRAM and check them in-DRAM. But NDC modifies DRAM's sensing circuitry and uses a CAM-like structure for tag matching, and ties hit/miss reporting to the RD/WR command itself (no idle-slot probing). TDRAM keeps standard DRAM sensing, uses an HM bus decoupled from data commands, and adds early tag probing — the paper measures TDRAM 1.82× faster on tag checks and 1.08× faster overall than NDC.
Q6What's the actual hardware cost?▾
About 8.24% extra die area (from smaller, more numerous tag mats on half the bank groups) and a 9.7% increase in total signal count (192 new signals: a 4-bit HM bus and 2 extra CA bits per 32-bit channel) — accommodated within HBM3's existing spare bump sites, so no new package is needed.
Q7Does TDRAM require operating-system or software changes?▾
No — TDRAM is entirely hardware-managed at the memory-controller and DRAM level, transparent to software. This is different from OS-managed tiering schemes, which make placement decisions in software at page granularity; TDRAM makes its hit/miss decision in hardware at cache-line granularity, in nanoseconds.
Q8Do predictors or prefetchers still help on top of TDRAM?▾
Marginally (1.03–1.04× from a MAP-I-style predictor). Predictors can't guarantee a predicted miss isn't actually a hit, and still require a data read before write to protect dirty lines — exactly the serialization TDRAM's early tag probing already resolves deterministically. TDRAM is designed to be orthogonal to such techniques, not to depend on them.
Q9Does associativity matter for TDRAM?▾
The mechanism supports set-associative caches (parallel comparators per way), but the paper's HPC workloads show negligible conflict misses on the DRAM cache, so direct-mapped and 2/4/8/16-way associative TDRAM perform similarly for these specific workloads — a workload property, not a design limitation.
Q10Why HBM3 specifically, and not DDR5 or CXL-attached memory directly?▾
HBM3 is already deployed as a cache in front of DDR5 in real systems (Intel Sapphire Rapids), giving TDRAM a concrete, already-adopted target. The authors note the tag/data separation is technology-agnostic — it applies to other DRAM types, including memory reachable over CXL, since only the tag-storage layout changes, not the underlying cell technology.
Q11How rare is write-miss-to-dirty, really, and does that matter?▾
Rare enough that a modest 16-entry flush buffer avoids essentially all stalls across the evaluated workloads (average occupancy 5 entries, max 12; only one workload configuration with a smaller 8-entry buffer stalled, and only 13 times total). It still has to be handled correctly for every access, which is exactly what motivates a dedicated, always-correct mechanism rather than a probabilistic one.
Q12What's left for future work?▾
The paper mentions exploring OS/software integration opportunities and GPU-specific adaptations (building on prior GPU DRAM-cache work), plus specialized predictors/prefetchers tuned for DRAM caches specifically — TDRAM's mechanism is presented as orthogonal groundwork those future techniques could build on.

Glossary, results, and provenance

Every term in one place, then where the numbers came from.

Core terms
TDRAMTag-enhanced DRAM — small, low-latency tag/metadata mats added on-die alongside the data mats.
ActRd / ActWrNew commands that activate tag mats and data mats in lockstep for a read or write, enabling parallel tag compare.
HM busNew 4-bit unidirectional Hit-Miss bus per channel, reporting compare result + metadata independent of the data bus.
Conditional data responseGating data-mat column decode on the tag-compare result — skip the DQ transfer when data isn't needed.
Early tag probingFilling idle CA/HM slots with tag-only checks for queued requests, ahead of their official MAIN slot.
Flush bufferBase-layer buffer holding dirty data displaced by write misses, unloaded opportunistically to avoid DQ-bus turnaround stalls.
Bandwidth bloat factorTotal bytes moved ÷ useful bytes moved for a demand; TDRAM's protocol minimizes this by skipping unneeded transfers.
Supporting terms
MatThe tiled subarray a DRAM bank is built from; smaller mats have shorter wordlines/bitlines and lower access latency.
Pseudo-channel (PC)HBM3 splits each 64-bit channel into two 32-bit PCs sharing a command bus; TDRAM makes each PC an independent channel.
Bank pairingStaggering ACT/RD across banks in different bank groups to deliver a 64B CPU line from 32B-granularity pseudo-channels.
IOSAIO Sense Amp region of a bank, where TDRAM places its on-die tag comparators.
LoopPointA checkpoint-driven sampling technique for multithreaded applications, used to keep execution phases consistent across designs.
Cascade Lake / Alloy / BEARBaselines: tag+metadata in ECC bits; tag+data in one 80B burst; tag+data together but skipping checks on write-hits, respectively.
NDCNative DRAM Cache — separate DRAM tag banks with in-DRAM comparison, but no early probing; TDRAM's closest relative.
GAPBS / NPBThe GAP Benchmark Suite (large graph kernels) and NAS Parallel Benchmarks — the multithreaded HPC workloads used for evaluation.

Related work

Supporting Very Large DRAM Caches with MissMap medium

Loh & Hill · IEEE Micro · 2012

One of the earliest block-based DRAM caches; introduced a MissMap to avoid accessing the DRAM cache on predicted misses.

Alloy Cache medium

Qureshi & Loh · MICRO · 2012

Streams tag and data together in a single 80B burst to reduce hit latency; one of TDRAM's direct evaluation baselines.

BEAR hard

Chou, Jaleel, Qureshi · ISCA/CAN · 2015

Reduces bandwidth bloat by having the LLC and DRAM cache exchange existence/eviction messages to skip tag checks on write-hits.

Native DRAM Cache (NDC) hard

Ryu, Kim, Jung, Ahn, Kim · ISCA · 2024

TDRAM's closest relative — separate DRAM tag banks with in-DRAM comparison via a CAM-like structure, but no early tag probing.

R-Cache hard

Behnam, Chowdhury, Bojnordi · ICCD · 2018

Uses resistive RAM for on-die tag storage; TDRAM's related-work discussion contrasts RRAM's latency/wear limits with DRAM tag mats.

Reducing Memory Access Latency with Asymmetric DRAM Bank Organizations hard

Son, Seongil, Ro, Lee, Ahn · ISCA · 2013

Source of the smaller-mat latency-reduction data TDRAM's tag-mat timing and area estimates are calibrated against.
