Giving concurrency to whoever's easiest to reason about, not whoever's fashionable this decade

Events won the "high concurrency" argument in the late '90s. This paper's authors — who helped build several event systems — changed their minds. Here's their case for threads, in plain English.

What you need going in

A TL;DR, a quick glossary of proper nouns, and ten prerequisite ideas — collapsed by default, open whichever you need.

⚡ TL;DR

  • Threads and events are Lauer–Needham duals — structurally equivalent — so a good thread runtime (fixing O(n) scheduler operations and context-switch cost) can match every strength claimed for events, while keeping ordinary call/return control flow.
  • An optimized GNU Pth thread package scales flat to 100,000 concurrent tasks in a synthetic SEDA benchmark, matching event-driven throughput; separately, the authors' 700-line threaded web server Knot (on a ~5,000-line thread package) hits ~700 Mbit/s, tested up to 65,536 clients — beating SEDA's event-driven Haboob (~500 Mbit/s peak, CPU-limited at 512 clients, 6× the context switches, out of memory past 16,384 clients).
  • It matters because the "threads vs. events" fight is really "who owns the concurrency policy — the runtime or the application" — the same question that recurs in scheduler design, and in deciding whether the OS or the application should drive resource placement.

1Threads vs. coroutines vs. processes▾

A thread is a unit of sequential execution with its own call stack, sharing memory with other threads in the same process. A coroutine is similar but only switches when it explicitly yields (cooperative, not preemptive). A process has its own address space too, which is heavier still.

This paper's thread package is user-level and cooperative — closer to coroutines than to kernel (preemptive, OS-scheduled) threads.

Now you're ready: when the paper says "threads," it usually means this lightweight, cooperatively-scheduled, user-level flavor — not the heavyweight kernel threads that gave threads a bad name.
2Blocking I/O vs. event loops (select/poll/epoll)▾

A blocking call (e.g. read()) suspends the whole thread until data arrives. An event loop instead calls select()/poll()/epoll() to ask "which of these many sockets are ready?" and dispatches a small handler for each — one thread serving thousands of connections without blocking any of them.

This is the mechanical reason events scaled where naive one-thread-per-connection servers didn't: not blocking meant not needing thousands of OS threads.

Now you're ready: the paper's whole point is that a good thread runtime can hide blocking calls behind the same non-blocking machinery, so you get the scalability without giving up call/return code.
3Context switches, and why they cost anything▾

Switching from running one thread to running another means saving one set of registers/state and loading another — and, for kernel threads, often a trip through the OS (a kernel crossing). That's real, measurable overhead, especially under preemption.

User-level cooperative threads can switch far more cheaply, since there's no kernel crossing and no preemption to guard against — the paper attributes the low cost to avoiding these, plus using a lightweight primitive (coro) for the actual switch.

Now you're ready: "threads are slow because of context switches" is exactly the claim this paper disputes — it's a property of specific implementations, not of the thread abstraction.
4Stacks: automatic state, at a size cost▾

Every thread's local variables and call history live on its stack. Stacks are usually fixed-size, so you must pick a size big enough to avoid overflow but small enough not to waste address space — awkward when you have 100,000 threads.

Event systems dodge this by keeping few threads (often one) and storing per-task state on the heap by hand instead.

Now you're ready: this tradeoff motivates the paper's proposed fix — compiler-assisted dynamic stack growth (Section 4.1) — one of its concrete "give threads compiler help" proposals.
5Callbacks and continuations▾

In an event system, instead of calling a function and waiting for its return, you register a callback to run later, when a reply arrives. Chained callbacks are a crude form of continuation — "what to do next" captured as data instead of as a suspended call stack.

The catch: whatever variables the original caller needed are no longer sitting on a stack — the programmer must package them up by hand and pass them along.

Now you're ready: this manual packaging is exactly "stack ripping" — the paper's central complaint about event-driven programming style.
6User-level (M:N) vs. kernel (1:1) threading▾

1:1 threading maps each thread straight to a kernel thread — simple, but every blocking call and context switch may cross into the kernel. M:N threading multiplexes many user-level threads onto few kernel threads, letting a runtime schedule cheaply in userspace and only cross into the kernel when it truly must (e.g., for actual blocking I/O).

Now you're ready: the paper's thread package is this kind of user-level, cooperatively-scheduled package (the paper itself just calls it a "user-level thread package," without using the M:N label) — that's what lets it get to 100,000 threads without 100,000 kernel-scheduled entities.
7Cooperative vs. preemptive scheduling▾

Preemptive scheduling can interrupt a thread anywhere, anytime — safe in general, but means any two lines of code might race, so you need locks around shared state. Cooperative scheduling only switches at explicit yield points (like a blocking call) — so code between yield points is automatically atomic, with no locks needed on a single core.

Now you're ready: event systems' "free synchronization" comes from being cooperative, not from being event-driven — and cooperative thread systems get the same benefit (Section 2.2, citing Adya et al.).
8Why "O(n) in the number of threads" is a red flag▾

A naive thread scheduler might scan every thread to find one that's runnable, or walk every thread's data structure on some housekeeping operation. That scan takes time proportional to the thread count — fine at 10 threads, ruinous at 100,000.

Now you're ready: removing exactly these O(n) operations from GNU Pth is what let the paper's optimized thread package scale to 100,000 threads (Figure 2) — the fix was a data-structure change, not a paradigm change.
9Reference counting and garbage collection, briefly▾

Event systems typically heap-allocate per-task state (since there's no stack to hold it), so something must eventually free it. Reference counting tracks how many places point to an object and frees it at zero — simple in principle, easy to get wrong on error paths. Garbage collection (as in Java) automates this but adds pause times and CPU overhead.

Now you're ready: the paper blames both approaches for real bugs and overhead in event systems (Inktomi's reference-counting leaks; Haboob's GC pressure) — problems threads sidestep via the call stack.
10Call graphs and whole-program compiler analysis▾

A call graph maps which functions can call which. Compilers can walk it to compute bounds — e.g., "how much stack could this call chain ever use?" — as long as the graph is mostly static (recursion and function pointers make it harder).

Now you're ready: this is the machinery behind the paper's compiler-support proposals (Section 4) — bounding stack growth per call site, and nesC's atomic-section checking on a similar graph.
The whole story in one place

The argument in a nutshell

Why the authors — event-system builders themselves — switched sides.

By the late 1990s, the conventional wisdom was that events were the only way to build servers handling tens of thousands of concurrent connections: cheap cooperative synchronization, no wasted per-thread stacks, application-level scheduling, flexible control flow. Threads, by contrast, had a reputation for poor scalability and heavyweight context switches.

The authors revisit Lauer–Needham duality (1978): a thread system and a message-passing/event system built to the same design are structural mirror images — every event concept maps onto a thread concept (Figure 1 in the paper). If duals are equally well implemented, they must perform equivalently. So if event systems were winning, the paper argues, it wasn't because events are inherently better — it was because nobody had built a thread runtime engineered for this workload.

They prove it two ways. First, they take an existing thread package (GNU Pth), remove its O(n)-in-thread-count scheduler operations, and show it scales flat to 100,000 threads, matching an event server. Second, they build Knot, a 700-line threaded web server on a ~5,000-line user-level thread runtime, and show it out-performs SEDA's Haboob: ~700 Mbit/s vs. ~500 Mbit/s, with Haboob becoming CPU-bound at 512 clients and running out of memory beyond 16,384 clients.

The upshot: threads keep the natural call/return programming model — no stack ripping, no hand-rolled continuations — while matching or beating events on every axis events were claimed to win. The paper's forward-looking claim is that compilers, not just runtimes, are the next lever: bounding stacks, pruning dead state, and checking atomicity statically.

🍯 Key takeaways

  • Threads and events are Lauer–Needham duals — the same power, mapped onto different vocabulary.
  • The paper argues the "problems with threads" are not intrinsic: performance is traced to implementation artifacts (O(n) operations, switch costs), control flow and scheduling are answered by a code survey and by duality, synchronization by cooperative scheduling, though for stack/state management and multiprocessor synchronization, its fix is a proposed compiler/runtime enhancement, not something it demonstrates eliminated.
  • Cooperative scheduling — not "being event-based" — is what gives "free" synchronization; it works for cooperative threads too.
  • Stack ripping is the real cost event programmers pay for avoiding threads — manually saving/restoring state across callback boundaries.
  • A modified GNU Pth scales to 100,000 threads in a synthetic benchmark; separately, Knot (700 lines) beats Haboob 700 vs. ~500 Mbit/s, with Haboob CPU-bound at 512 clients and OOM past 16,384 (Knot tested to 65,536).
  • The paper's forward bet: compiler support for stacks, live-state pruning, and atomicity checking is the next real lever for thread systems.
Seven everyday pictures

How to think about the threads/events debate

Each stands alone; every card is honest about where it stops being true.

The core idea · Lauer–Needham duality

Two translations of the same play

A play performed in English and the same play performed in French use different words for every line, but they're the same play — same plot, same pacing, same emotional beats. Threads and events are like that: SendMessage/AwaitReply is French for "procedure call"; SendReply is French for "return." Stage a good production in either language and audiences should react the same way.

Where it breaks: a bad translation ruins the play without touching the plot. That's the paper's whole point — a bad thread implementation "mistranslates" the abstraction, and people blamed the play instead of the translator.
Formalizing the duality · Blocking graph

The trail map, not the trailhead sign

A hiking map marks every fork and rest stop, no matter which language the signs are printed in — the terrain is what matters. The paper's blocking graph does the same for a program: nodes are blocking/yielding points, edges are the code in between. Draw this graph for a thread program and its event dual, and — if both are well built — they're the same map.

Where it breaks: the map only shows blocking points, not everything that makes a real hike hard (weather, fatigue) — likewise the blocking graph abstracts away real costs like memory layout and cache behavior that can still differ between implementations.
Cooperative scheduling · "Free" synchronization

An unlocked door, because no one's forcing it

You can leave your office door unlocked all day if you trust that nobody will walk in mid-sentence and rearrange your desk. That's cooperative scheduling: code between yield points runs uninterrupted, so you don't need locks — not because you're using events, but because nothing preempts you. Cooperative threads get the same unlocked door.

Where it breaks: the moment a second person (a second CPU core) has their own key, "nobody walks in" stops being true — cooperative scheduling's free lunch is a uniprocessor phenomenon, on both sides of the duality.
Stack ripping · State management

A novel that erases your bookmark every chapter

Imagine reading a novel where, at every chapter break, someone rips out your bookmark and your margin notes — you must rewrite from memory what you were thinking, who the characters were, before continuing. That's an event handler at a callback boundary: no call stack survives the break, so the programmer manually re-packages every variable that needs to live on ("stack ripping," per Adya et al.).

Where it breaks: a disciplined reader can keep good notes; likewise disciplined event programmers manage this — but the paper's point is that threads don't require the discipline in the first place. It's an unforced cost.
Fixing performance · Removing O(n) scheduler ops

A coat-check that stops re-counting every coat

A coat-check clerk who re-counts every coat on the rack each time one more arrives gets slower as the party grows — not because coat-checking is slow, but because that clerk's method is. Swap in a clerk who just adds one ticket to a running tally, and the party can grow to thousands with no slowdown. That's what removing O(n)-in-thread-count scheduler operations from GNU Pth did — same job, smarter bookkeeping.

Where it breaks: some bookkeeping is genuinely proportional to load (you do have to store each coat somewhere) — the fix removes needless re-scanning, not all per-thread cost.
Compiler support · Dynamic stack growth

A hotel room sized to your actual luggage

Building every hotel room to fit the biggest suitcase anyone might ever bring wastes space for everyone else; building rooms too small risks turning guests away. A compiler that analyzes each call site's stack needs can size — and re-size — a thread's stack to what it actually uses, sidestepping the fixed-size stack's overflow-vs-waste tradeoff entirely.

Where it breaks: a hotel can't predict a guest who shows up with an unplanned trunk; likewise recursion and function pointers make worst-case stack bounds genuinely hard to compute statically; the paper says these "produce additional challenges" that "can be addressed with further analyses", without showing how.
SEDA's compromise · Threads within, events between

An assembly line with a crew at every station

SEDA is an assembly line: items (requests) ride a conveyor (queue) between stations (stages), but each station has its own small crew (thread pool) doing real work. It's a genuine hybrid — Lauer–Needham's message-passing model between stages, ordinary threading within them. The paper credits SEDA with returning event systems to this more disciplined structure.

Where it breaks: every hand-off between stations still costs a conveyor trip (a queue enqueue/dequeue and, per this paper, a context switch) — Haboob's measured 30,000 context switches/second is that toll adding up under load.

Telling detail: the authors' own event-based Ninja system fell back to threads for its most complex parts, such as recovery, because getting them right with events (tried first) proved nearly impossible; and applications in those projects that did not need high concurrency were always written with threads.

5 · Compiler support (Section 4) — the forward-looking proposal

Having shown threads can match events today, the paper argues compilers are the next lever, since threads (unlike opaque event dispatch) expose a normal call graph for analysis:

// dynamic stack growth: compiler bounds stack need per call site
function handle_request():
    // (illustrative) compiler proves: ≤ 240 bytes live here
    buf = read_headers()      // may block; stack frame stays small
    if needs_more_stack(): grow_stack()   // only when a call site demands it
    parse(buf)
    // compiler pops dead temporaries before the next call
    write_response(buf)

Three concrete proposals: dynamic stack growth (bound per-call-site stack needs, grow on demand — hard for recursion/function pointers, but tractable for the common case); live-state pruning (pop dead temporaries before calls, warn on large state held across blocking calls); and static synchronization checking, modeled on nesC's atomic sections for TinyOS, which the compiler verifies never span a yield point.

6 · The evaluation (Section 5)

Two experiments carry the whole argument. Figure 2 (in §2.2, not §5) repeats SEDA's own threaded-vs-event benchmark; a GNU-Pth-based server, once its O(n) scheduling operations are removed, scales flat to 100,000 threads, matching the event server. Figure 3 pits the authors' own Knot (700 lines, on a ~5,000-line thread runtime) against SEDA's Haboob, on identical hardware (2×2000 MHz Xeon SMP, 1 GB RAM, Linux 2.4.20), both using plain poll() for a fair comparison.

The numbers: Knot-C (favoring active connections) reaches ~700 Mbit/s; Haboob peaks at ~500 Mbit/s, becoming CPU-limited at 512 clients, with 30,000 context switches/second, over 6× Knot's rate, and running out of memory beyond 16,384 clients. M1 · The two programming models, and where a request's state lives

Thread model. Each concurrent request gets a thread: a saved register set plus a private stack. The request is handled by ordinary sequential code. When the code makes a call that can block (reading a socket, reading a file), only that thread is suspended. While it waits, everything the request still needs, its live state (local variables, arguments, return addresses), stays in its stack frames. The scheduler keeps a run queue of ready threads and a record of what each blocked thread is waiting for.

Event model. One loop, usually on one kernel thread, asks the OS which I/O is ready (select/poll) and calls a handler for each ready event. A handler must not block: it runs to completion and returns to the loop. Anything a request needs after the handler returns must be saved by hand in a heap object, a continuation: "which handler runs next" plus "the variables it will need". One stack is enough, because it is empty between handlers.

The paper opens with the four strengths claimed for events: inexpensive synchronization due to cooperative multitasking; lower overhead for managing state (no stacks); better scheduling and locality, based on application-level information; and more flexible control flow (not just call/return). M4 takes them one at a time.

Section 3 rests the case for threads on two properties of servers: the concurrency comes from largely independent requests, and the code that handles each request is usually sequential. Under those two properties the thread model maintains a simple invariant: one request, one stack, one sequential flow of control, with every call matched to its return in the source. If requests interact heavily (dynamic fan-in or fan-out), or one request needs internal parallelism, the invariant no longer describes the workload, and the paper concedes events may then be more natural (M6).

From the lecture (10/1). M2 · Lauer–Needham duality, row by row

Lauer and Needham (1978) described two canonical system structures. In the message-passing one, a set of processes each own their data and communicate only by sending messages to ports; a process repeatedly waits for a message, handles it, and may send a reply. In the procedure-oriented one, many threads share data protected by monitors, communicate by calling monitor procedures, and wait on condition variables. They gave a one-to-one mapping between the concepts and argued that, with proper implementations, a program built one way and its dual built the other way perform the same; the choice should come down to which style is more natural for the application. The paper's Figure 1 restates the mapping in modern event vocabulary:

What the duality preserves. The mapping is mechanical, so the transformed program has the same blocking and yielding points with the same code between them (the blocking graph, M3). With equal per-operation costs, the two versions do the same work and make the same scheduling decisions, hence equal performance.

The paper's three refinements (§2.1). (1) Lauer and Needham ignore the cooperative scheduling that event systems use for synchronization (M8). (2) Most event systems use shared memory and global data structures, which Lauer and Needham describe as atypical for message-passing systems; the only event system that really matches their canonical model is SEDA, whose stages and queues map exactly to processes and message ports. The footnote adds that "arguably" one of SEDA's contributions was to return event systems to the "good practices" of Lauer–Needham. (3) The performance equivalence requires equally good implementations, and the authors do not believe a suitable thread implementation for very high concurrency had existed; they demonstrate one (§5) and propose more (§4).

Assumptions, and what breaks. The performance half of the duality assumes a thread switch costs about what an event dispatch costs, and a blocking call costs about what registering a callback costs. If thread switches are much more expensive (preemptive switches that save full state, kernel crossings), the duals perform differently, which is exactly the paper's diagnosis of earlier thread results. It also assumes each side can make the same scheduling choices (M9). The duality says nothing about which version is easier to write or debug; the paper's preference for threads in §3 is a programmability argument layered on top of performance equivalence.

🔗
Connection: Mesa monitors. The thread column of Figure 1 is Mesa's vocabulary: monitors with entry procedures, condition variables with WAIT, and FORK/JOIN. One mechanical parallel worth noting (inference): a Mesa thread woken from WAIT must re-check its condition, because other threads may have run in the monitor between the NOTIFY and its resumption. The event dual has the same property: when the reply message finally triggers the next handler, other handlers have run in between and may have changed shared state, so the handler must re-validate what it assumed before it returned to the loop.

M3 · The blocking graph

The paper names the object Lauer and Needham's argument implicitly relies on. In a blocking graph, each node is a blocking or yielding point, and each edge is the code executed between two such points. The duality argument "essentially says that duals have the same graph."

In thread code, a node is any call that can block or yield: accept, read, a file read, a lock acquire that can wait, an explicit yield. An edge is the straight-line code a thread runs from one such call to the next. In event code, an edge is a handler body (or part of one): the handler starts when the event at one node arrives, and it ends by registering for the event at the next node. So the two versions of a program have the same scheduling points and the same code between them.

The graph shows up twice more in the paper. In §4.3, the nesC compiler uses "a variation of a call graph that is similar to the blocking graph" and checks that every atomic section lies within one edge, so nothing inside an atomic section can yield or block, even indirectly. And it explains the cooperative-scheduling invariant (M8): code on one edge runs without interleaving.

What the graph does not capture (this guide's reading). It fixes where switches happen, not how much each one costs. An implementation can also add nodes the program does not need: in a staged event server, each hand-off between stages is a switch point even when nothing blocks (M13, Haboob). Two implementations of the "same" program with different graphs, or with different per-node costs, can perform differently without contradicting the duality.

The performance criticism, mechanically. The paper does not name the O(n) operations it removed from Pth. Typical ones in packages of that era (this guide's reading) are scanning every thread to find a runnable one, rebuilding the select/poll descriptor set from every blocked thread on each scheduling pass, and walking all thread records to check timeouts. If any of these runs on every switch, switch cost grows with n and throughput falls as concurrency rises, which looks like "threads don't scale" while really being "this scheduler doesn't scale". The usual fix is to keep ready threads on a queue and index waiting threads by what they wait for, so a wakeup costs O(1) per event.

On switch cost: a preemptive switch can happen at any instruction, so the full register state must be saved. A cooperative switch happens only inside a library call, where the calling convention already lets the caller-saved registers be clobbered, so only the callee-saved registers and the stack pointer need saving (inference from calling conventions; the paper just says preemption "requires saving registers and other state"). Kernel threads add a user-to-kernel-to-user crossing on top. User-level cooperative threads avoid both, and that is what the paper's own package relies on (M11).

M6 · Control flow: why call/return is enough for servers

The criticism (§2.2). Threads encourage programmers to think too linearly, which might rule out more efficient control-flow patterns.

The survey. The authors examined the code of the Flash web server and of several applications in Ninja, SEDA and TinyOS. Every control-flow pattern fell into three categories:

  • Call/return: ask another module for something and wait for the answer. Threads: a procedure call.
  • Parallel calls: issue several requests, then wait for all of them. Threads: fork several, then join.
  • Pipelines: items flow through a fixed sequence of stages. Threads: one thread per item walking the stages in order, or a thread per stage with queues between.

The authors argue more complex patterns are absent because they are hard to use well. The "accidental non-linearities" that already occur in event systems are hard to understand and cause subtle races; deliberately complicated control flow would be just as error-prone.

Why event code ends up as call/return anyway. The paper says "it is no coincidence": robust systems need acknowledgements for error handling, for storage deallocation and for cleanup, so they need a "return" even in the event model. Mechanically, if module A sends a request carrying a buffer to module B and never hears back, A cannot know when the buffer may be freed, whether the request failed, or whether to retry. So B must reply, and a send paired with its reply is a call/return written out by hand.

The concession. The only patterns the authors found less graceful with threads are dynamic fan-in and fan-out, where the number of parties is not known in advance, as in multicast or publish/subscribe. There "events are probably more natural". None of the high-concurrency servers they studied used these patterns.

The cost of the event version (§3). Many event systems "call" a method in another module by sending an event and expect a "return" through a similar event. To understand the program, the programmer must mentally match these call/return pairs even when they sit in different parts of the code; each pair usually requires saving and restoring live state by hand (stack ripping, M7); and the obscured control flow can lead to "subtle race conditions and logic errors due to unexpected message arrivals". An example of the last (this guide's): a handler waiting for a cache reply instead receives a connection-closed event; if the code assumed only the reply could come next, it touches state that the close path already freed. In a thread, the request is inside the call, and the close shows up as an error returned from that call.

Threads group calls with their returns in the syntax, which makes cause and effect easy to see and guarantees a one-to-one pairing. The run-time call stack holds all of a task's live state, so ordinary debuggers can show it.

M7 · Stack ripping, exception handling, and state lifetime

Definition. The paper borrows Adya et al.'s term: "stack ripping" is the programmer's manual saving and restoring of live state across the split points of an event-style call/return pair. In a thread, the variables a request needs while it waits are already in its stack frames. In an event handler the frame is gone when the handler returns, so those variables are "ripped" off the stack into a heap object and read back in the next handler.

The transformation, step by step (the procedure is this guide's spelled-out version of what the term means; the paper names the burden but does not list steps):

  1. Cut the function at every call that may block. A function with k blocking calls becomes k+1 handlers; each handler ends by issuing the asynchronous version of the next call, with the following handler registered as its completion.
  2. Find the live variables at each cut: those defined before it and used after it.
  3. Rip: allocate a heap continuation in the first handler, copy the live variables into it, and pass it along. Each later handler reads them from the continuation instead of its own frame.
  4. Flatten control structure. A loop, if, or try/finally that spans a cut cannot span handlers, so it becomes an explicit state machine (a state field in the continuation).
  5. Free on every exit. The normal end and every error branch in every handler must release the continuation and anything it owns.
  6. Propagate upward. The original function now returns before its work is done, so each caller must also take a completion callback, and the rip spreads up the call chain.
// threaded: live state stays in the frame across each blocking call
void serve(int fd) {
    char *buf = alloc(8192);
    req_t req = read_req(fd, buf);          // may block
    if (req.err) { free(buf); return; }      // cleanup is local
    data_t d = cache_get(req.path);         // may block
    write_all(fd, d);                       // may block
    free(buf);
}

// ripped: one handler per edge; live state copied into a heap continuation
struct cont { int fd; char *buf; req_t req; };
void serve(int fd) {
    struct cont *c = malloc(sizeof *c);
    c->fd = fd; c->buf = alloc(8192);       // the rip: save what later handlers need
    read_req_async(fd, c->buf, on_req, c);  // returns at once; caller cannot know when done
}
void on_req(struct cont *c, req_t r) {
    if (r.err) { free(c->buf); free(c); return; }   // forget either free: a leak
    c->req = r;
    cache_get_async(r.path, on_data, c);
}
void on_data(struct cont *c, data_t d) { write_async(c->fd, d, on_done, c); }
void on_done(struct cont *c, int err) { free(c->buf); free(c); }

Exception handling and state lifetime (§3). In a thread system, cleanup after an exception or a normal end is simple because the stack "naturally tracks the live state for that task". In event systems task state is usually heap allocated, and freeing it at the right time "can be extremely difficult" because branches in the control flow, especially error conditions, can skip deallocation steps. Two fixes were used in practice, and the paper reports a cost for each:

  • Garbage collection (Ninja, SEDA): previous work found Java's general-purpose collector inappropriate for high-performance systems (the Telegraph experience, ref. [14]). M13 lists GC load among Haboob's overheads.
  • Reference counting (Inktomi's Traffic Server): keeping counts correct was hard, particularly for error handling. Footnote 2: "Nearly every release battled with slow memory leaks due to this kind of reference counting; such leaks are often the limiting factor for the MTBF of the server."

Evidence from existing systems. The authors' own Ninja system used threads for its most complex parts, such as recovery, "simply because it was nearly impossible to get correct behavior using events (which we tried first)". Applications in those projects that did not need high concurrency were always written with threads, and the Harvest FTP server uses threads.

"Just fix events?" One could build tools or languages that solve reply matching, live-state management and shared-state management for event systems. The paper's answer: such tools would effectively duplicate the syntax and run-time behavior of threads. Adya et al.'s cooperative task management, which lets event-system users write thread-like code that is transformed into continuations around blocking calls, is the case in point: "fixing the problems with events is tantamount to switching to threads."

M8 · Synchronization: what "free" really comes from

The claim. Event systems say cooperative multitasking gives them synchronization "for free": the runtime needs no mutexes and no wait queues. The rebuttal, credited to Adya et al.: the advantage comes from cooperative multitasking (no preemption), not from events, so cooperative thread systems get the same benefit.

The invariant. Under cooperative scheduling a task gives up the CPU only at a yield or blocking point. So any stretch of code with no such point, one edge of the blocking graph, runs without any other task interleaving, and it is atomic with respect to every other task. An event handler body is such a stretch by construction. In a cooperative thread, the stretch between two blocking calls is too.

Conditions it depends on, and what breaks.

  • One processor. The paper is explicit: in either regime, cooperative multitasking provides free synchronization only on uniprocessors, "whereas many high-concurrency servers run on multiprocessors". On two CPUs, two tasks run truly at once and shared data needs locks or partitioning. Section 4.3 points to compiler techniques (M10).
  • Known yield points (inference, a point Adya et al. make). The atomicity holds only if the programmer knows which calls can yield. If a callee is changed so that it blocks, every caller's atomic stretch silently splits in two, with no visible change at the call site.
  • No preemption at all (inference). A long computation is never interrupted, so it stalls every other task; and a signal handler that touches shared state breaks the invariant.

Multiprocessors without locks. The paper cites libasync's hand-coded graph-coloring technique: callbacks are given colors, callbacks of the same color never run concurrently, and callbacks of different colors may run in parallel. In §4.3 the authors propose that a compiler infer which atomic sections are safe to run concurrently and pass that to the runtime, "thus automating the hand-coded graph coloring technique used in libasync".

M9 · Scheduling: application-level policy in a thread package

The criticism. Threads give each task a "virtual processor", which forces the runtime to be generic and keeps it from making optimal decisions. Event systems schedule event deliveries at application level, so the application can use shortest-remaining-completion-time scheduling, favor certain request streams, or improve code locality by running several events of the same kind in a row (the paper cites cohort scheduling, Larus and Parkes).

The rebuttal. One sentence: Lauer–Needham duality "indicates that we can apply the same scheduling tricks to cooperatively scheduled threads."

How that works (this guide's reading). An event scheduler's decision is "which ready event's handler runs next". The dual decision in a thread scheduler is "which ready thread resumes next". Every ready thread is parked at a known node of the blocking graph (a known blocking call), so a user-level scheduler that records where each thread is parked has the same information an event loop has. Cohort-style locality becomes: group ready threads by the call they are parked in and resume a batch of the same kind together. Favoring a request stream becomes a priority on threads serving that stream. What the trick needs is a user-level scheduler the application can influence; a kernel scheduler that only sees opaque threads cannot do it.

Evidence in the paper. The Knot-A / Knot-C pair (M12) is exactly an application-level scheduling policy implemented inside a thread package, and it changes the results visibly. In the related-work section the authors also agree with SEDA that a thread system's queues should be visible, because that enables better debugging and scheduling.

M10 · Compiler support for threads (§4)

The section's premise: "Tighter integration between compilers and runtime systems is an extremely powerful concept for systems design." Thread programs expose an ordinary call graph to the compiler; event programs hide their control flow in run-time dispatch (the next handler is a value, not a call site). The paper proposes three uses.

4.1 Dynamic stack growth ("We are developing a mechanism", so not yet built). A compiler analysis gives an upper bound on the stack space needed when calling each function, and determines which call sites may require stack growth. Recursive functions and function pointers "produce additional challenges, but these problems can be addressed with further analyses." The point is to escape the fixed-size tradeoff: start each thread small and grow only where needed.

// bound(f) = frame(f) + max over callees g of bound(g)      (acyclic part of the call graph)
// at each call site f → g, decide statically:
if bound(g) <= space already guaranteed at this point:
    no check                              // the common case, zero run-time cost
else:
    insert:  if (sp - bound(g) < limit) grow_stack();
// recursion: bound(g) is unbounded  → check at the recursive call (this guide's reading)
// function pointer: callee unknown → check before the call, or analyze the possible targets

The paper does not say how growth itself is done. Its related-work section cites Bruggeman et al.'s dynamically linked stacks, where a new stack chunk is linked in when one runs out (background: that is how the group's follow-on system, Capriccio, grew stacks). The invariant to keep: a thread never runs past the end of its current chunk, because every call site that might do so has a check in front of it.

4.2 Live state management. Event programmers keep live state small because they must copy it by hand; thread programmers get it saved automatically and "can be wasteful". The compiler could purge unnecessary state from the stack before function calls: pop temporaries before subroutine calls; pop the whole frame on a tail call; reorder variables with overlapping lifetimes, or move them off the stack, so that live variables do not "unnecessarily pin dead ones in memory"; and warn the programmer when a large amount of state is held across a blocking call. The reason it matters: while a thread is blocked, every frame on its stack is retained, so an 8 KB dead buffer sitting below a live integer stays in memory for the whole wait.

4.3 Synchronization. Compile-time analysis can warn about data races. Static race detection is hard, but the paper cites progress from compiler improvements and tractable whole-program analyses. The model is nesC, the language for TinyOS sensor networks: it supports atomic sections, and its compiler understands the concurrency model. TinyOS mixes events with run-to-completion threads; the compiler uses a variant of the call graph similar to the blocking graph and ensures every atomic section resides within one edge, so calls inside an atomic section cannot yield or block, even indirectly. The analysis can also determine which atomic sections are safe to run concurrently and give that to the runtime for safe execution on multiprocessors, automating libasync's hand-coded graph coloring.

What each proposal relies on. All three need the whole call graph (whole-program analysis, or summaries for libraries). Indirect calls and recursion weaken the stack bound; separately compiled libraries without summaries weaken the race and yield analysis (inference). In the paper, none of the three was built or measured at the time of writing.

M11 · The cooperative user-level thread package under Knot (§5)

What the paper states. A "simple (5000 line) user-level cooperative threading package for Linux". It uses the coro coroutine library for "minimalist context switching". It translates blocking I/O requests to asynchronous requests internally. Asynchronous socket I/O uses the UNIX poll() system call; asynchronous disk I/O is provided by a thread pool that performs blocking I/O operations. The library overrides blocking system calls and provides a simple emulation of pthreads, so applications written for it also compile unmodified against standard pthreads. This is a different package from the modified GNU Pth used for Figure 2.

A blocking read, step by step (this guide's reading of "translates blocking I/O requests to asynchronous requests"; the paper gives no code):

ssize_t read(int fd, void *b, size_t n):        // overridden system call
    loop:
        r = sys_read_nonblocking(fd, b, n)
        if r != EAGAIN: return r                  // data was there: no switch at all
        current.waiting_on = (fd, READABLE)       // record what this thread waits for
        poll_set.add(fd)
        schedule()                                // coro switch to another ready thread

schedule():
    if run_queue.empty():
        ready = poll(poll_set)                    // cost grows with |poll_set| (M13)
        for fd in ready: run_queue.push(waiter[fd])
        for done in disk_pool.completions(): run_queue.push(done.thread)
    next = run_queue.pop()                        // policy hook: Knot-A vs Knot-C (M12)
    coro_switch(current, next)                    // user level: no kernel crossing

file read: hand (fd, buf) to a helper kernel thread that calls blocking read();
           mark the caller waiting; the helper posts a completion when done

The key observation. Under the thread API sits an event loop: schedule() is poll() plus dispatch. The package is the duality made concrete. The programmer writes blocking, call/return code with automatic stacks; the runtime turns every blocking point into "register interest, switch away", which is exactly what an event programmer writes by hand.

Invariants. Exactly one user thread runs at a time. A switch happens only inside a library call (an overridden blocking call or an explicit yield). Each thread owns a stack plus a saved context.

Assumptions, and what breaks if each changes (inference unless noted):

  • Every blocking operation goes through the library. A system call the library does not override, a blocking call inside a third-party library, or a page fault blocks the underlying kernel thread, and with it every user thread.
  • No thread computes for long. With no preemption, a long CPU-bound request delays every other connection.
  • One CPU runs the user threads. The cooperative atomicity of M8 depends on it. The paper does not say how, or whether, Knot used the test machine's second Xeon.
  • poll() is the readiness mechanism. Each call passes the whole descriptor set to the kernel, which checks each one, so the cost of one call is O(descriptors). The paper notes that Linux's newer sys_epoll, where interest is registered once and only ready descriptors are returned, "avoids this problem and achieves excellent scalability" for Knot (M13).

M12 · Knot, Haboob, the test setup, and the two Knot policies

Knot. A 700-line test web server written on the package of M11. The paper does not spell out its threading structure; one thread per connection is the natural reading of "favors processing of active connections" and is assumed in this guide's figures. It serves static data requests, allows persistent connections (a client can send many requests on one connection), and includes a basic page cache. The authors say it is written in a clear, straightforward threaded style and "required very little performance tuning".

Haboob. SEDA's event-driven web server, run with the test suite used to evaluate SEDA. The original Haboob tests used a /dev/poll patch that had since been deprecated, so here Haboob used standard UNIX poll(), as Knot does. Haboob ran on IBM's 1.4 JVM with the JIT enabled.

Machine and workload. A 2 × 2000 MHz Xeon SMP with 1 GB of RAM running Linux 2.4.20. The workload is small, so there is little disk activity: the test exercises the network path, the page cache and the server's CPU costs, not disk I/O.

The two scheduling policies. The paper tested two policies for Knot:

  • Knot-C favors processing of active connections over accepting new ones. The paper: it "provides a natural throttling mechanism by limiting the number of new connections when the server is saturated with requests."
  • Knot-A does the reverse, favoring accepting new connections. It "was designed to create higher internal concurrency, and it more closely matches the policy used by Haboob."

The paper gives one sentence per policy and no code. A sketch of where the policy sits (this guide's reading):

// the scheduler's choice each time it gets control
pick_next():
    if policy == KNOT_C:
        if !run_queue.empty(): return run_queue.pop()   // finish work already admitted
        if listen_backlog.ready(): return acceptor          // admit only when nothing else can run
    if policy == KNOT_A:
        if listen_backlog.ready(): return acceptor          // admit first
        if !run_queue.empty(): return run_queue.pop()
    poll_and_refill()                                       // M11 step 4

Where the excess clients wait (inference). A client whose connection the kernel has completed but the server has not yet accepted sits in the kernel's listen backlog. It has no Knot thread, no stack, no buffers, and no entry in Knot's poll() set. Under Knot-C, at saturation, most excess clients stay there. Under Knot-A every pending connection is pulled in at once, so the number of connections the server holds, and polls over, rises with the number of clients. Phase 2, saturation. "When the server is saturated, the bandwidth levels out." From here the three lines separate.

  • Knot-C rises to ≈780 Mbit/s at 1,024 clients, ≈740 at 2,048, then holds at ≈670 to 690 all the way to 65,536. The paper: the steady state is "nearly 700 Mbit/s", where "the server is apparently limited by interrupt processing overhead in the kernel." The spike around 1,024 clients is "due to lower interrupt overhead when fewer connections to the server are being created" (the authors' stated belief, not a measurement).
  • Knot-A reaches the highest point on the graph, ≈815 at 1,024, then zig-zags (≈660 at 2,048, ≈750 at 4,096) and falls steadily: ≈625 at 8,192, ≈510 at 16,384, ≈330 at 32,768, ≈175 at 65,536. The paper's explanation: "The performance degradation for both Knot-A and Haboob is due to the poor scalability of poll()." Using sys_epoll with Knot avoids the problem, but the figure uses the poll() result for comparison because sys_epoll was incompatible with Haboob's socket library.
  • Haboob peaks at ≈495 Mbit/s (the paper says a maximum of 500) at around 512 to 1,024 clients and is "CPU limited at 512 clients". It then declines slowly, to ≈390 by about 104 clients, and its last plotted point, near 16,384, is below 200. Beyond that it ran out of memory.

Why Knot-A falls and Knot-C does not. Both use the same package and the same poll(); only admission differs. Each poll() costs time proportional to the number of descriptors passed in (M11). Knot-A pulls every pending connection in, so that number rises with the client count, and more CPU goes to scanning descriptors per unit of useful work. Knot-C, at saturation, keeps the excess in the kernel backlog, so the server's descriptor set, and the per-call poll() cost, stays roughly bounded (inference built on the Knot-C / Knot-A figure in M12). The paper's conclusion from the whole figure: Knot and Haboob show "the same general performance pattern", and "a well-designed thread package can achieve the same scaling behavior as a well-designed event system."

Why Haboob's maximum is lower (the paper's four reasons). Haboob becomes CPU-limited at 512 clients, well below Knot's peak:

  1. Context switches. Haboob's thread-pool-per-handler model requires a context switch whenever an event passes from one handler to another: 30,000 switches per second when fully loaded, "more than 6 times as frequently as Knot".
  2. Module crossings and queuing. The proliferation of small modules in Haboob and SEDA ("a natural outgrowth of the event programming model") creates many module crossings and queuing operations.
  3. Temporary objects and garbage collection. Haboob creates many temporary objects and relies heavily on GC.
  4. Run-time dispatch. The next handler is not known statically, so dispatch is dynamic. This relates to ambiguous control flow, which costs performance by reducing compiler optimization opportunities and increasing CPU pipeline stalls.

The paper says the first three challenges "seem deeply tied to the event model", while Knot's simpler threaded style avoids them. Note that it does not attribute them to Haboob's implementation choices; that is the authors' point.

What Figure 3 shows, and what it does not. It shows a simple threaded server matching the scaling shape of a mature event server, with Knot-C's steady state (nearly 700 Mbit/s) about 40% above Haboob's maximum (500 Mbit/s). It does not show:

  • the sys_epoll results the authors mention but do not plot;
  • latency or per-client fairness (only aggregate bandwidth; under Knot-C, clients waiting in the backlog get nothing until admitted, inference);
  • the language effect separately: Haboob is Java under a JIT with GC, Knot is C, so some of the gap may be language and runtime rather than events vs. threads (the third and fourth reasons partly concede this);
  • the Figure 2 package: Figure 3 uses the authors' own coro-based package, not the modified Pth;
  • disk-bound or dynamic-content workloads (the workload is small and static).

Also note that Knot-A collapses as badly as Haboob at high client counts in this figure. The win at 65,536 clients belongs to the Knot-C policy, not to threads by themselves.

M14 · Related systems and where each paper stands (§6)

  • Ousterhout (1996 talk). The best-known case for events, but "his arguments do not conflict with ours": programming with concurrency is fundamentally hard, so cooperatively scheduled events are preferable for most purposes because they let programmers avoid concurrent code. He explicitly supports threads for true concurrency, which is this paper's target space. The authors agree cooperative scheduling simplifies concurrency but argue it is better used inside the simpler thread programming model.
  • Adya et al. (2002). "Cover a subset of these issues better than we have": they identify the value of cooperative scheduling for threads and define stack ripping. This paper adds thread performance and compiler support.
  • SEDA. A hybrid: events between stages, threads within them. Close to Lauer and Needham's message-passing model, although Lauer and Needham advocate a single thread per stage, to avoid synchronization within a stage. SEDA showed the value of keeping a server in its operating range by using explicit queues; the authors agree that the various queues for threads should be visible, for debugging and scheduling. Stage boundaries give modularity that simplifies composing pipelines; but for call/return patterns those boundaries require stack ripping, and are better implemented with threads using blocking calls.
  • Prior techniques the package draws on. Filaments and NT's Fibers are cooperative user-level thread packages, but neither targets large numbers of blocking threads. Erlang and Concurrent ML have direct language support for concurrency and lightweight threads. Bruggeman et al. use dynamically linked stacks to implement one-shot continuations, which can be used to build user-level thread packages. The authors' stated contribution is bringing these techniques together in one package for a broader community.
🎓
From the lecture (10/1). Context for the three papers: Ousterhout's was a provocative invited keynote from someone building window systems, where events fit mouse, keyboard and packet input well, at a time when most machines had one processor. This paper came from Berkeley researchers who had built several high-performance event systems; HotOS takes position papers, which explains the few references. Asked whether the other papers agree with Ousterhout's carve-out (threads for CPU-bound, multiprocessor work such as scientific computing), the class answer was that this paper agrees threads are needed there, but argues that for servers, where most people used events, threads gave more performance and simpler code. Where things went: JavaScript is all in on events (browser and Node.js) and added closures and promises to make that bearable; Python has threads but a global interpreter lock, so parallelism comes from the shared-nothing multiprocessing library or from C++ libraries underneath; Go makes threads cheap and steers you toward channels instead of locks.
🔗
Connections across CS240, in one place. Mesa: Figure 1's thread column is Mesa's model (monitors, condition variables, FORK/JOIN); Mesa protects atomic regions with monitor locks where a cooperative package relies on having no yields (M2, M8). Eraser: a lockset checker assumes locks; a cooperative thread program has none, and nesC-style compile-time checking is the static alternative (M8, M10). Livelock: admission vs. completion priority under overload, the Knot-A / Knot-C question (M12). Adya et al.: stack ripping, and the task-management / stack-management split (M7). Ousterhout: agrees on cooperative scheduling, disagrees on the programming model for servers (M14). Memory papers: a thread's memory cost is its touched stack pages, which is what dynamic stack growth targets (M1, M10).

Follow the numbers, step by step

Worked examples

Four passes through the paper's actual figures and claims.

① Reading Figure 3: how much does Knot actually win by?

Knot-C's steady-state bandwidth is ~700 Mbit/s; Haboob's peak is ~500 Mbit/s. Quantify the gap, and note the two different ways Haboob fails.

  1. Relative bandwidth gap: (700 − 500) / 500 = +40% — Knot-C sustains 40% more throughput than Haboob's best.
  2. Failure mode #1 — CPU-bound: Haboob's bandwidth stops climbing at just 512 clients; adding more clients after that buys nothing because the CPU, not the network, is the bottleneck.
  3. Failure mode #2 — memory-bound: separately, Haboob can't even be run past 16,384 simultaneous clients — it runs out of memory outright, a harder ceiling than the CPU limit.
  4. Knot-C hits neither wall in the tested range: it holds ≈670 to 690 Mbit/s out to 65,536 clients. Knot-A does degrade, from a peak of ≈815 Mbit/s at 1,024 clients to ≈175 at 65,536, which the paper attributes (with Haboob's decline) to the poor scalability of poll().
🍯
Insight: "40% faster" undersells it: Haboob has a performance ceiling and a much lower scalability ceiling. For the CPU ceiling the paper gives four reasons (context switches between handler thread pools, module crossings and queuing, temporary objects and GC, run-time dispatch) and says the first three "seem deeply tied to the event model". It does not explain the out-of-memory limit. The high-client decline it attributes to poll(), which hurts Knot-A just as much.

② Backing out Knot's context-switch rate

The paper states Haboob context-switches 30,000 times/second under full load — "more than 6 times as frequently as Knot." What's Knot's rate, and why the difference?

  1. Solve for Knot's rate: 30,000 ÷ 6 ≈ 5,000 context switches/second (an upper bound consistent with "more than 6×").
  2. Why Haboob switches so much: its thread-pool-per-handler model means every time an event passes from one stage to another, control may hand off to a different thread — one switch per stage boundary crossed.
  3. Why Knot switches so little (inference; the paper only gives the ratio): a single thread runs a request from accept to response, so most of a request's lifetime needs zero switches; only genuine blocking points (e.g. a real I/O wait) trigger one.
  4. Connect it back: this is the "assembly-line toll" from the SEDA analogy — Haboob's stage boundaries are real conveyor trips, and conveyor trips cost context switches.

③ Applying the duality table to one request

Trace "read a request, then write a response" through both columns of Figure 1.

  1. Threaded version: a thread calls read_request() (procedure call), which blocks on a condition variable while data arrives, then returns the parsed request.
  2. Event version: the requester issues SendMessage(read_request) and then AwaitReply; the module serving the read waits for a "data arrived" message, then issues SendReply with the parsed request, and that reply completes the requester's AwaitReply.
  3. Map term-for-term: "waiting on condition variables" ↔ "waiting for messages"; "procedure call" ↔ "SendMessage/AwaitReply"; "return" ↔ "SendReply."
  4. The only real difference is who tracks "what happens after the reply" — the call stack (threads) or a manually-saved continuation (events, i.e. stack ripping).
💡
This is literally Lauer–Needham's Figure 1 mapping, applied — every event-based idiom in a real server has a thread-shaped twin, and vice versa.

④ How small is "small" — code size as evidence

The authors built a ~5,000-line user-level thread package and, on top of it, a 700-line web server that beats a mature, heavily-engineered event system. What does that ratio suggest?

  1. 5,000 lines buys a general-purpose, scalable, blocking-I/O-emulating thread runtime — a one-time cost, reusable by any application.
  2. 700 lines is then enough for a complete web server: static requests, persistent connections, a page cache — "written in a clear, straightforward threaded style," per the authors, with "very little performance tuning."
  3. Compare to events: SEDA/Haboob-style systems need explicit stages, queues, and handler wiring for the same functionality — the paper attributes part of Haboob's overhead to "the proliferation of small modules... a natural outgrowth of the event programming model."
  4. Takeaway: the simplicity isn't just aesthetic — fewer moving parts (no stage/queue plumbing) is also fewer places for context switches and GC pressure to hide.
Test yourself

Practice problems

Try each before opening the answer — every one names the misconception it's checking.

Problem 1 · easy
Event systems claim "free" synchronization from cooperative multitasking. Does a cooperative thread system get the same benefit? Does it hold on a multiprocessor?
Show answer
Yes to the first — the free synchronization comes from not being preempted between yield points, which is a property of cooperative scheduling, available to threads and events alike (Adya et al.'s insight, cited in §2.2). No to the second — on a multiprocessor, another core can run concurrently regardless of cooperative scheduling on this core, so both paradigms need real synchronization there.Misconception: that "free" synchronization is an event-specific feature. It's a uniprocessor, cooperative-scheduling feature, full stop.
Problem 2 · medium
Haboob context-switches 30,000 times/second, "more than 6 times as frequently as Knot." What is Knot's approximate context-switch rate, and what causes the difference?
Show answer
30,000 ÷ 6 ≈ 5,000/second, and since the ratio is "more than 6", Knot's rate is below that. Haboob's thread-pool-per-handler model context-switches whenever an event crosses a stage boundary; Knot's single thread per request only switches at genuine blocking points, so most of a request needs none.Misconception: that context switches are an unavoidable "threads tax." Here it's the opposite; the threaded server switches less, because it doesn't hand work between stages.
Problem 3 · medium
Define "stack ripping" (Adya et al.'s term) in your own words, and explain why it's a burden even for a careful, disciplined programmer.
Show answer
Stack ripping is the manual work of saving live state before a blocking call in an event handler (since it has no stack to preserve it) and restoring that state in whichever handler processes the reply. It's a burden regardless of discipline because it requires matching call/return pairs mentally, often across different parts of the codebase, and manually managing when that heap-allocated state is safe to free.Misconception: that stack ripping is just an unfamiliarity/style issue programmers get used to. The paper argues it's a structural cost independent of skill — threads simply don't require it.
Problem 4 · hard
Under Lauer–Needham duality, if a real thread system and a real event system perform differently, what does the paper conclude is the cause — and what would not count as a counterexample to the duality claim?
Show answer
The paper concludes the difference is due to implementation quality, not the abstraction — duality only guarantees equal performance for "equally good implementations." A single threaded system performing worse than a single event system is not a counterexample; it just means that particular thread runtime wasn't engineered as carefully (e.g., it still has O(n) scheduler operations).Misconception: that any observed performance gap disproves duality. Duality is a claim about idealized, well-engineered systems — real-world gaps are evidence about engineering effort, not about the theory.
Problem 5 · medium
Why do event systems typically heap-allocate per-task state, and what two mechanisms does the paper mention for cleaning it up — with what real-world cost for each?
Show answer
Event handlers unwind the stack after each callback, so nothing survives across a blocking point unless it's put on the heap by hand. Cleanup mechanisms: (1) garbage collection (Ninja, SEDA/Haboob use Java's) — the paper cites prior work finding general-purpose GC inappropriate for high-performance systems; (2) reference counting (Inktomi's Traffic Server) — correctness is hard to maintain, and the paper notes nearly every release battled slow memory leaks from it.Misconception: that heap allocation is a minor detail. The paper treats it as a root cause of two classes of real production bugs/overhead.
Problem 6 · hard
The paper says removing O(n)-in-thread-count operations from GNU Pth let it scale to 100,000 threads. Why would such operations exist in a thread scheduler in the first place, and why does removing them fix scalability rather than just delaying the problem?
Show answer
A naive scheduler might scan every thread to find a runnable one, or walk a linear list for bookkeeping (e.g., timers, priority updates) — simple to implement, and fine at small scale. Removing them (e.g., switching to O(1) or O(log n) data structures for the ready queue) fixes scalability fundamentally, rather than delaying it, because the cost per operation stops growing with thread count — at 100,000 threads the difference between O(n) and O(1) per operation is the difference between usable and unusable.Misconception: that "optimizing" a thread scheduler just buys you a bit more headroom. Removing an O(n) operation is a qualitative fix, not an incremental one — it changes the scaling curve's shape, not just its constant.
Problem 7 · medium
The paper says "arguably one of SEDA's contributions was to return event-driven systems to the 'good practices' of Lauer-Needham." What does that mean, given that most event systems don't match Lauer-Needham's canonical model?
Show answer
Most event systems use shared memory and global data structures, unlike Lauer and Needham's canonical message-passing systems, which pass messages through explicit channels with no shared state. SEDA's stages-and-queues architecture is the one event system the paper says does match that canonical model exactly — stages as processes, queues as message ports — so SEDA is, structurally, closer to the original 1978 idea than the event systems that came between.Misconception: that all "event-driven" systems are structurally similar. The paper treats SEDA as a special, more disciplined case, not representative of event systems generally.
Problem 8 · easy
The paper examined Flash, Ninja, SEDA, and TinyOS code and found only three control-flow patterns in practice. Name them, and explain why this undercuts the "events allow more flexible control flow" argument.
Show answer
Call/return, parallel calls, and pipelines. It undercuts the flexibility argument because all three map naturally onto threads (ordinary function calls, fork/join, and sequential stages respectively) — so the theoretical extra flexibility events offer (arbitrary fan-in/fan-out messaging) isn't actually exercised by real high-concurrency server code, except in rare multicast/publish-subscribe cases the studied systems didn't use.Misconception: that events' more general messaging model is a practical advantage. In the systems studied, it's an unused capability — real code sticks to patterns threads handle just as well.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Is this paper saying threads are always better than events?▾
Not quite — it says threads are at least as good for the specific case of high-concurrency servers with largely-independent requests and mostly-sequential per-request code, given a well-engineered runtime. The paper explicitly notes events remain more natural for dynamic fan-in/fan-out patterns (multicast, publish/subscribe) — patterns the servers they studied didn't actually use.
Q2What is Lauer–Needham duality, in one sentence?▾
A 1978 result showing that well-implemented thread systems and well-implemented message-passing (event) systems are structurally equivalent — every concept in one maps onto a concept in the other — so with equally good implementations, they should perform the same.
Q3What's "stack ripping" and why does it matter?▾
It's Adya et al.'s term for manually saving and restoring a task's live state across event-handler callback boundaries, since there's no call stack to do it automatically. It matters because it's the concrete, everyday cost event programmers pay that thread programmers simply don't.
Q4How did the authors prove threads can scale to 100,000?▾
They took GNU Pth, an existing user-level thread package, and removed operations that scanned or updated state in time proportional to the number of threads (O(n) operations). The result matched an event-based server's throughput up to 100,000 concurrent threads (Figure 2).
Q5What is Knot, and how does it compare to Haboob?▾
Knot is the authors' 700-line threaded test web server, built on their ~5,000-line thread package. Against SEDA's event-driven Haboob, Knot reaches ~700 Mbit/s vs. Haboob's ~500 Mbit/s peak; Haboob becomes CPU-limited at 512 clients and runs out of memory beyond 16,384 clients, while Knot was tested up to 65,536.
Q6Why does Haboob context-switch so much more than Knot?▾
Haboob's thread-pool-per-handler design context-switches whenever an event moves from one stage to another — 30,000 times/second at full load, over 6× Knot's rate — because Knot runs each request start-to-finish on one thread with minimal hand-offs.
Q7Does cooperative scheduling's "free synchronization" really come from events?▾
No — the paper (citing Adya et al.) attributes it to cooperative (non-preemptive) scheduling itself, which cooperative thread systems can equally exploit. It's also strictly a uniprocessor benefit; multiprocessors need real synchronization either way.
Q8What compiler support does the paper propose for threads?▾
Three things: dynamic stack growth (compiler-computed, per-call-site stack bounds, growing stacks on demand instead of fixed-sizing them); live-state pruning (popping dead temporaries before calls, warning about large state held across blocking calls); and static synchronization checking, modeled on nesC/TinyOS's atomic-section analysis.
Q9Did the authors' own earlier systems use events?▾
Yes — Ninja, SEDA, and Inktomi's Traffic Server, all built with heavy event-driven design. Their experience building these is exactly what led them to conclude events were the wrong choice — including that Ninja fell back to threads for its hardest parts (recovery) because getting them right with events was nearly impossible.
Q10How does this paper relate to Ousterhout's "Why Threads Are A Bad Idea"?▾
This paper's title directly echoes Ousterhout's 1996 talk, but the authors say their arguments don't actually conflict: Ousterhout argued cooperative events help programmers avoid concurrent code in cases that don't need true concurrency, and explicitly supported threads where true concurrency (their target: high-concurrency servers) is required.
Beyond this paper

Connections to modern OS & memory-systems design

Four short bridges from this 2003 debate to problems you're working on now.

🔀 io_uring echoes the same diagnosis

The paper argues events won mainly by avoiding expensive blocking syscalls and kernel crossings — an implementation cost, not a fundamental one. io_uring makes the same bet two decades later: it's an async submission/completion-ring interface that batches away exactly that kernel-crossing overhead — though it's still an asynchronous interface, not blocking-looking code, and it takes a runtime wrapped around it (not io_uring itself) to give application code back an ordinary call/return feel.

🧵 Green threads made a comeback

Capriccio-style user-level M:N threading, scaling to 100,000 threads by fixing scheduler data structures, is a conceptual forerunner — not a direct ancestor — of Go's goroutines and Java's virtual threads (Loom): both later bet, independently, that decoupling "logical concurrency unit" from "OS-scheduled entity" was the real fix, echoing this paper's argument rather than a switch to callback-based dispatch.

📍 The blocking graph is a policy-instrumentation problem, like page-access tracking

This paper's blocking graph tries to find the right granularity of "significant events" to instrument cheaply — every yield point, no more. OS-managed memory tiering faces the same design question: PTE access/dirty bits, hardware hotness counters, and periodic NUMA-balancing scans are all attempts to sample "significant events" (accesses) cheaply enough to drive page-placement decisions without instrumenting every load.

🛠 Compiler-assisted resource management, echoed in kernel-managed tiering

Section 4's pitch — let the compiler bound stacks and prune live state instead of making programmers do it by hand — is the same design instinct behind pushing page-placement policy into the kernel (automatic NUMA balancing, TPP-style hot/cold classification) rather than requiring every application to hand-tune numactl or manual tiering hints.

🍯
The recurring lesson — blame the implementation before the abstraction, and give the runtime/compiler good primitives instead of pushing policy into hand-rolled application logic — is exactly the bet behind OS-managed DRAM/CXL/NVM tiering over application-directed placement.
