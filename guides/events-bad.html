HotOS IX · 2003 · A Field Guide

Giving concurrency to whoever's easiest to reason about, not whoever's fashionable this decade

Events won the "high concurrency" argument in the late '90s. This paper's authors — who helped build several event systems — changed their minds. Here's their case for threads, in plain English.

📄 "Why Events Are A Bad Idea" · von Behren, Condit & Brewer 🎓 Grad-level OS/concurrency background assumed — primers cover the rest ⏱ ~25 min read

Before you begin

What you need going in

A TL;DR, a quick glossary of proper nouns, and ten prerequisite ideas — collapsed by default, open whichever you need.

⚡ TL;DR

  • Threads and events are Lauer–Needham duals — structurally equivalent — so a good thread runtime (fixing O(n) scheduler operations and context-switch cost) can match every strength claimed for events, while keeping ordinary call/return control flow.
  • An optimized GNU Pth thread package scales flat to 100,000 concurrent tasks in a synthetic SEDA benchmark, matching event-driven throughput; separately, the authors' 700-line threaded web server Knot (on a ~5,000-line thread package) hits ~700 Mbit/s, tested up to 65,536 clients — beating SEDA's event-driven Haboob (~500 Mbit/s peak, CPU-limited at 512 clients, 6× the context switches, out of memory past 16,384 clients).
  • It matters because the "threads vs. events" fight is really "who owns the concurrency policy — the runtime or the application" — the same question that recurs in scheduler design, and in deciding whether the OS or the application should drive resource placement.

1Threads vs. coroutines vs. processes▾

A thread is a unit of sequential execution with its own call stack, sharing memory with other threads in the same process. A coroutine is similar but only switches when it explicitly yields (cooperative, not preemptive). A process has its own address space too, which is heavier still.

This paper's thread package is user-level and cooperative — closer to coroutines than to kernel (preemptive, OS-scheduled) threads.

Now you're ready: when the paper says "threads," it usually means this lightweight, cooperatively-scheduled, user-level flavor — not the heavyweight kernel threads that gave threads a bad name.
2Blocking I/O vs. event loops (select/poll/epoll)▾

A blocking call (e.g. read()) suspends the whole thread until data arrives. An event loop instead calls select()/poll()/epoll() to ask "which of these many sockets are ready?" and dispatches a small handler for each — one thread serving thousands of connections without blocking any of them.

This is the mechanical reason events scaled where naive one-thread-per-connection servers didn't: not blocking meant not needing thousands of OS threads.

Now you're ready: the paper's whole point is that a good thread runtime can hide blocking calls behind the same non-blocking machinery, so you get the scalability without giving up call/return code.
3Context switches, and why they cost anything▾

Switching from running one thread to running another means saving one set of registers/state and loading another — and, for kernel threads, often a trip through the OS (a kernel crossing). That's real, measurable overhead, especially under preemption.

User-level cooperative threads can switch far more cheaply, since there's no kernel crossing and no preemption to guard against — the paper attributes the low cost to avoiding these, plus using a lightweight primitive (coro) for the actual switch.

Now you're ready: "threads are slow because of context switches" is exactly the claim this paper disputes — it's a property of specific implementations, not of the thread abstraction.
4Stacks: automatic state, at a size cost▾

Every thread's local variables and call history live on its stack. Stacks are usually fixed-size, so you must pick a size big enough to avoid overflow but small enough not to waste address space — awkward when you have 100,000 threads.

Event systems dodge this by keeping few threads (often one) and storing per-task state on the heap by hand instead.

Now you're ready: this tradeoff motivates the paper's proposed fix — compiler-assisted dynamic stack growth (Section 4.1) — one of its concrete "give threads compiler help" proposals.
5Callbacks and continuations▾

In an event system, instead of calling a function and waiting for its return, you register a callback to run later, when a reply arrives. Chained callbacks are a crude form of continuation — "what to do next" captured as data instead of as a suspended call stack.

The catch: whatever variables the original caller needed are no longer sitting on a stack — the programmer must package them up by hand and pass them along.

Now you're ready: this manual packaging is exactly "stack ripping" — the paper's central complaint about event-driven programming style.
6User-level (M:N) vs. kernel (1:1) threading▾

1:1 threading maps each thread straight to a kernel thread — simple, but every blocking call and context switch may cross into the kernel. M:N threading multiplexes many user-level threads onto few kernel threads, letting a runtime schedule cheaply in userspace and only cross into the kernel when it truly must (e.g., for actual blocking I/O).

Now you're ready: the paper's thread package is this kind of user-level, cooperatively-scheduled package (the paper itself just calls it a "user-level thread package," without using the M:N label) — that's what lets it get to 100,000 threads without 100,000 kernel-scheduled entities.
7Cooperative vs. preemptive scheduling▾

Preemptive scheduling can interrupt a thread anywhere, anytime — safe in general, but means any two lines of code might race, so you need locks around shared state. Cooperative scheduling only switches at explicit yield points (like a blocking call) — so code between yield points is automatically atomic, with no locks needed on a single core.

Now you're ready: event systems' "free synchronization" comes from being cooperative, not from being event-driven — and cooperative thread systems get the same benefit (Section 2.2, citing Adya et al.).
8Why "O(n) in the number of threads" is a red flag▾

A naive thread scheduler might scan every thread to find one that's runnable, or walk every thread's data structure on some housekeeping operation. That scan takes time proportional to the thread count — fine at 10 threads, ruinous at 100,000.

Now you're ready: removing exactly these O(n) operations from GNU Pth is what let the paper's optimized thread package scale to 100,000 threads (Figure 2) — the fix was a data-structure change, not a paradigm change.
9Reference counting and garbage collection, briefly▾

Event systems typically heap-allocate per-task state (since there's no stack to hold it), so something must eventually free it. Reference counting tracks how many places point to an object and frees it at zero — simple in principle, easy to get wrong on error paths. Garbage collection (as in Java) automates this but adds pause times and CPU overhead.

Now you're ready: the paper blames both approaches for real bugs and overhead in event systems (Inktomi's reference-counting leaks; Haboob's GC pressure) — problems threads sidestep via the call stack.
10Call graphs and whole-program compiler analysis▾

A call graph maps which functions can call which. Compilers can walk it to compute bounds — e.g., "how much stack could this call chain ever use?" — as long as the graph is mostly static (recursion and function pointers make it harder).

Now you're ready: this is the machinery behind the paper's compiler-support proposals (Section 4) — bounding stack growth per call site, and nesC's atomic-section checking on a similar graph.
The whole story in one place

The argument in a nutshell

Why the authors — event-system builders themselves — switched sides.

By the late 1990s, the conventional wisdom was that events were the only way to build servers handling tens of thousands of concurrent connections: cheap cooperative synchronization, no wasted per-thread stacks, application-level scheduling, flexible control flow. Threads, by contrast, had a reputation for poor scalability and heavyweight context switches.

The authors revisit Lauer–Needham duality (1978): a thread system and a message-passing/event system built to the same design are structural mirror images — every event concept maps onto a thread concept (Figure 1 in the paper). If duals are equally well implemented, they must perform equivalently. So if event systems were winning, the paper argues, it wasn't because events are inherently better — it was because nobody had built a thread runtime engineered for this workload.

They prove it two ways. First, they take an existing thread package (GNU Pth), remove its O(n)-in-thread-count scheduler operations, and show it scales flat to 100,000 threads, matching an event server. Second, they build Knot, a 700-line threaded web server on a ~5,000-line user-level thread runtime, and show it out-performs SEDA's Haboob: ~700 Mbit/s vs. ~500 Mbit/s, with Haboob becoming CPU-bound at 512 clients and running out of memory beyond 16,384 clients.

The upshot: threads keep the natural call/return programming model — no stack ripping, no hand-rolled continuations — while matching or beating events on every axis events were claimed to win. The paper's forward-looking claim is that compilers, not just runtimes, are the next lever: bounding stacks, pruning dead state, and checking atomicity statically.

🍯 Key takeaways

  • Threads and events are Lauer–Needham duals — the same power, mapped onto different vocabulary.
  • The paper attributes most "problems with threads" it examines (performance, control flow, synchronization, scheduling) to implementation artifacts, not intrinsic to threads — though for stack/state management and multiprocessor synchronization, its fix is a proposed compiler/runtime enhancement, not something it demonstrates eliminated.
  • Cooperative scheduling — not "being event-based" — is what gives "free" synchronization; it works for cooperative threads too.
  • Stack ripping is the real cost event programmers pay for avoiding threads — manually saving/restoring state across callback boundaries.
  • A modified GNU Pth scales to 100,000 threads in a synthetic benchmark; separately, Knot (700 lines) beats Haboob 700 vs. ~500 Mbit/s, with Haboob CPU-bound at 512 clients and OOM past 16,384 (Knot tested to 65,536).
  • The paper's forward bet: compiler support for stacks, live-state pruning, and atomicity checking is the next real lever for thread systems.
Seven everyday pictures

How to think about the threads/events debate

Each stands alone; every card is honest about where it stops being true.

The core idea · Lauer–Needham duality

Two translations of the same play

A play performed in English and the same play performed in French use different words for every line, but they're the same play — same plot, same pacing, same emotional beats. Threads and events are like that: SendMessage/AwaitReply is French for "procedure call"; SendReply is French for "return." Stage a good production in either language and audiences should react the same way.

Where it breaks: a bad translation ruins the play without touching the plot. That's the paper's whole point — a bad thread implementation "mistranslates" the abstraction, and people blamed the play instead of the translator.
Formalizing the duality · Blocking graph

The trail map, not the trailhead sign

A hiking map marks every fork and rest stop, no matter which language the signs are printed in — the terrain is what matters. The paper's blocking graph does the same for a program: nodes are blocking/yielding points, edges are the code in between. Draw this graph for a thread program and its event dual, and — if both are well built — they're the same map.

Where it breaks: the map only shows blocking points, not everything that makes a real hike hard (weather, fatigue) — likewise the blocking graph abstracts away real costs like memory layout and cache behavior that can still differ between implementations.
Cooperative scheduling · "Free" synchronization

An unlocked door, because no one's forcing it

You can leave your office door unlocked all day if you trust that nobody will walk in mid-sentence and rearrange your desk. That's cooperative scheduling: code between yield points runs uninterrupted, so you don't need locks — not because you're using events, but because nothing preempts you. Cooperative threads get the same unlocked door.

Where it breaks: the moment a second person (a second CPU core) has their own key, "nobody walks in" stops being true — cooperative scheduling's free lunch is a uniprocessor phenomenon, on both sides of the duality.
Stack ripping · State management

A novel that erases your bookmark every chapter

Imagine reading a novel where, at every chapter break, someone rips out your bookmark and your margin notes — you must rewrite from memory what you were thinking, who the characters were, before continuing. That's an event handler at a callback boundary: no call stack survives the break, so the programmer manually re-packages every variable that needs to live on ("stack ripping," per Adya et al.).

Where it breaks: a disciplined reader can keep good notes; likewise disciplined event programmers manage this — but the paper's point is that threads don't require the discipline in the first place. It's an unforced cost.
Fixing performance · Removing O(n) scheduler ops

A coat-check that stops re-counting every coat

A coat-check clerk who re-counts every coat on the rack each time one more arrives gets slower as the party grows — not because coat-checking is slow, but because that clerk's method is. Swap in a clerk who just adds one ticket to a running tally, and the party can grow to thousands with no slowdown. That's what removing O(n)-in-thread-count scheduler operations from GNU Pth did — same job, smarter bookkeeping.

Where it breaks: some bookkeeping is genuinely proportional to load (you do have to store each coat somewhere) — the fix removes needless re-scanning, not all per-thread cost.
Compiler support · Dynamic stack growth

A hotel room sized to your actual luggage

Building every hotel room to fit the biggest suitcase anyone might ever bring wastes space for everyone else; building rooms too small risks turning guests away. A compiler that analyzes each call site's stack needs can size — and re-size — a thread's stack to what it actually uses, sidestepping the fixed-size stack's overflow-vs-waste tradeoff entirely.

Where it breaks: a hotel can't predict a guest who shows up with an unplanned trunk — likewise recursion and function pointers make worst-case stack bounds genuinely hard to compute statically, which the paper admits is unsolved.
SEDA's compromise · Threads within, events between

An assembly line with a crew at every station

SEDA is an assembly line: items (requests) ride a conveyor (queue) between stations (stages), but each station has its own small crew (thread pool) doing real work. It's a genuine hybrid — Lauer–Needham's message-passing model between stages, ordinary threading within them. The paper credits SEDA with returning event systems to this more disciplined structure.

Where it breaks: every hand-off between stations still costs a conveyor trip (a queue enqueue/dequeue and, per this paper, a context switch) — Haboob's measured 30,000 context switches/second is that toll adding up under load.
The full explanation

How the argument actually works

Section by section, with the paper's key structures rebuilt as diagrams.

1 · The duality table (Figure 1)

Lauer and Needham's 1978 mapping, in the paper's own terms — every event concept has a thread-shaped twin:

EventsThreads

events accepted by a handlerfunctions exported by a module
SendMessage / AwaitReplyprocedure call, or fork/join
SendReplyreturn from procedure

📎
Only SEDA really matches the canonical message-passing system Lauer and Needham described — its stages and queues map exactly onto their processes and message ports. Most other "event systems" bend the model with shared memory and global data structures.

2 · The blocking graph

To argue duals perform the same, the paper implicitly uses a blocking graph: nodes are blocking/yielding points, edges are the code executed between them. The duality claim: a well-built thread program and its well-built event dual trace the same graph.

3 · Rebutting each criticism of threads

Section 2.2 walks through five standard complaints and traces each to an implementation artifact:

CriticismPaper's rebuttal
Threads perform poorlyO(n)-in-thread-count scheduler ops + preemption overhead — fixable; optimized GNU Pth scales to 100,000 threads
Threads have restrictive control flowReal servers (Flash, Ninja, SEDA, TinyOS) use only 3 patterns: call/return, parallel calls, pipelines — all natural with threads
Thread synchronization is heavyweight"Free" sync comes from cooperative scheduling, not events (Adya et al.) — cooperative threads get it too, only on uniprocessors either way
Stacks manage state poorlyReal tradeoff (overflow vs. waste) — paper proposes compiler-assisted dynamic stack growth as future work, not yet a demonstrated fix
Threads can't do app-level schedulingDuality says the same scheduling tricks apply to cooperatively-scheduled threads

4 · Why threads fit servers specifically

Section 3 grounds the abstraction choice in two properties of real servers: requests are largely independent, and the code handling one request is usually sequential. Under these conditions, threads let call/return group cause and effect syntactically, and the call stack becomes free, automatic cleanup on both normal return and exceptions — exactly the case where event systems instead need hand-rolled reply matching and heap-based state teardown (stack ripping, plus the reference-counting bugs that plagued Inktomi's Traffic Server).

💡
Telling detail: even the paper's own event-based systems (Ninja, SEDA) fell back to threads for their most complex parts — like recovery logic — because getting it right with events proved nearly impossible.

5 · Compiler support (Section 4) — the forward-looking proposal

Having shown threads can match events today, the paper argues compilers are the next lever, since threads (unlike opaque event dispatch) expose a normal call graph for analysis:

// dynamic stack growth: compiler bounds stack need per call site
function handle_request():
    // compiler proves: ≤ 240 bytes live here
    buf = read_headers()      // may block; stack frame stays small
    if needs_more_stack(): grow_stack()   // only when a call site demands it
    parse(buf)
    // compiler pops dead temporaries before the next call
    write_response(buf)

Three concrete proposals: dynamic stack growth (bound per-call-site stack needs, grow on demand — hard for recursion/function pointers, but tractable for the common case); live-state pruning (pop dead temporaries before calls, warn on large state held across blocking calls); and static synchronization checking, modeled on nesC's atomic sections for TinyOS, which the compiler verifies never span a yield point.

6 · The evaluation (Section 5)

Two experiments carry the whole argument. Figure 2 repeats SEDA's own threaded-vs-event benchmark; a GNU-Pth-based server, once its O(n) scheduling operations are removed, scales flat to 100,000 threads, matching the event server. Figure 3 pits the authors' own Knot (700 lines, on a ~5,000-line thread runtime) against SEDA's Haboob, on identical hardware (2×2000 MHz Xeon SMP, 1 GB RAM, Linux 2.4.20), both using plain poll() for a fair comparison.

🍯
The numbers: Knot-C (favoring active connections) reaches ~700 Mbit/s; Haboob peaks at ~500 Mbit/s, becoming CPU-limited at 512 clients — with 30,000 context switches/second, over 6× Knot's rate — and running out of memory beyond 16,384 clients, while Knot keeps running to 65,536.
Follow the numbers, step by step

Worked examples

Four passes through the paper's actual figures and claims.

① Reading Figure 3: how much does Knot actually win by?

Knot-C's steady-state bandwidth is ~700 Mbit/s; Haboob's peak is ~500 Mbit/s. Quantify the gap, and note the two different ways Haboob fails.

  1. Relative bandwidth gap: (700 − 500) / 500 = +40% — Knot-C sustains 40% more throughput than Haboob's best.
  2. Failure mode #1 — CPU-bound: Haboob's bandwidth stops climbing at just 512 clients; adding more clients after that buys nothing because the CPU, not the network, is the bottleneck.
  3. Failure mode #2 — memory-bound: separately, Haboob can't even be run past 16,384 simultaneous clients — it runs out of memory outright, a harder ceiling than the CPU limit.
  4. Knot hits neither wall in the tested range — the benchmark continues to 65,536 clients for Knot.
🍯
Insight: "40% faster" undersells it — Haboob has a performance ceiling and a much lower scalability ceiling. The paper attributes both to implementation choices (thread-pool-per-handler context switching; garbage-collected temporary objects), not to events per se.

② Backing out Knot's context-switch rate

The paper states Haboob context-switches 30,000 times/second under full load — "more than 6 times as frequently as Knot." What's Knot's rate, and why the difference?

  1. Solve for Knot's rate: 30,000 ÷ 6 ≈ 5,000 context switches/second (an upper bound consistent with "more than 6×").
  2. Why Haboob switches so much: its thread-pool-per-handler model means every time an event passes from one stage to another, control may hand off to a different thread — one switch per stage boundary crossed.
  3. Why Knot switches so little: a single thread runs a request from accept to response, so most of a request's lifetime needs zero switches — only genuine blocking points (e.g. a real I/O wait) trigger one.
  4. Connect it back: this is the "assembly-line toll" from the SEDA analogy — Haboob's stage boundaries are real conveyor trips, and conveyor trips cost context switches.

③ Applying the duality table to one request

Trace "read a request, then write a response" through both columns of Figure 1.

  1. Threaded version: a thread calls read_request() (procedure call), which blocks on a condition variable while data arrives, then returns the parsed request.
  2. Event version: a handler issues SendMessage(read_request) and AwaitReply; the socket layer eventually delivers a message; the handler resumes via SendReply.
  3. Map term-for-term: "waiting on condition variables" ↔ "waiting for messages"; "procedure call" ↔ "SendMessage/AwaitReply"; "return" ↔ "SendReply."
  4. The only real difference is who tracks "what happens after the reply" — the call stack (threads) or a manually-saved continuation (events, i.e. stack ripping).
💡
This is literally Lauer–Needham's Figure 1 mapping, applied — every event-based idiom in a real server has a thread-shaped twin, and vice versa.

④ How small is "small" — code size as evidence

The authors built a ~5,000-line user-level thread package and, on top of it, a 700-line web server that beats a mature, heavily-engineered event system. What does that ratio suggest?

  1. 5,000 lines buys a general-purpose, scalable, blocking-I/O-emulating thread runtime — a one-time cost, reusable by any application.
  2. 700 lines is then enough for a complete web server: static requests, persistent connections, a page cache — "written in a clear, straightforward threaded style," per the authors, with "very little performance tuning."
  3. Compare to events: SEDA/Haboob-style systems need explicit stages, queues, and handler wiring for the same functionality — the paper attributes part of Haboob's overhead to "the proliferation of small modules... a natural outgrowth of the event programming model."
  4. Takeaway: the simplicity isn't just aesthetic — fewer moving parts (no stage/queue plumbing) is also fewer places for context switches and GC pressure to hide.
Test yourself

Practice problems

Try each before opening the answer — every one names the misconception it's checking.

Problem 1 · easy
Event systems claim "free" synchronization from cooperative multitasking. Does a cooperative thread system get the same benefit? Does it hold on a multiprocessor?
Show answer
Yes to the first — the free synchronization comes from not being preempted between yield points, which is a property of cooperative scheduling, available to threads and events alike (Adya et al.'s insight, cited in §2.2). No to the second — on a multiprocessor, another core can run concurrently regardless of cooperative scheduling on this core, so both paradigms need real synchronization there.Misconception: that "free" synchronization is an event-specific feature. It's a uniprocessor, cooperative-scheduling feature, full stop.
Problem 2 · medium
Haboob context-switches 30,000 times/second, "more than 6 times as frequently as Knot." What is Knot's approximate context-switch rate, and what causes the difference?
Show answer
30,000 ÷ 6 ≈ 5,000/second. Haboob's thread-pool-per-handler model context-switches whenever an event crosses a stage boundary; Knot's single thread per request only switches at genuine blocking points, so most of a request needs none.Misconception: that context switches are an unavoidable "threads tax." Here it's the opposite — the threaded server switches less, because it doesn't hand work between stages.
Problem 3 · medium
Define "stack ripping" (Adya et al.'s term) in your own words, and explain why it's a burden even for a careful, disciplined programmer.
Show answer
Stack ripping is the manual work of saving live state before a blocking call in an event handler (since it has no stack to preserve it) and restoring that state in whichever handler processes the reply. It's a burden regardless of discipline because it requires matching call/return pairs mentally, often across different parts of the codebase, and manually managing when that heap-allocated state is safe to free.Misconception: that stack ripping is just an unfamiliarity/style issue programmers get used to. The paper argues it's a structural cost independent of skill — threads simply don't require it.
Problem 4 · hard
Under Lauer–Needham duality, if a real thread system and a real event system perform differently, what does the paper conclude is the cause — and what would not count as a counterexample to the duality claim?
Show answer
The paper concludes the difference is due to implementation quality, not the abstraction — duality only guarantees equal performance for "equally good implementations." A single threaded system performing worse than a single event system is not a counterexample; it just means that particular thread runtime wasn't engineered as carefully (e.g., it still has O(n) scheduler operations).Misconception: that any observed performance gap disproves duality. Duality is a claim about idealized, well-engineered systems — real-world gaps are evidence about engineering effort, not about the theory.
Problem 5 · medium
Why do event systems typically heap-allocate per-task state, and what two mechanisms does the paper mention for cleaning it up — with what real-world cost for each?
Show answer
Event handlers unwind the stack after each callback, so nothing survives across a blocking point unless it's put on the heap by hand. Cleanup mechanisms: (1) garbage collection (Ninja, SEDA/Haboob use Java's) — the paper cites prior work finding general-purpose GC inappropriate for high-performance systems; (2) reference counting (Inktomi's Traffic Server) — correctness is hard to maintain, and the paper notes nearly every release battled slow memory leaks from it.Misconception: that heap allocation is a minor detail. The paper treats it as a root cause of two classes of real production bugs/overhead.
Problem 6 · hard
The paper says removing O(n)-in-thread-count operations from GNU Pth let it scale to 100,000 threads. Why would such operations exist in a thread scheduler in the first place, and why does removing them fix scalability rather than just delaying the problem?
Show answer
A naive scheduler might scan every thread to find a runnable one, or walk a linear list for bookkeeping (e.g., timers, priority updates) — simple to implement, and fine at small scale. Removing them (e.g., switching to O(1) or O(log n) data structures for the ready queue) fixes scalability fundamentally, rather than delaying it, because the cost per operation stops growing with thread count — at 100,000 threads the difference between O(n) and O(1) per operation is the difference between usable and unusable.Misconception: that "optimizing" a thread scheduler just buys you a bit more headroom. Removing an O(n) operation is a qualitative fix, not an incremental one — it changes the scaling curve's shape, not just its constant.
Problem 7 · medium
The paper says "arguably one of SEDA's contributions was to return event-driven systems to the 'good practices' of Lauer-Needham." What does that mean, given that most event systems don't match Lauer-Needham's canonical model?
Show answer
Most event systems use shared memory and global data structures, unlike Lauer and Needham's canonical message-passing systems, which pass messages through explicit channels with no shared state. SEDA's stages-and-queues architecture is the one event system the paper says does match that canonical model exactly — stages as processes, queues as message ports — so SEDA is, structurally, closer to the original 1978 idea than the event systems that came between.Misconception: that all "event-driven" systems are structurally similar. The paper treats SEDA as a special, more disciplined case, not representative of event systems generally.
Problem 8 · easy
The paper examined Flash, Ninja, SEDA, and TinyOS code and found only three control-flow patterns in practice. Name them, and explain why this undercuts the "events allow more flexible control flow" argument.
Show answer
Call/return, parallel calls, and pipelines. It undercuts the flexibility argument because all three map naturally onto threads (ordinary function calls, fork/join, and sequential stages respectively) — so the theoretical extra flexibility events offer (arbitrary fan-in/fan-out messaging) isn't actually exercised by real high-concurrency server code, except in rare multicast/publish-subscribe cases the studied systems didn't use.Misconception: that events' more general messaging model is a practical advantage. In the systems studied, it's an unused capability — real code sticks to patterns threads handle just as well.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Is this paper saying threads are always better than events?▾
Not quite — it says threads are at least as good for the specific case of high-concurrency servers with largely-independent requests and mostly-sequential per-request code, given a well-engineered runtime. The paper explicitly notes events remain more natural for dynamic fan-in/fan-out patterns (multicast, publish/subscribe) — patterns the servers they studied didn't actually use.
Q2What is Lauer–Needham duality, in one sentence?▾
A 1978 result showing that well-implemented thread systems and well-implemented message-passing (event) systems are structurally equivalent — every concept in one maps onto a concept in the other — so with equally good implementations, they should perform the same.
Q3What's "stack ripping" and why does it matter?▾
It's Adya et al.'s term for manually saving and restoring a task's live state across event-handler callback boundaries, since there's no call stack to do it automatically. It matters because it's the concrete, everyday cost event programmers pay that thread programmers simply don't.
Q4How did the authors prove threads can scale to 100,000?▾
They took GNU Pth, an existing user-level thread package, and removed operations that scanned or updated state in time proportional to the number of threads (O(n) operations). The result matched an event-based server's throughput up to 100,000 concurrent threads (Figure 2).
Q5What is Knot, and how does it compare to Haboob?▾
Knot is the authors' 700-line threaded test web server, built on their ~5,000-line thread package. Against SEDA's event-driven Haboob, Knot reaches ~700 Mbit/s vs. Haboob's ~500 Mbit/s peak; Haboob becomes CPU-limited at 512 clients and runs out of memory beyond 16,384 clients, while Knot was tested up to 65,536.
Q6Why does Haboob context-switch so much more than Knot?▾
Haboob's thread-pool-per-handler design context-switches whenever an event moves from one stage to another — 30,000 times/second at full load, over 6× Knot's rate — because Knot runs each request start-to-finish on one thread with minimal hand-offs.
Q7Does cooperative scheduling's "free synchronization" really come from events?▾
No — the paper (citing Adya et al.) attributes it to cooperative (non-preemptive) scheduling itself, which cooperative thread systems can equally exploit. It's also strictly a uniprocessor benefit; multiprocessors need real synchronization either way.
Q8What compiler support does the paper propose for threads?▾
Three things: dynamic stack growth (compiler-computed, per-call-site stack bounds, growing stacks on demand instead of fixed-sizing them); live-state pruning (popping dead temporaries before calls, warning about large state held across blocking calls); and static synchronization checking, modeled on nesC/TinyOS's atomic-section analysis.
Q9Did the authors' own earlier systems use events?▾
Yes — Ninja, SEDA, and Inktomi's Traffic Server, all built with heavy event-driven design. Their experience building these is exactly what led them to conclude events were the wrong choice — including that Ninja fell back to threads for its hardest parts (recovery) because getting them right with events was nearly impossible.
Q10How does this paper relate to Ousterhout's "Why Threads Are A Bad Idea"?▾
This paper's title directly echoes Ousterhout's 1996 talk, but the authors say their arguments don't actually conflict: Ousterhout argued cooperative events help programmers avoid concurrent code in cases that don't need true concurrency, and explicitly supported threads where true concurrency (their target: high-concurrency servers) is required.
Beyond this paper

Connections to modern OS & memory-systems design

Four short bridges from this 2003 debate to problems you're working on now.

🔀 io_uring echoes the same diagnosis

The paper argues events won mainly by avoiding expensive blocking syscalls and kernel crossings — an implementation cost, not a fundamental one. io_uring makes the same bet two decades later: it's an async submission/completion-ring interface that batches away exactly that kernel-crossing overhead — though it's still an asynchronous interface, not blocking-looking code, and it takes a runtime wrapped around it (not io_uring itself) to give application code back an ordinary call/return feel.

🧵 Green threads made a comeback

Capriccio-style user-level M:N threading, scaling to 100,000 threads by fixing scheduler data structures, is a conceptual forerunner — not a direct ancestor — of Go's goroutines and Java's virtual threads (Loom): both later bet, independently, that decoupling "logical concurrency unit" from "OS-scheduled entity" was the real fix, echoing this paper's argument rather than a switch to callback-based dispatch.

📍 The blocking graph is a policy-instrumentation problem, like page-access tracking

This paper's blocking graph tries to find the right granularity of "significant events" to instrument cheaply — every yield point, no more. OS-managed memory tiering faces the same design question: PTE access/dirty bits, hardware hotness counters, and periodic NUMA-balancing scans are all attempts to sample "significant events" (accesses) cheaply enough to drive page-placement decisions without instrumenting every load.

🛠 Compiler-assisted resource management, echoed in kernel-managed tiering

Section 4's pitch — let the compiler bound stacks and prune live state instead of making programmers do it by hand — is the same design instinct behind pushing page-placement policy into the kernel (automatic NUMA balancing, TPP-style hot/cold classification) rather than requiring every application to hand-tune numactl or manual tiering hints.

🍯
The recurring lesson — blame the implementation before the abstraction, and give the runtime/compiler good primitives instead of pushing policy into hand-rolled application logic — is exactly the bet behind OS-managed DRAM/CXL/NVM tiering over application-directed placement.

Sharp questions for seminar

Each references a specific claim, number, or design choice from the paper.

  1. Haboob's 30,000 context switches/second are blamed on its "thread-pool-per-handler" model — is that inherent to staged event-driven architectures, or could a different stage-to-thread mapping (e.g., one thread serving a whole pipeline) have closed most of that gap without abandoning SEDA's structure? (worth probing whether the paper's fix targets SEDA's design or just one implementation choice within it)
  2. The paper credits removing "O(n) operations" for GNU Pth's jump to 100,000-thread scalability but never names which data structures replaced them — what would you guess changed, and does that fix generalize to preemptive, kernel-scheduled threads too? (the paper is vague here; useful to reason from first principles about ready-queue design)
  3. Lauer–Needham duality assumes "equally good implementations" — twenty years on, does async/await syntax (which compiles callback chains back into linear-looking code) count as a compiler-level fix to stack ripping, or does it just hide the same heap-allocated continuation underneath a nicer syntax? (a chance to connect 1978/2003 arguments to today's async language design)
  4. Dynamic stack growth is proposed but explicitly flagged as unsolved for recursion and function pointers — given that virtually every real server has both, how much of the paper's compiler-support story survives contact with a real, indirect-call-heavy codebase? (probe whether the evaluation over-relies on Knot's unusually simple, direct-call-style code)
  5. The paper's case for threads rests on "requests are independent and per-request code is sequential" — how well does that assumption hold for today's fan-out-heavy RPC/microservice workloads, which the paper itself concedes suit events better? (the paper's own escape hatch — worth pressing on where its argument stops applying)

Glossary & further reading

Every term in one place, then a path to go deeper, then the provenance of every number above.

Core terms
Lauer–Needham dualityThe 1978 result that well-implemented thread and message-passing (event) systems are structurally equivalent and should perform the same.
Blocking graphA graph of a program's blocking/yielding points (nodes) and the code between them (edges); the formal basis of the duality argument.
Stack rippingAdya et al.'s term for manually saving/restoring live state across event-handler callback boundaries, since there's no call stack to do it automatically.
SEDAStaged Event-Driven Architecture — stages connected by explicit queues, with a thread pool per stage; the event framework this paper benchmarks against.
HaboobSEDA's event-driven web server, used as the "events" side of the paper's head-to-head performance comparison.
KnotThe authors' 700-line threaded web server, built to prove threads can match or beat Haboob.
Cooperative multitaskingScheduling that only switches tasks at explicit yield points, so code between yields runs uninterrupted — the real source of "free" synchronization.
O(n) scheduler operationsBookkeeping (e.g., scanning for a runnable thread) that takes time proportional to thread count — the paper's real culprit behind "threads don't scale."
Supporting terms
poll() / epoll()System calls that ask "which of these sockets are ready?" — the mechanism event loops use to avoid blocking on any one connection.
M:N (user-level) threadingMultiplexing many user-level threads onto few kernel threads, so most scheduling and switching avoids kernel crossings.
Context switchSaving one task's execution state and loading another's; cheap for cooperative user-level threads, costlier under preemption or kernel involvement.
Reference countingFreeing heap-allocated state when its tracked reference count hits zero; the mechanism blamed for memory leaks at Inktomi's Traffic Server.
Garbage collection (GC)Automatic reclamation of heap memory (Ninja, SEDA/Haboob use Java's) — cited elsewhere as poorly suited to high-performance systems.
nesC / TinyOS atomic sectionsA compiler-checked language construct guaranteeing a code block never yields or blocks internally, used as a model for compiler-verified thread synchronization.
Dynamic stack growthThe paper's proposed compiler technique to size and resize thread stacks on demand instead of fixing their size in advance.
Fan-in / fan-outControl-flow patterns where one task's result feeds many, or many feed one (multicast, publish/subscribe) — the one case the paper concedes suits events better.
GNU PthAn existing user-level thread package the authors modify (removing O(n) scheduler operations) for the Figure 2 scaling experiment.
