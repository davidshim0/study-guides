HPCA 2025 · A Field Guide

Move the math to where the data already lives, not to where the GPU sits waiting

Every decoder step re-reads a growing Key/Value cache just to score one query. PAISE decides, layer by layer, when that memory-bound work is cheaper to run inside memory — on Processing-In-Memory (PIM) — instead of dragging the data across the bus to the GPU.

📄 Lee, Baek, Son, Choi, Moon, Jang · Samsung SDS · HPCA'25 🎓 GPU/HBM basics assumed — the primers cover PIM specifics ⏱ ~25 min read
💾

Offload a layer to PIM only when its reuse benefit beats its layout + padding overhead — recomputed per layer, per model, per batch size.
u = benefit − overhead; offload iff u > 0.

1Arithmetic intensity: compute-bound vs memory-bound▾

Arithmetic intensity = how many FLOPs you do per byte moved from memory. High intensity → the chip is busy computing (compute-bound); low intensity → the chip mostly waits on data (memory-bound).

A GPU is built to be compute-bound: thousands of ALUs, fed by a wide but ultimately finite memory bus. Memory-bound work leaves those ALUs idle.

Now you're ready: PAISE's whole premise is that the attention layer stays memory-bound no matter the batch size, so parking its computation next to the memory (PIM) skips the idle wait.
2GEMV vs GEMM, and why batching turns one into the other▾

A single inference request needs a matrix-vector multiply (GEMV) — one activation vector times a weight matrix. Serve many requests together and you can stack their vectors into a matrix, turning it into a matrix-matrix multiply (GEMM), which GPUs handle far more efficiently per byte moved.

Now you're ready: this batching trick works for FC layers (shared weights across requests) but not for attention — each request has its own K/V matrices, so attention stays GEMV-shaped even at large batch.
3The KV cache, and why it grows every token▾

To avoid recomputing attention over the whole sequence at every step, LLMs cache each token's Key and Value vectors. Each new generated token appends one more row to K and one more column to Vᵗ — so the matrices grow from the prompt length up to the maximum sequence length Lseq as generation proceeds.

Now you're ready: that growth is why attention's memory traffic scales with output length — and why PAISE targets the generation (decode) phase, not the one-shot summarization/prefill phase.
4Processing-In-Memory: a compute unit inside the DRAM die▾

PIM places a small Processing Unit (PU) next to each memory bank, so read bandwidth and compute scale together with the number of banks — instead of being bottlenecked by a single external memory bus. This paper uses Aquabolt-XL, a real HBM2-PIM device stacked with the GPU in one package.

Now you're ready: because PIM computes where data sits, it particularly favors GEMV — one read, one local multiply-accumulate, no long trip back to the GPU.
5Banks, bankgroups, channels — how PIM is physically organized▾

A PIM System-in-Package (SiP) nests: 4 chips → 4 PIM dies each → 4 pseudo-channels each → 4 bankgroups each → 4 banks each (paired even/odd) = 1024 banks total. Each bank's PU processes 256B (128 FP16 elements) per iteration.

Because a PU alternates between an even and an odd bank per multiply-accumulate step, the smallest useful operation spans 512B (256 elements) across a bank pair.

Now you're ready: PIM is allocated in units of banks and bank-pairs, the same way a cache is allocated in ways — and there's an "optimal" matrix size, (4096, 256), that exactly fills all 512 bank-pairs across a SiP's 64 pseudo-channels.
6DRAM command ordering and the memory fence▾

DRAM controllers normally reorder commands for efficiency — fine for regular reads, but disastrous for PIM, whose correctness depends on commands hitting banks in a specific sequence. HBM-PIM uses fences to preserve ordering, allowing 8 commands to be issued between fences, but fences themselves cost latency.

Now you're ready: PAISE's Data Layout Adjustment exists specifically to arrange data so the host processor never needs to reorder or interrupt a PIM command sequence.
7Weight reuse — why batch size changes the offloading math▾

Setting up a matrix for PIM (transforming its layout, copying it into PIM memory) costs overhead. That cost is worth paying only if the matrix will be reused many times before being replaced — i.e. across many decode iterations or many batched requests.

Now you're ready: this is exactly the "reuse rate" term in PAISE's offloading formula — more decoder iterations and longer output sequences make PIM more attractive; a single one-shot use does not.
8Idle-bank / zero-padding inefficiency▾

If a weight matrix doesn't perfectly match PIM's optimal size (4096, 256), the unused banks in that region still get allocated and zero-padded — you pay for capacity you don't use, and the true compute density drops accordingly.

Now you're ready: this is the second overhead term in PAISE's scheduling formula, and it's exactly what interleaving DLA is designed to shrink by packing several small matrices together instead of padding each one alone.
9Static analytical scheduling vs the online monitoring you know▾

If you've worked with hotness-tracking tiering systems (TPP, HeMem, Memtis) or pool-based CXL memory (Pond), you're used to online decisions: continuously sample access patterns at runtime and migrate data based on observed behavior.

PAISE's scheduler is different: it is a closed-form analytical decision computed once from known model configuration (embedding dimension, heads, sequence length) and known PIM hardware constants (α, γ, β) — no runtime access-pattern monitoring at all.

Now you're ready: think of PAISE's offloading decision less like a tiering policy that watches hotness, and more like a compiler-time placement decision — it knows the whole computation graph in advance, so it doesn't need to guess.
The whole story in one place

PAISE in a nutshell

Why attention and FC layers behave differently, and how PAISE turns that difference into a scheduling decision.

In a transformer decoder, the FC layer executes O(khw) compute against O(hw) memory traffic (batch size k ≪ weight dims h,w) — as k grows, compute outgrows memory movement, and the layer shifts from memory-bound to compute-bound, where the GPU wins. The attention layer is structurally different: each request carries its own K/V matrices, so its compute and memory traffic are both O(k·dhead·h·w) — asymptotically equal for any batch size. Attention never becomes compute-bound; it is memory-bound at every scale.

PIM devices like HBM-PIM excel exactly where GEMV dominates: their measured GEMV execution-time ratio (GPU time ÷ PIM time) exceeds 1.8× at batch k=1, but that advantage shrinks as k grows and GPUs pull ahead on GEMM. PAISE turns this into a per-layer scheduling rule (Algorithm 1): compute an offloading incentive u = (PIM's speed advantage × weight reuse) − (layout overhead) − (idle-bank padding waste); offload to PIM only when u > 0.

Because attention's memory-boundedness doesn't fade with batch size, it is almost always worth offloading. FC layers are worth offloading only when batch size is small and the matrix fits PIM's optimal layout without excess padding — otherwise they stay on GPU. To make offloading actually fast, PAISE also introduces interleaving DLA and an IB-GEMV kernel that removes the standard PIM kernel's costly GPU-side reduction step.

The payoff: offloading attention alone cuts GPT-2 end-to-end latency by up to 48.3% (at 80 output tokens) versus GPU-only, with a stable ~10% reduction once output exceeds 200 tokens, and total energy consumption drops by roughly 11.5% as execution time falls from 159.0s to 142.6s.

🍯 Key takeaways

  • FC layers become compute-bound as batch size grows; attention stays memory-bound at any batch size (both are O(k·dhead·h·w)).
  • PIM-GEMV beats GPU by >1.8× at k=1; the advantage shrinks as k grows toward GEMM territory.
  • Offloading incentive u = reuse benefit − DLA overhead − idle-bank waste; offload iff u > 0, decided per layer.
  • Interleaving DLA + IB-GEMV pack multiple small matrices into PIM's optimal (4096, 256) region and drop the GPU reduction step.
  • Attention offload is nearly always worth it; FC offload only helps at small batch and when PIM memory (physically limited) permits it.
  • Result: up to 48.3% latency cut, ~11.5% energy reduction, on real HBM-PIM hardware — not a simulator.
Six everyday pictures

How to think about PAISE

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Attention vs FC

A short-order cook vs a conveyor bakery

A short-order cook (PIM) is unbeatable for one custom order at a time — no setup, immediate turnaround. A conveyor-belt bakery (GPU) is unbeatable once you need a thousand identical loaves — the per-loaf cost drops as volume rises. Attention always arrives as "one custom order per request" (each has its own K/V matrix), so the cook wins at any serving scale. FC layers can be batched into identical loaves, so the bakery eventually wins.

Where it breaks: real cooks can hire help to scale up; PIM's hardware layout is fixed at fabrication — it can't restructure itself the way a kitchen can add staff.
Sequential DLA's flaw · Idle banks

Renting four half-empty trucks

Basic sequential DLA gives each small matrix its own PIM region and zero-pads the rest — like renting a full moving truck for every half-load of furniture. You pay for (and can't share) the empty space. PAISE's interleaving DLA instead loads four half-loads into one truck, splitting each shipment into column-fractions that fit a transaction and packing them side by side — no idle capacity.

Where it breaks: real movers can just add a smaller truck; PIM's unit region size (4096, 256) is fixed by the hardware, so under-filling always means either padding or clever interleaving — there's no third truck size to pick.
Bank-level parallelism · Even/odd pairs

A bucket brigade passing bricks left, right, left

Each Processing Unit works a bank pair the way a two-person brigade passes bricks: reach left (even bank), multiply-accumulate, reach right (odd bank), multiply-accumulate, repeat. That alternation is why the smallest efficient operation spans two banks (512B) rather than one — you need both hands moving to keep the line full.

Where it breaks: a brigade can skip a person if bricks run out; PIM's even/odd alternation is fixed by wiring, so an operand matrix that isn't shaped to use both banks per step just wastes the idle one.
The scheduler · Reuse vs setup cost

Preheating a specialty oven

Firing up a pizza oven takes real setup time and fuel — worth it only if you'll bake many pizzas before switching dishes. PAISE's incentive u is exactly this calculation for a weight matrix: the DLA "preheat" cost (γ) and idle-bank waste (β) are fixed per use, but the payoff (α × reuse count) grows with how many decoder iterations — how many pizzas — that matrix will serve before being replaced.

Where it breaks: a real oven's preheat cost doesn't change with the recipe; PAISE's β term does — a matrix that fits PIM's optimal shape "preheats" far cheaper than a mismatched one.
Bulk memcpy · Fewer, larger trips

One moving van instead of forty grocery bags

Copying a KV-cache update one 32-byte transaction at a time is like carrying groceries into the house one bag per trip. PAISE's bulk-memcpy consolidates a whole token's worth of K/V updates into one transfer — a single van trip — cutting the fixed per-trip overhead that dominates when each trip is tiny.

Where it breaks: bulk copying still moves the same total bytes — it removes per-transaction overhead, not the underlying data volume. The paper still finds sequential-DLA GEMV slower than GPU-only overall (only 25% bank-bandwidth utilized) even with bulk memcpy; interleaving DLA is what actually fixes bandwidth use.
vs. runtime tiering · Static vs online

A seating chart printed before the party, not adjusted during it

A seating chart made in advance from the guest list (who's coming, who knows whom) is PAISE's approach: compute the placement once from known model configuration and hardware constants, before inference even runs. Online tiering systems like TPP or HeMem are more like a host rearranging seats mid-party based on who's actually mingling with whom — reacting to observed behavior, not planning from a list.

Where it breaks: a printed chart can't react if the party's mood shifts; PAISE's decision is recomputed per layer configuration but not per live access pattern, so unlike TPP/HeMem/Memtis it can't adapt within a single inference run if actual reuse deviates from the analytical estimate.
The full explanation

How it actually works

From hardware layout to the scheduling formula to the kernel that executes it.

1 · Why attention and FC diverge

For an FC layer with batch k, weight height h, width w: compute is O(khw), memory I/O is O(kh + hw + kw) ≈ O(hw) when k ≪ h,w. As k grows, compute outpaces memory movement — the layer becomes compute-bound, favoring the GPU. For MHA with dhead heads, both compute and memory I/O are O(k·dhead·h·w) — they scale together, so attention is memory-bound regardless of k.

2 · Standard PIM-GEMV's two limitations

The stock PIM-GEMV kernel multiplies in 32B transaction units, then relies on the GPU to reduce (sum) partial results into the final output vector. Two problems follow: (1) real weight matrices rarely match the optimal (4096, 256) shape, leaving banks idle and zero-padded; (2) because the kernel sums everything in a region into one output, you can't pack multiple small matrices into one region — their results would blend into an unusable sum.

3 · The scheduling algorithm

For an FC layer with weight matrix shaped by DLA into (n, m), PAISE computes:

u = αk·(Lseq−s)·d·n·m − γ·n·m − β·(n*m* − n·m)
# α_k: PIM's GEMM speed advantage at width k · (L_seq−s)·d: reuse count across output tokens × decoders
# γ·nm: DLA + copy overhead · β(n*m*−nm): idle-bank padding waste

For an attention layer, the K/V matrix is updated one row at a time regardless of batch, halving effective reuse and overhead:

u = α1·(Lseq−s)·d·h·nm/2 − γ·nm/2 − β(n*m* − nm/2)

Offload to PIM iff u > 0. Since attention's α1 (the k=1 GEMV advantage) stays high at any serving batch size while FC's αk shrinks as k grows, attention crosses this threshold far more often than FC.

💡
Why the summarization phase is excluded: the weight matrix is reused less there (fewer output tokens = smaller Lseq−s), so the reuse term shrinks and overhead dominates — PAISE deliberately targets only the generation phase.

4 · Execution flow for offloaded attention

Each decoder step: (1) GPU computes Q/K/V; (2) host issues a bulk memcpy of the new K/V row(s) into the PIM memory region, concatenating with the existing cache; (3) PIM's IB-GEMV kernel computes attention scores and values directly against the resident K/V cache; (4) results return to GPU for softmax/residual (PIM cannot execute Softmax, GELU, LayerNorm, or residual — these stay on GPU); (5) after the final token, the PIM region is reset.

Follow the numbers, step by step

Worked examples

Four traces using the paper's real model configurations, matrix sizes, and measured latencies.

① GPT-2's projection layer: why FC offload is inefficient

GPT-2's projection layer weight is (768, 768). It's split across three PIM unit regions of (4096, 256). What fraction of allocated PIM capacity is actually used?

  1. Total allocated capacity: 3 regions × 4096 × 256 = 3,145,728 elements.
  2. Actual weight elements: 768 × 768 = 589,824 elements.
  3. Utilization: 589,824 ÷ 3,145,728 ≈ 18.75% — over 80% of the allocated banks sit idle, zero-padded.
  4. Check against the paper's idle-bank figure: 3,145,728 − 589,824 = 2,555,904 elements idle, which the paper reports as a (3328, 768) idle region: 3328 × 768 = 2,555,904. ✓ matches.
🍯
Insight: this is exactly the idle-bank term β in Algorithm 1 — at only 18.75% utilization, the overhead is large enough that FC offload for GPT-2 needs very high reuse (large batch, many iterations) to pay off, and the paper reports it generally doesn't.

② Llama2-7B's 12 GB problem

Llama2-7B's FC layers per decoder block: 4 matrices of (4096,4096) [Q,K,V,O], 2 of (11008,4096) [gate, up], 1 of (4096,11008) [down], in FP16, across 32 decoder blocks. Does it fit in 8 GB of PIM memory?

  1. QKVO: 4 × 4096 × 4096 = 67,108,864 elements.
  2. Gate + Up: 2 × 11008 × 4096 = 90,144,768 elements.
  3. Down: 4096 × 11008 = 45,072,384 elements.
  4. Per block total: 67,108,864 + 90,144,768 + 45,072,384 = 202,326,016 elements → × 2 bytes (FP16) ≈ 385.9 MB.
  5. × 32 decoder blocks: 385.9 MB × 32 ≈ 12.06 GB — matching the paper's "over 12 GB" claim exactly, and exceeding the paper's stated 8 GB PIM memory limit.
⚠
A discrepancy worth flagging: the paper's text states "8 GB of physical memory," but Table III lists the Aquabolt-XL device as "6 GB (VRAM)." Either figure makes the same point — all FC layers don't fit — but the two numbers in the paper don't agree with each other.
💡
This is why PAISE offloads only output, up, and down projections — down projection needs just 43 PIM regions (4096, 43×256 = 11008 columns), fewer than the 48 regions gate/up projections need, so it's chosen first under the memory budget.

③ Reading Table II: when does FC offload stop paying off?

Llama2-7B end-to-end latency (seconds), input/output length 2048/2048: batch 1 → 56.48 (GPU-only), 50.73 (attn-only), 41.83 (attn+FC); batch 4 → 87.42, 67.85, 79.12.

  1. Batch 1, attn-only vs GPU-only: (56.48 − 50.73) / 56.48 ≈ 10.2% faster.
  2. Batch 1, attn+FC vs GPU-only: (56.48 − 41.83) / 56.48 ≈ 25.9% faster — FC offload adds a further large win at small batch.
  3. Batch 4, attn-only vs GPU-only: (87.42 − 67.85) / 87.42 ≈ 22.4% faster.
  4. Batch 4, attn+FC vs GPU-only: (87.42 − 79.12) / 87.42 ≈ 9.5% faster — still better than GPU-only, but worse than attention-only (22.4%). FC offload has become a net drag relative to leaving FC on GPU.
🍯
Insight: this is αk shrinking as batch k grows (Section II-B) made concrete — at batch 4, FC's compute has grown enough to favor the GPU's GEMM engine, so the earlier win from PIM's GEMV advantage reverses. Attention's incentive doesn't reverse, because its α stays anchored near α₁ regardless of batch.

④ Energy: why power × time isn't the whole story

The paper reports average power 103 W (GPU-only) vs 100 W (KV-cache offload), execution time 159.0s → 142.6s, and a total energy reduction of ~11.5%.

  1. Naive estimate, GPU-only: 103 W × 159.0 s ≈ 16,377 J.
  2. Naive estimate, PAISE: 100 W × 142.6 s ≈ 14,260 J.
  3. Naive reduction: (16,377 − 14,260) / 16,377 ≈ 12.9% — noticeably higher than the paper's reported 11.5%.
  4. Why the mismatch: 100 W and 103 W are rounded averages over a fluctuating power trace (Fig. 16 samples every 0.1s); the paper's 11.5% comes from integrating the actual trace, not multiplying two rounded averages. The takeaway direction is right — less energy — but treat "11.5%" as the paper's number and the naive 12.9% as a sanity-check approximation, not a replacement.
💡
The larger latency reduction (10.3%: 159.0→142.6s) is the dominant driver of the energy savings — average power barely moves (103→100 W), which makes sense: PIM offload shifts where memory traffic happens, not how much total power the SiP draws while busy.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks for.

Problem 1 · easy
A team doubles the serving batch size for an LLM. Why does this make offloading the FC layer to PIM less attractive, but barely change the case for offloading the attention layer?
Show answer
FC layer compute is O(khw) while its memory I/O stays ~O(hw); doubling k grows compute faster than memory movement, pushing FC toward compute-bound territory where the GPU wins, and shrinking PIM's speed advantage αk. Attention's compute and memory I/O are both O(k·dheadhw) — they grow together — and critically, each request still needs its own K/V GEMV regardless of how many requests are batched, so its effective per-request k stays near 1.Misconception: that "batch size" is a single global lever. It changes FC's arithmetic intensity but doesn't change attention's fundamentally GEMV-shaped, per-request memory access pattern.
Problem 2 · medium
A weight matrix is (2048, 2048) FP16. How many (4096, 256) PIM unit regions does it need, and what fraction of allocated capacity is used?
Show answer
2048 rows fit within one 4096-row region (with 2048 rows unused vertically); 2048 columns need ⌈2048/256⌉ = 8 unit-width slices. So it needs roughly 1 region's worth of row-capacity × 8 column-slices — in practice this is packed as fewer full (4096,256) regions with column concatenation; using the paper's GPT-2-style method, total allocated capacity for 8 slices of (4096,256) = 8 × 4096 × 256 = 8,388,608 elements. Actual weight elements = 2048×2048 = 4,194,304. Utilization ≈ 4,194,304/8,388,608 = 50%.Misconception: assuming a matrix that's "close to square" automatically fits PIM's layout well. Fit depends on matching the (4096, 256) row:column ratio (16:1), not on being square or even large.
Problem 3 · medium
Why can't the standard PIM-GEMV kernel simply place four unrelated small matrices side-by-side in one (4096,256) region to avoid idle banks?
Show answer
The standard kernel performs vector addition (GPU-side reduction) across the entire region to produce one output vector — it can't tell which partial sums belong to which of the four matrices. Interleaving DLA plus the IB-GEMV kernel solve this by decomposing each matrix into transaction-sized column-fractions, interleaving them, and running a separate reduction per matrix instead of one reduction over the whole region.Misconception: that packing is purely a data-layout problem. It's also a kernel problem — you need a modified reduction step (IB-GEMV), not just clever placement.
Problem 4 · hard
Llama2-7B's FC layers need ~12 GB of PIM memory for all 32 decoder blocks at batch 1, but the device provides only 8 GB (per the paper's text). PAISE offloads only output, up, and down projections. Why not simply offload FC layers for the first N decoder blocks and leave the rest on GPU?
Show answer
The paper doesn't evaluate that specific per-block-truncation strategy — it chooses which matrix types (down, then up/gate/output) to offload across all blocks within the memory budget, prioritizing the projection with the smallest PIM region count (down needs 43 regions vs 48 for gate/up). This is consistent with the paper's per-layer-type incentive formula, which doesn't have a notion of "give up after decoder block N" — it evaluates u per matrix, not per position in the stack.Misconception: that PAISE's scheduling operates at block granularity. It operates at the matrix/layer-type granularity, constrained globally by total PIM memory capacity.
Problem 5 · medium
Table VI shows the AS layer's output-transformation overhead (68 µs on GPT2-Medium batch 32) is much larger than the AV layer's (13 µs). Why?
Show answer
The AS layer's batched output size scales with sequence length Lseq, which is generally much larger than the head dimension dhead that bounds the AV layer's output. A bigger output means more elements to transform back from PIM's physical layout to the GPU's logical layout, and the AS layer's use of interleaving DLA (needed because its input is smaller and output larger) requires more complex index calculations than AV's simpler layout.Misconception: that AS and AV layers are symmetric just because they're both "attention." Their matrix shapes are transposed relative to each other (Lseq×dhead vs dhead×Lseq), which changes which dimension dominates the transformation cost.
Problem 6 · easy
Why can't PIM run the Softmax step of attention, and what does that mean for the execution flow?
Show answer
HBM-PIM's Processing Units support multiply-accumulate operations for GEMM/GEMV but not nonlinear functions like Softmax, GELU, LayerNorm, or residual addition — those stay excluded from PIM offloading entirely. This means every offloaded attention step still returns to the GPU between the AS/AV GEMV kernels and the softmax/residual steps, adding a GPU↔PIM handoff that PAISE's kernel stream management must coordinate.Misconception: that offloading "the attention layer" moves the whole layer's computation onto PIM. Only the GEMV-shaped score/value matmuls move; the nonlinear glue stays on GPU by hardware necessity.
Problem 7 · hard
A colleague argues PAISE's scheduling algorithm is "just like" an online memory-tiering policy (e.g. TPP) because both decide where data/compute should live. What's the key structural difference?
Show answer
TPP-style tiering continuously samples access patterns at runtime (e.g. via hardware access bits or PEBS sampling) and migrates pages based on observed hotness — an online, feedback-driven loop. PAISE's Algorithm 1 computes u analytically from known model configuration (demb, heads, Lseq) and fixed PIM hardware constants (α, γ, β), with no runtime monitoring of actual access behavior — closer to a compile-time placement decision than a tiering policy.Misconception: that "deciding where computation/data should live" is inherently an online, adaptive process. PAISE shows it can be a closed-form calculation when the workload's structure (a known transformer architecture) is fully known in advance.
Problem 8 · medium
Why does PAISE's latency improvement (Fig. 15) show a sawtooth pattern in Time Per Output Token rather than a smooth curve?
Show answer
The GPU allocates memory for growing tensors (like the KV cache) in step-wise increments rather than continuously, so latency jumps at each reallocation boundary and then holds until the next one — producing the sawtooth. Offloading to PIM lowers the peaks of that sawtooth and lengthens the period between jumps, because PIM's KV-cache update kernel writes new tokens directly with constant-time token concatenation, unlike GPU's approach which re-reads the whole cache for concatenation as it grows.Misconception: that "latency vs output length" should look like a clean line. Real GPU memory management is discrete and step-wise, which is why the paper reports linear regressions rather than exact curves.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What does PAISE actually offload — whole layers or specific operations?▾
Specific GEMM/GEMV operations within layers: the attention score (AS) and attention value (AV) matmuls, and — only under favorable batch size and memory constraints — select FC projections (output, up, down for Llama2-7B). Nonlinear operations (softmax, GELU, LayerNorm, residual) never move to PIM; the hardware can't run them.
Q2Why is attention layer offloading almost always beneficial but FC layer offloading only sometimes?▾
FC layer compute grows faster than its memory traffic as batch size increases (O(khw) vs O(hw)), eventually favoring the GPU's GEMM engine. Attention's compute and memory traffic scale together at any batch size (O(k·dheadhw) both), so it stays memory-bound — PIM's home turf — regardless of how many requests are served together.
Q3Is PAISE tested on a simulator or real hardware?▾
Real hardware: an AMD Instinct MI100 GPU paired with Samsung Aquabolt-XL HBM2-PIM, running ROCm 4.0 and a modified version of Samsung's open-source PIMLibrary. The paper explicitly contrasts this with prior PIM-LLM work (NeuPIMs, AttAcc, TransPIM) that relies on DRAM simulators like DRAMsim3.
Q4What is interleaving DLA solving that sequential DLA doesn't?▾
Sequential DLA gives each small weight matrix its own PIM region, wasting the rest as zero-padded idle banks. Interleaving DLA decomposes multiple matrices into transaction-sized column-fractions and packs them together into one region with no idle banks, paired with an IB-GEMV kernel that keeps each matrix's output distinguishable via separate reduction.
Q5How big is the measured speedup, exactly?▾
Offloading the attention layer cuts GPT-2 end-to-end latency by up to 48.3% at 80 output tokens, and by a more stable ~10% once output exceeds 200 tokens. For Llama2-7B at batch 1, offloading attention plus 8 FC layers cuts latency from 56.48s to 41.83s (~25.9%).
Q6Why does the paper report offloading FC layers sometimes making things worse?▾
At larger batch sizes (e.g. Llama2-7B batch 4 in Table II), FC compute has grown enough to favor GPU's GEMM engine, so offloading FC to PIM adds overhead without a matching benefit — total latency at batch 4 is worse with FC offloaded (79.12s) than with attention-only offload (67.85s), though still better than GPU-only (87.42s).
Q7What is the KV cache "bulk memcpy," and why was it needed?▾
The original PIMLibrary copied KV cache updates in small 32-byte transactions, which profiling showed was a major latency source. PAISE's bulk-memcpy consolidates a token's K/V update into one larger transfer, cutting up to 21.4% of execution time versus the conventional copy — though the sequential-DLA GEMV path still lags GPU-only overall because it only uses 25% of PIM's bank bandwidth; interleaving DLA is what closes that gap.
Q8Does PAISE require changing the model itself?▾
No — GPT-2 and Llama2-7B run with their standard Hugging Face pretrained weights. PAISE modifies the inference-serving code path (via a Python-level API) to route specific matmuls through its PIM kernel, not the model architecture or weights.
Q9How does PAISE's scheduling decision differ from an online memory-tiering policy like TPP or HeMem?▾
PAISE's Algorithm 1 is a closed-form calculation from known model configuration and fixed PIM hardware constants (α, γ, β) — no runtime access-pattern monitoring. Online tiering systems continuously sample actual access behavior and adapt. PAISE knows the transformer's computation graph in advance, so it can plan rather than react.
Q10What's the energy story?▾
In the paper's KV-cache-offload experiment, average power drops only slightly (103W → 100W) but execution time drops from 159.0s to 142.6s, yielding a reported ~11.5% total energy reduction — driven mostly by finishing faster, not by drawing meaningfully less power while running.
Q11What are the main limitations acknowledged by the authors?▾
No fine-grained scheduling between GPU-only kernels and PIM kernels (currently hand-coded to avoid concurrent execution), a single-process-only PIM memory allocator, and no multi-GPU support yet — all listed as future work, alongside integration with frameworks like DeepSpeed and FlashAttention.
Q12How does PAISE relate to NeuPIMs, AttAcc, and TransPIM?▾
All target PIM acceleration for transformer LLM inference, but NeuPIMs and AttAcc are evaluated via simulators and focus on NPU/PIM pipeline scheduling for batched inference, while TransPIM proposes a hybrid in-bank/near-bank architecture. PAISE's distinguishing contribution is running on real HBM-PIM hardware and contributing a general offloading-decision framework (the scheduling algorithm) plus the DLA/IB-GEMV kernel needed to make that decision executable.

Glossary & further reading

Every term in one place, then provenance.

Core terms
PAISEPIM-Accelerated Inference Scheduling Engine — the paper's framework: a scheduling algorithm plus a modified PIM kernel for offloading transformer LLM operations.
Offloading incentive (u)u = PIM's reuse benefit − DLA/copy overhead − idle-bank waste. Offload to PIM iff u > 0.
Interleaving DLADecomposes multiple weight matrices column-wise into transaction-sized fractions and interleaves them into one PIM region, eliminating idle banks.
Sequential DLARow-wise or column-wise placement of one weight matrix per PIM region — simple but leaves idle, zero-padded banks when the matrix doesn't match the optimal size.
IB-GEMV / IB-GEMMInterleave-Batched GEMV/GEMM kernel — performs separate per-matrix reduction instead of the standard kernel's single GPU-side reduction, enabling multiple matrices to share one PIM region.
αk (effectiveness)PIM's execution-time speed advantage over GPU for GEMM/GEMV with input width k. α1 > 1.8 measured; decreases as k grows.
γ (DLA overhead)Per-element cost of transforming and copying a weight matrix into PIM's layout.
β (idle-bank inefficiency)Per-element cost of zero-padded, unused banks when a matrix doesn't match PIM's optimal (4096, 256) region.
Supporting terms
AS / AV layerAttention-Score layer (K·Qᵗ) and Attention-Value layer (scores·V) — the two GEMV-shaped matmuls inside multi-head attention.
Unit weight matrix (4096, 256)The PIM region size that exactly fills all 512 bank-pairs across a SiP's 64 pseudo-channels without extra memory fences.
SiP (System-in-Package)GPU + stacked HBM-PIM dies communicating via logic dies and TSV interposer; here, MI100 + 4 Aquabolt-XL stacks.
Memory fenceA DRAM command barrier preserving PIM's required command ordering; allows 8 commands between fences, at a latency cost.
All-bank modeA single DRAM command broadcast to and processed by all PUs in parallel within a pseudo-channel.
Bulk memcpyPAISE's consolidated KV-cache transfer API, replacing many small 32B transactions with one larger copy.
TPOTTime Per Output Token — shows a sawtooth pattern tied to GPU's step-wise tensor memory allocation.
Summarization / generation phasePrefill (process the prompt, produce first token) vs decode (produce each subsequent token autoregressively) — PAISE targets only generation.

The commercial HBM2-PIM device PAISE runs on; source of the hardware specifics (bank hierarchy, PU design, memory fence behavior) used throughout this guide.
