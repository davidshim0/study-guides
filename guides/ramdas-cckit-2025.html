ACM TOCS 2025 · A Field Guide

Letting an FPGA say "I own this line", not just "may I borrow it?"

CCKit gives an FPGA a real home agent — its own slice of coherent address space, symmetric with the CPU — so accelerator logic can watch, drive, and even customize the cache-coherence protocol instead of just riding along as a dumb cache.

📄 Ramdas et al., ACM Trans. Comput. Syst. 43,3 (2025) 🎓 Assumes you know MESI/MOESI basics — primers cover the rest ⏱ ~25 min read
🧩

Symmetric coherence means both CPU and FPGA run a home agent — so the FPGA isn't just a cache client asking permission, it can issue forwards, locks, and clean-invalidates of its own.

Before you begin

Quick glossary + eight primers

Acronyms first, then concepts. Skip anything you already know.

Quick glossary

1What "cache coherence" actually guarantees▾

When multiple caches hold copies of the same memory line, coherence ensures everyone sees a consistent value: only one writer at a time (SWMR), and reads always return the latest write. A directory-based protocol tracks, per line, who has which state (M/E/S/I) in a central or distributed directory rather than broadcasting to everyone (snooping).

Now you're ready: CCKit builds exactly this kind of directory-based MESI protocol — but puts a directory on the FPGA too.
2Symmetric vs. asymmetric coherence▾

Asymmetric (today's CXL 1.1, Intel HARPv2, IBM CAPI): only the CPU has a home agent — the component that tracks line ownership and arbitrates requests. The accelerator is just a caching client; to touch even its own local memory, it may have to round-trip through the CPU. Symmetric: both sides have home agents, like a 2-socket NUMA system — the FPGA owns and polices its own address range.

Now you're ready: this is the central design axis of the paper. CCKit is a symmetric protocol; it's what lets the FPGA issue its own forward-downgrade or clean-invalidate messages instead of just answering the CPU's.
3Directory states, transient states, and why protocols explode▾

Textbook MESI has 4 states. Real implementations add dozens to hundreds of transient states to handle messages that are in-flight, reordered, or conflicting (e.g., a line being evicted just as it's requested elsewhere). CCKit's own state machine on Enzian has 79 states and 304 transitions for just 25 message types.

Now you're ready: this complexity is exactly what CCKit hides from application logic — exposing only the 4 stable states plus simple requests, while the generated state machine handles the other 75.
4FPGAs as reconfigurable accelerators▾

An FPGA is reprogrammable hardware: instead of running instructions, you synthesize custom digital circuits. This makes it ideal for prototyping new protocols (unlike a fixed CPU), but FPGAs run far slower — here, 322 MHz vs. the CPU's 2 GHz, over 6× slower per clock.

Now you're ready: a recurring theme is how CCKit claws back that 6× clock disadvantage using parallel hardware units instead of raw speed — see primer 8.
5Why simulators aren't enough▾

Cycle-accurate RTL simulators that are detailed enough to be trustworthy run in the kHz range — far too slow to run a real database workload or OS. Faster simulators usually buy speed by simplifying the protocol, which is exactly where the subtle correctness bugs live.

Now you're ready: this motivates CCKit's whole approach — a real hardware implementation on a real platform (Enzian), not another simulator.
6CXL's two (eventually three) protocol flavors▾

CXL.io (PCIe-like I/O), CXL.cache (device caches host memory), CXL.mem (host accesses device memory as expanded capacity). Today's CXL 1.1 hardware is asymmetric; fully symmetric coherence is reserved for the still-unreleased CXL 3.0.

Now you're ready: the paper's two main applications map directly onto these: the concurrent table (§5.4) is CCKit's analogue of CXL.cache, and the prefetcher (§5.5) is CCKit's analogue of CXL.mem.
7Sets, ways — no, wait: NUMA and memory-mapped I/O▾

In a NUMA (non-uniform memory access) system, each socket has local memory that's faster for it to reach, but every socket can coherently access every other socket's memory, just at higher latency. CCKit's kernel module exposes FPGA memory to Linux user-space processes via mmap(), much like /dev/mem, so an application just sees another NUMA-remote memory region.

Now you're ready: this is why CCKit's CPU-FPGA table-sharing experiment (§5.4) can be directly compared to a plain 2-socket CPU-CPU NUMA baseline — they're structurally the same kind of system.
8Pipelining vs. spatial parallelism▾

A CPU cache controller is deeply pipelined — many operations in flight at once, overlapped in time, at high clock speed. CCKit instead uses spatial parallelism: dozens of simple, non-pipelined Directory Controller Units (DCUs) running at low clock speed but all at once, each responsible for a disjoint slice of address space.

Now you're ready: this is literally how CCKit matches CPU-class bandwidth at 1/6th the clock — 64 DCUs working in parallel rather than one fast pipeline (How It Works §4.3).
The whole story in one place

CCKit in a nutshell

The gap it fills, the trick that makes it fast, and the payoff.

As accelerators proliferate, the question of how deeply they should participate in cache coherence is still open — commercial protocols like CXL are converging toward it, but today's hardware is asymmetric: the CPU owns the one true home agent, and the device is a second-class caching client. That makes it hard to even ask research questions like "what should an accelerator's own home agent look like?" because no open, flexible, server-class hardware exists to experiment on.

CCKit answers this with a fully symmetric directory-based MESI protocol, implemented as an open-source FPGA toolkit on the Enzian research platform (a real 48-core ARM CPU + Xilinx FPGA, linked by the ECI interconnect at ~20 GiB/s, 230 ns round trip). Two components — the Directory Controller (DC) for FPGA-homed lines and the simpler Cache Controller (CC) for CPU-homed ones — expose a simplified MESI-state interface to application logic, hiding a formally-generated 79-state, 304-transition protocol machine underneath.

The key engineering trick for speed: rather than pipelining like a CPU controller (hard at 322 MHz vs. the CPU's 2 GHz), CCKit uses spatial parallelism — dozens of simple, serial Directory Controller Units (DCUs) each handling a disjoint slice of address space, together matching CPU-class throughput.

The payoff: read/write throughput and latency competitive with native CPU-CPU coherence; four demonstration use cases — a custom prefetcher (7.8→17.4 GiB/s), database materialized-view maintenance at interconnect speed (19.5 GiB/s), concurrent table access matching NUMA behavior, and synchronous CPU-FPGA RPC at 930 ns median — all while CCKit's full coherence stack (ECI+DC+MIGs) uses well under a third of FPGA resources (~17–30% of LUT/CLB/BRAM depending on resource type), leaving the majority of the FPGA for application logic.

🍯 Key takeaways

  • Symmetric means the FPGA has its own home agent — it can issue coherence messages, not just respond to them.
  • CCKit factors the protocol into a DC (FPGA-homed lines) and simpler CC (CPU-homed lines) with a shared simplified interface.
  • The full protocol — 79 states, 304 transitions, 25 message types — is generated offline from a formal specification, not hand-written.
  • Speed comes from spatial parallelism (64 simple DCUs) rather than pipelining, compensating for a 6× clock disadvantage.
  • Beyond caching: CCKit exposes clean / clean-invalidate / lock / unlock — enough to build application-specific coherence protocols on top.
  • CCKit's full stack (ECI+DC+MIGs) uses ~19% LUT, ~30% CLB, ~17% BRAM — leaving the majority of FPGA resources for the application. (The prefetcher's own small BRAM buffers are the one component that's genuinely <1%.)
Six everyday pictures

How to think about CCKit

Each stands alone. Every card ends with where it breaks.

The core idea · Symmetric coherence

Renter vs. co-owner

Asymmetric coherence makes the FPGA a renter: every use of "its own" apartment (local memory) technically needs the landlord's (CPU's) sign-off. Symmetric coherence makes it a co-owner of a duplex, with its own keys and its own say over its half — a neighbor relationship, not a tenancy.

Where it breaks: co-owners still must coordinate on shared areas — that coordination overhead (the 304-transition state machine) doesn't vanish, it's just now symmetric rather than one-sided.
Why so many states · Transient states

A busy intersection with no cameras

Four stable "textbook" states (MESI) is like four traffic-light phases. But real cars (messages) are already mid-turn when the light changes, and some arrive out of order. The 79 states CCKit generates are the catalog of every possible "car half-way through the intersection" situation — not a design choice, a necessity of a real, latent, reorder-prone network.

Where it breaks: an intersection eventually clears; cache-line conflicts under heavy sharing can recur continuously, which is why throughput (not just correctness) matters.
Making up for slow clock · Spatial parallelism

Four slow clerks beat one fast one

A single clerk who serves customers 6× faster beats four slow ones — unless you can line up four slow clerks at four separate windows, each with their own queue, serving simultaneously. CCKit's 64 DCUs are 64 slow (322 MHz), simple, non-pipelined clerks, each owning a disjoint slice of address space — together matching a single fast (2 GHz) CPU cache controller.

Where it breaks: clerks only help if customers spread evenly across windows. A workload hammering one address range (bursty, non-sequential writes) queues up at one DCU while others sit idle — exactly the random-access slowdown seen in §5.2.
Fast routing · Header/payload split

Sorting mail by envelope, not contents

A postal sorting facility routes letters by reading only the envelope (address), never opening them — the bulky contents ride a separate, slower conveyor and get reattached only at final delivery. CCKit's DCS does the same: the small, fixed-size header carries routing/state info through arbitration logic; the larger, variable payload sits in a BRAM table and is fetched only when a DCU actually needs to generate an AXI transaction.

Where it breaks: real mail sorting has no notion of "state" — the coherence header isn't just an address, it also carries dirty bits and message type that steer the protocol ROM, more like an envelope that also contains handling instructions.
Scaling to real apps · Application-specific protocol

A universal remote with a custom macro button

Standard universal remotes give you power/volume/channel — CXL-style primitives. CCKit also gives you a programmable macro button: wire up "on CPU-invalidate of line X, trigger a custom FPGA routine that touches lines Y and Z." The materialized-view use case (§5.6) is exactly this — a CPU write triggers an FPGA-side aggregate recompute, with the base table and view kept consistent without the CPU ever calling flush/fence.

Where it breaks: a universal remote's macro is pre-recorded and simple; CCKit's "macro" runs arbitrary FPGA logic reacting to real-time coherence traffic, so correctness depends on getting the application protocol's interaction with the base protocol right — not a trivial recording.
RPC over coherence · Doorbell-and-swap

Swapping keys instead of mailing a package

Instead of shipping an RPC request as a network packet, CCKit's RPC (§5.7) uses two cache lines, A and B, each exclusively owned by one side — like two neighbors who each hold a spare key to the other's door. Writing a request and then "requesting the key back" (a load-exclusive) is both the doorbell and the handoff — no separate signaling channel, just the coherence protocol itself doing double duty.

Where it breaks: real key-swapping has no notion of the CPU pipeline literally stalling until the key returns — that hardware stall (letting the core sleep) is the trick that makes this faster/cheaper than a polling-based software queue.
The full explanation

How it actually works

From architecture to protocol generation to the performance tricks.

1 · High-level architecture

CCKit splits physical address space between CPU and FPGA. For FPGA-homed lines, a Directory Controller (DC) tracks both the local protocol state and the state it believes the CPU holds. For CPU-homed lines cached by FPGA logic, a simpler Cache Controller (CC) handles the (no-directory-needed) client side. Neither actually stores the cache-line data — that's left to application logic connected via AXI, directly to FPGA DRAM/BRAM or to custom processing.

2 · The FPGA-side interface — more than a cache

Application logic sees: an AXI read/write interface (serving the CPU's upgrade/downgrade requests), a request-acknowledge interface to actively trigger clean (writeback) or clean-invalidate on the CPU's LLC, and lock/unlock to prevent the CPU from re-upgrading a line until the FPGA releases it. Critically, an app can infer protocol state from traffic alone: seeing an AXI read request means the line was invalid in the CPU's LLC; an AXI write means it was invalid or shared, never E/M.

💡
Why lock matters: after a clean, the FPGA is told the CPU's copy is now gone/clean — but without locking, the CPU could silently re-acquire and dirty the line again before the FPGA finishes using the data it just forced back. Locking makes the "FPGA has the authoritative copy" guarantee hold until the FPGA says otherwise.

3 · Generating a correct protocol — from rules to state machine

Hand-writing a coherence state machine is notoriously bug-prone. CCKit instead (1) collects the fixed rules of interaction (CPU-initiated upgrade/downgrade, DC-initiated forward-downgrade, no cancellation, timeout-based failure handling) and the interconnect's properties (deadlock-free, reliable delivery, but no ordering guarantee — n in-flight messages can arrive in any of n! orders); (2) enumerates all conflict-free pathways as state-equations; (3) widens the set to cover conflicts caused by latency; (4) widens again to cover every reordering (n messages → n! new equations); then (5) runs offline state-space exploration to collapse indistinguishable states and generate the final machine, stalling only requests (never responses, to avoid deadlock) when needed.

4 · Achieving full performance — spatial parallelism

The ThunderX-1's cache controller is deeply pipelined at 2 GHz; CCKit's FPGA logic runs at 322 MHz — >6× slower per cycle. Rather than fight this with pipelining (hard to verify, resource-hungry), CCKit uses many simple, serial, non-pipelined DCUs in parallel, each owning a disjoint address range. An example configuration uses 64 DCUs (split into odd/even Directory Controller Slices) to sustain 24 GiB/s — comfortably above the 20 GiB/s the ECI link actually delivers.

🌱
Each DCU is strictly one-transaction-at-a-time per type (read/write/coherence), but never stalls waiting on a resource — if an event can't be handled now, the DCU tries a different one, round-robin, with responses prioritized over requests. All parallelism comes from different DCUs working concurrently, not from overlapping work within one.

Follow the numbers

Worked examples

Four traces using the paper's real measurements.

① Decomposing CCKit's added read latency

LLC+DDR (2-CPU baseline) reads at 268 ns; DC+DDR (CPU-FPGA via CCKit) reads at 591 ns; DC+BRAM (isolating the DC from DRAM) reads at 454 ns. Where does the extra 323 ns go?

  1. Total CCKit overhead = 591 − 268 = 323 ns vs. a native 2-CPU system.
  2. Isolate the DC itself: DC+DDR − DC+BRAM = 591 − 454 = 137 ns is DRAM latency + AXI interconnect (the MIG controller and its known non-sequential inefficiency).
  3. The DC's own contribution: DC+BRAM − LLC+DDR = 454 − 268 = 186 ns is the directory/protocol-ROM logic plus crossing ECI.
  4. Check: 186 + 137 = 323 ns ✓ — matches the total.
🍯
Insight: roughly 57% of CCKit's added latency is the DC/ECI crossing itself (hard to shrink further without a faster FPGA clock), and 43% is the off-the-shelf DRAM controller — the paper explicitly flags the Xilinx MIG as the likelier target for future improvement.

② Clean-invalidate throughput bounds

DC+DDR clean-invalidate throughput is measured at 230×10⁶ cache lines/s, bounded below by 150×10⁶ CL/s (writeback bandwidth limit) and above by 322×10⁶ CL/s (1 request/cycle at 322 MHz). Where does CCKit land, and why isn't it at the ceiling?

  1. Lower bound (writeback-limited): 20 GiB/s ECI ÷ 128 B lines ≈ 150×10⁶ CL/s — the rate if every single line were dirty and had to be written back.
  2. Upper bound (issue-limited): 1 request/cycle × 322 MHz = 322×10⁶ CL/s — the rate if no line needed a writeback at all (CPU already evicted it).
  3. Measured 230×10⁶ CL/s falls between the two bounds, closer to the issue-rate ceiling than the writeback floor. The paper attributes this to an unpredictable fraction of lines already having been voluntarily evicted by the CPU before the FPGA's invalidate arrives — it doesn't claim that fraction can be read off directly by interpolating linearly between the two throughput numbers.
💡
The paper's conclusion generalizes: for any workload with a non-trivial fraction of dirty cached data, FPGA-initiated invalidation rate is set by writeback bandwidth, not by the DC's own issue rate — the DC is not the bottleneck.

③ Prefetcher speedup, by the numbers

The custom sequential prefetcher raises 4-thread read throughput from 7.8 GiB/s to 17.4 GiB/s using 8 parallel 8 KiB blocks.

  1. Speedup = 17.4 / 7.8 ≈ 2.23× — "nearly 2×" as the paper states.
  2. BRAM cost: 8 blocks × 8 KiB = 64 KiB total — the paper notes this is <1% of available BRAM on the VU9P.
  3. Mechanism: on an LLC miss, the prefetcher serves the hot (requested) line first via the direct DRAM path, while fetching the rest of its containing block in the background via 64-beat AXI bursts — latency-hiding, not just bandwidth-maximizing.
🍯
Insight: this is CCKit's CXL.mem story — the "memory controller" is entirely custom FPGA logic exploiting the application's known sequential pattern, something a fixed commodity memory controller can't do.

④ RPC latency vs. its own theoretical floor

Null RPC median latency is 930 ns, described as "two interconnect roundtrips." ECI round-trip latency (Figure 5) is 230 ns.

  1. Naive floor: 2 roundtrips × 230 ns = 460 ns.
  2. Observed: 930 ns — roughly 2× the naive floor.
  3. Why it's not a clean 2×: the paper doesn't give a hop-by-hop decomposition of the 930 ns RPC figure. The 230 ns ECI number is a raw link round trip for a simple read; each RPC round trip additionally involves DC directory lookups, forwarding/lock bookkeeping, and coherence-state transitions that a plain read never touches. The extra ~470 ns reflects that added protocol work, but the paper doesn't itself attribute it to a specific per-crossing figure — treat any such split as illustrative, not as the paper's own accounting.
💡
Even with that overhead, 930 ns for a fully synchronous, pipeline-stalling CPU↔FPGA call is fast enough that the paper argues it beats software polling-based approaches like FastForward, especially since the core can sleep while stalled rather than busy-poll.
Test yourself

Practice problems

Try before revealing. Each answer flags the misconception it checks.

Problem 1 · easy
Under CXL 1.1 (asymmetric), an FPGA wants to read a line from its own local DRAM that the CPU has never touched. Does this require an interconnect round trip?
Show answer
Yes, potentially — in the asymmetric model the CPU is the only home agent, so even "local" FPGA memory access to a line's coherence state may need to go through the CPU's tracking, unless a non-coherent bypass mode is used. This is exactly the overhead CXL added a special bypass mode to mitigate, and exactly what CCKit's symmetric DC avoids by letting the FPGA home its own lines.Misconception: that "the device's own memory" is automatically fast to access just because it's physically local. Under asymmetric coherence, physical locality and coherence-protocol locality are different things.
Problem 2 · medium
CCKit's DC+DDR read latency is 591 ns vs. the CPU-CPU baseline's 268 ns. A colleague claims "that gap is entirely because FPGAs are slow." Using the paper's isolated BRAM measurement, is this right?
Show answer
Not entirely. DC+BRAM (removing DRAM from the picture) measures 454 ns, so DRAM/AXI-interconnect effects (DC+DDR − DC+BRAM = 137 ns) account for less than half the total 323 ns gap. The DC logic itself (DC+BRAM − baseline = 186 ns) is actually the larger single contributor. "FPGAs are slow" conflates two separate, roughly comparable-sized costs: the coherence logic and the off-the-shelf DRAM controller.Misconception: treating "it's an FPGA" as a single monolithic explanation rather than decomposing overhead into its actual sources — a habit worth carrying into any heterogeneous-system latency analysis.
Problem 3 · medium
Why does CCKit need to enumerate n! reorderings for a coherence transaction involving n in-flight messages, rather than just handling messages as they arrive?
Show answer
Because the ECI interconnect guarantees reliable delivery but explicitly makes no ordering guarantee — with n messages in flight, any of the n! possible arrival orders is possible. A state machine that only handled the "expected" order would hit undefined behavior (or a protocol violation) the first time two messages were reordered — which real workloads with their inherent nondeterminism will eventually trigger. The n! expansion is how CCKit guarantees it has a defined transition for every order, not just the common one.Misconception: assuming message order roughly follows send order on a reliable link. Reliable delivery (nothing lost) and ordered delivery (arrives in-order) are independent guarantees — ECI provides only the first.
Problem 4 · hard
CCKit's DCUs are described as serial/blocking (one outstanding transaction at a time) yet the system still sustains ~20 GiB/s, matching a pipelined 2 GHz CPU controller. Explain the apparent contradiction.
Show answer
There's no contradiction — concurrency comes from a different axis. A CPU controller gets throughput by pipelining: overlapping stages of many transactions over time, on one fast clock. CCKit instead gets throughput by spatial parallelism: 64 separate, individually serial DCUs, each handling a disjoint address range, all working simultaneously. Total throughput is the sum across 64 slow-but-concurrent workers rather than one fast overlapped pipeline — the same total work, divided differently.Misconception: equating "serial/non-pipelined" with "slow in aggregate." A component can be serial internally and still contribute to high aggregate throughput if enough independent copies run at once.
Problem 5 · medium
In the RPC protocol (§5.7), why are exactly two cache lines (A and B) needed instead of one?
Show answer
Each line is held exclusively by one side at quiescence — A by the CPU (to hold arguments), B by the FPGA (to hold the eventual result/doorbell). A single shared line can't be simultaneously exclusive to both sides (that would violate SWMR), so the protocol needs one line per direction of "ownership," with roles swapping after each call. Using one line would force the CPU to give up exclusive ownership just to write its own request, losing the ability to write locally without a round trip.Misconception: thinking of "shared state" as something both parties can write to freely. SWMR means true concurrent write access never exists in MESI — the two-line design works around this, it doesn't violate it.
Problem 6 · easy
CCKit reports <1% extra FPGA area for the full ECI+DC+MIG configuration's resource overhead, similar in spirit to UCP's <1% cache-area monitor overhead. Are these numbers measuring the same kind of thing?
Show answer
No — CCKit's number is FPGA logic resources (LUT/CLB/BRAM utilization, ~19–30% depending on resource type, "leaving 70% for applications" is the more precise framing, not literally <1%). Always check which specific resource and configuration a percentage refers to; "small overhead" claims in hardware papers usually bundle several different units (LUTs, BRAM, power, latency) that don't automatically agree.Misconception: assuming a single percentage number generalizes across all resource types (LUT vs. BRAM vs. CLB) or across all configurations (bare DC vs. full DC+MIG).
Quick answers

Frequently asked questions

Tap any to expand.

Q1Is CCKit trying to compete with CXL?▾
No — the paper is explicit that CCKit is a research vehicle, not a commercial competitor. It exists to let researchers explore symmetric-coherence applications before CXL 3.0 hardware (which plans symmetric coherence) becomes widely available, and to generate evidence that can inform future interconnect standards.
Q2Does CCKit cache the data itself?▾
No. Neither the DC nor the CC stores cache-line data — only directory/protocol state. Whether and how to cache data is left entirely to application logic, which connects via AXI to its own DRAM, BRAM, or further processing logic.
Q3What hardware does CCKit actually run on?▾
The Enzian research platform: one socket with a 48-core, 2 GHz Marvell ThunderX-1 ARMv8 CPU (16 MiB shared LLC, 128 B lines), the other with a Xilinx VU9P UltraScale+ FPGA, connected by the Enzian Coherent Interconnect (ECI) at ~20 GiB/s achievable, 230 ns round trip.
Q4Why 79 states instead of the textbook 4 (MESI)?▾
The 4 MESI states are only the stable states. Real systems need intermediate states to track messages that are in-flight, conflicting, or arriving out of order due to the interconnect's lack of ordering guarantees. CCKit generates all of them offline from a formal specification rather than hand-coding them.
Q5How does CCKit get FPGA-class throughput at 1/6th the clock speed of the CPU?▾
Spatial parallelism, not pipelining: many simple, non-pipelined Directory Controller Units (e.g., 64) each handle a disjoint slice of address space concurrently. Aggregate throughput sums across all of them rather than relying on one fast, deeply overlapped pipeline.
Q6What's the difference between "clean" and "clean-invalidate"?▾
Clean forces writeback of a dirty line from the CPU's LLC without evicting it (CPU keeps a clean copy). Clean-invalidate does the same writeback but also invalidates the CPU's copy entirely, guaranteeing the FPGA alone holds the current data afterward.
Q7Why does the FPGA need to "lock" a cache line at all?▾
After a clean/clean-invalidate, the FPGA needs a guarantee that the CPU won't silently re-acquire and modify the line while the FPGA is using the freshly-fetched data. Locking prevents CPU upgrades until the FPGA explicitly unlocks, preserving the "FPGA has the authoritative copy" invariant.
Q8Does CCKit require changes to the Linux kernel's memory management?▾
CCKit adds a loadable kernel module exposing FPGA address space as a device file (`mmap()`-able like `/dev/mem`), but deliberately bypasses standard in-kernel page-mapping interfaces rather than deeply integrating with Linux's heterogeneous-memory support, which the authors found insufficient for CCKit's needs.
Q9What's the biggest performance bottleneck in the current implementation?▾
Non-sequential (random) DRAM access via the Xilinx MIG memory controller IP, which the paper notes is known to be inefficient on non-sequential patterns — compounded by the CPU LLC's address scrambler turning even sequential accesses into pseudo-random patterns at the DRAM level.
Q10Is CCKit's RPC mechanism faster than software approaches like FastForward?▾
The paper argues yes, in latency terms: CCKit's null RPC requires two interconnect roundtrips and achieves 930 ns median latency using hardware pipeline stalls, which software message-passing queues can't replicate as cheaply — plus the CPU core can sleep while stalled, rather than busy-poll.
Q11Can CCKit scale beyond a 2-node (1 CPU + 1 FPGA) system?▾
The current implementation targets 2-node systems as a deliberate scope limitation; the paper frames rack-scale, multi-node symmetric coherence (and interoperability across differing protocols) as future work and an open research question that CXL 3.0-class standards are also still working out.
Q12Is CCKit open source?▾
Yes — the paper states the entire toolkit, along with all use-cases and benchmarks described, is publicly available as open source (hosted on the ETH GitLab, per the paper's footnote).

Related papers

A Primer on Memory Consistency and Cache Coherence (2nd ed.) medium

Nagarajan, Sorin, Hill, Wood · Synthesis Lectures, 2020

The textbook CCKit itself cites for symmetric/asymmetric terminology and directory-protocol fundamentals (refs [73],[74]).

Enzian: An Open, General CPU/FPGA Platform medium

Cock et al. · ASPLOS 2022

The host platform CCKit's first implementation runs on — covers the ECI interconnect and shell in more depth.

TPP: Transparent Page Placement for CXL-enabled Tiered Memory medium

Maruf et al. · ASPLOS 2023

A CXL-based tiering system cited as related work — concerned with near-NUMA latency rather than coherence, contrasted with CCKit's focus.

Pond: CXL-based Memory Pooling Systems medium

Li et al. · ASPLOS 2023

Another CXL-adjacent disaggregation system cited alongside TPP as sharing CCKit's broader motivation but not its coherence focus.

Cohmeleon: Learning-Based Orchestration of Accelerator Coherence hard

Zuckerman, Giri, Kwon, Mantovani, Carloni · MICRO 2021

Shows the best coherence protocol varies by accelerator and workload at runtime — directly motivating CCKit's flexible, customizable approach.

Crossing Guard: Mediating Host-Accelerator Coherence Interactions hard

Olson, Hill, Wood · ASPLOS 2017

An intermediate-interface approach for heterogeneous coherence that CCKit's DC/CC abstraction can be compared against.
