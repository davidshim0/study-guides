Leave the weights on the GPU, and share the scratch space between iterations

A GPU is normally handed to one deep learning job at a time. Salus puts a single execution service between the frameworks and the GPU, keeps every admitted job's small persistent memory resident, and switches or packs jobs at iteration boundaries, where their large scratch memory is free anyway.

Before you begin

Share one GPU among many deep learning jobs by exploiting how their memory behaves

A 2020 MLSys paper from the University of Michigan: a user-level execution service that sits under TensorFlow, gives the GPU two primitives it lacks (fast job switching and memory sharing), and uses them to build alternatives to first-in first-out (FIFO) scheduling such as preemptive shortest-remaining-time-first, packing and fair sharing.

⚡ TL;DR

  • Problem: a GPU is usually allocated to one job at a time. Clusters therefore run deep learning (DL) jobs first-in first-out, so a short job waits behind a long one (head-of-line blocking), and a job that uses only part of the GPU's memory still holds all of it. Preempting a job means copying its state off the GPU, which takes too long to do often.
  • Observation: a training job's memory is periodic. Every iteration allocates large ephemeral scratch memory (layer outputs) and frees it all at the end; only the persistent memory (model parameters plus framework bookkeeping) lives across iterations. Persistent memory is small: 110.9 MB (googlenet_25) to 822.2 MB (resnet152_75), against peaks as high as 13.8 GB on a 16 GB P100.
  • Primitive 1, fast job switching: keep every admitted job's persistent memory on the GPU and switch jobs only at iteration boundaries, when the departing job's ephemeral memory is already freed. Nothing is copied; a switch waits at most for the running iteration to end ("tens of milliseconds to a few seconds").
  • Primitive 2, memory sharing with GPU lanes: persistent memory grows from one end of GPU memory, ephemeral memory from the other; the ephemeral region is cut into lanes. Jobs in one lane take turns; lanes run in parallel on separate GPU streams. A safety condition (sum of persistent memory + sum of lane sizes ≤ capacity) keeps the two regions from colliding, so each lane always has room for its current iteration (the paper: "at least one job in the lane can proceed"), and lanes defragment for free at iteration boundaries.
  • Results (TensorFlow 1.5, two P100s): preemptive SRTF cuts average job completion time 3.19× versus FIFO (170.6 → 53.4 min) on a 100-job trace; packing 300 hyper-parameter jobs cuts makespan 2.38× for superres_128 but only 1.07× for resnet50_50; 42 inference models fit on 1 GPU instead of 42 (6 with NVIDIA's Multi-Process Service, MPS). Per-iteration overhead is under 10% except for two models with heavy CPU work (vae 1.81× and superres 1.83×, values printed on Figure 12).
  • Scope: a mechanism paper. The policies (PACK, SRTF, FAIR) are demonstrations; SRTF assumes job durations are known; only TensorFlow is integrated.

Quick glossary
GPU (graphics processing unit)A processor chip with dozens of independent compute units, each running many threads in lockstep, attached to its own large, fast memory and to the host CPU over a bus. The CPU sends it work; it does not run an operating system of its own.
Device memoryThe GPU's own memory (16 GB of HBM2, stacked high-bandwidth DRAM, on the paper's P100), separate from the host's DRAM. Data must be copied into it over the bus before a kernel can use it.
KernelA function compiled for the GPU and launched by the CPU to run on many GPU threads at once, for example one matrix multiplication or one convolution layer. A DL iteration is a sequence of hundreds of kernel launches.
StreamAn in-order queue of GPU operations (kernel launches, copies) inside one process's GPU context. Operations in one stream run one after another; operations in different streams may run at the same time.
GPU contextThe per-process state the GPU driver keeps for a program using the GPU: its GPU address space, loaded kernels and allocations. Kernels from different contexts do not run concurrently on GPUs of this era; the GPU switches between contexts (general knowledge).
NVIDIA MPS (Multi-Process Service)An NVIDIA server process that funnels the GPU work of several client processes into one shared context, so their kernels can run concurrently without context switches. It does not move or manage their memory (general knowledge).
Iteration (training step)One pass of a training loop: run a batch of samples forward through the model, compute gradients backward, and update the parameters. A training job is thousands of identical iterations.
Batch sizeThe number of samples (for example images) processed in one iteration. It sets how much intermediate data an iteration creates; the paper names workloads by model and batch size, as in alexnet_25.
Persistent memoryGPU memory a job keeps across iterations: model memory (parameters) plus framework-internal memory (bookkeeping, input pipeline buffers). In the paper it is a few hundred MB per job.
Ephemeral memoryGPU memory a job allocates during one iteration (layer outputs, temporaries) and releases before the next. It is most of a job's peak usage.
Iteration boundaryThe moment between two iterations of one job, when its ephemeral memory has been released and only its persistent memory remains: the trough of its memory trace.
Salus execution serviceA single process that owns the GPU and runs the GPU work of every DL job on the machine; frameworks send it graphs and iteration requests instead of using the GPU directly.
AdaptorThe Salus-specific code inside a DL framework (TensorFlow here) that makes the Salus service look like one more computation device, so user scripts run unchanged.
GPU laneA contiguous slice of the ephemeral region of GPU memory, sized for the largest ephemeral need of the jobs assigned to it, plus the rule that those jobs run their iterations one at a time in it. Different lanes run in parallel on different streams.
Safety conditionSalus's admission invariant: the persistent memory of all admitted jobs plus the sizes of all lanes must not exceed GPU memory, so every lane can always finish an iteration.
Head-of-line (HOL) blockingThe delay a short job suffers when it must wait in a first-in first-out queue behind a long job that arrived earlier.
JCT and makespanJob completion time (JCT) is one job's time from arrival to finish; makespan is the time from the first arrival until the last job of a set finishes.
SRTFShortest remaining time first: a preemptive scheduling rule that always runs the job with the least remaining work, which minimizes average completion time when durations are known.
Short primers (tap to open)
1What a GPU is, from first principles▾

A CPU core runs one instruction stream fast. A GPU runs tens of thousands of simple threads at once, grouped into streaming multiprocessors (SMs); the P100 used in the paper has 56 SMs and 3,584 single-precision arithmetic units (general knowledge, not in the paper). It is built for work where the same operation applies to many numbers, which is what matrix multiplication and convolution are.

The GPU sits on a bus (PCI Express, PCIe) next to the CPU and has its own device memory: 16 GB of HBM2 on the P100, with roughly 730 GB/s of internal bandwidth, against about 16 GB/s per direction over PCIe 3.0 x16 (general knowledge). Data crosses the bus slowly and is used on the GPU quickly, so a program puts everything the GPU will touch into device memory and leaves it there.

The CPU drives the GPU through NVIDIA's CUDA runtime (CUDA is NVIDIA's GPU programming platform) by launching kernels: it puts a request "run this function over this grid of threads, with these pointers" into a stream, and the GPU executes the stream's requests in order. The CPU does not wait; it can queue many launches ahead. Copies between host and device memory go into streams too.

Now you're ready: a DL job on a GPU is a CPU program that queues hundreds of kernels per iteration into streams, operating on tensors that must already sit in device memory.
2Why a GPU is hard to share: contexts, time slicing, spatial sharing, and no paging▾

Each process that uses the GPU gets a context. On GPUs of this generation, kernels from different contexts do not run at the same time: the GPU time-slices between contexts, and a switch has to drain or save the running work (general knowledge). An administrator can also put the GPU in an exclusive mode that allows only one context at all, which is how clusters typically hand out GPUs.

Spatial sharing means running kernels of two jobs at the same moment on different SMs. That happens only within one context, using different streams (general knowledge). NVIDIA's MPS gets there for separate processes by merging them into one server context. Salus gets there by being the one process that owns the GPU.

Memory is the harder part. A CPU's virtual memory can page: if a process touches memory that is not present, the OS evicts something to disk and brings the page in. Classic GPU allocations (cudaMalloc) are fixed device memory with no paging, so if two jobs together ask for more than 16 GB, one allocation simply fails and the job usually crashes. NVIDIA's Unified Memory can oversubscribe by migrating pages over the bus on faults, but the paper calls it "too slow to use": in Figure 13, static partitioning with MPS plus memory overcommit took 698.45 s of average job completion time versus about 88 s without overcommit.

Now you're ready: sharing a GPU means solving two problems the hardware leaves open, who runs now (time) and who holds which memory (space), without being able to page.
3Deep learning training and inference, and where the memory goes▾

A neural network is a chain of layers, each a function with learned parameters (weights). Training repeats an iteration: the forward pass feeds a batch through the layers and keeps every layer's output (the activations) because the next step needs them; the backward pass walks the layers in reverse computing gradients, and each layer's activations can be freed once its gradient is done; the update adjusts the parameters using the gradients and the optimizer's own state (for example momentum).

So memory has two kinds of contents. Parameters and optimizer state live for the whole job: the paper's model memory. Activations, gradients and temporaries grow with the batch size and exist only during the iteration: the paper's ephemeral memory. With batch sizes in the tens, activations dwarf the parameters, which is why resnet152_75 can peak near 14 GB while its persistent memory is 822.2 MB (general knowledge for the mechanism; the numbers are the paper's).

Inference (serving a trained model) runs only the forward pass, for one request or a small batch, and can free each activation as soon as the next layer has consumed it. Its ephemeral memory is small and its iterations last milliseconds, so what matters is request latency, not throughput.

Now you're ready: "persistent" and "ephemeral" in this paper are exactly "parameters and their state" versus "activations and temporaries".
4Why a job's memory use is periodic▾

A framework like TensorFlow 1.x builds a computation graph once and then executes the same graph every iteration, on a batch of the same shape. The same kernels run in the same order and request the same tensor sizes at the same points, so memory rises and falls in the same pattern each time (the paper: "DL jobs go through the same sequence of operations and memory allocations in each iteration").

Within an iteration the shape is a sawtooth: usage climbs during the forward pass as activations accumulate, peaks around the start of the backward pass, and falls as activations are released (general knowledge, consistent with the TensorFlow trace in the paper's Figure 2, which rises sharply and declines gradually). At the end, only persistent memory remains: the trough. In Figure 2 (resnet101_75 on a P100) the cycle repeats about every 0.6 s, between roughly 0.3 GB and 8.8 GB (read off the plot).

The first iteration or two look different: higher spikes (about 11 GB in Figure 2) while the framework sets up and tries alternatives (general knowledge for the cause; the spike is visible in the figure).

Now you're ready: the trough between iterations is a moment, repeated every fraction of a second, when a job can be paused with almost nothing in flight.
5How TensorFlow manages GPU memory▾

Calling the driver's allocator for every tensor would be slow, so frameworks run their own allocator on top of a large region of device memory. TensorFlow 1.x by default grabs nearly all free GPU memory when a session starts and carves tensors out of it with a best-fit allocator that splits and coalesces chunks (the "BFC" allocator); an option makes it grow the region on demand instead (general knowledge, not in the paper).

Two consequences matter here. First, a default TensorFlow process looks like it uses the whole GPU even if it needs 1 GB, so a second job cannot start beside it: GPU memory is effectively allocated per job. Second, inside that region, allocations of very different sizes and lifetimes interleave, so free memory can be scattered in pieces too small for the next large request: fragmentation, which the paper says gets worse when several jobs' iterations allocate at the same time.

Salus replaces this per-job ownership: the framework's allocations go to the Salus service, which places persistent ones in one region and ephemeral ones in a lane.

Now you're ready: the memory manager in Salus is a shared replacement for each framework's private allocator, with two regions instead of one heap.
6Cluster scheduling words: FIFO, HOL blocking, SRTF, makespan, fairness▾

A FIFO scheduler runs jobs to completion in arrival order. If a 3-hour job arrives one second before a 5-minute job, the short job's completion time is 3 hours and 5 minutes: head-of-line blocking. SRTF runs whichever job has the least remaining work and preempts the current job when a shorter one arrives; with known durations it minimizes the average completion time (a classic result, general knowledge). It needs cheap preemption and can starve long jobs.

Makespan is when the last job of a batch finishes; it matters when results are useful only as a set, as in hyper-parameter search, where hundreds of variants of one model train and the best is chosen. Packing several jobs on one device can cut makespan if they do not fully use it alone. Fair sharing gives concurrent jobs equal service over time, at the cost of finishing each later than it would alone.

Before Salus, GPU cluster schedulers that time-share (Gandiva, Tiresias) "enforce sharing over many minutes due to high switching overhead": a switch means checkpointing a job out of GPU memory and restoring it, which in Gandiva takes seconds ("second-scale suspend/resume").

Now you're ready: every policy in the paper needs either cheap preemption (SRTF, FAIR) or safe co-location (PACK); Salus provides both.
The whole story in one place

Separate what a job keeps from what it throws away

The GPU hardware and the frameworks stay the same. A service in between decides who runs and where their memory goes.

In 2020 a GPU in a cluster was handed to one deep learning job at a time. That makes two things expensive. To preempt a job, a scheduler has to push its state out of GPU memory and load it back later, so schedulers either run jobs first-in first-out and accept head-of-line blocking, or time-share on a scale of minutes. And a job that needs a fraction of the 16 GB still holds the whole device: the paper finds that for memory-intensive training jobs "the average GPU memory utilization is often less than 50%", and inference models with low request rates each sit on their own GPU.

The paper's starting point is a measurement of 15 models (45 workloads). Peak memory varies widely across jobs, from 35 MB (vae) to 13.8 GB (resnet152). Within a job, every iteration repeats the same sawtooth: memory climbs to a peak and falls back to a trough. The trough is the persistent memory, model parameters plus framework bookkeeping, and it is small: 110.9 MB to 822.2 MB. Everything above it is ephemeral scratch that is freed at the end of each iteration.

That split gives the first primitive, fast job switching. Keep every admitted job's persistent memory on the GPU permanently, and switch from one job to another only at an iteration boundary, when the departing job's scratch is already gone. A switch then copies nothing; the next job's iteration simply starts. Copying even the parameters alone over the bus would cost more than an entire inference request for some models (Figure 4), which is why the paper rules copying out.

The second primitive is memory sharing through GPU lanes. Persistent memory is allocated from one end of GPU memory and ephemeral memory from the other, like a stack and a heap. The ephemeral side is divided into lanes. Jobs assigned to the same lane take turns, one iteration at a time; different lanes run at the same time on separate GPU streams. Admission obeys a safety condition: the persistent memory of all jobs plus the sizes of all lanes must fit in the GPU. Since the GPU cannot page, this is what keeps every lane able to finish its current iteration (the paper: "at least one job in the lane can proceed"), and because a lane is empty at every iteration boundary, lanes can be moved and resized there without copying anything.

All of this runs in one user-level process, the Salus execution service, which owns the GPU and executes every job's graph; a small adaptor inside TensorFlow makes it look like another device, so user scripts do not change. On top of the two primitives the authors write three short policies. Preemptive SRTF cuts average completion time on a 100-job trace from 170.6 to 53.4 minutes (3.19×). PACK cuts the makespan of 300 superres_128 hyper-parameter jobs 2.38×, but only 1.07× for resnet50_50 where compute is the limit, and Salus holds 42 low-traffic inference models on one GPU (the paper does not name the policy used for that experiment). FAIR rebalances throughput within seconds of a job arriving. The price is an execution engine that is slower than TensorFlow's own for models with heavy CPU work (up to 1.83× per iteration), and a scheduler that needs to know each job's memory needs and, for SRTF, its duration.

🍯 Key takeaways

  • DL memory has two lifetimes: a small persistent part (parameters, bookkeeping) and a large ephemeral part that is freed every iteration.
  • Fast switching = never evict persistent memory, and switch only at iteration boundaries; no data moves.
  • GPU lanes = a two-ended layout plus "one iteration at a time per lane", so the sum of lane sizes bounds ephemeral use and every lane can finish its iteration without paging.
  • Iterations, not kernels, are the scheduling unit: fine enough (tens of ms to seconds) and free of the overhead the authors found in a kernel-level prototype.
  • Policies are small programs on the primitives: SRTF 3.19× better average JCT than FIFO; PACK 1.07× to 2.38× makespan; 42 inference models on 1 GPU.
  • The limits: the service's own engine costs up to 1.83× per iteration for CPU-heavy models, packing does not create compute, and the policies assume known memory needs and durations.
Six everyday pictures

How to think about Salus

Each stands alone. Every card ends with where the picture stops being true.

Persistent versus ephemeral memory · fast switching

A shared kitchen with lockers and one big counter

Each cook keeps knives and spices in a small locker that never moves (persistent memory). The big counter is for preparing one dish and is wiped clean when the dish goes out (ephemeral memory). Handing the counter to another cook between dishes costs nothing: no one carries their locker home. Under the old rule each cook had to pack up the whole kitchen before the next one came in.

Where it breaks: a cook can be replaced only between dishes, never halfway through one; Salus switches only at iteration boundaries, so a job with multi-second iterations makes others wait that long (M8, M9).
GPU lanes · serial within, parallel across

Pool lanes where only one swimmer at a time may be in the water

The pool (the ephemeral region) is divided into lanes. Each lane has a queue of swimmers who take turns, one length each (one iteration). Different lanes swim at the same time. A lane is as wide as the widest swimmer assigned to it, so everyone in it always fits, and the lanes together never exceed the pool.

Where it breaks: a real lane holds several swimmers at once; a Salus lane holds exactly one iteration, and while a small job swims, the rest of its lane's width sits unused (M13).
Persistent and ephemeral regions growing from opposite ends

A shelf filled from both ends

Reference books (persistent) are shelved from the left; library loans of the day (ephemeral) from the right. The free space is one gap in the middle, so the shelf never has a book that cannot fit merely because the free space is in the wrong place. The only question is whether the total fits, which the librarian checks before accepting a new borrower: the safety condition.

Where it breaks: a program's stack and heap find out they collided only when it happens; Salus admits a job only if its declared sizes already fit, so it needs to know each job's persistent and peak ephemeral memory in advance (M12, M14).
Lane auto-defragmentation

Food trucks that leave the lot every evening

A lot rents spaces to food trucks that drive away each night. When one truck stops coming, nobody has to tow the others to close the gap: tomorrow morning they simply park next to each other. Ephemeral memory is the same: each lane is empty at every iteration boundary, so a lane below a departed job just starts its next iteration higher up, with no copying (Figure 6b).

Where it breaks: the persistent region holds parked cars that never leave; holes there from finished jobs are not cleaned up by this trick, and the paper does not describe compacting them (M15).
SRTF with cheap preemption

A photocopier where the person with one page cuts in

Someone copying a 500-page thesis pauses at the end of a chapter so a person with one page can copy it, then resumes. Everyone's average wait drops sharply; the thesis finishes a little later. This works only because pausing at a chapter boundary is free: the thesis stays on the machine's tray. That is SRTF on Salus: 3.19× lower average completion time than FIFO.

Where it breaks: the copier queue knows each job's page count; SRTF in the paper simply assumes known durations, and every paused job keeps its persistent memory on the GPU, so too many paused jobs can block the next short one from being admitted (M18; this guide's reading of an admission rule the paper states only briefly).
Scheduling granularity: iterations, not kernels

Booking a meeting room by the meeting, not by the sentence

You could let teams take turns in a meeting room sentence by sentence, which is fair to the second but means a receptionist must approve every sentence and nobody can prepare their next slide in advance. Booking by the meeting keeps the receptionist idle most of the time. Salus's authors built the sentence-level version (kernel-level switching) and found "too much overhead for little gain".

Where it breaks: meetings have fixed lengths; DL iterations range from tens of milliseconds to seconds, so a job's turn length depends on its model and batch size, not on the scheduler (M9).

What a DL job keeps in GPU memory
  • Model memory: the parameters and, for training, the optimizer's state for them. Fixed in size for the life of the job. Persistent.
  • Framework-internal memory: the framework's own bookkeeping and buffers of the input pipeline. Small allocations that "often persist across iterations". Persistent.
  • Ephemeral memory: activations, gradients and temporaries of the current iteration. Large, released at the end of each iteration.

Without Salus each TensorFlow process allocates all of these from its own region of device memory, in its own GPU context, and nothing else can use that memory until the process exits. With Salus a single service owns the GPU; it places persistent allocations of all jobs in one region and ephemeral allocations in lanes, and launches every job's kernels itself.

1 · What is wasted when a GPU belongs to one job

With exclusive allocation, preempting a job means getting its whole state off the GPU, so clusters run FIFO and suffer head-of-line blocking, or time-share in minutes (M1). Memory goes unused in two ways: jobs have very different peaks, from 35 MB to 13.8 GB (M2), and within a job usage swings every iteration between a high peak and a low trough (M3), whose floor is the small persistent memory (M4). Static partitioning and MPS cannot recover the swing, and kernel-level time slicing was designed for programs with a few kernels (M5).

2 · Fast job switching

Copying a job's GPU state out and in takes longer than an inference request for some models (M6). But a job's memory is of three kinds, and the persistent kinds (model, framework-internal) are much smaller than the ephemeral kind (M7). So Salus keeps every admitted job's persistent memory resident and switches only at iteration boundaries, where the ephemeral memory is already free (M8). It chose iterations over kernels as the unit after a kernel-level prototype cost too much (M9).

3 · One service for all jobs

Salus runs as a single process that consolidates all GPU access. Inside TensorFlow an adaptor turns Salus into a virtual device; each job becomes a session in Salus, which requests a lane, receives iterations and runs them on the GPU (M10). Because the service runs the jobs' graphs with its own execution engine, it also runs their CPU operations, which is the source of most of its overhead (M11).

4 · Memory sharing with GPU lanes

Persistent memory is allocated from one end of GPU memory and ephemeral memory from the other (M12). The ephemeral region is divided into lanes; iterations within a lane run one at a time and lanes run in parallel on GPU streams (M13). Admission keeps the safety condition, persistent sum plus lane sum at most the capacity (M14). Lanes are empty at iteration boundaries, so they are moved and resized there for free (M15). Algorithm 1 picks a lane for an arriving job: a new lane if it fits, else the best existing lane that is big enough, else grow the smallest lane that can be grown, else wait (M16).

5 · Policies and results

PACK puts jobs in separate lanes to raise utilization (M17); SRTF preempts long jobs for short ones (M18); FAIR time-shares jobs in a lane with equal service (M19). On a 100-job trace SRTF improves average JCT 3.19× over FIFO; PACK improves hyper-parameter makespan 2.38× for superres_128 and 1.07× for resnet50_50; 42 inference models need 1 GPU instead of 42 (MPS: 6). Overhead is under 10% per iteration except for vae and superres (about 1.8×). Section F walks through every figure.

Background and context
  • Peifeng Yu and Mosharaf Chowdhury, University of Michigan (SymbioticLab). Proceedings of the 3rd MLSys Conference, Austin, TX, 2020. 10 pages plus appendices; code at github.com/SymbioticLab/Salus (Apache-2.0).
  • Setting: GPU clusters for DL training and model serving, where the "minimum granularity of GPU allocation today is often the entire GPU". Cluster managers cited: Gandiva (OSDI 2018), Tiresias (NSDI 2019), Kubeflow, Mesos, YARN, Kubernetes.
  • Platform: TensorFlow 1.5.0 and CUDA 8.0 on an Intel Xeon E5-2670 with two NVIDIA Tesla P100 GPUs (16 GB each) on CloudLab. PyTorch is used only to show that memory traces look similar (Figures 2 and 14).
  • Prior GPU sharing cited: static partitioning, NVIDIA MPS, TensorRT Inference Server and Samanta et al. (inference only), driver-call interception with kernel time slicing (Pai et al., Ravi et al., Chimera), new GPU programming APIs (Suzuki et al., Pagoda, G-NET).
The problem

Exclusive GPU allocation causes two inefficiencies the paper names: "coarse-grained, one-at-a-time GPU allocation model hinders the scheduling ability of GPU cluster managers" (preemption is costly, so FIFO and HOL blocking), and "not all DL jobs can fully utilize a GPU all the time" (average memory utilization "often less than 50%" for memory-intensive jobs; idle serving models each occupy a GPU).

The result

Two primitives, fast job switching and memory sharing via GPU lanes, built into a single execution service transparent to TensorFlow users, with three demonstration policies. Abstract: "Salus can improve the average completion time of DL training jobs by 3.19×, GPU utilization for hyper-parameter tuning by 2.38×, and GPU utilization of DL inference applications by 42× over not sharing the GPU and 7× over NVIDIA MPS with small overhead." The 2.38× is a makespan ratio and the 42× and 7× are GPU-count ratios; Figure 10 supports 6× over MPS, not 7× (F12, Class Prep C7).

Mechanisms in dependency order
  1. Characterize the waste (M1 to M5): exclusive allocation, heterogeneous peaks, iteration-periodic usage, small persistent memory, and why existing sharing fails.
  2. Make switching cheap (M6 to M9): copying is too slow; three allocation kinds; keep persistent memory resident; switch at iteration boundaries, not kernels.
  3. Put one service in charge (M10, M11): adaptor, sessions, iteration scheduler, memory manager, own execution engine.
  4. Share memory safely (M12 to M16): two-ended layout, lanes, safety condition, free defragmentation, lane assignment.
  5. Write policies on top (M17 to M19): PACK, SRTF, FAIR; then measure (F).
The central trade-offs
  • Switch granularity versus overhead: "there is a tradeoff between maximum utilization and efficiency for a given scheduling granularity." Iterations are coarse enough to be cheap and fine enough (tens of ms to seconds) to be useful.
  • Resident state versus capacity: keeping every admitted job's persistent memory on the GPU makes switches free but spends memory on jobs that are not running, and bounds how many jobs can be admitted.
  • Safety versus packing density: lanes are sized for the largest ephemeral peak of their jobs and iterations in a lane never overlap, which rules out out-of-memory errors and deadlock without paging, but leaves memory idle whenever a smaller job is the one running.
  • Transparency versus speed: a separate execution service lets scripts run unchanged, but it re-implements execution, including CPU operations, and costs up to 1.83× per iteration for some models.
Effect of changes (whole design)
  • If iterations are not uniform (dynamic shapes, variable sequence lengths, general knowledge), peak ephemeral memory changes from iteration to iteration and a lane sized from one measurement can overflow (inference; see M13, M14).
  • If the bus were much faster (NVLink-class, general knowledge), Observation 1 weakens and swapping persistent memory becomes an option for training, though Salus's design would still avoid it (inference; see M6).
  • If GPUs gained fast demand paging, the safety condition could be relaxed into an overcommit policy like ESX's, at the risk of thrashing (inference; the paper's Unified Memory test was 698.45 s versus about 89 s).
  • If the model does not fit beside others (persistent memory near the GPU's capacity, as with large language models, general knowledge), keeping all admitted jobs' persistent memory resident leaves no room; switching would have to copy after all (inference).

M1 · Exclusive GPU allocation and its two costs

TL;DR
Problem"each GPU can only be allocated to exactly one application", so preemption needs a full purge of GPU state, and unused memory cannot be lent.
Mechanism (status quo)Cluster managers give whole GPUs to jobs and schedule them non-preemptively (FIFO), or preempt by checkpoint and restore with "large performance overhead".
Trade-offSimple, isolated, efficient hardware use per job, in exchange for HOL blocking, minute-scale time sharing, and idle memory.
Breaks whenShort jobs queue behind long ones; jobs use a fraction of GPU memory; many low-traffic inference models each need a GPU; hyper-parameter search launches hundreds of small jobs at once.
Key points
  • "While such exclusiveness in accessing a GPU simplifies the hardware design and makes it efficient in the first place, it leads to two major inefficiencies."
  • First: "a running DL job must fully be purged from the GPU before another one can start, incurring large performance overhead. As such, GPU clusters often employ non-preemptive scheduling, such as FIFO ... which is susceptible to the head-of-line (HOL) blocking problem; or they suffer large overhead when using preemptive scheduling."
  • Footnote 1: "It is possible to forcibly run multiple processes on the same GPU, but that leads to high overhead compared to exclusive mode."
  • Second: for memory-intensive training jobs "the average GPU memory utilization is often less than 50% ... due to varied memory usage over time and between iterations. Similar patterns can also be observed in compute-intensive training jobs."
  • Serving: "the ability to hold many DL models on the same GPU when request rates are low can significantly cut the cost by decreasing the number of GPUs needed in serving clusters."
  • Hyper-parameter tuning, "pre-training": "One exploration task usually generates hundreds of training jobs in parallel, many of which are killed as soon as they are deemed to be of poor quality", and "the result is useful only after all jobs are finished", so makespan matters.
How it works, step by step: HOL blocking on an exclusive GPU
  1. t = 0: a training job L that needs 180 minutes of GPU time starts on GPU 0 (illustrative numbers). TensorFlow by default reserves nearly all of the GPU's 16 GB in its own context (general knowledge).
  2. t = 1 min: a 5-minute job S arrives. GPU 0 is exclusively L's. FIFO puts S in the queue.
  3. Preempting L instead would mean checkpointing its state to host memory or disk, killing the process, and later restarting it: Gandiva's "second-scale suspend/resume", so a scheduler cannot afford to do it often.
  4. Result under FIFO: S finishes at 185 min; its JCT is 184 minutes for 5 minutes of work. The average JCT of the two is (180 + 184) / 2 = 182 minutes; running S first would give (5 + 185) / 2 = 95 minutes (this guide's arithmetic).
  5. Meanwhile L's iterations peak at, say, 8 GB and fall to under 1 GB between iterations: half or more of the device memory is idle and could hold S entirely (see M3, M4).
Assumptions it relies on
  • A1. The GPU is the scarce resource, and cluster schedulers allocate it in whole devices (stated).
  • A2. Preemption requires moving a job's GPU state out (stated, as the status quo Salus attacks).
  • A3. Job mixes contain both long and short jobs, and jobs that do not fill a GPU (stated, from the measured workloads and the Tiresias trace distribution).
If an assumption changes
  • A1 changes (hardware partitioning): later GPUs offer hardware partitioning into isolated slices with their own memory (general knowledge: NVIDIA Multi-Instance GPU (MIG) on the A100, 2020). That solves static partitioning with isolation but still fixes slice sizes in advance, so the peak-to-trough waste within a slice remains (inference).
  • A2 changes (state can stay put): this is Salus's own move: if persistent state stays resident, preemption becomes a scheduling decision instead of a data transfer (M8).
  • A3 changes (all jobs equal and GPU-filling): FIFO is then close to optimal for average JCT and packing gains nothing; the paper's resnet50_50 result (1.07×) shows the compute-bound end of this (inference connecting to F).
Design notes and rejected alternatives

The paper does not argue for a hardware change; it accepts exclusive hardware and builds sharing in software above the driver. It also does not try to fix this at the cluster level (Gandiva and Tiresias already do cluster scheduling); Salus is a per-GPU mechanism that "can be utilized by a GPU cluster scheduler".

Connections

ESX: server consolidation for VMs is the same motive as packing inference models: idle reservations of a scarce resource (inference). Livelock: FIFO with long non-preemptible work is the kind of scheduling pathology the Livelock paper fixes by bounding work per unit (inference). Exokernel: the paper keeps policy above a mechanism layer, which mirrors the Exokernel separation (inference).

M2 · Heterogeneous peak memory across jobs

TL;DR
ProblemA scheduler that treats every job as needing a whole GPU wastes memory on small jobs.
ObservationPeak memory ranges from 35 MB (vae) to 13.8 GB (resnet152) across the 15 models; it grows with model size and batch size.
Trade-offOpportunity to co-locate small jobs, at the price of having to know each job's peak to pack safely.
Breaks whenAll jobs are near the device capacity (no room to co-locate), or peaks are not known in advance.
Key points
  • Workloads: 15 models (11 image classifiers from the TensorFlow CNN (convolutional neural network) benchmarks plus vae, superres, speech and seq2seq), each at 3 batch sizes: "45 distinct workloads" (Table 2).
  • "As models become larger (with more and wider layers) and the batch size increases, memory requirements of DL jobs increase as well. For example, we observed peak memory usages as high as 13.8 GB for resnet152 and as low as less than 1 GB for vae."
  • Figure 1 caption: "The average and peak usage for vae is 22 MB, 35 MB, which are too small to show in the figure."
  • "Such high variations suggest that even during peak allocation periods, it may be possible to run multiple models on the same GPU instead of FIFO."
  • Why memory first: "the entire DL model and its associated data must reside in memory for the GPU to perform any computation; in contrast, computations can be staggered over time given sufficient GPU memory."
How it works, step by step: reading Figure 1 as a packing problem
  1. Peaks read off Figure 1 (approximate, GB): alexnet 1.6, googlenet 3.2, superres 1.0, overfeat 4.2, seq2seq 5.0, speech 5.6, vgg11 7.2, resnet50 8.4, vgg16 9.4, vgg19 9.6, inception3 11.3, resnet101 11.4, inception4 14.4, resnet152 14.6, vae ≈0. The text's "13.8 GB for resnet152" is below the bar's ≈14.6, and inception4's bar is also above 13.8 (an inconsistency, listed in Reference). Figure 1 has one bar per model, not per workload; which batch size each bar shows is not stated.
  2. Naive packing by peak on 16 GB: alexnet + googlenet + overfeat + seq2seq = 1.6 + 3.2 + 4.2 + 5.0 = 14.0 GB fits; four jobs share one GPU even if each held its peak forever (this guide's arithmetic).
  3. Big jobs pack poorly by peak: any two of inception3, resnet101, inception4, resnet152 exceed 16 GB by peak. Packing them needs the time dimension: their peaks do not happen at the same moments (M3).
  4. Averages are far lower: resnet152 average ≈5.1 against peak ≈14.6 (35%), vgg19 ≈1.7 against 9.6 (18%), speech ≈3.7 against 5.6 (66%). Most models are under the 50% the introduction mentions.
Assumptions it relies on
  • A1. The 15 models and batch sizes are representative of cluster workloads (stated as the paper's choice; not demonstrated).
  • A2. Peak memory is a property of the workload (model plus batch size), stable across runs (implicit).
  • A3. Memory, not compute, is the binding constraint for co-location (stated as a premise).
If an assumption changes
  • A1 changes (much larger models): if every job's parameters alone approach the device capacity, there is nothing to co-locate and the opportunity disappears (inference).
  • A2 changes (peak depends on input): peaks vary per iteration with variable-length inputs; a scheduler using a measured peak risks out-of-memory (inference).
  • A3 changes (compute-bound jobs): co-located jobs slow each other down and the gain shrinks; exactly the resnet50_50 hyper-parameter result (1.07×).
Design notes and rejected alternatives

The paper uses heterogeneity only as motivation; its mechanisms do not need it explicitly. Salus does not pick co-located pairs by compute profile, and does not claim performance isolation (it criticizes static partitioning and MPS for lacking it, but offers memory safety, not compute isolation).

Connections

ESX: the gap between what a VM is configured with and what it touches is the reason for ESX's overcommit; here the gap is between a job's peak and its average (inference). vLLM: per-request reservations sized for the maximum length waste most of the reserved key-value (KV) cache memory, the same peak-versus-actual waste (inference).

M3 · Periodic memory within a job

TL;DR
ProblemA job's peak lasts a small part of each iteration; reserving the peak for the whole job wastes the rest.
Observation"each iteration of a DL training job is highly predictable with a well-defined peak memory usage and a trough in between iterations."
Trade-offPredictable troughs make good switching points, but only between iterations; within an iteration a job cannot give memory back.
Breaks whenIterations differ (dynamic graphs, variable shapes) or the job is mostly in warm-up.
Key points
  • Cause: "This is because DL jobs go through the same sequence of operations and memory allocations in each iteration."
  • Use: "The presence of predictable peaks and troughs can help us identify scheduler invocation points."
  • Figure 2 shows resnet101_75 on a P100 in both TensorFlow and PyTorch: the same period, different shapes (TensorFlow a sawtooth, PyTorch flat-topped pulses).
How it works, step by step: one iteration of resnet101_75 in TensorFlow
  1. Trough (≈0.3 GB, read-off): only parameters, optimizer state and framework buffers are allocated.
  2. Forward pass: each layer's output is allocated and kept; usage jumps to ≈8.8 GB within about 0.05 s (read-off). A batch of 75 images through 101 layers produces many large activation tensors (general knowledge for the cause).
  3. Backward pass: gradients are computed layer by layer in reverse and activations are released as they are no longer needed; usage declines over about 0.3 s (read-off).
  4. End of iteration: the update is applied and the remaining temporaries are freed; usage returns to the trough. The next iteration starts about 0.6 s after the previous one (read-off).
  5. Time-weighted average of one cycle: roughly 3 GB, about a third of the 8.8 GB peak (the area under the sawtooth divided by its 0.6 s period; this guide's estimate from the plot). A reservation sized at the peak leaves about two thirds of it idle on average. Figure 1's resnet101 bars give a similar ratio (≈3.1 of ≈11.4 GB).
Assumptions it relies on
  • A1. A static computation graph executed with the same input shapes every iteration (stated cause: "the same sequence of operations and memory allocations").
  • A2. The framework actually frees ephemeral memory at the end of each iteration (stated for TensorFlow and PyTorch by the traces).
  • A3. Warm-up is short relative to the job (implicit; in Figure 2 it lasts about 1.3 s).
If an assumption changes
  • A1 changes (variable-length inputs, e.g. sequence models with padding to different lengths): peaks vary by iteration; a lane sized by one observed peak can be too small for a longer batch (inference; the paper's seq2seq uses fixed "Small, Medium, Large" configurations).
  • A2 changes (a framework caches freed memory instead of returning it): the trough Salus sees would stay high. Salus avoids this by providing the allocator itself (inference; M11).
  • A3 changes (long warm-up, or the first iteration peaks higher): Figure 2's warm-up spikes to ≈11 GB, about 2.5 GB above the steady peak; a lane sized for the steady peak would not hold the warm-up (read-off and inference; see Class Prep).
Design notes and rejected alternatives

The paper uses periodicity to choose where to switch, not to predict allocation addresses in advance. It mentions memory planners that plan an iteration's allocations before running it (Chen et al., 2015) but notes "they are not available to all frameworks"; Salus instead isolates each iteration's allocations in a lane.

Connections

ESX: working-set estimation by sampling assumes a stable working set over time; here the working set is periodic with a period under a second, so time-sharing at period boundaries replaces sampling (inference). Superpages: a burst of large, short-lived allocations every period is the pattern that makes allocator fragmentation matter (inference).

M4 · Low persistent memory

TL;DR
ProblemTo resume a job quickly, its state must be on the GPU; to share the GPU, that state must be small.
ObservationPersistent memory (the trough) is 110.9 MB (googlenet_25) to 822.2 MB (resnet152_75), a few percent of the peaks.
Trade-offMany jobs' persistent memory fits at once, but each resident job costs that memory permanently even while paused.
Breaks whenModels are large relative to the GPU (parameters dominate rather than activations).
Key points
  • "Another important characteristic of GPU memory usage of DL jobs is the use of persistent memory to hold parameters of a model ... this corresponds to the consistent troughs across iterations."
  • "Even though the peak usage can be very high, most of it is temporary data created and destroyed within the same iteration."
  • "the size of persistent memory is often very low in comparison to the peak, ranging from 110.9 MB for googlenet_25 to 822.2 MB for resnet152_75."
  • "As long as the model parameter is already in GPU memory, we can quickly start an iteration of that model."
How it works, step by step: how many jobs' persistent memory fits
  1. Largest persistent: 822.2 MB. Ratio to resnet152's 13.8 GB peak: 0.82 / 13.8 = 6% (this guide's arithmetic).
  2. 16 GB of nothing but persistent memory would hold 16,000 / 822.2 ≈ 19 resnet152_75 jobs or 16,000 / 110.9 ≈ 144 googlenet_25 jobs, before any lane (this guide's arithmetic, using 1 GB = 1000 MB as the paper's figures appear to).
  3. With one lane for resnet152_75's ephemeral memory (≈13.8 − 0.82 ≈ 13.0 GB, inference that peak = persistent + ephemeral), the persistent budget is 16 − 13.0 = 3.0 GB: three resnet152_75 jobs can be resident and time-share (Worked Example ③).
  4. Back of the envelope for resnet152: about 60 million parameters × 4 bytes ≈ 240 MB of weights; with momentum and framework buffers, several hundred MB, consistent with 822.2 MB (general knowledge for the parameter count; inference for the breakdown).
Assumptions it relies on
  • A1. Activations, which scale with batch size, dominate parameters (implicit; true for the CNNs measured).
  • A2. Persistent memory is constant over the job (stated for model memory: "the model size is typically fixed during the entire training process").
If an assumption changes
  • A1 changes (parameter-dominated models, e.g. multi-billion-parameter language models): persistent memory approaches or exceeds a GPU's capacity, so keeping several jobs resident is impossible and fast switching loses its basis (inference; see S on vLLM).
  • A2 changes (models that grow, or optimizer state allocated lazily): a job's persistent memory increases after admission and can violate the safety condition the scheduler checked on arrival (inference).
Design notes and rejected alternatives

The paper states persistent sizes for only the two extremes; it does not list per-workload persistent memory. All later packing arithmetic in this guide that needs other values says so.

Connections

Hints: keep the cheap-to-keep state close so the common operation (switching) is fast; a direct use of "make the common case fast" (inference). Dune / x86 VMM: a VMM keeps a paused guest's memory in place and switches by saving a small register state; Salus's "small state" is the persistent region, which stays in device memory (inference).

M5 · Prior sharing techniques and why they fall short

TL;DR
ProblemSeveral partial solutions exist; none gives both cheap preemption and dynamic memory sharing for unmodified training and inference jobs.
Mechanisms reviewedStatic memory partitioning; NVIDIA MPS; inference servers (TensorRT Inference Server, Samanta et al.); driver interception with kernel time slicing; new GPU programming APIs; checkpoint-based suspend and resume (Gandiva).
Trade-offEach is simpler than Salus in one dimension and missing another: dynamic memory, isolation, training support, or scalability to hundreds of kernels.
Breaks whenJobs have high peak-to-average memory (static partitioning), need flexible policies (MPS), are training jobs (inference servers), or have hundreds of unique kernels (kernel slicing).
Key points
  • Straw man: "disabling the exclusive access mode and statically partitioning the GPU memory among DL jobs. This cannot completely address the underutilization problem due to high peak-to-average memory usage of DL jobs."
  • MPS "can be used to speed up the static partitioning approach for GPU sharing by avoiding costly GPU context switches. Nonetheless, MPS has limited support for DL frameworks or companies' in-house monitoring tool according to our experiments and various bug reports."
  • "Static partitioning and MPS also fail to provide performance isolation." Gandiva handles interference "by trial and error and fallback to non-sharing mode"; Xu et al. predict interference with an ML model.
  • TensorRT Inference Server and Samanta et al. "achieve simultaneous DL inference in parallel on a single GPU. But they lack support for DL training."
  • Kernel-level approaches "are designed for jobs with a few GPU kernels; as such, they are not scalable to DL applications, where the number of unique kernels can easily go up to several hundreds."
How it works, step by step: what each option does with two jobs, A (peak 8 GB, trough 0.5 GB) and B (peak 6 GB, trough 0.3 GB), on 16 GB
  1. Exclusive: A runs; B waits until A finishes (M1).
  2. Static partitioning: give A 8 GB and B 6 GB, each in its own process and context. Both run, but the GPU time-slices between two contexts, and a third job C with a 5 GB peak cannot start even though A and B together average well under 8 GB (illustrative numbers).
  3. Static partitioning + MPS: same partitions, but one MPS server context, so kernels of A and B overlap without context switches. Memory is still fixed per job. The paper's Figure 13: static partitioning (SP) ≈105 s, SP+MPS ≈88 s average JCT (read-off).
  4. + memory overcommit (Unified Memory): give each job more than its share and let pages migrate. Figure 13: 698.45 s, "significantly bad performance that is beyond useful".
  5. Salus: one process; persistent 0.8 GB resident; A and B either alternate in one 7.5 GB lane or run in two lanes of 7.5 and 5.7 GB (14.0 GB total with persistent); C can be admitted into an existing lane by time sharing (this guide's arithmetic, M14).
Assumptions it relies on
  • A1. MPS's limitations are practical (framework and tool support), not fundamental (stated as "according to our experiments and various bug reports").
  • A2. DL jobs have hundreds of unique kernels, so per-kernel techniques do not scale (stated).
If an assumption changes
  • A1 changes (MPS matures): MPS would match Salus on throughput (Figure 13 already shows them equal for two alexnet_25 jobs) but still lacks dynamic memory sharing and policy control; the 42-model inference result (MPS 6 GPUs, Salus 1) depends on dynamic memory, not on MPS's bugs (inference).
  • A2 changes (fused graphs with few kernels): kernel-level scheduling would cost less, but it would still break batching and pipelining in the framework (M9; inference).
Design notes and rejected alternatives

The paper rejects all of these but does not reject the idea of a central process: Salus is itself a single server like MPS, with a memory manager and scheduler added. The difference from MPS is that Salus understands iterations and allocation types, which MPS cannot see.

Connections

ESX: static partitioning is the "reserve the configured memory" baseline that ESX's overcommit improves on; ESX can page and balloon, while GPU overcommit here was 7.9× slower than static partitioning with MPS (698.45 / 88, this guide's arithmetic). Exokernel: MPS multiplexes without understanding the application; Salus understands the application (iterations) to multiplex better, the opposite direction from Exokernel's minimal kernel (inference).

M6 · Why copying a job's state off the GPU is too slow (Observation 1)

TL;DR
ProblemPreemption by checkpoint moves a job's GPU memory to the host and back. Even the parameters alone take a long time compared with an inference request.
EvidenceFigure 4: the ratio of "theoretical minimal transfer time" (model size at 30 GB/s) to inference latency, for 15 models; about a fifth of models have a ratio above 1, up to about 2.8 (read-off).
Trade-offCopying frees GPU memory for others but costs time on every switch; Salus gives up the memory to save the time.
Breaks whenThe bus is fast relative to the job's iteration time, or switches are rare (minutes apart), as in Gandiva.
Key points
  • "Suspending a running job and resuming the same or another one have always been possible on GPU as well. Modern DL frameworks extensively use checkpointing ... The same technique is applied by Gandiva ... to achieve second-scale suspend/resume."
  • "Nevertheless, checkpointing can result in large data transfers from and to the GPU memory, even in the best case when only model parameters are transferred, the communication time is still non-negligible."
  • "It even becomes unacceptable if the system ever wants to support inference workloads: the theoretical minimal transfer time can be even several times longer than the inference latency itself."
  • Observation 1: "Transferring GPU memory back and forth is not practical to achieve low latency given current GPU communication bandwidth."
  • Figure 4 caption: "Transfer time is calculated using 30 GB/s for transfer speed."
How it works, step by step: the cost of one checkpoint-style switch
  1. State to move: at best the persistent memory, 822.2 MB for resnet152_75 (the largest the paper reports).
  2. At the paper's 30 GB/s: 822.2 MB / 30 GB/s = 27.4 ms out, and 27.4 ms back in for the next job: about 55 ms per switch for two jobs of this size (this guide's arithmetic).
  3. At a realistic PCIe 3.0 x16 rate of about 12 to 16 GB/s (general knowledge, not in the paper), the same copy takes 51 to 69 ms each way. The paper's 30 GB/s is therefore an optimistic floor, which makes its argument conservative.
  4. Compared with inference: an inference job needs only the weights. alexnet has about 61 million parameters and vgg16 about 138 million (general knowledge), so 244 MB and 552 MB in 32-bit floats: 8.1 ms and 18.4 ms at 30 GB/s. Figure 10 shows their TensorFlow inference latencies at ≈3 ms and ≈8 ms (read-off): ratios of about 2.7 and 2.3, which matches the top of Figure 4's range (≈2.8). A deep but narrow model such as resnet152 (≈60 million parameters, 240 MB, 8 ms) against ≈26 ms latency gives ≈0.3, in the bulk of the CDF (this guide's arithmetic and inference; the paper does not list per-model ratios).
  5. Compared with training: a resnet101_75 iteration lasts about 0.6 s (Figure 2), so a 55 ms swap per switch is about 9% of one iteration; swapping is slow for inference, merely costly for training (this guide's arithmetic; the paper does not make this comparison).
  6. What the paper's alternative costs: zero bytes moved; the price is that the resident persistent memory stays allocated (M8).
Assumptions it relies on
  • A1. Host-GPU bandwidth is the bottleneck of a switch (stated in Observation 1).
  • A2. The ratio that matters is transfer time to request latency (stated for inference via Figure 4).
  • A3. At least the persistent memory has to move on a checkpoint switch (stated: "even in the best case when only model parameters are transferred").
If an assumption changes
  • A1 changes (NVLink-class or unified-memory hardware with hundreds of GB/s, general knowledge): 822 MB would move in a few milliseconds and swapping persistent state between iterations becomes viable even for inference; Salus's resident-memory rule would then be a choice, not a necessity (inference).
  • A2 changes (training only, switches every few minutes): a 55 ms copy every minute is 0.1% overhead; Observation 1 then argues against swapping only through latency, not throughput (inference).
  • A3 changes (checkpoints need more than raw copies): Gandiva's second-scale suspend and resume includes framework work (saving, process teardown and restart, general knowledge), so real checkpoint switches are slower than Figure 4's bound; the gap to Salus is larger than Figure 4 shows (inference).
Design notes and rejected alternatives

The rejected alternative is checkpoint-based suspend and resume as used by Gandiva, and, implicitly, any swapping of persistent memory. The paper's Figure 4 is a bound, not a measurement: it uses 30 GB/s and only the model size, so the true switching cost of copying is higher. The paper does not give its inference latencies in Figure 4's text; Figure 10 provides some.

Connections

ESX: swapping a VM's pages to disk is the slow path ESX avoids with ballooning and sharing; here swapping to host memory is the slow path Salus avoids by keeping state resident (inference). vLLM: vLLM does swap KV cache blocks to CPU memory on preemption, or recomputes them, because per-request state there is large and short-lived; it measures the same transfer-versus-recompute trade-off (inference, see S).

M7 · Three kinds of allocation: model, ephemeral, framework-internal (Observation 2)

TL;DR
ProblemTo keep some memory resident and treat the rest as disposable, the system needs a rule for which allocation is which.
MechanismClassify allocations into model (parameters), ephemeral (per-iteration scratch) and framework-internal (bookkeeping, input pipeline); model and framework-internal together are "persistent".
Trade-offPersistent memory is small and stays; ephemeral memory is large but disappears every iteration, so it can be shared over time.
Breaks whenAn allocation's lifetime does not match its class (for example a cache kept across iterations by a framework).
Key points
  • Model: "These mostly hold model parameters and typically consist of a few large chunks of memory. They are persistent because they have to be available throughout the whole job's lifetime. Because the model size is typically fixed during the entire training process, model data has little or no temporal variations and is predictable."
  • Ephemeral: "the scratch memory needed during each iteration. These memory usually hold intermediate layers' outputs as well as temporary data generated by the algorithm itself. They are only needed during computations and are released between iterations ... They are often large memory allocations as well."
  • Framework-internal: "usually used by the DL framework for book-keeping or for data preparation pipeline. They often persist across iterations."
  • "Collectively, model and framework-internal memory are persistent across iterations."
  • Observation 2: "There is significantly less persistent memory than ephemeral ones in a DL job. It is possible to keep more than one job's persistent memory in GPU while still having enough space for either one's ephemeral memory."
How it works, step by step: reading Figure 5 (inception3_50)
  1. Count of allocations (right panel, x axis at the end of each curve, read-off): about 1,700 framework-internal, about 500 model, about 800 ephemeral.
  2. Size per allocation (left panel, CDF, read-off): framework-internal allocations are tiny, about a fifth of them a few bytes and most under 64 KB; model allocations are 60% under about 1 KB (biases and normalization parameters) with the rest up to a few MB; ephemeral allocations range from about 1 MB to a few hundred MB, median about 16 MB.
  3. Total bytes (right panel, log scale, read-off): framework ≈ 100 to 200 MB, model ≈ 300 MB, ephemeral reaching tens of GB. The ephemeral total exceeds the 16 GB GPU, so the plot must count bytes allocated over time, including memory freed and reallocated (inference).
  4. Reading: by count, framework-internal allocations dominate; by bytes, ephemeral allocations dominate by about two orders of magnitude. That is Observation 2 in one picture.
  5. Why the small framework allocations still matter: "while the framework-internal memory allocations are small in size, they can have a large impact on the overall memory layout and may create more memory fragments when multiple iterations are allocating simultaneously" (Section 3.3). That is why they go in the persistent region, away from lanes (M12).
Assumptions it relies on
  • A1. Allocations can be told apart by kind at allocation time (implicit; the paper does not say how Salus classifies them).
  • A2. Ephemeral allocations really are all freed by the end of each iteration (stated: "released between iterations").
  • A3. Persistent memory is much smaller than ephemeral (stated as Observation 2, shown for inception3_50 and for the persistent range in Section 2.1).
If an assumption changes
  • A1 changes (no classification possible): everything would have to be treated as persistent, and lanes would hold nothing; Salus would reduce to static partitioning (inference).
  • A2 changes (an "ephemeral" tensor survives the iteration, e.g. a cached workspace): at the iteration boundary the lane is not empty, so moving or reusing the lane would overwrite live data or the lane cannot move (inference; M15 depends on this).
  • A3 changes (small batch, big model): the ratio flips for inference-sized batches of large models; then resident persistent memory costs most of the GPU (inference).
Design notes and rejected alternatives

The paper's classification is semantic (what the memory is for), but what Salus needs operationally is lifetime (does it survive the iteration). The two coincide for model and ephemeral memory; framework-internal memory is grouped with persistent because it "often" persists. How the implementation decides at allocation time is not described (inference: memory allocated while an iteration runs and freed before it ends can be served from the lane; memory allocated outside iterations, such as variables at session creation, from the persistent region).

Connections

Superpages and memory allocators: segregating allocations by lifetime is a classic anti-fragmentation technique (general knowledge: region or arena allocation). vLLM: also separates a model's weights (static, loaded once) from per-request KV cache (dynamic, the part that is managed and shared), the same split by lifetime (inference).

M8 · Fast job switching: keep persistent memory resident, switch at iteration boundaries

TL;DR
ProblemPreemption and time sharing need a switch that costs far less than an iteration.
MechanismNever remove an admitted job's persistent memory from the GPU; let an "iteration-granularity job scheduler" decide "which job's iteration should be run next".
Trade-offA switch moves no data, in exchange for GPU memory held by jobs that are not running, and switch points only every iteration.
Breaks whenPersistent memory of all admitted jobs plus one lane does not fit; or iterations are long (a job holds the GPU for its whole iteration).
Key points
  • "The above two observations naturally lead to the conclusion that fast job switching can be enabled by not removing persistent memory from GPU at all."
  • "Thus unlike existing works (Xiao et al., 2018), Salus is designed to enable significantly faster suspend/resume operations by keeping persistent memory around, and then an iteration-granularity job scheduler (e.g., time sharing or preemption-based) decides which job's iteration should be run next."
  • Figure 8b: "at the moment of a job switching, the second job's iteration starts immediately after the first job stops."
  • Evaluation context: "we show fast job switching can achieve fair sharing among DL jobs in seconds-granularity ... instead of minutes."
How it works, step by step: switching from job A to job B in one lane
  1. State before: A (persistent 0.8 GB) and B (persistent 0.4 GB) are both admitted; their persistent memory sits in the persistent region. One lane of 7.2 GB holds A's running iteration (illustrative sizes).
  2. A's iteration k ends: the framework releases A's ephemeral allocations; the lane is empty. A's session is idle until its script submits iteration k+1.
  3. Scheduler decision: at this boundary the scheduler picks the next iteration to run in the lane. Under SRTF, if B has less remaining time, B goes next; under FAIR, whoever has received less service.
  4. B's iteration starts: its kernels are launched on the lane's stream and its ephemeral allocations are served from the same lane. Its parameters are already resident, so the first kernel can start right away.
  5. Cost: nothing is copied. In Figure 8b the gap between the last iteration of one job and the first of the next is about 0.3 s (normalized time, read-off), roughly two of the first job's own inter-iteration troughs (≈0.15 s).
  6. Resuming A later is the same operation in reverse: A's next iteration starts in the lane; nothing was lost because nothing ephemeral existed at the boundary.
Assumptions it relies on
  • A1. All admitted jobs' persistent memory fits simultaneously with the lanes (stated through the safety condition, M14).
  • A2. Iteration boundaries are visible to Salus (stated: iterations "are generated by the user script and forwarded to the corresponding session in Salus").
  • A3. Nothing ephemeral survives an iteration (stated, M7).
  • A4. Iterations are short enough that waiting for one to end is acceptable (stated: "ranging from tens of milliseconds to a few seconds").
If an assumption changes
  • A1 changes (too many paused jobs): a new job, even the shortest, cannot be admitted until some job finishes, because Salus does not evict persistent memory; SRTF stops being able to preempt for it (inference; Class Prep C2). The paper's SRTF rule, "it can run alone on the GPU ... regardless of other already-running jobs", could be read as admitting the job anyway, but no mechanism for evicting paused jobs' persistent memory is described.
  • A2 changes (a framework that runs a whole training loop in one call, general knowledge: graph-level loops): Salus would see one "iteration" lasting the whole job and could never switch (inference).
  • A3 changes: the next job could find the lane partly occupied; switching would require waiting for or copying the survivor (inference).
  • A4 changes (iterations of tens of seconds, e.g. huge batches): preemption latency becomes tens of seconds; still far better than minutes, but not interactive (inference).
Design notes and rejected alternatives

Rejected: checkpoint-based switching (M6) and kernel-granularity switching (M9). The design uses memory to buy time: the scheduler can preempt as often as every iteration without data movement. The paper gives no direct switch-latency number; the evidence is Figure 8b's plot and the FAIR experiment's quick reaction (Figure 9).

Connections

x86 VMM, Dune: a context switch that saves only a small register state while memory stays mapped is the CPU analogue: Salus's "register state" is nothing at all, because the switch point is chosen when nothing is in flight (inference). Livelock: switching only at well-defined points (iteration boundaries) is like processing a packet to completion before switching, which bounds wasted work per switch (inference).

M9 · Scheduling granularity: iterations, not kernels

TL;DR
ProblemFiner scheduling could fill GPU gaps better, but every decision costs something and may disturb the framework's own optimizations.
MechanismSchedule whole iterations. A kernel-level prototype was built and dropped.
Trade-offLow overhead and intact framework optimizations, in exchange for switch latency of up to one iteration and no interleaving inside an iteration (except across lanes).
Breaks whenIterations are long, or a single iteration leaves most of the GPU's compute idle and only one lane exists.
Key points
  • "Given that iterations are typically short in DL jobs (ranging from tens of milliseconds to a few seconds), with an even finer granularity, e.g., at the GPU kernel level, it may be possible to further utilize GPU resources. However, finer-grained scheduling also adds more overhead to the execution service."
  • "Indeed, there is a tradeoff between maximum utilization and efficiency for a given scheduling granularity."
  • "we prototyped a GPU kernel-level switching mechanism as well only to find that scheduling at that level incurs too much overhead for little gain. It requires all GPU kernels to go through a central scheduler, which, in addition to becoming a single bottleneck, breaks common efficiency optimizations in DL frameworks such as kernel batching and pipelining."
  • The acknowledgments thank a person who "helped with evaluating an earlier version of Salus that used GPU kernel-granularity scheduling". No numbers for that version are given.
How it works, step by step: decisions per second at each granularity
  1. A job with 0.1 s iterations and 500 kernel launches per iteration (illustrative; the paper says unique kernels number "several hundreds").
  2. Iteration level: 10 scheduling decisions per second per job.
  3. Kernel level: 5,000 decisions per second per job. If each decision through the central scheduler cost 20 µs of serialized CPU time (illustrative), that is 100 ms of scheduler time per second per job: the scheduler alone would saturate with 10 such jobs (this guide's arithmetic on illustrative inputs).
  4. Pipelining lost: a framework normally enqueues many kernels ahead into a stream and lets the GPU run them back to back (general knowledge). A per-kernel gatekeeper must hold each launch until it decides, so the GPU can go idle between kernels while the CPU decides.
  5. What iteration level gives up: within one lane, while job A's iteration runs, job B cannot fill idle SMs. Salus recovers some of this with multiple lanes, which run concurrently on separate streams (M13).
Assumptions it relies on
  • A1. Iterations are tens of ms to a few seconds (stated).
  • A2. Kernels number in the hundreds per job and are launched asynchronously in batches (stated for count and for "kernel batching and pipelining").
If an assumption changes
  • A1 changes (multi-second iterations with tight latency goals, e.g. a short job behind a giant batch): preemption waits a whole iteration; a finer unit would be needed for responsiveness (inference).
  • A2 changes (few, long kernels, e.g. fused or compiled graphs): kernel-level scheduling becomes cheaper and finer interleaving could pay off (inference).
Design notes and rejected alternatives

The rejected alternative is the earlier kernel-granularity Salus. The paper's argument is qualitative; it gives no overhead number for the prototype, so "too much overhead for little gain" cannot be checked from the paper.

Connections

Livelock: the paper's choice is the same as bounding the cost of scheduling per unit of useful work: decide per batch, not per item (inference). Hints: "use batch processing if possible" is a Lampson hint; iteration-level scheduling is batch-level control (inference). Mesa (monitors): preemption only at well-defined points simplifies reasoning about shared state, here GPU memory (inference).

M10 · The singleton execution service and a job's life cycle

TL;DR
ProblemSharing needs one place that sees every job's iterations and allocations, without changing user scripts and without GPU context switches between processes.
MechanismA single Salus process "consolidates all GPU accesses". A framework-specific adaptor turns it into a virtual device; each job becomes a session that gets a lane and submits iterations to an iteration scheduler.
Trade-offTransparent to users and free of context switches, in exchange for an adaptor per framework and a service that re-executes the job's graph (including CPU work).
Breaks whenA framework cannot route its execution through a remote device, or the service itself becomes a CPU bottleneck.
Key points
  • "At the highest level, Salus is implemented as a singleton execution service, which consolidates all GPU accesses, thus enabling sharing while avoiding costly context switch among processes on the GPU. As a result, any unmodified DL job can leverage Salus using a DL framework-specific adaptor."
  • "From a framework's point of view, the adaptor abstracts away low level details, and Salus can be viewed as another (virtual) computation device; From a user's perspective, the API of the framework does not change at all. All scripts will work the same as before."
  • Life cycle (Figure 3): (1a) "When a job is created in an user script, Salus adaptor in the DL framework creates a corresponding session in Salus. The computation graph of the DL job is also sent to Salus during the creation." (1b) "The session then proceeds to request a lane from the memory manager. Depending on current jobs in the system, this process can block and the session will be queued." (2a) "iterations are generated by the user script and forwarded to the corresponding session in Salus." (2b) "They are then scheduled according to their associated GPU lanes by the iteration scheduler, and send to GPU for execution."
  • "The Salus execution service thus achieves GPU sharing via iteration-granularity scheduling of DL jobs."
How it works, step by step: one training job from start to finish
  1. User script creates a TensorFlow session on the Salus device (via the adaptor, the script does not change). (1a) The adaptor opens a session in the Salus service and ships the job's computation graph.
  2. (1b) Lane request: the session asks the memory manager for a lane, given the job's persistent need P and ephemeral need E. Algorithm 1 returns a new lane, an existing lane, a grown lane, or "not found"; on "not found" the session waits in a queue (M16).
  3. Persistent allocations (variables, framework state) are placed in the persistent region.
  4. (2a) Each training step the script calls the session; the adaptor forwards that iteration to the Salus session.
  5. (2b) The iteration scheduler picks, per lane, which waiting iteration runs next according to the policy (PACK, SRTF, FAIR), and launches it on the GPU in that lane.
  6. Job ends: its persistent memory is released and its lane share is dropped; lane sizes are adjusted at the next iteration boundaries (M15).
Assumptions it relies on
  • A1. The framework has a device abstraction that can be implemented remotely (stated for TensorFlow: "another (virtual) computation device").
  • A2. All jobs on the GPU go through Salus (stated: "consolidates all GPU accesses").
  • A3. The job's computation graph is known at session creation (stated: "sent to Salus during the creation").
If an assumption changes
  • A1 changes (eager frameworks such as PyTorch of the time, general knowledge): there is no graph to ship at creation; an adaptor would have to forward individual operations, which pushes toward kernel-level granularity that the paper rejected (inference).
  • A2 changes (a non-Salus process also uses the GPU): its memory is invisible to the safety condition and can cause the out-of-memory errors lanes are meant to prevent (inference).
  • A3 changes (graphs that change during training): the session would need the new graph and possibly new P and E (inference).
Design notes and rejected alternatives

A single process means one GPU context: no context switches between jobs, and kernels of different lanes can overlap. MPS achieves the same with a server context, but it neither sees iterations nor manages memory. The paper does not describe fault isolation: a crash in the service takes down every job on the GPU (inference).

Connections

Exokernel: Salus is a user-level resource manager that multiplexes hardware and exports primitives to policies, but it sits above the driver and below the framework rather than in the kernel (inference). NFS: like an NFS client that makes a remote server look like a local file system through the vnode interface, the adaptor makes a remote service look like a local device through TensorFlow's device interface (inference).

M11 · Inside the implementation: adaptor, execution engine, streams, and where overhead comes from

TL;DR
ProblemTo place allocations and time iterations, Salus must execute the jobs itself rather than watch them from outside.
MechanismA modified TensorFlow (the adaptor) sends the graph and iterations to the Salus server; Salus "implements its own execution engine", runs both GPU and CPU operations, serves every allocation from its memory manager, and launches each lane's kernels on its own GPU stream.
Trade-offFull control over memory and timing, in exchange for an engine that is "not yet heavily optimized" for CPU operations.
Breaks whenA model does much of its work on the CPU: vae 1.81× and superres 1.83× per-iteration time (Figure 12).
Key points
  • "Since Salus implements its own execution engine, the CPU computation is also redirected and sent to Salus for execution, which is not yet heavily optimized."
  • Lanes: "Iteration execution is serialized within a lane and parallelism is achieved across lanes, which is implemented using GPU streams."
  • "For most CNN models, Salus has minimal overhead ... less than 10%, except for a few. The common point of these high-overhead DL models is that they also performs large portion of CPU computation in addition to heavy GPU usage."
  • Artifact appendix: server in C++ built with G++ 7 and CMake; the modified TensorFlow ("tensorflow-salus") built with Bazel 0.5.4; dependencies include boost, cppzmq/zeromq, protobuf, nlohmann-json and gperftools; "The server code requires NVIDIA P100 GPUs."
How it works, step by step: how a kernel of job A reaches the GPU (with labels on what is stated)
  1. Script: calls session.run for one training step, as it would on a local GPU (stated that scripts are unchanged; the call name is general knowledge of TensorFlow 1.x).
  2. Adaptor: instead of running the graph locally, sends the iteration request to the Salus server. The transport is not described; the artifact's dependencies (ZeroMQ, protobuf) suggest message passing with serialized requests (inference).
  3. Session in Salus: holds the job's graph and its lane assignment; the iteration waits until the scheduler picks it (stated).
  4. Execution engine: walks the graph, running CPU operations on the server's CPU threads and launching GPU kernels (stated that CPU work is redirected; the threading is inference).
  5. Memory: each tensor allocation goes to Salus's memory manager, which places persistent allocations in the persistent region and ephemeral ones in the job's lane (stated as the layout policy; the hook point in TensorFlow's allocator is inference).
  6. Stream: kernels are launched on the stream of the job's lane in Salus's single GPU context, so kernels from different lanes can run concurrently on the SMs (stated: lanes use GPU streams).
  7. Completion: results needed by the script (e.g. the loss value) are returned to the adaptor; the iteration's ephemeral allocations are freed; the scheduler is invoked at this boundary (stated that scheduling is event-driven at iteration boundaries).
Assumptions it relies on
  • A1. Moving execution into a separate process is cheap relative to an iteration (implicit; true for most CNNs, false for vae and superres).
  • A2. One GPU context per GPU is enough for all jobs (implicit in "singleton").
  • A3. The modified TensorFlow is version-matched to the server (stated by the artifact: Bazel 0.5.4, specific dependency versions).
If an assumption changes
  • A1 changes (input pipelines with heavy CPU preprocessing): the service's CPU becomes a shared bottleneck for all jobs on the machine; the 1.8× slowdowns would spread to co-located jobs (inference).
  • A2 changes (per-job contexts for isolation): context switches return and kernels of different jobs cannot overlap, losing the MPS-like benefit (inference).
  • A3 changes (framework upgrades): each TensorFlow release needs a re-ported adaptor; the evaluation uses TensorFlow 1.5.0 while the artifact lists CUDA 9.1 and the paper's environment says CUDA 8.0 (a small inconsistency, Reference).
Design notes and rejected alternatives

The paper chose to own execution rather than intercept CUDA calls (the driver-interception approach of earlier work, M5). Owning execution gives iteration boundaries and allocation types for free, which interception could not see. The cost is visible in Figure 12. The paper does not say how a job's P and E are obtained before admission (Algorithm 1 takes them as inputs).

Connections

Dune: Dune gives a process direct access to hardware; Salus takes direct access away from processes and gives it to one trusted service, the opposite trade (inference). Exokernel: the overhead of a user-level execution layer is the classic cost of moving functions out of the component that owns the hardware (inference).

M12 · The two-ended memory layout: persistent from one end, ephemeral from the other

TL;DR
ProblemLong-lived and short-lived allocations interleaved in one heap fragment it; several jobs allocating at once makes it worse.
MechanismSplit GPU memory into a persistent region and an ephemeral region "growing from both end of the memory space", like a stack and a heap.
Trade-offFree space is always one contiguous gap in the middle, and short-lived data never pins holes among long-lived data, in exchange for having to classify every allocation.
Breaks whenThe two regions would meet, which the safety condition is there to prevent (M14).
Key points
  • "First of all, learning from classic memory management techniques of stack and heap to seperate dynamic allocations from static ones, we divide GPU memory space into ephemeral (Eph.) and persistent (Pst.) regions, growing from both end of the memory space (Figure 6a)."
  • "A DL job's ephemeral memory goes into the ephemeral region, while other types of memory is allocated in the persistent region." So framework-internal memory, though small and numerous, goes with the model memory.
  • Figure 6a draws the ephemeral region at the top growing down and the persistent region at the bottom growing up, with three jobs (A, B, C) each having a slice in both.
How it works, step by step: three jobs arrive
  1. Empty 16 GB GPU. The persistent region is empty at address 0 and grows up; the ephemeral region is empty at 16 GB and grows down (illustrative orientation; Figure 6a).
  2. Job A (P = 0.8 GB, E = 7.2 GB) arrives: 0.8 GB of persistent memory is placed at the bottom; a 7.2 GB lane is reserved at the top (16.0 to 8.8 GB).
  3. Job B (P = 0.4 GB, E = 4.6 GB): 0.4 GB stacked above A's persistent memory (0.8 to 1.2 GB). B's ephemeral need fits A's lane, so B can share lane 1 (time-shared) or open a lane of its own. This example puts B in lane 1 to match the Big Idea figure; Algorithm 1 as printed would instead open a second lane for B (1.2 + 7.2 + 4.6 = 13.0 ≤ 16) and later put C into B's 4.6 GB lane (M16; this guide's arithmetic).
  4. Job C (P = 0.5 GB, E = 2.6 GB): 0.5 GB at 1.2 to 1.7 GB; a new 2.6 GB lane just below lane 1 (8.8 to 6.2 GB).
  5. Free gap: 6.2 − 1.7 = 4.5 GB, one contiguous piece in the middle, usable by either side.
Assumptions it relies on
  • A1. Every allocation can be routed to the right region at allocation time (implicit).
  • A2. Persistent memory is allocated once, early, and freed only when the job ends (implicit; stated for model memory).
If an assumption changes
  • A1 changes (misclassification): an ephemeral allocation placed in the persistent region leaves a hole when freed; a persistent allocation placed in a lane blocks the lane from being moved at boundaries (inference).
  • A2 changes (jobs come and go): when a job in the middle of the persistent stack finishes, its persistent slice becomes a hole between other jobs' slices. Lanes defragment for free (M15), but the paper does not say how persistent holes are reclaimed (inference; a gap in the paper's description).
Design notes and rejected alternatives

The rejected alternative is one shared heap (what several TensorFlow processes would effectively do if they shared an allocator). The paper also mentions ahead-of-time memory planners as an alternative for fragmentation, set aside because "they are not available to all frameworks". The two-ended layout uses the same idea as a process's stack and heap: two growth directions so that neither needs a fixed boundary.

Connections

Superpages: the Superpages paper also separates allocations by expected lifetime and contiguity needs, and fights fragmentation that would block large contiguous allocations (inference). LFS: segregating data by lifetime (hot and cold) to make cleaning cheap is the LFS cleaner's policy; here ephemeral and persistent are the extreme case of short and long lifetimes (inference).

M13 · GPU lanes: one iteration at a time within a lane, lanes in parallel

TL;DR
ProblemEphemeral allocations "happens in small chunks and cannott be predicted ahead", and the GPU cannot page, so two iterations running in shared space can each hold part of memory and need more: deadlock or out-of-memory. Fragmentation can cause "superfluous out-of-memory errors" even when total memory suffices.
MechanismDivide the ephemeral region into lanes ("continuous memory spaces"); each lane runs one iteration at a time, of any of the jobs assigned to it; lanes run concurrently "using GPU streams".
Trade-offNo two iterations ever compete for the same memory, so every running iteration can finish; in exchange, a lane is sized for its largest job, and jobs in a lane cannot overlap even if their compute would.
Breaks whenA job's ephemeral use exceeds the lane size it was admitted with; or one lane holds jobs of very different sizes.
Key points
  • "The ephemeral region is further divided into lanes, which are continuous memory spaces that can contain ephemeral memory allocation for iterations. Lanes are not only about memory, though. Iteration execution is serialized within a lane and parallelism is achieved across lanes, which is implemented using GPU streams. Each lane can be assigned to multiple DL jobs, which are time-shared within the lane."
  • "simply putting two iterations together may cause deadlock because there is no swapping for the oversubscribed memory." Footnote 3: "The existing memory overcommit technique Unified Memory Access is too slow to use. See §5.4."
  • "Even if enough memory is ensured for both peak memory usage for two iterations, memory fragmentation can still cause superfluous out-of-memory errors if not handled correctly."
  • "we approach the problem by limiting the dynamic allocation in the ephemeral region and isolate memory allocations across lanes to ensure maximum compatibility while achieving adequate flexibility."
How it works, step by step: why serializing within a lane prevents deadlock
  1. Without lanes: 16 GB GPU, 1 GB persistent in use, so 15 GB for scratch. Iterations of X and Y each need 9 GB at peak and allocate it in many small pieces over the forward pass (illustrative).
  2. Both start together. After a while X holds 7.5 GB and Y holds 7.5 GB: 15 GB, all of it. Each asks for its next activation tensor. Neither can get it, and neither will free anything until its iteration completes. With no paging there is no third option: the allocator either waits forever (deadlock) or fails (out-of-memory) (this guide's trace of the paper's argument).
  3. With lanes: X and Y together would need two lanes of 9 GB, 18 GB > 15 GB, so Salus puts them in one 9 GB lane (or makes one wait). In one lane, X's iteration runs to completion using up to 9 GB; then Y's runs. Each iteration has its whole lane, so each finishes.
  4. Across lanes: if Y needed only 5 GB, two lanes (9 + 5 = 14 GB ≤ 15) can run at once on two streams; each iteration allocates only inside its own lane, so neither can take memory the other needs.
  5. Fragmentation is confined: inside a lane only one iteration allocates at a time, so the interleaving of several jobs' small and large allocations that the paper blames for "superfluous" out-of-memory errors cannot occur within a lane.
Assumptions it relies on
  • A1. A job's peak ephemeral need E is known and stable across iterations (implicit; required by Algorithm 1's input E).
  • A2. An iteration that has its full E available always completes and frees everything (implicit, from M7).
  • A3. GPU streams give concurrency across lanes (stated).
If an assumption changes
  • A1 changes (E grows, e.g. a longer input): the iteration overflows its lane; either it fails or it spills into the free gap and can collide with the persistent region, which is exactly what the safety condition promised would not happen (inference).
  • A2 changes (an iteration blocks on something outside the GPU, e.g. input data): the lane is held idle by a job that is not computing; others in the lane wait (inference).
  • A3 changes (kernels from different streams serialize because each fills the GPU): lanes still keep memory safe but add no throughput; the resnet50_50 hyper-parameter result (1.07×) is consistent with this (the paper: "computation becomes the bottleneck").
Design notes and rejected alternatives

Rejected: letting iterations of different jobs allocate freely from one shared ephemeral pool (deadlock and fragmentation), ahead-of-time memory planning (not available in all frameworks), and memory overcommit through Unified Memory (too slow, M5). The lane is a reservation: it trades average utilization for a guarantee. A lane's size is the maximum E of its jobs, so a 2 GB job sharing a 7 GB lane leaves 5 GB idle during its turn (this guide's arithmetic; the paper notes only that lane assignment is an open question).

Connections

Livelock and deadlock avoidance in general: reserving each consumer's maximum need before admitting it is the banker's-algorithm idea of avoiding deadlock by admission control (general knowledge; inference that it applies). vLLM: vLLM's PagedAttention instead allocates KV cache in small fixed blocks on demand and handles exhaustion by preempting a request (swap or recompute), the opposite choice: no reservation, plus a recovery path (inference).

M14 · The safety condition

TL;DR
ProblemThe persistent region and the ephemeral region grow toward each other; if they meet, some allocation fails.
MechanismAlways keep Σjob i Pi + Σlane l maxjob j in l(Ej) ≤ C.
Trade-offA hard guarantee that every lane can complete its current iteration, at the price of reserving each lane's worst case and admitting fewer jobs.
Breaks whenP or E is underestimated, or something outside Salus uses GPU memory.
Key points
  • "Throughout the process, the following 'safety' condition is always kept to make sure the persistent region and ephemeral region do not collide into each other: Σjob i Pi + Σlane l maxjob j in l(Ej) ≤ C".
  • "where P and E are respectively the persistent (model and framework-internal) and ephemeral memory usage of a job. C is the capacity of the GPU. The second term is the sum of all lanes' size, which is defined as the maximum ephemeral memory usage of all jobs in the lane."
  • "By ensuring enough capacity for persistent memory of all the admitted jobs and enough remaining for the iteration with the largest temporary memory requirement, Salus increases the utilization while making sure that at least one job in the lane can proceed."
  • PACK, SRTF and FAIR all run "with Salus specific constrains (i.e., safety condition)".
How it works, step by step: checking the condition
  1. Inputs (illustrative): C = 16 GB. Jobs A (P 0.8, E 7.2), B (P 0.4, E 4.6), C (P 0.5, E 2.6).
  2. One lane for all three: 1.7 + max(7.2, 4.6, 2.6) = 1.7 + 7.2 = 8.9 GB ≤ 16. Safe, 7.1 GB unused, no concurrency.
  3. A and B in lane 1, C in lane 2: 1.7 + 7.2 + 2.6 = 11.5 GB ≤ 16. Safe; C runs alongside whichever of A or B is running.
  4. Three lanes: 1.7 + 7.2 + 4.6 + 2.6 = 16.1 GB > 16. Not allowed, by 0.1 GB.
  5. Why "max" and not "sum" within a lane: jobs in a lane never run iterations at the same time, so at any moment the lane holds at most one job's ephemeral memory, and the largest is the worst case.
  6. Why persistent is a sum over all jobs, running or not: persistent memory of paused jobs stays resident (M8), so it counts whether or not the job is currently scheduled.
Assumptions it relies on
  • A1. P and E are known per job when it arrives (implicit; they are Algorithm 1's inputs).
  • A2. A job's peak equals P + E, and both are constant (implicit).
  • A3. Salus is the only user of the GPU's memory, and C is the usable capacity after driver and context overheads (implicit).
If an assumption changes
  • A1 changes (E measured from the first iterations): Figure 2's warm-up spike is about 2.5 GB above the steady peak; measuring E early overestimates the lane (wasted space), measuring in steady state underestimates the warm-up (a possible overflow at start) (read-off and inference).
  • A2 changes (E varies): the guarantee is only as good as the maximum used; a safety margin or a dynamic resize would be needed (inference).
  • A3 changes (driver and CUDA context reserve part of the 16 GB, general knowledge): C must be the usable amount, not the nominal 16 GB, or the condition passes while allocations fail (inference).
Design notes and rejected alternatives

The condition is conservative by design: it ignores that the peaks of different lanes rarely coincide in time. An overcommitting variant (admit if the expected sum fits) would pack more but reintroduce the out-of-memory risk that the GPU cannot recover from by paging. The paper does not explore such a variant.

Connections

ESX: ESX admits VMs against a reservation and overcommits the rest, relying on ballooning and swapping to recover; Salus admits only against worst-case reservations because its device has no cheap recovery path (inference). Leases: both bound the damage of a component misbehaving by fixing a budget in advance, time for leases, memory for lanes (inference).

M15 · Lane auto-defragmentation at iteration boundaries

TL;DR
ProblemLanes move fragmentation from inside a lane to "fragmentation at the lane level": when a lane in the middle is released, a hole appears between lanes.
MechanismAt its next iteration boundary, a lane below the hole simply starts its next iteration higher up, closing the hole; its previous iteration's data is already dead, so nothing is copied.
Trade-offDefragmentation "almost automatically at no cost", but only at iteration boundaries and only for the ephemeral region.
Breaks whenSomething in a lane survives the iteration, or a lane's job never reaches a boundary (very long iterations).
Key points
  • "Having lanes does not eliminate memory fragmentation, it moves fragmentation within lane to fragmentation at the lane level. However, defragmentation is much easier at this level."
  • "Traditionally, defragmentation is achieved by first moving data out of memory and later moving it back again. In case of lanes, the allocations are released completely at the end of each iteration ... they are ephemeral memory after all. Therefore, defragmentation happens almost automatically at no cost: no extra memory movement is needed."
  • "Consider the situation illustrated in Figure 6b, when job C stops, its lane space is quickly reclaimed (the red arrow) at the iteration boundary by job B that was allocated below it."
  • "Implementation-wise, the system is event-driven, and reacts when there are jobs arriving or finishing, or at iteration boundaries when auto defragmentation happens."
How it works, step by step: Figure 6b with sizes
  1. Iteration k−1: the ephemeral region holds, from the top, A's lane (2 GB), C's lane (4 GB) and B's lane (3 GB): addresses 16 to 14, 14 to 10, 10 to 7 GB (illustrative sizes; the order is Figure 6b's).
  2. C stops (finishes or is removed). Its 4 GB lane becomes a hole between A's and B's lanes: the free space is now 14 to 10 GB plus the middle gap below 7 GB, two pieces.
  3. Iteration k: B's iteration is still running in 10 to 7 GB; its data is live, so it cannot move yet.
  4. B's boundary (k to k+1): B's ephemeral memory is all freed. Its lane is re-placed directly under A's: 14 to 11 GB. B's next iteration allocates there. Nothing was copied.
  5. Result: free space is one contiguous gap again (below 11 GB), available for a new lane or for persistent memory of a new job.
  6. A traditional compactor would have had to copy B's 3 GB of live data upward while B was paused: at about 730 GB/s of device bandwidth that is roughly 8 ms (3 GB read plus 3 GB written), and during the copy B would be stopped (general knowledge for the bandwidth; this guide's arithmetic).
Assumptions it relies on
  • A1. All of a lane's allocations are freed at every iteration boundary (stated).
  • A2. Every job reaches iteration boundaries frequently (stated: tens of ms to a few seconds).
  • A3. Lanes can be re-placed at any address, i.e. nothing outside the iteration holds pointers into a lane (implicit).
If an assumption changes
  • A1 changes: a surviving allocation pins the lane in place; the hole above it stays until the job ends (inference).
  • A2 changes (one job with 30 s iterations): the hole persists for up to 30 s, delaying admission of jobs that need contiguous space (inference).
  • A3 changes (cached device pointers, e.g. pre-built kernel arguments reused across iterations, general knowledge of graph-capture techniques): moving the lane would invalidate them (inference).
Design notes and rejected alternatives

Rejected: conventional defragmentation by moving data out and back. The paper's cost claim, "at no cost", refers to data movement; the lane still waits for its own boundary, and the persistent region gets no such treatment. Growing a lane in the middle of the stack (Algorithm 1's resize, M16) also needs the lanes below it to move, which the same mechanism allows at their boundaries (inference).

Connections

LFS: the cleaner's cheapest case is a segment with no live data, which can be reused without copying; every lane is such a segment at every iteration boundary (inference). Superpages: the Superpages paper's contiguity-aware page daemon works hard to recover contiguous free regions because pages are live; Salus recovers contiguity for free because the data is dead (inference). F2FS: F2FS likewise prefers to clean sections with the fewest valid blocks; zero valid blocks is the free case (inference).

M16 · Lane assignment: Algorithm 1

TL;DR
ProblemWhen a job arrives, Salus must choose: open a new lane, share an existing one, enlarge one, or make the job wait, without breaking the safety condition.
MechanismAlgorithm 1 "Find GPU Lane for Job": (1) new lane of size E if everything fits; (2) else an existing lane with Lj ≥ E that "is the best match"; (3) else the smallest lane that can be grown to E within capacity; (4) else "not found".
Trade-offSimple, greedy and fast, in exchange for no attempt at an optimal number or sizes of lanes ("an open question").
Breaks whenJob mixes need re-partitioning of existing lanes, or when the joining branch is taken without room for the new job's persistent memory (see below).
Key points
  • "It is vital to determine the size and number of lanes in the GPU, as well as how lanes are assigned to jobs. Salus uses a simple yet efficient algorithm to decide between opening a new lane and putting jobs into existing lanes."
  • Inputs: "P: the job's persistent memory requirement; E: the job's ephemeral memory requirement; C: total memory capacity of the GPU; Pi: persistent memory usage of existing job i; Lj: lane size of existing lane j; 𝕃: set of existing lanes".
  • Line 2: "if Σi Pi + P + Σj Lj + E ≤ C then lane ← new GPU lane with capacity E". Lines 6 to 10: "for all j ∈ 𝕃 do if Lj ≥ E and is the best match then return j". Lines 11 to 16: "for r ∈ 𝕃 in Lr ascending order do if Σi Pi + P + Σj Lj − Lr + E ≤ C then Lr ← E; return r". Line 17: "return not found".
  • "How to reorganize lane assignments is an open question. We find the one implemented in our algorithm works fairly well in practice, but there are more possibilities about finding the optimal number of lanes given a set of jobs."
How it works, step by step: four arrivals on a 16 GB GPU
  1. Job 1 (P 1.0, E 6.0) on an empty GPU: line 2: 0 + 1.0 + 0 + 6.0 = 7.0 ≤ 16 → new lane L1 = 6.0. State: ΣP = 1.0, lanes {6.0}.
  2. Job 2 (P 0.5, E 4.0): line 2: 1.0 + 0.5 + 6.0 + 4.0 = 11.5 ≤ 16 → new lane L2 = 4.0. State: ΣP = 1.5, lanes {6.0, 4.0}, total 11.5.
  3. Job 3 (P 0.5, E 5.0): line 2: 1.5 + 0.5 + 10.0 + 5.0 = 17.0 > 16. Lines 6 to 10: L1 = 6.0 ≥ 5.0 (L2 = 4.0 is too small), so join L1. Check by hand: 2.0 + 10.0 = 12.0 ≤ 16, safe. Job 3 time-shares L1 with job 1.
  4. Job 4 (P 0.5, E 8.0): line 2: 2.0 + 0.5 + 10.0 + 8.0 = 20.5 > 16. No lane ≥ 8.0. Lines 11 to 16, ascending: r = L2 (4.0): 2.0 + 0.5 + 10.0 − 4.0 + 8.0 = 16.5 > 16, no. r = L1 (6.0): 2.0 + 0.5 + 10.0 − 6.0 + 8.0 = 14.5 ≤ 16 → L1 ← 8.0, job 4 joins L1. State: ΣP = 2.5, lanes {8.0, 4.0}, total 14.5.
  5. Job 5 (P 0.5, E 9.0): no new lane (2.5 + 0.5 + 12 + 9 = 24), no lane ≥ 9, grow L2: 3.0 + 12 − 4 + 9 = 20 > 16; grow L1: 3.0 + 12 − 8 + 9 = 16.0 ≤ 16 → L1 ← 9.0. Exactly at capacity.
  6. Note on lines 11 to 16: they are reached only when no lane has Lj ≥ E, so "Lr ← E" always enlarges a lane, never shrinks one. Enlarging L1 in the middle of the ephemeral stack needs the lanes below it to shift, which can happen only at their iteration boundaries (M15; inference).
A gap in the pseudocode: the joining branch does not check P

Lines 6 to 10 return an existing lane whenever Lj ≥ E, with no capacity test. Joining a lane adds the new job's P to the persistent sum, so the resulting total is Σi Pi + P + Σj Lj, which line 2's failure does not bound. Example: lanes {7, 6} (13 GB), ΣPi = 2.5 GB, arriving job P = 1.0, E = 5. Line 2: 2.5 + 1.0 + 13 + 5 = 21.5 > 16; line 7: the 6 GB lane fits E = 5 and is returned. New total: 2.5 + 1.0 + 13 = 16.5 > 16, which violates the safety condition the paper says "is always kept" (this guide's arithmetic). Either the implementation adds a check that the printed pseudocode omits, or the condition can be broken in this case; the paper does not say which.

Assumptions it relies on
  • A1. P and E are known on arrival (stated as inputs).
  • A2. Greedy, one-job-at-a-time decisions are good enough (stated: "works fairly well in practice").
  • A3. Lanes can be enlarged later at iteration boundaries (implicit in line 13).
  • A4. A job that gets "not found" can wait (stated in Section 3.1: the lane request "can block and the session will be queued").
If an assumption changes
  • A1 changes: the algorithm cannot run; an estimate must be supplied, with the risks in M14 (inference).
  • A2 changes (arrivals in a burst, as in hyper-parameter search): placing jobs one by one can leave lanes sized for early jobs; a batch assignment (bin packing over the whole set) could open fewer, better-sized lanes (inference; the paper calls this open).
  • A3 changes (a lane cannot move because a job in it has long iterations): the enlargement waits; the new job's admission is delayed (inference).
  • A4 changes (latency-critical inference arrivals): "not found" means a request stream with no GPU; a serving system would have to send it elsewhere, which the paper leaves to future auto-scaling work.
Design notes and rejected alternatives

"Best match" is not defined; the smallest lane with Lj ≥ E (best fit) is the natural reading (inference). The order of preferences (new lane first) favors concurrency over packing tightly; PACK in Section 4.1 describes putting jobs "in separate GPU lanes", consistent with that preference. Shrinking lanes when a large job leaves is not in Algorithm 1; the event-driven reorganization at iteration boundaries is described only in prose (M15).

Connections

Superpages: new region, then best fit, then grow, then wait is a placement policy with admission control, like an allocator choosing a free extent before falling back (inference). Hints: "keep it simple" and "do one thing well": the greedy rule is deliberately simple, with optimality left open (inference).

M17 · PACK: put jobs in separate lanes to raise utilization

TL;DR
ProblemWhen many jobs are ready at once (hyper-parameter search, low-traffic inference), running them one at a time leaves memory and compute idle and stretches makespan.
Mechanism"many jobs with different GPU memory requirements can be packed together in separate GPU lanes based on their memory usages", subject to the safety condition; "No fairness is considered among lanes."
Trade-offShorter makespan and fewer GPUs, in exchange for slower individual jobs (they share compute) and no fairness between lanes.
Breaks whenCompute, not memory, is the bottleneck: resnet50_50 gains only 1.07×.
Key points
  • "packing too many lanes exceeding the GPU memory capacity will either crash the jobs or incur costly paging overhead (if memroy overcommit is enabled), both of which would do more harm than good. Consequently, this policy works with 'safety' condition to ensure that the total peak memory usage across all lanes is smaller than the GPU memory capacity."
  • "By simultaneously holding many models in the same GPU's memory, Salus can significantly decrease the GPU requirements of model serving systems like Clipper."
  • Evaluation: makespan 287.4 min versus FIFO 303.4 min on the 100-job trace ("because of online job arrivals, we do not observe large improvement from PACK"); 2.38× (superres_128) and 1.07× (resnet50_50) on 300-job hyper-parameter sets; 42 inference models on 1 GPU (Section 5.3, which does not name the policy used).
  • For resnet50_50: "while the GPU has enough memory, computation becomes the bottleneck under such heavy sharing."
How it works, step by step: packing a hyper-parameter sweep of superres_128
  1. 300 jobs arrive together. superres peaks at ≈1.0 GB in Figure 1 (read-off; assuming the bar is the largest batch size, 128) with an average of ≈0.1 GB.
  2. By memory alone, at most about 16 / 1.0 = 16 jobs (fewer after persistent memory) could each have their own lane at once (this guide's arithmetic; the paper does not report how many lanes PACK opened).
  3. Measured: makespan ≈480 min under FIFO in TensorFlow versus ≈200 min under Salus (Figure 11 read-off), the paper's 2.38×. So 300 jobs take ≈1.6 min each under FIFO and the effective rate under Salus is ≈1.5 jobs per minute.
  4. Per-iteration overhead: Figure 12 shows superres at 1.83× TensorFlow's per-iteration time (largest batch size). To still be 2.38× faster overall, the packed jobs must collectively deliver 2.38 × 1.83 ≈ 4.4 times the throughput of one job running alone under Salus (this guide's arithmetic): about four or more jobs' worth of useful concurrency.
  5. Why not 15×: concurrency across lanes is limited by the GPU's compute and by the service's CPU work for each job; memory was not the limit (inference).
  6. resnet50_50: Figure 11 ≈615 min (TF) versus ≈575 min (Salus), 1.07×. Each job already keeps the GPU busy, so co-running only time-slices the same compute.
Assumptions it relies on
  • A1. Jobs do not use all of the GPU's compute alone (implicit; stated as the reason resnet50_50 gains little).
  • A2. Many jobs are ready at the same time (stated: "especially useful when many/all jobs are ready to run").
  • A3. Memory needs are known so the safety condition can be checked (stated).
If an assumption changes
  • A1 changes (compute-saturating jobs): packing gives near 1× (resnet50_50) and makes each job slower, which hurts if early results are used to kill poor configurations (inference).
  • A2 changes (online arrivals): few jobs overlap, so the 100-job trace shows only 303.4 → 287.4 min (5.3%).
  • A3 changes: overpacking crashes jobs or pages; the paper explicitly refuses that.
Design notes and rejected alternatives

PACK is a policy over Algorithm 1: open new lanes while the safety condition allows. It does not choose which jobs to co-locate by compute profile, and it has no fairness across lanes, so a lane of small jobs and a lane with a large job progress at whatever rates the GPU's stream scheduling gives them (inference).

Connections

ESX: consolidating idle servers into fewer machines; Salus does it for inference models (42 → 1 GPU) without overcommit (inference). vLLM: batching many requests on one GPU to raise throughput is vLLM's goal; vLLM shares one model's weights across all requests, Salus packs different models (inference).

M18 · SRTF: preempt the long job for the short one

TL;DR
ProblemUnder FIFO a short test run waits for a long training job: HOL blocking.
MechanismShortest remaining time first with preemption at iteration boundaries; "The higher priority job is admitted as long as its own safety condition is met ... i.e., at least, it can run alone on the GPU ... regardless of other already-running jobs."
Trade-offAverage JCT 170.6 → 53.4 min (3.19×), in exchange for needing job durations and for starving long jobs while shorter ones keep arriving.
Breaks whenDurations are unknown or wrong, or paused jobs' persistent memory leaves no room to admit the short job.
Key points
  • "Instead of waiting for an on-going large training to finish, Salus can enable preemption ... the large job is paused ... to let the smaller one finish faster. This way, Salus can support job priorities based on arbitrary criteria, including size and/or duration to implement the shortest-remaining-time-first (SRTF) policy."
  • "Note that we assume the job execution time is known and thus it is possible to implement SRTF ... the subject is beyond the scope of this paper."
  • Table 1: SRTF average queuing 28.6 min (FIFO 167.6), average JCT 53.4 min (FIFO 170.6), 95th percentile JCT 217.0 min (FIFO 251.1), makespan 306.0 min (FIFO 303.4).
  • Figure 8a (a slice of the trace, "time is normalized"): "When job #1 arrives, the background job #0 is immediately stopped and Salus switches to run the newly arrived shorter job. Job #2 comes early than job #3, but since #3 is shorter, it is scheduled first. And finally since job #5 is shorter, #4 is preempted and let #5 run to completion. During the process, the background job #0 is only scheduled when there is no other shorter job existing."
How it works, step by step: the Figure 8a slice, as read off the plot
  1. 0 to 6 s: background job 0 runs; job 1 is in the "queuing" state (the paper's grey) for about 6 s; jobs 2 and 3 are already queued.
  2. 6 to 40 s: job 1 runs to completion (≈34 s active). Job 0 gets a sliver at ≈41 s, then job 3 (≈42 s of work) runs 41 to 83 s, before job 2 (≈53 s), as the paper says.
  3. 83 to 136 s: job 2 runs. Job 4 arrives at ≈127 s and waits.
  4. 136 to 139 s: job 0 runs briefly while job 4 is still marked as queuing; job 4 starts at ≈139 s.
  5. 158 s: job 5 (arrived ≈153 s) starts and job 4 is paused; job 5 runs 158 to 228 s (≈70 s); job 4 resumes 228 to 246 s; job 0 runs from 246 s.
  6. A puzzle in the plot: job 4's total active time is ≈19 + 18 = 37 s and its remaining time when job 5 arrived was ≈18 s, while job 5 ran ≈70 s. With true remaining times, SRTF would not preempt job 4 for job 5. The plot fits the text only if the scheduler's duration estimates differed from the actual run times, or the per-row time scales differ ("time is normalized" is not explained) (read-off; listed as an inconsistency in Reference).
  7. The queuing stretches before jobs start (≈6 s for job 1, ≈5 s for job 5, ≈12 s for job 4 of which ≈9 s while job 2 legitimately ran) suggest that a newly arrived job needs a few (normalized) seconds of setup (session creation, graph transfer, lane request) before it can preempt; job 0 keeps the GPU busy meanwhile (inference).
Assumptions it relies on
  • A1. Job durations are known (stated).
  • A2. Preemption is cheap (stated, M8).
  • A3. The new job's needs fit beside the paused jobs' persistent memory (implicit; the paper states only that the job's "own safety condition" must hold, "i.e., at least, it can run alone on the GPU", and does not say whether paused jobs' persistent memory counts).
  • A4. The trace is a single lane (stated for Section 5.1.2: "In both cases, we consider a single GPU lane").
If an assumption changes
  • A1 changes (estimates off by a factor): SRTF can preempt the wrong job (possibly what Figure 8a shows); with very poor estimates its average JCT advantage shrinks toward that of a random preemptive order (inference).
  • A2 changes (checkpoint-cost preemption): each preemption costs seconds or more; short jobs, the whole point of SRTF, pay the most (inference from Observation 1).
  • A3 changes (many paused large jobs): with resnet152_75-sized jobs (P = 0.82 GB, E ≈ 13.0 GB if peak 13.8 = P + E), a single lane fits n jobs only while 0.82n + 13.0 ≤ 16, so n ≤ 3. A fourth job, however short, cannot be admitted until one finishes: SRTF degrades to FIFO for it (this guide's arithmetic; Class Prep C2).
  • A4 changes (several lanes): a short job could run in a second lane next to the long one instead of preempting it, if memory allows; this mixes PACK and SRTF, which the paper does not evaluate (inference).
Design notes and rejected alternatives

SRTF here is a demonstration that preemption is cheap enough to schedule this way, not a proposal for a production policy. The phrase "regardless of other already-running jobs" means a higher-priority job does not need room to run beside them, only room to run alone with them paused; their persistent memory still counts (inference from M8 and M14). The 95th percentile JCT (217.0 min) is also better than FIFO's (251.1), so in this trace the starvation of long jobs did not show up in the tail.

Connections

Livelock: SRTF's risk is starvation of long jobs, as receive-livelock starves the user process when interrupts always win; both need a bound or quota to guarantee progress (inference). vLLM: vLLM preempts requests when KV cache runs out (first-come-first-served with swap or recompute); Salus preempts by priority without moving memory (inference).

M19 · FAIR: equalize service among jobs in a lane

TL;DR
ProblemDuring high contention, users may want every job to progress, not the lowest average JCT.
Mechanism"we admit new jobs into the GPU while maintaining the safety condition, and equalize total service over time for jobs in each lane."
Trade-offEqual shares that adapt within seconds, in exchange for later completion of each job and a worse 95th percentile JCT than FIFO in the trace (281.2 versus 251.1 min).
Breaks whenJobs in different lanes need fairness between them (not provided), or iterations are long so turns are coarse.
Key points
  • "Note that there may be many different so-called fair algorithms based on time sharing; we demonstrate the feasibility of implementing one or more of them instead of proposing the optimal fairness policy."
  • Figure 9: three inception3_50 jobs "start at time 0s, 15s and 30s. At 15s, when the second job starts, while the total throughput remains unchanged, each job's share is halved. It further reduces to about a third when the third job arrives. Similarly, the reverse happens when jobs finishes in the reverse order. The system throughput roughly remains the same throughout the experiment. Note that Salus reacts almost immediately for job arriving and leaving events."
  • "In contrast, FIFO scheduling or other sharing policies (e.g., MPS) cannot enforce fair sharing."
  • Table 1: FAIR average JCT 96.6 min, average queuing 58.5 min, makespan 301.6 min.
How it works, step by step: Figure 9 with numbers read off the plot
  1. 0 to 15 s: job 1 alone, ≈128 images per second.
  2. 15 s: job 2 arrives. Within about a second both run at ≈64 images per second; aggregate ≈128. Each job's iterations alternate in the single lane.
  3. 30 s: job 3 arrives. Individual rates spread between ≈35 and ≈60 images per second; aggregate ≈130 to 150, with spikes near 170.
  4. ≈68 s: job 3 finishes; jobs 1 and 2 return to ≈64 each. ≈86 s: job 2 finishes; job 1 returns to ≈128. ≈98 s: job 1 finishes.
  5. Work per job (this guide's integration of the read-off rates): job 3 ≈1,800 images, job 2 ≈3,800, job 1 ≈7,300. The jobs ran different amounts of work, which is why they finish in reverse order of arrival.
  6. What "equalize total service" means here: the late-arriving job 3 does not get the whole GPU until it catches up with jobs 1 and 2; it gets about a third. So the policy as measured equalizes the rate of service from now on, not cumulative service since arrival (inference from the plot).
Assumptions it relies on
  • A1. Jobs in a lane have comparable iteration lengths, or service is measured in time rather than iterations (implicit; the experiment uses identical models to avoid the question).
  • A2. One lane (stated for this experiment).
If an assumption changes
  • A1 changes (a 2 s-iteration job shares a lane with a 50 ms one): equal turns would give the long job 40× the GPU time; equal time requires the short job to run about 40 iterations per turn of the long one (inference).
  • A2 changes (several lanes): FAIR equalizes within each lane; jobs in different lanes are not equalized, so a lane holding one job gets that lane's full stream (inference from "for jobs in each lane").
Design notes and rejected alternatives

The aggregate rising above the single-job rate with three jobs (≈140 versus ≈128) while only one iteration runs at a time in the lane suggests that one job's CPU-side work overlaps another's GPU work (inference; the paper says only that throughput "roughly remains the same"). The paper does not define the service metric (iterations or GPU time).

Connections

Lottery and stride scheduling, fair-share CPU schedulers: equal service over time is their goal; Salus's quantum is one iteration (general knowledge; inference). Livelock: fair round-robin among sources is what the Livelock paper uses to keep one source from monopolizing the CPU (inference).

F7 · Algorithm 1: "Find GPU Lane for Job"

L · Stated limitations and future work

What the paper itself says is unfinished
  • Policy: "Salus provides a mechanism but the question of policy ... what is the best scheduling algorithm for DL jobs running on a shared GPU? ... remains open."
  • Lanes: "How to reorganize lane assignments is an open question ... there are more possibilities about finding the optimal number of lanes given a set of jobs."
  • Scope: "Salus can be extended to multiple GPUs or even other accelerators on the same machine", and "we plan to extend it to GPUs across multiple machines leveraging RDMA" (remote direct memory access).
  • Inference: "A future work is to detect current request rate for inference jobs and automatically scale up or down horizontally."
  • SRTF: job execution time is assumed known; estimation "is beyond the scope of this paper".
  • Engine: CPU computation in Salus's execution engine "is not yet heavily optimized" (vae, superres ≈1.8× per iteration).
  • Prior kernel-level design: "too much overhead for little gain" (no numbers).
What the evaluation does not cover (this guide's list)
  • How P and E are obtained before admission, and what happens if they are wrong or vary across iterations.
  • A direct measurement of switch latency; only plots at seconds scale (Figure 8b) and normalized time.
  • Compute interference between lanes and any form of performance isolation, which the paper criticizes other approaches for lacking.
  • Holes in the persistent region when jobs leave; only lane defragmentation is described.
  • Fault isolation: one service process for all jobs on a GPU.
  • Distributed (multi-GPU) training jobs, frameworks other than TensorFlow 1.5, and dynamic-shape models.
  • Mixed policies (PACK with SRTF) and fairness across lanes; one training trace of 100 jobs.
  • Whether FIFO in Table 1 ran in Salus or in plain TensorFlow, which decides what the "little overhead" inference shows.
  • The tail of inference latency; only averages per model are plotted.

C · Connections to the other CS240 papers (mechanical only)

  • vLLM (11/19): the same problem, GPU memory for DL, in the opposite regime (S). Both separate static weights from dynamic per-iteration or per-request memory, and both schedule at iteration granularity.
  • ESX: consolidating idle servers (42 inference models on 1 GPU) is ESX's motive; ESX overcommits with ballooning, sharing and swapping, while Salus cannot overcommit because GPU paging (Unified Memory) was 698.45 s versus ≈89 s in Figure 13 (inference).
  • Superpages: lifetime-segregated regions and the fight against fragmentation that blocks large contiguous allocations; Salus's lanes are contiguous regions that can be compacted for free (inference).
  • Livelock: scheduling granularity and preemption points: Salus decides once per iteration rather than per kernel, as the Livelock fixes bound per-packet scheduling overhead; SRTF's starvation of long jobs mirrors receive livelock's starvation of user work (inference).
  • Exokernel: Salus exports two primitives and leaves policy to small modules (PACK, SRTF, FAIR), echoing "separate protection from management", but as a user-level service above the driver (inference).
  • x86 VMM and Dune: multiplexing hardware among clients that each think they own it; Salus does it at the framework's device interface, not at the instruction set (inference).
  • LFS and F2FS: cleaning is free when a segment holds no live data; every Salus lane is in that state at every iteration boundary (inference).
  • Mesa: preemption only at well-defined points (iteration boundaries) avoids reasoning about partially updated shared state, like switching only at monitor boundaries (inference).
  • Hints: make the common case fast (keep persistent memory resident), use batch processing (iteration-level control), keep it simple (greedy lane assignment) (inference).
  • NFS: the adaptor presents a remote service through a local device interface, as NFS presents a remote server through the vnode interface (inference).

Worked examples

① What Table 1 says about the trace, and where 3.19× comes from

Paper, Table 1: FIFO makespan 303.4, average queuing 167.6, average JCT 170.6 min; SRTF 306.0, 28.6, 53.4 min. 100 jobs.

  1. Headline: 170.6 / 53.4 = 3.195, printed as 3.19×.
  2. Mean job duration: under FIFO a job runs alone once started, so average JCT − average queuing = 170.6 − 167.6 = 3.0 min is the mean run time (assuming "queuing" is time before first start).
  3. Busy GPU: 100 × 3.0 = 300 min of work against a 303.4 min makespan: the GPU was idle only about 1% of the time under FIFO. Jobs mostly waited; the average job waited 56 times its own run time (167.6 / 3.0).
  4. SRTF: queuing falls to 28.6 min; JCT − queuing rises to 24.8 min because started jobs are often paused for shorter ones.
  5. Makespan: SRTF 306.0 versus 303.4 (+0.9%): total work is the same, so the extra 2.6 min roughly bounds what SRTF's preemptions cost relative to this FIFO run (the paper does not say whether its FIFO ran on Salus or on plain TensorFlow).
🍯
The trace is heavily loaded (almost no idle time), which is the regime where reordering, not packing, gives the large gain: SRTF moves waiting from short jobs to long ones without changing the total.

② The price of switching by copying versus keeping state resident

Paper: persistent memory up to 822.2 MB (resnet152_75); Figure 4 assumes 30 GB/s. Figure 2: ≈0.6 s per resnet101_75 iteration (read-off). PCIe 3.0 x16 ≈ 12 to 16 GB/s is general knowledge.

  1. One direction at 30 GB/s: 0.8222 GB / 30 GB/s = 27.4 ms. A switch evicts one job and loads another: ≈55 ms.
  2. At 16 GB/s: 51 ms each way, ≈103 ms per switch; at 12 GB/s, ≈137 ms.
  3. Relative to a training iteration of 0.6 s: 9% to 23% if switching every iteration, as FAIR in one lane does.
  4. Relative to inference: alexnet weights ≈244 MB (61 M parameters, general knowledge) take 8.1 ms at 30 GB/s against ≈3 ms of inference (Figure 10): 2.7×.
  5. Salus: 0 bytes; the cost is 0.82 GB of GPU memory held by every paused job of this size.
💡
Observation 1 is decisive for inference and for per-iteration time sharing; for training jobs switched every few minutes the copy would cost well under 1%, which is why minute-scale systems such as Gandiva can afford checkpoints.

③ How many resnet152_75 jobs can SRTF keep paused on one 16 GB GPU?

Paper: P = 822.2 MB; peak 13.8 GB (text). Assumption (inference): peak = P + E, so E ≈ 13.0 GB. Single lane, as in Section 5.1.2.

  1. Safety condition with n such jobs in one lane: 0.822 n + 13.0 ≤ 16.
  2. Solve: n ≤ 3.0 / 0.822 = 3.65, so n = 3. Check: 2.47 + 13.0 = 15.47 ≤ 16; n = 4: 3.29 + 13.0 = 16.29 > 16.
  3. Consequence: with three of them admitted, a fourth arrival must wait, even if it is the shortest job in the system. If the figure's 14.6 GB peak is used instead, E ≈ 13.8 and n ≤ 2.2/0.822 = 2.7, so only two.
  4. Mixed case: two resnet152_75 jobs (1.64 GB) plus a googlenet_25 job (0.11 GB) leave 16 − 13.0 − 1.75 = 1.25 GB; a fourth small job with P ≤ 1.25 GB and E ≤ 13.0 GB can still join the lane.
🍯
Fast switching is bounded by how much persistent memory fits beside the largest lane; big-activation jobs leave little room for paused neighbors.

④ Running Algorithm 1, and catching the missing check

C = 16 GB. Existing: ΣPi = 2.5 GB, lanes {7.0, 6.0}. Illustrative numbers.

  1. Current total: 2.5 + 13.0 = 15.5 ≤ 16. Safe.
  2. New job P = 0.4, E = 2.0. Line 2: 2.5 + 0.4 + 13.0 + 2.0 = 17.9 > 16, no new lane.
  3. Lines 6 to 10: both lanes ≥ 2.0; best match (smallest that fits) = 6.0. Return it. New total: 2.9 + 13.0 = 15.9 ≤ 16. Safe.
  4. Another job P = 1.0, E = 5.0 on the original state: line 2 gives 21.5 > 16; lines 6 to 10 return the 6.0 lane; new total 3.5 + 13.0 = 16.5 > 16. The printed algorithm admits it and the safety condition fails.
  5. Correct behavior (what the condition requires): "not found", because joining any lane gives 3.5 + 13.0 = 16.5 > 16; the job waits. Simply falling through to line 11 would not give that: line 12 for r = 6.0 computes 2.5 + 1.0 + 13.0 − 6.0 + 5.0 = 15.5 ≤ 16 and would set that lane to 5.0, shrinking it below jobs already in it. Lines 11 to 16 are safe only when every lane is smaller than E, which is the only way they are reached in the printed algorithm (this guide's arithmetic).
💡
Joining a lane does not grow the lane, but it does grow the persistent sum. Any admission rule must re-check Σ P + Σ L ≤ C, not just L ≥ E.

⑤ superres_128: 1.83× slower per iteration, yet 2.38× faster overall

Figure 12: superres (largest batch, 128) per-iteration time in Salus = 1.83 × TensorFlow. Figure 11: 300 superres_128 jobs, Salus ≈200 min, TF ≈480 min (2.38× in the text). Figure 1: superres peak ≈1.0 GB.

⑥ Do 42 inference models plausibly fit on one 16 GB GPU?

Problem 1 · easy
Classify each as model, ephemeral or framework-internal memory in the paper's taxonomy, and say which are persistent: (a) the weights of a convolution layer; (b) the output of that layer during the forward pass; (c) a buffer of the input pipeline holding the next batch; (d) the momentum values of the optimizer.
Show answer

Problem 2 · easy
Why does Salus switch jobs only at iteration boundaries rather than at any moment the scheduler wants?
Show answer
At a boundary the departing job's ephemeral memory has been freed, so nothing but its persistent memory remains, and that stays resident. Switching mid-iteration would leave gigabytes of live activations that would have to be kept (occupying the lane) or copied out. Kernel-level switching was also tried and rejected for overhead and for breaking kernel batching and pipelining.Misconception: that the choice is about fairness or simplicity only. It is what makes a switch free of data movement.
Problem 3 · easy
The abstract claims "42× over not sharing the GPU and 7× over NVIDIA MPS" for inference. What quantities produce 42 and 7?
Show answer
Number of GPUs needed to host 42 low-rate inference instances (14 models × 3): 42 without sharing, 6 with MPS, 1 with Salus. 42 / 1 = 42 is Salus over no sharing. Salus over MPS is 6 / 1 = 6, not 7. The number 7 is 42 / 6, which is MPS's own improvement over no sharing (or the number of models MPS fits per GPU). Measured as models per GPU, Salus holds 42 and MPS 7, again a ratio of 6. The abstract's "7× over NVIDIA MPS" does not follow from Figure 10 (an inconsistency, listed in Reference).Misconception: accepting a ratio without recomputing it from the figure; "7" appears in the data, but as MPS versus no sharing.

Problem 12 · hard

Show answer

Connecting outward

What Salus teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

Lifetime is the property that matters, not size or type

Salus's whole design rests on one classification: does this allocation survive the iteration? Persistent memory is placed once and never moved; ephemeral memory is placed in a region that is guaranteed empty at known moments, which makes moving, resizing and compacting that region free. Memory tiers can use the same lever: data whose lifetime is known (scratch that dies at a phase boundary, state that lives for the whole job) can be placed where its access pattern and endurance needs are best served, and regions that are periodically dead never need copying to reorganize.

The cheapest migration is the one you schedule for when the data is dead

Traditional defragmentation and checkpointing move live data. Salus waits for the moment the data is dead (the iteration boundary) and then reorganizes for nothing. LFS cleaning and flash garbage collection are cheapest on empty segments for the same reason. Any system with phases (training iterations, request completions, epoch boundaries, garbage-collection cycles) can align its expensive reorganizations with the phase ends and pay only the waiting time.

No paging forces admission control

A CPU OS can overcommit memory because it can page. The GPU here cannot (Unified Memory was ≈7.9× slower than static partitioning with MPS in Figure 13), so Salus reserves each lane's worst case and refuses jobs that would not fit. Devices without a cheap fallback tier (on-chip SRAM, device memory, persistent memory used as a cache) push systems toward reservation and admission control; adding a fast enough fallback tier is what would let them overcommit, which is exactly the role vLLM gives CPU memory for KV cache blocks.

Resident state is the price of fast switching

Switching costs nothing because every paused job's parameters stay on the GPU; the price is memory held by jobs that are not running, which caps how many jobs can be admitted (three resnet152_75-sized jobs per lane, Worked Example ③). The same trade appears with CPU context switches that keep page tables and caches warm, and with tiered memory where keeping a working set in the fast tier avoids migration on every phase change. The question to ask is always: what is the smallest state whose residency makes a switch free?

Predictable periodicity is a scheduling resource

The paper's memory traces repeat every ≈0.6 s with the same peak. That predictability gives safe preemption points and sizes for reservations without any learning. Workloads with stable periodic behavior (DL iterations, batch phases, refresh cycles in DRAM, wear-leveling epochs in flash) let a manager act at the period boundary with full knowledge; workloads without it need either overprovisioning or a recovery path.

Sharing does not create bandwidth or compute

superres_128 gained 2.38× from packing; resnet50_50 gained 1.07× because one job already used the compute. Packing raises utilization only where a resource is idle; when it is not, sharing just slices it. For memory systems the analogous trap is consolidating workloads onto one device by capacity when they will contend for its bandwidth.

Questions with real answers

Each one is a tricky case the paper does not spell out, but it has a definite answer you can work through from the paper's own numbers. The quoted block is how to ask it in class. Try your own answer before opening the worked one.

C1 · Can Algorithm 1 break its own safety condition?

The paper says the safety condition, Σ Pi + Σ lane sizes ≤ C, "is always kept". But in Algorithm 1, lines 6 to 10 return an existing lane whenever Lj ≥ E, with no capacity test, and joining a lane still adds the new job's persistent memory P. Suppose I have a 16 GB GPU with lanes of 7 and 6 GB and 2.5 GB of persistent memory, and a job with P = 1 GB and E = 5 GB arrives. What does the printed algorithm do, and does the condition still hold?

AnswerWork it out first, then open▾

Line 2: 2.5 + 1 + 13 + 5 = 21.5 > 16, so no new lane. Lines 6 to 10: the 6 GB lane is ≥ 5 and is the best match, so it is returned. The job's 1 GB goes into the persistent region: 3.5 + 13 = 16.5 GB > 16. The condition is violated by 0.5 GB.

The fix is a test on line 7 that Σ Pi + P + Σ Lj ≤ C, and "not found" when it fails: joining either lane gives 16.5 GB, so the job must wait. (Falling through to line 11 as printed would not do it: for the 6 GB lane, 2.5 + 1 + 13 − 6 + 5 = 15.5 ≤ 16, and line 13 would shrink that lane to 5 GB under the jobs already in it.) Either the implementation has this check and the pseudocode omits it, or admission can overcommit in this case; the paper does not say which.

Where the answer comes from: Algorithm 1 as printed (Section 3.3.2) and the safety condition's definition; the numbers are this guide's example.

C2 · How many paused jobs can SRTF keep, and what happens to the next short one?

SRTF admits a higher-priority job "as long as its own safety condition is met ... i.e., at least, it can run alone on the GPU", and fast switching works by never evicting persistent memory. resnet152_75 has 822.2 MB of persistent memory and peaks at 13.8 GB. If I keep everything in a single 16 GB lane, how many such jobs can be resident at once, and what happens to a fourth one that is the shortest job in the system?

AnswerWork it out first, then open▾

If peak = P + E, then E ≈ 13.0 GB. One lane: 0.822 n + 13.0 ≤ 16 gives n ≤ 3.65, so three. Three use 2.47 + 13.0 = 15.47 GB; a fourth makes it 16.29 GB.

The fourth job cannot be admitted, however short, until one of the three finishes; SRTF cannot preempt for it because preemption here never frees persistent memory. For that job the policy behaves like FIFO. With Figure 1's ≈14.6 GB bar instead of the text's 13.8, only two fit. The paper's single-lane experiments do not hit this case. This answer counts paused jobs' persistent memory, as the safety condition requires; the literal words "can run alone on the GPU ... regardless of other already-running jobs" would admit the fourth job (0.82 + 13.0 ≤ 16) only by breaking that condition, since the paper describes no way to evict a paused job's persistent memory.

Where the answer comes from: The persistent and peak numbers are the paper's (Section 2.1); peak = P + E is an inference; the arithmetic is this guide's.

C3 · Does Figure 8a actually show shortest-remaining-time-first?

The text says "since job #5 is shorter, #4 is preempted and let #5 run to completion." When I read Figure 8a, job 4 runs about 19 s, is paused, and later runs about 18 more seconds; job 5 runs about 70 s straight. At the moment job 5 starts, which job has less remaining time, and what does that say about how the scheduler ranks jobs?

AnswerWork it out first, then open▾

Either way the figure shows fast preemption, not that the ranking was right.

Where the answer comes from: Read-offs from Figure 8a (approximate) against the text of Section 5.1.2.

C4 · Figure 13: two one-minute jobs, average JCT ≈89 s. Is that sharing?

Figure 13 runs two alexnet_25 training jobs, "each runs for a minute", and reports average JCT: SP about 105 s, SP+MPS about 88 s, Salus about 89 s. If I assume each job needs one minute of work when it runs alone, what average JCT would simply running them one after the other give, and what does the figure then show?

AnswerWork it out first, then open▾

Sequentially: JCTs 60 and 120 s, average 90 s. Perfect time sharing with no overlap gain: both end at 120 s, average 120 s. Perfect overlap: both end at 60 s.

Salus and MPS at ≈88 to 89 s are about the same as running sequentially, so average JCT cannot distinguish sharing from no sharing here. If both jobs finished together at ≈89 s, they achieved about 120 / 89 ≈ 1.35× the throughput of one job alone, a real overlap gain; the figure does not show per-job times. What it does show: Salus matches MPS, SP is worse than sequential, and overcommit (698.45 s) is unusable.

C5 · How can superres_128 be 1.83× slower per iteration and 2.38× faster overall?

Figure 12 says superres (largest batch size, 128) takes 1.83× TensorFlow's time per iteration in Salus. Figure 11 says 300 superres_128 hyper-parameter jobs finish 2.38× faster in Salus than FIFO in TensorFlow. How many jobs' worth of concurrent progress do I need to get both numbers, and is memory the limit?

AnswerWork it out first, then open▾

One job in Salus runs at 1 / 1.83 = 0.55 of TensorFlow speed. To be 2.38× faster overall, the packed set must progress at 2.38 / 0.55 ≈ 4.4 Salus-speed jobs at once.

Memory is not the limit: superres peaks at ≈1.0 GB (Figure 1), so up to about 16 such lanes would fit in 16 GB. The limit is compute and the service's own CPU-side work, which is also where the 1.83× comes from. The result says packing helped this small model by more than four times its per-iteration overhead.

Where the answer comes from: Figures 11 and 12 (read-offs and printed values) and Figure 1's peak; the arithmetic is this guide's.

C6 · Do similar makespans in Table 1 prove "little overhead"?

The paper concludes from FIFO, SRTF and FAIR makespans of 303.4, 306.0 and 301.6 min that "Salus introduces little overhead." Table 1 also gives average JCT minus average queuing for FIFO as 170.6 − 167.6 = 3.0 min. What does that tell me about how busy the GPU was, and what exactly can the makespan comparison measure?

AnswerWork it out first, then open▾

Under FIFO a started job runs alone, so 3.0 min is the mean job duration; 100 jobs × 3.0 min = 300 min of work against a 303.4 min makespan: the GPU was busy about 99% of the time. In a saturated trace, makespan ≈ total work + overhead, so SRTF's extra 2.6 min over 100 jobs (≈1.6 s per job) bounds its switching overhead relative to FIFO.

That is overhead relative to whatever FIFO ran on. If FIFO ran inside Salus, the comparison measures the cost of preemption, not the cost of Salus versus plain TensorFlow; the paper does not say which FIFO this is. The per-iteration comparison with TensorFlow is Figure 12, not Table 1.

Where the answer comes from: Table 1 and the paper's sentence in Section 5.1.1; the derived duration assumes queuing means time before first start.

C7 · Is it 7× over MPS, or 6×?

The abstract says Salus improves inference GPU utilization "by 42× over not sharing the GPU and 7× over NVIDIA MPS". Figure 10's right panel shows 42 GPUs for TensorFlow, 6 for MPS and 1 for Salus. When I compute Salus versus MPS from the figure, which ratio do I get?

AnswerWork it out first, then open▾

Salus versus MPS is 6 / 1 = 6×. Per GPU, Salus hosts 42 instances and MPS 7: again 6×. The number 7 is 42 / 6, MPS's improvement over no sharing.

So the abstract's 7× appears to be the wrong ratio; the figure supports 6×. The qualitative point stands: dynamic memory sharing beats MPS's fixed per-process memory by a large factor for low-rate inference.

Where the answer comes from: Figure 10's right panel (printed bar heights) and the abstract.

C8 · "Average latency overhead is less than 5 ms": which average?

Section 5.3 says that with 42 models on one GPU "the average latency overhead is less than 5ms". Reading Figure 10's per-model bars, resnet152 goes from about 26 ms in TensorFlow to about 53.5 ms in Salus. When I compute the mean and the median of the per-model overhead, which one matches the claim?

AnswerWork it out first, then open▾

Read-off overheads (ms): 2.5, 8, 14, 18.5, 2.5, 18, 27.5, 11, 3.5, 4, 2, 1.5, 2.5, 3. Sum 118.5; mean ≈8.5 ms. Sorted, the middle two are 3.5 and 4: median ≈3.75 ms.

The claim matches the median (or an average weighted toward the small models), not the mean of the per-model bars. Relative overhead is about 2× for the deep models (resnet101, resnet152), which are the ones a latency target would bind on.

Where the answer comes from: Approximate read-offs from Figure 10 and this guide's arithmetic; the paper does not say how it averaged.

Glossary, results, and provenance

Every term in one place, then where the numbers came from and what this guide found inconsistent in the paper.

Core terms
Salus execution serviceA single user-level process per machine that holds the only GPU context, receives every DL job's graph and iterations from framework adaptors, executes them with its own engine, and manages all GPU memory.
AdaptorCode added to a DL framework (a modified TensorFlow in the paper) that implements the framework's device interface by forwarding sessions, graphs and iterations to the Salus service, so the service appears as one more device.
SessionThe Salus service's record of one job: its computation graph, its lane assignment and its queue of submitted iterations.
Iteration schedulerThe Salus component that, at each iteration boundary, picks which job's pending iteration runs next in each lane according to the active policy.
Memory managerThe Salus component that owns GPU memory: it places persistent allocations in the persistent region and ephemeral allocations in lanes, runs Algorithm 1 for arriving jobs, and enforces the safety condition.
Model memoryGPU memory holding a job's parameters (and their associated state): a few large chunks, fixed for the job's life.
Framework-internal memoryGPU memory the framework uses for bookkeeping and its data preparation pipeline: many small allocations that usually persist across iterations.
Ephemeral memoryGPU memory allocated during one iteration for layer outputs and temporaries and released by its end; most of a job's peak.
Persistent memoryModel plus framework-internal memory: what remains allocated at the trough between iterations, 110.9 to 822.2 MB in the paper's workloads.
Persistent region / ephemeral regionThe two parts of GPU memory under Salus, growing toward each other from opposite ends of the address space; the free space is the gap between them.
GPU laneA contiguous part of the ephemeral region, as large as the largest ephemeral need of the jobs assigned to it, in which one iteration at a time runs, on the lane's own GPU stream.
Safety conditionThe invariant Σjobs Pi + Σlanes maxj in lane Ej ≤ C, which guarantees that the two regions never collide and that every lane can finish its iteration.
Lane auto-defragmentationRe-placing a lane at its job's iteration boundary, when it holds no live data, to close a hole left by a departed lane; it copies nothing.
Algorithm 1 (Find GPU Lane for Job)Salus's greedy lane-assignment procedure: open a new lane if it fits, else join the best existing lane at least as large as E, else grow the smallest growable lane to E, else report not found.
Fast job switchingSalus's first primitive: changing which job's iterations run on the GPU at an iteration boundary while every admitted job's persistent memory stays resident, so no data moves.
Iteration-granularity schedulingScheduling in which the unit of allocation is one whole DL iteration, so the scheduler is invoked only between iterations.
PACKThe Salus policy that places jobs in separate lanes, as many as the safety condition allows, to raise utilization and cut makespan, with no fairness between lanes.
SRTFThe Salus policy that preempts the running job for any job with less remaining time, admitting it if "it can run alone on the GPU" (this guide reads that as alone with the others paused and their persistent memory still resident); durations are assumed known.
FAIRThe Salus policy that admits jobs under the safety condition and equalizes service over time among the jobs of each lane.
Supporting terms
GPUA processor with many streaming multiprocessors running thousands of threads in parallel, with its own device memory, driven by the CPU over a bus.
Streaming multiprocessor (SM)One of the GPU's independent compute units; a kernel's thread blocks are spread over the SMs (56 on the P100).
Device memoryThe GPU's own DRAM (16 GB HBM2 on the P100), separate from host memory and not paged in classic CUDA.
KernelA function launched by the CPU to run on the GPU over a grid of threads, such as one layer's convolution.
StreamAn in-order queue of GPU operations within one context; operations in different streams may overlap.
GPU contextThe driver's per-process GPU state (address space, loaded code, allocations); contexts are time-sliced, not run concurrently, on GPUs of this era.
Exclusive (compute) modeA GPU setting that permits only one context at a time, giving one process the whole device.
NVIDIA MPSA server process that merges several client processes' GPU work into one context so their kernels can overlap; it does not manage their memory.
Unified Memory (the paper's "Unified Memory Access")A CUDA feature giving host and device one address space with on-demand page migration, which allows oversubscribing device memory at a large speed cost.
Static partitioning (SP)Dividing GPU memory into fixed per-job shares, each job in its own process.
CheckpointingSaving a job's state (at least its parameters) out of GPU memory so the job can be stopped and later restored; Gandiva uses it for suspend and resume.
Computation graphA framework's description of a model's operations and data dependencies, built once and executed every iteration (TensorFlow 1.x).
Forward pass / backward passThe two halves of a training iteration: computing layer outputs from inputs, then computing gradients from the last layer back to the first.
ActivationThe output tensor of one layer for one batch, kept from the forward pass until the backward pass has used it; the bulk of ephemeral memory.
Batch sizeThe number of samples processed per iteration; it scales activation memory and iteration time.
Workload name (model_batch)The paper's naming of a job by model and batch size, for example resnet152_75.
Hyper-parameter tuningTraining many variants of a model with different settings (learning rate, sizes) to pick the best; the paper's "pre-training" use case for PACK.
Inference (serving)Running a trained model's forward pass on incoming requests, where per-request latency is the goal.
HOL blockingDelay of a short job queued behind a long one under FIFO.
JCTJob completion time: from a job's arrival to its finish.
MakespanTime from the first arrival to the finish of the last job in a set.
FragmentationFree memory split into pieces too small or misplaced for a request, so an allocation fails although the total free memory would suffice.
Gandiva, TiresiasGPU cluster schedulers (OSDI 2018, NSDI 2019) that time-share GPUs between jobs at a granularity of minutes.
