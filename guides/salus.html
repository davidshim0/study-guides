MLSys 2020 · A Field Guide

Letting many small jobs use the GPU that one big job would otherwise hog

A GPU today is handed to exactly one process at a time. Salus is a user-space service that fakes finer-grained sharing — fast enough to preempt, pack, and time-slice deep learning jobs without ever moving their model weights off the card.

📄 "Salus: Fine-Grained GPU Sharing Primitives" · Yu & Chowdhury 🎓 Some TensorFlow/scheduling basics assumed — primers cover them ⏱ ~25 min read
🧩

Keep a job's persistent memory (model weights) parked on the GPU forever; only ever release and reuse its ephemeral scratch memory at iteration boundaries.
That one design choice is what makes switching jobs cheap.

Before you begin

What Salus assumes you already know

Skim the TL;DR, then the glossary, then open whichever primer looks unfamiliar.

⚡ TL;DR

  • Salus is a user-space execution service that gives GPUs two primitives — fast job switching and a memory-layout scheme called a "GPU lane" — so many unmodified DL jobs can share one GPU instead of one process owning it exclusively.
  • It cuts average training completion time 3.19× with an SRTF scheduler, raises hyperparameter-tuning GPU utilization 2.38×, and lets 42 inference instances (14 models × 3 each) share 1 GPU instead of 42 (7× better than NVIDIA MPS's 6 GPUs) — most models add <10% training overhead, with a few CPU-heavy outliers reaching ~1.8×.
  • It matters because it turns "one GPU, one process" into a schedulable resource, closing the same coarse-granularity gap that memory tiering research is closing for DRAM/NVM/CXL.

Quick glossary

SRTFShortest-Remaining-Time-First — a preemptive scheduling policy that always runs whichever job has the least work left.

1Why a GPU is normally "exclusive"▾

Unlike a CPU core, which the OS timeslices between many processes, a GPU today is typically handed wholesale to one process. There's no OS-level scheduler deciding "run 10ms of job A, then job B" — the GPU driver doesn't support that granularity.

Now you're ready: Salus's whole job is inventing that missing scheduling layer, entirely in user space.
2Job Completion Time and head-of-line blocking▾

If jobs run strictly one-at-a-time in arrival order (FIFO), a 5-hour training job that arrived first will delay a 30-second job that arrived second by nearly 5 hours — even though swapping them would finish both far sooner. That's HOL blocking.

Now you're ready: preemptive scheduling (SRTF) fixes this — but only if switching jobs is cheap.
3What checkpointing costs▾

Before Salus, "pausing" a job means writing its state to disk/host memory and freeing the GPU (checkpointing), then reloading it later. Even the best case — transferring just model parameters — competes with PCIe bandwidth limits.

Now you're ready: Salus's Figure 4 shows this transfer time can exceed an entire inference request's latency, which is why Salus avoids transferring anything at all.
4Iterations, sessions, and TensorFlow's execution model▾

A DL training job repeats the same loop thousands of times: an "iteration" runs the computation graph once, updates parameters, and reuses the exact same allocation pattern next time. A "session" is the framework's handle to one running job.

Now you're ready: Salus schedules at iteration granularity — coarse enough to be cheap, fine enough to switch jobs in under a second.
5Peak vs. persistent GPU memory▾

A training job's memory usage spikes during each iteration (activations, gradients) and drops between iterations — but the model's weights stay resident the whole time. Peak can be 10-15GB; the resident weights are often under 1GB.

Now you're ready: that big gap between peak and persistent is exactly the room Salus exploits to pack more jobs per GPU.
6NVIDIA MPS as the existing baseline▾

MPS lets multiple CUDA processes share a GPU context, reducing context-switch overhead between them. In the paper's baseline, memory is still statically partitioned per process up front — MPS speeds up switching between those fixed partitions but doesn't itself add DL-aware scheduling, dynamic resizing, or fairness.

Now you're ready: wherever you see "vs MPS" in the results, that's the strongest existing alternative Salus beats.
The whole story in one place

Salus in a nutshell

The problem, the two primitives, and the payoff.

GPUs are allocated in units of one whole GPU per process. That's fine when a job saturates the GPU, but most DL jobs don't: memory usage regularly averages under 50%, and compute is often idle between kernel launches. Worse, because a running job can't be cheaply suspended, cluster schedulers default to FIFO — which suffers from head-of-line blocking: a long job at the front delays every short job behind it.

Salus is a consolidated, singleton execution service that sits between DL frameworks and the GPU. It exposes two primitives: fast job switching and dynamic memory sharing (GPU lanes). The key enabler is a memory classification: DL jobs' GPU memory splits into model and framework-internal (persistent, small) versus ephemeral (large, but released every iteration). Salus never moves persistent memory — ephemeral memory is simply released at the end of each iteration, and its lane space is reused by whichever job runs next, which is nearly free.

On top of these primitives, Salus implements ordinary scheduling policies — PACK (maximize utilization), SRTF (minimize average completion time via preemption), and FAIR (equalize throughput via time-slicing) — that were previously impractical on GPUs because switching cost too much.

The payoff: SRTF cuts average JCT by 3.19× over FIFO; PACK improves hyperparameter-tuning makespan by up to 2.38×; for inference, Salus needs just 1 GPU for 42 inference instances (14 models × 3 instances each) where exclusive allocation needs 42 and MPS needs 6 — a 42× and 7× improvement, respectively — with under 5ms added latency; most CNN training models see <10% overhead, though a few CPU-heavy outliers reach roughly 1.8× (Figure 12).

🔷 Key takeaways

  • Exclusive, whole-GPU allocation causes both underutilization and HOL blocking under FIFO scheduling.
  • DL memory splits cleanly into persistent (model + framework-internal, small) and ephemeral (large, released every iteration).
  • Never moving persistent memory is what makes job switching fast — no checkpoint transfer needed.
  • GPU lanes carve ephemeral memory into regions; iterations within a lane serialize, lanes run in parallel via GPU streams.
  • A safety condition (Σpersistent + Σlane sizes ≤ capacity) governs admission and lane assignment.
  • Scheduling granularity is the iteration, not the kernel — coarse enough to be cheap, fine enough (ms–s) to matter.
  • Result: 3.19× JCT (SRTF), 2.38× utilization (PACK), 42×/7× inference GPU reduction, mostly <10% training overhead.
Five everyday pictures

How to think about Salus

Each stands alone. Every card ends with where the picture breaks down.

Fast switching · Persistent vs ephemeral

A hotel room you never check out of

Your suitcase (model weights) stays in the room the whole trip. Only your day's activities (ephemeral scratch memory) come and go. Moving from one guest's "active" turn to another's doesn't mean repacking luggage — it's instant.

Where it breaks: a hotel room is exclusive; Salus's whole point is that many jobs' "suitcases" fit in the same GPU simultaneously.
Spatial sharing · GPU lanes

Highway lanes for iterations

Each lane runs one car (iteration) at a time — no collisions inside a lane — but cars in different lanes drive in parallel. Widen or narrow a lane and you change how many cars per hour it handles, without touching the other lanes.

Where it breaks: real lanes are fixed-width; GPU lanes resize dynamically and can even be reclaimed automatically at "iteration boundaries" (traffic lights), not mid-drive.
Admission control · The safety condition

A restaurant that only seats parties it can feed

Before seating a new table, the host checks: can the kitchen still guarantee food for everyone already seated, plus this new party's minimum order? Salus's safety condition does the same arithmetic before opening a new lane or admitting a job — always leaving enough room for at least one job's peak.

Where it breaks: unlike a host guessing at appetite, Salus takes each job's ephemeral memory requirement E as a declared input (Algorithm 1) and sizes a lane to the largest E among the jobs sharing it — a bound is given up front, not inferred from watching orders come in.
Fairness · FAIR policy time-slicing

Splitting a conference room by the clock

Three teams share one room; each gets an equal slice of meeting time, renegotiated the instant a team leaves or arrives. Salus's FAIR policy does this to GPU throughput in seconds, not the minutes-scale suspend/resume of prior GPU schedulers.

Where it breaks: the room analogy implies equal slices are always desirable; Salus explicitly notes there's no single "correct" fairness definition — FAIR here is one reasonable choice among many.
Preemption · Avoiding HOL blocking

Letting the express checkout cut ahead

A shopper with one item shouldn't wait behind a full cart. SRTF lets Salus pause the "full cart" job (a long training run) mid-stream — cheaply, because nothing needs to be unloaded — run the short job to completion, then resume exactly where it left off.

Where it breaks: SRTF needs to know each job's remaining time in advance; real clusters must estimate this, and a bad estimate can reintroduce the very blocking SRTF is meant to avoid.
The full explanation

How it actually works

From memory classification to lane packing to the scheduling policies built on top.

1 · Architecture — a singleton execution service

Salus sits between the DL framework and the GPU as one consolidated process. A framework-specific adaptor makes it transparent: user scripts don't change. When a job starts, the adaptor creates a session in Salus and sends over the computation graph; the session requests a lane from the memory manager; then each training/inference call generates an iteration, which the iteration scheduler queues and dispatches to the GPU according to the active policy.

2 · Three types of GPU memory

Salus's whole design rests on classifying every allocation a DL job makes:

TypeBehaviorSize (typical)
ModelParameters, fixed for the job's life, persistent110.9 MB – 822.2 MB
EphemeralPer-iteration scratch, released every iterationup to ~13.8 GB of a job's total peak memory (Figure 1); persistent share is comparatively tiny
Framework-internalBook-keeping / data pipeline, persists across iterations, small chunkssmall but fragmentation-prone
📊
Model + framework-internal = persistent memory; both stay resident. Because persistent memory is tiny relative to ephemeral peak, several jobs' persistent footprints fit in a GPU with room left for one job's ephemeral peak — the basis for sharing.

3 · The GPU lane — spatial memory sharing

GPU memory is split into a persistent region and an ephemeral region growing from opposite ends (stack-and-heap style). The ephemeral region is subdivided into lanes: contiguous spaces where iterations from assigned jobs execute serially (parallelism instead comes from running different lanes concurrently as GPU streams). Because ephemeral memory is entirely released at the end of each iteration, defragmentation is free — a finished lane's space is reclaimed at the next iteration boundary with no data movement.

4 · Admission — the safety condition

Salus never lets total committed memory exceed GPU capacity C. It sums every job's persistent usage plus, per lane, the largest ephemeral usage seen among the jobs sharing that lane:

Σ P_i (persistent, all jobs)  +  Σ max_j(E_j) (per lane)  ≤  C

Given a new job's requirements, Salus first tries opening a fresh lane; failing that, it reuses an existing lane whose size already covers the new job; failing that, it grows the smallest lane that can still fit within C. This keeps at least one job in every lane always able to proceed.

5 · Scheduling granularity — why iterations, not kernels

Salus prototyped kernel-level switching (interleaving individual GPU kernel launches) and found it added too much overhead: routing every kernel through a central scheduler bottlenecks it and breaks framework-level batching/pipelining optimizations. Iteration-level scheduling (tens of ms to a few seconds per unit) is coarse enough to avoid that overhead while still fine enough to preempt and time-slice usefully.

6 · Policies built on the primitives

💡
PACK greedily opens lanes for as many jobs as the safety condition allows — maximizes utilization/makespan, no fairness guarantee.
💡
SRTF admits a higher-priority (shorter) job whenever it alone would satisfy the safety condition, preempting the current job — needs known/estimated job durations.
💡
FAIR admits jobs under the safety condition and equalizes their accumulated GPU service time within each lane via time-slicing.
Follow the numbers

Worked examples

Four calculations, straight from the paper's own tables and figures.

① The 3.19× SRTF speedup

Table 1 reports average JCT of 170.6 min under FIFO and 53.4 min under SRTF, over the same 100-job trace. Where does "3.19×" come from?

  1. Ratio: 170.6 min ÷ 53.4 min = 3.194× — matches the paper's headline number.
  2. Why it works: SRTF preempts the currently-running long job the instant a shorter one arrives, using fast job switching to avoid checkpoint-transfer cost.
  3. The tradeoff: average queuing time drops from 167.6 min to 28.6 min, but SRTF's 95th-percentile JCT (217.0 min) is still worse than its average by roughly 4×, since the least-favored (longest) jobs can be repeatedly deprioritized.
  4. Sanity check on makespan: FIFO's makespan (303.4 min) and SRTF's (306.0 min) are nearly identical — Salus's switching overhead doesn't blow up total system throughput even while improving individual JCTs.
🔷
Insight: SRTF's win is entirely about *reordering*, not raw speed — total work done is the same; who waits behind whom changes completely.

② Why PACK helps 2.38× on one workload but only 1.07× on another

300-job hyperparameter sweeps: superres_128 improves 2.38× under PACK; resnet50_50 improves only 1.07×. Same policy, very different gains — why?

  1. PACK's lever is memory: it opens more concurrent lanes as long as the safety condition (Σpersistent + Σlanes ≤ C) holds.
  2. superres_128 has modest per-job memory needs relative to GPU capacity, so many lanes fit — high concurrency, big makespan win.
  3. resnet50_50 also fits memory-wise, but its jobs are compute-heavy: once several run concurrently, they contend for the same GPU compute pipeline, not memory.
  4. Conclusion: PACK relieves a memory bottleneck; it cannot relieve a compute bottleneck. When compute saturates first, extra lanes buy little.
💡
This is the paper's own explanation (§5.2) — a reminder that GPU sharing has two independent resource axes, and Salus only directly attacks the memory one.

③ 42 inference jobs on 1 GPU vs 6 for MPS

42 low-traffic inference instances (14 models × 3 each). Exclusive allocation needs 42 GPUs; MPS needs 6; Salus needs 1. Check the ratios.

  1. Salus vs exclusive: 42 GPUs ÷ 1 GPU = 42× fewer GPUs needed — matches the paper.
  2. Salus vs MPS: 6 GPUs ÷ 1 GPU = 6× by direct arithmetic, yet the paper's headline figure is 7×. The paper doesn't walk through the reconciliation itself — it simply reports Salus needing 1 GPU, MPS needing 6, and states "7× over MPS" as the headline number. Treat this as a reported, somewhat ambiguous figure rather than something fully explained by the 6-vs-1 arithmetic.
  3. Why MPS needs more GPUs: MPS reduces context-switch overhead, but the baseline still fixes each process's memory partition statically up front rather than dynamically packing or reclaiming it — so it can't push persistent+ephemeral memory as tightly as Salus's lanes.
  4. Cost of packing: average inference latency overhead stays under 5 ms even at this density — the "clean sharing, small cost" pattern seen throughout the paper.
🔷
Insight: inference is the best case for Salus — many small, low-traffic persistent footprints, almost no ephemeral contention, so lanes pack extremely tightly.

④ A toy safety-condition check

googlenet_25's persistent memory is ≈110.9 MB and resnet152_75's is ≈822.2 MB; a P100 has capacity C = 16 GB. Figure 1 reports each job's total peak GPU memory (persistent + ephemeral combined) as roughly 3 GB and 13.8 GB — since persistent memory is small by comparison, we treat these totals as stand-ins for each job's lane-size (ephemeral) requirement below. This is an approximation for illustration, not a number the paper reports directly as "ephemeral peak."

  1. Sum persistent: 110.9 MB + 822.2 MB ≈ 0.93 GB.
  2. Sum lane sizes (approximate max ephemeral per lane): 3 GB + 13.8 GB = 16.8 GB.
  3. Total: 0.93 + 16.8 ≈ 17.7 GB — this exceeds C = 16 GB, so the safety condition fails and both jobs cannot get dedicated lanes simultaneously at full peak.
  4. What Salus does instead: it would either queue one job, or rely on the fact that peaks rarely align exactly in time — but the algorithm's admission check is conservative and uses the declared per-job requirement, so it would correctly refuse this combination rather than risk an OOM.
💡
This illustrates why heavy resnet152-scale training doesn't pack as tightly as the small inference workloads in example ③ — persistent memory is cheap, but ephemeral peaks are the real constraint.
Test yourself

Practice problems

Try each before revealing the answer.

Problem 1 · easy
Why doesn't Salus checkpoint jobs to host memory when switching, the way earlier suspend/resume schemes did?
Show answer
Because transferring GPU memory over PCIe is slow relative to DL iteration/inference latency — the paper's Figure 4 shows the theoretical minimum transfer time can exceed the inference latency itself for many models. Salus avoids the transfer entirely by keeping persistent memory resident and only ever touching ephemeral memory, which is freed rather than moved.Misconception: that "suspend" always means "move off the device." Salus's insight is that for DL jobs specifically, persistent memory is small enough to just leave in place.
Problem 2 · medium
Classify each as model, ephemeral, or framework-internal memory: (a) convolution layer weights, (b) an intermediate activation tensor computed mid-iteration, (c) the input data-loading pipeline's buffers.
Show answer
(a) Model — persists for the job's life. (b) Ephemeral — created and destroyed within one iteration. (c) Framework-internal — persists across iterations but isn't part of the trained model itself.Misconception: that "persistent" only means model weights. Framework-internal memory is also persistent (and can fragment the layout) even though it's not what most people think of as "the model."
Problem 3 · hard
Two jobs need persistent memory of 500 MB and 300 MB, and each needs its own lane sized 5 GB and 4 GB respectively. Does the safety condition allow both on a 10 GB GPU?
Show answer
Sum persistent = 0.8 GB. Sum lane sizes = 9 GB. Total = 9.8 GB ≤ 10 GB — yes, it fits, with 0.2 GB to spare. Both jobs can run simultaneously in separate lanes.Misconception: that lane size and persistent memory are the same pool. They're separate terms in the safety condition — persistent memory is summed across jobs, lane size is the max ephemeral usage per lane, and both must fit together.
Problem 4 · medium
Why did Salus's authors reject kernel-level (rather than iteration-level) scheduling, even though it seems finer-grained and thus more flexible?
Show answer
Routing every individual GPU kernel launch through a central scheduler becomes a bottleneck itself, and it breaks framework-level optimizations like kernel batching and pipelining that assume kernels from the same job run back-to-back without interruption. The overhead outweighed the flexibility gained.Misconception: that finer granularity is always better. There's a genuine efficiency-vs-flexibility tradeoff, and DL frameworks' own internal optimizations set a practical floor on how fine you can go.
Problem 5 · medium
SRTF preempts a running job when a shorter one arrives. What single condition must the incoming job satisfy to be admitted, regardless of what's currently running?
Show answer
Its own safety condition must hold even in isolation — i.e., it must be able to run alone on the GPU (its persistent + lane memory ≤ capacity). If that's satisfied, Salus admits it and preempts whatever lower-priority job is running, since fast switching makes that cheap.Misconception: that SRTF needs to check compatibility with the currently running job's memory footprint. It only needs to guarantee the new job alone would fit — the old job's resources will be freed by preemption.
Problem 6 · easy
On the CNN overhead chart, most models show under 10% overhead per iteration, but a couple spike well above (up to 1.83×). What do those outlier models have in common?
Show answer
They perform a large share of their per-iteration work on the CPU rather than the GPU. Because Salus runs its own execution engine, CPU-side computation also gets redirected through Salus, which isn't yet as optimized as native TensorFlow's CPU path.Misconception: that Salus's overhead is purely a GPU-sharing cost. Some of it is an engineering gap in Salus's CPU-side execution path, not an inherent cost of the sharing primitives themselves.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Does Salus require modifying DL application code?▾
No. A framework-specific adaptor (integrated with TensorFlow in the paper) handles the translation transparently; user scripts run unchanged and see Salus as just another compute device.
Q2Does Salus support multiple GPUs or multiple machines?▾
The evaluated system targets a single GPU. The authors list extending to multiple GPUs/accelerators on one machine, and across machines via RDMA, as future work.
Q3How is Salus different from just disabling exclusive mode and statically partitioning memory?▾
Static partitioning sizes each job's slice for its peak usage up front, wasting the large gap between peak and average utilization. Salus dynamically resizes lanes and reclaims ephemeral memory every iteration, packing jobs far more tightly.
Q4Why not just use NVIDIA MPS?▾
MPS avoids costly context switches but still lacks DL-aware scheduling, dynamic memory sharing, and fairness/priority policies — and in the paper's tests, the static-partitioning-plus-MPS baseline needed 6× more GPUs than Salus for the same inference workload.
Q5What happens if a lane's ephemeral memory need suddenly exceeds what was provisioned?▾
Algorithm 1 takes each job's ephemeral memory requirement E as an input and sizes a lane to the maximum E among the jobs assigned to it — it's a declared requirement, not an online "observed so far" heuristic. The paper doesn't describe a runtime recovery path for a job whose actual usage exceeds its declared E, beyond the admission-time safety condition.
Q6Does SRTF need to know a job's exact runtime in advance?▾
The evaluation assumes known/estimated durations (citing prior work like Optimus for estimation). The paper explicitly scopes runtime prediction as outside its contribution — Salus only provides the mechanism to act on such estimates cheaply.
Q7How much does packing many jobs hurt individual job throughput?▾
It depends on which resource saturates. If GPU memory was the bottleneck, packing helps utilization with little per-job slowdown (e.g. superres_128's 2.38×). If compute saturates first, packing gains little (resnet50_50's 1.07×) since jobs now compete for the same compute pipeline.
Q8Is Salus's fairness policy the "correct" definition of fairness?▾
The authors are explicit that there are many plausible fairness definitions based on time-sharing; FAIR demonstrates feasibility of implementing one such policy, not a claim that it's optimal or unique.
Q9Why does defragmentation come "for free" in GPU lanes?▾
Because ephemeral allocations are entirely released at the end of every iteration anyway. When a lane's job finishes, the next iteration boundary naturally reclaims that space for whichever job is positioned to grow into it — no extra memory-movement pass is needed.
Q10What's the single biggest limitation the authors acknowledge?▾
Policy design is left largely open — Salus provides mechanism (fast switching + lanes), not the optimal scheduling algorithm for shared-GPU DL workloads. They also flag CPU-side execution overhead and single-machine/single-GPU scope as current limits.
Beyond this paper

Connections to OS & memory-systems design

Four short bridges between Salus's design and the broader tiered-memory/OS literature.

🔹 Hot/cold classification is page-placement thinking

Salus's persistent/ephemeral split is functionally the same move as classifying pages "hot" (keep in DRAM) vs "cold" (demote to NVM/CXL) in tiered-memory systems — both trade a coarse, one-size-fits-all allocation for a cheap runtime classifier that captures most of the benefit.

🔹 A consolidated user-space service resembles a microkernel device server

Rather than modifying the GPU driver or kernel, Salus interposes entirely in user space — the same architectural move microkernels make by pushing device management into isolated servers, trading a bit of overhead for portability and avoiding kernel modifications.

🔹 Iteration granularity is a coarse-grained hotness-sampling interval

Choosing "one iteration" as the scheduling unit mirrors the granularity tradeoff in CXL/NVM hotness tracking: sample too finely (per-kernel, per-access) and overhead dominates; sample too coarsely and you miss opportunities. Both settle on "coarse enough to be cheap, fine enough to matter."

🔹 The RDMA future-work item is disaggregated memory by another name

The authors' own stated next step — extending Salus across machines via RDMA — is exactly the disaggregated/pooled-memory research question: once persistent state doesn't have to live on the same device as compute, you're one step from CXL-attached memory pools.

🔷
Takeaway for tiering research: Salus is a case study in getting most of the benefit of fine-grained resource sharing from one cheap classifier (persistent vs. ephemeral) instead of a general-purpose mechanism — the same bet OS-managed memory tiering makes with hot/cold page classification.

Discussion questions

Each ties to a specific claim, number, or design decision in the paper.

  1. Algorithm 1 sizes a lane to the maximum declared ephemeral requirement E among the jobs assigned to it, taken as an input rather than measured online — what happens to the safety condition, and to co-located jobs, if a job's actual ephemeral usage ends up exceeding its declared E? (the paper doesn't specify a runtime recovery path beyond admission-time checks)
  2. The 42×/7× inference results report only average added latency (<5ms) — is average latency the right metric for a serving system, or does packing risk long tail latencies the paper doesn't show? (compare against how Clipper or TensorRT report P99 latency)
  3. SRTF's 3.19× JCT improvement assumes job durations are known or estimated via prior work (Optimus) — how sensitive is the 3.19× figure to estimation error, and would a systematically underestimated job "starve" under SRTF the way it would under any priority scheduler? (connect to Tiresias's 2-D scheduling, which explicitly avoids requiring exact durations)
  4. Kernel-level scheduling was rejected for breaking framework batching/pipelining optimizations, in favor of iteration-level scheduling — do newer execution modes like CUDA graphs or graph-captured pipelines (which batch even more aggressively than 2018-era TensorFlow) undermine the ephemeral/persistent split Salus relies on? (pushes on whether the memory classification still holds under more aggressive kernel fusion)
  5. PACK only improved resnet50_50's makespan by 1.07× because compute, not memory, was the bottleneck — since Salus's primitives are entirely memory-centric, what would a compute-aware lane/scheduling primitive need to add? (think about whether GPU streams alone can express fine-grained compute time-slicing the way lanes express memory sharing)
