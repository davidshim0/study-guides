HotStorage '26 · A Field Guide

Pay for context once — rebuild it on the GPU, or restore it from storage

Every evicted KV-cache block hides the same question: is it cheaper to read it back from disk, or to just recompute it? The answer flips depending on your GPU, your storage, and your SLOs — so a fixed threshold is always wrong somewhere. This is the plain-English story of the policy that asks the question dynamically.

📄 Najafizadeh, Tarasov, Merenstein, Zhu, Zadok · HotStorage '26 🎓 Assumes OS/memory-hierarchy background, not LLM internals ⏱ ~25 min read
⚖️

Split the requested blocks so the GPU recompute path and the storage restore path finish at the same instant — then check that instant against your SLO.
Whichever path is idle first was given too little work.

Before you begin

Quick glossary, then eight primers

The acronyms first — LLM-serving terms a systems person meets cold. Then the concepts the paper leans on, each with a "now you're ready" bridge back to the main argument.

Quick glossary

LLMLarge Language Model — the transformer serving the inference requests this paper is about.
KV-cacheThe saved key/value vectors from attention layers for already-processed tokens — not a key-value store in the database sense.
HBMHigh Bandwidth Memory — the GPU's on-package DRAM; this paper's fastest, smallest tier (e.g. 141GB on an H200).
TTFT / TTLTTime-To-First-Token / Time-To-Last-Token — latency to the first vs. the final generated token.
Prefill / decodePrefill processes the whole input prompt at once (where restore/recompute happens); decode generates output tokens one at a time.
SLOService-Level Objective — a target the system must meet, e.g. a latency bound or a throughput floor.
P9595th-percentile — the latency experienced by the slowest 5% of requests; this paper's tail-latency metric.
MFUModel FLOPs Utilization — fraction of a GPU's peak FLOP/s actually achieved; written η in the paper's compute model.
PCIeThe interconnect linking GPU, CPU, and storage; its bandwidth can bottleneck a restore even when the storage device is fast.
Block tablevLLM/PagedAttention's map from logical token positions to physical KV-cache block locations — enables zero-copy reads.
GPU recompute path storage restore path the I/O-aware policy SLOs / highlights
1What a KV-cache actually is▾

Transformer attention needs every prior token's key and value vectors to process the next one. Without caching, generating token N means recomputing attention over all N−1 prior tokens — cost grows as O(N²) with context length. Cache those vectors once and reuse them, and the incremental cost per new token drops to O(N).

Concretely: on an H200, producing the first token of a 128K-token prompt takes 18 seconds with no KV-cache reuse, and under 2 seconds with it.

Now you're ready: the whole paper is about what happens when that cache doesn't fit in GPU memory and has to live somewhere slower.
2The three-tier hierarchy — and the gap is bigger than you're used to▾

This paper's modeled hierarchy is GPU HBM → single-node CPU DRAM → local SSD (the paper mentions remote storage only as background/future context, not part of the evaluated system) — functionally the same ladder you already reason about with CXL-attached NVM: a small fast tier, a larger slower one, decisions about what to keep where. The quantitative gap is just far steeper: HBM delivers up to 3,360 GB/s; NVMe Gen5 storage delivers roughly 10 GB/s — a ~300× drop, versus the roughly 2–10× DRAM/NVM gap that TPP, HeMem, Memtis, and Pond-style tiering policies are built around.

Now you're ready: a "restore" from the bottom tier here is proportionally far more expensive than a page fault to CXL memory — which is exactly why recomputing on the GPU can sometimes beat waiting for it.
3The trade-off traditional memory tiering doesn't have▾

In DRAM/NVM tiering, a cold page has exactly one remedy: fetch it. There's no "recompute the page instead." LLM inference is unusual because the *data* (KV vectors) and a *regeneration path* (GPU attention compute) both exist — so every eviction decision for a hot/cold page has a second escape hatch tiering policies never get: skip the fetch and rebuild it from compute instead.

Now you're ready: the restore-vs-recompute decision is a problem class you haven't had to solve in page migration, because memory pages don't come with a "regenerate" function — but the two-sided balancing logic (Section 4) will look familiar.
4Lookup, store, restore — only one of these hurts▾

Cache systems do three things with KV-cache blocks: lookup (metadata only, negligible cost — it stays in CPU DRAM), store (writes blocks out, runs asynchronously, off the critical path), and restore (reads blocks back in). Restore is technically asynchronous from the cache's perspective, but the inference request can't proceed without its data — so restore is effectively blocking, and its I/O queueing delay lands directly on the user.

Now you're ready: everything in this paper is about managing restore cost specifically — lookup and store are not the problem.
5Zero-copy and the block table▾

Inference engines like vLLM don't copy KV-cache blocks into one contiguous buffer; a block table maps logical token positions to wherever their blocks physically live, and attention reads them in place. The consequence: a block must be GPU-resident before it's usable — there's no "read it on demand mid-computation."

Now you're ready: this is why restoration must complete before prefill can proceed, not interleaved with it — reinforcing why restore latency lands squarely on TTFT.
6The two SLOs this paper optimizes▾

Of the many possible serving metrics (TTFT, TTLT, cost, energy), this paper narrows to two: service throughput (requests/sec, GPU-compute-bound) and P95 tail latency of prefill (storage/compute-bound). Decode latency is assumed unaffected by the restore/recompute choice, so it's left out.

Now you're ready: the policy in Section 4 has exactly two constraints to satisfy — a throughput bound and a tail-latency bound — nothing else.
7Why hardware choice swings restore time by orders of magnitude▾

The paper's simulator sweeps 6 GPUs × 6 PCIe generations × 7 DRAM configs × 7 storage devices = 1,764 configurations. At a fixed context length, restoration time varies by 2–3 orders of magnitude across configurations — purely from hardware choice, before any workload differences.

Now you're ready: no single static threshold for "restore vs. recompute" can be right across this space — which motivates a policy that reads live hardware rates instead of hardcoding a cutoff.
8Balancing two parallel pipelines▾

Because restoration (I/O) and recomputation (GPU compute) can run concurrently on disjoint resources, a request's completion time is set by whichever path is slower — so splitting work unevenly wastes the faster path's idle time. The optimal split equalizes both paths' finish times, the same way you'd balance load across two queues with different service rates.

Now you're ready: this is literally the paper's one formula (Section 4) — everything else is bookkeeping around it.
The whole story in one place

I/O-aware KV-cache management in a nutshell

The problem, the fix, and the numbers that justify it.

When a user's session goes idle, its KV-cache blocks may get evicted from GPU HBM down to CPU DRAM or disk to make room for active sessions. When that user returns, the inference engine needs those blocks back — either by restoring them from wherever they landed, or by recomputing them from scratch on the GPU. Existing systems pick one policy, or a fixed threshold, and keep it fixed across deployments. But the right answer depends on live, shifting quantities: GPU compute throughput, storage and interconnect bandwidth, context length, and the SLO being targeted — exactly the kind of multi-factor, workload-dependent decision that static policies get wrong somewhere in the configuration space.

The paper's fix is an I/O-aware KV-cache management policy, applied at the disk tier — GPU-resident blocks need no restore at all, and CPU DRAM is treated as a transient buffer rather than a decision point. For each disk-bound restore, it computes how many of the N requested blocks to restore versus recompute so that both paths finish at the same time — maximizing throughput while meeting a P95 tail-latency target. When no split can satisfy both objectives, the policy falls back to a best-effort mode that minimizes the worst constraint violation rather than failing outright.

The payoff: across 1,764 simulated hardware configurations and six GPU generations, the policy sustains up to a 10× improvement in the fraction of scenarios meeting both throughput and tail-latency targets, compared to always-restore or always-recompute — and the decision itself costs only 5.07 μs on average, measured over 20.2 million simulated scheduling decisions.

🍯 Key takeaways

  • KV-cache offloading is the main source of inference I/O overhead; restore is the latency-critical operation (lookup and store are not).
  • Restoration time varies by 2–3 orders of magnitude across hardware configurations at a fixed context length — no static threshold generalizes.
  • Restore and recompute can run in parallel on disjoint resources (storage I/O vs. GPU compute), so the optimum balances their completion times rather than picking one exclusively.
  • The policy solves a closed-form split k, checks it against a tail-latency bound and two utilization bounds, and falls back to best-effort if infeasible.
  • On a high-compute GPU (H200), restore-only can be up to 10× slower than necessary; on a lower-end GPU (A5000), restore and recompute are roughly comparable.
  • Result: up to a 10× improvement in the success rate — the fraction of configurations meeting both SLOs — versus static restore-only or recompute-only policies, for ~5 μs of decision overhead.
Six everyday pictures

How to think about restore vs. recompute

Each stands alone — read in any order. Every card ends with where the picture stops being true.

The core idea · Rematerialize vs. fetch

Rebuilding a diagram vs. finding your old copy

You sketched a diagram yesterday. Need it again? You can dig through old folders (storage restore) or just redraw it from memory (recompute) — whichever is faster depends on how messy the folders are and how quick you are at redrawing today. KV-cache blocks have the same two options, and the policy just asks which is faster right now, continuously.

Where it breaks: redrawing from memory can be wrong if you misremember; recomputing attention is exact — it's guaranteed to reproduce the identical keys and values, so there's no correctness trade-off, only a speed one.
The hierarchy · Steeper than you're used to

The same ladder, a much longer drop

You already reason about a fast-tier/slow-tier ladder with DRAM and CXL-attached NVM — tiering systems like TPP, HeMem, Memtis, and Pond live entirely in that gap. This paper's ladder has the same shape (HBM → DRAM → disk) but the bottom rung is roughly 300× slower than the top one (3,360 GB/s vs. ~10 GB/s), not the 2–10× gap NVM tiering deals with.

Where it breaks: NVM tiering's only remedy for a cold page is to fetch it faster or avoid the fault. This ladder has a second remedy — skip the fetch and recompute — that doesn't exist for ordinary memory pages.
The balancing act · Equalizing finish times

Two checkout lines, one register each

A shopper (the request's blocks) can split their cart between two checkout lines that scan at different speeds. The fastest total checkout time comes from splitting the cart so both lines finish together — send everything to the fast line and the slow line sits idle wastefully; split evenly regardless of speed and the slow line drags everyone down. The paper's k is exactly this: the split that makes T_c = T_s.

Where it breaks: real checkout lines don't change speed between customers; GPU recompute throughput and storage bandwidth do drift over time, so the split has to be recomputed per request, not solved once.
Three operations · Only one is urgent

Checking a library catalog vs. waiting at the desk

Looking up whether a book is in the library is instant (metadata). Returning a book can happen whenever (async write-back). But if you need the book right now to keep reading, you wait at the desk while someone fetches it — that wait is the only one that actually delays you. Lookup and store are the catalog check and the return slot; restore is the desk wait.

Where it breaks: a librarian fetch has no alternative to "wait." A KV-cache restore does — recompute — which is the whole point of this paper.
SLO trade-off · Throughput vs. tail latency

A kitchen's prep speed vs. the slowest ticket

A kitchen's average ticket time tells you its throughput; its slowest ticket on a bad night tells you whether a customer walks out. A restaurant can run fast on average while still failing its worst-case promise. The policy checks both — a utilization bound (don't overload either the GPU or the storage path) and a P95 bound (don't let the unluckiest 5% of requests wait too long) — because satisfying only one doesn't satisfy the other.

Where it breaks: a kitchen can simply refuse more orders to protect its worst ticket. The policy's equivalent — best-effort mode — doesn't refuse requests, it accepts a bounded SLO violation and minimizes it.
Overhead · A nearly-free referee

A traffic light, not a toll booth

A toll booth makes every car stop and pay — real, felt overhead. A traffic light reads sensors and switches in microseconds, invisible against the minutes-long trips it's directing. The policy's 5.07 μs decision cost is a traffic light next to a restore that can take minutes: negligible relative to what it's arbitrating, and it reads state (GPU/storage rates) that already exists rather than instrumenting anything new.

Where it breaks: a traffic light's decision doesn't change as traffic patterns shift mid-cycle; this policy's inputs (X, Y) are explicitly expected to drift, which is the entire reason it re-decides per request instead of once at startup.
The full explanation

How it actually works

From the capacity model, to the case study that motivates the policy, to the policy's one formula and how it's enforced.

1 · Why offloading is unavoidable

A 128K-token context on Llama-3.1-70B needs roughly 30GB of KV-cache. Ten concurrent users exceed 300GB — well past a single H200's 141GB of HBM, and that's before subtracting space for model weights. With many users and long contexts, inactive sessions' KV-cache gets evicted to CPU DRAM or disk, and restoring it later becomes routine rather than rare.

2 · The performance model

The simulator computes recomputation time with a roofline-style model: processing N blocks requires attending to all preceding blocks, so compute scales quadratically:

t_compute = N² · T_block · t̂      # T_block = tokens/block, t̂ = per-token compute time
t̂ = F_token(≈2P) / (Φ_peak · η)  # F_token = FLOPs/token, Φ_peak = GPU peak FLOP/s, η = MFU (assumed 1)

Restoration time is computed piece-wise from HBM outward: no transfer cost for HBM-resident blocks; otherwise throughput is capped by min(β_tier, β_link) for DRAM or disk. The simulator swept 1,764 configurations (6 GPUs × 6 PCIe generations × 7 DRAM configs × 7 storage devices) and found restoration time spans 2–3 orders of magnitude at a fixed context length — and recomputation curves for nearly every GPU except the H200 cross the restoration-time distributions, meaning neither path is uniformly better.

3 · The case study that motivates the policy

To make this concrete, the authors constrained an H200 and an RTX A5000 to 2GB HBM + 1GB DRAM of KV-cache capacity (forcing spill to a SATA SSD) while serving Llama-3.1-8B-Instruct over a 200-session ShareGPT-based chatbot workload (~8 requests/session, ~1,000 input tokens/request). As sessions accumulated, aggregate context length grew from ~1.6×10³ to ~1.6×10⁶ tokens.

🔍
Result: on the H200, restoring from disk instead of recomputing can cost up to 10× more time, because the H200's compute is fast enough that recompute is nearly free by comparison. On the A5000, restore and recompute costs converge — its compute is slow enough that neither option dominates. (Paper, §3, Fig. 2)

4 · The policy — one formula, two checks

At a disk-tier restore request of N blocks (B bytes each) — GPU-resident blocks need no restore, and DRAM-resident blocks are handled as a transient buffer rather than through this decision — M of the N are unconditional cache misses (must be recomputed). The policy reassigns k additional cache-hit blocks from restore to recompute, so recomputation handles N_c = M+k and restoration handles N_s = N−M−k. Because the two paths run in parallel, total request time is max(T_c, T_s) — minimized when the paths finish together:

# solve T_c = T_s for k, then clamp to the feasible range
k = max( 0, min( N−M, N·X / (X+Y) − M ) )

# X = GPU recompute throughput, Y = storage restore throughput (bytes/s)
N_c = M + k          # blocks to recompute
N_s = N − M − k       # blocks to restore
T_c = N_c·B / X ,  T_s = N_s·B / Y ,  T_req = max(T_c, T_s)

if T_req <= p  and  r·T_c <= 1  and  r·T_s <= 1:
    accept allocation
else:
    best-effort: choose the allocation minimizing the worst violation
💡
Why equalize instead of minimizing each term separately? Because the two paths run concurrently, the request only finishes once both are done — any imbalance just means one resource sat idle while the request waited on the other. Equalizing is the only split that wastes neither resource.

5 · Evaluation

Across six GPUs (A5000, V100, RTX 6000 Ada, A100, H100, H200, slowest to fastest) and varying cache-hit ratios, the paper measures success rate: the fraction of configurations meeting both the throughput and tail-latency objectives. At low cache-hit ratios (<25%), restore-only beats recompute-only by up to 25 percentage points — few blocks need restoring, so its I/O cost is small. As the cache-hit ratio rises, more blocks route through the slower disk path and restore-only degrades, while the I/O-aware policy keeps adapting and sustains up to a 10× improvement in success rate over either static policy. On slower GPUs, both static policies struggle (recompute-only success <20%, restore-only <40%) because the GPU itself is the weak link — but the I/O-aware policy remains consistently highest across the board. Running the policy costs 5.07 μs/decision on average over 20.2 million simulated decisions — about 2×10⁵ decisions/s.

Follow the numbers, step by step

Worked examples

Four calculations carried all the way through, using the paper's own figures.

① How little of a 128K context actually fits in HBM

H200 HBM = 141GB. Llama-3.1-70B, bf16 (2 bytes/param). The paper states a full 128K-token KV-cache for this model is ≈30GB. How many tokens of KV-cache fit in HBM after reserving space for weights?

  1. Weight reservation: 2P = 2 × 70×10⁹ bytes = 140GB.
  2. Effective HBM for KV-cache = 141GB − 140GB = 1GB.
  3. KV-cache scales linearly with context length: 30GB ↔ 128K tokens, so 1GB ↔ (1/30) × 128K ≈ 4,300 tokens.
  4. A 128K-token context needs roughly 30× that — the remaining ~124K tokens of KV-cache must live off-HBM.
🍯
Insight: this isn't an edge case — at realistic model sizes, almost the entire long-context KV-cache is forced off the GPU's fastest tier by construction. Offloading isn't an optimization here; it's structural to the design. (A generic "2MB per 16-token block" estimate would overstate this to ~8K tokens — the paper's own 30GB figure for this exact model is the more reliable number to scale from.)

② Solving for the balanced split k

A restore request has N=100 blocks, M=20 unconditional cache misses. On the H200 profile, GPU recompute throughput X=400 blocks/s, storage restore throughput Y=50 blocks/s. Find the optimal k.

  1. Plug into the formula: k = N·X/(X+Y) − M = 100 × 400/450 − 20.
  2. 100 × 400/450 = 88.9.
  3. k = 88.9 − 20 = 68.9, clamp to [0, N−M] = [0, 80] → k ≈ 69.
  4. Check: N_c = 20+69 = 89, N_s = 100−89 = 11. T_c = 89/400 = 0.223s; T_s = 11/50 = 0.22s. ✓ nearly equal.
  5. Compare to k=0 (restore-only): T_s = 80/50 = 1.6s — over 7× slower than the balanced 0.223s, just from sending every cache-hit block down the slow path.
💡
This is exactly why the H200 case study shows restore-only costing up to 10×: a compute-rich GPU can absorb almost all the work, but a restore-only policy never lets it.

③ Same formula, a compute-poor GPU

Same N=100, M=20, but now X=60 blocks/s (A5000-like) and Y=50 blocks/s (same disk). Find k and compare to ②.

  1. k = 100 × 60/110 − 20 = 54.5 − 20 = 34.5 → k ≈ 35.
  2. N_c = 55, N_s = 45. T_c = 55/60 = 0.917s; T_s = 45/50 = 0.9s. ✓ nearly equal.
  3. Notice the optimal fraction sent to recompute dropped from 89% (H200) to 55% (A5000) — because X itself dropped from 400 to 60.
  4. Compare restore-only (k=0) here: T_s = 80/50 = 1.6s vs. balanced T_req ≈ 0.92s — still an improvement, but a much smaller multiple (~1.7×) than the H200's ~7×.
🍯
Insight: the same formula explains both halves of the case study — a compute-rich GPU benefits enormously from leaning on recompute, a compute-poor one barely does, because its own compute throughput is the thing limiting k in the first place.

④ Is the scheduler's own overhead a problem?

The paper reports 5.07 μs/decision averaged over 20.2 million timed decisions. What does that cost at serving scale?

  1. Decisions/sec sustained: 1 ÷ 5.07×10⁻⁶s ≈ 197,000/s — matches the paper's reported ≈2×10⁵/s.
  2. Scheduling 10⁶ real-world requests: 10⁶ × 5.07×10⁻⁶s ≈ 5.07s total — matches the paper's reported ≈5.1s.
  3. Compare to a fixed (static) policy: the paper reports ≈0.23s for the same 10⁶ requests — implying ≈0.23 μs/decision, about 22× cheaper per decision than the adaptive policy.
  4. In context: a single disk restore in the case study can take minutes to over an hour at large context lengths — so even the "expensive" 5.07 μs adaptive decision is roughly six to eight orders of magnitude smaller than what it's deciding about.
💡
The paper is explicit that no new state is required — the scheduler reads parameters (GPU/storage rates) the cache subsystem and inference engine already track, so the only true cost is this computation, not added instrumentation.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A cache system logs a "restore" as asynchronous from its own perspective. Does that mean it doesn't affect inference latency?
Show answer
No. "Asynchronous from the cache's perspective" just means the cache system itself doesn't block on the I/O call. But the inference request does need the restored data before prefill can proceed (zero-copy reads require GPU-resident blocks), so the request waits regardless — the restore is effectively blocking from the inference engine's point of view.Misconception: conflating "asynchronous" (a property of the cache's API) with "non-blocking for the end-to-end request" (a property of the critical path). They're not the same thing here.
Problem 2 · medium
N=50 blocks, M=10 unconditional misses, X=200 blocks/s (GPU), Y=200 blocks/s (storage, equal to GPU). What's the optimal k, and what does that tell you about the split when the two paths are equally fast?
Show answer
k = N·X/(X+Y) − M = 50×200/400 − 10 = 25 − 10 = 15. N_c=25, N_s=25 — an exactly even split of the remaining 40 cache-hit blocks. When X=Y, the formula reduces to splitting the non-miss blocks 50/50, which makes sense: with identical throughput, the fastest way to finish together is to give each path the same amount of work.Misconception: assuming "equal throughput" means "ignore the split and restore everything" — the formula still actively balances load even when rates match, it just happens to produce an even split.
Problem 3 · medium
Why does the paper apply its policy only at the disk tier, treating CPU DRAM as a transient transfer buffer rather than a decision point?
Show answer
The restore-vs-recompute trade-off is sharpest where restoration is slowest and most capacity-constrained — the disk tier, where bandwidth is ~10 GB/s versus HBM's 3,360 GB/s. DRAM restoration is comparatively cheap, so the GPU-vs-storage trade-off is far less pronounced there; the paper explicitly scopes DRAM-tier policy to future work.Misconception: assuming the policy should apply uniformly across every tier. The paper deliberately targets where the trade-off has real teeth, not where it's largely moot.
Problem 4 · hard
At a low cache-hit ratio (<25%), restore-only outperforms recompute-only by up to 25 percentage points of success rate. Why does that advantage shrink — and eventually reverse — as the cache-hit ratio rises?
Show answer
A low cache-hit ratio means most blocks are misses anyway (must be recomputed), so restore-only only has a small fraction of blocks to actually restore — its I/O cost stays small and it wins easily. As the cache-hit ratio rises, more blocks are eligible for restoration, so restore-only commits an increasing fraction of the request to the slow disk path, and its success rate degrades. Recompute-only's cost doesn't depend on the cache-hit ratio at all (it recomputes regardless), so its relative position improves as the ratio climbs — eventually the crossover favors leaning on recompute, which is exactly the regime the I/O-aware policy navigates instead of committing to either extreme.Misconception: assuming "cache-hit ratio" behaves like it does in ordinary caching, where higher is unambiguously better. Here, a higher ratio also means more work is eligible to go down the expensive restore path if the policy mismanages it.
Problem 5 · medium
The policy enforces T_req ≤ p (tail latency) and r·T_c ≤ 1, r·T_s ≤ 1 (utilization) as separate constraints. Construct a scenario where a split satisfies the latency bound but violates a utilization bound.
Show answer
Suppose T_c and T_s are both comfortably under the P95 target p for a single request — so T_req ≤ p holds. But if the request rate r is high and T_c is large relative to 1/r (e.g., r=10 req/s and T_c=0.15s, so r·T_c=1.5 > 1), the GPU can't keep up with sustained arrivals even though any single request looks fine in isolation — it will queue and throughput collapses. This is why the policy checks both: per-request latency and sustained resource utilization are independent failure modes.Misconception: assuming "this request finishes fast enough" is sufficient. A policy can satisfy every individual request's latency bound and still overload a resource under sustained load.
Problem 6 · hard
In classic DRAM/NVM memory tiering, there's no "recompute" option for a cold page — only fetch. Why doesn't that option exist there, and what would have to be true of a memory system for it to exist?
Show answer
A memory page's content is typically the final output of arbitrary prior computation (or user data) — there's no cheap, general function that regenerates "whatever was written to this address" from something else. KV-cache blocks are special: they're a *pure, deterministic function* of the model weights and the preceding tokens, so recomputing them is well-defined and exact. A memory system would need an equivalent property — content defined by a cheap, deterministic, re-runnable function of other already-available state — for "recompute instead of fetch" to make sense; this is close to what gradient-checkpointing or memoization-vs-recomputation trade-offs exploit in other domains, but it's not a property ordinary virtual memory pages have.Misconception: treating "restore vs. recompute" as a generally portable idea to memory tiering. It specifically depends on the cached data being cheaply re-derivable, which most memory pages are not.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly is stored in a KV-cache block?▾
The key and value vectors that a transformer's attention layers computed for a fixed number of prior tokens (e.g., 16 or 32) — not raw text, not a generic key-value pair. Reusing them avoids recomputing attention over those tokens for every future token.
Q2Why not just always restore from storage — isn't fetching data always cheaper than recomputing it?▾
Not when storage bandwidth is the bottleneck and GPU compute is abundant. On a compute-rich GPU like the H200, restoring from a slow SSD can take up to 10× longer than just recomputing the blocks on the idle-ish GPU. The "fetch is always cheaper" intuition holds for ordinary memory hierarchies but breaks when the alternative to fetching is a fast, exact, parallel compute path.
Q3Why not just always recompute and skip storage entirely?▾
On lower-throughput GPUs (e.g., RTX A5000), recompute cost rises enough that restoring becomes competitive or better — and recompute cost grows quadratically with the number of blocks involved, so for very long contexts it can become the more expensive option. Neither extreme is universally right, which is the paper's whole point.
Q4Can a single request split its blocks between both restore and recompute at once?▾
Yes — that's exactly what the policy does. It reassigns k cache-hit blocks from the restore path to the recompute path, so restoration and recomputation run concurrently on the remaining blocks of the same request.
Q5Why does the paper only optimize prefill latency, not decode?▾
Restoration and recomputation decisions only affect getting the initial context into GPU memory — the prefill phase. Token-by-token decode latency is assumed unaffected by which policy restored the context, so it's held constant and left out of the evaluation.
Q6What happens if no split can satisfy both the throughput and latency targets?▾
The policy switches to a best-effort mode: instead of failing, it picks the allocation that minimizes the worst constraint violation. This can happen when the available hardware simply can't meet the requested SLOs — in that case the answer is more resources, a relaxed SLO, or a different cache placement, not a smarter split.
Q7Why only apply the policy at the disk tier, not CPU DRAM?▾
The trade-off is most pronounced where restoration is slowest and capacity is most constrained — disk. CPU DRAM is treated as a fast transient buffer where the cost asymmetry is much smaller; extending the policy to DRAM is explicitly left as future work.
Q8How expensive is running the scheduler itself?▾
About 5.07 μs per decision, measured over 20.2 million simulated scheduling decisions — sustaining roughly 2×10⁵ decisions/s. It reads parameters (GPU/storage throughput) that already exist in the cache subsystem and inference engine, so no new instrumentation is required.
Q9Is this validated on a real production system, or only simulated?▾
The core SLO evaluation (Figure 3, "up to 10×") is theoretical/simulated across 1,764 hardware configurations; the H200-vs-A5000 case study used real measured restoration/recomputation behavior to motivate the problem. A production-grade implementation and real-workload validation are explicitly listed as ongoing/future work.
Q10How does this connect to OS-level memory tiering research (TPP, HeMem, Memtis, Pond)?▾
Structurally, it's the same multi-tier placement problem you already work on — a fast, small tier and a slow, large one, with a policy deciding what to keep where. The key difference is the extra degree of freedom: a cold KV-cache block can be regenerated via GPU compute, an option ordinary memory pages don't have. The HBM↔disk bandwidth gap here (~300×) is also far steeper than the DRAM↔NVM gap those systems manage (~2–10×), which is why recompute becomes competitive here in a way it rarely would for an ordinary page fault — though this specific framing/comparison is this guide's, not the paper's.

Core terms
I/O-aware policyThis paper's mechanism: dynamically splits KV-cache blocks between restore and recompute based on live GPU/storage throughput and SLOs.
kThe number of cache-hit blocks reassigned from the restore path to the recompute path; solved to equalize both paths' completion times.
N, MN = total requested blocks; M = blocks that are unconditional cache misses and must be recomputed regardless of policy.
X, YGPU recomputation throughput and storage restoration throughput, in bytes/s — the two live inputs the policy reads each decision.
T_c, T_s, T_reqRecomputation time, restoration time, and overall request completion time = max(T_c, T_s).
Best-effort modeFallback used when no split satisfies both SLOs: choose the allocation minimizing the worst constraint violation.
Success rateThe evaluation metric: fraction of hardware/workload configurations that meet both throughput and tail-latency objectives simultaneously.
Cache-hit ratioFraction of requested KV-cache blocks that can be restored from storage (vs. must be recomputed as misses).
Supporting terms
KV-cacheStored key/value attention vectors for previously processed tokens; reusing them turns attention cost from O(N²) to O(N).
HBM / DRAM / diskThe three-tier hierarchy modeled: GPU High Bandwidth Memory, CPU DRAM (storage tier in §3's simulator, transient buffer in §4's policy), and local SSD.
TTFT / TTLT / P95Time-to-first-token, time-to-last-token, and 95th-percentile tail latency — the SLO vocabulary used throughout.
Roofline modelA hardware-performance model combining FLOPs required and peak FLOP/s achievable; used here to estimate recomputation time.
MFU (η)Model FLOPs Utilization — the fraction of peak GPU throughput actually achieved; assumed η=1 in this paper's model.
Zero-copy / block tablevLLM-style design where KV-cache blocks are read in place via a block-to-location map, rather than copied into a contiguous buffer.
Lookup / store / restoreThe three KV-cache operations; only restore is latency-critical for inference.
