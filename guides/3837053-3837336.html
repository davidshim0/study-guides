HotStorage 2026 · A Field Guide

When fetching a memory back is slower than just redoing the math

Every LLM request that reuses old conversation history faces a choice: pull its attention memory (the KV-cache) back from storage, or recompute it fresh on the GPU. This paper shows that choice should never be fixed — it should be measured, live, and split.

📄 Najafizadeh, Tarasov, Merenstein, Zhu, Zadok · HotStorage'26 🎓 Assumes some LLM-serving & storage-tiering background ⏱ ~25 min read
⚖️

Split a request's KV-cache blocks between GPU recompute and storage restore so both paths finish together — never let the slower one set the pace.
Measure GPU and storage speed first, then divide.

Before you begin

Quick glossary, then eight ideas the paper assumes you know

The paper's acronyms first, defined once so nothing later is opaque. Then eight collapsible primers — open whatever looks unfamiliar.

Quick glossary

1Why LLM inference is expensive, and quadratically so▾

Generating text means running the input through many transformer layers of matrix multiplication. Producing the very first output token — prefill — requires attending every input token to every other input token, so cost grows roughly with the square of context length. The paper's headline number: an H200 GPU needs 18 seconds to produce the first token for a 128K-token Llama-3.1-70B prompt if it must redo all that attention work from scratch.

Now you're ready: that 18-second number is exactly what a KV-cache is built to erase — if you don't have to recompute it.
2What a KV-cache actually stores▾

For every token already processed, each attention layer produces a key and value vector. Future tokens reuse those vectors instead of recomputing them. Reuse turns the cost of processing N tokens from O(N²) down to O(N). With KV-cache reuse enabled, that same 128K-token H200 example drops from 18s to under 2 seconds.

Now you're ready: the whole paper is about what happens when that cache doesn't fit in GPU memory and has to live somewhere else.
3The storage hierarchy: HBM, DRAM, disk — capacity vs. bandwidth▾

GPU HBM is fast but tiny and expensive (H200: 141GB at up to 3,360 GB/s). CPU DRAM is bigger, slower to reach from the GPU. Local or remote disk/SSD is huge but slow (NVMe Gen5: roughly 10 GB/s) — a ~300× bandwidth gap from HBM. This paper considers exactly that three-tier hierarchy connected by one interconnect (e.g., PCIe).

Now you're ready: whichever tier holds a KV-cache block determines how long it takes to bring back — the core variable in the restore-vs-recompute decision.
4Blocks and the block table▾

KV-cache isn't one blob — it's split into blocks, each holding a fixed number of tokens (e.g., 16). A block table maps each block to its physical location so the model can read it directly, in place — no copying into a contiguous buffer (zero-copy). For a Llama-3 model with 16-token blocks, one block is about 2MB.

Now you're ready: restore-vs-recompute is decided per block, which is what makes a partial, mixed allocation (some blocks restored, some recomputed) possible at all.
5Why KV-cache gets evicted in the first place▾

Inference engines serve many users concurrently; each session's KV-cache competes for GPU memory. Worse, model weights themselves eat into HBM — a 70B-parameter model at bf16 precision needs 2 bytes/parameter, i.e. ~140GB, on an H200 with only 141GB of HBM total. With 10 users each needing ~30GB of KV-cache for a 128K context, demand hits 300GB — far beyond what's left. Inactive sessions' KV-cache gets evicted to lower tiers to make room.

Now you're ready: when an evicted session returns, its data must be restored from wherever it landed — or recomputed instead.
6Prefill vs. decode, TTFT vs. TTLT▾

Prefill processes the whole input prompt at once, producing the first output token (TTFT). Decode then generates subsequent tokens one at a time (contributing to TTLT). Restoring or recomputing KV-cache only affects prefill — decode latency is assumed unchanged across policies, so the paper measures prefill (P95) latency specifically.

Now you're ready: every SLO number in this paper is about prefill, not the full request.
7Lookup, store, restore — and why restore is the dangerous one▾

Cache systems perform three operations: lookup (metadata only, cheap), store (asynchronous, low impact), and restore (bringing evicted blocks back). Restore is asynchronous from the cache's perspective but effectively blocking from inference's perspective — the request must wait for its data before proceeding, creating queueing delay.

Now you're ready: restore is the one operation worth optimizing, because it's the one on the critical path of a stalled request.
8The roofline model — why recompute time ignores storage▾

A roofline model estimates compute time from the model's FLOP cost divided by the GPU's peak throughput (adjusted by utilization efficiency, MFU/η). Recomputation time therefore depends only on the model and the GPU — never on which storage tier anything sits in. Restoration time depends only on storage and interconnect bandwidth — never on GPU compute power. Two independent clocks, racing.

Now you're ready: because these two times are governed by disjoint hardware, they can be computed independently and compared live — exactly what the policy in Section 4 does.
The whole story in one place

An I/O-aware policy, in a nutshell

The problem, the balancing trick that fixes it, and how the pieces connect.

When a KV-cache block has been evicted to disk, an inference engine has two ways to get it back: restore it over the storage/interconnect path, or recompute it from scratch on the GPU. Existing systems pick one policy — a fixed threshold on time or token count — and hard-code it. The paper's core finding: across 1,764 hardware configurations (6 GPUs × 6 interconnects × 7 DRAM configs × 7 storage devices), restoration time varies by 2–3 orders of magnitude at a fixed context length, while recomputation time depends only on the GPU and model. A threshold tuned for one deployment is simply wrong for the next.

Their fix is a small I/O-aware policy that, for every restore request, measures the GPU's current recompute throughput X and the storage tier's current restore throughput Y, then computes how many of the request's blocks to reassign from restore to recompute so that both paths finish at the same time — no idle GPU waiting on a slow disk, no idle disk bandwidth while the GPU churns. The allocation is then checked against throughput and tail-latency SLOs; if neither path alone can satisfy both, the policy falls back to a best-effort split that minimizes the worst violation.

The payoff: up to 10× improvement in SLO-success rate over static restore-only or recompute-only policies, at an average decision cost of just 5.07 µs — negligible next to the millisecond-to-hour restoration times it's arbitrating between.

🍯 Key takeaways

  • Restoration time depends on storage/interconnect; recomputation time depends on GPU/model — two independent clocks.
  • Across 1,764 configs, restoration time spans 2–3 orders of magnitude at fixed context length; a static threshold can't generalize.
  • The policy reassigns k cache-hit blocks from restore to recompute so T_c ≈ T_s (both paths finish together).
  • Allocation is validated against tail-latency (P95) and throughput SLOs; infeasible cases fall back to a best-effort minimum-violation split.
  • Result: up to 10× success-rate improvement, 5.07 µs/decision, no extra state beyond what the cache and inference engine already track.
Six everyday pictures

How to think about restore vs. recompute

Each stands alone — read in any order. Every card ends with an honest note about where it breaks.

The core idea · Balance

Delivery vs. cooking from scratch

Restoring is ordering delivery: fast if the kitchen is next door (HBM/DRAM), slow if it's across town (disk). Recomputing is cooking it yourself — the time is set by your own stove (the GPU), not by distance. The policy's trick: split your order so the delivery and your cooking finish plating at the same moment.

Where it breaks: a real kitchen can't cook and wait for delivery on the *same dish* at once — but here restore and recompute act on different blocks of the same request, genuinely running in parallel on separate hardware.
The hierarchy · Capacity vs. bandwidth

A desk, a back room, and an off-site warehouse

HBM is your desk — small, everything within arm's reach, instant. DRAM is the back room — bigger, a short walk (bounded by the link). Disk is the off-site warehouse — vast, but a real trip (~10GB/s vs. HBM's 3,360GB/s, a ~300× gap). What you keep on the desk vs. ship to the warehouse determines how long any given fetch takes.

Where it breaks: in a real office you choose what goes where once; here, model weights alone claim most of the desk (140GB of a 141GB H200 for one 70B bf16 model) before any KV-cache gets a seat.
Why cost is quadratic · N²

Introducing every guest to every guest

At a party, the Nth guest must be introduced to all N−1 already there. Total introductions grow as N² — add guests slowly, work explodes. Attention does the same: token N attends to all N−1 before it. That's the N² term in the paper's compute-time formula, and why doubling context length roughly quadruples recompute time.

Where it breaks: guests remember introductions forever; a KV-cache block, once evicted, has to be re-fetched or re-"introduced" every time — the party never truly ends.
The balancing formula · k

Two checkout lines, split so you leave together

An express lane (fast GPU) and the regular line (slow disk) both lead to the exit. Put too much in your cart for the express lane and it's no longer express; put too little and the regular line drags you down. The right split sends just enough items to each line that both carts reach the exit at the same time — exactly what solving T_c = T_s for k does.

Where it breaks: real checkout lines don't know each other's speed in advance; here the policy explicitly reads current GPU throughput X and storage throughput Y before deciding.
Why one threshold fails · variance

One umbrella size fits nobody

A fixed rain-or-shine threshold ("bring an umbrella past 40% humidity") works for one city's climate and fails in the next. Across 1,764 hardware configurations, restoration time swings 2–3 orders of magnitude at a fixed context length — a threshold tuned for one GPU+storage pairing is simply the wrong size for another.

Where it breaks: climate is roughly stable; a deployment's GPU/storage mix is a one-time hardware choice, so the "wrong size" doesn't average out over time — it's wrong every single day.
SLOs · Tail latency

The convoy waits for the slowest truck

A convoy's arrival time is set by its slowest truck, not the average. P95 prefill latency is exactly that: the slowest 5% of requests, which is what actually determines SLO compliance — a great average hides a convoy stuck behind one truck restoring a huge block from disk.

Where it breaks: in a convoy the slow truck is usually the same one; here, which request lands in the tail can shift request-to-request depending on which blocks happen to be evicted to the slow tier.
The full explanation

How the policy actually works

From the tiered-storage model to the balancing formula to SLO validation, with the paper's key relationships rebuilt as diagrams.

1 · Modeling the tiered hierarchy

The simulator models one GPU with HBM, one CPU DRAM tier, and one disk/SSD tier, connected by a single interconnect. Model weights first claim HBM space (2 bytes/parameter at bf16); only what's left is available for KV-cache:

Effective_HBM = Capacity_HBM − 2P            # P = parameter count; weights reserved first
KVC_Space_HBM = floor(Effective_HBM / S_block)  # S_block ≈ 2MB for 16-token Llama-3 blocks

Restoration is charged piece-wise across tiers, bandwidth-limited by whichever is slower — the tier itself or the interconnect:

effective_bw(DRAM) = min(β_dram, β_link)
effective_bw(disk)  = min(β_disk,  β_link)

2 · Compute time via the roofline model

Recomputation cost is estimated independently of storage — purely from the model and GPU:

t_compute = N² · T_block · t̂        # N = blocks; T_block = tokens/block
t̂ = F_token / (Φ_peak · η)          # F_token: FLOPs/token; Φ_peak: GPU peak FLOP/s; η: MFU
💡
Because t_compute has no storage term at all, and restoration time has no GPU term at all, the two can be estimated independently and compared live — that independence is what makes a per-request balancing decision possible.

3 · The balancing formula

Of N requested blocks, M are unconditional cache misses (must be recomputed). Let k be additional cache-hit blocks reassigned from restore to recompute. Because the two paths run in parallel, the request finishes when the slower path finishes — minimized exactly when both paths take equal time:

T_c = N_c·B / X          # N_c = M + k blocks recomputed, throughput X
T_s = N_s·B / Y          # N_s = N − M − k blocks restored, throughput Y
k = max(0, min(N−M,  N·X/(X+Y) − M))

4 · Validate against SLOs, or fall back

The balanced allocation is then checked against the tail-latency target p and the target request rate r:

T_req = max(T_c, T_s) ≤ p        # tail-latency (P95) constraint
r·T_c ≤ 1  and  r·T_s ≤ 1        # throughput / no resource overload
⚠
If neither holds: the current storage and compute capabilities simply cannot serve this request within both SLOs at once. The policy then runs in best-effort mode, choosing the allocation that minimizes the maximum constraint violation, rather than blindly forcing an infeasible split.

5 · What it costs to decide

Measured over 20.2 million timed scheduling decisions, the policy averages 5.07 µs per decision — sustaining roughly 2×10⁵ decisions/second. Scheduling a million real-world requests costs about 5.1 s of decision overhead (vs. 0.23 s for a fixed, no-computation policy). Crucially, every parameter the policy reads (GPU throughput, storage throughput, cache-hit state) already exists inside the cache subsystem and inference engine — no new monitoring infrastructure, only this small computation.

Follow the numbers, step by step

Worked examples

Four traces: why offloading is unavoidable, the balancing formula in action, why compute cost explodes, and whether the policy's own overhead is actually negligible.

① Why offloading is unavoidable, for a 70B model on an H200

An H200 has 141GB of HBM. Llama-3.1-70B is served at bf16 (2 bytes/parameter). How much HBM is actually left for KV-cache?

  1. Weight footprint: 2 bytes × 70×10⁹ params = 140GB just for model weights.
  2. Effective HBM for KV-cache: 141GB − 140GB = ~1GB — barely anything.
  3. One user's 128K-token context needs ~30GB of KV-cache (paper's figure) — already 30× more than what's left.
  4. With 10 concurrent users: demand is ~300GB, and effective on-GPU capacity is ~1GB. Nearly all of it must live off-GPU.
🍯
Insight: offloading isn't a tuning knob — for large models it's the default state. The restore-vs-recompute decision is therefore on the hot path for almost every multi-tenant request, not an edge case.

② The balancing formula, in two throughput regimes

A request needs N=64 blocks (B=2MB each), of which M=16 are unconditional cache misses. Illustrative throughputs: (a) storage faster than GPU, X=200MB/s, Y=800MB/s; (b) GPU faster than storage, X=2000MB/s, Y=200MB/s. Find k, T_c, T_s each time.

  1. Case (a): k = max(0, min(48, 64·200/1000 − 16)) = max(0, min(48, −3.2)) = 0. All 48 cache hits stay on the fast restore path; only the 16 misses recompute.
  2. Case (b): k = max(0, min(48, 64·2000/2200 − 16)) = max(0, min(48, 42.2)) = ≈42. N_c = 16+42 = 58 blocks recompute; N_s = 6 restore.
  3. Check the balance in (b): T_c = 58×2MB / 2000MB/s = 58ms. T_s = 6×2MB / 200MB/s = 60ms — within 2ms of each other, essentially balanced.
  4. The lesson: when storage is the faster path, almost everything restores; when the GPU is faster, the policy shifts the bulk of the work to recompute — automatically, from the same formula.
💡
Note the formula never needs to know which hardware it's running on — only the currently observed X and Y. That's what makes it generalize across the 1,764-configuration space instead of needing a threshold per deployment.

③ Why prefill cost explodes quadratically

Using t_compute = N²·T_block·t̂ with T_block=16 and an illustrative t̂=1µs/token, compare compute time at N=10 blocks vs. N=100 blocks (a 10× increase in blocks).

  1. N=10: t_compute = 10² × 16 × 1µs = 100 × 16µs = 1.6ms.
  2. N=100 (10× more blocks): t_compute = 100² × 16 × 1µs = 10,000 × 16µs = 160ms.
  3. Ratio: 160ms / 1.6ms = 100× — a 10× increase in blocks yields a 100× increase in compute time, exactly the N² scaling.
  4. Matches the paper's own headline number: going from a short prompt to a 128K-token Llama-3.1-70B prompt on an H200 costs 18 seconds of pure recompute — the same quadratic wall, at real scale.
🍯
Insight: this is exactly why restoring (which is only O(N), linear in blocks moved) becomes attractive for long contexts — but only if the storage path is actually fast enough, which is precisely what the balancing formula checks.

④ Is the policy's own overhead actually negligible?

The paper reports 5.07µs/decision average and ≈2×10⁵ decisions/s. Verify the claimed cost of scheduling 10⁶ real-world requests, and compare it to typical restoration times.

  1. 10⁶ requests × 5.07µs/decision = 5.07 × 10⁶ µs = 5.07s — matches the paper's reported ≈5.1s.
  2. Fixed policy (no computation), reported 0.23s for 10⁶ requests implies ≈0.23µs/decision — pure overhead floor, consistent with "no additional state required."
  3. Compare to restoration times: from the case study, restoring even moderate context lengths costs tens of ms to minutes. A 5.07µs decision is 3–7 orders of magnitude smaller than the thing it's optimizing.
💡
For a reader used to weighing OS-level migration or page-fault overhead against DRAM/NVM access latency: this is the same shape of argument — a microsecond-scale scheduling decision is cheap fuel for a millisecond-to-second-scale I/O decision, so the smarter policy essentially costs nothing extra.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
A deployment always restores KV-cache from disk, never recomputes. On a high-end GPU (H200), why can this be a bad policy even though restoring "reuses work already done"?
Show answer
Because reuse only helps if fetching the result is faster than redoing it. On an H200, recompute throughput is very high, while disk restoration is bandwidth-limited to ~10GB/s (or slower, link-limited). Once context length pushes data onto disk, restoring can cost up to 10× longer than just recomputing on the GPU — "already computed" doesn't mean "cheap to retrieve."Misconception: that avoiding recomputation is always a win. It's a win only when the retrieval path is actually faster than the compute path — which depends on the specific GPU and storage tier.
Problem 2 · medium
N=32 blocks, B=2MB, M=8 unconditional misses, GPU throughput X=1000MB/s, storage throughput Y=250MB/s. Compute k, N_c, N_s, and check whether T_c and T_s are roughly balanced.
Show answer
k = max(0, min(24, 32·1000/1250 − 8)) = max(0, min(24, 17.6)) = 17.6 ≈ 18. N_c = 8+18 = 26, N_s = 32−26 = 6. T_c = 26×2/1000 = 52ms. T_s = 6×2/250 = 48ms — within 4ms, essentially balanced, confirming the formula works as intended.Misconception: that k should just be N−M (send every possible block to the faster path). That would starve the restore path entirely and waste its available bandwidth — the formula finds the point where both paths are used as fully as balance allows, not where one is maximized.
Problem 3 · medium
The policy is applied only at the disk tier — CPU DRAM is treated purely as a transient transfer buffer, with no restore-vs-recompute decision made there. Why might that be a reasonable simplification for a first version?
Show answer
DRAM sits much closer to HBM bandwidth-wise than disk does, so the restore-vs-recompute gap is much narrower there — the tradeoff is least pronounced exactly where it's most expensive to build extra machinery. The paper explicitly scopes the policy to "where its impact is most pronounced and can be most clearly observed" and leaves DRAM-tier extension to future work.Misconception: that every tier needs its own restore/recompute decision to be useful. The biggest win comes from targeting the tier with the worst bandwidth gap first — disk, not DRAM.
Problem 4 · hard
Recomputation time is essentially constant across the 1,764 hardware configurations for a fixed GPU, while restoration time varies by 2–3 orders of magnitude at the same context length. Explain the asymmetry using the paper's two formulas.
Show answer
t_compute = N²·T_block·t̂ depends only on N (blocks), T_block, and t̂ = F_token/(Φ_peak·η) — all fixed once you pick a model and GPU, with zero dependence on storage hardware. Restoration time, by contrast, is gated by min(β_tier, β_link), and both storage bandwidth and interconnect bandwidth vary enormously across real hardware (6 interconnects × 7 storage devices in the study) — so restoration inherits all of that variance while recomputation inherits none of it.Misconception: that "I/O overhead" scales with the same factors as compute. They're governed by entirely disjoint hardware, which is exactly why they can — and must — be measured and compared independently rather than assumed proportional.
Problem 5 · medium
Why does the paper focus on prefill (TTFT) latency specifically, rather than the full request latency (TTLT)?
Show answer
Restoring or recomputing KV-cache only affects the prefill phase — turning the input context into usable attention state before generation begins. Decode (token-by-token generation afterward) is assumed unchanged across policies, since it doesn't touch the offloaded KV-cache. Measuring TTLT would blend in decode latency that has nothing to do with the restore-vs-recompute decision, diluting the signal.Misconception: that any latency SLO is a fair evaluation metric here. Only phases actually affected by the policy under test should be measured, or the comparison gets noisy.
Problem 6 · hard
Suppose the computed allocation satisfies the tail-latency constraint T_req ≤ p but violates the throughput constraint r·T_s ≤ 1 (storage would be overloaded at the target request rate). What should the policy do, and why not just force the balanced k anyway?
Show answer
The policy falls back to best-effort mode, picking the allocation that minimizes the maximum constraint violation — which here likely means shifting more blocks toward recompute (increasing k beyond the pure time-balancing point) to relieve pressure on storage, even if that makes T_c and T_s slightly less balanced. Forcing the "balanced" k anyway would satisfy the balance goal while quietly overloading storage across many concurrent requests, degrading throughput for the whole system, not just this one request.Misconception: that minimizing one request's completion time is always correct. The throughput constraint is a system-wide resource-utilization guard, and it can outrank per-request time-balancing when they conflict.
Problem 7 · easy
Two GPUs serve the same model and storage hierarchy: one is an H200, the other an RTX A5000. For which GPU does the restore-vs-recompute decision matter less, and why?
Show answer
The A5000 — because its lower compute throughput makes recomputation slow enough that it's often comparable to restoration time across the whole context-length range, so either choice yields similar performance (both are "viable alternatives that produce the same outputs," per the case study). On the H200, the gap is stark (restore can cost up to 10× more at long context), so getting the decision right matters far more.Misconception: that a smarter policy always buys a big win. Its value scales with how far apart the two paths' speeds are — on hardware where they're already close, an adaptive policy has less headroom to exploit.
Problem 8 · medium
The paper notes 6 GPUs × 6 interconnects × 7 DRAM configs × 7 storage devices = 1,764 configurations, and that for nearly all GPUs except the H200, recomputation curves intersect the restoration-time distributions. What does that intersection imply for policy design?
Show answer
An intersection means that, for a given context length, some hardware configurations favor restoration and others favor recomputation — there is no single globally-better choice, even holding context length fixed. Only the H200's recompute curve stays cleanly below (or crosses least often), because its compute throughput is high enough to nearly always win. This is exactly why a single static threshold across configurations is unsound, and why the policy reads live X and Y instead of using a fixed cutoff.Misconception: that "faster hardware always restores better" or vice-versa. The crossover point is hardware-specific and workload-specific; only measuring live throughput handles all cases correctly.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What exactly is being decided — one choice per request, or per block?▾
Per block, within a request. A restore request may contain many evicted blocks; the policy computes how many of them (k) get reassigned to GPU recompute vs. how many stay on the storage restore path, mixing both within a single request.
Q2Why can restore and recompute run in parallel at all?▾
They use disjoint hardware paths — recompute runs on the GPU's compute units, restore runs over the storage/interconnect path. As long as the missing blocks are correctly partitioned between the two, both engines can work simultaneously on different pieces of the same request.
Q3Does the policy need to know the specific GPU or storage model?▾
No — it only needs the currently observed throughput X (GPU recompute) and Y (storage restore), which the cache subsystem and inference engine already track. That's what lets one formula generalize across all 1,764 evaluated hardware configurations without per-deployment tuning.
Q4What happens to blocks that were never cached at all (true cache misses)?▾
They're recomputed unconditionally — that's the M term in the formula. The policy only has a choice for the N−M blocks that are available on disk (cache hits); M is fixed overhead on the recompute path regardless of the split.
Q5Why measure tail latency (P95) instead of average latency?▾
Averages hide the slow requests that actually break an SLO. If most requests are fast but 5% wait minutes for a disk restore, the average looks fine while user experience doesn't. P95 prefill latency directly captures that slow tail.
Q6Is this the same problem as choosing an eviction policy (what to keep in HBM)?▾
No — eviction decides what leaves GPU memory and when; this policy decides, after something has already been evicted and is being requested back, how to retrieve it. They're complementary: a good eviction policy reduces how often this restore-vs-recompute decision is even needed.
Q7Does this work require modifying the inference engine's internals?▾
The described policy sits at the KV-cache management layer, using metadata (which blocks are cached, current throughputs) that pluggable cache connectors already expose to inference engines like vLLM or SGLang — the paper positions it as complementary to, not a replacement for, those systems.
Q8Why is the reported 10× improvement described as "theoretical" / "initial"?▾
The results come from the performance-modeling simulator (Section 3), not a deployed production system. The authors explicitly list implementing the policy in a real LLM-serving system as future work, to validate the model's accuracy under real operating conditions.
Q9How does cache-hit ratio affect which policy wins?▾
At low cache-hit ratios (<25%), most blocks must be recomputed anyway (few are cached), so restoration's remaining share is small and it can outperform blind recomputation by up to 25%. As the cache-hit ratio rises, more blocks would be restored under a restore-only policy, increasing storage load — and the I/O-aware policy's advantage grows, up to 10×, by shifting excess load to the GPU.
Q10What's explicitly left for future work?▾
A real production-system implementation (to measure actual overhead and validate the model), extending the policy to the DRAM tier, studying how data placement/cache-hit ratios/access patterns affect it in dynamic multi-tier hierarchies, and extending to distributed inference where KV-cache is shared or migrated across nodes.
