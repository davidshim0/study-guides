SOSP 2026 · A Field Guide

Give the hardware a formal model even when you can't see inside it

Systems programmers configure SoCs from thousand-page PDF manuals — closed-source, ambiguous, sometimes wrong. Sockeye turns those manuals into a tiny DSL a solver can attack: find bugs, or prove they can't exist.

Before you begin

What you need to know first

A quick-reference glossary, then six primers. Skim what's unfamiliar.

Quick glossary — acronyms you'll see everywhere

SoCSystem-on-Chip — CPU cores plus dozens of on-chip devices, firewalls, and controllers sharing one die.
RTLRegister-Transfer Level — the hardware's actual source code. Vendors almost never release it.
TEE / TZTrusted Execution Environment / Arm TrustZone — splits a core into Secure and Non-Secure worlds.
SMMSystem Management Mode — x86's "ring -2," a highly privileged interrupt-driven mode.
DMADirect Memory Access — a device reads/writes RAM without going through the CPU core, and its own permissions.
ASCAddress Space Controller — the ThunderX-1 unit that filters DRAM requests by TrustZone world.
SMMU / IOMMUAn MMU for devices: translates and restricts the addresses a DMA-capable device can touch.
DSLDomain-Specific Language — here, Sockeye's own language for hardware, software, and properties.
SMTSatisfiability Modulo Theories — the solving technology (Z3) behind bug-finding and proofs.
CBMCC Bounded Model Checker — one of Sockeye's two main verification backends (the other is Rosette).
1Why closed-source hardware is the actual problem▾

Most SoC verification tools (fuzzers, model checkers) assume you have the RTL. Systems programmers writing firmware for a vendor's chip almost never do — they have a PDF manual, written in prose, that may be ambiguous, incomplete, or simply wrong.

Now you're ready: Sockeye's entire premise is "model from the manual, not the RTL" — the same starting point any kernel/firmware engineer actually has.
2Arm TrustZone — Secure vs Non-Secure worlds▾

TrustZone splits a core (and the memory system) into two worlds: Secure (trusted firmware, key material) and Non-Secure (the regular OS/apps). Memory regions and peripherals are tagged with which world may touch them — orthogonal to user/kernel privilege levels.

Now you're ready: almost every case study in this paper is "did the interconnect correctly enforce the Secure/Non-Secure split," including the paper's headline bug.
3Bug-finding vs. proof — the whac-a-mole problem▾

A fuzzer or bounded checker can report "here's an exploit" — but silence doesn't mean safety, just that it didn't look hard enough. A proof instead rules out an entire class of bugs, for any input, forever (within the model).

Now you're ready: Sockeye deliberately supports both on the same model, so you can convince yourself a proof would have caught a known bug by re-inserting it.
4Symbolic execution and SMT solving, briefly▾

Instead of running a program on one concrete input, symbolic execution runs it on a symbolic variable representing all possible inputs, collecting a logical formula for what happens on each branch. An SMT solver (Z3) then asks: is there an assignment to the symbolic variables that satisfies all assumes but violates an assert? If yes, that assignment is a concrete counterexample — a bug trace.

Now you're ready: this is literally Sockeye's bug-finding loop — Rosette does the symbolic execution, Z3 answers the query.
5Underspecification: modeling "I don't know" honestly▾

Manuals are ambiguous. Rather than guess, Sockeye lets you write any<T> for "some valid value of type T, unconstrained" — an honest over-approximation. If a property holds even when the ambiguous part is adversarially worst-case, it holds regardless of the true (unknown) behavior.

Now you're ready: any, assume, and assert are the three primitives that do all of Sockeye's modeling work — see them everywhere in How It Works.
6Induction: proving "forever" from two finite checks▾

Testing 2 or 3 steps only rules out short attacks. To prove a property holds after any number of steps, find an invariant that (a) holds at boot (base case) and (b) is preserved by every possible single step from an arbitrary state (inductive step), then show the invariant implies your real property.

Now you're ready: this is the exact structure of every proof in §6.2 — three small SMT queries stand in for an unbounded-time guarantee.
The whole story in one place

Sockeye in a nutshell

The problem with configuring closed hardware, the DSL that fixes it, and what it found.

Configuring a modern SoC securely means trusting a chain: vendor docs, the firmware written against them, and the actual silicon — any link can break. RTL-based verification tools can't help systems programmers because they never see the RTL. Fuzzers find individual bugs but prove nothing about the rest. Interactive proof assistants (Dafny, Verus, Rocq) prove things but can't automatically produce counterexamples, so nobody can sanity-check what the proof actually excludes.

Sockeye is a single DSL used to write three things in the same language: the hardware's behavior (transcribed from the reference manual), the firmware/software actions that configure it, and the security property you want. A graph of modules/instances/callees models components (CPU, DMA engine, address-space controllers, DRAM); any<T>, assume, and assert model ambiguity and desired guarantees. The same spec compiles to Rosette (symbolic execution over Z3) or CBMC (bounded model checking) — giving explicit counterexamples for bug-finding, and inductive proofs for the properties that hold for good.

The payoff: across 8 real SoCs — from a 48-core Marvell server chip to a Raspberry Pi microcontroller — Sockeye found a previously-unknown vulnerability in the ThunderX-1's Address Space Controller (confirmed by Marvell, affecting shipping OCTEON network appliances), reproduced two known bugs (AMD's Sinkclose, an STM32H753 erratum), surfaced several documentation errors, and produced four inductive proofs of memory confidentiality/integrity across three platforms.

🍯 Key takeaways

  • Sockeye models from the manual, not RTL — the only source most systems programmers actually have.
  • One DSL, three uses: hardware behavior, firmware actions, and security properties — all checkable by the same solvers.
  • any/assume/assert replace quantifiers Sockeye deliberately omits, to keep SMT queries tractable.
  • Bug-finding gives explicit, hardware-testable counterexamples; proofs use base case + inductive step, no manual invariant search beyond that.
  • Two backends (Rosette, CBMC) act as a performance/cross-validation portfolio — neither dominates the other.
  • Found 1 novel CVE-track vulnerability, reproduced 2 known bugs, several doc errors, 4 proofs across 8 SoCs.
Five everyday pictures

How to think about Sockeye

Each stands alone. Every card ends with where the picture breaks.

The core move · Model from the manual

A locksmith working from the blueprint

You can't open the vault to inspect its gears, but you were handed the manufacturer's blueprint. Cut a key that matches the blueprint precisely, and test it: does it turn? Sockeye transcribes the "blueprint" (the manual) into something testable, without ever touching the vault's actual mechanism (RTL).

Where it breaks: a blueprint can itself be wrong. If the manual misdescribes the vault, a "correct" key built from it may still fail on the real lock — which is exactly the documentation-bug case Sockeye can't rule out by itself.
Bug-finding vs. proof · Whac-a-mole and a fence

Whac-a-mole vs. building a fence

A fuzzer whacks moles as they pop up — satisfying, but there's always another hole. Sockeye's induction proofs instead build a fence: show the invariant holds at the start and can't be broken by any single step, and no mole gets through, ever, without checking each hole individually.

Where it breaks: the fence only protects the yard it encloses — the invariant and property you chose to model. A real attack outside that scope (e.g. a side channel) walks right around it.
Noninterference · Two-copy comparison

Twins raised in parallel, identical rooms

Give two twins the same public information but different secrets, raise them under identical rules, and watch their public behavior. If it ever diverges, the divergence must have come from the differing secret — a leak. Sockeye runs two low-equivalent copies of the SoC in lockstep and asserts their observable state stays equal, exactly this trick, to catch confidentiality leaks that a single-copy snapshot comparison would miss.

Where it breaks: Sockeye has no ∀ quantifier, so "identical rules" for the secret itself has to be built by copying concrete (but nondeterministic) values in an assume_low_equivalent helper — an engineering workaround, not a native quantifier.
Induction · Domino chain

Knocking over an infinite line of dominoes

You can't push every domino by hand — instead show the first one falls (base case), and that any falling domino knocks the next (inductive step). Two finite checks, an infinite conclusion. Sockeye's base_case/inductive_step/invariant_is_useful triple is exactly this, applied to "the security invariant holds at every future clock step."

Where it breaks: you must pick a domino spacing (invariant) that's neither too loose (doesn't actually block the attack) nor too tight (fails its own inductive step) — a real design choice, not automatic.
Underspecification · any/assume/assert

A courtroom sketch, not a photograph

When a witness can't recall a face precisely, a sketch artist draws a face consistent with every known detail, leaving the rest open. any<T> is that sketch: any valid value, unconstrained by whatever the manual didn't pin down. Checking a property against every possible "sketch" is strictly safer than guessing one detail wrong.

Where it breaks: over-approximating too much can make an innocent property "fail" against a sketch that's more permissive than reality — you then have to sharpen the model with an assume, at the risk of assuming away a real bug.
The full explanation

How it actually works

From the component graph to the ThunderX-1 exploit to induction proofs.

1 · The component graph — modules, instances, callees

A Sockeye model is a tree of module instances (the "consists-of" relation); an instance that needs to reach a non-child instance declares a callee (a "depends-on" relation) that an ancestor must wire up explicitly. Mutable state only exists via two primitives: State<T>(init) for a single value, Array<K,V> for indexed storage like DRAM.

2 · The bug — a missing check in request()

The ASC's request() function first checks whether an address targets the region-configuration registers; if so, it dispatches to asc_region_request without checking whether the requester is Secure. Concretely, from the ThunderX-1 manual as transcribed:

mut fn request(r: Request) -> Response {
  if is_region_config_addr(r.address) {   // missing: && r.is_secure
    asc_region_request(r)
  } else if is_allowed_dram_addr(r) { dram_request(r) }
  else { { ok: false, value: any } }
}
⚠
Consequence: Non-Secure code can rewrite region3.ATTR to ATTR_NONSEC — even though region3 overlaps the Secure DRAM range — then read/write "Secure" memory freely. Two register writes; two CPU steps.

3 · Expressing the property, and finding the counterexample

The security scenario: set the CPU to Non-Secure, snapshot DRAM, run two steps, snapshot again, and assert that every address in the Secure range (≤ 0x1f_ffff) is unchanged — any<BitInt(31)> stands in for "for all such addresses." Rosette turns this into an SMT query; when Z3 finds a satisfying assignment (violating the assert), Sockeye replays it through its interpreter to print a trace.

4 · Fixing it, and proving the fix by induction

Add && r.is_secure to the guard; Z3 now returns unsat for the two-step scenario — but that's only a bounded guarantee. To prove it for any number of steps, pick an invariant: "every region is either ATTR_EMPTY/ATTR_SEC, or its address range is disjoint from the Secure range." Check it holds after setup_regions() (base case), that any single step from an arbitrary (havoc'd) state preserves it (inductive step), and that it implies the real property (invariant_is_useful).

💡
Why havoc() before the inductive step? Starting from an arbitrary state (not just the reset state) is what makes the check work for every reachable state, not just states reachable from boot in ≤N steps — the crux of turning a bounded check into an unbounded proof.
Follow the numbers

Worked examples

Four traces through the paper's own data.

① Reconstructing the ThunderX-1 exploit trace

Sockeye's printed trace (Listing 6) is two CPU requests. What does each do?

  1. Request 1: address 0x8000_0000_0070, is_secure: false, write, value 1. Decode the address: bit 47 set (region-config space), bits [6:5] = region id, [4:3] = register id. This targets region3.ATTR, setting it to 1 = ATTR_NONSEC.
  2. Why region 3 matters: in the setup, region3 was configured EMPTY with START=END=0 — but allows() only checks START ≤ addr ≤ END, and 0 ≤ 0 ≤ 0 is true, so address 0 (inside the Secure range) now also matches region3, which is Non-Secure-accessible.
  3. Request 2: address 0, is_secure: false, write, value 0x48ad_c33c_fdc9_99d4. This lands inside the Secure DRAM range (region0, 0 – 0xff_ffff) but is now also permitted by region3 — the write succeeds.
  4. Total cost: exactly 2 steps, both plain MMIO writes a Non-Secure driver could issue — no special privilege needed.
🍯
Insight: the bug isn't in the ASC's DRAM-filtering logic — it's that the filter's own configuration registers weren't behind the filter.

② Reading the region configuration (Figure 2)

The sample setup: region0 = 0x0–0xff_ffff (SEC), region1 = 0x100_0000–0x3_ffff_ffff (NONSEC), regions 2/3 EMPTY.

  1. Secure range size: 0xff_ffff + 1 = 0x100_0000 = 16,777,216 bytes = 16 MB.
  2. Non-secure range size: 0x3_ffff_ffff − 0x100_0000 + 1 ≈ 0x3_ff00_0000 ≈ 16.4 GB — matches the 16 GB DRAM array (2³¹ × 8-byte words = 2³⁴ bytes = 16 GB).
  3. The test property checks addresses ≤ 0x1f_ffff (2 MB) — a sub-range of the 16 MB Secure region, chosen for solver tractability, not because the rest is unprotected.
💡
Note the asymmetry: 4 configurable regions must partition a 16.4 GB address space with byte-level START/END fields — a tiny, easy-to-misconfigure control surface guarding a huge memory.

③ Sizing the specs — Table 1's LOC counts

Spec size (S), scenario/proof size (V), and total (T) lines of code, from Table 1.

  1. Jetson TX2: S = 9667. The paper calls it "the most difficult system to model" — ambiguous carveout-region overlap semantics. LOC bears that out: 4–9× every other platform's spec.
  2. ThunderX-1: S = 2366, V = 1160. V is unusually large relative to S — reflecting the ZIP-engine proof (§6.2) plus multiple bug scenarios, not just the minimized example in §2.
  3. Raspberry Pi Pico: S = 1096, the smallest spec — a microcontroller has far fewer components than a server SoC — yet V = 450, the second-largest scenario code, because of its two separate induction proofs (DMA-only, and with core 1 + FORCE_CORE_NS).
🍯
Insight: spec size roughly tracks documentation ambiguity/component count, not chip complexity per se — Jetson's GPU-heavy SoM is smaller in raw transistor terms than a 48-core server chip, but far larger in Sockeye LOC.

④ Why restricting the search space matters (Table 2, §7.3)

The Zynq (zynq) DMA/TrustZone bug scenario.

  1. Unrestricted: Rosette times out (>900s) searching over 8 DMA channels × arbitrary steps × arbitrary register values.
  2. Fix the DMA channel to one specific controller: bug found in <2 minutes — cutting an 8-way channel choice out of the search.
  3. Also fix the step to "CPU initiates a DMA transfer": bug found in <20 seconds — over 2 orders of magnitude faster than unrestricted.
  4. Compare: aspeed's bug scenario needs 542.4s in Rosette and times out in CBMC — some platforms are simply harder for the solver regardless of restriction.
💡
The lever is always the same: every unconstrained any<T> multiplies the search space. Domain knowledge ("I only care about this channel") is how a human keeps solving times interactive.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
Why can't Sockeye be applied by simply running an existing RTL verification tool on these SoCs?
Show answer
Those tools require the RTL source, which vendors of closed-source platforms don't release to systems programmers. Sockeye's whole value proposition is working from the reference manual instead.Misconception: that "formal hardware verification" always implies RTL access. Sockeye deliberately targets the RTL-less case.
Problem 2 · medium
Sockeye finds a counterexample violating a security property. What are the two possible root causes, and how does Sockeye distinguish them?
Show answer
Either a hardware bug (the spec faithfully describes genuinely unsafe hardware) or a documentation bug (the manual/spec is wrong and the real hardware behaves differently). Sockeye distinguishes them by replaying the exact counterexample trace on real hardware: if the exploit reproduces, it's a hardware bug; if not, it's a documentation bug (as with the Pico 2's DMA security-level write, which was silently ignored on real hardware).Misconception: that a counterexample from the model is automatically a real vulnerability. It's only a real vulnerability once confirmed against actual hardware.
Problem 3 · medium
Why does Sockeye omit ∀ and ∃ quantifiers from its language, and how is "for all addresses" property still expressed?
Show answer
Quantifiers make SMT queries much harder to solve efficiently, hurting the tractability the DSL is designed for. "For all addresses, X holds" is instead expressed by picking one any<T> address adversarially and asserting X for it — since the solver is trying to find a violation, if it can't for an arbitrary/adversarial choice, no concrete choice would violate it either.Misconception: that omitting quantifiers means Sockeye can't express universal properties. It emulates ∀ (in assert position) via adversarial any, though assuming a universal fact needs the separate assume_low_equivalent-style workaround.
Problem 4 · hard
Construct the base case / inductive step / usefulness triple needed to prove "Non-Secure code can never modify Secure DRAM" for MiniThunderX1, in general terms.
Show answer
base_case: after setup_regions() with CPU set Non-Secure, assert the invariant (every region is EMPTY/SEC, or disjoint from the Secure range) holds. inductive_step: havoc() the whole system into an arbitrary state, assume the invariant, take one step(), assert the invariant still holds. invariant_is_useful: havoc()+assume the invariant, snapshot DRAM, take one step, snapshot again, assert Secure-range bytes are unchanged (using an adversarial any address). Together: invariant holds always (induction) and implies the real property (usefulness) → property holds always.Misconception: that the induction alone is the proof. Without the third "usefulness" check, you've only proven the invariant holds — not that it implies the property you actually care about.
Problem 5 · medium
The paper reports Rosette generally outperforms CBMC, but not always. What does this imply for how Sockeye should be used in practice?
Show answer
Since solver performance is famously sensitive to seemingly small encoding choices, and no single backend dominates, Sockeye's practical value comes from treating verification as a portfolio: run the same spec through multiple backends, take whichever finishes, and get free cross-validation (agreement between backends increases confidence; disagreement flags a possible bug in one of the backends/encoders themselves).Misconception: that a "better" backend should simply replace the weaker one. Backend performance is workload-dependent, so redundancy is a feature, not wasted effort.
Problem 6 · easy
Why does Sockeye disallow loops in function bodies?
Show answer
To keep SMT solving times short and the analysis tractable — sequential composition and branching (but no loops) are supported by essentially all backends in the verification space Sockeye targets (Rosette, CBMC, direct SMT). This restriction doesn't prevent expressing complex properties or induction proofs, since the "unbounded" part of a proof comes from induction over steps, not from a loop inside one step.Misconception: that no loops means no unbounded reasoning is possible. Unboundedness comes from the induction structure across separate scenario invocations, not from loops within a single function.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Is Sockeye a hardware description language like Verilog?▾
No. Sockeye is deliberately at a higher level than RTL — it models software-visible behavior (registers, memory-mapped requests, access control) transcribed from manuals, not cycle-accurate gate-level logic. It's closer to a modeling DSL for security-relevant control flow than a synthesizable hardware language.
Q2How do requests and responses between components work?▾
Sockeye takes a higher-level view than real wire protocols: a request is modeled as a function call between module instances, and a response is simply the value that call returns — no bus-level timing or signaling is modeled.
Q3What's the difference between an instance and a callee?▾
instance models "consists-of" — a child component that is part of the parent (forms a tree). callee models "depends-on" — a reference to some other instance elsewhere in the tree, which an ancestor must explicitly wire up (e.g. asc.dram -> dram).
Q4What did the ThunderX-1 vulnerability actually let an attacker do?▾
A Non-Secure-world actor (regular OS/firmware) could reconfigure an unused ASC region to also cover Secure DRAM, then read or write that memory directly — completely bypassing the TrustZone Secure/Non-Secure separation the ASC exists to enforce. Marvell confirmed it also affects their current OCTEON processors used in shipping network appliances.
Q5Does Sockeye require access to physical hardware boards?▾
Not strictly — the specification and analysis only need the manual. But the authors had boards for most of their 8 case studies and used them to classify counterexamples as hardware bugs vs. documentation bugs (e.g. testing the Pico 2 exploit for real, finding it was a documentation bug).
Q6Why can Sockeye's proofs not express "eventually" properties?▾
Sockeye's current property language (assume/assert over scenarios, plus base-case/inductive-step for induction) can express safety properties ("nothing bad ever happens") but not liveness properties ("something good eventually happens") — the paper explicitly lists this as a current limitation.
Q7What happens if the manual is right but the hardware is wrong, and Sockeye reports "secure"?▾
This is the one blind spot the paper is explicit about: if the spec (faithful to the manual) proves a property, but the real silicon deviates from its own documentation in a way that breaks the property, Sockeye has no way to catch it — that requires techniques working from the hardware itself, like fuzzing or RTL-hardware refinement proofs.
Q8Are Sockeye's proofs peer-reviewed to the same standard as, say, Coq proofs?▾
They're fully automatic SMT-discharged proofs (no interactive tactic scripts), which trades some assurance (trusting the SMT solver, the backend encoders, and the compiler chain — explicitly listed among the paper's stated assumptions) for dramatically lower proof-engineering effort compared to hand-written invariants in an interactive prover.
Q9How long does it take a new user to become productive in Sockeye?▾
The paper reports bachelor's/master's students with little prior formal-methods or SoC background were modeling their own platform within a few weeks of starting a thesis, with the main bottleneck being manual ambiguity/complexity rather than the DSL itself. All managed to find bugs; fewer completed full proofs, which are more involved.
Q10What's next for Sockeye?▾
The authors mention more backends (e.g. KLEE) run in parallel for lower wall-clock latency, fuzzing-based bug-finding, auto-generating hardware setup/test code from found exploits, translating from existing formal ISA specs (Sail, ASL) or even using LLMs to help transcribe manuals, and better support for true concurrency (currently each request runs to completion before the next starts).

Glossary & further reading

Every term in one place, then a path to go deeper.

Core DSL terms
ModuleA blueprint for a component, instantiable multiple times; may contain instances, callees, state, and functions.
InstanceA concrete child of a module — the "consists-of" relationship. Instances form a tree rooted at Main.
CalleeA "depends-on" reference to another instance not in the local subtree; must be wired by an ancestor.
State<T>(init)Primitive module holding one mutable value of type T with getter/setter methods.
Array<K,V>Primitive module for indexed storage (e.g. DRAM); supports sparse representation to avoid allocating huge arrays.
any<T>Nondeterministic choice of any valid value of type T — Sockeye's tool for underspecification and emulated quantifiers.
assume / assertRestrictions (assume) and proof obligations (assert) evaluated by the SMT solver during verification.
InterfaceA named set of function signatures a module can implement, for implementation-agnostic component boundaries.
Verification & hardware terms
RosetteA Racket-based symbolic-execution language over Z3 — Sockeye's primary, best-performing backend.
CBMCBounded model checker for generated C code — Sockeye's second backend, used for cross-validation.
Induction proof (base/step)base_case establishes an invariant initially; inductive_step (from a havoc'd state) shows it's preserved by any single step.
ASC (Address Space Controller)The ThunderX-1's TrustZone-aware DRAM request filter — site of the paper's headline vulnerability.
ATTR_SEC / NONSEC / EMPTYThe three region-attribute values controlling which TrustZone world may access an ASC region.
SMMU/IOMMUA device-facing MMU; in the ThunderX-1 ZIP-engine proof, abstracted to a plain virtual-to-physical map.
Low-equivalenceTwo system states agreeing on all low-confidentiality data, possibly differing on high-confidentiality data — the basis of noninterference checks.
Air-gapped modelA "spec" model with obviously-separate state (e.g. per-process virtual memory maps) run in parallel with a realistic "implementation" model with intertwined state, to catch isolation bugs by divergence.
