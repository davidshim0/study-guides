HotStorage 2026 · A Field Guide

Sending compaction to whoever has room, not whoever's cores look free

Split compute and storage across the network, and LSM compaction becomes a cross-node resource fight. This is the plain-English story of RLSM, a scheduler that watches the resource that actually bites — not CPU.

📄 "RLSM: A Disaggregated LSM-Based Key-Value Store with Resource-Aware Compaction" · Lou, Wei, Zhang, Li, Xu 🎓 LSM-tree and RDMA basics assumed — primers cover them ⏱ ~25 min read
🗜️

Route each compaction task by the CRITICAL resource on its path, not by whichever node's CPU looks idle.
MN service state gates near-data; RDMA headroom gates CN-side fallback.

Before you begin

Quick glossary, then nine ideas the paper assumes

Acronyms first, so nothing later is opaque. Then nine collapsed primers — read in order the first time, or jump to whatever's unfamiliar.

1What an LSM-tree is, and why compaction exists▾

An LSM-tree buffers writes in memory, then flushes them as immutable SSTables. That turns random writes into fast sequential I/O. But SSTables pile up, so reads must check more and more files (read amplification) and obsolete entries waste space.

Compaction merges SSTables to reclaim space and bound lookup cost. Production engines even block foreground writes once too many SSTables accumulate, so compaction throughput directly caps write throughput.

Now you're ready: RLSM is entirely about deciding where compaction merge work runs — because that decision now crosses a network.
2Disaggregated memory — splitting compute from storage▾

Instead of one machine holding both CPU and all its data, a disaggregated deployment splits them: compute nodes (CNs) run the application logic, memory nodes (MNs) hold the data pool, and the two talk over a fast network. This lets memory and compute scale independently.

For an LSM store, SSTables live on the MN while the CN runs foreground reads/writes and tree control. RLSM's whole topology in evaluation is 3 CNs sharing 1 MN.

Now you're ready: because SSTables live remotely, a compaction task now has to choose which node does the merge work.
3RDMA — fast, but still a shared, finite pipe▾

RDMA lets a CN read/write MN memory directly, without involving the MN's CPU, at much lower latency than TCP. It's what makes disaggregation viable at all.

But RDMA bandwidth is still a physical resource shared by every CN talking to that MN. In this paper's hardware it hard-caps around 10–12 GB/s. Push enough compaction traffic through it and everyone's foreground and background I/O slows down together.

Now you're ready: "CPU is idle" does not mean "the network has room." RLSM's whole argument rests on that gap.
4Two places a compaction task can run▾

CN-side compaction: the CN pulls input SSTables over RDMA, merges them locally with its own compute, and pushes the outputs back — round-trip network traffic in both directions.

Near-data compaction: the merge runs on an MN-side worker, using local reads/writes; only the CN's metadata update crosses the network. Near-data avoids the RDMA round trip entirely.

Now you're ready: those two paths stress completely different resources — RDMA fabric vs. MN compute — which is the seed of RLSM's design.
5Compaction thread pools and queue depth▾

Each node runs compaction tasks through a fixed-size thread pool. Utilization is the fraction of pool workers busy; queue depth is how many tasks are waiting for a free worker. A pool can be highly utilized with a short queue (keeping up) or highly utilized with a long queue (falling behind, tasks piling up).

Now you're ready: utilization alone doesn't tell you if a pool is coping — queue depth does. RLSM's diagnosis leans on exactly this distinction.
6Write stalls and slowdowns — the LSM's backpressure▾

When SSTables build up faster than compaction can clear them, the engine applies backpressure: a slowdown throttles write rate, and a full stall blocks writes outright until compaction catches up. Counting how often these trigger is a direct readout of whether compaction is keeping pace.

Now you're ready: fewer slowdown/stall events under the same write load is evidence a scheduler is placing compaction well.
7Why CPU utilization looks like the natural signal▾

Compaction does merge computation, so "pick the idle node" is a reasonable first instinct — that's exactly what the prior CPU-aware scheduler, dLSM_dynamic, does: it routes tasks toward CN-side or near-data execution based on CPU-utilization readings.

Now you're ready: RLSM's central claim is that this instinct is wrong in disaggregated settings — the primer after next explains why.
8Admission control and credits▾

An admission controller decides whether a task may enter a limited resource right now, rather than always trying and failing under contention. A credit is a token representing one unit of that capacity; holding a credit means you're allowed in, and releasing it on completion lets the next waiting task in.

Now you're ready: RLSM's near-data path is exactly this — MN admission is credit-gated by pending remote-task count, not attempted blindly.
9Elasticity — why you can't just add MN CPU▾

The whole point of disaggregation is letting memory capacity scale independently of compute. If an MN's compaction pool becomes the bottleneck, permanently overprovisioning MN CPU "solves" it — but re-couples memory and compute cost, eroding the elasticity disaggregation was meant to deliver.

Now you're ready: that's why RLSM controls admission into the finite MN pool instead of asking for a bigger pool.
The whole story in one place

RLSM in a nutshell

The mismatch, the fix, and how the pieces connect.

In a disaggregated LSM store, compaction can run on the CN (fetching SSTables over RDMA) or near the data on the MN. Prior dynamic schedulers, like dLSM_dynamic, pick between them using CPU utilization — a reasonable instinct, since compaction does merge computation. But in disaggregation the path-critical bottlenecks are elsewhere: CN-side compaction is bound by shared RDMA bandwidth, and near-data compaction is bound by the MN's finite compaction-pool capacity. CPU utilization measures neither.

The paper's measurements make the mismatch concrete: CN-side compaction reaches only about 50% of near-data compaction's write throughput despite having more compute threads, because it repeatedly saturates the fabric's 10–12 GB/s hardware ceiling. And CPU-aware scheduling — despite using CPU on both sides — also lands at only about half of near-data's throughput, because it keeps shifting work back onto the RDMA-heavy CN-side path whenever CN cores look free.

RLSM's fix: gate placement by the actual critical resource on each path. MN service state (queue depth, not just utilization) governs near-data admission; RDMA bandwidth headroom, measured from real dual-run task timings, governs CN-side fallback. A completion collector closes the loop, batching completions under one lock and releasing credits so staged tasks can retry.

The payoff: RLSM improves aggregate write throughput by 31%–53% over the strongest baseline (near-data dLSM) across 4/8/16 foreground threads per CN, while keeping peak RDMA bandwidth at 5.52 GB/s versus 11–13 GB/s for the CPU-driven baselines, and holds comparable throughput under read-heavy mixed workloads.

🍯 Key takeaways

  • CPU-aware scheduling splits by idle compute; RLSM splits by the resource each path actually consumes: RDMA for CN-side, MN service capacity for near-data.
  • CN-side compaction reaches only ~50% of near-data throughput despite more threads — the bottleneck is fabric bandwidth (10–12 GB/s ceiling), not CN compute.
  • Queue depth, not utilization alone, exposes MN backlog: near-data hits 94.2% util with a queue of 33.9 — tasks arrive faster than the pool can drain them.
  • A dual-run diagnostic shows CN-side is typically 2.0–2.3× slower than near-data, and competitive only when pre-launch RDMA usage is below ~2 GB/s.
  • RLSM: MN heartbeats + CN bandwidth summaries → two-layer throttled dispatcher (near-data admission, then RDMA-gated CN fallback) → batched completion collector.
  • Result: +31%–53% write throughput over the strongest baseline, comparable throughput under read-heavy mixes, and a stable ~70% MN dispatch ratio as CN count scales.
Six everyday pictures

How to think about RLSM

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The core idea · Critical resource, not idle compute

Picking a shipping route by an empty loading dock

A warehouse manager sees an empty loading dock (idle CPU) and assumes it's safe to ship there — never checking that the highway leading out (RDMA fabric) is already backed up. The dock being free doesn't mean the route is. RLSM checks the road (RDMA headroom), not just the dock.

Where it breaks: a road's capacity is roughly fixed; RDMA headroom fluctuates task-by-task, which is why RLSM measures it live via dual-run task timing rather than assuming a static limit.
Two paths · Data locality

Cooking at the grocery store vs. hauling groceries home

Near-data compaction cooks right where the ingredients (SSTables) already sit — only the finished dish (metadata update) travels. CN-side compaction hauls every raw ingredient home over the highway, cooks there, then hauls the leftovers back — the same trip, twice, for every task.

Where it breaks: the store's "kitchen" (MN compaction pool) is small and shared by every CN — unlike a real kitchen, it can only cook so many dishes at once, which is exactly the second bottleneck RLSM has to manage.
Utilization vs. backlog · Table 1

A busy cashier with, or without, a line

Two cashiers can both be "94% busy." One has no one waiting — busy but coping. The other has thirty people in line — busy and falling behind. Watching only "is the cashier working?" (utilization) can't tell them apart; watching the line (queue depth) can. Near-data compaction hits 94.2% MN utilization and a queue depth of 33.9 — the second number is the one that matters.

Where it breaks: a real line has a visible physical length; RLSM's "queue" is a soft, sampled signal from periodic heartbeats, not instantaneously exact — good enough for admission decisions, not a precise count.
The gate · Threshold behavior (Fig. 3)

A highway on-ramp metering light

Busy highways use ramp meters: a light only lets a car merge when there's genuinely room, rather than letting everyone flood in and jam the whole road. RLSM's CN-side fallback gate works the same way — its dual-run diagnostic shows CN-side compaction is only competitive when pre-launch RDMA usage sits below roughly 2 GB/s; above that, it's typically 2.0–2.3× slower, so the gate stays shut.

Where it breaks: a ramp meter is a single global light; RLSM's gate also checks local conditions (a free CN worker, bounded task cost), so a task can be denied even when the "highway" itself has room.
Completion collector · Batching

One signature for a stack of packages, not fifty

A courier delivering fifty packages could make you sign fifty separate slips — or hand you one manifest to sign once for the whole batch. RLSM's completion collector does the latter: it gathers ready compaction completions, applies all their metadata edits under a single lock, then releases credits and wakes staged tasks — instead of every completion separately contending for the lock.

Where it breaks: batching trades a little latency (waiting to accumulate a batch) for less contention; it's a net win under load, but for a single sparse completion it adds a small delay a per-completion lock wouldn't.
Fairness · Staging & priority growth

A ticket line that jumps the impatient to the front

A staged task that keeps losing to higher-priority work is like a customer repeatedly passed over — annoying, but not forgotten. Each time a task fails admission it adds to the round's delay (letting in-flight work finish and free capacity) and its own staging priority quietly rises, so a long-waiting task eventually wins the next round.

Where it breaks: a real ticket line is strictly ordered; RLSM's priority growth is a soft nudge layered on top of level-awareness (L0 tasks still matter more), so a low-priority task can wait longer than a naive "oldest first" queue would allow.
The full explanation

How it actually works

Section by section, with the paper's key structures rebuilt as diagrams you can read at a glance.

1 · The measurements that motivate RLSM

Three placement strategies were measured on the same write workload: pure CN-side, pure near-data, and CPU-aware switching (dLSM_dynamic). Despite more aggregate compute threads, CN-side compaction lands at only ~50% of near-data throughput; CPU-aware scheduling, despite using CPU on both sides, also lands near half.

⚠
Read the CN-side row carefully: only 42.6% CN utilization, yet the worst throughput and the most write stalls. Idle compute did not translate into throughput — the RDMA path was the bottleneck the whole time.

2 · Resource visibility — cheap, decentralized signals

Critical-resource-aware dispatch needs live visibility into each path's limiting resource, without expensive coordination.

3 · Throttled dispatch — two gates, in order

Each task is first classified by expected resource pressure, then tried against Layer 1 before ever considering Layer 2 — near-data is always preferred when it's admissible.

# dispatch round (per CN, sketch of §3.2)
for task in staged_and_new (highest priority first):
    if mn_queue[task.mn] < class_bound(task) and cn_pending < allowance(level=task.level):
        admit_near_data(task)          # Layer 1: preferred path
    elif task.bounded_cost and cn_worker_free and rdma_headroom(local, global) >= needed:
        admit_cn_side(task)            # Layer 2: RDMA-gated fallback
    else:
        task.priority += 1; stage(task) # wait, don't starve

4 · Completion batching

Every completed compaction needs an incremental metadata (version) update installed before its output is visible. Conventional multithreaded compaction has each completion separately acquire the metadata lock — a source of contention. RLSM's collector instead batches ready completions, applies all their edits under one lock, publishes a single updated view, then releases one remote-task credit per near-data completion and wakes staged tasks — keeping completion and dispatch state consistently ordered.

💡
The ablation in the next tab shows this batching alone contributes a smaller but consistent 5%–15% throughput gain — dispatch placement is the primary lever, batching trims the remaining control-path overhead. (§3.3, §4.2)

5 · Try it: does the RDMA gate open?

Slide the current shared RDMA usage and watch RLSM's Layer-2 gate react, using the paper's own dual-run finding: CN-side compaction is competitive only when pre-launch bandwidth is below ~2 GB/s, and typically 2.0–2.3× slower above that (Fig. 3), against a fabric hardware ceiling of ~10–12 GB/s (§2.1).

6 · Beyond this paper's fabric — generalizing the signal

RLSM's authors are explicit that the specific thresholds are deployment-tuned, but the methodology — identify each path's critical resource and gate on it — is meant to generalize. They name CXL-based systems with near-memory compute as one candidate, since one-sided RDMA access without MN CPU involvement (letting CN read remote SSTables without disturbing MN compute) is structurally similar to CXL.mem access without host-CPU involvement on the memory side. In TCP-based or SSD-backed disaggregation, they note protocol-processing CPU and storage I/O would become additional path-critical resources requiring their own signals and thresholds. (§3.4)

🧭
For tiering/CXL readers: this is the same critique that motivates comparing promotion/demotion signals across TPP, HeMem, Memtis, and Pond — a resource-placement decision is only as good as the signal it's built on, and CPU/access-frequency proxies can miss the resource that's actually saturated. RLSM's finding — that per-path critical-resource visibility beats a single global proxy — is a data-placement-layer instance of the same argument these tiering systems make at the memory-page layer.
Follow the numbers, step by step

Worked examples

Four traces through the paper's own tables and figures — reading utilization vs. queue, RDMA reduction, ablation arithmetic, and dispatch-ratio stability.

① Utilization vs. queue depth at 16 threads (Table 2)

RLSM and dLSM (near-data) reach nearly identical MN utilization — 92.6% vs 94.8%. Does that mean they perform the same?

  1. Read both queue depths. dLSM's MN queue averages 29.2; RLSM's averages 1.2 — a ~24× difference (29.2 ÷ 1.2 ≈ 24.3), despite near-identical utilization.
  2. Interpretation: dLSM's MN pool is saturated and backlogged — tasks queue up faster than they drain. RLSM's admission control keeps the pool just as busy but without the backlog, by throttling how many tasks are allowed to queue.
  3. Confirm with write control: RLSM's slowdown/stall counts (4334/1281) are both lower than dLSM's (4691/1756) — fewer backpressure events, consistent with a shorter queue.
🍯
Insight: "fully utilized" and "falling behind" are different facts. RLSM's admission controller explicitly reads queue depth, not just utilization — this is the paper's central diagnostic move (§2.2, Table 1/2).

② How much RDMA pressure RLSM removes (Table 2, 16 threads)

Compute the peak and average RDMA bandwidth reduction vs. the CN-side baseline (RocksDB_MD).

  1. Peak bandwidth: RocksDB_MD 12.78 GB/s → RLSM 5.52 GB/s. Reduction = (12.78 − 5.52) / 12.78 = 56.8% lower peak.
  2. Average bandwidth: RocksDB_MD 3.74 GB/s → RLSM 1.58 GB/s. Reduction = (3.74 − 1.58) / 3.74 = 57.8% lower average.
  3. Against the fabric's ~10–12 GB/s hardware ceiling (§2.1): RocksDB_MD's peak (12.78) sits essentially at the ceiling; RLSM's peak (5.52) leaves roughly half the fabric's capacity as headroom for foreground traffic.
💡
This is the direct mechanism behind RLSM's write-throughput gain: by admitting most tasks near-data and gating the rest on real RDMA headroom, it simply asks far less of the shared fabric.

③ Do the ablation gains add up to the full-system gain?

Dispatcher-only improves 21%–36% over dLSM; collector-only improves 5%–15%. Full RLSM improves 31%–53% over the strongest baseline. Roughly consistent?

  1. Low end: 21% (dispatcher) + 5% (collector) = 26%, vs. full RLSM's reported low end of 31% — close, with the extra few points plausibly from the two mechanisms interacting (less lock contention because dispatch already reduced contended completions).
  2. High end: 36% + 15% = 51%, vs. full RLSM's reported high end of 53% — again close but not exactly additive.
  3. Takeaway: the two mechanisms are largely complementary rather than overlapping, and dispatch placement is clearly the dominant lever (21–36% alone vs. 5–15% for batching).
📎
The paper itself only claims the two mechanisms are complementary and that dispatch is primary (§4.2) — the near-additivity above is this guide's arithmetic check, not a claim the paper makes directly.

④ How stable is the MN dispatch ratio as CN count scales? (Fig. 8)

Compare the spread of dLSM_dynamic's and RLSM's MN dispatch ratio across 1, 2, and 3 sharing CN nodes.

  1. dLSM_dynamic: 67.5% → 55.3% → 52.3%. Spread = 67.5 − 52.3 = 15.2 percentage points, a relative drop of 15.2/67.5 ≈ 22.5%.
  2. RLSM: 70.0% → 70.7% → 69.8%. Spread = 70.7 − 69.8 = 0.9 percentage points, a relative variation of roughly 1.3%.
  3. Why it matters: as more CNs share one MN, dLSM_dynamic sees more idle CN cores in aggregate and routes progressively more compaction to the RDMA-bound CN-side path — exactly the failure mode CPU signals are prone to. RLSM's RDMA-headroom gate doesn't care how many CN cores are idle; it cares whether the shared fabric has room, so the ratio barely moves.
🍯
Insight: this is the clearest evidence in the paper that the CPU signal actively gets worse at scale, while the resource-aware signal stays flat — the core claim of the paper made visible in one figure.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
CN-side compaction shows only 42.6% CPU utilization yet performs worst of the three strategies in Table 1. What's actually limiting it?
Show answer
The shared RDMA fabric, not CN compute. CN-side compaction must fetch full SSTable inputs and push outputs back over RDMA for every task; those transfers repeatedly push aggregate bandwidth to the 10–12 GB/s hardware ceiling, so tasks wait on the network while CPU sits idle.Misconception: that idle CPU means a path is "not the bottleneck." In disaggregation, the bottleneck can be a resource the CPU-utilization metric never touches.
Problem 2 · medium
Near-data compaction reaches 94.2% MN utilization with a queue depth of 33.9. A colleague says "94.2% isn't even 100%, so the MN has room for more work." Evaluate that claim.
Show answer
Misleading. A queue depth of 33.9 means, on average, ~34 tasks are already waiting for a free worker — the pool is effectively saturated and backlogged, not "6% free." Admitting more work would only grow the queue further. That's exactly why RLSM's admission controller gates on queue depth against a task-class bound, not on "is utilization under 100%."Misconception: treating utilization headroom (100% − util) as available capacity. A long queue means the pool is already oversubscribed regardless of the utilization number.
Problem 3 · medium
As more CNs share one MN, dLSM_dynamic's MN dispatch ratio falls (67.5% → 52.3%). Explain the mechanism, in terms of what CPU-aware scheduling actually observes.
Show answer
With more CNs, the aggregate pool of "some CN core is idle somewhere" grows, even though the shared RDMA fabric hasn't grown at all. CPU-aware scheduling sees more idle CN capacity and routes more compaction to CN-side execution — exactly the resource that's shared and finite, RDMA bandwidth, gets more contended just as the scheduler is sending it more traffic.Misconception: that more compute nodes automatically means more "room" for compute-heavy tasks. The fabric they all share doesn't scale with CN count, so CPU-driven placement gets worse, not better, as the cluster grows.
Problem 4 · hard
The dual-run diagnostic (Fig. 3) shows CN-side compaction is competitive only when pre-launch RDMA usage is below ~2 GB/s. If current usage is 1.5 GB/s and a task is bounded-cost with a free CN worker, should RLSM's Layer 2 gate open?
Show answer
Yes — 1.5 GB/s is below the ~2 GB/s threshold where CN-side becomes roughly time-competitive with near-data, and the other two Layer-2 conditions (bounded cost, free CN worker) are already satisfied. All three conditions of §3.2's CN-side fallback gate hold, so the task is admissible for CN-side execution.Misconception: that the RDMA gate is the only condition. Layer 2 requires bounded cost and worker availability too — low RDMA usage alone doesn't automatically admit a task.
Problem 5 · medium
Why does RLSM's completion collector apply many completions under one lock instead of letting each completion lock and publish independently, as conventional compaction does?
Show answer
Conventional per-completion locking means N completions cause N separate lock acquisitions, each contending with foreground and other compaction threads. Batching collapses that to one lock acquisition per batch — the metadata edits for all ready completions are applied together, then a single updated view is published, cutting lock contention on the control path.Misconception: that batching makes results visible later and is therefore strictly worse for correctness or freshness. It changes only the granularity of publication, not correctness — and the ablation shows it's a net throughput win (5%–15%).
Problem 6 · hard
Under a 90% read-heavy mixed workload, RLSM, dLSM, dLSM_dynamic, and RocksDB_MD all achieve comparable throughput (Fig. 9). Doesn't this undercut RLSM's value?
Show answer
No — it's expected and consistent with RLSM's design target. RLSM optimizes compaction placement under write pressure. At a 90% read ratio, foreground writes no longer saturate the system, so compaction pressure (and hence the cost of misplacing it) drops, and placement strategy matters less. The four schemes converge because the resource contention RLSM is built to manage simply isn't present at that point.Misconception: that a good scheduler should show gains everywhere. RLSM is explicitly a write-intensive-workload optimization; comparable performance under read-heavy load is the paper's own evidence that it isn't degrading reads, not a shortfall.
Problem 7 · medium
RLSM's near-data admission allowance is "level-aware," giving L0 compaction tasks higher priority. Why single out L0?
Show answer
L0 is the latency-critical top level of the LSM-tree — if L0 compaction falls behind, L0 files accumulate quickly and foreground writes hit their configured SSTable limit sooner, triggering stalls. Giving L0 tasks a higher admission allowance keeps that latency-critical path open even when overall MN admission is being throttled for other levels.Misconception: that all compaction levels are interchangeable for scheduling purposes. Backlog at different levels has very different consequences for foreground write stalls.
Problem 8 · easy
Why doesn't RLSM just permanently add more compaction workers to the MN's pool to fix the near-data bottleneck?
Show answer
That would relieve the immediate bottleneck but re-couple memory and compute provisioning — the exact tight coupling memory disaggregation is meant to break, reducing elasticity and cost efficiency. Instead, RLSM controls how many tasks are admitted into the existing finite MN pool, which is scalable without touching MN hardware provisioning.Misconception: that a resource bottleneck should always be solved by adding more of that resource. In a disaggregated system, adding MN compute has an architectural cost the paper explicitly wants to avoid (§2.2).
Quick answers

Frequently asked questions

Twelve questions newcomers ask most. Tap any to expand.

Q1What problem is RLSM actually solving?▾
Where each LSM compaction task should execute in a disaggregated store: on the compute node (CN-side, over RDMA) or near the data on the memory node (near-data). It replaces CPU-utilization-based placement with placement gated by each path's actual bottleneck resource — RDMA bandwidth for CN-side, MN service capacity for near-data.
Q2Why is CPU utilization the wrong signal here?▾
Because in disaggregated memory the compaction paths are bound by resources CPU utilization doesn't measure: CN-side compaction is bound by shared RDMA fabric bandwidth (a 10–12 GB/s hardware ceiling), and near-data compaction is bound by MN queue backlog, which utilization alone doesn't expose. CPU-aware scheduling (dLSM_dynamic) still lands at only ~50% of near-data throughput.
Q3What exactly is "near-data" compaction?▾
Running the SSTable merge on an MN-side worker, using local reads/writes to storage that's already on that node. Only the resulting metadata (version) update crosses the network back to the CN — no bulk SSTable transfer.
Q4What are the two layers of RLSM's dispatcher?▾
Layer 1 tries near-data admission first, gated on MN queue depth against a task-class bound and the CN's pending remote-task allowance (level-aware, favoring L0). Layer 2, tried only if Layer 1 fails, gates CN-side fallback on bounded task cost, a free local CN worker, and sufficient local and global RDMA headroom.
Q5What happens to a task that fails both gates?▾
It's staged: the dispatcher repeatedly retries near-data admission as MN conditions improve, and each failed round both adds delay (letting in-flight tasks finish and free capacity) and raises the task's own staging priority — preventing indefinite starvation while still favoring near-data.
Q6What does the completion collector actually do?▾
It receives both CN-side and near-data completions, batches ready ones, applies all their metadata edits under a single lock instead of one lock per completion, publishes one updated view, then releases one remote-task credit per near-data completion and wakes staged tasks.
Q7How much does each mechanism contribute?▾
The dispatcher (near-data admission + RDMA-gated fallback) alone improves throughput 21%–36% over dLSM. The completion collector alone adds a smaller 5%–15%. Combined, full RLSM reaches the reported 31%–53% over the strongest baseline — dispatch placement is the primary lever.
Q8Does RLSM hurt read performance?▾
Not measurably. Under mixed readrandomwriterandom workloads, RLSM and the three baselines achieve comparable throughput at low write pressure (90% reads), since compaction placement matters less once writes stop saturating the system. RLSM's gains are concentrated in write-heavy regimes.
Q9Is this specific to RDMA, or does the idea generalize?▾
The paper frames the underlying methodology — identify the path-critical resource per execution path, gate on it — as generalizable, explicitly naming CXL-based systems with near-memory compute as a candidate. It also notes that TCP-based or SSD-backed disaggregation would need different signals (protocol-processing CPU, storage I/O) in place of RDMA bandwidth.
Q10How is RLSM evaluated?▾
On CloudLab r6525 nodes (AMD EPYC 7543, 256 GB DRAM, Mellanox ConnectX-6 100 Gbps RDMA NICs) in a 3CN–1MN topology, using RocksDB's db_bench with 20-byte keys, 400-byte values, and 100M fillrandom operations at 4/8/16 foreground threads per CN, against RocksDB_MD, dLSM, and dLSM_dynamic baselines.
Q11Why is the MN's compaction pool configured smaller than the CN's?▾
In the evaluation, MN thread settings are half the CN-side values (CN: 4 persistent + up to 16 on-demand threads; MN: half of both). This mirrors the target setting where compute is elastic on CNs but each MN shard exposes only finite near-data service capacity — exactly the constraint RLSM's admission control is built to respect rather than paper over with more MN threads.
Q12What's left as future/related work in this space?▾
The paper positions itself against two related lines: disaggregated-storage systems that mainly optimize foreground lookups/transactions (RDMA-aware indexes, caching, fault tolerance), and LSM compaction-management work that changes where or how compaction runs (near-data, remote, decomposed, service-style) without resolving which resource signal should drive dynamic placement — the gap RLSM fills.

Critical resourceThe specific resource that actually bounds a given execution path's throughput — RDMA bandwidth for CN-side, MN service capacity for near-data.
Throttled dispatcherRLSM's two-layer scheduler: near-data admission control, then RDMA-gated CN-side fallback.
Completion collectorBatches compaction completions under one lock, releases credits, wakes staged tasks.
Remote-task creditA token representing permission for one outstanding near-data task from a CN; released on completion.
MN dispatch ratioThe fraction of compaction tasks placed on the MN (near-data) rather than the CN.
