Routing compaction by who has headroom, not whoever's core is idle

Split an LSM store across a compute node and a memory node, and "run compaction wherever CPU is free" quietly breaks — it ignores the one resource that's actually scarce. This is the plain-English story of RLSM.

📄 "RLSM: Resource-Aware Compaction" · Lou, Wei, Zhang, Li, Xu 🎓 Some LSM/RDMA basics assumed — primers cover them ⏱ ~20 min read
🧭

Route each compaction task by the resource its path actually burns — MN queue depth near the data, RDMA headroom on the compute node — never by CPU utilization alone.

Before you begin

Quick glossary, then six ideas the paper assumes

Acronyms first — you'll see them everywhere below. Then collapsed primers; open whatever's unfamiliar.

LSM-treeLog-Structured Merge tree: buffers writes in memory, flushes as immutable SSTables, merges them later via compaction.
SSTableAn immutable, sorted on-disk file produced by an LSM flush or compaction.
CN / MNCompute Node (runs the engine, issues writes) / Memory Node (stores SSTables) in a disaggregated deployment.
RDMARemote Direct Memory Access: one-sided, low-latency, high-bandwidth access to another node's memory without its CPU.
dLSM / dLSM_dynamicPrior near-data-compaction LSM for disaggregated memory, and its CPU-utilization-based dynamic-placement variant — RLSM's two baselines, with dLSM the stronger-performing of the pair in the results.
MopsMillion operations per second — the paper's write-throughput unit.
near-data compaction (fast, limited) CN-side compaction (RDMA-heavy) RLSM's dispatcher the critical-resource signal
1Why LSM-trees need compaction▾

Writes land in memory, then flush as immutable SSTables. Left alone, SSTables pile up — reads get slower (checking more files) and space is wasted on stale versions. Compaction merges SSTables to bound both. Most engines stall writes once too many SSTables accumulate.

Now you're ready: compaction throughput caps sustainable write throughput — which is exactly what RLSM is trying to protect.
2Disaggregated memory: splitting CN and MN▾

Instead of one machine owning both compute and memory, a compute node (CN) runs the engine while a memory node (MN) holds the data, connected by a fast network (RDMA). This lets memory and compute scale independently — but now every remote access costs network bandwidth, not just time.

Now you're ready: once SSTables live on the MN, compaction can run either on the CN (fetch data over RDMA) or on the MN (near the data) — a choice that didn't exist before.
3RDMA: fast, but still a shared, finite pipe▾

RDMA lets a CN read/write MN memory directly, bypassing the MN's CPU — great for low latency. But the NIC and fabric still have a hard bandwidth ceiling (here, ConnectX-6 100 Gbps ≈ 10–12 GB/s), and every CN sharing an MN competes for it.

Now you're ready: "RDMA is fast" doesn't mean "RDMA is free." Bulk SSTable transfers for compaction can saturate the same fabric foreground reads depend on.
4Compaction placement = a cross-node resource decision▾

Run compaction on the CN and you pay in RDMA bandwidth (fetching inputs, pushing outputs back). Run it on the MN and you pay in MN's finite worker-pool capacity, shared across every CN it serves. Neither is free — the question is which bottleneck you'd rather pressure, and when.

Now you're ready: this is RLSM's whole premise — placement is not a CPU question, it's a "which shared resource has headroom right now" question.
5Why CPU utilization is a misleading signal here▾

CPU-based schedulers place compaction wherever a core is idle. But an idle CN core doesn't make the RDMA-heavy path safe — the bottleneck is the network, not compute. And MN CPU utilization doesn't expose whether its compaction queue is backlogged. Idle CPU can coexist with a saturated path.

Now you're ready: RLSM replaces CPU signals with the two resources that actually gate each path: MN queue depth, and RDMA bandwidth headroom.
6Write stalls and slowdowns▾

When compaction can't keep up, SSTables pile up past configured thresholds and the engine throttles ("slowdown") or fully blocks ("stall") foreground writes to let compaction catch up. Counting these events is how the paper measures how badly a scheduling policy let compaction fall behind.

Now you're ready: fewer slowdowns/stalls (Table 1, 2) is the operational proof that a scheduler kept the critical resource under control.
The whole story in one place

RLSM in a nutshell

The problem, the fix, and how the pieces connect.

In a CN–MN disaggregated LSM store, every compaction task must execute somewhere: on the CN (reading remote SSTables over RDMA, merging, writing back) or near the data on the MN (using a small, shared MN worker pool). CN-side compaction turns out to cost about 2.0–2.3× more time than near-data compaction, driven by a saturated fabric (10–12 GB/s), not idle compute. Near-data compaction is faster per task but shares one finite queue across every CN — push it too hard and its queue depth balloons (33.9 average under pure near-data placement).

Prior dynamic schedulers (dLSM_dynamic) pick a side using CPU utilization — but CPU is the wrong signal in this setting: idle CN cores don't make the RDMA path safe, and MN CPU doesn't expose compaction backlog. The result is CPU-aware scheduling that still drives RDMA to 8–10 GB/s and only matches about half of near-data's standalone throughput.

RLSM's fix: make the path-critical resource visible and gate on it directly — MN queue depth/worker occupancy for near-data admission, and shared RDMA headroom for CN-side fallback — combined with task priority (L0 tasks get precedence) and a batched completion collector that cuts metadata-lock contention. The result: 31%–53% higher write throughput than the strongest baseline, with comparable performance under read-heavy mixed workloads.

🧭 Key takeaways

  • CN-side compaction is RDMA-bound (2.0–2.3× slower), not CPU-bound — idle cores don't help it.
  • Near-data compaction is faster but shares one finite MN worker pool across all CNs.
  • CPU-utilization scheduling (dLSM_dynamic) mistakes idle compute for a safe path and re-saturates RDMA.
  • RLSM gates by path-critical resource: MN queue depth for admission, RDMA headroom for fallback.
  • A completion collector batches metadata updates under one lock instead of one lock per task.
  • Result: +31–53% write throughput vs. strongest baseline; comparable under read-heavy mixes.
Four everyday pictures

How to think about RLSM

Each stands alone. Every card ends with where the picture breaks.

The core idea · CPU ≠ bottleneck

An empty parking lot, a jammed highway

A store has plenty of empty parking (idle CPU), but the only road to it is backed up for miles (saturated RDMA). "There's parking, go there" is useless advice. CPU-aware scheduling sends compaction to the CN whenever a core is free, ignoring that the road — the shared fabric — is what's actually jammed.

Where it breaks: the highway (RDMA) is shared by everyone's foreground traffic too, so the jam isn't static — RLSM has to keep re-checking headroom, not just check once.
The limit · MN queue depth

One call center, many branches

Every branch (CN) routes support calls to one central call center (the MN worker pool). It answers faster per call than a branch handling it alone — but if every branch floods it at once, callers wait in an ever-growing queue. Near-data compaction is fast per task, yet still bounded by this one shared pool.

Where it breaks: you could hire more call-center staff (more MN CPU), but that defeats the point of disaggregation — elastic memory decoupled from compute.
Fairness · Aging staged tasks

A numbered-ticket waiting room

Every time your ticket isn't called, the clerk nudges you a little higher in priority and your wait adds a small, known delay for everyone else — so nobody is skipped forever, but the room isn't thrown into chaos either. RLSM's staged tasks age the same way: repeated rejection raises priority and delay budget, preventing starvation without synchronous coordination.

Where it breaks: a real waiting room has one clerk; RLSM has independent per-CN dispatchers making uncoordinated local decisions off shared heartbeats — closer to several waiting rooms reading the same noticeboard.
Completion batching · Fewer locks

One cashier closing many registers

Instead of every register closing out and locking the safe separately (one lock per completed task), a single cashier waits, collects several closed-out drawers, and reconciles the safe once. RLSM's collector batches ready compaction completions and applies all their metadata edits under a single lock, instead of contending once per task.

Where it breaks: batching trades a little latency (waiting to collect a batch) for less contention — fine under heavy write load, but a pointless delay if completions are rare.
The full explanation

How RLSM actually works

Three components, in the order a task passes through them.

1 · Resource visibility — cheap, asynchronous signals

Each MN periodically broadcasts a heartbeat to the CNs it serves: compaction-pool size, busy-worker count, and queue depth. Each CN measures its own recent compaction RDMA traffic and exchanges a bandwidth summary with sibling CNs sharing that MN. Every CN's dispatcher then decides locally from cached reports — no synchronous cross-node round-trip sits in the placement decision itself.

2 · Why conservative ordering matters

The dispatcher always tries near-data first and treats CN-side execution as a last resort, not a peer choice — because a wrong CN-side dispatch congests the shared fabric for every CN, while waiting slightly longer for MN capacity only delays one task. Small, bounded-cost tasks are the ones allowed to fall back; large tasks wait, since a large task occupying RDMA for a long time is the exact failure mode that saturated CN-side compaction in the first place (§2.1).

# dispatch round, per task (simplified)
if mn_queue_depth[target] < class_bound and cn_pending[self] < allowance[priority]:
    admit_near_data(task)
elif task.bounded_cost and local_worker_free and rdma_headroom_local and rdma_headroom_fabric:
    dispatch_cn_side(task)
else:
    stage(task)              # delay + priority both increase on repeat failure

3 · Completion batching — closing the loop

Both CN-side and near-data completions report to a single collector instead of each independently acquiring the metadata lock. The collector batches ready completions, applies all their version edits under one lock, publishes a single updated view, then releases one remote-task credit per near-data completion and wakes staged tasks — keeping completion and dispatch state consistently ordered.

💡
Why this matters at scale: under conventional per-task locking, N completions mean N lock acquisitions contending with foreground metadata reads. Batching turns that into one acquisition per batch — directly reducing the control-path overhead the ablation attributes a 5–15% gain to.
Follow the numbers

Worked examples

Three traces through the paper's real measurements.

① Why CN-side compaction saturates the fabric (§2.1)

At 16 compaction threads per CN, where does CN-side compaction's bandwidth go, and why doesn't adding threads help?

  1. Each CN-side task moves data twice: RDMA-reads input SSTables from the MN, then RDMA-writes merged outputs back. More threads = more concurrent transfers, not more useful work once the pipe is full.
  2. The fabric's hardware ceiling is ~10–12 GB/s (100 Gbps ConnectX-6 NICs). CN-side compaction's 16-thread run repeatedly hits exactly that ceiling.
  3. Near-data compaction, by contrast, keeps RDMA traffic between 2–6 GB/s — well under that ceiling, since merging happens locally on the MN instead of pulling SSTables across the network.
  4. Result: CN-side reaches only ~50% of the strongest baseline's write throughput despite having more compute threads working on it.
🧭
Insight: this is the paper's core empirical claim — the bottleneck is RDMA bandwidth, not CN compute, so adding CN threads cannot fix it.

② Reading Table 2: what RLSM actually controls

At 16 foreground threads per CN, compare RLSM to dLSM (pure near-data) and dLSM_dynamic (CPU-aware).

  1. MN utilization is nearly identical: RLSM 92.6% vs. dLSM 94.8% — both keep the MN busy.
  2. But MN queue depth diverges sharply: RLSM 1.2 vs. dLSM 29.2. High utilization with low queueing means RLSM admits only what the MN can actually absorb promptly.
  3. Peak RDMA bandwidth: RLSM 5.52 GB/s vs. dLSM_dynamic 11.15 GB/s and RocksDB_MD 12.78 GB/s — RLSM's CN fallback stays well clear of the fabric ceiling.
  4. Write control events: RLSM has the fewest slowdowns (4334) and stalls (1281) of all four schemes — direct evidence compaction kept pace with writes.
💡
Insight: "high MN utilization" alone isn't a problem — it's utilization with a growing queue (dLSM's 29.2) that signals harmful backlog. This is exactly why RLSM's signal is queue depth, not just utilization.

③ The dual-run diagnosis that sets the RDMA gate (§2.4, Fig. 3)

The diagnostic variant runs each task on both CN and MN and logs pre-launch RDMA bandwidth. What threshold does this justify?

  1. CN-side compaction is typically 2.0–2.3× slower than near-data for the same task, confirming near-data as the default-preferred path.
  2. CN-side only becomes competitive when pre-launch RDMA bandwidth drops below ~2 GB/s — i.e., when the fabric already has slack.
  3. This motivates the RDMA-gated fallback rule directly: allow CN-side execution only when headroom (both local and fabric-wide) is sufficient, not as a default second choice.
🧭
Insight: the ~2 GB/s crossover point isn't an arbitrary design constant — it's read directly off measured task-pair completion times, grounding the gate in observed behavior rather than a guess.
Test yourself

Practice problems

Try each before opening the answer.

Problem 1 · easy
A CN has 8 idle compaction threads and the MN queue is deep. A CPU-aware scheduler dispatches the next task to the CN. Why might this be the wrong call?
Show answer
Idle CN threads say nothing about RDMA headroom. If the shared fabric is already near its ~10–12 GB/s ceiling, adding a CN-side task (which must RDMA-read inputs and write outputs) can push it into saturation regardless of spare compute — CN-side compaction is RDMA-bound, not CPU-bound.Misconception: that idle cores imply a safe execution path. The path-critical resource for CN-side compaction is network bandwidth, not CPU.
Problem 2 · medium
Why does RLSM gate near-data admission on MN queue depth rather than MN CPU utilization?
Show answer
High MN utilization can be healthy (near-data under dLSM runs at 94.8% utilization and still outperforms CN-side) — the harmful signal is a growing queue (dLSM's 29.2 average depth), which means tasks arrive faster than the pool can drain them. Utilization alone can't distinguish "busy and keeping up" from "busy and falling behind." In the actual admission rule, queue depth below a task-class bound is paired with a cap on the CN's own pending remote-task count, and the MN's heartbeat also reports pool size and busy-worker count — queue depth is the headline signal, but not the whole gate.Misconception: that any "resource-aware" signal must be utilization. The paper explicitly shows utilization and backlog diverge (Table 1/2), and backlog is the one that predicts harm.
Problem 3 · medium
A small, bounded-cost compaction task is staged after failing near-data admission. Under what conditions may it fall back to CN-side execution?
Show answer
Only if all three hold: the task has bounded cost, the local CN has a free compaction worker, and RDMA headroom is sufficient both locally and across the shared fabric. Large tasks typically keep waiting for MN admission instead, since occupying RDMA for a long transfer is exactly the failure mode that saturates the fabric.Misconception: that CN-side fallback is a simple "if MN is busy, use the CN" rule. It's a conjunction of conditions specifically designed to keep fallback traffic small and bounded.
Problem 4 · hard
As more CNs share one MN, dLSM_dynamic's MN dispatch ratio falls from 67.5% (1 CN) to 52.3% (3 CNs), while RLSM stays near 70%. Explain the mechanism behind dLSM_dynamic's drop.
Show answer
The paper attributes this to dLSM_dynamic's CPU-aware scheduler: as CN-side CPU becomes more available, it assigns more compaction work to the CN. But the scheduler has no visibility into the shared RDMA fabric, which is now serving more CNs at once and therefore has less headroom per CN, not more. CPU availability (the signal dLSM_dynamic tracks) and fabric contention (the resource that actually matters) move in opposite directions as CN count grows.Misconception: that more CNs simply means more total compute to exploit. More CNs sharing one MN and one fabric means more contention for the actually-scarce resource (RDMA bandwidth), which a CPU signal cannot see.
Problem 5 · easy
Under a 90% read-heavy workload, RLSM, dLSM, dLSM_dynamic, and RocksDB_MD achieve comparable throughput. Why doesn't RLSM's advantage disappear by design here — i.e., why is this expected?
Show answer
RLSM's gains come from resolving compaction-placement contention under write pressure. When reads dominate, foreground writes no longer saturate the system, so compaction pressure (and therefore the benefit of smarter placement) drops — there's simply less of the bottleneck RLSM was built to manage. This is expected, not a weakness specific to RLSM: all four schemes converge once the thing being contended for is no longer scarce.Misconception: that a scheduler's reported gains should hold constant across all workload mixes. Resource-aware scheduling only matters when the resource it manages is actually under pressure.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does RLSM schedule?▾
Individual compaction tasks in a CN–MN disaggregated LSM store, deciding for each one whether it executes on the compute node (over RDMA) or near the data on the memory node.
Q2Why is CPU utilization the wrong signal in disaggregated memory?▾
Because the path-critical resources are elsewhere: CN-side compaction is bottlenecked by shared RDMA bandwidth, and near-data compaction is bottlenecked by MN compaction-pool backlog. Idle CPU on either side doesn't indicate either path is actually safe to use.
Q3Does RLSM avoid CN-side compaction entirely?▾
No — it prefers near-data compaction but permits CN-side execution for small, bounded-cost tasks when RDMA headroom is sufficient both locally and across the fabric. It's a conservative fallback, not a ban.
Q4How does RLSM know the MN's state without constant polling?▾
MNs periodically broadcast heartbeats (pool size, busy-worker count, queue depth) to the CNs they serve. Each CN's dispatcher caches the latest report and decides locally, avoiding synchronous remote coordination on every dispatch.
Q5What stops a staged task from waiting forever?▾
Each time a task fails admission, both its contributed staging delay and its priority increase, so repeatedly rejected tasks gradually climb toward dispatch — preventing starvation without needing synchronous fairness coordination.
Q6Why batch completions instead of handling each one immediately?▾
Each completion needs to update shared metadata under a lock. Handling completions one at a time means one lock acquisition per task; batching applies many completions' edits under a single lock, cutting contention — the ablation attributes a 5–15% throughput gain to this alone.
Q7Which design piece matters more: the dispatcher or the collector?▾
The dispatcher. Resource-aware placement alone (dispatcher-only) improves throughput 21–36% over dLSM, while completion batching alone adds a smaller 5–15%. Combined, RLSM reaches its full 31–53% gain.
Q8Does this generalize beyond RDMA-based disaggregation?▾
The paper argues the methodology generalizes — identify each execution path's actual bottleneck and gate on it — citing CXL-based near-memory compute as a plausible fit. But the specific signals change: TCP-based or SSD-backed disaggregation would need protocol-processing CPU and storage I/O as the tracked resources instead.
Q9What workload is RLSM evaluated on?▾
RocksDB's db_bench with 20-byte keys, 400-byte values, 100M fillrandom operations at 4/8/16 foreground threads per CN, on CloudLab r6525 nodes (AMD EPYC 7543, 256GB DRAM, ConnectX-6 100Gbps RDMA) in a 3CN-1MN topology, plus a readrandomwriterandom mix at 10/50/90% read ratios.
Q10Does RLSM change compaction's merge logic or just where it runs?▾
Placement, admission, and completion handling — not the merge logic itself. RLSM doesn't change what compaction does (merging SSTables to bound read amplification); it changes which node executes each task and when (the dispatcher), and how completions get applied to shared metadata (the completion collector), based on path-critical resource state.
