Put it near what it is read with, in blocks big enough to matter

The 4.2BSD fast file system kept the UNIX file interface and rebuilt everything under it: cylinder groups, 4096-byte blocks with fragments, and an allocator that knows how fast the disk spins. This guide opens every mechanism, every number in the tables, and every assumption the design leans on.

Before you begin

Put related data near each other, and size blocks for both big and small files

A 1984 paper from Berkeley's Computer Systems Research Group: the 4.2BSD file system that replaced the original UNIX layout, why reads got about 8 times faster on the same hardware, and five interface features added while everyone had to rebuild their disks anyway.

⚡ TL;DR

  • Problem: the original UNIX file system used only about 2% of the disk's bandwidth (about 20 KB/s). Inodes sat in one region at the front and data in another, so every file access began with a long seek; blocks were only 512 bytes; and the free list became random after a few weeks of use, so consecutive blocks of a file ended up anywhere on the disk. Doubling the block size to 1024 bytes helped (175 KB/s on a new file system) but fell to about 30 KB/s as the disk aged.
  • Layout fix: split the disk into cylinder groups, each with its own inodes, free-block bitmap and a backup copy of the superblock. Put a file's inode and data in the same group, put the files of one directory in the same group, and spread directories and very large files across groups so no group fills up.
  • Block size fix: blocks of at least 4096 bytes so a transfer moves more data, plus fragments (a block split into 2, 4 or 8 pieces) at the end of small files so the bigger blocks do not waste space. A 4096/1024 file system wastes about as much space as the old 1024-byte one.
  • Disk-aware placement: the allocator knows how fast the disk spins, how many blocks fit on a track and how long the CPU needs between transfers, and places the next block of a file where the head will be when the CPU is ready (rotationally optimal). A 10% free space reserve keeps enough empty blocks for these policies to work.
  • Result: on the same controller, reads go from 29 KB/s (3% of the disk's bandwidth) to 221 to 233 KB/s, about 8 times faster; on a faster controller the new system reaches 466 KB/s, 47% of the bandwidth, and the rates stay stable as the file system ages. The new limit is the CPU: copying data from kernel to user buffers takes about 40% of the time.
  • Interface additions: file names up to 255 characters, advisory file locks, symbolic links, an atomic rename, and per-user disk quotas.

Quick glossary
Platter, surface, headA disk is a stack of rotating platters coated on both surfaces; each surface has one read/write head, and all heads hang from one arm that moves them together.
TrackOne ring of data on one surface: everything a single head can read without the arm moving, in one revolution.
CylinderThe set of tracks at the same arm position on all surfaces. Everything in one cylinder can be read without a seek, only by switching which head is active.
SectorThe smallest unit the disk reads or writes, a fixed-size slice of a track, typically 512 bytes.
SeekMoving the arm to a different cylinder. It costs milliseconds to tens of milliseconds, depending on distance.
Rotational latencyThe time spent waiting for the wanted sector to rotate under the head after the arm is in place: up to one full revolution (16.7 ms at 3600 rpm).
Disk bandwidthThe fastest the disk can deliver data: bytes per track times revolutions per second. The paper measures everything as a percentage of this.
PartitionA contiguous range of a disk's sectors set aside for one purpose; each holds at most one file system.
File system blockThe unit in which a file system allocates and transfers file data: 512 bytes in the original UNIX, 1024 in the "old" Berkeley version, 4096 or more in the new one.
FragmentAn addressable piece of a block, 1/2, 1/4 or 1/8 of it, used to store the tail of a small file without spending a whole block on it.
InodeThe on-disk record for one file: owner, permissions, times, size and the addresses of its data blocks. It does not hold the file's name.
Indirect blockA block that holds more block addresses instead of file data, used once a file outgrows the addresses that fit in its inode.
SuperblockThe record at a known place in a partition that describes the whole file system: its size, block and fragment sizes, and where everything else is.
Free listThe old file system's record of free space: a linked list of free blocks, handed out in list order.
Cylinder groupA run of consecutive cylinders that the new file system manages as a unit, with its own inodes, its own free-space bitmap and a copy of the superblock.
Free-space bitmapAn array with one bit per fragment in a cylinder group, set when the fragment is in use. It replaces the free list.
Rotationally optimal blockThe free block that will arrive under the head just as the CPU is ready to start the next transfer, so no revolution is wasted.
Free space reserveA percentage of blocks (10% by default) that only the system administrator can allocate, so the layout policies always find free space nearby.
Advisory lockA lock the kernel records and grants but does not enforce on reads and writes: it only stops other processes that also ask for the lock.
Symbolic linkA small file whose contents are a pathname; when the kernel meets it while resolving a path, it continues with that pathname instead.
Short primers (tap to open)
1How a 1984 disk reads data, and where the time goes▾

A request to read one block costs three things in sequence. Seek: move the arm to the right cylinder, a few milliseconds for a neighboring cylinder and tens of milliseconds across the disk. Rotational latency: wait for the block to come around; at 3600 revolutions per minute one revolution is 16.7 ms, so the average wait is about 8.3 ms. Transfer: the block passes under the head; on a track of 32 sectors of 512 bytes (16 KB), a 4096-byte block passes in a quarter revolution, about 4.2 ms.

So moving 512 bytes after a random seek costs roughly 30 ms of positioning for half a millisecond of transfer. The only way to use the disk well is to make each positioning delay pay for a lot of data: bigger blocks, consecutive blocks of a file on the same cylinder, and the next block placed so it arrives just when it is wanted.

The paper's yardstick: the most a disk can deliver is bytes per track times revolutions per second. For the test disk that is 983 KB/s, which matches 32 sectors × 512 bytes × 60 revolutions per second (this guide's reconstruction; the paper gives only the 983).

Now you're ready: every mechanism in this paper is a way to avoid a seek or a lost revolution.
2Inodes, directories and indirect blocks▾

A file is an inode plus data blocks. The inode lists the first few block addresses directly (the paper assumes 8 for the old system; 4.2BSD uses 12, which is where the paper's 48 KB threshold comes from). Bigger files use a single indirect block full of block addresses, then a double indirect block of addresses of single indirect blocks, then triple. With 512-byte blocks and 4-byte addresses, an indirect block holds 128 addresses.

A directory is a file whose contents are (name, inode number) entries. Opening /a/b reads the root directory, finds a's inode number, reads that inode, reads a's data to find b, reads b's inode, then b's data. Each arrow can be a separate disk access, which is why where inodes live relative to their data and to each other matters so much.

Now you're ready: "inodes at the front, data after" means every one of those arrows can be a long seek.
3The buffer cache, synchronous reads and asynchronous writes▾

The kernel keeps recently used blocks in memory. A read() that misses must wait for the disk, so a program reading a file issues one request, waits, issues the next: the requests reach the disk one at a time, in file order. A write() normally copies data into a cached block and returns; the disk write happens later. Many pending writes can sit in the disk queue at once, and the driver sorts them to minimize seeking.

This asymmetry explains a puzzle in the paper's results: the old file system writes faster than it reads (48 vs 29 KB/s), because its scattered writes get reordered in the queue while its scattered reads cannot be.

Now you're ready: good layout matters most for reads, because the disk cannot reorder what it has not been asked for yet.
4Interrupts, I/O channels, and why CPU speed affects layout▾

When a transfer finishes, the disk controller interrupts the CPU. The CPU runs the driver, picks the next request and starts it. While it does that, the platter keeps turning. If the next block of the file is physically right behind the one just read, it has already passed the head by the time the next transfer starts, and the disk must wait a full revolution for it to come around again.

Mainframes had I/O channels, separate processors that start the next transfer with no CPU involvement, so back-to-back blocks work. A VAX without one needs some fixed time, which the paper treats as a per-machine parameter. The new file system leaves a gap of the right size between consecutive blocks of a file.

UNIBUS and MASSBUS are two DEC buses for attaching disk controllers to the VAX; the paper's only difference between its two test setups is the controller on each.

Now you're ready: "rotationally optimal" depends on the CPU, not only the disk, which is why the parameter can change when a disk pack moves to another machine.
5The 1984 setting▾

Berkeley's 4.2BSD UNIX ran on DEC VAX-11 computers, for workloads that the original PDP-11 UNIX did not anticipate: VLSI design and image processing that stream large files, and programs that map files into large virtual address spaces and page them in and out. Disks were removable packs or fixed Winchester drives of a few hundred megabytes; the test disk is an Ampex Capricorn 330 MB drive on a VAX-11/750.

Changing the on-disk layout meant every installation had to dump its file systems to tape, rebuild them, and restore them. That one-time cost is why the authors also bundled in interface changes that would have required the same step.

Now you're ready: the interface features in Section 5 are there because the disk format was changing anyway, not because they make the file system faster.
The whole story in one place

Locality, block size, and knowing the hardware

The UNIX file interface stays the same. Only where things go on the disk changes.

The original UNIX file system was simple: a superblock, then all the inodes, then all the data, with free blocks kept on a linked list. On a 1980s disk that layout wastes almost all of the time. Opening a file means reading its inode at the front of the partition and then seeking to its data; listing a directory reads inodes scattered across the inode area; and because freed blocks go back on the free list in whatever order they were freed, after a few weeks the list is random and a file's consecutive blocks land anywhere. Each 1024-byte block then costs a seek and a rotational delay: 30 KB/s out of a disk that can deliver nearly 1 MB/s.

The new file system keeps the UNIX interface and changes the layout in three ways. First, bigger blocks: at least 4096 bytes, so each seek and rotational wait moves four times as much data, and two levels of indirect blocks reach 232 bytes. Because most UNIX files are small, a big block would waste nearly half the disk, so the last partial block of a file can be a fragment of a block.

Second, cylinder groups. The disk is divided into groups of adjacent cylinders, each with its own inodes, free-space bitmap and superblock copy. A file's inode and its data go in the same group; the files of one directory go in the same group; new directories and the later parts of large files are sent to emptier groups so that no group fills up and forces everything else to scatter. Locality and spreading pull in opposite directions, and the policies are heuristics for balancing them.

Third, the allocator is parameterized by the hardware. It knows the blocks per track, the rotation speed and how long the CPU needs to start the next transfer, and it places each new block of a file where the head will be at that moment. A 10% free space reserve keeps enough empty blocks around for all these choices to succeed.

The result is reads at up to 47% of the disk's bandwidth, steady over time instead of decaying. The bottleneck moves to the CPU (copying buffers, allocating blocks), which is why the paper ends its performance section with the next ideas it chose not to build: avoiding the copy, chaining contiguous blocks into one transfer, and preallocating blocks. The rewrite also forced every site to dump and restore its disks, so the authors added long file names, file locking, symbolic links, atomic rename and quotas at the same time.

🍯 Key takeaways

  • A disk's cost is positioning, not transfer: make each seek and rotational wait move more data, and avoid them altogether when possible.
  • Cylinder groups give every file and directory a "home" region on the disk: inodes next to their data, files next to their siblings, with directories and huge files spread out to keep homes from filling up.
  • Big blocks for speed, fragments for space: a 4096/1024 file system wastes about as much space as the old 1024-byte one.
  • Placement uses real hardware numbers: blocks per track, rotation speed, CPU time to start a transfer. A 10% free reserve keeps the policies working.
  • Reads reach 47% of disk bandwidth and do not decay with age; the CPU becomes the limit (about 40% of I/O time is a buffer copy).
  • Long names, advisory locks, symbolic links, atomic rename and quotas came along because everyone had to rebuild their file systems anyway.
Six everyday pictures

How to think about the fast file system

Each stands alone. Every card ends with where the picture stops being true.

Aging free list · scattered blocks

A library that reshelves returns in any empty slot

On opening day the shelves are in order, so a novel's volumes sit side by side. After weeks of returns put into whatever gap is free, volume 1 is in aisle 3 and volume 2 in aisle 40. Every volume now costs a walk. That is the old free list: in order when the file system is made, random a few weeks later, 175 KB/s decaying to 30 KB/s.

Where it breaks: a librarian can reshelve overnight; the old file system had no way to restore order short of dumping the disk to tape and restoring it (M2).
Cylinder groups · directory locality · spreading directories

Assigning hotel floors to families

Give each family rooms on one floor, so visiting each other is a short walk: the files of one directory get inodes in one cylinder group. But put each new family on the emptiest floor, or the first floor fills up and later relatives end up scattered. That is the directory rule: a new directory goes to a group with more free inodes than average and the fewest directories.

Where it breaks: a family that keeps growing (one huge file) is deliberately split across floors every megabyte, which a hotel would never do to a family (M11).
Fragments · aligned within one block

Selling pizza whole or by the slice

Big orders get whole pizzas; a small order gets a few slices so the shop does not hand out a whole pie for one slice of appetite. A file's full blocks are whole pizzas, and its small tail is a few fragments. The leftover slices of a cut pizza are sold to the next small order.

Where it breaks: one order's slices must all come from the same pizza, and slices from two half-eaten pizzas cannot be combined into a whole one: fragments 6 to 9 in the paper's Figure 1 cannot become a block (M6).
Rotational layout · rotdelay

Taking plates from a sushi conveyor

You take a plate, set it down, and then reach again. If the dishes of your order were placed on adjacent spots, the next one has already passed while you were busy, and you wait for a full lap. The chef who knows your pace leaves a gap of one or two spots between your dishes. That is placing the next block where the head will be when the CPU has started the next transfer.

Where it breaks: a diner with a helper (an I/O channel) can take adjacent plates, and if you move the conveyor to a slower diner, every dish already placed still has the old spacing (M9).
Free space reserve (10%)

A parking lot that counts as full at 90%

When a lot is nearly full, the last cars circle for a long time and park at the far end, away from the door they wanted. Closing the lot at 90% keeps a space near every door. The file system's 10% reserve does the same for the allocator: there is almost always a free block close to where the policy wants one, and past that point only the administrator can allocate.

Where it breaks: the lot loses only convenience; the file system loses about half its throughput when full, and files written while it was full stay slow until their data is moved (M8).
Advisory locks

An "in use" sign on a door with no lock

Everyone who checks the sign waits their turn; anyone who ignores it can walk right in. The kernel keeps the sign, wakes waiters when it comes down, and removes it automatically when its owner leaves (the process exits), so no stale sign survives a crash.

Where it breaks: the authors chose a sign over a real lock on purpose: UNIX lets the administrator override any protection, and the programs that most need locks run as the administrator (M16).

What a UNIX file system keeps on disk
  • Superblock: the description of the whole file system (size, block size, how many inodes, where things are). The kernel reads it at mount time.
  • Inodes: one fixed-size record per file, holding owner, mode, times, size and block addresses. A file's inode number is its slot number.
  • Directory data: files whose contents are (name, inode number) entries.
  • Free-space record: a linked free list in the old file system; per-group bitmaps in the new one.
  • File data blocks and indirect blocks (blocks of addresses for large files).

The old file system put these in one fixed order across the whole partition: superblock, all inodes, all data. The new one repeats the bookkeeping in every cylinder group, so each group is a small file system of its own with data, inodes and a bitmap close together.

1 · The old layout, and why it got slower with age

A 150 MB old file system is 4 MB of inodes followed by 146 MB of data, so reaching a file's data from its inode is a long seek, and the inodes of one directory's files are scattered across the 4 MB. Blocks were 512 bytes (later 1024), and free blocks came from a linked list that was in good order only when the file system was new. After a few weeks of creating and deleting files, the list was random, and so was the placement of every new file: a seek before every block. Measured result: 175 KB/s on a new old file system, about 30 KB/s after weeks of use (M1, M2).

2 · The new organization: cylinder groups, bigger blocks, fragments

The partition is cut into cylinder groups, each holding a superblock copy, a fixed number of inodes, a bitmap of free fragments and summary counts (M4, M5). Blocks are at least 4096 bytes, so that two levels of indirection reach 232 bytes and each transfer moves more data (M3). The last partial block of a small file is stored as fragments, so the large block costs no more space than the old 1024-byte system did (M6, M7). A free space reserve keeps the disk from being run completely full (M8).

3 · Placement: global policies choose the group, local routines choose the block

Global policies decide which cylinder group gets a new directory (an emptier one), a new file's inode (its directory's group), and a file's data (its inode's group, until 48 KB and then a new group every megabyte) (M10, M11). They ask for a specific block. The local allocator gives that block if free, otherwise the free block rotationally closest to it on the same cylinder, then elsewhere in the group, then in another group found by quadratic hashing, then by exhaustive search (M12). "Rotationally closest" uses each disk's parameters: blocks per track, rotation speed, and the CPU's time to start the next transfer (M9).

4 · What it achieved and what still limits it

On a VAX-11/750, reads reach 466 KB/s (47% of the disk's bandwidth) and do not decay as the file system ages (M13). Writes are a little slower because allocation costs CPU time. The CPU is now the bottleneck: copying between kernel and user buffers is about 40% of I/O time, and the half-bandwidth ceiling from never using adjacent blocks could only be lifted by changing every disk driver (M14).

5 · Interface changes made while everyone was rebuilding anyway

File names up to 255 characters in variable-length directory entries (M15), advisory shared and exclusive locks (M16), symbolic links that can cross file systems (M17), an atomic rename (M18), and per-user quotas on inodes and blocks (M19).

Background and context
  • McKusick, Joy, Leffler and Fabry, Computer Systems Research Group, UC Berkeley. ACM Transactions on Computer Systems 2(3), August 1984, pages 181 to 197. Received July 1983. The file system shipped with 4.2BSD.
  • Machines: DEC VAX-11 (the measurements use a VAX-11/750) with UNIBUS and MASSBUS disk controllers; test disk: an Ampex Capricorn 330 MB Winchester drive.
  • Workloads that motivated it: VLSI design and image processing ("a small amount of processing on large quantities of data") and programs that map files into large virtual address spaces and page them.
  • Prior work cited: Ferrin's Version 7 UNIX improvements, DEMOS (Powell; preallocation ideas), Multics (symbolic links), Maruyama's disk reorganization, Kowalski's fsck.
The problem

The original 512-byte UNIX file system "provides only about two percent of the maximum disk bandwidth or about 20 kilobytes per second per arm". Berkeley's first fix (1024-byte blocks) doubled that but still used about 4% of the bandwidth, and decayed from 175 KB/s to 30 KB/s over weeks as the free list scrambled.

The result

Up to 47% of disk bandwidth for both reads and writes (8192-byte blocks, MASSBUS), stable over time, with about the same space efficiency as the old system thanks to fragments. The abstract's summary: "File access rates of up to ten times faster than the traditional UNIX file system are experienced."

Mechanisms in dependency order
  1. Diagnose the old system (M1, M2): separated inodes and data, small blocks, a free list that randomizes with age.
  2. Change the units (M3, M6, M7): blocks of 4096 bytes or more for transfer size and file size limits; fragments so small files do not waste space; tell programs the best I/O size.
  3. Change the layout (M4, M5, M8): cylinder groups with local inodes and bitmaps; superblock copies that survive any single track, cylinder or platter; a free reserve so there is always room to place well.
  4. Change the placement (M9 to M12): hardware parameters, rotational layout tables, global policies for inodes and data, a four-level local allocator.
  5. Measure and name the next bottleneck (M13, M14): reads up to 47% of bandwidth; the CPU (copies, allocation) now limits.
  6. Use the forced rebuild (M15 to M19): long names, locks, symbolic links, rename, quotas.
The central trade-offs
  • Locality versus spreading: "If too much localization is attempted, the local cylinder group may run out of space forcing the data to be scattered to nonlocal cylinder groups. Taken to an extreme, total localization can result in a single huge cluster of data resembling the old file system."
  • Transfer size versus wasted space: 4096-byte blocks waste 45.6% (Table I) unless the last partial block can be split; fragments cost extra copying when a file grows a little at a time.
  • Hardware knowledge versus portability: placement tuned for one CPU and disk can be badly wrong after a disk pack moves to another machine; the parameters are therefore adjustable while mounted.
Effect of changes (whole design)
  • If disks hide their geometry (as later drives with zoned recording and remapped sectors do, general knowledge), cylinder and rotational calculations aim at a fiction; cylinder groups still help because nearby logical addresses are usually physically close (inference).
  • If the disk reads whole tracks into its own cache (later drives, general knowledge), the CPU's restart delay no longer costs a revolution and the best rotational gap becomes zero (inference; see M9).
  • If there is no seek or rotation at all (flash, general knowledge), the layout policies lose their purpose, but large blocks and fewer metadata writes still matter (inference).
  • If small-file writes dominate (the LFS paper's premise for the 1990s), the synchronous inode and directory writes that this paper never discusses become the bottleneck (see S).

M1 · The original layout: superblock, then all inodes, then all data

TL;DR
ProblemThe 512-byte UNIX file system, adequate on the PDP-11, delivered about 2% of the disk's bandwidth (about 20 KB/s per arm) on the VAX.
MechanismSuperblock at the start; all inodes next (4 MB of a 150 MB file system); all data after; free blocks on a linked list; 512-byte transfers.
Trade-offSimplicity and no placement constraints on file growth, in exchange for a long seek from every inode to its data and seeks between 512-byte transfers.
Breaks whenWorkloads stream large files (VLSI, images, paging mapped files), or list directories with many files.
Key points
  • "each disk drive is divided into one or more partitions. Each of these disk partitions may contain one file system. A file system never spans multiple partitions." The superblock holds "the number of data blocks in the file system, a count of the maximum number of files, and a pointer to the free list".
  • An inode holds ownership, time stamps, and block indices; the paper assumes 8 direct blocks (footnote 5: "usually in the range 5-13") plus single, double and triple indirect blocks of 128 addresses each with 512-byte blocks.
  • "A 150-megabyte traditional UNIX file system consists of 4 megabytes of inodes followed by 146 megabytes of data. This organization segregates the inode information from the data; thus accessing a file normally incurs a long seek from the file's inode to its data."
  • "Files in a single directory are typically not allocated consecutive slots in the 4 megabytes of inodes", so listing a directory touches many separate inode blocks.
  • "The traditional file system never transfers more than 512 bytes per disk transaction and often finds that the next sequential data block is not on the same cylinder, forcing seeks between 512-byte transfers."
  • Footnote 3: in practice a file is limited to "less than about one gigabyte". With 512-byte blocks and 128 addresses per indirect block, triple indirection reaches 1283 × 512 bytes = 230 bytes, which is where that limit comes from (this guide's arithmetic).
How it works, step by step: ls -l on a directory of 50 files
  1. Read the directory's inode in the inode area (near the start of the partition), then seek out to the directory's data blocks in the data area.
  2. For each of the 50 entries, read that file's inode. The inode slots were handed out as files were created over time, so they are spread across the 4 MB inode area: up to 50 separate disk reads, each with a short seek and a rotational wait (the paper: "typically requires one disk transfer to fetch the inode for each file in a directory").
  3. Reading one of those files means another long seek from the inode area to the file's blocks, and between consecutive 512-byte blocks often another seek.
  4. Cost per 512 bytes: tens of milliseconds of positioning for half a millisecond of transfer, which is how the system ends up near 2% of bandwidth (inference from Step 0's numbers).
Assumptions it relies on
  • A1. Files are small and accessed a little at a time, so transfer size does not matter much (implicit; true of the PDP-11 workloads it was designed for).
  • A2. Placement does not need to know the hardware (implicit: "the old file system ignores the parameters of the underlying hardware" except when the free list is first created).
  • A3. The disk is fast relative to the CPU's needs (implicit; false on the VAX).
If an assumption changes
  • A1 changes (large sequential files): each 512-byte transfer pays full positioning cost, so throughput is a small fraction of the disk's; this is the VAX situation the paper describes.
  • A2 changes (placement must match hardware): nothing in the old design can express "same cylinder" or "next rotational position"; the new design adds the parameters (M9).
  • A3 changes (CPU outpaces disk): applications that "map files from the file system into large virtual address spaces" page constantly, and the file system becomes the bottleneck.
Design notes and rejected alternatives

The authors kept the UNIX interface ("well understood and not inherently slow") and changed only the implementation, so "users of the system have not been faced with massive software conversion." The only one-time cost is dumping and restoring every file system.

Key points
  • Reliability: "staging modifications to critical file system information so that they could either be completed or repaired cleanly by a program after a crash" (citing Kowalski's fsck).
  • Throughput improved "by a factor of more than two" with 1024-byte blocks, for two reasons: "each disk transfer accessed twice as much data, and most files could be described without need to access indirect blocks since the direct blocks contained twice as much data."
  • The paper calls this version "the old file system" from here on. It "was still using only about four percent of the disk bandwidth."
  • "The main problem was that although the free list was initially ordered for optimal access, it quickly became scrambled as files were created and removed. Eventually the free list became entirely random, causing files to have their blocks allocated randomly over the disk. This forced a seek before every block access."
  • "There was no way of restoring the performance of an old file system except to dump, rebuild, and restore the file system." Maruyama's alternative: a process that periodically reorganizes the disk.
How it works, step by step: how a free list scrambles
  1. mkfs builds the free list in an order chosen for fast sequential access (the old file system's one use of hardware parameters). New files get consecutive, well-spaced blocks.
  2. Files are deleted in an order unrelated to where their blocks are. Each freed block is pushed onto the head of the list.
  3. The next file created pops blocks from the head: the last few blocks freed, which came from different deleted files in different places on the disk.
  4. After weeks, the list order has no relation to disk position, so each new file is a random scatter. Reading it costs a seek and a rotational wait per 1024-byte block: 175 KB/s becomes about 30 KB/s.
Assumptions it relies on
  • A1. Free space can be tracked as an unordered set (implicit in a LIFO free list).
  • A2. A file system's performance when new is its performance in use (implicit, and false).
If an assumption changes
  • A1 changes (the allocator needs to find a free block near a given place): a list cannot answer "is there a free block on this cylinder?"; a bitmap per region can. This is why the new system replaces the list with per-group bitmaps (M5).
  • A2 changes (measure aged systems): the paper's Table II is measured on file systems "in production use for at least a month", precisely because aging is what killed the old system.
Design notes and rejected alternatives

Larger blocks were "a good method for improving throughput" (the doubling proved it), which motivated going to 4096 and 8192, but the decay showed that block size alone cannot fix placement. A reorganizing process (Maruyama) was mentioned but not used; the new design avoids needing it by placing well at allocation time.

Connections

Superpages: the same pattern appears in physical memory: a free list that randomizes over time destroys the contiguity that superpages need, and the Superpages paper uses a buddy allocator and a contiguity-aware page daemon to keep it (inference connecting the two papers). LFS: LFS replaces "find free space near X" with "write everything at the end of the log" and pays for it with a cleaner.

M3 · Big blocks: at least 4096 bytes, so two levels of indirection reach 232 bytes

TL;DR
ProblemSmall transfers waste positioning time, and large files need many levels of indirect blocks.
MechanismBlock size is any power of two ≥ 4096 bytes, chosen when the file system is created and recorded in its superblock.
Trade-offFour or more times as much data per transfer and files up to 232 bytes with two indirection levels, in exchange for wasted space on small files (fixed by fragments, M6) and no way to change the size later.
Breaks whenMost files are small and fragments are not available, or a file system needs a different block size after it is built.
Key points
  • "To insure that it is possible to create files as large as 232 bytes with only two levels of indirection, the minimum size of a file system block is 4096 bytes. The size of file system blocks can be any power of two greater than or equal to 4096."
  • "The block size of a file system is recorded in the file system's superblock so it is possible for file systems with different block sizes to be simultaneously accessible on the same system." It "cannot be subsequently changed without rebuilding the file system."
  • "disk accesses in the new file system may transfer up to four times as much information per disk transaction" than with 1024-byte blocks, and "several 4096-byte blocks may be allocated from the same cylinder so that even larger data transfers are possible before requiring a seek."
How it works, step by step: why 4096 is the minimum
  1. Addresses per indirect block: with 4-byte block addresses (general knowledge for 4.2BSD), a 4096-byte block holds 4096 / 4 = 1024 addresses.
  2. Single indirect: 1024 blocks × 4096 bytes = 4 MB.
  3. Double indirect: 1024 × 1024 blocks × 4096 bytes = 210 × 210 × 212 = 232 bytes = 4 GB. Two levels are enough.
  4. With 2048-byte blocks instead: 512 addresses per block; double indirect = 512 × 512 × 2048 = 229 bytes = 512 MB, so a third level would be needed. 4096 is the smallest power of two that makes two levels suffice (this guide's arithmetic).
  5. Why levels matter: each level is another block to read (and allocate) before reaching data in a cold cache; fewer levels means fewer seeks for large files (inference).
  6. Where indirection starts: 4.2BSD inodes have 12 direct addresses (general knowledge), so a 4096-byte-block file needs its first indirect block at 12 × 4 KB = 48 KB. That is exactly the paper's first spill point (M11, footnote 8).
Assumptions it relies on
  • A1. Large transfers are what matter for throughput (stated: VLSI, image processing, paging).
  • A2. Block addresses are 32 bits (implicit; general knowledge).
  • A3. Small files can be handled separately (stated; fragments, M6).
  • A4. One block size per file system is enough, fixed at creation (stated).
If an assumption changes
  • A1 changes (mostly small random accesses): a 4096-byte read for a 100-byte record moves 40 times the needed data; the transfer time grows while positioning still dominates, so little is lost on a 1984 disk but little is gained either (inference).
  • A2 changes (wider addresses): fewer addresses fit per block, so the same block size reaches less with two levels; 8-byte addresses would need 8192-byte blocks for 232 (inference).
  • A3 changes (no fragments): Table I's 45.6% waste at 4096 bytes would make the design unacceptable.
  • A4 changes (mixed workloads on one file system): the only remedy is to rebuild, or to place different workloads on different file systems with different block sizes, which the superblock field makes possible on one machine.
Design notes and rejected alternatives

The authors chose a single large block plus fragments over many block sizes (an extent-style design); the fragment rules (M6) only allow pieces within one block, which keeps the bitmap simple. Larger-than-block transfers were left to a future driver change (block chaining, M14).

Connections

NFS: NFS's 8 KB read and write requests are the size of one 8192-byte block of this file system (inference), and NFS's "synchronous write" covers the data block, an indirect block if one changed, and the inode, the structures described here. Superpages: the same size trade-off (reach versus internal fragmentation) in the TLB.

M4 · Superblock copies that spiral through the pack

TL;DR
ProblemLosing the superblock loses the whole file system, and copies placed at the same offset in every group would all sit on one platter.
MechanismStore a copy in every cylinder group, starting each group's bookkeeping about one track further in than the previous group's, so copies land on different surfaces.
Trade-offSurvives the loss of any single track, cylinder or platter, in exchange for a little data placed before the bookkeeping in each group and a special case for the first group.
Breaks whenDamage spans several surfaces, or the disk's real geometry differs from what the file system was told.
Key points
  • "Because the superblock contains critical data, it is replicated to protect against catastrophic loss. This is done when the file system is created; since the superblock data does not change, the copies need not be referenced unless a head crash or other hard disk error causes the default superblock to be unusable."
  • "if this approach were used, all the redundant information would be on the top platter. A single hardware failure that destroyed the top platter could cause the loss of all redundant copies of the superblock."
  • "The offset for each successive cylinder group is calculated to be about one track further from the beginning of the cylinder group than the preceding cylinder group. In this way the redundant information spirals down into the pack so that any single track, cylinder, or platter can be lost without losing all copies of the superblock."
  • "Except for the first cylinder group, the space between the beginning of the cylinder group and the beginning of the cylinder group information is used for data blocks."
  • Footnote 6: the first 8 KB of the disk are reserved for a bootstrap program, and cylinder group information must begin on a file system block boundary. With blocks of 16 KB or more, the first group would have to leave a gap after the boot block whose size depends on the block size, and "Without knowing the size of the file system blocks, the system would not know what roundup function to use to find the beginning of the first cylinder group."
How it works, step by step
  1. mkfs computes, for group i, an offset of about i tracks from the group's start, wrapping around within the group (general knowledge for the wrap).
  2. Group i's bookkeeping (superblock copy, group summary and bitmap, inodes) is written at that offset; the tracks before it hold ordinary data blocks.
  3. At mount, the kernel reads only the primary superblock at its fixed location; the copies are never read in normal operation.
  4. After a head crash on the top surface, the primary superblock may be unreadable. The repair program reads a copy from another group, whose bookkeeping is on a different surface, and rebuilds (general knowledge: fsck -b).
Assumptions it relies on
  • A1. Superblock contents never change after creation (stated), so copies never need updating.
  • A2. Failures are physically local: one track, one cylinder, or one platter (stated).
  • A3. The file system knows the real tracks-per-cylinder layout (implicit).
If an assumption changes
  • A1 changes (some fields do change, such as free-space totals): 4.2BSD updates those only in the primary superblock and the per-group summaries and leaves the copies stale; that is acceptable because the repair program recomputes such counts from the bitmaps (general knowledge). A copy must never be trusted for anything that changes.
  • A2 changes (whole-drive failure): no layout on one drive helps; that needs a second drive (inference).
  • A3 changes (the drive remaps or zones its sectors): "one track further" no longer means "next surface", so copies may cluster on one platter without anyone noticing (inference).
Design notes and rejected alternatives

Putting all bookkeeping at the start of each group was explicitly rejected because every copy would sit on the top platter. Placing the first group's bookkeeping at the "known" superblock location was rejected by footnote 6's boot-block and alignment argument.

Connections

NFS: the NFS guide's discussion of the boot block (why every partition reserves 8 KB) is the same footnote. LFS: LFS keeps only two fixed-location structures, the superblock and two checkpoint regions, and alternates checkpoints between them for crash safety.

M5 · Cylinder groups and their bookkeeping

TL;DR
ProblemOne global inode area and one global free list put metadata far from data and cannot answer "is there free space near here?"
MechanismDivide the partition into groups of consecutive cylinders; each has a superblock copy, a fixed set of inodes (one per 2048 bytes of space by default), a bitmap of free fragments, and summary counts.
Trade-offMetadata near data and fast local searches, in exchange for a fixed inode count chosen at creation and per-group space accounting.
Breaks whenA group runs out of inodes or blocks while others have plenty, forcing allocations elsewhere.
Key points
  • "A cylinder group is comprised of one or more consecutive cylinders on a disk."
  • Each group's bookkeeping "includes a redundant copy of the superblock, space for inodes, a bit map describing available blocks in the cylinder group, and summary information describing the usage of data blocks within the cylinder group. The bit map of available blocks in the cylinder group replaces the traditional file system's free list."
  • "For each cylinder group a static number of inodes is allocated at file system creation time. The default policy is to allocate one inode for each 2048 bytes of space in the cylinder group, expecting this to be far more than will ever be needed."
  • From M10: "a cylinder group may have no more than 2048 inodes."
  • The bitmap records space "at the fragment level"; the summary information also counts free blocks at each of eight rotational positions (M9).
How it works, step by step: sizing a group
  1. Inode density: one inode per 2048 bytes of space by default. A group with 4 MB of space gets 4 × 220 / 2048 = 2048 inodes.
  2. Inode cap: "a cylinder group may have no more than 2048 inodes", so at the default density a group holds at most about 2048 × 2048 bytes = 4 MB (this guide's arithmetic; larger groups would need a lower density).
  3. Cross-check with M11: footnote 8 says the "every megabyte" spill is meant to redirect a file "when a file has used about 25 percent of the data blocks in a cylinder group". 1 MB is 25% of 4 MB, consistent with groups of about 4 MB (inference).
  4. Inode space: with 128-byte inodes (the 4.2BSD size, general knowledge), 2048 inodes take 256 KB, about 6% of a 4 MB group, for an expected "far more than will ever be needed" number of files.
  5. Bitmap size: one bit per fragment; 4 MB of 1024-byte fragments is 4096 bits = 512 bytes, which fits in one block (inference).
Assumptions it relies on
  • A1. The number of files is predictable enough to fix the inode count at creation (stated: one per 2048 bytes is expected to be "far more than will ever be needed").
  • A2. Moving within a few adjacent cylinders is cheap compared with a seek across the partition (implicit).
  • A3. Allocation decisions can be made from per-group information (implicit; M10 to M12).
If an assumption changes
  • A1 changes (millions of tiny files, for example a mail spool): a group can run out of inodes while it still has free blocks, and the file system can report "no space" with free space left; the only fix is to rebuild with a higher inode density (inference; general knowledge of later FFS behavior).
  • A2 changes (seek cost does not depend on distance, as on flash): grouping no longer saves time; it still keeps bitmaps small and searches local (inference).
  • A3 changes (a policy needs global information): the superblock and summary areas keep per-group totals so global policies can compare groups without reading every bitmap (paper, M10: "file system wide summary information").
Design notes and rejected alternatives

The bitmap replaces the free list because a list only answers "give me any free block", while the layout policies need "give me a free block here". The fixed inode table keeps inode lookup a simple computation from the inode number (group = number / inodes per group, general knowledge).

Connections

NFS: an NFS file handle contains the inode number; with cylinder groups the server finds the inode by arithmetic, which is part of why a stateless server can decode a handle cheaply. LFS: LFS has no fixed inode locations; an inode map in the log records where each inode currently is.

M6 · Fragments: big blocks without wasting space on small files

TL;DR
Problem"most UNIX file systems are composed of many small files"; with uniform 4096-byte blocks, 45.6% of the space would be wasted (Table I).
MechanismA block can be split into 2, 4 or 8 addressable fragments. A file is zero or more full blocks plus, at most, one partly used block made of fragments. The bitmap tracks free space per fragment.
Trade-offSpace use like the old 1024-byte system with the transfer size of 4096, in exchange for copying when a fragmented tail grows (M7) and more bookkeeping for free space.
Breaks whenFree fragments are scattered in different blocks: they cannot be combined into a full block.
Key points
  • "each file system block can be broken optionally into 2, 4, or 8 fragments, each of which is addressable. The lower bound on the size of these fragments is constrained by the disk sector size, typically 512 bytes." The fragment size is fixed at creation.
  • "The block map associated with each cylinder group records the space available in a cylinder group at the fragment level; to determine if a block is available, aligned fragments are examined."
  • "Fragments of adjoining blocks cannot be used as a full block, even if they are large enough." In Figure 1, fragments 6 to 9 are free but span blocks 1 and 2, so "only fragments 12-15 can be coalesced into a full block."
  • "a file is represented by zero or more 4096-byte blocks of data, and possibly a single fragmented block. If a file system block must be fragmented to obtain space for a small amount of data, the remaining fragments of the block are made available for allocation to other files."
  • Space results: a 4096/1024 file system wastes "about the same" as the old 1024-byte system; 4096/512 about the same as the 512-byte system. The new system uses less space for indexing large files and the same for small files, offset by "more space for keeping track of available free blocks."
  • General knowledge, not in the paper: in 4.2BSD only a file's last block, and only while that block is one of the 12 direct blocks, may be a fragment; larger files end in a full block.
How it works, step by step: checking whether a block is free
  1. Block b on a 4096/1024 file system covers fragments 4b to 4b+3 (they are "aligned" to the block).
  2. The block is free only if all four of those bits are free. Block 3 in Figure 1: OOOO, free. Block 1: XXOO, not free.
  3. A request for 2 fragments can use any 2 adjacent free fragments inside one block: 6 and 7 in block 1, or 8 and 9 in block 2, but not 7 and 8, which belong to different blocks.
  4. Why the rule: a block address must name one aligned unit so a whole block can be read in one transfer at a computable location; letting a "block" straddle two would break that (inference).
Assumptions it relies on
  • A1. Most files are small, but most bytes are in big files (implicit in Table I and in the decision to keep big blocks).
  • A2. Only the end of a file needs to be partial (stated: "possibly a single fragmented block").
  • A3. The sector size bounds the fragment size (stated).
  • A4. Leftover fragments in split blocks will be used by other small files (implicit).
If an assumption changes
  • A1 changes (nearly all files are huge): fragments rarely matter; a big block with no fragments would waste little (inference).
  • A2 changes (sparse files or files with holes in the middle): the design has no fragments in the middle of a file, so partial middle blocks still occupy full blocks (inference).
  • A3 changes (4096-byte sectors, as on later disks): a 4096-byte block cannot be split at all; fragments only help with larger blocks (inference).
  • A4 changes (many files freed, leaving one free fragment in many different blocks): plenty of free space, but few whole free blocks; large files then cannot be laid out well, a form of external fragmentation the paper does not measure (inference).
Design notes and rejected alternatives

Table I shows the alternatives: one block size for everything (waste grows to 45.6% at 4096) or small blocks for everything (slow). Fragments keep one block size for transfers and borrow a smaller unit only for allocation. The cost moves to the bitmap (one bit per fragment instead of per block) and to copying during growth (M7).

Connections

Superpages: the same internal-fragmentation trade-off for memory, solved there by reserving a large region and promoting it only when fully populated. F2FS and LFS: log-structured designs write variable amounts of data per segment and have no fragment concept (inference).

M7 · Growing a file: the three cases, the copying cost, and the optimal I/O size

TL;DR
ProblemA file that ends in fragments must sometimes move them when it grows, and a program writing a little at a time causes repeated moves.
MechanismOn each write that grows the file, apply one of three cases; separately, report each file's block size to programs so libraries can write whole blocks.
Trade-offSmall files stay compact, in exchange for copying the tail as it grows; buffered libraries avoid the copies.
Breaks whenA program appends small amounts directly with system calls (for example a log written one line per write).
Key points
  • "Space is allocated to a file when a program does a write system call." Overwriting the middle of a file needs no allocation (footnote 7).
  • Case 1: "There is enough space left in an already allocated block or fragment to hold the new data."
  • Case 2: the file has no fragmented blocks: fill the last block, allocate full blocks while a full block of new data remains, then for the remainder "a block with the necessary fragments is located; otherwise a full block is located."
  • Case 3: the file ends in fragments that are too small: if old fragment data plus new data exceed a block, "a new block is allocated. The contents of the fragments are copied to the beginning of the block and the remainder of the block is filled with new data," and continue as in case 2. Otherwise locate "a block with the necessary fragments or a full block" and write the old fragments plus the new data there.
  • "The problem with expanding a file one fragment at a time is that data may be copied many times as a fragmented block expands to a full block. Fragment reallocation can be minimized if the user program writes a full block at a time, except for a partial block at the end of the file."
  • "the file system interface has been extended to provide application programs the optimal size for a read or write. For files, the optimal size is the block size of the file system". The Standard I/O library and utilities such as archivers and loaders use it.

Reading the paper's rules literally, every 4 KB of file costs 1 + 2 + 3 = 6 KB of copying plus three fragment allocations and three frees (this guide's arithmetic). With a 4096-byte write each time, the file never has a fragment except at its very end: no copies. General knowledge, not in the paper: 4.2BSD first tries to extend the fragments in place when the neighboring fragments in the same block are free, so the copies happen only when they are not.

Assumptions it relies on
  • A1. Most programs write through a buffered library that can use the optimal size (stated: the Standard I/O library uses it).
  • A2. Files are mostly written sequentially and grow at the end (implicit in the three cases).
  • A3. Copying a few KB in memory is cheap compared with disk time (implicit).
If an assumption changes
  • A1 changes (unbuffered small appends): each block's worth of appends pays several reallocations and copies; the paper's own warning case.
  • A2 changes (random writes inside the file): no allocation for overwrites (footnote 7), so the cases do not apply; writes beyond the end into a new region follow case 2 (inference).
  • A3 changes (CPU becomes the bottleneck, as M13 shows it did): copies and allocations show up directly in write throughput; this is why 4096-byte writes are slower than reads in Table IIb (M13).
Design notes and rejected alternatives

Rather than make the kernel predict file growth, the authors expose the block size and let libraries buffer. Preallocating several blocks for a fast-growing file (from DEMOS) was considered and rejected because allocation was under 10% of write time (M14).

Connections

Mesa and Hints: exposing the right I/O size instead of hiding it is an example of the interface letting clients do the efficient thing (inference). LFS: LFS batches many small writes in memory and writes them as one segment, so small appends cost no reallocation on disk.

M8 · The free space reserve: never let the disk fill up

TL;DR
ProblemLayout policies need free blocks near where they want to place data; on a nearly full disk there are none, and every allocation becomes effectively random.
MechanismA parameter, the free space reserve (10% in the measurements), below which only the system administrator can allocate blocks. It can be changed while mounted.
Trade-offSteady performance, in exchange for 10% of the disk users cannot fill.
Breaks whenThe administrator fills the reserve, or the reserve is set to zero: throughput "tends to be cut in half".
Key points
  • "In order for the layout policies to be effective, a file system cannot be kept completely full."
  • "If the number of free blocks drops below this level only the system administrator can continue to allocate blocks. The value of this parameter may be changed at any time, even when the file system is mounted and active."
  • "If the number of free blocks falls to zero, the file system throughput tends to be cut in half, because of the inability of the file system to localize blocks in a file." Performance comes back by removing files; "Access rates for files created during periods of little free space may be restored by moving their data once enough space is available."
  • "The free space reserve must be added to the percentage of waste when comparing the organizations given in Table I." An old 1024-byte system (11.8% waste) is "roughly comparable" to a new 4096/512 system (6.9% waste) with a 5% reserve.
How it works, step by step: the space accounting
  1. A 300 MB partition with a 10% reserve: ordinary users see "full" when 270 MB is allocated (illustrative numbers).
  2. Effective cost of the new design versus the old: 4096/1024 waste ≈ 11.8% (same as old 1024) plus a 10% reserve, so about 10 percentage points more than the old system on the same files. With 4096/512 and a 5% reserve: 6.9 + 5 = 11.9%, about the old 11.8%.
  3. Why 10% is enough: spread across many cylinder groups, 10% free means most groups have free blocks on most cylinders, so the local allocator's first or second level almost always succeeds (inference; the paper only says file systems with 10% free "rarely use" the hashing fallback).
  4. The NFS paper's df listing shows the reserve in action: used + available = 90% of each file system's size (the NFS guide's worked example).
Assumptions it relies on
  • A1. Spare capacity is cheap enough to give up 5 to 10% (implicit).
  • A2. Free space is spread across groups, not concentrated in a few (implicit, helped by the spreading policies of M10 and M11).
  • A3. Users can be stopped at the reserve while the administrator continues (stated).
If an assumption changes
  • A1 changes (disk space is the scarce resource): the reserve can be lowered at any time, and the paper accepts the cost: about half the throughput when full.
  • A2 changes (one group fills while others are empty): files in that group spill elsewhere, which is what the directory and large-file spreading policies are designed to prevent.
  • A3 changes (everything runs as root): the reserve no longer stops anyone; the disk can fill completely (inference).
Design notes and rejected alternatives

The paper chooses a soft limit enforced by permissions over any automatic reorganizer. Damage from running full is persistent: files written while space was short stay scattered until their data is moved.

Connections

Flash (general knowledge): SSDs keep a hidden spare area for the same reason, so the garbage collector always has room; performance falls sharply when it is too small. LFS: the LFS cleaner's cost rises steeply with disk utilization for exactly this reason: free segments are what make writing cheap.

M9 · Parameterization and rotational layout: place the next block where the head will be

TL;DR
ProblemWithout an I/O channel, the CPU needs some time after one transfer to start the next; if the file's next block is physically adjacent, it has already passed the head, and the disk waits a full revolution.
MechanismRecord the disk's blocks per track and rotation speed and the CPU's restart time; allocate the next block of a file the right number of blocks later on the same cylinder. Per-group counts at eight rotational positions and superblock "rotational layout tables" make the search fast.
Trade-offSequential reads avoid lost revolutions, in exchange for never using adjacent blocks (at most half of each track's bandwidth on these disks) and a layout tied to one CPU.
Breaks whenThe disk moves to a slower CPU: "throughput will drop precipitously because of lost disk revolutions on nearly every block."
Key points
  • "the new file system tries to allocate new blocks on the same cylinder as the previous block in the same file. Optimally, these new blocks will also be rotationally well-positioned."
  • With an I/O channel, "two consecutive disk blocks can often be accessed without suffering lost time"; without one, "the main processor must field an interrupt and prepare for a new disk transfer," and the time "depends on the speed of the main processor."
  • Disk parameters: "the number of blocks per track and the rate at which the disk spins", giving "the number of milliseconds required to skip over a block." CPU parameter: "the expected time to service an interrupt and schedule a new disk transfer." The allocator computes "the number of blocks to skip over".
  • "Eight rotational positions are distinguished, so the resolution of the summary information is 2 milliseconds for a typical 3600 revolution per minute drive."
  • "The superblock contains a vector of lists called rotational layout tables. The vector is indexed by rotational position. Each component of the vector lists the index into the block map for every data block contained in its rotational position."
  • The delay parameter "can be changed at any time, even when the file system is mounted and active." A file system laid out for a 2 ms processor and moved to a 4 ms one loses revolutions on nearly every block; reconfiguring after the move makes "all further allocation" correct.
How it works, step by step: computing the skip
  1. Time per block: 16.67 ms per revolution / 4 blocks per track = 4.17 ms per 4096-byte block (8.33 ms for 8192-byte blocks, 2 per track).
  2. Blocks to skip: the smallest whole number of blocks whose passing time covers the CPU's restart time: ⌈2 ms / 4.17 ms⌉ = 1 block. For a 4 ms CPU: still 1 block (4.17 ≥ 4). For a 5 ms CPU: 2 blocks (inference from the stated rule).
  3. Rotational positions: 16.67 ms / 8 positions ≈ 2.08 ms each. With 4 blocks per track, blocks start at positions 0, 2, 4 and 6; with 2 blocks per track, at 0 and 4 (inference).
  4. Finding a block: the allocator wants, say, position 4 on the current cylinder. It reads the group's count of free blocks at position 4; if non-zero, it takes the rotational layout table's list for position 4 and checks only those bitmap entries. If zero, it tries nearby positions ("rotationally closest", M12).
  5. After a move to a slower machine, the administrator changes the parameter; new files get the new spacing, existing files keep the old one until copied (inference from "all further allocation").

Assumptions it relies on
  • A1. The CPU's restart time is predictable and roughly constant (stated as a parameter).
  • A2. The file system knows the true blocks per track and rotation speed (stated).
  • A3. Head switching takes no time (stated in M12: "It is assumed here that head switching time is zero").
  • A4. Files are read sequentially at the speed the CPU can request blocks (implicit).
  • A5. The disk does not buffer data on its own (implicit; true of 1984 drives).
If an assumption changes
  • A1 changes (a slower or busier CPU): the restart takes longer than the gap, so each block costs an extra revolution: the "precipitous" drop, about 197 KB/s instead of 491 KB/s in the figure's setting (inference; Worked Example ④ shows when a slower CPU does and does not trigger it).
  • A2 changes (wrong geometry): "rotationally optimal" blocks are at the wrong angle; the result is random extra rotational delay (inference).
  • A3 changes (head switches cost time): blocks on another surface of the same cylinder arrive later than computed; the paper suggests building that into the tables but says "This, however, has not yet been tried."
  • A4 changes (the program processes each block slowly): the gap is too short no matter what; the disk waits for the program (inference).
  • A5 changes (the drive reads the whole track into its own buffer, as later drives do, general knowledge): the next block is already in the drive's buffer when the CPU asks, so adjacent placement is best; later BSD versions set the rotational delay to zero for such drives (general knowledge).
Design notes and rejected alternatives

The paper rejects ignoring the hardware (the old system's approach) and also stops short of reading contiguous blocks in one request, which would need every disk driver rewritten (M14). Eight positions is a resolution choice: fine enough at 2 ms for a 3600 rpm drive, cheap enough to count per cylinder.

Connections

Livelock: the "time to service an interrupt and schedule a new disk transfer" is the same per-interrupt CPU cost that the Livelock paper shows can dominate under load (inference). LFS: LFS writes whole segments in one transfer, which removes the per-block restart problem for writes.

M10 · Global policy for inodes: siblings together, directories spread out

TL;DR
ProblemCommands like ls -l read the inode of every file in a directory; with inodes scattered, that is one disk transfer per file.
MechanismPut a new file's inode in its directory's cylinder group. Put a new directory in a group with more free inodes than average and the fewest directories. Inside a group, take the next free inode.
Trade-offReading all inodes of a directory costs a small constant number of transfers, in exchange for directories being far from their parents.
Breaks whenA directory's group runs out of inodes, or a workload walks up and down a deep tree (parent and child are in different groups).
Key points
  • Two layers: "global policies that use file system wide summary information to make decisions regarding the placement of new inodes and data blocks", and below them "local allocation routines that use a locally optimal scheme to lay out data blocks."
  • The tension: global policies "must also try to spread unrelated data among different cylinder groups. If too much localization is attempted, the local cylinder group may run out of space".
  • "The layout policy tries to place all the inodes of files in a directory in the same cylinder group."
  • "A new directory is placed in a cylinder group that has a greater than average number of free inodes, and the smallest number of directories already in it. The intent of this policy is to allow the inode clustering policy to succeed most of the time."
  • "The allocation of inodes within a cylinder group is done using a next-free strategy. Although this allocates the inodes randomly within a cylinder group, all the inodes for a particular cylinder group can be read with 8 to 16 disk transfers. (At most, 16 disk transfers are required because a cylinder group may have no more than 2048 inodes.)" The old system "typically requires one disk transfer to fetch the inode for each file in a directory."
  • Measured (Section 4): listing a large directory of directories, inode disk accesses cut "by a factor of two"; a large directory of only files, "by a factor of eight". Good news for "spooling daemons that access many small files".
How it works, step by step
  1. mkdir: compute the average free inodes per group from the summary information; among groups above it, pick the one with the fewest directories; take its next free inode.
  2. creat in that directory: use the directory's group; take its next free inode. Siblings end up in one group's inode area.
  3. ls -l: the inodes of all files are somewhere in that group's inode area. Reading the whole area costs at most 16 transfers, regardless of how many files the directory has.
  4. Checking the 8 to 16 (this guide's arithmetic): 2048 inodes × 128 bytes (the 4.2BSD inode size, general knowledge) = 256 KB. That is 16 transfers of 16 KB or 32 of 8 KB. The paper does not state the inode size or transfer size, so read "8 to 16" as an order of magnitude: tens of transfers instead of one per file.
Assumptions it relies on
  • A1. Files in one directory are accessed together (stated: "Inodes of files in the same directory are frequently accessed together").
  • A2. A directory and its parent are not accessed together often enough to matter (implicit; the spreading rule separates them).
  • A3. Summary counts per group are available without reading each group (implicit; "file system wide summary information").
If an assumption changes
  • A1 changes (files accessed by type across many directories, for example all .h files in a source tree): the clustering does not help those accesses (inference).
  • A2 changes (a workload that walks a deep tree, like find or untarring a source tree): every subdirectory lands in a different group, so the walk seeks between groups; later BSD versions changed the directory policy to keep new directories closer to their parents for this reason (general knowledge).
  • A3 changes (summary counts are stale): the choice is merely worse, never wrong; any free inode is still a valid inode (inference).
Design notes and rejected alternatives

Placing a directory near its parent would cluster whole subtrees in one group and fill it, which is the "single huge cluster" the paper warns against. The policy gives up parent-child locality to protect sibling locality.

Connections

NFS: the NFS paper's attribute cache and directory name cache attack the same ls -l pattern from the client side, by not asking the server at all. LFS: LFS writes a new file's inode next to its data and its directory's updated blocks in the same segment, getting this locality for writes without a policy.

M11 · Global policy for data blocks: stay with the inode, then spill at 48 KB and every megabyte

TL;DR
ProblemA file's blocks should be together and near its inode, but a large file kept in one group would fill it and push everyone else's files out.
MechanismAllocate a file's blocks in its inode's group, at rotationally optimal places on the same cylinder; when the file passes 48 KB, and every megabyte after that, move to a group with more free blocks than average.
Trade-offNo group fills up, in exchange for one long seek per megabyte of a large file (and one at 48 KB).
Breaks whenFiles between 48 KB and about 1 MB are common and read whole: each pays a long seek for a small amount of data.
Key points
  • "the policy routines try to place all data blocks for a file in the same cylinder group, preferably at rotationally optimal positions in the same cylinder."
  • "large files will quickly use up available space in the cylinder group, forcing a spill over to other areas. Further, using all the space in a cylinder group causes future allocations for any file in the cylinder group to also spill to other areas. Ideally none of the cylinder groups should ever become completely full."
  • "The heuristic solution chosen is to redirect block allocation to a different cylinder group when a file exceeds 48 kilobytes, and at every megabyte thereafter. The newly chosen cylinder group is selected from those cylinder groups that have a greater than average number of free blocks left."
  • "Although big files tend to be spread out over the disk, a megabyte of data is typically accessible before a long seek must be performed, and the cost of one long seek per megabyte is small."
  • Footnote 8: 48 KB is where a file on a 4096-byte-block file system "first requires a single indirect block"; the megabyte points are chosen to redirect "when a file has used about 25 percent of the data blocks in a cylinder group."
How it works, step by step: cost of the spills
  1. A 3 MB file has about 4 groups' worth of runs: 48 KB, then about 1 MB, 1 MB and the rest. Reading it sequentially costs 3 long seeks extra.
  2. At 466 KB/s, 1 MB takes about 2.2 s; a long seek of, say, 30 ms (illustrative) adds about 1.4%: "small", as the paper says.
  3. A 100 KB file: 48 KB in the inode's group, 52 KB elsewhere. Transfer time about 0.21 s; one extra 30 ms seek adds about 14%. The spill rule costs medium-sized files most (inference).
  4. Why 25%: if a file can take at most about a quarter of a group before moving on, a group is never filled by one file, and three or four large files writing at once cannot fill it either (inference from footnote 8).
Assumptions it relies on
  • A1. Keeping every group partly free matters more than keeping each large file in one place (stated: "Ideally none of the cylinder groups should ever become completely full").
  • A2. A long seek per megabyte is negligible (stated).
  • A3. Groups hold about 4 MB, so 1 MB is about 25% (inference from footnote 8 and the inode cap in M5).
If an assumption changes
  • A1 changes (one huge file on an otherwise empty disk): the file still hops groups every megabyte, losing a little bandwidth for no benefit (inference).
  • A2 changes (much faster transfer rates, as on later disks): a megabyte takes far less time to read while a long seek does not shrink as fast, so the per-megabyte seek becomes a significant fraction; later systems raised the spill size (inference; general knowledge).
  • A3 changes (much larger groups): 1 MB becomes a small fraction of a group and the threshold could be raised; the paper ties the number to the group size, not to a fixed rule (inference).
Design notes and rejected alternatives

Keeping a whole large file in one group is rejected because it fills the group; scattering every block is the old system. The 48 KB point lines up with the first indirect block, which has to be read anyway before the next block's address is known (inference).

Connections

Superpages: reservations there are also sized to the object and released when unused, a similar balance between contiguity for one user and space for others (inference). LFS: LFS lays out a large file sequentially in the log as it is written, but a file updated in pieces over time ends up spread across segments, the case LFS reads poorly.

M12 · The local allocator: the requested block, or the closest one, in four widening circles

TL;DR
ProblemThe global policy asks for a specific block, which may already be taken; complete information to always ask for a free one is too expensive.
MechanismIf the requested block is free, use it. Otherwise: (1) the rotationally closest free block on the same cylinder; (2) any block in the same group; (3) another group chosen by quadratic hashing; (4) exhaustive search of all groups.
Trade-offGood placement in the common case with cheap bookkeeping, in exchange for heuristics that work only while free space is plentiful.
Breaks whenThe file system is nearly full: allocations reach levels 3 and 4 and are effectively random.
Key points
  • "The local allocation routines will always allocate the requested block if it is free, otherwise it allocates a free block of the requested size that is rotationally closest to the requested block."
  • "If the global layout policies had complete information, they could always request unused blocks and the allocation routines would be reduced to simple bookkeeping. However, maintaining complete information is costly; thus the implementation of the global layout policy uses heuristics that employ only partial information."
  • The four levels, verbatim in substance: "(1) Use the next available block rotationally closest to the requested block on the same cylinder." "(2) If there are no blocks available on the same cylinder, use a block within the same cylinder group." "(3) If that cylinder group is entirely full, quadratically hash the cylinder group number to choose another cylinder group to look for a free block." "(4) Finally if the hash fails, apply an exhaustive search to all cylinder groups."
  • "Quadratic hash is used because of its speed in finding unused slots in nearly full hash tables" (citing Knuth). "File systems that are parameterized to maintain at least 10 percent free space rarely use this strategy." When there is no free space, "almost any allocation is random; the most important characteristic of the strategy used under such conditions is that the strategy be fast."
How it works, step by step
  1. The global policy computes a preferred block: for the next block of a file, the block one rotational gap after the previous one (M9), in the same group (M11).
  2. Free? Check its bits in the group's bitmap. Usually yes when the file is being written sequentially into a fresh area.
  3. Level 1: scan rotational positions outward from the wanted one on this cylinder, using the per-position counts and layout tables (M9). Different surfaces of the cylinder count as "same cylinder" because "head switching time is zero".
  4. Level 2: any free block in the group, preferring nearby cylinders (general knowledge: a forward scan of the bitmap from the wanted place).
  5. Level 3: the group is full; probe group i + 1, then i + 3, i + 7, i + 15, ... (mod the number of groups) (general knowledge). A few probes find a group with space even when most are full.
  6. Level 4: every group in turn.
Assumptions it relies on
  • A1. Free space is plentiful (about 10%), so levels 1 and 2 almost always succeed (stated).
  • A2. Switching heads within a cylinder is free (stated).
  • A3. Partial information is good enough for the global policy (stated).
If an assumption changes
  • A1 changes (full disk): levels 3 and 4 dominate; placement is random and throughput halves (M8).
  • A2 changes (head switches cost time): level 1's "rotationally closest" choices on other surfaces arrive late, costing part of a revolution; the paper suggests folding head-switch time into the tables but has not tried it.
  • A3 changes (the global policy asks for blocks that are rarely free): the local allocator does most of the work and the result drifts away from the intended layout (inference).
Design notes and rejected alternatives

Linear probing over groups would pile up near full groups; quadratic hashing jumps away from clusters quickly, which is why it is the textbook choice for nearly full tables. The paper is explicit that in the full case speed of the search matters more than its quality.

Connections

Hints: the global policy's request is a hint: usually right, cheap to check, and the allocator falls back safely when it is wrong (inference using Lampson's terminology).

M14 · What still limits throughput, and three improvements the authors chose not to build

TL;DR
ProblemWith layout fixed, the CPU and the driver limit throughput: copies, allocation, and one block per disk request.
MechanismNone built. Three options are analyzed: remap pages instead of copying, chain contiguous blocks into one transfer, preallocate blocks for growing files.
Trade-offEach would help, but each needs an interface change or a rewrite of every disk driver, and the CPU already limits throughput.
Breaks whenCPUs get faster: then the never-adjacent layout's 50% ceiling becomes the limit.
Key points
  • "The performance of the new file system is currently limited by memory to memory copy operations required to move data from disk buffers in the system's address space to data buffers in the user's address space. These copy operations account for about 40 percent of the time spent performing an I/O operation."
  • Page remapping instead of copying was not implemented "because it would change the user interface to the file system in two major ways: user programs would be required to allocate buffers on page boundaries, and data would disappear from buffers after being written."
  • Block chaining: "Many disks used with UNIX systems contain either 32 or 48 512-byte sectors per track. Each track holds exactly two or three 8192-byte file system blocks, or four or six 4096-byte file system blocks." Without contiguous blocks, "the minimum spacing to the next allocatable block on any platter is between a sixth and a half a revolution", so "the best possible layout without contiguous blocks uses only half of the bandwidth of any given track."
  • "If each track contains an odd number of sectors, then it is possible to resolve the rotational delay to any number of sectors by finding a block that begins at the desired rotational position on another track."
  • Chaining not implemented: "it would require rewriting all the disk drivers in the system, and the current throughput rates are already limited by the speed of the available processors."
  • Preallocation (from DEMOS) not implemented "because block allocation currently accounts for less than 10 percent of the time spent in a write system call".
How it works, step by step: where "a sixth to a half" comes from
  1. 48 sectors, 4096-byte blocks: 6 blocks per track; skipping one block = 1/6 revolution.
  2. 32 sectors, 8192-byte blocks: 2 blocks per track; skipping one block = 1/2 revolution.
  3. Either way, if every other block is used, a track yields half its data per revolution: the 50% ceiling.
  4. Odd sector counts (say 33): blocks on different tracks start at different angles, so some track has a block starting just after the CPU is ready; the gap can be smaller than a whole block, and with zero-cost head switches the ceiling rises (inference from the paper's sentence).
  5. Chaining: one request for several contiguous blocks keeps the head reading with no gap; the CPU restart cost is paid once per chain instead of per block (inference).
Assumptions it relies on
  • A1. The UNIX read/write interface (copy semantics, arbitrary buffer alignment) must not change (stated).
  • A2. The CPU is the limit, so driver work would not pay off yet (stated).
  • A3. Allocation cost is small (stated: under 10% of a write call).
If an assumption changes
  • A1 changes (programs can use page-aligned buffers or map files): copying can be avoided; memory-mapped files later did this (general knowledge).
  • A2 changes (faster CPUs): the 50% ceiling of never-adjacent layouts binds; clustering contiguous blocks into large transfers became the next FFS improvement (general knowledge: McVoy and Kleiman's extent-like clustering for SunOS, 1991).
  • A3 changes (allocation becomes expensive, for example with many small writes): preallocation or batching becomes worthwhile; LFS batches everything (inference).
Design notes and rejected alternatives

All three rejected options trade compatibility or engineering effort for speed that the CPUs of 1984 could not yet use. The paper is explicit that its 47% is a CPU-and-driver limit, not a layout limit.

Connections

NFS: the NFS paper's performance work is also mostly removing copies (three to two per side) once the protocol was right. LFS: the LFS paper's premise is that CPUs got faster and the remaining problem is disk positioning for small writes.

M15 · Long file names: variable-length entries in 512-byte chunks

TL;DR
ProblemThe old directory format limited names (14 characters in Version 7 UNIX, general knowledge); any change requires rebuilding every file system, which the new layout already requires.
MechanismDirectories are made of 512-byte chunks holding variable-length entries: inode number, entry size, name length, then the name padded to 4 bytes. Names up to 255 characters. Free space is absorbed into a neighbor's entry size.
Trade-offNearly arbitrary names with no wasted fixed-size slots, in exchange for programs that read directories needing a new library interface.
Breaks whenA program parses directory files directly instead of using the access routines.
Key points
  • "File names can now be of nearly arbitrary length. Only programs that read directories are affected by this change." A set of directory access routines provides "a consistent interface to directories on both old and new systems."
  • "Directories are allocated in 512-byte units called chunks. This size is chosen so that each allocation can be transferred to disk in a single operation." "No directory entry is allowed to span multiple chunks."
  • Entry layout: three fixed-length fields (inode number, entry size, name length), then "a null terminated file name, padded to a 4-byte boundary. The maximum length of a file name in a directory is currently 255 characters."
  • "Available space in a directory is recorded by having one or more entries accumulate the free space in their entry size fields." "When an entry is deleted from a directory, its space is returned to a previous entry in the same directory chunk by increasing the size of the previous entry by the size of the deleted entry. If the first entry of a directory chunk is free, then the entry's inode number is set to zero to indicate that it is unallocated."
How it works, step by step
  1. Lookup: walk the chunk entry by entry, jumping by each entry's size; compare names of the stated length; skip entries with inode 0.
  2. Create "a.out": needs 8 + 8 = 16 bytes (5 + 1 = 6 → 8). Find an entry whose size exceeds its own needs by at least 16; shrink it to its own size and put the new entry in the slack. In the "after" chunk, ".." has 20 spare bytes, so the new entry goes right after it (inference from the stated rules).
  3. Delete: add the entry's size to the previous entry's size; nothing moves.
  4. Why chunks of 512: a chunk fits in one sector-sized disk write, so a crash cannot leave an entry half in one sector and half in another (inference from "transferred to disk in a single operation").
Assumptions it relies on
  • A1. Programs read directories through library routines, not raw (stated as the portability measure).
  • A2. Directories are small enough that a linear scan is acceptable (implicit; there is no index).
  • A3. A 512-byte write is atomic on the disk (implicit).
If an assumption changes
  • A1 changes: programs that read 16-byte entries directly break on the new format; this is why the routines were introduced first.
  • A2 changes (directories with tens of thousands of entries): every lookup and create scans linearly; later systems added hashed or tree-indexed directories (general knowledge).
  • A3 changes (larger sectors or non-atomic writes): the chunk size would have to match whatever the disk writes atomically (inference).
Design notes and rejected alternatives

Merging deleted space into the previous entry keeps every byte of the chunk accounted for ("Space allocated to a directory should always be completely accounted for by totaling up the sizes of its entries"), which makes the format easy to check after a crash.

Connections

NFS: NFS's readdir cookies point into exactly this structure; a cookie is effectively an offset to an entry (general knowledge). LFS: LFS keeps the same directory format and adds a directory operation log for crash consistency.

M16 · Advisory file locks: shared and exclusive, on open files

TL;DR
ProblemProcesses synchronized by creating "lock files": busy-waiting, stale locks after crashes, and no protection for the administrator, who can always create files.
MechanismA kernel lock on a whole open file, shared or exclusive, advisory (only callers that ask are blocked), optionally non-blocking, released when the process exits.
Trade-offSimple, crash-proof, usable by administrator programs, in exchange for no protection against programs that do not use the locks and no byte ranges.
Breaks whenOne program in a group of cooperating programs ignores the locks.
Key points
  • Lock-file drawbacks: "Processes consumed CPU time by looping over attempts to create locks. Locks left lying around because of system crashes had to be manually removed (normally in a system startup command script). Finally, processes running as system administrator are always permitted to create files, so were forced to use a different mechanism."
  • Granularity: byte-level locking exists elsewhere (Onyx), but "for the standard system applications, a mechanism that locks at the granularity of a file is sufficient."
  • Hard versus advisory: "A hard lock is always enforced when a program tries to access a file; an advisory lock is only applied when it is requested by a program." Because "programs with system administrator privilege are allowed override any protection scheme" and many programs that need locks run as the administrator, "we chose to implement advisory locks".
  • "Only one process may have an exclusive lock on a file while multiple shared locks may be present. Both shared and exclusive locks cannot be present on a file at the same time."
  • "Locks are applied or removed only on open files", so a process can take a shared lock, read, decide, and upgrade to exclusive without reopening. A request can be made to return an error instead of blocking. "Since locks exist only while the locking processes exist, lock files can never be left active after the processes exit or if the system crashes."
  • "Almost no deadlock detection is attempted": only that a second request for a lock of the same type the file already has will fail.

How it works, step by step: the print spooler example
  1. The first daemon starts, opens the spool directory, and requests an exclusive lock, non-blocking. It gets it and starts serving.
  2. A second daemon starts later, makes the same request, and gets an error immediately: an active daemon exists, so it exits.

  • A1. All programs that touch a shared file cooperate (stated as the condition for advisory locks to work).
  • A2. Whole-file locks are fine-grained enough (stated for standard applications).
  • A3. Locks are local to one machine's kernel (implicit).
If an assumption changes
  • A1 changes: a non-cooperating writer corrupts data regardless; only mandatory (hard) locks prevent that, with an override policy for the administrator that the authors wanted to avoid.
  • A2 changes (databases updating different records of one file): whole-file locks serialize everything; byte-range locks (later fcntl locks, general knowledge) are needed.
  • A3 changes (files shared across machines, as with NFS): the lock must live on the server and survive crashes of either side; the NFS paper leaves this to a separate stateful lock service.
Design notes and rejected alternatives

Hard locks were rejected because the administrator's override would make them either useless for system programs or inconsistent with UNIX's protection model. Deadlock detection was left out beyond the same-type check.

Connections

NFS: NFS explicitly has no locking in its protocol; this local mechanism is exactly what NFS clients lose. Leases: a lease is a time-limited lock that a crashed holder cannot keep forever; these locks are released by process exit, which a remote server cannot observe. Eraser and Mesa: those papers study locking discipline inside programs; these locks coordinate between programs.

M17 · Symbolic links: a file whose contents are a pathname

TL;DR
ProblemHard links name an inode, so they cannot cross file systems or machines.
MechanismA symbolic link is a file containing a pathname; when path resolution meets one, it substitutes the link's contents for that component and continues.
Trade-offLinks across file systems (and later machines), in exchange for links that can dangle and extra lookups during resolution.
Breaks whenThe target is moved or deleted, or a relative link is interpreted from a different place than intended.
Key points
  • "inodes do not reside in directories, but exist separately and are referenced by links. When all the links to an inode are removed, the inode is deallocated. This style of referencing an inode does not allow references across physical file systems, nor does it support intermachine linkage."
  • "A symbolic link is implemented as a file that contains a pathname. When the system encounters a symbolic link while interpreting a component of a pathname, the contents of the symbolic link is prepended to the rest of the pathname, and this name is interpreted to yield the resulting pathname."
  • "If a symbolic link contains an absolute pathname, the absolute pathname is used, otherwise the contents of the symbolic link is evaluated relative to the location of the link in the file hierarchy."
  • "Three new system calls provide the ability to detect, read, and write symbolic links; seven system utilities required changes to use these calls." (General knowledge: lstat, readlink, symlink.)
  • Future: with remote file systems, "it will be possible to create symbolic links that span machines."
How it works, step by step: resolving /usr/src/sys/h/param.h
  1. /usr/src/sys is a symbolic link containing ../sys-4.2 (illustrative).
  2. Resolution reaches the component sys in /usr/src, finds a link, and prepends its contents to the rest: ../sys-4.2/h/param.h.
  3. The contents are relative, so they are interpreted from the link's directory, /usr/src: /usr/src/../sys-4.2/h/param.h = /usr/sys-4.2/h/param.h.
  4. If the link had contained /u2/sys-4.2 (absolute), resolution would restart at the root, possibly on another file system mounted at /u2.
Assumptions it relies on
  • A1. Most programs should not notice links (stated: "Normally programs do not want to be aware").
  • A2. Links are resolved on the machine doing the lookup (implicit).
If an assumption changes
  • A1 changes (backup, archiving, ls): these must see the link itself, hence the three new calls and seven changed utilities.
  • A2 changes (the link lives on an NFS server): the client interprets it in the client's namespace; an absolute link can point somewhere different on each client. The NFS paper's server stores the string uninterpreted for this reason.
Design notes and rejected alternatives

Following Multics, the link is a name, not a reference, so it needs no reference counting and can point anywhere, including at nothing. Loops are possible; general knowledge: the kernel limits the number of links followed in one lookup.

Connections

NFS: NFS's symlink and readlink procedures carry exactly these strings; the NFS paper's /private scheme for diskless clients is built from symbolic links.

M18 · Atomic rename

TL;DR
ProblemReplacing a file safely (write a temporary, then rename it over the original) took three system calls; a crash in between could leave the target missing.
MechanismA rename system call that "guarantees the existence of the target name", for files and directories, with checks that directory renames do not create loops.
Trade-offSafe replacement for every program, in exchange for kernel complexity: tree checks on directory renames.
Breaks whenA directory is moved into its own subtree, which the check forbids.
Key points
  • "Programs that create a new version of an existing file typically create the new version as a temporary file and then rename the temporary file with the name of the target file. In the old UNIX file system renaming required three calls to the system. If a program were interrupted or the system crashed between these calls, the target file could be left with only its temporary name."
  • "The rename call does the rename operation in a fashion that guarantees the existence of the target name."
  • For directories, "the system must do special validation checks to insure that the directory tree structure is not corrupted by the creation of loops or inaccessible directories. Such corruption would occur if a parent directory were moved into one of its descendants."
How it works, step by step
  1. Old way (general knowledge of the three calls): unlink("passwd"), link("ptmp", "passwd"), unlink("ptmp"). A crash after the first call leaves no passwd at all; only ptmp holds the data.
  2. New way: rename("ptmp", "passwd"). At every moment, the name passwd refers to either the old file or the new one.
  3. Directory check: rename("/a", "/a/b/c") would make a its own descendant; the kernel walks up from the target's parent toward the root and refuses if it meets /a.
Assumptions it relies on
  • A1. The kernel can order its on-disk updates so a crash never loses the target name (implicit; general knowledge: done with ordered synchronous writes, repaired by fsck).
If an assumption changes
  • A1 changes (writes reordered by the disk or cached): the "atomic" guarantee depends on metadata write ordering; without it a crash can still show both names or neither (inference).
Connections

NFS: NFS's rename procedure is not idempotent: a retry after a lost reply finds the old name gone. LFS: the LFS directory operation log exists to make operations like rename consistent after a crash.

M19 · Quotas: per-user limits on inodes and blocks

TL;DR
Problem"any single user can allocate all the available space in the file system."
MechanismPer user, per file system, limits on inodes and on disk blocks, each with a soft limit (warning) and a hard limit (enforced).
Trade-offFair sharing without stopping work in progress, in exchange for bookkeeping on every allocation.
Breaks whenA user stays over the soft limit for too many log-in sessions: the soft limit is then enforced as the hard limit.
Key points
  • "The quota mechanism sets limits on both the number of inodes and the number of disk blocks that a user may allocate. A separate quota can be set for each user on each file system."
  • "When a program exceeds a soft limit, a warning is printed on the users terminal; the offending program is not terminated unless it exceeds its hard limit. The idea is that users should stay below their soft limit between log-in sessions, but they may use more resources while they are actively working."
  • "users are warned when logging in if they are over any of their soft limits. If users fail to correct the problem for too many log-in sessions, they are eventually reprimanded by having their soft limit enforced as their hard limit."
  • Acknowledgment: Robert Elz added disk quotas "in a rational and efficient manner".
How it works, step by step
  1. Alice has soft 10 MB, hard 12 MB. A compile pushes her to 11 MB: warning, work continues.
  2. She logs out still at 11 MB. At each of her next log-ins she is warned.
  3. After "too many" log-ins over the soft limit (the number is not given in the paper), her soft limit acts as the hard limit: at 10 MB further allocation fails until she deletes files.
Assumptions it relies on
  • A1. Users work in log-in sessions and can clean up between them (stated).
  • A2. Counting both inodes and blocks covers the ways a user can exhaust a file system (implicit; inodes are a fixed resource, M5).
If an assumption changes
  • A1 changes (long-running daemons acting for users): there is no log-in to trigger warnings; the soft limit is only a delayed hard limit (inference).
  • A2 changes (one user creates millions of empty files): without the inode quota they could exhaust a group's static inodes while using almost no blocks; the inode limit covers exactly this.
Connections

ESX: ESX's memory shares and limits are the same idea for physical memory: guaranteed minimums and caps instead of a free-for-all (inference).

L · Stated limitations and future work

What the paper itself says is unfinished
  • Head switching time is assumed zero; building it into the rotational layout tables "has not yet been tried."
  • The memory-to-memory copy (about 40% of I/O time) remains; page remapping was not done because it would change the read/write interface.
  • Block chaining in the disk drivers, which would lift the half-bandwidth limit, was not done because every driver would need rewriting and the CPU is already the limit.
  • Preallocation for growing files (DEMOS) was not done because allocation is under 10% of a write.
  • Remote file systems reachable by pathname, and symbolic links spanning machines, are future work ("In future Berkeley software distributions").
  • Byte-range locking and deadlock detection are left out deliberately.
What the evaluation does not cover (this guide's list)
  • Small-file creation and deletion throughput, and the synchronous metadata writes they involve (the LFS paper's main criticism, S).
  • Crash recovery cost (fsck time) for the new layout.
  • Aging beyond about a month of production use; the claim that rates "do not appear to change over time" is not plotted.
  • More than one machine type and one disk model; the parameterization is argued for, not measured across hardware.
  • The "about half" rate when full comes from "synthetic work loads" with no table.

Follow the numbers

Worked examples

Seven calculations from the paper's own numbers. Where a hardware detail is not in the paper, it is labeled.

① Where 983 KB/s comes from, and why 466 is nearly the best possible

Paper: the upper bound is "the number of bytes on a track by the number of revolutions of the disk per second"; 983 KB/s for the test disk; typical disks have 32 or 48 sectors of 512 bytes per track.

  1. Track: 32 × 512 = 16,384 bytes. Speed: 3600 rpm = 60 revolutions per second. Bound: 16,384 × 60 = 983,040 bytes/s = 983 KB/s in the paper's units. (The 32-sector track is this guide's reconstruction; it matches exactly.)
  2. Never-adjacent layout: with 4096-byte blocks (4 per track) or 8192-byte blocks (2 per track) and a gap of one block, the head reads every other block: half the track per revolution = 491 KB/s.
  3. Measured: 466 KB/s for both MASSBUS read rows = 466 / 491 = 95% of that ceiling, 47% of the raw bound.
🍯
The layout policies are nearly perfect for this disk; the remaining factor of two needs contiguous blocks read in one request, which is a driver change (M14).

② The largest file: why 4096 bytes is the minimum block size

Paper: "files as large as 232 bytes with only two levels of indirection"; footnote 3: old files limited to "less than about one gigabyte". Address size of 4 bytes is general knowledge.

  1. New, 4096-byte blocks: 4096 / 4 = 1024 addresses per indirect block. Double indirect: 1024 × 1024 × 4096 = 232 bytes = 4 GB.
  2. 2048-byte blocks: 512 addresses; double indirect 512 × 512 × 2048 = 229 = 512 MB. Not enough, so 4096 is the smallest power of two that works.
  3. Original, 512-byte blocks: 128 addresses; even triple indirect reaches only 1283 × 512 = 230 = 1 GB, which explains footnote 3.
💡
An 8× bigger block holds 8× more addresses per indirect block, so with one fewer level of indirection it still reaches 4× further (232 versus 230), and each level saved is one less block to read before reaching data.

③ What fragments save on a directory full of small files

100 files of 1,500 bytes each (illustrative). Compare 4096-byte blocks without fragments, 4096/1024, and 4096/512.

  1. Data: 100 × 1,500 = 150,000 bytes.
  2. 4096, no fragments: each file takes one block: 409,600 bytes, waste 259,600 = 173% of the data.
  3. 4096/1024: ⌈1500 / 1024⌉ = 2 fragments = 2,048 bytes each: 204,800, waste 54,800 = 37%.
  4. 4096/512: ⌈1500 / 512⌉ = 3 fragments = 1,536 each: 153,600, waste 3,600 = 2.4%.
  5. The paper's own example: 11,000 bytes on 4096/1024 = 2 blocks + 3 fragments = 11,264 bytes, 264 wasted.
🍯
Waste per file is at most one fragment, not one block; that is the whole trick of Table I's comparison.

④ When does moving a disk to a slower CPU hurt?

Paper: a file system laid out for a 2 ms processor, moved to a 4 ms processor, drops "precipitously". Rotation 3600 rpm (16.67 ms per turn); 4096-byte blocks.

  1. 32-sector track (4 blocks per track, 4.17 ms each): for 2 ms the gap is one block = 4.17 ms. On the 4 ms CPU, 4.17 ≥ 4, so the next block still arrives in time. No drop.
  2. 48-sector track (6 blocks per track, 2.78 ms each): for 2 ms the gap is one block = 2.78 ms, giving 3 blocks per revolution = 12 KB / 16.67 ms ≈ 737 KB/s (half of the 1,475 KB/s bound).
  3. Moved to 4 ms: 2.78 < 4, so each next block has just passed and comes back a revolution later: from the start of one block to the start of the next is 2.78 (read) + 2.78 (gap) + 16.67 (missed turn) ≈ 22.2 ms, so 4 KB / 22.2 ms ≈ 184 KB/s, a 4× drop.
  4. Reconfigured: gap of two blocks = 5.56 ms ≥ 4: 2 blocks per revolution ≈ 491 KB/s for files written after the change. Files written before still have the one-block gap and stay at about 184 KB/s until rewritten.
💡
Whether the paper's example "drops precipitously" depends on how much slack the geometry leaves; with finer blocks per track there is less slack (this guide's arithmetic).

⑤ How big is a cylinder group, from the paper's own numbers?

Paper: one inode per 2048 bytes by default; at most 2048 inodes per group; the megabyte spill is meant to trigger at about 25% of a group's data blocks.

  1. Inode cap: 2048 inodes × 2048 bytes per inode = 4 MB of space per group, at most, at the default density.
  2. Spill rule: 1 MB = 25% of 4 MB. The two independent statements agree on groups of about 4 MB.
  3. 48 KB: 12 direct blocks × 4 KB (12 is 4.2BSD's direct count, general knowledge) = 48 KB, the point where the first indirect block is needed, per footnote 8.
  4. How many groups: a 330 MB disk in one file system would have about 330 / 4 ≈ 80 groups (inference).

⑥ Which numbers make "up to ten times faster"?

Table II. The old file system was measured only on UNIBUS.

  1. Same controller (UNIBUS), reads: 233 / 29 ≈ 8.0×; writes: 215 / 48 ≈ 4.5×.
  2. Across controllers: new MASSBUS read / old UNIBUS read = 466 / 29 ≈ 16×; new MASSBUS write / old write = 466 / 48 ≈ 9.7×.
  3. So "up to ten times" matches the write comparison across controllers; the same-controller read gain is about 8×.
  4. CPU per KB/s: old reads 11 / 29 = 0.38% per KB/s; new 8192 MASSBUS reads 54 / 466 = 0.12%: about a third of the CPU per byte.
🍯
The new system needs less CPU per byte but moves so many more bytes that the CPU becomes the limit, exactly the paper's conclusion.

⑦ The cost of growing a file one small write at a time

4096/1024 file system, the paper's three cases applied literally (no in-place extension).

  1. 1 KB writes: tail grows 1 → 2 → 3 → 4 fragments; each step moves the old tail: 1 + 2 + 3 = 6 KB copied per 4 KB block.
  2. 512-byte writes: the 1 KB fragment absorbs a second 512-byte write (case 1), so copies happen only when the tail crosses a fragment boundary: again 1 + 2 + 3 = 6 KB per block.
  3. 4096-byte writes: each write fills a whole block (case 2); no copies.
💡
The copying depends on how many fragment boundaries the tail crosses, not on how small the writes are; buffering to the block size (the "optimal size" the interface now reports) removes it.
Test yourself

Practice problems

Try each before opening the answer. Each answer ends with the misconception it checks.

Problem 1 · easy
In the paper's Figure 1 (bits XXXX XXOO OOXX OOOO), a file needs a whole free block. Fragments 6, 7, 8 and 9 are free. Can it use them? Which block can it use?
Show answer
No. Fragments 6 and 7 belong to block 1 and fragments 8 and 9 to block 2; a block is four aligned fragments of the same block. Only block 3 (fragments 12 to 15) is a free block.Misconception: that any four adjacent free fragments make a block. "Fragments of adjoining blocks cannot be used as a full block, even if they are large enough."
Problem 2 · easy
How much space does a 5,000-byte file take on a 4096/512 file system, and on a 4096/1024 file system?
Show answer
5,000 = 4,096 + 904. On 4096/512: one block plus ⌈904/512⌉ = 2 fragments = 4,096 + 1,024 = 5,120 bytes. On 4096/1024: one block plus 1 fragment = 5,120 bytes as well (904 fits in one 1024-byte fragment). With 4096-byte blocks and no fragments it would be 8,192.Misconception: that smaller fragments always save space. They only save when the tail would otherwise round up past a smaller fragment boundary; here both round to 5,120.
Problem 3 · easy
Why did the old 1024-byte file system run at 175 KB/s when new but about 30 KB/s after a few weeks, with the same hardware and the same files?
Show answer
Free blocks were kept on a list, initially in good order. Deletions pushed freed blocks back in arbitrary order, so after weeks the list was random, and each new file's consecutive blocks landed anywhere on the disk. Every block then needed a seek and a rotational wait. Only dumping and restoring the file system restored the order.Misconception: that the disk or the files got slower. Only the placement of new files changed, because the allocator had no notion of "near".
Problem 4 · medium
Four cylinder groups have 800, 1600, 1500 and 1300 free inodes and 3, 6, 2 and 1 directories. Where does mkdir put a new directory? Where do files created in it go?
Show answer
Average free inodes = 5200 / 4 = 1300. "Greater than average" means groups 1 (1600) and 2 (1500); group 3 has exactly 1300, not greater. Of groups 1 and 2, group 2 has fewer directories (2), so the directory's inode goes in group 2. Files created in it get inodes in group 2 too, and their data blocks are allocated in group 2 until a file passes 48 KB.Misconception: picking group 3 because it has the fewest directories. The fewest-directories rule applies only among groups with above-average free inodes.
Problem 5 · medium
A program appends 512 bytes per write() to a new file on a 4096/1024 file system. Using the paper's three cases literally, how many bytes are copied while the file grows from 0 to 4096 bytes? Would 1024-byte writes copy more?
Show answer
Writes 2, 4, 6 and 8 fit in the current fragments (case 1). Writes 3, 5 and 7 cross a fragment boundary and move the tail: 1 KB, then 2 KB, then 3 KB into a full block. Total 6 KB. With 1024-byte writes the copies are the same 1 + 2 + 3 = 6 KB. With 4096-byte writes, none.Misconception: smaller writes always cost more copying. The copying is per fragment boundary crossed, which is why reporting the block size to the Standard I/O library fixes it.
Problem 6 · medium
The old file system writes at 48 KB/s but reads at 29 KB/s. The new 4096/1024 file system on MASSBUS reads at 466 but writes at 323. Explain both asymmetries.
Show answer
Old: writes are asynchronous, so many pending writes sit in the buffer cache and the disk queue sorts them to reduce seeking; reads are synchronous, so the scattered blocks are requested one at a time in file order with full seeks. New: layout is already good, so reordering gains nothing; writes cost more CPU because each block must be allocated, and with 4096-byte blocks there are twice as many allocations per byte as with 8192, so the CPU (94%) limits writes.Misconception: that writes are inherently faster or slower. The old asymmetry comes from queue reordering; the new one from CPU cost of allocation.
Problem 7 · medium
A file system is set up for a 2 ms CPU restart time and then moved to a host that needs 4 ms. The administrator changes the parameter right away. Which files are fast afterwards?
Show answer
Only files written after the change. The parameter controls where new blocks are allocated ("all further allocation"); existing files keep the spacing they were written with. If the old gap is shorter than 4 ms on this disk's geometry, reading an old file loses about a revolution per block until the file is copied.Misconception: that changing the parameter re-lays out the disk. Nothing moves; the parameter only guides future allocation.
Problem 8 · medium
A file system with a 10% reserve is 100% full because the administrator kept writing. Users delete files until it is 80% full. Is performance fully restored?
Show answer
For new files, yes: the allocator can again find free blocks near where it wants them. Files written while the disk was nearly full keep their scattered layout and stay slow: "Access rates for files created during periods of little free space may be restored by moving their data once enough space is available."Misconception: that freeing space repairs existing layout. Layout is decided at allocation time and never revisited.
Problem 9 · hard
A disk has 48 sectors per track and spins at 3600 rpm. The file system uses 8192-byte blocks and a one-block rotational gap. What is the best sequential read rate, as KB/s and as a percentage of the disk's bandwidth?
Show answer
Track = 48 × 512 = 24 KB = 3 blocks of 8 KB, each passing in 5.56 ms. Bandwidth bound = 24,576 × 60 ≈ 1,475 KB/s. With a one-block gap the head reads slot 0, skips 1, reads 2, skips 0, reads 1, ...: one block every two slots, so 1.5 blocks per revolution = 12 KB per 16.67 ms ≈ 737 KB/s = 50%. Same ceiling as the paper's half-bandwidth statement.Misconception: that an odd number of blocks per track lets the layout beat 50%. It is an odd number of sectors that would help, by letting blocks on different tracks start at different angles (M14).
Problem 10 · hard
Table I says the 4096-byte organization wastes 45.6%. If 1128.3 MB of disk holds 775.2 MB of user data, what fraction of the disk is not user data? Which definition does the table use?
Show answer
(1128.3 − 775.2) / 1128.3 = 31.3% of the disk is not user data. The table's 45.6% is (1128.3 − 775.2) / 775.2, overhead relative to the data. Every row follows the second formula, although the text defines waste as "the percentage of space on the disk not containing user data".Misconception: taking a percentage at face value without checking its denominator; the comparison between rows is unaffected, but the absolute "nearly half the disk" reading is wrong.
Problem 11 · hard
An administrator builds a file system with one inode per 8192 bytes instead of 2048, keeping the 2048-inode cap per group. How large can a group now be, and what happens to the "every megabyte" spill rule's intent?
Show answer
2048 inodes × 8192 bytes = 16 MB per group. The rule was chosen to redirect "when a file has used about 25 percent of the data blocks in a cylinder group"; 1 MB is now about 6% of a group, so large files hop groups four times more often than intended relative to group size. Keeping the intent would mean spilling about every 4 MB (inference).Misconception: that 1 MB is a fundamental constant. Problem 12 · medium
/usr/local/bin/cc is a symbolic link containing ../../bin/cc. What file does opening it reach? What if the link contained /bin/cc and the file system is NFS-mounted on a client whose /bin is different?
Show answer
Relative contents are interpreted from the link's directory, /usr/local/bin: /usr/local/bin/../../bin/cc = /usr/bin/cc. Connecting outward

What FFS teaches a memory and storage systems person

These connections are this guide's framing, not claims the authors make.

The OS used the device's physical timing, and later lost the ability to

FFS is a clear case of an operating system placing data using a device's real characteristics: blocks per track, rotation time, the CPU's restart cost. Within a decade drives hid that information behind a flat block address space with remapped sectors and zoned tracks, and the rotational parameters became fiction. The same tension recurs with flash translation layers and memory controllers: abstraction makes devices interchangeable, exposure lets the OS exploit asymmetries. FFS shows both the payoff (7 to 8× on the same controller) and the cost (a layout tied to one CPU, M9).

Measure aged systems, not fresh ones

The old file system lost most of its speed in weeks (175 → 30 KB/s), invisible in a benchmark on a freshly built disk. The authors measured only file systems with a month of production use. Any allocator with a free pool (disk blocks, physical pages, flash erase blocks) can degrade this way, and fragmentation only shows up after churn.

A free space reserve is over-provisioning

Keeping 10% free so placement policies always have nearby room is the same idea as an SSD's hidden spare area for garbage collection, or headroom in a memory allocator that needs contiguous runs. In each case performance falls sharply as utilization approaches 100%, and the remedy is to forbid the last few percent rather than to make the full case fast.

Two granularities: a big unit for speed, a small unit for space

Blocks plus fragments mirror huge pages plus base pages, or sectored cache lines: transfer and map in large units, allocate the leftovers in small ones. The constraint that fragments must sit inside one aligned block is the same alignment constraint that superpages and buddy allocators impose, and it creates the same kind of external fragmentation (free pieces that cannot be combined).

Fix the device bottleneck and the CPU appears

Once layout was right, copying between kernel and user buffers took about 40% of I/O time and allocation saturated the CPU on writes. The paper names zero-copy remapping and chained transfers and declines both for interface and driver reasons. Every storage stack since has followed this pattern: after placement, the next costs are copies, interrupts and per-request overhead.

Put metadata next to the data it describes

Moving inodes from one region at the front into every cylinder group cut directory-listing inode accesses by 2 to 8×. Co-locating metadata with data is a recurring design choice: per-region allocation bitmaps, per-bank or per-channel tables in memory controllers, and inline versus separate placement of tags and ECC. The trade-off is the same: locality for the common access, and a fixed split decided in advance (FFS's static inode count per group).

Questions with real answers

Each one is a tricky case the paper does not spell out, but it has a definite answer you can work through from the paper's own numbers. The quoted block is how to ask it in class. Try your own answer before opening the worked one.

C1 · Table I's 45.6%: 45.6% of what?

Table I is the paper's main argument for fragments: with 4096-byte blocks, 45.6% "waste", which the text calls intolerable, and it defines waste as "the percentage of space on the disk not containing user data." But 1128.3 MB of disk holds 775.2 MB of data. If I compute the paper's definition I don't get 45.6%. Which denominator does the table actually use, and does it change the conclusion?

AnswerWork it out first, then open▾

The table uses the user data as the denominator: (1128.3 − 775.2) / 775.2 = 45.6%, and every row checks the same way (4.2, 6.9, 11.8, 22.4). By the text's own definition, waste as a share of the disk, the rows are 4.0, 6.5, 10.5, 18.3 and 31.3%.

The conclusion survives, because the ranking and the roughly doubling pattern are the same under either denominator, and fragments still bring the 4096 organization down to the 1024 row. But "nearly half the disk wasted" is an overstatement: it is about a third of the disk, or 46% extra space relative to the data.

Where the answer comes from: Recomputed from Table I's own numbers and the sentence that defines waste (Section 3.1).

C2 · Which numbers give "up to ten times faster"?

The abstract says file access is "up to ten times faster" than the traditional file system. In Table II the old file system was only measured on the UNIBUS controller, while the best new results are on MASSBUS, and the paper says the controller was the only difference between those runs. If I compare like with like, how much faster is the new layout, and where does ten come from?

AnswerWork it out first, then open▾

Same controller (UNIBUS): reads go from 29 to 221 to 233 KB/s, about 8×; writes from 48 to 142 to 215, about 3 to 4.5×. Ten comes from comparing the new 8192/1024 file system's MASSBUS write (466) with the old UNIBUS write (48): 9.7×. The MASSBUS read comparison would be 16×.

So the layout change alone is worth about 8× for reads on identical hardware, and the remaining factor of two in the headline comes from the faster controller, which the old file system was never measured on.

Where the answer comes from: Ratios computed from Table II; the observation that the old system has no MASSBUS row is from the table itself.

C3 · Why do the 4096- and 8192-byte file systems read at exactly the same 466 KB/s?

On MASSBUS, the 4096/1024 and 8192/1024 file systems both read at 466 KB/s, 47% of the disk's bandwidth, even though the 8192 one uses much less CPU (54% versus 73%). If neither the CPU nor the block size is limiting, what is? Is 47% close to the best this design can do?

AnswerWork it out first, then open▾

The layout is. Without block chaining, consecutive blocks of a file are never adjacent, so at most every other block on a track is read in one revolution: half the bandwidth, 491 KB/s for this 983 KB/s disk. With 4 blocks per track (4096) or 2 (8192), skipping one block gives the same half either way.

466 is 95% of that 491 ceiling. The paper says this directly in Section 4 ("the best possible layout without contiguous blocks uses only half of the bandwidth"), but never connects it to Table II's identical numbers.

Where the answer comes from: Derived from Table II, the 983 KB/s bound and the half-bandwidth statement in Section 4.

C4 · Does the 2 ms → 4 ms move always drop throughput?

The paper's example: a file system laid out for a processor that needs 2 ms to start the next transfer, moved to one that needs 4 ms, "will drop precipitously because of lost disk revolutions on nearly every block." On the test disk's geometry (32 sectors per track, 4096-byte blocks) a one-block gap is 4.17 ms. Does the drop actually happen there? On what kind of disk does it, and how big is it?

AnswerWork it out first, then open▾

Not on that geometry: the gap is a whole block, 4.17 ms, which already covers 4 ms, so the next block still arrives in time. The drop needs a geometry where the gap is shorter than the new restart time, for example 48 sectors per track with 4096-byte blocks: 2.78 ms per block.

There, the 2 ms layout gives 3 blocks per revolution (≈ 737 KB/s); on the 4 ms CPU every block misses and costs an extra revolution: ≈ 22.2 ms per block ≈ 184 KB/s, a 4× drop. Changing the parameter fixes only files written afterwards; existing files keep the short gap until copied.

Where the answer comes from: Derived from Section 3.2's rule (gap = blocks to skip so the next block arrives after the restart time) and the sector counts in Section 4.

C5 · How big is a cylinder group, and does it match the spill rule?

The paper never states the size of a cylinder group. It gives a default of one inode per 2048 bytes, a cap of 2048 inodes per group, and a footnote saying the 1 MB spill points were chosen to redirect a file when it has used "about 25 percent of the data blocks in a cylinder group." Can I get the group size from these, and are they consistent?

AnswerWork it out first, then open▾

Yes. 2048 inodes × 2048 bytes = 4 MB of space per group at most at the default density. The footnote's 1 MB = 25% also implies about 4 MB. The two independent statements agree.

A consequence the paper does not discuss: the spill rule is tied to the defaults. A file system built with fewer inodes per byte has larger groups, and 1 MB becomes a much smaller fraction of a group than intended.

Where the answer comes from: Arithmetic on Sections 3 and 3.3 and footnote 8.

C6 · Do the 8 to 16 transfers for a group's inodes add up?

The paper says all inodes of a cylinder group "can be read with 8 to 16 disk transfers. (At most, 16 disk transfers are required because a cylinder group may have no more than 2048 inodes.)" How big must each transfer be for that to hold, and is that consistent with the file system's block size?

AnswerWork it out first, then open▾

With 4.2BSD's 128-byte inodes (general knowledge), 2048 inodes are 256 KB. Sixteen transfers means 16 KB per transfer; with 8192-byte blocks it would be 32 transfers, and with 4096-byte blocks 64.

The bound fits if transfers are 16 KB or the inodes were 64 bytes (the Version 7 size). Either way the point stands: a constant, small number of reads for any directory, instead of one per file. But the specific 16 does not follow from the stated block sizes.

Where the answer comes from: The inode size is general knowledge; the rest is arithmetic on Section 3.3.

C7 · Does a 100 KB file end in a fragment?

The paper says a file is "zero or more 4096-byte blocks of data, and possibly a single fragmented block." A 100,000-byte file on a 4096/1024 file system is 24 full blocks plus 1,696 bytes. Does its last block become two fragments, or a full block?

AnswerWork it out first, then open▾

A full block. In 4.2BSD fragments are used only when the file's last block is one of the 12 direct blocks, that is for files under 48 KB; a file that already needs an indirect block ends in a whole block (general knowledge from the 4.2BSD code). So the 100 KB file wastes 4096 − 1696 = 2400 bytes rather than 352.

Why it is reasonable: large files are a minority of files, the waste is at most one block per large file, and avoiding fragment copies for big growing files saves CPU. The paper's sentence is true but does not say this restriction.

Where the answer comes from: General knowledge of the 4.2BSD implementation; the paper's own text is silent on it.

Glossary, results, and provenance

Every term in one place, then where the numbers came from and what this guide found inconsistent in the paper.

Core terms
Cylinder groupA run of consecutive cylinders that the file system manages as one unit, with its own superblock copy, inodes, fragment bitmap and summary counts.
Block (file system block)The unit in which the file system allocates and transfers file data: a power of two of at least 4096 bytes in the new system, fixed when the file system is created.
FragmentAn addressable 1/2, 1/4 or 1/8 of a block, at least one sector, used to hold the last partial block of a small file.
Fragment bitmap (block map)One bit per fragment in a cylinder group, recording which fragments are in use; a block is free when all of its aligned fragments are free.
SuperblockThe record describing a whole file system (sizes, block and fragment size, layout parameters). The primary copy is at a fixed place; every cylinder group holds a backup copy.
InodeThe fixed-size on-disk record for one file: owner, mode, times, size and block addresses. The new system allocates a fixed number per cylinder group.
Indirect blockA block filled with block addresses instead of data; single, double and triple indirect blocks extend a file past its inode's direct addresses.
Free listThe old file system's linked list of free blocks, allocated from the head; it becomes random as files are created and deleted.
Free space reserveThe minimum percentage of free blocks (10% in the measurements) below which only the system administrator can allocate; changeable while mounted.
Rotationally optimal blockThe free block that reaches the head just as the CPU can start the next transfer after the previous block.
Rotational positionOne of eight equal slices of a revolution (about 2 ms each at 3600 rpm) used to classify where each block starts on its track.
Rotational layout tableA superblock table, indexed by rotational position, listing the blocks of a cylinder that start at that position, so the allocator can check only those bits of the bitmap.
Global policyThe allocation routines that choose a cylinder group and a preferred block using file-system-wide summary information.
Local allocatorThe routines that return the requested block if free, or else the nearest free block by a four-level search: same cylinder, same group, quadratic hash over groups, exhaustive search.
Quadratic hashingA probing sequence that tries slots at growing distances from the starting point, which finds an empty slot quickly even in a nearly full table.
Supporting terms
SectorThe smallest unit a disk reads or writes, 512 bytes on these drives.
TrackOne ring of sectors on one surface, read in one revolution without moving the arm.
CylinderThe tracks at one arm position on all surfaces; readable by switching heads with no seek.
SeekMovement of the arm to another cylinder, taking milliseconds to tens of milliseconds.
Rotational latencyTime spent waiting for the wanted sector to rotate under the head, up to one revolution.
Head switchChanging which surface's head is active within a cylinder; the paper assumes it takes no time.
Disk bandwidth (paper's definition)Bytes per track times revolutions per second: the most the disk can transfer with no positioning delays.
I/O channelA separate processor that runs a sequence of transfers with no CPU involvement between them.
UNIBUS, MASSBUSTwo DEC buses for attaching peripherals and disk controllers to VAX and PDP-11 computers; the paper's two test setups differ only in which one the disk controller used.
Buffer cacheKernel memory holding recently used disk blocks; writes normally go to it and reach the disk later, reads that miss wait for the disk.
Optimal I/O sizeThe read or write size the file system reports for an open file, equal to its block size, so libraries can transfer whole blocks.
Directory chunkA 512-byte unit of a directory, holding whole variable-length entries; no entry spans two chunks.
Directory entryA record mapping one name to an inode: inode number, entry size, name length, then the name padded to 4 bytes.
Hard linkA directory entry naming an inode directly; it cannot cross file systems.
Symbolic linkA file whose contents are a pathname, substituted during path resolution; absolute contents start at the root, relative contents at the link's directory.
Advisory lockA kernel-recorded lock that blocks only other callers that request a conflicting lock; reads and writes are not checked.
Hard (mandatory) lockA lock enforced on every access to the file, which requires a kernel override policy for the administrator.
Shared / exclusive lockAny number of shared locks may coexist; an exclusive lock excludes all others.
Quota (soft and hard limit)Per-user, per-file-system limits on inodes and blocks; exceeding the soft limit warns, the hard limit refuses allocation.
Dump and restoreCopying a whole file system to tape and back, which rebuilds it from scratch; the only way to restore an aged old file system's speed.
fsckThe UNIX file system checker, which scans all metadata after a crash and repairs inconsistencies.
VAX-11/750The DEC minicomputer on which all of Table II was measured.
