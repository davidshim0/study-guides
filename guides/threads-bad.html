Reaching for events before reaching for threads

Shared state plus preemption makes a program hard to reason about. This is the plain-English case for why almost nobody should reach for threads first, and for the one criterion, true CPU concurrency, that justifies it, covering both scientific computing and high-end servers.

📖 Quick glossary

ThreadAn independent execution stream that shares memory with its siblings and is scheduled preemptively.
PreemptionThe scheduler can suspend a thread between any two instructions; the thread doesn't choose when.
Lock / mutexA gate letting only one thread touch a piece of shared data at a time.
DeadlockA cycle of threads each waiting on a lock another holds — nobody can move.
Event loopA single-threaded dispatcher that waits for the next event and runs its handler to completion.
CallbackA function registered in advance to run later, when some event fires.
ReentrancyA handler calling back into the event loop while it's still running, letting a second event interleave inside it.
Threaded kernelIsolating the few truly CPU-parallel operations inside a small locked core, keeping the rest single-threaded.
1What a thread actually is▾

A thread is an independent stream of instruction execution that shares memory, open files, and other state with its sibling threads, and is scheduled preemptively by the OS or runtime.

Now you're ready: the talk's entire argument follows from that one word, "shares" — shared state is what makes threads dangerous.
2Preemptive scheduling▾

Preemption means the scheduler can interrupt a thread at essentially any point, not just where the programmer chose to yield. That's what makes concurrent access to shared data unpredictable — any interleaving is possible.

Now you're ready: this unpredictability is exactly why threaded code needs locks, and why forgetting one is catastrophic rather than merely awkward.
3Locks and synchronization▾

A lock (mutex) lets only one thread execute a critical section at a time. Every thread that touches the shared data must remember to acquire the right lock — every time, in every code path.

Now you're ready: the talk's first complaint about threads is exactly this — forget one lock and data silently corrupts, with no crash to point at the bug.
4Deadlock▾

Deadlock happens when threads wait on each other's locks in a cycle: thread 1 holds lock A and wants B, thread 2 holds B and wants A. Neither can proceed, and the system hangs.

Now you're ready: this exact two-lock scenario is the talk's slide 6 diagram, and it reappears (dressed as a callback) in the module-abstraction problem.
5The event-driven model▾

One execution stream. An event loop waits for the next event and dispatches it to a registered handler, which runs to completion before the loop waits again — no preemption, no concurrent execution.

Now you're ready: this is the talk's proposed alternative — deliberately avoiding concurrency rather than embracing it.
6Callbacks▾

A callback is code registered ahead of time — "call this function when the button is pressed" — rather than code that blocks waiting for the event to happen.

Now you're ready: callbacks are safe on their own, but the talk shows they become dangerous the moment a lock is held while one fires.
7Reentrancy▾

A handler must return before the next event can be dispatched — a handler can't just "wait" mid-way. If a long handler periodically re-enters the event loop to stay responsive, a second event can start running inside the first.

Now you're ready: this is where events reintroduce their own, milder version of interleaving bugs.
8True CPU concurrency▾

Time-slicing one CPU among many threads is an illusion of concurrency. True CPU concurrency means actual simultaneous execution on multiple physical CPUs — the one thing a single-threaded event loop structurally cannot provide.

Now you're ready: this is the talk's one legitimate reason to use threads at all.
9Module independence▾

Good software design lets modules be built and tested independently. Threads break this: a lock held by module A while it calls into module B means A's and B's locking behavior are no longer independent — each must know the other's internals.

Now you're ready: this abstraction-breaking is the talk's deeper complaint, beyond "locks are annoying."
10The "threaded kernel" pattern▾

Instead of an all-or-nothing choice, isolate the small amount of genuinely CPU-parallel work inside a tightly-scoped, carefully-locked core ("kernel"), and keep everything around it — GUIs, request handling — single-threaded and event-driven.

Now you're ready: this is the talk's actual recommendation, not "never use threads."
The whole story in one place

The argument in a nutshell

Why threads look powerful, why that power is rarely needed, and what to use instead.

Threads grew out of the OS world (one kernel thread per process) and were then generalized into a user-level tool, proposed as the solution to concurrency wherever it comes up — GUIs, distributed servers, scientific computing. Ousterhout's claim is that this generalization went too far: threads are a general-purpose concurrency mechanism that is genuinely hard to use correctly, and for almost every purpose people reach for them, an event-driven design does the same job with far less risk.

The hardness isn't cosmetic. Shared state plus preemptive scheduling means every access to shared data needs a lock, and forgetting even one silently corrupts memory instead of crashing loudly. Locks compose badly: a lock held across a callback into code you don't control can deadlock, and this breaks the basic promise that modules can be designed independently. None of this shows up in a compiler error — it shows up as an intermittent hang or a data corruption bug weeks later.

Events sidestep almost all of it by refusing concurrency in the first place: one execution stream, no preemption mid-handler, and no locks needed for state that only the event loop touches — so no deadlock over that state either. The cost is real but narrower — long-running handlers freeze the loop, handlers can't casually hold state across separate events, and a single event loop gives you no actual multi-CPU parallelism. The recommendation is not "abolish threads" — it's to default to events everywhere, and reserve threads for a small, carefully isolated "threaded kernel" used only where true CPU concurrency is the point (high-end database servers, CPU-bound scientific code).

🍯 Key takeaways

  • Threads reward power, not correctness: they let you express concurrency, but most programmers can't use them safely.
  • The two named hazards are synchronization (forget a lock, corrupt data silently) and deadlock (circular lock waits, system hangs).
  • Threads break module independence: a lock held across a callback can deadlock two modules that were each individually correct.
  • Events avoid concurrency by construction for state the loop alone touches — no locks, no preemption mid-handler, no deadlock over that state — at the cost of no true CPU parallelism.
  • The fix isn't "no threads," it's a threaded kernel: isolate the few genuinely parallel operations, keep the rest event-driven.
Five everyday pictures

How to think about threads vs. events

Each stands alone. Every card ends with where the picture stops being true.

The core hazard · shared state

One kitchen, two cooks, one knife rack

Two cooks share a kitchen and one knife. Forget to hand it off with a word and you'll both grab it — or worse, one cook cuts while the other reaches. Threads share memory the same way locks share the knife: forget one handoff and the "kitchen" (shared data) gets corrupted, silently, with no crash to point at.

Where it breaks: a real kitchen has cooks who notice a collision. Corrupted shared memory doesn't announce itself — that's what makes it worse than the analogy suggests.
Deadlock · slide 6

Passing the salt and the pepper

You hold the salt and want the pepper; your neighbor holds the pepper and wants the salt. Both wait for the other to pass first. Nobody moves — that's exactly thread 1 holding lock A while wanting B, and thread 2 holding B while wanting A.

Where it breaks: at a real table, someone eventually just puts something down. Locks don't — there's no timeout by default, so the "table" (system) hangs indefinitely.
The alternative · event loop

A receptionist with one desk

One receptionist, one queue: handle the person at the window fully, then call the next. No two visitors are ever served at once, so there's nothing to coordinate between them — the receptionist's single-stream discipline is exactly what removes the need for locks.

Where it breaks: if one visitor's request takes an hour, everyone behind them waits — the receptionist has no way to serve two people "at once" even when it would genuinely help.
Broken abstraction · slide 7

Calling a locksmith while the door is locked

One thread is inside module A, holding A's lock, and calls down into module B. At the same moment a second thread is inside B, holding B's lock, and makes a callback up into A. Each now waits at the door the other is holding shut. Neither module was wrong on its own; the deadlock only exists because calls go down (A then B) while callbacks go up (B then A).

Where it breaks: a locksmith would just tell you the door's stuck. Software gives no such warning — the entanglement is invisible until it hangs.
The recommendation · slide 14

An engine room on a sailboat

A sailboat is mostly wind and rigging — quiet, single-crew logic — but keeps one small, tightly-run engine room for the rare moment true power is needed. Everything outside that room stays simple by design; only the engine room's crew needs to know its hazards.

Where it breaks: the engine room in this analogy runs on its own; the real "threaded kernel" still has to interoperate carefully with the event-driven code calling into it.
The full argument

How the case is actually built

Section by section, with the talk's own diagrams rebuilt.

1 · What threads are, and where they came from

Threads began as an OS concept (one kernel thread per user process), then became a general user-level tool proposed for OS design, scientific computing (one thread per CPU), distributed servers (overlap I/O), and GUIs (keep the display alive during long computation). The talk's claim isn't that these uses are wrong in principle — it's that the mechanism itself is too hard for the programmer population actually reaching for it.

2 · Why threads are hard, continued: abstraction and performance

Beyond deadlock, threads break the promise that modules can be designed independently: a lock held across a callback into another module can deadlock two pieces of code that were each correct in isolation. And getting good performance is its own fight — coarse locking (monitors) kills concurrency, fine-grained locking adds complexity and can be slower in the common case, and OS scheduling/context-switch costs impose a floor no amount of careful locking removes. On top of that, 1995-era thread support was uneven: standard libraries, window systems, and kernel calls weren't reliably thread-safe, and debugging tools were scarce.

3 · What events cost

Long-running handlers freeze the whole application — the fix is to fork subprocesses for genuinely long work and use an event to learn when it's done, or break the work into event-driven chunks, or periodically re-enter the event loop (accepting the reentrancy complexity that brings back). A handler also can't casually keep local state alive across two separate events, since it must return before the next event dispatches. And fundamentally, one event loop is one execution stream: no true CPU concurrency, so events alone are unsuitable for CPU-bound scientific work.

M1 · The thread model: five properties and what each one costs

Slide 3 defines threads by five bullets and one picture (a row of thread circles, each with an arrow up to one box labelled "Shared state (memory, files, etc.)"):

  1. "General-purpose solution for managing concurrency." One mechanism offered for every kind of concurrency (M2 shows there are really three kinds).
  2. "Multiple independent execution streams." Each thread has its own program counter, registers and stack. The stack holds its local variables and return addresses, so a thread that blocks keeps its whole call chain intact.
  3. "Shared state." All threads see the same memory, open files and other process state. Any pointer one thread holds can be dereferenced by another.
  4. "Pre-emptive scheduling." The scheduler, not the thread, decides when a thread stops. On a uniprocessor a timer interrupt can switch threads between any two instructions; on a multiprocessor two threads literally execute at the same instant.
  5. "Synchronization (e.g. locks, conditions)." Because of 3 and 4, the programmer must add locks (mutual exclusion) and condition variables (waiting for a state change) to restore any invariant across more than one memory operation.

The invariant. The thread model by itself guarantees nothing about what another thread may do between two of your statements. Every invariant on shared data exists only because the programmer created it with locks. That is the root of every hazard in M4 to M8.

Slide 4 lists the uses that made threads look universal. The key to the whole talk is that these uses want different things, and only one of them needs more than one CPU executing at once. This guide's classification of each bullet:

Why the distinction matters. On a uniprocessor, threads can only interleave. For I/O overlap and responsiveness, interleaving is all you need, and an event loop interleaves too (it switches to another handler whenever one handler finishes). So on one CPU, threads buy those two goals at the price of the full synchronization machinery, while events buy them with none. Only the first goal, parallel computation, is impossible for a single event loop. Slide 2 states the resulting claim: "Threads should be used only when true CPU concurrency is needed."

What breaks if the assumption changes. The argument is calibrated to machines with one CPU. On a multicore machine a server's request processing is itself CPU work that can be spread across cores, so "high-concurrency server" moves toward the row that needs true CPU concurrency. von Behren et al. use exactly this: they say Ousterhout "explicitly supports the use of threads for true concurrency, which is the case in our target space" (Events-bad §6).

M4 · Synchronization: the lock discipline and what a forgotten lock does

Slide 6, first half: "Must coordinate access to shared data with locks." and "Forget a lock? Corrupted data."

The mechanism of corruption. A statement like count = count + 1 compiles to a load, an add and a store. Two threads running it on the same variable can interleave as load(T1), load(T2), add, add, store(T1), store(T2): both read the old value, both store old+1, and one increment is lost. Nothing traps, nothing crashes. The damage is a wrong value that some later reader trips over, possibly much later and in unrelated code. For multi-word invariants (a linked list's pointers, a count that must match a table) the symptom is a structure that is internally inconsistent, which can later crash anywhere that trusts it.

The discipline that prevents it. Associate each shared variable (or each invariant) with one lock, and hold that lock for every access, for the whole span over which the invariant is temporarily broken. Two failure modes follow directly: forgetting the lock on one access path (a race), and taking it on each access but releasing it in the middle of a multi-step update (an atomicity violation: every individual access is locked, yet another thread sees the half-done state).

Why it is hard to get right. The discipline is global. Every code path in every module that touches the variable must obey it, including code written later by someone else. The compiler does not check it, and a violation shows up only in some interleavings, so tests usually pass (M7).

Events. With one execution stream and no preemption of handlers, only one handler touches shared data at a time, so the discipline holds without any locks. This depends on two conditions: handlers never run in parallel (one loop, one CPU), and a handler never lets another handler run while its update is half done (no re-entering the loop, M12; no hidden wait, M17).

M5 · Deadlock: circular wait, and why it depends on timing

Slide 6, second half: "Circular dependencies among locks." and "Each process waits for some other process: system hangs." The diagram: thread 1 points at lock A, thread 2 points at lock B, a red arrow runs from lock A to lock B (thread 1, holding A, wants B) and a blue arrow from lock B back to lock A (thread 2, holding B, wants A).

The mechanism. A thread that requests a held lock sleeps until the holder releases it. If the waits form a cycle, no holder in the cycle will ever run its release, so every thread in the cycle sleeps forever. The textbook conditions (background, not on the slide) are all present with ordinary blocking locks: mutual exclusion, hold-and-wait (a thread keeps A while asking for B), no preemption of locks (nobody can take A away from thread 1), and circular wait.

The cure and its price. The standard prevention is a global lock order: every thread acquires locks in the same order, which makes a cycle impossible. Mesa's paper gives the same rule ("impose a partial ordering on resources"). The price is that the order is a global property of the program. A module must know which locks its callers might already hold and which locks its callees will take, which is exactly the abstraction break of M6.

Why it is a debugging problem, not just a design problem. The cycle forms only in interleavings where both threads take their first lock before either takes its second. In most runs one thread finishes both acquisitions first and the program works. The figure shows the same two threads under two schedules.

M6 · Callbacks vs locks: the two module diagrams on slide 7

Slide 7 makes two claims, "Threads break abstraction: can't design modules independently." and "Callbacks don't work with locks.", and backs them with two small diagrams. Each shows two modules, A above B, each protecting its data with its own lock (a monitor per module). The existing worked example in this guide simplifies them; here is what each diagram actually shows.

Left diagram: waiting inside a nested call. T1 enters Module A, then calls down into Module B, and in B it goes to "sleep". T2 also comes in through Module A, heading down into B to do the "wakeup". The red "deadlock!" is on T2's entry into A. Step by step:

  1. T1 calls an entry procedure of A: it acquires lock A.
  2. Still inside A, T1 calls an entry procedure of B: it acquires lock B.
  3. In B, T1 must wait for some condition, so it does wait(c). A condition wait releases the lock of the monitor it is in, which is lock B. Lock A, taken one level up, stays held.
  4. The only thread that can make the condition true is T2, and B's interface is reached through A. T2 calls A and blocks on lock A.
  5. T1 waits for T2's signal; T2 waits for lock A, which T1 holds while asleep. Neither moves.

Right diagram: a callback runs into the lock order. T1 "calls" down from A into B. T2 starts inside B and makes "callbacks" up into A. The "deadlock!" mark is on the upward arrow. Step by step:

  1. T1 enters A (holds lock A) and calls down into B, so it needs lock B.
  2. Meanwhile T2 is running inside B (holds lock B). For example B is a lower layer, such as a network or window-system module, delivering a notification.
  3. T2 invokes a callback that A registered with B. The callback is A's code, so it needs lock A.
  4. T1 holds A and waits for B; T2 holds B and waits for A. This is the circular wait of M5, produced by two calls that each look reasonable in isolation: downward calls take locks in the order A then B, callbacks take them in the order B then A.

The usual repairs, and why each costs abstraction (background and inference). For the left case: release A's lock before calling into B (but then A's invariants must hold at the call, and A must revalidate afterward), or restructure so the call to B is made from code outside A's monitor. For the right case: never invoke callbacks while holding your own lock (B must queue notifications and deliver them after unlocking), or impose a global order and forbid upcalls that violate it. Every repair requires one module to make promises about its locking behavior to the other, so the lock protocol becomes part of each module's interface.

Events. In a single-threaded event program there are no locks, so neither cycle can form: a callback is an ordinary procedure call on the one stream. The left case has no analog either, because a handler cannot sleep waiting for another handler (it must return, M13). What events do not remove is the reentrancy version of the right case: B calling back into A while A is in the middle of an update, so A's callback sees A's invariants broken. That is a logic bug instead of a hang (M17).

M7 · Debugging: data dependencies and timing dependencies

Slide 7's first bullet: "Hard to debug: data dependencies, timing dependencies." Slide 12 states the comparison: "Debugging easier with events: Timing dependencies only related to events, not to internal scheduling. Problems easier to track down: slow response to button vs. corrupted memory."

The mechanism behind "timing dependencies". In a preemptive threaded program, the outcome depends on where the scheduler switched threads, at instruction granularity. That schedule is not part of the program's input; it depends on timer interrupts, cache misses, other processes and the number of CPUs. Rerunning the same input usually produces a different interleaving, and adding a print statement or a debugger breakpoint changes the timing enough to hide the bug. "Data dependencies" is the other half: the bug is in the data that two threads share, so the thread that notices corruption (and whose stack you can see) is usually not the thread that caused it.

Why events are easier on this axis (this guide's reading of slide 12). In an event program the only scheduling decision is which event the loop dispatches next, and switches happen only at handler boundaries. Given the same sequence of events, the handlers execute the same way, so a recorded event sequence can be replayed. And the typical failure mode changes: a mistake in an event program usually shows up as a handler that takes too long (the "slow response to button") rather than as memory silently corrupted by an unlucky interleaving.

What the claim leaves out. Events trade one debugging problem for another. Adya et al. list the "debugging stack" as a cost of manual stack management: when the debugger stops in a handler, "the call stack only shows the state of the current event handler and provides no information about the sequence of events that the ripped task performed before arriving at the current event handler invocation." von Behren et al. add that "the run-time call stack encapsulates all live state for a task, making existing debugging tools quite effective" in threads.

M8 · Performance: the locking granularity trap and the OS floor

Slide 8: "Achieving good performance is hard: Simple locking (e.g. monitors) yields low concurrency. Fine-grain locking increases complexity, reduces performance in normal case. OSes limit performance (scheduling, context switches)." Slide 13 gives the event side: "Events faster than threads on single CPU: No locking overheads. No context switching."

Coarse locks. One lock per module (a monitor) is easy to get right but serializes every entry into the module. Threads that need the module queue on its lock, so a program with many threads may have only one doing useful work in the hot module. On a uniprocessor this costs switches; on a multiprocessor it removes the parallelism threads were supposed to provide.

Fine-grained locks. Splitting the data and giving each piece its own lock lets threads proceed in parallel, but (1) every lock is another thing to forget (M4) and another edge in the lock order (M5), and (2) every acquire and release costs atomic instructions even when no other thread is anywhere near. The "normal case" in the slide is the uncontended one, and in the normal case fine-grained locking is pure overhead.

The OS floor. With kernel-implemented threads, a switch involves a kernel entry, saving and restoring registers, and a scheduler decision. The application cannot reduce that cost by writing better locking code.

The event-side claim and its condition. On one CPU an event loop needs no locks (one stream) and switches between "tasks" by returning from one handler and calling the next, an ordinary procedure return and call. Both advantages depend on "single CPU". On a multiprocessor an event loop still pays no locking cost, but it uses only one CPU, which slide 13 concedes in the same breath: threads give "scalable performance on multiple CPUs."

Cost sketch (inference, no numbers in the paper). Per unit of work on one CPU: threads pay work + lock operations + thread switches; events pay work + handler dispatch, plus one blocking wait in select() or the equivalent each time the loop runs out of ready events. The talk's argument is that the second sum is smaller. The 2002 and 2003 papers attack the size of the first sum, not its form.

🔗
Rebuttals on performance. von Behren et al. accept that many threaded servers performed badly but call this "an artifact of poor thread implementations": operations that are O(n) in the number of threads, plus switch overhead "due to both preemption ... and additional kernel crossings (in the case of kernel threads)." Their modified GNU Pth user-level package, with most O(n) scheduler operations removed, "scales quite well up to 100,000 threads" in the SEDA benchmark (Events-bad Fig. 2), and their threaded Knot server reached nearly 700 Mbit/s against a 500 Mbit/s maximum for the event-based Haboob, whose thread-pool-per-handler design makes it "context switch 30,000 times per second when fully loaded", more than six times as often as Knot. Adya et al. measured a fiber switch at "less than ten times the cost of a procedure call." Both attack the "no context switching" bullet: a cooperative user-level switch never enters the kernel, and with no preemption there are no locks to pay for on a uniprocessor.
🎓
From the lecture: a student raised context switch overhead; the professor noted that with enough cores you might not need to switch at all, but these papers assumed uniprocessors, so time is spent switching from one thread to another. On why large thread counts failed in old packages, he pointed to data structures written assuming tens of threads (operations that were O(n)), and to stacks: "if you just have a dozen threads, it's not a big deal," but with 10,000 or a million threads you can overwhelm the virtual memory system with stacks. He added that the papers assumed 32-bit address spaces; today's 64-bit machines (with 40 to 50 bits actually implemented) make address space much less of a concern.

M9 · Support and portability in 1995, and "often don't want concurrency anyway"

Slide 8 lists four support problems and one design observation:

  • "Hard to port threaded code (PCs? Macs?)." Thread APIs differed from system to system, and some desktop platforms of the time had no comparable preemptive thread facility at all (the slide only poses the question).
  • "Standard libraries not thread-safe." Library routines with hidden static state (internal buffers, global error variables) give wrong results when two threads call them at once. A threaded program must avoid them or wrap them in locks, and must know which ones are unsafe.
  • "Kernel calls, window systems not multi-threaded." If the window system or a system call interface assumes a single caller, every thread that touches it must be serialized anyway, which turns the threaded GUI back into a single stream with extra locks.
  • "Few debugging tools (LockLint, debuggers?)." LockLint was a Sun static lock-checking tool (background); the parenthetical question mark says debuggers that understood threads were scarce.
  • "Often don't want concurrency anyway (e.g. window events)." Window events carry an order that matters: a button press must be processed before the release, keystrokes in the order typed. If each event got its own thread, the program would need locks or queues to put the order back (this guide's reading). A single loop processing events in arrival order gets it for free.

Slide 13 condenses this to "Events more portable than threads." The mechanism is that an event loop needs only one thread plus some way to wait for several input sources, which every platform had.

What changed. These are claims about 1995 tooling, not about the model. The lecture notes that POSIX later standardized a thread API (pthreads) that vendors implemented even on top of their own thread systems, which removed most of the porting problem; thread-safe libraries and race detectors (Eraser in this course) followed. von Behren et al. make the general version of this argument: the weaknesses of threads are "artifacts of specific threading implementations and not inherent to the threading paradigm."

🎓
From the lecture: each system of the time had its own thread API; they "all tended to do almost exactly the same thing" but with different routine names and parameter orders, so a portable threaded program needed #defines. The POSIX standards body then defined pthreads, which every vendor adopted even if it had its own thread system underneath. On thread-safe libraries: "That's even true today": you must check the documentation of anything you call from a multithreaded program.

M10 · The event-driven model: registration, the loop, run to completion

Slide 9 defines the alternative with five bullets and a picture (an "Event Loop" box with an arrow curving back into itself, and arrows fanning down to a row of "Event Handlers"):

  • "One execution stream: no CPU concurrency."
  • "Register interest in events (callbacks)."
  • "Event loop waits for events, invokes handlers."
  • "No preemption of event handlers."
  • "Handlers generally short-lived."

Spelled out as code (this guide's sketch of the standard structure; the slide gives only the bullets):

// registration: "register interest in events (callbacks)"
register(source, condition, handler, clientData):
    table[source, condition] = (handler, clientData)   // clientData: heap state the handler will need

// the loop: "event loop waits for events, invokes handlers"
event_loop():
    while app is alive:
        ready = wait_for_any(table)     // select()/poll() on sockets and pipes, the window
                                       // system's queue, the nearest timer deadline.
                                       // The ONLY place this stream ever blocks.
        for e in ready:                 // one at a time, in order
            (h, cd) = table[e.source, e.condition]
            h(e, cd)                   // runs to completion; no other handler can start
                                       // until h returns ("no preemption of event handlers")

The invariant. At most one handler executes at any moment, and each handler runs from entry to return without any other handler running in between. Equivalently, every handler is an atomic operation on the program's shared state. Between handlers the stack is empty except for the loop's own frame, so one stack serves the whole program.

What follows from the invariant. No locks are needed for state touched only by handlers (M4). No lock deadlocks are possible (M5, M6). Only one stack exists, so per-task memory is whatever heap state the program chooses to keep (the clientData), not a reserved stack per task. A handler's view of shared state at entry is exactly what the previous handler left.

The assumptions, and what breaks if each fails.

AssumptionIf it fails
A1. Handlers never block (every slow operation has a non-blocking form that reports completion as an event)One blocking call stops the entire program: no other event is dispatched until it returns. A page fault or a blocking library call has the same effect (M17).
A2. Handlers are short ("generally short-lived")Every queued event waits behind the long handler: the application is "non-responsive" (slide 11, M12).
A3. One CPU is enoughOther CPUs sit idle; the loop cannot use them (M14).

Ousterhout is the creator of Tcl/Tk, whose event loop works this way: fileevent registers a handler for a readable or writable channel, after registers a timer handler, and update re-enters the event loop from inside a handler, which is the third escape hatch on slide 11 (M12). This is the context in which the talk was written: the lecture describes him as doing research on window systems at the time.

M11 · What events are used for: one handler per event, one handler per input source

Slide 10 lists two domains. GUIs: "One handler for each event (press button, invoke menu entry, etc.)" and "Handler implements behavior (undo, delete file, etc.)." Distributed systems: "One handler for each source of input (socket, etc.)", "Handler processes incoming request, sends response.", and "Event-driven I/O for I/O overlap."

How a server overlaps I/O with one stream. Each connection's socket is registered for "readable". When a request arrives, its handler reads what is available without blocking, and if the request is complete, computes and starts sending the response. If the response does not fit in the kernel's buffer, the handler registers for "writable" and returns; the rest is sent by a later handler. While any one connection waits on the network, the loop serves the others. Per-connection progress is a small state machine kept in a heap object, not a stack.

The hidden condition. "Handler processes incoming request, sends response" in one handler is only possible when processing never waits. If processing needs a disk read or a call to another server, the handler must end at that point and a second handler must finish the job when the result arrives (M13). The professor's CS142 example shows what that does to the code.

🎓
From the lecture (CS142 slides): a typical server step written with threads is three lines: request = readRequest(socket); reply = processRequest(request); sendReply(socket, reply);. If those calls did not block, the event version would look the same. Because they do, each blocking call takes an extra "done" callback argument: readRequest(socket, doneRead), then doneRead(request) calls processRequest(request, doneProcess), doneProcess(reply) calls sendReply(socket, reply, doneSend), and doneSend(errorCode) calls the caller's doneCb(errorCode). What was a straight sequence of instructions "is now jumping all over" the source files. In JavaScript it was common to write the callbacks as nested anonymous functions instead, so the calls at least appear in order, "a little bit getting shifted over to the right" with each level.

M12 · Long-running handlers and the three escape hatches

Slide 11, first problem: "Long-running handlers make application non-responsive." Under the run-to-completion invariant, every queued event waits for the running handler (figure in M10). The slide gives three remedies; each preserves a different part of the invariant.

M13 · "Can't maintain local state across events (handler must return)"

Slide 11's second problem is one line, but it is the problem the two companion papers are mostly about.

The mechanism. A thread that needs to wait (for a disk block, a network reply, the user's next click) simply blocks. Its stack frames, with every local variable and every return address up the call chain, stay intact, and when it resumes it continues inside the same procedure. An event handler cannot wait: the loop can dispatch nothing else until the handler returns, so the handler must return at the point where it would have waited. Its stack frame is popped. Anything the continuation of the computation will need (the socket, the request, a loop index, the caller's identity) must be copied into a heap object and registered together with the handler that will continue the work. When the awaited event arrives, the next handler gets that object and copies the values back out.

Consequences (Adya et al. §3.2 list them for every function that is split this way): one conceptual function becomes several language functions; automatic variables move to a heap structure; any loop or branch that contains a wait must be cut into separate functions; and the debugger's call stack no longer shows how the task got here. Adya et al. name this "stack ripping". Worse, when a function that used to return immediately gains a wait, every caller up the call graph must be split too, until one is reached that already uses continuation-passing form (M17).

Ousterhout's position. The slide lists this as a cost of events without remedy, and "Problems with Events" sits alongside slide 13's concession that threads "can have long-running stateful handlers without freezes." The talk's judgment is that the cost is worth paying for most programs because most handlers do not need to wait (GUI handlers that run briefly and return).

🎓
From the lecture: on "stack ripping", a student explained that wherever a task would yield, the code must be split into separate procedures; asked what is being ripped, another said local variables that used to live on the stack must be put on the heap so each handler can reach them. The professor: with threads the request's state is pushed on the stack and held there; with events "you don't have a stack, really," so "all this stuff that was in the stack needed to be ripped off and put somewhere." On closures (JavaScript): a nested function captures the variables it uses, so "you don't need to rip it since the closure grabs it," at the risk of accidentally keeping something large alive (he once captured a gigabyte data structure that way). Closures remove the copying, not the splitting of the code.

M14 · No CPU concurrency, and event-driven I/O that is "not always well supported"

"No CPU concurrency (not suitable for scientific apps)." One execution stream runs on one CPU at a time. A multiprocessor gives an event program nothing, unless the program is split into independent pieces. Two ways to split while keeping the event model's lock-free invariant: run work in separate processes (escape hatch (a) of M12), or partition the shared data so that several loops each own a disjoint part and never touch each other's state. Adya et al. call the second idea data partitioning: "task-specific state needs no concurrency considerations because it has been explicitly partitioned from shared state." von Behren et al. mention the "hand-coded graph coloring technique used in libasync" (background: callbacks are given colors, and callbacks with the same color never run concurrently).

"Event-driven I/O not always well supported (e.g. poor write buffering)." The event model assumes every slow operation has a non-blocking form that reports completion as an event (assumption A1 of M10). The slide says this was not always true. A reading of the example (background and inference, not spelled out on the slide): a non-blocking write to a socket or pipe may accept only part of the data, so the program must keep the remainder in its own buffer, register for "writable", and finish the write in a later handler; and on Unix systems of the time, readiness notification did not cover ordinary disk files, which always appear ready, so a disk read or write inside a handler could block the entire loop.

How real systems close the gap. Both companion papers add helper threads for exactly this: in von Behren's Knot, "asynchronous disk I/O is provided by a thread pool that performs blocking I/O operations"; Adya et al.'s systems "use extra threads for converting blocking I/O operations to non-blocking operations," and "data partitioning prevents synchronization problems between the I/O threads and the state shared by cooperatively-managed tasks." That is slide 14's recommendation in practice: a small threaded component under a single-threaded main program (M16).

🎓
From the lecture: on data partitioning ("coloring techniques"), a student said it matters for threads because if each partition is accessed by only one thread you need no locks; the professor agreed and added that it "actually turns out it works for events as well": you cannot run several copies of the event loop on the same shared data, because that violates "the assumption that I only have one event running at a time," but if the data is partitioned, several event loops can run in parallel on the partitions "since they aren't talking to each other." Another student proposed one event loop per processor with I/O-bound tasks distributed among them; the professor agreed that threads and events can be combined in one system.

M18 · The rebuttals, claim by claim

Adya et al.'s decomposition (USENIX 2002). "Threads vs events" mixes two independent choices. Task management: serial (each task runs to completion), cooperative (tasks yield only at well-defined points, usually I/O), or preemptive (tasks can be interrupted anywhere, or run in parallel). Stack management: automatic (a task's state lives on its own stack while it waits) or manual (the programmer rips the task into handlers and carries state in continuations). Ousterhout's "threads" are preemptive plus automatic; his "events" are cooperative plus manual. Their claim: "Ousterhout's arguments are really about the task management decision", and cooperative task management can be combined with automatic stacks (the "sweet spot"), which they built with Windows fibers and adaptors between the two styles.

von Behren, Condit and Brewer (HotOS 2003). The problems with threads are artifacts of implementations: O(n) schedulers, kernel crossings, fixed-size stacks. With a cooperative user-level package, threads match events in performance (Lauer and Needham's duality: with good implementations the two structures should perform the same), keep call/return control flow and stack-based state, and are better targets for compiler help (dynamic stack growth, live-state reduction, race warnings).

Worked examples

Four scenarios straight from the talk's own diagrams and categories, traced step by step.

① Tracing the two-lock deadlock

Thread 1 and thread 2 each need locks A and B, acquired in opposite order.

  1. Thread 1 acquires lock A. Thread 2 acquires lock B. Both proceed normally so far.
  2. Thread 1 now needs B — but thread 2 holds it. Thread 1 blocks and waits.
  3. Thread 2 now needs A — but thread 1 holds it. Thread 2 blocks and waits.
  4. Neither thread will release its lock until it gets the other's. Nothing moves — the system hangs (slide 6).
🍯
Insight: nothing here was a coding mistake in the usual sense — both threads locked correctly. The bug is purely in the order of acquisition across threads, which is invisible from either thread's code alone.

② The callback deadlock across modules

Slide 7, right-hand diagram: two modules, each with its own lock. T1 calls down from A into B; T2 is running inside B and calls back up into A.

  1. T1 calls an entry procedure of module A and acquires lock A (slide 7's "calls" arrow).
  2. Meanwhile T2 is running inside module B, holding lock B; for example B is delivering an input notification.
  3. T1, still inside A, calls into B and blocks waiting for lock B.
  4. T2 invokes a callback that A registered with B (the "callbacks" arrow). The callback is A's code, so it needs lock A, held by T1. T1 waits for T2 and T2 waits for T1: deadlock.
  5. Both A and B were individually correct; the failure exists only because downward calls take the locks in the order A, B while callbacks take them in the order B, A. (The slide's left-hand diagram is a second variant, a condition wait inside B while A stays locked; Part II, M6 traces both.)
💡
This is the talk's sharpest point: threads don't just add bugs, they remove the ability to reason about a module in isolation — the exact thing good software design tries to preserve.

③ Why events avoid two specific overheads

The talk claims events are faster than threads on a single CPU (slide 13) for two named reasons.

  1. No locking overhead: a single-stream event loop never has two handlers touching shared state concurrently, so no lock acquire/release cost is ever paid.
  2. No thread context-switching overhead: since there's only one stream, the OS never has to save/restore application thread state to time-slice between handlers — though it can still preempt the event-loop process itself.
  3. A threaded equivalent doing the same work pays both costs on every shared-data access and every scheduling quantum, even when no two handlers were actually going to collide.
🌱
Note the scope: this is a single-CPU claim from 1995. It says nothing about whether events keep this speed advantage on today's many-core machines — a fair question for discussion.

④ Applying the decision rule to three systems

The talk's own categories (slides 4 and 14): GUIs, low-end distributed servers, and high-end database servers.

  1. GUI reacting to button clicks: no CPU-bound parallel work — use events (this is the talk's explicit GUI recommendation).
  2. Low-end server overlapping request I/O: concurrency is about overlapping waiting, not computing in parallel — use event-driven I/O.
  3. High-end database server doing genuine parallel query execution: this is exactly "true CPU concurrency" — the talk's named exception where threads (inside a small kernel) are justified.
🍯
Insight: the deciding question is never "is this performance-critical?" — it's "does this specific piece of work need multiple CPUs running simultaneously?"

Problem 1 · easy
A GUI needs to stay responsive during a 2-second file save. Spawn a thread, or use events?
Show answer
Events — fork a subprocess for the save and use an event to learn when it finishes, or chunk the work through the event loop. No CPU parallelism is needed, just not blocking the UI.Misconception: any operation that takes noticeable time needs a thread. The talk explicitly gives event-driven alternatives for exactly this case.
Problem 2 · easy
Thread 1 locks A then wants B; thread 2 locks B then wants A. Name what happens.
Show answer
Deadlock — a circular lock dependency where each thread waits on a lock the other holds, so neither ever proceeds (slide 6).Misconception: more locking always means more safety. Here, correct individual locking still produces a total hang.
Problem 3 · medium
Thread T1 holds module A's lock and calls down into module B, while thread T2 holds module B's lock and makes a callback up into A. What happens, and why does it defeat independent module design?
Show answer
Deadlock: T1 holds A and waits for B, T2 holds B and waits for A, because downward calls acquire the locks in the order A, B and callbacks acquire them in the order B, A. It defeats independence because A's and B's locking behavior are no longer separable: each module now must know the other's locking discipline (for example, that B calls back while holding its lock) to avoid a hang, which is exactly the coupling module boundaries are meant to prevent (slide 7).Misconception: locking is a purely local, per-module concern. Once a callback crosses a lock boundary, it isn't.
Problem 4 · medium
Name the two overheads the talk says events avoid that make them faster than threads on one CPU.
Show answer
Locking overhead (no lock acquire/release since there's only one stream) and thread context-switching overhead (no application thread-to-thread switches between handlers, though the OS can still preempt the event-loop process itself) (slide 13).Misconception: single-threaded automatically means slower. Here it's the reverse, specifically because no synchronization machinery is needed at all.
Problem 5 · hard
The talk allows one exception where full threading is justified. State the exact criterion and one example the talk itself gives.
Show answer
The criterion is that "true CPU concurrency" is needed: actual parallel execution across multiple physical CPUs. Examples given: high-end database servers, and CPU-bound scientific applications using one thread per CPU (slides 4, 11, 14).Misconception: "performance-critical" alone justifies threads. The criterion is specifically multi-CPU parallelism, not speed in general.
Problem 6 · hard
Why can't an event handler keep local state alive across two separate events, e.g. partway through a multi-step dialog?
Show answer
A handler must return control to the event loop before the next event can be dispatched — there's no way to "pause" a handler mid-execution and resume it later on the next event. Anything that needs to persist across events must be stored explicitly in an object/heap state, not left on the call stack (slide 11).Misconception: an event handler behaves like an ordinary blocking function that can wait partway through. It can't — it must run to completion or fork off separate work.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Does "threads" here mean kernel threads specifically?▾
No — the argument is about the general mechanism: multiple execution streams sharing memory, scheduled preemptively, coordinated with locks/conditions (slide 3). It applies whether the threads are kernel- or user-level.
Q2Don't I need concurrency to keep a GUI responsive during long work?▾
You need responsiveness, not necessarily threads. Fork a subprocess for the long work and use an event to find out when it's done, or break the work into event-driven chunks (slide 11).
Q3Why exactly is synchronization so error-prone?▾
Forgetting a single lock corrupts shared data silently instead of crashing, and correctness depends on every caller, everywhere, remembering the same discipline (slide 6).
Q4How is deadlock different from a missing-lock bug?▾
Deadlock is a visible, reproducible hang from circular waiting. A missing lock is a silent race that corrupts data without necessarily stopping anything — often harder to even notice (slide 6).
Q5Do events eliminate concurrency bugs entirely?▾
No — reentrancy (re-entering the event loop inside a long handler to stay responsive) reintroduces its own, milder interleaving bugs (slide 11).
Q6Can an event loop use multiple CPUs?▾
Not by itself — one event loop is one execution stream. That's the one thing threads structurally offer that events alone cannot (slide 13).
Q7What exactly is the "threaded kernel" recommendation?▾
Put the small amount of genuinely CPU-parallel code inside a tightly-scoped, carefully-locked core, and keep everything else — GUIs, request dispatch — single-threaded and event-driven around it (slide 14).
Q8Why single out callbacks as especially dangerous with locks?▾
A callback runs upward through the module stack, against the order in which ordinary calls take locks. If a lower module invokes a callback while holding its own lock, and another thread is coming down from the upper module holding the upper lock, the two acquire the locks in opposite orders and deadlock. Avoiding it requires each module to know the other's locking behavior, which breaks independent module design (slide 7).
Q9Is the "events are more portable" claim timeless?▾
The talk's claim is era-specific: in 1995, threaded code was hard to port, standard libraries weren't thread-safe, and kernel calls and window systems weren't multi-threaded (slide 8, summarized on slide 13 as "Events more portable than threads"). Worth treating as a claim about 1995 tooling, not a permanent law.
Q10Does the talk say threads are never worth it?▾
No — it explicitly carves out high-end servers and CPU-bound scientific code needing one thread per CPU. The claim is "avoid wherever possible," not "never" (slide 14).
Connecting to your world

Insights for OS & memory-systems design

Where this 1995 argument still shapes modern kernel and memory-tiering design.

io_uring and epoll are the event loop, industrialized

Completion queues and readiness notification are literally "event loop + handlers" scaled to kernel I/O — the same shift the talk argued for in distributed servers, now the default way Linux does high-performance storage and networking without a thread per connection.

Thread-per-core is the "threaded kernel," taken literally

Seastar/DPDK-style thread-per-core runtimes (and io_uring's optional SQPOLL kernel thread) pin one thread per core with private state, avoiding shared-state locking almost entirely — arguably a stricter, more disciplined version of the talk's "isolate the concurrency" recommendation than the talk itself imagined.

eBPF is a partial, verifier-enforced echo of the event model

Many eBPF program types are triggered by kernel events and run non-preemptibly to completion — a narrow, verifier-enforced version of the talk's run-to-completion discipline. But this is a loose analogy, not a paper-grounded claim: modern eBPF also has sleepable program types, helpers, maps, and concurrency rules that go well beyond a simple event loop, and the talk itself says nothing about eBPF.

Memory-tiering daemons sit right on the talk's fault line

Should a NUMA/CXL hotness-migration daemon (in the spirit of kswapd, or TPP's page-scan threads) be a dedicated background thread, or an event-driven callback off page-fault/PEBS-sample interrupts? It's exactly the talk's tradeoff: a scanning thread buys autonomy and steady progress at the cost of locking against the fault path; an event-driven callback avoids a dedicated thread but can't block or run long.

🍯
For OS-managed tiering work, the talk's framework raises the question more than it settles it: promotion/demotion decision logic off page faults or hotness samples fits the event-driven model cleanly, but bulk page-copy/migration is usually bounded by memory bandwidth and interconnect latency rather than CPU parallelism in Ousterhout's sense — so whether it deserves a dedicated thread has to be argued on its own terms, not read directly off this talk.
