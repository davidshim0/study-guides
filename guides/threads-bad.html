Reaching for events before reaching for threads

A shared cache is hard to split fairly. A shared program is worse. This is the plain-English case for why almost nobody should reach for threads first — and the one criterion, true CPU concurrency, that justifies it, covering both scientific computing and high-end servers.

⚡ TL;DR

  • This is a 1995 position talk, not a benchmark paper: its core contribution is a clean argument that threads solve a concurrency problem most code doesn't have, and events solve the one it usually does.
  • Headline claim, not a number: as concurrency mechanisms get more powerful (VB → C → C++ → threads), the pool of programmers who can use them correctly shrinks to a small slice of "wizards" — threads sit at the very top of that pyramid.
  • Why it matters: it's an influential, sharply argued early case for the event-loop/callback style used across GUIs, async I/O, and — much later — kernel mechanisms like io_uring and epoll, and it hands you a decision rule (events by default, threads only for true CPU concurrency) still worth applying to today's kernel and memory-tiering daemons.

📖 Quick glossary

ThreadAn independent execution stream that shares memory with its siblings and is scheduled preemptively.
PreemptionThe scheduler can suspend a thread mid-instruction at any point — the thread doesn't choose when.
Lock / mutexA gate letting only one thread touch a piece of shared data at a time.
DeadlockA cycle of threads each waiting on a lock another holds — nobody can move.
Event loopA single-threaded dispatcher that waits for the next event and runs its handler to completion.
CallbackA function registered in advance to run later, when some event fires.
ReentrancyA handler calling back into the event loop while it's still running, letting a second event interleave inside it.
Threaded kernelIsolating the few truly CPU-parallel operations inside a small locked core, keeping the rest single-threaded.
1What a thread actually is▾

A thread is an independent stream of instruction execution that shares memory, open files, and other state with its sibling threads, and is scheduled preemptively by the OS or runtime.

Now you're ready: the talk's entire argument follows from that one word, "shares" — shared state is what makes threads dangerous.
2Preemptive scheduling▾

Preemption means the scheduler can interrupt a thread at essentially any point, not just where the programmer chose to yield. That's what makes concurrent access to shared data unpredictable — any interleaving is possible.

Now you're ready: this unpredictability is exactly why threaded code needs locks, and why forgetting one is catastrophic rather than merely awkward.
3Locks and synchronization▾

A lock (mutex) lets only one thread execute a critical section at a time. Every thread that touches the shared data must remember to acquire the right lock — every time, in every code path.

Now you're ready: the talk's first complaint about threads is exactly this — forget one lock and data silently corrupts, with no crash to point at the bug.
4Deadlock▾

Deadlock happens when threads wait on each other's locks in a cycle: thread 1 holds lock A and wants B, thread 2 holds B and wants A. Neither can proceed, and the system hangs.

Now you're ready: this exact two-lock scenario is the talk's slide 6 diagram, and it reappears (dressed as a callback) in the module-abstraction problem.
5The event-driven model▾

One execution stream. An event loop waits for the next event and dispatches it to a registered handler, which runs to completion before the loop waits again — no preemption, no concurrent execution.

Now you're ready: this is the talk's proposed alternative — deliberately avoiding concurrency rather than embracing it.
6Callbacks▾

A callback is code registered ahead of time — "call this function when the button is pressed" — rather than code that blocks waiting for the event to happen.

Now you're ready: callbacks are safe on their own, but the talk shows they become dangerous the moment a lock is held while one fires.
7Reentrancy▾

A handler must return before the next event can be dispatched — a handler can't just "wait" mid-way. If a long handler periodically re-enters the event loop to stay responsive, a second event can start running inside the first.

Now you're ready: this is where events reintroduce their own, milder version of interleaving bugs.
8True CPU concurrency▾

Time-slicing one CPU among many threads is an illusion of concurrency. True CPU concurrency means actual simultaneous execution on multiple physical CPUs — the one thing a single-threaded event loop structurally cannot provide.

Now you're ready: this is the talk's one legitimate reason to use threads at all.
9Module independence▾

Good software design lets modules be built and tested independently. Threads break this: a lock held by module A while it calls into module B means A's and B's locking behavior are no longer independent — each must know the other's internals.

Now you're ready: this abstraction-breaking is the talk's deeper complaint, beyond "locks are annoying."
10The "threaded kernel" pattern▾

Instead of an all-or-nothing choice, isolate the small amount of genuinely CPU-parallel work inside a tightly-scoped, carefully-locked core ("kernel"), and keep everything around it — GUIs, request handling — single-threaded and event-driven.

Now you're ready: this is the talk's actual recommendation, not "never use threads."
The whole story in one place

The argument in a nutshell

Why threads look powerful, why that power is rarely needed, and what to use instead.

Threads grew out of the OS world (one kernel thread per process) and were then generalized into a user-level tool, proposed as the solution to concurrency wherever it comes up — GUIs, distributed servers, scientific computing. Ousterhout's claim is that this generalization went too far: threads are a general-purpose concurrency mechanism that is genuinely hard to use correctly, and for almost every purpose people reach for them, an event-driven design does the same job with far less risk.

The hardness isn't cosmetic. Shared state plus preemptive scheduling means every access to shared data needs a lock, and forgetting even one silently corrupts memory instead of crashing loudly. Locks compose badly: a lock held across a callback into code you don't control can deadlock, and this breaks the basic promise that modules can be designed independently. None of this shows up in a compiler error — it shows up as an intermittent hang or a data corruption bug weeks later.

Events sidestep almost all of it by refusing concurrency in the first place: one execution stream, no preemption mid-handler, and no locks needed for state that only the event loop touches — so no deadlock over that state either. The cost is real but narrower — long-running handlers freeze the loop, handlers can't casually hold state across separate events, and a single event loop gives you no actual multi-CPU parallelism. The recommendation is not "abolish threads" — it's to default to events everywhere, and reserve threads for a small, carefully isolated "threaded kernel" used only where true CPU concurrency is the point (high-end database servers, CPU-bound scientific code).

🍯 Key takeaways

  • Threads reward power, not correctness: they let you express concurrency, but most programmers can't use them safely.
  • The two named hazards are synchronization (forget a lock, corrupt data silently) and deadlock (circular lock waits, system hangs).
  • Threads break module independence: a lock held across a callback can deadlock two modules that were each individually correct.
  • Events avoid concurrency by construction for state the loop alone touches — no locks, no preemption mid-handler, no deadlock over that state — at the cost of no true CPU parallelism.
  • The fix isn't "no threads," it's a threaded kernel: isolate the few genuinely parallel operations, keep the rest event-driven.
Five everyday pictures

How to think about threads vs. events

Each stands alone. Every card ends with where the picture stops being true.

The core hazard · shared state

One kitchen, two cooks, one knife rack

Two cooks share a kitchen and one knife. Forget to hand it off with a word and you'll both grab it — or worse, one cook cuts while the other reaches. Threads share memory the same way locks share the knife: forget one handoff and the "kitchen" (shared data) gets corrupted, silently, with no crash to point at.

Where it breaks: a real kitchen has cooks who notice a collision. Corrupted shared memory doesn't announce itself — that's what makes it worse than the analogy suggests.
Deadlock · slide 6

Passing the salt and the pepper

You hold the salt and want the pepper; your neighbor holds the pepper and wants the salt. Both wait for the other to pass first. Nobody moves — that's exactly thread 1 holding lock A while wanting B, and thread 2 holding B while wanting A.

Where it breaks: at a real table, someone eventually just puts something down. Locks don't — there's no timeout by default, so the "table" (system) hangs indefinitely.
The alternative · event loop

A receptionist with one desk

One receptionist, one queue: handle the person at the window fully, then call the next. No two visitors are ever served at once, so there's nothing to coordinate between them — the receptionist's single-stream discipline is exactly what removes the need for locks.

Where it breaks: if one visitor's request takes an hour, everyone behind them waits — the receptionist has no way to serve two people "at once" even when it would genuinely help.
Broken abstraction · slide 7

Calling a locksmith while the door is locked

Module A holds a lock, then calls out to module B (a callback) to get help — but B, without knowing A's internals, tries to come back through the very door A is still holding shut. Neither module was wrong on its own; the deadlock only exists because their locking behavior became entangled.

Where it breaks: a locksmith would just tell you the door's stuck. Software gives no such warning — the entanglement is invisible until it hangs.
The recommendation · slide 14

An engine room on a sailboat

A sailboat is mostly wind and rigging — quiet, single-crew logic — but keeps one small, tightly-run engine room for the rare moment true power is needed. Everything outside that room stays simple by design; only the engine room's crew needs to know its hazards.

Where it breaks: the engine room in this analogy runs on its own; the real "threaded kernel" still has to interoperate carefully with the event-driven code calling into it.
The full argument

How the case is actually built

Section by section, with the talk's own diagrams rebuilt.

1 · What threads are, and where they came from

Threads began as an OS concept (one kernel thread per user process), then became a general user-level tool proposed for OS design, scientific computing (one thread per CPU), distributed servers (overlap I/O), and GUIs (keep the display alive during long computation). The talk's claim isn't that these uses are wrong in principle — it's that the mechanism itself is too hard for the programmer population actually reaching for it.

2 · Why threads are hard, continued: abstraction and performance

Beyond deadlock, threads break the promise that modules can be designed independently: a lock held across a callback into another module can deadlock two pieces of code that were each correct in isolation. And getting good performance is its own fight — coarse locking (monitors) kills concurrency, fine-grained locking adds complexity and can be slower in the common case, and OS scheduling/context-switch costs impose a floor no amount of careful locking removes. On top of that, 1995-era thread support was uneven: standard libraries, window systems, and kernel calls weren't reliably thread-safe, and debugging tools were scarce.

3 · What events cost

Long-running handlers freeze the whole application — the fix is to fork subprocesses for genuinely long work and use an event to learn when it's done, or break the work into event-driven chunks, or periodically re-enter the event loop (accepting the reentrancy complexity that brings back). A handler also can't casually keep local state alive across two separate events, since it must return before the next event dispatches. And fundamentally, one event loop is one execution stream: no true CPU concurrency, so events alone are unsuitable for CPU-bound scientific work.

Trace it through

Worked examples

Four scenarios straight from the talk's own diagrams and categories, traced step by step.

① Tracing the two-lock deadlock

Thread 1 and thread 2 each need locks A and B, acquired in opposite order.

  1. Thread 1 acquires lock A. Thread 2 acquires lock B. Both proceed normally so far.
  2. Thread 1 now needs B — but thread 2 holds it. Thread 1 blocks and waits.
  3. Thread 2 now needs A — but thread 1 holds it. Thread 2 blocks and waits.
  4. Neither thread will release its lock until it gets the other's. Nothing moves — the system hangs (slide 6).
🍯
Insight: nothing here was a coding mistake in the usual sense — both threads locked correctly. The bug is purely in the order of acquisition across threads, which is invisible from either thread's code alone.

② The callback deadlock across modules

Module A holds a lock and calls into module B, which calls back into A.

  1. Module A acquires its lock, then calls a callback that runs code in module B (slide 7's "calls" arrow).
  2. Module B, unaware A is locked, calls back into A (the "callbacks" arrow) — perhaps on a different thread.
  3. That call needs A's lock, which A itself still holds. Deadlock.
  4. Both A and B were individually correct; the failure exists only because their locking behavior became entangled through the callback.
💡
This is the talk's sharpest point: threads don't just add bugs, they remove the ability to reason about a module in isolation — the exact thing good software design tries to preserve.

③ Why events avoid two specific overheads

The talk claims events are faster than threads on a single CPU (slide 13) for two named reasons.

  1. No locking overhead: a single-stream event loop never has two handlers touching shared state concurrently, so no lock acquire/release cost is ever paid.
  2. No thread context-switching overhead: since there's only one stream, the OS never has to save/restore application thread state to time-slice between handlers — though it can still preempt the event-loop process itself.
  3. A threaded equivalent doing the same work pays both costs on every shared-data access and every scheduling quantum, even when no two handlers were actually going to collide.
🌱
Note the scope: this is a single-CPU claim from 1995. It says nothing about whether events keep this speed advantage on today's many-core machines — a fair question for discussion.

④ Applying the decision rule to three systems

The talk's own categories (slides 4 and 14): GUIs, low-end distributed servers, and high-end database servers.

  1. GUI reacting to button clicks: no CPU-bound parallel work — use events (this is the talk's explicit GUI recommendation).
  2. Low-end server overlapping request I/O: concurrency is about overlapping waiting, not computing in parallel — use event-driven I/O.
  3. High-end database server doing genuine parallel query execution: this is exactly "true CPU concurrency" — the talk's named exception where threads (inside a small kernel) are justified.
🍯
Insight: the deciding question is never "is this performance-critical?" — it's "does this specific piece of work need multiple CPUs running simultaneously?"
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it checks.

Problem 1 · easy
A GUI needs to stay responsive during a 2-second file save. Spawn a thread, or use events?
Show answer
Events — fork a subprocess for the save and use an event to learn when it finishes, or chunk the work through the event loop. No CPU parallelism is needed, just not blocking the UI.Misconception: any operation that takes noticeable time needs a thread. The talk explicitly gives event-driven alternatives for exactly this case.
Problem 2 · easy
Thread 1 locks A then wants B; thread 2 locks B then wants A. Name what happens.
Show answer
Deadlock — a circular lock dependency where each thread waits on a lock the other holds, so neither ever proceeds (slide 6).Misconception: more locking always means more safety. Here, correct individual locking still produces a total hang.
Problem 3 · medium
Module A holds a lock and calls a callback into module B, which calls back into A. What's this called, and why does it defeat independent module design?
Show answer
Callback deadlock. It defeats independence because A's and B's locking behavior are no longer separable — each module now must know the other's locking discipline to avoid a hang, which is exactly the coupling module boundaries are meant to prevent (slide 7).Misconception: locking is a purely local, per-module concern. Once a callback crosses a lock boundary, it isn't.
Problem 4 · medium
Name the two overheads the talk says events avoid that make them faster than threads on one CPU.
Show answer
Locking overhead (no lock acquire/release since there's only one stream) and thread context-switching overhead (no application thread-to-thread switches between handlers, though the OS can still preempt the event-loop process itself) (slide 13).Misconception: single-threaded automatically means slower. Here it's the reverse, specifically because no synchronization machinery is needed at all.
Problem 5 · hard
The talk allows one exception where full threading is justified. State the exact criterion and one example the talk itself gives.
Show answer
The criterion is "true CPU concurrency" is needed — actual parallel execution across multiple physical CPUs. Examples given: high-end database servers, and CPU-bound scientific applications using one thread per CPU (slides 4, 14).Misconception: "performance-critical" alone justifies threads. The criterion is specifically multi-CPU parallelism, not speed in general.
Problem 6 · hard
Why can't an event handler keep local state alive across two separate events, e.g. partway through a multi-step dialog?
Show answer
A handler must return control to the event loop before the next event can be dispatched — there's no way to "pause" a handler mid-execution and resume it later on the next event. Anything that needs to persist across events must be stored explicitly in an object/heap state, not left on the call stack (slide 11).Misconception: an event handler behaves like an ordinary blocking function that can wait partway through. It can't — it must run to completion or fork off separate work.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Does "threads" here mean kernel threads specifically?▾
No — the argument is about the general mechanism: multiple execution streams sharing memory, scheduled preemptively, coordinated with locks/conditions (slide 3). It applies whether the threads are kernel- or user-level.
Q2Don't I need concurrency to keep a GUI responsive during long work?▾
You need responsiveness, not necessarily threads. Fork a subprocess for the long work and use an event to find out when it's done, or break the work into event-driven chunks (slide 11).
Q3Why exactly is synchronization so error-prone?▾
Forgetting a single lock corrupts shared data silently instead of crashing, and correctness depends on every caller, everywhere, remembering the same discipline (slide 6).
Q4How is deadlock different from a missing-lock bug?▾
Deadlock is a visible, reproducible hang from circular waiting. A missing lock is a silent race that corrupts data without necessarily stopping anything — often harder to even notice (slide 6).
Q5Do events eliminate concurrency bugs entirely?▾
No — reentrancy (re-entering the event loop inside a long handler to stay responsive) reintroduces its own, milder interleaving bugs (slide 11).
Q6Can an event loop use multiple CPUs?▾
Not by itself — one event loop is one execution stream. That's the one thing threads structurally offer that events alone cannot (slide 13).
Q7What exactly is the "threaded kernel" recommendation?▾
Put the small amount of genuinely CPU-parallel code inside a tightly-scoped, carefully-locked core, and keep everything else — GUIs, request dispatch — single-threaded and event-driven around it (slide 14).
Q8Why single out callbacks as especially dangerous with locks?▾
A callback fired while holding a lock hands control to code the lock-holder didn't write and can't reason about; if that code tries to reacquire the same lock, it deadlocks — breaking independent module design (slide 7).
Q9Is the "events are more portable" claim timeless?▾
The talk's claim is era-specific: in 1995, thread APIs, window systems, and kernel calls weren't uniformly thread-safe across platforms (slide 13). Worth treating as a claim about 1995 tooling, not a permanent law.
Q10Does the talk say threads are never worth it?▾
No — it explicitly carves out high-end servers and CPU-bound scientific code needing one thread per CPU. The claim is "avoid wherever possible," not "never" (slide 14).
Connecting to your world

Insights for OS & memory-systems design

Where this 1995 argument still shapes modern kernel and memory-tiering design.

io_uring and epoll are the event loop, industrialized

Completion queues and readiness notification are literally "event loop + handlers" scaled to kernel I/O — the same shift the talk argued for in distributed servers, now the default way Linux does high-performance storage and networking without a thread per connection.

Thread-per-core is the "threaded kernel," taken literally

Seastar/DPDK-style thread-per-core runtimes (and io_uring's optional SQPOLL kernel thread) pin one thread per core with private state, avoiding shared-state locking almost entirely — arguably a stricter, more disciplined version of the talk's "isolate the concurrency" recommendation than the talk itself imagined.

eBPF is a partial, verifier-enforced echo of the event model

Many eBPF program types are triggered by kernel events and run non-preemptibly to completion — a narrow, verifier-enforced version of the talk's run-to-completion discipline. But this is a loose analogy, not a paper-grounded claim: modern eBPF also has sleepable program types, helpers, maps, and concurrency rules that go well beyond a simple event loop, and the talk itself says nothing about eBPF.

Memory-tiering daemons sit right on the talk's fault line

Should a NUMA/CXL hotness-migration daemon (in the spirit of kswapd, or TPP's page-scan threads) be a dedicated background thread, or an event-driven callback off page-fault/PEBS-sample interrupts? It's exactly the talk's tradeoff: a scanning thread buys autonomy and steady progress at the cost of locking against the fault path; an event-driven callback avoids a dedicated thread but can't block or run long.

🍯
For OS-managed tiering work, the talk's framework raises the question more than it settles it: promotion/demotion decision logic off page faults or hotness samples fits the event-driven model cleanly, but bulk page-copy/migration is usually bounded by memory bandwidth and interconnect latency rather than CPU parallelism in Ousterhout's sense — so whether it deserves a dedicated thread has to be argued on its own terms, not read directly off this talk.
