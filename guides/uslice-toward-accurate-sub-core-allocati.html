Pacing the burst, not just capping the period

A cgroup can stay under its quota all period long and still finish a short request 20× faster than its configured share implies. This is the plain-English story of μslice, an eBPF scheduler that closes that gap.

📄 Lin & Shahrad, "μslice: Toward Accurate Sub-Core Allocation with eBPF" · eBPF '26 🎓 cgroups/CFS/eBPF basics assumed — primers cover them ⏱ ~25 min read
⏱️

Release a CPU grant only if delivered service stays within f·(t−a) — not whatever's left in the period's quota.

Before you begin

Quick glossary, then eight primers

The acronyms first, then short cards on the OS/eBPF concepts the paper leans on. Skim what you already know.

Quick glossary — the acronyms you'll see everywhere

eBPFExtended Berkeley Packet Filter — sandboxed, verified programs loaded into the kernel without a kernel patch or module.
CFS / EEVDFCompletely Fair Scheduler / Earliest Eligible Virtual Deadline First — Linux's default (and newer, since 6.6) task schedulers.
cgroupControl group — a Linux mechanism for grouping processes and capping/accounting their resource use (here, CPU).
sched_extA Linux facility letting a BPF program implement a whole scheduling policy as a pluggable "scheduler class."
P, Qcgroup bandwidth-control period and quota: a cgroup's tasks may use at most Q CPU-time per P wall-clock time.
fConfigured fractional CPU allocation, f∈(0,1); Q = f·P.
ROverallocation ratio, R = d*/d — how much faster a request finished (d) than its resource contract (d*=C/f) implies.
C/f contractThe "ideal" completion time for CPU demand C under share f: d* = C/f.
DSQDispatch queue — a sched_ext queue that holds runnable tasks awaiting placement on a CPU.
CVCoefficient of variation — stddev/mean of execution durations; the paper's jitter metric.
1What a cgroup is, and what cpu.max controls▾

A cgroup groups one or more processes so the kernel can cap and account their resource use together. For CPU, cpu.max sets a period P and quota Q: tasks in the cgroup may collectively run for at most Q out of every P wall-clock time.

Now you're ready: a fractional allocation f is just Q=f·P — the knob cloud platforms expose as "0.25 vCPU" or similar.
2CFS and EEVDF — who runs next▾

These are Linux's fairness-oriented schedulers: they pick which runnable task gets the CPU next so that, over time, everyone gets a fair share. They operate at tick/scheduling granularity — tens of microseconds to milliseconds — independent of cgroup bandwidth control.

Now you're ready: CFS/EEVDF decide fairness within a period; cgroup bandwidth control caps how much CPU a whole cgroup gets per period. μslice adds a third layer that paces when grants release.
3Why a full quota upfront is a trap for short bursts▾

Each period starts with the full quota Q available. If a request's CPU demand C is ≤ Q, it can run start-to-finish at full-core speed inside one period — no throttling ever kicks in, even though the cgroup is fully compliant with its quota.

Now you're ready: "compliant with the quota" and "running at the configured rate f" are different things — that gap is the paper's whole subject.
4Fractional vCPUs as a billing/provisioning knob▾

Cloud platforms let customers request less than one core: Google Cloud Run down to 0.08 vCPU, AWS Lambda's default is 0.072 vCPU. Providers bill roughly allocation × wall-clock duration, so how fast a request actually finishes matters for both performance and cost accounting.

Now you're ready: if period-level quota lets a request finish early, both the provider's capacity model and its billing math are based on a rate the workload didn't actually receive.
5Millisecond-scale, single-concurrency workloads▾

Serverless functions, microservice stages, and edge handlers increasingly run for just a few milliseconds per invocation, and platforms like AWS Lambda run one request at a time per instance (single concurrency) — no intra-instance parallelism to reason about.

Now you're ready: at C = a few ms and P = tens of ms, the bandwidth-control period and the workload duration are the same order of magnitude — that's exactly where overallocation bites hardest.
6eBPF and sched_ext — policy without a kernel patch▾

eBPF lets verified, sandboxed programs run inside the kernel. sched_ext is a scheduler class built on eBPF: a BPF program can implement scheduling callbacks (enqueue, dispatch, running, stopping, quiescent) that the kernel invokes at the right moments, without forking CFS.

Now you're ready: μslice's CPU pacer is a sched_ext BPF program — this is what lets it add a pacing layer on commodity kernels without patching them.
7Dispatch queues (DSQs) and timers▾

Under sched_ext, runnable tasks sit in dispatch queues until a CPU is ready to take one. A BPF timer can be armed to fire at a future time and trigger an action — e.g., wake a CPU to re-check a queue.

Now you're ready: μslice holds paced tasks in a release-time-ordered DSQ and uses a timer to wake a CPU at or after their grant becomes compliant — not sooner, though actual wakeup is subject to scheduler/dispatch latency.
8Work-conserving vs non-work-conserving▾

A work-conserving scheduler never leaves a CPU idle while runnable work waits — it always gives someone the core. A non-work-conserving one may deliberately idle a CPU (or delay a task) to enforce a rate, even though work is ready.

Now you're ready: μslice is deliberately non-work-conserving by design — it's the whole mechanism by which it refuses to let a burst run "for free" ahead of its configured rate.
The whole story in one place

μslice in a nutshell

The mismatch, the fix, and how the pieces connect.

cgroup CPU bandwidth control enforces fairness at the period level (P, typically 10–100 ms): a cgroup may use up to quota Q per period. For long-running workloads this averages out to the configured rate f=Q/P. But for millisecond-scale bursts — common in serverless, microservices, and edge computing (the paper reports roughly 37% of Alibaba microservice requests finishing in under 10 ms) — a request with CPU demand C ≤ Q can consume its whole demand at full-core speed inside one period, finishing in roughly C time instead of the C/f resource contract. The paper calls the resulting speedup the overallocation ratio R = d*/d, and shows it reaching 2×–20× across common period settings, with jitter near quantization boundaries.

μslice fixes this without touching the cgroup interface. It runs as a sched_ext BPF scheduler that paces admitted cgroups: it tracks delivered CPU service S since a pacing epoch began at anchor time a, and releases the next grant only if the cgroup would remain within its service allowance f·(t−a) afterward. Tasks that aren't yet eligible sit in a release-time-ordered dispatch queue; a BPF timer marks them eligible and kicks a CPU at or after r, though actual wakeup is subject to scheduling/dispatch latency.

To stay safe under heavy load, μslice tracks the count of actively-paced workloads and falls back to the work-conserving path once that count crosses an overload threshold — protecting latency instead of chasing perfect pacing when the server is saturated.

🍯 Key takeaways

  • Period-level cgroup control enforces the quota per period, not the rate f over sub-period timescales.
  • Millisecond bursts (the paper reports ~37% of Alibaba microservice requests finish <10 ms) under small fractional vCPUs are exactly where this gap opens up.
  • μslice paces grants against gc(t) = max(0, (f(t−a)−S)/(1−f)) — the largest grant that keeps the cgroup on-contract.
  • It's implemented as a sched_ext BPF scheduler: no kernel patch, cgroup interface unchanged.
  • An overload bypass reverts to work-conserving scheduling when too many workloads are being paced at once.
  • Result: mean R ≈ 0.974 (vs 1.07–1.6 for baselines), geomean CV 0.023 (vs 0.21–0.32); overhead stays small — pacer-path latency ~50.3 μs, plus ~207.33 μs extra kernel/scheduling time vs the Q=1ms baseline (two separate measurements, not additive).
Six everyday pictures

How to think about μslice

Each stands alone — read in any order. Every card names where the picture stops being true.

The trap · Period-level quota

A monthly data cap you can burn through on day one

"5 GB per month" sounds like a steady trickle, but nothing stops you from streaming it all in one binge on the first morning. cgroup's quota works the same way: a full Q is available the instant the period starts, so a short burst just spends it all at once, at full speed.

Where it breaks: the phone plan resets once a month; cgroup periods reset every 10–100 ms, repeatedly — but because requests are shorter than the window, the "binge" effect reappears every single period.
The fix · Rate pacing

Cruise control vs a gas pedal you stomp then release

cgroup's quota is like driving flat-out until the tank (quota) empties, then coasting until it refills. μslice is cruise control: it computes, moment to moment, the largest grant that keeps you at the set speed f, and never lets you surge ahead of it — even though the "tank" would technically allow it.

Where it breaks: cruise control adjusts continuously; μslice only checks compliance at discrete grant boundaries (ge quanta), so it's a close approximation, not a perfectly smooth rate.
The mechanism · Release-time DSQ

A relay handoff timed to a stopwatch, not a tap on the shoulder

A relay runner doesn't get the baton the instant they're ready — they get it at the scheduled handoff moment. μslice's paced dispatch queue works the same way: a task waiting for CPU sits ordered by its earliest compliant release time r, and a timer fires the handoff at or after then — not the moment the CPU happens to be free, though actual wakeup is subject to scheduler latency.

Where it breaks: a relay handoff is a single instant; μslice recomputes r continuously as delivered service S accrues, so "the schedule" itself shifts as the request runs.
The formula · gc(t)

A savings account that stops paying out once you've drawn your allowance

You're entitled to withdraw at rate f of the time elapsed since the account opened (anchor a). gc(t) is exactly "allowance so far minus what you've already drawn" — once your withdrawals (S) catch up to f·(t−a), the available balance hits zero and you must wait for more time to accrue.

Where it breaks: a bank balance is simple subtraction; gc(t) divides by (1−f) because granting more CPU also advances t itself — the "interest" compounds slightly as you spend.
The safety valve · Overload bypass

Ramp meters that switch off during gridlock

Highway on-ramp meters pace cars onto the freeway one at a time to keep traffic flowing smoothly — but during a real jam, meters switch off and let everyone merge, because precise pacing no longer helps and only adds delay. μslice's overload bypass does the same: past 500 actively-paced workloads, it reverts admitted cgroups to the plain work-conserving path.

Where it breaks: ramp meters are usually a hard on/off; μslice's bypass has hysteresis (activate at 500, only recover below 400 after a 30 ms hold-down), so it doesn't flap at the boundary.
Why it matters · Billing & fairness

A taxi meter that sometimes runs fast, sometimes slow

If the meter (effective CPU rate) sometimes overcharges time and sometimes runs true, two riders paying the "same fare structure" get inconsistent service — one finishes fast and cheap, another waits and pays full price for the same trip. That's exactly the inter-tenant fairness problem the paper measures via R's spread across tenants (p5–p95 of 0.80–2.07 for the strongest baseline).

Where it breaks: a taxi meter error is a bug; cgroup's period-level overallocation is a structural consequence of the mechanism, not a malfunction — which is why it needs a different enforcement layer, not a bug fix.
The full explanation

How it actually works

From the quantization problem, through the grant formula, to the architecture that enforces it.

1 · The problem, formally

For a single-threaded CPU-bound workload needing CPU time C under cgroup bandwidth control (period P, quota Q=fP), the actual wall-clock duration is:

d = floor(C/Q)·P + (C mod Q)         # if C mod Q ≠ 0
d = (floor(C/Q) − 1)·P + Q          # if C mod Q = 0

When C ≤ Q — the common case for millisecond bursts under fractional shares — this collapses to d≈C, far below the resource contract d* = C/f. The overallocation ratio R = d*/d quantifies the gap.

2 · The grant cap, gc(t)

μslice tracks, per paced cgroup, an anchor time a (epoch start) and delivered service S. At wall-clock time t, the contract permits at most f(t−a) total service. A grant g is compliant only if S+g ≤ f(t+g−a), which solves to the largest allowable grant:

gc(t) = max(0, (f·(t−a) − S) / (1 − f))

The pacer targets an eligibility quantum ge (base 250 μs, capped by max quantum gr=8 ms) and computes the earliest release time r = a + ceil((S + ge·(1−f)) / f). If r is in the future, the task is parked in a paced DSQ with virtual time r and a BPF timer is armed; if r has passed, it's eligible immediately. Under contention, low-share tenants (f≤0.3) coarsen to ge=gr=1 ms to cut scheduling overhead.

3 · Enforcement at run time

When a paced task starts running, the pacer computes slice g = min(gc(t), gr). If dispatch was delayed by τ past r, the task can "catch up" to a larger grant gc(r+τ) ≈ ge + f/(1−f)·τ — but if gc(t) < ge, the pacer reparks the task rather than overallocate. On stopping, elapsed runtime updates S in cg_runtime; on quiescent, transient state is cleared.

4 · Overload bypass — protecting against pacing backlog

μslice maintains an event-driven count of actively-paced workloads. Past an activation threshold of 500, admitted cgroups fall back to the work-conserving path; pacing resumes only after the count stays below a recovery threshold of 400 for a 30 ms hold-down window. This is a local pressure signal, not a full load model — the controller can combine it with external metrics for system-wide bypass decisions under heavy load.

💡
Why bypass rather than queue forever? At high density, precise pacing itself becomes the bottleneck (queuing delay dominates). Falling back avoids an unbounded pacing backlog — the paper shows R and dispatch behavior converging back toward the commodity scheduler as density rises past ~700 tenants.

Follow the numbers

Worked examples

Four traces from the paper's own figures: computing R by hand, deriving a release time, walking the overload bypass, and tallying overhead.

① Computing the overallocation ratio by hand

A single-threaded request needs C=5 ms, configured at f=0.05, under Linux's default P=100 ms. What's R?

  1. Quota: Q = f·P = 0.05 × 100 ms = 5 ms.
  2. Since C ≤ Q, the request finishes at full-core speed within one period: d ≈ 5 ms.
  3. Contract: d* = C/f = 5 / 0.05 = 100 ms.
  4. R = d*/d = 100 / 5 = 20× — the request received 20× the CPU service rate its configured 0.05 share implies.
🍯
This is the paper's own headline example (§2.3). μslice would instead pace this request to finish near d*=100 ms, keeping R within ~0.98–0.99 of the ideal.

② Deriving an earliest release time from gc(t)

At the start of a pacing epoch (S=0), with f=0.1 and the base eligibility quantum ge=250 μs, when is the first grant allowed to release?

  1. Formula: r = a + ceil((S + ge·(1−f)) / f).
  2. Plug in: S=0, ge=0.25 ms, f=0.1 → (0 + 0.25×0.9) / 0.1 = 0.225 / 0.1 = 2.25 ms.
  3. So r = a + 2.25 ms — even though the granted quantum is only 0.25 ms, the request must wait 2.25 ms of wall-clock time before that grant is compliant.
  4. Why the wait is longer than the quantum: at low f, a small grant represents a disproportionately large fraction of the allowed service rate, so more wall-clock time must elapse to "earn" it.
💡
This is exactly how μslice avoids Trap ①: a low-f cgroup can't front-load its quantum — it must wait proportionally longer between grants, which is what makes d track d*=C/f.

③ Walking the overload bypass as density rises

Using the paper's stress test (C=5 ms, f=0.05, varying tenant count K), trace what happens to mean R.

  1. K ≤ 500: mean R tightly bounded between 0.987 and 0.990 — pacing works cleanly, bypass inactive.
  2. K = 600 tenants: mean R dips to 0.962 — dispatch-capacity contention starts to bite even though the 500-count bypass threshold (which tracks actively-paced workloads in the scheduler, not the total tenant count K) hasn't triggered a policy change yet.
  3. K ≥ 700: the system converges toward the commodity scheduler's behavior as bypass activates more often.
  4. K = 800: overload bypass is used for 48% of requests. K ≥ 900: 99% of requests bypass pacing.
🍯
Insight: the fallback is gradual, not a cliff — μslice degrades toward commodity scheduling as density rises, rather than accumulating an unbounded pacing backlog.

④ Tallying measured overhead at K=500

Is the pacing machinery actually cheap relative to millisecond-scale requests?

  1. Pacer path latency: timer, dispatch, and handoff paths add 50.3 μs per request on average (p99 = 78.6 μs) — the wall-clock cost of the pacing mechanism itself.
  2. Extra kernel time: 207.33 μs per request on average, relative to the Q=1ms EEVDF baseline — a separate measurement folding in broader scheduling/context-switch overhead; it is not additive with the pacer-path number above.
  3. Bottom line: both figures are small next to the 1–10 ms C values the paper targets, even considered independently.
  4. Context switches: +6.77% at the workload level, +20.53% system-wide, vs the Q=1ms baseline.
  5. Memory: BPF maps use ~0.43 MB for 1000 managed workloads — ≈430 bytes/workload.
💡
The dominant remaining gap from ideal completion time is platform wakeup/scheduling latency under contention (avg dispatch queue delay 0.90 ms at K=500) — not the pacer's own compute cost.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it's checking.

Problem 1 · easy
C=5 ms, f=0.1, P=100 ms. Compute Q, then R, without running μslice.
Show answer
Q=f·P=10 ms ≥ C, so d≈C=5 ms. d*=C/f=5/0.1=50 ms. R=d*/d=50/5=10×.Misconception: that staying under quota per period means complying with the fractional rate. Compliance with the quota ≠ compliance with the rate f.
Problem 2 · easy
True or false: shrinking the cgroup period to 2 ms eliminates overallocation entirely.
Show answer
False. The paper reports 11–33% overallocation even at 2 ms/5 ms periods, and Linux's 1 ms minimum quota floor (fP≥1ms) narrows which small f values are even valid at fine periods.Misconception: that finer period granularity alone solves quantized enforcement. A hard minimum-quota floor still limits how small P can usefully go.
Problem 3 · medium
Using gc(t)=max(0,(f(t−a)−S)/(1−f)), explain why gc shrinks toward 0 as S catches up to f(t−a).
Show answer
The numerator f(t−a)−S is the remaining allowed service budget; as delivered service S approaches the allowance f(t−a), the numerator — and hence gc — shrinks to zero, meaning no further grant is compliant until more wall-clock time elapses.Misconception: that pacing throttles based on absolute CPU time consumed. It throttles relative to elapsed wall-clock time scaled by f — a moving target, not a fixed budget.
Problem 4 · medium
Why do low-share tenants (f≤0.3) switch to ge=gr=1 ms under contention instead of keeping the default 250 μs/8 ms?
Show answer
Coarser quanta reduce timer, dispatch, and context-switch churn per unit of delivered service when ≥2 cgroups are waiting or no CPU is idle — trading finer-grained pacing accuracy for lower scheduling overhead exactly when overhead matters most.Misconception: assuming μslice always uses the smallest possible granularity for best accuracy. It adapts granularity to contention to bound its own overhead.
Problem 5 · medium
Why does the work-conserving CPU Weight baseline behave similarly to P=100ms in the overallocation experiment?
Show answer
CPU Weight has no hard cap, so a 5 ms burst runs instantly; P=100ms's period is long enough that a short burst never nears exhausting its quota either — both effectively let the request run at full-core speed.Misconception: that "work-conserving" and "period-capped" are fundamentally different regimes. For bursts much shorter than P, a long period behaves like no cap at all.
Problem 6 · hard
μslice's mean R dips to 0.962 at K=600 tenants — well above the 500-count bypass threshold — yet the paper still reports this as a regime where explicit bypass hasn't kicked in. Why doesn't the threshold catch it?
Show answer
The 500/400 bypass thresholds count actively-paced workloads inside the scheduler, not the total tenant count K used to parameterize the experiment — so K=600 tenants doesn't automatically mean the internal counter has crossed 500. Meanwhile, rising tenant density already strains the server's practical dispatch capacity, so queuing/dispatch delay degrades pacing accuracy before the bypass policy itself changes.Misconception: that K (the experiment's total tenant count) and the bypass mechanism's internal actively-paced-workload counter are the same number. Real contention can erode accuracy even while the explicit bypass counter stays below its trigger.
Problem 7 · hard
μslice adds +6.77% context switches at the workload level but +20.53% system-wide vs the Q=1ms baseline. Why is the system-wide number so much larger?
Show answer
Pacing adds context switches via cross-CPU bookkeeping — timer firings, scx_bpf_kick_cpu wakeups, and dispatch across many cores — that show up in the system-wide total but aren't attributed to any single tenant's own switch count.Misconception: that scheduler overhead is purely per-tenant. A scheduling-class mechanism has system-wide coordination cost on top of each workload's own cost.
Problem 8 · easy
Would μslice meaningfully help a workload with C=50 ms and f=0.9?
Show answer
Barely. At high f and larger C, the quota is more likely to be exhausted within a period, so the workload already approaches steady-state throttling and R is already close to 1 even under commodity baselines (Fig. 3 converges near f=1).Misconception: that μslice uniformly helps all workloads. Its benefit concentrates where period-level quota availability creates the largest gap — short C, small f.
Quick answers

Frequently asked questions

Ten questions newcomers ask most.

Q1Why does a compliant cgroup still "overallocate"?▾
Because the quota is enforced per period, not continuously. A short request that fits entirely within one period's quota finishes at full-core speed, never triggering throttling, even though its configured share f implies a slower rate over the request's own duration.
Q2Doesn't shrinking the period (e.g. Q=1ms baseline) fix it?▾
It helps but doesn't eliminate the effect — the paper measures 11–33% residual overallocation even at 2–5 ms periods — and Linux's 1 ms minimum quota caps how small P can go for a given f, narrowing the valid fractional-allocation space.
Q3What does μslice change that Q=1ms doesn't?▾
Q=1ms still enforces at a fixed quota/period granularity; μslice instead paces every grant against a continuously-tracked service contract gc(t), so it adapts to exactly when and how much a task has run rather than a coarse per-period cap.
Q4How does μslice decide exactly when to release a grant?▾
It computes the earliest wall-clock time r at which the next eligibility quantum ge would remain compliant with gc(t), parks the task in a release-time-ordered dispatch queue until then, and arms a BPF timer to wake the CPU at or after r (actual wakeup is subject to scheduler/dispatch latency).
Q5Why build this as a BPF scheduler instead of patching CFS?▾
sched_ext lets a verified BPF program implement scheduling policy without a kernel fork or patch, so μslice can be deployed, updated, and iterated on commodity kernels while complementing (not replacing) existing bandwidth control.
Q6Does pacing add unbounded latency under heavy load?▾
No — an overload bypass mechanism tracks the count of actively-paced workloads and reverts admitted cgroups to the work-conserving path once it exceeds 500, recovering only after it stays below 400 for a 30 ms hold-down window.
Q7Does μslice make short requests faster?▾
No — by design it's the opposite of a speedup. It removes the "free" excess service a request was getting beyond its configured share, so completion time moves closer to (typically increases toward) the C/f contract. The payoff is predictability and fairness, not lower latency.
Q8What workloads are out of scope?▾
Long-running or I/O-dominant requests (where period-level averaging already works fine), workloads with CPU bursts interleaved with substantial I/O, and multi-concurrency or multithreaded instances — the current design assumes single-concurrency execution, matching the paper's controlled setup (AWS Lambda, Google Cloud Run functions 1st gen, Huawei's default configuration, etc.). Note plain Cloud Run *services* can serve concurrent requests per instance, so not all Google Cloud Run deployments fit this single-concurrency model.
Q9How expensive is μslice to run?▾
At K=500 managed workloads: ~50.3 μs pacer-path latency and ~207.33 μs extra kernel time per request on average (two separate measurements), +6.77%/+20.53% context-switch rate (workload/system-wide), and ~430 bytes of BPF-map memory per managed workload.
Q10Does it change the cgroup interface or billing model?▾
No — μslice preserves cpu.max/cgroup semantics and the configured share f; it adds a pacing layer underneath. The paper argues this makes effective CPU service (and therefore allocation-based billing) actually match the configured contract, rather than requiring corrective fixed per-request charges.
