Persistent Memory Verification · A Field Guide

The order stores actually land in — proven safe, not just tested

Write-back caches commit stores to non-volatile memory in whatever order the cache coherence protocol likes — not the order your program wrote them. This paper turns "did my program survive every possible crash?" into a graph-cycle question an SMT solver can answer, with no test inputs and no user annotations.

📄 Han & He, Tsinghua · ASPLOS'25 💾 Intel-x86 NVM · PMDK pmemobj benchmarks 🎓 Assumes memory consistency models & SAT/SMT basics ⏱ ~40 min read
🔁

A program is robust iff every non-volatile state a crash could leave behind is also a state reachable by simply running the program forward, crash-free, under x86-TSO — turned into a graph-cycle check, this lets you verify crash consistency without ever executing the program.

Before you begin

Nine ideas this paper builds on

You know DRAM/NVM tiering and the Linux memory stack; this paper lives one layer down, in formal concurrency/persistency semantics and SMT-based verification. These primers build the ladder from "NVM stores commit out of order" up to "an SMT solver can prove that's safe." Tap any open; read in order the first time.

1Why NVM stores land out of order — the crash gap▾

Intel-x86 NVM systems use a three-layer hierarchy: instructions issue to a thread-local store buffer, propagate to a global persistent buffer (the write-back caches — still volatile!), and only later get committed to NVM. A store becomes visible to other threads when it leaves the store buffer, but it isn't persistent until it leaves the cache — two different moments, two different orders.

The paper's running example: a single thread executes a = 1; b = 1; then the system crashes. Upon recovery it is entirely possible to observe a = 0; b = 1 — the later store (b) persisted while the earlier one (a) was still sitting in a volatile cache line when power was lost.

Now you're ready: "persist order" (nvo) and "visibility order" (hb) are two separate orders over the same stores, and NVM's whole correctness problem lives in the gap between them.
2Flush/fence instructions, and x86-TSO in one page▾

To constrain persist order, Intel-x86 gives you three cache-line write-back instructions: clflush (strongest — reorders only with earlier loads), clflushopt and clwb (weaker — can reorder with stores/flushes to other cache lines; clwb additionally keeps the line cached instead of invalidating it). Two fences tighten ordering further: mfence (total barrier) and sfence (still lets later loads slip ahead).

Visibility order itself is governed by standard x86-TSO: a global happens-before order hb over events, built from preserved program order ppo (program order minus the one relaxation x86 allows — a store or flush can be reordered after a later read), plus cross-thread reads-from (rfe), a per-variable coherence order (co), and the derived from-read order (fr). An execution is valid iff hb = (ppo ∪ rfe ∪ co ∪ fr)⁺ is acyclic.

Now you're ready: everything the paper calls "valid" or "reachable" reduces to acyclicity of some such hb-like graph. That's the computational core the whole method rides on.
3Persist order (nvo) and "reachable non-volatile state"▾

Definition 1 (Persist Order). Given a fixed visibility order, the persist order nvo is a total order over all stores and flushes satisfying two axioms: (1) it agrees with visibility order between stores to the same variable; (2) if a store is visibility-ordered before a flush to the same variable, it must persist before any store visibility-ordered after that flush.

At any moment only a prefix of nvo has actually persisted; if a crash hits there, the surviving prefix induces a non-volatile state (last-persisted value per location). If that prefix contains all flush events, the state is called a reachable non-volatile state — a legitimate thing a crash could leave behind.

Now you're ready: "which non-volatile states are reachable" is a question about nvo-prefixes, and it's the object the whole verification problem is quantifying over.
4Crash consistency vs. Robustness — why decouple them▾

Crash consistency says: from whatever state a crash leaves behind, the program can resume correctly (no crashes, no corruption). Checking that directly needs to reason about a huge space of crash points, and most prior tools (XFDetector, PMTest, PMDebugger) require developers to hand-annotate commit variables or ordering constraints to avoid false alarms.

Robustness (Gorjiara et al., PLDI'22, adapted here) sidesteps annotation entirely: Definition 6 — a program is robust iff every reachable non-volatile state is also reachable by some ordinary (crash-free) execution under x86-TSO. If so, crash consistency reduces to the well-studied problem of proving the program correct under weak memory consistency — no reasoning about crashes required at all.

Now you're ready: robustness is a bridge: prove it once, and you may reuse any existing x86-TSO correctness verifier unmodified. (Note: this paper's Definition 6 is deliberately reformulated from the original PLDI'22 definition, which used strict persistency instead of state-reachability — Primer 9 of the FAQ picks this up.)
5Event Order Graphs (EOG) — the formal substrate▾

An execution is represented as an EOG G = (E, E₀, po, rf): a set of events (reads R(x,v), writes W(x,v), flushes FL(x), fences F), initialization events E₀, program order po (total per thread), and reads-from rf (which write a read observes). From these, coherence order co (a per-variable total order over writes) and fr = rf⁻¹;co are derived, and hb is built as in Primer 2.

This is the same declarative-semantics toolkit used across the weak-memory verification literature — it's what lets "is this execution valid" become "is this specific graph acyclic," a problem with decades of efficient tooling behind it.

Now you're ready: every later construction (recovery observer, dtpo, DPTSO) is just more relations added to an EOG, checked for cycles the same way.
6The Recovery Observer — a hypothetical crash camera▾

To enumerate candidate post-crash states, the paper instruments the program with a virtual extra thread Pᵣ — the recovery observer — containing one read per shared variable, deliberately left unordered with everything else (including with each other). As the observer's reads interleave with the real threads in every possible way, they sweep through every possible combination of "last surviving value per variable."

The projection of rf onto the observer's reads is written rrf (recovery read-from), and it directly induces an observed non-volatile state s₀: whatever the observer's read of x saw becomes s₀(x).

Now you're ready: the recovery observer turns "enumerate all crash states" into "enumerate all ways an extra unordered thread could read" — a search problem the same machinery from Primer 5 already handles.
7dtpo & DPTSO — turning a crash question into a cycle check▾

The central trick: reachability of a post-crash state under Px86 (the formal x86 persistency model) is known to be decidable but no algorithm was known for it. The paper reduces it to validity-checking instead, via a derived order dtpo (from Khyzha & Lahav's DPTSO): if the observer's read rrf saw an old value w′, then any flush on that variable must be ordered before every store that is coherence-ordered after w′ — otherwise that later store should have persisted, overwriting what the observer saw.

Theorem 1: for an execution valid under x86-TSO, the observed state s₀ is reachable under it iff the execution is valid under DPTSO (x86-TSO's hb plus dtpo edges) — i.e., iff hb ∪ dtpo stays acyclic.

Now you're ready: "is this a real crash state" is now the exact same kind of question as "is this a valid execution" — just with one extra relation (dtpo) added to the graph.
8Partial executions and the search algorithm▾

A crash can happen mid-flight, before every event has even propagated — so the algorithm must reason about partial executions: prefix-closed subsets of events (per po ∪ rf) rather than the full event set. Algorithm 1 explores all partial (instrumented) executions G; whenever consDPTSO(G) holds, it further checks whether some "alternation" of G (same events, same rrf, but other reads-from possibly rearranged) is valid under plain x86-TSO. If none is, a robustness violation is reported. If consDPTSO(G) fails, the algorithm prunes — blocking every expansion of G, since adding more ordering constraints can't resurrect an already-invalid execution.

Now you're ready: the search is exhaustive but prunable — the DPTSO check is a cheap first filter before the more expensive x86-TSO reachability check ever runs.
9SMT encoding & DPLL(T) — why it still hits state explosion▾

The prototype PMVerify instantiates Algorithm 1 by encoding the program (in SSA form) plus Boolean variables for every ordering relation (enabled(e), coherence ws, reads-from rf) into one SMT formula, solved via the DPLL(T) framework: a SAT solver proposes an assignment, and a dedicated theory solver checks it against ordering-consistency theory (essentially an incremental cycle detector), returning conflict clauses that prune the search.

This is far more efficient than brute-force enumeration of executions — but it is still, ultimately, an exhaustive search over an exponential space. Keep that in mind for the Worked Examples and Practice tabs, where you'll see runtimes measured in thousands of seconds even on small (500-LOC-scale) programs.

Now you're ready: you have the full pipeline — visibility order → persist order → recovery observer → dtpo/DPTSO → search → SMT encoding. The rest of this guide fills in each stage with the paper's own figures and numbers.
The whole story in one place

Robustness verification in a nutshell

The crash-order problem, the reduction that makes it tractable, the search algorithm, and what the evaluation actually found.

NVM devices are byte-addressable and persistent, but the caches that sit in front of them are not: a crash can lose any store still sitting in a volatile write-back cache. Because persist order (when stores actually reach NVM) can differ from visibility order (when they become visible to other threads), a crash can expose a state that never "made program sense" — like observing a=0;b=1 after a=1;b=1 ran to completion. Developers are supposed to insert clflush/clflushopt/clwb/fences to prevent this, and getting it wrong is exactly the kind of error most existing detection tools need hand-written annotations to catch.

Robustness reframes the problem: instead of asking "is every post-crash state correct," ask "is every post-crash state one that could have arisen anyway, from a normal crash-free run?" If yes, the program is robust, and crash-consistency checking collapses into ordinary weak-memory-consistency checking — a problem with mature tooling. The paper's technical core is showing that reachability of a post-crash state — a genuinely hard question about persist orders — can be reduced to validity of an execution under an augmented model, DPTSO, that simply adds one extra derived ordering relation, dtpo, to the familiar x86-TSO graph. A recovery observer (a virtual thread of unordered reads) is used to enumerate every candidate crash state in the first place.

Algorithm 1 wraps this into a search: explore partial executions; cheaply filter with the DPTSO cycle check; only for survivors, run the more expensive x86-TSO reachability check across "alternations" of the same execution; report a robustness violation the moment a state is found reachable by the crash but by nothing else. The whole thing is implemented as a dedicated theory solver inside a DPLL(T) SMT framework, in a prototype called PMVerify (built on the Deagle verifier and the CBMC bounded model checker).

The result: on 26 PMDK pmemobj example programs, PMVerify detected 12 robustness violations — 6 more than the dynamic tool PSan found — and proved one program (and, after manual instrumentation, six more) fully robust, something no dynamic tool can ever do. The cost is verification time measured in tens of minutes to hours per program, versus PSan's seconds — a soundness/speed tradeoff that's the recurring theme of the Worked Examples tab.

🍯 Key takeaways

  • The gap: persist order (nvo) and visibility order (hb) over the same stores can legitimately disagree — that gap is the entire NVM crash-consistency problem.
  • Robustness (Def. 6): a program is robust iff every reachable non-volatile state is also reachable under x86-TSO — no user annotation needed.
  • The reduction (Thm. 1): checking if a crash state is reachable ⟺ checking if the execution, augmented with a derived order dtpo, stays acyclic (consDPTSO).
  • The trick that makes states enumerable: a recovery observer — a virtual thread of unordered reads — turns "which crash states exist" into "which reads-from assignments exist."
  • Search (Algorithm 1): explore partial executions, prune on DPTSO failure, escalate to x86-TSO reachability only on survivors, report violation only if no alternation is x86-TSO-valid.
  • Implementation: SSA + Boolean ordering encoding, solved via DPLL(T) with a dedicated ordering-consistency theory solver — prototype tool PMVerify, built atop Deagle/CBMC.
  • Headline result: 12 violations found (vs. PSan's 6) across 26 PMDK programs, plus 7 robustness proofs that no dynamic tool could produce — at a real cost of ~46 minutes average runtime per program.
Six everyday pictures

How to think about robustness verification

Each picture stands alone — read in any order. Every card ends with an honest note about where the analogy stops being true.

The core gap · Persist vs. visibility order

Announcing news vs. archiving it

A newsroom announces a story the moment a reporter files it (visible instantly). The archive department files the physical copy on its own schedule, sometimes hours later, in whatever order the filing clerk gets to it. If the building loses power before the archive catches up, you can find yesterday's late-breaking story filed, but this morning's "confirmed" story missing — the announcement order and the archive order aren't the same order at all.

Where it breaks: a real archive filing is unordered chaos; the paper's persist order (nvo) is a genuine total order constrained by two strict axioms (Definition 1) — it's not arbitrary, just different from visibility order.
The instrumentation · Recovery Observer

A security camera with amnesia between frames

Imagine a camera that can snap a photo of every shelf in a warehouse simultaneously, at any instant you choose — but each snapshot is independent, unordered with respect to every other snapshot or event. Take enough snapshots at enough different instants and you'll eventually capture every combination of "what was on which shelf." That's the recovery observer: an extra unordered thread that reads every shared variable, sweeping through every possible post-crash memory image via its rrf reads.

Where it breaks: a real camera doesn't need a search algorithm; enumerating every valid combination of the observer's reads-from assignments is exactly the expensive part Algorithm 1 has to search over.
The bridge · dtpo

The alibi that contradicts the timeline

A witness (the recovery observer) testifies they saw the old, unfiled version of a record. Detective logic says: if that's true, the record's later revision must have been filed strictly after your testimony's timestamp — otherwise you'd have seen the new version. Now suppose the case file's own timeline already says the revision happened before your testimony. Contradiction — the story can't be true. dtpo is exactly this logical constraint, made formal and checked for contradictions (cycles) automatically.

Where it breaks: detectives resolve contradictions with more investigation; the algorithm just declares the specific execution invalid and moves on — it doesn't (and doesn't need to) explain the contradiction in narrative terms.
The reduction · Theorem 1

Translating a hard puzzle into a familiar one

You can't directly tell whether a Sudoku-like arrangement has "a solution reachable by legal moves," but you can tell whether a graph has a cycle in linear time. Theorem 1 is a translation dictionary: it rewrites the hard, crash-specific question ("is this post-crash state reachable?") word-for-word into the easy, generic question ("is this graph, with one more relation added, acyclic?") — and proves the translation preserves the answer exactly.

Where it breaks: the translation itself required a real proof (both directions, Section 3.2) — it's not a free lunch, just a one-time investment that pays off every time the algorithm runs afterward.
The search discipline · Prefix-closed pruning

A train that can only ever be coupled from the front

A freight train's cars are coupled in order — you can never have car 5 attached without cars 1–4 already there. A "partial execution" is like a train halted mid-marshalling: whatever prefix of cars exists is complete and consistent, even though the rest never got attached. Algorithm 1 exploits exactly this shape: the moment a partial train (execution) is found already invalid, there is no point coupling on more cars — every longer train built from it inherits the same contradiction, so the search prunes the whole branch.

Where it breaks: real trains couple in one fixed order; the search here explores many different interleavings of the "cars" (events) across threads simultaneously — the prefix-closure is about causal order, not physical sequencing.
The engine · DPLL(T)

A quick guesser paired with a strict referee

One player rapidly proposes candidate answers (the SAT solver, working on a simplified Boolean version of the problem). A specialist referee — the ordering-consistency theory solver — checks each candidate against the real rules (do these orderings actually form a cycle?), and whenever the guesser is wrong, hands back a precise reason ("these three choices conflict") so the guesser never repeats that exact mistake. Back and forth, the search converges far faster than either player working alone.

Where it breaks: the guesser and referee in DPLL(T) share complete information at each round; human guess-and-check games rarely have such a crisp, complete "here's exactly why you're wrong" feedback channel.
Section by section

How robustness verification actually works

The persist/visibility split → formalizing validity → the recovery observer & dtpo → partial executions & the search → the SMT engine. Figures are rebuilt from the paper's own Figures 1–6.

1 · The persist/visibility split (Section 2.1)

Every store on this Intel-x86 NVM model passes through three layers: thread-local store buffer → global persistent buffer (write-back caches) → NVM. A store's visibility point (S) is when it leaves the store buffer; its persist point (P) is when it later leaves the cache and reaches NVM — a separate, independently-orderable event.

2 · Formalizing validity: EOG, ppo, hb, x86-TSO (Section 2.2)

Executions are Event Order Graphs G=(E,E₀,po,rf). Preserved program order drops exactly the one relaxation x86 permits: ppo ≜ {(e₁,e₂) ∈ po | e₁ ∈ W∪FL → e₂ ∉ R} — a store or flush may be reordered after a later read, but never a later write. Coherence order co (per-variable, total over writes) and from-read fr = rf⁻¹;co complete the picture. Definition 5: G is valid under x86-TSO iff some co makes hb=(ppo ∪ rfe ∪ co ∪ fr)⁺ irreflexive, and fr;po irreflexive (per-location coherence).

◆
Why this matters for everything downstream. "Valid execution" is now purely graph-theoretic: pick a coherence order, build hb, check for cycles. Robustness verification's entire strategy is to keep reusing this exact check, just with extra relations spliced in.

3 · The recovery observer & dtpo (Section 3)

The program is instrumented as P' = P ∥ Pᵣ, where Pᵣ has one read aₓ = x per shared variable x, deliberately unordered with everything (REC is never po-related to anything). The projected reads-from rrf = rf|(W×REC) induces the observed state s₀.

4 · Partial executions & the search (Section 4)

A crash can hit before propagation finishes, so the algorithm must search partial executions — prefix-closed (w.r.t. po ∪ rf) subsets of the full event set. Dropping flush x; a=y; x=a from Thread 1 above removes the only flush x event entirely, so no dtpo edge can target x at all — the paper shows this partial execution is valid under DPTSO, meaning x=0; y=1 genuinely is a reachable non-volatile state for that crash point.

// Algorithm 1 — Robustness Checking Framework (paraphrased)
input: program P running on NVM
output: whether P is robust

P' ← P ∥ P_r                         // instrument with recovery observer
while hasNext(P'):
  G ← next(P')                       // next partial instrumented execution
  if consDPTSO(G):               // cheap filter: is a crash state reachable here?
    for each G' ≃ G:              // alternations: same events & rrf, other rf may vary
      if consTSO(atomic(G')):     // expensive check: reachable under x86-TSO too?
        continue outer loop       // fine — keep exploring
    return false                    // no alternation valid ⇒ ROBUSTNESS VIOLATION
  else:
    block({G'' | G ≺ G''})           // prune: nothing built on an invalid G can be valid
return true                        // exhaustive, no violation ⇒ ROBUST (Theorem 2)
◇
atomic(G′) (Definition 9). To check reachability under plain x86-TSO, the observer's REC reads are collapsed into one atomic fresh event eᵣ that inherits their combined reads-from — effectively treating "read the whole memory at once" as instantaneous, exactly as the recovery-observer idea originally intended (Section 3.1).

5 · The SMT engine: DPLL(T) (Section 5)

The program is compiled to SSA, and every ordering relation becomes a Boolean variable: enabled(e) (is event e in this partial execution), wsⁱⱼˣ (coherence order between stores i,j on x), rfⱼᵢˣ (read i takes its value from store j). Axioms tie these together (e.g. ws must be a total order over enabled stores; rf must match the value read; enabled must respect ppo-prefix-closure), plus derived rules for fr and dtpo.

●
Where the runtime actually goes. None of this changes the underlying complexity — Boolean encoding plus DPLL(T) makes the search dramatically more efficient than brute-force enumeration, but the space is still exponential in program size. That's the direct explanation for the multi-thousand-second runtimes in the next tab.

Worked examples

Three calculations using the paper's own examples and evaluation tables, plus an interactive widget for the dtpo cycle mechanism. All arithmetic below is recomputed from the paper's stated figures.

Example 1 — why a=0;b=1 is non-robust (Section 1's opening example)

Single thread: a = 1; b = 1;, both a,b shared, initial value 0. Suppose a crash exposes a=0; b=1.

  1. Is it a plausible crash state? Yes — Section 1 states this directly: persist order can differ from visibility order, so store b=1 can persist while a=1 is still sitting in a volatile cache line.
  2. Is it reachable under x86-TSO (crash-free)? Per Table 1, write→write pairs in program order are always preserved (✓, cannot reorder). So any crash-free execution must make a=1 visible strictly before b=1 — the coherence/hb order can never place b's write before a's. A state with b=1 visible while a is still 0 is therefore impossible under ordinary x86-TSO execution.
  3. Conclusion (Definition 6): a reachable non-volatile state (a=0;b=1) is not reachable under x86-TSO ⇒ the program is non-robust, exactly as the paper states.
◆
Takeaway: robustness violations are precisely the crash states that "shouldn't be possible" by ordinary program logic — which is exactly why they're the dangerous, easy-to-miss bugs that motivate this whole line of work.

Check yourself

Practice

Work the answer before opening it. Each answer ends with the misconception the question is designed to catch.

Warm-up
Why does the paper need a separate persist order (nvo) in addition to the ordinary visibility order (hb), instead of just reusing hb for everything?
Show answer
Because they can genuinely differ: a store can become visible to other threads (leave the store buffer) while still sitting in a volatile write-back cache, not yet persisted to NVM. Definition 1 constrains nvo to agree with hb only for same-variable stores and around flushes — everywhere else, the two orders are free to diverge, which is exactly the source of NVM's crash-consistency bugs. Catches: assuming "ordered" is a single, universal notion. On NVM there are (at least) two independently-meaningful orders over the same events, and conflating them hides real bugs.
Diagnose
In the two-thread example (Figures 2–4), why does removing flush x; a=y; x=a from the partial execution make x=0;y=1 reachable, when the full execution proved it wasn't?
Show answer
dtpo is only generated from enabled flush events (enabled(FL_x) is a precondition in the definition). Dropping flush x from the partial execution removes the only source of a dtpo edge on x — with no dtpo edge, there's nothing to contradict program order, so consDPTSO holds and the state is a genuine reachable non-volatile state (Figure 4). This is exactly the real-world scenario it represents: the crash hit before that flush (and everything after it) ever propagated. Catches: thinking robustness violations are properties of a whole program in isolation. They're properties of specific (partial) executions — the very same program can have both robust and non-robust crash points depending on how far execution got.
Diagnose
Table 2 shows PMVerify's average runtime (2768.42s) is roughly 166× PSan's (16.7s) by direct division, yet the paper's prose claims PSan is "on average 33 times shorter." Is this a contradiction the tools disagree on, or something else?
Show answer
Almost certainly a subset mismatch, not a real contradiction: PMVerify's 2768.42s is averaged over the 13 cases it solves, while PSan's 16.7s is averaged over the 6 cases it solves — different, non-identical sets of programs with presumably different intrinsic difficulty. The paper's "33×" claim is most plausibly computed over a common comparison set (e.g., the 6 cases PSan solves), which this guide cannot fully reconstruct from the published tables alone. Catches: dividing two averages computed over different populations and treating the ratio as meaningful without checking what each average is actually averaging over.
Design
Table 4's instrumented (flush-after-every-store) programs are strictly larger in event count than the originals, yet PMVerify's average runtime on the 6 it solves (4734.15s) is only about 1.7× the original average (2768.42s), not exponentially worse. Why doesn't the added instrumentation blow up the search?
Show answer
Two effects roughly cancel. Adding a flush after every store increases the raw event count and search space (more redundancy). But it also shrinks the set of reachable non-volatile states, because stronger ordering constraints leave fewer valid partial executions to explore — and since PMVerify checks consDPTSO (the cheap filter) before ever reaching the expensive x86-TSO reachability check, many candidate states are pruned early. The paper reports this explicitly: heavier instrumentation trades a larger search space for fewer states surviving the first, cheap filter. Catches: assuming "more instructions in the program" always means "proportionally more verification cost." The cost is driven by the number of reachable states that survive filtering, not raw program size alone.
Design
The paper notes robustness is only a sufficient, not necessary, condition for crash consistency, and that it may be "over-strong," disallowing benign programming idioms. Sketch a scenario where a program could be crash-consistent but still fail the robustness check.
Show answer
Robustness demands every reachable non-volatile state also be reachable under ordinary crash-free execution — a state-level guarantee. A program could instead be written so that any post-crash state it can produce, even an "unusual" one no crash-free run would reach, still leads to a correct, safe recovery routine (e.g., a recovery handler that explicitly re-derives or re-validates the value rather than trusting it blindly) — this can be crash-consistent by construction without being robust by Definition 6. The paper cites this exact concern (referencing Margalit & Lahav's weaker robustness notions) as future work. Catches: treating "robust" and "crash-consistent" as synonyms. Robustness is a convenient, fully-automatable proxy for crash consistency, not a redefinition of it — the paper is explicit that robustness is sufficient, not equivalent.
Loose ends

Frequently asked

The questions that come up once the mechanism clicks.

QIs this the same "robustness" definition Gorjiara et al. (PLDI'22) introduced?▾
Related but explicitly reformulated. The original PLDI'22 definition is stated in terms of strict persistency — the strongest persistency model, where any recovered state must be an observable volatile state. This paper's Definition 6 (Footnote 1) instead defines robustness directly via reachability of the recovered non-volatile state under x86-TSO, which is what makes the dtpo/DPTSO reduction possible.
QWhy not just enumerate persist orders (nvo) directly instead of reducing to DPTSO?▾
A naive approach — enumerate all persist orders consistent with the two axioms of Definition 1, then check each prefix against the observed state — is correct but redundant and inefficient; even pruned by the axioms it remains impractical. The paper's insight is that only the last persisted stores and the ordering constraints they induce (dtpo) actually matter for reachability, collapsing an enumeration problem into a single acyclicity check (Theorem 1).
QIs DPTSO a real hardware persistency model, or an artifact of this proof?▾
DPTSO ("derived TSO propagation order," from Khyzha & Lahav, POPL'21) is a genuine prior formalism relating memory consistency and persistency, reused here as the target of the reduction — it is not invented for this paper. The actual hardware persistency model being respected throughout is Px86 (Raad et al., POPL'20).
QWhy build PMVerify on a bounded model checker (CBMC) if the goal is to prove robustness?▾
CBMC unrolls loops that aren't statically bounded, which the paper's own Limitations section acknowledges leaves the implementation incomplete for proving robustness in general (an unbounded loop can't be exhaustively unrolled). The authors note this is a limitation of the current prototype's exploration backend, not of Algorithm 1 itself — other exploration methods (Section 4) could, in principle, restore completeness.
QWhat does "UNKNOWN" mean in Table 2 — is it a false negative?▾
No — it means the tool neither proved robustness nor found a violation within the 2-hour timeout (or, for PMVerify, sometimes because the program uses PMDK primitives the frontend doesn't model, e.g. pmemobj_tx_add_range_direct). It's an honest "didn't finish," not a claim about the program's actual robustness.
QDoes this paper say anything about CXL-attached memory or OS-managed DRAM/NVM tiering?▾
No — this is the guide's own framing, not the paper's content. The paper is scoped entirely to Intel-x86's native persistency model (Px86/x86-TSO) for locally-attached NVM accessed via load/store/clflush-family instructions; it never discusses CXL, memory pooling, or tiering policy. If you work on OS-managed tiering, the connection worth drawing yourself is: any tiering layer that migrates "persistent-seeming" pages between DRAM and CXL-attached persistent memory inherits the same persist/visibility-order gap this paper formalizes — but validating that inheritance is outside this paper's scope and would need its own analysis.
QHow does PMVerify compare to Jaaru, the dynamic model checker PSan is built on?▾
Jaaru is PSan's underlying dynamic engine: it observes memory operations at runtime and checks the observed trace for persistency bugs, reducing search space by focusing on last-writes-per-location. PMVerify is static and symbolic (SMT-based) rather than dynamic — it can prove the absence of violations across all executions, which a dynamic, trace-sampling tool structurally cannot do, at the cost of far greater runtime.

Core terms
RobustnessA program is robust iff every reachable non-volatile (post-crash) state is also reachable under x86-TSO (Definition 6) — the paper's central correctness property.
Persist order (nvo)A total order over all stores and flushes, distinct from visibility order, satisfying the two axioms of Definition 1; governs what actually reaches NVM.
Visibility order (hb)The x86-TSO happens-before order over memory events: (ppo ∪ rfe ∪ co ∪ fr)⁺, required to be irreflexive for a valid execution.
Recovery observer (P_r, REC)A virtual, unordered thread instrumented into the program with one read per shared variable, used to enumerate candidate post-crash states via its reads-from relation rrf.
dtpoA derived ordering relation: a flush on x must precede any store to x that is coherence-ordered after the store the observer's rrf read — the bridge in Theorem 1.
DPTSOx86-TSO augmented with dtpo (Definition 8, from Khyzha & Lahav); an execution's validity under DPTSO is equivalent to reachability of its observed state (Theorem 1).
Event Order Graph (EOG)G=(E,E₀,po,rf) — the declarative representation of an execution that all later relations (co, fr, hb, dtpo) are built on top of.
Partial executionA prefix-closed (w.r.t. po∪rf) subset of a program's full event set, modeling a crash that hits before propagation finishes.
Supporting terms
ppoPreserved program order — program order minus the one x86 relaxation: a store/flush may be reordered after a later read.
co / frCoherence order (total order per variable over writes) and from-read (rf⁻¹;co), the two derived relations used to build hb.
s₀The non-volatile state observed via rrf: for each variable x, the value the recovery observer's read of x saw.
Alternation / expansion (G′≃G / G≺G′)Alternation: same events & rrf, other rf may differ. Expansion: a strict superset of events and rf. Both drive Algorithm 1's search and pruning.
DPLL(T)SMT framework pairing a SAT solver (over a Boolean skeleton) with theory solvers that check background-theory consistency and return conflict clauses.
PMVerifyThis paper's prototype tool, built by extending Deagle (an SMT-based weak-memory verifier atop the CBMC bounded model checker) with a robustness-checking theory solver.
PSan / JaaruPSan (Gorjiara et al., PLDI'22) is the only prior robustness-violation detector, built on Jaaru's dynamic model checking engine; used as PMVerify's evaluation baseline.
PMDK pmemobjIntel's Persistent Memory Development Kit object-store library; its 26 bundled example programs form the paper's evaluation benchmark (avg. 548 LOC).

📌 Summary card · as of 2026-08-30 · ASPLOS'25

  • What: a fully-automated, static method to verify robustness — a sufficient condition for NVM crash consistency — with no user annotation.
  • Why it's hard: persist order (nvo) and visibility order (hb) over the same stores can legitimately differ, letting a crash expose "impossible" states.
  • The core reduction (Theorem 1): reachability of a post-crash state ⟺ validity under DPTSO (x86-TSO + the derived order dtpo) — a graph-cycle check.
  • The enabling trick: a recovery observer (unordered virtual thread of reads) enumerates candidate crash states via its reads-from relation.
  • The algorithm: exhaustively search partial executions, filter cheaply via consDPTSO, escalate survivors to an x86-TSO reachability check, report a violation only if no alternation is valid.
  • The engine: SSA + Boolean ordering encoding solved via DPLL(T) with a dedicated ordering-consistency theory solver; prototype tool PMVerify (built on Deagle/CBMC).
  • Headline numbers: 26 PMDK programs; PMVerify solves 13 (1 proved robust, 12 violations — 6 more than PSan's), avg. 2768.42s; on 12 manually-strengthened robust variants, proves 6, avg. 4734.15s.
  • Tradeoff: PMVerify is sound and can prove robustness; PSan is orders of magnitude faster but, being dynamic, can never prove absence of violations.
  • Known limitations: CBMC's bounded-loop unrolling makes the implementation incomplete; robustness itself may be too strong a property for some benign idioms.
