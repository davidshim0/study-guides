eBPF '26 (ACM) · A Field Guide

What the kernel JIT leaves on the table

eBPF code is safety-checked, then JIT-compiled — but how much bigger is that native code than if you'd just compiled it straight for x86? This paper builds the first fair yardstick to find out.

📄 Duong, Sun, Su · "Quantifying the Code-Size Overhead of eBPF JIT Compilation" 🎓 Some LLVM/compiler basics assumed — primers cover them ⏱ ~25 min read
⚖️

Compile near-identical source two ways — eBPF and native x86 — hold everything else equal, and the gap that's left is code-generation overhead, not a fact of life.
27.6% more instructions, 16.6% more bytes — almost all of it in the backend.

Before you begin

Quick glossary, then the concepts

The acronyms first, then eight short primers. Skip anything you already know.

eBPFextended Berkeley Packet Filter — a restricted bytecode users load into the Linux kernel; a verifier checks it, a JIT compiles it to native code.
JITJust-In-Time compiler — here, the in-kernel pass that turns verified eBPF bytecode into native x86 machine code at load time.
ISAInstruction Set Architecture — the fixed vocabulary of operations a CPU (or virtual machine like eBPF) supports.
LLVM / IRThe compiler framework used to build eBPF programs; IR is its target-independent intermediate form, shared by the frontend and midend.
DCEDead-Code Elimination — removing instructions/branches that can never execute or whose result is never used.
XDP / CNIXDP: eXpress Data Path, a fast eBPF packet-processing hook. CNI: Container Network Interface — Cilium plugs into Kubernetes as one.
CSECommon Subexpression Elimination — reusing an already-computed value instead of recomputing it; a backend optimization pass.
Spill / rematerializationSpill: writing a value to the stack because registers ran out. Rematerialization: recomputing a value instead of keeping it in a register.
1What eBPF actually is▾

eBPF lets you load small programs into the Linux kernel without recompiling it. Before anything runs, an in-kernel verifier statically checks the bytecode for safety — guaranteed termination, valid memory accesses — and only then does a JIT compiler turn it into real machine code that runs at full speed in kernel hooks like networking or tracing.

Now you're ready: this paper isn't about the verifier's safety rules — it's about how efficient the machine code is once the JIT is done with it.
2The LLVM pipeline: frontend, midend, backend▾

Clang (frontend) parses C into target-independent LLVM IR. Most optimizations (the midend, e.g. -O2) run on that IR and look similar across targets. The backend (llc) then lowers IR into architecture-specific machine instructions — this is where a target's real character shows up.

Now you're ready: the paper's central finding is that eBPF and native diverge almost entirely in this last stage, the backend.
3Why eBPF's ISA is restricted▾

eBPF deliberately has a small register set, limited instruction types, and no unrestricted memory access — this keeps the verifier's job tractable and the kernel JIT's attack surface small. But it also means the backend has fewer tools: no 8-bit compare, no fused address computation, fewer registers than x86-64's sixteen.

Now you're ready: some of the paper's overhead is genuinely forced by this restricted ISA; some is not — separating the two is the paper's core contribution.
4Configuration-dependent dead code▾

Projects like Cilium compile one program to serve many configurations, using volatile const globals that a loader patches just before load. Because they're volatile, the compiler can't fold them away — the dead branches they guard survive all the way into the bytecode, and only the verifier removes them, late, at load time.

Now you're ready: this is obstacle #2 the paper must neutralize — a native compiler would have deleted that dead code much earlier, which would otherwise make the comparison unfair.
5Verifier rewrites▾

After verification, the kernel sometimes rewrites the bytecode with extra instructions unrelated to your source logic — inlined bounds checks, runtime division checks. This is real behavior, but it would contaminate a code-generation comparison, so the paper disables it to isolate pure backend output.

Now you're ready: the paper's numbers measure code generation, not the verifier's safety machinery layered on top.
6Instruction count vs byte size▾

Two different rulers. Instruction count is simply how many machine instructions exist. Byte size is how many bytes they assemble to — and these can diverge, because some instructions (like leaq with a complex addressing mode) pack a lot into one instruction, while many small instructions (masks, zero-extends) can each be short.

Now you're ready: eBPF's 27.6% instruction gap and 16.6% byte gap aren't the same number for exactly this reason — it trades a few large native instructions for many small eBPF ones.
7Register pressure, spills, and rematerialization▾

A CPU has a fixed number of fast registers. When a compiler needs more live values than it has registers, it must spill one to the stack (slow) or rematerialize it (recompute it later instead of storing it). Both cost extra instructions. Fewer available registers means more of both.

Now you're ready: eBPF gives the backend only 11 usable registers vs x86-64's 16 — part of why its stack operations balloon by 120%.
8What a "fair baseline" requires▾

To compare two pipelines honestly, everything except the thing you're testing must be held equal: same source logic, same optimization level, same build flags. Differences in any of those would explain away the gap instead of isolating it.

Now you're ready: the paper's entire methodology (Section 3) is the work of engineering exactly this — a native x86 path that's identical to the eBPF path except at the backend.
The whole story in one place

A native baseline for eBPF code generation

The problem, the fair comparison that isolates it, and where the overhead lives.

eBPF programs are verified, then JIT-compiled to native code — but there was no clear reference point for how efficient that final code actually is. The paper builds one: compile nearly identical C source through both the standard eBPF pipeline (LLVM's eBPF backend → kernel JIT) and a native pipeline (LLVM's x86 backend directly), sharing the same frontend and midend so the two differ only in backend target.

Getting there cleanly required neutralizing three confounds: inline eBPF assembly that can't compile natively (replaced with size-matched x86 substitutes), configuration-dependent dead code that eBPF only removes late (forced to resolve identically in both pipelines), and kernel verifier rewrites that would otherwise inject unrelated instructions (disabled).

Applied to seven real Cilium datapath objects, the result is stark: the two pipelines are nearly identical through the frontend (<0.1% gap) and midend (+4.2%) — then diverge sharply in the backend, where eBPF emits 27.6% more instructions and 16.6% more bytes. That isolates the overhead almost entirely to code generation, not source logic or optimization level.

The paper then attributes that gap to recurring causes — ISA-bound (the eBPF instruction set genuinely lacks a compact form, e.g. no sub-32-bit ops, no fused addressing) vs pipeline-structural (the ISA has what's needed, the backend just doesn't use it, e.g. byte-wise memory copies, missing branch-folding passes) — with register pressure contributing to both.

🔑 Key takeaways

  • Frontend/midend agree almost exactly (<0.1% / +4.2%) — the divergence is backend-only (+27.6% instr / +16.6% bytes).
  • Byte size understates the gap relative to instruction count: eBPF trades a few large native instructions for many small ones.
  • Stack ops grow +120.4%, arithmetic +109.9%, logic/bitwise +103.3% — data movement, the biggest category, grows only +15.0%.
  • Split the causes: ISA-bound (needs a new eBPF instruction, e.g. no 8-bit compare, no leaq) vs pipeline-structural (needs a better backend, e.g. byte-wise copies, missing branch folding/CSE).
  • Register pressure is the crosscutting factor: eBPF has 11 usable registers vs x86-64's 16, but spills grow only ~50% while rematerializations grow >6×, so it's not purely register-count-forced.
  • The comparison held under two different dead-code-elimination timings, within a point of each other — the gap is robust, not an artifact.
Six everyday pictures

How to think about the eBPF backend gap

Each stands alone. Every card ends with where it stops being true.

The method · Fair comparison

A controlled experiment, not a guess

You don't learn whether a drug works by comparing treated patients to an unrelated population — you hold diet, age, dosage equal and change one thing. The paper does the same to code: near-identical source, same optimizer, same build flags, differing only in backend target. Whatever gap remains belongs to code generation, not confounds.

Where it breaks: native x86 is still an idealized comparator — it never has to satisfy the verifier or JIT safety constraints, so it's an upper bound on quality, not a target eBPF could fully reach.
The finding · Staged divergence

Two rivers from the same spring

Two rivers share a source and flow together through the same gentle terrain (frontend, midend) — indistinguishable until they reach a fork (the backend) where one is forced through a narrow, rocky channel. That's frontend <0.1%, midend +4.2%, backend +27.6%: nearly one river until the very end, then a sharp split.

Where it breaks: the "terrain" isn't fixed geography — the backend gap is largely a matter of engineering (better passes, ISA extensions), unlike a river's rocks.
ISA-bound overhead · Addressing

No express lane, only local roads

x86 has a single "express lane" instruction (leaq) that computes base + index×scale + offset in one step. eBPF has no such lane — it must take local roads: move, multiply, add, add again, four instructions to reach the same address. No amount of clever driving avoids it; the road itself is missing.

Where it breaks: not everything is a missing road — some "slow routes" (byte-wise copies) exist even though a fast lane (wide load/store) is already built. That's the next analogy.
Pipeline-structural · Byte-wise copies

Moving boxes one item at a time

You own a hand truck that can move a stacked pallet in four trips — but the mover insists on carrying items one by one, sixteen trips instead of four. Nothing stops the efficient move; eBPF's wide load/store exists, but the backend doesn't reach for it when copying a 16-byte struct (like an IPv6 address), rebuilding it byte by byte — 40+ instructions instead of 4.

Where it breaks: this one is pure backend immaturity, not an ISA limit — which is exactly why the paper calls it "recoverable within the existing ISA."
Crosscutting · Register pressure

A desk with fewer drawers

Two desks, one with 16 drawers, one with only 11. Both workers have similar piles of papers to keep handy, but the 11-drawer desk runs out sooner — papers spill onto the floor (spills) or get thrown out and rewritten from memory later (rematerialization) more often. Fewer drawers is a real constraint, but a messier worker with the same desk would spill even more.

Where it breaks: the paper finds spills grow only ~50% (roughly register-count-proportional) while rematerializations grow >6× — so "fewer drawers" alone doesn't explain it; some of the mess is avoidable.
Backend maturity · Missing late passes

Not taking the shortcut you already paved

Two hikers walk the same trail map. One spots a shortcut that skips a redundant switchback (branch folding, CSE) and takes it; the other, using an older map, walks the long way every time even though the shortcut exists. Native's backend applies branch folding 4,370 times and CSE 706 times; eBPF's applies them 345 and 94 times — the shortcuts exist, they're just rarely taken.

Where it breaks: this doesn't fully explain the gap either — even with every shortcut taken, the ISA-bound instructions (no compact addressing, no sub-32-bit ops) would still remain.
The full explanation

How the baseline is built and the gap measured

Methodology, then the measured breakdown, then the two root-cause buckets.

1 · Two pipelines, one source

The comparison pipeline compiles near-identical C through the eBPF path (Clang target=bpf → midend O2 → eBPF backend → verifier/JIT) and a native path (Clang target=x86 → midend O2 → x86 backend), sharing frontend and midend and diverging only at the backend.

2 · DCE timing doesn't change the story

Table 1 compares two strategies: No DCE (dead branches survive into the backend) and Early DCE (branches resolved in the midend). Both show a small IR gap (~4–5%) and a large backend gap (~27–29%):

Early DCE is used for the rest of the paper's analysis: it reflects the intended datapath (branches actually removed) and loads all seven objects — under No DCE, one object (bpf_host) failed to verify because moving config variables out of the read-only section broke a bounds check.

3 · The backend gap, by instruction category

Every one of the seven Cilium objects is larger under eBPF, from +25.5% (bpf_host) to +41.4% (bpf_sock) — a systematic effect, not an outlier. Breaking the total down by category:

Data movement is the biggest category in raw count but grows the least (+15%) — the biggest relative blowups (stack ops, arithmetic, logic) are smaller categories, and that's exactly where register pressure and instruction-widening patterns concentrate.

4 · Two root causes, and which is fixable without touching the ISA

ISA-bound overhead: the eBPF instruction set has no compact form of the operation. Address computation (no fused leaq: native uses 5,676, eBPF replaces with 5,660 extra addqs) and operand width (no sub-32-bit ops: native's 3,264 cmpb/testb/andb become movzbq + mask + shift sequences in eBPF) both require a new instruction to fix, not just a smarter JIT.

Pipeline-structural overhead: the ISA already has what's needed, the backend just doesn't use it. Byte-wise memory copies (40+ instructions to copy 16 bytes that native does in 4 wide-move instructions) and missing late passes (native's 4,370 branch folds vs eBPF's 345; 706 CSEs vs 94) are backend-work, recoverable without changing the ISA.

Register pressure spans both: eBPF's 11 usable registers (vs x86-64's 16) force some spilling regardless of backend quality, but spills grow only ~50% while rematerializations grow >6× (3,232 vs 2,150 spills; 10,024 vs 1,590 rematerializations) — register count alone doesn't explain the full gap, so part of that disproportionate rematerialization growth is attributable to backend allocation choices rather than the register deficit itself.

Follow the numbers

Worked examples

Four traces using the paper's real figures — from a single comparison to a byte copy to the overall percentages.

① The cmpb expansion (operand width)

Why does one native byte-compare become three eBPF instructions?

  1. Native: cmpb $1, (%rdi) — one instruction, because x86 has an 8-bit compare that can read memory directly.
  2. eBPF has no 8-bit compare (ISA-bound), so it must first widen: movzbl (%rdi), %eax loads the byte and zero-extends to 32 bits.
  3. Mask: andl $0xff, %eax — isolates the byte's value explicitly (eBPF lacks x86's implicit zero-extension in some forms).
  4. Compare: cmpl $1, %eax — now a 32-bit compare, since that's what eBPF supports.
  5. Ratio: 1 native instruction → 3 eBPF instructions, for this one pattern. Across the corpus this recurs as 3,264 native sub-32-bit ops replaced by thousands of movzbq/andl/shll in eBPF.
🔑
Insight: this is primarily ISA-bound — the compact instruction doesn't exist in eBPF's vocabulary, so the paper argues the real fix is extending the ISA. A sufficiently clever JIT could in principle pattern-match this expansion back into a single x86 cmpb, but that's a narrower backend workaround, not the structural fix.

② Address computation: leaq vs four instructions

Native folds base+index×scale+offset into one instruction; what does eBPF do instead?

  1. Native: leaq 0x20(%rdi,%rax,4), %rcx — one instruction computes rdi + rax×4 + 0x20.
  2. eBPF step 1: movq %rdi, %rcx — copy the base.
  3. eBPF step 2: imulq $4, %rax — compute the scaled index separately.
  4. eBPF step 3–4: addq %rax, %rcx then addq $0x20, %rcx — add index, then offset.
  5. Total: 1 → 4 instructions. Across the corpus: native uses 5,676 leaqs absent from eBPF, replaced by 5,660 extra addqs (roughly 1-for-1, consistent with this pattern recurring thousands of times).
💡
ISA-bound again: eBPF has no addressing mode that folds a scale-and-offset computation, so every such address must be built explicitly.

③ Copying a 16-byte IPv6 address

Native copies a struct field in two load/store pairs; the paper reports eBPF needs 40+ instructions. Why is this pipeline-structural, not ISA-bound?

  1. Native: movq (%rsi), %rax then movq %rax, (%rdi) — an 8-byte load/store pair, repeated once more for the second 8 bytes = 4 instructions for the full 16-byte copy.
  2. eBPF has wide load/store instructions too — the ISA supports this. But the backend instead rebuilds the copy one byte at a time: movzbq, shift, repeat.
  3. 16 bytes, one byte per iteration, each iteration needing a load, a shift, and eventually a store/OR to assemble the word — the paper reports 40+ instructions for this one field copy.
  4. Ratio: 4 → 40+, roughly 10×, for a pattern this widespread in networking code (IP addresses, MAC addresses, packet headers).
  5. Because the wide instructions exist in the ISA, this is classified pipeline-structural: a backend pass that recognized byte-copy loops and replaced them with wide moves would recover this — no ISA change required.
🔑
Insight: this single pattern touches data movement, arithmetic, and logic categories at once (each byte needs a shift/OR to assemble) — part of why those three categories show outsized growth in Table 2.

④ From per-object gaps to the headline 27.6%

Seven objects range from +25.5% to +41.4% individually — how does that aggregate to the reported +27.6%?

  1. Per object, the gap varies with how much of each object's code touches the patterns above: bpf_host +25.5% up to bpf_sock +41.4%.
  2. The aggregate isn't an average of percentages — it's computed from totals: eBPF's 163,629 backend instructions vs native's 128,216, across all seven objects combined.
  3. (163,629 − 128,216) / 128,216 = 35,413 / 128,216 ≈ 0.276, i.e. +27.6% — matching Table 2's total row.
  4. Bytes follow the same arithmetic but land lower (+16.6%) because eBPF's extra instructions (masks, zero-extends, address arithmetic) are short to encode, while the native instructions it's missing (leaq, memory operands, cmov) are comparatively long.
💡
Every object gets larger under eBPF — not just the aggregate — which is what lets the paper call this a systematic backend effect rather than a quirk of one program.
Test yourself

Practice problems

Try each before opening the answer. Every one names the misconception it checks.

Problem 1 · easy
The paper reports frontend gap <0.1%, midend +4.2%, backend +27.6%. What does this staged pattern prove about where the overhead comes from?
Show answer
It shows the two pipelines are compiling essentially the same logic through essentially the same optimizations — so the backend divergence can't be an artifact of a mismatched source or a difference in what got optimized away. The overhead is a code-generation effect, isolated almost entirely to the backend stage.Misconception: that the source or the C-level optimization differs between the two paths. They agree almost exactly until the backend — the source itself is not the cause.
Problem 2 · medium
Instruction count grows 27.6% but byte size grows only 16.6%. Explain the gap between these two numbers using what you know about the instruction categories.
Show answer
eBPF's extra instructions are mostly short encodings — zero-extensions, masks, small arithmetic ops (movzbq, andl, addq) — while the native instructions eBPF is missing tend to be longer encodings (leaq with complex addressing, memory operands, cmov). So eBPF trades a few long native instructions for many short eBPF ones: more instructions, but each one contributes fewer bytes on average.Misconception: that instruction count and byte size should move in lockstep. They're different rulers measuring different things — one counts operations, the other counts encoded size — and eBPF's pattern of many-small-instructions makes them diverge.
Problem 3 · hard
Arithmetic grows +109.9% and logic/bitwise +103.3% — both roughly double — while data movement, the largest category, grows only +15.0%. What single recurring pattern explains why arithmetic and logic move almost together?
Show answer
Byte-wise memory copies. Rebuilding a multi-byte value one byte at a time requires a shift (arithmetic) paired with an OR or mask (logic) for nearly every byte, so the same pattern inflates both categories in near lockstep. Data movement also grows from this pattern (more loads/stores), but it starts from a much larger base count, so the same absolute increase is a smaller percentage.Misconception: that each instruction category has an independent cause. Several categories can balloon from one shared root pattern — which is exactly why fixing byte-wise copies would recover gains across multiple rows of Table 2 at once.
Problem 4 · medium
Spills grow ~50% (2,150 → 3,232) but rematerializations grow >6× (1,590 → 10,024), even though both stem from "register pressure." What does this gap imply about whether the fix requires more eBPF registers?
Show answer
If register count alone explained the pressure, spills and rematerializations should scale together, roughly proportional to the register deficit (11 vs 16). Instead rematerializations grow far faster — meaning register count alone doesn't explain the full gap, and part of that growth reflects backend register-allocation choices rather than a hard ISA limit. The paper doesn't quantify how much a better allocator could recover, only that the disproportion rules out register count as the sole cause.Misconception: that all register-pressure overhead is "ISA-bound" and unfixable without more registers. Some is genuinely forced by the 11-vs-16 register count, but the disproportionate rematerialization growth shows register count isn't the whole story.
Problem 5 · easy
The paper disables verifier rewrites (inlined bounds checks, helper inlining) before measuring. Why would leaving them enabled distort the comparison?
Show answer
Verifier rewrites inject instructions unrelated to the program's original source logic (e.g., turning a map-lookup call into an inlined bounds check and offset computation). Since the native pipeline has no equivalent rewrite step, leaving this enabled would inflate the eBPF side with code that isn't a code-generation difference at all — it's a separate safety-enforcement mechanism layered on top.Misconception: that more eBPF-side instructions always mean worse code generation. Some extra instructions come from unrelated machinery (verifier safety rewrites), not the backend, and must be excluded to isolate code-gen quality specifically.
Problem 6 · medium
Under "No DCE," one object (bpf_host) failed to verify when its configuration variables moved out of the read-only section. Does this undermine the paper's headline 27.6%/16.6% numbers?
Show answer
No — the headline numbers come from the "Early DCE" configuration, which loads all seven objects successfully and better reflects the intended datapath setup (branches genuinely removed from final code). The No-DCE failure is reported as a side finding about read-only placement mattering for verification, with the affected object excluded only from that row's six-object gap — and even so, the No-DCE gap (+28.8%) stays within a point of Early DCE's (+27.6%), showing the timing choice barely affects the result.Misconception: that a verification failure in one configuration invalidates the whole study. It's a narrow, version-dependent side observation in an alternate configuration, not a flaw in the primary (Early DCE) measurement.
Problem 7 · hard
The paper measures code size, not runtime. Native's llc statistics show 8,715 macro-op fusions vs 0 for eBPF — but this number isn't used in the size comparison at all. Why not, and what would be needed to measure it properly?
Show answer
Macro-op fusion pairs a comparison with its branch during instruction scheduling — it affects how fast the CPU executes the code (by reducing the effective instruction stream at execution time), not how many instructions or bytes exist in the binary. So it's invisible to a code-size metric by construction. Measuring it properly would require running both the eBPF and a hypothetical native-quality version inside the kernel, on the same hook with the same maps/helpers — which needs a patched kernel or custom loader, and would also need to account for instruction-cache and branch-prediction effects the size numbers say nothing about.Misconception: that code size is a complete proxy for runtime performance. The paper is explicit that it is only a partial proxy — some backend differences (scheduling, fusion) matter for speed but leave no trace in size, and runtime comparison is left as future work.
Quick answers

Frequently asked questions

Tap any to expand.

Q1Why compare against native x86 instead of just measuring eBPF in isolation?▾
Without a reference point, you can't tell whether a given instruction count is "a lot" — you need something to measure it against. Native LLVM x86 code generation is an approximate best case, so the gap between it and eBPF's output isolates exactly how much room the eBPF pipeline has to improve.
Q2Is the native baseline something eBPF could realistically reach?▾
No — it's explicitly called an upper bound, not a target. Native code never has to satisfy the in-kernel verifier or the JIT's safety constraints, both of which legitimately cost some overhead. The gap is a useful reference for tracking improvement, not a promise that eBPF can close it entirely.
Q3Why Cilium specifically?▾
Cilium's datapath objects are large, run in hot per-packet paths, cover a wide range of verifier-constrained code, and are heavily built around configuration-dependent dead code — making them representative and stress-testing exactly the patterns the paper studies. Cilium is also fully open source, which matters for reproducibility.
Q4Does the ~28% overhead apply to every eBPF program?▾
The specific numbers (27.6%/16.6%) are measured on Cilium's datapath alone. The paper is explicit that the method generalizes — to other eBPF workloads (e.g. XDP load balancers), other architectures (arm64, RISC-V), and other backends (GCC's BPF backend) — but the exact percentages would need to be re-measured for each.
Q5Would the gap look different on arm64 or RISC-V?▾
The paper suspects a smaller ISA-bound portion there, since arm64 and RISC-V are architecturally closer to eBPF (e.g. they also lack some of x86's sub-32-bit conveniences). The register-pressure-driven overhead would likely persist, since both provide more registers than x86-64, not fewer — making eBPF's 11-register deficit more pronounced by comparison. The paper does not test this directly and names it as future work.
Q6What's the difference between "ISA-bound" and "pipeline-structural" overhead, practically?▾
ISA-bound overhead requires changing what eBPF instructions exist (e.g. adding sub-32-bit ops or fused addressing) — a slow, ecosystem-wide change. Pipeline-structural overhead is fixable by improving the LLVM eBPF backend alone (better peephole passes, smarter register allocation) — deployable independently, without touching the verifier or kernel ABI.
Q7Why does code size matter if eBPF programs already run fast enough?▾
Two reasons given in the paper: eBPF code runs from kernel memory in hot per-packet paths, so its size adds directly to the kernel's instruction footprint (affecting icache pressure); and the in-kernel verifier enforces hard size and complexity limits on the bytecode it checks, which can decide whether a program is even allowed to load at all.
Q8How is this different from prior eBPF bytecode optimizers like K2 or EPSO?▾
K2, EPSO, and Merlin optimize the bytecode that goes into the verifier — the JIT's input. This paper instead measures the JIT's output, comparing it against a native reference to quantify and attribute backend overhead. It's a measurement/diagnostic contribution, not a new optimizer, though its findings point at what an optimizer should target.
Q9Could the same method be run against GCC's BPF backend?▾
Yes — the paper notes this as natural follow-up work. Since this study uses LLVM for both pipelines, it measures one LLVM backend against another within the same compiler. Running the same split through GCC (to both BPF and native) would test whether an overhead pattern is ISA-driven (likely appears in both compilers) or backend-specific (appears only in one, suggesting where that compiler could improve).
Q10Does this paper propose fixes, or just measure the problem?▾
Primarily measurement and attribution — it identifies the largest recoverable items (byte-wise memory copies and missing late machine passes like branch folding/CSE) and sketches what a fix would look like (a backend pass recognizing copy loops, a stronger register allocator), but implementing and validating those fixes is left as future work.
