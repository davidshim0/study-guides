PLOS '26, Prague · A Field Guide

Giving Rust programs bulkheads without asking anyone to retrofit them

Rust's borrow checker doesn't save you from unsafe, foreign code, or its own soundness bugs. This is the plain-English story of zBulk, a compiler that reads your program's types and automatically walls it off into SGX-isolated compartments — zero code changes required.

📄 "zBulk: Towards Automatic Compartmentalization in Rust" · Onciul, Raffeck, Wägemann, Kapitza 🎓 Some Rust ownership & SGX basics assumed — primers cover them ⏱ ~25 min read
⚓

Split the program along the boundaries the compiler already understands — not the ones a developer has time to retrofit by hand.
If a function's data can't cross a boundary safely, leave it out — don't force it.

1Ownership, borrowing, and Rust's safety promise▾

Rust's compiler tracks, at compile time, who owns each piece of data and who merely holds a temporary reference (borrow) to it. It enforces that mutable references never alias — no two pieces of code can both mutate the same memory at once. This is what gives Rust memory safety without a garbage collector.

The compiler even tells LLVM about this guarantee, marking mutable references noalias, letting LLVM reorder and optimize code around them.

Now you're ready: if that noalias promise is ever broken by a bug, the optimizer's reordering becomes exploitable — that's exactly what happened in the CVE zBulk uses as its motivating example.
2unsafe — Rust's escape hatch▾

Some operations (raw pointer arithmetic, calling foreign functions, manual buffer management) can't be proven safe by the compiler. The unsafe keyword lets a developer perform them anyway — but now they, not the compiler, must guarantee correctness.

unsafe code is rare by volume but common in performance-sensitive libraries, and a single mistake inside it can undermine safety guarantees the rest of the program relies on.

Now you're ready: Microsoft found ~70% of CVEs stem from memory-safety bugs — mostly in exactly this kind of code. zBulk doesn't remove unsafe; it limits the blast radius when it goes wrong.
3Compartmentalization, in one sentence▾

Split a program into pieces (compartments), run each in its own isolated execution context, and let them talk through explicit interfaces instead of shared memory. If one compartment is compromised, the damage should, ideally, stay inside it.

This has two separable parts: a policy (which pieces go where) and an enforcement mechanism (what actually keeps them apart at runtime).

Now you're ready: zBulk automates the policy (which functions can become compartments) and stays agnostic about the mechanism — it currently plugs in Intel SGX, but the split logic doesn't depend on it.
4Trusted execution and SGX enclaves▾

Intel SGX lets a program create an enclave: a region of memory the CPU encrypts and isolates so that even a compromised OS or hypervisor can't read or tamper with its contents. Entering an enclave is called an ecall; calling back out to untrusted code is an ocall.

Enclaves reserve their memory from a fixed, limited pool called the EPC (Enclave Page Cache) — you cannot simply create unlimited enclaves.

Now you're ready: zBulk uses one enclave per compartment. Every cross-compartment call becomes a round-trip of ecalls/ocalls plus serialization — the paper's whole performance story runs through this fact.
5Serialization — turning data into bytes to cross a boundary▾

Compartments don't share memory. To pass a parameter from one to another, you must convert it into a plain byte sequence (serialize) on one side and reconstruct it (deserialize) on the other. Rust's serde crate does this automatically for most types via a #[derive] annotation.

Not everything can be serialized: a raw pointer, a mutex lock, a closure, or a reference into someone else's memory has no meaningful byte representation on the other side of the boundary.

Now you're ready: this single fact — "can this function's signature be fully serialized?" — is the test zBulk runs on every function to decide if it's eligible to become a compartment interface.
6Compiler intermediate representations (AST → MIR)▾

rustc doesn't compile source code directly to machine code. It passes through stages: the AST (raw syntax tree), HIR (names resolved), THIR (HIR with types resolved), and MIR (a lowered, simplified control-flow form used for borrow checking and optimization).

Each stage knows more about the program than the last, but is progressively harder to turn back into editable source code.

Now you're ready: zBulk needs full type information but also needs to emit valid Rust source — that tension is exactly why the paper spends a whole section justifying which IR it builds on (spoiler: THIR).
7Call graphs and why "which function?" is hard in Rust▾

A call graph records which function calls which. In a simple language this is easy; in Rust it's complicated by generics (one function, many compiled variants), method overloading across different impl blocks, nested modules, private items, and re-exports that give one item multiple visible paths.

Uniquely naming "this exact function, in this exact context" therefore requires real type and name analysis, not just text matching.

Now you're ready: when two compartments need to route a call to each other, the callee needs an unambiguous identity for the target function — this is zBulk's CrossCrateId problem.
8cargo, crates, and the build unit zBulk hooks into▾

Rust code is organized into crates (compilation units), which cargo resolves, downloads, and builds according to a Cargo.toml manifest. A workspace lets several crates share configuration.

Any tool that wants to transform a Rust build must plug into this pipeline — cargo invokes the compiler once per crate, in dependency order.

Now you're ready: zBulk intercepts this exact pipeline, running its own compiler passes per crate and synthesizing new Cargo.toml manifests for the compartments it creates.
9Why "safe" languages still get CVEs▾

Memory safety guarantees hold only for code the compiler can fully check. unsafe blocks, foreign-function calls, and — rarely — bugs in the compiler itself, all fall outside that guarantee. A widely-used framework can ship such a bug for years before anyone notices.

zBulk's running example is exactly this: a real, disclosed CVE in the Actix-Web framework that persisted across multiple "fixed" releases.

Now you're ready: compartmentalization doesn't fix the bug — it limits what the bug can reach. That's the entire value proposition this paper is built on.
The whole story in one place

zBulk in a nutshell

The problem, the automatic decision that fixes it, and how the pieces connect.

Rust eliminates most memory-safety bugs at compile time — but not all of them. unsafe blocks, foreign code, and rare compiler-soundness bugs can still open a door. The paper's example: a real CVE in Actix-Web where a dangling mutable reference, combined with the compiler's noalias optimization promise, produced an exploitable write primitive — and it survived several "fixed" releases.

Compartmentalization limits how far such a bug can reach by splitting a program into mutually distrusting pieces. The catch: doing this by hand requires deep systems expertise and is, by the authors' own framing, "labor-intensive and error-prone" — which is why, per a 2025 systematization of 211 research efforts, mainstream adoption remains rare.

zBulk's answer: stop asking developers to retrofit anything. Walk the program's fully-typed compiler representation (THIR), and for every function ask one question — can its parameters and return value be fully serialized? If yes, it's eligible to become its own compartment interface, wired up automatically with serde and a custom CrossCrateId for dispatch. A configurable placement rule then decides how many of these eligible functions actually get their own isolated Intel SGX enclave.

The result, so far: a base64 en/decoder with one dependency, fully automatically split into up to eight compartments — with measured SGX overhead that stays well under the cost of a full fork/exec, even at maximum granularity.

🧱 Key takeaways

  • Rust's safety guarantees stop at unsafe, FFI, and compiler soundness bugs — compartmentalization contains what's left over.
  • zBulk needs zero manual retrofitting: the eligibility test is purely "can this signature be serialized?", answered from the compiler's own type information.
  • Built on THIR (not AST or MIR) — the only IR that gives full name/type resolution while still letting source code be recovered.
  • A custom CrossCrateId solves cross-compartment dispatch despite Rust's generics, overloading, and re-exports.
  • The placement rule (which functions share a compartment) is deliberately decoupled from the enforcement mechanism (SGX today, others possible later).
  • Finer compartments ⇒ more security promise but more cross-compartment calls ⇒ more overhead — an explicit, measured trade-off (C3).
  • Proof of concept: a base64 utility auto-split into up to 8 SGX-isolated compartments, all faster than one fork/exec.
Six everyday pictures

How to think about zBulk

Each stands alone — read in any order. Every card ends with an honest note about where the picture stops being true.

The name itself · zBulk

Ship bulkheads

A bulkhead is a wall dividing a ship's hull so a hull breach floods one chamber, not the whole vessel. zBulk's namesake: split the program into chambers so a compromised function can only flood its own compartment, not the whole process's memory.

Where it breaks: a ship's bulkheads are sized once by the hull designer. zBulk's "chambers" are chosen per build, automatically, and can be merged or split again without touching the ship.
C1 · Serialization limits

Sealing a letter

You can mail a copy of a document, but you can't mail someone a pointer into your own filing cabinet. Serialization is the envelope: a function's parameters get copied into bytes and reconstructed on the other side — but a reference that points back into the caller's own memory has nothing valid to reconstruct.

Where it breaks: a real letter can carry anything paper allows. zBulk's "envelope" currently only accepts fully-owned data — no references, closures, or locks — which is exactly the gap the authors flag as future work.
C2 · Entry dispatch

Inter-office mail with a case number

Two company branches don't share a filing system, so every request between them needs a case number the receiving branch can look up unambiguously. Rust's generics, overloads, and re-exports mean a plain function name isn't unique enough — zBulk's CrossCrateId is that case number.

Where it breaks: a case number is opaque to everyone; zBulk's ID is derived deterministically from compiler-internal identifiers, so it's less like an arbitrary ticket and more like a well-defined, stable hash.
C3 · Placement rule

Merging assembly-line stations

A factory line can run as many tiny stations as workers to inspect, or fuse several steps into one station to cut walking time between them. zBulk's placement rule works the same way: start with the finest split possible, then merge adjacent compartments to trade some isolation for fewer, cheaper hand-offs.

Where it breaks: a factory manager merges stations based on throughput data. zBulk's current merging ("balanced adjacent merging") is a simple graph heuristic for evaluation — it doesn't yet weigh performance or security when deciding what to fuse.
Enforcement cost · ecall / ocall

Airport security checkpoints

Walking between two airport terminals through a shared concourse is instant; walking between two secured terminals means a checkpoint each way. Crossing into and out of an SGX enclave is exactly this checkpoint — fixed overhead per crossing, regardless of what you're carrying (unless it's a lot of luggage, i.e. a large payload).

Where it breaks: airport checkpoints get faster with more staff. The ecall/ocall overhead is close to a hardware-fixed cost — the paper's whole optimization lever is therefore reducing how often you cross, not making each crossing faster.
Resource limit · EPC

A bank vault of safety-deposit boxes

A vault only has so many boxes — rent them all out and the next customer waits, no matter how much money they have. The EPC (Enclave Page Cache) is the same: a fixed pool of protected memory, so the number of enclaves you can run concurrently is capped by capacity, not ambition.

Where it breaks: vault boxes don't get evicted automatically. Teaclave, the enclave runtime zBulk uses, cannot yet dynamically resize an enclave's footprint once created — closer to renting a box for a fixed size than paying by what you actually store.
The full explanation

How it actually works

Challenge by challenge, with the paper's own diagrams rebuilt as visuals you can read at a glance.

0 · The motivating bug — why compartmentalization matters even in Rust

Actix-Web, a widely-used Rust web framework, once held a mutable reference buf into a message buffer while later calling buffer.reserve(len), which can reallocate that same buffer — leaving buf dangling. Because the borrow checker had (wrongly, in this unsafe section) promised the compiler that mutable references never alias, LLVM was free to reorder code around that promise. A crafted request could exploit the reordering to gain a write primitive into the heap — reading or writing other sessions' data, in the worst case redirecting a vtable call.

⚠
Still present: the CVE (2018-25025) was marked fixed as of version 0.7.15, but the authors show the vulnerable pattern remained in version 0.7.19 and have proposed updating the advisory. Fixing a flagged line doesn't always fix the bug class.

Confining the parser that owns buf to its own compartment would restrict this write primitive to the parser's own isolated memory — session data and the rest of the application stay untouched, CVE or not.

1 · C1 — turning functions into interfaces

Every compartment interface needs serializable parameters and a serializable return value, because compartments share no memory. zBulk checks this automatically using serde: primitives and most standard-library types already support it; user-defined types usually need only a derive annotation, which zBulk injects if — and only if — none of their members are references, function pointers, closures, or dynamically-dispatched generics. A mutex or heap allocation can't cross either: neither is meaningfully serializable.

🔍
The current boundary, precisely: "zBulk can only transform a function if its signature contains only owned types, generic types included." Borrowed parameters, closures, and global mutable state are explicitly out of scope for this prototype — and flagged as future work.

2 · C2 — why dispatch needs its own identifier

Rust lets two impl blocks define methods with the same name but different generic bounds, lets modules re-export items under new paths, and lets visibility hide some paths entirely. A callee compartment receiving a plain function name has no reliable way to resolve it. zBulk instead derives a CrossCrateId — a size- and performance-optimized hybrid of rustc's own DefId and DefPathHash — stable from as early as the AST, and used verbatim as the dispatch key on both sides of a call.

3 · Why build on THIR, not AST or MIR

zBulk is a source-to-source compiler: it must emit valid Rust, so the generated compartments still go through the borrow checker for a correctness guarantee. That requirement rules out working purely on MIR (fully resolved, but not a public, source-recoverable interface) and pushes hard against AST (source-recoverable, but no name/type resolution at all).

ASTNone — pre name/type resolutionYes, triviallyBlocks R3 (needs fully resolved types) and R5

💡
zBulk hooks THIR via rustc's LateLintPass (with optional MIR access for monomorphization results) for the main analysis, and an EarlyLintPass on the AST to recover source-level attributes like #[cfg(...)] or doc comments that THIR strips away.

4 · C3 — the performance/security trade-off, and SGX specifics

zBulk's placement rule starts maximal — every eligible function gets its own compartment, the finest possible granularity — then can be refined (merged) toward fewer, cheaper compartments. Each SGX enclave, running via Apache Teaclave, reserves: 256 pages of heap, 64 pages of stack, 5 guard pages, and roughly 135 pages of enclave-runtime overhead. Communication between enclaves happens only through untrusted shared memory in the host process, so every cross-compartment message must be serialized and encrypted — and the receiver copies ciphertext into its own memory before decrypting, specifically to prevent TOCTOU attacks on the shared buffer.

🧊
Framing (ours, not the paper's): the EPC is itself a small, fast, capacity-bounded memory tier sitting in front of ordinary DRAM — much like the DRAM tier in a DRAM/NVM or CXL hierarchy. Teaclave's current inability to dynamically resize an enclave once created is the enclave-world analogue of a tiering system that can't yet migrate or reclaim pages on demand: capacity has to be reserved up front rather than grown as working sets change.
Follow the numbers, step by step

Worked examples

Four calculations, each using the paper's own measurements end to end.

① How big is one enclave, and how many can fit?

The paper reserves 256 pages of heap, 64 pages of stack, 5 guard pages, and ~135 pages of enclave-runtime overhead per enclave (4 KiB pages).

  1. Total pages: 256 + 64 + 5 + 135 = 460 pages.
  2. In bytes: 460 × 4096 B = 1,884,160 B ≈ 1.84 MB — the paper rounds this up to "a slightly over-provisioned 2 MB enclave."
  3. Configured EPC capacity ÷ enclave size: 2 GB ÷ ~2 MB ≈ ~1000 concurrent enclaves, enough for complex, deeply compartmentalized applications.
  4. The actual hardware limit on the test server is 64 GB of EPC — 32× the configured value — giving substantial headroom beyond the estimate above.
🧱
Insight: the EPC, not raw CPU cycles, is the real ceiling on how many compartments a system can run at once — exactly the kind of fixed-capacity constraint familiar from any bounded fast-memory tier.

② What does one cross-compartment hop actually cost?

Using the 16 B column of Table 1: 1 compartment (0 hops) = 0.4 ms; 2 compartments (1 hop) = 0.9 ms; 4 and 8 compartments (2 hops) = 1.2 ms.

  1. Enter/leave-enclave floor: 0.4 ms (1 compartment) − 22 µs (no isolation) ≈ 0.38 ms just for the mandatory ecall in / ecall out of the enclave hosting main.
  2. Cost of the first hop: 0.9 ms − 0.4 ms = 0.5 ms for one ocall + one ecall + two returns + serialize/encrypt/decrypt.
  3. Cost of the second hop: 1.2 ms − 0.9 ms = 0.3 ms — less than the first, consistent with the paper's note that "additional enclaves that are not entered incur no runtime overhead" once the pipeline is already crossing boundaries.
  4. Going from 4 to 8 compartments costs nothing extra (both stay at 1.2 ms for 16 B) — the base64 crate's unused API surface simply sits idle.
💡
Overhead tracks hops taken on the executed path, not compartment count — the same test program could, in principle, be split into far more than 8 compartments at no extra runtime cost, as long as it doesn't call into the unused ones.

③ Why does the 64 kB column jump so much more?

stdin is buffered at 8 KiB. A 64 kB payload therefore needs multiple buffer refills, each forcing a host↔enclave transition.

  1. Refills needed: 64 kB ÷ 8 KiB = 8 buffer refills to consume the whole payload — versus effectively one for 16 B or 1 kB.
  2. Gap to baseline at small payload: 8-compartment / no-isolation = 1.2 ms ÷ 22 µs ≈ 55× — transition overhead totally dominates a tiny payload.
  3. Gap to baseline at 64 kB: 2.5 ms ÷ 504 µs ≈ 5× (single-compartment: 1.9 ms ÷ 504 µs ≈ 3.8×) — matching the paper's own claim that the gap "narrows to roughly 4×" as data-handling cost starts to outweigh fixed transition cost.
  4. Takeaway: the 64 kB curve is steep because of buffering, not because of the number of compartments — the same eight-compartment split costs only +1.3 ms (2.5 − 1.2) going from 16 B to 64 kB, versus the isolation floor itself.

④ Is SGX compartmentalization actually cheaper than processes?

The paper's fork/exec reference: 6.9 ms (16 B), 6.8 ms (1 kB), 7.3 ms (64 kB).

  1. Worst-case SGX config (8 compartments, 64 kB) = 2.5 ms.
  2. fork/exec at the same payload = 7.3 ms.
  3. Ratio: 7.3 ms ÷ 2.5 ms ≈ 2.9× — even the most fine-grained, most boundary-crossing SGX configuration in this experiment beats a single process fork by roughly 3×.
  4. Caveat: fork/exec here is explicitly described as bracketing cost "from above" — a reference point, not a like-for-like security comparison, since it isolates far less strongly than SGX enclaves do.
🧱
This is the headline evaluation result: zBulk's finest-grained, fully automatic split is not just feasible — it's cheaper than the crude process-based isolation it's implicitly competing with.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it checks.

Problem 1 · easy
A function's return type is &'a str — a reference borrowed from one of its own parameters. Can zBulk turn it into a compartment interface?
Show answer
No. A pointer valid in the caller's compartment is meaningless in the callee's — compartments don't share memory. Even if &'a str's contents could be serialized, the reference itself can't be reconstructed as a valid pointer on the other side, so zBulk excludes this function from becoming an interface.Misconception: that adding #[derive(Serialize)] fixes anything with a reference in it. The blocker isn't "can the bytes be copied" — it's "does a pointer make sense across a memory boundary," and it never does.
Problem 2 · easy
The Actix-Web CVE involved a mutable reference (buf) held across a buffer reallocation. Which zBulk limitation means the vulnerable function itself couldn't yet be automatically compartmentalized away?
Show answer
The function operates on borrowed/mutable-reference data, and zBulk's current prototype only transforms functions whose signatures contain owned types. Supporting borrowed parameters (by serializing the referenced data and passing a reference to a deserialized copy on the callee side) is explicitly named as the prerequisite for compartmentalizing Actix-Web-style code.Misconception: that Rust's memory safety means bugs like this "can't happen." They can, in unsafe sections — that's precisely why compartmentalization exists as a second line of defense.
Problem 3 · medium
Using Table 1's 1 kB column (1 compartment = 0.4 ms, 2 = 0.9 ms, 4 = 1.2 ms), compute the cost of the first cross-compartment hop and the second.
Show answer
First hop: 0.9 − 0.4 = 0.5 ms (the 1→2 compartment jump, adding one hop). Second hop: 1.2 − 0.9 = 0.3 ms (the 2→4 compartment jump, adding a second hop). The second hop is cheaper than the first — consistent with unused enclaves costing nothing and only the calls actually taken on the executed path adding time.Misconception: that overhead scales with the number of compartments created. It scales with the number of cross-compartment calls executed, which is why 4 and 8 compartments cost the same here.
Problem 4 · medium
Why did zBulk's authors choose to build their analysis on THIR rather than starting from MIR, which has strictly more type information resolved?
Show answer
zBulk is a source-to-source compiler (R1): it must emit valid Rust that the borrow checker can re-verify. MIR is fully resolved but has no public, source-recoverable path back to editable Rust code — you can't cleanly turn a MIR transformation back into source. THIR, by contrast, is exposed via rustc's LateLintPass and rustc tracks enough provenance to recover source code from it, at the cost of generics not being fully monomorphized yet (which zBulk compensates for with optional MIR access).Misconception: that more resolved type information is strictly better for every purpose. Here, "recoverable to source" was the binding constraint, not "maximally resolved."
Problem 5 · medium
Given the paper's enclave footprint estimate (~1.84 MB) and a configured EPC of 2 GB, roughly how many enclaves can run concurrently? What changes if the server's actual EPC of 64 GB is used instead?
Show answer
2 GB ÷ ~2 MB ≈ ~1000 enclaves under the configured EPC. Using the real hardware limit of 64 GB instead: 64 GB ÷ ~2 MB ≈ ~32,000 enclaves — roughly 32× more headroom than the conservative configured estimate the paper reports.Misconception: that EPC size scales with total system RAM (123 GB here). EPC is a separately configured, much smaller reserved pool — the 123 GB of host RAM is irrelevant to this specific cap.
Problem 6 · hard
Merging zBulk's 8 initial compartments down to 4 halves the number of enclaves, but the paper says the 4-compartment configuration exposes two entry points per compartment instead of one. Why doesn't merging shrink the total exposed API surface?
Show answer
Merging combines compartments, but every entry point that was reachable from outside before the merge is still reachable from outside afterward — the entry points simply accumulate onto fewer enclaves. Since zBulk does not yet perform reachability analysis (which could prune entry points whose only callers are now co-located in the same compartment), merging changes how many enclaves exist, not how many externally-callable functions exist.Misconception: that fewer compartments automatically mean a smaller attack surface. The surface (total entry points) stays the same here — only the number of isolation boundaries shrinks.
Problem 7 · hard
The current prototype lets any compartment invoke any exposed interface of any other compartment. What security property is missing, and what information does zBulk already have that could fix it?
Show answer
Missing: caller authorization / least-privilege enforcement at the dispatch step — any compartment can call any other's public interface, not just the ones it's supposed to call. zBulk already builds a global, aggregated call graph during aggregate_graphs, which records exactly which compartment legitimately calls which interface — the paper names deriving per-caller allow-lists from this existing graph as "a natural next step," not a new analysis.Misconception: that compartmentalizing a program automatically makes it least-privilege. Splitting into compartments is necessary but not sufficient — without restricting who may call whom, every compartment's interface is still callable by every other compartment.
Quick answers

Frequently asked questions

Ten questions newcomers ask most. Tap any to expand.

Q1What does "zero manual retrofitting" actually promise?▾
That a developer doesn't have to annotate, rewrite, or restructure their program at all. zBulk decides, purely from the compiler's own type and call-graph information, which functions can become compartment interfaces, and generates all the serialization, dispatch, and SGX boilerplate itself. It does not promise every function becomes a compartment — only those whose signatures are fully serializable.
Q2Does zBulk soundly isolate the entire program?▾
No — the paper is explicit that "zero manual effort does not mean that zBulk soundly and completely isolates every function." Functions with borrowed parameters, closures, global mutable state, or foreign-function calls are currently excluded from automatic compartmentalization and either stay in their caller's compartment or block the transformation entirely.
Q3Why SGX specifically, and not just OS processes?▾
SGX gives a smaller trusted computing base than process isolation and, crucially, means a compromised host OS cannot inspect or alter a compartment's state — a guarantee process boundaries alone don't provide. The evaluation also shows SGX-based compartments, even at maximum granularity, run faster than a single fork/exec.
Q4How does the callee know which function to actually run?▾
Every cross-compartment call carries a CrossCrateId — a stable identifier zBulk derives from rustc's own name-resolution data (a hybrid of DefId and DefPathHash). The callee's dispatcher switches on this ID to find the right "skeleton," deserializes the arguments, and makes the real local call.
Q5Are messages between compartments encrypted?▾
Yes — because enclaves can only communicate through untrusted shared memory in the host process, every payload is serialized and encrypted before crossing, and decrypted only after the receiver copies the ciphertext into its own memory (to block TOCTOU attacks on the shared buffer). The current prototype uses pre-distributed keys; mutually authenticated, replay-protected channels via TLS and local attestation are future work.
Q6Why doesn't more compartments always mean proportionally more overhead?▾
Overhead scales with the number of cross-compartment calls actually executed, not with how many compartments exist. A compartment that's part of the topology but never invoked on a given run costs nothing at runtime — which is exactly why the 4- and 8-compartment configurations in Table 1 have identical latency for small payloads.
Q7Does compartmentalizing Actix-Web-style code fix the CVE?▾
No — compartmentalization doesn't remove the bug, it limits its reach. Confining the vulnerable parser to its own compartment would restrict a write primitive to that compartment's own isolated memory, protecting session data and the rest of the application, but the underlying dangling-reference bug would still exist. zBulk can't yet even attempt this specific case, since it involves borrowed parameters.
Q8Why is rustc's THIR the right hook instead of a standalone parser?▾
Writing a standalone parser (e.g. with syn, at the AST level) gets source-recoverability for free but has no name or type resolution — useless for deciding serializability. THIR, exposed via rustc's own lint-pass interface, gives full name/type resolution while still letting zBulk recover the original source for each structure, satisfying both requirements at once.
Q9What's the difference between a "placement rule" and an "enforcement mechanism"?▾
The placement rule decides which functions go in which compartments — a policy question. The enforcement mechanism decides how those compartments are actually kept apart at runtime — SGX today, something else potentially tomorrow. zBulk deliberately separates these so a new isolation mechanism only needs a new compartment template and launcher script, not a new placement algorithm.
Q10What's explicitly left for future work?▾
Supporting borrowed parameters, global mutable state, and foreign functions as compartment interface material; deriving per-caller allow-lists from the existing call graph to stop any-compartment-calls-any-compartment; adding TLS-based mutual authentication and replay protection between enclaves; and developing performance- and security-aware placement policies (beyond the simple adjacent-merging heuristic used for evaluation) — including dynamic, hot-path-driven analysis.

EPCEnclave Page Cache — the fixed-size pool of protected physical memory enclaves draw from; the real cap on concurrent compartments.
Supporting terms
ecall / ocallEntering an SGX enclave / calling back out of one to untrusted code — the two directions every cross-compartment hop needs.
AST / HIR / MIRrustc's other intermediate representations: raw syntax, name-resolved, and fully lowered/monomorphized, respectively.
serdeThe Rust serialization crate zBulk leans on to turn eligible types into byte sequences automatically.
TOCTOUTime-of-check-to-time-of-use race; guarded against by copying ciphertext into trusted memory before decrypting it.
noaliasAn LLVM optimization hint from Rust's borrow checker promising a mutable reference never aliases — the promise the motivating CVE violates.
TCBTrusted Computing Base — the code that must be correct for security to hold; SGX aims to shrink this relative to trusting a full OS.
Workspace / manifestcargo's mechanism for a multi-crate project and the Cargo.toml files zBulk synthesizes per compartment.
HopsThe number of cross-compartment calls actually executed on a given run — the real driver of runtime overhead, not compartment count.

Related work the paper positions against

SoK: Software Compartmentalization hard

Lefeuvre, Dautenhahn, Chisnall, Olivier · S&P · 2025

Systematizes 211 research efforts and 61 mainstream systems; the definition of compartmentalization zBulk adopts, and the source of the claim that no surveyed approach fully automates Rust compartmentalization before zBulk.

ACES: Automatic Compartments for Embedded Systems medium

Clements, Almakhdhub, Bagchi, Payer · USENIX Security · 2018

Fully automated compartmentalization for embedded C — exploits well-defined task/peripheral structure that generic Rust applications don't have, and doesn't support Rust.

Cadote: Compiler-Aided Trusted Enclaves in Rust medium

Dreissig, Röckl, Müller · ARES · 2022

The closest prior Rust-and-enclaves work, but requires developer annotations and only splits into two partitions — zBulk automates the split entirely and supports an arbitrary number of compartments.

Rust-SGX / EActors medium

Wang et al. (CCS '19); Sartakov et al. (Middleware '18)

Offer abstractions for an arbitrary number of SGX partitions at arbitrary functions, but rely entirely on manual developer effort — the gap zBulk closes.

Glamdring: Automatic Application Partitioning for Intel SGX medium

Lind et al. · USENIX ATC · 2017

Splits into a trusted/untrusted pair guided by developer-tagged sensitive data — a two-partition, annotation-driven approach zBulk's fine-grained, zero-annotation split goes beyond.
