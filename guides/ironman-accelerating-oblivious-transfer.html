Two crypto bottlenecks, two very different fixes — silicon for one, the DRAM rank for the other

Private AI inference spends 51–69% of its time not on the neural network, but on generating oblivious-transfer correlations. Ironman splits that cost into a compute-bound half and a memory-bound half, and fixes each one where it actually lives.

📄 Lin, Yang, Xu, Liang, Wang, Chen, Wang, Gao, Li · MICRO'25 🎓 Crypto primitives explained; architecture assumed ⏱ ~25 min read
🔐

SPCOT is compute-bound — give it a leaner PRG and a bushier tree.
LPN is memory-bandwidth-bound — move the computation to the DRAM rank instead of hauling data to the CPU.

Before you begin

The crypto primitives this paper assumes

Architecture background (caches, DRAM ranks, NMP) is assumed — this guide spends its time on the cryptographic pieces (OT, GGM trees, LPN) that make Ironman's workload look so unusual.

Quick glossary
OTOblivious Transfer — sender has two messages, receiver picks one by a secret bit, sender never learns which.
COTCorrelated OT — a cheaper OT variant where the two outputs differ by a fixed secret offset Δ.
SPCOTSingle-Point COT — the sub-protocol that builds one GGM tree per correlation batch.
LPNLearning Parity with Noise — the sparse matrix-vector step that expands few correlations into many.
GGM treeA binary (or m-ary) tree grown from one seed via a PRG — doubles (or m-tuples) nodes each level.
PCGPseudorandom Correlation Generator — the style of OTE with sub-linear communication.
PRGPseudo-Random Generator — expands a short seed into a longer pseudorandom string (AES or ChaCha here).
NMPNear-Memory Processing — compute logic placed on the DIMM buffer chip, next to the DRAM banks.
CRHFCorrelation-Robust Hash Function — turns COT outputs into standard OT outputs.
PPMLPrivacy-Preserving Machine Learning — inference on encrypted/secret-shared data via HE+MPC.
SPCOT — compute-bound LPN — memory-bandwidth-bound Ironman-NMP machinery CPU baseline (the bottleneck)
1Why PPML leans on Oblivious Transfer at all▾

Hybrid HE/MPC frameworks compute linear layers (convolutions, matmuls) with homomorphic encryption, but nonlinear layers (ReLU, GeLU, Softmax) are cheaper to evaluate exactly using secret-shared comparisons built from OT — no accuracy loss, no fine-tuning needed.

Now you're ready: every ReLU or GeLU call in a private inference needs a batch of OT correlations prepared in advance — and preparing them is what Ironman accelerates.
2OT and its cheaper cousin, Correlated OT▾

Plain OT: sender holds m0,m1; receiver holds bit b; receiver learns only m_b. Building millions of these directly is expensive. COT is a lighter-weight primitive: the sender gets two random strings r0,r1 with r0⊕r1=Δ fixed across the whole batch, and the receiver gets b and r_b. A hash function later turns COT into standard OT.

Now you're ready: the entire paper is about generating COT correlations fast — OTE (OT Extension) means "stretch a few expensive COTs into millions of cheap ones."
3PRGs and the GGM tree — one seed, exponentially many outputs▾

A GGM tree starts from one random seed and, at each level, applies a double-length PRG to turn every node into two children (a 2-ary tree) — so ℓ leaves cost roughly 2ℓ−1 PRG calls. On CPUs the PRG is built from AES, since AES-NI makes AES essentially free per call.

Now you're ready: SPCOT's entire cost is "how many PRG calls does it take to grow this tree" — which is exactly what the m-ary tree optimization in this paper attacks.
4What SPCOT actually computes▾

Sender and receiver jointly grow a GGM tree such that the receiver ends up knowing every leaf except one secret index α. Four steps: ① sender locally expands its own full tree; ② sender packages the XOR of even/odd nodes at each level as keys for a tiny 1-of-2 OT; ③ receiver uses those keys to reconstruct every leaf except the α-th; ④ sender sends one more XOR sum so the receiver can recover even that.

Now you're ready: "Local Expansion" (sender) and "Tree Reconstruction" (receiver) are both just GGM-tree growth — the same operation, different data flow. That symmetry is what lets Ironman share hardware between the two roles.
5PCG-style extension — why sub-linear communication matters▾

Older OTE (IKNP-style) sends roughly one message per output correlation — linear communication, which becomes the bottleneck at scale. PCG-style OTE (used here) compresses many SPCOT outputs into millions of correlations using only sub-linear communication, at the cost of much more local computation. That's the trade this whole paper is reacting to: communication got cheap, computation became the new bottleneck.

6LPN encoding — a sparse matrix-vector multiply▾

After SPCOT, both parties hold short vectors and locally compute output = (sparse matrix A) · (their vector), where A has exactly 10 nonzero (binary) entries per row. Each output element is the XOR-sum of 10 randomly located 128-bit values — one XOR per random read, roughly 10 reads per output element, across a vector that can be hundreds of megabytes.

Now you're ready: LPN is "one XOR per random read" — almost no computation per byte moved, which is the textbook definition of memory-bandwidth-bound.
7Reading the roofline: compute-bound vs memory-bound (quick recap)▾

You already know this shape from tiering work: operation intensity (work per byte moved) determines whether you're capped by peak compute or by bandwidth. SPCOT's intensity is high — one seed generates a whole subtree of AES/ChaCha work. LPN's intensity is low — one XOR per random 16-byte fetch.

8CSR — how the sparse LPN matrix is actually stored▾

Compressed Sparse Row format needs three arrays: values, column indices, and row pointers. Because every LPN matrix entry is binary and every row has exactly 10 nonzeros, Ironman drops the value array entirely and keeps only Colidx (which columns are nonzero) — the index sequence that gets sorted for locality.

The whole story in one place

Ironman in a nutshell

One bottleneck, two very different root causes, one accelerator with two matching halves.

Profiling SOTA hybrid HE/MPC frameworks (CrypTFlow2, Bolt) shows OT Extension eating 51–69% of total inference time — more than the linear layers, more than the HE computation. Inside OTE, the two phases behave nothing alike: SPCOT generates hundreds of GGM trees via AES calls and is compute-bound — it sits near the CPU's peak AES throughput on a roofline plot. LPN does a sparse matrix-vector multiply with only one XOR per random access (10 such reads per output element) and is memory-bandwidth-bound — it sits down on the DRAM bandwidth line, far from peak compute.

Ironman answers each half separately. For SPCOT, a hardware-aware m-ary GGM tree expansion paired with a ChaCha8 PRG (which outputs 512 bits per call instead of AES's 128) cuts PRG calls 6× with no extra area. For LPN, an Ironman-NMP architecture puts small compute units on the DIMM buffer chip, exploits DRAM rank-level parallelism, and uses an offline index-sorting algorithm plus a small memory-side cache to turn LPN's random accesses into something closer to sequential ones.

The payoff: 39.2–237.4× OT throughput over a full-thread CPU baseline, and 2.1–3.4× end-to-end latency reduction across CNN and Transformer PPML frameworks — for roughly 3% of one DRAM chip's die area.

🍯 Key takeaways

  • OT Extension, not the neural network, is the bottleneck in modern PPML — 51–69% of runtime.
  • SPCOT (GGM tree growth) is compute-bound; LPN (sparse matmul) is memory-bandwidth-bound — they need opposite fixes.
  • Swapping AES for a longer-output ChaCha8 PRG and using a 4-ary (not 2-ary) tree gives a 6× SPCOT speedup for free in area.
  • LPN's index matrix is fixed forever, so it can be sorted once, offline, for permanent locality gains — no runtime hotness tracking needed.
  • Ironman-NMP puts a memory-side cache + rank-level compute on the DIMM buffer chip — under 3mm², under 1.5W.
  • Result: 39.2–237.4× OT throughput, 2.1–3.4× end-to-end PPML latency — but communication, not OT, becomes the new bottleneck on slow networks.
Six everyday pictures

How to think about Ironman

Each stands alone, each ends with where it breaks — several deliberately contrast with the dynamic hot-page tracking you already know from memory tiering.

The core split · Compute vs memory bound

A machinist and a mail-sorter

A machinist limited only by how fast her lathe spins can be sped up with a faster lathe — that's SPCOT: give it a leaner PRG and it goes faster. A mail-sorter limited by how fast letters arrive at random slots can't be sped up by sorting faster — she needs the letters delivered in a better order. That's LPN: no amount of extra ALU helps until the access pattern improves.

Where it breaks: the lathe analogy hides that SPCOT's "faster lathe" (ChaCha8) only pays off when paired with a wider tree — the two-part fix (§4) is co-designed, not independent.
GGM tree · m-ary expansion

A photocopier that makes 4 copies at once

A 1-to-2 copier doubles your stack each pass; a 1-to-4 copier quadruples it, reaching the same pile in fewer passes. That's the m-ary tree: a 4-ary GGM tree needs only 4 PRG calls to make 4 children where a 2-ary tree needed 6 (two levels of doubling). ChaCha8 is a copier that also happens to physically produce 4 sheets per pass — pairing the two compounds the saving.

Where it breaks: a real copier keeps getting cheaper with more output slots; ChaCha8 tops out at 4 blocks/call, so going from 4-ary to 32-ary barely helps (3.86× vs 2-ary, not 16×) — and it increases the OT communication needed per level.
Near-memory processing

A pantry with its own sous-chef

Instead of a chef hauling every ingredient across the kitchen to a distant counter, you station a helper right at the pantry door who does the simple prep (measuring, mixing) on the spot. Ironman-NMP puts small XOR logic on the DIMM buffer chip itself — right where the LPN vector lives — so most of the "random reads + XOR" work never crosses the memory bus at all.

Where it breaks: the paper is explicit that this needs custom logic — commercial PIM like UPMEM (general-purpose cores, too slow for ChaCha) or Samsung HBM-PIM (AI-specialized, wrong primitives) don't quite fit; you'd still need a custom ASIC on the buffer chip.
Index sorting · a permanent, not adaptive, fix

A grocery list re-ordered by aisle — once, forever

If your store's aisle layout never changes, you can sort your recurring shopping list by aisle a single time and reuse that order every week — no need to re-observe your habits. LPN's index matrix A is fixed for the lifetime of the protocol, so Ironman's column-swap + row-look-ahead sort runs once, offline, and every subsequent LPN pass gets the locality for free.

Where it breaks — deliberately, for you: this is the opposite of the hot-page tracking in TPP/HeMem/Memtis, where access patterns shift at runtime and must be re-measured continuously. LPN's "hotness" is a static, protocol-level property, not a workload-dependent one — there's no equivalent of a cold page suddenly turning hot.
Unified sender/receiver hardware

A turnstile that spins both ways

Rather than build one gate for entering and a separate one for exiting, a single turnstile handles both directions — the mechanism (an XOR tree) is identical, only the direction data flows through it differs. Ironman's Unified Unit is exactly that: as sender it's a Key Generator (compute both even/odd sums), as receiver it's a Message Decoder (recover just the needed sum) — same silicon.

Where it breaks: a turnstile is symmetric by nature; here the receiver's Node Buffer must also store nodes recovered from the sender's XOR sum, a slightly larger buffer than the sender needs — a small, deliberate asymmetry the design absorbs rather than eliminates.
DRAM rank-level parallelism

Every checkout lane open at once

A store with four registers but only one open lane serves customers no faster than a single-lane store. Ironman activates every rank in a DIMM concurrently and gives each its own small compute unit, so the aggregate internal DRAM bandwidth — not just the narrow external bus — becomes available to LPN.

Where it breaks: real checkout lanes serve independent customers; DRAM ranks here are pre-loaded with an even row-wise partition of matrix A so each rank does equal work — an offline load-balancing step the grocery-store analogy skips.
The full explanation

How it actually works

Section by section, with the paper's key diagrams rebuilt for a quick read.

1 · Locating the bottleneck

Profiling CrypTFlow2, Cheetah, and Bolt across CNN and Transformer models shows OT Extension consuming 51–69% of end-to-end latency — more than HE computation, linear layers, or online communication combined. Splitting OTE's own time (Fig. 1b) shows SPCOT and LPN as the two costs that matter; a roofline plot of both (Fig. 1c) shows SPCOT hugging peak AES throughput while LPN sits far below it, near the DRAM bandwidth roof.

2 · Hardware-aware m-ary tree expansion

Growing a GGM tree to ℓ leaves as a 2-ary tree costs 2ℓ−1 PRG calls. Generalizing to an m-ary tree (each node fans out to m children instead of 2) costs only:

ops(m) = m · (ℓ−1) / (m−1)     # fewer calls as m grows, but with diminishing returns

Separately, swapping the PRG from AES (128-bit output) to ChaCha8 (512-bit output — 4 blocks per call) divides the call count by up to 4×, since one ChaCha8 call can directly produce a 4-ary node's worth of children. The two optimizations compound: 4-ary tree + ChaCha8 needs only 1 call for the same 4-leaf tree that costs 2-ary+AES 6 calls.

🌱
The catch: m-ary trees need (m−1)-out-of-m OT instead of plain 1-out-of-2 OT. The paper shows this is built from the same m-node GGM tree at no extra hardware cost — just log₂m OT correlations per level.

3 · Scheduling the tree — hybrid depth/breadth-first

A pure depth-first GGM expansion stalls the ChaCha8 pipeline for its full latency (8 cycles) between each parent-to-child step, since child nodes depend on their parent. Pure breadth-first avoids stalls but needs buffer space proportional to the whole tree (O(ℓ) vs O(log ℓ)). Ironman's Hybrid GGM-tree Expansion fills idle pipeline slots with nodes from other, independent trees when the current tree doesn't have enough ready work — reaching 100% ChaCha8 core utilization while keeping the small depth-first buffer footprint.

4 · LPN as near-memory processing

LPN is a sparse matrix-vector multiply with 10 nonzeros per row, each read costing one XOR — a compute-to-memory-access ratio far too low for a normal cache to help once the working set grows large: storing the receiver's vector r together with matrix A exceeds 900 MB once the OT output size passes 2²⁴. Ironman's Ironman-NMP sits on the DIMM buffer chip: it partitions matrix A row-wise across ranks, broadcasts the shared vectors once, and lets each rank compute its own partial XOR-sum locally and in parallel — exploiting DRAM's internal bandwidth instead of the narrow external bus.

5 · The unified sender/receiver architecture

Sender and receiver both need an XOR tree to combine ChaCha8 outputs — the sender computes both even and odd sums (Key Generator mode, two XOR-tree passes), the receiver computes only the one sum it's missing and stores the recovered node (Message Decoder mode, one pass). Because the difference is dataflow, not logic, one Unified Unit serves both roles — critical since MPC protocols frequently swap which party is sender vs receiver mid-computation.

Follow the numbers, step by step

Worked examples

Four traces using the paper's own numbers — tree arithmetic, the m-ary sweet spot, the hardware budget, and why a 237× speedup on OT still lands at "only" 2–3× end-to-end.

① Counting PRG calls for a 4-leaf tree

Using ops(m) = m·(ℓ−1)/(m−1) with ℓ = 4 leaves, verify the four configurations in Fig. 6.

  1. 2-ary + AES: ops(2) = 2·3/1 = 6 AES calls.
  2. 4-ary + AES: ops(4) = 4·3/3 = 4 AES calls.
  3. ChaCha8 halves the 2-ary count (its 512-bit output covers a 2-ary node in one call): 6/2 = 3 calls.
  4. ChaCha8 quarters the 4-ary count (a 4-ary node's 4 children fit in one 512-bit call): 4/4 = 1 call.
  5. Net reduction, 4-ary+ChaCha8 vs 2-ary+AES: 6/1 = 6× — with the same ChaCha8 silicon in every case.
🍯
Insight: the two optimizations are genuinely independent multipliers — tree arity reduces AES-equivalent calls, PRG choice reduces calls-per-node — which is why they compound instead of overlapping.

② Why 4-ary, not 32-ary, at real scale (ℓ = 4096)

Using the same formula with the paper's ℓ = 4096 parameter (the 2²⁰-OT set), compare fan-outs.

  1. 2-ary + AES baseline: ops = 2·4095/1 = 8190 calls.
  2. 4-ary + ChaCha8: ops(4) = 4·4095/3 = 5460 AES-equivalent, ÷4 for ChaCha8 = 1365 calls → 8190/1365 = 6.0× reduction.
  3. 32-ary + ChaCha8: ops(32) = 32·4095/31 ≈ 4226 AES-equivalent; ChaCha8 still only covers 4 children/call, so ÷4 = ≈1057 calls → 8190/1057 ≈ 7.75× reduction.
  4. Marginal gain from 4-ary → 32-ary: only 7.75/6.0 ≈ 1.3× more — because ChaCha8's 4-block cap means every m ≥ 4 gets the same ÷4 discount; the AES-equivalent term itself barely shrinks past m=8.
  5. But communication grows with m (Fig. 7b,c): more fan-out means more (m−1)-out-of-m OT correlations per level. Verdict: 4-ary is the sweet spot — near-maximal compute reduction, minimal communication overhead.
💡
This reproduces the paper's own stated ratios almost exactly: 4-ary vs 2-ary (both ChaCha8) ≈ 2.99×, 32-ary vs 2-ary (both ChaCha8) ≈ 3.86× (§4.1, Fig. 7a).

③ Tallying the hardware budget

Is a per-DIMM NMP unit actually cheap next to a real DRAM chip?

  1. One ChaCha8 core (45nm): 0.215 mm², 45.33 mW.
  2. Full Ironman-NMP PU, 256 KB memory-side cache: 1.482 mm² total, 1.301 W.
  3. Full Ironman-NMP PU, 1 MB memory-side cache: 2.995 mm² total, 1.430 W.
  4. As a fraction of one DRAM chip (~100 mm²): 1.482/100 ≈ 1.5%; 2.995/100 ≈ 3.0%.
  5. As a fraction of an LRDIMM's power budget (~10 W): 1.301/10 ≈ 13%; 1.430/10 ≈ 14% — modest, and it removes far more CPU-side power than it adds.
💡
That's the punchline: a 39–237× throughput jump costs about 1.5–3% of one DRAM chip's die area, sitting on the buffer chip rather than adding a new die.

④ Why 237× on OT becomes "only" 2–3× end-to-end

If OT extension is 51–69% of runtime and Ironman speeds it up by up to 237×, why isn't the application 237× faster? Amdahl's law gives the intuition — though not an exact bound.

  1. Amdahl's law: total speedup = 1 / [(1 − f) + f/S], where f = fraction of time spent on OT, S = OT's speedup.
  2. Illustrative case: f = 0.6 (midpoint of 51–69%), S = 100 (mid-range OT speedup). New OT time = 0.6/100 = 0.006; remaining time = 0.4. Total = 0.406 of original → speedup = 1/0.406 ≈ 2.46×.
  3. This lands inside the paper's reported 2.1–3.4× range for LAN settings — but the fit is only approximate: taking f at its reported maximum (0.69) and letting S→∞ caps speedup at 1/(1−0.69) ≈ 3.23×, yet the paper reports up to 3.40×. The gap means f (and the achievable S) varies by benchmark — this framing is a useful intuition pump, not a derivation that tightly bounds the paper's own numbers.
  4. On WAN (low bandwidth, high round-trip latency), the "everything else" term grows — communication that used to be hidden behind OT's slowness is now the visible bottleneck, which is consistent with why Table 5's WAN speedups (1.3–1.7×) trail the LAN speedups (2.9–3.4×).
🌱
This Amdahl's-law framing is mine, not the paper's explicit derivation — it's built from the paper's own stated OT-time fraction (§1, Fig. 1a) and measured speedup range (§6.5) to give intuition for the order of magnitude, but treat it as approximate: the paper's peak measured speedup (3.4×) slightly exceeds the naive single-f cap.
Test yourself

Practice problems

Try each before opening the answer. Every one ends with the misconception it's checking for.

Problem 1 · easy
Ironman gets up to 237.4× OT throughput, but the paper reports only 2.1–3.4× end-to-end PPML speedup. Is Ironman "underperforming" its own headline number?
Show answer
No — this is Amdahl's law, not underperformance. OT was only 51–69% of total runtime, so even a very large OT speedup gives diminishing total-speedup returns: as an intuition (not an exact bound), total speedup is roughly on the order of 1/(1−f) ≈ 2–3×. The other 30–50% of the time (linear layers, HE, online communication) is untouched by Ironman and now dominates. (This is approximate — the paper's own reported range slightly exceeds the naive cap computed from a single f value, since f and achievable OT speedup vary across benchmarks.)Misconception: assuming a component-level speedup transfers 1:1 to end-to-end speedup, regardless of what fraction of total time that component occupied.
Problem 2 · medium
A 32-ary GGM tree reduces PRG calls more than a 4-ary tree by the formula alone. Why does Ironman still choose 4-ary?
Show answer
Two reasons. First, ChaCha8 only produces 4 blocks per call, so any m ≥ 4 gets the same ÷4 discount — the AES-equivalent term itself has diminishing returns past m≈8 (32-ary only reaches ≈3.86× vs 2-ary/ChaCha, compared to 4-ary's ≈2.99×). Second, larger m needs more (m−1)-out-of-m OT correlations per level, which increases online communication and latency — a real cost in bandwidth-limited deployments.Misconception: that a bigger fan-out/branching factor is free just because the compute formula looks favorable — real designs trade compute against communication.
Problem 3 · hard
LPN's index matrix A is sorted once, offline, and reused forever. In OS memory tiering, page hotness must be re-measured continuously (e.g., via PEBS sampling in TPP/Memtis). Why the difference?
Show answer
A's sparsity pattern is a fixed structural property of the LPN-based protocol — it's chosen at protocol-parameter setup and never changes across executions, so any reordering computed once stays valid forever. Page hotness, by contrast, is a property of a running program's actual, unpredictable memory access behavior, which shifts across phases — there's no protocol guarantee it stays fixed, so tiering systems must keep re-measuring.Misconception: conflating "sparse and irregular" (a structural property, fixable once) with "dynamically hot" (a runtime behavior, requiring continuous tracking) just because both eventually get described as "improving locality."
Problem 4 · medium
SPCOT and LPN both do "a lot of AES-like operations," yet one is compute-bound and the other memory-bound. What's the actual difference?
Show answer
Operation intensity — work done per byte moved. SPCOT's GGM tree expands one small seed into an exponentially large tree: a huge number of PRG calls happen per byte of external data touched, so it's limited by how fast the PRG silicon runs. LPN does exactly one XOR per random 16-byte read from a huge index vector: minimal computation per byte moved, so it's limited by how fast those bytes can be fetched from DRAM.Misconception: assuming that because both operations "use AES," they must have the same performance bottleneck — the roofline position depends on the ratio of compute to memory traffic, not on which primitive is used.
Problem 5 · medium
Going from a 1 MB to a 2 MB memory-side cache costs 2.21× more area but yields "limited improvement" in hit rate. Why doesn't the bigger cache help more?
Show answer
Once the sorted index sequence's useful working set is mostly captured by ~256 KB–1 MB, additional cache capacity mostly holds data that won't be re-referenced before eviction anyway — diminishing returns on hit rate, just like any cache once past its workload's effective working-set size. Combined with the area/power cost of doubling SRAM, the paper settles on 1 MB for small parameter sets and 256 KB for large ones rather than always maximizing cache size.Misconception: "bigger cache is always better" — ignoring that hit-rate gains saturate once the cache exceeds the reused working set, while area/power cost keeps growing linearly.
Problem 6 · hard
CPUs get AES essentially free via AES-NI, yet Ironman's custom hardware prefers ChaCha8. Isn't that a step backward?
Show answer
No — the two environments have different constraints. On a CPU, AES-NI's dedicated instruction makes AES calls cheap in a way ChaCha8 can't match without its own instruction. On custom ASIC/NMP silicon, that's a level playing field — you design a core for whichever PRG helps most, and ChaCha8's longer 512-bit output directly enables the m-ary tree optimization (4 children per call) while also being more power-efficient per output block (Table 2: 4.49× perf/area, 3.09× power/block vs AES). The "free" AES-NI advantage is a CPU-specific artifact that disappears once you're building your own logic.Misconception: assuming a hardware acceleration advantage on one platform (AES-NI on CPUs) automatically transfers to a different platform (custom ASIC) with different design freedoms.
Problem 7 · easy
Does the Unified Unit mean Ironman needs twice the XOR-tree hardware to support both sender and receiver roles?
Show answer
No — it's the same XOR tree used both ways. As sender, it runs twice (computing both even and odd sums); as receiver, it runs once (recovering only the missing sum). The Node Buffer contents differ slightly, but no duplicate tree is built.Misconception: assuming "supports two different protocols" implies "needs two copies of the hardware," when the two protocols actually share almost all their logic and differ mainly in dataflow.
Problem 8 · medium
Does moving LPN to near-memory processing eliminate the network communication bottleneck in private inference?
Show answer
No — NMP only accelerates the local computation of generating COT correlations. The generated correlations still need to travel from the NMP unit back to the CPU, and Ironman overlaps that generation with streaming results back over the internal DDR bus to hide most of that internal transfer cost — but that is a local, on-node data path, separate from the actual OT protocol's network round trips between the two parties. Those genuine sender-receiver network hops are untouched by NMP. This is exactly why WAN speedups (1.3–1.7×) trail LAN speedups (2.9–3.4×) — once local compute is fast, party-to-party network communication becomes the visible limiter.Misconception: treating "accelerator" as synonymous with "removes all bottlenecks," and conflating the internal NMP-to-CPU DDR transfer that Ironman overlaps with the actual sender-receiver network transmission, which it does not touch.
Quick answers

Frequently asked questions

Tap any to expand.

Q1What exactly does Ironman accelerate?▾
The OT Extension (OTE) phase of PCG-style oblivious transfer — specifically its two sub-steps, SPCOT (GGM tree generation) and LPN (sparse matrix-vector multiply). It doesn't touch the neural network's linear layers or the online OT protocol itself.
Q2Why does OT dominate PPML runtime if the actual math (matmuls, convolutions) is done with HE?▾
Nonlinear activations (ReLU, GeLU, Softmax) are cheaper and more accurate to compute via secret-shared comparisons built on OT, rather than approximating them in HE. Every nonlinear call needs a batch of pre-generated OT correlations, and generating those correlations at scale is what eats 51–69% of runtime.
Q3Why is AES used to build a GGM tree at all — isn't AES for encryption?▾
Any strong pseudorandom generator (PRG) works; AES is chosen on CPUs purely because AES-NI makes it nearly free per call. The security property needed is that the PRG's output looks random given the seed — AES-as-PRG and ChaCha-as-PRG both satisfy this at 128-bit-plus security levels.
Q4Why not just throw more CPU threads or a GPU at OTE instead of building custom hardware?▾
The paper tried a GPU (A6000): it gets a 5.88× throughput gain, mostly because a GPU's larger L1/L2 caches absorb more of LPN's random accesses. But Ironman still beats the GPU by 40.31× in latency and 84.5× in power, because LPN's core problem — a bandwidth wall, not a compute deficit — isn't fixed by adding more ALUs, only by moving compute closer to the memory.
Q5Is Ironman's "memory-side cache" the same idea as an ordinary CPU cache?▾
Functionally similar (it caches recently-touched entries of the error vector to avoid DRAM round-trips) but tiny and purpose-built — 256 KB or 1 MB per rank module, sized specifically against LPN's access pattern after offline index sorting, not a general-purpose cache serving arbitrary code.
Q6How can permuting the LPN input vector not break correctness?▾
The LPN hardness assumption only requires that both parties use the same input vector — it says nothing about the order of its entries. Column swapping just relabels which array position holds which logical vector element; both sender and receiver apply the same fixed permutation, so the protocol's output is unaffected.
Q7Could this run on off-the-shelf PIM hardware like UPMEM or Samsung HBM-PIM?▾
Not directly. UPMEM's cores are general-purpose but too slow for ChaCha8's throughput needs; Samsung HBM-PIM has specialized logic tuned for AI workloads (matrix multiply/accumulate), not the XOR-tree and PRG operations Ironman needs. The paper concludes a custom ASIC on the buffer chip is required, though the overall NMP architecture (compute on the buffer chip, rank-level parallelism) is the same idea these commercial systems use.
Q8Why does Ironman decouple and overlap SPCOT and LPN?▾
The random vector e and fixed matrix A used in LPN don't depend on SPCOT's output u — they can be generated/loaded independently. So LPN's memory-bound work and SPCOT's compute-bound work can run concurrently on separate hardware (DIMM-NMP for SPCOT, Rank-NMP for LPN), hiding one behind the other.
Q9Does Ironman change what OT protocols compute, or just how fast?▾
Just speed. Ironman implements the same PCG-style OTE math (Ferret's protocol, specifically) — its m-ary tree and NMP architecture are algorithmic/hardware optimizations of existing correct protocols, not new cryptography.
Q10Why do Transformer models benefit more than CNNs (2.9–3.4× vs 2.1–2.7×)?▾
Transformer nonlinearities (Softmax, GeLU, LayerNorm) are more complex than a CNN's ReLU and consume proportionally more OT correlations per layer — so OT was a larger fraction of Transformer runtime to begin with, giving Ironman's OT speedup more total time to reclaim.
Q11What did the paper leave unaddressed?▾
The evaluation is on multiprogrammed, two-party PPML inference; extending to malicious-security protocols, more than two parties, or training (rather than inference) workloads isn't covered. Communication cost under low bandwidth remains the dominant limiter after Ironman's fix, as the WAN results show.

Glossary, results, and provenance

Every term in one place, then where the numbers came from.

Core terms
SPCOTSingle-Point Correlated OT — the GGM-tree-growing sub-protocol; compute-bound.
LPN encodingThe sparse matrix-vector multiply that expands short correlations into many; memory-bandwidth-bound.
GGM treeA tree grown from one seed via repeated PRG expansion; m-ary variants fan out to m children per node.
m-ary tree expansionGrowing a GGM tree with fan-out m > 2 to reduce total PRG calls, at the cost of needing (m−1)-out-of-m OT.
ChaCha8 PRGA stream-cipher-based PRG producing 512-bit (4-block) output per call — enables m-ary expansion in fewer calls than AES.
Ironman-NMPThe near-memory processing unit on the DIMM buffer chip, combining a ChaCha8-based SPCOT engine with rank-level LPN compute.
Index sorting (column swap + row look-ahead)An offline reordering of LPN's fixed sparse matrix to improve spatial/temporal locality of its accesses.
Unified UnitThe shared XOR-tree hardware that serves as Key Generator (sender) or Message Decoder (receiver).
Supporting terms
COT / Δ-correlationCorrelated OT: sender's two outputs differ by a fixed secret Δ; cheaper than plain OT to generate in bulk.
PCG-style OTEOT Extension with sub-linear communication, at the cost of higher local computation — the style this paper targets.
CRHFCorrelation-Robust Hash Function; converts COT outputs into standard OT outputs for the online phase.
CSR (Colidx-only)Compressed Sparse Row storage, reduced to just column indices since LPN's matrix entries are all binary.
DIMM-NMP / Rank-NMPThe two module types inside each Ironman-NMP PU — DIMM-level for SPCOT, per-rank for LPN's parallel XOR-sums.
Rank-level parallelismActivating multiple DRAM ranks concurrently, each with its own small compute unit, to use internal DRAM bandwidth.
Roofline modelA performance/intensity plot separating compute-bound and memory-bound regions — used here to justify the two-part design.
Marginal ops / m-ary reductionThe diminishing-returns curve of PRG-call savings as tree fan-out m grows past ChaCha8's 4-block cap.
